# Как проектировать тему для изучения и повторения

База рассчитана на Java middle, который хочет понимать причины поведения и уверенно отвечать на уточнения senior-уровня. У страницы две задачи: объяснить механизм при первом чтении и помочь восстановить его из памяти позже. Глубину сохраняем; обязательные задачи после каждого ответа убираем.

## На чём основана подача

Исследование учебного формата проверено 02.10.2026. Источники ниже относятся к обучению в целом. Перенос принципов на Java KB — наше авторское решение; конкретные числа шагов и карточек исследованиями не установлены.

| Что поддерживает источник | Как применяем в базе |
|---|---|
| [IES / WWC, Organizing Instruction and Study to Improve Student Learning, 2007](https://ies.ed.gov/ncee/wwc/PracticeGuide/1): связывать конкретные и абстрактные представления, сочетать схему с объяснением, задавать вопросы о причинах. | Сначала знакомая ситуация, затем механизм на её объектах. Схема показывает связи или изменение состояния; текст объясняет, почему это происходит. |
| [Chandler & Sweller, 1992](https://bpspsychub.onlinelibrary.wiley.com/doi/10.1111/j.2044-8279.1992.tb01017.x): в экспериментах согласованное размещение взаимосвязанных частей инструкции помогало по сравнению с разделёнными источниками. | Код, условия опыта и его результат находятся рядом. Ключевая строка объяснена комментарием; читателю достаточно страницы, чтобы понять доказательство. |
| [Roediger & Karpicke, 2006](https://www.psychologicalscience.org/journals/psychological-science/j.1467-9280.2006.01693.x/): воспроизведение изученного текста по памяти улучшало результат отсроченной проверки по сравнению с повторным чтением. | Карточка сначала показывает вопрос. При повторении читатель пробует ответить, затем раскрывает ответ и сравнивает объяснение. Дополнительная задача нужна только для отдельной полезной развилки. |

Эти работы поддерживают объяснение, осмысленную иллюстрацию и самостоятельное воспроизведение. Они не доказывают, что любая схема полезна или что каждой карточке нужны несколько задач. Рекомендации IES также включают чередование разобранных примеров с самостоятельным решением; в нашей базе его дают выборочные разборы и отдельные практикумы.

## Перед написанием: исследовать и факт, и способ его объяснить

1. Составь карту поведения по документации и исходникам. Укажи версию, значения по умолчанию и условия, меняющие результат: флаги компилятора, подключённую инфраструктуру, момент вызова.
2. Прочитай объяснение в книге или хорошем курсе. Запиши, что делает его понятным: выбранный пример, порядок причин, сравнение вариантов. Само наличие ссылки на книгу ещё не исследование подачи.
3. Сформулируй центральный вопрос и спланируй доказательство. Для каждой важной развилки отметь, что увидит читатель и какие строки кода позволят объяснить результат.
4. Выбери схему под вопрос. Для IoC полезен граф ссылок, для времени жизни — повторные обращения во времени, для инициализации — изменение состояния объекта, для AOP — путь вызова через оболочку.
5. Сверь вопросы собеседования с картой. Каждый пункт должен попасть в урок, карточку, дополнительный разбор или явно указанную соседнюю тему.

Карту и причины выбора подачи держи в рабочих заметках. Проверки фактов выполняй до написания вывода.

## Начало страницы: понятная опорная мысль

В начале `.lesson` можно добавить `div.note.tip` с 3–5 связанными предложениями. Он помогает повторить знакомую идею и даёт ориентир для первого чтения. После него читатель должен представлять, что происходит с конкретными объектами.

Плохо: «BeanDefinition — рецепт, BeanFactory — сборка, Context — окружение». Это словарь.

Лучше: «Сервис получает готовое подключение к банку. Spring выбирает и подготавливает его по конфигурации, затем передаёт ссылку в конструктор. При неожиданном поведении проследи, какой объект получил сервис». Названия механизмов раскрываются дальше вместе с причиной их появления.

## Основной урок: объяснение с доказательством

Сохраняй ориентиры `quality.md`: 4–7 шагов, типичный шаг из 3–6 абзацев по 2–4 предложения плюс уместное доказательство. Они помогают заметить недообъяснённое место. Каждый шаг связывает утверждение, механизм, наблюдение и практическое следствие.

Демо должно быть понятно на странице. В `examples/` допустимо вынести imports, обвязку запуска и повторяющуюся настройку. Если результат сравнивает Full и Lite, оба варианта и сравниваемые вызовы должны быть показаны рядом с выводом. Ссылка на файл дополняет объяснение, а не уносит его.

Один опыт отвечает на один вопрос. Разные опыты из общего файла показывай в соответствующих шагах и помечай фрагменты вывода. Условия, меняющие исход, показывай вместе: например, один код с `-parameters` и без него. Комментарии поясняют ключевые строки. Абзац после вывода связывает наблюдение с применением, вместо повторения каждой строки.

Пиши обычными глаголами: «Spring выбирает», «метод создаёт», «сервис получает ссылку». Названия API оставляй точными. «Перехватывает calls» замени на «перехватывает вызовы»; «inspect BeanDefinition» — на «посмотреть описание бина». Сначала скажи, что происходит и почему; ограничение добавь там, где оно меняет решение.

«Под капотом» хранит дополнительную глубину: путь по исходникам и детали реализации. Причина основного результата остаётся в открытом уроке. Итог в конце помогает восстановить несколько ключевых связей через месяц.

## Карточка для повторения

Ориентир: для `freq: 3` — 4–6 карточек, для остальных — 3–4. Вопросы берутся из карты покрытия, самые частые идут первыми.

Каждая карточка содержит естественный вопрос, ответ обычной речью на минуту и senior-уточнения, которые добавляют новую причину или границу. При повторении читатель отвечает до раскрытия. Это уже самостоятельное воспроизведение; отдельные задачи после каждого ответа избыточны.

`div.check` остаётся необязательным. Добавляй его для полезной развилки: изменится ли результат после изменения условия, как отличить две причины ошибки, какой компромисс выбрать. Урок должен объяснять механизм без прохождения проверок. У отдельного практикума сохраняются его требования.

## Проверка автора

Закрой названия API и перескажи, что случилось с объектами. Затем объясни результат по коду на самой странице и ответь на неудобное уточнение. Если приходится уходить в другой файл за причиной вывода, верни нужный фрагмент в урок.

После этого пройди `review.md` целиком. В браузере проверь также пробелы внутри `pre`: отступы HTML не должны менять отображаемый и копируемый код. Прохождение валидатора подтверждает структуру; качество объяснения автор проверяет отдельно.
