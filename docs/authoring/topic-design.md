# Как спроектировать тему, которую хочется читать

Для Java middle, который идёт к senior, важнее связная модель, чем число блоков. Страница должна работать в двух режимах: быстро вернуть тему в память и позволить спокойно разобраться в причинах поведения.

## Перед написанием

1. Прочитай первоисточник и найди объяснение в книге или хорошем курсе. Список интервью-вопросов используй только как проверку покрытия; ответы сверяй с документацией и исходниками.
2. Сформулируй центральный вопрос: какое поведение станет понятно после этой страницы? Собери карту покрытия, отметь соседние темы и версии.
3. Выбери подачу под механизм. Для IoC важен граф объектов, для scopes — идентичность и время жизни, для lifecycle — изменение состояния, для AOP — путь вызова. Не копируй одинаковый сценарий в каждую тему.

## Два режима чтения

В начале `.lesson` допустим короткий `div.note.tip`: одна связная модель в 3–5 предложениях, без списка терминов. Читатель, который повторяет, узнаёт знакомую идею; тот, кто изучает впервые, получает ориентир. Термины раскрываются ниже. Это не замена уроку.

Основная часть — история от конкретного вопроса к устройству и границам. Число шагов выбирай по содержанию; ориентир 4–7. Внутри шага нужна причина, а не обязательная последовательность блоков. Некоторые мысли лучше доказывает схема, другие — сравнение, маленький пример или объяснение исходников. Не добавляй код к каждому абзацу.

Раздел «Под капотом» оставляет дополнительный уровень глубины: детали реализации, которые полезны senior, но мешают первому чтению. Если деталь нужна для понимания основного механизма, она должна быть в самом уроке.

В конце — несколько связей, которые нужно удержать через месяц. Не повторяй этот итог в каждой карточке.

## Вопросы без экзамена на каждом экране

Карточка задаёт один естественный вопрос. Основной ответ — речь на собеседовании, затем senior-уточнения с новыми причинами и границами. Обычно хватает 3–6 карточек; выбирай по карте покрытия, а не по квоте.

`div.check` необязателен. Добавляй короткий разбор только при наличии полезной развилки: почему код ведёт себя иначе, чем кажется; как различить две причины ошибки; какой компромисс ты выберешь. Не требуй 2–4 проверки на каждый вопрос и обязательные «задачу»/«ревью» на каждую тему. Обычная карточка с хорошим ответом уже полезна для повторения. Практикумы остаются отдельным типом.

Демо нужно автору для проверки факта, а читателю — для наблюдения механизма. Это разные цели. Полный запускаемый пример можно хранить рядом в `examples/` и ссылаться на него, а на странице показывать только значимые строки. Явно обозначай фрагменты и версии. Вывод должен быть взят из запуска полного примера.

## Проверка качества

Перескажи объяснение без терминов. Затем нарисуй механизм и ответь на неудобное уточнение. Если это не получается, добавь недостающую причинную связь. Если получается только после чтения десяти проверок, перенеси объяснение из проверок в урок.

Число слов, схем и задач помогает заметить слабое место, но не определяет качество. Не раздувай текст ради валидатора и не сокращай глубину ради удобного трафарета. Проверка автора по `review.md` остаётся обязательной: читателю не нужно видеть всю служебную работу.
