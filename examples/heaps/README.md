# Heaps: очередь платежей и локальный порядок

Четыре независимых single-file демо, JDK 21, без зависимостей и сборки.
Запуск из корня репозитория:

```sh
java examples/heaps/BinaryHeapDemo.java
java examples/heaps/PriorityQueueDemo.java
java examples/heaps/MutablePriorityDemo.java
java examples/heaps/TopKDemo.java
```

Проверено на JBR 21.0.11+10-b1163.116.

BinaryHeapDemo — авторская min-heap на заранее выделенном массиве int.
При заполнении offer бросает IllegalStateException, на пустоте peek/poll —
NoSuchElementException. Это отличается от растущей PriorityQueue и её null
при пустом peek/poll. Вывод состоит из четырёх блоков:

- Вставка 5 в [10,30,20,70,40,50,60]: последний индекс 7, затем подъём через 3,
  1 и 0. Состояния печатаются после добавления и каждого обмена.
- Извлечение 5: последний 70 занимает корень, size уменьшается до 7,
  спуск проходит через 1 и 3. Неиспользуемый хвост массива не входит в snapshot.
- Построение из [7,6,5,4,3,2,1]: спуски от 2,1,0 дают [1,3,2,4,6,7,5].
  Массив стал кучей, но не отсортированным списком.
- 1023 убывающих ключа: heapify делает 2026 сравнений, отдельные offer — 8194.
  Считаются только сравнения значений в less, не границы циклов и не время JVM.
  Последовательные poll из предыдущей семиэлементной кучи дают [1,2,3,4,5,6,7].

PriorityQueueDemo сравнивает FIFO с приоритетом, обход с последовательностью poll,
равные приоритеты с явным вторым критерием sequence, equals при contains/remove
и начальную ёмкость с фактическим размером. Наблюдаемый на этом JDK порядок
равных элементов — [A,C,B]; API допускает любой порядок внутри равного приоритета.
Сравнение по priority+sequence задаёт [A,B,C]. Начальная ёмкость 1 допускает
дальнейший рост до 20. Null запрещён.

MutablePriorityDemo намеренно меняет приоритет C с 20 на 1 внутри очереди.
Peek всё ещё возвращает A:5, серия poll — [A:5,C:1,B:10]. Исправленный вариант
удаляет C до изменения и добавляет заново; получается [C:1,A:5,B:10].
Класс Job использует equals из Object, поэтому remove(c) ищет тот же объект.

TopKDemo сохраняет три наибольшие суммы в min-heap. Корень — граница отбора,
а не максимальная сумма. Массив в промежуточном kept не обязан быть отсортирован;
заключительный результат [90,70,60] сортируется отдельно. Демо использует k=3;
при переносе в общий метод нужно отдельно обработать k=0 и неверные значения k.

На [странице](../../topics/heaps.html) вывод разбит по вопросам опытов.
Названия блоков лишь разделяют консольный вывод. Приоритеты, индексы и сравнения
детерминированы для показанных входов; порядок равных элементов и обхода JDK
не является дополнительной гарантией библиотеки.
