Abstraction

Абстракция — контракт, за которым можно менять реализацию: сервис платежей знает про Gateway.pay, а не про СБП или эквайера. В Java два инструмента. Интерфейс — контракт без состояния: абстрактные методы, а с Java 8 ещё default- и static-методы, с Java 9 — private; класс может реализовать сколько угодно интерфейсов. Абстрактный класс — частичная реализация с полями, конструктором и шаблонными методами, но родитель у класса один. Default-методы появились ради эволюции: в демо старый класс-реализация, не пересобранный, работает с новым default-методом. С новым абстрактным методом он падает AbstractMethodError. Конфликты default-методов решаются тремя правилами: метод класса важнее интерфейса, более конкретный интерфейс важнее общего, а неразрешимый конфликт компилятор требует переопределить. Выбор по умолчанию — интерфейс; абстрактный класс — когда реализациям нужно общее состояние или фиксированный алгоритм с точками расширения.

Контракт вместо конкретного шлюза

Платёжный сервис работает с несколькими шлюзами: СБП, карточный эквайер, кошелёк. Если сервис вызывает SbpClient.sendTransfer и AcquirerClient.authorize напрямую, каждый новый шлюз — правка сервиса, а тест без настоящих шлюзов невозможен. Абстракция выделяет то, что важно сервису, — «провести оплату на сумму и получить результат» — в контракт Gateway. Реализации прячут детали за ним, сервис зависит от контракта, а не от реализаций; выбор реализации во время выполнения — полиморфизм из Polymorphism.

Хорошая абстракция названа и сформулирована в терминах задачи, а не реализации: pay(Payment), а не sendHttpPost(Map). Она не протекает: вызывающему не нужно знать, что под ней HTTP, чтобы правильно обработать ошибки, — поэтому шлюз переводит SocketTimeoutException в свой GatewayUnavailable. И она минимальна: интерфейс из двадцати методов, половину которых каждая реализация не поддерживает, нарушает принцип разделения интерфейсов (ISP) и ведёт к UnsupportedOperationException, как в Inheritance & Composition.

Интерфейс и абстрактный класс

interface Gateway {
    String pay(long amount);
    default String name() { return "gateway"; }
    default String payLogged(long amount) { return log(name() + " pays " + amount) + " -> " + pay(amount); }  // default через абстрактный
    private String log(String s) { return "[" + s + "]"; }                                                  // private-метод интерфейса
}
static abstract class RetryingGateway implements Gateway {
    private final int attempts;
    private int calls;
    protected RetryingGateway(int attempts) { this.attempts = attempts; }
    public final String pay(long amount) { /* повторяет doPay до attempts раз */ }
    protected abstract String doPay(long amount);        // точка расширения
}

Демо DispatchDemo.java. Default-метод payLogged построен на абстрактном pay и вспомогательном private-методе: интерфейс даёт поведение, не зная реализаций. Но состояния у интерфейса нет: поля интерфейса — неявно public static final константы. Абстрактный RetryingGateway хранит число попыток и счётчик вызовов, получает настройку через конструктор и фиксирует алгоритм в final-методе pay — это шаблонный метод: наследник реализует только шаг doPay и не может сломать логику повторов. Интерфейс с одним абстрактным методом — функциональный, его реализует лямбда, как в Lambdas.

Static-метод интерфейса не наследуется реализациями: Rub.cents(5) не компилируется, вызывать нужно Money.cents(5) — иначе добавление static-метода в интерфейс ломало бы классы с методом того же имени. Так устроены фабрики List.of, Comparator.comparing, Map.entry.

Какой default выполнится: три правила

interface CardGateway extends Gateway { default String name() { return "card"; } }
static class BaseGateway { public String name() { return "base-class"; } }
static class Sbp extends BaseGateway implements Gateway { ... }        // класс + default интерфейса
static class Visa implements Gateway, CardGateway { ... }              // общий + конкретный интерфейс
== which name() runs

Visa (Gateway + CardGateway):     card

Это «ромб», который Java решает без множественного наследования состояния: default-методы наследуют поведение, но не поля, поэтому классической проблемы C++ — две копии полей общего предка — нет. Ещё одно ограничение: default-метод не может переопределить метод Object — equals, hashCode, toString. Компилятор отвечает default method equals in interface Identified overrides a member of java.lang.Object: по первому правилу такой default всё равно никогда бы не выполнился — метод класса Object важнее.

Скрипт evolve.sh собирает Sbp против первой версии интерфейса и больше его не трогает — как реализацию из чужого модуля или библиотеки. Добавление default-метода совместимо: старый Sbp.class работает, вызов refund получает реализацию по умолчанию. Добавление абстрактного метода ломает: код загружается и pay работает, но вызов refund падает AbstractMethodError во время выполнения, а пересборка Sbp — ошибкой компиляции.

Именно ради этого default-методы появились в Java 8: в Collection нужно было добавить stream(), removeIf, forEach, не сломав миллионы реализаций коллекций во всех библиотеках мира. Обратная сторона видна в Inheritance & Composition: новый default достаётся реализациям молча и может обойти их проверки. Поэтому default-метод в публичном API — решение о поведении для всех чужих реализаций; его пишут через абстрактные методы интерфейса и документируют. До Java 8 эту задачу решали парой «интерфейс + скелетная реализация»: List и AbstractList, Map и AbstractMap — паттерн жив и сейчас, когда скелету нужно состояние.

Как выбрать и где абстракция вредит

По умолчанию — интерфейс: он не забирает единственного родителя, его можно добавить к существующему классу, замокать в тесте, реализовать лямбдой, обернуть прокси JDK из Annotations & Reflection. Абстрактный класс — когда у реализаций есть общее состояние или общий алгоритм, который нужно зафиксировать: шаблонный метод, как AbstractRoutingDataSource, OncePerRequestFilter в Spring или RetryingGateway в демо. Частая комбинация — интерфейс как контракт и абстрактный класс как необязательная база для реализаций. Закрытый набор вариантов — не абстракция для расширения, а sealed-иерархия из Sealed & Pattern Matching.

Абстракция стоит денег: лишний уровень косвенности, который читатель проходит, чтобы найти реальный код. Интерфейс с единственной реализацией «на будущее» — частый шум; для мока в тесте он сейчас не обязателен, Mockito мокает классы. Интерфейс оправдан, когда реализаций несколько или граница действительно важна: модуль, внешняя система, порт в гексагональной архитектуре, где ядро определяет интерфейс, а адаптер его реализует, — инверсия зависимостей из Polymorphism. Абстракция, выделенная по двум похожим кускам кода, а не по смыслу, ломается на третьем: правило трёх — обобщать, когда случаев три, — защищает от неверной абстракции, которая хуже дублирования.

Default-методы дают в Java множественное наследование, как в C++.

Наследуется только поведение, не состояние: у интерфейса нет полей экземпляра. Конфликт решают три правила — класс важнее интерфейса, конкретный интерфейс важнее общего, остальное компилятор требует переопределить, как в демо с Audited и Traced.

  • Абстракция — контракт, за которым меняется реализация; формулируется в терминах задачи, не протекает, минимальна.
  • Интерфейс: без состояния, abstract/default/static/private методы, реализаций сколько угодно, лямбда.
  • Абстрактный класс: поля, конструктор, final-шаблонный метод; родитель один.
  • Правила default: класс выигрывает, конкретный интерфейс выигрывает, конфликт — переопределить и X.super.m().
  • Default не может переопределить методы Object; static-методы интерфейса не наследуются.
  • Новый default совместим со старыми реализациями, новый абстрактный — AbstractMethodError.
  • По умолчанию интерфейс; абстрактный класс — для общего состояния и алгоритма; без лишних интерфейсов «на будущее».

На собеседовании

Чем абстрактный класс отличается от интерфейса и когда что выбрать?

Интерфейс — контракт без состояния: только константы, абстрактные, default-, static- и private-методы; класс реализует сколько угодно интерфейсов. Абстрактный класс может иметь поля, конструктор, методы с любым доступом и final-методы, но наследовать можно только один. Интерфейс выбирают для контракта и ролей, абстрактный класс — когда реализациям нужны общее состояние или зафиксированный алгоритм с точками расширения.

  • Частая пара: интерфейс + скелетная реализация (List и AbstractList).
  • Интерфейс реализуется лямбдой и проксируется JDK Proxy.
  • Интерфейс с одной реализацией «на будущее» — шум.

Зачем нужны default-методы и как решается конфликт двух default?

Default-методы позволили добавлять методы в интерфейсы, не ломая существующие реализации: так в Java 8 в Collection появились stream и removeIf. Конфликт решается правилами: метод класса важнее default; из интерфейсов выигрывает более конкретный; если два несвязанных интерфейса дают одинаковый default, класс обязан переопределить метод и может вызвать нужный через Interface.super.method().

  • Default не может переопределить equals, hashCode, toString.
  • Старый класс с новым абстрактным методом — AbstractMethodError при вызове.
  • Новый default молча достаётся всем реализациям — может обойти их инварианты.
Что напечатает вызов и почему? 
interface Named { default String name() { return "named"; } }
class Base { public String name() { return "base"; } }
class Gateway extends Base implements Named { }
System.out.println(new Gateway().name());

base. Метод класса или суперкласса всегда важнее default-метода интерфейса. Правило гарантирует, что добавление default-метода в интерфейс не изменит поведение классов, у которых метод с таким именем уже есть.

Что можно объявить в интерфейсе в современной Java?

Абстрактные методы; default-методы с реализацией (Java 8); static-методы (Java 8) — вызываются только через имя интерфейса и не наследуются; private-методы (Java 9) — общие помощники для default-методов; константы — неявно public static final. Полей экземпляра и конструкторов нет; также можно объявлять вложенные типы.

  • Static-методы интерфейса не наследуются, чтобы их добавление не ломало классы с методом того же имени.
  • Sealed-интерфейсы (Java 17) ограничивают круг реализаций.

Что такое протекающая абстракция?

Абстракция, которая заставляет вызывающего знать детали реализации, чтобы правильно ею пользоваться. Например, Gateway, бросающий SocketTimeoutException или SQLException, раскрывает HTTP или базу под собой. Шлюз должен переводить их в исключения своего уровня. Ленивые ассоциации JPA — классическая утечка: LazyInitializationException вне транзакции.

  • Закон протекающих абстракций Спольски: все нетривиальные абстракции протекают.
  • Неверная абстракция хуже дублирования — правило трёх.
