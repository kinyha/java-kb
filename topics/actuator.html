Spring Boot: Actuator

Actuator добавляет к сервису служебный вход для людей и машин. Kubernetes спрашивает у него, можно ли слать трафик и не пора ли перезапустить pod. Prometheus забирает у него числа: сколько платежей прошло и за сколько миллисекунд. Человек смотрит, какие настройки и бины реально работают. Каждый из этих ответов собирается из обычных бинов приложения, поэтому его можно расширить своим кодом. И каждый можно случайно открыть всему интернету, если не подумать о доступе.

Процесс жив, но платежи не проходят, и снаружи этого не видно

Платёжный сервис работает в трёх pod-ах за общим Service в Kubernetes. Ночью у одного pod-а рвётся соединение с банком. JVM жива, порт открыт, контроллер отвечает. Только каждый третий платёж клиента теперь заканчивается ошибкой, а дежурный узнаёт об этом из жалоб.

Чтобы платформа и дежурный реагировали сами, сервис должен отвечать на три вопроса. Можно ли сейчас слать мне запросы? На это отвечает readiness. Не сломан ли я так, что поможет только перезапуск? Это liveness. Как я работаю в цифрах? Это метрики: число платежей, ошибки, задержки. Четвёртый вопрос — где именно застрял конкретный платёж — решает трассировка.

Писать эти ответы в каждом сервисе вручную долго и однообразно. Стартер spring-boot-starter-actuator приносит готовые endpoints: health, metrics, prometheus, env, loggers и другие. Под ними лежат Micrometer для метрик и модель доступности приложения. Тема разбирает эти части на одном демо.

Демо ActuatorDemo.java поднимает веб-сервер на случайном порту. Банк заменён флагом Bank.up, а HTTP-запросы к сервису программа делает сама. Стек: JDK 21, Spring Boot 4.1.1, Micrometer 1.17.

cd examples/actuator
./run.sh ActuatorDemo # Maven и JDK 21; банк, Kubernetes и Prometheus не нужны.

Endpoint отвечает, только если он доступен и открыт наружу

У каждого endpoint-а два независимых переключателя. Первый — доступ: существует ли endpoint вообще и что через него можно делать. С Boot 3.4 он задаётся через management.endpoint.<id>.access со значениями none, read-only и unrestricted; старое enabled заменено. Второй — экспозиция: по какому каналу endpoint виден, HTTP или JMX.

По умолчанию доступ есть почти у всех endpoint-ов, но по HTTP открыт только health. Поэтому первый запуск демо без настроек выглядит бедно: метрики уже собираются в памяти, но /actuator/metrics отдаёт 404.

// Первый контекст демо: никаких management.* настроек.
call("GET", "/actuator");         // Список открытых endpoints.
call("GET", "/actuator/health");  // Общий статус без подробностей.
call("GET", "/actuator/metrics"); // Метрики есть, но не открыты по HTTP.
GET /actuator -> 200 {"_links":{"self":{},"health-path":{},"health":{}}}
GET /actuator/health -> 200 {"groups":["liveness","readiness"],"status":"UP"}
GET /actuator/metrics -> 404

Ссылки href в выводе вырезаны ради длины строки. Обрати внимание на groups: группы liveness и readiness уже есть, хотя Kubernetes рядом нет. В Boot 4 probes включены по умолчанию; в Boot 3 они включались сами только при запуске в Kubernetes, иначе требовали management.endpoint.health.probes.enabled=true.

Во втором контексте демо открывает три endpoint-а и включает подробности health:

management:
  endpoints:
    web:
      exposure:
        include: health,metrics,prometheus # Список, а не "*": открываем только нужное.
  endpoint:
    health:
      show-details: always # В проде обычно when-authorized.

Типичная прод-схема: endpoints слушают отдельный порт management.server.port, который не публикуется наружу через ingress. Kubernetes и Prometheus ходят на него изнутри кластера. Всё, что опаснее health и метрик, закрыто Spring Security или не открыто вовсе. Отдельный порт ещё и отделяет служебные запросы от пула потоков, который обслуживает платежи.

Endpoints под /actuator безопасны, потому что про этот путь никто не знает.

Путь /actuator стандартный, и сканеры проверяют его первым. Открытый heapdump уже приводил к утечкам ключей из памяти. Защищай endpoints доступом и сетью, а не надеждой на неизвестный адрес.

Health собирает индикаторы в дерево и сводит их к худшему статусу

Каждый бин типа HealthIndicator — один узел дерева health. Boot сам добавляет индикаторы для того, что нашёл в контексте: db для DataSource, redis, diskSpace, ping, ssl. Свой индикатор — обычный бин. Имя компонента берётся из имени бина без суффикса HealthIndicator.

@Component("bankHealthIndicator") // Компонент health получит имя "bank".
class BankHealthIndicator implements HealthIndicator {
    private final Bank bank;

    BankHealthIndicator(Bank bank) { this.bank = bank; }

    @Override
    public Health health() { // Вызывается на каждый запрос к health.
        return bank.up.get()
                ? Health.up().withDetail("latencyMs", 42).build()
                : Health.down().withDetail("error", "connect timed out").build();
    }
}

Без явного имени бина вложенный класс из демо получил бы имя actuatorDemo.BankHealthIndicator, а компонент — actuatorDemo.Bank. Так в JSON появляются странные ключи. Имя компонента — часть договора с мониторингом, поэтому задавай его явно.

Статус родителя вычисляет StatusAggregator: побеждает самый плохой статус по порядку DOWN, OUT_OF_SERVICE, UP, UNKNOWN. Затем HttpCodeStatusMapper переводит его в HTTP-код: DOWN и OUT_OF_SERVICE дают 503, остальные — 200. Именно код, а не JSON, читают балансировщик и Kubernetes.

Проверим на демо. Банк падает, два платежа проходят с ошибкой, затем программа спрашивает общий health и обе группы. Из большого JSON общего health оставлены компонент банка, компонент readinessState и итоговый статус.

bank.up.set(false); // Соединение с банком потеряно.
call("POST", "/pay?id=p-2");
call("POST", "/pay?id=p-3");
call("GET", "/actuator/health");            // Всё дерево.
call("GET", "/actuator/health/readiness");  // Группа для балансировки.
call("GET", "/actuator/health/liveness");   // Группа для перезапуска.
health    -> 503 "bank":{"details":{"error":"connect timed out"},"status":"DOWN"} ... "readinessState":{"status":"UP"} ... status=DOWN
readiness -> 200 {"status":"UP"}
liveness  -> 200 {"status":"UP"}

Общий health отвечает 503, а readiness и liveness — 200. Это не ошибка, а намеренное решение Boot. Если направить probe Kubernetes на общий /actuator/health, падение банка выключит из балансировки все три pod-а сразу. Сервис перестанет отвечать даже на запросы, которым банк не нужен: статус платежа, история, возвраты из очереди.

Индикатор вызывается синхронно на каждый запрос к health. Медленная проверка банка с таймаутом в 10 секунд сделает медленным и сам health, и probe Kubernetes упадёт по своему таймауту. Тяжёлые проверки кешируют или проверяют фоном и отдают последний результат.

Liveness и readiness отвечают оркестратору на разные вопросы

Kubernetes по-разному реагирует на два ответа. Неудачный readiness исключает pod из Service: новые запросы идут в другие pod-ы, сам pod продолжает работать. Неудачный liveness заставляет kubelet убить контейнер и запустить заново. Первый ответ значит «подожди», второй — «я сломан безнадёжно».

Внутри Boot эти ответы хранит ApplicationAvailability. Состояния меняются событием AvailabilityChangeEvent. Liveness бывает CORRECT или BROKEN, readiness — ACCEPTING_TRAFFIC или REFUSING_TRAFFIC. Boot сам переводит readiness в ACCEPTING после запуска runner-ов и обратно в REFUSING при начале остановки; подробно это разобрано в Startup & Packaging.

Шаг 4 демо делает прямо в коде. Readiness сразу отвечает 503 со статусом OUT_OF_SERVICE, а liveness остаётся 200:

// Сервис сам решил временно не принимать запросы.
AvailabilityChangeEvent.publish(context, ReadinessState.REFUSING_TRAFFIC);
call("GET", "/actuator/health/readiness");
call("GET", "/actuator/health/liveness");
readiness -> 503 {"status":"OUT_OF_SERVICE"}
liveness  -> 200 {"status":"UP"}

Группы настраиваются. Например, management.endpoint.health.group.readiness.include=readinessState,db добавит базу в readiness. Это разумно, если без базы pod бесполезен, а у других pod-ов база может быть доступна, например при отдельных репликах. Если база общая для всех, её падение одновременно выключит все pod-ы, и клиенты вместо понятной ошибки 503 от сервиса получат отказ от балансировщика.

В liveness стоит проверять базу и внешние сервисы: если они недоступны, сервис сломан.

Liveness ведёт к перезапуску. Перезапуск не чинит базу, зато все pod-ы одновременно уходят в рестарт, холодный старт и повторное открытие соединений. Короткий сбой базы превращается в полный отказ сервиса. В liveness — только состояние самого процесса.

Для медленного старта в Kubernetes используют отдельный startupProbe на тот же путь liveness с большим запасом времени. Пока он не прошёл, liveness не проверяется, и kubelet не убивает pod, который просто долго прогревается.

Micrometer записывает измерения, а реестр решает, куда их отдать

Код сервиса пишет измерения в MeterRegistry и не знает, какая система мониторинга их прочитает. Micrometer — то же, что SLF4J для логов: один API, разные реализации. Подключил micrometer-registry-prometheus — появился endpoint /actuator/prometheus в формате Prometheus. Подключил OTLP-реестр — те же метрики уходят в OpenTelemetry Collector.

Тип метраЧто измеряетПример в платежах

TimerЧисло событий, сумма и максимум длительности, гистограммаВремя списания
GaugeТекущее значение, которое читается при опросеРазмер очереди возвратов
DistributionSummaryРаспределение величины без времениСумма платежа

Метр определяется именем и набором тегов. Тег — измерение, по которому потом режут график: outcome, bank, method. В демо контроллер замеряет каждое списание и помечает результат тегом:

@PostMapping("/pay")
String pay(@RequestParam String id) {
    Timer.Sample sample = Timer.start(registry); // Засекаем время начала.
    String outcome = bank.up.get() ? "ok" : "bank_down";
    // Тег с малым числом значений; id платежа в тег не кладём.
    sample.stop(registry.timer("payments.charge", "outcome", outcome));
    return outcome + ":" + id;
}

Один платёж прошёл при живом банке, два — при упавшем. Программа читает один тег через /actuator/metrics и строки из /actuator/prometheus:

payments.charge outcome=bank_down -> COUNT=2.0
payments_charge_seconds_count{outcome="bank_down"} 2
payments_charge_seconds_count{outcome="ok"} 1

Имя изменилось при экспорте. Реестр Prometheus переводит точки в подчёркивания и добавляет базовую единицу таймера: payments.charge становится payments_charge_seconds с рядами _count, _sum и _max. В коде ты всегда пишешь имя через точки, а реестр приводит его к правилам своей системы.

Многое Boot измеряет сам: http.server.requests для каждого контроллера с тегами uri, method, status и outcome, пулы HikariCP, память и GC JVM, потоки Tomcat. Шаблон пути попадает в тег uri как /payments/{id}, а не как конкретный адрес. Иначе каждый платёж порождал бы свой временной ряд.

Каждая уникальная комбинация тегов — отдельный временной ряд в памяти сервиса и в Prometheus. Тег paymentId на миллионе платежей даёт миллион рядов: память сервиса растёт, Prometheus тормозит или отбрасывает данные. В теги кладут значения из короткого известного списка. Идентификатор конкретного платежа нужен в логах и трейсах, а не в метриках.

Перцентили считают по гистограмме, а не по каждому pod-у отдельно

Таймер может считать перцентили прямо в приложении: publishPercentiles(0.95, 0.99). Но такой p99 посчитан по одному pod-у, и среднее трёх p99 не равно p99 всего сервиса. Для общего перцентиля включают гистограмму: management.metrics.distribution.percentiles-histogram.payments.charge=true. Сервис отдаёт счётчики по корзинам _bucket, а Prometheus складывает корзины всех pod-ов и считает histogram_quantile(0.99, …). Цена — несколько десятков рядов на каждую комбинацию тегов.

Трассировка связывает один платёж через сервисы, а цена и доступ задают границы

Метрика скажет, что p99 списания вырос до двух секунд. Но какой платёж тормозил и в каком сервисе: в нашем, в антифроде или у банка? На это отвечает распределённая трассировка. Каждый запрос получает traceId, каждый участок работы — span с началом, длительностью и родителем.

В Spring измерения строятся на Observation API. Одно наблюдение, например обработка HTTP-запроса, сразу даёт и таймер для метрик, и span для трассировки. Micrometer Tracing передаёт span-ы в OpenTelemetry или Brave, а экспортёр отправляет их в Jaeger, Tempo или Zipkin.

  1. Запрос приходит в платёжный сервис без заголовка трассировки. Сервис создаёт traceId и корневой span.
  2. Сервис вызывает антифрод через RestClient, собранный из бина RestClient.Builder. Клиент сам добавляет заголовок W3C traceparent с тем же traceId и id текущего span-а.
  3. Антифрод читает заголовок и создаёт дочерний span того же trace.
  4. Оба сервиса пишут traceId и spanId в MDC логов, поэтому по одному traceId находятся все строки всех сервисов про этот платёж.

Частая поломка — клиент, созданный через RestClient.create() или new RestTemplate(). В нём нет наблюдения, заголовок не передаётся, и trace рвётся на границе сервиса. Клиентов для трассировки берут из билдеров, которые настроил Boot.

По умолчанию Boot сохраняет 10% трасс: management.tracing.sampling.probability=0.1. Хранить каждый span дорого. В тестовом окружении ставят 1.0, в проде выбирают долю по объёму трафика. Само решение о выборке принимает первый сервис, и оно передаётся дальше в заголовке, поэтому trace не обрывается на середине. Трассировку в этой теме мы не запускали: для неё нужны коллектор и второй сервис, а поведение описано по документации Boot.

Где Actuator заканчивается

Actuator отдаёт данные, но не хранит историю, не рисует графики и не будит дежурного. Это работа Prometheus, Grafana и Alertmanager или облачного аналога. Сервис отвечает только на вопросы «каков я сейчас» и «что я посчитал с момента старта».

Сбор измерений стоит ресурсов. Каждый метр живёт в памяти, каждый таймер добавляет немного работы на запрос, каждый сохранённый span — сетевой трафик. Обычно это проценты, но лишние теги и стопроцентная выборка под нагрузкой делают служебную часть заметной. Проверяй /actuator/metrics: сотни неожиданных имён или тегов с идентификаторами — признак будущей проблемы.

  • Endpoint работает, если к нему есть доступ и он открыт по HTTP или JMX. По умолчанию по HTTP открыт только health.
  • Health сводит индикаторы к худшему статусу и переводит его в HTTP-код: DOWN и OUT_OF_SERVICE дают 503.
  • Readiness говорит «не шли трафик», liveness — «перезапусти меня». Внешние зависимости в liveness приводят к массовым рестартам.
  • Micrometer отделяет код метрик от системы мониторинга. Каждая комбинация тегов — временной ряд, поэтому id в теги не кладут.
  • Трассировка связывает сервисы через заголовок traceparent и traceId в логах; клиенты для неё берут из билдеров Boot.

На собеседовании

Чем liveness отличается от readiness и что в них проверять?

Readiness отвечает, можно ли сейчас слать в pod трафик. Если он падает, Kubernetes убирает pod из Service, но не трогает контейнер. Liveness отвечает, жив ли процесс. Если он падает, kubelet перезапускает контейнер. В Boot это группы /actuator/health/readiness и /actuator/health/liveness, а состояния хранит ApplicationAvailability.

В liveness я проверяю только сам процесс. Внешние сервисы туда не кладу: если база упала, рестарт всех pod-ов её не починит, а сервис потеряет ещё и прогретые кеши и соединения. Базу в readiness добавляю осознанно, когда без неё pod бесполезен и другие pod-ы могут работать.

  • Boot переводит readiness в ACCEPTING_TRAFFIC после runner-ов и в REFUSING_TRAFFIC в начале graceful shutdown, чтобы балансировщик успел убрать pod до закрытия соединений.
  • Для долгого старта нужен startupProbe: он откладывает проверки liveness, иначе kubelet убьёт pod во время прогрева.
  • В Boot 4 probes включены по умолчанию; в Boot 3 они включались автоматически только в Kubernetes.
  • Приложение может само опубликовать REFUSING_TRAFFIC при перегрузке, и тогда pod выходит из балансировки без рестарта.
Банк недоступен, общий /actuator/health отдаёт 503. Что сделает Kubernetes, если probes смотрят на группы Boot?

Ничего. В группу readiness по умолчанию входит только readinessState, в liveness — только livenessState, поэтому обе отвечают 200. Трафик продолжает идти, сервис сам возвращает клиентам понятную ошибку или кладёт платёж в очередь. Если бы probe смотрел на общий health, все pod-ы одновременно вышли бы из балансировки.

Какие endpoints Actuator открыты по умолчанию и как их защитить?

По HTTP по умолчанию открыт только health, и он показывает статус без подробностей. Остальные endpoints доступны, но их надо явно открыть через management.endpoints.web.exposure.include. Я перечисляю нужные по именам и не ставлю *.

В проде я выношу Actuator на отдельный management.server.port, который не публикуется наружу, и закрываю всё, кроме health и метрик, через Spring Security. Особенно опасны heapdump, env и loggers: в дампе памяти лежат секреты, через loggers можно включить DEBUG на проде.

  • С Boot 3.4 доступ задаётся management.endpoint.<id>.access: none, read-only или unrestricted. Read-only запрещает операции записи, например смену уровня логов.
  • Значения в env и configprops скрыты по умолчанию (show-values: never); when-authorized показывает их только пользователям с нужной ролью.
  • Отдельный порт ещё и отделяет служебные запросы от рабочего пула потоков, поэтому probe отвечает даже при забитом основном пуле.

Как добавить свою бизнес-метрику и что может пойти не так?

Я внедряю MeterRegistry и создаю Counter или Timer с понятным именем через точки и тегами, например payments.charge с тегом outcome. Micrometer сам приведёт имя к формату системы: в Prometheus это будет payments_charge_seconds_count. Для замера метода можно повесить @Timed или @Observed, если подключена поддержка аспектов.

Главная ошибка — тег с неограниченным числом значений: id платежа, email, полный URL. Каждая комбинация тегов — отдельный временной ряд, и метрики съедают память сервиса и Prometheus. Такие значения пишу в логи и трейсы.

  • Перцентили, посчитанные в приложении, нельзя усреднить между pod-ами. Для общего p99 включаю гистограмму и считаю histogram_quantile в Prometheus.
  • Gauge держит слабую ссылку на объект. Если объект собран GC, gauge начнёт отдавать NaN; передавать нужно долгоживущий объект.
  • Аннотации @Timed работают через прокси, поэтому вызов изнутри того же бина не измеряется.
Найди проблему в метрике отказов банка 
void onDecline(Payment p, String reason) {
    registry.counter("payments.declined",
            "merchant", p.merchantId(),  // 40 тысяч магазинов
            "reason", reason)            // текст ошибки от банка
        .increment();
}

Оба тега неограниченные. Магазинов десятки тысяч, а reason — свободный текст банка, где бывают номера транзакций и даты. Число рядов растёт как произведение значений, память сервиса и Prometheus растёт вместе с ним. Исправление: reason свести к короткому списку кодов (insufficient_funds, fraud, other), а разбивку по магазинам считать в аналитике по логам или событиям. Если разрез по магазину нужен в мониторинге, оставляют только крупнейших и складывают остальных в other.

Как работает health и как написать свой индикатор?

Каждый бин HealthIndicator — узел дерева. Boot сам добавляет индикаторы для базы, Redis, диска и других найденных компонентов. Общий статус — худший из дочерних по порядку DOWN, OUT_OF_SERVICE, UP, UNKNOWN; DOWN и OUT_OF_SERVICE дают HTTP 503.

Свой индикатор — бин с методом health(), который возвращает Health.up() или Health.down() с деталями. Имя компонента берётся из имени бина без суффикса HealthIndicator. Я слежу, чтобы проверка была быстрой: она выполняется на каждый запрос к health.

  • Группы позволяют выбрать набор индикаторов для конкретного потребителя: readiness, liveness или своя группа для балансировщика.
  • Медленную проверку кешируют или выполняют фоном; иначе таймаут внешнего сервиса превращается в таймаут probe.
  • Подробности health по умолчанию скрыты (show-details: never): они раскрывают устройство инфраструктуры.
