How Code Agents Work

Код-агент — это языковая модель в цикле. Модель получает всю историю: системный промпт, описания инструментов, задачу и результаты прошлых шагов. В ответ она либо пишет текст и останавливается, либо просит вызвать инструмент — прочитать файл, найти строку, выполнить команду. Программа вокруг модели решает, разрешён ли вызов, выполняет его и кладёт результат в историю следующим сообщением. Цикл повторяется. Сама модель ничего не выполняет и ничего не помнит между вызовами: вся её «память» — контекстное окно, которое растёт с каждым шагом. В настоящем прогоне Claude Code ещё до задачи в окне было около 19,7 тыс. токенов системного промпта и описаний инструментов. Поэтому контекст — ограниченный ресурс, а длинная сессия работает хуже короткой. Разрешения проверяет код, а не модель. Во втором прогоне все три попытки компиляции были отклонены, но агент всё равно ответил «Ошибок компиляции нет». Ответ агента — утверждение; доказательство — вывод инструмента.

«Ошибок компиляции нет» без компиляции

Агенту дали маленький Java-проект из двух классов — расчёт комиссии и возврата — и попросили скомпилировать его. Разрешены только чтение и поиск: Read, Grep, Glob. Модель не врёт в человеческом смысле: она генерирует правдоподобное продолжение, и «нет ошибок» правдоподобно для двух коротких классов. Но для инженера это главный урок про агентов: итоговый текст — не результат работы, а утверждение о нём. Результат — это вывод инструмента: зелёный тест, лог компиляции, ответ команды. Поэтому хороший процесс с агентом из AI Task Workflow требует показать прогон тестов, а не слово «готово».

Чтобы понимать, почему так получилось и как это предотвращать, нужно разобрать, что такое агент на самом деле: какой код работает вокруг модели, что она видит и кто решает, какие действия разрешены.

Тот же цикл можно написать самому — это несколько десятков строк. AgentLoop.java воспроизводит устройство: история сообщений, вызов модели, гейт прав, выполнение инструмента, результат обратно в историю, ограничение числа ходов. «Модель» в нём заскриптована решениями из второго прогона — так видно устройство, а не качество модели:

for (int turn = 1; turn <= maxTurns; turn++) {
    Message reply = scripted.next(history);                          // модель видит ВСЮ историю
    history.add(reply);
    ...
    for (ToolUse c : calls) {                                         // stop_reason = tool_use
        Decision d = gate(c);
        String out = d == Decision.ALLOW ? TOOLS.get(c.tool()).apply(c.input()) : "This command requires approval";
        results.add(new ToolResult(c.id(), d == Decision.DENY, out));
    }
    history.add(new Message("user", results));                       // результат идёт обратно как сообщение
}

Отсюда несколько свойств, о которых спрашивают. Модель не имеет состояния между вызовами: «память» агента — это история, которую программа каждый раз отправляет заново. Агент — это программа, а не модель: Claude Code, Codex CLI и Cursor могут использовать разные модели, но устроены одинаково. И проверку результата можно встроить в программу — последняя строка демо считает успешные запуски компилятора и помечает ответ без них. Настоящие агенты делают похожее хуками, о которых — в Least Privilege & Approval Gates.

Контекстное окно — главный ресурс

В трассе видна цифра context — сколько токенов модель получила на вход в этом вызове. Первый вызов — 19 703 токена, хотя пользователь написал одно предложение: это системный промпт Claude Code и описания 31 инструмента. Дальше каждый вызов добавляет всё, что произошло: запросы инструментов, их результаты, рассуждения. 20 046, потом 20 481. Два коротких файла почти ничего не добавили, но в реальной задаче один Read большого класса или вывод сборки — тысячи токенов, и за час работы окно заполняется.

Почему это дорого. Деньги смягчает кеширование промпта — cached 19693: повторно отправленное начало истории обрабатывается со скидкой, поэтому весь прогон стоил около 5 центов. Но качество кеш не спасает. Anthropic называет это context rot: чем больше токенов в окне, тем хуже модель находит и использует нужное. Архитектурная причина — внимание трансформера связывает каждый токен с каждым, и «бюджет внимания» распределяется по всему окну. Практическая формулировка из их статьи об инженерии контекста: нужен наименьший набор высокосигнальных токенов, который максимизирует шанс нужного результата.

ПриёмЧто делаетКогда
Новая сессия (/clear)Пустая история, только системный промптМежду задачами; после двух неудачных попыток исправить одно и то же

Файл правил проекта — CLAUDE.md у Claude Code, AGENTS.md у Codex — загружается в каждую сессию и тоже тратит окно. Поэтому его держат коротким: команды сборки и тестов, неочевидные соглашения, запреты. Всё, что агент узнает, прочитав код, туда не пишут. Как собрать контекст под конкретную задачу — в AI Task Workflow.

Кто решает, что агенту можно

В начале обоих прогонов tools=31, хотя в команде было --allowedTools "Read,Grep,Glob". Это частое непонимание: allowedTools — список инструментов, которые выполняются без вопроса, а не список доступных. Модель видит все 31 и может попросить любой. Что будет с остальными, решает режим прав: в интерактивной сессии Claude Code спросит человека, а в неинтерактивном -p спросить некого, и вызов отклоняется. Так и вышло во втором прогоне: Bash не был в списке, find прошёл как команда только для чтения, а mkdir и javac получили отказ. Ограничить сам набор инструментов — флаг --tools; запретить — --disallowedTools.

Отказ не останавливает агента. Он возвращается в историю обычным tool_result с пометкой ошибки, и модель решает, что делать дальше: попробовать иначе — как здесь, разбив команду на части, — или сдаться и объяснить. Или, как в демо, выдать правдоподобный ответ без проверки. Поэтому гейт прав защищает систему от действий агента, но не защищает человека от неверного вывода. Второе решается процессом: доказательство — в выводе инструмента, а не в тексте.

Режимы прав Claude Code 2.1.287 (--permission-mode): manual — спрашивать о каждом действии с побочным эффектом, acceptEdits — правки файлов без вопроса, plan — только чтение и план, auto — решения принимает автоматическая проверка, dontAsk и bypassPermissions — без вопросов, только в изолированной среде. У Codex CLI похожая пара настроек: песочница (--sandbox read-only | workspace-write | danger-full-access) и политика подтверждений. Как настроить права так, чтобы агент не мог навредить, — тема Least Privilege & Approval Gates.

Ландшафт: один цикл, разная обвязка

АгентГде работаетФайл правилПрава
Claude CodeТерминал, IDE, desktop, облачные сессии; claude -p для скриптов и CICLAUDE.mdРежимы, правила allow/ask/deny в settings.json, хуки

Различия — в обвязке: где выполняются команды, как устроены права, какие модели доступны, как агент подключает внешние инструменты (протокол MCP). Цикл везде один. Поэтому на собеседовании ценнее не список инструментов, которые вы пробовали, а умение объяснить этот цикл и рассказать одну задачу целиком: какой контекст дали, как проверяли, что нашли в диффе. Сравнения «какой агент лучше» быстро устаревают — модели и продукты обновляются каждые несколько месяцев.

Если агент написал, что тесты прошли и ошибок нет, — значит, так и есть.

Итоговый текст — продолжение, которое модель сочла правдоподобным. В прогоне все три попытки компиляции были отклонены, а ответ был «Ошибок компиляции нет». Доверять можно выводу инструмента: логу тестов, коду возврата, а не пересказу.

Как попробовать самому

Если вы ещё не работали с агентами, вот минимальный путь, чтобы увидеть всё описанное своими глазами.

  1. Установить Claude Code. brew install --cask claude-code на macOS или npm install -g @anthropic-ai/claude-code (нужен Node.js 18+); способы для других систем — в документации Claude Code. Затем запустить claude в любом каталоге и войти — подойдёт подписка Claude Pro/Max или API-ключ.
  2. Интерактивно. В каталоге проекта: claude, затем задать вопрос о коде. Команда /context покажет, сколько окна занято и чем; /clear начнёт с чистой истории; Shift+Tab переключает режим, в том числе режим плана. На каждое действие с побочным эффектом агент спросит разрешение — это гейт из шага 4.
  3. Неинтерактивно, с потоком событий. Скрипт run.sh создаёт учебный репозиторий скриптом setup.sh и делает два прогона из этой темы: claude -p --model haiku --output-format stream-json --verbose --allowedTools "Read,Grep,Glob" "вопрос". Каждая строка вывода — событие цикла в JSON; python3 trace.py runs/run1.jsonl печатает их как в трассах выше. Модель Haiku и короткие вопросы — прогон стоит порядка цента. Ваши ответы и число шагов будут отличаться: модель не детерминирована.
  4. Без сети и ключей. java AgentLoop.java показывает устройство цикла на заскриптованной модели.
  5. Codex CLI. npm install -g @openai/codex, вход через codex; неинтерактивно — codex exec --sandbox read-only --json "вопрос", события тоже идут JSONL-потоком.
  • Агент — модель в цикле: модель возвращает tool_use, программа проверяет права, выполняет и кладёт tool_result в историю.
  • Модель не помнит ничего между вызовами; память — история, отправляемая заново каждый раз.
  • До задачи окно уже занято системным промптом и инструментами (≈19,7k токенов в прогоне); каждый шаг его растит.
  • Context rot: больше токенов — хуже внимание; помогают /clear, сжатие, субагенты, заметки в файлах.
  • allowedTools — список без вопросов, а не список доступных; в -p режиме остальное отклоняется.
  • Отказ возвращается модели как ошибка инструмента; агент может ответить «готово» без проверки — доказательство только в выводе инструмента.
  • Claude Code, Codex, Cursor — один цикл, разная обвязка: права, песочница, файл правил.

На собеседовании

Как устроен AI-агент для кода?

Это языковая модель в цикле, которым управляет обычная программа. Модель получает историю — системный промпт, описания инструментов, задачу, результаты прошлых шагов — и отвечает либо текстом, либо запросом инструмента с аргументами. Программа проверяет права, выполняет инструмент и добавляет результат в историю, после чего модель вызывается снова. Цикл заканчивается, когда модель отвечает без запроса инструмента или достигнут лимит ходов.

  • Модель без состояния: контекст пересылается каждый вызов, кеширование промпта снижает цену, но не качество.
  • Права и проверки — в коде вокруг модели: правила, песочница, хуки.
  • Агенты отличаются обвязкой, а не циклом.

Почему длинная сессия с агентом работает хуже короткой?

Всё, что произошло в сессии, лежит в контекстном окне и уходит в модель на каждом шаге. Чем больше токенов, тем хуже модель находит нужное — context rot, — а нерелевантные куски прошлых задач и неудачных попыток сбивают её. Поэтому между задачами начинают новую сессию, длинную задачу сжимают, исследование выносят в субагента, а план и прогресс держат в файле.

  • Ещё до задачи окно занято системным промптом и схемами инструментов — десятки тысяч токенов.
  • Файл правил проекта загружается всегда — его держат коротким.
  • После двух неудачных исправлений лучше новая сессия с точным промптом.

Агент сказал, что всё работает. Как это проверить?

Не верить тексту, смотреть на вывод инструментов: прогон тестов, лог сборки, код возврата. Итоговое сообщение модели — правдоподобное продолжение, а не отчёт: агент может ответить «ошибок нет», даже если компиляция была отклонена гейтом прав. В процессе работы с агентом это закрепляют требованием — готовность доказывается прогоном, а в CI проверки повторяются независимо.

  • Поток событий (stream-json) показывает каждый вызов и отказ — по нему видно, что реально выполнялось.
  • Хуки могут блокировать завершение без зелёных тестов.
Что не так с этим шагом CI? 
claude -p "Почини падающие тесты и убедись, что всё зелёное" --allowedTools "Edit,Bash(mvn test)"
git commit -am "fix tests (verified by agent)"

Коммит опирается на слова агента. Если mvn test был отклонён, упал или агент поправил тест вместо кода, сообщение «всё зелёное» ничего не гарантирует. После прогона агента нужно самому запустить mvn test и коммитить только при нулевом коде возврата — а изменения в тестах просматривать отдельно, чтобы агент не «починил» их ослаблением проверок.
