Least Privilege & Approval Gates

Агенту дают ровно столько прав, сколько нужно для задачи, и обеспечивают это кодом, а не просьбой в промпте. «Будь осторожен» — не механизм контроля: модель следует инструкциям вероятностно и может быть сбита с толку данными, которые читает. Защита строится слоями. Первый — набор инструментов. Второй — правила allow/ask/deny, где запрет сильнее разрешения. Третий — хуки: детерминированные скрипты, которые смотрят на каждый вызов и могут его остановить. Дальше идут песочница ОС, отдельные учётные данные с минимальными правами и без доступа к продакшену, обязательное подтверждение человека для опасных операций и журнал всех вызовов. В демо Claude Code правило deny закрыло .env, миграции и curl. Хук остановил rm -rf, хотя rm был разрешён правилом. Песочница macOS не дала писать за пределы рабочего каталога и выходить в сеть. А правила allow из непроверенного репозитория Claude Code проигнорировал, пока папке не выдано доверие. Хуки этого репозитория при этом выполнились: это код, и запускать агента в чужом репозитории опасно.

Почему права, а не просьба в промпте

Агент выполняет команды с правами процесса, в котором запущен, — обычно с вашими. Он видит ваши SSH-ключи, токены в переменных окружения, конфиг облака и может выполнить git push, terraform apply или DELETE в базе, если до неё дотянется. Ошибки агента бывают двух видов. Собственные: неверно понял задачу, «почистил» не тот каталог, решил, что миграцию проще переписать. И навязанные: в прочитанном файле, issue или ответе API оказалась инструкция, которую модель приняла за задание, — prompt injection из LLM Risks. От обоих видов просьба в системном промпте не защищает: она меняет вероятность, а не возможность.

Принцип наименьших привилегий здесь тот же, что для сервисов со скоупами из OAuth 2.0 & OIDC: каждое право явно выдано, по умолчанию — запрет, права ограничены задачей и временем. Разница в том, что у агента нет стабильного поведения, которое можно один раз проверить. Поэтому ограничения ставят снаружи модели, там, где их нельзя уговорить: в коде агента, в ОС, в учётных данных и в CI.

Правила allow, ask и deny

Учебный проект — шаблон project-template/.claude/settings.json: исходники можно править, тесты запускать, rm и ls разрешены; git push только с подтверждением; секреты, миграции и сеть закрыты:

"permissions": {
  "allow": ["Read", "Edit(src/**)", "Bash(./test.sh)", "Bash(rm:*)", "Bash(ls:*)"],
  "ask":   ["Bash(git push:*)"],
  "deny":  ["Read(./.env)", "Edit(db/migrations/**)", "Bash(curl:*)"]

Правка исходника и запуск тестов прошли по allow. Миграция и curl отклонены по deny — решение кода, а не модели: в выводе сообщение Claude Code, а не рассуждение. Детерминированный запрет на .env виден в следующем прогоне. Правило для .env закрывает только инструмент Read: cat .env через Bash — другой инструмент. Правила allow из непроверенного каталога проигнорированы: правка исходника и тесты остались без разрешения, а в неинтерактивном режиме спросить некого — отказ. Но хуки этого же репозитория выполнились: журнал аудита записан, guard.py остановил rm -rf. Хук — произвольная команда, и "command": "python3 .claude/hooks/audit.py" могла бы отправить ваши ключи куда угодно. Выводы практические. Не запускать агента в неинтерактивном режиме в репозитории, которому вы не доверяете. Просматривать изменения в .claude/, AGENTS.md и конфигурации MCP в PR так же внимательно, как CI-пайплайны. А в автоматизации запускать агента в песочнице или контейнере, где у него нет ваших секретов. Codex CLI по той же причине требует подтверждения доверия к хукам (флаг --dangerously-bypass-hook-trust это отключает).

Хуки: детерминированный контроль и журнал

call = json.load(sys.stdin)
cmd = call.get("tool_input", {}).get("command", "")
RULES = [
    (r"\brm\s+-[a-zA-Z]*r[a-zA-Z]*f|\brm\s+-[a-zA-Z]*f[a-zA-Z]*r", "recursive force delete is blocked by policy"),
    (r"git\s+push\s+.*(--force|-f\b)", "force push is blocked by policy"),
    (r"db/migrations", "migrations change only through a reviewed PR"),
]
for pattern, reason in RULES:
    if re.search(pattern, cmd):
        print(f"BLOCKED by guard.py: {reason}: {cmd}", file=sys.stderr)
        sys.exit(2)

guard.py подключён как PreToolUse-хук для Bash. Claude Code передаёт ему вызов в JSON; код возврата 2 блокирует вызов, stderr становится сообщением для модели. В обоих прогонах rm -rf был разрешён правилом Bash(rm:*) и всё равно остановлен — хук сильнее разрешающего правила. Во втором прогоне агент написал абсолютный путь rm -rf $DEMO/build; хук смотрит на смысл команды, а не на точную строку, поэтому это не помогло. Хуки — место для политик, которые плохо выражаются шаблонами правил: запрет в любом месте команды, проверка аргументов, обращения к внешней системе политик. Но регулярное выражение по тексту команды обходится: find build -delete, скрипт или python -c удалят каталог без слов rm -rf. Поэтому хук — слой, а не единственная защита; от записи туда, куда нельзя, надёжно защищает песочница.

audit.py подключён на PreToolUse и PostToolUse для всех инструментов и пишет строку на каждую попытку и каждое выполнение. Журнал второго прогона — recorded/audit-with-settings.jsonl:

И главное — журнал пишется туда, куда агент писать не может: в учебном демо он лежит в рабочем каталоге, и агент с правом Edit мог бы его подправить. Как устроены журналы и трассировка вообще — в Observability.

Песочница ОС

Правила и хуки работают на уровне вызова инструмента. Но команда, которую они пропустили, может запустить что угодно: тест, который пишет в домашний каталог; сборку, которая скачивает зависимости; скрипт из репозитория. Песочница ограничивает сам процесс и всех его потомков на уровне ядра. Скрипт sandbox-demo.sh использует sandbox-exec — механизм Seatbelt в macOS, на котором стоит песочница Bash в Claude Code. Профиль запрещает запись вне рабочего каталога и исходящую сеть:

write inside the work dir                   ok
write to the home directory                 blocked (exit 1): Operation not permitted
write to /tmp outside the work dir          blocked (exit 1): Operation not permitted
read a file outside (allowed here)          ok
outgoing network: curl example.com          blocked (exit 6)
home file does not exist

Запись внутри рабочего каталога прошла, в домашний каталог и в остальной /tmp — Operation not permitted от ядра. curl завершился с кодом 6 — не смог разрешить имя: сеть закрыта целиком, включая DNS. Чтение снаружи в этом профиле разрешено; в настоящей песочнице закрывают и чтение секретов — ~/.ssh, ~/.aws, файлы с токенами. В Claude Code песочница включается командой /sandbox: команды Bash выполняются внутри неё, запись ограничена рабочим каталогом, сеть — разрешёнными доменами. У Codex CLI это --sandbox read-only | workspace-write. Для автоматизации надёжнее всего отдельный контейнер или виртуальная машина без ваших учётных данных — механизм изоляции из Docker.

Подтверждение человека ценно, только если человек понимает, что подтверждает. Если агент спрашивает разрешение на каждое чтение, через десять минут «да» нажимают не глядя — усталость от подтверждений превращает гейт в формальность. Поэтому безопасные действия разрешают без вопросов, опасные запрещают, а подтверждение оставляют для редких действий с понятными последствиями. Режим bypassPermissions (--dangerously-skip-permissions) отключает вопросы совсем — только внутри изолированной среды без секретов и сети. В Claude Code администратор может запретить этот режим и задать обязательные правила через управляемые настройки, которые пользователь не переопределит.

Если в настройках проекта написано allow, агент будет это делать, а deny на .env защищает секреты.

Правила allow из непроверенного каталога Claude Code игнорирует, пока каталогу не выдано доверие, — в демо правки и тесты остались без разрешения. А Read(./.env) закрывает только инструмент Read: команда cat .env через Bash — отдельный путь, который нужно закрыть правилом, хуком или песочницей.

Как попробовать самому

  1. Посмотреть свои права. В Claude Code команда /permissions показывает действующие правила и откуда они взяты. Правила проекта — в .claude/settings.json (в git), личные для проекта — в .claude/settings.local.json, глобальные — в ~/.claude/settings.json.
  2. Повторить демо. examples/ai-permissions/setup.sh копирует учебный проект во временный каталог. Дальше команда со страницы: claude -p --setting-sources project --settings .claude/settings.json --strict-mcp-config --permission-mode manual --model haiku --tools "Read,Edit,Bash" --output-format stream-json --verbose "...". Разбор — python3 ../ai-agents/trace.py, журнал — .claude/audit.jsonl в том каталоге. Порядка 5 центов. --strict-mcp-config отключает ваши MCP-серверы: без него в первом прогоне было 70 инструментов и 46 тыс. токенов на старте.
  3. Свой хук. Скопируйте guard.py в .claude/hooks/ своего проекта и добавьте блок hooks из шаблона в .claude/settings.json. Проверить хук без агента: echo '{"tool_input":{"command":"rm -rf x"}}' | python3 .claude/hooks/guard.py; echo $? — должно быть 2.
  4. Песочница. ./sandbox-demo.sh на macOS. В Claude Code — команда /sandbox. В Codex — codex --sandbox workspace-write.
  • Права агента обеспечиваются кодом снаружи модели; просьба в промпте меняет вероятность, а не возможность.
  • Слои: набор инструментов, правила deny › ask › allow, хуки, песочница ОС, учётные данные без прода, человек для опасных операций.
  • deny по Read не закрывает Bash: правила привязаны к инструменту.
  • allow из непроверенного каталога игнорируется до выдачи доверия, deny действует; хуки репозитория — исполняемый код.
  • Хук PreToolUse с кодом 2 блокирует вызов даже при allow; регулярное выражение по команде обходится — нужна песочница.
  • Песочница ограничивает процесс и потомков на уровне ядра: запись вне рабочего каталога и сеть.
  • Журнал прогона: каждая попытка и выполнение, пишется туда, где агент не может его изменить.

На собеседовании

Как вы ограничиваете права AI-агента?

Слоями, и все снаружи модели. Минимальный набор инструментов под задачу. Правила: безопасное — allow, опасное — deny, редкое и значимое — ask. Хуки, которые кодом проверяют каждый вызов и блокируют запрещённое. Песочница ОС на запись вне рабочего каталога и на сеть. Отдельные учётные данные с минимальными правами, без прода. Миграции, деплой и force push — только через PR и CI с человеком.

  • deny сильнее allow; правила привязаны к инструменту — Bash закрывают отдельно.
  • Управляемые настройки администратора, которые пользователь не переопределит.
  • Журнал вызовов вне досягаемости агента.
Что не так с такой настройкой для CI? 
- run: claude -p "Почини flaky-тесты и запушь" --dangerously-skip-permissions
  env:
    GITHUB_TOKEN: ${{ secrets.ADMIN_TOKEN }}
    DATABASE_URL: ${{ secrets.PROD_DATABASE_URL }}

Агент без единого гейта получает административный токен и URL боевой базы. Любая ошибка или prompt injection из кода и логов тестов превращается в push в любую ветку или запрос к продакшену. Нужно: токен только на чтение и создание PR в одном репозитории, тестовая база, обычный режим прав со списком allow, запуск в контейнере без сети, кроме нужных доменов, и результат — PR на ревью, а не push.

Зачем хуки, если есть правила прав?

Правила — шаблоны по имени инструмента и аргументу. Хук — произвольный код: видит весь вызов, может проверить смысл команды, обратиться к внешней политике, записать журнал. PreToolUse-хук с кодом 2 блокирует вызов даже там, где правило разрешает, и объясняет модели причину. PostToolUse — для журнала и проверок после действия.

  • Хуки репозитория — исполняемый код; изменения в .claude/ ревьюят как CI.
  • Проверка текста команды обходится — от записи защищает песочница.

Для каких операций нужен approval человека и как его реализовать?

Для необратимых и внешних: миграции, деплой и изменения инфраструктуры, force push и слияние в основную ветку, доступ к секретам, внешняя сеть, массовые изменения. Реализуется не просьбой к агенту, а механизмом: ask или deny в правилах, хук, защищённые ветки, деплой только из CI, отсутствие у агента нужных кредов.
