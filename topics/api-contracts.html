API: OpenAPI & Contracts

Контракт API — машиночитаемое описание того, что API принимает и возвращает. OpenAPI описывает пути, параметры, схемы тел и коды ответов в одном файле. Его можно получить из кода (code-first) или написать раньше кода и генерировать по нему сервер и клиентов (contract-first). Главная польза контракта — автоматическая проверка: сравнение двух версий в CI ловит ломающие изменения до релиза, а контрактные тесты потребителей проверяют то, что клиенты реально используют. Контракт полезен ровно настолько, насколько он точен.

«Небольшой рефакторинг» сломал трёх клиентов, и ни один тест не упал

Разработчик переименовал поле amount в amountMinor, чтобы было понятно, что сумма в копейках. Заодно сделал фильтр по магазину обязательным и добавил статус REFUND_PENDING. Тесты сервиса зелёные: сервис согласован сам с собой. После релиза сломались мобильное приложение, партнёрская выгрузка и сервис сверки — каждый по своей причине.

Тесты сервиса проверяют, что он делает то, что задумал автор. Они не проверяют, что он делает то, на что рассчитывают клиенты. Для этого нужен контракт — описание API, отдельное от кода, — и проверки, которые сравнивают изменения с ним. Демо ContractDemo.java поднимает две версии контроллера на Spring Boot 4.1 со springdoc 3.1 и сохраняет их OpenAPI-описания, а утилита oasdiff в Docker сравнивает их, как в CI: ./run.sh ContractDemo, затем docker run tufin/oasdiff breaking.

OpenAPI описывает API в одном файле, который читают люди и программы

Спецификация OpenAPI — документ YAML или JSON: пути и методы, параметры, схемы тел запросов и ответов на JSON Schema, коды ответов, способы аутентификации. По ней строится документация в Swagger UI, генерируются клиенты на любом языке, настраиваются шлюзы и моки. Демо получает её из кода — springdoc строит описание по аннотациям Spring MVC и типам Java:

record CreatePayment(@Positive long amount, String currency) {}

@PostMapping("/payments")
ResponseEntity<Payment> create(@RequestBody CreatePayment r) {
    return ResponseEntity.created(URI.create("/payments/p-1")).body(...); // Возвращает 201.
}
v1.json: 1380 bytes
  CreatePayment: {"type":"object","properties":{"amount":{"type":"integer","format":"int64","exclusiveMinimum":0},"currency":{"type":"string"}}}
  POST /payments responses: {"200":{"description":"OK","content":{"*/*":{"schema":{"$ref":"#/components/schemas/Payment"}}}}}

Из long получился integer int64, из @Positive — exclusiveMinimum: 0. Но в описании две ошибки, которые незаметны, пока не начнёшь его читать. Ответ POST описан кодом 200, хотя метод возвращает 201: springdoc не видит, что вернёт ResponseEntity.created во время работы. И ни одно поле не помечено обязательным: в record нет способа сказать это без аннотаций, а поле без отметки по схеме можно не присылать. Клиент, сгенерированный по такому описанию, будет считать все поля nullable.

Ещё одна деталь из лога запуска: springdoc предупреждает, что /v3/api-docs включён по умолчанию. Публичное описание внутреннего API — подарок атакующему, поэтому в проде его закрывают или выключают springdoc.api-docs.enabled=false.

Code-first описывает то, что получилось, contract-first — то, что договорились сделать

При code-first контракт — побочный продукт кода. Это быстро и всегда синхронно с реализацией, но описание точно настолько, насколько подробно размечен код аннотациями @Schema, @ApiResponse, @NotNull. Изменение контракта происходит незаметно, вместе с рефакторингом, как в нашей аварии.

При contract-first сначала пишут и обсуждают спецификацию: с командой мобильного приложения, с партнёром. По ней генерируют серверные интерфейсы и клиентов, например openapi-generator с генератором spring и опцией interfaceOnly. Сервер реализует сгенерированный интерфейс, и разойтись с контрактом невозможно: изменение начинается с правки спецификации, которую видят на ревью все стороны. Цена — ещё один артефакт и шаг сборки, а сгенерированный код бывает неудобным.

Code-firstContract-first
Источник правдыКод и аннотацииФайл спецификации
Изменение контрактаНеявно, при правке кодаЯвно, ревью спецификации
ТочностьЗависит от аннотаций: коды, обязательностьКак написали
Когда подходитВнутренние API, быстрый стартПартнёры, много клиентов, параллельная разработка

Сгенерированные клиентские модели не стоит пропускать вглубь своего кода. Класс PaymentResponse из генератора меняется вместе с чужим API, поэтому его переводят в свою модель на границе — в адаптере, как в Clean & Hexagonal Architecture.

Сравнение двух версий контракта в CI ловит ломающие изменения до релиза

Если описание API хранится или генерируется на каждой сборке, его можно сравнить с описанием последнего релиза. Демо сохранило две версии, и oasdiff нашёл в «небольшом рефакторинге» вот что:

./run.sh ContractDemo                     # out/v1.json и out/v2.json
docker run --rm -v "$PWD/out":/specs:ro tufin/oasdiff breaking /specs/v1.json /specs/v2.json
5 changes: 4 error, 1 warning, 0 info
error	[request-parameter-became-required] at /specs/v2.json
	in API GET /payments
		the `query` request parameter `merchant` became required

error	[response-property-enum-value-added] at /specs/v2.json
	in API GET /payments/{id}
		added the new `REFUND_PENDING` enum value to the `status` response property for the response status `200`

warning	[request-property-removed] at /specs/v2.json
	in API POST /payments
		removed the request property `amount`

Показаны три из пяти находок; ещё две — тот же новый статус в ответах двух других методов. Обязательный параметр и новое значение enum — ошибки: старые клиенты получат 400 или упадут на незнакомом статусе. Переименование поля инструмент видит как удаление amount и добавление amountMinor. Для запроса это только предупреждение, а удаление поля из ответа он не отметил вовсе: в схеме поле необязательное, значит, клиенту и так разрешено его не получить. Неточный контракт ослепляет и проверку.

Если набор значений по замыслу растёт, его объявляют расширяемым (x-extensible-enum), и клиенты обязаны быть к этому готовы. С флагом --fail-on ERR oasdiff возвращает ненулевой код, и CI останавливает сборку. Сравнение схем ловит структурные поломки, но не смысловые: если поле amount осталось, а единицы поменялись с рублей на копейки, схема одинакова. Для этого нужны контрактные тесты.

Контрактные тесты потребителей проверяют то, что клиенты действительно используют

Схема говорит, что API может вернуть. Потребитель знает, что ему нужно на самом деле: какие поля, какие значения, в каких сценариях. Consumer-driven contracts переворачивают проверку: каждый клиент в своих тестах записывает ожидания от API, а провайдер в своей сборке проверяет, что выполняет ожидания всех клиентов.

Инструменты — Pact и Spring Cloud Contract. Pact хранит контракты в брокере и отвечает на вопрос «можно ли выкатить эту версию» по матрице проверенных пар версий. Контракт проверяет смысл: если мобильному приложению нужна сумма в рублях, его тест упадёт при переходе на копейки, даже если имя поля не изменилось.

У подхода есть цена: каждый клиент должен писать и поддерживать контрактные тесты, а это работает только когда клиенты — свои команды. С внешними партнёрами вместо контрактных тестов остаются строгая спецификация, сравнение схем, версионирование и период поддержки старой версии из API Design.

Контракт полезен, пока он точен и проверяется автоматически

Спецификация, которую никто не проверяет, расходится с реализацией за несколько релизов: документация обещает одно, сервер делает другое, и клиенты перестают ей верить. Контракт держат точным три вещи. Он генерируется или проверяется на каждой сборке. В CI сравнивается с последним релизом. И его точность проверяют тесты: ответы сервиса валидируют по схеме, например в интеграционных тестах, чтобы поймать 201, описанный как 200.

Контракт не описывает всё. В нём нет поведения под нагрузкой, лимитов, порядка событий, семантики «сумма в копейках». Эти договорённости записывают в описание полей и в документацию, а самые важные — в контрактные тесты.

Если у API есть OpenAPI-спецификация, клиенты защищены от поломок.

Спецификация защищает, только если она точна и с ней сравнивают изменения. Сгенерированная из кода без аннотаций, она отмечает все поля необязательными и неверно описывает коды ответов, и сравнение версий пропускает удаление полей из ответа.

  • OpenAPI описывает пути, параметры, схемы и коды; по нему строят документацию, клиентов и проверки.
  • Code-first описывает то, что получилось: в демо 201 описан как 200, а все поля необязательные. Contract-first делает изменение контракта явным.
  • oasdiff в CI нашёл обязательный параметр и новый enum как ошибки, переименование — только как предупреждение.
  • Контрактные тесты потребителей проверяют реальное использование и смысл, но требуют, чтобы клиенты были своими.
  • Сгенерированные модели переводят в свои на границе; /v3/api-docs в проде закрывают.

На собеседовании

Contract-first или code-first: что выбрать?

Code-first — спецификацию генерирует библиотека вроде springdoc из кода. Быстро и всегда синхронно, но точность зависит от аннотаций, а изменение контракта происходит незаметно при рефакторинге. Contract-first — сначала пишут и согласуют спецификацию, по ней генерируют интерфейсы сервера и клиентов. Изменение контракта видно на ревью всем сторонам.

Для внутренних API с одним-двумя клиентами хватает code-first с проверкой в CI. Для партнёров и множества клиентов лучше contract-first.

  • Code-first без аннотаций описывает все поля необязательными и не видит реальных кодов ответа: в демо 201 описан как 200.
  • Сгенерированные клиентские модели переводят в свою модель на границе, чтобы чужой API не протекал в домен.
  • Точность спецификации проверяют валидацией реальных ответов по схеме в тестах.

Как не выпустить ломающее изменение API?

Сравнивать спецификацию с последним релизом в CI, например oasdiff с --fail-on ERR. Он находит удалённые поля и эндпоинты, новые обязательные параметры, сменённые типы и новые значения enum. Для смысловых изменений и реального использования нужны контрактные тесты потребителей: Pact или Spring Cloud Contract.

  • Переименование поля для инструмента — удаление и добавление; в ответе с необязательными полями удаление может не считаться ломающим.
  • Растущие наборы значений объявляют как x-extensible-enum и требуют от клиентов терпимого чтения.
  • can-i-deploy в Pact проверяет совместимость конкретных версий провайдера и клиентов перед выкаткой.
Почему проверка совместимости в CI пропустила удаление поля из ответа? 
record Payment(String id, long amount, String currency, Status status) {} // v1
record Payment(String id, long amountMinor, String currency, Status status) {} // v2
// springdoc генерирует схему, CI сравнивает: ошибок по ответу нет.

В сгенерированной схеме ни одно поле не обязательное, поэтому amount в ответе формально можно не присылать, и его удаление инструмент не считает ломающим. Клиенты при этом рассчитывали на поле. Нужно отмечать обязательные поля (например, @Schema(requiredMode = REQUIRED)) и проверять реальные ответы по схеме в тестах.

Что такое consumer-driven contracts?

Каждый потребитель в своих тестах описывает, что ему нужно от API: запросы, поля и значения ответов. Эти контракты публикуются в брокер, а сборка провайдера проверяет, что настоящий сервис их выполняет. Провайдер узнаёт о поломке клиента до релиза и может свободно менять то, что никто не использует.

  • Проверяют смысл, а не только структуру: смена единиц суммы ломает контракт при том же имени поля.
  • Работают, когда клиенты — свои команды; с внешними партнёрами остаются спецификация и версионирование.
  • OpenAPI Specification — основа урока: пути, параметры, схемы, коды ответов.
  • oasdiff — проверки совместимости и список ломающих изменений.
  • springdoc-openapi — генерация описания из Spring MVC, аннотации @Schema и @ApiResponse.
  • Pact и Martin Fowler: Consumer-Driven Contracts — контрактные тесты потребителей.
