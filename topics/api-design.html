API: REST

REST — стиль, в котором API — это набор ресурсов с адресами, а действия над ними выражаются стандартными методами и кодами HTTP. Платёж — ресурс /payments/p-1, его создание — POST в коллекцию, ответ — 201 и адрес нового ресурса. Бизнес-действие вроде списания тоже становится ресурсом: /payments/p-1/captures. Ответ показывает текущее состояние и ссылки на действия, которые сейчас допустимы. Долгая операция возвращает 202 и адрес, где следить за результатом. Когда API следует этим правилам, клиенты, прокси и кеши понимают его без отдельного описания каждого эндпоинта.

API из глаголов приходится заучивать по одному эндпоинту

Первая версия платёжного API выглядела так: POST /createPayment, POST /capturePayment, POST /cancelPayment?id=17, POST /getPaymentStatus. Всё через POST, всё возвращает 200 с полем success. Каждый эндпоинт — отдельный договор: что принимает, что возвращает, можно ли повторить, что значит ошибка. Клиент не может закешировать статус, прокси не может повторить безопасный запрос, мониторинг не видит ошибок, потому что код всегда 200.

Это RPC поверх HTTP: HTTP используется как транспорт, а его семантика выброшена. REST предлагает обратное: смоделировать предметную область как ресурсы и выразить работу с ними через то, что HTTP уже умеет. Семантика методов и кодов разобрана в HTTP; здесь — как построить на ней API. Демо RestDemo.java поднимает на loopback маленький платёжный API на встроенном HttpServer и проходит жизненный цикл платежа: java RestDemo.java на JDK 21.

Ресурс — существительное с адресом, и действие тоже можно сделать ресурсом

Ресурс — то, о чём можно говорить отдельно: платёж, магазин, возврат, выписка. У него есть адрес и представление. Коллекция /payments содержит платежи, /payments/p-1 — один платёж. Адрес описывает, что это, а метод — что с ним сделать, поэтому глаголов в адресе нет.

Самый частый вопрос — как выразить бизнес-действие, которое не похоже на создание или изменение поля. Ответ: превратить действие в ресурс. Возврат — не изменение платежа, а новый объект со своим id, суммой, статусом и историей. POST /payments/p-1/refunds создаёт возврат, и его можно потом получить, перечислить все возвраты платежа и повторить запрос с ключом идемпотентности. Альтернатива PATCH /payments/p-1 {"status": "REFUNDED"} прячет бизнес-операцию за изменением поля и теряет её данные: какую сумму вернули, кто, когда.

Адрес не обязан повторять схему базы. Таблица payment_events не должна стать ресурсом только потому, что существует, а ресурс «выписка за день» может собираться из пяти таблиц. Вложенность держат неглубокой: /payments/p-1/refunds/r-3 ещё читается, а пять уровней означают, что ресурс заслуживает собственного корня /refunds/r-3.

Метод и код ответа сообщают результат без чтения тела

show(client, "POST", base + "/payments", "{\"amount\":500}");
show(client, "POST", base + "/payments/p-1/cancellations", "{}"); // После списания.
show(client, "DELETE", base + "/payments/p-1", null);              // Удалять платёж нельзя.
show(client, "GET", base + "/payments/p-404", null);
POST /payments -> 201 Location: /payments/p-1
    {"id":"p-1","status":"AUTHORIZED","links":{"self":"/payments/p-1","capture":"/payments/p-1/captures","cancel":"/payments/p-1/cancellations"}}
POST /payments/p-1/cancellations -> 409
    {"title":"payment is CAPTURED, cancellations not allowed","instance":"/payments/p-1"}
DELETE /payments/p-1 -> 405 Allow: GET
GET /payments/p-404 -> 404
    {"title":"payment not found","instance":"/payments/p-404"}

Каждый ответ понятен по коду. 201 с Location — ресурс создан, вот его адрес; клиенту не нужно собирать URL самому. 409 Conflict — запрос корректен, но противоречит текущему состоянию: списанный платёж нельзя отменить. Это не 400 (запрос не битый) и не 422 (данные не противоречат правилам сами по себе). 405 с заголовком Allow говорит, какие методы ресурс поддерживает. 404 — такого платежа нет. Тело ошибки здесь в формате Problem Details из RFC 9457; правила его оформления и версионирования API — в API Design.

Выбор метода определяет, что посредники могут делать с запросом. GET безопасен и кешируем, PUT и DELETE идемпотентны, POST — нет, поэтому создание платежа требует ключа идемпотентности. Подробно — в HTTP.

Ответ показывает состояние и ссылки на действия, которые сейчас допустимы

В представлении платежа демо есть поле links. Его содержимое зависит от состояния: авторизованный платёж можно списать или отменить, списанный — только вернуть.

GET /payments/p-1 -> 200
    {"id":"p-1","status":"AUTHORIZED","links":{"self":"/payments/p-1","capture":"/payments/p-1/captures","cancel":"/payments/p-1/cancellations"}}
GET /payments/p-1 -> 200
    {"id":"p-1","status":"CAPTURED","links":{"self":"/payments/p-1","refund":"/payments/p-1/refunds"}}

Это HATEOAS — гипермедиа как механизм состояния приложения. Клиент не хранит у себя таблицу переходов статусов: он показывает кнопку «Вернуть», если в ответе есть ссылка refund. Когда бизнес добавит правило «возврат только в течение 180 дней», сервер просто перестанет отдавать ссылку, и мобильное приложение не потребует релиза. Форматы HAL, JSON:API и Siren стандартизируют, как оформлять такие ссылки.

На практике почти все API, которые называют REST, — уровень 2, и этого обычно хватает. Филдинг, автор REST, считает гипермедиа обязательной частью стиля, но для внутренних API между сервисами её польза мала: клиент всё равно пишется под конкретный API. Уровень 3 окупается там, где поведение клиента зависит от состояния и клиентов много: мобильные приложения, партнёрские интеграции.

Долгая операция возвращает 202 и адрес, где следить за результатом

Списание ждёт ответа банка, а он может прийти через несколько секунд. Держать HTTP-запрос открытым всё это время плохо: соединения клиента и балансировщика имеют таймауты, а повтор после обрыва может провести списание дважды. Вместо этого сервер принимает задачу и сразу отвечает 202 Accepted с адресом ресурса операции.

POST /payments/p-1/captures -> 202 Location: /operations/op-2
    {"operation":"op-2","status":"RUNNING"}
GET /operations/op-2 -> 200 Retry-After: 1
    {"operation":"op-2","status":"RUNNING"}
GET /operations/op-2 -> 200
    {"operation":"op-2","status":"DONE","links":{"payment":"/payments/p-1"}}

Опрос прост и надёжен: клиент сам решает, когда спросить, а потерянный ответ безопасно повторить, потому что GET идемпотентен. Минус — лишние запросы. Альтернатива — вебхук: клиент при создании передаёт адрес, и сервер сам отправит туда результат. Вебхук быстрее, но требует от клиента публичного адреса, повторов при недоступности, проверки подписи и защиты от дублей. Часто делают оба: вебхук для скорости и опрос как запасной путь.

REST хорош для ресурсов и плох для процессов, которые не ложатся на них

REST требует, чтобы каждый запрос был самодостаточным: сервер не хранит состояние сеанса клиента между запросами. Всё нужное — кто клиент, какой ресурс, какая версия — приходит в самом запросе: токен в Authorization, id в адресе, ETag в If-Match. Поэтому любой экземпляр сервиса может обработать любой запрос, а балансировщику не нужна привязка клиента к экземпляру.

У стиля есть пределы. Чтение сложного графа — платёж, магазин, возвраты, история — превращается в серию запросов или в специальный ресурс-проекцию, и тут GraphQL удобнее. Частые вызовы между сервисами с жёстким контрактом и стримингом удобнее делать на gRPC. Команды, которые не ложатся на ресурсы, вроде «пересчитать комиссии за месяц», честнее выразить ресурсом-задачей POST /fee-recalculations, чем притворяться, что это обновление поля. Сравнение стилей — в gRPC, GraphQL, SOAP.

REST — это когда CRUD-операции над таблицами базы выставлены как GET, POST, PUT и DELETE.

REST — про ресурсы предметной области и их состояние, а не про таблицы. API, повторяющий схему базы, переносит её в договор с клиентами: любое изменение таблиц ломает клиентов. Бизнес-действия вроде списания и возврата — тоже ресурсы, со своими данными и историей.

В Spring такой API строится на @RestController: ResponseEntity.created(uri) даёт 201 с Location, ResponseEntity.accepted() — 202, Spring HATEOAS собирает ссылки, а ProblemDetail оформляет ошибки. Путь запроса через Spring MVC разобран в Spring MVC.

  • Ресурс — существительное с адресом; метод говорит, что сделать. Бизнес-действие оформляют ресурсом со своими данными: refunds, captures.
  • Коды отвечают без чтения тела: 201 с Location, 202 для долгих операций, 409 для конфликта с состоянием, 405 с Allow.
  • Ссылки в ответе показывают допустимые сейчас действия; большинство API — уровень 2 Ричардсона, и этого обычно хватает.
  • Долгая операция: 202, ресурс операции, опрос с Retry-After или вебхук.
  • REST не копирует схему базы; графы данных и потоковые вызовы лучше ложатся на GraphQL и gRPC.

На собеседовании

Что такое REST и чем REST API отличается от RPC поверх HTTP?

REST — архитектурный стиль: система — набор ресурсов с адресами, работа с ними идёт стандартными методами HTTP, сервер не хранит состояние сеанса, ответы можно кешировать, а представления содержат ссылки на связанные ресурсы и действия. В RPC поверх HTTP адреса — это имена функций, почти всё идёт через POST, а результат — в теле с кодом 200.

Польза REST — единый договор: клиенты, прокси и кеши понимают методы и коды без описания каждого эндпоинта. Например, GET платежа можно закешировать и безопасно повторить.

  • Модель зрелости Ричардсона: 0 — один адрес, 1 — ресурсы, 2 — методы и коды, 3 — гипермедиа. Большинство API — уровень 2.
  • Бизнес-действия моделируют ресурсами-существительными: refunds, captures, а не PATCH поля status.
  • Отсутствие состояния сеанса на сервере позволяет любому экземпляру обработать любой запрос.

Как в REST выразить действие, которое не похоже на CRUD, например возврат?

Сделать действие ресурсом. Возврат — новый объект: POST /payments/p-1/refunds создаёт возврат с id, суммой и статусом, его можно потом получить и перечислить. Это лучше, чем PATCH платежа со статусом REFUNDED: теряется информация о самой операции, а частичные и повторные возвраты не выразить.

Если действие долгое, ресурс операции возвращают с кодом 202 и адресом, где следить за результатом.

  • POST на ресурс-действие не идемпотентен, поэтому ему нужен ключ идемпотентности.
  • Нарушение правил состояния — 409 Conflict, а не 400: запрос корректен, но не подходит к текущему состоянию.
Что не так с этим API возвратов? 
PATCH /payments/p-1
{"status": "REFUNDED", "refundAmount": 200}
→ 200 {"success": false, "error": "refund window expired"}

Возврат спрятан в изменение полей платежа: второй частичный возврат перезапишет первый, истории нет. Ошибка бизнес-правила возвращается с кодом 200, поэтому мониторинг и клиентская библиотека считают её успехом. Нужен ресурс возвратов POST /payments/p-1/refunds с ответом 201 и Location, а отказ по правилу — 409 или 422 с Problem Details.

Как сделать в REST долгую операцию?

Сервер принимает задачу и сразу отвечает 202 Accepted с заголовком Location на ресурс операции. Клиент опрашивает этот ресурс, сервер подсказывает интервал заголовком Retry-After, а по завершении операция содержит ссылку на результат. Так не нужно держать соединение открытым и рисковать таймаутом.

Альтернатива — вебхук: сервер сам вызывает адрес клиента, когда операция закончилась.

  • Вебхуку нужны повторы, подпись запроса и защита от дублей на стороне клиента; опрос остаётся запасным путём.
  • Ресурс операции хранит статус и ошибку, чтобы клиент мог узнать результат даже после обрыва.

Что такое HATEOAS и нужен ли он на практике?

Ответ содержит не только данные, но и ссылки на действия, доступные в текущем состоянии. Авторизованный платёж приходит со ссылками capture и cancel, списанный — только с refund. Клиент показывает кнопки по ссылкам и не хранит у себя правила переходов.

Для внутренних API между сервисами польза небольшая. Для мобильных и партнёрских клиентов полезно: сервер меняет правила, не выпуская новую версию клиента.

  • Форматы ссылок: HAL, JSON:API, Siren; в Spring — Spring HATEOAS.
  • Ссылки не отменяют версионирование: изменение формата данных всё равно ломает клиентов.
  • Roy Fielding, Architectural Styles and the Design of Network-based Software Architectures, глава 5 — основа урока: ограничения REST, ресурсы, гипермедиа.
  • Martin Fowler: Richardson Maturity Model — уровни зрелости с примерами.
  • RFC 9110: HTTP Semantics — 201 с Location, 202, 405 с Allow, 409.
  • Google API Improvement Proposals: AIP-151 Long-running operations — ресурс операции для долгих действий.
