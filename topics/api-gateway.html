API Gateway & Service Discovery

API-шлюз — единая точка входа для внешних клиентов: он маршрутизирует запросы к сервисам по пути, проверяет аутентификацию, ограничивает частоту и добавляет сквозные заголовки вроде идентификатора запроса, чтобы каждый сервис не делал этого сам. Шлюз не должен содержать бизнес-логики и сам становится критичным компонентом: его резервируют и масштабируют. Обнаружение сервисов отвечает на вопрос, по какому адресу сейчас живут экземпляры: реестр (Consul, Eureka) или DNS платформы (Kubernetes, Docker). Типичная ловушка — прокси, который разрешает имя один раз: в демо nginx с именем в upstream отправил все 30 запросов на старый экземпляр и не заметил новый, а с resolver и именем в переменной распределил запросы по трём.

Каждый сервис сам проверяет токен и сам считает лимиты

Мобильное приложение обращается к десяти сервисам напрямую. В каждом своя проверка JWT — в трёх уже забыли проверить срок действия, — свои лимиты, своя схема логирования, и клиенту известны десять адресов. Переименование или разделение сервиса ломает старые версии приложения, которые обновятся через месяцы. Шлюз прячет внутреннее устройство за одним адресом и делает общие вещи в одном месте.

Тема разбирает обязанности шлюза, обнаружение сервисов и связанные ловушки. Демо gateway.sh поднимает в Docker-сети шлюз на nginx 1.31, сервис аутентификации и сервисы orders и users в нескольких экземплярах; экземпляры одного сервиса имеют общее сетевое имя, как поды за Service в Kubernetes. Балансировка между экземплярами — в Load Balancing, лимиты — в Rate Limiting.

Маршрутизация, аутентификация, лимиты — в одном месте

location = /_auth {                           # подзапрос к сервису аутентификации
    internal;
    proxy_pass http://auth:8080/auth;
    proxy_pass_request_body off;
    proxy_set_header Content-Length "";
}
location /orders/ {
    auth_request /_auth;                       # 2xx — пропустить, 401/403 — отказать
    limit_req zone=perclient burst=2 nodelay;  # 5 r/s на токен
    limit_req_status 429;
    set $orders http://orders:8080;
    proxy_set_header X-Request-Id $request_id; # сквозной идентификатор для логов и трассировки
    proxy_set_header X-User anna;              # шлюз передаёт сервису, кто пользователь
    proxy_pass $orders;
}
== routing and authentication at the gateway
   GET /orders/42, no token           401 401 Authorization Required
   GET /orders/42, bad token          401 401 Authorization Required
   GET /orders/42, good token         200 orders-2 req=<32 hex> user=anna
   GET /users/7, good token           200 users-1 req=<32 hex> user=
== rate limit 5 r/s, burst 2: 10 requests at once
   200 200 200 429 429 429 429 429 429 429

Без токена и с плохим токеном шлюз отвечает 401, не дойдя до сервиса: сервис аутентификации вернул 401 на подзапрос auth_request. С хорошим токеном запрос ушёл в orders с добавленными X-Request-Id (случайный, заменён в выводе заглушкой) и X-User. Из 10 одновременных запросов лимит пропустил 3 — один по скорости и два из запаса burst, — остальные получили 429. В маршруте /users/ заголовок X-User не задан — сервис его не получил: каждую сквозную функцию нужно включить в каждом маршруте, и это довод в пользу шлюзов с общими фильтрами.

== cost of auth_request: 300 sequential requests
   /plain/ (no auth_request): 0.59 ms per request
   /users/ (auth_request):    0.65 ms per request

Подзапрос к сервису аутентификации на каждый запрос здесь почти ничего не стоит — 0,06 мс, — потому что всё работает в одной Docker-сети на одной машине. В продакшене к каждому запросу добавится круг по сети до сервиса аутентификации и его работа, а при его отказе отказывает весь API. Поэтому выбор способа проверки — важное решение для шлюза:

СпособКакЦена
Локальная проверка JWTШлюз проверяет подпись по публичному ключу (JWKS) и срокБез сетевого вызова; отзыв токена — только по истечении срока
ИнтроспекцияШлюз спрашивает сервер авторизации, жив ли токен (как auth_request)Круг по сети на запрос; кешируют результат на секунды
Обмен токенаВнешний непрозрачный токен меняется на короткий внутренний JWTВнешний токен легко отозвать, внутренние сервисы проверяют локально

Шлюз проверяет, кто пользователь, но не что ему можно с конкретным заказом: это решает сервис, который знает владельца заказа. Сервис не должен слепо доверять заголовку X-User, если до него можно дойти в обход шлюза; внутренний трафик защищают сетью и mTLS или передают подписанный токен, а не голый заголовок.

Типичный набор обязанностей шлюза: маршрутизация и версии API, завершение TLS, аутентификация (проверка подписи JWT или обмен непрозрачного токена на внутренний, как в OAuth2 / OIDC), лимиты на клиента, идентификатор запроса и начало трассы, CORS, сжатие, иногда кеш. Бизнес-правила — нет: шлюз, который знает, какие заказы можно отменять, становится распределённым монолитом, через который должен проходить каждый релиз. В Java-экосистеме — Spring Cloud Gateway, в инфраструктуре — nginx, Kong, Envoy, облачные шлюзы.

Обнаружение сервисов: прокси, который разрешил имя один раз

upstream users { server users:8080; }          # имя разрешается один раз, при старте nginx
resolver 127.0.0.11 valid=1s ipv6=off;        # DNS Docker; нужен для переменной ниже
set $orders http://orders:8080;               # имя в переменной — разрешается заново по TTL
proxy_pass $orders;
== discovery: start orders-3 and users-2, then send 30 requests to each
   /orders/ (name in a variable, resolver valid=1s): orders-1=8 orders-2=11 orders-3=11
   /users/  (name resolved at nginx start):         users-1=30

Демо запускает третий экземпляр orders и второй экземпляр users. Маршрут /orders/ держит имя в переменной и с resolver перечитывает DNS раз в секунду — новый экземпляр сразу получил свою треть запросов (точное распределение меняется от запуска к запуску). Маршрут /users/ записан через upstream: nginx разрешил имя при старте, когда экземпляр был один, и все 30 запросов ушли на users-1; users-2 не получит трафика до перезагрузки конфигурации. Та же ловушка у Java: InetAddress кеширует успешные ответы DNS, а HTTP-клиент держит открытые соединения со старыми адресами, поэтому новые экземпляры получают трафик с задержкой, а удалённые ещё какое-то время получают запросы.

СпособКак узнают адресаПримеры
СерверныйКлиент идёт на один адрес, балансировщик знает экземплярыKubernetes Service (ClusterIP), облачный балансировщик
КлиентскийКлиент получает список из реестра и балансирует самEureka + Spring Cloud LoadBalancer, gRPC с headless Service
DNSИмя разрешается во все адреса экземпляровDocker, headless Service, Consul DNS
Сервисная сетьSidecar-прокси получает адреса от управляющего слояIstio, Linkerd на Envoy

Реестр должен знать не только адреса, но и здоровье: экземпляр регистрируется при старте, подтверждает жизнь сердцебиениями и удаляется при остановке или пропаже сердцебиений. В Kubernetes это делает платформа: под попадает в Endpoints, когда проходит readiness-пробу, и исчезает при остановке, поэтому отдельный реестр в Kubernetes обычно не нужен. Клиентское обнаружение даёт гибкость — свой алгоритм балансировки, повторы, учёт зон, — но каждый клиент должен его реализовать; серверное проще для клиентов, но добавляет переход по сети.

Шлюз как точка отказа, BFF и агрегация

Все внешние запросы идут через шлюз, поэтому его отказ — отказ всего API. Его разворачивают в нескольких экземплярах за L4-балансировщиком в нескольких зонах, держат без состояния (лимиты — в общем хранилище, как в Rate Limiting) и выкатывают изменения конфигурации постепенно. Каждая функция в шлюзе добавляет задержку ко всем запросам — подзапрос auth_request на каждый запрос стоит круга по сети, поэтому результат проверки кешируют на короткое время или проверяют подпись JWT локально.

Backend for Frontend — отдельный шлюз для каждого типа клиента: мобильному приложению нужен компактный ответ одним запросом, веб-приложению — другой набор данных. BFF собирает ответ из нескольких сервисов (агрегация, API composition) и принадлежит команде клиента. Агрегация в шлюзе превращает один запрос клиента в несколько внутренних — их делают параллельно, с тайм-аутами и частичным ответом при отказе второстепенного сервиса, иначе задержка и недоступность перемножаются, как в Monolith & Microservices.

Достаточно указать в прокси DNS-имя сервиса, и новые экземпляры начнут получать трафик автоматически.

Многие прокси и клиенты разрешают имя один раз или кешируют ответ надолго. В демо nginx с именем в upstream отправил все 30 запросов на старый users-1 и не увидел users-2. Нужен явный повторный опрос DNS (resolver с переменной, настройки кеша DNS в JVM) или обнаружение через реестр.

  • Шлюз — единая точка входа: маршрутизация, TLS, аутентификация, лимиты, X-Request-Id; бизнес-логики в нём нет.
  • Демо: без токена — 401 на шлюзе; лимит 5 r/s с burst 2 пропустил 3 запроса из 10.
  • Проверка токена: локально по JWKS, интроспекцией с кешем или обменом на внутренний токен; права на объект проверяет сервис.
  • Обнаружение: серверное, клиентское, DNS, сервисная сеть; реестр знает и здоровье.
  • nginx с именем в upstream разрешил его при старте — новый экземпляр не получил ни одного запроса из 30; resolver с переменной распределил по трём.
  • Шлюз резервируют и держат без состояния; BFF — шлюз под клиента с агрегацией параллельными вызовами.

На собеседовании

Зачем нужен API-шлюз и что в нём делать не стоит?

Единая точка входа для внешних клиентов: скрывает внутреннее устройство, маршрутизирует по пути и версии, завершает TLS, проверяет аутентификацию, ограничивает частоту, добавляет идентификатор запроса и начинает трассу. Бизнес-логику туда не кладут — иначе шлюз становится монолитом, через который проходит каждый релиз.

  • Шлюз — критичный компонент: несколько экземпляров, без состояния, постепенная выкатка.
  • Каждая функция добавляет задержку ко всем запросам; проверку токена кешировать или делать локально.
  • BFF — отдельный шлюз под тип клиента с агрегацией.

Как сервисы находят друг друга?

Через реестр или DNS платформы. Серверное обнаружение — клиент идёт на один адрес, балансировщик знает экземпляры (Kubernetes Service). Клиентское — клиент получает список из реестра (Eureka, Consul) и балансирует сам. Экземпляры регистрируются при старте, подтверждают жизнь и удаляются при остановке.

  • Кеширование DNS в прокси и JVM: новые экземпляры не получают трафик, удалённые получают.
  • В Kubernetes Endpoints обновляет платформа по readiness; отдельный реестр не нужен.
Почему после масштабирования payments с 2 до 6 подов нагрузка не перераспределилась? 
# ingress-шлюз собран вручную на nginx
upstream payments { server payments.prod.svc.cluster.local:8080; }   # headless Service
location /payments/ { proxy_pass http://payments; }

Для headless Service DNS возвращает адреса подов, а nginx разрешает имя в upstream один раз при запуске или перезагрузке конфигурации. Шлюз продолжает слать запросы двум старым подам; новые четыре не получат трафика до перезагрузки, а если старые поды удалят, шлюз будет ходить на несуществующие адреса. Нужен resolver с именем в переменной, обычный ClusterIP Service вместо headless или ingress-контроллер, который следит за Endpoints.

Что такое Backend for Frontend?

Отдельный шлюз для каждого типа клиента — мобильного, веба, партнёрского API. Он собирает ответ из нескольких сервисов под нужды конкретного клиента, адаптирует формат и принадлежит команде этого клиента. Вызовы к сервисам делает параллельно, с тайм-аутами и частичным ответом.

  • Агрегация в одном общем шлюзе для всех клиентов быстро обрастает частными случаями.
  • GraphQL — альтернатива BFF: клиент сам выбирает поля.
  • microservices.io: API Gateway / BFF, Client-side discovery, Server-side discovery.
  • nginx: auth_request, resolver.
  • Spring Cloud Gateway.
  • Azure Architecture: Backends for Frontends.
