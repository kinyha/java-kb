API: Design Practices

Хороший API переживает изменения данных и самого себя. Пагинация по смещению ломается, когда между запросами появляются новые записи, и дорожает с глубиной; курсор по ключу сортировки стабилен и быстр. Фильтры и сортировки принимают только из разрешённого списка. Ошибки возвращают в одном формате Problem Details с машинным кодом. Изменения бывают совместимыми — добавить поле — и ломающими — переименовать поле или добавить значение enum для строгих клиентов. Ломающие изменения выпускают новой версией с периодом поддержки старой.

Партнёр выгружает платежи постранично и получает дубли, а старое приложение падает на новом статусе

Магазин-партнёр каждую ночь выгружает свои платежи через API постранично. Однажды сверка показала, что один платёж выгрузился дважды, а другой не выгрузился вовсе. В тот же день вышла новая версия бэкенда со статусом REFUND_PENDING, и старая версия мобильного приложения начала падать при открытии истории. Ни один эндпоинт не изменился, и ни один тест не упал.

Обе аварии — про договор API во времени: данные меняются между запросами клиента, а сам API меняется между релизами. REST-основы — ресурсы, методы, коды — разобраны в REST; здесь — практики, которые делают API устойчивым. Демо PagingDemo.java воспроизводит обе аварии: java PagingDemo.java на JDK 21. Цена глубокой пагинации измерена в PostgreSQL 17 в контейнере.

Страница по смещению сдвигается от новых записей, а курсор держится за ключ

Самая простая пагинация — ?offset=3&limit=3, в SQL LIMIT 3 OFFSET 3. Страница — это позиция в списке на момент запроса. Если между запросами в начало списка попала новая запись, все позиции сдвигаются на одну:

offsetPage(0, 3);                        // Первая страница.
table.add(new Payment(107, "CAPTURED")); // Новый платёж между запросами.
offsetPage(3, 3);                        // Вторая страница.

cursorPage(null, 3);                     // Первая страница, курсор = последний id.
table.add(new Payment(107, "CAPTURED"));
cursorPage(104L, 3);                     // «Всё, что старше 104».
== offset paging while a payment arrives
page 1 (offset 0): [106, 105, 104]
page 2 (offset 3): [104, 103, 102]
== cursor paging while a payment arrives
page 1: [106, 105, 104], next cursor=104
page 2 (after 104): [103, 102, 101]

Курсорная (keyset) пагинация запоминает не позицию, а ключ последней увиденной записи: «дай 20 платежей с id меньше 104». Вставки и удаления в начале списка на неё не влияют. Второе преимущество — цена. База не умеет перепрыгнуть на позицию 900 000: она читает и отбрасывает все предыдущие строки. Таблица на миллион платежей в PostgreSQL 17:

select id from payment order by id desc limit 20 offset 900000;        -- Глубокая страница по смещению.
select id from payment where id < 100001 order by id desc limit 20;    -- Та же страница по курсору.
== offset 900000

== keyset after 100001

Смещение прочитало 900 020 строк индекса ради двадцати и заняло 67 мс; курсор прочитал ровно 20 за сотые доли миллисекунды. Цена смещения растёт линейно с глубиной, цена курсора от глубины не зависит. Время снято на машине автора, отношение будет похожим везде.

Курсор отдают клиенту непрозрачной строкой, например закодированными в base64 значениями сортировки, и клиент возвращает её как есть: ?cursor=eyJpZCI6MTA0fQ&limit=20. Если сортировка не по уникальному полю, в курсор добавляют id для разрешения равенства: (created_at, id) < (:t, :id), иначе записи с одинаковым временем потеряются на границе страниц. Минусы курсора: нельзя перейти сразу на 50-ю страницу и показать «страница 7 из 312». Общее количество — отдельный COUNT(*), который на больших таблицах дорог, поэтому его делают необязательным или приблизительным.

Фильтр и сортировку принимают из разрешённого списка, а порядок делают однозначным

Фильтры передают параметрами запроса: GET /payments?merchant=m-7&status=CAPTURED&createdFrom=2026-10-01, сортировку — sort=-createdAt. Соблазн — принимать любое поле и подставлять его в запрос. Это сразу три проблемы. Сортировка по полю без индекса превращает запрос в полный перебор таблицы. Имя поля, подставленное в SQL строкой, открывает SQL-инъекцию: параметры PreparedStatement защищают значения, но не имена колонок. А внутренние поля становятся частью договора, и их уже не переименовать.

Поэтому API объявляет конечный список: эти поля фильтруются, эти сортируются, для каждого сочетания есть индекс. Неизвестный параметр — ошибка 400, а не молчаливое игнорирование: иначе опечатка ?stauts=FAILED вернёт все платежи, и партнёр не заметит. Сортировка обязана быть однозначной: если сортируют по дате, вторым ключом добавляют id. Без этого две записи с одинаковой датой база вправе вернуть в разном порядке на разных страницах.

Все ошибки приходят в одном формате с машинным кодом

Каждая команда придумывала свой формат ошибок: где-то {"error": "..."}, где-то {"message": ..., "code": 17}, где-то HTML-страница от балансировщика. Клиенту приходится писать разбор на каждый случай. RFC 9457 Problem Details задаёт общий формат с типом application/problem+json:

{
  "type": "https://api.pay.example/problems/refund-window-expired",
  "title": "Refund window expired",
  "status": 409,
  "detail": "Payment p-1 was captured 190 days ago, refunds are allowed for 180 days.",
  "instance": "/payments/p-1/refunds",
  "errors": [{"field": "amount", "code": "exceeds_captured"}]
}

type — стабильный машинный идентификатор проблемы: клиент ветвится по нему, а не по тексту, который может перевестись или поменяться. title и detail — для человека. Дополнительные поля вроде списка ошибок валидации разрешены. В ответ не кладут стектрейсы, SQL и внутренние имена классов: это подсказки атакующему. Для разбора ошибки на стороне сервера достаточно trace id в заголовке или в поле расширения. Spring поддерживает формат через ProblemDetail, как разобрано в Validation & Errors.

Добавить поле безопасно, а добавить значение enum — нет, если клиент строгий

Изменение API совместимо, если старые клиенты продолжают работать без изменений. Добавить новое необязательное поле в ответ, новый эндпоинт, новый необязательный параметр — совместимо. Удалить или переименовать поле, поменять тип, сделать параметр обязательным, поменять смысл кода ответа — ломает. Самый коварный случай — новое значение в перечислении:

enum Status { AUTHORIZED, CAPTURED, REFUNDED }          // Так клиент знал API при сборке.

static Status strict(String s) { return Status.valueOf(s); }  // Неизвестное — исключение.
static Optional<Status> tolerant(String s) {                     // Неизвестное — пусто.
    try { return Optional.of(Status.valueOf(s)); } catch (IllegalArgumentException e) { return Optional.empty(); }
}
strict CAPTURED -> CAPTURED
tolerant CAPTURED -> CAPTURED
strict REFUND_PENDING -> IllegalArgumentException
tolerant REFUND_PENDING -> UNKNOWN

Сервер ничего не удалил, только добавил статус, а строгий клиент упал — та самая авария с историей платежей. Защищаются с двух сторон. Клиент следует принципу терпимого читателя (tolerant reader): игнорирует неизвестные поля и отображает неизвестные значения как «другое», а не падает. Jackson по умолчанию падает на неизвестном поле, но Spring Boot это отключает; на неизвестное значение enum есть отдельная настройка READ_UNKNOWN_ENUM_VALUES_USING_DEFAULT_VALUE. Сервер в документации заранее предупреждает, что набор значений может расширяться.

Проверять совместимость руками ненадёжно. Схему OpenAPI сравнивают между версиями инструментами вроде oasdiff в CI, а договор с конкретными клиентами фиксируют контрактными тестами — это тема OpenAPI & Contracts.

Ломающее изменение выходит новой версией, а старая живёт объявленный срок

Когда ломающее изменение неизбежно, его выпускают как новую версию, а старая продолжает работать. Версию передают в пути (/v2/payments), в заголовке (Api-Version: 2026-10-01) или в типе содержимого (Accept: application/vnd.pay.v2+json). Версия в пути самая наглядная: её видно в логах, её легко маршрутизировать на балансировщике. Версия-дата в заголовке, как у Stripe, позволяет менять API мелкими шагами без пересадки клиентов на целиком новую версию.

ШагЧто делает сервер
РасширитьДобавляет новое поле или эндпоинт рядом со старым, оба работают
ОбъявитьПомечает старое заголовками Deprecation и Sunset с датой отключения, пишет клиентам
НаблюдатьМетрики показывают, кто ещё вызывает старое
СократитьПосле даты отключает старое

Это схема «расширить — сократить» (expand-contract), та же, что для миграций базы без простоя. Заголовок Sunset стандартизирован в RFC 8594, Deprecation — в RFC 9745. Главное правило — не держать несколько версий вечно: каждая живая версия умножает код, тесты и место для ошибок. Срок поддержки объявляют заранее, а мобильным клиентам дают больше времени, потому что старые версии приложений живут на телефонах годами.

  • Offset сдвигается от вставок и удалений и дорожает с глубиной: в опыте 900 020 строк ради 20. Курсор по ключу стабилен и не зависит от глубины.
  • Фильтры и сортировки — из разрешённого списка с индексами; неизвестный параметр — 400; сортировка однозначна с id.
  • Ошибки — Problem Details: машинный type, человеческий detail, без стектрейсов.
  • Добавить поле совместимо; новое значение enum ломает строгих клиентов — клиенты читают терпимо.
  • Ломающее изменение — новая версия, Deprecation и Sunset, метрики использования и отключение в срок.

На собеседовании

Чем курсорная пагинация лучше пагинации по смещению?

Смещение считает позиции в текущем списке. Если между запросами в начало добавилась запись, следующая страница повторит последнюю запись предыдущей, а если удалилась — одну пропустит. И база читает все строки до смещения: в опыте OFFSET 900000 прочитал 900 020 строк и занял 67 мс.

Курсор запоминает ключ последней записи и просит «всё, что меньше него». Вставки в начало не мешают, и запрос идёт по индексу за постоянное время — 0,023 мс в том же опыте.

  • При сортировке по неуникальному полю курсор включает id: (created_at, id) < (:t, :id).
  • Курсор отдают непрозрачной строкой, чтобы клиенты не строили его сами и не зависели от формата.
  • Минусы: нельзя прыгнуть на произвольную страницу, общее число — отдельный дорогой COUNT.

Какие изменения API ломают клиентов и как развивать API без поломок?

Ломают удаление и переименование полей, смена типа, новый обязательный параметр, изменение смысла кода ответа. Коварный случай — новое значение enum: строгий клиент, который делает Enum.valueOf, падает, хотя ничего не удалено. Совместимо — добавлять необязательные поля, параметры и эндпоинты.

Клиенты читают терпимо: игнорируют неизвестные поля и значения. Сервер выпускает ломающее изменение новой версией, помечает старую заголовками Deprecation и Sunset и отключает её в объявленный срок.

  • Схему OpenAPI сравнивают между версиями в CI, договор с клиентами фиксируют контрактными тестами.
  • Expand-contract: сначала добавить новое рядом со старым, перевести клиентов по метрикам, потом убрать старое.
  • Мобильные клиенты живут годами, поэтому для них срок поддержки старой версии длиннее.
Что опасного в этой сортировке? 
@GetMapping("/payments")
List<Payment> list(@RequestParam String sort) {
    return jdbc.query("select * from payment order by " + sort + " limit 50", mapper);
}

Имя колонки подставлено строкой: ?sort=amount;drop table payment-- даёт SQL-инъекцию, и параметры PreparedStatement тут не помогут, потому что имена колонок не параметризуются. Даже без атаки клиент может отсортировать по полю без индекса и вызвать полный перебор, а внутренняя колонка становится частью договора. Нужен белый список: имя параметра → колонка, для каждой — индекс, и id вторым ключом для однозначного порядка.

Как оформлять ошибки в API?

В одном формате для всех эндпоинтов. Стандарт — RFC 9457 Problem Details: type — стабильный машинный идентификатор проблемы, title и detail — для человека, status и instance, плюс свои поля вроде списка ошибок валидации. Код HTTP соответствует проблеме: 400, 409, 422, 404.

Клиент ветвится по type, а не по тексту. Стектрейсы и SQL в ответ не попадают; для расследования достаточно trace id.

  • В Spring — ProblemDetail и ErrorResponse, единообразно через @ControllerAdvice.
  • Ошибки балансировщика и gateway тоже стоит приводить к этому формату, иначе клиент получит HTML.
  • Markus Winand: We need tool support for keyset pagination — основа урока о пагинации: почему OFFSET медленный и как работает keyset.
  • RFC 9457: Problem Details for HTTP APIs — формат ошибок.
  • Martin Fowler: Tolerant Reader — как клиенту переживать изменения API.
  • RFC 8594: Sunset Header и RFC 9745: Deprecation Header — объявление об отключении.
