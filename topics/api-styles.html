API: gRPC, GraphQL, SOAP

У каждого стиля API своя сильная сторона. gRPC — строгий контракт, бинарный Protobuf поверх HTTP/2, стриминг и сроки выполнения, которые передаются по цепочке вызовов; хорош между сервисами. GraphQL — одна точка входа, где клиент сам выбирает поля и связи; хорош для экранов приложений, но требует пакетной загрузки против N+1 и защиты от дорогих запросов. SOAP — XML-конверты по строгому WSDL, которые до сих пор живут в банках и госсистемах. REST остаётся выбором по умолчанию для публичных API.

Разным клиентам платёжной системы нужны разные формы API

У платёжной системы три вида клиентов. Внутренние сервисы — антифрод, сверка, уведомления — вызывают друг друга тысячи раз в секунду, и им нужны быстрые типизированные вызовы с понятными сроками. Мобильное приложение на одном экране показывает платёж, магазин, возвраты и бонусы, и шесть REST-запросов на экран дают заметную задержку на мобильной сети. А старый банк-партнёр принимает только SOAP с подписанными XML-конвертами.

Одного стиля на всех не бывает. Тема разбирает, как устроены gRPC, GraphQL и SOAP, какие у них ловушки и когда что выбирать. REST разобран в REST. Демо в examples/api-styles используют настоящие библиотеки: gRPC 1.84 на Netty и graphql-java 26.1 с DataLoader. Запуск — ./run.sh GrpcDemo и ./run.sh GraphQlDemo на JDK 21 с Maven.

gRPC — вызов метода по контракту, Protobuf внутри кадров HTTP/2

В gRPC контракт пишут в файле .proto: сервис, методы и сообщения с номерами полей. Генератор строит по нему клиентский стаб и серверный интерфейс на любом языке, поэтому клиент на Go и сервер на Java совпадают по типам на этапе компиляции. Вызов уходит запросом HTTP/2 на путь /пакет.Сервис/Метод, а сообщения кодируются Protobuf — компактно и быстро.

service Payments {
  rpc GetPayment (PaymentId) returns (Payment);              // unary: запрос — ответ
  rpc WatchPayment (PaymentId) returns (stream PaymentEvent); // сервер шлёт поток событий
}
message PaymentId { string id = 1; }  // Номер поля — часть контракта навсегда.

Демо обходится без генерации кода, чтобы показать сам транспорт: сообщения — строки, а маршаллер превращает их в байты кадра. С Protobuf меняется только маршаллер.

MethodDescriptor<String, String> GET = MethodDescriptor.<String, String>newBuilder()
        .setType(MethodDescriptor.MethodType.UNARY)
        .setFullMethodName("payments.Payments/GetPayment") // HTTP/2 путь вызова.
        .setRequestMarshaller(TEXT).setResponseMarshaller(TEXT).build();

ClientCalls.blockingUnaryCall(channel, GET, CallOptions.DEFAULT, "p-1");
ClientCalls.blockingUnaryCall(channel, GET, CallOptions.DEFAULT, "x-9"); // Сервер: NOT_FOUND.
ClientCalls.blockingServerStreamingCall(channel, WATCH, CallOptions.DEFAULT, "p-1");
unary: p-1:CAPTURED
unknown: NOT_FOUND — payment x-9 not found
stream: p-1:AUTHORIZED p-1:CAPTURED p-1:SETTLED

Ошибки в gRPC — не коды HTTP, а свои статусы: NOT_FOUND, INVALID_ARGUMENT, UNAVAILABLE, DEADLINE_EXCEEDED. HTTP-ответ при этом обычно 200, а статус приходит в трейлере. Поэтому обычный HTTP-балансировщик и мониторинг не видят ошибок gRPC без специальной поддержки. Стриминг бывает в обе стороны: сервер шлёт поток событий платежа, клиент шлёт поток записей, или оба одновременно. Номера полей Protobuf нельзя менять и переиспользовать — правила эволюции схемы разобраны в Serialization Formats.

Срок вызова доходит до сервера, но остановить работу сервер должен сам

У каждого вызова gRPC может быть deadline — момент, после которого ответ клиенту не нужен. Срок передаётся серверу в заголовке grpc-timeout, и сервер видит, сколько осталось. Демо вызывает медленный метод со сроком 100 мс, а сервер работает 300:

// Клиент: срок 100 мс.
ClientCalls.blockingUnaryCall(channel, GET, CallOptions.DEFAULT.withDeadlineAfter(100, MILLISECONDS), "slow");

// Сервер: видит срок, но работает 300 мс и только потом проверяет отмену.
var deadline = Context.current().getDeadline();
sleep(300);
System.out.println("server: cancelled by client=" + Context.current().isCancelled());
server: deadline left ~90 ms
deadline: DEADLINE_EXCEEDED after ~100 ms
server: cancelled by client=true

gRPC сигнализирует отмену, но не прерывает код обработчика. Сервер должен сам проверять Context.current().isCancelled() между шагами или подписаться на отмену, а главное — передавать оставшийся срок в свои исходящие вызовы. gRPC делает это автоматически для вызовов из того же контекста: если обработчик вызывает антифрод через gRPC, тот получит не больше оставшихся 90 мс. Так срок пользовательского запроса распространяется по всей цепочке сервисов, и никто не работает дольше, чем клиент готов ждать. С HTTP-клиентами это приходится делать вручную.

Ещё одна особенность — долгоживущие соединения HTTP/2. Клиент gRPC держит одно соединение и шлёт по нему все вызовы, поэтому балансировщик уровня L4 не распределяет нагрузку. Об этом — в HTTP/2 & HTTP/3.

GraphQL отдаёт ровно запрошенные поля, но наивные резолверы ходят в базу на каждый объект

GraphQL — одна точка входа и схема типов. Клиент присылает запрос, в котором перечисляет нужные поля и связи, и получает ответ ровно этой формы. Экран истории платежей просит id платежа и название магазина — сумма в ответ не попадёт, потому что её не просили:

String query = "{ payments { id merchant { name } } }"; // amount не запрошен.
response: {payments=[{id=p-1, merchant={name=Coffee}}, {id=p-2, merchant={name=Books}}, {id=p-3, merchant={name=Coffee}}, {id=p-4, merchant={name=Taxi}}, {id=p-5, merchant={name=Books}}]}

На сервере у каждого поля есть резолвер — функция, которая достаёт значение. Резолвер merchant вызывается для каждого платежа отдельно. Если он ходит в базу напрямую, пять платежей дают пять запросов, включая повторные для одного и того же магазина. Это та же проблема N+1, что и в Relations & Fetching, только на уровне API.

// Наивно: один SQL на каждый вызов резолвера.
env -> merchantById(((Payment) env.getSource()).merchantId());

// DataLoader: копит ключи в течение уровня запроса и загружает их одним вызовом.
env -> env.getDataLoader("merchants").load(((Payment) env.getSource()).merchantId());
DataLoaderFactory.newDataLoader(ids -> CompletableFuture.supplyAsync(() -> merchantsByIds(ids)));
naive: 5 merchant queries
  select * from merchant where id = 'm-1'
  select * from merchant where id = 'm-2'
  select * from merchant where id = 'm-1'
  select * from merchant where id = 'm-3'
  select * from merchant where id = 'm-2'
dataloader: 1 merchant queries
  select * from merchant where id in [m-1, m-2, m-3]

DataLoader не загружает магазин сразу. Он копит ключи, пока GraphQL обходит все платежи текущего уровня, убирает дубли и вызывает пакетную функцию один раз. Пять запросов превратились в один с тремя уникальными id. DataLoader живёт на один запрос: его кеш нельзя делить между пользователями, иначе один увидит данные, загруженные для другого. В Spring for GraphQL пакетную загрузку дают @BatchMapping и BatchLoaderRegistry.

Гибкость GraphQL стоит кеширования, защиты от тяжёлых запросов и проверки прав на каждое поле

Раз клиент сам составляет запрос, он может составить и очень дорогой: платежи, у каждого — магазин, у магазина — все платежи, у них — снова магазины, десять уровней. Один такой запрос кладёт базу. Поэтому сервер ограничивает глубину и вычисляет сложность запроса до выполнения, отклоняя слишком дорогие. Для своих приложений часто включают persisted queries: клиент присылает не текст, а id заранее одобренного запроса.

HTTP-кеш почти не помогает: все запросы идут POST на один адрес /graphql, и прокси с CDN не могут их различить. Кешируют на уровне резолверов или с помощью persisted queries через GET. Ошибки тоже устроены иначе: ответ обычно 200 с массивом errors рядом с частично заполненными данными, поэтому мониторинг по кодам HTTP их не видит.

Проверка прав — на уровне полей и объектов, а не адресов. В REST достаточно закрыть /admin/**; в GraphQL поле merchant.bankAccount доступно через любой путь графа, и проверять доступ нужно там, где оно резолвится. Каждый новый путь к объекту — новый способ обойти проверку, сделанную в другом месте.

SOAP живёт в старых интеграциях, а выбор стиля зависит от клиента и границы

SOAP — протокол обмена XML-конвертами с жёсткой схемой в WSDL. Конверт содержит заголовок и тело, а стандарты WS-* добавляют подпись и шифрование отдельных частей сообщения (WS-Security), надёжную доставку и транзакции. Его выбирали за строгий контракт и подпись на уровне сообщения, которая переживает любые прокси. Сегодня SOAP редко выбирают для нового API, но в банках, страховании и госсистемах он работает десятилетиями. В Java с ним работают через JAX-WS или Spring Web Services; клиентский код генерируется по WSDL.

Типичная система использует несколько стилей одновременно: REST наружу для партнёров, gRPC между внутренними сервисами, GraphQL в backend-for-frontend для мобильного приложения и адаптер к SOAP-банку на краю. Важно не смешивать их внутри одной границы и не выбирать модный стиль там, где клиенту нужен обычный кешируемый REST. Браузерам gRPC напрямую недоступен — нужен gRPC-Web и прокси, поэтому для публичного веба он редкость.

GraphQL быстрее REST, потому что клиент получает всё одним запросом.

Один запрос клиента может превратиться на сервере в сотни запросов к базе, если резолверы не пакетируют загрузку. GraphQL экономит круги по сети для клиента, а нагрузку переносит на сервер. Без DataLoader и ограничения сложности он медленнее и опаснее REST.

  • gRPC: контракт .proto, Protobuf поверх HTTP/2, стриминг, свои статусы вместо кодов HTTP; хорош между сервисами.
  • Deadline передаётся серверу и дальше по цепочке, но код обработчика сам должен проверять отмену: в демо сервер работал 300 мс при сроке 100.
  • GraphQL отдаёт запрошенные поля; наивные резолверы дают N+1 (5 запросов), DataLoader пакетирует их в один.
  • GraphQL требует ограничения сложности, своего кеширования и проверки прав на поля.
  • SOAP — для существующих интеграций; стиль выбирают по клиенту и границе, часто несколько сразу.

На собеседовании

Когда выбрать gRPC, а когда REST?

gRPC — для вызовов между внутренними сервисами: строгий контракт в .proto, генерация кода, компактный Protobuf, HTTP/2 с мультиплексированием, стриминг и сроки вызовов. REST — для публичных и партнёрских API: понятен любому клиенту, работает в браузере, кешируется прокси и CDN, ошибки видны по кодам HTTP.

  • Deadline в gRPC передаётся по цепочке, но обработчик сам проверяет отмену, иначе работает впустую.
  • Статус gRPC приходит в трейлере при HTTP 200; балансировщикам и мониторингу нужна поддержка gRPC.
  • Долгоживущее HTTP/2-соединение требует L7- или клиентской балансировки.
Что не так с этим обработчиком gRPC при перегрузке? 
public void getRisk(RiskRequest r, StreamObserver<RiskScore> out) {
    var history = historyRepository.load(r.getAccountId()); // 400 мс на тяжёлый аккаунт
    var score = model.score(history);                        // ещё 200 мс
    out.onNext(score);
    out.onCompleted();
}

Клиент платежа ждёт антифрод 150 мс. Обработчик не смотрит на срок и отмену: после ухода клиента он ещё 450 мс грузит историю и считает модель. Под нагрузкой такие брошенные запросы съедают потоки и соединения базы, нужные живым запросам. Нужно проверять Context.current().isCancelled() между шагами, передавать оставшийся срок в запрос к базе как таймаут и сразу отвечать DEADLINE_EXCEEDED, если времени не осталось.

Что такое проблема N+1 в GraphQL и как её решают?

Резолвер связи вызывается отдельно для каждого родительского объекта. Если он ходит в базу напрямую, список из N платежей даёт N запросов за магазинами. В демо пять платежей дали пять запросов, из них два повторных.

Решение — DataLoader: он копит ключи всего уровня, убирает дубли и загружает их одним пакетным запросом. В демо остался один запрос с тремя id. В Spring for GraphQL это @BatchMapping.

  • DataLoader и его кеш живут на один запрос; общий кеш между пользователями даёт утечку данных.
  • Глубину и сложность запроса ограничивают до выполнения, иначе один запрос кладёт базу.
  • Права проверяют на уровне полей: к объекту можно прийти разными путями графа.

Когда GraphQL оправдан, а когда нет?

Оправдан, когда много разных клиентов собирают экраны из связанных данных и им важна каждая поездка по сети: мобильные приложения, BFF. Клиент сам выбирает поля и связи и получает всё одним запросом. Не оправдан для простых API, публичных интеграций и там, где важен HTTP-кеш: все запросы — POST на один адрес.

  • Ошибки приходят в массиве errors при HTTP 200 вместе с частичными данными.
  • Persisted queries дают и защиту от произвольных запросов, и кеширование через GET.
