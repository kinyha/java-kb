Design: Clean & Hexagonal Architecture

Clean Architecture и гексагональная архитектура говорят одно: бизнес-правила — центр приложения, а база, веб, банк и фреймворк — детали на краях. Зависимости в исходном коде направлены только внутрь, к правилам. Ядро описывает, что ему нужно от мира, интерфейсами-портами, а адаптеры на краях реализуют их для конкретной базы или банка. Тогда правило оплаты проверяется тестом за миллисекунды без Spring и PostgreSQL, а смена банка не трогает ядро. Цена — лишние интерфейсы и перекладывание данных между моделями, и для простого CRUD она не окупается.

Правило оплаты размазано по контроллеру, JPA-сущности и клиенту банка

Правило «платёж выше 10 000 ₽ требует подтверждения» живёт в трёх местах: часть проверки в контроллере, часть в сервисе, а лимит берётся из поля JPA-сущности, которое заполняет Hibernate. Чтобы проверить правило тестом, нужно поднять Spring, базу и заглушку банка: тест идёт десять секунд и падает, когда меняется схема таблицы. Когда банк сменил SDK, правка дошла до сервиса платежей, потому что тот принимал и возвращал классы SDK.

Роберт Мартин в «Чистой архитектуре» называет это смешением политики и деталей. Политика — то, ради чего существует система: правила оплаты, лимиты, статусы. Детали — то, как она общается с миром: HTTP, JSON, PostgreSQL, Hibernate, API банка. Детали меняются часто и по внешним причинам, политика — по решениям бизнеса. Архитектура должна позволять менять одно, не трогая другое.

Демо HexagonalDemo.java собирает одно и то же ядро с разными адаптерами и проверяет правило зависимостей: java HexagonalDemo.java на JDK 21.

Слоистая архитектура направляет все зависимости к базе

Привычная схема Spring-приложения — три слоя: контроллер вызывает сервис, сервис вызывает репозиторий, репозиторий работает с базой. Каждый слой знает о нижнем. Для большинства CRUD-сервисов это хорошая схема: понятная, с минимумом кода.

Проблема в направлении. Сервис, где живут правила, зависит от слоя доступа к данным, а значит, от JPA-сущностей, аннотаций Hibernate и формы таблиц. Модель предметной области становится моделью таблиц: поле добавляют потому, что появилась колонка, а связь делают ленивой потому, что так быстрее грузится. Проектирование начинается со схемы базы, и бизнес-правила подстраиваются под неё.

Вторая проблема — утечки. Сервис возвращает контроллеру JPA-сущность, контроллер отдаёт её Jackson, и ленивая связь падает с LazyInitializationException при сериализации. Сервис принимает DTO запроса с аннотациями валидации и JSON. Границы между слоями есть на диаграмме, но классы ходят сквозь них.

Правило зависимостей: стрелки в коде направлены только внутрь, к политике

Clean Architecture рисует приложение кругами. В центре — сущности предметной области и их правила, которые верны независимо от приложения: деньги не бывают отрицательными, платёж переходит между статусами по таблице. Вокруг — сценарии использования (use cases): правила этого приложения, например «провести оплату: проверить сумму, списать в банке, сохранить». Дальше — адаптеры интерфейсов, которые переводят данные между сценариями и внешним миром. Снаружи — фреймворки и драйверы: Spring MVC, Hibernate, PostgreSQL, SDK банка.

Главное правило одно: зависимости в исходном коде направлены только внутрь. Ничто во внутреннем круге не упоминает имён из внешнего — классов, функций, аннотаций, форматов данных. Как же сценарий вызывает банк, если не знает о нём? Через интерфейс, который объявлен во внутреннем круге, а реализован во внешнем. Это инверсия зависимостей из SOLID: вызов идёт наружу, импорт — внутрь.

Данные через границу передают простыми структурами, удобными внутреннему кругу. Сценарий не принимает HTTP-запрос и не возвращает JPA-сущность: контроллер переводит JSON в команду сценария, а адаптер хранилища переводит Payment в строку таблицы. Мартин отдельно подчёркивает: количество кругов не догма, важно только направление.

Порты и адаптеры: ядро объявляет интерфейсы, края их реализуют

Гексагональная архитектура Алистера Кокберна раньше сформулировала ту же идею другими словами. У ядра есть порты — интерфейсы, через которые оно общается с миром. Входящие (driving) порты описывают, что приложение умеет: PayUseCase. Исходящие (driven) порты описывают, что ему нужно: PaymentStore, Bank. Адаптеры подключают к портам конкретные технологии: REST-контроллер к входящему порту, JPA и SDK банка к исходящим.

// ЯДРО: модель, сценарий и порты. Ни одного импорта Spring, JPA или SDK.
record Money(long cents) {
    Money { if (cents <= 0) throw new IllegalArgumentException("amount must be positive"); }
}
interface PayUseCase { Payment pay(String id, long cents); }      // Входящий порт.
interface PaymentStore { void save(Payment p); }                   // Исходящие порты:
interface Bank { boolean charge(String id, Money amount); }        // владелец — ядро.

final class PayService implements PayUseCase {
    PayService(Bank bank, PaymentStore store) { … }
    public Payment pay(String id, long cents) {
        Money amount = new Money(cents);                           // Правило: сумма > 0.
        Status status = bank.charge(id, amount) ? APPROVED : DECLINED;
        Payment p = new Payment(id, amount, status);
        store.save(p);
        return p;
    }
}

// АДАПТЕРЫ: переводят мир в порты и обратно.
final class PaymentHttpAdapter { /* JSON → pay(id, cents) → JSON, 400 при ошибке */ }
final class LimitBank implements Bank { /* тестовый банк: отказ выше 10 000 ₽ */ }

201 {"id":"p-2","status":"DECLINED"}

stored: [p-1=APPROVED, p-2=DECLINED]

Тест в демо собрал ядро с хранилищем в памяти и банком-заглушкой и проверил три случая за доли миллисекунды: одобрение, отказ банка выше лимита и отказ по правилу суммы. Второй запуск подключил другой банк — и тот же сценарий одобрил платёж на 25 000 ₽, потому что лимит — свойство тестового адаптера, а не ядра. Ядро ни разу не изменилось. Так же в проде меняется Тинькофф на Сбер: новый адаптер, новый бин в конфигурации.

В Spring-проекте структура обычно выглядит так: payments.domain для сущностей, payments.application для сценариев и портов, payments.adapter.in.web, payments.adapter.out.persistence, payments.adapter.out.bank для адаптеров. Пакеты верхнего уровня называются по предметной области, а не по технологиям. Мартин называет это кричащей архитектурой: по структуре папок видно, что это платёжная система, а не «приложение на Spring». Как эти пакеты держат границу и чем раскладка по портам отличается от раскладки по фичам и компонентам, разобрано в Project Structure.

Правило зависимостей нарушают незаметно, поэтому его проверяют автоматически

Интерфейсы и пакеты ничего не гарантируют сами. Достаточно одного импорта: кто-то пишет в ядре отчёт и берёт хранилище напрямую, потому что так быстрее. Демо проверяет правило рефлексией: для каждого класса ядра смотрит типы полей и параметров методов и ищет среди них адаптеры. В демо заранее подложено нарушение:

// Класс ядра, который знает конкретное хранилище.
static final class DailyReport implements Core {
    private final InMemoryStore store; // Ссылка из ядра на адаптер.
    long total() { return store.all().stream().mapToLong(p -> p.amount().cents()).sum(); }
}
== dependency rule check
violations: [DailyReport -> InMemoryStore]

Код компилируется и работает, тесты зелёные. Нарушение видно только проверкой структуры. В реальных проектах её делают ArchUnit — правилами вроде «классы в ..domain.. не зависят от ..adapter.. и org.springframework..», которые запускаются как обычные тесты, — или Spring Modulith для границ между модулями. Эти инструменты разобраны в Components & Modules.

Кто тогда собирает всё вместе? Мартин называет это главным компонентом (Main): самое «грязное» место, которое знает обо всех адаптерах и связывает их с портами. В Spring это классы @Configuration и сам контейнер. Им разрешено зависеть от всего, и именно поэтому туда не кладут бизнес-логику.

Каждая граница стоит маппинга, и для простого CRUD она не окупается

Чистое ядро означает несколько моделей одного платежа: DTO запроса в контроллере, доменный Payment в ядре, JPA-сущность в адаптере хранилища. Между ними — перекладывание полей туда и обратно. Новое поле в API требует правки трёх классов и двух мапперов. Это реальная цена, и её стоит называть на собеседовании.

СтратегияКак устроеноКогда уместно
Одна модельJPA-сущность — она же доменная модель и ответ APICRUD, прототип; правил почти нет
Модель + DTOСущность общая для ядра и базы, на вход и выход — DTOТипичный сервис; API отделён от схемы
Полный маппингСвои модели у API, ядра и хранилищаСложные правила, долгоживущее ядро, несколько каналов

Компромисс, который часто выбирают в Spring-проектах: доменная модель — JPA-сущность с аннотациями, но её поведение написано как доменное (методы authorize, capture вместо сеттеров), а наружу она не выходит — API получает DTO. Аннотации Hibernate в ядре — нарушение чистоты, но они не меняют поведения правил, а маппинг из-за них не нужен. Такое решение должно быть осознанным, а не случайным.

Вторая цена — интерфейсы. Порт оправдан, когда за ним реально бывают разные реализации или тест без него невозможен: банк, внешние API, очереди. Интерфейс PaymentStore с единственной реализацией на Spring Data — спорный случай: Spring Data и так даёт интерфейс репозитория. Мартин сам описывает частичные границы: подготовить место для разделения, не платя за полное, и разделить, когда это понадобится.

Решение принимают по сложности правил, а не по моде. Сервис справочника валют с тремя эндпоинтами — слоистый, и это правильно. Платёжное ядро с лимитами, статусами, несколькими банками и каналами — кандидат на порты и адаптеры. Модели предметной области внутри ядра посвящена тема DDD.

Clean Architecture значит, что в доменном коде не может быть ни одной аннотации Spring или JPA.

Правило — про направление зависимостей и про то, чтобы детали не управляли политикой. Многие команды осознанно оставляют JPA-аннотации на сущностях ради отказа от маппинга. Ошибка не в аннотации, а в том, что форма таблицы или HTTP-запроса начинает диктовать бизнес-правила.

  • Политика — правила бизнеса, детали — база, веб, банк, фреймворк; они меняются по разным причинам.
  • Правило зависимостей: импорт только внутрь, к политике. Вызов наружу идёт через интерфейс, которым владеет ядро.
  • Порты описывают, что ядро умеет и что ему нужно; адаптеры подключают к ним технологии и тестовые заглушки.
  • Нарушения незаметны в работе и ловятся только проверкой структуры: ArchUnit, Spring Modulith.
  • Граница стоит маппинга и интерфейсов; для CRUD слоистой архитектуры достаточно.

На собеседовании

Что такое Clean Architecture и правило зависимостей?

Это способ организовать приложение так, чтобы бизнес-правила не зависели от деталей: базы, веба, фреймворка, внешних API. В центре сущности и сценарии использования, снаружи адаптеры и фреймворки. Главное правило — зависимости в исходном коде направлены только внутрь: внутренний круг не знает имён из внешнего.

Когда сценарий должен вызвать банк, он объявляет интерфейс у себя, а адаптер банка снаружи его реализует. Вызов идёт наружу, импорт — внутрь. Это DIP, применённый к целому приложению.

  • Число кругов не догма; важно только направление зависимостей.
  • Через границу передают простые структуры, удобные внутреннему кругу, а не HTTP-запросы и JPA-сущности.
  • Main — конфигурация Spring — зависит от всего и связывает адаптеры с портами; логики в нём нет.

Что такое порты и адаптеры?

Гексагональная архитектура: у ядра приложения есть порты — интерфейсы общения с миром. Входящие порты описывают, что приложение умеет, их вызывают REST-контроллер, обработчик очереди, тест. Исходящие описывают, что ядру нужно: хранилище, банк, отправка уведомлений, их реализуют адаптеры на JPA, SDK банка, Kafka.

Польза — ядро тестируется без инфраструктуры, а смена технологии меняет только адаптер. В демо один и тот же сценарий работал с тестовым банком и с другим банком без изменений.

  • И входящие, и исходящие адаптеры зависят от портов; различается только направление вызова.
  • Пакеты называют по предметной области — «кричащая архитектура» — а не по слоям.
  • Порт без второй реализации и без нужды в тесте — кандидат на частичную границу.

Чем Clean Architecture отличается от обычной трёхслойной?

В трёхслойной контроллер зависит от сервиса, сервис — от репозитория и базы. Бизнес-логика зависит от слоя данных, и модель часто становится копией таблиц. В Clean Architecture направление развёрнуто: слой данных зависит от интерфейсов, которые объявило ядро, и бизнес-логика ни от чего внешнего не зависит.

Для CRUD-сервиса трёхслойной хватает, и она проще. Чистое ядро окупается, когда правил много, они долго живут и к ним подключается несколько каналов и внешних систем.

  • Типичная утечка слоистой схемы — JPA-сущность в ответе API и LazyInitializationException при сериализации.
  • Цена чистой схемы — маппинг между моделями и лишние интерфейсы.

Нужно ли отделять JPA-сущность от доменной модели?

Зависит от сложности. Отдельная доменная модель защищает правила от формы таблиц и аннотаций, но требует маппинга в обе стороны на каждое поле. Многие команды осознанно используют JPA-сущность как доменную модель: с доменными методами вместо сеттеров и с DTO на входе и выходе API.

Главное — чтобы схема базы не диктовала бизнес-правила, а сущность не выходила наружу в ответы API.

  • Признак, что пора разделять: правила начинают обходить ограничения Hibernate — ленивые связи, прокси, требования к конструктору.
  • Агрегаты из DDD хорошо ложатся на Spring Data JDBC, где маппинг проще и нет контекста персистентности.
Что нарушено в этом сценарии? 
package com.acme.payments.application;

public class PayUseCase {
    private final PaymentJpaRepository repository; // Spring Data JPA
    private final TinkoffClient bank;              // SDK банка

    public PaymentEntity pay(PaymentRequestDto request) { … } // DTO из web-слоя
}

Сценарий зависит от трёх деталей сразу: от Spring Data, от SDK банка и от DTO HTTP-запроса. Его нельзя проверить без JPA и SDK, смена банка правит сценарий, а изменение формата API — тоже. Нужны порты в пакете application (PaymentStore, Bank), команда сценария вместо DTO и доменный результат вместо JPA-сущности; адаптеры переводят одно в другое.
