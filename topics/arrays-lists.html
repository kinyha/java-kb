Arrays & Lists

Последовательность можно хранить в слотах массива или в узлах, соединённых ссылками. В массиве индекс сразу указывает нужный слот, но вставка сдвигает соседей. В цепочке узлов соседей легко пересвязать, когда нужное место уже найдено. Для работы только с концами часто хватает массива, замкнутого в кольцо. Выбор начинается с того, какие операции делает сервис: читает по номеру, проходит всё подряд или добавляет и забирает с концов.

Индекс находит слот, а запас места ещё не является данными

Сервис сверки получает пачку платежей и показывает её постранично. Нужны чтение по индексу и последовательный проход. Во время обработки к пачке иногда добавляются новые платежи. Обычный массив даёт быстрый доступ, но его длина фиксируется при создании. Для следующего элемента сверх длины придётся выделить другое хранилище.

Массив задаёт последовательность слотов одинакового типа. Чтобы добраться до a[i], не нужно проходить предыдущие элементы: смещение слота вычисляется по индексу. Это O(1) доступа в принятой модели памяти. Длина массива определяет доступные индексы: от 0 до length − 1. Число смысловых записей приложение хранит отдельно, если заполняет массив частично.

В int[] слоты содержат значения. В Payment[] — ссылки; объекты платежей живут отдельно. Последовательное расположение ссылок не означает, что все объекты лежат рядом. ArrayList<Payment> добавляет поверх массива число занятых элементов size и правила расширения. Длина внутреннего массива — его ёмкость, или capacity.

Посмотрим на реальную реализацию JDK 21. Полный SequenceDemo.java запускается командой ниже. Флаг открывает внутреннее поле для наблюдения: обычному использованию списка он не нужен. Числа ёмкости — результат JBR 21.0.11+10, а не обещание политики роста всех будущих JDK.

Как демо узнаёт длину внутреннего массива

У ArrayList нет публичного метода capacity. Эта обвязка читает диагностическое поле elementData и печатает классы исключений. Она находится в том же классе, что и фрагменты далее. Для импорта нужны java.lang.reflect.Field и java.util.*.

static final Field DATA;
static {
    try {
        DATA = ArrayList.class.getDeclaredField("elementData");
        DATA.setAccessible(true); // Только наблюдение: нужен --add-opens.
    } catch (ReflectiveOperationException e) { throw new ExceptionInInitializerError(e); }
}
static Object[] slots(ArrayList<?> list) throws IllegalAccessException {
    return (Object[]) DATA.get(list);
}
static void report(String name, Runnable operation) {
    try { operation.run(); }
    catch (RuntimeException e) { System.out.println(name + ": " + e.getClass().getSimpleName()); }
}

new ArrayList<>(100) создал сто свободных слотов, но size остался нулём. Метод get проверяет индекс по числу элементов, поэтому доступ к нулевому элементу падает. Для сравнения, у new int[100] уже есть сто доступных значений, изначально равных нулю.

В OpenJDK 21 пустой ArrayList без параметров сначала использует общий пустой массив. При первом добавлении выделяет десять слотов. Это объясняет пару capacity=0 и capacity=10. Запас ёмкости помогает при известном размере пачки: можно сразу создать список с нужным резервом или вызвать ensureCapacity, чтобы избежать нескольких расширений. Создавать фиктивные элементы ради резерва не нужно.

Рост копирует ссылки, а вставка в середину сдвигает хвост

В списке четыре платежа, внутренний массив заполнен. Пятый не помещается. ArrayList выделяет более длинный массив, копирует туда старые ссылки и меняет ссылку на хранилище. Затем записывает новый элемент. Сами платежи продолжают жить на прежних местах.

var list = new ArrayList<String>(4);
list.addAll(List.of("A", "B", "C", "D"));
Object[] old = slots(list);
System.out.println("before: " + list + " capacity=" + old.length);
list.add("E"); // Места нет: новое хранилище и копирование ссылок.
System.out.println("after: " + list + " capacity=" + slots(list).length);
System.out.println("backing changed=" + (old != slots(list)) + " same first object=" + (old[0] == slots(list)[0]));
System.out.println("removed=" + list.remove(1)); // Сдвиг C, D, E влево.
System.out.println("slots after remove=" + Arrays.toString(slots(list)));
list.clear(); // Удаляет ссылки, но сохраняет ёмкость.
System.out.println("clear: size=" + list.size() + " capacity=" + slots(list).length);
list.trimToSize();
System.out.println("trim: size=" + list.size() + " capacity=" + slots(list).length);

В этой версии предпочтительный прирост непустого массива — половина старой длины: 4 + (4 >> 1) = 6. Если операция требует сразу большего запаса, новая длина должна покрыть весь запрос; это особенно важно для addAll и ensureCapacity. Политика роста является деталью реализации, а амортизированная стоимость добавления в конец входит в описание ArrayList.

Почему дорогой рост совместим с O(1) на добавление

Одна операция, вызвавшая рост, стоит O(n): приходится скопировать все занятые слоты. Но после роста несколько следующих добавлений обходятся одной записью. При геометрическом расширении размеры копируемых массивов образуют геометрическую сумму. Для коэффициента около 1,5 старые размеры в обратном порядке похожи на C/1,5 + C/1,5² + …; сумма ограничена постоянным множителем последнего размера.

Поэтому последовательность из n добавлений в изначально пустой список стоит O(n), и на одну операцию приходится амортизированное O(1). Это оценка всей последовательности, без предположений о случайности данных. Она не обещает, что каждое добавление одинаково быстро. У одного запроса может оказаться копирование крупного массива и выделение памяти.

Сдвиг нужен даже тогда, когда свободного места достаточно

При вставке в индекс i нужно освободить слот: n − i ссылок переезжают на одну позицию вправо. При удалении в i оставшийся хвост сдвигается влево. В демо удаление B переносит C, D, E, а прежний последний занятый слот получает null. Без сброса ссылки список продолжал бы удерживать уже удалённый объект за своей логической границей.

Обычное удаление сохраняет ёмкость. clear() убирает ссылки на все элементы, но массив остаётся пригодным для следующей пачки. trimToSize() уменьшает хранилище до текущего size. Вызывать trim после каждого удаления дорого: следующий рост снова потребует копирования. Для редко повторяемой большой пачки освобождение запаса может быть полезно, для постоянно переиспользуемого буфера запас экономит работу.

Диагностическая переменная old в демо всё ещё удерживает прежний массив и его ссылки. Сброс элемента из нового хранилища удаляет только одну из ссылок на объект. Сборка мусора возможна, когда исчезли все сильные пути до него. В обычной работе приложение не должно сохранять внутренние массивы ArrayList.

Узел легко пересвязать, когда он уже найден

Теперь сервис вставляет корректировку рядом с найденным платежом. Связный список хранит каждый элемент в отдельном узле. В односвязной цепочке есть ссылка на следующего, в двусвязной — на следующего и предыдущего. Java LinkedList хранит двусвязные узлы и ссылки на оба конца.

Чтобы вставить узел между двумя известными соседями, достаточно нескольких присваиваний ссылок. Удаление известного узла тоже пересвязывает соседей. Длина цепочки на эту работу не влияет. Но перед операцией нужно получить место изменения: если дан только индекс или значение платежа, сначала придётся пройти список.

LinkedList ищет индекс от ближайшего конца. Доступ к i требует порядка 1 + min(i, n − 1 − i) работы. Доступ к середине остаётся O(n). У односвязного списка с указателем на хвост добавление в конец занимает O(1), но удаление хвоста всё равно требует найти его предшественника: обратной ссылки там нет.

Обычный индексный цикл может превратить один проход в квадратичный

Для ArrayList цикл for (i = 0; i < size; i++) get(i) линейный. Для LinkedList каждый get заново начинает поиск от конца цепочки. Можно измерить именно эту лишнюю работу без ненадёжного сравнения наносекунд.

Ниже полный LinkedTraversalDemo.java: учебная двусвязная цепочка повторяет выбор ближайшего конца из LinkedList JDK 21. Счётчик считает чтения next/prev; у стандартного LinkedList публичного счётчика нет. Запуск: java examples/arrays-lists/LinkedTraversalDemo.java.

public class LinkedTraversalDemo {
    // Учебная двусвязная цепочка. JDK не публикует счётчик переходов.
    static class Node {
        final int value;
        Node prev, next;
        Node(int value) { this.value = value; }
    }
    final int size;
    Node first, last;
    long links;
    LinkedTraversalDemo(int n) {
        size = n;
        for (int i = 0; i < n; i++) {
            Node node = new Node(i);
            node.prev = last;
            if (last == null) first = node; else last.next = node;
            last = node;
        }
    }
    int get(int index) {
        if (index < 0 || index >= size) throw new IndexOutOfBoundsException(index);
        Node node;
        if (index < size / 2) { // Как node(index) в LinkedList JDK 21.
            node = first;
            for (int j = 0; j < index; j++) { node = node.next; links++; }
        } else {
            node = last;
            for (int j = size - 1; j > index; j--) { node = node.prev; links++; }
        }
        return node.value;
    }
    public static void main(String[] args) {
        var chain = new LinkedTraversalDemo(1000);
        long sum = 0;
        for (int i = 0; i < chain.size; i++) sum += chain.get(i);
        System.out.println("indexed: sum=" + sum + " links=" + chain.links);
        chain.links = 0; sum = 0;
        for (Node p = chain.first; p != null; p = p.next) {
            sum += p.value;
            chain.links++; // Чтение next; последнее ведёт к null.
        }
        System.out.println("one pass: sum=" + sum + " links=" + chain.links);
    }
}

one pass: sum=499500 links=1000

У тысячи узлов расстояния до ближайшего конца — 0, 1, …, 499, 499, …, 1, 0. Их сумма — 2 × 499 × 500 / 2 = 249 500. Последовательный проход читает next тысячу раз, включая последнее чтение, которое возвращает null. Сумма значений одинаковая: изменился путь к ним, а не результат расчёта.

Курсор сохраняет найденное место между операциями

var linked = new LinkedList<>(List.of("A", "B", "C"));
var cursor = linked.listIterator();
cursor.next(); // Прошли A; курсор между A и B.
cursor.add("X"); // Пересвязываем соседей; курсор теперь перед B.
System.out.println("next=" + cursor.next());
cursor.remove(); // Удаляем именно элемент, возвращённый next: B.
System.out.println("list=" + linked + " next=" + cursor.next());
next=B
list=[A, X, C] next=C

ListIterator сначала находится между элементами. После next() прошёл A и стоит перед B. Добавление X вставляет его перед следующим элементом; следующий next() по-прежнему возвращает B. remove() удаляет последний элемент, возвращённый next или previous. Так можно за один проход вставлять и удалять в LinkedList около текущей позиции.

Создание listIterator(i) в середине само требует поиска. Если каждый раз создавать новый курсор, выгода исчезнет. У ArrayList тот же интерфейс курсора не отменяет сдвиг хвоста. Удобная абстракция скрывает устройство, но не делает одинаковыми стоимости разных реализаций.

Память и локальность — ещё одна цена узлов

LinkedList выделяет узел для каждой записи. У него есть служебная часть объекта и поля item, next, prev. ArrayList хранит плотный массив ссылок и запас пустых слотов. Точные байты зависят от JVM, выравнивания и сжатия ссылок; сравнивать их без условий запуска нельзя.

При проходе по массиву соседние ссылки читаются последовательно. В цепочке адрес следующего узла узнаётся только после чтения текущего. Это зависимые обращения к памяти и больше отдельных объектов для GC. Поэтому «оба обхода O(n)» ещё не означает одинаковую скорость. Объекты самих платежей при этом могут быть разбросаны и у массива.

Стек и очередь задают порядок, а дек даёт оба конца

Для последовательной обработки платежей важнее порядок выдачи, чем номер элемента. FIFO-очередь отдаёт самый ранний добавленный платёж. Стек работает по LIFO: последний добавленный забирается первым. Дек позволяет добавлять, читать и удалять с обоих концов. Из него можно получить оба режима, выбрав нужные операции.

В Java для локального стека или очереди обычно подходит Deque<E> с реализацией ArrayDeque. Для FIFO добавляй через addLast/offerLast, забирай через removeFirst/pollFirst. Для стека push означает addFirst, а pop — removeFirst: оба работают на одном конце. Класс Stack унаследовал API Vector и синхронизацию отдельных методов; для такого режима Deque яснее.

Deque<String> fifo = new ArrayDeque<>();
fifo.addLast("A"); fifo.addLast("B"); fifo.addLast("C");

Пара removeFirst/pollFirst различается поведением на пустой очереди: первая операция бросает исключение, вторая возвращает null. Аналогично работают getFirst/peekFirst. Выбирай исключение, если пустота нарушает логику сценария; выбирай специальный результат, если она ожидаема.

У обычного ArrayDeque нет фиксированного пользовательского лимита: он расширяется. Поэтому offer не является проверкой, выдержит ли сервис ещё один платёж. ArrayDeque запрещает null. LinkedList null принимает, и тогда возврат null из poll уже неоднозначен: очередь могла быть пустой или содержать пустой элемент. Для очереди работ лучше сохранять ясный смысл результата.

Название интерфейса Queue само по себе не обещает FIFO: например, PriorityQueue выбирает по приоритету. Её устройство и порядок обхода — в Heaps. Здесь рассматриваем последовательность и работу на её концах; приоритетное извлечение требует другого инварианта.

Кольцо повторно использует слоты без сдвига остальных

Если хранить FIFO-очередь в ArrayList и удалять индекс 0, каждый платёж сдвигает весь остаток. Можно сохранить данные на местах, а вместо этого двигать индекс головы. После физического конца массива индекс возвращается в начало: освобождённые слоты снова доступны для записи. Такой массив работает как кольцевой буфер.

В учебной ограниченной очереди head указывает следующий элемент для чтения, tail — следующий слот для записи. Ещё храним число элементов size. Тогда совпадение head и tail возможно и у полного, и у пустого буфера; size различает эти состояния. Размер массива всегда равен четырём, порядок чтения определяется головой, а не физическим индексом 0.

Это модель с явным лимитом, не копия ArrayDeque JDK. Она возвращает false, когда все четыре слота заняты. В OpenJDK 21 ArrayDeque использует другой способ различать состояния: в обычном завершённом состоянии остаётся свободный слот, равенство head и tail означает пустоту. Когда запись догоняет голову, хранилище расширяется. Сам индексный переход в этой версии проверяет границу массива; длина не обязана быть степенью двойки.

Полный RingQueueDemo.java ниже. Запуск: java examples/arrays-lists/RingQueueDemo.java. Печать показывает физические слоты, затем реальные чтения по порядку очереди.

import java.util.Arrays;
import java.util.Objects;

public class RingQueueDemo {
    static class Ring {
        final String[] a;
        int head, tail, size;
        Ring(int capacity) {
            if (capacity <= 0) throw new IllegalArgumentException("capacity");
            a = new String[capacity];
        }
        boolean offer(String payment) {
            Objects.requireNonNull(payment);
            if (size == a.length) return false; // Фиксированный лимит очереди.
            a[tail] = payment;
            tail = (tail + 1) % a.length;
            size++;
            return true;
        }
        String poll() {
            if (size == 0) return null;
            String payment = a[head];
            a[head] = null; // Освобождаем ссылку на обработанный платёж.
            head = (head + 1) % a.length;
            size--;
            return payment;
        }
        void show() {
            System.out.println(Arrays.toString(a) + " head=" + head + " tail=" + tail + " size=" + size);
        }
    }
    public static void main(String[] args) {
        Ring q = new Ring(4);
        q.offer("A"); q.offer("B"); q.offer("C"); q.show();
        System.out.println("polled=" + q.poll() + "," + q.poll()); q.show();
        q.offer("D"); q.offer("E"); q.show();
        q.offer("F"); q.show();
        System.out.println("offer G=" + q.offer("G"));
        System.out.println("drain=" + q.poll() + "," + q.poll() + "," + q.poll() + "," + q.poll());
        q.show(); System.out.println("empty=" + q.poll());
    }
}

[null, null, null, null] head=2 tail=2 size=0

После перехода через конец массива E лежит в слоте 0, но первым всё ещё выдаётся C из слота 2. Получаем C, D, E, F, а не порядок физического массива E, F, C, D. Сброс прочитанного слота в null освобождает ссылку. У ограниченного кольца обе операции делают постоянное число действий: O(1) без расширения.

Растущий ArrayDeque иногда выделяет и перекладывает хранилище, поэтому операции на концах имеют амортизированную оценку O(1). Удаление по значению всё ещё требует поиска и может сдвигать часть данных. Возможность работать с обоими концами не даёт доступ по произвольному индексу: такого API у ArrayDeque нет.

Выбирай структуру по операции, размеру очереди и владельцу данных

Для готовой пачки с чтением по номеру ArrayList даёт прямой доступ и удобный проход. Для изменений у уже найденного места LinkedList может сохранить курсор и пересвязать узлы. Для стека и FIFO-очереди ArrayDeque обходится без узла на каждый элемент. В каждом случае полезно назвать точную операцию: «много вставок» не объясняет, где искать место и сколько раз это делать.

Java 21 добавила методы концов и в List: например, addFirst есть у ArrayList. Это удобство интерфейса, а не новое устройство хранилища. Вставка в начало ArrayList по-прежнему сдвигает хвост. Извлечение всех n элементов через remove(0) делает примерно n(n − 1)/2 переносов. Замена на deque устраняет именно эту лишнюю работу.

Представление и копия имеют разный срок жизни

var source = new ArrayList<>(List.of("A", "B", "C", "D"));
var page = source.subList(1, 3);
page.clear(); // Это представление: убираем B и C из исходного списка.
System.out.println("source after page.clear=" + source);
source.add("E"); // Структурное изменение вне представления.
report("page.size", page::size);
var iterator = source.iterator();
source.add("F");
report("iterator.next", iterator::next);
source after page.clear=[A, D]
page.size: ConcurrentModificationException
iterator.next: ConcurrentModificationException

subList — представление диапазона исходного списка. Его clear меняет источник. Структурное изменение источника в обход представления лишает его прежнего соответствия данным; в этом запуске ArrayList обнаружил изменение и бросил ConcurrentModificationException. Если отдельной странице нужна независимая последовательность, создай new ArrayList<>(source.subList(from, to)).

Долгоживущее маленькое представление также может удерживать большой исходный список и его массив. Размер представления не равен объёму удерживаемой памяти. Итераторы ArrayList и LinkedList стараются обнаруживать изменение в обход себя. Это диагностика ошибок, а не синхронизация: ни одна из трёх рассмотренных коллекций не обеспечивает согласованный доступ нескольких потоков сама.

Очередь в памяти не заменяет ограничение нагрузки

Если сервис принимает тысячу платежей в секунду, а обрабатывает девятьсот, хвост растёт на сто в секунду. Другой контейнер не изменит это соотношение. Ограниченная очередь заставляет выбрать действие при заполнении: замедлить источник, отказать в приёме или сохранить работу в устойчивом хранилище. Растущий массив просто откладывает этот выбор до давления на память.

Для передачи работ между потоками нужны структуры и протокол, обеспечивающие публикацию и координацию, например подходящая BlockingQueue. Их устройство — в Concurrent Collections. Для восстановления после падения процесса нужна запись вне локальной памяти. Выбирай устройство последовательности отдельно от гарантий доставки и обработки.

  • Индекс массива даёт прямой доступ. Size обозначает данные, capacity — запас слотов; резерв не создаёт элементов списка.
  • Геометрическое расширение даёт O(1) амортизированно на добавление в конец. Конкретный рост и вставка в середину могут стоить O(n).
  • Связный список пересвязывает известные узлы за O(1). Поиск индекса остаётся проходом; повторять его в цикле дорого.
  • Стек и FIFO задают порядок выдачи. Дек позволяет работать с обоих концов; кольцо убирает сдвиг при удалении головы.
  • Представление сохраняет связь с источником. Ограничение нагрузки и координацию потоков нужно задавать отдельно от выбора контейнера.

На собеседовании

Чем отличаются массив, ArrayList и LinkedList? Что выберешь для платежей?

Массив даёт доступ к слоту по индексу, но его длина фиксирована. ArrayList хранит элементы в расширяемом массиве: индекс быстрый, а вставка в середину требует сдвига хвоста. LinkedList хранит отдельные двусвязные узлы. Когда место уже найдено, соседей можно пересвязать за постоянное число действий, но сам поиск индекса линейный.

Для пачки платежей с чтением по номеру я начну с ArrayList. Для стека или очереди возьму ArrayDeque. LinkedList рассмотрю, если есть последовательный проход с большим числом изменений около текущего курсора. Сначала проверю реальные операции, а не только число вставок.

  • ArrayList хранит плотный набор ссылок с запасом ёмкости, LinkedList выделяет узел на каждый элемент. При равной оценке O(n) последовательный проход и работа GC могут сильно различаться; объекты платежей отдельно от слотов в обоих случаях.
  • Массив примитивов содержит сами числа. Список Integer содержит ссылки на обёртки, поэтому при больших числовых наборах цена памяти и обращения к данным отличается.
  • Вставка LinkedList по известному индексу всё ещё включает поиск. Пользовательский код обычно не получает прямой доступ к приватному Node; пригодный для повторных изменений доступ даёт курсор.
Вызываем remove с int и Integer. Какие платежи удалятся из List<Integer>? 
List<Integer> ids = new ArrayList<>(List.of(10, 20, 30));
System.out.println("remove index=" + ids.remove(1) + " list=" + ids);
System.out.println("remove value=" + ids.remove(Integer.valueOf(10)) + " list=" + ids);
remove index=20 list=[10, 30]
remove value=true list=[30]

Первый вызов выбрал remove(int): удалён элемент с индексом 1, то есть 20. Второй выбрал remove(Object): удалено значение 10. Возвращаемые типы тоже различаются — сам удалённый элемент и boolean. Для числовых идентификаторов это частая ошибка, которую устройство списка не исправляет.

Почему add у ArrayList называют O(1), если он копирует массив?

Речь о добавлении в конец и амортизированной оценке. Некоторые добавления заполняют свободный слот, а некоторые вызывают расширение и копирование. При геометрическом росте общая стоимость n добавлений линейна, поэтому на одну приходится O(1). Одно конкретное добавление всё ещё может стоить O(n).

Это не среднее по случайным входам. Оценка получается из суммы объёмов копирования за последовательность операций. Если размер пачки заранее известен, резерв ёмкости уберёт часть расширений, но size от этого не изменится.

  • Амортизация не ограничивает задержку отдельного запроса. Крупный рост требует выделения нового массива и копирования ссылок; исходное и новое хранилища некоторое время сосуществуют.
  • Если после каждого добавления принудительно сжимать хранилище до size, свободный запас исчезает. Следующее добавление снова копирует массив; такая последовательность может стать квадратичной.
  • Коэффициент роста JDK — деталь реализации. Для объяснения оценки достаточно постоянного геометрического коэффициента больше единицы; меньший коэффициент экономит запас и увеличивает частоту копирования.

Правда ли, что вставка и удаление в LinkedList всегда O(1)?

За O(1) можно пересвязать узлы у уже найденного места. Если вызван add(i, value), сначала нужно найти индекс i. LinkedList идёт от ближайшего конца, но для середины это всё равно O(n). Remove(value) тоже сначала ищет нужное значение.

Выгода появляется при изменениях около текущего ListIterator во время одного прохода. Курсор сохраняет позицию между вызовами. Если снова и снова получать get(i) или создавать курсор в середине, поиск съедает преимущество.

  • У односвязного списка удаление известного узла обычно требует его предшественника. У двусвязного он доступен через prev; дополнительные ссылки покупают более удобные операции ценой памяти.
  • Вызов ListIterator.remove относится к последнему элементу, возвращённому next или previous. После add или remove нельзя снова удалить тот же элемент без нового перехода: курсор имеет правила состояния.
  • Разные реализации List дают одинаковый результат операций, но разную стоимость. В общем коде предпочтительнее один проход итератором, если произвольный индекс не нужен.

Как связаны стек, очередь и дек? Зачем ArrayDeque нужен кольцевой массив?

Стек отдаёт последний добавленный элемент, FIFO-очередь — первый. Дек работает с обоих концов, поэтому позволяет реализовать оба режима. Для локального стека я использую push и pop на одном конце ArrayDeque, для FIFO — добавление в конец и удаление с начала.

Кольцевой массив двигает индексы головы и хвоста вместо сдвига всех элементов после удаления головы. Освободившиеся слоты используются повторно. Если растущему ArrayDeque не хватает места, он расширяет хранилище; операции на концах имеют амортизированную постоянную стоимость.

  • Poll возвращает null на пустоте, remove бросает исключение. Запрет null в ArrayDeque сохраняет однозначность результата; при LinkedList с null этого уже недостаточно.
  • В кольце нужно различать пустоту и заполнение. Наше учебное кольцо хранит size, а ArrayDeque JDK 21 сохраняет свободный слот и расширяется при достижении головы хвостом. Нельзя переносить условие head == tail между моделями без этой детали.
  • ArrayDeque не является ограниченной или потокобезопасной очередью. Для устойчивой обработки платежей отдельно нужны ограничение хвоста, координация участников и решение о сохранении работ при падении процесса.
