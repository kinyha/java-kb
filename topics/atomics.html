Concurrency: Atomics & CAS

Счётчик без блокировок — и 58 миллионов напрасных попыток

Атомарный счётчик обходится без блокировок: поток читает значение и записывает новое, только если за это время никто другой его не изменил. Иначе повторяет. Посчитаем, сколько таких повторов случается под нагрузкой. Каждый поток увеличивает счётчик миллион раз:

import java.util.concurrent.atomic.*;

public class CasRetries {
    static final AtomicLong counter = new AtomicLong();
    static final LongAdder failures = new LongAdder();

    // то, что делает incrementAndGet, только с подсчётом неудач
    static long increment() {
        while (true) {
            long current = counter.get();                        // прочитали
            if (counter.compareAndSet(current, current + 1))     // записали, только если никто не успел раньше
                return current + 1;
            failures.increment();                                // успели — повторяем с новым значением
        }
    }

    public static void main(String[] args) throws Exception {
        for (int threads : new int[]{1, 2, 4, 8, 16}) {
            counter.set(0); failures.reset();
            Thread[] ts = new Thread[threads];
            long start = System.nanoTime();
            for (int t = 0; t < threads; t++) {
                ts[t] = new Thread(() -> { for (int i = 0; i < 1_000_000; i++) increment(); });
                ts[t].start();
            }
            for (Thread t : ts) t.join();
            System.out.printf("%2d потоков: итог %,11d, неудачных CAS %,11d (%.1f на успешный), %4d мс%n",
                threads, counter.get(), failures.sum(), (double) failures.sum() / counter.get(), (System.nanoTime() - start) / 1_000_000);
        }
    }
}
 1 потоков: итог   1,000,000, неудачных CAS           0 (0.0 на успешный),    6 мс
 2 потоков: итог   2,000,000, неудачных CAS     634,466 (0.3 на успешный),   44 мс
 4 потоков: итог   4,000,000, неудачных CAS   7,520,654 (1.9 на успешный),  273 мс

16 потоков: итог  16,000,000, неудачных CAS  58,266,121 (3.6 на успешный), 1495 мс

Итог всегда точный — ни одно увеличение не потеряно, в отличие от count++ из темы Thread Safety. Но на 16 потоках на каждую успешную запись пришлось 3,6 неудачных, а работа в 16 раз больше заняла в 250 раз больше времени. Lock-free не значит бесплатно. В этой теме — как устроена операция compare-and-set, какие атомарные классы есть в JDK и почему incrementAndGet быстрее этого цикла. А ещё — как LongAdder убирает конкуренцию, что такое проблема ABA и когда вообще стоит писать код без блокировок.

CAS записывает новое значение, только если старое не изменилось

Compare-and-set (CAS) — одна инструкция процессора: «если в ячейке по-прежнему expected, записать new и вернуть успех, иначе ничего не делать». Атомарность обеспечивает железо: LOCK CMPXCHG на x86, CAS или пара LDAXR/STLXR на ARM. В Java это compareAndSet(expected, new) у атомарных классов. Вокруг неё строится цикл: прочитать, вычислить, попытаться записать, при неудаче повторить.

Кроме атомарности, CAS даёт те же гарантии видимости, что чтение и запись volatile: значение, записанное успешным CAS, видят все следующие чтения.

Этот цикл спрятан в updateAndGet и accumulateAndGet: они принимают функцию и повторяют CAS, пока не получится. Отсюда важное следствие — функция может выполниться несколько раз:

import java.util.concurrent.atomic.*;

public class SideEffect {
    public static void main(String[] args) throws Exception {
        AtomicLong balance = new AtomicLong();
        LongAdder calls = new LongAdder();
        Thread[] ts = new Thread[8];
        for (int t = 0; t < ts.length; t++) {
            ts[t] = new Thread(() -> {
                for (int i = 0; i < 100_000; i++) {
                    balance.updateAndGet(x -> {
                        calls.increment();                           // «побочный эффект»: например, запись в аудит
                        return x + 1;
                    });
                }
            });
            ts[t].start();
        }
        for (Thread t : ts) t.join();
        System.out.printf("обновлений: %,d, вызовов функции: %,d%n", balance.get(), calls.sum());
    }
}
обновлений: 800,000, вызовов функции: 4,332,798

Функция выполнилась в 5,4 раза чаще, чем обновилось значение. Если бы она писала в аудит или отправляла событие, получились бы лишние записи. Javadoc требует, чтобы функция не имела побочных эффектов. То же касается ConcurrentHashMap.compute и merge.

incrementAndGet — не цикл CAS, а одна инструкция процессора

Атомарные классы JDK:

Цикл из шага 1 на 8 потоках занял 881 мс. Но в теме Thread Safety AtomicInteger.incrementAndGet на тех же 8 потоках справился за 69 мс. Дело в том, что простое сложение JIT превращает в одну атомарную инструкцию сложения — LOCK XADD на x86, LDADD на ARM — без цикла повторов. Сравним три способа на 1–16 потоках, по миллиону увеличений на поток:

import java.util.concurrent.atomic.*;

public class Scaling {
    static long run(int threads, Runnable op) throws InterruptedException {
        Thread[] ts = new Thread[threads];
        long start = System.nanoTime();
        for (int t = 0; t < threads; t++) {
            ts[t] = new Thread(() -> { for (int i = 0; i < 1_000_000; i++) op.run(); });
            ts[t].start();
        }
        for (Thread t : ts) t.join();
        return (System.nanoTime() - start) / 1_000_000;
    }

    public static void main(String[] args) throws Exception {
        AtomicLong a = new AtomicLong(), b = new AtomicLong();
        LongAdder adder = new LongAdder();
        for (int round = 0; round < 2; round++) {                // первый круг — прогрев
            System.out.println(round == 0 ? "прогрев" : "потоков  incrementAndGet  updateAndGet(x -> x + 1)  LongAdder");
            for (int threads : new int[]{1, 2, 4, 8, 16}) {
                long t1 = run(threads, a::incrementAndGet);
                long t2 = run(threads, () -> b.updateAndGet(x -> x + 1));
                long t3 = run(threads, adder::increment);
                if (round == 1) System.out.printf("%6d  %12d мс  %20d мс  %8d мс%n", threads, t1, t2, t3);
            }
        }
    }
}

updateAndGet с той же арифметикой — это цикл CAS, и на 16 потоках он в 6,5 раза медленнее incrementAndGet. Но и одна атомарная инструкция не масштабируется: все ядра по очереди получают в эксклюзивное владение одну строку кеша, и время растёт с числом потоков. Не растёт только у LongAdder: 5 мс на 16 миллионов увеличений.

LongAdder убирает конкуренцию, раскладывая счёт по ячейкам

Идея LongAdder — не бороться за одну ячейку. Пока конкуренции нет, он увеличивает поле base через CAS. Как только CAS не прошёл, адер заводит массив ячеек cells, и каждый поток дальше увеличивает свою ячейку, выбранную по хешу потока. Ячейки разнесены по разным строкам кеша (@Contended), поэтому ядра друг другу не мешают. Число ячеек растёт до числа ядер. sum() складывает base и все ячейки.

Цена — в чтении:

  • sum() обходит все ячейки, это дороже чтения AtomicLong;
  • sum() — не атомарный снимок. Если в это время идут увеличения, результат может не совпасть ни с одним моментом времени;
  • нет compareAndSet и incrementAndGet с возвратом нового значения;
  • памяти больше: по ячейке с выравниванием на каждое ядро.

Отсюда правило. LongAdder — для статистики, которую часто пишут и редко читают: метрики, счётчики запросов, суммы. AtomicLong — когда по значению принимают решение прямо сейчас: генератор id, лимит «не больше N», порядковый номер. LongAccumulator обобщает идею на любую ассоциативную операцию, например максимум: new LongAccumulator(Math::max, Long.MIN_VALUE).

Тот же принцип лежит в основе ConcurrentHashMap: счётчик размера там устроен как LongAdder. Поэтому size() при параллельных изменениях приблизителен.

ABA: значение вернулось прежним, и CAS не заметил, что всё изменилось

CAS сравнивает значения, а не историю. Если за время между чтением и CAS значение успело смениться с A на B и обратно на A, CAS пройдёт, хотя состояние вокруг уже другое. Это проблема ABA. Классический пример — стек без блокировок, у которого узлы переиспользуются из пула. Настоящее чередование двух потоков поймать сложно, поэтому воспроизведём его по шагам:

import java.util.concurrent.atomic.*;

public class Aba {
    static final class Node {
        final String value;
        Node next;
        Node(String value) { this.value = value; }
    }

    static String dump(Node n) {
        StringBuilder sb = new StringBuilder();
        for (; n != null; n = n.next) sb.append(n.value).append(n.next != null ? " → " : "");
        return sb.length() == 0 ? "пусто" : sb.toString();
    }

    public static void main(String[] args) {
        // стек задач A → B → C; узлы берутся из пула и переиспользуются
        Node a = new Node("A"), b = new Node("B"), c = new Node("C");
        a.next = b; b.next = c;

        AtomicReference<Node> top = new AtomicReference<>(a);
        // поток 1 начал pop(): прочитал вершину и следующий узел — и его вытеснили
        Node seen = top.get(), seenNext = seen.next;                 // A и B

        // поток 2 за это время: pop A, pop B, push A обратно (узел из пула)
        top.set(b); top.set(c);                                      // сняли A и B
        a.next = top.get(); top.set(a);                              // вернули A поверх C
        System.out.println("стек после потока 2: " + dump(top.get()));

        // поток 1 продолжает: вершина снова A — CAS проходит
        boolean ok = top.compareAndSet(seen, seenNext);
        System.out.println("CAS(A → B) потока 1: " + ok + ", стек: " + dump(top.get()) + "   ← B уже забран потоком 2, A потерян");

        // то же со штампом: каждое изменение увеличивает версию
        a.next = b; b.next = c;
        AtomicStampedReference<Node> stamped = new AtomicStampedReference<>(a, 0);
        int[] stampHolder = new int[1];
        Node seen2 = stamped.get(stampHolder);
        int seenStamp = stampHolder[0];                              // поток 1 запомнил A и версию 0
        Node seenNext2 = seen2.next;
        stamped.set(b, 1); stamped.set(c, 2);                        // поток 2: pop, pop
        a.next = c; stamped.set(a, 3);                               // поток 2: push A
        boolean ok2 = stamped.compareAndSet(seen2, seenNext2, seenStamp, seenStamp + 1);
        System.out.println("со штампом: CAS " + ok2 + ", стек: " + dump(stamped.getReference()));
    }
}
стек после потока 2: A → C
CAS(A → B) потока 1: true, стек: B → C   ← B уже забран потоком 2, A потерян
со штампом: CAS false, стек: A → C

Поток 1 запомнил «вершина A, под ней B» и хочет сдвинуть вершину на B. Пока он ждал, поток 2 снял A и B и вернул A обратно, уже поверх C. Вершина снова A, CAS проходит — и ставит на вершину узел B, который уже забрал поток 2. Задача B будет обработана дважды, а A пропала. AtomicStampedReference хранит вместе со ссылкой версию, и CAS сравнивает обе. Версия сменилась трижды — операция отказала.

В Java ABA встречается реже, чем в C: если узлы всегда создаются заново через new, сборщик мусора не отдаст адрес старого узла, пока на него ссылается поток 1. Опасны переиспользование объектов из пула и CAS по числам и состояниям, которые могут вернуться к прежнему значению. Например, «баланс 100 → 50 → 100» для CAS неотличим от «ничего не произошло».

Lock-free гарантирует, что система движется, даже если поток остановился

Алгоритмы делят по гарантиям продвижения:

КлассГарантияПример
блокирующийесли поток, держащий замок, остановлен, остальные ждутsynchronized, ReentrantLock
lock-freeза конечное число шагов хотя бы один поток завершит операциюцикл CAS: кто-то всегда побеждает
wait-freeкаждый поток завершит операцию за конечное число своих шаговincrementAndGet на процессоре с инструкцией атомарного сложения

Классическая lock-free структура — стек Трайбера. Вершина хранится в AtomicReference, а push и pop — это цикл CAS по вершине. Узлы неизменяемы и не переиспользуются, поэтому ABA здесь не возникает:

import java.util.concurrent.*;
import java.util.concurrent.atomic.*;

public class Treiber<T> {
    private record Node<T>(T value, Node<T> next) { }            // узлы неизменяемы и не переиспользуются
    private final AtomicReference<Node<T>> top = new AtomicReference<>();

    void push(T value) {
        Node<T> current, fresh;
        do {
            current = top.get();
            fresh = new Node<>(value, current);                  // новый узел поверх текущей вершины
        } while (!top.compareAndSet(current, fresh));            // вершина не сменилась — записали
    }

    T pop() {
        Node<T> current;
        do {
            current = top.get();
            if (current == null) return null;
        } while (!top.compareAndSet(current, current.next()));
        return current.value();
    }

    public static void main(String[] args) throws Exception {
        Treiber<Integer> stack = new Treiber<>();
        LongAdder pushed = new LongAdder(), popped = new LongAdder();
        ExecutorService pool = Executors.newFixedThreadPool(8);
        for (int t = 0; t < 8; t++) pool.submit(() -> {
            for (int i = 0; i < 1_000_000; i++) {
                stack.push(i); pushed.add(i);
                Integer v = stack.pop();
                if (v != null) popped.add(v);
            }
        });
        pool.shutdown();
        pool.awaitTermination(1, TimeUnit.MINUTES);
        Integer v;
        while ((v = stack.pop()) != null) popped.add(v);         // добрать остаток
        System.out.println("сумма положенных = сумма снятых: " + (pushed.sum() == popped.sum()));
    }
}
сумма положенных = сумма снятых: true

Восемь потоков сделали по миллиону push и pop, и ни один элемент не потерялся и не задвоился. На том же приёме — CAS по одной ссылке или полю — построены ConcurrentLinkedQueue, вставка в пустую корзину ConcurrentHashMap и поле state в AQS, на котором держатся все замки из темы Locks.

Писать собственные lock-free структуры в прикладном коде почти никогда не нужно. Они сложны: ABA, порядок операций, проверка корректности. А под высокой конкуренцией, как показал шаг 1, CAS-цикл тратит CPU на повторы. Правильный выбор обычно — готовые классы: атомики для одной переменной, LongAdder для счётчиков, ConcurrentHashMap и очереди из java.util.concurrent для структур.

  • CAS атомарно записывает новое значение, только если в ячейке всё ещё ожидаемое. Вокруг него строят цикл: прочитать, вычислить, попытаться, повторить. Видимость — как у volatile.
  • Под конкуренцией CAS-цикл тратит работу на повторы: на 16 потоках — 3,6 неудачных попытки на успешную.
  • Функция в updateAndGet может выполниться несколько раз (в замере — в 5,4 раза чаще обновлений) и должна быть без побочных эффектов.
  • incrementAndGet — одна атомарная инструкция без повторов, но и она не масштабируется на одной ячейке. LongAdder раскладывает счёт по ячейкам и почти не зависит от числа потоков; sum() — не атомарный снимок.
  • ABA: значение вернулось к прежнему, и CAS не заметил изменений. Защита — AtomicStampedReference или неизменяемые, не переиспользуемые узлы.
  • Lock-free — хотя бы один поток всегда продвигается. Свои lock-free структуры пишут редко: готовые классы JDK надёжнее.

На собеседовании

Что такое CAS и как на нём работают атомарные классы?

Compare-and-set — атомарная инструкция процессора: записать новое значение, только если в ячейке сейчас ожидаемое, и сообщить, получилось ли. На ней строится цикл без блокировок: прочитать текущее значение, вычислить новое, попытаться записать через CAS; если кто-то успел раньше — повторить. Так работают updateAndGet, accumulateAndGet и compareAndSet в AtomicInteger, AtomicLong и AtomicReference. Потоки не блокируются, и итог всегда точный.

  • incrementAndGet и getAndAdd JIT компилирует в одну атомарную инструкцию сложения, без цикла. На 16 потоках это в 6,5 раза быстрее updateAndGet(x -> x + 1).
  • CAS даёт семантику volatile для видимости.
  • Функция в updateAndGet может вызываться многократно — побочные эффекты запрещены.
balance.updateAndGet(x -> { audit.log("списание"); return x - amount; }) — что не так?

Функция может выполниться несколько раз: при каждом неудачном CAS она вызывается снова. Аудит получит лишние записи — в замере урока на 8 потоках функция вызывалась в 5,4 раза чаще, чем менялось значение. Аудит пишут после успешного обновления, а функцию оставляют чистой.

Чем LongAdder отличается от AtomicLong?

AtomicLong — одна ячейка, за которую при конкуренции соревнуются все потоки. LongAdder при конкуренции раскладывает счёт по нескольким ячейкам, каждый поток увеличивает свою, а sum() складывает их. Запись масштабируется почти идеально: в замере урока 16 потоков сделали 16 млн увеличений за 5 мс против 88 мс у AtomicLong. Зато чтение дороже, sum() — не атомарный снимок, и нет compareAndSet. Поэтому LongAdder — для метрик и счётчиков, AtomicLong — когда по значению принимают решение: id, лимиты.

Что такое проблема ABA?

CAS сравнивает только текущее значение. Если между чтением и CAS значение сменилось с A на B и обратно на A, CAS пройдёт, хотя состояние вокруг изменилось. Классика — lock-free стек с переиспользуемыми узлами: CAS восстанавливает вершину на узел, который уже снят другим потоком. Решение — AtomicStampedReference, где вместе со ссылкой хранится версия, или узлы, которые не переиспользуются.

  • В Java сборщик мусора защищает от ABA по адресам, пока на узел есть ссылка. Но ABA остаётся при пулах объектов и при CAS по значениям, которые могут вернуться: числа, состояния.

Всегда ли lock-free быстрее блокировок?

Нет. Без конкуренции CAS очень дёшев. Под сильной конкуренцией CAS-цикл тратит CPU на неудачные попытки: в замере урока на 16 потоках — 3,6 повтора на каждую успешную запись, и работа в 16 раз больше заняла в 250 раз больше времени. Главное достоинство lock-free — не скорость, а гарантия продвижения: остановленный поток не блокирует остальных. Для горячих счётчиков лучше убрать конкуренцию (LongAdder), для структур — взять готовые классы java.util.concurrent.

  • java.util.concurrent.atomic (JDK 21) — основа урока: атомарные классы, требования к функциям обновления.
  • LongAdder (JDK 21) — когда предпочесть его AtomicLong.
  • VarHandle (JDK 21) — режимы доступа и CAS на низком уровне.
  • Brian Goetz et al., Java Concurrency in Practice, гл. 15 «Atomic Variables and Nonblocking Synchronization» — CAS, стек Трайбера, ABA.
