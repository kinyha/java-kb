Authentication Basics

Аутентификация отвечает на вопрос «кто прислал этот запрос». Человек входит один раз, а дальше каждый запрос несёт доказательство: id сессии в cookie, токен или ключ. Сессия хранится на сервере и отзывается мгновенно, но требует общего хранилища. Самодостаточный токен проверяется без хранилища, но живёт до своего срока. Basic передаёт пароль в каждом запросе, API-ключ — долгоживущий секрет, который хранят как хеш. Подпись запроса HMAC доказывает знание секрета, не передавая его, и защищает тело от подмены.

Платёжный API впускает людей, партнёров и вебхуки, и каждому нужен свой способ

Оператор поддержки входит в панель через браузер. Магазин-партнёр вызывает API со своего сервера по расписанию. Платёжная система отправляет вебхук, и магазин должен убедиться, что это действительно она, а не кто-то, кто подобрал адрес. Три вида клиентов, три разных ответа на «кто это».

Тема разбирает способы аутентификации на уровне протокола: что передаётся, что хранит сервер, как отозвать доступ и где ломается. Как Spring Security собирает это из фильтров и провайдеров, разобрано в Authentication, а токены JWT — в JWT. Демо AuthDemo.java показывает все механизмы без библиотек: java AuthDemo.java на JDK 21. Ключи и подписи в выводе случайные и при каждом запуске другие.

Basic передаёт пароль в каждом запросе, и base64 его не прячет

HTTP Basic — самый простой способ: заголовок Authorization: Basic и base64 от логин:пароль. Base64 — кодировка, а не шифрование; обратное преобразование не требует ключа:

String header = "Basic " + Base64.getEncoder().encodeToString("shop-7:s3cret!".getBytes(UTF_8));
new String(Base64.getDecoder().decode(header.substring(6)), UTF_8);
== basic
Authorization: Basic c2hvcC03OnMzY3JldCE=
decoded: shop-7:s3cret!

Пароль уходит в каждом запросе, поэтому без TLS Basic недопустим, а с TLS у него остаются две проблемы. Пароль попадает в логи прокси и трассировки, если они пишут заголовки. И сервер проверяет пароль на каждом запросе, а правильная проверка — медленный хеш вроде bcrypt на десятки миллисекунд — превращает каждый вызов API в дорогой. Поэтому Basic оставляют для внутренних инструментов и для обмена логина на токен, а не для постоянной работы.

Сессию можно отозвать мгновенно, а самодостаточный токен живёт до своего срока

После входа пароль больше не нужен: сервер выдаёт доказательство, которое клиент предъявляет в каждом запросе. Есть два принципиально разных вида. Сессия — случайный id, а всё остальное хранится на сервере: кто пользователь, когда вошёл, какие права. Самодостаточный токен несёт данные в себе и подписан сервером, поэтому для проверки хранилище не нужно. Демо выдаёт пользователю и то, и другое, а потом делает выход:

sessions.put(sid, "anna");                              // Сессия: состояние на сервере.
String selfContained = body + "|" + hmacHex(tokenKey, body); // Токен: "anna|exp" и подпись.

sessions.remove(sid);                                    // Выход или блокировка.
== session vs self-contained token
before logout: session=anna, token=anna
after logout:  session=401, token=anna

Сессия исчезла из хранилища, и следующий запрос получил 401. Токен остался валидным: подпись верна, срок не истёк, и сервер не знает, что пользователь вышел. Это и есть главный выбор. Сессия даёт мгновенный отзыв, но каждый запрос читает хранилище, и при нескольких экземплярах сервиса оно должно быть общим — Redis или база. Токен проверяется локально любым экземпляром и любым сервисом, у которого есть ключ, но отозвать его можно только сроком жизни или списком отозванных, который возвращает хранилище обратно.

На практике их сочетают: короткий access-токен на минуты для API и долгая сессия или refresh-токен на сервере, которые можно отозвать. Об этом — в JWT.

Cookie сессии защищают атрибуты, а не сама cookie

В браузере id сессии хранят в cookie: браузер сам прикладывает её к запросам на свой сайт. Сама по себе cookie уязвима к трём атакам, и каждую закрывает свой атрибут:

Set-Cookie: __Host-SID=Qm9q...; Path=/; Secure; HttpOnly; SameSite=Lax; Max-Age=28800
АтрибутЧто делаетОт чего защищает
HttpOnlyCookie недоступна из JavaScriptКражи сессии через XSS
SecureОтправляется только по HTTPSПерехвата в открытой сети
SameSite=LaxНе отправляется в фоновых межсайтовых запросах: POST формы, fetch, картинкиБольшей части CSRF
Префикс __Host-Браузер принимает cookie только с Secure, Path=/ и без DomainПодмены cookie с поддомена
Max-AgeСрок жизни в браузереВечных сессий на чужих компьютерах

Без Domain cookie уходит только на тот хост, который её поставил. С Domain=pay.example она уходит и на все поддомены, включая забытый promo.pay.example на стороннем хостинге. Время жизни сессии ограничивают дважды: по бездействию и абсолютно, например 30 минут и 8 часов. После входа id сессии меняют, иначе атакующий, подсунувший жертве свой id заранее, окажется в её сессии — это фиксация сессии, разобранная в Authentication. CSRF и XSS подробно — в Web Vulnerabilities.

API-ключ показывают один раз, а хранят только хеш

Серверу партнёра не нужен вход с паролем: ему выдают API-ключ — длинную случайную строку, которую он передаёт в заголовке. Ключ — тот же пароль, только долгоживущий и машинный, поэтому в базе его не хранят открытым текстом. Утечка таблицы ключей не должна давать доступ к API:

String prefix = "pk_live_" + token(4);               // Открытая часть: поиск и опознание.
String fullKey = prefix + "." + token(24);            // Отдаётся клиенту один раз.
keysByPrefix.put(prefix, new StoredKey("shop-7", sha256Hex(fullKey)));

StoredKey k = keysByPrefix.get(prefix);               // Поиск по префиксу.
MessageDigest.isEqual(sha256Hex(presented).getBytes(), k.sha256().getBytes()); // Сравнение без раннего выхода.
== api keys
issued:  pk_live_3K6HBg.pjJRBObgurayGoqHc1XcbCrRzz4sZn3C
stored:  pk_live_3K6HBg -> StoredKey[owner=shop-7, sha256=181c55c64347bd3948f2a98c04b65b4128933e8847d86369358be92decd3d407]
check valid:   shop-7
check guessed: 401

Здесь достаточно SHA-256, хотя для паролей он запрещён. Пароль придумывает человек, и его подбирают по словарю: медленный хеш вроде bcrypt делает каждую попытку дорогой. Ключ — 24 случайных байта, 192 бита, и перебрать их невозможно при любой скорости хеша, а быстрый хеш не тормозит каждый запрос. Префикс решает две задачи: по нему ищут запись в базе по индексу, и по нему сканеры секретов в GitHub находят утёкшие ключи. Часть live отличает боевой ключ от тестового.

Сравнение — MessageDigest.isEqual, а не equals: обычное сравнение строк выходит на первом несовпавшем символе, и по времени ответа можно подбирать значение по символу. У ключа должны быть владелец, права, дата последнего использования и возможность выпустить новый, пока старый ещё работает, — без этого ротация означает простой у партнёра.

Подпись запроса доказывает знание секрета и защищает тело от подмены

Ключ в заголовке подтверждает, кто отправил запрос, но не защищает его содержимое и сам ключ: тот, кто увидел запрос в логе прокси, может повторить его с любым телом. Подпись HMAC работает иначе. Клиент и сервер знают общий секрет, но по сети он не передаётся. Клиент собирает строку из метода, пути, времени и хеша тела, вычисляет от неё HMAC-SHA256 секретом и отправляет результат в заголовке. Сервер вычисляет то же самое и сравнивает:

String sign(String method, String path, long ts, String body) {
    return hmacHex(shopSecret, method + "\n" + path + "\n" + ts + "\n" + sha256Hex(body));
}
if (Math.abs(serverNow - ts) > 300) return "401 stale timestamp";   // Окно против повтора.
== signed requests
signature: 1c6fe0bf23da6b6d...
original:        200
amount changed:  401 bad signature
replayed +10min: 401 stale timestamp

Так устроены AWS Signature V4 и подписи вебхуков в Stripe и GitHub: магазин проверяет, что вебхук прислала платёжная система и что сумму в нём никто не менял. Подписывают сырые байты тела, а не JSON после разбора: переразметка меняет пробелы и порядок полей, и подпись перестанет совпадать. Для связи между своими сервисами вместо общих секретов часто используют mTLS — клиентский сертификат проверяется при TLS-рукопожатии, разобранном в TLS.

Раз API работает по HTTPS, ключа в заголовке достаточно, и подпись запросов не нужна.

HTTPS защищает канал, но не концы: заголовки попадают в логи прокси, трассировки и отчёты об ошибках, и ключ оттуда используют для любых запросов. Подпись не раскрывает секрет и привязана к телу и времени, поэтому перехваченный запрос нельзя изменить и можно повторить только в коротком окне.

  • Basic — base64 пароля в каждом запросе: только с TLS и не для постоянной работы.
  • Сессия отзывается сразу, но требует общего хранилища; самодостаточный токен проверяется локально и живёт до срока — в демо он пережил выход.
  • Cookie сессии: HttpOnly, Secure, SameSite, префикс __Host-, без Domain; id меняют после входа.
  • API-ключ: показать один раз, хранить SHA-256 с префиксом для поиска, сравнивать за постоянное время.
  • HMAC-подпись: метод, путь, время и хеш тела; секрет не передаётся, подмена и старый повтор дают 401.

На собеседовании

Чем stateful-аутентификация через сессии отличается от stateless через токены?

Сессия — случайный id у клиента, а данные пользователя хранятся на сервере. Её можно отозвать сразу, удалив запись, но каждый запрос читает хранилище, и при нескольких экземплярах оно должно быть общим. Самодостаточный токен вроде JWT несёт данные в себе и подписан: любой сервис с ключом проверяет его без хранилища, но отозвать его до срока нельзя.

Поэтому access-токены делают короткими, а долгую часть — refresh-токен или сессию — хранят на сервере, чтобы её можно было отозвать.

  • Список отзыва для токенов возвращает хранилище и сводит на нет выигрыш stateless.
  • Для браузера и своего бэкенда сессия в HttpOnly-cookie часто безопаснее токена в JavaScript.
  • Сессию ограничивают по бездействию и абсолютно, а после входа меняют её id.

Как правильно выдавать и хранить API-ключи?

Ключ генерируют криптостойким генератором, показывают клиенту один раз, а в базе хранят только хеш. Для ключа достаточно SHA-256: он случайный и длинный, перебор невозможен, а медленный хеш затормозил бы каждый запрос. Открытый префикс нужен для поиска записи и для сканеров утёкших секретов. Сравнивают за постоянное время.

  • У ключа есть владелец, права, срок и дата последнего использования.
  • Ротация без простоя: выдать новый ключ, пока старый работает, и отключить старый после перехода.
  • Ключ в заголовке виден в логах; для защиты тела и от повтора используют подпись HMAC или mTLS.
Что не так с этой проверкой ключа? 
ApiKey k = repo.findByValue(request.getHeader("X-Api-Key")); // Ключи хранятся как есть.
if (k == null) throw new Unauthorized();
log.info("request from key {}", request.getHeader("X-Api-Key"));

Ключи лежат в базе открытым текстом: утечка таблицы или бэкапа даёт доступ ко всем партнёрам. Ключ пишется в лог целиком, и любой, кто читает логи, может им воспользоваться. Нужно хранить SHA-256 ключа, искать по открытому префиксу, сравнивать хеши через MessageDigest.isEqual и логировать только префикс.

Как проверить, что вебхук пришёл от настоящего отправителя?

Отправитель подписывает запрос HMAC-SHA256 общим секретом: строка из времени и сырого тела. Получатель вычисляет ту же подпись и сравнивает за постоянное время. Секрет по сети не передаётся, а изменение тела меняет подпись. Время в подписи и проверка окна в несколько минут защищают от повтора старых вебхуков.

  • Подписывают сырые байты тела: после разбора и сериализации JSON подпись не совпадёт.
  • Внутри окна повтор ловят по id события, который сохраняют как ключ идемпотентности.
  • Так устроены подписи вебхуков Stripe и GitHub и AWS Signature V4.

Какие атрибуты нужны cookie сессии?

HttpOnly — чтобы JavaScript и XSS не могли её прочитать. Secure — только по HTTPS. SameSite=Lax или Strict — чтобы браузер не отправлял её в межсайтовых фоновых запросах, это закрывает большую часть CSRF. Разумный срок жизни.

  • Префикс __Host- требует Secure, Path=/ и запрещает Domain: поддомен не подменит cookie.
  • Domain расширяет отправку на все поддомены, включая сторонние.
  • SameSite не заменяет CSRF-токен полностью: поддомены считаются тем же сайтом.
  • OWASP: Session Management Cheat Sheet — основа урока о сессиях: id, атрибуты cookie, сроки, фиксация.
  • RFC 7617: The 'Basic' HTTP Authentication Scheme — формат Basic.
  • AWS: Create a signed request (SigV4) — каноническая строка и подпись запроса.
  • Stripe: Verify webhook signatures — подпись вебхуков, время и защита от повтора.
