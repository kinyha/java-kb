Background Jobs

Фоновая задача — работа, которую не нужно делать, пока пользователь ждёт ответа: письмо, отчёт, вызов медленного внешнего API. Её кладут в очередь и отвечают сразу (202 Accepted со ссылкой на статус), а воркеры выполняют задачи независимо. Очередь можно держать в той же базе: воркер берёт задачу через FOR UPDATE SKIP LOCKED, иначе все воркеры выстраиваются за одной строкой — в демо 11,7 с вместо 1,4. Воркер может умереть посреди задачи, поэтому задача берётся в аренду со сроком: по истечении её забирает другой. Значит, задача может выполниться дважды и должна быть идемпотентной. Неудачи повторяют с растущей задержкой, а после нескольких попыток задачу откладывают в dead letter для разбора.

Ответ ждёт отправки письма и формирования PDF

Обработчик оформления заказа сохраняет заказ, формирует PDF-чек за 800 мс и отправляет письмо через внешний сервис, который иногда отвечает за 5 секунд. Пользователь ждёт всё это время, а если почтовый сервис недоступен, оформление заказа падает, хотя заказ уже сохранён. Чек и письмо не нужны для ответа: достаточно записать задачу «отправить чек по заказу 42» в той же транзакции, что и заказ, и ответить сразу.

Тема разбирает очередь задач в PostgreSQL, аренду и повторы, асинхронный запрос-ответ и выбор между базой и брокером. Публикация событий из той же транзакции — в Transactional Outbox, брокеры — в Messaging. Демо JobQueueDemo.java держит очередь в таблице PostgreSQL 17; задача — 20 мс работы, воркеров 8.

create table job(
  id bigserial primary key,
  payload text,
  status text not null default 'READY',          -- READY, RUNNING, DONE, DEAD
  attempts int not null default 0,
  run_at timestamptz not null default now(),     -- не раньше этого времени (backoff)
  locked_until timestamptz,                      -- аренда: после истечения задачу берёт другой
  done_by text);
create index on job (run_at) where status = 'READY';

FOR UPDATE выстраивает воркеров в очередь, SKIP LOCKED — нет

// Классический вариант: строка заблокирована, пока идёт работа.
ResultSet r = c.createStatement().executeQuery(
    "select id from job where status = 'READY' order by id limit 1 for update" + lockMode);
long id = r.getLong(1);
Thread.sleep(20);                                           // работа под блокировкой
c.createStatement().executeUpdate("update job set status = 'DONE' where id = " + id);
c.commit();
== 400 jobs, 8 workers, each job takes 20 ms; row locked for the whole job
   for update               done 400 in 11663 ms, empty polls 0
   for update skip locked   done 400 in  1376 ms, empty polls 8

С FOR UPDATE 400 задач по 20 мс выполнялись 11,7 с — дольше, чем 400 × 20 мс = 8 с одним воркером: восемь воркеров не только не помогли, но и добавили накладные расходы на ожидание и перепроверку строк. С SKIP LOCKED — 1,4 с, почти 8-кратное ускорение. Несколько пустых опросов в конце — воркеры, которые видели только заблокированные последние задачи. SKIP LOCKED есть в PostgreSQL с 9.5, в MySQL 8 и Oracle; на нём, например, работает режим lock-and-fetch планировщика db-scheduler. Время выполнения меняется от запуска к запуску, соотношение — нет.

Аренда вместо долгой транзакции: упавший воркер не теряет задачу

update job set status = 'RUNNING', attempts = attempts + 1,
               locked_until = now() + interval '2 seconds', done_by = ?
where id = (
  select id from job
  where (status = 'READY' and run_at <= now())
     or (status = 'RUNNING' and locked_until < now())     -- аренда истекла: воркер умер
  order by id limit 1
  for update skip locked)
returning id
== same, but claim commits at once and the lease protects the job
   claim + lease            done 400 in  1404 ms, empty polls 0
== worker crashes after taking a job; lease is 2 s
   w-crashed took job 1, status RUNNING
   w2 immediately: nothing to take
   w2 after 2.2 s: took job 1, attempts 2

Держать транзакцию открытой всю работу плохо: задача на минуту — это минута открытой транзакции, которая мешает VACUUM и держит соединение из пула, как в VACUUM. Поэтому задачу берут короткой транзакцией: помечают RUNNING с арендой locked_until, коммитят и работают уже без блокировок. Скорость та же — 1,4 с на 400 задач. Если воркер упал, не закончив, задача остаётся RUNNING, но после истечения аренды её забирает другой: в демо w2 сразу ничего не взял, а через 2,2 с взял ту же задачу второй попыткой. Долгие задачи продлевают аренду периодически (heartbeat).

Обратная сторона аренды — повтор выполнения. Воркер мог не упасть, а зависнуть на сборке мусора или медленном вызове: аренда истекла, задачу взял второй, а первый проснулся и тоже закончил. Задача выполнится дважды, поэтому она должна быть идемпотентной: письмо — с ключом идемпотентности у почтового провайдера, запись — через upsert, как в Idempotency. Гарантию «ровно один раз» очередь задач не даёт — только «хотя бы один раз».

Повторы с задержкой и dead letter

== job fails: retry with backoff, then dead letter after 3 attempts
   attempt 1: failed -> retry in 200 ms
   attempt 2: failed -> retry in 400 ms
   attempt 3: failed -> DEAD, needs a human

Неудача задачи — обычное дело: внешний сервис вернул 503, база была перегружена. Задачу возвращают в READY с run_at в будущем, увеличивая задержку с каждой попыткой (в демо 200, 400 мс; в жизни — секунды и минуты), чтобы не долбить больной сервис, как разобрано в Overload. После нескольких попыток задача уходит в DEAD — dead letter: дальше повторять бессмысленно, нужен человек или исправление кода. Мёртвые задачи должны быть видны в мониторинге, а их повторный запуск после исправления — одной командой. Ошибки, которые повтор не исправит (неверные данные, 400 от внешнего API), сразу отправляют в DEAD без повторов.

Асинхронный запрос-ответ и выбор между базой и брокером

POST /v1/reports            { "month": "2026-09" }
202 Accepted
Location: /v1/reports/jobs/81

GET /v1/reports/jobs/81
200 OK  { "status": "RUNNING" }
...
200 OK  { "status": "DONE", "result": "/v1/reports/81.pdf" }

Когда результат нужен пользователю, но считается долго, API принимает задачу ответом 202 со ссылкой на статус, а клиент опрашивает статус или получает вебхук по завершении. Статус — это и есть строка задачи. Опрос дешевле держать короткими запросами с Retry-After, чем держать соединение открытым.

Очередь в базе проще: нет нового компонента, задача ставится атомарно с данными, видно статус и историю. Её выбирают, пока поток задач умеренный. Брокер нужен, когда задач очень много, их потребляют разные сервисы или нужна доставка с малой задержкой без опроса. Планировщики по расписанию (@Scheduled, Quartz) в кластере из нескольких экземпляров запускают задачу на каждом экземпляре; чтобы выполнял один, используют блокировку в базе — ShedLock или тот же SKIP LOCKED.

Чем больше воркеров читают очередь из таблицы, тем быстрее она разбирается.

С FOR UPDATE воркеры выбирают одну и ту же первую строку и ждут друг друга: восемь воркеров разобрали 400 задач за 11,7 с — дольше, чем 400 × 20 мс = 8 с чистой последовательной работы. Параллельность даёт SKIP LOCKED: 1,4 с.

  • Работу, не нужную для ответа, кладут в очередь в той же транзакции, что и данные, и отвечают сразу.
  • FOR UPDATE: 8 воркеров разбирают 400 задач за 11,7 с; SKIP LOCKED — за 1,4 с.
  • Задачу берут короткой транзакцией с арендой; после истечения аренды её забирает другой воркер.
  • Аренда даёт «хотя бы один раз»: задачи должны быть идемпотентными.
  • Повторы с растущей задержкой, после N попыток — dead letter с мониторингом.
  • Долгий результат — 202 Accepted и статус; база — для умеренного потока, брокер — для большого.

На собеседовании

Как сделать очередь задач на реляционной базе?

Таблица задач со статусом, числом попыток, временем следующего запуска и сроком аренды. Воркер берёт задачу UPDATE ... WHERE id = (SELECT ... FOR UPDATE SKIP LOCKED LIMIT 1) RETURNING, помечает RUNNING с арендой и коммитит; работает вне транзакции; по завершении — DONE, при ошибке — READY с задержкой или DEAD. Задача с истёкшей арендой снова доступна.

  • Без SKIP LOCKED воркеры ждут одну строку и работают последовательно.
  • Частичный индекс по готовым задачам; старые DONE удалять или переносить, чтобы таблица не росла.
  • Задачи идемпотентны: аренда даёт «хотя бы один раз».
Что не так с этим воркером? 
@Scheduled(fixedDelay = 1000)
@Transactional
public void process() {
    List<Job> jobs = jobRepository.findTop100ByStatusOrderById(READY);   // select ... for update
    for (Job job : jobs) {
        mailClient.send(job.getPayload());                                  // до 5 секунд
        job.setStatus(DONE);
    }
}

Одна транзакция на 100 задач с внешними вызовами — до 500 секунд открытой транзакции с блокировками: остальные экземпляры приложения ждут те же строки, VACUUM не может чистить таблицу. Если отправка одного письма упадёт, откатятся статусы всех ста, и уже отправленные письма уйдут повторно. Нужно брать задачи по одной или небольшими пачками с SKIP LOCKED и арендой, коммитить сразу, отправлять письма вне транзакции и делать отправку идемпотентной.

Как обрабатывать неудачи фоновых задач?

Повторять с экспоненциальной задержкой и ограничением числа попыток; после него — dead letter, видимый в мониторинге, с возможностью перезапуска после исправления. Ошибки, которые повтор не исправит, сразу в dead letter. Задачи должны быть идемпотентными, потому что повтор возможен и после частичного выполнения.

  • Jitter к задержке, чтобы задачи не повторялись разом.
  • Отдельно различать «упал воркер» (аренда) и «упала задача» (повтор с backoff).

Как вернуть клиенту результат долгой операции?

Асинхронный запрос-ответ: принять задачу ответом 202 Accepted со ссылкой на статус, выполнить в фоне, а клиент опрашивает статус или получает вебхук или сообщение по WebSocket. Статус хранится в строке задачи, результат — по ссылке после завершения.

  • Retry-After в ответе статуса задаёт частоту опроса.
  • Ключ идемпотентности на создание задачи, чтобы повтор POST не запустил вторую.

  • Azure Architecture: Asynchronous Request-Reply и Competing Consumers.
  • ShedLock, db-scheduler — планировщики на базе в кластере.
