Banking Basics

Когда сервис переводит деньги, он меняет обязательства перед людьми и организациями. Остаток показывает текущее положение, а журнал объясняет, откуда оно взялось. Каждая проведённая операция связывает дебетовые и кредитовые строки на одинаковую сумму. Повтор запроса, резерв и исправление требуют своих правил: само равенство сумм этих ошибок не ловит. Внешняя сверка проверяет, совпадает ли наша история с тем, что произошло за пределами сервиса.

Остаток показывает результат, но не объясняет движение денег

У Alice 1 000 ₽, у Bob — 0. Сервис переводит 120 ₽: уменьшает один остаток и увеличивает другой. Между изменениями процесс падает. После запуска Alice видит 880 ₽, Bob по-прежнему 0. По двум числам нельзя восстановить, какая операция оборвалась и должен ли сервис дописать вторую половину.

Это модель двух независимых записей, а не поведение транзакционной БД. В LedgerDemo.java сбой задан явно. Все суммы демо — в копейках; запуск — JDK 21, без библиотек: java -ea examples/banking/LedgerDemo.java.

static void brokenBalances() {
    long alice = 100_000, bob = 0;
    try {
        alice -= 12_000; // Первый независимый UPDATE успел завершиться.
        throw new IllegalStateException("crash before credit");
    } catch (IllegalStateException e) {
        System.out.printf("partial alice=%d bob=%d total=%d%n", alice, bob, alice + bob);
    }
}

partial alice=88000 bob=0 total=88000

Транзакция решает проблему частичной записи, но для объяснения истории нужен учёт операции. Счёт в такой системе группирует денежные требования или обязательства. Строка проводки меняет один счёт по дебету или кредиту. Журнальная операция связывает строки общей причиной: переводом, комиссией, пополнением. Слово «транзакция» здесь лучше уточнять: бизнес-операция и транзакция БД — разные уровни.

Номер счёта клиента, внутренний идентификатор счёта в ledger и номер карты тоже выполняют разные задачи. Один человек может иметь несколько счетов в разных валютах. Одна карта может давать доступ к счёту, но сама не является его остатком. Система учёта, ledger, хранит счета и изменения их положения; продуктовый сервис хранит смысл платежа, его участников и состояние обработки.

Текущий баланс можно получить из начального положения и проведённых строк. В рабочей системе его часто поддерживают как отдельный итог для быстрого чтения. Такой итог должен соответствовать журналу на той же границе данных. Исправить только итог, оставив журнал прежним, — значит создать две несовместимые версии истории.

Тип счёта определяет, что увеличивают дебет и кредит

Сначала выбери, чьи книги ведёт сервис. На счёте Alice лежат её деньги, поэтому для неё это актив. Для банка тот же остаток означает обязательство перед Alice. Отсюда внешне странное правило: кредит клиентского счёта увеличивает долг банка клиенту, дебет — уменьшает. Дебет и кредит называют стороны записи, а не универсальные «минус» и «плюс».

В учебных книгах банка сначала появятся 1 000 ₽ денежного актива и обязательство перед Alice на ту же сумму: дебет cash, кредит alice. Это упрощённое начальное положение, не полный баланс банка. Теперь переведём Bob 120 ₽ и удержим комиссию 3 ₽. Дебетуем обязательство перед Alice на 123 ₽; кредитуем обязательство перед Bob на 120 ₽ и доход на 3 ₽.

Дебетовые суммы и кредитовые суммы операции равны: 123 = 120 + 3. Двойная запись означает согласованное отражение обеих сторон изменения; строк может быть больше двух. Упрощённое уравнение положения после операции: актив 1 000 = обязательства 877 + 120 + доход 3. В полной модели доходы и расходы меняют капитал; отдельно показанный доход здесь объясняет источник разницы.

Ниже типы и данные из LedgerDemo. debitNormal задаёт сторону, которая увеличивает положительный остаток счёта. Реализация Ledger.post будет раскрыта в следующем шаге. Здесь видно, какой тип имеет каждый счёт и какие строки составляют перевод.

enum Side { D, C }
enum Kind {
    ASSET(true), LIABILITY(false), INCOME(false);
    final boolean debitNormal;
    Kind(boolean debitNormal) { this.debitNormal = debitNormal; }
}
record Account(Kind kind, String currency) {}
record Line(String account, Side side, long minor) {}
record Journal(String id, List<Line> lines) {
    Journal { lines = List.copyOf(lines); }
}
static Journal opening() {
    return new Journal("opening", List.of(
        new Line("cash", Side.D, 100_000),
        new Line("alice", Side.C, 100_000)));
}

static Journal transfer(String id) {
    return new Journal(id, List.of(
        new Line("alice", Side.D, 12_300), // Обязательство банка перед Alice уменьшается.
        new Line("bob", Side.C, 12_000),   // Обязательство перед Bob растёт.
        new Line("fee", Side.C, 300)));   // Комиссионный доход растёт.
}

static Ledger opened() {
    Ledger l = new Ledger(); l.post(opening()); return l;
}

static void show(String name, Ledger l) {
    System.out.printf("%s alice=%d bob=%d fee=%d cash=%d journals=%d%n", name,
        l.balance("alice"), l.balance("bob"), l.balance("fee"),
        l.balance("cash"), l.journal.size());
}

static void check(boolean ok) { if (!ok) throw new AssertionError(); }
static void normal() {
    Ledger l = opened(); l.post(transfer("pay-1")); show("posted", l);
    check(l.balance("alice") == 87_700 && l.balance("bob") == 12_000);
}

normal();
posted alice=87700 bob=12000 fee=300 cash=100000 journals=2

Сумма клиентских остатков уменьшилась на комиссию, а денежный актив не изменился. Это корректно для выбранной модели внутреннего перевода. При переводе во внешний банк появляется расчётная сторона: требование или обязательство к участнику расчёта, а затем движение расчётных средств. Конкретные промежуточные счета определяются процессом; один универсальный «счёт денег» скрывает эти различия.

«Раз все строки сошлись, платёж проведён правильно».

Сбалансированными могут быть ошибочный получатель, повторный платёж и неверная комиссия. Равенство ловит потерянную сторону суммы. Правила назначения счетов, уникальность операции и проверка внешнего результата отвечают за другие ошибки.

Публикуй операцию целиком и сохраняй её при исправлении

У журнальной операции есть устойчивый идентификатор, причина и набор строк. Перед проведением проверь существование счетов, допустимость суммы и баланс дебета с кредитом. Валюты проверяй раздельно: десять рублей нельзя уравновесить десятью долларами. Обмен требует связанных валютных сторон и правила курса; числовая сумма разных валют не имеет учётного смысла.

В демо сначала вычисляем всё на копии остатков. При ошибке копия выбрасывается. Только после проверок она становится новым состоянием, а операция добавляется в журнал. Это модель одного потока в памяти. Настоящая система сохраняет строки, регистрацию ключа и зависимые итоги одной транзакцией в устойчивом хранилище; между двумя присваиваниями Java нет гарантии восстановления после сбоя процесса.

static final class Ledger {
    final Map<String, Account> accounts = Map.of(
        "cash", new Account(Kind.ASSET, "RUB"),
        "alice", new Account(Kind.LIABILITY, "RUB"),
        "bob", new Account(Kind.LIABILITY, "RUB"),
        "fee", new Account(Kind.INCOME, "RUB"));
    Map<String, Long> balances = new HashMap<>();
    final Map<String, Journal> journal = new LinkedHashMap<>();

    boolean post(Journal j) {
        if (j.id() == null || j.id().isBlank()) throw new IllegalArgumentException("empty id");
        Journal old = journal.get(j.id());
        if (old != null) {
            if (!old.equals(j)) throw new IllegalArgumentException("id conflict");
            return false; // Тот же ключ и те же строки: уже проведено.
        }
        if (j.lines().size() < 2) throw new IllegalArgumentException("too few lines");
        Map<String, Long> net = new HashMap<>();
        Map<String, Long> next = new HashMap<>(balances); // Пока меняем только копию.
        for (Line l : j.lines()) {
            Account a = accounts.get(l.account());
            if (a == null || l.side() == null || l.minor() <= 0)
                throw new IllegalArgumentException("invalid line");
            long signed = l.side() == Side.D ? l.minor() : -l.minor();
            net.merge(a.currency(), signed, Math::addExact); // Каждая валюта отдельно.
            long delta = a.kind().debitNormal ? signed : -signed;
            next.merge(l.account(), delta, Math::addExact);
        }
        if (net.values().stream().anyMatch(n -> n != 0))
            throw new IllegalArgumentException("unbalanced");
        balances = next;
        journal.put(j.id(), j); // Учебная публикация: один поток, память, без БД.
        return true;
    }
    long balance(String account) { return balances.getOrDefault(account, 0L); }
}
static void rejected() {
    Ledger l = opened();
    try {
        l.post(new Journal("broken", List.of(
            new Line("alice", Side.D, 12_300), new Line("bob", Side.C, 12_000))));
    } catch (IllegalArgumentException e) { System.out.println("rejected=" + e.getMessage()); }
    show("unchanged", l);
    check(l.balance("alice") == 100_000 && l.journal.size() == 1);
}

Для отказавшей операции отсутствует комиссия 300 копеек, поэтому проверка обнаруживает разницу. Обязательство банка перед Alice остаётся равным 100 000 копеек, в журнале только начальная запись. Не нужно искать, какую половину удалось применить: отклонённый набор не стал частью проведённой истории.

Равенство сумм не узнаёт повтор

Один и тот же ключ с прежним содержимым возвращает прежний результат. Тот же ключ с другой суммой — конфликт, который нельзя тихо принять. Новый ключ означает новую операцию. В примере строки сравниваются как список, включая порядок; промышленный отпечаток запроса строят по заранее определённому набору значимых полей и правилам нормализации.

static void retries() {
    Ledger l = opened(); Journal payment = transfer("pay-1");
    System.out.println("first=" + l.post(payment));
    System.out.println("retry=" + l.post(payment));
    try {
        l.post(new Journal("pay-1", List.of(
            new Line("alice", Side.D, 12_400), new Line("bob", Side.C, 12_400))));
    } catch (IllegalArgumentException e) { System.out.println("conflict=" + e.getMessage()); }
    l.post(transfer("pay-2")); // Новый ключ: даже одинаковые суммы считаются новой операцией.
    show("new-key", l);
    check(l.balance("alice") == 75_400 && l.journal.size() == 3);
}

Оба проведённых платежа с разными ключами сбалансированы. Alice уменьшилась до 754 ₽, Bob получил 240 ₽, доход стал 6 ₽. Если это один пользовательский платёж, ошибку создало назначение нового ключа на повторе. Генерировать его нужно на границе возникновения операции и сохранять при повторной доставке.

Исправление оставляет след исходной ошибки

Уже проведённую ошибку исправляем новой операцией. В учебном примере меняем стороны всех строк pay-1 и связываем обратную запись с исходной через её идентификатор. Результат возвращается к началу, но в журнале остаются opening, pay-1 и reverse:pay-1. Такое полное сторнирование отличается от отдельного возврата товара: комиссию, частичную сумму и расчёт с другой стороной определяет бизнес-правило.

static void correction() {
    Ledger l = opened(); Journal original = transfer("pay-1"); l.post(original);
    List<Line> opposite = original.lines().stream()
        .map(x -> new Line(x.account(), x.side() == Side.D ? Side.C : Side.D, x.minor()))
        .toList();
    l.post(new Journal("reverse:pay-1", opposite)); // Новая запись, исходная сохранена.
    show("reversed", l);
    System.out.println("original-kept=" + l.journal.get("pay-1").equals(original));
    check(l.balance("alice") == 100_000 && l.balance("fee") == 0);
}

correction();
reversed alice=100000 bob=0 fee=0 cash=100000 journals=3
original-kept=true

Новая запись делает историю проверяемой: что было проведено, когда нашли ошибку и чем её исправили. Для одного полного сторно нужен запрет повторного сторнирования исходной операции, а не только уникальность произвольного ключа новой записи. Если получатель уже потратил деньги, обратные строки нельзя безусловно применять поверх ограничения на отрицательный остаток. Может потребоваться отдельное требование к получателю; исходные сведения от этого не исчезают.

Глубже: что должна обеспечить граница записи в БД

Уникальность ключа разрешает конкуренцию двух одинаковых запросов: один фиксирует результат, другой читает уже существующий или получает конфликт. Проверка доступного остатка и его уменьшение должны иметь общую границу сериализации. Иначе два разных платежа прочитают 1 000 ₽ и каждый разрешит списать 600 ₽. Двойная запись обоих наборов не запретит перерасход.

Выбор блокировки, условного изменения версии или сериализуемой транзакции зависит от хранилища. При переводе нескольких счетов нужен согласованный порядок захвата и повтор транзакции после разрешимого конфликта. Событие о проведении сохраняют вместе с журналом через outbox, если получатель находится за границей БД. Эти механизмы разобраны в DB Transactions, DB Locks и Outbox.

Сумма становится деньгами только вместе с валютой и правилом округления

Число 12 300 само по себе ничего не говорит о размере платежа. В нашем контракте это RUB и две десятичные цифры, то есть 123 ₽. Храни единицу вместе со значением и проверяй её на границе операции. В примере ledger валюта принадлежит счёту, Money несёт её в самом значении. Сложение разных валют требует операции обмена, а не арифметики без проверки.

Двоичный double не представляет многие десятичные доли точно. Переход к BigDecimal после такого преобразования не восстанавливает исходное десятичное намерение. В MoneyDemo.java сравниваются двоичное значение и сумма из строк.

static void binary() {
    System.out.println("double=" + (0.1 + 0.2));
    System.out.println("constructor=" + new BigDecimal(0.1).toPlainString());
    System.out.println("text=" + new BigDecimal("0.1").add(new BigDecimal("0.2")));
}

Строка или целое число минимальных единиц сохраняют входную точность. BigDecimal.valueOf(double) использует десятичную строку double и отличается от его конструктора, но уже выполненную неточную арифметику этим не исправить. Для API задай формат суммы до вычисления: например, десятичная строка или целое значение с указанной единицей.

Точность и место округления — часть тарифа

Пусть в учебном тарифе комиссия равна 1% с округлением HALF_UP до копейки. Три платежа по 0,50 ₽ дают три комиссии по 0,01 ₽. Если сначала объединить платежи, комиссия с 1,50 ₽ округлится до 0,02 ₽. Оба вычисления точны по своему правилу, но правила разные.

static void rounding() {
    BigDecimal gross = new BigDecimal("0.50"), rate = new BigDecimal("0.01");
    BigDecimal each = gross.multiply(rate).setScale(2, RoundingMode.HALF_UP);
    BigDecimal separately = each.multiply(BigDecimal.valueOf(3));
    BigDecimal together = gross.multiply(BigDecimal.valueOf(3)).multiply(rate)
        .setScale(2, RoundingMode.HALF_UP);
    System.out.println("per-payment=" + separately + " per-batch=" + together);
    if (!separately.equals(new BigDecimal("0.03"))) throw new AssertionError();
}

rounding();
per-payment=0.03 per-batch=0.02

Поэтому сохраняй применённый тариф, исходную базу и денежный результат. Если при сверке пересчитать старые операции по новому тарифу или с другой точкой округления, получится новая история вместо проверки прежней. При распределении округлённой суммы между получателями остаточную копейку назначают по явному правилу так, чтобы сумма частей совпала с общей суммой.

record Money(String currency, long minor) {
    Money add(Money other) {
        if (!currency.equals(other.currency)) throw new IllegalArgumentException("currency mismatch");
        return new Money(currency, Math.addExact(minor, other.minor));
    }
}

static long rubMinor(String amount) {
    return new BigDecimal(amount).setScale(2, RoundingMode.UNNECESSARY)
        .movePointRight(2).longValueExact(); // Контракт примера: RUB, две десятичные цифры.
}
static void validation() {
    System.out.println("minor=" + rubMinor("123.00"));
    try { rubMinor("1.001"); }
    catch (ArithmeticException e) { System.out.println("extra-fraction=rejected"); }
    try { new Money("RUB", 100).add(new Money("USD", 100)); }
    catch (IllegalArgumentException e) { System.out.println("mixed=" + e.getMessage()); }
    try { new Money("RUB", Long.MAX_VALUE).add(new Money("RUB", 1)); }
    catch (ArithmeticException e) { System.out.println("overflow=rejected"); }
}

extra-fraction=rejected

Для входной суммы в контракте RUB выбрано правило: лишнюю дробную точность отклонить, а не округлить молча. Для расчёта комиссии правило другое и явно задано. longValueExact проверяет, что значение помещается в long; Math.addExact ловит переполнение сложения. Молча переполненное целое способно превратить большой положительный остаток в отрицательный.

У всех валют нет общего числа «два знака». Currency.getDefaultFractionDigits возвращает число минимальных десятичных разрядов по данным валюты; для JPY это 0, для EUR — 2, для псевдовалют возможен -1. Контракт платёжного провайдера может задавать собственную единицу передачи. Курсы и промежуточные расчёты требуют большей точности, чем конечное денежное списание. Подробные правила Java относятся к теме BigDecimal; здесь важно согласовать представление с учётной моделью.

Резерв уменьшает доступное, а проведение меняет учтённый остаток

Для платежа иногда надо сначала удержать возможность потратить сумму, а позже определить окончательный результат. На учтённом остатке 1 000 ₽ резервируем 300 ₽. Учтённые средства ещё 1 000 ₽, но потратить доступно только 700 ₽. В простом кошельке без овердрафта: доступно = учтено − активные резервы. Кредитный лимит и другие ограничения требуют отдельного правила.

В нашем примере окончательно проводится 280 ₽ из резерва 300 ₽. Учтённый остаток становится 720 ₽, резерв снимается целиком, доступно 720 ₽. Именно освобождённые 20 ₽ объясняют, почему доступное увеличилось относительно состояния резерва. Модель предполагает одно окончательное проведение. Продукт с несколькими частичными захватами должен вести оставшуюся сумму и отдельные операции захвата.

В HoldDemo.java показан один резерв одного кошелька. Он демонстрирует переходы состояний и вычисление доступного. Парная проводка счёта получателя здесь опущена: класс не заменяет ledger и не реализует полноценный перевод.

enum State { NONE, HELD, CAPTURED, RELEASED }

static final class Wallet {
    long posted = 100_000, held;
    State state = State.NONE;
    long available() { return Math.subtractExact(posted, held); }
    void reserve(long amount) {
        if (state != State.NONE || amount <= 0 || amount > available())
            throw new IllegalArgumentException("cannot reserve");
        held = amount; state = State.HELD;
    }
    void capture(long actual) {
        if (state != State.HELD) throw new IllegalStateException("hold is " + state);
        if (actual <= 0 || actual > held) throw new IllegalArgumentException("capture exceeds hold");
        posted = Math.subtractExact(posted, actual);
        held = 0; state = State.CAPTURED; // В примере захват окончательный, остаток резерва снят.
    }
    void release() {
        if (state != State.HELD) throw new IllegalStateException("hold is " + state);
        held = 0; state = State.RELEASED;
    }
    void show(String tag) {
        System.out.printf("%s posted=%d held=%d available=%d state=%s%n",
            tag, posted, held, available(), state);
    }
}
public static void main(String[] args) {
    Wallet w = new Wallet(); w.reserve(30_000); w.show("reserve");
    w.capture(28_000); w.show("capture");
    if (w.available() != 72_000) throw new AssertionError();
    Wallet cancelled = new Wallet(); cancelled.reserve(30_000);
    cancelled.release(); cancelled.show("release");
    try { cancelled.capture(28_000); }
    catch (IllegalStateException e) { System.out.println("late-capture=" + e.getMessage()); }
    cancelled.show("after-late");
}

После снятия резерва позднее подтверждение не должно снова использовать освобождённое право списания. В демо состояние RELEASED запрещает capture, и остаток остаётся 100 000 копеек. Во внешней сети сообщение о реально совершённой операции всё равно может прийти поздно. Его надо сопоставить с текущими сведениями и обработать по правилам домена, а не выбросить как несуществующее денежное событие.

При нескольких резервах каждому нужны идентификатор, остаточная сумма и состояние. Проверка доступного и создание резерва выполняются атомарно: два запроса не должны одновременно зарезервировать одни и те же средства. Таймаут освобождает локальное ограничение, но не доказывает, что внешний платёж не состоялся. Устройство карточной авторизации и окончательного расчёта относится к Payments.

В TigerBeetle Two-Phase Transfers резерв и его завершение также разделены; это пример конкретной реализации учётного правила. Название «две фазы» здесь не означает, что Java-класс или любая карточная сеть выполняют распределённый протокол 2PC.

Сверяй отдельные движения и оставляй проверяемый след исправления

Внутренние строки могут быть сбалансированы, но не совпадать с внешней историей. Банк действительно исполнил операцию, а сообщение потерялось; мы повторно учли одну строку; комиссия удержана отдельно; файл получен не за тот период. Поэтому нужна сверка: сопоставление независимых источников по определённым правилам, с сохранением найденных расхождений.

Начни с того, что сравнивается. Статус бизнес-платежа, проведённая операция ledger и строка внешней выписки относятся к разным слоям. Для сверки денежных движений задай счёт, валюту, направление, идентификатор внешней операции и границу периода. Время получения файла отличается от времени проведения и даты валютирования. Неполный период способен создать расхождение, которое исчезнет после получения следующей части.

Простое демо использует только исходящие движения RUB за один и тот же законченный период. В обоих списках есть 30 000 копеек. Но у нас вторая операция — p2, во внешнем списке — p3. Сверка только итогов эту замену пропустит.

record Row(String ref, String currency, long outgoing) {}
static Map<String, Row> unique(List<Row> rows) {
    Map<String, Row> byRef = new TreeMap<>();
    for (Row row : rows)
        if (byRef.putIfAbsent(row.ref(), row) != null)
            throw new IllegalArgumentException("duplicate " + row.ref());
    return byRef; // Проверяем дубликаты до сопоставления; не затираем их.
}
static void reconcile(List<Row> ours, List<Row> bank) {
    Map<String, Row> a = unique(ours), b = unique(bank);
    Set<String> ids = new TreeSet<>(a.keySet()); ids.addAll(b.keySet());
    for (String id : ids) {
        if (!a.containsKey(id)) System.out.println("extra-external=" + id);
        else if (!b.containsKey(id)) System.out.println("missing-external=" + id);
        else if (!a.get(id).equals(b.get(id))) System.out.println("different=" + id);
    }
}
static long total(List<Row> rows) {
    return rows.stream().mapToLong(Row::outgoing).reduce(0, Math::addExact);
}
public static void main(String[] args) {
    List<Row> ours = List.of(new Row("p1", "RUB", 10_000), new Row("p2", "RUB", 20_000));
    List<Row> bank = List.of(new Row("p1", "RUB", 10_000), new Row("p3", "RUB", 20_000));
    System.out.printf("totals ours=%d bank=%d%n", total(ours), total(bank));
    reconcile(ours, bank); // Суммы совпали, идентичность операций — нет.
    reconcile(List.of(new Row("p1", "RUB", 10_000)), List.of(new Row("p1", "RUB", 9_900)));
    try { reconcile(ours, List.of(bank.get(0), bank.get(0))); }
    catch (IllegalArgumentException e) { System.out.println("rejected=" + e.getMessage()); }
}

Полный исходник — ReconcileDemo.java. В нём ключ ref уникален по контракту примера. Реальная выписка может иметь несколько допустимых строк одного платежа: основной расчёт, комиссию, корректировку. Тогда ключ и правило сопоставления должны учитывать вид движения, а не считать все повторения идентификатора ошибкой.

Для сравнения нетто с брутто явно разложи сумму: например, 120 ₽ расчёта = 117 ₽ полученного нетто + 3 ₽ отдельно удержанной комиссии. Если в нашем учёте обе части есть, это согласованная история. Если комиссия пропущена, не добавляй допуск «плюс-минус три рубля»: он начнёт скрывать другие ошибки такого размера. Правило сопоставления должно объяснять разницу.

Аудит связывает денежное изменение с основанием

Для проверки недостаточно строки лога «платёж успешен». Нужны связи между бизнес-операцией, журнальной записью, внешним идентификатором, источником сообщения и последующей корректировкой. Сохраняй причину исправления, кто его инициировал и когда оно проведено. Воспроизводимая сверка также сохраняет исходный файл, его версию или отпечаток, выбранный период и версию правил сравнения.

Неизменяемый журнал — свойство модели записи. Защита от несанкционированной правки дополнительно требует прав доступа, контроля ручных корректировок, журналирования административных действий и проверяемых резервных копий. Если один и тот же процесс может бесследно переписать и историю, и её контрольную сумму, сама сумма не делает историю достоверной. Сроки хранения и ограничения доступа определяются требованиями системы и её юрисдикции; универсального числа лет здесь нет.

Границы модели важны: ledger отвечает за учёт, но не превращает сетевой таймаут в доказанный отказ и не принимает решение о спорном внешнем списании. Ошибку сверки сначала исследуют, затем проводят обоснованное исправление. Соседние темы Payment System и Idempotency разбирают распределённое выполнение; Payments — участников и стадии платёжных систем. План счетов и правила признания операций согласовывают с владельцами учёта, а не выводят из имён Java-классов.

  • Выбери, чьи книги ведёшь. Средства клиента для банка являются обязательством.
  • Операция связывает дебетовые и кредитовые строки на равную сумму; строк может быть больше двух.
  • Баланс операции, атомарная запись, защита от повтора и проверка доступного ловят разные ошибки.
  • Валюта, единица и точка округления входят в правило денежного расчёта.
  • Резерв уменьшает доступное до проведения. Исправление проведённого сохраняет исходную историю.
  • Сверка сравнивает отдельные движения независимых источников; аудит сохраняет их основания и связи.

На собеседовании

Как работают дебет, кредит и двойная запись?

Я сначала уточню, чьи книги ведём. Средства клиента — его актив, но обязательство банка перед ним. Дебет уменьшает такой клиентский остаток, кредит увеличивает. Для активного счёта стороны действуют наоборот.

При переводе 120 ₽ с комиссией 3 ₽ банк дебетует обязательство перед отправителем на 123 ₽ и кредитует обязательство перед получателем на 120 ₽ и доход на 3 ₽. Дебет и кредит равны, хотя строк три. Это проверяет сохранение учётного равенства, а правильность получателя и защиту от повтора проверяю отдельно.

  • Сумма всех положительных остатков не обязана сохраняться: комиссия перераспределяет обязательства в доход, а денежный актив при внутреннем переводе остаётся прежним.
  • Баланс каждой валюты проверяю отдельно. Для FX нужны согласованные валютные стороны и правило оценки, а не сложение разных единиц.
  • Клиентские счета могут быть частью операционного учёта, которую агрегируют в главную книгу. Соответствие двух уровней тоже требует контроля.
Повторный перевод снова сошёлся по дебету и кредиту. Почему это всё ещё ошибка?

Каждый из двух переводов отражён полностью, поэтому учётное равенство сохраняется. Но вместо одного бизнес-действия записаны два. Нужны устойчивый идентификатор операции и проверка содержания при повторе. Если повтор пришёл с новым идентификатором, равенство строк не поможет узнать его.

Как провести операцию безопасно и исправить ошибочную проводку?

Я проверю счета, валюты, суммы и равенство сторон, затем сохраню операцию, её строки и зависимые итоги одной транзакцией. Ключ повтора находится в той же устойчивой записи. Иначе после сбоя можно повторить уже сделанный денежный эффект.

Проведённую ошибку исправляю новой связанной записью. Для полного сторно она меняет стороны исходных строк, а исходную историю сохраняет. Возврат по бизнес-правилам может иметь другую сумму и комиссию, поэтому его не приравниваю к полному сторно.

  • Для ограничения расхода сериализую проверку доступного и запись. Уникальный ключ повтора не защищает от двух разных платежей по одному остатку.
  • Запрет повторного полного сторно привязываю к исходной операции. Два новых ключа корректировки иначе создадут два возврата.
  • Если средства получателя уже потрачены, проверяю правило задолженности и дальнейшего взыскания. Учётная обратимость записи не гарантирует возможность вернуть реальный платёж.

Как хранить деньги и чем доступный остаток отличается от учтённого?

Я храню сумму вместе с валютой: целые минимальные единицы или BigDecimal с явной точностью. Вход проверяю по контракту, расчёт округляю по тарифу. Для целых проверяю переполнение; двоичную арифметику double в денежное правило не переношу.

Учтённый остаток отражает проведённые движения. Активные резервы ограничивают новую трату, поэтому в простом кошельке вычитаются для получения доступного. Резерв 300 ₽ при остатке 1 000 ₽ оставляет 700 ₽ доступными. После окончательного списания 280 ₽ и снятия всего резерва доступны 720 ₽.

  • Округление по каждой операции и по пачке дают разные результаты. Сохраняю применённое правило и сумму, чтобы сверка повторяла именно этот расчёт.
  • При нескольких частичных проведениях храню оставшийся резерв и уникальность каждого проведения. Модель одного окончательного capture сюда не переносится без изменений.
  • Кредитный лимит и замороженные суммы требуют явной формулы доступного. Отрицательный остаток оценивается по разрешённому типу счёта и правилам продукта.
Резерв снят по таймауту. Можно ли поздний capture провести поверх его прежнего состояния?

Снятый резерв уже не удерживает средства, поэтому использовать его как действующее разрешение нельзя. Проверь текущее состояние и сопоставь внешнюю операцию: действительно ли деньги уже переместились, какое событие потерялось, какое правило применяется к позднему подтверждению. Простой локальный повтор capture отклоняется, но внешнее денежное событие остаётся предметом разбирательства и учёта.

Зачем сверка, если ledger уже сбалансирован, и что нужно для аудита?

Баланс ledger проверяет внутреннее равенство. Сверка сравнивает его с независимым источником: внешним банком, провайдером или другим уровнем учёта. Я согласую период, валюту, направление и состав суммы, затем сопоставлю отдельные движения. Совпавший итог ещё может скрывать пропущенную и лишнюю строки.

Расхождение сохраняю и исследую до исправления. Для аудита связываю платёж, проводку, внешнее движение и корректировку с её причиной и инициатором. Тогда можно восстановить, что произошло и на каком основании изменились средства.

  • Повтор файла и несколько видов строк одного платежа — разные ситуации. Ключ сопоставления должен отражать контракт источника.
  • Фиксирую полноту периода и версию правил сверки. Иначе повторный запуск на другом срезе нельзя честно сравнить с прежним результатом.
  • Контрольная сумма обнаруживает изменение только при доверенном хранении её основания. Права и административный след защищают журнал отдельно.
  • TigerBeetle: Financial Accounting — основа урока: перспектива владельца книг, типы счетов, дебет и кредит. Учебные Java-модели реализованы отдельно, TigerBeetle не запускается.
  • TigerBeetle: Two-Phase Transfers — разделение резерва и проведения, окончательное разрешение резерва.
  • TigerBeetle: Correcting Transfers — новые записи для исправления и сохранение первоначальной истории.
  • JDK 21: BigDecimal и Currency — конструкторы, точные преобразования, округление и минимальная единица валюты.
