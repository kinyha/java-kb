Spring: Bean Lifecycle

Созданный объект сначала получает зависимости и проходит подготовку, затем становится доступным клиенту. Конструктор — только начало этого пути. Если другой компонент получил ссылку слишком рано, он способен увидеть пустые поля или обойти ожидаемый перехват. Проследим состояние объекта от описания до готовности и штатного завершения.

Выполненный конструктор ещё не означает готовый Spring-объект

Gateway должен получить Clock и подготовить соединение перед первым платежом. Если обратиться к полю с @Autowired прямо в конструкторе, оно ещё пусто. Если вызвать метод сервиса из собственной инициализации, ожидаемая транзакция или другой перехват может ещё отсутствовать. Эти ситуации становятся понятными, когда разделяешь создание Java-объекта и его подготовку контейнером.

Конструктор создаёт исходный экземпляр. Затем Spring внедряет поля и вызывает методы внедрения, сообщает сведения контейнера, выполняет инициализацию и подключает обработчики. В конце фабрика выдаёт клиенту подготовленную ссылку. Иногда эта ссылка ведёт к прокси, а исходный объект остаётся за ним.

Зависимость конструктора уже доступна внутри него, потому что Spring получил её перед вызовом. Поля и сеттеры заполняются позже. Такой порядок позволяет объекту на этапе init использовать уже внедрённые зависимости и проверить целостность настройки.

При цикле зависимостей контейнер в некоторых режимах способен выдать ссылку раньше завершения этого пути. Поэтому «ссылка уже есть» и «объект закончил подготовку» — разные состояния. Сначала разберём обычный путь, затем его раннее ответвление.

Сначала расширения меняют описания, затем обрабатывают экземпляры

Предположим, для Gateway нужно задать способ прогрева из общей конфигурации. Это можно сделать в описании до создания объекта. BeanFactoryPostProcessor получает фабрику и меняет её метаданные. BeanDefinitionRegistryPostProcessor дополнительно умеет добавлять определения; его этап предшествует обычной обработке фабрики.

ConfigurationClassPostProcessor использует этот ранний этап, чтобы разобрать @Configuration, @Bean и импорты. После него общий реестр знает, какие объекты предстоит собрать. На этом уровне меняют способ создания и настройки, а не вызывают рабочие методы сервисов.

BeanPostProcessor работает уже с объектами. Его основные методы вызываются перед и после init; расширенные интерфейсы участвуют и в выборе конструктора, заполнении полей, подготовке метаданных, ранней ссылке и уничтожении. Поэтому внедрение @Autowired и вызов @PostConstruct тоже выполняются обработчиками.

Обработчики нужно создать раньше обычных компонентов. Если метод @Bean, возвращающий BFPP, зависит от экземпляра конфигурации, тот может понадобиться слишком рано. Для такого метода обычно используют static и точный возвращаемый тип. У BPP также следует избегать обычных сервисов в зависимостях: их ранняя сборка способна произойти до подключения всей цепочки обработчиков.

BFPP и BPP — два названия одного способа обработать бин.

BFPP меняет описания до сборки, BPP обрабатывает экземпляры в ходе сборки. Вызов getBean из BFPP начинает создание слишком рано и смешивает эти этапы.

Готовность появляется после внедрения и init, а не после new

Для обычного создаваемого бина порядок такой: конструктор → заполнение зависимостей → BeanNameAware, BeanClassLoaderAware и BeanFactoryAware → обработчики перед init → afterPropertiesSet → настроенный init-метод → обработчики после init. Дополнительные Aware-интерфейсы контекста обрабатываются его собственным BPP, поэтому все разновидности Aware нельзя считать одним отдельным вызовом фабрики.

@PostConstruct выполняется внутри обработки перед init, через CommonAnnotationBeanPostProcessor. Если одновременно заданы разные init-методы, сначала идёт @PostConstruct, затем InitializingBean.afterPropertiesSet и затем настроенный метод. Одинаковый метод, заданный несколькими способами, Spring старается вызывать один раз; смешивать три способа в реальном сервисе обычно незачем.

В LifecycleDemo.java все три способа намеренно разные, чтобы увидеть порядок. Trace добавлен вручную раньше обработчика аннотаций, поэтому его before init печатается перед postConstruct. Это условие опыта, а не обещание, что любой BPP всегда предшествует аннотации.

Полный пример LifecycleDemo.java, Java 21, Spring 7.0.9. 

cd examples/spring-core
./run.sh LifecycleDemo
import jakarta.annotation.PostConstruct;
import jakarta.annotation.PreDestroy;
import java.time.Clock;
import org.springframework.beans.factory.*;
import org.springframework.beans.factory.annotation.Autowired;
import org.springframework.beans.factory.config.BeanPostProcessor;
import org.springframework.context.annotation.AnnotationConfigApplicationContext;

public class LifecycleDemo {
    static class Gateway implements BeanNameAware, InitializingBean, DisposableBean {
        @Autowired Clock clock;
        boolean ready;
        Gateway() { System.out.println("constructor: clock=" + (clock != null)); }
        public void setBeanName(String name) {
            System.out.println("aware: " + name + ", clock=" + (clock != null));
        }
        @PostConstruct void annotatedInit() { System.out.println("postConstruct"); }
        public void afterPropertiesSet() { System.out.println("afterPropertiesSet"); }
        void warmup() { ready = true; System.out.println("warmup"); }
        @PreDestroy void annotatedDestroy() { System.out.println("preDestroy"); }
        public void destroy() { System.out.println("destroy"); }
        void disconnect() { System.out.println("disconnect"); }
    }
    static class Trace implements BeanPostProcessor {
        public Object postProcessBeforeInitialization(Object bean, String name) {
            if (bean instanceof Gateway) System.out.println("before init");
            return bean;
        }
        public Object postProcessAfterInitialization(Object bean, String name) {
            if (bean instanceof Gateway) System.out.println("after init");
            return bean; // Другой обработчик здесь мог бы вернуть прокси.
        }
    }
    public static void main(String[] args) {
        try (var ctx = new AnnotationConfigApplicationContext()) {
            ctx.registerBean("clock", Clock.class, Clock::systemUTC);
            ctx.registerBean("gateway", Gateway.class);
            ctx.addBeanFactoryPostProcessor(factory -> {
                var definition = factory.getBeanDefinition("gateway");
                definition.setInitMethodName("warmup");
                definition.setDestroyMethodName("disconnect");
                System.out.println("definitions changed"); // Объекта Gateway ещё нет.
            });
            // Добавлен вручную раньше обработчика аннотаций PostConstruct.
            ctx.getBeanFactory().addBeanPostProcessor(new Trace());
            ctx.refresh();
            System.out.println("usable: " + ctx.getBean(Gateway.class).ready);
        } // Закрытие вызывает три разных способа завершения Gateway.
    }
}

Методы init удобно используют для проверки конфигурации и подготовки внутреннего состояния. Обращение к собственному методу с @Transactional из @PostConstruct проходит внутри исходного объекта: обычный внешний путь через AOP-прокси ещё не используется. Для действий, которым нужна готовая инфраструктура приложения, есть этапы после создания singleton.

Цикл полей может дать ссылку на ещё недостроенный объект

При A(B) и B(A) фабрике нужно завершить один конструктор, чтобы вызвать другой. Ни одного экземпляра пока нет, и цикл останавливается с BeanCurrentlyInCreationException. Замена одного аргумента на provider откладывает получение только при условии, что getObject вызывается позже; немедленный вызов из того же конструктора восстанавливает цикл.

Для singleton с внедрением в поля или сеттеры экземпляр A уже существует до получения B. При разрешённых циклах Spring может сохранить возможность получить раннюю ссылку на A. B получает её, завершает свою подготовку, после чего фабрика возвращается к A. В этот промежуток B способен увидеть незаполненное состояние A.

Три структуры фабрики обслуживают этот путь. singletonObjects содержит готовые singleton; earlySingletonObjects — уже выданные ранние ссылки; singletonFactories — функции получения ранней ссылки. Последняя нужна, чтобы обработчик мог подготовить ранний прокси до выдачи. Это функция для существующего объекта, а не ещё один вызов его конструктора.

В демо B печатает A.b из собственного @PostConstruct. Регистрации классов, флаг разрешения циклов и оба вида внедрения показаны полностью. Для простого Framework-контейнера флаг разрешения циклов по умолчанию true; Boot задаёт spring.main.allow-circular-references=false. В опыте флаг указан явно для каждого варианта.

Полный пример CycleDemo.java, Java 21, Spring 7.0.9. 

cd examples/spring-core
./run.sh CycleDemo
import jakarta.annotation.PostConstruct;
import java.util.logging.*;
import org.springframework.beans.factory.annotation.Autowired;
import org.springframework.context.annotation.AnnotationConfigApplicationContext;

public class CycleDemo {
    static class ConstructorA {
        ConstructorA(ConstructorB b) {}
    }
    static class ConstructorB {
        ConstructorB(ConstructorA a) {}
    }
    static class FieldA { @Autowired FieldB b; }
    static class FieldB {
        @Autowired FieldA a;
        @PostConstruct void init() {
            System.out.println("B init sees A.b: " + a.b); // A ещё ожидает готовый B.
        }
    }
    static void run(String label, boolean allow, Class<?> a, Class<?> b) {
        System.out.println(label);
        try (var ctx = new AnnotationConfigApplicationContext()) {
            ctx.getDefaultListableBeanFactory().setAllowCircularReferences(allow);
            ctx.register(a, b);
            try {
                ctx.refresh();
                var first = ctx.getBean(FieldA.class);
                System.out.println("connected: " + (first.b.a == first));
            } catch (org.springframework.beans.factory.BeanCreationException ex) {
                Throwable cause = ex;
                while (cause.getCause() != null) cause = cause.getCause();
                System.out.println(cause.getClass().getSimpleName());
            }
        }
    }
    public static void main(String[] args) {
        Logger.getLogger("org.springframework").setLevel(Level.SEVERE);
        run("constructor cycle:", true, ConstructorA.class, ConstructorB.class);
        run("field cycle allowed:", true, FieldA.class, FieldB.class);
        run("field cycle forbidden:", false, FieldA.class, FieldB.class);
    }
}

Такое разрешение относится к подходящим singleton-циклам. Prototype не получает этот механизм кеширования. Для некоторых комбинаций прокси фабрика также обнаружит несовместимость ранней и окончательной ссылки. Практическое исправление — отделить общий компонент или изменить направление связи, чтобы готовность одного сервиса не требовала полусобранного другого.

Под капотом: как ранняя ссылка согласуется с прокси

В doCreateBean фабрика регистрирует функцию getEarlyBeanReference перед populateBean. SmartInstantiationAwareBeanPostProcessor может вернуть через неё ранний прокси. После initializeBean фабрика проверяет согласованность выданной ссылки с итоговым объектом. Если другому бину уже дали исходный объект, а поздний BPP заменил его неподходящей оболочкой, запуск может завершиться ошибкой вместо публикации двух разных представлений.

Запуск фоновой работы требует готовности всего нужного окружения

Gateway может проверить URL в init. А consumer, который начнёт принимать платежи, должен запускаться после подготовки его зависимостей. Блокировать init ожиданием задачи, которая сама просит ещё создаваемые бины, опасно: подготовка singleton может удерживать блокировку создания. Долгие внешние действия лучше отделить от готовности самого объекта.

SmartLifecycle позволяет задать isAutoStartup и фазу getPhase. При автоматическом запуске меньшие фазы стартуют раньше, при остановке большие завершаются раньше. Явные зависимости также учитываются и могут определить порядок сильнее номера фазы. Это позволяет сначала поднять инфраструктуру, затем начать принимать работу, а остановить их в обратной последовательности.

Для асинхронной остановки stop(Runnable callback) должен вызвать callback после фактического завершения работы. Иначе контейнер ждёт до ограниченного таймаута. Простой Lifecycle.start не равен проверке готовности приложения: компонент может запустить поток, которому ещё требуется время на подключение.

Отложенные бины могут оставаться несозданными после refresh. ContextRefreshedEvent также возможен у родителя и ребёнка; слушатель должен учитывать, какой контекст запущен. В Boot готовность приложения к работе дополнительно учитывает runners и события Boot. Эти уровни полезно различать при выборе места для миграций и запуска consumer.

При штатном закрытии сначала прекращают работу, затем освобождают ресурсы

Платёжный consumer должен прекратить принимать новые задания до закрытия соединения с банком. Lifecycle-stop даёт ранний сигнал остановки; затем контейнер уничтожает singleton. Зависимый сервис уничтожается раньше зависимости, которой он пользуется. Для обычных singleton этому помогают сведения графа зависимостей и @DependsOn.

Для трёх разных методов завершения порядок зеркалит способы настройки: @PreDestroy, DisposableBean.destroy, затем настроенный destroyMethod. Это видно в последних строках LifecycleDemo. Метод @Bean по умолчанию также может обнаружить public close или shutdown; если закрытием владеет другой компонент, такое автоматическое обнаружение можно отключить через destroyMethod="".

Prototype после выдачи клиенту автоматически этим путём не проходит — это разобрано в Bean Scopes. Для request/session время завершения задаёт соответствующая область. Контейнер закрывает ресурс по своей регистрации, а не потому, что JVM собирается удалить объект.

Штатный close или зарегистрированный shutdown hook дают возможность выполнить cleanup. Принудительное завершение процесса не оставляет такой возможности. Поэтому обработка платежей и фиксация состояния должны выдерживать падение в любой точке: callback завершения помогает аккуратной остановке, но не заменяет устойчивый протокол работы.

Диагностика начинается с этапа, на котором объект оказался

Null в конструкторе при внедрении в поле означает слишком раннее обращение. Ошибка циклического создания указывает на обратную зависимость во время сборки. Сообщение «not eligible for getting processed by all BeanPostProcessors» помогает найти компонент, созданный до подключения всей цепочки BPP. В каждом случае полезно выписать путь регистрации и момент первого getBean.

Падение refresh обычно приводит к уничтожению уже созданных подходящих singleton. Но внешний эффект init, например отправленный платёж или изменённый файл, автоматически не откатывается вместе с контекстом. Инициализация должна быть повторяемой, а существенные внешние действия — иметь собственное устойчивое состояние и понятную обработку повторного запуска.

Используй один способ инициализации для одной обязанности и один владелец завершения ресурса. Сложный callback, который ищет половину контекста и запускает бизнес-процесс, обычно смешивает сборку с работой приложения. Выделение запускаемого компонента делает порядок и остановку видимыми.

Следующая тема, AOP & Proxies, прослеживает, куда ведёт опубликованная ссылка и почему вызов собственного метода обходит перехват. Lifecycle объясняет, когда ссылка появляется; AOP — что случится при её использовании.

  • BFPP меняет метаданные, BPP обрабатывает объекты в процессе сборки.
  • Поле с Autowired заполняется после конструктора; init выполняется после внедрения.
  • PostConstruct — часть обработки перед init. После неё идут afterPropertiesSet и настроенный метод.
  • Ранняя ссылка разрешает некоторые singleton-циклы, но сохраняет риск полусобранного состояния.
  • Фоновый запуск и остановку удобно выражать через Lifecycle; принудительное падение требует отдельной устойчивости.

На собеседовании

Какой жизненный цикл у обычного Spring-бина?

После конструктора Spring внедряет поля и методы, выполняет подходящие Aware-вызовы, обработку перед init, методы инициализации и обработку после init. Затем клиент получает готовую ссылку, иногда на прокси. Поэтому зависимость конструктора доступна сразу, а поле с Autowired — позже.

Если настроены разные способы init, порядок такой: PostConstruct, afterPropertiesSet, настроенный init-метод. PostConstruct вызывается одним из BPP перед init, поэтому порядок конкретных обработчиков требует отдельного учёта.

  • BeanNameAware/BeanFactoryAware вызывает фабрика; дополнительные Aware контекста выполняет его обработчик.
  • Для ранней ссылки в цикле часть подготовки ещё не завершена. Существование ссылки само по себе не доказывает готовность.

Чем BPP отличается от BFPP и зачем static @Bean для инфраструктуры?

BFPP меняет описания до обычного создания объектов. BPP работает с экземплярами при создании: внедряет зависимости, вызывает аннотации и может вернуть прокси. Registry post-processor добавляет определения на ещё более раннем этапе.

Обработчики должны появиться первыми. Static Bean позволяет получить BFPP без преждевременного создания экземпляра конфигурации. Для BPP я также избегаю обычных сервисов в зависимостях.

  • Программно добавленные BPP применяются по порядку регистрации; Ordered у них сам по себе этот порядок не меняет.
  • Ранний getBean из инфраструктуры способен создать компонент до подключения всех обработчиков и лишить его части ожидаемого поведения.

Как Spring разрешает циклические зависимости и почему это опасно?

Цикл обязательных конструкторов не даёт создать первый экземпляр. Для некоторых singleton-циклов с полями или сеттерами фабрика может выдать уже созданный, но ещё неготовый объект. B закончит init, затем Spring вернётся к A.

Я предпочитаю изменить граф: вынести общее действие или зависимость. Включение разрешения циклов сохраняет риск раннего использования; в демо B видит пустое поле A во время своего init.

  • Готовые ссылки находятся в singletonObjects, ранние — в earlySingletonObjects, функции получения ранней ссылки — в singletonFactories.
  • Функция ранней ссылки позволяет подготовить прокси. Несогласованность ранней и окончательной оболочки способна остановить запуск.
  • Framework по умолчанию разрешает попытку таких циклов, Boot по умолчанию запрещает. Prototype не использует этот путь.

Когда использовать PostConstruct, SmartInitializingSingleton и SmartLifecycle?

PostConstruct подходит для подготовки самого объекта. После предварительной сборки singleton можно использовать SmartInitializingSingleton или событие refresh. Для фонового компонента с управляемой остановкой я выбираю SmartLifecycle.

Фаза задаёт относительный порядок start/stop: меньшее значение стартует раньше и останавливается позже. Асинхронный stop сообщает завершение через callback.

  • Зависимости учитываются дополнительно к фазам, а таймаут ограничивает ожидание остановки.
  • Refresh не создаёт все lazy-бины и не означает, что внешние соединения любого запущенного потока уже готовы.

Что происходит при закрытии контекста?

Контейнер сначала останавливает Lifecycle-компоненты, затем уничтожает singleton, учитывая их зависимости. Зависимый сервис должен завершиться раньше ресурса, которым он пользуется. Для разных методов порядок — PreDestroy, destroy интерфейса, настроенный destroyMethod.

Я разделяю аккуратную остановку и устойчивость к падению. При принудительном завершении процесса cleanup может не выполниться; существенное состояние должно выдерживать это независимо.

  • Prototype после выдачи автоматически не уничтожается: владелец — получивший его код.
  • Bean-метод может автоматически обнаружить close/shutdown. Нужно согласовать это с реальным владельцем ресурса.
