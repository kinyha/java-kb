Spring: Bean Scopes

Общий сервис может жить всё время работы приложения, а черновик нужен только одному платежу. Spring позволяет задать правила выдачи таких объектов, но ссылка в поле сохраняет полученный экземпляр. Для разного времени жизни важно выбрать и область бина, и способ его получения: напрямую, через provider или через прокси текущего запроса.

Черновик одного платежа опасно хранить в общем сервисе

PaymentService обслуживает сразу много HTTP-запросов. Если он сохраняет в поле черновик текущего платежа, запрос второго клиента способен перезаписать данные первого. Настройки банка удобно разделять между вызовами, а номер счёта и сумму конкретной операции — держать отдельно. Вопрос времени жизни начинается с того, кто пользуется состоянием одновременно.

Scope задаёт, как контейнер возвращает экземпляры одного описания бина. По умолчанию используется singleton: одна сохранённая ссылка для этого бина в конкретной фабрике. Два имени могут описывать два объекта одного класса; два самостоятельных контекста также имеют собственные экземпляры.

Поэтому singleton-сервис удобен для работы без состояния отдельного клиента. Зависимости и общая конфигурация находятся в полях, данные платежа — в аргументах и локальных переменных. При этом общий кеш или счётчик допустимы, если ты отдельно обеспечил конкурентный доступ. Область видимости определяет совместное использование, а правила работы потоков определяет сам класс.

Сессия тоже допускает параллельный доступ: браузер может отправить два запроса из разных вкладок. Даже request-объект можно передать в несколько задач вручную. Отдельный экземпляр уменьшает число разделяющих его клиентов, но синхронизация всё равно нужна там, где один объект реально используют несколько потоков.

Prototype создаётся на запрос фабрики, а поле хранит полученную ссылку

Кажется естественным пометить Draft как prototype и внедрить его в PaymentService. Но сервис создаётся один раз. В этот момент Spring создаёт один Draft и записывает ссылку в поле. Дальше каждый платёж читает это же поле. Вызов метода сервиса сам по себе снова к фабрике не обращается.

Новый prototype появляется при новом getBean или getObject у provider. Обычный доступ к полю сохраняет объект ровно так же, как любая ссылка Java. Схема показывает, где проходит граница между использованием существующего объекта и запросом нового.

Время фактической жизни зависит и от ссылок. Если singleton удерживает prototype, сборщик мусора видит его достижимым столько же, сколько сам singleton. Название scope не задаёт срок, после которого JVM удаляет объект. Оно описывает политику выдачи контейнера.

Prototype внутри singleton автоматически новый на каждый вызов сервиса.

Прямое внедрение выполняется при создании сервиса. Для нового объекта на каждую операцию сервис должен в этот момент запросить фабрику: например, через ObjectProvider.

Provider позволяет выбрать момент создания нового объекта

ObjectProvider<Draft> сохраняет возможность получить зависимость. Сервис вызывает getObject в начале платежа и использует полученный Draft до конца операции. Два вызова getObject для prototype дадут два черновика: если первый нужен для нескольких действий, удержи его в локальной переменной.

В демо ниже прямое поле и provider относятся к одному prototype-описанию. Счётчики различают создание, инициализацию и завершение. Полный ScopesDemo.java, Java 21, Spring 7.0.9; все причины вывода показаны на странице.

Полный пример ScopesDemo.java, Java 21, Spring 7.0.9. Ниже — фрагмент.

cd examples/spring-core
./run.sh ScopesDemo
import jakarta.annotation.PostConstruct;
      import jakarta.annotation.PreDestroy;
      import org.springframework.beans.factory.ObjectProvider;
      import org.springframework.context.annotation.*;
      
      public class ScopesDemo {
          static int created, initialized, destroyed;
          static class Draft {
              final int id = ++created;
              @PostConstruct void init() { initialized++; }
              @PreDestroy void destroy() { destroyed++; }
          }
          record Service(Draft fixed, ObjectProvider<Draft> fresh) {}
          @Configuration(proxyBeanMethods = false)
          static class Config {
              @Bean @Scope("prototype") Draft draft() { return new Draft(); }
              @Bean Service service(Draft draft, ObjectProvider<Draft> provider) {
                  return new Service(draft, provider); // Прямая ссылка выбирается один раз.
              }
          }
          public static void main(String[] args) {
              try (var ctx = new AnnotationConfigApplicationContext(Config.class)) {
                  Service s = ctx.getBean(Service.class);
                  System.out.println("fixed: " + s.fixed().id + " " + s.fixed().id);
                  Draft first = s.fresh().getObject(); // Новый запрос к фабрике.
                  Draft second = s.fresh().getObject();
                  System.out.println("provider: " + first.id + " " + second.id);
                  System.out.println("initialized: " + initialized);
              } // Закрытие контекста не уничтожает выданные prototype.
              System.out.println("destroyed after close: " + destroyed);
          }
      }
fixed: 1 1
provider: 2 3
initialized: 3
destroyed after close: 0

ObjectFactory предоставляет основной getObject, а ObjectProvider добавляет способы получить необязательную зависимость и группу. При singleton оба используют сохранённый бин. Для выбора класса объекта обычная фабрика Java часто проще: например, черновик платежа можно создавать напрямую, передавая данные конструктору, а Spring оставить сборку самих сервисов.

Когда встречается @Lookup

@Lookup позволяет Spring переопределить метод получения зависимости в созданном подклассе. Класс и метод должны допускать переопределение. Такой подход работает, когда экземпляр создаёт контейнер; для объекта, возвращённого методом @Bean, Spring не создаёт нужный подкласс автоматически. Provider делает момент получения видимым в коде и обычно проще для тестирования.

Прокси с prototype устроен иначе, чем локально полученный объект: каждый вызов его метода может создать новый целевой экземпляр. Если сначала вызвать draft.setAmount, затем draft.send через такой прокси, действия могут попасть в два разных Draft. Для одной составной операции удобнее получить конкретный экземпляр один раз.

Прокси хранится в сервисе, а объект выбирается из текущего запроса

Для данных, общих в пределах одного HTTP-запроса, подходит request scope. Singleton-сервис живёт дольше запроса, поэтому прямую ссылку на единственный request-объект ему дать нельзя при обычном старте. Вместо неё Spring передаёт долгоживущий прокси. Когда сервис вызывает его метод, прокси получает реальный Draft из текущего запроса.

@RequestScope по умолчанию включает прокси на основе класса. Целевой класс и перехватываемые методы должны допускать такой перехват; состояние читают через методы целевого объекта. Прямое чтение поля прокси не выполняет поиск текущего Draft. Для интерфейсного варианта можно указать ScopedProxyMode.INTERFACES.

В Servlet-приложении DispatcherServlet, RequestContextFilter или RequestContextListener связывает запрос с обслуживающим потоком. RequestScope использует эту информацию. Новый поток из executor её автоматически не получает. Вызов прокси в фоновой задаче способен закончиться ScopeNotActiveException даже при том, что исходный HTTP-запрос ещё выполняется.

Демо использует MockHttpServletRequest из spring-test: запрос привязывается явно, но сама область видимости и прокси работают в Spring. Полный файл включает создание веб-контекста и все условия опыта. HTTP-сервер здесь не требуется.

Полный пример RequestScopeDemo.java, Java 21, Spring 7.0.9. 

cd examples/spring-core
./run.sh RequestScopeDemo
import org.springframework.context.annotation.*;
      import org.springframework.mock.web.MockHttpServletRequest;
      import org.springframework.mock.web.MockServletContext;
      import org.springframework.web.context.annotation.RequestScope;
      import org.springframework.web.context.request.*;
      import org.springframework.web.context.support.AnnotationConfigWebApplicationContext;
      
      public class RequestScopeDemo {
          public static class Draft {
              static int created;
              final int id = ++created;
              public int id() { return id; } // Читаем поле через метод реального объекта.
          }
          record Service(Draft draft) {
              int currentId() { return draft.id(); }
          }
          @Configuration(proxyBeanMethods = false)
          static class Config {
              @Bean @RequestScope Draft draft() { return new Draft(); }
              @Bean Service service(Draft draft) {
                  return new Service(draft); // В singleton передаётся долгоживущий прокси.
              }
          }
          public static void main(String[] args) {
              try (var ctx = new AnnotationConfigWebApplicationContext()) {
                  ctx.setServletContext(new MockServletContext());
                  ctx.register(Config.class);
                  ctx.refresh(); // Реального HTTP-запроса пока нет, сервис уже создан.
                  var s = ctx.getBean(Service.class);
                  for (int request = 1; request <= 2; request++) {
                      var attrs = new ServletRequestAttributes(new MockHttpServletRequest());
                      RequestContextHolder.setRequestAttributes(attrs);
                      try {
                          System.out.println("request " + request + ": " +
                              s.currentId() + " " + s.currentId());
                      } finally {
                          attrs.requestCompleted(); // Завершение времени жизни запроса.
                          RequestContextHolder.resetRequestAttributes();
                      }
                  }
                  try { s.currentId(); } // Получение target требует активного запроса.
                  catch (org.springframework.beans.factory.support.ScopeNotActiveException ex) {
                      System.out.println("outside request: " + ex.getClass().getSimpleName());
                  }
              }
          }
      }
request 1: 1 1
request 2: 2 2
outside request: ScopeNotActiveException

Session scope ищет объект в сессии, application — в ServletContext. Последняя может объединять несколько Spring-контекстов одного веб-приложения, тогда как singleton относится к одной фабрике. WebSocket scope в Spring относится к STOMP-сессии. Для этих областей нужна соответствующая инфраструктура; обычный AnnotationConfigApplicationContext знает стандартные singleton и prototype, а веб-области регистрируются веб-контекстом.

Клиент prototype отвечает за освобождение его ресурсов

При создании prototype Spring внедряет зависимости и выполняет инициализацию, в том числе @PostConstruct. После выдачи он перестаёт учитывать каждый экземпляр для автоматического уничтожения. Поэтому закрытие контекста в первом демо оставляет счётчик @PreDestroy равным нулю, хотя инициализированы все три объекта.

Если prototype держит файл, соединение или временный буфер с явным освобождением, определи владельца. Получивший объект код может закрыть его через AutoCloseable и try-with-resources. Для вызова настроенных Spring-методов уничтожения существует фабричный destroyBean, но приложение должно знать, какой экземпляр и когда ему передать. Вызов GC ресурсный протокол не заменяет.

Для singleton контейнер сохраняет регистрацию уничтожения и вызывает её при штатном закрытии. Request scope привязывает завершение к концу запроса, session — к завершению сессии. Это срок управления контейнера; Java-объект может оставаться в памяти, если приложение сохранило ссылку, но продолжать пользоваться закрытым ресурсом уже нельзя.

Отдельный список всех prototype ради будущего cleanup тоже требует осторожности: такой список удержит объекты и может расти бесконечно. Лучше выразить владение на уровне одной операции. Подробный порядок методов инициализации и уничтожения разобран в Bean Lifecycle.

Время жизни выбирай по состоянию, которое действительно нужно хранить

Начинай с сервиса без состояния клиента и явных параметров операции. Если нужно получить подготовленный Spring объект для каждой операции, добавь provider и локальную ссылку. Если данные должны разделять компоненты одного HTTP-запроса, request scope выражает это время жизни. Каждый вариант должен отвечать на вопрос: кто владеет состоянием и когда перестаёт им пользоваться?

Scope удобен, пока граница исполнения совпадает с границей жизни объекта. Для фоновых задач лучше передать неизменяемый снимок нужных данных — идентификатор клиента, язык, номер платежа. Сохранение request-прокси не сохраняет исходный запрос: при более позднем вызове он ищет объект из контекста того момента.

В распределённом backend session-объект одного процесса ещё не является общим состоянием всех узлов. Для устойчивого состояния заказа или платежа нужен явный источник данных и протокол изменения. Scope регулирует локальные объекты приложения, а хранение данных и конкурентные обновления решаются на другом уровне.

При диагностике выпиши три вещи: область бина, место получения ссылки и место вызова. Это отличает prototype, сохранённый в singleton, от provider, вызываемого на операцию, и от request-прокси, вызванного в чужом потоке. Аннотация одна, а пути использования различаются.

  • Singleton — общий бин одной фабрики; состояние клиента лучше держать вне его полей.
  • Prototype новый на запрос создания, а не на каждый вызов использующего его сервиса.
  • Provider делает момент получения явным; один экземпляр на операцию сохраняют локально.
  • Request-прокси выбирает target из текущего запроса. Фоновому потоку данные передают отдельно.
  • Инициализацию prototype выполняет Spring, освобождением ресурсов после выдачи занимается клиент.

На собеседовании

Что означает singleton в Spring и делает ли он объект потокобезопасным?

Singleton — одна сохранённая ссылка на бин в конкретной фабрике. Один класс может иметь несколько таких бинов под разными именами. Я учитываю, что общий сервис вызывают параллельно, и держу данные отдельных платежей в аргументах и локальных переменных.

Если в общем объекте есть изменяемый кеш или счётчик, я отдельно выбираю безопасный способ доступа. Scope определяет, кто получает один экземпляр; конкурентность определяется кодом объекта.

  • Session scope также допускает одновременные запросы одной сессии.
  • Application scope привязан к ServletContext и может объединять несколько Spring-контекстов веб-приложения.

Что получится при внедрении prototype в singleton?

При создании singleton Spring один раз создаст prototype и передаст ссылку. Она останется в поле между вызовами. Если нужен новый объект на каждый платёж, я получаю его через provider в начале операции.

Полученный экземпляр сохраняю локально на всю операцию. Повторный getObject для prototype означает уже новый объект.

  • Долгоживущая ссылка может удерживать prototype в памяти до уничтожения сервиса.
  • Prototype-прокси способен получать новый target на каждый вызов метода; последовательность set и execute тогда попадёт в разные объекты.

Как внедрить request-бин в singleton и что будет в фоне?

Я передаю singleton-сервису прокси request-бина. Прокси живёт вместе с сервисом, а метод направляет вызов в объект текущего запроса. Внутри запроса это один target, в следующем — другой.

При переносе работы в executor я передаю нужные данные явно. Сам новый поток не получает привязку HTTP-запроса, поэтому обращение через прокси там может упасть.

  • RequestScope по умолчанию использует прокси класса; final-методы мешают перехвату, а чтение полей обходит его.
  • Сохранённый прокси не является снимком данных предыдущего запроса.

Кто уничтожает prototype и когда нужен @Lookup?

Spring создаёт и подготавливает prototype, затем отдаёт клиенту. Автоматический destroy для каждого выданного экземпляра при закрытии контекста не выполняется. Я определяю владельца ресурса и закрываю объект после операции.

Для повторного получения мне обычно достаточно ObjectProvider. Lookup позволяет контейнеру переопределить метод получения, но этот скрытый механизм сложнее наблюдать и тестировать.

  • Lookup требует подкласса и переопределяемого метода; для экземпляра, возвращённого @Bean, такой путь не применяется.
  • Чтобы вызвать Spring destruction callbacks вручную, нужно передать конкретный экземпляр подходящему destroyBean; простой выход из метода этого не делает.
