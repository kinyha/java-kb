BigDecimal & Money

Сумма счёта зависит от того, какие данные пришли и когда их округлили. BigDecimal точно хранит конечную десятичную дробь, но не выбирает валюту, допустимую точность и правила расчёта. Для денег отдельно определяют равенство сумм, границу округления и судьбу остатка при распределении. Тогда результат можно объяснить и воспроизвести, а не исправлять потерянные центы форматированием.

Точные десятичные числа не гарантируют одинаковый итог счёта

В счёте три расчётные строки по 0.015 EUR. Один сервис округляет каждую строку до двух знаков с HALF_EVEN и суммирует: 0.06. Другой складывает исходные значения и округляет итог: 0.04. В обоих случаях нет double и нет двоичной погрешности. Сервисы реализуют разные правила, хотя оба разработчика сказали «используем BigDecimal».

В RoundingDemo.java исходные строки создаются из текста. Каждая 0.015 находится ровно посередине между 0.01 и 0.02; HALF_EVEN выбирает 0.02, где последняя сохраняемая цифра чётная. Но сумма 0.045 находится между 0.04 и 0.05, и тот же режим выбирает 0.04. Округление не распределяется по сложению.

// Фрагмент RoundingDemo.java; JDK 21 без зависимостей
List<BigDecimal> lines = List.of(
        new BigDecimal("0.015"), new BigDecimal("0.015"), new BigDecimal("0.015"));
BigDecimal lineFirst = lines.stream()
        .map(x -> x.setScale(2, RoundingMode.HALF_EVEN)) // округление ДО сложения
        .reduce(BigDecimal.ZERO, BigDecimal::add);
BigDecimal exactTotal = lines.stream().reduce(BigDecimal.ZERO, BigDecimal::add);
BigDecimal totalFirst = exactTotal.setScale(2, RoundingMode.HALF_EVEN); // ПОСЛЕ
System.out.println("line first=" + lineFirst + ", exact total=" + exactTotal
        + ", total first=" + totalFirst);
line first=0.06, exact total=0.045, total first=0.04

Правило «округлять как можно позже» полезно для промежуточных вычислений, но не отменяет контракт отдельных строк, налогов или расчёта с контрагентом. Если строка сама является окончательно оплачиваемой суммой, её граница может требовать округления раньше. Зафиксируй в модели, что считается исходной расчётной величиной, что — денежной суммой к проведению и какой результат должны видеть все участники.

Точность начинается при чтении исходного значения

Double хранит двоичную дробь с ограниченным числом битов. Десятичная 0.1 не имеет конечного представления в этой системе, поэтому сохраняется ближайшее приближение. BigDecimal хранит конечную десятичную дробь точно, но передача ему уже вычисленного double не возвращает потерянные исходные цифры. Подробный разбор битов находится в Numbers & Text.

Конструктор BigDecimal(double) точно переносит значение именно двоичного double. Поэтому длинный хвост — не ошибка десятичного сложения, а видимое приближение входа. ValueOf(double) идёт через каноническую строку Double.toString и для литерала 0.1 выглядит ожидаемо. Но для результата 0.1 + 0.2 он честно перенесёт 0.30000000000000004.

// Фрагмент InputDemo.java; java examples/bigdecimal/InputDemo.java
System.out.println("double sum=" + (0.1 + 0.2));
System.out.println("text sum=" + new BigDecimal("0.1").add(new BigDecimal("0.2")));
System.out.println("double constructor=" + new BigDecimal(0.1));
System.out.println("valueOf literal=" + BigDecimal.valueOf(0.1));
System.out.println("valueOf sum=" + BigDecimal.valueOf(0.1 + 0.2));
System.out.println("minor units=" + BigDecimal.valueOf(1234, 2)); // 1234 × 10^-2

Если источник — десятичный текст, разбирай его сразу как BigDecimal. Если источник — целые минимальные единицы, задавай их вместе с scale. Конструктор из double нужен, когда важен именно точный десятичный эквивалент двоичного значения; для денежного ввода это обычно другой контракт. ValueOf — удобная конверсия существующего double, а не способ исправить предыдущую арифметику.

В отличие от double, BigDecimal не имеет NaN, infinities и отдельного отрицательного нуля. InputDemo подтверждает, что valueOf(Double.NaN) бросает NumberFormatException. Деление на ноль бросит ArithmeticException. Используй отдельную доменную модель отсутствующей суммы или ошибки расчёта, а не специальные числовые значения и не случайный null в цепочке методов.

Scale задаёт степень десяти, precision — количество цифр коэффициента

Логическое представление — unscaled integer × 10−scale. У 12.340 коэффициент 12340, scale 3, precision 5. Последний ноль не меняет числовую величину, но входит в представление. У 0.00120 precision равен 3: ведущие нули дробной записи не становятся цифрами коэффициента. У нулевого коэффициента precision равен 1.

Scale может быть отрицательным. После stripTrailingZeros число 1200 представлено как 12 × 10², то есть scale −2, и toString печатает 1.2E+3. Метод удаляет десятичные нули коэффициента с изменением scale; это не настройка вывода «без лишних нулей». ToPlainString даёт 1200 без экспоненты, но не сохраняет прежний отрицательный scale при обратном чтении строки.

// Фрагмент RepresentationDemo.java; describe печатает свойства аргумента
BigDecimal price = new BigDecimal("12.340");
describe("price", price);
describe("tiny", new BigDecimal("0.00120"));
describe("stripped", new BigDecimal("1200").stripTrailingZeros());
System.out.println("plain=" + new BigDecimal("1200").stripTrailingZeros().toPlainString());
price.setScale(2); // результат проигнорирован, исходный BigDecimal не меняется
System.out.println("unchanged=" + price);
System.out.println("sum=" + price.add(new BigDecimal("0.66")));
System.out.println("product=" + price.multiply(new BigDecimal("2.0")));

Методы возвращают результат; слово set в setScale не означает мутацию. Сохраняй возвращённую ссылку. Точное сложение и вычитание используют максимум scales, потому что нужно привести коэффициенты к общей степени десяти. Точное умножение складывает scales: 3 + 1 = 4. Эти правила объясняют нули в 13.000 и 24.6800; они не задают денежный scale результата автоматически.

Под капотом: логический коэффициент не всегда отдельный BigInteger

В OpenJDK 21 BigDecimal использует compact long для подходящих коэффициентов и BigInteger для больших. Это оптимизация реализации, а не ограничение API до long. Arbitrary precision означает, что коэффициент может расти, но память и время конечны; scale остаётся 32-битным int, и его переполнение может дать ArithmeticException. Ограничивай длину входа, величину exponent/scale и допустимую precision до дорогих операций и toPlainString. Строка с большим положительным exponent способна превратить короткую запись в огромный текст.

Числовое равенство и равенство представлений дают разные ключи

CompareTo сравнивает величины: 7.0 и 7.00 дадут ноль. Equals требует одинаковые величину и scale: это два разных представления. HashCode согласован с equals и учитывает scale. Поэтому сравнение с порогом обычно пишут как amount.compareTo(limit) >= 0, а не как комбинацию equals и проверки «больше».

HashSet опирается на equals/hashCode, TreeSet с natural order — на compareTo. Переход между ними изменит дедупликацию сумм: у первого будет два элемента, у второго один. Это не исправление одного типа коллекции другим, а изменение выбранного отношения равенства. Денежный ключ должен также учитывать валюту и смысл идентичности; одинаковая сумма не делает два платежа одним платежом.

// Фрагмент RepresentationDemo.java
BigDecimal a = new BigDecimal("7.0"), b = new BigDecimal("7.00");
System.out.println("equals=" + a.equals(b) + ", compareTo=" + a.compareTo(b));
System.out.println("hash set=" + new HashSet<>(List.of(a, b)).size());
System.out.println("tree set=" + new TreeSet<>(List.of(a, b)).size());
// Этот overload divide берёт scale делимого: представление меняет операцию
System.out.println("scale 1 division=" + a.divide(BigDecimal.valueOf(4), RoundingMode.HALF_EVEN));
System.out.println("scale 2 division=" + b.divide(BigDecimal.valueOf(4), RoundingMode.HALF_EVEN));
equals=false, compareTo=0
hash set=2
tree set=1
scale 1 division=1.8
scale 2 division=1.75

Scale участвует в контракте не только ради печати. В показанном overload деление 7.0 сохраняет один дробный знак, а 7.00 — два. Поэтому численно равные объекты не всегда взаимозаменяемы для всех операций. Для предсказуемого расчёта задавай нужный result scale явно, а не позволяй точности входного представления выбирать его за тебя.

Если в модели settled money scale фиксирован валютой, нормализация в конструкторе позволяет оставить обычный equals, включая generated equals record. Используй UNNECESSARY, чтобы не скрыть недопустимую дробь. StripTrailingZeros подходит другой модели числового значения, но может дать отрицательный scale и экспоненциальную запись. Нормализацию определяют один раз на границе; менять только equals без согласованного hashCode нельзя.

Scale, MathContext и RoundingMode ограничивают результат по-разному

SetScale(2, mode) требует два знака после точки. Round(new MathContext(4, mode)) оставляет четыре значащие цифры всего числа: у 123.456 получится 123.5, а не 123.46. MathContext передаётся конкретной операции; это не глобальная настройка, которую BigDecimal запомнит для всех будущих вычислений. Precision 0 означает точную арифметику, а не «округлить до нуля знаков».

SetScale(int) без режима требует точного изменения масштаба. Удалить ноль у 12.340 можно, а отбросить ненулевую цифру у 123.456 нельзя: будет ArithmeticException. Если нужно именно округление, режим задают явно. Поэтому слово scale само по себе ещё не говорит, разрешена ли потеря информации.

Точное деление возможно, только если результат имеет конечную десятичную запись. У сокращённой дроби в знаменателе должны остаться только множители 2 и 5: 1/8 заканчивается, 1/3 — нет. Без выбранной точности последнее бросает ArithmeticException. MathContext.UNLIMITED не может сохранить бесконечное число цифр и тоже отвергает 1/3.

// Фрагмент RoundingDemo.java; все причины результата находятся здесь
BigDecimal one = BigDecimal.ONE, three = BigDecimal.valueOf(3);
try { one.divide(three); }
catch (ArithmeticException expected) { System.out.println("exact 1/3 rejected"); }
System.out.println("exact 1/8=" + one.divide(BigDecimal.valueOf(8)));
System.out.println("scaled 1/3=" + one.divide(three, 2, RoundingMode.HALF_EVEN));
System.out.println("scale inherited=" + one.divide(three, RoundingMode.HALF_EVEN));
BigDecimal x = new BigDecimal("123.456");
try { x.setScale(2); }
catch (ArithmeticException expected) { System.out.println("scale without mode rejected"); }
System.out.println("scale 2=" + x.setScale(2, RoundingMode.HALF_EVEN));
System.out.println("precision 4=" + x.round(new MathContext(4, RoundingMode.HALF_EVEN)));
try { one.divide(three, MathContext.UNLIMITED); }
catch (ArithmeticException expected) { System.out.println("unlimited 1/3 rejected"); }

Режим определяет сторону округления и обработку точной середины. UP и DOWN работают относительно нуля, CEILING и FLOOR — относительно направления числовой оси. Для отрицательных сумм это разные решения. Таблица ниже получена RoundingDemo для setScale(2) у 1.225 и −1.225; UNNECESSARY требует точного результата и здесь бросает исключение.

HALF_EVEN не означает «всегда вниз»: для 1.235 этот опыт даёт 1.24. Он снижает направленное смещение на сериях подходящих значений, но не является универсальным правилом денег. Выбери режим по контракту операции. Также нельзя считать безопасным повторное округление: 1.2451 сразу до двух знаков даёт 1.25, а через три знака превращается в точную середину 1.245 и затем в 1.24.

BigDecimal source = new BigDecimal("1.2451");
System.out.println("once=" + source.setScale(2, RoundingMode.HALF_EVEN)

Под капотом: округлённое сложение теряет ассоциативность
// Фрагмент RoundingDemo.java; precision 3 действует в каждой add
MathContext mc = new MathContext(3, RoundingMode.HALF_UP);
BigDecimal a = new BigDecimal("1000"), b = BigDecimal.ONE, c = new BigDecimal("-1000");
System.out.println("left=" + a.add(b, mc).add(c, mc).toPlainString()
        + ", right=" + a.add(b.add(c, mc), mc).toPlainString());
left=0, right=1

Слева 1001 сначала округлился до 1000, потеряв единицу. Справа −999 точно помещается в три цифры, затем сложение с 1000 даёт 1. Такой accumulator не ассоциативен: изменение дерева группировки в parallel reduce способно изменить результат. Точное BigDecimal::add не имеет этой числовой потери; границу округления всё равно задают отдельно. Требования reduce разобраны в Streams и Parallel Streams.

Денежная модель хранит валюту, проверяет единицы и сохраняет остатки

BigDecimal сам по себе — число. Для денежной суммы нужны валюта и правила допустимого значения. В MoneyDemo.java Money означает уже проводимую сумму в стандартных минимальных единицах валюты, а не курс или промежуточную цену с дробными центами. Конструктор приводит representation к валютному scale без потери цифр; plus запрещает смешать EUR с USD.

// Фрагмент MoneyDemo.java; отдельная модель settled amount
record Money(BigDecimal amount, Currency currency) {
    Money {
        Objects.requireNonNull(currency);
        Objects.requireNonNull(amount);
        int digits = currency.getDefaultFractionDigits();
        if (digits < 0) throw new IllegalArgumentException("no supported minor unit");
        amount = amount.setScale(digits, RoundingMode.UNNECESSARY); // проверка, не тихое округление
    }
    Money plus(Money other) {
        if (!currency.equals(other.currency)) throw new IllegalArgumentException("currency mismatch");
        return new Money(amount.add(other.amount), currency);
    }
    long minorUnits() {
        return amount.movePointRight(currency.getDefaultFractionDigits()).longValueExact();
    }
}
Currency eur = Currency.getInstance("EUR");
Money a = new Money(new BigDecimal("7.0"), eur);
Money b = new Money(new BigDecimal("7.00"), eur);
System.out.println("money equal=" + a.equals(b) + ", amount=" + a.amount()
        + ", minor=" + a.minorUnits());
money equal=true, amount=7.00, minor=700

На проверенном JDK Currency сообщает EUR → 2, JPY → 0, KWD → 3 дробных знака. Поэтому «всегда два знака» не подходит всем валютам. Эти метаданные не описывают округление наличных платежей, допустимую точность курса или правила конкретного провайдера. Для таких контрактов нужны отдельные настройки; pseudo-currency с digits −1 наша модель явно отклоняет. Отрицательные суммы допустимы здесь для возвратов, а запрет отрицательного платежа задаёт конкретная операция.

На границах проверь единицы и сохранение общей суммы

BigDecimal в БД обычно соответствует точному NUMERIC/DECIMAL с явно выбранными precision и scale; целые minor units — целому столбцу плюс коду валюты и соглашению об единицах. Ограничения хранения проверяют до записи. Например, PostgreSQL 18 округляет вход до объявленного scale, а не обязательно отвергает лишнюю дробь; правила его ties могут отличаться от HALF_EVEN приложения. Это граница договора с хранилищем, описанная в документации БД, а не запущенный SQL-опыт этой страницы.

Long minor units удобен для целого учёта, но не устраняет переполнение и остаток деления. LongValue молча отбрасывает дробь и может терять старшие биты при выходе за диапазон; longValueExact отвергает обе потери. MoneyDemo проверяет отказ для лишней дроби 7.001 EUR, смешения валют и конверсии 92233720368547758.08 EUR в long. Для сложения двух long используй Math.addExact, если переполнение должно быть ошибкой.

// Фрагмент MoneyDemo.java; модель Money и eur объявлены в предыдущем шаге
try { new Money(new BigDecimal("7.001"), eur); }
catch (ArithmeticException expected) { System.out.println("extra fraction rejected"); }
try { a.plus(new Money(new BigDecimal("7.00"), Currency.getInstance("USD"))); }
catch (IllegalArgumentException expected) { System.out.println("currency mismatch rejected"); }
try { new Money(new BigDecimal("92233720368547758.08"), eur).minorUnits(); }
catch (ArithmeticException expected) { System.out.println("long overflow rejected"); }
try { Math.addExact(Long.MAX_VALUE, 1); }
catch (ArithmeticException expected) { System.out.println("minor unit addition overflow rejected"); }

Деление 1 EUR между тремя участниками не может дать три одинаковые суммы в целых центах. Округлить каждую долю до 0.33 — значит потерять цент. В нашем контракте остаточные единицы получают первые участники стабильного порядка: [34, 33, 33]. Это правило распределения, которое надо сделать явным, а не спрятать в выбранном RoundingMode.

// Фрагмент MoneyDemo.java; политика: неотрицательная сумма, count > 0
static long[] allocateMinorUnits(long total, int count) {
    if (total < 0 || count <= 0) throw new IllegalArgumentException("invalid allocation");
    long quotient = total / count, remainder = total % count;
    long[] shares = new long[count];
    for (int i = 0; i < count; i++)
        shares[i] = quotient + (i < remainder ? 1 : 0); // остаток распределяем, не теряем
    return shares;
}
long[] shares = allocateMinorUnits(100, 3);
System.out.println("shares=" + Arrays.toString(shares) + ", sum=" + Arrays.stream(shares).sum());
System.out.println("truncating conversion=" + new BigDecimal("1.239")
        .movePointRight(2).longValue()); // опасная альтернатива Exact
shares=[34, 33, 33], sum=100
truncating conversion=123

Проверка распределения в полном файле сравнивает сумму через независимый BigInteger, требует неотрицательных долей и разницы максимум в одну единицу. Пройдены ноль, сумма меньше числа участников, Long.MAX_VALUE и 100 случайных случаев. Для пропорциональных весов, отрицательных распределений или другой справедливости нужен другой согласованный алгоритм; равные доли не универсальны.

На границе JSON получатель тоже должен сохранять точность: маршрут через double снова уничтожит гарантию. Выбор number или string закрепляют в схеме API; его round trip разобран в Serialization & Schemas. Отображение суммы с локальными разделителями — отдельная операция, которая не должна становиться исходными данными расчёта. Проверяй весь путь: ввод → вычисление → округление → хранение → другой потребитель.

  • BigDecimal сохраняет точное десятичное значение, если точным был вход; valueOf не исправляет double-арифметику.
  • Представление — coefficient × 10−scale; precision считает цифры coefficient, scale может быть отрицательным.
  • CompareTo сравнивает величину, equals/hashCode — величину вместе со scale; коллекции могут дедуплицировать по-разному.
  • SetScale ограничивает дробные знаки, MathContext — значащие цифры. Деление без конечного результата требует решения о точности.
  • Режим и место округления — части контракта; повторное округление и разные группировки могут изменить итог.
  • Деньги включают валюту, единицы, пределы и правила остатков. Exact-конверсии выявляют потерю данных.

На собеседовании

Почему деньги не считают в double и как правильно создать BigDecimal?

Double хранит двоичную дробь ограниченной точности, поэтому десятичная 0.1 уже приближённая. Для точных денежных данных я беру BigDecimal из исходной строки или из целых минимальных единиц с заданным scale. Тогда десятичные сложение и умножение сохраняют точный результат, пока я сам не выберу округление.

New BigDecimal(0.1) точно переносит приближённый double и показывает длинный хвост. ValueOf(0.1) идёт через Double.toString и даёт 0.1, но valueOf(0.1 + 0.2) оставляет 0.30000000000000004. Поэтому точность нужна от самого ввода, а не только у последней переменной.

  • Конструктор из double корректен для точного переноса его двоичного значения; это другой контракт, чем исходная денежная десятичная строка.
  • BigDecimal не содержит NaN и infinity. Отсутствие значения и ошибка вычисления должны быть явными вариантами модели.
  • Нужно проверить сериализацию и клиент: промежуточный double в другом слое снова теряет цифры.

Чем отличаются scale, precision и MathContext?

BigDecimal — целый коэффициент, умноженный на десять в степени минус scale. У 12.340 unscaled равен 12340, scale равен 3, precision — 5 цифр коэффициента. Scale может быть отрицательным: 1200 после удаления нулей имеет коэффициент 12 и scale −2.

SetScale(2, HALF_EVEN) задаёт два дробных знака с явным округлением, а MathContext с precision 4 и тем же режимом задаёт четыре значащие цифры результата операции. Поэтому 123.456 станет соответственно 123.46 или 123.5. BigDecimal immutable: я сохраняю возвращённое значение, а не ожидаю, что setScale изменит исходный объект.

  • SetScale(int) без режима бросает ArithmeticException, если изменение scale требует округления.
  • Precision 0 в MathContext означает точность без округления; бесконечное десятичное деление всё равно невозможно.
  • Точные add/subtract берут максимальный scale, multiply складывает scales; денежный scale не следует из этих операций автоматически.
  • Compact long — оптимизация OpenJDK. Размер коэффициента, exponent и вывод toPlainString требуют лимитов входа, несмотря на arbitrary precision.

Почему equals и compareTo расходятся и что будет в HashSet и TreeSet?

Equals сравнивает числовое значение и scale, а compareTo — только величину. Поэтому 7.0 и 7.00 не equals, но compareTo даёт ноль. HashCode учитывает scale, чтобы поддерживать контракт equals. Для числового порога я использую compareTo.

HashSet сохранит оба представления, TreeSet с natural order оставит одно. Я сначала выбираю отношение равенства модели. Если сумма денег имеет фиксированный валютный scale, нормализую в конструкторе без скрытого округления и могу использовать обычный equals.

  • Равные численно значения могут дать разные результаты divide(divisor, mode): этот overload наследует scale делимого.
  • StripTrailingZeros меняет представление, иногда создаёт отрицательный scale и научную запись. Это политика нормализации, а не косметика.
  • Generated equals record унаследует правила BigDecimal-компонента. Любое собственное числовое equals требует согласованного hashCode и учёта валюты.

Почему divide бросает ArithmeticException и как выбрать округление?

Divide без ограничения точности требует точную конечную десятичную дробь. 1/8 представляется как 0.125, 1/3 не заканчивается и бросает ArithmeticException. Я задаю result scale и RoundingMode либо MathContext с нужной precision, исходя из контракта операции.

Режимы различаются направлением и ties: DOWN идёт к нулю, FLOOR к минус бесконечности; HALF_UP на середине идёт от нуля, HALF_EVEN выбирает чётную последнюю цифру. UNNECESSARY использую для проверки, что значение уже допустимо без потери данных.

  • Divide(divisor, mode) использует scale делимого и для BigDecimal.ONE / 3 может дать 0. Явный scale убирает эту зависимость от входа.
  • HALF_EVEN не является универсальной денежной политикой; учитывают правила конкретного расчёта и поведение БД.
  • Переполнение scale и деление на ноль тоже могут дать ArithmeticException. Нужно различать причину, а не добавлять округление к любой ошибке.

Почему сумма округлённых строк отличается от округлённой суммы?

Округление теряет информацию, поэтому оно не распределяется по сложению. Три точные строки 0.015 с HALF_EVEN до двух знаков дают 0.02 каждая, то есть 0.06. Если сначала сложить, получится 0.045, а округление итога даст 0.04.

Я согласую место округления: отдельная строка, налог, итог или сумма к проведению. Промежуточные расчётные значения сохраняю с нужной точностью, а на договорённой границе применяю единый режим. Сам выбор BigDecimal ещё не делает правила разных сервисов одинаковыми.

  • Двойное округление может изменить результат: 1.2451 сразу до scale 2 даёт 1.25, а через scale 3 с HALF_EVEN — 1.24.
  • Сложение с ограниченным MathContext не ассоциативно. Parallel reduce может изменить дерево группировки и числовой итог.
  • При распределении оплачиваемой суммы нужен явный алгоритм остатка, иначе сумма долей не совпадёт с исходным total.

Как хранить деньги: BigDecimal или long в минимальных единицах?

Для суммы храню значение вместе с валютой и соглашением об единицах. BigDecimal удобен для десятичных вычислений и точного NUMERIC/DECIMAL; long удобен для целого числа минимальных единиц при известном диапазоне. У long всё равно возможны overflow и остатки, а у BigDecimal нужно ограничивать допустимые precision и scale.

Вход уже проводимой суммы проверяю через setScale с UNNECESSARY, а перевод в long — через longValueExact. Для EUR наша модель задаёт два дробных знака, но это не универсальный scale всех валют. Курсы и промежуточные величины имеют отдельный контракт точности.

  • LongValue молча усечёт дробь и может потерять старшие биты. Math.addExact выявляет переполнение сложения minor units.
  • Currency fraction digits — метаданные стандартных единиц, а не правила cash rounding или внешнего провайдера.
  • Колонка с объявленным scale может округлить вход; JSON-потребитель может прочитать double. Гарантия должна сохраняться по всему пути.
