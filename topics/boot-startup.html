Spring Boot: Startup & Packaging

При запуске Boot сначала готовит окружение и собирает контекст, затем завершает подготовку приложения. Встроенный сервер успевает открыть порт раньше, чем закончится твой прогрев банка. При остановке происходит обратный переход: сервис перестаёт получать новый трафик и даёт начатым запросам время закончиться. Упаковка определяет, как JVM найдёт код и библиотеки, а AOT позволяет подготовить часть работы заранее. Для платёжного сервиса важно различать работающий процесс, открытый порт и готовность проводить платежи.

Открытый порт ещё не означает, что сервис готов принимать платежи

После деплоя сервис загружает справочник банка и проверяет локальный кеш маршрутов платежей. На это уходит несколько секунд. Команда ждёт сообщения о запуске Tomcat и отправляет первые запросы. Контроллер уже работает, но нужный справочник ещё не загружен.

Встроенный Tomcat запускается во время refresh контекста. Пользовательские ApplicationRunner выполняются позже. Поэтому запрос, отправленный напрямую в открытый порт, способен пройти до ApplicationReadyEvent. Состояние readiness сообщает платформе о готовности; оно само по себе не ставит запрет перед каждым контроллером.

Проверим это на небольшом сервисе. Прогрев удерживается защёлкой, а отдельный поток отправляет запрос. Контроллер просто показывает, завершён ли прогрев. Никакой временной гонки с sleep здесь нет: запрос приходит после входа в runner, а runner продолжится только после нашего разрешения.

static final CountDownLatch runnerEntered = new CountDownLatch(1);
static final CountDownLatch releaseRunner = new CountDownLatch(1);
static final AtomicBoolean warmed = new AtomicBoolean();

@RestController
class PaymentController {
    @GetMapping("/pay")
    String pay() { return "warm=" + warmed.get(); } // Readiness не блокирует этот маршрут.
}

@Bean
ApplicationRunner warmup() {
    return args -> {
        runnerEntered.countDown(); // Контекст готов, сервер уже запущен.
        releaseRunner.await(); // Изображает незаконченный прогрев банка.
        warmed.set(true);
    };
}

// app.run выполняется в отдельном потоке; здесь драйвер опыта.
runnerEntered.await();
var early = get(client, port, "/pay"); // Настоящий HTTP-запрос к Tomcat.
System.out.println("before Ready: HTTP " + early.statusCode() + ", " + early.body());
System.out.println("before readiness=" + availability.getReadinessState());
releaseRunner.countDown(); // Только теперь разрешаем закончить запуск.
before Ready: HTTP 200, warm=false
before readiness=REFUSING_TRAFFIC

Это фрагмент настоящего вывода StartupDemo.java. Демо работает на JDK 21, Boot 4.1.1, Framework 7.0.9 и управляемом Boot Tomcat 11.0.24. В полном файле ожидания ограничены сроком, сервер использует случайный свободный порт, а драйвер сам закрывает контекст.

Платформа должна отправлять обычный трафик только после успешной readiness-проверки. При прямом обращении к порту эта защита обходится. Если маршрут должен сам отказывать до готовности своей зависимости, вырази это явно в приложении. Подробные probes и endpoints разобраны в Actuator.

SpringApplication готовит окружение до сборки контекста

SpringApplication.run связывает несколько этапов. Сначала определяет вид приложения и готовит Environment: аргументы, профили и Config Data. После этого создаёт подходящий контекст и передаёт ему окружение. Настройки сервера и условия конфигурации должны быть известны раньше, чем контейнер начнёт создавать инфраструктуру.

Обычное MVC-приложение использует servlet-контекст с поддержкой встроенного сервера. Для WebFlux без MVC выбирается reactive-контекст, для приложения без веб-инфраструктуры — обычный. Если MVC и WebFlux подключены вместе, по умолчанию выбирается MVC. Тип можно задать явно через WebApplicationType, например NONE для фонового приложения.

Перед загрузкой пользовательских источников выполняются ApplicationContextInitializer. Затем Boot загружает главную конфигурацию и начинает refresh. Внутри него Spring разбирает конфигурации, регистрирует бины, выполняет обработчики и создаёт singleton-объекты. Servlet-контекст Boot также получает ServletWebServerFactory; автоконфигурация для обычного MVC-приложения даёт фабрику Tomcat.

Фабрика создаёт сервер внутри процесса JVM. Boot связывает его с контекстом и регистрирует servlet-инфраструктуру, включая DispatcherServlet. Создание объекта сервера и начало приёма соединений — разные моменты. Порт открывается при запуске серверного жизненного цикла до завершения refresh. Это и делает ранний запрос из первого шага возможным.

Ранние события нельзя надёжно ловить обычным слушателем-бином: он ещё не создан. Для них слушателя добавляют через SpringApplication.addListeners до вызова run. Тяжёлую подготовку также не стоит прятать в синхронном слушателе события: он задерживает поток публикации. Для подготовки после сборки контекста есть runners.

Если startup падает, Boot публикует событие ошибки и закрывает уже созданный контекст. FailureAnalyzer превращает известные ошибки, например занятый порт, в понятное объяснение. При неизвестной причине смотри исходное исключение и этап: сбой чтения настроек, создания бина и пользовательского прогрева требуют разных исправлений.

Runners завершают подготовку после запуска сервера

ApplicationRunner и CommandLineRunner — бины, которые Boot вызывает после успешного refresh и перед объявлением готовности. Первый получает разобранные ApplicationArguments, второй — исходный массив строк. Оба подходят для подготовки, которой уже нужны готовые зависимости контейнера.

Если runners несколько, Boot объединяет их в упорядоченный набор. Порядок задают через @Order или Ordered. Когда подготовка банка закончена, следом может прогреться зависящий от неё кеш. @Order здесь определяет порядок вызова runners; это не универсальный способ упорядочить создание всех бинов.

SpringApplication.run возвращает контекст после успешной подготовки и объявления готовности. Обычно завершение main не завершает веб-приложение: серверные потоки продолжают работать. В нашем опыте контекст запускается в отдельном потоке, чтобы проверить состояние во время runner; драйвер потом закрывает его явно.

Если runner выбрасывает исключение, Boot считает запуск неуспешным. Ready не публикуется, контекст закрывается. В полном демо есть режим, в котором после отпускания защёлки прогрев банка выбрасывает IllegalStateException. Последняя строка вывода этого режима:

./run.sh StartupDemo --fail-warmup # Runner падает после раннего запроса.
startup failed, Ready=false

Учебный драйвер перехватывает ожидаемый сбой и завершает опыт с кодом 0. Сам сервис успешный запуск не завершил.

Можно запустить прогрев через CompletableFuture внутри runner и сразу вернуть управление: Boot дождётся работы.

Boot ждёт завершения метода runner. Фоновая работа, которую тот только отправил в пул, в это ожидание не входит. Runner должен дождаться обязательной подготовки и передать ошибку наружу. Иначе готовность будет объявлена раньше нужного состояния.

Длинная подготовка требует собственного срока и понятного поведения при недоступном банке. Можно сорвать запуск, если без справочника сервис бесполезен. Можно запустить приложение в ограниченном режиме и управлять readiness отдельно. Не превращай внешний сбой банка в причину бесконечно перезапускать здоровый процесс.

Исполняемый jar запускает приложение через загрузчик Boot

Обычный jar с классами сервиса ещё не содержит весь путь запуска. JVM должна найти Spring, Tomcat и остальные зависимости. При запуске из IDE это делает подготовленный classpath. Для доставки одним файлом Maven-плагин Boot выполняет repackage: складывает код приложения и jar-зависимости в архив и добавляет загрузчик.

В таком архиве JVM сначала вызывает загрузчик Boot. Он создаёт загрузчик классов для вложенных библиотек, находит главный класс приложения и вызывает его main. Поэтому в манифесте два имени: Main-Class — вход для JVM, Start-Class — вход для приложения. Вот строки из собранного демо:

Main-Class: org.springframework.boot.loader.launch.JarLauncher
Start-Class: kb.boot.StartupDemo

Начиная с Boot 3.2 JarLauncher находится в пакете org.springframework.boot.loader.launch. Имя org.springframework.boot.loader.JarLauncher относится к прежнему загрузчику. При переносе старого Dockerfile, где загрузчик вызван вручную, это различие становится причиной ошибки запуска.

Это вложенные jar, а не объединение всех файлов библиотек в один плоский архив. Библиотеки сохраняют границы; классы приложения лежат отдельно. BOOT-INF/classpath.idx может задавать порядок вложенных библиотек. BOOT-INF/layers.idx описывает слои для извлечения при сборке образа: стабильные зависимости отдельно от часто меняющегося кода. Слои помогают кешу Docker и не создают отдельные контейнеры Spring.

В packaging/pom.xml используется родитель Boot 4.1.1, который связывает repackage с упаковкой, и плагин с явным главным классом. Фрагмент конфигурации:

<plugin>
  <groupId>org.springframework.boot</groupId>
  <artifactId>spring-boot-maven-plugin</artifactId>
  <configuration>
    <mainClass>kb.boot.StartupDemo</mainClass> <!-- Попадёт в Start-Class. -->
  </configuration>
</plugin>
cd examples/boot/packaging
mvn -q package # Собирает StartupDemo и упаковывает вместе с зависимостями.
java -jar target/startup-demo-1.0.jar # Тот же опыт, теперь из одного архива.
loader=org.springframework.boot.loader.launch.LaunchedClassLoader

Показана первая строка запуска. Остальные строки опыта совпадают с запуском через classpath из шага 3. Проверены и содержимое архива, и настоящий запуск: сервер отвечает внутри JVM, библиотеки доступны из BOOT-INF/lib.

Почему код из IDE работает, а из jar не находит ресурс

В исполняемом jar системный загрузчик видит загрузчик Boot, а ресурсы приложения доступны загрузчику приложения. Библиотеки часто ищут их через Thread.currentThread().getContextClassLoader(). Поток с неверным context class loader способен потерять ресурсы, хотя класс вызывающего кода уже загружен.

В демо запуск вынесен в отдельный поток. Перед его стартом явно задан загрузчик StartupDemo.class.getClassLoader(). Это важно при исполнении из jar: рабочий поток общего ForkJoinPool использует системный загрузчик и не подходит для такого запуска без настройки. Для библиотечного кода предпочитай штатный поиск ресурсов через загрузчик нужного класса или корректный загрузчик потока.

Boot также умеет упаковать WAR для внешнего servlet-контейнера. Тогда сервером управляет среда размещения, а приложение подключает контекст через SpringBootServletInitializer. Исполняемый jar нужен там, где сервис доставляет и запускает свой сервер сам.

Graceful shutdown даёт начатому платежу закончиться в пределах срока

Платёж уже ушёл в банк, когда платформа присылает процессу SIGTERM. Мгновенная остановка оборвёт ожидание клиента. При штатном завершении JVM вызывает зарегистрированный Boot shutdown hook, который закрывает контекст. Сервер прекращает принимать новые запросы и даёт уже начатым время завершиться. В учебном драйвере hook выключен: мы вызываем context.close() сами и видим тот же путь закрытия контекста.

С Boot 3.4 server.shutdown=graceful включён по умолчанию. Стандартный срок spring.lifecycle.timeout-per-shutdown-phase — 30 секунд. Демо задаёт пять секунд явно, чтобы результат не зависел от внешней конфигурации.

server.shutdown=graceful
spring.lifecycle.timeout-per-shutdown-phase=5s
# Это предел ожидания каждой фазы закрытия, а не всего процесса.

В ShutdownDemo.java контроллер удерживает начатый запрос, пока драйвер не разрешит ответ банка. Закрытие запускается параллельно. Вот существенный фрагмент; в полном файле каждый срок ожидания ограничен:

@GetMapping("/pay")
String pay() throws Exception {
    paymentEntered.countDown(); // Запрос уже выполняется внутри контроллера.
    releaseBank.await(); // Банк пока не ответил.
    paymentFinished.set(true);
    return "paid";
}

// Драйвер дождался входа запроса в контроллер.
var closing = CompletableFuture.runAsync(context::close);
try {
    closing.get(100, TimeUnit.MILLISECONDS); // Закрытие пока не должно закончиться.
    throw new IllegalStateException("close returned while payment blocked");
} catch (TimeoutException expected) {
    System.out.println("close waits for payment=true");
}
releaseBank.countDown(); // Разрешаем ответ в пределах пятисекундной фазы.
cd examples/boot
./run.sh ShutdownDemo # Запрос начался до close и успевает закончиться.
payment entered
readiness=REFUSING_TRAFFIC
close waits for payment=true
payment: HTTP 200, paid
context closed, paymentFinished=true

Теперь сократим срок фазы до 200 миллисекунд и оставим банк ждать. Драйвер отпустит защёлку только после закрытия контекста. Это второй режим того же файла:

./run.sh ShutdownDemo expire # Банк не успевает до предела фазы.
payment entered
readiness=REFUSING_TRAFFIC
context closed, paymentFinished=false

Graceful означает ограниченное ожидание. По достижении срока контекст продолжает закрытие, хотя наш платёж ещё не закончен. Срок задаётся на фазу жизненного цикла, поэтому несколько фаз и последующее уничтожение бинов могут занять больше времени. SmartLifecycle позволяет компонентам остановить приём работы и сообщить о завершении; компоненты с более высокой фазой останавливаются раньше. После остановки жизненного цикла контейнер уничтожает singleton-бины и вызывает их методы освобождения ресурсов.

Поведение нового клиента зависит от сервера и соединения. Tomcat прекращает приём на сетевом уровне; обещать каждому новому запросу HTTP 503 нельзя. Существующее постоянное соединение тоже требует учёта правил конкретного сервера. Важен результат для маршрутизации: новые платежи должны уходить на работающие экземпляры.

В проде согласуй срок удаления экземпляра из маршрутизации, время ожидания банка, сроки фаз Spring и предел между SIGTERM и принудительным SIGKILL у платформы. kill -9 обходит shutdown hook. Собственные очереди и фоновые задания требуют своего завершения: ожидание HTTP-запросов не учитывает работу, которую контроллер отправил в отдельный пул и уже покинул.

Даже правильная остановка не доказывает, что клиент узнал результат платежа. Банк может списать деньги, а соединение оборвётся до ответа. Идемпотентный ключ, сохранённое состояние операции и сверка результата защищают повтор; увеличение graceful-срока решает лишь часть проблемы.

AOT переносит подготовку структуры приложения в сборку

Когда важны быстрый старт и память большого числа экземпляров, часть подготовки можно выполнить до запуска. Spring AOT анализирует конфигурацию приложения при сборке и генерирует код создания и регистрации бинов, а также подсказки для рефлексии, ресурсов и прокси. При запуске приложение использует подготовленный путь вместо повторного полного исследования структуры.

Этот путь полезен и на JVM: подготовленное приложение запускают с -Dspring.aot.enabled=true. GraalVM Native Image идёт дальше: собирает платформенный исполняемый файл из достижимого кода. Для него особенно важны сведения о действиях, которые статический анализ не видит: имени класса из строки, рефлексивном конструкторе, ресурсе по динамическому пути.

Например, платёжный адаптер читает шаблон из classpath по имени банка. В обычном запуске ресурс лежит в jar. Для native нужно обеспечить включение этого ресурса в образ. Если библиотека не предоставляет подходящие hints, их добавляют через RuntimeHintsRegistrar и подключают через @ImportRuntimeHints. Проверять нужно настоящий путь работы, включая редкий обработчик ошибки, а не только успешный старт.

После AOT набор бинов зафиксирован. Профиль или условие, меняющее состав контекста, должно быть учтено при подготовке. Переключить такой состав произвольным аргументом запуска уже не получится. Адрес банка и срок ожидания могут оставаться настройками времени запуска, если они меняют значения внутри готовой структуры, а не выбор бинов.

CDS и кеш JDK ускоряют старт без native image

У JVM есть отдельная возможность сохранить результат подготовки классов. На JDK 21 доступен CDS; на JDK 25 и новее Boot документирует AOT cache JDK из проекта Leyden. Эти механизмы работают с подготовкой JVM и не заменяют Spring AOT. Boot предлагает обучающий запуск извлечённого приложения с -Dspring.context.exit=onRefresh: контекст завершает refresh и закрывается, runners не выполняются.

# Схема из Boot Reference для CDS на JDK 21; имя jar подставь своё.
java -Djarmode=tools -jar payment.jar extract --destination application
cd application # Извлечение даёт подходящую для кеша форму classpath.
java -XX:ArchiveClassesAtExit=payment.jsa -Dspring.context.exit=onRefresh -jar payment.jar
java -XX:SharedArchiveFile=payment.jsa -jar payment.jar # Рабочий запуск с архивом классов.

Для JDK 25+ соответствующая пара — обучающий запуск с -XX:AOTCacheOutput=payment.aot и рабочий с -XX:AOTCache=payment.aot. Кеш готовят для нужной сборки приложения и JDK. После изменения их состава его пересоздают. Это документированные команды, а не измерение ускорения нашего демо; CDS, AOT cache и native-сборка здесь не запускались.

Стоимость переносится в сборку и обучение: нужны подходящее окружение, воспроизводимые настройки и проверки ресурсных путей. Конструктор бина, который сразу проводит внешний платёж, опасен и при обычном старте, и при подготовке приложения. Внешние действия должны иметь явно выбранный этап и условия выполнения.

Выбор делают по измерениям: длительность старта, память, размер поставки, время сборки и скорость типичной нагрузки. Ленивое создание бинов сокращает видимую работу при старте, но переносит задержку и часть ошибок на первый запрос. Для платёжного сервиса это может ухудшить именно тот момент, ради которого ускоряли запуск.

  • Environment готовится до refresh. Встроенный сервер открывает порт во время сборки контекста, runners завершаются позже.
  • Ready следует за runners. Readiness помогает маршрутизации; прямой запрос способен получить HTTP 200 ещё до готовности.
  • В исполняемом jar Main-Class запускает загрузчик Boot, Start-Class — приложение. Код и вложенные библиотеки находятся в BOOT-INF.
  • Graceful shutdown ждёт начатые запросы в пределах срока фазы. Сохранение результата платежа и безопасный повтор требуют отдельного механизма.
  • Spring AOT фиксирует структуру приложения при сборке. Native image и кеши JVM дают разные способы перенести подготовку до рабочего запуска.

На собеседовании

Что происходит внутри SpringApplication.run?

Сначала Boot готовит окружение: аргументы, профили и файлы настроек. Затем создаёт подходящий контекст, применяет initializers, загружает главную конфигурацию и выполняет refresh. Во время refresh Spring собирает бины, а веб-контекст создаёт и запускает встроенный сервер.

После refresh Boot публикует Started, вызывает runners и объявляет Ready. Только после успешной подготовки run возвращает контекст. Если один из этапов падает, запуск считается неуспешным, уже созданный контекст закрывается.

  • ApplicationPreparedEvent ещё не означает, что все конфигурации разобраны: полный разбор и обработка бинов происходят внутри refresh.
  • Ранние события ловлю слушателем, добавленным к SpringApplication до run. Слушатель-бин на этом этапе может ещё не существовать.
  • Если одновременно подключены MVC и WebFlux, по умолчанию Boot выбирает MVC. Для фонового запуска могу явно задать WebApplicationType.NONE.

Порт открыт. Значит ли это, что приложение уже готово? Где делать прогрев?

Открытый порт говорит о работающем сервере. Подготовка сервиса ещё может идти: ApplicationRunner и CommandLineRunner выполняются после refresh, но перед Ready. В демо прямой запрос получил HTTP 200 с warm=false, пока runner ждал справочник банка.

Обязательный прогрев, которому нужны готовые бины, делаю в runner и дожидаюсь результата. ApplicationRunner даёт разобранные аргументы, CommandLineRunner — исходные строки. Платформе передаю readiness, чтобы она направляла обычный трафик только после готовности.

  • Boot ждёт возврата из runner. Отправка работы в пул без ожидания позволяет объявить Ready раньше завершения подготовки; ошибка фоновой работы тоже уже не срывает этот startup.
  • Runners разных типов упорядочиваются вместе через Ordered или Order. Этот порядок относится к их вызову и не задаёт порядок создания всех бинов.
  • Readiness становится ACCEPTING_TRAFFIC сразу после ApplicationReadyEvent. Синхронный слушатель самого Ready ещё может видеть прежнее состояние.
  • При недоступном банке выбираю осмысленную политику готовности. Перезапуск здоровой JVM не восстановит внешнюю зависимость; срок подготовки и ограниченный режим задаю отдельно.
Runner запустил прогрев в CompletableFuture и вернул управление. Нужно остановить поступление платежей до конца прогрева. Что поменяешь?

Если подготовка обязательна для успешного старта, runner должен дождаться её с ограниченным сроком и передать ошибку наружу. Если сервис запускается в ограниченном режиме, готовность управляется отдельно до завершения прогрева. Сам факт существования future Boot не удерживает. Прямой платёжный маршрут при необходимости также проверяет своё состояние готовности.

Как работает исполняемый jar Spring Boot и зачем ему JarLauncher?

Плагин Boot упаковывает приложение в BOOT-INF/classes, зависимости — отдельными jar в BOOT-INF/lib, а в корень кладёт загрузчик. JVM вызывает Main-Class из манифеста, то есть JarLauncher. Он создаёт загрузчик для вложенных областей и вызывает main класса из Start-Class.

Поэтому файл запускается через java -jar без отдельно собранного classpath. Это упаковка вместе с зависимостями, при которой библиотеки сохраняются отдельными архивами. Встроенный Tomcat остаётся библиотекой внутри процесса приложения.

  • С Boot 3.2 полный путь загрузчика — org.springframework.boot.loader.launch.JarLauncher. Проверяю явные команды запуска в старых Dockerfile при обновлении Boot.
  • Системный загрузчик не раскрывает BOOT-INF/lib. Если библиотека ищет ресурс через context class loader потока, неверный загрузчик может объяснить сбой только в упакованном приложении.
  • layers.idx помогает разнести стабильные зависимости и код по слоям образа. Это влияет на повторное использование слоёв при сборке, а не на число контекстов приложения.

Как останавливать платёжный сервис без обрыва начатых запросов?

При штатном сигнале завершения JVM запускает hook Boot и закрывает контекст. Graceful shutdown прекращает новый трафик и ждёт начатые запросы в пределах срока фазы. Затем освобождаются ресурсы. С Boot 3.4 graceful включён по умолчанию; стандартный срок фазы — 30 секунд.

Согласую это ожидание со сроком ответа банка и временем, которое платформа даёт процессу до SIGKILL. В демо ответ банка успел — клиент получил 200 и close завершился после запроса. Во втором режиме срок вышел, и контекст закрылся при ещё незавершённом платеже.

  • timeout-per-shutdown-phase ограничивает каждую фазу. Сумма нескольких фаз и уничтожение бинов могут превысить это число; это не общий предел завершения JVM.
  • SmartLifecycle останавливается в порядке убывания фаз. Фоновому обработчику и его ресурсам задаю согласованный порядок и собственное завершение, особенно если HTTP-метод уже вернул ответ.
  • Новый клиент не обязательно получит 503: Tomcat прекращает приём на сетевом уровне. Проверяю поведение конкретного сервера и маршрутизации, включая постоянные соединения.
  • Если банк уже списал деньги, потеря ответа оставляет исход неизвестным клиенту. Идемпотентность и сверка операции нужны даже при корректном graceful shutdown.
Срок фазы выставлен в 30 секунд, а платформа присылает SIGKILL через 10 секунд после SIGTERM. Какой срок реально доступен запросу?

Не больше оставшегося времени до принудительного завершения процесса, причём часть этих десяти секунд уже уйдёт на остальные действия. Настройка Spring не задерживает SIGKILL платформы. Нужно согласовать оба бюджета и прекращение нового трафика; одним увеличением числа в приложении проблему не решить.

Как ускорить старт: Spring AOT, native image или кеш JVM?

Сначала измерю, что занимает старт и какую цель мы хотим улучшить. Spring AOT готовит структуру бинов и генерирует код при сборке; его результат можно использовать на JVM. Native Image создаёт отдельный исполняемый файл и требует заранее знать достижимый код и динамические обращения.

Без native можно подготовить архив классов CDS на JDK 21 или AOT cache JDK на JDK 25+. Boot поддерживает обучающий запуск с spring.context.exit=onRefresh: контекст подготовлен, но runners ещё не выполнялись. Выбор проверю на реальном сервисе по старту, памяти, сборке и рабочей нагрузке.

  • AOT фиксирует состав контекста. Условия и профили, меняющие бины, учитываю при подготовке; обычное значение адреса банка может оставаться параметром запуска.
  • Для native отдельно проверяю рефлексию, ресурсы и прокси, включая редко исполняемые пути. Недостающие сведения добавляю hints; успешный старт ещё не доказывает работу обработки ошибки банка.
  • Кеш JVM привязан к подходящей сборке и JDK. Обучение с onRefresh не покрывает код runners, а внешние действия в создании бина всё ещё могут выполниться.
  • Ленивое создание переносит подготовку и ошибки на первый запрос. Сокращение времени старта за счёт задержки первого платежа может ухудшить нужный показатель.
