Maven & Gradle

Сборщик превращает исходники и объявления зависимостей в конкретный набор файлов для запуска. Он выбирает версии библиотек, строит порядок работ и вызывает компилятор, тесты и упаковку. Успешная компиляция проверяет только тот код и classpath, которые участвовали в ней. Если чужой готовый JAR вызывает метод из другой версии API, ошибка обнаружится уже в JVM.

Собранный JAR ещё не содержит всё приложение

Сервис платежей состоит из app, своей библиотеки domain и двух адаптеров банка. На ноутбуке команда сборки зелёная, но в контейнер скопировали только app-1.0.jar. При запуске JVM не находит demo.Fee из domain. Первое, что надо восстановить, — какие файлы сборщик создал и какой набор файлов получил процесс.

Maven и Gradle задают повторяемую процедуру вместо ручного javac -cp …. Для Java оба понимают привычные каталоги src/main/java, src/main/resources, src/test/java и src/test/resources: основной код, его ресурсы и отдельные тестовые входы. Maven пишет результат в target, Gradle — в build. Тестовый класс не становится частью основной библиотеки лишь потому, что тест прошёл.

Зависимость определяется координатами, например demo.fixture:money-api:2.0: group, artifact, version. В Maven для различения артефактов важны также type и classifier — основной JAR, sources и tests могут иметь одни координаты GAV, но разные файлы. Репозиторий отдаёт метаданные POM и сам JAR: POM нужен для обхода транзитивных зависимостей, JAR — для компиляции или исполнения. Gradle умеет читать POM и более богатые Gradle Module Metadata с вариантами.

Полный проверяемый проект использует одни Java-исходники для двух сборок. Запуски ниже выполнены на JDK 21.0.11, Maven 3.9.16 и Gradle 9.6.1. verify.py компилирует собственные фикстуры, создаёт отдельный файловый репозиторий и сохраняет реальные логи. Плагины и JUnit 5.11.4 загружаются из Maven Central; production-сервис или контейнер здесь не нужны.

# Из подготовленной копии проекта; Maven создал app/target/app-1.0.jar.
java -cp app/target/app-1.0.jar demo.App
# В classpath только app: внешней библиотеки domain здесь нет.
Exception in thread "main" java.lang.NoClassDefFoundError: demo/Fee

Это первая строка реального исключения, без последующего стектрейса. Для запуска нужен полный runtime classpath, дистрибутив с каталогом библиотек либо специальная упаковка: shaded JAR или Spring Boot executable JAR. jar и package сами по себе такую упаковку не обещают. После восстановления classpath нас ждёт другая ошибка: библиотека есть, но её API не совпадает.

Maven выполняет цели плагинов до выбранной фазы

В Maven package — фаза жизненного цикла, а compiler:compile — цель плагина. Фаза задаёт место работы в последовательности; цель выполняет конкретную работу. Для packaging jar Maven связывает compile с Compiler Plugin, test с Surefire и package с Jar Plugin. У packaging pom нет такой же компиляции: родитель описывает сборку, а не обязательно содержит код.

Вызов mvn verify проходит default lifecycle от начала до verify включительно. Промежуточные фазы есть и между знакомыми названиями: ресурсы надо скопировать до компиляции, тесты — скомпилировать до запуска. Если к фазе не привязана работа, само её название ничего не запускает. Поэтому verify не создаёт интеграционные тесты из воздуха: соответствующие цели надо подключить.

КомандаЧто получает проектЧего она ещё не делает
mvn testОсновной и тестовый код, запуск unit-тестовНе упаковывает JAR
mvn packageПредыдущие фазы и упакованный артефактНе проходит фазы после package
mvn verifyТакже настроенные integration-test, post-integration-test и проверки verifyНе устанавливает артефакт в локальный репозиторий
mvn installТакже JAR и POM в локальном репозиторииНе публикует их коллегам
mvn deployТакже публикацию в удалённый репозиторий артефактовНе выкатывает сервис в Kubernetes

Версии плагинов фиксируем в родительском pluginManagement, а Java API — через maven.compiler.release. Management даёт настройки, когда плагин используется. Compiler уже вызван стандартной привязкой packaging; произвольный дополнительный плагин одной записью в management не включается. Ему нужна запись в build/plugins и execution с goal и фазой либо прямой вызов цели.

<!-- Фрагмент корневого pom.xml: версии наследуют domain и app. -->
<properties>
  <maven.compiler.release>21</maven.compiler.release>
</properties>
<build>
  <pluginManagement>
    <plugins>
      <plugin>
        <groupId>org.apache.maven.plugins</groupId>
        <artifactId>maven-compiler-plugin</artifactId>
        <version>3.14.0</version>
      </plugin>
    </plugins>
  </pluginManagement>
</build>
# clean — отдельный lifecycle: verify сам не удаляет target.
mvn -pl app -am verify
# Только цель compile после clean: нет прохождения test и package.
mvn -pl domain clean org.apache.maven.plugins:maven-compiler-plugin:3.14.0:compile
[INFO] --- compiler:3.14.0:compile (default-compile) @ domain ---
[INFO] --- compiler:3.14.0:testCompile (default-testCompile) @ domain ---
[INFO] --- surefire:3.5.3:test (default-test) @ domain ---
[INFO] Tests run: 2, Failures: 0, Errors: 0, Skipped: 0
[INFO] --- jar:3.4.2:jar (default-jar) @ domain ---

Это выбранные строки первого запуска, в исходном порядке. Во втором запуске создался Fee.class, но не появились ни surefire-reports, ни domain-1.0.jar: драйвер проверил это по файлам. Прямой goal не эквивалентен фазе. Например, голый surefire:test не обязан предварительно скомпилировать тесты.

Почему интеграционные тесты заканчивают через verify

Failsafe выполняет тесты в integration-test и проверяет их результат в verify. Ошибка теста не останавливает lifecycle раньше post-integration-test, где можно выключить поднятую среду. Если остановиться командой mvn integration-test, до этого cleanup и окончательной проверки не дойдёшь. Обе цели Failsafe подключают явно; подробный выбор тестов — в теме Testing.

-DskipTests пропускает запуск тестов Surefire, но сохраняет их компиляцию. -Dmaven.test.skip=true понимают также Compiler и Failsafe, поэтому он пропускает и test-compile. Эти флаги меняют смысл зелёной сборки: успешная упаковка без исполнения тестов не доказывает корректность поведения.

Gradle выбирает граф задач, а не префикс фаз

В Gradle settings.gradle(.kts) определяет состав сборки, а build-скрипты применяют плагины и настраивают проекты. При initialization появляются проекты; при configuration регистрируются задачи и определяется нужный граф; при execution выполняются их действия. Код верхнего уровня build-скрипта работает при конфигурации. doLast относится к выполнению задачи: сетевой запрос в верхнем уровне может неожиданно происходить даже при просмотре списка задач.

Java Plugin добавляет compileJava, test, jar и lifecycle-задачи. build объединяет assemble и check; для Java они ведут к упаковке и тестам. Задача jar тянет подготовку основных классов, но не тестовую ветку. Поэтому порядок «compile, test, jar» из Maven нельзя переносить в Gradle как универсальное правило.

Плагин добавляет модель предметной области: Java Plugin знает source sets, Application Plugin — main class, runtime classpath и дистрибутив. В нашем app Application Plugin запускает demo.App через run. Groovy DSL и Kotlin DSL настраивают одну модель Gradle; разница в синтаксисе и проверке скрипта, а не в правиле выбора зависимостей.

// Фрагмент app/build.gradle: application добавляет run и дистрибутив.
plugins { id 'application' }
java { toolchain { languageVersion = JavaLanguageVersion.of(21) } }
tasks.withType(JavaCompile).configureEach { options.release = 21 }
application { mainClass = 'demo.App' }
dependencies {
    implementation project(':domain') // Порядок компиляции выводится из зависимости.
    implementation 'demo.fixture:legacy-adapter:1.0'
    implementation 'demo.fixture:new-adapter:1.0'
}

Для своих работ tasks.register позволяет отложить создание задачи до необходимости. dependsOn добавляет обязательную работу в граф. mustRunAfter лишь ограничивает порядок уже выбранных задач: он не означает «всегда выполни подготовку». В отдельном минимальном проекте это различие видно без шума Java Plugin.

// settings.gradle
rootProject.name = 'lifecycle'
println 'INIT settings'

// build.gradle
println 'CONFIG build'
tasks.register('prepare') { doLast { println 'EXEC prepare' } }
tasks.register('ship') {
    dependsOn('prepare') // ship включает prepare.
    doLast { println 'EXEC ship' }
}
tasks.register('audit') {
    mustRunAfter('prepare') // audit не включает prepare.
    doLast { println 'EXEC audit' }
}
# Из lifecycle; configuration cache отключён, чтобы видеть чтение скриптов.
gradle -q --no-configuration-cache ship
gradle -q --no-configuration-cache audit
INIT settings
CONFIG build
EXEC prepare
EXEC ship

INIT settings
CONFIG build
EXEC audit

Пустая строка разделяет два реальных запуска. Во втором prepare не выбран. Для диагностики используй gradle :app:build --dry-run: граф часто объясняет пропущенный тест или генератор лучше догадки о «неправильном порядке» строк в скрипте.

Один граф запросов даёт разные выбранные версии

Теперь внешние JAR в classpath есть. legacy-adapter:1.0 просит money-api 1.0; new-adapter:1.0 просит 2.0. Новый адаптер уже скомпилирован с методом minorUnits(). Его готовый байткод сборщик заново не компилирует. На этапе сборки app компилятору достаточно публичного метода самого адаптера, а внутренний вызов API JVM свяжет при исполнении.

Maven по умолчанию выбирает ближайшее объявление зависимости; при одинаковой глубине выигрывает первое. Gradle по умолчанию выбирает наибольшую из запрошенных версий одного модуля, независимо от глубины. Это выбор среди требований графа, а не загрузка «последней версии из интернета». Дополнительные management, constraints и resolution rules меняют эти правила.

// Собственные фикстуры: два варианта одной demo.fixture.MoneyApi.
// money-api:1.0
public final class MoneyApi {
    public static String currency() { return "EUR"; }
}
// money-api:2.0 — тот же FQCN, добавлен метод.
public final class MoneyApi {
    public static String currency() { return "EUR"; }
    public static int minorUnits() { return 2; }
}
// legacy-adapter скомпилирован с API 1.0; его POM просит 1.0.
public static String currency() { return MoneyApi.currency(); }
// new-adapter скомпилирован с API 2.0; его POM просит 2.0.
public static int minorUnits() { return MoneyApi.minorUnits(); }

// App.main: компилятор app видит методы адаптеров.
System.out.println("fee=" + Fee.minorUnits(101));
System.out.println("legacy=" + LegacyAdapter.currency());
System.out.println("new=" + NewAdapter.minorUnits());

Это фрагменты четырёх полных классов фикстур и App; они не вставляются в один Java-файл. Их POM создаёт драйвер: legacy и new имеют обычную compile-зависимость money-api нужной версии. В app оба адаптера объявлены в указанном порядке. Domain считает комиссию для 101 minor units как (101 + 49) / 50 = 3; подробная денежная модель — в BigDecimal & Money.

# После install: отдельному goal доступны метаданные своего domain.
mvn -pl app org.apache.maven.plugins:maven-dependency-plugin:3.8.1:tree \
  -Dverbose -Dincludes='demo.fixture:*'
# Конкретная причина выбора в runtime-конфигурации Gradle.
gradle :app:dependencyInsight --dependency money-api --configuration runtimeClasspath
[INFO] demo.build:app:jar:1.0
[INFO] +- demo.fixture:legacy-adapter:jar:1.0:compile
[INFO] |  \- demo.fixture:money-api:jar:1.0:compile
[INFO] \- demo.fixture:new-adapter:jar:1.0:compile
[INFO]    \- (demo.fixture:money-api:jar:2.0:compile - omitted for conflict with 1.0)

В tree omitted означает отброшенную ветку, а не вторую версию на classpath. В Gradle dependencyInsight надо читать Selection reasons и пути требований, а не только прямые строки build-скрипта. Драйвер построил runtime classpath Maven через dependency:build-classpath, добавил app JAR и запустил настоящую JVM; Gradle запустил тот же App через :app:run.

fee=3
legacy=EUR
Exception in thread "main" java.lang.NoSuchMethodError: 'int demo.fixture.MoneyApi.minorUnits()'

Это Maven с исходным порядком, первые строки без стектрейса. В Gradle и в исправленном Maven последний результат — new=2. Наличие более высокого номера версии не доказывает совместимость вообще: в опыте 2.0 сохранила старый метод, а реальный major-релиз способен его удалить. Если одинаковые классы приходят из разных artifactId, обычная медиация одного модуля такой конфликт не устраняет.

Maven кладёт все версии, а JVM потом сама выбирает правильную.

Для одного конфликтующего модуля Maven заранее выбирает версию. JVM не читает POM и не согласовывает версии: она загружает доступный класс и связывает нужный метод. При ручном classpath с дубликатами порядок поиска создаёт отдельную проблему.

Версия и видимость зависимости — разные решения

В Maven dependencyManagement задаёт параметры зависимости, когда она встречается в графе. Запись сама не добавляет библиотеку. В нашем профиле align money-api уже приходит через адаптеры; management выбирает 2.0 для этих транзитивных запросов. Если app прямо использует MoneyApi, dependency стоит объявить явно, чтобы обновление адаптера не удалило случайно её единственный путь.

<!-- Фрагмент профиля align в родителе; включается -Palign. -->
<dependencyManagement>
  <dependencies>
    <dependency>
      <groupId>demo.fixture</groupId>
      <artifactId>money-api</artifactId>
      <version>2.0</version> <!-- Управляет уже пришедшей зависимостью. -->
    </dependency>
  </dependencies>
</dependencyManagement>

BOM — POM с согласованными версиями целого семейства библиотек. Maven импортирует его с type=pom и scope=import в management; конкретные dependencies всё равно объявляются отдельно. Управление зависимостями приложения не управляет зависимостями Maven-плагина: плагин работает в своём контексте загрузки. Поэтому обновление библиотеки приложения не всегда устраняет ошибку старого плагина.

В Gradle обычная constraint 1.0 не закрепляет верхнюю границу: запрос 2.0 по-прежнему способен выиграть. strictly ограничивает допустимый выбор. В опыте строгое 1.0 разрешается успешно, но запуск ломается — метаданные не знают, что готовый new-adapter использует новый метод. Это полезное различие между удовлетворением правил resolver и бинарной совместимостью.

// Фрагменты app/build.gradle; адаптеры объявлены выше в обоих случаях.
// -Pordinary: обычная constraint допускает выбор более высокой 2.0.
constraints { implementation 'demo.fixture:money-api:1.0' }

// -Pstrict: строгая constraint заставляет этот граф выбрать 1.0.
constraints {
    implementation('demo.fixture:money-api') {
        version { strictly '1.0' }
    }
}
# Три раздельных запуска: условия меняет свойство проекта.
gradle -q :app:run
gradle -q :app:run -Pordinary
gradle :app:run -Pstrict
# Maven: изменить политику или только поменять местами два объявления.
# В драйвере для запуска с каждым набором заново строится runtime classpath.
mvn -pl app org.apache.maven.plugins:maven-dependency-plugin:3.8.1:build-classpath \
  -DincludeScope=runtime -Palign
mvn -pl app org.apache.maven.plugins:maven-dependency-plugin:3.8.1:build-classpath \
  -DincludeScope=runtime -Dfirst.adapter=new-adapter -Dsecond.adapter=legacy-adapter
fee=3
legacy=EUR
new=2

Одинаковый stdout получили Gradle по умолчанию, Gradle с ordinary, Maven с align и Maven с обратным порядком. Strict 1.0 получил тот же NoSuchMethodError, что исходный Maven. Перестановка случайно меняет победителя при равной глубине; management выражает намерение. Для приложения удобнее согласованный набор через BOM/platform, а опасное расхождение можно превращать в ошибку сборки проверками Maven Enforcer или политиками Gradle.

Scope/configuration отвечает на другой вопрос: в каком classpath нужен файл. В Maven compile — значение по умолчанию и присутствует в основных compile/runtime и тестах; provided есть для компиляции и тестов, но ожидается от среды при запуске; runtime нужен при исполнении и в тестах, но не для основных исходников; test — только для тестов. Provided и test не распространяются на потребителей как обычная compile-зависимость. Например, JDBC-драйвер можно подключить runtime, если код компилируется только против java.sql.

Gradle implementation видна основному коду своего проекта и в runtime. api дополнительно экспортирует типы в compile classpath потребителя. Если публичная сигнатура lib возвращает тип MoneyApi, потребителю нужен этот тип для компиляции — зависимость относится к api. Внутренний вызов, возвращающий клиенту обычную строку, можно оставить implementation: меньше связности и меньше причин перекомпилировать клиента. compileOnly, runtimeOnly, testImplementation и testRuntimeOnly позволяют описать остальные потребности; compileOnly не является полным синонимом Maven provided, включая тесты.

// visibility/lib/build.gradle: ровно одна из двух веток.
plugins { id 'java-library' }
dependencies {
    if (providers.gradleProperty('expose').isPresent()) {
        api 'demo.fixture:money-api:2.0'
    } else {
        implementation 'demo.fixture:money-api:2.0'
    }
}
// visibility/client/build.gradle
dependencies { implementation project(':lib') }
def compilePath = configurations.compileClasspath
def runtimePath = configurations.runtimeClasspath
tasks.register('paths') {
    doLast {
        println "compile money-api=${compilePath.files.any { it.name == 'money-api-2.0.jar' }}"
        println "runtime money-api=${runtimePath.files.any { it.name == 'money-api-2.0.jar' }}"
    }
}
# Из visibility; два запуска одной модели потребителя.
gradle -q :client:paths --no-configuration-cache
gradle -q :client:paths -Pexpose --no-configuration-cache
compile money-api=false
runtime money-api=true

compile money-api=true
runtime money-api=true

Пустая строка разделяет запуски. В этом опыте lib не содержит Java-кода: проверяется именно resolver и видимость файлов, а не вызов методов. Установка api не встраивает деньги в JAR lib. Отдельные наборы файлов сохраняются до упаковки специальным плагином.

Состав сборки, наследование и зависимость не совпадают

В Maven родитель передаёт свойства, management и настройки через parent. Aggregator перечисляет modules, которые участвуют в одном запуске. Эти роли часто совмещают в корневом POM с packaging pom, но они независимы: модуль может наследовать корпоративный parent из репозитория, а собираться в другом агрегаторе. Наличие общей папки не означает зависимость классов одного модуля от другого.

Reactor собирает выбранные проекты и сортирует их по настоящим связям. В корневом POM нашего примера app перечислен раньше domain, но app зависит от demo.build:domain:1.0, поэтому domain собирается первым. Простая запись в dependencyManagement не создаёт эту зависимость и не задаёт порядок reactor. Цикл app → domain → app не имеет корректного порядка и указывает на проблему границы модулей.

<!-- payments/pom.xml: это состав сборки, не classpath app. -->
<packaging>pom</packaging>
<modules><module>app</module><module>domain</module></modules>
<!-- app/pom.xml: parent наследует настройки. -->
<parent>
  <groupId>demo.build</groupId><artifactId>payments</artifactId><version>1.0</version>
</parent>
<!-- Отдельно нужна настоящая зависимость на код domain. -->

Успех dependency:tree до install не опровергает это: он вывел предупреждение о недостающем POM domain и частичный граф, а полноценной компиляции нужен сам JAR. В Gradle include('app', 'domain') в settings создаёт проекты, а implementation project(':domain') задаёт потребление результатов domain. Gradle получает зависимости работ из этой модели; вручную привязывать app.compileJava к domain.jar не требуется. При этом :app:build тянет необходимый domain.jar, но не означает «запусти все тесты domain». В проверенном dry-run domain.test отсутствовал. Вызов gradle build из корня нашего проекта выбрал build в обоих подпроектах и запустил тесты domain.

Модули полезны для разных API, ответственности и независимой компиляции. Деление по каждой технической папке без устойчивых границ добавляет настройку, но не убирает связанность. Общую build-логику в Maven держат в parent, в Gradle — в convention plugins; копирование сотни одинаковых настроек между модулями оставляет пространство для дрейфа.

Воспроизводимость требует одинаковых входов, а не только clean

Если ноутбук и CI выбирают разные библиотеки, сначала сравни версию инструмента, effective-конфигурацию, активные profiles, repositories и нужный classpath. Для Maven помогают mvn -version, help:effective-pom, help:active-profiles и tree; для Gradle — версия wrapper, dependencies --configuration runtimeClasspath, insight и --info. Maven settings управляет зеркалами и доступом к репозиториям, поэтому одинаковый POM ещё не означает одинаковую среду. Пароли остаются в пользовательских/CI секретах, а не в проектном POM.

Wrapper фиксирует Maven/Gradle, toolchain выбирает JDK для работ, а --release задаёт уровень языка, байткода и доступного стандартного API. Это три разных входа. На JDK 21 один -source 17 -target 17 всё ещё позволяет скомпилировать вызов нового API List.getFirst(), которого нет в Java 17. --release 17 отвергает его при компиляции. Даже release не проверяет совместимость сторонних JAR с целевой JVM.

// Полный проверяемый ReleaseProbe; getFirst появился в JDK 21.
import java.util.List;
class ReleaseProbe {
    Object first() { return List.of("EUR").getFirst(); }
}
# Обе команды выполняются javac из JDK 21 на одном файле.
javac -source 17 -target 17 ReleaseProbe.java # Проходит: API взят из текущего JDK.
javac --release 17 ReleaseProbe.java        # Ошибка: API ограничен Java 17.
  symbol:   method getFirst()
  location: interface List<String>

Это две строки диагностики второго запуска; путь файла и строка кода опущены. Toolchain в демо выбирает установленный JDK 21, не требует скачивать его. Для команд Gradle на странице использован установленный инструмент, версия зафиксирована в условиях опыта; в рабочем сервисе wrapper и его файлы хранят вместе с кодом. Замена XML на Kotlin не заменяет фиксацию версии инструмента.

Фиксируй версии зависимостей и плагинов; SNAPSHOT и динамическое 1.+ позволяют менять входы без изменения исходников. Gradle version catalog даёт имена и централизованные объявления, platform/BOM согласует набор требований, dependency locking записывает фактически разрешённые версии для конфигураций. Это разные функции: наличие каталога само не превращает все запросы графа в строгую фиксацию. Для byte-for-byte результата также нужны детерминированные генераторы и архивы: одинаковые версии — необходимое, но не полное условие.

Это выбранные строки повторной сборки. Тестовое действие не исполнилось заново: его входы и выходы не изменились. Своя задача обязана честно объявлять файлы, параметры и окружение, влияющие на результат; иначе сборщик способен принять устаревший результат за актуальный. У задачи с побочным сетевым действием нельзя механически включить кеш как у чистого преобразования файлов.

Offline-режим Maven -o или Gradle --offline ограничивает работу доступными зависимостями и метаданными, а не делает пустую машину самодостаточной. Первое скачивание, другой profile или новая версия плагина потребуют недостающие входы. Для малого однофайлового опыта достаточно javac, но сервису с библиотеками и проверками нужен объявленный процесс сборки. Выбор между Maven и Gradle определяется существующей сборкой, плагинами и ценой поддержки её логики; универсальное «Gradle всегда быстрее» не объясняет ни граф, ни корректность.

Сборка проверяет выбранные тесты и формирует артефакты. Она не доказывает отсутствие ошибок в неисполненных путях, не гарантирует одинаковую production-конфигурацию и не выкатывает приложение сама. Границы тестов — в Testing, доставка артефактов и окружений — в CI/CD, связывание классов — в Class Loading.

  • Артефакт своего модуля и runtime classpath — разные результаты. Обычный JAR не включает внешние библиотеки.
  • Maven идёт до фазы и выполняет привязанные цели. Gradle выбирает задачи вместе с их prerequisites; jar не означает test.
  • Maven без management выбирает ближайшую версию, при равной глубине первую; Gradle без специальных правил — наибольшую запрошенную.
  • Resolver не проверяет методы чужого байткода. Успешная сборка способна закончиться NoSuchMethodError при запуске.
  • Management/constraints управляют выбором, scopes/configurations — доступностью, parent/modules/project dependencies — разными связями между проектами.
  • Повторяемая сборка требует фиксированных входов и честно описанных работ. Clean не заменяет wrapper, release, согласование библиотек и проверки.

На собеседовании

Чем фаза Maven отличается от goal и от задачи Gradle?

В Maven я выбираю этап жизненного цикла, например verify. Maven проходит предыдущие фазы и запускает связанные с ними цели плагинов: компиляцию, тесты, упаковку. Goal — сама работа, например compiler:compile; прямой вызов этой цели не равен прохождению фаз до compile.

В Gradle я выбираю задачу и получаю её граф prerequisites. Build включает упаковку и проверки, но jar сам тесты не тянет. Поэтому в CI смотрю на реальную команду и подключённые плагины: зелёный package или jar ещё не означает, что прошёл весь набор проверок.

  • Clean — отдельный Maven lifecycle. Install публикует в локальный репозиторий, deploy — в удалённый репозиторий артефактов; это не выкладка сервиса.
  • Failsafe разделяет integration-test и verify, чтобы ошибка теста не помешала post-integration-test очистить среду. Проверять сборку надо до verify.
  • В Gradle configuration и task action происходят в разные моменты. DependsOn включает prerequisite; mustRunAfter лишь упорядочивает уже выбранные работы.
CI выполняет mvn package -DskipTests. Что подтверждает зелёный результат?

Код и тесты скомпилировались и артефакт упакован, но тесты Surefire не исполнились. Фазы после package также не пройдены. Если нужен согласованный набор unit/integration-проверок, его подключают и запускают до verify без такого пропуска.

Как Maven и Gradle разрешают конфликт версий и почему сборка проходит, а сервис падает?

Я сначала смотрю граф нужного classpath. В Maven без специальных настроек выигрывает ближайшее объявление, а при равной глубине первое. В Gradle по умолчанию выигрывает наибольшая запрошенная версия. Tree и dependencyInsight показывают, откуда пришли требования и что выбрано.

Выбор одной версии не проверяет внутренние вызовы уже скомпилированных библиотек. Если адаптер собирали с новым методом API, а при запуске ему дали старую библиотеку, получим NoSuchMethodError. Я согласую совместимые версии через management или constraints и проверяю именно runtime classpath и проблемный путь, а не лечу ошибку перезапуском.

  • DependencyManagement не добавляет JAR и не управляет classpath Maven-плагинов. BOM импортирует набор настроек, а реальные зависимости остаются в declarations.
  • Обычная Gradle constraint не запрещает повышение версии. Strictly ограничивает выбор, но способна закрепить бинарно несовместимую версию: в нашем демо strict 1.0 снова ломает new-adapter.
  • Медиация одного модуля не устраняет одинаковые FQCN из разных artifactId. Тут нужны диагностика дубликатов и проверка реального способа загрузки классов.

Как устроить многомодульную сборку и проверить изменение общей библиотеки?

Я разделяю три связи: parent передаёт настройки, modules включает проекты в запуск, dependency даёт одному проекту код другого. В Maven reactor сортирует по настоящим зависимостям, поэтому список modules не обязан быть порядком компиляции. Для сборки app вместе с нужной библиотекой использую -pl app -am; для проверки потребителей изменения смотрю также на -amd.

В Gradle включаю проекты в settings и объявляю project dependency, чтобы порядок работ выводился из модели. При этом сборка одного app не обещает тестировать все библиотеки. Для изменения domain выбираю команду, которая проверяет его тесты и нужных потребителей, а не только пересобирает JAR.

  • После Maven verify артефакт есть в target и доступен текущему reactor. Новая отдельная сборка потребителя ищет его в репозиториях: нужен install или опубликованная версия.
  • Management не создаёт ребро reactor. Корневой aggregator может включать модули с другим parent; наследование не равно совместному выпуску.
  • Циклический граф модулей ломает порядок. Выделение малого общего контракта полезнее взаимных зависимостей app и domain или копирования классов между ними.
В Gradle :app:build прошёл после правки domain. Достаточно этого, чтобы считать тесты domain проверенными?

Нет. Project dependency тянет результаты domain, нужные app, но не обязана выбирать domain.test. В демо dry-run включал domain.jar и не включал domain.test. Надо выбрать отдельную проверку domain либо согласованную корневую команду, включающую оба набора тестов.

Почему одинаковый исходный код собирается по-разному локально и в CI?

Я сравниваю все входы: версию сборщика и JDK, profiles, repositories, версии плагинов и фактически выбранные библиотеки. Wrapper фиксирует инструмент, toolchain выбирает JDK, release ограничивает Java API и байткод. Динамическая версия или SNAPSHOT позволяют изменить результат без изменения нашего кода.

Ещё важно сравнивать один и тот же classpath: тесты могут видеть библиотеку, которой нет в runtime. В Gradle implementation скрывает внутреннюю зависимость от компиляции потребителя, но оставляет её при запуске; api экспортирует её типы. Я диагностирую конкретное расхождение и фиксирую входы, а clean использую для удаления результатов, а не как объяснение проблемы.

  • Source/target не заменяют release: JDK 21 с target 17 способен разрешить getFirst(), отсутствующий на Java 17. Release отвергает такой код раньше запуска.
  • Version catalog централизует объявления, platform согласует требования, locking хранит выбранные версии. Их задачи различаются; каталог сам не фиксирует весь транзитивный граф.
  • UP-TO-DATE проверяет текущие входы/выходы, build cache восстанавливает выходы, configuration cache переиспользует подготовку работ. Неполно объявленные inputs создают ложную актуальность, а не ускоряют корректную сборку.
