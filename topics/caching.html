Caching Strategies

Кеш хранит копию данных ближе к тому, кто их читает, и отвечает за доли миллисекунды вместо десятков. Чаще всего используют cache-aside: приложение смотрит в кеш, при промахе читает базу и кладёт результат со сроком жизни. Трудная часть — не положить, а вовремя убрать: даже правильный порядок «обновить базу, удалить ключ» оставляет окно, в котором старое значение возвращается в кеш до истечения TTL. Вторая беда — stampede: когда популярный ключ истекает под нагрузкой, все запросы одновременно идут в базу. TTL как страховка, блокировка на загрузку и разброс сроков решают большую часть проблем.

Тариф поменяли в базе, а платежи час шли по старому, и каждый час база захлёбывалась

Платёжный сервис на каждый платёж читает тариф магазина. Чтобы не нагружать базу, тарифы положили в Redis на час. Через месяц выяснилось, что после смены тарифа часть платежей ещё час проходила по старой ставке, хотя код при обновлении удаляет ключ. А каждый раз, когда ключ тарифа крупного магазина истекает, на графике базы виден всплеск: сотня одинаковых запросов за одну миллисекунду.

Тема разбирает стратегии кеширования независимо от фреймворка: где держать кеш, как его заполнять и обновлять, откуда берутся устаревшие данные и лавина запросов. Аннотации Spring @Cacheable и ловушки прокси — в Caching в Spring, сам Redis — в Redis Basics, кеширование ответов на уровне HTTP — в HTTP Cache & CDN. Демо CachingDemo.java работает с настоящим Redis 8 в Docker через Jedis 8; база заменена заглушкой с задержкой 20 мс и счётчиком запросов.

Локальный кеш быстрее, распределённый согласованнее между экземплярами

Часто их сочетают: небольшой локальный кеш с коротким TTL перед Redis снимает нагрузку с сети для самых горячих ключей, а Redis держит общую копию. Цена — два уровня устаревания: локальная копия может пережить удаление в Redis на свой TTL. Поэтому локальный уровень оставляют для данных, где секунды устаревания допустимы: справочники, настройки, тарифы с плавным переходом.

Cache-aside заполняет кеш по промаху, а остальные стратегии прячут кеш за слоем данных

static String get(String key, long ttlSec) {
    String v = redis.get(key);
    if (v != null) return v;                                // Попадание.
    v = dbRead(key);                                        // Промах: читаем базу...
    redis.set(key, v, SetParams.setParams().ex(ttlSec));    // ...и кладём в кеш со сроком.
    return v;
}
== cache-aside read 1: 2.0% in 31.1 ms, db reads 1
== cache-aside read 2: 2.0% in 0.5 ms, db reads 1
== cache-aside read 3: 2.0% in 0.4 ms, db reads 1

Первое чтение — промах: 20 мс базы плюс сеть до Redis. Следующие — попадания за полмиллисекунды, база больше не нужна. Cache-aside прост и устойчив: если Redis недоступен, приложение может читать базу напрямую. Кеш наполняется только тем, что реально читают.

Write-behind заманчив скоростью записи, но превращает кеш в основное хранилище: падение узла до сброса в базу теряет данные. Для денег его не используют. Write-through требует, чтобы запись в базу и в кеш не разошлась при сбое между ними, — та же проблема двойной записи, что и в Transactional Outbox.

Даже удаление ключа после обновления оставляет окно, в котором старое значение возвращается

Правильный порядок для cache-aside — сначала обновить базу, потом удалить ключ. Обратный порядок очевидно плох: между удалением и обновлением читатель успеет положить старое значение. Но и правильный порядок не спасает полностью. Демо воспроизводит гонку, расставив шаги в нужной последовательности:

== race: db=1.5%, cache=2.0%, ttl=3600 s

База и кеш разошлись на час. Окно узкое — читатель должен прочитать базу до записи и положить в кеш после удаления, — но под нагрузкой оно случается регулярно. Защиты разной силы. TTL — обязательная страховка: он ограничивает время расхождения, поэтому для данных, которые меняются, его выбирают по допустимой устарелости, а не «на всякий случай на сутки». Отложенное повторное удаление — удалить ключ ещё раз через секунду после записи — закрывает большинство гонок. Надёжнее всего версии: значение в кеше хранит версию строки, и запись в кеш разрешается только с версией не меньше текущей, атомарно через Lua-скрипт. Инвалидацию по CDC из журнала базы, как в Transactional Outbox, используют, когда изменения приходят из многих мест.

Истёкший популярный ключ отправляет в базу все запросы сразу

Пока ключ в кеше, база его не видит. В момент истечения все запросы, пришедшие за время одной загрузки, получают промах и идут в базу. Демо запускает 50 одновременных клиентов на пустой ключ:

// Один загружает, остальные ждут значения в кеше.
if ("OK".equals(redis.set("lock:" + key, token, SetParams.setParams().nx().px(2000)))) {
    v = redis.get(key);                       // Перепроверить: пока ждали, могли загрузить.
    if (v != null) return v;
    v = dbRead(key);
    redis.set(key, v, SetParams.setParams().ex(60));
}
sleep(5);                                     // Кто-то уже грузит: подождать и проверить кеш.
== stampede, 50 concurrent misses, no protection: db reads 50, all answered in 33 ms
== stampede, 50 concurrent misses, SET NX lock: db reads 1, all answered in 41 ms

Без защиты — 50 одинаковых запросов в базу. С блокировкой SET NX PX загружает один клиент, остальные ждут несколько миллисекунд и читают готовое значение — один запрос. Перепроверка кеша после захвата блокировки важна: в первом варианте демо без неё база получила 2 запроса, потому что второй клиент захватил блокировку, уже освобождённую первым, и загрузил ключ повторно. Срок блокировки PX нужен на случай, если загрузчик упадёт: без него ключ останется заблокированным навсегда.

Есть и другие приёмы. Внутри одного экземпляра одновременные промахи схлопывает сам кеш — sync=true в Spring или LoadingCache в Caffeine. Stale-while-revalidate отдаёт старое значение, пока одно фоновое обновление загружает новое: пользователь не ждёт вовсе. Вероятностное раннее обновление обновляет ключ чуть раньше истечения со случайной вероятностью, растущей к концу срока. И разброс TTL: если десять тысяч ключей положили одной пачкой с TTL ровно 3600, они истекут в одну секунду; добавка случайных ±10 % размазывает истечение.

Кешируют то, что часто читают и редко меняют, и меряют долю попаданий

Кеш окупается, когда доля попаданий высокая, а цена промаха большая: тарифы, справочники, профили, результаты тяжёлых запросов. Данные, которые читают один раз или меняют чаще, чем читают, только тратят память и добавляют расхождений. Hit ratio — главная метрика кеша; если он ниже 80–90 %, кеш, скорее всего, не на своём месте или TTL слишком короткий.

Две атаки на кеш стоит учесть заранее. Запросы несуществующих ключей — /merchants/m-999999 — всегда промахиваются и всегда идут в базу; их кешируют как «нет значения» с коротким TTL. И кеш не должен становиться единственной опорой: если Redis упал, а база рассчитана только на 5 % промахов, она ляжет следом. Ёмкость базы планируют с учётом холодного кеша, а к Redis ставят таймауты и предохранитель, как в Resilience Patterns.

Если при обновлении удалять ключ из кеша, кеш не будет отдавать устаревшие данные.

Удаление закрывает только обычный случай. Читатель, прочитавший базу до обновления и записавший в кеш после удаления, вернёт старое значение, и оно проживёт весь TTL — в демо час. Нужны TTL по допустимой устарелости, повторное удаление или версионная запись в кеш.

  • Локальный кеш быстрее, распределённый общий для экземпляров; их сочетают с коротким TTL на локальном уровне.
  • Cache-aside: промах — база и запись в кеш со сроком; 31 мс против 0,5 мс в демо. Write-behind рискует потерей данных.
  • «Обновить базу, удалить ключ» оставляет гонку: устаревшее значение вернулось в кеш на час. TTL, повторное удаление, версии.
  • Stampede: 50 промахов — 50 запросов в базу; SET NX с перепроверкой — один. Ещё sync в процессе, stale-while-revalidate и разброс TTL.
  • Кешируют часто читаемое и редко меняемое; меряют hit ratio; кешируют отсутствие ключа; база должна пережить холодный кеш.

На собеседовании

Какие бывают стратегии кеширования?

Cache-aside: приложение читает кеш, при промахе — базу и кладёт результат в кеш; при записи обновляет базу и удаляет ключ. Read-through: загрузку при промахе делает сам кеш. Write-through: запись синхронно идёт в кеш и в базу. Write-behind: запись в кеш, в базу — асинхронно пачками, быстро, но с риском потерь. Write-around: запись только в базу, кеш наполняется при чтении.

  • Cache-aside переживает недоступность кеша: можно читать базу напрямую.
  • Write-through и write-behind — двойная запись со всеми её проблемами при сбоях.
  • Ключ удаляют, а не обновляют: обновление при конкурентной записи легко оставляет старое значение.

Как сохранить согласованность кеша и базы?

Полностью — никак, поэтому выбирают допустимую устарелость и задают по ней TTL. Порядок — обновить базу, затем удалить ключ. Остаётся гонка: читатель, прочитавший базу до обновления, может положить старое значение после удаления. Её закрывают повторным удалением через короткое время или версиями: в кеш пишут значение с версией строки и только если версия не меньше текущей.

  • Удаление после коммита транзакции, а не внутри неё: иначе читатель снова загрузит незакоммиченное старое.
  • Для изменений из многих источников — инвалидация по CDC из журнала базы.
  • Локальный кеш у каждого экземпляра требует рассылки инвалидаций, например через Redis Pub/Sub.
Что не так с обновлением тарифа? 
@Transactional
public void updateTariff(String merchant, BigDecimal rate) {
    redis.del("tariff:" + merchant);
    tariffs.update(merchant, rate);
}
// чтение: cache-aside, TTL 24 часа

Ключ удаляется до обновления и до коммита транзакции: читатель между удалением и коммитом прочитает из базы старый тариф и положит его в кеш на сутки. Нужно удалять после коммита (afterCommit или событие после транзакции), добавить повторное удаление или версионную запись и выбрать TTL по допустимой устарелости, а не сутки.

Что такое cache stampede и как с ним бороться?

Когда популярный ключ истекает, все запросы, пришедшие за время его загрузки, промахиваются и одновременно идут в базу. Защиты: блокировка на загрузку (SET NX с TTL в Redis или sync в локальном кеше), чтобы грузил один, а остальные ждали; stale-while-revalidate — отдавать старое, пока одно фоновое обновление грузит новое; разброс TTL, чтобы ключи не истекали одновременно.

  • После захвата блокировки кеш перепроверяют: без этого в демо вышло 2 загрузки вместо одной.
  • У блокировки обязателен срок на случай падения загрузчика.
  • Вероятностное раннее обновление снимает пик без блокировок.
  • Microsoft: Cache-Aside pattern — основа урока: заполнение по промаху, TTL, согласованность.
  • Facebook: Scaling Memcache at Facebook — leases против устаревших записей и stampede.
  • Vattani et al.: Optimal Probabilistic Cache Stampede Prevention — вероятностное раннее обновление.
  • Redis: SET — опции NX, PX и EX.
