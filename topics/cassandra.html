Cassandra

Cassandra — распределённое хранилище без ведущего узла: все узлы равноправны, данные распределены по кольцу токенов, каждая партиция хранится на нескольких репликах. Таблицу проектируют под запрос: partition key определяет, на каких узлах лежат данные, clustering key — порядок строк внутри партиции, а запрос без partition key база отказывается выполнять. Уровень согласованности выбирается на каждый запрос: при R + W больше фактора репликации чтение видит последнюю запись. Запись — всегда upsert с меткой времени, удаление — tombstone, а условные операции IF NOT EXISTS идут через Paxos и стоят в несколько раз дороже.

Журнал событий платежей пишется без проблем, но найти платёж по id нельзя

Для журнала событий платёжной системы выбрали Cassandra: миллионы записей в минуту, несколько дата-центров, отказ узла не останавливает запись. Таблицу сделали по образцу реляционной, с первичным ключом по магазину и времени. Через месяц поддержка просит найти платёж по его id — запрос отклонён. Аналитики удаляют устаревшие события, и чтения начинают падать по таймауту. А во время учений с отключением двух узлов часть запросов вернула ошибку, хотя один узел с данными был жив.

Тема разбирает устройство Cassandra, моделирование под запрос, уровни согласованности, upsert и Paxos. Обзор моделей NoSQL и когда выбирать Cassandra — в Overview, consistent hashing — в Consistent Hashing, CAP и согласованность — в CAP & Consistency. Демо demo.sh работает с кластером из трёх узлов Cassandra 5.0.9 в Docker (скрипт setup.sh) через cqlsh и nodetool.

Все узлы равны, а партиция лежит на репликах, выбранных по токену

create keyspace pay with replication = {'class': 'NetworkTopologyStrategy', 'dc1': 3};
== replicas of partition (7, 2026-10-02)
172.25.0.3
172.25.0.4
172.25.0.2

Хеш partition key (Murmur3) даёт токен, а токены разделены между узлами кольца; каждый узел владеет несколькими участками (vnodes, здесь 16 на узел). Партиция хранится на узле-владельце и на следующих по кольцу — столько, сколько задаёт фактор репликации. При RF=3 на трёх узлах каждая партиция есть на всех трёх. Клиент может прийти к любому узлу, и тот станет координатором запроса: разошлёт его репликам и соберёт ответы. Нет primary, нет failover — отказ узла означает лишь, что реплик стало меньше.

Запись устроена как LSM-дерево: сначала в commit log для надёжности и в memtable в памяти, потом memtable сбрасывается на диск неизменяемым файлом SSTable. Чтение собирает строку из memtable и нескольких SSTable, отсеивая лишние фильтрами Блума, а фоновая компакция сливает SSTable. Поэтому запись в Cassandra дешёвая и последовательная, а чтение дороже и зависит от компакции.

Таблицу проектируют под запрос: partition key выбирает узлы, clustering key — порядок

create table pay.payments_by_merchant (
    merchant_id int, day date, created_at timestamp, payment_id text, amount bigint,
    primary key ((merchant_id, day), created_at, payment_id)       -- партиция: магазин за день
) with clustering order by (created_at desc, payment_id asc);
== query by partition key: last 3 payments of merchant 7 for a day
 created_at                      | payment_id | amount
---------------------------------+------------+--------
 2026-10-02 10:05:00.000000+0000 |        p-5 |    500
 2026-10-02 10:04:00.000000+0000 |        p-4 |    400
 2026-10-02 10:03:00.000000+0000 |        p-3 |    300
(3 rows)
== query without partition key
<stdin>:1:InvalidRequest: Error from server: code=2200 [Invalid query] message="Cannot execute this query as it might involve data filtering and thus may have unpredictable performance. If you want to execute this query despite the performance unpredictability, use ALLOW FILTERING"

Первичный ключ состоит из двух частей. Partition key (merchant_id, day) — все платежи магазина за день лежат вместе на одних репликах. Clustering key created_at, payment_id — порядок строк внутри партиции на диске, поэтому «последние три платежа» читаются подряд без сортировки. Запрос по сумме без partition key Cassandra отклонила: чтобы его выполнить, пришлось бы опросить все партиции на всех узлах. ALLOW FILTERING разрешает это, но на проде это полный обход кластера.

Отсюда правило моделирования: сначала перечисляют запросы, потом под каждый делают таблицу. Поиск платежа по id — отдельная таблица payments_by_id с partition key payment_id, и приложение пишет в обе; batch с обеими вставками гарантирует, что обе применятся со временем, но не изоляцию. День в partition key ограничивает размер партиции: без него все платежи крупного магазина за годы оказались бы в одной огромной партиции на одних и тех же трёх узлах. Партиции держат в пределах десятков, максимум сотни мегабайт.

Уровень согласованности выбирают на запрос, и R + W > RF даёт свежее чтение

== consistency levels with two of three replicas down
-- CONSISTENCY ONE
 count
-------
     5
(1 rows)
-- CONSISTENCY QUORUM
<stdin>:1:NoHostAvailable: ('Unable to complete the operation against any hosts', {<Host: 127.0.0.1:9042 dc1>: Unavailable('Error from server: code=1000 [Unavailable exception] message="Cannot achieve consistency level QUORUM" info={\'consistency\': \'QUORUM\', \'required_replicas\': 2, \'alive_replicas\': 1}')})

С двумя остановленными узлами из трёх чтение с ONE получило ответ от единственной живой реплики, а QUORUM требует двух и сразу отказал: required_replicas: 2, alive_replicas: 1. Это ошибки из истории с учениями. Выбор уровня — компромисс: QUORUM на запись и чтение даёт R + W = 4 > 3, и чтение гарантированно видит последнюю подтверждённую запись, а кластер переживает потерю одного узла. ONE быстрее и доступнее, но может вернуть устаревшее. В нескольких дата-центрах используют LOCAL_QUORUM, чтобы не ждать межконтинентальную сеть.

Реплики сходятся несколькими механизмами: координатор сохраняет подсказки для недоступной реплики и дошлёт их, когда она вернётся (hinted handoff); чтение с несколькими репликами чинит отстающую (read repair); регулярный nodetool repair сверяет реплики полностью. Без регулярного repair удалённые данные могут «воскреснуть».

Любая запись — upsert с меткой времени, условная — через Paxos

== INSERT is an upsert: same primary key, new amount
 payment_id | amount
------------+--------
        p-1 |    999
(1 rows)
== lightweight transaction: insert only if absent
 [applied]
-----------
      True
 [applied] | key  | payment_id
-----------+------+------------
     False | k-42 |      p-100

INSERT с существующим первичным ключом не дал ошибки: он перезаписал сумму. В Cassandra INSERT и UPDATE — одна операция upsert, а конфликт между репликами решается по метке времени: побеждает более поздняя запись (last write wins). Если часы узлов расходятся, «более поздней» может оказаться не та запись. Проверка «нет ли уже такого платежа» обычным SELECT перед INSERT не защищает от гонки — это потерянное обновление из ACID & Isolation без всяких транзакций.

Для таких проверок есть lightweight transactions: INSERT ... IF NOT EXISTS или UPDATE ... IF balance = 100. Первый ключ идемпотентности записан, второй отклонён с текущим значением — как уникальное ограничение. Внутри это протокол Paxos между репликами: несколько кругов сообщений вместо одного, поэтому LWT в разы медленнее и применяется точечно — ключи идемпотентности, резервирование. Полноценные транзакции на протоколе Accord (CEP-15) разрабатываются для следующих версий и в 5.0 не входят.

Удаление записывает tombstone — пометку об удалении, которая хранится не меньше gc_grace_seconds (10 дней), чтобы дойти до всех реплик. Чтение должно пропустить все tombstone в партиции, и таблица-очередь, где строки постоянно удаляются, превращается в кладбище: после 100 тысяч tombstone в одном запросе Cassandra прерывает его. Это и было падение чтений после чистки. Для данных с ограниченным сроком используют TTL и стратегию компакции по времени, а очереди в Cassandra не строят.

В Cassandra можно перенести реляционную схему и добавить индексы под новые запросы.

Запрос без partition key Cassandra отклоняет, потому что он требует обхода всего кластера; вторичные индексы спасают лишь отдельные случаи. Модель строят от запросов: таблица под каждый способ чтения, денормализация при записи, partition key с ограниченным размером партиции.

  • Кольцо без ведущего: токен partition key выбирает RF реплик; любой узел — координатор. Запись — LSM: commit log, memtable, SSTable.
  • Таблица под запрос: (merchant_id, day) — партиция, created_at — порядок; без partition key запрос отклонён.
  • CL на запрос: при двух упавших из трёх ONE ответил, QUORUM — Unavailable; R + W > RF даёт свежее чтение.
  • INSERT — upsert, LWW по меткам времени; IF NOT EXISTS через Paxos отклонил второй ключ; tombstone и очереди — антипаттерн.

На собеседовании

Как моделировать данные в Cassandra?

От запросов: для каждого способа чтения — своя таблица, где partition key соответствует условию равенства в запросе, а clustering key — порядку и диапазону. Данные денормализуют и пишут в несколько таблиц. Partition key выбирают так, чтобы партиции были ограничены по размеру и распределялись равномерно: например, магазин плюс день.

  • Запрос без partition key требует ALLOW FILTERING — обход кластера.
  • Logged batch гарантирует, что все записи применятся, но не изоляцию.
  • Большие и горячие партиции — главная причина проблем с производительностью.

Что такое уровни согласованности в Cassandra?

Сколько реплик должно ответить на запрос: ONE, QUORUM (большинство), ALL, LOCAL_QUORUM (большинство в своём дата-центре). Выбирается на каждый запрос. Если число реплик записи плюс чтения больше фактора репликации, чтение пересекается с записью и видит её: QUORUM + QUORUM при RF=3. Если живых реплик меньше уровня, запрос сразу получает Unavailable.

  • Hinted handoff, read repair и регулярный repair сводят реплики.
  • LWW по меткам времени зависит от синхронизации часов.
  • LOCAL_QUORUM избегает задержек между дата-центрами.
Что не так с этой таблицей для очереди выплат? 
create table payouts_queue (shard int, id timeuuid, payload text, primary key (shard, id));
-- воркеры: select ... where shard = 0 limit 100; затем delete каждой обработанной строки
-- consistency ONE для записи и чтения

Очередь с постоянными удалениями копит tombstone в одной партиции shard = 0, и чтения начинают пропускать сотни тысяч пометок, пока не упадут по лимиту. Одна партиция — один набор реплик и горячая точка. ONE на запись и чтение не гарантирует, что воркер увидит новую запись или удаление. Очереди строят на брокере сообщений, а в Cassandra хранят журнал с TTL и разбиением по времени.

Когда выбирать Cassandra?

Для огромного потока записи с известными заранее запросами по ключу: журналы, события, телеметрия, история операций; когда нужна работа в нескольких дата-центрах без ведущего узла и отказ узлов не должен останавливать запись. Не подходит для произвольных запросов, соединений, транзакций через сущности и очередей.

  • LWT для идемпотентности и резервирования, но они в разы дороже.
  • Аналитику по данным Cassandra выносят в Spark или отдельное хранилище.
