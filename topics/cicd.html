CI/CD

Непрерывная интеграция проверяет каждое изменение до слияния: сборка, тесты, анализ — быстро и одинаково для всех. Непрерывная поставка доводит проверенное изменение до продакшена одним и тем же артефактом. Три практических правила из демо. Кеш зависимостей делает конвейер быстрым: mvn verify с пустым локальным репозиторием — 53,6 с и 116 скачанных jar, с прогретым — 3,1 с. Сборка должна быть воспроизводимой: две сборки одного коммита дали разные jar, пока не задан project.build.outputTimestamp. И артефакт собирают один раз, а между окружениями продвигают тот же самый: перетегированный образ сохраняет digest, пересобранный для продакшена — уже другой, не тот, что проверяли.

На стенде работало, в продакшене — другой jar

Конвейер платёжного сервиса собирает образ для стенда, прогоняет на нём тесты, а для продакшена собирает образ заново из того же коммита — «чтобы с продакшен-настройками». За время между сборками вышла новая версия транзитивной зависимости, указанной диапазоном, и в продакшен уехал jar, который никто не тестировал. Конвейер к тому же шёл 20 минут, потому что каждый раз скачивал зависимости, и разработчики перестали ждать его перед слиянием.

Тема разбирает устройство конвейера и правила, которые делают его быстрым и надёжным. Демо cicd.sh работает с копией Maven-проекта из Testing Strategy: меряет кеш, проверяет воспроизводимость сборки и продвигает образ. Пример конвейера GitHub Actions — ci.yml: его YAML проверен разбором, но сам конвейер в демо не запускался. Выкатка в окружения — в Deployment Strategies, ветки и слияние — в Git.

Конвейер: быстрые проверки раньше, один артефакт дальше

      - uses: actions/setup-java@v5
        with: { distribution: temurin, java-version: '21', cache: maven }   # кеш ~/.m2 по хешу pom.xml
      - name: Build and unit tests
        run: mvn -B -Dproject.build.outputTimestamp=2026-10-01T00:00:00Z verify
...
  deploy-prod:
    needs: deploy-staging
    environment: production                                   # ручное подтверждение в настройках окружения

В GitHub Actions конвейер — workflow из jobs, в GitLab CI — pipeline из stages и jobs в .gitlab-ci.yml; принципы одинаковы. Отмена устаревших прогонов (concurrency с cancel-in-progress) экономит раннеры, когда в ветку пушат несколько раз подряд. Окружения с обязательным подтверждением отделяют выкатку в продакшен. Секреты хранят в хранилище CI и выдают только нужным job; лучше вовсе без долгоживущих ключей — через OIDC-доверие между CI и облаком.

Кеш зависимостей: 53 секунды против трёх

== mvn verify (compile + unit tests): cold vs warm dependency cache
   empty cache:   53.6 s, downloaded 116 jars, 58 MB
   warm cache:     3.1 s

Чистый раннер начинает с пустым локальным репозиторием Maven: на этом небольшом проекте с JUnit, Mockito, AssertJ и H2 сборка скачала 116 jar на 58 МБ и заняла 53,6 секунды, из которых сама компиляция и тесты — около трёх. С прогретым кешем — 3,1 секунды. Кеш привязывают к хешу pom.xml: изменились зависимости — кеш строится заново, не изменились — восстанавливается. Тот же принцип в Docker-сборке: слой зависимостей до слоя кода, как в Docker. Быстрый конвейер — не роскошь: если проверка идёт 20 минут, её перестают ждать, а изменения копятся пачками.

Воспроизводимая сборка и «собрал один раз»

== the same commit built twice
   default:                   bf3c47c2afa6 vs e9a7c303d490 -> different
   with outputTimestamp:      3b03aa40b3e2 vs 3b03aa40b3e2 -> identical
== build once, promote the same image
   kb-ci:sha-1a2b3c   8a9a2a54e8a6
   kb-ci:staging      8a9a2a54e8a6
   kb-ci:prod         8a9a2a54e8a6
   rebuilt for prod: 097c4a5a57c0 (another artifact than the one tested)

Два mvn package одного коммита с паузой в 2 секунды дали jar с разными хешами: внутри архива записано время изменения каждого файла. С -Dproject.build.outputTimestamp Maven ставит всем записям одно время, и сборки совпали байт в байт. Воспроизводимость позволяет проверить, что артефакт действительно собран из этого коммита, и сравнивать артефакты по хешу.

Но даже воспроизводимая сборка не гарантирует того же результата завтра: зависимости с диапазонами версий, плагины без зафиксированной версии и обновлённый базовый образ меняют результат. Поэтому артефакт собирают один раз и продвигают: теги staging и prod указывают на тот же образ с digest 8a9a2a54e8a6, а образ, пересобранный для продакшена, — уже другой (097c4a5a57c0), которого никто не тестировал. Тег по коммиту неизменяем; тег latest в манифестах не используют — он не говорит, что именно запущено, и меняется под ногами.

Пересобрать образ для продакшена из того же коммита — то же самое, что взять образ со стенда.

Даже две сборки одного коммита дали разные jar без outputTimestamp, а со временем меняются зависимости и базовые образы. Пересобранный образ получил другой digest. В продакшен продвигают тот самый артефакт, что прошёл проверки, — по тегу коммита или digest.

Защита ветки main делает проверки обязательными: слияние только через pull request, только при зелёных обязательных проверках и одобренном ревью, без force push. Merge queue (очередь слияния в GitHub, merge trains в GitLab) проверяет изменение уже поверх актуального main вместе с соседними изменениями в очереди — иначе два PR, каждый зелёный по отдельности, вместе ломают main.

Главный враг конвейера — нестабильные тесты. Тест, который падает раз в двадцать прогонов без изменений кода, учит команду нажимать «перезапустить» и не читать красный статус — а потом пропускается настоящая ошибка. Такие тесты отправляют в карантин с задачей на исправление, а причины обычно одни и те же: зависимость от времени и порядка, общее состояние между тестами, ожидание фиксированным sleep вместо условия, как разобрано в Testing Strategy.

На собеседовании

Из чего состоит хороший CI/CD-конвейер для Java-сервиса?

На каждый pull request: сборка, модульные тесты, интеграционные тесты (Testcontainers), статический анализ и проверка зависимостей; слияние только при зелёных проверках и ревью. После слияния — сборка образа с тегом коммита, публикация в реестр, выкатка на стенд, смоук-тесты, продвижение того же образа в продакшен с подтверждением или автоматически по метрикам.

  • Кеш зависимостей и слоёв, отмена устаревших прогонов.
  • Воспроизводимая сборка, неизменяемые теги, продвижение по digest.
  • Секреты через OIDC, минимальные права job.
Что не так с этим конвейером? 
deploy-prod:
  steps:
    - run: mvn package -DskipTests
    - run: docker build -t registry/payments:latest . && docker push registry/payments:latest
    - run: kubectl set image deploy/payments app=registry/payments:latest
  env:
    PROD_DB_PASSWORD: ${{ secrets.PROD_DB_PASSWORD }}   # доступен всем шагам

Продакшен-образ собирается заново и без тестов — это не тот артефакт, что проверяли на стенде. Тег latest неизменяемым не является: по нему нельзя понять, что запущено, а kubectl set image с тем же тегом может вообще не перезапустить поды. Пароль базы доступен всем шагам, включая сборку со сторонними плагинами. Нужно: продвигать образ, собранный и проверенный раньше, по тегу коммита или digest; секреты — только шагу выкатки или вовсе в кластере, а не в CI.

Как ускорить конвейер?

Кеш зависимостей по хешу файлов сборки и кеш слоёв Docker; быстрые проверки раньше медленных; параллельные job для независимых проверок; отмена устаревших прогонов; запуск только затронутых модулей в монорепозитории. В демо кеш зависимостей сократил сборку с 53,6 до 3,1 секунды.

  • Разделение тестов по шардам на нескольких раннерах.
  • Нестабильные тесты — карантин и исправление, иначе им перестают верить.

Почему артефакт собирают один раз и продвигают, а не пересобирают для каждого окружения?

Пересборка даёт другой артефакт: время в архивах, плавающие версии зависимостей, обновлённый базовый образ. В продакшене окажется не то, что тестировали. Поэтому собирают один раз, публикуют с неизменяемым тегом коммита и продвигают тот же образ, меняя только конфигурацию окружения.

  • outputTimestamp и зафиксированные версии делают сборку воспроизводимой.
  • Подпись образов и проверка происхождения (SLSA, cosign).
  • Jez Humble, David Farley, «Continuous Delivery» — один артефакт и конвейер развёртывания.
  • Maven: Reproducible Builds — project.build.outputTimestamp.
  • GitHub Actions, GitLab CI/CD.
  • SLSA — происхождение и целостность артефактов.
