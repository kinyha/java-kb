Classes & Objects

Класс описывает состояние и поведение, объект — экземпляр в куче, с которым код работает только через ссылки. Ссылки передаются по значению, поэтому метод может изменить объект, но не может подменить переменную вызывающего. Создание объекта идёт в строгом порядке. Сначала один раз инициализируется класс: static-поля и static-блоки, от родителя к потомку, лениво, при первом активном использовании. Потом для каждого объекта: память обнуляется, вызывается конструктор родителя, затем инициализаторы полей и блоки этого класса, затем тело конструктора. Компилятор буквально копирует инициализаторы полей в каждый конструктор, вызывающий super(). Из этого порядка следуют ловушки: переопределённый метод из конструктора видит null, а static-поле — одно на класс и общее для всех потоков. final запрещает переприсвоить ссылку, но не защищает содержимое объекта.

Объект, ссылка и передача по значению

static void applyFee(Payment p) { p.amount += 15; }          // меняет объект по копии ссылки
static void replace(Payment p)  { p = new Payment(0); }       // меняет только локальную копию ссылки

Payment p = new Payment(1000);
applyFee(p);
replace(p);
== references are passed by value
after applyFee: 1015
after replace:  1015

new Payment(1000) создаёт объект в куче и возвращает ссылку на него; переменная p хранит ссылку, а не объект. Java всегда передаёт аргументы по значению: метод получает копию ссылки. Через копию можно изменить тот же объект — applyFee увеличил сумму, вызывающий код это видит. Присвоить копии новую ссылку тоже можно, но это меняет только локальную переменную метода: после replace у вызывающего прежний объект с суммой 1015. Отсюда и ответ на частый вопрос «передача по ссылке или по значению»: по значению, а значение переменной объектного типа — ссылка.

Из того же следует, почему изменяемый объект, отданный наружу, — риск: любой, у кого есть ссылка, может его поменять. Об этом — в Encapsulation. Устройство объекта в памяти — заголовок, поля, выравнивание — разобрано в Object Layout, а методы, которые есть у каждого объекта, — в Object Methods.

Порядок инициализации класса и объекта

Платёжная карта Card наследует Base. У обоих есть static-поле и static-блок, поле экземпляра с инициализатором, блок экземпляра и конструктор. Конструктор Base вызывает переопределяемый describe(). Демо InitOrderDemo.java печатает каждый шаг:

static class Base {
    static String S1 = log("Base static field");
    static { log("Base static block"); }
    String f1 = log("Base instance field");
    { log("Base instance block"); }
    Base() { log("Base constructor"); describe(); }      // виртуальный вызов из конструктора
    void describe() { log("Base.describe"); }
}
static class Card extends Base {
    static String S2 = log("Card static field");
    static { log("Card static block"); }
    private final String mask = log("Card instance field");
    { log("Card instance block"); }
    Card() { super(); log("Card constructor, mask = " + mask); }
    @Override void describe() { log("Card.describe sees mask = " + mask); }
}

Вызов переопределяемого метода из конструктора — известная ловушка из Polymorphism: подкласс работает с полуготовым объектом, и даже final-поле там ещё null. В конструкторе вызывают только private, static или final-методы. Отдавать this наружу из конструктора — регистрировать в слушателях, запускать с ним поток — так же опасно: другой код увидит объект до конца инициализации, а другой поток — ещё и без гарантий видимости полей из JMM.

Конструкторы, this() и куда попадают инициализаторы

public class Payment {
    private final String id;
    private final long amount;
    private String currency = "RUB";          // инициализатор поля
    { System.out.println("init block"); }       // блок инициализации экземпляра

    public Payment(String id, long amount, String currency) {
        this.id = id; this.amount = amount; this.currency = currency;
    }
    public Payment(String id, long amount) {
        this(id, amount, "RUB");                // делегирование: инициализаторы здесь не повторяются
    }
}

В байткоде нет отдельных «инициализаторов полей» и «блоков»: скрипт javap.sh показывает, что компилятор вставил их в конструктор <init> сразу после invokespecial Object.<init> — вызова super(), — а затем идёт тело. Если конструкторов, вызывающих super(), несколько, копия попадёт в каждый. Конструктор с this(...) инициализаторов не содержит: он делегирует, и они выполнятся один раз в вызванном конструкторе. Видно и лишнее: currency записан дважды — сначала "RUB" из инициализатора, потом значение из параметра.

Правила конструкторов следуют отсюда. this(...) или super(...) — первый оператор: объект родителя должен быть готов раньше всего остального (с JDK 25, JEP 513, перед вызовом разрешён код, который не читает this — например, проверка аргументов). Если конструктора нет, компилятор добавит конструктор без параметров с super(); если есть хоть один — не добавит, и это ломает фреймворки, которым нужен конструктор без аргументов, например JPA из JPA Basics. final-поле должно быть присвоено ровно один раз на каждом пути каждого конструктора — это проверяет компилятор. Много перегруженных конструкторов сводят к одному основному через this(...), а при большом числе необязательных параметров переходят на статическую фабрику или билдер из Creational Patterns.

static: одно на класс и ленивая инициализация

static class FeeCalculator {
    static long lastFee;                      // «временная» переменная, вынесенная в static
    long fee(long amount) {
        lastFee = amount / 100;
        Thread.onSpinWait();
        return lastFee;
    }
}
// 8 потоков, у каждого свой new FeeCalculator() и своя сумма
== static field shared by all instances and threads
wrong fees: > 0 out of 1600000

Static-поле принадлежит классу, а не объекту: оно одно на класс в загрузчике классов, и его видят все экземпляры и все потоки. В демо каждый поток создал собственный FeeCalculator, но поле lastFee общее, и потоки перезаписывают значения друг друга — часть комиссий посчитана для чужой суммы. Тот же дефект в Spring возникает с полем экземпляра синглтон-бина из Bean Scopes: бин один на приложение. Static уместен для констант, чистых функций без состояния и фабричных методов. Изменяемое static-состояние — глобальная переменная: его трудно тестировать, оно переживает тесты и требует синхронизации.

Класс инициализируется лениво: при первом создании объекта, вызове static-метода, обращении к static-полю, при Class.forName или инициализации подкласса. Чтение Limits.MAX класс не инициализировало: static final int, заданный константным выражением, — константа времени компиляции, и компилятор подставил число 100000 прямо в код вызывающего. Поэтому если поменять константу в библиотеке и не пересобрать зависимые модули, они продолжат использовать старое значение. Integer BOXED — не константа, и обращение к нему запустило static-блок. Литерал Lazy.class класс загружает, но не инициализирует.

JVM гарантирует, что инициализация класса выполняется ровно один раз и потокобезопасно — под блокировкой класса. На этом построен ленивый потокобезопасный синглтон без synchronized и volatile — идиома holder: private static class Holder { static final Registry INSTANCE = new Registry(); }, объект создаётся при первом обращении к Holder.INSTANCE. Обратная сторона: исключение в static-инициализаторе делает класс непригодным навсегда — первый раз ExceptionInInitializerError, дальше NoClassDefFoundError при каждом обращении. Как классы загружаются и связываются — в JVM Architecture.

final и модификаторы доступа

== final reference, mutable contents
final list changed from outside: [p-1, p-2]

final у поля означает «присваивается один раз», а не «объект не меняется». В Batch поле ids — final, но список снаружи пополнили через геттер. Неизменяемость требует ещё неизменяемого содержимого и отсутствия утечек ссылок: List.copyOf, защитные копии — это тема Encapsulation. У final-полей есть и гарантия из модели памяти: после завершения конструктора их значения видны любому потоку, получившему ссылку на объект, даже без синхронизации, если this не утёк из конструктора. final-класс нельзя наследовать (String, records), final-метод нельзя переопределить, final-локальную переменную нельзя переприсвоить; лямбды захватывают только фактически final переменные.

Две детали, о которых спрашивают. protected открывает член всему пакету, а не только наследникам, и подкласс из другого пакета может обращаться к нему только через ссылку своего типа — не к чужому экземпляру родителя. private работает на уровне класса, а не объекта: метод equals читает приватные поля другого экземпляра того же класса. Package-private — недооценённый уровень: он скрывает детали реализации внутри пакета, не показывая их всему приложению. С Java 9 над этим стоят модули: public-класс неэкспортированного пакета снаружи модуля недоступен, как в Annotations & Reflection.

final-поле нельзя увидеть неинициализированным.

Можно, если читать его до присваивания: из переопределённого метода, вызванного конструктором родителя, или через this, утёкший из конструктора. В демо Card.describe увидел final-поле mask равным null.

  • Переменная хранит ссылку; аргументы передаются по значению — объект изменить можно, переменную вызывающего нельзя.
  • Класс инициализируется один раз и лениво: родитель, потом потомок; static-поля и блоки в порядке записи.
  • Объект: память обнулена → super() → инициализаторы и блоки → тело конструктора.
  • Инициализаторы полей компилятор копирует в каждый конструктор с super(); конструктор с this(...) их не содержит.
  • Переопределённый метод из конструктора видит null даже в final-поле.
  • Static-поле одно на класс: общее для всех экземпляров и потоков; константы времени компиляции подставляются в код.
  • final — одно присваивание, а не неизменяемость; protected открыт всему пакету.

На собеседовании

В каком порядке инициализируются класс и объект при наследовании?

При первом использовании класса один раз выполняется его статическая инициализация: сначала родителя, потом потомка; static-поля и static-блоки — в порядке записи. При создании объекта память обнуляется, конструктор потомка сразу вызывает конструктор родителя; родитель выполняет свои инициализаторы полей, блоки и тело конструктора; затем то же делает потомок.

  • Инициализаторы полей и блоки компилятор вставляет в каждый конструктор после super().
  • Виртуальный вызов из конструктора родителя видит неинициализированные поля потомка.
  • Инициализация класса потокобезопасна — на этом построена идиома holder.
Что напечатает этот код и почему? 
class Account {
    Account() { System.out.println(currency()); }
    String currency() { return "RUB"; }
}
class UsdAccount extends Account {
    private final String code = "USD-" + System.nanoTime() % 1;
    @Override String currency() { return code; }
}
new UsdAccount();

Напечатается null. Конструктор Account выполняется до инициализаторов полей UsdAccount, а currency() вызывается виртуально — версия UsdAccount, где code ещё не присвоен. Выражение для code не константное, поэтому компилятор не подставил его заранее. Если бы поле было private final String code = "USD", оно стало бы константой времени компиляции, currency() вернул бы подставленный литерал и напечатал USD. Исправление: не вызывать переопределяемые методы из конструктора.

Java передаёт аргументы по ссылке или по значению?

Всегда по значению. Для объектного типа значение — ссылка, поэтому метод получает копию ссылки: может изменить сам объект, и вызывающий это увидит, но присвоение параметру нового объекта меняет только локальную копию. Метод swap(a, b) для объектов в Java написать нельзя.

  • Отсюда риск отдать изменяемый объект наружу и защитные копии.
  • Примитивы копируются целиком; обёртки неизменяемы, поэтому ведут себя как значения.

Чем static отличается от поля экземпляра и когда инициализируется класс?

Static-поле одно на класс и общее для всех экземпляров и потоков; поле экземпляра — своё у каждого объекта. Static-метод не имеет this и не переопределяется, а скрывается. Класс инициализируется лениво — при создании объекта, вызове static-метода, обращении к неконстантному static-полю, Class.forName, инициализации подкласса.

  • Константы времени компиляции подставляются в код вызывающего и не инициализируют класс.
  • Ошибка в static-инициализаторе: ExceptionInInitializerError, затем NoClassDefFoundError.
  • Static одно на класс в загрузчике: два загрузчика — две копии.

Что означает final для поля, метода, класса и переменной?

Поле и переменную можно присвоить только один раз; final-поле обязано быть присвоено в каждом конструкторе. Метод нельзя переопределить, класс — наследовать. final не делает объект неизменяемым: final-список можно пополнять. Лямбды и анонимные классы захватывают только фактически final локальные переменные.

  • JMM: значения final-полей видны всем потокам после конструктора без синхронизации, если this не утёк.
  • static final с константным выражением — константа времени компиляции.

  • JLS §17.5 final Field Semantics, §6.6 Access Control.
