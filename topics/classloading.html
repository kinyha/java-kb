Class Loading

Сервис может стартовать, а упасть только на редком платеже

Платёжный сервис поднялся и принимает обычные платежи. Но обработка крупного перевода впервые обращается к RiskRules из отдельного JAR и получает NoClassDefFoundError. Успешный старт не доказывает, что все class-файлы приложения уже найдены: JVM загружает классы по мере необходимости.

У класса есть несколько разных состояний. Загрузить байты — не то же самое, что проверить их, подготовить статические поля и выполнить static-инициализацию. Ошибка может возникнуть в любом из этих мест. Поэтому при расследовании сначала выясни, что именно произошло и какой загрузчик искал класс.

В обычном сервисе стартовый класс загружает системный application class loader. Он ищет классы приложения в classpath или module path. Но библиотека, контейнер приложений или plugin может создать свой загрузчик, и тогда одинаковое имя класса не гарантирует, что это один и тот же тип.

Если приложение запустилось, все зависимости точно на месте.

JVM не обязана разрешить каждую ссылку при старте. Отсутствующий класс или метод может обнаружиться только при исполнении пути, который его использует. Прогон критичных сценариев в том же образе, что и прод, ловит это раньше клиента.

Загрузчик определяет, откуда брать байты и чьим станет класс

В JDK 21 есть bootstrap loader для базовых классов, platform loader для части платформенных модулей и system/application loader для приложения. String.class.getClassLoader() возвращает null: это обозначение bootstrap loader в Java API, а не отсутствие загрузки. Родитель application loader — platform loader; его родитель в API также null.

Объект загрузчика не просто читает файл. Он участвует в идентичности класса и держит набор уже загруженных типов. Когда Java-код ссылается на RiskRules, JVM получает class-файл через подходящий loader и создаёт объект Class, связанный с определившим его загрузчиком.

Выполни на JDK 21: String.class.getClassLoader() и ClassLoader.getPlatformClassLoader().getParent() дают null, а ClassLoader.getSystemClassLoader().getParent() == ClassLoader.getPlatformClassLoader() даёт true. Это способ проверить реальную иерархию, а не запоминать картинку без связи с API.

Стандартный loadClass спрашивает родителя раньше своего JAR

Алгоритм ClassLoader.loadClass(name, resolve) в исходниках JDK 21 начинается с findLoadedClass. Если класс уже загружен, второй раз байты не читаются. Иначе loader спрашивает родителя; лишь если тот не нашёл класс, вызывает собственный findClass. При resolve=true затем вызывается resolveClass.

Для java.lang.String запрос из application loader уйдёт вверх и завершится на bootstrap. Для RiskRules родители не найдут class-файл приложения, поэтому его определит application loader. Такой порядок не даёт случайному java.lang.String внутри JAR подменить базовый класс.

Parent delegation — поведение базового loadClass, а не непреложный закон JVM. Загрузчик может переопределить алгоритм, например для plugin isolation, но обязан учитывать ограничения на пакеты платформы и совместимость типов. В проде child-first без чёткой причины часто заканчивается двумя копиями одной библиотеки и ошибками приведения.

Одинаковое имя не делает классы одним типом

Представь два plugin-загрузчика, A и B. Каждый прочитал свои байты bank.RiskRules и сам определил класс. JVM различает эти классы по паре «бинарное имя + defining loader», поэтому объект из A нельзя привести к bank.RiskRules, который ожидает B, даже если байты одинаковые.

Отсюда и типичная проблема hot reload: старый loader удерживается ссылкой из thread, static cache или callback, а вместе с ним остаются его классы и метаданные. Разбор Metaspace и утечек — в «Memory Areas» и «Diagnostics». Здесь достаточно помнить: выгрузка класса связана с достижимостью его defining loader, а не с удалением JAR с диска.

Загрузка не равна static-инициализации

После получения байтов JVM делает linking: проверяет class-файл и байткод, подготавливает static-поля с начальными значениями, разрешает символические ссылки. Затем при первом активном использовании класса выполняется initialization: присваивания static-полей и блоки static {} в текстовом порядке. Для подкласса сначала инициализируется его суперкласс.

На этапе preparation поле fee ещё равно нулю. Константа LIMIT получает 100 из атрибута ConstantValue, а вызов initFee() относится к последующей initialization. Чтение compile-time константы может вообще не загружать Rules в момент чтения: значение встроено в вызывающий class-файл. Литерал Rules.class и Class.forName(name, false, loader) не инициируют класс; чтение Rules.fee инициирует.

public class LoadDemo {
    static class Rules {
        static final int LIMIT = 100;
        static int fee = initFee();
        static int initFee() {
            System.out.println("Rules init");
            return 5;
        }
    }
    static class Broken {
        static {
            if (true) throw new IllegalStateException("bad config");
        }
    }
    public static void main(String[] args) throws Exception {
        System.out.println("start");
        System.out.println(Rules.LIMIT);
        System.out.println(Rules.class.getSimpleName());
        Class.forName("LoadDemo$Rules", false, LoadDemo.class.getClassLoader());
        System.out.println(Rules.fee);
        for (int i = 0; i < 2; i++) {
            try { Class.forName("LoadDemo$Broken"); }
            catch (Throwable e) { System.out.println(e.getClass().getSimpleName()); }
        }
    }
}

Любое упоминание класса в коде запускает его static-блок.

Константа времени компиляции встраивается в вызывающий код; .class и Class.forName(..., false, ...) не инициируют initialization. Чтение обычного static-поля Rules.fee или Class.forName(name) инициирует.

Под капотом: однократность и сбой инициализации

JLS §12.4.2 описывает синхронизацию инициализации: один поток выполняет её, остальные ждут; повторно успешная инициализация не запускается. Если инициализация завершилась с ошибкой, класс помечается erroneous в этом loader. Поэтому перехватить первый ExceptionInInitializerError и просто повторить тот же вызов нельзя: нужен исправленный конфиг и новый процесс или новый defining loader.

При сбое смотри на фазу и источник загруженного класса

Ошибка поиска по имени (ClassNotFoundException) часто приходит из явного loadClass или Class.forName. NoClassDefFoundError при выполнении может означать отсутствующий class-файл, который был нужен для уже скомпилированной ссылки, либо класс с проваленной инициализацией. Поэтому одного простого названия исключения мало: читай cause и полный stack trace.

Включи -Xlog:class+load=info и найди интересующий класс и source. На JDK 21.0.11 после компиляции LoadDemo.java в /tmp лог содержит строки ниже; время и путь зависят от машины. Если класс пришёл из неожиданного JAR, исправляй classpath или конфликт версий, а не static-код класса.

[0.020s][info][class,load] LoadDemo$Rules source: file:/private/tmp/
[0.020s][info][class,load] LoadDemo$Broken source: file:/private/tmp/

Для диагностики имени класса в приложении выведи SomeClass.class.getClassLoader() и SomeClass.class.getProtectionDomain().getCodeSource(), учитывая, что для некоторых платформенных классов CodeSource может быть null. В plugin-системах сравни Class и loader обеих сторон приведения.

Этот урок объясняет поиск и жизненный цикл одного класса. Стек вызовов и heap — «Memory Areas», машинный код горячих методов — «JIT», команды для работающего процесса — «Diagnostics». Если задержка платежа вызвана базой или сетью, загрузчик классов здесь ни при чём: сначала нужен профиль запроса, а не флаги JVM.

  • JVM загружает классы по мере необходимости, поэтому ошибку зависимости можно увидеть после успешного старта.
  • Стандартный loadClass проверяет уже загруженное, затем родителя, затем ищет сам; child-first требует отдельной реализации.
  • Бинарное имя вместе с defining loader задаёт тип. Два plugin-loader'а могут создать несовместимые классы с одним именем.
  • Loading, linking и initialization — разные фазы. Константа и class literal не обязаны запускать static-блок.
  • После провала static-инициализации класс остаётся ошибочным для этого loader; повторный доступ не перезапускает блок.

На собеседовании

Что такое parent delegation и зачем она нужна?

Стандартный ClassLoader.loadClass сначала проверяет, не загружен ли класс, потом спрашивает родителя и только при отказе ищет байты сам. Поэтому запрос java.lang.String из кода приложения заканчивается на bootstrap loader, а класс платежного сервиса определяет application loader.

Так системные классы не подменяются случайной копией из JAR. Если класс не находится, я проверяю classpath и то, какой loader сделал запрос: наличие файла на диске само по себе недостаточно.

  • Child-first возможен у кастомного loader, но разные копии общего API ломают приведения между plugin'ами.
  • findLoadedClass возвращает уже определённый класс, чтобы loader не создавал новый тип при повторном запросе.
В application JAR лежит свой java.lang.String. Какой класс получит стандартный loader?

Базовый java.lang.String от bootstrap loader. Application loader делегирует запрос родителю прежде, чем искать в своём JAR. Кроме того, определение классов пакета java.* ограничено.

Можно ли вообще обойти parent-first?

Можно переопределить loadClass в своём loader, как делают некоторые plugin-системы. Это требует явных правил: какие пакеты общие через родителя, какие изолированы. Иначе один и тот же интерфейс окажется двумя типами.

Когда запускается static-блок класса?

Static-блок выполняется при initialization класса после loading и linking, один раз для конкретного defining loader. Активное использование вроде чтения обычного static-поля, создания объекта или Class.forName(name) запускает инициализацию. Если это подкласс, сначала инициализируется суперкласс.

Поэтому в платёжном сервисе конфигурационный static-блок может упасть только при первом обращении к редкому пути, хотя приложение давно работает. Для поиска причины я смотрю исходное исключение внутри ExceptionInInitializerError.

  • Compile-time constant может быть встроена в вызывающий class-файл и не инициировать свой класс.
  • Class.forName(name, false, loader) загружает без initialization; Foo.class тоже не запускает static-блок.
  • JLS синхронизирует initialization: при конкурентном первом доступе только один поток выполняет код, остальные ждут.
В LoadDemo что напечатается до Rules init?

start, 100, Rules. Константа LIMIT встроена компилятором, а class literal не инициирует класс. Чтение Rules.fee запускает initialization.

Код использует static-блок для подключения к внешней базе. В чём риск?

Сбой БД при первом активном использовании оставит класс erroneous для этого loader. Повтор вызова не переинициализирует его, а даст NoClassDefFoundError. Инициализацию внешнего ресурса держи в управляемом жизненном цикле приложения с явной обработкой и повтором, а не в static-блоке класса.

Почему два класса с одинаковым полным именем могут дать ClassCastException?

Для JVM идентичность типа — бинарное имя вместе с определившим его class loader. Если два plugin-loader'а сами определили bank.RiskRules, это два типа даже при одинаковых байтах. Объект из одного нельзя привести к классу второго.

При такой ошибке я сравню loader у реального объекта и у ожидаемого типа. Общие интерфейсы plugin'ов должны загружаться общим родителем, чтобы обе стороны видели один объект Class.

  • В stack trace современных JVM часто указаны loader и module обоих несовместимых классов; это помогает увидеть проблему без дебаггера.
  • Ссылки на thread, static cache и callback могут удержать старый loader после hot reload и помешать выгрузке его классов.
Plugin A передал объект Payment в Plugin B; оба собраны из одного JAR, но cast упал. Что проверить?

Проверь object.getClass().getClassLoader() и Payment.class.getClassLoader() на стороне B. Если A и B определили тип разными loader'ами, это разные классы. Общий API подними в родительский loader, а реализации оставь изолированными.

Удаление старого JAR выгрузит его классы?

Нет. Классы связаны с defining loader, который может оставаться достижимым из потока или кеша. Выгрузка требует убрать удерживающие ссылки; сам файл на диске здесь не критерий.

Чем различаются ClassNotFoundException и NoClassDefFoundError?

ClassNotFoundException — проверяемое исключение при явном поиске имени, например через Class.forName или loadClass, когда loader его не нашёл. NoClassDefFoundError — ошибка линковки или доступа к классу во время исполнения: нужное определение недоступно либо предыдущая инициализация этого класса провалилась.

Поэтому я не угадываю по одному имени ошибки. Смотрю cause, исходный stack trace и источник class-файла в -Xlog:class+load=info: тогда видно, отсутствует JAR, загружена не та версия или упал static-блок.

  • После первого ExceptionInInitializerError повторный доступ к тому же классу через тот же loader даст NoClassDefFoundError, даже если class-файл лежит на месте.
  • NoSuchMethodError и NoSuchFieldError обычно указывают на несовместимую версию зависимости, найденную при разрешении символической ссылки.
В логах NoClassDefFoundError: Could not initialize class RiskRules. Инженер добавляет JAR. Верно?

Нет: сообщение говорит, что определение нашли, но инициализация раньше завершилась ошибкой. Найди первый ExceptionInInitializerError и его cause. Исправь причину и перезапусти процесс или создай новый loader; добавление JAR без этого не перезапустит static-блок.

Как узнать, из какого JAR пришёл класс?

Включи -Xlog:class+load=info и найди строку с именем и source. В коде можно посмотреть getProtectionDomain().getCodeSource(), но у платформенных классов источник не всегда доступен. Для конфликтов версий сравни этот путь с деревом зависимостей сборки.
