JVM: загрузка классов

Собранный сервис может не найти класс при запуске

Сервис платежей собрался, но на первом запросе упал с NoClassDefFoundError: библиотека была при компиляции, а в runtime classpath её нет. Компиляция проверила ссылки по доступным файлам; при работе JVM должна сама найти и загрузить нужный class-файл. Поэтому ошибка может появиться позже старта.

Чтобы разобрать такую аварию, разделяй три действия: loading находит определение класса, linking подготавливает его к исполнению, initialization выполняет static-инициализацию.

Класс определяется именем и загрузчиком

Загрузчик приложения ищет классы в classpath или module path. Перед собственной попыткой обычный ClassLoader делегирует запрос родителю: application → platform → bootstrap. Так приложение не подменяет стандартный java.lang.String своим файлом.

Для JVM идентичность класса — пара «бинарное имя + определивший загрузчик». Два плагина могут загрузить bank.Payment из разных JAR и получить два несовместимых класса. Поэтому при ClassCastException с одинаковыми именами проверь загрузчики обеих сторон.

Под капотом: initiating и defining loader

Загрузчик, которому пришёл запрос, может передать его родителю. Первый инициирует загрузку, а тот, кто вызвал defineClass, определяет класс. Для identity важен defining loader.

Linking проверяет и готовит класс до инициализации

После loading JVM проверяет формат байткода и правила типов (verification), выделяет статические поля с начальными значениями (preparation) и разрешает символические ссылки на классы, поля и методы (resolution). Разрешение отдельных ссылок может происходить лениво; нельзя считать, что весь граф зависимостей уже найден при старте.

Эти стадии объясняют разные ошибки: ClassNotFoundException — явный поиск не нашёл класс; NoClassDefFoundError — JVM не смогла получить определение, которое понадобилось программе; ExceptionInInitializerError — упал static-инициализатор.

Первое активное использование запускает static-код один раз

Чтение compile-time константы может не инициализировать класс: значение уже встроено в код вызывающего. Чтение обычного static-поля требует инициализации. JVM выполняет static-инициализаторы класса один раз при успешной инициализации, под синхронизацией, а повторное чтение использует готовое поле.

public class LoadDemo {
    static class Config {
        static final int LIMIT = 10;
        static int value = init();
        static { System.out.println("static block"); }
        static int init() {
            System.out.println("init value");
            return 7;
        }
    }
    public static void main(String[] args) {
        System.out.println(Config.LIMIT);
        System.out.println(Config.value);
        System.out.println(Config.value);
    }
}

Загрузчик решает изоляцию, но добавляет границы совместимости

Свой загрузчик полезен для плагинов и контейнеров приложений: разные версии библиотек могут жить отдельно. Цена — классы с одинаковым именем не становятся взаимозаменяемыми, а удержанный ClassLoader может удерживать все загруженные им классы и объекты через статические поля.

При обычном сервисе сначала проверь сборку JAR, classpath/module path и версии зависимостей. Собственный ClassLoader вводи только если нужна настоящая изоляция или загрузка кода из нового источника.

  • Loading находит байткод, linking проверяет и подготавливает класс, initialization выполняет static-код.
  • Обычная делегация идёт к родителю; identity класса включает определивший загрузчик.
  • Preparation ставит статическим полям значения по умолчанию, пользовательские инициализаторы работают позже.
  • Чтение compile-time константы может не запускать инициализацию класса.
  • Ошибки загрузки, связывания и static-инициализации требуют разных проверок.

На собеседовании

Чем отличаются loading, linking и initialization?

Loading находит class-файл и создаёт описание класса в JVM. Linking проверяет байткод, готовит статические поля и разрешает ссылки. Initialization выполняет static-инициализаторы и присваивания.

При сбое сервиса я сначала определяю стадию: отсутствующий JAR, несовместимый байткод и ошибка в static-блоке лечатся по-разному.

  • Resolution может быть ленивым; verification и preparation должны завершиться до initialization.
  • Повторная попытка использовать класс после неудачной initialization обычно даёт NoClassDefFoundError.
Когда value получит ноль?

На стадии preparation статическое поле int value получает 0. Его объявленный инициализатор выполнится позже, при initialization.

Загрузка всегда означает запуск static-блока?

Нет. Класс может быть загружен и связан до первого активного использования, которое запускает инициализацию.

Что такое parent delegation и зачем оно нужно?

Обычный загрузчик сначала просит родителя найти класс, а уже затем ищет его сам. Так стандартные классы платформы берутся из доверенного загрузчика и одна зависимость не определяется случайно разными загрузчиками.

В backend-плагинах я проверяю, кто определил класс: одинаковое имя не гарантирует совместимость, если defining loader разный.

  • Bootstrap loader не является обычным Java-объектом ClassLoader; getClassLoader() для его классов возвращает null.
  • Контейнеры и плагины могут нарушать обычный порядок делегации для изоляции зависимостей.
Почему два bank.Payment могут не приводиться друг к другу?

JVM считает типом пару «имя + defining loader». При разных загрузчиках это разные типы даже при одинаковом байткоде.

Кто грузит классы приложения?

Обычно application class loader. Platform и bootstrap обслуживают платформенные классы, но точный маршрут зависит от модулей и конфигурации запуска.

Когда выполняется static-инициализация?

Обычно при первом активном использовании класса: создании экземпляра, вызове static-метода или чтении обычного static-поля. JVM сначала инициализирует нужные родительские классы и выполняет инициализаторы данного класса в порядке объявления.

Я не кладу в static-блок сетевые вызовы: ошибка там может сделать класс непригодным для дальнейшего использования в процессе.

  • Чтение compile-time константы не обязательно запускает класс, потому что значение встраивается в вызывающий код.
  • Class.forName(name) по умолчанию инициализирует класс; перегрузка с initialize=false позволяет это отложить.
Что выведет LoadDemo из урока?

10, затем init value, static block, 7, 7. Константа встроена, а первое чтение value запускает инициализацию один раз.

Что будет после исключения из static-блока?

Первый вызов обычно получает ExceptionInInitializerError; последующие попытки использовать неуспешно инициализированный класс получают ошибку определения класса.
