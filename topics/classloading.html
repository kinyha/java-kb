JVM: Class Loading

Класс грузится, когда впервые понадобился, — и там же может упасть

Платёжный сервис после деплоя прошёл все проверки: health зелёный, мелкие платежи проходят. Через час приходит первый крупный перевод, и сервис отвечает ошибкой NoClassDefFoundError: RiskRules. Класс правил антифрода лежал в отдельном risk.jar, и этот JAR не попал в образ.

Почему упало не при старте? Потому что JVM не загружает все классы приложения заранее. Класс ищут в момент, когда код впервые к нему обращается. Пока ни один платёж не дошёл до ветки антифрода, отсутствие JAR никто не заметил.

public class Lazy {
    // Правила антифрода: в сервисе они лежат в отдельном risk.jar
    static class RiskRules {
        static boolean allow(long amount) { return amount < 1_000_000; }
    }

    public static void main(String[] args) {
        long amount = Long.parseLong(args[0]);
        System.out.println("платёж " + amount);
        // RiskRules нужен только крупным платежам:
        // пока ветка не выполнилась, JVM этот класс даже не ищет
        if (amount > 100_000) {
            System.out.println("антифрод: " + RiskRules.allow(amount));
        }
    }
}

Этим занимаются загрузчики классов. Чтобы разбирать такие аварии, нужно знать четыре вещи: какие загрузчики есть, в каком порядке они ищут класс, через какие этапы проходит класс после загрузки и почему одно имя может означать два разных класса. Об этом следующие шаги.

Чтобы ловить такие ошибки до клиента, прогоняй критичные сценарии на том же образе, что уйдёт в прод. Проверки health и smoke-тест на мелком платеже редкую ветку не заденут.

Три встроенных загрузчика, у каждого свой источник классов

Загрузчик класса — объект, который по имени класса находит его байты и превращает их в объект Class. В JDK 21 их три, и они выстроены цепочкой через ссылку parent.

Проверить цепочку можно из кода. Запускай пример через javac и java -cp, а не командой java Loaders.java: в режиме исходника класс грузит отдельный MemoryClassLoader лаунчера, и цепочка станет на одно звено длиннее.

public class Loaders {
    public static void main(String[] args) {
        // Класс приложения: его определил загрузчик приложения
        ClassLoader app = Loaders.class.getClassLoader();
        System.out.println(app.getName());
        // Родитель app — platform, у platform родитель bootstrap,
        // но bootstrap живёт внутри JVM, и в Java он выглядит как null
        System.out.println(app.getParent().getName());
        System.out.println(app.getParent().getParent());
        // java.sql — модуль платформы, его грузит platform
        System.out.println(java.sql.Connection.class.getClassLoader().getName());
        // java.lang.String из java.base — bootstrap, поэтому снова null
        System.out.println(String.class.getClassLoader());
    }
}

Под капотом: что было до Java 9

До модулей цепочка выглядела так: bootstrap читал rt.jar, extension loader — каталог lib/ext, application loader — classpath. В Java 9 платформу разрезали на модули, rt.jar и lib/ext исчезли, а extension loader заменил platform loader. Часть модулей, которые раньше грузил bootstrap, переехала в platform: так у них стало меньше привилегий. На собеседовании про «extension class loader» ещё спрашивают — отвечай, что в современных JDK его место занял platform.

Загрузчик сначала спрашивает родителя и только потом ищет сам

Порядок поиска задаёт метод ClassLoader.loadClass. Ниже — его логика из исходников JDK 21, без блокировок и замеров времени. Так ищут все загрузчики, унаследованные от ClassLoader: URLClassLoader, загрузчики Tomcat и Spring Boot, твои собственные.

protected Class<?> loadClass(String name, boolean resolve) throws ClassNotFoundException {
    // 1. Этот загрузчик уже загружал класс с таким именем? Тогда вернуть тот же Class
    Class<?> c = findLoadedClass(name);
    if (c == null) {
        try {
            // 2. Спросить родителя. parent == null означает bootstrap: его спрашивают отдельным методом
            c = (parent != null) ? parent.loadClass(name, false)
                                 : findBootstrapClassOrNull(name);
        } catch (ClassNotFoundException e) {
            // родитель не нашёл — это нормально, идём дальше
        }
        if (c == null) {
            // 3. Только теперь искать в своём источнике: JAR, каталог, сеть
            c = findClass(name);   // внутри читает байты и вызывает defineClass
        }
    }
    if (resolve) resolveClass(c);
    return c;
}

Проследи по шагам, что происходит, когда сервис впервые обращается к RiskRules.

Зачем такой обход, если класс всё равно лежит в JAR приложения? Ради двух гарантий. Первая: системный класс нельзя подменить. Запрос java.lang.String оборвётся на шаге 4, потому что bootstrap найдёт его в java.base, и до risk.jar очередь не дойдёт. Вторая: каждый класс платформы существует в процессе в одном экземпляре, и объекты String из разных библиотек совместимы между собой.

Под капотом: встроенные загрузчики знают про модули

App и platform в JDK 9+ — наследники jdk.internal.loader.BuiltinClassLoader, и у них своя версия поиска, loadClassOrNull. Сначала загрузчик смотрит, не принадлежит ли пакет класса именованному модулю платформы. Если принадлежит, запрос уходит сразу загрузчику этого модуля: java.sql.Connection app отдаст прямо platform, java.lang.String — прямо bootstrap. Классическая цепочка через родителей работает для классов без модуля, то есть для всего classpath, как RiskRules на схеме. Ещё одно отличие: не найдя класс, встроенный загрузчик возвращает null, а не бросает ClassNotFoundException, — поэтому на схеме вниз идёт null.

Если положить свой java.lang.String в JAR и написать свой загрузчик, можно подменить системный класс.

Определить класс в пакете java.* может только bootstrap. Любой другой загрузчик на defineClass получит SecurityException: Prohibited package name: java.lang. Проверено на JDK 21.

После загрузки класс проходит связывание и инициализацию

Найти байты — только начало. Между «класс загружен» и «можно вызвать метод» JVM проходит три этапа, и на каждом свои ошибки. Если знаешь, на каком этапе что ломается, по названию исключения сразу понятно, где искать.

Loading находит байты и создаёт Class. Если байтов нет, получаешь ClassNotFoundException при явном поиске или NoClassDefFoundError, если на класс ссылался скомпилированный код. Сюда же относится проверка версии class-файла: слишком новый файл даёт UnsupportedClassVersionError.

Linking состоит из трёх частей. Verify проверяет, что байткод не нарушает правил JVM: типы на стеке сходятся, переходы не выходят за метод. Prepare выделяет static-поля и ставит им нули: USD пока равен 0.0. Resolve превращает символические ссылки в реальные методы и поля, обычно лениво, при первом использовании. Если в библиотеке другой версии нужного метода нет, падает NoSuchMethodError.

Initialization выполняет код: инициализаторы static-полей и блоки static {} в порядке их записи в исходнике. Компилятор собирает их в один метод <clinit>. Если он бросил исключение, JVM заворачивает его в ExceptionInInitializerError и запоминает, что класс ошибочный.

public class BrokenInit {
    static class FxRates {
        // Инициализатор поля — часть static-инициализации класса
        static final double USD = load();

        static double load() {
            throw new IllegalStateException("rates.yaml not found");
        }
    }

    public static void main(String[] args) {
        for (int attempt = 1; attempt <= 2; attempt++) {
            try {
                System.out.println(FxRates.USD);   // первое чтение запускает инициализацию
            } catch (Throwable e) {
                System.out.println(attempt + ": " + e);        // тип ошибки и её сообщение
                if (e instanceof ExceptionInInitializerError) {
                    System.out.println("   причина: " + e.getCause());
                }
            }
        }
    }
}

Вторая попытка не запускает инициализацию заново: класс уже помечен ошибочным. В проде это выглядит коварно. Первая ошибка с настоящей причиной случилась один раз, при старте или на первом запросе. А дальше в логах сотни одинаковых NoClassDefFoundError, и кажется, будто класса нет в JAR.

Не клади в static-инициализацию то, что может временно не сработать: чтение файла, запрос в сеть или базу. Одна неудача делает класс непригодным до перезапуска процесса. Такие вещи место в бине с нормальной обработкой ошибок и повторами.

Инициализацию запускает только активное использование

Когда именно выполнится <clinit>, JLS описывает точно: при первом активном использовании класса. Это создание объекта через new, вызов static-метода, чтение или запись static-поля, Class.forName(name) и инициализация подкласса. Всё остальное класс не инициализирует, даже если выглядит как обращение к нему. На собеседовании любят именно эти исключения.

public class InitRules {
    static class Limits {
        static final long MAX = 1_000_000;           // compile-time константа
        static final Long BOXED = 500_000L;          // final, но не константа: Long — объект
        static long daily = log("Limits");           // обычное static-поле
    }
    static class Base { static int fee = log("Base"); }
    static class Card extends Base { static int cashback = log("Card"); }

    static int log(String name) {
        System.out.println("  init " + name);        // печатается из static-инициализации
        return 1;
    }

    public static void main(String[] args) throws Exception {
        ClassLoader loader = InitRules.class.getClassLoader();
        System.out.println("MAX");
        long max = Limits.MAX;                       // javac уже подставил 1_000_000 в этот класс
        System.out.println(".class");
        Class<?> type = Limits.class;                // ссылка на Class: загрузка без инициализации
        System.out.println("массив");
        Limits[] slots = new Limits[3];              // создаётся массив, а не объект Limits
        System.out.println("loadClass");
        loader.loadClass("InitRules$Limits");        // только загрузка
        System.out.println("BOXED");
        Long boxed = Limits.BOXED;                   // чтение настоящего поля: первое активное использование
        System.out.println("Card.fee");
        int fee = Card.fee;                          // поле объявлено в Base, инициализируется только Base
        System.out.println("Card.cashback");
        int cashback = Card.cashback;                // собственное поле Card: теперь и Card
    }
}

Инициализация класса — готовая ленивая и потокобезопасная загрузка

JVM выполняет <clinit> ровно один раз и под блокировкой класса: если два потока одновременно обратились к классу, второй ждёт, пока первый закончит. На этом построена идиома holder — ленивое значение без synchronized и volatile.

public class RatesDemo {
    static class FxRates {
        // Holder грузится при первом вызове usd(), а не при старте FxRates
        private static class Holder {
            static final double USD = load();       // JVM выполнит это один раз, под своей блокировкой
        }

        static double usd() { return Holder.USD; }

        private static double load() {
            System.out.println("загружаем курсы");  // дорогая операция: файл, сеть, база
            return 92.5;
        }
    }

    public static void main(String[] args) {
        System.out.println("сервис стартовал");
        System.out.println(FxRates.usd());          // первый вызов: инициализация Holder
        System.out.println(FxRates.usd());          // дальше — готовое значение
    }
}

Под капотом: как устроена блокировка инициализации

JLS §12.4.2 описывает процедуру по шагам. У каждого класса есть состояние: не инициализирован, инициализируется таким-то потоком, инициализирован, ошибочный. Поток, который застал класс в состоянии «инициализируется другим», ждёт. Тот же поток при рекурсивном обращении проходит сразу: поэтому внутри своего <clinit> класс может увидеть собственные поля ещё нулями. А два класса, которые в static-инициализации обращаются друг к другу из разных потоков, могут заблокировать друг друга навсегда. Такой deadlock не найти поиском synchronized по коду: потоки ждут друг друга внутри static-инициализации.

Класс — это имя плюс загрузчик, который его определил

Для JVM класс опознаётся не по имени, а по паре «полное имя + defining loader». Пока в процессе один загрузчик приложения, разница незаметна. Она всплывает там, где загрузчиков несколько: в плагинах, веб-контейнерах, при горячей перезагрузке.

Проверим на плагине антифрода. Скомпилируй правила отдельно, в каталог plugin-out, и загрузи их двумя независимыми загрузчиками.

public class RiskRules {
    public boolean allow(long amount) { return amount < 1_000_000; }
}
import java.net.URL;
import java.net.URLClassLoader;
import java.nio.file.Path;

public class TwoLoaders {
    public static void main(String[] args) throws Exception {
        URL[] plugin = { Path.of("plugin-out").toUri().toURL() };
        // Два независимых загрузчика читают один и тот же каталог.
        // parent = null: делегировать некому, кроме bootstrap
        ClassLoader a = new URLClassLoader("plugin-a", plugin, null);
        ClassLoader b = new URLClassLoader("plugin-b", plugin, null);

        Class<?> rulesA = a.loadClass("RiskRules");
        Class<?> rulesB = b.loadClass("RiskRules");
        System.out.println(rulesA.getName().equals(rulesB.getName()));  // имена одинаковые
        System.out.println(rulesA == rulesB);                           // а классы?

        Object fromA = rulesA.getDeclaredConstructor().newInstance();
        System.out.println(rulesB.isInstance(fromA));                   // объект A — экземпляр класса B?
        try {
            rulesB.cast(fromA);                                         // то же, что (RiskRules) fromA в коде B
        } catch (ClassCastException e) {
            System.out.println(e.getMessage());
        }
        System.out.println(a.loadClass("RiskRules") == rulesA);         // повторный запрос к тому же loader
    }
}

Одни и те же байты, одно имя — и два несовместимых класса. Сообщение «Cannot cast RiskRules to RiskRules» выглядит абсурдно, пока не спросишь у обеих сторон getClass().getClassLoader(). Чинится это общим контрактом: интерфейс лежит в родительском загрузчике, который видят оба плагина, а в плагинах — только реализации.

Где свои загрузчики встречаются в backend

Сам ты их почти не пишешь, но работаешь среди них каждый день:

  • Spring Boot fat jar. Стандартный app loader не умеет читать JAR внутри JAR. Лаунчер Spring Boot создаёт свой загрузчик (LaunchedClassLoader в Boot 3.2+), который читает BOOT-INF/lib.
  • Spring Boot DevTools. Библиотеки грузит base-загрузчик, а твои классы — restart-загрузчик, который выбрасывают при каждой перезагрузке. Объект, переживший restart в кэше или сессии, даёт тот самый «Cannot cast X to X».
  • Tomcat и другие веб-контейнеры. У каждого веб-приложения свой загрузчик, и он ищет сначала у себя, а потом у родителя (child-first). Так два приложения в одном Tomcat живут с разными версиями библиотек. Классы java.* всё равно отдаются вверх.
  • Прокси и генерация кода. CGLIB и ByteBuddy, на которых стоят прокси Spring и Hibernate, генерируют байткод на лету и определяют классы через загрузчик.

Остаётся правило видимости из шага 2: платформа не видит классы приложения. А ServiceLoader или JDBC DriverManager из платформы должны найти реализацию, которая лежит в твоём JAR. Для этого у каждого потока есть context class loader — Thread.currentThread().getContextClassLoader(), по умолчанию это app. Библиотека платформы грузит реализации через него, в обход обычного делегирования. Фреймворки подменяют его, когда код плагина выполняется в общем потоке.

Отсюда же видны утечки загрузчиков. Класс выгружается только вместе со своим загрузчиком, когда до загрузчика больше нельзя дойти по ссылкам. Если старый загрузчик держит ThreadLocal, static-кэш или незавершённый поток, после каждого редеплоя или перезагрузки плагина в памяти остаётся ещё один комплект классов. Растёт Metaspace, и однажды приходит OutOfMemoryError: Metaspace. В VM.classloader_stats это видно как десятки загрузчиков одного типа вместо одного.

Когда своего загрузчика не нужно? В обычном Spring Boot сервисе — почти никогда: одно приложение, один classpath, всё делает лаунчер. Свой загрузчик оправдан, если нужна настоящая изоляция: плагины разных версий в одном процессе, загрузка кода из внешнего источника. Если нужно просто найти реализации интерфейса, хватит ServiceLoader или бинов Spring.

  • JVM грузит класс при первом обращении, поэтому отсутствующий класс может проявиться через час после старта, на редкой ветке кода.
  • Загрузчики выстроены цепочкой app → platform → bootstrap. Каждый сначала спрашивает родителя, и это защищает классы платформы от подмены.
  • После загрузки идут linking и initialization. Ошибку легко отнести к этапу по названию: CNFE и NoClassDefFoundError — поиск, VerifyError и NoSuchMethodError — связывание, ExceptionInInitializerError — static-код.
  • Инициализацию запускает только активное использование. Константы, .class, массивы и loadClass её не запускают. Неудачная инициализация делает класс ошибочным до перезапуска.
  • Класс — это имя плюс загрузчик. Отсюда «Cannot cast X to X» и утечки Metaspace от удержанных загрузчиков.

На собеседовании

Какие загрузчики классов есть в JVM и что такое parent delegation?

В JVM три встроенных загрузчика. Bootstrap грузит ядро платформы, java.lang и java.util, и в Java виден как null. Platform грузит остальные модули платформы, например java.sql. App грузит классы приложения из classpath. Они связаны ссылкой parent. Parent delegation значит, что загрузчик сначала спрашивает родителя и ищет сам, только если родитель класс не нашёл.

Отсюда два свойства. Системный класс нельзя подменить своим JAR: до JAR очередь просто не дойдёт. И каждый класс платформы существует в процессе в одном экземпляре. Если в сервисе пропал RiskRules, запрос пройдёт до bootstrap и обратно, а ошибку выбросит app, когда не найдёт класс в classpath.

  • До Java 9 вместо platform был extension loader с каталогом lib/ext. С модулями его убрали.
  • Делегирование — поведение метода loadClass, его можно переопределить. Tomcat для веб-приложений ищет сначала у себя (child-first), но java.* всё равно отдаёт вверх: определить их может только bootstrap.
  • Родитель не видит классы ребёнка. Поэтому ServiceLoader и JDBC грузят реализации через context class loader потока.
Что вернёт getClassLoader() для java.util.List, java.sql.Connection и класса из твоего JAR?

null (bootstrap), platform и app. Проверено на JDK 21 при запуске через java -cp. При запуске java File.java твой класс определит MemoryClassLoader лаунчера, а app станет его родителем.

Коллега положил в JAR свой java.lang.String с «исправленным» equals. Что будет?

Ничего не подменится. Запрос java.lang.String дойдёт до bootstrap, тот найдёт класс в java.base, и JAR никто не откроет. Если попытаться определить класс в пакете java.* своим загрузчиком напрямую, defineClass бросит SecurityException: Prohibited package name.

RiskRules лежит в JAR приложения. Зачем его ищут ещё два загрузчика?

App заранее не знает, что выше класса нет: правило — сначала родитель. Цена — пара лишних вызовов при первой загрузке. Дальше класс берётся из кэша app, и цепочку не проходят.

Когда JVM инициализирует класс и чем это отличается от загрузки?

Загрузка — найти байты и создать объект Class. Инициализация — выполнить инициализаторы static-полей и блоки static. Она происходит при первом активном использовании: new, вызов static-метода, чтение или запись static-поля, которое не является константой, Class.forName(name), инициализация подкласса. Константы времени компиляции, Foo.class, создание массива Foo[] и loadClass класс не инициализируют.

На этом держится ленивая загрузка через holder: курсы валют грузятся при первом вызове, а не при старте сервиса, и JVM гарантирует, что это произойдёт один раз, даже при параллельных запросах.

  • Инициализация идёт под блокировкой класса (JLS §12.4.2), другие потоки ждут. Поэтому holder безопасен без volatile. Но два класса, которые в static-коде обращаются друг к другу из разных потоков, могут заблокироваться навсегда.
  • Обращение Card.fee к полю, объявленному в Base, инициализирует только Base.
  • static final Long — не константа. Константа — это поле примитивного типа или String со значением, известным компилятору.
Что выведет этот код? 
public class Quiz {
    static class Account {
        static { System.out.println("init Account"); }
        static final String BANK = "ACME";
        static String region = "EU";
    }
    public static void main(String[] args) {
        System.out.println(Account.BANK);
        Account[] batch = new Account[2];
        System.out.println(Account.region);
    }
}
ACME
init Account
EU

BANK — строковая константа, javac подставил "ACME" прямо в Quiz. Массив создаёт массив, а не объект Account. Инициализацию запускает только чтение обычного поля region.

Найди проблему в ленивом singleton для курсов 
class FxRates {
    private static FxRates instance;

    static FxRates get() {
        if (instance == null) {
            synchronized (FxRates.class) {
                if (instance == null) instance = new FxRates();
            }
        }
        return instance;
    }
}

Поле instance не volatile. Другой поток может увидеть ссылку на объект раньше, чем записи его полей, и прочитать недоинициализированные курсы. Исправить — объявить поле volatile или взять holder: инициализация класса сама даёт и ленивость, и безопасную публикацию.

Чем Class.forName отличается от loadClass?

Class.forName(name) по умолчанию инициализирует класс, loader.loadClass(name) только загружает. Поэтому старые JDBC-драйверы подключали через Class.forName: драйвер регистрировал себя в static-блоке. С JDBC 4 драйверы находятся через ServiceLoader сами.

Чем ClassNotFoundException отличается от NoClassDefFoundError?

ClassNotFoundException — checked-исключение явного поиска: мой код вызвал Class.forName или loadClass, и класс не нашли. NoClassDefFoundError — ошибка JVM: класс был при компиляции, код на него ссылается, а при исполнении получить определение не удалось.

У второй две разные причины. Если в cause ClassNotFoundException — класса нет в рантайме, смотрю состав образа и scope зависимости. Если сообщение «Could not initialize class» — класс есть, но его инициализация уже упала, и я ищу в логе первое ExceptionInInitializerError.

  • В JDK 21 у «Could not initialize class» в cause уже есть исходная ошибка инициализации. В старых версиях её приходилось искать в логе выше.
  • NoSuchMethodError и NoSuchFieldError — родственники: класс нашёлся, но не той версии. Почти всегда это конфликт версий библиотек.
В логе сотни ошибок NoClassDefFoundError: Could not initialize class bank.fx.FxRates. Коллега предлагает добавить JAR с FxRates в образ. Прав ли он?

Нет. Класс нашёлся, упала его инициализация. Нужна первая ошибка — ExceptionInInitializerError с настоящей причиной, скорее всего при старте или на первом запросе. Класс останется ошибочным до перезапуска процесса, поэтому после исправления причины сервис придётся перезапустить.

Почему NoClassDefFoundError может появиться через час после старта?

JVM ищет класс при первом обращении. Если к нему обращается только редкая ветка, например антифрод крупных переводов, ошибка появится, когда туда впервые зайдёт запрос.

Почему приведение может упасть с «Cannot cast X to X»?

Для JVM класс — это пара из полного имени и загрузчика, который его определил. Если два загрузчика независимо определили RiskRules даже из одних и тех же байтов, получатся два разных класса, и объект одного нельзя привести к другому.

В backend это встречается с плагинами, веб-контейнерами и Spring Boot DevTools. При restart DevTools перегружает классы приложения новым загрузчиком, а объект из кэша или сессии остался от старого. Лечится общим контрактом в родительском загрузчике или тем, что объекты не переживают перезагрузку.

  • Свои загрузчики нужны для изоляции и перезагрузки: веб-приложения в Tomcat, вложенные JAR Spring Boot, плагины, прокси, сгенерированные на лету.
  • Класс выгружается только вместе со своим загрузчиком. Ссылка на старый загрузчик из ThreadLocal, static-кэша или потока держит все его классы, и после серии редеплоев растёт Metaspace.
Что напечатает TwoLoaders, если оба загрузчика создать с parent = app, а RiskRules положить в classpath приложения?

Четыре раза true, и исключения не будет. Оба загрузчика сначала спросят app, тот найдёт RiskRules в своём classpath и определит его один раз. Проверено на JDK 21.

Что такое context class loader потока и зачем он нужен?

Это загрузчик, привязанный к потоку, по умолчанию app. Код платформы, например ServiceLoader, не видит классы приложения через свою цепочку, поэтому ищет реализации через context class loader. Фреймворки подменяют его, когда в общем потоке выполняется код плагина или веб-приложения.
