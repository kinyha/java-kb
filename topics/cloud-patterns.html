Cloud Patterns

Облачные паттерны решают типовые задачи распределённых систем вне бизнес-кода. Sidecar — вспомогательный процесс рядом с приложением, в том же сетевом пространстве, как контейнеры одного пода: он берёт на себя повторы, TLS, метрики. В демо сайдкар-посол (ambassador) поднял долю успешных вызовов нестабильного сервиса с 70 % до 97 % без единой строки в приложении. Anti-corruption layer переводит чужую модель — устаревшей системы или внешнего API — в свою, чтобы она не расползалась по коду. Strangler fig заменяет систему по кусочку за маршрутизатором, BFF собирает API под конкретного клиента. Каждый паттерн переносит сложность, а не убирает её: сайдкар — ещё один процесс, который надо обновлять и отлаживать.

Повторы, TLS и метрики переписаны в каждом сервисе по-своему

В компании двадцать сервисов на Java, Go и Python. Каждый сам настраивает повторы к внешнему сервису курсов, сам поднимает TLS к соседям, сам отдаёт метрики в своём формате. Повторы в трёх сервисах без задержки, в двух — без ограничения числа попыток; обновление сертификатов — ручная работа в двадцати местах. Это инфраструктурная логика, одинаковая для всех и не связанная с бизнесом, — кандидат на вынос из кода.

Тема разбирает sidecar и ambassador на демо, anti-corruption layer на коде и сводку остальных паттернов. Демо sidecar.sh запускает в Docker нестабильный сервис курсов (около 30 % ответов 503), контейнер приложения с curl и nginx 1.31 как сайдкар в сетевом пространстве приложения. Strangler fig подробно — в Monolith & Microservices, BFF — в API Gateway, повторы — в Resilience Patterns.

Sidecar и ambassador: инфраструктура рядом с приложением, а не в нём

# Приложение — alpine с curl; ничего не знает о повторах.
docker run -d --name app --network cp-net alpine sleep 600
# Сайдкар разделяет сетевое пространство app: для приложения он — localhost:9000.
docker run -d --name ambassador --network container:app -v "$PWD/ambassador.conf":/etc/nginx/nginx.conf:ro nginx:1.31-alpine
location / {
    proxy_pass http://rates;                     # три записи одного адреса — три попытки
    proxy_next_upstream error timeout http_503;
    proxy_next_upstream_tries 3;
    proxy_connect_timeout 200ms;
    proxy_read_timeout 1s;
}
== the app calls the rates service 200 times (about 30% of responses are 503)
   directly, http://rates:8080:            200 x140  503 x60
   via ambassador, http://localhost:9000:  200 x194  503 x6
== same network namespace
   inside the app container, port 9000 is open: 0.0.0.0:9000
   app container runs: ps sleep

Последние строки вывода показывают сам механизм. Внутри контейнера приложения открыт порт 9000, хотя процессов nginx там нет — только sleep и ps: сетевое пространство общее, а процессы раздельные. Так же устроены контейнеры одного пода в Kubernetes, и так работает сервисная сеть: Istio и Linkerd добавляют в каждый под прокси Envoy, который перехватывает весь входящий и исходящий трафик и даёт mTLS, повторы, тайм-ауты и метрики для любых языков без изменения кода.

Ambassador — частный случай сайдкара для исходящих вызовов: представитель внешнего сервиса рядом с приложением. Другие типичные сайдкары: агент сбора логов, прокси для подключения к облачной базе (Cloud SQL Proxy), обновление сертификатов и секретов. Цена — ресурсы на каждый под, ещё одна точка отказа и отладки, лишний переход через localhost на каждый вызов. И главное: повторы в сайдкаре должны знать об идемпотентности. nginx из демо POST не повторит: по умолчанию он не передаёт неидемпотентный запрос следующему серверу, если уже отправил его, — это включается только флагом non_idempotent. В сервисной сети политика повторов задаётся для маршрута, и если включить её для пути платежей, POST повторится: двойное списание, если сервис успел выполнить запрос до 503.

Anti-corruption layer: чужая модель останавливается на границе

// Модель устаревшей банковской системы: строки, коды, суммы в копейках строкой.
record LegacyTxn(String ACCT_NO, String TXN_CD, String AMT_KOP, String DT_YYYYMMDD) {}

// Своя модель предметной области.
record Payment(AccountId account, PaymentType type, Money amount, LocalDate date) {}

// Слой перевода: единственное место, которое знает о LegacyTxn.
final class LegacyBankTranslator {
    Payment toDomain(LegacyTxn t) {
        return new Payment(
            new AccountId(t.ACCT_NO().strip()),
            switch (t.TXN_CD()) {                       // коды старой системы — только здесь
                case "01", "11" -> PaymentType.CARD;
                case "07" -> PaymentType.TRANSFER;
                default -> throw new UnknownLegacyCode(t.TXN_CD());
            },
            Money.ofMinor(Long.parseLong(t.AMT_KOP()), "RUB"),
            LocalDate.parse(t.DT_YYYYMMDD(), DateTimeFormatter.BASIC_ISO_DATE));
    }
}

Новый сервис платежей интегрируется со старой банковской системой, у которой своя модель: поля в верхнем регистре, коды операций числами в строках, суммы в копейках строкой, даты без разделителей. Если эти типы проникают в код сервиса, новая модель начинает жить по правилам старой: условия на «07» появляются в десятке мест, и замена старой системы требует переписать всё. Anti-corruption layer — слой перевода на границе: снаружи он говорит на языке старой системы, внутрь отдаёт только свою модель. Неизвестный код операции — явная ошибка перевода, а не тихое значение по умолчанию.

Этот слой — естественное место для адаптеров из гексагональной архитектуры, как в Clean & Hexagonal Architecture, и для перевода между ограниченными контекстами из DDD. При постепенной замене системы по strangler fig он позволяет новому коду работать сначала со старой системой через перевод, а затем с новой — без изменения модели.

Valet key и claim check решают одну задачу — не гонять большие данные через сервис. Клиент загружает файл в S3 по подписанной ссылке с правом записи одного объекта на 10 минут, и сервис не держит соединение на время загрузки. Сообщение о загруженном файле несёт ссылку на объект, а не сам файл: брокеры рассчитаны на сообщения в килобайты, а не в мегабайты. Competing consumers — основа очередей задач из Background Jobs.

Повторы в сайдкаре или сервисной сети безопасны: приложение ничего не знает, а успешных запросов больше.

Сайдкар не знает, выполнил ли сервис запрос перед ответом 503 или обрывом. В демо повторы подняли успех GET с 140 до 194 из 200; nginx по умолчанию не повторяет POST, но политика повторов в сервисной сети, включённая для маршрута платежей, повторит и его. Повторы в инфраструктуре включают только для идемпотентных методов или запросов с ключом идемпотентности.

  • Sidecar — процесс рядом с приложением в общем сетевом пространстве; ambassador — для исходящих вызовов.
  • Демо: сайдкар с тремя попытками поднял успех вызовов к сервису с 30 % отказов со 140 до 194 из 200.
  • В контейнере приложения открыт порт сайдкара, но нет его процесса: сеть общая, процессы раздельные.
  • Anti-corruption layer держит чужую модель на границе; неизвестные значения — явная ошибка перевода.
  • Valet key и claim check не гоняют большие данные через сервис; повторы в инфраструктуре — только для идемпотентного.

На собеседовании

Что такое sidecar и когда он оправдан?

Вспомогательный контейнер рядом с приложением в одном поде с общей сетью и томами. Он берёт инфраструктурные задачи — прокси с TLS и повторами, сбор логов, метрики, обновление секретов — одинаково для сервисов на любых языках. Оправдан, когда сервисов много и на разных стеках; для одного сервиса на Java проще библиотека.

  • Сервисная сеть (Istio, Linkerd) — сайдкар Envoy в каждом поде.
  • Цена: ресурсы на каждый под, задержка лишнего перехода, сложность отладки и обновления.
  • Повторы в сайдкаре — только для идемпотентных запросов.

Зачем нужен anti-corruption layer?

Чтобы модель чужой системы — устаревшей или внешней — не проникала в свой код. Слой перевода на границе принимает чужие типы и коды и отдаёт свою модель предметной области. Тогда замена внешней системы меняет только этот слой.

  • Неизвестные коды — явная ошибка, а не значение по умолчанию.
  • Естественно ложится на адаптеры гексагональной архитектуры и границы контекстов DDD.
Что не так с этой интеграцией? 
@Service
class RefundService {
    void refund(LegacyTxn txn) {                         // тип старой системы в бизнес-коде
        if (txn.TXN_CD().equals("07")) { ... }           // код операции «перевод»
        long amount = Long.parseLong(txn.AMT_KOP());
        ledger.post(txn.ACCT_NO(), -amount);
    }
}

Бизнес-логика возвратов зависит от типов и кодов старой системы: «07», копейки строкой и номер счёта с пробелами расползутся по всем сервисам, а замена системы потребует их переписать. Нужен слой перевода, который превращает LegacyTxn в свою модель Payment с типом, деньгами и счётом, а RefundService работает только с ней.

Как принимать большие файлы, не гоняя их через сервис?

Valet key: сервис выдаёт клиенту подписанную ссылку на загрузку одного объекта в объектное хранилище с коротким сроком, и клиент грузит файл напрямую. Затем сервис получает уведомление о загрузке. В сообщениях между сервисами передают ссылку на объект, а не содержимое (claim check).

  • Права ссылки — только запись конкретного ключа, ограничение размера и типа.
  • Проверку содержимого (антивирус, формат) делают после загрузки асинхронно.
