Code Review

Code review проверяет, что изменение сохраняет нужное поведение системы. Ревьюер восстанавливает путь от входа до эффекта, ищет разрывы при ошибках и проверяет, что тесты их ловят. Замечание становится полезным, когда объясняет последствие и нужное свойство. Небольшой PR помогает удержать этот путь целиком, а одобрение относится к проверенной итоговой версии.

Сначала восстанови поведение, которое обещает PR

Автор добавил защиту от повторных уведомлений о платеже. В описании PR написано: «Один ID обрабатывается один раз». Тесты зелёные; новая коллекция называется done. Ревьюер предлагает переименовать её в processedIds. Но банк иногда отказывает до списания, а уведомление затем приходит снова. Если ID записан до вызова банка, второй запрос будет пропущен вместе с ещё не выполненным платежом.

Начни с результата, который должен увидеть пользователь. Для k7 на сумму 100 после временного отказа и успешного повтора должно быть одно списание 100. Нужно уточнить, что значит «обработан»: запрос получен, попытка начата или платёж подтверждён. Это разные состояния. Имя done не доказывает переход между ними.

Прочитай описание изменения, условие задачи и вызывающий код. Восстанови вход, границы эффекта, ответ и повторный вызов. Затем смотри diff: где появился новый переход, что переживает исключение и кто повторяет операцию. Проверка по одному успешному запросу не показывает окно между локальной записью и внешним действием.

Ниже минимальная локальная модель для ревью. charged — счётчик эффекта в минимальных единицах, Bank не выполняет HTTP и не хранит деньги. TemporaryFailure бросается до эффекта, ReplyLost — после него. Флаги позволяют увидеть обе стороны окна; useKey позже покажет гарантию на стороне провайдера.

record Request(String key, long amount) {}

static final class TemporaryFailure extends RuntimeException {}
static final class ReplyLost extends RuntimeException {}
static final class PayloadConflict extends RuntimeException {}

static final class Bank {
    final Map<String, Long> accepted = new HashMap<>();
    long charged;
    int calls;
    boolean failBefore, loseReply;

    String charge(Request request, boolean useKey) {
        calls++;
        if (failBefore) {
            failBefore = false;
            throw new TemporaryFailure();     // эффект ещё не произошёл
        }
        if (useKey && accepted.containsKey(request.key())) {
            if (accepted.get(request.key()) != request.amount()) {
                throw new PayloadConflict();   // тот же ключ с другой суммой запрещён
            }
            return "REPLAY";                  // прошлый эффект не выполняется повторно
        }
        charged = Math.addExact(charged, request.amount());
        if (useKey) accepted.put(request.key(), request.amount());
        if (loseReply) {
            loseReply = false;
            throw new ReplyLost();             // эффект есть, клиент ответа не увидел
        }
        return "CHARGED";
    }
}

static final class Handler {
    final Set<String> done = new HashSet<>();
    final Bank bank;
    final boolean markFirst, useKey;

    Handler(Bank bank, boolean markFirst, boolean useKey) {
        this.bank = bank;
        this.markFirst = markFirst;
        this.useKey = useKey;
    }

    String pay(Request request) {
        if (done.contains(request.key())) return "SKIPPED";
        if (markFirst) done.add(request.key());   // пока лишь локальная отметка
        String result = bank.charge(request, useKey);
        if (!markFirst) done.add(request.key());  // сюда не попадём при потере ответа
        return result;
    }
}

static String attempt(Handler handler, Request request) {
    try {
        return handler.pay(request);
    } catch (TemporaryFailure e) {
        return "TEMPORARY_FAILURE";
    } catch (ReplyLost e) {
        return "REPLY_LOST";
    }
}

Bank bank = new Bank();
bank.failBefore = true;
Handler handler = new Handler(bank, true, false);
Request request = new Request("k7", 100);
System.out.println("== mark before external effect ==");
System.out.println("first=" + attempt(handler, request));
System.out.println("retry=" + attempt(handler, request));
System.out.println("done=" + handler.done.contains("k7"));
System.out.println("bank calls=" + bank.calls + " charged=" + bank.charged);

Блокирующее замечание здесь относится к потерянному платежу. Оно должно ссылаться на конкретный переход и наблюдение: «После отказа до списания ключ уже в done; повтор возвращает SKIPPED, а charged остаётся 0. Нужен путь завершения платежа при повторе». Выбор коллекции и имя переменной рассматриваются после этого.

Проверяй связи и чередование вызовов вокруг изменённых строк

В diff видны несколько строк, но их смысл определяется окружающим кодом. Проследи путь уведомление → проверка ID → вызов банка → сохранение результата → ответ. Найди владельца ключа, обработку исключений и границу транзакции. Уточни, откуда приходит повтор и остаётся ли ключ тем же. Если ключ создаётся заново на каждой попытке, одинаковый payload ещё не делает попытки одной операцией.

Для Java backend полезно пройти по конкретным вопросам. Проверка доступа относится к нужному плательщику или только к существованию ID? Сумма хранится в нужных единицах и безопасно вычисляется? Состояние не меняется до проверки допустимого перехода? Ресурс закрывается, число обращений к БД ограничено, ожидание внешнего сервиса имеет границу? Для миграции проверь совместимость читающей и пишущей версии, backfill и момент появления ограничения.

Конкурентность проверяется на составном решении. ConcurrentHashMap защищает отдельные операции, но «проверить отсутствие → записать → списать» занимает несколько действий. Два обработчика могут оба получить false. Это видно только при рассмотрении чередования, даже если последовательный тест идеален.

import java.util.concurrent.*;
import java.util.concurrent.atomic.AtomicInteger;

public class ConcurrentReviewDemo {
    static void unsafe(ConcurrentMap<String, Boolean> done, AtomicInteger charged,
                       CyclicBarrier bothRead) throws Exception {
        boolean existed = done.containsKey("k7"); // обе проверки пройдут до записи
        bothRead.await(5, TimeUnit.SECONDS);      // фиксируем нужное чередование
        if (!existed) {
            done.put("k7", true);
            charged.incrementAndGet();           // каждый поток создаёт эффект
        }
    }

    static void atomicClaim(ConcurrentMap<String, Boolean> done, AtomicInteger charged,
                            CyclicBarrier start) throws Exception {
        start.await(5, TimeUnit.SECONDS);
        if (done.putIfAbsent("k7", true) == null) { // один победитель внутри одной карты
            charged.incrementAndGet();
        }
    }

    static int race(boolean atomic) throws Exception {
        ConcurrentMap<String, Boolean> done = new ConcurrentHashMap<>();
        AtomicInteger charged = new AtomicInteger();
        CyclicBarrier gate = new CyclicBarrier(2);
        try (ExecutorService pool = Executors.newFixedThreadPool(2)) {
            Callable<Void> task = () -> {
                if (atomic) atomicClaim(done, charged, gate);
                else unsafe(done, charged, gate);
                return null;
            };
            Future<Void> first = pool.submit(task);
            Future<Void> second = pool.submit(task);
            first.get(10, TimeUnit.SECONDS);
            second.get(10, TimeUnit.SECONDS);
        }
        return charged.get();
    }

    static int sequential() {
        ConcurrentMap<String, Boolean> done = new ConcurrentHashMap<>();
        AtomicInteger charged = new AtomicInteger();
        for (int i = 0; i < 2; i++) {
            if (!done.containsKey("k7")) {
                done.put("k7", true);
                charged.incrementAndGet();
            }
        }
        return charged.get();
    }

    public static void main(String[] args) throws Exception {
        System.out.println("== thread-safe map, compound decision ==");
        System.out.println("sequential effects=" + sequential());
        System.out.println("two reads before write=" + race(false));
        System.out.println("atomic claim effects=" + race(true));
    }
}
== thread-safe map, compound decision ==
sequential effects=1
two reads before write=2
atomic claim effects=1

Полный ConcurrentReviewDemo.java; запуск java examples/code-review/ConcurrentReviewDemo.java. CyclicBarrier удерживает оба потока до завершения проверок. sleep не используется; таймауты ограничивают ожидание неисправного опыта.

putIfAbsent даёт одного победителя внутри этой карты при успешном выполнении эффекта. Это исправление показанной гонки, но окно отказа из первого шага остаётся: победитель мог отметить ключ и упасть до списания. Между двумя процессами карты вообще разные. Замечание «добавь synchronized» без указания общей границы координации ещё не решает требование.

Не нужно повторно проверять всё устройство технологий в одном PR. Сосредоточься на изменённых путях и затронутых гарантиях. Если затронута незнакомая область, назови её и привлеки владельца: например, протокол банка или миграцию горячей таблицы. Когда части разделены между ревьюерами, у каждого должна быть понятная зона проверки.

Зелёный тест полезен только тогда, когда ловит нужную ошибку

В тесте сломанного Handler можно проверить, что done содержит k7. Такой тест зелёный именно после потерянного платежа: он подтверждает наличие отметки, а не обещанный эффект. Посмотри на утверждения теста и спроси: «Какую неверную версию они отвергнут?» Существование тестового файла и число покрытых строк этого не объясняют.

Для этого сценария проверяется одно успешное списание после допустимого повтора, его сумма и отсутствие второго эффекта. Полезны отдельные случаи: временный отказ до эффекта, потеря ответа после эффекта, одновременные попытки, тот же ключ с иной суммой. В каждом есть конкретная наблюдаемая гарантия. В тесте отказа нужно знать, произошёл эффект или нет: один общий mock «бросает исключение» этого не различает.

Автор может исправить первый тест перестановкой done.add после charge. Отказ до списания тогда допускает повтор. Но при потере ответа списание уже произошло, а локальной отметки ещё нет. Следующая попытка повторит эффект. Это второй тест, который должен пережить исправление первого.

В обоих опытах исключение означает, что клиент не получил обычный ответ. Оно не сообщает, что внешний эффект отсутствует. Ревьюер смотрит на место сбоя и гарантию повторной операции, а не только на catch. Тесты с правильными фазами сбоя защищают именно эту связь.

Фейк из демо задаёт простую модель, а реальный адаптер может передать другой заголовок, потерять ключ или интерпретировать конфликт как успех. Для исправления нужны проверка логики и проверка границы с фактическим API: стабильность ключа, поведение при повторе, ограничения срока хранения. Для БД уникальность проверяется на реальном ограничении и конкурентных транзакциях. Как выбирать уровни тестов — в Testing Strategy, как не скопировать ошибку в подмену — в Test Doubles.

Проверяй и обслуживание изменения. Нужны ли обновлённая документация ошибки, тест обратной совместимости, миграция данных, метрика неопределённого результата? Это определяется поведением PR. Мелкое переименование не требует той же инфраструктуры, что новое взаимодействие с банком; проверка должна закрывать реальную развилку.

Замечание связывает место в коде, риск и проверяемое требование

«Плохо», «переделай» и «так не принято» заставляют автора угадывать, что исправлять. Напиши наблюдение, затем последствие, затем нужное свойство. Добавь короткий пример или способ проверки. Автор сможет предложить другое исправление, которое сохранит то же свойство.

Для сломанного Handler: «Здесь k7 записывается до ответа банка. При TemporaryFailure до списания повтор вернёт SKIPPED, хотя платёж ещё не выполнен. Это блокирует изменение: нужен повтор, который сможет довести операцию до одного эффекта. Проверь отказ до списания и потерю ответа после него; простая перестановка строки второй случай не закрывает». Замечание предъявляет результат, а не назначает единственный шаблон классов.

Это пример соглашения команды, а не встроенные статусы Git. Вопрос может стать блокирующим после ответа. Нарушение принятого обязательного форматирования проще исправлять автоматом; личное предпочтение по допустимым вариантам не стоит выдавать за дефект. Укажи, какие замечания нужны до слияния, а какие оставлены как предложение.

При несогласии сравните варианты на одной цели. «Карта потокобезопасная» и «решение атомарное» — разные утверждения; расписание двух потоков даёт общий предмет разговора. Для спорной цены абстракции покажи зависимость, сценарий изменения и добавляемую сложность. Если обсуждение ходит по кругу, коротко разберите его голосом с владельцем решения и сохраните вывод в PR.

Пиши о поведении кода. Полезно отметить и удачный выбор с причиной: «Хорошо, что тест различает отказ до списания и потерю ответа; теперь перестановка строки не сможет выдать себя за полное исправление». Такое замечание сохраняет инженерное объяснение, которое пригодится следующему автору.

Размер PR определяется законченной проверяемой правкой

Большой PR тяжело проверять, когда в нём одновременно новый retry, переименование пакетов, смена DTO и миграция. Ревьюер теряет связь между требованием и изменёнными строками. Маленькая правка должна иметь собственный смысл: после её слияния и проверки система находится в допустимом состоянии. Число строк само по себе этого не гарантирует.

Отдели независимую чистку от изменения поведения. Код, тесты и нужная документация одного поведения остаются вместе. Разбивать их по принципу «сначала прод, потом тест» неудобно: первый PR нельзя проверить как завершённое изменение. Для связанной цепочки назови предусловия каждой части и правила включения.

В этом примере PR 1 добавляет в адаптер явную передачу ключа, сохраняя используемый старый путь. PR 2 переводит обработчик на стабильный ключ операции и проверяет взаимодействие. PR 3 включает дополнительные повторы только после проверки гарантии провайдера и развёртывания нужной версии обработчика. Каждый шаг можно рассмотреть отдельно; включение retry не должно обогнать готовность предыдущих шагов.

Если безопасного промежуточного состояния нет, механическое деление сделает изменение опаснее. Сохрани связанную часть вместе либо сначала введи совместимый переход. Схема БД, которую новая версия требует немедленно, и удаление поля, которое ещё читает старая версия, нуждаются в порядке развёртывания. Для такого PR важнее явный план совместимости, чем лимит строк.

Описание PR начинается с наблюдаемой проблемы и результата. Например: «Повтор после потери ответа банка мог создать второе списание. Обработчик передаёт тот же ключ операции в каждую попытку; адаптер проверяет повторный результат и конфликт payload. Проверено: отказ до эффекта, потеря ответа после эффекта, совпадающий ключ с иной суммой. Гарантия реального API подтверждается отдельной интеграционной проверкой». Это пример описания предполагаемого продуктового изменения; демо страницы проверяет только локальную модель.

Автор сначала просматривает весь собственный патч, включая новые файлы. Убирает случайные правки, показывает способ проверки и зовёт ревьюера, знающего затронутый путь. Например, git diff --check без аргументов не включает уже staged-правки; непроиндексированные новые файлы тоже отсутствуют в обычном diff. После git add проверь git diff --cached --check; для готового коммита — git diff HEAD^ HEAD --check. Варианты сравнения описаны в документации git diff; подготовка и переписывание истории — в теме Git.

Одобряй итоговую версию с понятными пределами проверки

После исправлений вернись к причине блокирующего замечания. Посмотри новый переход и оба окна отказа; затем прогон, который их различает. Закрытая ветка обсуждения означает, что её закрыли в интерфейсе. Она ещё не подтверждает правильность кода. Новые коммиты могут изменить соседние гарантии, поэтому решение относится к конкретной итоговой версии.

В модели повтор после ReplyLost становится безопасным, когда тот же ключ доходит до Bank, а Bank сохраняет его вместе с эффектом. Повтор возвращает прошлый результат без нового списания. Перестановка локального done этого свойства не давала.

Bank bank = new Bank();
bank.loseReply = true;
Handler handler = new Handler(bank, false, true);
Request request = new Request("k7", 100);
System.out.println("== same key reaches the bank ==");
System.out.println("first=" + attempt(handler, request));
System.out.println("retry=" + attempt(handler, request));
System.out.println("bank calls=" + bank.calls + " charged=" + bank.charged);

Ключ должен связываться и с существенным содержимым операции. Запрос на 200 с ключом прежнего платежа 100 нельзя молча назвать тем же платежом. Модель Bank отказывает на таком повторе.

Bank bank = new Bank();
bank.charge(new Request("k7", 100), true);
System.out.println("== the key also binds the payload ==");
try {
    bank.charge(new Request("k7", 200), true);
    throw new AssertionError("conflict expected");
} catch (PayloadConflict expected) {
    System.out.println("same key, new amount=CONFLICT");
}
System.out.println("charged=" + bank.charged);
== the key also binds the payload ==
same key, new amount=CONFLICT
charged=100

Проверка здесь вызвала Bank напрямую. У Handler всё ещё только Set ID: для ключа в done он вернёт SKIPPED, даже если сумма другая. Поэтому это демо границы провайдера, а не законченный сервис. В настоящем обработчике нужно хранить и проверять содержание операции и возвращаемый результат. Кроме того, Map демо не переживает перезапуск и не координирует разные процессы; эти свойства надо закрепить реальным хранилищем и протоколом.

Перед одобрением сверь финальный diff, проверки нужной версии и состояние обязательных замечаний. Если после ревью изменились база ветки или затронутый код, проверь получившуюся комбинацию. Автоматический анализ, форматирование и CI помогают снять повторяющуюся работу; ревью остаётся местом для проверки смысла и предположений на границах. Порядок проверки итоговой сборки — в CI/CD.

Code review не требует довести каждую систему до идеала в одном PR. Одобрение возможно, когда изменение удовлетворяет своим требованиям и улучшает поддерживаемость в заданных границах. Известный дефект в изменённом платёжном пути нельзя закрыть обещанием «после релиза». Независимую уборку можно вынести, если её отсутствие не ломает этот путь. Область проверки и оставшаяся работа должны быть понятны автору и следующему ревьюеру.

  • Восстанови обещанный результат пользователя. Локальная отметка, успешный HTTP-ответ и состоявшийся платёж — разные наблюдения.
  • Смотри на контекст вызова и составное решение. Потокобезопасная коллекция не объединяет несколько действий в одну гарантию.
  • Тест ценен ошибкой, которую он поймает. Отказ до эффекта и потеря ответа после эффекта проверяют разные окна.
  • Связывай замечание с местом, последствием и требованием; отделяй блокирующий дефект от вопроса и необязательной полировки.
  • PR должен давать проверяемое допустимое состояние. Повторы, миграции и зависимости между версиями требуют явного порядка включения.
  • Вернись к причинам замечаний на финальной версии. Одобрение модели не подтверждает свойства реальной внешней системы.

На собеседовании

Что ты смотришь на code review в первую очередь?

Сначала понимаю задачу и ожидаемое поведение. Прохожу изменённый путь от входа до эффекта и ответа: данные, права, состояние, ошибки, повторы и конкурентные вызовы. Затем смотрю, подтверждают ли тесты эти свойства. Имена и читаемость важны, когда помогают удержать смысл; форматирование по правилам команды лучше проверять автоматом.

На платеже с повтором мне нужно одно списание после допустимого retry. Наличие ID в коллекции этого не подтверждает. Поэтому проверю отказ до эффекта и потерю ответа после него, а не только две удачные доставки подряд.

  • Для внешнего эффекта различаю «ответ не получен» и «эффект не произошёл». Разрыв между провайдером и локальной записью требует явной гарантии, не только транзакции в своей БД.
  • Смотрю на совместимость развёртываемых версий: изменение DTO, схемы или enum может сломать старого читателя даже при зелёных тестах новой версии.
  • Если ревью разделено, указываю проверенную область. Граница адаптера и гарантия реального банка могут требовать владельца протокола; чтение одной стороны вызова не подтверждает вторую.

Как написать замечание и что считать блокирующим?

Покажу место, последствие и свойство, которое нужно сохранить. Например: «Ключ записан до списания; после отказа повтор пропускается и платёж остаётся невыполненным. Нужна проверка отказа до эффекта и потери ответа после него». Автор может выбрать реализацию, если она действительно закрывает оба случая.

Блокирую нарушение требований, безопасности или обязательных правил команды. Для вопроса обозначаю, какой контекст нужен. Необязательный вариант называю предложением или Nit. Так автор понимает, что требуется до слияния, и может предметно возразить.

  • У спорного замечания проверяю исходную предпосылку. Например, атомарная операция с локальной картой действительно снимает одну гонку, но не охватывает другой процесс и отказ внешнего вызова.
  • У несколько одинаково пригодных дизайнов сравниваю стоимость изменения и поддержки. Личный привычный стиль не превращает альтернативу в дефект.
  • Если переписка повторяется, обсуждаю с автором и владельцем решения конкретный сценарий, затем фиксирую вывод в PR. Решение должно оставаться доступным следующему читателю.
Ревьюер пишет: «Замени HashSet на ConcurrentHashMap, и повторов не будет». Достаточно?

Нет. Нужно уточнить, какая составная операция атомарна и где общий набор. В демо две containsKey у потокобезопасной карты обе дали false, и оба обработчика создали эффект. putIfAbsent снимает показанную гонку внутри одной карты, но захват до эффекта сохраняет окно потери платежа; разные процессы не разделяют эту карту.

Какой PR считаешь достаточно маленьким?

Тот, в котором могу проследить одну законченную цель, её проверки и безопасное состояние после слияния. Новое поведение, его тесты и нужная документация идут вместе. Независимое переименование или форматирование выношу, потому что они увеличивают diff и затрудняют проверку причины изменения.

У меня нет универсального числа строк. Миграция с переходом между версиями может быть больше небольшого рефакторинга. Для цепочки PR фиксирую зависимости и момент включения поведения, чтобы retry не включился раньше стабильного ключа у провайдера.

  • Разбиение по файлам не равно разбиению по безопасным состояниям. У первого PR уже должен быть законченный результат, иначе промежуточная версия переносит риск на выпуск.
  • Цепочку зависимых PR нужно проверять и отдельно, и в итоговой комбинации. Изменение базового PR может пересобрать смысл и проверки следующих.
  • Для большой неизбежной правки даю карту затронутых путей, порядок чтения и конкретные доказательства. Подсчёт строк не заменяет эту работу.

Тесты зелёные. Когда всё равно не одобришь?

Когда вижу нарушение требования, которое тесты не проверяют, или их утверждения описывают внутреннюю деталь вместо результата. В демо marker test зелёный при charged=0. Также не считаю проверенной гарантию банка только потому, что фейк всегда отвечает так, как удобно обработчику.

Попрошу минимальный пример по причине ошибки и подходящую проверку границы. Затем посмотрю исправление и прогон итоговой версии. Если замечание было о потере ответа после списания, один тест обычного успешного ответа его не закрывает.

  • CI относится к определённому коммиту и среде. Последующие изменения или новая база требуют проверки актуального сочетания, особенно на общих DTO и миграциях.
  • Для гонки прохождение многих случайных запусков не опровергает допустимое ошибочное расписание. Управляемый барьер проверяет именно то чередование, которое обсуждается.
  • Демо с in-memory провайдером даёт механизм, но не подтверждает долговечность и атомарность настоящего API. Вывод должен соответствовать области фактической проверки.
Повтор k7 с новой суммой отсекается в Handler по Set ID. Провайдер умеет проверять payload. Проблема решена?

Нет: повтор до провайдера не дошёл. Handler вернул SKIPPED по одному ключу и не проверил, что новый запрос относится к той же операции. Нужна проверка существенных полей на локальной границе и сохранённый результат. Сценарий changedPayload страницы проверяет только прямой вызов Bank, поэтому он не доказывает корректность Handler.
