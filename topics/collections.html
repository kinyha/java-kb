Collections Overview

Пять объектов с типом List: add, set и contains(null) ведут себя по-разному

Сервис проверки платежей держит список заблокированных счетов. Список приходит из разных мест: из базы, из конфига, из кеша, из стрима. Везде тип один — List<String>. Код проверки вызывает contains(account), где account бывает null у платежей без счёта-отправителя, а процедура обновления делает add и set. Что будет с каждым из списков:

import java.util.*;

public class FiveLists {
    static String attempt(Runnable action) {                       // выполнить и вернуть ok или имя исключения
        try { action.run(); return "ok"; }
        catch (RuntimeException e) { return e.getClass().getSimpleName(); }
    }

    public static void main(String[] args) {
        List<String> fromDb = new ArrayList<>(List.of("acc-1", "acc-2", "acc-3"));
        Map<String, List<String>> lists = new LinkedHashMap<>();
        lists.put("new ArrayList", new ArrayList<>(fromDb));                    // обычный изменяемый список
        lists.put("Arrays.asList", Arrays.asList("acc-1", "acc-2", "acc-3"));    // обёртка над массивом
        lists.put("List.of", List.of("acc-1", "acc-2", "acc-3"));              // неизменяемый, Java 9
        lists.put("unmodifiableList", Collections.unmodifiableList(fromDb));    // обёртка только для чтения
        lists.put("stream().toList()", fromDb.stream().toList());              // неизменяемый, Java 16

        System.out.printf("%-18s %-30s %-30s %s%n", "", "add", "set(0, …)", "contains(null)");
        lists.forEach((name, list) -> System.out.printf("%-18s %-30s %-30s %s%n", name,
            attempt(() -> list.add("acc-4")),
            attempt(() -> list.set(0, "acc-0")),
            attempt(() -> list.contains(null))));
    }
}

Пять объектов одного типа — четыре разных поведения. Arrays.asList разрешает set, но не add. List.of падает даже на безобидном contains(null). В юнит-тесте, где список создан через new ArrayList, всё проходит, а в проде тот же метод получает List.of из конфига и падает.

Это не баг JDK, а контракт. В javadoc List.add помечен как optional operation: реализация вправе отказаться и бросить UnsupportedOperationException. Collection так же разрешает реализациям запрещать null и бросать NullPointerException даже при поиске. Интерфейс говорит, какие операции существуют, но не обещает, что они разрешены. Изменяемость и отношение к null — свойство конкретной реализации.

Отсюда устройство урока. Сначала карта: какие интерфейсы есть и как выбрать реализацию. Потом неизменяемые коллекции и представления — источник первого сюрприза. Потом итератор и ConcurrentModificationException, порядок через Comparator, новые методы Java 21 и в конце — сколько коллекции стоят по памяти.

Collection и Map — две иерархии, а реализацию выбирают по нужным операциям

Каркас коллекций — набор интерфейсов. Каждый добавляет обещание к родителю. Collection — группа элементов: добавить, удалить, проверить наличие, обойти. List добавляет порядок и доступ по индексу, Set — уникальность, Queue — «взять следующий». Map стоит отдельно: она хранит пары ключ → значение, и операция «добавить элемент» у неё не имеет смысла — нужен ещё ключ.

По схеме видно, почему Map — не Collection: у неё другая основная операция, put(key, value). Но Map отдаёт три коллекции-представления: keySet(), values(), entrySet(). Через них карту обходят и чистят. Над всем стоит Iterable — «можно обойти в for-each».

Реализацию выбирают не по названию, а по операциям, которые нужны быстро, и по порядку обхода:

Здесь важен один столбец — порядок обхода. «Не определён» значит, что на порядок нельзя опираться вовсе. Для неизменяемых Set.of и Map.of JDK делает это правило наглядным: порядок обхода меняется от запуска к запуску.

import java.util.*;

public class MapOrder {
    public static void main(String[] args) {
        Map<String, Integer> limits = Map.of("RUB", 100, "USD", 5, "EUR", 4, "CNY", 30);
        Map<String, Integer> copy = new HashMap<>(limits);          // HashMap из тех же четырёх пар
        System.out.println("Map.of:  " + limits.keySet());
        System.out.println("HashMap: " + copy.keySet());
    }
}

Map.of при старте JVM берёт случайную «соль» из System.nanoTime() и от неё начинает обход. Так сделано нарочно, чтобы код, случайно зависящий от порядка, сломался в тестах, а не в проде после обновления JDK. Интереснее вторая строка. HashMap тоже поменял порядок: USD и CNY попали в одну корзину из восьми, и внутри корзины они лежат в порядке вставки — а вставляли их в порядке обхода Map.of. Порядок HashMap зависит от хешей, ёмкости таблицы и истории вставок. Нужен предсказуемый — бери LinkedHashMap или TreeMap.

HashMap обходит ключи в порядке добавления, по крайней мере для маленьких карт.

Порядок определяется номерами корзин, и при расширении таблицы он меняется целиком. Тесты, которые сравнивают toString() карты или JSON из HashMap со строкой-эталоном, ломаются при смене ключей, ёмкости или версии JDK.

Под капотом: RandomAccess, AbstractList и класс Collections

RandomAccess — пустой интерфейс-метка. Его реализует ArrayList и не реализует LinkedList. Алгоритмы из класса Collections (binarySearch, shuffle) проверяют метку и для списков без неё идут через итератор, а не через get(i), который у связного списка стоит O(n).

Классы AbstractCollection, AbstractList, AbstractMap реализуют большинство методов через несколько базовых. Чтобы написать свой список только для чтения, достаточно get и size, а add по умолчанию бросит UnsupportedOperationException — так и устроены «необязательные операции».

Collections (с «s») — не интерфейс, а служебный класс со статическими методами: sort, unmodifiableList, synchronizedMap, emptyList, nCopies. Путать его с Collection — классика вопросов для джунов.

List.of — неизменяемая копия, а unmodifiableList и Arrays.asList — окна в чужие данные

Вернёмся к первому шагу. Три «нестандартных» списка из пяти устроены по-разному, и разница важнее, чем кажется. Одни — копии со своим хранилищем. Другие — представления (view): у них нет своих данных, они обращаются к чужому массиву или списку.

import java.util.*;

public class Views {
    public static void main(String[] args) {
        String[] fromConfig = {"acc-1", "acc-2", "acc-3"};
        List<String> asList = Arrays.asList(fromConfig);            // обёртка над тем же массивом
        asList.set(0, "acc-X");                                     // пишет прямо в массив
        System.out.println("массив после asList.set: " + Arrays.toString(fromConfig));

        List<String> source = new ArrayList<>(List.of("acc-1", "acc-2", "acc-3"));
        List<String> view = Collections.unmodifiableList(source);   // окно только для чтения
        List<String> copy = List.copyOf(source);                    // снимок в собственный массив
        source.add("acc-4");                                        // меняем исходный список
        System.out.println("view: " + view + ", copy: " + copy);

        List<String> firstTwo = source.subList(0, 2);               // subList — тоже представление
        firstTwo.clear();                                           // удаляет из source
        System.out.println("source после subList.clear(): " + source);
        System.out.println("List.copyOf(copy) == copy: " + (List.copyOf(copy) == copy));
    }
}

Геттер, который возвращает Collections.unmodifiableList(items), защищает список от изменений.

Он защищает только от записи через возвращённый объект. Класс продолжает менять items, и вызывающий увидит изменения, в том числе посреди своего обхода. Если нужен снимок, возвращай List.copyOf(items).

Неизменяемые коллекции из List.of, Set.of, Map.of к тому же строгие: ловят ошибки при создании, а не при использовании.

import java.util.*;
import java.util.stream.*;

public class Strict {
    static void attempt(String name, Runnable action) {
        try { action.run(); System.out.println(name + ": ok"); }
        catch (RuntimeException e) { System.out.println(name + ": " + e.getClass().getSimpleName()); }
    }

    public static void main(String[] args) {
        attempt("Set.of с дубликатом", () -> Set.of("RUB", "USD", "RUB"));      // дубликат — ошибка создания
        attempt("Map.of с null", () -> Map.of("RUB", null));                   // null нельзя ни в ключ, ни в значение
        attempt("toList() с null", () -> Stream.of("acc-1", null).toList());    // этот метод null пропускает
        Map<String, Integer> limits = Map.of("RUB", 100);
        attempt("Map.of containsKey(null)", () -> limits.containsKey(null));     // даже вопрос про null запрещён
        attempt("HashMap containsKey(null)", () -> new HashMap<>(limits).containsKey(null));
    }
}
Set.of с дубликатом: IllegalArgumentException
Map.of с null: NullPointerException
toList() с null: ok
Map.of containsKey(null): NullPointerException
HashMap containsKey(null): ok

Почему так строго. null в коллекции почти всегда — ошибка данных, и лучше упасть там, где он появился, чем через час в чужом коде. Дубликат в Set.of — скорее всего опечатка в константе. А неизменяемость даёт то же, что у String: такой список можно без копирования отдавать между потоками и хранить в полях. Поэтому List.copyOf от уже неизменяемого списка возвращает тот же объект — копировать незачем.

Итератор хранит позицию обхода. Если коллекцию поменять мимо него — удалить элемент прямо через map.remove, — позиция может указывать на удалённое или пропустить элемент. Вместо тихой порчи обычные коллекции java.util падают. Сервис чистит истёкшие сессии:

import java.util.*;

public class Sessions {
    public static void main(String[] args) {
        Map<String, Long> sessions = new HashMap<>();                // sessionId → когда истекает
        for (int i = 1; i <= 6; i++) sessions.put("s" + i, i % 2 == 0 ? 0L : Long.MAX_VALUE);  // s2, s4, s6 истекли
        long now = System.currentTimeMillis();
        try {
            for (String id : sessions.keySet())                      // обход через скрытый Iterator
                if (sessions.get(id) < now) sessions.remove(id);     // удаление мимо итератора
        } catch (ConcurrentModificationException e) {
            System.out.println(e + ", осталось " + sessions.size() + " из 6: " + sessions.keySet());
        }
        sessions.values().removeIf(expiresAt -> expiresAt < now);    // удаление через итератор самой коллекции
        System.out.println("после removeIf: " + sessions.keySet());
    }
}
java.util.ConcurrentModificationException, осталось 5 из 6: [s3, s5, s6, s1, s2]
после removeIf: [s3, s5, s1]

Один поток, никакой многопоточности — и ConcurrentModificationException. Название сбивает: «concurrent» здесь значит «одновременно с обходом», а не «из другого потока». И заметь: одна сессия уже удалена, а исключение вылетело позже. Как итератор это узнал:

Что из этого следует на практике:

  • Удалять при обходе — только через итератор: it.remove() или removeIf. Для карты — через представление: map.values().removeIf(…), map.entrySet().removeIf(e -> …), map.keySet().removeAll(expired).
  • Структурное изменение — только добавление и удаление. put по существующему ключу меняет значение, но не modCount, поэтому пересчитать лимиты в цикле по keySet() можно без исключения. Для этого есть и готовый replaceAll.
  • Fail-fast — не гарантия, а попытка. Javadoc прямо говорит, что на исключение нельзя опираться. Счётчик не volatile, и при изменении из другого потока итератор может ничего не заметить и вернуть мусор. Исключение ловит ошибки в логике, а не защищает от гонок.
  • ListIterator у списков умеет больше: ходит в обе стороны, возвращает индекс, делает set и add в текущую позицию — всё без исключения, потому что это изменения через итератор. Про удаление из ArrayList по индексу и его ловушки — тема List.

Коллекции из java.util.concurrent не бросают ConcurrentModificationException. Итераторы ConcurrentHashMap слабо согласованные: видят какое-то состояние карты во время обхода. Итератор CopyOnWriteArrayList обходит снимок массива на момент создания. Иногда их называют «fail-safe», но в javadoc такого термина нет. Разбор — в теме Concurrent Collections.

Comparator задаёт порядок, а в TreeSet и TreeMap — ещё и равенство

Порядок элементов задают двумя способами. Comparable — «естественный порядок», который класс объявляет сам: compareTo у String, Integer, BigDecimal, LocalDate. Comparator — внешнее правило, которое передают в sort, TreeMap, PriorityQueue: платежи по сумме, по дате, по клиенту. Одному классу — один естественный порядок и сколько угодно компараторов.

Главная ловушка в коллекциях: TreeSet и TreeMap не вызывают equals и hashCode. Два элемента для них одинаковы, если compare вернул 0. Если порядок не согласован с equals, коллекции начинают расходиться:

import java.math.BigDecimal;
import java.util.*;

public class Amounts {
    record Payment(String id, BigDecimal amount) {}

    public static void main(String[] args) {
        List<BigDecimal> amounts = List.of(new BigDecimal("100"), new BigDecimal("100.0"), new BigDecimal("100.00"));
        System.out.println("equals: " + amounts.get(0).equals(amounts.get(1))           // сравнивает и масштаб
            + ", compareTo: " + amounts.get(0).compareTo(amounts.get(1)));            // сравнивает только число
        System.out.println("HashSet: " + new HashSet<>(amounts) + ", TreeSet: " + new TreeSet<>(amounts));

        List<Payment> payments = List.of(new Payment("p1", new BigDecimal("500")),
            new Payment("p2", new BigDecimal("500")), new Payment("p3", new BigDecimal("70")));
        Set<Payment> byAmount = new TreeSet<>(Comparator.comparing(Payment::amount));  // «отсортируй по сумме»
        byAmount.addAll(payments);
        System.out.println("TreeSet по сумме: " + byAmount.stream().map(Payment::id).toList());
        Set<Payment> fixed = new TreeSet<>(Comparator.comparing(Payment::amount)
            .thenComparing(Payment::id));                                              // равные суммы различаются по id
        fixed.addAll(payments);
        System.out.println("с thenComparing(id): " + fixed.stream().map(Payment::id).toList());
    }
}
equals: false, compareTo: 0
HashSet: [100.00, 100.0, 100], TreeSet: [100]
TreeSet по сумме: [p3, p1]
с thenComparing(id): [p3, p1, p2]

У BigDecimal equals учитывает масштаб, а compareTo — только значение. Поэтому одни и те же три суммы дают три элемента в HashSet и один в TreeSet. Второй случай опаснее: TreeSet с компаратором «по сумме» молча выбросил платёж p2, потому что его сумма равна сумме p1. add вернул false, никакого исключения. В отчёте просто не хватает платежа.

Правило: компаратор для TreeSet и ключей TreeMap должен различать все элементы, которые ты считаешь разными. Добавляй в конец цепочки уникальное поле — thenComparing(Payment::id). Для sort это не важно: сортировка ничего не выбрасывает, равные элементы просто остаются рядом.

Компаратор по числу проще всего написать как (a, b) -> a.amount() - b.amount().

Разность переполняется: для сумм в копейках порядка миллиардов знак результата переворачивается, и сортировка тихо ломается. Пиши Long.compare или Comparator.comparingLong. Контракт компаратора и что бывает при его нарушении — в теме Sorting Basics.

Java 21 дала упорядоченным коллекциям общий интерфейс SequencedCollection

До Java 21 у коллекций с порядком не было общего предка. «Взять последний элемент» у каждого типа писалось по-своему, а у LinkedHashSet, который порядок хранит, способа не было вовсе — только пройти весь набор. JEP 431 добавил три интерфейса и вставил их в иерархию (зелёные на схеме шага 2):

import java.util.*;

public class Sequenced {
    public static void main(String[] args) {
        List<String> history = new ArrayList<>(List.of("p1", "p2", "p3"));
        Deque<String> queue = new ArrayDeque<>(history);
        SortedSet<String> sorted = new TreeSet<>(history);
        LinkedHashSet<String> recent = new LinkedHashSet<>(history);

        // до Java 21: у каждого типа свой способ взять последний элемент
        String a = history.get(history.size() - 1);
        String b = queue.getLast();
        String c = sorted.last();
        String d = null; for (String s : recent) d = s;            // LinkedHashSet: только обойти всё
        System.out.println("до 21: " + a + " " + b + " " + c + " " + d);

        // Java 21: один метод для всех
        List<SequencedCollection<String>> all = List.of(history, queue, sorted, recent);
        System.out.println("Java 21: " + all.stream().map(SequencedCollection::getLast).toList());

        recent.addFirst("p3");                                     // уже есть — переставляется в начало
        System.out.println("addFirst(p3): " + recent + ", reversed: " + recent.reversed());
        List<String> rev = history.reversed();                     // представление, а не копия
        rev.add("p0");                                             // конец rev — это начало history
        System.out.println("history после rev.add: " + history);
        try { sorted.addFirst("p0"); }                             // место в TreeSet определяет порядок
        catch (UnsupportedOperationException e) { System.out.println("TreeSet.addFirst: " + e); }

        LinkedHashMap<String, Integer> limits = new LinkedHashMap<>(Map.of("RUB", 100));
        limits.putFirst("USD", 5);                                 // SequencedMap
        System.out.println(limits.firstEntry() + " " + limits.lastEntry() + " " + limits.sequencedKeySet().reversed());
        System.out.println("HashSet — SequencedCollection? " + (new HashSet<>(history) instanceof SequencedCollection));
    }
}

Детали, которые видны в выводе:

  • reversed() — представление. Он не копирует, а переворачивает индексы: rev.add("p0") добавил элемент в начало history. Обойти список с конца теперь можно обычным for-each по list.reversed() без ListIterator.
  • addFirst у LinkedHashSet переставляет уже существующий элемент в начало, а не игнорирует его, как add. То же у LinkedHashMap.putFirst.
  • Отсортированные коллекции не дают вставить «в начало». Место элемента в TreeSet определяет компаратор, поэтому addFirst и addLast бросают UnsupportedOperationException. Читать с краёв можно.
  • HashSet, HashMap и PriorityQueue — не sequenced: порядка обхода у них нет, и обещать «первый» и «последний» нечего.

Коллекция хранит ссылки: миллион long в HashSet занимает в 8 раз больше массива

Коллекции работают только с объектами. List<Long> хранит не числа, а ссылки на объекты Long, а HashSet добавляет к каждому элементу ещё и узел хеш-таблицы. Сколько это стоит, видно по гистограмме heap — той же, что печатает jcmd <pid> GC.class_histogram. Программа снимает её до и после построения каждой структуры:

import java.lang.management.ManagementFactory;
import java.util.*;
import java.util.function.Supplier;
import javax.management.ObjectName;

public class Footprint {
    // гистограмма живых объектов: класс → байты, как у jcmd GC.class_histogram
    static Map<String, Long> histogram() throws Exception {
        String text = (String) ManagementFactory.getPlatformMBeanServer().invoke(
            new ObjectName("com.sun.management:type=DiagnosticCommand"), "gcClassHistogram",
            new Object[]{null}, new String[]{String[].class.getName()});
        Map<String, Long> bytes = new HashMap<>();
        for (String line : text.lines().toList()) {
            String[] f = line.trim().split("\\s+");                 // " 1:  1000000  24000000  java.lang.Long"
            if (f.length >= 4 && f[0].endsWith(":")) bytes.put(f[3], Long.parseLong(f[2]));
        }
        return bytes;
    }

    static final List<Object> keep = new ArrayList<>();          // держим все структуры живыми

    static void measure(String name, Supplier<Object> build) throws Exception {
        Map<String, Long> before = histogram();
        keep.add(build.get());
        Map<String, Long> after = histogram();
        long total = 0;
        StringBuilder parts = new StringBuilder();
        for (var e : after.entrySet()) {
            long delta = e.getValue() - before.getOrDefault(e.getKey(), 0L);
            if (delta > 1_000_000) {                               // только крупные классы, без шума JDK
                total += delta;
                parts.append(String.format("  %s %.1f", e.getKey(), delta / (double) N));
            }
        }
        System.out.printf("%-16s %5.1f байт на элемент =%s%n", name, total / (double) N, parts);
    }

    static final int N = 1_000_000;                                // значения от 1 000 000: мимо кеша Long

    public static void main(String[] args) throws Exception {
        measure("long[]", () -> { long[] a = new long[N]; for (int i = 0; i < N; i++) a[i] = 1_000_000L + i; return a; });
        measure("ArrayList<Long>", () -> { List<Long> l = new ArrayList<>(N); for (int i = 0; i < N; i++) l.add(1_000_000L + i); return l; });
        measure("HashSet<Long>", () -> { Set<Long> s = new HashSet<>(); for (int i = 0; i < N; i++) s.add(1_000_000L + i); return s; });
    }
}

Одни и те же восемь мегабайт полезных данных:

  • long[] — 8 байт на число, ровно 8 МБ плюс заголовок массива.
  • ArrayList<Long> — 28 байт на число. Массив ссылок по 4 байта (сжатые указатели при heap меньше 32 ГБ) и объект Long по 24 байта: 12 байт заголовка, 8 байт значения и выравнивание до 8.
  • HashSet<Long> — 64 байта на число, в 8 раз больше массива. К тем же 24 байтам Long добавляется узел HashMap$Node на 32 байта (хеш, ключ, значение, ссылка на следующий) и таблица корзин: 221 ссылок по 4 байта, то есть 8,4 байта на элемент. Корзин вдвое больше, чем элементов, потому что миллион не влез в 220 корзин при коэффициенте загрузки 0,75.

Кроме памяти, каждая ссылка — это переход по указателю при обходе, а объекты Long могут лежать в любом месте heap. Поэтому обход List<Long> медленнее обхода long[] не на проценты, а в разы. В замере на этой машине сумма 10 млн чисел заняла 2 мс для long[], 17 мс для ArrayList<Long> и 47 мс для того же списка после Collections.shuffle, когда соседние ссылки ведут в далёкие друг от друга места heap. Числа — после прогрева, первые проходы медленнее.

Где это важно — миллионы чисел в памяти, кеши идентификаторов, агрегаты в отчётах, — берут массивы примитивов или библиотеки примитивных коллекций: fastutil, Eclipse Collections, HPPC. Там LongOpenHashSet хранит числа прямо в массиве long[]. Размеры объектов и выравнивание подробно — в теме Object Layout.

Вторая граница — потоки. Ни одна коллекция из этой папки не потокобезопасна. Старые Vector, Hashtable и Stack синхронизируют каждый метод, но это не делает безопасными составные действия и обход, а замок на каждый вызов стоит дорого. Их не используют в новом коде. Для нескольких потоков — ConcurrentHashMap, CopyOnWriteArrayList, BlockingQueue (тема Concurrent Collections) или неизменяемая коллекция, опубликованная через volatile-поле.

  • Интерфейс List или Map не обещает, что запись и null разрешены: add — необязательная операция. Не меняй коллекцию, которую получил, если не создавал её сам.
  • List.of, List.copyOf, stream().toList() — неизменяемые копии. unmodifiableList, Arrays.asList, subList, keySet() — представления: изменения источника видны сквозь них.
  • Реализацию выбирают по нужным быстрым операциям и порядку обхода. У HashMap и HashSet порядка нет, Map.of меняет его от запуска к запуску нарочно.
  • ConcurrentModificationException бывает в одном потоке: итератор сверяет modCount на каждом next(). Удаляй при обходе через it.remove() или removeIf.
  • TreeSet и TreeMap считают элементы равными, если compare вернул 0, и молча выбрасывают «дубликаты». Компаратор должен различать все разные элементы.
  • Java 21: getFirst, getLast, reversed() у всех коллекций с порядком. Коллекция объектов стоит в 3–8 раз больше массива примитивов.

На собеседовании

Расскажи об иерархии коллекций. Почему Map не наследует Collection?

Наверху Iterable — всё, что можно обойти в for-each. От него Collection: группа элементов с add, remove, contains, size. Дальше три ветки: List — порядок и индексы, Set — уникальность, Queue и Deque — очередь и дек. Основные реализации: ArrayList, HashSet, LinkedHashSet, TreeSet, ArrayDeque, PriorityQueue.

Map — отдельная иерархия, потому что хранит пары, а не элементы: операция add(e) для неё бессмысленна, нужен put(key, value). Зато карта отдаёт три коллекции-представления: keySet, values, entrySet. Реализации — HashMap, LinkedHashMap, TreeMap.

  • В Java 21 между Collection и List/Deque встал SequencedCollection, а у множеств и карт — SequencedSet и SequencedMap (JEP 431).
  • Методы записи в интерфейсах — необязательные операции: реализация может бросить UnsupportedOperationException. Поэтому один интерфейс покрывает и изменяемые, и неизменяемые коллекции.
  • RandomAccess — метка быстрого доступа по индексу, по ней алгоритмы Collections выбирают способ обхода.
Чем Collection отличается от Collections?

Collection — корневой интерфейс коллекций. Collections — служебный класс со статическими методами: sort, reverse, unmodifiableList, synchronizedMap, emptyList, frequency. Похожая пара — Array в reflection и служебный класс Arrays.

public void settle(ArrayList<Payment> payments) — метод только обходит платежи. Что не так с сигнатурой?

Параметр привязан к реализации: метод нельзя вызвать с List.of, LinkedList, результатом stream().toList() или Set, и вызывающим придётся копировать данные в ArrayList. Для обхода достаточно Collection<Payment> или даже Iterable<Payment>. Правило: в параметрах и возвращаемых типах — самый общий интерфейс, которого хватает; конкретный класс — только в new.

Как выбрать реализацию коллекции под задачу?

Я смотрю, какие операции должны быть быстрыми и нужен ли порядок обхода. Список с доступом по индексу — ArrayList. Очередь или стек — ArrayDeque. Быстрый contains и уникальность — HashSet, если важен порядок добавления — LinkedHashSet. Сортировка и поиск ближайшего — TreeSet или TreeMap за O(log n). Всегда брать самый приоритетный — PriorityQueue. Ключи-enum — EnumMap.

Например, проверку «счёт в стоп-листе» на каждом платеже делаю через HashSet, а не через List.contains: на ста тысячах счетов это O(1) против прохода по всему списку.

  • Коллекции хранят ссылки: миллион Long в HashSet занимает 64 МБ против 8 МБ в long[]. Для больших объёмов примитивов — массивы или fastutil/Eclipse Collections.
  • LinkedList почти никогда не выигрывает у ArrayList и ArrayDeque из-за промахов кеша и 24 байт на узел.
  • Если коллекцию читают из нескольких потоков — неизменяемая копия или коллекции из java.util.concurrent; Vector и Hashtable — наследие.
Подбери коллекцию: 1) убрать дубликаты id платежей, сохранив порядок прихода; 2) хранить курсы валют по дате и находить курс на ближайшую прошедшую дату; 3) очередь задач на выплату, где первыми идут самые крупные суммы.

1) LinkedHashSet: уникальность за O(1) и порядок вставки. 2) TreeMap<LocalDate, Rate> и floorEntry(date) — ближайший ключ не больше заданного за O(log n). 3) PriorityQueue с Comparator.comparing(Payout::amount).reversed(); если задачи берут несколько потоков — PriorityBlockingQueue.

static final List<String> BLOCKED = loadFromDb(); // 80 000 счетов … if (BLOCKED.contains(payment.account())) reject(); — вызывается на каждом платеже. Что поправить?

List.contains идёт по списку и вызывает equals до совпадения: 80 000 сравнений на каждый платёж, O(n). Нужен Set.copyOf(loadFromDb()) — поиск по хешу за O(1), заодно неизменяемый. Если у счёта может не быть значения, проверь null до вызова: Set.copyOf(...).contains(null) бросит NullPointerException.

Чем List.of отличается от Collections.unmodifiableList и Arrays.asList?

List.of и List.copyOf создают настоящую неизменяемую копию: любая запись — UnsupportedOperationException, null запрещён даже в contains. Collections.unmodifiableList — обёртка только для чтения над чужим списком: через неё писать нельзя, но изменения исходного списка через неё видны. Arrays.asList — представление массива фиксированной длины: set работает и пишет прямо в массив, а add и remove бросают исключение.

Поэтому из геттера сущности я возвращаю List.copyOf(items), если нужен снимок, и unmodifiableList, только если вызывающий должен видеть живые изменения.

  • stream().toList() (Java 16) неизменяем, но пропускает null. Collectors.toList() сейчас возвращает ArrayList, но javadoc изменяемость не обещает.
  • List.copyOf от уже неизменяемого списка возвращает тот же объект, без копирования.
  • Set.of и Map.of бросают IllegalArgumentException на дубликате и меняют порядок обхода от запуска к запуску.
String[] ids = {"a", "b", "c"}; List<String> list = Arrays.asList(ids); list.set(1, "X"); ids[2] = "Y"; — что в list и в ids? Что сделает list.remove("a")?

И list, и ids — [a, X, Y]: это одно и то же хранилище, изменения видны в обе стороны. list.remove("a") бросит UnsupportedOperationException: длина массива фиксирована. Если нужен обычный список — new ArrayList<>(Arrays.asList(ids)).

class Account { private final List<Payment> history = new ArrayList<>(); public List<Payment> getHistory() { return Collections.unmodifiableList(history); } } — отчёт обходит getHistory(), пока в счёт добавляют платежи. Что может пойти не так?

Обёртка не копирует данные: отчёт обходит тот же ArrayList, в который пишет другой код. В одном потоке это ConcurrentModificationException, если платёж добавят посреди обхода. Из разных потоков — вообще гонка без гарантий. Нужен снимок List.copyOf(history), а при записи из нескольких потоков — ещё и синхронизация в самом Account.

Почему List.of запрещает null?

Чтобы ошибка данных падала там, где null появился, а не позже в чужом коде. Ещё это делает однозначными ответы: indexOf, contains, Map.get — null из get у Map.of значит только «ключа нет». Цена — contains(null) тоже бросает NullPointerException, поэтому проверку на null делают до обращения к коллекции.

Что такое fail-fast итератор? Когда бывает ConcurrentModificationException?

Коллекции java.util считают структурные изменения — добавления и удаления — в поле modCount. Итератор при создании запоминает его значение и на каждом next() сравнивает. Если коллекцию изменили мимо итератора, счётчики расходятся, и итератор бросает ConcurrentModificationException вместо того, чтобы вернуть неверные данные.

Чаще всего это однопоточная ошибка: map.remove(key) внутри for-each по keySet(). Удалять при обходе нужно через iterator.remove() или removeIf — они обновляют ожидаемый счётчик.

  • Fail-fast — best effort: modCount не volatile, при гонке исключения может не быть. Опираться на него для корректности нельзя.
  • put по существующему ключу не структурное изменение и исключения не вызывает.
  • Итераторы ConcurrentHashMap слабо согласованные, CopyOnWriteArrayList — по снимку; ни те ни другие не бросают CME.
Что выведет этот код? 
import java.util.*;

public class Structural {
    public static void main(String[] args) {
        Map<String, Long> limits = new HashMap<>();
        limits.put("RUB", 100L); limits.put("USD", 5L); limits.put("EUR", 4L);
        for (String cur : limits.keySet()) limits.put(cur, limits.get(cur) * 2);
        System.out.println(limits);
        try {
            for (String cur : limits.keySet()) limits.put("CNY", 30L);
        } catch (ConcurrentModificationException e) { System.out.println("put нового ключа: " + e); }
        Iterator<String> it = limits.keySet().iterator();
        it.next(); it.remove();
        try { it.remove(); } catch (IllegalStateException e) { System.out.println("второй remove: " + e); }
    }
}

Удвоение лимитов проходит: замена значения у существующего ключа не меняет modCount. Новый ключ CNY — структурное изменение, и следующий next() бросает исключение. Второй it.remove() подряд — IllegalStateException: удалять можно только элемент, возвращённый последним next(), и только один раз.

for (Payment p : payments) if (p.status() == FAILED) payments.remove(p); — «в тестах работает». Что не так?

Удаление мимо итератора: на следующем next() будет ConcurrentModificationException. В тестах «работает», если там один неудачный платёж на предпоследнем месте — у ArrayList после такого удаления hasNext() возвращает false, и последний элемент тихо пропускается (разбор — тема List). Правильно: payments.removeIf(p -> p.status() == FAILED).

Что такое fail-safe итератор?

Так неофициально называют итераторы, которые не бросают CME при изменении коллекции. Их два вида. Снимок у CopyOnWriteArrayList: обходит массив на момент создания и изменений не видит. Слабо согласованный у ConcurrentHashMap и ConcurrentLinkedQueue: видит часть изменений, сделанных во время обхода, но никогда не падает и не возвращает элемент дважды.

Чем Comparable отличается от Comparator?

Comparable реализует сам класс: метод compareTo задаёт его естественный порядок — так сравниваются String, числа, даты. Comparator — отдельный объект с методом compare, его передают в sort, TreeMap, PriorityQueue. Порядков через компараторы может быть сколько угодно: платежи по сумме, по дате, по клиенту. Собираю их фабриками: Comparator.comparing(Payment::amount).thenComparing(Payment::id).

  • TreeSet и TreeMap определяют равенство через compare, а не equals: при несогласованном порядке «равные» элементы молча теряются.
  • BigDecimal: equals учитывает масштаб, compareTo — нет, поэтому 100 и 100.00 — два элемента в HashSet и один в TreeSet.
  • reversed() в конце цепочки переворачивает всю цепочку; для одного ключа — comparing(key, reverseOrder()).
new BigDecimal("100"), new BigDecimal("100.0") и new BigDecimal("100.00") кладут в HashSet и в TreeSet. Какие размеры у множеств?

HashSet — 3, TreeSet — 1. equals и hashCode у BigDecimal учитывают масштаб, поэтому для хеш-множества это разные элементы. compareTo сравнивает только значение и возвращает 0, и TreeSet считает их одним элементом. Проверено запуском в уроке.

Для отчёта «платежи по возрастанию суммы» написали new TreeSet<>(Comparator.comparing(Payment::amount)) и addAll(payments). Бухгалтерия говорит, что сумма по отчёту меньше реальной. Почему?

У платежей с одинаковой суммой компаратор возвращает 0, и TreeSet считает их дубликатами: add возвращает false, второй платёж не попадает в отчёт. Исправление — либо thenComparing(Payment::id), чтобы порядок различал все платежи, либо вообще не множество, а List и sort: сортировка ничего не выбрасывает.

Что такое Sequenced Collections в Java 21?

Это три новых интерфейса из JEP 431: SequencedCollection, SequencedSet и SequencedMap. Они объединили все коллекции с определённым порядком обхода — List, Deque, LinkedHashSet, TreeSet, LinkedHashMap, TreeMap — и дали им общие методы: getFirst, getLast, addFirst, addLast, removeFirst, removeLast и reversed(). Раньше последний элемент брали у каждого типа по-своему, а у LinkedHashSet — только обходом всего набора.

  • reversed() — представление, запись через него меняет исходную коллекцию.
  • У TreeSet addFirst бросает UnsupportedOperationException: место определяет компаратор. HashSet и HashMap не sequenced.
  • LinkedHashSet.addFirst и LinkedHashMap.putFirst переставляют существующий элемент в начало.
LinkedHashSet<String> s = new LinkedHashSet<>(List.of("a", "b", "c")); s.add("a"); s.addFirst("c"); s.reversed().addFirst("z"); — что в s?

[c, a, b, z]. add("a") ничего не меняет: элемент уже есть. addFirst("c") переставляет существующий c в начало. reversed().addFirst("z") — начало перевёрнутого представления — это конец исходного набора.

Почему HashSet не реализует SequencedCollection, а TreeSet реализует?

У TreeSet порядок обхода определён — по возрастанию, поэтому у него есть «первый» и «последний»: те же first() и last(). У HashSet порядок зависит от хешей и ёмкости таблицы и меняется при расширении, так что «последний элемент» ничего не значит.
