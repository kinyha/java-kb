Collectors

Коллектор — рецепт сборки стрима в результат из четырёх функций. supplier создаёт пустой контейнер, accumulator добавляет в него элемент, combiner сливает два контейнера — только в параллельном стриме, finisher превращает контейнер в результат. Стандартные коллекторы покрывают почти всё. toMap бросает IllegalStateException на повторяющемся ключе, если не задана функция слияния, и NullPointerException на null-значении. groupingBy возвращает HashMap списков и не принимает null-ключи. Второй аргумент groupingBy — downstream-коллектор, который собирает каждую группу отдельно: counting, summingLong, mapping, maxBy, вложенный groupingBy. partitioningBy всегда содержит оба ключа true и false, а groupingBy по условию — только встретившиеся. teeing (Java 12) собирает поток двумя коллекторами за один проход.

toMap: дубликаты и null

Отчёт по клиентам: сколько каждый заплатил. Естественная первая попытка — toMap(Payment::client, Payment::amount). Демо CollectorsDemo.java на пяти платежах трёх клиентов:

BATCH.stream().collect(toMap(Payment::client, Payment::amount));                          // падает
BATCH.stream().collect(toMap(Payment::client, Payment::amount, Long::sum, TreeMap::new));  // слияние и тип карты
BATCH.stream().collect(toMap(Payment::id, Payment::status));                               // статус p-5 = null
== toMap with a duplicate key
IllegalStateException: Duplicate key acme (attempted merging values 500 and 90000)
with merge Long::sum into TreeMap: {acme=90500, beta=70000, zeta=120300}
toMap with a null value: NullPointerException

У acme два платежа, и toMap без функции слияния падает с Duplicate key — сообщение (Java 9+) называет ключ и оба значения. Это осознанное решение: молча перезаписать значение было бы хуже. Третий аргумент — функция слияния: Long::sum для итога, (a, b) -> a чтобы оставить первое, (a, b) -> b — последнее. Четвёртый — фабрика карты: TreeMap::new для сортировки, LinkedHashMap::new для порядка появления. На тестах с уникальными ключами всё работает, а в проде первый же повтор роняет запрос — поэтому вопрос «что делать с дубликатом» нужно решить при написании, а не после инцидента.

Вторая ловушка — null-значение: статус p-5 ещё не известен, и toMap бросил NullPointerException, хотя HashMap сам null-значения допускает. Внутри toMap использует Map.merge, а он null-значения запрещает. Варианты: отфильтровать, подставить значение по умолчанию или собрать через collect(HashMap::new, (m, p) -> m.put(...), Map::putAll). Карта с семантикой HashMap из HashMap, но неизменяемая — toUnmodifiableMap.

groupingBy и downstream-коллекторы

== groupingBy and downstream collectors
groupingBy -> HashMap of ArrayList, RUB ids [p-1, p-3, p-4]
counting:      {EUR=1, RUB=3, USD=1}
summingLong:   {EUR=300, RUB=190500, USD=90000}
mapping ids:   {acme=p-1,p-2, beta=p-4, zeta=p-3,p-5}
max per client: {acme=p-2, beta=p-4, zeta=p-3}
two levels:    {acme={RUB=1, USD=1}, beta={RUB=1}, zeta={EUR=1, RUB=1}}

groupingBy(classifier) — HashMap<K, List<T>>: порядок ключей не определён, поэтому в демо результаты обёрнуты в TreeMap или собраны с фабрикой карты groupingBy(key, TreeMap::new, downstream). Downstream-коллекторы решают, что хранить в группе: counting(), summingLong, averagingDouble, mapping(f, downstream) — преобразовать элемент до сборки, filtering и flatMapping (Java 9), toSet(), maxBy/minBy — возвращают Optional, поэтому в демо обёрнуты в collectingAndThen(..., o -> o.get().id()); в непустой группе максимум есть всегда. Вложенный groupingBy даёт карту карт — отчёт клиент × валюта.

groupingBy a null key: NullPointerException (element cannot be mapped to a null key)

groupingBy не принимает null-ключ: платёж с неизвестным статусом уронил группировку по статусу с понятным сообщением. Нужен явный ключ для отсутствия — Optional.ofNullable(p.status()).orElse("UNKNOWN") — или фильтр. filtering внутри groupingBy отличается от filter перед ним: группа с нулём подходящих элементов останется в карте с пустым значением, а с внешним filter исчезнет.

partitioningBy, joining, teeing

== partitioningBy always has both keys
big (> 1 000 000): {false=5, true=0}
groupingBy same:   {false=5}

partitioningBy(predicate) — частный случай группировки на две части, но с гарантией: в результате всегда оба ключа. Крупных платежей нет, а true=0 в карте есть; groupingBy по тому же условию вернул карту только с false, и get(true) дал бы null. Для отчётов «прошли/не прошли» это разница между нулём и NullPointerException. Внутри partitioningBy — специальная карта из двух полей, а не HashMap.

== joining, teeing, summarizing
[p-1, p-2, p-3, p-4, p-5]
teeing min/max: p-5..p-3
stats: count 5, sum 280800, min 300, max 120000, avg 56160.0

joining(delimiter, prefix, suffix) собирает строки через StringBuilder — это и есть правильная замена конкатенации в цикле из Strings. teeing(c1, c2, merger) (Java 12) пропускает поток через два коллектора одновременно и объединяет результаты — минимум и максимум за один проход, без двух стримов и без сохранения элементов. summarizingLong считает количество, сумму, минимум, максимум и среднее разом; среднее — double, для денег его округляют явно, как в BigDecimal & Money.

Отчёт целиком: сортировка по значению и топ-N в группе

Map<String, Long> totals = BATCH.stream().collect(groupingBy(Payment::client, summingLong(Payment::amount)));
List<String> top = totals.entrySet().stream()
        .sorted(Map.Entry.<String, Long>comparingByValue().reversed().thenComparing(Map.Entry.comparingByKey()))
        .limit(2)
        .map(e -> e.getKey() + "=" + e.getValue())
        .toList();

== top-2 payments inside each currency
{EUR=[p-5], RUB=[p-3, p-4], USD=[p-2]}
== most frequent currency
RUB=5
== index by id, keeping order of appearance

Демо ReportDemo.java собирает задачи, которые чаще всего дают на live coding. Отсортировать карту по значению коллектор не умеет: карта упорядочена по ключам или не упорядочена вовсе. Поэтому отчёт делается в два этапа: сначала агрегат в карту, потом второй стрим по entrySet() с Map.Entry.comparingByValue(). Явный тип в Map.Entry.<String, Long>comparingByValue() нужен, потому что после .reversed() компилятор уже не выводит параметры. thenComparing по ключу делает результат детерминированным при равных суммах — без него порядок равных зависит от порядка HashMap.

Топ-N внутри каждой группы — collectingAndThen(toList(), l -> ...sorted().limit(2)): группа сначала собирается целиком, потом сортируется. Самый частый элемент — counting() и max(comparingByValue()) по записям. Индекс по идентификатору с сохранением порядка — toMap с LinkedHashMap::new. Больше таких задач с разбором — в Stream Practice.

В рабочем коде важно ещё одно решение: где агрегировать. groupingBy по миллиону платежей требует сначала загрузить миллион объектов из базы в память, а GROUP BY в SQL вернёт три строки. Агрегаты по большим таблицам считают в базе — с индексами и без передачи данных по сети, как в SQL. Коллекторы — для данных, которые уже в памяти: ответа внешнего API, небольшой выборки, результата нескольких запросов, которые нужно свести вместе. И даже там groupingBy без downstream держит всю группу в списках; counting, summingLong и teeing хранят только агрегат.

Коллектор изнутри

Collector<Payment, long[], Long> sum = Collector.of(
        () -> new long[1],                                    // supplier: пустой контейнер
        (acc, p) -> acc[0] += p.amount(),                     // accumulator: добавить элемент
        (a, b) -> { combines[0]++; a[0] += b[0]; return a; }, // combiner: слить два контейнера
        acc -> acc[0]);                                       // finisher: результат
== a collector is four functions
sequential: 280800, combiner calls 0
parallel:   280800, combiner calls 4

collect — изменяемая свёртка: в отличие от reduce из Stream API, который на каждом шаге создаёт новое значение, коллектор накапливает в изменяемый контейнер. В последовательном стриме контейнер один, и combiner не вызывается ни разу — его ошибки на тестах не видны. В параллельном каждая часть потока собирается в свой контейнер, а потом они сливаются попарно: пять элементов — пять частей — четыре слияния. Поэтому combiner обязан быть корректным, даже если вы пишете последовательный код: кто-то добавит .parallel(). Характеристики коллектора (IDENTITY_FINISH, UNORDERED, CONCURRENT) дают стриму право пропустить finisher или не сохранять порядок; groupingByConcurrent собирает все части в одну ConcurrentHashMap вместо слияния — об этом в Parallel Streams.

Свой коллектор пишут редко — обычно комбинации стандартных хватает. Хорошая причина — повторяющаяся доменная агрегация (сумма в Money с проверкой валюты, статистика по процентилям), которую удобно назвать и протестировать отдельно. Плохая — заменить простой цикл: шесть строк с Collector.of читаются хуже трёх строк с for.

toMap ведёт себя как HashMap.put: повторный ключ перезапишет значение, а null-значение допустимо.

Повторный ключ без функции слияния — IllegalStateException: Duplicate key, а null-значение — NullPointerException, потому что внутри используется Map.merge. В демо упали оба случая.

  • Коллектор: supplier, accumulator, combiner (только в параллельном), finisher.
  • toMap: дубликат без merge — IllegalStateException; null-значение — NPE; четвёртый аргумент — тип карты.
  • groupingBy — HashMap списков; downstream решает, что хранить: counting (Long), summingLong, mapping, maxBy, вложенный groupingBy.
  • groupingBy не принимает null-ключ; filtering сохраняет пустые группы, внешний filter — нет.
  • partitioningBy всегда содержит true и false.
  • joining — StringBuilder; teeing — два коллектора за проход; summarizing — пять агрегатов.
  • combiner надо писать корректно, даже если стрим сейчас последовательный.
  • Сортировка по значению — второй стрим по entrySet с comparingByValue; большие агрегаты — в SQL, а не в памяти.

На собеседовании

Что произойдёт, если в toMap встретятся одинаковые ключи?

IllegalStateException: Duplicate key. Чтобы обработать повторы, передают третий аргумент — функцию слияния: сумма, первое, последнее значение. Четвёртый аргумент задаёт реализацию карты — TreeMap, LinkedHashMap. Ещё одна ловушка — null-значение даёт NullPointerException, потому что внутри Map.merge.

  • Если нужен список всех значений по ключу — groupingBy, а не toMap.
  • toUnmodifiableMap запрещает и null-ключи.
Почему выгрузка падает только в проде? 
Map<String, Account> byIban = accounts.stream()
        .collect(Collectors.toMap(Account::iban, a -> a));

В тестовых данных IBAN уникальны, а в продакшене у одного клиента может быть закрытый и новый счёт с тем же IBAN, или данные просто содержат дубликаты. Первый повтор — IllegalStateException: Duplicate key. Нужно решить, что значит дубликат: оставить активный ((a, b) -> a.isActive() ? a : b), собрать все (groupingBy) или явно падать с понятной ошибкой валидации.

Как работает groupingBy и что такое downstream-коллектор?

groupingBy вычисляет ключ для каждого элемента и собирает элементы с одинаковым ключом. По умолчанию результат — HashMap<K, List<T>>. Второй аргумент — downstream-коллектор, который собирает каждую группу: counting, summingLong, mapping, toSet, maxBy, вложенный groupingBy. Можно задать фабрику карты, например TreeMap::new для сортировки ключей.

  • counting возвращает Long; maxBy — Optional, оборачивают collectingAndThen.
  • null-ключ — NullPointerException.
  • partitioningBy всегда содержит оба ключа, groupingBy по условию — нет.

Из чего состоит Collector?

Из четырёх функций: supplier создаёт контейнер, accumulator добавляет элемент, combiner сливает два контейнера, finisher превращает контейнер в результат. Плюс характеристики: IDENTITY_FINISH, UNORDERED, CONCURRENT. collect — изменяемая свёртка, в отличие от reduce.

  • combiner вызывается только в параллельном стриме — ошибки в нём не видны на последовательных тестах.
  • CONCURRENT + UNORDERED позволяют собирать в один общий контейнер.

Как найти топ-3 клиентов по сумме платежей стримом?

Сначала groupingBy по клиенту с summingLong, потом стрим по entrySet: sorted по Map.Entry.comparingByValue().reversed(), limit(3), map в нужный вид. Сортировать саму карту по значению нельзя — её порядок задают ключи. Для детерминированности при равных суммах добавляют thenComparing по ключу.

  • Для большого числа клиентов вместо полной сортировки — куча на 3 элемента.
  • Если данные в базе — GROUP BY ... ORDER BY ... LIMIT 3, а не загрузка в память.
  • Collectors — toMap, groupingBy, partitioningBy, teeing.
  • Collector — функции, характеристики, требования identity и associativity.
