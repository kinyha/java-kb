Concurrency: CompletableFuture

Три асинхронных вызова, а ответ не быстрее последовательного

Перед платежом сервис спрашивает три других: данные клиента (100 мс), лимиты (150 мс) и курс валюты (120 мс). По очереди это 370 мс. Разработчик переписал на CompletableFuture — и получил ровно столько же:

import java.util.concurrent.*;

public class Checkout {
    static final ExecutorService io = Executors.newFixedThreadPool(8);   // пул для вызовов сервисов

    static String call(String service, int ms) {
        try { Thread.sleep(ms); } catch (InterruptedException e) { throw new RuntimeException(e); }
        return service;
    }

    public static void main(String[] args) {
        long start = System.nanoTime();
        String a = call("клиент", 100), b = call("лимиты", 150), c = call("курс", 120);   // по очереди
        System.out.printf("последовательно:         %d мс%n", (System.nanoTime() - start) / 1_000_000);

        start = System.nanoTime();
        String a2 = CompletableFuture.supplyAsync(() -> call("клиент", 100), io).join();   // запустили — и сразу ждём
        String b2 = CompletableFuture.supplyAsync(() -> call("лимиты", 150), io).join();
        String c2 = CompletableFuture.supplyAsync(() -> call("курс", 120), io).join();
        System.out.printf("supplyAsync + join сразу: %d мс%n", (System.nanoTime() - start) / 1_000_000);

        start = System.nanoTime();
        CompletableFuture<String> client = CompletableFuture.supplyAsync(() -> call("клиент", 100), io);
        CompletableFuture<String> limits = CompletableFuture.supplyAsync(() -> call("лимиты", 150), io);
        CompletableFuture<String> rate = CompletableFuture.supplyAsync(() -> call("курс", 120), io);
        String all = CompletableFuture.allOf(client, limits, rate)          // все три идут одновременно
            .thenApply(v -> client.join() + " + " + limits.join() + " + " + rate.join())
            .join();
        System.out.printf("все три параллельно:     %d мс → %s%n", (System.nanoTime() - start) / 1_000_000, all);
        io.shutdown();
    }
}
последовательно:         385 мс
supplyAsync + join сразу: 379 мс
все три параллельно:     156 мс → клиент + лимиты + курс

Вторая версия запускает вызов в другом потоке и тут же ждёт его. Асинхронности нет, есть только лишний переход между потоками. Выигрыш появляется, когда все три запущены до первого ожидания. Тогда время равно самому долгому вызову, 150 мс, а не сумме.

CompletableFuture — это обещание результата, которое можно завершить позже и на которое можно навесить следующие шаги, не блокируя поток. В этой теме — чем он отличается от обычного Future, thenApply и thenCompose, в каком потоке выполняется каждый шаг, как идут ошибки по цепочке, как объединять результаты и ставить таймауты — и почему cancel(true) ничего не отменяет.

Future можно только ждать, CompletableFuture — продолжать

Обычный Future из ExecutorService.submit умеет немного: проверить готовность, отменить и ждать через get(). Чтобы что-то сделать с результатом, поток должен заблокироваться. CompletableFuture реализует Future и добавляет CompletionStage — цепочки продолжений, которые выполнятся, когда результат будет готов:

МетодЧто делаетАналог в стримах
supplyAsync(supplier, executor)запустить задачу с результатом—
thenApply(f)преобразовать результат: T → Umap
thenCompose(f)продолжить асинхронным шагом: T → CompletableFuture<U>flatMap
thenCombine(other, f)объединить два независимых результата—
thenAccept, thenRunпотребить результат / просто выполнить послеforEach
allOf, anyOfдождаться всех / первого—
exceptionally, handle, whenCompleteобработка ошибок — шаг 4—
complete(v), completeExceptionally(e)завершить вручную, например из колбэка чужой библиотеки—

Разница между thenApply и thenCompose — как между map и flatMap. Если шаг сам возвращает CompletableFuture, thenApply завернёт его во второй слой:

import java.util.concurrent.*;

public class Errors {
    static CompletableFuture<Long> balance(String account) {                 // асинхронный запрос баланса
        return CompletableFuture.supplyAsync(() -> {
            if (account.equals("blocked")) throw new IllegalStateException("счёт заблокирован");
            return 1_000L;
        });
    }

    public static void main(String[] args) throws Exception {
        CompletableFuture<CompletableFuture<Long>> nested = CompletableFuture.completedFuture("acc-1").thenApply(Errors::balance);
        CompletableFuture<Long> flat = CompletableFuture.completedFuture("acc-1").thenCompose(Errors::balance);
        System.out.println("thenApply:   " + nested.join().join() + " (пришлось join дважды)");
        System.out.println("thenCompose: " + flat.join());

        CompletableFuture<String> failed = balance("blocked")
            .thenApply(b -> { System.out.println("этап не выполнится"); return b * 2; })  // пропускается
            .thenApply(b -> "баланс " + b);
        try { failed.join(); } catch (CompletionException e) { System.out.println("join бросил: " + e); }
        try { failed.get(); } catch (ExecutionException e) { System.out.println("get бросил:  " + e.getClass().getSimpleName() + " с причиной " + e.getCause().getMessage()); }

        String recovered = failed.exceptionally(e -> "баланс недоступен: " + e.getCause().getMessage()).join();
        System.out.println("exceptionally: " + recovered);

        String handled = balance("acc-1").handle((b, e) -> e == null ? "баланс " + b : "ошибка").join();
        System.out.println("handle:        " + handled);

        try {
            balance("blocked").whenComplete((b, e) -> System.out.println("whenComplete увидел ошибку: " + (e != null))).join();
        } catch (CompletionException e) {
            System.out.println("после whenComplete ошибка осталась: " + e.getCause().getMessage());
        }
    }
}
thenApply:   1000 (пришлось join дважды)
thenCompose: 1000
join бросил: java.util.concurrent.CompletionException: java.lang.IllegalStateException: счёт заблокирован
get бросил:  ExecutionException с причиной счёт заблокирован
exceptionally: баланс недоступен: счёт заблокирован
handle:        баланс 1000
whenComplete увидел ошибку: true
после whenComplete ошибка осталась: счёт заблокирован

Первые две строки — о thenCompose: с ним цепочка остаётся плоской, CompletableFuture<Long> вместо вложенного. Остальной вывод разберём в шаге 4.

Шаг без Async выполняется в том потоке, который оказался рядом

Самый частый вопрос на собеседовании про CompletableFuture — в каком потоке выполнится thenApply. Ответ зависит от момента регистрации:

import java.util.concurrent.*;

public class WhichThread {
    static String name() { return Thread.currentThread().getName(); }

    public static void main(String[] args) throws Exception {
        ExecutorService bank = Executors.newSingleThreadExecutor(r -> new Thread(r, "bank-io"));

        CompletableFuture<Integer> done = CompletableFuture.completedFuture(1);          // уже завершён
        done.thenApply(x -> { System.out.println("thenApply на готовом:    " + name()); return x; });

        CompletableFuture<Integer> slow = CompletableFuture.supplyAsync(() -> {           // завершится позже
            try { Thread.sleep(100); } catch (InterruptedException e) { }
            return 1;
        }, bank);
        slow.thenApply(x -> { System.out.println("thenApply на незавершённом: " + name()); return x; });
        slow.thenApplyAsync(x -> { System.out.println("thenApplyAsync:            " + name()); return x; });
        slow.thenApplyAsync(x -> { System.out.println("thenApplyAsync(executor):  " + name()); return x; }, bank);
        Thread.sleep(300);
        bank.shutdown();
    }
}
thenApply на готовом:    main
thenApply на незавершённом: bank-io
thenApplyAsync:            ForkJoinPool.commonPool-worker-1
thenApplyAsync(executor):  bank-io
  • Шаг без Async, будущее уже завершено — выполняется сразу в потоке, который вызвал thenApply, здесь main.
  • Шаг без Async, будущее ещё не завершено — выполнится в потоке, который его завершит, здесь bank-io. Какой из двух случаев сработает, зависит от гонки: код один, а поток разный.
  • thenApplyAsync(f) — в ForkJoinPool.commonPool().
  • thenApplyAsync(f, executor) — в указанном пуле.

Отсюда практические правила. Тяжёлый или блокирующий шаг без Async может выполниться в потоке ввода-вывода чужой библиотеки — например, в event loop HTTP-клиента — и остановить его. Блокирующие шаги и supplyAsync всегда получают свой пул вторым аргументом. Иначе они уходят в commonPool, где, как в теме Executors, мешают всем остальным. И ещё: в другом потоке нет ThreadLocal вызывающего — ни MDC, ни пользователя Spring Security, ни транзакции (тема Threads).

Ошибка пропускает все шаги до ближайшего обработчика

Исключение внутри шага завершает его будущее с ошибкой. Все следующие thenApply, thenCompose и thenAccept пропускаются: в выводе шага 2 нет строки «этап не выполнится». Ошибка доходит до ближайшего обработчика:

Три обработчика из вывода шага 2 ведут себя по-разному:

МетодКогда вызываетсяВосстанавливает?
exceptionally(e -> value)только при ошибкеда, заменяет ошибку значением
handle((value, e) -> result)всегда; одно из двух — nullда, возвращает новый результат
whenComplete((value, e) -> ...)всегданет: ошибка идёт дальше, как в последней строке вывода

Детали, на которых ошибаются:

  • Исключение приходит в обработчик обёрнутым в CompletionException, поэтому исходную ошибку достают через e.getCause(). В шаге 2 так сделано в exceptionally.
  • join() бросает unchecked CompletionException, get() — checked ExecutionException. В лямбдах удобнее join().
  • Цепочка без обработчика и без join() в конце теряет ошибку так же молча, как submit() в теме Executors.

allOf ждёт всех даже после первой ошибки, а таймаут не останавливает задачу

allOf возвращает CompletableFuture<Void>: он лишь сообщает, что все завершились, а результаты забирают из исходных будущих через join(), как в шаге 1. anyOf — первый завершившийся. Что происходит, если один из вызовов падает сразу:

import java.util.concurrent.*;

public class AllOfFail {
    static CompletableFuture<String> call(String name, int ms, boolean fail) {
        return CompletableFuture.supplyAsync(() -> {
            try { Thread.sleep(ms); } catch (InterruptedException e) { }
            if (fail) throw new IllegalStateException(name + " недоступен");
            return name;
        });
    }

    public static void main(String[] args) {
        long start = System.nanoTime();
        try {
            CompletableFuture.allOf(call("клиент", 100, false), call("лимиты", 20, true), call("курс", 300, false)).join();
        } catch (CompletionException e) {
            System.out.printf("allOf: %s — через %d мс%n", e.getCause().getMessage(), (System.nanoTime() - start) / 1_000_000);
        }
        start = System.nanoTime();
        Object first = CompletableFuture.anyOf(call("банк А", 120, false), call("банк Б", 60, false)).join();
        System.out.printf("anyOf: первым ответил %s — через %d мс%n", first, (System.nanoTime() - start) / 1_000_000);
    }
}
allOf: лимиты недоступен — через 304 мс
anyOf: первым ответил банк Б — через 65 мс

Лимиты упали через 20 мс, но allOf сообщил об этом через 304 мс — когда закончился самый долгий вызов. Если ответ бессмыслен без всех частей, это лишнее ожидание. «Упасть при первой ошибке» allOf не умеет. Приходится вешать на каждое будущее exceptionally, которое завершает общий результат с ошибкой. В Java 21 это делает structured concurrency в статусе preview (тема Virtual Threads).

Таймауты появились в Java 9 и выглядят так же непривычно:

import java.util.concurrent.*;
import java.util.concurrent.atomic.AtomicBoolean;

public class Timeouts {
    static CompletableFuture<String> rate(int ms, AtomicBoolean finished) {   // сервис курсов отвечает ms миллисекунд
        return CompletableFuture.supplyAsync(() -> {
            try { Thread.sleep(ms); } catch (InterruptedException e) { return "прерван"; }
            finished.set(true);
            return "курс 90.1";
        });
    }

    public static void main(String[] args) throws Exception {
        AtomicBoolean f1 = new AtomicBoolean();
        try {
            rate(2_000, f1).orTimeout(200, TimeUnit.MILLISECONDS).join();       // не дождались — ошибка
        } catch (CompletionException e) {
            System.out.println("orTimeout: " + e.getCause());
        }
        String cached = rate(2_000, new AtomicBoolean())
            .completeOnTimeout("курс из кеша 90.0", 200, TimeUnit.MILLISECONDS).join();  // не дождались — значение
        System.out.println("completeOnTimeout: " + cached);

        AtomicBoolean f2 = new AtomicBoolean();
        CompletableFuture<String> call = rate(500, f2);
        Thread.sleep(100);
        System.out.println("cancel(true): " + call.cancel(true) + ", isCancelled: " + call.isCancelled());
        Thread.sleep(600);
        System.out.println("а задача всё равно доработала: " + f2.get());
        Thread.sleep(1_200);
        System.out.println("задача после orTimeout тоже доработала: " + f1.get());
    }
}
orTimeout: java.util.concurrent.TimeoutException
completeOnTimeout: курс из кеша 90.0
cancel(true): true, isCancelled: true
а задача всё равно доработала: true
задача после orTimeout тоже доработала: true

orTimeout завершает будущее с TimeoutException, completeOnTimeout — запасным значением. Но задача, которая считала результат, об этом не узнаёт. Та же история с cancel(true): будущее отменено, а задача доработала до конца. В отличие от FutureTask из ExecutorService, CompletableFuture не знает, в каком потоке выполняется его задача, и параметр mayInterruptIfRunning игнорирует — так написано в javadoc. Значит, настоящий таймаут на ввод-вывод ставят в самом клиенте: таймаут HTTP-запроса, queryTimeout в JDBC. Таймаут будущего только перестаёт ждать.

  • Параллельность появляется, только если все задачи запущены до первого ожидания. supplyAsync(...).join() подряд — это последовательный код.
  • thenApply — map, thenCompose — flatMap для шага, который сам асинхронный. thenCombine объединяет два независимых результата.
  • Шаг без Async выполняется в вызывающем потоке, если будущее уже готово, или в потоке, который его завершит. *Async без пула уходит в commonPool. Блокирующим шагам — свой пул.
  • Ошибка пропускает шаги до обработчика. exceptionally и handle восстанавливают, whenComplete — нет. Причина лежит в CompletionException.getCause().
  • allOf ждёт всех даже после ошибки и возвращает Void. orTimeout, completeOnTimeout и cancel(true) не останавливают саму задачу.

На собеседовании

Чем CompletableFuture отличается от Future?

Future позволяет только проверить готовность, отменить и заблокироваться на get(). CompletableFuture реализует ещё CompletionStage: на него навешивают продолжения (thenApply, thenCompose, thenCombine), объединяют несколько (allOf, anyOf), обрабатывают ошибки (exceptionally, handle) без блокировки потоков. Его можно завершить вручную через complete, есть таймауты orTimeout и completeOnTimeout.

Чем thenApply отличается от thenCompose?

thenApply преобразует результат синхронной функцией T → U, как map. thenCompose принимает функцию, которая сама возвращает CompletableFuture<U>, и «разворачивает» его, как flatMap. Если передать асинхронный шаг в thenApply, получится CompletableFuture<CompletableFuture<U>>, и придётся ждать дважды.

В каком потоке выполняется thenApply?

Если будущее уже завершено к моменту вызова — сразу в вызывающем потоке. Если нет — в потоке, который его завершит. thenApplyAsync(f) выполняется в ForkJoinPool.commonPool(), thenApplyAsync(f, executor) — в указанном пуле. supplyAsync без пула тоже использует commonPool.

  • Из-за гонки один и тот же код выполняется то в одном потоке, то в другом. Тяжёлый шаг без Async может заблокировать поток ввода-вывода чужой библиотеки.
  • Блокирующие вызовы в commonPool тормозят параллельные стримы и все *Async без своего пула.
  • ThreadLocal-контекст (MDC, security, транзакция) в другой поток не переходит.
В контроллере: CompletableFuture.supplyAsync(() -> jdbcTemplate.query(...)).thenApply(this::toDto). Что не так?

Блокирующий запрос к базе уходит в commonPool, рассчитанный на вычисления: под нагрузкой он займёт все его потоки и затормозит остальных пользователей пула. Нужен отдельный пул под базу, размером не больше пула соединений, и вторым аргументом supplyAsync. Ещё в потоке пула не будет транзакции и контекста безопасности вызывающего потока.

Как обрабатывать ошибки в CompletableFuture?

Исключение завершает будущее с ошибкой, и все следующие шаги пропускаются до обработчика. exceptionally вызывается только при ошибке и возвращает значение взамен. handle вызывается всегда, получает значение или ошибку и возвращает новый результат. whenComplete вызывается всегда, но результат не меняет: ошибка идёт дальше. В обработчик исключение приходит обёрнутым в CompletionException, исходное — в getCause(). join() бросает CompletionException, get() — ExecutionException.

allOf(a, b, c), где b падает через 20 мс, а c работает 300 мс. Когда join() на allOf бросит исключение?

Через 300 мс, когда завершится последний. allOf ждёт всех, даже если кто-то уже упал, — в замере урока 304 мс. Чтобы падать сразу, на каждое будущее навешивают обработчик, который завершает общий результат с ошибкой, или используют structured concurrency.

Останавливает ли cancel(true) или orTimeout задачу CompletableFuture?

Нет. CompletableFuture не знает, какой поток выполняет его задачу, и cancel(true) не прерывает её: будущее помечается отменённым, а задача дорабатывает. orTimeout и completeOnTimeout так же только завершают будущее. В замере урока задачи доработали до конца после отмены и после таймаута. Реальный таймаут на ввод-вывод ставят в клиенте: HTTP, JDBC, брокера сообщений.

  • CompletableFuture (JDK 21) — основа урока: правила выполнения шагов, исключения, cancel без прерывания.
  • CompletionStage (JDK 21) — контракт продолжений и обработки ошибок.
  • JEP 453: Structured Concurrency (Preview) — альтернатива allOf с отменой остальных при первой ошибке.
