Big O

Маленькая сверка скрывает квадратичный рост

Сервис сверки сравнивает каждый платёж в пакете с каждым следующим: ищет подозрительно похожие операции. На тысяче платежей проверок около полумиллиона. Вчера пакет вырос до ста тысяч — теперь почти пять миллиардов сравнений. Ускорить само сравнение вдвое полезно, но это не отменяет рост количества пар.

Прежде чем ставить O, назови размер входа и единицу работы. Здесь n — число платежей, а единица — одно сравнение пары фиксированных по размеру записей. Сеть, чтение базы и разбор JSON в этот счётчик не входят: их стоимость придётся оценить отдельно, если они есть в реальном обработчике.

Сохрани как CostMeter.java, запусти java CostMeter.java на JDK 21.

public class CostMeter {
    static long compareEveryPair(int n) {
        long checks = 0;
        for (int i = 0; i < n; i++) {
            for (int j = i + 1; j < n; j++) {
                checks++; // Сравниваем два разных платежа ровно один раз.
            }
        }
        return checks;
    }

    public static void main(String[] args) {
        for (int n : new int[]{5, 10, 1000, 2000}) {
            System.out.println(n + " payments: " + compareEveryPair(n));
        }
    }
}

При удвоении n с 1000 до 2000 работа увеличилась почти в четыре раза. Это не измеренные миллисекунды: счётчик доказывает число посещённых пар и не зависит от JIT, скорости CPU или фоновых процессов.

Первый платёж сравнивается с n − 1 следующими, второй — с n − 2. Складываем: (n − 1) + … + 1 = n(n − 1)/2. Удаление симметричных повторов уменьшило константу, но не степень n. На собеседовании это различие важнее фразы «там два for».

Оценка начинается с суммы выполненной работы

Запись T(n) ∈ O(f(n)) означает верхнюю асимптотическую границу: существуют постоянные c > 0 и n₀, после которых T(n) ≤ c·f(n). Для числа пар достаточно f(n) = n². Множитель 1/2 и линейное слагаемое не меняют класс роста: при больших n они укладываются в постоянный множитель.

Ω(f(n)) задаёт нижнюю границу, а Θ(f(n)) — обе сразу. Для полного перебора пар точная по порядку оценка Θ(n²). O(n³) тоже верная верхняя граница, но бесполезно рыхлая. Когда интервьюер просит «Big O», обычно ожидает наиболее точную простую верхнюю оценку, а не любую формально верную.

Последовательные части складываются: проверить n платежей, затем m счетов — Θ(n + m). Сопоставить каждый платёж каждому счёту — Θ(n·m). Не заменяй разные размеры одной буквой без условия m = n. Если длина номера счёта L переменна, сравнение двух строк в худшем случае потребует Θ(L) работы, а не одной операции.

Для n = 2²⁰ линейный проход — 1 048 576 единиц работы, n·log₂ n — 20 971 520, а n² — 1 099 511 627 776. Сам логарифм равен 20: столько делений пополам нужно, чтобы из 2²⁰ получить 1. Это сравнение моделей стоимости, а не обещание времени выполнения.

Глубина вложенности циклов и есть степень n.

Нужно сложить фактические длины проходов. Вложенный while, который суммарно двигает левую границу лишь n раз, даёт линейную работу. Если границу сбрасывать на каждой внешней итерации, доказательство исчезает. Такой подсчёт используется в Sliding Window.

Под капотом: что считается операцией за O(1)

В модели word RAM считаем чтение машинного слова и арифметику над ним постоянными по цене. Это подходит для ограниченных int/long, пока контролируем переполнение. Для BigInteger длина числа растёт, и сложение требует прохода по его машинным словам. Перебор до числового значения V — O(V), но при входе из b бит V может быть порядка 2ᵇ: «линейно по значению» не означает линейно по длине записи входа.

Случай входа выбирают отдельно от O-нотации

В журнале платежей ищем конкретный ID. Совпадение в первой записи требует одного сравнения, в последней — n. Если ID отсутствует, тоже проверяем все n записей. Алгоритм один, длина входа одна, но стоимость зависит от содержимого и положения ответа.

Сохрани как SearchCost.java, запусти java SearchCost.java на JDK 21.

public class SearchCost {
    static int comparisons(int[] ids, int target) {
        int count = 0;
        for (int id : ids) {
            count++;
            if (id == target) break; // Ранний выход меняет стоимость конкретного входа.
        }
        return count;
    }

    public static void main(String[] args) {
        int[] ids = {11, 22, 33, 44};
        System.out.println(comparisons(ids, 11));
        System.out.println(comparisons(ids, 44));
        System.out.println(comparisons(ids, 99));
    }
}

4
4

Лучший случай этого поиска — Θ(1), худший — Θ(n). Средний успешный поиск стоит (n + 1)/2 сравнений при условии, что нужная запись равновероятно находится в любой из n позиций. Если распределение запросов неизвестно, это число нельзя выдавать за характеристику реального сервиса.

Математическое ожидание может браться и по случайным решениям самого алгоритма при фиксированном входе. Например, случайный выбор опорного элемента меняет дерево разбиений quicksort. Поэтому в ответе нужно назвать источник вероятности: распределение данных или внутреннюю рандомизацию.

O означает худший случай, а Ω — лучший.

Это разные оси описания. Сначала выбираешь функцию: например, максимальное время среди входов размера n. Затем даёшь её верхнюю, нижнюю или точную по порядку границу. Худший случай линейного поиска одновременно O(n) и Ω(n).

Редкие копирования оплачивает вся серия добавлений

Платежи накапливаются в расширяемом буфере. Пока в массиве есть место, добавить запись дёшево. Когда места нет, выделяем массив вдвое больше, переносим все старые записи и добавляем новую. Одна операция становится линейной по текущему размеру, хотя большинство добавлений не копируют ничего.

После n добавлений из пустого буфера ёмкости 1 каждый платёж записан один раз. Дополнительные переносы происходят пачками 1, 2, 4, …, 2ᵏ, где последнее число меньше n. Их сумма 2ᵏ⁺¹ − 1 < 2n. Вместе с n новыми записями это меньше 3n единиц работы: амортизированно O(1) на добавление.

Вероятность здесь не нужна. Граница верна для всей такой последовательности, даже если пользователь специально остановился сразу после дорогого расширения. Но она не обещает O(1) для отдельно взятого добавления. Если анализ начинаешь с уже заполненного буфера большого размера, его начальное состояние тоже надо учесть в стоимости.

Сохрани как GrowthCost.java, запусти java GrowthCost.java на JDK 21.

import java.util.Arrays;

public class GrowthCost {
    public static void main(String[] args) {
        int[] buffer = new int[1];
        int size = 0;
        long total = 0;
        for (int payment = 1; payment <= 9; payment++) {
            int copies = 0;
            if (size == buffer.length) {
                copies = size; // Каждую старую запись переносим в новый массив.
                buffer = Arrays.copyOf(buffer, buffer.length * 2);
            }
            buffer[size++] = payment;
            int cost = copies + 1; // Считаем переносы и запись; не наносекунды.
            total += cost;
            System.out.println("add=" + payment + " capacity=" + buffer.length
                    + " cost=" + cost + " total=" + total);
        }
    }
}

Здесь намеренно считаем только переносы и записи. Выделение и обнуление нового массива тоже требуют линейной работы по его длине, но сумма геометрически растущих длин остаётся O(n). Если увеличивать ёмкость на одну ячейку, переносы дадут 1 + 2 + … + (n − 1) = Θ(n²).

Что именно гарантирует Java ArrayList

Javadoc JDK 21 гарантирует амортизированное постоянное время add и линейную суммарную стоимость n добавлений. Точный коэффициент роста не является контрактом API. Удвоение в примере — наша учебная политика, не обещание, что ArrayList растёт именно так. Если верхняя граница размера пакета известна, предварительная ёмкость переносит выделение памяти в начало, но увеличивает резерв.

Для обработчика с ограничением на задержку отдельного запроса важен дорогой resize, а не только средняя стоимость серии. Предварительная ёмкость, ограниченный размер пакета и метрики выделения памяти помогают связать математическую оценку с наблюдаемым скачком latency.

Память считают по одновременно живому состоянию

Время суммирует выполненную работу. Дополнительная память — максимальный объём одновременно нужного состояния сверх входа; договорись отдельно, входит ли в неё результат. Массив из n платежей уже дан на входе: пара индексов и счётчик требуют O(1) дополнительной памяти. Копия массива потребует O(n), даже если копирование спрятано за одной строкой API.

Рекурсивная сумма делит диапазон платежей пополам и передаёт границы, а не копирует куски массива. Для четырёх элементов будет семь вызовов, но одновременно активны максимум три. Вызовы левого и правого поддеревьев идут последовательно: после возврата слева его кадры освобождены, остаётся одно значение суммы.

Сохрани как CallSpace.java, запусти java CallSpace.java на JDK 21.

public class CallSpace {
    static int calls, maxDepth;

    static long sum(int[] amounts, int from, int to, int depth) {
        calls++;
        maxDepth = Math.max(maxDepth, depth);
        if (to - from == 1) return amounts[from];
        int mid = from + (to - from) / 2;
        long left = sum(amounts, from, mid, depth + 1);
        // Левый вызов уже завершён; в кадре остался только его результат.
        long right = sum(amounts, mid, to, depth + 1);
        return left + right;
    }

    public static void main(String[] args) {
        System.out.println("sum=" + sum(new int[]{10, 20, 30, 40}, 0, 4, 1));
        System.out.println("calls=" + calls + " maxDepth=" + maxDepth);
    }
}

calls=7 maxDepth=3

В этом примере n ≥ 1; для пустого входа нужна отдельная проверка перед вызовом. Дерево содержит 2n − 1 вызовов, поэтому время Θ(n). Максимальная глубина Θ(log n), каждый кадр хранит постоянное число значений: дополнительная память O(log n). Цикл посчитает ту же сумму за Θ(n) времени и O(1) памяти. Если рекурсия уменьшает n лишь на 1, стек уже линейный; подробнее — в теме Recursion.

Не путай пиковое состояние и суммарный объём выделений. Создать и отпустить n временных массивов длины n — Θ(n²) выделенных ячеек за весь запуск, хотя алгоритму может быть нужен только один массив за раз. Реальный heap дополнительно зависит от того, когда GC уберёт недостижимые объекты.

Ещё одна граница — размер ответа. Если API должно вернуть все n(n − 1)/2 пар платежей, хранение ответа само требует Θ(n²) ячеек, а запись всех пар — Ω(n²) времени. Потоковая выдача уменьшит одновременную память, но не число элементов результата. Это причина заранее уточнить: нужны сами пары, их количество или только факт существования.

Асимптотика не предсказывает миллисекунды

Метод с одним циклом не обязан быть линейным. Если внутри каждого шага вызывается LinkedList.get(i), список заново проходит от ближайшего края к индексу. Сумма расстояний до середины и обратно растёт как n². Итератор хранит текущий узел и проходит каждое ребро один раз — именно поэтому он устраняет лишнюю работу.

Стоимость библиотечного вызова входит в стоимость алгоритма. Для хеш-таблицы ожидаемое O(1) доступа требует подходящего распределения хешей и учёта цены hashCode/equals. Если ключ — длинная строка, первое вычисление её хеша и сравнение могут зависеть от длины. Аллокации, упаковка чисел и локальность памяти не меняют буквенную оценку, но могут изменить практический выбор при заданном n.

Подготовку нельзя прятать: если сначала сортируешь n платежей, а потом делаешь q двоичных поисков, получаешь O(n log n + q log n), а не просто O(log n). Нужно также учесть память выбранной сортировки. Когда q = 1, построение индекса может оказаться дороже одного линейного просмотра.

На собеседовании называй размер входа, модель операции, нужный случай, суммарную работу и дополнительную память. Затем проверяй ограничения и крайние входы. Для измерения производительности Java пригодится JMH: прогрев, отдельные JVM и использование результата помогают не принять работу JIT или удалённое вычисление за ускорение алгоритма. Измеряй несколько размеров и распределений данных; математическая оценка объясняет тенденцию, а замер — конкретную среду.

Посчитать пары, не перебирая их

В пакете n платежей, 0 ≤ n ≤ 10⁹. Верни количество неупорядоченных пар разных платежей. Нужен только счётчик; сами записи читать не надо. Найди решение без цикла и объясни, почему это не противоречит квадратичной сложности проверки всех пар.

n = 5 → 10

Подсказка 1

Посчитай длины строк треугольника сравнений.

Подсказка 2

Каждая из n записей имеет n − 1 партнёров, но пару посчитали дважды. Продумай тип до умножения.

Решение

Для каждого платежа есть n − 1 другой. Упорядоченных пар n(n − 1), неупорядоченных вдвое меньше. Размер счётчика фиксирован, и для данного диапазона long хватает.

    static long pairs(int n) {
        return (long) n * (n - 1) / 2; // Расширяем ДО умножения, иначе int переполнится.
    }

Формула считает количество за O(1) времени и памяти в модели машинных слов. Она не выполняет проверку содержимого каждой пары. Если требуется вывести пары или сравнить их поля, число таких действий остаётся Θ(n²).

Почему return (long) (n * (n - 1)) / 2 даёт неверный ответ?

Умножение произойдёт в int и может переполниться до преобразования. Приведи хотя бы один операнд к long заранее. Тест 65 537 проверяет эту границу.

А если n дан как строка с миллионом цифр?

Тогда чтение входа и арифметика уже зависят от длины записи. Нельзя переносить оценку O(1) для фиксированного машинного слова на произвольную точность.

Вложенный цикл с уменьшающимся пакетом

Обработчик делает проход по n записям, потом по ⌊n/2⌋, потом по ⌊n/4⌋ и так до нуля. Каждое посещение стоит одну единицу. Для 0 ≤ n ≤ 10⁹ верни точное число посещений, не выполняя сами проходы. Оцени отдельно исходный обработчик и свой калькулятор.

n = 8: 8 + 4 + 2 + 1 → 15
n = 5: 5 + 2 + 1 → 8

Подсказка 2

На каждой стадии прибавь размер оставшегося пакета и раздели размер на 2.

Решение

Симулируем только смену размера. Каждый полный проход заменяется одним сложением его длины. Для степеней двойки точный результат 2n − 1, но при округлении вниз для других n это уже не равенство.

    static long work(int n) {
        long total = 0;
        for (int size = n; size > 0; size /= 2) {
            total += size; // Сразу прибавляем длину прохода, сам проход не выполняем.
        }
        return total;
    }

Исходный обработчик делает от n до менее 2n посещений: Θ(n). Калькулятор делает Θ(log n) стадий для n ≥ 2 и использует O(1) памяти. Само возвращаемое число может быть линейным по n, хотя его вычисление не требует стольких действий.

Что изменится, если каждый проход всё время имеет длину n?

Стадий останется Θ(log n), но каждая стоит Θ(n): всего Θ(n log n). Геометрическая сумма больше не описывает тело внутреннего цикла.

Коллега написал: «есть два цикла, поэтому O(n²)». Как исправить обоснование?

Записать сумму n + ⌊n/2⌋ + …, ограничить её сверху 2n, снизу n. Само O(n²) формально является верхней границей, но скрывает точный порядок Θ(n).

Исправить скрытый квадрат в отчёте

Сумма сумм платежей вычислялась индексным циклом: for (int i = 0; i < amounts.size(); i++) total += amounts.get(i);. Параметр имеет тип List<Integer>, вызывающий код передаёт ArrayList или LinkedList. Перепиши метод так, чтобы для обеих реализаций он работал за O(n) времени, без копии коллекции. Элементы не null, итог помещается в long.

[10, -3, 10] → 17
[2 147 483 647, 1] → 2 147 483 648

Подсказка 1

Важна цена get(i), а не интерфейс List в сигнатуре.

Подсказка 2

Нужен обход, который помнит текущую позицию в LinkedList. enhanced for использует iterator.

Решение

Для ArrayList доступ по индексу постоянный. LinkedList идёт от ближайшего края до i; сумма этих расстояний по всем индексам квадратична. Итератор переносит текущую позицию вперёд, не начиная поиск заново.

    static long sum(List<Integer> amounts) {
        long total = 0;
        for (int amount : amounts) total += amount; // Итератор движется по списку один раз.
        return total;
    }

Время Θ(n) для двух названных реализаций, дополнительная память O(1): аккумулятор и итератор. Размер коллекции и её элементы — вход. Для произвольной пользовательской реализации List такой контракт сложности из одного интерфейса не следует.

Почему заменить get(i) на stream().mapToInt(...).sum() недостаточно?

Поток убирает индексный обход стандартного LinkedList, но int-сумма переполнится на тесте MAX_VALUE + 1. Для этих входов нужен long-аккумулятор или mapToLong. Потоковая форма сама по себе не является доказательством сложности.

Достаточно ли теста с верным результатом, чтобы доказать O(n)?

Нет: медленный вариант тоже вернёт правильную сумму. Здесь доказательство опирается на обход узлов LinkedList итератором. Рост затрат дополнительно проверяют профилем или счётчиком посещений при нескольких n.

Сравнить две политики роста буфера

Начинаем с пустого массива ёмкости 1 и добавляем n платежей, 0 ≤ n ≤ 100 000. Каждая запись нового платежа стоит 1, перенос старого тоже стоит 1. Если буфер заполнен, политика doubling удваивает ёмкость, другая увеличивает её на 1. Верни суммарную стоимость. Массив выделять не нужно. Отдельно оцени цену добавлений и сложность своего расчёта.

n = 5, doubling = true  → 12
n = 5, doubling = false → 15
n = 9, doubling = true  → 24

Подсказка 1

Без расширений уже выполнено n новых записей. Осталось добавить копирования.

Подсказка 2

Расширение происходит только из заполненного массива: число переносов равно его прежней ёмкости.

Решение

Перебираем только ёмкости, из которых потребуется расти. Условие capacity < n важно: если последний платёж ровно заполнил массив, расширение ещё не нужно.

    static long writes(int n, boolean doubling) {
        long capacity = 1;
        long total = n; // По одной записи на добавляемый платёж.
        while (capacity < n) {
            total += capacity; // Растёт только полный массив: копируем capacity записей.
            capacity = doubling ? capacity * 2 : capacity + 1;
        }
        return total;
    }

При удвоении калькулятор работает за O(log n) времени и O(1) памяти, а сама серия добавлений — за Θ(n). При росте на 1 этот калькулятор делает Θ(n) шагов, тогда как реальные добавления требуют Θ(n²) переносов и записей. Для второй политики калькулятор можно заменить формулой n(n + 1)/2 и считать за O(1).

Какова худшая стоимость девятого добавления и средняя по первым девяти?

При удвоении девятое стоит 8 переносов + 1 запись = 9. Суммарно первые девять стоят 24, то есть 24/9 единицы на добавление. Это не утверждение, что каждое стоило около 2,67.

Что сломается при условии capacity <= n?

Будет посчитано расширение после последнего добавления, которого ещё не было. Например, для n = 1 верный ответ 1; лишняя итерация добавит фиктивный перенос.

Можно ли гарантировать постоянный p99 из амортизированного O(1)?

Нет. Амортизированная оценка ограничивает суммарную работу, но ничего не говорит о процентилях задержки на заданном потоке. Расширения, выделение памяти и GC оцениваются отдельно.
