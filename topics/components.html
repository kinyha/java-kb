Components & Modules

Граница модуля помогает менять одну часть сервиса, не разбирая весь сервис. Для этого внутри собирают код, который меняется вместе, а снаружи оставляют небольшой понятный вход. Направление зависимостей решает, кому придётся подстраиваться под очередную правку. Пакеты и интерфейсы выражают это решение в Java; автоматическая проверка удерживает его после сотни новых изменений. Число модулей и количество интерфейсов сами по себе качество не показывают.

Правка банка заставила пересобрать платежи и уведомления

В платёжном сервисе три части: payments проводит платёж, bank общается с банком, notifications готовит сообщение клиенту. Новый SDK банка поменял тип ответа. Платёжный сервис напрямую использует BankClient, банк берёт удобный метод из PaymentService, а уведомления читают внутренний PaymentLedger. Компилятор доволен. Разработчик меняет один класс и обнаруживает, что соседние части уже знают его устройство.

Начать можно с логических модулей одного приложения: задача, публичный вход и скрытая реализация. У Мартина компонент — единица выпуска и развёртывания, например библиотека JAR. Пакет сам по себе такой единицей не становится: нужно задать его границу.

kb.modules
├── payments
│   ├── PaymentService.java       // Вход для проведения платежа.
│   ├── PaymentReceipt.java       // Результат для соседних модулей.
│   ├── BankGateway.java          // Требуемая платежам операция банка.
│   └── internal
│       └── PaymentLedger.java   // Деталь реализации платежей.
├── bank
│   └── BankClient.java           // Реализация BankGateway.
└── notifications
    └── NotificationSender.java // Использует готовый PaymentReceipt.

Это package by feature: сначала возможность приложения, потом её устройство. В глобальных пакетах controller, service, repository один сценарий размазан по трём каталогам. Внутри крупного payments слои полезны: payments.web, payments.application, payments.persistence. Переставить файлы недостаточно — важны разрешённые связи.

Java считает payments и payments.internal разными пакетами. Доступ с уровнем package-private через эту границу не проходит. Поэтому внутренний класс иногда приходится сделать public, чтобы его видел свой соседний пакет. Теперь его видит и notifications. Имя internal остаётся намерением автора; компилятор его не понимает.

Демо ModuleDemo.java читает настоящие .class трёх пакетов через ArchUnit 1.5.1. run.sh собирает три варианта. Нужны JDK 21 и Maven; запуск из корня репозитория: bash examples/design/modules/run.sh. Остальные примеры в examples/design запускаются без сборки.

Вместе держат то, что выпускают, меняют и используют вместе

Три принципа связности из части IV «Чистой архитектуры» помогают выбрать состав компонента. Они смотрят на выпуск, причины изменения и потребителей одного набора классов.

ПринципВопрос к границеПример платежей
REP — Reuse/Release EquivalenceЧто потребитель получает как один поддерживаемый выпуск?Клиент банка с адаптером ошибок выпускается одной версией; пользователю не нужно собирать совместимые классы вручную.
CCP — Common ClosureКакие классы меняет одна и та же причина?Правка протокола банка меняет его запросы, разбор ответа и перевод ошибок внутри bank.
CRP — Common ReuseКакие классы нужны одним и тем же потребителям?Коду, которому нужен Money, не следует тянуть SDK банка, JDBC и шаблоны писем.

REP связывает повторное использование с выпуском. Пользователь библиотеки получает совместимый набор, видит изменения и выбирает момент обновления. Копирование классов из чужой ветки этой возможности не даёт. В монолите отдельная версия каждому пакету обычно не нужна; для библиотеки с несколькими потребителями управляемый выпуск уже важен.

CCP переносит единую причину изменения с класса на компонент. Новая банковская подпись должна менять один адаптер и его тесты. Если она требует совместного выпуска payments-api, bank-models и notification-utils, границы разрезали одну причину. «Закрытость» означает, что одни и те же изменения затрагивают код вместе.

CRP защищает от лишней зависимости. Отчётности нужен тип денежной суммы. Если его библиотека содержит банковский HTTP-клиент, обновление клиента затрагивает и отчёты. Между этими группами классов может почти не быть вызовов, но потребители у них разные.

Принципы тянут в разные стороны. CCP собирает изменяющиеся вместе классы, CRP разделяет код для разных потребителей. Большой common заставляет всех обновляться из-за чужих правок; слишком мелкие библиотеки превращают одну правку в десять выпусков. Молодому сервису полезно сначала держать сценарий целиком. Самостоятельную границу оправдывают собственные потребители и причина меняться отдельно.

Связность объясняет история изменений. Общий суффикс Service или аннотация Spring для этого слишком слабы.

Порт платежей разрывает цикл, хотя вызов по-прежнему идёт в банк

ADP — Acyclic Dependencies Principle требует граф без циклов. Стрелка payments → bank означает: исходный код платежей знает тип из банка. При обратной стрелке каждая сторона тащит вторую, а порядок «сначала проверить банк, потом платежи» теряет смысл. Java такой код компилирует; отдельным модулям цикл мешает задавать порядок сборки.

Вот существенные строки из файлов каталога broken. Обратную связь породил всего один удобный статический метод:

// payments/PaymentService.java
private final BankClient bank;                 // payments знает реализацию bank.
public static String bankReference(String id) { return "bank:" + id; }

// bank/BankClient.java
public String charge(String id) {
    return PaymentService.bankReference(id);   // bank уже знает payments: цикл замкнулся.
}

Исправление через DIP начинается с владельца интерфейса. Платежам нужна операция списания, поэтому BankGateway принадлежит платежам. Они выражают свою потребность, банк её реализует. Формат банковской ссылки остаётся деталью банка. Существенные части варианта fixed:

// payments/BankGateway.java
public interface BankGateway {
    String charge(String paymentId);           // Операция на языке потребителя.
}

// payments/PaymentService.java
private final BankGateway bank;                // Зависимость теперь внутри payments.
public PaymentService(BankGateway bank) { this.bank = bank; }
public PaymentReceipt pay(String id) {
    return new PaymentReceipt(id, ledger.caption(id), bank.charge(id));
}

// bank/BankClient.java
public final class BankClient implements BankGateway { // bank зависит от payments.
    @Override public String charge(String id) { return "bank:" + id; }
}

Внешняя точка сборки соединяет стороны: new PaymentService(new BankClient()). В Spring это конфигурация бинов. Передача объекта через конструктор сама по себе цикл не разрывает. Если оставить BankGateway внутри bank, платежи продолжат зависеть от банка. Важен владелец интерфейса.

Другое исправление ADP — вынести самостоятельное общее понятие в третий компонент. Его существование тоже нужно обосновать: common со всеми неудобными типами быстро начинает управлять приложением. Одинаково меняющиеся части иногда лучше объединить.

@Lazy может изменить момент создания Spring-бина. Он не меняет импорт Java и не убирает цикл компонентов. Аналогично, асинхронное событие разрывает прямой вызов, но сохраняет зависимость от формата события и добавляет правила доставки. Выбор механизма должен соответствовать задаче.

Зависимости направляют к устойчивому API, а метрики объясняют цену правки

Если десятки модулей используют платёжное ядро, а ядро импортирует тип ответа меняющегося SDK, правка SDK расходится далеко. SDP — Stable Dependencies Principle направляет зависимости к более устойчивым компонентам. Устойчивость означает сопротивление изменению из-за зависимых потребителей. Это не работоспособность сервиса и не частота правок.

До подсчёта выбирают единицу и область: компоненты или классы, рабочий код или тесты, включать ли сторонние библиотеки. Между запусками правила должны совпадать.

МетрикаСмыслРасчёт
Ca, входящая связностьКто зависит от компонента. Большое значение увеличивает число затронутых потребителей.В демо — число других компонентов с входящей зависимостью.
Ce, исходящая связностьОт кого зависит компонент. Эти внешние изменения могут прийти внутрь.В демо — число других компонентов, на которые он ссылается.
I, неустойчивость0 — только входящие связи; 1 — только исходящие.I = Ce / (Ca + Ce)
A, абстрактностьДоля интерфейсов и абстрактных классов.A = Na / Nc
D, расстояние до главной последовательностиОтклонение от линии A + I = 1.D = |A + I − 1|, диапазон 0…1.

В формулировке главы 14 «Чистой архитектуры» Fan-in считает классы снаружи, зависящие от компонента, а Fan-out — классы внутри, зависящие от внешних классов. ArchUnit считает связи между выделенными компонентами; десять импортов в один соседний компонент дают одну связь Ce. Ещё одно отличие: его A учитывает только публичные типы. Это нужно помнить перед сравнением отчёта инструмента с примером из книги. Если Ca и Ce оба равны нулю, формула I содержит деление на ноль: значение для изолированного компонента определяется соглашением инструмента, а не особым архитектурным законом.

В исправленном демо мы измеряем только три собственных модуля. Внешние типы JDK не входят в этот граф. bank → payments и notifications → payments, поэтому у payments Ca=2 и Ce=0. У него четыре публичных типа: PaymentService, PaymentReceipt, BankGateway и PaymentLedger. Только один из четырёх — интерфейс.

var components = MetricsComponents.fromPackages(
    fixed.getPackage("kb.modules").getSubpackages()); // С вложенными пакетами каждой функции.
var metrics = ArchitectureMetrics.componentDependencyMetrics(components);

// ModuleDemo печатает Ca, Ce, I, A и D для каждого компонента.
metrics.getInstability("kb.modules.payments");
metrics.getAbstractness("kb.modules.payments");
metrics.getNormalizedDistanceFromMainSequence("kb.modules.payments");
payments Ca=2 Ce=0 I=0.00 A=0.25 D=0.75
bank Ca=0 Ce=1 I=1.00 A=0.00 D=0.00
notifications Ca=0 Ce=1 I=1.00 A=0.00 D=0.00

SDP соблюдён: модули с I=1 зависят от payments с I=0. Но D у payments велик. SAP — Stable Abstractions Principle предлагает устойчивой части абстракции: потребители затрудняют правку, поэтому изменяемое поведение расширяют через точки подключения. DIP и SAP работают вместе: интерфейс в устойчивой части, сменяемая реализация — снаружи.

Зона боли рядом с (I=0, A=0): на конкретный код завязано много потребителей, а менять его трудно. Зона бесполезности рядом с (I=1, A=1): абстракции существуют, но в выбранном графе от них никто не зависит. Главная последовательность показывает баланс, а не обязанность каждого пакета попасть на линию.

В payments лежат порт, реализация и результат. Делать интерфейс для PaymentReceipt ради уменьшения D бессмысленно: конкретный тип значения полезен. В расчёт A попал и public-класс PaymentLedger, скрытый нашим правилом. Метрика видит модификатор Java, а не границу API. Выделение маленького payments-api с портами и типами оправдывают потребители, а не один отчёт.

Под капотом: почему идеальная метрика не гарантирует удобный API

Два компонента имеют одинаковые I и A. API первого принимает charge(paymentId), API второго выставляет двадцать флагов чужого SDK. Числа не видят смысл методов и стоимость согласования команд. Общая схема БД, строковый поиск бина и сетевой протокол также связывают модули вне графа Java-типов.

Проверка границ ловит и цикл, и доступ к внутреннему классу

Новый разработчик увидит публичный класс и воспользуется им. ArchUnit читает байткод и строит связи между типами. Демо импортирует отдельный каталог классов для каждого варианта и проверяет зависимости настоящего кода.

JavaClasses classes = new ClassFileImporter().importPath(target.resolve(variant));

ArchRule noCycles = slices().matching("kb.modules.(*)..") // Первый пакет под modules — модуль.
    .should().beFreeOfCycles();

ArchRule noInternalAccess = noClasses()
    .that().resideOutsideOfPackage("kb.modules.payments..")
    .should().dependOnClassesThat()
    .resideInAPackage("kb.modules.payments.internal..");  // public не снимает этот запрет.

EvaluationResult cycleResult = noCycles.evaluate(classes);
EvaluationResult boundaryResult = noInternalAccess.evaluate(classes);
// Демо печатает hasViolation(). В CI обычно вызывают rule.check(classes):
// любое нарушение тогда бросает AssertionError и роняет тест.

В сломанном варианте уведомления знают внутренний журнал:

// broken/notifications/NotificationSender.java
private final PaymentLedger ledger = new PaymentLedger(); // Чужая внутренняя реализация.
public String message(String id) { return ledger.caption(id); }

// fixed/notifications/NotificationSender.java
public String message(PaymentReceipt receipt) {
    return receipt.caption();                             // Публичный результат платежей.
}

Вариант port берёт исправленные платежи и банк, но старый NotificationSender. Предскажи обе проверки: направление связи банка поменялось, а уведомления всё ещё обходят API. Начало вывода:

У port и fixed одинаковые стрелки модулей. Уведомления перешли с payments.internal.PaymentLedger на payments.PaymentReceipt. Поэтому циклы и доступ к внутренностям проверяют отдельно. Ещё можно ограничить направления: например, только банковскому адаптеру разрешить типы SDK.

Spring Modulith задаёт похожую модель поверх Spring-приложения. При стандартном обнаружении прямые подпакеты пакета приложения становятся модулями. Публичные типы корневого пакета модуля составляют его API, вложенные пакеты считаются внутренними. Метод verify() проверяет циклы, обращения к внутренностям и явно заданные разрешённые зависимости.

// В Spring-приложении класс Application находится в kb.modules.
ApplicationModules.of(Application.class).verify(); // Выполнить в архитектурном тесте.

// kb/modules/notifications/package-info.java
@org.springframework.modulith.ApplicationModule(allowedDependencies = "payments")
package kb.modules.notifications;                // Зависимость от bank теперь запрещена.

Если нужный внешним модулям порт лежит в payments.spi, такой пакет можно явно открыть через @NamedInterface("bank") в его package-info.java. Потребитель указывает allowedDependencies = "payments :: bank" и получает только этот именованный API. Это явный выбор границы; перенос всех внутренностей в открытые пакеты уничтожит её смысл. Фрагмент Modulith показывает настройку для Spring-проекта. Исполняемое демо этой страницы использует ArchUnit.

Проверка с одними классами платежей не увидит нарушение из отсутствующего notifications. Импортируй весь код выбранных модулей и проверяй шаблон пакетов. Демо явно отвергает пустой каталог. Исключения из правил должны быть узкими и иметь владельца.

Модуль оправдан, когда его граница упрощает реальные изменения

Исправление банковского протокола остаётся в bank; новый текст письма — в notifications; правила платежа — в payments. У границы есть владелец, небольшой вход и правила совместимости. Публичный результат помогает соседу обойтись без чтения внутренних полей и таблиц.

ГраницаЧто удерживаетЧто остаётся решить
Пакеты по возможностям + ArchUnitНаправление связей и доступ к выбранным внутренним пакетам в одном приложении.Правила нужно запускать; общий classpath сохраняет технический доступ к public-типам.
Maven/Gradle-модулиЯвные зависимости сборки и состав classpath.После подключения JAR его public-типы обычно доступны целиком.

Отдельный сервисОтдельный процесс, выпуск и сетевой протокол.Добавляются задержки, отказы, совместимость сообщений и распределённые операции.

Логический модуль не обязан становиться микросервисом. Одна транзакция может вызывать два модуля монолита, если сценарий этого требует. Агрегат задаёт границу согласованного изменения предметной модели; модуль собирает связанную возможность приложения и может содержать несколько агрегатов. Bounded context задаёт границу языка и модели. Эти границы стоит согласовать, но они отвечают на разные вопросы — подробнее в DDD и Application Architecture.

Уведомления могут выполнить SQL к таблице платежей без импорта их типов. Граф станет чище, зависимость от чужой схемы останется. Поэтому нужны правила доступа к данным, проверки контрактов и интеграционные тесты. При обмене событиями добавляются совместимость формата, обработка повторов и срок, за который сосед увидит изменение.

Небольшому CRUD-сервису достаточно пакетов, явного API и пары правил. Отдельные артефакты для каждого класса преждевременно усложняют сборку. Постоянные совместные правки требуют пересмотреть разделение; обращения к внутренностям — улучшить API. Метрики находят такие места, история изменений помогает выбрать решение.

На собеседовании

Как REP, CCP и CRP помогают выбрать состав компонента?

Я смотрю на три вещи. REP требует понятного выпуска для повторно используемого кода: потребитель получает совместимый набор одной версии. CCP собирает то, что меняется по одной причине. CRP разделяет то, что нужно разным потребителям, чтобы им не приходилось тянуть лишние зависимости. В платежах запросы банка и перевод его ошибок меняются вместе; Money для отчётов не должен приносить весь SDK банка.

  • Компромисс меняется со временем: ранний проект выигрывает от быстрых локальных правок, библиотека с десятками потребителей — от узкого API и контролируемых выпусков.
  • Повторное использование и совместное изменение — разные свидетельства. Общий код, который две команды постоянно хотят менять по-разному, может быть выгоднее разделить, чем навязывать им один выпуск.
  • Проверяю изменения из истории Git и зависимости потребителей. Число классов или общий технический суффикс не объясняют границу.

Как разорвать цикл модулей через DIP?

Сначала выясняю, что означает каждая стрелка. Если платежи знают BankClient, а BankClient знает PaymentService, есть цикл типов. Выделяю нужную платежам операцию в BankGateway внутри платежей. PaymentService работает через свой порт, а BankClient реализует его. При выполнении платежи вызывают банк как раньше, но зависимость исходного кода теперь идёт из банка в платежи. Соединяет объекты внешняя конфигурация.

  • Если два модуля всё время правятся совместно, цикл может указывать на искусственное разделение. Слияние иногда лучше нового порта.
  • Третий компонент подходит для самостоятельного общего понятия. Перенос интерфейса в технический common без владельца оставляет согласование обеим сторонам.
  • Цикл создания бинов, цикл вызовов во время выполнения и цикл зависимостей компонентов — разные графы. Настройка контейнера исправляет только тот граф, на который она действует.

Что показывают SDP, SAP и метрики I, A, D?

SDP направляет зависимости к более устойчивой части. Устойчивость здесь связана с числом потребителей: менять общий API трудно. I=Ce/(Ca+Ce) показывает долю исходящих связей, A — долю абстрактных типов. SAP предлагает устойчивой части точки расширения через абстракции. D=|A+I−1| показывает отклонение от баланса: устойчивый конкретный код может попасть в зону боли. Метрики помогают искать опасные связи; высокий D сам по себе не требует переписывать модуль.

  • Область измерения меняет числа: добавление внешних библиотек или тестов может изменить I без единой правки рабочего кода. Сравниваю отчёты с одинаковыми правилами подсчёта.
  • ArchUnit считает межкомпонентные связи и только публичные типы для A. Результат нужно читать с учётом этих соглашений.
  • Стабильные конкретные значения, DTO и схемы данных бывают полезны при A=0. Интерфейс не отменяет несовместимое изменение метода или смысла данных.

Как проверить границы модулей в Java и Spring?

Я собираю код по возможностям, выбираю публичные типы и закрываю внутренние пакеты архитектурным тестом. ArchUnit проверяет зависимости по байткоду: отдельно циклы, отдельно доступ к внутренностям и разрешённые направления. Spring Modulith умеет вывести модули из структуры пакетов и проверить ту же дисциплину через ApplicationModules.of(Application.class).verify(). Maven-модули ограничивают зависимости сборки, а JPMS может дополнительно закрыть неэкспортируемые пакеты.

  • Сначала проверяю, что тест импортирует все нужные классы. Недостающий потребитель делает его нарушения невидимыми.
  • В Modulith именованный интерфейс открывает выбранный пакет; список allowedDependencies ограничивает, какие API может использовать модуль. Устранение цикла не заменяет ни одно из этих правил.
  • Строковые ссылки, общие таблицы и сетевые сообщения требуют других проверок. Чистый граф типов ещё не гарантирует самостоятельность команды и выпуска.
Циклов нет, тест зелёный. Можно ли считать границу payments защищённой? 
// В notifications появился импорт:
import kb.modules.payments.internal.PaymentLedger;

Именно поэтому промежуточный вариант демо проходит cycles и проваливает internal access. Если тест вообще не импортировал notifications, сначала исправляют область проверки.
