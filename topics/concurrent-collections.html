Concurrency: Concurrent Collections

HashMap в восьми потоках: потери, исключение или вечный цикл

Кеш платежей на обычном HashMap, и восемь потоков кладут в него записи. Ключи у потоков не пересекаются, так что, казалось бы, мешать друг другу им нечем:

import java.util.*;
import java.util.concurrent.*;

public class BrokenMap {
    public static void main(String[] args) throws Exception {
        Map<Integer, Integer> map = new HashMap<>();                 // не потокобезопасна
        ExecutorService pool = Executors.newFixedThreadPool(8);
        List<Future<?>> fs = new ArrayList<>();
        for (int t = 0; t < 8; t++) {
            int base = t * 100_000;
            fs.add(pool.submit(() -> { for (int i = 0; i < 100_000; i++) map.put(base + i, i); }));  // ключи не пересекаются
        }
        try {
            for (Future<?> f : fs) f.get(10, TimeUnit.SECONDS);
            System.out.println("ожидали 800000, size = " + map.size());
        } catch (ExecutionException e) {
            System.out.println("исключение внутри HashMap: " + e.getCause());
        } catch (TimeoutException e) {
            System.out.println("за 10 с не закончили — потоки зациклились внутри HashMap");
        }
        System.exit(0);
    }
}

Одновременные вставки и перестройка таблицы испортили внутренние ссылки, и в структуре появился цикл. В проде это выглядит как «CPU 100%, запросы висят», и лечится только перезапуском. Причина — в том, что HashMap не рассчитана на несколько потоков вообще, даже на «безобидные» записи в разные ключи.

В этой теме — три способа сделать коллекцию потокобезопасной. Обёртки Collections.synchronized*, как устроен ConcurrentHashMap и почему он быстрее в 20 раз, копирование при записи в CopyOnWriteArrayList и блокирующие очереди, которые связывают производителей и потребителей.

Collections.synchronized* защищает методы, но не обход и не составные действия

Collections.synchronizedMap(map), synchronizedList и остальные оборачивают коллекцию: каждый метод выполняется под одним общим замком. Это исправляет BrokenMap, но оставляет две проблемы.

Первая — обход. Итератор обращается к коллекции много раз, и между шагами другой поток может её изменить:

import java.util.*;
import java.util.concurrent.*;

public class IterateSync {
    public static void main(String[] args) throws Exception {
        List<String> payments = Collections.synchronizedList(new ArrayList<>());
        for (int i = 0; i < 1000; i++) payments.add("p" + i);
        Thread adder = new Thread(() -> {
            for (int i = 0; i < 1_000_000; i++) payments.add("new" + i);   // каждый add под замком списка
        });
        adder.start();
        try {
            long sum = 0;
            for (String p : payments) sum += p.length();                   // итерация — нет
            System.out.println("обход прошёл");
        } catch (ConcurrentModificationException e) {
            System.out.println("synchronizedList: " + e);
        }
        adder.join();

        List<String> listeners = new CopyOnWriteArrayList<>();
        for (int i = 0; i < 1000; i++) listeners.add("l" + i);
        Iterator<String> it = listeners.iterator();                        // обход начался
        Thread adder2 = new Thread(() -> { for (int i = 0; i < 1000; i++) listeners.add("new" + i); });
        adder2.start();
        adder2.join();                                                     // пока обход идёт, добавили ещё 1000
        int seen = 0;
        while (it.hasNext()) { it.next(); seen++; }
        System.out.println("CopyOnWriteArrayList: обход увидел " + seen + ", в списке уже " + listeners.size());
    }
}
synchronizedList: java.util.ConcurrentModificationException
CopyOnWriteArrayList: обход увидел 1000, в списке уже 2000

Итератор обёртки — это итератор исходного ArrayList, и он fail-fast: заметил изменение и бросил ConcurrentModificationException. Javadoc требует обходить такую коллекцию внутри synchronized (payments) { ... }. Тогда на всё время обхода остальные потоки встают. Вторая часть вывода — к шагу 5.

Вторая проблема — составные действия вроде «если нет — положить». Каждый метод атомарен, а их сочетание — нет, как в теме Thread Safety. И третья, практическая, — один замок на всё. Замер: восемь потоков, случайные ключи, 90% чтений и 10% записей, одна секунда:

import java.util.*;
import java.util.concurrent.*;
import java.util.concurrent.atomic.LongAdder;

public class Throughput {
    static volatile boolean stop;

    static long ops(Map<Integer, Integer> map, int threads) throws Exception {
        for (int i = 0; i < 100_000; i++) map.put(i, i);
        LongAdder done = new LongAdder();
        stop = false;
        Thread[] ts = new Thread[threads];
        for (int t = 0; t < threads; t++) {
            ts[t] = new Thread(() -> {
                ThreadLocalRandom rnd = ThreadLocalRandom.current();
                long n = 0;
                while (!stop) {
                    int key = rnd.nextInt(100_000);
                    if (rnd.nextInt(10) == 0) map.put(key, key);         // 10% записей
                    else map.get(key);                                   // 90% чтений
                    n++;
                }
                done.add(n);
            });
            ts[t].start();
        }
        Thread.sleep(1000);
        stop = true;
        for (Thread t : ts) t.join();
        return done.sum();
    }

    public static void main(String[] args) throws Exception {
        for (int round = 0; round < 2; round++) {                        // первый круг — прогрев
            for (int threads : new int[]{1, 8}) {
                long s = ops(Collections.synchronizedMap(new HashMap<>()), threads);
                long c = ops(new ConcurrentHashMap<>(), threads);
                if (round == 1) System.out.printf("%d потоков: synchronizedMap %,12d операций/с, ConcurrentHashMap %,12d%n", threads, s, c);
            }
        }
    }
}
1 потоков: synchronizedMap  111,433,388 операций/с, ConcurrentHashMap  135,795,155
8 потоков: synchronizedMap   20,529,268 операций/с, ConcurrentHashMap  429,439,826

Восемь потоков с synchronizedMap сделали в пять раз меньше операций, чем один. Они стоят в очереди за одним замком и перекидывают друг другу строку кеша с ним. ConcurrentHashMap на тех же восьми потоках в 21 раз быстрее. Второй запуск дал те же числа с точностью до 5%.

ConcurrentHashMap блокирует одну корзину, а читает без блокировок

С Java 8 ConcurrentHashMap — массив корзин, как у HashMap, но каждая операция трогает только свою корзину:

Ещё детали, которые спрашивают на собеседовании:

  • Цепочка длиннее 8 узлов (TREEIFY_THRESHOLD) при таблице от 64 корзин превращается в красно-чёрное дерево, как в HashMap. Если таблица меньше, она вместо этого расширяется.
  • size() считают как в LongAdder: базовый счётчик и массив CounterCell. При параллельных изменениях результат приблизителен. Для больших карт есть mappingCount(), возвращающий long.
  • Итераторы слабо согласованные: не бросают ConcurrentModificationException и видят какое-то состояние карты между началом и концом обхода.
  • null нельзя ни в ключ, ни в значение. Если get вернул null, это однозначно значит «ключа нет». В HashMap для этого нужен второй вызов containsKey, а между двумя вызовами в многопоточной карте всё может измениться.
  • В Java 7 карта делилась на 16 сегментов, каждый со своим ReentrantLock (lock striping). В Java 8 сегменты заменили блокировкой отдельной корзины и CAS.

compute-методы атомарны, потому что держат замок корзины — их функция должна быть короткой

Составные действия у ConcurrentHashMap есть готовые: putIfAbsent, computeIfAbsent, compute, merge. Для отсутствующего ключа computeIfAbsent вызывает функцию ровно один раз — в отличие от AtomicLong.updateAndGet, которая может повторяться. Цена этой гарантии: функция выполняется, пока держится замок корзины. Отсюда два правила. Функция должна быть быстрой, иначе ждут все, кто пришёл в эту корзину. И она не должна менять ту же карту:

import java.util.*;
import java.util.concurrent.*;

public class Recursive {
    static final Map<Integer, Long> cache = new ConcurrentHashMap<>();

    // числа Фибоначчи с кешем «по-умному»: вычисление само пишет в тот же кеш
    static long fib(int n) {
        if (n < 2) return n;
        return cache.computeIfAbsent(n, k -> fib(k - 1) + fib(k - 2));
    }

    public static void main(String[] args) {
        try {
            System.out.println("fib(40) = " + fib(40));
        } catch (IllegalStateException e) {
            System.out.println("computeIfAbsent: " + e);
        }
    }
}
computeIfAbsent: java.lang.IllegalStateException: Recursive update

Функция для ключа 40 вызвала computeIfAbsent для 39 и 38 внутри той же карты. JDK с Java 9 распознаёт такое рекурсивное изменение и бросает исключение. В Java 8 тот же код мог зависнуть навсегда. Кеш для рекурсивных вычислений заполняют снаружи: сначала посчитать, потом putIfAbsent.

Частая ошибка — долгий вызов внутри computeIfAbsent: запрос в базу или HTTP-клиент для «ленивой загрузки в кеш». Пока идёт вызов, корзина заблокирована, и все ключи, попавшие в неё, ждут. Для загрузок с задержкой используют кеш, который умеет асинхронную загрузку, например Caffeine.buildAsync. Или кладут в карту CompletableFuture, а саму загрузку выполняют вне замка.

CopyOnWriteArrayList копирует массив на каждую запись, зато обход не блокируется

У CopyOnWriteArrayList внутри неизменяемый массив. Каждая запись копирует массив целиком, меняет копию и публикует её одной volatile-записью. Итератор берёт ссылку на массив в момент создания и обходит этот снимок — поэтому в шаге 2 он увидел 1000 элементов, хотя в списке их уже было 2000. Блокировок при чтении и обходе нет, ConcurrentModificationException не бывает.

Цена — запись. Каждый add копирует весь массив, поэтому заполнение списка из N элементов стоит O(N²):

import java.util.*;
import java.util.concurrent.*;

public class CowCost {
    public static void main(String[] args) {
        for (int round = 0; round < 2; round++) {                        // первый круг — прогрев
            List<Integer> sync = Collections.synchronizedList(new ArrayList<>());
            List<Integer> cow = new CopyOnWriteArrayList<>();
            long start = System.nanoTime();
            for (int i = 0; i < 50_000; i++) sync.add(i);
            long syncMs = (System.nanoTime() - start) / 1_000_000;
            start = System.nanoTime();
            for (int i = 0; i < 50_000; i++) cow.add(i);                   // каждый add копирует весь массив
            long cowMs = (System.nanoTime() - start) / 1_000_000;
            if (round == 1) System.out.printf("50 000 add: synchronizedList %d мс, CopyOnWriteArrayList %d мс%n", syncMs, cowMs);
        }
    }
}
50 000 add: synchronizedList 0 мс, CopyOnWriteArrayList 142 мс

Меньше миллисекунды против 142 мс, и разница растёт квадратично. Поэтому CopyOnWriteArrayList — для коллекций, которые читают постоянно, а меняют редко: слушатели событий, обработчики, конфигурация маршрутов. Классический случай — список слушателей. Его обходят при каждом событии, а подписываются редко, и слушатель может отписаться прямо во время обхода. Для множества есть CopyOnWriteArraySet.

Самое важное свойство ограниченной очереди — противодавление (backpressure). Если потребитель медленнее производителя, полная очередь заставляет производителя ждать. Неограниченная растёт, пока не кончится память. Производитель принимает платежи из сети, потребитель медленно пишет их в базу:

import java.util.concurrent.*;

public class Backpressure {
    public static void main(String[] args) throws Exception {
        BlockingQueue<byte[]> queue = args[0].equals("bounded")
            ? new ArrayBlockingQueue<>(1_000)                            // не больше 1000 элементов
            : new LinkedBlockingQueue<>();                               // ёмкость Integer.MAX_VALUE
        Thread producer = new Thread(() -> {                             // принимает платежи из сети: быстро
            try { while (true) queue.put(new byte[1024]); } catch (InterruptedException e) { }
        });
        Thread consumer = new Thread(() -> {                             // пишет в базу: медленно
            try { while (true) { queue.take(); Thread.sleep(0, 100_000); } } catch (InterruptedException e) { }
        });
        producer.setDaemon(true); consumer.setDaemon(true);
        producer.start(); consumer.start();
        Runtime rt = Runtime.getRuntime();
        for (int step = 1; step <= 5; step++) {
            Thread.sleep(200);
            System.out.printf("%4d мс: в очереди %,9d, heap занят %,5d МБ%n",
                step * 200, queue.size(), (rt.totalMemory() - rt.freeMemory()) >> 20);
        }
    }
}

Неограниченная очередь съела гигабайт heap меньше чем за полсекунды, и процесс упал: памяти не хватило даже на то, чтобы напечатать стек. Так было в каждом из четырёх запусков, в одном — ещё до первой строки. Ограниченная держит 1000 элементов и 6–13 МБ: производитель просто ждёт в put(), пока потребитель освободит место. В реальном сервисе это ожидание дойдёт до входа — сервис перестанет принимать новые запросы быстрее, чем может их обработать, вместо того чтобы упасть.

Отсюда главное правило для очередей между потоками: ограничивать ёмкость и решать, что делать при переполнении, — ждать, отказать через offer или сбросить старое. Та же ловушка скрыта в Executors.newFixedThreadPool: его очередь задач — неограниченная LinkedBlockingQueue (тема Executors).

  • HashMap под несколькими потоками теряет записи, бросает исключения изнутри и может зациклиться со 100% CPU.
  • Collections.synchronized* ставят каждый метод под один замок. Обход требует внешнего synchronized, составные действия не атомарны, а масштабирования нет: в замере 8 потоков сделали в 5 раз меньше, чем один.
  • ConcurrentHashMap: CAS в пустую корзину, synchronized на первом узле занятой, чтение без блокировок, совместное расширение. В замере в 21 раз быстрее обёртки. null запрещён, итераторы слабо согласованные, size() приблизителен.
  • computeIfAbsent вызывает функцию один раз, но под замком корзины: функция короткая и не трогает ту же карту — иначе Recursive update.
  • CopyOnWriteArrayList копирует массив на каждую запись и обходит снимок. Подходит, когда читают часто, а меняют редко.
  • BlockingQueue связывает производителей и потребителей. Ограниченная ёмкость даёт противодавление, неограниченная растёт до OutOfMemoryError.

На собеседовании

Как устроен ConcurrentHashMap?

С Java 8 — массив корзин, как у HashMap. Вставка в пустую корзину идёт одной CAS без блокировки. Если корзина занята, поток захватывает synchronized на её первом узле, и блокируется только эта корзина. Чтение не блокируется вообще: ссылки на узлы читаются как volatile. Длинные цепочки превращаются в дерево. При расширении таблицы перенесённые корзины помечаются ForwardingNode, и пишущие потоки помогают переносу. Ключи и значения не могут быть null.

  • В Java 7 было 16 сегментов со своими ReentrantLock — lock striping.
  • Размер считается по схеме LongAdder (CounterCell), поэтому size() при параллельных изменениях приблизителен.
  • Итераторы слабо согласованные: без ConcurrentModificationException, но и без снимка.
  • compute-методы держат замок корзины на время функции; рекурсивное изменение той же карты даёт IllegalStateException: Recursive update.
Почему ConcurrentHashMap не допускает null, а HashMap допускает?

Чтобы get был однозначным. В HashMap null из get может значить и «ключа нет», и «значение null», а различают их вторым вызовом containsKey. В многопоточной карте между двумя вызовами состояние может измениться, и ответ станет ложным. Запрет null делает одиночный get достаточным.

Чем Collections.synchronizedMap отличается от ConcurrentHashMap?

synchronizedMap — обёртка, где каждый метод выполняется под одним общим замком. Все операции, включая чтение, идут по очереди. Обход нужно делать под внешним synchronized, иначе ConcurrentModificationException. ConcurrentHashMap блокирует только одну корзину при записи, читает без блокировок, итераторы не бросают исключений, и у него есть атомарные составные операции: putIfAbsent, compute, merge. В замере урока на 8 потоках он был в 21 раз быстрее.

static Map<String, Rate> cache = new HashMap<>(); — кеш курсов, который обновляет планировщик и читают потоки запросов. «Записи редкие, ничего страшного». Что скажешь?

Даже редкие записи параллельно с чтениями и между собой ломают HashMap: потери, исключения изнутри, зацикливание со 100% CPU — всё это случилось в замере урока. Ещё без синхронизации читатели могут не увидеть обновления. Нужен ConcurrentHashMap, а если кеш обновляется целиком — неизменяемый Map.copyOf в volatile-поле.

Когда использовать CopyOnWriteArrayList?

Когда читают и обходят часто, а меняют редко: слушатели событий, обработчики, конфигурация. Каждая запись копирует весь массив, зато чтение и обход идут без блокировок по снимку и никогда не бросают ConcurrentModificationException. На частых записях он неприменим: в замере урока 50 000 add заняли 142 мс против долей миллисекунды у synchronizedList, и разница растёт квадратично.

Какие бывают BlockingQueue и чем они отличаются?

ArrayBlockingQueue — ограниченная, на массиве, с одним замком. LinkedBlockingQueue — на связном списке, с отдельными замками на голову и хвост, по умолчанию фактически неограниченная. SynchronousQueue — без ёмкости, передача из рук в руки. PriorityBlockingQueue — по приоритету, DelayQueue — с задержкой. Методы: put/take ждут, offer/poll возвращают особое значение или ждут с таймаутом, add/remove бросают исключение.

  • Ограниченная очередь даёт противодавление: быстрый производитель ждёт медленного потребителя. Неограниченная в замере урока съела гигабайт heap за полсекунды.
  • newFixedThreadPool использует неограниченную LinkedBlockingQueue, newCachedThreadPool — SynchronousQueue.
  • ConcurrentHashMap (JDK 21) — основа урока: гарантии операций, слабо согласованные итераторы, compute-методы.
  • Collections.synchronizedList (JDK 21) — требование обходить под внешним synchronized.
  • BlockingQueue (JDK 21) — таблица методов и семантика.
  • CopyOnWriteArrayList (JDK 21) — снимок при обходе и цена записи.
