Consensus & Time

Консенсус — способ нескольким узлам согласиться об одном значении или порядке операций, даже если часть узлов упала. Raft в etcd делает это через лидера и большинство: лидер принимает записи, запись подтверждена, когда её сохранило большинство, а при пропаже лидера оставшиеся выбирают нового с увеличенным номером срока. Аварийное падение лидера в демо стоило кластеру 1,1–3,2 с недоступности записи, штатная остановка — 55 мс: лидер успел передать полномочия. Блокировка с арендой поверх консенсуса не защищает от клиента, который заснул и проснулся после истечения аренды: в демо такой клиент записал данные поверх нового владельца. Защита — fencing token: хранилище отвергает записи со старым токеном. По времени разных узлов события не упорядочивают — часы расходятся и прыгают.

Два планировщика решили, что каждый из них главный

Выплаты магазинам запускает планировщик, который работает в трёх экземплярах; выполнять должен один — лидер. Лидерство держалось на записи в Redis с TTL 10 секунд. Один экземпляр ушёл в долгую сборку мусора на 15 секунд, его запись истекла, лидером стал второй. Первый проснулся, не проверил, что он больше не лидер, и тоже запустил выплаты. Магазины получили деньги дважды. Это split brain — два узла одновременно считают себя главными.

Тема разбирает Raft на кластере etcd 3.6, блокировки с арендой и fencing token, а также порядок событий без общих часов. Поведение кворума при сетевом разделении — в CAP & Consistency, блокировки на Redis — в Redis in Production. Демо consensus.sh поднимает три узла etcd в Docker и клиентов на alpine.

Raft: лидер, большинство и номер срока

== leader election (Raft, election timeout 1000 ms by default)
   kill  etcd-3 (term 2): writes accepted again after 3238 ms, new leader etcd-2 (term 4)
   stop  etcd-2 (term 4): writes accepted again after   54 ms, new leader etcd-1 (term 5)

Демо роняет лидера двумя способами. docker kill — аварийное падение: кластер не принимал записи 3,2 с. В двух других запусках было 1,1 с при сроке, выросшем на единицу: тайм-аут выборов плюс сами выборы. В этом запуске первые выборы не дали лидера — срок вырос сразу на два, — и простой оказался втрое длиннее. docker stop посылает SIGTERM, и etcd при штатной остановке передаёт лидерство другому узлу до выхода: 54 мс. Отсюда практический вывод — штатные остановки при деплое почти бесплатны, а цена аварийного падения определяется тайм-аутом выборов. Уменьшить его можно, но тогда кратковременные задержки сети чаще будут вызывать лишние выборы.

Номер срока — главный инструмент против двух лидеров. Узел, узнавший о большем сроке, сразу перестаёт считать себя лидером, а сообщения со старым сроком отвергаются. Старый лидер, оказавшийся в меньшинстве, не может подтвердить ни одной записи: для этого ему нужно большинство, а оно уже признало нового лидера. Поэтому в Raft двух лидеров, подтверждающих записи, не бывает. Нечётное число узлов — 3 или 5 — выбирают потому, что 4 узла переживают отказ одного, как и 3, а голосов для большинства нужно больше.

Блокировка с арендой не останавливает уснувшего клиента

# write.sh — хранилище за блокировкой; токен = ревизия блокировки etcd
last=$(cat /data/last 2>/dev/null || echo 0)
if [ "$token" -lt "$last" ]; then
  echo "$who token=$token REJECTED (seen $last)" >> /data/fenced.log
else
  echo "$token" > /data/last
  echo "$who token=$token accepted" >> /data/fenced.log
fi
== lock with a 2 s lease; client A freezes while holding it
   A got the lock, token 4
   B got the lock, token 6
   naive storage:
     B token=6
     A token=4
   fenced storage:
     B token=6 accepted
     A token=4 REJECTED (seen 6)

Хранилище без проверки приняло запись A после записи B — ровно сценарий двойной выплаты. Хранилище, которое помнит наибольший виденный токен и отвергает меньшие, отклонило A. Это fencing token: блокировка выдаёт монотонно растущий номер, клиент передаёт его с каждой записью, а проверяет не клиент, а ресурс. Клиент не может сам надёжно понять, что его аренда истекла: проверка «я ещё владелец?» и запись — два действия, между которыми может случиться ещё одна пауза.

В etcd токеном служит ревизия ключа блокировки, в ZooKeeper — zxid или версия узла. В базе данных проверку делают условием записи: update ... where id = ? and fence_token <= ?. Блокировка на Redis вроде Redlock монотонного токена не даёт, поэтому её используют для оптимизаций (не делать работу дважды без вреда), а не для корректности.

Порядок событий без общих часов

Часы разных машин расходятся на миллисекунды и больше, а NTP может сдвинуть их назад, как в Snowflake из Unique ID Generation. Поэтому сравнивать метки времени, поставленные разными узлами, чтобы решить, что было раньше, нельзя: событие с меньшей меткой могло произойти позже. На этом ломается last write wins — «последняя» по часам запись может оказаться не последней по факту.

Самый практичный ответ — не упорядочивать по часам вовсе, а брать порядок у того, кто его назначает: номер в журнале, ревизию, смещение в партиции. Монотонные часы процесса (System.nanoTime) годятся для измерения интервалов внутри одного процесса, но не для сравнения между машинами; настенные (System.currentTimeMillis, Instant.now) — для показа людям и грубых сроков вроде аренды, с запасом на расхождение.

Если блокировка выдана с TTL через консенсус-хранилище вроде etcd, два клиента не смогут работать с ресурсом одновременно.

etcd гарантирует, что блокировкой в каждый момент владеет один клиент с точки зрения etcd. Клиент, замерший дольше аренды, этого не знает и продолжает: в демо A записал после B. Защищает только проверка fencing token на стороне ресурса.

  • Raft: лидер, подтверждение большинством, выборы по тайм-ауту со случайной добавкой, номер срока против двух лидеров.
  • Аварийное падение лидера: 1,1–3,2 с без записи (второй раунд выборов при разделении голосов); штатная остановка с передачей лидерства — 54 мс.
  • Аренда не останавливает замерший клиент: без проверки запись с токеном 4 легла после записи с токеном 6.
  • Fencing token — монотонный номер от блокировки, проверяемый ресурсом; в etcd — ревизия.
  • Порядок — от журнала (ревизия, offset, LSN), а не по часам разных машин.

На собеседовании

Как Raft выбирает лидера и почему не бывает двух лидеров?

Лидер рассылает сердцебиения. Последователь, не получавший их дольше случайного тайм-аута выборов, становится кандидатом: увеличивает номер срока и просит голоса. Узел голосует за одного кандидата в сроке и только если журнал кандидата не отстаёт. Получивший большинство — лидер. Записи подтверждаются большинством, поэтому старый лидер в меньшинстве не может подтвердить ничего, а увидев больший срок, слагает полномочия.

  • Случайный тайм-аут уменьшает разделение голосов; в демо один раз понадобились вторые выборы.
  • Штатная остановка с передачей лидерства — десятки мс, аварийная — тайм-аут выборов.
  • 3 или 5 узлов: 4 переживают столько же отказов, что и 3.

Почему распределённой блокировки с TTL недостаточно?

Клиент может замереть (пауза GC, своп) дольше TTL: блокировка истекает, её берёт другой, а первый просыпается и продолжает работу, считая себя владельцем. Проверка «я ещё владелец» перед записью не помогает — пауза может случиться между проверкой и записью. Нужен fencing token: монотонный номер от блокировки, который ресурс проверяет и отвергает устаревшие.

  • etcd — ревизия ключа блокировки, ZooKeeper — zxid; в базе — условие в UPDATE.
  • Redlock монотонного токена не даёт — годится для оптимизаций, не для корректности.
Что не так с этим выбором лидера? 
@Scheduled(fixedDelay = 5_000)
void tick() {
    boolean leader = redis.set("payouts:leader", instanceId, SetParams.setParams().nx().px(10_000)) != null
                  || instanceId.equals(redis.get("payouts:leader"));
    if (leader) {
        redis.pexpire("payouts:leader", 10_000);
        payouts.runDue();                       // может работать дольше 10 секунд
    }
}

Если runDue или пауза GC длятся дольше 10 секунд, ключ истекает, лидером становится другой экземпляр, а первый продолжает выплаты — два лидера. Проверка и продление — отдельные команды, между ними ключ может смениться. Нужен fencing token, который проверяет хранилище выплат (например, условие на номер эпохи лидера в UPDATE), и идемпотентность самих выплат по ключу периода и магазина, чтобы повтор ничего не выплатил дважды.

Можно ли упорядочивать события разных сервисов по времени?

Нельзя полагаться: часы машин расходятся и могут прыгнуть назад при синхронизации, и событие с меньшей меткой может быть более поздним. Порядок берут у того, кто его назначает: номер в журнале консенсуса, смещение в партиции Kafka, LSN базы. Для причинно-следственного порядка — логические часы Лэмпорта или векторные.

  • Last write wins по часам теряет записи при расхождении часов.
  • nanoTime — для интервалов в одном процессе, не для сравнения между машинами.
  • Spanner делает время безопасным ожиданием конца интервала неопределённости.
