Consistent Hashing

Раскладка ключей по hash % N ровная, но при изменении N переезжает почти всё: при переходе с 4 узлов на 5 — 80 % ключей. Консистентное хеширование помещает и ключи, и узлы на одно кольцо хешей; ключ принадлежит первому узлу по часовой стрелке, поэтому новый узел забирает только свою дугу — около 1/N ключей. С одной точкой на узел дуги случайны и нагрузка неравна — от 7 до 195 % средней. Виртуальные узлы — сотни точек на узел — выравнивают нагрузку до нескольких процентов и распределяют ключи упавшего узла по всем остальным. Redis Cluster вместо кольца использует 16 384 фиксированных слота, а Kafka — hash % partitions, поэтому добавление партиций меняет раскладку ключей.

Добавили пятый узел кеша, и база легла

Кеш карт клиентов разложен по четырём узлам Redis на стороне приложения: node = hash(cardId) % 4. Под нагрузкой добавили пятый узел, и формула стала % 5. Почти каждый ключ теперь ищется не на том узле, где лежит: кеш как будто очистился целиком, все запросы пошли в базу, и она не выдержала. Ровно то же происходит, когда один узел падает и N уменьшается.

Тема разбирает, сколько ключей переезжает при разных схемах, как кольцо и виртуальные узлы решают задачу и где эти идеи живут в Redis Cluster, Cassandra и Kafka. Шардирование баз целиком — в Sharding, кеширование и лавина промахов — в Caching. Демо HashRingDemo.java раскладывает миллион ключей и считает переезды и нагрузку.

hash % N переносит почти все ключи при изменении N

== adding cache-5 to 4 nodes: share of 1,000,000 keys that move
   hash % N             moved  80.0%   load on 5 nodes: min  100%, max  100% of average
   ring, 1 vnodes       moved   8.1%   load on 5 nodes: min    7%, max  195% of average
   ring, 10 vnodes      moved  26.6%   load on 5 nodes: min   57%, max  141% of average
   ring, 100 vnodes     moved  21.1%   load on 5 nodes: min   96%, max  105% of average
   ring, 1000 vnodes    moved  20.5%   load on 5 nodes: min   97%, max  103% of average

Ключ остаётся на месте при переходе с 4 на 5 узлов, только если h % 4 == h % 5, то есть остаток от деления на 20 меньше 4 — для 4 значений из 20. Поэтому переезжает 16/20 = 80 % ключей, что и показала первая строка. В общем случае при переходе с N на N + 1 остаётся на месте лишь 1/(N + 1) ключей: чем больше кластер, тем хуже. Минимально возможный переезд — только то, что должно уйти на новый узел, 1/5 = 20 % ключей.

При этом раскладка % N идеально ровная — каждый узел получил 100 % средней нагрузки. Задача консистентного хеширования — сохранить ровность и переносить при изменении состава только необходимый минимум.

Кольцо: новый узел забирает только свою дугу

// Кольцо: каждый узел занимает vnodes точек; ключ идёт к первой точке по часовой стрелке.
static Placement ring(List<String> nodes, int vnodes) {
    TreeMap<Long, String> ring = new TreeMap<>();
    for (String n : nodes) for (int v = 0; v < vnodes; v++) ring.put(hash(n + "#" + v), n);
    return h -> {
        SortedMap<Long, String> tail = ring.tailMap(h);           // точки не меньше хеша ключа
        return tail.isEmpty() ? ring.firstEntry().getValue()      // за концом — переход на начало
                              : tail.get(tail.firstKey());
    };
}

Поиск узла — TreeMap.ceilingEntry по хешу ключа, O(log V), где V — число точек. Хеш-функция должна хорошо перемешивать: String.hashCode для похожих имён вроде «cache-1», «cache-2» даёт близкие значения, и все точки соберутся в одном месте кольца. Демо берёт первые 8 байт MD5; в продакшене — MurmurHash или xxHash, которые быстрее и не претендуют на криптостойкость.

С одной точкой новый узел забрал 8,1 % ключей вместо ожидаемых 20 % — ему досталась короткая дуга. Это та же неравномерность: переезжает ровно то, что легло на новую дугу. С 100 и 1 000 точками переезд — 21,1 % и 20,5 %, почти идеальные 20 %. Строка с 10 точками — 26,6 % при нагрузке от 57 до 141 % — показывает, что десятка точек мало: разброс дуг ещё велик.

Виртуальные узлы распределяют ключи упавшего узла по всем

== cache-3 fails: who takes its keys
   ring, 1 vnodes: {cache-2=349228}
   ring, 100 vnodes: {cache-1=29871, cache-2=56400, cache-4=32307, cache-5=80430}

С одной точкой на узел упавший cache-3 отдаёт все свои 349 тысяч ключей единственному соседу по кольцу. Сосед получает двойную нагрузку разом — промахи кеша, прогрев, запросы к базе — и может упасть следом, передав ещё больше ключей следующему: каскадный отказ. Со 100 точками те же ключи расходятся по всем четырём оставшимся узлам. Распределение не идеально ровное — от 30 до 80 тысяч, — но ни один узел не получает весь удар.

Виртуальные узлы дают и третью возможность: разное число точек для узлов разной мощности. Узел с вдвое большей памятью получает вдвое больше точек и вдвое больше ключей. Цена — память под кольцо (тысячи точек на кластер — копейки) и более сложная картина при перебалансировке: новый узел забирает понемногу у всех, поэтому все узлы участвуют в переносе данных.

Как это устроено в Redis Cluster, Cassandra и Kafka

Фиксированные слоты Redis Cluster — вариант той же идеи: число слотов не меняется, меняется только их владелец, поэтому ключи никогда не пересчитывают формулу заново. Схема проще кольца и позволяет переносить нагрузку слотами вручную. У Kafka, наоборот, формула % партиций: увеличение числа партиций переводит часть ключей в другие партиции, и события одного ключа оказываются в двух партициях с разным порядком, как разобрано в Kafka Producer. Поэтому число партиций выбирают с запасом заранее.

Есть и другие схемы с тем же свойством минимального переноса. Rendezvous hashing (HRW) считает для ключа хеш с каждым узлом и выбирает максимальный — без кольца, O(N) на поиск. Jump consistent hash от Google вычисляет номер узла за O(log N) без памяти, но умеет только добавлять и убирать узлы с конца списка.

Консистентное хеширование само по себе распределяет нагрузку равномерно.

С одной точкой на узел дуги случайны: в демо нагрузка от 7 до 195 % средней, а ключи упавшего узла целиком ушли одному соседу. Равномерность дают виртуальные узлы — при 100 точках 96–105 %. Горячий ключ при этом всё равно лежит на одном узле: от него спасает не хеширование, а репликация чтений или локальный кеш.

  • hash % N при переходе с 4 на 5 узлов переносит 80 % ключей; минимум — 20 %.
  • Кольцо: ключ принадлежит первому узлу по часовой стрелке; новый узел забирает только свою дугу.
  • Одна точка на узел — нагрузка 7–195 % средней; 100 виртуальных узлов — 96–105 %, переезд 21 %.
  • Ключи упавшего узла: с одной точкой — все одному соседу, с виртуальными — по всем.
  • Redis Cluster — 16 384 фиксированных слота; Cassandra — токены и vnodes; Kafka — hash % партиций.

На собеседовании

Что такое консистентное хеширование и зачем оно?

Способ распределить ключи по узлам так, чтобы при добавлении или удалении узла переезжал минимум ключей. Ключи и узлы хешируются на одно кольцо, ключ принадлежит первому узлу по часовой стрелке. Новый узел забирает только дугу перед собой — около 1/N ключей, тогда как hash % N при переходе с 4 на 5 узлов переносит 80 %.

  • Без виртуальных узлов нагрузка неравна, и упавший узел целиком нагружает соседа.
  • Поиск — TreeMap.ceilingEntry, O(log V).
  • Альтернативы: фиксированные слоты, rendezvous hashing, jump hash.

Зачем нужны виртуальные узлы?

С одной точкой на узел длины дуг случайны, и нагрузка сильно неравна. Каждый физический узел получает много точек на кольце, сумма многих коротких дуг близка к средней. Ключи упавшего узла расходятся по всем остальным, а не достаются одному соседу. Число точек можно сделать пропорциональным мощности узла.

  • Десятка точек мало: в демо 57–141 % средней; сотни — несколько процентов.
  • Цена — все узлы участвуют в перебалансировке.
Что не так с этим шардингом кеша? 
List<Jedis> nodes = ...;                       // 6 узлов, при пиках добавляем седьмой
Jedis nodeFor(String key) {
    return nodes.get(Math.abs(key.hashCode()) % nodes.size());
}

При добавлении седьмого узла остаток меняется почти у всех ключей — с 6 на 7 узлов на месте остаются лишь около 1/7 ключей — и кеш фактически обнуляется в момент пика, когда он нужнее всего. Math.abs(Integer.MIN_VALUE) отрицателен, и для такого хеша индекс выйдет за границы; нужен Math.floorMod. String.hashCode плохо перемешивает похожие ключи. Нужно кольцо с виртуальными узлами и хорошей хеш-функцией или Redis Cluster со слотами.

Как распределяются ключи в Redis Cluster и Kafka?

Redis Cluster: CRC16 ключа по модулю 16 384 слота, слоты назначены узлам и переносятся между ними явно; ключи с одинаковым hash tag в фигурных скобках попадают в один слот. Kafka: murmur2 ключа по модулю числа партиций, поэтому добавление партиций меняет раскладку ключей и нарушает порядок по ключу.

  • Фиксированное число слотов — та же идея, что и кольцо: формула не меняется, меняется владелец.
  • Число партиций Kafka выбирают с запасом заранее.
