Cryptography

У бэкенда четыре криптографические задачи, и для каждой свой инструмент. Пароли хранят медленным хешем с солью — bcrypt, scrypt, Argon2id или PBKDF2, — чтобы перебор после утечки был дорогим. Целостность сообщения с общим секретом проверяют HMAC. Данные шифруют AES-GCM: он и скрывает содержимое, и обнаруживает подмену, но ломается при повторе nonce. Подпись закрытым ключом — RSA, ECDSA, Ed25519 — доказывает авторство любому, у кого есть публичный ключ. Собственные схемы не изобретают, а ключи держат в KMS, а не в коде.

Утёкший бэкап базы проверяет, правильно ли выбраны алгоритмы

Бэкап базы платёжного сервиса оказался в открытом бакете. В нём таблица пользователей с хешами паролей, таблица магазинов с банковскими реквизитами и журнал вебхуков с подписями. Что атакующий сможет с этим сделать, зависит не от сложности алгоритмов, а от того, правильный ли инструмент выбран для каждой задачи: быстрый хеш паролей перебирается за часы, шифрование в режиме ECB показывает повторы, повтор nonce в GCM раскрывает данные без ключа.

Тема разбирает, какой примитив для какой задачи и где его ломают неправильным применением. Как Spring Security хранит пароли через PasswordEncoder, разобрано в Authentication, а как криптография работает в TLS — в TLS. Демо CryptoDemo.java использует только стандартные провайдеры JDK: java CryptoDemo.java на JDK 21. Ключи, соли и nonce случайные; скорость снята на машине автора, на одном ядре.

Пароль хешируют медленно и с солью, чтобы перебор стал дорогим

Криптографический хеш вроде SHA-256 необратим, но быстр. Это хорошо для проверки целостности файлов и плохо для паролей: атакующий с утёкшим хешем не обращает его, а перебирает кандидатов из словаря и сравнивает. Скорость перебора — скорость хеша:

sha.digest(pwd);                                                     // SHA-256
pbkdf2.generateSecret(new PBEKeySpec(pwd, salt, 600_000, 256));     // PBKDF2-HMAC-SHA256, 600 000 итераций
== password hashing cost (one core)
SHA-256:                ~33.0 million guesses/s
PBKDF2-SHA256 x600000:  ~50 ms per guess (~20 guesses/s)

Одно ядро процессора проверяет 33 миллиона паролей в секунду по SHA-256 и 20 — по PBKDF2 с 600 000 итераций: в полтора миллиона раз медленнее. Словарь из миллиарда популярных паролей по SHA-256 перебирается за полминуты на одном ядре, а видеокарта на порядки быстрее. Для пользователя 50 мс при входе незаметны. Специализированные функции — bcrypt, scrypt, Argon2id — ещё и требуют памяти, что лишает видеокарты преимущества. OWASP рекомендует Argon2id, а если его нет — scrypt, bcrypt или PBKDF2 с 600 000 итераций; стоимость поднимают по мере роста железа.

== salt
anna  sha256(pwd)        = daaad6e5604e8e17...
boris sha256(pwd)        = daaad6e5604e8e17...  same password visible
anna  pbkdf2(salt, pwd)  = b9096fbefc54be1e...  salt 1b705602...
boris pbkdf2(salt, pwd)  = 06072da00c049146...  salt bd62d280...

Без соли одинаковые пароли дают одинаковые хеши: видно, у кого общий пароль, а заранее посчитанные таблицы хешей популярных паролей находят их мгновенно. Соль — случайные байты, уникальные для каждого пользователя и хранимые рядом с хешем. Она не секрет; её задача — заставить атакующего перебирать каждого пользователя отдельно. Перец (pepper) — дополнительный секрет, общий для всех и хранимый вне базы, например в KMS: утечка одной базы без него бесполезна.

HMAC проверяет целостность и автора, если секрет общий

Хеш сообщения сам по себе не защищает от подмены: атакующий изменит сообщение и пересчитает хеш. Нужен ключ. HMAC — хеш с секретом, построенный так, что без ключа нельзя вычислить правильное значение для изменённого сообщения. На нём держатся подписи вебхуков и запросов из Authentication Basics и токены HS256 из JWT.

Самодельная замена sha256(secret + message) уязвима: у SHA-256 и SHA-1 есть атака удлинения сообщения, позволяющая дописать данные к сообщению и вычислить правильный хеш, не зная секрета. HMAC специально построен с двумя проходами хеша и этой атаке не подвержен. Сравнивают HMAC за постоянное время — MessageDigest.isEqual.

HMAC проверяет только тот, у кого есть секрет, и он же может подделать сообщение. Если проверяющих много или нужно доказать авторство третьей стороне, нужна асимметричная подпись.

AES-GCM скрывает данные и ловит подмену, но не прощает повтора nonce

Симметричное шифрование — один ключ для шифрования и расшифровки; стандарт — AES. Сам AES шифрует блок в 16 байт, а то, как шифруются длинные данные, определяет режим. Простейший режим ECB шифрует каждый блок независимо одним ключом:

== ECB vs GCM, three equal 16-byte blocks
ECB: 7ccef691… 7ccef691… 7ccef691…
GCM: 4430ba6e… c6f85531… c1b855c4…

Три одинаковых блока открытого текста дали три одинаковых блока шифртекста: не зная ключа, атакующий видит, где данные повторяются, и может переставлять блоки. ECB не используют никогда. GCM превращает AES в поточный шифр со счётчиком и уникальным nonce, поэтому повторы исчезают, и добавляет тег аутентичности — 16 байт, проверяемых при расшифровке:

== GCM tamper
flipped 1 bit -> AEADBadTagException

Это AEAD — шифрование с аутентификацией: изменение хоть одного бита отклоняется, а не расшифровывается в искажённые данные. Режимы без аутентификации, как CBC и CTR, молча расшифровывают подделку, и на этом построены атаки вроде padding oracle. Цена GCM — строгое требование к nonce: он не должен повторяться для одного ключа никогда.

byte[] c1 = gcm(key, iv, "card=4111111111111111".getBytes());
byte[] c2 = gcm(key, iv, "card=5500005555555559".getBytes());   // Тот же nonce.
recovered[i] = (byte) (c1[i] ^ c2[i] ^ p1[i]);                   // Ключ не нужен.
== GCM nonce reuse
attacker knows p1, recovers p2 = card=5500005555555559

При одинаковом nonce оба сообщения шифруются одним и тем же потоком ключа, и XOR двух шифртекстов равен XOR двух открытых текстов. Зная одно сообщение, атакующий читает второе без ключа; кроме того, он может подделывать теги. Nonce в 12 байт генерируют SecureRandom для каждого шифрования или берут счётчиком, а после примерно 232 шифрований со случайным nonce ключ меняют. Для Java сторонние библиотеки вроде Google Tink дают API, в котором nonce выбрать неправильно нельзя.

Асимметричная пара: публичным ключом проверяют подпись и договариваются о ключе

В асимметричной криптографии у владельца пара ключей: закрытый держат в секрете, публичный раздают всем. Для бэкенда важны две операции. Подпись: владелец подписывает закрытым ключом, любой проверяет публичным, и никто, кроме владельца, не может подписать. Согласование ключа (ECDH): две стороны, обменявшись публичными ключами, получают общий секрет, которого не было в сети; так TLS получает симметричный ключ сессии.

== Ed25519 signature
signature bytes = 64, public key (X.509) bytes = 44
verify original = true
verify amount=5000 = false

Ed25519 — подпись на эллиптической кривой: ключ 32 байта, подпись 64, быстрая и без подводных камней со случайностью, которые были у ECDSA. RSA-2048 даёт подписи по 256 байт и нужен для совместимости. Шифрование данных публичным ключом напрямую почти не используют: асимметричные операции медленные и ограничены размером. Вместо этого применяют гибридную схему: данные шифруют случайным симметричным ключом, а его — публичным ключом получателя или через ECDH.

Ключ в коде сводит на нет любой алгоритм

Шифрование реквизитов в базе бесполезно, если ключ лежит в application.yml в том же репозитории или в переменной окружения рядом с паролем от базы. Ключи хранят в KMS — облачном сервисе ключей или HSM, из которого главный ключ не выходит. Данные шифруют по схеме конвертов (envelope encryption):

Остальные правила короткие. Случайность для ключей, токенов и nonce — только SecureRandom; java.util.Random предсказуем по нескольким выходам. Устаревшие MD5, SHA-1, DES и RSA с PKCS#1 v1.5 для шифрования не применяют в новом коде. Шифрование не заменяет контроль доступа: если приложение расшифровывает данные для любого, кто спросил, шифрование защищает только бэкапы и диски.

Пароли надо шифровать, чтобы их можно было восстановить для пользователя.

Пароль, который можно расшифровать, утечёт вместе с ключом. Пароли хешируют необратимо медленной функцией с солью, а вместо восстановления дают сбросить пароль через подтверждённый канал.

  • Пароли: Argon2id, bcrypt, scrypt или PBKDF2 с солью; в демо SHA-256 — 33 млн проверок в секунду, PBKDF2 — 20.
  • HMAC — целостность с общим секретом; sha256(secret + msg) уязвим к удлинению.
  • AES-GCM — шифрование с аутентификацией; ECB показывает повторы, повтор nonce раскрывает текст без ключа.
  • Подпись закрытым ключом проверяет любой; данные шифруют гибридно: симметричный ключ плюс асимметричная обёртка.
  • Ключи в KMS, envelope encryption, SecureRandom; своих схем не изобретают.

На собеседовании

Как правильно хранить пароли и зачем соль?

Хешировать специализированной медленной функцией — Argon2id, bcrypt, scrypt или PBKDF2 с большим числом итераций. Быстрый SHA-256 даёт десятки миллионов проверок в секунду на ядро, и словарные пароли после утечки подбираются быстро. Соль — случайное значение на пользователя, хранится рядом с хешем: одинаковые пароли дают разные хеши, а заранее посчитанные таблицы бесполезны.

  • Стоимость подбирают под 50–500 мс на сервере и повышают со временем; хеш хранит параметры, чтобы перехешировать при входе.
  • Argon2id и scrypt требуют памяти и лишают видеокарты преимущества.
  • Перец — общий секрет вне базы; bcrypt учитывает только первые 72 байта пароля.

Чем симметричное шифрование отличается от асимметричного и где что применяют?

Симметричное — один общий ключ, быстрое, для данных: AES-GCM. Асимметричное — пара ключей: публичным проверяют подпись или шифруют, закрытым подписывают или расшифровывают; медленное и ограничено размером. На практике их совмещают: TLS договаривается о симметричном ключе через ECDH и проверяет сервер по подписи, а данные шифрует AES.

  • Подпись (Ed25519, ECDSA, RSA) доказывает авторство любому; HMAC — только владельцу общего секрета.
  • Envelope encryption: данные — ключом данных, ключ данных — главным ключом в KMS.

Почему AES-GCM, а не ECB или CBC, и что важно при его использовании?

ECB шифрует одинаковые блоки одинаково и раскрывает структуру данных. CBC без MAC не обнаруживает подмену и уязвим к padding oracle. GCM — AEAD: шифрует и проверяет целостность тегом, любой изменённый бит даёт ошибку расшифровки.

Главное требование GCM — уникальный nonce для каждого шифрования одним ключом. Повтор nonce раскрывает XOR открытых текстов и позволяет подделывать теги.

  • Nonce 12 байт из SecureRandom или счётчик; после ~2^32 сообщений со случайным nonce ключ меняют.
  • Библиотеки вроде Tink скрывают nonce и режим, чтобы их нельзя было выбрать неправильно.
Что не так с шифрованием реквизитов? 
private static final byte[] KEY = "pay-secret-key-0123456789abcdef!".getBytes();
private static final byte[] IV = new byte[12];

byte[] encrypt(String iban) throws Exception {
    Cipher c = Cipher.getInstance("AES/GCM/NoPadding");
    c.init(Cipher.ENCRYPT_MODE, new SecretKeySpec(KEY, "AES"), new GCMParameterSpec(128, IV));
    return c.doFinal(iban.getBytes());
}

Nonce — нулевой и одинаковый для всех записей: XOR двух шифртекстов раскрывает XOR двух IBAN, а зная один, атакующий читает остальные; теги тоже можно подделать. Ключ зашит в код и попадает в репозиторий и артефакты. Нужен случайный nonce на каждое шифрование, сохраняемый рядом с шифртекстом, и ключ из KMS по схеме конвертов.
