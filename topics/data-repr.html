Numbers & Text

Сумма платежа и его назначение хранятся в конечных последовательностях битов. Для суммы важны ширина числа и правила арифметики, для текста — номера знаков и кодировка. При странном результате восстанови цепочку: значение → тип или кодировка → операция → результат. Так становится видно, где потерялись разряды или изменился смысл байтов.

Правильные входные данные ещё не обещают правильный результат

Сервис складывает два пакета платежей: 15 млн и 10 млн рублей, суммы хранит в копейках. Каждый пакет помещается в int, сумма за день становится отрицательной, а исключения нет. Рядом сверка комиссии не признаёт равными 0.1 + 0.2 и 0.3. В чеке четыре видимых знака, но лимит в пять байт превышен вдвое.

Ошибки возникают ещё до базы и сети. Целое число, двоичная дробь, позиция в строке и байт после кодирования — разные меры. Каждая полезна для своей задачи; сбой начинается, когда от неё ждут свойств другой.

Все фрагменты ниже взяты из одного DataRepresentationDemo.java, без библиотек и сборки. Запуск проверен на OpenJDK JBR 21.0.11; в каждом шаге показан вывод соответствующего метода, без служебной строки с его именем.

# Из корня базы; java -version должен показывать 21.
java examples/cs/DataRepresentationDemo.java
int firstBatch = 1_500_000_000;               // Копейки, оба пакета по отдельности влезают в int.
int secondBatch = 1_000_000_000;
int dailyTotal = firstBatch + secondBatch;  // Сумма уже не влезает в 32 знаковых бита.
System.out.println("daily total = " + dailyTotal);
System.out.println("0.1 + 0.2 == 0.3: " + (0.1 + 0.2 == 0.3));
String receipt = "A\u042F\u20AC\uD83D\uDCB3"; // AЯ€💳: последний знак занимает два char.
System.out.println("receipt chars/bytes = " + receipt.length() + "/"
        + receipt.getBytes(StandardCharsets.UTF_8).length);

Дневная сумма 2_500_000_000 копеек превышает максимум int. double хранит ближайшие доступные двоичные дроби вместо точных десятых. length() считает единицы UTF-16, getBytes(UTF_8).length — байты передачи. Разберём, что сохраняет каждое представление.

Дополнительный код даёт старшему биту отрицательный вес

У восьми битов ровно 256 комбинаций. В unsigned их значения идут от 0 до 255, веса разрядов — 128, 64, 32, 16, 8, 4, 2, 1. У целых Java дополнительный код, two’s complement: старший вес становится −128, остальные сохраняются.

11111011 как byte равен −128 + 64 + 32 + 16 + 8 + 2 + 1 = −5. В unsigned те же биты дают 251: изменилось правило чтения, а не данные. Старший бит показывает знак, но остальные семь не являются модулем числа.

В n битах отрицание равно ~x + 1. Число и его инверсия в сумме дают 2ⁿ − 1; ещё единица даёт 2ⁿ, от которого в n битах остаётся ноль. Поэтому один двоичный сумматор работает и с положительными, и с отрицательными числами.

Диапазон несимметричен: −2ⁿ⁻¹ … 2ⁿ⁻¹−1. Для byte это −128…127, для int −2 147 483 648…2 147 483 647. Ноль занимает одну комбинацию 000…0, поэтому отрицательных значений на одно больше. Положительный партнёр минимума в том же типе не помещается.

byte delta = -5;
String bits = String.format(Locale.ROOT, "%8s",
        Integer.toBinaryString(delta & 0xff)).replace(' ', '0'); // Только младшие 8 бит.
System.out.println("-5 bits = " + bits);
System.out.println("unsigned byte = " + Byte.toUnsignedInt(delta)); // Та же восьмёрка бит.
System.out.printf(Locale.ROOT, "widen to int = %08X%n", (int) delta); // Знак расширяется.
byte min = Byte.MIN_VALUE;
System.out.println("-min as int/byte = " + (-min) + "/" + (byte) -min);
-5 bits = 11111011
unsigned byte = 251
widen to int = FFFFFFFB
-min as int/byte = 128/-128

При расширении byte −5 до int слева добавляются единицы: FB → FFFFFFFB. Расширение знака сохраняет значение. Для байта протокола со смыслом 0…255 нужны Byte.toUnsignedInt(b) или b & 0xff: сохранить младшие восемь битов, обнулить старшие.

Знаковое число — это один бит знака и положительный модуль в остальных битах.

У целых Java старший бит имеет отрицательный вес. Например, 10000000 — это −128, а не «минус ноль». Модель «знак и модуль» даст неверные ответы про диапазон, отрицание и переполнение.

Ширину вычисления выбирают операнды, а не переменная результата

При сложении и умножении фиксированная ширина оставляет только младшие биты результата. Это арифметика по модулю 2ⁿ: сумма из первого шага 2_500_000_000 читается как отрицательная, потому что старший бит 32-битного результата установлен. Её знаковое значение равно 2_500_000_000 − 4_294_967_296 = −1_794_967_296. Java не выбрасывает исключение при таком переполнении.

long total не расширяет всю правую часть. Перед обычной целочисленной арифметикой byte, short, char расширяются до int. Есть операнд long — вычисление в long; иначе в int. Переменная слева получает уже готовый результат.

Переведём 30 млн рублей в копейки. Множитель 100 помещается в int, произведение 3 млрд — нет. Нужно расширить операнд до умножения или явно отклонить переполнение.

int rubles = 30_000_000;
long late = rubles * 100;          // Сначала int * int, затем расширение повреждённого результата.
long early = (long) rubles * 100;  // long участвует в умножении: вычисление сразу 64-битное.
System.out.println("late/early = " + late + "/" + early);
try {
    System.out.println(Math.multiplyExact(rubles, 100)); // int-версия сообщает о переполнении.
} catch (ArithmeticException e) {
    System.out.println("multiplyExact = " + e.getClass().getSimpleName());
}
byte count = 127;
System.out.println("count + 1 = " + (count + 1)); // byte расширяется до int перед сложением.
count++;                                       // Сложение сужается обратно до byte.
System.out.println("count++ = " + count);
late/early = -1294967296/3000000000
multiplyExact = ArithmeticException
count + 1 = 128
count++ = -128

(long) (rubles * 100) даёт тот же повреждённый результат, что late, а rubles * 100L — правильный, как early. Правило действует на каждый узел выражения: в (long) (a * b) + c произведение всё ещё считается в int.

Для денег выбирай единицу и диапазон вместе. Целые копейки в long точны, но комиссия в процентах потребует правила округления. Проверяемые операции превращают тихое переполнение в управляемую ошибку. Дополнительно нужны бизнес-границы: помещающееся число ещё не допустимый платёж.

Comparator на a − b может переполниться и перевернуть порядок. Используй Integer.compare(a, b) или Long.compare(a, b). Более широкий тип тоже не отменяет проверку промежуточных значений.

Под капотом: минимальное число не становится положительным от минуса

−Integer.MIN_VALUE и Math.abs(Integer.MIN_VALUE) остаются отрицательным минимумом: положительное 2³¹ не помещается. Integer.MIN_VALUE / −1 тоже возвращает минимум без исключения; деление целого на ноль бросает ArithmeticException. У long та же граница.

−Byte.MIN_VALUE даёт 128, потому что отрицание выполняется в int. Сужение обратно в byte даёт −128. Promotion меняет ответ о переполнении: правило минимального int нельзя механически переносить на byte.

Double меняет абсолютную точность вместе с величиной числа

double охватывает огромные и маленькие числа в 64 битах, задавая отдельно значащую часть и двоичный порядок. В нормальном binary64: один бит знака, 11 битов порядка, 52 бита дробной части. Неявная ведущая единица даёт 53 значащих двоичных бита.

Формула нормального числа: (−1)ˢ × (1 + fraction / 2⁵²) × 2^(exponent − 1023). Поле порядка смещено на bias 1023. Двигается двоичная точка, а число значащих разрядов остаётся фиксированным. У float поля 1/8/23 и 24 значащих бита.

Конечная двоичная дробь после сокращения имеет знаменатель — степень двойки: 1/2, 3/8. У 1/10 остаётся множитель 5, запись бесконечна: 0.0001100110011…₂. Литерал 0.1 округляется до binary64, операция округляет результат ещё раз. Десятичная печать не меняет внутреннее представление.

Арифметика округляет к ближайшему числу, при равном расстоянии — к чётному младшему значащему биту, ties-to-even. Все целые −2⁵³ … 2⁵³ точны. После 2⁵³ расстояние до следующего значения равно 2; с ростом порядка шаг удваивается. Отдельные большие целые, например 2⁵³ + 2, тоже точны.

double sum = 0.1 + 0.2; // Оба литерала и результат округляются до доступного binary64.
System.out.println("sum = " + sum);
System.out.println("0.1 hex = " + Double.toHexString(0.1));
System.out.printf(Locale.ROOT, "0.1 raw = %016X%n", Double.doubleToRawLongBits(0.1));
double big = 9_007_199_254_740_992d; // 2^53: расстояние до следующего double равно двум.
System.out.println("2^53 + 1 == 2^53: " + (big + 1 == big));
System.out.println("ulp(2^53) = " + Math.ulp(big));
System.out.println("order = " + ((1e16 + -1e16) + 1) + "/" + (1e16 + (-1e16 + 1)));
double invalid = 0.0 / 0.0; // NaN проходит проверку только на отрицательность.
System.out.println("NaN < 0 / NaN == NaN = " + (invalid < 0) + "/" + (invalid == invalid));
System.out.println("1/+0 / 1/-0 = " + (1.0 / 0.0) + "/" + (1.0 / -0.0));

Math.ulp(x) показывает шаг точности. Допуск 1e−9 не универсален: около 1e16 он меньше шага представления. Для измерений выбирай абсолютную и относительную ошибки по задаче. Для точных денег — целую минимальную единицу или BigDecimal & Money с явным округлением.

Специальные значения тоже участвуют в вычислениях

Порядок из единиц отведён под бесконечности и NaN. Переполнение даёт бесконечность, 0.0 / 0.0 — NaN без исключения. NaN не равен себе, сравнения <, >, <=, >= с ним ложны. Поэтому проверка amount < 0 его пропускает: отдельно нужна Double.isFinite(amount).

+0.0 == −0.0, но деление единицы различает их знаком бесконечности. При нулевом поле порядка ведущая единица исчезает: это ноль или subnormal. Subnormal дают постепенную потерю точности около нуля. Для платежа граница проще: сумма должна быть конечной и допустимой.

Double — это long с возможностью хранить дробную часть.

У него другая раскладка битов. Порядок расширяет диапазон, а 53 значащих бита ограничивают точность. Перевод идентификатора из long в double может потерять единицы задолго до максимума long; обратное приведение не восстановит потерянное.

Unicode задаёт номера знаков, а кодировка задаёт их запись

Unicode назначает знакам code points: Я — U+042F, € — U+20AC, 💳 — U+1F4B3. UTF-8 и UTF-16 задают запись этих номеров. Unicode не означает «один знак — один байт»: это смысловой слой над конкретной кодировкой.

Диапазон code points — U+0000…U+10FFFF, область U+D800…U+DFFF отведена под surrogates. Отдельный surrogate не является Unicode scalar value и не кодируется в правильном UTF-8. Java char — 16-битная единица UTF-16: для scalar value в BMP достаточно одной, выше U+FFFF нужна пара high/low surrogate.

String считает индексы в единицах UTF-16: length(), charAt(), substring(). Здесь charAt(3) даёт high surrogate, codePointAt(3) — полный U+1F4B3. Для обхода есть codePoints(), для сдвига на число code points — offsetByCodePoints(). Полученный индекс по-прежнему измеряется в UTF-16.

String receipt = "A\u042F\u20AC\uD83D\uDCB3"; // AЯ€💳.
System.out.println("UTF-16 units = " + receipt.length());
System.out.println("code points = " + receipt.codePointCount(0, receipt.length()));
System.out.println("UTF-8 bytes = " + receipt.getBytes(StandardCharsets.UTF_8).length);
System.out.printf(Locale.ROOT, "charAt(3) / codePointAt(3) = %04X/%X%n",
        (int) receipt.charAt(3), receipt.codePointAt(3));
System.out.println("bytes = " + HexFormat.of().withUpperCase().withDelimiter(" ")
        .formatHex(receipt.getBytes(StandardCharsets.UTF_8)));
String composed = "\u00E9";       // é: одна code point.
String decomposed = "e\u0301";   // Та же буква на экране: e и combining acute accent.
System.out.println("e-acute units = " + composed.length() + "/" + decomposed.length());
System.out.println("equals / NFC equals = " + composed.equals(decomposed) + "/"
        + composed.equals(Normalizer.normalize(decomposed, Normalizer.Form.NFC)));

Видимый знак — grapheme cluster. é бывает одной code point U+00E9 или двумя: U+0065 и U+0301. Вид совпадает, длины различаются. Emoji с модификаторами и ZWJ тоже объединяют несколько code points. Для курсора и обрезки пользовательского текста нужна сегментация grapheme clusters.

NFC приводит канонически эквивалентные записи é к одной форме. Применяй её, если контракт сравнения требует такой эквивалентности. String.equals() сравнивает единицы без нормализации. NFC не объединяет все визуально похожие знаки и не заменяет правила идентификатора.

Лимит протокола измеряй в закодированных байтах, число code points — через их подсчёт, видимые знаки — через grapheme clusters. Для ограничения поля базы уточни его единицу. Обрезка substring(0, n) способна оставить половину surrogate pair.

Под капотом: как U+1F4B3 превращается в два char

Из U+1F4B3 вычитают 0x10000: получается 0xF4B3. Деление на две десятки битов даёт верхние 0x3D и нижние 0xB3. Пара: 0xD800 + 0x3D = 0xD83D, 0xDC00 + 0xB3 = 0xDCB3. Диапазоны половинок позволяют распознать пару.

Java допускает одинокий surrogate. codePointAt() и codePoints() его не валидируют: могут вернуть непарную единицу отдельно. Для строгого Unicode используй CharsetEncoder с REPORT. Модель API UTF-16 не описывает физическую раскладку String в heap.

На границе байтов нужны кодировка и политика ошибок

UTF-8 записывает scalar value в 1–4 байтах, ASCII сохраняет однобайтные значения. Первый байт задаёт длину, продолжения начинаются с 10 и несут по шесть полезных битов. Поэтому Я занимает два байта, € три, карта четыре. Знаковый Java byte не меняет этих восьми битов.

Диапазон scalar valueШаблон байтовПример
U+0000…U+007F0xxxxxxxA → 41
U+0080…U+07FF110xxxxx 10xxxxxxЯ → D0 AF
U+0800…U+FFFF, кроме surrogates1110xxxx 10xxxxxx 10xxxxxx€ → E2 82 AC

Биты U+20AC 0010 0000 1010 1100 делятся на группы 0010 | 000010 | 101100. С префиксами получаются 11100010 10000010 10101100, то есть E2 82 AC. Копирование первых n байтов может обрезать последовательность внутри знака.

На входе платежного API фиксируй кодировку и политику ошибок. new String(bytes, UTF_8) заменяет испорченный ввод U+FFFD; успешный вызов не доказывает корректность. CharsetDecoder с REPORT отклоняет ошибку; это его default, явно заданный для ясности контракта. Он также отвергает overlong encoding, surrogates и номера выше U+10FFFF.

byte[] euro = "\u20AC".getBytes(StandardCharsets.UTF_8); // E2 82 AC — один знак в трёх байтах.
byte[] cut = Arrays.copyOf(euro, 2);                     // E2 82: последовательность оборвана.
String replaced = new String(cut, StandardCharsets.UTF_8); // Конструктор заменяет ошибку.
System.out.printf(Locale.ROOT, "replacement = U+%04X%n", replaced.codePointAt(0));
try {
    StandardCharsets.UTF_8.newDecoder()
            .onMalformedInput(CodingErrorAction.REPORT)  // На границе платежного API нужен отказ.
            .onUnmappableCharacter(CodingErrorAction.REPORT)
            .decode(ByteBuffer.wrap(cut));
} catch (CharacterCodingException e) {
    System.out.println("strict = " + e.getClass().getSimpleName());
}
String wrong = new String(euro, StandardCharsets.ISO_8859_1); // Все байты допустимы, смысл другой.
System.out.println("wrong charset = " + wrong.codePoints()
        .mapToObj(cp -> String.format(Locale.ROOT, "U+%04X", cp)).toList());
String recovered = new String(wrong.getBytes(StandardCharsets.ISO_8859_1), StandardCharsets.UTF_8);
System.out.println("recover known mistake = " + recovered.equals("\u20AC"));

strict = MalformedInputException
wrong charset = [U+00E2, U+0082, U+00AC]

В ISO-8859-1 байты E2 82 AC допустимы, но означают три других номера. Строгая проверка не угадывает правильную кодировку. Обратное преобразование в демо возможно: ошибка точно известна, байты сохранились. После U+FFFD, отбрасывания или неизвестных преобразований общего восстановления нет.

Не декодируй каждый кусок потока отдельным new String(). Сохраняй непотреблённые байты после UNDERFLOW, продолжай тем же decoder. Финальный endOfInput = true превращает неполный хвост в ошибку. UNDERFLOW не доказывает корректность завершённого поля. Один decoder хранит состояние одной операции и не разделяется между потоками.

Для диагностики возьми обезличенные сырые байты и известную кодировку. Выведи hex, длину байтов, UTF-16 и code points, как в демо. Правильный UTF-8 гарантирует уровень текста; разбор JSON и совместимость схем относятся к Serialization Formats.

  • Дополнительный код задаёт старшему разряду отрицательный вес; те же биты можно прочитать как unsigned с другим значением.
  • Приводи операнд к long до вычисления. Присваивание повреждённого int в long уже ничего не восстанавливает.
  • У double 53 значащих бита: порядок увеличивает диапазон, а шаг точности растёт с величиной. NaN требует отдельной проверки.
  • UTF-16 units, Unicode code points, grapheme clusters и UTF-8 bytes — разные меры длины с разными задачами.
  • На границе байтов фиксируй кодировку, сохраняй неполный ввод и решай, отклонять ошибки или заменять их. Ни успешный new String, ни валидность выбранной кодировки не гарантируют исходного смысла.

На собеседовании

Как хранятся отрицательные целые и что произойдёт при переполнении?

Я представляю byte, short, int и long как дополнительный код фиксированной ширины. У старшего бита отрицательный вес, поэтому для n битов диапазон равен −2ⁿ⁻¹…2ⁿ⁻¹−1. Отрицание получается инверсией и прибавлением единицы; минимум не имеет положительного партнёра в том же типе.

Обычная арифметика сохраняет младшие биты и не сообщает о переполнении. Для суммы платежей я выбираю диапазон промежуточных результатов и проверяемые операции вроде Math.addExact. Если нужно вычисление в long, расширяю операнд заранее: переменная long слева не расширяет умножение двух int.

  • Promotion делает арифметику byte и short 32-битной. Поэтому −Byte.MIN_VALUE — 128, а −Integer.MIN_VALUE — снова минимум; тип промежуточного выражения меняет ответ.
  • При чтении протокола отрицательный Java byte не означает отрицательное поле. b & 0xff даёт беззнаковое значение в int; обычное расширение сохраняет знак.
  • Проверяю каждый промежуточный результат, например произведение до деления в расчёте процента. Математически маленький итог не спасает переполнившееся произведение.
Вернёт ли long точную сумму в копейках? 
long toCents(int rubles) {
    return (long) (rubles * 100);
}

Нет. При 30 млн рублей умножение уже переполнилось в int, а cast расширяет повреждённое значение. Выбор зависит от контракта: (long) rubles * 100 сохраняет точный результат для любого int, а Math.multiplyExact(rubles, 100) отклоняет результат, который не помещается именно в int. Отдельно нужны допустимый знак и бизнес-лимит суммы.

Почему 0.1 + 0.2 не равно 0.3 и почему double не подходит для любых денег?

Я начинаю с основания системы счисления: десятая часть не имеет конечной двоичной записи. В double хранится ближайшее доступное значение, а результат операции округляется ещё раз. У binary64 53 значащих бита, поэтому он даёт приближённые числа с большим диапазоном, а абсолютный шаг точности растёт вместе с порядком.

Для точных сумм беру целое число минимальных единиц или BigDecimal с правилами округления. Для измерений double удобен, но сравнение задаю через допустимую ошибку самой задачи. Вывод 0.3 — формат печати, он не доказывает наличие точной десятичной дроби внутри.

  • Округление делает сложение неассоциативным: порядок агрегации влияет на итог. Поэтому параллельная сумма и последовательная могут отличаться, даже если обе выполняют правильный код.
  • Большие целочисленные ID нельзя безоговорочно передавать через double. Точная непрерывная сетка целых заканчивается на 2⁵³; дальше отдельные кратные шагу точны, а соседние значения могут слиться.
  • Для внешнего числового ввода проверяю конечность до бизнес-сравнений: NaN проходит проверку amount < 0, а бесконечность способна испортить расчёт без исключения.
Какое значение пройдёт обе проверки допустимой суммы? 
if (amount < 0 || amount > 1_000_000) {
    throw new IllegalArgumentException("amount");
}

NaN пройдёт: обе части сравнения ложны. Исправление для такого контракта — сначала !Double.isFinite(amount), затем границы диапазона. Альтернатива !(amount >= 0 && amount <= 1_000_000) тоже отклонит NaN, но явная проверка конечности лучше выражает причину отказа. Корректность представления не заменяет выбор подходящего типа для денег.

Чем char отличается от Unicode-символа и что считает String.length()?

Я уточняю, что значит «символ». char — 16-битная unit UTF-16, code point — номер в Unicode, а пользовательский знак может состоять из нескольких code points. String.length() считает units UTF-16. Поэтому supplementary code point занимает две позиции, и charAt() может вернуть половину surrogate pair.

Если нужно число code points, использую codePointCount(); если размер сообщения, кодирую его в нужную кодировку и считаю байты. Для ограничения видимых знаков нужна сегментация grapheme clusters. У строки AЯ€💳 четыре code points, пять units UTF-16 и десять байтов UTF-8.

  • Канонически эквивалентные последовательности вроде é и e + U+0301 не равны через String.equals(). Нормализацию назначает контракт данных; применение её перед подписью изменит подписываемые байты.
  • Проход по code points сохраняет supplementary знаки, но всё ещё может разрезать grapheme cluster. Для обрезки отображаемого имени сначала определяю единицу, которую обещает интерфейс.
  • Строка Java может содержать непарный surrogate. API code points его не валидирует; строгий encoder с REPORT позволяет остановиться перед отправкой некорректного Unicode.

Как устроен UTF-8 и как обнаружить испорченный текст на входе?

UTF-8 кодирует Unicode scalar value в один–четыре байта. ASCII остаётся однобайтным; у многобайтной записи первый префикс задаёт длину, а продолжения начинаются с 10. Поэтому граница произвольного байтового куска может оказаться внутри знака.

Я фиксирую кодировку в контракте и выбираю политику ошибок. new String(bytes, UTF_8) заменяет испорченную запись, а строгий CharsetDecoder сообщает ошибку. При поточном чтении сохраняю непотреблённый хвост и продолжаю декодирование; если ввод закончился посреди знака, отклоняю его.

  • Валидность байтов в выбранной кодировке не доказывает, что выбрана правильная кодировка. ISO-8859-1 примет байты евро из UTF-8 и даст три других code points без ошибки.
  • UTF-8 допускает только кратчайшую запись code point и запрещает кодирование surrogate values. Строгая проверка нужна до дальнейшей интерпретации, иначе разные декодеры могут прочитать разные строки.
  • После замены ошибочных байтов символом U+FFFD исходные данные не восстановить в общем случае. Для диагностики сохраняю обезличенные исходные байты до преобразования, а не только получившийся текст.
E2 82 пришло в первом чтении, AC — во втором. Ввод испорчен?

Если это части одного потока, нет: вместе они составляют правильный UTF-8 для евро. После первого чтения нужно оставить E2 82 в буфере и сообщить decoder, что ввод ещё продолжается. Если первый кусок объявлен отдельным завершённым полем, он испорчен и должен вызвать ошибку. Развилка определяется границей сообщения, а не числом вызовов чтения.
