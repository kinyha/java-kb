Date & Time

Пользователь назначает встречу по календарю и местным часам. Для отправки напоминания сервису нужен определённый момент на временной линии. Часовой пояс связывает эти два представления, но иногда одно местное время соответствует двум моментам или не соответствует ни одному. Выбор типа, правила разрешения и единицы арифметики сохраняют смысл встречи между сервисами.

Одинаковое местное 02:30 может означать две разные встречи

Встреча назначена на 27 октября 2024 года в 02:30, Europe/Berlin. Сервис сохранил только LocalDateTime и при отправке напоминания добавил пояс. В этот день часы переводят назад: интервал 02:00–03:00 проходит дважды. Первое 02:30 имеет offset +02:00 и соответствует 00:30Z; второе — +01:00 и 01:30Z. Потерянный выбор нельзя восстановить из сохранённых полей.

Это не погрешность часов и не ошибка форматирования. Одна календарная надпись обозначила два возможных момента с разницей в час. TimelineDemo.java проверен на JDK 21 с TZDB 2026a; версия правил напечатана самой программой. Здесь даты фиксированы, поэтому опыт не зависит от текущего времени и default zone машины.

// Фрагмент TimelineDemo.java; java examples/date-time/TimelineDemo.java
ZoneId berlin = ZoneId.of("Europe/Berlin");
System.out.println("tzdb=" + ZoneRulesProvider.getVersions("Europe/Berlin").lastKey());
LocalDateTime requested = LocalDateTime.parse("2024-10-27T02:30");
ZonedDateTime early = requested.atZone(berlin); // нет предпочтения: ранний offset
ZonedDateTime late = early.withLaterOffsetAtOverlap();
System.out.println("valid offsets=" + berlin.getRules().getValidOffsets(requested));
System.out.println("early=" + early + ", instant=" + early.toInstant());
System.out.println("late=" + late + ", instant=" + late.toInstant());
System.out.println("same fields=" + early.toLocalDateTime().equals(late.toLocalDateTime())
        + ", elapsed minutes=" + Duration.between(early, late).toMinutes());
tzdb=2026a
valid offsets=[+02:00, +01:00]
early=2024-10-27T02:30+02:00[Europe/Berlin], instant=2024-10-27T00:30:00Z
late=2024-10-27T02:30+01:00[Europe/Berlin], instant=2024-10-27T01:30:00Z
same fields=true, elapsed minutes=60

В журнале уже случившегося события сохраняй определённый момент. Для ввода будущей встречи сохраняй смысл пользовательской договорённости и решение об overlap. Добавить любой пояс в конце обработки — значит принять новое решение о времени, которое пользователь мог не делать.

Календарные поля и момент связывает конкретный offset

LocalDate хранит год, месяц и день; LocalTime — время суток; LocalDateTime соединяет их без зоны. Слово local не означает «пояс сервера»: пояс вообще отсутствует. День рождения нужен как LocalDate, а повторяющееся время открытия магазина — как LocalTime вместе с отдельными правилами расписания. Такие значения ещё не определяют точку на временной линии.

Instant хранит epoch seconds и наносекундную часть относительно 1970-01-01T00:00:00Z. Его можно показать в разных регионах, сохранив тот же момент. OffsetDateTime добавляет к календарным полям фиксированное смещение от UTC. ZonedDateTime хранит поля, ZoneId и разрешённый offset, поэтому даже внутри overlap обозначает один момент. Эти значения immutable: plus и with возвращают результат, который надо сохранить.

ZoneOffset +01:00 — смещение, а ZoneId Europe/Berlin — регион с правилами изменения смещения. Фиксированный offset не содержит будущий переход на летнее время. Для instant правила региона дают один offset; для местных полей приходится выбирать среди допустимых вариантов. Поэтому преобразование instant → zone не имеет той неоднозначности, которую имеет local → zone.

// Фрагмент TimelineDemo.java; early определён в предыдущем шаге
System.out.println("Tokyo same instant="
        + early.withZoneSameInstant(ZoneId.of("Asia/Tokyo"))); // прежний момент, новые поля
System.out.println("Tokyo same local="
        + early.withZoneSameLocal(ZoneId.of("Asia/Tokyo"))); // прежние поля, другой момент
OffsetDateTime a = OffsetDateTime.parse("2024-10-27T02:30+02:00");
OffsetDateTime b = OffsetDateTime.parse("2024-10-27T00:30Z");
System.out.println("offset equals=" + a.equals(b) + ", isEqual=" + a.isEqual(b)
        + ", compareTo=" + a.compareTo(b));
Tokyo same instant=2024-10-27T09:30+09:00[Asia/Tokyo]
Tokyo same local=2024-10-27T02:30+09:00[Asia/Tokyo]
offset equals=false, isEqual=true, compareTo=1

SameInstant подходит для показа события пользователю в другом поясе. SameLocal означает переназначение местных полей в другом регионе и может дополнительно разрешить gap/overlap по его правилам. Выбор между ними — изменение смысла, которое нельзя заменить форматтером.

Equals у OffsetDateTime сравнивает представление: local fields и offset. IsEqual сравнивает только instant. Natural compareTo сначала сравнивает моменты, затем местные поля, поэтому у двух представлений одного instant здесь возвращает 1. Если ключ или сортировка должны отражать только временную линию, используй Instant; одинаковый timestamp сам по себе ещё не идентификатор события.

Gap и overlap требуют явной политики разрешения

31 марта 2024 в Berlin после 01:59:59 наступило 03:00. Местного 02:30 в этот день нет: getValidOffsets вернёт пустой список. AtZone не бросает ошибку, а сдвигает поля на длину gap, здесь на один час: получится 03:30+02:00. Это предсказуемая политика API, но она может нарушить обещание «встреча ровно в выбранное время».

// Фрагмент ResolutionDemo.java; java examples/date-time/ResolutionDemo.java
ZoneId berlin = ZoneId.of("Europe/Berlin");
LocalDateTime gap = LocalDateTime.parse("2024-03-31T02:30");
System.out.println("gap offsets=" + berlin.getRules().getValidOffsets(gap));
System.out.println("transition=" + berlin.getRules().getTransition(gap));
System.out.println("atZone gap=" + gap.atZone(berlin));
try { ZonedDateTime.ofStrict(gap, ZoneOffset.ofHours(1), berlin); }
catch (DateTimeException expected) { System.out.println("strict gap rejected"); }
gap offsets=[]
transition=Transition[Gap at 2024-03-31T02:00+01:00 to +02:00]
atZone gap=2024-03-31T03:30+02:00[Europe/Berlin]
strict gap rejected

Для формы встречи можно отклонять и gap, и overlap, предлагая другой час или явный offset. В обычном случае список содержит один offset; при overlap — два. OfStrict проверяет переданный offset по правилам региона: он принимает любой из двух допустимых вариантов overlap, но не пропускает несуществующее время или произвольное +03:00.

// Фрагмент ResolutionDemo.java; политика: принять только однозначный ввод
static ZonedDateTime requireUnique(LocalDateTime local, ZoneId zone) {
    List<ZoneOffset> offsets = zone.getRules().getValidOffsets(local);
    if (offsets.size() != 1) throw new IllegalArgumentException("choose a valid unique moment");
    return ZonedDateTime.ofStrict(local, offsets.getFirst(), zone);
}
for (String text : List.of("2024-03-31T02:30", "2024-10-27T02:30", "2024-10-27T04:30")) {
    try { System.out.println("unique=" + requireUnique(LocalDateTime.parse(text), berlin)); }
    catch (IllegalArgumentException expected) { System.out.println("unique rejected=" + text); }
}
LocalDateTime overlap = LocalDateTime.parse("2024-10-27T02:30");
System.out.println("strict chosen=" + ZonedDateTime.ofStrict(overlap, ZoneOffset.ofHours(1), berlin));
try { ZonedDateTime.ofStrict(overlap, ZoneOffset.ofHours(3), berlin); }
catch (DateTimeException expected) { System.out.println("wrong offset rejected"); }
unique rejected=2024-03-31T02:30
unique rejected=2024-10-27T02:30
unique=2024-10-27T04:30+01:00[Europe/Berlin]
strict chosen=2024-10-27T02:30+01:00[Europe/Berlin]
wrong offset rejected

Политика зависит от продукта: напоминание можно перенести, а для записи на определённый рейс требуется уточнение. Не зашивай предположение «переход всегда час»: правила содержат длительность конкретного gap и исторические изменения. Для диагностики сохраняй local, region, выбранный offset, instant и версию TZDB — тогда расхождение сервисов можно воспроизвести.

Под капотом: один offset, сдвиг gap или выбор overlap

В OpenJDK 21 метод ZonedDateTime.ofLocal запрашивает ZoneRules.getValidOffsets. Один элемент используется прямо; при пустом списке берётся getTransition, к полям добавляется его duration и выбирается offsetAfter. При overlap сохраняется допустимый preferredOffset, иначе берётся первый. Date-based изменения уже существующего ZonedDateTime вызывают resolveLocal с прежним offset как предпочтением. Поэтому правило «в overlap всегда ранний» верно для нашего atZone без предпочтения, но слишком грубо для всех методов изменения.

Следующий календарный день и следующие 24 часа — разные операции

Напоминание «завтра в полдень» изменяет календарную дату, затем заново применяет правила региона. Period хранит годы, месяцы и дни и выражает такую операцию. Таймер «через 24 часа» двигается по временной линии: Duration хранит seconds/nanos, а ofDays(1) означает ровно 86400 секунд. В день перехода местные часы покажут другое время.

У ZonedDateTime plusDays работает по local timeline, plusHours — по instant timeline. Если новый календарный час попал в gap или overlap, правила разрешения применяются снова. В нашем опыте берём полдень, чтобы отдельно увидеть длину дня, без дополнительной неоднозначности выбранного часа.

// Фрагмент CalendarDemo.java; java examples/date-time/CalendarDemo.java
ZoneId berlin = ZoneId.of("Europe/Berlin");
for (LocalDate date : new LocalDate[]{LocalDate.of(2024, 3, 30), LocalDate.of(2024, 10, 26)}) {
    ZonedDateTime start = date.atTime(12, 0).atZone(berlin);
    ZonedDateTime calendar = start.plus(Period.ofDays(1)); // местный полдень завтра
    ZonedDateTime elapsed = start.plus(Duration.ofDays(1)); // 24 elapsed hours
    System.out.println("start=" + start);
    System.out.println("period=" + calendar + ", elapsed hours=" + Duration.between(start, calendar).toHours());
    System.out.println("duration=" + elapsed + ", elapsed hours=" + Duration.between(start, elapsed).toHours());
}
start=2024-03-30T12:00+01:00[Europe/Berlin]
period=2024-03-31T12:00+02:00[Europe/Berlin], elapsed hours=23
duration=2024-03-31T13:00+02:00[Europe/Berlin], elapsed hours=24
start=2024-10-26T12:00+02:00[Europe/Berlin]
period=2024-10-27T12:00+01:00[Europe/Berlin], elapsed hours=25
duration=2024-10-27T11:00+01:00[Europe/Berlin], elapsed hours=24

Месяц нельзя заменить фиксированным количеством секунд. PlusMonths при невозможном дне берёт последний допустимый день целевого месяца. Поэтому последовательное прибавление месяца к результату 31 января дрейфует: после февраля получается 29 марта. Если контракт — исходное число месяца или всегда конец месяца, вычисляй очередную дату от исходного якоря либо применяй соответствующий TemporalAdjuster.

// Фрагмент CalendarDemo.java; якорь сохраняет правило повторения
LocalDate anchor = LocalDate.of(2024, 1, 31);
LocalDate feb = anchor.plusMonths(1);
System.out.println("month once=" + feb + ", chained=" + feb.plusMonths(1)
        + ", anchored=" + anchor.plusMonths(2));
System.out.println("month end=" + feb.plusMonths(1).with(TemporalAdjusters.lastDayOfMonth()));
LocalDate begin = LocalDate.of(2024, 1, 1), end = LocalDate.of(2024, 3, 3);
System.out.println("period=" + Period.between(begin, end) + ", day component="
        + Period.between(begin, end).getDays() + ", total days=" + ChronoUnit.DAYS.between(begin, end));
month once=2024-02-29, chained=2024-03-29, anchored=2024-03-31
month end=2024-03-31
period=P2M2D, day component=2, total days=62

GetDays у Period возвращает компонент после лет и месяцев, а не общую длину. Для числа календарных дней между LocalDate подходит ChronoUnit.DAYS.between. Duration.between двух LocalDateTime считает разность их полей без знания DST; физическую длительность между событиями вычисляй по Instant или разрешённым ZonedDateTime. Ни Period, ни TemporalAdjusters сами не знают праздничные и рабочие дни компании.

Форматтер проверяет поля по выбранному режиму, но не придумывает смысл

Parsing состоит из двух этапов: извлечь поля из текста по шаблону, затем разрешить их в дату или время. DateTimeFormatter.ofPattern по умолчанию использует SMART: допустимые по диапазону поля могут быть скорректированы до существующей даты. Для строгого контрактного ввода используй STRICT и проверяй результат, а не только совпадение текста с маской.

// Фрагмент FormattingDemo.java; java examples/date-time/FormattingDemo.java
DateTimeFormatter smart = DateTimeFormatter.ofPattern("uuuu-MM-dd", Locale.ROOT);
DateTimeFormatter strict = smart.withResolverStyle(ResolverStyle.STRICT);
DateTimeFormatter lenient = smart.withResolverStyle(ResolverStyle.LENIENT);
System.out.println("smart=" + LocalDate.parse("2023-02-29", smart));
System.out.println("lenient=" + LocalDate.parse("2023-02-29", lenient));
try { LocalDate.parse("2023-02-29", strict); }
catch (DateTimeParseException expected) { System.out.println("strict invalid date rejected"); }
System.out.println("strict leap=" + LocalDate.parse("2024-02-29", strict));
try { LocalDate.parse("2024-02-29", DateTimeFormatter.ofPattern("yyyy-MM-dd", Locale.ROOT)
        .withResolverStyle(ResolverStyle.STRICT)); }
catch (DateTimeParseException expected) { System.out.println("strict year-of-era without era rejected"); }
smart=2023-02-28
lenient=2023-03-01
strict invalid date rejected
strict leap=2024-02-29
strict year-of-era without era rejected

Uuuu обозначает proleptic year, yyyy — year-of-era. В строгом разборе последнему без era не хватает данных, чтобы собрать LocalDate. YYYY — ещё другое поле: год недели. Он зависит от правил недель locale и около Нового года может отличаться от календарного года; сочетание YYYY-MM-dd способно напечатать убедительную, но неверную календарную дату.

// Фрагмент FormattingDemo.java; locale задан, чтобы вывод был воспроизводим
LocalDate lastDay = LocalDate.of(2021, 12, 31);
System.out.println("calendar year=" + lastDay.format(DateTimeFormatter.ofPattern("uuuu-MM-dd", Locale.US)));
System.out.println("US week year=" + lastDay.format(DateTimeFormatter.ofPattern("YYYY-MM-dd", Locale.US)));
System.out.println("UK week year=" + lastDay.format(DateTimeFormatter.ofPattern("YYYY-MM-dd", Locale.UK)));
String text = "2024-10-27T02:30:00+02:00";
System.out.println("protocol instant=" + OffsetDateTime.parse(text).toInstant()); // offset есть в данных
try { Instant.parse("2024-10-27T02:30:00"); }
catch (DateTimeParseException expected) { System.out.println("instant without offset rejected"); }

US week year=2022-12-31
UK week year=2021-12-31

Для протокола выбирай согласованный ISO-формат и тип: дата без времени, определённый момент с Z/offset или local плюс отдельный region и политика. Строка без offset не становится UTC из-за букв T и двоеточий. Для интерфейса человека locale задаёт язык месяцев и правила вывода; для протокола фиксируй его явно, если используешь собственный шаблон.

DateTimeFormatter immutable и thread-safe, поэтому готовый экземпляр можно хранить в static final и использовать в разных потоках. SimpleDateFormat имеет изменяемое внутреннее состояние и требует другой организации доступа. Thread safety не выбирает правильный pattern, ResolverStyle или часовой пояс: эти ошибки остаются смысловыми.

Текущее время должно быть зависимостью проверяемого правила

Если напоминание истекает при now ≥ deadline, тест непосредственно на границе должен воспроизводить равенство. Instant.now внутри метода мешает управлять входом, а sleep делает тест медленным и нестабильным. Clock передаёт источник текущего момента и зону для календарных представлений; Clock.fixed позволяет точно проверить момент до границы и саму границу.

// Фрагмент ClockDemo.java; java examples/date-time/ClockDemo.java
static boolean expired(Instant deadline, Clock clock) {
    return !clock.instant().isBefore(deadline); // равенство уже означает expired
}
Instant deadline = Instant.parse("2024-10-27T00:30:00Z");
Clock justBefore = Clock.fixed(deadline.minusNanos(1), ZoneOffset.UTC);
Clock atDeadline = Clock.fixed(deadline, ZoneOffset.UTC);
System.out.println("before expired=" + expired(deadline, justBefore));
System.out.println("at expired=" + expired(deadline, atDeadline));
Clock tokyo = atDeadline.withZone(ZoneId.of("Asia/Tokyo"));
System.out.println("clock same instant=" + atDeadline.instant().equals(tokyo.instant()));
System.out.println("UTC fields=" + LocalDateTime.now(atDeadline) + ", Tokyo fields=" + LocalDateTime.now(tokyo));
before expired=false
at expired=true
clock same instant=true
UTC fields=2024-10-27T00:30, Tokyo fields=2024-10-27T09:30

WithZone у fixed clock меняет календарный вид, сохраняя момент. Используй явную zone для бизнес-дня и systemUTC clock для глобальных timestamps; не позволяй default zone контейнера выбирать смысл сделки. Если правило требует один снимок now, прочитай clock.instant один раз и передай значение дальше: два последовательных чтения реальных часов могут пересечь границу дня или deadline.

Наносекундная часть Instant задаёт точность представления, а не разрешение и точность реального источника времени. Системные wall clocks корректируются; разность Instant.now не является надёжным таймером длительности кода. Для elapsed time внутри одной JVM используй разность System.nanoTime. Его произвольная точка отсчёта не годится для timestamp, хранения в БД или сравнения двух процессов; даже единица ns не обещает изменение показаний каждую наносекунду.

Fixed clock здесь проверяет правило истечения, а не реализацию планировщика. Тесты очереди задач, повторных попыток и конкурентных действий требуют отдельного управления исполнением; эти подходы находятся в Testing. Замена часов не заставляет сторонний scheduler автоматически исполнять задачи при продвижении времени.

На границах сохраняй смысл времени, единицы и допустимую точность

Случившийся платёж хранится как определённый instant; оригинальный region/offset можно сохранять дополнительно для аудита. Будущая договорённость «каждый понедельник в 09:00 Berlin» должна сохранить местное правило и ZoneId. Offset, рассчитанный сегодня, не заменяет регион для следующих дат. Если власти изменят правила зоны, нужно решить, сохраняется ли местный час или ранее вычисленный instant, и пересчитать будущие исполнения по этому контракту.

Обновление JDK меняет встроенную TZDB. При расхождении времени проверь версию правил, region ID, исходные поля и выбранный offset; сравни instant, а не только строку в логе. Для каждого преобразования заранее назови, что сохраняется. Java.time не обеспечивает синхронизацию часов разных серверов и не доказывает причинный порядок событий лишь сортировкой timestamps.

Запрос «все встречи за 31 марта по Berlin» задаёт локальный календарный день. Получи начало дня и начало следующего по тому же региону, затем преобразуй обе границы в instants. Используй полуоткрытый диапазон [from, until): он не зависит от точности столбца и не требует выдумывать последнюю наносекунду дня. AtStartOfDay(zone) выбирает самое раннее допустимое время дня; в отдельных правилах оно не обязано быть 00:00.

// Фрагмент CalendarDemo.java; две календарные границы, а не start + 24h
LocalDate day = LocalDate.of(2024, 3, 31);
Instant from = day.atStartOfDay(berlin).toInstant();
Instant until = day.plusDays(1).atStartOfDay(berlin).toInstant();
System.out.println("day interval=[" + from + ", " + until + "), hours="
        + Duration.between(from, until).toHours());
day interval=[2024-03-30T23:00:00Z, 2024-03-31T22:00:00Z), hours=23

На внешней границе тип тоже может потерять данные. Java.util.Date представляет instant с точностью миллисекунд и изменяемым состоянием, а не только дату; Date.from(...).toInstant() не сохраняет лишние nanos. Числовой epoch без единиц опасен: секунды и миллисекунды различаются в тысячу раз, но обе величины помещаются в long и могут успешно построить совсем другую дату.

// Фрагмент ClockDemo.java; deadline задан выше
Instant precise = Instant.parse("2024-10-27T00:30:00.123456789Z");
Instant restored = Date.from(precise).toInstant();
System.out.println("legacy=" + restored + ", nanos lost=" + Duration.between(restored, precise).toNanos());
long millis = deadline.toEpochMilli();
System.out.println("epoch millis=" + millis + ", correct=" + Instant.ofEpochMilli(millis));
System.out.println("wrong seconds=" + Instant.ofEpochSecond(millis)); // ошибка единиц, не исключение
legacy=2024-10-27T00:30:00.123Z, nanos lost=456789
epoch millis=1729989000000, correct=2024-10-27T00:30:00Z
wrong seconds=+56791-03-03T20:00:00Z

Не делай вывод о JDBC-столбце по одному имени Timestamp: сохранение instant, local fields и zone зависит от типа столбца, драйвера и настроек. Это разбирается в JDBC & Connection Pools; JSON-формат и round trip — в Serialization Formats. После записи и чтения проверяй смысл и поддерживаемую точность. Нельзя требовать equality наносекундного значения, если согласованная граница хранит только миллисекунды.

Что восстановить из памяти

  • LocalDateTime — поля без пояса. Instant — момент; связь требует допустимого offset.
  • Region ZoneId содержит правила. Gap даёт ноль offsets, overlap — два; политика разрешения должна быть явной.
  • Period меняет календарь, Duration двигает временную линию. Один местный день не всегда 24 часа.
  • Строгий ввод требует правильных полей шаблона и STRICT; thread-safe formatter не исправляет смысл.
  • Clock делает now управляемым входом. На границах сохраняй единицы, точность и исходное намерение.

На собеседовании

Чем отличаются Instant, LocalDateTime, OffsetDateTime и ZonedDateTime?

Instant — определённый момент на временной линии, его я использую для событий и deadline. LocalDateTime — дата и время без пояса; это местные поля, которые ещё не определяют момент. Для встречи я должен знать регион и разрешить его правила. В осеннем Berlin одно 02:30 соответствует двум instants.

OffsetDateTime добавляет фиксированный offset; ZonedDateTime хранит ещё и регион с правилами изменения offset. Для показа события в другом поясе я сохраняю instant и меняю представление. Для дня рождения нужен LocalDate, без придуманного часа и UTC-конверсии.

  • WithZoneSameLocal переназначает поля и меняет момент; withZoneSameInstant сохраняет его.
  • Equals у OffsetDateTime сравнивает представление, isEqual — instant. CompareTo различает представления одного момента.
  • Будущее локальное расписание должно сохранить local rule и ZoneId: только instant не сохраняет намерение при изменении TZDB.

Что произойдёт с несуществующим или повторяющимся временем в часовом поясе?

Правила региона дают для местного времени один offset в обычном случае, ноль в gap и два в overlap. AtZone для gap сдвигает время вперёд на длину перехода, а для overlap без предпочтения выбирает ранний offset. Поэтому вызов может успешно построить другое местное время, чем ввёл пользователь.

Я выбираю политику продукта: разрешать сдвиг, требовать offset или отклонять неоднозначный ввод. GetValidOffsets позволяет увидеть варианты, ofStrict проверяет выбранный offset по правилам региона. Offset +01:00 сам по себе не хранит будущие изменения Europe/Berlin.

  • При изменении существующего ZonedDateTime допустимый прежний offset сохраняется как предпочтение; не все методы всегда выбирают ранний.
  • Длительность перехода берут из ZoneRules, а не фиксируют час. Версия TZDB входит в воспроизводимую диагностику.
  • Интервал локального дня строят из двух atStartOfDay границ: длина может быть 23/25 часов, начало не всегда полночь.

Чем Duration отличается от Period и почему plusDays(1) не равен plusHours(24)?

Duration хранит seconds и nanos, Period — годы, месяцы и дни. Для таймера на 24 часа я беру Duration; для «завтра в тот же местный час» — календарный день в регионе. У ZonedDateTime первая операция идёт по instant timeline, вторая меняет местные поля и заново применяет правила зоны.

Через весенний переход Berlin полдень следующего дня наступит через 23 часа, осенью — через 25. Duration.ofDays(1) всегда добавляет 24 часа. Для общего числа календарных дней между LocalDate я беру DAYS.between, потому что getDays у Period возвращает только компонент.

  • PlusMonths обрезает недопустимый день до конца месяца. Последовательные прибавления дрейфуют; нужны якорь или правило конца месяца.
  • Duration.between LocalDateTime не знает DST. Для elapsed time нужны разрешённые моменты.
  • Праздники и рабочие дни требуют доменного календаря; стандартный adjuster не знает эти правила.

Почему парсинг даты может принять неверный день и можно ли разделять formatter между потоками?

DateTimeFormatter immutable и thread-safe, готовый экземпляр можно разделять между потоками. Но ofPattern по умолчанию использует SMART: например, 2023-02-29 он разрешит как 28 февраля. Для строгого входа я задаю STRICT и проверяю ожидаемый тип результата.

Я также выбираю правильные поля: uuuu — год, yyyy — год эры, YYYY — год недели. Для строгой ISO-подобной календарной даты без era подходит uuuu. Locale и зона должны быть явными там, где меняют смысл, а для передачи момента строка должна содержать Z или offset.

  • Parsing сначала извлекает поля, затем разрешает их. STRICT меняет второй этап, а не только маску текста.
  • Week-year зависит от locale: 31 декабря 2021 с YYYY даёт 2022 в US и 2021 в UK.
  • Границы now проверяют через Clock.fixed без sleep; nanos в типе не обещают такое разрешение системных часов.
  • Legacy Date теряет sub-millisecond precision; единицы epoch и точность хранилища проверяют round trip.
