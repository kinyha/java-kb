Locks

Блокировка строки — способ сказать «я принимаю решение по этим данным, не меняйте их, пока я не закончу». SELECT ... FOR UPDATE блокирует строки до конца транзакции, и конкурент ждёт; NOWAIT и SKIP LOCKED позволяют не ждать. Оптимистичная блокировка не держит ничего, а проверяет версию при записи и требует повтора при конфликте. Две транзакции, захватывающие строки в разном порядке, попадают во взаимоблокировку, и PostgreSQL через секунду убивает одну. Блокировки таблиц берут DDL-команды, и ожидающий ALTER TABLE останавливает за собой даже обычные SELECT.

Переводы между счетами иногда падают с deadlock, а миграция на минуту остановила весь сервис

Сервис переводов блокирует оба счёта и меняет балансы. Под нагрузкой часть переводов падает с deadlock detected, хотя код «правильный». В другой день разработчик запустил миграцию, добавляющую колонку — операция мгновенная, — и на минуту все запросы к таблице счетов встали: миграция ждала долгий отчёт, а остальные ждали миграцию.

Тема разбирает блокировки PostgreSQL: строк и таблиц, пессимистичные и оптимистичные, взаимоблокировки и очередь ожидания. Аномалии, от которых блокировки защищают, — в ACID & Isolation, почему читатели не блокируют писателей — в MVCC, @Version и блокировки в JPA — в Locking & Caching. Демо LocksDemo.java работает с PostgreSQL 17 в Docker, несколькими соединениями JDBC.

FOR UPDATE блокирует строку до конца транзакции, и конкурент ждёт

a: select balance from account where id = 'acc-1' for update;   // A заблокировала строку.
b: select balance from account where id = 'acc-1' for update;   // B ждёт.
a: update account set balance = balance - 30 ...; commit;       // B получает строку.
== waiting: Lock/transactionid — select balance from account where id = 'acc-1' for update
== B got the row after 318 ms, balance 70

B ждала, пока A не закоммитит, и получила уже новое значение 70: блокировка превратила «прочитать, проверить, записать» в последовательные операции. pg_stat_activity показывает ожидание типа Lock/transactionid: в PostgreSQL блокировка строки записывается в саму строку, а ждут завершения транзакции, которая её держит. Блокировки строк держатся до конца транзакции — коммита или отката, — поэтому транзакция с блокировками должна быть короткой и не ходить в сеть: вызов банка внутри неё держит строку всё время ответа банка.

РежимКто берётЧто блокирует
FOR UPDATEЯвно; DELETE, UPDATE ключевых колонокЛюбые изменения и все остальные блокировки строки
FOR NO KEY UPDATEОбычный UPDATE неключевых колонокИзменения, но не FOR KEY SHARE
FOR SHAREЯвноИзменения; другие FOR SHARE совместимы
FOR KEY SHAREПроверка внешнего ключа при вставке в дочернюю таблицуУдаление и смену ключа

Четыре режима нужны, чтобы вставка платежа со ссылкой на магазин не ждала, пока кто-то обновляет название магазина: проверка внешнего ключа берёт FOR KEY SHARE, а обычный UPDATE — FOR NO KEY UPDATE, и они совместимы.

NOWAIT, SKIP LOCKED и lock_timeout — когда ждать нельзя

== FOR UPDATE NOWAIT: 55P03 ERROR: could not obtain lock on row in relation "account"

NOWAIT сразу возвращает ошибку 55P03, если строка занята: пользователю лучше сразу ответить «операция уже выполняется», чем держать его запрос. SKIP LOCKED пропускает занятые строки и возвращает свободные — так несколько воркеров разбирают очередь задач в таблице, не мешая друг другу, как ретрансляторы в Transactional Outbox. lock_timeout ограничивает ожидание любой блокировки временем, после которого запрос падает с той же 55P03. Для запросов приложения его ставят чуть меньше таймаута HTTP-запроса, чтобы зависшее ожидание не держало соединение из пула.

Оптимистичная блокировка ничего не держит, а проверяет версию при записи

update account set balance = :new, version = version + 1
where id = 'acc-2' and version = :readVersion;   -- 0 строк: кто-то успел раньше
== optimistic: A updated 1 row, B updated 0 rows (version changed) -> B retries

Обе транзакции прочитали версию 0 без блокировок. A записала и увеличила версию, а UPDATE B с условием version = 0 не нашёл строки: B узнаёт о конфликте по счётчику обновлённых строк и повторяет операцию, перечитав данные. Так работает @Version в JPA. Оптимистичный подход выигрывает, когда конфликты редки и между чтением и записью проходит много времени — например, пользователь редактирует карточку магазина минуту. Пессимистичный — когда конфликты часты: при оптимистичном каждый конфликт стоит повторной работы, а при сотне конкурентов на одну строку повторы съедят всё.

Встречные переводы захватывают строки в разном порядке и попадают во взаимоблокировку

Перевод A со счёта 1 на счёт 2 и встречный перевод B со счёта 2 на счёт 1 начинаются одновременно. Каждый первым делом списывает со своего счёта, блокируя его строку, а потом идёт за второй:

== deadlock detected after 1009 ms: A ok; B 40P01 ERROR: deadlock detected

PostgreSQL не ищет взаимоблокировки постоянно: проверка запускается, если ожидание длится дольше deadlock_timeout, поэтому до ошибки прошла секунда. Транзакция-жертва откатывается целиком, и её нужно повторить. Предотвращают взаимоблокировки единым порядком захвата: перевод блокирует счета в порядке возрастания id — select ... where id in (:from, :to) order by id for update — независимо от направления. Тогда второй перевод будет ждать первый, но цикла не возникнет. Короткие транзакции и повтор при 40P01 закрывают остальное.

Ожидающий ALTER TABLE ставит в очередь за собой все запросы к таблице

Любой запрос к таблице берёт на неё лёгкую блокировку: SELECT — ACCESS SHARE, UPDATE — ROW EXCLUSIVE. Они совместимы друг с другом. Но большинство ALTER TABLE требуют ACCESS EXCLUSIVE, несовместимую ни с чем. Демо держит открытой транзакцию отчёта, запускает добавление колонки и затем обычный SELECT:

   waiting: alter table account add column note text (relation)
   waiting: select balance from account where id = 'acc-1' (relation)
== plain SELECT behind waiting ALTER: 57014 after 1001 ms
   report finished -> ALTER done
== ALTER with lock_timeout 200ms: 55P03 after 211 ms, others not blocked

ALTER ждёт, пока отчёт отпустит ACCESS SHARE. А SELECT, пришедший после ALTER, встаёт в очередь за ним: его блокировка совместима с отчётом, но не с ожидающим ALTER, и PostgreSQL не пропускает его вперёд, чтобы ALTER не ждал вечно. Сама операция добавления колонки мгновенна, но пока долгий отчёт не закончится, таблица недоступна для всех — SELECT упал по statement_timeout через секунду. Так миграция и остановила сервис.

Защита — lock_timeout для DDL: если блокировку не удалось получить за 200 мс, ALTER падает, очередь рассасывается, а миграцию повторяют позже. Миграционные инструменты делают это обёрткой с повторами. Как менять схему без простоя, разобрано в Schema Migrations.

ALTER TABLE ADD COLUMN без значения по умолчанию мгновенный, поэтому его можно запускать под нагрузкой без подготовки.

Мгновенно само изменение, но ему нужна ACCESS EXCLUSIVE, и пока он её ждёт, все новые запросы к таблице стоят за ним. Один долгий запрос превращает мгновенную миграцию в остановку таблицы. DDL запускают с lock_timeout и повторами.

  • FOR UPDATE держит строку до конца транзакции: B ждала 318 мс и получила новое значение. Внутри транзакции с блокировками — никаких сетевых вызовов.
  • NOWAIT — сразу 55P03, SKIP LOCKED — свободные строки, lock_timeout — предел ожидания.
  • Оптимистичная версия: 0 обновлённых строк сигналит о конфликте и требует повтора.
  • Встречные переводы дали 40P01 через deadlock_timeout; лечат единым порядком захвата и повтором.
  • Ожидающий ALTER TABLE блокирует все запросы за собой; DDL — с lock_timeout.

На собеседовании

Оптимистичная или пессимистичная блокировка: что и когда?

Пессимистичная — SELECT ... FOR UPDATE: строка блокируется на время транзакции, конкуренты ждут. Подходит при частых конфликтах и коротких транзакциях. Оптимистичная — колонка версии и UPDATE ... WHERE version = :v: ничего не держится, конфликт обнаруживается по нулю обновлённых строк, операцию повторяют. Подходит при редких конфликтах и долгом времени между чтением и записью.

  • При частых конфликтах оптимистичный подход тратит ресурсы на повторы.
  • Пессимистичная блокировка держит строку и соединение; сетевые вызовы внутри неё продлевают ожидание всех.
  • NOWAIT и SKIP LOCKED меняют ожидание на ошибку или пропуск.

Как возникает deadlock в базе и как его избежать?

Две транзакции захватывают одни и те же строки в разном порядке: A держит первую и ждёт вторую, B держит вторую и ждёт первую. PostgreSQL через deadlock_timeout (1 с) находит цикл и отменяет одну транзакцию с 40P01. Избегают единым порядком захвата — например, по возрастанию id, — короткими транзакциями и повтором при 40P01.

  • Порядок обновления строк в одном UPDATE не определён; для нескольких строк блокируют явно с ORDER BY.
  • Взаимоблокировки бывают и между блокировками строк и внешних ключей, и при DDL.
Почему этот перевод иногда падает с deadlock? 
@Transactional
public void transfer(String from, String to, long amount) {
    Account a = accounts.findByIdForUpdate(from);
    Account b = accounts.findByIdForUpdate(to);
    a.debit(amount);
    b.credit(amount);
}

Строки блокируются в порядке «откуда, куда», а встречный перевод блокирует их в обратном порядке: каждая транзакция держит свой счёт и ждёт чужой. Нужно блокировать оба счёта в едином порядке — по возрастанию id, одним запросом с ORDER BY id FOR UPDATE — и повторять транзакцию при 40P01.

Почему миграция может остановить все запросы к таблице?

Большинство ALTER TABLE берут ACCESS EXCLUSIVE, несовместимую ни с какими запросами. Если таблицу читает долгий запрос, ALTER ждёт его, а все новые запросы встают в очередь за ALTER. Даже мгновенная операция блокирует таблицу на время самого долгого запроса. Защита — lock_timeout для DDL и повторы.

  • CREATE INDEX CONCURRENTLY не блокирует запись, но работает дольше и не в транзакции.
  • Долгие транзакции и idle in transaction опасны и для миграций, и для VACUUM.
