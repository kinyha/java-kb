Schema Migrations

Миграции — версионированные скрипты изменения схемы, которые Flyway или Liquibase применяют по порядку и записывают в таблицу истории. Без простоя их делают по схеме «расширить — сократить»: сначала добавить новое так, чтобы работали и старая, и новая версия приложения, затем переключить код, и только потом удалить старое. Опасны не сами изменения, а блокировки: некоторые ALTER переписывают таблицу под эксклюзивной блокировкой, обычный CREATE INDEX останавливает запись. У большинства есть безопасные варианты: CREATE INDEX CONCURRENTLY, ограничения с NOT VALID и отдельной проверкой, lock_timeout с повтором.

Добавление колонки остановило платежи на секунду, а переименование сломало старые поды

Миграция добавила в таблицу платежей колонку created_at со значением по умолчанию clock_timestamp(). На проде с сотнями миллионов строк это заняло минуты, и всё это время ни один платёж не записался. В другой раз колонку amount переименовали в amount_minor: миграция прошла мгновенно, но поды старой версии, которые ещё не обновились при выкатке, начали падать на каждом запросе.

Тема разбирает, как устроены инструменты миграций, как менять схему без простоя при выкатке и какие команды PostgreSQL берут опасные блокировки. Очередь блокировок за ожидающим ALTER и lock_timeout — в Locks, выкатка нескольких версий приложения — в Deployment Strategies. Демо MigrationDemo.java выполняет каждое изменение на таблице из трёх миллионов платежей в PostgreSQL 17, а в соседнем соединении всё это время вставляет платежи и меряет самое долгое ожидание вставки.

Flyway и Liquibase применяют скрипты по порядку и помнят, что уже применено

db/migration/
  V1__create_payment.sql
  V2__add_currency.sql
  V3__index_payment_merchant.sql

Flyway при старте приложения или в отдельном шаге выкатки сравнивает файлы в каталоге с таблицей flyway_schema_history и применяет недостающие по номеру версии. Для каждого применённого скрипта хранится контрольная сумма: изменить уже применённый файл нельзя, Flyway откажется стартовать. Ошибку исправляют новой миграцией. Liquibase делает то же через changelog с наборами изменений и умеет описывать их в XML или YAML независимо от базы.

В PostgreSQL DDL транзакционный, и Flyway выполняет каждую миграцию в транзакции: упавшая миграция откатывается целиком. Исключение — команды, которые нельзя выполнять в транзакции, как CREATE INDEX CONCURRENTLY: такую миграцию помечают как нетранзакционную (executeInTransaction=false в Flyway, runInTransaction="false" в Liquibase) и держат в ней одну команду. Если в кластере несколько подов, миграции запускает один — отдельным Job перед выкаткой или с блокировкой, которую инструменты берут в базе сами.

Опасна не операция, а блокировка, которую она держит

== add column, constant default:    DDL     2 ms, worst concurrent insert     2 ms
== add column, volatile default:    DDL  1034 ms, worst concurrent insert  1018 ms
== create index:                    DDL   408 ms, worst concurrent insert   401 ms
== create index concurrently:       DDL   616 ms, worst concurrent insert     7 ms
== set not null (full scan):        DDL    90 ms, worst concurrent insert    88 ms
== add check not valid:             DDL     2 ms, worst concurrent insert     2 ms
== validate constraint:             DDL    92 ms, worst concurrent insert     5 ms
== set not null (uses valid check): DDL     1 ms, worst concurrent insert     2 ms

Колонка с константным умолчанием добавилась за 2 мс: с PostgreSQL 11 значение хранится в каталоге, и строки не переписываются. С clock_timestamp() значение своё у каждой строки, и база переписала всю таблицу под ACCESS EXCLUSIVE: вставка ждала целую секунду на трёх миллионах строк, на сотнях миллионов — минуты. Безопасно добавить колонку без умолчания или с константой и заполнить её пачками отдельно.

Обычный CREATE INDEX держит блокировку, запрещающую запись, всё время построения: 400 мс здесь, часы на большой таблице. CONCURRENTLY строит индекс в несколько проходов, не мешая записи, — дольше по времени, но вставка ждала 7 мс. Если такое построение упадёт, остаётся невалидный индекс, который нужно удалить и создать заново. SET NOT NULL проверяет всю таблицу под эксклюзивной блокировкой. Обходной путь — CHECK (amount is not null) NOT VALID, который проверяет только новые строки, затем VALIDATE CONSTRAINT с лёгкой блокировкой, не мешающей записи, и после этого SET NOT NULL мгновенный: PostgreSQL видит действующий CHECK и не сканирует таблицу. Так же через NOT VALID добавляют внешние ключи.

Даже мгновенным командам нужна эксклюзивная блокировка, и они ждут долгие запросы, выстраивая за собой очередь — эффект, разобранный в Locks. Поэтому каждую миграцию запускают с SET lock_timeout = '2s' и повторяют при неудаче.

Переименование без простоя — четыре выкатки, а не одна миграция

Во время выкатки старая и новая версии приложения работают одновременно, и схема должна подходить обеим. Переименование колонки ломает старую версию мгновенно. Поэтому его делают по схеме «расширить — сократить»:

Каждый шаг совместим с соседними версиями приложения, и любой можно откатить, кроме последнего. Тот же принцип для любых несовместимых изменений: смена типа колонки, разделение таблицы, новое обязательное поле. Обязательность новой колонки включают в самом конце, через NOT VALID и VALIDATE, когда все версии кода её заполняют. Удаление колонки тоже двухшаговое: сначала код перестаёт её использовать — а JPA-сущность перестаёт её упоминать, — и только потом миграция её удаляет.

Миграция, выполнившаяся за миллисекунды на тестовой базе, безопасна для прода.

Время на тестовой базе ничего не говорит о блокировках на проде. В демо добавление колонки с clock_timestamp() на трёх миллионах строк держало вставку секунду, а на сотнях миллионов — минуты; мгновенная команда может часами стоять в очереди за долгим запросом. Проверяют тип блокировки и переписывание таблицы, а запускают с lock_timeout.

  • Flyway и Liquibase применяют версионированные скрипты по порядку; применённое не меняют, исправляют новой миграцией.
  • Константное умолчание — 2 мс, volatile — переписывание таблицы и секунда ожидания записи.
  • CREATE INDEX блокирует запись (401 мс), CONCURRENTLY — нет (7 мс), но не в транзакции.
  • SET NOT NULL без сканирования: CHECK NOT VALID, VALIDATE, затем SET NOT NULL за 1 мс.
  • Несовместимые изменения — expand-contract в несколько выкаток; каждая миграция с lock_timeout и повтором.

На собеседовании

Как переименовать колонку или изменить схему без простоя?

По схеме expand-contract: добавить новую колонку, писать в обе (триггером или кодом), заполнить старые строки пачками, выкатить код, который читает новую, и только после полной выкатки удалить старую. На каждом шаге схема совместима и со старой, и с новой версией приложения, которые работают одновременно во время выкатки.

  • Заполнение — пачками в коротких транзакциях, чтобы не держать горизонт VACUUM и блокировки.
  • Обязательность включают в конце через CHECK NOT VALID и VALIDATE.
  • Удаление колонки — после того как ни одна версия кода её не упоминает.

Какие DDL-операции опасны на большой таблице PostgreSQL и как их заменить?

ADD COLUMN с volatile-умолчанием и смена типа колонки переписывают таблицу под ACCESS EXCLUSIVE. CREATE INDEX блокирует запись на всё время построения — заменяют на CREATE INDEX CONCURRENTLY. SET NOT NULL, новые CHECK и внешние ключи сканируют таблицу под блокировкой — заменяют на NOT VALID и отдельный VALIDATE. Любая DDL с эксклюзивной блокировкой встаёт в очередь за долгими запросами — запускают с lock_timeout и повтором.

  • ADD COLUMN с константным умолчанием мгновенный с PostgreSQL 11.
  • Упавший CONCURRENTLY оставляет невалидный индекс; его удаляют и строят заново.
  • CONCURRENTLY нельзя в транзакции: в Flyway и Liquibase такую миграцию делают нетранзакционной.
Что опасного в этой миграции для таблицы на 500 млн строк? 
-- V42__payment_improvements.sql
alter table payment add column created_at timestamptz not null default now();
alter table payment alter column amount type numeric(19,2);
create index on payment(created_at);
alter table payment add constraint fk_merchant foreign key (merchant_id) references merchant(id);

now() — стабильная функция, и колонка добавится мгновенно, но смена типа amount переписывает всю таблицу под ACCESS EXCLUSIVE, обычный CREATE INDEX блокирует запись на время построения, а внешний ключ без NOT VALID сканирует таблицу под блокировкой. Всё в одной транзакции — блокировки держатся до конца. Нужно разнести на отдельные миграции: тип менять через новую колонку по expand-contract, индекс — CONCURRENTLY в нетранзакционной миграции, внешний ключ — NOT VALID и VALIDATE; все с lock_timeout.

Как работают Flyway и Liquibase?

Хранят историю применённых миграций в служебной таблице и при запуске применяют недостающие по порядку версий. Flyway работает с SQL-файлами V1__…, V2__… и проверяет контрольные суммы применённых; Liquibase — с changelog и changeSet, может описывать изменения независимо от базы и откатывать их. Изменять уже применённую миграцию нельзя — исправляют новой.

  • Миграции запускает один экземпляр: Job перед выкаткой или встроенная блокировка инструмента.
  • В PostgreSQL миграция идёт в транзакции и откатывается целиком при ошибке.
