ACID & Isolation

Транзакция обещает четыре вещи: всё или ничего, сохранность инвариантов, независимость от параллельных транзакций и сохранность после коммита. Слабее всего на практике изоляция: уровень по умолчанию в PostgreSQL — READ COMMITTED, и на нём «прочитать, посчитать, записать» теряет чужие изменения. REPEATABLE READ в PostgreSQL даёт снимок данных на всю транзакцию и отклоняет конфликтующее обновление ошибкой 40001, но пропускает write skew — когда две транзакции читают одно и то же, а пишут в разные строки. Только SERIALIZABLE ловит и его. Всё, что выше READ COMMITTED, требует повторять транзакцию при ошибке сериализации.

Два списания с одного счёта прошли оба, а правило «один дежурный на смене» нарушили два честных запроса

Сервис счетов списывает деньги так: прочитать баланс, проверить, что хватает, записать новый. Две параллельные операции на 30 и 50 со счёта со 100 оставили на нём 50, а не 20: одно списание потерялось. В соседнем сервисе выплат действует правило: крупную выплату ведёт хотя бы один дежурный. Два дежурных одновременно ушли со смены — каждый проверил, что второй остаётся, — и выплата осталась без ответственного. Обе транзакции в каждом случае были корректны сами по себе.

Это аномалии изоляции, и тема разбирает их на настоящем PostgreSQL 17: что видит транзакция, какие изменения могут потеряться и какой уровень что гарантирует. Блокировки строк и SELECT FOR UPDATE — в Locks, внутреннее устройство снимков — в MVCC, транзакции в Spring — в Transactions. Демо IsolationDemo.java ведёт две транзакции в двух соединениях JDBC строго по шагам.

Consistency в ACID — свойство приложения больше, чем базы: база проверит check (balance >= 0), но правило «хотя бы один дежурный на выплате» она не знает. Изоляция настраивается: полная — дорого, поэтому базы предлагают уровни, каждый из которых допускает определённые аномалии. Стандарт SQL описывает их через три явления — грязное чтение, неповторяемое чтение, фантом, — но в реальности важнее два других: потерянное обновление и write skew.

READ COMMITTED видит чужие коммиты посреди транзакции, REPEATABLE READ — нет

Транзакция A читает баланс, транзакция B меняет его и коммитит, A читает снова. Отчёт A считает сумму счетов, B добавляет новый счёт, A пересчитывает:

== non-repeatable read, READ COMMITTED: A read 100, then 40
== non-repeatable read, REPEATABLE READ: A read 100, then 100
== phantom, READ COMMITTED: report saw 2 accounts / 300, then 3 accounts / 800
== phantom, REPEATABLE READ: report saw 2 accounts / 300, then 2 accounts / 300

На READ COMMITTED каждый запрос видит данные, закоммиченные к его началу. Поэтому в одной транзакции два чтения дали 100 и 40, а отчёт посчитал сначала два счёта, потом три: неповторяемое чтение и фантом. Отчёт, который берёт итог из одного запроса, а детали из другого, на этом уровне может не сойтись сам с собой. На REPEATABLE READ транзакция видит снимок данных на момент первого запроса, и оба чтения согласованы. В PostgreSQL этот уровень — изоляция снимков (snapshot isolation), и фантомов на нём нет, хотя стандарт их допускает. Грязного чтения в PostgreSQL нет вовсе: READ UNCOMMITTED работает как READ COMMITTED.

«Прочитать, посчитать, записать» теряет чужое обновление на READ COMMITTED

long ba = balance(a), bb = balance(b);                                    // Оба прочитали 100.
a.executeUpdate("update account set balance = " + (ba - 30) + " ...");  a.commit();
b.executeUpdate("update account set balance = " + (bb - 50) + " ...");  b.commit();

// Атомарно: база сама читает текущее значение под блокировкой строки.
update account set balance = balance - 50 where id = 'acc-1';
== lost update, READ COMMITTED: B committed; balance 50 (expected 20)
== lost update, REPEATABLE READ: B failed: 40001 ERROR: could not serialize access due to concurrent update; balance 70 (expected 20)
== atomic update balance = balance - x, READ COMMITTED: balance 20

На READ COMMITTED B записал 100 − 50, вычисленное по старому значению, и затёр списание A: итог 50 вместо 20. Это и есть история с двумя списаниями. На REPEATABLE READ PostgreSQL обнаружил, что строку изменила транзакция, закоммиченная после начала снимка B, и отклонил обновление ошибкой 40001. Данные целы — 70 после списания A, — но B должна повторить транзакцию с начала, иначе её списание пропадёт. Атомарное balance = balance - 50 решает задачу без смены уровня: второй UPDATE ждёт блокировку строки, затем перечитывает актуальное значение и вычитает из него. Когда атомарный UPDATE невозможен — проверка сложнее одного выражения, — используют SELECT ... FOR UPDATE или оптимистичную версию, как в Locks.

Write skew проходит через снимок: две транзакции читают одно, а пишут разное

Правило: выплату po-1 ведёт хотя бы один дежурный. Анна и Борис одновременно решают уйти со смены. Каждый проверяет, сколько дежурных, видит двоих и снимает с дежурства себя:

== write skew, REPEATABLE READ: both committed; on duty now 0
== write skew, SERIALIZABLE: B failed: 40001 ERROR: could not serialize access due to read/write dependencies among transactions; on duty now 1

Write skew — это аномалия изоляции снимков: решение принимается по прочитанному, а пишется в другое место. Типичные случаи — двойная бронь, лимит на сумму операций, уникальность, которую нельзя выразить индексом. Защиты три. SERIALIZABLE в PostgreSQL реализован как Serializable Snapshot Isolation: снимки плюс отслеживание зависимостей чтения и записи, без блокировок чтения. Явная блокировка тех строк, на которых строится решение: SELECT ... FOR UPDATE по обоим дежурным. Или превращение правила в ограничение базы, если это возможно: уникальный индекс, exclusion constraint.

Значения по умолчанию у баз разные: READ COMMITTED в PostgreSQL, Oracle и SQL Server, REPEATABLE READ в MySQL InnoDB, причём поведение одноимённых уровней тоже разное. REPEATABLE READ в MySQL читает из снимка, но UPDATE и SELECT ... FOR UPDATE работают с последней версией строки, и потерянное обновление там не отклоняется ошибкой, как в PostgreSQL. Поэтому опираются не на название уровня, а на проверенное поведение конкретной базы.

Уровни выше READ COMMITTED отвечают на конфликт ошибкой, а не ожиданием, и приложение обязано повторить транзакцию целиком: заново прочитать и заново принять решение. Повтор без перечитывания вернёт ту же ошибку или, хуже, запишет старое решение. В Spring это отдельная обёртка с повтором на SQLState 40001 снаружи @Transactional-метода, а не внутри него. Цена SERIALIZABLE — больше откатов под нагрузкой и память на отслеживание чтений; его включают для транзакций, где инварианты зависят от прочитанного, а не на всё приложение.

REPEATABLE READ защищает от всех проблем параллельных транзакций, кроме фантомов.

В PostgreSQL REPEATABLE READ как раз не допускает фантомов, но пропускает write skew: в демо оба дежурных ушли со смены и обе транзакции закоммитились. А потерянное обновление он не предотвращает молча, а отклоняет ошибкой 40001, которую нужно обработать повтором.

  • ACID: атомарность, инварианты, изоляция, долговечность через WAL; Consistency во многом на приложении.
  • READ COMMITTED видит чужие коммиты между запросами: 100, потом 40; 2 счёта, потом 3.
  • Чтение-расчёт-запись на READ COMMITTED потеряло списание (50 вместо 20); атомарный UPDATE дал 20; REPEATABLE READ — ошибка 40001.
  • Write skew проходит REPEATABLE READ (0 дежурных) и ловится SERIALIZABLE; альтернатива — FOR UPDATE или constraint.
  • Умолчания и поведение уровней различаются между базами; ошибки 40001 повторяют всей транзакцией.

На собеседовании

Какие есть уровни изоляции и от каких аномалий они защищают?

READ UNCOMMITTED допускает грязное чтение; READ COMMITTED видит только закоммиченное, но разные запросы транзакции видят разные коммиты — неповторяемое чтение и фантомы. REPEATABLE READ фиксирует прочитанное; SERIALIZABLE гарантирует результат, как при последовательном выполнении. В PostgreSQL по умолчанию READ COMMITTED, REPEATABLE READ — снимок на всю транзакцию без фантомов, SERIALIZABLE — SSI.

  • Стандартные три явления не описывают потерянное обновление и write skew, а именно они ломают бизнес-логику.
  • В PostgreSQL READ UNCOMMITTED работает как READ COMMITTED.
  • Одноимённые уровни в MySQL и PostgreSQL ведут себя по-разному; в MySQL умолчание — REPEATABLE READ.

Что такое lost update и как его избежать?

Две транзакции читают одно значение, каждая вычисляет новое и записывает; вторая запись затирает первую. На READ COMMITTED это происходит молча. Решения: атомарный UPDATE с выражением (balance = balance - x), SELECT ... FOR UPDATE перед расчётом, оптимистичная блокировка по версии или REPEATABLE READ в PostgreSQL, который отклонит вторую запись ошибкой 40001.

  • Ошибку 40001 обрабатывают повтором всей транзакции с перечитыванием.
  • В MySQL REPEATABLE READ потерянное обновление не отклоняет: UPDATE работает с последней версией строки.
Что не так с этим списанием? 
@Transactional
public void charge(String accountId, long amount) {
    Account acc = accounts.findById(accountId).orElseThrow();
    if (acc.getBalance() < amount) throw new InsufficientFunds();
    acc.setBalance(acc.getBalance() - amount);
    accounts.save(acc);
}

На READ COMMITTED по умолчанию два параллельных списания прочитают один баланс, оба пройдут проверку, и второе затрёт первое: деньги спишутся один раз, а операции пройдут обе, или баланс уйдёт в минус. Нужен атомарный update с условием (balance = balance - :x where balance >= :x и проверка числа строк), SELECT FOR UPDATE при загрузке или @Version с повтором при конфликте.

Что такое write skew и почему его пропускает snapshot isolation?

Две транзакции читают одни и те же данные, по ним принимают решения и пишут в разные строки. Конфликта записи нет, поэтому изоляция снимков пропускает обе, и вместе они нарушают инвариант: в демо оба дежурных ушли со смены. Защита — SERIALIZABLE, явная блокировка прочитанных строк через FOR UPDATE или ограничение базы.

  • SERIALIZABLE в PostgreSQL — SSI: отслеживает зависимости чтения и записи и отклоняет одну из транзакций цикла.
  • Если строк, которые надо заблокировать, ещё нет (двойная бронь), конфликт материализуют отдельной таблицей слотов.
