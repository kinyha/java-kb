DDD

Платёж для банка и платёж для бухгалтерии означают разные вещи. DDD помогает договориться о смысле внутри каждой части бизнеса и выразить его в коде. Границу модели задаёт bounded context; внутри него агрегат удерживает связанные правила при изменении состояния. Между границами передают явные команды и факты. Хорошая модель позволяет прочитать метод возврата и понять, почему сервис не вернёт больше принятой суммы.

Один Payment начинает противоречить разным правилам бизнеса

Банк прислал CAPTURED: списание подтверждено. Платёжный сервис поставил status=PAID, а бухгалтерский отчёт тут же показал проведённую операцию. Но проводка ещё не создана. Команды спорят, что означает PAID, и добавляют поля reallyPaid, posted и settled в один общий объект.

Проблема глубже enum. Обработка платежа отвечает за подтверждение банка и возможность возврата. Учёт отвечает за проводки, баланс книги и сверку. Название одно, но состояния и правила разные. Универсальная модель заставляет каждого читателя помнить чужие исключения: «PAID, но для отчёта ещё не оплачен».

Начало DDD — разговор с людьми, которые знают эти правила. Разбери конкретные сценарии: частичный возврат, повтор команды, отмена, неизвестный результат банка. Запиши, кто принимает решение и какое состояние меняется. Из сценариев возникает ubiquitous language, единый язык внутри команды и её модели: «запросить возврат», «провести запись», «сопоставить отчёт». Те же слова появляются в методах, тестах и обсуждениях.

У Хононова сначала идут бизнес-области и язык, затем границы моделей и классы. Subdomain описывает задачу бизнеса, bounded context — границу модели решения. Одна задача может обслуживаться несколькими системами; одна система — охватывать несколько простых задач.

Core subdomain даёт бизнесу преимущество и заслуживает глубокой модели. Generic-задачи часто закрывает готовый продукт; supporting-часть нужна бизнесу, но обычно проще ядра. Приоритет выбирают по правилам и выгоде, а не по числу таблиц.

Контекст сохраняет свой смысл, а context map показывает отношения с соседями

В контексте обработки Payment хранит принятую сумму и допустимые возвраты. В учёте ему соответствует Posting с проводками. Общего Java-класса для них нет: изменение формата отчёта не должно менять решение о возврате. Общий внешний идентификатор позволяет сопоставить записи, сохраняя две самостоятельные модели.

Контекст — граница смысла и ответственности за модель. Он может быть модулем монолита, отдельным приложением или частью большой системы. Один контекст не обязан равняться одной таблице, одному агрегату или одному микросервису. Физическое разделение выбирают после того, как понятны язык, владельцы и взаимодействие.

Context map дополняет границы отношениями. Кто задаёт формат интеграции? Кто может попросить его изменить? Кто приспосабливается к изменениям? Upstream влияет на потребителя, downstream от него зависит. Это направление влияния модели и API; сетевой запрос при этом может идти из downstream в upstream.

Open Host Service задаёт поддерживаемый API, Published Language — формат и смысл сообщений. Их можно сочетать с ACL. В нашем примере он переводит ответ банка в язык обработки: CAPTURED ещё не означает проводку. Общая библиотека всех entity вместо такого перевода связывает релизы контекстов.

Сущность узнают по идентичности, значение — по содержимому

Платёж p-17 остаётся тем же платежом после запроса возврата: состояние меняется, идентичность сохраняется. Это entity. Сумма 1000 RUB не имеет собственного жизненного цикла в нашем расчёте. Два равных значения можно заменить друг другом без изменения смысла. Это value object, объект-значение.

Value object удобен как неизменяемый тип с проверкой при создании. Метод получает Money, а не две независимые переменные, которые можно перепутать или сложить с другой валютой. Но record даёт равенство компонентов и final-поля, а правильную семантику компонентов ты выбираешь сам.

record Money(long minor, String currency) {
    Money {
        if (minor < 0) throw new IllegalArgumentException("negative money");
        currency = Objects.requireNonNull(currency).toUpperCase(Locale.ROOT);
        Currency.getInstance(currency); // Проверяем код; в опытах RUB, суммы в копейках.
    }
    Money plus(Money other) {
        sameCurrency(other); // RUB + USD — ошибка, а не новый Money.
        return new Money(Math.addExact(minor, other.minor), currency); // Защита от переполнения.
    }
    Money minus(Money other) {
        sameCurrency(other);
        return new Money(Math.subtractExact(minor, other.minor), currency);
    }
    void sameCurrency(Money other) {
        if (!currency.equals(other.currency)) throw new IllegalArgumentException("currency mismatch");
    }
}

Полный DddDemo.java содержит четыре режима. Money хранит целое число минимальных единиц валюты: для RUB это копейки. Дробные расчёты требуют явной точности и округления. Нормализация валюты делает 1000 RUB равным 1000 rub.

PaymentId тоже подходит для record: это значение идентификатора. Два объекта Payment с тем же id представляют одну entity, хотя их ссылки и снимки различаются. Для изменяемой entity автоматическое сравнение всех полей record подменяет идентичность содержимым; стратегию equals/hashCode для ORM выбирают отдельно.

Агрегат меняет связанное состояние через корень и сохраняет инвариант

Платёж принял 1000 копеек. Первый запрос возврата резервирует 700. Второй просит 400. Если каждый Refund сохраняется своим сервисом без общей проверки платежа, оба запроса пройдут, и сервис пообещает вернуть 1100. Проверка суммы относится ко всему платежу: её нельзя доверить каждой строке возврата отдельно.

Aggregate объединяет объекты, которые должны сохранять согласованное правило при изменении. Внешний код обращается к aggregate root, корню: payment.requestRefund. Корень проверяет команду и меняет связанные данные. Инвариант нашего примера: резерв под запросы возврата не превышает принятую сумму, а повтор той же команды не резервирует её дважды.

static final class Payment {
    final PaymentId id;
    final Money captured;
    private Money reserved;
    private final LinkedHashMap<String, Refund> refunds = new LinkedHashMap<>();
    private final List<RefundRequested> pending = new ArrayList<>();

    Payment(PaymentId id, Money captured) {
        this.id = Objects.requireNonNull(id); this.captured = Objects.requireNonNull(captured);
        if (captured.minor() == 0) throw new IllegalArgumentException("empty capture");
        reserved = new Money(0, captured.currency());
    }
    boolean requestRefund(String refundId, Money amount) {
        if (refundId == null || refundId.isBlank()) throw new IllegalArgumentException("empty refund id");
        Objects.requireNonNull(amount);
        captured.sameCurrency(amount);
        if (amount.minor() == 0) throw new IllegalArgumentException("empty refund");
        var previous = refunds.get(refundId);
        if (previous != null) {
            if (!previous.amount.equals(amount)) throw new IllegalStateException("refund id reused");
            return false; // Тот же id с тем же смыслом — уже принятая команда.
        }
        var next = reserved.plus(amount);
        if (next.minor() > captured.minor()) throw new IllegalStateException("refund exceeds capture");
        // Проверки прошли до изменения полей; частично принятого запроса нет.
        refunds.put(refundId, new Refund(refundId, amount));
        reserved = next;
        pending.add(new RefundRequested(id, refundId, amount));
        return true;
    }
    Money available() { return captured.minus(reserved); }
    List<Refund> refunds() { return List.copyOf(refunds.values()); }
}

var p = new Payment(new PaymentId("p-17"), new Money(1_000, "RUB"));

System.out.println("duplicate accepted=" + p.requestRefund("r-1", new Money(700, "RUB")));
try { p.requestRefund("r-2", new Money(400, "RUB")); }
catch (IllegalStateException e) { System.out.println("second request=" + e.getMessage()); }
try { p.refunds().clear(); } // Внешний код не получает изменяемую коллекцию корня.
catch (UnsupportedOperationException e) { System.out.println("collection change=" + e.getClass().getSimpleName()); }
System.out.println("reserved=" + p.reserved.minor() + ", available=" + p.available().minor()
    + ", refunds=" + p.refunds.size() + ", pending events=" + p.pending.size());

Отказ не оставил второго Refund или события. В демо Refund неизменяем; для изменяемых дочерних объектов одной копии списка мало, наружу нужно безопасное представление. Резерв означает принятие запроса, а не выполненный возврат банка. Отказ банка и освобождение резерва — отдельные переходы. Репозиторий сохраняет корень, сохраняя это правило для всех способов записи.

Правильный объект ещё не защищает от двух запросов

Два обработчика могут загрузить два снимка p-17, каждый с reserved=0, и каждый успешно принять 700. Оба Java-объекта соблюдают инвариант. Поэтому граница агрегата также требует согласованного сохранения: проверки версии, блокировки либо условной записи в базе. Агрегат не является глобальной блокировкой сам по себе.

record Loaded(Payment payment, long version) {}
var first = store.load(); var second = store.load(); // Два самостоятельных снимка version=0.
first.payment().requestRefund("r-1", new Money(700, "RUB"));
second.payment().requestRefund("r-2", new Money(700, "RUB"));
System.out.println("local available=" + first.payment().available().minor()
    + "," + second.payment().available().minor());
System.out.println("first version=" + store.commit(first));
try { store.commit(second); }
catch (IllegalStateException e) { System.out.println("second commit=" + e.getMessage()); }

// Внутри commit перед сохранением: if (loaded.version() != version) throw ... "version conflict".
// Успешный commit увеличивает version. Полный метод показан в следующем шаге.
var retry = store.load(); // Теперь в нём reserved=700 и новая версия.

Store в демо хранит копии в памяти, а commit проверяет ожидаемую версию. Два снимка воспроизводят порядок двух запросов без потоков и базы. В рабочем репозитории проверку выполняет хранилище, например UPDATE по версии. Реальный JPA-опыт — в Locking & Caching. После конфликта решение принимают по новой загрузке.

Под капотом: когда маленькую границу надо пересмотреть

Если два агрегата должны немедленно соблюдать общее правило, одного события между ними мало. Можно выделить общий объект-координатор, согласованный резерв или выбрать транзакционную защиту нескольких записей. Часть задач действительно требует другой границы. Правило «один агрегат на транзакцию» полезно как ориентир проектирования, а не как запрет думать об инварианте.

Обратная крайность — загрузить магазин со всеми платежами, чтобы каждый возврат прошёл через магазин. Операции разных платежей начинают конфликтовать, коллекция растёт без границы, а контекст держит ненужные данные. Размер агрегата проверяют по его реальным командам и частоте конкурентных изменений.

Событие фиксирует факт модели, а доставку обеспечивает отдельный механизм

Корень принял запрос возврата и создал RefundRequested. Это доменное событие: что произошло, с каким платежом и какой суммой. Оно описывает уже принятое решение. Команда RequestRefund, наоборот, выражает намерение: её ещё можно отклонить.

record RefundRequested(PaymentId paymentId, String refundId, Money amount) {}

// Последние строки успешно принятой команды, после проверки инварианта:
refunds.put(refundId, new Refund(refundId, amount));
reserved = next;
pending.add(new RefundRequested(id, refundId, amount)); // Пока событие только в памяти объекта.

// Публикация здесь в брокер сделала бы внешний факт раньше успешного сохранения платежа.

Если сразу отправить событие в Kafka, а сохранение платежа потом упадёт, соседний контекст увидит запрос, которого нет в базе. Если сначала сделать commit, а затем отдельно отправить, процесс может упасть между этими действиями. Бизнес-решение и обещание его доставить должны сохраняться вместе. Для этого используют outbox: запись агрегата и сообщение для последующей отправки входят в одну локальную транзакцию.

Учебный Store ниже моделирует эти границы в памяти. Искусственная ошибка возникает до изменения двух сохранённых структур. Это доказательство порядка действий модели, а не настоящая транзакция базы, брокер или реализация восстановления после падения процесса.

// В Store: stored — сохранённая копия, version — её версия, outbox — отдельный список.
synchronized long commit(Loaded loaded) {
    if (loaded.version() != version) throw new IllegalStateException("version conflict");
    if (failNextCommit) {
        failNextCommit = false;
        throw new IllegalStateException("commit failed"); // Две сохранённые структуры ещё не тронуты.
    }
    stored = loaded.payment().storedCopy(); // Копия хранит состояние без прежнего pending.
    outbox.addAll(loaded.payment().events()); // Принято то же бизнес-решение.
    return ++version;
}

var loaded = store.load();
loaded.payment().requestRefund("r-1", new Money(400, "RUB"));

Новая загрузка имеет пустой pending: чтение не создаёт бизнес-факт. После commit событие остаётся в outbox для публикатора. Старый объект в демо больше не используют; в рабочем unit of work события помечают сохранёнными после успеха. Очистка до сохранения способна их потерять.

Доменное событие и публичное сообщение — разные поверхности. Внешний формат получает версию, eventId и нужные потребителю данные. Не сериализуй целую entity с внутренними enum и ссылками. Потребитель переводит факт в свой язык и обрабатывает дубли: отправка может повториться после потери подтверждения.

Событие не объединяет контексты одной транзакцией. Учёт принимает факт позже; нужны промежуточное состояние, повтор и исправление ошибки. Немедленный общий инвариант требует другого протокола. Границы Spring разобраны в Transactions, доставка — в Kafka Integration и AMQP Integration.

Глубокая модель нужна сложным правилам, а простому CRUD хватает простого кода

У формы справочника три поля и одна проверка обязательности. Пять интерфейсов, корень агрегата и три доменных события не сделают её полезнее. Transaction Script с ясной транзакцией и ограничениями базы справится дешевле. DDD начинается с понимания языка и границ; богатая объектная модель — один из вариантов реализации сложной части.

В нашей обработке возвратов модель оправдана: команды меняют связанные суммы, повтор имеет свой смысл, конкуренция опасна. Правило живёт в Payment, а приложение загружает его, вызывает команду и сохраняет в выбранной транзакционной границе. HTTP-контроллер разбирает запрос, репозиторий отвечает за сохранение, адаптер банка — за внешний API. Координатор сценария не должен заново считать допустимый возврат мимо корня.

DDD не требует микросервисов, CQRS или event sourcing. DTO-запрос может читать несколько агрегатов, сохраняя отдельные границы их изменения. Event sourcing делает историю событий источником состояния; outbox этого не делает. В демо источник — сохранённый Payment.

Открой сценарий с экспертом и проверь правило. Затем закрепи границы пакетов, чтобы чужая модель не входила через импорты: Components & Modules. Размещение портов и адаптеров — в Clean & Hexagonal Architecture.

  • Единый язык действует внутри выбранной модели. Один внешний платёж может иметь разные представления в обработке и учёте.
  • Bounded context удерживает смысл; context map описывает влияние, владение и перевод между моделями.
  • Entity сохраняет идентичность при изменении. Value object сравнивается по смыслу значений; record сам не выбирает этот смысл и не копирует вложенные коллекции.
  • Корень агрегата проверяет связанную команду. Версия или блокировка хранилища защищает её от конкурентных снимков.
  • Событие в памяти ещё не обещание доставки. Состояние и outbox сохраняются вместе; соседние контексты принимают факт отдельно.

На собеседовании

Что такое bounded context и чем он отличается от микросервиса?

Я ограничиваю место, где модель и её слова имеют один согласованный смысл. В обработке платежа успех — подтверждение capture, в учёте — проведённая запись. Поэтому оставляю две модели и явный перевод, вместо общего Payment со всеми чужими статусами.

Микросервис — физическая граница приложения и эксплуатации. Контекст может жить модулем монолита. Context map показывает, кто задаёт формат, кто зависит от него и как команды согласуют изменения.

  • Subdomain относится к задаче бизнеса, bounded context — к выбранной модели решения. Прямое равенство между ними не предполагаю.
  • Upstream/downstream обозначает влияние API и модели. Направление HTTP-вызова само по себе его не определяет.
  • Shared Kernel требует совместного владения маленькой общей частью. Общая библиотека всех entity создаёт связанность релизов.

Как выбрать границу агрегата и что гарантирует его корень?

Я начинаю с инварианта и команды, а не с таблиц. Если запросы возврата должны укладываться в принятую сумму, Payment проверяет резерв и добавляет Refund вместе. Внешний код обращается к корню и не может переписать дочернюю сумму отдельно.

Два снимка корня всё ещё способны пройти локальную проверку одновременно. Поэтому репозиторий сохраняет с проверкой версии либо блокировкой. После конфликта новая попытка читает актуальные данные и заново принимает решение.

  • Большой граф владения увеличивает загрузку и число конфликтов. Другие агрегаты адресую по id и не включаю в корень только ради удобного getter.
  • Для общего немедленного правила нескольких агрегатов нужна точка координации. Одно сообщение между ними не даёт атомарности.
  • Отдельный DTO-запрос вправе читать несколько агрегатов. Граница изменения не запрещает удобную форму чтения.
Лимит магазина хранится отдельно от двух платежей. Достаточно @Version на каждом Payment?

Нет. Два запроса изменят разные строки и не столкнутся по их версиям, но вместе могут превысить лимит. Нужна согласованная запись резерва магазина, общий координатор, нужная блокировка либо другой протокол проверки общего инварианта. Выбор делаю по требуемой согласованности и нагрузке.

Чем entity отличается от value object? Подходит ли record?

Entity я узнаю по идентичности: p-17 остаётся тем же платежом после возврата. Value object определяется содержимым и заменяется равным значением: сумма 1000 RUB не требует отдельного жизненного цикла. Для значения удобен неизменяемый record с проверкой при создании.

Record сравнивает компоненты, поэтому их равенство должно соответствовать домену. В демо BigDecimal 10.0 и 10.00 дали false, а сумма в канонических минимальных единицах — true. Список внутри record нужно защищать отдельно.

  • PaymentId как record — объект-значение идентификатора. Сам Payment сохраняет отдельную семантику идентичности.
  • Копия контейнера не делает изменяемые элементы неизменяемыми. Наружу отдаю безопасное представление, соответствующее границе модели.
  • Роль зависит от контекста: возврат с жизненным циклом — entity в обработке, но его поля могут быть строкой DTO в отчёте.

Как надёжно передать доменное событие другому контексту?

Агрегат создаёт факт после успешной проверки команды. В брокер он сам не ходит. Для надёжной внешней отправки сохраняю состояние и запись outbox одной транзакцией; отдельный публикатор отправляет её после commit. Получатель обрабатывает повторы и переводит факт в свою модель.

Если сохранение платежа упало, отправлять соседу факт уже принятого возврата нельзя. Если процесс упал после commit, запись outbox позволяет продолжить отправку. Это отдельный механизм над моделью, с явно выбранными правилами повторов.

  • После неуспешного сохранения Java-объект может остаться изменённым. Повтор начинаю с новой загрузки, а не старого графа и pending.
  • Доменное событие и публичное сообщение имеют разные цели. Внешнюю схему, eventId и совместимость проектирую отдельно.
  • Outbox не равен event sourcing: источник состояния может оставаться обычной записью агрегата. И событие не объединяет контексты в одну транзакцию.
