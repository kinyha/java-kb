Concurrency: Deadlocks & Liveness

Два заказа одновременно — и пул из двух потоков завис навсегда

Обработка заказа считает скидку отдельной задачей в том же пуле и ждёт её результат. На одном заказе всё работает. Под нагрузкой сервис перестаёт отвечать:

import java.util.concurrent.*;

public class PoolDeadlock {
    static final ExecutorService pool = Executors.newFixedThreadPool(2);   // общий пул сервиса

    static long discount(long orderId) { return orderId % 10; }

    static long processOrder(long orderId) throws Exception {
        Future<Long> d = pool.submit(() -> discount(orderId));   // подзадача в тот же пул
        return 1_000 - d.get();                                  // ждём её результат
    }

    public static void main(String[] args) throws Exception {
        for (int n : new int[]{1, 2}) {
            long start = System.nanoTime();
            Future<?>[] orders = new Future<?>[n];
            for (int i = 0; i < n; i++) {
                long id = i;
                orders[i] = pool.submit(() -> processOrder(id));
            }
            try {
                for (Future<?> f : orders) f.get(2, TimeUnit.SECONDS);
                System.out.printf("%d заказ(а) одновременно: готово за %d мс%n", n, (System.nanoTime() - start) / 1_000_000);
            } catch (TimeoutException e) {
                System.out.printf("%d заказа одновременно: за 2 с не готово — пул завис%n", n);
            }
        }
        System.exit(0);
    }
}
1 заказ(а) одновременно: готово за 2 мс
2 заказа одновременно: за 2 с не готово — пул завис

Оба потока пула заняты заказами, и каждый ждёт скидку. Задачи скидок стоят в очереди того же пула, и взять их некому. Дамп потоков показывает обоих рабочих в WAITING (parking) внутри FutureTask.get. Строки Found one Java-level deadlock нет: JVM ищет циклы только на замках, а здесь ресурс — потоки пула.

	at java.util.concurrent.FutureTask.get(java.base@21.0.11/FutureTask.java:190)
	at PoolDeadlock.processOrder(PoolDeadlock.java:10)

Это deadlock — взаимная блокировка: каждый участник держит ресурс и ждёт ресурс, который держит другой. Здесь ресурс — место в пуле, а бывают замки, соединения из пула базы, строки таблицы. В этой теме — четыре условия, при которых возникает deadlock, как его предотвратить порядком захвата и как найти. А ещё два родственных вида отказа: livelock, когда потоки активны, но не продвигаются, и starvation, когда поток годами ждёт своей очереди.

Исправления для пула: не блокироваться в задаче на результате подзадачи того же ограниченного пула. Можно считать скидку синхронно, вынести подзадачи в отдельный пул или собрать цепочку без блокировок через CompletableFuture.thenCompose (тема CompletableFuture).

Deadlock возможен только при четырёх условиях сразу, и цикл — главное из них

На практике чаще всего разрывают последнее условие. Как возникает цикл и как порядок захвата его убирает — на двух встречных переводах:

Порядок захвата по id убирает deadlock из переводов

Восемь потоков делают по миллиону переводов между десятью случайными счетами. Первый вариант берёт замки в порядке аргументов, второй — по возрастанию id. После пяти секунд ожидания программа спрашивает у JVM, есть ли взаимные блокировки:

import java.lang.management.*;
import java.util.concurrent.*;
import java.util.concurrent.atomic.AtomicLong;

public class Transfers {
    static final class Account {
        final long id;
        long balance = 1_000_000;
        Account(long id) { this.id = id; }
    }

    static void transfer(Account from, Account to, long amount) {
        synchronized (from) {                                    // порядок захвата зависит от аргументов
            synchronized (to) {
                from.balance -= amount;
                to.balance += amount;
            }
        }
    }

    static void orderedTransfer(Account from, Account to, long amount) {
        Account first = from.id < to.id ? from : to;              // всегда сначала меньший id
        Account second = first == from ? to : from;
        synchronized (first) {
            synchronized (second) {
                from.balance -= amount;
                to.balance += amount;
            }
        }
    }

    public static void main(String[] args) throws Exception {
        boolean ordered = args[0].equals("ordered");
        Account[] accounts = new Account[10];
        for (int i = 0; i < accounts.length; i++) accounts[i] = new Account(i);
        AtomicLong done = new AtomicLong();
        ExecutorService pool = Executors.newFixedThreadPool(8);
        for (int t = 0; t < 8; t++) {
            pool.submit(() -> {
                ThreadLocalRandom rnd = ThreadLocalRandom.current();
                for (int i = 0; i < 1_000_000; i++) {
                    Account a = accounts[rnd.nextInt(10)], b = accounts[rnd.nextInt(10)];
                    if (a == b) continue;
                    if (ordered) orderedTransfer(a, b, 1); else transfer(a, b, 1);
                    done.incrementAndGet();
                }
            });
        }
        pool.shutdown();
        boolean finished = pool.awaitTermination(5, TimeUnit.SECONDS);
        System.out.printf("переводов: %,d, все потоки закончили: %s%n", done.get(), finished);

        ThreadMXBean threads = ManagementFactory.getThreadMXBean();
        long[] stuck = threads.findDeadlockedThreads();          // то же, что ищет jstack
        if (stuck != null)
            for (ThreadInfo info : threads.getThreadInfo(stuck))
                System.out.println("  " + info.getThreadName() + " ждёт " + info.getLockName() + ", который держит " + info.getLockOwnerName());
        System.exit(0);
    }
}
$ java Transfers plain

  pool-1-thread-2 ждёт Transfers$Account@34c45dca, который держит pool-1-thread-1
$ java Transfers ordered
переводов: 7,199,736, все потоки закончили: true

Без порядка система встала после 382 переводов, во втором запуске — после 150. Два потока образовали цикл, остальные шесть встали за ними в очередь на те же счета. С порядком по id — 7,2 млн переводов без единого зависания. Добавилось две строки кода.

Если у объектов нет естественного уникального ключа, порядок строят по System.identityHashCode. Он может совпасть у двух объектов, поэтому для равных хешей берут третий, общий замок-«разрешитель» — так описано в Java Concurrency in Practice. Для замков из java.util.concurrent есть и другой путь — tryLock(timeout): не дождался второго замка — отпусти первый и попробуй позже (тема Locks).

Самые коварные циклы возникают, когда замок держат, вызывая чужой код: слушателя, колбэк, метод другого сервиса. Этот код может взять свой замок и через цепочку вызовов прийти к вашему в обратном порядке. Правило открытых вызовов (open calls): под замком только работа с собственным состоянием. Список слушателей копируют под замком, а вызывают их после выхода.

В базе данных всё то же самое. Две транзакции обновляют строки счетов в разном порядке — PostgreSQL находит цикл и откатывает одну из них с ошибкой deadlock detected. Лечится так же: обновлять строки в одном порядке (например, ORDER BY id в SELECT ... FOR UPDATE) и повторять откатанную транзакцию.

JVM находит циклы на замках, но не видит ожидание ресурсов

Взаимную блокировку на мониторах и на замках java.util.concurrent JVM находит сама. Так делает jcmd <pid> Thread.print в конце дампа (тема Diagnostics), и то же доступно из кода через ThreadMXBean.findDeadlockedThreads(), как в шаге 3. На этом строят сторожей, которые раз в минуту проверяют процесс и пишут алерт.

Чего JVM не найдёт — ожидания, в котором нет цикла на замках:

  • Голодание пула, как в шаге 1: потоки ждут Future, а не замок.
  • Потерянный сигнал wait/notify: все в wait set, никто не держит замок (тема synchronized & wait/notify).
  • Внешние ресурсы: пул соединений к базе исчерпан потоками, каждый из которых ждёт второе соединение. Или deadlock между двумя сервисами, которые синхронно вызывают друг друга.

Признак у всех один: потоки есть, CPU простаивает, работа не движется. В дампе видно, где стоят рабочие потоки и чего они ждут. Защита — таймауты на всех ожиданиях: get(timeout), таймаут получения соединения, tryLock(timeout). Зависание превращается в ошибку, которую видно в логах и метриках.

Livelock: потоки работают, но вежливо уступают друг другу по кругу

Попробуем обойти deadlock «вежливо»: взять первый замок, попытаться взять второй через tryLock(), а при неудаче отпустить первый и начать заново. Два потока берут одни и те же замки в разном порядке:

import java.util.concurrent.*;
import java.util.concurrent.atomic.AtomicLong;
import java.util.concurrent.locks.*;

public class Polite {
    static final Lock a = new ReentrantLock(), b = new ReentrantLock();
    static final AtomicLong retries = new AtomicLong();

    // взять оба замка; если второй занят — вежливо отпустить первый и попробовать снова
    static void both(Lock first, Lock second, boolean randomPause) throws InterruptedException {
        while (true) {
            first.lock();
            try {
                if (second.tryLock()) {
                    try { return; } finally { second.unlock(); }  // работа с двумя ресурсами
                }
            } finally {
                first.unlock();
            }
            retries.incrementAndGet();
            if (randomPause) Thread.sleep(0, ThreadLocalRandom.current().nextInt(1000));
            else Thread.onSpinWait();
        }
    }

    public static void main(String[] args) throws Exception {
        boolean random = args[0].equals("random");
        int n = 200_000;
        long start = System.nanoTime();
        Thread t1 = new Thread(() -> { try { for (int i = 0; i < n; i++) both(a, b, random); } catch (InterruptedException e) { } });
        Thread t2 = new Thread(() -> { try { for (int i = 0; i < n; i++) both(b, a, random); } catch (InterruptedException e) { } });
        t1.start(); t2.start(); t1.join(); t2.join();
        System.out.printf("%s: %,d операций, %,d повторов, %d мс%n", args[0], 2 * n, retries.get(), (System.nanoTime() - start) / 1_000_000);
    }
}
$ java Polite spin
spin: 400,000 операций, 824,963 повторов, 81 мс
$ java Polite random
random: 400,000 операций, 3,708 повторов, 16 мс

Deadlock ушёл, но при немедленном повторе на каждую полезную операцию пришлось два холостых круга. Потоки одновременно берут свой первый замок, одновременно не получают второй, одновременно отпускают и снова начинают в такт. Это livelock: потоки не заблокированы, CPU занят, а работа почти не движется. В худшем случае — не движется совсем. Случайная пауза перед повтором ломает синхронность: повторов стало в 200 раз меньше, время — в пять раз меньше.

Тот же принцип работает далеко за пределами потоков. Клиенты, которые повторяют запросы к упавшему сервису с одинаковой паузой, приходят к нему синхронными волнами. Поэтому ретраи делают с экспоненциальной паузой и случайным разбросом (jitter).

Starvation: несправедливый замок может надолго обделить поток

Starvation (голодание) — поток готов работать, но постоянно проигрывает борьбу за ресурс. Четыре потока одну секунду по очереди берут замок на 10 мкс работы. Сравним обычный ReentrantLock и справедливый, new ReentrantLock(true):

import java.util.*;
import java.util.concurrent.locks.*;

public class Starve {
    public static void main(String[] args) throws Exception {
        for (boolean fair : new boolean[]{false, true}) {
            Lock lock = new ReentrantLock(fair);
            long[] got = new long[4];
            long end = System.nanoTime() + 1_000_000_000L;
            Thread[] ts = new Thread[4];
            for (int t = 0; t < 4; t++) {
                int id = t;
                ts[t] = new Thread(() -> {
                    while (System.nanoTime() < end) {
                        lock.lock();
                        try {
                            got[id]++;
                            long until = System.nanoTime() + 10_000;         // 10 мкс работы под замком
                            while (System.nanoTime() < until) Thread.onSpinWait();
                        } finally {
                            lock.unlock();
                        }
                    }
                });
                ts[t].start();
            }
            for (Thread t : ts) t.join();
            long total = Arrays.stream(got).sum();
            System.out.printf("%-9s всего %,6d, по потокам: %s%n", fair ? "fair:" : "unfair:", total, Arrays.toString(got));
        }
    }
}
unfair:   всего 94,317, по потокам: [6044, 41520, 17235, 29518]
fair:     всего 87,444, по потокам: [21864, 21861, 21860, 21859]

Несправедливый замок отдал одному потоку в семь раз больше, чем другому: 41 520 против 6 044. Поток, который только что отпустил замок, уже работает на ядре и успевает схватить его снова раньше, чем проснётся ждущий. Справедливый замок раздаёт строго по очереди, но пропускная способность ниже на 7%: каждую передачу приходится будить спящий поток. synchronized тоже несправедлив, и порядок входа не гарантирует.

Другие источники голодания:

  • длинные критические секции: пока один держит замок секунды, остальные ждут;
  • ReadWriteLock с постоянным потоком читателей может не пустить писателя (тема Locks);
  • приоритеты потоков — подсказка ОС, а не гарантия, и полагаться на них нельзя;
  • общий пул, где медленные задачи одного типа занимают все потоки, а быстрые ждут в очереди. Лечится разделением пулов (bulkhead).

Справедливость нужна редко: обычно важнее общая пропускная способность, а голодание при коротких критических секциях не критично. Справедливый замок берут, когда задержка одного потока недопустима и измерена.

  • Deadlock — цикл ожидания: каждый держит ресурс и ждёт чужой. Нужны все четыре условия Коффмана; на практике разрывают циклическое ожидание.
  • Единый порядок захвата — по id, по identityHashCode с замком-разрешителем — убирает deadlock. В замере урока: 382 перевода до зависания без порядка и 7,2 млн с порядком.
  • Под замком не вызывают чужой код (open calls). В базе те же правила: обновлять строки в одном порядке и повторять транзакцию после deadlock detected.
  • JVM находит циклы на замках (jstack, findDeadlockedThreads), но не голодание пула, потерянный notify и внешние ресурсы. От них защищают таймауты.
  • Задача не должна блокироваться на подзадаче того же ограниченного пула.
  • Livelock — потоки активны, но уступают друг другу в такт. Лечится случайной паузой.
  • Starvation — поток постоянно проигрывает. Справедливый замок раздаёт по очереди ценой пропускной способности.

На собеседовании

Что такое deadlock и как его избежать?

Ситуация, когда потоки ждут друг друга по кругу: каждый держит ресурс и ждёт ресурс, который держит другой. Нужны четыре условия: взаимное исключение, удержание с ожиданием, невозможность отнять ресурс и циклическое ожидание. Чаще всего разрывают цикл единым порядком захвата: например, замки счетов всегда берут по возрастанию id. Ещё помогают tryLock с таймаутом, правило не вызывать чужой код под замком и минимум вложенных блокировок.

  • Без уникального ключа порядок строят по System.identityHashCode с дополнительным замком для равных хешей.
  • Deadlock бывает не только на замках: голодание пула, исчерпанный пул соединений, синхронные взаимные вызовы сервисов. Защита — таймауты на всех ожиданиях.
Напишите transfer(from, to, amount) на synchronized без deadlock при встречных переводах.

Брать замки в порядке, не зависящем от направления: Account first = from.id < to.id ? from : to; Account second = first == from ? to : from; synchronized (first) { synchronized (second) { ... } }. В замере урока такой вариант сделал 7,2 млн переводов, а вариант с порядком аргументов завис после 382.

Как найти deadlock в работающем приложении?

Снять дамп потоков: jcmd <pid> Thread.print или jstack. JVM сама ищет циклы на мониторах и замках java.util.concurrent и в конце дампа пишет Found one Java-level deadlock: какие потоки, какие замки держат и каких ждут, на каких строках. Из кода то же даёт ThreadMXBean.findDeadlockedThreads().

  • JVM не найдёт ожидание без цикла на замках: голодание пула, потерянный notify, внешние ресурсы. Тогда смотрят, где стоят рабочие потоки и чего ждут: FutureTask.get, получение соединения, Object.wait.

Может ли deadlock возникнуть без явных замков?

Может. Классика — голодание пула: задача в фиксированном пуле отправляет подзадачу в тот же пул и ждёт её get(). Когда все потоки заняты такими задачами, подзадачи стоят в очереди, и исполнить их некому. В замере урока пул из двух потоков завис на двух одновременных заказах. То же бывает с пулом соединений базы, если поток держит одно соединение и ждёт второе.

В обработчике запроса: var a = executor.submit(this::loadUser); var b = executor.submit(this::loadOrders); return merge(a.get(), b.get()); — обработчик сам выполняется в executor. Что не так?

Обработчик блокирует поток пула в ожидании подзадач того же пула. Под нагрузкой все потоки займут обработчики, подзадачи будут ждать в очереди, и сервис встанет. Нужен отдельный пул для подзадач, или цепочка без блокировок на CompletableFuture, или синхронные вызовы. А get всегда с таймаутом.

Чем deadlock отличается от livelock и starvation?

При deadlock потоки заблокированы и ждут друг друга, CPU простаивает. При livelock потоки активны, но реагируют друг на друга так, что работа не движется. Например, оба уступают ресурс и повторяют в такт — лечится случайной паузой. Starvation — поток готов работать, но постоянно проигрывает борьбу за ресурс. Причины — несправедливый замок, длинные критические секции, читатели, не пускающие писателя.

Почему ReentrantLock по умолчанию несправедлив, если справедливость лучше?

Справедливость дорогая: каждую передачу замка приходится будить спящий поток, а поток, который уже работает на ядре, взять замок без очереди не может. В замере урока справедливый замок дал на 7% меньше операций, зато поровну: около 21 860 на поток против разброса от 6 044 до 41 520 у несправедливого.

  • ThreadMXBean.findDeadlockedThreads (JDK 21) — поиск взаимных блокировок из кода.
  • ReentrantLock (JDK 21) — справедливость и tryLock.
