Deployment Strategies

Стратегия выкатки решает, как долго старая и новая версии работают одновременно и как быстро можно откатиться. Rolling update заменяет поды по одному: в демо 7 секунд из 12 обе версии отвечали вперемешку — код и схема базы обязаны это выдерживать. Blue-green держит две полные копии и переключает трафик разом: смешение длилось меньше двух секунд, а откат — такое же переключение назад, но нужна двойная мощность. Canary пускает на новую версию малую долю трафика — 31 запрос из 400 при 1 поде из 10 — и расширяет её, пока метрики в норме. Feature flags отделяют выкатку кода от включения функции. Самое трудное — база: миграция, несовместимая со старой версией, ломает ещё работающие поды и делает откат бесполезным; совместимость даёт схема expand/contract.

Новая версия переименовала столбец, и откат не помог

Релиз платёжного сервиса переименовал столбец amount в amount_minor миграцией при старте. Первый новый под применил миграцию, и три старых пода, которые ещё обслуживали трафик, начали падать на каждой записи. Через пять минут ошибок решили откатиться — но старая версия тоже падала: столбца, с которым она работает, больше не было. Откатывать пришлось и код, и схему, вручную, под нагрузкой.

Тема разбирает стратегии выкатки на кластере k3s 1.34 и совместимость миграций на PostgreSQL 17. Демо deploy.sh использует образ из Kubernetes Basics, который отвечает номером своей версии; клиентский под шлёт запрос каждые 100 мс. Демо migrate.sh выполняет миграции так, как их видят одновременно работающие версии. Пробы и корректная остановка подов — в Java in Kubernetes, миграции подробно — в Migrations.

Rolling update: версии работают одновременно

spec:
  replicas: 4
  minReadySeconds: 3                 # новый под должен 3 с оставаться готовым, прежде чем выкатка пойдёт дальше
  strategy: { rollingUpdate: { maxSurge: 1, maxUnavailable: 0 } }
== rolling update v1 -> v2, 4 replicas, maxSurge 1, maxUnavailable 0
   seconds with both versions answering: 7; failed requests: 0
    0s  v1=7
    1s  v1=10
    2s  v1=9
    3s  v1=9
    4s  v1=9 v2=1
    5s  v1=9
    6s  v1=6 v2=3
    7s  v1=5 v2=5
    8s  v1=5 v2=5
    9s  v2=9
   10s  v1=6 v2=3
   11s  v1=2 v2=8
== rollback: kubectl rollout undo
   back to v1 in 13 s, revisions: 2 3

В хронологии демо видно, как растёт доля v2: с 4-й секунды появляются ответы новой версии, к 11-й их уже большинство, и 7 из 12 секунд обе версии отвечают одновременно. Пользователь может получить ответ v2, а следующий запрос — от v1. Значит, обе версии должны понимать формат друг друга в API, в сообщениях брокера, в кеше и в базе. Ошибок нет: maxUnavailable: 0 и readiness-проба не дают убрать старый под раньше, чем готов новый. Без minReadySeconds выкатка проходила примерно за 2 секунды, и смешение почти не попадало в выборку клиента.

Откат — kubectl rollout undo: Deployment хранит прежние ReplicaSet как ревизии и выкатывает предыдущую тем же постепенным способом — 13 секунд. Откат кода безопасен, только если состояние, которое успела создать новая версия, понятно старой, — об этом последний шаг.

Blue-green и canary: переключить всё сразу или понемногу

# blue-green: две полные копии, Service переключается сменой селектора
svc '{ app: payments, color: blue }'     # весь трафик на blue (v1)
svc '{ app: payments, color: green }'    # весь трафик на green (v2), blue продолжает работать для отката

# canary: стабильная и канареечная версии за одним Service
dep stable 1 9 '{ app: payments, track: stable }'
dep canary 2 1 '{ app: payments, track: canary }'
== blue-green: switch the Service selector
   seconds with both versions answering: 1; failed requests: 0
== canary: 9 stable pods v1 + 1 canary pod v2 behind one Service
   v1: 369 of 400
   v2: 31 of 400

Blue-green держит две полные копии: синюю с текущей версией и зелёную с новой, прогретой и проверенной заранее. Переключение — смена селектора Service: ответы v1 и v2 смешивались в пределах одной секунды, пока kube-proxy обновлял правила, ошибок нет. Откат — переключение обратно за ту же секунду, потому что синяя копия продолжает работать. Цена — двойная мощность на время выкатки и та же проблема с базой: обе копии работают с одной схемой.

Canary пускает на новую версию малую долю трафика и смотрит на её метрики. В демо доля задаётся соотношением реплик: один канареечный под из десяти получил 31 запрос из 400 — около 8 % при ожидаемых 10 %, балансировка соединений случайна. Точное деление — 1 %, 5 %, только для внутренних пользователей — делают на уровне L7: ingress-контроллер, сервисная сеть или шлюз с весами маршрутов. Решение «расширять или откатывать» принимают по SLI канарейки в сравнении со стабильной версией: доля ошибок, p99, бизнес-метрики. Автоматизируют это Argo Rollouts и Flagger.

Feature flags отделяют выкатку от релиза: новый код выкатывается выключенным, а функцию включают для 1 % пользователей, для сотрудников или для одного магазина без деплоя. Откат функции — выключение флага за секунды, без выкатки. Цена — ветвления в коде и долг: каждый флаг после полного включения надо удалять, иначе код обрастает мёртвыми путями.

Миграции базы: expand/contract совместим с обеими версиями

== breaking: rename the column in one step
   migration: rename amount -> amount_minor
     OK
   v1 pods still running:
     ERROR:  column "amount" of relation "invoice" does not exist
   v2 pods:
     OK
   rollback to v1 does not help:
     ERROR:  column "amount" of relation "invoice" does not exist
== expand / contract
   1. expand: add the new column, nullable
     OK
   v1 writes the old column:
     OK
   v2 writes both columns:
     OK
   2. backfill old rows:
     OK
   rows missing amount_minor: 0
   3. contract, after no v1 is left and rollback to v1 is no longer needed:
     OK
   v2 writes only the new column:
     OK
   rows: 100 100 200 200

Миграция, переименовавшая столбец одним шагом, сразу сломала все ещё работающие поды v1 — при rolling update они обслуживают трафик всё время выкатки, при blue-green синяя копия работает с той же базой. Откат кода на v1 не помогает: схема уже новая. Откатывать схему под нагрузкой — ещё один риск, а если v2 успела записать данные в новом формате, они могут потеряться.

Expand/contract разбивает изменение на шаги, каждый из которых совместим с соседними версиями кода. Сначала схема расширяется: новый столбец добавляется необязательным — v1 его не замечает и продолжает писать старый. v2 пишет оба столбца и читает новый с запасным чтением старого. Фоновая задача переносит старые строки — пачками, чтобы не держать длинных блокировок, как в Migrations. Только когда v1 не осталось нигде и откат на неё больше не планируется, отдельным релизом схема сужается: новый столбец становится обязательным, старый удаляется. Переименование превращается в три-четыре релиза — это цена выкаток без простоя и с возможностью отката. То же правило для API и сообщений: сначала принимать оба формата, потом писать новый, потом перестать понимать старый.

Если новая версия сломалась, достаточно откатить деплой.

Откат кода не откатывает базу. В демо после переименования столбца и v2, и откаченная v1 работают с новой схемой — и v1 падает на каждой записи. Миграции делают совместимыми с предыдущей версией кода (expand/contract), тогда откат кода безопасен.

  • Rolling update (maxSurge 1, maxUnavailable 0, minReadySeconds 3): 7 из 12 секунд обе версии отвечают, ошибок 0; откат — 13 с.
  • Blue-green: переключение селектора, смешение около секунды, мгновенный откат, двойная мощность.
  • Canary: 1 под из 10 получил 31 запрос из 400; точные доли — на L7; решение по SLI.
  • Feature flags отделяют выкатку от включения функции.
  • Переименование столбца одним шагом ломает v1 и откат; expand → двойная запись → перенос → contract.

На собеседовании

Какие стратегии выкатки вы знаете и чем они отличаются?

Recreate — остановить старое, запустить новое: просто, но простой. Rolling update — заменять поды постепенно: без простоя, но версии работают одновременно. Blue-green — две полные копии и мгновенное переключение трафика: быстрый откат, двойная мощность. Canary — новая версия на малой доле трафика с расширением по метрикам. Feature flags — включение функций без деплоя.

  • maxSurge, maxUnavailable и minReadySeconds управляют темпом rolling update.
  • Canary по репликам грубый; точные доли — ingress, сервисная сеть, Argo Rollouts.
  • Все стратегии, кроме recreate, требуют совместимости версий.

Как выкатывать изменения схемы базы без простоя?

По схеме expand/contract: каждая миграция совместима с текущей и предыдущей версиями кода. Добавить новое необязательным, научить код писать оба варианта, перенести данные, переключить чтение на новое, и только отдельным релизом удалить старое. Никаких переименований и удалений в одном релизе с кодом, который их требует.

  • Перенос данных пачками, индексы CONCURRENTLY, без долгих блокировок.
  • Откат кода безопасен, только если схема совместима с предыдущей версией.
  • То же для API и событий: сначала читать оба формата.
Что не так с этим релизом? 
-- V42__payment_status.sql, выполняется Flyway при старте пода v2
alter table payment drop column legacy_status;
alter table payment alter column status set not null;
-- v1 пишет legacy_status и не заполняет status

Миграция выполняется при старте первого пода v2, когда поды v1 ещё обслуживают трафик: v1 сразу начинает падать — столбца legacy_status нет, а status стал обязательным, хотя v1 его не заполняет. Откат на v1 невозможен без ручного восстановления схемы, а данные столбца уже удалены. Нужно: в этом релизе только добавить и заполнять status, перенести старые строки, а удаление legacy_status и NOT NULL — отдельным релизом, когда v1 нигде не осталось.

Как понять, что канареечный релиз можно расширять?

Сравнить SLI канарейки и стабильной версии за одно и то же время: доля ошибок, задержка p99, насыщение, бизнес-метрики вроде успешных платежей. Если канарейка не хуже в пределах порога — расширять долю по шагам; если хуже — откатить. Анализ автоматизируют Argo Rollouts или Flagger по запросам к Prometheus.

  • Малая доля трафика — мало данных: окно анализа должно набрать статистику.
  • Канарейку отделяют меткой версии в метриках и трассах.
  • Kubernetes: Rolling Update Deployment, Rolling back.
  • Martin Fowler: BlueGreenDeployment, CanaryRelease, Feature Toggles.
  • Martin Fowler: ParallelChange — expand/contract.
  • Argo Rollouts.
