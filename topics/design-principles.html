Design: SOLID & Principles

SOLID — пять правил о том, как расставить границы в коде, чтобы изменение одного требования трогало одно место. Класс отвечает перед одним заказчиком изменений. Новое поведение добавляется новым классом, а не правкой старого. Подтип выполняет договор родителя, а не только компилируется. Клиент видит только нужные ему методы. Бизнес-логика зависит от интерфейсов, которыми владеет сама, а инфраструктура подстраивается под них. Каждое правило — ответ на конкретную боль, и применять его без этой боли — лишняя сложность.

Класс платежей правят пять команд, и каждая ломает чужое

Платёжный сервис начинался с одного класса. За два года в нём оказалось всё: выбор способа оплаты через switch, расчёт комиссии, запись в базу, текст SMS, формат чека. Любое изменение — новая комиссия для финансов, новый текст для маркетинга, новая колонка для DBA — правит один и тот же файл.

class PaymentService {
    Receipt pay(Payment p) {
        long fee = switch (p.method()) {        // Финансы: правила комиссии.
            case "card" -> p.cents() * 15 / 1000;
            case "sbp" -> 0;
            default -> throw new IllegalArgumentException(p.method());
        };
        String status = switch (p.method()) {   // Каждый новый способ оплаты — правка здесь.
            case "card" -> tinkoff.charge(p.card(), p.cents() + fee);
            case "sbp" -> sbp.createQr(p.cents());
            default -> throw new IllegalArgumentException(p.method());
        };
        jdbc.update("insert into payment ...");  // DBA: схема таблицы.
        sms.send(p.phone(), "Оплачено " + p.cents() / 100 + " ₽"); // Маркетинг: тексты.
        return new Receipt(p.id(), status, fee);
    }
}

Проблема не в длине метода. Изменения разных людей сталкиваются в одном месте: маркетинг правит текст SMS и случайно ломает округление комиссии, потому что они в одной строке. Разработчик добавляет способ оплаты и правит два switch, а тест на третий забыт. Слияния веток конфликтуют, потому что все пишут в один файл.

SOLID — пять принципов, которые Роберт Мартин собрал из работ Мейера, Лисков и своих статей начала 2000-х. Все пять отвечают на один вопрос: как расставить границы, чтобы изменение одного требования не тянуло за собой правки в несвязанных местах. Демо SolidDemo.java запускается без сборки: java SolidDemo.java на JDK 21.

SRP: модуль отвечает перед одним заказчиком изменений

Самая частая неправильная формулировка — «класс должен делать одну вещь». По ней любой класс можно оправдать («он делает платежи») или раздробить до класса на метод. Мартин в «Чистой архитектуре» уточняет: модуль должен отвечать перед одним и только одним актором — группой людей, которые просят изменений. Принцип про причины изменений, а не про количество методов.

После разделения каждый класс меняется по своей причине. Финансы правят FeeCalculator и его тесты; текст SMS живёт в PaymentNotifier, и его правка не может задеть расчёт денег. PaymentService остаётся координатором: получить комиссию, списать, сохранить, уведомить. Он меняется, только когда меняется сам сценарий оплаты.

Обратная ошибка — дробить по методам. Класс PaymentAmountValidator, PaymentAmountValidatorFactory и PaymentAmountValidationResultMapper на десять строк кода меняются всегда вместе, по одной причине. Это одна ответственность, размазанная по трём файлам: читать труднее, а пользы нет. Код, который меняется вместе, держат вместе — это и есть связность (cohesion).

OCP: новый способ оплаты добавляется новым классом, а не правкой switch

Принцип открытости-закрытости: модуль открыт для расширения и закрыт для изменения. Добавить СБП — значит написать новый код, а не править проверенный. В Java это достигается полиморфизмом: сервис зависит от интерфейса, а каждый способ оплаты — отдельная реализация.

interface PaymentProcessor {
    String method();             // Какой способ оплаты обрабатывает.
    String charge(Payment p);
}

class PaymentService {
    private final Map<String, PaymentProcessor> byMethod;

    // В Spring сюда придут все бины-реализации: List<PaymentProcessor>.
    PaymentService(List<PaymentProcessor> processors) {
        byMethod = processors.stream().collect(toMap(PaymentProcessor::method, identity()));
    }

    String pay(Payment p) {
        var processor = byMethod.get(p.method());
        if (processor == null) throw new IllegalArgumentException("unsupported method " + p.method());
        return processor.charge(p);
    }
}
card: 3-D Secure, charged 500
sbp: QR sent for 700
unsupported method crypto

Чтобы добавить криптовалюту, достаточно класса CryptoProcessor с аннотацией @Component. PaymentService, CardProcessor и их тесты не меняются. Spring внедрит в конструктор все реализации интерфейса, и новая попадёт в карту сама. Это и есть паттерн «стратегия», разобранный в Behavioral Patterns.

OCP защищает от изменений по одной оси, которую ты предвидел: способы оплаты. От всех изменений сразу закрыться нельзя. Если завтра комиссия начнёт зависеть от страны, интерфейс придётся менять. Поэтому точки расширения добавляют там, где изменения уже случались или точно случатся. Интерфейс «на всякий случай» для класса, у которого одна реализация и нет второй на горизонте, стоит дороже, чем правка в будущем.

LSP: подтип выполняет договор родителя, а не только компилируется

Принцип подстановки Барбары Лисков: код, написанный для типа, должен правильно работать с любым его подтипом. Компилятор проверяет только сигнатуры. Договор — что метод обещает сделать — он не проверяет. Подтип может скомпилироваться и при этом обмануть вызывающего.

interface RefundingProcessor extends PaymentProcessor {
    String refund(Payment p); // Договор: вернуть деньги клиенту.
}

class WalletProcessor implements RefundingProcessor {
    public String refund(Payment p) {
        throw new UnsupportedOperationException("wallet refunds are manual"); // Договор нарушен.
    }
}

// Код возвратов написан под интерфейс и о кошельке ничего не знает.
for (var processor : processors) System.out.println(processor.refund(p));
== LSP: refunds
  card: refunded 300
  wallet: UnsupportedOperationException — wallet refunds are manual

Ночной job возвратов проходит по всем процессорам и падает на кошельке. Чтобы его починить, в общий код добавляют if (processor instanceof WalletProcessor), и полиморфизм из OCP перестаёт работать: каждый новый особый случай снова правит общий код. Нарушение LSP почти всегда видно по таким проверкам типа у вызывающего.

Формально договор описывают так: подтип не усиливает предусловия (не требует от вызывающего большего), не ослабляет постусловия (не обещает меньшего) и сохраняет инварианты. Бросить исключение, которого договор не предусматривал, — ослабить постусловие. Исправление здесь — не наследовать то, что не можешь выполнить: кошелёк реализует только PaymentProcessor, а возвраты требуют отдельного интерфейса, который кошелёк не реализует.

Нарушение LSP в самой JDK

List<String> methods = new ArrayList<>(List.of("card"));
List<String> view = Collections.unmodifiableList(methods); // Тоже List.
view.add("sbp");    // List обещает add, этот List — нет.
methods.add("sbp"); // Меняем исходный список.
System.out.println(view);

view after source change: [card, sbp]

Интерфейс List помечает add как «необязательную операцию», и неизменяемые списки бросают UnsupportedOperationException. Это сознательный компромисс JDK, чтобы не плодить отдельные интерфейсы для чтения и записи, и он ровно об этом принципе: метод, принимающий List, не знает, можно ли в него писать. Вторая строка вывода — отдельная ловушка: unmodifiableList — это вид на исходный список, а не копия, и он видит его изменения. Неизменяемую копию даёт List.copyOf.

Квадрат — это прямоугольник, поэтому Square extends Rectangle — правильное наследование.

Код для Rectangle рассчитывает, что setWidth не меняет высоту. Квадрат обязан менять обе стороны, и вызывающий получает другую площадь, чем ожидал. «Является» в жизни не значит «подставим» в коде: наследование проверяют по поведению, а не по словам.

ISP: клиент зависит только от методов, которые вызывает

Принцип разделения интерфейсов: не заставляй клиента зависеть от методов, которыми он не пользуется. Шлюз банка умеет списывать, возвращать, делать выплаты и выгружать отчёты. Если всё это один интерфейс BankGateway, то сервис чеков, которому нужен только отчёт, зависит и от списаний.

// Толстый интерфейс: у каждого клиента свой кусок, но зависят все от всего.
interface BankGateway {
    ChargeResult charge(ChargeRequest r);   // платежи
    RefundResult refund(RefundRequest r);   // возвраты
    PayoutResult payout(PayoutRequest r);   // выплаты продавцам
    Report dailyReport(LocalDate day);      // сверка
}

// Роли по клиентам: реализация одна, интерфейсы разные.
interface Charging  { ChargeResult charge(ChargeRequest r); }
interface Reporting { Report dailyReport(LocalDate day); }
class TinkoffGateway implements Charging, Reporting { /* ... */ }

Зачем это нужно, видно при изменениях. Добавили в payout параметр — с толстым интерфейсом перекомпилируется и пересобирается сервис сверки, хотя выплат он не касается. Тест сверки мокает интерфейс из четырёх методов, три из которых ему не нужны. Ролевые интерфейсы показывают по сигнатуре конструктора, чем класс реально пользуется.

В Spring тот же вопрос возникает с репозиториями. JpaRepository даёт сервису сверки deleteAll и saveAll, хотя ему нужно только чтение. Свой интерфейс-наследник Repository с двумя нужными методами сужает поверхность и делает зависимость честной. Подробнее — в Spring Data.

DIP: бизнес-логика владеет интерфейсом, а инфраструктура его реализует

Принцип инверсии зависимостей: модули верхнего уровня (политика, бизнес-правила) не зависят от модулей нижнего уровня (детали: банк, база, HTTP). Оба зависят от абстракции, и абстракция принадлежит верхнему уровню. Ключевое слово — «принадлежит»: интерфейс лежит в пакете домена и описан языком домена.

Слева PaymentService импортирует класс SDK банка. Смена банка, обновление SDK, даже тест без сети требуют трогать бизнес-код. Справа PaymentService знает только свой BankGateway с методами вроде charge(Money, CardToken), описанными в терминах платежей. TinkoffAdapter в пакете инфраструктуры переводит этот язык в вызовы SDK. Новый банк — новый адаптер, бизнес-код не меняется, а в тесте вместо адаптера подставляется заглушка.

Частая путаница на собеседовании — смешать DIP, DI и IoC. IoC — общий принцип: управление созданием и вызовами передано фреймворку. DI — способ получить зависимости снаружи, через конструктор; его делает контейнер Spring. DIP — правило о том, кто от кого зависит в исходном коде. Spring внедрит конкретный TinkoffClient в PaymentService так же охотно, как интерфейс: DI не гарантирует DIP. Его гарантирует только то, где лежит интерфейс и что импортирует пакет домена.

Принципы — ответ на боль изменений, и без боли они превращаются в церемонию

SOLID хорошо объясняет, почему код трудно менять. Он плохо подходит как чек-лист «чтобы было правильно». Интерфейс на каждый класс, фабрика на каждый конструктор и три слоя абстракции над вызовом одного метода делают код длиннее и труднее для чтения, ничего не защищая. Каждая граница стоит денег: лишний файл, лишний переход в IDE, лишняя мысль у читателя.

ПринципСутьГде перебарщивают
DRYОдно знание — в одном местеСклеивают одинаковый на вид код с разными причинами изменения; потом его разводят флагами

Про DRY стоит сказать точнее. Два одинаковых метода проверки суммы — для платежа и для выплаты продавцу — выглядят как дублирование. Но лимиты платежей задают риски, а лимиты выплат — юристы. Если их склеить, первое же изменение одного превратит общий метод в набор флагов. DRY — про знание, а не про текст: дублирование одинаковых строк с разными причинами изменения — случайное сходство, и его можно оставить.

Хорошая проверка — история изменений. Если два класса всегда меняются вместе, граница между ними лишняя. Если в один класс регулярно приходят правки от разных людей — границы не хватает. Связь между классами при этом должна быть слабой (low coupling): изменение внутри одного не требует правок в другом. Как эти же идеи работают на уровне модулей и пакетов, разобрано в Components & Modules, а на уровне всего приложения — в Clean & Hexagonal Architecture.

  • SRP — про заказчиков изменений: одна группа людей, один модуль. Код, который меняется вместе, держат вместе.
  • OCP достигается полиморфизмом и защищает только от предвиденной оси изменений.
  • LSP — про поведение: подтип не бросает неожиданных исключений и не обещает меньше. Признак нарушения — instanceof у вызывающего.
  • DIP — про направление импортов: интерфейс принадлежит бизнес-логике. DI в Spring его не гарантирует.
  • Граница стоит денег; её ставят там, где изменения уже сталкиваются, а не на всякий случай.

На собеседовании

Расскажи про SOLID на примере из своей работы

Это пять принципов о границах в коде. SRP: модуль отвечает перед одной группой заказчиков изменений. OCP: новое поведение добавляется новым кодом, как новый способ оплаты новой реализацией интерфейса. LSP: подтип выполняет договор родителя. ISP: клиент видит только нужные ему методы. DIP: бизнес-логика зависит от своих интерфейсов, а инфраструктура их реализует.

В платёжном сервисе это выглядело так: switch по способам оплаты заменили на List<PaymentProcessor> из Spring, интерфейс шлюза банка перенесли в пакет домена, а SDK банка спрятали в адаптер. Новый способ оплаты и новый банк перестали трогать бизнес-код.

  • Принципы отвечают на боль изменений; интерфейс на каждый класс без второй реализации — церемония.
  • OCP закрывает только от предвиденной оси изменений; точки расширения ставят по истории правок.
  • На уровне модулей те же идеи дают принципы компонентов: ацикличность и направление к стабильности.

Что значит «одна ответственность» в SRP?

Не «делает одну вещь». У Мартина формулировка такая: модуль должен отвечать перед одним актором — группой людей, которые просят изменений. Если в класс платежей приходят правки и от финансов, и от маркетинга, и от DBA, их изменения сталкиваются и ломают друг друга.

Я делю по причинам изменений: расчёт комиссии отдельно, уведомления отдельно, хранение отдельно, а сервис связывает шаги сценария.

  • Обратная ошибка — дробить по методам: классы, которые всегда меняются вместе, — одна ответственность в нескольких файлах.
  • Проверка по истории git: что меняется вместе и кто приходит с правками.
  • SRP на уровне компонентов — Common Closure Principle: то, что меняется по одной причине, собирают в один модуль.

Приведи пример нарушения принципа Лисков

Интерфейс возвратов обещает вернуть деньги, а реализация для кошелька бросает UnsupportedOperationException. Код компилируется, но ночной job возвратов падает на кошельке, и в общий код начинают добавлять instanceof. Подтип не выполнил договор родителя.

Пример из JDK — неизменяемые списки: List обещает add, а Collections.unmodifiableList и List.of бросают исключение. JDK сознательно пошла на это, назвав add необязательной операцией.

  • Формально: подтип не усиливает предусловия, не ослабляет постусловия и сохраняет инварианты.
  • Признак нарушения — проверки типа у вызывающего; исправление — не наследовать то, что не можешь выполнить, и разделить интерфейсы.
  • Квадрат-прямоугольник: «является» в жизни не значит «подставим» в коде, если setWidth меняет и высоту.
unmodifiableList — это неизменяемый список?

Нет. Это вид на исходный список без методов записи. Если кто-то изменит исходный список, вид покажет изменения: в демо после methods.add("sbp") вид стал [card, sbp]. Неизменяемую копию даёт List.copyOf или List.of.

Чем DIP отличается от dependency injection и IoC?

IoC — общий принцип: управление созданием объектов и вызовами передаётся фреймворку. DI — способ получить зависимости снаружи, например через конструктор; это делает контейнер Spring. DIP — правило о направлении зависимостей в коде: бизнес-логика зависит от абстракции, которую сама и описывает, а инфраструктура её реализует.

Spring внедрит конкретный класс SDK банка в сервис так же легко, как интерфейс. DI есть, а DIP нарушен. DIP проверяется по тому, где лежит интерфейс и что импортирует пакет домена.

  • Инверсия касается зависимости в исходном коде, а не потока вызовов: платёж всё так же идёт в банк.
  • Интерфейс описывают языком домена, а не копией API SDK; иначе детали банка протекают в бизнес-код.
  • Правило зависимостей Clean Architecture — DIP, применённый ко всем слоям сразу.
Здесь есть DI. Есть ли DIP? 
package com.acme.payments;

import ru.tinkoff.acquiring.sdk.TinkoffClient;     // Класс SDK банка.
import ru.tinkoff.acquiring.sdk.InitResponse;

@Service
class PaymentService {
    private final TinkoffClient bank;                // Внедряется контейнером.
    PaymentService(TinkoffClient bank) { this.bank = bank; }

    Receipt pay(Payment p) {
        InitResponse r = bank.init(p.cents(), p.id()); // Ответ SDK в бизнес-коде.
        return new Receipt(p.id(), r.getPaymentId());
    }
}

DI есть: зависимость приходит через конструктор. DIP нет: пакет payments импортирует классы SDK, и типы ответа банка протекли в бизнес-логику. Смена банка или версии SDK правит PaymentService, а тест без SDK не написать. Исправление: интерфейс BankGateway в пакете payments с методами на языке платежей и адаптер в пакете инфраструктуры, который один знает о TinkoffClient.

Почему советуют композицию вместо наследования?

Наследование жёстко связывает подкласс с реализацией родителя: изменение в родителе меняет поведение всех наследников, а подкласс зависит от деталей, которые родитель не обещал. Композиция собирает поведение из объектов через интерфейсы, и части можно заменять независимо, в том числе в тестах.

Наследование уместно, когда подкласс действительно подставим вместо родителя и выполняет его договор. Для переиспользования кода его лучше не брать.

  • Хрупкий базовый класс: родитель вызывает свой переопределяемый метод изнутри, и подкласс ломается при изменении порядка вызовов.
  • Spring сам строит поведение композицией: прокси, декораторы, цепочки фильтров.
  • sealed-иерархии в Java 17+ делают наследование явным и закрытым, когда набор подтипов известен.
  • Роберт Мартин, «Чистая архитектура», часть III, главы 7–11 — основа урока: SRP через акторов, OCP, LSP, ISP, DIP.
  • Barbara Liskov, Jeannette Wing, «A Behavioral Notion of Subtyping», 1994 — формальное определение подстановки.
  • Joshua Bloch, Effective Java, 3-е изд., пункты 18–20 — композиция вместо наследования, интерфейсы вместо абстрактных классов.
  • Andrew Hunt, David Thomas, The Pragmatic Programmer, 20th Anniversary Edition, раздел «DRY» — дублирование знания, а не текста.
