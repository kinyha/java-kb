Distributed Transactions

Когда операция меняет данные в двух сервисах или базах, обычная транзакция не помогает: у каждого участника свой коммит. Двухфазный коммит (2PC) делает их атомарными: сначала все участники подготавливаются и обещают закоммитить, потом координатор командует коммит. Цена — блокировки до решения координатора: если он упал между фазами, данные участников заперты. Поэтому между сервисами используют саги: цепочку локальных транзакций, где каждая видна сразу, а при отказе на следующем шаге предыдущие отменяются компенсирующими транзакциями. Сага не даёт изоляции: промежуточные состояния видны всем, и это проектируют явно.

Деньги ушли с кошелька, а до магазина не дошли

Оплата заказа с внутреннего кошелька затрагивает два сервиса: кошелёк списывает деньги у покупателя, банковский сервис зачисляет их магазину. У каждого своя база. Кошелёк закоммитил списание, а зачисление упало: счёт магазина заблокирован. Деньги покупателя исчезли — их нет ни на кошельке, ни у магазина. Сделать обе операции одной транзакцией базы невозможно: баз две.

Тема сравнивает два подхода к атомарности через границы: двухфазный коммит и сагу. Транзакции внутри одной базы — в ACID & Isolation, надёжная публикация шагов саги — в Transactional Outbox, повторы шагов — в Idempotency. Демо DistTxDemo.java работает с двумя базами PostgreSQL 17 — wallet и bank — в одном контейнере с включёнными prepared-транзакциями.

2PC: все участники обещают закоммитить, потом координатор командует

exec(w, "update wallet set balance = balance - 300 where id = 'anna'");
exec(b, "update account set balance = balance + 300 where id = 'shop-7'");
exec(w, "prepare transaction 'pay-1-wallet'");    // Фаза 1: каждая база обещает, что сможет закоммитить.
exec(b, "prepare transaction 'pay-1-bank'");
exec(w, "commit prepared 'pay-1-wallet'");        // Фаза 2: координатор говорит «коммит» обеим.
exec(b, "commit prepared 'pay-1-bank'");
== 2PC: anna 700, shop-7 300

После фазы 1 каждый участник гарантирует, что сможет закоммитить, — изменения записаны в WAL, проверки пройдены. Если хоть один ответил «не могу», координатор откатывает всех. Так получается атомарность через несколько баз: в демо 300 ушли от Анны и пришли магазину одним решением.

Упавший координатор оставляет участников с запертыми данными

== coordinator crashed after prepare: 1 prepared transaction left
   another payment of anna: 55P03 ERROR: canceling statement due to lock timeout
   after manual ROLLBACK PREPARED anna = 700

Координатор подготовил транзакцию кошелька и упал. Prepared-транзакция пережила отключение клиента и держит блокировку строки Анны: любой другой платёж Анны ждёт и падает по таймауту. Решить судьбу транзакции может только восстановленный координатор по своему журналу решений или человек командой ROLLBACK PREPARED. Пока писалось это демо, его упавший запуск оставил такие транзакции, и следующий запуск повис на DROP TABLE — пришлось убирать их вручную.

Отсюда минусы 2PC между сервисами: координатор — единая точка отказа, блокировки держатся на время сетевых кругов всех участников, а каждый участник должен поддерживать протокол. В Java это XA и JTA-менеджеры транзакций, но HTTP-API партнёров, Kafka и большинство NoSQL-хранилищ в XA не участвуют. Поэтому 2PC живёт внутри распределённых баз — Spanner, CockroachDB, Citus делают его сами с отказоустойчивым координатором, — а между сервисами используют саги.

Сага — цепочка локальных транзакций с компенсациями

// Шаг 1 — локальная транзакция кошелька, сразу видна всем.
exec(wallet, "update wallet set balance = balance - 200 where id = 'anna'");
// Шаг 2 — зачисление в банке; неактивный счёт — бизнес-отказ.
if (bank.update("... where id = ? and active") == 0) {
    // Компенсация шага 1 — отдельная транзакция, не откат.
    exec(wallet, "update wallet set balance = balance + 200 where id = 'anna'");
}
== saga to shop-7: wallet: -200 committed -> bank: +200 committed
   anna balance seen by others meanwhile: 500, final anna 500
== saga to shop-9: wallet: -200 committed -> bank: rejected (account shop-9 is not active) -> wallet: +200 compensation committed
   anna balance seen by others meanwhile: 300, final anna 500

Каждый шаг саги — обычная локальная транзакция своего сервиса, коммитится сразу и никого не блокирует. Если следующий шаг невозможен, сага выполняет компенсации уже сделанных шагов в обратном порядке. Компенсация — не откат, а новая бизнес-операция: «вернуть 200 на кошелёк» с собственной записью в истории. Платёж магазину shop-9 отклонён, и деньги Анны вернулись.

Обратите внимание на строку «seen by others meanwhile: 300». Пока сага шла к отказу, баланс Анны был 300 — и любой, кто читал его в этот момент, видел деньги списанными. Если в это время Анна попробовала оплатить что-то ещё на 400, ей отказали бы, хотя после компенсации у неё 500. Это отсутствие изоляции — главная особенность саг. С ней работают явно: семантическая блокировка — статус PENDING у платежа и резерв вместо списания, — порядок шагов, при котором самые вероятные отказы проверяются первыми, и коммутативные операции, которым неважен порядок.

Оркестратор держит состояние саги, хореография раздаёт его по событиям

Кто ведётОркестратор вызывает шаги и компенсацииСервисы реагируют на события друг друга
Где состояние сагиВ таблице оркестратора, видно целикомРазмазано по сервисам и событиям
Добавить шагИзменить оркестраторПодписать новый сервис
ПодходитСложные процессы с ветвлениями, платежиКороткие цепочки, слабая связанность

Оркестратор хранит состояние саги в своей базе — на каком шаге, что выполнено, что компенсировано — и после перезапуска продолжает с того же места. Отсюда требования к шагам: каждый шаг и каждая компенсация должны быть идемпотентными, потому что после сбоя оркестратор повторит последний неподтверждённый шаг. Команды и события между шагами отправляют через outbox, чтобы не потерять их между локальной транзакцией и брокером. Компенсация не может провалиться окончательно: её повторяют, пока не выполнится, а то, что не компенсируется — отправленное письмо, выданный наличными платёж, — ставят последним шагом. Готовые движки — Temporal, Camunda, Axon — берут на себя хранение состояния и повторы.

Сага — это распределённая транзакция с откатом, только без блокировок.

Сага не откатывает, а компенсирует новыми операциями, и её промежуточные состояния видны всем: в демо баланс Анны на время саги был 300, хотя итог 500. У неё нет изоляции, и последствия — двойные траты, ложные отказы — проектируют явно: резервы, статусы PENDING, порядок шагов.

  • 2PC: prepare у всех, затем commit; атомарно, но участники держат блокировки до решения координатора.
  • Упавший координатор оставил prepared-транзакцию: чужой платёж упал по lock timeout до ручного ROLLBACK PREPARED.
  • 2PC живёт внутри распределённых баз; между сервисами — саги.
  • Сага: локальные транзакции и компенсации; изоляции нет — баланс 300 был виден, итог 500.
  • Оркестрация хранит состояние саги; шаги и компенсации идемпотентны, команды через outbox, необратимое — последним.

На собеседовании

Чем 2PC отличается от саги и что выбрать между микросервисами?

2PC даёт атомарность: участники сначала подготавливаются, затем по команде координатора коммитят. Но они держат блокировки до решения, координатор — единая точка отказа, и все участники должны поддерживать протокол. Сага — цепочка локальных транзакций с компенсациями при отказе: без блокировок и общего протокола, но без изоляции, промежуточные состояния видны. Между микросервисами выбирают сагу.

  • XA в Java существует, но HTTP-API, Kafka и многие хранилища в нём не участвуют.
  • 2PC с отказоустойчивым координатором — внутри распределённых баз: Spanner, CockroachDB.
  • Отсутствие изоляции в саге закрывают семантическими блокировками и порядком шагов.

Как спроектировать надёжную сагу?

Для каждого шага определить компенсацию. Хранить состояние саги в базе оркестратора, чтобы после перезапуска продолжить. Делать шаги и компенсации идемпотентными, потому что их повторяют после сбоев. Отправлять команды и события через outbox. Компенсации повторять до успеха, а необратимые действия ставить в конец.

  • Резерв вместо списания и статус PENDING — семантическая блокировка.
  • Шаг, после которого сага уже не откатывается, — pivot; до него — компенсируемые, после — повторяемые.
  • Temporal, Camunda, Axon хранят состояние и повторы.
Что не так с этой сагой оплаты? 
public void pay(Order o) {
    wallet.debit(o.customer(), o.amount());           // HTTP
    try {
        bank.credit(o.merchant(), o.amount());        // HTTP
        notifications.sendReceipt(o);                 // HTTP, письмо клиенту
    } catch (Exception e) {
        wallet.credit(o.customer(), o.amount());      // компенсация
        throw e;
    }
}

Состояние саги живёт только в памяти: если процесс упадёт между debit и credit, никто не сделает ни зачисление, ни компенсацию. Вызовы без ключей идемпотентности при повторе спишут или вернут дважды. Если упадёт sendReceipt, деньги магазину уже зачислены, а клиенту вернут списание — сага откатит успешный платёж из-за письма; необратимое и неважное должно идти после точки невозврата и не вызывать компенсацию. Нужен оркестратор с состоянием в базе, идемпотентные шаги, компенсация с повтором до успеха и письмо отдельным событием через outbox.
