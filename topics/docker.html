Docker

Образ — неизменяемый набор слоёв файловой системы и настройка запуска; контейнер — процесс, запущенный из образа в изолированных namespaces и с ограничениями cgroups. Это не виртуальная машина: ядро общее, а изоляция — механизм ядра. Для Java-сервиса из этого следуют практические правила. Сборка в несколько стадий и среда выполнения без компилятора уменьшают образ: в демо 554 МБ на JDK, 285 МБ на JRE и 74 МБ со средой из jlink. Редко меняющиеся зависимости кладут отдельным слоем раньше кода: после правки кода изменился один слой из восьми. JVM 21 видит лимиты контейнера, но по умолчанию берёт под heap только четверть памяти: 123 МБ из 512. И java должна быть PID 1 или получать сигналы: скрипт запуска без exec превратил корректную остановку в убийство через 10 секунд.

Образ на 600 МБ, сборка по 5 минут и сервис, который убивают при каждом деплое

Платёжный сервис собирают в образе на полном JDK вместе с Maven-кешем, и образ весит 600 МБ. Каждое изменение одной строки кода заново скачивает и пушит зависимости. В Kubernetes контейнеру дали 1 ГБ, а JVM взяла heap 256 МБ и упирается в сборку мусора. При каждом деплое поды завершаются по SIGKILL, обрывая платежи посреди обработки, хотя в коде есть хук корректной остановки.

Тема разбирает образы и слои, изоляцию контейнера и то, как в нём ведёт себя JVM. Демо docker.sh собирает мини-сервис App.java на JDK HttpServer в нескольких вариантах на eclipse-temurin:21 alpine и запускает их в Docker 29.8. Запуск в Kubernetes — в Kubernetes Basics и Java in Kubernetes, память JVM — в JVM Memory.

Образ — стопка слоёв; в продакшен едет только нужное

# Сборка на JDK, запуск на JRE: в итоговом образе только классы и среда выполнения.
FROM eclipse-temurin:21-jdk-alpine AS build
WORKDIR /src
COPY app/App.java .
RUN javac -d out App.java

FROM eclipse-temurin:21-jre-alpine
WORKDIR /app
COPY --from=build /src/out .
CMD ["java", "App"]
== image size
   single stage on JDK:   554 MB
   multi-stage, JRE:      285 MB
   multi-stage, jlink:    74 MB

Образ на JDK несёт компилятор, отладчики и исходники стандартной библиотеки — в продакшене они не нужны, а каждый лишний бинарник — ещё одна потенциальная уязвимость в отчёте сканера. Многостадийная сборка компилирует в первой стадии, а в итоговую копирует только результат: 285 МБ на JRE. jlink собирает среду выполнения из нужных модулей — здесь java.base и jdk.httpserver — и кладёт её на голый alpine: 74 МБ. Для Spring Boot модулей нужно больше, их список подсказывает jdeps --print-module-deps. Ещё меньше и безопаснее — distroless-образы без shell и пакетного менеджера; цена — отладка без sh внутри контейнера.

Порядок инструкций определяет, что пересобирается

# Зависимости меняются редко — отдельным слоем до кода приложения.
FROM eclipse-temurin:21-jre-alpine
WORKDIR /app
COPY libs/ libs/
COPY --from=kb-docker-multistage /app .
CMD ["java", "-cp", "libs/*:.", "App"]

   12.3kB	COPY --chmod=755 entrypoint.sh /__cacert_ent…

Слой определяется содержимым, а не фактом изменения файлов. При первом прогоне демо я менял только комментарий в исходнике — и изменённых слоёв оказалось ноль: javac выдал те же байты классов, и слой остался прежним. Для Maven-проектов то же правило: сначала копируют pom.xml и скачивают зависимости (mvn dependency:go-offline), потом копируют исходники и собирают. Spring Boot умеет раскладывать jar по слоям сам (java -Djarmode=tools -jar app.jar extract --layers): зависимости, snapshot-зависимости, ресурсы и код приложения ложатся отдельными слоями.

Что JVM видит в контейнере

== what the JVM sees in a container
   no limits:                         cpus=18 maxHeap=1984MB
   --memory=512m --cpus=2:            cpus=2 maxHeap=123MB
   same + -XX:MaxRAMPercentage=75:    cpus=2 maxHeap=371MB
   cgroup memory.max inside:          536870912

Контейнер — обычный процесс хоста в отдельных namespaces: свой список процессов (PID), своя сеть, своя файловая система (mount), свои имя хоста и пользователи. Ограничения ресурсов задают cgroups: лимит памяти виден внутри контейнера как /sys/fs/cgroup/memory.max — ровно 512 МБ. Ядро общее с хостом, поэтому контейнер стартует за доли секунды, но и изоляция слабее, чем у виртуальной машины.

JVM 21 читает cgroups: при --cpus=2 availableProcessors вернул 2 вместо 18 ядер машины, и от этого числа зависят размеры пулов, число потоков GC и параллельных стримов. Под heap по умолчанию берётся четверть доступной памяти: без лимита — 1 984 МБ от памяти виртуальной машины Docker Desktop, с лимитом 512 МБ — 123 МБ (четверть, за вычетом одного survivor-пространства, которое maxMemory() не учитывает). Сервис получает 512 МБ, а пользуется 123. Поэтому в контейнерах задают -XX:MaxRAMPercentage, обычно 60–75: 371 МБ heap при 75 %. Оставшееся нужно не-heap-памяти — метаспейсу, стекам потоков, коду JIT, прямым буферам. Если поставить 100 %, процесс превысит лимит cgroup, и ядро убьёт его (OOMKilled) без всякого OutOfMemoryError.

PID 1 и сигналы: кто получает SIGTERM

#!/bin/sh
# Скрипт запуска без exec: java — дочерний процесс, PID 1 остаётся sh.
echo "starting"
java App          # правильно: exec java App
== docker stop -t 10: who is PID 1
   kb-docker-multistage   PID 1 = java  stop took  0.1 s, exit code 143, shutdown hook ran: yes
   kb-docker-shell        PID 1 = java  stop took  0.1 s, exit code 143, shutdown hook ran: yes
   kb-docker-noexec       PID 1 = start.sh stop took 10.1 s, exit code 137, shutdown hook ran: no
   kb-docker-exec         PID 1 = java  stop took  0.1 s, exit code 143, shutdown hook ran: yes

docker stop и Kubernetes при удалении пода посылают SIGTERM процессу с PID 1, ждут и затем посылают SIGKILL. Если PID 1 — java, срабатывает хук завершения: сервис перестаёт принимать запросы, дорабатывает текущие и выходит с кодом 143 (128 + 15, SIGTERM) за 0,1 с. Если PID 1 — скрипт запуска без exec, сигнал получает sh, а он как PID 1 по умолчанию игнорирует SIGTERM и не пересылает его дочерним процессам. Контейнер ждёт весь тайм-аут — 10 секунд — и умирает от SIGKILL с кодом 137, хук не выполнился: текущие запросы оборваны.

Шелл-форма CMD java App в этом образе оказалась безопасной: busybox sh -c заменяет себя последней командой, и PID 1 — java. На это нельзя полагаться — другой shell или команда из двух частей (java App && echo done) поведёт себя иначе. Правила: exec-форма CMD ["java", ...]; в скриптах — exec java ...; если нужен настоящий init для сбора зомби-процессов — docker run --init или tini. Без флага -t Docker 29.8 на этой машине ждал 3 секунды вместо документированных 10; в Kubernetes ожидание задаёт terminationGracePeriodSeconds, по умолчанию 30.

JVM в контейнере сама использует выделенную контейнеру память.

JVM видит лимит, но берёт под heap по умолчанию 25 %: в демо 123 МБ из 512. Нужен -XX:MaxRAMPercentage около 75 % с запасом под не-heap-память; 100 % приводит к OOMKilled от ядра без OutOfMemoryError.

  • Образ — слои по содержимому; контейнер — процесс в namespaces с ограничениями cgroups, ядро общее с хостом.
  • Многостадийная сборка: 554 МБ на JDK → 285 МБ на JRE → 74 МБ с jlink.
  • Зависимости — слоем раньше кода: после правки изменился 1 слой из 8; комментарий не меняет классы и слой.
  • JVM видит 2 CPU и 512 МБ лимита, но heap — 123 МБ; MaxRAMPercentage=75 — 371 МБ.
  • java должна быть PID 1: скрипт без exec — 10 с ожидания, SIGKILL, код 137, хук не выполнен.

На собеседовании

Чем контейнер отличается от виртуальной машины?

Виртуальная машина эмулирует оборудование и запускает своё ядро. Контейнер — обычный процесс хоста, изолированный механизмами ядра: namespaces дают свои процессы, сеть, файловую систему и имя хоста, cgroups ограничивают CPU и память. Поэтому контейнер стартует за доли секунды и занимает мало, но изоляция слабее — ядро общее.

  • Образ — слои файловой системы по содержимому плюс настройка запуска.
  • Docker Desktop на macOS запускает контейнеры в Linux-виртуалке.
  • Повышенная изоляция — gVisor, Kata Containers.

Как написать хороший Dockerfile для Java-сервиса?

Многостадийная сборка: компиляция на JDK, запуск на JRE или среде из jlink. Зависимости — отдельным слоем раньше кода, чтобы правки кода не пересобирали их. Exec-форма CMD или ENTRYPOINT, чтобы java получала сигналы. Непривилегированный пользователь, фиксированные версии базового образа, MaxRAMPercentage для heap.

  • Spring Boot layered jar — слои зависимостей и кода.
  • Distroless — меньше уязвимостей, но нет shell для отладки.
  • .dockerignore, чтобы target и .git не попадали в контекст.
Что не так с этим Dockerfile? 
FROM maven:3-eclipse-temurin-21
COPY . /src
WORKDIR /src
RUN mvn package -DskipTests
ENTRYPOINT ./run.sh                  # run.sh: java -Xmx256m -jar target/app.jar

Образ на Maven и JDK несёт инструменты сборки и кеш зависимостей в продакшен. COPY . /src до сборки — любая правка кода заново скачивает все зависимости. Шелл-форма ENTRYPOINT и скрипт без exec: PID 1 — shell, SIGTERM не доходит до java, и при каждом деплое контейнер убивают по тайм-ауту. Жёсткий -Xmx256m не связан с лимитом контейнера. Нужно: две стадии, сначала pom.xml и dependency:go-offline, потом исходники; запуск на JRE, exec java -XX:MaxRAMPercentage=75 -jar.

Как JVM ведёт себя в контейнере с лимитом памяти?

Современные JVM читают лимиты cgroups: availableProcessors учитывает лимит CPU, а heap по умолчанию — 25 % лимита памяти. Это мало, поэтому задают MaxRAMPercentage около 75 %, оставляя память метаспейсу, стекам, JIT и прямым буферам. Если процесс превысит лимит, ядро убьёт его — OOMKilled без OutOfMemoryError.
