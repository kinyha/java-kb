Elasticsearch

Elasticsearch — поисковый движок на Lucene. Он строит инвертированный индекс: для каждого слова — список документов, где оно встречается. Перед индексацией текст проходит анализатор, который разбивает его на слова и приводит к основе, поэтому «кофейни» находит «кофейнях». Поле text анализируется для полнотекстового поиска, поле keyword хранится целиком для точных совпадений, сортировки и агрегаций. Результаты ранжируются по BM25. Новые документы появляются в поиске после refresh — по умолчанию через секунду. Elasticsearch — вторичный индекс, а не основное хранилище: данные в него доставляют из базы.

Поиск платежей по описанию на LIKE шёл секундами, а в Elasticsearch магазин не находится по названию

Поддержке нужен поиск платежей по описанию: «оплата в кофейне». В PostgreSQL это description ilike '%кофейн%' по сотням миллионов строк — полный проход. Платежи начали индексировать в Elasticsearch, и поиск стал мгновенным, но появились новые вопросы: точный фильтр по магазину «Coffee Point» ничего не находит, только что созданный платёж не ищется, а агрегация по магазинам падает с ошибкой.

Тема разбирает инвертированный индекс и анализаторы, типы полей, ранжирование, near-real-time и место Elasticsearch в архитектуре. Индексы для поиска внутри PostgreSQL — GIN и триграммы — в Index Types, доставка изменений из базы — в Transactional Outbox. Демо demo.sh работает с Elasticsearch 9.2.0 (Lucene 10.3) в Docker через REST API.

Анализатор превращает текст в термины, и по ним строится инвертированный индекс

== analyzers: 'Оплата заказов в кофейнях Москвы'
   standard: ['оплата', 'заказов', 'в', 'кофейнях', 'москвы']
   russian: ['оплат', 'заказ', 'кофейн', 'москв']

Стандартный анализатор только режет текст на слова и приводит к нижнему регистру: «кофейнях» и «кофейни» для него разные термины. Русский анализатор отбрасывает стоп-слова («в») и приводит слова к основе: «кофейн», «оплат». Запрос проходит тот же анализатор, поэтому «кофейни оплата» находит «оплата в кофейне» и «кофейнях». Поиск идёт по готовому списку документов для каждого термина — в отличие от LIKE, которому нужно проверить каждую строку.

Документы ранжируются по BM25: редкие слова и короткие поля весят больше

== match 'кофейни оплата' (russian analyzer), ranked by BM25
   0.737  p-1  Оплата заказа в кофейне
   0.652  p-3  Оплата книги о кофе и кофейнях
   0.652  p-4  Поездка до кофейни, оплата картой

Все три документа содержат оба термина, но p-1 выше: его описание короче, и найденные слова составляют большую его часть. BM25 учитывает три вещи: сколько раз термин встречается в документе (с насыщением — десятый повтор почти ничего не добавляет), насколько термин редок во всём индексе (редкие слова важнее частых) и длину поля. «Возврат за кофе» не найден: «кофе» анализатор превратил в «коф», а это другая основа, чем «кофейн». Ранжирование настраивают весами полей, синонимами и функциями — например, поднимать свежие платежи.

text — для поиска по словам, keyword — для точных значений и агрегаций

"merchant": {"type": "text", "fields": {"raw": {"type": "keyword"}}}
== term 'Coffee Point' on text field vs keyword field
   merchant      hits: 0
   merchant.raw  hits: 2
== terms aggregation on merchant.raw
   Coffee Point: 2 payments, 650
   Book House: 1 payments, 900
   Taxi Go: 1 payments, 300
== aggregation on text field
   Fielddata is disabled on [merchant] in [payments]. Text fields are not optimised for operations that require p

Поле text хранится в индексе как термины «coffee» и «point». Запрос term не анализирует значение и ищет термин «Coffee Point» целиком — его нет, ноль результатов. Это и был «не находится по названию». Поле keyword хранит значение целиком: точный фильтр нашёл оба платежа. Для агрегаций и сортировки нужны колоночные doc values, которые есть у keyword и чисел, а у text нет — отсюда ошибка. Поэтому строковые поля, по которым и ищут, и группируют, делают мультиполем: text плюс подполе keyword. Динамический маппинг делает так по умолчанию, но с ним легко получить неверные типы, и маппинг важных индексов задают явно.

Документ попадает в поиск после refresh, а не после ответа на запись

== near real time: index and search immediately
   right after index: 0
   get by id:         True
   after refresh:     1

Запись подтверждена, но поиск сразу после неё не нашёл документ. Lucene пишет документы в буфер и делает их видимыми для поиска, только когда создаёт новый сегмент индекса — это refresh, по умолчанию раз в секунду. GET по id документ уже находит: он читает из журнала транзакций (translog). Через полторы секунды поиск находит документ. Отсюда near-real-time: секунда задержки. Если поиск должен сразу видеть свою запись, используют refresh=wait_for на конкретном запросе, но не refresh=true на каждый: частые refresh плодят мелкие сегменты и нагружают слияние. При массовой загрузке refresh, наоборот, отключают.

Elasticsearch — вторичный индекс: данные приходят из базы, а число шардов фиксировано

Индекс делится на primary-шарды, каждый — отдельный индекс Lucene, и у каждого есть реплики на других узлах. Документ попадает в шард по хешу _id (или routing), поэтому число primary-шардов задаётся при создании индекса и не меняется без переиндексации — та же проблема, что mod N в Sharding. Поиск идёт на все шарды и сливает их результаты, а глубокая пагинация через from дорога по тем же причинам, что OFFSET; для неё есть search_after.

У Elasticsearch нет транзакций, соединений и ограничений целостности, а запись может потеряться при неудачной конфигурации, поэтому основным хранилищем платежей он не бывает. Источник правды — база, а в индекс изменения доставляют асинхронно: событиями через outbox или CDC, с переиндексацией с нуля как запасным вариантом. Поиск, соответственно, отстаёт от базы на доставку плюс refresh, и интерфейс должен это учитывать.

Elasticsearch можно использовать как основную базу: он хранит документы и быстро их ищет.

В нём нет транзакций и ограничений, видимость новых документов отложена до refresh — в демо поиск сразу после записи вернул 0, — а маппинг и число шардов меняются только переиндексацией. Elasticsearch — вторичный индекс, наполняемый из базы.

  • Инвертированный индекс: термин → документы; русский анализатор приводит «кофейнях» и «кофейни» к «кофейн».
  • BM25: короче поле и реже термин — выше релевантность; p-1 выше p-3 и p-4.
  • text для поиска по словам, keyword для точных фильтров и агрегаций: term по text — 0, по keyword — 2.
  • Near-real-time: сразу после записи поиск — 0, GET — найден, после refresh — 1.
  • Шарды фиксированы при создании; Elasticsearch — вторичный индекс, данные из базы через outbox или CDC.

На собеседовании

Как Elasticsearch ищет по тексту быстрее, чем LIKE в базе?

Он строит инвертированный индекс: при индексации текст проходит анализатор — разбивка на слова, нижний регистр, стоп-слова, приведение к основе, — и для каждого термина хранится список документов. Запрос проходит тот же анализатор, и поиск пересекает списки, а не проверяет каждую строку. Результаты ранжируются по BM25.

  • Анализатор при индексации и при поиске должен совпадать.
  • Для поиска внутри PostgreSQL есть полнотекстовый поиск с GIN и pg_trgm.

Чем text отличается от keyword?

text анализируется и разбивается на термины — для полнотекстового поиска. keyword хранится целиком — для точных фильтров, сортировки и агрегаций, у него есть doc values. Запрос term по text-полю с исходной строкой обычно ничего не находит, а агрегация по text падает. Строки, по которым и ищут, и группируют, делают мультиполем.

  • Маппинг существующего поля не меняется без переиндексации.
  • Динамический маппинг удобен для прототипа, но важные индексы описывают явно.
Почему этот поиск и отчёт работают неправильно? 
// индекс создан динамическим маппингом
var hits = es.search(s -> s.index("payments")
        .query(q -> q.term(t -> t.field("status").value("CAPTURED"))));
// после сохранения платежа сразу ищем его по описанию и показываем пользователю

Динамический маппинг сделал status полем text с подполем keyword, и term по status ищет термин «CAPTURED», а в индексе он хранится как «captured» — ничего не найдётся; нужно status.keyword или явный маппинг keyword. Поиск сразу после сохранения не увидит документ до refresh; для этого случая нужен refresh=wait_for или чтение по id, а платежи в индекс должны приходить из базы через outbox или CDC.

Почему только что записанный документ не находится поиском?

Elasticsearch — near-real-time: документ становится видимым для поиска после refresh, который создаёт новый сегмент Lucene, по умолчанию раз в секунду. GET по id видит документ сразу через translog. Если нужно, на запросе ставят refresh=wait_for.

  • Частые refresh плодят мелкие сегменты и нагружают слияние.
  • При массовой загрузке refresh_interval выключают.
