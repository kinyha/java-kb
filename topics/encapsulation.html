Encapsulation

Инкапсуляция — не «private-поля с геттерами и сеттерами», а гарантия, что состояние объекта меняется только через операции, которые держат его инвариант. Правило «баланс не меньше нуля» должно жить в одном методе debit, а не в каждом вызывающем коде; сеттер setBalance это правило отменяет. Инкапсуляцию легко нарушить незаметно: геттер, отдающий внутренний список, или конструктор, сохранивший чужой список, делят состояние с внешним кодом. Collections.unmodifiableList — только окно на исходный список, и в демо через него стал виден чужой элемент. Защищают копиями на входе и выходе, а лучше — неизменяемостью: final-поля, неизменяемое содержимое, операции, возвращающие новый объект. Изменяемый ключ в HashSet теряется. Границу дополнительно держат package-private и модули: неэкспортированный пакет не виден ни компилятору, ни глубокой рефлексии.

Сеттеры отменяют правила

Счёт клиента хранит баланс и историю операций. Первая версия — класс с private-полями, геттерами и сеттерами; формально поля закрыты. Демо InvariantDemo.java:

OpenAccount open = new OpenAccount();
open.setBalance(500);
open.setBalance(open.getBalance() - 800);       // сервис возвратов забыл проверку остатка
open.getHistory().add("debit p-1 800");
open.getHistory().clear();                      // отчёт «почистил» историю для вывода
== open fields: every caller must remember the rules
balance = -300, history = []

Баланс ушёл в минус, история пуста — и класс в этом не участвовал. Правило «нельзя списать больше остатка» есть только в головах тех, кто вызывает setBalance, и одного забывчивого сервиса хватило. Геттер getHistory() отдал ссылку на внутренний список, и код отчёта стёр историю. Private-поле с геттером и сеттером на каждое поле закрывает поле от синтаксиса, но не от изменений: это та же открытая структура данных, только с лишними строками. Такую модель называют анемичной: данные в одном месте, правила размазаны по сервисам.

void debit(String paymentId, long amount) {
    if (amount <= 0) throw new IllegalArgumentException("amount must be positive");
    if (amount > balance) throw new IllegalStateException("insufficient funds: " + balance + " < " + amount);
    balance -= amount;
    history.add("debit " + paymentId + " " + amount);
}
List<String> history() { return List.copyOf(history); }    // снимок, а не ссылка на внутренний список
== invariant kept inside the class
rejected: insufficient funds: 200 < 800
history().clear(): UnsupportedOperationException
balance = 200, history = [debit p-1 300]

Инкапсулированный Account не даёт изменить баланс напрямую — только операцией debit, которая проверяет сумму, меняет баланс и пишет историю вместе. Инвариант «баланс ≥ 0, история соответствует операциям» проверяется в одном месте и держится для любого вызывающего кода. Конструктор тоже проверяет входные данные: объект не может родиться в неверном состоянии. История отдаётся снимком, и попытка её очистить падает. Такой объект в терминах DDD — сущность или агрегат с поведением; правила предметной области живут в нём, а не в сервисах.

Утечки ссылок и защитные копии

static final class LeakyBatch {
    private final List<String> ids;
    LeakyBatch(List<String> ids) { this.ids = ids; }                   // хранит чужой список
    List<String> ids() { return Collections.unmodifiableList(ids); }    // окно на него же
}
static final class Batch {
    private final List<String> ids;
    Batch(List<String> ids) { this.ids = List.copyOf(ids); }           // копия на входе
    List<String> ids() { return ids; }                                  // уже неизменяемый
}
== unmodifiable view vs copy
unmodifiableList view: [p-1, p-2, p-evil]
List.copyOf snapshot:  [p-1, p-2]
List.copyOf(immutable) returns same instance: true

Утечка бывает в обе стороны: конструктор или сеттер сохраняет ссылку на чужой изменяемый объект — внешний код меняет состояние после проверок; геттер отдаёт ссылку на внутренний — внешний код меняет его напрямую, как с историей счёта. Защита — копия на входе и неизменяемое представление на выходе. Классические кандидаты — коллекции, массивы (массив всегда изменяем; clone() или List.of), старый java.util.Date (вместо него неизменяемые типы из Date & Time).

Детали, о которых спрашивают на senior-уровне. List.copyOf не копирует, если аргумент уже неизменяемый список из List.of/copyOf, — демо показало тот же экземпляр; копия дешёвая там, где не нужна. Он же запрещает null-элементы. Копию делают до проверки аргументов, а не после: иначе другой поток может поменять оригинал между проверкой и копированием (TOCTOU — time-of-check to time-of-use), и проверенным окажется не то, что сохранили. Для изменяемых классов-аргументов, которые могут быть подменены подклассом, Блох советует не использовать clone(), а копировать конструктором или фабрикой.

Неизменяемость: самая сильная инкапсуляция

MutableMoney m = new MutableMoney(100, "RUB");    // equals и hashCode по amount и currency
seen.add(m);
m.amount = 200;                                    // хеш изменился, корзина — нет

record Money(long amount, String currency) {
    Money plus(long delta) { return new Money(amount + delta, currency); }   // новый объект вместо изменения
}
== mutable key in a HashSet
contains after mutation: false, size = 1
immutable: price = 100, withFee = 115

Объект лежит в множестве, размер 1, но contains его не находит. HashSet положил его в корзину по старому хешу; после изменения суммы хеш другой, поиск идёт в другую корзину. Объект потерян внутри коллекции: удалить его тоже нельзя. Так ломаются кеши и множества с изменяемыми ключами — подробнее о корзинах в HashMap, о контракте equals/hashCode — в Object Methods. С неизменяемым Money такой ошибки нет: plus возвращает новый объект, старый не меняется.

Неизменяемый класс: все поля private final; нет методов, меняющих состояние; класс final или с закрытым конструктором, чтобы подкласс не добавил изменяемость; изменяемые компоненты скопированы на входе и не отдаются наружу. Records дают первые пункты бесплатно, но не последний: record с полем List не защищён, пока компактный конструктор не сделает List.copyOf, — это тема Records. Неизменяемые объекты можно свободно передавать, кешировать и делить между потоками без синхронизации; их final-поля видны любому потоку после конструктора по правилам JMM. Цена — новый объект на каждое изменение; для горячих путей с крупными объектами её учитывают, для значений вроде денег, идентификаторов и диапазонов дат она почти всегда оправдана.

Уровни доступа: класс, пакет, модуль

Модификаторы доступа — инструмент, а не цель. Минимальный уровень — лучший: поле private; метод, нужный только соседним классам пакета, — package-private (без модификатора); public — то, что составляет контракт. Пакет — естественная граница: Account, его фабрика и репозиторий в одном пакете могут пользоваться package-private-конструктором, а остальной код видит только публичные операции. Таблица модификаторов — в Classes & Objects.

Слабость пакета в том, что public-класс видят все. В библиотеке платежей служебный Ledger приходится делать public, потому что им пользуется Payments из соседнего пакета, — и тогда им может пользоваться любой клиент. Модули Java 9 добавляют уровень выше: модуль экспортирует только пакеты-контракт. Скрипт modules.sh собирает модуль payments, экспортирующий com.pay.api, и модуль app, который от него зависит:

module payments {
    exports com.pay.api;              // internal не экспортирован
}
// app: import com.pay.internal.Ledger;   — public-класс неэкспортированного пакета
== run app
pay via exported API: 500
deep reflection into payments: InaccessibleObjectException
== run app with --add-opens payments/com.pay.api=app
deep reflection into payments: allowed
== compile app code that imports com.pay.internal
BadMain.java:3: error: package com.pay.internal is not visible

public-класс Ledger из неэкспортированного пакета недоступен при компиляции: package com.pay.internal is not visible. Даже экспорт пакета не открывает его для глубокой рефлексии: setAccessible к приватному полю Payments бросает InaccessibleObjectException. Для этого пакет должен быть открыт — директивой opens в module-info или флагом --add-opens при запуске. Именно поэтому фреймворкам, которые читают приватные поля (Hibernate, Jackson), в модульном приложении открывают пакеты сущностей. На практике многие приложения запускаются с classpath, где всё в безымянном модуле, — тогда границы модулей действуют только для самого JDK.

Где инкапсуляцию обходят и сколько стоят геттеры

== reflection vs final
final field of a class changed via reflection: 1000000
record field: IllegalAccessException

Рефлексия с setAccessible(true) обходит private в коде своего модуля и classpath — и даже final: демо записало новое значение в final-поле обычного класса. Так работает десериализация и часть фреймворков. Для records, скрытых классов и static final-полей запись запрещена — IllegalAccessException. В JDK 26 запись в final-поля через рефлексию начинает выдавать предупреждения (JEP 500, «Prepare to Make Final Mean Final»), и в будущем её закроют по умолчанию. Вывод для своего кода: private защищает от ошибок коллег, а не от злонамеренного кода в том же процессе.

Геттеры и сеттеры. Геттер на неизменяемое значение безвреден и нужен фреймворкам, которые ищут свойства по соглашению JavaBeans: Jackson, JPA, шаблонизаторы. Сеттер на каждое поле — повод спросить, какую операцию он изображает: setStatus(PAID) скорее markPaid(at) с проверкой перехода из Enums. По производительности геттер ничего не стоит: JIT встраивает короткие методы, и обращение компилируется в чтение поля, как разобрано в JIT. «Tell, don't ask»: вместо того чтобы спросить объект о его данных и принять решение снаружи, попросите объект выполнить операцию.

Обратная крайность — инкапсулировать всё. DTO на границе API, записи событий, строки отчётов — это данные без поведения, и прятать их поля за операциями незачем; для них есть records. Инкапсуляция нужна там, где есть инвариант, который можно нарушить.

Если вернуть Collections.unmodifiableList(list), внутренний список защищён.

Это окно на исходный список: менять через него нельзя, но изменения исходного видны. Если исходный список пришёл от вызывающего кода и сохранён без копии, тот может его поменять — в демо в пачку попал p-evil. Нужна копия на входе (List.copyOf).

  • Инкапсуляция — изменение состояния только через операции, держащие инвариант; сеттер на каждое поле её отменяет.
  • Конструктор проверяет вход: объект не рождается в неверном состоянии.
  • Утечки: сохранённая чужая ссылка и отданная внутренняя; защита — копия на входе, неизменяемое представление на выходе.
  • unmodifiableList — окно, copyOf — снимок; копию делают до проверки.
  • Неизменяемость — самая сильная инкапсуляция; изменяемый ключ теряется в HashSet.
  • Модуль скрывает public-классы неэкспортированных пакетов и закрывает глубокую рефлексию без opens.
  • setAccessible обходит private и final обычных классов, но не records.

На собеседовании

Что такое инкапсуляция? Это просто private-поля с геттерами и сеттерами?

Нет. Инкапсуляция — сокрытие состояния за операциями, которые сохраняют инвариант объекта. Если на каждое поле есть сеттер, правило «баланс не меньше нуля» должен помнить каждый вызывающий, и один забывчивый вызов его нарушит. Правильно — операция debit, которая проверяет и меняет состояние в одном месте, и конструктор, который не даёт создать неверный объект.

  • Анемичная модель против богатой: правила в сервисах или в объекте.
  • Tell, don't ask; уровни границ — класс, пакет, модуль.
  • Для DTO без инвариантов инкапсуляция не нужна — records.
Что не так с этим классом? 
public final class Refund {
    private final List<String> paymentIds;
    public Refund(List<String> paymentIds) {
        if (paymentIds.isEmpty()) throw new IllegalArgumentException("empty");
        this.paymentIds = paymentIds;
    }
    public List<String> getPaymentIds() { return paymentIds; }
}

Класс выглядит неизменяемым, но хранит чужой список и отдаёт его наружу. Вызывающий может очистить свой список после конструктора — и инвариант «не пусто» нарушится, а любой получатель геттера может изменить содержимое. Нужно this.paymentIds = List.copyOf(paymentIds) до проверки (if (this.paymentIds.isEmpty())) — тогда и геттер безопасен.

Как сделать класс неизменяемым и зачем?

Все поля private final, нет методов, меняющих состояние, класс final, изменяемые компоненты копируются на входе и не отдаются наружу. Изменение — новый объект. Неизменяемые объекты безопасны как ключи HashMap, их можно кешировать и делить между потоками без синхронизации.

  • JMM: final-поля видны всем потокам после конструктора, если this не утёк.
  • Record не копирует List сам — нужен компактный конструктор.
  • Цена — аллокации; для значений почти всегда оправдана.

Чем Collections.unmodifiableList отличается от List.copyOf?

unmodifiableList — обёртка-окно: менять через неё нельзя, но изменения исходного списка видны. List.copyOf — неизменяемая копия, не связанная с исходным списком. Для защиты состояния от вызывающего кода нужна копия.

  • copyOf не копирует уже неизменяемый список и запрещает null.
  • Копию делают до проверки, иначе TOCTOU.

Как модули Java усиливают инкапсуляцию?

Модуль экспортирует только перечисленные пакеты. Public-класс из неэкспортированного пакета недоступен другим модулям при компиляции. Глубокая рефлексия к приватным членам требует, чтобы пакет был открыт через opens или --add-opens. Так JDK закрыл свои внутренние API, например String.value.

  • На classpath всё в безымянном модуле — границы действуют только для JDK.
  • JEP 500: запись в final через рефлексию будет закрыта.

  • The State of the Module System, JEP 403: Strongly Encapsulate JDK Internals.
  • JEP 500: Prepare to Make Final Mean Final.
  • Martin Fowler, Anemic Domain Model, Tell Don't Ask.
