Event-driven, CQRS, Event Sourcing

Три идеи, которые часто смешивают. Событийная архитектура: сервис публикует факт «заказ оплачен», а не вызывает каждого, кому это интересно, — новые потребители подключаются без изменения источника. CQRS: модель для записи и модель для чтения разделены, и чтение обслуживает отдельная проекция, которая догоняет запись с задержкой. Event sourcing: источник истины — не текущее состояние, а журнал событий, и состояние вычисляется свёрткой. Event sourcing даёт полную историю, состояние на любой момент и новые проекции из старых событий без миграции. Цена — оптимистичная проверка версии потока при записи, eventual consistency чтения, эволюция схем событий и невозможность просто удалить данные.

Сервис заказов знает обо всех, кому интересна оплата

После оплаты заказа сервис заказов синхронно вызывает склад, уведомления, программу лояльности, аналитику и антифрод. Каждый новый потребитель — изменение и релиз сервиса заказов; недоступность программы лояльности ломает оплату; задержки складываются, как в Monolith & Microservices. Если вместо вызовов публиковать событие «заказ оплачен», сервис заказов перестаёт зависеть от потребителей: склад, уведомления и аналитика подписываются сами.

Тема разбирает события и команды, CQRS с асинхронной проекцией и event sourcing на журнале в PostgreSQL. Надёжная публикация событий вместе с изменением в базе — в Transactional Outbox, хореография саг — в Distributed Transactions, доставка через брокер — в Kafka Delivery. Демо EventStoreDemo.java хранит события заказов в одной таблице PostgreSQL 17.

Событие — факт в прошлом, команда — просьба

КомандаСобытие
ИмяShipOrder — повелительноеOrderShipped — прошедшее время
АдресатОдин исполнительЛюбое число подписчиков, источник их не знает
Можно отказатьДа: проверка правил, ошибкаНет: это уже произошло
СвязностьОтправитель знает, кто сделаетИсточник не знает, кто отреагирует

Событие бывает тонким — «заказ 42 оплачен», и подписчик сам запрашивает подробности, — или толстым, с данными, нужными потребителям (event-carried state transfer): тогда потребитель не ходит к источнику и может держать у себя копию нужных полей. Толстые события снижают связность во время работы, но превращают формат события в публичный контракт, который нельзя менять как угодно. Событийная архитектура меняет и способ отладки: цепочку «оплата → склад → уведомление» больше не видно в коде одного сервиса, её восстанавливают по трассировке и журналам событий.

Event sourcing: состояние — свёртка журнала событий

// Состояние заказа восстанавливается из событий; само по себе нигде не хранится.
record Order(String status, long paid, long refunded) {
    Order apply(Event e) {
        return switch (e.type()) {
            case "OrderPlaced" -> new Order("PLACED", paid, refunded);
            case "PaymentCaptured" -> new Order("PAID", paid + e.amount(), refunded);
            case "ItemRefunded" -> new Order(status, paid, refunded + e.amount());
            case "OrderShipped" -> new Order("SHIPPED", paid, refunded);
            default -> this;
        };
    }
}
== state is a fold of events
   v0 OrderPlaced      -> Order[status=PLACED, paid=0, refunded=0]
   v1 PaymentCaptured  -> Order[status=PAID, paid=12000, refunded=0]
   v2 ItemRefunded     -> Order[status=PAID, paid=12000, refunded=3000]

В обычной модели строка заказа хранит текущие значения, и каждое изменение затирает предыдущее. В event sourcing хранится только журнал: что произошло и в каком порядке. Текущее состояние — результат применения всех событий потока к пустому состоянию; состояние на любой момент — применение событий до этого момента. Так устроены журналы проводок в бухгалтерии, как в Digital Wallet, и журнал изменений базы данных. Если у потока тысячи событий, хранят снимок состояния на некоторой версии и применяют только более поздние события.

create table event(
  position bigserial primary key,           -- глобальный порядок для проекций
  stream text not null, version int not null,
  type text not null, amount bigint not null default 0,
  unique (stream, version));                -- оптимистичная проверка версии
== two commands on order-1 at version 3 at the same time
   appended 1, conflicts 1 (23505 on unique (stream, version))

Две команды одновременно прочитали поток заказа — 3 события — и решили добавить своё событие с версией 3: одна — возврат, другая — отгрузку. Уникальный индекс (stream, version) пропустил одну, вторая получила нарушение уникальности 23505. Проигравшая команда перечитывает поток и решает заново: возможно, после возврата отгрузка уже недопустима. Это оптимистичная блокировка на уровне потока — без блокировок при чтении, с конфликтом только при настоящей гонке за один агрегат. Какая из двух команд выиграет, решает планировщик; итог «одна добавлена, одна отклонена» повторяется.

CQRS: проекция для чтения догоняет журнал

== read model is updated asynchronously
   view before projector: missing
   projector applied 5 events: PAID, paid 12000
   after OrderShipped:    PAID, paid 12000  (stale until next run)
   next projector run:    SHIPPED, paid 12000

CQRS разделяет модель записи (агрегаты, проверка правил, журнал) и модели чтения (таблицы под конкретные экраны и запросы). Каждую модель чтения можно хранить там, где её удобно читать: в PostgreSQL, Elasticsearch, Redis. Цена — eventual consistency: сразу после команды чтение может вернуть старое состояние. Интерфейс должен это учитывать — показывать результат команды из её ответа, а не перечитывать представление, — тот же read-your-writes, что в CAP & Consistency. CQRS не требует event sourcing: проекции можно строить и из обычной базы через outbox или CDC.

== new read model built by replaying old events
   order-1 refunded 3000 in 1 refund(s)

Главная выгода журнала — новые вопросы к старым данным. Понадобилась статистика возвратов — новая проекция строится проходом по всем событиям, включая события годовой давности, без миграции и без потери истории: в обычной модели, где хранится только итоговое состояние, информации о прошлых возвратах могло не остаться вовсе.

Чем платят за event sourcing

Порядок для проекций. Демо читает события по position из bigserial. Это работает в одном потоке записи, но при конкурентных транзакциях значение последовательности выдаётся до коммита: транзакция с позицией 101 может закоммититься позже транзакции с позицией 102. Если проектор успел прочитать 102 и сохранить её как позицию, событие 101 он не увидит никогда. Решения — читать только события старше минимального активного идентификатора транзакции (pg_snapshot_xmin), сериализовать запись в журнал или публиковать события через логическую репликацию, которая выдаёт их в порядке коммита.

Эволюция схем. События неизменяемы и живут годами, а код меняется. Старые версии событий читают с апкастингом — преобразованием старого формата в новый при чтении, — а не переписывают журнал. Удалять поля из события опасно: старые проекции на них опираются.

Удаление данных. Требование удалить персональные данные противоречит неизменяемому журналу. Персональные данные не кладут в события, а хранят отдельно по ссылке, или шифруют ключом пользователя и удаляют ключ (crypto-shredding).

Сложность. Event sourcing оправдан там, где история — часть предметной области: деньги, учёт, аудит, процессы с большим числом состояний. Для справочников и CRUD он добавляет сложность без пользы. Чаще всего в системе event sourcing — только у одного-двух агрегатов, а остальное хранится обычно.

Event sourcing и CQRS — одно и то же, и одно без другого не бывает.

CQRS — разделение моделей записи и чтения; проекции можно строить из обычной базы через outbox или CDC. Event sourcing — хранение журнала как источника истины; читать можно и свёрткой, как в первом опыте демо. Вместе они часто встречаются, потому что журнал удобно проецировать.

  • Событие — факт в прошлом для любого числа подписчиков; команда — просьба к одному исполнителю.
  • Event sourcing: состояние — свёртка событий; снимки сокращают свёртку.
  • Оптимистичная проверка: unique (stream, version) — из двух одновременных команд одна добавлена, другая получила 23505.
  • CQRS: проекция догоняет журнал; позиция и изменения представления — в одной транзакции; чтение видит старое до следующего прогона.
  • Новая проекция строится из старых событий без миграции.
  • Цена: порядок коммитов для проекций, эволюция схем, удаление данных, сложность.

На собеседовании

Что такое event sourcing и когда он оправдан?

Хранение журнала событий как источника истины вместо текущего состояния. Состояние — свёртка событий потока, состояние на любой момент — свёртка событий до него. Даёт полную историю и аудит, новые проекции из старых событий, разбор инцидентов. Оправдан, где история — часть предметной области: деньги, учёт, сложные процессы. Для CRUD — лишняя сложность.

  • Конкуренция — оптимистичная проверка версии потока при добавлении.
  • Снимки, апкастинг старых версий событий, crypto-shredding для удаления данных.

Что такое CQRS и какие у него последствия?

Разделение модели записи и моделей чтения. Команды проверяют правила и меняют состояние, запросы читают из проекций, построенных под конкретные экраны, возможно в другом хранилище. Проекции обновляются асинхронно, поэтому чтение может отставать; интерфейс и API должны это учитывать.

  • Позиция проектора и изменения представления — в одной транзакции, иначе повтор применит событие дважды.
  • Проекции можно перестроить с нуля, если журнал полный.
Почему проекция иногда пропускает события? 
-- проектор раз в секунду
select * from event where position > :last order by position limit 1000;
-- после обработки: :last = max(position) из выборки
-- запись: insert into event(...) в разных транзакциях из 20 потоков; position bigserial

Значения bigserial выдаются в момент вставки, а видны событию после коммита. Транзакция с позицией 101 может закоммититься после транзакции с позицией 102; если проектор прочитал 102 и запомнил её, событие 101 станет видно уже ниже сохранённой позиции и будет пропущено навсегда. Нужно читать только события, чьи транзакции точно завершены (граница pg_snapshot_xmin), сериализовать запись или брать события из логической репликации в порядке коммита.

Чем событие отличается от команды и что положить в событие?

Команда — просьба к одному исполнителю, её можно отклонить. Событие — факт, который уже произошёл, для любого числа подписчиков, источник их не знает. Тонкое событие несёт идентификатор, и подписчик запрашивает детали; толстое — нужные данные, и подписчик независим от источника во время работы, но формат события становится контрактом.

  • Публиковать события вместе с изменением в базе — через outbox.
  • Версионировать события, совместимо расширять, не удалять поля.
