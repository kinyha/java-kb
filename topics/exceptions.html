Exceptions

Списание сверх лимита «прошло успешно» — исключение съел finally

Метод списания бросает исключение, если сумма больше лимита. В finally кто-то добавил запись в аудит и «гарантированный ответ клиенту»:

public class FinallyReturn {
    static boolean charge(long amount) {
        try {
            if (amount > 10_000) throw new IllegalStateException("превышен лимит");   // списание не прошло
            return true;
        } finally {
            System.out.println("  аудит: попытка списания " + amount);
            return true;                                                  // «всегда отвечаем клиенту»
        }
    }

    static int counter() {
        int x = 1;
        try {
            return x;                                                     // значение возврата уже вычислено
        } finally {
            x = 100;                                                      // не влияет на результат
        }
    }

    public static void main(String[] args) {
        System.out.println("списание 50 000: " + charge(50_000));
        System.out.println("counter() = " + counter());
    }
}
  аудит: попытка списания 50000
списание 50 000: true
counter() = 1

Исключение исчезло без следа: return в finally отменяет и исключение, и возврат из try. Вызывающий получил true. javac умеет об этом предупредить, но только с флагом -Xlint:finally:

$ javac -Xlint:finally FinallyReturn.java
FinallyReturn.java:9: warning: [finally] finally clause cannot complete normally

Вторая функция показывает обратное: присваивание в finally не меняет уже вычисленное значение return x. Правило — в finally только освобождение ресурсов, без return и без исключений.

В этой теме — иерархия исключений, checked и unchecked, try-with-resources и подавленные исключения, сохранение причины при переводе исключений, стоимость исключений и то, как JIT «теряет» stack trace. И главное практическое правило: где исключения ловить.

Всё, что бросается, — Throwable, и компилятор проверяет только одну ветку

ВеткаЧто означаетЧто с ней делать
Errorсбой JVM или среды: нет памяти, переполнен стек, не найден классне ловить; процесс обычно не в состоянии продолжать (тема Diagnostics)

Checked-исключения — особенность Java, и их спорность видна в лямбдах. Функциональные интерфейсы вроде Consumer не объявляют throws, поэтому метод с checked-исключением внутри стрима или forEach не компилируется:

import java.nio.file.*;
import java.util.*;

public class Statements {
    public static void main(String[] args) {
        List<Path> files = List.of(Path.of("sber.csv"), Path.of("vtb.csv"));
        files.forEach(f -> System.out.println(Files.readString(f)));   // readString бросает IOException
    }
}
Statements.java:7: error: unreported exception IOException; must be caught or declared to be thrown
        files.forEach(f -> System.out.println(Files.readString(f)));   // readString бросает IOException
                                                              ^

Приходится ловить внутри лямбды и оборачивать в unchecked — для ввода-вывода в JDK есть UncheckedIOException. Поэтому современные библиотеки, включая Spring (DataAccessException), бросают только unchecked. Свои исключения в прикладном коде обычно тоже делают unchecked, наследуя от RuntimeException.

try-with-resources закрывает ресурсы и не теряет исходную ошибку

Классический try/finally с закрытием ресурса в finally имеет изъян: если бросили и тело, и close(), исключение из finally заменяет исходное:

public class Suppressed {
    static class BankConnection implements AutoCloseable {
        void transfer() { throw new IllegalStateException("перевод отклонён банком"); }
        @Override public void close() { throw new IllegalStateException("соединение оборвалось при закрытии"); }
    }

    static void manual() {
        BankConnection c = new BankConnection();
        try {
            c.transfer();
        } finally {
            c.close();                                                   // исключение из finally заменяет исходное
        }
    }

    static void withResources() {
        try (BankConnection c = new BankConnection()) {
            c.transfer();
        }                                                                // close() вызван автоматически
    }

    public static void main(String[] args) {
        try { manual(); } catch (Exception e) {
            System.out.println("try/finally:        " + e.getMessage() + ", suppressed: " + e.getSuppressed().length);
        }
        try { withResources(); } catch (Exception e) {
            System.out.println("try-with-resources: " + e.getMessage());
            for (Throwable s : e.getSuppressed()) System.out.println("  suppressed:       " + s.getMessage());
        }
    }
}
try/finally:        соединение оборвалось при закрытии, suppressed: 0
try-with-resources: перевод отклонён банком
  suppressed:       соединение оборвалось при закрытии

После try/finally в логе окажется «соединение оборвалось», а настоящая причина — отказ банка — потеряна. try-with-resources (Java 7) бросает исходное исключение, а ошибку close() прикрепляет к нему как подавленную (getSuppressed()). В stack trace она печатается строкой Suppressed:.

  • Ресурс — любой AutoCloseable: потоки, соединения, ExecutorService с Java 19 (тема Executors), свои классы.
  • Несколько ресурсов закрываются в обратном порядке объявления, и каждый закрывается, даже если предыдущий бросил.
  • close() вызывается до catch и finally этого же оператора.
  • С Java 9 можно указать уже существующую effectively final переменную: try (connection) { … }.

Переводя исключение на язык своего слоя, передавайте причину

Слою бизнес-логики не нужно знать про FileNotFoundException или SQLException. Их переводят в исключение своего уровня — exception translation. Главное при этом — не потерять исходную ошибку:

import java.io.*;

public class Translate {
    static class PaymentException extends RuntimeException {             // исключение своего слоя
        PaymentException(String message, Throwable cause) { super(message, cause); }
        PaymentException(String message) { super(message); }
    }

    static String readStatement(String bank) throws IOException {
        throw new FileNotFoundException("/data/" + bank + ".csv (No such file or directory)");
    }

    static void importLost(String bank) {
        try { readStatement(bank); }
        catch (IOException e) { throw new PaymentException("не удалось загрузить выписку " + bank); }        // причина потеряна
    }

    static void importKept(String bank) {
        try { readStatement(bank); }
        catch (IOException e) { throw new PaymentException("не удалось загрузить выписку " + bank, e); }     // причина сохранена
    }

    public static void main(String[] args) {
        try { importLost("sber"); } catch (PaymentException e) {
            System.out.println("без cause: " + e.getMessage() + " | причина: " + e.getCause());
        }
        try { importKept("sber"); } catch (PaymentException e) {
            System.out.println("с cause:   " + e.getMessage() + " | причина: " + e.getCause());
        }
    }
}
без cause: не удалось загрузить выписку sber | причина: null
с cause:   не удалось загрузить выписку sber | причина: java.io.FileNotFoundException: /data/sber.csv (No such file or directory)

Без cause на дежурстве будут знать только, что «не удалось загрузить выписку», но не почему: нет файла, нет прав или битая кодировка. С cause полный stack trace содержит обе части, связанные строкой Caused by:. Свои исключения всегда объявляют с конструктором (String message, Throwable cause).

Когда своё исключение действительно нужно: если вызывающий должен различать эту ситуацию — «недостаточно средств» и «счёт заблокирован» дают разные ответы клиенту. В остальных случаях хватает стандартных: IllegalArgumentException для неверного аргумента, IllegalStateException для недопустимого состояния, UnsupportedOperationException.

Исключение дорого из-за стека, а JIT может этот стек выбросить

Конструктор Throwable вызывает fillInStackTrace — обходит стек и сохраняет его. Цена растёт с глубиной. Сравним обычное исключение и лёгкое — без стека, через защищённый конструктор (message, cause, enableSuppression, writableStackTrace):

public class Cost {
    static class NotFound extends RuntimeException {                     // обычное: собирает стек
        NotFound(String m) { super(m); }
    }
    static class LightNotFound extends RuntimeException {                // без стека: для потока управления
        LightNotFound(String m) { super(m, null, false, false); }
    }

    static int depth(int n, boolean light) {                            // исключение на глубине n кадров
        if (n == 0) throw light ? new LightNotFound("нет платежа") : new NotFound("нет платежа");
        return depth(n - 1, light) + 1;
    }

    static long run(boolean light, int stack) {
        long start = System.nanoTime();
        for (int i = 0; i < 200_000; i++) {
            try { depth(stack, light); } catch (RuntimeException e) { }
        }
        return (System.nanoTime() - start) / 200_000;
    }

    public static void main(String[] args) {
        run(false, 50); run(true, 50);                                    // прогрев
        for (int stack : new int[]{10, 100})
            System.out.printf("глубина %3d: со стеком %,5d нс, без стека %,4d нс на исключение%n", stack, run(false, stack), run(true, stack));
    }
}
глубина  10: со стеком   775 нс, без стека  430 нс на исключение
глубина 100: со стеком 5,680 нс, без стека 4,167 нс на исключение

Сбор стека на глубине 100 стоит около 1,5 мкс, а сама раскрутка стека через 100 кадров — ещё 4 мкс. Для ошибок это неважно. Для штатного потока управления — «платёж не найден» тысячи раз в секунду — это уже заметно, и там лучше возвращать Optional или результат-объект. В типичном стеке Spring глубина запросов около сотни кадров.

Обратная сторона оптимизации — пропадающий stack trace. Если одно и то же место часто бросает NPE, ArithmeticException или ArrayIndexOutOfBoundsException, C2 перестаёт создавать исключение и бросает заранее созданное, без сообщения и без стека:

public class FastThrow {
    record Payment(String currency) { }

    static int codeLength(Payment p) {
        return p.currency().length();                                   // NPE, если валюта не заполнена
    }

    public static void main(String[] args) {
        Payment broken = new Payment(null);
        for (int i = 1; i <= 200_000; i++) {
            try {
                codeLength(broken);
            } catch (NullPointerException e) {
                if (i == 1 || i == 200_000)
                    System.out.printf("NPE №%,d: message = %s, кадров стека = %d%n", i, e.getMessage(), e.getStackTrace().length);
            }
        }
    }
}
$ java FastThrow
NPE №1: message = Cannot invoke "String.length()" because the return value of "FastThrow$Payment.currency()" is null, кадров стека = 2
NPE №200,000: message = null, кадров стека = 0
$ java -XX:-OmitStackTraceInFastThrow FastThrow
NPE №1: message = Cannot invoke "String.length()" because the return value of "FastThrow$Payment.currency()" is null, кадров стека = 2
NPE №200,000: message = Cannot invoke "String.length()" because the return value of "FastThrow$Payment.currency()" is null, кадров стека = 2

В проде это выглядит так: в логах тысячи строк java.lang.NullPointerException без единого кадра, и непонятно, где ошибка. Полный стек был только у первых исключений, до компиляции метода C2. Их ищут в начале лога после старта или отключают оптимизацию флагом -XX:-OmitStackTraceInFastThrow.

Ловят там, где могут что-то сделать, а превращают в ответ — на границе

Исключение ловят в одном из двух мест:

  • Там, где можно восстановиться: повторить запрос, взять запасное значение из кеша, перевести в исключение своего слоя с причиной.
  • На границе приложения: в обработчике HTTP-запроса (@ControllerAdvice в Spring), в слушателе сообщений, в фоновой задаче. Там исключение логируют один раз со стеком и превращают в ответ: код 4xx или 5xx, сообщение в DLQ, метрику.

Всё остальное — антипаттерны:

АнтипаттернЧем плох
catch (Exception e) { }ошибка исчезает, система продолжает работать в неверном состоянии
catch (Exception e) { log.error(e); throw e; } на каждом уровнеодна ошибка — пять записей в логе, непонятно, где она произошла

Checked-исключения надёжнее: компилятор заставляет их обработать.

Компилятор заставляет их упомянуть, а не обработать. Чаще всего checked-исключение ловят там, где сделать с ним нечего, и глушат пустым catch или оборачивают. Надёжность даёт продуманное место обработки на границе, а не проверка компилятора.

  • Throwable → Error (сбои JVM, не ловить) и Exception. Checked — всё под Exception, кроме RuntimeException.
  • return или throw в finally молча отменяет исходное исключение. javac предупреждает с -Xlint:finally.
  • try-with-resources закрывает ресурсы в обратном порядке и сохраняет исходную ошибку, прикрепляя ошибку close() как suppressed.
  • При переводе исключений передают cause, иначе причина теряется.
  • Исключение со стеком стоит микросекунды на глубоком стеке. Для штатных ситуаций — Optional или результат-объект.
  • После частых NPE C2 бросает исключение без сообщения и стека. Лечится флагом -XX:-OmitStackTraceInFastThrow или поиском первых исключений в логе.
  • Ловят там, где можно восстановиться, или на границе — один раз, с логом и ответом.

На собеседовании

Чем checked-исключения отличаются от unchecked?

Checked — наследники Exception, кроме RuntimeException. Компилятор требует поймать их или объявить в throws. Это ожидаемые сбои внешнего мира: файл, сеть, база. Unchecked — RuntimeException и Error, компилятор их не проверяет. RuntimeException обычно означает ошибку в программе или нарушенный контракт, Error — сбой JVM.

  • Checked-исключения плохо сочетаются с лямбдами: функциональные интерфейсы не объявляют throws. Поэтому Spring и современные библиотеки используют unchecked, а JDK предлагает UncheckedIOException.
  • Проверка на уровне компилятора: в байткоде различий нет, и Kotlin, например, checked-исключения не требует.

Всегда ли выполняется finally? Что будет, если в finally есть return?

finally выполняется при любом выходе из try: нормальном, через return, break или исключение. Не выполнится, если JVM остановилась — System.exit, kill -9, падение процесса — или если поток завис навсегда внутри try. return в finally отменяет и исключение, и значение из try: исключение пропадает без следа.

int x = 1; try { return x; } finally { x = 100; } — что вернёт метод?

1. Выражение return x вычислено до выполнения finally, и значение сохранено. Присваивание в finally меняет только переменную. Проверено запуском.

try { charge(); return true; } finally { audit(); return true; } — что не так?

return в finally глушит исключение из charge(): вызывающий получит true даже при отказе. В замере урока списание сверх лимита «прошло». return из finally убрать; javac покажет такие места с -Xlint:finally.

Как работает try-with-resources? Что такое suppressed-исключения?

Ресурсы, объявленные в скобках, — любые AutoCloseable — закрываются автоматически после блока, в обратном порядке объявления, до catch и finally. Если бросили и тело, и close(), наружу уходит исключение тела, а исключение close() добавляется к нему как suppressed (getSuppressed()). В ручном try/finally исключение из close() заменило бы исходное, и причина потерялась бы.

Дорого ли бросать исключения? Почему в логах бывают NPE без stack trace?

Основная цена — сбор стека в конструкторе и раскрутка стека при броске: в замере урока около 0,8 мкс на глубине 10 и 5,7 мкс на глубине 100. Для ошибок это неважно, для штатного потока управления в горячем коде — заметно. Там возвращают Optional или результат-объект, либо используют исключение без стека (конструктор с writableStackTrace = false).

  • Если одно место часто бросает NPE или ArithmeticException, C2 заменяет его заранее созданным исключением без сообщения и стека. Флаг -XX:-OmitStackTraceInFastThrow отключает оптимизацию, а полный стек есть у первых исключений после старта.

Где и как правильно обрабатывать исключения?

Ловить там, где можно что-то сделать: повторить, подставить запасное значение, перевести в исключение своего слоя с сохранением причины. Всё остальное пробрасывать до границы — обработчика HTTP-запроса, слушателя сообщений, фоновой задачи. Там исключение логируют один раз со стеком и превращают в ответ. Не глушить пустым catch, не логировать на каждом уровне, не ловить Throwable, не терять cause.

catch (IOException e) { throw new ImportException("ошибка импорта: " + e.getMessage()); } — что не так?

Причина потеряна: у нового исключения нет cause, поэтому пропали тип исходной ошибки и её стек. В замере урока getCause() вернул null. Нужно new ImportException("ошибка импорта", e).
