Concurrency: Executors

Пул «от 2 до 10 потоков» под нагрузкой так и работает двумя

Сервис ходит в банк через пул: два потока в обычное время, до десяти под нагрузкой. Так задумано. Приходит всплеск из 100 запросов, каждый ждёт банк полсекунды. Сравним пул с неограниченной очередью и с очередью на 20 задач:

import java.util.concurrent.*;

public class MaxIgnored {
    static void load(String name, ThreadPoolExecutor pool) throws Exception {
        int rejected = 0;
        for (int i = 0; i < 100; i++) {
            try {
                pool.execute(() -> { try { Thread.sleep(500); } catch (InterruptedException e) { } });  // запрос к банку
            } catch (RejectedExecutionException e) {
                rejected++;
            }
        }
        System.out.printf("%-26s потоков %2d, в очереди %2d, отклонено %2d%n",
            name, pool.getPoolSize(), pool.getQueue().size(), rejected);
        pool.shutdownNow();
    }

    public static void main(String[] args) throws Exception {
        // «2 потока обычно, до 10 под нагрузкой» — так задумано
        load("LinkedBlockingQueue():", new ThreadPoolExecutor(2, 10, 60, TimeUnit.SECONDS, new LinkedBlockingQueue<>()));
        load("ArrayBlockingQueue(20):", new ThreadPoolExecutor(2, 10, 60, TimeUnit.SECONDS, new ArrayBlockingQueue<>(20)));
    }
}
LinkedBlockingQueue():     потоков  2, в очереди 98, отклонено  0
ArrayBlockingQueue(20):    потоков 10, в очереди 20, отклонено 70

С неограниченной очередью пул так и остался на двух потоках, а 98 запросов встали в очередь: последний дождётся ответа через 25 секунд. maximumPoolSize = 10 не сработал ни разу. С ограниченной очередью пул вырос до десяти, но 70 запросов получили отказ. Оба результата удивляют, пока не знаешь порядок, в котором ThreadPoolExecutor принимает решения.

В этой теме — параметры ThreadPoolExecutor и этот порядок, ловушки фабрик Executors, политики отказа, как выбрать размер пула, куда пропадают исключения задач, как остановить пул и почему нельзя блокироваться в ForkJoinPool.commonPool().

Почему очередь раньше новых потоков? Пул рассчитан на короткие всплески: очередь сглаживает их без затрат на создание потоков, а лишние потоки нужны, только если очередь не справилась. Как newCachedThreadPool ведёт себя под всплеском из 10 000 задач, каждая из которых ждёт банк секунду:

import java.util.concurrent.*;

public class Cached {
    public static void main(String[] args) throws Exception {
        ThreadPoolExecutor pool = (ThreadPoolExecutor) Executors.newCachedThreadPool();
        long start = System.nanoTime();
        for (int i = 0; i < 10_000; i++) {
            pool.execute(() -> { try { Thread.sleep(1_000); } catch (InterruptedException e) { } });  // банк отвечает секунду
        }
        System.out.printf("за %d мс создано потоков: %,d%n", (System.nanoTime() - start) / 1_000_000, pool.getPoolSize());
        pool.shutdown();
        pool.awaitTermination(1, TimeUnit.MINUTES);
        System.out.println("максимум одновременно: " + pool.getLargestPoolSize());
    }
}

максимум одновременно: 10000

Десять тысяч потоков ОС за секунду. По замеру из темы Threads это около 700 МБ памяти одних стеков. А банк получил 10 000 одновременных запросов. В проде такой пул превращает задержку внешней системы в падение сервиса.

Поэтому для серверного кода пул создают явно: new ThreadPoolExecutor(...) с ограниченной очередью, осознанной политикой отказа и фабрикой потоков, которая даёт им имена. Имена вроде bank-client-3 вместо pool-7-thread-3 окупаются при первом же чтении дампа потоков.

Политика отказа решает, что станет с лишней задачей, — и одна из них теряет её молча

Четыре встроенные политики на пуле из двух потоков с очередью на три задачи. Двадцать задач по 50 мс приходят сразу:

import java.util.concurrent.*;
import java.util.concurrent.atomic.AtomicInteger;

public class Policies {
    static void run(String name, RejectedExecutionHandler policy) throws Exception {
        AtomicInteger done = new AtomicInteger(), onCaller = new AtomicInteger();
        ThreadPoolExecutor pool = new ThreadPoolExecutor(2, 2, 0, TimeUnit.SECONDS, new ArrayBlockingQueue<>(3), policy);
        Thread caller = Thread.currentThread();
        int exceptions = 0;
        long start = System.nanoTime();
        for (int i = 0; i < 20; i++) {
            try {
                pool.execute(() -> {
                    if (Thread.currentThread() == caller) onCaller.incrementAndGet();
                    try { Thread.sleep(50); } catch (InterruptedException e) { }
                    done.incrementAndGet();
                });
            } catch (RejectedExecutionException e) {
                exceptions++;
            }
        }
        pool.shutdown();
        pool.awaitTermination(10, TimeUnit.SECONDS);
        System.out.printf("%-20s выполнено %2d из 20, исключений %2d, в потоке вызывающего %2d, %4d мс%n",
            name, done.get(), exceptions, onCaller.get(), (System.nanoTime() - start) / 1_000_000);
    }

    public static void main(String[] args) throws Exception {
        run("AbortPolicy", new ThreadPoolExecutor.AbortPolicy());               // по умолчанию
        run("CallerRunsPolicy", new ThreadPoolExecutor.CallerRunsPolicy());
        run("DiscardPolicy", new ThreadPoolExecutor.DiscardPolicy());
        run("DiscardOldestPolicy", new ThreadPoolExecutor.DiscardOldestPolicy());
    }
}
AbortPolicy          выполнено  5 из 20, исключений 15, в потоке вызывающего  0,  164 мс
CallerRunsPolicy     выполнено 20 из 20, исключений  0, в потоке вызывающего  6,  383 мс
DiscardPolicy        выполнено  5 из 20, исключений  0, в потоке вызывающего  0,  159 мс
DiscardOldestPolicy  выполнено  5 из 20, исключений  0, в потоке вызывающего  0,  157 мс
  • AbortPolicy (по умолчанию) бросает RejectedExecutionException. Вызывающий узнаёт об отказе и может вернуть клиенту 503.
  • CallerRunsPolicy выполняет задачу в потоке вызывающего. Все 20 выполнены, 6 из них — самим вызывающим, и пока он их выполнял, новых задач не подавал. Получается естественное противодавление: вход замедляется до скорости обработки.
  • DiscardPolicy молча выбрасывает задачу: 15 из 20 пропали без единого следа. Для платежей — худший выбор.
  • DiscardOldestPolicy выбрасывает самую старую задачу из очереди и ставит новую. Годится для «важно только последнее значение», например обновления котировок.

Своя политика — это реализация RejectedExecutionHandler: записать метрику и лог, сохранить задачу в хранилище для повтора, вернуть понятную ошибку.

Для вычислений хватает пула по числу ядер, для ожидания нужно больше

Размер пула зависит от того, что делают задачи. Одинаковый объём работы — 720 задач — на пулах разного размера, 18 ядер:

import java.util.*;
import java.util.concurrent.*;

public class Sizing {
    static double cpuTask() {                                    // ~2 мс чистых вычислений
        double x = 1;
        for (int i = 0; i < 2_000_000; i++) x = x * 1.0000001 + 1e-9;
        return x;
    }

    static long run(int threads, Callable<Object> task, int count) throws Exception {
        ExecutorService pool = Executors.newFixedThreadPool(threads);
        long start = System.nanoTime();
        for (Future<Object> f : pool.invokeAll(Collections.nCopies(count, task))) f.get();
        pool.shutdown();
        return (System.nanoTime() - start) / 1_000_000;
    }

    public static void main(String[] args) throws Exception {
        System.out.println("ядер: " + Runtime.getRuntime().availableProcessors());
        run(18, Sizing::cpuTask, 200);                              // прогрев
        System.out.print("CPU-задачи (720 шт.):");
        for (int t : new int[]{1, 4, 9, 18, 36, 144})
            System.out.printf("  %d → %d мс", t, run(t, Sizing::cpuTask, 720));
        System.out.println();
        System.out.print("IO-задачи по 20 мс (720 шт.):");
        for (int t : new int[]{1, 18, 36, 144, 720})
            System.out.printf("  %d → %d мс", t, run(t, () -> { Thread.sleep(20); return null; }, 720));
        System.out.println();
    }
}
ядер: 18
CPU-задачи (720 шт.):  1 → 1760 мс  4 → 448 мс  9 → 206 мс  18 → 113 мс  36 → 111 мс  144 → 113 мс
IO-задачи по 20 мс (720 шт.):  1 → 17307 мс  18 → 947 мс  36 → 478 мс  144 → 124 мс  720 → 48 мс

Вычисления ускоряются до 18 потоков — по числу ядер — и дальше не ускоряются: ядер больше нет. Задачи, которые ждут, ускоряются с каждым новым потоком: ожидающий поток ядро не занимает. Классическая оценка из Java Concurrency in Practice:

потоков ≈ ядер × (1 + время ожидания / время вычислений)

Для сервиса, который 90 мс ждёт базу и 10 мс считает, на 8 ядрах это 8 × (1 + 9) = 80 потоков. Формула даёт стартовую точку, а не ответ. Реальный предел часто ставит не CPU, а внешний ресурс. Пул из 200 потоков бессмыслен перед пулом соединений к базе на 20: 180 потоков будут ждать соединение. Размеры связанных пулов согласуют между собой и проверяют нагрузочным тестом.

В контейнере availableProcessors() возвращает лимит CPU пода, а не число ядер машины. Пул, посчитанный по нему, автоматически подстраивается под лимиты — как и эргономика JVM из темы Choosing a Collector.

submit() прячет исключение в Future, а незакрытый пул не даёт JVM завершиться

Одна и та же ошибка в задаче, отправленной через submit и через execute:

import java.util.concurrent.*;

public class Lost {
    public static void main(String[] args) throws Exception {
        ExecutorService pool = Executors.newFixedThreadPool(1);
        pool.submit(() -> { throw new IllegalStateException("submit: платёж не проведён"); });  // Future никто не спросил
        pool.execute(() -> { throw new IllegalStateException("execute: платёж не проведён"); });
        pool.shutdown();
        pool.awaitTermination(1, TimeUnit.SECONDS);
        System.out.println("пул завершён");
    }
}
Exception in thread "pool-1-thread-1" java.lang.IllegalStateException: execute: платёж не проведён
	at Lost.lambda$main$1(Lost.java:7)
	at java.base/java.util.concurrent.ThreadPoolExecutor.runWorker(ThreadPoolExecutor.java:1144)
	...
пул завершён

Ошибки из submit нет нигде: она лежит в Future, который никто не спросил. execute доводит исключение до обработчика потока, и оно хотя бы попадает в stderr. Рабочий поток при этом умирает, и пул создаёт новый. Правила: результат submit всегда проверяют через get(), а задачи, которые запускают «и забывают», оборачивают в try/catch с логированием. Централизованно это делает переопределённый afterExecute в своём ThreadPoolExecutor.

Остановка пула:

  • shutdown() — больше не принимать задачи, но выполнить уже принятые, включая очередь.
  • shutdownNow() — прервать работающие задачи через interrupt() и вернуть список невыполненных из очереди. Задача, которая глотает прерывание, не остановится (тема Threads).
  • awaitTermination(timeout) — дождаться завершения. Стандартная последовательность: shutdown, ожидание, при таймауте — shutdownNow.

Потоки пула по умолчанию не daemon, поэтому забытый пул не даёт JVM завершиться. С Java 19 ExecutorService реализует AutoCloseable, и close() делает shutdown и ждёт все задачи:

import java.util.concurrent.*;

public class Close {
    public static void main(String[] args) {
        long start = System.nanoTime();
        try (ExecutorService pool = Executors.newFixedThreadPool(4)) {   // Java 19+: ExecutorService — AutoCloseable
            for (int i = 0; i < 8; i++) pool.submit(() -> { Thread.sleep(100); return null; });
        }                                                                // close(): shutdown() и ожидание всех задач
        System.out.printf("все задачи выполнены до выхода из try: %d мс%n", (System.nanoTime() - start) / 1_000_000);
    }
}
все задачи выполнены до выхода из try: 213 мс

Восемь задач по 100 мс на четырёх потоках — две волны, 213 мс. Блок try не отпустил поток, пока все не закончились. В Spring пулы-бины закрывает контейнер при остановке, но свои пулы, созданные в коде, нужно закрывать самим.

ForkJoinPool крадёт работу у соседей, а блокирующий код в commonPool тормозит всех

ForkJoinPool устроен иначе, чем ThreadPoolExecutor. У каждого потока своя двусторонняя очередь задач. Поток кладёт подзадачи в свою очередь и берёт из неё сам, а освободившийся поток крадёт задачи из чужих очередей с другого конца. Это эффективно для рекурсивного деления работы (fork/join): задача делится на подзадачи, а join() не простаивает, а выполняет другие задачи из очереди.

В JVM есть общий экземпляр — ForkJoinPool.commonPool(). На нём по умолчанию работают параллельные стримы и все методы CompletableFuture.*Async без явного пула. Его размер — число ядер минус один. Он рассчитан на вычисления, и блокирующий код в нём мешает всем остальным пользователям:

import java.util.concurrent.*;
import java.util.stream.IntStream;

public class CommonPool {
    public static void main(String[] args) throws Exception {
        System.out.println("parallelism commonPool: " + ForkJoinPool.commonPool().getParallelism());

        long start = System.nanoTime();
        CompletableFuture.supplyAsync(() -> 42).get();                    // быстрая задача, пул свободен
        System.out.printf("supplyAsync на свободном пуле: %.1f мс%n", (System.nanoTime() - start) / 1e6);

        Thread report = new Thread(() ->                                  // отчёт: 200 «запросов в банк» параллельным стримом
            IntStream.range(0, 200).parallel().forEach(i -> {
                try { Thread.sleep(100); } catch (InterruptedException e) { }
            }));
        report.start();
        Thread.sleep(50);                                                 // отчёт занял commonPool

        start = System.nanoTime();
        CompletableFuture.supplyAsync(() -> 42).get();                    // та же быстрая задача
        System.out.printf("supplyAsync, пока идёт отчёт: %.1f мс%n", (System.nanoTime() - start) / 1e6);
        report.join();
    }
}
parallelism commonPool: 17
supplyAsync на свободном пуле: 1.1 мс
supplyAsync, пока идёт отчёт: 771.8 мс

Задача, которая возвращает константу, ждала 772 мс: все 17 потоков общего пула спали в «запросах к банку» из чужого отчёта. В сервисе так один эндпоинт с parallelStream() и HTTP-вызовами внутри замедляет всё, что использует supplyAsync без своего пула. Правила: в commonPool — только короткие вычисления; блокирующие задачи — в отдельный пул нужного размера, который явно передают вторым аргументом supplyAsync(task, executor).

  • ThreadPoolExecutor решает так: потоки до core, затем очередь, затем потоки до max, затем отказ. С неограниченной очередью max не работает.
  • Фабрики Executors прячут опасные параметры: у fixed и single — неограниченная очередь, у cached — неограниченное число потоков (10 000 за секунду в замере). В серверном коде пул создают явно, с ограниченной очередью и именами потоков.
  • Политики отказа: Abort бросает исключение, CallerRuns даёт противодавление, Discard теряет задачи молча, DiscardOldest выбрасывает старые.
  • Для вычислений — пул по числу ядер, для ожидания — больше: ядра × (1 + ожидание/вычисления), с поправкой на внешние лимиты.
  • submit() прячет исключение в Future. Пул закрывают: shutdown, awaitTermination, shutdownNow или close() с Java 19.
  • ForkJoinPool — очереди на поток и кража работы. commonPool обслуживает параллельные стримы и *Async. Блокирующий код в нём тормозит всех.

На собеседовании

Какие параметры у ThreadPoolExecutor и как он принимает задачу?

Параметры: corePoolSize, maximumPoolSize, keepAliveTime, очередь задач, фабрика потоков и обработчик отказа. Задача обрабатывается так. Если потоков меньше core — создаётся новый поток. Иначе задача идёт в очередь. Если очередь полна и потоков меньше max — создаётся поток сверх core. Иначе срабатывает обработчик отказа, по умолчанию он бросает RejectedExecutionException. Потоки сверх core завершаются после keepAliveTime простоя.

  • С неограниченной очередью пул никогда не вырастет выше core: в замере урока пул «2–10» под 100 задачами остался на двух потоках с 98 задачами в очереди.
  • allowCoreThreadTimeOut(true) позволяет завершать и core-потоки, prestartAllCoreThreads() — создать их заранее.
ThreadPoolExecutor(2, 10, 60 с, ArrayBlockingQueue(20)), приходят 100 долгих задач сразу. Сколько будет потоков, сколько в очереди, сколько отказов?

Первые 2 задачи создадут core-потоки, следующие 20 встанут в очередь, ещё 8 создадут потоки до 10. Оставшиеся 70 получат отказ. Итого 10 потоков, 20 в очереди, 70 отказов — в замере урока ровно так.

Почему не рекомендуют Executors.newFixedThreadPool и newCachedThreadPool в сервисах?

У newFixedThreadPool неограниченная очередь: если задачи приходят быстрее, чем выполняются, очередь растёт до OutOfMemoryError, а задержка растёт без предела. У newCachedThreadPool неограниченное число потоков: при медленной внешней системе он создаёт поток на каждую задачу — в замере урока 10 000 потоков за секунду. В сервисах пул создают явно через ThreadPoolExecutor: ограниченная очередь, понятная политика отказа, фабрика с именами потоков.

Какие бывают политики отказа?

AbortPolicy (по умолчанию) бросает RejectedExecutionException. CallerRunsPolicy выполняет задачу в потоке вызывающего и тем самым замедляет поступление задач. DiscardPolicy молча выбрасывает задачу. DiscardOldestPolicy выбрасывает самую старую задачу из очереди. Можно написать свою реализацию RejectedExecutionHandler — с метрикой, логом и сохранением для повтора.

Пул отправки уведомлений о платежах настроен с DiscardPolicy, «чтобы не падать под нагрузкой». Что скажешь?

Под нагрузкой уведомления будут пропадать без единого следа: ни исключения, ни лога. В замере урока 15 из 20 задач исчезли молча. Лучше AbortPolicy с обработкой отказа или своя политика, которая пишет метрику и сохраняет уведомление для повторной отправки. Если важна скорость входа — CallerRunsPolicy.

Как выбрать размер пула потоков?

Для вычислительных задач — по числу ядер (availableProcessors(), в контейнере это лимит CPU пода): больше потоков не ускорит, в замере урока выигрыш кончился на 18 потоках на 18 ядрах. Для задач, которые ждут ввод-вывод, — больше, по оценке «ядра × (1 + ожидание / вычисления)». Затем учитывают внешние лимиты — пул соединений к базе, лимиты партнёров — и проверяют нагрузочным тестом.

Чем submit() отличается от execute()?

execute(Runnable) ничего не возвращает, и исключение задачи уходит в обработчик потока: печатается в stderr, поток пула заменяется новым. submit принимает Runnable или Callable и возвращает Future, в котором хранится результат или исключение. Если get() никто не вызовет, ошибка пропадёт бесследно.

Что такое ForkJoinPool и commonPool?

Пул с очередью задач на каждый поток и кражей работы: освободившийся поток забирает задачи из чужих очередей. Рассчитан на рекурсивное деление вычислений. commonPool — общий экземпляр размером «ядра минус один». На нём по умолчанию работают параллельные стримы и CompletableFuture.*Async. Блокирующие операции в нём занимают потоки и замедляют всех остальных, поэтому для ввода-вывода используют свой пул.

Почему один эндпоинт с parallelStream() и HTTP-вызовами внутри может замедлить весь сервис?

Параллельный стрим выполняется в commonPool, и его потоки спят в HTTP-вызовах. Все supplyAsync без своего пула ждут свободный поток. В замере урока задача, возвращающая константу, ждала 772 мс вместо 1 мс, пока параллельный стрим «ходил в банк».
