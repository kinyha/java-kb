JVM: G1

Большой heap нельзя собирать целиком — G1 собирает его по кускам

Сервис выписок держит в памяти 6 ГБ живых данных: справочники, кеши, агрегаты за день. Со сборщиком Parallel молодые сборки короткие, но раз в несколько минут old заполняется, и полная сборка с уплотнением всего old останавливает сервис на несколько секунд. Время полной сборки растёт с объёмом живых данных, и никакая настройка его не сократит: чтобы уплотнить 6 ГБ, их надо обойти и переместить.

G1 (Garbage-First) решает это иначе: он никогда не собирает old целиком без крайней нужды. Heap поделён на одинаковые регионы, и за одну паузу G1 собирает только часть из них — столько, сколько успеет за целевое время. G1 — сборщик по умолчанию в HotSpot начиная с Java 9, если машина не совсем маленькая. Разберём, как он устроен, как понимает, какие регионы собирать, и где у этого подхода слабые места.

Heap G1 — сетка одинаковых регионов, поколение — это роль региона

У классических сборщиков young и old — две сплошные области. У G1 heap — сетка из примерно двух тысяч регионов одного размера, от 1 до 32 МБ. У каждого региона есть роль: eden, survivor, old, humongous или свободный. Роль меняется: свободный регион становится eden, пережившие сборку объекты переезжают в регион, который становится survivor или old.

Размер региона JVM выбирает по размеру heap, так чтобы регионов было около 2048. Проверено на JDK 21 флагом -Xlog:gc+init:

-Xmx256 МБ2 ГБ8 ГБ32 ГБ
регион1 МБ1 МБ4 МБ16 МБ

Регионы дают G1 главное — свободу выбора. Собрать можно любой набор регионов, не трогая остальные. Молодые сборки у G1 устроены так же, как в теме Generations: живые из регионов eden и survivor копируются в свободные регионы, и старые регионы целиком освобождаются. Новое — то, как G1 чистит old.

Garbage-First: собирать в первую очередь регионы, где больше мусора

Чтобы чистить old по частям, G1 надо знать, в каком регионе сколько живых. Это знание даёт конкурентная маркировка из темы GC Algorithms. Когда заполнение heap переходит порог (InitiatingHeapOccupancyPercent, 45% по умолчанию, дальше G1 подстраивает его сам), G1 запускает маркировку параллельно с приложением. По её итогам у каждого old-региона есть процент живых данных. Дальше пролистай.

Смешанных сборок после одной маркировки обычно несколько: по умолчанию G1 стремится разобрать выбранные регионы за 8 пауз (G1MixedGCCountTarget) и не трогает регионы, где живых больше 85%. В логе это цепочка Pause Young (Prepare Mixed), затем Pause Young (Mixed) — такие строки показаны в теме GC Algorithms.

Выгода в том, что old чистится маленькими порциями, каждая — внутри целевой паузы. Цена — копирование: даже в mixed GC живые объекты перемещаются, пока приложение стоит, поэтому пауза зависит от объёма живых в выбранных регионах.

MaxGCPauseMillis — цель, под которую G1 подгоняет размер young

Главная настройка G1 — -XX:MaxGCPauseMillis, по умолчанию 200 мс. Это не гарантия, а цель. G1 ведёт статистику, сколько времени стоит копирование одного региона, и перед каждой сборкой подбирает, сколько регионов в неё взять. Прежде всего он меняет размер молодого поколения: меньше eden — меньше живых к копированию — короче пауза, но сборки чаще.

Проверим на нагрузке с большим объёмом живых: очередь из 3 миллионов недавних платежей.

import java.util.ArrayDeque;

public class Churn {
    record PaymentDto(long id, long amount, byte[] body) { }

    static final ArrayDeque<PaymentDto> RECENT = new ArrayDeque<>();

    public static void main(String[] args) {
        int keep = Integer.parseInt(args[0]);             // сколько недавних платежей держать живыми
        long sum = 0;
        long end = System.nanoTime() + 5_000_000_000L;     // работаем 5 секунд
        long id = 0;
        while (System.nanoTime() < end) {
            PaymentDto dto = new PaymentDto(id, id % 1000, new byte[200]);
            sum += dto.amount();
            RECENT.addLast(dto);                           // держим, пока не вытеснят
            if (RECENT.size() > keep) RECENT.removeFirst();
            id++;
        }
        System.out.println(sum);
    }
}

Три вывода. Первый: цели 200 и 20 мс дали одно и то же — паузы и так укладывались, и G1 ничего не менял. Настройка, которая ни во что не упирается, ничего не делает. Второй: при цели 5 мс G1 уменьшил young, сборок стало в полтора раза больше, а паузы — короче. Третий: цель 2 мс недостижима. У паузы есть пол — время на копирование живых молодых объектов и обход корней. Сборок стало больше вдвое, а медиана остановилась на 3,6 мс. Чересчур жёсткая цель только съедает пропускную способность.

Чтобы G1 соблюдал цель, надо зафиксировать размер молодого поколения через -Xmn.

Наоборот: -Xmn или NewRatio лишают G1 главного рычага, и цель по паузе он игнорирует. Для G1 размер young оставляют ему самому и управляют только целью.

Remembered set позволяет собрать регион, не обходя остальные

Чтобы собрать регион, нужно найти все ссылки на его объекты извне: при копировании их надо переписать на новые адреса. Обходить ради этого весь heap нельзя. Поэтому у каждого региона есть remembered set — список карт в других регионах, откуда на него ссылаются. Это развитие card table из темы Generations: там одна таблица на весь old, здесь — у каждого региона своя запись о входящих ссылках.

Поддерживает их барьер записи: при записи ссылки из одного региона в другой карта попадает в очередь, а фоновые потоки уточнения (refinement) разносят её по remembered set целевого региона. При сборке remembered set выбранных регионов служат дополнительными корнями.

Цена — память и CPU. В замере темы Native Memory у процесса с heap 256 МБ категория GC в Native Memory Tracking занимала 66 МБ: это remembered sets, card table и битовые карты маркировки. Для heap в десятки гигабайт это сотни мегабайт вне heap, и их надо закладывать в лимит пода.

Объект больше половины региона — humongous, и он дорог

Объект размером от половины региона G1 называет humongous. Его не копируют: слишком дорого. Под него сразу выделяются подряд идущие свободные регионы в old, и хвост последнего региона пропадает. Вернёмся к загадке из темы Memory Areas, где в heap на 16 МБ поместилось всего шесть массивов по мегабайту:

import java.util.ArrayList;
import java.util.List;

public class Humongous {
    public static void main(String[] args) {
        int size = Integer.parseInt(args[0]) * 1024;     // размер массива в КБ из аргумента
        List<byte[]> kept = new ArrayList<>();
        try {
            while (true) kept.add(new byte[size]);      // держим все массивы, пока heap не кончится
        } catch (OutOfMemoryError e) {
            int n = kept.size();
            kept.clear();
            System.out.println("массивов по " + size / 1024 + " КБ: " + n
                    + " = " + (long) n * size / 1024 / 1024 + " МБ из 16");
        }
    }
}

Heap 16 МБ, регион 1 МБ, реальные запуски java -Xmx16m -cp out Humongous …:

массивов по 400 КБ: 28 = 10 МБ из 16      # меньше половины региона: обычные объекты
массивов по 520 КБ: 13 = 6 МБ из 16       # больше половины: каждый занял целый регион
массивов по 1024 КБ: 6 = 6 МБ из 16       # мегабайт + заголовок: каждый занял два региона

Массив на 520 КБ занял регион на 1 МБ, а массив ровно на мегабайт из-за 16 байт заголовка — два региона. Почти половина heap пропала впустую. В логе это видно по причине сборки:

$ java -Xmx16m -Xlog:gc,gc+heap -cp out Humongous 1024

GC(0) Pause Young (Concurrent Start) (G1 Humongous Allocation) 6M->6M(16M) 0.265ms
GC(4) Pause Young (Normal) (G1 Humongous Allocation) (Evacuation Failure) 14M->14M(16M) 0.158ms

Humongous-объекты опасны не только расходом памяти. Каждое такое выделение может запустить сборку и старт маркировки — видно по G1 Humongous Allocation. А если не найдётся нужного числа свободных регионов подряд, G1 уходит в полную сборку. Короткоживущие humongous-массивы, у которых нет ссылок из других объектов, G1 умеет освобождать на молодой сборке, но в целом это дорогой путь.

Что делать, если в логах много Humongous Allocation: не держать гигантские массивы — делить большие ответы и буферы на куски, стримить вместо чтения целиком. Если без больших объектов никак, увеличить регион флагом -XX:G1HeapRegionSize, чтобы объекты перестали считаться humongous.

Full GC у G1 — признак, что он не успел

Полная сборка у G1 есть: параллельный mark-compact всего heap. Но в нормальной работе её не должно быть, и каждая — повод разбираться. Причины три:

  • Evacuation failure — при копировании живых не нашлось свободных регионов. В логе (Evacuation Failure) или To-space exhausted, за которыми часто следует полная сборка.
  • Маркировка проиграла гонку — heap заполнился до конца конкурентного цикла. Этот случай с Pause Full (G1 Compaction Pause) разобран в теме GC Algorithms.
  • Humongous-выделение не нашло свободных регионов подряд.

Лечение почти всегда одно — запас: больше heap, чтобы копированию было куда класть живых, раньше старт маркировки, запасные регионы (G1ReservePercent, 10% по умолчанию). И проверка, что живых данных не стало больше, чем помещается: при утечке G1 будет честно пытаться, пока не упадёт.

Где G1 — не лучший выбор? Если нужна пауза меньше миллисекунды при heap в десятки гигабайт, G1 её не даст: копирование живых в паузе ставит пол, как показал замер. Тогда смотрят на ZGC. А в поде с одним CPU JVM сама выберет Serial вместо G1, об этом тема Choosing a Collector.

  • G1 делит heap на ~2048 одинаковых регионов. Eden, survivor и old — роли регионов, а не сплошные области.
  • После конкурентной маркировки G1 знает долю живых в каждом old-регионе. Смешанные сборки забирают регионы, где мусора больше всего, — отсюда Garbage-First.
  • MaxGCPauseMillis — цель, под которую G1 подгоняет размер young. Ниже пола, заданного живыми данными, её не опустить, а -Xmn лишает G1 этого рычага.
  • Remembered sets позволяют собирать регион, не обходя heap, но стоят памяти вне heap и работы барьера записи.
  • Объекты от половины региона — humongous: занимают регионы целиком и могут вызвать полную сборку. Full GC у G1 — признак нехватки запаса.

На собеседовании

Как работает G1?

G1 делит heap на примерно две тысячи одинаковых регионов, и у каждого есть роль: eden, survivor, old или humongous. Молодые сборки копируют живых из eden и survivor в свободные регионы. Когда heap заполняется выше порога, G1 параллельно с приложением маркирует объекты и узнаёт долю живых в каждом old-регионе. Потом смешанные сборки забирают вместе с young несколько old-регионов, где мусора больше всего.

Так old чистится маленькими порциями, каждая в пределах целевой паузы MaxGCPauseMillis, и полной сборки всего heap в нормальной работе нет. Для сервиса с большим heap это разница между паузами в десятки миллисекунд и в секунды.

  • Копирование в G1 всегда в паузе, поэтому пауза зависит от объёма живых в выбранных регионах. Меньше миллисекунды G1 не даёт.
  • Цена — remembered sets и барьер записи: память вне heap и CPU приложения.
Как G1 выбирает размер региона?

Так, чтобы регионов было около 2048, в пределах от 1 до 32 МБ степенью двойки. На JDK 21 heap в 2 ГБ дал регион 1 МБ, 8 ГБ — 4 МБ, 32 ГБ — 16 МБ. Задать вручную можно флагом -XX:G1HeapRegionSize.

Что такое mixed GC и почему G1 называется Garbage-First?

Mixed GC — сборка, которая берёт все молодые регионы и часть старых. Какие старые — решает конкурентная маркировка: G1 знает долю живых в каждом регионе и выбирает те, где мусора больше всего. Копировать там почти нечего, а освобождается целый регион. Отсюда Garbage-First: сначала собирать самое замусоренное.

Регионы, где живых больше 85%, G1 вообще не трогает: копировать дорого, выгоды мало.

После маркировки у old-регионов доля живых 95%, 60%, 30%, 10%. Какие соберёт mixed GC в первую очередь и что получится?

10% и 30%: их живые, вместе 40% региона, поместятся в один свободный регион, а освободятся два. Регион с 95% G1 пропустит, 60% — возможно, в следующих смешанных сборках, если укладывается в паузу.

Что делает MaxGCPauseMillis? Можно ли поставить 1 мс?

Это цель по длительности паузы, по умолчанию 200 мс. G1 ведёт статистику стоимости копирования и подгоняет под цель, сколько регионов взять в сборку, — прежде всего размер молодого поколения. Меньше цель — меньше young, паузы короче, но сборки чаще.

1 мс поставить можно, но G1 её не выдержит: у паузы есть пол — копирование живых и обход корней. В замере урока цель 2 мс дала вдвое больше сборок, а медиана остановилась на 3,6 мс. Если нужны паузы меньше миллисекунды, нужен ZGC.

  • Жёсткий -Xmn отключает адаптацию young, и цель перестаёт работать.
  • Если паузы уже ниже цели, изменение цели ничего не даёт: 200 и 20 мс в замере дали одинаковый результат.
В JAVA_OPTS стоит -XX:+UseG1GC -Xmn2g -XX:MaxGCPauseMillis=50, а паузы по 150 мс. Что не так?

-Xmn2g фиксирует молодое поколение, и G1 не может уменьшить его, чтобы уложиться в 50 мс. Нужно убрать -Xmn и дать G1 подбирать young самому. -XX:+UseG1GC тоже лишний: G1 и так по умолчанию, кроме совсем маленьких машин.

Что такое humongous-объекты и чем они опасны?

Это объекты размером от половины региона. G1 их не копирует, а сразу выделяет под них подряд идущие регионы в old. Хвост последнего региона пропадает: в уроке массив на мегабайт с заголовком занял два региона по мегабайту, и в heap на 16 МБ поместилось лишь шесть таких массивов.

Кроме потерь памяти, humongous-выделения запускают сборки и маркировку, а при нехватке регионов подряд — полную сборку. Лечится отказом от гигантских массивов — делить буферы, стримить — или увеличением региона.

Регион 4 МБ. Каким будет массив на 3 МБ и сколько он займёт?

Humongous, раз он больше половины региона. Займёт один регион целиком: 4 МБ, из них 1 МБ пропадёт.

Когда у G1 бывает full GC?

Когда G1 не успел по-хорошему. Три причины: при копировании не нашлось свободных регионов (evacuation failure), heap заполнился до конца конкурентной маркировки, humongous-объекту не нашлось регионов подряд. Тогда G1 делает параллельный mark-compact всего heap с остановкой.

Лечение — запас: больше heap, раньше старт маркировки, резерв регионов. И проверка, нет ли утечки: при растущем живом объёме G1 будет падать в full GC всё чаще.

Как в логе отличить эти причины?

По скобкам: (Evacuation Failure) или To-space exhausted у молодой сборки перед полной, Pause Full (G1 Compaction Pause) при незавершённом Concurrent Mark Cycle, (G1 Humongous Allocation) у сборок перед полной.

Что такое remembered set?

Это список мест в других регионах, откуда есть ссылки на объекты данного региона. Он нужен, чтобы собрать регион, не обходя весь heap: при копировании ссылки на перенесённые объекты надо переписать, и remembered set говорит, где их искать. Поддерживает его барьер записи вместе с фоновыми потоками уточнения.

Стоят remembered sets памяти вне heap: в замере темы Native Memory категория GC заняла 66 МБ при heap в 256 МБ.

Чем remembered set отличается от card table?

Card table — одна таблица карт на heap: какие карты менялись. Remembered set есть у каждого региона и хранит входящие ссылки: какие карты других регионов ссылаются сюда. G1 использует оба: карты отмечает барьер, а потоки уточнения переносят их в remembered sets.
