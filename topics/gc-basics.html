JVM: GC Basics

Раз в несколько секунд все запросы замирают одновременно

На графике латентности платёжного API обычные запросы идут за 20 мс, но p99 время от времени прыгает до 200. Задержка бьёт по всем эндпоинтам сразу, независимо от того, ходят они в базу или нет. Каждая такая строка — момент, когда JVM остановила все потоки приложения, чтобы собрать мусор. Heap был занят на 25 МБ, после сборки осталось 2, и заняло это четверть миллисекунды. У сервиса с гигабайтами живых данных те же строки показывают десятки и сотни миллисекунд. Чтобы понимать, почему паузы бывают, от чего зависит их длина и что с ними делать, нужно разобраться, как сборщик вообще решает, что можно удалить.

Живой — не «нужный», а достижимый

Сборщик мусора не знает, какие объекты программе ещё понадобятся. Он решает по формальному признаку: объект жив, если до него можно дойти по ссылкам от корней — мест, где программа точно держит ссылки прямо сейчас. Всё, до чего не дойти, программа уже никогда не прочитает, значит, это мусор.

Важное следствие: ссылки объектов друг на друга ничего не решают. Счёт идёт только от корней. Поэтому циклические ссылки, на которых ломается подсчёт ссылок в Python или Objective-C, для JVM не проблема.

public class Cycles {
    static class Account { Transfer lastTransfer; }
    static class Transfer { Account from; byte[] payload = new byte[1024]; }

    public static void main(String[] args) {
        for (int i = 0; i < 10_000_000; i++) {
            Account account = new Account();
            Transfer transfer = new Transfer();
            account.lastTransfer = transfer;       // счёт ссылается на перевод,
            transfer.from = account;               // перевод — на счёт: цикл
        }                                          // на следующей итерации до пары не дойти ни от одного корня
        System.out.println("создано 10 млн пар Account ↔ Transfer, heap: "
                + Runtime.getRuntime().maxMemory() / 1024 / 1024 + " МБ");
    }
}

Запусти с heap в 16 МБ: java -Xmx16m -cp out Cycles.

создано 10 млн пар Account ↔ Transfer, heap: 16 МБ

Через 16 МБ прошло около 10 ГБ объектов, связанных в циклы, и ни одного OutOfMemoryError. Каждая пара держит друг друга, но от корней до неё не дойти, и сборщик её убирает.

Чтобы объекты с циклическими ссылками собрались, связи нужно разорвать вручную, присвоив null.

В JVM нужно лишь, чтобы до цикла не было пути от корней. Обнулять ссылки имеет смысл в другом случае — когда долгоживущий объект держит ненужную ссылку, например элемент в самописном стеке на массиве.

Обход начинается с корней: стеков потоков, static-полей и других

Корни — ссылки, которые живы по определению, без всяких объектов вокруг:

  • локальные переменные и параметры во всех кадрах всех живых потоков;
  • static-поля загруженных классов: они живут, пока жив класс, а класс — пока жив его загрузчик;
  • объекты, на которых потоки держат мониторы synchronized;
  • JNI-ссылки из native-кода и внутренние ссылки самой JVM: системные классы, объекты исключений на случай OOM.

Сборка начинается с маркировки: сборщик обходит граф от корней и помечает всё, до чего дошёл. Пролистай маркировку на маленьком heap.

Главное свойство этой схемы — стоимость. Маркировка обходит только живые объекты: мусор сборщик даже не трогает, он просто считает его место свободным. Поэтому сборка тем дороже, чем больше живых данных, и почти не зависит от того, сколько мусора накопилось. Это основа всех современных сборщиков, и на ней держится идея поколений из следующей темы.

Утечка в Java — достижимый объект, который больше не нужен

Раз сборщик судит по достижимости, утечка в Java выглядит так: программа держит ссылку на объект, который ей больше не понадобится. Для сборщика такой объект живой, и он честно его хранит. Классический пример — static-коллекция, в которую добавляют и никогда не удаляют.

import java.lang.management.ManagementFactory;
import java.util.HashMap;
import java.util.Map;

public class Leak {
    // static-поле — корень: всё, что лежит в карте, достижимо всегда
    static final Map<String, byte[]> SESSIONS = new HashMap<>();

    public static void main(String[] args) {
        for (int minute = 1; minute <= 5; minute++) {
            for (int i = 0; i < 2_000; i++) {
                SESSIONS.put("s-" + minute + "-" + i, new byte[1024]);   // сессии добавляют, но не удаляют
            }
            System.gc();                                                 // для наглядности: собрать всё, что можно
            long live = ManagementFactory.getMemoryMXBean().getHeapMemoryUsage().getUsed();
            System.out.println("минута " + minute + ": живых данных после GC " + live / 1024 / 1024 + " МБ");
        }
    }
}

минута 4: живых данных после GC 11 МБ
минута 5: живых данных после GC 13 МБ

Это и есть признак утечки: растёт не просто занятый heap, он всегда пилообразный, а живой объём после сборок — нижние точки пилы. Если при той же нагрузке нижние точки ползут вверх, кто-то держит ссылки. Типичные источники в сервисах:

  • кеш на HashMap без размера и срока жизни;
  • слушатели и колбэки, которые регистрируют и не снимают;
  • ThreadLocal в пуле потоков: поток живёт вечно, и значение вместе с ним;
  • коллекция в singleton-бине Spring, куда складывают данные запросов.

Кто именно держит объекты, показывает heap dump: путь от объекта до корня прямо называет виновника. Как его снять и прочитать — в теме Diagnostics.

Чтобы обойти граф, сборщик останавливает все потоки в safepoint

Почему нельзя маркировать, пока приложение работает? Потому что потоки меняют ссылки прямо во время обхода. Пусть сборщик уже прошёл объект A и пометил его. В этот момент поток переносит ссылку на ещё не помеченный объект C в поле A и удаляет старый путь к C. Сборщик в A больше не заглянет, до C не дойдёт и освободит живой объект. Программа получит ссылку на мусор.

Самое простое решение — на время работы остановить все потоки приложения. Это stop-the-world пауза. Современные сборщики делают большую часть маркировки параллельно с приложением, отслеживая изменения ссылок специальными барьерами, но короткие остановки нужны всем. Как устроены такие сборщики — в теме GC Algorithms.

Остановить поток в произвольной инструкции нельзя: в этот момент JVM может не знать, какие регистры содержат ссылки. Поэтому потоки останавливаются только в safepoint — точках, где состояние известно: на выходе из метода, на обратном переходе цикла, при вызове. Скомпилированный код периодически проверяет флаг «пора остановиться». Пауза начинается, когда в safepoint пришёл последний поток. Пролистай, что будет, если один поток сильно задержится.

Так бывает на самом деле. В JDK 21 проверка safepoint стоит даже внутри длинных счётных циклов, но её можно выключить диагностическим флагом и увидеть разницу. Поток в фоне крутит цикл до Integer.MAX_VALUE, а главный поток выделяет память, вызывая сборки.

public class Ttsp {
    static volatile long sink;

    public static void main(String[] args) throws Exception {
        Thread batch = new Thread(() -> {
            for (int round = 0; round < 50; round++) {
                long sum = 0;
                for (int i = 0; i < Integer.MAX_VALUE; i++) {   // счётный цикл по int: миллиарды итераций
                    sum += i % 7;
                }
                sink = sum;
            }
        });
        batch.setDaemon(true);
        batch.start();
        Thread.sleep(500);                                      // даём циклу скомпилироваться
        for (int i = 0; i < 3; i++) {                          // выделяем память, чтобы вызвать сборки
            byte[][] junk = new byte[200][];
            for (int k = 0; k < 200; k++) junk[k] = new byte[1024 * 1024];
            Thread.sleep(200);
        }
    }
}

Реальные запуски на JDK 21, строки лога сокращены до нужных полей:

$ java -Xmx64m -Xlog:safepoint -cp out Ttsp

Safepoint "G1CollectForAllocation", Reaching safepoint: 29042 ns

$ java -XX:+UnlockDiagnosticVMOptions -XX:-UseCountedLoopSafepoints -Xmx64m -Xlog:safepoint -cp out Ttsp

#                                  ждали цикл 588 мс                  сама работа 0,48 мс
Safepoint "G1CollectForAllocation", Reaching safepoint: 51786995291 ns   # следующая остановка ждала 51,8 с

Сама работа заняла полмиллисекунды, а приложение простояло 588 мс в ожидании одного потока. Следующая остановка в том же запуске ждала почти минуту — пока цикл не закончил очередной круг. Поэтому при разборе длинных пауз смотрят не только время сборки, но и Reaching safepoint в логе -Xlog:safepoint. Долгое достижение safepoint бывает из-за длинных циклов в старых JDK, больших копирований массивов, native-вызовов, а safepoint нужны не только сборщику: деоптимизации, снятию thread dump, отзыву классов.

Паузы, пропускная способность, память — выбрать можно два

У сборки мусора три цены, и уменьшить сразу все нельзя:

ЦенаЧто этоКому важна
Паузы (latency)сколько приложение стоит на одну сборкуплатёжный API, p99 ответа
Пропускная способность (throughput)какая доля CPU уходит на приложение, а не на сборкуночной батч, пересчёт выписок
Память (footprint)сколько heap и служебных структур нужно сверх живых данныхподы с тесным лимитом

Короткие паузы достигаются тем, что сборщик работает параллельно с приложением, а это стоит CPU и памяти на барьеры и служебные структуры. Максимальная пропускная способность — когда сборщик останавливает всё и работает во все ядра, зато паузы длиннее. Маленький heap — чаще сборки. Каждый сборщик HotSpot — это выбранная точка в этом треугольнике, об этом тема Choosing a Collector.

Отсюда и ответ на вопрос «можно ли вызвать сборку вручную». System.gc() — просьба, а не приказ, но HotSpot по умолчанию её выполняет, причём полной сборкой с остановкой. Звать его из прикладного кода — значит добровольно платить паузой. Сама JVM вызывает его в одном случае, который стоит помнить: когда кончается direct-память, об этом — в теме Native Memory.

Где кончается эта тема? Мы разобрали, что сборщик ищет и почему останавливает приложение. Как именно он освобождает память — копирует живых, сдвигает или просто отмечает свободные места — и почему молодые объекты собирают отдельно, разбирают следующие темы: Generations и GC Algorithms.

  • Объект жив, если до него есть путь по ссылкам от корней: стеков потоков, static-полей, мониторов, JNI-ссылок. Циклы без пути от корней собираются.
  • Маркировка обходит только живые объекты, поэтому стоимость сборки растёт с объёмом живых данных, а не мусора.
  • Утечка в Java — достижимый, но ненужный объект. Признак — растёт живой объём после сборок, а не просто занятый heap.
  • Чтобы граф не менялся под ногами, сборщик останавливает потоки в safepoint. Пауза включает ожидание самого медленного потока — time to safepoint.
  • Паузы, пропускная способность и память конкурируют: каждый сборщик выбирает свой компромисс.

На собеседовании

Что такое GC roots?

Это ссылки, с которых сборщик начинает обход графа и которые живы по определению. Основные: локальные переменные и параметры в кадрах живых потоков, static-поля загруженных классов, объекты под мониторами synchronized, JNI-ссылки из native-кода. Всё, до чего можно дойти от них, — живое, остальное — мусор.

На практике чаще всего корнем утечки оказывается static-поле: кеш или коллекция в singleton, которая только растёт. В heap dump путь от объекта до такого корня прямо показывает виновника.

  • Static-поля живут, пока жив класс, а класс — пока жив его загрузчик. Поэтому утечка загрузчика держит все его static-данные.
  • Живой поток — тоже корень вместе со всем стеком и своими ThreadLocal. Потоки пула не умирают, и значения в них живут вечно.
Метод создал объект и сохранил его только в локальную переменную. Когда объект станет недостижимым?

Когда ссылка перестанет быть нужна кадру — формально после выхода из метода. JIT может считать переменную мёртвой даже раньше, после последнего использования: сборщик учитывает только живые в данной точке ссылки.

Найди, что держит объекты в памяти 
@Component
class AuditService {
    private final List<PaymentEvent> events = new ArrayList<>();

    void onPayment(PaymentEvent event) {
        events.add(event);
        send(event);
    }
}

Singleton-бин живёт всё время работы приложения, его поле достижимо от корней через контекст Spring. Список только растёт: каждое событие остаётся в памяти навсегда. Если события нужно только отправить, список не нужен. Если нужно хранить — с ограничением размера или во внешнем хранилище.

Как сборщик понимает, что объект можно удалить? Что с циклическими ссылками?

По достижимости. Сборщик обходит граф от корней и помечает всё, до чего дошёл. Непомеченное недостижимо: программа никогда его не прочитает, значит, это мусор. Счётчиков ссылок в JVM нет.

Поэтому циклические ссылки не мешают сборке. Счёт и перевод, ссылающиеся друг на друга, соберутся, как только до них не будет пути от корней. В уроке миллионы таких пар прошли через heap в 16 МБ без ошибок.

  • Стоимость маркировки пропорциональна живым данным, а не мусору. Сборка heap с 10 ГБ мусора и 100 МБ живых данных дешёвая.
  • Подсчёт ссылок проще, но не собирает циклы и требует атомарных операций на каждое присваивание ссылки в многопоточной программе.
Нужно ли обнулять поля, чтобы помочь сборщику?

Обычно нет: объект, до которого не дойти, соберётся с любыми полями. Обнуление нужно, когда долгоживущий объект держит ссылку на ненужное, например элемент в самописной очереди на массиве или поле в singleton.

Бывают ли утечки памяти в Java?

Бывают, но не в смысле C, где память забыли освободить. В Java утечка — это объект, до которого ещё есть путь от корней, хотя программе он больше не нужен. Сборщик честно считает его живым. Типичные случаи: кеш без размера и TTL, static-коллекции, слушатели, которые не снимают, ThreadLocal в пуле потоков.

Распознаю утечку по живому объёму после сборок: если нижние точки пилы heap растут при той же нагрузке, кто-то держит ссылки. Дальше heap dump и путь от растущих объектов до корня.

  • Бывают и утечки вне heap: загрузчики классов, direct-буферы, потоки, native-память библиотек.
  • Растущий занятый heap сам по себе не признак: сборщик может просто не спешить. Смотреть нужно после сборок.
Почему этот код течёт в веб-приложении? 
private static final ThreadLocal<List<String>> AUDIT =
        ThreadLocal.withInitial(ArrayList::new);

void handle(Request request) {
    AUDIT.get().add(request.id());
    process(request);
}

Потоки веб-сервера живут всё время работы и переиспользуются. Список в ThreadLocal потока никогда не очищается и растёт от запроса к запросу. Нужно AUDIT.remove() в finally или вообще не хранить состояние запроса в ThreadLocal потока пула.

Что такое stop-the-world и safepoint?

Stop-the-world — пауза, когда JVM останавливает все потоки приложения, чтобы сборщик мог работать с графом объектов, который никто не меняет. Останавливаются потоки не где попало, а в safepoint — точках, где JVM точно знает, где лежат ссылки: на вызовах, выходах из методов, обратных переходах циклов.

Пауза начинается, когда в safepoint пришёл последний поток. Если один поток долго туда идёт, ждут все. В логе -Xlog:safepoint это видно как большое Reaching safepoint.

  • Safepoint нужны не только GC: деоптимизация, thread dump, отзыв кода.
  • Concurrent-сборщики сокращают паузы, делая большую часть работы параллельно с приложением, но короткие safepoint у них остаются.
GC-лог показывает паузы по 2 мс, а мониторинг — простои по 300 мс. Где искать разницу?

В time to safepoint. Лог -Xlog:gc показывает работу сборщика, а приложение стоит ещё и пока все потоки добираются до safepoint. Нужен -Xlog:safepoint: там видно и время достижения, и какая операция его запросила.

Что делает System.gc() и стоит ли его вызывать?

Формально это просьба к JVM собрать мусор, и гарантий спецификация не даёт. В HotSpot по умолчанию она выполняется полной сборкой с остановкой всех потоков. Из прикладного кода вызывать не стоит: это добровольная пауза, которая не решает никакую проблему памяти.

Его вызывает сама JVM, когда кончается direct-память, поэтому запрещать его флагом -XX:+DisableExplicitGC опасно для сервисов на Netty и NIO.

В ночном джобе после каждой пачки стоит System.gc() «чтобы освободить память». Что скажешь?

Каждый вызов — полная пауза, а память сборщик освободит и сам, когда она понадобится. Вызов только замедляет джоб. Если после пачки растёт живой объём, проблема в удержании ссылок, и System.gc() её не решит.
