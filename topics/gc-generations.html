JVM: Generations

Полные сборки идут одна за другой, хотя живых данных почти нет

Антифрод платёжного сервиса держит в памяти последние 20 000 платежей, чтобы искать подозрительные серии. Новые платежи добавляются, самые старые вытесняются. Живых данных немного — 20 000 записей, около 5 МБ. Но в логе сборщика регулярно появляются полные сборки, и каждая освобождает почти весь heap.

import java.util.ArrayDeque;

public class Recent {
    record PaymentDto(long id, long amount, byte[] body) { }

    // «Недавние платежи»: каждый живёт, пока его не вытеснят 20 000 следующих
    static final ArrayDeque<PaymentDto> RECENT = new ArrayDeque<>();

    public static void main(String[] args) {
        int keep = Integer.parseInt(args[0]);                             // сколько платежей держать
        long sum = 0;
        for (long id = 0; id < 5_000_000; id++) {
            PaymentDto dto = new PaymentDto(id, id % 1000, new byte[200]);  // платёж из запроса
            sum += dto.amount();
            RECENT.addLast(dto);
            if (RECENT.size() > keep) {
                RECENT.removeFirst();                                    // самый старый становится мусором
            }
        }
        System.out.println(sum);
    }
}

Запустим с классическим сборщиком Serial, у которого поколения видны лучше всего: heap 64 МБ, из них 16 МБ под молодое поколение. Реальный запуск на JDK 21:

$ java -XX:+UseSerialGC -Xmx64m -Xmn16m -Xlog:gc -cp out Recent 20000
GC(9)  Pause Young (Allocation Failure) 45M->35M(62M) 0.558ms     # после молодой сборки занято 35 МБ?
GC(15) Pause Full (Allocation Failure) 61M->7M(62M) 4.898ms       # полная сборка: из 61 МБ живы 7
GC(29) Pause Full (Allocation Failure) 59M->7M(62M) 4.332ms
...                                                                   # итого 92 молодые и 6 полных сборок

Странная картина. Полная сборка находит лишь 7 МБ живых данных из 61 — значит, heap забит мусором. Но почему этот мусор не убрали быстрые молодые сборки, которых было 92? Чтобы ответить, нужно понять, как heap поделён на поколения и как объект переходит из одного в другое. В конце урока одна настройка уберёт все полные сборки.

Большинство объектов умирает молодыми, поэтому heap делят на поколения

Посмотри на объекты платёжного сервиса. DTO запроса, JSON-строки, промежуточные коллекции живут миллисекунды — пока обрабатывается запрос. Кеш тарифов, пулы соединений, бины Spring живут всё время работы процесса. Середины почти нет. Это слабая гипотеза поколений: большинство объектов умирает вскоре после создания, а пережившие несколько сборок, скорее всего, проживут долго.

Из прошлой темы: маркировка обходит только живые объекты. Значит, если собирать отдельно область, где лежат одни новые объекты, почти всё там окажется мусором, и сборка будет очень дешёвой. Так heap и устроен:

  • Eden — здесь рождаются все объекты, по сдвигу указателя в TLAB (тема Object Layout & Allocation).
  • Survivor S0 и S1 — две одинаковые маленькие области для тех, кто пережил сборку. В каждый момент одна из них пустая.
  • Old, или tenured, — область для объектов, которые пережили достаточно сборок.

Сборка только молодого поколения называется minor GC или young GC. В логе выше это Pause Young: доли миллисекунды, хотя через eden прошли десятки мегабайт.

Minor GC копирует выживших между survivor и считает их возраст

Когда eden заполнен, происходит minor GC. Сборщик находит живые объекты eden и одного survivor и копирует их во второй, пустой survivor. Всё остальное в eden и старом survivor — мусор, и обе области просто объявляются пустыми. Каждое копирование увеличивает возраст объекта на единицу. Пролистай несколько сборок подряд.

Два survivor нужны из-за копирования: живые объекты переносятся из занятого survivor и eden в пустой. После этого старая область пуста целиком, без дыр, и в ней снова можно выделять память сдвигом указателя. Цена — один survivor всегда пустует.

Копирование обходится дёшево, потому что живых мало: на каждой сборке сборщик трогает только их. Сборка молодого поколения размером в гигабайт, где живы 20 МБ, стоит как копирование 20 МБ.

Порог возраста подвижен, и переполненный survivor отправляет всех в old

Возраст хранится в 4 битах заголовка объекта (тема Object Layout & Allocation), поэтому максимум — 15. Это и есть MaxTenuringThreshold. Но реальный порог JVM подбирает на каждой сборке сама: если выжившие не помещаются в целевую половину survivor (TargetSurvivorRatio=50), порог снижается. Это видно в логе возрастов. Реальный запуск того же примера:

$ java -XX:+UseSerialGC -Xmx64m -Xmn16m -Xlog:gc+age=trace,gc -cp out Recent 20000
GC(0) Desired survivor size 819200 bytes, new threshold 1 (max threshold 15)   # порог упал до 1
GC(0) - age   1:    1638400 bytes,    1638400 total                            # survivor 1,6 МБ забит целиком
GC(0) Pause Young (Allocation Failure) 15M->7M(62M) 1.102ms
GC(1) - age   1:    1638384 bytes,    1638384 total
GC(1) Pause Young (Allocation Failure) 19M->10M(62M) 0.968ms                    # после сборки занято больше:
GC(2) Pause Young (Allocation Failure) 23M->13M(62M) 0.981ms                    # old растёт на 3 МБ каждый раз

Вот ответ на загадку из первого шага. Недавних платежей 20 000, около 5 МБ, а survivor вмещает 1,6. Всё, что пережило сборку и не влезло, уходит в old — и там умирает через несколько секунд, когда платёж вытесняют из очереди. Minor GC old не собирает. Мёртвые платежи копятся в old, пока он не заполнится, и тогда приходится делать полную сборку всего heap. Живых в нём снова 7 МБ.

Лечение — дать молодому поколению вместить объекты средней жизни, чтобы они умирали, не доезжая до old. Увеличим heap и молодое поколение:

$ java -XX:+UseSerialGC -Xmx128m -Xmn96m -Xlog:gc+age=trace,gc -cp out Recent 20000
GC(1) Desired survivor size 5013504 bytes, new threshold 15 (max threshold 15)  # порог держится на 15
GC(9) Pause Young (Allocation Failure) 83M->7M(118M) 0.359ms                     # после сборки те же 7 МБ
...                                                                              # итого 15 молодых и 0 полных

Шесть полных сборок исчезли. Живых данных столько же, но теперь они умирают в молодом поколении, где мусор бесплатный. Отсюда правило настройки: объекты средней жизни должны умирать в young. Признаки проблемы — порог возраста в логе постоянно низкий, а old растёт после каждой молодой сборки.

Если полных сборок много, нужно увеличить heap.

Здесь помогло не увеличение heap само по себе, а размер молодого поколения. Больший old с тем же маленьким young только реже бы заполнялся мёртвыми платежами, но полные сборки остались бы и стали бы длиннее.

Ссылки из old в young минор находит по card table, не обходя old

У minor GC есть проблема. Корни — это стеки и static-поля, но живой молодой объект может быть достижим и из old: кеш тарифов в old получил ссылку на новый объект курса. Если minor GC не увидит эту ссылку, он соберёт живой объект. А обходить весь old на каждой молодой сборке — значит потерять всю выгоду поколений.

Решение — card table. Old разбит на карты по 512 байт, и для каждой карты есть байт-отметка. Каждый раз, когда программа записывает ссылку в поле объекта, JIT добавляет пару инструкций — барьер записи — и помечает карту этого объекта грязной. На minor GC сборщик сканирует как дополнительные корни только грязные карты.

Поэтому write barrier — плата за поколения, которую приложение платит всё время, а не только во время сборки. G1 устроен сложнее: у каждого его региона есть remembered set — список мест, откуда на регион ссылаются. Но идея та же, об этом тема G1.

Minor, major и full — это разный объём работы

Названия сборок в разговорах используют вольно, поэтому договоримся:

СборкаЧто собираетКак выглядит в логеЦена
minor, youngтолько молодое поколениеPause Youngпропорциональна живым в young, обычно миллисекунды
major, oldстарое поколение, часто параллельно с приложениему G1: Concurrent Mark и Pause Young (Mixed)зависит от сборщика
fullвесь heap целиком, с остановкойPause Fullпропорциональна всем живым данным: на больших heap — секунды

Full GC в сервисе — почти всегда сигнал проблемы, а не нормальный режим. Причины в логе пишутся в скобках:

  • Allocation Failure — old заполнен и места нет. Часто это преждевременное повышение, как в этом уроке, или утечка.
  • G1 Compaction Pause у G1 — не хватило свободных регионов, чтобы скопировать живые объекты.
  • System.gc() — его вызвал код или сама JVM из-за direct-памяти.
  • Metadata GC Threshold — вырос Metaspace, нужна выгрузка классов.

Где кончается гипотеза поколений? Она верна для типичного сервиса, но бывают нагрузки иначе: большие кеши с вытеснением по LRU, где объекты живут минуты и умирают уже в old; сессии пользователей со временем жизни в полчаса. Для них настройкой young не обойтись, и выбирают сборщик, который собирает old эффективно или конкурентно: G1 со смешанными сборками, generational ZGC. Об этом темы G1, ZGC & Shenandoah и Choosing a Collector.

  • Большинство объектов умирает молодыми, поэтому heap делят на young (eden и два survivor) и old. Minor GC трогает только живых в young и стоит миллисекунды.
  • Minor GC копирует живых из eden и одного survivor в другой survivor. Каждое копирование — плюс один к возрасту. Два survivor нужны, чтобы после копирования область оставалась сплошной.
  • После 15 сборок объект переезжает в old. Если survivor переполнен, выжившие уходят в old сразу — premature promotion — и там копятся мёртвыми до full GC.
  • Объекты средней жизни должны умирать в young: признак беды — низкий порог в логе gc+age и рост old после каждой молодой сборки.
  • Ссылки из old в young minor GC находит через card table, которую помечает барьер записи — постоянная цена поколений.

На собеседовании

Зачем heap делят на поколения?

Из-за слабой гипотезы поколений: большинство объектов умирает вскоре после создания. Сборка обходит только живые объекты, поэтому область, где лежат одни новые объекты, собирается очень дёшево: почти всё там мусор. Heap делят на young — eden и два survivor — и old для долгожителей, и молодое поколение собирают часто и отдельно.

В сервисе это DTO запросов, JSON и промежуточные коллекции: они умирают за миллисекунды и почти не стоят сборщику. А кеши и бины живут в old, куда сборщик заглядывает редко.

  • Цена поколений — барьер записи на каждое присваивание ссылки и card table, чтобы находить ссылки из old в young.
  • Гипотеза ломается на объектах средней жизни: LRU-кешах, сессиях. Они доживают до old и умирают там.
Почему сборка молодого поколения размером 1 ГБ может идти миллисекунды?

Потому что стоимость зависит от живых объектов, а не от размера области. Если из гигабайта живы 20 МБ, сборщик скопирует 20 МБ, а остальное просто объявит свободным.

Как проходит minor GC? Зачем два survivor?

Когда eden заполнен, сборщик останавливает приложение, находит живые объекты в eden и в занятом survivor и копирует их в пустой survivor, увеличивая возраст на единицу. После этого eden и старый survivor объявляются пустыми целиком. Объекты, пережившие порог сборок, по умолчанию до 15, переезжают в old.

Два survivor нужны, потому что это копирующая сборка: живые переносятся в пустую область, а исходная освобождается целиком, без дыр. Поэтому один survivor всегда пустует.

  • Максимум 15, потому что под возраст в mark word отведено 4 бита.
  • Реальный порог JVM снижает сама, если выжившие не помещаются в survivor, — это видно в логе -Xlog:gc+age=trace.
В eden 100 объектов, в занятом survivor 10. Живы 5 в eden и 3 в survivor. Что будет после minor GC?

Восемь живых объектов окажутся в другом survivor: пять с возрастом 1 и три с возрастом на единицу больше прежнего, если никто из трёх не достиг порога — тогда он переедет в old. Eden и прежний survivor станут пустыми, 102 мёртвых объекта сборщик даже не трогал.

Когда объект попадает в old? Что такое premature promotion?

Объект переезжает в old, когда переживёт порог молодых сборок, по умолчанию до 15. Ещё в old сразу уходят выжившие, которым не хватило места в survivor, и очень большие объекты. Преждевременное повышение — когда в old попадают объекты средней жизни, которые умерли бы через пару сборок. Они копятся в old мёртвыми и в итоге вызывают full GC.

В уроке очередь недавних платежей на 5 МБ не помещалась в survivor на 1,6 МБ, и это давало шесть полных сборок. Увеличение молодого поколения убрало их все.

В логе gc+age постоянно new threshold 1, а old растёт после каждой молодой сборки. Что предложишь?

Survivor переполнен, объекты средней жизни уезжают в old раньше времени. Нужно больше места в молодом поколении: увеличить -Xmn или долю young. Для G1 — не мешать ему подстраивать young, убрав жёсткий -Xmn, и проверить цель по паузам. Параллельно стоит проверить, не держит ли код объекты дольше необходимого.

Чем minor, major и full GC отличаются?

Minor GC собирает только молодое поколение, обычно за миллисекунды. Major — сборка старого поколения, у современных сборщиков её большая часть идёт параллельно с приложением. Full GC собирает весь heap целиком с остановкой, и её длина пропорциональна всем живым данным: на больших heap это секунды.

Full GC в сервисе я считаю симптомом. Смотрю причину в скобках в логе: Allocation Failure, System.gc(), Metadata GC Threshold, у G1 — нехватка регионов для копирования.

Что означает Pause Young (Mixed) в логе G1?

Смешанную сборку: G1 собирает все молодые регионы и заодно часть старых, где больше всего мусора. Так G1 чистит old постепенно, без полной сборки. Подробно — в теме G1.

Как minor GC находит ссылки из old в young?

Через card table. Old разбит на карты по 512 байт, и у каждой есть отметка. При каждой записи ссылки в поле объекта скомпилированный код выполняет барьер записи и помечает карту грязной. На minor GC сборщик сканирует как дополнительные корни только грязные карты, а не весь old.

Это постоянная плата за поколения: несколько лишних инструкций на каждое присваивание ссылки в работающем приложении.

Что будет, если minor GC не учтёт ссылку из old в young?

Он посчитает молодой объект мёртвым и освободит его место, а старый объект останется со ссылкой на мусор. Это повреждение памяти, поэтому барьер записи обязателен.
