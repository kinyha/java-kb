JVM: References

Кеш на WeakHashMap, а записи не исчезают

Задача: хранить сессию, пока жив объект пользователя, и забывать её, когда пользователь больше никому не нужен. Для этого есть WeakHashMap — карта, которая сама удаляет запись, когда ключ перестал быть нужен кому-то, кроме неё. Сессия хранит ссылку на своего пользователя, это естественно:

import java.util.*;

public class SessionCache {
    record User(String login) { }
    record Session(User user, byte[] data) { }                // значение держит ключ

    public static void main(String[] args) throws Exception {
        Map<User, Session> cache = new WeakHashMap<>();
        for (int i = 0; i < 10_000; i++) {
            User u = new User("user" + i);
            cache.put(u, new Session(u, new byte[1024]));      // ссылка на u из значения
        }
        System.gc();
        Thread.sleep(100);
        System.out.println("записей после GC: " + cache.size());

        Map<User, byte[]> fixed = new WeakHashMap<>();
        for (int i = 0; i < 10_000; i++) fixed.put(new User("user" + i), new byte[1024]);
        System.gc();
        Thread.sleep(100);
        System.out.println("без ссылки на ключ: " + fixed.size());
    }
}
записей после GC: 10000
без ссылки на ключ: 0

Никто, кроме карты, не держит пользователей. Но первая карта не отдала ни одной записи, а вторая отдала все. Разница — одно поле: Session.user. Карта держит значение обычной ссылкой, значение держит ключ, и ключ остаётся достижимым из самой карты.

Чтобы видеть такие вещи сразу, нужно понимать, что такое «слабая» ссылка для сборщика. В этой теме разберём четыре силы ссылок: как GC обращается с каждой, как устроены WeakHashMap и ReferenceQueue, почему кеш на SoftReference — плохая идея и почему finalize() заменили на Cleaner.

Сила ссылки решает, когда GC имеет право забрать объект

Обычная ссылка в поле или переменной — сильная: пока до объекта есть путь по сильным ссылкам от корней, GC его не тронет. Остальные три вида — это объекты-обёртки из java.lang.ref. Сама обёртка — обычный объект, на который ссылаются сильно. Но её внутреннее поле referent сборщик при маркировке не считает за сильную ссылку. Поэтому объект, до которого можно дойти только через обёртку, GC может забрать, соблюдая правила её вида.

Проверим на живой JVM. Soft- и weak-ссылки по 10 МБ, heap 64 МБ. Сначала явная сборка, потом заполняем heap до OutOfMemoryError:

import java.lang.ref.*;
import java.util.*;

public class Kinds {
    public static void main(String[] args) {
        byte[] strongArr = new byte[10 << 20];
        SoftReference<byte[]> soft = new SoftReference<>(new byte[10 << 20]);  // 10 МБ
        WeakReference<byte[]> weak = new WeakReference<>(new byte[10 << 20]);
        System.gc();
        System.out.printf("после System.gc(): soft=%s weak=%s%n", soft.get() != null, weak.get() != null);

        List<byte[]> hog = new ArrayList<>();
        try {
            while (true) hog.add(new byte[1 << 20]);               // съедаем heap по мегабайту
        } catch (OutOfMemoryError e) {
            hog = null;                                            // отпускаем память
            System.out.printf("после OOM: soft=%s, strong жив: %s%n", soft.get() != null, strongArr.length > 0);
        }
    }
}
$ java -Xmx64m Kinds
после System.gc(): soft=true weak=false
после OOM: soft=false, strong жив: true

Weak-ссылку очистила первая же сборка. Soft пережила полную сборку и исчезла, только когда памяти не осталось. Сильную ссылку GC не тронул и перед OOM: OutOfMemoryError — это отказ выделить память, а не разрешение отбирать живое.

WeakHashMap держит ключи слабо, а значения — сильно

Устройство WeakHashMap объясняет и пример из начала, и все её ловушки. Каждая запись — это WeakReference на ключ с общей очередью; в исходниках JDK это class Entry<K,V> extends WeakReference<Object>. Значение запись хранит обычным полем.

  • Когда ключ стал слабо достижим, GC очищает ссылку в записи и ставит запись в очередь.
  • Карта не узнаёт об этом сама. При следующем обращении — get, put, size — она вызывает expungeStaleEntries(), вынимает записи из очереди и удаляет их вместе со значениями.
  • В очередь ссылки ставит не сам сборщик, а поток JDK Reference Handler, уже после паузы. Поэтому сразу после System.gc() карта ещё полная. Проверено: 1000 записей сразу после сборки и 0 через 100 мс. Отсюда Thread.sleep(100) в примерах урока.

Отсюда первая ловушка: значение не должно ссылаться на ключ ни прямо, ни через цепочку объектов. Иначе ключ сильно достижим через значение, а значение — через карту. Так было с Session.user. Вторая ловушка — ключи, которые живут вечно сами по себе:

import java.util.*;

public class CachedKeys {
    public static void main(String[] args) throws Exception {
        Map<Object, String> map = new WeakHashMap<>();
        for (int i = 0; i < 1000; i++) map.put(i, "v");            // автоупаковка: Integer.valueOf(i)
        map.put("literal", "v");                                  // строковый литерал из пула
        map.put(new String("copy"), "v");
        System.gc();
        Thread.sleep(100);                                         // очередь ссылок наполняется асинхронно
        System.out.println("осталось: " + map.size() + ", literal: " + map.containsKey("literal"));
    }
}
осталось: 129, literal: true

Осталось 129 записей: ключи 0–127 — это закешированные Integer.valueOf, на них всегда ссылается внутренний кеш Integer. Ещё одна — литерал: его держит пул строк класса. Слабый ключ работает только с объектами, у которых есть естественный конец жизни.

Третья ловушка — сравнение ключей. WeakHashMap сравнивает через equals. Если ключ — record или строка, другой равный объект найдёт запись, но жизнь записи привязана к конкретному экземпляру. Для метаданных «к этому объекту» обычно нужна идентичность. В Caffeine так и устроено: Caffeine.newBuilder().weakKeys() сравнивает ключи по ==.

ThreadLocal: слабый ключ не спасает значение

Внутри каждого потока ThreadLocal хранит значения в карте ThreadLocalMap, где ключ — слабая ссылка на сам ThreadLocal, а значение — обычная. Если ThreadLocal забыт, ключ обнулится, но значение останется в карте потока. Уберёт его только следующее обращение этого потока к своей карте. В пуле потоки живут долго:

import java.util.concurrent.*;

public class PoolLocals {
    static long usedMb() {
        System.gc();
        Runtime rt = Runtime.getRuntime();
        return (rt.totalMemory() - rt.freeMemory()) >> 20;
    }

    static void task(boolean remove) {
        ThreadLocal<byte[]> ctx = new ThreadLocal<>();              // новый ThreadLocal на задачу
        ctx.set(new byte[100_000]);                                 // ~100 КБ контекста запроса
        if (remove) ctx.remove();
    }

    public static void main(String[] args) throws Exception {
        boolean remove = args[0].equals("remove");
        ExecutorService pool = Executors.newSingleThreadExecutor(); // поток живёт между задачами
        for (int i = 0; i < 1000; i++) pool.submit(() -> task(remove)).get();
        System.out.println("после 1000 задач и GC: " + usedMb() + " МБ");
        pool.submit(() -> task(true)).get();                        // поток снова тронул свою карту
        System.out.println("после ещё одной задачи: " + usedMb() + " МБ");
        pool.shutdown();
    }
}
$ java -Xmx1g PoolLocals leak
после 1000 задач и GC: 33 МБ
после ещё одной задачи: 2 МБ
$ java -Xmx1g PoolLocals remove
после 1000 задач и GC: 2 МБ
после ещё одной задачи: 2 МБ

После полной сборки 33 МБ значений остались жить (в разных запусках от 33 до 43 МБ: часть карта успевает убрать сама между задачами). Ключи обнулены, а значения держит карта потока. Их убрала только следующая задача, которая сама вызвала set. Типичный случай в проде хуже: ThreadLocal лежит в static-поле и не умирает никогда, поэтому слабый ключ вообще не срабатывает. Значение живёт до конца жизни потока, а следующий запрос в этом потоке видит чужой контекст. Правило одно: remove() в finally.

SoftReference живёт, пока ею пользуются и пока heap свободен

Soft-ссылку HotSpot очищает не «когда памяти мало», а по правилу давности. Ссылку очистят, если к ней не обращались дольше, чем

свободно в heap, МБ  ×  SoftRefLRUPolicyMSPerMB (по умолчанию 1000 мс)

«Свободно» здесь — от максимального heap: -Xmx минус занятое после прошлой сборки. Обращение — это get(): он обновляет метку времени. При heap 256 МБ и 2 МБ занятых порог — 254 МБ × 1000 мс, больше четырёх минут. Если памяти не хватает, до OutOfMemoryError очищаются все soft-ссылки.

Проверим правило. Программа создаёт soft-ссылку и раз в 100 мс вызывает полную сборку. Проверяет она ссылку через refersTo(null) (Java 16+): этот метод, в отличие от get(), не обновляет метку времени.

import java.lang.ref.SoftReference;

public class SoftAge {
    public static void main(String[] args) throws Exception {
        SoftReference<byte[]> soft = new SoftReference<>(new byte[1024]);
        long start = System.currentTimeMillis();
        while (!soft.refersTo(null) && System.currentTimeMillis() - start < 5000) {
            Thread.sleep(100);
            System.gc();                                  // полная сборка раз в 100 мс
        }
        System.out.println(soft.refersTo(null)
            ? "очищена через " + (System.currentTimeMillis() - start) + " мс"
            : "жива через 5 с");
    }
}
$ java -Xmx256m SoftAge                                  # порог 254 × 1000 мс ≈ 4 мин
жива через 5 с
$ java -Xmx256m -XX:SoftRefLRUPolicyMSPerMB=10 SoftAge   # порог 254 × 10 мс ≈ 2,5 с
очищена через 2697 мс
$ java -Xmx256m -XX:SoftRefLRUPolicyMSPerMB=1 SoftAge    # порог ≈ 0,25 с
очищена через 445 мс

Если в цикле проверять ссылку через get(), она не очищается ни при каком значении флага: каждый вызов делает её «свежей». Проверено тем же запуском.

Отсюда понятно, почему кеш на soft-ссылках — плохая идея:

  • Размер кеша задаёт сборщик, а не ты. Пока heap свободен, soft-кеш растёт и держит почти всё. Heap выглядит занятым, и G1 чаще запускает маркировку и смешанные сборки.
  • Очистка приходит волной. При нехватке памяти GC сбрасывает все soft-ссылки разом. Кеш пустеет целиком в самый нагруженный момент, и все запросы идут в базу.
  • Поведение зависит от -Xmx и флагов. Тот же код ведёт себя по-разному на подах разного размера.

Поэтому кеши ограничивают явно — по числу записей или по весу, например Caffeine.newBuilder().maximumSize(10_000). Предсказуемо, и видно в метриках.

ReferenceQueue сообщает, что объект умер, а PhantomReference — только это

Проверять get() == null в цикле неудобно. Если при создании ссылки передать ReferenceQueue, сборщик сам поставит в неё обёртку, когда очистит ссылку. Остаётся забрать её через poll() или ждать через remove():

import java.lang.ref.*;

public class Queue {
    public static void main(String[] args) throws Exception {
        ReferenceQueue<Object> queue = new ReferenceQueue<>();
        Object weakTarget = new Object(), phantomTarget = new Object();
        WeakReference<Object> weak = new WeakReference<>(weakTarget, queue);
        PhantomReference<Object> phantom = new PhantomReference<>(phantomTarget, queue);
        System.out.println("phantom.get() = " + phantom.get());   // всегда null
        System.out.println("в очереди до GC: " + queue.poll());

        weakTarget = null;
        phantomTarget = null;                                     // объекты стали недостижимы
        System.gc();
        for (int i = 0; i < 2; i++) {
            Reference<?> r = queue.remove(1000);                  // ждём, пока GC положит ссылку
            System.out.println("из очереди: " + (r == weak ? "weak" : r == phantom ? "phantom" : r)
                + ", get() = " + r.get());
        }
    }
}
phantom.get() = null
в очереди до GC: null
из очереди: weak, get() = null
из очереди: phantom, get() = null

В очередь попадает обёртка, а не объект: к этому моменту он уже недоступен. Поэтому данные для уборки хранят не в объекте, а рядом с обёрткой — например, в подклассе ссылки или в карте «ссылка → ресурс». Так и работает WeakHashMap: её запись — это и есть подкласс ссылки с ключом и значением.

Зачем нужна ссылка, через которую ничего нельзя получить? Чтобы узнать о смерти объекта, не давая возможности его «оживить». Weak-ссылку GC очищает, пока объект ещё может ожить через finalize(). Phantom-ссылка попадает в очередь, только когда объект окончательно недостижим. С Java 9 GC и очищает её сам, как weak, так что память объекта освобождается сразу. На phantom-ссылках построен Cleaner — замена finalize().

finalize() замедляет выделение, воскрешает объекты и копит очередь до OOM

Метод finalize() был первым способом освобождать внешние ресурсы. JVM вызывает его один раз, когда объект стал недостижим. С Java 9 он deprecated, с Java 18 помечен к удалению (JEP 421), и javac предупреждает:

warning: [removal] finalize() in Object has been deprecated and marked for removal

Почему от него отказались — видно по замерам. Три миллиона объектов по 1 КБ, с непустым finalize() и без:

public class Finalizers {
    static volatile long finalized;
    static final Object[] SINK = new Object[1024];                   // чтобы JIT не убрал выделение

    static class Plain { byte[] data = new byte[1024]; }

    static class WithFinalize {
        byte[] data = new byte[1024];
        @Override @SuppressWarnings("removal")
        protected void finalize() { finalized++; }                   // любое непустое тело
    }

    public static void main(String[] args) {
        boolean withFinalize = args[0].equals("finalize");
        long start = System.nanoTime();
        for (int i = 0; i < 3_000_000; i++)                          // 3 млн объектов по ~1 КБ
            SINK[i & 1023] = withFinalize ? new WithFinalize() : new Plain();
        System.out.printf("%s: %d мс, finalize() вызван для %d тыс.%n",
            args[0], (System.nanoTime() - start) / 1_000_000, finalized / 1000);
    }
}
$ java -Xmx2g Finalizers plain
plain: 270 мс, finalize() вызван для 0 тыс.
$ java -Xmx2g Finalizers finalize
finalize: 1321 мс, finalize() вызван для 2213 тыс.
$ java -Xmx256m Finalizers finalize
Exception: java.lang.OutOfMemoryError thrown from the UncaughtExceptionHandler in thread "main"
$ java --finalization=disabled -Xmx256m Finalizers finalize
finalize: 239 мс, finalize() вызван для 0 тыс.

В пять раз медленнее при 2 ГБ и OutOfMemoryError при 256 МБ, хотя живых объектов — не больше 1024. Причины:

  • Регистрация при создании. Для каждого объекта класса с finalize() JVM создаёт служебную FinalReference. С -Xlog:gc+phases+ref=debug видно, что одна молодая сборка нашла 34 174 таких ссылки: FinalReference Discovered: 34174. На обработку ссылок ушло 6,4 мс паузы.
  • Две сборки вместо одной. Мёртвый объект с finalize() нельзя сразу освободить. GC оставляет его живым вместе со всем, на что он ссылается, и ставит в очередь. После вызова метода объект освобождает только следующая сборка.
  • Один поток на всех. finalize() вызывает единственный поток Finalizer. Если объекты умирают быстрее, чем он успевает, очередь растёт до OOM. Именно это случилось при 256 МБ.

Любопытная деталь: с пустым finalize() { } замедления нет. HotSpot видит пустое тело и не регистрирует объекты — проверено тем же замером.

Ещё одна проблема — воскрешение. В finalize() можно сохранить this в статическое поле, и объект снова станет достижим. Но второй раз метод не вызовется:

public class Resurrect {
    static Resurrect saved;
    static int calls;

    @Override @SuppressWarnings("removal")
    protected void finalize() {
        calls++;
        saved = this;                                  // объект снова достижим
    }

    public static void main(String[] args) throws Exception {
        new Resurrect();
        for (int round = 1; round <= 2; round++) {
            saved = null;                              // снова недостижим
            System.gc();
            Thread.sleep(100);                         // finalize() работает в отдельном потоке
            System.out.println("раунд " + round + ": finalize вызван " + calls + " раз, объект жив: " + (saved != null));
        }
    }
}
раунд 1: finalize вызван 1 раз, объект жив: true
раунд 2: finalize вызван 1 раз, объект жив: false

Вдобавок нет гарантии, что finalize() вызовется вообще: JVM может завершиться раньше. А исключение внутри метода молча проглатывается. С Java 18 финализацию можно выключить флагом --finalization=disabled и проверить, не зависит ли от неё приложение.

Cleaner освобождает ресурс, если действие очистки не держит сам объект

java.lang.ref.Cleaner (Java 9) решает ту же задачу через phantom-ссылки. Объект регистрируется вместе с действием очистки. Когда объект становится недостижим, отдельный поток Cleaner выполняет действие. Воскресить объект нельзя: действие его не получает. А очистку можно запустить и вручную, через clean().

Правильный шаблон — ресурс с close() для явного освобождения и Cleaner как страховка, если close() забыли:

import java.lang.ref.Cleaner;
import java.util.concurrent.atomic.AtomicInteger;

public class NativeBuffer implements AutoCloseable {
    static final Cleaner CLEANER = Cleaner.create();
    static final AtomicInteger FREED = new AtomicInteger();

    // состояние для очистки: отдельный static-класс без ссылки на NativeBuffer
    private static final class State implements Runnable {
        final long address;
        State(long address) { this.address = address; }
        public void run() { FREED.incrementAndGet(); }           // здесь был бы free(address)
    }

    private final Cleaner.Cleanable cleanable;

    NativeBuffer(long address) {
        this.cleanable = CLEANER.register(this, new State(address));
    }

    @Override
    public void close() { cleanable.clean(); }                    // явное освобождение; повторно не выполнится

    public static void main(String[] args) throws Exception {
        try (NativeBuffer b = new NativeBuffer(1)) { }            // закрыт явно
        for (int i = 0; i < 1000; i++) new NativeBuffer(i);       // забыли закрыть
        System.gc();
        Thread.sleep(200);                                        // поток Cleaner работает асинхронно
        System.out.println("освобождено: " + FREED.get());
    }
}
освобождено: 1001

Один буфер закрыт явно, тысячу подобрал Cleaner. Так устроен и DirectByteBuffer в JDK: при создании он регистрирует Deallocator — record с адресом и размером памяти, без ссылки на сам буфер.

Главная ловушка — действие очистки, которое ссылается на объект. Самый частый случай — лямбда, которая захватила this:

import java.lang.ref.Cleaner;
import java.util.concurrent.atomic.AtomicInteger;

public class LeakyCleaner {
    static final Cleaner CLEANER = Cleaner.create();
    static final AtomicInteger FREED = new AtomicInteger();
    final long address;

    LeakyCleaner(long address) {
        this.address = address;
        CLEANER.register(this, () -> free(this.address));          // лямбда захватила this
    }

    static void free(long address) { FREED.incrementAndGet(); }

    public static void main(String[] args) throws Exception {
        for (int i = 0; i < 1000; i++) new LeakyCleaner(i);
        System.gc();
        Thread.sleep(200);
        System.out.println("освобождено: " + FREED.get());
    }
}
освобождено: 0

Ни одного. Cleaner держит действие сильной ссылкой, действие держит this, и объект никогда не станет недостижимым. Это та же ошибка, что с Session.user в начале урока: путь от «держателя» к объекту через то, что должно было быть независимым. То же случится с анонимным или нестатическим вложенным классом — они тоже держат ссылку на внешний объект.

Cleaner — это замена close(), можно не закрывать ресурсы явно.

Cleaner срабатывает, только когда GC заметит, что объект недостижим, — через секунды, минуты или никогда, если памяти хватает. Файловые дескрипторы или соединения кончатся раньше. Основной путь — try-with-resources, Cleaner — только страховка.

  • Сильная ссылка держит объект всегда. Soft, weak и phantom — обёртки, поле referent которых GC не считает сильной ссылкой.
  • Weak очищается первой же сборкой, которая увидит объект только слабо достижимым. Soft — при нехватке памяти или если давно не использовалась: порог — свободные мегабайты × SoftRefLRUPolicyMSPerMB.
  • WeakHashMap держит ключ слабо, а значение сильно. Значение не должно ссылаться на ключ. Кешированные Integer и литералы как ключи не умирают.
  • ReferenceQueue получает обёртки очищенных ссылок. Phantom-ссылка: get() всегда null, только сигнал о смерти объекта.
  • finalize() медленный, воскрешает объекты и может довести до OOM. Замена — close() плюс Cleaner, действие которого не ссылается на объект.
  • Кеш ограничивают размером, а не soft-ссылками. ThreadLocal в пуле очищают через remove() в finally.

На собеседовании

Какие виды ссылок есть в Java и чем они отличаются?

Четыре. Сильная — обычная ссылка: пока объект сильно достижим, GC его не тронет. SoftReference очищается, когда памяти не хватает или ссылкой давно не пользовались, и гарантированно до OutOfMemoryError. WeakReference очищается на первой же сборке, где объект достижим только слабо. PhantomReference всегда возвращает null и нужна, чтобы узнать через ReferenceQueue, что объект умер, — на ней построен Cleaner.

Примеры: weak — WeakHashMap, ключи ThreadLocalMap, слушатели; phantom — освобождение native-памяти у DirectByteBuffer.

  • Soft-ссылки HotSpot очищает по давности: порог — свободные МБ heap × SoftRefLRUPolicyMSPerMB (1000 мс). get() обновляет метку времени.
  • С Java 9 phantom-ссылки очищаются автоматически, как weak, и память объекта освобождается без вызова clear().
  • В очередь ссылки ставит поток Reference Handler после паузы, поэтому сразу после сборки очередь может быть пуста.
Зачем нужна ссылка, у которой get() всегда возвращает null?

Чтобы получить сигнал о смерти объекта без возможности его воскресить. Обёртка попадает в очередь, когда объект окончательно недостижим. Данные для уборки хранят рядом с ней, а не в объекте. Так работают Cleaner и освобождение памяти DirectByteBuffer.

В WeakHashMap положили ключи 0..999 через автоупаковку и строковый литерал. Сколько записей останется после GC?

129. Integer.valueOf кеширует значения от −128 до 127, на них ссылается кеш, так что 128 ключей живы. Литерал держит пул строк. Остальные 872 ключа умрут. Проверено запуском.

Как работает WeakHashMap и когда она не очищается?

Каждая запись — WeakReference на ключ с общей ReferenceQueue, значение хранится обычным полем. Когда ключ становится слабо достижим, GC очищает ссылку и ставит запись в очередь. Карта удаляет такие записи при следующем обращении — get, put, size.

Не очищается, если значение прямо или косвенно ссылается на ключ; если ключи живут сами — кешированные Integer, литералы, enum; если ключ где-то ещё держат сильно.

Кеш: Map<User, Session> cache = new WeakHashMap<>(); cache.put(u, new Session(u, data)). Жалуются на рост памяти. Что не так?

Session ссылается на User. Карта держит значение сильно, значение держит ключ, и ключ никогда не станет слабо достижимым. Нужно убрать ссылку на ключ из значения или хранить её как WeakReference. А лучше взять кеш с явным ограничением и вытеснением, например Caffeine.

Стоит ли делать кеш на SoftReference?

Обычно нет. Размер такого кеша определяет сборщик. Пока heap свободен, кеш держит почти всё, и G1 чаще запускает маркировку. При нехватке памяти GC сбрасывает все soft-ссылки разом, кеш пустеет целиком под нагрузкой, и запросы идут в базу. Поведение зависит от -Xmx. Лучше ограничить кеш явно — по числу записей или весу — и видеть его в метриках.

Soft-ссылка в тесте не очищается, хотя SoftRefLRUPolicyMSPerMB=1 и сборки идут. Почему?

Скорее всего, тест проверяет её через get(). Каждый вызов обновляет метку последнего использования, и ссылка всегда «свежая». Проверять без обновления можно через refersTo(null) (Java 16+).

Почему finalize() устарел и чем его заменить?

finalize() не гарантирует, что вызов вообще случится и когда. Он замедляет создание объектов: каждый регистрируется через FinalReference. Мёртвый объект живёт на одну сборку дольше. Все вызовы идут в одном потоке, и при быстрой смерти объектов очередь растёт до OOM. Ещё finalize() позволяет воскресить объект. С Java 18 метод помечен к удалению.

Замена — явное освобождение через AutoCloseable и try-with-resources, а как страховка — java.lang.ref.Cleaner на phantom-ссылках.

  • В замере урока 3 млн объектов с непустым finalize() создавались в пять раз дольше, а при heap 256 МБ программа упала с OOM.
  • --finalization=disabled (Java 18+) проверяет, не зависит ли приложение от финализации.
В конструкторе: CLEANER.register(this, () -> free(this.address)). Что не так?

Лямбда захватила this. Cleaner держит действие сильно, действие держит объект, и объект никогда не станет недостижимым: очистка не выполнится ни разу, в замере урока — 0 из 1000. Действие должно быть статическим классом или лямбдой, захватывающей только нужные значения, например локальную копию адреса.

Почему ThreadLocal может течь в пуле потоков?

Значения хранятся в карте самого потока, ThreadLocalMap. Ключ — слабая ссылка на ThreadLocal, значение — сильная. Поток пула живёт долго, и значение живёт вместе с ним, пока его не удалят. Если ThreadLocal статический, ключ не умирает никогда. Если его забыли, значение остаётся до следующего обращения потока к карте. Ещё следующая задача в этом потоке может увидеть чужой контекст. Решение — remove() в finally.
