JVM: GC Logs & Tuning

Паузы по 2 мс, а через десять секунд — OutOfMemoryError

На дашборде сервиса график максимальной паузы GC зелёный: меньше 3 мс. Вот лог сборщика этого сервиса за десять секунд до падения. Это реальный запуск сервиса урока с heap 512 МБ (его код — в шаге 4); показаны строки Prepare Mixed подряд, остальные пропущены:

А в консоли процесса одна строка. Памяти не хватило даже на то, чтобы напечатать стек:

Exception: java.lang.OutOfMemoryError thrown from the UncaughtExceptionHandler in thread "main"

Паузы в этих строках даже уменьшаются: 1,8 → 1,4 мс. Смерть предсказывает другое число — то, что стоит после стрелки: 368 → 380 → 394 → 406 → 417 МБ. После каждой сборки в heap остаётся на 12 МБ больше. Это утечка, и лог показал её за десять секунд до падения.

В этой теме — как включить лог и прочитать строку, какие три числа из него извлекать и как по ним отличить утечку от маленького heap. Потом разберём причины full GC и настройки: какие помогают, а какие ломают то, что работало.

Лог GC включают одним флагом, и в проде он нужен всегда

С Java 9 все логи JVM идут через единый механизм unified logging и включаются флагом -Xlog. Рабочий вариант для прода:

java \
  -Xlog:gc*:file=/var/log/app/gc-%p.log:time,uptime,level,tags:filecount=5,filesize=20m \
  -jar app.jar
# gc*                   что писать: тег gc и все его сочетания (gc+heap, gc+phases, gc+cpu...)
# file=...gc-%p.log     куда: файл, %p заменится на pid процесса
# time,uptime,...       что писать в квадратных скобках перед сообщением
# filecount, filesize   ротация: 5 старых файлов по 20 МБ, дальше самые старые удаляются

Общая форма флага — -Xlog:что:куда:декораторы:опции, любую часть справа можно опустить. -Xlog:gc пишет одну строку на паузу в stdout; -Xlog:gc* добавляет фазы, регионы и CPU — порядка килобайта на сборку. Если сборки идут раз в секунду, за сутки набирается около 100 МБ, поэтому нужна ротация.

Строка gc,cpu помогает найти скрытую проблему. В норме User больше Real: несколько потоков работали параллельно. Если Real заметно больше User + Sys, потоки сборщика стояли без CPU. Обычно это троттлинг контейнера или своп, и настройкой GC такое не лечится.

Из лога берут три числа: скорость выделения, живые данные и долю пауз

Все решения о настройке сводятся к трём числам:

  • Allocation rate — сколько мегабайт в секунду создаёт приложение. От него зависит частота молодых сборок: при eden 240 МБ и 400 МБ/с сборка будет примерно каждые 0,6 с.
  • Live set — сколько данных действительно живо. От него зависит минимальный разумный heap, длительность маркировки и full GC.
  • Доля времени в паузах — сколько процентов времени приложение стоит. Если держится выше нескольких процентов, пора разбираться.

Сервис урока — имитация: кеш на заданное число мегабайт и 50 000 запросов в секунду, каждый создаёт 8 КБ временных данных и обновляет одну запись кеша. Аргументы: размер кеша в МБ, режим (ok или leak) и длительность в секундах, например java -Xmx512m -Xlog:gc:file=gc.log Service 150 ok 90.

import java.util.*;

public class Service {
    static final Map<Integer, byte[]> CACHE = new HashMap<>(); // живые данные: кеш
    static final List<byte[]> AUDIT = new ArrayList<>();       // утечка: только растёт

    public static void main(String[] args) {
        int entries = Integer.parseInt(args[0]) * 10_000;       // ~100 байт на запись с ключом и узлом
        boolean leak = args[1].equals("leak");
        long end = System.currentTimeMillis() + Integer.parseInt(args[2]) * 1000L, req = 0;
        for (int i = 0; i < entries; i++) CACHE.put(i, new byte[32]);
        Random rnd = new Random(1);
        while (System.currentTimeMillis() < end) {
            long tick = System.nanoTime();
            for (int i = 0; i < 50; i++, req++) {                // 50 запросов в миллисекунду
                byte[] body = new byte[8 * 1024];                // временные данные запроса
                body[rnd.nextInt(body.length)] = 1;
                CACHE.put(rnd.nextInt(entries), new byte[32]);   // кеш обновляется
                if (leak && req % 10 == 0) AUDIT.add(new byte[4 * 1024]);
            }
            while (System.nanoTime() - tick < 1_000_000) Thread.onSpinWait();
        }
        System.out.println("запросов: " + req / 1000 + " тыс.");
    }
}

Все три числа видны на графике занятости heap, если построить его по строкам лога. Ниже реальный лог сервиса урока за 45 секунд. Heap 512 МБ, флаг G1ReservePercent объяснён в шаге 7.

Отсюда правило: live set оценивают по занятости после смешанной или полной сборки, а не после молодой. Точнее всего он виден после full GC: в другом запуске того же сервиса полная сборка оставила 148 МБ. Разница с 185 МБ — объекты молодого поколения и регионы old, которые G1 не стал чистить, потому что живых в них больше 85%.

Считать всё это глазами по сотням строк неудобно. Для разбора лога есть готовые инструменты — GCeasy, GCViewer, JDK Mission Control для JFR. Но три числа легко получить и самому, а заодно понять, откуда они берутся:

import java.nio.file.*;
import java.util.*;
import java.util.regex.*;

public class GcLogStats {
    // [12.345s][info][gc] GC(7) Pause Young (Normal) (G1 Evacuation Pause) 687M->182M(864M) 3.309ms
    static final Pattern PAUSE = Pattern.compile(
        "\\[(\\d+\\.\\d+)s\\].* GC\\(\\d+\\) (Pause \\w+).* (\\d+)M->(\\d+)M\\(\\d+M\\) (\\d+\\.\\d+)ms");

    public static void main(String[] args) throws Exception {
        double first = -1, last = 0, prevAfter = -1, allocated = 0, pauseSum = 0, pauseMax = 0;
        int pauses = 0;
        TreeMap<Integer, Double> floorByWindow = new TreeMap<>(); // минимум «после» в каждом 10-секундном окне
        for (String line : Files.readAllLines(Path.of(args[0]))) {
            Matcher m = PAUSE.matcher(line);
            if (!m.find()) continue;
            double t = Double.parseDouble(m.group(1)), before = Double.parseDouble(m.group(3));
            double after = Double.parseDouble(m.group(4)), ms = Double.parseDouble(m.group(5));
            if (first < 0) first = t;
            if (prevAfter >= 0 && before > prevAfter) allocated += before - prevAfter; // выросло между сборками
            prevAfter = after;
            last = t;
            pauses++; pauseSum += ms; pauseMax = Math.max(pauseMax, ms);
            if (m.group(2).equals("Pause Young") || m.group(2).equals("Pause Full"))
                floorByWindow.merge((int) t / 10 * 10, after, Math::min);
        }
        double seconds = last - first;
        System.out.printf("allocation rate: %.0f МБ/с%n", allocated / seconds);
        System.out.printf("паузы: %d, сумма %.0f мс (%.1f%% времени), макс %.1f мс%n",
            pauses, pauseSum, pauseSum / 10 / seconds, pauseMax);
        floorByWindow.forEach((w, mb) -> System.out.printf("  %3d–%3d с: после сборки ≥ %.0f МБ%n", w, w + 10, mb));
    }
}

Утечку выдаёт нижняя граница, которая растёт даже после маркировки

Теперь тот же сервис с утечкой. Каждый десятый запрос добавляет 4 КБ в список, из которого ничего не удаляют. Это 20 МБ/с на фоне тех же 400 МБ/с короткоживущих объектов. Heap тот же, 512 МБ. График построен по реальному логу этого запуска:

Увеличение heap утечку не лечит, а только откладывает падение. При утечке 20 МБ/с каждый лишний гигабайт heap даёт меньше минуты. Поэтому в проде сразу включают дамп при падении: -XX:+HeapDumpOnOutOfMemoryError -XX:HeapDumpPath=/dumps. Дамп покажет, какой объект держит память, — в этом примере список AUDIT. Как снимать и читать дамп — в теме Diagnostics.

Паузы короткие — значит, со сборщиком всё в порядке.

Короткие паузы не говорят о здоровье. В примере с утечкой ни одна пауза не превысила 22 мс, а сервис умер. Смотреть нужно на нижнюю границу после сборок, частоту сборок и долю времени в паузах.

Heap меньше трёх live set — это постоянная маркировка и full GC

Какой heap дать сервису с live set 148 МБ? Прогоним тот же сервис без утечки по 30 секунд с разным -Xmx. Нагрузка одинаковая: 50 000 запросов в секунду, 400 МБ/с. CPU в паузах — сумма User + Sys из строк gc,cpu:

  • Меньше 2,5× live set G1 почти всё время маркирует: 75 циклов за 30 секунд при 1,6×. Это конкурентная работа на CPU, которой нет в паузах. И всё равно дважды он не успел и упал в full GC — максимальная пауза выросла в пять-семь раз.
  • С 3,5× маркировок и full GC за 30 секунд нет, паузы до 5 мс.
  • Дальше heap работает как кеш времени: чем больше eden, тем реже молодые сборки и меньше CPU на них. Но отдача падает: переход с 1 на 2 ГБ сэкономил 0,3 секунды CPU за 30 секунд работы.

Отсюда стартовое правило — heap в 3–4 раза больше live set. Дальше его проверяют по логу под нагрузкой. Это ориентир, а не закон. Сервису с большим allocation rate и объектами средней жизни нужно больше: программе из темы ZGC & Shenandoah с live set 728 МБ не хватило и 3× — 74 full GC за 10 секунд, а 6× хватило.

Ещё три практических правила:

  • -Xms равен -Xmx в проде. Heap не будет расти и сжиматься на ходу, а под всё равно резервирует память под лимит. Флаг -XX:+AlwaysPreTouch заранее трогает все страницы heap: старт медленнее, зато первые запросы не платят за page fault.
  • В контейнере heap задают долей от лимита: -XX:MaxRAMPercentage=75. Остальное нужно metaspace, стекам потоков, direct-буферам и code cache — подробно в теме Native Memory.
  • Число после ( в строке лога — текущий размер heap, а не -Xmx. Если он заметно меньше -Xmx и сборки частые, G1 держит heap маленьким. Это ещё один довод за -Xms = -Xmx.

У каждого full GC в G1 есть причина, и она написана в скобках

В G1 full GC — аварийный режим: сборщик не успел или не смог освободить место обычным путём. Поэтому любой full GC — повод разобраться. Причина записана в строке лога, а для первых двух ниже виден и сигнал, который ей предшествует.

Evacuation Failure: живых некуда копировать

Сервис урока без утечки, heap 512 МБ, 90 секунд. Первая же смешанная сборка после маркировки не нашла свободных регионов для копирования:

[41.520s][info][gc] GC(68) Pause Young (Mixed) (G1 Evacuation Pause) (Evacuation Failure) 483M->505M(512M) 6.926ms
[41.537s][info][gc] GC(69) Pause Young (Mixed) (G1 Evacuation Pause) (Evacuation Failure) 510M->510M(512M) 5.800ms
[41.554s][info][gc] GC(70) Pause Full (G1 Compaction Pause) 510M->148M(512M) 16.608ms

Занятость после сборки выросла: 483 → 505 МБ. Часть объектов успела скопироваться, а скопировать остальные было некуда. Они остались на месте, и регион не освободился — в нём теперь и оригиналы, и часть копий. G1 держит запас под копирование — G1ReservePercent, по умолчанию 10% heap. Смешанной сборке пришлось копировать живые записи кеша из old, и запаса не хватило. Следующая пауза уже не смогла ничего, и G1 сделал full GC. Он же показал настоящий live set — 148 МБ.

Три способа это лечить, каждый прогнан на том же сервисе по 90 секунд:

+ -XX:G1ReservePercent=200025,1 мс
+ -XX:InitiatingHeapOccupancyPercent=30 -XX:-G1UseAdaptiveIHOP00414,3 мс

Больший запас решает проблему точечно — это запуск, по которому построен график шага 4. Ранняя маркировка тоже работает, но ценой 41 цикла за полторы минуты: это CPU, которого нет в паузах. Больше heap — самое простое решение, если память есть.

System.gc(): полная сборка по просьбе кода

System.gc() в G1 по умолчанию делает full GC. Его вызывают не только из кода приложения, но и из библиотек и самого JDK. Например, java.nio.Bits.reserveMemory вызывает System.gc(), когда кончается лимит direct-памяти: так он заставляет JVM освободить буферы, на которые уже никто не ссылается. Проверим программой, которая выделяет тысячу direct-буферов по мегабайту и сразу их бросает, при лимите 64 МБ:

import java.nio.ByteBuffer;

public class Direct {
    public static void main(String[] args) {
        for (int i = 0; i < 1_000; i++) {
            ByteBuffer buf = ByteBuffer.allocateDirect(1024 * 1024); // 1 МБ вне heap
            buf.put(0, (byte) 1);                                     // ссылка теряется сразу
        }
        System.out.println("выделено 1000 МБ direct-буферами");
    }
}

Популярный совет «выключите System.gc() флагом DisableExplicitGC» ломает приложения с direct-буферами — Netty, Kafka-клиенты, NIO-серверы. Безопаснее -XX:+ExplicitGCInvokesConcurrent: вызов запускает конкурентную маркировку вместо full GC, и буферы освобождаются без длинной паузы.

Metaspace: утечка классов

Когда Metaspace доходит до порога, G1 запускает маркировку, чтобы выгрузить ненужные классы — это (Metadata GC Threshold). Если задан -XX:MaxMetaspaceSize и места не хватает, дальше идёт full GC, потом ещё один с очисткой soft-ссылок, и в конце OOM. Программа грузит 20 000 копий класса, каждую своим загрузчиком, и держит их:

import java.util.*;

public class ClassLeak {
    static class Box { int a, b, c; }

    public static void main(String[] args) throws Exception {
        byte[] bytes = ClassLeak.class.getResourceAsStream("ClassLeak$Box.class").readAllBytes();
        List<Class<?>> keep = new ArrayList<>();       // классы держатся — их загрузчики не выгрузить
        for (int i = 0; i < 20_000; i++) {
            keep.add(new ClassLoader() {                // свой загрузчик на каждую копию, как при редеплое
                Class<?> load() { return defineClass(null, bytes, 0, bytes.length); }
            }.load());
        }
    }
}
$ java -XX:MaxMetaspaceSize=16m -Xlog:gc ClassLeak     # показаны строки Pause Full
[0.044s][info][gc] GC(1) Pause Full (Metadata GC Threshold) 4M->4M(32M) 4.351ms
[0.047s][info][gc] GC(3) Pause Full (Metadata GC Clear Soft References) 4M->4M(32M) 3.187ms
[0.052s][info][gc] GC(5) Pause Full (Metadata GC Threshold) 5M->2M(32M) 4.358ms
java.lang.OutOfMemoryError: Metaspace

Heap здесь почти пуст, 4 МБ: смотреть на него бесполезно. Типичные причины в проде — загрузчик приложения, который не выгрузился после редеплоя, или библиотека, которая генерирует классы на каждый вызов. Лечат поиском утечки, а не увеличением лимита.

Heap мал или утечка

Это случаи из шагов 5 и 6: Pause Full (G1 Compaction Pause) без Evacuation Failure перед ним, но с растущей нижней границей или границей у самого -Xmx.

Настройку G1 начинают с heap и цели паузы, а флаги из статей чаще вредят

У G1 есть главная ручка — -XX:MaxGCPauseMillis, по умолчанию 200 мс. По ней сборщик сам подбирает размер молодого поколения и число old-регионов в смешанной сборке. Интуиция подсказывает: поставлю цель поменьше — паузы станут короче. Проверим на программе из темы ZGC & Shenandoah: она 10 секунд обрабатывает платежи с максимальной скоростью и держит живыми 3 млн последних. Heap 4 ГБ, live set около 728 МБ:

Повторные запуски расходятся на 2%. Что видно:

  • Цель 10 мс недостижима для этой нагрузки. G1 честно уменьшил молодое поколение, и сборок стало больше. Объекты стали чаще переживать сборку и уходить в old, а old заполнялся быстрее, чем G1 его чистил. Итог — 14 full GC, максимальная пауза стала хуже, и обработано на 17% меньше. Пауз дольше 10 мс стало вдвое меньше, но не ноль.
  • -Xmn фиксирует размер молодого поколения и отключает подстройку под цель паузы. Об этом прямо предупреждает руководство Oracle по G1. Маленький young — больше сборок и full GC. Большой — пропускная способность выросла на 9%, но пауза выросла вдвое, и начались full GC.
  • Цель 50 мс на этой нагрузке почти ничего не изменила: реальные паузы и так ниже.

Порядок настройки, который работает:

  1. Включить лог и снять три числа под настоящей нагрузкой.
  2. Убрать причины full GC: утечки, System.gc(), лишние humongous-объекты.
  3. Подобрать heap: 3–4× live set, -Xms = -Xmx.
  4. Задать реалистичную цель паузы, если 200 мс не устраивают.
  5. Только потом точечные флаги вроде G1ReservePercent или G1HeapRegionSize. Менять по одному и сравнивать лог до и после.
  6. Если цели не достичь ни при каком heap — менять сборщик. Об этом тема Choosing a Collector.

На собеседовании

Как включить лог GC и что в нём смотреть?

С Java 9 — флагом -Xlog:gc* в файл с ротацией, например -Xlog:gc*:file=gc.log:time,uptime,level,tags:filecount=5,filesize=20m. В проде лог включён всегда: он дешёвый, а без него после инцидента не восстановить картину.

В каждой строке смотрю тип сборки и причину в скобках, занятость heap до и после, размер heap и длительность паузы. По всему логу считаю три числа: allocation rate, live set и долю времени в паузах. И ищу тревожные строки: Evacuation Failure, Pause Full, System.gc().

  • На работающем процессе лог включается без рестарта: jcmd <pid> VM.log output=file=gc.log what=gc=info.
  • -Xlog:async (Java 17+) убирает блокировку на записи в медленный диск.
  • В строке gc,cpu Real больше User + Sys — потокам GC не давали CPU: троттлинг контейнера или своп.
Две строки подряд: [8.0s] Pause Young 432M->189M(512M) и [8.6s] Pause Young 431M->190M(512M). Какой allocation rate?

Между сборками занятость выросла со 189 до 431 МБ, то есть на 242 МБ за 0,6 с. Это около 400 МБ/с. Считают от «после» предыдущей сборки до «до» следующей, а не по одной строке.

Сервис стартует с -XX:+PrintGCDateStamps после перехода на Java 17 и не поднимается. Почему?

Флаг удалён вместе со старым логированием GC, и JVM с неизвестным флагом не стартует: Unrecognized VM option. Замена — декоратор time в -Xlog:gc*:...:time,uptime,level,tags.

Что такое allocation rate и live set и зачем их знать?

Allocation rate — сколько мегабайт в секунду создаёт приложение. Вместе с размером eden он задаёт частоту молодых сборок. Live set — объём действительно живых данных. От него зависят минимальный разумный heap и длительность маркировки и full GC.

Оба числа берут из лога. Allocation rate — рост занятости между сборками, делённый на время. Live set — занятость после смешанной или полной сборки: после молодой в old ещё лежат мёртвые объекты.

После каждой молодой сборки занятость растёт на пару мегабайт. Это утечка?

Не обязательно. Молодая сборка не проверяет old, и туда копятся объекты, которые умерли после перехода в old. Вывод делают по границе после маркировки и смешанных сборок. Если она возвращается на прежний уровень — утечки нет, если растёт от цикла к циклу — есть.

В логе частые full GC. Что будешь делать?

Сначала смотрю причину в скобках и что было перед full GC. Evacuation Failure — не хватило места под копирование: увеличиваю heap или запас G1ReservePercent. System.gc() — ищу, кто вызывает. Если это direct-буферы, ставлю ExplicitGCInvokesConcurrent. Metadata GC Threshold — утечка классов.

Потом смотрю на занятость после full GC во времени. Если она стабильна и близка к -Xmx — heap мал. Если растёт от сборки к сборке — это утечка, и нужен heap dump, а не больше памяти.

  • Full GC, который освобождает почти ничего, при растущей частоте сборок — признак скорого OOM. Ставлю HeapDumpOnOutOfMemoryError заранее, чтобы получить дамп при падении.
  • DisableExplicitGC ломает освобождение direct-памяти: Bits.reserveMemory рассчитывает на System.gc().
Строки: Pause Full (G1 Compaction Pause) 511M->460M(512M), через секунду 511M->485M, потом 509M->487M, 506M->488M, 503M->488M с интервалом 50–70 мс. Диагноз?

Утечка на грани OOM. Каждая полная сборка освобождает всё меньше, 460 → 485 → 487 МБ живых, и идут они всё чаще. Heap почти целиком занят живыми объектами. Нужен heap dump и поиск держателя; увеличение heap только отложит падение.

В PR к конфигу: «убираем full GC от System.gc() — добавил -XX:+DisableExplicitGC». Сервис на Netty. Что скажешь?

Опасно. При исчерпании лимита direct-памяти JDK вызывает System.gc(), чтобы освободить брошенные буферы. С этим флагом вызов ничего не делает, и сервис может упасть с OutOfMemoryError: Cannot reserve ... direct buffer memory. Лучше -XX:+ExplicitGCInvokesConcurrent или найти и убрать явный вызов.

Как выбрать размер heap?

Измеряю live set под реальной нагрузкой — по занятости после смешанных или полных сборок. Стартовый heap — в 3–4 раза больше. Дальше проверяю по логу: нет full GC, маркировки не идут подряд, доля пауз маленькая. В проде -Xms равен -Xmx, в контейнере heap задаю через MaxRAMPercentage и оставляю место под native-память.

  • При heap меньше 2,5× live set G1 почти непрерывно маркирует и иногда срывается в full GC. Это видно по числу Concurrent Mark Cycle.
  • Больше heap — реже молодые сборки и меньше CPU на них, но отдача быстро падает.

Какие параметры G1 ты бы настраивал?

Сначала никакие — пока лог не показал проблему. Потом по порядку: убрать причины full GC, подобрать heap, задать реалистичную цель паузы MaxGCPauseMillis. Точечные флаги — только после этого, по одному, с логом до и после.

Не трогаю -Xmn и NewRatio: они фиксируют молодое поколение и отключают подстройку под цель паузы.

Коллега поставил -XX:MaxGCPauseMillis=10 -Xmn2g, «чтобы паузы были короче». Что ответишь?

Эти флаги спорят друг с другом: -Xmn фиксирует молодое поколение, и цель паузы для него перестаёт работать. В замере урока -Xmn2g удвоил максимальную паузу и дал 11 full GC. А цель 10 мс на той же нагрузке снизила пропускную способность на 17% и тоже привела к full GC. Нужно убрать оба флага, снять лог и смотреть, откуда длинные паузы. Если цель в единицы миллисекунд обязательна — пробовать ZGC.
