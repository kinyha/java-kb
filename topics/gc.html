JVM: Garbage Collection

Платёж ждёт GC, хотя бизнес-код не изменился

Сервис проводит платежи за десятки миллисекунд, но иногда ответ задерживается на сотни. В этот момент JVM может останавливать Java-потоки ради части работы GC. По одной задержке нельзя объявить GC виновником: нужно сопоставить таймлайн запроса с GC-логом или JFR.

Сборщик возвращает место в heap для новых объектов. Его задача — найти объекты, до которых программа больше не может добраться; он не знает, нужен ли бизнесу объект «по смыслу».

Достижимость от корней решает судьбу объекта

GC начинает с корней: ссылок в активных кадрах потоков, статических полей и других JVM-структур. Он проходит цепочки сильных ссылок. Объект, к которому путь остался, жив даже если приложение больше никогда его не прочитает: так выглядит утечка через неограниченный кеш.

import java.util.ArrayList;
import java.util.List;
public class ReachabilityDemo {
    static final List<byte[]> cache = new ArrayList<>();
    public static void main(String[] args) {
        cache.add(new byte[1024]);
        System.out.println(cache.size());
        cache.clear();
        System.out.println(cache.size());
    }
}
1
0

После clear() массив из примера может стать недостижимым, но вывод 0 говорит лишь о размере списка. Он не доказывает, что GC уже освободил память.

G1 собирает регионы и копирует живые объекты

В JDK 21 HotSpot по умолчанию использует G1. Он делит heap на регионы и логически выделяет young и old. Большинство новых объектов быстро умирает, поэтому young-область собирают чаще; пережившие сборки объекты могут перейти в old.

Цель -XX:MaxGCPauseMillis — ориентир, а не жёсткая гарантия. Слишком маленькая цель может увеличить частоту сборок и снизить throughput.

ZGC выбирают по требованию к паузам, измеряя цену

ZGC выполняет большую часть дорогой работы конкурентно с приложением и рассчитан на низкие паузы. За это платят ресурсами CPU и запасом памяти. Для JDK 21 поколенческий вариант включается флагами -XX:+UseZGC -XX:+ZGenerational; на более новых JDK набор флагов может отличаться.

Переключение GC не исправит удержание объектов: live set продолжит расти при любом сборщике.

Слабые ссылки и флаги не заменяют политику памяти

WeakReference не удерживает объект от сборки, поэтому подходит для вспомогательных соответствий, например канонизации. SoftReference JVM очищает под давлением памяти по своей политике; для бизнес-кеша с требованиями к TTL и размеру это слишком непредсказуемо.

Вызов System.gc() гарантирует немедленную очистку памяти.

Это запрос к JVM, а не контракт на момент и объём сборки. Для сервиса сначала собирай GC-логи и измеряй allocation rate, live set и длительность пауз.

Сначала задай разумный -Xmx с запасом до лимита контейнера, включи -Xlog:gc* и измерь нагрузку. Тюнинг конкретных флагов делай только после наблюдаемой проблемы.

  • GC сохраняет объекты, достижимые от корней; логическая утечка для него выглядит как живые данные.
  • G1 — сборщик HotSpot по умолчанию в JDK 21; он использует регионы и поколения.
  • Пауза GC видна в логах и JFR, но её нужно сопоставить с задержкой запроса.
  • ZGC снижает паузы ценой ресурсов; выбор проверяют на своей нагрузке.
  • Weak и soft ссылки не задают предсказуемый размер или TTL бизнес-кеша.

На собеседовании

Как GC понимает, что объект можно удалить?

Он проходит от GC roots по сильным ссылкам. Если до объекта не осталось пути, он может быть собран. Время освобождения не гарантировано.

В платёжном сервисе static-кеш чеков остаётся корнем цепочки. Пока чек в кеше, GC его сохраняет, даже если запрос давно завершился.

  • WeakReference и SoftReference вводят другие уровни достижимости; правила описаны в java.lang.ref.
  • Heap dump с путём к GC root показывает, кто удерживает объект.
Поможет ли GC убрать запись из живого HashMap?

Нет, если HashMap и значение достижимы сильными ссылками. Нужна политика удаления, лимит или TTL.

Что изменилось после cache.clear() в примере?

Путь через список исчез. Это делает массив кандидатом на сборку при отсутствии других ссылок, но сборка не обязана произойти сразу.

Чем отличаются G1 и ZGC и как выбрать?

G1 — сбалансированный сборщик по умолчанию в HotSpot 21: делит heap на регионы, молодые объекты собирает часто, часть работы делает параллельно и конкурентно. ZGC ориентирован на низкие паузы, выполняя большую часть работы одновременно с приложением.

Я начну с G1, соберу GC-логи и p99 под типичной нагрузкой. Если именно паузы GC нарушают цель, проверю ZGC и цену в CPU и памяти.

  • MaxGCPauseMillis у G1 — цель, а не SLA на каждую паузу.
  • В JDK 21 поколенческий ZGC включается дополнительно через -XX:+ZGenerational.
  • Недостаточный heap или высокий allocation rate могут вызвать частые сборки при любом алгоритме.
Почему G1 копирует живые объекты?

Копирование освобождает исходный регион целиком и уплотняет живые данные, уменьшая фрагментацию.

Уменьшит ли ZGC p99 HTTP-запроса всегда?

Нет. Если задержка в сети, БД или блокировке, смена GC не устранит её; нужно сопоставить события по времени.

Чем WeakReference отличается от SoftReference?

Weak-ссылка не мешает сборке объекта, когда сильных ссылок больше нет. Soft-ссылка тоже слабее сильной, но JVM может сохранять объект до давления на память. В обоих случаях нельзя строить корректность бизнеса на том, что объект останется доступен.

Для кеша тарифов я выбираю явный лимит и TTL, а слабые ссылки применяю для вспомогательных данных, которые легко восстановить.

  • WeakHashMap ослабляет ключи, но сильная ссылка из значения обратно на ключ может помешать ожидаемой очистке.
  • SoftReference не задаёт детерминированную политику вытеснения между запросами.
Можно ли по System.gc() проверить WeakReference?

Такой тест ненадёжен: момент сборки не гарантирован. Проверяй контракт через документацию, а не фиксированный вывод одного запуска.

Что случится с объектом только под weak-ссылкой?

Когда GC обнаружит его слабо достижимым, он очистит weak-ссылку; после этого объект может быть освобождён.
