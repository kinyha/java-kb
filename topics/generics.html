Generics

Generics переносят проверку типов элементов из времени выполнения во время компиляции: положить строку в List<Payment> нельзя, а читать можно без приведения. Делает это только компилятор. После проверки параметры типа стираются: в байткоде List<Payment> — просто List, а приведение checkcast вставлено в каждом месте чтения. Поэтому ошибка, пропущенная через сырой тип, падает не там, где её сделали, а там, где читают. Стирание объясняет все ограничения: нельзя new T(), instanceof List<String> и перегрузку по List<String> и List<Integer>. Параметризованные типы инвариантны: List<Payment> — не List<Object>; гибкость дают wildcard по правилу PECS — читаешь из ? extends, пишешь в ? super.

Чужой элемент в списке и падение в другом месте

Сервис сверки получает пачку платежей и передаёт её в старый модуль импорта, написанный до Java 5. Тот добавляет в пачку запись о возврате — строкой. Ничего не падает. Падает позже, в коде, который суммирует платежи и ничего не знает о старом модуле. Демо RawDemo.java:

@SuppressWarnings({"rawtypes", "unchecked"})
static void importLegacy(List batch) {            // старый код без параметра типа
    batch.add("REFUND:42:500");                     // строка вместо Payment — компилятор молчит
}

List<Payment> batch = new ArrayList<>();
batch.add(new Payment("p-1", 1000));
importLegacy(batch);                                // сюда пришёл чужой элемент
for (Payment p : batch) total += p.amount();        // ClassCastException здесь, а не в importLegacy
size = 2, contents = [Payment[id=p-1, amount=1000], REFUND:42:500]
ClassCastException at the read site: class java.lang.String cannot be cast to class RawDemo$Payment

Список без параметра типа — сырой тип — принимает что угодно. Строка спокойно легла рядом с платежом, и batch.size() честно вернул 2. Исключение возникло в цикле суммирования, и по стеку вызовов найти, кто положил строку, нельзя: тот код давно отработал. До Java 5 так выглядела любая коллекция — List хранил Object, а каждое чтение было приведением, которое могло упасть.

Параметр типа: ошибку видит компилятор

С параметром типа контракт «в этом списке только платежи» становится частью сигнатуры. Если importLegacy объявить как importLegacy(List<Payment> batch), строку в него не положить: код не скомпилируется с ошибкой incompatible types: String cannot be converted to Payment. Ошибка находится там, где её делают, а не там, где она проявляется. А при чтении приведение больше не пишут руками: batch.get(0).amount().

Предупреждения компилятора — часть этой защиты. Демо скрывает их @SuppressWarnings({"rawtypes", "unchecked"}), и именно так ошибки и проходят: unchecked означает, что компилятор не может гарантировать типобезопасность в этом месте. В рабочем коде подавление ставят на минимальную область — одну переменную или метод — и с комментарием, почему это безопасно.

Стирание: что остаётся в байткоде

Параметры типа существуют только при компиляции. Компилятор проверяет типы, затем стирает параметры до их границ — T до Object, T extends Comparable<T> до Comparable — и вставляет приведения там, где значение стёртого типа используется как конкретное. Скрипт javap.sh компилирует Erased.java и показывает нужные строки javap -c -v:

    return batch.get(0).amount();          // get возвращает Object; компилятор вставляет checkcast
}
static <T extends Comparable<T>> T max(T a, T b) {
    return a.compareTo(b) >= 0 ? a : b;    // T стирается до своей границы — Comparable
}

Демо ErasureDemo.java показывает обе стороны. ArrayList<String> и ArrayList<Payment> — один класс при выполнении: объект не знает своего параметра типа. Но объявление поля static List<Payment> pending знает: getGenericType() читает его из Signature. На этом построены super type token в Jackson (new TypeReference<List<Payment>>() {}) и ParameterizedTypeReference в Spring: анонимный подкласс сохраняет параметр в сигнатуре своего родителя, и библиотека достаёт его рефлексией, как в Annotations & Reflection.

Что следует из стирания: мост-методы и ограничения

compareTo(Amount) bridge=false synthetic=false
compareTo(Object) bridge=true synthetic=true
raw compareTo("five"): ClassCastException in the bridge

Record Amount implements Comparable<Amount> объявил один метод compareTo(Amount), а в классе их два. После стирания интерфейс Comparable требует compareTo(Object), и компилятор сгенерировал синтетический мост-метод, который приводит аргумент к Amount и вызывает настоящий. Вызов через сырой тип со строкой упал внутри моста — снова приведение, вставленное компилятором. Мост-методы нужны, чтобы переопределение работало после стирания; в стеке исключения они видны как строки без номера в исходнике.

Стирание выбрали в Java 5 ради совместимости: старый байткод и библиотеки без generics работали с новым кодом без перекомпиляции, а сырые типы остались ради этой совместимости. Цена — ограничения из таблицы и то, что типобезопасность держится только на компиляторе. В C# параметры типа существуют и при выполнении, поэтому new T() и List<int> без боксинга там есть.

Инвариантность и PECS: когда нужен wildcard

Object[] = new Payment[1]; store String: ArrayStoreException
sorted with Comparator<Object>: [p-1, p-2]

Массивы ковариантны: Payment[] — подтип Object[]. За это платят проверкой при каждой записи: в массив, объявленный как Object[], но созданный как Payment[], строка не легла — ArrayStoreException. С generics такая проверка невозможна — параметр стёрт, — поэтому параметризованные типы инвариантны: List<Payment> не является ни подтипом, ни надтипом List<Object>, и List<Object> list = new ArrayList<Payment>() не компилируется. Иначе через list.add("x") в список платежей попала бы строка, и проверить это было бы нечем.

static long total(List<? extends Payment> source) {          // производитель: читаем
    long sum = 0;
    for (Payment p : source) sum += p.amount;
    // source.add(new Payment(1));   // не компилируется: неизвестно, Card это список или Sbp
    return sum;
}
static void addCards(List<? super CardPayment> sink, int n) { // потребитель: пишем
    for (int i = 1; i <= n; i++) sink.add(new CardPayment(i * 100));
}
static <T> void copy(List<? super T> dst, List<? extends T> src) { dst.addAll(src); }
cards = [CardPayment:100, CardPayment:200], total = 300
all   = [CardPayment:100, SbpPayment:700], total = 800
audit = [CardPayment:100, SbpPayment:700]

Правило PECS — producer extends, consumer super. Из List<? extends Payment> можно читать Payment: что бы там ни лежало, это подтип Payment. Писать нельзя: за wildcard может стоять List<SbpPayment>, и карточный платёж в нём был бы чужим. В List<? super CardPayment> можно писать CardPayment: список гарантированно принимает его — это List<CardPayment>, List<Payment> или List<Object>. Читать можно только Object. Демо PecsDemo.java передаёт один и тот же addCards и List<CardPayment>, и List<Payment>.

Так устроены сигнатуры JDK: Collections.copy(List<? super T> dest, List<? extends T> src), Collections.max(Collection<? extends T>, Comparator<? super T>), List.sort(Comparator<? super E>) — поэтому в ErasureDemo список платежей отсортирован компаратором Comparator<Object>. Правило для своих API: wildcard — в параметрах методов, где он расширяет круг принимаемых аргументов; в возвращаемых типах wildcard не ставят — он заставляет вызывающий код работать с неизвестным типом.

Границы: загрязнение кучи и переусложнение

@SafeVarargs   // ложное обещание: метод пишет в массив varargs
static void poison(List<String>... lists) {
    Object[] array = lists;                 // List<String>[] — на деле List[]
    array[0] = List.of(42);                 // ArrayStoreException не будет: тип элемента — List
}
heap pollution: ClassCastException on read, far from poison()
flatten = [p-1, p-2, p-3]

Generic varargs создаёт массив стёртого типа: List<String>... при выполнении — List[]. В такой массив можно положить List.of(42), и проверка записи массива не сработает — она знает только про List. Это загрязнение кучи (heap pollution): переменная параметризованного типа указывает на объект другого параметризованного типа. Демо VarargsDemo.java упало на чтении, вдали от poison, — та же история, что в первом демо. @SafeVarargs — обещание, которое компилятор не проверяет: метод не пишет в массив varargs и не отдаёт его наружу. flatten только читает — его обещание честное; так помечены List.of и Arrays.asList.

Обратная крайность — переусложнение: <K extends Comparable<? super K>, V, M extends Map<K, List<V>>> в бизнес-коде читать некому. Параметр типа оправдан, когда код действительно работает с разными типами одинаково — коллекции, кеши, репозитории, результаты, — и когда без него пришлось бы приводить типы. Сервис возвратов, который всегда работает с Payment, параметр типа не делает лучше.

Generics гарантируют, что в List<Payment> лежат только платежи.

Гарантирует компилятор и только там, где нет сырых типов, непроверенных приведений и ложных @SafeVarargs. При выполнении параметр стёрт: в демо строка легла в список платежей через сырой List, а падение случилось при чтении, на вставленном компилятором checkcast. Предупреждения unchecked — сигнал, что гарантии в этом месте нет.

  • Generics — проверка типов при компиляции; сырой тип пропустил строку в список платежей, и упало чтение.
  • Стирание: в дескрипторе (Ljava/util/List;)J, при чтении checkcast, полный тип — в Signature для рефлексии.
  • ArrayList<String> и ArrayList<Payment> — один класс; объявления полей и методов свой тип помнят.
  • Мост-метод compareTo(Object) сохраняет переопределение после стирания; отсюда же ограничения: нет new T(), instanceof List<String>, перегрузки по параметру.
  • Массивы ковариантны с проверкой записи, параметризованные типы инвариантны; PECS: читать из ? extends, писать в ? super.
  • @SafeVarargs не проверяется: запись в массив varargs загрязняет кучу.

На собеседовании

Что такое стирание типов и какие у него последствия?

Параметры типа существуют только при компиляции. Компилятор проверяет типы, затем заменяет параметры их границами — обычно Object — и вставляет приведения checkcast в местах чтения. При выполнении ArrayList<String> и ArrayList<Integer> — один класс. Отсюда нельзя создать new T() и массив T[], проверить instanceof List<String>, перегрузить метод по List<String> и List<Integer>, использовать примитив как параметр.

  • Полный тип объявлений хранится в атрибуте Signature — на нём работают TypeReference в Jackson и ParameterizedTypeReference в Spring.
  • Мост-методы сохраняют переопределение после стирания.
  • Стирание выбрано ради совместимости с байткодом до Java 5.

Что означает PECS и зачем нужны wildcard?

Параметризованные типы инвариантны: List<Payment> не подтип List<Object>, иначе через него можно было бы положить в список платежей что угодно. Wildcard дают гибкость: из List<? extends Payment> можно читать Payment, но нельзя писать — это производитель; в List<? super CardPayment> можно писать CardPayment, а читать только Object — это потребитель. Producer extends, consumer super.

  • Сигнатуры JDK: Collections.copy, Collections.max, List.sort(Comparator<? super E>).
  • Массивы ковариантны и платят ArrayStoreException при записи.
  • Wildcard — в параметрах, не в возвращаемых типах.
Почему этот метод нельзя вызвать со списком карточных платежей? 
static long total(List<Payment> payments) {
    return payments.stream().mapToLong(Payment::amount).sum();
}
List<CardPayment> cards = loadCards();
total(cards);                         // не компилируется

List<CardPayment> не является подтипом List<Payment>: параметризованные типы инвариантны. Метод только читает, значит, его параметр — производитель: List<? extends Payment>. Тогда он примет и List<CardPayment>, и List<Payment>, а компилятор запретит случайную запись в чужой список.

Чем опасны сырые типы и непроверенные предупреждения?

Сырой тип отключает проверку параметра: в List<Payment>, переданный как List, можно положить строку. Исключение возникнет не при записи, а при чтении — на вставленном компиляторе checkcast, далеко от места ошибки. Предупреждение unchecked означает, что компилятор не может гарантировать типобезопасность; подавлять его можно только на минимальной области и с обоснованием.

  • Heap pollution через generic varargs и ложный @SafeVarargs.
  • Collections.checkedList проверяет записи при выполнении для отладки.

Как получить параметр типа при выполнении, если он стирается?

Параметр объекта узнать нельзя, но параметры объявлений сохранены в атрибуте Signature: тип поля, параметры и возвращаемый тип метода, родительский класс. Поэтому библиотеки просят анонимный подкласс: new TypeReference<List<Payment>>() {} — его родитель записан с параметром, и Jackson читает его через getGenericSuperclass(). Другой путь — передать Class<T> явно.

  • Spring использует ResolvableType, чтобы внедрять бины по параметризованному типу.
  • Параметры типа локальных переменных и лямбд рефлексия не видит.
