Git

Git хранит историю как граф неизменяемых коммитов, а ветка — лишь указатель на коммит. Отсюда всё остальное. Merge соединяет две линии новым коммитом с двумя родителями и ничего не переписывает. Rebase заново создаёт коммиты ветки поверх другой — с новыми хешами, поэтому его делают только с ещё не опубликованными коммитами. Revert отменяет коммит новым коммитом и безопасен для общей ветки, а reset передвигает указатель и для общей ветки опасен. «Потерянный» после reset коммит не исчезает сразу: reflog помнит, куда указывал HEAD. Bisect находит коммит с регрессией двоичным поиском: среди 32 коммитов — за 5 запусков теста.

После rebase общей ветки у коллег «пропали» коммиты

Разработчик сделал git rebase main на ветке, где уже работали двое, и git push --force. У коллег локальные копии указывают на старые коммиты, которых в удалённой ветке больше нет; следующий push одного из них возвращает старые коммиты рядом с новыми, и история раздваивается. Другой разработчик, пытаясь откатить неудачный коммит в main, сделал reset --hard и force push — и удалил заодно два чужих коммита. Обе ошибки — от непонимания того, что git хранит и что переписывает.

Тема разбирает операции на демо git.sh, которое создаёт временный репозиторий и выполняет каждую операцию; даты коммитов зафиксированы, поэтому хеши в выводе повторяются при каждом запуске. Ревью изменений — в Code Review, проверки перед слиянием — в CI/CD.

Коммит — снимок дерева со ссылками на родителей

== what a commit is: git cat-file -p M
   tree 02eeaa03e6bc537b3e4e04451fdaf0940db7c014
   parent ad2636f530a25eb7dfee6b3ec1ceed60c319e5ac
   parent 317e1b1efe115ec023dc88bd734c44ac3104b77b
   author dev
   M: merge feature
   tree of M: cashback.txt currency.txt fee.txt limit.txt
   branch file: .git/refs/heads/m -> 3c406aa, HEAD -> ref: refs/heads/m

Коммит M — небольшой текстовый объект: ссылка на дерево (полный снимок всех файлов проекта, а не разница с предыдущим), ссылки на родителей, автор, время и сообщение. У merge-коммита два родителя, у обычного — один, у первого — ни одного. Имя каждого объекта — хеш его содержимого: поменяйте хоть родителя, хоть время, и получится другой объект с другим именем. Поэтому история неизменяема: «изменить» коммит можно, только создав новый.

Ветка — файл с хешем одного коммита (.git/refs/heads/m), а HEAD — указатель на текущую ветку. Новый коммит просто передвигает указатель ветки вперёд. Отсюда видно, что делают команды: merge добавляет коммит с двумя родителями, rebase создаёт новые коммиты и переставляет указатель, reset переставляет указатель назад, а сами объекты коммитов остаются в хранилище, пока сборка мусора не удалит недостижимые. Detached HEAD — состояние, когда HEAD указывает на коммит, а не на ветку: новые коммиты в нём ни к какой ветке не привязаны и найдутся только через reflog.

Merge соединяет историю, rebase переписывает её

== merge: history keeps both lines and a merge commit
   *   M: merge feature
   |\
   | * F2: cashback 3%
   | * F1: cashback
   * | C: currency
   |/
   * B: limit
   * A: fee 1%
== rebase: feature commits are re-created on top of main
   * F2: cashback 3%
   * F1: cashback
   * C: currency
   F1 before rebase 17f8b78, after 8d84bcb: new commits, new hashes

Хеш коммита считается от содержимого, родителя, автора и времени, поэтому любое изменение истории порождает новые коммиты. Rebase делает историю линейной и удобной для чтения, но переписывает её; правило — переписывать только то, что ещё не опубликовано, или свою личную ветку, о которой знают, что её переписывают. Для общей ветки после rebase нужен git push --force-with-lease, который откажет, если на сервере появились чужие коммиты, — в отличие от --force, который их просто удалит. Многие команды делают rebase своей ветки на main перед слиянием, а сливают через squash или merge — это выбор стиля истории, а не правильности.

Конфликт: git не выбирает за вас

== conflict: both branches change the same line
   git status: UU fee.txt
   <<<<<<< HEAD
   fee = 1.5%
   =======
   fee = 2%
   >>>>>>> fee-2
   resolved: fee = 2%

Обе ветки изменили одну строку от общего предка: main поставил 1,5 %, ветка fee-2 — 2 %. Git сливает изменения построчно и при пересечении останавливается: файл помечен UU (изменён обеими сторонами), внутри маркеры с обеими версиями. Решение — отредактировать файл, git add и завершить слияние коммитом. Конфликт — это сигнал, что два человека меняли одно и то же решение, и выбирает человек, а не инструмент. Конфликтов меньше, когда ветки живут недолго и сливаются часто: через день конфликт в одной строке, через месяц — в половине файлов.

Отменить: revert для общей истории, reset для своей, reflog — если ошиблись

== cherry-pick a fix and revert a bad commit
   release got: H: hotfix limit 500, limit = 500
   main after revert: Revert "H: hotfix limit 500", limit = 1000
== reset --hard loses a commit; reflog finds it
   after reset: important.txt exists: no
   reflog: f3df300 found again, important.txt exists: yes

Cherry-pick переносит изменения одного коммита на другую ветку новым коммитом — так хотфикс из main попадает в уже отделившуюся релизную ветку. Revert отменяет коммит новым коммитом с обратными изменениями: история только растёт, и это безопасно для общей ветки, которую уже скачали другие. Reset передвигает указатель ветки назад: коммиты после него исчезают из ветки, и для опубликованной истории это то же переписывание, что и rebase.

reset --hard убрал коммит I вместе с файлом, но коммит не удалён: reflog хранит, куда указывал HEAD при каждом действии, по умолчанию 90 дней для достижимых записей и 30 дней для недостижимых. Демо нашло потерянный коммит в reflog и вернуло на него ветку. Безвозвратно теряются только незакоммиченные изменения — поэтому перед рискованной операцией лучше закоммитить или сделать git stash.

Bisect: двоичный поиск коммита с регрессией

git bisect start HEAD HEAD~32                    # плохой коммит, хороший коммит
git bisect run sh -c '[ "$(grep latency perf.txt | cut -d= -f2)" -lt 50 ]'   # 0 — хорошо, 1 — плохо
== bisect: find the commit that broke the test among 32
   first bad: P23, test runs: 5

Задержка выросла где-то в последних 32 коммитах. Bisect берёт коммит посередине, запускает проверку и отбрасывает половину диапазона: log₂ 32 = 5 запусков нашли P23. Проверка — любая команда с кодом выхода: тест, бенчмарк, сборка. Для тысячи коммитов хватит 10 запусков. Работает хорошо, если каждый коммит собирается и проходит тесты, — ещё одна причина делать небольшие осмысленные коммиты, а не «wip».

Trunk-basedКороткие ветки на часы–дни, слияние в main ежедневно, незаконченное — за feature flagНепрерывная поставка, сервисы

Git flow придуман для продуктов с явными версиями и долгой поддержкой; для сервиса, который выкатывается несколько раз в день, его ветки develop и release добавляют слияния и конфликты без пользы. Trunk-based development держит main всегда готовым к выкатке, ветки — короткими, а незаконченные функции — выключенными флагами, как в Deployment Strategies.

Rebase и merge дают одинаковый результат, просто история выглядит по-разному.

Содержимое файлов совпадает, но rebase создаёт новые коммиты с новыми хешами: в демо F1 был 17f8b78, стал 8d84bcb. У всех, кто скачал старые коммиты, они остаются, и force push общей ветки раздваивает историю. Merge ничего не переписывает.

  • Коммит — снимок дерева, родители, автор, время; ветка — файл с хешем; хеш зависит от родителя, поэтому rebase даёт новые коммиты.
  • Merge — коммит с двумя родителями без переписывания; rebase — только для неопубликованного, push с --force-with-lease.
  • Конфликт — правка одной строки с двух сторон; короткие ветки — меньше конфликтов.
  • Revert для общей ветки, reset — для своей; reflog вернул коммит после reset --hard.
  • Bisect: 32 коммита — 5 запусков; trunk-based для сервисов, git flow — для версионированных продуктов.

На собеседовании

Чем merge отличается от rebase?

Merge соединяет две ветки коммитом с двумя родителями; существующие коммиты не меняются, история показывает параллельную работу. Rebase заново применяет коммиты ветки поверх другой: история линейная, но коммиты новые, с новыми хешами. Rebase делают только для коммитов, которые ещё никто не скачал, иначе история раздваивается у коллег.

  • force-with-lease вместо force: не удалит чужие коммиты на сервере.
  • Squash-merge: одна задача — один коммит в main.
  • Интерактивный rebase для приведения своих коммитов в порядок перед ревью.

Как отменить неудачный коммит в общей ветке?

git revert: новый коммит с обратными изменениями, история не переписывается, коллегам ничего не ломается. reset с force push для общей ветки опасен: он удаляет коммиты из ветки, включая чужие, появившиеся позже. Reset уместен для своих неопубликованных коммитов.

  • Revert merge-коммита требует указать родителя (-m 1) и усложняет повторное слияние.
  • Потерянное после reset находится в reflog.
Что не так с этой последовательностью? 
git switch main
git reset --hard HEAD~3        # убрать три неудачных коммита
git push --force

Main — общая ветка: если после этих трёх коммитов кто-то успел запушить свои, --force их удалит с сервера, а у всех, кто скачал main, история разойдётся с удалённой. Нужно отменять через git revert трёх коммитов новым коммитом. Если переписывать всё же необходимо — --force-with-lease и предупреждение команды; на сервере main обычно защищён от force push.

Git flow или trunk-based development?

Git flow — долгие ветки develop, release, hotfix для продуктов с версиями и поддержкой нескольких релизов. Trunk-based — короткие ветки и частое слияние в main, всегда готовый к выкатке; незаконченное прячут за feature flags. Для сервисов с непрерывной поставкой обычно выбирают trunk-based или GitHub flow.

  • Долгие ветки — большие конфликты и интеграция в конце.
  • Обязательные проверки CI и ревью перед слиянием в main.
  • Pro Git — главы о ветвлении, rebase и внутреннем устройстве.
