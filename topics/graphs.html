Graphs

Платёж проходит через несколько сервисов, а к банку бывает несколько маршрутов. Граф сохраняет возможные переходы; алгоритм выбирает, какую вершину обработать следующей. Очередь ведёт по числу переходов, стек исследует одну ветку до конца, а куча выбирает наименьшую известную стоимость. Правильный выбор зависит от смысла ребра и от того, когда найденный результат уже можно считать окончательным.

Маршрут определяется рёбрами, а не расположением объектов

Платёж не дошёл до settlement. Поддержка собирает возможные цепочки вызовов: gateway → bank, gateway → risk, bank → settlement и risk → settlement. Одного дерева мало: у settlement несколько входящих связей, а повторный вызов может вернуть маршрут к уже знакомому сервису. Для такого устройства нужен граф: вершины представляют объекты, рёбра — разрешённые переходы между ними.

Ниже вершины имеют номера 0…5: gateway, bank, risk, settlement, audit, archive. Стрелка u → v означает, что из u можно перейти в v. Это ориентированный граф; обратный переход существует только при отдельном ребре. В неориентированном графе связь доступна в обе стороны. Изолированная вершина archive тоже часть графа: её нельзя терять только потому, что она не встречается в списке рёбер.

Путь — последовательность допустимых переходов. Для поиска достижимости достаточно узнать, есть ли такой путь. Для кратчайшего пути надо уточнить меру: число рёбер или сумма их весов. Цикл возвращает к исходной вершине. Дерево — частный случай: связный неориентированный граф без циклов; произвольному графу нужны пометки, чтобы не возвращаться бесконечно.

В списке смежности каждой вершине соответствует список исходящих соседей. Чтобы обработать ребро u → v, смотрим строку u. В матрице смежности ячейка [u][v] отвечает, есть ли это ребро. У ориентированного графа матрица не обязана быть симметричной. Список рёбер хранит пары отдельно: удобен для загрузки и полного просмотра, но для поиска соседей придётся просматривать весь набор либо строить дополнительный индекс.

Фрагменты GraphWalkDemo.java, JDK 21. Все номера лежат в диапазоне [0, n); в учебном конструкторе это условие входа. Порядок соседей совпадает с порядком добавления:

static List<List<Integer>> graph(int n, int[][] edges) {
    var g = new ArrayList<List<Integer>>(n);
    for (int i = 0; i < n; i++) g.add(new ArrayList<>()); // Изолированные вершины тоже существуют.
    for (int[] e : edges) g.get(e[0]).add(e[1]); // Ориентированное ребро: только from -> to.
    return g;
}

V — число вершин, E — число рёбер. Для неориентированной связи u—v в списки обычно добавляют и u → v, и v → u: всего 2E записей, та же оценка O(V + E). Сумма исходящих степеней ориентированного графа равна E, сумма входящих — тоже E. У неориентированного графа сумма степеней равна 2E; петля даёт вклад 2 в степень.

Список подходит для разреженного графа, где у каждой вершины мало соседей. Матрица удобна для небольшого плотного графа и частых проверок одной пары. У взвешенной матрицы значение 0 может означать реальный бесплатный переход. Отсутствие ребра обозначают отдельно: например, булевой маской или специальным INF. У параллельных рёбер могут быть разные веса или идентификаторы; одна булева ячейка их различие теряет.

Под капотом: списки объектов и плоское хранение

O(V + E) не описывает цену заголовков объектов, ссылок и упаковки Integer. ArrayList<List<Integer>> создаёт отдельные списки; взвешенная версия ниже ещё и Edge для каждого ребра. Для большого неизменяемого графа используют плоские массивы: offsets длины V + 1 задаёт границы строк, to длины E хранит соседей, weights — веса. Это CSR, compressed sparse row: соседи u занимают [offsets[u], offsets[u+1]).

Плотное хранение сокращает число объектов и улучшает последовательное чтение. Цена — сложное изменение структуры: добавление ребра в середину готового массива требует перестройки или дополнительного слоя. Выбор зависит от обновлений, а не только от асимптотики поиска.

Очередь находит путь с наименьшим числом переходов

Сервис хочет добраться от gateway 0 до audit 4 через наименьшее число промежуточных вызовов. Перебирать все пути дорого: в графе много развилок, а цикл 1 → 3 → 4 → 1 разрешает обходы произвольной длины. Для достижимости и минимума числа рёбер достаточно один раз обработать каждую вершину, выбирая их по слоям расстояния.

BFS, breadth-first search, использует FIFO-очередь. Старт получает расстояние 0. Когда обрабатываем вершину расстояния d, впервые найденные соседи получают d + 1 и встают в хвост. В очереди сначала остаются вершины слоя d, затем идут вершины d + 1. Более длинный путь до соседа появится позже и уже не сможет улучшить первое расстояние.

Поэтому пометка ставится при добавлении в очередь. Если отложить её до извлечения, две вершины одного слоя добавят общего соседа дважды. Лишние записи раздуют очередь; повторное присваивание parent может испортить выбранный путь. В нашем ромбе 1 первой обнаружит 3, а 2 увидит уже заполненный dist[3].

Продолжение GraphWalkDemo.java. В Search храним расстояния, родителей и порядок извлечения. Trace только печатает состояние:

record Search(int[] dist, int[] parent, List<Integer> order) {}

static Search bfs(List<List<Integer>> g, int start, boolean trace) {
    int[] dist = new int[g.size()], parent = new int[g.size()];
    Arrays.fill(dist, -1); // -1 означает «ещё не обнаружен».
    Arrays.fill(parent, -1);
    var queue = new ArrayDeque<Integer>();
    var order = new ArrayList<Integer>();
    dist[start] = 0;
    queue.addLast(start);
    if (trace) System.out.println("start queue=" + queue + " dist=" + Arrays.toString(dist));
    while (!queue.isEmpty()) {
        int v = queue.removeFirst(); // FIFO: сначала все более близкие вершины.
        order.add(v);
        for (int w : g.get(v)) {
            if (dist[w] != -1) continue;
            dist[w] = dist[v] + 1; // Пометка при добавлении исключает повторы в очереди.
            parent[w] = v;
            queue.addLast(w);
        }
        if (trace) System.out.println("take=" + v + " queue=" + queue + " dist=" + Arrays.toString(dist));
    }
    return new Search(dist, parent, order);
}

static List<Integer> path(Search search, int target) {
    if (search.dist()[target] == -1) return List.of();
    var path = new ArrayList<Integer>();
    for (int v = target; v != -1; v = search.parent()[v]) path.add(v);
    Collections.reverse(path); // parent хранит путь в обратном направлении.
    return path;
}

Для восстановления маршрута идём по parent от цели к старту, затем разворачиваем список. Недостижимая цель даёт пустой путь; путь из старта в него самого состоит из одной вершины. Фрагмент main использует граф из предыдущего шага:

BFS со списками смежности стоит O(V + E) в худшем случае. Каждая вершина попадает в очередь один раз, каждое исходящее ребро просмотрено один раз; инициализация массивов стоит O(V). Для поиска от одного старта рёбра недостижимой части не просматриваются. Дополнительная память O(V): расстояния, родители, очередь и результат. С матрицей каждое посещение просматривает V столбцов, поэтому худшее время O(V²).

Для пути к одной цели BFS можно остановить при её первом обнаружении, сохранив parent. Для расстояний до всех целей обход продолжают. Несколько источников кладут в очередь сразу с расстоянием 0: тот же инвариант находит ближайший источник. Это полезно для распространения отказа или поиска ближайшей доступной точки.

Стек отличает текущую ветку от уже завершённого обхода

Теперь проверим, не вернётся ли цепочка зависимостей к самой себе. Для простого поиска любой достижимой вершины хватает boolean visited. Но сообщение «встретил уже посещённую вершину — значит цикл» ошибочно для ориентированного графа. Два разных пути могут соединиться в одном завершённом узле, как 0 → 1 → 3 и 0 → 2 → 3.

DFS, depth-first search, проходит одну ветку до конца и затем возвращается к развилке. Рекурсивный вызов хранит, из какой вершины пришли и какое следующее ребро ещё надо проверить. Для обнаружения ориентированного цикла различаем три состояния: 0 — не начата, 1 — активна в текущем стеке, 2 — полностью завершена. Их часто называют белым, серым и чёрным.

Ребро к активной вершине замыкает путь: от неё уже дошли по стекам вызовов до текущей, теперь есть дорога обратно. Ребро к завершённой вершине такой дороги не доказывает. Под «стеком» здесь понимаем один текущий DFS-путь; вершина, отложенная для будущей обработки, ещё не стала активным предком.

Фрагменты CycleDemo.java. Конструктор graph тот же, что в первом шаге. При обнаружении цикла метод заканчивает поиск сразу; оставшиеся color после такого выхода не используются:

static boolean dfs(List<List<Integer>> g, int v, int[] color, boolean trace) {
    color[v] = 1; // Серый: вызов начался, но ещё не завершён.
    if (trace) System.out.println("enter=" + v);
    for (int w : g.get(v)) {
        if (color[w] == 1) {
            if (trace) System.out.println("back edge=" + v + "->" + w);
            return true; // w лежит на текущем пути: найден ориентированный цикл.
        }
        if (color[w] == 0 && dfs(g, w, color, trace)) return true;
        if (trace && color[w] == 2) System.out.println("done edge=" + v + "->" + w);
    }
    color[v] = 2; // Чёрный: все исходящие рёбра обработаны.
    if (trace) System.out.println("exit=" + v);
    return false;
}

static boolean hasCycle(List<List<Integer>> g, boolean trace) {
    int[] color = new int[g.size()];
    for (int v = 0; v < g.size(); v++) { // Цикл может быть вне компоненты вершины 0.
        if (color[v] == 0 && dfs(g, v, color, trace)) return true;
    }
    return false;
}

Явный стек должен сохранять состояние возврата

Глубина рекурсии DFS достигает V на длинной цепочке. Это O(V) памяти и риск StackOverflowError на стеке JVM. Порог зависит от -Xss и формы кода, поэтому вместо выдуманного «безопасного числа вершин» для глубокого графа используем явный стек. Для простой достижимости в нём могут лежать только номера; для точного момента завершения вершины нужны кадры с оставшимися рёбрами.

record Frame(int vertex, Iterator<Integer> edges) {}

static boolean iterativeCycle(List<List<Integer>> g) {
    int[] color = new int[g.size()];
    var stack = new ArrayDeque<Frame>();
    for (int start = 0; start < g.size(); start++) {
        if (color[start] != 0) continue;
        color[start] = 1;
        stack.push(new Frame(start, g.get(start).iterator()));
        while (!stack.isEmpty()) {
            Frame frame = stack.peek();
            if (!frame.edges().hasNext()) {
                color[frame.vertex()] = 2; // Выход из кадра после всех детей.
                stack.pop();
                continue;
            }
            int w = frame.edges().next(); // Родитель запомнил, какое ребро смотреть дальше.
            if (color[w] == 1) return true;
            if (color[w] == 0) {
                color[w] = 1;
                stack.push(new Frame(w, g.get(w).iterator()));
            }
        }
    }
    return false;
}

Стек из кадров обработал цепочку 100 000 вершин без рекурсивных вызовов. Он хранит те же незавершённые переходы, что рекурсия, поэтому цвет 1 остаётся признаком предка текущей вершины. Просто положить в стек сразу всех соседей и покрасить их активными — другая логика: у отложенного соседа ещё нет пути до текущей вершины.

DFS со списками стоит O(V + E), дополнительная память O(V). Он находит какой-нибудь путь, но не гарантирует минимум рёбер: длинная первая ветка может закончиться на цели раньше короткой второй. У неориентированного графа каждое ребро записано в обе стороны, и обратный переход к родителю не означает цикл. Для простого графа его пропускают по parent; при параллельных рёбрах пропускают только идентификатор того же ребра, иначе можно потерять цикл из двух рёбер.

Зависимую работу можно поставить после всех её предпосылок

Оплата состоит из проверки входа 0, оценки риска 1, резервирования 2, списания 3 и квитанции 4. Метрики 5 независимы. Теперь смысл стрелки меняется явно: u → v означает, что u должно завершиться раньше v. Списать можно после риска и резерва; путь вызова и граф предпосылок — разные модели одного сервиса.

Топологический порядок помещает начало каждого ребра раньше его конца. Он существует ровно для DAG — directed acyclic graph, ориентированного графа без циклов. В цикле 1 → 3 → 1 пришлось бы поставить 1 раньше 3 и одновременно 3 раньше 1. Порядок обычно не единственный: независимые вершины можно переставлять.

Алгоритм Кана считает входящую степень каждой вершины. Степень 0 означает, что все её предпосылки уже сняты, и вершину можно включить в порядок. Извлекли готовую вершину — мысленно удалили её исходящие рёбра. Когда очередная степень стала 0, новая вершина готова. Реальные списки рёбер при этом сохраняем: меняется только массив счётчиков.

Фрагменты DependenciesDemo.java. Конструктор ориентированного графа такой же. Входящий счётчик учитывает каждое записанное ребро; при его снятии уменьшение также происходит один раз:

static List<Integer> topological(List<List<Integer>> g, boolean trace) {
    int[] in = new int[g.size()];
    for (var list : g) for (int w : list) in[w]++; // Сколько предпосылок ещё не снято.
    var ready = new ArrayDeque<Integer>();
    for (int v = 0; v < g.size(); v++) if (in[v] == 0) ready.addLast(v);
    var order = new ArrayList<Integer>();
    if (trace) System.out.println("start ready=" + ready + " in=" + Arrays.toString(in));
    while (!ready.isEmpty()) {
        int v = ready.removeFirst();
        order.add(v);
        for (int w : g.get(v)) if (--in[w] == 0) ready.addLast(w);
        if (trace) System.out.println("take=" + v + " ready=" + ready + " in=" + Arrays.toString(in));
    }
    if (order.size() != g.size()) {
        var blocked = new ArrayList<Integer>();
        for (int v = 0; v < g.size(); v++) if (in[v] > 0) blocked.add(v);
        // Остаток включает зависимые от цикла вершины, а не только сам цикл.
        throw new IllegalStateException("partial=" + order + " blocked=" + blocked);
    }
    return order;
}

Число в outdegree ничего не говорит о готовности — важны именно входящие предпосылки. Если API хранит наоборот «задача → что ей нужно», перед этим алгоритмом разворачивают рёбра.

Если очередь опустела, а в результате меньше V вершин, оставшиеся зависимости содержат цикл. В любом конечном DAG есть вершина с входящей степенью 0: иначе можно бесконечно идти против рёбер и неизбежно повторить вершину. Поэтому отсутствие готовой вершины в непустом остатке доказывает цикл. Однако сам остаток ещё не показывает, какие рёбра его составляют.

Цикл образуют 1 и 3. Квитанция 4 тоже заблокирована, потому что зависит от 3, но обратного пути от 4 к циклу нет. Называть все blocked участниками цикла — ошибка диагностики. Для точного объяснения возвращают цикл из DFS, запоминая parent, либо находят сильно связные компоненты; один только список положительных in этого не даёт.

Кан с FIFO работает за O(V + E), память O(V). Если среди готовых всегда нужно брать минимальный номер, ставят PriorityQueue: тогда время O(E + V log V). Другой способ — DFS: после завершения каждой вершины добавляют её в список, затем разворачивают весь список. Для ребра u → v в DAG вершина v завершится раньше u; обратный порядок сохраняет предпосылки. Предварительно проверяют цикл теми же активными цветами.

Расчёт порядка не запускает работу. В настоящем исполнителе уменьшать счётчик надо после успешного завершения предпосылки, а не после её отправки в пул. Обновление счётчиков должно быть атомарным; сбой или отмена предка требуют отдельной политики. Топологический порядок решает структурную часть, а не повторы, идемпотентность и долговечность платёжного процесса.

При разных весах сначала закрепляется самый дешёвый путь

Теперь между сервисами задана стоимость перехода. Пусть прямой путь 0 → 3 стоит 10, путь 0 → 1 → 3 стоит 7, а 0 → 2 → 1 → 3 стоит 3. BFS выберет прямое ребро: один переход меньше трёх. Если задача — минимум суммарной стоимости, первое обнаружение цели ещё ничего не закрепляет.

В Дейкстре dist[v] — лучшая известная стоимость до v. Для ребра v → w считаем dist[v] + weight и заменяем dist[w], если новый путь дешевле. Это релаксация. Следующей берём вершину с минимальным известным расстоянием из min-heap. На этом этапе расстояние окончательно, если все веса неотрицательны.

Причина гарантии — в порядке выбора. Предположим, остался более короткий путь к извлечённой v. На этом пути должна быть первая ещё не закреплённая вершина x после уже закреплённого предка. При обработке предка очередь получила расстояние до x не больше стоимости всего предполагаемого пути: оставшиеся рёбра неотрицательны. Тогда x стояла бы в очереди с меньшим расстоянием, чем v, и была бы извлечена раньше. Противоречие показывает, почему отрицательный вес ломает доказательство.

Фрагменты WeightedRoutesDemo.java. Здесь веса и расстояния имеют тип long, а вершины — int. INF обозначает отсутствие пути; допустимые конечные расстояния меньше Long.MAX_VALUE. Все вершины существуют заранее, номера корректны:

record Edge(int to, long weight) {}
record Entry(int vertex, long distance) {} // Неизменяемый снимок, не ссылка на dist[].
record Routes(long[] dist, int[] parent) {}
static final long INF = Long.MAX_VALUE;

static List<List<Edge>> graph(int n, long[][] edges) {
    var g = new ArrayList<List<Edge>>(n);
    for (int i = 0; i < n; i++) g.add(new ArrayList<>());
    for (long[] e : edges) g.get((int) e[0]).add(new Edge((int) e[1], e[2]));
    return g;
}

static Routes dijkstra(List<List<Edge>> g, int start, boolean trace) {
    for (var list : g) for (Edge e : list) {
        if (e.weight() < 0) throw new IllegalArgumentException("negative weight");
    }
    long[] dist = new long[g.size()];
    int[] parent = new int[g.size()];
    Arrays.fill(dist, INF);
    Arrays.fill(parent, -1);
    var queue = new PriorityQueue<Entry>(Comparator.comparingLong(Entry::distance)
            .thenComparingInt(Entry::vertex)); // Сравниваем без вычитания и переполнения.
    dist[start] = 0;
    queue.offer(new Entry(start, 0));
    while (!queue.isEmpty()) {
        Entry current = queue.poll();
        int v = current.vertex();
        if (current.distance() != dist[v]) {
            if (trace) System.out.println("stale=" + v + " saved=" + current.distance() + " best=" + dist[v]);
            continue; // Старое расстояние больше найденного позже.
        }
        if (trace) System.out.println("settle=" + v + " distance=" + dist[v]);
        for (Edge e : g.get(v)) {
            long next = Math.addExact(dist[v], e.weight()); // Переполнение не станет «коротким путём».
            if (next == INF) throw new ArithmeticException("distance equals INF");
            if (next < dist[e.to()]) {
                dist[e.to()] = next; // Релаксация: новый путь улучшает известный.
                parent[e.to()] = v;
                queue.offer(new Entry(e.to(), next)); // Старую запись не ищем и не меняем.
                if (trace) System.out.println("relax=" + v + "->" + e.to() + " distance=" + next);
            }
        }
    }
    return new Routes(dist, parent);
}

static List<Integer> path(Routes routes, int target) {
    if (routes.dist()[target] == INF) return List.of();
    var path = new ArrayList<Integer>();
    for (int v = target; v != -1; v = routes.parent()[v]) path.add(v);
    Collections.reverse(path);
    return path;
}

В PriorityQueue нет быстрого штатного decrease-key. Поэтому кладём неизменяемую пару (вершина, найденное расстояние) при каждом улучшении. Старые пары остаются в куче. При извлечении сравниваем сохранённое расстояние с dist[v] и отбрасываем устаревшую запись. Компаратор читает пару; компаратор, который читает изменяемый внешний dist, нарушил бы порядок уже построенной кучи.

Вариант BFS для того же взвешенного представления

Этот метод намеренно игнорирует вес и минимизирует число рёбер. Parent заполняется при первом обнаружении, как в обычном BFS:

static List<Integer> fewestEdges(List<List<Edge>> g, int start, int target) {
    boolean[] seen = new boolean[g.size()];
    int[] parent = new int[g.size()];
    Arrays.fill(parent, -1);
    var queue = new ArrayDeque<Integer>();
    seen[start] = true;
    queue.addLast(start);
    while (!queue.isEmpty()) {
        int v = queue.removeFirst();
        for (Edge e : g.get(v)) if (!seen[e.to()]) {
            seen[e.to()] = true; // Правильно для числа рёбер, не для суммы весов.
            parent[e.to()] = v;
            queue.addLast(e.to());
        }
    }
    if (!seen[target]) return List.of();
    var path = new ArrayList<Integer>();
    for (int v = target; v != -1; v = parent[v]) path.add(v);
    Collections.reverse(path);
    return path;
}

Здесь проверяем все веса до запуска, включая недостижимую часть. Math.addExact останавливает расчёт при переполнении любой проверяемой суммы, даже для слишком дорогого обходного пути; отдельная проверка запрещает реальную цену, равную INF. Это строгая политика учебного API. В прикладном варианте чрезмерные суммы можно отдельно отбрасывать, если модель допускает такой предел. Молчаливое переполнение long дало бы отрицательное расстояние и вынесло его на вершину кучи. Сравнение расстояний через вычитание с приведением к int опасно по той же причине.

У этой реализации есть цена простоты: успешных улучшений до O(E), значит в куче могут храниться O(E) снимков. Вместе с проверкой входа, инициализацией и просмотром рёбер время O(V + E log(V + E)), дополнительная память O(V + E). Для простого графа E ≤ V², логарифм можно записать как O(log V); формулировка O((V + E) log V) привычна для Дейкстры, но сама по себе не обещает кучу размера V. Индексированная куча с настоящим decrease-key хранит одну запись на вершину и даёт O((V + E) log V) при O(V) дополнительной памяти.

Цель добавлена в очередь: кратчайший взвешенный маршрут найден.

Первый маршрут до 3 имел цену 10 и позже улучшился до 3. Для одной цели останавливают Дейкстру после извлечения её актуальной минимальной записи. Остановка при добавлении или после устаревшей записи нарушает основание выбора.

Алгоритм отвечает на вопрос только внутри выбранной модели

Сначала назови, что означает ребро и что минимизируется. Кратчайший маршрут по количеству вызовов не обязан иметь меньшую задержку. Вес «миллисекунды» полезен лишь при принятой модели сложения: параллельные этапы, очередь в банке и повторные попытки требуют дополнительных условий. Если стоимость перехода зависит от уже пройденного пути, одного номера сервиса как состояния недостаточно: вершиной может стать пара (сервис, оставшийся лимит).

Bellman–Ford допускает отрицательные рёбра, но достижимый отрицательный цикл снимает нижнюю границу цены для всех целей, достижимых после него: цикл можно пройти ещё раз и удешевить маршрут. Отрицательный цикл в недостижимой части не меняет пути от выбранного старта. Для одного источника это существенное различие; для проверки всех компонентов берут виртуальный источник, соединённый с каждой вершиной ребром веса 0.

Граф зависимостей и граф вызовов обычно меняются со временем. Алгоритмы выше работают с неизменяемым снимком на время обхода. Одновременное добавление рёбер может дать результат, который не соответствует ни старой, ни новой версии; ConcurrentHashMap сам по себе не создаёт согласованный снимок всех соседей и счётчиков. В сервисе выбирают версию графа, копию, блокировку или специальный алгоритм динамического обновления.

Обход графа вызывает методы чтения структуры, а не реальные банковские операции. Если adj(v) каждый раз делает сетевой запрос, оценка O(V + E) перестаёт описывать задержку: появляется цена ввода-вывода, тайм-ауты и частичные ошибки. Сначала извлекают структуру пакетно или задают явные лимиты глубины, вершин, рёбер и времени. При достижении лимита ответ «не найден» заменяют на «поиск не завершён», иначе неполный обход выдаст ложную недостижимость.

Для диагностики полезны число V и E, доля недостижимых вершин, максимум очереди или стека, число релаксаций и устаревших записей. Пик очереди BFS зависит от ширины фронта, пик стека DFS — от глубины. В Дейкстре большое число улучшений и stale указывает на цену ленивых снимков. Измерять только время маленького примера недостаточно: оно смешивает запуск JVM, упаковку объектов и собственно обход.

У неориентированного графа обходы из ещё не посещённых вершин находят компоненты связности. У ориентированного простая достижимость уже не симметрична: «дошли из 0 в 4» не означает «дошли из 4 в 0». Сильно связная компонента требует взаимной достижимости всех её вершин. Поиск таких компонент, минимальное остовное дерево и максимальный поток решают другие вопросы и не заменяются произвольным BFS.

Структура очереди и стека разобрана в Arrays & Lists, min-heap и изменяемый приоритет — в Heaps. Graph Search отведён задачам на острова, неявные графы матриц, маршруты и зависимости. Здесь важна основа для них: смысл ребра, правило выбора следующей вершины и момент, когда результат можно закрепить.

  • Список хранит реальные рёбра за O(V + E), матрица — все возможные пары за O(V²). Изолированные вершины остаются в обоих представлениях.
  • BFS помечает при добавлении в FIFO и минимизирует число рёбер. Parent хранит один из кратчайших маршрутов.
  • DFS различает активный путь и завершённые вершины. Для ориентированного цикла нужен переход к активному предку.
  • Топологический порядок существует у DAG. Остаток Кана содержит цикл и может содержать заблокированные им задачи.
  • Дейкстра закрепляет минимальное актуальное расстояние при извлечении. Нужны неотрицательные веса, честное сложение и корректный порядок в куче.

На собеседовании

Как хранить граф? Когда список смежности, а когда матрица?

Я сначала уточню направление рёбер, веса, плотность и нужные операции. Список смежности хранит для каждой вершины её исходящих соседей и занимает O(V + E). Обход соседей стоит O(outdegree). Матрица занимает O(V²), зато отвечает на наличие одной пары за O(1); поиск всех соседей просматривает целую строку.

Для разреженной карты вызовов выберу списки. Для небольшого плотного графа с частыми проверками пар матрица может быть удобнее. В неориентированном списке каждую связь записываю в обе стороны. Изолированным вершинам оставляю пустые списки, иначе потеряется часть модели.

  • Для взвешенной матрицы 0 нельзя автоматически считать отсутствием ребра: нулевой вес допустим. Представление отдельно хранит отсутствие и стоимость.
  • Параллельные рёбра требуют списка рёбер с идентификаторами или явного правила объединения. Для минимума стоимости иногда можно оставить минимальный вес, а для независимых каналов и пропускной способности это уже потеря смысла.
  • HashSet соседей ускоряет проверку пары ожидаемо до O(1), но добавляет память и меняет правила дублей. Для большого неизменяемого графа плоское CSR-хранение уменьшает число объектов; изменения обходятся дороже.

Чем BFS отличается от DFS? Как восстановить путь и найти цикл?

BFS использует очередь и идёт по слоям. При первом добавлении вершины задаю расстояние и parent, поэтому нахожу путь с минимальным числом рёбер. DFS использует стек: идёт по ветке до конца и возвращается. Он даёт достижимость и какой-нибудь путь, но минимум длины не обещает. Со списками оба обхода стоят O(V + E), дополнительно O(V).

Путь восстанавливаю от цели по parent и разворачиваю. Для ориентированного цикла в DFS отмечаю активные и завершённые вершины: ребро к активной замыкает текущий путь. Ребро к завершённой может просто вести в общий потомок. Для проверки всего графа начинаю обход из каждой ещё не обработанной вершины.

  • В BFS пометка при извлечении допускает повторное добавление общего соседа. Очередь и parent становятся уязвимы к дублям; первая пометка должна сопровождать добавление.
  • Явный DFS-стек для обнаружения цикла или postorder хранит позицию в соседях. Просто стопка всех отложенных вершин не означает текущую цепочку активных предков.
  • У неориентированного графа пропускаю обратное ребро к родителю. В мультиграфе нужен идентификатор ребра: второе параллельное ребро нельзя пропустить вместе с первым.

Как построить порядок зависимостей? Что говорит неполный результат?

Пусть ребро u → v значит, что u должно быть раньше v. Считаю входящую степень и кладу в очередь вершины без предпосылок. Извлекаю готовую, включаю в порядок и уменьшаю счётчики её потомков. Новый нулевой счётчик добавляет вершину в очередь. Это алгоритм Кана, O(V + E).

Если обработал меньше V, оставшаяся часть содержит цикл и полный порядок невозможен. При этом остаток включает и зависимые от цикла задачи. Для сообщения «вот цикл» нужен отдельный путь из DFS или анализ сильно связных компонент. Порядок независимых задач может быть разным; это не ошибка.

  • Если вход хранит «задача → предпосылка», сначала разворачиваю направление. Иначе получу порядок, удобный для обратной задачи.
  • DFS даёт порядок через обратный список завершений, но только после проверки отсутствия цикла. Ни наличие finish time, ни сам список не доказывают DAG.
  • При параллельном запуске снимаю предпосылку после успеха задачи. Ошибка, повторное событие завершения и отмена требуют собственного состояния; счётчик, дважды уменьшенный одним завершением, может разрешить работу раньше срока.

Почему работает Дейкстра? Когда результат ещё нельзя считать окончательным?

Поддерживаю лучшую найденную цену до каждой вершины и min-heap по этой цене. Извлекаю актуальную минимальную запись и пробую улучшить соседей через неё. При неотрицательных весах расстояние извлечённой вершины окончательно: любой ещё не пройденный путь начинается с не более дешёвой вершины и уже не уменьшится за счёт оставшихся рёбер.

Первое добавление в очередь ничего не закрепляет. Для Java PriorityQueue удобно добавлять новые неизменяемые пары при улучшении и пропускать старые при извлечении. Если ищу одну цель, останавливаюсь только на её актуальном извлечении. Отрицательные веса требуют другого алгоритма.

  • Ленивый вариант держит до O(E) снимков; индексированная куча — O(V) записей с decrease-key. Меньше кода не означает одинаковый пик памяти.
  • Компаратор, читающий меняющийся dist[], не перестраивает готовую кучу. Расстояние сохраняю в Entry и сравниваю через comparingLong, а сложение проверяю на переполнение.
  • В DAG релаксации идут по топологическому порядку за O(V + E), даже при отрицательных весах. При весах 0/1 достаточно deque. Алгоритм выбирается по свойствам входа, а не по знакомому названию.
Коллега помечает вершину done при первом offer в PriorityQueue. Почему путь к банку останется дороже?

Из 0 сразу нашли банк 1 с ценой 6 и пометили done. Позже риск 2 с ценой 1 предлагает путь 0 → 2 → 1 ценой 2, но пометка запрещает улучшение. Это перенос правила BFS в задачу с разными весами. Нужны релаксации до актуального извлечения, неизменяемые записи и пропуск устаревших цен; в варианте выше отдельный done вообще не требуется.
