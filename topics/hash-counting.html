Arrays & Hashing

Сверка платежей снова ищет сумму среди уже прочитанных операций. Если сохранить нужные сведения в таблице, следующий элемент проверяется одним запросом вместо нового прохода по прошлому. Значение таблицы зависит от вопроса: встречался ли id, сколько раз, на какой позиции или в какую группу он попал. Самая важная часть решения — выбрать ключ и объяснить, что таблица содержит перед очередным шагом.

Повторный поиск можно заменить памятью о прочитанном

В выгрузке суммы [40, 20, 90, 30]. Нужно найти две разные позиции с суммой 50. Прямой способ берёт каждую сумму и сравнивает её со всеми следующими. Для одного небольшого файла это просто, но при росте входа одна и та же часть списка просматривается снова и снова.

Для n элементов существует n(n − 1)/2 пар. Если подходящей пары нет или она в конце, перебор проверит их все: O(n²) времени и O(1) дополнительной памяти. Отрицательные суммы и повторы не мешают перебору. Даже здесь надо считать в подходящем типе: две суммы int могут дать результат, который не помещается в int.

Фрагменты PairDemo.java, JDK 21. Счётчик считает только проверки суммы; вход не меняется:

record Brute(int[] pair, int comparisons) {}

static Brute brute(int[] nums, int target) {
    int comparisons = 0;
    for (int i = 0; i < nums.length; i++) {
        for (int j = i + 1; j < nums.length; j++) { // Разные позиции, каждую пару один раз.
            comparisons++;
            if ((long) nums[i] + nums[j] == target) return new Brute(new int[]{i, j}, comparisons);
        }
    }
    return new Brute(new int[0], comparisons);
}

int[] amounts = {40, 20, 90, 30};
System.out.println("== repeated search ==");
Brute result = brute(amounts, 50);
System.out.println("brute pair=" + Arrays.toString(result.pair()) + " comparisons=" + result.comparisons());

== repeated search ==
brute pair=[1, 3] comparisons=5

На позиции j известно текущее x. Его партнёр должен иметь значение target − x. Вместо перебора прошлых позиций сохраним значение → индекс и спросим, есть ли дополнение. Если есть, ответ восстановим сразу. Если нет, текущее значение пригодится следующему элементу, поэтому добавим его в таблицу.

Это обмен памяти на время. Для хеш-таблицы с подходящим распределением ключей поиск и вставка ожидаемо стоят O(1), весь проход — ожидаемое O(n), память O(n). Гарантию для любого входа за O(1) хеширование не даёт. Устройство коллизий и расширения уже разобрано в Hash Tables; здесь важнее доказать, какие сведения таблица обязана хранить.

Перед запросом таблица содержит только предыдущие позиции

Сформулируем инвариант: перед обработкой j таблица хранит ранний индекс каждого значения из [0, j). Значит, найденный индекс i всегда меньше j. Текущий элемент ещё не участвует в поиске, и пара не использует одну операцию дважды. После неудачного запроса добавление позиции j делает инвариант верным для следующего шага.

Почему ответ не пропущен? У любой подходящей пары есть более поздний индекс j. Когда дойдём до него, раннее значение уже лежит в таблице. Даже если его запись представляет ещё более раннюю копию той же суммы, она тоже образует допустимую пару. Мы возвращаем первую найденную пару по правому индексу; сохранение раннего индекса делает выбор среди копий воспроизводимым.

Продолжение PairDemo.java. LinkedHashMap используется для понятного порядка в trace; при поиске без печати достаточно HashMap. Значения таблицы — Integer с индексом, null туда не записываем. Поэтому null из get однозначно означает отсутствие значения. Индекс 0 — полноценный найденный ответ:

static int[] find(int[] nums, int target, boolean trace) {
    var seen = new LinkedHashMap<Long, Integer>(); // Порядок нужен только для читаемой печати.
    for (int j = 0; j < nums.length; j++) {
        long need = (long) target - nums[j]; // Сначала расширяем тип, потом вычитаем.
        Integer i = seen.get(need); // Таблица содержит только позиции < j.
        if (trace) System.out.println("j=" + j + " x=" + nums[j] + " need=" + need + " before=" + seen + " found=" + i);
        if (i != null) return new int[]{i, j};
        seen.putIfAbsent((long) nums[j], j); // Сохраняем самый ранний индекс для равного значения.
    }
    return new int[0];
}

Порядок запроса и записи — часть алгоритма

Если сначала записать текущую 5, а затем искать дополнение к сумме 10, таблица вернёт ту же позицию. При двух отдельных пятёрках ответ [0, 1] допустим, при одной [0, 0] — нет. Проверка «i != j» могла бы исправить отдельный вариант, но инвариант прошлых позиций делает лишнюю проверку и связанные с ней ошибки ненужными.

static int[] wrongInsertFirst(int[] nums, int target) {
    var seen = new HashMap<Long, Integer>();
    for (int j = 0; j < nums.length; j++) {
        seen.put((long) nums[j], j); // Ошибка: j уже доступен как «предыдущий» индекс.
        Integer i = seen.get((long) target - nums[j]);
        if (i != null) return new int[]{i, j};
    }
    return new int[0];
}

Достаточно HashSet: он же проверяет наличие дополнения.

Если нужен только ответ «есть пара», множества хватит при запросе до добавления. Чтобы вернуть исходные индексы, нужен индекс в значении таблицы. Сортировка меняет позиции, поэтому вариант с двумя указателями хранит связь с исходным массивом отдельно.

Количество копий нельзя восстановить из множества

В журнале ids = [A, B, A, C, B, A]. Для вопроса «встречался ли этот id» достаточно множества. Для «сколько раз» нужна таблица частот. Для «какой id был вторым дублем» нужен порядок события обнаружения. Это разные сведения: один HashMap не угадает за тебя, какой смысл должно иметь его значение.

Счётчик после обработки первых j элементов равен числу появлений ключа в этом префиксе. Новый элемент увеличивает ровно свой счётчик на 1. Если нужен первый уникальный id всего входа, раннего ответа во время первого появления нет: следующий элемент ещё может повторить его. Сначала считаем весь вход, затем проходим исходный порядок и берём первый со счётчиком 1.

Фрагменты FrequencyDemo.java. LinkedHashMap сохраняет порядок первого появления ключей при печати, LinkedHashSet — порядок добавления уникальных найденных дублей:

static Map<String, Long> counts(String[] ids) {
    var count = new LinkedHashMap<String, Long>();
    for (String id : ids) count.merge(id, 1L, Long::sum); // Новому ключу 1, прежнему +1.
    return count;
}

static List<String> duplicates(String[] ids) {
    var seen = new HashSet<String>();
    var repeated = new LinkedHashSet<String>();
    for (String id : ids) if (!seen.add(id)) repeated.add(id);
    return new ArrayList<>(repeated); // Порядок второго появления, каждый id один раз.
}

static String firstUnique(String[] ids) {
    Map<String, Long> count = counts(ids);
    for (String id : ids) if (count.get(id) == 1) return id; // Повторный проход сохраняет порядок входа.
    return null;
}

String[] ids = {"A", "B", "A", "C", "B", "A"};
System.out.println("== set and counts ==");
System.out.println("counts=" + counts(ids));
System.out.println("duplicates=" + duplicates(ids));
System.out.println("first unique=" + firstUnique(ids));

Дубль A попал в результат при втором появлении и остался там один раз, хотя пришёл и в третий раз. Для простой проверки одного дубля можно вернуть true, как только seen.add даст false. Для поиска всех дублирующихся id второе множество не позволяет печатать один id несколько раз. Дедупликация списка и подсчёт кратности решают разные задачи.

У aab и abb одинаковое множество букв, но разные частоты. Анаграммы — строки, у которых совпадает мультимножество символов: каждая буква встречается столько же раз. Для фиксированного алфавита a…z таблица не нужна: буква напрямую задаёт ячейку int[26]. Каждый элемент хранит число появлений соответствующей буквы:

static int[] latinCounts(String s) {
    int[] count = new int[26]; // Вход: только a…z. Индекс буквы — прямой адрес.
    for (int i = 0; i < s.length(); i++) count[s.charAt(i) - 'a']++;
    return count;
}

static Set<Character> letters(String s) {
    var letters = new HashSet<Character>();
    for (int i = 0; i < s.length(); i++) letters.add(s.charAt(i));
    return letters;
}

Сравнение двух массивов из 26 частот стоит O(26), то есть константу относительно длины слов. Полная проверка двух слов занимает O(|s| + |t| + 26) времени и O(26) памяти. В задаче ниже вместо построения двух массивов можно постепенно израсходовать частоты первого слова символами второго. Ранний отрицательный счётчик означает, что нужных копий не хватает.

Что считается одним символом: char, кодовая точка или видимый знак?

Ограничение a…z должно быть частью условия. Для произвольного Unicode charAt читает кодовые единицы UTF-16; одна дополнительная кодовая точка занимает пару char. Разные пары могут дать одинаковый набор отдельных char. Если анаграмма определена по кодовым точкам, считаем codePoints(), а не charAt. Видимый знак тоже может состоять из нескольких кодовых точек: это ещё один уровень задачи.

static Map<Integer, Integer> charBag(String s) {
    var count = new TreeMap<Integer, Integer>(); // TreeMap упорядочивает только печать ключей.
    for (int i = 0; i < s.length(); i++) count.merge((int) s.charAt(i), 1, Integer::sum);
    return count;
}

static Map<Integer, Integer> codePointBag(String s) {
    var count = new TreeMap<Integer, Integer>();
    s.codePoints().forEach(cp -> count.merge(cp, 1, Integer::sum));
    return count;
}

В первых двух строках обе суррогатные пары корректны, но составлены по-разному. Мультимножество char совпало, мультимножество кодовых точек — нет. Для é и e + комбинируемого акцента сырые кодовые точки тоже различны. NFC уравнивает эту канонически эквивалентную запись; применять такую нормализацию надо по условиям продукта. Регистр, пробелы и видимые составные символы требуют своих правил, которые нельзя молча добавить в алгоритм.

Группа определяется полной неизменяемой подписью

Теперь нужно собрать все метки-анаграммы в группы. Сравнивать новое слово со всеми прежними группами — снова многократный поиск. Вычислим каноническую подпись: для анаграмм она одинакова, для разных мультимножеств различна. Таблица будет хранить подпись → список слов этой группы.

Первый вариант — отсортировать буквы: pay и yap дают apy, bat и tab дают abt. Второй — вектор частот всех 26 букв. Порядок слов исчезает в обоих вариантах, но количество каждой буквы сохраняется. Сортировка слова длины m требует O(m log m), подсчёт — O(m + 26); подпись потом всё равно надо сформировать, хешировать и сравнивать.

Фрагменты GroupingDemo.java. Вариант countKey возвращает String с разделителями. Подпись неизменяема, а список группы остаётся изменяемым: в него последовательно добавляются слова:

static String sortedKey(String word) {
    char[] chars = word.toCharArray();
    Arrays.sort(chars);
    return new String(chars); // Строка неизменяема, равенство по содержимому.
}

static String countKey(String word) {
    int[] count = new int[26];
    for (int i = 0; i < word.length(); i++) count[word.charAt(i) - 'a']++;
    return Arrays.toString(count); // Разделители сохраняют границы чисел.
}

static List<List<String>> group(String[] words, boolean sorting) {
    var groups = new LinkedHashMap<String, List<String>>();
    for (String word : words) {
        String key = sorting ? sortedKey(word) : countKey(word);
        groups.computeIfAbsent(key, ignored -> new ArrayList<>()).add(word);
    }
    return new ArrayList<>(groups.values()); // Группы по первому появлению, слова по входу.
}

String[] words = {"pay", "bat", "yap", "aab", "tab", "aba", "abb"};
System.out.println("== canonical groups ==");
System.out.println("sorted=" + group(words, true));
System.out.println("counts=" + group(words, false));

== canonical groups ==
sorted=[[pay, yap], [bat, tab], [aab, aba], [abb]]

Оба способа дали одинаковые группы. LinkedHashMap в обычном режиме вставки сохраняет порядок первого появления подписи, ArrayList — порядок добавления слов. Повторное слово остаётся второй записью: группировка сама по себе не удаляет дубли. HashMap также собрал бы правильные группы, но порядок обхода групп не обещал бы. В условиях задачи надо отдельно сказать, важен ли этот порядок.

Подпись и её хеш — разные вещи

Числа частот надо разделять. Если склеить десятичные записи без границ, [1, 11] и [11, 1] дадут одну строку 111. Другой опасный способ — использовать только Arrays.hashCode(count): разные массивы могут иметь одинаковый хеш, а таблице тогда уже нечего сравнивать. Хеш выбирает место поиска; полный ключ подтверждает, что группа действительно та же.

Сам массив тоже не готовый ключ по содержимому. Его обычные equals и hashCode работают с идентичностью объекта. Record с компонентом int[] сохраняет это правило компонента: final-ссылка не добавляет сравнение элементов и не делает элементы массива неизменяемыми. Два независимо построенных массива одной частоты окажутся разными ключами.

record BadKey(int[] count) {} // equals компонента — обычный equals массива.

У двух массивов [0, 31] и [1, 0] один Arrays.hashCode — 992, хотя содержимое разное. Два BadKey с содержимым [2, 1] создали две записи; строковая подпись создала одну. Для рабочей подписи можно написать отдельный value object, который копирует массив и реализует Arrays.equals/Arrays.hashCode. Копирование и отсутствие изменяемого доступа нужны, чтобы хеш ключа не менялся после вставки.

Если всего N слов и T символов, сортированные подписи требуют суммарного времени O(Σ mᵢ log mᵢ) плюс чтение, хеширование и группировка. Частотный вариант ожидаемо O(T + 26N) при фиксированном алфавите. Для строки Arrays.toString ещё есть цена десятичной записи счётчиков; при длинных словах учитывай длину ключа. Результат хранит N ссылок на исходные слова, ключи — по одной подписи на группу. При возвращении готовых групп память результата тоже O(N), даже если считать только один проход по входу.

На собеседовании сначала назови сведения, которые нужно сохранить

Узнать этот паттерн помогают повторяющиеся запросы к уже прочитанной части: «есть ли дополнение», «сколько было копий», «найти повтор», «объединить по одинаковому признаку». Сначала назови перебор, затем выведи нужный ключ и значение. Фраза «использую HashMap» ещё не объясняет ни алгоритм, ни то, почему он сохраняет ответ.

Произнеси инвариант до цикла: «здесь только индексы меньше j», «здесь число копий в обработанном префиксе» или «этот ключ представляет всё мультимножество». Потом покажи сохранение после каждого действия. Проверь пустой вход, одну копию, несколько одинаковых элементов, отсутствие ответа и переполнение. Для строк уточни алфавит; для групп — равенство ключей и порядок результата.

Память зависит от числа различных ключей d, а не только от n. Однако ключ длины m не хешируется и не сравнивается магически за один символ: учитывай его создание и чтение. ContainsValue ищет по значениям и просматривает таблицу; если часто нужен обратный поиск, выбирают обратный индекс или меняют смысл ключа. При известном маленьком диапазоне частоты массива обходятся без упаковки ключей и записи хешей.

Порядок массива важен не во всех задачах. Если нужны цепочки последовательных значений, HashSet позволяет начинать расширение только там, где нет предшественника. Это не подмассив из соседних позиций. В последней задаче ниже внешний цикл идёт по уникальным значениям: множество сохраняет наличие, а длину цепочки получаем из соседних запросов. Дубликаты начала иначе заставили бы снова проходить уже известную цепочку.

Если память O(n) не помещается, рассмотрим сортировку и соседние сравнения или два указателя. Это часто O(n log n) времени; при сохранении исходных индексов нужна дополнительная обвязка. Для выгрузки больше памяти процесса возможны внешняя сортировка или GROUP BY в базе. Подсчёт частот в ограниченном локальном окне разобран в Sliding Window, суммы подмассивов — в Prefix Sums; выбор самых частых — в Heap & Top-K.

В платёжном сервисе одинаковая сумма не означает одинаковый платёж. Ключ дедупликации должен включать нужную бизнес-идентичность: например, merchantId вместе с idempotencyKey. Подсчёт выгрузки в HashSet не обеспечивает идемпотентность между перезапусками и не согласует несколько экземпляров сервиса. На собеседовании отдели решение задачи по массиву от хранения факта операции: Idempotency разбирает эту границу отдельно.

Уточнения senior-уровня меняют условия задачи, а не просто длину кода: все пары вместо одной, окно вместо всего префикса, Unicode вместо a…z, несколько потоков вместо одного прохода. Сначала выясни, какие новые сведения нужны. Например, все пары требуют нескольких индексов на значение, а при уходе элемента из окна счётчик надо уменьшить. Один метод merge не заменяет согласование общего изменяемого состояния.

  • Таблица убирает повторный поиск ценой памяти. Выбирай отдельно ключ и смысл значения.
  • Для Two Sum сначала запрос, затем вставка: партнёр лежит в прошлой части и отличается по индексу.
  • Множество хранит наличие, частоты — количество. Анаграммы требуют полного мультимножества.
  • Подпись должна быть полной и неизменяемой. Один хеш и массив с обычным equals для этого не подходят.
  • В оценке времени учитывай создание и длину ключа; порядок результата и бизнес-идентичность уточняются отдельно.

Подсказка 2

Храни значение → ранний индекс. Сначала ищи дополнение, потом добавляй текущую позицию; разность вычисляй в long.

Решение

Перед j таблица содержит только позиции меньше j. Дополнение из неё образует пару с текущей позицией. PutIfAbsent сохраняет минимальный i, а порядок прохода даёт минимальный j. В отличие от исходного LeetCode здесь отсутствие ответа допустимо и выбор при нескольких ответах определён.

static int[] twoSum(int[] nums, int target) {
    var seen = new HashMap<Long, Integer>();
    for (int j = 0; j < nums.length; j++) {
        Integer i = seen.get((long) target - nums[j]); // Только предыдущие позиции.
        if (i != null) return new int[]{i, j};
        seen.putIfAbsent((long) nums[j], j); // При равных числах сохраняем ранний индекс.
    }
    return new int[0];
}

Ожидаемое O(n) времени и O(d) памяти, d — число разных прочитанных значений. Вход не сортируется. Long нужен для дополнения за пределами int.

Массив — запас букв первой строки. Каждая буква второй забирает одну копию. Если счётчик стал отрицательным, копий не хватает. При равных длинах и отсутствии отрицательных остатков сумма всех счётчиков равна 0, значит каждое значение равно 0: весь запас израсходован.

static boolean isAnagram(String s, String t) {
    if (s.length() != t.length()) return false;
    int[] count = new int[26];
    for (int i = 0; i < s.length(); i++) count[s.charAt(i) - 'a']++;
    for (int i = 0; i < t.length(); i++) {
        if (--count[t.charAt(i) - 'a'] < 0) return false; // t запросила лишнюю копию буквы.
    }
    return true; // Длины равны: израсходован весь запас s, остатка нет.
}

Подсказка 2

Ключ должен сравниваться по содержимому и сохранять границы счётчиков. LinkedHashMap задаст порядок групп, список — порядок слов.

Решение

Для каждого слова строим частоты и сериализуем их в неизменяемую строку с разделителями. ComputeIfAbsent создаёт список только для новой подписи; слово добавляется в существующий список. LinkedHashMap сохраняет порядок первой вставки ключа. Подписи пустых слов одинаковы, поэтому они попадают в одну группу.

static List<List<String>> groupAnagrams(String[] words) {
    var groups = new LinkedHashMap<String, List<String>>();
    for (String word : words) {
        int[] count = new int[26];
        for (int i = 0; i < word.length(); i++) count[word.charAt(i) - 'a']++;
        String key = Arrays.toString(count); // Не массив и не один его hashCode.
        groups.computeIfAbsent(key, ignored -> new ArrayList<>()).add(word);
    }
    return new ArrayList<>(groups.values());
}

При N словах и T символах подсчёт и обработка 26 частот дают ожидаемое O(T + 26N), плюс длина текстовых подписей. Дополнительно — ключи для групп и O(N) ссылок результата. Подпись одного слова нельзя сократить до одного hashCode.

static List<String> duplicates(String[] ids) {
    var seen = new HashSet<String>();
    var repeated = new LinkedHashSet<String>();
    for (String id : ids) if (!seen.add(id)) repeated.add(id);
    return new ArrayList<>(repeated); // Второе появление определяет порядок выдачи.
}

Ожидаемое O(n) операций таблиц и O(d) памяти. Для строк учитывай хеширование и сравнение их содержимого; при ограниченной длине это ожидаемое O(n) времени. Результат занимает до O(d) ссылок.

Подсказка 2

Начинай только из числа без предшественника. Перебирай уникальные числа, чтобы повторный старт не расширял одну цепочку ещё раз. Границы int проверяй до +1 и −1.

Решение

Множество удаляет повторы. Если есть start − 1, текущая вершина не начинает цепочку и пропускается. Иначе расширяемся вправо до первого отсутствующего значения. Каждая уникальная цепочка обходится один раз. MIN_VALUE не имеет допустимого предшественника, MAX_VALUE не имеет допустимого следующего числа; проверки стоят до арифметики.

static int longestConsecutive(int[] nums) {
    var values = new HashSet<Integer>();
    for (int x : nums) values.add(x);
    int best = 0;
    for (int start : values) { // По уникальным числам: дубли старта не повторяют всю цепочку.
        if (start != Integer.MIN_VALUE && values.contains(start - 1)) continue;
        int end = start, length = 1; // Предшественника нет: это начало одной цепочки.
        while (end != Integer.MAX_VALUE && values.contains(end + 1)) {
            end++;
            length++;
        }
        best = Math.max(best, length);
    }
    return best;
}

Построение множества и проверки предшественников требуют ожидаемого O(n). Суммарно while проходит O(d) уникальных значений: одно значение принадлежит одной цепочке. Память O(d). Вложенный while не даёт O(n²), потому что повторные старты исключены.

Внешний цикл заменили на for (int start : nums). Ответ тот же. Что испортилось?

При входе [1,1,…,1,2,3,…,m] каждая копия 1 снова расширит цепочку до m. Дублей старта может быть O(n), длина цепочки тоже O(n), и время станет квадратичным. Внешний цикл по множеству или отдельная пометка обработанного начала сохраняют линейный суммарный обход.
