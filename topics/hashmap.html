HashMap

HashMap — массив корзин table, длина которого всегда степень двойки. Индекс корзины — hash & (n − 1). Сначала hashCode перемешивается: h ^ (h >>> 16), чтобы старшие биты тоже влияли на индекс. В демо тысяча хешей, различающихся только старшими битами, без перемешивания попала бы в одну корзину. Внутри корзины узлы связаны в список. Поиск сравнивает сначала хеш, потом equals, поэтому equals без hashCode ломает карту. Когда записей больше, чем 0,75 длины таблицы, таблица удваивается, и каждая корзина делится на две: элемент остаётся на месте или переезжает на i + oldCap. Корзина длиннее 8 узлов становится красно-чёрным деревом, но только при таблице от 64; до этого карта просто растёт. Дерево спасает от плохих хешей, если ключи Comparable: 5000 поисков среди 50 000 коллизий заняли 0,5 мс против 463 мс у несравнимых ключей. HashMap не потокобезопасен: восемь потоков потеряли больше половины записей.

От ключа к корзине

Кеш курсов, справочник счетов, группировка платежей по клиенту — везде HashMap, потому что get и put работают за O(1). Эта O(1) держится на трёх вещах: хорошем распределении ключей по корзинам, коротких корзинах и правильных equals/hashCode. Демо InternalsDemo.java показывает внутренности через рефлексию (флаг --add-opens):

== where keys land in a table of 16
p-1   hashCode     109076  spread     109077  index  5
p-2   hashCode     109077  spread     109076  index  4
p-17  hashCode    3381411  spread    3381392  index  0
RUB   hashCode      81503  spread      81502  index 14
USD   hashCode      84326  spread      84327  index  7
null  -> index 0
== why the high bits are mixed in
1000 hashes i<<16: distinct buckets without mixing = 1, with mixing = 16

Зачем перемешивание: тысяча хешей вида i << 16 различаются только старшими битами. Без перемешивания все они дают индекс 0 в таблице 16 — одна корзина на тысячу ключей, поиск O(n). С перемешиванием заняты все 16 корзин. Такие хеши реальны: Float, Double, числовые идентификаторы с шагом степени двойки. Одной операции XOR хватает, чтобы закрыть самые частые плохие случаи, а от совсем плохого hashCode защищают деревья — шаг 4.

equals и hashCode — контракт, на котором всё держится

== equals without hashCode
size = 2, get = null

Демо PitfallsDemo.java: Account переопределил equals по IBAN, но не hashCode. Два равных счёта получили разные хеши из Object.hashCode, попали в разные корзины, и карта хранит оба; get с третьим равным объектом ищет в третьей корзине и возвращает null. Правило: равные объекты обязаны иметь равные хеши; поля в hashCode — подмножество полей equals. Обратное не требуется — разные объекты с одинаковым хешем это коллизия, разрешённая, но дорогая. Контракт подробно — в Object Methods; records и Lombok генерируют пару согласованно.

Вторая половина контракта — ключ не должен меняться, пока лежит в карте. Узел хранит хеш, вычисленный при вставке; если поменять поле ключа, участвующее в hashCode, ключ окажется в «чужой» корзине и станет недостижим — разобрано на примере с HashSet в Encapsulation. Поэтому ключами делают неизменяемые типы: String, обёртки, records, enum. String к тому же кеширует свой хеш в поле, и повторные вычисления бесплатны.

Load factor, рост и деление корзин

== resize: table and threshold
new HashMap(): table = null
after put #1   table  16, threshold  12
after put #13  table  32, threshold  24
after put #25  table  64, threshold  48
after put #49  table 128, threshold  96
after put #97  table 256, threshold 192

Таблица создаётся лениво — при первом put, на 16 корзин. Порог threshold = capacity × loadFactor, load factor по умолчанию 0,75: при 13-й записи в таблице 16 карта удваивается. 0,75 — компромисс между памятью и длиной корзин: при случайных хешах длина корзины подчиняется распределению Пуассона со средним около 0,5, и вероятность корзины из 8 элементов — порядка 6 на 100 миллионов, как написано в комментарии к исходнику HashMap. Меньший load factor — короче корзины и больше памяти, больший — наоборот.

new HashMap<>(100) holds 100 without resize: false
HashMap.newHashMap(100) holds 100 without resize: true
new HashMap<>(100) table = 128, newHashMap(100) table = 256

Частая ошибка: new HashMap<>(100) — это ёмкость, а не число элементов. Таблица 128, порог 96, и сотый элемент вызывает рост. С Java 19 есть HashMap.newHashMap(numMappings), который сам делит на 0,75: таблица 256, сто записей без роста. До Java 19 писали new HashMap<>((int) (n / 0.75f) + 1) или Maps.newHashMapWithExpectedSize из Guava.

== split on resize: index i stays or moves to i + oldCap
key  5: index in 16 = 5, in 32 =  5 (hash & 16 =  0)
key 21: index in 16 = 5, in 32 = 21 (hash & 16 = 16)
key 37: index in 16 = 5, in 32 =  5 (hash & 16 =  0)
key 53: index in 16 = 5, in 32 = 21 (hash & 16 = 16)

При удвоении маска получает один новый бит. Для каждого ключа индекс либо прежний (новый бит хеша 0), либо i + oldCap (бит 1) — третьего не дано. Поэтому resize не вычисляет индексы заново: он проходит корзину один раз, раскладывает узлы в два списка lo и hi, сохраняя порядок, и кладёт их в i и i + oldCap. Сохранение порядка появилось в Java 8. В Java 7 перенос разворачивал список, и при одновременном росте из двух потоков узлы могли замкнуться в цикл — знаменитый бесконечный цикл HashMap.get под нагрузкой. В Java 8+ цикла нет, но гонки остались — шаг 5.

Рост — O(n) копирования, и отдельный put может занять заметное время на большой карте. Это та же амортизация, что у ArrayList из List. Удаление таблицу не уменьшает. А порядок обхода HashMap зависит от индексов, поэтому меняется при росте:

== iteration order is not stable
4 keys:        [p-9, p-12, p-11, p-10]
after a resize: [p-12, p-11, p-10, p-9]

Те же четыре ключа после роста и удаления временных записей обходятся в другом порядке. Код, который полагается на порядок HashMap — в тестах, в JSON-ответах, в выборе «первого» элемента, — ломается от изменения объёма данных или версии JDK. Нужен порядок вставки — LinkedHashMap, сортировка — TreeMap, обе в Other Maps & Sets.

Коллизии: список, потом дерево

== collisions: list, then tree
 8 keys in one bin: table  16, bin node Node
 9 keys in one bin: table  32, bin node Node
10 keys in one bin: table  64, bin node Node
11 keys in one bin: table  64, bin node TreeNode

Ключи BadKey с hashCode() = 42 все попадают в одну корзину. Когда в корзине становится больше 8 узлов (TREEIFY_THRESHOLD), HashMap пытается превратить её в красно-чёрное дерево. Но если таблица меньше 64 (MIN_TREEIFY_CAPACITY), вместо дерева она растёт: длинная корзина в маленькой таблице чаще означает «мало корзин», чем «плохой хеш». В демо 9-й ключ увеличил таблицу до 32, 10-й — до 64, и только 11-й превратил корзину в дерево из TreeNode. Обратно в список дерево превращается, когда при росте в нём остаётся 6 узлов и меньше (UNTREEIFY_THRESHOLD) — разрыв между 8 и 6 не даёт корзине прыгать туда-обратно.

== get() cost with 50 000 keys in one bin
5000 gets: Comparable keys 0.5 ms, non-Comparable keys 463.5 ms (sum 249950000)

Дерево упорядочивает узлы сначала по хешу, а при равных хешах — по compareTo, если ключи одного класса реализуют Comparable. Для BadKey это работает: поиск в дереве из 50 000 узлов — O(log n), 5000 поисков за 0,5 мс. У BadKeyNoCompare хеши равны, сравнить нечем, и при вставке порядок выбирается по имени класса и identityHashCode — для поиска это бесполезно. get не знает, в каком поддереве искать, и обходит оба: O(n), в 900 раз медленнее. Деревья появились в Java 8 как защита от атак HashDoS: злоумышленник присылает тысячи параметров запроса с одинаковым хешем, и сервер тратит на них квадратичное время. Строки — Comparable, поэтому для них защита работает.

Узел дерева TreeNode примерно вдвое больше обычного Node, и при нормальных хешах деревьев не бывает вовсе. Если в профиле видно TreeNode — это сигнал о плохом hashCode: например, считающем только по одному полю с малым числом значений, или по Enum.ordinal.

Многопоточность и практика

== HashMap shared by threads
expected 400000: HashMap 243418, ConcurrentHashMap 400000
expected 400000: HashMap 183824, ConcurrentHashMap 400000
expected 400000: HashMap 108914, ConcurrentHashMap 400000

Восемь потоков вставили 400 000 разных ключей. HashMap потерял от 40 до 70% записей: два потока одновременно записали узел в одну пустую корзину — один перезаписал другого; поток читал старую таблицу, пока другой переносил её при росте; size без синхронизации теряет инкременты. Исключения нет, карта просто тихо неверна. ConcurrentHashMap вставил все: CAS на пустую корзину, блокировка только головы корзины, совместный рост — устройство в Concurrent Collections. Если карта строится в одном потоке и потом только читается, достаточно безопасно её опубликовать — например, через Map.copyOf в final-поле.

== counting: merge instead of get + put
counts = {EUR=1, RUB=3, USD=1}

API Java 8 убирает двойной поиск и шаблонный код: merge(k, 1, Integer::sum) для счётчиков, computeIfAbsent(k, x -> new ArrayList<>()).add(v) для группировки, getOrDefault, putIfAbsent. В ConcurrentHashMap эти методы атомарны, в HashMap — просто короче. Функция внутри computeIfAbsent не должна изменять ту же карту: HashMap в этом случае бросает ConcurrentModificationException (с Java 9). Карта ключей-enum — EnumMap из Enums: массив по ordinal без хешей.

Красно-чёрные деревья гарантируют O(log n) при любых коллизиях.

Только если ключи Comparable. Без этого дереву не по чему упорядочить равные хеши, и get обходит оба поддерева: в демо 50 000 несравнимых ключей в одной корзине искались в 900 раз медленнее сравнимых. И дерево появляется лишь при таблице от 64 корзин.

  • table — массив корзин длиной степень двойки; индекс hash & (n − 1) после h ^ (h >>> 16).
  • В корзине сравнивается хеш, затем equals; equals без hashCode даёт дубликаты и null из get.
  • Таблица ленивая (16), растёт вдвое при size > 0,75 × capacity; new HashMap(100) — ёмкость, newHashMap(100) — число записей.
  • При росте корзина делится на lo (i) и hi (i + oldCap) по одному биту; порядок сохраняется с Java 8.
  • Порядок обхода HashMap меняется при росте.
  • Корзина > 8 узлов → дерево, если таблица ≥ 64; иначе рост. Дерево быстро только для Comparable-ключей.
  • HashMap в нескольких потоках тихо теряет записи; ConcurrentHashMap — нет.

На собеседовании

Как устроен HashMap?

Массив корзин, длина — степень двойки. При put вычисляется hashCode ключа, перемешивается со старшими битами, индекс корзины — hash & (n − 1). В корзине — связный список узлов; поиск сравнивает хеш, затем equals. Когда записей больше capacity × 0,75, таблица удваивается. С Java 8 корзина длиннее 8 узлов превращается в красно-чёрное дерево при таблице от 64. get и put — O(1) в среднем.

  • При росте узел остаётся в i или переезжает в i + oldCap — по одному биту хеша.
  • Дерево — защита от HashDoS; эффективно только для Comparable-ключей.
  • Java 7 разворачивала списки при росте — бесконечный цикл при гонке.

Что будет, если переопределить equals, но не hashCode?

Равные объекты получат разные хеши из Object.hashCode и попадут в разные корзины. Карта сохранит «одинаковые» ключи дважды, а get с равным объектом вернёт null. Контракт: равные объекты обязаны иметь равные хеши. Ещё одна ошибка — менять поля ключа, участвующие в hashCode, пока ключ лежит в карте: ключ становится недостижим.

  • Узел хранит хеш, вычисленный при вставке, и сравнивает его первым.
  • Ключи — неизменяемые типы; String кеширует хеш.
Почему этот кеш курсов растёт без ограничений? 
record RateKey(String from, String to, Instant at) {}
Map<RateKey, BigDecimal> cache = new ConcurrentHashMap<>();
BigDecimal rate(String from, String to) {
    return cache.computeIfAbsent(new RateKey(from, to, Instant.now()), k -> provider.load(from, to));
}

В ключ входит Instant.now() с наносекундами: каждый вызов создаёт новый, ни с чем не равный ключ. Кеш никогда не попадает и бесконечно растёт. Ключ должен содержать только то, от чего зависит значение: валютную пару и, если нужно, дату или окно времени (LocalDate, усечённое время). Плюс ограничение размера и вытеснение — Caffeine или LinkedHashMap с removeEldestEntry.

Что такое load factor и когда HashMap расширяется?

Load factor — доля заполнения, после которой таблица удваивается; по умолчанию 0,75. Таблица 16 растёт на 13-й записи. Меньше — короче корзины и больше памяти, больше — наоборот. new HashMap(n) задаёт ёмкость, а не число записей; чтобы вместить n без роста, нужно HashMap.newHashMap(n) (Java 19) или ёмкость n / 0,75.

  • При 0,75 и случайных хешах корзина из 8 узлов почти невероятна (Пуассон).
  • Рост — O(n), отдельный put на большой карте может быть медленным.

Почему HashMap нельзя использовать из нескольких потоков?

Операции не атомарны: два потока одновременно пишут в одну корзину и затирают друг друга, чтение во время роста видит частично перенесённую таблицу, size теряет инкременты. В результате записи тихо теряются — без исключений. Нужен ConcurrentHashMap или, для карты «построил и только читаю», безопасная публикация неизменяемой копии.

  • В Java 7 гонка при росте могла зациклить список и повесить get.
  • Collections.synchronizedMap блокирует всю карту на каждую операцию.
