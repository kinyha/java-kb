Heap Sort

Для отчёта суммы платежей должны идти по возрастанию. Heap sort сначала перестраивает тот же массив так, чтобы максимум всегда стоял в корне. Затем переносит этот максимум вправо, сужает рабочую часть и восстанавливает корень. Слева остаётся куча, справа растёт отсортированный суффикс. Буфер слияния и рекурсивный стек не нужны: порядок хранится в отношениях между индексами.

Отношения родителей и детей дают максимум без нового поиска

Сервис готовит отчёт по суммам оплат. Исходный массив уже в памяти, но второго массива для слияния хотелось бы избежать. Простой способ — находить максимум оставшихся платежей и ставить его в конец. Однако каждый поиск заново просматривает почти весь остаток: (n − 1) + (n − 2) + … + 1 = n(n − 1)/2 сравнений. Это квадратичная работа.

Сохраним достаточно порядка, чтобы максимум был известен сразу. Представим массив как полное двоичное дерево: уровни заполнены, последний заполняется слева. Узлы лежат по уровням, поэтому для индекса i дети имеют индексы 2*i + 1 и 2*i + 2. Индекс родителя при i > 0 — (i − 1)/2. Отдельные объекты-узлы создавать не нужно.

В max-heap значение родителя не меньше значений его детей. По цепочке родителей это отношение доходит до корня, значит, в a[0] находится максимум всей кучи. Но отношения между братьями и соседями в массиве не заданы. Посмотри на 100 перед 600 в нижнем ряду: куча уже правильная, массив ещё не отсортирован.

Куча занимает префикс [0, size); size — исключительная граница, а не последний индекс. Ребёнок существует только при индексе меньше size. Это важно, когда конец массива уже готов: он остаётся физически рядом, но в дерево больше не входит.

Если корень максимален, массив уже является max-heap.

Максимальный корень — следствие инварианта, но не весь инвариант. Например, у [900, 100, 700, 800] корень максимален, а ребро 100 → 800 нарушено. Проверять нужно каждого родителя; восстанавливать только корень можно при уже правильных дочерних поддеревьях.

Каждый пример — один Java-файл без зависимостей. Запуск из корня: java examples/heap-sort/HeapSortDemo.java; прогон ниже выполнен на JDK 21.0.11. Полный файл содержит трассировки и счётчики, README — команды задач. Служебные метки секций в выводах убраны.

Маленький корень спускается через большего ребёнка

Дочерние поддеревья уже являются кучами, но в корень положили 100. Слева стоит 900, справа 700. Обмен с левым ребёнком исправляет верхнее ребро: 900 не меньше ни 100, ни 700. Теперь нарушение может остаться только там, куда спустилось 100. Повторим тот же выбор среди его детей 800 и 600.

Выбирать нужно большего ребёнка. Если поднять 700 вместо 900, новое значение корня окажется меньше второго ребёнка и инвариант не восстановится. Если же текущий узел уже не меньше большего ребёнка, он не меньше обоих; ниже порядок верен по условию. Спуск можно закончить.

static long comparisons, swaps; // только наблюдение за числом действий
static void siftDown(int[] a, int root, int size) {
    while (root < size / 2) {           // только узлы с левым ребёнком
        int child = 2 * root + 1;
        if (child + 1 < size) {
            comparisons++;
            if (a[child] < a[child + 1]) child++; // выбираем большего ребёнка
        }
        comparisons++;
        if (a[root] >= a[child]) return; // в поддеревьях порядок уже верен
        swap(a, root, child);
        root = child;                  // нарушение могло уйти только сюда
    }
}
static void swap(int[] a, int x, int y) {
    int t = a[x]; a[x] = a[y]; a[y] = t;
    swaps++;
}

Цикл идёт только по одной ветви дерева. Условие root < size / 2 означает «есть левый ребёнок» и позволяет безопасно вычислить его индекс. Правый ребёнок проверяется отдельно: на последнем уровне его может не быть. Счётчики измеряют сравнения значений и обмены для следующего опыта; границы циклов в них не входят.

Трассировка тех же обменов

Обвязка печатает начальное состояние, состояние после каждого обмена и конец спуска. Ниже указаны все её действия; в основном алгоритме такой печати нет.

static void traceRoot(int[] a, int size) {
    int root = 0;
    show(a, root, "start");
    while (root < size / 2) {
        int child = 2 * root + 1;
        if (child + 1 < size && a[child] < a[child + 1]) child++;
        if (a[root] >= a[child]) break;
        swap(a, root, child);
        root = child;
        show(a, root, "swap");
    }
    show(a, root, "done");
}
static void show(int[] a, int root, String phase) {
    System.out.println(Arrays.toString(a) + " root=" + root + " " + phase);
}
traceRoot(new int[]{100, 900, 700, 800, 600, 200, 500}, 7);

Высота полного дерева — floor(log₂ size). Поэтому один sift-down делает не больше этого числа спусков и стоит O(log n) в худшем случае. Если корень уже подходит, проверка заканчивается на первом уровне. Рекурсия здесь не нужна: два индекса хранят весь путь.

Построение снизу тратит мало работы на большинство узлов

Чтобы начать сортировку, нужна куча из всего входа. Вызывать sift-down от корня к листьям неверно: спуск предполагает, что дочерние поддеревья уже являются кучами. Листья удовлетворяют этому условию сами. Начнём с последнего внутреннего узла n/2 − 1 и будем двигаться к корню.

static void heapify(int[] a) {
    for (int root = a.length / 2 - 1; root >= 0; root--) {
        siftDown(a, root, a.length);    // дети обработаны раньше родителя
    }
}

static void traceBuild(int[] a) {
    System.out.println("input " + Arrays.toString(a));
    for (int root = a.length / 2 - 1; root >= 0; root--) {
        siftDown(a, root, a.length);
        System.out.println("root=" + root + " " + Arrays.toString(a));
    }
}
traceBuild(new int[]{400, 200, 500, 100, 300});
input [400, 200, 500, 100, 300]
root=1 [400, 300, 500, 100, 200]
root=0 [500, 300, 400, 100, 200]

Для пяти платежей первыми обрабатываются дети узла 1: 100 и 300. После спуска у его поддерева корень 300. Затем обрабатывается узел 0; обе его дочерние части уже правильные. На выходе максимум 500 оказался в начале, но 300 стоит перед 400: построение кучи не завершает сортировку.

Мы вызвали sift-down n/2 раз, значит heapify стоит Θ(n log n).

Это грубая верхняя оценка, которая назначает каждому узлу высоту всего дерева. Но около половины узлов — листья, а большинство остальных может спуститься только на один-два уровня. Длинный путь есть у немногих узлов.

Суммарно не больше 11 спусков, а не 15 × 3. Для произвольного размера можно посчитать узлы, которым доступен хотя бы один уровень вниз, затем хотя бы два и так далее. Их не больше floor(n/2), floor(n/4), floor(n/8), …. Сумма высот меньше n/2 + n/4 + n/8 + … = n. Каждый спуск требует постоянного числа сравнений, остановки тоже дают лишь линейную добавку: bottom-up heapify работает за O(n).

Последовательные вставки с подъёмом вверх дают другой процесс и верхнюю оценку O(n log n). Для готового массива bottom-up использует уже известное расположение узлов. Динамические вставки и очередь с приоритетом — в теме Heaps; здесь массив сразу доступен целиком.

Максимум уходит вправо, а рабочая куча сужается

Теперь максимум доступен в a[0]. Поменяем его с последним элементом рабочей части и уменьшим size. Максимум занял окончательную позицию справа. В корень пришло значение с последнего уровня: дочерние поддеревья остались кучами, а исправить нужно только новый корень.

static void sort(int[] a) {
    heapify(a);
    for (int size = a.length; size > 1;) {
        swap(a, 0, --size);             // максимум занимает начало суффикса
        siftDown(a, 0, size);           // суффикс [size, n) больше не трогаем
    }
}

Перед каждым извлечением верны три утверждения: [0, size) — max-heap; [size, n) отсортирован по возрастанию; любой элемент префикса не больше любого элемента суффикса. Новый максимум остатка ставится перед прежним суффиксом, поэтому общий порядок справа сохраняется. После sift-down восстановлено и первое утверждение.

Сначала извлекли 500, затем 400. Хотя максимумы приходят по убыванию, мы записываем их справа налево, и результат получается возрастающим. Когда size равен 1, оставшийся минимум уже на месте. Для пустого массива и одного элемента оба рабочих цикла ничего не делают.

Код, который печатает шесть кадров

Первый обмен показан до восстановления: строка swap честно обозначает временно нарушенную кучу. Все строки heap печатаются после восстановления. Это тот же цикл, с дополнительными наблюдениями.

static void traceSort(int[] a) {
    heapify(a);
    System.out.println("heap size=" + a.length + " " + Arrays.toString(a));
    for (int size = a.length; size > 1;) {
        swap(a, 0, --size);
        if (size == a.length - 1) {
            System.out.println("swap size=" + size + " " + Arrays.toString(a));
        }
        siftDown(a, 0, size);
        System.out.println("heap size=" + size + " " + Arrays.toString(a));
    }
}

Вызов siftDown(a, 0, a.length) после извлечения разрушит готовый суффикс: 500 опять станет кандидатом на подъём. Передавай уменьшенный size. Сортировка не удаляет элементы; она меняет границу, по которой их рассматривает как дерево.

Гарантия времени не даёт стабильности и не отменяет стоимость сравнений

Построение стоит O(n), затем выполняется не больше n − 1 извлечений по O(log n). Сортировка имеет верхнюю оценку O(n log n) и такую же оценку худшего случая. Здесь нет выбора опоры, который мог бы оставить цепочку из частей размера n − 1: высота кучи ограничена её формой.

Проверим работу нашего кода на возрастающем массиве и на одинаковых значениях. Счётчик сравнения увеличивается только перед сравнением двух значений; счётчик обменов — в swap. Для общего числа продолжаем извлечение из уже построенной кучи, не строим её повторно.

static void work(String name, int[] a) {
    comparisons = 0; swaps = 0;
    heapify(a);
    long buildComparisons = comparisons, buildSwaps = swaps;
    for (int size = a.length; size > 1;) {
        swap(a, 0, --size);
        siftDown(a, 0, size);
    }
    System.out.println(name + ": build comparisons=" + buildComparisons
            + ", build swaps=" + buildSwaps + ", total comparisons=" + comparisons);
}
int[] increasing = new int[1000], equal = new int[1000];
for (int i = 0; i < increasing.length; i++) increasing[i] = i;
Arrays.fill(equal, 7);
work("increasing n=1000", increasing);
work("equal n=1000", equal);
increasing n=1000: build comparisons=1982, build swaps=992, total comparisons=17583
equal n=1000: build comparisons=999, build swaps=0, total comparisons=2994

У 1000 возрастающих значений построение потребовало 1982 сравнения, а вся сортировка — 17 583. На равных наш спуск сразу останавливается: построение не сделало ни одного обмена, и суммарная работа линейна. Это не обещание лучшего поведения на «почти отсортированных» данных. O(n log n) — гарантия сверху, а не требование пройти log n уровней на каждом входе.

Итеративные циклы используют O(1) дополнительной памяти: индексы и переменную обмена. Сам вход в эту оценку не включается. Печать массивов, копии для проверок и эталонные сортировки в демо не относятся к памяти алгоритма. Рекурсивный sift-down добавил бы стек O(log n); новая PriorityQueue на все платежи потребовала бы отдельное хранилище.

Равные платежи могут поменяться местами

Наше сравнение останавливается на равных, но это не делает сортировку стабильной. Дальний обмен корня с концом меняет исходный порядок записей с одинаковой суммой. В этом опыте строки с id 10 и 20 равны для компаратора, который смотрит только на сумму:

record Payment(long id, long amount) {
    @Override public String toString() { return id + ":" + amount; }
}
static void sortPayments(Payment[] a, Comparator<Payment> order) {
    for (int root = a.length / 2 - 1; root >= 0; root--) sink(a, root, a.length, order);
    for (int size = a.length; size > 1;) {
        Payment t = a[0]; a[0] = a[--size]; a[size] = t;
        sink(a, 0, size, order);
    }
}
static void sink(Payment[] a, int root, int size, Comparator<Payment> order) {
    while (root < size / 2) {
        int child = 2 * root + 1;
        if (child + 1 < size && order.compare(a[child], a[child + 1]) < 0) child++;
        if (order.compare(a[root], a[child]) >= 0) return;
        Payment t = a[root]; a[root] = a[child]; a[child] = t;
        root = child;
    }
}
Payment[] p = {new Payment(10, 100), new Payment(20, 100), new Payment(30, 200)};
System.out.println("before " + Arrays.toString(p));
sortPayments(p, Comparator.comparingLong(Payment::amount));
System.out.println("after  " + Arrays.toString(p));
before [10:100, 20:100, 30:200]
after  [20:100, 10:100, 30:200]

Теперь 20 стоит раньше 10. Если отчёт должен сохранять исходный порядок равных, нужен стабильный алгоритм, например обычный Merge Sort. Если нужно другое правило — «при одинаковой сумме сначала меньший id» — сравнивай оба ключа. Это новый порядок, а не сохранение исходного; третья задача использует именно его.

Оценка времени предполагает сравнение за O(1). Для длинных строк или вычисляемого ключа прибавь стоимость компаратора. Для обычного массива не делай вывод «heap sort быстрее quick sort» только по худшей оценке: измерение учитывает работу с памятью и константы. Quick Sort разбирает другую гарантию, Sorting in Java — библиотечные контракты. Heap sort выбирают, когда нужен готовый массив, постоянная дополнительная память и ограничение худшего времени; он не предназначен для уже отсортированных потоков, где полезнее слияние.

  • Max-heap задаёт порядок на рёбрах, а не во всём массиве. Этого хватает, чтобы максимум был в корне.
  • Sift-down предполагает правильные дочерние кучи и поднимает большего ребёнка. После обмена нарушение остаётся только на одной ветви.
  • Bottom-up начинает с n/2 − 1. Сумма высот всех узлов линейна, поэтому построение стоит O(n).
  • После переноса максимума граница size сужается. Суффикс окончателен, и восстановление больше не должно его видеть.
  • Итеративный heap sort даёт O(n log n) сверху и O(1) дополнительной памяти, но не сохраняет порядок равных записей.

Задачи

Восстановить только изменённый корень

Префикс [0, size) хранит дерево с правильными дочерними max-heap. Нарушен может быть только корень. Восстанови весь префикс за O(log size) сверху и O(1) памяти. Элементы с индексами от size менять нельзя. Граница корректна, массив не null; при size 0 ничего не делай.

[100,200,300], size=3 → [300,200,100]
[100,200,999], size=2 → [200,100,999]
[], size=0 → []

Подсказка 1

Нарушение может спускаться только по одной ветви. Остальные поддеревья уже правильные.

Подсказка 2

Сначала выбери большего существующего ребёнка. В сравнениях используй size, а не длину массива.

Решение

Поднимаем большего ребёнка, затем продолжаем с позицией прежнего корня. Если корень не меньше выбранного ребёнка, дальнейший спуск не нужен. Пустой префикс отсекается условием цикла до обращения к a[0].

static void restoreRoot(int[] a, int size) {
    int root = 0;
    while (root < size / 2) {
        int child = 2 * root + 1;
        if (child + 1 < size && a[child] < a[child + 1]) child++; // больший из существующих
        if (a[root] >= a[child]) return; // оба ребёнка уже не больше
        int t = a[root]; a[root] = a[child]; a[child] = t;
        root = child; // единственная ветвь, где осталось нарушение
    }
}

Проверка с 999 отличает рабочую границу от физического конца. Случай с единственным левым ребёнком ловит чтение отсутствующего правого. Высота пути ограничивает время, а цикл не добавляет стек.

Сработает ли этот метод на [900,100,700,800]?

Корень уже максимален, поэтому он остановится. Но дочернее поддерево с корнем 100 нарушено. Не выполнено условие задачи; для произвольного массива нужен bottom-up heapify, а не один спуск от корня.

Оставить k крупнейших платежей в готовом суффиксе

Дан массив сумм и k. Переставь элементы так, чтобы [n − k, n) содержал k крупнейших значений по возрастанию, а оставшийся префикс был max-heap. Полностью сортировать префикс не нужно. Повторы учитываются как отдельные платежи. Все значения должны сохраниться; вход изменяется, дополнительная память O(1).

При k = 0 построй кучу из всего массива. При k = n отсортируй весь массив. Если k вне [0, n], брось IllegalArgumentException. Вспомогательный спуск уже дан.

[400,200,500,100,300], k=2 → [куча из 100,200,300 | 400,500]
[500,100,500,200], k=2 → [куча из 100,200 | 500,500]

Авторская задача · medium · O(n + k log n), JDK 21

Заготовка: HeapSuffix.java 
import java.util.Arrays;

public class HeapSuffix {
    static void keepLargest(int[] a, int k) {
        throw new UnsupportedOperationException("TODO");
    }
    static void siftDown(int[] a, int root, int size) {
        while (root < size / 2) {
            int child = 2 * root + 1;
            if (child + 1 < size && a[child] < a[child + 1]) child++;
            if (a[root] >= a[child]) return;
            swap(a, root, child);
            root = child;
        }
    }
    static void swap(int[] a, int x, int y) {
        int t = a[x]; a[x] = a[y]; a[y] = t;
    }
    static void check(int[] input, int k, int[] wantSuffix) {
        int[] sorted = input.clone();
        Arrays.sort(sorted); // эталон только для проверки сохранения всех значений
        keepLargest(input, k);
        int size = input.length - k;
        int[] gotSuffix = Arrays.copyOfRange(input, size, input.length);
        if (!Arrays.equals(gotSuffix, wantSuffix)) throw new AssertionError("suffix");
        for (int child = 1; child < size; child++) {
            if (input[(child - 1) / 2] < input[child]) throw new AssertionError("heap");
        }
        if (size > 0 && k > 0 && input[0] > input[size]) throw new AssertionError("boundary");
        int[] after = input.clone();
        Arrays.sort(after);
        if (!Arrays.equals(after, sorted)) throw new AssertionError("lost values");
        System.out.println("OK " + Arrays.toString(input) + " suffix=" + Arrays.toString(gotSuffix));
    }
    public static void main(String[] args) {
        check(new int[]{400, 200, 500, 100, 300}, 2, new int[]{400, 500});
        check(new int[]{500, 100, 500, 200}, 2, new int[]{500, 500});
        check(new int[]{100, 300, 200}, 0, new int[]{}); // всё равно строим кучу
        check(new int[]{300, 100, 200}, 3, new int[]{100, 200, 300});
        check(new int[]{}, 0, new int[]{});
        try {
            keepLargest(new int[]{100}, 2);
            throw new AssertionError("invalid k accepted");
        } catch (IllegalArgumentException expected) {
            System.out.println("OK invalid k");
        }
    }
}
Подсказка 1

Построй max-heap один раз. Последующие максимумы уже известны в её корне.

Подсказка 2

Повтори перенос максимума и сужение границы ровно k раз. Восстанови остаток, даже если это последнее извлечение задачи.

Решение

Это остановленный heap sort. После каждого извлечения максимум ставится перед прежним суффиксом и не превышает его значений. Восстановленный остаток остаётся кучей. При k = n последний обмен происходит с собой, а спуск с size 0 ничего не читает.

static void keepLargest(int[] a, int k) {
    if (k < 0 || k > a.length) throw new IllegalArgumentException("k");
    int size = a.length;
    for (int root = size / 2 - 1; root >= 0; root--) siftDown(a, root, size);
    for (int taken = 0; taken < k; taken++) {
        swap(a, 0, --size);
        siftDown(a, 0, size); // остаток снова куча, суффикс уже готов
    }
}

OK [200, 100, 500, 500] suffix=[500, 500]
OK [300, 100, 200] suffix=[]
OK [100, 200, 300] suffix=[100, 200, 300]
OK [] suffix=[]
OK invalid k

Построение — O(n), k извлечений — O(k log n) сверху. При k = 0 остаётся линейное построение. Проверки отдельно контролируют порядок суффикса, инвариант префикса, границу между ними и сохранение всех значений; конкретное расположение префикса не задано условием.

А если вход приходит потоком, а k намного меньше n?

Тогда хранить весь max-heap необязательно: другой вариант держит min-heap только из k кандидатов и заменяет минимального. Он требует O(k) памяти и O(n log k) времени сверху. Здесь задача про готовый массив и переиспользование его суффикса; потоковый отбор разобран в Heaps.

Упорядочить записи по сумме и id на месте

Дан массив Payment. Упорядочи его по сумме amount типа long со знаком, а при равенстве — по id, оба ключа по возрастанию. Значения могут включать корректировки и крайние long: сравнение вычитанием запрещено. Компаратор уже задан. Реализуй heap sort без второго массива и рекурсии; записи не null, их поля неизменны.

[20:100, 10:100, 30:200] → [10:100, 20:100, 30:200]
[] → []

Авторская задача · medium · O(n log n) сверху, O(1) памяти

Заготовка: PaymentHeapSort.java 
import java.util.Arrays;
import java.util.Comparator;

public class PaymentHeapSort {
    record Payment(long id, long amount) {
        @Override public String toString() { return id + ":" + amount; }
    }
    static final Comparator<Payment> ORDER = (p, q) -> {
        int byAmount = Long.compare(p.amount(), q.amount()); // не вычитаем long
        return byAmount != 0 ? byAmount : Long.compare(p.id(), q.id());
    };
    static void sort(Payment[] a) {
        throw new UnsupportedOperationException("TODO");
    }
    static void check(Payment[] input, Payment[] want) {
        sort(input);
        if (!Arrays.equals(input, want)) throw new AssertionError(Arrays.toString(input));
        System.out.println("OK " + Arrays.toString(input));
    }
    public static void main(String[] args) {
        check(new Payment[]{new Payment(20, 100), new Payment(10, 100), new Payment(30, 200)},
                new Payment[]{new Payment(10, 100), new Payment(20, 100), new Payment(30, 200)});
        check(new Payment[]{new Payment(2, Long.MAX_VALUE), new Payment(1, Long.MIN_VALUE), new Payment(3, 0)},
                new Payment[]{new Payment(1, Long.MIN_VALUE), new Payment(3, 0), new Payment(2, Long.MAX_VALUE)});
        check(new Payment[]{new Payment(9, 500)}, new Payment[]{new Payment(9, 500)});
        check(new Payment[]{}, new Payment[]{});
    }
}
Подсказка 1

Все отношения max-heap теперь задаёт ORDER.compare. Нельзя выбирать ребёнка по одному ключу, а остановку проверять по двум.

Подсказка 2

Переноси ссылки целиком, сохраняя id и amount одной записи. Границы и порядок построения те же, что для int[].

Решение

Сравниваем детей и родителя одним компаратором. В корне находится максимум по паре ключей, а не только по сумме. Обмены переставляют ссылки, новые Payment внутри сортировки не создаются.

static void sort(Payment[] a) {
    for (int root = a.length / 2 - 1; root >= 0; root--) sink(a, root, a.length);
    for (int size = a.length; size > 1;) {
        Payment t = a[0]; a[0] = a[--size]; a[size] = t; // максимум пары ключей вправо
        sink(a, 0, size);
    }
}
static void sink(Payment[] a, int root, int size) {
    while (root < size / 2) {
        int child = 2 * root + 1;
        if (child + 1 < size && ORDER.compare(a[child], a[child + 1]) < 0) child++; // больший ребёнок
        if (ORDER.compare(a[root], a[child]) >= 0) return;
        Payment t = a[root]; a[root] = a[child]; a[child] = t;
        root = child;
    }
}

Long.compare сохраняет правильный знак для крайних значений. Выражение (int) (p.amount() − q.amount()) сначала может переполнить long, затем ещё и потерять старшие биты при приведении. Размеры тестов не подтверждают сложность: её дают высота кучи и граница извлечений.

Достаточно добавить id, чтобы назвать heap sort стабильным?

Нет. Мы задали другой ключ и получили детерминированный порядок по id. Стабильность по amount требует сохранить исходную последовательность равных сумм, а она может отличаться от порядка id. Привязка к исходной позиции потребовала бы хранить эту позицию или выбрать стабильный алгоритм.
