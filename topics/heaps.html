Heaps

Очередь платежей постоянно получает новые задачи, а обработчик каждый раз выбирает самый высокий приоритет. Куча хранит для этого ровно столько порядка, сколько нужно: лучший элемент стоит в корне, а каждый родитель не хуже своих детей. Добавление и извлечение меняют один путь, а весь массив не сортируют. Поэтому куча быстро отдаёт следующую задачу, но обход её хранилища не показывает порядок выполнения.

Для следующего платежа достаточно знать лучший элемент

В сервисе накопились повторные попытки оплаты. Задачи пришли с приоритетами 50, 10 и 30; договоримся, что меньшая цифра означает более срочную работу. FIFO-очередь отдаст 50, потому что этот платёж пришёл первым. Очередь с приоритетом отдаст 10. Приход новых задач делает сортировку всего списка после каждого добавления лишней работой.

Первый фрагмент PriorityQueueDemo.java, JDK 21:

var fifo = new ArrayDeque<Integer>(List.of(50, 10, 30));
var priority = new PriorityQueue<Integer>(List.of(50, 10, 30));
System.out.println("FIFO first=" + fifo.remove() + " priority first=" + priority.poll());

FIFO first=50 priority first=10

Очередь с приоритетом — набор операций: добавить элемент, посмотреть лучший, извлечь лучший. Двоичная куча, binary heap, — способ реализовать эти операции. Она состоит из полного двоичного дерева: все уровни, кроме последнего, заполнены, последний заполняется слева направо. В min-heap значение родителя не больше значений детей; в max-heap — не меньше. Здесь дальше используем min-heap.

Из локального правила следует глобальное: по любому пути от корня значения не убывают, поэтому минимум находится в корне. Но у братьев взаимный порядок не задан. Всё правое поддерево не обязано быть больше левого: это не правило BST. Найти произвольный ключ по этому порядку нельзя, а выбрать минимум можно без обхода.

Полная форма позволяет хранить дерево в массиве без объектов-узлов и ссылок. Узлы идут по уровням. У индекса i дети 2*i + 1 и 2*i + 2, родитель при i > 0 — (i - 1)/2. Куча занимает префикс [0, size); размер выделенного массива может быть больше. Правый ребёнок существует только при индексе меньше size.

Высота полного дерева — O(log n) независимо от порядка вставки. Это даёт короткий путь перестройки. Одна только форма ещё не обеспечивает минимум: нужны отношения родителей и детей. И минимальный корень ещё не доказывает, что вся куча правильна: в [1, 9, 3, 2] нарушено ребро 9 → 2.

Добавление и извлечение исправляют один путь

Добавим приоритет 5 в готовую кучу [10, 30, 20, 70, 40, 50, 60]. Для сохранения формы новый элемент занимает последний слот, индекс 7. Его родитель 70 нарушает порядок. Меняем их местами и продолжаем сравнение с новым родителем. Этот подъём, sift-up, заканчивается на корне либо на родителе, который уже не больше добавленного значения.

Остальные поддеревья остаются правильными. Значение родителя, опущенное вниз, не нарушает порядок с прежними потомками: раньше оно было не больше всей своей ветки. Возможное нарушение движется вверх вместе с новым маленьким элементом, поэтому полный просмотр массива не нужен.

Фрагменты BinaryHeapDemo.java. Это учебная куча целых чисел с заранее выделенным массивом. При заполнении она бросает исключение. Готовая PriorityQueue расширяется; её API и ограничения разберём дальше. Метод less считает только сравнения значений, swap меняет два слота:

final int[] a;
int size;
long comparisons;
boolean trace;
Heap(int capacity) { a = new int[capacity]; }
Heap(int[] values) {
    a = Arrays.copyOf(values, Math.max(16, values.length));
    size = values.length;
    heapify();
}
boolean less(int x, int y) {
    comparisons++; // Только сравнения значений, не проверка границ.
    return a[x] < a[y];
}
void swap(int x, int y) {
    int value = a[x]; a[x] = a[y]; a[y] = value;
}

void offer(int value) {
    if (size == a.length) throw new IllegalStateException("heap is full");
    int at = size++;
    a[at] = value; // Новый элемент занимает последнее место дерева.
    if (trace) show("append");
    while (at > 0) {
        int parent = (at - 1) / 2;
        if (!less(at, parent)) break;
        swap(at, parent);
        at = parent;
        if (trace) show("up " + at);
    }
}

Фрагмент main. Конструктор из массива строит кучу методом heapify; в начальном массиве все отношения уже соблюдены. Trace печатает состояние после добавления и после каждого обмена:

var heap = new Heap(new int[]{10, 30, 20, 70, 40, 50, 60});
heap.trace = true;
heap.offer(5);

up 3: [10, 30, 20, 5, 40, 50, 60, 70] size=8
up 1: [10, 5, 20, 30, 40, 50, 60, 70] size=8
up 0: [5, 10, 20, 30, 40, 50, 60, 70] size=8

Освободившийся корень заполняет последний элемент

Извлекаем лучший приоритет 5. Удалить корень и сдвинуть массив — значит поменять отношения множества индексов. Вместо этого запоминаем результат, переносим последний элемент 70 в корень и уменьшаем size. Форма полного дерева сохранилась, дочерние поддеревья остались кучами. Нарушение теперь может быть только на пути из корня вниз.

Чтобы восстановить порядок, сравниваем детей и поднимаем меньшего. Если поднять 20 при втором ребёнке 10, корень всё ещё будет неправильным. После обмена с меньшим ребёнком верхний уровень исправлен, а 70 продолжает спуск из новой позиции. Это спуск, sift-down. Он заканчивается на листе либо когда текущий элемент уже не больше обоих детей.

int peek() {
    if (size == 0) throw new NoSuchElementException();
    return a[0];
}
int poll() {
    int result = peek();
    a[0] = a[--size]; // Последний элемент заполняет корень, последний слот покидает кучу.
    if (trace) show("replace last");
    siftDown(0);
    return result;
}
void siftDown(int at) {
    while (at < size / 2) {
        int child = 2 * at + 1;
        if (child + 1 < size && less(child + 1, child)) child++;
        if (!less(child, at)) break; // Родитель уже не больше обоих детей.
        swap(at, child);
        at = child;
        if (trace) show("down " + at);
    }
}

heap.show("before");
int first = heap.poll();
System.out.println("returned=" + first + " valid=" + heap.valid());

before: [5, 10, 20, 30, 40, 50, 60, 70] size=8
replace last: [70, 10, 20, 30, 40, 50, 60] size=7
down 1: [10, 70, 20, 30, 40, 50, 60] size=7
down 3: [10, 30, 20, 70, 40, 50, 60] size=7
returned=5 valid=true

Последний физический слот массива не исчез, но больше не входит в диапазон [0, size). В примере с int оставшееся число за этой границей не мешает. При хранении ссылок удалённый слот очищают: иначе массив продолжит удерживать извлечённый объект. PriorityQueue JDK 21 делает именно такую очистку.

Подъём и спуск проходят не больше высоты дерева: O(log n). Peek читает корень за O(1). Для нашей фиксированной ёмкости это оценки отдельных операций. В растущем массиве отдельное offer может дополнительно скопировать O(n) ссылок; при геометрическом росте эта часть оплачивается амортизированно. Сама перестройка кучи остаётся логарифмической.

Куча из готового массива строится снизу за O(n)

Если сразу пришла пачка задач, можно по одной вставить их в пустую кучу. Каждый подъём ограничен O(log n), поэтому общий верхний предел — O(n log n). Но большая часть исходного массива уже содержит готовые кучи: каждый лист является кучей из одного элемента. Начнём с их родителей и будем расширять готовые поддеревья к корню.

Последний родитель имеет индекс size/2 - 1. Спускаем его, затем предыдущий узел и так далее до 0. К моменту каждого спуска оба дочерних поддерева уже готовы. Значит, нарушение действительно может идти только по одному пути. В массиве длины 0 или 1 начальный индекс отрицательный и цикл ничего не делает.

void heapify() {
    for (int at = size / 2 - 1; at >= 0; at--) siftDown(at);
}

var steps = new Heap(7);
int[] input = {7, 6, 5, 4, 3, 2, 1};
System.arraycopy(input, 0, steps.a, 0, input.length);
steps.size = input.length;
steps.show("raw");
for (int at = steps.size / 2 - 1; at >= 0; at--) {
    steps.siftDown(at);
    steps.show("root " + at);
}
System.out.println("valid=" + steps.valid() + " min=" + steps.peek());

raw: [7, 6, 5, 4, 3, 2, 1] size=7
root 2: [7, 6, 1, 4, 3, 2, 5] size=7
root 1: [7, 3, 1, 4, 6, 2, 5] size=7
root 0: [1, 3, 2, 4, 6, 7, 5] size=7
valid=true min=1

Ни один промежуточный массив не отсортирован; последний тоже содержит 3 перед 2. Для кучи это нормально. Финальное valid проверяет отношения каждого родителя и ребёнка, а peek возвращает 1. Чтобы получить весь порядок, придётся последовательно извлечь элементы или отдельно отсортировать копию.

Логарифмический спуск есть только у небольшого числа узлов

Неверно умножать n на максимальную высоту каждого узла. Примерно половина узлов — листья, им некуда спускаться. Около четверти находятся на один уровень выше листьев, около восьмой части — на два. При высоте поддерева h число таких узлов имеет порядок n/2ʰ⁺¹. Общая работа ограничена суммой n * (1/4 + 2/8 + 3/16 + …), а ряд сходится к константе. Поэтому bottom-up heapify работает за O(n).

Посчитаем реальные сравнения той же реализации на 1023 числах в убывающем порядке. При последовательных вставках каждый новый минимум поднимается до корня; при построении снизу длинные спуски нужны лишь верхним узлам. Счётчик не измеряет время JVM:

int n = 1023;
int[] descending = new int[n];
for (int i = 0; i < n; i++) descending[i] = n - i;
var bottomUp = new Heap(descending);
var repeated = new Heap(n);
for (int value : descending) repeated.offer(value);
System.out.println("heapify n=" + n + " comparisons=" + bottomUp.comparisons
        + " valid=" + bottomUp.valid() + " min=" + bottomUp.peek());
System.out.println("offers n=" + n + " comparisons=" + repeated.comparisons
        + " valid=" + repeated.valid() + " min=" + repeated.peek());
var drained = new ArrayList<Integer>();
while (steps.size > 0) drained.add(steps.poll());
System.out.println("poll order=" + drained);

heapify n=1023 comparisons=2026 valid=true min=1
offers n=1023 comparisons=8194 valid=true min=1
poll order=[1, 2, 3, 4, 5, 6, 7]

2026 и 8194 — результат конкретного входа и нашего метода обменов, а не универсальные коэффициенты. Они подтверждают, где выполняется работа. Извлечение всех семи элементов после heapify дало отсортированный порядок, но стоило серии poll. Построение кучи за O(n) не делает сортировку линейной; Heap Sort использует последующие перестройки и работает за O(n log n).

Под капотом: какой конструктор PriorityQueue использует heapify

В JDK 21 конструктор из обычной Collection переносит её элементы в массив и вызывает heapify. Из SortedSet или другой PriorityQueue он использует сведения о готовом порядке и компараторе. Напротив, addAll в уже созданную очередь добавляет элементы через отдельные add/offer. Эти способы загрузки не следует считать одним и тем же алгоритмом.

У конструктора из обычной коллекции нет параметра Comparator: для произвольного списка нужен естественный порядок элементов. Если требуется свой компаратор, можно создать очередь с ним и добавить элементы, но это уже последовательные вставки. Линейное построение конкретного массива с произвольным правилом требует реализации, которая явно поддерживает такой вход.

PriorityQueue упорядочивает извлечение, а не обход

PriorityQueue в Java реализует очередь с приоритетом на массивной двоичной куче. По умолчанию меньший элемент по Comparable становится первым; переданный Comparator определяет собственное правило. Для max-очереди можно использовать обратный компаратор. Сравнение должно быть согласованным и транзитивным: вычитание двух int вместо Integer.compare опасно переполнением.

Обход Iterator, копирование через toArray и stream не выполняют серию poll. Они получают элементы без обещанного приоритетного порядка. На JDK 21 в следующем запуске виден порядок внутреннего массива; полагаться на него в приложении нельзя. Метод drain здесь по очереди извлекает элементы до пустоты:

static <T> List<T> drain(PriorityQueue<T> queue) {
    var result = new ArrayList<T>();
    while (!queue.isEmpty()) result.add(queue.poll());
    return result;
}

var queue = new PriorityQueue<Integer>();
for (int value : new int[]{10, 30, 20, 70, 40, 50, 60}) queue.offer(value);
System.out.println("iteration=" + new ArrayList<>(queue)); // Обход, не последовательность poll.
System.out.println("peek=" + queue.peek() + " size=" + queue.size());
System.out.println("polls=" + drain(queue));
System.out.println("empty peek=" + queue.peek() + " poll=" + queue.poll());

iteration=[10, 30, 20, 70, 40, 50, 60]
peek=10 size=7
polls=[10, 20, 30, 40, 50, 60, 70]
empty peek=null poll=null

Peek не удалил 10: размер остался 7. Последовательность poll уже отсортирована, но сама очередь в результате опустела. Для отчёта, который должен оставить очередь рабочей, скопируй элементы и отсортируй копию тем же компаратором. Полная выдача требует O(n log n), а не постоянного чтения всего порядка.

Равные приоритеты сохраняют все задачи

Пусть A, B и C одинаково срочны. Нулевой результат сравнения не объединяет их в один элемент: PriorityQueue хранит все добавления, включая повторное добавление того же объекта. Но порядок между равными приоритетами произвольный. Если требуется FIFO внутри одной срочности, добавь последовательный номер поступления как второй критерий.

record Job(String id, int priority, long sequence) {
    @Override public String toString() { return id; }
}

Comparator<Job> byPriority = Comparator.comparingInt(Job::priority);
var jobs = List.of(new Job("A", 1, 0), new Job("B", 1, 1), new Job("C", 1, 2));
var ties = new PriorityQueue<>(byPriority);
ties.addAll(jobs);
System.out.println("size=" + ties.size() + " compare A,B=" + byPriority.compare(jobs.get(0), jobs.get(1)));
System.out.println("priority only=" + drain(ties)); // Точный порядок — наблюдение JDK 21.
var stable = new PriorityQueue<>(byPriority.thenComparingLong(Job::sequence));
stable.addAll(jobs);
System.out.println("priority+sequence=" + drain(stable));

size=3 compare A,B=0
priority only=[A, C, B]
priority+sequence=[A, B, C]

Порядок A, C, B — конкретное наблюдение JDK 21. После извлечения A последний C заполнил корень; при равенстве с B перестановка не понадобилась. Это объясняет результат, но не задаёт гарантию выбора равных элементов. Второй компаратор различает задачи по sequence и явно задаёт A, B, C. В нескольких потоках порядок назначения номеров и приёма задач надо согласовать отдельно.

Равенство при удалении отличается от равенства при сравнении

Contains и remove(Object) ищут элемент через equals. В нашем record B отличается от A полями id и sequence, хотя приоритет одинаковый. Поэтому удалить B из очереди с одним A не получилось. Это отличается от TreeSet, где compare == 0 определяет один элемент.

var sameRank = new PriorityQueue<>(byPriority);
sameRank.add(jobs.get(0));
System.out.println("contains B=" + sameRank.contains(jobs.get(1))
        + " remove B=" + sameRank.remove(jobs.get(1)));
sameRank.add(jobs.get(0)); // Дубликаты допустимы, это не TreeSet.
System.out.println("same object twice size=" + sameRank.size());
var small = new PriorityQueue<Integer>(1); // Начальный резерв, а не верхний предел.
for (int value = 0; value < 20; value++) small.offer(value);
System.out.println("initialCapacity=1 size=" + small.size());
try {
    small.offer(null);
} catch (NullPointerException error) {
    System.out.println("null=" + error.getClass().getSimpleName());
}

contains B=false remove B=false
same object twice size=2
initialCapacity=1 size=20
null=NullPointerException

Начальная ёмкость 1 не ограничила очередь: она приняла 20 элементов. Null запрещён, поэтому null из peek или poll однозначно означает пустоту. Element и remove без аргумента на пустоте бросают NoSuchElementException; remove(Object) означает совсем другую операцию — поиск и удаление совпадения.

Под капотом: удалённая середина может потребовать подъёма

При remove(Object) найденный слот заполняет последний элемент. Он может оказаться и слишком большим для детей, и слишком маленьким для нового родителя. В JDK 21 removeAt сначала пробует siftDown, а если элемент остался на месте — siftUp. В нашем poll хватает спуска, потому что новый элемент поставлен именно в корень и родителя у него нет.

Изменение приоритета требует новой перестройки

Сервис повысил срочность уже ожидающего платежа C. Объект тот же, поле изменилось, но массив кучи и ссылки внутри него остались на месте. PriorityQueue не наблюдает изменения объектов и не вызывает sift-up сама. Даже peek теперь способен вернуть элемент, который по текущему компаратору уже не лучший.

В MutablePriorityDemo.java три задачи сначала имеют приоритеты A:5, B:10 и C:20. После изменения C:1 код сравнивает сломанный вариант с удалением перед изменением и повторной вставкой:

static final class Job {
    final String id;
    int priority;
    Job(String id, int priority) { this.id = id; this.priority = priority; }
    @Override public String toString() { return id + ":" + priority; }
}

Comparator<Job> byPriority = Comparator.comparingInt(job -> job.priority);
var a = new Job("A", 5);
var b = new Job("B", 10);
var c = new Job("C", 20);
var broken = new PriorityQueue<>(byPriority);
broken.addAll(List.of(a, b, c));
c.priority = 1; // Ссылки и массив остались на прежних местах.
System.out.println("changed C: peek=" + broken.peek());
System.out.println("broken polls=" + drain(broken));

c.priority = 20;
var fixed = new PriorityQueue<>(byPriority);
fixed.addAll(List.of(a, b, c));
fixed.remove(c); // Ищет по equals за O(n); Job здесь использует равенство ссылок.
c.priority = 1; // Значимое поле меняем уже вне очереди.
fixed.offer(c); // Вставка восстановит путь до корня.
System.out.println("reinserted C: peek=" + fixed.peek());
System.out.println("fixed polls=" + drain(fixed));

changed C: peek=A:5
broken polls=[A:5, C:1, B:10]
reinserted C: peek=C:1
fixed polls=[C:1, A:5, B:10]

В сломанной очереди первой всё ещё вышла A:5. Лишь очередной poll перестроил часть пути и поднял C:1. Это не способ обновления: сколько элементов выйдет раньше, зависит от прежней структуры. Правильный вариант вынул C до изменения, затем вставил с новым значением. В прикладном коде удобно хранить неизменяемые записи: старую вынуть, новую вставить.

Remove(Object) сначала ищет задачу за O(n), поэтому массовые изменения приоритетов способны стать узким местом. Отдельный индекс позиции в собственной куче решает другую задачу: найти узел по id за ожидаемое O(1), затем поднять или опустить за O(log n). После каждого обмена индекс позиций нужно обновлять вместе с массивом. Стандартная PriorityQueue такого decrease-key API не даёт.

Под капотом: обновление через версии без поиска старой записи

Можно хранить неизменяемые записи с id, приоритетом и версией. При обновлении добавлять новую запись и сохранять её версию в отдельной таблице. После poll сравнивать версию с актуальной: устаревшую запись пропускать. Так обновление обходится без линейного remove, но в куче накапливаются старые записи. Нужны ограничение накопления и очистка; задержка одного извлечения также может включать пропуск многих устаревших элементов.

Чтобы сохранить три наибольшие суммы, держим минимальную кучу

Куча полезна и без очереди обработчика. Для трёх наибольших сумм потока храним только три кандидата. Корень должен быть наименьшим из сохранённых, то есть границей отбора. Пока мест меньше k, добавляем сумму. Затем новое значение выше границы вытесняет корень; остальные значения пропускаем. Для k > 0 это O(n log k) времени и O(k) памяти; результат ещё нужно упорядочить отдельно.

int k = 3;
var largest = new PriorityQueue<Integer>(); // Корень — худшая из сохранённых сумм.
for (int amount : new int[]{40, 10, 70, 20, 60, 90, 50}) {
    if (largest.size() < k) largest.offer(amount);
    else if (amount > largest.peek()) {
        largest.poll();
        largest.offer(amount);
    }
    System.out.println("amount=" + amount + " kept=" + largest + " cutoff=" + largest.peek());
}
var result = new ArrayList<>(largest);
result.sort(Comparator.reverseOrder()); // Вывод трёх сумм отдельно сортируем.
System.out.println("top3 descending=" + result);

amount=40 kept=[40] cutoff=40
amount=10 kept=[10, 40] cutoff=10
amount=70 kept=[10, 40, 70] cutoff=10
amount=20 kept=[20, 70, 40] cutoff=20
amount=60 kept=[40, 70, 60] cutoff=40
amount=90 kept=[60, 70, 90] cutoff=60
amount=50 kept=[60, 70, 90] cutoff=60
top3 descending=[90, 70, 60]

Сумма 50 не прошла границу 60. При этом массив [20, 70, 40] в промежуточном выводе был правильной кучей, хотя не отсортирован. Для задачи с k наибольшими нужна min-heap; max-heap на k местах дала бы быстрый доступ к лучшему, а нам нужен именно худший сохранённый. Полные задачи с крайними случаями — в Heap & Top-K.

Куча не обещает справедливость: постоянный поток срочных платежей способен надолго задержать обычные. Политика приоритетов должна учитывать это требование. И приоритет не означает время готовности: очередь с ключом deadline отдаёт ближайший элемент сразу, а не ждёт наступления срока. Ожидание времени — отдельный механизм.

Наблюдай не только size, но и возраст старейшей ожидающей задачи по каждому приоритету. Общая очередь может выглядеть небольшой, пока несколько обычных платежей ждут слишком долго. Если CPU тратится на Comparator, проверь цену вычисления приоритета: заранее подготовленное неизменяемое число дешевле расчёта по большому объекту при каждом сравнении.

PriorityQueue предназначена для последовательного доступа либо внешней координации. PriorityBlockingQueue добавляет согласование потоков и ожидание при пустоте, но тоже не задаёт верхний предел размера. Если платежи поступают быстрее обработки, нужен явный предел накопления и решение об отказе или переносе работы. Долговечность задач после падения процесса также решается хранилищем. Эти вопросы продолжаются в Concurrent Collections и темах о сообщениях.

Для диапазонов по ключу лучше дерево поиска. Для одной фиксированной пачки, которую целиком нужно выдать по порядку, обычно проще сортировать. Куча выигрывает, когда набор меняется, а из него постоянно нужен следующий экстремум: приоритетная обработка, верхние k значений, слияние упорядоченных потоков и выбор ближайшей вершины в алгоритмах графов.

  • Полная форма даёт массивное представление и логарифмическую высоту. Порядок на рёбрах даёт лучший элемент в корне.
  • Вставка поднимает последний элемент. Извлечение заменяет корень последним и спускает через лучшего ребёнка.
  • Heapify строит готовые поддеревья снизу и стоит O(n); длинный спуск нужен немногим узлам.
  • PriorityQueue упорядочивает poll, сохраняет дубликаты и не обещает FIFO для равных приоритетов.
  • Мутация значимых полей не перестраивает кучу. Ограничение размера, потоки и сохранение задач требуют отдельных решений.

На собеседовании

Как устроена двоичная куча? Почему вставка и извлечение O(log n)?

Куча — полное двоичное дерево с порядком между родителем и детьми. В min-heap родитель не больше детей, поэтому минимум в корне. Дерево можно хранить в массиве по уровням: дети i имеют индексы 2i+1 и 2i+2, родитель — (i−1)/2.

При вставке дописываю элемент в конец и поднимаю через родителей. При извлечении запоминаю корень, ставлю туда последний элемент и спускаю через меньшего ребёнка. Оба изменения сохраняют полную форму и исправляют один путь. Его длина O(log n), а peek просто читает корень за O(1).

  • Лучший корень — только следствие инварианта. Если нарушено отношение ниже, последующее извлечение может вернуть неверный результат. Проверка относится к каждому ребру.
  • У братьев нет взаимного порядка, поэтому найти произвольный ключ бинарным поиском нельзя. Куча решает выбор экстремума, BST — навигацию по упорядоченным диапазонам.
  • Рост массива может сделать отдельную вставку линейной из-за копирования. Логарифм относится к перестройке, а расходы на геометрическое расширение амортизируются отдельно.

Почему heapify работает за O(n), а не за O(n log n)?

Я начинаю с последнего родителя и делаю sift-down до корня. Листья уже являются кучами из одного элемента. Когда обрабатывается узел, его дочерние поддеревья готовы, поэтому можно исправить только путь этого узла вниз.

Большинство узлов стоят близко к листьям и спускаются совсем недалеко. Примерно половина не делает спуск, четверть проходит один уровень, восьмая часть — два. Сумма таких расходов линейна. При вставках по одной каждый новый минимум может подниматься до корня, и общий худший предел получается O(n log n).

  • Последний родитель при индексах с нуля — n/2−1. При n=0 или n=1 цикл не начинается. Правого ребёнка может не быть, поэтому его наличие проверяется отдельно.
  • Линейное построение кучи не сортирует массив. Выдача всех n значений через poll всё ещё выполняет O(n log n) работы.
  • Конструктор PriorityQueue из обычной Collection в JDK 21 использует heapify; addAll в существующую очередь идёт через отдельные вставки. У готовой отсортированной коллекции или другой очереди конструктор может использовать их порядок.

Почему PriorityQueue выдаёт странный порядок? Можно ли изменить приоритет элемента?

Сначала уточню, речь об обходе или poll. Итератор не обещает приоритетного порядка; правильный порядок даёт последовательное извлечение. Равные приоритеты выходят произвольно, поэтому для FIFO внутри одного приоритета добавлю номер поступления в компаратор.

Значимые поля элемента нельзя просто изменить внутри очереди: куча не переместит объект сама. Нужно удалить его до изменения и добавить заново либо хранить неизменяемые записи и управлять версиями. Remove(Object) ищет по equals за O(n), поэтому частые изменения требуют другой организации.

  • Нулевое сравнение в PriorityQueue не удаляет дубликаты. Contains и remove(Object) используют equals; сравнение определяет приоритет, а не идентичность всех элементов.
  • При удалении произвольного слота последний элемент может потребовать и подъёма, и спуска. При poll достаточно спуска, потому что у корня нет родителя.
  • Ленивое обновление через версии добавляет устаревшие записи и расходы на их пропуск. Индексированная куча вместо этого поддерживает соответствие id → позиция при каждом обмене.
Разработчик поставил initialCapacity=1000 и считает очередь платежей ограниченной. Что произойдёт на пике?

PriorityQueue продолжит расширять массив. Начальная ёмкость — резерв памяти, а не предел числа задач. Нужен явный предел накопления и решение при достижении: остановить приём, отказать или сохранить работу вне памяти. Замена на PriorityBlockingQueue сама по себе этого не исправит: она также не ограничена размером.
