HTTP Cache & CDN

HTTP-кеш живёт вне приложения: в браузере, в обратном прокси, в CDN. Чем и как долго кешировать, решает сервер заголовком Cache-Control. max-age задаёт, сколько ответ свежий; после этого кеш спрашивает origin с If-None-Match и при неизменном ETag получает 304 без тела. private запрещает общим кешам хранить персональный ответ, no-store — хранить вообще, а no-cache разрешает хранить, но требует проверки перед каждым использованием. Vary добавляет заголовки запроса в ключ кеша. CDN — распределённый общий кеш; изменения доставляют версионированными URL или очисткой.

CDN показал одному клиенту профиль другого, а новый тариф полчаса не доходил до мобильного приложения

Команда поставила CDN перед API, чтобы снять нагрузку со справочников. Через день пришла жалоба: пользователь открыл «Мой профиль» и увидел чужое имя. Ответ /me не имел Cache-Control, CDN по своим правилам закешировал его, а ключ кеша — только адрес, без пользователя. В тот же день бизнес поменял тариф, и мобильное приложение ещё полчаса показывало старый: ответ был закеширован на полчаса, и CDN честно отдавал его до истечения.

Тема разбирает HTTP-кеширование с точки зрения бэкенда: что означают директивы, как общий кеш выбирает между HIT, ревалидацией и запросом к origin, чем опасны персональные ответы и как CDN доставляет изменения. Семантика методов и базовый механизм ETag и 304 — в HTTP, кеширование данных в приложении — в Caching Strategies. Демо HttpCacheDemo.java поднимает origin на JDK, а перед ним в Docker стоит nginx 1.31 с proxy_cache в роли CDN; заголовок X-Cache показывает решение кеша.

Cache-Control говорит кешам, кто может хранить ответ и как долго он свежий

ДирективаСмысл
max-age=60Ответ свежий 60 секунд; в это время кеш отдаёт его без обращения к origin
s-maxage=300То же, но только для общих кешей (CDN, прокси); перекрывает max-age для них
public / privateМожно хранить в общих кешах / только в кеше браузера одного пользователя
no-cacheХранить можно, но перед каждым использованием проверять у origin
no-storeНе хранить нигде: для чувствительных данных
must-revalidateПосле истечения нельзя отдавать устаревшее, даже если origin недоступен
stale-while-revalidate=3030 секунд после истечения можно отдавать старое, обновляя в фоне
immutableОтвет не изменится никогда: браузер не проверяет его даже при перезагрузке

Частая путаница — no-cache и no-store. no-cache не запрещает кеширование, а запрещает отдавать без проверки: с ETag это дешёвые 304 вместо полных ответов. Запрет хранения — только no-store. И отсутствие Cache-Control не означает «не кешировать»: если в ответе есть Last-Modified, кеши вправе вычислить свежесть эвристически, обычно как десятую часть возраста документа. Поэтому у каждого ответа API заголовок кеширования должен быть явным.

Общий кеш отдаёт свежее сам, а истёкшее проверяет у origin по ETag

Origin отдаёт тарифы с Cache-Control: public, max-age=3 и ETag версии. Демо делает запросы через nginx, ждёт истечения и меняет версию тарифа:

== public, max-age=3
GET /tariffs              -> 200 MISS        tariff v1
GET /tariffs              -> 200 HIT         tariff v1
GET /tariffs              -> 200 REVALIDATED tariff v1
GET /tariffs              -> 200 HIT         tariff v1
GET /tariffs              -> 200 EXPIRED     tariff v2

Первый запрос — MISS: кеш пуст и сходил в origin. Второй — HIT без обращения к origin. Третий пришёл после истечения: nginx отправил origin условный запрос с If-None-Match, получил 304 без тела и снова считает ответ свежим на 3 секунды. Затем тариф сменился на v2, но четвёртый запрос всё равно получил v1 — ответ свежий, и кеш об изменении не спрашивает. Это ситуация с мобильным приложением, только с max-age в 30 минут. Пятый пришёл после истечения, ETag уже другой, и origin отдал новое тело. Всего три обращения к origin на пять запросов.

Персональный ответ без private может попасть в общий кеш и уйти другому пользователю

== private, max-age=60
GET /me      (user anna)  -> 200 MISS        profile of anna
GET /me      (user boris) -> 200 MISS        profile of boris

С private nginx не сохранил ответ: каждый пользователь получил свой профиль от origin. Ключ общего кеша по умолчанию — метод и URL; ни Authorization, ни cookie, ни кастомный заголовок пользователя в него не входят. Если бы /me пришёл с public, max-age=60, Борис получил бы профиль Анны. По стандарту общий кеш не хранит ответы на запросы с Authorization, если ответ явно не разрешает, но аутентификация cookie или своим заголовком такой защиты не даёт.

Персональные ответы помечают private или no-store, а данные, которые нельзя оставлять даже в браузере на общем компьютере, — no-store. Отдельная атака — web cache deception: CDN настроен кешировать всё, что выглядит как статика (*.css), а приложение отвечает на /me/profile.css профилем пользователя. Защита — кешировать по явным заголовкам origin, а не по расширению в адресе.

Vary добавляет заголовки запроса в ключ кеша

== Vary: Accept-Language
GET /terms   (ru)         -> 200 MISS        terms in ru
GET /terms   (en)         -> 200 MISS        terms in en
GET /terms   (ru)         -> 200 HIT         terms in ru

Условия обслуживания зависят от языка, и origin отвечает Vary: Accept-Language. Кеш хранит отдельную копию на каждое значение заголовка: русская и английская версии — разные записи, и повторный русский запрос получил HIT. Без Vary первый пришедший язык достался бы всем. Цена — дробление кеша: Vary: Accept-Language при сотнях вариантов строк вида ru-RU,ru;q=0.9,en;q=0.8 почти обнуляет попадания, поэтому CDN нормализуют заголовок до нескольких значений. Vary: Cookie или Vary: * делают ответ практически некешируемым в общем кеше.

CDN доставляет изменения через версии в URL, очистку или stale-while-revalidate

CDN — сеть общих кешей близко к пользователям. В модели pull узел CDN при промахе сам забирает ответ у origin и кеширует по его заголовкам; в модели push контент заранее загружают в CDN, и origin в обслуживании не участвует. Для API почти всегда pull, для больших файлов и релизов — бывает push.

Изменения доставляют тремя способами. Версионированные URL — app.3f9a1c.js или /v2/tariffs?rev=42: содержимое по адресу не меняется никогда, ему ставят max-age=31536000, immutable, а новая версия — новый адрес. Очистка (purge) по API CDN удаляет конкретные адреса или теги; она асинхронна и занимает секунды на сотнях узлов. И короткий max-age со stale-while-revalidate, когда устарелость в секунды допустима, а ожидание — нет:

== stale-while-revalidate=30, max-age=1
GET /rates                -> 200 MISS        rates 958
GET /rates                -> 200 STALE       rates 958
GET /rates                -> 200 HIT         rates 583

После истечения max-age=1 кеш сразу отдал старый ответ (STALE) и параллельно обновил его у origin; следующий запрос получил уже новое значение. Клиент не ждал origin ни разу, а origin получил один запрос на обновление, а не по запросу на клиента. Похожая директива stale-if-error разрешает отдавать устаревшее, если origin отвечает ошибкой, — CDN продолжает обслуживать справочники, пока origin лежит.

Cache-Control: no-cache запрещает кешировать ответ.

no-cache разрешает хранить ответ, но требует проверять его у origin перед каждым использованием; с ETag это 304 без тела. Запрещает хранение только no-store. А ответ вовсе без Cache-Control кеши вправе закешировать эвристически.

  • max-age — допустимая устарелость: в демо кеш отдавал v1, когда в origin уже был v2.
  • После истечения кеш спрашивает origin с If-None-Match: 304 без тела продлевает свежесть.
  • private и no-store для персональных ответов: ключ общего кеша — только метод и URL.
  • Vary разделяет варианты, но дробит кеш; Vary: Cookie делает ответ почти некешируемым.
  • CDN: версионированные URL с immutable, purge по API, stale-while-revalidate и stale-if-error.

На собеседовании

Чем no-cache отличается от no-store, а private от public?

no-store запрещает хранить ответ где-либо. no-cache разрешает хранить, но перед каждым использованием кеш проверяет ответ у origin условным запросом; при неизменном ETag приходит 304 без тела. private разрешает хранить только в кеше одного пользователя — браузере, public — и в общих кешах: прокси, CDN.

  • s-maxage задаёт срок только для общих кешей.
  • Без Cache-Control кеши могут вычислить свежесть эвристически по Last-Modified.
  • must-revalidate запрещает отдавать устаревшее при недоступном origin; stale-if-error — наоборот, разрешает.

Как CDN может отдать чужие данные и как это предотвратить?

Ключ общего кеша по умолчанию — метод и URL, без cookie и пользовательских заголовков. Если персональный ответ закешировать как public или CDN кеширует по своим правилам, следующий пользователь по тому же адресу получит чужой ответ. Персональные ответы помечают private или no-store, а CDN настраивают уважать заголовки origin.

  • Web cache deception: CDN кеширует по расширению, а приложение отдаёт профиль на /me/x.css.
  • Ответы на запросы с Authorization общий кеш не хранит без явного разрешения, но cookie-аутентификацию это не защищает.
Что не так с заголовками этих ответов? 
GET /api/me              → Cache-Control: public, max-age=300
GET /api/tariffs         → (без Cache-Control), Last-Modified: ...
GET /static/app.js       → Cache-Control: max-age=31536000

Профиль помечен public: CDN закеширует его по URL и отдаст другим пользователям; нужен private или no-store. Тарифы без Cache-Control кеши закешируют эвристически на непредсказуемое время; нужен явный max-age по допустимой устарелости. app.js на год без версии в имени: после релиза пользователи год получают старый скрипт; нужен отпечаток в имени файла и immutable.

Как обновить контент, закешированный в CDN?

Лучше всего — версионированные URL: статика с хешем содержимого в имени кешируется навсегда с immutable, а новая версия получает новый адрес. Для остального — purge через API CDN по адресу или тегу и разумный max-age. Если устарелость в секунды допустима, stale-while-revalidate позволяет отдавать старое и обновлять в фоне.

  • Purge асинхронный и распространяется по узлам секунды; на него не полагаются для мгновенной согласованности.
  • Pull CDN забирает у origin при промахе, push — заранее загруженный контент.
  • RFC 9111: HTTP Caching — основа урока: свежесть, ревалидация, директивы, общие кеши и Authorization.
  • RFC 5861: stale-while-revalidate и stale-if-error.
  • MDN: HTTP caching — практическое руководство.
  • nginx: proxy_cache — настройки кеша из демо.
