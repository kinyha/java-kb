Networking: HTTP

HTTP — договор не только между клиентом и сервером, но и со всеми, кто стоит между ними: прокси, CDN, балансировщиками, библиотеками клиентов. Метод говорит им, можно ли запрос повторить и закешировать. Код ответа — кто виноват и стоит ли пробовать снова. Заголовки управляют кешем, условными запросами и cookies. Если API нарушает этот договор — меняет данные в GET или отвечает 200 на ошибку, — посредники делают правильные по стандарту, но разрушительные вещи: повторяют платёж, кешируют ошибку, теряют тело запроса на редиректе.

Между клиентом и API стоят посредники, и они читают метод и коды

Запрос мобильного приложения к платёжному API проходит через HTTP-клиент с повторами, CDN, балансировщик и ingress. Каждый из них принимает решения по правилам HTTP: можно ли повторить запрос при обрыве, можно ли отдать ответ из кеша, куда пойти по редиректу. Платёжный API, который не следует этим правилам, получает дубли платежей и устаревшие данные, хотя сам код сервера верный.

Демо HttpDemo.java поднимает на loopback встроенный в JDK HttpServer и вызывает его стандартным java.net.http.HttpClient: java HttpDemo.java на JDK 21. Каждый опыт показывает правило, которое клиент или посредник выполняет без участия твоего кода. Семантика HTTP описана в RFC 9110; формат сообщения HTTP/1.1 — в RFC 9112.

Метод обещает посредникам, безопасен ли запрос и можно ли его повторить

HTTP/1.1-сообщение — текст: стартовая строка, заголовки, пустая строка и тело. Как это выглядит в байтах, показано в How a Request Travels. Тело отделяется по Content-Length или кусками Transfer-Encoding: chunked, когда размер заранее неизвестен.

Главная часть стартовой строки — метод. Стандарт приписывает методам три свойства. Безопасный — клиент не просит ничего менять: такой запрос можно сделать заранее, например, при предзагрузке. Идемпотентный — повтор того же запроса даёт тот же эффект на сервере, что и один. Кешируемый — ответ можно сохранить и отдать повторно.

МетодБезопасныйИдемпотентныйПлатёжный API

OPTIONSдадаPreflight CORS, разрешённые методы

Идемпотентность говорит об эффекте, а не об ответе. Первый DELETE /drafts/17 вернёт 204, второй — 404, но состояние сервера после обоих одинаковое: черновика нет. PATCH не идемпотентен в общем случае: «увеличить лимит на 1000» дважды даёт другой результат, а «установить лимит 5000» — тот же.

Эти свойства — обещание посредникам, а не проверка. Если GET меняет данные (GET /payments/17/confirm), браузер может выполнить его при предзагрузке ссылки, краулер — при обходе сайта, прокси — повторить при обрыве. Всё по правилам, и каждый раз подтверждая платёж.

POST не идемпотентен, и повтор после таймаута создаёт второй платёж

Клиент отправил POST создания платежа, сервер его провёл, а ответ потерялся: таймаут, обрыв соединения. Клиент не знает, прошёл ли платёж, и повторяет. Для POST сервер не может отличить повтор от нового платежа на ту же сумму:

for (int attempt = 1; attempt <= 2; attempt++) {      // Второй раз — «повтор после таймаута».
    var b = HttpRequest.newBuilder(URI.create(base + "/payments"))
            .POST(HttpRequest.BodyPublishers.ofString("{\"cents\":500}"));
    if (key != null) b.header("Idempotency-Key", key); // Один ключ на одну операцию.
    client.send(b.build(), ofString());
}
no key, attempt 1 -> 201 p-101
no key, attempt 2 -> 201 p-102
payments created: 2
key 7f3c-01, attempt 1 -> 201 p-101
key 7f3c-01, attempt 2 -> 200 p-101 (replayed)
payments created: 1

Ключ создаёт клиент — на операцию, а не на попытку. Сервер хранит ключ вместе с результатом и проверяет, что повтор пришёл с тем же телом, иначе это ошибка клиента. Ключ и сам платёж пишутся в одной транзакции, а два одновременных запроса с одним ключом не должны оба пройти проверку «ключа ещё нет» — нужен уникальный индекс. Заголовок Idempotency-Key описан в черновике стандарта IETF и используется Stripe, Adyen и многими банковскими API. Подробно схема разобрана в Idempotency.

Код ответа говорит, кто виноват и стоит ли пробовать снова

Клиенты, балансировщики и мониторинг принимают решения по классу кода. 2xx — успех, 3xx — иди в другое место, 4xx — ошибка клиента, повтор того же запроса не поможет, 5xx — ошибка на стороне сервера, повтор может помочь. API, который возвращает 200 {"error": "insufficient funds"}, ломает всё сразу: кеш сохраняет ошибку, метрики не видят отказов, клиентская библиотека не бросает исключение.

ПараРазличие
400 и 422400 — запрос не разобран: битый JSON, неверный тип. 422 — разобран, но нарушает правила: сумма отрицательная
401 и 403401 — неизвестно, кто ты: нет или неверный токен. 403 — известно, но нельзя
404 и 410404 — нет такого ресурса. 410 — был и удалён навсегда
409 и 412409 — конфликт с текущим состоянием: платёж уже отменён. 412 — не выполнилось условие If-Match
429Слишком много запросов; Retry-After говорит, когда пробовать снова
500, 502, 503, 504500 — упал сам сервер. 502 — прокси получил плохой ответ от backend. 503 — сервис временно не принимает. 504 — прокси не дождался backend

Для повторов главное различие — выполнилась ли операция. 503 с Retry-After и 429 означают «запрос не обработан, приходи позже». 504 опаснее: прокси не дождался backend, но backend мог успеть провести платёж. Повторять POST после 504 можно только с ключом идемпотентности. 502 и 504 говорят, что ответил прокси, а не приложение: искать причину надо в связи прокси с backend. Формат тела ошибок для API стандартизирован в RFC 9457 (Problem Details), который Spring поддерживает через ProblemDetail — разобрано в Validation & Errors.

Редирект 302 превращает POST в GET и теряет тело

Адрес платёжного API переехал, и старый путь отвечает редиректом. Клиент следует за ним автоматически. Что он отправит по новому адресу, зависит от кода:

var client = HttpClient.newBuilder().followRedirects(HttpClient.Redirect.NORMAL).build();
// /old-pay-302 и /old-pay-307 отвечают редиректом на /pay.
client.send(HttpRequest.newBuilder(URI.create(base + path))
        .POST(HttpRequest.BodyPublishers.ofString("{\"cents\":500}")).build(), ofString());
POST /old-pay-302 -> 200 pay got GET body=
POST /old-pay-307 -> 200 pay got POST body={"cents":500}

После 302 клиент пошёл на новый адрес методом GET и без тела, а ответ всё равно 200: сервер просто показал «что-то» по GET. Так исторически делали браузеры, и стандарт разрешил это поведение для 301 и 302. Коды 307 и 308 появились, чтобы сказать явно: повтори тот же метод с тем же телом. 303 — наоборот, явное «теперь сделай GET», его используют после POST формы.

ВременныйПостоянный
Метод может смениться на GET302301
Метод и тело сохраняются307308

Для API это значит: переносить эндпоинты, принимающие POST, только через 307 или 308, а лучше не полагаться на редиректы в API вовсе. Типичная ловушка — редирект с http на https на балансировщике кодом 301: браузер его переживёт, а платёжный POST клиента, по ошибке настроенного на http, молча превратится в GET.

ETag позволяет не пересылать неизменившийся ответ и не перезаписать чужое изменение

Тариф банка меняется раз в день, а запрашивают его тысячи раз. Cache-Control: max-age=60 разрешает клиенту и CDN минуту отдавать сохранённый ответ без запроса. После этого клиент может спросить, изменился ли ресурс, передав его версию — ETag — в условном запросе:

var first = client.send(get("/tariff"), ofString());
String etag = first.headers().firstValue("ETag").orElseThrow();
var again = client.send(get("/tariff").header("If-None-Match", etag).build(), ofString()); // «Если не изменился».
GET /tariff -> 200, ETag "tariff-v42", body 57 bytes
GET /tariff If-None-Match -> 304, body 0 bytes

Ответ 304 Not Modified идёт без тела: клиент берёт сохранённую копию. Экономия — трафик и время сервера на сборку ответа, но не круг до сервера. Для ответов с персональными данными ставят Cache-Control: private или no-store, иначе общий кеш CDN отдаст счёт одного клиента другому. no-cache не запрещает кеширование, а требует проверять копию у сервера перед каждым использованием.

Тот же ETag защищает от потерянных обновлений. Клиент прочитал настройки магазина с ETag "v7", изменил и отправил PUT с If-Match: "v7". Если за это время настройки поменял кто-то другой, сервер ответит 412 Precondition Failed вместо того, чтобы молча перезаписать чужое изменение. Это оптимистичная блокировка на уровне HTTP, та же идея, что @Version в Locking & Caching.

Атрибуты cookie решают, куда браузер её отправит

HTTP не хранит состояние между запросами. Сессию держат cookies: сервер отдаёт Set-Cookie, клиент возвращает значение в заголовке Cookie следующих запросов. Куда именно клиент её вернёт, определяют атрибуты:

ex.getResponseHeaders().add("Set-Cookie", "SESSION=abc; Path=/; HttpOnly; SameSite=Lax");
ex.getResponseHeaders().add("Set-Cookie", "TRACK=xyz; Path=/; Secure");
// Следующий запрос по http:// к тому же серверу.
cookies sent: [SESSION=abc]

Клиент сохранил обе cookies, но по обычному HTTP отправил только одну: Secure разрешает передавать cookie только по HTTPS. HttpOnly закрывает её от JavaScript страницы, и XSS не сможет её украсть. SameSite решает, отправлять ли cookie в запросах, начатых с чужого сайта: Strict — никогда, Lax — только при переходе по ссылке методом GET, None — всегда, но только вместе с Secure. Domain и Path ограничивают, к каким адресам она уйдёт.

Cookie браузер прикладывает сам, и именно поэтому существует CSRF: чужая страница может отправить запрос, и cookie сессии уйдёт с ним. Токен в заголовке Authorization браузер сам не подставляет. Об этом выборе — в Architecture и OAuth2 & JWT.

  • Метод — обещание посредникам: GET безопасен и может быть повторён и закеширован, POST — нет.
  • Идемпотентность — об эффекте, а не ответе; POST делают повторяемым ключом идемпотентности на операцию.
  • Код ответа говорит, кто виноват и поможет ли повтор; 504 не значит, что операция не выполнилась.
  • 301 и 302 разрешают сменить POST на GET; для API — 307 и 308.
  • ETag даёт 304 без тела и защищает PUT через If-Match; атрибуты Secure, HttpOnly, SameSite решают судьбу cookie.

На собеседовании

Какие HTTP-методы идемпотентны и как сделать идемпотентным создание платежа?

Идемпотентны GET, HEAD, OPTIONS, PUT и DELETE: повтор даёт тот же эффект на сервере, хотя ответ может отличаться — второй DELETE вернёт 404. POST не идемпотентен, PATCH — в общем случае тоже. Безопасные методы — GET, HEAD, OPTIONS — вообще не меняют состояние.

Создание платежа делаю идемпотентным ключом: клиент генерирует Idempotency-Key на операцию, сервер сохраняет ключ с результатом в той же транзакции и при повторе возвращает сохранённый ответ. В демо без ключа повтор создал два платежа, с ключом — один.

  • Ключ проверяется уникальным индексом: два одновременных запроса не должны оба пройти проверку «ключа нет».
  • Повтор с тем же ключом, но другим телом — ошибка клиента, а не новая операция.
  • Прокси и клиенты могут автоматически повторять идемпотентные запросы при обрыве, поэтому GET с побочным эффектом опасен.

Чем отличаются 401 и 403, 400 и 422, 502, 503 и 504?

401 — сервер не знает, кто ты: токена нет или он неверный. 403 — знает, но прав не хватает. 400 — запрос не удалось разобрать, 422 — разобран, но нарушает бизнес-правила. 502 — прокси получил неверный ответ от backend, 503 — сервис временно недоступен, 504 — прокси не дождался ответа backend.

Класс кода определяет поведение клиентов и мониторинга: 4xx повторять бессмысленно, 5xx иногда можно. Ответ 200 с ошибкой в теле ломает кеши, метрики и клиентские библиотеки.

  • 504 не значит, что операция не выполнилась: backend мог успеть; POST повторяют только с ключом идемпотентности.
  • 429 и 503 с Retry-After — явное «не обработано, приходи позже».
  • Тело ошибок API стандартизирует RFC 9457 Problem Details.

Чем отличаются POST, PUT и PATCH?

POST — создать ресурс, адрес которого выберет сервер, или выполнить операцию; повтор создаёт новый ресурс. PUT — положить ресурс целиком по известному адресу: повтор даёт то же состояние, поэтому он идемпотентен. PATCH — частично изменить ресурс; идемпотентен только если описывает установку значений, а не приращение.

PUT с неполным телом по смыслу стирает отсутствующие поля, поэтому для частичных изменений нужен PATCH.

  • Форматы PATCH: JSON Merge Patch (RFC 7396) и JSON Patch (RFC 6902) со списком операций.
  • PUT и PATCH защищают от потерянных обновлений через If-Match с ETag и ответ 412.

Как работает кеширование в HTTP?

Сервер управляет кешем заголовком Cache-Control: max-age — сколько секунд копия свежая, private — только кеш клиента, no-store — не сохранять вовсе, no-cache — сохранять, но проверять у сервера перед использованием. Для проверки сервер отдаёт ETag или Last-Modified, а клиент присылает If-None-Match или If-Modified-Since; если ресурс не изменился, ответ 304 без тела.

  • Ответы с персональными данными без private попадают в общий кеш CDN и уходят другим пользователям.
  • Заголовок Vary говорит кешу, от каких заголовков запроса зависит ответ: Accept-Encoding, Authorization.
  • 304 экономит трафик и сборку ответа, но не круг до сервера.
Почему клиенты жалуются, что видят чужие счета? 
@GetMapping("/me/invoices")
ResponseEntity<List<Invoice>> invoices(Authentication user) {
    return ResponseEntity.ok()
            .cacheControl(CacheControl.maxAge(Duration.ofMinutes(5))) // Разгрузить сервер.
            .body(service.invoicesOf(user.getName()));
}

max-age без private разрешает общим кешам — CDN и прокси — сохранить ответ. Адрес /me/invoices одинаковый для всех, поэтому кеш отдаст счета первого пользователя следующим. Нужен CacheControl.maxAge(...).cachePrivate() или no-store для персональных данных, а если ответ зависит от заголовка авторизации — ещё и Vary.

Какие атрибуты cookie важны для безопасности?

Secure — отправлять только по HTTPS; в демо такая cookie не ушла по обычному HTTP. HttpOnly — недоступна JavaScript, поэтому XSS не украдёт сессию. SameSite — отправлять ли cookie в запросах с чужих сайтов: Strict — никогда, Lax — только при переходе по ссылке GET-запросом, None — всегда и только с Secure.

  • SameSite=Lax по умолчанию в браузерах сильно снижает риск CSRF, но не заменяет токен.
  • Domain с точкой открывает cookie всем поддоменам; без нужды его не задают.
  • Префиксы __Host- и __Secure- заставляют браузер проверить Secure, Path и отсутствие Domain.
  • RFC 9110: HTTP Semantics — основа урока: методы, их свойства, коды ответов, условные запросы, редиректы.
  • RFC 9111: HTTP Caching — Cache-Control, проверка свежести, 304.
  • IETF draft: The Idempotency-Key HTTP Header Field — ключ идемпотентности для POST и PATCH.
  • MDN: Using HTTP cookies — атрибуты Secure, HttpOnly, SameSite и префиксы.
