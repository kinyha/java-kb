Unique ID Generation

Идентификатор выбирают по пяти свойствам: уникален ли без координации, растёт ли со временем, сколько места занимает, раскрывает ли что-то наружу и что будет при сбое часов. Последовательность базы компактна и монотонна, но требует одного источника и выдаёт число заказов. UUID v4 генерируется где угодно, но случаен, и вставка в B-tree идёт в случайные страницы: индекс в демо на 1 млн строк занял 39 МБ с 30 % пустоты против 21 МБ у bigserial. UUID v7 начинается с времени и вставляется в правый край индекса — но только если внутри миллисекунды он монотонен: наивный v7 дал те же 31 % пустоты, монотонный — 10 %. Snowflake упаковывает время, номер узла и счётчик в 64 бита и ломается, если часы идут назад.

Заказ 1042 рассказал конкурентам, сколько у нас продаж

Интернет-магазин выдавал заказам номера из последовательности базы: 1041, 1042, 1043. Конкурент сделал два заказа с разницей в неделю и вычел номера — получил число продаж за неделю. Затем сервис заказов разделили на два региона со своими базами, и последовательности начали выдавать одинаковые номера. Пришлось переходить на UUID — и после миграции вставка в таблицу заказов замедлилась, а индекс первичного ключа вырос почти вдвое.

Тема разбирает схемы генерации, их поведение в B-tree индексе и устройство Snowflake. Устройство B-tree и страниц — в Indexes, шардирование, при котором идентификатор должен быть уникален между шардами, — в Sharding. Демо IdDemo.java вставляет миллион строк в PostgreSQL 17 с разными ключами и генерирует Snowflake.

Два v4 не имеют ничего общего. Два v7, созданных с паузой в 2 мс, совпадают в первых 12 шестнадцатеричных цифрах — это 48 бит миллисекунд Unix-времени, — а цифра 7 в третьей группе означает версию. Значения случайные и меняются при каждом запуске.

Случайный ключ раздувает B-tree, упорядоченный — нет

== insert 1,000,000 rows into a table with a primary key, PostgreSQL 17
   bigserial    890 ms   pk index 21 MB    free space in leaf pages 10%
   uuid v4     1713 ms   pk index 39 MB    free space in leaf pages 30%
   uuid v7     1315 ms   pk index 39 MB    free space in leaf pages 31%
   v7 mono     1013 ms   pk index 30 MB    free space in leaf pages 10%

Числа демо это подтверждают. У bigserial и монотонного v7 в листовых страницах 10 % пустоты — ровно fillfactor 90. У v4 — 30 %, а индекс вдвое больше bigserial: 39 МБ против 21 МБ, из них около 9 МБ — разница в размере ключа (16 байт против 8), остальное — пустота от делений пополам. Время вставки плавает от запуска к запуску на сотни миллисекунд, а размеры и пустота повторяются.

Самое поучительное — строка uuid v7. Демо генерирует около тысячи идентификаторов в миллисекунду, а в наивной реализации 12 бит после времени случайны. Внутри миллисекунды порядок случаен, и индекс ведёт себя как при v4. RFC 9562 предлагает для этого монотонный счётчик или долю миллисекунды в этих битах; так сделан uuidV7Monotonic, и пустота вернулась к 10 %. PostgreSQL 18 добавил функцию uuidv7(), которая кладёт в эти биты долю миллисекунды и гарантирует возрастание в пределах сеанса.

// Монотонный v7 (RFC 9562, метод 1): в 12 битах rand_a — счётчик внутри миллисекунды.
static synchronized UUID uuidV7Monotonic() {
    long ms = System.currentTimeMillis();
    if (ms <= lastMs) { ms = lastMs; if (++counter > 0xfff) { ms++; counter = 0; } }  // переполнение — следующая мс
    else counter = 0;
    lastMs = ms;
    long hi = (ms << 16) | 0x7000L | counter;                                     // время, версия 7, счётчик
    long lo = (rnd.nextLong() & 0x3fffffffffffffffL) | 0x8000000000000000L;      // вариант 10, случайные биты
    return new UUID(hi, lo);
}

На миллионе строк весь индекс помещается в память, поэтому разница во времени умеренная. Когда индекс таблицы в сотни гигабайт перерастает память, случайная вставка v4 требует читать с диска случайную страницу почти на каждую строку, а упорядоченная работает с горячим правым краем — тогда разница становится кратной. Это видно в росте чтений из pg_stat_io и в задержках вставки, но в этом демо не измерялось.

Snowflake: время, узел и счётчик в одном long

synchronized long next() {
    long ms = System.currentTimeMillis();
    if (ms < lastMs) throw new IllegalStateException("refusing ids for " + (lastMs - ms) + " ms");
    if (ms == lastMs) {
        seq = (seq + 1) & 0xfff;
        if (seq == 0) while ((ms = System.currentTimeMillis()) <= lastMs) { }   // 4096 за мс исчерпаны: ждём
    } else seq = 0;
    lastMs = ms;
    return ((ms - EPOCH) << 22) | (node << 12) | seq;
}
== snowflake: 41 bits ms, 10 bits node, 12 bits sequence
   two ids: 232119003257008128 232119003257008129 increasing true
   decoded: node 7, seq 0/1
   clock moved back: refusing ids for N ms

Snowflake из Twitter даёт 64-битный растущий идентификатор без обращения к общему источнику: 41 бит миллисекунд от собственной эпохи (хватает примерно на 69 лет), 10 бит номера узла (1 024 узла) и 12 бит счётчика (4 096 значений на узел за миллисекунду). Уникальность держится на двух условиях. Номера узлов не должны совпадать — их раздают из конфигурации, порядковый номер пода StatefulSet в Kubernetes или аренду в ZooKeeper и etcd. И часы не должны идти назад: если NTP отвёл время, генератор выдал бы уже выданные значения, поэтому он отказывается работать до момента, когда часы догонят последнее время. Демо имитирует сдвиг часов на 5 мс; число миллисекунд ожидания зависит от момента и заменено на N.

Близкий по идее способ — блоки из базы: сервис берёт у последовательности сразу 50 значений и раздаёт их из памяти. Так работает allocationSize = 50 у @SequenceGenerator в Hibernate: последовательность увеличивается с шагом 50, и база участвует один раз на блок. Значения нескольких экземпляров перемешиваются во времени, а при перезапуске остаток блока пропадает — в последовательности появляются дыры, что нормально.

UUID v7 упорядочен по времени, поэтому любая реализация вставляется в индекс так же плотно, как bigserial.

Упорядочены только миллисекунды. Демо генерирует около тысячи идентификаторов в миллисекунду, и наивный v7 со случайными битами после времени дал 31 % пустоты — как v4. Монотонный счётчик в этих битах вернул 10 %, как у bigserial.

Что выбрать

Одна база и внутренние идентификаторы — bigserial или identity: компактно и быстро, а наружу отдают отдельный неугадываемый идентификатор. Несколько источников записи, генерация на клиенте до вставки, слияние данных из разных баз — монотонный UUID v7: уникален без координации и дружит с индексом. Нужен 64-битный растущий номер при большом числе узлов — Snowflake с надёжной раздачей номеров узлов и мониторингом часов. Публичные идентификаторы не должны раскрывать объёмы: последовательность раскрывает число записей, а v7 и Snowflake — время создания. Если и это чувствительно, наружу отдают v4 или зашифрованный внутренний номер.

Идентификатор как ключ идемпотентности — отдельная тема: если клиент создаёт его до запроса, повтор запроса приходит с тем же идентификатором, и вставка с конфликтом по ключу становится естественной защитой от дублей, как в Idempotency.

  • Свойства схемы: уникальность без координации, рост со временем, размер, что раскрывает, поведение при сбое часов.
  • 1 млн строк: bigserial — индекс 21 МБ и 10 % пустоты; v4 — 39 МБ и 30 %; монотонный v7 — 30 МБ и 10 %.
  • Наивный v7 со случайными битами внутри миллисекунды дал 31 % пустоты — как v4.
  • Snowflake: 41 бит времени, 10 бит узла, 12 бит счётчика; при часах, ушедших назад, генератор должен отказать.
  • Последовательность раскрывает число записей, v7 и Snowflake — время создания.

На собеседовании

UUID или автоинкремент для первичного ключа?

Автоинкремент компактен (8 байт) и вставляется в правый край индекса, но требует одного источника и раскрывает число записей. UUID v4 генерируется где угодно, но вдвое больше и случаен: вставка идёт в случайные страницы, индекс раздувается — в демо 39 МБ против 21 МБ и 30 % пустоты. UUID v7 сочетает генерацию без координации с ростом по времени и плотным индексом.

  • v7 должен быть монотонным внутри миллисекунды, иначе при высокой частоте индекс ведёт себя как при v4.
  • PostgreSQL 18 — встроенная uuidv7(); в JDK 21 генератора v7 нет.
  • Разница во времени становится кратной, когда индекс перерастает память.
Таблица платежей на 2 млрд строк. Что не так? 
@Entity
class Payment {
    @Id UUID id = UUID.randomUUID();      // публичный id, используем и как первичный ключ
    ...
}
// GET /payments/{id} отдаёт платёж любому, кто знает id

На 2 млрд строк индекс первичного ключа из случайных UUID не помещается в память, и почти каждая вставка читает случайную страницу с диска; пустота в листьях около 30 % раздувает индекс и все вторичные индексы, которые ссылаются на строку. Лучше монотонный v7 или внутренний bigint с отдельным публичным идентификатором. Последняя строка — отдельная проблема: неугадываемый id не заменяет проверку прав, и выдача платежа должна проверять владельца, как в Web Security.

Как устроен Snowflake и что с ним может пойти не так?

64 бита: 41 бит миллисекунд от своей эпохи, 10 бит номера узла, 12 бит счётчика внутри миллисекунды. Генерируется локально, растёт со временем, 4 096 значений на узел за миллисекунду. Ломается, если два узла получили один номер или часы пошли назад: тогда генератор должен отказать, пока часы не догонят.

  • Номера узлов — из конфигурации, StatefulSet ordinal или аренды в ZooKeeper и etcd.
  • Исчерпание счётчика — ожидание следующей миллисекунды.
  • Эпоха своя, чтобы 41 бита хватило на десятилетия.

Как генерировать уникальные идентификаторы в распределённой системе?

Без координации: UUID v4 или v7 — уникальность обеспечивает случайность. С разделённым пространством: Snowflake с уникальным номером узла. С редкой координацией: блоки из последовательности (hi/lo, allocationSize в Hibernate). Централизованный генератор — простой, но единая точка отказа и лишний сетевой вызов.

  • Выбор по пяти свойствам: координация, порядок, размер, что раскрывает, сбой часов.
  • Порядок по времени между узлами приблизителен: часы расходятся.
