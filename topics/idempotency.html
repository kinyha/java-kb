Idempotency

Операция идемпотентна, если повтор не меняет результат: второй запрос «списать по заказу 42» не списывает второй раз. В распределённой системе повторы неизбежны — таймаут не говорит, выполнился ли запрос, — поэтому всё, что меняет деньги, должно переживать повтор. Естественная идемпотентность — условное обновление или запись по ключу. Для операций вроде создания платежа клиент присылает ключ идемпотентности, а сервер атомарно занимает его, выполняет операцию один раз, сохраняет ответ и на повтор возвращает тот же ответ. Ключ передают и дальше, в банк, потому что сбой возможен между любыми двумя шагами.

Клиент не дождался ответа, повторил запрос, и деньги списались дважды

Интернет-магазин вызывает API платёжного сервиса, чтобы списать 500 рублей. Банк отвечает медленно, и запрос магазина обрывается по таймауту через 200 мс. Магазин не знает, прошло ли списание, и повторяет запрос — так поступает любой разумный клиент, а заодно ретраи в HTTP-клиенте, балансировщике и сервисной сетке. Первый запрос тем временем завершился, и покупатель видит два списания.

Тема разбирает, как сделать операцию безопасной для повторов на уровне API и как довести эту гарантию до конца цепочки. Семантика методов HTTP — в HTTP, идемпотентные консьюмеры сообщений — в Brokers & Guarantees, повторы и их настройка — в Resilience Patterns. Демо IdempotencyDemo.java поднимает платёжный эндпоинт на JDK HttpServer с таблицей ключей в PostgreSQL 17; «банк» списывает 500 мс, дольше таймаута клиента.

Таймаут не говорит, выполнилась ли операция

== without idempotency: client times out at 200 ms and retries
   POST /naive/payments  key=null -> HttpTimeoutException
   POST /naive/payments  key=null -> 201 {"payment":"p-2"}
   bank charges: 2

Клиент получил таймаут на первый запрос и успешный ответ на второй, а банк списал дважды. У таймаута три возможных объяснения: запрос не дошёл, дошёл и выполняется, выполнился, но не дошёл ответ. Клиент не может их различить, и единственный безопасный способ — повторить, если сервер гарантирует, что повтор не выполнит операцию второй раз.

Часть операций идемпотентна по своей природе. PUT /payments/p-1/status = CAPTURED или update ... set status = 'CAPTURED' where id = ? and status = 'AUTHORIZED' безопасно выполнить дважды: второй раз ничего не изменит. Вставка с уникальным ключом из предметной области — unique (merchant_id, order_id) — не создаст второй платёж по тому же заказу. А вот «создать новый платёж» или «списать ещё 500» сами по себе не идемпотентны, и для них нужен явный ключ.

Ключ идемпотентности занимают атомарно, а ответ сохраняют для повтора

create table idempotency_key(
    merchant text, key text, request_hash text not null,
    status text not null,                    -- IN_PROGRESS или DONE
    response_code int, response_body text,
    created_at timestamptz default now(),
    primary key (merchant, key));            -- ключ уникален в рамках клиента
== with Idempotency-Key: same retry
   POST /payments        key=k-1  -> HttpTimeoutException
   POST /payments        key=k-1  -> 201 (replayed) {"payment":"p-3"}
   bank charges: 1
== two concurrent requests with the same key
   POST /payments        key=k-2  -> 409 {"title":"request with this key is in progress"}
   POST /payments        key=k-2  -> 201 {"payment":"p-4"}
   bank charges: 1
== same key, different body
   POST /payments        key=k-1  -> 422 {"title":"key reused with a different request"}

Повтор после таймаута вернул тот же ответ с пометкой Idempotent-Replayed, а банк списал один раз. Два одновременных запроса с одним ключом не списали дважды: вставку выиграл один, второй получил 409. Ключ, присланный с другим телом, отклонён 422: это ошибка клиента, и тихо вернуть ответ на другой запрос было бы хуже. Для этого рядом с ключом хранится хеш запроса.

Ключ генерирует клиент — UUID на одну логическую операцию, — и он одинаков во всех повторах этой операции. Уникальность — в рамках клиента: (merchant, key), иначе ключи разных магазинов столкнутся. Хранят ключи ограниченное время — Stripe держит их 24 часа, — после чего повтор считается новым запросом. Проверка «нет ли уже такого ключа» отдельным SELECT перед вставкой гонку не закрывает: только уникальное ограничение или атомарный SET NX в Redis.

Сбой между списанием и сохранением ответа оставляет ключ в IN_PROGRESS

Схема выше не закрывает один случай: сервер вызвал банк, банк списал, а сервер упал, не успев перевести ключ в DONE. Ключ навсегда IN_PROGRESS, клиент получает 409, а списание было. Повторить вызов банка нельзя — он спишет ещё раз. Выход — та же идея на следующем шаге: передать в банк собственный ключ идемпотентности, производный от ключа клиента. Тогда восстановление — повторить вызов банка с тем же ключом: банк вернёт результат уже выполненного списания. Зависшие IN_PROGRESS с истёкшей арендой разбирает фоновая задача.

Если операция целиком внутри своей базы — создать запись, изменить баланс, — всё проще: ключ, изменения и ответ записывают в одной транзакции, и сбой откатывает их вместе. Сложность появляется на каждой границе с внешней системой, и на каждой нужна своя идемпотентность: клиент → сервис по ключу клиента, сервис → банк по ключу операции, сервис → брокер через Transactional Outbox, брокер → консьюмер по id события.

Достаточно проверить, был ли уже такой запрос, перед тем как его выполнять.

Проверка и выполнение — два шага, и два параллельных повтора оба увидят «не было». Ключ должен заниматься атомарно — уникальным ограничением или SET NX, — запрос, пока он выполняется, должен видеть статус IN_PROGRESS, а сбой посреди операции закрывается идемпотентностью следующего шага, а не проверкой.

«Ровно один раз» складывается из повторов и идемпотентности на каждом шаге

Доставить сообщение или запрос ровно один раз через ненадёжную сеть невозможно: можно либо не повторять и иногда терять, либо повторять и иногда дублировать. На практике выбирают второе и делают каждый шаг идемпотентным, тогда эффект получается однократным. Цепочка платёжного сервиса выглядит так:

ШагПовторы возникают из-заЗащита
Клиент → APIТаймауты, ретраи клиента и проксиIdempotency-Key, сохранённый ответ
Сервис → банкТаймауты, восстановление после сбояКлюч операции у банка, статус-запрос
Сервис → брокерПадение между базой и отправкойOutbox, at-least-once
Брокер → консьюмерПовторная доставкаТаблица обработанных id, условные обновления

Идемпотентность — не только защита от дублей, но и право повторять: сервисы с идемпотентными операциями можно смело ретраить, перезапускать и переигрывать сообщения из очереди при восстановлении.

  • Таймаут не говорит, выполнилась ли операция; без защиты повтор дал два списания.
  • Естественная идемпотентность — условные обновления и уникальные ключи предметной области; для создания — ключ клиента.
  • Ключ занимают атомарно (unique, SET NX), хранят статус, хеш запроса и ответ: повтор — тот же 201, параллельный — 409, другое тело — 422.
  • Сбой между внешним вызовом и сохранением закрывает ключ идемпотентности у следующего шага и фоновое восстановление.
  • Однократный эффект = повторы + идемпотентность на каждом шаге цепочки.

На собеседовании

Как реализовать ключ идемпотентности в API?

Клиент присылает заголовок Idempotency-Key — уникальный для одной логической операции и одинаковый во всех её повторах. Сервер атомарно вставляет ключ в таблицу с уникальным ограничением и статусом IN_PROGRESS, выполняет операцию, сохраняет код и тело ответа и ставит DONE. Повтор с тем же ключом получает сохранённый ответ, параллельный — 409, тот же ключ с другим телом — 422.

  • Ключ уникален в рамках клиента и хранится ограниченное время.
  • Хеш запроса рядом с ключом ловит повторное использование ключа для другого запроса.
  • Если операция только в своей базе — ключ, изменения и ответ в одной транзакции.
Почему эта защита пропускает двойные списания? 
public PaymentResponse pay(String key, PayRequest r) {
    var cached = redis.get("idem:" + key);
    if (cached != null) return json.read(cached);
    PaymentResponse resp = bank.charge(r);
    redis.set("idem:" + key, json.write(resp), Duration.ofHours(24));
    return resp;
}

Проверка и запись разделены: два параллельных повтора оба не найдут ключ и оба спишут. Ключ должен заниматься атомарно до вызова банка — SET NX со статусом IN_PROGRESS, — а параллельный запрос должен получать 409. Если процесс упадёт после bank.charge, ключа в Redis не будет, и повтор спишет снова — в банк нужно передавать собственный ключ идемпотентности. Ключ не привязан к клиенту и телу запроса.

Как добиться exactly-once в распределённой системе?

Доставку ровно один раз через ненадёжную сеть гарантировать нельзя, поэтому выбирают at-least-once — повторы — и делают каждый шаг идемпотентным: ключ идемпотентности на API, ключ операции у внешнего сервиса, outbox при публикации событий и дедупликация по id у консьюмера. Эффект становится однократным.

  • Идемпотентность даёт право на повторы, перезапуски и переигрывание сообщений.
  • Exactly-once в Kafka — только внутри Kafka; внешние эффекты защищают идемпотентностью.

Какие операции идемпотентны сами по себе?

Чтение; установка значения, а не приращение (PUT, set status = X); условное обновление с проверкой текущего состояния (where status = 'AUTHORIZED'); удаление по id; вставка с уникальным ключом предметной области (merchant_id, order_id). Неидемпотентны создание новой сущности без ключа и приращения: «списать ещё 500», increment.

  • Методы GET, PUT, DELETE идемпотентны по HTTP-семантике, но реализация может её нарушить.
  • Условное обновление по версии превращает приращение в идемпотентное.
