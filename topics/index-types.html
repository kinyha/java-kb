Index Types

B-tree отвечает на равенство, диапазон и сортировку, но не на всё. GIN — инвертированный индекс: для каждого элемента — ключа jsonb, слова, триграммы — список строк, где он встречается; он ищет вхождения и подстроки. GiST хранит обобщённые «рамки» и умеет пересечения диапазонов и геометрию, на нём строят exclusion constraint против пересекающихся броней. BRIN хранит только минимум и максимум на группу страниц и весит килобайты, но работает лишь там, где значения коррелируют с физическим порядком. Частичный индекс хранит только нужные строки, индекс по выражению — вычисленное значение.

Поиск по атрибутам платежа и по части email шёл полным проходом, а индекс по времени занял 20 ГБ

Антифрод ищет платежи по атрибутам в jsonb: страна, канал, уровень риска. Поддержка ищет клиента по куску email. Обычные B-tree-индексы не помогли ни там, ни там. Таблица событий, куда только дописывают, получила B-tree по created_at размером с треть самой таблицы. А двум операторам удалось забронировать один и тот же терминал на пересекающееся время.

Тема разбирает типы индексов PostgreSQL помимо B-tree и случаи, когда каждый из них нужен. Основы и составные индексы — в Indexes, write skew и двойные брони — в ACID & Isolation. Демо IndexTypesDemo.java работает с PostgreSQL 17 в Docker на миллионе событий; строка вывода — узел доступа к таблице, прочитанные страницы и время.

GIN — инвертированный индекс: для каждого элемента список строк

create index ev_attrs_gin on ev using gin (attrs jsonb_path_ops);
select count(*) from ev where attrs @> '{"country": "KZ", "risk": 3}';

create extension pg_trgm;
create index ev_email_trgm on ev using gin (email gin_trgm_ops);
select count(*) from ev where email like '%r777@%';
== jsonb containment attrs @> {country: KZ, risk: 3}
   Seq Scan on ev (actual rows=14286 loops=1); Buffers: shared hit=16254 read=988; Execution Time: 56.460 ms
   Bitmap Heap Scan on ev (actual rows=14286 loops=1); Buffers: shared hit=8161 read=6183 written=6145; Execution Time: 25.160 ms
== substring email like '%r777@%'
   Seq Scan on ev (actual rows=20 loops=1); Buffers: shared hit=15857 read=1379 written=32; Execution Time: 40.227 ms
   Bitmap Heap Scan on ev (actual rows=20 loops=1); Buffers: shared hit=44 read=13; Execution Time: 0.193 ms

B-tree упорядочивает значения целиком и не знает, что внутри jsonb-документа или строки. GIN разбирает значение на элементы — пары путь-значение в jsonb, триграммы в тексте — и для каждого хранит список строк. Запрос на вхождение пересекает списки нужных элементов. Для поиска по атрибутам это 25 мс вместо 56: подходит 14 тысяч строк, полтора процента таблицы, и большую часть времени занимает чтение самих строк. Для подстроки в email эффект огромный — 0,19 мс вместо 40: триграммы r77, 777, 77@ встречаются редко, и индекс сразу сужает поиск до двадцати строк.

Цена GIN — запись: одна строка добавляет записи для всех своих элементов. Чтобы вставки не тормозили, GIN копит изменения в списке ожидания (fastupdate) и вливает их пачкой, поэтому поиск сразу после массовой вставки бывает медленнее. Триграммный индекс большой: 34 МБ на колонку email миллиона строк. jsonb_path_ops компактнее стандартного класса для jsonb, но поддерживает только оператор вхождения @>.

BRIN хранит минимум и максимум на группу страниц и весит килобайты

== time range on append-only table: btree vs brin
   Bitmap Heap Scan on ev (actual rows=8640 loops=1); Buffers: shared hit=6 read=255 written=255; Execution Time: 1.016 ms
== index sizes
   ev_created_brin      24 kB
   (btree on created_at for comparison: 21 MB)

BRIN (block range index) делит таблицу на диапазоны по 128 страниц и для каждого хранит минимальное и максимальное значение. Запрос за сутки отбрасывает все диапазоны, чьи границы не пересекают сутки, и читает оставшиеся страницы целиком, проверяя строки. Здесь это 261 страница и миллисекунда — почти как у B-tree, а индекс весит 24 КБ против 21 МБ. Для журнала событий, логов и платёжных проводок за годы разница в размере — гигабайты.

Условие одно: значения должны коррелировать с физическим положением строк. Таблица, куда события дописываются по времени, подходит идеально. Если строки обновляются и переезжают или время вставки не связано с колонкой, у каждого диапазона границы окажутся широкими, и BRIN не отбросит ничего. Корреляцию показывает pg_stats.correlation: около 1 или −1 — BRIN подходит.

Частичный индекс хранит только нужные строки, и планировщик предпочитает его

create index ev_failed_partial on ev(created_at) where status = 'FAILED';
== partial index for rare status
   Index Only Scan using ev_failed_partial on ev (actual rows=4903 loops=1); Buffers: shared hit=1 read=16; Execution Time: 0.177 ms
   Index Only Scan using ev_failed_partial on ev (actual rows=4903 loops=1); Buffers: shared hit=17; Execution Time: 0.203 ms
== index sizes
   ev_status_full       39 MB
   ev_failed_partial    240 kB

Неудачных платежей — один процент. Частичный индекс содержит только их и весит 240 КБ вместо 39 МБ у полного индекса по (status, created_at). Запрос по неудачным платежам прочитал 17 страниц, и даже когда рядом создали полный индекс, планировщик остался на частичном (вторая строка): он меньше и дешевле. Частичный индекс используется, только если условие запроса явно включает условие индекса: status = 'FAILED' в запросе обязателен, параметр status = ? со значением при подготовленном запросе может его не задействовать.

Частичный уникальный индекс решает задачи, которые иначе требуют блокировок: create unique index on payment(order_id) where status <> 'FAILED' — у заказа может быть сколько угодно неудачных попыток, но только один не неудачный платёж. Индекс по выражению хранит вычисленное значение, например lower(email), как показано в Indexes.

GiST знает о пересечениях, и exclusion constraint запрещает двойные брони

create extension btree_gist;                       -- равенство по int внутри GiST
create table slot(terminal int, during tstzrange,
    exclude using gist (terminal with =, during with &&));
== exclusion constraint: no overlapping bookings of one terminal
   [2026-10-03 11:00, 2026-10-03 12:00) -> inserted
   [2026-10-03 10:30, 2026-10-03 11:30) -> 23P01 ERROR: conflicting key value violates exclusion constraint "slot_terminal_during_excl"

GiST — каркас для индексов с произвольными «рамками»: диапазоны, геометрия, сети. Он умеет ответить, какие диапазоны пересекаются с данным. Exclusion constraint обобщает уникальность: запрещены две строки, у которых совпадает терминал и пересекается время. Бронь с 11:00 до 12:00 встала рядом с бронью до 11:00 — полуоткрытые диапазоны не пересекаются. Бронь с 10:30 отклонена ошибкой 23P01, даже если две транзакции вставляют её одновременно: проверка идёт через индекс с блокировками, как у уникального ключа. Это защита от write skew из ACID & Isolation без SERIALIZABLE.

Для поиска по jsonb или по подстроке достаточно обычного индекса на колонку.

B-tree упорядочивает значение целиком и не видит, что внутри документа или строки. В демо поиск по атрибутам и по куску email шёл полным проходом, пока не появились GIN-индексы: jsonb_path_ops для @> и gin_trgm_ops для LIKE '%…%'.

  • GIN — инвертированный индекс: @> по jsonb 25 мс вместо 56, подстрока email 0,19 мс вместо 40; дорогая запись.
  • BRIN — минимум и максимум на 128 страниц: 24 КБ против 21 МБ у B-tree, но только при корреляции с физическим порядком.
  • Частичный индекс: 240 КБ против 39 МБ, планировщик выбирает его, если условие запроса включает условие индекса.
  • GiST и exclusion constraint запрещают пересечения диапазонов: 23P01 для двойной брони.

На собеседовании

Какие типы индексов есть в PostgreSQL и когда какой нужен?

B-tree — по умолчанию: равенство, диапазоны, сортировка. Hash — только равенство. GIN — инвертированный индекс для составных значений: jsonb, массивы, полнотекстовый поиск, триграммы для LIKE '%…%'. GiST — для пересечений и близости: диапазоны, геометрия, exclusion constraints. BRIN — сверхкомпактный индекс для огромных таблиц с колонкой, коррелирующей с порядком записи.

  • Частичные индексы и индексы по выражению работают с любым типом.
  • GIN дорог на запись и копит изменения в fastupdate.
  • BRIN бесполезен без корреляции: pg_stats.correlation.

Что такое частичный индекс и где он полезен?

Индекс с условием WHERE: он содержит только подходящие строки. Полезен для редких значений — неудачные платежи, необработанные задачи, — где он в десятки раз меньше полного и быстрее. Частичный уникальный индекс выражает правила вроде «один активный платёж на заказ».

  • Используется, только если условие запроса логически влечёт условие индекса.
  • С подготовленными запросами и generic plan параметр вместо константы может не позволить его выбрать.
Как надёжнее запретить двойную бронь терминала? 
@Transactional
public void book(int terminal, Instant from, Instant to) {
    if (slots.existsOverlap(terminal, from, to)) throw new AlreadyBooked();
    slots.save(new Slot(terminal, from, to));
}

Проверка и вставка — разные шаги: две транзакции одновременно не увидят пересечения и обе вставят бронь (write skew, на READ COMMITTED и REPEATABLE READ). Надёжно — exclusion constraint в базе: exclude using gist (terminal with =, during with &&) с btree_gist; второй вставке база ответит 23P01, которую приложение превращает в «уже занято».

Когда BRIN лучше B-tree?

Когда таблица огромная, в неё в основном дописывают, а колонка поиска растёт вместе с физическим порядком — время события, автоинкрементный id. BRIN хранит минимум и максимум на группу страниц, весит килобайты вместо гигабайтов и отбрасывает ненужные группы. Для точечных запросов и неупорядоченных данных он проигрывает B-tree.

  • pages_per_range настраивает точность и размер.
  • Обновления и вставки в середину размывают границы диапазонов.
