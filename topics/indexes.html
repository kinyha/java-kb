Indexes

B-tree индекс — отсортированный список значений с адресами строк, по которому база находит нужный диапазон за несколько страниц вместо чтения всей таблицы. В составном индексе порядок колонок решает всё: сначала колонки с условием равенства, потом колонка диапазона или сортировки. Покрывающий индекс содержит все нужные запросу колонки и отвечает без обращения к таблице. Индекс бесполезен, если запрос выбирает большую долю строк или строки разбросаны по всем страницам, если колонка обёрнута в функцию или шаблон начинается с %. Каждый индекс замедляет запись и занимает место.

Лента платежей магазина читала миллион строк ради двадцати

Личный кабинет магазина показывает 20 последних платежей за период. На тестовой базе запрос шёл миллисекунды, на проде — сотни: таблица выросла до сотен миллионов строк. Индекс по created_at и merchant уже был, но помог слабо. Другой разработчик добавил индекс по статусу, чтобы ускорить отчёт по успешным платежам, — отчёт не ускорился, а вставка платежей замедлилась.

Тема разбирает, как устроен B-tree, почему порядок колонок важен, что такое покрывающий индекс и когда индекс не помогает. Чтение планов подробно — в Query Plans, другие типы индексов — в Index Types, keyset-пагинация по индексу — в API Design. Демо IndexDemo.java работает с PostgreSQL 17 в Docker на таблице из миллиона платежей и показывает EXPLAIN (ANALYZE, BUFFERS): сколько страниц прочитал запрос и сколько он шёл.

B-tree — отсортированные значения со ссылками на строки

Листья B-tree индекса — значения ключа в отсортированном порядке, и у каждого адрес строки в таблице. Над листьями — несколько уровней внутренних страниц, по которым поиск спускается к нужному листу: для миллиона строк это три уровня, для миллиарда — четыре-пять. Найдя начало диапазона, поиск идёт по листьям слева направо, а за каждой строкой ходит в таблицу. Поэтому индекс выигрывает, когда диапазон узкий, и проигрывает полному чтению, когда нужна большая часть таблицы.

select id, amount from pay
where merchant = 42 and created_at >= '2026-09-01'
order by created_at desc limit 20;
== no index
   Buffers: shared hit=12196
   ->  Seq Scan on pay (actual rows=160 loops=1)
   Filter: ((created_at >= '2026-09-01 00:00:00+03'::timestamp with time zone) AND (merchant = 42))
   Rows Removed by Filter: 999840
   Execution Time: 17.296 ms

Без индекса база прочитала все 12 196 страниц таблицы, проверила миллион строк и отбросила 999 840 ради 160 подходящих, а потом отсортировала их ради двадцати. 17 мс на миллионе строк — терпимо, но время растёт линейно с таблицей.

В составном индексе сначала равенство, потом диапазон

== index (created_at, merchant)
   Buffers: shared hit=39 read=80
   ->  Index Scan Backward using pay_created_merchant on pay (actual rows=20 loops=1)
   Index Cond: ((created_at >= '2026-09-01 00:00:00+03'::timestamp with time zone) AND (merchant = 42))
   Execution Time: 0.330 ms
== index (merchant, created_at)
   Buffers: shared hit=20 read=3
   ->  Index Scan Backward using pay_merchant_created on pay (actual rows=20 loops=1)
   Index Cond: ((merchant = 42) AND (created_at >= '2026-09-01 00:00:00+03'::timestamp with time zone))
   Execution Time: 0.035 ms

Оба индекса содержат обе колонки, но работают по-разному. В (created_at, merchant) записи упорядочены по времени, а магазины внутри перемешаны: поиск идёт от конца назад по всем платежам после 1 сентября и проверяет магазин у каждой — 119 страниц. В (merchant, created_at) все платежи магазина 42 лежат подряд, уже упорядоченные по времени: поиск спускается к концу этого куска и читает ровно 20 записей — 23 страницы, в десять раз быстрее. Отдельная сортировка не нужна: индекс отдаёт строки в нужном порядке.

Правило для составного индекса: сначала колонки с условием равенства, затем одна колонка с диапазоном или сортировкой. Колонки после диапазона индекс использует только как фильтр. Индекс (a, b) обслуживает и запросы только по a, но не только по b. Начиная с PostgreSQL 18 появился skip scan, который частично снимает это ограничение для колонок с малым числом значений, но для PostgreSQL 17 правило строгое.

Покрывающий индекс отвечает без обращения к таблице

== covering index (merchant, created_at) include (amount)
   Buffers: shared hit=1 read=3
   ->  Index Only Scan Backward using pay_merchant_created_cov on pay (actual rows=20 loops=1)
   Index Cond: ((merchant = 42) AND (created_at >= '2026-09-01 00:00:00+03'::timestamp with time zone))
   Heap Fetches: 0
   Execution Time: 0.020 ms

Если в индексе есть все колонки, которые нужны запросу, база может не ходить в таблицу вовсе: Index Only Scan прочитал 4 страницы вместо 23. INCLUDE (amount) кладёт колонку в листья индекса, не делая её частью ключа сортировки. Есть оговорка, связанная с MVCC: индекс не знает, видима ли версия строки, и Index Only Scan проверяет карту видимости — страницы, где все версии видны всем. Её обновляет VACUUM, поэтому на часто меняемой таблице без свежей очистки Heap Fetches будет большим, и выигрыш исчезнет. Здесь после VACUUM — ноль обращений к таблице.

Индекс проигрывает, когда нужна большая часть таблицы или строки разбросаны

== status = 'FAILED' (5% of rows)
   Buffers: shared hit=12196 read=44
   ->  Index Scan using pay_status_idx on pay (actual rows=50000 loops=1)
   Index Cond: (status = 'FAILED'::text)
   Execution Time: 9.550 ms
== status = 'CAPTURED' (95% of rows)
   Buffers: shared hit=12196
   ->  Seq Scan on pay (actual rows=950000 loops=1)
   Filter: (status = 'CAPTURED'::text)
   Rows Removed by Filter: 50000
   Execution Time: 40.026 ms

Для 95 % строк планировщик выбрал полный проход по таблице и был прав: идти по индексу к каждой из 950 тысяч строк дороже, чем прочитать таблицу подряд. Индекс по статусу для такого отчёта бесполезен и только замедляет запись. Интереснее строка с FAILED: строк всего 5 %, индекс использован, но прочитаны все 12 196 страниц таблицы. Неудачные платежи — каждый двадцатый, на каждой странице есть хотя бы один, и индексный поиск всё равно трогает все страницы. Важна не только доля строк, но и их корреляция с физическим порядком: недавние платежи лежат рядом, а платежи одного статуса разбросаны.

Для редких значений помогает частичный индекс — create index on pay(created_at) where status = 'FAILED': он хранит только нужные строки и меньше весит, о нём — в Index Types.

Функция над колонкой и шаблон с % в начале выключают индекс

== email = ...
   ->  Bitmap Index Scan on pay_email_idx (actual rows=20 loops=1)
   Execution Time: 0.052 ms
== lower(email) = ...
   Seq Scan on pay (actual rows=20 loops=1)
   Filter: (lower(email) = 'user777@mail.example'::text)
   Rows Removed by Filter: 999980
   Execution Time: 110.246 ms
== lower(email) = ... with index on lower(email)
   ->  Bitmap Index Scan on pay_lower_idx (actual rows=20 loops=1)
   Index Cond: (lower(email) = 'user777@mail.example'::text)
   Execution Time: 0.049 ms
== email like '%777@mail.example'
   Seq Scan on pay (actual rows=1000 loops=1)
   Filter: (email ~~ '%777@mail.example'::text)
   Execution Time: 38.257 ms
== insert 200k rows with 0 extra indexes: 121 ms
== insert 200k rows with 4 extra indexes: 475 ms

Индекс хранит значения email, а не lower(email), поэтому условие с функцией превратило 0,05 мс в 110: полный проход с вычислением функции для миллиона строк. Решение — индекс по выражению, который хранит ровно то, что ищет запрос. Шаблон с % в начале не может использовать упорядоченность B-tree: неизвестно, с чего начинается строка; для поиска подстроки нужен триграммный GIN-индекс. Те же грабли — неявное приведение типов (сравнение varchar-колонки с числом), OR по разным колонкам и арифметика над колонкой: created_at + interval '1 day' > now() вместо created_at > now() - interval '1 day'.

У индексов есть цена. Вставка 200 тысяч строк с четырьмя дополнительными индексами заняла 475 мс вместо 121: каждый индекс обновляется при каждой вставке и при любом UPDATE, который не HOT. Индексы занимают место и память в shared buffers и раздуваются так же, как таблицы. Неиспользуемые индексы находят по idx_scan = 0 в pg_stat_user_indexes и удаляют.

Если запрос медленный, нужно добавить индекс на каждую колонку из WHERE.

Отдельные индексы на колонки не заменяют один составной в правильном порядке: в демо индекс (created_at, merchant) прочитал 119 страниц, а (merchant, created_at) — 23. Индекс по колонке с низкой селективностью планировщик не использует, а каждый лишний индекс замедляет запись: 475 мс против 121.

  • B-tree — отсортированные значения со ссылками на строки; без индекса — 12 196 страниц и миллион проверок ради 20 строк.
  • Составной индекс: сначала равенство, потом диапазон или сортировка; (merchant, created_at) — 23 страницы против 119.
  • INCLUDE даёт Index Only Scan: 4 страницы, Heap Fetches 0 — если карта видимости свежая.
  • Большая доля строк или разбросанные строки делают индекс бесполезным; частичный индекс для редких значений.
  • Функция над колонкой и LIKE '%…' выключают индекс; индекс по выражению и GIN. Каждый индекс замедляет запись.

На собеседовании

Как выбрать порядок колонок в составном индексе?

Индекс отсортирован по первой колонке, внутри неё — по второй. Поэтому сначала идут колонки с условием равенства, затем одна колонка с диапазоном или ORDER BY. Тогда подходящие строки лежат непрерывным куском, уже упорядоченным. Индекс (a, b) обслуживает запросы по a и по a с b, но не по одной b.

  • Колонки после диапазона используются только как фильтр внутри диапазона.
  • Индекс может отдать строки в нужном порядке и убрать сортировку, включая обратный порядок.
  • Skip scan в PostgreSQL 18 частично ослабляет правило для первой колонки с малым числом значений.
Какой индекс нужен этому запросу? 
select id, amount, created_at from payment
where merchant_id = :m and status = 'CAPTURED' and created_at >= :from
order by created_at desc limit 50;
-- есть индексы: (created_at), (merchant_id), (status)

Три одноколоночных индекса не дают упорядоченного куска: база выберет один и будет фильтровать и сортировать остальное. Нужен составной (merchant_id, status, created_at) — равенства, затем диапазон и сортировка, — а с INCLUDE (amount) запрос станет index-only. Индекс только по status с низкой селективностью, скорее всего, лишний и замедляет запись.

Почему база может не использовать индекс?

Запрос выбирает большую долю строк, и полный проход дешевле. Строки разбросаны по страницам, и индекс всё равно трогает почти все. Колонка обёрнута в функцию или выражение, есть неявное приведение типов, шаблон LIKE начинается с %. Порядок колонок составного индекса не подходит к условию. Статистика устарела, и планировщик ошибается в оценке строк.

  • Индекс по выражению для функций, GIN с pg_trgm для подстрок.
  • Корреляция физического порядка с индексом влияет на стоимость Index Scan; Bitmap Scan сглаживает разбросанное чтение.
  • ANALYZE обновляет статистику; EXPLAIN ANALYZE показывает расхождение оценки и факта.

Что такое покрывающий индекс и Index Only Scan?

Индекс, содержащий все колонки, нужные запросу: ключевые и добавленные через INCLUDE. Тогда база отвечает из индекса без чтения таблицы — Index Only Scan. В демо это 4 страницы вместо 23.

  • PostgreSQL проверяет видимость по карте видимости, которую обновляет VACUUM; без неё растут Heap Fetches.
  • INCLUDE-колонки не участвуют в сортировке и уникальности, но увеличивают размер индекса.
