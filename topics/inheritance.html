Inheritance & Composition

Наследование реализации связывает подкласс с внутренним устройством родителя: какие методы вызывают какие. В демо счётчик в наследнике HashSet насчитал 6 вместо 3, потому что addAll родителя сам вызывает переопределённый add. Это проблема хрупкого базового класса: подкласс ломается от деталей реализации или от новых методов в родителе. Так replaceAll из Java 8 обошёл проверку в наследнике ArrayList. Композиция — хранить объект внутри и делегировать ему — зависит только от публичного контракта и не ломается от того же изменения. Наследование оправдано, когда подкласс действительно «является» родителем по поведению — принцип подстановки Лисков (LSP). Подкласс не может ужесточать предусловия, ослаблять постусловия или отказываться от операций родителя. Ошибки самого JDK — Stack extends Vector, Properties extends Hashtable — классические контрпримеры.

Наследник, который считает неправильно

Для мониторинга нужно знать, сколько идентификаторов платежей добавили в множество за всё время, включая повторы. Проще всего унаследовать HashSet и переопределить оба метода добавления. Демо FragileBaseDemo.java:

static class CountingSet extends HashSet<String> {
    int added;
    @Override public boolean add(String id) { added++; return super.add(id); }
    @Override public boolean addAll(Collection<? extends String> ids) { added += ids.size(); return super.addAll(ids); }
}
s.addAll(List.of("p-1", "p-2", "p-3"));
== self-use inside HashSet.addAll
extends HashSet: added = 6 (expected 3)
composition:     added = 3

Чтобы правильно унаследовать HashSet, нужно знать, какие его методы вызывают какие, — а это деталь реализации, которая не описана в контракте и может поменяться между версиями. Подкласс зависит не от того, что делает родитель, а от того, как. Это и называют проблемой хрупкого базового класса: изменение, безопасное для родителя, ломает наследников, о которых его автор ничего не знает.

Родитель растёт, проверки наследника обходят

static class NonBlankList extends ArrayList<String> {
    @Override public boolean add(String id) { return super.add(check(id)); }
    @Override public void add(int i, String id) { super.add(i, check(id)); }
    @Override public String set(int i, String id) { return super.set(i, check(id)); }
}
ids.replaceAll(id -> "");                         // Java 8: ArrayList.replaceAll не вызывает set
ids.addAll(Arrays.asList("p-2", null));           // addAll не переопределён
== base class grows methods the subclass did not override
add(" "): rejected
after replaceAll and addAll: [, p-2, null]

Список «без пустых идентификаторов» закрыл add и set, и прямое добавление пробела отклонено. Но в Java 8 у ArrayList появился replaceAll, который пишет прямо во внутренний массив, минуя set, — и в списке оказалась пустая строка. addAll копирует массив без вызова add — и попал null. Автор наследника не мог защититься от метода, которого в момент написания не существовало. В Java 8 так же появились removeIf, sort и, у Map, putIfAbsent, compute и merge. В Java 21 у List появились addFirst, addLast и reversed() из SequencedCollection; в ArrayList они сейчас проходят через add (проверено на JDK 21), и наследнику повезло — но это снова деталь реализации, а не обещание контракта.

== JDK's own mistakes: Stack extends Vector, Properties extends Hashtable
stack after add(0)/remove(2): [p-0, p-1, p-3], pop = p-3
getProperty("timeout") = null, get = 30

Сам JDK содержит два учебных примера. Stack наследует Vector, поэтому у стека есть add(0, x) и remove(i) — вставка в дно и удаление из середины ломают смысл LIFO: из стека пропал p-2, хотя его никто не снимал. Стек — не вектор, ему нужен был вектор внутри; сегодня вместо Stack берут ArrayDeque из Queue & Deque. Properties наследует Hashtable<Object, Object>, и put("timeout", 30) кладёт число — а getProperty возвращает только строки и молча отдаёт null.

Композиция и делегирование

static class CountingSetComposed extends AbstractSet<String> {
    private final Set<String> inner = new HashSet<>();          // реализация внутри
    int added;
    @Override public boolean add(String id) { added++; return inner.add(id); }
    @Override public boolean addAll(Collection<? extends String> ids) { added += ids.size(); return inner.addAll(ids); }
    @Override public Iterator<String> iterator() { return inner.iterator(); }
    @Override public int size() { return inner.size(); }
}

Композиционный вариант хранит HashSet в поле и передаёт ему вызовы. Внутренний inner.addAll вызывает inner.add — метод HashSet, а не наш, поэтому счётчик верный: 3. Обёртка зависит только от публичного контракта Set; если реализация HashSet изменится, обёртка этого не заметит. Новый метод в Set обёртка тоже не пропустит молча: либо он default и реализован через наши add/iterator, либо абстрактный, и компилятор потребует его реализовать. Внутренний объект можно подменить — LinkedHashSet, TreeSet, мок в тесте — не меняя класса.

Это паттерн декоратор из Structural Patterns: класс реализует интерфейс и делегирует вложенному объекту, добавляя одно поведение. Так устроены Collections.unmodifiableList, буферизованные потоки и прокси Spring из Annotations & Reflection. Цена композиции — методы-переходники, которые пишут руками (AbstractSet сокращает их до двух; Kotlin делегирует одной строкой by); и то, что обёртка не равна по ссылке внутреннему объекту — передав this внутреннему объекту для обратного вызова, вы получите вызовы мимо обёртки.

LSP: когда подкласс действительно подкласс

static class GiftCardPayment extends Payment {
    @Override void refund(long amount) {
        if (amount != refundable) throw new UnsupportedOperationException("gift card: full refund only");
        super.refund(amount);
    }
}
static void refundHalf(List<Payment> batch) { for (Payment p : batch) p.refund(p.refundable / 2); }
== a subclass that strengthens the precondition
   p-1 refunded half, left 500
   g-1 UnsupportedOperationException: gift card: full refund only

Принцип подстановки Лисков: код, написанный для родителя, должен корректно работать с любым подклассом. Контракт Payment.refund — «вернуть любую сумму не больше остатка». GiftCardPayment ужесточил предусловие — «только целиком», и refundHalf, честно написанный по контракту, упал на подарочной карте. Демо LspDemo.java. Синтаксически всё верно: GiftCardPayment — подтип, компилятор доволен. Нарушение видно только по поведению. Правила: подкласс не ужесточает предусловия, не ослабляет постусловия, сохраняет инварианты родителя и не бросает исключений, которых контракт не допускает. UnsupportedOperationException в переопределённом методе — почти всегда признак нарушения.

Исправление — пересмотреть иерархию: возможность частичного возврата — отдельный интерфейс PartiallyRefundable, который реализуют только платежи, поддерживающие её; код возвратов принимает этот интерфейс, и компилятор не даст передать подарочную карту. Знаменитый пример с квадратом и прямоугольником — о том же: квадрат — прямоугольник в геометрии, но не в коде, где у прямоугольника независимые setWidth и setHeight. Неизменяемые объекты нарушают LSP гораздо реже: без сеттеров нет постусловий, которые подкласс мог бы сломать.

== equals across a hierarchy
plain.equals(rub) = true, rub.equals(plain) = false
list[rub].contains(plain) = true
list[plain].contains(rub) = false

Тот же конфликт в equals. Подкласс CurrencyMoney добавил валюту в сравнение — и симметрия сломалась: plain.equals(rub) истинно, обратное ложно, а результат contains зависит от того, что лежит в списке. Блох формулирует жёстко: нельзя расширить инстанцируемый класс, добавив значимое поле, и сохранить контракт equals. Выход — композиция (CurrencyMoney содержит Money) или final-классы-значения, как records. Контракт equals — в Object Methods.

Проектировать для наследования или запретить его

Блох: «Design and document for inheritance or else prohibit it». Класс, предназначенный для наследования, документирует самоиспользование — какие переопределяемые методы вызывает и когда (в Javadoc JDK это раздел @implSpec: «This implementation iterates over the specified collection, and adds each object... in turn»). Он не вызывает переопределяемые методы из конструктора — подкласс увидит неинициализированные поля, как в Classes & Objects. Он предоставляет защищённые точки расширения — шаблонный метод с protected-шагами — и тестируется написанием подклассов. Всё остальное делают final или с закрытым конструктором и фабрикой. Записи и enums — final по умолчанию.

Абстрактный класс, спроектированный под наследование, — нормальное решение: AbstractList требует реализовать get и size и даёт остальное; шаблонный метод в JdbcTemplate или OncePerRequestFilter Spring открывает ровно одну точку расширения. Выбор между абстрактным классом и интерфейсом — в Abstraction. Sealed-иерархии из Sealed & Pattern Matching ограничивают круг наследников явным списком — родитель знает всех детей и может на это полагаться. Наследование интерфейсов — отдельная история: интерфейс не несёт реализации и состояния (кроме default-методов без полей), поэтому хрупкость здесь гораздо меньше.

Переопределить add и addAll — достаточно, чтобы контролировать добавление в наследнике коллекции.

Нужно знать, как родитель вызывает свои методы, а это меняется между версиями. В демо addAll через add посчитал элементы дважды, а replaceAll из Java 8 обошёл проверку в set. Контролируемую коллекцию делают обёрткой, а не наследником.

  • Наследование реализации связывает подкласс с внутренним устройством родителя — хрупкий базовый класс.
  • Self-use: addAll родителя вызвал переопределённый add, счётчик 6 вместо 3.
  • Новые методы родителя обходят проверки наследника: replaceAll в Java 8.
  • Stack extends Vector и Properties extends Hashtable — ошибки JDK; Stack заменяет ArrayDeque.
  • Композиция зависит от контракта, а не реализации; это декоратор.
  • LSP: подкласс не ужесточает предусловия и не отказывается от операций; UnsupportedOperationException в override — сигнал.
  • Значимое поле в подклассе ломает симметрию equals.
  • Проектируй и документируй для наследования или делай final.

На собеседовании

Почему советуют композицию вместо наследования?

Наследование реализации делает подкласс зависимым от внутреннего устройства родителя: какие методы вызывают какие. Если родитель вызывает свой переопределяемый метод, подкласс получает неожиданные двойные вызовы; если в родителе появляется новый метод, он обходит проверки подкласса. Композиция — хранить объект в поле и делегировать ему — зависит только от публичного контракта, позволяет подменить реализацию и не ломается от изменений внутри родителя.

  • Пример Блоха: счётчик в наследнике HashSet насчитывает вдвое больше.
  • replaceAll и removeIf в Java 8 — новые методы, которые наследники не переопределили.
  • Наследование оправдано для «является» и классов, спроектированных под него.
Что не так с этим классом аудита? 
public class AuditedPaymentMap extends HashMap<String, Payment> {
    @Override public Payment put(String id, Payment p) {
        audit.log("put " + id);
        return super.put(id, p);
    }
}

Аудит видит только put. putAll, putIfAbsent, compute, merge и replaceAll в HashMap не обязаны вызывать put — часть из них пишет в таблицу напрямую, и изменения пройдут без аудита. Новые методы будущих версий тоже. Нужна обёртка, реализующая Map и делегирующая внутреннему HashMap, — тогда каждый изменяющий метод придётся реализовать явно.

Что такое принцип подстановки Лисков? Приведите нарушение.

Код, написанный для базового типа, должен правильно работать с любым подтипом. Подкласс не ужесточает предусловия, не ослабляет постусловия, сохраняет инварианты и не бросает неожиданных исключений. Нарушение: подкласс платежа, который разрешает возврат только целиком, — код, вернувший половину по контракту родителя, падает. Классика: квадрат как наследник прямоугольника с независимыми сеттерами.

  • UnsupportedOperationException в override — почти всегда нарушение.
  • Исправление — отдельный интерфейс для возможности.
  • Значимое поле в подклассе ломает симметрию equals.

Какие ошибки наследования есть в самом JDK?

Stack наследует Vector, поэтому у стека есть вставка и удаление по индексу — LIFO можно сломать. Properties наследует Hashtable<Object, Object>: put кладёт любое значение, а getProperty для не-строки возвращает null. Правильнее было бы содержать вектор или таблицу внутри. Вместо Stack сегодня используют ArrayDeque.

  • java.sql.Timestamp extends Date нарушает симметрию equals.

Как проектировать класс, от которого будут наследоваться?

Документировать самоиспользование — какие переопределяемые методы вызываются и когда. Не вызывать переопределяемые методы из конструктора. Открывать продуманные точки расширения — protected-шаги шаблонного метода, — остальное делать final. Если наследование не предусмотрено — класс final или закрытый конструктор с фабрикой.

  • @implSpec в Javadoc JDK описывает самоиспользование.
  • Sealed-классы ограничивают наследников явным списком.
