Sorting in Java

Сортировка в Java начинается с двух решений: какой порядок нужен и какие данные можно менять. Стабильность сохраняет входной порядок равных элементов, а второй ключ задаёт порядок между ними. Затем имеет смысл выбирать реализацию: сортировка объектов учитывает уже упорядоченные участки, примитивы идут другим путём, а параллельная сортировка расходует память и общий пул потоков. Имена алгоритмов объясняют цену операции; требуемый результат задают API и компаратор.

Сортируя представление массива, сервис меняет сам массив

Сервис сверки получил платежи в порядке поступления. Для отчёта суммы нужны по возрастанию, а журнал должен сохранить исходный порядок. Разработчик оборачивает массив в Arrays.asList и сортирует «список для отчёта». После этого порядок в журнале тоже меняется. У массива и списка общее хранилище элементов.

Примеры этого и следующих шагов — фрагменты SortingDemo.java. Запуск: java examples/java-sorting/SortingDemo.java на JDK 21. Платёж хранит сумму в целых единицах; буква — его идентификатор. Ниже общая обвязка, чтобы по выводу было видно, какие платежи переставились.

record Payment(String id, int amount) {
    @Override public String toString() { return id + ":" + amount; }
}
static Payment[] fixture() {
    return new Payment[]{new Payment("C", 200), new Payment("A", 100),
            new Payment("B", 200), new Payment("D", 100)};
}
static void report(String name, Runnable operation) {
    try { operation.run(); }
    catch (RuntimeException e) {
        System.out.println(name + ": " + e.getClass().getSimpleName());
    }
}

var byAmount = Comparator.comparingInt(Payment::amount);
Payment[] original = fixture();
List<Payment> view = Arrays.asList(original); // Хранит переданный массив.
view.sort(byAmount);                        // Переставляет его элементы.
System.out.println("array after view.sort: " + Arrays.toString(original));
report("view.add", () -> view.add(new Payment("E", 50)));

List<Payment> immutable = List.of(fixture()); // Этот список менять нельзя.
report("List.of.sort", () -> immutable.sort(byAmount));
List<Payment> copy = new ArrayList<>(immutable); // Копия набора ссылок.
copy.sort(byAmount);
System.out.println("sorted copy: " + copy);
System.out.println("original list: " + immutable);
array after view.sort: [A:100, D:100, C:200, B:200]
view.add: UnsupportedOperationException
List.of.sort: UnsupportedOperationException
sorted copy: [A:100, D:100, C:200, B:200]
original list: [C:200, A:100, B:200, D:100]

Фиксированный размер и запрет изменений — разные свойства. Arrays.asList допускает замену элементов и сортировку, но не добавление нового слота. List.of запрещает и перестановку. Метод List.sort требует возможности заменять элементы; увеличивать размер ему не нужно.

В демо платежи — неизменяемые record, поэтому поверхностной копии достаточно. Для общего изменяемого списка сама операция копирования тоже требует согласованного чтения: new ArrayList<>(shared) не создаёт атомарный снимок, если другой поток одновременно меняет shared.

Диапазон задаётся правой границей, которая не входит в сортировку

int[] amounts = {999, 3, 1, 2, -999};
Arrays.sort(amounts, 1, 4); // Сортируются индексы 1, 2, 3. Края сохраняются.
System.out.println("range: " + Arrays.toString(amounts));
report("from>to", () -> Arrays.sort(amounts, 4, 1));
report("from<0", () -> Arrays.sort(amounts, -1, 2));
range: [999, 1, 2, 3, -999]
from>to: IllegalArgumentException
from<0: ArrayIndexOutOfBoundsException

Для sort(a, from, to) диапазон — [from, to). Пустой корректный диапазон допустим, to == a.length тоже допустимо. Отрицательная граница или граница за массивом — ошибка индекса. Обратный диапазон — ошибка аргументов. Такой интерфейс позволяет сортировать страницу внутри буфера, не трогая служебные элементы по краям.

Стабильность сохраняет входной порядок, а второй ключ задаёт новый

В отчёте суммы 100 должны идти раньше 200. Этого правила недостаточно, чтобы решить, какой из двух платежей по 200 показывать первым. Для компаратора по сумме платежи C и B равны. Стабильная сортировка оставит их в порядке поступления: сначала C. Сортировка по сумме и идентификатору поставит сначала B.

var byAmount = Comparator.comparingInt(Payment::amount);
Payment[] a = fixture(); // C:200, A:100, B:200, D:100.
Arrays.sort(a, byAmount); // compare(C, B) == 0; сохраняем их входной порядок.
System.out.println("stable: " + Arrays.toString(a));
a = fixture();
Arrays.sort(a, byAmount.thenComparing(Payment::id)); // Сначала сумма, затем id.
System.out.println("tie key: " + Arrays.toString(a));
stable: [A:100, D:100, C:200, B:200]
tie key: [A:100, D:100, B:200, C:200]

Равенство здесь означает compare(x, y) == 0, а не x.equals(y). Наши C:200 и B:200 — разные записи и разные платежи, но по первому компаратору равны. Стабильность — гарантия объектных Arrays.sort и List.sort. Она полезна при нескольких последовательных сортировках: сначала по младшему ключу, затем стабильной сортировкой по старшему. Одна цепочка thenComparing обычно яснее и делает меньше проходов.

Если входной порядок случайный, стабильный результат тоже будет зависеть от этого случая. Например, SQL-запрос без ORDER BY не задаёт порядок равных сумм. Для повторяемой выгрузки сервису нужен явный последний ключ, обычно уникальный id. Для сортировки событий по времени сначала задают createdAt, а id добавляют при совпадении времени. Стабильность сама не превращает входной список в хронологию.

Компаратор задаёт согласованный порядок на всех данных

Знак результата сравнения говорит «раньше», «равен» или «позже». Величина результата не важна. Сравнение должно менять знак при перестановке аргументов и быть транзитивным: если a < b и b < c, то a < c. Для равных по компаратору элементов сравнение с любым третьим должно иметь одинаковый знак. Иначе алгоритм не может построить согласованный отсортированный ряд.

report("natural Payment", () -> Arrays.sort(fixture())); // У record нет Comparable.
System.out.println("subtract MAX-(-1): " + (Integer.MAX_VALUE - (-1)));
System.out.println("compare MAX,-1: " + Integer.compare(Integer.MAX_VALUE, -1));
// (x, y) -> x.amount() - y.amount() может переполниться.
// comparingInt(Payment::amount) сравнивает int без вычитания.
natural Payment: ClassCastException
subtract MAX-(-1): -2147483648
compare MAX,-1: 1

Переполнение разворачивает порядок: максимальное положительное число вдруг оказывается меньше -1. Для long опасно ещё и приводить разность к int. Используй Integer.compare, Long.compare или comparingInt/comparingLong. Естественный порядок появляется только у типов с Comparable; объявление record его автоматически не создаёт.

Компаратор по статусу, который читает меняющийся объект или текущее время, может давать разные ответы для одной пары. Сортировка может обнаружить часть нарушений и бросить IllegalArgumentException, но это лишь частичная диагностика. Исключение — полезный симптом, успешный запуск — слабое доказательство корректности компаратора. Нужные для сравнения поля лучше зафиксировать до сортировки.

Объекты и примитивы сортируются разными способами

Объект хранит не только ключ, но и остальные данные платежа. Его положение среди равных ключей может иметь смысл, поэтому объектный API гарантирует стабильность. У двух одинаковых значений int нет различимого идентификатора: перестановку равных значений наблюдать нельзя. Для них JDK может выбрать иной алгоритм и иной расход памяти.

Это устройство OpenJDK 21, а не обязательные для всех будущих JDK имена алгоритмов. Выбирать по API стоит гарантии порядка, изменения данных и допустимости null. Обсуждать стоимость реализации — с названием версии. Не превращай знание TimSort в обещание, что любой сторонний List использует его: реализация списка может переопределить sort.

TimSort использует порядок, который уже есть

При последовательном просмотре TimSort ищет серии: участки по возрастанию или строго по убыванию. Убывающую серию разворачивает, короткую достраивает вставками. Полученные отсортированные серии складывает в стек и постепенно сливает. На случайных данных приходится работать со многими сериями. Полностью отсортированный массив уже является одной серией: сортировка почти целиком превращается в проверку соседей.

Integer[] ascending = new Integer[128], descendingValues = new Integer[128];
for (int i = 0; i < 128; i++) {
    ascending[i] = i;
    descendingValues[i] = 127 - i;
}
long[] count = {0};
Comparator<Integer> counted = (x, y) -> {
    count[0]++; // Последовательный вызов: считаем обращения к компаратору.
    return Integer.compare(x, y);
};
Arrays.sort(ascending, counted);
System.out.println("ascending: " + count[0]);
count[0] = 0;
Arrays.sort(descendingValues, counted);
System.out.println("descending: " + count[0]);
ascending: 127
descending: 127

Для 128 элементов достаточно 127 сравнений соседей, чтобы распознать одну серию. На убывающем массиве после этого переставляются ссылки, но дополнительные вызовы компаратора не нужны. Это наблюдение о работе алгоритма, а не измерение скорости в наносекундах.

Почему разворачивают только строго убывающую серию

Если развернуть [C:200, B:200, A:100] целиком, равные C и B поменяются местами. Это нарушило бы стабильность. Поэтому в возрастающую серию входят равные соседние элементы, а убывающая серия требует строгого уменьшения. При слиянии равных ключей раньше берётся элемент из более ранней серии.

Для слияния TimSort копирует меньшую из двух серий во временный буфер. Когда одна серия долго выигрывает сравнения, режим «галопирования» ищет границу сразу для нескольких элементов, вместо попеременного сравнения каждого. Правила стека удерживают размеры серий в таком соотношении, чтобы не сливать большую серию с крошечными снова и снова. В худшем случае работа занимает O(n log n), временное хранилище может дойти примерно до n/2 ссылок; на удачных входах расход меньше.

Почему Arrays.sort(int[]) нельзя приравнять к учебному Quick Sort

Учебная сортировка с последним опорным элементом может уйти в O(n²) на упорядоченном входе. В OpenJDK 21 DualPivotQuicksort выбирает ветви по размеру, распределению и глубине работы. Маленькие участки сортирует вставками, подходящие серии может сливать, а чрезмерную глубину прерывает Heap Sort. Схему одного разделения смотри в Quick Sort, построение кучи — в Heap Sort.

Даже примитивная сортировка JDK не означает «только перестановки и O(1) дополнительной памяти на любом входе»: некоторые ветви используют буфер для слияния. Для byte, short и char конечный диапазон значений позволяет применять подсчёт. Граница выбора — деталь реализации, которую не стоит переносить с одного типа массива на другой.

reversed разворачивает ровно тот порядок, который уже собран

Отчёт требует суммы по убыванию, идентификаторы по возрастанию, отсутствующие платежи в конце. Здесь три отдельных правила. Если собрать их все, а потом вызвать reversed(), развернутся все три: идентификаторы тоже пойдут по убыванию, а null переедет в начало.

var byAmount = Comparator.comparingInt(Payment::amount);
Comparator<Payment> descending = Comparator.nullsLast(
        byAmount.reversed().thenComparing(Payment::id)); // Развернули только сумму.
Payment[] nullable = {new Payment("B", 100), null,
        new Payment("A", 100), new Payment("C", 200)};
Arrays.sort(nullable, descending);
System.out.println("amount desc, id asc, null last: " + Arrays.toString(nullable));

Arrays.sort(nullable,
        Comparator.nullsLast(byAmount.thenComparing(Payment::id)).reversed());
System.out.println("whole comparator reversed: " + Arrays.toString(nullable));
amount desc, id asc, null last: [C:200, A:100, B:100, null]
whole comparator reversed: [null, C:200, B:100, A:100]

nullsLast сравнивает отсутствие объекта раньше, чем вызывает внутренний компаратор. Поэтому Payment::amount получает только реальные платежи. Если объект есть, но может отсутствовать его поле, обёртка нужна на уровне поля: например, comparing(Payment::id, nullsLast(naturalOrder())). Обёртка всего объекта не защитит от null внутри id.

Сортировка не очищает данные. Без подходящей обёртки естественный порядок или извлечение поля из null может дать NullPointerException. Для платёжного отчёта часто лучше заранее отвергнуть отсутствие обязательного платежа. Компаратор с nullsLast подходит, если пустое значение имеет осмысленное место в результате.

У чисел с плавающей точкой тоже есть заданный полный порядок

double[] special = {Double.NaN, 0.0, -0.0, Double.NEGATIVE_INFINITY, 2.0};
Arrays.sort(special);
System.out.println(Arrays.toString(special));
[-Infinity, -0.0, 0.0, 2.0, NaN]

Для сортировки double[] значение -0.0 идёт перед +0.0, а NaN — после числовых значений. Это отличается от обычных проверок < и ==: сравнения с NaN ими не образуют нужный порядок. Для компаратора обёрток используй Double.compare или comparingDouble. Денежные суммы в сервисе по-прежнему лучше сравнивать как целые минимальные единицы или подходящий десятичный тип: порядок сортировки не исправляет ошибки представления денег.

parallelSort делит работу, но остаётся клиентом общего пула

Для большой выгрузки хочется добавить слово parallel и получить ускорение. Параллельная сортировка сначала должна разделить диапазон, затем отсортировать части, затем слить их. Создание задач и движение данных стоят времени. Компаратор может выполняться одновременно в разных потоках, а сортировка конкурирует за общий пул с другими задачами сервиса.

В объектной реализации OpenJDK 21 диапазон до 8192 элементов включительно сортируется последовательно. При ForkJoinPool.getCommonPoolParallelism() == 1 последовательная ветка выбирается и для большого массива. Иначе размер частей зависит от размера диапазона и параллелизма пула. Эти числа относятся к объектной ветке JDK 21: переносить их на int[] или другую версию нельзя.

Схема показывает уровни зависимостей. На реальном выполнении одна пара может начать сливаться, пока другая ещё сортируется. Важен порядок для каждой ветви: слияние ждёт готовности обеих входных серий. Общий пул предоставляет исполнителей, а буфер — место для слияния. Объектов платежей не копируют: копируют ссылки.

Запуск показывает, какая ветка действительно работала

Полный ParallelSortDemo.java ниже. Каждый id совпадает с входным индексом. Поэтому возрастание id внутри равных сумм проверяет сохранение входного порядка. Потоки записываем в потокобезопасное множество: обычный HashSet внутри компаратора сделал бы само наблюдение ошибочным.

import java.util.*;
import java.util.concurrent.*;

public class ParallelSortDemo {
    record Payment(int id, int amount) {}
    static void run(int size) {
        Set<String> threads = new ConcurrentSkipListSet<>();
        var random = new SplittableRandom(42);
        Payment[] a = new Payment[size];
        for (int i = 0; i < size; i++) a[i] = new Payment(i, random.nextInt(10));
        Comparator<Payment> comparator = (x, y) -> {
            threads.add(Thread.currentThread().getName());
            return Integer.compare(x.amount, y.amount); // Ответ не зависит от потока.
        };
        Payment[] explicitOrder = a.clone();
        Arrays.parallelSort(a, comparator);
        boolean ordered = true, stable = true;
        for (int i = 1; i < size; i++) {
            ordered &= a[i - 1].amount <= a[i].amount;
            if (a[i - 1].amount == a[i].amount) stable &= a[i - 1].id < a[i].id;
        }
        if (!ordered) throw new AssertionError("order");
        System.out.println("n=" + size + " ordered=" + ordered + " stable=" + stable);
        System.out.println("comparison threads=" + threads);
        Arrays.parallelSort(explicitOrder, Comparator.comparingInt(Payment::amount)
                .thenComparingInt(Payment::id)); // Задаём второй ключ явно.
        boolean idsAscending = true;
        for (int i = 1; i < size; i++) {
            if (explicitOrder[i - 1].amount == explicitOrder[i].amount)
                idsAscending &= explicitOrder[i - 1].id < explicitOrder[i].id;
        }
        if (!idsAscending) throw new AssertionError("explicit tie key");
        System.out.println("explicit id order=" + idsAscending);
    }
    public static void main(String[] args) {
        System.out.println("common parallelism=" + ForkJoinPool.getCommonPoolParallelism());
        run(8192);
        run(32768);
    }
}

Реальный запуск на JBR 21.0.11+10 с явным параллелизмом общего пула:

java -Djava.util.concurrent.ForkJoinPool.common.parallelism=2 examples/java-sorting/ParallelSortDemo.java
common parallelism=2
n=8192 ordered=true stable=true
comparison threads=[main]
explicit id order=true
n=32768 ordered=true stable=false
comparison threads=[ForkJoinPool.commonPool-worker-1, ForkJoinPool.commonPool-worker-2, main]
explicit id order=true

Размер 8192 остался в последовательной ветке. При 32768 сравнения выполнялись и в вызывающем потоке, и в рабочих потоках общего пула. Их точные имена и участие зависят от планировщика; это снимок запуска, а не обещание использовать каждый рабочий поток.

stable=false в этом запуске — нарушение гарантии API. Документация объектного Arrays.parallelSort обещает стабильность. В OpenJDK зарегистрирована JDK-8076446: параллельное слияние может менять порядок равных элементов. Наш корректный компаратор воспроизводит эту проблему в указанной сборке. Это не основание учить, что parallelSort «по определению нестабилен».

Если отчёт требует сохранения входного порядка, последовательный объектный Arrays.sort решает эту задачу. Если результат должен задаваться бизнес-ключами, добавь их в компаратор. В нашем примере id одновременно задаёт второй ключ и совпадает с входным индексом; в другом сервисе эти два порядка могут различаться. При смене JDK пример позволяет проверить именно нужный сценарий.

Теперь оставим тот же большой массив, но зададим параллелизм 1 до инициализации пула:

java -Djava.util.concurrent.ForkJoinPool.common.parallelism=1 examples/java-sorting/ParallelSortDemo.java
common parallelism=1
n=8192 ordered=true stable=true
comparison threads=[main]
explicit id order=true
n=32768 ordered=true stable=true
comparison threads=[main]
explicit id order=true

Для этих запусков слово parallel в имени метода не заставляет создавать параллельную работу. Менять глобальный параллелизм ради одного отчёта опасно: параметр затрагивает других пользователей общего пула. У самого Arrays.parallelSort нет аргумента для передачи отдельного пула.

Ускорение имеет смысл измерять на данных сервиса

Параллельная сортировка объектов использует до O(n) дополнительных ссылок для слияния. Если сервис сначала скопировал исходный массив, а потом начал параллельную сортировку копии, в памяти могут одновременно жить исходные слоты, копия и рабочий буфер. При выгрузке миллионов платежей это влияет и на память, и на работу GC. Возможность выполнить задачу быстрее не означает возможность выполнить больше таких задач одновременно.

Не вызывай банк, базу или HTTP из компаратора: один элемент может сравниваться много раз, а в параллельной ветке — одновременно. Сначала получи нужные ключи, затем сравнивай локальные неизменяемые данные. То же касается дорогого разбора строки даты: подготовленный ключ часто даёт больший выигрыш, чем дополнительные потоки.

Сравнивать sort и parallelSort стоит на одинаковых свежих входах, с учётом размера, числа повторов, готовых серий и конкурирующей нагрузки. Повторная сортировка уже отсортированного массива измеряет другой сценарий. Для измерения коротких операций нужен корректный прогрев и инструмент вроде JMH; два вызова nanoTime в демонстрации механизма не дают надёжной рекомендации для прода.

Если нужны только несколько крупнейших платежей, полная сортировка может быть лишней: куча размера k или выбор элемента дают другую цену. Если выгрузка уже читается из БД, сначала проверь, может ли нужный порядок и ограничение объёма дать запрос с индексом. Алгоритмы этих вариантов разобраны в соседних темах; API сортировки полезен для диапазона, который действительно нужно целиком упорядочить в памяти.

  • Arrays.sort меняет массив, List.sort меняет список. Arrays.asList разделяет слоты с переданным массивом; копия списка отделяет порядок, но сохраняет ссылки на объекты.
  • Стабильность сохраняет входной порядок при compare == 0. Для заданного порядка равных сумм нужен следующий ключ.
  • Согласованный компаратор сравнивает значения без переполнения, задаёт правила null и не читает меняющиеся во время сортировки ключи.
  • В JDK 21 объекты обычно сортирует TimSort, а примитивы — специализированные гибриды. Название алгоритма является деталью реализации.
  • parallelSort использует общий пул и рабочий буфер. Проверяй реальную ветку, требуемые гарантии и эффект на нагрузке сервиса.

На собеседовании

Чем отличаются Arrays.sort, List.sort и Collections.sort?

Arrays.sort переставляет элементы массива. Для примитивного массива сортируется само значение, для объектного — ссылка на объект. List.sort переставляет элементы списка и требует возможности заменять их. Добавлять элементы ему не нужно, поэтому список фиксированного размера из Arrays.asList подходит, а List.of — нет.

Collections.sort — удобный вход для списка, который в современной JDK делегирует в List.sort. Я выбираю API по типу данных и по тому, можно ли менять вход. Для отдельного отчёта сначала делаю копию, если исходный порядок нужен другим частям сервиса.

  • Метод List.sort по умолчанию сортирует массив-копию и записывает результат итератором. Это защищает связный список от многократного дорогого доступа по индексу; ArrayList переопределяет метод и сортирует свой внутренний массив.
  • Поверхностная копия коллекции не изолирует изменяемые поля объектов. Для воспроизводимого отчёта иногда нужен отдельный снимок ключей, а не только копия слотов.
  • Сортировку общего массива или списка надо согласовывать с читателями. Контроль modCount у ArrayList помогает обнаружить часть конфликтов, но не превращает операцию в потокобезопасную транзакцию.

Что значит «стабильная сортировка»? Заменяет ли она thenComparing?

Стабильная сортировка сохраняет входной порядок элементов, для которых компаратор вернул ноль. У двух платежей с одной суммой могут быть разные id, но компаратор по сумме считает их равными. Объектные Arrays.sort и List.sort оставят их в прежнем порядке.

thenComparing задаёт дополнительное правило. Если мне нужны сумма и затем id, я явно собираю эту цепочку. Стабильность полезна, когда входной порядок уже имеет смысл; случайный порядок чтения из базы она не делает осмысленным.

  • Можно сначала сортировать по младшему ключу, а затем стабильной сортировкой по старшему. Это работает благодаря сохранению порядка равных групп, но единый компаратор обычно яснее.
  • Для пагинации и повторяемой выгрузки последний ключ должен различать строки, например уникальный id. Иначе добавление или удаление равной строки может менять границы страниц независимо от стабильности сортировки.
  • API объектного parallelSort тоже обещает стабильность. Наблюдаемое нарушение в конкретной JDK — ошибка реализации, как в нашем воспроизведении JDK-8076446; его надо отделять от правильного ответа о гарантиях API.

Какие ошибки в Comparator ломают сортировку?

Частая ошибка — вернуть разность чисел: она может переполниться и дать неправильный знак. Я использую compare или comparingInt/comparingLong. Затем проверяю транзитивность, симметрию знака и поведение равных элементов. Компаратор должен задавать один порядок на всех входных данных.

Отдельно задаю null и направление каждого ключа. reversed на готовой цепочке разворачивает всё, включая второй ключ и расположение null. Ещё компаратор должен давать постоянный ответ для одной пары во время сортировки: читать меняющийся статус из сервиса здесь опасно.

  • Равенство по компаратору может отличаться от equals. Для сортировки платежей только по сумме это допустимо; для TreeSet тот же компаратор означает, что второй платёж с равной суммой не добавится как отдельный элемент. Смысл compare == 0 зависит от потребителя.
  • Метод сравнения может вызываться многократно и в разных потоках. Извлечение дорогих ключей лучше выполнить заранее; побочные эффекты внутри компаратора требуют отдельного обоснования.
  • Нарушение порядка может привести к IllegalArgumentException, но отсутствие исключения не подтверждает весь контракт. Особенно важны граничные числа, равные ключи и сравнение каждой пары в обе стороны.
Две задачи требуют противоположного порядка null. Можно ли заменить сортировку по убыванию на «отсортировать по возрастанию и развернуть список»?

Только если действительно требуется разворот всех правил. При развороте готового списка null из конца попадут в начало, а порядок внутри равных групп тоже развернётся. Если суммы должны идти по убыванию, id по возрастанию и null в конце, правильнее сразу задать эти три условия компаратором. Разворот списка не является стабильной заменой смене направления одного ключа.

Какие алгоритмы использует Java и когда имеет смысл parallelSort?

В обычном режиме OpenJDK 21 объектный Arrays.sort использует стабильный TimSort: ищет готовые упорядоченные серии и сливает их. Поэтому уже отсортированные данные могут обрабатываться почти линейно. Для int[] работает гибрид Dual-Pivot Quicksort с дополнительными ветвями; для других примитивов выбор может отличаться.

parallelSort делит диапазон и сливает отсортированные части с участием общего ForkJoinPool. Для большого массива это может помочь, но на небольшом входе цена задач и слияния съест выигрыш. В сервисе я смотрю ещё на рабочую память, стоимость компаратора и конкуренцию за пул.

  • Порог 8192 относится к объектной ветке JDK 21. При parallelism == 1 даже большой объектный массив идёт по последовательному пути; число задач не равно числу потоков.
  • TimSort хранит серии и временный буфер для слияния. Для примитивной сортировки OpenJDK 21 тоже нельзя обещать одну постоянную оценку дополнительной памяти: распознавание серий может включать буферизованную ветку.
  • Сравнение вариантов должно учитывать одинаковые свежие данные и нагрузку соседей. Если нужно только k лучших элементов, сначала рассмотрю выбор или ограниченную кучу, а не ускорение полной сортировки.

  • List.sort и Comparator: запись результата в список, порядок сравнения, nullsLast, reversed и thenComparing.
  • Исходники OpenJDK 21: TimSort, DualPivotQuicksort, ArraysParallelSortHelpers. Смотри распознавание серий, Heap Sort при глубокой рекурсии и движение ссылок между массивом и буфером.

  • Команды запуска двух демо; Merge Sort, Quick Sort, Heap Sort — устройство базовых алгоритмов.
