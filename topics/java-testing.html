Java: Testing

Автоматический тест запускает выбранный путь программы и сравнивает наблюдаемое поведение с договором. JUnit управляет запуском и жизненным циклом, AssertJ формулирует утверждения, Mockito заменяет нужных соседей, Testcontainers добавляет настоящую инфраструктуру. Полезность теста определяется тем, какую ошибку он способен отличить от правильного результата, и какой код действительно вошёл в его путь.

Зелёный тест защищает только то утверждение, которое ты написал

Платёж на 101 цент должен получить комиссию 2% с округлением вверх до целого цента: 3. После правки в production-функции осталось деление на 50, и комиссия стала 2. Тест вызвал функцию, получил положительное число и позеленел. Запуск кода прошёл, но правило округления никто не проверил.

Тест состоит из arrange, act, assert: создаёт условия, выполняет действие и проверяет его наблюдаемый результат. Oracle — правило, которое решает, допустим ли результат. Здесь expected 3 следует из требования, а не из повторной копии того же деления внутри теста. Иначе одинаковая ошибка в двух формулах останется зелёной.

// Проверенный FeePolicy.java; imports опущены.
public final class FeePolicy {
    public long cents(long amount) {
        if (amount <= 0) throw new IllegalArgumentException("amount must be positive");
        // 2%, ceiling to a whole cent. Division before addition avoids amount+49 overflow.
        return amount / 50 + (amount % 50 == 0 ? 0 : 1);
    }
}
// Фрагмент FeePolicyTest, oracle намеренно слабый.
@Test void weakOracleAcceptsTheRoundingBug() {
    assertThat(fees.cents(101)).isPositive(); // even a buggy floor result 2 passes
}

Это версии эксперимента. verify.py работает в новой копии, запускает 27 unit invocation и три SQL-теста PostgreSQL, затем меняет только в отдельной mutant-копии формулу на return amount / 50;. У unit-теста граница определяется выполненным кодом, а не суффиксом Test. Дальше мы проверим PaymentService с настоящей политикой комиссии и fixed Clock, но с заменой банка и fake-списком вместо БД. Он защитит правило «при отказе не сохранять», но не проверит SQL и HTTP-контракт банка. Их требуется наблюдать в других проверках.

Jupiter исполняет каждую invocation внутри своего жизненного цикла

@Test — описание метода для engine, а не самостоятельная команда запуска. IDE, Surefire или Gradle обращаются к JUnit Platform; launcher выбирает TestEngine и строит test plan. Jupiter задаёт аннотации, parameterized tests и extension model. Его API нужен для компиляции, engine — для discovery и исполнения. Vintage служит старым JUnit 3/4 тестам и не запускает Jupiter вместо него.

В POM демо junit-jupiter подключает API, params и engine, а junit-bom 5.11.4 согласует версии Jupiter 5.11.4 и Platform 1.11.4. Убрали только engine JAR из runtime classpath, оставив API, launcher и тестовые классы. При фактическом discovery получили:

// Проверенный DiscoveryProbe.java; imports опущены.
public class DiscoveryProbe {
    public static void main(String[] args) {
        try {
            var launcher = LauncherFactory.create();
            var request = LauncherDiscoveryRequestBuilder.request().selectors(selectClass(FeePolicyTest.class)).build();
            launcher.discover(request); // actual engine lookup can be deferred until discovery
            System.out.println("launcher=" + launcher.getClass().getSimpleName());
        } catch (RuntimeException e) {
            System.out.println(e.getClass().getSimpleName() + ": " + e.getMessage());
        }
    }
}

Само LauncherFactory.create() в нашем запуске ещё вернуло ленивую обёртку. Пример вызывает discover, чтобы действительно потребовать engine. Аналогично зелёная сборка без найденных тестов не подтверждает их выполнение: проверяй число invocation, фильтры, naming convention и отчёты, а не только цвет команды.

Стандартный lifecycle Jupiter — PER_METHOD: каждая test invocation получает новый экземпляр тестового класса. @BeforeEach и @AfterEach относятся к каждой invocation, включая каждый набор параметров. @BeforeAll/@AfterAll относятся к классу и при PER_METHOD обычно static. Новый экземпляр очищает поля объекта, но не static-поля, singleton, файловую систему или базу.

// Проверенный LifecycleTest.java; imports опущены.
@TestMethodOrder(MethodOrderer.OrderAnnotation.class) // ONLY to make this teaching trace stable
class LifecycleTest {
    static int nextInstance;
    static int shared;
    final int instance = ++nextInstance;
    int local;
    @BeforeAll static void beforeAll() { System.out.println("lifecycle: beforeAll"); }
    @BeforeEach void beforeEach() {
        System.out.printf("beforeEach instance=%d local=%d shared=%d%n", instance, local, shared);
    }
    @Order(1) @ParameterizedTest @ValueSource(ints={7, 8})
    void eachInvocationIsANewInstance(int input) {
        assertThat(local).isZero();
        System.out.printf("body input=%d instance=%d%n", input, instance);
        local++; shared++;
    }
    @Order(2) @Test void fieldFreshButStaticRemains() {
        assertThat(local).isZero();
        assertThat(shared).isEqualTo(2);
        System.out.printf("body final instance=%d local=%d shared=%d%n", instance, local, shared);
    }
    @AfterEach void afterEach() { System.out.printf("afterEach instance=%d local=%d%n", instance, local); }
    @AfterAll static void afterAll() { System.out.println("lifecycle: afterAll"); }
}

@TestMethodOrder и @Order нужны здесь только для читаемой трассы. По умолчанию порядок методов не следует читать как порядок объявления в исходнике; независимые проверки проходят в любом порядке. Последний метод получил #3 и local=0, но shared=2 — это причина, по которой «новый объект на тест» не равно «всё состояние чистое».

При PER_CLASS экземпляр один, и BeforeAll разрешён как instance-метод. Это удобно для дорогой локальной фикстуры, но её изменяемые поля нужно возвращать в исходное состояние между invocation. Вторая параметризованная invocation ниже уже начинает с local=1:

// Проверенный SharedLifecycleTest.java; imports опущены.
@TestInstance(TestInstance.Lifecycle.PER_CLASS)
class SharedLifecycleTest {
    int local;
    @BeforeAll void beforeAll() { System.out.println("PER_CLASS beforeAll local=" + local); }
    @BeforeEach void beforeEach() { System.out.println("PER_CLASS beforeEach local=" + local); }
    @ParameterizedTest @ValueSource(ints={1,2})
    void bothInvocationsShareTheField(int ignored) {
        assertThat(local).isLessThan(2);
        local++;
    }
    @AfterAll void afterAll() {
        assertThat(local).isEqualTo(2);
        System.out.println("PER_CLASS afterAll local=" + local);
    }
}

Как extensions попадают в тот же цикл

@ExtendWith(MockitoExtension.class) регистрирует callback, создающий @Mock до тела теста и проверяющий strict stubs после него. Testcontainers extension управляет полями @Container вокруг методов или класса. Ты можешь создать собственный extension для ресурса или ParameterResolver, но он должен закрывать ресурс на своей границе жизни. @Mock сам по себе, без extension или явной инициализации, не выполняет Mockito.

@Nested группирует сценарии с общими условиями; он не отменяет lifecycle внешнего класса. @DisplayName влияет на читаемость отчёта, @Tag — на выбор тестов. @Disabled пропускает тест, assumption прерывает его как aborted; ни один из этих исходов не означает, что assert проверил договор.

Параметры выбирают случаи, assertion задаёт точный смысл результата

Комиссия меняется на границе кратности 50. Один happy path не различает floor и ceiling, поэтому тестируются 49/50/51, 100/101, минимальная сумма и long max. Для каждой пары input/expected Jupiter создаёт отдельную invocation; before/after hooks выполняются для неё заново. Ошибка одного набора видна под его display name и не скрывает остальные.

// Проверенный FeePolicyTest.java; imports опущены.
class FeePolicyTest {
    final FeePolicy fees = new FeePolicy();

    @ParameterizedTest(name = "{0} cents -> fee {1}")
    @CsvSource({"1,1", "49,1", "50,1", "51,2", "100,2", "101,3",
                "9223372036854775807,184467440737095517"})
    void roundsUpWithoutOverflow(long amount, long expected) {
        // Oracle is a specified constant, not a copy of the production formula.
        assertThat(fees.cents(amount)).as("fee for %s", amount).isEqualTo(expected);
    }

    @ParameterizedTest
    @ValueSource(longs = {0, -1})
    void rejectsInvalidAmount(long amount) {
        assertThatThrownBy(() -> fees.cents(amount))
                .isInstanceOf(IllegalArgumentException.class).hasMessage("amount must be positive");
    }

    @Test void weakOracleAcceptsTheRoundingBug() {
        assertThat(fees.cents(101)).isPositive(); // even a buggy floor result 2 passes
    }
}

У parameterized tests должен быть модуль params. @ValueSource удобен для одного аргумента; CsvSource — для небольших таблиц, MethodSource — для объектов и сложных случаев. Обычный MethodSource при PER_METHOD является static, при PER_CLASS может быть instance. NullSource/EmptySource помогают проверить соответствующие входы поддерживаемых ссылочных типов; примитивный long не принимает null.

AssertJ делает contract читаемым через цепочку assertions и полезные сообщения. as("fee for %s", amount) ставится до проверки, чтобы её ошибка получила описание. Но fluent стиль не выбирает правильную семантику за тебя: isEqualTo BigDecimal учитывает scale через equals, isEqualByComparingTo сравнивает числовое значение. Для коллекции exact-order и any-order тоже означают разные договоры.

// Проверенный AssertionsTest.java; imports опущены.
class AssertionsTest {
    @Test void preemptiveTimeoutChangesTheThreadLocalScope() {
        var context = new ThreadLocal<String>();
        context.set("TX");
        try {
            String same = assertTimeout(Duration.ofSeconds(1), context::get);
            String other = assertTimeoutPreemptively(Duration.ofSeconds(1), context::get);
            assertThat(same).isEqualTo("TX");
            assertThat(other).isNull();
            System.out.println("timeout same-thread=TX; preemptive other-thread=null");
        } finally { context.remove(); }
    }
    @Test void chosenEqualityChangesTheContract() {
        var amount = new BigDecimal("2.0");
        assertThat(amount).isEqualByComparingTo("2.00");
        var scaleFailure = assertThrows(AssertionError.class,
                () -> assertThat(amount).isEqualTo(new BigDecimal("2.00")));
        System.out.println("BigDecimal numeric comparison=pass, equals(scale)=AssertionError");
        assertThat(scaleFailure).hasMessageContaining("2.00");
        var rows = List.of("P2", "P1");
        assertThat(rows).containsExactlyInAnyOrder("P1", "P2");
        assertThrows(AssertionError.class, () -> assertThat(rows).containsExactly("P1", "P2"));
        System.out.println("rows any-order=pass, ordered=AssertionError");
    }
    @Test void softAssertionsNeedATerminalCheck() {
        var soft = new SoftAssertions();
        soft.assertThat(new FeePolicy().cents(101)).as("fee").isEqualTo(2);
        soft.assertThat("APPROVED").as("status").isEqualTo("DECLINED");
        System.out.println("soft collected=2; before assertAll no exception");
        var failure = assertThrows(AssertionError.class, soft::assertAll);
        assertThat(failure).hasMessageContaining("fee").hasMessageContaining("status");
        System.out.println("soft assertAll=AssertionError");
    }
}

Это реальный stdout AssertionsTest. Ошибки equals и ordered comparison намеренно перехвачены assertThrows: тест доказывает выбранную семантику и сам проходит. Обычные assertions fail fast; SoftAssertions собирает ошибки, но должен дойти до assertAll. Забытая завершающая проверка оставляет метод зелёным. assertSoftly или SoftAssertionsExtension выполняют финальную проверку за тебя.

Проверяй у исключения нужный тип, message, cause или domain code, а не просто «бросилось что-то». JUnit assertThrows принимает и подклассы ожидаемого типа, assertThrowsExactly требует точное совпадение. В assertThatThrownBy передавай узкое действие, которое должно упасть: ошибка arrange внутри той же lambda может ложно подтвердить ожидаемый исход. ThreadLocal-проба в этом же классе ещё покажет границу preemptive timeout в последнем шаге.

Mock банка управляет внешним исходом, настоящее правило остаётся под тестом

PaymentService сначала проверяет сумму и считает fee, затем вызывает bank.charge и сохраняет Receipt только при true. Замена банка делает test независимым от его доступности и позволяет точно получить approval, decline или timeout. Если заменить mock-ом сам FeePolicy, тест больше не проверит вычисление комиссии, ради которого написан.

// Проверенный PaymentService.java; imports опущены.
public final class PaymentService {
    public record Receipt(String id, long amount, long fee, Instant at) {}
    public interface Bank { boolean charge(String id, long amount); }
    public interface Repository { void save(Receipt receipt); }
    public static final class Declined extends RuntimeException {
        public Declined() { super("bank declined"); }
    }
    private final FeePolicy fees;
    private final Bank bank;
    private final Repository repository;
    private final Clock clock;
    public PaymentService(FeePolicy fees, Bank bank, Repository repository, Clock clock) {
        this.fees = fees; this.bank = bank; this.repository = repository; this.clock = clock;
    }
    public Receipt pay(String id, long amount) {
        Objects.requireNonNull(id, "id");
        long fee = fees.cents(amount); // real policy validates BEFORE external charge
        if (!bank.charge(id, amount)) throw new Declined();
        var receipt = new Receipt(id, amount, fee, clock.instant());
        repository.save(receipt);
        return receipt;
    }
}

Зависимости переданы конструктору явно. Clock фиксирует время, repository-лямбда кладёт Receipt в ArrayList, Bank создан через MockitoExtension. Возвращаемое значение и сохранённое состояние проверяются AssertJ; verify наблюдает важное внешнее действие. verify(bank) по умолчанию ожидает один подходящий вызов. Валидация доказывает отсутствие эффекта на банковской границе, поэтому здесь оправдан verifyNoInteractions.

// Проверенный PaymentServiceTest.java; imports опущены.
@ExtendWith(MockitoExtension.class)
class PaymentServiceTest {
    @Mock Bank bank;
    final ArrayList<Receipt> saved = new ArrayList<>(); // fake state, not PostgreSQL
    final Clock clock = Clock.fixed(Instant.parse("2026-10-10T00:00:00Z"), ZoneOffset.UTC);
    PaymentService service() { return new PaymentService(new FeePolicy(), bank, saved::add, clock); }

    @Test void approvedReceiptHasTheRealFeeAndTime() {
        when(bank.charge("P7", 101)).thenReturn(true);
        var receipt = service().pay("P7", 101);
        assertThat(receipt).isEqualTo(new Receipt("P7", 101, 3, clock.instant()));
        assertThat(saved).containsExactly(receipt);
        verify(bank).charge("P7", 101); // effect at the outgoing bank boundary
        System.out.println("approved: fee=3 saved=1 bank charge verified");
    }
    @Test void invalidAmountNeverChargesBank() {
        assertThatThrownBy(() -> service().pay("P7", 0)).isInstanceOf(IllegalArgumentException.class);
        verifyNoInteractions(bank);
        assertThat(saved).isEmpty();
        System.out.println("invalid: bank calls=0 saved=0");
    }
    @Test void declinedBankMustNotPersist() {
        when(bank.charge("P7", 101)).thenReturn(false);
        assertThatThrownBy(() -> service().pay("P7", 101)).isInstanceOf(Declined.class);
        assertThat(saved).isEmpty();
        System.out.println("declined: saved=0");
    }
    @Test void timeoutMustNotPersist() {
        when(bank.charge("P7", 101)).thenThrow(new IllegalStateException("timeout"));
        assertThatThrownBy(() -> service().pay("P7", 101)).hasMessage("timeout");
        assertThat(saved).isEmpty();
        System.out.println("timeout: saved=0");
    }
}

Stub задаёт ответ, verification проверяет, было ли обращение. Один Mockito mock умеет обе роли. Это не повод проверять каждым verify всю внутреннюю цепочку методов: такое требование делает тест чувствительным к рефакторингу без изменения результата. Когда договором является сохранённый Receipt, наблюдай Receipt; когда договором является единственная отправка в банк, наблюдай отправку.

@InjectMocks умеет подставить созданные mocks в объект через поддержанные способы injection, но не является Spring DI и не поднимает произвольный граф зависимостей. В демо конструктор прозрачно показывает real FeePolicy и Clock. Важную зависимость легче увидеть там, чем гадать, какое поле было автоматически оставлено null.

Если verify банка прошёл, интеграция с банком проверена.

Mockito проверил вызов Java-объекта с ожидаемыми аргументами. HTTP encoder, заголовки, разбор ответа и актуальность внешнего контракта в этот путь не вошли. Их проверяют на реальном клиенте с protocol stub или контрактным тестом.

ArgumentCaptor нужен, когда удобнее проверить уже переданный объект по нескольким полям. InOrder нужен, если порядок внешних эффектов входит в договор; порядок вызовов своих private helpers обычно не входит. Классификация fake/stub/mock/spy подробно разобрана в Test Doubles, а замена Spring beans — в Spring: Testing.

Настройка Mockito сама может выбрать неверную ветку или выполнить настоящий код

Ненастроенный mock не вызывает сеть и не знает, что хотел тест. Default answer возвращает подходящие значения: false для boolean, 0 для чисел, null для многих ссылок и пустые значения для ряда типов вроде коллекций/Optional. Поэтому забытый stub bank.charge выбирает Declined. Получить green test на «отказе» легко, даже если намерение было проверить успешное сохранение.

Strict stubbing помогает отличить актуальные условия от забытых. MockitoExtension использует STRICT_STUBS; явная MockitoSession ниже показывает UnnecessaryStubbingException при закрытии с неиспользованным stub. Strictness также диагностирует определённые несовпадения аргументов stubbing. lenient применяй к конкретному оправданному stub, а не ко всему набору, чтобы скрыть ошибку сценария.

// Проверенный MockitoTrapsTest.java; imports опущены.
class MockitoTrapsTest {
    @Test void unstubbedDefaultCanSelectABusinessBranch() {
        Bank bank = mock(Bank.class);
        var saved = new ArrayList<Receipt>();
        var service = new PaymentService(new FeePolicy(), bank, saved::add, Clock.systemUTC());
        assertThatThrownBy(() -> service.pay("P7", 101)).isInstanceOf(Declined.class);
        assertThat(saved).isEmpty();
        System.out.println("unstubbed boolean=false -> Declined");
    }
    @Test void unusedStubIsDetectedAtStrictSessionClose() {
        var session = mockitoSession().strictness(Strictness.STRICT_STUBS).startMocking();
        Bank bank = mock(Bank.class); // created while the strict session is active
        when(bank.charge("P7", 101)).thenReturn(true);
        assertThrows(UnnecessaryStubbingException.class, session::finishMocking);
        System.out.println("unused stub -> UnnecessaryStubbingException");
    }
    @Test void aSpyRunsTheMethodWhileWhenIsEvaluated() {
        List<String> spy = spy(new ArrayList<String>());
        assertThrows(IndexOutOfBoundsException.class, () -> when(spy.get(0)).thenReturn("P7"));
        doReturn("P7").when(spy).get(0); // no get(0) during setup
        assertThat(spy.get(0)).isEqualTo("P7");
        assertThat(spy).isEmpty(); // stub did not add an element
        System.out.println("spy when(get(0))=IndexOutOfBoundsException, doReturn=P7, size=0");
    }
    @Test void captorObservesArgumentsAndMatchersMustBeConsistent() {
        Bank bank = mock(Bank.class);
        assertThrows(InvalidUseOfMatchersException.class,
                () -> when(bank.charge(eq("P7"), 101)).thenReturn(true));
        when(bank.charge(eq("P7"), eq(101L))).thenReturn(true);
        assertThat(bank.charge("P7", 101)).isTrue();
        var id = ArgumentCaptor.forClass(String.class);
        verify(bank).charge(id.capture(), eq(101L));
        assertThat(id.getValue()).isEqualTo("P7");
        System.out.println("mixed matchers=InvalidUseOfMatchersException; captured id=P7");
    }
    @Test void inlineMakerCanStubFinalMethodsWithExplicitAgent() {
        var fees = mock(FeePolicy.class);
        when(fees.cents(101)).thenReturn(99L); // FeePolicy is final
        assertThat(fees.cents(101)).isEqualTo(99);
        System.out.println("final FeePolicy mock=99; real FeePolicy=3");
        assertThat(new FeePolicy().cents(101)).isEqualTo(3);
    }
}

В spy ненастроенные методы выполняют настоящий код. Выражение when(spy.get(0)) вызывает get до того, как when сможет записать stub, и пустой список бросает исключение. doReturn("P7").when(spy).get(0) настраивает ответ без такого вызова, но не добавляет элемент: size остался 0. Spy полезен для ограниченного legacy seam; избыточная частичная подмена часто означает, что граница зависимости не выделена.

Matchers записывают условия для всего обращения. Если один аргумент задан eq/any/capture, остальные также должны быть matcher, например eq(101L). Captor.capture в verify участвует в этом правиле. Точное значение без matcher допустимо, когда все аргументы обычные значения. any(Class) не является обещанием принять null; для null используй подходящий явный matcher.

В Mockito 5 inline maker стал default и поддерживает final классы/методы. Это проверено на final FeePolicy: mock вернул 99, real вернул 3. Старые пояснения «Mockito не умеет final» относятся к прежним режимам. На JDK 21 демо подключает Mockito Core явно как startup agent в тестовой JVM. Оно не полагается на автоматическое self-attach:

<!-- Фрагменты pom.xml: весь POM по ссылке. -->

  <groupId>org.apache.maven.plugins</groupId>

Static mocking, если оно требуется, ограничивают try-with-resources scope; после него возвращают обычное поведение. Создавать свежие mocks на тест понятнее, чем reset общего объекта и неясная история stubs.

Testcontainers добавляет настоящий SQL-путь, которого нет у mock

ArrayList fake сохранил Receipt, но production SQL может ссылаться на неверную колонку или нарушать constraint. В SQL-пробе поднимаем настоящий PostgreSQL 17.11 в Docker и выполняем PreparedStatement через JDBC driver 42.7.7. Здесь проверяем конкретный SQL и транзакционное поведение; весь PaymentService и настоящий банк в этот тест не включены.

JUnit extension находит @Container. Static поле запускается один раз до методов класса и останавливается после них; instance поле стартует и останавливается для каждого метода. Это жизненный цикл контейнера, а не очистка таблиц. Не объявляй static @Container в базовом классе как гарантию «один контейнер на весь suite»: разные тестовые классы и extension callbacks имеют собственные границы. Для всего suite нужен согласованный владелец singleton lifecycle.

Контейнерный порт отображается на назначенный host port. Используй getJdbcUrl/getHost/getMappedPort после start, а не localhost:5432 из памяти. Успешный start процесса и readiness приложения разные: профиль PostgreSQL ждёт готовности базы, для собственного GenericContainer задают подходящий Wait strategy. Thread.sleep не сообщает, что сервис действительно готов. Модуль БД не заменяет JDBC driver — в POM он подключён отдельно.

// Проверенный PaymentRepositoryIT.java; imports опущены.
@Testcontainers // fail when Docker is missing, don't silently disable these checks
class PaymentRepositoryIT {
    @Container static final PostgreSQLContainer postgres = new PostgreSQLContainer("postgres:17.11-alpine")
            .withDatabaseName("payments").withUsername("kb").withPassword("kb");

    Connection open() throws SQLException {
        // Read real mapped connection settings AFTER extension has started the container.
        var c = DriverManager.getConnection(postgres.getJdbcUrl(), postgres.getUsername(), postgres.getPassword());
        assertThat(c.getAutoCommit()).isTrue();
        assertThat(c.getTransactionIsolation()).isEqualTo(Connection.TRANSACTION_READ_COMMITTED);
        return c;
    }
    @BeforeEach void schemaAndCleanup() throws SQLException {
        try (var c = open(); var s = c.createStatement()) {
            s.execute("""
                    CREATE TABLE IF NOT EXISTS payment (
                      id text PRIMARY KEY,
                      amount bigint NOT NULL CHECK (amount > 0),
                      fee bigint NOT NULL CHECK (fee > 0)
                    )
                    """);
            s.execute("TRUNCATE payment"); // container reuse does not erase rows
            assertThat(count(c)).isZero();
        }
    }
    long insert(Connection c, String id, long amount) throws SQLException {
        try (var s = c.prepareStatement("INSERT INTO payment(id,amount,fee) VALUES (?,?,?) RETURNING fee")) {
            s.setString(1, id); s.setLong(2, amount); s.setLong(3, new FeePolicy().cents(amount));
            try (var r = s.executeQuery()) { r.next(); return r.getLong(1); }
        }
    }
    long count(Connection c) throws SQLException {
        try (var s = c.createStatement(); var r = s.executeQuery("SELECT count(*) FROM payment")) {
            r.next(); return r.getLong(1);
        }
    }
    @Test void executesRealSqlAndRejectsDuplicatePrimaryKey() throws Exception {
        try (var c = open()) { // JDBC default autocommit=true
            assertThat(insert(c, "P7", 101)).isEqualTo(3);
            var failure = Assertions.assertThrows(SQLException.class, () -> insert(c, "P7", 101));
            assertThat(failure.getSQLState()).isEqualTo("23505");
            assertThat(count(c)).isEqualTo(1);
            System.out.println("postgres: INSERT RETURNING fee=3, duplicate SQLState=23505, rows=1");
            try (var s = c.createStatement()) {
                var rejected = Assertions.assertThrows(SQLException.class,
                        () -> s.executeUpdate("INSERT INTO payment VALUES ('BAD',-1,1)"));
                assertThat(rejected.getSQLState()).isEqualTo("23514");
                System.out.println("postgres: amount CHECK SQLState=23514");
            }
        }
    }
    @Test void rollbackDoesNotUndoAnotherConnectionsCommit() throws Exception {
        try (var test = open(); var application = open()) {
            test.setAutoCommit(false);
            insert(test, "UNCOMMITTED", 101);
            assertThat(count(test)).isEqualTo(1);
            assertThat(count(application)).isZero();
            insert(application, "COMMITTED", 51); // independent autocommit
            assertThat(count(test)).isEqualTo(2); // READ COMMITTED sees the other commit on next SELECT
            test.rollback();
            assertThat(count(test)).isEqualTo(1);
            assertThat(count(application)).isEqualTo(1);
            System.out.println("postgres: test saw own row=1; other saw it=0; after test rollback committed rows=1");
        }
    }
    @Test void startsWithACleanDatabaseEvenInSharedContainer() throws Exception {
        try (var c = open()) {
            assertThat(count(c)).isZero();
            System.out.println("postgres: BeforeEach TRUNCATE -> rows=0");
        }
    }
}

postgres: INSERT RETURNING fee=3, duplicate SQLState=23505, rows=1
postgres: amount CHECK SQLState=23514
postgres: test saw own row=1; other saw it=0; after test rollback committed rows=1

Это весь PaymentRepositoryIT без imports. SQLState 23505 пришёл от настоящего primary key, 23514 — от CHECK; отказные statements в autocommit не уничтожили предыдущую committed строку. Тесты assert-ом подтвердили autocommit и READ COMMITTED у открываемых соединений. Реальный driver, SQL и база вошли в наблюдаемый путь, в отличие от Mockito Repository.

В Testcontainers 2 PostgreSQL-модуль называется testcontainers-postgresql, класс лежит в org.testcontainers.postgresql и не требует generic-параметра из старых 1.x примеров. В демо JUnit integration-модуль называется testcontainers-junit-jupiter. При недоступном Docker эти проверки падают: тихий skip сделал бы verify зелёным без обещанной SQL-защиты.

Репозиторий приложения отдельно тестируют его настоящим adapter-кодом и миграциями. H2 не становится PostgreSQL только от compatibility mode: другой SQL dialect, типы и transaction semantics меняют условия. Контейнер совпадающего семейства БД сокращает это расхождение, но его локальный диск и сеть не воспроизводят весь production кластер. Spring Data/JPA, контекст и @ServiceConnection разобраны в соседней Spring-теме.

Изоляция теста заканчивается на общем ресурсе и чужой транзакции

Static контейнер сохраняет базу между методами, а PER_METHOD создаёт только новый объект Java. В демо BeforeEach явно делает TRUNCATE и проверяет нулевой count. Без него состояние переживёт метод. При параллельном исполнении один тест мог бы удалить строки другого: эти SQL-тесты запускаются последовательно, и такое cleanup не пригодно для общего параллельного стенда.

В SQL-пробе test connection видит свою незавершённую строку, другое соединение не видит её. Второе соединение коммитит свою запись; следующий SELECT первого видит обе. Затем rollback убирает только первую строку. Ни JDBC, ни JUnit не обещают откатить чужую транзакцию. HTTP-запрос к серверу и фоновая задача обычно исполняются за другой границей; Spring test transaction рассмотрена в Spring: Testing.

Timeout тоже способен изменить границу. assertTimeout выполняет действие в текущем потоке и сообщает превышение после его возврата. Preemptive вариант исполняет действие в другом потоке и пытается прервать его по сроку. Он не переносит ThreadLocal и не гарантирует остановку некооперативного кода. В AssertionsTest текущий поток прочитал TX, другой — null. Это проверка thread scope, а не доказательство rollback конкретного Spring bean.

Для воспроизводимости важно, какие тесты выбрала сборка. В демо Surefire запускает обычные классы *Test в test, Failsafe — *IT в integration-test и проверяет итог в verify. Они не включаются одной случайной аннотацией: Failsafe executions записаны в POM. Драйвер подтвердил, что после mvn test каталога failsafe-reports нет, а после verify есть три выполненных SQL-метода, без skipped.

Проверяй XML counts, skip/abort и точку, в которой assertion был выполнен.

В CI фиксируют версии зависимостей и образа, readiness, входные данные и время; при диагностике сохраняют test reports и логи контейнера. «Could not find a valid Docker environment» означает проблему доступа к runtime, а не падение business assertion. Параллельные JVM-форки имеют отдельные static-поля, но способны делить внешнюю БД; совпадающие fixed ports и общие таблицы снова создадут конфликт. При async-коде ожидай наблюдаемое условие с дедлайном, а не «достаточно долгий sleep».

Unit oracle, mock и SQL-проба защищают разные гипотезы. Контракт реального банка, маршрутизация Spring, миграции всего сервиса и production delivery требуют собственных границ наблюдения. Выбор пропорции набора, мутации и flaky tests — в Testing Strategy; граф Maven/Gradle — в Maven & Gradle. Добавлять инструмент полезно там, где он даёт увидеть нужную ошибку.

  • Проверяй точный договор независимым oracle. Зелёная isPositive не защищает округление.
  • API позволяет скомпилировать аннотации; Platform и engine нужны для discovery и исполнения. Смотри число найденных и выполненных invocation.
  • PER_METHOD очищает поля экземпляра, но не static и внешние ресурсы. Parameterized tests проходят собственные before/after hooks.
  • Stub задаёт ответы соседа, verify наблюдает эффекты. Spy вызывает настоящий код; when может вызвать его уже при настройке.
  • Настоящий PostgreSQL проверяет SQL и ограничения; shared контейнер требует отдельного управления данными.
  • Rollback принадлежит транзакции, ThreadLocal — потоку. Failsafe, timeout и parallel execution способны изменить границу проверки.

На собеседовании

Из чего состоит JUnit 5 и как он создаёт и запускает тесты?

Я разделяю JUnit Platform и Jupiter. Platform запускает engine и строит план тестов для IDE или сборщика. Jupiter даёт @Test, параметризованные сценарии и extensions; его engine исполняет эти тесты. Vintage нужен, если в проекте остались JUnit 3/4. Один API JAR позволяет компиляцию, но не заменяет engine в runtime.

По умолчанию Jupiter создаёт новый экземпляр на test invocation. BeforeEach и AfterEach выполняются для каждой, включая каждый набор параметров; BeforeAll и AfterAll относятся к классу. Поэтому изменённое поле объекта не переходит в следующий тест, а static или база переходят. Для общего экземпляра есть PER_CLASS, но тогда я явно управляю очисткой его состояния.

  • BOM согласует API, engine и Platform; их major/minor номера различаются. Случайная смесь dependency versions может сломать discovery до business кода.
  • Создание launcher способно быть ленивым: в демо отсутствие engine выявлено при discover. Отдельно проверяю naming, tags и число invocation, чтобы пустой набор не выглядел защитой.
  • Extensions управляют ресурсами в callbacks; PER_CLASS позволяет instance BeforeAll. Порядок методов задают специально только там, где он часть сценария.
Один parameterized метод с двумя значениями: сколько BeforeEach и экземпляров?

При стандартном PER_METHOD — два BeforeEach, два AfterEach и два экземпляра. При PER_CLASS callbacks всё ещё два раза, экземпляр один. Static поле остаётся общим в обоих режимах. LifecycleTest и SharedLifecycleTest показывают это работающей трассой.

Как написать полезный параметризованный тест и что даёт AssertJ?

Я начинаю с правила и ошибки, которую тест должен различить. Выбираю обычный вход, обе стороны границы и недопустимые значения, а expected задаю независимо от реализации. Параметризованный метод запускает одну проверку на нескольких наборах; каждый набор имеет собственный lifecycle и имя в отчёте. Для маленькой таблицы беру CsvSource, для объектов MethodSource.

AssertJ позволяет выразить результат читаемой цепочкой: точное значение, элементы коллекции, поля и ожидаемое исключение. Важно выбрать договор, например учитывается ли порядок и scale BigDecimal. isPositive вместо точной комиссии пропускает неправильное округление. Ошибка assertion должна помогать понять, какой вход и какое требование нарушены.

  • SoftAssertions требует assertAll; иначе ошибки накоплены, но результат теста зелёный. Extension или assertSoftly обеспечивают завершение автоматически.
  • assertThrows принимает подкласс; assertThrowsExactly проверяет точный тип. Узкая lambda отделяет ошибку arrange от ожидаемой ошибки act.
  • containsExactlyInAnyOrder всё ещё проверяет состав и кратность. Для SQL без ORDER BY нельзя навязывать порядок, который query не обещает.
Почему expected по той же формуле не защищает правило? 
long expected = amount / 50;
assertThat(fees.cents(amount)).isEqualTo(expected);

Oracle повторяет ту же потенциально ошибочную формулу. Для 101 он и floor-реализация одинаково получат 2. Ожидаемое 3 следует из требований комиссии; отдельно нужны 49/50/51 и крайние значения. В isolated mutation сборке пять точных случаев поймали дефект при прошедшем isPositive.

Чем stubbing отличается от verification и что проверять Mockito?

Stubbing задаёт, что заменённый сосед вернёт или бросит. Verification проверяет, какие обращения к нему произошли. В тесте оплаты я задаю банку approval или timeout, оставляю настоящую комиссию и проверяю итоговый Receipt. Отдельно проверяю, что неверная сумма не вызвала charge, потому что это важный внешний эффект.

Мне не нужно verify для каждого внутреннего метода: это привязывает тест к реализации. Использую mock на контролируемой границе, наблюдаю результат или значимый эффект и проверяю переданные аргументы. Без stub boolean по умолчанию false; тест способен незаметно попасть в ветку отказа. Strict stubs помогают обнаружить неиспользованные условия.

  • MockitoExtension инициализирует @Mock и выполняет strict проверку; @InjectMocks не является контейнером DI. Прозрачный конструктор показывает, что именно осталось настоящим.
  • ArgumentCaptor наблюдает переданный аргумент после действия. Если есть matcher, остальные аргументы тоже задают matcher; InOrder нужен при договоре о порядке внешних эффектов.
  • verifyNoMoreInteractions на каждом mock делает тест хрупким. Использую отрицательную проверку там, где отсутствие вызова само является требованием.
Что означает UnnecessaryStubbingException?

В строгом scope был stub, который выполненный сценарий не использовал. Проверь вход, выбор ветки и точные аргументы; убери лишнюю подготовку. Это может быть реальный дефект теста, а не повод сразу включить lenient на всём классе. В демо ошибка получена при finishMocking явной session.

Чем mock отличается от spy и почему when на spy иногда падает?

Mock заменяет поведение: ненастроенные методы дают default ответы. Spy позволяет выполнять настоящие методы и подменить отдельные обращения. Когда я пишу when(spy.get(0)), Java сначала вызывает get. На пустом списке он бросает исключение ещё до настройки. Для такой ситуации использую doReturn, который задаёт stub без вызова метода при setup.

Spy не делает тест автоматически ближе к production: часть поведения всё равно подменена, а реальные методы могут выполнить нежелательный эффект. Обычно проще выделить зависимость и передать её через конструктор. Частичную подмену оставляю для ограниченного legacy seam и проверяю, что результат не появился только из stubbing.

  • Inline maker Mockito 5 поддерживает final методы/классы; старое универсальное ограничение устарело. В демо mock final FeePolicy вернул 99, реальный объект 3.
  • На JDK 21 startup javaagent явно обеспечивает instrumentation в forked тестовой JVM. Настройка Maven JVM не автоматически настройка IDE или другого runner.
  • Static mock ограничивают try-with-resources scope. Долгоживущая подмена глобального поведения мешает независимости соседних тестов.
После doReturn("P7").when(spy).get(0) появился ли элемент в списке?

Нет. get(0) вернул настроенный ответ, но список остался пустым: stub не выполнял add. Это одновременно проверено get и isEmpty в MockitoTrapsTest. У mock/spy нужно отличать возвращённое значение от реального состояния объекта.

Зачем Testcontainers и как управлять контейнерами и данными тестов?

Я использую Testcontainers, когда важна совместимость настоящего кода с внешней системой, например PostgreSQL SQL, constraints и транзакции. Mock репозитория или H2 этого не доказывает. Контейнер запускается через Docker, модуль ждёт готовности, а тест получает реальный JDBC URL и mapped port. Driver и schema подключаются отдельно.

В JUnit extension static @Container живёт на класс, instance @Container на метод. Shared container не очищает строки, поэтому управлять данными нужно явно: cleanup, отдельная схема или транзакция в подходящей границе. Если обработчик работает через другое соединение и коммитит, rollback тестового соединения его запись не уберёт.

  • Общий базовый static @Container не является универсальной гарантией singleton на suite. Владелец start/stop должен совпадать с нужной границей, особенно при нескольких классах.
  • Readiness не равно «процесс запустился», а host port не равно container port. Hardcoded 5432 и sleep делают тест зависимым от окружения.
  • JUnit integration Testcontainers документирует последовательный режим; TRUNCATE общей таблицы не даёт изоляцию параллельным тестам. Разные JVM-форки тоже могут конфликтовать на внешнем ресурсе.
Тест вставил U без commit, второе соединение закоммитило C. Что останется после rollback теста?

Только C. В READ COMMITTED собственное соединение видело U и после чужого commit увидело C; rollback отменил только его транзакцию. SQL-проба проверяет число строк через оба соединения. Откат не является глобальной очисткой базы.

Что стоит мокать в сервисе и как понять, что тест проверяет нужный путь?

Я выбираю границу под конкретную ошибку. Комиссию и другие детерминированные правила выполняю настоящими, время фиксирую Clock. Исход банка задаю заменой внешнего клиента; SQL проверяю настоящим adapter и базой. Если всё заменено mock-ами, можно подтвердить согласованность настроек вместо поведения сервиса.

Смотрю, какое утверждение увидит ошибку, и какие участки действительно выполнились. Verify на Java-интерфейсе не проверяет HTTP-контракт. Наличие контейнера не означает запуск всего приложения. Для отказа проверяю отсутствие сохранения, для approval — содержимое Receipt, для SQL — результат, ограничения и транзакцию. У каждого теста должна быть понятная гипотеза.

  • Preemptive timeout меняет поток и ThreadLocal scope. Он может вынести действие за тестовую транзакцию и не останавливает некорректно реагирующий на interrupt код гарантированно.
  • Surefire test и Failsafe verify выбирают разные имена и этапы. Проверяю reports, counts и skipped/aborted, чтобы green сборка не скрывала отсутствие нужных тестов.
  • После рефакторинга сохраняю наблюдаемый договор; внутренний порядок вызовов не фиксирую без причины. Стратегия всего набора выбирается по вероятным ошибкам, а не квоте mock-ов.
Почему сервис с mock FeePolicy вернул правильную комиссию при ошибке в FeePolicy?

Ожидаемую комиссию дал stub, а production политика в путь не вошла. Оставь FeePolicy настоящим и проверяй known input/expected; замени только внешний банк. Если проверяется исключительно оркестрация при заданном результате политики, такой mock допустим, но формула требует своего отдельного теста. Область доказательства должна быть названа явно.
