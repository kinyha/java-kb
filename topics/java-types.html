Types & Wrappers

Проверка владельца заказа работает для id до 127 и ломается дальше

Сервис проверяет, что заказ принадлежит пользователю. Идентификаторы из базы приходят как Long. На тестовых данных с маленькими id всё работает, в проде пользователи начинают получать «заказ не найден»:

import java.util.*;

public class SameUser {
    record Order(Long userId, long amount) { }
    record User(Long id, String name) { }

    static boolean owns(User user, Order order) {
        return order.userId() == user.id();                      // сравнение Long через ==
    }

    public static void main(String[] args) {
        for (long id : new long[]{42, 127, 128, 100_500}) {
            User user = new User(id, "user" + id);               // id из базы — автоупаковка в Long
            Order order = new Order(id, 1_000);
            System.out.printf("id %6d: owns = %s, equals = %s%n", id, owns(user, order), order.userId().equals(user.id()));
        }
    }
}
id     42: owns = true, equals = true
id    127: owns = true, equals = true
id    128: owns = false, equals = true
id 100500: owns = false, equals = true

== между двумя Long сравнивает ссылки на объекты, а не числа. Для значений от −128 до 127 JDK отдаёт одни и те же закешированные объекты, поэтому сравнение случайно работает. С 128 объекты разные, и == даёт false для равных чисел.

В этой теме — примитивы и обёртки: как работает автоупаковка и где она роняет NPE, что с переполнением и приведением типов, и почему в Java всё передаётся по значению, даже объекты.

Восемь примитивов хранят значение, обёртки — ссылку на объект

В Java восемь примитивных типов. Их значения лежат прямо в переменной — на стеке или внутри объекта — без заголовка и без ссылки:

public class Ranges {
    public static void main(String[] args) {
        System.out.printf("byte   %d байт  %d … %d%n", Byte.BYTES, Byte.MIN_VALUE, Byte.MAX_VALUE);
        System.out.printf("short  %d байт  %d … %d%n", Short.BYTES, Short.MIN_VALUE, Short.MAX_VALUE);
        System.out.printf("char   %d байт  %d … %d%n", Character.BYTES, (int) Character.MIN_VALUE, (int) Character.MAX_VALUE);
        System.out.printf("int    %d байт  %d … %d%n", Integer.BYTES, Integer.MIN_VALUE, Integer.MAX_VALUE);
        System.out.printf("long   %d байт  %d … %d%n", Long.BYTES, Long.MIN_VALUE, Long.MAX_VALUE);
        System.out.printf("float  %d байт  ~7 значащих цифр,  до %.2e%n", Float.BYTES, Float.MAX_VALUE);
        System.out.printf("double %d байт  ~15 значащих цифр, до %.2e%n", Double.BYTES, Double.MAX_VALUE);
        System.out.println("16777216f + 1 = " + (16_777_216f + 1));   // у float кончились значащие биты
    }
}
byte   1 байт  -128 … 127
short  2 байт  -32768 … 32767
char   2 байт  0 … 65535
int    4 байт  -2147483648 … 2147483647
long   8 байт  -9223372036854775808 … 9223372036854775807
float  4 байт  ~7 значащих цифр,  до 3.40e+38
double 8 байт  ~15 значащих цифр, до 1.80e+308
16777216f + 1 = 1.6777216E7
  • Все целые — знаковые, кроме char. Беззнакового int нет, есть методы Integer.toUnsignedString, Integer.divideUnsigned.
  • char — это 16-битная единица UTF-16, а не «символ». Эмодзи занимает два char (тема Strings).
  • Размер boolean спецификация не задаёт. В массиве HotSpot тратит байт на элемент.
  • float хранит около 7 значащих цифр: к 16 777 216 уже нельзя прибавить единицу. Для денег не годятся ни float, ни double — тема BigDecimal & Money.

У каждого примитива есть обёртка — неизменяемый класс: Integer, Long, Double, Boolean, Character и другие. Обёртки нужны там, где требуется объект: в коллекциях, в дженериках, для null как «значения нет». Цена — объект в heap: 16 байт вместо 4 для Integer (тема Object Layout & Allocation), ссылка вместо значения и возможность null.

Автоупаковка вставляет valueOf и intValue там, где их не видно

С Java 5 компилятор сам превращает int в Integer (Integer.valueOf) и обратно (intValue()). Это удобно, пока не забываешь, что вызов там есть. Четыре классические ловушки:

import java.util.*;

public class Boxing {
    public static void main(String[] args) {
        Integer a = 127, b = 127, c = 128, d = 128;               // Integer.valueOf под капотом
        System.out.println("127 == 127: " + (a == b) + ", 128 == 128: " + (c == d));

        Map<String, Integer> limits = new HashMap<>(Map.of("card", 50_000));
        try {
            int limit = limits.get("sbp");                         // ключа нет — get вернул null
        } catch (NullPointerException e) {
            System.out.println("распаковка null: " + e.getMessage());
        }

        boolean vip = false;
        try {
            Integer bonus = vip ? 100 : limits.get("sbp");         // тернарный оператор с int и Integer
            System.out.println("bonus = " + bonus);
        } catch (NullPointerException e) {
            System.out.println("тернарный оператор: NPE, хотя результат — Integer");
        }

        Map<Long, String> users = new HashMap<>(Map.of(1L, "Анна"));
        System.out.println("users.get(1) = " + users.get(1) + ", users.get(1L) = " + users.get(1L));
        System.out.println("Long.valueOf(1).equals(1) = " + Long.valueOf(1).equals(1));
    }
}
127 == 127: true, 128 == 128: false
распаковка null: Cannot invoke "java.lang.Integer.intValue()" because the return value of "java.util.Map.get(Object)" is null
тернарный оператор: NPE, хотя результат — Integer
users.get(1) = null, users.get(1L) = Анна
Long.valueOf(1).equals(1) = false
  1. Кеш. Integer.valueOf возвращает закешированные объекты для −128…127, для остальных создаёт новые. Поэтому == работает «иногда», как в шаге 1. Верхнюю границу кеша для Integer можно поднять флагом -XX:AutoBoxCacheMax=1000 — тогда и 128 == 128 станет true. Но это только маскирует ошибку. У Long, Short, Byte и Character кеш фиксированный. Обёртки сравнивают через equals или распаковывают.
  2. Распаковка null. int limit = map.get(key) — это map.get(key).intValue(). Нет ключа — NPE. Сообщение с Java 14 подсказывает, что именно было null (helpful NPE, JEP 358).
  3. Тернарный оператор. Если одна ветка int, а другая Integer, тип всего выражения — int. Компилятор распаковывает Integer-ветку и только потом упаковывает результат обратно. null из map.get падает на распаковке, хотя присваиваем в Integer. Решение — сделать обе ветки Integer: vip ? Integer.valueOf(100) : map.get(k).
  4. equals между разными обёртками. Long.equals возвращает true только для другого Long. Литерал 1 упаковывается в Integer, поэтому Map<Long, …>.get(1) молча возвращает null. Компилятор не предупреждает: get принимает Object.

Ещё одна цена упаковки — объекты. Сумма миллиона элементов списка в переменную Long вместо long:

import java.lang.management.ManagementFactory;
import java.util.*;

public class BoxedSum {
    public static void main(String[] args) {
        var threads = (com.sun.management.ThreadMXBean) ManagementFactory.getThreadMXBean();
        List<Long> amounts = new ArrayList<>();
        for (long i = 0; i < 1_000_000; i++) amounts.add(i * 37 % 10_000);
        for (int round = 0; round < 3; round++) {                         // первые круги — прогрев
            long bytes = threads.getCurrentThreadAllocatedBytes(), start = System.nanoTime();
            Long boxed = 0L;
            for (Long a : amounts) boxed += a;                               // boxed = Long.valueOf(boxed + a)
            long boxedNs = System.nanoTime() - start, boxedMb = (threads.getCurrentThreadAllocatedBytes() - bytes) >> 20;

            bytes = threads.getCurrentThreadAllocatedBytes(); start = System.nanoTime();
            long primitive = 0;
            for (Long a : amounts) primitive += a;                           // распаковка, сумма в long
            long primNs = System.nanoTime() - start, primMb = (threads.getCurrentThreadAllocatedBytes() - bytes) >> 20;
            if (round == 2)
                System.out.printf("Long sum: %.1f мс, выделено %d МБ; long sum: %.1f мс, выделено %d МБ (%b)%n",
                    boxedNs / 1e6, boxedMb, primNs / 1e6, primMb, boxed == primitive);
        }
    }
}
Long sum: 2.0 мс, выделено 22 МБ; long sum: 0.5 мс, выделено 0 МБ (true)

Одна буква в типе переменной — миллион объектов Long по 24 байта и вчетверо медленнее. Сравнение boxed == primitive в последней строке работает правильно: если один операнд примитив, второй распаковывается.

Конструкторы new Integer(5) и остальные устарели с Java 9 и с Java 16 помечены к удалению (JEP 390): обёртки — value-based классы, и полагаться на идентичность их объектов нельзя. javac предупреждает даже о synchronized на них (тема synchronized & wait/notify).

Переполнение в Java молчит, а приведение отрезает биты

Целочисленная арифметика в Java не проверяет переполнение: результат просто оборачивается по модулю 232 или 264. Самая частая ошибка — выражение, которое считается в int и только потом расширяется:

public class Overflow {
    public static void main(String[] args) {
        long monthMs = 30 * 24 * 60 * 60 * 1000;                     // считается в int, потом расширяется
        long monthMsOk = 30L * 24 * 60 * 60 * 1000;                  // L у первого множителя — всё в long
        System.out.println("30 дней в мс: " + monthMs + " вместо " + monthMsOk);

        int balance = Integer.MAX_VALUE;
        System.out.println("MAX_VALUE + 1 = " + (balance + 1));      // молча переходит через ноль
        try {
            Math.addExact(balance, 1);
        } catch (ArithmeticException e) {
            System.out.println("Math.addExact: " + e.getMessage());
        }

        System.out.println("(int) 3_000_000_000L = " + (int) 3_000_000_000L);   // отбрасываются старшие биты
        System.out.println("(int) 99.99 = " + (int) 99.99 + ", (int) -99.99 = " + (int) -99.99);
        System.out.println("(byte) 200 = " + (byte) 200);
        System.out.println("(int) 1e20 = " + (int) 1e20 + ", (int) Double.NaN = " + (int) Double.NaN);
        System.out.println("0.1 + 0.2 = " + (0.1 + 0.2));
        System.out.println("-7 / 2 = " + (-7 / 2) + ", -7 % 2 = " + (-7 % 2) + ", Math.floorMod(-7, 2) = " + Math.floorMod(-7, 2));
        System.out.println("Math.abs(Integer.MIN_VALUE) = " + Math.abs(Integer.MIN_VALUE));

        byte b = 10;
        b += 300;                                                    // скрытое приведение: b = (byte) (b + 300)
        System.out.println("byte b = 10; b += 300 → " + b);
        char c = 'A';
        System.out.println("'A' + 1 = " + ('A' + 1) + ", (char) ('A' + 1) = " + (char) (c + 1));
    }
}

Где переполнение недопустимо — суммы, счётчики, размеры, — используют Math.addExact, multiplyExact, toIntExact: они бросают ArithmeticException вместо тихого мусора. Отдельный сюрприз — Math.abs(Integer.MIN_VALUE): у минимального значения нет положительной пары в int, и модуль остаётся отрицательным. Отсюда ошибки в коде вида Math.abs(hash) % n — индекс оказывается отрицательным.

Java всегда передаёт по значению — для объектов копируется ссылка

При вызове метода каждый аргумент копируется в параметр. Для примитива копируется число, для объекта — ссылка. Поэтому метод может изменить объект, но не может заменить его у вызывающего:

public class ByValue {
    static class Account {
        long balance;
        Account(long balance) { this.balance = balance; }
    }

    static void deposit(Account acc, long amount) {
        acc.balance += amount;                       // меняем объект по скопированной ссылке — видно снаружи
    }

    static void reopen(Account acc) {
        acc = new Account(0);                        // меняем копию ссылки — снаружи не видно
        acc.balance = 999;
    }

    static void addBonus(Integer bonus) {
        bonus += 100;                                // bonus = Integer.valueOf(bonus + 100) — новый объект в копии
    }

    static void swap(Account x, Account y) {
        Account t = x; x = y; y = t;                 // меняются только локальные копии
    }

    public static void main(String[] args) {
        Account acc = new Account(100);
        deposit(acc, 50);
        System.out.println("после deposit: " + acc.balance);
        reopen(acc);
        System.out.println("после reopen:  " + acc.balance);

        Integer bonus = 10;
        addBonus(bonus);
        System.out.println("после addBonus: " + bonus);

        Account a = new Account(1), b = new Account(2);
        swap(a, b);
        System.out.println("после swap: a=" + a.balance + ", b=" + b.balance);
    }
}
после deposit: 150
после reopen:  150
после addBonus: 10
после swap: a=1, b=2

По той же причине addBonus не изменил Integer вызывающего: обёртка неизменяема, и bonus += 100 создаёт новый объект в локальной копии. А swap двух объектов в Java написать нельзя — только поменять их содержимое. Метод, которому нужно вернуть несколько значений, возвращает record или объект-результат, а не пытается менять аргументы.

  • Восемь примитивов хранят значения, обёртки — неизменяемые объекты со ссылкой и возможным null.
  • == на обёртках сравнивает ссылки. Кеш −128…127 заставляет его «работать» на маленьких числах. Обёртки сравнивают через equals.
  • Распаковка null — NPE, в том числе в тернарном операторе с веткой-примитивом. Long.equals(Integer) — всегда false, отсюда Map<Long,…>.get(1) == null.
  • Упаковка в цикле создаёт объекты: в замере миллион Long и вчетверо медленнее.
  • Целые переполняются молча. long x = a * b считается в int. Сужение отбрасывает биты, дробное в целое — к нулю. Для проверок — Math.*Exact.
  • Передача всегда по значению: для объекта копируется ссылка. Метод может изменить объект, но не заменить его у вызывающего.

На собеседовании

Почему Integer a = 127, b = 127; a == b — true, а для 128 — false?

Автоупаковка вызывает Integer.valueOf, который для −128…127 возвращает объекты из кеша, а для остальных создаёт новые. == на объектах сравнивает ссылки: для 127 это один и тот же объект, для 128 — два разных. Обёртки сравнивают через equals или распаковкой.

  • Верхнюю границу кеша Integer можно поднять флагом -XX:AutoBoxCacheMax, у Long и остальных кеш фиксированный.
  • Обёртки — value-based классы: конструкторы помечены к удалению (JEP 390), полагаться на их идентичность нельзя.
if (order.getUserId() == currentUser.getId()) — оба Long. Тесты проходят. Что не так?

Сравниваются ссылки. В тестах id маленькие и попадают в кеш Long, поэтому всё работает; в проде id больше 127, и проверка начинает возвращать false для равных значений — в замере урока с id 128. Нужно Objects.equals(a, b) или сравнение примитивов.

Где автоупаковка может привести к NullPointerException?

При распаковке null: int x = map.get(key), если ключа нет; арифметика с Integer-полем, равным null; Boolean в условии if. Менее очевидный случай — тернарный оператор: если одна ветка int, а другая Integer, тип выражения int, и null из Integer-ветки распаковывается, даже если результат присваивают в Integer.

Map<Long, String> users = Map.of(1L, "Анна"); что вернёт users.get(1)?

null. Литерал 1 упаковывается в Integer, а Long.equals возвращает true только для Long. Компилятор не предупреждает: Map.get принимает Object. Нужно users.get(1L).

Что происходит при переполнении int? Как его заметить?

Ничего не бросается: результат оборачивается по модулю 232, Integer.MAX_VALUE + 1 даёт MIN_VALUE. Чтобы переполнение стало ошибкой, используют Math.addExact, multiplyExact, toIntExact. Частая ловушка — long x = a * b, где a и b — int: произведение считается в int и переполняется до расширения.

long monthMs = 30 * 24 * 60 * 60 * 1000; — чему равно?

−1 702 967 296. Все множители int, произведение 2 592 000 000 не помещается в int и переполняется, а в long расширяется уже испорченное значение. Исправление — 30L * 24 * ..., тогда всё считается в long.

В Java передача по значению или по ссылке?

Всегда по значению. Для примитивов копируется значение, для объектов — значение ссылки. Поэтому метод может изменить состояние переданного объекта, и вызывающий это увидит. Но присвоить параметру другой объект так, чтобы изменилась переменная вызывающего, нельзя. Классическая проверка — метод swap(a, b) для объектов в Java не работает.

Почему метод addBonus(Integer bonus) { bonus += 100; } не меняет значение у вызывающего?

Integer неизменяем. bonus += 100 — это bonus = Integer.valueOf(bonus + 100): создаётся новый объект, и ссылка на него записывается в локальную копию параметра. Переменная вызывающего по-прежнему указывает на старый объект.
