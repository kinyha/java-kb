Java Upgrade

Сервис связан с платформой не одним контрактом, а пятью: стандартный API, формат байткода, внутренности JDK, флаги JVM и умолчания поведения. Каждый релиз Java меняет какой-то из этих слоёв, и каждое изменение проявляется на своём этапе: при сборке, при старте JVM, при первом вызове или только под реальной нагрузкой. Миграция — это поиск всех поломок до продакшена и раскатка, где каждый шаг меняет одно и откатывается заменой образа. Что появилось в языке и API, разобрано в What's New; здесь — что ломается и почему.

Сервис собрался на новой JDK и всё равно упал

Сервис платежей живёт на Java 8 и Spring Boot 2.7. Задача — перейти на Java 21, а следом на 25. Команда поднимает JDK в CI до 21, сборка и тесты зелёные, образ уходит на стенд. Дальше по очереди:

  • Под не стартует: скрипт запуска передаёт -XX:+PrintGCDateStamps, и JVM 21 отвечает Unrecognized VM option.
  • Флаг убрали. Под проходит readiness, а первый платёж падает с NoClassDefFoundError: javax/xml/bind/DatatypeConverter внутри библиотеки банковского шлюза.
  • Аудит пишет платёж старым сериализатором и получает InaccessibleObjectException на поле BigDecimal.
  • Через неделю после перехода на Spring Boot 3 кэш курсов перестал прогреваться, а партнёр не может разобрать время на чеке. Ошибок в логе нет.

Тесты пропустили всё это по разным причинам. Флаги живут в скрипте запуска, а не в сборке. До класса из удалённого модуля тесты не дошли: JVM ищет класс при первом обращении, а не при старте. Рефлексия в классы JDK ломается в рантайме, компилятор её не видит. А изменённые умолчания вообще не бросают исключений: код работает, но иначе.

Поэтому миграцию раскладывают по этапам, на которых поломка становится видна, и для каждого этапа заводят проверку, которая поймает её раньше прода.

Сам путь 8 → 11 → 17 → 21 → 25 удобно держать в голове как список слоёв, которые менялись на каждом прыжке. Колонки ниже — не фичи, а то, что ломает существующий код.

Удалённый API падает при первом вызове, а не при старте

В JDK 11 из платформы ушли модули Java EE: JAXB (javax.xml.bind), JAX-WS, JavaBeans Activation, Common Annotations (javax.annotation), JTA и CORBA (JEP 320). Причина — у них были свои спецификации и свой цикл развития, а держать их копии внутри JDK значило тормозить обе стороны. Свой код это ломает честно: javac --release 11 скажет package javax.xml.bind does not exist. Опасны чужие JAR, которые скомпилированы под Java 8 и приходят в сервис уже готовым байткодом.

Опыт: библиотека шлюза собрана под 8 и подписывает запрос через DatatypeConverter. Сервис собран под 21 и запущен на JDK 21.

// bank-lib.jar: javac --release 8 (в Java 8 этот класс есть)
import javax.xml.bind.DatatypeConverter;
public class BankClient {
    public String sign(byte[] payload) {
        return DatatypeConverter.printHexBinary(payload);   // ссылка на класс из удалённого модуля
    }
}

// сервис: javac --release 21 -cp bank-lib.jar, запуск на JDK 21
System.out.println("service started on Java " + Runtime.version().feature());
BankClient client = new BankClient();      // BankClient загружен, DatatypeConverter ещё никто не искал
System.out.println("health check: OK");
String signature = client.sign(new byte[] {(byte) 0xCA, (byte) 0xFE});   // здесь
service started on Java 21
health check: OK
Exception in thread "main" java.lang.NoClassDefFoundError: javax/xml/bind/DatatypeConverter
	at bank.BankClient.sign(BankClient.java:9)
	at app.PaymentService.main(PaymentService.java:10)
Caused by: java.lang.ClassNotFoundException: javax.xml.bind.DatatypeConverter

Сборка прошла, потому что компилятор сервиса видит только сигнатуры BankClient, а тело метода sign уже скомпилировано. Старт прошёл, потому что JVM разрешает ссылки на классы лениво. В class-файле BankClient имя javax/xml/bind/DatatypeConverter лежит в constant pool как строка, и искать класс JVM начинает только тогда, когда выполнение впервые доходит до инструкции, которая его использует. Пролистай, как это происходит:

Отсюда первое правило: зелёный readiness ничего не говорит о миграции. Нужна проверка, которая смотрит на байткод всех JAR, а не на выполненные пути. Её делает jdeps из целевой JDK:

jdeps bank-lib.jar                       # зависимости по пакетам, jdeps из JDK 21
bank-lib.jar -> java.base
bank-lib.jar -> not found                # пакет, которого нет ни в JDK, ни в переданном classpath
   bank      -> java.lang          java.base
   bank      -> javax.xml.bind     not found

В реальном сервисе jdeps запускают по всем JAR из собранного образа с ключами --class-path и --multi-release 21, а -summary или --missing-deps сокращают вывод до проблемных пакетов. Всё, что помечено not found, — кандидат на NoClassDefFoundError.

Вернуть API — значит выбрать правильное пространство имён

Удалённые модули продолжили жизнь отдельными артефактами в Eclipse Foundation и стали Jakarta EE. В Jakarta EE 9 их переименовали: javax.xml.bind стал jakarta.xml.bind. Переименование пакета ломает бинарную совместимость: в байткоде старой библиотеки зашито полное имя класса, и класс с другим пакетом для JVM — другой класс.

jar tf jakarta.xml.bind-api-4.0.5.jar | grep DatatypeConverter.class
jakarta/xml/bind/DatatypeConverter.class          # пакет jakarta, а библиотеке нужен javax
java -cp bank-lib.jar:app:jakarta.xml.bind-api-4.0.5.jar app.PaymentService
Exception in thread "main" java.lang.NoClassDefFoundError: javax/xml/bind/DatatypeConverter

Библиотеке под Java 8 нужен API 2.3.x, где пакет ещё javax: jakarta.xml.bind:jakarta.xml.bind-api:2.3.3 и реализация org.glassfish.jaxb:jaxb-runtime:2.3.x. Версии 3.0+ — уже jakarta, их берут вместе с кодом, переведённым на новые имена. API без реализации тоже падает, но позже: JAXBContext.newInstance не найдёт провайдера.

Если сервис стартовал на новой JDK, удалённых API в нём нет.

Классы ищутся лениво, при первом выполнении инструкции, которая их использует. Код за редкой веткой — ошибкой банка, ночным отчётом, SOAP-клиентом для одного партнёра — упадёт через дни. Полноту даёт только статический анализ байткода: jdeps по всем JAR.

Под капотом: почему повторный вызов падает так же

JVMS §5.4.3: если разрешение символьной ссылки не удалось, последующие попытки разрешить ту же ссылку бросают ту же ошибку. Поэтому подложить JAR в работающий сервис не поможет: нужен перезапуск. NoClassDefFoundError — это LinkageError, то есть ошибка связывания уже загруженного кода. ClassNotFoundException — проверяемое исключение от ClassLoader.loadClass и Class.forName, его увидит код, который сам ищет класс по имени. Цепочка загрузчиков и то, как app передаёт запрос в platform и bootstrap, разобраны в Class Loading.

Версия class-файла решает, можно ли откатиться

Каждый class-файл начинается с номера формата: байты 6–7, major version. Для Java N это N + 44: 52 у Java 8, 55 у 11, 61 у 17, 65 у 21, 69 у 25, 71 у 27. JVM читает файлы своей версии и всех старших, а более новые отвергает до загрузки, не глядя на содержимое. Поэтому байткод Java 8 работает на JDK 25, а байткод 25 на JDK 21 — нет, даже если в нём нет ни одной новой конструкции.

javac -d cv25 Receipt.java                # javac из JDK 25 без --release
javac --release 21 -d cv21 Receipt.java   # тот же javac, но формат и API Java 21
javap -v cv25/Receipt.class | grep major
  major version: 69
javap -v cv21/Receipt.class | grep major
  major version: 65
java -cp cv25 Receipt                     # на JDK 21: откат рантайма после сборки на 25
Error: LinkageError occurred while loading main class Receipt
	java.lang.UnsupportedClassVersionError: Receipt has been compiled by a more recent version of the Java Runtime (class file version 69.0), this version of the Java Runtime only recognizes class file versions up to 65.0

С cv21 тот же JDK 21 печатает receipt printed on Java 21. Из этой асимметрии следует главное правило раскатки. Сначала меняют рантайм, а байткод оставляют старым: тогда откат — это просто прошлый образ. Поднимать --release можно только тогда, когда откат на старую JDK больше не нужен. --release заодно ограничивает доступный API версией N. Почему -source/-target этого не делают и как toolchain выбирает JDK для сборки, разобрано в Maven & Gradle.

Байткод читают не только JVM

Номер версии проверяет не одна JVM. Сканеры classpath (Spring, Hibernate), Mockito и Byte Buddy, JaCoCo, APM-агенты и обфускаторы разбирают class-файлы сами, обычно через библиотеку ASM. ASM знает форматы только до версии, которая была на момент её выпуска, и на более новом файле останавливается, хотя сама работает на любой JDK.

// Так читают байткод сканеры и агенты: через ASM, а не через JVM.
byte[] bytes = ...;                                          // файл с диска или класс из JDK
int major = ((bytes[6] & 0xFF) << 8) | (bytes[7] & 0xFF);   // байты 6–7: major version
System.out.println("class file major version: " + major);
new ClassReader(bytes).accept(new ClassVisitor(Opcodes.ASM9) { ... }, 0);
## ASM 9.7.1, Receipt.class от javac 25        (запуск на JDK 21)
class file major version: 69
Exception in thread "main" java.lang.IllegalArgumentException: Unsupported class file major version 69
## ASM 9.8, тот же файл
class file major version: 69
ASM parsed: Receipt
## ASM 9.7.1, java/lang/String.class из JDK, на которой запущен
JDK 21: class file major version: 65 → ASM parsed: java/lang/String
JDK 25: class file major version: 69 → IllegalArgumentException: Unsupported class file major version 69

Последние две строки важнее всего. Даже если твой код собран с --release 21, на JDK 25 классы самой платформы имеют версию 69. Агент, который инструментирует java.lang или java.net, и Mockito, который строит подклассы JDK-типов, упадут на новом рантайме. Поэтому порядок такой: сначала обновить всё, что читает байткод (Spring, Byte Buddy, Mockito, JaCoCo, Lombok, агенты APM, плагины сборки), на старой JDK, и только потом менять рантайм.

Собрали под 21, значит, на JDK 25 ничего, кроме нашего кода, не сломается.

--release управляет только твоими class-файлами. Библиотеки с устаревшим ASM внутри падают на классах самой JDK 25. Их версию проверяют по таблице совместимости библиотеки, а не по версии сборки сервиса.

Под капотом: multi-release JAR

Библиотеке, которая должна работать и на 8, и на 21, не нужно выбирать минимум. В multi-release JAR (JEP 238, JDK 9) базовые классы лежат в корне, а версии под новые JDK — в META-INF/versions/N/. При Multi-Release: true в манифесте JarFile отдаёт для каждого класса самую новую версию, не старше текущего рантайма. JDK 8 про META-INF/versions ничего не знает и просто читает корень.

javac --release 8  -d mr8  base/lib/*.java                 # Workers.forIo(): fixed pool
javac --release 21 -d mr21 java21/lib/Workers.java         # та же сигнатура: virtual threads
jar --create --file workers.jar --main-class lib.Main -C mr8 . --release 21 -C mr21 .
jar tf workers.jar | grep class
lib/Main.class
lib/Workers.class
META-INF/versions/21/lib/Workers.class
Java 21: VirtualThread[#28]/runnable@ForkJoinPool-1-worker-1   # java -jar на JDK 21
Java 25: VirtualThread[#35]/runnable@ForkJoinPool-1-worker-1   # на JDK 25: берётся versions/21
Java 21: Thread[#28,pool-1-thread-1,5,main]                     # -Djdk.util.jar.enableMultiRelease=false

Номера потоков меняются от запуска к запуску. На JDK 8 этот JAR не запускался: локально его нет. Публичный API версий обязан совпадать, это проверяет jar --validate. Для сервиса multi-release обычно не нужен: у него один рантайм. Он нужен общей библиотеке, которой пользуются сервисы на разных JDK во время миграции.

Strong encapsulation: рефлексия больше не открывает JDK

С Java 9 JDK разбита на модули, и модуль сам решает, что показывать. exports открывает пакет для обычного доступа: компилируй и вызывай public-члены. opens разрешает глубокую рефлексию: setAccessible(true) на private-полях и методах. java.base экспортирует java.math, но не открывает его. Весь classpath — это один безымянный модуль (unnamed module), и правила для него те же.

Закрывали это постепенно. В JDK 9–15 действовал --illegal-access=permit: все пакеты JDK 8 оставались открытыми для classpath, а первое обращение печатало WARNING: Illegal reflective access. Многие годами его игнорировали. В JDK 16 по умолчанию стал deny (JEP 396), в JDK 17 опцию убрали совсем (JEP 403): теперь она только печатает предупреждение. Так выглядит старый сериализатор, который обходит все поля объекта, включая поля классов JDK:

record Payment(String id, BigDecimal amount) {}

static String dump(Object o) throws IllegalAccessException {
    if (o == null || o instanceof String || o instanceof Integer || o instanceof Long) return String.valueOf(o);
    StringBuilder sb = new StringBuilder(o.getClass().getSimpleName()).append('{');
    for (Field f : o.getClass().getDeclaredFields()) {
        if (Modifier.isStatic(f.getModifiers())) continue;
        f.setAccessible(true);          // свой record — можно; поля BigDecimal — глубокая рефлексия в java.base
        sb.append(' ').append(f.getName()).append('=').append(dump(f.get(o)));
    }
    return sb.append(" }").toString();
}

Field intCompact = BigDecimal.class.getDeclaredField("intCompact");
System.out.println("trySetAccessible: " + intCompact.trySetAccessible());  // проверка без исключения
System.out.println(dump(new Payment("pay-42", new BigDecimal("199.90"))));
## java LegacySerializer.java                                 (JDK 21, так же на 25)
trySetAccessible: false
Exception in thread "main" java.lang.reflect.InaccessibleObjectException: Unable to make field private final java.math.BigInteger java.math.BigDecimal.intVal accessible: module java.base does not "opens java.math" to unnamed module @5e4c8041
## java --add-opens java.base/java.math=ALL-UNNAMED LegacySerializer.java
trySetAccessible: true
Payment{ id=pay-42 amount=BigDecimal{ intVal=null scale=2 precision=5 stringCache=null intCompact=19990 } }

Сообщение исключения — готовый рецепт: модуль java.base, пакет java.math, получатель unnamed module. Отсюда флаг --add-opens java.base/java.math=ALL-UNNAMED. Хеш после @ меняется от запуска к запуску. Обрати внимание: поля самого Payment открылись без флагов, потому что record лежит в том же безымянном модуле.

Как чинить, по порядку

  1. Обновить библиотеку. Почти все популярные библиотеки давно не лезут в JDK или делают это через публичные API: MethodHandles.privateLookupIn, VarHandle, ReflectionFactory для сериализации.
  2. Заменить вызов. Если в JDK лезет свой код, почти всегда есть публичный путь: BigDecimal.unscaledValue() вместо поля intVal.
  3. Открыть один пакет. Если обновиться нельзя — узкий --add-opens на конкретный пакет, а не на весь java.base. Флаг нужен везде, где выполняется код: в скрипте запуска, в argLine Surefire и Failsafe, в Gradle jvmArgs тестов.

Если флаги некуда вписать, пригодятся ещё два места. Переменную окружения JDK_JAVA_OPTIONS читает лаунчер java с JDK 9. Атрибут Add-Opens в манифесте работает только для JAR, запущенного через java -jar:

printf 'Main-Class: LegacySerializer\nAdd-Opens: java.base/java.math\n' > manifest.txt
jar --create --file enc.jar --manifest manifest.txt -C classes .
java -jar enc.jar | head -1              # манифест прочитан лаунчером
trySetAccessible: true
java -cp enc.jar LegacySerializer | head -1   # тот же JAR, но не главный: атрибут не действует
trySetAccessible: false

Можно один раз прописать --add-opens java.base/java.lang=ALL-UNNAMED и ещё десяток таких же и забыть.

Каждый такой флаг — задокументированный долг: библиотека, которую не обновили. Список флагов растёт от релиза к релизу, а в JDK 26 к нему добавилась отдельная проверка изменения final-полей (JEP 500), которую --add-opens не снимает. Держи флаги рядом с причиной: какая библиотека, какая версия её починит.

Близкий флаг --add-exports нужен для другого: доступа к public-классам неэкспортированного пакета, например sun.security.x509, на этапе компиляции и в рантайме. Он не даёт setAccessible на private-члены. Подробнее про рефлексию и модули — в Annotations & Reflection.

Каждый релиз закрывает следующую дверь: warn, deny, remove

После 17 strong encapsulation расширили на всё, чем код может обойти гарантии платформы: sun.misc.Unsafe, JNI, динамическую загрузку агентов, изменение final-полей, Security Manager. В OpenJDK это называют integrity by default. Все такие изменения идут одним маршрутом, растянутым на несколько релизов, и миграция 21 → 25 — это в основном прохождение по нему.

Unsafe: молчит на 21, предупреждает на 25

Методы доступа к памяти в sun.misc.Unsafe (allocateMemory, putLong, getLong и другие) объявлены forRemoval в JDK 23 (JEP 471), потому что у них есть поддерживаемые замены: VarHandle с JDK 9 и Foreign Function & Memory API с JDK 22. С JDK 24 первое обращение печатает предупреждение (JEP 498). Класс ниже скомпилирован один раз и запущен на двух JDK:

Field f = Unsafe.class.getDeclaredField("theUnsafe");
f.setAccessible(true);                      // sun.misc открыт модулем jdk.unsupported: исключения нет
Unsafe unsafe = (Unsafe) f.get(null);
long address = unsafe.allocateMemory(64);   // метод доступа к памяти
unsafe.putLong(address, 199_90L);
System.out.println("off-heap value: " + unsafe.getLong(address));
unsafe.freeMemory(address);
## JDK 21
off-heap value: 19990
## JDK 25
WARNING: A terminally deprecated method in sun.misc.Unsafe has been called
WARNING: sun.misc.Unsafe::allocateMemory has been called by OffHeapBuffer (file:<tmp>/int/)
WARNING: Please consider reporting this to the maintainers of class OffHeapBuffer
WARNING: sun.misc.Unsafe::allocateMemory will be removed in a future release
off-heap value: 19990
## JDK 25 с --sun-misc-unsafe-memory-access=deny
Exception in thread "main" java.lang.UnsupportedOperationException: allocateMemory

Предупреждение пишется в stderr один раз за процесс и называет вызывающий класс и его JAR — по ним видно, какую библиотеку обновлять. JEP 498 планирует сделать deny поведением по умолчанию, но и в JDK 26, и в JDK 27 по умолчанию стоит warn: это видно в sun/misc/Unsafe.java обоих релизов. Готовность проверяют заранее: прогоняют тесты с --sun-misc-unsafe-memory-access=deny. Так же работают соседние проверки: --illegal-native-access=deny для JNI (JEP 472, предупреждение с JDK 24), --illegal-final-field-mutation=deny для изменения final-полей (JEP 500, JDK 26). Динамическую загрузку агентов JDK 21 тоже сопровождает предупреждением (JEP 451). Её первым замечает Mockito с inline mock maker: агент подключают явно через -javaagent в тестах.

Security Manager: флаг, который убивает JVM

Security Manager объявлен forRemoval в JDK 17 (JEP 411). С JDK 18 включить его можно только явным -Djava.security.manager=allow. В JDK 24 его отключили навсегда (JEP 486). Классы остались для совместимости, но работать больше не будут:

Найти всё это заранее

jdeprscan ищет в готовых JAR использования API с пометкой @Deprecated, jdeps --jdk-internals — обращения к внутренностям JDK. Оба работают по байткоду, поэтому видят и чужие библиотеки:

Флаги JVM проходят тот же путь

У флагов HotSpot свой цикл, он записан в таблице special_jvm_flags в arguments.cpp. Deprecated — флаг работает и печатает предупреждение. Obsolete — флаг игнорируется с предупреждением. Expired — флага больше нет, и JVM отказывается стартовать. Один и тот же скрипт запуска на двух JDK:

java -XX:-IgnoreUnrecognizedVMOptions -XX:MaxRAMFraction=2 -version      # Java 8: доля памяти в контейнере
# JDK 21:
OpenJDK 64-Bit Server VM warning: Option MaxRAMFraction was deprecated in version 10.0 and will likely be removed in a future release.
# JDK 25:
Unrecognized VM option 'MaxRAMFraction=2'
Error: Could not create the Java Virtual Machine.

java -XX:-IgnoreUnrecognizedVMOptions -XX:+G1UsePreventiveGC -version
# JDK 21:
OpenJDK 64-Bit Server VM warning: Ignoring option G1UsePreventiveGC; support was removed in 21.0
# JDK 25:
Unrecognized VM option 'G1UsePreventiveGC'

java -XX:-IgnoreUnrecognizedVMOptions -XX:+PrintGCDateStamps -version    # GC-лог в стиле Java 8
# JDK 21 и 25:
Unrecognized VM option 'PrintGCDateStamps'

MaxRAMFraction стал obsolete в 23 и expired в 24. Его ставили в Java 8 в контейнерах, а с JDK 10 вместо него есть MaxRAMPercentage, подробнее в Java in Kubernetes. Флаги GC-логов Java 8 исчезли в JDK 9 вместе с переходом на -Xlog (JEP 271): -XX:+PrintGCDetails ещё переводится в -Xlog:gc* с предупреждением, а PrintGCDateStamps уже нет. Проверка до прода — запустить в CI java $JAVA_OPTS -version с настоящими флагами из манифеста деплоя.

Опыты выше запущены с -XX:-IgnoreUnrecognizedVMOptions. В локальной JBR 21 этот флаг по умолчанию true, и неизвестные опции молча пропускаются. В обычной сборке OpenJDK и в JBR 25 он false. Если дома всё стартует, а в контейнере нет, сравни java -XX:+PrintFlagsFinal -version | grep IgnoreUnrecognized.

Самое опасное меняется без ошибки

У предыдущих поломок есть стектрейс. У следующих его нет: код выполняется, но результат другой. Их ловит только сравнение старой и новой версии на одинаковых данных — тестом с точным ожидаемым значением или канарейкой с метриками.

Аннотации из чужого пакета просто не видны

Spring Boot 3 стоит на Spring Framework 6 и Jakarta EE 9+: Servlet, JPA, Bean Validation, Common Annotations переехали из javax.* в jakarta.*. Код, который ссылается на javax.servlet.Filter, не скомпилируется, если старого API нет на classpath. Опаснее, когда старый API приходит транзитивно: всё компилируется, а фреймворк такие аннотации и интерфейсы просто не ищет.

public static class JavaxRateCache {
    boolean warmed;
    @javax.annotation.PostConstruct          // так было в Spring Boot 2 (Java EE, пакет javax)
    void warmUp() { warmed = true; }
}

public static class JakartaRateCache {
    boolean warmed;
    @jakarta.annotation.PostConstruct        // так нужно в Spring Boot 3+ (пакет jakarta)
    void warmUp() { warmed = true; }
}

try (var ctx = new AnnotationConfigApplicationContext(JavaxRateCache.class, JakartaRateCache.class)) {
    System.out.println("Spring " + SpringVersion.getVersion());
    System.out.println("javax   @PostConstruct called: " + ctx.getBean(JavaxRateCache.class).warmed);
    System.out.println("jakarta @PostConstruct called: " + ctx.getBean(JakartaRateCache.class).warmed);
}
Spring 7.0.9
javax   @PostConstruct called: false
jakarta @PostConstruct called: true

Оба JAR с аннотациями лежат на classpath, контекст поднялся без единого предупреждения, а кэш курсов не прогрет. Так же молча Hibernate 6 не находит сущность с @javax.persistence.Entity, Hibernate Validator 8 не проверяет @javax.validation.constraints.NotNull, а бин, реализующий javax.servlet.Filter, не попадает в цепочку фильтров Tomcat 10. Поведение зависит даже от минорной версии: исходники CommonAnnotationBeanPostProcessor показывают, что Spring 6.0.0–6.0.10 javax-аннотации не видит, 6.0.11–6.2 снова их поддерживает, а 7.0 убрал эту поддержку.

Поэтому перевод на jakarta делают целиком и механически: рецептами OpenRewrite для Spring Boot 3, Eclipse Transformer для чужих JAR без новой версии. После этого проверяют, что в собранном образе не осталось javax.servlet, javax.persistence, javax.validation, javax.annotation: mvn dependency:tree и jdeps по JAR. Пакеты javax.sql, javax.crypto, javax.net — часть Java SE, их это не касается. Переименованные свойства конфигурации Boot подсказывает модуль spring-boot-properties-migrator в логе старта. Подробнее про запуск Boot — в Startup & Packaging.

Форматы и кодировки

С JDK 9 данные локалей берутся из CLDR (JEP 252), а в JDK 20 CLDR 42 поставил между временем и AM/PM узкий неразрывный пробел U+202F. Строка на чеке выглядит так же, а партнёр, который разбирает её старым форматом с обычным пробелом, падает. Обратная проблема тоже есть: наш парсер не принимает строку с обычным пробелом.

DateTimeFormatter fmt = DateTimeFormatter.ofLocalizedTime(FormatStyle.SHORT).withLocale(Locale.US);
String time = fmt.format(LocalTime.of(15, 30));
char gap = time.charAt(time.length() - 3);                 // символ между "3:30" и "PM"
System.out.printf("time=%s gap=U+%04X%n", time, (int) gap);
LocalTime.parse("3:30 PM", fmt);                           // обычный пробел, как в старых тестах и клиентах
System.out.println("default charset: " + Charset.defaultCharset());
## JDK 21
time=3:30 PM gap=U+202F
parse '3:30 PM': DateTimeParseException
default charset: UTF-8
## JDK 21, -Djava.locale.providers=COMPAT
WARNING: COMPAT locale provider will be removed in a future release
time=3:30 PM gap=U+0020
parse '3:30 PM': OK
## JDK 25, -Djava.locale.providers=COMPAT
INFO: Invalid locale provider adapter "COMPAT" ignored.
WARNING: COMPAT locale provider has been removed
time=3:30 PM gap=U+202F
parse '3:30 PM': DateTimeParseException

На 21 флаг COMPAT возвращал старые форматы. В JDK 23 провайдер удалили, и на 25 тот же флаг даёт строку в логе и CLDR-форматы. JVM не падает, поэтому временная заплатка исчезает незаметно. Строки из лога даты и времени опущены. Надёжная починка — явный шаблон ofPattern("h:mm a", Locale.US) там, где формат — часть контракта с внешней системой.

С кодировкой похожая история. До JDK 18 кодировка по умолчанию бралась из ОС, с JDK 18 это UTF-8 (JEP 400). Сервис, который в контейнере с LANG=C писал файлы в US-ASCII, после перехода пишет их в UTF-8. Старое поведение возвращает -Dfile.encoding=COMPAT: на JDK 21 с LANG=C он даёт default charset: US-ASCII, без него — UTF-8.

Эргономика JVM

JVM выбирает сборщик и размеры сама, и эти правила тоже меняются. На JDK 21 и 25 при одном доступном CPU выбирается Serial: -XX:ActiveProcessorCount=1 -Xlog:gc печатает Using Serial. Под в Kubernetes с limits.cpu: 1 видит один CPU. В JDK 27 JVM всегда выбирает G1 (JEP 523): в gcConfig.cpp тега jdk-27-ga проверка «серверного класса» машины осталась только для сборок без G1. В том же JDK 27 компактные заголовки объектов включены по умолчанию (JEP 534), заголовок занимает 8 байт вместо 12, и heap становится меньше. JDK 27 локально не запускалась. Это хорошие изменения, но паузы, CPU и память после них другие, поэтому их сравнивают метриками. Как выбирать сборщик — в Choosing a Collector, про заголовки — в Object Layout & Allocation.

Ещё два классических тихих изменения. В апреле 2021 TLS 1.0 и 1.1 отключили по умолчанию в JDK 16, 11.0.11 и 8u291 через jdk.tls.disabledAlgorithms: старый банковский шлюз перестал отвечать на рукопожатие. Java 8 до 8u191 не учитывала лимиты контейнера и считала heap от памяти узла: после переезда в Kubernetes такой сервис получает OOMKill.

Раскатка: каждый шаг меняет одно и откатывается образом

Из предыдущих шагов следуют правила порядка. Байткод новее рантайма не запустится, значит, сначала рантайм, потом --release. Библиотеки со своим ASM ломаются на классах новой JDK, значит, их обновляют до смены рантайма. Spring Boot 3 требует Java 17, значит, сначала рантайм, потом фреймворк. Если склеить всё в один релиз, при проблеме непонятно, что откатывать, а откат требует пересборки. Так выглядит путь сервиса платежей с 8 на 21 и затем на 25:

CI до прода

Сборка идёт на одной JDK, а тесты — на матрице: текущая версия и целевая. Toolchain позволяет собирать с --release 8 на JDK 21 и запускать тесты на другой JDK. Полезно добавить джоб на early-access сборке следующей версии с jdk.java.net: так поломки видны за полгода до релиза. В тестовый запуск на целевой JDK добавляют флаги будущего поведения: --sun-misc-unsafe-memory-access=deny, --illegal-native-access=deny, а на JDK 26+ --illegal-final-field-mutation=deny. Предупреждения превращаются в падения сейчас, а не через релиз.

// Gradle: собрать на одной JDK, гонять тесты ещё и на целевой
java { toolchain { languageVersion = JavaLanguageVersion.of(21) } }
tasks.withType(JavaCompile).configureEach { options.release = 8 }   // байткод 52 до шага 4
tasks.register('testOn25', Test) {
    testClassesDirs = sourceSets.test.output.classesDirs
    classpath = sourceSets.test.runtimeClasspath
    useJUnitPlatform()
    javaLauncher = javaToolchains.launcherFor { languageVersion = JavaLanguageVersion.of(25) }
    jvmArgs '--sun-misc-unsafe-memory-access=deny', '--illegal-native-access=deny'
}

Это фрагмент для иллюстрации, в демо темы Gradle не запускался. Toolchain, release и разница с -source/-target проверены запуском в Maven & Gradle.

Канарейка и что сравнивать

Смена рантайма выкатывается на долю подов, как любой рискованный деплой (Deploy Strategies). Сравнивают не только ошибки, а то, что меняется тихо. GC: паузы, частоту, выбранный сборщик — его печатает -Xlog:gc первой строкой. Память процесса: RSS и heap, а не только -Xmx. Latency p99, CPU, время старта и прогрева JIT. Флаги сравнивают диффом java -XX:+PrintFlagsFinal -version старой и новой JDK с одинаковыми опциями. На подозрительных подах снимают JFR-запись.

Когда не прыгать и куда прыгать

  • Только LTS для прода, если не готов обновляться каждые полгода. LTS — 8, 11, 17, 21, 25; Oracle планирует следующую, 29, на сентябрь 2027. Не-LTS 26 и 27 Oracle поддерживает по полгода: Premier Support для 27 — до марта 2027. Premier Support для 17 закончился в сентябре 2026, для 21 — сентябрь 2028, для 25 — сентябрь 2030. Сроки поддержки у Temurin, Corretto и других вендоров свои.
  • Промежуточные LTS проходить не обязательно. Прыжок 8 → 21 — это те же поломки, что 8 → 11 → 17 → 21, только сразу. Шаги делят по типу риска, как на схеме, а не по номерам версий.
  • Фреймворк задаёт потолок. Spring Boot 2.7.18 совместим с Java до 21, Spring Boot 4.1 — с Java 17–26. В день релиза JDK 27 фреймворк ещё не объявил её поддержку. Новую JDK берут, когда её поддерживают фреймворк, агенты и сборка.
  • Иногда дешевле остаться. Сервис, который выводят из эксплуатации, или монолит на сервере приложений Java EE 8 можно держать на 8 или 11 с коммерческой поддержкой. Остальную миграцию тогда тормозят зависимости, которые уходят с 8, а не сама JDK.
  • Поломка проявляется на своём этапе: сборка, старт JVM, первый вызов, поведение. Тесты ловят только первые; для остальных нужны jdeps, скрипт прода в CI и канарейка.
  • JVM ищет классы лениво: удалённый API падает NoClassDefFoundError при первом вызове, а не при старте. javax и jakarta — разные классы для JVM.
  • Байткод новее рантайма не запустится. Сначала меняют рантайм, потом --release; до смены рантайма обновляют всё, что читает байткод через ASM.
  • Strong encapsulation закрыла глубокую рефлексию в JDK. Лечение — обновить библиотеку; --add-opens на один пакет — задокументированный долг.
  • Integrity by default идёт маршрутом deprecated → warn → deny → удалено. Флаг, который возвращал старое на 21, на 25 может не дать JVM стартовать.

На собеседовании

Расскажите, как вы переводили сервис на новую версию Java

Сначала инвентаризация: прогоняю jdeps и jdeprscan из целевой JDK по всем JAR образа, выписываю флаги из скрипта запуска и библиотеки, которые сами читают байткод, — Byte Buddy, Mockito, Lombok, агент APM. Их обновляю ещё на старой JDK. Потом меняю только рантайм, оставляя --release старым: байткод старой версии работает на новой JVM, и откат — это просто прошлый образ.

На этом шаге всплывают удалённые флаги, InaccessibleObjectException от рефлексии в JDK и тихие изменения вроде форматов дат. Канарейкой сравниваю GC-паузы, память, p99. Переход на Spring Boot 3 с javax → jakarta делаю отдельным релизом, потому что он меняет код. --release поднимаю в самом конце, когда откат на старую JDK уже не нужен.

  • Порядок следует из асимметрии class-файлов: JVM 21 отвергает major 69 с UnsupportedClassVersionError, а JVM 25 читает 65. Поэтому рантайм раньше байткода, иначе откат требует пересборки.
  • Даже с --release 21 на JDK 25 падают библиотеки со старым ASM: классы самой платформы имеют версию 69, и агенту или Mockito нужно их разобрать.
  • Тесты на целевой JDK гоняю с будущими значениями проверок: --sun-misc-unsafe-memory-access=deny, --illegal-native-access=deny. Ещё держу джоб на early-access следующей версии.
  • Промежуточные LTS проходить не обязательно: 8 → 21 даёт те же поломки, что лестница через 11 и 17. Шаги режу по типу риска, а не по номерам версий.
Сервис собрали на JDK 25 без --release и выкатили на JDK 25. Через час решили откатить рантайм на 21. Что будет?

Под не стартует: UnsupportedClassVersionError ... class file version 69.0, this version of the Java Runtime only recognizes class file versions up to 65.0. Откатить можно только целиком на прошлую сборку, а не заменой базового образа. Если бы сборка шла с --release 21, откат рантайма был бы безопасным.

После перехода на 21 выросла память пода, ошибок нет. С чего начнёте?

Сравню, что изменилось без моего участия. Какой сборщик выбран (-Xlog:gc: при одном CPU это Serial, в 27 — всегда G1), фактические размеры heap и MaxRAMPercentage, дифф -XX:+PrintFlagsFinal двух версий. Затем Native Memory Tracking (-XX:NativeMemoryTracking=summary и jcmd VM.native_memory), чтобы разделить heap, metaspace, потоки и code cache. Число потоков тоже могло измениться после обновления библиотек.

Что такое InaccessibleObjectException и как его чинить?

Это результат strong encapsulation модулей. Модуль может экспортировать пакет — тогда доступны public-классы — и открыть его — тогда разрешена глубокая рефлексия на private-членах. java.base экспортирует, например, java.math, но не открывает, поэтому setAccessible(true) на поле BigDecimal из кода на classpath бросает InaccessibleObjectException. В JDK 9–15 это было предупреждение Illegal reflective access, в 16 стал запрет по умолчанию, в 17 опцию --illegal-access убрали.

Чиню по порядку: обновляю библиотеку, которая лезет в JDK. Если это свой код — меняю на публичный API. Если ни то ни другое невозможно — узкий --add-opens java.base/java.math=ALL-UNNAMED на один пакет, и в скрипте запуска, и в настройках тестов.

  • --add-exports даёт доступ к public-типам неэкспортированного пакета, --add-opens — рефлексию на private. Первый не заменяет второй.
  • sun.misc.Unsafe оставлен доступным через jdk.unsupported (JEP 260), но его методы памяти с JDK 24 печатают предупреждение и пойдут в deny.
  • Флаги можно передать через JDK_JAVA_OPTIONS или атрибут Add-Opens в манифесте; атрибут действует только для JAR, запущенного через java -jar.
  • В JDK 26 изменение final-поля рефлексией печатает отдельное предупреждение (JEP 500), даже если пакет открыт.
В JAR указан Add-Opens: java.base/java.math. Сервис запускают как java -cp app.jar:libs/* com.pay.Main. Откроется ли пакет?

Нет. Атрибуты Add-Opens и Add-Exports читает только лаунчер для главного JAR при java -jar. В опыте темы тот же JAR при -jar дал trySetAccessible: true, а при -cp — false. Для запуска через -cp флаг передают в командной строке или в JDK_JAVA_OPTIONS.

Почему в проде упало, хотя тесты на той же JDK зелёные и флаг в скрипте запуска есть?

Чаще всего наоборот: флаг есть в argLine тестов, но не в манифесте деплоя, или код рефлексии выполняется только на редкой ветке, до которой тесты не доходят. Ещё вариант — флаг открывает не тот пакет: сообщение исключения называет точный модуль и пакет, и --add-opens должен совпадать с ним буквально.

Чем опасен переход на Spring Boot 3 и javax → jakarta?

Spring Boot 3 требует Java 17 и стоит на Jakarta EE 9+, где Servlet, JPA, Bean Validation и Common Annotations переименованы из javax.* в jakarta.*. Для JVM это другие классы: старая библиотека, скомпилированная против javax.servlet, с Tomcat 10 не работает, даже если всё остальное совпадает.

Самое опасное — то, что не падает. Если javax-аннотации приходят транзитивно, код компилируется, а фреймворк их не ищет: @javax.annotation.PostConstruct не вызывается, сущность с @javax.persistence.Entity не видна, @javax.validation.NotNull не проверяется. Поэтому перевожу всё механически, рецептами OpenRewrite, и проверяю образ на остатки javax-пакетов.

  • Переход на Boot 3 меняет код, поэтому его откат — revert и пересборка. Его отделяю от смены рантайма: сначала Boot 2.7.18 на новой JDK, потом Boot 3.
  • Для чужих JAR без jakarta-версии есть Eclipse Transformer: он переписывает имена пакетов прямо в байткоде.
  • Поддержка javax-аннотаций плавала даже между минорными версиями: Spring 6.0.0–6.0.10 их не видит, 6.0.11–6.2 видит, 7.0 снова не видит. Опираться на неё нельзя.
  • Не всё javax уходит: javax.sql, javax.crypto, javax.net — часть Java SE и остаются.
Сервис на Spring Boot 3. Что не так с этим бином? 
import javax.annotation.PostConstruct;     // пришло транзитивно из старого клиента

@Component
public class RateCache {
    private Map<String, BigDecimal> rates = Map.of();

    @PostConstruct
    void warmUp() { rates = ratesClient.loadAll(); }
}

Spring 6.0.0–6.0.10 и 7.x не ищут javax.annotation.PostConstruct, поэтому метод не вызовется, а кэш останется пустым без единой ошибки. В опыте темы Spring 7.0.9 вызвал только jakarta-вариант. Исправление — jakarta.annotation.PostConstruct, а старый API нужно убрать из зависимостей, чтобы такой импорт перестал компилироваться.

Что сломается при переходе с Java 21 на 25?

Язык почти не ломает, ломается то, что обходило гарантии платформы. Методы памяти sun.misc.Unsafe на 25 печатают предупреждение при первом вызове, и к ним готовят deny. Security Manager отключён навсегда: -Djava.security.manager=allow, который на 21 возвращал его, на 25 не даёт JVM стартовать. Истекли старые флаги вроде MaxRAMFraction, удалён провайдер локалей COMPAT.

Ещё на 25 у классов самой JDK версия class-файла 69, поэтому библиотеки со старым ASM — агенты, Mockito, JaCoCo — нужно обновить заранее. Проверяю всё это тестами на 25 с флагами deny и прогоном скрипта запуска в CI.

  • JNI тоже на маршруте: с JDK 24 предупреждение без --enable-native-access (JEP 472). Нативные библиотеки вроде Netty epoll или драйверов это задевает.
  • COMPAT на 25 не падает: JVM пишет в лог, что провайдер удалён, и использует CLDR. Заплатка из JDK 21 исчезает тихо.
  • За 25 идут 26 и 27: предупреждение при изменении final-полей (JEP 500), G1 по умолчанию при любом числе CPU (JEP 523), компактные заголовки (JEP 534).
Скрипт запуска передаёт -Djava.security.manager=allow -XX:MaxRAMFraction=2. Как поведут себя JDK 21 и JDK 25?

JDK 21 стартует с одним предупреждением: MaxRAMFraction deprecated. allow только разрешает Security Manager, и WARNING появится, когда код вызовет setSecurityManager. JDK 25 не создаст JVM. Первой сработает проверка флагов: Unrecognized VM option 'MaxRAMFraction=2'. Если убрать её, следующей будет java.lang.Error: A command line option has attempted to allow or enable the Security Manager. Обе ошибки видны в первые миллисекунды, если в CI запускать java $JAVA_OPTS -version.
