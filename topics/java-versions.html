Java: What's New

Новая JDK на ноутбуке ещё не означает новую Java в сервисе

Сервис уведомлений собирают на JDK 25, а контейнер в проде ещё запускает Java 21. Разработчик не использовал ни одной новой конструкции, но приложение падает до main. Номер Java относится сразу к синтаксису, доступным API, формату class-файла и JVM; эти границы должны согласоваться.

Самое интересное в современной Java — переход от ручных проверок и большого числа служебных классов к более точной модели данных и дешёвому ожиданию I/O. Для backend сначала изучи records вместе с sealed и pattern matching, затем virtual threads, затем Scoped Values. var, text blocks, новый switch и API коллекций облегчают ежедневный код; смена JVM приносит ещё и изменения GC, JIT и диагностики.

javac --release 21 проверяет язык и документированные API платформы 21, затем выпускает её формат байткода. Без этого флага javac 25 выпускает major 69, который JVM 21, понимающая major 65, не принимает. Вот полный исходник из проверенных демо и реальные команды:

// Проверенный RuntimeFloor.java; imports опущены.
public class RuntimeFloor {

        System.out.println("notifications ready");
    }

Совместимость не получается установкой одной версии в IDE: проверь JDK сборки, release приложения, требования зависимостей и образ запуска. --release проверяет твои исходники; чужой JAR, собранный для более новой JVM, всё ещё способен сломать запуск.

Помни изменения по задачам, а версии — по первой стабильной поставке

Релизная линия Java идёт небольшими шагами: после 9 новые feature releases выходят раз в полгода. LTS означает длительную поддержку выбранной линии у поставщика JDK. Это не особый язык и не единственное место появления фич: var стал стабильным в 10, а при переходе с 8 на LTS 11 ты получаешь его вместе с другими изменениями.

Таблица показывает удобные точки сравнения для backend. «Есть к этому LTS» включает промежуточные релизы, число рядом с фичей — первая окончательная поставка. Preview не считается окончательной, даже если её можно было попробовать раньше.

У OpenJDK 27 заметны compact object headers по умолчанию и G1 по умолчанию во всех окружениях, если сборщик не выбран явно. Эти нововведения сверены по JEP; исполняемые примеры этой страницы идут на 21 и 25.

Для интервью полезнее связка «проблема → фича → граница», чем перечень номеров. Например: sealed ограничивает наследников, record описывает данные, pattern switch обрабатывает варианты. Это три части одного решения, но ни одна не делает бизнес-модель или обработку ошибок правильной автоматически.

Records появились в Java 17, switch expressions — в Java 21.

Это удобные LTS, на которых фичи часто начинают применять. Records стабильны с 16, switch expressions — с 14; в 21 окончательно появился switch с pattern matching.

Компилятор берёт на себя больше работы, но сохраняет правила типов

var экономит повтор типа справа и слева, но Java остаётся статически типизированной. Компилятор выводит тип по инициализатору; он не пересматривает его после следующих присваиваний. var items = new ArrayList<String>() выводит конкретный ArrayList, а не интерфейс List. Это меняет доступные методы и выбор перегрузки, даже когда объект тот же.

У инициализатора с var нет ожидаемого типа слева. Поэтому пустой diamond в new ArrayList<>() здесь даёт ArrayList<Object>, а голая lambda или null не позволяют вывести нужный тип. var применяют к локальным переменным с инициализатором, не к полю и не к типу возврата; (var x) -> ... для параметров lambda — отдельное расширение 11. Это reserved type name, а не динамический тип и не обещание final.

Switch expression возвращает значение, поэтому каждый путь должен дать результат или бросить исключение. Стрелочная ветка не проваливается в следующую, блок возвращает значение через yield. Полный enum можно покрыть без default: при добавлении константы пересборка покажет пропущенную ветку. Text block остаётся String: он задаёт многострочное содержимое и отступы, но сам не подставляет параметры и не защищает SQL.

// Проверенный VarSwitchDemo.java; imports опущены.
public class VarSwitchDemo {
    enum Route { CARD, SBP }
    static String kind(List<String> value) { return "List"; }
    static String kind(ArrayList<String> value) { return "ArrayList"; }
    static String receipt(Route route, long cents) {
        long fee = switch (route) { // Java 14: each successful branch produces a value
            case CARD -> {
                long calculated = cents * 15 / 1000;
                yield calculated;
            }
            case SBP -> 0;
        };
        return """
                route=%s
                fee=%d
                """.formatted(route, fee).strip(); // Java 15: ordinary String, not a template engine
    }
    public static void main(String[] args) {
        var inferred = new ArrayList<String>(); // static type is ArrayList<String>, not List<String>
        List<String> explicit = inferred; // same object, different compile-time type
        String overloads = kind(inferred) + " / " + kind(explicit);
        if (!overloads.equals("ArrayList / List")) throw new AssertionError(overloads);
        System.out.println("overload=" + overloads);
        var diamond = new ArrayList<>(); // no target type: ArrayList<Object>
        diamond.add(10);
        diamond.add("note");
        System.out.println("diamond=" + diamond);
        String receipt = receipt(Route.CARD, 1000).replace('\n', '|');
        if (!receipt.equals("route=CARD|fee=15")) throw new AssertionError(receipt);
        System.out.println("receipt=" + receipt);
    }
}
overload=ArrayList / List
diamond=[10, note]
receipt=route=CARD|fee=15

Здесь перегрузку выбирает статический тип, а не объект. В receipt .formatted выполняет подстановку отдельно от text block; .strip удаляет крайние пробелы и переносы, замена newline на | сделана только для компактного вывода. Инварианты типов сохраняются, просто часть повторов исчезает.

Records и sealed идут дальше: данные и допустимые варианты становятся явными для компилятора. У record компоненты, конструктор, accessors, equals/hashCode и toString связаны одной декларацией; sealed закрывает набор прямых наследников. В Java 21 record pattern извлекает компоненты прямо в ветке switch. Final-ссылка record при этом не замораживает объект, на который она указывает:

// Проверенный DataPatternsDemo.java; imports опущены.
public class DataPatternsDemo {
    sealed interface Result permits Sent, SafeSent, Failed {}
    record Sent(List<String> ids) implements Result {} // final reference, mutable object still shared
    record SafeSent(List<String> ids) implements Result {
        SafeSent { ids = List.copyOf(ids); } // defensive snapshot, elements are immutable Strings
    }
    record Failed(String reason) implements Result {}
    static String describe(Result result) {
        return switch (result) { // Java 21: exhaustive type patterns and record deconstruction
            case Sent(var ids) -> "sent=" + ids.size();
            case SafeSent(var ids) -> "safe=" + ids.size();
            case Failed(var reason) -> "failed=" + reason;
        };
    }
    public static void main(String[] args) {
        var ids = new ArrayList<>(List.of("P1"));
        Result shared = new Sent(ids);
        Result snapshot = new SafeSent(ids);
        ids.add("P2"); // record's implicit final does not freeze ids
        String got = describe(shared) + "; " + describe(snapshot);
        if (!got.equals("sent=2; safe=1")) throw new AssertionError(got);
        System.out.println(got);
        System.out.println(describe(new Failed("timeout")));
    }
}
sent=2; safe=1
failed=timeout

Различие sent=2 и safe=1 вызвано владением списком, а не «особым record equals». Копия защищает структуру списка; для изменяемых элементов потребуется отдельно решить их владение. Подробные ограничения, конструкторы и эволюция иерархии — в Records и Sealed & Pattern Matching; правила отступов — в Strings.

Новые API упрощают вызов, но не меняют смысл ответа и владение данными

HttpClient из java.net.http стал стандартным в 11: один клиент переиспользует соединения, HttpRequest описывает запрос, BodyHandler выбирает обработку тела. send ждёт ответ, sendAsync возвращает CompletableFuture. Асинхронность задаёт способ ожидания, а не успех бизнес-операции: HTTP 500 — полученный ответ, его статус проверяет приложение.

Демо на JDK 21 поднимает loopback-сервер с ответом 500. Оба пути завершаются нормально. Обрыв сети или timeout — другой исход с исключением; retry и идемпотентность нужно проектировать отдельно. AutoCloseable и close у HttpClient доступны с 21, поэтому try-with-resources ниже нельзя целиком переносить на 11:

// Проверенный HttpClientDemo.java; imports опущены.
public class HttpClientDemo {
    public static void main(String[] args) throws Exception {
        var server = HttpServer.create(new InetSocketAddress("127.0.0.1", 0), 0);
        server.createContext("/bank", exchange -> { // fixture always responds with a real HTTP 500
            byte[] body = "bank unavailable".getBytes(StandardCharsets.UTF_8);
            exchange.sendResponseHeaders(500, body.length);
            try (var out = exchange.getResponseBody()) { out.write(body); }
            finally { exchange.close(); }
        });
        server.start();
        try (var client = HttpClient.newHttpClient()) { // close/AutoCloseable is available since Java 21
            var request = HttpRequest.newBuilder(URI.create(
                    "http://127.0.0.1:" + server.getAddress().getPort() + "/bank"))
                    .timeout(Duration.ofSeconds(3)).GET().build();
            var sync = client.send(request, HttpResponse.BodyHandlers.ofString());
            var async = client.sendAsync(request, HttpResponse.BodyHandlers.ofString()).join();
            if (sync.statusCode() != 500 || async.statusCode() != 500
                    || !sync.body().equals("bank unavailable")) throw new AssertionError();
            System.out.println("sync=" + sync.statusCode() + "; async=" + async.statusCode()
                    + "; body=" + sync.body()); // HTTP error status is still a successfully received response
        } finally { server.stop(0); }
    }
}
sync=500; async=500; body=bank unavailable

В сервисе клиент живёт дольше одного запроса, чтобы соединения переиспользовались. Пример закрывает его и сервер после опыта; реального банка, TLS и HTTP/2 здесь нет. Протоколы и безопасность URL — в HTTP, HTTP/2 & HTTP/3 и Web Security.

SequencedCollection, SequencedSet и SequencedMap с 21 выражают encounter order: есть первый, последний элемент и обратное представление. Это общий контракт для упорядоченных коллекций, а не требование сортировать каждую коллекцию. У List, Deque и LinkedHashSet появляется единообразный доступ к концам; HashSet такого порядка не обещает.

// Проверенный SequencedDemo.java; imports опущены.
public class SequencedDemo {
    public static void main(String[] args) {
        var original = new ArrayList<>(List.of("P1", "P2"));
        var snapshot = List.copyOf(original);
        var reverse = original.reversed(); // Java 21: a view over the same data
        reverse.addFirst("P3"); // first in reverse order is last in original order
        if (!original.equals(List.of("P1", "P2", "P3"))) throw new AssertionError();
        System.out.println("original=" + original);
        System.out.println("reverse=" + reverse);
        System.out.println("snapshot=" + snapshot);
        try {
            snapshot.addFirst("P4"); // new API does not make an immutable list mutable
            throw new AssertionError("mutation accepted");
        } catch (UnsupportedOperationException expected) {
            System.out.println("snapshot mutation=" + expected.getClass().getSimpleName());
        }
    }
}
original=[P1, P2, P3]
reverse=[P3, P2, P1]
snapshot=[P1, P2]
snapshot mutation=UnsupportedOperationException

Reverse view отражает изменения оригинала и, если разрешено, записывает изменения обратно. Immutable list не принимает addFirst; SortedSet также не позволяет навязать первый элемент в обход сортировки. Выбирай snapshot, когда нужен независимый результат, и view, когда нужна работа с теми же данными в обратном порядке. Иерархия и ограничения подробнее в Collections Overview.

Виртуальные потоки удешевляют ожидание, а не увеличивают ёмкость банка или БД

До virtual threads thread-per-request заставлял держать OS thread, пока запрос ждёт сеть. Виртуальный поток — экземпляр Thread, который JDK выполняет на carrier threads. При поддерживаемом блокирующем ожидании он паркуется и освобождает carrier; другой virtual thread продолжает работу. Поэтому последовательный код остаётся читаемым, а много одновременных I/O-запросов требует меньше OS threads.

В 21 virtual threads окончательные: Executors.newVirtualThreadPerTaskExecutor() создаёт новый VT на задачу. Их не объединяют в пул ради экономии потока; ограничивают дефицитный ресурс — подключения, запросы к банку, одновременно обрабатываемые данные. CPU-задачи по-прежнему ограничены ядрами; тысячи VT не сделают арифметику быстрее.

В проверенном опыте 12 задач, но только два permit. Barrier вынуждает пары держателей пересекаться, поэтому максимум точно достигает двух без измерения времени. Это модель ограничения ресурса; она не заменяет нагрузочное испытание драйвера или базы:

// Проверенный VirtualThreadsDemo.java; imports опущены.
public class VirtualThreadsDemo {
    public static void main(String[] args) throws Exception {
        var permits = new Semaphore(2); // fixture for a scarce external resource, not a real DB pool
        var pair = new CyclicBarrier(2); // forces two holders to overlap without a timing benchmark
        var active = new AtomicInteger();
        var peak = new AtomicInteger();
        var tasks = new ArrayList<Future<Boolean>>();
        try (var executor = Executors.newVirtualThreadPerTaskExecutor()) {
            for (int i = 0; i < 12; i++) tasks.add(executor.submit(() -> {
                permits.acquire(); // waiting tasks do not each require an OS thread
                int users = active.incrementAndGet();
                peak.accumulateAndGet(users, Math::max);
                try {
                    pair.await(3, TimeUnit.SECONDS);
                    return Thread.currentThread().isVirtual();
                } finally { active.decrementAndGet(); permits.release(); }
            }));
            boolean allVirtual = true;
            for (var task : tasks) allVirtual &= task.get(5, TimeUnit.SECONDS);
            if (!allVirtual || peak.get() != 2 || active.get() != 0) throw new AssertionError();
            System.out.println("completed=" + tasks.size() + "; max resource users=" + peak.get()
                    + "; all virtual=" + allVirtual);
        }
    }
}
completed=12; max resource users=2; all virtual=true

Важно помнить версию механизма. В исходной реализации HotSpot 21 блокирование внутри synchronized может удерживать carrier — pinning. С JDK 24 HotSpot устранил прежнее pinning, связанное с synchronized, поэтому в 25 совет «перепиши все synchronized на ReentrantLock» уже не является общей рекомендацией. Native-вызовы и другие границы требуют отдельного анализа; исчезновение этой причины pinning не отменяет contention и deadlock.

Выбор между блокирующей моделью, CompletableFuture и реактивным стеком зависит также от streaming, backpressure и интеграций. Подробные carriers, диагностика и сценарии — в Virtual Threads, лимиты executor — в Executors. ThreadLocal работает и в VT, но дорогие объекты «по одному на поток» при большом числе задач стоит пересмотреть.

В Java 25 контекст получает границы вызова, а JVM — новые способы оптимизации

В request chain нужно передать tenant или principal через несколько методов, не добавляя параметр в каждую сигнатуру. ThreadLocal позволяет читать контекст, но время жизни значения приходится ограничивать вручную, иначе следующий запрос в том же platform thread может получить старое значение. ScopedValue связывает значение с выполнением run или call и автоматически завершает привязку при выходе.

Scoped Values окончательные с 25; в 21 они были preview. Это неизменяемая привязка, не глубокая неизменяемость переданного объекта. Nested binding может задать другое значение для своих вызовов, затем внешнее восстанавливается. Для контекста выбирай неизменяемые данные и закрытый ключ ScopedValue, чтобы посторонний код не получал возможность читать или переопределять его.

// Проверенный ScopedValuesDemo.java; imports опущены.
public class ScopedValuesDemo {
    private static final ScopedValue<String> TENANT = ScopedValue.newInstance();
    static void observe(String label, String expected) {
        if (!TENANT.get().equals(expected)) throw new AssertionError();
        System.out.println(label + "=" + TENANT.get());
    }
    public static void main(String[] args) {
        ScopedValue.where(TENANT, "A").run(() -> {
            observe("outer", "A");
            try {
                ScopedValue.where(TENANT, "B").run(() -> {
                    observe("inner", "B");
                    throw new IllegalStateException("fixture");
                });
            } catch (IllegalStateException expected) {
                if (!expected.getMessage().equals("fixture")) throw expected;
            }
            observe("restored", "A"); // nested binding disappears even after an exception
            var child = Thread.startVirtualThread(() -> {
                if (TENANT.isBound()) throw new AssertionError("unexpected inheritance");
                System.out.println("plain child bound=" + TENANT.isBound());
            });
            try { child.join(); }
            catch (InterruptedException ex) { Thread.currentThread().interrupt(); throw new RuntimeException(ex); }
        });
        if (TENANT.isBound()) throw new AssertionError("binding leaked");
        System.out.println("after bound=" + TENANT.isBound());
    }
}
outer=A
inner=B
restored=A
plain child bound=false
after bound=false

Plain child не наследует binding просто потому, что он virtual thread. Передача контекста дочерним задачам поддерживается StructuredTaskScope, который удерживает их время жизни внутри области родителя. Но в 25 Structured Concurrency — пятый preview, хотя Scoped Values уже final. Область ThreadLocal и область вызова — разные способы передачи данных, не взаимозаменяемые имена API.

Что ещё стоит увидеть в 25

Instance main можно объявить без static и без параметра String[]. Compact source file убирает явную оболочку class и автоматически импортирует типы java.base. В окончательной версии методы IO не импортируются статически: нужен IO.println, а не просто println. Полный проверенный compact-файл выглядит так:

// Проверенный CompactReceipt.java.
// Java 25: compact source file implicitly imports java.base types, but not static IO methods.
void main() {
    IO.println(List.of("P1", "P2").reversed());
}
[P2, P1]

В обычном классе import module позволяет импортировать публичные типы экспортируемых пакетов модуля; он не скачивает библиотеку и не добавляет модуль в runtime image. Flexible constructor body разрешает подготовить и проверить аргументы перед super. В примере пустое имя отклоняется до конструктора родителя; чтение недостроенного this не используется:

// Проверенный Java25Syntax.java.
import module java.base; // imports public types from the module's exported packages

public class Java25Syntax {
    static class Named {
        static int constructed;
        final String name;
        Named(String name) { constructed++; this.name = name; }
    }
    static class Receipt extends Named {
        Receipt(String raw) {
            String normalized = raw.strip(); // Java 25: validate arguments before super
            if (normalized.isEmpty()) throw new IllegalArgumentException("empty");
            super(normalized); // constructor prologue did not read this or call an instance method
        }
    }
    void main() { // Java 25: instance main, launcher constructs Java25Syntax
        try {
            new Receipt("  ");
            throw new AssertionError("empty accepted");
        } catch (IllegalArgumentException expected) {
            if (Named.constructed != 0) throw new AssertionError();
            System.out.println("rejected before base=" + (Named.constructed == 0));
        }
        var receipt = new Receipt("  P7  ");
        System.out.println("name=" + receipt.name + "; base calls=" + Named.constructed);
        System.out.println("month=" + LocalDate.of(2025, 9, 16).getMonth()); // resolved by module import
    }
}
rejected before base=true
name=P7; base calls=1
month=SEPTEMBER

Более узкие, но интересные изменения к 25: Stream Gatherers, окончательные с 24, добавляют настраиваемые промежуточные операции, например оконную обработку. FFM API, окончательное с 22, описывает доступ к памяти вне heap и вызовы native-функций без обязательной JNI-обвязки; время жизни и допуск native-вызовов всё равно контролируются. Это отдельные механизмы, здесь показано их место, а не курс native interop.

Для эксплуатации важны AOT-подготовка и профили, новые события JFR и compact object headers. В проверенной OpenJDK 25.0.2 UseCompactObjectHeaders=false: фича окончательная, но включается отдельно через -XX:+UseCompactObjectHeaders. Измеряй heap, паузы, CPU и startup на своей нагрузке; наличие нового флага не доказывает ускорения. Формат объектов — в Object Layout, инструменты — в JVM Diagnostics.

В срезе 25 Stable Values ещё preview, Vector API — incubator. К 27 Stable Values развилась в Lazy Constants, Structured Concurrency остаётся preview. Не переносить имя или API из старого preview в проект по памяти: сверь JEP нужной версии. В 27 compact object headers включены по умолчанию (JEP 534), а value objects из Project Valhalla приходят preview в 28 — в Value Objects.

Внедряй фичу по её статусу и проверяй весь путь до контейнера

Preview означает полностью реализованную, но ещё непостоянную фичу. Обратная связь может изменить синтаксис, имя или контракт, а фича может не стать окончательной. Например, switch expression в preview 12 возвращал значение через break, в 13 перешёл на yield и в 14 стал final. Incubator обычно отделяет новый API в модуле jdk.incubator.*, experimental относится к экспериментальной возможности JVM; это разные режимы включения.

Для language preview нужны --enable-preview при компиляции и запуске, причём feature release должен совпадать. Нельзя новой JDK включить старую preview через --release: она компилирует preview только своей версии. Такой бинарник носит специальный minor 65535 и не становится переносимым от одного runtime-флага.

Unnamed variable была preview в 21 и стала final в 22. Тем не менее старый class 65.65535 не запускается в 25: final-статус исходной конструкции не меняет уже выпущенный бинарник. Ниже полный исходник, команды и итог драйвера, который проверяет return code, диагностику и байты заголовка:

// Проверенный Preview21.java; imports опущены.
public class Preview21 {
    public static void main(String[] args) {
        int _ = 42; // unnamed variable: preview in Java 21, permanent in Java 22
        System.out.println("preview ran");
    }
}

Перед переходом сервиса обнови поддерживаемые библиотеки, плагины сборки, тестовые агенты и runtime image; зафиксируй toolchain и --release в Maven/Gradle. Что именно ломается при переходе и как раскатывать новую версию по шагам — в Java Upgrade. Прогоняй unit, интеграционные тесты и smoke-запуск собранного артефакта именно в целевом образе. Проверяй нужный patch level и условия поддержки выбранного поставщика, а не только большое число на версии.

Старые внутренние API, глубокая reflection и удалённые части JDK могут потребовать правки зависимостей. Например, JAXB перестал входить в JDK с 11, а усиленная инкапсуляция в 17 закрыла многие внутренние элементы. --add-opens открывает конкретный пакет для глубокой reflection, но не исправляет несовместимый байткод и не заменяет обновление библиотеки. Следи также за изменениями charset и поведения среды в IO & NIO.

Для твоей подготовки порядок такой: понимать базу 8; уверенно объяснять язык и данные, доступные к 17; уметь выбрать и ограничить virtual threads на 21; знать Scoped Values и статус важных фич 25. Новую JVM оценивай вместе с измерениями и диагностикой, а код переписывай там, где меняется ясность или поведение. Эти демо проверяют конкретные правила на JBR 21.0.11 и OpenJDK 25.0.2; производительность приложения, TLS, реальные БД, наследование через preview StructuredTaskScope и запуск на JDK 27 не проверялись.

  • Разделяй JDK сборки, --release, API зависимостей и JVM запуска; новое число в IDE не согласует их автоматически.
  • Первая final-версия фичи и удобный LTS для внедрения — разные даты: var 10, switch expression 14, text blocks 15, records 16.
  • Records, sealed и patterns делают модель данных точнее, но не обеспечивают глубокую неизменяемость или корректность бизнеса.
  • Virtual threads масштабируют ожидание I/O; ресурсные лимиты, backpressure и CPU остаются отдельными ограничениями.
  • Scoped Values final в 25, Structured Concurrency там preview; доступность родственного API нельзя выводить из названия проекта Loom.
  • Новые runtime-возможности проверяй по версии и нагрузке. Preview class требует своей JVM и флага; LTS относится к поддержке поставщика.

На собеседовании

Что важного изменилось в Java после 8?

Я группирую изменения по тому, что они дают сервису. Для читаемости появились var, switch expressions и text blocks. Для модели данных — records, sealed и pattern matching: можно задать закрытые варианты результата, а компилятор проверит их обработку. Из API выделяю встроенный HttpClient и единый контракт упорядоченных коллекций.

Для I/O-нагрузки наиболее заметны virtual threads, окончательные в 21: сохраняю блокирующий стиль кода, а ожидающие задачи не занимают каждая OS thread. В 25 окончательны Scoped Values для контекста с ограниченным временем жизни. Версию называю точно: records final с 16, switch expressions с 14; попадание в LTS 17 не означает, что они впервые появились там.

  • К LTS 25 относятся и промежуточные нововведения: FFM final в 22, Gatherers и устранение synchronized pinning в 24. Это не список «всё впервые в 25».
  • JDK обновляет не только исходный язык: GC, AOT и JFR влияют на эксплуатацию даже без переписывания кода; ускорение подтверждаю измерением.
  • Статус соседних фич различается: Scoped Values final, Structured Concurrency preview в 25. LTS не делает все включённые preview постоянными.
В презентации написано «var — 11, text blocks — 17, pattern switch — 17». Что исправить?

Если речь о первой final-поставке: var — 10, text blocks — 15, pattern switch — 21. Если автор группирует по LTS, нужно явно назвать это группировкой; в 17 pattern switch ещё не final. Не путать его с обычными switch expressions, final с 14.

var — это динамическая типизация? Всегда ли он безопасно заменяет явный тип?

Нет. Я даю компилятору вывести статический локальный тип по инициализатору. Дальше действуют обычные правила присваивания и перегрузки. В var list = new ArrayList<String>() выводится ArrayList<String>, а в явном List<String> list — интерфейс; один объект может попасть в разные перегрузки.

Пишу var, когда по выражению и имени понятно значение и мне подходит выведенный тип. Оставляю явный тип для важного контракта или неочевидного результата. var не делает переменную final и не подходит для полей или типов возврата; lambda без целевого функционального интерфейса и null не дают достаточного типа.

  • Инициализатор с var не получает target type слева: diamond без аргументов способен вывести Object и незаметно ослабить модель данных.
  • var — reserved type name, а не общий keyword. Синтаксис параметров lambda с var появился отдельно в 11 и не разрешает var в обычной сигнатуре метода.
  • При замене меняется набор видимых методов и выбор overload; считаю это изменением поведения кода, а не чистой косметикой.

Зачем backend virtual threads и Scoped Values? Что они не решают?

Я беру virtual threads для большого числа задач, которые в основном ждут I/O. JDK планирует их на общих carrier threads, поэтому не держу отдельный OS thread на каждое ожидание. При этом отдельно ограничиваю банк или БД: число виртуальных потоков не добавляет подключений и не ускоряет CPU.

Scoped Values передают контекст по цепочке вызовов и завершают привязку при выходе из run или call. Это удобно для неизменяемого tenant или principal, когда лишние параметры раздувают внутренние API. Не обещаю автоматическую передачу в любую задачу executor: plain virtual child binding не наследует.

  • Pinning зависит от JDK: в 21 synchronized может удерживать carrier, с 24 прежняя причина устранена. Native boundaries и contention диагностирую отдельно.
  • Привязка ScopedValue неизменяема, но mutable payload остаётся mutable. Ключ ограничиваю по доступу, контекст проектирую с ясным владением.
  • Наследование binding через StructuredTaskScope связано с ограниченным временем жизни дочерних задач; в 25 этот API ещё preview, а не готовая замена любого ExecutorService.
В сервисе 10 000 VT и 20 соединений БД. Сколько запросов к БД выполняется одновременно?

Не больше ёмкости пула — 20, если каждый держатель использует одно соединение. Остальные ждут или выполняют другую работу. Добавление VT удешевляет часть ожиданий, но не снимает нагрузку с БД; нужны лимиты времени, очередей и приёма запросов.

Как безопасно обновить Java и почему новая JVM не запускает старый preview class?

Я отдельно фиксирую JDK сборки, --release и JVM в контейнере, обновляю поддерживаемые зависимости и инструменты. Прогоняю собранный артефакт в целевой среде. source и target без старых API недостаточны: код может скомпилироваться с вызовом метода, которого нет на старой платформе.

Preview привязан к feature release. Для language preview нужен флаг при сборке и запуске, а class с minor 65535 разрешён только JVM этой версии. Поэтому preview class из 21 новая JVM 25 отвергает даже с флагом; пересобираю исходники под нужный релиз и проверяю изменения API. LTS означает политику поддержки, не исключение из этого правила.

  • --release не пересобирает транзитивные JAR и не проверяет весь runtime image: их минимальные версии и доступность модулей проверяю отдельно.
  • Новая JVM не гарантирует совместимость внутренних API или глубокой reflection; --add-opens точечно открывает пакет, но не решает все виды несовместимости.
  • Фича бывает final, но ещё выключена по умолчанию, как compact headers в 25. Preview, incubator, experimental и runtime defaults проверяю по отдельности.
Можно ли на javac 25 собрать preview Java 21 через --enable-preview --release 21?

Нет: javac разрешает preview только своей текущей версии. Для старой preview нужна соответствующая JDK; для перехода на 25 пересмотри исходник и компилируй его правилами 25. Окончательная unnamed variable в 25 не требует preview, но старый class 65.65535 нужно заменить.
