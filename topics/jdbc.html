JDBC & Connection Pools

Платёж выполняет SQL через соединение с базой. DataSource даёт приложению это соединение, а пул позволяет использовать уже открытые соединения повторно. Пока код держит выданную оболочку, слот занят даже во время ожидания банка. PreparedStatement передаёт значения отдельно от SQL, JdbcTemplate управляет обычной работой с ресурсами. Чтобы списание и зачисление завершились вместе, им нужна одна транзакция на одном соединении.

Платёж может ждать соединение ещё до первого SQL

После роста нагрузки платежи стали завершаться через несколько секунд. База почти свободна, тяжёлых запросов в её журнале нет. Команда ускоряет SELECT, но задержка остаётся. Оказывается, запросы стоят перед DataSource.getConnection(): все соединения заняты другими платежами.

Каждый платёж взял соединение, прочитал счёт и отправил запрос в банк. Ответ банка ждёт две секунды, и всё это время соединение удерживается. Следующему платежу нужен свободный слот, хотя SQL предыдущего давно закончился. Поэтому время выполнения SQL и время владения соединением могут отличаться в десятки раз.

JDBC — интерфейсы Java для работы с реляционной базой. Конкретный драйвер превращает операции этих интерфейсов в протокол PostgreSQL, MySQL или другой СУБД. Connection представляет соединение и его состояние: текущую транзакцию, autoCommit, изоляцию и параметры сессии. Код SQL выполняется в базе; JVM получает результат через драйвер.

DataSource отвечает за получение соединений. Сам интерфейс не обещает пул: простая реализация способна открывать новое соединение при каждом обращении. HikariCP — реализация с пулом. Она хранит ограниченный набор открытых соединений и выдаёт приложению временный доступ к одному из них. DriverManager удобен для небольшого самостоятельного опыта, но сам повторное использование соединений не организует.

Дальше разберём путь платёжного запроса от получения соединения до его возврата. Полный JdbcDemo.java запускается на JDK 21, Framework 7.0.9, HikariCP 7.0.2 и H2 2.4.240; версии библиотек задаёт BOM Boot 4.1.1. H2 работает внутри JVM, поэтому пример доказывает поведение JDBC и пула, а сетевые сбои PostgreSQL здесь не имитируются.

Пул выдаёт временную оболочку над живым соединением

Открыть сетевое соединение — значит установить связь, пройти аутентификацию и создать сессию базы. Делать это заново для каждого SQL дорого. Пул разделяет время жизни физического соединения и время, когда конкретный код им пользуется. getConnection() выдаёт оболочку, а close() этой оболочки возвращает соединение в пул.

Поставим в демо один слот. Пока первое соединение удерживается, тот же поток попробует получить второе. Никакого SQL второе обращение выполнить не успеет: получение закончится по сроку ожидания пула. Затем закроем первую оболочку и возьмём следующую. В H2 можно открыть оболочку через unwrap и сравнить настоящий объект соединения.

HikariConfig config = new HikariConfig();
config.setJdbcUrl("jdbc:h2:mem:jdbc-demo;DB_CLOSE_DELAY=-1");
config.setUsername("sa");
config.setMaximumPoolSize(1); // Всего один слот: занятые и свободные вместе.
config.setMinimumIdle(1);
config.setConnectionTimeout(300); // Миллисекунды ожидания свободного соединения.
config.setValidationTimeout(250);

// В полном main пул закрывается после всех опытов через try-with-resources.
HikariDataSource pool = new HikariDataSource(config);
Connection first = pool.getConnection();
var physical = first.unwrap(JdbcConnection.class); // H2: только для наблюдения в опыте.
try (first) {
    try (Connection second = pool.getConnection()) {
        // SQL пошёл бы только после успешного получения соединения.
    } catch (SQLException expected) {
        System.out.println("second borrow=" + expected.getClass().getSimpleName());
    }
}
System.out.println("logical closed=" + first.isClosed() + ", physical closed=" + physical.isClosed());
try (Connection next = pool.getConnection()) {
    System.out.println("new wrapper=" + (next != first)
        + ", same physical=" + (next.unwrap(JdbcConnection.class) == physical));
}
cd examples/data
./run.sh JdbcDemo # Один запуск показывает пул, параметры SQL и три исхода перевода.
held active=1, idle=0
second borrow=SQLTransientConnectionException
logical closed=true, physical closed=false
new wrapper=true, same physical=true

Это первый фрагмент вывода полного демо. Закрытая оболочка больше непригодна к работе, но физическое соединение живо. Следующий заём получил другую оболочку над тем же объектом. unwrap здесь нужен только для доказательства: рабочий код не должен сохранять физический объект и продолжать через него работу после возврата в пул.

Пул сбрасывает отслеживаемые стандартные свойства соединения перед повторным использованием. Поэтому предыдущий код не должен оставлять следующему заёмщику свой autoCommit или изоляцию. Но произвольный SQL с настройкой сессии, временные объекты и состояние драйвера требуют отдельного внимания: пул не понимает смысл всех команд, выполненных в базе.

Connection берут на короткий участок работы и закрывают через try-with-resources. Её не хранят в singleton-сервисе и не используют одновременно несколькими платежами. Общее физическое соединение означает общие транзакцию и состояние сессии. Даже если драйвер допускает некоторые параллельные обращения, независимых транзакций из этого не получится.

PreparedStatement отделяет значения от структуры SQL

Платёж указывает счёт и сумму. Если склеить счёт со строкой SQL, значение сможет превратиться в часть условия. PreparedStatement задаёт структуру запроса с ?, а методы setString и setLong передают типизированные значения параметров. Кавычки и слова SQL внутри значения остаются данными.

Списание в демо проверяет остаток в той же команде, которая его меняет. Между отдельным SELECT остатка и последующим UPDATE другой платёж мог бы потратить деньги. Условие cents >= ? и проверка количества изменённых строк дают понятный результат одной операции.

try (var statement = connection.prepareStatement(
        "update account set cents = cents - ? where id = ? and cents >= ?")) {
    statement.setLong(1, 1_000L); // Индексы JDBC начинаются с 1. Сумма в копейках.
    statement.setString(2, "payer");
    statement.setLong(3, 1_000L); // Остаток проверяется атомарно вместе со списанием.
    if (statement.executeUpdate() != 1) {
        throw new IllegalStateException("payer missing or insufficient funds");
    }
} // Statement закрыт; соединение остаётся у вызывающего кода.

executeUpdate() возвращает число изменённых строк. Это часть проверки бизнес-операции: ноль означает, что счёт не найден или условие остатка не выполнено. executeQuery() возвращает ResultSet. Его курсор сначала стоит перед первой строкой; чтение начинается после успешного next(). Закрывать нужно результат, statement и затем соединение — каждый на своём уровне владения.

Проверим строку, которая при склейке могла бы изменить условие. Этот фрагмент полного демо использует JdbcTemplate, который создаёт PreparedStatement и связывает параметр за нас:

String input = "payer' OR '1'='1";
var matches = jdbc.query("select id, cents from account where id = ?",
    (rs, rowNum) -> new Account(rs.getString("id"), rs.getLong("cents")), input);
System.out.println("parameter rows=" + matches.size()); // Ищем именно такой id целиком.
parameter rows=0

В таблице есть payer и merchant, но нет счёта с указанной длинной строкой. Значение не расширило выборку. Параметр может заменить значение; имя таблицы, столбца и направление сортировки через ? не выбирают. Для таких частей нужен ограниченный набор заранее известных вариантов SQL.

Любой PreparedStatement гарантирует единственную компиляцию запроса на сервере и всегда работает быстрее Statement.

JDBC задаёт интерфейс подготовки и параметров. Момент серверной подготовки, протокол и кеш плана зависят от драйвера и базы. Польза параметров для структуры SQL сохраняется, а производительность измеряют на конкретной системе. HikariCP сам кеш PreparedStatement не создаёт.

Для больших наборов однотипных записей полезен batch: параметры нескольких выполнений собираются и отправляются через addBatch / executeBatch. Драйвер может сократить число сетевых обменов. Batch не задаёт общую транзакцию сам; при частичном сбое учитывай режим autoCommit, сведения BatchUpdateException и возможности драйвера.

JdbcTemplate управляет ресурсами, пока ты управляешь SQL

В ручном JDBC легко закрыть statement, но забыть результат; обработать ошибку SQL, но потерять первоначальную причину при close. JdbcTemplate берёт на себя получение соединения, создание и закрытие обычных ресурсов и перевод SQLException в иерархию DataAccessException. SQL и преобразование строки в объект остаются у приложения.

Созданный и настроенный JdbcTemplate можно разделять между репозиториями. Он хранит DataSource и параметры работы, а не одну занятую Connection. Поэтому singleton-шаблон безопасен для параллельного использования после настройки. Менять его общие настройки перед каждым запросом нельзя: соседний запрос использует тот же объект.

record Account(String id, long cents) {}
JdbcTemplate jdbc = new JdbcTemplate(pool); // Общий шаблон, соединение берётся на время работы.

var payer = jdbc.queryForObject("select id, cents from account where id = ?",
    (rs, rowNum) -> new Account(rs.getString("id"), rs.getLong("cents")), "payer");
// RowMapper читает текущую строку: next() вызывает сам шаблон.
System.out.println("mapped=" + payer);

try {
    jdbc.queryForObject("select cents from account where id = ?", Long.class, "missing");
} catch (DataAccessException expected) {
    System.out.println("missing row=" + expected.getClass().getSimpleName());
}
try {
    jdbc.update("insert into account(id, cents) values (?, ?)", "payer", 0L);
} catch (DataAccessException expected) {
    System.out.println("duplicate=" + expected.getClass().getSimpleName());
}
mapped=Account[id=payer, cents=10000]
missing row=EmptyResultDataAccessException
duplicate=DuplicateKeyException

Показаны строки вывода того же запуска с пропуском строки parameter rows из предыдущего шага. queryForObject ожидает ровно одну строку. Ноль строк даёт EmptyResultDataAccessException, несколько — ошибку количества строк. Это отличается от SQL NULL в найденной строке: значение может быть null, хотя строка существует. В нашей таблице cents объявлено NOT NULL.

query обычно возвращает список и подходит для выборки произвольного размера. RowMapper преобразует одну текущую строку; он не должен сам перемещать курсор. При чтении допускающего NULL числового столбца getLong даёт ноль, и нужен wasNull либо чтение объектного значения. Иначе «остаток отсутствует» превратится в «остаток равен нулю».

Исключения Spring позволяют различать повтор ключа, нарушение ограничения и ошибку доступа независимо от прямой зависимости на SQLException. Конкретное отображение зависит от SQLState, кодов ошибки и драйвера. Перевод исключения сам по себе не откатывает всю бизнес-операцию и не делает повтор безопасным.

Обычная выборка в список закрывает JDBC-ресурсы до возврата результата. При queryForStream владение меняется: возвращённый Stream нужно закрыть, обычно через try-with-resources. Пока он читается, результат и соединение могут оставаться заняты. fetchSize регулирует поведение получения строк у драйвера; он не превращает уже собираемый список в обработку с постоянным расходом памяти.

Как шаблон узнаёт о Spring-транзакции

JdbcTemplate получает соединение через DataSourceUtils. Если менеджер Spring уже привязал соединение этой DataSource к текущему потоку, шаблон использует его. После отдельного SQL ресурс освобождается логически; физическое соединение остаётся у транзакции до её конца.

Ручной вызов setAutoCommit(false) на отдельно взятой Connection такую привязку не создаёт. Если, удерживая её, вызвать JdbcTemplate, тот может запросить другое соединение. В пуле из одного слота получится ожидание самого себя, а в большем пуле SQL окажется в другой транзакции. Ручная транзакция демо поэтому выполняет обе команды напрямую через свою Connection. Работа менеджера и прокси разобрана в Transactions.

NamedParameterJdbcTemplate добавляет именованные параметры, например :accountId, а JdbcClient предлагает связный API для обычных запросов. Они используют ту же инфраструктуру JDBC. Выбор удобной записи не меняет правил владения соединением и границы транзакции.

Списание и зачисление должны завершиться на одном соединении

У плательщика 10 000 копеек, у магазина — ноль. Перевод на 1 000 копеек состоит из двух UPDATE. Между ними приложение готовит квитанцию и падает. При стандартном autoCommit=true списание уже зафиксировано отдельной транзакцией, а зачисление ещё не произошло. Закрытие соединения отменить зафиксированное списание не может.

try (Connection connection = pool.getConnection()) {
    debit(connection); // При autoCommit=true UPDATE фиксируется отдельно.
    throw new IllegalStateException("receipt failed"); // До credit(connection) не дошли.
} catch (IllegalStateException expected) {
    System.out.println("autoCommit failure: " + balances(jdbc));
}
autoCommit failure: payer=9000, merchant=0

Чтобы обе записи составили одну операцию, берём одно соединение, выключаем autoCommit до первого SQL и фиксируем только после успеха. При ошибке явно вызываем rollback. Реальное списание и зачисление из демо проверяют число изменённых строк; исчезнувший магазин также сорвёт перевод, и списание будет отменено.

try (Connection connection = pool.getConnection()) {
    connection.setAutoCommit(false); // Одна JDBC-транзакция для обеих команд.
    try {
        debit(connection); // UPDATE с проверкой остатка из шага 3.
        if (fail) throw new IllegalStateException("receipt failed");
        credit(connection); // UPDATE магазина; также требует ровно одну изменённую строку.
        connection.commit(); // Теперь фиксируем обе записи.
    } catch (SQLException | RuntimeException failure) {
        try {
            connection.rollback(); // Отменяем все изменения этой транзакции.
        } catch (SQLException rollbackFailure) {
            failure.addSuppressed(rollbackFailure); // Сохраняем исходную ошибку перевода.
        }
        throw failure;
    }
} // Hikari очищает стандартное состояние и возвращает соединение в пул.

После первого неудачного опыта демо восстанавливает исходные остатки. Затем запускает транзакционный вариант с ошибкой и проверяет новое получение соединения. После этого повторяет перевод без ошибки. Это оставшиеся строки вывода:

rollback: payer=10000, merchant=0
after return autoCommit=true
commit: payer=9000, merchant=1000

Факт закрытия ресурса и исход транзакции — разные вопросы. JDBC советует завершить активную транзакцию через commit или rollback до close; результат закрытия незавершённой транзакции зависит от реализации. Hikari умеет откатить оставленную изменённую транзакцию при возврате, но это последняя защита пула. Платёжный код должен явно выбирать исход и обрабатывать его ошибку.

Переключать autoCommit обратно в true до завершения работы опасно: JDBC фиксирует текущую транзакцию при таком изменении режима. В нашем коде возврат состояния происходит после явного commit или rollback. Если соединение взято и управляется менеджером Spring, вручную менять режим, фиксировать или закрывать его тоже не нужно: этим владеет менеджер.

При сетевом разрыве во время commit приложение может получить исключение уже после фиксации в базе. Ошибка ответа не доказывает rollback. Для безопасного повтора платежа нужны идентификатор операции, уникальное ограничение и возможность проверить результат. Повторять весь перевод только по классу SQLException опасно.

Одна локальная JDBC-транзакция охватывает одну базу на одном соединении. Внешний банк её участником не становится. Удерживать блокировки и слот пула на всём внешнем вызове обычно дорого; согласование состояний банка и локального журнала проектируют отдельно. Изоляция, распространение и границы @Transactional разобраны в Transactions.

Настраивай время владения соединением и общий бюджет базы

Вернёмся к задержке платежей. Начни с места ожидания: получение соединения, исполнение SQL, блокировка в базе или внешний вызов. Для пула полезны число занятых и свободных соединений, число ожидающих потоков, время получения и время использования. Для базы — активные запросы, блокировки и план медленного SQL. Пустой журнал SQL при очереди за соединением не означает, что пул сломан.

В обычном Boot стартер spring-boot-starter-jdbc подключает HikariCP. При доступном Hikari Boot предпочитает его и создаёт DataSource по настройкам; собственный бин DataSource меняет эту автоконфигурацию. Шаблон JDBC работает поверх той же DataSource. Пример настроек для сервиса с PostgreSQL, где драйвер PostgreSQL добавлен отдельно:

spring:
  datasource:
    url: jdbc:postgresql://db:5432/payments
    username: ${DB_USER}
    password: ${DB_PASSWORD} # Секрет приходит из окружения деплоя.
    hikari:
      maximum-pool-size: 10
      connection-timeout: 1500 # Миллисекунды до отказа в получении соединения.
      validation-timeout: 500 # Проверка живости короче времени получения.
# minimum-idle оставлен по умолчанию: равен maximum-pool-size.

Этот YAML иллюстрирует настройки продового окружения и не используется H2-демо. Выбранный срок получения — 1500ms; стандартный Hikari — 30000ms. Значения Hikari ниже сверены для 7.0.2, время в этой таблице задано в миллисекундах.

ПараметрПо умолчаниюКакой вопрос решает
maximumPoolSize10Сколько физических соединений может держать этот пул, включая свободные
minimumIdleКак maximumPoolSizeКакой запас свободных соединений пул пытается поддержать в пределах максимума
connectionTimeout30000Сколько ждать получения соединения; это не предел SQL
validationTimeout5000Сколько ждать проверки живости соединения
maxLifetime1800000Когда заменять старое физическое соединение; занятое не обрывается по этому сроку
idleTimeout600000Когда убрать лишнее свободное соединение; действует при minimumIdle ниже максимума

Срок получения, срок SQL и сетевой срок — разные настройки. Statement.setQueryTimeout задаётся в секундах и относится к выполнению statement; детали отмены зависят от драйвера. Драйвер PostgreSQL имеет свои connectTimeout и socketTimeout. Последний ограничивает ожидание чтения из сокета. Уменьшение connectionTimeout Hikari не прервёт долгий UPDATE на уже полученном соединении.

Размер пула считают на все экземпляры приложения. Четыре экземпляра с десятью слотами способны занять сорок соединений; после масштабирования до двадцати экземпляров предел вырастет до двухсот. Базе ещё нужны соединения других сервисов, миграций и администрирования. Большой пул способен увеличить конкуренцию за CPU и блокировки, хотя очередь в приложении временно уменьшится.

Прикидка по средним значениям помогает найти порядок величины: 40 операций в секунду и 50ms владения соединением дают в среднем два занятых соединения. Если тот же путь держит его две секунды, получается восемьдесят. Это учебный расчёт, а не готовый размер пула: всплески, длинные хвосты и реальный предел базы нужно измерить.

Утечка и долгий законный заём выглядят похоже. leakDetectionThreshold пишет предупреждение и стек места получения, когда соединение удерживается слишком долго; он не отнимает его и не устраняет причину. По умолчанию диагностика выключена. Для расследования сравнивай стек с временем транзакции, открытым Stream и ожиданием банка.

Здоровое соединение тоже стареет. Срок жизни пула согласуют с пределами базы, прокси и сети; проверка свободного соединения не гарантирует, что сеть останется живой во время следующего SQL. При сбое определяй, удалось ли выполнить операцию и можно ли повторить её. Виртуальные потоки позволяют дешевле ждать, но не добавляют базе мощности и не делают количество JDBC-соединений неограниченным.

  • DataSource даёт соединения; наличие пула определяет её реализация. Получение соединения может задержать запрос ещё до SQL.
  • close оболочки Hikari возвращает соединение в пул. Физическая сессия обычно живёт дольше отдельного платежа.
  • PreparedStatement отделяет значения от SQL. Имена таблиц и направление сортировки выбирают из известных вариантов отдельно.
  • JdbcTemplate управляет ресурсами и переводит ошибки. Общую транзакцию двух UPDATE нужно задать отдельно.
  • Для локального перевода нужны одно соединение, явный commit при успехе и rollback при ошибке. Потерянный ответ commit оставляет исход неизвестным.
  • Пул настраивают по времени владения и общему бюджету базы. Срок получения соединения не ограничивает исполнение SQL.

На собеседовании

Чем отличаются DataSource, Connection и пул соединений?

DataSource — точка получения соединений. Connection представляет соединение с базой и его состояние, включая транзакцию. Наличие пула зависит от реализации DataSource: Hikari хранит открытые соединения и выдаёт временные оболочки, простая реализация может открывать новое при каждом получении.

Я беру Connection на участок работы и закрываю через try-with-resources. У Hikari close возвращает её в пул; закрытая оболочка больше не используется. В демо новая оболочка получила тот же физический объект, поэтому дорогая сессия не создавалась заново.

  • Соединение несёт состояние сессии. Пул сбрасывает стандартные свойства, но произвольные настройки через SQL требуют отдельной дисциплины, особенно при выборе схемы или арендатора.
  • Connection не держу в singleton и не разделяю между независимыми параллельными платежами: их транзакции и настройки смешаются.
  • Физическое соединение может быть удалено из пула после сбоя или окончания срока жизни. Повторное использование — обычный путь, а не обещание вечной идентичности объекта.

Что даёт PreparedStatement и защищает ли он от SQL injection?

Он отделяет структуру SQL от значений параметров. Я пишу условие id = ?, затем передаю id через setString. Кавычки и OR внутри такого значения остаются данными. В демо строка payer' OR '1'='1 не расширила выборку, а вернула ноль строк.

Защита относится к связанным значениям. Если я всё равно склею часть SQL из ввода, наличие PreparedStatement этого не исправит. Имя таблицы и направление сортировки выберу из ограниченного набора заранее известных вариантов.

  • Серверная подготовка и повторное использование плана зависят от драйвера и СУБД. Интерфейс JDBC не обещает единственную компиляцию и выигрыш на любой нагрузке.
  • Hikari не кеширует PreparedStatement. Если кеш подготовки нужен, изучаю механизм конкретного драйвера и его цену по памяти и планам на соединение.
  • Связывание параметров защищает структуру SQL, но не проверяет право пользователя обратиться к счёту. Это отдельная проверка платёжного пути.
  • Для изменения остатка проверяю число изменённых строк. Параметризованный запрос, который обновил ноль строк, ещё не означает успешный перевод.

Что делает JdbcTemplate и почему его можно использовать как singleton?

JdbcTemplate управляет обычным циклом JDBC: получает соединение, создаёт statement, связывает значения, закрывает ресурсы и переводит SQLException в DataAccessException. Я оставляю в репозитории SQL и RowMapper, который читает одну текущую строку.

Шаблон хранит DataSource, а не одно занятое соединение. После настройки его можно безопасно разделять между репозиториями и потоками. queryForObject ожидает ровно одну строку: отсутствие строки даёт исключение, а не обычный null.

  • В Spring-транзакции шаблон через DataSourceUtils получает соединение, привязанное к текущему потоку. Вне неё отдельные операции сами по себе не образуют общий commit.
  • Ручной setAutoCommit(false) не привязывает Connection к шаблону. Смешение этих путей может взять второй слот и выполнить SQL в другой транзакции.
  • queryForStream возвращает ресурс, который закрывает вызывающий код. Долгая обработка результата способна всё это время занимать соединение.
  • SQL NULL в единственной найденной строке отличается от отсутствия строки. При чтении nullable чисел учитываю wasNull или использую объектный тип.

Как сделать перевод из двух UPDATE атомарным на уровне JDBC?

Выполню обе команды на одном соединении с autoCommit=false. После успеха вызову commit, при ошибке — rollback, затем закрою соединение. При autoCommit=true каждое изменение фиксируется отдельно: падение после списания оставит деньги списанными без зачисления.

В демо этот сбой оставил 9000 и 0. Явная транзакция с rollback сохранила 10000 и 0, а успешная фиксация дала 9000 и 1000. Проверяю также число обновлённых строк: пропавший получатель должен сорвать всю операцию.

  • Активную транзакцию завершаю до close. Полагаться на поведение закрытия как на бизнес-rollback непереносимо; изменение autoCommit на true может зафиксировать её.
  • Если rollback тоже падает, сохраняю первичную ошибку и добавляю вторую как suppressed. Иначе расследование начнётся с ошибки уборки вместо причины сбоя платежа.
  • Разрыв во время commit оставляет исход неизвестным: база могла зафиксировать изменения до потери ответа. Повтор требует ключа операции и проверки результата.
  • Внешний банк не входит в эту локальную транзакцию. Долгий внешний вызов внутри неё удерживает соединение и может удерживать блокировки; согласование состояний решается отдельно.
Два метода репозитория каждый берут своё Connection, выключают autoCommit, выполняют UPDATE и делают commit. Объединяет ли вызов обоих методов перевод в одну транзакцию?

Нет: это два независимых завершения транзакции. Нужно передать одно соединение обеим операциям и зафиксировать его после общего успеха либо задать общую границу через менеджер Spring. Даже если пул последовательно выдаст один и тот же физический объект, между вызовами уже был commit; идентичность соединения не склеивает зафиксированные операции.

Пул исчерпан, но база почти свободна. Что проверишь и будешь ли увеличивать пул?

Сначала проверю время владения соединением и стеки кода, который его держит. Это может быть утечка, открытый Stream, длинная транзакция или ожидание банка после завершённого SQL. Затем сравню число занятых соединений, очередь получения и активность базы.

Увеличивать пул сразу не буду: сначала сокращу ненужное время владения. Если реальная параллельная работа требует больше слотов, проверю запас базы и число экземпляров приложения. Каждый экземпляр держит свой пул, поэтому масштабирование умножает общий предел соединений.

  • connectionTimeout Hikari ограничивает получение соединения. Запрос на уже занятом соединении требует своих сроков statement, драйвера и базы.
  • Предупреждение leak detection говорит о слишком долгом заёме и показывает место получения. Оно не возвращает соединение принудительно и само не отличает утечку от долгой законной работы.
  • Вложенное получение может ждать соединение, которое удерживает сам вызывающий код. Для независимой вложенной транзакции нужен дополнительный бюджет слотов; это важно при REQUIRES_NEW.
  • Виртуальные потоки уменьшают цену ожидания в JVM. Лимит мощности базы, блокировки и число физических сессий остаются.
connectionTimeout уменьшили до 500ms. UPDATE держит соединение и ждёт блокировку 20 секунд. Остановится ли он через полсекунды?

Нет. Этот срок относится к getConnection, который уже завершился. Нужны подходящие пределы выполнения SQL и ожидания блокировки с учётом драйвера и базы. Другие запросы, которые ждут свободное соединение, действительно смогут получить отказ примерно по своему сроку получения.
