JVM: JIT

Первые запросы после старта в двадцать раз медленнее

После деплоя метрики задержки несколько секунд выглядят плохо, потом выравниваются. Код тот же, данные те же — меняется то, чем исполняется код. Посмотрим на это в миниатюре: «запрос» считает комиссию для 100 платежей, и мы засекаем каждый из 10 000 запросов:

public class Warmup {
    // «бизнес-логика»: комиссия по сумме платежа
    static long fee(long amount) {
        long f = amount * 3 / 100;
        if (f < 10) f = 10;
        if (f > 5_000) f = 5_000;
        return f;
    }

    // «запрос»: посчитать комиссии для 100 платежей
    static long handle(long seed) {
        long sum = 0;
        for (int i = 0; i < 100; i++) sum += fee(seed + i * 37L);
        return sum;
    }

    public static void main(String[] args) {
        int requests = 10_000;
        long[] ns = new long[requests];
        long sink = 0;
        for (int r = 0; r < requests; r++) {                     // печать — после, чтобы не мешала замеру
            long start = System.nanoTime();
            sink += handle(r);
            ns[r] = System.nanoTime() - start;
        }
        int[][] ranges = {{1, 1}, {2, 10}, {11, 100}, {101, 300}, {301, 1000}, {1001, 3000}, {3001, 10000}};
        for (int[] g : ranges) {
            long sum = 0;
            for (int r = g[0]; r <= g[1]; r++) sum += ns[r - 1];
            System.out.printf("запросы %5d–%-5d: %7.0f нс на запрос%n", g[0], g[1], (double) sum / (g[1] - g[0] + 1));
        }
        System.out.println("sink " + sink % 10);
    }
}

запросы     2–10   :    4338 нс на запрос
запросы    11–100  :    1717 нс на запрос
запросы   101–300  :     542 нс на запрос
запросы   301–1000 :     242 нс на запрос
запросы  1001–3000 :     210 нс на запрос
запросы  3001–10000:     148 нс на запрос

От запуска к запуску числа гуляют на 5–10%, картина — нет. Первые запросы — 3–4 мкс, последние — 0,15 мкс. Разница больше чем в двадцать раз. Никакого кеша в программе нет. Сначала байткод исполняет интерпретатор, потом метод компилирует быстрый компилятор C1, потом оптимизирующий C2. Весь этот путь занял 17 миллисекунд, но на реальном сервисе с тысячами методов прогрев растягивается на секунды и минуты.

В этой теме — как JVM решает, что и когда компилировать, что умеют C1 и C2, почему inlining — главная оптимизация, и как спекуляции C2 откатываются деоптимизацией. В конце — что делать с прогревом в проде.

Метод поднимается по уровням: интерпретатор, C1 с профилем, C2

Схема называется tiered compilation и включена по умолчанию с Java 8. Для каждого метода JVM считает вызовы и итерации циклов и по порогам переводит его на следующий уровень:

Путь конкретных методов виден с флагом -XX:+PrintCompilation. Для программы из шага 1:

$ java -XX:+PrintCompilation Warmup | grep Warmup::
16    5       3       Warmup::fee (36 bytes)                   # мс от старта, id, уровень 3
16    6       4       Warmup::fee (36 bytes)                   # уровень 4: C2
16    8       3       Warmup::handle (35 bytes)
16    5       3       Warmup::fee (36 bytes)   made not entrant  # версию C1 заменили на C2
16    9 %     4       Warmup::handle @ 5 (35 bytes)            # % — OSR-компиляция цикла, шаг 6
17   10       4       Warmup::handle (35 bytes)
17    8       3       Warmup::handle (35 bytes)   made not entrant

made not entrant значит: новые вызовы в эту версию больше не заходят. Так бывает в двух случаях — версию заменили на лучшую, как здесь, или её деоптимизировали, как в шаге 5. Уровень 2 (C1 с частичным профилем) JVM выбирает редко, когда очередь C2 перегружена.

Tiered-режим берёт лучшее из обоих: C1 быстро убирает интерпретатор, C2 догоняет по профилю. Компилируют они в фоновых потоках, число которых зависит от CPU. На 18 ядрах CICompilerCount = 12. В контейнере с одним-двумя CPU потоков компиляции мало, и прогрев идёт заметно дольше.

Inlining — главная оптимизация, потому что открывает все остальные

Inlining — подстановка тела вызываемого метода в место вызова. Сам по себе он экономит немного: пару инструкций на вызов. Главное в другом: после подстановки компилятор видит код вызывающего и вызываемого вместе. Он может вынести проверки из цикла, свернуть константы, убрать лишние выделения памяти. Без inlining каждая такая оптимизация ограничена одним методом.

Решения компилятора видно с диагностическими флагами -XX:+UnlockDiagnosticVMOptions -XX:+PrintInlining. Для Warmup:

17    8       3       Warmup::handle (35 bytes)                      # C1
                              @ 22   Warmup::fee (36 bytes)   callee is too large
17    9 %     4       Warmup::handle @ 5 (35 bytes)                  # C2
                              @ 22   Warmup::fee (36 bytes)   inline (hot)

Метод fee занимает 36 байт байткода — на байт больше лимита C1 (C1MaxInlineSize = 35). Поэтому C1 его не встроил. C2 смотрит на частоту: горячие методы он встраивает до 325 байт (FreqInlineSize), холодные — до 35 (MaxInlineSize). Отсюда практический вывод: маленькие методы, геттеры и цепочки мелких вызовов в горячем коде ничего не стоят. Разбивать код на методы ради читаемости можно без оглядки на производительность.

Одна из оптимизаций, которую открывает inlining, — escape analysis. Если объект не выходит за пределы скомпилированного кода, C2 может не создавать его в heap, а разложить поля по регистрам (scalar replacement). Проверим по счётчику выделенных байт потока:

import java.lang.management.ManagementFactory;

public class Escape {
    record Money(long amount, String currency) {
        Money plus(Money o) { return new Money(amount + o.amount, currency); }
    }

    static long total(long[] amounts) {
        Money sum = new Money(0, "RUB");
        for (long a : amounts) sum = sum.plus(new Money(a, "RUB"));   // два new на итерацию
        return sum.amount();
    }

    public static void main(String[] args) {
        var threads = (com.sun.management.ThreadMXBean) ManagementFactory.getThreadMXBean();
        long[] amounts = new long[1_000];
        for (int i = 0; i < amounts.length; i++) amounts[i] = i;
        long sink = 0;
        for (int i = 0; i < 20_000; i++) sink += total(amounts);          // прогрев
        long before = threads.getCurrentThreadAllocatedBytes();
        for (int i = 0; i < 10_000; i++) sink += total(amounts);          // 20 млн Money в коде
        long after = threads.getCurrentThreadAllocatedBytes();
        System.out.printf("выделено в heap: %d МБ (%d)%n", (after - before) >> 20, sink % 10);
    }
}
$ java Escape
выделено в heap: 229 МБ (0)
$ java -XX:-DoEscapeAnalysis Escape
выделено в heap: 457 МБ (0)

В коде 20 млн объектов по 24 байта — 457 МБ. С escape analysis выделено ровно вдвое меньше. Аргумент new Money(a, "RUB") после встраивания plus никуда не уходит, и C2 его убрал. А sum переходит из итерации в итерацию, и этот объект C2 здесь не разложил. Escape analysis помогает, но полагаться на него вслепую нельзя: проверяют замером.

Эта же оптимизация ломает наивные бенчмарки. В теме References первая версия замера finalize() показала одинаковое время с ним и без. JIT просто убрал выделение объектов, которые никуда не сохранялись. Для замеров производительности есть JMH: он защищает результат от удаления и отделяет прогрев от измерения.

C2 делает ставку на профиль, а деоптимизация откатывает проигравшую ставку

Самые сильные оптимизации C2 — спекулятивные. Если в вызов fee.of(x) по профилю всегда приходил один класс, C2 встраивает его метод с дешёвой проверкой класса. Если приходило два — встраивает оба. На случай «вдруг придёт другой» он оставляет ловушку (uncommon trap), которая деоптимизирует код. Проверим на одном месте вызова, куда постепенно добавляются новые классы:

public class Deopt {
    interface Fee { long of(long amount); }
    static final class Card implements Fee { public long of(long a) { return a * 3 / 100; } }
    static final class Sbp implements Fee { public long of(long a) { return a * 4 / 1000; } }
    static final class Crypto implements Fee { public long of(long a) { return a / 50; } }

    static long total(Fee[] fees, int n) {
        long sum = 0;
        for (int i = 0; i < n; i++) sum += fees[i % fees.length].of(i);  // один call site
        return sum;
    }

    static void phase(String name, Fee... fees) {
        long sink = 0, best = Long.MAX_VALUE;
        for (int round = 0; round < 200; round++) {
            long start = System.nanoTime();
            sink += total(fees, 100_000);
            best = Math.min(best, System.nanoTime() - start);
        }
        System.out.printf("%-22s %.2f нс на вызов (%d)%n", name, best / 100_000.0, sink % 7);
    }

    public static void main(String[] args) {
        phase("только Card", new Card());
        phase("Card и Sbp", new Card(), new Sbp());
        phase("Card, Sbp и Crypto", new Card(), new Sbp(), new Crypto());
        phase("снова только Card", new Card());
    }
}
только Card            0.54 нс на вызов (6)
Card и Sbp             0.57 нс на вызов (5)
Card, Sbp и Crypto     1.59 нс на вызов (4)
снова только Card      1.45 нс на вызов (6)

С флагом -Xlog:deoptimization=debug видно, что происходило на переходах между фазами (строки сокращены):

[0.047s][debug][deoptimization] cid=  16 level=4 Deopt.total(...) trap_bci=22 class_check maybe_recompile
[0.063s][debug][deoptimization] cid= 143 level=4 Deopt.total(...) trap_bci=22 bimorphic_or_optimized_type_check maybe_recompile
  • Один класс — мономорфный вызов. C2 встроил Card.of с проверкой класса: 0,54 нс.
  • Появился Sbp — проверка класса не прошла (class_check), код деоптимизирован на инструкции 22, то есть на invokeinterface. C2 перекомпилировал метод и встроил обе реализации — биморфный вызов, почти так же быстро.
  • Третий класс — снова деоптимизация (bimorphic_or_optimized_type_check). Для трёх и больше типов C2 не встраивает, а делает настоящий виртуальный вызов через таблицу методов. Мегаморфный вызов в три раза медленнее.
  • Снова только Card — а быстрее не стало. Профиль уже «видел» три класса, и C2 не возвращается к оптимистичной версии. Код остаётся медленным до конца жизни процесса.

Деоптимизация сама по себе дешёвая и нормальная: при прогреве таких событий десятки. Проблема — когда она повторяется в цикле: компиляция, деоптимизация, компиляция. Это видно в -XX:+PrintCompilation по многократным made not entrant одного метода.

Интерфейс с одной реализацией медленнее прямого вызова, поэтому интерфейсы в горячем коде вредны.

Мономорфный и биморфный вызовы C2 встраивает, и стоят они как прямой вызов. Цена появляется на трёх и больше реализациях в одном месте вызова. И даже тогда это наносекунда на вызов, заметная только в очень горячих циклах.

OSR переключает уже идущий цикл на скомпилированный код

Компиляция по числу вызовов не помогает методу, который вызван один раз и крутит длинный цикл, — например, main или обработчику пакетного задания. Следующий вызов, который мог бы попасть в скомпилированную версию, не случится. Для этого есть on-stack replacement: JVM считает итерации цикла, компилирует метод с точкой входа посреди цикла и переносит кадр стека из интерпретатора в скомпилированный код прямо на ходу.

public class Osr {
    public static void main(String[] args) {
        long start = System.nanoTime(), sum = 0;
        for (int i = 0; i < 500_000_000; i++) sum += i % 7;       // main вызывается один раз
        System.out.printf("%d мс (%d)%n", (System.nanoTime() - start) / 1_000_000, sum % 10);
    }
}
$ java Osr
254 мс (4)
$ java -XX:-UseOnStackReplacement Osr
2086 мс (4)
$ java -XX:+PrintCompilation Osr | grep Osr
17    5 %     3       Osr::main @ 9 (71 bytes)                 # OSR: вход на инструкции 9, начале цикла
17    6       3       Osr::main (71 bytes)
17    7 %     4       Osr::main @ 9 (71 bytes)
18    5 %     3       Osr::main @ 9 (71 bytes)   made not entrant
272    7 %     4       Osr::main @ 9 (71 bytes)   made not entrant  # цикл закончился — код после него не был в профиле

Без OSR цикл в восемь раз медленнее. Знак % в логе — OSR-компиляция, @ 9 — номер инструкции байткода, где цикл проверяет условие. Последняя строка — ещё одна деоптимизация: C2 не компилировал код после цикла, потому что за время профилирования тот ни разу не выполнялся. Когда цикл закончился, OSR-версия ушла в ловушку, и печать выполнил интерпретатор.

OSR объясняет, почему микробенчмарк с одним большим циклом в main меряет не тот код, что работает в проде: OSR-версия компилируется иначе, чем обычный вызов метода.

Прогрев в проде решают до того, как под получит трафик

Для сервиса прогрев значит: первые секунды или минуты после старта задержки выше, а CPU занят компиляцией. Если под сразу получает полную долю трафика, p99 после каждого деплоя подпрыгивает. Что с этим делают:

Скомпилированный код хранится в code cache вне heap (по умолчанию 240 МБ, ReservedCodeCacheSize). Если он заполнится, JVM выключает компилятор, и всё новое остаётся в интерпретаторе. Проверено с искусственно маленьким кешем:

$ java -XX:ReservedCodeCacheSize=3m -XX:-SegmentedCodeCache Warmup
[0.037s][warning][codecache] CodeCache is full. Compiler has been disabled.
[0.037s][warning][codecache] Try increasing the code cache size using -XX:ReservedCodeCacheSize=

В проде с настройками по умолчанию это редкость, но такое сообщение в логе объясняет внезапную деградацию после нескольких часов работы. Состояние кеша на живом процессе показывает jcmd <pid> Compiler.codecache.

Флаги JIT в проде обычно не трогают. Пороги, размеры inlining и число потоков компиляции подобраны под типичную нагрузку. Их изменение — эксперимент с замером через JMH или нагрузочный тест, а не строчка из статьи.

  • Код начинает в интерпретаторе. После 200 вызовов его компилирует C1 с профилем, после 5000 или горячего цикла — C2 по профилю. Тривиальные методы сразу идут в C1 без профиля.
  • C1 компилирует быстро, C2 — медленно, но даёт самый быстрый код. Tiered-режим совмещает оба. TieredStopAtLevel=1 ускоряет старт коротких процессов.
  • Inlining — главная оптимизация: он открывает остальные, включая escape analysis. C2 встраивает горячие методы до 325 байт байткода, C1 — до 35.
  • C2 спекулирует по профилю: встраивает один или два типа в месте вызова. Если спекуляция не подтвердилась, код деоптимизируется. Три и больше типов — мегаморфный вызов, и обратно C2 не откатывается.
  • OSR переключает уже идущий цикл на скомпилированный код. В логе это знак %.
  • Прогрев в проде — прогрев перед readiness, плавный ввод трафика, запас CPU, AOT-кеш Leyden. Флаги JIT без замеров не трогают.

На собеседовании

Что такое JIT и как работает tiered compilation?

JIT компилирует байткод в машинный код во время работы программы, и только горячие методы. Метод стартует в интерпретаторе, который считает вызовы и итерации циклов. После 200 вызовов его компилирует C1 — быстро, со встроенным профилированием. После 5000 вызовов или горячего цикла — C2, оптимизирующий компилятор, который использует собранный профиль. Поэтому Java-сервис после старта какое-то время работает медленнее — прогрев.

  • Уровни: 0 — интерпретатор, 1 — C1 без профиля для тривиальных методов, 2 — C1 с частичным профилем, 3 — C1 с полным, 4 — C2.
  • -XX:+PrintCompilation показывает переходы. % — OSR, made not entrant — версия заменена или деоптимизирована.
  • Потоки компиляции зависят от CPU. В поде с одним CPU прогрев заметно дольше.
Зачем два компилятора, если C2 генерирует код быстрее?

C2 компилирует медленно и нуждается в профиле, который собирает C1. Без C1 метод 10 000 вызовов сидит в интерпретаторе. В замере урока с -XX:-TieredCompilation запросы 301–1000 шли в пять раз медленнее, чем в режиме по умолчанию. C1 быстро убирает интерпретатор, C2 потом догоняет.

Какие оптимизации делает JIT?

Главная — inlining: подстановка тела метода в место вызова. Она открывает остальные: свёртку констант, вынос проверок из циклов, удаление мёртвого кода. Escape analysis позволяет не создавать в heap объекты, которые не выходят за пределы метода. Ещё есть спекулятивные оптимизации по профилю: встраивание конкретного типа в виртуальный вызов, выкидывание веток, которые не выполнялись. Если спекуляция неверна — деоптимизация.

  • C2 встраивает горячие методы до 325 байт байткода (FreqInlineSize), остальные — до 35 (MaxInlineSize). Решения видно в -XX:+PrintInlining.
  • Escape analysis не всесилен: в замере урока объект, который переходит между итерациями цикла, остался в heap — убрано ровно одно выделение из двух.
Метод fee занимает 36 байт байткода и вызывается в горячем цикле. Встроит ли его C1? А C2?

C1 — нет: его лимит C1MaxInlineSize = 35 байт, в логе будет callee is too large. C2 — да: метод горячий, а для горячих лимит 325 байт, в логе inline (hot). Проверено на программе урока.

Что такое деоптимизация и когда она происходит?

Откат скомпилированного C2 кода обратно в интерпретатор, когда не подтвердилось предположение, на котором построена оптимизация. Например, C2 встроил метод единственного класса, который приходил в вызов, и тут пришёл объект другого класса. Или выполнилась ветка, которая по профилю была мёртвой. Метод снова собирает профиль и перекомпилируется.

  • Один или два типа в месте вызова C2 встраивает, три и больше — мегаморфный вызов через таблицу методов. В замере урока это 0,54 против 1,59 нс на вызов.
  • Профиль не «забывает» типы: после мегаморфной фазы код остался медленным, даже когда снова приходил один класс.
  • Причины деоптимизаций видны в -Xlog:deoptimization=debug: class_check, bimorphic_or_optimized_type_check, unstable_if.
Для «чистоты» в горячем обработчике добавили третью реализацию интерфейса, который раньше имел две. После релиза CPU вырос на 5%. Как такое могло случиться?

Место вызова стало мегаморфным: с двумя типами C2 встраивал обе реализации, с тремя — делает виртуальный вызов и теряет inlining, а с ним и оптимизации вокруг. Проверить можно через -XX:+PrintInlining или профилировщиком. Если место действительно горячее, можно разнести типы по разным местам вызова или вынести общую логику.

Что такое прогрев JVM и как с ним бороться в проде?

После старта код идёт через интерпретатор и C1, пока горячие методы не скомпилирует C2. Первые запросы медленнее, в замере урока — в двадцать раз. В проде прогревают до готовности: прогоняют типичные запросы перед тем, как отдать readiness, вводят трафик плавно и дают поду запас CPU на компиляцию.

  • Долгий цикл в одном вызове компилируется через OSR — это знак % в PrintCompilation.
  • В JDK 24–25 появился AOT-кеш Project Leyden: заранее загруженные классы (JEP 483) и сохранённые профили методов (JEP 515). Другие варианты — CRaC и GraalVM native image.
  • Заполненный code cache выключает компилятор: CodeCache is full. Compiler has been disabled.
Почему бенчмарк на System.nanoTime() в main может показать ерунду?

JIT может убрать код, результат которого не используется. Первые итерации идут в интерпретаторе, а длинный цикл в main компилируется через OSR, не так, как обычный вызов. Для замеров используют JMH: он отделяет прогрев, защищает результат от удаления и запускает измерения в отдельных процессах.

  • Java HotSpot VM Performance Enhancements (JDK 21) — основа урока: tiered compilation, escape analysis, compressed oops.
  • HotSpot Performance Techniques — список оптимизаций C2 от авторов HotSpot: inlining, спекуляции, деоптимизация.
  • JEP 483: Ahead-of-Time Class Loading & Linking и JEP 515: Ahead-of-Time Method Profiling — Project Leyden против прогрева.
  • JMH — как правильно мерить производительность Java-кода.
