JVM: JIT-компиляция

Одинаковый код может работать быстрее после прогрева

После деплоя платёжный сервис сначала отвечает медленнее, а потом ускоряется без изменения нагрузки. Одно возможное объяснение — HotSpot успела собрать профиль горячих методов и скомпилировать их JIT. Но причиной также могут быть холодные соединения, кеши и загрузка классов; тайминг одного запроса ничего не доказывает.

public class JitDemo {
    static long fee(long kopecks) { return kopecks * 15 / 1000; }
    public static void main(String[] args) {
        long total = 0;
        for (int i = 0; i < 1_000_000; i++) total += fee(10_000);
        System.out.println(total);
    }
}
150000000

Результат программы одинаков при обычном запуске и с -Xint, который отключает JIT и исполняет байткод интерпретатором. Скорость и сообщения -XX:+PrintCompilation зависят от JVM и окружения, поэтому их нельзя записывать как фиксированный вывод.

Tiered compilation меняет скорость и качество профиля

HotSpot обычно начинает с интерпретатора. Когда метод или цикл становится горячим, C1 быстро компилирует код и может собирать профиль дальше. C2 тратит больше времени на оптимизации и выпускает машинный код для устойчивого горячего пути. Не каждый метод проходит все стадии: пороги и решения динамические.

Такая смена уровней объясняет, почему первые секунды синтетического теста не показывают устойчивую производительность сервиса.

Inlining открывает дорогу другим оптимизациям

При inlining JIT вставляет тело маленького метода в место вызова. Это убирает стоимость вызова и даёт оптимизатору увидеть данные по обе стороны границы метода: свернуть константы или убрать промежуточные операции. Вызов через интерфейс тоже может быть заинлайнен, если профиль показывает подходящие классы.

Escape analysis помогает понять, покидает ли объект область использования. Если объект не утекает, JIT иногда заменяет его поля скалярами и вообще не создаёт отдельный heap-объект. Это возможность оптимизации, а не обещание для каждого new.

Оптимизированный код опирается на проверяемые предположения

Допустим, на точку вызова PaymentMethod.fee долго приходил только Card. JIT может встроить его реализацию и проверять класс объекта. После подключения Sbp проверка не проходит: JVM деоптимизирует код и продолжает корректное исполнение, затем может собрать новый профиль.

JIT «замораживает» поведение метода при первом вызове.

Оптимизации сохраняют семантику Java. Спекулятивные предположения проверяются, а при их нарушении JVM откатывается к безопасному коду.

Поэтому микробенчмарк, в котором всегда один тип, может отличаться от реального сервиса с десятками реализаций.

Прогрев и бенчмарк нужны только для измеренной горячей точки

Если p99 платежа определяется запросом к БД, тюнинг JIT ничего не даст. Сначала JFR или профилировщик покажет, где процесс тратит CPU; затем проверь warmup и стабильную нагрузку. Для микробенчмарка используй JMH: он учитывает прогрев, повторения и защиту от устранения бесполезной работы.

Флаги -Xint и -XX:+PrintCompilation полезны для изучения механизма, но не как обычная настройка продакшна. На стабильном сервисе измеряй сквозную задержку и throughput, а не только время одного метода.

  • javac создаёт байткод заранее; JIT компилирует выбранные горячие участки во время работы.
  • Tiered compilation сочетает быстрый старт, профилирование и более дорогие оптимизации C2.
  • Inlining и escape analysis могут убрать вызовы и часть выделений, но не гарантированы.
  • При нарушении предположений JVM деоптимизирует код, сохраняя корректность.
  • Сначала измеряй CPU-профиль и устойчивую нагрузку; прогрев не равен бизнес-ускорению.

На собеседовании

Чем JIT отличается от javac?

javac до запуска переводит Java-исходник в переносимый байткод. JIT внутри работающей JVM берёт горячие участки этого байткода и переводит их в машинный код текущего процессора, используя профиль реальных вызовов.

Для платёжного сервиса это значит, что горячий расчёт комиссии может ускориться после прогрева, а редкий административный метод останется интерпретируемым.

  • JIT не меняет наблюдаемую семантику; при ошибке предположения возможна deoptimization.
  • -Xint полезен для сравнения поведения без JIT, но обычно резко снижает throughput.
В class-файле лежит машинный код?

Нет. В нём байткод, константы и ссылки. Машинный код JIT создаёт во время исполнения для текущей платформы.

Почему не компилировать сразу всё?

Компиляция требует времени и памяти; редкий код может не окупить её стоимость. Профиль также помогает выбрать полезные оптимизации.

Что делают C1 и C2?

При tiered compilation C1 быстро выдаёт машинный код и помогает собирать профиль. C2 оптимизирует горячие методы глубже, используя эти данные. JVM сама решает, какие методы и циклы когда переводить между уровнями.

Я учитываю прогрев при сравнении производительности после деплоя и не делаю вывод по первому запуску теста.

  • Компиляция может запускаться по счётчику вызовов метода или горячему циклу через OSR.
  • Code cache ограничен; его заполнение может остановить дальнейшую JIT-компиляцию.
Что такое OSR?

On-stack replacement позволяет перейти на скомпилированную версию прямо внутри долго работающего цикла, не дожидаясь следующего вызова метода.

Каждый метод получит код C2?

Нет. Многие методы слишком редкие или невыгодные для такой компиляции; решения зависят от профиля.

Что такое деоптимизация и когда она случается?

JIT может оптимизировать горячий код под наблюдавшиеся типы и ветви. Если новый запрос нарушит предположение, JVM возвращается к корректному менее оптимизированному состоянию и при необходимости компилирует код снова.

Например, сначала приходили только оплаты картой, потом добавился СБП. Старый быстрый путь нельзя применять без проверки класса, но результат расчёта остаётся правильным.

  • Деоптимизация — часть нормальной работы адаптивной JVM, а не обязательно авария.
  • Профиль, собранный микробенчмарком с одним типом, может давать нехарактерный для прода код.
Можно ли наблюдать компиляции?

Для изучения используй -XX:+PrintCompilation или JFR. Вывод зависит от JVM и нагрузки.

Почему inlining не всегда полезен?

Слишком крупный код увеличивает code cache и время компиляции. JIT выбирает баланс по профилю и бюджету.
