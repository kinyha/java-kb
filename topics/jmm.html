Concurrency: Java Memory Model

Поток не видит, что флаг уже false, и крутится вечно

Фоновый поток работает, пока флаг running равен true. Главный поток через полсекунды сбрасывает флаг и ждёт остановки:

public class StopFlag {
    static boolean running = true;                               // без volatile

    public static void main(String[] args) throws Exception {
        Thread worker = new Thread(() -> {
            long loops = 0;
            while (running) loops++;                             // крутимся, пока не попросят остановиться
            System.out.println("worker остановился после " + loops + " итераций");
        });
        worker.setDaemon(true);
        worker.start();
        Thread.sleep(500);
        running = false;                                         // просим остановиться
        System.out.println("main: running = false");
        worker.join(3000);
        System.out.println("через 3 с worker жив: " + worker.isAlive());
    }
}
$ java StopFlag
main: running = false
через 3 с worker жив: true

$ java -Xint StopFlag                              # только интерпретатор
main: running = false
worker остановился после 194274565 итераций
через 3 с worker жив: false

С JIT поток не остановился: запись false он не увидел ни через три секунды, ни позже. В интерпретаторе тот же код работает. C2 увидел, что внутри цикла running никто не меняет, прочитал поле один раз до цикла и превратил его в while (true). Для однопоточной программы такая оптимизация честная. Чтобы запретить её, нужно сообщить компилятору, что поле читают и пишут разные потоки. Хватит одного слова — static volatile boolean running: с ним поток остановился сразу.

Java Memory Model (JMM, глава 17 JLS) — это договор о том, какие значения поток вправе увидеть при чтении общей переменной. Ни компилятору, ни процессору не нужно показывать записи других потоков немедленно и в исходном порядке. Гарантии появляются только там, где их явно запросили. В этой теме — почему так устроено, что такое happens-before, что даёт volatile, как безопасно опубликовать объект и почему классический double-checked locking сломан.

Процессор переставляет запись и чтение, и получается невозможный результат

Компилятор — не единственный источник сюрпризов. Классический тест: два потока одновременно записывают свою переменную и читают чужую. Раунд запускается одновременно для обоих, повторяем миллион раз:

import java.util.concurrent.atomic.AtomicInteger;

public class StoreBuffer {
    static int x, y;                                             // обычные поля
    static int r1, r2;
    static volatile int round;                                   // стартовый сигнал для раунда
    static final AtomicInteger done = new AtomicInteger();

    public static void main(String[] args) throws Exception {
        int rounds = 1_000_000;
        Thread a = new Thread(() -> {
            for (int i = 1; i <= rounds; i++) {
                while (round != i) Thread.onSpinWait();
                x = 1;                                           // записал своё
                r1 = y;                                          // прочитал чужое
                done.incrementAndGet();
            }
        });
        Thread b = new Thread(() -> {
            for (int i = 1; i <= rounds; i++) {
                while (round != i) Thread.onSpinWait();
                y = 1;
                r2 = x;
                done.incrementAndGet();
            }
        });
        a.start(); b.start();
        long[] outcomes = new long[4];                           // индекс r1 * 2 + r2
        for (int i = 1; i <= rounds; i++) {
            x = 0; y = 0;
            done.set(0);
            round = i;                                           // старт раунда
            while (done.get() < 2) Thread.onSpinWait();
            outcomes[r1 * 2 + r2]++;
        }
        a.join(); b.join();
        System.out.printf("r1=0 r2=0: %,d%nr1=0 r2=1: %,d%nr1=1 r2=0: %,d%nr1=1 r2=1: %,d%n",
            outcomes[0], outcomes[1], outcomes[2], outcomes[3]);
    }
}
r1=0 r2=0: 997,346
r1=0 r2=1: 940
r1=1 r2=0: 1,714
r1=1 r2=1: 0

Если бы операции потоков просто чередовались, первая строка была бы невозможна. Кто-то из потоков записывает первым, и второй обязан прочитать его единицу. Но результат 0, 0 — это 99,7% раундов. Так же выходит и в интерпретаторе (-Xint: 997 487), значит, дело не в JIT. Каждое ядро кладёт запись в свой store buffer и продолжает работу, не дожидаясь, пока запись дойдёт до общей памяти. Чтение чужой переменной выполняется раньше, чем собственная запись стала видна соседу. Для одного потока это незаметно, для двух — это переупорядочивание «запись, потом чтение».

С volatile int x, y результат 0, 0 не встретился ни разу за миллион раундов. Запуски — на Apple M5 Pro (ARM). Модель памяти x86 тоже разрешает именно это переупорядочивание «запись, потом чтение», у него тоже есть store buffer. А вот две записи x86 не переставляет, ARM — переставляет. Шаг 5 покажет, к чему это приводит.

Переставлять операции могут три участника: компилятор javac (редко), JIT и процессор с его буферами и кешами. Каждый из них сохраняет иллюзию последовательного выполнения для одного потока (as-if-serial) и не обязан сохранять её для остальных. JMM не описывает кеши и буферы конкретного процессора. Она задаёт правила, по которым программист может получить гарантии на любом железе.

happens-before — единственный способ гарантировать, что чтение увидит запись

Главное понятие JMM — отношение happens-before. Если действие A happens-before действия B, то всё, что сделано до A включительно, видно в B. Если между записью и чтением такого отношения нет, чтение вправе вернуть и старое значение, и новое. Это и называется data race.

Рёбра между потоками дают не только volatile. Правила из JLS 17.4.5 и гарантии пакета java.util.concurrent:

Действие Ahappens-before действия B
выход из synchronized (unlock)последующий вход в synchronized на том же мониторе
запись volatile-поляпоследующее чтение этого поля
t.start()любое действие в потоке t
любое действие в потоке tвозврат из t.join()
конец конструктора (для final-полей)чтение этих полей через ссылку на объект
запись до executor.submit(task)выполнение task
действия задачивозврат из future.get()
положить в ConcurrentHashMap, BlockingQueueдостать тот же элемент в другом потоке

Поэтому код, где потоки общаются только через пулы, очереди и потокобезопасные коллекции, работает без единого volatile. Эти классы дают рёбра happens-before внутри себя.

volatile даёт видимость и порядок, но не атомарность

Что гарантирует volatile-поле:

  • Видимость. Чтение видит последнюю запись в это поле из любого потока. JIT не может закешировать значение в регистре, как в шаге 1.
  • Порядок. Записи, сделанные до записи в volatile, нельзя перенести после неё. Чтения после чтения volatile нельзя перенести до него. Отсюда публикация через флаг в шаге 3.
  • Атомарность одной записи long и double. Без volatile JLS разрешает разрывать 64-битную запись на две половины. На 64-битных JVM этого не бывает, но формально гарантии нет.

Чего volatile не даёт — атомарности составных действий. count++ на volatile-поле так же теряет увеличения, как в теме Thread Safety: чтение и запись по отдельности видимы, но между ними вклинивается другой поток.

Где volatile — правильный инструмент:

  • флаг остановки или состояния, который пишет один поток, а читают многие;
  • публикация ссылки на неизменяемый объект: конфигурация, кеш, собранный целиком и подменяемый одной записью;
  • поле, которое пишет только один поток: тогда гонок записи нет, и нужна только видимость.

Цена volatile на современных процессорах — барьер памяти при записи и запрет некоторых оптимизаций. Это дешевле блокировки, но заметно дороже обычного поля в горячем цикле. Если нужна атомарная операция «прочитать и изменить», берут атомики (тема Atomics & CAS).

Объект, опубликованный без синхронизации, можно увидеть недостроенным

Самое контринтуитивное следствие JMM: поток может получить ссылку на объект раньше, чем увидит значения, записанные в его конструкторе. Проверим на ARM. Писатель 20 млн раз создаёт объект с amount = 42 и кладёт в обычное статическое поле, читатель проверяет, что видит:

public class Publish {
    static class Payment {
        long amount;                                             // обычное поле
        Payment(long amount) { this.amount = amount; }
    }
    static class FinalPayment {
        final long amount;                                       // final-поле
        FinalPayment(long amount) { this.amount = amount; }
    }

    static Payment shared;                                       // публикация без синхронизации
    static FinalPayment sharedFinal;

    public static void main(String[] args) throws Exception {
        int rounds = 20_000_000;
        Thread writer = new Thread(() -> {
            for (int i = 1; i <= rounds; i++) {
                shared = new Payment(42);
                sharedFinal = new FinalPayment(42);
            }
        });
        long[] seen = new long[4];                               // [увидел объект, amount=0, final: увидел, amount=0]
        Thread reader = new Thread(() -> {
            for (int i = 0; i < rounds; i++) {
                Payment p = shared;
                if (p != null) { seen[0]++; if (p.amount == 0) seen[1]++; }
                FinalPayment f = sharedFinal;
                if (f != null) { seen[2]++; if (f.amount == 0) seen[3]++; }
            }
        });
        writer.start(); reader.start(); writer.join(); reader.join();
        System.out.printf("обычное поле: amount=0 в %d из %d прочитанных объектов%n", seen[1], seen[0]);
        System.out.printf("final-поле:   amount=0 в %d из %d прочитанных объектов%n", seen[3], seen[2]);
    }
}
обычное поле: amount=0 в 23 из 19987895 прочитанных объектов
final-поле:   amount=0 в 0 из 19980868 прочитанных объектов

23 раза читатель получил объект Payment, у которого amount — ноль. Нигде в программе ноль в это поле не пишется: это состояние до конструктора. В трёх запусках — 23, 16 и 42 раза. Процессор ARM вправе сделать запись ссылки в shared видимой раньше, чем запись поля внутри объекта. Раз между потоками нет happens-before, JMM это разрешает.

Объект с final-полем недостроенным не встретился ни разу: JMM даёт final-полям особую гарантию. Любой поток, получивший ссылку на объект после конструктора, видит final-поля проинициализированными, даже при гонке. Условие одно — this не должен утечь из конструктора. С static volatile Payment shared ноль тоже не встретился ни разу за три запуска.

Способы безопасной публикации — ссылка и состояние объекта становятся видимы вместе:

  • инициализация в статическом инициализаторе: JVM инициализирует класс под блокировкой;
  • запись в volatile-поле или AtomicReference;
  • запись в final-поле другого объекта, который сам опубликован корректно;
  • запись и чтение под одной блокировкой;
  • передача через потокобезопасную коллекцию, очередь или пул потоков.

На x86 процессор не переставляет записи, и этот тест там, скорее всего, покажет нули. Но это не делает код правильным: JIT вправе переставить записи и на x86, а код, который «работает на моём ноутбуке», сломается на ARM-серверах — Graviton, Ampere — или после обновления JDK.

Double-checked locking без volatile публикует недостроенный объект

Классический ленивый синглтон, который хочет не брать блокировку на каждом вызове:

// СЛОМАНО: instance без volatile
private static Config instance;

static Config get() {
    if (instance == null) {                                      // 1. проверка без блокировки
        synchronized (Config.class) {
            if (instance == null) instance = new Config();       // 2. создание под блокировкой
        }
    }
    return instance;                                             // 3. ссылка может быть видна раньше полей
}

Проблема та же, что в шаге 5. Поток, который прошёл первую проверку без блокировки, не имеет с создателем никакого happens-before. Он может увидеть ненулевую ссылку и поля конструктора в состоянии по умолчанию. Блокировка защищает только тех, кто в неё вошёл. Исправления:

import java.util.concurrent.atomic.AtomicInteger;

public class Singletons {
    static final AtomicInteger created = new AtomicInteger();

    static class Config {
        final String url;
        Config() {
            created.incrementAndGet();
            url = "jdbc:postgresql://db/payments";
        }
    }

    // 1. double-checked locking: работает только с volatile
    private static volatile Config instance;
    static Config dcl() {
        Config c = instance;                                     // одно volatile-чтение на быстром пути
        if (c == null) {
            synchronized (Singletons.class) {
                c = instance;
                if (c == null) instance = c = new Config();
            }
        }
        return c;
    }

    // 2. holder: JVM сама инициализирует класс лениво и потокобезопасно
    private static class Holder {
        static final Config INSTANCE = new Config();
    }
    static Config holder() { return Holder.INSTANCE; }

    public static void main(String[] args) throws Exception {
        System.out.println("до holder(): создано " + created.get());   // Holder ещё не инициализирован
        holder();
        System.out.println("после holder(): создано " + created.get());
        Thread[] ts = new Thread[4];
        for (int i = 0; i < ts.length; i++) {
            ts[i] = new Thread(() -> { dcl(); holder(); }, "t" + i);
            ts[i].start();
        }
        for (Thread t : ts) t.join();
        System.out.println("после 4 потоков: создано " + created.get() + " — по одному на способ");
        System.out.println("один и тот же объект: " + (dcl() == dcl()) + ", " + (holder() == holder()));
    }
}
до holder(): создано 0
после holder(): создано 1
после 4 потоков: создано 2 — по одному на способ
один и тот же объект: true, true
  • DCL с volatile работает с Java 5, когда JMM переписали (JSR-133). Локальная переменная c экономит второе volatile-чтение на быстром пути.
  • Holder — вложенный класс со статическим полем. JVM инициализирует класс при первом обращении и сама гарантирует, что это произойдёт один раз, под блокировкой, с публикацией результата всем потокам. Вывод показывает ленивость: до первого вызова holder() объект не создан. Кода синхронизации нет вовсе.
  • enum с одним элементом — то же, что holder, плюс защита от повторного создания через сериализацию и рефлексию.

В прикладном коде на Spring синглтоны создаёт контейнер, и DCL встречается в основном в библиотеках и на собеседованиях. Но механизм тот же, что у любого ленивого кеша, который сохраняют в обычное поле.

  • Без синхронизации поток может не увидеть запись другого потока вообще (JIT вынес чтение из цикла) или увидеть записи в другом порядке (store buffer, переупорядочивание записей на ARM).
  • Гарантия видимости есть только при happens-before: unlock → lock, запись volatile → чтение, start, join, final-поля, классы java.util.concurrent. Отношение транзитивно.
  • volatile даёт видимость и порядок, но не атомарность count++. Подходит для флагов и публикации неизменяемых объектов.
  • Объект, опубликованный через обычное поле, можно увидеть недостроенным: в замере на ARM — 16–42 раза на 20 млн. final-поля и volatile-ссылка это исключают.
  • Double-checked locking работает только с volatile. Проще — holder-класс или enum.

На собеседовании

Что такое happens-before?

Отношение из Java Memory Model: если действие A happens-before действия B, то результаты A и всё, что было до A, видны в B. Без такого отношения чтение общей переменной может вернуть устаревшее значение, а записи могут стать видны в другом порядке. Основные правила: порядок программы внутри потока, unlock монитора перед последующим lock того же монитора, запись volatile перед последующим чтением, Thread.start() перед действиями потока, действия потока перед возвратом из join(). Отношение транзитивно.

  • Классы java.util.concurrent документируют свои рёбра: submit → выполнение задачи, задача → Future.get(), put в очередь → take.
  • Data race — конфликтующие доступы (хотя бы одна запись) без happens-before между ними. Программа без data race ведёт себя последовательно согласованно (гарантия DRF-SC).
Писатель: data = 42; ready = true; (ready — volatile). Читатель: if (ready) print(data). data — обычное поле. Что напечатает читатель, если условие выполнилось?

Гарантированно 42. Запись data идёт раньше записи ready по порядку программы, запись volatile ready happens-before её чтения, а чтение ready — раньше чтения data. По транзитивности запись data видна. Если ready не volatile, может напечатать и 0.

Что делает volatile? Гарантирует ли он атомарность?

volatile гарантирует видимость: чтение видит последнюю запись из любого потока, и JIT не может закешировать поле в регистре. Ещё он гарантирует порядок: записи до записи в volatile-поле видны тому, кто прочитал это поле. Атомарности составных операций нет: count++ на volatile всё равно теряет обновления. Атомарна только сама запись или чтение, в том числе для long и double.

  • Типичные применения: флаг остановки, публикация неизменяемого объекта, поле с одним писателем, double-checked locking.
  • Цена — барьеры памяти при записи и запрет оптимизаций, дешевле блокировки.
static boolean stop; поток крутит while (!stop) { work(); }, другой поток ставит stop = true. На стенде поток иногда не останавливается. Почему и как исправить?

Без volatile между записью и чтением нет happens-before. JIT вправе прочитать stop один раз до цикла, и поток не увидит изменение никогда. В замере урока поток с таким флагом не остановился, а в интерпретаторе остановился сразу. Исправление — volatile boolean stop или AtomicBoolean; ещё лучше — прерывание через interrupt().

Что не так с double-checked locking?

Без volatile поток, который проверяет instance без блокировки, может увидеть ненулевую ссылку на объект, конструктор которого для него ещё не завершён: поля в значениях по умолчанию. Запись ссылки и запись полей могут стать видны в другом порядке. С volatile DCL корректен начиная с Java 5. Проще и надёжнее — holder-класс со статическим полем или enum: JVM сама лениво и потокобезопасно инициализирует класс.

Можно ли увидеть недостроенный объект на практике, или это теория?

Можно. В замере урока на ARM (Apple M5 Pro) читатель получал объект с полем в значении по умолчанию 16–42 раза на 20 млн публикаций через обычное поле. С final-полем или volatile-ссылкой — ни разу. На x86 процессор не переставляет записи, но это вправе сделать JIT.

Что такое безопасная публикация объекта?

Передача ссылки другому потоку так, чтобы вместе со ссылкой он гарантированно увидел и состояние объекта. Способы: статический инициализатор; volatile-поле или AtomicReference; final-поле корректно опубликованного объекта; запись и чтение под одной блокировкой; потокобезопасная коллекция, очередь или пул. Неизменяемые объекты с final-полями безопасны даже при публикации через гонку.

Какую гарантию JMM даёт final-полям?

Если this не утёк из конструктора, любой поток, получивший ссылку на объект, увидит final-поля проинициализированными, даже без синхронизации. Гарантия распространяется и на объекты, достижимые через final-поле, в состоянии на конец конструктора. На этом держится потокобезопасность неизменяемых классов вроде String.

Что значит «this утёк из конструктора» и чем это опасно?

Ссылка на объект стала доступна другому потоку до окончания конструктора: например, конструктор зарегистрировал this как слушателя или запустил поток, который его использует. Такой поток может увидеть даже final-поля неинициализированными — гарантия действует только после конца конструктора.
