JPA Locking & Caching

Два платежа способны прочитать один баланс и затем затереть изменения друг друга. Версия entity позволяет заметить такой конфликт, блокировка строки — выстроить операции в очередь. Кеш сокращает чтение, но сам по себе не защищает финансовое правило. Во всех случаях следи, какое состояние сейчас есть у Java-объекта, какую строку видит база и когда изменения действительно фиксируются.

Две успешные транзакции способны потерять одно списание

На счёте 100 учебных денежных единиц. Первый платёж списывает 10, второй — 20. Оба прочитали исходное значение до первого commit. У каждого свой persistence context и свой объект счёта, поэтому Java-поля стали 90 и 80. Без проверки конкуренции второй UPDATE записывает 80 поверх 90. Правильный итог 70 так и не появился.

Транзакция делает каждое списание атомарным, но не обнаруживает, что объект второго запроса устарел. Это lost update: изменение первой операции заменилось вычислением по старому состоянию. Варианты защиты — условный SQL, версия entity или блокировка строки до чтения. Выбор зависит от того, что именно нужно проверить перед списанием.

Ниже два открытых Session Hibernate работают как независимые контексты. В PlainAccount есть @Id и баланс, а поля @Version нет. Полный опыт — в LockingDemo.java; он использует JDK 21, Hibernate 7.4.5.Final, Jakarta Persistence 3.2 и H2 2.4.240. Зависимости управляются BOM Boot 4.1.1.

@Entity
class PlainAccount {
    @Id Long id;
    int balance; // Версии нет: UPDATE проверит только id.
}

first.beginTransaction();
second.beginTransaction();
var a = first.find(PlainAccount.class, 1L); // 100
var b = second.find(PlainAccount.class, 1L); // Тоже 100, в другом контексте.
a.balance -= 10;
b.balance -= 20;
first.getTransaction().commit(); // Сохранили 90.
second.getTransaction().commit(); // Сохранили 80 поверх 90.

// Итог читаем из новой транзакции, а не из старого объекта a или b.
factory.inTransaction(s ->
        System.out.println("final balance=" + s.find(PlainAccount.class, 1L).balance));
cd examples/data
./run.sh LockingDemo lost
final balance=80

Если операция сводится к арифметике, база может выполнить её без промежуточного чтения: UPDATE account SET balance = balance - :amount WHERE id = :id AND balance >= :amount. Число изменённых строк сообщает, удалось ли списание. Когда решение зависит от нескольких полей загруженной entity, удобно проверить, что с момента чтения она не изменилась.

Version отвергает запись, рассчитанную по старому состоянию

@Version добавляет к состоянию entity номер изменения. Hibernate запоминает версию при загрузке. При flush он отправляет UPDATE с условием по id и старой версии, а в новое состояние записывает следующую. Если другой запрос уже изменил строку, условие не совпадёт: обновлено ноль строк, возникнет OptimisticLockException.

@Entity
class Account {
    @Id Long id;
    int balance;
    @Version long version; // Начальную и следующую версии назначает Hibernate.
}

// Смысл UPDATE для первого платежа при версии 0.
// UPDATE account SET balance=90, version=1 WHERE id=1 AND version=0

first.beginTransaction();
second.beginTransaction();
var a = first.find(Account.class, 1L);
var b = second.find(Account.class, 1L);
System.out.printf("loaded versions=%d,%d%n", a.version, b.version);
a.balance -= 10;
b.balance -= 20;
first.getTransaction().commit(); // База: 90, version=1.
try { second.getTransaction().commit(); } // Старое условие version=0 не совпало.
catch (PersistenceException error) {
    System.out.println("second exception=" + error.getClass().getSimpleName());
    if (second.getTransaction().isActive()) second.getTransaction().rollback();
}
// Оба старых контекста закрываем. В полном демо печатаем состояние из новой транзакции.

factory.inTransaction(s -> s.find(Account.class, 1L).balance -= 20);
// Повтор загрузил 90/version=1, а не перенёс устаревшие 80/version=0.

Optimistic locking подходит, когда конфликт редок и повтор дешёв. Он не держит блокировку с момента чтения, но обычный UPDATE всё равно использует блокировки СУБД. Проверка может произойти при явном flush или при commit. После конфликта откатывай всю операцию и начинай новый контекст: повтор одного UPDATE с устаревшим объектом теряет смысл проверки.

Перед повтором снова проверяй бизнес-условия. Нового баланса может уже не хватать. Повторы ограничивай; сетевое списание нельзя слепо выполнить второй раз. Все способы записи должны соблюдать версию: SQL WHERE id=:id без version обходит защиту entity. Bulk JPQL UPDATE также не применяет проверку и увеличение версии автоматически.

Под капотом: версия защищает entity, а не произвольный инвариант

OPTIMISTIC запрашивает проверку версии, в том числе для прочитанной entity без обычного изменения. OPTIMISTIC_FORCE_INCREMENT дополнительно требует увеличение версии. Это полезно, когда изменение зависимых данных должно конфликтовать через общий объект-координатор.

Две операции способны изменить разные versioned entity и нарушить общий лимит, не столкнувшись по версии ни одной строки. Для инварианта нескольких счетов нужна общая точка проверки: блокировка нужных строк, условная запись, объект с общей версией или подходящий уровень изоляции. Поле version не меняй вручную в бизнес-коде.

Блокировка строки удерживает очередь до завершения транзакции

Если операции постоянно конфликтуют, повторные вычисления становятся дорогими. PESSIMISTIC_WRITE просит базу получить блокировку при загрузке счёта, до изменения Java-поля. Второй запрос с несовместимой блокировкой ждёт освобождения строки либо получает ошибку ожидания. Первый держит блокировку до commit или rollback.

JPA задаёт режим, а диалект Hibernate выбирает SQL для СУБД, например SELECT ... FOR UPDATE. Это не Java-monitor и не блокировка одного JVM-объекта. Конкурирующий сервис на другой машине обращается к той же базе и попадает под её правила. Обычное чтение в MVCC-базе при этом способно читать снимок без ожидания; обещать блокировку «всех SELECT» нельзя.

// H2 настроена через URL: LOCK_TIMEOUT=1500 (миллисекунды).
first.beginTransaction();
second.beginTransaction();
var account = first.find(Account.class, 1L, LockModeType.PESSIMISTIC_WRITE);
System.out.println("first locked balance=" + account.balance);
try {
    second.find(Account.class, 1L, LockModeType.PESSIMISTIC_WRITE);
    // Первая транзакция всё ещё держит строку, поэтому вторая не получит её вовремя.
} catch (PersistenceException error) {
    System.out.println("second exception=" + error.getClass().getSimpleName());
} finally {
    if (second.getTransaction().isActive()) second.getTransaction().rollback();
}
account.balance -= 10;
first.getTransaction().commit(); // Блокировка освобождается только здесь.

factory.inTransaction(session -> {
    var fresh = session.find(Account.class, 1L, LockModeType.PESSIMISTIC_WRITE);
    System.out.println("after release: locked balance=" + fresh.balance);
    fresh.balance -= 20; // Прочитан уже сохранённый результат первого платежа.
});

Точные исключения и поддержка таймаутов зависят от базы и драйвера. JPA различает LockTimeoutException для сбоя на уровне выражения и PessimisticLockException для отката транзакции. В сервисе такую ошибку лучше обрабатывать за внешней границей с новой транзакцией. Hint jakarta.persistence.lock.timeout выражает запрос на срок ожидания, но его поддержку проверяют у выбранного диалекта.

PESSIMISTIC_READ запрашивает разделяемую блокировку, а PESSIMISTIC_WRITE — более строгую защиту от конкурентной записи; база вправе использовать более сильный доступный режим. PESSIMISTIC_FORCE_INCREMENT дополнительно увеличивает version. @Version полезно оставить и при pessimistic locking: оно защищает остальные пути изменения этой entity.

Для перевода между счетами бери строки в одном порядке, например по id. Иначе первая операция держит счёт 1 и ждёт счёт 2, а вторая держит счёт 2 и ждёт счёт 1: база обнаружит deadlock и отменит одну из них. Не держи блокировку во время HTTP-вызова банка. Срок ожидания строки, срок SQL и срок всей транзакции — разные настройки.

Persistence context сохраняет идентичность объекта, а не свежесть строки

Кеш первого уровня, L1, — часть persistence context. В одном контексте одному ключу entity соответствует один managed-объект. Повторный find(Account.class, 1L) вернёт ту же ссылку. Это нужно не только для скорости: dirty checking и связи должны работать с единым состоянием счёта внутри операции.

L1 не перечитывает строку каждый раз, когда где-то произошло изменение. Даже прямой SQL на том же подключении способен поменять базу, оставив Java-поле старым. refresh() загружает состояние базы в существующий managed-объект. clear() отсоединяет все объекты контекста; следующий find() создаст новый.

factory.inTransaction(session -> {
    var first = session.find(Account.class, 1L);
    var same = session.find(Account.class, 1L);
    System.out.printf("same reference=%s, prepared statements=%d%n",
            first == same, factory.getStatistics().getPrepareStatementCount());

    session.doWork(connection -> {
        try (var statement = connection.createStatement()) {
            statement.executeUpdate("update account set balance=80 where id=1");
            // Обошли ORM: managed-объект всё ещё хранит 100.
        }
    });
    System.out.println("after SQL: find balance="
            + session.find(Account.class, 1L).balance);
    session.refresh(first); // Перечитали строку в тот же объект.
    System.out.println("after refresh: balance=" + first.balance);
    session.clear(); // Отсоединили объекты; данные базы остаются.
    var fresh = session.find(Account.class, 1L);
    System.out.printf("after clear: same reference=%s, balance=%d%n",
            first == fresh, fresh.balance);
});

same reference=true, prepared statements=1
after SQL: find balance=100
after refresh: balance=80

В этом режиме L2 отключён; счётчик Hibernate обнулён после подготовки данных. Прямой JDBC не включается в счётчик подготовленных ORM-выражений. Опыт показывает именно состояние объекта: база уже содержит 80, повторный find() видит прежние 100, а refresh() возвращает его к состоянию строки.

Кеш первого уровня избавляет от любого повторного SELECT в транзакции.

find по известному ключу способен взять объект из L1. JPQL-запрос всё ещё должен найти строки в базе. При сборке результата Hibernate переиспользует уже managed-объекты с теми же ключами, поэтому SQL возможен без обновления их полей.

Перед clear() явно отправь нужные изменения через flush(): отсоединённые объекты больше не участвуют в dirty checking. refresh() заменяет состояние объекта и способен потерять несохранённые локальные правки. Эти методы управляют контекстом, а не служат универсальной кнопкой исправления конфликтов. После optimistic conflict безопасная граница — rollback и новый контекст.

Общий кеш хранит состояние между контекстами и требует правил согласованности

Persistence context заканчивается вместе с операцией. Для часто читаемого тарифа можно добавить кеш второго уровня, L2, общий для SessionFactory. Он обычно хранит разобранное состояние entity, а не её managed-ссылку. Новый контекст получает данные из региона кеша и создаёт свой объект. Два контекста остаются независимыми.

Без провайдера регионов Hibernate не включает L2. В демо добавлены hibernate-jcache и локальный Caffeine JCache; кеширование разрешено только для тарифа. @Cacheable говорит о возможности кеширования entity, а Hibernate-аннотация @Cache выбирает стратегию региона. Для баланса, который постоянно меняется, выгода может оказаться меньше цены согласования.

@Entity
@Cacheable
@Cache(usage = CacheConcurrencyStrategy.READ_WRITE)
class Tariff {
    @Id Long id;
    int fee;
    @Version long version;
}

// Настройки SessionFactory; зависимости указаны в examples/data/pom.xml.
config.setProperty("hibernate.cache.use_second_level_cache", "true");
config.setProperty("hibernate.cache.region.factory_class", "jcache");
config.setProperty("hibernate.javax.cache.provider",
        "com.github.benmanes.caffeine.jcache.spi.CaffeineCachingProvider");
config.setProperty("hibernate.javax.cache.missing_cache_strategy", "create");
config.setProperty("hibernate.cache.use_query_cache", "false"); // Это другой кеш.

factory.getCache().evictAllRegions(); // Начинаем измерение с пустого L2.
factory.getStatistics().clear();
var first = tariff(factory); // Каждый tariff() открывает/закрывает новый Session.
var second = tariff(factory); // Получит данные L2, но создаст другой объект.

for (int i = 0; i < 2; i++) factory.inTransaction(session ->
        session.createSelectionQuery("from Tariff", Tariff.class).getResultList());
// Обычный JPQL выполнится дважды, хотя entity разрешено кешировать.

factory.inTransaction(session -> session.doWork(connection -> {
    try (var statement = connection.createStatement()) {
        statement.executeUpdate("update tariff set fee=200 where id=1");
        // Эта запись минует механизм обновления/инвалидации L2.
    }
}));
System.out.println("after external SQL: fee=" + tariff(factory).fee);
factory.getCache().evictEntityData(Tariff.class, 1L); // Убрали конкретную запись региона.
System.out.println("after eviction: fee=" + tariff(factory).fee);
./run.sh LockingDemo l2

second: same reference=false, SQL=1, L2 hits=1
two JPQL queries: SQL=2
after external SQL: fee=100

SQL=1 во второй строке — накопленный счётчик Hibernate: второй find() не добавил выражения. Полный файл печатает статистику и сравнение ссылок. Прямой JDBC UPDATE моделирует другого писателя: L2 остался с fee=100. Eviction убрал устаревшую запись; следующий контекст загрузил 200 из базы.

Кеш результатов запросов включается отдельно и по умолчанию выключен. Запрос тоже надо пометить кешируемым. Его ключ включает запрос и параметры; состав сохранённого результата зависит от версии и настройки Hibernate, поэтому сводить его всегда к «списку id» неверно. Смотри стоимость заполнения, инвалидации и чтения, а не только число попаданий.

Caffeine в демо живёт в одном процессе. Два пода с локальными регионами не получают общую инвалидацию автоматически. SQL другого приложения тоже не уведомляет Hibernate. Для изменяемых данных нужен согласованный провайдер, явная инвалидация либо отказ от L2. @Version обнаруживает устаревшую запись при UPDATE, если все писатели соблюдают изменение версии. Чтение кеша при этом всё равно может вернуть старые данные.

Batch сокращает отправку SQL, а flush и clear ограничивают память

Импорт квитанций через persist() создаёт managed-объект и удерживает его до очистки контекста. Большой импорт растит память для объектов, снимков и очереди изменений. JDBC batching решает другую часть задачи: группирует совместимые SQL-операции вместо отдельной отправки каждой записи. Поэтому размер batch и размер контекста надо ограничивать отдельно.

У Hibernate hibernate.jdbc.batch_size по умолчанию равен 0: batching выключен. В учебном варианте зададим 3 и после каждых трёх квитанций выполним flush(), затем clear(). Ключ квитанции известен заранее; все INSERT имеют одинаковую форму. В реальном импорте размер группы выбирают по памяти, драйверу и замерам, а не копируют учебное число.

@Entity
class Receipt {
    @Id Long id; // Известный ключ позволяет отложить INSERT до batch.
    int amount;
}

config.setProperty("hibernate.jdbc.batch_size", "3"); // batch; в batch-off задано 0.
factory.getStatistics().clear();
factory.inTransaction(session -> {
    for (int i = 1; i <= 6; i++) {
        session.persist(new Receipt(i, 10));
        if (i % 3 == 0) {
            System.out.println("before clear: managed=" + session.getStatistics().getEntityCount());
            session.flush(); // Выполнили SQL. Вся транзакция ещё не зафиксирована.
            session.clear(); // Убрали managed-объекты и их снимки.
            System.out.println("after clear: managed=" + session.getStatistics().getEntityCount());
        }
    }
}); // Commit всех шести записей вместе.
System.out.printf("inserted=%d, prepared statements=%d%n",
        factory.getStatistics().getEntityInsertCount(),
        factory.getStatistics().getPrepareStatementCount());

Заголовки # добавлены к stdout. При batching подготовлено два ORM-выражения для двух групп, без него — шесть. Это счётчик подготовки statements, а не универсальное измерение сетевых пакетов или времени. Число сохранённых entity одинаковое, а контекст в обоих вариантах освобождается каждые три объекта.

IDENTITY меняет момент INSERT

При GenerationType.IDENTITY ключ выдаёт выполненный INSERT. Hibernate вынужден получить его сразу и отключает JDBC batching таких вставок. Сам параметр batch_size может оставаться положительным; это не доказывает, что все таблицы пишутся пачками.

@Entity
class IdentityReceipt {
    @Id @GeneratedValue(strategy = GenerationType.IDENTITY) Long id;
    int amount;
}

// Вместо Receipt(i, 10) в том же цикле и при batch_size=3:
session.persist(new IdentityReceipt(10)); // Для назначения id нужен отдельный INSERT.
./run.sh LockingDemo identity
before clear: managed=3
after clear: managed=0
before clear: managed=3
after clear: managed=0
inserted=6, prepared statements=6

Для генерации ключей с batching часто выбирают sequence и подходящий размер выделения id. hibernate.order_inserts и hibernate.order_updates помогают собрать совместимые выражения, но добавляют сортировку. SQL-лог с шестью INSERT ещё не доказывает отсутствие JDBC batch: смотри статистику и работу драйвера. default_batch_fetch_size относится к чтению связей и не включает batch-запись.

flush() — не commit, clear() — не освобождение блокировок базы. Одна длинная транзакция после очистки контекста всё ещё держит подключение и уже полученные блокировки. Если данные допустимо сохранять частями, дели импорт на короткие транзакции с контрольной точкой и безопасным повтором. Для простого массового SQL без жизненного цикла entity JDBC batch может оказаться яснее ORM. Bulk JPQL, в свою очередь, обходит managed-состояние и требует продуманной очистки контекста.

  • Version проверяет исходное состояние вычисления через WHERE по старой версии. Конфликт требует новой транзакции и повторной проверки бизнес-условий.
  • PESSIMISTIC_WRITE получает блокировку строки до изменения объекта и держит её до завершения транзакции. Не выполняй под ней сетевую работу.
  • L1 сохраняет идентичность managed-объекта. Повторный find не обещает свежую строку; refresh и clear меняют состояние контекста.
  • L2 переносит данные между контекстами, а не общий Java-объект. Другие писатели и несколько процессов требуют отдельного согласования кеша.
  • Batch группирует SQL, flush отправляет изменения, clear отсоединяет объекты. Ни один из них не заменяет commit и не снимает блокировки.

На собеседовании

Как работает optimistic locking и что делать после OptimisticLockException?

Я добавляю @Version. При чтении Hibernate запоминает версию, а при UPDATE проверяет старую в WHERE и записывает следующую. Если другой платёж уже изменил счёт, обновлено ноль строк и возникнет OptimisticLockException. Чужое изменение не затрётся. Я откатываю операцию и при допустимом повторе начинаю новую транзакцию, читаю актуальное состояние и снова проверяю условия.

  • Проверка происходит при flush/commit; чистый выход из Java-метода ещё не доказывает успех. Повтор должен окружать завершённую границу транзакции.
  • Bulk JPQL и SQL других писателей способны обойти версию. Все пути изменения строки должны следовать общей стратегии.
  • Версии разных entity не защищают автоматически общий лимит. Нужна точка координации инварианта.
После конфликта можно просто повторить merge того же объекта?

У него остались прежние данные и версия. Такой повтор либо снова конфликтует, либо при ручной подмене версии затирает чужой результат. Повторяй смысл операции по новым данным, а не перенос старого снимка. После неуспешной транзакции старый persistence context закрывают.

Когда выбрать pessimistic locking, а когда @Version?

При редких конфликтах я беру optimistic locking: читаю без ранней блокировки и проверяю версию на записи. Если конфликт частый или повтор дорог, PESSIMISTIC_WRITE позволяет взять строку до вычисления и выстроить конкурирующие операции в очередь. Цена — ожидание, занятые подключения и риск deadlock. Блокировка живёт до commit или rollback, поэтому операция должна быть короткой.

  • Блокировка базы работает между процессами; synchronized на объекте entity защищает только один JVM-объект.
  • MVCC позволяет обычному SELECT читать снимок несмотря на блокировку записи. Точный SQL и режим ожидания задаёт СУБД/диалект.
  • При нескольких счетах беру блокировки в одном порядке. Ошибку ожидания обрабатываю снаружи транзакции, а не продолжаю её вслепую.

Чем отличаются кеш первого уровня, второго уровня и кеш запросов?

L1 — persistence context с единственным managed-объектом на ключ. Он обеспечивает идентичность и dirty checking. L2 общий для SessionFactory и хранит данные, из которых новый контекст создаёт свой объект. Для него нужны провайдер и выбор кешируемых entity. Кеш результатов запросов включается отдельно; @Cacheable на entity не отменяет выполнение любого JPQL.

  • Повторный JPQL может выполнить SQL и вернуть прежний объект L1. Для явного обновления есть refresh, для отсоединения всех объектов — clear.
  • READ_WRITE координирует регион кеша, но не заменяет row lock и не уведомляется о любом внешнем SQL.
  • Локальный Caffeine не даёт автоматической инвалидации между подами. TTL ограничивает срок устарелости, а не обеспечивает мгновенную согласованность.

Как организовать большую batch-запись и почему batch_size бывает недостаточно?

Я включаю JDBC batching для совместимых SQL и ограничиваю размер persistence context через flush, затем clear. Flush отправляет изменения, clear отсоединяет объекты и их снимки. Commit остаётся отдельной границей. При IDENTITY Hibernate нужен выполненный INSERT для получения ключа, поэтому batching таких вставок отключён, даже если batch_size положительный.

  • Очистка контекста уменьшает память JVM, но не отдаёт подключение и блокировки незавершённой транзакции.
  • Сортировка inserts/updates повышает шанс собрать batch и сама стоит времени. Проверяю статистику и драйвер вместо вывода по одному SQL-логу.
  • Транзакции по частям требуют контрольной точки и идемпотентного повтора. Если жизненный цикл entity не нужен, рассматриваю JDBC batch.
