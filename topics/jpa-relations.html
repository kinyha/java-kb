Relations & Fetching

У платежа есть магазин и возвраты. В Java это ссылки и коллекции; в базе — внешние ключи и строки. Hibernate переводит одно представление в другое, но направление записи и план чтения ты выбираешь сам. Сначала определи, какое поле управляет внешним ключом. Затем реши, какие данные нужны конкретной операции и сколькими SQL-запросами она их получит.

Внешний ключ меняет владелец связи, а Java-граф согласует сервис

Платёж №17 ошибочно привязали к магазину №1. Сервис добавляет его в merchant2.payments и выполняет commit. На следующем запросе платёж снова у первого магазина: коллекция изменилась, но payments.merchant_id определяет поле Payment.merchant.

В двунаправленной связи одна сторона — owning side, владелец записи отношения. Вторая — обратная сторона с mappedBy, именем Java-поля владельца. Для ManyToOne / OneToMany владельцем служит сторона «многие»: там находится внешний ключ. mappedBy = "merchant" — это имя атрибута, а не имя SQL-колонки.

@Entity(name = "Merchant") @Table(name = "merchants")
class Merchant {
    @Id Long id;
    String name;
    @OneToMany(mappedBy = "merchant") // Эта коллекция не записывает merchant_id.
    List<Payment> payments = new ArrayList<>();
    public List<Payment> getPayments() { return payments; }
}

@Entity(name = "Payment") @Table(name = "payments")
class Payment {
    @Id Long id;
    @ManyToOne(fetch = FetchType.LAZY)
    @JoinColumn(name = "merchant_id") // Владелец записи внешнего ключа.
    Merchant merchant;

    void moveTo(Merchant next) {
        if (merchant != null) merchant.getPayments().remove(this);
        merchant = next; // Эта строка определяет изменение FK в базе.
        if (next != null && !next.getPayments().contains(this))
            next.getPayments().add(this); // Согласуем обратную сторону в Java.
    }
}

Полный RelationsDemo.java запускается через общий run.sh. Стек: JDK 21.0.11, Hibernate 7.4.5.Final, Jakarta Persistence 3.2, H2 2.4.240; версии задаёт BOM Boot 4.1.1 в pom.xml. Ниже — три отдельные транзакции режима owning. Внешний ключ читается напрямую через JDBC на том же соединении после flush.

// 1. Платёж исходно принадлежит магазину 1.
next.getPayments().add(p); // next — магазин 2; меняем только mappedBy.
em.flush();
System.out.println("inverse-only: fk=" + merchantId(em));

// 2. Новый контекст: загружаем обе коллекции, затем меняем только владельца.
old.getPayments().size(); next.getPayments().size();

System.out.println("owning-only: fk=" + merchantId(em)

Во втором варианте SQL правильный, но чтение старой коллекции приведёт к ошибке бизнес-правила. Методы add, remove и moveTo должны согласовывать обе стороны.

Каскад распространяет операцию, а orphanRemoval удаляет зависимый объект

Возврат принадлежит одному платежу, магазин существует независимо. Эта разница определяет каскад: какие операции над родителем распространяются на связанные объекты. Каскад не выбирает владельца FK или план чтения.

// На Payment: возвраты — зависимые части его жизненного цикла.
@OneToMany(mappedBy = "payment", cascade = CascadeType.ALL, orphanRemoval = true)
List<Refund> refunds = new ArrayList<>();

// На Refund: именно эта ссылка задаёт payment_id.
@ManyToOne(fetch = FetchType.LAZY) @JoinColumn(name = "payment_id")
Payment payment;

void addRefund(Refund refund) {
    refunds.add(refund); refund.payment = this; // Согласуем обе стороны перед persist.
}
void removeRefund(Refund refund) {
    refunds.remove(refund); refund.payment = null; // Объект больше не часть платежа.
}

Payment p = new Payment(17L, merchant);
p.addRefund(new Refund(101L));
em.persist(p); // PERSIST проходит к Refund; Merchant сохраняется отдельно.

PERSIST распространяет создание, MERGE — перенос состояния, REMOVE — удаление. ALL включает также DETACH и REFRESH. Поэтому ALL должен описывать реальный общий жизненный цикл. На ссылке Payment.merchant каскад REMOVE означал бы попытку удалить магазин вместе с одним платежом; это ошибка модели.

orphanRemoval = true действует и при разрыве отношения: удаляем возврат из коллекции управляемого платежа, и Hibernate выполнит DELETE при синхронизации, хотя em.remove(refund) явно не вызван. Если удаляем сам платёж, orphanRemoval также распространяет удаление на зависимые возвраты; отдельно добавлять REMOVE для этого не требуется. Каскад REMOVE без orphanRemoval распространяет удаление родителя, но простое исключение возврата из коллекции его не удаляет.

tx(factory, em -> {
    Payment p = em.find(Payment.class, 17L);
    System.out.println("before remove: refunds=" + p.refunds.size());
    p.removeRefund(p.refunds.getFirst()); // Разрыв связи плюс orphanRemoval.
    em.flush();
    long count = em.createQuery(
            "select count(r) from Refund r where r.id = 101", Long.class)
        .getSingleResult();
    System.out.println("after orphan flush: rows=" + count);
});

OrphanRemoval подходит зависимому владению. Перенос в другой агрегат требует отдельного решения: отвязывание уже запланировало удаление. Для аудита возвраты часто переводят в другое состояние вместо физического удаления.

JPA-каскад — то же самое, что ON DELETE CASCADE в базе.

JPA распространяет операции над объектами. ON DELETE CASCADE работает при SQL в базе, включая SQL другого приложения, и не исправляет загруженный Java-граф. Согласуй оба механизма со схемой, аудитом и кешами; не считай их взаимозаменяемыми.

Lazy переносит чтение до обращения, eager требует данные заранее

Экран списка не всегда показывает реквизиты магазина и возвраты. Загрузка всего графа тратит время на ненужные данные. Lazy оставляет связь незагруженной до обращения; конкретный запрос задаёт нужное чтение.

АннотацияFetch по умолчанию в JPA 3.2Практический выбор
ManyToOne, OneToOneEAGERЧасто задают LAZY явно и загружают нужное конкретным запросом.
OneToMany, ManyToManyLAZYНе раскрывать большие коллекции без плана чтения.

Eager — требование загрузить состояние, а не команда «один JOIN». Провайдер может получить связь отдельным SELECT. Lazy по спецификации — подсказка: провайдер вправе загрузить раньше. Значит, аннотация на поле задаёт исходную политику, но число запросов всё равно проверяют для реального пути использования.

Hibernate часто использует прокси с известным id и обёртки коллекций. Метод, которому нужны остальные поля, запускает чтение через контекст. Прямое чтение поля прокси не равно вызову getter; в демо имя читается через getName().

// На Payment: ленивое чтение магазина задано явно.
@ManyToOne(fetch = FetchType.LAZY) @JoinColumn(name = "merchant_id")
Merchant merchant;

Payment p;
try (EntityManager em = factory.createEntityManager()) {
    p = em.find(Payment.class, 17L); // Получили платёж, магазин ещё не прочитан.
} // Контекст закрылся, загружать магазин через него больше нельзя.
try {
    System.out.println(p.merchant.getName());
} catch (LazyInitializationException e) {
    System.out.println("after close: " + e.getClass().getSimpleName());
}
./run.sh RelationsDemo closed
after close: LazyInitializationException

Переход всех связей в EAGER загрузит ненужное в остальных операциях. Собери нужный DTO внутри сервиса. Уже прочитанную связь можно использовать после закрытия контекста; ошибка относится к ещё не загруженному состоянию.

Под капотом: почему OneToOne бывает трудно оставить ленивой

У ManyToOne есть FK для прокси. У обратной необязательной OneToOne надо выяснить, существует ли строка в другой таблице. Это требует чтения даже при LAZY; bytecode enhancement помогает с некоторыми такими отображениями.

Equals, hashCode, toString и JSON тоже способны раскрыть ленивые ссылки. Не включай весь граф в сгенерированные методы entity.

План чтения для списка убирает N+1 без смены всей модели

Список содержит три платежа трёх разных магазинов. Сначала Hibernate читает платежи одним SELECT. Затем преобразование в ответ обращается к названию каждого магазина и запускает ещё три SELECT. Получилось N+1: один запрос к корням плюс дополнительные запросы при обходе связей. Если в списке 100 разных магазинов, число сетевых обращений растёт вместе со списком.

Eager тоже способен дать N+1. Несколько платежей одного магазина используют общий объект, поэтому дополнительные запросы зависят от числа разных FK. В опыте магазины разные, L2-кеш выключен, контекст для каждого варианта свежий.

Fetch join и EntityGraph задают нужный граф конкретному запросу

join fetch в JPQL требует загрузить связанную сущность вместе с корневой. Обычный join нужен для условий и соединения, но сам по себе не обещает инициализацию Java-связи. Для необязательной связи выбирай left join fetch, иначе INNER JOIN исключит платёж без магазина.

// Во всех вариантах перед запросом: новый EntityManager, sql.clear().
// Считаем SELECT через StatementInspector; L2-кеш выключен.

// lazy: одна выборка платежей, затем чтение трёх магазинов.
List<Payment> payments = em.createQuery(
        "select p from Payment p order by p.id", Payment.class).getResultList();
List<String> names = payments.stream().map(p -> p.merchant.getName()).toList();
System.out.println("lazy: names=" + names + ", selects=" + sql.selects());

// join: запрос сразу требует связанный магазин.
List<Payment> payments = em.createQuery(
        "select p from Payment p join fetch p.merchant order by p.id", Payment.class)
    .getResultList();
List<String> names = payments.stream().map(p -> p.merchant.getName()).toList();
System.out.println("join: names=" + names + ", selects=" + sql.selects());

// graph: тот же JPQL, но с отдельным описанием нужного графа.
EntityGraph<Payment> graph = em.createEntityGraph(Payment.class);
graph.addAttributeNodes("merchant");
List<Payment> payments = em.createQuery(
        "select p from Payment p order by p.id", Payment.class)
    .setHint("jakarta.persistence.fetchgraph", graph).getResultList();
List<String> names = payments.stream().map(p -> p.merchant.getName()).toList();
System.out.println("graph: names=" + names + ", selects=" + sql.selects());

fetchgraph трактует указанные атрибуты как EAGER, остальные — как LAZY. loadgraph добавляет указанные атрибуты к исходным правилам отображения. Провайдер вправе прочитать дополнительные данные; граф не обещает ровно один SQL во всех случаях. Один SELECT в выводе — проверенное поведение нашего отображения и Hibernate.

EntityGraph назначают аннотацией, программно или через @EntityGraph в Spring Data. Для вложенных связей есть subgraph. Включение всех уровней превращает экран в выгрузку домена.

Загрузить весь граф одним JOIN часто дороже, чем сделать два точных запроса

Связь «один магазин на платёж» не размножает строки платежа. Коллекция возвратов размножает: платёж с пятью возвратами появляется в SQL-результате пять раз. Hibernate собирает повторные строки в один объект, но база, сеть и сборка графа уже оплатили их объём. Устранить N+1 — не значит минимизировать только число запросов.

Две коллекции одного платежа усиливают проблему. Пять возвратов и четыре попытки банка дают до 20 комбинаций строк на один платёж. Несколько bag-коллекций Hibernate может вообще отказать загружать вместе с MultipleBagFetchException. Замена List на Set иногда снимает конкретный запрет, но не убирает декартово произведение и не делает запрос дешёвым.

Страница корней и страница строк JOIN — разные страницы

Если применить LIMIT к JOIN платежей и возвратов, он ограничит строки, а не количество платежей, и способен обрезать коллекцию. Hibernate для collection fetch с пагинацией может загрузить результат целиком и ограничить его в памяти. В проде полезно включить hibernate.query.fail_on_pagination_over_collection_fetch=true, чтобы такое решение стало явной ошибкой, а не случайной полной выгрузкой.

// Эскиз двух этапов: сначала страница ключей с устойчивой сортировкой.
List<Long> ids = em.createQuery(
        "select p.id from Payment p order by p.id", Long.class)
    .setFirstResult(offset).setMaxResults(size).getResultList();

// Затем полный нужный граф только для выбранных ключей, без LIMIT на JOIN.
List<Payment> page = ids.isEmpty() ? List.of() : em.createQuery(
        "select p from Payment p left join fetch p.refunds where p.id in :ids",
        Payment.class).setParameter("ids", ids).getResultList();
// IN не сохраняет порядок ids: упорядочи результат по исходной странице.

Это эскиз запроса для страницы, а не отдельный режим демо. Между двумя SELECT данные могут измениться; требуемую согласованность выбирают через транзакцию и изоляцию. Для больших таблиц вместо глубокого OFFSET рассматривают keyset-пагинацию. Для одного экрана проще бывает DTO-проекция: выбрать только сумму и название магазина, вообще не строя управляемый граф.

ПриёмКогда полезенЦена
Fetch join to-oneНужен магазин каждого платежаШире строка; необязательную связь учитывать LEFT JOIN.
Fetch одной коллекцииНебольшой известный набор корнейПовторные строки; размер коллекций надо знать.
Batch fetchingДочитываем несколько ленивых ссылокНесколько SELECT с IN; это чтение, не JDBC batch-запись.

@BatchSize и hibernate.default_batch_fetch_size позволяют Hibernate загрузить несколько ещё не прочитанных ссылок одной порцией. Это сокращает N+1 без большого JOIN. Размер порции выбирают по ограничениям базы и фактическому SQL. Не путай этот приём с hibernate.jdbc.batch_size, который группирует записи и разобран в Locking & Caching.

Наследование и составной ключ выбирают по форме данных и запросов

Платёж картой и перевод имеют общую сумму, но разные реквизиты. Наследование Java должно превратиться в таблицы. Выбор определяет ограничения и цену общей выборки, а не только красоту классов.

ОтображениеТаблицыКомпромисс
SINGLE_TABLEОдна таблица для всей иерархии, колонка типаПростая общая выборка; поля подтипов часто nullable. Ограничения по типу задают отдельно.
JOINEDОбщая таблица и таблицы подтипов с тем же PKМеньше пустых колонок, сильнее структура; чтение подтипов и общих списков требует соединений.
TABLE_PER_CLASSКаждый конкретный тип имеет свою таблицу с общими полямиПолиморфное чтение объединяет таблицы; общий ключ и связи сложнее.
MappedSuperclassПоля наследуются в таблицы потомков, собственной entity нетУдобно для id и аудита; запрос к этому базовому типу как entity невозможен.

Для entity-иерархии JPA использует SINGLE_TABLE по умолчанию. Стратегию лучше указать явно на корне. Discriminator помогает провайдеру определить подтип строки. Для MappedSuperclass дискриминатора и общей полиморфной выборки нет: это повторное использование отображения полей.

// Эскиз отображения; демонстрация SELECT выше использует обычный Payment.
@Entity
@Inheritance(strategy = InheritanceType.SINGLE_TABLE)
@DiscriminatorColumn(name = "payment_kind")
abstract class PaymentBase {
    @Id Long id;
    long amount;
    protected PaymentBase() {}
}
@Entity @DiscriminatorValue("CARD")
class CardPayment extends PaymentBase {
    String maskedCard; // В одной таблице рядом живут и поля банковского перевода.
    protected CardPayment() {}
}
@Entity @DiscriminatorValue("TRANSFER")
class BankTransfer extends PaymentBase {
    String bankReference;
    protected BankTransfer() {}
}

Если отличается в основном поведение, композиция проще: entity хранит способ оплаты, сервис выбирает стратегию. Иерархия базы не обязана копировать бизнес-код.

Составной ключ — одна идентичность из нескольких колонок

Проводку можно идентифицировать парой «платёж и номер строки». @EmbeddedId объединяет эту пару в отдельный объект ключа. @IdClass оставляет поля ключа на entity и описывает соответствующий класс отдельно. В обоих случаях имена и типы должны соответствовать отображению, а equals/hashCode ключа — равенству колонок.

@Embeddable
public static class EntryId implements java.io.Serializable {
    Long paymentId;
    int lineNo;
    protected EntryId() {}
    // equals/hashCode учитывают paymentId и lineNo; ключ не меняем после persist.
}

@Entity
class LedgerEntry {
    @EmbeddedId EntryId id;
    @MapsId("paymentId") // Связь использует ту же колонку, что часть ключа.
    @ManyToOne(fetch = FetchType.LAZY)
    @JoinColumn(name = "payment_id")
    Payment payment;
    long amount;
    protected LedgerEntry() {}
}

Здесь MapsId связывает идентичность дочерней записи с ключом платежа: одна колонка участвует и в ключе, и в связи. Не меняй первичный ключ управляемой entity, чтобы «перенести проводку»: это другая идентичность. Составные ключи усложняют внешние ключи и API; отдельный технический id плюс UNIQUE на бизнес-пару часто удобнее, если предметная модель не требует именно составного PK.

Отображение должно обслуживать реальные операции. Огромный двунаправленный граф трудно читать и обновлять. Однонаправленная связь или id другой части системы помогают удержать границу.

  • Владелец связи записывает FK; mappedBy лишь указывает обратную сторону. Обе ссылки в Java согласует твой метод.
  • Каскад описывает распространение операции. OrphanRemoval описывает удаление зависимого объекта при разрыве связи.
  • EAGER требует данные, но не обещает один JOIN. LAZY переносит чтение и требует доступного контекста для незагруженного состояния.
  • N+1 исправляют планом конкретного чтения. Fetch join, EntityGraph, порции и DTO решают разные задачи.
  • Collection fetch размножает SQL-строки. Пагинацию корней и загрузку коллекций часто лучше разделить.

На собеседовании

Что такое owning side? Почему изменение коллекции не сохранилось?

В двунаправленной связи одна сторона определяет запись отношения в базу. В ManyToOne/OneToMany это сторона «многие» с внешним ключом. MappedBy на коллекции указывает поле владельца, здесь Payment.merchant. Я меняю его для SQL и одновременно согласую коллекции магазинов для корректного Java-графа.

  • Owning side не равен владельцу агрегата в бизнес-модели: запись FK и жизненный цикл — разные решения.
  • OneToOne требует UNIQUE или общего PK на уровне базы. Аннотация без миграции ограничения не защищает реальные данные.
  • ManyToMany с атрибутами отношения лучше превратить в отдельную entity связи; тогда её поля, ключ и жизненный цикл становятся явными.

Что такое N+1 и как ты его исправляешь?

Один запрос получает список платежей, а обращение к связям запускает дополнительные SELECT. Я проверяю SQL полного сценария, включая преобразование в ответ. Затем задаю нужный граф конкретному запросу: fetch join, EntityGraph или DTO-проекцию.

Перевод всех полей в EAGER не решает проблему: eager тоже способен выполнять отдельные запросы. И один огромный JOIN не всегда лучше нескольких — коллекции размножают строки.

  • Тест на одном платеже не показывает N+1. Нужны несколько разных FK и свежий контекст; кеши иначе скрывают дополнительные SELECT.
  • Batch fetching дочитывает несколько ленивых ссылок через порции IN. Это отличается от JDBC batch-записи.
  • Fetchgraph меняет правила указанных и неуказанных атрибутов, loadgraph дополняет исходные. Ни один не даёт общей гарантии «всегда один SQL».
Запрос сделал один SELECT, но экран всё равно медленный. Что проверишь?

Число SQL-строк после соединения коллекций, ширину результата, объём данных и работу сборки графа. Один платёж с пятью возвратами и четырьмя попытками даёт до двадцати строк. Разделение чтения или DTO может ускорить экран даже при большем числе SQL-запросов.

Чем lazy отличается от eager? Как исправить LazyInitializationException?

Eager требует загрузить данные заранее, lazy позволяет отложить до обращения. Это не выбор между JOIN и SELECT: SQL определяет провайдер и план запроса. Незагруженная ссылка после закрытия её контекста не сможет прочитаться, и Hibernate выдаст LazyInitializationException.

Я загружаю нужные данные в сервисной операции и возвращаю DTO. Тогда JSON не раскрывает граф случайно. Общий переход на EAGER только разносит цену этой проблемы по всем запросам.

  • Lazy — подсказка спецификации, eager — требование. Обратная необязательная OneToOne бывает сложнее для ленивого чтения, потому что у неё нет своего FK.
  • ToString, equals и сериализация способны вызвать скрытую загрузку. Контекст доступен — ещё не значит, что обход графа был запланирован.
  • Open EntityManager in View продлевает контекст, но не делает весь веб-запрос одной транзакцией и маскирует SQL после сервиса.

Чем cascade REMOVE отличается от orphanRemoval?

Каскад REMOVE распространяет удаление родителя на связанные сущности. OrphanRemoval удаляет зависимый объект, когда его убрали из отношения, даже без удаления родителя. Для возврата внутри платежа это может подходить, а магазин живёт независимо и не должен удаляться вместе с одним платежом.

  • ON DELETE CASCADE работает в базе, JPA-каскад работает через операции объектов. Внешний SQL не выполняет доменные методы и не согласует граф в памяти.
  • OrphanRemoval предполагает зависимое владение. Перенос объекта между родителями и аудит удаления надо проектировать отдельно.
  • Массовый JPQL DELETE обходит обычный жизненный цикл сущностей; рассчитывать на те же каскады и callbacks нельзя.

Можно ли сделать fetch коллекции вместе с пагинацией?

Collection fetch размножает строки корня. LIMIT тогда ограничивает строки JOIN, а не число платежей, поэтому страницу корней часто выбираю отдельно от их коллекций. Несколько коллекций дают декартово произведение; одного запроса может оказаться слишком много.

  • Ошибка Hibernate при нескольких bags и цена декартова произведения — разные проблемы. Замена List на Set не лечит объём SQL-результата.
  • После запроса по IN восстанавливаю порядок страницы. Между этапами возможно изменение данных, поэтому выбираю нужную изоляцию.
  • Запрещаю случайную пагинацию collection fetch настройкой fail_on_pagination_over_collection_fetch. Для экрана рассматриваю DTO или keyset.

Как выбираешь отображение наследования и составного ключа?

SINGLE_TABLE проще читать, JOINED разделяет поля ценой соединений, TABLE_PER_CLASS усложняет полиморфную выборку. Я выбираю по запросам и ограничениям схемы. Для составного ключа использую EmbeddedId или IdClass с правильными equals/hashCode; общую колонку связи выражаю через MapsId.

  • MappedSuperclass наследует отображение, но не создаёт entity для полиморфного запроса. Его выбирают для общих полей, а не общей таблицы.
  • Составной PK переносится во все ссылающиеся FK. Технический id плюс UNIQUE на бизнес-пару может упростить схему и API.

  • Jakarta Persistence 3.2 — разделы 2.4, 2.11–2.14, 3.8: составные ключи, владельцы отношений, наследование и семантика EntityGraph.
  • Spring Data JPA: Query Methods — назначение EntityGraph конкретному методу репозитория.
  • Java Persistence with Hibernate, 2-е издание — объектные связи, жизненный цикл зависимых сущностей и выбор плана загрузки.
