JPA Basics

Сервис загружает платёж, меняет его сумму и завершает транзакцию. Hibernate следит за загруженным объектом и сам готовит SQL для изменений. Пока объект принадлежит текущему контексту, повторное чтение того же платежа вернёт ту же ссылку. Поэтому при странном результате сначала выясни, какой объект изменился, кто сейчас за ним следит и когда изменения дошли до базы.

Изменение загруженного платежа сохраняется без вызова save

В обработчик возврата приходит платёж №17. Сервис уменьшает сумму и заканчивает работу. В коде нет UPDATE, а в базе сумма изменилась. Другой обработчик делает то же самое с объектом, пришедшим из предыдущего запроса, — и в базе ничего не происходит. Разница в том, кто управляет объектом в момент изменения.

JPA — привычное название спецификации Jakarta Persistence. Она задаёт модель объектов, операций и запросов. Hibernate — конкретная реализация этой модели. Spring управляет границей транзакции и даёт приложению EntityManager; Spring Data добавляет репозитории. Это разные слои, и для автоматического сохранения управляемого объекта репозиторий вообще не нужен.

Entity представляет запись с устойчивой идентичностью. Два объекта с одинаковыми полями ещё не обязательно один платёж; главным остаётся его первичный ключ. В простом примере деньги хранятся в минимальных единицах валюты, поэтому сумма — long. Для произвольной точности используют BigDecimal с согласованными scale и правилами округления.

@Entity(name = "Payment") // Имя типа в JPQL; это не имя таблицы.
@Table(name = "payments")
public static class Payment {
    @Id Long id; // Аннотация на поле выбирает доступ к полям.
    @Column(nullable = false, unique = true) String merchantRef;
    @Column(nullable = false) long amount;
    @Enumerated(EnumType.STRING) @Column(nullable = false) Status status;
    protected Payment() {} // Провайдер создаёт объект при чтении строки.
    Payment(Long id, long amount) {
        this.id = id; this.amount = amount;
        this.merchantRef = "shop-" + id; this.status = Status.NEW;
    }
}
enum Status { NEW, PAID }

em.getTransaction().begin();
Payment p = em.find(Payment.class, 17L); // Загрузили в текущий контекст.
p.amount = 250;                        // Это изменение управляемого объекта.
em.getTransaction().commit();          // Здесь Hibernate синхронизирует изменения.

Это фрагмент полного JpaDemo.java. В нём Hibernate 7.4.5.Final, Jakarta Persistence 3.2, H2 2.4.240 и JDK 21.0.11. Общий pom.xml использует BOM Boot 4.1.1. Дальше показан настоящий вывод четырёх режимов демо; каждый запуск начинает с платежа №17 и суммы 100.

Entity требует конструктора без аргументов и не подходит для record: состояние меняется, а провайдеру часто нужен прокси. Положение @Id выбирает доступ к полям или свойствам. Для смешанного доступа укажи @Access; наличие setter само по себе не определяет сохранение.

@Column(nullable = false) описывает отображение в таблицу. Это не заменяет проверку запроса на входе. Ошибка ограничения может обнаружиться только при выполнении SQL. В проде схему ведут миграции; hbm2ddl.auto=create-drop из демо удаляет учебные таблицы и для платёжной базы не подходит.

Контекст связывает ключ записи с одним управляемым объектом

Persistence context — рабочая память провайдера для управляемых сущностей. У него есть соответствие «тип сущности и ключ → объект», сведения о состоянии объекта и данные для обнаружения изменений. Если сервис дважды вызывает find(Payment.class, 17L) в одном контексте, он получает одну и ту же Java-ссылку. Второй вызов не обязан снова читать строку.

Это важно для согласованности графа: изменение платежа через одну ветку сразу видно через другую. Отдельный контекст загружает отдельный объект той же строки.

Payment first = em.find(Payment.class, 17L);
Payment second = em.find(Payment.class, 17L);
System.out.println("same instance=" + (first == second)); // Сравниваем именно ссылки.
same instance=true

Это кеш первого уровня, а не кеш любых запросов. JPQL может выполнить SQL и сопоставить строки имеющимся объектам. Если другая транзакция поменяла платёж, повторный find не обновит его поля. Для перечитывания есть refresh, а для защиты конкурентной записи — блокировки или версия.

Кто создаёт контекст в Spring

EntityManagerFactory создают на приложение. Настоящий EntityManager нельзя делить между параллельными потоками, включая виртуальные: внутри изменяемый граф и очередь операций. Между задачами передавай id или DTO; каждой транзакционной задаче нужен свой контекст.

@PersistenceContext внедряет Spring-оболочку, которая находит контекст текущей транзакции. Singleton-сервис хранит эту оболочку в поле, но не должен хранить там загруженный Payment: следующий запрос обслуживает другого клиента и другой контекст.

@Service
class RefundService {
    @PersistenceContext EntityManager em; // Spring-оболочка, а не один контекст на всех.

    @Transactional
    public void reduceAmount(long id, long amount) {
        Payment p = em.find(Payment.class, id); // Контекст текущей транзакции.
        p.amount = amount;
    } // JpaTransactionManager завершит транзакцию и синхронизирует изменения.
}

Если объект есть в Java-памяти, Hibernate продолжает за ним следить.

За объектом следит конкретный контекст. Java-ссылка может жить после его закрытия сколько угодно, но сама по себе не приводит к SQL. Это и есть причина, по которой один setter сохраняется, а другой остаётся только в памяти.

Операция меняет состояние объекта, а merge возвращает другую ссылку

Жизненный цикл entity отвечает на практический вопрос: с какого момента и до какого момента изменения объекта участвуют в синхронизации. New — объект создали через new, но ещё не передали контексту. Managed — контекст им управляет. Detached — идентичность есть, а связи с прежним контекстом больше нет. Removed — объект помечен на удаление, которое должно дойти до базы.

persist делает новый объект управляемым. Это не обещание немедленного INSERT: время SQL зависит от генерации ключа и момента синхронизации. find получает управляемый объект. detach убирает один объект, clear — весь контекст, а close закрывает его. Перед отделением объекта сохрани нужные изменения через flush, иначе контекст больше не обнаружит их при завершении транзакции.

Почему результат merge надо использовать

Сервис получил платёж из старого контекста. merge(detached) ищет или создаёт управляемый объект с той же идентичностью и копирует в него поля. Возвращается управляемый результат. Переданный объект остаётся отделённым: поздние изменения этой исходной ссылки больше никуда не копируются сами.

Payment detached;
try (EntityManager old = factory.createEntityManager()) {
    detached = old.find(Payment.class, 17L);
} // Старый контекст закрыт.
detached.amount = 300;

tx(factory, em -> {
    Payment managed = em.merge(detached); // Копируем текущее состояние в новый контекст.
    System.out.println("merge same instance=" + (managed == detached));
    System.out.println("contains original=" + em.contains(detached)
            + ", copy=" + em.contains(managed));
    detached.amount = 900; // Правка старой ссылки уже не влияет на managed.
}); // commit сохраняет 300 из managed.
System.out.println("after merge: database=" + savedAmount(factory)
        + ", original=" + detached.amount);
# Из examples/data: режим запускает именно фрагмент выше.
./run.sh JpaDemo merge
merge same instance=false
contains original=false, copy=true
after merge: database=300, original=900

Managed-объекту merge не нужен. Новому нужен persist, а для detached вызов persist — ошибка, обнаруживаемая при вызове или синхронизации. Remove тоже требует управляемого объекта: загрузи платёж в текущей транзакции и удали.

Полный merge полученного от клиента объекта часто слишком широк. Клиент мог прислать старую сумму, пустую коллекцию или поле, которое ему нельзя менять. Для команды «подтвердить платёж» загрузить entity и вызвать доменный метод безопаснее, чем переносить всю клиентскую копию поверх текущего состояния. Защита от параллельной записи через @Version разобрана в Locking & Caching.

Под капотом: идентичность в базе и equals — разные задачи

Контекст узнаёт entity по типу и ключу; equals нужен твоим коллекциям. Генерируемый id меняется после INSERT. Зависимый от него hashCode ломает размещение в HashSet. Выбирай устойчивый бизнес-ключ с UNIQUE либо сравнение ненулевых id со стабильным hashCode; отдельно учитывай прокси и наследование.

Не включай весь граф в equals, hashCode и toString: связи способны выполнить SQL и уйти в рекурсию. Меняющиеся сумма и статус тоже не определяют идентичность платежа.

Flush выполняет SQL, а commit решает судьбу транзакции

Dirty checking обнаруживает изменения управляемых объектов. При загрузке Hibernate сохраняет сведения об исходных значениях. Во время flush он проверяет состояние, готовит INSERT, UPDATE и DELETE и выполняет нужные операции через JDBC. Изменение поля в Java и запись строки в базе разделены во времени.

Демо читает сумму напрямую через JDBC на том же соединении. Это принципиально: обычный find вернул бы уже изменённый объект из контекста, а JPQL-запрос мог бы сначала вызвать автоматический flush. Такой опыт ничего не сказал бы о том, когда появился UPDATE.

em.getTransaction().begin();
Payment first = em.find(Payment.class, 17L);
Payment second = em.find(Payment.class, 17L);
System.out.println("same instance=" + (first == second));
sql.clear(); // StatementInspector считает реально подготовленные UPDATE.
first.amount = 250;
System.out.println("before flush: database=" + databaseAmount(em)
        + ", updates=" + sql.updates());
em.flush(); // SQL дошёл до соединения, но commit ещё не был вызван.
System.out.println("after flush: database=" + databaseAmount(em)
        + ", updates=" + sql.updates());
em.getTransaction().rollback();
em.close();
System.out.println("after rollback: database=" + savedAmount(factory));

// Чтение строки без EntityManager.find и без JPQL.
long databaseAmount(EntityManager em) {
    return em.unwrap(Session.class).doReturningWork(connection -> {
        try (var s = connection.prepareStatement(
                "select amount from payments where id = 17");
             ResultSet row = s.executeQuery()) {
            row.next(); return row.getLong(1);
        }
    });
}
./run.sh JpaDemo dirty # Счётчики исключают SQL начального наполнения.
same instance=true
before flush: database=100, updates=0
after flush: database=250, updates=1
after rollback: database=100

Commit синхронизирует нужные изменения и фиксирует транзакцию. Flush нужен для раннего SQL: проверить ограничение или подготовить данные для следующей операции. Блокировки остаются до завершения транзакции, а изменения ещё можно откатить.

Rollback не является кнопкой «вернуть все Java-поля назад». Ранее полученная ссылка может по-прежнему хранить 250, хотя база снова хранит 100. После ошибки откатывай транзакцию и начинай следующую попытку с нового контекста. Не продолжай тот же бизнес-процесс на прежнем графе, рассчитывая, что он стал точной копией базы.

Под капотом: снимки, усиление байткода и порядок SQL

Bytecode enhancement помогает entity отмечать изменённые атрибуты и сокращает сравнение графа. Но setter всё ещё не означает немедленный SQL. Порядок SQL тоже не равен порядку Java-вызовов: новый INSERT может обогнать DELETE и встретить прежний UNIQUE-ключ.

При IDENTITY INSERT часто нужен раньше, чтобы получить ключ; SEQUENCE позволяет получить ключ отдельно. Поэтому время записи проверяют по фактическому SQL и стратегии ключа. Промежуточный flush должен решать конкретную задачу.

Запрос способен вызвать flush, а массовый UPDATE обходит объекты

Сервис поменял платёж, а затем посчитал сумму платежей через JPQL. Если выполнить SELECT по старым строкам, результат противоречит изменениям текущего сервиса. Поэтому FlushModeType.AUTO, режим JPA по умолчанию, обеспечивает видимость изменений, влияющих на результат запроса. Hibernate перед JPQL-запросом к затронутым таблицам может выполнить flush.

Это не значит «AUTO всегда выполняет все UPDATE перед любым SELECT». Провайдер учитывает запрос и свои правила синхронизации. Для native SQL поведение дополнительно зависит от API и сведений о затронутых таблицах. Если корректность конкретной операции требует уже выполненного SQL, вызови flush явно, а не пытайся угадать, распознает ли провайдер зависимость.

// Первый опыт: режим AUTO, в базе исходно 100.
tx(factory, em -> {
    Payment p = em.find(Payment.class, 17L); p.amount = 200;
    sql.clear();
    long result = em.createQuery(
            "select p.amount from Payment p where p.id = 17", Long.class)
        .getSingleResult(); // Скалярный результат приходит из SELECT, а не из поля p.
    System.out.println("AUTO query=" + result + ", updates=" + sql.updates());
}); // В базе теперь 200.

// Второй опыт: COMMIT откладывает синхронизацию; используем тот же провайдер.
tx(factory, em -> {
    em.setFlushMode(FlushModeType.COMMIT);
    Payment p = em.find(Payment.class, 17L); p.amount = 300;
    sql.clear();
    long result = em.createQuery(
            "select p.amount from Payment p where p.id = 17", Long.class)
        .getSingleResult();
    System.out.println("COMMIT query=" + result + ", memory=" + p.amount
            + ", updates=" + sql.updates());
});
System.out.println("after commit: database=" + savedAmount(factory));
./run.sh JpaDemo query
AUTO query=200, updates=1
COMMIT query=200, memory=300, updates=0
after commit: database=300

В режиме COMMIT влияние несинхронизированных изменений на результат запроса спецификация не определяет. Вывод 200 здесь — поведение указанного Hibernate, а не универсальная гарантия для всех провайдеров. Выбирать COMMIT ради уменьшения SQL и затем ожидать от всех запросов актуального состояния объектов — противоречивое решение.

Один запрос меняет много строк, но не обновляет уже загруженный граф

JPQL update и delete выполняют массовую операцию над таблицами. Провайдер не загружает каждую сущность, не вызывает её доменные методы и не исправляет все соответствующие Java-поля. Это полезно для архивации миллионов платежей, но старые управляемые объекты после такого SQL уже не отражают строки.

tx(factory, em -> {
    Payment p = em.find(Payment.class, 17L); // В памяти amount=100.
    int rows = em.createQuery(
            "update Payment p set p.amount = 900 where p.id = 17")
        .executeUpdate(); // Изменяет строку напрямую, минуя p.
    System.out.println("bulk rows=" + rows + ", memory=" + p.amount
            + ", database=" + databaseAmount(em));
    System.out.println("find same instance=" + (p == em.find(Payment.class, 17L)));
    em.refresh(p); // SELECT перезаписывает состояние управляемого объекта.
    System.out.println("after refresh: memory=" + p.amount);
});
./run.sh JpaDemo bulk
bulk rows=1, memory=100, database=900
find same instance=true
after refresh: memory=900

Повторный find не спас: контекст честно вернул прежнюю ссылку. Для одного объекта подходит refresh. Для массовой операции обычно проще сначала синхронизировать нужные изменения, выполнить SQL и очистить контекст, а затем перечитать требуемые данные. В Spring Data этому соответствуют настройки @Modifying; сам вызов репозитория не меняет природу массового UPDATE.

refresh заменяет локальные поля данными строки и способен потерять ещё не сохранённые изменения. clear отделяет весь граф и тоже не выполняет flush сам. Перед ними реши, какие изменения надо сохранить. Это действие над рабочим состоянием, а не безобидная команда «почистить кеш».

Граница контекста должна совпадать с понятной единицей работы

Держи контекст вокруг короткой бизнес-операции: загрузить платёж, проверить переход, изменить состояние, зафиксировать. Долгий вызов банка внутри транзакции удерживает соединение и увеличивает конкуренцию за данные. Результат внешнего вызова не откатывается вместе с JDBC-транзакцией.

Чем больше управляемых объектов, тем больше памяти занимают объекты, коллекции и сведения провайдера, и тем больше работы остаётся для flush. Долгоживущий контекст, читающий выгрузку за месяц, способен удержать весь граф. Для больших потоков данных используют порции, проекции или прямой SQL, а для записи порциями — осмысленные flush и clear. Размер пакета и JDBC batch разобраны в соседней теме.

tx(factory, em -> {
    Payment p = em.find(Payment.class, 17L);
    p.amount = 700;
    em.clear(); // Нет flush: объект отделили раньше, чем синхронизировали правку.
    System.out.println("after clear: managed=" + em.contains(p));
}); // commit уже не найдёт изменение отделённого p.
System.out.println("after clear+commit: database=" + savedAmount(factory));
after clear: managed=false
after clear+commit: database=100

Это последние две строки режима dirty: после предыдущего rollback строка снова содержит 100. Добавление em.flush() перед clear() изменит смысл — UPDATE попадёт в транзакцию и сможет сохраниться при её commit. Но вызов flush после каждой строки убирает преимущества накопления изменений и увеличивает число обращений к базе.

Что возвращать за границу сервиса

Верни DTO, собранный внутри известной границы. Сериализация entity может выполнить случайные SELECT или упасть после закрытия контекста. Выбор данных без N+1 разобран в Relations & Fetching.

Open EntityManager in View держит контекст до конца веб-запроса и позволяет дочитывать связи после сервиса. Это маскирует неявный SQL и не превращает HTTP-запрос в одну транзакцию. Extended-контекст тоже живёт дольше одной операции, но требует явного управления временем жизни; он не делает singleton-сущности безопасными.

При расследовании смотри SQL, границу транзакции, количество сущностей и время flush. Через contains проверь managed-состояние; найди clear и массовые UPDATE. Для сложной агрегации используй проекцию или JDBC. ReadOnly и правила @Transactional разобраны в Transactions.

  • Автоматически сохраняются изменения managed-объекта в конкретном контексте, а не любой Java-ссылки на entity.
  • Один ключ в одном контексте означает один объект. Это объясняет повторный find и устаревшее состояние после внешнего SQL.
  • Merge копирует состояние и возвращает управляемую ссылку. Исходная отделённая ссылка остаётся отделённой.
  • Flush выполняет SQL внутри транзакции; rollback всё ещё может отменить эти изменения.
  • Массовые операции и clear требуют явного решения о синхронизации, иначе память и строки расходятся.

На собеседовании

Чем отличаются JPA и Hibernate? Что делает persistence context?

JPA — спецификация, Hibernate её реализует. EntityManager загружает платёж в контекст: тот связывает тип и ключ с одним объектом и следит за изменениями. Два find дают одну ссылку. Spring задаёт транзакционную границу, Spring Data добавляет репозитории; для изменения managed-объекта дополнительный save не нужен.

  • Идентичность контекста не равна изоляции базы. Объект остаётся в памяти, даже если другая транзакция изменила строку. Refresh и защита конкурентной записи решают разные задачи.
  • EntityManagerFactory разделяют между потоками; настоящий EntityManager и entity-граф параллельно не используют. Внедрённая Spring-оболочка выбирает контекст текущей транзакции.
  • JPQL способен выполнить SQL даже при наличии сущностей в контексте. Кеш первого уровня хранит идентичность объектов, а не ответы любых запросов.

Какие состояния есть у entity? Что делают persist и merge?

New ещё не принадлежит контексту, managed отслеживается, detached отделён, removed помечен на удаление. Persist подключает новый объект. Merge переносит состояние detached в управляемый результат, а исходная ссылка остаётся detached. Продолжаю с возвращённой ссылкой; для команды клиента чаще загружаю актуальный платёж и меняю разрешённые поля.

  • Persist detached-объекта не заменяет UPDATE. Момент обнаружения ошибки зависит от вызова и последующей синхронизации.
  • Merge может читать строку и каскадно переносить связанный граф. Это цена операции над состоянием, а не бесплатное подключение ссылки.
  • Автоматически сгенерированный id и прокси требуют аккуратного equals/hashCode. Изменение hashCode после persist ломает размещение объекта в HashSet.
Контроллер получает JSON с id и вызывает merge всего объекта. Что проверишь?

Разрешено ли клиенту менять все поля и связи; как отличаются «поле не прислали» и «обнулить поле»; есть ли защита от старой версии. Для подтверждения платежа лучше отдельная команда с id, проверка владения и перехода состояния в транзакции. Merge не заменяет авторизацию и валидацию бизнес-перехода.

Как работают dirty checking и flush? Чем flush отличается от commit?

При flush Hibernate обнаруживает изменения управляемых сущностей и выполняет SQL. Setter до этого меняет объект. Flush синхронизирует данные внутри транзакции, commit фиксирует её, а rollback способен отменить уже выполненный UPDATE. Успешный flush ещё не означает устойчивое сохранение платежа.

  • Bytecode enhancement помогает отслеживать изменённые атрибуты, но момент SQL всё равно определяется синхронизацией и стратегией ключа.
  • Порядок SQL при flush не обязан совпадать с порядком Java-вызовов. Ограничения UNIQUE и внешние ключи делают это заметным.
  • Откат базы не возвращает Java-граф к прежним полям. После ошибки транзакции я перечитываю данные в новом контексте, а не продолжаю прежнюю попытку.

Почему SELECT вызывает UPDATE? Почему после массового UPDATE entity старая?

В AUTO провайдер учитывает изменения, влияющие на запрос, поэтому перед SELECT может выполнить flush. Массовый JPQL UPDATE, наоборот, меняет строки без обновления Java-графа. Повторный find даёт старый объект. Я делаю refresh либо синхронизирую нужные изменения, очищаю контекст и перечитываю данные.

  • В COMMIT влияние ещё не синхронизированных правок на результаты запросов не определено спецификацией. Поведение конкретного Hibernate не превращаю в переносимую гарантию.
  • Bulk-операции обходят доменные методы и обычный жизненный цикл каждой entity. При необходимости версий, аудита и инвариантов это надо учитывать отдельно.
  • Refresh и clear могут уничтожить несохранённое рабочее состояние. Сначала выбираю, что сохранить, а затем очищаю.

Какие проблемы даёт слишком долгий persistence context?

Контекст удерживает сущности и сведения о состоянии. Большая выгрузка увеличивает память и работу flush; я беру порции или проекции. За веб-границу возвращаю DTO, чтобы JSON не выполнял случайный SQL. Контекст и транзакция должны обслуживать понятную бизнес-операцию.

  • Open EntityManager in View продлевает время жизни контекста, но не делает весь HTTP-запрос атомарной транзакцией. Ленивая загрузка после сервиса имеет свои условия чтения.
  • Entity в singleton-поле или общей асинхронной задаче смешивает время жизни данных и контекста. Между задачами передаю id или неизменяемые данные.
