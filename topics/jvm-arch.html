How JVM Runs Code

Платёжный сервис может собраться и не запуститься

Ты собрал платёжный сервис на JDK 21, а в контейнере оставил Java 17. Сборка прошла, но сервис не дошёл до main: Java 17 не понимает class-файл версии 65. Это не ошибка бизнес-кода. Между исходником и работающим процессом есть отдельный контракт — формат class-файла.

JDK даёт инструменты разработки, включая javac, javap и runtime. JVM — виртуальная машина, которая исполняет class-файлы. JRE называют среду для запуска: JVM вместе со стандартной библиотекой и нужными файлами runtime. Для современных Java это полезное понятие, но отдельный JRE-дистрибутив не обязан поставляться рядом с JDK; runtime-образ можно собрать через jlink.

Проверяй обе стороны: версию компилятора в CI и версию runtime в образе. На установленном JDK 21 javap -verbose показывает major version: 65. Компиляция того же файла с javac --release 17 даёт версию 61 и запрещает API, отсутствующие в Java 17.

Достаточно поставить -source 17 -target 17, чтобы программа работала на Java 17.

Эти флаги задают синтаксис и формат class-файла, но не ограничивают ссылки на новые стандартные API. Для совместимости с Java 17 используй --release 17 и отдельно проверяй сторонние зависимости и нативные библиотеки.

Компилятор сохраняет инструкции, а не исходный Java-код

javac разбирает типы и преобразует исходник в class-файл. В нём лежат версия формата, constant pool со ссылками и литералами, описания полей и методов, а у исполняемых методов — атрибут Code с байткодом. JVM не обязана знать, как были написаны отступы, локальные имена или выражение 2 + 3.

В примере фиксированное выражение компилятор сворачивает до iconst_5. Вызов total(Integer.MAX_VALUE, 1) остаётся вызовом метода, а в его теле видна инструкция iadd. Она складывает два int с переполнением по правилам JVM, поэтому получается отрицательное число.

public class PaymentMath {
    static int total(int amount, int fee) {
        return amount + fee;
    }
    public static void main(String[] args) {
        int fixed = 2 + 3;
        int overflow = total(Integer.MAX_VALUE, 1);
        System.out.println(fixed + ":" + overflow);
    }
}
5:-2147483648

Запусти javac PaymentMath.java, затем javap -c -p PaymentMath. Это не декомпиляция в Java: javap печатает инструкции из class-файла. Ниже — проверенный фрагмент на JDK 21.0.11.

static int total(int, int);
  Code:
     0: iload_0
     1: iload_1
     2: iadd
     3: ireturn

public static void main(java.lang.String[]);
  Code:
     0: iconst_5
     1: istore_1
     2: ldc           #9   // int 2147483647
     4: iconst_1
     5: invokestatic  #10  // Method total:(II)I

invokestatic #10 ссылается на запись constant pool с именем и сигнатурой метода. При исполнении JVM разрешит эту символическую ссылку в конкретный метод. Индексы pool и номера строк могут отличаться после изменения кода или версии компилятора; смысл инструкций остаётся.

Под капотом: что хранится в class-файле

Class-файл начинается с magic 0xCAFEBABE и пары minor/major version. Инструкции метода находятся в атрибуте Code, где есть также max_stack, max_locals и таблица обработчиков исключений. Ссылки на методы и поля обычно идут через constant pool, а не через адреса памяти из машины разработчика. Формат описан в JVMS §4.

Метод вычисляет результат через локальные слоты и стек операндов

У каждого вызова метода есть кадр: локальные переменные и стек операндов. Для static total(int amount, int fee) два аргумента занимают слоты 0 и 1. iload_0 и iload_1 кладут значения на стек, iadd снимает оба и кладёт сумму, ireturn возвращает верхнее значение вызывающему методу.

Пройди четыре инструкции для total(2147483647, 1). Это позволяет предсказать результат даже без исходного Java: в байткоде нет проверки переполнения, iadd оставляет младшие 32 бита.

Кадр принадлежит вызову, а не классу. Если total вызовут два потока, у каждого будет свой кадр и свой стек операндов. Где физически лежат кадры, объекты и метаданные, подробно разобрано в «Memory Areas».

Перед main JVM должна подготовить класс

Команда java PaymentMath запускает процесс и передаёт имя стартового класса launcher'у. JVM находит его через classpath или module path, загружает байты, проверяет формат и допустимость байткода, подготавливает статические поля и выполняет инициализацию класса. После этого вызывает main(String[]).

Это отдельные фазы, поэтому ошибки выглядят по-разному. ClassNotFoundException или сообщение launcher'а «Could not find or load main class» указывает на поиск класса; UnsupportedClassVersionError — на слишком новую версию class-файла; ExceptionInInitializerError — на исключение во время static-инициализации. Разбор parent delegation, linking и порядка инициализации — в соседнем уроке «Class Loading».

JVM не загружает сразу все классы приложения. Зависимый класс может понадобиться позже, поэтому часть ошибок обнаруживается только при достижении определённого пути исполнения. В PaymentMath основной путь короткий, но в сервисе с условными интеграциями это различие важно.

HotSpot ускоряет горячий код, сохраняя результат байткода

Сначала HotSpot может исполнять метод интерпретатором и собирать профиль вызовов. Для часто выполняемого кода JIT создаёт машинные инструкции; они хранятся в code cache и исполняются на текущем процессоре. Это способ ускорить работу, а не изменить смысл программы: PaymentMath печатает одинаково в обычном режиме и с -Xint, где JIT отключён.

$ java -cp . PaymentMath
5:-2147483648
$ java -Xint -cp . PaymentMath
5:-2147483648

На JDK 21 -XX:+PrintCompilation показывает компиляции методов, но какие именно методы станут горячими и когда — зависит от нагрузки и профиля. Один короткий запуск PaymentMath может завершиться до компиляции его total. Фиксированного «после N вызовов JIT всегда включается» для приложения нет.

JIT может встроить тело total в вызывающий код и убрать сам вызов, но обязан сохранить наблюдаемый результат, включая переполнение int и исключения. Если оптимизация опиралась на профиль, который перестал быть верным, HotSpot может деоптимизировать код. Tiered compilation, C1/C2, OSR и деоптимизация подробно идут в отдельной теме «JIT».

Java всегда интерпретируется и потому медленная.

Байткод — входной формат JVM. HotSpot умеет и интерпретировать его, и компилировать горячие участки в машинный код. Скорость конкретного сервиса зависит от прогрева, аллокаций, I/O и алгоритма; наличие JIT само по себе не делает запрос быстрым.

Граница JVM проходит по runtime, зависимостям и ОС

Class-файл переносим между совместимыми реализациями JVM, но процесс опирается на стандартную библиотеку, сторонние JAR, системные библиотеки и ОС. Если в образе нет нужной зависимости, можно получить NoClassDefFoundError или ClassNotFoundException. Если вызов уходит в JNI или сторонний нативный драйвер, одного байткода уже недостаточно для переносимости.

Для деплоя фиксируй версию сборки и runtime. Сначала проверь java -version внутри контейнера, затем javap -verbose PaymentMath | grep 'major version' для class-файла. Если версия подходит, проверяй classpath/module path и зависимости, затем журналы загрузки -Xlog:class+load=info. Эта последовательность быстрее гадания о «сломавшемся JIT».

Команда java PaymentMath.java на JDK 21 компилирует исходник в памяти и запускает его; она удобна для одного файла, но не заменяет сборку сервиса. java -jar app.jar запускает JAR по его manifest, java -cp ... Main ищет класс по classpath. В каждом случае исполняет JVM, но способ найти стартовый класс и зависимости разный.

Если сервис уже работает и жалоба — паузы, рост памяти или медленный метод, схема запуска не объяснит проблему целиком. Для этого нужны темы «Memory Areas», «Garbage Collection», «JIT» и «Diagnostics»: они разбирают соответствующие механизмы и инструменты.

  • JDK собирает class-файл, runtime с JVM исполняет его; версия class-файла должна поддерживаться runtime.
  • Class-файл хранит байткод и символические ссылки. javap -c показывает, что реально получил исполнитель.
  • Метод работает с кадром, локальными слотами и стеком операндов; iadd в примере переполняет int по правилам JVM.
  • Загрузка, проверка и инициализация класса происходят до вызова main; на этих этапах запуск может оборваться.
  • Интерпретатор и JIT — два пути исполнения с одинаковой наблюдаемой семантикой.

На собеседовании

Чем отличаются JDK, JRE и JVM?

JVM — машина, которая загружает class-файлы и исполняет байткод. JRE — среда запуска: JVM, стандартные модули и необходимые файлы. JDK включает runtime и инструменты разработки, например javac и javap. В современных поставках Java отдельный JRE-пакет не обязателен.

Если платёжный сервис собирается в CI, а в контейнере не стартует, я сравню версии JDK при сборке и runtime в образе. Ошибка может появиться ещё до main, если class-файл слишком новый.

  • jlink собирает runtime-образ с выбранными модулями; размер меньше полного JDK, но отсутствие нужного модуля обнаружится при запуске.
  • JVM как спецификация и HotSpot как реализация — разные уровни: контракт байткода общий, JIT и GC зависят от реализации.
В контейнере только runtime без javac. Можно ли запустить PaymentMath.class?

Да, если runtime поддерживает версию class-файла и содержит нужные модули. javac нужен для компиляции, а запуск class-файла делает JVM. Для java PaymentMath.java нужен source-file launcher с компиляцией, поэтому этот сценарий не равен запуску готового class-файла.

JVM — это то же самое, что HotSpot?

Нет. JVM задаёт виртуальную машину и правила исполнения class-файлов. HotSpot — одна из реализаций JVM в OpenJDK: у неё свои JIT, GC и диагностические флаги.

Что такое байткод и почему class-файл от Java 21 не запускается на Java 17?

Байткод — инструкции JVM внутри class-файла. javac пишет вместе с ними версию формата; у Java 21 это major 65, у Java 17 — major 61. Java 17 не обязана понимать будущий формат и останавливает загрузку с UnsupportedClassVersionError.

Для сервиса, который должен работать на Java 17, я соберу его с javac --release 17 и проверю зависимости. Этот флаг ограничивает не только формат class-файла, но и доступные стандартные API.

  • -source и -target без --release могут пропустить вызов API, которого нет в старом runtime.
  • Новые class-файлы понимает новая JVM; обратное направление не работает автоматически, даже если исходный код выглядит старым.
В CI стоит javac -source 17 -target 17, а деплой на Java 17. Где риск?

Сборка на JDK 21 может сослаться на стандартный API, добавленный после Java 17. Формат class-файла будет 61, но при выполнении нужного API не окажется. Замени пару флагов на --release 17 и проверь версии сторонних JAR.

javap -verbose показывает major version 65. Какая минимальная версия Java SE нужна?

Java 21. Для сравнения, javac --release 17 создаёт major 61. Это проверено на JDK 21.0.11 на одном и том же примере PaymentMath.

Как JVM исполняет вызов метода и зачем ей стек операндов?

Для вызова создаётся кадр с локальными слотами и стеком операндов. В total(int, int) аргументы лежат в слотах 0 и 1. Инструкции iload кладут их на стек, iadd снимает оба и кладёт сумму, ireturn отдаёт её вызывающему методу.

Поэтому я могу взять javap -c и проверить, что реально исполняется. Это полезно, когда компилятор свернул константу, добавил вызов или поведение кода кажется неожиданным.

  • Символические ссылки на методы и поля хранятся в constant pool; JVM разрешает их при linking или использовании.
  • Верификатор проверяет корректность типов и переходов байткода перед исполнением; это граница для повреждённого или вручную созданного class-файла.
Что покажет javap для int fixed = 2 + 3: iadd или iconst_5?

iconst_5. Константное выражение свернул javac. У метода total(amount, fee) остаётся iadd, потому что он складывает параметры вызова.

Где лежит возвращаемое значение после ireturn?

ireturn снимает значение со стека текущего кадра и передаёт его вызывающему кадру как результат вызова. Кадр завершённого метода удаляется. Детальное расположение кадров в памяти разбирается в «Memory Areas».

Java интерпретируется или компилируется?

Сначала javac компилирует Java в байткод. Во время работы HotSpot может интерпретировать байткод и компилировать горячие методы в машинный код через JIT. Поэтому это не выбор одного из двух: оба пути работают в одном процессе.

Для короткой программы JIT может не успеть скомпилировать её методы, а для долгоживущего платёжного сервиса прогрев влияет на задержки. Я сравню поведение с -Xint только как диагностический эксперимент, потому что он заметно меняет скорость.

  • HotSpot профилирует типы и частоты; JIT может встроить вызов, а потом деоптимизировать код, если предположение о типах перестало выполняться.
  • -XX:+PrintCompilation показывает события компиляции, но не обещает фиксированное число вызовов до JIT.
В отчёте сказано: «С -Xint переполнение исчезнет, ведь JIT отключён». Верно?

Нет. Переполнение int — семантика инструкции iadd, а не оптимизация JIT. Пример печатает 5:-2147483648 и с JIT, и с -Xint. Меняется путь исполнения и скорость, не результат.

Почему не стоит мерить производительность коротким java PaymentMath?

Программа заканчивается до устойчивого прогрева, а время запуска и загрузки классов сравнимо со временем работы метода. Для оценки горячего кода нужен корректный benchmark, например JMH, с прогревом, несколькими итерациями и контролем оптимизаций.
