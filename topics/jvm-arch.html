JVM: как выполняется код

Исходник сам по себе сервер не запустит

Платёжный сервис написан на Java, а процессор выполняет машинные инструкции. Между исходником и процессором есть два перехода: компилятор создаёт байткод, затем JVM выполняет его на конкретной машине. Это позволяет собрать один набор class-файлов для разных операционных систем.

public class JvmRun {
    static long fee(long kopecks) { return kopecks * 15 / 1000; }
    public static void main(String[] args) {
        System.out.println(fee(10_000));
    }
}

Сохрани код как JvmRun.java и запусти java JvmRun.java. Команда компилирует одиночный исходный файл в памяти и запускает его; обычная сборка сначала вызывает javac JvmRun.java, а потом java JvmRun. Вывод одинаковый.

JDK включает инструменты, JVM исполняет байткод

JDK содержит компилятор javac, java, javap и диагностические инструменты. JVM — виртуальная машина, которая загружает классы, исполняет код и управляет памятью. JRE — историческое имя среды исполнения из JVM и библиотек без инструментов разработки; с Java 9 привычный отдельный дистрибутив JRE больше не является обязательной формой поставки.

В проде приложение часто запускают на урезанном runtime image, собранном jlink, но смысл не меняется: внутри есть реализация JVM и необходимые модули. Термины описывают роли, а не три последовательных процесса.

Class-файл хранит инструкции и ссылки, а не готовый машинный код

javac проверяет типы и записывает в class-файл байткод методов, константы и символические ссылки на другие классы и методы. JVM проверит формат и разрешит ссылки при загрузке и связывании. Поэтому отсутствующая библиотека может обнаружиться уже при запуске, хотя собственный исходник успешно скомпилировался.

javac JvmRun.java
javap -c JvmRun

javap -c показывает инструкции, например invokestatic для вызова fee. Это полезно, когда нужно понять, что сделал компилятор, но вывод javap — ещё не машинный код процессора.

Сначала код исполняется, горячие участки ускоряются

После загрузки класса JVM вызывает main. HotSpot сначала может интерпретировать байткод и собирать профиль: какие методы и ветви используются. Часто исполняемые участки JIT компилирует в машинный код; редкие могут так и остаться интерпретируемыми.

JIT не обещает ускорения любого метода: решение зависит от профиля и бюджета компиляции. Подробности уровней C1/C2 вынесены в отдельную тему «JIT».

JVM отвечает за исполнение, но не за всю платформу

Байткод может создать не только javac: например, Kotlin и Scala тоже используют JVM. При этом Java API предоставляет библиотеки, а JVM Specification задаёт формат class-файла и поведение инструкций. Конкретные GC и JIT — выбор реализации HotSpot, а не обещание каждой JVM.

Java всегда интерпретируется и поэтому медленная.

HotSpot сочетает интерпретацию и JIT. Реальную задержку сервиса измеряют по профилю, а не выводят из слова «виртуальная».

Если программа упирается в сеть или базу, тонкая настройка JIT не устранит ожидание I/O. Сначала измерь, где тратится время, затем выбирай инструмент диагностики.

  • javac создаёт байткод; JVM загружает и выполняет его.
  • JDK — инструменты и runtime; JRE — роль среды исполнения, а не обязательный отдельный пакет.
  • Class-файл переносим между платформами, машинный код JIT создаётся для текущего процессора.
  • Интерпретация даёт быстрый старт, JIT ускоряет горячие участки.
  • Спецификация JVM и конкретная реализация HotSpot — разные уровни описания.

На собеседовании

Чем отличаются JDK, JRE и JVM?

JDK беру для разработки: в нём есть javac, java, javap и инструменты диагностики. JVM загружает class-файлы и исполняет байткод. JRE называют набором, достаточным для запуска: JVM плюс нужные библиотеки.

Для backend-сервиса я собираю приложение JDK, а запускаю его на подходящем runtime. Отдельный пакет с названием JRE сегодня необязателен.

  • JVM Specification не предписывает конкретный GC или JIT; это решения реализации.
  • jlink может собрать runtime image только с нужными модулями.
Можно ли запустить Java без javac?

Да. Готовые class-файлы и JAR запускаются без компилятора; режим java File.java, напротив, требует компиляции исходника.

Как увидеть байткод метода?

Скомпилируй javac JvmRun.java и вызови javap -c JvmRun. Флаг -c печатает инструкции методов.

Что происходит после команды java JvmRun?

Лаунчер создаёт JVM, она находит основной класс, загружает и связывает его, инициализирует при первом активном использовании и вызывает main. По ходу выполнения она загружает другие классы и выполняет их байткод, а горячие методы может скомпилировать JIT.

Если в проде появляется NoClassDefFoundError, я сначала проверю classpath и зависимости, а не настройки GC.

  • Загрузка, linking и initialization разделены; детали переходов — в теме Class Loading.
  • Разрешение символических ссылок может происходить лениво, поэтому ошибка не обязательно возникает в момент старта.
Все классы приложения загружаются сразу?

Нет. JVM загружает классы по мере необходимости, а linking и разрешение отдельных ссылок могут откладываться.

Где появляется машинный код?

HotSpot JIT создаёт его во время работы для выбранных горячих участков. В class-файле лежит переносимый байткод.

Зачем Java байткод, если CPU его не понимает?

Байткод — стабильный промежуточный формат. Компилятор проверяет программу один раз, а JVM на конкретной платформе исполняет её и может оптимизировать под текущий процессор и профиль нагрузки.

Это удобно для сервиса, который собирается в CI и запускается на разных ОС или архитектурах. Совместимость всё равно зависит от версии class-файла и доступных API.

  • Более новая версия class-файла на старой JVM даёт UnsupportedClassVersionError.
  • Байткод не гарантирует одинаковую производительность: JIT, GC и железо различаются.
Можно ли открыть class-файл обычным редактором?

Это бинарный формат. Для структуры используй javap -v, для инструкций — javap -c.

Kotlin нужен отдельный JVM runtime?

Его компилятор тоже выпускает class-файлы для JVM. Приложению могут понадобиться библиотеки Kotlin, но механизм исполнения байткода тот же.
