JVM: How JVM Runs Code

После деплоя сервис первые секунды медленнее — так работает JVM

После каждого деплоя платёжного сервиса на графике латентности видна одна и та же картина: первые запросы идут в несколько раз дольше, а через минуту всё выравнивается. Код тот же, нагрузка та же. Меняется то, как JVM исполняет этот код.

Повторим это в миниатюре: шесть раз подряд делаем одну и ту же работу и замеряем время.

public class Warmup {
    // Комиссия 1,5 % в копейках — горячий метод платёжного сервиса
    static long fee(long amount) { return amount * 15 / 1000; }

    public static void main(String[] args) {
        for (int round = 1; round <= 6; round++) {
            long start = System.nanoTime();
            long total = 0;
            // одна и та же работа в каждом раунде: 100 000 вызовов fee
            for (long amount = 0; amount < 100_000; amount++) {
                total += fee(amount);
            }
            long micros = (System.nanoTime() - start) / 1_000;
            System.out.println("раунд " + round + ": " + micros + " мкс");
        }
    }
}

Время зависит от машины, поэтому ниже — реальный запуск на JDK 21, а не вывод для предсказания.

$ java -cp out Warmup

раунд 2: 633 мкс
раунд 3: 175 мкс          # с третьего раунда в 5 раз быстрее
раунд 4: 164 мкс
раунд 5: 178 мкс
раунд 6: 178 мкс

$ java -Xint -cp out Warmup     # -Xint: только интерпретатор, JIT выключен
раунд 1: 1547 мкс
раунд 2: 1542 мкс         # ускорения нет вообще
раунд 3: 1522 мкс

Работа одинаковая, а третий раунд в пять раз быстрее первого. С флагом -Xint ускорения нет, и каждый раунд в восемь раз медленнее прогретого. Значит, по ходу работы JVM что-то делает с кодом. Чтобы понять что, пройдём весь путь: от исходника до машинных инструкций, которые исполняет процессор.

JDK, JRE и JVM вложены друг в друга

Три аббревиатуры путают постоянно, хотя отношение между ними простое: каждая следующая — часть предыдущей.

JVM — виртуальная машина: загружает классы, исполняет байткод, управляет памятью и потоками. JRE — среда запуска: JVM плюс стандартная библиотека, то есть всё, что нужно, чтобы запустить готовое приложение. JDK — JRE плюс инструменты разработчика: компилятор javac, jar, javap, диагностика jcmd и jfr, сборщик образов jlink.

Отдельный дистрибутив JRE Oracle перестала выпускать с Java 11, но слово осталось. Другие поставщики, например Eclipse Temurin, собирают JRE-сборки сами, а jlink умеет собрать runtime только из нужных модулей. На практике выбор такой: в CI нужен JDK, чтобы компилировать, а в образ для прода достаточно runtime. Он меньше, и в нём меньше лишнего. Но в минимальном образе может не оказаться jcmd, и снять thread dump при аварии будет нечем. Это стоит решить заранее.

JVM — это ещё и спецификация. JVMS описывает формат class-файла и поведение инструкций, а реализаций несколько: HotSpot из OpenJDK, Eclipse OpenJ9, GraalVM. Почти всегда в проде работает HotSpot, и всё, что дальше говорится про JIT и GC, относится к нему.

javac превращает исходник в байткод, а не в машинный код

javac проверяет типы и пишет class-файл: версию формата, пул констант и байткод каждого метода. Байткод — это инструкции не для процессора, а для JVM. Поэтому один class-файл запускается на Linux, macOS и Windows, на x86 и ARM: машинный код под конкретный процессор делает уже JVM на месте.

Class-файл — обычные байты, и программа может прочитать собственный. Запускай через javac и java -cp out.

public class FeeCalc {
    static long fee(long amount) {
        return amount * 15 / 1000;
    }

    public static void main(String[] args) throws Exception {
        // Читаем собственный class-файл как обычные байты
        byte[] bytes = FeeCalc.class.getResourceAsStream("FeeCalc.class").readAllBytes();
        // Первые 4 байта у любого class-файла одинаковые — «магическое число»
        System.out.printf("magic: %02X%02X%02X%02X%n", bytes[0], bytes[1], bytes[2], bytes[3]);
        // Байты 6–7 — major version: по ней JVM решает, сможет ли прочитать файл
        int major = ((bytes[6] & 0xFF) << 8) | (bytes[7] & 0xFF);
        System.out.println("major version: " + major);
        System.out.println("fee: " + fee(250_000));
    }
}
magic: CAFEBABE
major version: 65
fee: 3750

Версия 65 — это Java 21, у каждой версии Java своя: 61 у Java 17, 66 у Java 22. Более старая JVM не читает файл новее себя и падает ещё до main. Если поднять в файле версию до 66 и запустить на Java 21, получится вот что:

Error: LinkageError occurred while loading main class FeeCalc
	java.lang.UnsupportedClassVersionError: FeeCalc has been compiled by a more recent version
	of the Java Runtime (class file version 66.0), this version of the Java Runtime only
	recognizes class file versions up to 65.0

Это частая авария после деплоя: сервис собрали на JDK 21, а в образе осталась Java 17. Если код должен работать на старой Java, собирай с флагом javac --release 17: он выставит версию 61 и не даст использовать API, которого в Java 17 ещё нет.

Что именно лежит внутри, покажет javap -c. Вот байткод метода fee:

Числа слева — смещение инструкции в байтах, #7 — номер записи в пуле констант. Ни одной переменной с именем, ни одного регистра процессора: только стек и слоты. Как это работает, разберём на следующем шаге.

Под капотом: что ещё хранит class-файл

После magic и версии идёт пул констант: строки, числа, имена классов, сигнатуры методов. Инструкции ссылаются на него номерами, поэтому в байткоде нет адресов памяти, только символические имена вроде java/lang/String. JVM превратит их в реальные ссылки при связывании класса. Дальше — флаги доступа, суперкласс, интерфейсы, поля и методы. У каждого метода есть атрибут Code: байткод, размер стека операндов, число локальных слотов и таблица обработчиков исключений. Формат описан в JVMS, глава 4, а javap -v покажет всё это для любого класса.

JVM — стековая машина: инструкции берут и кладут значения на стек

Каждый вызов метода получает в стеке потока свой кадр (frame). В кадре два хранилища: массив локальных переменных, куда при вызове кладут аргументы, и стек операндов, на котором идут все вычисления. Ещё у каждого потока есть pc-регистр — номер текущей инструкции. Пролистай, как выполняется fee(250_000).

Стековая модель — причина, по которой байткод получился компактным и переносимым: инструкциям не нужно знать, сколько регистров у процессора. Стоимость — лишние перекладывания. Интерпретатор честно выполняет каждое, отсюда 1500 мкс на раунд с -Xint. JIT же видит всю цепочку целиком и превращает её в пару машинных инструкций на регистрах.

У каждого потока свой стек кадров, поэтому два потока, одновременно вызвавшие fee, не мешают друг другу: у каждого своя копия amount и свой стек операндов. Глубина стека ограничена флагом -Xss, и слишком глубокая рекурсия кончается StackOverflowError. Это разбирается в теме Memory Areas.

Внутри JVM три подсистемы: загрузка, память и исполнение

Теперь можно собрать картину целиком. Любое описание архитектуры JVM, в том числе на собеседовании, сводится к трём частям и связям между ними.

  • Загрузка классов. Загрузчики находят class-файлы, проверяют и связывают их, кладут описания классов в Metaspace. Подробно — в теме Class Loading.
  • Области памяти. Heap для объектов, общий для всех потоков. Metaspace для классов и байткода. Стек и pc-регистр у каждого потока свои. Code cache для машинного кода от JIT. Подробно — в Memory Areas.
  • Исполнение. Интерпретатор выполняет байткод инструкция за инструкцией. JIT-компиляторы превращают горячие методы в машинный код. Сборщик мусора освобождает heap от недостижимых объектов. Через JNI JVM вызывает native-код: системные вызовы, драйверы, библиотеки на C.

Теперь понятен замер из первого шага. HotSpot стартует на интерпретаторе, считает вызовы и собирает профиль. Когда метод становится горячим, его компилирует быстрый C1, а затем оптимизирующий C2. Это видно своими глазами:

$ java -Xint -version
OpenJDK 64-Bit Server VM (build 21.0.11…, interpreted mode, sharing)

$ java -XX:+PrintCompilation -cp out Warmup | grep -E "Warmup|раунд"
16    5       3       Warmup::fee (10 bytes)                   # fee скомпилирован C1 (уровень 3)
16    6       4       Warmup::fee (10 bytes)                   # и тут же C2 (уровень 4)
16    5       3       Warmup::fee (10 bytes)   made not entrant  # старая версия больше не используется

Первые раунды платят за интерпретацию и за саму компиляцию. После неё цикл исполняет машинный код, и время падает в пять раз. Уровни компиляции, OSR и деоптимизация подробно разобраны в теме JIT.

Java интерпретируемая, поэтому медленнее C++.

Горячий код в HotSpot исполняется как машинный, скомпилированный под этот процессор и под реальный профиль вызовов. Медленными остаются старт и прогрев, а не установившаяся работа.

Процесс живёт, пока работает хотя бы один не-daemon поток

Команда java -cp out FeeCalc запускает лаунчер. Он создаёт JVM и её служебные потоки: компиляторы, сборщик мусора. Затем загружает, связывает и инициализирует главный класс и вызывает main в потоке main. Если класс не нашёлся или его версия слишком новая, дело до main не дойдёт.

Самое интересное — как процесс заканчивается. Выход из main не завершает JVM. Она ждёт, пока закончатся все не-daemon потоки. Daemon-потоки процесс не держат: их просто обрывают.

public class Shutdown {
    public static void main(String[] args) {
        // Хук выполнится, когда JVM начнёт завершаться
        Runtime.getRuntime().addShutdownHook(
                new Thread(() -> System.out.println("hook: закрываем пул соединений")));

        Thread worker = new Thread(() -> {
            pause(300);                                      // проводим платёж
            System.out.println("worker: платёж проведён");
        });
        worker.setDaemon(args.length > 0);                   // с аргументом поток станет daemon
        worker.start();

        System.out.println("main: вышел из main");           // main закончился, а процесс?
    }

    static void pause(long ms) {
        try { Thread.sleep(ms); } catch (InterruptedException e) { Thread.currentThread().interrupt(); }
    }
}
main: вышел из main
worker: платёж проведён
hook: закрываем пул соединений

Процесс дождался платежа и только потом выполнил хук. А если сделать поток daemon, платёж оборвётся на полуслове:

$ java -cp out Shutdown daemon
main: вышел из main
hook: закрываем пул соединений       # worker оборван: daemon-поток процесс не держит

Shutdown hook — поток, который JVM запускает при штатном завершении. На нём держится graceful shutdown: Spring закрывает контекст из такого хука, бины получают @PreDestroy, пулы соединений закрываются. Но хуки срабатывают не всегда.

Проверено на JDK 21: на SIGTERM хук напечатал сообщение, на SIGKILL — нет. Для сервиса это важно. Kubernetes сначала шлёт SIGTERM и ждёт, по умолчанию 30 секунд, а потом добивает SIGKILL. Если хуки не успели дописать данные или закрыть транзакции, они просто не выполнятся.

Хук должен быть коротким и не вызывать System.exit. Вызов exit во время работы хуков по javadoc блокируется навсегда, и процесс зависнет до SIGKILL.

Где кончается эта модель? JIT даёт лучшую установившуюся скорость, но платит медленным стартом и прогревом. Если важнее мгновенный старт — функции, короткоживущие задачи, CLI — код компилируют в машинный заранее: GraalVM Native Image собирает один исполняемый файл без JVM. Цена — рефлексию и динамическую загрузку классов нужно описывать заранее, а пиковая скорость обычно ниже, чем у прогретого C2.

  • JDK = инструменты + JRE, JRE = библиотека + JVM. В CI нужен JDK, в проде достаточно runtime, но подумай, чем снимать дампы при аварии.
  • javac пишет переносимый байткод. Major version в class-файле должна поддерживаться runtime, иначе UnsupportedClassVersionError до main.
  • JVM — стековая машина: у каждого вызова кадр с локальными слотами и стеком операндов, у каждого потока свой стек и pc.
  • HotSpot работает в mixed mode: интерпретатор на старте, C1 и C2 для горячего кода. Отсюда прогрев после деплоя.
  • JVM завершается, когда кончились не-daemon потоки, по System.exit или SIGTERM. Хуки выполняются только при штатном завершении, SIGKILL их обходит.

На собеседовании

Чем отличаются JDK, JRE и JVM?

Они вложены друг в друга. JVM — виртуальная машина, которая загружает классы, исполняет байткод, управляет памятью и потоками. JRE — JVM плюс стандартная библиотека, всё, что нужно для запуска готового приложения. JDK — JRE плюс инструменты разработки: javac, jar, javap, jcmd, jlink.

На практике в CI я собираю сервис JDK, а в образ для прода кладу только runtime: он меньше и безопаснее. При этом проверяю, что в образе есть чем снять thread dump при аварии.

  • Отдельный JRE Oracle не выпускает с Java 11. Runtime берут в сборках поставщиков или собирают jlink только из нужных модулей.
  • JVM — спецификация (JVMS), HotSpot — её реализация в OpenJDK. Есть и другие: OpenJ9, GraalVM. JIT и GC — детали реализации.
Dockerfile сервиса собирается на образе с полным JDK и так уходит в прод. Что предложишь?

Многоступенчатую сборку: компилировать в образе с JDK, а запускать в образе с runtime или собранном через jlink. Образ станет меньше, в нём не будет компилятора и лишних утилит. Отдельно реши, как снимать диагностику: добавить модуль jdk.jcmd в jlink или держать отладочный образ.

JVM и HotSpot — одно и то же?

Нет. JVM — это спецификация: формат class-файла и поведение инструкций. HotSpot — самая распространённая её реализация, со своими JIT-компиляторами, сборщиками мусора и флагами.

Что такое байткод и почему Java кроссплатформенная?

Байткод — набор инструкций для JVM, который javac записывает в class-файл. Он не зависит от процессора и ОС: машинный код под конкретную платформу делает JVM, которая там установлена. Поэтому один JAR запускается на Linux и macOS, на x86 и ARM — «write once, run anywhere».

Ограничение — версия. В class-файле записан major version, у Java 21 это 65. Старая JVM не читает файлы новее себя и падает с UnsupportedClassVersionError до вызова main.

  • Переносимость заканчивается на native-коде: JNI-библиотеки и драйверы собираются под платформу.
  • Байткод стековый, поэтому компактный и не зависит от числа регистров. Скорость дают не инструкции, а JIT.
javap -v показывает major version: 65. На какой Java можно запустить этот класс?

На Java 21 и новее. Java 17 понимает версии до 61 и откажется с UnsupportedClassVersionError.

Сервис собирают на JDK 21 с флагами -source 17 -target 17, а запускают на Java 17. Где риск?

Эти флаги задают синтаксис и версию файла, но не проверяют API: код может вызвать метод, которого в Java 17 нет, и упасть уже в рантайме с NoSuchMethodError. javac даже предупреждает: «system modules path not set in conjunction with -source 17». Нужен --release 17: он собирает против API Java 17.

Во что компилируется склейка строк "fee: " + amount?

С Java 9 — в инструкцию invokedynamic с методом makeConcatWithConstants. Стратегию склейки JVM выбирает при первом вызове, а не javac, поэтому её можно улучшать без перекомпиляции кода. До Java 9 здесь был StringBuilder.

Из каких частей состоит JVM?

Из трёх подсистем. Загрузчики классов находят class-файлы, проверяют их и кладут описания классов в память. Области памяти: heap для объектов, Metaspace для классов, стек и pc у каждого потока, code cache для скомпилированного кода. Исполнение: интерпретатор, JIT-компиляторы C1 и C2 и сборщик мусора. Native-код вызывается через JNI.

Эта карта помогает в диагностике. OutOfMemoryError: Metaspace — вопрос к загрузке классов, Java heap space — к объектам, StackOverflowError — к стеку потока.

Поток вызвал fee(250_000). Что появилось в памяти и где?

В стеке этого потока — новый кадр с локальным слотом amount и пустым стеком операндов, pc указывает на первую инструкцию. Байткод метода лежит в Metaspace, общий для всех потоков. В heap ничего не создано: метод работает только с примитивами.

Зачем каждому потоку свой pc-регистр?

Потоки исполняют разные места кода одновременно. Каждому нужно помнить свою текущую инструкцию, чтобы продолжить с неё после переключения.

Java компилируемая или интерпретируемая?

И то и другое. Сначала javac компилирует исходник в байткод. При запуске HotSpot исполняет байткод интерпретатором и собирает профиль, а горячие методы компилирует JIT в машинный код: сначала быстрый C1, потом оптимизирующий C2. java -version так и пишет: mixed mode.

Для сервиса отсюда прогрев: первые запросы после деплоя медленнее, пока код не скомпилирован. На замере в уроке прогретый цикл работал в пять раз быстрее первого прохода и в восемь раз быстрее чистого интерпретатора.

  • JIT компилирует под реальный профиль: встраивает вызовы, убирает проверки. Если профиль меняется, код деоптимизируют и компилируют заново.
  • Прогрев сглаживают: гоняют тёплые запросы до того, как readiness-проба пустит трафик. AppCDS ускоряет саму загрузку классов на старте. Для мгновенного старта есть AOT: GraalVM Native Image.
Коллега замерил метод одним вызовом сразу после старта и сделал вывод, что он медленный. Что не так?

Замер попал на интерпретатор и компиляцию, а не на установившуюся работу. Нужны прогрев и много итераций, лучше JMH: он прогревает код, повторяет измерения и не даёт JIT выбросить результат как неиспользуемый.

Что покажет java -Xint -version и зачем этот флаг?

interpreted mode: JIT выключен, весь код исполняет интерпретатор. Флаг полезен для экспериментов и сравнения, но не для прода — в замере урока он замедлил цикл в восемь раз.

Когда завершается JVM и что такое shutdown hook?

JVM завершается, когда закончились все не-daemon потоки, при System.exit или по сигналу вроде SIGTERM. Выход из main процесс не завершает, если работают другие не-daemon потоки. Daemon-потоки процесс не держат и обрываются.

Shutdown hook — поток, который JVM запускает при штатном завершении. На нём держится graceful shutdown: Spring закрывает контекст, бины получают @PreDestroy. Но при SIGKILL хуки не выполняются, поэтому в Kubernetes важно уложиться в terminationGracePeriodSeconds.

  • Порядок хуков не гарантирован, они работают параллельно. Хук не должен вызывать System.exit: такой вызов блокируется навсегда.
  • Фоновые задачи на daemon-потоках теряют работу при остановке. Для важной работы нужен штатный shutdown пула с ожиданием.
Что выведет пример Shutdown из урока, если запустить его с аргументом daemon?

main: вышел из main, затем hook: закрываем пул соединений. Строка про платёж не появится: daemon-поток не держит процесс, и его оборвали.

Под в Kubernetes удаляют. Что получит Java-процесс?

Сначала SIGTERM: JVM запустит хуки, Spring корректно остановится. Если процесс не завершился за terminationGracePeriodSeconds, по умолчанию 30 секунд, придёт SIGKILL, и оставшееся не выполнится.
