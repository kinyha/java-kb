JVM: Diagnostics

Сервис завис, CPU на нуле — ответ в дампе потоков

Платёжный сервис перестал отвечать на переводы. Процесс жив, CPU почти ноль, в логах тишина. Перезапуск поможет на час, но причину уничтожит. Правильный первый шаг — снять дамп потоков: одна команда, процесс не останавливается. Вот упрощённый код переводов:

import java.util.concurrent.*;

public class Stuck {
    static class Account {
        final String id;
        long balance = 1_000;
        Account(String id) { this.id = id; }
    }

    // перевод блокирует счета в порядке «откуда, куда»
    static void transfer(Account from, Account to, long amount) throws InterruptedException {
        synchronized (from) {
            Thread.sleep(50);                                    // успеваем получить встречный перевод
            synchronized (to) {
                from.balance -= amount;
                to.balance += amount;
            }
        }
    }

    public static void main(String[] args) throws Exception {
        Account a = new Account("A"), b = new Account("B");
        new Thread(() -> { try { transfer(a, b, 10); } catch (InterruptedException e) { } }, "transfer-1").start();
        new Thread(() -> { try { transfer(b, a, 20); } catch (InterruptedException e) { } }, "transfer-2").start();

        BlockingQueue<String> queue = new LinkedBlockingQueue<>();
        new Thread(() -> { try { queue.take(); } catch (InterruptedException e) { } }, "consumer").start();

        Thread.sleep(Long.MAX_VALUE);
    }
}

Диагноз готов без отладчика и без гипотез: transfer-1 держит счёт A и ждёт B, transfer-2 — наоборот. Строка 15 — внутренний synchronized (to). Лечится единым порядком блокировок, например по id счёта.

Эта тема — про такие инструменты: jcmd и дампы потоков, Java Flight Recorder, статистика GC на лету, гистограммы классов и дампы heap. Главный сценарий в конце — как найти, кто держит утекающую память.

Attach работает только от того же пользователя ОС и через общий временный каталог. В Kubernetes jcmd запускают внутри контейнера приложения (kubectl exec), от пользователя, под которым работает JVM. Если в образе только JRE без jcmd, диагностику заранее закладывают в образ или в debug-контейнер. Флаг -XX:+DisableAttachMechanism отключает attach целиком.

Горячий поток: два дампа и разница cpu=

Другой частый случай — CPU на 100%. Поток, который его ест, находят по полю cpu=: оно растёт у горячего потока между двумя дампами. Модель — пул обработчиков, один из которых получил большой запрос и ушёл в квадратичный алгоритм:

import java.util.*;
import java.util.concurrent.*;

public class Busy {
    // убрать повторы, сохранив порядок; contains у ArrayList — полный проход по списку
    static List<String> dedupe(List<String> ids) {
        List<String> result = new ArrayList<>();
        for (String id : ids)
            if (!result.contains(id)) result.add(id);
        return result;
    }

    public static void main(String[] args) throws Exception {
        ExecutorService pool = Executors.newFixedThreadPool(4, r -> new Thread(r, "http-exec-" + UUID.randomUUID().toString().substring(0, 4)));
        List<String> small = List.of("p1", "p2", "p1");
        List<String> big = new ArrayList<>();
        for (int i = 0; i < 300_000; i++) big.add("payment-" + i);   // один «большой» запрос
        for (int i = 0; i < 3; i++) pool.submit(() -> dedupe(small));
        pool.submit(() -> dedupe(big));
        Thread.sleep(Long.MAX_VALUE);
    }
}

За 5 секунд у потока f0c7 прибавилось 5 секунд CPU — он занят на 100%. У остальных ноль. Стек показывает место: contains внутри dedupe. Отсюда правило: снимают несколько дампов с интервалом в несколько секунд. Один дамп — мгновенный снимок, и по нему не отличить «застрял» от «случайно оказался здесь». На Linux то же самое делают через top -H -p <pid>: колонка PID там — это nid потока.

Виртуальные потоки Java 21 в Thread.print не попадают — их могут быть миллионы. Для них есть jcmd <pid> Thread.dump_to_file -format=json threads.json: он пишет все потоки, сгруппированные по контейнерам — пулам и executor'ам.

JFR записывает, что делала JVM, почти бесплатно

Дамп потоков — снимок одного момента. Java Flight Recorder — запись во времени: сэмплы стеков, выделения памяти, паузы GC, блокировки, ввод-вывод, исключения. Он встроен в JVM и по данным Oracle с настройками по умолчанию стоит около 1% производительности. Поэтому его можно держать включённым в проде постоянно, в кольцевом буфере.

# с самого старта, в кольцевом буфере: последние 6 часов или 500 МБ
java -XX:StartFlightRecording=maxage=6h,maxsize=500m,filename=/dumps/app.jfr,dumponexit=true -jar app.jar

# на живом процессе: записать 60 секунд с более подробными настройками
jcmd <pid> JFR.start name=cpu settings=profile duration=60s filename=/tmp/cpu.jfr

С Java 21 файл можно читать прямо в терминале: у утилиты jfr есть команда view с готовыми отчётами. Запись пяти секунд работы программы Busy:

$ jcmd Busy JFR.start name=cpu duration=5s filename=busy.jfr
$ jfr view hot-methods busy.jfr

                      Java Methods that Executes the Most

Method                                                          Samples Percent
--------------------------------------------------------------- ------- -------
java.util.ArrayList.indexOfRange(Object, int, int)                  198 100.00%

Все сэмплы CPU пришлись на один метод. Кроме hot-methods, в JDK 21 есть gc-pauses, allocation-by-site, contention-by-site (где потоки ждут блокировок), exception-by-site, container-cpu-throttling и десятки других. Полный список выводит jfr view без аргументов. Для графического анализа тот же файл открывают в JDK Mission Control.

Главное преимущество JFR перед профилировщиком, который подключают по запросу: запись уже шла, когда случилась проблема. После инцидента сохраняют буфер через jcmd <pid> JFR.dump filename=incident.jfr и смотрят, что было за минуты до него.

Утечку ищут по шагам: подтвердить, найти класс, найти держателя

Возьмём сервис с утечкой из темы GC Logs & Tuning. Каждый десятый запрос кладёт 4 КБ в статический список AUDIT, из которого ничего не удаляют. Запускаем с heap 2 ГБ и включённым JFR и проходим путь, как в проде.

1. Подтвердить. Лог GC показывает рост нижней границы, а на лету то же видно через jstat — по строке раз в 2 секунды:

Дамп heap при OOM настраивают заранее, и он содержит все данные приложения

Самый ценный дамп — снятый в момент OutOfMemoryError: в нём ровно то, что заполнило heap. Его нельзя снять потом, поэтому флаги ставят при старте:

$ java -Xmx512m -XX:+HeapDumpOnOutOfMemoryError -XX:HeapDumpPath=/dumps Service 150 leak 60
java.lang.OutOfMemoryError: Java heap space
Dumping heap to /dumps/java_pid5683.hprof ...
Heap dump file created [601187940 bytes in 0.178 secs]

Файл получился 601 МБ при heap 512 МБ: формат hprof хранит у каждого объекта идентификаторы и ссылки, поэтому миллионы мелких объектов делают его больше самого heap. Места на диске под дамп нужно не меньше -Xmx, а лучше с запасом.

Снятие дампа вручную на живом процессе:

$ jcmd 5688 GC.heap_info
 garbage-first heap   total 888832K, used 577010K [0x0000007000800000, 0x0000007040800000)
$ jcmd 5688 GC.heap_dump /dumps/live.hprof
Heap dump file created [221555774 bytes in 0.095 secs]

Занято было 577 МБ, а в дампе 221 МБ: GC.heap_dump по умолчанию сначала делает полную сборку и пишет только живые объекты. Флаг -all пишет всё, включая мусор. Иногда это нужно, например чтобы увидеть, что создавалось в больших количествах.

  • Пауза. На время записи JVM стоит целиком. Здесь это доли секунды на быстром диске. На heap в десятки гигабайт — секунды и больше, и балансировщик может снять под с трафика. Поэтому дамп снимают с пода, выведенного из балансировки, или с реплики.
  • Данные. В дампе все строки из памяти: токены, пароли из конфигурации, персональные данные клиентов. Обращаются с ним как с базой данных прода — не отправляют в общий чат и не оставляют на ноутбуке.
  • Контейнер. HeapDumpPath должен указывать на volume, который переживёт перезапуск контейнера. Иначе дамп исчезнет вместе с ним.

Что делать процессу после OOM? Состояние приложения после OutOfMemoryError непредсказуемо: ошибка могла вылететь в любом потоке посреди любой операции. Флаг -XX:+ExitOnOutOfMemoryError завершает JVM сразу после первой OOM (и после записи дампа), чтобы оркестратор перезапустил под. Это лучше, чем полуживой процесс, который отвечает ошибками.

Если сервис падает с OutOfMemoryError, нужно увеличить -Xmx.

Сначала нужно понять, что заполнило heap. При утечке больший heap только отложит падение. Дамп при OOM, гистограмма или OldObjectSample в JFR покажут, кто держит память. Увеличивают heap, когда живые данные законно выросли — например, стало больше клиентов в кеше.

  • jcmd — главный инструмент: дамп потоков, гистограмма, дамп heap, JFR, флаги, логи на живом процессе. Работает от того же пользователя внутри контейнера.
  • Дамп потоков показывает состояния, блокировки и CPU каждого потока, а deadlock на мониторах JVM находит сама. Снимают несколько дампов с интервалом; горячий поток виден по росту cpu=.
  • JFR пишет события почти бесплатно и может работать в проде постоянно. jfr view в JDK 21 даёт готовые отчёты: hot-methods, gc-pauses, allocation-by-site.
  • Утечку ищут так: подтвердить по логу GC и jstat, найти растущий класс по двум гистограммам, найти держателя через OldObjectSample или dominator tree в дампе.
  • Retained size — сколько освободится без объекта; dominator tree сортирует по нему и показывает держателя.
  • HeapDumpOnOutOfMemoryError и HeapDumpPath ставят заранее. Дамп — пауза, файл размером с heap и все данные приложения.

На собеседовании

Сервис завис и не отвечает. Что будешь делать?

До перезапуска снимаю несколько дампов потоков с интервалом в несколько секунд: jcmd <pid> Thread.print или jstack. Смотрю, где стоят потоки обработки запросов. Если в конце дампа Found one Java-level deadlock, JVM уже нашла взаимную блокировку. Если потоки в BLOCKED на одном мониторе — ищу, кто его держит, по строке - locked. Если в WAITING на пуле соединений или внешнем вызове — проблема снаружи: база, HTTP-клиент без таймаута.

Параллельно смотрю лог GC: процесс может «висеть» в череде full GC перед OOM.

  • Для ReentrantLock владельца показывает только Thread.print -l.
  • Виртуальные потоки видны только в Thread.dump_to_file -format=json.
  • Если CPU высокий — сравниваю cpu= у потоков в двух дампах или смотрю top -H: там PID потока совпадает с nid в дампе.
В дампе: поток A — «waiting to lock <0x…6010>», «locked <0x…5ff8>», поток B — наоборот. Что это и как исправить?

Взаимная блокировка: каждый держит монитор, который ждёт другой. Так бывает, когда потоки захватывают одни и те же замки в разном порядке, например переводы A→B и B→A. Исправление — единый порядок захвата, например по id счёта, или tryLock с таймаутом.

Как найти утечку памяти в Java-приложении?

Сначала подтверждаю утечку: в логе GC нижняя граница занятости после смешанных или полных сборок растёт от цикла к циклу. На лету это видно через jstat -gcutil. Потом снимаю две гистограммы классов с интервалом (jcmd <pid> GC.class_histogram) и смотрю, какой класс растёт. Чтобы найти держателя, снимаю дамп heap и открываю в MAT: dominator tree по retained size показывает, какой объект удерживает больше всего памяти.

В проде заранее включаю -XX:+HeapDumpOnOutOfMemoryError с HeapDumpPath на постоянный volume.

  • JFR с path-to-gc-roots=true пишет события OldObjectSample с цепочкой ссылок до корня и стеком создания — часто этого хватает без дампа.
  • HeapDumpOnOutOfMemoryError — manageable-флаг, его можно включить на живом процессе через jcmd VM.set_flag.
  • Дамп останавливает JVM и содержит все данные приложения, включая секреты и персональные данные.
Чем retained size отличается от shallow size?

Shallow — собственный размер объекта: заголовок и поля. Retained — сколько освободится, если объект станет недостижим: он сам и всё, до чего можно дойти только через него. У ArrayList из урока shallow 24 байта, а retained около 504 МБ. Утечку ищут по retained.

В двух гистограммах с интервалом 10 с растёт только [B: 393 → 600 МБ. Что это значит и что дальше?

[B — это byte[]. Растут байтовые массивы, остальные классы стабильны. Но byte[] лежат внутри строк, буферов и кешей, поэтому гистограмма не называет держателя. Дальше — OldObjectSample в JFR или дамп heap и dominator tree.

Что такое JFR и когда его использовать?

Java Flight Recorder — встроенный в JVM механизм записи событий: сэмплы стеков для профилирования CPU, выделения памяти, паузы GC, блокировки, ввод-вывод, исключения. С настройками по умолчанию стоит около 1%, поэтому его держат включённым в проде в кольцевом буфере и сохраняют при инциденте через jcmd JFR.dump. Запускается флагом -XX:StartFlightRecording или через jcmd JFR.start. Смотрят в JDK Mission Control или, с Java 21, через jfr view.

Чем JFR лучше подключения профилировщика после жалобы?

Запись уже шла, когда случилась проблема: видно, что происходило за минуты до инцидента. Профилировщик, подключённый потом, увидит только то, что происходит сейчас, — а проблема к этому моменту могла пройти.

Как снять дамп heap и чем это опасно?

Автоматически при OOM — флагами -XX:+HeapDumpOnOutOfMemoryError -XX:HeapDumpPath=.... Вручную — jcmd <pid> GC.heap_dump file.hprof или jmap -dump:live,format=b,file=.... По умолчанию перед записью выполняется полная сборка, и в файл идут только живые объекты.

Опасности: JVM стоит на всё время записи; файл бывает больше самого heap; в нём все данные из памяти, включая пароли и персональные данные.

В манифесте пода: -XX:+HeapDumpOnOutOfMemoryError -XX:HeapDumpPath=/tmp, emptyDir не подключён. Что не так?

/tmp внутри контейнера исчезнет при его перезапуске после OOM, и дамп пропадёт. Нужен volume, который переживёт перезапуск, и места на нём не меньше -Xmx с запасом. Ещё стоит добавить -XX:+ExitOnOutOfMemoryError, чтобы после дампа процесс сразу завершился и под перезапустился.
