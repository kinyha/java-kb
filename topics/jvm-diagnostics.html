JVM: диагностика

У сервиса вырос p99: сначала собери свидетельства

Платежи начали отвечать медленно. Перезапуск освободит память и уничтожит часть следов, но не объяснит причину. Сначала уточни симптом: CPU занят, потоки ждут, heap растёт или паузы GC совпадают с p99. У каждого случая свой снимок.

JDK даёт jcmd для команд работающей JVM, JFR для временной шкалы событий и GC-логи для сборки мусора. Снимки помогают сформулировать гипотезу, а не заменяют сравнение с нагрузкой и кодом.

Thread dump показывает, где остановились потоки

При зависшем запросе несколько раз сними стеки потоков через jcmd <pid> Thread.print -l. Один снимок может попасть на нормальное ожидание; повторяющийся кадр и состояние важнее одиночной строки. BLOCKED указывает на монитор, WAITING бывает нормальным ожиданием очереди, а RUNNABLE не всегда значит работу CPU.

jcmd -l
jcmd <pid> Thread.print -l

Если поток платежа ждёт соединение БД, исправление в пуле или запросе, а не в GC. При подозрении на deadlock ищи цикл владельцев и ожидающих блокировок в дампе.

Heap dump отвечает, кто удерживает память

Для роста heap сначала сравни live set после сборок и histogram классов. Если растёт число byte[], это ещё не доказательство утечки: нужно найти путь удержания. Heap dump сохраняет объекты и ссылки; в анализаторе смотри dominator tree и путь от подозрительного объекта к GC root.

import java.util.ArrayList;
import java.util.List;
public class DiagDemo {
    static final List<byte[]> retained = new ArrayList<>();
    public static void main(String[] args) throws InterruptedException {
        for (int i = 0; i < 3; i++) retained.add(new byte[1024 * 1024]);
        System.out.println("ready");
        Thread.sleep(30_000);
    }
}
ready
jcmd <pid> GC.class_histogram
jcmd <pid> GC.heap_dump /tmp/payments.hprof

В примере static-список удерживает три массива примерно по мегабайту. Dump может содержать персональные данные платежей и занимать много диска; команда способна вызвать тяжёлую работу JVM. Сохраняй его только в защищённом месте и планируй влияние на продакшн.

JFR и GC-лог связывают задержку с событием

JFR записывает события с временем: CPU, allocation, блокировки, I/O и GC. Для короткого исследования можно запустить запись на 60 секунд, затем открыть файл в JDK Mission Control или посмотреть сводку через jfr summary. Профиль profile подробнее обычного default и дороже по накладным расходам.

jcmd <pid> JFR.start name=incident settings=profile duration=60s filename=/tmp/incident.jfr
jfr summary /tmp/incident.jfr
java -Xlog:gc* -jar payments.jar

GC-лог показывает тип и длительность сборок. Сопоставь время длинной паузы с p99 запроса; если совпадения нет, ищи другую причину. В идеале GC-лог включают при старте сервиса, а JFR запускают для нужного окна наблюдения.

Команда диагностики тоже расходует ресурсы

jcmd обычно требует того же пользователя ОС, что запустил JVM; в контейнере важны PID namespace и доступ к процессу. Histogram и heap dump могут остановить потоки или потребовать заметный диск, поэтому на нагруженном сервисе выбирай момент и снимай минимально нужные данные.

Если растёт память процесса, а heap стабилен, проверь native-области. Native Memory Tracking включают при старте: -XX:NativeMemoryTracking=summary, затем смотрят jcmd <pid> VM.native_memory summary. NMT не показывает выделения стороннего native-кода.

  • Thread dump помогает разбирать ожидания, блокировки и deadlock; полезны несколько снимков.
  • Histogram показывает распределение классов, heap dump — цепочки удержания.
  • JFR и GC-логи дают время событий для сравнения с p99.
  • Dump дорог и может содержать данные пользователя; учитывай ресурсы и доступ.
  • Стабильный heap при росте RSS переводит расследование к native-памяти и лимитам контейнера.

На собеседовании

Как разберёшь внезапный рост p99 у Java-сервиса?

Сопоставлю задержки запросов с CPU, GC и числом ожидающих потоков. Если запросы зависают, сниму несколько thread dump; если есть подозрение на паузы — посмотрю GC-лог и JFR за тот же интервал.

Например, поток может ждать соединение из пула БД, пока GC-паузы короткие. Тогда настройка сборщика не решит проблему.

  • Один thread dump — снимок, а не история; повторение и JFR помогают увидеть длительность ожидания.
  • В контейнере команда jcmd -l может не увидеть процесс в другом PID namespace.
RUNNABLE означает 100% CPU?

Нет. Состояние Java-потока не всегда отражает состояние ОС; он может находиться в native I/O. Сопоставляй с CPU-профилем.

Как найти deadlock?

В thread dump ищи цикл: поток A держит монитор, который ждёт B, а B ждёт монитор A. Несколько снимков помогают подтвердить устойчивость.

Как искать утечку памяти в JVM?

Сначала убеждаюсь, что после GC растёт live set при сопоставимой нагрузке. Histogram покажет, какие классы растут; heap dump и пути к GC roots покажут удерживающий объект, например static-кеш платежей.

Исправление — ограничить срок жизни данных и повторить наблюдение. Просто увеличить -Xmx значит отложить падение, если коллекция продолжает расти.

  • Histogram и heap dump сами могут дать паузу и потребовать существенные ресурсы.
  • Рост RSS при стабильном heap требует NMT и проверки native-библиотек или потоков.
Что даёт dominator tree?

Он помогает найти объект, удержание которого объясняет большой объём heap, например кеш с миллионами значений.

Почему файл dump нужно защищать?

В нём могут быть строки, токены, DTO и другие данные живых объектов процесса.

Чем JFR отличается от heap dump и thread dump?

JFR — запись событий во времени: где процесс тратил CPU, выделял объекты, блокировался и собирал мусор. Thread dump — один снимок стеков. Heap dump — один снимок объектов и ссылок.

Для скачка p99 я предпочту временную шкалу JFR; для вопроса «кто держит 2 ГБ объектов» нужен heap dump. Инструмент выбираю под гипотезу.

  • Настройка default пригодна для длительной записи с меньшим overhead; profile подробнее и дороже.
  • События allocation не равны полному списку всех живых объектов; это разные вопросы.
Как начать JFR без перезапуска?

jcmd <pid> JFR.start ...; список поддерживаемых параметров проверь через jcmd <pid> help JFR.start.

Где смотреть записанный файл без GUI?

jfr summary file.jfr показывает сводку, jfr print печатает события для фильтрации.

  • jcmd, JDK 21 — основа урока: Thread.print, GC.heap_dump, JFR.start и ограничения команд.
  • JDK 21 Diagnostic Tools — histogram, heap dump и NMT.
  • Troubleshoot Memory Leaks — порядок поиска утечки и анализ dump.
  • jfr command — summary и print записей.
