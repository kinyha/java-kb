JVM: Memory Areas

Два падения за неделю, и -Xmx помог только от одного

В понедельник платёжный сервис упал с OutOfMemoryError. Heap стоял 512 МБ, а отчёт по выпискам за квартал грузил в память больше. Подняли -Xmx до 2 ГБ, и всё заработало. В пятницу сервис упал снова, опять с OutOfMemoryError, хотя heap был заполнен на треть. Подняли -Xmx ещё раз — не помогло.

понедельник:  java.lang.OutOfMemoryError: Java heap space
пятница:      java.lang.OutOfMemoryError: Metaspace

Имя исключения одно, а после двоеточия — разные области памяти. Память JVM не один большой кусок, а несколько областей. У каждой своё содержимое, свой лимит и свой флаг, и переполнение одной ничего не говорит о другой. -Xmx ограничивает только heap. В пятницу кончилось место под классы, и размер heap к этому не относится.

Чтобы по тексту ошибки сразу понимать, куда смотреть, нужна карта: какие области есть, что в каждой лежит и когда она кончается.

Память JVM — несколько областей со своими лимитами

Главное деление — на общие области и области потока. Общие создаются при старте JVM и доступны всем потокам. Область потока появляется вместе с потоком и исчезает вместе с ним.

  • Heap — все объекты и массивы. Здесь же String pool и static-поля классов: с Java 8 они хранятся вместе с объектом Class. Heap чистит сборщик мусора, размер задают -Xms и -Xmx.
  • Metaspace — описания классов: поля, методы, байткод, пул констант. Живёт вне heap, в native-памяти процесса.
  • Code cache — машинный код, который сгенерировал JIT.
  • Стек потока — кадры вызовов: локальные переменные и стек операндов. Размер стека задаёт -Xss.
  • pc-регистр — адрес текущей инструкции потока.

На собеседовании области часто называют терминами спецификации JVMS, а в логах и флагах видны названия HotSpot. Соответствие такое:

В кадре лежат примитивы и ссылки, а сами объекты — в heap

Вопрос «что где лежит» лучше всего видно на одном вызове. Метод pay создаёт платёж и чек и записывает чек в журнал — static-список. Пролистай, что происходит со стеком и heap.

static final List<Receipt> JOURNAL = new ArrayList<>();   // static-поле: список в heap

static void pay(long amount) {              // amount — примитив, лежит прямо в кадре
    Payment p = new Payment(amount);        // объект в heap, в кадре только ссылка p
    Receipt r = new Receipt(p);             // чек ссылается на платёж
    JOURNAL.add(r);                         // второй путь к чеку — из static-поля
}                                           // кадр pay снят: amount, p и r исчезли

Отсюда три правила, которые проверяют на собеседовании. Примитивы и ссылки локальных переменных живут в кадре и исчезают вместе с ним — без участия GC. Объекты живут в heap, пока до них можно дойти от корней: стеков, static-полей и других. А «локальная переменная потокобезопасна» верно только для самой переменной: объект, на который она ссылается, может быть доступен другим потокам.

Объекты, созданные в методе, удаляются, когда метод заканчивается.

Удаляется только кадр со ссылками. Объект остаётся в heap, пока на него есть путь от корней, и освобождается сборщиком мусора позже. Бывает и наоборот: JIT может вообще не создавать в heap объект, который не выходит за пределы метода. Это escape analysis, о нём — в теме Object Layout & Allocation.

Стек потока конечен, и глубокая рекурсия его исчерпывает

Каждый вызов занимает кадр, а размер стека фиксируется при создании потока. По умолчанию он 1 МБ на Linux x64. На macOS arm64, где запускались примеры урока, — 2 МБ. Когда кадры не помещаются, JVM бросает StackOverflowError.

public class Depth {
    static int depth = 0;

    // Каждый вызов кладёт в стек потока новый кадр
    static void validate() {
        depth++;
        validate();                  // рекурсия без выхода: кадры копятся, пока стек не кончится
    }

    public static void main(String[] args) {
        try {
            validate();
        } catch (StackOverflowError e) {
            // Ошибку можно поймать: стек уже размотался, и места снова хватает
            System.out.println("глубина: " + depth);
        }
    }
}

Глубина зависит от размера кадров, а их меняет JIT, поэтому ниже — реальные запуски, а не вывод для предсказания:

$ java -cp out Depth              # стек по умолчанию, 2 МБ на этой машине
глубина: 44661                    # от запуска к запуску 44–47 тысяч
$ java -Xss256k -cp out Depth
глубина: 1479                     # в 8 раз меньше стек — в 30 раз меньше глубина
$ java -Xss4m -cp out Depth
глубина: 151851

Почему не пропорционально? Первые вызовы идут в интерпретаторе, и его кадры крупнее. На маленьком стеке рекурсия кончается раньше, чем JIT успевает скомпилировать validate с компактными кадрами. На большом стеке основная часть глубины приходится на скомпилированный код.

В сервисе StackOverflowError почти всегда означает бесконечную рекурсию: toString или equals двух сущностей, которые ссылаются друг на друга, циклический вызов бинов, Jackson на двунаправленной связи JPA. Лечится исправлением цикла, а не ростом -Xss. Есть и обратная сторона: стек выделяется каждому потоку. Тысяча потоков с -Xss2m резервирует 2 ГБ адресного пространства вне heap. Поэтому -Xss иногда уменьшают, а не увеличивают.

Heap — общая область объектов с верхней границей -Xmx

Размер heap задают два флага. -Xms — сколько занять на старте, -Xmx — сколько можно занять максимум. Если флаги не заданы, JVM смотрит на доступную память: максимум — 25% (MaxRAMPercentage), старт — 1/64. В контейнере JVM видит лимит контейнера, а не память машины: под с лимитом 4 ГБ получит heap в 1 ГБ.

import java.util.ArrayList;
import java.util.List;

public class HeapLimits {
    public static void main(String[] args) {
        // maxMemory — это и есть -Xmx: сколько heap JVM разрешено занять
        System.out.println("max heap: " + Runtime.getRuntime().maxMemory() / 1024 / 1024 + " МБ");

        List<byte[]> receipts = new ArrayList<>();
        try {
            while (true) {
                receipts.add(new byte[64 * 1024]);   // список держит все чеки — GC их не отдаст
            }
        } catch (OutOfMemoryError e) {
            receipts.clear();                        // отпускаем память, чтобы было чем печатать
            System.out.println("1: " + e.getMessage());
        }

        try {
            long[] ledger = new long[Integer.MAX_VALUE];   // массив больше предела JVM
        } catch (OutOfMemoryError e) {
            System.out.println("2: " + e.getMessage());
        }
    }
}

Запусти с маленьким heap: java -Xmx16m -cp out HeapLimits.

max heap: 16 МБ
1: Java heap space
2: Requested array size exceeds VM limit

Первая ошибка — heap кончился честно: живых объектов больше, чем помещается. Вторая — массив запрошен длиннее, чем JVM вообще умеет выделить, и дело тут не в размере heap. А так ведут себя проценты без -Xmx (флаг -XX:MaxRAM имитирует машину с 4 ГБ):

$ java -XX:MaxRAM=4g -cp out HeapLimits | head -1
max heap: 1024 МБ                         # 25% по умолчанию
$ java -XX:MaxRAM=4g -XX:MaxRAMPercentage=75 -cp out HeapLimits | head -1
max heap: 3072 МБ                         # так обычно настраивают сервис в контейнере

Для сервиса в контейнере часто задают -XX:MaxRAMPercentage=75 вместо жёсткого -Xmx. Heap подстраивается под лимит пода, а оставшиеся 25% идут на Metaspace, стеки, code cache и native-буферы. Ставить heap равным лимиту контейнера нельзя: процесс превысит лимит за счёт памяти вне heap, и его убьёт OOM killer. Подробно — в теме Native Memory.

String pool тоже в heap

Одинаковые строковые литералы в JVM — один объект из String pool, таблицы уникальных строк. До Java 7 пул жил в PermGen и мог его переполнить, с Java 7 он в heap, и неиспользуемые строки из него собирает GC.

public class Pool {
    public static void main(String[] args) {
        String a = "RUB";                  // литерал: берётся из String pool
        String b = "RUB";                  // тот же литерал — тот же объект из пула
        String c = new String("RUB");      // new всегда создаёт новый объект в heap
        String d = c.intern();             // intern: вернуть объект из пула с тем же текстом
        String e = "RU" + "B";             // обе части — константы, javac склеил на этапе компиляции
        String part = "RU";
        String f = part + "B";             // склейка во время работы: новый объект

        System.out.println(a == b);
        System.out.println(a == c);
        System.out.println(a == d);
        System.out.println(a == e);
        System.out.println(a == f);
        System.out.println(a.equals(f));   // сравнение текста, а не ссылок
    }
}

Классы живут в Metaspace, вне heap

Описания классов — поля, методы, байткод, пул констант — лежат в Metaspace. Так было не всегда, и вопрос «чем Metaspace отличается от PermGen» задают до сих пор.

PermGen был частью heap с фиксированным размером. Его приходилось угадывать заранее: сервер приложений после нескольких редеплоев упирался в PermGen space. Metaspace живёт в native-памяти и по умолчанию не ограничен (MaxMetaspaceSize не задан). Метаданные освобождаются, когда выгружается загрузчик классов, который их определил.

«Не ограничен» не значит «не кончится». Проверим: создаём классы новыми загрузчиками и держим загрузчики в списке, как делает приложение с утечкой.

import java.util.ArrayList;
import java.util.List;

public class MetaOom {
    public static class Rules { public int limit() { return 42; } }

    public static void main(String[] args) throws Exception {
        byte[] bytes = MetaOom.class.getResourceAsStream("MetaOom$Rules.class").readAllBytes();
        List<ClassLoader> loaders = new ArrayList<>();   // держим загрузчики — их классы не выгрузятся
        try {
            while (true) {
                // Новый загрузчик + те же байты = новый класс и новые метаданные в Metaspace
                ClassLoader loader = new ClassLoader(null) {
                    @Override protected Class<?> findClass(String name) {
                        return defineClass(name, bytes, 0, bytes.length);
                    }
                };
                loader.loadClass("MetaOom$Rules");
                loaders.add(loader);
            }
        } catch (OutOfMemoryError e) {
            int count = loaders.size();
            loaders.clear();
            System.out.println(e.getMessage() + " после " + (count / 1000) + " тыс. классов");
        }
    }
}
$ java -XX:MaxMetaspaceSize=32m -cp out MetaOom
Metaspace после 5 тыс. классов

$ java -cp out MetaOom                    # без лимита Metaspace
Compressed class space после 524 тыс. классов

Без лимита программа всё равно упала, но с другим текстом. Часть метаданных — описания самих классов — лежит в compressed class space. Это отдельный кусок Metaspace фиксированного размера, по умолчанию 1 ГБ (CompressedClassSpaceSize). Он нужен, чтобы ссылка из объекта на его класс занимала 4 байта вместо 8. Настоящая причина обоих падений одна — утечка загрузчиков, как в теме Class Loading.

В проде MaxMetaspaceSize часто задают, например 256–512 МБ. Без лимита утечка классов медленно съест память контейнера, и процесс убьёт OOM killer без понятной ошибки. С лимитом будет OutOfMemoryError: Metaspace с heap dump.

Code cache: переполнение не роняет процесс

Code cache хранит машинный код от JIT, по умолчанию до 240 МБ. Когда он заполнен, исключения нет, а в лог падает предупреждение:

$ java -XX:ReservedCodeCacheSize=2600k -cp out Busy    # искусственно маленький code cache
[warning][codecache] CodeCache is full. Compiler has been disabled.
[warning][codecache] Try increasing the code cache size using -XX:ReservedCodeCacheSize=

Сервис продолжает работать, но новые горячие методы больше не компилируются и остаются в интерпретаторе. Симптом — постепенная деградация латентности без ошибок. Поэтому это предупреждение стоит ловить в алертах по логам.

Для heap сразу включи три флага. Без них расследование начинается с «воспроизведи на проде».

-XX:+HeapDumpOnOutOfMemoryError        # при OOM сохранить heap dump
-XX:HeapDumpPath=/dumps/               # в том, который переживёт перезапуск пода
-XX:+ExitOnOutOfMemoryError            # после OOM завершить процесс, а не жить полумёртвым

Последний флаг важен в Kubernetes. После OutOfMemoryError часть потоков могла умереть посреди работы, и процесс в таком состоянии хуже упавшего: health может быть зелёным, а платежи не проводятся. Лучше завершиться и дать оркестратору поднять чистый под.

Где кончается эта карта? Бывает, что heap заполнен наполовину, Metaspace в норме, а контейнер всё равно убивают за превышение памяти. Значит, растёт то, что вне этих областей: direct-буферы, стеки тысяч потоков, память native-библиотек. Это тема Native Memory. А если heap действительно растёт, следующий вопрос — кто держит объекты, и это тема Garbage Collection и Diagnostics.

  • Память JVM — это heap, Metaspace, code cache и стеки потоков. У каждой области свой лимит, -Xmx касается только heap.
  • В кадре лежат примитивы и ссылки, объекты — в heap. Объект живёт, пока до него можно дойти от корней, а не пока жив метод.
  • StackOverflowError почти всегда означает бесконечную рекурсию. Стек выделяется каждому потоку, поэтому -Xss умножается на число потоков.
  • С Java 8 классы живут в Metaspace вне heap, по умолчанию без лимита, но в пределах compressed class space в 1 ГБ. String pool и static-поля — в heap.
  • Текст OutOfMemoryError называет область. В проде нужны HeapDumpOnOutOfMemoryError и ExitOnOutOfMemoryError.

На собеседовании

Что хранится в heap, а что в стеке?

В стеке потока лежат кадры вызовов: локальные переменные примитивных типов, ссылки на объекты и стек операндов. У каждого потока свой стек, и кадр исчезает, когда метод возвращается. В heap лежат все объекты и массивы. Heap общий для всех потоков, и объект живёт там, пока до него можно дойти по ссылкам от корней, а не пока жив метод, который его создал.

Отсюда практика. Если метод положил объект в static-коллекцию, объект переживёт метод, и это частая причина утечки. А локальная переменная безопасна между потоками только сама по себе: объект, на который она ссылается, может быть общим.

  • JIT с escape analysis может вообще не выделять в heap объект, который не выходит за метод, и разложить его поля по регистрам.
  • Static-поля с Java 8 хранятся в heap вместе с объектом Class, а не в Metaspace.
Где окажутся amount, p и объект Payment в методе pay из урока?

amount и ссылка p — в кадре pay в стеке потока. Объект Payment — в heap. После выхода из метода amount и p исчезнут сразу, а объект — когда до него не останется путей от корней.

«Метод потокобезопасен: он работает только с локальными переменными». Всегда ли? 
void apply(Account account, long amount) {
    long balance = account.getBalance();
    account.setBalance(balance - amount);
}

Нет. balance и ссылка account локальные, но сам объект Account в heap может менять другой поток. Между чтением и записью баланса второй поток успеет списать деньги, и одно списание потеряется. Нужна синхронизация или атомарная операция на уровне базы.

Чем Metaspace отличается от PermGen?

Обе области хранят метаданные классов. PermGen до Java 8 был частью heap с фиксированным размером MaxPermSize. Его приходилось угадывать, и серверы приложений падали с PermGen space после редеплоев. В Java 8 PermGen убрали, метаданные переехали в Metaspace в native-памяти. Она растёт по необходимости и по умолчанию не ограничена.

Но утечка классов от этого не исчезла, она стала менее заметной. Поэтому в проде я задаю MaxMetaspaceSize, чтобы получить понятный OutOfMemoryError: Metaspace, а не убийство контейнера.

  • String pool и static-поля ушли из PermGen в heap ещё в Java 7.
  • Внутри Metaspace есть compressed class space, по умолчанию 1 ГБ: он ограничивает число классов даже без MaxMetaspaceSize.
  • Метаданные освобождаются только при выгрузке загрузчика классов целиком.
Что в сервисе может заполнять Metaspace?

Классы приложения и библиотек, а ещё сгенерированные на лету: прокси Spring и Hibernate, лямбды, классы от шаблонизаторов и скриптовых движков. Опасна генерация в цикле с новым загрузчиком, который потом не выгружается.

Сервис переводят на Java 21, а в скрипте запуска осталось -XX:MaxPermSize=256m. Что будет?

JVM не запустится: Unrecognized VM option 'MaxPermSize=256m' — проверено на JDK 21. PermGen нет с Java 8; там флаг ещё игнорировался с предупреждением, в современных версиях его просто не существует. Если нужен лимит на метаданные, это -XX:MaxMetaspaceSize. Такие остатки старых флагов стоит вычищать при каждом переходе на новую Java.

Какие бывают OutOfMemoryError и что делать с каждым?

Текст после двоеточия называет область. Java heap space — кончился heap: либо утечка, либо живых данных больше -Xmx. Metaspace — слишком много классов, обычно утечка загрузчиков. unable to create native thread — упёрлись в лимит потоков или памяти под стеки. Direct buffer memory — direct-буферы сверх лимита.

Для heap я сначала смотрю heap dump, который снят флагом HeapDumpOnOutOfMemoryError, и ищу, кто держит объекты. Увеличивать -Xmx имеет смысл, только когда ясно, что это нормальный объём данных, а не утечка.

  • После OOM процесс может остаться в полусломанном состоянии. В контейнере лучше ExitOnOutOfMemoryError и перезапуск.
  • Если контейнер убит OOM killer без Java-ошибки, heap тут ни при чём: растёт память вне heap.
Под с лимитом 4 ГБ падает с Java heap space. Предлагают поставить -Xmx4g. Что скажешь?

Это сломает по-другому: heap займёт весь лимит, а Metaspace, стеки, code cache и буферы вытолкнут процесс за границу, и его убьёт OOM killer без понятной ошибки. Сначала heap dump и поиск утечки. Если объём честный — поднимать лимит пода и держать heap около 75% от него.

Какую ошибку даст new long[Integer.MAX_VALUE] на heap в 16 ГБ?

Requested array size exceeds VM limit. Массив такой длины JVM не выделяет в принципе, размер heap тут ни при чём.

Что такое StackOverflowError и как на него влияет -Xss?

У каждого потока стек фиксированного размера, по умолчанию 1 МБ на Linux x64. Каждый вызов кладёт в него кадр. Когда кадры не помещаются, JVM бросает StackOverflowError. -Xss меняет размер стека каждого потока.

В сервисе это почти всегда бесконечная рекурсия: toString или equals у сущностей, которые ссылаются друг на друга, сериализация двунаправленной связи JPA в JSON. Я чиню цикл, а не увеличиваю стек.

  • Стек выделяется каждому потоку вне heap: тысяча потоков с -Xss2m резервирует 2 ГБ адресного пространства.
  • Глубина при одном -Xss плавает: кадры интерпретатора крупнее, чем у скомпилированного JIT кода.
Найди причину StackOverflowError при логировании платежа 
class Payment {
    Account account;
    public String toString() { return "Payment{account=" + account + "}"; }
}
class Account {
    List<Payment> payments;
    public String toString() { return "Account{payments=" + payments + "}"; }
}

Payment.toString печатает счёт, счёт печатает список платежей, каждый платёж снова печатает счёт — бесконечная рекурсия. Исправить: в toString одной из сторон выводить только идентификатор. Тот же цикл ломает equals, hashCode и сериализацию в JSON.

Где хранится String pool и зачем intern?

String pool — таблица уникальных строк, куда попадают все строковые литералы. Одинаковые литералы в программе — один и тот же объект. С Java 7 пул лежит в heap, раньше был в PermGen. intern() возвращает объект из пула с тем же текстом, добавляя его туда при необходимости.

Поэтому == на литералах иногда совпадает случайно, но строки из JSON, базы или склейки — новые объекты. Сравнивать строки нужно через equals.

Что выведет этот код? 
String currency = "USD";
String fromApi = new StringBuilder("US").append("D").toString();
System.out.println(currency == fromApi);
System.out.println(currency == fromApi.intern());
System.out.println(currency == "US" + "D");
false
true
true

fromApi собран во время работы — новый объект. intern вернул объект из пула, тот же, что у литерала. "US" + "D" — константное выражение, javac склеил его сам, и получился тот же литерал.

Что такое -Xms и -Xmx и какие значения по умолчанию?

-Xms — начальный размер heap, -Xmx — максимальный. Без флагов JVM берёт 1/64 доступной памяти на старт и 25% как максимум. В контейнере это проценты от лимита пода, поэтому под на 4 ГБ по умолчанию получит всего гигабайт heap.

Для сервиса в контейнере я задаю -XX:MaxRAMPercentage=75: heap следует за лимитом пода, а остальное остаётся на память вне heap. Часто ставят -Xms равным максимуму, чтобы heap не рос рывками под нагрузкой.

Сколько heap получит JVM в поде с лимитом 2 ГБ без флагов? А с -XX:MaxRAMPercentage=75?

512 МБ по умолчанию — 25% от лимита — и 1536 МБ с 75%. Проверить можно так: java -XX:+PrintFlagsFinal -version | grep MaxHeapSize внутри контейнера.
