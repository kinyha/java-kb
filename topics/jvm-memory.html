JVM: области памяти

Память процесса растёт, хотя запрос уже завершился

Платёжный сервис после нескольких часов работы занимает всё больше памяти. В каждом запросе создаётся чек; метод быстро возвращается, но чеки попадают в static-список. Вышедший из метода локальный указатель исчез, а объект остаётся доступен через список.

Здесь важно различать области памяти JVM и путь достижимости объекта. Значение -Xmx ограничивает heap, но не всю память процесса: есть стеки потоков, метаданные классов, code cache и native-выделения.

Heap общий, а стек вызовов принадлежит потоку

Объекты и массивы обычно создаются в общем heap. У каждого Java-потока есть собственный стек из кадров вызовов: локальные переменные, операнды и информация о возврате. Локальная переменная ссылочного типа хранит ссылку на объект, а не сам объект.

Спецификация JVM также описывает общую method area и per-thread pc register. В HotSpot метаданные классов размещаются в Metaspace за пределами Java heap; скомпилированный JIT-код — в code cache. Эти названия описывают реализацию HotSpot, а не обязательную раскладку любой JVM.

Вышедший кадр не освобождает объект, если есть другой путь

В примере список retained — static-поле, поэтому он доступен пока жив его класс. После возврата из handle кадр исчезает, но список продолжает держать массивы. Это логическая утечка: GC честно сохраняет то, что приложение считает достижимым.

import java.util.ArrayList;
import java.util.List;
public class MemoryDemo {
    static final List<byte[]> retained = new ArrayList<>();
    static void handle() {
        byte[] receipt = new byte[1024];
        retained.add(receipt);
        System.out.println(retained.size());
    }
    public static void main(String[] args) {
        handle();
        handle();
    }
}

Размер объекта не равен сумме размеров полей

В HotSpot объект имеет заголовок, данные полей и выравнивание; точные размеры зависят от разрядности, compressed oops и настроек JVM. Массив дополнительно хранит длину. Поэтому тысяча маленьких объектов может занимать заметно больше памяти, чем один массив из тысячи значений.

JIT может устранить часть временных объектов, если доказал, что они не утекают за пределы участка кода: это escape analysis и scalar replacement. Нельзя обещать, что конкретный new обязательно создаст heap-объект или обязательно будет устранён; проверяй профилем и на нужной версии JVM.

Разные OutOfMemoryError ведут к разным проверкам

Java heap space указывает на недостаток heap для живых объектов или на слишком маленький -Xmx. Metaspace заставляет искать избыточную загрузку классов или удержанные загрузчики. unable to create native thread связано с потоками, лимитами ОС и native-памятью; увеличение -Xmx может только ухудшить ситуацию.

Если память кончается, достаточно увеличить heap.

Сначала смотри текст ошибки, heap histogram, GC-логи и память процесса. Увеличенный heap не устранит удержание объектов и не исправит исчерпание native-памяти.

Тему GC изучай после карты памяти: сборщик работает с достижимостью heap-объектов, а не с любым байтом процесса.

  • Heap хранит объекты и массивы; каждый поток имеет свой стек кадров вызовов.
  • Ссылка в локальной переменной и сам объект могут жить разное время.
  • Static-поле может удерживать объект после завершения запроса.
  • Metaspace и code cache относятся к HotSpot и живут вне Java heap.
  • По тексту OOME выбирай область диагностики, прежде чем менять размеры памяти.

На собеседовании

Что лежит в heap и в стеке потока?

В heap обычно лежат объекты и массивы, общие для потоков. В стеке каждого потока лежат кадры вызовов с локальными переменными и промежуточными значениями; переменная ссылочного типа указывает на объект в heap.

Если метод платежа вернулся, его кадр исчез. Но чек, оставленный в static-списке, остаётся живым: GC видит путь от корня к объекту.

  • JVM Specification определяет абстрактные области; JIT может устранить некоторые выделения через escape analysis.
  • Большое число потоков увеличивает затраты на стеки и может упереться в native-лимиты до заполнения heap.
Объект удалится сразу после выхода из метода?

Только если он станет недостижимым, и даже тогда время сборки не гарантировано. Другие ссылки могут удерживать его.

Где хранится static-поле?

Это поле класса в модели JVM. Важно, что его значение может быть GC root или вести к живым объектам; конкретная физическая раскладка — деталь реализации.

Что такое Metaspace и почему она может заполниться?

Metaspace — область HotSpot для метаданных загруженных классов за пределами Java heap. Если приложение непрерывно создаёт новые классы или удерживает их загрузчики, метаданные не освобождаются и процесс может получить OutOfMemoryError: Metaspace.

В сервисе я проверю число классов и загрузчиков, динамические прокси и перезагрузку приложений, а не только -Xmx.

  • Освобождение метаданных связано с выгрузкой классов и загрузчиков; один живой ClassLoader может удерживать много классов.
  • Method area — термин спецификации, Metaspace — конкретное решение HotSpot.
Поможет ли увеличение -Xmx при Metaspace OOME?

Нет: -Xmx ограничивает Java heap, а Metaspace использует native-память.

Какой счётчик посмотреть?

Смотри количество загруженных классов, память Metaspace и при необходимости Native Memory Tracking.

Сервис получил OutOfMemoryError. С чего начнёшь?

Сначала читаю полный текст OOME и контекст: heap, Metaspace, direct memory или создание потока требуют разных действий. Для heap проверяю GC-логи, histogram и heap dump: растёт ли live set и кто держит объекты.

Например, если static-кеш чеков не ограничен, увеличение -Xmx лишь отсрочит падение. Исправлю срок жизни или лимит кеша и подтвержу это повторным профилем.

  • Память процесса включает heap и native-области; лимит контейнера может завершить процесс без Java OOME.
  • Heap dump и histogram могут давать паузу и занимать много места; в проде учитывай их стоимость.
Что такое live set?

Объекты, остающиеся достижимыми после сборки. Его устойчивый рост при неизменной нагрузке — повод искать удержание.

Что показывает heap dump?

Снимок heap-объектов и ссылок между ними. По dominator tree и путям к GC roots можно найти удерживающую коллекцию.

  • JVMS 21, §2.5 Run-Time Data Areas — основа урока: heap, стеки, method area и ошибки.
  • HotSpot VM Guide — allocation и runtime-реализация.
  • JDK 21 Diagnostic Tools — heap dump, histogram и Native Memory Tracking.
