JWT

JWT — три части через точку: заголовок, утверждения и подпись, каждая в base64url. Содержимое читает кто угодно, подпись лишь доказывает, кто его выпустил. HS256 подписывает общим секретом, поэтому любой проверяющий может и выпускать токены; RS256 и ES256 подписывают закрытым ключом издателя. Проверка опасна, если алгоритм берётся из самого токена: тогда проходят alg: none и HS256 с публичным ключом вместо секрета. Сервер фиксирует алгоритм и проверяет издателя, аудиторию и срок. Отозвать JWT нельзя, поэтому access-токен живёт минуты, а refresh-токен ротируется при каждом использовании.

Подделанный токен с ролью admin прошёл проверку, хотя подпись никто не взламывал

Платёжный сервис принимает JWT от своего сервера авторизации. Проверку написали сами: разобрать заголовок, взять алгоритм, проверить подпись. На пентесте токен с "role": "admin" и пустой подписью прошёл. Второй, подписанный публичным ключом сервера, который лежит в открытом доступе, — тоже. Ни один ключ не украли, криптографию не взламывали: ошибка в том, кто выбирает правила проверки.

Тема разбирает JWT как формат и как протокол: что подписывается, чем отличаются алгоритмы, какие атаки на проверку известны, что делать с отзывом и где хранить токен на клиенте. Как Spring Security проверяет JWT в resource server и строит права из claims, разобрано в OAuth2 & JWT. Демо JwtAttacksDemo.java собирает токены вручную на JDK, без библиотек, чтобы были видны подписываемые байты: java JwtAttacksDemo.java. Значения exp зависят от времени запуска.

Токен — это открытый JSON и подпись над его base64-формой

== token
header:  {"alg":"RS256","typ":"JWT"}
payload: {"iss":"https://id.pay.example","sub":"anna","aud":"payments","role":"user","exp":1790955636}
length:  504 chars

Токен — base64url(header) . base64url(payload) . base64url(signature). Подписываются не JSON-объекты, а ровно ASCII-строка из первых двух частей с точкой между ними: проверяющий не разбирает и не пересобирает JSON до проверки подписи. Base64url — кодировка, и любой, у кого есть токен, читает утверждения. Поэтому в JWT не кладут ничего секретного: ни номера карт, ни персональных данных сверх необходимого. Если содержимое нужно скрыть, используют зашифрованный JWE, но это редкость.

ClaimСмыслЧто проверяет сервер
issКто выпустилСовпадает с доверенным издателем
subО ком токенИспользуется как id пользователя
audДля кого выпущенСодержит имя этого сервиса
exp, nbf, iatСрок, начало действия, время выпускаТекущее время в окне с небольшим допуском
jtiУникальный id токенаДля списка отзыва и защиты от повтора

Токен в 500 символов уходит в каждом запросе. Если сложить в него все роли, группы и права пользователя, он вырастет до нескольких килобайт и упрётся в лимиты заголовков прокси, обычно 8 КБ на все заголовки. Права, которые часто меняются, лучше хранить на сервере, а в токене оставить идентичность и крупные роли.

HS256 позволяет выпускать токены каждому, кто может их проверить

HS256 — HMAC-SHA256 общим секретом. Один и тот же ключ подписывает и проверяет. Если токены проверяют пять сервисов, секрет есть у всех пяти, и утечка из любого позволяет выпускать токены от имени издателя. HS256 уместен, когда издатель и проверяющий — один сервис.

RS256 и ES256 — подпись RSA и ECDSA. Издатель подписывает закрытым ключом, а сервисы проверяют публичным, которым подписать нельзя. Публичные ключи издатель публикует как JWKS — JSON со списком ключей по адресу вроде /.well-known/jwks.json, а в заголовке токена указывает kid, каким ключом подписан. Это позволяет менять ключи без простоя: опубликовать новый ключ рядом со старым, начать подписывать новым, а старый убрать, когда истекут все выпущенные им токены. ES256 даёт подписи короче, чем RS256: 64 байта против 256 у RSA-2048.

Проверяющий кеширует JWKS и перечитывает его, когда встречает незнакомый kid, но не чаще чем раз в некоторое время: иначе поток токенов с выдуманными kid превратится в поток запросов к серверу авторизации.

Алгоритм проверки выбирает сервер, а не заголовок токена

Демо выпускает пять токенов: настоящий, два поддельных с ролью admin, настоящий для другого сервиса и просроченный. Наивная проверка берёт алгоритм из заголовка и проверяет только подпись:

String alg = claim(header, "alg");                    // Алгоритм выбирает токен.
boolean ok = switch (alg) {
    case "none"  -> true;
    case "HS256" -> isEqual(hmac(publicPem, input), signature); // «Ключ проверки» — публичный PEM.
    case "RS256" -> rsVerify(issuer, input, signature);
    default      -> false;
};
== naive verifier: trusts header alg, checks only signature
valid                  -> accepted, role=user
alg=none               -> accepted, role=admin
HS256 with public key  -> accepted, role=admin
aud=reports            -> accepted, role=user
expired 2 min ago      -> accepted, role=user

alg: none — легальный по спецификации «токен без подписи», и библиотека, которая его поддерживает, принимает пустую подпись. Подмена алгоритма хитрее. Сервер настроен проверять RS256 ключом издателя. Атакующий ставит в заголовок HS256 и подписывает токен HMAC, используя как секрет публичный ключ — он ведь публичный. Если библиотека берёт «ключ проверки» и применяет к нему алгоритм из заголовка, HMAC сходится. Так ломались реальные библиотеки, в том числе с CVE.

Ещё две строки прошли без всякой подделки. Токен для сервиса отчётов подписан тем же издателем, и без проверки aud его можно предъявить платёжному сервису. Просроченный токен прошёл, потому что срок не смотрели. Строгая проверка закрывает все пять случаев:

if (!"RS256".equals(alg)) return "rejected: alg";                       // Список алгоритмов — у сервера.
if (!rsVerify(issuer, input, signature)) return "rejected: signature";
if (!"https://id.pay.example".equals(iss)) return "rejected: iss";
if (!"payments".equals(aud)) return "rejected: aud";
if (exp + 60 < now) return "rejected: exp";                            // Допуск 60 с на рассинхрон часов.
== strict verifier: RS256 only, iss, aud, exp with 60 s skew
valid                  -> accepted, role=user
alg=none               -> rejected: alg
HS256 with public key  -> rejected: alg
aud=reports            -> rejected: aud
expired 2 min ago      -> rejected: exp

В Java проверку не пишут сами: Nimbus JOSE + JWT, jjwt и Spring Security явно привязывают ключ к алгоритму. Но настроить их всё равно нужно: Spring resource server по умолчанию проверяет подпись, срок и издателя, а аудиторию — только если её указать. Заголовки jku и x5u, предлагающие адрес ключа, игнорируют: иначе токен сам скажет, каким ключом его проверять.

Короткий access-токен и ротация refresh-токена заменяют отзыв

JWT нельзя отозвать: подписанный токен действителен, пока не истёк срок. Поэтому access-токен живёт 5–15 минут — столько длится окно, в котором украденный токен работает. Чтобы пользователь не входил заново каждые 15 минут, вместе с ним выдают refresh-токен — долгоживущий, непрозрачный и хранящийся на сервере авторизации. Его можно отозвать как обычную сессию.

Refresh-токен ценнее access-токена, поэтому его ротируют: каждое использование выдаёт новый, а старый становится использованным. Если старый приходит второй раз, значит, у него две копии — у клиента и у вора, — и сервер отзывает всё семейство токенов:

== refresh rotation
thief  uses rt-1   -> 200 new access + rt-2
client uses rt-1   -> 401 reuse detected, family f-anna revoked
thief  uses rt-2   -> 401

Если нужно отозвать доступ немедленно — блокировка аккаунта, смена пароля, — короткого срока мало. Тогда сервис хранит список отозванных jti до истечения их срока или номер версии сессии пользователя, который сравнивается с claim в токене. Оба способа возвращают обращение к хранилищу; это осознанная цена, которую платят только за критичные операции.

В браузере токен безопаснее держать на сервере, чем в localStorage

Мобильное приложение хранит токены в защищённом хранилище ОС: Keychain или Keystore. В браузере выбор хуже. localStorage доступен любому JavaScript на странице, и одна XSS-уязвимость или скомпрометированный npm-пакет выносит токены. Переменная в памяти переживает XSS чуть лучше, но теряется при перезагрузке. HttpOnly-cookie JavaScript не прочитает, но тогда возвращается защита от CSRF из Authentication Basics.

Поэтому для браузерных приложений рекомендуют паттерн BFF — backend for frontend. Браузер общается только со своим бэкендом через сессию в HttpOnly-cookie, а токены хранит и обновляет бэкенд; в JavaScript они не попадают вовсе. Это возвращение к сессиям, но токены продолжают работать между сервисами, где они действительно нужны.

JWT безопаснее сессий, потому что подписан и не хранится на сервере.

Подпись защищает от подделки, но не от кражи: украденный JWT работает до конца срока, и отозвать его нельзя без хранилища. Сессия отзывается мгновенно. JWT выигрывает в распределённой проверке между сервисами, а не в безопасности.

  • JWT — открытые header и payload в base64url плюс подпись над их строкой; секретов в нём не хранят.
  • HS256 — общий секрет, проверяющий может выпускать токены; RS256 и ES256 — закрытый ключ у издателя, JWKS с kid для ротации.
  • Алгоритм фиксирует сервер: наивная проверка в демо приняла alg=none и HS256 с публичным ключом.
  • Обязательно проверяют iss, aud и exp с небольшим допуском.
  • Access-токен на минуты, refresh-токен ротируется; повторное использование отзывает семейство.
  • В браузере — BFF и HttpOnly-cookie, а не localStorage.

На собеседовании

Как устроен JWT и что гарантирует подпись?

Три части через точку: заголовок с алгоритмом, payload с утверждениями — iss, sub, aud, exp, роли — и подпись. Первые две — base64url от JSON, их читает кто угодно. Подпись вычисляется над строкой header.payload и доказывает, что токен выпустил владелец ключа и что содержимое не менялось. Она не скрывает данные, поэтому секретов в JWT не кладут.

  • HS256 — общий секрет у всех проверяющих; RS256 и ES256 — публичный ключ из JWKS, выпускать может только издатель.
  • kid в заголовке выбирает ключ и позволяет ротацию без простоя.
  • Большой токен упирается в лимиты заголовков; часто меняющиеся права держат на сервере.

Какие ошибки проверки JWT приводят к подделке токенов?

Доверие алгоритму из заголовка: alg=none с пустой подписью и подмена RS256 на HS256, когда HMAC вычисляется публичным ключом как секретом. Отсутствие проверки aud — токен для другого сервиса того же издателя принимается. Отсутствие проверки exp и iss.

Сервер задаёт допустимые алгоритмы и ключи сам и проверяет iss, aud, exp с небольшим допуском на рассинхрон часов.

  • Заголовки jku и x5u игнорируют: токен не должен указывать, каким ключом его проверять.
  • Незнакомый kid перечитывает JWKS не чаще заданного интервала.
  • Spring resource server не проверяет aud, пока её не настроить.
Что не так с этой проверкой? 
DecodedJWT jwt = JWT.decode(token);
Algorithm alg = switch (jwt.getAlgorithm()) {
    case "HS256" -> Algorithm.HMAC256(publicKeyPem);
    default      -> Algorithm.RSA256(publicKey, null);
};
alg.verify(jwt);
return jwt.getClaim("role").asString();

Алгоритм выбирается по заголовку токена, и для HS256 секретом становится публичный ключ, который знают все: атакующий подписывает HMAC этим ключом любой payload. Нужен один заранее заданный алгоритм RS256 и верификатор с проверкой издателя, аудитории и срока; verify здесь проверяет только подпись.

Как отозвать JWT и зачем нужен refresh-токен?

Сам JWT отозвать нельзя: он действителен до exp. Поэтому access-токен делают коротким, на 5–15 минут, а для продления выдают refresh-токен, который хранится на сервере авторизации и отзывается как сессия. Для немедленного отзыва ведут список отозванных jti до их истечения или версию сессии пользователя.

  • Refresh-токен ротируют: каждый обмен выдаёт новый, повтор старого отзывает всё семейство.
  • Список отзыва возвращает обращение к хранилищу на каждый запрос; его применяют там, где мгновенный отзыв критичен.

Где хранить JWT в браузере?

localStorage доступен любому скрипту, и XSS крадёт токен. HttpOnly-cookie скрипт не прочитает, но нужна защита от CSRF: SameSite и CSRF-токен. Лучший вариант для SPA — BFF: браузер держит только сессию в HttpOnly-cookie со своим бэкендом, а токены хранит и обновляет бэкенд.

  • Мобильные приложения хранят токены в Keychain или Keystore.
  • Токен в памяти страницы теряется при перезагрузке и всё равно доступен XSS во время работы.
  • RFC 8725: JSON Web Token Best Current Practices — основа урока о проверке: фиксация алгоритмов, aud, атаки на заголовок.
  • RFC 7519: JSON Web Token — формат и зарегистрированные claims.
  • RFC 9700: OAuth 2.0 Security Best Current Practice — ротация refresh-токенов и обнаружение повторного использования.
  • OAuth 2.0 for Browser-Based Applications — BFF и хранение токенов в браузере.
