Java in Kubernetes

Java-сервису в Kubernetes нужны три настройки, без которых он работает хуже, чем на виртуальной машине. Память: лимит контейнера покрывает весь процесс, а не только heap, — при MaxRAMPercentage=100 ядро убило под (OOMKilled, код 137) без единой строки об ошибке, при 75 % JVM сама бросила OutOfMemoryError. Пробы: readiness решает, получает ли под трафик, liveness — перезапускать ли его; liveness, зависящая от базы, в демо перезапустила все поды 2–3 раза за 30 секунд недоступности базы и ничего не исправила. Остановка: при выкатке под получает SIGTERM одновременно с удалением из Service, и без паузы preStop клиенты получили 7 ошибок, с паузой — одну.

Поды падают с OOMKilled, перезапускаются при сбое базы и роняют запросы при каждом деплое

Платёжный сервис перенесли в Kubernetes: лимит памяти 1 ГБ, -Xmx1g, liveness-проба — тот же /actuator/health, что проверяет базу. Под нагрузкой поды убиваются с OOMKilled без следов в логах. Когда база на минуту ушла на переключение, Kubernetes начал перезапускать все поды сервиса, и после возвращения базы сервис ещё пять минут прогревался. А при каждом деплое мониторинг показывает всплеск 502.

Тема разбирает ресурсы, пробы и корректную остановку на кластере k3s 1.34 в Docker. Демо k8s-java.sh запускает мини-сервис App.java с эндпоинтами /, /live и /ready, который считает себя готовым, если отвечает «база» — отдельный сервис db. Объекты Kubernetes — в Kubernetes Basics, JVM в контейнере — в Docker, стратегии выкатки — в Deployment Strategies.

Лимит памяти — на весь процесс, а не на heap

resources:
  requests: { memory: 256Mi, cpu: 100m }   # для планировщика: сколько зарезервировать на узле
  limits:   { memory: 256Mi }               # потолок: превышение — OOMKilled
env:
  - { name: JAVA_TOOL_OPTIONS, value: "-XX:MaxRAMPercentage=75" }
== memory: limit 256Mi, the app fills 300 MB of heap
   MaxRAMPercentage=100:        maxHeap=247MB, terminated: OOMKilled, exit 137, last log: allocated 200MB
   MaxRAMPercentage=75:         maxHeap=185MB, terminated: Error, exit 1, last log: Exception in thread "main" java.lang.OutOfMemoryError: Java

Requests — что планировщик резервирует на узле, limits — потолок. Для памяти обычно ставят requests равным limits: под не будет вытеснен из-за того, что узел переполнен соседями, и поведение предсказуемо. Лимит CPU для JVM спорен: при превышении процесс не убивают, а притормаживают (throttling), и паузы сборки мусора или прогрев JIT растягиваются; многие ставят только request по CPU. Число CPU, которое видит JVM, определяется лимитом, а при его отсутствии — числом ядер узла, поэтому пулы потоков и GC иногда настраивают явно (-XX:ActiveProcessorCount).

Readiness выводит из трафика, liveness перезапускает

readinessProbe: { httpGet: { path: /ready, port: 8080 }, periodSeconds: 2, failureThreshold: 1 }
livenessProbe:  { httpGet: { path: /live,  port: 8080 }, periodSeconds: 2, failureThreshold: 3 }
== the database is down for 30 s (db scaled to 0)
   liveness on /live:  ready endpoints during outage: 0, restarts: 0 0 0
   liveness on /ready: ready endpoints during outage: 0, restarts: 3 2 2

База недоступна 30 секунд. В обоих вариантах readiness-проба провалилась, и все три пода вышли из endpoints Service — запросы к сервису получают быстрый отказ, а не зависание. Разница в liveness. Если liveness проверяет только, что процесс жив и отвечает (/live), поды переживают сбой без перезапусков и сразу возвращаются в трафик, когда база ожила. Если liveness проверяет базу, Kubernetes каждые 6 секунд считает поды мёртвыми и перезапускает их — 2–3 перезапуска за полминуты. Перезапуск не чинит базу, зато сбрасывает кеши, пулы и прогретый JIT, а при длительном сбое под уходит в CrashLoopBackOff с растущими паузами и возвращается позже, чем база.

Правило: liveness проверяет только то, что исправит перезапуск, — процесс завис, deadlock, исчерпан пул потоков самого сервиса. Внешние зависимости — только в readiness, и то осторожно: если все поды одновременно станут неготовы из-за общей зависимости, сервис отдаёт 503 сразу, что лучше зависаний, но не всегда желательно. В Spring Boot Actuator для этого есть группы /actuator/health/liveness и /actuator/health/readiness. Startup probe защищает медленный старт: пока она не прошла, liveness не проверяется, и долго стартующий сервис не убивают в цикле.

Остановка при выкатке: SIGTERM приходит раньше, чем под уходит из Service

spec:
  terminationGracePeriodSeconds: 30
  containers:
    - name: app
      lifecycle:
        preStop: { exec: { command: ["sleep", "5"] } }   # дать кластеру убрать под из endpoints
== two rollout restarts under load (client: request every 50 ms, timeout 1 s)
   preStop none:  requests 882, failed 7
   preStop sleep: requests 917, failed 1

Демо делает две выкатки под непрерывной нагрузкой: без preStop — 7 неудачных запросов из 882, с паузой — 1 из 917. На одном узле k3s маршруты обновляются быстро; в больших кластерах kube-proxy на десятках узлов обновляет правила с задержкой в секунды, и разница больше. Оставшуюся ошибку дают крайние случаи — соединение, установленное в момент закрытия. Для полной картины нужны все части: preStop-пауза, обработка SIGTERM в приложении (server.shutdown=graceful в Spring Boot — по умолчанию с 3.4), terminationGracePeriodSeconds больше суммы паузы и времени дообработки, стратегия maxUnavailable: 0, чтобы новые поды стали готовы до удаления старых, и java как PID 1, как в Docker. В Kubernetes 1.30+ вместо exec sleep можно использовать встроенное действие preStop: sleep, которому не нужен бинарник sleep в образе.

Горизонтальное масштабирование (HPA) добавляет поды по CPU или собственным метрикам. Для JVM у этого две особенности: новый под стартует медленнее и первые минуты работает на непрогретом JIT, поэтому масштабируются заранее или с запасом; а метрика CPU в момент прогрева завышена, что вызывает лишнее масштабирование — его гасят окном стабилизации behavior.scaleUp.

Liveness-проба должна проверять всё, от чего зависит сервис, — базу, брокер, внешние API.

Liveness перезапускает под, а перезапуск не чинит базу. В демо liveness на проверку базы перезапустила все три пода 2–3 раза за 30 секунд сбоя. Зависимости проверяют в readiness, которая только убирает под из трафика: так поды пережили сбой без перезапусков.

  • Лимит памяти — на весь процесс: при MaxRAMPercentage=100 — OOMKilled без следов, при 75 — OutOfMemoryError в логе.
  • Requests памяти = limits; лимит CPU даёт throttling, число CPU для JVM — от лимита.
  • Readiness — получать ли трафик; liveness — только то, что лечит перезапуск: liveness на базу дала 2–3 перезапуска за 30 с.
  • Startup probe для медленного старта; группы health в Actuator.
  • preStop-пауза + graceful shutdown + maxUnavailable 0: ошибок при выкатке 7 → 1.

На собеседовании

Чем liveness отличается от readiness и startup probe?

Readiness — готов ли под принимать трафик: провал убирает его из endpoints Service. Liveness — жив ли процесс: провал перезапускает контейнер. Startup — закончился ли старт: пока она не прошла, liveness не проверяется. Liveness проверяет только то, что исправит перезапуск; внешние зависимости — в readiness.

  • Liveness на базу при её сбое перезапускает все поды: в демо 2–3 перезапуска за 30 с, потом CrashLoopBackOff.
  • Actuator: группы liveness и readiness.
  • Тайм-ауты проб — меньше пауз GC, иначе ложные перезапуски.
Что не так с этими пробами? 
livenessProbe:
  httpGet: { path: /actuator/health, port: 8080 }   # включает db, redis, kafka
  initialDelaySeconds: 10
  timeoutSeconds: 1
  failureThreshold: 1
# приложение стартует 40-60 секунд

Liveness на общий health включает внешние зависимости: сбой Redis или базы перезапустит все поды. Старт 40–60 секунд при начальной задержке 10 и одном провале — под убьют до старта, и он уйдёт в CrashLoopBackOff. Тайм-аут 1 секунда с порогом 1 — одна долгая пауза GC перезапускает под. Нужно: liveness на /actuator/health/liveness, startup probe с бюджетом на старт, порог 3 и тайм-аут больше типичных пауз, зависимости — в readiness.

Как настроить память JVM в Kubernetes?

Лимит контейнера покрывает весь процесс: heap, метаспейс, стеки, JIT, прямые буферы. Heap задают долей от лимита — -XX:MaxRAMPercentage около 70–75 %, а не жёстким -Xmx, не связанным с лимитом. Requests памяти равны limits. При превышении лимита ядро убивает процесс (OOMKilled), а при нехватке heap JVM бросает OutOfMemoryError.

  • Native Memory Tracking показывает не-heap; потоки и прямые буферы — частые причины роста.
  • HeapDumpOnOutOfMemoryError в том, который переживёт перезапуск.
  • Лимит CPU — throttling; ActiveProcessorCount при необходимости.

Почему при деплое бывают ошибки и как сделать выкатку без потерь?

При удалении пода SIGTERM и удаление из маршрутизации происходят параллельно; если приложение сразу закрывает порт, запросы, уже направленные к нему, падают. Нужны preStop-пауза на несколько секунд, graceful shutdown в приложении, terminationGracePeriodSeconds с запасом, maxUnavailable 0 и readiness-проба, чтобы новые поды получали трафик только готовыми.

  • В демо: 7 ошибок без preStop, 1 с паузой.
  • java как PID 1, иначе SIGTERM не дойдёт до приложения.
  • Долгие соединения и потребители Kafka тоже завершать корректно.
