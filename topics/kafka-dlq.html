Kafka: Retries & DLQ

Одно сообщение останавливает партицию

Сервис кешбэка читает топик payments. Продюсер выкатил баг, и в одном событии не оказалось суммы: обработчик бросает NullPointerException. Что дальше?

Kafka не подтверждает сообщения по одному — консьюмер двигает позицию в партиции. Пока сообщение 42 не обработано, позиция стоит на нём, и всё, что за ним, ждёт. Посмотри, что происходит по умолчанию в Spring Kafka и что меняет DLQ:

Два плохих исхода без настройки — партиция стоит или сообщение теряется. DLQ (dead letter queue, в Kafka — dead letter topic, DLT) даёт третий: отложить сообщение, которое не получается обработать, и не держать из-за него остальные.

Повторять стоит не всё

Прежде чем настраивать повторы, раздели ошибки на два вида. От этого зависит, помогут ли повторы вообще.

ВременнаяПостоянная
ПримерыТаймаут HTTP, 503 от соседнего сервиса, deadlock в БД, база перезапускаетсяСообщение не десериализуется, нет обязательного поля, нарушено бизнес-правило, баг в коде

Spring Kafka часть постоянных ошибок распознаёт сам. DeserializationException, MessageConversionException, ConversionException, MethodArgumentResolutionException, NoSuchMethodException и ClassCastException он не повторяет, а сразу отдаёт в DLT. Свои постоянные ошибки, например ошибку валидации, добавляют в этот список сами.

Чем больше повторов, тем надёжнее.

Для постоянной ошибки каждый повтор — время, пока партиция стоит. А частые повторы к упавшему соседнему сервису добивают его и мешают ему подняться. Повторы нужны с паузой, ограничением и только для временных ошибок.

Повтор на месте и DLT

Самая частая настройка: несколько повторов на месте с растущей паузой, потом DLT. В Spring Boot достаточно объявить бин обработчика ошибок, и он подключится ко всем @KafkaListener:

@Bean
DefaultErrorHandler kafkaErrorHandler(KafkaTemplate<Object, Object> template) {
    // после неудачных попыток — в топик payments-dlt, в ту же партицию
    var recoverer = new DeadLetterPublishingRecoverer(template);

    var backOff = new ExponentialBackOffWithMaxRetries(3);   // три повтора: через 1 с, 2 с, 4 с
    backOff.setInitialInterval(1_000);
    backOff.setMultiplier(2.0);

    var handler = new DefaultErrorHandler(recoverer, backOff);
    handler.addNotRetryableExceptions(ValidationException.class);   // сразу в DLT
    return handler;
}

Что важно в этой схеме:

  • Порядок сохраняется. Пока запись повторяется, следующие записи партиции ждут. Для событий одного счёта, где порядок важен, это правильное поведение.
  • Паузы должны быть короткими. Всё время повторов партиция стоит. Если паузы длиннее max.poll.interval.ms (по умолчанию 5 минут), брокер решит, что консьюмер завис, и запустит rebalance. Для длинных пауз в Spring Kafka есть ContainerPausingBackOffHandler: он ставит контейнер на паузу, но продолжает общаться с брокером.
  • DLT по умолчанию называется <топик>-dlt и получает запись в ту же партицию, что у оригинала. Значит, партиций в DLT должно быть не меньше, чем в основном топике, — создай его заранее.
  • В заголовках записи — вся история. Класс и текст исключения, стектрейс, исходные топик, партиция, offset и группа: kafka_dlt-exception-message, kafka_dlt-original-offset и другие константы KafkaHeaders.DLT_*.

DefaultErrorHandler без настроек защищает от потери сообщений.

Он повторяет запись 10 раз без пауз, а потом только логирует её и коммитит offset дальше. Без DeadLetterPublishingRecoverer запись после этого нигде не хранится.

Повторы без остановки: retry-топики

Если соседний сервис лежит минут десять, повторять на месте нельзя: партиция встанет на всё это время. Тогда запись после ошибки перекладывают в отдельный топик с задержкой и читают её оттуда позже, а основная партиция продолжает работу.

@RetryableTopic(attempts = "3")               // попытка в основном топике и две в retry-топиках
@KafkaListener(topics = "payments", groupId = "cashback")
public void onPayment(PaymentEvent event) {
    cashback.accrue(event);
}

@DltHandler
public void onDeadLetter(PaymentEvent event) {
    alerts.cashbackFailed(event.paymentId());   // попытки кончились — сообщить людям
}

Задержки настраиваются в той же аннотации или через RetryTopicConfigurationBuilder. Главная цена — порядок. Возврат, который пришёл после списания, может обработаться раньше него, если списание ушло в retry-топик. Поэтому retry-топики подходят, когда события независимы: уведомления, начисление кешбэка, выгрузки.

DLQ — не корзина

Сообщение в DLT — не решённая проблема, а отложенная. Если туда никто не смотрит, это та же потеря, только дороже: топик растёт, а клиенты ждут кешбэк. Нужен процесс:

  1. Алерт на появление записей в DLT или на их количество за период. Один случай — баг в данных, сотни — баг в коде или упавшая зависимость.
  2. Разбор. Заголовки DLT-записи говорят, что упало и где лежит оригинал. Читать их можно отдельным консьюмером или утилитой.
  3. Исправление. Чинят код или данные. Иногда запись правильно выбросить — тогда это решение, и его стоит записать.
  4. Повторная отправка. Запись публикуют обратно в основной топик — утилитой, админкой или отдельным консьюмером DLT, который включают по команде.
@KafkaListener(topics = "payments-dlt", groupId = "payments-dlt-monitor")
public void onDeadLetter(ConsumerRecord<String, String> rec) {
    Header error = rec.headers().lastHeader(KafkaHeaders.DLT_EXCEPTION_MESSAGE);
    log.warn("DLT key={} error={}", rec.key(),
            error == null ? "?" : new String(error.value(), StandardCharsets.UTF_8));
    metrics.counter("payments.dlt").increment();
}

Повторная отправка — это та же запись второй раз, и в конце партиции. Поэтому консьюмер должен быть идемпотентным: хранить id обработанных платежей или делать операции, которые не страшно повторить. Без этого исправление ошибки легко превращается в двойное начисление.

Если сообщение даже не читается

Когда запись не десериализуется, исключение возникает при чтении, ещё до вызова обработчика, и обработчик ошибок её не видит. Чтобы такие записи тоже попадали в DLT, десериализатор оборачивают в ErrorHandlingDeserializer: он ловит ошибку и передаёт её дальше как DeserializationException, которую обработчик сразу отправит в DLT.

Под капотом: как DefaultErrorHandler повторяет запись

Консьюмер получает из poll() пачку записей. Если обработчик падает, например, на четвёртой, Spring Kafka коммитит offset трёх обработанных и делает seek на упавшую запись в её партиции и на первые необработанные — в остальных. Следующий poll() вернёт их снова, и упавшая запись придёт на повтор. Счётчик попыток хранится в памяти обработчика, поэтому после рестарта или rebalance отсчёт начнётся заново.

С версии 2.9 можно отключить seek (seekAfterError = false): контейнер сам держит необработанные записи и повторно отдаёт их обработчику без нового запроса к брокеру.

  • Kafka двигает позицию, а не подтверждает сообщения по одному: необработанная запись держит всю партицию.
  • Spring Kafka по умолчанию повторяет 10 раз без пауз, потом логирует и пропускает — это потеря.
  • Временные ошибки повторяй с паузой, постоянные — сразу в DLT.
  • Повтор на месте сохраняет порядок, но останавливает партицию. Retry-топики не останавливают, но ломают порядок.
  • DLT нужен процесс: алерт, разбор, исправление, повторная отправка. А консьюмер должен выдерживать повторы.

На собеседовании

Что такое DLQ и зачем она нужна?

DLQ, dead letter queue, — отдельная очередь, а в Kafka отдельный топик, куда откладывают сообщения, которые не получилось обработать. В Kafka это особенно важно: консьюмер двигает позицию в партиции, а не подтверждает сообщения по одному, поэтому одно ядовитое сообщение останавливает всю партицию, либо его приходится пропустить и потерять.

Обычно делают так: временные ошибки повторяют несколько раз с растущей паузой, постоянные — не повторяют. Если не помогло, запись с причиной ошибки уходит в DLT, а партиция едет дальше. На DLT ставят алерт, разбирают причину и после исправления отправляют записи обратно в основной топик.

  • В Spring Kafka это DefaultErrorHandler с DeadLetterPublishingRecoverer. По умолчанию без recoverer он повторяет 10 раз без пауз, потом логирует и пропускает запись — фактически теряет её.
  • DLT создают заранее с числом партиций не меньше, чем у основного топика: recoverer по умолчанию пишет в ту же партицию.
  • Повторная отправка кладёт запись в конец партиции, так что консьюмер должен быть идемпотентным и терпеть изменённый порядок.
Обработчик всегда падает на одной записи. Spring Kafka, DefaultErrorHandler без настроек. Сколько раз вызовется обработчик и что будет потом?

10 раз: первая попытка и 9 повторов (FixedBackOff(0, 9)), подряд, без пауз. Потом recoverer по умолчанию запишет запись в лог с уровнем ERROR, offset закоммитится, и консьюмер пойдёт дальше. Сообщение останется только в логе.

Что делать с сообщением, которое не десериализуется?

Обернуть десериализатор в ErrorHandlingDeserializer. Без него исключение возникает при чтении, до обработчика, и запись не может ни обработаться, ни попасть в DLT. С ним ошибка превращается в DeserializationException, которую DefaultErrorHandler не повторяет и сразу отдаёт recoverer.

Как повторять обработку и не нарушить порядок сообщений?

Повторять на месте: DefaultErrorHandler с короткой растущей паузой и DLT в конце. Пока запись повторяется, следующие записи партиции ждут, поэтому порядок сохраняется, но растёт lag. Это подходит, когда события одного ключа зависят друг от друга, например списание и возврат по одному счёту.

Если внешний сервис может лежать долго, повторы на месте остановят партицию на всё это время. Тогда используют retry-топики — @RetryableTopic: запись уходит в отдельный топик с задержкой, а партиция продолжает работу. Порядок при этом ломается, поэтому так делают только для независимых событий.

  • Сумма пауз на месте должна укладываться в max.poll.interval.ms, иначе консьюмера выкинут из группы. Для длинных пауз есть ContainerPausingBackOffHandler.
  • Компромисс для упорядоченных событий: при ошибке откладывать не одну запись, а все последующие записи того же ключа. Встроенного решения нет, это пишут сами — например, храня «заблокированные» ключи в БД.
Почему нельзя просто поставить 30 повторов с паузой по минуте?

Партиция будет стоять до получаса, а лимит max.poll.interval.ms по умолчанию — 5 минут: брокер решит, что консьюмер завис, и отдаст партицию другому. Тот начнёт повторы заново, и так по кругу. Длинное ожидание — это retry-топики или пауза контейнера, а не длинный backoff в потоке консьюмера.

Как вернуть сообщения из DLQ в обработку?

Сначала понять причину: заголовки DLT-записи содержат исключение и координаты оригинала. Потом исправить код или данные и опубликовать записи обратно в основной топик — утилитой, админкой или консьюмером DLT, который включают по команде. Возвращённая запись ляжет в конец партиции с новым offset.

Главное условие — идемпотентный консьюмер. Запись может обработаться второй раз, если часть работы была сделана до ошибки, и уже не в исходном порядке. Поэтому консьюмер хранит id обработанных сообщений или делает операции, которые безопасно повторить.

Что не так с этой повторной отправкой? 
@KafkaListener(topics = "payments-dlt", groupId = "dlt-replayer")
public void replay(ConsumerRecord<String, String> rec) {
    kafkaTemplate.send("payments", rec.value());
}
  • Работает всегда, а не по команде: запись, которая падает из-за бага, по кругу летит payments → DLT → payments.
  • Потерян ключ: send без ключа кладёт запись в случайную партицию, и порядок по счёту ломается окончательно. Нужно send("payments", rec.key(), rec.value()).
  • Не перенесены заголовки: трассировка и метаданные пропадут.
  • Нет учёта: неизвестно, какие записи вернули, сколько раз и кто это решил.
