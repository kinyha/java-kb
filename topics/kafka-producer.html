Kafka: Producer

Продюсер Kafka не отправляет каждое сообщение отдельно: send() кладёт запись в буфер, а фоновый поток собирает батчи по партициям и отправляет их брокерам. Партицию выбирает ключ — хеш ключа по модулю числа партиций, — поэтому события одного платежа идут в одну партицию и сохраняют порядок. linger.ms и batch.size решают, сколько ждать наполнения батча. acks определяет, чьего подтверждения ждать: никого, лидера или всех синхронных реплик. Идемпотентный продюсер, включённый по умолчанию, нумерует батчи, и брокер отбрасывает повторы и не даёт ретраям переставить сообщения.

События платежа пришли в обратном порядке, а Kafka получала тысячу запросов на тысячу сообщений

Сервис платежей публикует события в топик payments. Сверка видит возврат раньше списания у одного платежа: события ушли без ключа и попали в разные партиции. Мониторинг брокеров показывает почти по запросу на каждое сообщение, хотя сообщения маленькие. А после отключения одного брокера часть событий пропала, хотя send() не бросал исключений.

Все три истории — про настройки и устройство продюсера. Что такое топик, партиция и смещение, разобрано в Basics, отправка через KafkaTemplate — в Kafka in Spring, реплики и ISR — в Replication. Демо ProducerDemo.java работает с кластером из трёх брокеров Kafka 4.3 в Docker (KRaft) через kafka-clients 4.3.1; топики на 6 партиций с тремя репликами.

send() кладёт запись в буфер, а отправляет фоновый поток

Вызов producer.send(record) сериализует ключ и значение, выбирает партицию и добавляет запись в батч этой партиции в общем буфере (buffer.memory, 32 МБ по умолчанию). Метод сразу возвращает Future. Отдельный поток Sender забирает готовые батчи, группирует их по брокерам-лидерам и отправляет одним запросом на брокер. Результат приходит в callback или в Future.

Отсюда несколько следствий. Ошибка сети не придёт из send() — только в callback; код, который не смотрит на результат, теряет сообщения молча, как в истории выше. Если брокеры недоступны и буфер заполнился, send() блокируется до max.block.ms (60 секунд) — поток HTTP-запроса зависает на отправке события. А delivery.timeout.ms ограничивает всё время доставки с повторами: после него запись отбрасывается с ошибкой в callback.

== defaults: acks=-1 enable.idempotence=true max.in.flight=5 linger.ms=5 delivery.timeout.ms=120000

Это умолчания kafka-clients 4.3: acks=-1 — то же, что all, идемпотентность включена, до 5 запросов в полёте на соединение, 2 минуты на доставку. linger.ms по умолчанию 5 мс начиная с Kafka 4.0; раньше был 0.

Ключ выбирает партицию, а без ключа партицию держат, пока не заполнится батч

for (String key : List.of("p-1", "p-2", "p-3", "p-1", "p-2", "p-1"))
    p.send(new ProducerRecord<>("payments", key, "event")).get();
for (int i = 0; i < 6; i++)
    p.send(new ProducerRecord<>("payments", null, "no-key-" + i));
== key -> partition: {p-1=[4, 4, 4], p-2=[4, 4], p-3=[1]}
== null key, sent together: partitions [0, 0, 0, 0, 0, 0]

Для записи с ключом партиция — murmur2(key) mod число_партиций. Все события p-1 попали в партицию 4, и консьюмер этой партиции прочитает их в порядке отправки. p-2 тоже в 4 — совпадение по модулю, а не правило. Порядок есть только внутри партиции, поэтому ключ выбирают по сущности, для которой важен порядок: id платежа, счёта, клиента.

Без ключа продюсер использует «липкий» партиционер: держит одну партицию, пока не заполнится батч, и только потом переключается. Все шесть записей ушли в партицию 0 одним батчем. Так батчи получаются полнее, чем при старом распределении по кругу, где каждая запись шла в свою партицию. Встроенный партиционер также учитывает загрузку брокеров и реже выбирает медленные.

Две ловушки. Горячий ключ — крупный магазин, через который идёт половина платежей, — перегружает одну партицию, и добавление партиций не помогает: все его события всё равно в одной. И изменение числа партиций меняет отображение ключей: после увеличения с 6 до 12 новые события p-1 могут попасть в другую партицию, чем старые, и порядок между ними нарушится. Поэтому число партиций выбирают с запасом заранее.

linger.ms превращает поток мелких записей в батчи

Батч отправляется, когда он заполнен до batch.size (16 КБ) или когда истёк linger.ms. При высокой нагрузке батчи заполняются сами. При умеренной — каждое сообщение уходит почти отдельным запросом, если продюсер не подождёт. Демо отправляет 1000 сообщений по 200 байт с темпом около 5000 в секунду:

== linger.ms=0  1000 records -> produce requests 904, avg batch 290 bytes
== linger.ms=5  1000 records -> produce requests 165, avg batch 746 bytes
== linger.ms=50 1000 records -> produce requests 25, avg batch 5975 bytes

Без ожидания продюсер сделал 904 запроса на 1000 сообщений; от запуска к запуску это число гуляет — в другом прогоне было 599, — потому что зависит от того, успеет ли следующая запись догнать отправку предыдущей. Пять миллисекунд по умолчанию сократили запросы в пять с половиной раз, 50 мс — в 36 раз. Меньше запросов — меньше нагрузка на сеть и брокеры, лучше сжатие (compression.type сжимает батч целиком), но каждое сообщение ждёт до linger.ms дольше. Для потока событий задержка в десятки миллисекунд обычно незаметна; для синхронного запроса, где пользователь ждёт подтверждения отправки, её учитывают.

acks определяет, чьего подтверждения ждёт продюсер

== acks=0   partition=0 offset=-1
== acks=1   partition=0 offset=7
== acks=all partition=0 offset=8

С acks=0 продюсер не ждёт ответа вовсе: смещение неизвестно (-1), и если брокер не принял запись, никто об этом не узнает. С acks=1 подтверждает лидер партиции, записав сообщение к себе; если лидер упадёт до того, как реплики скопируют запись, она потеряется при выборе нового лидера. С acks=all лидер ждёт, пока запись получат все реплики из ISR, и вместе с min.insync.replicas=2 это значит: подтверждённая запись есть хотя бы на двух брокерах. Как это работает и что происходит, когда ISR сокращается, показано в Replication.

Идемпотентный продюсер не даёт ретраям создать дубли и переставить батчи

Продюсер повторяет батч, если не получил ответ: запрос мог потеряться, а мог дойти, и потерялся только ответ. Без защиты это даёт две проблемы. Повтор батча, который уже записан, — дубль. А при нескольких запросах в полёте повтор первого батча может записаться после второго — порядок нарушен:

Идемпотентный продюсер включён по умолчанию с Kafka 3.0 и требует acks=all, повторов и не больше 5 запросов в полёте — ровно умолчания из демо. Он защищает от дублей и перестановок, вызванных повторами внутри одной сессии продюсера. Если сервис перезапустился и отправил событие заново, у нового экземпляра другой producer id, и брокер не узнает дубль. От этого защищают транзакционный продюсер с постоянным transactional.id или идемпотентный консьюмер, о чём — в Delivery Semantics.

Раз send() не бросил исключение, сообщение записано в Kafka.

send() только кладёт запись в буфер и возвращает Future. Ошибки доставки приходят в callback, а если его нет и Future никто не проверяет, сообщение теряется молча. Надёжная отправка проверяет результат: callback с логированием и обработкой или get() там, где нужно знать, что запись принята.

  • send() асинхронный: буфер, фоновый поток, ошибки — в callback; при полном буфере блокируется до max.block.ms.
  • Ключ → murmur2 mod партиций: порядок по ключу; без ключа — липкий партиционер; смена числа партиций ломает отображение.
  • linger.ms при умеренном потоке: 0 мс — 904 запроса на 1000 сообщений, 50 мс — 25. В Kafka 4 по умолчанию 5 мс.
  • acks=0 не знает смещения, acks=1 теряет при падении лидера, acks=all с min.insync.replicas=2 держит запись на двух брокерах.
  • Идемпотентный продюсер по умолчанию: producer id и номера последовательности убирают дубли и перестановки от повторов.

На собеседовании

Как Kafka гарантирует порядок сообщений и как продюсер может его нарушить?

Порядок гарантируется только внутри партиции. Продюсер выбирает партицию по хешу ключа, поэтому все сообщения с одним ключом попадают в одну партицию и читаются в порядке записи. Сообщения без ключа или с разными ключами порядка между собой не имеют.

Нарушить порядок может повтор при нескольких запросах в полёте: первый батч повторяется после второго. Идемпотентный продюсер, включённый по умолчанию, нумерует батчи, и брокер не принимает их не по порядку.

  • Без идемпотентности порядок требует max.in.flight.requests.per.connection=1.
  • Увеличение числа партиций меняет отображение ключей, и новые события ключа могут уйти в другую партицию.
  • Горячий ключ ограничен пропускной способностью одной партиции.

Что означают acks=0, 1 и all?

acks=0 — продюсер не ждёт ответа, возможна незаметная потеря. acks=1 — подтверждает лидер после записи к себе; если лидер упадёт до репликации, запись потеряется. acks=all — лидер ждёт все реплики из ISR; вместе с min.insync.replicas=2 подтверждённая запись есть минимум на двух брокерах.

  • acks=all — умолчание с Kafka 3.0 и условие идемпотентного продюсера.
  • Если ISR меньше min.insync.replicas, запись с acks=all отклоняется с NotEnoughReplicas.
  • Задержка acks=all определяется самой медленной репликой в ISR.
Почему события иногда пропадают? 
public void publish(Payment p) {
    producer.send(new ProducerRecord<>("payments", p.toJson()));
}
// props: acks=1, retries=0

Результат send() никто не проверяет, поэтому ошибки доставки теряются молча. acks=1 и отключённые повторы теряют записи при смене лидера и сетевых сбоях. Ключа нет, поэтому события одного платежа попадают в разные партиции без порядка. Нужны ключ id платежа, acks=all с идемпотентностью и повторами по умолчанию и callback, который обрабатывает ошибку.

Как продюсер группирует сообщения и как настроить батчи?

send() кладёт запись в батч её партиции; батч отправляется, когда достиг batch.size или прошло linger.ms. Небольшой linger.ms при умеренном потоке резко сокращает число запросов: в демо 50 мс дали 25 запросов вместо 904 на 1000 сообщений, ценой задержки до 50 мс. Сжатие применяется к батчу целиком, поэтому крупные батчи сжимаются лучше.

  • В Kafka 4 linger.ms по умолчанию 5 мс; раньше 0.
  • Липкий партиционер для записей без ключа заполняет одну партицию до конца батча.
  • buffer.memory и max.block.ms определяют, что будет при недоступном кластере.
  • Apache Kafka: Producer Configs — основа урока: acks, linger.ms, batch.size, идемпотентность, таймауты.
  • KIP-480: Sticky Partitioner и KIP-794 — партиционирование без ключа.
  • KIP-679 — acks=all и идемпотентность по умолчанию.
  • KIP-1030 — новые умолчания Kafka 4.0, включая linger.ms=5.
