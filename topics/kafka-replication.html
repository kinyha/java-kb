Kafka: Replication

У каждой партиции один лидер и несколько последователей, которые копируют его лог. ISR — реплики, которые не отстают; лидер выбирается только из них. Запись с acks=all подтверждается, когда её получили все реплики ISR, а min.insync.replicas запрещает запись, если ISR стал слишком мал. Стандарт надёжности — три реплики и min.insync.replicas=2: кластер переживает потерю брокера без потерь и без остановки записи. Unclean leader election отдаёт лидерство отставшей реплике, чтобы партиция ожила, и стирает подтверждённые записи. Метаданными кластера в Kafka 4 управляет кворум контроллеров KRaft.

Брокер ушёл на обслуживание, второй упал — и одна команда потеряла события, а другая перестала писать

В кластере из трёх брокеров один вывели на обновление ОС, и в этот момент второй упал по памяти. Сервис платежей начал получать таймауты на каждую отправку, и очередь событий в нём росла. В соседней команде, где топики были настроены «для скорости», запись продолжалась, но после возвращения брокеров часть подтверждённых событий исчезла.

Это две стороны одного выбора между доступностью и сохранностью, который в Kafka задают три настройки: фактор репликации, min.insync.replicas и unclean.leader.election.enable. Тема показывает, как они работают на живом кластере. Устройство брокеров и партиций — в Basics, acks со стороны продюсера — в Producer. Демо ReplicationDemo.java и UncleanDemo.java работают с Kafka 4.3 в Docker — три контроллера KRaft и три брокера — и сами останавливают и запускают контейнеры брокеров.

ISR — реплики, которые успевают за лидером; лидер выбирается только из них

Продюсеры и консьюмеры работают только с лидером партиции. Последователи постоянно запрашивают у лидера новые записи, как консьюмеры. Реплика входит в ISR (in-sync replicas), пока не отстаёт дольше replica.lag.time.max.ms (30 секунд). Отставшую или остановленную реплику лидер исключает из ISR через контроллер, а догнавшую возвращает.

Консьюмеры читают только до high watermark — смещения, до которого запись есть на всех репликах ISR. Поэтому запись, которую видел хоть один консьюмер, переживёт смену лидера на любую реплику из ISR. Настройки min.insync.replicas=2 и фактор репликации 3 задают ровно это: каждая подтверждённая запись есть минимум на двух брокерах.

new NewTopic("ledger-rep", 1, (short) 3).configs(Map.of("min.insync.replicas", "2"));
== all brokers up: leader=2 replicas=[1, 2, 3] isr=[1, 2, 3]
   acks=all -> ok, offset 0
-- docker stop kafka-1
== broker 1 stopped: leader=2 replicas=[1, 2, 3] isr=[2, 3]
   acks=all -> ok, offset 1

Брокер 1 остановлен, ISR сократился до двух реплик, и запись с acks=all по-прежнему проходит: двух реплик достаточно. Это и есть смысл схемы 3/2 — плановое обслуживание или падение одного брокера незаметно для продюсеров.

Когда ISR меньше min.insync.replicas, Kafka отказывает в записи, а не рискует данными

-- docker stop kafka-3
== broker 3 stopped too: leader=2 replicas=[1, 2, 3] isr=[2]
   acks=all -> TimeoutException
   acks=all, retries=0 -> NotEnoughReplicasException
   acks=1   -> ok, offset 2

Остался один брокер, ISR из одной реплики меньше min.insync.replicas=2, и лидер отклоняет запись с acks=all ошибкой NotEnoughReplicasException. Ошибка повторяемая, поэтому обычный продюсер молча повторяет её до delivery.timeout.ms и в итоге отдаёт TimeoutException — именно эти таймауты видел сервис платежей. Запись с acks=1 при этом проходит: min.insync.replicas проверяется только для acks=all, и такая запись лежит на единственном брокере.

Это осознанный выбор Kafka: лучше остановить запись, чем подтвердить данные, которые исчезнут при следующем сбое. Партиция остаётся доступной для чтения. Когда брокеры вернулись, они догнали лидера и вернулись в ISR:

-- docker start kafka-1
-- docker start kafka-3
== both brokers back: leader=2 replicas=[1, 2, 3] isr=[1, 2, 3]
-- docker stop kafka-2
== leader 2 stopped: leader=3 replicas=[1, 2, 3] isr=[1, 3]
   acks=all -> ok, offset 3
-- docker start kafka-2
== broker 2 back: leader=3 replicas=[1, 2, 3] isr=[1, 2, 3]
   records readable: 4

Остановка лидера привела к выборам: контроллер назначил лидером брокер 3 из ISR, и запись продолжилась. Все четыре подтверждённые записи на месте, включая записанную с acks=1: брокеры вернулись к живому лидеру и скопировали её. Продюсеры и консьюмеры узнают о новом лидере из метаданных и переключаются сами.

Unclean leader election оживляет партицию ценой подтверждённых записей

Если все реплики ISR недоступны, у партиции нет лидера, и она недоступна ни для записи, ни для чтения, пока одна из реплик ISR не вернётся. unclean.leader.election.enable=true разрешает выбрать лидером реплику не из ISR — отставшую. Партиция оживает сразу, но всё, чего у этой реплики не было, теряется. Демо создаёт топик «для скорости» — min.insync.replicas=1 и unclean-выборы включены:

== start: leader=3 isr=[1, 2, 3]
   ack before-1 offset 0
   ack before-2 offset 1
   ack before-3 offset 2
-- docker stop kafka-1
-- docker stop kafka-2
   ack only-leader-1 offset 3
   ack only-leader-2 offset 4
   ack only-leader-3 offset 5
-- docker stop kafka-3
-- docker start kafka-1
-- docker start kafka-2
== old leader down, followers back: leader=1 isr=[1, 2]
-- docker start kafka-3
== old leader back: leader=1 isr=[1, 2, 3]
   acknowledged 6, readable: [before-1, before-2, before-3]

Продюсер получил шесть подтверждений, а прочитать можно три. Потерю создали две настройки вместе: min.insync.replicas=1 позволил подтверждать записи, которые есть на одном брокере, а unclean-выборы отдали лидерство брокеру без них. По умолчанию unclean-выборы выключены, и правильная реакция на такую аварию — ждать возвращения реплики из ISR. Включают их для данных, где доступность важнее полноты: метрики, логи.

Метаданными управляет кворум контроллеров KRaft, и его потеря замораживает кластер

Кто лидер партиции, кто в ISR, какие есть топики — всё это метаданные кластера. С Kafka 4.0 их хранит только KRaft: несколько контроллеров ведут журнал метаданных по протоколу Raft, а ZooKeeper удалён. Один контроллер активный, остальные — горячий резерв; изменение метаданных принимается, когда его записало большинство контроллеров. Три контроллера переживают потерю одного, пять — двух. Брокеры получают метаданные из журнала контроллеров и регулярно шлют им heartbeat.

Первый вариант демо держал роли брокера и контроллера на тех же трёх узлах. Остановка двух брокеров заодно останавливала два контроллера из трёх: кворум метаданных терялся, оставшийся брокер не мог подтвердить своё состояние и перестал принимать запись даже с min.insync.replicas=1. Поэтому в проде контроллеры выносят на отдельные узлы, а в демо их три отдельных контейнера. Совмещённый режим годится для разработки и маленьких кластеров. Как работает кворум и выборы лидера в Raft, разобрано в Consensus & Time.

С фактором репликации 3 данные в Kafka не теряются.

Три копии защищают только подтверждённое на нескольких из них. С acks=1 или min.insync.replicas=1 запись может существовать на одном брокере, и unclean-выборы её сотрут: в демо из шести подтверждённых записей осталось три. Надёжность даёт сочетание RF=3, min.insync.replicas=2, acks=all и выключенных unclean-выборов.

  • Лидер обслуживает партицию, последователи копируют; ISR — не отставшие реплики, лидер выбирается из них.
  • Консьюмеры читают до high watermark — записанного на всех репликах ISR.
  • RF=3 и min.insync.replicas=2: потеря одного брокера незаметна; двух — NotEnoughReplicas для acks=all, а продюсер видит TimeoutException.
  • acks=1 и min.insync=1 подтверждают записи на одном брокере; unclean-выборы стирают их: 6 подтверждено, 3 прочитано.
  • KRaft: кворум контроллеров хранит метаданные; контроллеры выносят на отдельные узлы.

На собеседовании

Что такое ISR и min.insync.replicas?

ISR — набор реплик партиции, которые не отстают от лидера дольше replica.lag.time.max.ms; новый лидер выбирается только из них. min.insync.replicas — минимальный размер ISR, при котором лидер принимает запись с acks=all; если реплик меньше, запись отклоняется с NotEnoughReplicas. Схема RF=3, min.insync.replicas=2 переживает потерю одного брокера без остановки записи и без потерь.

  • NotEnoughReplicas повторяемая: продюсер повторяет её до delivery.timeout.ms и отдаёт TimeoutException.
  • min.insync.replicas не действует на acks=1 и acks=0.
  • Консьюмеры читают до high watermark, поэтому видимая запись переживёт смену лидера в пределах ISR.

Что такое unclean leader election и когда его включать?

Выбор лидером реплики не из ISR, когда все реплики ISR недоступны. Партиция становится доступной сразу, но записи, которых не было у новой реплики, теряются, а старый лидер при возвращении обрезает лог. По умолчанию выключено; включают для данных, где доступность важнее полноты, — метрики, логи.

  • Опасно в сочетании с acks=1 или min.insync.replicas=1: подтверждённые записи живут на одном брокере.
  • Без unclean-выборов партиция остаётся без лидера, пока не вернётся реплика из ISR.
Чем опасна эта конфигурация топика платежей? 
replication.factor=3
min.insync.replicas=1
unclean.leader.election.enable=true
# продюсер: acks=1

Подтверждённая запись может существовать только на лидере: acks=1 не ждёт реплик, а min.insync.replicas=1 позволил бы и acks=all подтверждать при ISR из одного брокера. При падении лидера unclean-выборы отдадут лидерство отставшей реплике, и подтверждённые события пропадут, как в демо. Для платежей нужны acks=all, min.insync.replicas=2 и выключенные unclean-выборы.

Что такое KRaft и чем он заменил ZooKeeper?

KRaft — режим, в котором метаданные кластера хранит кворум контроллеров Kafka в журнале по протоколу Raft, без внешнего ZooKeeper. Один контроллер активный, изменения подтверждает большинство. С Kafka 4.0 ZooKeeper не поддерживается. Брокеры получают метаданные из журнала контроллеров и шлют им heartbeat.

  • Три контроллера переживают потерю одного; потеря кворума замораживает изменения метаданных и выборы лидеров.
  • В проде контроллеры выносят на отдельные узлы, чтобы падение брокеров не роняло кворум.
