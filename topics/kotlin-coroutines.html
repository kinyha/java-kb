Kotlin Coroutines

Сервис платежей почти всё время ждёт сеть. Корутина позволяет написать ожидание как обычный последовательный код, но во время ожидания не держать поток. Компилятор превращает suspend-функцию в колбэк с сохранённым состоянием, а библиотека kotlinx.coroutines решает, на каком потоке продолжить и кого отменить, если что-то упало. Дальше — как это устроено в байткоде и что из этого следует для отмены, блокирующих вызовов, ошибок и выбора между корутинами, виртуальными потоками и Reactor.

Авторизация ждёт сеть, а поток простаивает

Перед списанием платёжный сервис спрашивает антифрод (≈100 мс) и сервис лимитов (≈80 мс). Считает он мало — в основном ждёт ответы. В модели «поток на запрос» каждый ждущий запрос держит платформенный поток со своим стеком. Пул Tomcat в 200 потоков — это 200 одновременных авторизаций, остальные стоят в очереди, хотя CPU свободен.

Java-ответ до виртуальных потоков — CompletableFuture. Поток не держится, но логика переезжает в колбэки, а отмену и контекст нужно протаскивать руками:

CompletableFuture<Boolean> authorize(String id, long amount) {
    return fraudScore(id).thenCombine(limitLeft(id),
            (score, limit) -> score < 9 && amount <= limit);   // бизнес-правило внутри колбэка
}

В Kotlin тот же код пишется последовательно, а работает как колбэки. Оба вызова идут параллельно, и ни один поток не ждёт:

suspend fun fraudScore(id: String): Int { delay(100); return id.length % 10 }   // сетевой вызов, 100 мс
suspend fun limitLeft(id: String): Long { delay(80); return 50_000 }           // ещё один, 80 мс

suspend fun authorize(id: String, amount: Long): Boolean = coroutineScope {
    val score = async { fraudScore(id) }                  // запустить и не ждать
    val limit = async { limitLeft(id) }
    score.await() < 9 && amount <= limit.await()          // ждать здесь, без блокировки потока
}

fun main() = runBlocking {                                // один поток: main
    val threads = ConcurrentHashMap.newKeySet<String>()
    val start = System.nanoTime()
    val results = (1..10_000).map { i ->
        async {
            threads += Thread.currentThread().name
            authorize("p-$i", 1_000)
        }
    }.awaitAll()
    val ms = (System.nanoTime() - start) / 1_000_000
    println("authorizations=${results.size} threads=$threads elapsed=${ms} ms")
}
authorizations=10000 threads=[main] elapsed=176 ms

10 000 авторизаций, каждая ждёт около 100 мс, завершились за 176 мс на одном потоке main. Точное время зависит от машины, порядок — нет: последовательно это заняло бы 10 000 × 100 мс ≈ 17 минут, а параллельно на платформенных потоках потребовало бы 10 000 потоков. delay не спит: он приостанавливает корутину и отдаёт поток другим. Как функция может «остановиться на середине» и продолжить потом — следующий шаг.

suspend-функция — это колбэк, который написал компилятор

Слово suspend меняет сигнатуру метода. Компилятор добавляет последний параметр Continuation — объект «что делать дальше», а тип результата делает Object: функция возвращает либо значение, либо маркер COROUTINE_SUSPENDED. Это continuation-passing style, тот же колбэк, что в CompletableFuture, только его пишет компилятор.

$ javap -p pay.mechanism.MechanismKt 'pay.mechanism.MechanismKt$authorize$1'
public static final java.lang.Object authorize(java.lang.String, long, kotlin.coroutines.Continuation<? super java.lang.String>);

final class MechanismKt$authorize$1 extends kotlin.coroutines.jvm.internal.ContinuationImpl {
  java.lang.Object L$0;        # сохранённая ссылочная переменная (id)
  long J$0;                    # сохранённый long (amount)
  java.lang.Object result;     # значение, с которым функцию возобновили
  int label;                   # на какой точке приостановки остановились
  public final java.lang.Object invokeSuspend(java.lang.Object);   # повторный вход в authorize
}

Тело функции становится state machine. Каждая точка приостановки — вызов другой suspend-функции — получает номер label. Перед вызовом функция сохраняет живые локальные переменные в поля continuation и записывает следующий label. Если вызванная функция вернула COROUTINE_SUSPENDED, authorize возвращает его же, и так по всей цепочке до самого низа: стек раскручивается, поток свободен. Когда результат готов, кто-то вызывает continuation.resume(value). Это снова входит в authorize, та по label прыгает в нужное место и восстанавливает переменные из полей:

Механизм работает без библиотеки kotlinx.coroutines, на одной stdlib. Функция suspendCoroutine отдаёт continuation «сетевому клиенту», а suspend-функцию можно вызвать как обычный JVM-метод, передав continuation руками:

var pending: Continuation<Int>? = null           // «сетевой клиент» держит continuation до ответа

suspend fun fraudScore(id: String): Int = suspendCoroutine { cont ->
    pending = cont                               // запомнили, куда вернуть результат
    println("  fraud request sent for $id")
}                                                // лямбда вернулась — функция приостановлена

suspend fun authorize(id: String, amount: Long): String {
    println("  authorize: start, label 0")
    val score = fraudScore(id)                   // точка приостановки
    println("  authorize: resumed with score=$score on ${Thread.currentThread().name}")
    return if (score < 10 && amount <= 50_000) "APPROVED" else "DECLINED"
}

fun main() {
    val done = Continuation<String>(EmptyCoroutineContext) { println("  completion: $it") }
    val raw = ::authorize as (String, Long, Continuation<String>) -> Any?   // так метод видит JVM
    val result = raw("p-1", 1_000, done)
    println("1. authorize returned: $result")    // не String, а маркер приостановки
    println("2. thread is free, doing other work")
    val responder = Thread({ pending!!.resume(3) }, "fraud-response")   // ответ пришёл в другом потоке
    responder.start(); responder.join()
    println("3. main: end")
}

  fraud request sent for p-1
1. authorize returned: COROUTINE_SUSPENDED
2. thread is free, doing other work
  authorize: resumed with score=3 on fraud-response
  completion: Success(APPROVED)

Корутина — не поток, а этот объект-continuation плюс цепочка таких же объектов вызывающих функций. Пока она ждёт, она занимает несколько сотен байт в heap, а не стек потока. Возобновить её может любой поток — здесь это fraud-response. В kotlinx.coroutines на каком потоке продолжить решает dispatcher (шаг 4).

Корутина — лёгкий поток со своим маленьким стеком.

Своего стека у корутины нет. Пока она выполняется, она использует стек текущего потока. При приостановке её переменные переезжают в поля continuation, а кадры снимаются со стека. Поэтому приостановиться можно только внутри suspend-функции: обычная функция не умеет сохранить себя и вернуть маркер.

Под капотом: «окрашенные» функции и повторное использование continuation

Вызвать suspend-функцию из обычной нельзя: нечего передать в параметр Continuation. Функции делятся на два «цвета», и переход между ними — явный мост: runBlocking блокирует текущий поток до результата, launch и async запускают корутину в scope, future { } отдаёт её Java-коду как CompletableFuture. Виртуальные потоки этой проблемы не имеют: там приостанавливается сама JVM.

Первые строки байткода authorize проверяют, не пришёл ли в параметре уже свой объект authorize$1 с выставленным старшим битом label. Так функция отличает повторный вход через invokeSuspend от нового вызова и не создаёт второй объект. Новый объект выделяется на каждый вызов, который может приостановиться; если приостановки не случилось, он быстро становится мусором и убирается при minor GC.

Structured concurrency: корутины живут в дереве, ошибки и отмена идут по нему

С колбэками легко потерять задачу. CompletableFuture, запущенный и забытый, работает дальше, даже если запрос уже отменён, а его исключение никто не увидит. kotlinx.coroutines так не даёт: launch и async — функции на CoroutineScope, и новая корутина становится ребёнком Job этого scope.

У дерева три правила. Родитель не завершается, пока не завершились все дети. Ошибка ребёнка отменяет родителя, а родитель отменяет остальных детей. Отмена родителя отменяет всех детей. coroutineScope { } создаёт такой scope внутри suspend-функции и возвращает результат только после всех детей.

suspend fun authorize(id: String): Long = coroutineScope {
    val fraud = async {
        try { delay(200); log("fraud done"); 3L }
        catch (e: CancellationException) { log("fraud cancelled"); throw e }   // отмену пробрасываем дальше
    }
    val limits = async<Long> {
        delay(50)
        throw IllegalStateException("limits service 503")
    }
    launch {
        try { delay(300); log("fx rate cached") }
        finally { log("fx finally, active=$isActive") }                         // finally выполняется и при отмене
    }
    fraud.await() + limits.await()
}

try { authorize("p-1") }
catch (e: IllegalStateException) { log("caller got: ${e.message}") }
  50 ms  fraud cancelled
  60 ms  fx finally, active=false
  60 ms  caller got: limits service 503

fraud не дождался своих 200 мс, а fx выполнил finally с active=false. Отмена приходит как CancellationException в точке приостановки, поэтому finally и use закрывают ресурсы как обычно. Вызывающий получил исходную ошибку limits, а не CancellationException. Времена в выводе усечены до 10 мс и плавают на 10–20 мс от запуска к запуску.

Отмена кооперативная

Отмена — это флаг в Job. Корутина узнаёт о нём только в точке приостановки (delay, await, withContext, yield) или при явной проверке: ensureActive(), isActive. Код без приостановок — CPU-цикл или блокирующий вызов — отмену не замечает:

fun processBatch() = Thread.sleep(40)                         // блокирующая пачка сверки

suspend fun reconcile(cooperative: Boolean, done: AtomicInteger) {
    repeat(10) {
        if (cooperative) currentCoroutineContext().ensureActive()   // точка проверки отмены
        processBatch()
        done.incrementAndGet()
    }
}

for (cooperative in listOf(false, true)) {
    val done = AtomicInteger()
    val result = withContext(Dispatchers.Default) {
        withTimeoutOrNull(100) { reconcile(cooperative, done); "finished" }
    }
    println("cooperative=$cooperative result=$result batches=${done.get()}")
}
cooperative=false result=finished batches=10
cooperative=true result=null batches=3

Без проверок таймаут в 100 мс ничего не прервал: все 10 пачек по 40 мс выполнились, и вернулся даже результат finished. С ensureActive() перед каждой пачкой работа остановилась после третьей: проверка на 80 мс прошла, на 120 мс — нет. Для блокирующих вызовов, которые реагируют на interrupt, есть runInterruptible { }: он превращает отмену в Thread.interrupt().

catch (e: Exception) вокруг suspend-вызова — безопасная защита от падений.

Отмена — это исключение CancellationException, и такой catch её проглатывает: корутина продолжает работать после отмены. Её надо пробрасывать: ловить конкретные исключения или ставить catch (e: CancellationException) { throw e } выше общего. Та же ловушка у runCatching.

suspend fun pollStatuses() {
    repeat(5) { i ->
        try { delay(50); log("poll $i") }
        catch (e: Exception) { log("poll $i: swallowed ${e::class.simpleName}") }   // глотает и отмену
    }
}

val job = launch { pollStatuses(); log("pollStatuses returned normally") }
delay(120)
log("cancel"); job.cancelAndJoin()
  50 ms  poll 0

 130 ms  poll 2: swallowed JobCancellationException
 140 ms  poll 3: swallowed JobCancellationException
 140 ms  poll 4: swallowed JobCancellationException

После отмены каждый delay сразу бросает исключение, catch его съедает, и цикл крутится дальше. Здесь он короткий; бесконечный цикл опроса после такой «отмены» не остановится никогда и будет жечь CPU. Учти ещё одну деталь: CancellationException в JVM наследует IllegalStateException, поэтому catch (e: IllegalStateException) тоже ловит отмену.

Dispatcher выбирает поток для продолжения, а блокирующий вызов занимает его целиком

Continuation можно возобновить на любом потоке. Какой выбрать, решает CoroutineDispatcher из контекста корутины: при каждом старте и resume он ставит продолжение в свою очередь, и его подхватывает один из потоков.

withContext(Dispatchers.IO) { repo.findById(id) } переносит блок на другой dispatcher и возвращает результат обратно. Опыт показывает, зачем. Ночная сверка обрабатывает 100 платежей, каждый — один вызов на 100 мс. После сотни задач запускается быстрая health-check-корутина, и мы меряем, сколько она ждала старта:

fun jdbcCall() = Thread.sleep(100)                 // блокирующий вызов: JDBC, старый HTTP-клиент
suspend fun httpCall() = delay(100)                // неблокирующий: поток отпускается

suspend fun batch(name: String, ctx: CoroutineContext, call: suspend () -> Unit) = coroutineScope {
    repeat(100) { launch(ctx) { threads += Thread.currentThread().threadId(); call() } }
    val h = System.nanoTime()
    launch(ctx) { healthLatency = (System.nanoTime() - h) / 1_000_000 }.join()   // встаёт в ту же очередь
    …                                                                             // ждём всех и печатаем
}

18 потоков Default и 100 задач по 100 мс сна — это 6 волн, около 640 мс. Хуже всего health-check: он встал в очередь за 82 спящими задачами и ждал 530 мс. В сервисе на месте health-check окажется обработка HTTP-запросов, и сервис «зависнет» при свободном CPU. На IO 64 потока, две волны, 220 мс. С delay потоки не заняты, и всё заняло около 100 мс. Числа сняты на машине с 18 CPU: волн будет ceil(100 / CPU), а соотношение останется тем же.

  • Блокирующий код — в withContext(Dispatchers.IO), а лучше заменить неблокирующим клиентом.
  • IO общий на всё приложение. Медленному клиенту дают свой лимит: Dispatchers.IO.limitedParallelism(10), тогда он не съест 64 потока.
  • Dispatcher на виртуальных потоках выдержал 100 блокирующих вызовов за 115 мс без пула: каждый вызов получил свой виртуальный поток. Это мост к шагу 7.

suspend-функция не блокирует поток.

suspend только разрешает приостановку. Если внутри Thread.sleep, JDBC или synchronized с долгим ожиданием, поток заблокирован так же, как в Java. Неблокирующей функцию делают точки приостановки внутри: delay, await, вызовы неблокирующего клиента.

runBlocking блокирует поток, пока корутина не завершится. Он нужен в main и как мост в старом коде; в тестах — runTest с виртуальным временем. runBlocking в обработчике запроса или внутри корутины на Default держит поток пула и при нагрузке приводит к тому же голоданию, что на схеме, а иногда к взаимной блокировке.

async, SupervisorJob и обработчик: исключение уходит родителю, а не в await

async возвращает Deferred, аналог Future. Ошибка хранится в нём до await, но внутри обычного scope она ещё и сразу отменяет родителя. Поэтому забытый await ошибку не спрячет:

suspend fun send(channel: String): String {
    delay(if (channel == "sms") 20L else 50L)
    if (channel == "sms") throw IllegalStateException("sms gateway down")
    return "$channel sent"
}

try {
    coroutineScope {
        val email = async { send("email") }
        val sms = async { send("sms") }        // await для sms не вызываем
        println("1. email: ${email.await()}")
    }
} catch (e: IllegalStateException) { println("1. scope failed: ${e.message}") }
1. scope failed: sms gateway down

Email так и не отправился: SMS упал через 20 мс и отменил весь scope. Для одной авторизации это правильно — без лимитов нет смысла ждать антифрод. Но уведомления независимы, и падение SMS не должно отменять email. Для этого есть supervisorScope и SupervisorJob: ошибка ребёнка не идёт вверх, родитель и соседи живут, а ошибку async-ребёнка ты получишь в его await:

supervisorScope {
    val jobs = listOf("email", "sms", "push").associateWith { async { send(it) } }
    for ((channel, d) in jobs) {
        try { println("2. ${d.await()}") }
        catch (e: IllegalStateException) { println("2. $channel failed: ${e.message}") }
    }
}
2. email sent
2. sms failed: sms gateway down
2. push sent

Третий случай — долгоживущий scope сервиса, из которого запускают фоновую работу: отправку чеков, прогрев кеша. У launch нет await, ошибку некому вернуть. Её получает CoroutineExceptionHandler из контекста, а без него — обработчик потока, то есть лог. Важнее другое — какой Job у самого scope:

val handler = CoroutineExceptionHandler { _, e -> println("   handler: ${e.message}") }
for ((name, job) in listOf("Job()" to Job(), "SupervisorJob()" to SupervisorJob())) {
    val scope = CoroutineScope(job + Dispatchers.Default + handler)
    scope.launch { send("sms") }.join()                      // первая задача падает
    val second = scope.launch { println("   second receipt: ${send("email")}") }
    second.join()
    println("3. $name: scope active=${scope.isActive}, second cancelled=${second.isCancelled}")
}
   handler: sms gateway down
3. Job(): scope active=false, second cancelled=true
   handler: sms gateway down
   second receipt: email sent
3. SupervisorJob(): scope active=true, second cancelled=false

С обычным Job() первая упавшая задача отменила весь scope. Второй чек не отправился, и ошибки об этом нет: launch в отменённом scope просто создаёт уже отменённую корутину. С SupervisorJob() scope пережил ошибку. Поэтому scope компонента, который живёт всё время работы сервиса, строят на SupervisorJob и отменяют при остановке компонента.

Где упалоЧто происходит

async в supervisorScopeСоседи живут, исключение — в await

Handler вызывается только для корневой корутины scope или прямого ребёнка supervisor. У вложенных launch ошибка идёт родителю, и handler в их контексте не срабатывает. GlobalScope — scope без родителя и без отмены: запущенное в нём живёт, пока не закончится само, поэтому в сервисе он не нужен.

Flow — холодный поток значений, где backpressure — это приостановка

suspend-функция возвращает одно значение. Для последовательности — выгрузка платежей, статусы, события — есть Flow. flow { } — рецепт: код внутри не выполняется, пока кто-то не вызовет collect, и выполняется заново на каждый collect. Это холодный поток, как Flux без подписки в Reactor.

fun paymentsFromDb(): Flow<String> = flow {
    println("   SELECT * FROM payments")
    emit("p-1"); emit("p-2")
}

val payments = paymentsFromDb()
println("1. flow created, nothing executed")
payments.collect { println("   a: $it") }
payments.collect { println("   b: $it") }
1. flow created, nothing executed
   SELECT * FROM payments
   a: p-1
   a: p-2
   SELECT * FROM payments
   b: p-1
   b: p-2

Запрос выполнился дважды — по разу на подписчика. emit — suspend-функция. Без буфера она приостанавливается, пока collector обрабатывает значение, и источник с потребителем идут по очереди в одной корутине. Это и есть backpressure: быстрый источник не завалит медленного потребителя, ему просто не дадут продолжить. buffer(), conflate() и collectLatest меняют это поведение явно.

flow { for (i in 1..3) { println("   emit $i"); emit(i) } }
    .collect { println("   process $it"); delay(10) }
   emit 1
   process 1
   emit 2
   process 2
   emit 3
   process 3

Горячие потоки: StateFlow и SharedFlow

Горячий поток живёт независимо от подписчиков. StateFlow хранит одно текущее значение: новый подписчик сразу получает его, одинаковые значения не рассылаются, а быстрые обновления сливаются — подписчик видит последнее, а не историю. SharedFlow — поток событий: без replay событие, отправленное без подписчиков, теряется.

val status = MutableStateFlow("NEW")
val ui = launch { status.collect { println("2. ui sees $it") } }
yield()                                       // дать подписчику стартовать
status.value = "AUTHORIZED"                   // без приостановки между присваиваниями
status.value = "CAPTURED"
status.value = "CAPTURED"                     // то же значение — не событие
yield()
ui.cancel()

val events = MutableSharedFlow<String>()
events.emit("refund r-1")                     // подписчиков нет: emit вернулся сразу
val audit = launch { events.collect { println("3. audit got $it") } }
yield()
events.emit("refund r-2")
yield()
audit.cancel()
2. ui sees NEW
2. ui sees CAPTURED
3. audit got refund r-2

AUTHORIZED подписчик не увидел: два присваивания прошли без приостановки, и к моменту, когда collector получил поток, значение уже было CAPTURED. Для состояния так и надо: экрану или health-индикатору нужен текущий статус. Для событий «деньги списаны» — нет. Такие события идут через SharedFlow с буфером, а если их нельзя терять при падении процесса — через брокер и outbox: Flow живёт в памяти одного процесса.

В backend Flow встречается на краях сервиса. Spring WebFlux принимает его как тело ответа для стрима JSON и SSE, а Spring Data отдаёт из корутинных репозиториев. Подробнее про Spring — в теме Kotlin with Spring & JPA.

Корутины, virtual threads или Reactor: выбор зависит от стека сервиса

Все три решают одну задачу: не держать поток, пока запрос ждёт сеть. Различаются тем, кто приостанавливает выполнение и как выглядит код.

  • Spring MVC, JDBC, Java-команда — virtual threads: переписывать ничего не нужно. На JDK 21 помни про pinning при блокировке внутри synchronized; в JDK 24 его убрал JEP 491.
  • Kotlin-команда, несколько параллельных вызовов в одном запросе, таймауты и отмены — корутины. coroutineScope и async дают то, что в Java пока только в превью StructuredTaskScope.
  • Потоки данных, сложная композиция, уже WebFlux — Reactor, а Kotlin-код поверх него пишут suspend-функциями и Flow через kotlinx-coroutines-reactor (awaitSingle, asFlow, mono { }).

Мосты между мирами есть в обе стороны. CompletableFuture из Java-клиента приостанавливает корутину через await(), и отмена корутины отменяет future. Обратно future { } отдаёт корутину Java-коду. Оба моста входят в kotlinx-coroutines-core:

fun bankApi(id: String, latencyMs: Long): CompletableFuture<String> =      // Java-клиент банка
    CompletableFuture.supplyAsync { Thread.sleep(latencyMs); "bank-ok:$id" }

suspend fun charge(id: String, latencyMs: Long = 50): String =
    bankApi(id, latencyMs).await()                 // приостановка без блокировки потока

val appScope = CoroutineScope(SupervisorJob() + Dispatchers.Default)
fun chargeForJava(id: String): CompletableFuture<String> = appScope.future { charge(id) }   // для Java-кода

println(charge("p-1"))
println(chargeForJava("p-2").get())
val slow = bankApi("p-3", 500)
val r = withTimeoutOrNull(50) { slow.await() }     // отмена корутины отменяет и future
println("timeout result=$r future cancelled=${slow.isCancelled}")
bank-ok:p-1
bank-ok:p-2
timeout result=null future cancelled=true

Отменённая future не прерывает поток внутри supplyAsync: CompletableFuture.cancel не делает interrupt, и сон продолжится. Отменяется ожидание, а не работа. Корутины можно запускать и на виртуальных потоках через asCoroutineDispatcher(), как в шаге 4: блокирующий вызов внутри тогда не держит пул. Это удобный переходный вариант для Kotlin-сервиса со старыми JDBC-репозиториями.

  • suspend-функция получает параметр Continuation и превращается в state machine: переменные переезжают в поля, label запоминает точку, COROUTINE_SUSPENDED освобождает поток.
  • Корутина — объект в heap, а не поток. Продолжить её может любой поток; какой — выбирает dispatcher.
  • Structured concurrency: дети живут внутри scope, ошибка ребёнка отменяет соседей и уходит родителю. SupervisorJob делает детей независимыми.
  • Отмена кооперативна: без точек приостановки или ensureActive() код её не заметит, а catch (e: Exception) её проглотит.
  • Блокирующий вызов в корутине блокирует поток пула. Его место — Dispatchers.IO с лимитом или виртуальные потоки.
  • Flow холодный и выполняется на каждый collect; StateFlow хранит текущее значение, SharedFlow раздаёт события тем, кто подписан.

На собеседовании

Как работает suspend-функция и чем корутина отличается от потока?

Компилятор добавляет suspend-функции параметр Continuation и превращает её тело в state machine. Перед каждой точкой приостановки живые переменные сохраняются в поля continuation, а в label записывается номер точки. Если вызванная функция вернула COROUTINE_SUSPENDED, функция возвращает его же, стек раскручивается, и поток свободен. Когда результат готов, resume снова входит в функцию, и она продолжает с нужного label.

Поэтому корутина — не поток, а объект в heap с цепочкой continuation. Тысячи ожидающих корутин занимают мегабайты heap, а не тысячи стеков. Пока корутина выполняется, она занимает поток, и на каком потоке её продолжить, решает dispatcher.

  • Корутины stackless: приостановиться можно только в suspend-функции, функции «окрашены». Виртуальные потоки stackful: JVM сохраняет весь стек, и приостанавливается любой блокирующий вызов.
  • Механизм — часть языка и stdlib (suspendCoroutine, startCoroutine); kotlinx.coroutines добавляет поверх него Job, dispatcher, scope и Flow.
  • Continuation можно возобновить из любого потока, поэтому ThreadLocal и MDC не переезжают сами: для них есть ThreadContextElement и MDCContext.
Можно ли вызвать suspend-функцию из Java?

Технически да: это обычный метод с последним параметром Continuation, и он может вернуть COROUTINE_SUSPENDED. Но реализовать continuation руками неудобно и легко ошибиться. На практике Kotlin-модуль отдаёт Java-коду обёртку: scope.future { charge(id) } возвращает CompletableFuture, а runBlocking подходит только там, где блокировка потока допустима.

Что такое structured concurrency и как отменяются корутины?

Каждая корутина запускается в scope и становится ребёнком его Job. Родитель не завершается, пока не завершены дети. Ошибка ребёнка отменяет родителя и всех соседей, отмена родителя отменяет детей. Поэтому корутина не может «утечь»: если запрос упал или отменён, всё, что он запустил, остановится, а ошибка дойдёт до вызывающего.

Отмена кооперативная. Это флаг в Job, и корутина узнаёт о нём в точке приостановки — там прилетает CancellationException — или при проверке ensureActive(). Блокирующий вызов или CPU-цикл без проверок отмену не заметит. CancellationException нельзя глотать общим catch (e: Exception), иначе корутина продолжит работать.

  • coroutineScope отменяет всех при первой ошибке, supervisorScope и SupervisorJob — нет: ошибка async-ребёнка приходит в await, ошибка launch — в CoroutineExceptionHandler.
  • Долгоживущий scope сервиса строят на SupervisorJob: с обычным Job первая ошибка отменит scope насовсем, и новые launch молча не стартуют.
  • Для очистки после отмены, где нужна приостановка, используют withContext(NonCancellable) в finally. Блокирующий вызов, реагирующий на interrupt, оборачивают в runInterruptible.
Что выведет этот код? 
fun processBatch() = Thread.sleep(40)

suspend fun reconcile(done: AtomicInteger) {
    repeat(10) { processBatch(); done.incrementAndGet() }
}

fun main() = runBlocking {
    val done = AtomicInteger()
    val result = withContext(Dispatchers.Default) {
        withTimeoutOrNull(100) { reconcile(done); "finished" }
    }
    println("result=$result batches=${done.get()}")
}
result=finished batches=10

Таймаут выставил флаг отмены на 100 мс, но внутри нет ни одной точки приостановки, и код его не проверял. Все 10 пачек выполнились, и блок вернул результат. С currentCoroutineContext().ensureActive() перед каждой пачкой результат был бы null после трёх пачек.

Что не так с этим фоновым обработчиком? 
@Component
class ReceiptSender(private val client: ReceiptClient) {
    private val scope = CoroutineScope(Job() + Dispatchers.IO)

    fun onPaid(paymentId: String) {
        scope.launch {
            while (true) {
                try {
                    client.send(paymentId)          // suspend
                    break
                } catch (e: Exception) {
                    delay(1_000)                    // повторяем через секунду
                }
            }
        }
    }
}
  • catch (e: Exception) глотает CancellationException. Когда scope отменят — а при остановке бина его нужно отменять, — цикл не выйдет: delay сразу бросит отмену, catch её съест, и так по кругу, нагружая CPU.
  • Scope на Job(): если исключение вылетит из launch, scope отменится насовсем, и следующие чеки молча не уйдут. Нужен SupervisorJob().
  • Scope никто не отменяет при остановке бина. Нужен @PreDestroy fun stop() = scope.cancel(), а повторы — с лимитом попыток. Чек, который нельзя потерять при рестарте, лучше отправлять через outbox, а не из памяти.

Что будет, если вызвать JDBC внутри корутины?

JDBC блокирует поток, и пометка suspend этого не меняет. Если корутина выполняется на Dispatchers.Default, поток пула спит, а там их всего по числу CPU. При десятке одновременных запросов все потоки Default уснут, и встанет любая другая работа на нём, даже короткая. В опыте с 18 потоками health-check ждал 530 мс.

Поэтому блокирующий вызов оборачиваю в withContext(Dispatchers.IO): там до 64 потоков, и они общие с Default. Для тяжёлого клиента задаю отдельный лимит через limitedParallelism, а если можно — беру неблокирующий драйвер (R2DBC) или запускаю корутины на виртуальных потоках.

  • IO ограничен 64 потоками на всё приложение. Пул соединений к базе обычно меньше, так что реальный лимит параллельности задаёт он: лишние корутины ждут соединение, держа поток IO.
  • runBlocking в обработчике запроса или внутри корутины даёт то же голодание пула, а в худшем случае взаимную блокировку.
  • В WebFlux блокирующий вызов на потоке event loop останавливает обработку всех соединений этого потока; BlockHound ловит такие вызовы в тестах.

Корутины, virtual threads или Reactor — что выберешь для нового сервиса?

Все три не держат поток, пока запрос ждёт сеть. Virtual threads делают это в JVM: код остаётся блокирующим, JDBC и старые клиенты работают как есть. Корутины делают это в компиляторе: код последовательный, но приостанавливается только в suspend-точках, зато есть structured concurrency с отменой и таймаутами. Reactor — библиотека операторов над потоками данных с backpressure.

Для Spring MVC с JDBC и Java-командой выберу виртуальные потоки: это одна настройка. Для Kotlin-сервиса с параллельными вызовами внутри запроса — корутины. Для потоковой обработки и уже существующего WebFlux — Reactor, а Kotlin-код поверх него — на suspend-функциях и Flow.

  • Корутины и виртуальные потоки совместимы: Executors.newVirtualThreadPerTaskExecutor().asCoroutineDispatcher() делает блокирующие вызовы внутри корутин дешёвыми.
  • У виртуальных потоков на JDK 21 есть pinning при блокировке в synchronized, исправленный в JDK 24 (JEP 491); у корутин аналог — блокирующий вызов на Default.
  • Мосты: CompletableFuture.await() и future { } в kotlinx-coroutines-core, awaitSingle, mono { } и asFlow в kotlinx-coroutines-reactor. Отмена корутины отменяет future, но не прерывает поток внутри него.
  • Kotlin docs: Coroutines guide — основа урока: разделы Cancellation and timeouts, Coroutine context and dispatchers, Coroutine exceptions handling, Asynchronous Flow.
  • KEEP: Kotlin Coroutines — дизайн-документ: continuation-passing style, state machine, COROUTINE_SUSPENDED, почему корутины stackless.
  • kotlinx.coroutines API: Dispatchers — размеры Default и IO, limitedParallelism.
  • Roman Elizarov, «Structured concurrency» (2018) и «Blocking threads, suspending coroutines» — почему у корутин есть родитель и чем suspend отличается от блокировки.
  • JEP 444: Virtual Threads и JEP 491 — с чем сравнивать корутины в Java 21+.
