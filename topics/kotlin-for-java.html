Kotlin for Java Devs

Kotlin-код после компиляции — обычные Java-классы: поля, геттеры, static-методы и проверки на null, которые за тебя написал компилятор. Гарантии языка действуют, пока компилятор видит весь код. На стыке с Java, в рефлексии и в прокси фреймворков работает уже байткод, а в нём нет ни nullability, ни read-only коллекций. Поэтому про любую конструкцию Kotlin полезно спрашивать: «во что она компилируется и как её увидит Java?». Все примеры ниже — с javap и запуском.

NPE в Kotlin-модуле, где null «не бывает»

Платёжный сервис написан на Java: ядро, репозитории, Spring. Новый модуль возвратов команда пишет на Kotlin: кода меньше, а null safety встроена в типы. В первую неделю в проде модуль падает с NullPointerException, хотя в нём нет ни одного !!.

Причина — старый Java-репозиторий. Для закрытого счёта он возвращает null, и в сигнатуре это никак не отмечено:

// Java, LegacyAccounts: аннотаций нет, null — часть поведения
public String findOwner(String accountId) {
    return accountId.startsWith("closed-") ? null : "Ivan Petrov";
}

В Kotlin-коде два почти одинаковых способа взять владельца. Оба компилируются без предупреждений:

fun ownerDeclared(repo: LegacyAccounts, id: String): Int {
    val owner: String = repo.findOwner(id)   // тип указан явно
    return owner.length
}

fun ownerInferred(repo: LegacyAccounts, id: String): Int {
    val owner = repo.findOwner(id)           // тип выведен компилятором
    println("  owner loaded")                // код идёт дальше
    return owner.length
}

// оба вызываем для счёта "closed-42"
declared:
  java.lang.NullPointerException: findOwner(...) must not be null
inferred:
  owner loaded
  java.lang.NullPointerException: Cannot invoke "String.length()" because "owner" is null

Первый вариант падает сразу на присваивании, и текст исключения написал не JDK, а Kotlin: findOwner(...) must not be null. Второй проходит дальше, печатает строку и падает на первом обращении. В реальном коде между этими точками может оказаться другой метод, очередь или кеш, и стек вызовов уже не покажет, откуда пришёл null.

Это главная мысль темы. Kotlin даёт гарантии на уровне компилятора, а выполняется тот же JVM-байткод, что и у Java. Поведение на стыке определяет то, что компилятор вставил в байткод: здесь — проверку в одном случае и её отсутствие в другом. Дальше разберём, что именно он генерирует для свойств, объектов, null-проверок, data class, extension- и inline-функций, и где его гарантии кончаются.

Kotlin-код — это обычные Java-классы, которые написал компилятор

Kotlin компилирует в те же .class-файлы. Java вызывает Kotlin и наоборот напрямую, без мостов и сериализации, а в одном Gradle-модуле можно держать оба языка. Но конструкции Kotlin не совпадают с Java один в один, и компилятор раскладывает их на привычные части. Возьмём класс платежа с типичным набором:

// Payment.kt
class Payment(
    val id: String,                       // val: private final поле + getId()
    var status: String = "NEW",           // var: поле + getStatus() + setStatus(); значение по умолчанию
) {
    val isFinal: Boolean                  // свойство без поля: только геттер
        get() = status == "PAID" || status == "DECLINED"

    companion object {                    // вложенный класс Payment.Companion + static-поле Companion
        const val MAX_AMOUNT = 1_000_000L // const: настоящая static final константа
        fun of(id: String) = Payment(id)  // метод экземпляра Companion, не static
        @JvmStatic fun draft(id: String) = Payment(id, "DRAFT")  // + static-мост в Payment
    }
}

object FeePolicy {                        // синглтон: static INSTANCE + private конструктор
    var percent = 15
    fun fee(amount: Long) = amount * percent / 1000
}

fun formatAmount(kopecks: Long) = "%d.%02d".format(kopecks / 100, kopecks % 100)  // top-level функция

Это объект-синглтон вложенного класса. Static в байткоде только поле-ссылка Companion, а методы компаньона — методы экземпляра. Поэтому компаньон может реализовать интерфейс и передаваться как значение, например как фабрика. Настоящие static-члены дают @JvmStatic, const и @JvmField.

Под капотом: как посмотреть байткод и что ещё генерирует компилятор

В IntelliJ IDEA: Tools → Kotlin → Show Kotlin Bytecode, кнопка Decompile показывает тот же класс как Java-код. Из консоли — javap -c -p по собранным классам, как здесь.

Внутри класса private-свойство без своих аксессоров читается прямо из поля, геттер не вызывается. У lateinit var поле получает видимость сеттера, то есть обычно public: в javap видно public java.lang.String gateway. Лямбды Kotlin 2.x по умолчанию компилирует через invokedynamic, как Java, а не отдельными классами. kotlinc без флагов собирает байткод Java 8 (major 52); в Gradle с jvmToolchain(21) jvmTarget будет 21, и это меняет байткод, например для sealed-классов (шаг 4).

Null safety — это типы при компиляции и проверки на границе

В Kotlin nullability — часть типа. String не может быть null, String? может. Вызвать owner.length у String? компилятор не даст. Нужна безопасная навигация ?., значение по умолчанию ?:, проверка if (owner != null), после которой тип сужается до String (smart cast), или !!. В байткоде оба типа — java.lang.String: это ограничения для компилятора, а не два разных класса.

Внутри Kotlin-кода этого хватает: компилятор видит все объявления. Сложности начинаются на границе, где он не знает правды. Направлений два.

Java вызывает Kotlin

javac не знает, что параметр Kotlin-функции не-null, и пропустит туда null. Поэтому в начало каждой не-private функции компилятор вставляет проверку параметров. Метод Receipts.line(owner: String, amount: Long) в байткоде:

public final java.lang.String line(java.lang.String, long);
   0: aload_1
   1: ldc           "owner"                          # имя параметра — для сообщения
   3: invokestatic  Intrinsics.checkNotNullParameter # null → NPE прямо на входе
   6: new           java/lang/StringBuilder          # дальше — тело функции
// Java: findOwner вернул null, и он уходит в Kotlin
String owner = new LegacyAccounts().findOwner("closed-7");
return receipts.line(owner, 1_500);
java.lang.NullPointerException: Parameter specified as non-null is null: method pay.Receipts.line, parameter owner

null останавливается на входе, а сообщение называет метод и параметр. У private-функций проверок нет: их вызывает только Kotlin-код того же класса, и компилятор уверен в аргументах. internal-функции проверяются: в байткоде они public.

Kotlin вызывает Java: platform types

Тип результата findOwner в Java ничем не помечен. Если бы Kotlin считал все Java-типы nullable, код утонул бы в ?. и !!, особенно с коллекциями: список из Java был бы List<String?>?. Поэтому тип из Java становится platform type, в сообщениях компилятора — String!. Это значит «не знаю, решай сам»: с таким значением можно обращаться и как со String, и как со String?.

Что случится дальше, зависит от того, куда ты положил значение. Это и есть разница двух функций из первого шага:

ownerDeclared:   val owner: String = repo.findOwner(id)
  14: invokevirtual LegacyAccounts.findOwner
  17: dup
  18: ldc           "findOwner(...)"                        # текст для сообщения
  20: invokestatic  Intrinsics.checkNotNullExpressionValue  # проверка при присваивании
  23: astore_2

ownerInferred:   val owner = repo.findOwner(id)
  14: invokevirtual LegacyAccounts.findOwner
  17: astore_2                                              # тип String!, проверки нет

Отсюда практическое правило: на границе с Java объявляй тип явно. String, если уверен, — тогда null остановится в месте вызова с понятным сообщением. String?, если не уверен, — тогда компилятор заставит его обработать. Элементы коллекций это правило не защищает: val ids: List<String> = javaList проверит только сам список, а null внутри него пройдёт.

Аннотации превращают platform type в обычный

Если Java-код размечен аннотациями nullability, Kotlin читает их, и platform type исчезает. Поддерживаются аннотации JetBrains, JSR-305, Android, Lombok и другие, но основной стандарт сейчас — JSpecify. @NullMarked на классе или пакете делает все типы не-null, @Nullable отмечает исключения. Начиная с Kotlin 2.1 несоответствие JSpecify-аннотациям — ошибка компиляции, а не предупреждение:

@NullMarked                                         // всё в классе не-null, кроме помеченного
public class Accounts {
    public @Nullable String findOwner(String accountId) { … }
    public String currency(String accountId) { return "RUB"; }
}
val owner: String = repo.findOwner(id)          // теперь это String?, а не String!
fun currencyOf(repo: Accounts): String? = repo.currency(null)   // параметр не-null по @NullMarked
$ kotlinc UseAccounts.kt Accounts.java -cp jspecify-1.0.0.jar
UseAccounts.kt:4:23: error: initializer type mismatch: expected 'String', actual 'String?'.
UseAccounts.kt:8:57: error: null cannot be a value of a non-null type 'String'.

Тот же null, что в первом шаге уронил прод, теперь останавливается при сборке. Spring Framework 7 и Spring Boot 4 размечены JSpecify, поэтому Kotlin видит null-контракты всего Spring API. Как это влияет на Kotlin-код со Spring — в теме Kotlin with Spring & JPA.

Где NPE создаёшь сам: !! и lateinit

!! — явное «я уверен, что не null». В байткоде это Intrinsics.checkNotNull: на null он бросает обычный java.lang.NullPointerException без сообщения. В тестах и там, где инвариант доказан, это нормально. В бизнес-коде лучше ?: throw AccountNotFound(id): исключение сразу объясняет причину.

lateinit var — не-null свойство, которое заполнят после конструктора: внедрение через поле, подготовка в @BeforeEach. В байткоде это обычное поле, до присваивания в нём null. Геттер проверяет поле и бросает собственное исключение с именем свойства. Работает только для var и не-примитивных типов; проверить заполненность можно через ::gateway.isInitialized.

repo.findOwner("closed-42")!!.length           // !! на platform type

class Checkout {
    lateinit var gateway: String               // заполнит DI-контейнер... если заполнит
    fun pay() = "via $gateway"
}
Checkout().pay()
!!:
  java.lang.NullPointerException: null
lateinit:
  kotlin.UninitializedPropertyAccessException: lateinit property gateway has not been initialized

null в первой строке — это e.message: у исключения от !! нет текста. В Spring lateinit почти не нужен: внедрение через конструктор даёт обычные val.

В Kotlin не бывает NullPointerException.

NPE не бывает там, где компилятор видит все типы. Он возникает на стыке с Java (platform types, Java передаёт null), от !!, от незаполненного lateinit со своим типом исключения и даже в чистом Kotlin: если open-метод вызван из конструктора базового класса, он видит ещё не присвоенные не-null поля наследника.

Под капотом: можно ли выключить проверки

Флаги -Xno-param-assertions и -Xno-call-assertions убирают проверки параметров и результатов Java-вызовов. Выигрыш почти нулевой: проверка — одно сравнение со ссылкой, и JIT её инлайнит. Потеря заметная: null снова уходит вглубь кода, как во втором пути на схеме. Без измеренной причины их не трогают.

data class похож на record, но равенство и копия устроены иначе

Платёжному сервису нужны значения: деньги, возвраты, ответы шлюза. В Java для них есть record, в Kotlin — data class. Компилятор генерирует equals, hashCode, toString, componentN и copy по свойствам первичного конструктора. Выглядит как record, но на трёх отличиях ловят и в проде, и на собеседовании.

data class Refund(val paymentId: String, var amount: Long) {  // var в data class разрешён
    var comment: String = ""                                     // тело класса: не входит в equals/hashCode/toString
}

val r = Refund("p-1", 500)
val sent = hashSetOf(r)
r.amount = 300                                // hashCode изменился, а объект лежит в старом бакете
println("contains=${r in sent} size=${sent.size}")

val a = Refund("p-2", 100).apply { comment = "клиент передумал" }
val b = Refund("p-2", 100).apply { comment = "двойное списание" }
println("equals=${a == b} $a")                // comment не участвует

val half = a.copy(amount = 50)                // copy: новый объект через первичный конструктор
println("$half comment='${half.comment}'")

val (id, amount) = half                       // componentN(): деструктуризация по позиции

Отдельно про copy и проверки в конструкторе:

Закрытая иерархия результатов: sealed и when

Ответ шлюза — «оплачен», «отклонён» или «таймаут». В Java 21 это sealed-интерфейс и switch с проверкой полноты (Sealed & Pattern Matching). В Kotlin то же самое через sealed и when. Все наследники sealed-типа обязаны лежать в том же модуле и пакете, поэтому компилятор знает их список. when-выражение по такому типу не требует else, а в каждой ветке значение уже приведено к нужному типу.

sealed interface PayResult
data class Paid(val txId: String) : PayResult
data class Declined(val reason: String) : PayResult
data object Timeout : PayResult                              // синглтон с читаемым toString

fun httpStatus(r: PayResult): Int = when (r) {               // без else: полноту проверит компилятор
    is Paid -> 200                                           // smart cast: r здесь уже Paid
    is Declined -> if (r.reason == "fraud") 403 else 402
    Timeout -> 504
}

listOf(Paid("tx-1"), Declined("fraud"), Declined("no money"), Timeout)
    .forEach { println("$it -> ${httpStatus(it)}") }
Paid(txId=tx-1) -> 200
Declined(reason=fraud) -> 403
Declined(reason=no money) -> 402
Timeout -> 504

Добавишь data class Pending — функция перестанет компилироваться: 'when' expression must be exhaustive. Add the 'is Pending' branch or an 'else' branch. Поэтому else в таком when вредит: он молча проглотит новый вариант.

В байткоде when — цепочка instanceof, а в конце стоит throw NoWhenBranchMatchedException на случай, которого компилятор не видел. Такой случай реален: при jvmTarget 1.8, а это умолчание у kotlinc, JVM ничего не знает о sealed, и Java-класс может реализовать интерфейс. С jvmTarget 17+ компилятор пишет в класс атрибут PermittedSubclasses, и чужой наследник не соберётся:

public class JavaRefund implements PayResult {           // Java «дописывает» вариант
    public static void main(String[] args) {
        System.out.println(SealedKt.httpStatus(new JavaRefund()));
    }
}

Extension и inline: static-вызов и копия тела, а не новая магия

Extension functions

Extension-функция вызывается как метод чужого класса: 10_000L.withFee(15). Сам класс Long не меняется. Компилятор делает обычный static-метод в классе файла, а получатель передаёт первым параметром. Отсюда всё поведение extension-функций:

open class Payment(val amount: Long) {
    fun describe() = "member"                       // метод класса
}
class CardPayment(amount: Long) : Payment(amount)

fun Payment.kind() = "payment"                      // static ExtensionsKt.kind(Payment)
fun CardPayment.kind() = "card"                     // static ExtensionsKt.kind(CardPayment): перегрузка
fun Payment.describe() = "extension"                // член с той же сигнатурой всегда выигрывает
fun Long.withFee(percentX10: Int): Long = this + this * percentX10 / 1000

val p: Payment = CardPayment(10_000)                // объявленный тип Payment, объект CardPayment
println(p.kind())
println((p as CardPayment).kind())
println(p.describe())
println(10_000L.withFee(15))
payment
card
member
10150
$ javap -p pay.ExtensionsKt
public final class pay.ExtensionsKt {
  public static final java.lang.String kind(pay.Payment);      # получатель — первый параметр
  public static final java.lang.String kind(pay.CardPayment);
  public static final java.lang.String describe(pay.Payment);  # есть, но Kotlin его не вызовет
  public static final long withFee(long, int);                 # из Java: ExtensionsKt.withFee(10000L, 15)
}

Выбор extension-функции статический: компилятор смотрит на объявленный тип Payment, как при перегрузке, а не на класс объекта. Полиморфизма здесь нет (как выбирается метод). Член класса всегда выигрывает у extension с той же сигнатурой; компилятор только предупреждает extension is shadowed by a member. И extension не видит private-членов: это внешняя функция.

В backend extension-функции хороши для преобразований и утилит над чужими типами: fun PaymentEntity.toDto(), fun BigDecimal.toKopecks(). Плохой знак — extension с бизнес-логикой своего же агрегата: правило размазывается по файлам, и его не найти в классе.

inline и reified

Функции вроде filter, map, forEach принимают лямбды. Для обычной функции лямбда — объект, и каждый вызов идёт через invoke. inline-функцию компилятор не вызывает, а копирует её тело вместе с телом лямбды в место вызова. Почти весь API коллекций Kotlin inline, поэтому events.filter { … } в байткоде — обычный цикл с ArrayList, без объекта лямбды.

Из копирования следуют две возможности. Первая — non-local return: return внутри лямбды forEach выходит из окружающей функции, потому что после встраивания это обычный return в её теле. Вторая — reified: в обычной generic-функции тип T стёрт (type erasure), а в копии тела компилятор подставляет конкретный класс.

sealed interface Event
data class PaymentEvent(val id: String) : Event
data class RefundEvent(val id: String) : Event

// reified: T известен в теле, потому что тело копируется в место вызова
inline fun <reified T : Event> List<Event>.only(): List<T> = filter { it is T }.map { it as T }

// Java-способ: тип передаётся явно, Class<T> — объект во время выполнения
fun <T : Event> List<Event>.onlyOf(type: Class<T>): List<T> = filter(type::isInstance).map(type::cast)

fun firstRefund(events: List<Event>): String {
    events.forEach {                                // forEach — inline-функция
        if (it is RefundEvent) return it.id         // non-local return: выход из firstRefund
    }
    return "none"
}

val events = listOf(PaymentEvent("p-1"), RefundEvent("r-1"), PaymentEvent("p-2"))
println(events.only<PaymentEvent>())
println(events.onlyOf(RefundEvent::class.java))
println(firstRefund(events))
[PaymentEvent(id=p-1), PaymentEvent(id=p-2)]
[RefundEvent(id=r-1)]
r-1
$ javap -c pay.InlineKt          # метод main(), фрагмент
 116: instanceof    pay/PaymentEvent        # тело only() встроено с конкретным классом
 265: ldc           pay/RefundEvent         # а onlyOf получает Class как аргумент
 267: invokestatic  onlyOf
$ javap -v pay.InlineKt | grep -A2 ' only('
    flags: (0x1019) ACC_PUBLIC, ACC_STATIC, ACC_FINAL, ACC_SYNTHETIC

У inline есть цена. Тело копируется в каждое место вызова, поэтому большая inline-функция раздувает байткод; смысл она имеет для небольших функций с параметрами-лямбдами. reified-функцию нельзя вызвать из Java: метод в классе есть, но помечен синтетическим, и javac его не видит. Если лямбду нужно сохранить в поле или передать дальше, её параметр помечают noinline. Если лямбда вызывается из другого контекста, например из другой лямбды или потока, — crossinline, и non-local return в ней запрещён.

Где гарантии Kotlin кончаются: read-only коллекции, final и стык с Java

Read-only не значит immutable

List в Kotlin — интерфейс без add и remove, MutableList — с ними. Но в байткоде оба — java.util.List: компилятор просто не показывает мутирующие методы. Объект за ссылкой обычно изменяемый ArrayList, и Java-код, получивший его, ничего о запрете не знает.

class FeeTable {
    private val fees = mutableListOf(150L, 200L)
    val view: List<Long> get() = fees              // наружу — List, но это тот же ArrayList
}

val table = FeeTable()
println(JavaLedger.tryAdd(table.view))          // Java: fees.add(99L)
println(table.view)                             // состояние FeeTable изменилось

val many: List<Long> = listOf(150L, 200L)       // vararg → Arrays.asList
println(many.javaClass.name + ": " + JavaLedger.trySet(many) + ", " + JavaLedger.tryAdd(many))

val one: List<Long> = listOf(150L)              // один элемент → Collections.singletonList
println(one.javaClass.name + ": " + JavaLedger.trySet(one))

println((table.view as MutableList<Long>).removeAll { it > 100 })  // каст из Kotlin тоже проходит
println(table.view)
add ok [150, 200, 99]
[150, 200, 99]
java.util.Arrays$ArrayList: set ok [0, 200], add failed: UnsupportedOperationException
java.util.Collections$SingletonList: set failed: UnsupportedOperationException
true
[99]

Обрати внимание на результаты listOf: с несколькими элементами это Arrays.asList, где set работает, а add нет; с одним — singletonList, где падает и set. Неизменяемость нужно делать явно: отдавать копию (toList()), оборачивать Collections.unmodifiableList или брать kotlinx.collections.immutable. И val items: List<Item> в data class не делает объект неизменяемым.

Классы и методы final по умолчанию

В Kotlin классы и методы final, пока не написан open. Это сознательное решение по совету Effective Java (item 19): наследование либо проектируют, либо запрещают. Для Java-кода это обычные ошибки компиляции:

class PaymentService { fun charge(amount: Long) = "charged $amount" }   // final класс

open class RefundService {
    open fun refund(amount: Long) = "refunded $amount"
    fun audit() = "audit"                   // метод final, хотя класс open
}
$ javac Subclasses.java                 # Java пытается наследоваться
Subclasses.java:8: error: cannot inherit from final PaymentService
Subclasses.java:5: error: audit() in LoggingRefunds cannot override audit() in RefundService

Больнее для фреймворков, которые наследуются от твоих классов во время работы. CGLIB-прокси Spring для @Transactional и @Configuration (AOP & Proxies), ленивые прокси Hibernate (JPA) — все они подклассы. Компилятор об этом не предупредит. Решение — плагины компилятора all-open (kotlin-spring) и no-arg (kotlin-jpa), их разбирает Kotlin with Spring & JPA. Mockito с версии 5 по умолчанию мокает final-классы через inline mock maker, поэтому в тестах проблема ушла.

Цена стыка и когда Kotlin не окупается

  • Вызовы из Java. Аргументы по умолчанию требуют @JvmOverloads, компаньон — @JvmStatic, top-level функции живут в классах …Kt. Если модуль активно зовут из Java, Kotlin-API приходится писать с оглядкой на это.
  • Сборка смешанного модуля. Сначала kotlinc компилирует Kotlin, читая .java только как исходники типов, затем javac собирает Java уже с классами Kotlin. Методы, которые генерирует Lombok в Java-классах того же модуля, Kotlin при этом не видит: Lombok работает позже. Lombok-классы обычно переписывают на Kotlin или выносят в отдельный модуль.
  • Зависимости и инструменты. kotlin-stdlib (около 1,8 МБ), для Spring и Jackson ещё kotlin-reflect; компиляция медленнее javac; в команде два языка и два стиля.

Java 21 закрыла часть разрыва: records, sealed и pattern matching, виртуальные потоки. Kotlin по-прежнему даёт nullability в типах, copy и аргументы по умолчанию, extension-функции и корутины. Выигрыш заметен в новом модуле, который пишут целиком на Kotlin; в старом Java-коде с Lombok, где Kotlin-класс вставлен в середину, больше уходит на стык. Сборку Kotlin-модуля в Gradle — плагины и Kotlin DSL — смотри в Maven & Gradle.

  • Kotlin-код — обычные Java-классы: свойства становятся полями с геттерами, object и companion — объектами со static-ссылкой, top-level функции — static-методами класса …Kt.
  • Null safety — проверка компилятора. На границе с Java работают вставленные проверки Intrinsics; null без явного типа проходит границу и падает позже. JSpecify-разметка убирает platform types.
  • data class сравнивает только свойства первичного конструктора, разрешает var и даёт copy; настоящий record — через @JvmRecord.
  • Extension-функция — static-метод, выбирается по объявленному типу и проигрывает члену класса. inline копирует тело в место вызова, и только поэтому работает reified.
  • Read-only List — ограничение ссылки, а не объекта. Final по умолчанию ломает прокси Spring и Hibernate, пока не подключены плагины.

На собеседовании

Зачем Kotlin в Java-сервисе и чем за него платишь?

Kotlin компилируется в тот же байткод и полностью совместим с Java: те же библиотеки, Spring и JPA, оба языка можно держать в одном модуле. Он даёт nullability в системе типов, data class и sealed с исчерпывающим when, аргументы по умолчанию, extension-функции и корутины. Код короче, и часть ошибок, которые в Java ловишь тестами, ловит компилятор.

Платишь стыком с Java. Значения из Java без аннотаций — platform types, и там NPE возможен. Классы final по умолчанию, поэтому для Spring и JPA нужны плагины all-open и no-arg. Аргументы по умолчанию и компаньоны неудобно вызывать из Java. Плюс два языка в команде, более медленная компиляция и kotlin-stdlib в зависимостях.

  • Гарантии Kotlin действуют при компиляции. В байткоде остаются проверки Intrinsics на входе не-private функций и при присваивании Java-значений, а JSpecify-разметка (Spring 7, Boot 4) превращает platform types в настоящие.
  • Java 21 закрыла часть разрыва: records, sealed и pattern matching, виртуальные потоки. Остались nullability в типах, copy, extension-функции и structured concurrency корутин.
  • В смешанном модуле kotlinc идёт первым и не видит то, что генерирует Lombok. Миграцию удобнее начинать с тестов и новых модулей, а не с середины старого кода.
Как Java-код вызывает top-level функцию, object и companion?

Top-level функция из файла Payment.kt — static-метод класса PaymentKt; имя класса меняет @file:JvmName. object FeePolicy — класс с полем INSTANCE: FeePolicy.INSTANCE.fee(x). Методы компаньона — методы объекта Payment.Companion; static-версию добавляет @JvmStatic, константу — const val, публичное поле без геттера — @JvmField.

Как устроена null safety в Kotlin и откуда всё-таки берётся NPE?

Nullability в Kotlin — часть типа: String и String?. Компилятор не даст разыменовать String? без ?., ?:, проверки со smart cast или !!. В байткоде оба типа — java.lang.String, поэтому на границе с Java компилятор вставляет проверки: на входе функций — checkNotNullParameter, при присваивании Java-значения в не-null переменную — checkNotNullExpressionValue.

NPE появляется на стыке. Значение из Java без аннотаций — platform type: если положить его в переменную с выведенным типом, null пройдёт дальше и упадёт позже. Ещё источники — !!, незаполненный lateinit и Java, которая передаёт null в Kotlin-метод. На границе я объявляю тип явно, а Java-код размечаю JSpecify.

  • С Kotlin 2.1 несоответствие JSpecify-аннотациям — ошибка компиляции. Spring Framework 7 размечен JSpecify, и platform types из его API исчезли.
  • Элементы коллекций из Java не проверяются: присваивание в List<String> проверит только сам список.
  • В чистом Kotlin NPE даёт open-метод, вызванный из конструктора базового класса: поля наследника ещё не присвоены.
  • Проверки снимаются флагами -Xno-param-assertions и -Xno-call-assertions, но стоят они почти ничего, а null без них уходит вглубь.
Что выведет этот код без единой строчки Java? 
open class Gateway {
    init { println("registered: " + describe()) }
    open fun describe() = "gateway"
}

class BankGateway(val bankName: String) : Gateway() {
    override fun describe() = "bank " + bankName.uppercase()
}

fun main() {
    try { BankGateway("sber") }
    catch (e: NullPointerException) { println(e.message) }
}
Cannot invoke "String.toUpperCase(java.util.Locale)" because "this.bankName" is null

Конструктор BankGateway сначала вызывает конструктор Gateway, и только потом присваивает bankName. init базового класса вызывает переопределённый describe(), а поле наследника в этот момент null, хотя тип String. Строка registered: не печатается: исключение вылетает раньше. Правило то же, что в Java: из конструктора не вызывают open-методы.

Когда lateinit, когда nullable, когда by lazy?

lateinit var — значение точно будет, но присваивается после конструктора: поле в тесте, внедрение через поле. Только var и не примитивы. Nullable — когда отсутствие значения законно по бизнес-смыслу: у платежа может не быть возврата. val x by lazy { … } — вычислить один раз при первом обращении; по умолчанию инициализация синхронизирована. В Spring внедрение через конструктор обычно убирает нужду в lateinit.

Чем data class отличается от Java record?

Оба — классы-значения с equals, hashCode и toString по полям. data class генерирует ещё copy и componentN, разрешает var, может наследовать open-класс, а свойства, объявленные в теле, не участвуют в equals. Record — только final-компоненты, аксессоры вида amount(), неявно extends Record.

На практике для DTO и value object я делаю data class только с val. Если Java-коду или библиотеке нужен настоящий record, ставлю @JvmRecord: тогда класс наследует java.lang.Record, но var в нём запрещён.

  • var в data class, которая лежит ключом в HashMap или в HashSet, — потерянный элемент после изменения.
  • copy идёт через первичный конструктор: проверки init выполняются. Но copy публичный даже при private-конструкторе; в Kotlin 2.x это предупреждение, с языковой версии 2.5 станет ошибкой (@ConsistentCopyVisibility).
  • Для JPA-сущностей data class не годится: equals по всем полям, ленивые связи в toString, final. Это разбирается в теме про Kotlin со Spring и JPA.
Что выведет этот код? 
data class Refund(val paymentId: String, var amount: Long)

val r = Refund("p-1", 500)
val sent = hashSetOf(r)
r.amount = 300
println("contains=${r in sent} size=${sent.size}")
contains=false size=1

hashCode считается по amount. После изменения объект ищется в бакете для нового хеша, а лежит в старом. Элемент есть, но найти и удалить его по значению уже нельзя.

Если все свойства data class — val со списками, она неизменяема?

Нет. val items: List<Item> запрещает заменить ссылку и прячет add от Kotlin-кода, но объект за ссылкой обычно ArrayList. Его может изменить тот, кто передал список в конструктор, или Java-код. Для настоящей неизменяемости делают копию при создании: items.toList() или List.copyOf.

Как работают extension-функции и inline? Что в байткоде?

Extension-функция — static-метод в классе файла, получатель передаётся первым параметром. Поэтому она выбирается статически по объявленному типу, а не по классу объекта, проигрывает члену класса с той же сигнатурой и не видит private. Из Java это обычный вызов ExtensionsKt.withFee(amount, 15).

inline-функцию компилятор не вызывает, а копирует её тело вместе с лямбдами в место вызова. Объект лямбды не создаётся, return из лямбды выходит из окружающей функции, а параметр типа можно сделать reified и писать it is T: в копии тела стоит конкретный класс.

  • reified не обходит стирание: тип не передаётся в рантайм, его вписывают в скопированный код. Поэтому reified-функцию нельзя вызвать из Java: метод помечен ACC_SYNTHETIC.
  • Цена inline — размер байткода в каждом месте вызова. Лямбду, которую нужно сохранить, помечают noinline, вызываемую из другого контекста — crossinline.
  • Extension может принимать nullable-получатель: fun String?.isNullOrBlank() вызывается и на null. Так устроена часть stdlib.
Что выведет этот код? 
open class Payment
class CardPayment : Payment()

fun Payment.kind() = "payment"
fun CardPayment.kind() = "card"

val p: Payment = CardPayment()
println(p.kind())
println((p as CardPayment).kind())
payment
card

Обе функции — static-методы kind(Payment) и kind(CardPayment). Компилятор выбирает между ними, как между перегрузками, по объявленному типу выражения. Класс объекта не важен; после приведения тип выражения другой, и выбирается вторая функция.

Есть ли в Kotlin static?

Ключевого слова нет. Его роль играют top-level функции и свойства (static-члены класса …Kt), object и companion object (синглтоны со static-ссылкой). Компаньон — объект: он реализует интерфейсы и передаётся как значение. Настоящие static-члены для Java появляются с @JvmStatic, const val и @JvmField.
