Kotlin with Spring & JPA

Spring и Hibernate написаны для Java: они наследуются от твоих классов, создают объекты через конструктор без аргументов и читают параметры конструктора по именам. Kotlin по умолчанию делает классы final, конструктор без аргументов не генерирует, а null-проверки вставляет прямо в конструктор. Поэтому Kotlin-сервис на Spring держится на нескольких плагинах компилятора и модулях. Без них он ломается так, что из кода причину не видно. Дальше — что именно ломается, с запуском на Spring 7.0.9 и Hibernate 7.4.1, и что каждый плагин чинит.

Без all-open Spring не может построить прокси, а final-метод выполняется на пустом прокси

Платёжный сервис переписывают на Kotlin. Для @Transactional, @Async, @Cacheable и @Configuration Spring создаёт CGLIB-прокси — подкласс твоего бина, который переопределяет методы и добавляет поведение (AOP & Proxies). В Kotlin классы и методы final по умолчанию. Тот же код собран дважды: обычным kotlinc и с плагином kotlin-spring:

@Component
class PaymentService(private val ledger: Ledger) {            // без плагина: final class
    @Transactional
    fun pay(id: String) = ledger.save(id)
}

@Component
open class RefundService(private val ledger: Ledger) {         // класс открыли руками...
    @Transactional
    fun refund(id: String) = ledger.save(id)                   // ...а метод остался final
}

@Configuration                                                  // full mode: тоже CGLIB-подкласс
class FeeConfig {
    @Bean fun feeRate() = 15
}
// Менеджер транзакций в опыте только печатает BEGIN и COMMIT
=== без плагина
final class + @Transactional:
    IllegalArgumentException: Cannot subclass final class pay.proxy.PaymentService
open class, final method:
    bean class: RefundService$$SpringCGLIB$$0
    NullPointerException: Cannot invoke "pay.proxy.Ledger.save(String)" because "this.ledger" is null
final @Configuration:
    BeanDefinitionParsingException: Configuration problem: @Configuration class 'FeeConfig' may not be final. Remove the final modifier to continue.
=== с kotlin-spring
final class + @Transactional:
    bean class: PaymentService$$SpringCGLIB$$0

    COMMIT
    result: saved p-1
open class, final method:

Без плагина два случая из трёх честно падают на старте: первый — с BeanCreationException: Could not generate CGLIB subclass, корневая причина напечатана выше. Опасен средний. Класс открыт, CGLIB построил подкласс, бин создан, и Spring только предупредил в лог: Public final method [...refund...] cannot get proxied via CGLIB. Вызов refund не попал в перехватчик: транзакции нет, BEGIN не напечатан. Тело метода выполнилось на самом прокси, а у прокси поля пустые — ledger равен null, хотя в Kotlin он объявлен не-null. Если бы метод не трогал поля, он бы просто молча отработал без транзакции.

Что делает плагин all-open

Плагин kotlin("plugin.spring") — это all-open с готовым набором аннотаций. Класс, помеченный @Component, @Async, @Transactional, @Cacheable или @SpringBootTest, компилируется открытым вместе со всеми членами. Мета-аннотации тоже считаются, поэтому @Service, @Repository, @Controller и @Configuration, помеченные @Component, попадают в список автоматически.

$ javap -p RefundService PaymentService          # без плагина
public class pay.proxy.RefundService {
  public final java.lang.String refund(java.lang.String);     # open class, но метод final
public final class pay.proxy.PaymentService {
  public final java.lang.String pay(java.lang.String);

$ javap -p RefundService PaymentService          # с kotlin-spring
public class pay.proxy.RefundService {
  public java.lang.String refund(java.lang.String);           # открыт плагином
public class pay.proxy.PaymentService {
  public java.lang.String pay(java.lang.String);

Плагин открывает только классы с этими аннотациями. Обычный класс без них, например Ledger, остаётся final. В проекте со Spring Initializr плагин подключён сразу; если модуль собирали руками, его стоит проверить первым, когда @Transactional «не работает».

Достаточно написать open class, и прокси заработает.

open на классе не открывает методы: каждый метод final, пока не помечен open. CGLIB построит подкласс, но не переопределит final-методы, и вызов пройдёт мимо перехватчика. Ошибки не будет, только предупреждение в логе.

JPA-сущность на Kotlin: конструктор без аргументов, открытый класс и не data class

Hibernate создаёт сущность при загрузке из базы так: вызывает конструктор без аргументов через reflection, затем заполняет поля из строки результата. Для ленивой связи он генерирует подкласс-прокси, как Spring. Kotlin-класс с первичным конструктором не даёт ни того, ни другого:

@Entity
class Merchant(@Id val id: Long, var name: String)

@Entity
class Payment(
    @Id val id: Long,
    var amount: Long,
    @ManyToOne(fetch = FetchType.LAZY) val merchant: Merchant,   // хотим загрузку по требованию
)

val p = em.find(Payment::class.java, 10L)
println("merchant class=${p.merchant.javaClass.simpleName}, " +
    "initialized=${Hibernate.isInitialized(p.merchant)}, statements=${stats.prepareStatementCount}")
=== без плагинов
InstantiationException: No default constructor for entity 'pay.jpa.Payment'
=== kotlin-jpa (no-arg)
merchant class=Merchant, initialized=true, statements=2
=== kotlin-jpa + all-open для @Entity
merchant class=Merchant$HibernateProxy, initialized=false, statements=1

Без плагинов сохранение прошло, а загрузка упала: конструктора без аргументов нет. Плагин kotlin("plugin.jpa") — это no-arg с набором @Entity, @Embeddable, @MappedSuperclass. Он добавляет синтетический конструктор без аргументов, который видит только reflection: из Kotlin и Java его не вызвать. Инициализаторы свойств этот конструктор не выполняет — значения ставит Hibernate.

Со вторым результатом сложнее, потому что он выглядит рабочим. Сущность загрузилась, но LAZY не сработал: Merchant final, прокси-подкласс построить нельзя, и Hibernate молча загрузил продавца вторым запросом. Ни ошибки, ни предупреждения нет; на списке из сотни платежей это сотня лишних запросов (JPA). Только с all-open для JPA-аннотаций продавец стал прокси, и запрос остался один. kotlin("plugin.spring") сущности не открывает: это делается отдельно в Gradle.

// build.gradle.kts
plugins {
    kotlin("plugin.spring") version "2.4.10"     // all-open для @Component, @Transactional и др.
    kotlin("plugin.jpa") version "2.4.10"        // no-arg для @Entity, @Embeddable, @MappedSuperclass
}
allOpen {                                        // сущности тоже должны быть open — для lazy-прокси
    annotation("jakarta.persistence.Entity")
    annotation("jakarta.persistence.MappedSuperclass")
    annotation("jakarta.persistence.Embeddable")
}

Почему сущность не data class

data class генерирует equals, hashCode и toString по всем свойствам конструктора. Для сущности это ломает три вещи сразу:

@Entity
data class Refund(                                                // так делать не надо
    @Id @GeneratedValue var id: Long? = null,
    var amount: Long,
    @ManyToOne(fetch = FetchType.LAZY) var merchant: Merchant? = null,
)

val refund = Refund(amount = 100, merchant = em.getReference(Merchant::class.java, 1L))
val pending = hashSetOf(refund)
em.persist(refund)                          // id присвоен при сохранении
println("refund id=${refund.id}, still in set: ${refund in pending}")

val detached = em.createQuery("select r from Refund r", Refund::class.java).singleResult
em.close()
println(detached)                           // toString читает merchant
refund id=1, still in set: false
LazyInitializationException: Could not initialize proxy [pay.jpa.Merchant#1] - no session
  • hashCode меняется. До persist id равен null, после — 1. Сущность «теряется» в HashSet, в котором лежала, как изменённый ключ.
  • toString и equals трогают ленивые связи. Внутри сессии это лишние запросы, вне её — LazyInitializationException. Здесь хватило println в логе. Без all-open для сущностей этого исключения не было бы: связь загрузилась бы сразу, о чём шла речь выше.
  • copy и equals по всем полям противоречат тождеству сущности: две загрузки одной строки с разным amount — это одна сущность в разных состояниях, а не два разных значения.

Сущность — обычный класс с равенством по идентификатору:

@Entity
class Payment(
    @Id val id: UUID = UUID.randomUUID(),        // id известен до persist: hashCode не меняется
    var amount: Long,
    @ManyToOne(fetch = FetchType.LAZY) val merchant: Merchant,
) {
    override fun equals(other: Any?): Boolean {
        if (this === other) return true
        if (other !is Payment) return false      // прокси Hibernate — подкласс, проверку проходит
        return id == other.id                    // id у прокси читается без загрузки
    }
    override fun hashCode() = id.hashCode()
    override fun toString() = "Payment(id=$id, amount=$amount)"   // без ленивых связей
}

Если id генерирует база (@GeneratedValue), равенство пишут как «оба id не null и равны», а hashCode делают постоянным для класса, например javaClass.hashCode(). Тогда объект не теряется в коллекции при persist.

Jackson без Kotlin-модуля не знает про значения по умолчанию и null safety

REST-контроллер принимает запрос на оплату. Его удобно описать data class со значением по умолчанию для валюты:

data class PaymentRequest(
    val id: String,
    val amount: Long,
    val currency: String = "RUB",        // клиент может не присылать
    val comment: String? = null,
)

val mapper = JsonMapper.builder().build()           // Jackson 3, без Kotlin-модуля
for (json in listOf(
    """{"id":"p-1","amount":350,"currency":"EUR"}""",
    """{"id":"p-2","amount":350}""",
    """{"amount":350}""",
)) println("$json -> " + runCatching { mapper.readValue(json, PaymentRequest::class.java) }…)

Результат зависит от флага компилятора. Без -java-parameters имён параметров конструктора в байткоде нет, и Jackson не видит, как создать объект. С флагом — видит, но работает с конструктором как с Java-конструктором:

== kotlinc без флагов
{"id":"p-1","amount":350,"currency":"EUR"} -> InvalidDefinitionException: Cannot construct instance of `pay.jackson.PaymentRequest` (no Creators, like default constructor, exist): cannot deserialize from Object value (no delegate- or property-based Creator)
== kotlinc -java-parameters
{"id":"p-1","amount":350,"currency":"EUR"} -> PaymentRequest(id=p-1, amount=350, currency=EUR, comment=null)
{"id":"p-2","amount":350} -> ValueInstantiationException: Cannot construct instance of `pay.jackson.PaymentRequest`, problem: Parameter specified as non-null is null: method pay.jackson.PaymentRequest.<init>, parameter currency
{"amount":350} -> ValueInstantiationException: Cannot construct instance of `pay.jackson.PaymentRequest`, problem: Parameter specified as non-null is null: method pay.jackson.PaymentRequest.<init>, parameter id

Второй запрос валиден по контракту API: валюта не пришла, должна стать RUB. Jackson же передал в конструктор null, и сработала проверка параметра из темы Kotlin for Java Devs. Значение по умолчанию живёт в синтетическом конструкторе с битовой маской, и Java-библиотека про него не знает. Третий запрос должен падать, но падает с внутренним NPE вместо понятной ошибки «нет поля id».

Это чинит jackson-module-kotlin. Он читает метаданные Kotlin через kotlin-reflect: какие параметры nullable, у каких есть значения по умолчанию. Отсутствующий currency модуль пропускает, и подставляется "RUB". Отсутствующий не-null id превращается в KotlinInvalidNullException с именем поля. Это подкласс InvalidNullException из Jackson, и Spring отвечает на него 400 Bad Request, а не 500. Тот же код с модулем в classpath, причём -java-parameters уже не нужен: модуль берёт имена из метаданных Kotlin:

val mapper = JsonMapper.builder()
    .addModule(KotlinModule.Builder().build())      // это делает Spring Boot, если модуль в classpath
    .build()
== jackson-module-kotlin 3.1.5 + kotlin-reflect, kotlinc без флагов
{"id":"p-1","amount":350,"currency":"EUR"} -> PaymentRequest(id=p-1, amount=350, currency=EUR, comment=null)
{"id":"p-2","amount":350} -> PaymentRequest(id=p-2, amount=350, currency=RUB, comment=null)
{"amount":350} -> KotlinInvalidNullException: Instantiation of [simple type, class pay.jackson.PaymentRequest] value failed for JSON property id due to missing (therefore NULL) value for creator parameter id which is a non-nullable type

Spring Boot регистрирует модуль сам, если он есть в classpath, а Spring Initializr добавляет его в Kotlin-проект вместе с kotlin-reflect. Boot 4 работает с Jackson 3, поэтому артефакт — tools.jackson.module:jackson-module-kotlin; у Jackson 2 он был в группе com.fasterxml.jackson.module. Флаг -java-parameters Spring Boot Gradle plugin ставит Kotlin-компиляции сам.

Spring читает nullability Kotlin, а Kotlin читает JSpecify-аннотации Spring

Null safety работает в обе стороны. Spring смотрит на типы Kotlin и делает nullable-параметры необязательными. Kotlin смотрит на аннотации Spring и не даёт забыть, что метод может вернуть null.

Nullable — значит необязательно

SMS-шлюз подключён не во всех окружениях. В Java необязательную зависимость пишут через Optional, ObjectProvider или @Autowired(required = false) (Optional). В Kotlin достаточно nullable-типа:

class SmsGateway

@Component
class Notifier(private val sms: SmsGateway?) {       // nullable: зависимость необязательна
    fun channels() = if (sms == null) "email only" else "email + sms"
}

AnnotationConfigApplicationContext(Notifier::class.java).use { ctx ->   // SmsGateway не зарегистрирован
    println("notifier: " + ctx.getBean(Notifier::class.java).channels())
}
-- без kotlin-reflect в classpath
NoSuchBeanDefinitionException: No qualifying bean of type 'pay.nulls.SmsGateway' available
-- с kotlin-reflect
notifier: email only

Тип SmsGateway? в байткоде — обычный SmsGateway, nullability хранится в метаданных Kotlin. Spring читает их через kotlin-reflect. Без этой библиотеки он видит обязательный параметр, и контекст не стартует. По той же причине в Spring MVC @RequestParam comment: String? необязателен. Поэтому kotlin-reflect — обязательная зависимость Kotlin-проекта на Spring.

Spring 7 размечен JSpecify

Spring Framework 7 и Spring Boot 4 перешли на JSpecify: пакеты помечены @NullMarked, а методы, которые могут вернуть null, — @Nullable. Kotlin 2.1+ считает несоответствие ошибкой компиляции, поэтому platform types на стыке со Spring пропали:

// queryForObject объявлен как @Nullable T
val count: Long = jdbc.queryForObject("select count(*) from payment", Long::class.java)
JdbcNulls.kt:7:21: error: initializer type mismatch: expected 'Long', actual 'Long?'.

На Spring 6 тот же код компилировался, и null из пустого результата проходил в Long через platform type. Теперь компилятор требует решить: ?: 0, ?: error("…") или nullable-тип. При переходе на Boot 4 такие ошибки компиляции ожидаемы: это места, где null и раньше был возможен. Флаг -Xjsr305=strict, который Spring Initializr по-прежнему добавляет, относится к аннотациям JSR-305: на них были размечены Spring 5 и 6 и часть других библиотек. Для JSpecify строгий режим включён по умолчанию.

Аннотации на свойствах из первичного конструктора: до Kotlin 2.2 @NotBlank val id: String попадала только на параметр конструктора, и Bean Validation, которая смотрит на поле, её не видела — поэтому в старом коде пишут @field:NotBlank. Kotlin 2.2 ввёл новое правило: аннотация без цели ставится и на параметр, и на поле. Spring Initializr включает его флагом -Xannotation-default-target=param-property; на Kotlin 2.4.10 в javap аннотация видна на обоих местах и без флага. На старых версиях Kotlin @field: по-прежнему нужен.

suspend-контроллер: Spring вызывает его через Reactor и Dispatchers.Unconfined

Spring MVC и WebFlux принимают suspend-функции в контроллерах и Flow как тело ответа (Coroutines). Снаружи это обычный метод:

@RestController
class PaymentController(private val gateway: BankGateway) {
    @GetMapping("/payments/{id}")
    suspend fun status(@PathVariable id: String): PaymentStatus =
        gateway.status(id)                       // suspend-вызов банка, поток не держится
}

Как Spring вызывает такой метод, видно в байткоде spring-core 7.0.9. Обработчик проверяет KotlinDetector.isSuspendingFunction и уходит в CoroutinesUtils.invokeSuspendingFunction. Тот запускает функцию внутри mono { } из kotlinx-coroutines-reactor с контекстом Dispatchers.Unconfined и возвращает Publisher:

$ javap -c -p -cp spring-core-7.0.9.jar org.springframework.core.CoroutinesUtils
public static Publisher<?> invokeSuspendingFunction(Method, Object, Object...);
   6: invokestatic  Dispatchers.getUnconfined          # контекст по умолчанию
public static Publisher<?> invokeSuspendingFunction(CoroutineContext, Method, Object, Object...);
  50: invokestatic  kotlinx/coroutines/reactor/MonoKt.mono   # корутина завёрнута в Mono

Что это значит на практике, видно на MockMvc. Контроллер печатает поток до и после приостановки; поток теста назван как поток Tomcat:

@RestController
class PaymentController {
    @GetMapping("/payments/{id}")
    suspend fun status(@PathVariable id: String): String {
        val before = thread()                 // поток запроса
        delay(50)                             // «ответ банка»: точка приостановки
        val after = thread()                  // кто нас возобновил
        return "$id PAID; before delay: $before; after delay: $after"
    }
}

Thread.currentThread().name = "http-nio-1"
val started = mvc.perform(get("/payments/p-1")).andReturn()
println("async started: ${started.request.isAsyncStarted}, response yet: '${started.response.contentAsString}'")
started.getAsyncResult(2_000)
val done = mvc.perform(asyncDispatch(started)).andReturn()
println("status ${done.response.status}: ${done.response.contentAsString}")
async started: true, response yet: ''
status 200: p-1 PAID; before delay: http-nio-1; after delay: kotlinx.coroutines.DefaultExecutor

Обработчик вернулся сразу, запрос перешёл в асинхронный режим, и поток запроса освободился. После delay функция продолжила работу в kotlinx.coroutines.DefaultExecutor — служебном потоке таймера kotlinx.coroutines, одном на всё приложение. Без kotlinx-coroutines-reactor в classpath тот же запрос падает с NoClassDefFoundError: kotlinx/coroutines/reactor/MonoKt.

Отсюда три практических следствия.

  • Нужны зависимости. kotlinx-coroutines-reactor и reactor-core должны быть в classpath даже в Spring MVC. Результат-Publisher MVC обрабатывает как асинхронный запрос Servlet API.
  • Unconfined — это «где придётся». До первой приостановки функция идёт в потоке запроса, после — в том потоке, который её возобновил: потоке HTTP-клиента или, как здесь, таймера DefaultExecutor. Блокирующий вызов после delay займёт этот общий поток и задержит все таймеры приложения, поэтому JDBC и другие блокирующие вызовы оборачивают в withContext(Dispatchers.IO).
  • ThreadLocal не переезжает. MDC, SecurityContextHolder, транзакция, привязанная к потоку, после приостановки могут оказаться в другом потоке. Для логов есть MDCContext, для Security в WebFlux — реактивный контекст, а не ThreadLocal.

@Transactional на suspend-функции

TransactionAspectSupport в spring-tx 7.0.9 поддерживает suspend-функции только в реактивной ветке: если менеджер транзакций — ReactiveTransactionManager (R2DBC, реактивный MongoDB). JPA и JDBC используют PlatformTransactionManager, который хранит транзакцию в ThreadLocal. Что получается, если всё же поставить @Transactional на suspend-функцию с таким менеджером:

@Component
class RefundService {
    @Transactional
    suspend fun refund(id: String): String {
        println("    before delay: tx active=${TransactionSynchronizationManager.isActualTransactionActive()}")
        delay(50)
        return "refunded $id"
    }
}
// менеджер — блокирующий AbstractPlatformTransactionManager, печатает BEGIN и COMMIT с потоком
println("    result: " + runBlocking { service.refund("r-1") })
    BEGIN on main
    COMMIT on main
    before delay: tx active=false
    result: refunded r-1

Транзакция открылась и закрылась раньше, чем выполнилась первая строка метода. Прокси вызвал suspend-функцию через CoroutinesUtils, получил ленивый Mono и счёл вызов завершённым: COMMIT. Тело выполнилось позже, при подписке, уже без транзакции. Ни ошибки, ни предупреждения нет, а запись в базу в таком методе пройдёт вне транзакции, и откатить её будет нечем. Для JPA в Kotlin-сервисе транзакционный код оставляют обычной функцией и вызывают из корутины через withContext(Dispatchers.IO), либо работают на виртуальных потоках без suspend.

Без какого плагина что сломается: чек-лист Kotlin-модуля на Spring

Почти все проблемы этой темы — молчаливые: сервис стартует, а поведение не то. Поэтому настройку сборки проверяют по списку, а не по симптомам. Сам Gradle и Kotlin DSL разобраны в Maven & Gradle.

Где Kotlin со Spring не окупается

  • Lombok в Java-классах того же модуля. Kotlin компилируется раньше и сгенерированных геттеров не видит. Сущности с Lombok обычно переписывают на Kotlin целиком или держат в отдельном Java-модуле.
  • JPA и корутины вместе. Транзакция JPA привязана к потоку. Если сервис построен на JPA, корутины дают немного: виртуальные потоки решают ту же задачу без переписывания (Virtual Threads).
  • Spring и Hibernate наследуются от твоих классов. В Kotlin это требует all-open: plugin.spring для бинов и отдельный allOpen для сущностей.
  • final-метод в open-классе — худший случай: прокси создан, вызов мимо перехватчика, поля прокси пустые.
  • Сущность — обычный open-класс с no-arg конструктором от plugin.jpa и равенством по id, а не data class.
  • kotlin-reflect и jackson-module-kotlin переводят nullability и значения по умолчанию из метаданных Kotlin в поведение Spring и Jackson.
  • Spring 7 размечен JSpecify: Kotlin-компилятор видит, где Spring может вернуть null.
  • suspend-контроллер Spring запускает через mono { } на Unconfined. @Transactional на suspend-функции с JPA-менеджером коммитит пустую транзакцию до выполнения тела.

На собеседовании

Зачем в Kotlin-проекте на Spring плагин kotlin-spring?

Spring строит CGLIB-прокси для @Transactional, @Async, @Cacheable и full-mode @Configuration. Прокси — подкласс бина, а Kotlin делает классы и методы final по умолчанию. Плагин kotlin-spring — это all-open с набором аннотаций Spring: такие классы и их методы компилируются открытыми.

Без него final-класс с @Transactional не стартует: CGLIB не может его унаследовать, а final @Configuration отклоняется при разборе конфигурации. Хуже, если класс открыть руками, а метод оставить final: бин создастся, вызов пройдёт мимо перехватчика без транзакции, и метод выполнится на прокси с пустыми полями.

  • Плагин учитывает мета-аннотации: @Service и @Configuration открываются через @Component. Классы без аннотаций остаются final.
  • Сущности JPA kotlin-spring не открывает: для lazy-прокси Hibernate нужен отдельный allOpen для @Entity.
  • Альтернатива — JDK-прокси через интерфейс, но в Boot по умолчанию proxyTargetClass = true, и CGLIB используется даже при наличии интерфейса.
Почему здесь не откатывается транзакция? 
@Service
open class RefundService(private val repo: RefundRepository) {
    @Transactional
    fun refund(cmd: RefundCommand) {
        repo.save(Refund(cmd))
        if (cmd.amount > LIMIT) throw LimitExceeded()
    }
}
// Gradle: плагин kotlin-spring не подключён

open открыл класс, но refund остался final. CGLIB его не переопределил, и вызов пошёл в тело метода на самом прокси, без перехватчика транзакций. У прокси repo равен null, поэтому здесь будет NPE; если бы метод обращался к полям иначе, он бы отработал без транзакции, и откатывать было бы нечего. Исправление — подключить kotlin("plugin.spring") и убрать ручной open.

Как правильно писать JPA-сущность на Kotlin и почему не data class?

Hibernate создаёт сущность через конструктор без аргументов и строит прокси-подклассы для ленивых связей. Поэтому нужен плагин kotlin-jpa, который генерирует синтетический no-arg конструктор, и allOpen для @Entity, иначе lazy-связи молча загружаются сразу.

Data class не подходит: equals и hashCode по всем полям меняются после persist, когда появляется id, а toString трогает ленивые связи и даёт лишние запросы или LazyInitializationException. Я пишу обычный класс с равенством по id и toString без связей.

  • С id из базы делаю equals «оба id не null и равны» и постоянный hashCode; с UUID, заданным в коде, — обычное равенство по id.
  • Проверка other !is Payment работает с прокси Hibernate: это подкласс. other.javaClass != javaClass на прокси даст неравенство.
  • No-arg конструктор не выполняет инициализаторы свойств: значение по умолчанию вроде val items = mutableListOf() будет null, пока его не заполнит Hibernate. Опция invokeInitializers это меняет.
Что выведет этот код, если сущности не открыты для прокси? 
// kotlin-jpa подключён, allOpen для @Entity — нет
@Entity class Merchant(@Id val id: Long, var name: String)
@Entity class Payment(
    @Id val id: Long, var amount: Long,
    @ManyToOne(fetch = FetchType.LAZY) val merchant: Merchant,
)

val p = em.find(Payment::class.java, 10L)
println("initialized=${Hibernate.isInitialized(p.merchant)}, statements=${stats.prepareStatementCount}")
initialized=true, statements=2

Merchant final, прокси-подкласс построить нельзя, и Hibernate 7.4.1 без предупреждения загружает связь вторым запросом. С allOpen для @Entity будет initialized=false, statements=1.

Как Spring и Jackson понимают null safety Kotlin?

Nullability и значения по умолчанию хранятся в метаданных Kotlin, а не в байткоде, поэтому Spring и Jackson читают их через kotlin-reflect. Spring делает nullable-параметр конструктора необязательной зависимостью, а @RequestParam x: String? — необязательным параметром. jackson-module-kotlin подставляет значения по умолчанию и превращает отсутствующее не-null поле в понятную ошибку, а не в NPE из конструктора.

В обратную сторону Spring 7 размечен JSpecify, и Kotlin видит, где методы Spring возвращают null: queryForObject возвращает T?, и присвоить его в не-null переменную компилятор не даст.

  • Без kotlin-reflect nullable-зависимость становится обязательной: NoSuchBeanDefinitionException на старте.
  • Без Kotlin-модуля Jackson 3 с -java-parameters создаёт data class через конструктор, но null из отсутствующего поля падает на проверке параметра, а значение по умолчанию не подставляется. С модулем отсутствующее не-null поле даёт KotlinInvalidNullException, то есть 400.
  • До Kotlin 2.2 аннотации на свойствах конструктора попадали только на параметр, и Bean Validation их не видела, поэтому писали @field:NotBlank.

Можно ли писать suspend-контроллеры в Spring MVC? Что с транзакциями?

Да, и в MVC, и в WebFlux. Spring видит suspend-метод и вызывает его через CoroutinesUtils: функция запускается в mono { } из kotlinx-coroutines-reactor на Dispatchers.Unconfined. В MVC это асинхронный запрос Servlet API, и поток Tomcat не ждёт ответа банка.

С транзакциями JPA осторожно. @Transactional на suspend-функции поддерживается только с ReactiveTransactionManager. С блокирующим менеджером транзакция открывается и коммитится до выполнения тела, и метод работает вне транзакции без всякой ошибки. Поэтому транзакционный JPA-код оставляю обычной функцией и вызываю из корутины через withContext(Dispatchers.IO).

  • Unconfined продолжает корутину в том потоке, который её возобновил: после delay это kotlinx.coroutines.DefaultExecutor. Блокирующий вызов там задержит все таймеры приложения.
  • ThreadLocal-контекст — MDC, SecurityContext — после приостановки теряется; для логов есть MDCContext.
  • Если сервис на JPA, виртуальные потоки обычно проще корутин: код остаётся блокирующим, и транзакции работают как раньше.
