Kubernetes Basics

Kubernetes хранит желаемое состояние — «три копии сервиса с такой-то конфигурацией» — и контроллеры непрерывно приводят к нему действительное. Pod — один или несколько контейнеров с общей сетью; Deployment управляет ReplicaSet, а тот держит нужное число подов: удалённый под в демо сразу заменился новым. Service — постоянный адрес для подов, отобранных по меткам: запросы разошлись по трём подам, а под, потерявший метку, сразу выпал из Service, хотя продолжил работать, и ReplicaSet создал ему замену. ConfigMap и Secret отделяют конфигурацию от образа, но переменные окружения из ConfigMap читаются только при старте пода: после правки файл в поде обновился, а переменная — только после перезапуска.

Серверы с ручным деплоем и ночные перезапуски упавших процессов

Платёжный сервис работает на трёх виртуальных машинах. Деплой — скрипт, который по очереди копирует jar и перезапускает процесс; если машина перезагрузилась, кто-то должен вспомнить запустить сервис; балансировщик настраивают руками, когда добавляют машину. Kubernetes заменяет этот ручной процесс декларацией: вы описываете, что должно работать, а система сама запускает, перезапускает, распределяет по узлам и обновляет адреса.

Тема разбирает основные объекты на живом кластере. Демо k8s.sh поднимает k3s 1.34 в Docker-контейнере, загружает в него образ мини-сервиса App.java, который отвечает именем пода, версией и конфигурацией, и применяет манифест app.yaml. Образы — в Docker, пробы, ресурсы и память JVM — в Java in Kubernetes.

Объекты: желаемое состояние и контроллеры

apiVersion: apps/v1
kind: Deployment
metadata: { name: payments }
spec:
  replicas: 3
  selector: { matchLabels: { app: payments } }
  template:
    metadata: { labels: { app: payments } }
    spec:
      containers:
        - name: app
          image: kb-k8s-app:1
          env:
            - name: GREETING                 # переменная окружения из ConfigMap — читается при старте
              valueFrom: { configMapKeyRef: { name: payments-config, key: GREETING } }
          volumeMounts:
            - { name: config, mountPath: /config }   # файл из ConfigMap — обновляется в работающем поде
---
apiVersion: v1
kind: Service
metadata: { name: payments }
spec:
  selector: { app: payments }                 # трафик получают поды с этой меткой
  ports: [{ port: 80, targetPort: 8080 }]

Всё в Kubernetes — объекты в API-сервере, которые хранятся в etcd, как в Consensus & Time. Контроллеры работают в цикле согласования: читают желаемое состояние, сравнивают с действительным и делают шаг к желаемому. Поэтому манифест описывает «что», а не «как», и повторное применение того же манифеста ничего не меняет. Namespace разделяет объекты команд и окружений; Ingress или Gateway API принимают внешний HTTP-трафик и маршрутизируют его по сервисам.

Что происходит после kubectl apply

Компоненты не вызывают друг друга напрямую — все общаются только через API-сервер, подписываясь на изменения нужных объектов. Поэтому система устойчива к сбоям отдельных частей: упавший планировщик после перезапуска просто увидит неразмещённые поды. Это же объясняет задержки: kubectl apply возвращается сразу, а готовность подов наступает через секунды или минуты — в демо скрипт ждёт её командой kubectl rollout status. Если под застрял в Pending — планировщик не нашёл узел; в ContainerCreating — kubelet не может скачать образ или смонтировать том; в CrashLoopBackOff — процесс падает, и kubelet перезапускает его с растущей паузой. Причины видны в kubectl describe pod и событиях.

Service распределяет запросы, ReplicaSet восстанавливает поды

== Service spreads requests over the pods (30 requests)
   pod=kxz66 x10
   pod=msfsp x9
   pod=sm24t x11
== a pod is deleted: the ReplicaSet creates a new one
   before: kxz66 msfsp sm24t
   after:  kdndt msfsp sm24t    (deleted kxz66)

Клиентский под обращается к сервису по имени http://payments — DNS кластера разрешает его в виртуальный IP сервиса, а kube-proxy распределяет соединения по подам: 10, 9 и 11 из 30. Это балансировка на уровне соединений (L4): каждый новый запрос wget — новое соединение. Для долгих соединений HTTP/2 и gRPC это значит, что все запросы одного клиента уйдут в один под, как разобрано в Load Balancing.

Удалённый под kxz66 ReplicaSet сразу заменил новым — kdndt: подов с меткой стало два, а должно быть три. Так же обрабатываются упавший узел, вытеснение пода по памяти и падение процесса: контейнер перезапускается kubelet'ом на месте, а под на мёртвом узле пересоздаётся на другом. Имена подов случайны и меняются при каждом пересоздании, поэтому к подам обращаются только через Service, а не по именам или IP.

ConfigMap: файл обновляется в работающем поде, переменная — нет

== ConfigMap changed to hello-v2
   after 69 s: pod=kdndt version=1 env=hello-v1 file=hello-v2
   after rollout restart: pod=cclc8 version=1 env=hello-v2 file=hello-v2

Значение в ConfigMap поменяли на hello-v2. Через 69 секунд под отвечает env=hello-v1 file=hello-v2: файл, смонтированный из ConfigMap, kubelet обновил на месте, а переменная окружения осталась старой — она передаётся процессу один раз при запуске контейнера. Задержка обновления файла зависит от периода синхронизации kubelet и кеша: в другом прогоне демо файл обновился за 2 секунды. После kubectl rollout restart новые поды получили и новую переменную.

Отсюда два подхода. Переменные окружения просты, но любое изменение требует перезапуска — и это даже хорошо: конфигурация меняется так же, как код, через постепенную выкатку и с возможностью отката. Файлы позволяют перечитывать конфигурацию без перезапуска, но приложение должно само следить за изменениями, а разные поды какое-то время работают с разной конфигурацией. Часто делают имя ConfigMap с хешем содержимого (Kustomize configMapGenerator), чтобы изменение конфигурации меняло шаблон пода и запускало выкатку. Secret устроен так же, но значения в нём только закодированы в base64, а не зашифрованы: защиту дают RBAC, шифрование etcd и внешние хранилища секретов.

Метки связывают объекты: потерял метку — выпал из сервиса

== a pod loses the label app=payments
   pods with app=payments: 3, with app=debug: 1
   endpoints of the Service: pmmkd cclc8 pg4nf
   relabeled pod still runs: Running (dvj2v)

Поду dvj2v сменили метку app=payments на app=debug. Произошло две вещи сразу. Service перестал направлять на него трафик — его нет среди endpoints. ReplicaSet увидел, что подов с нужной меткой стало два, и создал третий. При этом сам dvj2v продолжает работать: Kubernetes связывает объекты не владением по имени, а отбором по меткам. Этим пользуются для отладки — вывести под из-под нагрузки, сохранив его состояние для разбора, — и это же источник ошибок: опечатка в метке шаблона или селектора делает сервис пустым, а под — бесхозным.

Изменил ConfigMap — приложение сразу работает с новой конфигурацией.

Переменные окружения из ConfigMap читаются только при старте контейнера: в демо файл обновился в работающем поде, а переменная осталась hello-v1 до rollout restart. Обновление файлов тоже не мгновенно — от секунд до минуты.

  • Kubernetes хранит желаемое состояние, контроллеры приводят к нему действительное в цикле согласования.
  • apply → API-сервер и etcd → контроллеры → планировщик → kubelet; компоненты общаются только через API-сервер.
  • Deployment → ReplicaSet → поды; удалённый под сразу заменён новым с другим именем.
  • Service — имя и виртуальный IP для подов по метке; 30 запросов — 10, 9, 11; балансировка соединений (L4).
  • ConfigMap: файл обновился в работающем поде (2–69 с), переменная окружения — только после перезапуска.
  • Под без нужной метки выпал из Service и получил замену, но продолжил работать.

На собеседовании

Что такое Pod, Deployment и Service?

Pod — минимальная единица запуска: один или несколько контейнеров с общей сетью и томами, эфемерный. Deployment описывает шаблон пода и число копий, управляет ReplicaSet и обновлениями. Service даёт постоянное имя и адрес группе подов, отобранных по меткам, и балансирует между ними.

  • Цикл согласования: контроллеры приводят действительное состояние к желаемому.
  • Связь объектов — метки и селекторы, а не имена.
  • Service по умолчанию — L4: долгие соединения не перераспределяются.
Почему Service не отдаёт ни одного пода? 
kind: Deployment
spec:
  selector: { matchLabels: { app: payment } }
  template:
    metadata: { labels: { app: payment, tier: backend } }
---
kind: Service
spec:
  selector: { app: payments }
  ports: [{ port: 80, targetPort: 8080 }]

Селектор сервиса — app: payments, а у подов метка app: payment: ни один под не подходит, EndpointSlice пуст, запросы к сервису не проходят. Проверяют командой kubectl get endpointslices -l kubernetes.io/service-name=.... Метки шаблона, селектора Deployment и селектора Service должны совпадать.

Как передать конфигурацию и секреты в под?

ConfigMap для обычных настроек и Secret для паролей и ключей; подключаются как переменные окружения или как файлы в томе. Переменные читаются при старте контейнера, файлы обновляются в работающем поде с задержкой. Secret в base64 — не шифрование: нужны RBAC, шифрование etcd или внешнее хранилище секретов.

  • ConfigMap с хешем в имени — изменение конфигурации запускает выкатку.
  • External Secrets, Vault, sealed secrets — секреты вне git в открытом виде.

Что происходит, когда под или узел падает?

Упавший контейнер kubelet перезапускает на месте по restartPolicy. Удалённый или потерянный под ReplicaSet пересоздаёт, планировщик размещает его на подходящем узле. Service убирает неготовый под из endpoints, поэтому трафик идёт только на живые поды.

  • Отказ узла обнаруживается с задержкой: поды переносятся через минуты.
  • PodDisruptionBudget защищает от одновременного вывода многих подов при обслуживании узлов.
