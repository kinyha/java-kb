Lambdas

Лямбда — короткая запись реализации функционального интерфейса, то есть интерфейса с одним абстрактным методом. Тип лямбды задаёт контекст: одно и то же x -> x + 1 может быть Function<Integer, Integer> или IntUnaryOperator. Компилятор кладёт тело в приватный метод lambda$..., а на месте выражения ставит invokedynamic. При первом выполнении LambdaMetafactory создаёт в памяти скрытый класс, реализующий интерфейс. Лямбда без захвата — один объект на всё время работы, захватывающая — новый объект на каждое вычисление. Захватывать можно только фактически final локальные переменные. Ссылка на метод — сокращённая лямбда, но с отличием: получатель expr::method вычисляется один раз, при создании. Стандартные интерфейсы java.util.function не бросают checked-исключений. Их обобщённые версии упаковывают примитивы — в демо List<Integer> с Function оказался в 10 раз медленнее int[] с IntUnaryOperator.

От анонимного класса к ссылке на метод

Платежи нужно сортировать по сумме, фильтровать по валюте, считать комиссию — и каждый раз передавать в метод кусок поведения. До Java 8 это был анонимный класс в пять строк. Демо LambdaDemo.java пишет один компаратор тремя способами:

Comparator<Payment> c1 = new Comparator<>() { public int compare(Payment a, Payment b) { return Long.compare(a.amount(), b.amount()); } };
Comparator<Payment> c2 = (a, b) -> Long.compare(a.amount(), b.amount());
Comparator<Payment> c3 = Comparator.comparingLong(Payment::amount);
== from anonymous class to method reference
[p-2, p-1, p-3] [p-2, p-1, p-3] [p-3, p-1, p-2]

Синтаксис: параметры, стрелка, тело. Типы параметров компилятор выводит из целевого типа — Comparator<Payment> требует compare(Payment, Payment). Тело — выражение или блок в фигурных скобках с return. Лямбда сама по себе типа не имеет: var f = x -> x не компилируется, потому что неоткуда узнать интерфейс. Функциональный интерфейс — любой интерфейс с ровно одним абстрактным методом; default-методы и методы Object не считаются, поэтому Comparator с его equals и десятком default-методов — функциональный. Аннотация @FunctionalInterface необязательна, но заставляет компилятор проверить это правило. Третий вариант — комбинатор comparingLong со ссылкой на метод: читается как описание и собирается дальше (reversed(), thenComparing).

Демо подтверждает: две итерации цикла дали один и тот же объект для лямбды без захвата и два разных для лямбды, захватившей n. Ни то ни другое спецификация не гарантирует — она лишь разрешает не создавать новый объект, — поэтому сравнивать лямбды через == или полагаться на их идентичность (как ключ карты, как слушателя для последующего снятия) нельзя: удалить слушателя, переданного как this::onEvent, повторным this::onEvent не получится — это другой объект. Аллокацию захватывающей лямбды в горячем цикле JIT часто убирает анализом убегания из JIT.

Захват и ссылки на методы

Лямбда видит локальные переменные метода, только если они фактически final — им ничего не присваивают после инициализации. Причина та же, что у анонимных классов: захват — копия значения, а лямбда может выполниться позже и в другом потоке, когда переменной уже нет в стеке. Поля объекта и статические поля захватываются через this или класс, и их менять можно — но тогда лямбда разделяет изменяемое состояние, что в параллельных стримах из Parallel Streams превращается в гонку. this в лямбде — объект внешнего метода, лямбда не вводит новую область имён: объявить в ней переменную с именем уже существующей локальной нельзя.

Function<String, Integer> parse = Integer::parseInt;          // статический метод
ToLongFunction<Payment> bound = service::fee;                 // метод конкретного объекта
Function<Payment, String> unbound = Payment::currency;        // метод аргумента: p -> p.currency()
Function<String, StringBuilder> newSb = StringBuilder::new;   // конструктор
== method reference kinds
42 150 USD p-9 xy

Четыре вида ссылок на методы. Статический — Integer::parseInt. Связанный — service::fee, метод конкретного объекта. Несвязанный — Payment::currency, где первый параметр функции становится получателем: p -> p.currency(). Конструктор — StringBuilder::new, перегрузку выбирает целевой тип: здесь StringBuilder(String). Ссылка на метод обычно читается лучше лямбды, которая просто передаёт аргументы дальше; если нужны преобразования или несколько вызовов — лямбда.

Тонкое отличие связанной ссылки от «эквивалентной» лямбды: выражение слева от :: вычисляется один раз, при создании ссылки. currentRate()::toString вызвал currentRate() сразу и запомнил результат — три вызова get() вернули один и тот же курс. Лямбда () -> currentRate().toString() вызывает его на каждый get() — и увидит новый курс. Так же с null: nothing::length бросает NullPointerException в момент создания, а лямбда — только при вызове. Если поставщик значения должен быть ленивым — нужна лямбда.

Упаковка, исключения и отладка

== primitive specializations avoid boxing
10M fees: List<Integer> + Function 79 ms, int[] + IntUnaryOperator 8 ms (8493 8493)

Обобщения не работают с примитивами (Generics), поэтому Function<Integer, Integer> принимает и возвращает объекты: каждое значение больше 127 — новый Integer. На 10 миллионах комиссий вариант со списком обёрток и Function в 10 раз медленнее массива с IntUnaryOperator: аллокации, разыменование, нагрузка на сборщик. Для этого в java.util.function 43 интерфейса вместо десятка: IntPredicate, ToLongFunction, LongBinaryOperator и другие, а у стримов — IntStream, mapToLong из Stream API. В горячем коде с числами выбирают примитивные версии.

== checked exceptions do not fit java.util.function
wrapped: no such file: missing.csv

Методы стандартных интерфейсов не объявляют checked-исключений, и files.forEach(LambdaDemo::read), где read бросает IOException, не компилируется. Варианты: обернуть внутри лямбды в unchecked-исключение (UncheckedIOException существует ровно для этого), как делает адаптер unchecked в демо; объявить свой функциональный интерфейс с throws; для стримов с ошибками — собирать результаты или ошибки явно. Чего делать не стоит — «хитрые» обёртки, которые обманывают компилятор и выбрасывают checked-исключение без объявления (sneaky throw): вызывающий не узнает, что его нужно ловить.

В стеке исключения лямбда видна как lambda$main$10 — синтетический метод с номером по порядку в классе, а скрытый класс $$Lambda между forEach и ним JVM не показывает. При отладке длинных цепочек из лямбд номера мало что говорят; хорошая практика — выносить нетривиальную логику в именованный метод и передавать ссылку на него: в стеке будет нормальное имя, а метод можно протестировать отдельно.

Ссылка на метод obj::m — то же самое, что лямбда () -> obj.m().

Выражение obj вычисляется один раз, при создании ссылки, — в демо currentRate()::toString вызвал currentRate() один раз на три get(), а лямбда — три раза. И null::length падает при создании, а не при вызове.

  • Лямбда реализует функциональный интерфейс; тип задаёт контекст, var не работает.
  • Тело — приватный метод lambda$...; на месте выражения invokedynamic, bootstrap LambdaMetafactory создаёт скрытый класс.
  • Без захвата — один объект; с захватом — новый на каждое вычисление; на идентичность лямбд полагаться нельзя.
  • Захват — копия фактически final переменной; this — внешний объект.
  • Ссылки на методы: статические, связанные, несвязанные, конструкторы; получатель связанной вычисляется один раз.
  • Обобщённые интерфейсы упаковывают примитивы — для чисел IntUnaryOperator, ToLongFunction.
  • Checked-исключения не проходят через java.util.function: оборачивать или свой интерфейс.

На собеседовании

Что такое функциональный интерфейс и как лямбда к нему относится?

Интерфейс с ровно одним абстрактным методом; default-методы и методы Object не считаются. Лямбда — реализация этого метода, а её тип определяется контекстом: переменной, параметром, возвращаемым значением. @FunctionalInterface заставляет компилятор проверить правило. Стандартные интерфейсы — Function, Predicate, Consumer, Supplier, операторы и их примитивные версии.

  • Компилятор кладёт тело в приватный метод и ставит invokedynamic; LambdaMetafactory создаёт скрытый класс при первом выполнении.
  • Лямбда без захвата — один объект, с захватом — новый на вычисление.

Почему лямбда может использовать только effectively final переменные?

Лямбда получает копию значения локальной переменной, а выполниться может позже и в другом потоке, когда метода уже нет в стеке. Если бы переменную можно было менять, копия и оригинал разошлись бы. Поэтому разрешены только переменные, которым после инициализации ничего не присваивают. Поля объекта менять можно — они доступны через this.

  • Захваченное значение — параметр синтетического метода и поле объекта лямбды.
  • Обход через массив или AtomicLong меняет разделяемое состояние — в параллельном коде гонка.
Почему слушатель не отписывается? 
public void start() { bus.subscribe(this::onPayment); }
public void stop()  { bus.unsubscribe(this::onPayment); }   // слушатель продолжает получать события

Каждое вычисление this::onPayment — новый объект: ссылка захватывает this. unsubscribe ищет другой экземпляр, не равный подписанному, и ничего не удаляет. Нужно сохранить слушателя в поле (private final Consumer<Payment> listener = this::onPayment;) и использовать его в обоих методах — или получать из subscribe объект подписки и закрывать его.

Какие бывают ссылки на методы?

Четыре вида: на статический метод (Integer::parseInt), на метод конкретного объекта (service::fee), на метод произвольного объекта типа, где первый параметр становится получателем (Payment::currency), и на конструктор (ArrayList::new). Ссылка — сокращение лямбды, которая только передаёт аргументы в метод.

  • Получатель связанной ссылки вычисляется один раз, при создании; null::m падает сразу.
  • Перегрузку и конструктор выбирает целевой тип.

Как быть с checked-исключениями внутри лямбд?

Методы стандартных функциональных интерфейсов не объявляют checked-исключений, поэтому вызов метода с throws IOException в лямбде не компилируется. Обычно оборачивают в unchecked (UncheckedIOException) внутри лямбды или адаптером, либо объявляют свой функциональный интерфейс с throws.

  • Sneaky throw обманывает компилятор — вызывающий не узнает об исключении.
  • В стримах ошибки часто собирают как значения, а не бросают.
