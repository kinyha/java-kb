Linux Basics

При сбое платежа Linux помогает отделить состояние программы от состояния её ресурсов. Процесс может жить, но слушать другой адрес; файл может существовать, но быть недоступным через каталог; лог может исчезнуть, продолжая занимать место. Команда полезна, когда отвечает на конкретный вопрос об этой границе. Сначала связывают нужный процесс, сокет, путь и время ошибки, затем выбирают действие по найденной причине. Перезапуск до сбора этих фактов часто стирает самые полезные следы.

Живой процесс ещё не означает, что платёжный сервис доступен

Платежи перестали проходить, но контейнер всё ещё работает. Сначала выясняем, какой процесс обслуживает приложение и где он слушает запросы. PID оболочки запуска, PID JVM и PID внутри контейнера могут различаться. Для сервисов под systemd отправной точкой служит unit; в контейнере команды выполняют в нужном пространстве процессов и сети.

systemctl status payment.service              # Состояние unit и последние сообщения.
ps -p "$pid" -o pid,ppid,user,stat,etime,args   # Кто запустил процесс, под кем и с какими аргументами.
ss -ltnp '( sport = :8080 )'                   # TCP-слушатель: адрес, порт и доступные сведения о владельце.
lsof -nP -a -p "$pid" -iTCP -sTCP:LISTEN       # Только TCP-слушатели именно этого процесса.

Переменная pid здесь обозначает найденный PID приложения. ss с ключами -ltnp выбирает слушающие TCP-сокеты, оставляет числовые порты и показывает процесс, когда это разрешено. Адрес 127.0.0.1:8080 означает доступ через loopback данного сетевого пространства. Он не равен прослушиванию всех внешних интерфейсов. Отсутствие процесса в колонке владельца также может быть ограничением прав просмотра.

В LinuxDemo.sh режим service запускает собственный слушатель на loopback. Python нужен только для модели процесса: HTTP и списаний в нём нет. Демо получает PID своего ребёнка и порт из сообщения готовности, выполняет команды, затем посылает этому ребёнку SIGTERM. Фрагмент:

child_pid=$!                                  # PID именно программы, которую запустило демо.
ready                                        # Слушатель уже создан, обработчик SIGTERM установлен.
read -r port < "$work_dir/ready"
kill -0 "$child_pid"                          # Проверка существования и права послать сигнал.
ps -p "$child_pid" -o comm=                   # Имя команды, без заголовка.
ss -H -ltnp "( sport = :$port )"               # Находим конкретный слушатель.
lsof -nP -a -p "$child_pid" -iTCP -sTCP:LISTEN -F c
kill -TERM "$child_pid"                       # Просим остановить собственный процесс.
wait "$child_pid"                             # Отдельно подтверждаем выход.
kill -0 before TERM=true
ps command=python3
ss=LISTEN 127.0.0.1:<port>
lsof command=python3
TERM exit=0
log=INFO stopped by SIGTERM

Это вывод обвязки: она оставляет нужные поля команд и заменяет выбранный ОС порт маркером <port>. Процесс существовал и слушал loopback. SIGTERM вызвал его обработчик, тот записал строку и завершился с кодом 0. kill -0 сам по себе не проверил ни приём HTTP, ни доступность банка. Даже найденный LISTEN подтверждает только локальную готовность принимать соединения; состояние маршрута и ответ приложения проверяют отдельно.

SIGTERM даёт программе выполнить остановку. SIGKILL завершает её без обработчика и shutdown hooks; он не заменяет выяснение причины и не отменяет уже сохранённый платёж. После сигнала ещё проверяют выход и работу supervisor: тот может сразу запустить новый PID. Механизм сигналов — в Processes & Threads, порядок остановки Spring — в Boot Startup & Shutdown.

Все четыре режима демо проверены в отдельном Linux-контейнере под обычным пользователем. Нужны Bash, GNU coreutils/grep, procps-ng, iproute2, lsof и Python 3. Из examples/os: bash LinuxDemo.sh service. Остальные команды — в README. Демо создаёт собственный временный каталог, завершает своих детей и удаляет файлы через trap.

Расход CPU, ожидание ресурса и очередь запросов требуют разных проверок

Платёж долго отвечает. Одного показателя CPU мало: поток может считать, ждать банк, стоять на замке или ждать накопитель. ps даёт состояние и накопленные сведения; top помогает смотреть изменения. У procps-ng ключ -H показывает потоки, -p ограничивает выбор PID.

top -H -p "$pid"                              # Какие потоки потребляют CPU в динамике?
ps -L -p "$pid" -o pid,tid,stat,pcpu,comm      # Потоки и состояние; %CPU у ps имеет свой интервал учёта.
ss -tnp '( dport = :443 )'                    # Исходящие TCP-соединения к этому порту.
lsof -nP -p "$pid"                           # Какие файлы, сокеты и другие ресурсы удерживает процесс?
cat "/proc/$pid/limits"                       # Пределы самого процесса, например открытых файлов.

Load average в Linux отражает число готовых задач и задач в непрерываемом ожидании за разные промежутки. Это не процент занятого CPU. Высокая нагрузка при свободном CPU может указывать на ожидание I/O. Процент CPU также зависит от инструмента и режима представления; значение около 100 у процесса не обязательно означает занятость всех ядер.

У установленного TCP-соединения Recv-Q показывает данные, ещё не забранные приложением, Send-Q — отправленные данные, ещё не подтверждённые другой стороной. Для LISTEN эти колонки описывают очередь приёма и её предел, а не байты ответа. ESTABLISHED тоже не подтверждает успешный платёж: соединение может ждать ответ протокола. Детали TCP — в TCP & UDP.

Когда число открытых файлов приблизилось к лимиту, новое соединение или файл может не открыться. Считают ресурсы процесса и ищут их владельца. Простое число строк lsof не равно числу fd: вывод включает также отображения файлов, рабочий каталог и другие записи. Для fd смотрят /proc/<pid>/fd и соответствующие строки lsof. Рост лимита без устранения утечки лишь откладывает отказ.

Под капотом: команду нужно выполнять в пространстве нужного сервиса

PID и видимые сокеты зависят от пространств имён. Процесс внутри контейнера может иметь другой PID на хосте, а его 127.0.0.1 относится к другой сети. Прежде чем связывать вывод ps и ss, выясняют, откуда выполнены команды. Для JVM дальше сопоставляют нативный поток с диагностикой Java. Дамп потоков помогает понять ожидание, профиль — найти горячий код; Linux-состояние само по себе не раскрывает бизнес-причину.

Память Java heap и RSS процесса различаются. Контейнер дополнительно учитывает память по правилам cgroup. Команда top не заменяет данные лимита группы и события OOM. Эта модель и нужные показатели разобраны в Virtual Memory.

Доступ к квитанции проверяется на каждой части пути

Сервис не может прочитать квитанцию, хотя у файла выставлено 666. Для чтения нужно пройти ко всем каталогам пути, затем открыть файл. x у каталога разрешает поиск имени и проход. r у каталога разрешает читать список имён, а w вместе с x позволяет менять записи каталога. Поэтому права файла и права пути отвечают на разные вопросы.

Права выбираются для владельца, группы или остальных. Если процесс подходит как владелец, ядро использует его биты; более широкие биты группы не дополняют их автоматически. Значения r=4, w=2, x=1 образуют три восьмеричные цифры: 640 означает rw владельцу, r группе, ничего остальным. Важно проверить реального пользователя и группы процесса, а не только своего терминала.

id                                           # Мои UID и группы; у сервиса они могут отличаться.
ls -ld /srv/payment /srv/payment/receipts      # Права каталогов на пути, без чтения их содержимого.
ls -l /srv/payment/receipts/p42.txt            # Владелец, группа, режим самого файла.
chmod u+x "$work_dir/receipts"                 # Добавить владельцу проход, сохранив остальные биты.

Режим permissions работает обычным пользователем со своими файлами. Сначала у файла 666, у содержащего каталога 600. После добавления x чтение проходит. Затем файл получает 400, но каталог оставляет владельцу w+x, и имя файла удаётся удалить. Ключевые строки:

chmod 666 "$work_dir/receipts/p42.txt"         # Сам файл разрешает чтение и запись.
chmod 600 "$work_dir/receipts"                 # У каталога нет права прохода.
if cat "$work_dir/receipts/p42.txt" >/dev/null 2>&1; then
    readable=true
else
    readable=false
fi
chmod u+x "$work_dir/receipts"                 # Теперь можно дойти до файла.
cat "$work_dir/receipts/p42.txt"
chmod 400 "$work_dir/receipts/p42.txt"          # Содержимое стало доступно лишь для чтения владельцу.
rm -- "$work_dir/receipts/p42.txt" </dev/null  # Удаляем имя через доступный для записи каталог.
(
    umask 027                                # Из исходных прав новых объектов убираем эти биты.
    : > "$work_dir/new-file"
    mkdir "$work_dir/new-directory"
)
file mode=666, directory mode=600
read with missing directory x=false
read after chmod u+x=paid
file writable=false
unlink with directory wx=true
umask 027: file=640, directory=750

umask убирает биты из запрошенного режима при создании объекта. У обычного нового файла исходный режим часто 666, у каталога — 777. Для маски 027 получаем 0666 & ~0027 = 0640 и 0777 & ~0027 = 0750. Это битовая маска, а не арифметическое вычитание. Уже существующий файл от смены umask не меняется; наследуемые ACL могут дополнительно влиять на создание.

Исправление выбирают по требуемому доступу: правильный владелец и группа, проход нужным участникам, чтение или запись конкретного ресурса. Массовое chmod 777 открывает доступ слишком широко и скрывает причину. Если обычные биты выглядят подходящими, проверяют ACL, ограничения SELinux/AppArmor и режим монтирования. Право пользователя root делает его неподходящим для этого опыта: он может обходить обычную проверку доступа.

Под капотом: sticky bit защищает записи общего каталога

В общем каталоге с sticky bit, например типичном /tmp, права w+x ещё не дают любому участнику удалить чужое имя. Добавляется проверка владельца файла, каталога или соответствующей привилегии. Демо работает в собственном частном каталоге, поэтому показывает обычную границу удаления. Бит x на обычном файле, в отличие от каталога, относится к запуску; JAR, который JVM открывает как данные, не обязан быть исполняемым файлом ОС.

Оболочка соединяет потоки, а код конвейера может скрыть ошибку чтения

Для платежа p42 ищут ошибку в логе и считают строки. Конвейер grep | wc выдал 0, и команда закончилась успешно. Но это могло означать как отсутствие совпадений, так и невозможность открыть лог. Ноль строк без проверки причины — слабое доказательство.

У команды обычно есть stdin=0, stdout=1 и stderr=2. Оператор | соединяет stdout первой команды со stdin следующей; stderr остаётся отдельно. В Bash итоговый код конвейера по умолчанию берётся у последней команды. При pipefail выбирается код самой правой команды с ненулевым результатом, а если все успешны — 0.

grep -nF 'payment=p42' "$log"                  # -F: буквальная строка, -n: номер совпавшей строки.
grep -nE 'ERROR|WARN' "$log"                   # -E: расширенное регулярное выражение.

set +o pipefail
grep -F 'payment=p42' "$work_dir/missing.log" 2> "$work_dir/grep.err" |
    wc -l > "$work_dir/count"                 # wc успешно считает пустой вход.
snapshot=("$?" "${PIPESTATUS[@]}")             # Общий код и коды участников: копируем сразу.

set -o pipefail
grep -F 'payment=p42' "$work_dir/missing.log" 2> "$work_dir/grep.err" |
    wc -l > "$work_dir/count"
snapshot=("$?" "${PIPESTATUS[@]}")             # Теперь ошибка grep влияет на итог конвейера.
no matches: count=0, pipeline=0, grep=1
missing file without pipefail: count=0, pipeline=0, grep=2
missing file with pipefail: count=0, pipeline=2, grep=2

Это первая часть вывода режима pipeline. В первом опыте лог существует, но p99 не найден. Для grep код 0 означает совпадение, 1 — его отсутствие, 2 — ошибку. В двух следующих опытах имени файла вообще нет. Демо на время сбора кодов отключает errexit, чтобы показать оба варианта и продолжить. Одна дополнительная команда после конвейера уже могла бы заменить PIPESTATUS, поэтому массив копируется немедленно.

Перенаправления выполняются слева направо. >file открывает файл для stdout и обычно обрезает прежнее содержимое; >>file добавляет в конец. 2>&1 копирует текущее назначение stdout в stderr. Он не создаёт правило «stderr всегда следует за будущим stdout».

bash -c 'printf "%s\n" OUT; printf "%s\n" ERR >&2' > "$work_dir/both" 2>&1
# Сначала stdout стал файлом, затем stderr получил то же назначение.

escaped=$(bash -c 'printf "%s\n" OUT; printf "%s\n" ERR >&2' 2>&1 > "$work_dir/only-out")
# Сначала stderr получил прежний stdout; потом в файл ушёл только новый stdout.
# Подстановка команды здесь забрала ERR из прежнего stdout.
>file 2>&1: OUT,ERR
2>&1 >file: file=OUT, escaped=ERR

В командах для файлов кавычки сохраняют путь одним аргументом, а -- отделяет параметры от имени, которое могло бы начинаться с дефиса. Поиск по логу лучше ограничить временем, файлом и идентификатором платежа. Для структурированного JSON важна структура полей: совпавшая строка grep не доказывает, что совпало именно нужное поле.

Под капотом: pipe ограничен, а set -e зависит от контекста

Pipe хранит конечное количество байтов. Писатель заполненного канала ждёт читателя; если читателей не осталось, запись получает ошибку и возможен SIGPIPE. Команды конвейера работают совместно, а не передают друг другу весь готовый файл после завершения. Ожидание и EOF подробнее разобраны в I/O Models и Processes & Threads.

set -e не является универсальным обработчиком ошибок. Его действие зависит от условий if, списков команд, конвейеров и других контекстов Bash. Код 1 у grep может быть нормальным результатом поиска. В важном скрипте ожидаемые исходы обрабатывают явно, а остальные ошибки сохраняют вместе с контекстом.

Лог исчез из каталога, но его данные удерживает открытый дескриптор

Место закончилось. Старый app.log удалили, список файлов стал короче, а df всё ещё показывает занятое пространство. Удаление имени и закрытие открытого файла — разные события. Писатель может продолжать держать прежний файл и даже писать в него, пока новые читатели уже не находят имя.

df -h /var/log                               # Вместимость и использование файловой системы этого пути.
df -i /var/log                               # Может закончиться число inode, хотя байты ещё есть.
du -xhd1 /var/log                            # Занятые блоки доступных файлов, один уровень, без смены ФС.
lsof -nP +L1                                 # Открытые файлы с числом жёстких ссылок меньше 1.
lsof -nP -a -p "$pid" +L1                     # Ограничиваем поиск конкретным процессом.

df получает состояние файловой системы. du обходит видимые имена и суммирует использование файлов, к которым удалось дойти. Эти множества расходятся при удалённых открытых файлах, недоступных каталогах, других точках монтирования и особенностях хранения. У разреженных файлов логический размер также может быть больше числа занятых блоков; du --apparent-size отвечает на другой вопрос.

Режим deleted-log запускает собственного писателя. Тот создаёт четыре МиБ данных, сохраняет номер открытого fd и ждёт. Родитель удаляет имя и смотрит оставшийся ресурс:

read -r held_fd < "$work_dir/ready"            # Номер fd сообщил сам дочерний писатель.
rm -- "$work_dir/app.log"                     # Имя удалено, у ребёнка остаётся открытая ссылка.
lsof -nP -a -p "$child_pid" +L1 -F n          # Находим app.log (deleted) у этого ребёнка.
stat -Lc '%s' "/proc/$child_pid/fd/$held_fd"    # Размер того же открытого файла: 4194304 байта.
held_path=/proc/$child_pid/fd/$held_fd
kill -TERM "$child_pid"                       # В этом опыте ребёнок завершится стандартным действием сигнала.
wait "$child_pid" || true                     # Статус от сигнала ожидаем, дожидаемся освобождения ресурсов.
test -e "$held_path"                          # После выхода прежнего дескриптора уже нет.
path after unlink exists=false
lsof reports deleted=true
open descriptor bytes=4194304
descriptor after process exit exists=false

В сервисе сначала находят владельца старого fd и предусмотренный способ переоткрыть лог. Сигнал для перечитывания или ротации зависит от приложения; SIGHUP не гарантирует одинаковое действие всем программам. Logrotate тоже должен согласоваться с писателем. После изменения подтверждают, что старый дескриптор ушёл, новый лог читается и место действительно вернулось.

Если файловая система заполнена, ошибка может появиться при записи, синхронизации или отложенном выделении блоков. Отдельно проверяют inode, квоту, нужный mount и права просмотра. Удаление случайных файлов до выяснения этих границ способно потерять диагностику и оставить причину на месте. Контракт записи и fsync — в I/O Models.

Причину платежа восстанавливают по времени, процессу и месту записи лога

Идентификатор платежа связывает события приложения, а время отделяет нужный запуск от предыдущего. Лог может идти в файл, журнал systemd или stdout/stderr контейнера. Путь «по привычке» не гарантирует, что это нужный поток: после перенаправления или ротации место записи могло измениться.

journalctl -u payment.service --since '10 minutes ago' --no-pager
# Для установки с systemd: сообщения конкретного unit за нужный промежуток.

docker logs --since 10m --tail 200 payment
# Для этого контейнера: доступные через настроенный logging driver сообщения stdout/stderr.

tail -n 200 -- "$log"                          # Конец конкретного файла, без чтения всего архива.
tail -F -- "$log"                             # GNU tail следует имени и повторяет поиск после замены.
grep -nF -- 'payment=p42' "$log"               # Буквальный идентификатор и номера строк.

Journalctl и docker logs относятся к своим установкам. Они не запускались в демо: изолированный слушатель пишет в собственный временный файл. Поддержка чтения Docker-логов зависит от logging driver и конфигурации. Для файла GNU tail -f по умолчанию следит за дескриптором, а tail -F — за именем с повторными попытками; это существенно при замене файла.

В сообщениях ищут начало запуска, первую ошибку и цепочку конкретного платежа: приняли запрос, вызвали банк, получили ответ, сохранили результат. Отсутствие последней строки ещё не доказывает, что банк не списал деньги. После таймаута или остановки состояние сверяют по бизнес-протоколу. Команды ОС дают факты о процессе и ресурсах, но не заменяют эту сверку.

Сначала фиксируют время, запуск, PID, адрес и наблюдаемую ошибку. Затем проверяют гипотезу на конкретном ресурсе. Изменение имеет проверяемый результат: квитанция читается тем же UID, нужный порт доступен, старый fd исчез или очередь перестала расти. Для ядра, сетевого маршрута, JVM и платежной логики есть свои инструменты; полезно остановиться на той границе, которую команда действительно подтверждает.

Linux-диагностика связывает объекты: процесс с его сокетом, пользователя с путём, открытый fd с файлом, команду с потоками и кодом выхода. У каждой проверки узкая область доказательства. Сигнал отправлен — ещё не значит процесс вышел; строк нет — ещё не значит лог прочитан; имя удалено — ещё не значит данные освободились. Следующий шаг выбирают по установленной причине.

На собеседовании

Java-сервис не отвечает. С чего начнёшь диагностику в Linux?

Сначала связываю ошибку со временем и нужным запуском. Проверяю процесс через supervisor и ps, затем слушающий адрес и владельца сокета через ss или lsof. Живой PID ещё не означает здоровый сервис. Дальше различаю высокий CPU и ожидание: смотрю потоки в top, стеки Java, очереди и соединения. Логи беру из фактического источника и ищу цепочку конкретного запроса. Действие выбираю после этой проверки и затем подтверждаю результат тем же наблюдением.

  • Проверяю контекст контейнера: пространства PID и сети, квоты cgroup. Свободный хост и loopback хоста могут не описывать доступные ресурсы сервиса.
  • Рестарт стирает состояние очередей, соединений и потоков. Если доступность позволяет, перед ним сохраняю минимальную диагностику; после запуска проверяю также бизнес-состояние незавершённых платежей.
  • Зомби уже не исполняет код, поэтому очередной сигнал ему не поможет. Исправляю получение статуса родителем; для D выясняю причину ожидания в ядре.

Почему файл с 666 не читается, а файл без права записи иногда можно удалить?

Чтение требует пройти каталоги пути и иметь доступ к файлу. У каталога x разрешает поиск имени и проход; без него широкие права самого файла не помогают. Удаление меняет запись каталога, поэтому в обычном случае нужны w+x у содержащего каталога, а не w у файла. Я проверяю UID и группы процесса, все каталоги пути и выбранные для него биты. Umask влияет на создание новых объектов: убирает права из запрошенного режима, а уже существующие файлы не меняет.

  • Sticky bit добавляет правила удаления в общем каталоге. ACL и защитные механизмы среды тоже могут изменить итог проверки; chmod не описывает всю политику доступа.
  • Числовой UID внутри контейнера и владелец файла на подключённом томе должны согласоваться. Совпадения удобного имени пользователя недостаточно.
  • Исполняемый каталог и исполняемый файл — разные права. Для java -jar JVM читает JAR как данные; право запуска требуется самой запускаемой программе или скрипту.

Почему grep | wc завершился с кодом 0, хотя grep не смог открыть файл?

В Bash по умолчанию итог берётся у последней команды. Wc может успешно посчитать пустой вход и скрыть ошибку grep. Pipefail делает итогом самый правый ненулевой код, а PIPESTATUS позволяет посмотреть участников; его копирую сразу. У grep отдельно различаю найденные строки, отсутствие совпадений и ошибку. Stderr также не идёт в обычный pipe автоматически. Если объединяю его со stdout, учитываю порядок: 2>&1 копирует текущее назначение, поэтому >file 2>&1 и 2>&1 >file дают разный результат.

  • Ранний выход читателя, например head после нужного количества строк, может вызвать SIGPIPE у писателя. Ненулевой код такого конвейера нужно оценить по задаче, а не объявлять все исходы аварией.
  • При передаче аргументов сохраняю границы кавычками и использую --, когда имя может выглядеть как ключ. Корректный статус не спасает команду, которая искала другой путь.
  • Ожидание всего конвейера и поиск единственной совпавшей строки — разные операции. Для большого лога ограничиваю данные и время, а данные платежа связываю по структуре и идентификатору.
После включения pipefail отсутствие совпадений ломало скрипт. Разработчик дописал || true. Какой сбой он скрыл?

Теперь будут подавлены также ошибка чтения файла и другие ненулевые исходы конвейера. Код 1 grep можно считать ожидаемым «не найдено», но код 2 означает ошибку. Нужно обработать эти исходы отдельно и сохранить диагностику остальных команд. Безусловное || true одинаково трактует отсутствие платежа и невозможность прочитать данные о нём.

Почему df и du показывают разное, а удаление лога не освободило место?

Df показывает учёт файловой системы, du обходит видимые файлы. После удаления имени открытый файл может оставаться у писателя, поэтому du уже не видит этот путь, а место ещё занято. Проверяю lsof +L1, нахожу процесс и способ переоткрыть его лог, затем подтверждаю закрытие старого fd. Дополнительно проверяю нужную файловую систему, inode, доступ к каталогам и единицы сравнения. Логический размер разреженного файла тоже отличается от его занятых блоков.

  • Смена имени при ротации и следование открытому дескриптору расходятся. Выбираю режим tail и процедуру ротации, которые соответствуют поведению писателя.
  • Ротация через копирование и усечение имеет окно для конкурентных записей. Потеря или повтор строк требуют учёта в выбранном протоколе; команда ротации сама не делает запись атомарной.
  • Свободные байты не исключают исчерпанную квоту или inode. Проверяю вид отказа и границу учёта прежде, чем удалять новые данные.
