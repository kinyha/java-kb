Live Coding

На live coding нужно сделать путь к решению проверяемым. Сначала согласуй ответ на маленьком примере, затем объясни простой подход и работу, которую хочешь убрать. У каждого изменения должен сохраняться смысл состояния. Код проверяется на случаях, где правдоподобная ошибка даёт другой результат. В конце назови сложность, цену памяти и границы решения.

Сначала уточни, какой ответ будет считаться правильным

Интервьюер просит: «У платёжного сервиса повторяются уведомления. Найди первый дубликат». Можно быстро написать HashSet и всё равно решить другую задачу. «Первый» может означать ID, впервые появившийся раньше других, или повторную доставку, которую раньше других увидел сервис. На входе [A,B,B,A] эти ответы различаются.

Уточнение должно менять решение. Спроси: «Возвращаем ID или индекс? Первый по моменту повторного получения? ID сравниваем по содержимому? Если повтора нет, что вернуть?» Затем зафиксируй пример: «Для [A,B,B,A] возвращаю индекс 2: второй B пришёл раньше второго A». Один такой пример проверяет понимание лучше длинного пересказа.

Теперь ограничения: массив уже в порядке получения, ID — непустые строки без null, пустой массив допустим, вход сохраняется, отсутствие ответа обозначается −1. Узнай размер входа и длину ID. Для учебного метода пусть n≤100000, длина ID≤64 символов. Это допускает память под множество. Сортировка меняла бы порядок и исходные позиции, поэтому её цена включает сохранение индексов и копию входа.

Простой перебор уже может показать ошибку в трактовке. В правильной версии внешний цикл идёт по моменту повторной доставки j, а внутренний ищет совпадение среди более ранних i. Если поменять циклы, первым найдётся исходный A, хотя его повтор придёт позже.

static int baseline(String[] ids) {
    for (int j = 0; j < ids.length; j++) { // сначала минимизируем индекс повтора
        for (int i = 0; i < j; i++) {
            if (ids[i].equals(ids[j])) return j;
        }
    }
    return -1;
}

static int wrongOrder(String[] ids) {
    for (int i = 0; i < ids.length; i++) { // этот порядок минимизирует первый индекс
        for (int j = i + 1; j < ids.length; j++) {
            if (ids[i].equals(ids[j])) return j;
        }
    }
    return -1;
}

System.out.println("== first means different things ==");
String[] ids = {"A", "B", "B", "A"};
System.out.println("baseline=" + baseline(ids));
System.out.println("first original=" + wrongOrder(ids));

first original=3

Уточнять всё возможное заранее тоже дорого. Выбирай вопросы, от которых зависят ответ, структура данных или безопасная арифметика. Если интервьюер предлагает решить на разумных предположениях, назови их и двигайся дальше. Проверять null в коде нужно только при согласованном поведении для null: допустимое значение, ошибка или отсутствие входа — разные условия.

Удобная фраза: «Верну индекс первой повторной доставки. Проверю равенство строк по содержимому, вход не меняю, без повтора верну −1. Для [A,B,B,A] ответ 2. Верно?» Это рабочее уточнение на конкретных значениях.

Улучшение должно сохранять смысл простого решения

Перебор — исходная точка для объяснения и проверки. Для n разных ID он сравнивает каждый новый ID со всем префиксом: 0+1+…+(n−1)=n(n−1)/2 сравнений. При n=1000 это 499500. Для большого входа повторяется один вопрос: «Такой ID раньше был?» Сохраним ответ на него в множестве.

Перед чтением позиции j множество seen содержит ровно ID из позиций 0…j−1. Это инвариант — утверждение о состоянии, которое сохраняется на каждом шаге. Если ID уже есть, более ранняя доставка найдена. Если его ещё нет, добавляем и переходим к j+1. До этого все позиции проверены без повтора, поэтому найденный j минимален.

HashSet.add совмещает проверку и вставку: true означает, что элемент добавлен, false — такой элемент уже содержался. Если сначала вызвать add, а затем contains, второй вызов увидит текущий элемент. Смысл «был раньше» исчезнет. Причина результата должна быть понятна по коду на странице.

static int firstRepeat(String[] ids) {
    Set<String> seen = new HashSet<>();
    for (int j = 0; j < ids.length; j++) {
        if (!seen.add(ids[j])) return j; // add=false: такой ID был в префиксе
    }
    return -1;
}

static int wrongWrite(String[] ids) {
    Set<String> seen = new HashSet<>();
    for (int j = 0; j < ids.length; j++) {
        seen.add(ids[j]);                   // текущий элемент уже в памяти
        if (seen.contains(ids[j])) return j; // проверка всегда проходит
    }
    return -1;
}

System.out.println("== update changes the question ==");
String[] ids = {"A", "B", "B", "A"};
System.out.println("write then contains=" + wrongWrite(ids));
System.out.println("add result=" + firstRepeat(ids));

add result=2

Равенство ID относится к содержимому строк. Две доставки могут создать два объекта String с одинаковым ID. HashSet использует hashCode и equals, поэтому это повтор; сравнение ссылок через == пропустило бы его. Порядок обхода множества здесь не используется: ответ выбирается порядком массива.

System.out.println("== equal content, different objects ==");
String[] equal = {new String("p7"), new String("p7")};
System.out.println("same reference=" + (equal[0] == equal[1]));
System.out.println("repeat=" + firstRepeat(equal));
System.out.println("empty=" + firstRepeat(new String[0]));

Расскажи цену улучшения через операции. На входе без повторов выполняется n вставок; хранится до n ссылок на ID и служебные записи таблицы. При хорошем распределении хеша базовые операции HashSet имеют постоянную стоимость. Для ID ограниченной длины ожидаемое время метода O(n), дополнительная память O(n). Это оценка при указанных условиях, а не обещание одинакового времени для любых строк.

record Work(long comparisons, int inserts) {}
static Work uniqueWork(int n) {
    String[] ids = new String[n];
    for (int i = 0; i < n; i++) ids[i] = "p" + i;
    long comparisons = 0;
    for (int j = 0; j < n; j++) {
        for (int i = 0; i < j; i++) {
            comparisons++;                // считаем сравнения, а не миллисекунды
            if (ids[i].equals(ids[j])) throw new AssertionError("unique input");
        }
    }
    Set<String> seen = new HashSet<>();
    int inserts = 0;
    for (String id : ids) {
        inserts++;
        if (!seen.add(id)) throw new AssertionError("unique input");
    }
    return new Work(comparisons, inserts);
}

System.out.println("== count the repeated work ==");
Work w = uniqueWork(1000);
System.out.println("comparisons=" + w.comparisons());
System.out.println("set inserts=" + w.inserts());
== count the repeated work ==
comparisons=499500
set inserts=1000

Счётчики измеряют разные операции и доказывают устранение повторного поиска; они не сравнивают наносекунды. Если длина ID не ограничена, хеширование и сравнение строк тоже читают символы. При длине не больше L перебор требует до O(n²L), вариант с множеством при обычном распределении — O(nL). Строки уже существуют во входе: набор хранит ссылки, а не копирует их содержимое.

Фраза вслух: «Сначала O(n²) без дополнительного хранения. Заменю проверку префикса множеством. Перед каждым шагом оно содержит только прошлые ID; первый отказ add даёт нужный индекс. Выиграю время ценой O(n) памяти». После такого объяснения код занимает несколько строк. Устройство таблицы разобрано в Hash Tables, варианты задач — в Arrays & Hashing.

Проверка ищет нарушение условия, а не только красивый результат

После успешной компиляции решение ещё нужно проверить. Для каждого требования выбери вход, который отличит правильный код от правдоподобной ошибки. Пустой массив проверяет отсутствие ответа, одиночный — выход за границу, [A,B,B,A] — смысл «первого», два новых String("A") — равенство по содержимому. Одинаковые элементы, отсутствие повторов и сохранность входа проверяют другие свойства.

В задаче о двух платежах равенства суммы недостаточно: нужны два разных индекса. Перед поиском дополнения карта должна содержать только позиции i<j. Запись текущего индекса до поиска меняет это условие. Самый короткий контрпример — один платёж 7 и цель 14; две семёрки скрывают ошибку.

record Pair(int i, int j) {}

static Optional<Pair> solve(int[] amounts, int target) {
    Map<Integer, Integer> firstIndex = new HashMap<>();
    for (int j = 0; j < amounts.length; j++) {
        long need = (long) target - amounts[j]; // расширяем ДО вычитания
        if (need >= Integer.MIN_VALUE && need <= Integer.MAX_VALUE) {
            Integer i = firstIndex.get((int) need);
            if (i != null) return Optional.of(new Pair(i, j)); // i строго меньше j
        }
        firstIndex.putIfAbsent(amounts[j], j); // сохраняем самый ранний i
    }
    return Optional.empty();
}

static Optional<Pair> wrongSelf(int[] amounts, int target) {
    Map<Integer, Integer> seen = new HashMap<>();
    for (int j = 0; j < amounts.length; j++) {
        seen.putIfAbsent(amounts[j], j); // записали текущий индекс до поиска
        long need = (long) target - amounts[j];
        if (need >= Integer.MIN_VALUE && need <= Integer.MAX_VALUE) {
            Integer i = seen.get((int) need);
            if (i != null) return Optional.of(new Pair(i, j));
        }
    }
    return Optional.empty();
}

System.out.println("== a payment cannot pair with itself ==");
System.out.println("write first=" + wrongSelf(new int[]{7}, 14));
System.out.println("read first=" + solve(new int[]{7}, 14));
System.out.println("two positions=" + solve(new int[]{7, 7}, 14));

Границы чисел проверяются по арифметике самого выражения. Если target и amount — int, вычитание в int может завернуться и найти чужую сумму. Присваивание в long после вычитания уже опоздало. Расширь операнд до вычисления; если дополнение за диапазоном int, ни один элемент этого int-массива ему не равен.

static Optional<Pair> wrongInt(int[] amounts, int target) {
    Map<Integer, Integer> seen = new HashMap<>();
    for (int j = 0; j < amounts.length; j++) {
        int need = target - amounts[j]; // переполнение создаёт ложное дополнение
        Integer i = seen.get(need);
        if (i != null) return Optional.of(new Pair(i, j));
        seen.putIfAbsent(amounts[j], j);
    }
    return Optional.empty();
}

Оба опыта — из PairDemo.java. В данных разрешены отрицательные int-суммы; проверяется математическое равенство, а не равенство после переполнения.

При ошибке назови первое место, где фактическое состояние расходится с инвариантом. «В карту попал текущий индекс, поэтому вернулся Pair(0,0); перенесу запись после поиска и повторю тест с одной и двумя семёрками». Это проверяемая причина. Несвязанные изменения по очереди только прячут её.

Для небольшой задачи полезен независимый эталон: простой перебор. Здесь можно перечислить все строки из A,B,C длины 0…6 и сравнить быстрый ответ с baseline. У эталона внешний цикл j выбран непосредственно из определения ответа. Он не использует множество и потому не повторяет способ обновления быстрой версии.

static String[] input(int length, int code) {
    String[] ids = new String[length];
    String[] alphabet = {"A", "B", "C"};
    for (int i = length - 1; i >= 0; i--) {
        ids[i] = alphabet[code % 3];
        code /= 3;
    }
    return ids;
}
static void compareAll() {
    int checked = 0;
    String[] counterexample = null;
    for (int length = 0, count = 1; length <= 6; length++, count *= 3) {
        for (int code = 0; code < count; code++) {
            String[] ids = input(length, code);
            int want = baseline(ids);          // независимый перебор всех ранних пар
            if (firstRepeat(ids) != want) throw new AssertionError(Arrays.toString(ids));
            if (counterexample == null && wrongOrder(ids) != want) {
                counterexample = ids.clone(); // первый короткий случай, где версии расходятся
            }
            checked++;
        }
    }
    System.out.println("checked=" + checked);
    System.out.println("first mismatch=" + Arrays.toString(counterexample));
    System.out.println("baseline=" + baseline(counterexample));
    System.out.println("wrong order=" + wrongOrder(counterexample));
}

System.out.println("== small exhaustive oracle ==");
compareAll();
== small exhaustive oracle ==

first mismatch=[A, B, B, A]
baseline=2
wrong order=3

Фрагмент OracleDemo.java использует baseline, firstRepeat и wrongOrder из предыдущих шагов. Перечислено 1+3+9+27+81+243+729=1093 массива. Случай [A,B,B,A] появился автоматически, а не был подставлен в поиск.

Такой перебор хорошо находит короткие ошибки порядка и краёв. Он охватывает конечный набор, поэтому общее доказательство через инвариант остаётся нужным. Длинные строки, null и миллионы элементов в этот опыт не входят. На собеседовании достаточно нескольких осмысленных проверок; полный перебор полезен при самостоятельной тренировке.

Заканчивай проверенным решением и точными границами

Рассуждать вслух — делать решения понятными собеседнику. Говори в моменты выбора: что уточнил, какая работа повторяется, какое состояние сохраняешь, почему индекс правильный и какой тест ломает неверную версию. Называть каждое нажатие клавиши дорого. Перед длинным молчанием скажи: «Возьму полминуты, чтобы проверить границу цикла». Это поддерживает совместный разбор.

Если застрял, уменьши вход до двух-трёх элементов и выпиши состояние вручную. Вернись к перебору: что он вычисляет заново? Какие части ответа уже известны? Если подсказка изменила подход, объясни её роль: «Сохраним только прошлые суммы — тогда дополнение проверяется одним поиском». Так видно, что ты применил идею. При изменении требования перечитай пример и инвариант: новый смысл «первого» может потребовать другой порядок, а не дополнительный if.

Оставь время на работающий вариант и тесты. Для учебной тренировки на 35 минут можно выделить 4 минуты на условие, 6 на подход, 17 на код и 8 на проверку с итогом. Это предлагаемый режим практики, а не регламент компании. Если оптимизация не складывается, покажи корректный простой вариант, его узкое место и следующий шаг. Завершённая причина и честная сложность полезнее скрытого TODO в ключевой ветке.

Итог решения занимает несколько фраз: что возвращает метод, почему, время, дополнительная память и случаи без ответа. Различай память входа, рабочее хранение и память результата. У рюкзака или графа нужны отдельные параметры, например n и m; два вложенных цикла сами по себе не означают O(n²), если указатели суммарно проходят вход один раз. Проверки с long не исправляют вычисление, которое уже произошло в int.

У метода firstRepeat память живёт один вызов и видит один массив. Для постоянного потока seen растёт с числом разных ID. Очистка или TTL меняет требование: старый повтор может снова стать «новым». Перезапуск теряет память, две копии сервиса имеют разные множества. Подмена HashSet потокобезопасным набором не делает проверку общей между процессами и не связывает её атомарно с записью платежа.

На уточнение «а в настоящем сервисе?» обозначь границу текущего решения. Долговременная идемпотентность требует общего устойчивого ключа и атомарной фиксации эффекта в согласованном хранилище; частный вариант — уникальный ключ в БД и транзакция с изменением состояния. Это уже отдельная задача о практике API и Outbox. В алгоритмической задаче остаёмся внутри согласованного массива.

Финальная фраза: «Верну минимальный индекс повторной доставки. До шага в seen только прошлые ID, поэтому отказ add даёт нужный ответ. Проверил пустой массив, одиночный ID, два равных объекта и [A,B,B,A]. При длине ID≤64 ожидаемое время O(n), дополнительная память O(n). Массив сохраняется; отсутствие ответа — −1».

  • Уточнение полезно, когда меняет ответ, выбор алгоритма или безопасность вычисления. Проверь его конкретным примером.
  • Простой перебор помогает объяснить результат и проверить оптимизацию. Инвариант связывает быстрый код с тем же условием.
  • Проверка перед обновлением состояния отличает прошлые элементы от текущего. Порядок прохода задаёт правило выбора ответа.
  • Крайний случай должен ловить конкретную ошибку: самопару, равную границу, неверный индекс, переполнение или потерю последней группы.
  • Заверши код, прогони проверки и назови время и память с нужными параметрами. Локальный алгоритм и постоянный сервис живут при разных условиях.

Задачи

Решай вслух. До открытия подсказок сформулируй ответ, ограничения и два показательных теста. После решения объясни инвариант, сложность и случай, который ломает неверную версию. Это авторские мини-собеседования на платежах; подробные доказательства паттернов есть в соседних темах Arrays & Hashing, Intervals, Sliding Window и Graph Search.

Первый повтор: уточни значение слова «первый»

Даны ID уведомлений в порядке получения. Верни минимальный индекс j, для которого есть i<j с таким же ID. Если повтора нет, верни −1. Сравнение строк — по содержимому.

0≤n≤100000, ID — непустые строки длины≤64, null отсутствует. Вход сохраняется. Перед кодом объясни, чем ответ отличается от ID с самым ранним первым появлением, который повторится когда-нибудь позже.

[A,B,B,A] → 2

Подсказка 2

Сортируй копию через comparingLong. При next.start≤end продли end через max; при разрыве выдай текущий интервал. Последний выдаётся после цикла.

Решение

«Согласовали объединение со склеиванием касания. Сортирую копию, чтобы сохранить вход. Накопленный [start,end) — объединение последней связной группы уже прочитанных интервалов. Следующий либо продолжает её, либо начинает новую после разрыва». При вложении конец берётся через max, иначе широкий интервал мог бы сжаться.

static List<Range> solve(Range[] input) {
    if (input.length == 0) return List.of();
    Range[] sorted = input.clone();       // переставляем копию; record неизменяем
    Arrays.sort(sorted, Comparator.comparingLong(Range::start)
            .thenComparingLong(Range::end)); // сравнение без вычитания long
    List<Range> result = new ArrayList<>();
    long start = sorted[0].start(), end = sorted[0].end();
    for (int i = 1; i < sorted.length; i++) {
        Range next = sorted[i];
        if (next.start() <= end) {         // касание тоже образует один интервал объединения
            end = Math.max(end, next.end());
        } else {
            result.add(new Range(start, end));
            start = next.start();
            end = next.end();
        }
    }
    result.add(new Range(start, end));     // последний накопленный интервал ещё не выдан
    return List.copyOf(result);
}

static int solve(long[] times, long width) {
    int left = 0, best = 0;
    for (int right = 0; right < times.length; right++) {
        while (times[right] - times[left] >= width) { // правая граница полуоткрытая
            left++;                           // сортировка и width>0 оставят хотя бы right
        }
        best = Math.max(best, right - left + 1);
    }
    return best;
}

Подсказка 2

Среди готовых выбирай минимальный ID через PriorityQueue. Если выдано меньше n, остался цикл; частичный список не является ответом. Повторное ребро учитывай симметрично при добавлении и снятии.

Решение

«В ready лежат все ещё не выданные этапы без оставшихся предшественников. Любой допустимый следующий этап должен быть из ready. Выбираю минимальный ID — это минимизирует ближайшую ещё не выбранную позицию ответа». В DAG такой выбор всегда продолжается до всех вершин; снятие исходящих рёбер открывает новые готовые этапы. Если ready опустела до n, оставшийся подграф имеет цикл.

Обычная очередь может после выдачи 1 положить новый 0 в конец за 2 и 3, получив [1,2,3,0]. Все зависимости соблюдены, но лексикографический минимум потерян. Куча повторно выбирает минимум из текущего множества, а не только сортирует исходные вершины.

static Optional<List<Integer>> solve(int n, Edge[] edges) {
    List<List<Integer>> next = new ArrayList<>();
    for (int i = 0; i < n; i++) next.add(new ArrayList<>());
    int[] incoming = new int[n];
    for (Edge edge : edges) {
        next.get(edge.before()).add(edge.after());
        incoming[edge.after()]++;          // повторное ребро учитывается и здесь, и при снятии
    }
    PriorityQueue<Integer> ready = new PriorityQueue<>();
    for (int i = 0; i < n; i++) if (incoming[i] == 0) ready.add(i);
    List<Integer> order = new ArrayList<>();
    while (!ready.isEmpty()) {
        int id = ready.remove();           // минимальный ID среди допустимых прямо сейчас
        order.add(id);
        for (int after : next.get(id)) {
            if (--incoming[after] == 0) ready.add(after);
        }
    }
    if (order.size() != n) return Optional.empty(); // частичный порядок скрывал бы цикл
    return Optional.of(List.copyOf(order));
}

Решение и проверки: DependencyOrder.java. Запуск: java examples/live-coding/DependencyOrder.java.

Метод вернул [0] для графа 0, 1→2, 2→1. Что сломано?

Он выдал готовый этап 0 и остановился на цикле между 1 и 2, но принял частичный результат за полный. После цикла нужна проверка order.size()==n. Это видно на тесте с независимым префиксом перед циклом; один только тест самопетли не проверяет поведение уже накопленного ответа. Поиск конкретного цикла — дополнительное требование, текущий результат сообщает только невозможность полного порядка.
