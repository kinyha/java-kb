Load Balancing

Балансировщик решает три задачи: распределить запросы, убрать из ротации больной экземпляр и при сбое повторить запрос на другом. Round robin делит поровну и поэтому кормит медленный экземпляр так же, как быстрые: в демо он получил треть запросов, и p99 вырос до 1,2 с. Least connections смотрит на число активных соединений и сам уводит трафик от медленного — p99 0,4 с. Повтор на другом экземпляре безопасен только для идемпотентных запросов: nginx по умолчанию повторяет GET, даже если первый экземпляр его уже выполнил, и не повторяет POST, отдавая 502. L4-балансировщик распределяет соединения, L7 — запросы; для долгих соединений HTTP/2 и gRPC это разница между равномерной нагрузкой и одним перегруженным экземпляром.

Один экземпляр тормозит, и p99 всего сервиса — секунда

Сервис платежей работает в трёх экземплярах за nginx. На одном из них началась долгая сборка мусора — или его соседом по хосту оказался тяжёлый процесс, — и он стал отвечать в десять раз медленнее. Балансировщик продолжает отправлять ему ровно треть запросов: у него очередь, а у клиентов, которым он достался, — секундные задержки. Средняя задержка выглядит прилично, но p99 всего сервиса определяется худшим экземпляром.

Тема разбирает алгоритмы, проверки здоровья, повторы и уровни балансировки. Демо LoadBalancingDemo.java поднимает три бэкенда на JDK HttpServer с четырьмя рабочими потоками каждый — 8091 и 8092 отвечают за 20 мс, 8093 за 200 мс — и nginx 1.31 перед ними; 24 клиента отправляют 1 200 запросов. Шлюз с маршрутизацией и аутентификацией — в API Gateway, балансировка в Kubernetes — в Kubernetes.

Round robin кормит медленный экземпляр, least_conn — нет

upstream rr {                       # round robin — по умолчанию
    server backend:8091;
    server backend:8092;
    server backend:8093;
}
upstream lc {
    least_conn;                     # к серверу с меньшим числом активных соединений
    server backend:8091;
    server backend:8092;
    server backend:8093;
}
== 24 clients, 1200 requests; 8093 is 10x slower
   round robin  served {8091=400, 8092=400, 8093=400}   p50  31 ms, p99 1237 ms
   least_conn   served {8091=560, 8092=562, 8093=78}   p50  48 ms, p99 416 ms

Least connections адаптируется к скорости без всякой настройки — число открытых соединений и есть сигнал перегрузки. Другие алгоритмы решают другие задачи: веса (weight) учитывают заранее известную разницу мощностей, хеш по ключу (hash $arg_user consistent, ip_hash) привязывает клиента к экземпляру, чтобы попадать в его локальный кеш, а «два случайных выбора» (power of two choices) — взять два случайных бэкенда и выбрать менее загруженный — дают почти тот же эффект, что least connections, без глобального знания о всех бэкендах. Это важно, когда балансировщиков много и каждый видит только свои соединения.

Привязка клиента к экземпляру (sticky sessions) — вынужденная мера для сервисов с состоянием в памяти, например сессией. Она ломает равномерность и превращает отказ экземпляра в потерю сессий. Лучше держать сервис без состояния, а сессию — в Redis, как в Scalability.

Проверки здоровья и повторы: GET повторяется, даже если уже выполнен

Балансировщик узнаёт о больном экземпляре двумя способами. Пассивно — по ошибкам реальных запросов: в nginx max_fails=1 fail_timeout=10s по умолчанию, то есть одна ошибка убирает сервер из ротации на 10 секунд. Активно — периодическими запросами к /health: это умеют HAProxy, Envoy, облачные балансировщики, а в Kubernetes ту же роль играет readiness probe, как в Kubernetes для Java. Активная проверка находит больной экземпляр до того, как на нём споткнётся пользователь, а пассивная реагирует на то, что активная пропустила.

Самое опасное место — повтор запроса. Демо добавляет бэкенд 8094, который принимает запрос, выполняет «побочный эффект» (увеличивает счётчик) и закрывает соединение, не ответив, — как экземпляр, упавший посреди обработки. Запасной 8091 помечен backup, чтобы каждый запрос сначала шёл на 8094:

upstream crash {
    server backend:8094 max_fails=0;     # не помечать упавшим, чтобы каждый запрос шёл сюда первым
    server backend:8091 backup;
}
server { listen 8083; location / { proxy_pass http://crash; proxy_next_upstream error timeout; } }
server { listen 8084; location / { proxy_pass http://crash; proxy_next_upstream error timeout non_idempotent; } }
== backend 8094 dies in the middle of a request, 8091 is the backup
   GET  via :8083 -> 200, executed on {8091=1, 8094=1}
   POST via :8083 -> 502, executed on {8094=1}
   POST via :8084 -> 200, executed on {8091=1, 8094=1}

GET вернулся с 200, но выполнился дважды: nginx увидел обрыв и повторил его на запасном. Для настоящего GET без побочных эффектов это правильно, а для GET, который что-то меняет, — двойное действие. POST по умолчанию не повторяется после отправки на бэкенд: клиент получает 502 и не знает, выполнился ли запрос. С non_idempotent POST тоже повторяется — клиент видит 200, а платёж выполнен дважды. Безопасный вариант — повторять только запросы с ключом идемпотентности и дедупликацией на сервере, как в Idempotency. В демо max_fails=0 выставлен специально: со значением по умолчанию после первого обрыва 8094 был бы выключен на 10 секунд, и следующие запросы сразу шли бы на запасной, — что в жизни и есть желаемое поведение.

Разница становится критичной для долгих соединений. Клиент gRPC открывает одно HTTP/2-соединение и шлёт по нему тысячи запросов. L4-балансировщик — например, обычный Service в Kubernetes — выбрал бэкенд один раз, при установке TCP, и все запросы этого клиента идут в один под; новые поды после масштабирования не получают ничего, пока соединения не переоткроются. Решения — L7-балансировка, понимающая HTTP/2 (Envoy, Linkerd, Istio), клиентская балансировка, когда клиент сам знает список экземпляров и распределяет запросы, как в API Styles, или ограничение срока жизни соединения на сервере (maxConnectionAge в gRPC).

Балансировщик сам не должен быть единственной точкой отказа

Один nginx перед тремя экземплярами — сам единственная точка отказа. Его резервируют: пара с общим виртуальным IP (keepalived и VRRP — при отказе активного IP переезжает на запасной), облачный балансировщик, который провайдер держит в нескольких зонах, или DNS с несколькими адресами — грубый вариант, потому что клиенты кешируют DNS и продолжают ходить на мёртвый адрес до истечения TTL. Между регионами балансируют через DNS с геопривязкой или anycast.

При деплое экземпляр выводят из ротации до остановки: readiness переходит в «не готов», балансировщик перестаёт слать новые запросы, а начатые дорабатывают (connection draining). Иначе каждый деплой — порция обрывов, которые, как показало демо, превращаются в повторы GET и 502 на POST. В Spring Boot за это отвечает server.shutdown=graceful — ожидание текущих запросов при остановке; с версии 3.4 это значение по умолчанию.

Балансировщик сам повторит неудачный запрос на другом экземпляре, поэтому сбой экземпляра для клиента незаметен.

Повтор незаметен только для идемпотентных запросов. В демо GET выполнился на упавшем и на запасном экземплярах — дважды. POST nginx по умолчанию не повторил, и клиент получил 502 без знания, выполнен ли запрос; с non_idempotent POST выполнился дважды.

  • Round robin отдал медленному экземпляру треть запросов: p99 1 237 мс; least_conn — 78 из 1 200, p99 416 мс.
  • Пассивные проверки — по ошибкам запросов (max_fails, fail_timeout), активные — по /health и readiness.
  • nginx повторяет GET после обрыва, даже если запрос выполнен; POST по умолчанию не повторяет — 502.
  • L4 балансирует соединения, L7 — запросы; долгие HTTP/2 и gRPC соединения через L4 перегружают один экземпляр.
  • Балансировщик резервируют (VRRP, облако), экземпляры выводят из ротации до остановки.

На собеседовании

Какие алгоритмы балансировки вы знаете и когда какой выбрать?

Round robin — по кругу, хорош для одинаковых экземпляров и коротких запросов. Взвешенный — для разной мощности. Least connections — к экземпляру с меньшим числом активных соединений, сам уводит трафик от медленных и подходит для запросов разной длительности. Хеш по ключу или IP — привязка клиента к экземпляру ради локального кеша или состояния.

  • В демо least_conn снизил p99 втрое при одном медленном экземпляре.
  • Power of two choices — почти least connections без глобального знания, для многих балансировщиков.
  • Sticky sessions ломают равномерность и теряют состояние при отказе.

Чем L4-балансировщик отличается от L7?

L4 работает с TCP: видит адреса и порты, выбирает бэкенд для соединения, TLS проходит насквозь. L7 разбирает HTTP: маршрутизирует по пути и заголовкам, завершает TLS, повторяет запросы, выбирает бэкенд для каждого запроса. L4 быстрее и проще, L7 гибче.

  • gRPC и HTTP/2 через L4: все запросы соединения — на один экземпляр.
  • Решения: L7 с поддержкой HTTP/2, клиентская балансировка, ограничение возраста соединения.
После масштабирования с 3 до 6 подов новые поды почти без нагрузки. Почему? 
# gRPC-сервис ledger за обычным Service (ClusterIP)
apiVersion: v1
kind: Service
metadata: { name: ledger }
spec:
  selector: { app: ledger }
  ports: [{ port: 9090 }]
# клиенты: ManagedChannel на ledger:9090, один канал на всё приложение

ClusterIP балансирует на уровне соединений (kube-proxy, L4), а gRPC-клиент держит одно долгое HTTP/2-соединение. Клиенты подключились к трём старым подам и продолжают слать туда все запросы; новые поды получат трафик только от новых соединений. Нужна клиентская балансировка gRPC через headless Service (DNS со всеми подами и политика round_robin), L7-прокси с поддержкой HTTP/2 или maxConnectionAge на сервере, чтобы соединения периодически переоткрывались.

Безопасно ли балансировщику повторять запрос на другом экземпляре?

Только для идемпотентных запросов. Если экземпляр упал после начала обработки, повтор выполнит запрос второй раз. nginx по умолчанию повторяет GET и не повторяет POST после отправки на бэкенд — клиент получает 502. Для повторов неидемпотентных операций нужен ключ идемпотентности и дедупликация на сервере.

  • non_idempotent в proxy_next_upstream включает повтор POST — опасно без ключа.
  • Повторы на нескольких уровнях перемножаются: балансировщик, клиент, шлюз.
  • nginx: ngx_http_upstream_module — least_conn, max_fails, fail_timeout, backup.
  • nginx: proxy_next_upstream — повторы и non_idempotent.
