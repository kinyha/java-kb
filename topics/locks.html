Concurrency: Locks

Одно исключение без finally — и замок занят навсегда

Списание со счёта переписали с synchronized на ReentrantLock. Первый запрос пытается списать больше, чем есть на счёте, и получает исключение. Второй запрос, на 10 рублей, не отвечает:

import java.util.concurrent.*;
import java.util.concurrent.locks.*;

public class NoFinally {
    static final ReentrantLock lock = new ReentrantLock();
    static long balance = 100;

    static void withdraw(long amount) {
        lock.lock();
        if (amount > balance) throw new IllegalStateException("недостаточно средств");  // выход без unlock
        balance -= amount;
        lock.unlock();
    }

    public static void main(String[] args) throws Exception {
        ExecutorService pool = Executors.newFixedThreadPool(2);
        Future<?> first = pool.submit(() -> withdraw(500));
        try { first.get(); } catch (ExecutionException e) { System.out.println("первый запрос: " + e.getCause().getMessage()); }

        Future<?> second = pool.submit(() -> withdraw(10));
        try {
            second.get(2, TimeUnit.SECONDS);
            System.out.println("второй запрос прошёл");
        } catch (TimeoutException e) {
            System.out.println("второй запрос завис, замок занят: " + lock.isLocked()
                + ", ждут в очереди: " + lock.getQueueLength());
        }
        System.exit(0);
    }
}
первый запрос: недостаточно средств
второй запрос завис, замок занят: true, ждут в очереди: 1

synchronized отпускает монитор при любом выходе из блока. Lock — обычный объект, и unlock() вызывается, только если до него дошло выполнение. Исключение вылетело между lock() и unlock(), и замок остался за потоком пула навсегда. Поэтому у Lock одна обязательная идиома:

lock.lock();                     // до try: если lock() бросит, unlock вызывать нельзя
try {
    // работа с общим состоянием
} finally {
    lock.unlock();               // при любом выходе
}

Зачем тогда Lock, если synchronized безопаснее? Он умеет то, чего не умеет монитор: ждать с таймаутом, прерываться, держать несколько очередей ожидания, разделять чтение и запись. В этой теме — ReentrantLock и его возможности, Condition, ReadWriteLock и StampedLock. И замеры, которые показывают, что «более продвинутый» замок бывает медленнее простого.

Разницу в прерывании видно на двух потоках, которые ждут один и тот же занятый замок:

import java.util.concurrent.locks.*;

public class Interruptible {
    public static void main(String[] args) throws Exception {
        ReentrantLock lock = new ReentrantLock();
        lock.lock();                                             // main держит замок и не отпускает

        Thread plain = new Thread(() -> {
            lock.lock();                                         // ждёт, прерывание игнорирует
            try { System.out.println("plain: получил замок"); } finally { lock.unlock(); }
        });
        Thread polite = new Thread(() -> {
            try {
                lock.lockInterruptibly();                        // ждёт, но слышит interrupt()
                try { System.out.println("polite: получил замок"); } finally { lock.unlock(); }
            } catch (InterruptedException e) {
                System.out.println("polite: ожидание прервано");
            }
        });
        plain.start(); polite.start();
        Thread.sleep(200);
        plain.interrupt(); polite.interrupt();
        Thread.sleep(200);
        System.out.println("plain: " + plain.getState() + ", polite: " + polite.getState());
        lock.unlock();
        plain.join();
    }
}
polite: ожидание прервано
plain: WAITING, polite: TERMINATED
plain: получил замок

Поток с lock() проигнорировал прерывание и получил замок, только когда main его отпустил. lockInterruptibly() сразу вышел с InterruptedException — такой поток можно отменить через shutdownNow() или Future.cancel(true). Состояние ждущего потока — WAITING, а не BLOCKED: замки пакета java.util.concurrent паркуют поток через LockSupport.park().

Устроены ReentrantLock, Semaphore, CountDownLatch и ReentrantReadWriteLock одинаково — на AbstractQueuedSynchronizer (AQS). Это одно целое число state, которое меняют через CAS, и очередь ждущих потоков, которых паркуют и будят. Для ReentrantLock state — число повторных входов, для Semaphore — число свободных разрешений. Поэтому в дампе потоков все они выглядят одинаково: parking to wait for <...> (a ...ReentrantLock$NonfairSync).

Что выбирать? Для простой взаимной блокировки — synchronized: его невозможно забыть отпустить. Под сильной конкуренцией ReentrantLock в замере оказался быстрее: 8 потоков по миллиону захватов с увеличением счётчика — 65–73 мс против 177–211 мс у synchronized, в трёх запусках. Но если замок так горяч, сначала уменьшают конкуренцию, а не меняют вид замка. ReentrantLock — когда нужна одна из возможностей из таблицы. И в Java 21 с виртуальными потоками, если под замком есть блокирующий ввод-вывод: synchronized там закрепляет виртуальный поток за носителем (тема Virtual Threads).

tryLock с таймаутом превращает взаимную блокировку в повтор

В теме Deadlocks & Liveness встречные переводы A→B и B→A на synchronized зависали навсегда. С tryLock(timeout) поток, который не дождался второго счёта, отпускает первый и пробует снова после случайной паузы:

import java.util.concurrent.*;
import java.util.concurrent.locks.*;

public class TryTransfer {
    static final class Account {
        final String id;
        final ReentrantLock lock = new ReentrantLock();
        long balance = 1_000;
        Account(String id) { this.id = id; }
    }

    static final long START = System.nanoTime();
    static void log(String msg) {
        System.out.printf("%4d мс %s: %s%n", (System.nanoTime() - START) / 1_000_000, Thread.currentThread().getName(), msg);
    }

    // встречные переводы берут замки в разном порядке — как в теме Deadlocks
    static void transfer(Account from, Account to, long amount) throws InterruptedException {
        for (int attempt = 1; ; attempt++) {
            from.lock.lock();
            try {
                Thread.sleep(50);                                            // успевает начаться встречный перевод
                if (to.lock.tryLock(100 + ThreadLocalRandom.current().nextInt(100), TimeUnit.MILLISECONDS)) {
                    try {
                        from.balance -= amount;
                        to.balance += amount;
                        log("перевод " + from.id + "→" + to.id + " выполнен с попытки " + attempt);
                        return;
                    } finally { to.lock.unlock(); }
                }
                log("не дождался счёта " + to.id + ", отпускаю " + from.id);
            } finally {
                from.lock.unlock();
            }
            Thread.sleep(ThreadLocalRandom.current().nextInt(50));           // случайная пауза перед повтором
        }
    }

    public static void main(String[] args) throws Exception {
        Account a = new Account("A"), b = new Account("B");
        Thread t1 = new Thread(() -> { try { transfer(a, b, 10); } catch (InterruptedException e) { } }, "T1");
        Thread t2 = new Thread(() -> { try { transfer(b, a, 20); } catch (InterruptedException e) { } }, "T2");
        t1.start(); t2.start(); t1.join(); t2.join();
        System.out.println("балансы: A=" + a.balance + ", B=" + b.balance);
    }
}
 174 мс T2: не дождался счёта A, отпускаю B
 174 мс T1: не дождался счёта B, отпускаю A
 406 мс T2: не дождался счёта A, отпускаю B
 415 мс T1: перевод A→B выполнен с попытки 2
 502 мс T2: перевод B→A выполнен с попытки 3
балансы: A=1010, B=990

Оба перевода выполнены, суммы сошлись. Но посмотрите на цену: в этом запуске оба потока сначала отступили одновременно, и понадобилось пять попыток и полсекунды. В других запусках было от трёх до пяти. Без случайных таймаутов и пауз потоки отступали бы в такт — это livelock из темы Deadlocks & Liveness.

Поэтому tryLock — не замена единому порядку захвата, а страховка там, где порядок обеспечить нельзя. Другое его применение — бюджет времени: «если за 50 мс не получили замок, вернуть клиенту ошибку, а не держать запрос». tryLock() без аргументов не ждёт вовсе и, в отличие от версии с таймаутом, захватывает замок в обход справедливой очереди.

Condition даёт отдельную очередь ожидания на каждое условие

В теме synchronized & wait/notify буфер на один платёж с двумя производителями и двумя потребителями зависал с notify(): потребитель будил потребителя, и сигнал терялся. У монитора одна очередь ожидания на всех. У Lock очередей может быть сколько угодно — по одной Condition на условие:

import java.util.concurrent.atomic.AtomicLong;
import java.util.concurrent.locks.*;

public class OneSlotLock {
    private final Lock lock = new ReentrantLock();
    private final Condition notFull = lock.newCondition();       // ждут производители
    private final Condition notEmpty = lock.newCondition();      // ждут потребители
    private String slot;
    static final AtomicLong moved = new AtomicLong();

    void put(String p) throws InterruptedException {
        lock.lock();
        try {
            while (slot != null) notFull.await();
            slot = p;
            notEmpty.signal();                                   // будим именно потребителя
        } finally {
            lock.unlock();
        }
    }

    String take() throws InterruptedException {
        lock.lock();
        try {
            while (slot == null) notEmpty.await();
            String p = slot;
            slot = null;
            notFull.signal();                                    // будим именно производителя
            return p;
        } finally {
            lock.unlock();
        }
    }

    public static void main(String[] args) throws Exception {
        OneSlotLock buf = new OneSlotLock();
        for (int i = 0; i < 2; i++) {
            Thread producer = new Thread(() -> { try { while (true) buf.put("p"); } catch (InterruptedException e) { } });
            Thread consumer = new Thread(() -> { try { while (true) { buf.take(); moved.incrementAndGet(); } } catch (InterruptedException e) { } });
            producer.setDaemon(true); consumer.setDaemon(true);
            producer.start(); consumer.start();
        }
        for (int sec = 1; sec <= 3; sec++) {
            Thread.sleep(1000);
            System.out.printf("%d с: передано %,d%n", sec, moved.get());
        }
    }
}
1 с: передано 201,914
2 с: передано 424,375
3 с: передано 649,363

Та же конфигурация, что зависала на 5–10 передачах, работает с одиночным signal(). Производители ждут в notFull, потребители — в notEmpty, и сигнал всегда достаётся потоку с нужным условием. Так устроен ArrayBlockingQueue в JDK.

Правила те же, что у wait/notify: await() вызывают, держа замок, и всегда в цикле while. await() отпускает замок, а вернувшись, снова его держит. Spurious wakeup возможен и здесь. Есть версии с таймаутом: await(time, unit), awaitNanos.

ReadWriteLock ускоряет только долгие чтения, а на коротких проигрывает

ReentrantReadWriteLock пускает много читателей одновременно, а писателя — одного и без читателей. Кажется, что для данных, которые в основном читают, это всегда выигрыш. Проверим на котировке — паре цен bid и ask, которую нужно читать согласованно. Восемь читателей, один писатель обновляет пару раз в миллисекунду. Два варианта: чтение без дополнительной работы и чтение, после которого под замком ещё 2 мкс обработки:

import java.util.*;
import java.util.concurrent.atomic.LongAdder;
import java.util.concurrent.locks.*;

public class Quotes {
    // котировка: две связанные цены, читать нужно согласованную пару
    static double bid = 89.9, ask = 90.1;
    static int work;                                             // нс «обработки» внутри чтения

    static double spread() {                                     // чтение пары + обработка
        double s = ask - bid;
        long until = System.nanoTime() + work;
        while (work > 0 && System.nanoTime() < until) Thread.onSpinWait();
        return s;
    }
    static void update() { double mid = 90 + Math.random(); bid = mid - 0.1; ask = mid + 0.1; }

    interface Guard { double read(); void write(); }
    static final Object monitor = new Object();
    static final Guard SYNC = new Guard() {
        public double read() { synchronized (monitor) { return spread(); } }
        public void write() { synchronized (monitor) { update(); } }
    };
    static final ReadWriteLock rw = new ReentrantReadWriteLock();
    static final Guard RW = new Guard() {
        public double read() { rw.readLock().lock(); try { return spread(); } finally { rw.readLock().unlock(); } }
        public void write() { rw.writeLock().lock(); try { update(); } finally { rw.writeLock().unlock(); } }
    };
    static final StampedLock sl = new StampedLock();
    static final Guard STAMPED = new Guard() {
        public double read() {
            long stamp = sl.tryOptimisticRead();                 // не блокирует: запоминает версию
            double b = bid, a = ask;                             // читаем поля в локальные переменные
            if (!sl.validate(stamp)) {                           // была запись — пара могла порваться
                stamp = sl.readLock();
                try { b = bid; a = ask; } finally { sl.unlockRead(stamp); }
            }
            double s = a - b;                                    // обработка уже без замка
            long until = System.nanoTime() + work;
            while (work > 0 && System.nanoTime() < until) Thread.onSpinWait();
            return s;
        }
        public void write() { long s = sl.writeLock(); try { update(); } finally { sl.unlockWrite(s); } }
    };

    static long run(Guard g) throws InterruptedException {
        LongAdder reads = new LongAdder();
        long[] torn = new long[1];
        long end = System.nanoTime() + 1_000_000_000L;
        List<Thread> ts = new ArrayList<>();
        for (int r = 0; r < 8; r++) ts.add(new Thread(() -> {
            while (System.nanoTime() < end) {
                double s = g.read();
                if (Math.abs(s - 0.2) > 1e-9) torn[0]++;         // пара из разных обновлений
                reads.increment();
            }
        }));
        ts.add(new Thread(() -> {
            while (System.nanoTime() < end) {
                g.write();
                try { Thread.sleep(1); } catch (InterruptedException e) { }
            }
        }));
        ts.forEach(Thread::start);
        for (Thread t : ts) t.join();
        if (torn[0] > 0) System.out.println("  порванных пар: " + torn[0]);
        return reads.sum();
    }

    public static void main(String[] args) throws Exception {
        for (int w : new int[]{0, 2_000}) {
            work = w;
            run(SYNC); run(RW); run(STAMPED);                    // прогрев
            System.out.printf("чтение + %d нс работы:%n", w);
            System.out.printf("  synchronized:           %,12d чтений за 1 с%n", run(SYNC));
            System.out.printf("  ReentrantReadWriteLock: %,12d%n", run(RW));
            System.out.printf("  StampedLock optimistic: %,12d%n", run(STAMPED));
        }
    }
}

Строки «порванных пар» нет ни в одном варианте: все три защищают пару. Без защиты за секунду набралось 59 чтений, где bid взят из одного обновления, а ask — из другого.

  • Короткое чтение: ReadWriteLock в 2,5 раза медленнее synchronized. Каждый захват и освобождение чтения — CAS по общему счётчику читателей. Восемь ядер перекидывают друг другу одну строку кеша, и эти накладные расходы больше самого чтения.
  • Долгое чтение, 2 мкс: synchronized пропускает читателей по одному, и восемь ядер работают как одно. ReadWriteLock пускает их параллельно и выигрывает в шесть раз.

Вывод: ReadWriteLock имеет смысл, когда чтения действительно долгие и параллельные, а писатели редки. Для коротких чтений лучше неизменяемый снимок в volatile-поле или StampedLock. Решают замером, а не по названию.

Ещё две особенности ReentrantReadWriteLock:

import java.util.concurrent.TimeUnit;
import java.util.concurrent.locks.*;

public class Upgrade {
    public static void main(String[] args) throws Exception {
        ReentrantReadWriteLock rw = new ReentrantReadWriteLock();

        rw.writeLock().lock();
        rw.readLock().lock();                                    // понижение: запись → чтение — можно
        rw.writeLock().unlock();
        System.out.println("понижение: держим только чтение — " + (rw.getReadHoldCount() == 1));
        rw.readLock().unlock();

        rw.readLock().lock();
        boolean upgraded = rw.writeLock().tryLock(1, TimeUnit.SECONDS);   // повышение: чтение → запись
        System.out.println("повышение за 1 с: " + upgraded + " — с lock() поток ждал бы сам себя вечно");
    }
}
понижение: держим только чтение — true
повышение за 1 с: false — с lock() поток ждал бы сам себя вечно

Понизить запись до чтения можно, повысить чтение до записи — нет. Писатель ждёт, пока уйдут все читатели, включая его самого. Частая ошибка — «проверить под чтением, при необходимости взять запись», не отпустив чтение. Правильно — отпустить чтение, взять запись и перепроверить условие.

StampedLock читает оптимистично: без замка, с проверкой версии после

StampedLock (Java 8) добавляет третий режим — оптимистичное чтение. Читатель ничего не захватывает, а только запоминает номер версии, копирует поля в локальные переменные и проверяет, не менялась ли версия. Если не менялась — данные согласованы. Если менялась — читает заново, уже под обычной блокировкой чтения:

Ограничения, из-за которых StampedLock не заменяет всё остальное:

  • Не реентерабелен. Повторный writeLock() тем же потоком — взаимная блокировка с самим собой.
  • Нет Condition, ожидание условия не построить.
  • Оптимистичный участок должен переживать любые данные. До validate можно только копировать поля в локальные переменные. Нельзя ходить по ссылкам, делить на прочитанное значение или вызывать методы: объект может быть в промежуточном состоянии.
  • Штамп — число, а не владелец. Отпустить замок можно из другого потока, и ошибиться со штампом тоже просто.

Место StampedLock — небольшие структуры из нескольких примитивных полей, которые часто читают и редко пишут: координаты, котировки, счётчики с несколькими полями. В остальных случаях проще неизменяемый объект в volatile-поле.

  • Lock освобождают только в finally: lock() до try, unlock() в finally. Иначе исключение оставит замок занятым навсегда.
  • ReentrantLock добавляет к synchronized tryLock с таймаутом, lockInterruptibly, справедливость, несколько Condition и методы наблюдения. Для простого случая хватает synchronized.
  • tryLock(timeout) превращает взаимную блокировку в повтор, но ценой задержек. Нужны случайные паузы; единый порядок захвата надёжнее.
  • Condition — отдельная очередь ожидания на условие. С ней одиночный signal() безопасен там, где notify() вешал систему.
  • ReadWriteLock выигрывает на долгих параллельных чтениях (в 6 раз в замере) и проигрывает на коротких (в 2,5 раза). Повышать чтение до записи нельзя.
  • StampedLock читает оптимистично, с проверкой версии, и быстрее всех на редких записях. Но он не реентерабелен и не имеет Condition.

На собеседовании

Чем ReentrantLock отличается от synchronized?

Оба дают взаимное исключение, реентерабельность и одинаковую видимость. ReentrantLock добавляет попытку захвата без ожидания или с таймаутом (tryLock), прерываемое ожидание (lockInterruptibly), справедливый режим, несколько условий ожидания (newCondition) и методы наблюдения — isLocked, getQueueLength. Цена — ручное освобождение: unlock() обязательно в finally. Для простого случая выбирают synchronized, ReentrantLock — когда нужна одна из этих возможностей.

  • ReentrantLock сделан на AbstractQueuedSynchronizer, как Semaphore и CountDownLatch. Под сильной конкуренцией он в замере урока был быстрее synchronized в 2,5–3 раза.
  • В Java 21 блокирующий ввод-вывод под synchronized закрепляет виртуальный поток за носителем, под ReentrantLock — нет. В JDK 24 это ограничение сняли.
  • Ждущий на ReentrantLock поток в дампе — WAITING (parking), на мониторе — BLOCKED.
lock.lock(); if (amount > balance) throw new IllegalStateException(); balance -= amount; lock.unlock(); — что не так?

Исключение выходит из метода, минуя unlock(), и замок остаётся занятым навсегда: все следующие вызовы зависнут. В замере урока второй запрос на 10 рублей ждал бесконечно. Нужно lock.lock(); try { ... } finally { lock.unlock(); }.

Что такое Condition и зачем он нужен?

Очередь ожидания, привязанная к Lock, — аналог wait/notify у монитора. Но у одного замка может быть несколько условий, например notFull и notEmpty в ограниченной очереди. Тогда производители и потребители ждут в разных очередях, и signal() будит поток с нужным условием. Правила те же: await() только под замком и в цикле while.

Почему с двумя Condition можно использовать signal(), а с одним монитором notify() опасен?

В одной очереди ожидания монитора ждут потоки с разными условиями, и notify() может разбудить не того — сигнал потеряется. С отдельной Condition на каждое условие все ждущие в очереди ждут одного и того же, и любого из них достаточно разбудить. В замере урока конфигурация, которая с notify() зависала после 5–10 передач, с двумя Condition передала 650 тысяч платежей за 3 секунды.

Когда использовать ReadWriteLock?

Когда данные в основном читают, чтения длинные и могут идти параллельно, а записи редки. Тогда читатели не мешают друг другу, и выигрыш большой: в замере урока при 2 мкс работы в чтении — в 6 раз против synchronized. На коротких чтениях он проигрывает: каждый захват чтения — CAS по общему счётчику, и в замере было в 2,5 раза медленнее synchronized.

  • Понижение записи до чтения разрешено, повышение чтения до записи — нет: поток будет ждать сам себя.
  • Альтернативы для коротких чтений — неизменяемый снимок в volatile-поле или оптимистичное чтение StampedLock.
Кеш: под readLock проверили, что значения нет, затем внутри той же секции взяли writeLock, чтобы положить. Что произойдёт?

Поток зависнет навсегда: writeLock ждёт, пока уйдут все читатели, а один из них — сам этот поток. Нужно отпустить readLock, взять writeLock и перепроверить условие — за это время значение мог положить другой поток. Проще взять ConcurrentHashMap.computeIfAbsent.

Что такое StampedLock и оптимистичное чтение?

Замок с тремя режимами: запись, чтение и оптимистичное чтение. Оптимистичное чтение ничего не захватывает. tryOptimisticRead() возвращает номер версии, поля копируют в локальные переменные, затем validate(stamp) проверяет, не было ли записи. Если была — перечитывают под обычной блокировкой чтения. При редких записях это быстрее всех: в замере урока 15 млн чтений против 8,8 млн у synchronized.

  • Не реентерабелен, нет Condition. До validate можно только копировать поля: ходить по ссылкам и вызывать методы на возможно порванных данных нельзя.
