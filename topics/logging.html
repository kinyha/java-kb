Logging

Лог — событие с уровнем, именем источника, контекстом и причиной ошибки. Между вызовом в коде и найденной записью стоят несколько решений: существует ли provider, принят ли уровень, куда ведёт маршрут, какой контекст принадлежит событию и успел ли получатель его сохранить. Разобраться с пропавшим или чужим логом можно только восстановив эту цепочку.

Вызов SLF4J создаёт лог только через runtime provider

Платёж P7 дошёл до банка, но строку «payment accepted» в логах не нашли. Метод log.info компилируется и возвращается без ошибки. Это ещё не доказывает, что кто-то записывает событие: в classpath приложения оставили только slf4j-api, а реализацию убрали при упаковке.

SLF4J — facade: твой код зависит от org.slf4j.Logger и LoggerFactory. Logback Classic — provider, который реализует этот API и строит маршрут событий; Logback Core содержит общие appenders и инфраструктуру. Библиотеке достаточно API, чтобы не навязывать способ записи своему приложению. Приложение выбирает одну совместимую реализацию и её конфигурацию.

В SLF4J 2 provider обнаруживается через ServiceLoader и описание org.slf4j.spi.SLF4JServiceProvider. Старый binding 1.7 с StaticLoggerBinder не становится provider 2.0 автоматически. Несколько provider дают предупреждение и делают выбор зависимым от окружения; это чинят по runtime dependency tree и содержимому упаковки, а не дополнительным log.info.

Все демо ниже выполнены на JDK 21.0.11 с SLF4J 2.0.17 и Logback 1.5.18. Версии зафиксированы для повторяемости. Драйвер скачивает зависимости из Maven Central, компилирует через javac --release 21, запускает отдельные JVM и проверяет результаты; временные файлы остаются вне репозитория.

// Полный проверенный ProviderDemo.java; imports опущены.
public class ProviderDemo {
    public static void main(String[] args) {
        var log = LoggerFactory.getLogger("payments");
        log.info("payment accepted");
        System.out.println("factory=" + LoggerFactory.getILoggerFactory().getClass().getSimpleName());
    }
}

Строка payment accepted не появилась ни в одном потоке вывода. NOP отбрасывает вызовы; конфигурация Logback не исправит отсутствие его классов. Если factory уже LoggerContext, следующий вопрос — где effective level и какие appenders обслуживают нужное имя logger.

Bridge переводит чужой API в facade и может замкнуть цикл

Когда внешняя библиотека использует другой API, bridge направляет её события в выбранный стек. Например, jul-to-slf4j с установленным handler переводит JUL → SLF4J. Одновременный provider slf4j-jdk14 переводит обратно SLF4J → JUL: получается цикл. Provider и bridge выполняют разные роли, поэтому «включить все logging JAR» — плохая стратегия.

Для конфигурации Logback в обычном classpath используются logback-test.xml для тестов и logback.xml для приложения; путь можно задать явно через -Dlogback.configurationFile=…, как в JSON-демо. Если ожидаемый конфиг не применился, смотри внутренние status messages Logback и фактические ресурсы JAR. Конфигурация Spring Boot и внешняя доставка разобраны в соседних темах.

Уровень принимает событие, additivity ведёт его к appenders

Logger с именем demo.payments.Bank относится к ветке demo.payments. Иерархия строится по именам с точками, а не по наследованию Java-классов; parent — ближайшее существующее имя-предок. getLogger(Bank.class) просто использует полное имя класса, чтобы оно совпадало с пакетом.

Если собственный level не установлен, logger берёт ближайший заданный уровень вверх по дереву — effective level. У root уровень всегда есть; без иной настройки он DEBUG. Обычная проверка принимает событие, если его приоритет не ниже порога: TRACE < DEBUG < INFO < WARN < ERROR. OFF отключает обычные события, ALL снимает ограничение по уровню. В данном эксперименте нет TurboFilters, которые могут вмешаться ещё до стандартной проверки.

После принятия события logger вызывает свои appenders и поднимается к appenders предков. Это additivity, по умолчанию true. На предке level повторно не проверяется: событие DEBUG, принятое Bank, достигает appender у root с уровнем ERROR. Чтобы запретить низкие события именно в месте записи, ставят ThresholdFilter на appender. additivity=false останавливает подъём после собственных appenders данного logger.

// Полный проверенный RoutesDemo.java; imports опущены.
public class RoutesDemo {
    public static void main(String[] args) {
        var ctx = Support.reset();
        var root = ctx.getLogger("ROOT");
        root.setLevel(Level.ERROR);
        var payments = ctx.getLogger("demo.payments");
        payments.setLevel(Level.DEBUG);
        var log = ctx.getLogger("demo.payments.Bank"); // inherits DEBUG
        var local = Support.capture(ctx, "LOCAL");
        var shared = Support.capture(ctx, "SHARED");
        payments.addAppender(local);
        root.addAppender(shared);

        root.debug("must not be created");
        Support.check(local.messages.isEmpty() && shared.messages.isEmpty(), "root rejects own DEBUG");

        log.debug("accepted"); // root ERROR is not a second event-level check
        System.out.printf("root=ERROR, child=%s: LOCAL=%s, SHARED=%s%n",
                log.getEffectiveLevel(), local.messages, shared.messages);
        Support.check(shared.messages.equals(local.messages), "ancestor level must not reject");

        var threshold = new ThresholdFilter();
        threshold.setLevel("WARN");
        threshold.start();
        shared.addFilter(threshold); // appender filter actually rejects DEBUG
        local.messages.clear(); shared.messages.clear();
        log.debug("filtered");
        System.out.printf("SHARED threshold=WARN: LOCAL=%s, SHARED=%s%n", local.messages, shared.messages);
        Support.check(shared.messages.isEmpty(), "appender threshold");

        shared.clearAllFilters();
        payments.detachAppender(local);
        payments.addAppender(shared); // SAME appender now attached twice along route
        shared.messages.clear();
        log.info("duplicate");
        System.out.println("same appender on child+root: " + shared.messages);
        Support.check(shared.messages.size() == 2, "additivity duplicate");
        payments.setAdditive(false);
        shared.messages.clear();
        log.info("once");
        System.out.println("additivity=false on payments: " + shared.messages);
        Support.check(shared.messages.size() == 1, "stop at payments");
        System.out.printf("inherited unrelated=%s%n", ctx.getLogger("demo.other").getEffectiveLevel());
        ctx.stop();
    }
}

SHARED threshold=WARN: LOCAL=[filtered], SHARED=[]
same appender on child+root: [duplicate, duplicate]

Указанный дважды SHARED получил один event дважды: маршрут не делает дедупликацию appender. В production это выглядит как одинаковые строки с одним timestamp и request_id. Проверь привязки к logger и root; оставь appender в одном месте либо останови additivity в ветке, которая пишет отдельно. Порог и маршрутизация — разные настройки, и повышение root до ERROR не заменяет этот разбор.

Как демо наблюдает доставку и что делает фильтр

В Support нет скрытой обработки логов: reset очищает ранее настроенные appenders и задаёт root INFO для остальных демо. Capture сохраняет отформатированный текст и тип причины в момент вызова appender. Начало RoutesDemo явно меняет root на ERROR.

// Полный проверенный Support.java; imports опущены.
final class Support {
    static LoggerContext reset() {
        var ctx = (LoggerContext) LoggerFactory.getILoggerFactory();
        ctx.reset();
        ctx.getLogger("ROOT").setLevel(Level.INFO);
        return ctx;
    }

    static final class Capture extends AppenderBase<ILoggingEvent> {
        final List<String> messages = new ArrayList<>();
        final List<String> causes = new ArrayList<>();
        @Override protected void append(ILoggingEvent e) {
            // Resolve immediately: do not retain an event with lazy fields.
            messages.add(e.getFormattedMessage());
            causes.add(e.getThrowableProxy() == null ? "none" : e.getThrowableProxy().getClassName());
        }
    }

    static Capture capture(LoggerContext ctx, String name) {
        var app = new Capture();
        app.setContext(ctx);
        app.setName(name);
        app.start();
        return app;
    }
    static void check(boolean ok, String message) {
        if (!ok) throw new AssertionError(message);
    }
}

Appender filters возвращают DENY, NEUTRAL или ACCEPT. DENY прекращает доставку этому appender, ACCEPT завершает его цепочку фильтров положительно, NEUTRAL отдаёт решение следующему фильтру. ThresholdFilter ниже порога выдаёт DENY, иначе NEUTRAL. TurboFilter работает раньше, в контексте logger, поэтому способен изменить и решение о создании события. Не измеряй цену отключённого уровня, забыв о таком фильтре.

Плейсхолдер откладывает форматирование, но не вычисление аргумента

В отладочном логе платежа сериализуется большой ответ банка. После переключения сервиса на INFO CPU всё равно тратится на сериализацию. Причина — Java вычисляет аргументы до входа в debug. Запись debug("reply {}", serialize(reply)) запускает serialize даже при отключённом DEBUG.

{} позволяет backend отложить подстановку и toString до принятия события. Конкатенация уже строит строку у caller. Для дорогого получения аргумента используй isDebugEnabled() или fluent API 2.0 с Supplier. Lambda без вызова внутри — только описание работы; переданный в addArgument(expensive()) результат уже вычислен.

// Полный проверенный LazyDemo.java; imports опущены.
public class LazyDemo {
    static int calls;
    static int renders;
    static final Object value = new Object() {
        @Override public String toString() { renders++; return "payload"; }
    };
    static Object expensive() { calls++; return value; }

    public static void main(String[] args) {
        var ctx = Support.reset(); // INFO, DEBUG disabled
        var capture = Support.capture(ctx, "CAPTURE");
        ctx.getLogger("ROOT").addAppender(capture);
        var log = LoggerFactory.getLogger("demo.payments");
        log.debug("payload {}", expensive());
        System.out.printf("placeholders: calls=%d renders=%d%n", calls, renders);
        calls = renders = 0;
        log.debug("payload " + expensive());
        System.out.printf("concatenation: calls=%d renders=%d%n", calls, renders);
        calls = renders = 0;
        log.atDebug().addArgument(() -> expensive()).log("payload {}");
        System.out.printf("supplier: calls=%d renders=%d%n", calls, renders);
        if (log.isDebugEnabled()) log.debug("payload {}", expensive());
        System.out.printf("guard: calls=%d renders=%d%n", calls, renders);
        log.atInfo().addArgument(() -> expensive()); // forgot final log(): no event
        System.out.println("builder without log(): events=" + capture.messages.size());

        var failure = new IllegalStateException("bank timeout");
        log.error("failed {}", "P7", failure); // final argument remains a cause
        log.error("failed {}", failure.getMessage()); // only text, no stack/cause
        log.atError().setCause(failure).addKeyValue("payment_id", "P7").log("failed");
        for (int i = 0; i < capture.messages.size(); i++) {
            System.out.printf("%s | cause=%s%n", capture.messages.get(i), capture.causes.get(i));
        }
        Support.check(capture.causes.equals(java.util.List.of("java.lang.IllegalStateException", "none", "java.lang.IllegalStateException")), "cause extraction");
        ctx.stop();
    }
}

concatenation: calls=1 renders=1

В эксперименте calls считает получение аргумента, renders — его toString; это проверка механизма, не замер наносекунд. Builder без завершающего log() не создал событие даже на INFO. Последний Throwable в обычном вызове сохранён как причина; getMessage() оставил лишь текст и уничтожил для этого события stack trace и цепочку причин. Fluent setCause делает намерение явным.

Уровень описывает полезность и серьёзность события для эксплуатации. INFO — значимый переход платежа, DEBUG — детали диагностики, WARN — проблема с восстановлением или отклонение, ERROR — ошибка обработки, требующая разбора. Ожидаемый отказ по правилам бизнеса не обязан быть ERROR. Один сбой логирует граница, которая принимает решение: если каждый catch пишет ERROR и бросает дальше, одна причина превращается в несколько тревожных записей.

Параметризованный debug бесплатен, если уровень отключён.

Отключённый уровень избавляет от создания обычного события и форматирования, но не отменяет уже выполненные Java-выражения. Путь до уровня также имеет свою цену: lookup, проверка и возможные TurboFilters.

MDC принадлежит потоку и требует границы жизни запроса

Два запроса по одному платежу пишут перемежающиеся строки. Передавать request_id аргументом во все методы неудобно: MDC хранит строковую карту контекста текущего потока, из которой Logback может добавить поля к событию. В Logback 1.5.18 это обычный ThreadLocal, и новый дочерний поток не наследует карту.

Поток пула живёт дольше запроса. Если A положил request_id и не убрал его, следующий B на том же worker увидит A. Нельзя исправить это очисткой на другом потоке: MDC.clear() действует только на вызывающий поток. Начало request/task scope устанавливает нужный контекст, finally заканчивает его и возвращает прежнее состояние.

// Фрагмент MdcDemo: тот же worker, строгий порядок через get().
// pool объявлен как Executors.newSingleThreadExecutor();
// get() fixes ordering: the same worker executes A before B.
pool.submit(() -> MDC.put("request_id", "A")).get();
System.out.println("bad request B sees=" + pool.submit(() -> MDC.get("request_id")).get());
pool.submit(MDC::clear).get();
MDC.put("request_id", "MAIN");
System.out.println("plain pool sees=" + pool.submit(() -> MDC.get("request_id")).get());
Thread.ofVirtual().start(() -> System.out.println("new virtual thread sees=" + MDC.get("request_id"))).join();
bad request B sees=A
plain pool sees=null
new virtual thread sees=null

Это первые три строки запуска MdcDemo. Один worker и Future.get() задают точный порядок; утечка здесь не объясняется случайным планированием. Вторая задача без собственного ID получила A. После явной очистки новая карта caller MAIN не перешла ни в пул, ни в новый virtual thread.

Для вложенного scope простое удаление ключа недостаточно. MDC.putCloseable удобен для ключа, которого раньше не было, но close удаляет его, а не восстанавливает старое значение. Внешний request_id OUTER после внутреннего INNER исчезает:

// Фрагмент MdcDemo: вложенная область с существующим значением.
MDC.put("request_id", "OUTER");
try (var ignored = MDC.putCloseable("request_id", "INNER")) {
    System.out.println("closeable inside=" + MDC.get("request_id"));
}
System.out.println("closeable after=" + MDC.get("request_id"));
closeable inside=INNER
closeable after=null

Если граница гарантированно владеет всей пустой картой worker, ей достаточно установить карту и очистить в finally. Обёртка, которую вызывают внутри неизвестного внешнего scope, сохраняет и восстанавливает прежнюю карту. В неё кладут небольшие стабильные идентификаторы; MDC не должен удерживать большой payload или credentials после завершения запроса.

Асинхронной задаче нужен снимок контекста в момент submission

Платёж принят HTTP-потоком, отправка в банк выполняется executor. Если задача прочитает MDC только внутри run(), она прочитает карту worker, а не запрос отправителя. После submission caller уже может перейти к P8, поэтому связь с P7 нужно зафиксировать до очереди.

Обёртка делает копию карты у caller, затем на worker сохраняет его прежнюю карту, устанавливает снимок и выполняет тело. В finally возвращает предыдущую карту, в том числе после исключения. Это перенос контекста задачи, а не общий изменяемый объект между потоками.

// Фрагменты MdcDemo: обёртка и вызовы, влияющие на вывод.
static void install(Map<String, String> map) {
        if (map == null) MDC.clear(); else MDC.setContextMap(map);
    }
    static Runnable contextual(Runnable task) {
        var submitted = MDC.getCopyOfContextMap(); // caller NOW, not inside run()
        return () -> {
            var previous = MDC.getCopyOfContextMap(); // worker's enclosing scope
            try {
                install(submitted);
                task.run();
            } finally {
                install(previous); // also when task fails
            }
        };
    }

// Внутри того же single-thread pool:
pool.submit(() -> MDC.put("request_id", "OUTER")).get();
MDC.put("request_id", "P7");
Runnable wrapped = contextual(() -> {
    System.out.println("wrapped sees=" + MDC.get("request_id"));
    throw new IllegalStateException("bank timeout");
});
MDC.put("request_id", "P8"); // after capture, before execution
try { pool.submit(wrapped).get(); } catch (ExecutionException e) {
    System.out.println("task cause=" + e.getCause().getClass().getSimpleName());
}
String restored = pool.submit(() -> MDC.get("request_id")).get();
System.out.println("worker after failure=" + restored);
Support.check("OUTER".equals(restored), "restored worker scope");
System.out.println("caller still=" + MDC.get("request_id"));
wrapped sees=P7
task cause=IllegalStateException
worker after failure=OUTER
caller still=P8

Снимок остался P7, хотя до запуска caller сменил request_id на P8. Исключение задачи дошло до Future, worker восстановил OUTER, caller сохранил P8. Карту нельзя устанавливать только перед submit на caller и считать контекст перенесённым. Для каждого executor, CompletableFuture или callback проверь реальную границу исполнения; инструменты фреймворка могут декорировать её за тебя, но это отдельная настройка.

Внутри JVM MDC помогает связать события одного request/task. Через HTTP или брокер карту потока не отправляют: передают допустимый correlation/trace context в protocol headers, валидируют его и создают новый scope на принимающей стороне. Идентификатор не заменяет авторизацию. Построение spans и автоматическая propagation описаны в Tracing.

Структурный encoder сохраняет поля и экранирует входные данные

Поиск «все попытки платежа P7 в запросе R7» становится ненадёжным, если идентификаторы находятся только внутри свободного текста. Событие уже содержит logger, level, аргументы, MDC и Throwable; encoder должен отдать их отдельными полями. Структурные логи задают стабильную схему данных, пригодную для фильтрации, а JSON — один из форматов этой схемы.

Layout строит текст, encoder отдаёт байты получателю и определяет charset/представление записи. PatternLayoutEncoder подходит для читаемой строки: например %level %logger %X{request_id} %kvp %msg%n%ex. Само наличие MDC в событии не означает, что шаблон его напечатает. Fluent addKeyValue также передаёт поле backend; его место и вид зависят от encoder.

Ниже полный конфиг нативного JsonEncoder 1.5.18 и полный код вызова. При запуске драйвер передаёт -Dlogback.configurationFile=examples/logging/logback-json.xml. Меняющиеся timestamp, nanoseconds, threadName, sequenceNumber и context отключены ради повторяемого вывода; в рабочем журнале время и метаданные источника сохраняют. FormattedMessage включён явно — по умолчанию у этого encoder он выключен.

<configuration>
  <appender name="JSON" class="ch.qos.logback.core.ConsoleAppender">
    <encoder class="ch.qos.logback.classic.encoder.JsonEncoder">
      <!-- Only volatile metadata is disabled to make the experiment reproducible. -->
      <withSequenceNumber>false</withSequenceNumber>
      <withTimestamp>false</withTimestamp>
      <withNanoseconds>false</withNanoseconds>
      <withThreadName>false</withThreadName>
      <withContext>false</withContext>
      <withFormattedMessage>true</withFormattedMessage>
    </encoder>
  </appender>
  <root level="INFO"><appender-ref ref="JSON"/></root>
</configuration>
// Полный проверенный JsonDemo.java; imports опущены.
public class JsonDemo {
    public static void main(String[] args) {
        var log = LoggerFactory.getLogger("demo.payments");
        MDC.put("request_id", "R7");
        try {
            log.atInfo().addKeyValue("payment_id", "P7").addKeyValue("attempt", 2)
                    .log("bank reply {}", "ok\n\"level\":\"ERROR\"");

    }
}
{"level":"INFO","loggerName":"demo.payments","mdc": {"request_id":"R7"},"kvpList": [{"payment_id":"P7"},{"attempt":"2"}],"message":"bank reply {}","formattedMessage":"bank reply ok\n\"level\":\"ERROR\"","arguments": ["ok\n\"level\":\"ERROR\""],"throwable":null}

Это одна реальная строка JSON Lines, которую браузер может перенести визуально. Перенос и кавычки ответа банка экранированы внутри строки: вход ok\n"level":"ERROR" не создал второе событие и не изменил level INFO. Python JSON parser проверил число физических строк, decoded message, MDC и KVP. Ручная склейка "{\"reply\":\""+reply+"\"}" не обеспечивает такого свойства.

У этого encoder kvpList — массив объектов, а attempt превратился из Integer 2 в строку "2". Выбирая запросы и индексы collector, проверь фактические типы и вложенность; JSON сам по себе не делает поля числовыми. Стабильный event name, payment_id, outcome и duration_ms полезнее динамического ключа, содержащего конкретный ID.

Структура не решает вопрос, какие данные допустимы: не записывай токены, полные номера карт и необязательные персональные payload. Экранирование предотвращает подмену границ записей, но не скрывает секрет. Ограничивай размер входных данных и выбирай поля до encoder, иначе один большой ответ увеличит память очереди и стоимость индексации. Метрики для агрегатов и cardinality — в Metrics, связка источников — в Observability.

Асинхронная запись обменивает задержку на очередь и риск потери

Банк отвечает медленно, а файловый или сетевой sink пишет ещё медленнее. Синхронный appender выполняет работу в потоке приложения; задержка log-вызова входит в обработку платежа. AsyncAppender передаёт событие через bounded ArrayBlockingQueue своему worker и одному дочернему appender. Это развязывает скорости только пока очередь справляется с разницей.

Очередь хранит события, а не фиксированное число байтов. Десять маленьких сообщений и десять Throwable с большими аргументами занимают разную память. При длительном потоке быстрее sink очередь всё равно заполнится: увеличение queueSize покупает время и расходует heap. По thread dump можно увидеть producer в ArrayBlockingQueue.put, а worker — в медленном sink; отдельно наблюдай заполнение, write errors и путь доставки до collector.

Для точного эксперимента очередь уменьшена до 10: threshold при старте стал 2. Worker уже вынул первое INFO hold и ждёт latch, поэтому оно не занимает место. Затем producer вызывает 12 INFO и два ERROR. В этом положении результат можно вычислить, не гадая о скорости диска.

В AsyncDemo Gate — работающий appender с двумя latch: entered сообщает, что worker уже внутри, release позволяет продолжить. Полный код ниже содержит управление очередью и проверку stack frame заблокированного producer. Support.reset из второго шага задаёт INFO; пять секунд в ожиданиях — дедлайн зависшего эксперимента, а не benchmark.

// Полный проверенный AsyncDemo.java; imports опущены.
public class AsyncDemo {
    static final class Gate extends AppenderBase<ILoggingEvent> {
        final CountDownLatch entered = new CountDownLatch(1);
        final CountDownLatch release = new CountDownLatch(1);
        final CountDownLatch delivered;
        final List<String> messages = new ArrayList<>();
        final List<String> requests = new ArrayList<>();
        Gate(int expected) { delivered = new CountDownLatch(expected); }
        @Override protected void append(ILoggingEvent e) {
            if (messages.isEmpty()) {
                entered.countDown();
                try {
                    if (!release.await(10, TimeUnit.SECONDS)) throw new AssertionError("gate timeout");
                } catch (InterruptedException ex) { throw new AssertionError(ex); }
            }
            messages.add(e.getFormattedMessage());
            requests.add(e.getMDCPropertyMap().get("request_id"));
            delivered.countDown();
        }
    }
    static boolean inQueuePut(Thread thread) {
        return thread.getState() == Thread.State.WAITING
                && java.util.Arrays.stream(thread.getStackTrace()).anyMatch(
                        f -> f.getClassName().equals("java.util.concurrent.ArrayBlockingQueue")
                                && f.getMethodName().equals("put"));
    }
    static void scenario(boolean neverBlock) throws Exception {
        var ctx = Support.reset();
        var sink = new Gate(neverBlock ? 11 : 12); sink.setContext(ctx); sink.setName("GATE"); sink.start();
        var async = new AsyncAppender();
        async.setContext(ctx); async.setName("ASYNC");
        async.setQueueSize(10); // start() derives default threshold 10 / 5 = 2
        async.setNeverBlock(neverBlock);
        async.setMaxFlushTime(5000); // after releasing the controlled gate
        async.addAppender(sink); async.start();
        ctx.getLogger("ROOT").addAppender(async);
        var log = LoggerFactory.getLogger("demo.payments");
        Thread blocked = null;
        try {
            MDC.put("request_id", "R7");
            log.info("hold"); // worker takes this event, then blocks in Gate
            Support.check(sink.entered.await(5, TimeUnit.SECONDS), "worker entered gate");
            for (int i = 1; i <= 12; i++) log.info("info {}", i);
            System.out.printf("neverBlock=%s: queued INFO=%d, threshold=%d%n",
                    neverBlock, async.getNumberOfElementsInQueue(), async.getDiscardingThreshold());
            Support.check(async.getNumberOfElementsInQueue() == 9, "strict remaining < 2");
            log.error("error 1"); // low-priority discard rule does not apply
            Support.check(async.getNumberOfElementsInQueue() == 10, "ERROR fills last slot");
            if (neverBlock) {
                log.error("error 2"); // offer() on full queue returns false
                System.out.println("full queue: error 2 call returned");
            } else {
                blocked = Thread.ofPlatform().start(() -> log.error("error 2"));
                long deadline = System.nanoTime() + TimeUnit.SECONDS.toNanos(5);
                while (!inQueuePut(blocked) && System.nanoTime() < deadline) Thread.sleep(1);
                boolean parked = inQueuePut(blocked);
                System.out.println("full queue: producer parked in ArrayBlockingQueue.put=" + parked);
                Support.check(parked, "producer really blocked in queue, not inferred from delay");
            }
            MDC.clear(); // queued event must keep its producer context
        } finally {
            sink.release.countDown();
            if (blocked != null) { blocked.join(5000); Support.check(!blocked.isAlive(), "producer completed"); }
            // stop() interrupts the worker. First let the controlled latch wait end normally.
            Support.check(sink.delivered.await(5, TimeUnit.SECONDS), "all expected events delivered");
            async.stop(); // worker drains and exits; makes captures visible to main
            MDC.clear();
        }
        long infos = sink.messages.stream().filter(s -> s.equals("hold") || s.startsWith("info ")).count();
        long errors = sink.messages.stream().filter(s -> s.startsWith("error ")).count();
        System.out.printf("kept INFO=%d/13, ERROR=%d/2; first MDC=%s%n", infos, errors, sink.requests.getFirst());
        Support.check(infos == 10 && errors == (neverBlock ? 1 : 2), "exact delivered counts");
        Support.check("R7".equals(sink.requests.getFirst()), "MDC snapshot taken before async handoff");
        ctx.stop();
    }
    public static void main(String[] args) throws Exception {
        var ctx = Support.reset();
        var defaults = new AsyncAppender();
        defaults.setContext(ctx); defaults.setName("DEFAULTS");
        defaults.addAppender(Support.capture(ctx, "UNUSED")); defaults.start();
        System.out.printf("defaults: queue=%d threshold=%d neverBlock=%s callerData=%s flush=%dms%n",
                defaults.getQueueSize(), defaults.getDiscardingThreshold(), defaults.isNeverBlock(),
                defaults.isIncludeCallerData(), defaults.getMaxFlushTime());
        defaults.stop(); ctx.stop();
        scenario(false);
        scenario(true);
    }
}
defaults: queue=256 threshold=51 neverBlock=false callerData=false flush=1000ms
neverBlock=false: queued INFO=9, threshold=2
full queue: producer parked in ArrayBlockingQueue.put=true
kept INFO=10/13, ERROR=2/2; first MDC=R7
neverBlock=true: queued INFO=9, threshold=2

В обеих ветках принято 10 из 13 INFO: hold и девять ожидающих. ERROR не подчиняется low-priority discard, но при neverBlock=true заполненный offer теряет и ERROR. При false второй ERROR действительно стоит в put, затем после release доставляется. First MDC=R7 прочитан sink уже после очистки карты producer: AsyncAppender подготовил deferred поля до передачи worker.

discardingThreshold=0 отключает ранний discard по уровню. С neverBlock=false это выбирает ожидание свободного места; с true полная очередь всё равно теряет событие. При остановке контекста stop прерывает worker и ждёт до maxFlushTime. Превышение срока даёт внутреннее предупреждение, но возвращение stop не подтверждает доставку всех записей: worker может ещё дренировать очередь, а завершение JVM оборвёт его. В нашем демо gate сначала освобождён и ожидаемые события подсчитаны, только затем вызывается stop.

Даже синхронная запись и immediateFlush=true не означают fsync, сохранение удалённым collector или атомарность с DB commit. Пропавший диск, завершение процесса и повторная доставка добавляют новые границы. Локальным файлам нужна ограниченная retention и политика rotation; вывод в stdout перекладывает их на платформу. Это отдельная эксплуатационная цепочка, которую проверяют под своей нагрузкой.

Если запись нужна как доказательство списания, источником истины служит транзакционный журнал бизнес-данных с явной моделью доставки, например Outbox. Диагностический ERROR не заменяет audit event. Выбирай потерю, блокировку и retention под назначение логов: асинхронный appender не может одновременно сделать медленный sink быстрым, сохранить каждый event и обеспечить неограниченно низкую задержку caller.

  • API, provider, logger, appender и encoder отвечают за разные участки пути. Диагностика начинается с фактического runtime и конфига.
  • Effective level проверяется на logger-источнике. Additivity ведёт уже принятое событие вверх; root level не заменяет appender filter.
  • {} откладывает форматирование, Supplier или guard — дорогой вызов. Throwable передавай как cause, а не только getMessage.
  • MDC требует scope и cleanup на том же потоке. Для executor нужен снимок при submission и восстановление worker в finally.
  • Encoder задаёт schema и типы JSON. Проверяй их parser, ограничивай данные до записи.
  • Полная async очередь выбирает discard или backpressure. Вернувшийся log-вызов не подтверждает долговечный аудит.

На собеседовании

Чем SLF4J отличается от Logback и почему лог может пропасть или дублироваться?

Я использую SLF4J как API в коде, а Logback как реализацию, которая принимает событие и записывает его через appenders. Для библиотеки оставляю зависимость от API; в приложении выбираю один совместимый provider. Если его нет, SLF4J предупреждает и работает как NOP. Поэтому первым проверяю зависимости именно запускаемого артефакта.

Дальше смотрю имя logger, effective level, additivity и appender filters. Уровень наследуется от ближайшего заданного предка, а принятое событие доходит к appenders выше по дереву. Если один appender подключён и в ветке, и у root, запись будет двойной. Если root стоит ERROR, это ещё не значит, что он отфильтрует DEBUG дочерней ветки: для этого нужен фильтр appender.

  • В API 2.0 provider ищется через ServiceLoader; binding с StaticLoggerBinder от 1.7 недостаточно. Multiple providers и игнорируемые старые bindings видны в диагностике старта.
  • Bridge переводит чужой API в выбранный стек. Встречный provider способен замкнуть цикл, например JUL → SLF4J → JUL.
  • TurboFilters принимают решение до обычного level check; filters appender работают уже с событием. Проверка уровня и фильтра пункта назначения не взаимозаменяемы.
Root ERROR, child DEBUG, appender root без фильтра: что получит appender?

При additivity=true DEBUG ребёнка будет доставлен appender root. Источник уже принял событие. Собственный вызов DEBUG у root, напротив, не создаст событие. Это две разные точки входа, проверенные в RoutesDemo.

Зачем плейсхолдеры в логах и как правильно записать исключение?

Я пишу сообщение с плейсхолдерами, чтобы backend форматировал аргументы только для принятого события. Но Java всё равно вычислит serialize(payload) до вызова debug. Если получение аргумента дорогое, ставлю isDebugEnabled или передаю Supplier в fluent API. Конкатенация заранее строит строку даже для отключённого уровня.

Исключение передаю последним аргументом вместе с понятным контекстом операции либо задаю setCause. Тогда остаются stack trace и цепочка причин. Один getMessage этого не сохраняет. Сбой логирую на той границе, которая решает, как он повлиял на обработку, чтобы одна ошибка не превращалась в несколько одинаковых ERROR.

  • Fluent builder требует завершающего log(). addArgument и addKeyValue описывают событие, но сами не отправляют его.
  • Передать дорогой результат в addArgument — не то же самое, что передать lambda, которая получает результат. И lambda не должна менять бизнес-поведение: при отключённом уровне она не выполнится.
  • Caller stack extraction, Throwable formatting и сериализация большого payload — разные расходы. Supplier убирает вычисление отключённого аргумента, но не делает принятую запись дешёвой.
Почему CPU не упал после отключения DEBUG, а ERROR потерял причину? 
log.debug("bank reply {}", serialize(reply));
log.error("bank failed {}", e.getMessage());

Вызов serialize выполняется до проверки DEBUG. Поставь guard или Supplier. Второй вызов сохраняет лишь строку сообщения ошибки; передай log.error("bank failed {}", paymentId, e). Пример — ревью гипотетического фрагмента; свойства проверены счётчиками и Capture в LazyDemo.

Что такое MDC и как сохранить request_id в пуле потоков?

Для меня MDC — небольшая карта контекста текущего потока: request_id, trace_id, иногда идентификатор операции. Backend берёт её для события, а encoder решает, как вывести. Пул переиспользует потоки, поэтому контекст запроса ставлю на входе и убираю или восстанавливаю в finally на том же потоке.

У executor отдельная граница. Копирую карту до submission, на worker сохраняю его карту, ставлю снимок, выполняю задачу и возвращаю прежнее состояние в finally. Очистка MDC в HTTP-потоке не очищает worker, и дочерний поток Logback не наследует карту автоматически. Без этих правил лог следующего запроса может получить чужой ID.

  • Захват внутри run() читает контекст worker. Захват при создании обёртки сохраняет запрос отправителя даже после смены caller на следующий запрос.
  • putCloseable удаляет ключ при close, не возвращает прежнее значение. Для вложенных scope сохраняю старую карту или старое значение явно.
  • Новый virtual thread тоже не наследовал MDC в данном Logback. Framework context propagation нужно проверить отдельно; ThreadLocal сам не переносит контекст по HTTP или брокеру.
Исправит ли finally в HTTP-потоке утечку фоновой задачи? 
MDC.put("request_id", requestId);
try {
    executor.execute(() -> log.info("sending to bank"));
} finally {
    MDC.clear();
}

Этот фрагмент даже не устанавливает request_id worker: это разные карты. Нужна обёртка или настроенный task decorator с capture до execute и restore внутри worker. finally caller нужен для caller, но не исправляет другого потока. Исключение в worker также должно проходить через его finally.

Как организовать логи сервиса и какие гарантии даёт асинхронная запись?

Я задаю стабильные события и отдельные поля: logger, level, время, request_id, идентификатор операции и исход. Encoder отдаёт записи в формате, который collector разбирает без поиска ID в свободном тексте. Проверяю реальные типы и экранирование, исключаю credentials и лишние payload. Ошибку передаю с причиной; агрегированные показатели считаю метриками.

AsyncAppender переносит запись на worker через ограниченную очередь. При медленном sink запас заканчивается: часть событий отбрасывается или caller ждёт. В Logback низкие уровни теряются до полного заполнения по умолчанию, а neverBlock=true способен потерять и ERROR в полной очереди. Поэтому latency, потери и shutdown policy выбираю явно; лог не считаю подтверждением транзакционного аудита.

  • Threshold=0 убирает раннюю потерю low-priority событий, но не full-queue offer loss и не crash loss. Увеличение очереди расходует heap и не повышает пропускную способность sink.
  • AsyncAppender фиксирует threadName/MDC до worker. Caller data нужно включить отдельно, иначе стек места вызова нельзя надёжно восстановить в другом потоке.
  • stop ожидает worker ограниченное время; flush OutputStream не равно fsync или подтверждению collector. Для обязательной бизнес-записи нужен отдельный durable протокол, связанный с транзакцией.
Очередь 10, threshold 2, осталось 2 места: потеряется ли следующий INFO?

Он пройдёт: условие remainingCapacity() < discardingThreshold строгое. После добавления останется 1, следующий INFO потеряется. ERROR сможет занять последнее место; ещё один ERROR будет ждать при neverBlock=false или потеряется при true. Эти переходы воспроизведены latch, а не выводом по таймингу.

Почему запрос по attempt > 1 не дал ожидаемый результат?

Проверь raw JSON и схему индекса. В нативном JsonEncoder этого демо поле лежит внутри kvpList, а его значение "2" строковое. Java Integer в addKeyValue не обещает JSON number у любого encoder. Согласуй явную схему преобразования с collector, сохрани единицы duration и не меняй имена полей между событиями.
