Other Maps & Sets

Каждая карта, кроме HashMap, решает свою задачу. LinkedHashMap — HashMap плюс двусвязный список через все записи. В режиме порядка доступа и с removeEldestEntry он даёт LRU-кеш в десять строк: в демо get переставил RUB в хвост, а вставка CNY вытеснила USD. TreeMap — красно-чёрное дерево: O(log n) вместо O(1), в замере в 20 раз медленнее на миллионе ключей. Зато есть навигация: floorEntry находит тариф, действующий на дату, а headMap/tailMap — живые представления диапазонов. HashSet — обёртка над HashMap с заглушкой PRESENT в значениях. IdentityHashMap сравнивает ключи через == и хранит их в одном массиве с линейным пробированием. WeakHashMap теряет запись, когда ключ собран сборщиком, — но не если ключ — строковый литерал или значение ссылается на ключ. EnumMap — массив по ordinal.

LinkedHashMap и LRU-кеш

Сервис платежей ходит за курсами валют к внешнему поставщику. Курсы нужны свежие, памяти на все пары не хватает, и держать стоит то, что спрашивают чаще всего, — классическое вытеснение LRU (least recently used). LinkedHashMap даёт его почти даром. Демо MapsDemo.java:

static final class Lru<K, V> extends LinkedHashMap<K, V> {
    private final int max;
    Lru(int max) { super(16, 0.75f, true); this.max = max; }      // accessOrder = true
    @Override protected boolean removeEldestEntry(Map.Entry<K, V> eldest) { return size() > max; }
}
== LinkedHashMap: insertion order vs access order
insertion order after get(RUB): [RUB, USD, EUR]
access order after get(RUB):    [USD, EUR, RUB]
LRU(3) after put(CNY):          [EUR, RUB, CNY]  (USD evicted)

Ограничения такого кеша: он не потокобезопасен — даже get меняет список, поэтому нужна синхронизация каждой операции (Collections.synchronizedMap, и тогда кеш становится узким местом); нет вытеснения по времени жизни, статистики и загрузки. В продакшене используют Caffeine: он масштабируется по потокам, поддерживает TTL и алгоритм W-TinyLFU, который по частоте обращений удерживает популярное лучше чистого LRU. Кеши на уровне сервиса — в Caching и Spring Cache. Порядок вставки LinkedHashMap полезен и сам по себе: предсказуемый JSON, отчёты в том порядке, в каком пришли данные, Collectors.toMap(..., LinkedHashMap::new). С Java 21 у него есть putFirst, pollFirstEntry и reversed() из SequencedMap, разобранные в Collections.

TreeMap: порядок и навигация

NavigableMap<LocalDate, String> fee = new TreeMap<>();
fee.put(LocalDate.of(2026, 1, 1), "1.5%");
fee.put(LocalDate.of(2026, 4, 1), "1.2%");
fee.put(LocalDate.of(2026, 9, 15), "0.9%");
fee.floorEntry(date);                                   // наибольший ключ ≤ date — действующий тариф
== TreeMap: the rate in force on a date
2026-03-31 -> floorEntry = 2026-01-01=1.5%
2026-09-15 -> floorEntry = 2026-09-15=0.9%
2025-12-31 -> floorEntry = null
headMap(2026-06-01) = [2026-01-01, 2026-04-01]
tailMap view sees later put: [2026-04-01, 2026-09-15, 2026-12-01]

Тарифы комиссии меняются с определённых дат, и для платежа нужен тариф, действующий на его дату, — наибольшая дата начала, не превосходящая дату платежа. В HashMap это перебор всех ключей; в TreeMap — floorEntry за O(log n). До первого тарифа null — граничный случай, который нужно обработать явно. Семейство навигации: floor (≤), ceiling (≥), lower (<), higher (>), first/last, pollFirst. Так решают «ближайшее время в расписании», «диапазон IP по началу», «окно времени для метрик».

headMap, tailMap и subMap — не копии, а живые представления диапазонов: тариф, добавленный после создания tailMap, виден через него. Запись в представление за пределами его диапазона бросает IllegalArgumentException. Флаги включения границ (tailMap(from, true)) избавляют от ошибок на единицу. descendingMap() — обратный порядок без копирования.

HashMap        1M get:   18.1 ms (5000000)
LinkedHashMap  1M get:   29.6 ms (5000000)
TreeMap        1M get:  378.0 ms (5000000)

Цена порядка — замер LookupBench.java на миллионе строковых ключей. TreeMap в 20 раз медленнее HashMap: около 20 сравнений строк на поиск, каждое — переход по ссылке на узел в другом месте памяти и compareTo с общим префиксом acc-. LinkedHashMap медленнее HashMap в полтора раза: узлы больше на две ссылки, хуже ложатся в кеш процессора. Вывод: TreeMap берут ради навигации или сортированного обхода, а не «на всякий случай». Если сортировка нужна один раз при выдаче, дешевле собрать HashMap и отсортировать ключи в конце.

Ловушка TreeMap и TreeSet: равенство для них — compare == 0, а не equals. BigDecimal("1.0") и BigDecimal("1.00") — один ключ в TreeMap и два в HashMap; компаратор «по сумме» выбрасывает платежи с одинаковой суммой — подробно в Collections. Ключи null TreeMap с естественным порядком не принимает. Для конкурентного доступа есть ConcurrentSkipListMap с тем же API навигации, в Concurrent Collections.

Множества — это карты

== HashSet is a HashMap
inner HashMap, values: Object PRESENT

HashSet внутри — поле map типа HashMap, где элементы — ключи, а значение у всех одно: статический Object PRESENT. add(e) — это map.put(e, PRESENT) == null. Поэтому всё из HashMap относится и к множеству: рост по load factor, деревья в корзинах, контракт equals/hashCode, нестабильный порядок. Так же LinkedHashSet построен на LinkedHashMap, TreeSet — на TreeMap, а ConcurrentHashMap.newKeySet() — на ConcurrentHashMap. Цена — полноценный узел на элемент с неиспользуемым полем значения; ради простоты кода JDK её платит.

EnumMap и EnumSet — массив по ordinal и биты в long, без хешей и узлов, с обходом в порядке объявления, — разобраны в Enums. Для ключей-enum они всегда лучше хеш-версий.

IdentityHashMap и WeakHashMap: другое равенство и другая жизнь

== IdentityHashMap: == instead of equals
HashMap size 1, IdentityHashMap size 2
IdentityHashMap table: one Object[64], keys and values side by side, linear probing

IdentityHashMap сознательно нарушает общий контракт Map: ключи сравниваются через ==, хеш — System.identityHashCode. Две равные, но разные строки — два ключа. Устроен иначе, чем HashMap: один массив Object[], где ключ и значение лежат в соседних ячейках, а коллизии решаются линейным пробированием — без узлов вообще. Применяется там, где важна именно идентичность объекта: обход графа объектов с пометкой посещённых (сериализаторы, глубокое копирование — иначе два равных, но разных объекта склеятся, а объекты с переопределённым equals зациклятся), прокси и кеши метаданных по экземпляру.

== WeakHashMap: entry disappears with its key
after GC: {literal-key=pinned}
value references its key: size after GC = 1

WeakHashMap держит ключи через слабые ссылки: когда на ключ не остаётся сильных ссылок, сборщик его собирает, ссылка попадает в очередь, и при следующей операции карта удаляет запись. Сессия, обнулённая в демо, исчезла после сборки. Две классические ошибки видны там же. Ключ-литерал "literal-key" не исчезнет никогда: литералы живут в пуле строк, на них всегда есть сильная ссылка. И запись, чьё значение ссылается на свой ключ, тоже не исчезнет: карта держит значения сильно, значение держит ключ, — размер остался 1. Механика слабых ссылок — в References.

Чем WeakHashMap не является — кешем. Записи исчезают не по нехватке памяти и не по давности, а по достижимости ключа, а равенство ключей — через equals, что для слабых ключей странно: два равных ключа, один из которых собран, ведут себя непредсказуемо. Типичные применения — метаданные к объектам, которыми вы не владеете: ThreadLocal устроен похоже, классы и загрузчики классов в контейнерах. Для кеша — Caffeine с weakKeys/softValues или ограничением размера.

WeakHashMap подходит как кеш, который сам очищается при нехватке памяти.

Запись живёт, пока жив ключ, а не пока хватает памяти. Строковые литералы и значения, ссылающиеся на ключ, держат записи вечно — в демо обе такие записи пережили сборку. Для кеша нужен ограниченный размер или TTL.

  • LinkedHashMap — HashMap со списком через записи; accessOrder + removeEldestEntry = LRU за O(1).
  • В режиме доступа get меняет структуру; LRU на LinkedHashMap не потокобезопасен — для продакшена Caffeine.
  • TreeMap: floor/ceiling/head/tail/subMap, представления живые; get в 20 раз медленнее HashMap.
  • TreeMap сравнивает через compare, не equals.
  • HashSet — HashMap с PRESENT; TreeSet — TreeMap, LinkedHashSet — LinkedHashMap.
  • IdentityHashMap: ==, identityHashCode, один массив с линейным пробированием.
  • WeakHashMap удаляет записи с собранными ключами; литералы и значения со ссылкой на ключ держат запись.

На собеседовании

Как реализовать LRU-кеш на стандартных коллекциях?

LinkedHashMap с accessOrder = true в конструкторе и переопределённым removeEldestEntry, который возвращает true, когда size() больше лимита. LinkedHashMap держит двусвязный список через записи; при доступе узел переносится в хвост, после вставки удаляется голова — самый давно использованный. Все операции O(1).

  • Без LinkedHashMap — HashMap + собственный двусвязный список (задача LeetCode 146).
  • Не потокобезопасен даже на чтение; в продакшене Caffeine (W-TinyLFU, TTL).
Что не так с этим кешем, вызываемым из контроллера? 
private final Map<String, Rate> cache = new LinkedHashMap<>(16, 0.75f, true) {
    protected boolean removeEldestEntry(Map.Entry<String, Rate> e) { return size() > 1000; }
};
public Rate rate(String pair) {
    return cache.computeIfAbsent(pair, provider::load);
}

Контроллер вызывается из многих потоков, а LinkedHashMap в режиме порядка доступа меняет список даже при чтении — гонки повредят и таблицу, и список: потерянные записи, циклы в списке, исключения при обходе. Нужна синхронизация (простой synchronized вокруг доступа сделает кеш узким местом) или Caffeine.newBuilder().maximumSize(1000).build(provider::load). Ещё стоит подумать о TTL: курсы устаревают.

Когда использовать TreeMap вместо HashMap?

Когда нужен порядок ключей или навигация: обход по возрастанию, ближайший ключ (floorKey, ceilingKey), диапазоны (subMap, headMap, tailMap). TreeMap — красно-чёрное дерево, операции O(log n), заметно медленнее HashMap. Ключи сравниваются через compareTo или компаратор, а не equals.

  • Представления диапазонов живые; запись вне диапазона — IllegalArgumentException.
  • Конкурентный аналог — ConcurrentSkipListMap.
  • Компаратор, несогласованный с equals, «склеивает» разные ключи.

Как устроен HashSet?

Внутри HashMap: элементы — ключи, значения — общий объект-заглушка PRESENT. add возвращает true, если put вернул null. Поэтому у HashSet те же свойства, что у HashMap: O(1), нужен корректный hashCode и equals, порядок не гарантирован.

  • TreeSet построен на TreeMap, LinkedHashSet — на LinkedHashMap.
  • Конкурентное множество — ConcurrentHashMap.newKeySet().

Что такое WeakHashMap и IdentityHashMap?

WeakHashMap держит ключи слабыми ссылками: когда ключ становится недостижим, запись удаляется. Подходит для метаданных к чужим объектам, но не для кеша. IdentityHashMap сравнивает ключи через == и identityHashCode — нужен при обходе графов объектов и там, где важна идентичность, а не равенство.

  • WeakHashMap: литералы-ключи и значения со ссылкой на ключ держат запись вечно.
  • IdentityHashMap — один массив с линейным пробированием, без узлов.
  • LinkedHashMap.removeEldestEntry, NavigableMap.
  • WeakHashMap, IdentityHashMap.
  • Caffeine: Efficiency (W-TinyLFU).
