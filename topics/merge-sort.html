Merge Sort

Два упорядоченных журнала не нужно сортировать с нуля

Два обработчика выгрузили платежи, каждый уже по возрастанию суммы. Нужно получить единый отчёт. Можно объединить массивы и снова вызвать sort, но тогда алгоритм заново устанавливает часть порядка, который уже известен. Можно вставлять каждую запись второго массива на её место в первом — однако сдвиги элементов могут дать квадратичную работу.

У каждого журнала самый маленький из ещё не прочитанных платежей стоит в голове. Значит, следующий элемент общего отчёта — меньшая из двух голов. После его выбора продвигается только соответствующий указатель. Все записи остаются доступными последовательным чтением, без возвратов и поиска по середине массива.

Эта операция называется merge. Если длины частей m и n, каждую запись нужно выдать один раз, поэтому время Θ(m + n), а сравнений ключей при непустых частях не больше m + n − 1. Последнюю оставшуюся серию можно дописать без сравнений: внутри неё порядок уже известен.

Merge sort строит весь алгоритм вокруг этой операции. Он сначала получает отсортированные части, затем сливает их. Важно не смешивать эти два контракта: merge ожидает, что обе входные серии уже отсортированы. Сам по себе он не исправит беспорядок внутри серии.

Выбор минимальной головы сохраняет правильный префикс

Пусть слева A:100, B:200, C:400, справа D:100, E:300, F:400. Буква — ID платежа, число — ключ сортировки. Левая серия была раньше правой в исходной последовательности, поэтому при равных суммах левую запись нужно выдать раньше: так сохраняется стабильность.

Инвариант перед каждой записью: выходной префикс содержит все уже выбранные элементы в правильном порядке, а i и j указывают на первые невыбранные элементы своих серий. Среди всех оставшихся минимален один из двух головных. Выбор меньшей головы добавляет ровно следующий правильный элемент и не нарушает порядок уже записанного префикса.

За один шаг один указатель обязательно увеличивается. Когда серия заканчивается, её нельзя читать даже ради сравнения. Поэтому проверка исчерпания стоит до обращения к aux[i] и aux[j]. При записи обратно в исходный массив сначала сохраняем обе серии в буфер: иначе ранняя запись может затереть ещё не прочитанный вход.

При равных ключах можно выбирать любую сторону: отсортированность ведь сохранится.

Отсортированность сохранится, стабильность — нет. Если D:100 взять раньше A:100, равные ключи поменяют относительный порядок. Для стабильного слияния вперёд выбираем слева при равенстве; поэтому в коде стоит ≤.

То же слияние считает пересечения порядка — инверсии

Инверсия — пара исходных индексов i < j, для которой a[i] > a[j]. Если текущий правый элемент меньше левой головы, он меньше всех ещё не выбранных слева: левая часть отсортирована. Значит, одной правой записи соответствуют сразу mid − i новых инверсий. Инверсии внутри половин считают рекурсивно, пересекающие границу — во время merge.

Равенство не образует инверсию: условие строгое. Поэтому ветка ≤ забирает слева и не увеличивает счётчик. Всего пар может быть n(n − 1)/2, так что нужен long; менять тип только в самом конце поздно.

Деление пополам ограничивает число уровней

Как получить отсортированные половины произвольного массива? Сортировать их тем же методом. Диапазон длины 0 или 1 уже упорядочен. Для большего диапазона делим его на два, сортируем каждую часть и применяем доказанное слияние. Здесь рекурсия уменьшает длину примерно вдвое независимо от содержимого массива.

Используем полуинтервалы [lo, hi). Длина — hi − lo, середина — lo + (hi − lo)/2, левая часть [lo, mid), правая [mid, hi). Эти части не пересекаются и покрывают исходный диапазон. Такая запись позволяет обработать пустой массив без особого значения последнего индекса −1.

Сохрани как MergePayments.java и запусти java MergePayments.java на JDK 21.

import java.util.Arrays;

public class MergePayments {
    record Payment(String id, int cents) {}
    static int comparisons;

    static void sort(Payment[] a) {
        Payment[] aux = new Payment[a.length]; // Один буфер на весь вызов сортировки.
        sort(a, aux, 0, a.length);
    }

    static void sort(Payment[] a, Payment[] aux, int lo, int hi) {
        if (hi - lo < 2) return; // Пустой диапазон и один элемент уже отсортированы.
        int mid = lo + (hi - lo) / 2;
        sort(a, aux, lo, mid);
        sort(a, aux, mid, hi);
        comparisons++;
        if (a[mid - 1].cents() <= a[mid].cents()) return; // Серии уже стыкуются.
        System.arraycopy(a, lo, aux, lo, hi - lo);
        int i = lo, j = mid;
        for (int k = lo; k < hi; k++) {
            if (i == mid) a[k] = aux[j++];
            else if (j == hi) a[k] = aux[i++];
            else {
                comparisons++;
                // При равенстве выбираем ЛЕВУЮ запись: сохраняем стабильность.
                a[k] = aux[i].cents() <= aux[j].cents() ? aux[i++] : aux[j++];
            }
        }
    }

    public static void main(String[] args) {
        Payment[] a = {new Payment("A", 100), new Payment("B", 200),
                new Payment("C", 400), new Payment("D", 100),
                new Payment("E", 300), new Payment("F", 400)};
        sort(a);
        System.out.println(Arrays.stream(a).map(Payment::id).toList());
        System.out.println("first comparisons=" + comparisons);
        comparisons = 0;
        sort(a);
        System.out.println("sorted comparisons=" + comparisons);
    }
}

На отсортированном входе проверка границы сработала для каждого внутреннего узла: максимум слева не больше минимума справа, поэтому сливать нечего. Для шести элементов осталось ровно пять сравнений границ. Для первого входа также проверили пять границ и сделали пять сравнений в финальном слиянии — всего 10.

В худшем случае на каждом из O(log n) уровней читаем и записываем O(n) элементов: T(n) = 2T(n/2) + Θ(n), итог Θ(n log n). Порядок входа не может превратить деление в цепочку, как неудачный pivot у quicksort. Проверка уже состыкованных серий улучшает лучший случай до Θ(n), но не ухудшает худший.

Буфер создаётся один раз на весь вызов и передаётся рекурсивным методам. Память буфера O(n), стека O(log n); вместе O(n). Счётчик comparisons в демо служит только для наблюдения. В библиотечном коде разделяемое изменяемое состояние, включая static-буфер, мешало бы независимым одновременным сортировкам.

Серии можно удваивать без рекурсивного стека

Рекурсия определяет порядок выполнения слияний, но не нужна самой операции merge. Начни с серий длины 1, слей соседние пары, затем серии длины 2, затем 4, 8 и так далее. Это bottom-up merge sort. Инвариант перед проходом ширины w: каждая серия длины до w уже отсортирована.

После слияния соседних серий получаем серии длины до 2w. На последнем участке массива может не быть полной правой половины — ограничивай hi длиной массива. Если правой серии вообще нет, участок уже готов и не требует слияния. Длина, не равная степени двойки, — обязательный тест такого решения.

Время остаётся O(n log n), буфер O(n), но стек вызовов теперь O(1). Увеличение ширины вдвое требует внимания к переполнению int на больших массивах: в задаче ниже арифметика проходов сделана в long, и только гарантированно допустимые границы преобразуются в int.

Частая ошибка — выделять новый массив при каждом маленьком слиянии. Максимально живых элементов всё ещё может быть O(n), но суммарные выделения по уровням достигают O(n log n), нагружая аллокатор и GC. Один общий буфер уменьшает выделения, сохраняя тот же механизм. Чередование ролей входного и выходного массивов позволяет также уменьшить копирования, но требует более строгого учёта, в каком массиве лежит текущий результат.

На собеседовании сначала напиши корректное merge с понятными границами и проверками исчерпания. Затем оберни его рекурсивным или итеративным порядком вызовов. Проверять два механизма одновременно труднее, чем отдельно доказать слияние и порядок формирования серий.

Слияние удобно для потоков, но обычный массив требует буфера

Обычный merge sort массива не является алгоритмом с O(1) дополнительной памятью. Факт, что итог находится в исходном массиве, не отменяет aux. Сложные способы сливать внутри одного массива без линейного буфера существуют, но у них другой код и компромиссы; их свойства нельзя приписывать показанной реализации.

Особый случай проще: у первого массива есть свободный хвост для всех элементов второго. Тогда можно заполнять результат с конца, выбирая большую из двух последних записей. Место записи всегда лежит правее непрочитанного префикса первого массива, пока во втором ещё есть элементы, поэтому данные не затираются. Именно дополнительная ёмкость, заданная условием, позволяет обойтись без отдельного буфера.

Если такое обратное слияние должно быть стабильным относительно последовательности «сначала левый вход, потом правый», при равенстве выбирай правую запись: мы ставим её на более позднюю позицию. Это обратное правило тому, которое действует при записи вперёд. Обе версии сохраняют один и тот же конечный порядок равных элементов.

У связного списка одно слияние можно выполнить перестановкой next без буфера элементов. Но рекурсивная сортировка списка всё ещё может использовать стек: память считается для всей реализации. Для файлов последовательное чтение серий и запись результата подходят к внешней сортировке: сначала создают части, помещающиеся в память, затем сливают. При большом числе серий наивный поиск минимума среди всех голов дорог; k-way merge и куча разобраны в Heap & Top-K.

Применять полный merge sort для одного минимума из журнала не нужно: хватит прохода. Если нужен стабильный общий порядок и доступен O(n) буфер, алгоритм даёт понятные гарантии. Когда используется готовый Java API, его контракт и адаптивные реализации смотри в Sorting in Java; учебный MergePayments не заменяет промышленную сортировку.

  • Merge поддерживает правильный выходной префикс выбором меньшей головы двух уже отсортированных серий.
  • Слияние вперёд берёт равный ключ слева; с конца — справа, если нужна стабильность.
  • Сбалансированные половины дают O(log n) уровней и O(n) работы на уровень.
  • Один общий буфер даёт O(n) памяти; отказ от рекурсии убирает стек, но не буфер.
  • Инверсии через границу считаются пачкой: если правый элемент меньше головы слева, добавляется mid − i.

Подсказка 1

Запись с начала может затереть непрочитанный элемент a.

Подсказка 2

Заполняй справа налево: сравнивай последние ещё не выбранные элементы.

Решение

k указывает на последнюю свободную позицию результата, i и j — на концы оставшихся префиксов. Пока j ≥ 0, k = i + j + 1 > i: запись не затирает непрочитанную часть a. После исчерпания b оставшиеся элементы a уже находятся на правильных местах.

    static int[] merge(int[] a, int m, int[] b, int n) {
        int i = m - 1, j = n - 1, k = m + n - 1;
        while (j >= 0) {
            // С конца кладём больший: непрочитанный префикс a не повреждаем.
            if (i >= 0 && a[i] > b[j]) a[k--] = a[i--];
            else a[k--] = b[j--];
        }
        return a; // Если b закончился, оставшаяся часть a уже на месте.
    }

Время O(m + n), дополнительная память O(1). Пустой b не требует ни одного перемещения.

Почему while (i >= 0 && j >= 0) недостаточно?

После такого цикла могут остаться элементы b, которые надо скопировать. Остаток a можно оставить на месте, остаток b — нельзя. В решении цикл продолжается, пока не закончится b.

Почему при равенстве здесь берут справа?

Мы заполняем поздние позиции. Правая запись в исходном объединении шла позже левой, поэтому должна занять более позднее место. Для int это не видно по идентичности, но правило позволяет сохранить стабильность для записей.

Подсказка 1

Изначально серии длины 1 уже отсортированы. Каждый проход удваивает длину серий.

Подсказка 2

Правая граница последнего слияния — min(start + 2·width, n). Если правой серии нет, слияние пропускается.

Решение

Во внешнем цикле выбираем ширину уже отсортированных серий. Во внутреннем сливаем соседние пары в том же массиве через общий aux. Арифметика проходов в long защищает от переполнения при удвоении width; доступ к массиву использует проверенные int-границы.

    static int[] sort(int[] input) {
        int[] a = input.clone(); // Контракт задачи: вход не менять.
        int[] aux = new int[a.length];
        int n = a.length;
        for (long width = 1; width < n; width *= 2) {
            for (long start = 0; start + width < n; start += 2 * width) {
                int lo = (int) start;
                int mid = (int) (start + width);
                int hi = (int) Math.min(start + 2 * width, n);
                // long для размеров прохода не даёт переполниться width * 2.
                if (a[mid - 1] <= a[mid]) continue;
                System.arraycopy(a, lo, aux, lo, hi - lo);
                int i = lo, j = mid;
                for (int k = lo; k < hi; k++) {
                    if (i == mid) a[k] = aux[j++];
                    else if (j == hi) a[k] = aux[i++];
                    else a[k] = aux[i] <= aux[j] ? aux[i++] : aux[j++];
                }
            }
        }
        return a;
    }

Худшее время O(n log n), память O(n) на результат и буфер, стек вызовов O(1). Проверка границы позволяет пропустить уже состыкованные серии.

Какие участки сливаются последними при длине 5?

При width = 4 сливаются [0,4) и [4,5). Правую границу нельзя брать как 8: физическая длина массива равна 5.

Достаточно ли hi = min(start + 2 * width, n), если width имеет тип int?

Нет: переполнение может случиться при вычислении выражения до вызова min. Используй long для расчёта границ или другую схему, которая проверяет переполнение заранее.

Посчитать инверсии порядка платежей

Для массива ключей a посчитай число пар i < j, у которых a[i] > a[j]. Это число перестановок относительного порядка в журнале. Равные значения не образуют инверсию, вход не меняй. Результат верни в long; нужен O(n log n) алгоритм.

Подсказка 1

Раздели пары на три группы: обе позиции слева, обе справа, позиции по разные стороны середины.

Подсказка 2

Когда берёшь меньший элемент справа, все оставшиеся слева больше него. Их количество mid − i.

Решение

Рекурсивные вызовы вернули количество инверсий в половинах и отсортировали их. Во время merge считаем только пары через границу; каждая такая пара учитывается ровно при выборе её правого элемента. При равенстве выбираем слева без увеличения счётчика.

    static long count(int[] input) {
        int[] a = input.clone();
        return solve(a, new int[a.length], 0, a.length);
    }

    static long solve(int[] a, int[] aux, int lo, int hi) {
        if (hi - lo < 2) return 0;
        int mid = lo + (hi - lo) / 2;
        long result = solve(a, aux, lo, mid) + solve(a, aux, mid, hi);
        System.arraycopy(a, lo, aux, lo, hi - lo);
        int i = lo, j = mid;
        for (int k = lo; k < hi; k++) {
            if (i == mid) a[k] = aux[j++];
            else if (j == hi) a[k] = aux[i++];
            else if (aux[i] <= aux[j]) a[k] = aux[i++];
            else {
                a[k] = aux[j++];
                result += mid - i; // Правая запись меньше ВСЕХ оставшихся слева.
            }
        }
        return result;
    }

Время O(n log n), дополнительная память O(n), включая копию входа и буфер. Счётчик long нужен уже внутри рекурсии: для 65 537 убывающих элементов ответ больше Integer.MAX_VALUE.

Почему result++ вместо result += mid - i неверно?

Правый элемент может быть меньше сразу нескольких оставшихся слева. Например, при слиянии [2,4] и [1,3] выбор 1 даёт две инверсии, а не одну.

Сколько инверсий в [7,7,7] и в [3,2,1]?

В первом массиве 0, поскольку неравенство строгое. Во втором 3: (3,2), (3,1), (2,1). Оба случая проверяют смысл сравнения и формулу пачки.
