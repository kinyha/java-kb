Brokers & Guarantees

Брокер сообщений развязывает отправителя и получателя по времени: отправитель не ждёт, а получатель обрабатывает, когда может. Очередь раздаёт каждое сообщение одному из конкурирующих консьюмеров, публикация-подписка — копию каждому подписчику. Гарантия доставки определяется тем, когда консьюмер подтверждает сообщение: до обработки — at-most-once, сообщения теряются при падении; после — at-least-once, сообщения приходят повторно. Exactly-once между брокером и внешним миром не бывает; его заменяет at-least-once плюс идемпотентный консьюмер, который распознаёт повторы по id сообщения.

Списание провели дважды, а другое не провели вовсе — и брокер работал без сбоев

Сервис списаний читает команды «списать с карты» из брокера. После очередного деплоя два клиента получили двойное списание, а одна команда исчезла: в брокере её нет, в базе списания тоже. Брокер ни разу не падал. Причина в одном и том же месте — в моменте, когда консьюмер говорит брокеру «готово», относительно момента, когда он реально сделал работу. Деплой убил процессы посреди обработки, и в одном варианте кода это теряет сообщения, в другом — повторяет.

Тема разбирает модели доставки и гарантии, общие для всех брокеров. Устройство Kafka — в Basics, её транзакции и exactly-once — в Delivery Semantics, поведение RabbitMQ — в RabbitMQ, повторы и DLQ — в Retries & DLQ. Демо MessagingDemo.java работает с RabbitMQ 4.3.6 в Docker; падение процесса моделируется закрытием канала без подтверждения — для брокера это одно и то же.

Очередь делит сообщения между воркерами, публикация-подписка копирует их каждому

== queue (competing consumers): worker1=[p-1, p-3] worker2=[p-2, p-4]
== pub/sub (fanout): antifraud=[p-1, p-2] analytics=[p-1, p-2]

В модели очереди (point-to-point) два воркера подписаны на одну очередь, и брокер раздаёт сообщения по кругу: каждое обрабатывает ровно один. Так масштабируют обработку задач: больше воркеров — больше пропускная способность. В модели публикации-подписки событие получает каждый подписчик: и антифрод, и аналитика увидели оба платежа. Так одно событие доходит до всех заинтересованных сервисов, а отправитель о них не знает.

Брокеры совмещают обе модели. В RabbitMQ fanout-exchange копирует событие в очередь каждого сервиса, а внутри очереди экземпляры сервиса конкурируют. В Kafka топик читают несколько групп консьюмеров, каждая получает все события, а внутри группы партиции делятся между экземплярами. Правило одно: каждому логическому получателю — своя очередь или группа, а его экземпляры — конкурирующие консьюмеры внутри неё.

Подтверждение до обработки теряет сообщения при падении: at-most-once

Если консьюмер подтверждает сообщение сразу при получении (autoAck в RabbitMQ, коммит смещения до обработки в Kafka), брокер удаляет его до того, как работа сделана. Консьюмер получил три команды, обработал одну и упал:

received.add(body(ch.basicGet("charges", true)));   // autoAck=true: брокер удалил сразу.
processed.add(received.get(0));                     // Обработал одно и упал.
ch.close();
== at-most-once (autoAck): received [charge p-1, charge p-2, charge p-3], processed [charge p-1], left in queue 0

Две команды исчезли: брокер считает их доставленными, а консьюмер их не выполнил. Каждое сообщение обрабатывается не больше одного раза, а возможно, ни разу. Это допустимо для метрик, логов, обновлений позиции на карте — там, где потеря одного значения не важна, а следующее его заменит. Для денег и заказов — нет.

Подтверждение после обработки повторяет сообщения при падении: at-least-once

Если подтверждать после обработки, сообщение не потеряется: брокер удалит его только по ack, а неподтверждённое вернёт и доставит снова. Но если процесс упал после работы и до ack, работа будет сделана дважды:

handle(r2, done, log);      // Деньги списаны...
ch.close();                 // ...и процесс упал до ack.

static void handle(GetResponse r, Set<String> done, List<String> log) {
    boolean fresh = done.add(r.getProps().getMessageId());   // В проде — insert в той же транзакции.
    ...
}
== at-least-once (ack after work) + idempotent consumer:
  charge p-1 id=evt-1 redelivered=false -> charged
  charge p-2 id=evt-2 redelivered=false -> charged
  charge p-2 id=evt-2 redelivered=true -> duplicate, skipped
  charge p-3 id=evt-3 redelivered=false -> charged

Команда p-2 пришла дважды: второй раз с флагом redelivered=true. Флаг лишь подсказывает, что сообщение уже доставлялось, но не говорит, обработано ли оно, поэтому полагаться на него нельзя. Защищает идемпотентный консьюмер: отправитель даёт каждому сообщению уникальный id, а консьюмер в той же транзакции, что и списание, записывает id в таблицу обработанных. Повтор находит id и ничего не делает. В демо таблица — множество в памяти; в реальном сервисе это insert ... on conflict do nothing в базе, иначе после рестарта память пуста и дубль пройдёт.

Альтернатива таблице — естественная идемпотентность операции: update payment set status = 'CAPTURED' where id = ? and status = 'AUTHORIZED' безопасно выполнить дважды, второй раз изменит ноль строк. Для операций во внешней системе — банк, письмо — ключ идемпотентности передают дальше, если она его поддерживает.

Exactly-once — это at-least-once с дедупликацией, а не свойство брокера

Брокеры обещают exactly-once, и это правда в узких рамках. Kafka гарантирует, что цепочка «прочитать из топика — записать в топик — закоммитить смещение» выполнится атомарно, если всё происходит внутри Kafka. Как только обработчик пишет в базу, отправляет письмо или вызывает банк, транзакция Kafka эту запись не покрывает, и повтор после падения снова возможен. Подробно — в Delivery Semantics.

Практическая формула: at-least-once доставка плюс идемпотентная обработка дают эффект ровно один раз. Отправитель со своей стороны тоже должен публиковать надёжно — без потерь между базой и брокером, — для этого есть Transactional Outbox. Вместе получается цепочка: outbox на отправителе, at-least-once в брокере, inbox или идемпотентность на получателе.

Включим exactly-once в Kafka, и дубли списаний исчезнут.

Exactly-once в Kafka покрывает только запись в Kafka и коммит смещений. Списание в базе или вызов банка выполняются вне этой транзакции, и после падения обработчик повторит их. Дубли убирает идемпотентный консьюмер с id сообщения или идемпотентная операция.

Порядок и параллелизм конфликтуют: порядок держат по ключу

Гарантированный порядок есть только у одного потока сообщений с одним консьюмером: одна очередь с одним активным консьюмером или одна партиция Kafka. Любой параллелизм — несколько консьюмеров, повторы, prefetch с параллельной обработкой — позволяет более позднему сообщению обработаться раньше. Глобальный порядок обычно и не нужен: важен порядок событий одного платежа, а события разных платежей независимы. Поэтому сообщения разбивают по ключу — id платежа — на партиции или очереди, и внутри ключа порядок сохраняется, а между ключами идёт параллельная обработка.

Обработчик всё равно стоит защищать от неправильного порядка: повтор из DLQ, ручная переотправка или ошибка маршрутизации могут привести устаревшее событие. Версия агрегата в событии и проверка «применять, только если версия больше текущей» делают обработку устойчивой к переупорядочиванию так же, как id делает её устойчивой к дублям.

Ядовитое сообщение, которое никогда не обработается, при строгом порядке блокирует свой ключ или всю партицию. Его отправляют в DLQ после ограниченного числа попыток, понимая, что для этого ключа порядок нарушится; как это устроено, разобрано в Retries & DLQ.

  • Очередь — конкурирующие консьюмеры, каждое сообщение одному; pub/sub — копия каждому подписчику. Каждому сервису — своя очередь или группа.
  • Ack до работы — at-most-once: в демо две команды из трёх исчезли.
  • Ack после работы — at-least-once: падение до ack повторило списание; флаг redelivered не доказывает обработку.
  • Идемпотентный консьюмер: id сообщения в таблице обработанных в той же транзакции, что и работа.
  • Exactly-once — эффект at-least-once плюс дедупликации; порядок держат по ключу и версиям.

На собеседовании

Какие бывают гарантии доставки и от чего они зависят?

At-most-once — сообщение обработается не больше одного раза, но может потеряться: консьюмер подтверждает до обработки. At-least-once — не потеряется, но может прийти повторно: подтверждение после обработки, падение между ними даёт повтор. Exactly-once — ровно один раз; на уровне доставки между брокером и внешней системой недостижим, его эффект получают через at-least-once и идемпотентного консьюмера.

  • Гарантия определяется порядком «работа — подтверждение» у консьюмера и подтверждениями брокера у продюсера.
  • Exactly-once в Kafka покрывает только чтение, запись в Kafka и коммит смещений.
  • Отправителю нужна надёжная публикация: outbox вместо двойной записи.

Как сделать консьюмера идемпотентным?

У каждого сообщения уникальный id от отправителя. Консьюмер в той же транзакции, что и свою работу, вставляет id в таблицу обработанных; если id уже есть, сообщение пропускается. Либо сама операция идемпотентна: условный update по статусу или версии, upsert по ключу.

  • Хранилище id должно быть транзакционно связано с работой; set в памяти теряется при рестарте.
  • Флаг redelivered и номер попытки — подсказка, а не доказательство обработки.
  • Таблицу обработанных чистят по сроку больше окна возможных повторов.
Почему здесь всё равно возможно двойное списание? 
@RabbitListener(queues = "charges")
void onCharge(ChargeCommand cmd, @Header(AmqpHeaders.REDELIVERED) boolean redelivered) {
    if (redelivered) {
        log.info("skip redelivered {}", cmd.id());
        return;
    }
    bank.charge(cmd.cardToken(), cmd.amount());
}

Флаг redelivered ставится и тогда, когда первая попытка упала до списания, — такое сообщение будет пропущено и потеряно. А дубль, пришедший новым сообщением после переотправки продюсером, флага не имеет и спишет второй раз. Нужна дедупликация по id команды в базе в одной транзакции с фиксацией результата и ключ идемпотентности в вызове банка.

Чем очередь отличается от публикации-подписки?

В очереди каждое сообщение получает один из конкурирующих консьюмеров — так масштабируют обработку задач. В pub/sub каждый подписчик получает свою копию — так событие доходит до всех заинтересованных сервисов. Брокеры совмещают обе модели: своя очередь или группа консьюмеров на сервис, экземпляры сервиса конкурируют внутри неё.

  • В RabbitMQ — fanout или topic exchange плюс очередь на сервис; в Kafka — группа консьюмеров на сервис.
  • Порядок сохраняется только внутри одного потока: партиции или очереди с одним активным консьюмером.
  • Gregor Hohpe, Bobby Woolf, Enterprise Integration Patterns — основа урока: point-to-point, publish-subscribe, competing consumers, idempotent receiver.
  • RabbitMQ: Reliability Guide — подтверждения, повторная доставка, флаг redelivered.
  • Apache Kafka: Message Delivery Semantics — at-most-once, at-least-once, exactly-once в Kafka.
  • Martin Kleppmann, «Designing Data-Intensive Applications», глава 11 — гарантии потоковой обработки и идемпотентность.
