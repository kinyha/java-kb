Metrics

Метрика — число во времени с набором меток. Prometheus сам опрашивает сервисы (pull) и хранит ряды; в Java метрики пишут через Micrometer. Типы: counter только растёт и сбрасывается при перезапуске, поэтому его читают через rate(), которая учитывает сброс; gauge — текущее значение; histogram — счётчики по корзинам задержки, из которых histogram_quantile считает перцентиль по всем экземплярам. Перцентили нельзя усреднять: среднее p99 двух экземпляров в демо — 185 мс, а настоящий общий p99 — 313 мс. Каждое уникальное сочетание меток — отдельный ряд: метка с id пользователя дала 1 000 рядов у одного счётчика, а одна гистограмма — 69 рядов корзин на каждое сочетание меток. Число рядов — главная цена метрик.

Средняя задержка на дашборде в норме, а пользователи жалуются

На дашборде сервиса платежей — среднее по экземплярам p99, построенное из перцентилей, которые каждый экземпляр считает сам. Один экземпляр медленный, но получает мало трафика, и среднее выглядит терпимо. После деплоя график общего числа запросов проваливается вниз — счётчики перезапущенных экземпляров начались с нуля. А в прошлом месяце Prometheus упал по памяти: кто-то добавил к метрике метку с номером заказа.

Тема разбирает модель Prometheus, типы метрик и то, как их правильно читать и агрегировать. Демо MetricsDemo.java запускает два экземпляра сервиса со своими реестрами Micrometer 1.15: A — 250 запросов в секунду по ~10 мс, B — 5 в секунду по ~300 мс; на 20-й секунде B перезапускается. Prometheus 3.6 в Docker опрашивает их раз в секунду, итоги снимаются PromQL-запросами к его API. Обзор сигналов — в Observability Overview, SLO и алерты — в Availability & SLO.

Pull-модель и типы метрик

Timer timer = Timer.builder("http.server.requests").tag("uri", "/payments")
        .publishPercentileHistogram()           // корзины для histogram_quantile в Prometheus
        .register(registry);
timer.record(Duration.ofMillis(10));

// /metrics: текст в формате Prometheus. Prometheus 3 отвергает ответ без Content-Type.
ex.getResponseHeaders().set("Content-Type", "text/plain; version=0.0.4; charset=utf-8");
byte[] b = registry.scrape().getBytes(StandardCharsets.UTF_8);

Pull-модель удобна тем, что Prometheus сам знает, кого опрашивать (обнаружение целей через Kubernetes), и отличает «сервис молчит» от «сервис мёртв». Для коротких задач, которые не доживут до опроса, есть Pushgateway или отправка по OTLP. Prometheus 3 строже к формату: при первом прогоне демо обе цели были в состоянии down с ошибкой «non-compliant scrape target sending blank Content-Type» — самописный обработчик не выставлял заголовок. Spring Boot Actuator и библиотеки Prometheus выставляют его сами.

Счётчик сбрасывается при перезапуске, rate это учитывает

== counter reset when B restarted
   raw counter of B now         b=100
   resets of B in 45 s          b=1
   increase of B over 40 s      b=189

Экземпляр B за 40 секунд обработал 200 запросов, но на 20-й секунде перезапустился, и его счётчик начался заново — сейчас он показывает 100. График сырого значения провалился бы в момент перезапуска, а сумма сырых счётчиков по экземплярам после деплоя уменьшилась бы. resets() нашла один сброс, а increase() за 40 секунд — 189: функция замечает, что значение уменьшилось, считает это сбросом и продолжает суммировать прирост. Не ровно 200, потому что rate и increase экстраполируют по точкам опроса внутри окна. Поэтому счётчики всегда читают через rate или increase, а окно делают не меньше нескольких интервалов опроса.

Перцентили не усредняют — их считают по объединённым корзинам

== PromQL over the last 20 s
   requests/s by instance       a=224  b=4.525
   p99 from merged histograms   0.313
   p99 of each instance         a=0.013  b=0.357
   avg of per-instance p99      0.185
histogram_quantile(0.99, sum by (le) (rate(http_server_requests_seconds_bucket[20s])))           # верно
avg(histogram_quantile(0.99, sum by (instance, le) (rate(http_server_requests_seconds_bucket[20s]))))  # неверно

Из всех запросов 2 % — медленные запросы B. Значит, каждый сотый запрос пользователя — около 300 мс, и правильный p99 по объединённым корзинам — 313 мс. p99 каждого экземпляра — 13 мс у A и 357 мс у B, их среднее — 185 мс: такой задержки нет ни у одного запроса, и она на 40 % ниже настоящей. Среднее перцентилей не учитывает, сколько запросов за каждым стоит. Корзины же — счётчики, их можно складывать между экземплярами, и histogram_quantile считает перцентиль по общему распределению. Поэтому для задержки используют гистограммы, а summary — перцентили, посчитанные в процессе, — годятся только для одного экземпляра. В Micrometer 1.15 с включённой гистограммой реестр Prometheus и не отдаёт перцентили, посчитанные в процессе.

Скорость A — 224 в секунду вместо 250, потому что в 20-секундное окно попали 2,5 секунды после остановки нагрузки. А p99 у B — 357 мс при реальных 290–310: histogram_quantile предполагает равномерное распределение внутри корзины и интерполирует между её границами. Точность ограничена шириной корзин, поэтому их границы подбирают под SLO: если цель «p99 < 300 мс», нужна граница ровно на 300 мс.

Prometheus 3 поддерживает и нативные гистограммы: корзины с экспоненциальными границами, которые хранятся одним рядом, а не рядом на корзину. Они точнее и дешевле по кардинальности, но требуют поддержки в клиенте и формате обмена; классические гистограммы с метками le по-прежнему самый совместимый вариант.

Кардинальность: каждое сочетание меток — отдельный ряд

== series count
   orders{user_id=...} series   1000
   buckets of one timer         69

Счётчик заказов с меткой user_id для 1 000 пользователей — 1 000 рядов, для миллиона — миллион, и каждый ряд Prometheus держит в памяти. Гистограмма Micrometer по умолчанию — 69 рядов корзин на каждое сочетание меток, и метки перемножаются: 69 корзин × 20 URI × 5 кодов ответа × 3 метода × 30 экземпляров — уже 621 000 рядов у одной метрики. Правило: в метки кладут только ограниченные наборы значений — шаблон URI (/orders/{id}, а не /orders/42), класс кода ответа, имя метода. Идентификаторы пользователей, заказов, запросов — в логи и трассы. Корзины ограничивают через serviceLevelObjectives или minimumExpectedValue и maximumExpectedValue.

Что собирать: для сервисов — RED (rate, errors, duration) по каждому эндпоинту и вызову зависимостей; для ресурсов — USE (utilization, saturation, errors): пулы соединений, очереди, потоки. Micrometer в Spring Boot сразу отдаёт метрики JVM — heap, паузы GC, потоки, — HTTP-сервера, HikariCP и клиентов. Grafana строит дашборды по PromQL, а алерты строят по SLO и скорости сжигания бюджета, как в Alerting & Incidents.

Общий p99 сервиса — это среднее p99 его экземпляров.

Среднее перцентилей не учитывает, сколько запросов обработал каждый экземпляр. В демо среднее p99 — 185 мс, а p99 по объединённым корзинам гистограмм — 313 мс. Перцентили по нескольким экземплярам считают только из гистограмм.

  • Prometheus опрашивает /metrics (pull); Prometheus 3 требует Content-Type, иначе цель down.
  • Counter читают через rate/increase: B перезапустился, сырой счётчик 100, resets 1, increase за 40 с — 189.
  • Перцентили считают histogram_quantile по сумме корзин: 313 мс; среднее p99 экземпляров — неверные 185 мс.
  • Точность перцентиля — ширина корзины: B показал 357 мс при реальных ~300; границы — под SLO.
  • Кардинальность: метка user_id — 1 000 рядов, гистограмма — 69 рядов на сочетание меток; идентификаторы — в логи.

На собеседовании

Какие типы метрик есть в Prometheus и как их читать?

Counter — только растёт, сбрасывается при перезапуске; читают через rate или increase. Gauge — текущее значение, растёт и падает. Histogram — счётчики по корзинам значений, из них histogram_quantile считает перцентили, и их можно агрегировать по экземплярам. Summary — перцентили, посчитанные в процессе, не агрегируются.

  • rate учитывает сбросы счётчика и экстраполирует внутри окна.
  • Точность histogram_quantile — ширина корзины; границы подбирают под SLO.
  • Pull-модель: up=0 — отдельный сигнал отказа.

Что такое кардинальность метрик и почему она опасна?

Число уникальных сочетаний меток — каждое становится отдельным рядом, который Prometheus хранит в памяти. Метка с неограниченными значениями (id пользователя, заказа, полный путь с параметрами) создаёт миллионы рядов и роняет систему мониторинга. В метки кладут только ограниченные наборы: шаблон пути, класс статуса, метод.

  • Метки перемножаются, гистограмма умножает ещё на число корзин.
  • Идентификаторы — в логи и трассы, связь с метриками — через exemplars.
Что не так с этой метрикой? 
Timer.builder("payment.duration")
     .tag("path", request.getRequestURI())        // /payments/81723/confirm
     .tag("user", userId)
     .tag("status", String.valueOf(code))
     .publishPercentiles(0.5, 0.99)
     .register(registry)
     .record(elapsed);

Путь с идентификатором платежа и id пользователя дают новый ряд почти на каждый запрос — неограниченная кардинальность. Перцентили, посчитанные в процессе, нельзя агрегировать по экземплярам. Нужно: шаблон пути (/payments/{id}/confirm), без user, статус как класс или код, publishPercentileHistogram() с границами под SLO, а идентификаторы — в логи и трассы.

Какие метрики собирать для сервиса?

RED для каждого эндпоинта и каждой зависимости: скорость запросов, доля ошибок, распределение задержки гистограммой. USE для ресурсов: загрузка, насыщение, ошибки — пулы соединений, потоки, очереди, CPU и память. Метрики JVM: heap, паузы GC, потоки. Бизнес-метрики: успешные платежи в минуту.

  • Насыщение пулов и очередей предупреждает раньше, чем растут ошибки.
  • Алерты — по SLO и скорости сжигания бюджета, а не по каждому графику.
  • Prometheus: Metric types, Histograms and summaries.
  • PromQL functions — rate, increase, resets, histogram_quantile.
  • Micrometer: Histograms and percentiles.
  • Brendan Gregg, «The USE Method»; Tom Wilkie, «The RED Method».
