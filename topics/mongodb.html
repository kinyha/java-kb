MongoDB

MongoDB хранит документы — вложенные структуры в формате BSON — и делает атомарным изменение одного документа. Поэтому модель данных строят вокруг того, что меняется и читается вместе: связанные данные вкладывают в документ, а не раскладывают по коллекциям. Индексы похожи на B-tree в реляционных базах, и порядок полей в составном индексе подчиняется правилу ESR: равенство, сортировка, диапазон. Надёжность записи задаёт write concern: подтверждение одного узла или большинства реплика-сета. Транзакции на несколько документов есть, но дороже, чем в реляционной базе, и при хорошей модели нужны редко.

Возвраты по платежу превысили сумму платежа, а подтверждённая запись исчезла после смены primary

Сервис возвратов хранит платежи в MongoDB. Чтобы вернуть деньги, он читает платёж, проверяет, что сумма возвратов не превысит сумму платежа, и записывает новый возврат. Два параллельных возврата по 300 на платёж в 500 прошли оба. Другой сервис писал события с подтверждением одного узла; после переключения primary часть подтверждённых событий пропала. А лента платежей магазина работала медленно, хотя составной индекс по всем трём полям запроса был.

Тема разбирает модель документов, атомарность, индексы, write concern и транзакции MongoDB. Обзор NoSQL-моделей — в Overview, индексы в реляционной базе — в Indexes, репликация и потеря подтверждённых записей в PostgreSQL — в Replication. Демо MongoDemo.java работает с реплика-сетом из трёх узлов MongoDB 8.2 в Docker (скрипт setup.sh) через Java-драйвер 5.13. Образ mongo:8 не запустился на ядре 6.19 в Docker VM из-за известной несовместимости, поэтому версия закреплена.

Атомарен один документ, поэтому то, что меняется вместе, кладут в один документ

// Возврат проходит, только если вместе с прошлыми не превысит сумму платежа (500).
payments.updateOne(and(eq("_id", "p-1"), lte("refunded", 500 - 200)),
        combine(push("refunds", new Document("id", "r-1").append("amount", 200)), inc("refunded", 200)));
payments.updateOne(and(eq("_id", "p-1"), lte("refunded", 500 - 350)),
        combine(push("refunds", new Document("id", "r-2").append("amount", 350)), inc("refunded", 350)));
== refund 200: matched 1; refund 350 more: matched 0
   {"_id": "p-1", "merchant": 7, "amount": 500, "refunded": 200, "refunds": [{"id": "r-1", "amount": 200}]}

Возвраты вложены в документ платежа, и вместе с ними хранится сумма уже возвращённого. Проверка «не превысит ли» и запись идут одной командой: условие в фильтре, изменение в обновлении. MongoDB выполняет обновление одного документа атомарно, поэтому параллельный второй возврат увидит уже обновлённое refunded и не совпадёт с фильтром — второй возврат на 350 отклонён. Чтение, проверка в коде и отдельная запись, как в истории выше, гонку не закрывают — это то же потерянное обновление, что в ACID & Isolation.

Вкладывать стоит то, что читается и меняется вместе с родителем и растёт ограниченно: возвраты платежа, позиции заказа, адреса клиента. Ссылки через id — для того, что живёт отдельно, нужно многим родителям или растёт без предела: все платежи магазина нельзя вложить в документ магазина, у документа предел 16 МБ, и каждое изменение переписывает его целиком. Схема в MongoDB не обязательна, но для важных коллекций её задают валидатором $jsonSchema, чтобы отсутствующее поле не ломало условия, как случилось в первой версии этого демо, где фильтр по несуществующему refunded ничего не находил.

Порядок полей в индексе — равенство, сортировка, диапазон

c.find(and(eq("merchant", 42), gt("amount", 2500))).sort(descending("createdAt")).limit(10).explain();
== no index:                            docsExamined 200000, keysExamined      0, in-memory SORT true, COLLSCAN
== index (merchant, amount, createdAt): docsExamined     10, keysExamined     80, in-memory SORT true, IXSCAN
== index (merchant, createdAt, amount): docsExamined     10, keysExamined     22, in-memory SORT false, IXSCAN

Без индекса MongoDB прочитала все 200 тысяч документов (COLLSCAN) и отсортировала в памяти. Индекс в порядке полей запроса — (merchant, amount, createdAt) — сузил поиск, но из-за диапазона по amount ключи внутри него не упорядочены по времени, и понадобилась сортировка в памяти по 80 ключам. Индекс (merchant, createdAt, amount) отдаёт ключи магазина уже по времени, сортировка не нужна, и чтение остановилось после 22 ключей ради 10 результатов. Это правило ESR: Equality, Sort, Range. Сортировка в памяти ограничена 100 МБ и на больших выборках падает или уходит на диск, поэтому SORT в плане — сигнал проверить индекс.

Write concern решает, сколько узлов должно подтвердить запись

Реплика-сет — primary и secondary, которые копируют журнал операций (oplog) асинхронно. Write concern определяет, когда драйвер получит подтверждение: w:1 — когда запись принял primary, w:majority — когда большинство узлов. Демо останавливает обе secondary:

-- docker stop mongo-2
-- docker stop mongo-3
== two secondaries down, w:1 insert -> acknowledged
== w:majority insert -> WriteConcernTimeout: waiting for replication timed out
   documents on primary now: 2

С w:1 запись подтверждена — но она есть только на primary. Если он упадёт, новый primary из оставшихся узлов её не знает, а старый при возвращении откатит её в файл rollback: подтверждённое событие пропадёт, как в истории выше. С w:majority драйвер ждал подтверждения большинства и через 2 секунды получил таймаут. Важная деталь: документов на primary два — запись с таймаутом не отменена, она просто не подтверждена большинством. Приложение не знает, сохранится ли она, и повтор должен быть идемпотентным.

С MongoDB 5.0 умолчание — w:majority. Для чтения парный параметр — read concern: majority возвращает только данные, подтверждённые большинством и не способные откатиться. Чтение с secondary (readPreference=secondary) может вернуть устаревшие данные, как чтение с асинхронной реплики PostgreSQL.

Транзакции на несколько документов есть, но их стараются не требовать

session.withTransaction(() -> {
    acc.updateOne(session, eq("_id", "a"), inc("balance", -70));
    acc.updateOne(session, eq("_id", "b"), inc("balance", 70));
    return null;
});
== transfer in a transaction: [{"_id": "a", "balance": 30}, {"_id": "b", "balance": 70}]

С версии 4.0 MongoDB поддерживает транзакции на несколько документов в реплика-сете, с 4.2 — и в шардированном кластере. Перевод между счетами выполнился атомарно. withTransaction сам повторяет транзакцию при временных ошибках — TransientTransactionError — и коммит при неизвестном результате. Транзакции дороже одиночных операций, держат изменения в памяти и по умолчанию прерываются через 60 секунд, поэтому модель данных стараются строить так, чтобы инварианты жили в одном документе, а транзакции оставались исключением.

Масштабирование записи — шардирование коллекции по shard key: данные делятся на диапазоны (chunks), а балансировщик переносит их между шардами. Ключ выбирают по тем же правилам, что в Sharding: он должен быть в основных запросах и давать равномерную нагрузку; запросы без него рассылаются на все шарды. С версии 5.0 ключ можно сменить командой reshardCollection, но это тяжёлая операция с копированием всех данных.

MongoDB не поддерживает транзакции, поэтому для денег не подходит.

Атомарно обновление одного документа, а с 4.0 — и транзакции на несколько документов: в демо перевод прошёл транзакцией. Проблемы с деньгами возникают от модели «прочитать, проверить в коде, записать» и от w:1, а не от отсутствия транзакций. Условное обновление одного документа и w:majority закрывают гонку и потерю.

  • Атомарен один документ: условие и изменение в одном updateOne отклонили превышающий возврат.
  • Вкладывают то, что меняется вместе и растёт ограниченно; документ до 16 МБ; схему задают валидатором.
  • ESR: (merchant, createdAt, amount) — 22 ключа без сортировки, (merchant, amount, createdAt) — 80 ключей и SORT в памяти.
  • w:1 подтверждает запись одного узла, которая откатится при failover; w:majority с таймаутом не отменяет записанное.
  • Транзакции есть с 4.0, но дороже; шардирование по shard key с балансировщиком.

На собеседовании

Когда вкладывать документы, а когда ссылаться?

Вкладывают данные, которые читаются и меняются вместе с родителем и растут ограниченно: позиции заказа, возвраты платежа. Тогда чтение — один документ, а изменение — атомарное обновление одного документа. Ссылаются на то, что живёт отдельно, нужно многим или растёт без предела: платежи магазина, пользователи.

  • Предел документа 16 МБ; растущий массив переписывает документ при каждом изменении.
  • Инвариант в одном документе проверяется условием в фильтре обновления без транзакции.
  • $lookup соединяет коллекции, но дороже соединения в реляционной базе.
Почему возвраты могут превысить сумму платежа? 
Document p = payments.find(eq("_id", id)).first();
int refunded = p.getInteger("refunded");
if (refunded + amount > p.getInteger("amount")) throw new RefundExceeded();
payments.updateOne(eq("_id", id), combine(inc("refunded", amount), push("refunds", refund)));

Проверка в коде и запись разделены: два параллельных возврата прочитают одно refunded, оба пройдут проверку и оба запишутся. Условие нужно перенести в фильтр обновления — and(eq("_id", id), lte("refunded", total - amount)) — и проверять matchedCount: 0 означает отказ. Атомарность одного документа закроет гонку без транзакции.

Что такое write concern и read concern?

Write concern — сколько узлов реплика-сета должно подтвердить запись: w:1 — только primary, w:majority — большинство. С w:1 подтверждённая запись может откатиться при смене primary. Read concern — какие данные можно читать: majority возвращает только подтверждённые большинством, local — всё, что есть на узле.

  • С 5.0 умолчание w:majority.
  • Таймаут w:majority не отменяет запись: документ остаётся на primary, повтор должен быть идемпотентным.
  • Причинная согласованность — causal consistency в сессии.

Как строить составные индексы в MongoDB?

По правилу ESR: сначала поля с условием равенства, потом поле сортировки, потом поля с диапазоном. Тогда индекс отдаёт документы в нужном порядке, и не нужна сортировка в памяти. Проверяют через explain: COLLSCAN, SORT, totalKeysExamined и totalDocsExamined против nReturned.

  • Сортировка в памяти ограничена 100 МБ.
  • Покрытый запрос читает только индекс, если проекция содержит лишь индексированные поля без _id.
