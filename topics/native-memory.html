JVM: Native Memory

Под убили за память, хотя heap был заполнен наполовину

Платёжный шлюз работает в Kubernetes с лимитом памяти 1 ГБ. Чтобы «использовать всю память», в запуске стоит -Xmx1g. Раз в несколько часов под перезапускается. В логах приложения ни одной ошибки, OutOfMemoryError нет, график heap показывает 500–600 МБ. А kubectl describe pod говорит:

Last State:     Terminated
  Reason:       OOMKilled          # процесс убило ядро Linux, а не JVM
  Exit Code:    137                # 128 + 9: пришёл SIGKILL

Лимит пода считает всю память процесса, а -Xmx ограничивает только heap. Всё остальное — Metaspace, стеки потоков, code cache, структуры сборщика мусора, direct-буферы сетевой библиотеки — живёт в native-памяти процесса, вне heap. Heap в 1 ГБ плюс несколько сотен мегабайт сверху не помещаются в лимит 1 ГБ. Когда процесс его переходит, ядро убивает его сигналом SIGKILL. У JVM нет шанса даже записать ошибку, и shutdown hooks не выполняются.

В этом уроке разберём, из чего складывается память процесса, как её измерить и как выбрать размеры, чтобы под не убивали.

Память процесса — это heap плюс всё, что JVM держит рядом

Смоделируем небольшой сервис: 100 МБ данных в heap, 64 МБ direct-буферов, как у сетевой библиотеки, и 200 потоков.

import java.nio.ByteBuffer;
import java.util.ArrayList;
import java.util.List;
import java.util.concurrent.CountDownLatch;

public class Footprint {
    public static void main(String[] args) throws Exception {
        List<ByteBuffer> buffers = new ArrayList<>();
        for (int i = 0; i < 64; i++) {
            buffers.add(ByteBuffer.allocateDirect(1024 * 1024));   // 64 МБ вне heap, как у Netty
        }
        List<byte[]> heapData = new ArrayList<>();
        for (int i = 0; i < 100; i++) {
            heapData.add(new byte[1024 * 1024]);                   // 100 МБ живых данных в heap
        }
        CountDownLatch stop = new CountDownLatch(1);
        for (int i = 0; i < 200; i++) {                            // 200 потоков, как пул веб-сервера
            Thread worker = new Thread(() -> {
                try { stop.await(); } catch (InterruptedException e) { }
            });
            worker.setDaemon(true);
            worker.start();
        }
        System.out.println("ready " + ProcessHandle.current().pid());
        Thread.sleep(600_000);                                      // живём, пока снимаем замеры
    }
}

Запустим с heap в 256 МБ. Флаг -XX:+AlwaysPreTouch заставляет JVM сразу занять весь heap, как это происходит у нагруженного сервиса. RSS — сколько физической памяти реально занимает процесс — посмотрим через ps. Реальный замер на JDK 21:

$ java -Xms256m -Xmx256m -XX:+AlwaysPreTouch -cp out Footprint &
ready 93917
$ ps -o rss= -p 93917
419728            # в КБ: 410 МБ при heap 256 МБ

410 МБ при -Xmx256m — на 60% больше heap. Куда ушли 154 МБ, покажет Native Memory Tracking из следующего шага. Вот итог:

При лимите пода 384 МБ этот процесс убили бы, хотя heap занят меньше чем наполовину. И это маленький пример. В реальном сервисе к нему добавятся несколько тысяч классов Spring и Hibernate в Metaspace, JIT-код от многих методов, буферы Netty и драйверов.

Native Memory Tracking показывает, кто сколько взял

JVM умеет сама учитывать свою native-память. Включается это флагом при старте, а смотрят через jcmd у живого процесса:

$ java -XX:NativeMemoryTracking=summary -Xms256m -Xmx256m -XX:+AlwaysPreTouch -cp out Footprint &
$ jcmd 93917 VM.native_memory summary scale=MB

Total: reserved=2216MB, committed=883MB
-                 Java Heap (reserved=264MB, committed=256MB)     # heap: -Xmx
-                     Class (reserved=1024MB, committed=0MB)      # compressed class space: резерв 1 ГБ
                            (classes #721)
-                    Thread (reserved=455MB, committed=455MB)     # стеки 226 потоков по 2 МБ
                            (threads #226)
-                      Code (reserved=242MB, committed=7MB)       # code cache
-                        GC (reserved=66MB, committed=66MB)       # remembered sets, card table, bitmaps G1
-                     Other (reserved=64MB, committed=64MB)       # direct ByteBuffer
-        Shared class space (reserved=32MB, committed=28MB)       # CDS: классы JDK из общего архива
-                 Metaspace (reserved=64MB, committed=0MB)

Вывод обрезан до главных категорий. Три слова, без которых его не прочитать:

  • reserved — диапазон адресов, который JVM зарезервировала у ОС на будущее. Это не память, а обещание. Поэтому 2216 МБ reserved никого не пугают.
  • committed — память, которую JVM попросила у ОС реально использовать. ОС выдаёт физические страницы, только когда в них впервые пишут.
  • RSS — сколько физических страниц процесс уже тронул. Его видит ядро и по нему убивает контейнер.

Отсюда расхождение: committed 883 МБ, а RSS 410. Стеки на 455 МБ committed, но поток трогает лишь несколько килобайт своего стека. А heap благодаря AlwaysPreTouch тронут весь.

Для поиска утечки вне heap пригодится режим сравнения. Делаешь снимок-базу, ждёшь, пока память вырастет, и смотришь, какая категория выросла:

jcmd <pid> VM.native_memory baseline        # запомнить текущее состояние
# ... через час, когда RSS вырос ...
jcmd <pid> VM.native_memory summary.diff    # рост по каждой категории относительно базы

NMT стоит 5–10% производительности и немного памяти, поэтому его включают для расследования, а не постоянно. И NMT видит только память самой JVM. Если растёт память, которую через malloc берёт native-библиотека — JDBC-драйвер на C, компрессор, сертификаты через JNI, — NMT её не покажет. Тогда растёт RSS, а итог NMT стоит на месте.

Direct-буфер — айсберг: маленький объект в heap и мегабайт вне его

ByteBuffer.allocateDirect выделяет память вне heap. Зачем? Сетевые и файловые операции ОС работают с native-памятью. Обычный массив в heap может переехать при сборке мусора, поэтому перед записью в сокет его пришлось бы копировать. Direct-буфер не двигается, и ОС читает из него напрямую. Поэтому на direct-буферах построены Netty, NIO, клиенты Kafka и gRPC.

Лимит direct-памяти задаёт -XX:MaxDirectMemorySize. Если он не задан, лимит равен -Xmx — то есть сверху к heap можно добавить ещё столько же:

import java.nio.ByteBuffer;
import java.util.ArrayList;
import java.util.List;

public class DirectLimit {
    public static void main(String[] args) {
        List<ByteBuffer> buffers = new ArrayList<>();       // держим буферы, чтобы их не освободили
        try {
            while (true) {
                buffers.add(ByteBuffer.allocateDirect(1024 * 1024));
            }
        } catch (OutOfMemoryError e) {
            System.out.println(buffers.size() + " буферов, затем: " + e.getMessage());
        }
    }
}
$ java -Xmx64m -cp out DirectLimit            # MaxDirectMemorySize не задан
64 буферов, затем: Cannot reserve 1048576 bytes of direct buffer memory (allocated: 67108864, limit: 67108864)

Самое неочевидное — когда эта память освобождается. Объект DirectByteBuffer в heap весит несколько десятков байт, а за ним стоит мегабайт native-памяти. Освободить её можно, только когда сборщик мусора найдёт объект недостижимым. Пролистай, что из этого выходит.

Проверим на программе, которая берёт и сразу бросает буферы, как обработчик запросов:

import java.nio.ByteBuffer;

public class Churn {
    public static void main(String[] args) {
        long written = 0;
        for (int i = 0; i < 1_000; i++) {
            ByteBuffer buffer = ByteBuffer.allocateDirect(1024 * 1024);   // 1 МБ вне heap
            buffer.putLong(0, i);
            written += buffer.getLong(0);                                  // после этой строки буфер не нужен
        }
        System.out.println("обработано 1000 буферов по 1 МБ, сумма " + written);
    }
}
$ java -XX:MaxDirectMemorySize=16m -Xlog:gc -cp out Churn
[0.029s][info][gc] GC(0) Pause Full (System.gc()) 4M->2M(56M) 3.284ms     # сборку вызвал сам JDK
[0.031s][info][gc] GC(1) Pause Full (System.gc()) 3M->2M(32M) 2.063ms
...                                                                          # всего 62 полные паузы
обработано 1000 буферов по 1 МБ, сумма 499500

$ java -XX:MaxDirectMemorySize=16m -XX:+DisableExplicitGC -cp out Churn
Exception in thread "main" java.lang.OutOfMemoryError: Cannot reserve 1048576 bytes of direct
buffer memory (allocated: 16777216, limit: 16777216)                         # освободить нечем

На тысячу буферов — 62 полных паузы, которые никто не заказывал. А с флагом -XX:+DisableExplicitGC, который иногда ставят, чтобы «запретить всем звать System.gc()», программа падает: JDK больше не может освободить буферы, хотя почти все они мусор.

-XX:+DisableExplicitGC безопасен: приличный код не вызывает System.gc().

Его вызывает сам JDK, когда кончается direct-память. С этим флагом приложение на NIO или Netty может получить Direct buffer memory, хотя вся память — мусор. Правильное лечение — переиспользовать буферы через пул, как делает Netty, а не создавать их на каждый запрос.

Каждый поток — это стек в native-памяти и ресурс ОС

Платформенный поток Java — это поток ОС со своим стеком вне heap. Размер стека задаёт -Xss: 1 МБ на Linux x64, 2 МБ на macOS arm64, где запускались примеры. В замере NMT выше 226 потоков зарезервировали 455 МБ. Но стек занимает физическую память, только когда поток его использует, поэтому обычный поток пула с неглубоким стеком стоит в RSS десятки килобайт, а не мегабайты.

Тогда откуда берётся OutOfMemoryError: unable to create native thread? Эта ошибка не про heap. JVM попросила ОС создать поток, и ОС отказала. Причины бывают такие:

  • лимит числа процессов и потоков пользователя: ulimit -u;
  • лимит PID в контейнере: pids.max у cgroup, в Kubernetes — podPidsLimit;
  • кончилась память или адресное пространство под новые стеки.

Почти всегда за этим стоит утечка потоков: Executors.newCachedThreadPool без ограничения под всплеском нагрузки, new Thread на каждый запрос, пул, который создают и не закрывают. Смотри число потоков в jcmd <pid> Thread.print или в метрике jvm_threads_live_threads, а не размер heap.

Виртуальные потоки из Java 21 устроены иначе. Их стеки хранятся в heap как обычные объекты и растут по мере надобности, а исполняются они на небольшом пуле платформенных потоков. Миллион виртуальных потоков не создаёт миллион стеков ОС. Подробно — в теме Virtual Threads.

В контейнере heap — это доля лимита, а не весь лимит

Теперь можно ответить на вопрос из первого шага: сколько heap давать поду. Лимит пода должен вместить heap и всё, что вне его. Обычно так:

ЧастьСколько закладыватьЧем ограничить
heap60–75% лимита пода-XX:MaxRAMPercentage=75 или -Xmx
Metaspace100–300 МБ для Spring-сервиса-XX:MaxMetaspaceSize
direct-буферыпо профилю сетевой библиотеки-XX:MaxDirectMemorySize
стеки потоковчисло потоков × реально используемая глубинаразмер пулов, -Xss
code cache, GC, прочеедесятки–сотни МБобычно не трогают

Проценты удобнее жёсткого -Xmx: поменяли лимит пода — heap подстроился сам. Главное правило — никогда не ставить heap равным лимиту. Именно это произошло в первом шаге.

Что смотреть в мониторинге. Метрики JVM (jvm_memory_used_bytes в Micrometer) показывают heap и пулы, которые знает JVM. Контейнер убивают по container_memory_working_set_bytes — это ближе к RSS. Если рабочий набор контейнера растёт, а heap и non-heap в метриках JVM стоят, память уходит мимо JVM: direct-буферы, native-библиотеки, фрагментация malloc.

На Linux с glibc память, которую потоки берут через malloc, раскладывается по нескольким «аренам», по умолчанию до 8 на ядро. У процесса с сотнями потоков это даёт заметную фрагментацию, и RSS растёт без утечки. Часто помогает переменная окружения MALLOC_ARENA_MAX=2 или замена аллокатора на jemalloc. Сначала подтверди диагноз через NMT: если его итог стоит, а RSS растёт, дело вне JVM.

Где кончается эта тема? Если NMT показывает рост категории Java Heap или Class, это не native-проблема, а утечка объектов или классов: смотри Memory Areas и Diagnostics. А если растёт RSS, но NMT стоит на месте, нужны инструменты уровня ОС: pmap, профилирование аллокатора jemalloc, perf.

  • -Xmx ограничивает только heap. Процесс занимает больше: GC-структуры, классы, code cache, стеки, direct-буферы, память native-библиотек.
  • Контейнер убивают по RSS, сигналом SIGKILL, без Java-ошибки и без shutdown hooks. Heap ставят на 60–75% лимита пода, а не на весь лимит.
  • Native Memory Tracking (-XX:NativeMemoryTracking=summary и jcmd VM.native_memory) показывает, какая часть JVM сколько взяла. Reserved — обещание, committed — выдано, RSS — тронуто.
  • Direct-буфер освобождается только после того, как GC соберёт его объект. JDK для этого сам вызывает System.gc(), поэтому DisableExplicitGC опасен, а буферы стоит переиспользовать.
  • unable to create native thread — отказ ОС создать поток, обычно из-за утечки потоков, а не из-за heap.

На собеседовании

Почему Java-процесс занимает больше памяти, чем -Xmx?

-Xmx ограничивает только heap. Кроме него JVM держит в native-памяти Metaspace с классами, code cache с кодом JIT, стеки потоков, структуры сборщика мусора, direct-буферы NIO и Netty, а ещё память native-библиотек. В замере урока процесс с -Xmx256m занимал 410 МБ RSS.

Для контейнера это главное правило: heap ставят на 60–75% лимита пода. Если поставить heap равным лимиту, процесс переходит лимит за счёт памяти вне heap, и ядро убивает его как OOMKilled, без всякой Java-ошибки.

  • NMT различает reserved и committed, а ядро убивает по RSS — тронутым страницам. Стеки потоков обычно committed, но почти не тронуты.
  • Если растёт RSS, а итог NMT стоит, память берёт кто-то мимо JVM: native-библиотеки или фрагментация malloc.
В deployment: limits.memory 2Gi и JAVA_OPTS="-Xms2g -Xmx2g". Что не так?

Heap равен лимиту пода. Как только Metaspace, стеки, code cache и буферы займут хоть что-то сверх heap, процесс перейдёт лимит и получит OOMKilled. Нужно -XX:MaxRAMPercentage=75 или -Xmx1500m, либо поднять лимит.

Под перезапускается с Exit Code 137. Какие логи смотреть?

Логи приложения почти ничего не скажут: SIGKILL не даёт JVM записать ошибку. Смотри kubectl describe pod — Reason OOMKilled, метрику рабочего набора контейнера перед рестартом и метрики heap и non-heap JVM за то же время.

Что такое direct memory и когда она освобождается?

Это память вне heap, которую выделяет ByteBuffer.allocateDirect. Её используют для I/O: ОС читает её напрямую, без копирования из heap, поэтому на ней работают NIO, Netty, клиенты Kafka и gRPC. Лимит задаёт MaxDirectMemorySize, по умолчанию он равен -Xmx.

Освобождается она, только когда сборщик мусора находит недостижимым маленький объект буфера в heap. Если heap почти пуст, GC не запускается, и direct-память копится. Тогда JDK сам вызывает System.gc() — полную паузу. Поэтому буферы переиспользуют через пул, а не создают на каждый запрос.

  • С -XX:+DisableExplicitGC JDK не может вызвать сборку, и приложение падает с Direct buffer memory, хотя буферы — мусор.
  • В NMT direct-буферы видны в категории Other.
Сколько direct-памяти может занять процесс с -Xmx4g без других флагов?

До 4 ГБ: без MaxDirectMemorySize лимит direct-памяти равен максимальному heap. Вместе с heap это уже 8 ГБ, не считая остального.

Как выбрать размер heap для сервиса в контейнере?

Heap — это доля лимита пода, обычно 60–75%, остальное уходит на память вне heap. Я задаю -XX:MaxRAMPercentage=75 вместо жёсткого -Xmx: JVM видит лимит контейнера и считает heap от него. Для Spring-сервиса ещё ограничиваю MaxMetaspaceSize, чтобы утечка классов давала понятную ошибку, а не OOMKilled.

Потом проверяю на нагрузке: рабочий набор контейнера должен держаться с запасом ниже лимита, а heap после сборок — ниже своего максимума.

Почему не отдать heap всю память контейнера, раз больше в поде ничего нет?

Потому что сама JVM — это не только heap. Metaspace, code cache, стеки, GC-структуры и буферы займут ещё сотни мегабайт, и процесс перейдёт лимит.

Как найти, куда уходит память вне heap?

Включить Native Memory Tracking: -XX:NativeMemoryTracking=summary при старте. Потом jcmd <pid> VM.native_memory baseline, подождать роста и снять summary.diff — видно, какая категория растёт: Thread, Class, Code, GC, Other с direct-буферами.

Если итог NMT не растёт, а RSS растёт, память берёт не JVM: native-библиотеки или аллокатор. Тогда нужны pmap, профилирование jemalloc, MALLOC_ARENA_MAX.

Можно ли держать NMT включённым в проде постоянно?

Обычно нет: режим summary стоит несколько процентов производительности, detail — больше. Его включают на время расследования, например на одном поде из нескольких.
