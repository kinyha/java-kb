Nested Classes

Класс внутри класса бывает четырёх видов. Статический вложенный — обычный класс в пространстве имён внешнего, без связи с его экземпляром. Внутренний (inner, без static) — каждый его объект хранит скрытую ссылку this$0 на внешний объект. Локальный объявлен в методе, анонимный — там же и без имени. Оба захватывают копии фактически final локальных переменных в поля val$x. Скрытая ссылка — главная ловушка. Слушатель на глобальной шине держит внешний объект вместе с его данными, и в демо 40-мегабайтный отчёт не собран сборщиком. Тот же слушатель статическим вложенным классом отчёт не держит. С JDK 18 javac не создаёт this$0, если внутренний класс внешний объект не использует. Лямбда — не анонимный класс: отдельного класс-файла нет, this в ней — внешний объект, а захват this происходит только при обращении к полям. Правило по умолчанию: вложенный класс делают static, пока ему действительно не нужен внешний экземпляр.

Четыре вида и что компилятор из них делает

public class Outer {
    private long total;
    class Inner { void add(long a) { total += a; } }                 // внутренний: держит ссылку на Outer
    class Idle { long twice(long a) { return a * 2; } }               // внутренний, но Outer не использует
    static class Nested { long twice(long a) { return a * 2; } }      // статический вложенный: ссылки нет
    Runnable anonymous() { return new Runnable() { public void run() { total++; } }; }
    Runnable lambda() { return () -> total++; }
}

Для JVM вложенных классов не существует: скрипт javap.sh показывает обычные класс-файлы Outer$Inner, Outer$Nested и Outer$1 для анонимного. Внутренний класс компилятор превратил в класс с полем final Outer this$0 и конструктором, который принимает внешний объект: outer.new Inner() передаёт его неявно. Обращение к total — это getfield/putfield поля Outer.total через this$0. У Nested конструктор без параметров: связи с экземпляром нет, создаётся как new Outer.Nested().

Idle — внутренний класс, но Outer не трогает. Конструктор по-прежнему принимает Outer, а поля this$0 нет: с JDK 18 javac его не создаёт, если внешний экземпляр не используется (кроме сериализуемых классов). Конструктор параметр просто не сохраняет: в его байткоде только вызов Object.<init>. До JDK 18 ссылка хранилась всегда.

Утечка: слушатель держит внешний объект

Задание на построение отчёта держит 40 МБ строк и подписывается на глобальную шину событий, которая живёт всё время работы приложения. Отчёт построен, ссылку на задание отпустили. Соберёт ли его сборщик? Демо LeakDemo.java проверяет через WeakReference, по-разному реализуя слушателя:

static class ReportJob {
    final long[] rows = new long[5_000_000];                                 // ~40 МБ данных отчёта
    void subscribeInner()     { BUS.add(new Listener()); }                 // внутренний, читает поле отчёта
    void subscribeIdleInner() { BUS.add(new IdleListener()); }             // внутренний, внешний объект не трогает
    void subscribeNested()    { BUS.add(new StaticListener()); }           // статический вложенный
    void subscribeLambdaThis(){ BUS.add(e -> rows[0]++); }                 // лямбда, читающая поле
    class Listener implements Consumer<String> { public void accept(String e) { rows[0]++; } }
    ...
}

Утекает не слушатель, а всё, что он держит: внутренний объект невелик, но через this$0 тянет внешний целиком. Так же внутренний класс, отданный в кеш, пул потоков, планировщик или статическую коллекцию, держит свой внешний объект — классический источник утечек в Android (Activity, удерживаемая Handler-ом или AsyncTask) и в серверном коде (слушатели, не снятые с регистрации). Анонимный класс и лямбда, обращающиеся к полю, ведут себя так же: в демо оба удержали отчёт. Найти такую утечку помогает дамп кучи с путём до корня из JVM Diagnostics.

Исправления: сделать класс static и передать ему только нужные данные, а не весь внешний объект; снимать подписку, когда объект больше не нужен, — try/finally или AutoCloseable-подписка; если слушателю допустимо исчезнуть вместе с владельцем — слабые ссылки из References. Ещё одна причина держать класс статическим — сериализация: сериализация внутреннего класса тянет внешний объект, а имена синтетических полей не стабильны между компиляторами, поэтому Java прямо не рекомендует сериализовать внутренние классы.

Захват локальной переменной — копия значения в поле: у анонимного класса появилось поле long val$rate, заполненное в конструкторе. Поэтому переменная должна быть фактически final: если бы метод потом изменил rate, копия в объекте и переменная в стеке разошлись бы, а объект может жить дольше вызова метода. Обходной путь с массивом из одного элемента long[] counter = {0} компилируется, но делает изменяемое состояние общим — в многопоточном коде это гонка; для счётчика есть AtomicLong.

this в анонимном классе — сам анонимный объект (LeakDemo$2), а в лямбде — внешний объект: лямбда не вводит новой области видимости, это просто тело функции в контексте метода. Отличия глубже синтаксиса.

Тело лямбды компилятор кладёт в приватный метод lambda$lambda$0 самого Outer, а на месте выражения — invokedynamic: класс, реализующий Runnable, создаёт LambdaMetafactory при первом выполнении, в памяти, без класс-файла Outer$2. Сигнатура (LOuter;)Runnable показывает, что эта лямбда захватывает this — она обращается к total. Лямбда без захвата создаётся один раз и переиспользуется. Подробнее — в Lambdas. Анонимный класс по-прежнему нужен, когда у реализации несколько методов, собственное состояние или нужен абстрактный класс, а не функциональный интерфейс.

Доступ к private и nestmates

Вложенный класс видит приватные члены внешнего, а внешний — приватные члены вложенного: Inner пишет в private long total. Для JVM до Java 11 это были разные классы без доступа к приватному, и компилятор генерировал синтетические методы-мосты access$000 с пакетным доступом — лишний вызов в стеке и дыра, через которую любой класс пакета мог добраться до приватного поля. С Java 11 (JEP 181, nestmates) в класс-файлах есть атрибуты NestHost и NestMembers — в выводе javap у Outer$Inner стоит NestHost: class Outer, а у Outer перечислены все вложенные классы. JVM пускает к приватным членам внутри гнезда напрямую: getfield Outer.total без мостов. Рефлексия тоже учитывает гнездо — Class.getNestHost() и isNestmateOf().

Самый частый в коде вид — статический вложенный класс. Builder живёт внутри своего класса (Payment.builder() возвращает Payment.Builder) и имеет доступ к его приватному конструктору, о билдерах — в Creational Patterns. Узлы структур данных — HashMap.Node, LinkedList.Node — статические: узлов миллионы, и лишняя ссылка на внешний объект в каждом стоила бы памяти. Внутренние классы JDK использует там, где связь нужна: итератор ArrayList.Itr читает массив и modCount своего списка, как в List. Records, enums и интерфейсы, объявленные внутри класса, неявно статические.

Внутренний класс всегда держит ссылку на внешний объект.

С JDK 18 javac не создаёт поле this$0, если внутренний класс внешний экземпляр не использует, — в демо такой слушатель не удержал отчёт. Но стоит обратиться к любому полю или методу внешнего — ссылка появится. Надёжно — static.

  • Static nested — без связи с экземпляром; inner — скрытое поле this$0 и конструктор с внешним объектом.
  • Локальные и анонимные классы копируют фактически final переменные в поля val$x.
  • Слушатель-внутренний класс на долгоживущей шине держит внешний объект: 40 МБ отчёта не собраны.
  • С JDK 18 неиспользуемый this$0 не создаётся; лямбда захватывает this только при обращении к членам.
  • Лямбда — приватный метод + invokedynamic, без класс-файла; this в ней — внешний объект.
  • Nestmates (Java 11): доступ к private внутри гнезда без синтетических access$-методов.
  • По умолчанию вложенный класс static.

На собеседовании

Чем статический вложенный класс отличается от внутреннего?

Внутренний класс связан с экземпляром внешнего: каждый его объект хранит скрытую ссылку на внешний объект, создаётся через outer.new Inner() и может обращаться к его полям и методам. Статический вложенный — обычный класс в пространстве имён внешнего, без ссылки на экземпляр; создаётся через new Outer.Nested(). Оба видят приватные члены внешнего класса.

  • В байткоде — поле this$0 и конструктор с параметром Outer; с JDK 18 поле не создаётся, если не используется.
  • Скрытая ссылка — источник утечек и проблем сериализации.
  • Nestmates (Java 11) убрали синтетические access$-методы.
Почему память сервиса растёт после каждого отчёта? 
public class ReportService {
    private final byte[] buffer = new byte[50 * 1024 * 1024];
    public void build(Scheduler scheduler) {
        scheduler.every(Duration.ofMinutes(1), new Runnable() {
            public void run() { log.info("still building, buffer {}", buffer.length); }
        });
        // ... строим отчёт, задача в планировщике остаётся
    }
}

Анонимный Runnable обращается к buffer и поэтому держит ссылку на ReportService. Задача остаётся в планировщике навсегда, и каждый экземпляр сервиса с 50-мегабайтным буфером живёт вместе с ней. Нужно отменять задачу по окончании отчёта (сохранить ScheduledFuture и вызвать cancel) и не захватывать внешний объект — передать в задачу только нужное значение.

Чем лямбда отличается от анонимного класса?

this в лямбде — внешний объект, в анонимном классе — сам анонимный объект. Лямбда реализует только функциональный интерфейс, анонимный класс — любой интерфейс или абстрактный класс, может иметь поля и несколько методов. Обе захватывают только фактически final локальные переменные.

  • Лямбда компилируется в приватный метод и invokedynamic; класс создаёт LambdaMetafactory в памяти.
  • Лямбда без захвата — один переиспользуемый объект.
  • Лямбда захватывает this, только если обращается к членам внешнего объекта.

Почему локальные переменные в анонимном классе и лямбде должны быть final?

Захват — это копия значения в поле объекта, а объект может жить дольше вызова метода. Если бы переменная менялась после захвата, копия и оригинал разошлись бы. Поэтому Java требует фактически final переменные: значение одно и то же.

  • У анонимного класса копия видна как поле val$x.
  • Обход через массив из одного элемента компилируется, но в многопоточности даёт гонку.
  • JLS §8.1.3 Inner Classes and Enclosing Instances, §15.27.2 Lambda Body.
  • JEP 181: Nest-Based Access Control.
  • JDK-8271623: Omit enclosing instance fields from inner classes that don't use it.
  • Joshua Bloch, «Effective Java», 3-е издание, item 24 — favor static member classes over nonstatic.
