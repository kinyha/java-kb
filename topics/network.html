Networking: How a Request Travels

Запрос к API проходит несколько этапов, и у каждого своя цена. Сначала DNS превращает имя в IP-адрес, затем TCP открывает соединение, TLS договаривается о шифровании, и только потом уходит HTTP-запрос. Каждый уровень стека заворачивает данные верхнего в свой заголовок и знает свой адрес: MAC — до соседнего узла, IP — до машины, порт — до процесса, Host — до сайта. По дороге пакет проходит маршрутизаторы, NAT подменяет адреса, а прокси и балансировщики завершают соединения и открывают новые. Почти любую сетевую проблему диагностируют вопросом «на каком этапе ушло время и с кем на самом деле установлено соединение».

Клиент нажал «Оплатить», и полсекунды ушло до первого байта ответа

Мобильное приложение вызывает платёжный API, а пользователь видит спиннер. Сервер по своим логам отвечает за 30 мс. Где остальное время? Ответ даёт разбор запроса по этапам. curl умеет печатать время каждого этапа от начала запроса:

curl -s -o /dev/null -w 'dns=%{time_namelookup} tcp=%{time_connect} tls=%{time_appconnect} \
ttfb=%{time_starttransfer} total=%{time_total} http=%{http_version}\n' https://example.com/
# Все значения — секунды от начала запроса, нарастающим итогом.
dns=0.096031 tcp=0.097820 tls=0.393674 ttfb=0.529989 total=0.530287 http=2

Числа сняты на машине автора и в другой сети будут другими. Главное — структура. Полсекунды складываются из нескольких сетевых обменов, которые происходят до того, как сервер вообще увидел запрос. Чтобы понимать, какой из них можно сократить, нужно знать, что происходит на каждом уровне. DNS, TCP, TLS и HTTP подробно разобраны в соседних темах DNS, TCP & UDP, TLS & HTTPS и HTTP. Здесь — общая карта пути.

Каждый уровень заворачивает данные в свой заголовок и знает свой адрес

Сетевой стек делится на уровни, чтобы каждый решал одну задачу и не знал о деталях соседей. Модель OSI насчитывает семь уровней, на практике пользуются четырьмя уровнями TCP/IP. Когда приложение отправляет HTTP-запрос, каждый уровень ниже добавляет к данным свой заголовок. Это называют инкапсуляцией.

Демо RequestPathDemo.java отправляет HTTP-запрос через обычный сокет, без HTTP-клиента, и показывает, что такое «HTTP» на самом деле — текст поверх TCP:

String request = "GET /payments/17 HTTP/1.1\r\n"
        + "Host: " + host + "\r\n"     // Обязательный в HTTP/1.1: какой сайт нужен.
        + "Connection: close\r\n"
        + "\r\n";                       // Пустая строка — конец заголовков.
socket.getOutputStream().write(request.getBytes(StandardCharsets.US_ASCII));
cd examples/net
java RequestPathDemo.java # JDK 21; работает только на loopback, сеть не нужна.
connection: 127.0.0.1:60956 -> 127.0.0.1:60955
request bytes: 72, first line: GET /payments/17 HTTP/1.1
response: HTTP/1.1 200 OK | payments-backend served /payments/17 for client port 60956

Каждое TCP-соединение определяется четвёркой: IP и порт клиента, IP и порт сервера. Порт клиента выдаёт ядро из диапазона эфемерных портов, на macOS это 49152–65535 (sysctl net.inet.ip.portrange), на Linux по умолчанию 32768–60999. Порты в выводе меняются от запуска к запуску. Диапазон кончается: сервис, который открывает новое соединение на каждый запрос к одному адресу, упирается в эфемерные порты и TIME_WAIT. Это разобрано в TCP & UDP.

IP-пакет идёт от маршрутизатора к маршрутизатору, и каждый решает только следующий шаг

Ни один маршрутизатор не знает полного пути до сервера. У каждого есть таблица маршрутов: для какого диапазона адресов на какой интерфейс и какому соседу отдать пакет. Ноутбук отдаёт почти всё шлюзу по умолчанию — домашнему роутеру. Тот — провайдеру, и так далее, пока пакет не попадёт в сеть сервера. Между крупными сетями маршруты распространяет протокол BGP.

Каждый маршрутизатор уменьшает в заголовке IP поле TTL на единицу. Когда оно становится нулём, пакет выбрасывается, а отправителю уходит ICMP-сообщение «время жизни истекло». Это защищает сеть от петель. На этом же построен traceroute: он шлёт пакеты с TTL 1, 2, 3… и по ответам узнаёт каждый промежуточный узел.

route -n get 172.66.147.243 | grep interface # Через какой интерфейс уйдёт пакет к example.com.
traceroute -m 8 -q 1 -w 1 example.com
  interface: utun6
traceroute to example.com (172.66.147.243), 8 hops max, 40 byte packets
 1  *
 2  *
 3  *

На машине автора маршрут к example.com идёт не через Wi-Fi (en0), а через туннель utun6 — интерфейс VPN-клиента. Пакеты заворачиваются в ещё один уровень инкапсуляции и уходят на VPN-сервер, а traceroute не видит ни одного узла: туннель не отвечает на истёкший TTL. Звёздочки в traceroute не значат, что сеть сломана: многие узлы просто не отвечают на ICMP. Для живой диагностики полезнее mtr, который показывает потери и задержки на каждом узле непрерывно.

NAT подменяет адрес и порт, поэтому сервер видит не тебя

Ноутбук в домашней сети имеет частный адрес вида 192.168.1.20. В интернете такие адреса не маршрутизируются: их миллионы одинаковых. Роутер выполняет NAT — подменяет адрес и порт отправителя на свой публичный адрес и свободный порт, а соответствие запоминает в таблице. Адреса на схеме взяты из диапазонов для документации.

Для бэкенда у NAT несколько следствий. Сервер видит адрес NAT, а не клиента: сотни пользователей мобильного оператора приходят с одного IP, и лимит запросов «по IP» блокирует их всех вместе. Подключиться снаружи к машине за NAT нельзя без проброса порта — поэтому веб-хуки банка приходят на публичный адрес балансировщика, а не на pod. Таблица NAT конечна: в облаке NAT-шлюз ограничивает число одновременных соединений к одному адресу назначения, и сервис, открывающий соединение на каждый запрос к банку, упирается в этот лимит раньше, чем в свои ресурсы.

Прокси и балансировщик завершают соединение и открывают новое

Между клиентом и приложением почти всегда стоит что-то ещё: облачный балансировщик, ingress-контроллер Kubernetes, nginx, CDN. Балансировщик L4 видит IP и порты и распределяет TCP-соединения целиком, не заглядывая внутрь. Балансировщик L7 — обратный прокси — завершает TCP и TLS, читает HTTP и выбирает backend по заголовкам и пути. Демо делает именно это: на одном порту два «сайта», и выбор зависит только от заголовка Host.

// «Обратный прокси»: тот же IP и порт, backend выбирается по Host.
String backend = host.startsWith("admin.") ? "admin-backend" : "payments-backend";
response: HTTP/1.1 200 OK | payments-backend served /payments/17 for client port 60956
connection: 127.0.0.1:60957 -> 127.0.0.1:60955
request bytes: 74, first line: GET /payments/17 HTTP/1.1
response: HTTP/1.1 200 OK | admin-backend served /payments/17 for client port 60957

Запросы отличаются одной строкой Host, а попали в разные backend. Так один IP балансировщика обслуживает десятки сервисов. Цена L7: прокси держит два соединения на каждый запрос — с клиентом и с backend, — а приложение видит прокси, а не клиента. Адрес клиента и исходный протокол прокси передаёт заголовками X-Forwarded-For и X-Forwarded-Proto или стандартным Forwarded. Доверять им можно только от своего прокси: клиент может прислать любой X-Forwarded-For сам. В Spring Boot это включает server.forward-headers-strategy.

Теперь понятна аномалия из первого шага. TCP установился за 1.8 мс, а TLS занял 296 мс. До сервера в другом городе TCP-рукопожатие не может занять две миллисекунды: свет не успеет. Значит, TCP завершился на ближнем узле — здесь это VPN-клиент на самой машине, — а TLS-рукопожатие уже пошло через туннель до настоящего сервера. Время connect меньше нескольких миллисекунд почти всегда означает соединение с ближним прокси, sidecar или балансировщиком, а не с приложением.

Если в логах приложения IP клиента, значит, это адрес пользователя.

За балансировщиком приложение видит адрес балансировщика, за NAT оператора — адрес NAT. Настоящий адрес приходит в X-Forwarded-For, и только если прокси свой и доверенный. Правила лимитов и блокировок по IP строят с учётом всей цепочки.

Медленный запрос разбирают по этапам, и каждый этап лечится по-своему

ЭтапЦенаКак сократить
DNSДесятки миллисекунд при промахе кешаКеш резолвера; в JVM — networkaddress.cache.ttl; не резолвить на каждый запрос
TCPОдин круг до сервера (RTT)Переиспользовать соединения: keep-alive, пул в HTTP-клиенте
TLSЕщё один-два RTT и вычисленияTLS 1.3, возобновление сессий, то же переиспользование соединений

Второй запрос в первом шаге показал разницу: DNS взялся из кеша за 3.4 мс, но TLS снова занял 309 мс, потому что curl открыл новое соединение. HTTP-клиент с пулом соединений платит за TCP и TLS один раз, а дальше отправляет запросы по готовому соединению. Поэтому пул и таймауты HTTP-клиента — первое, что настраивают для вызовов банка, как разобрано в HTTP Clients. HTTP/2 и HTTP/3 идут дальше и разными способами сокращают задержки на одном соединении — это тема HTTP/2 & HTTP/3.

Набор инструментов для расследования: curl -w для этапов одного запроса, dig для DNS, ss или netstat для состояния соединений на машине, mtr для маршрута, openssl s_client для TLS. А в приложении — метрики HTTP-клиента: время получения соединения из пула отдельно от времени запроса.

  • Запрос проходит DNS, TCP, TLS и HTTP; до первого байта сервера уходит несколько сетевых кругов.
  • Каждый уровень добавляет свой заголовок и адресует своё: MAC — соседа, IP — машину, порт — процесс, Host — сайт.
  • Маршрутизаторы решают только следующий шаг; TTL защищает от петель, на нём построен traceroute.
  • NAT подменяет адрес и порт: сервер видит адрес NAT, а снаружи к машине за NAT не подключиться.
  • L7-прокси завершает соединение и выбирает backend по HTTP; адрес клиента приходит в X-Forwarded-For.

На собеседовании

Что происходит, когда вводишь адрес сайта в браузере?

Браузер разбирает URL и узнаёт IP через DNS: сначала свои кеши и кеш ОС, потом резолвер, который при необходимости обходит корневые, доменные и авторитативные серверы. Затем открывает TCP-соединение — трёхстороннее рукопожатие, — для HTTPS проводит TLS-рукопожатие и проверяет сертификат. После этого отправляет HTTP-запрос, получает ответ, разбирает HTML и делает новые запросы за ресурсами, обычно по тому же соединению.

По дороге пакеты проходят домашний роутер с NAT, маршрутизаторы провайдеров и, как правило, балансировщик или CDN перед приложением.

  • До первого байта ответа уходит несколько RTT: DNS, TCP, один-два на TLS; TLS 1.3 и HTTP/3 сокращают их.
  • Балансировщик L7 завершает TCP и TLS и открывает новое соединение к backend.
  • Переиспользование соединений и кеши убирают большую часть этих затрат для повторных запросов.

Зачем нужны уровни OSI и TCP/IP и что на каком уровне?

Уровни разделяют задачи: каждый решает свою и не знает деталей соседей. В TCP/IP их четыре: канальный (Ethernet, Wi-Fi, MAC-адреса), сетевой (IP, маршрутизация), транспортный (TCP и UDP, порты) и прикладной (HTTP, DNS, TLS). Отправляя данные, каждый уровень добавляет свой заголовок, а получатель снимает их в обратном порядке.

На практике уровни важны для понимания оборудования: маршрутизатор работает до IP, балансировщик L4 — до портов, L7 — с HTTP.

  • MTU Ethernet 1500 байт; после заголовков IP и TCP на данные остаётся 1460 — MSS. VPN и туннели уменьшают MTU.
  • TLS формально сидит между транспортом и приложением; в модели OSI его относят к уровням 5–6.

Как NAT и прокси влияют на бэкенд?

NAT подменяет частный адрес и порт клиента на публичный, поэтому сервер видит адрес NAT. Много пользователей оператора приходят с одного IP, а снаружи к машине за NAT не подключиться без проброса порта. Обратный прокси или балансировщик L7 завершает соединение клиента и открывает своё к приложению, так что приложение видит адрес прокси.

Настоящий адрес клиента приходит в X-Forwarded-For или Forwarded; в Spring Boot его учитывают через server.forward-headers-strategy и доверяют только своему прокси.

  • Лимиты и блокировки по IP за NAT оператора задевают сотни пользователей сразу.
  • У облачного NAT-шлюза ограничено число одновременных соединений к одному адресу; пул соединений к банку от этого спасает.
  • Время connect в единицы миллисекунд — признак, что соединение установлено с ближним прокси или sidecar, а не с сервером.
Почему лимит запросов по IP иногда блокирует сразу целый город? 
String clientIp = request.getRemoteAddr();            // Адрес, с которого пришло соединение.
if (rateLimiter.tooMany(clientIp)) return status(429); // 100 запросов в минуту на IP.

За балансировщиком getRemoteAddr вернёт адрес балансировщика, и лимит станет общим на всех клиентов. Если же адрес клиента берётся правильно, мобильный оператор всё равно выводит тысячи абонентов через несколько адресов NAT. Лимит по IP годится только как грубая защита; основной лимит строят по пользователю или ключу API, а адрес берут из X-Forwarded-For своего доверенного прокси.
