NoSQL Overview

NoSQL — не одна технология, а несколько моделей данных, каждая из которых жертвует частью возможностей реляционной базы ради одного свойства. Key-value даёт предельно быстрый доступ по ключу, документная модель — данные, читаемые и меняемые целиком, wide-column — горизонтальную запись огромных потоков, графовая — обход связей, поисковые движки — полнотекстовый поиск, time-series — метрики во времени. Выбирают не «SQL или NoSQL», а модель под конкретный способ доступа, и часто реляционной базы с jsonb и правильными индексами хватает. В одной системе обычно живут несколько хранилищ, каждое под свою задачу.

Команда выбрала MongoDB «для гибкости», а через год писала транзакции и соединения вручную

Новый сервис платежей начали на MongoDB: схема меняется быстро, документы удобны. Через год в нём были переводы между счетами, отчёты с группировкой по магазинам и проверка уникальности заказа — всё то, что реляционная база делает сама, а здесь пришлось писать транзакциями, конвейерами агрегации и ручными проверками. В соседней команде наоборот: журнал из миллиардов событий в PostgreSQL упёрся в один сервер, а Cassandra решила бы задачу без шардирования вручную.

Тема — карта моделей данных и критерии выбора. Каждое хранилище разобрано отдельно: Redis, MongoDB, Cassandra, Elasticsearch; компромиссы согласованности — в CAP & Consistency. Демо JsonbDemo.java показывает PostgreSQL 17 в роли документного хранилища.

Общее у большинства — отказ от чего-то, что реляционная база даёт бесплатно: произвольных запросов, соединений, транзакций через много сущностей, строгой схемы. Взамен — горизонтальное масштабирование, предсказуемая задержка или модель, близкая к задаче. Поэтому первый вопрос — какие запросы будут, второй — какие гарантии нужны, и только третий — объём.

Часто хватает реляционной базы с jsonb

create table payment_doc(
    id bigint primary key, merchant_id int not null, doc jsonb not null,
    check (doc ? 'currency' and (doc->>'amount')::bigint > 0));
create index on payment_doc using gin (doc jsonb_path_ops);
select count(*) from payment_doc where doc @> '{"card": {"country": "KZ"}, "tags": ["chargeback"]}';

PostgreSQL хранит документ в jsonb, ищет по вложенным полям через GIN-индекс — 6 мс вместо 38 на полмиллиона документов, — меняет одно поле через jsonb_set и при этом сохраняет то, чего нет в документных базах из коробки: CHECK-ограничение отклонило документ с отрицательной суммой, а обычный SQL с группировкой работает поверх документов. Гибкая часть данных — атрибуты карты, теги, метаданные партнёра — живёт в jsonb, а важные поля — в колонках с типами и ограничениями.

Отдельная документная база оправдана, когда документы — основной и почти единственный способ работы с данными, их очень много и нужен встроенный шардинг, а транзакции через документы редки. Если же нужна «гибкость схемы» поверх по сути реляционных данных — счетов, переводов, заказов, — она обычно оборачивается ручной реализацией того, что база умела.

Выбор начинают с запросов и гарантий, и в системе обычно несколько хранилищ

Типичная платёжная система держит деньги и связи в реляционной базе, а остальное раздаёт специализированным хранилищам: Redis для кеша и лимитов, Elasticsearch для поиска, колоночное хранилище для аналитики, иногда Cassandra для журнала огромного объёма. Данные в производные хранилища идут асинхронно — через outbox или CDC, — и каждое отстаёт от источника. Это polyglot persistence: выигрыш в каждой задаче оплачивается эксплуатацией нескольких систем и согласованием между ними, поэтому новое хранилище добавляют, когда существующее действительно не справляется.

NoSQL нужен, когда данных много, а SQL — когда мало.

PostgreSQL на одном сервере держит терабайты и десятки тысяч транзакций в секунду, а с секционированием и репликами — ещё больше. Выбор определяют способ доступа и гарантии: транзакции через сущности и произвольные запросы — к реляционной базе, запись огромного потока по ключу в нескольких дата-центрах — к Cassandra, полнотекстовый поиск — к Elasticsearch.

  • Key-value, документная, wide-column, поисковая, графовая, time-series — каждая оптимизирует один способ доступа.
  • Взамен отказываются от произвольных запросов, соединений, транзакций или строгой схемы.
  • PostgreSQL с jsonb: GIN-поиск 6 мс против 38, частичное обновление, CHECK по документу и SQL поверх документов.
  • В системе несколько хранилищ: источник правды и производные, наполняемые через outbox или CDC.

На собеседовании

Как выбрать между SQL и NoSQL?

По запросам и гарантиям. Если нужны транзакции через несколько сущностей, соединения, произвольные отчёты и ограничения целостности — реляционная база. Если доступ только по ключу с минимальной задержкой — key-value; данные читаются и меняются целиком документом — документная; огромный поток записи по ключу в нескольких дата-центрах — wide-column; полнотекстовый поиск — поисковый движок.

  • PostgreSQL с jsonb часто закрывает потребность в гибкой схеме без отдельной базы.
  • Polyglot persistence: источник правды плюс производные хранилища через CDC.
  • Масштаб — третий вопрос: один сервер PostgreSQL выдерживает больше, чем кажется.
Что спорного в этом выборе хранилищ? 
Сервис переводов между счетами клиентов:
- балансы и переводы — MongoDB, «чтобы не мучиться со схемой»
- проверка лимитов — чтение баланса, проверка в коде, запись
- история переводов для поддержки — та же коллекция, поиск по regex в описании

Переводы затрагивают два счёта и требуют атомарности и проверки инвариантов — это задача реляционной базы с транзакциями и ограничениями; в MongoDB понадобятся транзакции на несколько документов и аккуратная модель. Проверка лимита чтением и записью в коде теряет обновления при гонке. Поиск по regex без индекса — полный проход; для поиска поддержки нужен Elasticsearch или GIN-индекс. Схему лучше держать в PostgreSQL, гибкие атрибуты — в jsonb.

Какие модели данных относят к NoSQL и для чего каждая?

Key-value (Redis, DynamoDB) — доступ по ключу: кеш, сессии. Документная (MongoDB) — вложенные документы с гибкой схемой. Wide-column (Cassandra) — огромные потоки записи с запросами по partition key. Графовая (Neo4j) — обход связей. Поисковая (Elasticsearch) — полнотекстовый поиск. Time-series — метрики и события во времени.

  • Большинство жертвуют соединениями, произвольными запросами или транзакциями ради масштаба и задержки.
  • Многие NoSQL-базы со временем добавили транзакции и SQL-подобные языки, а реляционные — документы.

Когда хватит PostgreSQL с jsonb вместо документной базы?

Когда гибкая часть — атрибуты, метаданные, настройки — дополняет реляционные данные, а не заменяет их. jsonb индексируется GIN, поддерживает поиск по вложенным полям, частичное обновление и CHECK-ограничения, и при этом остаются транзакции, соединения и SQL. Отдельная документная база нужна, когда документы — основная модель, их очень много и нужен встроенный шардинг.

  • Важные поля держат колонками с типами, гибкие — в jsonb.
  • Обновление jsonb переписывает всё значение, большие документы уходят в TOAST.

  • PostgreSQL 17: JSON Types — jsonb, операторы и индексы.
