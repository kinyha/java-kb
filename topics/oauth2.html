OAuth 2.0 & OIDC

OAuth 2.0 — протокол делегирования: пользователь разрешает приложению действовать в API от его имени с ограниченными правами, не отдавая пароль. Приложение получает от сервера авторизации короткий код через браузер и меняет его на токен по прямому каналу. PKCE связывает код с секретом приложения, поэтому перехваченный код бесполезен; state связывает ответ с браузером; redirect_uri сравнивается точно. Сервисы без пользователя получают токен по client credentials. OpenID Connect добавляет поверх OAuth вход: id token сообщает приложению, кто пользователь, а access token остаётся пропуском в API.

Бухгалтерский сервис хочет читать платежи магазина и просит пароль от кабинета

Магазин подключает сторонний сервис бухгалтерии, которому нужна выписка платежей. Самый простой способ — ввести в бухгалтерии логин и пароль от платёжного кабинета. Тогда бухгалтерия получает всё: может делать выплаты, менять реквизиты и пароль. Забрать доступ можно только сменой пароля, которая отключит и всех остальных. А если бухгалтерию взломают, утечёт пароль владельца магазина.

OAuth решает это делегированием: владелец разрешает бухгалтерии одно действие — читать платежи, — а бухгалтерия получает токен с этим правом, без пароля и с возможностью отозвать его отдельно. Тема разбирает потоки OAuth и OpenID Connect на уровне протокола: что передаётся через браузер, что по прямому каналу и какие атаки закрывает каждая проверка. Настройка в Spring и Keycloak — в OAuth2 & JWT, формат токенов — в JWT. Демо OAuthFlowDemo.java реализует сервер авторизации с проверками из RFC в одном процессе: java OAuthFlowDemo.java на JDK 21. Verifier и state случайные при каждом запуске.

Четыре роли: владелец, клиент, сервер авторизации и API

РольВ примереЧто делает
Resource ownerВладелец магазинаДаёт согласие на доступ
ClientБухгалтерия, мобильное приложениеПолучает токен и вызывает API
Authorization serverKeycloak, Okta, Auth0Аутентифицирует владельца, выдаёт токены
Resource serverПлатёжный APIПроверяет токен и права

Права в OAuth выражаются scope — строками вроде payments:read, которые клиент запрашивает, а владелец подтверждает на экране согласия. Scope ограничивает клиента, а не пользователя: токен бухгалтерии со scope payments:read не даёт делать выплаты, даже если сам владелец может. Окончательное решение о доступе всё равно принимает API: scope разрешает тип действия, а принадлежность конкретного магазина пользователю проверяется по данным.

Клиенты бывают конфиденциальные — серверные приложения, которые могут хранить секрет, — и публичные — SPA и мобильные приложения, где любой секрет извлекается из кода. Для публичных клиентов секрет бессмыслен, и их защищает PKCE.

Authorization code передаёт через браузер только код, а токен — по прямому каналу

Браузер — ненадёжный канал: адреса попадают в историю, логи и заголовок Referer, а на мобильных устройствах редирект на схему приложения может перехватить другое приложение. Поэтому через браузер передаётся только короткоживущий одноразовый код, а токен приложение получает прямым POST на сервер авторизации:

== authorization code + PKCE
verifier  = 7Fh7kFov7SIw... (stays in the app)
challenge = DW3E1T6pb9lV... (sent to /authorize)
302 -> https://app.pay.example/cb?code=c-1&state=<state>
app checks state: match
attacker with stolen code -> 400 invalid_grant (PKCE verifier)
app with verifier         -> 200 access_token(sub=anna, aud=payments, scope=payments:read, exp=5m) + refresh_token
same code again           -> 400 invalid_grant (unknown or used code)

Атакующий перехватил код c-1 и успел обменять его первым, но verifier он не знает: в браузере был только хеш, а обратить SHA-256 нельзя. Попытка сожгла код, и приложение проходит вход заново. Повторный обмен уже использованного кода отклоняется. В RFC 9700 PKCE рекомендован для всех клиентов, включая конфиденциальные, а в OAuth 2.1 обязателен.

Точный redirect_uri и state закрывают кражу кода и подмену ответа

== authorize checks
redirect to evil.example  -> 400 invalid redirect_uri, no redirect
redirect with extra path  -> 400 invalid redirect_uri, no redirect
scope payouts:write       -> https://app.pay.example/cb?error=invalid_scope&state=s1
without PKCE              -> https://app.pay.example/cb?error=invalid_request&error_description=pkce_required&state=s2

redirect_uri сравнивается с зарегистрированным посимвольно. Если сервер разрешает префиксы или поддомены, атакующий подставит адрес, который отдаст код ему: /cb/../steal или страницу с открытым редиректом на том же домене. При неверном redirect_uri сервер не делает редирект вовсе, а показывает ошибку: иначе он сам отправит пользователя на чужой адрес. Остальные ошибки, как недопустимый scope, возвращаются на проверенный redirect_uri.

state — случайное значение, которое приложение кладёт в сессию браузера перед редиректом и сверяет в ответе. Без него атакующий может подсунуть жертве ссылку на callback со своим кодом, и жертва окажется залогинена в аккаунт атакующего — платёжные данные, которые она введёт, уйдут ему. Это CSRF на callback. PKCE частично закрывает эту атаку, но state остаётся стандартной защитой.

Два старых потока больше не используют. Implicit возвращал токен прямо в адресе браузера, где он утекал через историю и Referer. Resource owner password заставлял приложение принимать пароль пользователя, ради отказа от чего OAuth и создавался. RFC 9700 запрещает оба, и в OAuth 2.1 их нет.

Client credentials — токен для сервиса, действующего от себя

Ночная задача выплат вызывает платёжный API без пользователя. Ей не нужен браузер и согласие: она аутентифицируется собственными учётными данными и получает токен для себя:

== client credentials
payouts-job               -> 200 access_token(sub=payouts-job, scope=payouts:write, exp=5m), no refresh_token
wrong secret              -> 401 invalid_client
public client shop-app    -> 401 invalid_client

Refresh-токен здесь не нужен: у сервиса есть учётные данные, и он просто запросит новый токен. Публичный клиент этот поток использовать не может — у него нет секрета. Секрет в заголовке Basic — самый простой способ; надёжнее аутентифицировать клиента подписанным JWT (private_key_jwt) или клиентским сертификатом mTLS, тогда общего секрета нет вовсе.

Когда сервис A вызывает сервис B от имени пользователя, токен пользователя не стоит пробрасывать как есть: его аудитория — A, и B не должен принимать чужие токены. Для этого есть Token Exchange (RFC 8693): A меняет токен пользователя на новый, с аудиторией B и урезанным scope.

OIDC добавляет вход: id token для приложения, access token для API

OAuth отвечает на вопрос «что приложению можно делать», но не «кто пользователь». Access token предназначен API, его формат для клиента не определён, и использовать его как доказательство входа опасно: токен, выданный другому приложению, можно подсунуть. OpenID Connect — слой поверх authorization code flow. Клиент запрашивает scope openid и получает вместе с access token id token — JWT, адресованный самому клиенту:

ID tokenAccess token
Для когоДля клиента: aud = client_idДля API: aud = API
Что значитПользователь вошёл, вот кто онПредъявителю разрешены эти scope
ФорматВсегда JWTJWT или непрозрачная строка
Куда отправлятьНикуда, клиент читает самВ заголовке Authorization к API

Клиент проверяет подпись id token, iss, aud равный своему client_id, срок и nonce — значение, которое он сам передал в запросе, чтобы старый id token нельзя было подставить повторно. Адреса эндпоинтов и ключей клиент берёт из discovery-документа /.well-known/openid-configuration. Единый вход (SSO) получается сам собой: у пользователя есть сессия на сервере авторизации, и следующее приложение получает код без ввода пароля.

SAML решает ту же задачу входа в корпоративной среде: XML-утверждение, подписанное провайдером идентификации, передаётся через браузер POST-формой. Он старше OIDC и живёт в интеграциях с корпоративными каталогами, но для нового кода выбирают OIDC: проще, JSON и работает с мобильными клиентами.

OAuth — это способ входа через Google.

OAuth — делегирование доступа к API; он не говорит приложению, кто пользователь. Вход через Google — это OpenID Connect поверх OAuth, с id token, адресованным приложению. Аутентификация по одному access token позволяет подсунуть токен, выданный другому приложению.

  • OAuth делегирует доступ: клиент получает токен со scope, а пароль остаётся у сервера авторизации.
  • Authorization code: через браузер только код, токен — прямым POST; PKCE делает перехваченный код бесполезным.
  • redirect_uri сравнивается точно, state защищает callback; implicit и password grant запрещены.
  • Client credentials — для сервисов без пользователя; между сервисами — Token Exchange.
  • OIDC: id token для клиента с aud = client_id и nonce; access token — только для API. SAML — корпоративное наследие.

На собеседовании

Как работает authorization code flow и зачем нужен PKCE?

Клиент отправляет браузер на /authorize с client_id, redirect_uri, scope и state. Пользователь входит на сервере авторизации и соглашается, сервер возвращает браузер на redirect_uri с одноразовым кодом. Клиент меняет код на токены прямым POST на /token. Через браузер проходит только код, а токен — по прямому каналу.

PKCE защищает код от перехвата: клиент генерирует verifier, отправляет в /authorize его SHA-256, а при обмене предъявляет сам verifier. Перехвативший код не знает verifier и токен не получит.

  • Публичные клиенты не могут хранить секрет, поэтому для них PKCE — единственная привязка кода к клиенту; RFC 9700 рекомендует его всем.
  • Метод challenge — S256; plain допустим только если SHA-256 недоступен.
  • Implicit и password grant запрещены RFC 9700 и отсутствуют в OAuth 2.1.
Что опасного в такой настройке клиента на сервере авторизации? 
client_id:      shop-app
client_type:    public
redirect_uris:  https://app.pay.example/*
grant_types:    authorization_code, implicit
pkce_required:  false

Шаблон redirect_uri позволяет увести код на любую страницу домена, включая страницу с открытым редиректом. Implicit отдаёт токен в адресе браузера. Публичному клиенту без PKCE перехваченный код даёт токен. Нужно точное значение redirect_uri, только authorization_code и обязательный PKCE с S256.

Чем OpenID Connect отличается от OAuth 2.0, а id token от access token?

OAuth — делегирование доступа к API; он не сообщает клиенту, кто пользователь. OIDC — слой поверх OAuth для входа: scope openid, id token, userinfo-эндпоинт и discovery. ID token — JWT для клиента, aud равен client_id, в нём sub и данные о входе. Access token — для API, его отправляют в Authorization, и клиент не должен на него опираться как на доказательство входа.

  • Клиент проверяет подпись, iss, aud, exp и nonce id token.
  • Вход по access token уязвим: токен, выданный другому приложению, подходит.
  • SSO — следствие сессии на сервере авторизации; SAML решает ту же задачу через XML и встречается в корпоративных интеграциях.

Как сервис получает токен без пользователя и как передать права пользователя дальше по цепочке?

Client credentials: сервис аутентифицируется своими учётными данными на /token и получает access token на себя, без refresh-токена. Права задаются scope, выданными этому клиенту.

Чтобы вызвать следующий сервис от имени пользователя, используют Token Exchange: обменять токен пользователя на новый с аудиторией следующего сервиса и урезанными правами, а не пробрасывать исходный.

  • Вместо общего секрета — private_key_jwt или mTLS для аутентификации клиента.
  • Каждый сервис принимает только токены со своей aud, иначе токен одного сервиса работает во всех.
  • RFC 9700: Best Current Practice for OAuth 2.0 Security — основа урока: PKCE, точный redirect_uri, запрет implicit и password grant.
  • RFC 6749: The OAuth 2.0 Authorization Framework и RFC 7636: PKCE — потоки и ошибки.
  • OpenID Connect Core 1.0 — id token, nonce, проверки клиента.
  • RFC 8693: OAuth 2.0 Token Exchange — передача прав между сервисами.
