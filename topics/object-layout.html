JVM: Object Layout & Allocation

Кеш на миллион платежей занял в пять раз больше, чем данные

Сервис держит в памяти кеш платежей: HashMap<Long, Payment>. У платежа четыре поля: сумма long, код валюты int, флаг возврата boolean и ссылка на счёт. Если сложить размеры полей, получится 17 байт, миллион платежей — 16 МБ. Под это и рассчитали heap. Замер показывает другое.

import java.util.HashMap;
import java.util.Map;

public class Cache {
    static class Payment {
        long amount;
        int currency;
        boolean refunded;
        Object account;
    }

    static long usedHeap() {
        System.gc();                          // только для замера: убрать мусор, оставить живое
        Runtime rt = Runtime.getRuntime();
        return rt.totalMemory() - rt.freeMemory();
    }

    public static void main(String[] args) {
        int count = 1_000_000;
        long before = usedHeap();
        Map<Long, Payment> byId = new HashMap<>();
        for (long id = 0; id < count; id++) {
            byId.put(id, new Payment());       // ключ Long, значение Payment
        }
        long after = usedHeap();
        System.out.println("полезных данных: " + 17L * count / 1024 / 1024 + " МБ");
        System.out.println("занято в heap: " + (after - before) / 1024 / 1024 + " МБ");
        System.out.println("на один платёж: " + (after - before) / count + " байт");
        System.out.println(byId.size());       // держим карту живой до конца замера
    }
}

Замер через System.gc() даёт стабильный, но не гарантированный результат, поэтому ниже — реальный запуск на JDK 21:

$ java -Xmx2g -cp out Cache
полезных данных: 16 МБ
занято в heap: 92 МБ
на один платёж: 97 байт           # вместо 17

97 байт вместо 17 — это не утечка и не ошибка замера. Так устроены объекты в JVM. К концу урока ты разложишь эти 97 байт по полочкам и будешь понимать, откуда берётся каждый: заголовки, выравнивание, ссылки, обёртки и служебные структуры коллекции.

У каждого объекта есть заголовок, даже у пустого

В 64-битной HotSpot объект начинается с заголовка из двух частей. Mark word, 8 байт, хранит служебное состояние: identity hash code, возраст для сборщика мусора, состояние блокировки. Class pointer, 4 байта, указывает на описание класса в Metaspace. У массива сверху ещё 4 байта длины. И весь объект выравнивается до кратного 8 байтам.

Размер объекта в Java из кода напрямую не узнать, но это умеет Instrumentation.getObjectSize. Он доступен из java-агента — маленького JAR, который JVM загружает до main:

import java.lang.instrument.Instrumentation;

// Агент: JVM вызовет premain до main и передаст Instrumentation
public class SizeAgent {
    private static Instrumentation inst;

    public static void premain(String args, Instrumentation instrumentation) {
        inst = instrumentation;
    }

    // Размер самого объекта в байтах, без объектов, на которые он ссылается
    public static long sizeOf(Object o) {
        return inst.getObjectSize(o);
    }
}
public class Sizes {
    public static void main(String[] args) {
        System.out.println("Object       " + SizeAgent.sizeOf(new Object()));
        System.out.println("Integer      " + SizeAgent.sizeOf(Integer.valueOf(1000)));
        System.out.println("Long         " + SizeAgent.sizeOf(Long.valueOf(1000)));
        System.out.println("byte[0]      " + SizeAgent.sizeOf(new byte[0]));
        System.out.println("byte[3]      " + SizeAgent.sizeOf(new byte[3]));
        System.out.println("long[3]      " + SizeAgent.sizeOf(new long[3]));
        System.out.println("String RUB   " + SizeAgent.sizeOf("RUB"));   // только сам String, без массива с буквами
    }
}

Обёртка Long весит 24 байта ради 8 байт числа — втрое больше. Строка из трёх букв весит 48 байт, хотя вывод показал 24: getObjectSize меряет только сам объект String, а буквы лежат в отдельном массиве byte[] ещё на 24 байта.

В реальной работе для таких замеров берут библиотеку JOL (Java Object Layout) из OpenJDK: она печатает раскладку любого объекта и умеет считать весь граф. Агент в уроке — тот же механизм без зависимостей.

JVM сама решает порядок полей, и в объекте остаются дыры

Поля лежат не в том порядке, в каком объявлены. JVM переставляет их, чтобы каждое было выровнено по своему размеру: long — по 8 байтам, int — по 4. Где выравнивание не сходится, остаются пустые байты. Посмотрим, куда HotSpot положил поля Payment.

import java.lang.reflect.Field;
import sun.misc.Unsafe;

public class Layout {
    // Платёж: 8 + 4 + 1 + 4 = 17 байт полезных данных
    static class Payment {
        long amount;          // 8 байт
        int currency;         // 4 байта: числовой код валюты ISO 4217
        boolean refunded;     // 1 байт
        Object account;       // ссылка: 4 байта при compressed oops
    }

    public static void main(String[] args) throws Exception {
        // Unsafe умеет сказать, по какому смещению JVM положила поле
        Field field = Unsafe.class.getDeclaredField("theUnsafe");
        field.setAccessible(true);
        Unsafe unsafe = (Unsafe) field.get(null);

        for (String name : new String[] {"amount", "currency", "refunded", "account"}) {
            long offset = unsafe.objectFieldOffset(Payment.class.getDeclaredField(name));
            System.out.println(name + " @ " + offset);
        }
        System.out.println("размер: " + SizeAgent.sizeOf(new Payment()));
    }
}
amount @ 16
currency @ 12
refunded @ 24
account @ 28
размер: 32

currency объявлен вторым, а лежит первым: он занял четыре байта сразу за заголовком, куда long не помещается. Вот эти 32 байта целиком.

Из 32 байт полезных — 17. Отсюда два практических вывода. Первый: маленькие объекты дороги. Заголовок в 12 байт одинаков для объекта с одним полем и с десятью, поэтому миллион мелких объектов тратит память в основном на заголовки. Второй: возраст объекта занимает 4 бита, поэтому сборщик может считать переживания только до 15. Отсюда верхняя граница флага MaxTenuringThreshold, о ней — в теме Generations.

Mark word ещё и меняется во время жизни объекта. Когда поток берёт synchronized на объекте, биты блокировки меняются, и в mark word временно лежит ссылка на запись о блокировке. Когда первый раз вызывают hashCode() по умолчанию, в mark word записывается identity hash: так он остаётся одинаковым, даже если GC переместит объект.

Ссылки весят 4 байта, пока heap меньше 32 ГБ

На 64-битной машине адрес занимает 8 байт. Но в выводе выше ссылка account заняла 4. Это compressed oops (ordinary object pointers): JVM хранит ссылку как 32-битное число, а при обращении умножает его на 8 и прибавляет адрес начала heap. Умножение на 8 бесплатно — это сдвиг на 3 бита. А раз все объекты выровнены по 8 байтам, младшие три бита адреса всегда нули, и хранить их незачем.

32 бита дают 232 разных значений, умноженных на 8, — 32 ГБ адресов. Если heap больше, 4 байт не хватает, и JVM молча переходит на полные 8-байтные ссылки.

$ java -Xmx31g -XX:+PrintFlagsFinal -version | grep UseCompressedOops
     bool UseCompressedOops    = true        # heap 31 ГБ: ссылки по 4 байта
$ java -Xmx32g -XX:+PrintFlagsFinal -version | grep UseCompressedOops
     bool UseCompressedOops    = false       # heap 32 ГБ: ссылки по 8 байт

$ java -XX:-UseCompressedOops -javaagent:size-agent.jar -cp out:size-agent.jar Layout
amount @ 16
currency @ 12
refunded @ 24
account @ 32                                  # ссылка сдвинулась и выросла
размер: 40                                    # платёж на 25% тяжелее

Кеш из первого шага без compressed oops занял 116 МБ вместо 92: ссылки есть в каждом платеже, в каждом узле HashMap и в таблице. Отсюда парадокс, который любят на собеседованиях: heap в 32 ГБ вмещает меньше живых данных, чем heap в 31 ГБ, потому что все ссылки разом подорожали вдвое. Если нужно больше 32 ГБ, прыгать имеет смысл сразу заметно выше, на 40–48 ГБ.

Чтобы сэкономить память, достаточно выбрать поля поменьше: int вместо long, byte вместо int.

Поля платежа — 17 байт из 97. Основной расход — заголовки и обёртки. Экономят числом объектов: примитивные ключи вместо Long (специальные коллекции вроде fastutil или Eclipse Collections), массивы примитивов вместо списков объектов.

new почти ничего не стоит: у каждого потока свой кусок eden

Раз объектов так много, их создание должно быть дешёвым. Если бы каждый new брал общую блокировку на heap, сотни потоков стояли бы в очереди. Поэтому HotSpot выдаёт каждому потоку TLAB (thread-local allocation buffer) — свой участок в eden, области молодых объектов. Внутри TLAB выделение — это сдвиг указателя: объект кладут по адресу top, и top увеличивают на размер объекта.

Размеры на схеме условные: реальный TLAB — десятки и сотни килобайт, и JVM подстраивает его под скорость выделения потока. Главное — стоимость. Создать объект в TLAB — несколько машинных инструкций, дешевле, чем malloc в C. Платить приходится позже: объекты надо убрать, и цена new на самом деле — это цена сборки мусора. Об этом папка Garbage Collection.

Выделение по сдвигу указателя возможно потому, что eden после сборки мусора всегда пустой и сплошной. Живые объекты сборщик копирует из eden в другие области, поэтому искать дыры между занятыми кусками не нужно.

Объект, который не выходит из метода, JIT может не создавать вовсе

Самый дешёвый объект — тот, которого нет. JIT-компилятор C2 делает escape analysis: проверяет, может ли ссылка на объект выйти за пределы метода — вернуться из него, попасть в поле, в другой поток. Если не может, объект в heap не выделяется: его поля превращаются в обычные локальные переменные и живут в регистрах. Это scalar replacement.

import java.lang.management.ManagementFactory;

public class Escape {
    record Money(long kopecks, String currency) { }

    static Money last;                                   // static-поле: всё, что сюда попало, «сбежало»

    // Money живёт только внутри метода
    static long feeLocal(long amount) {
        Money money = new Money(amount, "RUB");
        return money.kopecks() * 15 / 1000;
    }

    // Тот же объект, но ссылка уходит в static-поле
    static long feeEscaping(long amount) {
        Money money = new Money(amount, "RUB");
        last = money;
        return money.kopecks() * 15 / 1000;
    }

    public static void main(String[] args) {
        // счётчик байтов, которые текущий поток выделил в heap
        var threads = (com.sun.management.ThreadMXBean) ManagementFactory.getThreadMXBean();
        for (int round = 1; round <= 4; round++) {
            long start = threads.getCurrentThreadAllocatedBytes();
            long sum = 0;
            for (int i = 0; i < 1_000_000; i++) sum += feeLocal(i);
            long local = threads.getCurrentThreadAllocatedBytes() - start;

            start = threads.getCurrentThreadAllocatedBytes();
            for (int i = 0; i < 1_000_000; i++) sum += feeEscaping(i);
            long escaping = threads.getCurrentThreadAllocatedBytes() - start;

            System.out.printf("раунд %d: локальный %,d КБ, сбежавший %,d КБ%n", round, local / 1024, escaping / 1024);
        }
    }
}

Результат зависит от того, когда отработает JIT, поэтому ниже — реальные запуски:

раунд 2: локальный 0 КБ, сбежавший 23,437 КБ       # C2 убрал Money из feeLocal полностью
раунд 3: локальный 0 КБ, сбежавший 23,437 КБ

$ java -XX:-DoEscapeAnalysis -cp out Escape         # escape analysis выключен

23 437 КБ на миллион вызовов — ровно 24 байта на объект Money: заголовок 12, ссылка на строку 4, long 8. В методе, где объект не сбегает, после прогрева выделений ноль. Код тот же, разница — только в том, куда уходит ссылка.

Escape analysis работает не всегда. Объект должен оставаться внутри одной скомпилированной единицы. Если метод, которому его передают, не заинлайнен, потому что слишком большой или вызывается через полиморфный вызов, анализ считает объект сбежавшим. Ещё он не помогает в интерпретаторе и не работает для больших массивов. Поэтому писать код в расчёте на escape analysis не стоит, но понимать, почему короткоживущие объекты в горячем коде часто бесплатны, полезно.

Где кончается эта модель? Раскладка — деталь HotSpot, спецификация её не фиксирует, и она меняется. В JDK 24 появились компактные заголовки (-XX:+UseCompactObjectHeaders, JEP 450): заголовок 8 байт вместо 12, пустой объект тоже 8. На JDK 21 урок описывает именно то, что работает сейчас.

  • Объект в 64-битной HotSpot — заголовок 12 байт (mark word 8 и class pointer 4), поля и выравнивание до кратного 8. new Object() — 16 байт, Long — 24.
  • JVM сама переставляет поля по выравниванию и оставляет дыры. На миллионах мелких объектов память уходит в основном на заголовки и обёртки.
  • В mark word на возраст отведено 4 бита, поэтому объект может пережить не больше 15 сборок в молодом поколении.
  • Compressed oops сжимают ссылки до 4 байт, пока heap меньше 32 ГБ. Heap в 32 ГБ вмещает меньше данных, чем в 31.
  • new в TLAB — сдвиг указателя без блокировок. Объекты, которые не сбегают из метода, C2 может не создавать вовсе.

На собеседовании

Сколько памяти занимает new Object() и Integer?

В 64-битной HotSpot у объекта заголовок 12 байт: mark word на 8 байт и сжатый указатель на класс на 4. Размер выравнивается до кратного 8. Поэтому new Object() — 16 байт, Integer — тоже 16: 12 заголовка и 4 числа. Long — 24, у массива ещё 4 байта на длину.

На практике это значит, что коллекции обёрток дорогие. List<Long> из миллиона чисел — это 24 байта на объект плюс 4 на ссылку, а long[] — 8 байт на число.

  • Без compressed class pointers заголовок 16 байт. В JDK 24 появились компактные заголовки на 8 байт (JEP 450).
  • Точный размер показывает JOL или Instrumentation.getObjectSize. Спецификация размеры не фиксирует, это деталь реализации.
Сколько байт займёт объект с полями long id, byte status, Object owner при настройках по умолчанию?

32. Поля — 13 байт, заголовок — 12, но выровнять их плотнее не выйдет. Замер через Layout из урока на JDK 21 показывает: status лёг на смещение 12, сразу за заголовком, и оставил после себя три пустых байта. Дальше id на 16, owner на 24, всего 28 и выравнивание до 32. Порядок полей JVM выбирает сама, поэтому такие подсчёты проверяют замером, а не в уме.

Кеш курсов хранит Map<String, Double> на 10 миллионов записей и не помещается в heap. Что предложишь?

Посчитать, куда уходит память: каждая запись — это Double на 16 байт, узел HashMap на 32, строка-ключ от 48 байт и слот таблицы. Сами числа — 8 байт из сотни. Варианты: хранить ключи как числовые идентификаторы, взять коллекцию с примитивными значениями, держать данные в массивах, а не в объектах.

Что такое compressed oops и почему heap в 32 ГБ хуже, чем в 31?

Compressed oops — сжатые ссылки на объекты. JVM хранит ссылку как 32-битное число, а при обращении сдвигает его на 3 бита и прибавляет базу heap. Сдвиг возможен, потому что все объекты выровнены по 8 байтам. 232 × 8 — это 32 ГБ, и пока heap меньше, каждая ссылка весит 4 байта вместо 8.

При heap от 32 ГБ JVM молча переходит на 8-байтные ссылки. Все объекты со ссылками разом тяжелеют, и живых данных помещается меньше, чем в 31 ГБ. Поэтому heap либо держат ниже 32 ГБ, либо увеличивают сразу заметно выше.

  • Проверить можно так: java -Xmx32g -XX:+PrintFlagsFinal -version | grep UseCompressedOops.
  • С -XX:ObjectAlignmentInBytes=16 граница сдвигается до 64 ГБ ценой большего выравнивания каждого объекта.
Под перевели с -Xmx30g на -Xmx34g «с запасом», и частота GC выросла. Почему?

На 34 ГБ выключились compressed oops, ссылки стали по 8 байт. Живые данные заняли больше места, и свободного heap для новых объектов стало меньше, чем было на 30 ГБ. Нужно вернуться ниже 32 ГБ или брать существенно больше.

Почему выделение объекта в Java дешёвое? Что такое TLAB?

Каждый поток получает свой участок eden — TLAB, thread-local allocation buffer. Выделение внутри него — сдвиг указателя top на размер объекта, без блокировок и поиска свободного места. Это несколько машинных инструкций, дешевле, чем malloc. Когда TLAB кончается, поток берёт новый из eden, это редкий медленный путь.

Настоящая цена new — сборка мусора потом. Поэтому оптимизируют не саму аллокацию, а её объём в горячем коде: меньше временных объектов — реже сборки.

  • Выделение сдвигом указателя возможно, потому что после сборки eden пустой и сплошной: живые объекты скопированы.
  • Объекты больше TLAB выделяются в обход него. В G1 объекты от половины региона становятся humongous и сразу попадают в old.
Видны ли объекты из TLAB одного потока другим потокам?

Да. TLAB — только способ выделения, а не отдельная память. Объект лежит в общем heap, и ссылку на него можно передать куда угодно. Потоку принадлежит лишь право выделять в этом участке.

Что такое escape analysis?

Это анализ, который делает JIT-компилятор C2: может ли ссылка на объект выйти за пределы метода — вернуться, попасть в поле, в другой поток. Если не может, объект не выделяется в heap, а его поля становятся локальными переменными в регистрах. Это scalar replacement.

В уроке метод с локальным Money после прогрева не выделял ни байта, а тот же метод, сохранявший объект в static-поле, выделял по 24 байта на вызов.

  • Работает только в скомпилированном коде и в пределах инлайнинга. Передача объекта в незаинлайненный метод считается побегом.
  • Может убрать и блокировки на объекте, который не сбегает (lock elision).
Сбегает ли объект в методе, который создаёт StringBuilder, склеивает строку и возвращает builder.toString()?

Сам StringBuilder не сбегает: наружу уходит новая строка. Если append и toString заинлайнены, C2 может убрать объект builder, но строка и её массив всё равно выделятся — они возвращаются из метода.

  • JEP 450: Compact Object Headers — заголовок на 8 байт в JDK 24.
