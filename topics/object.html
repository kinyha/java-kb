equals & hashCode

Платёж равен уже обработанному, но HashSet его не узнаёт

Обработчик платежей защищается от повторной доставки: обработанные платежи хранятся в HashSet, и повтор с тем же id пропускается. equals в классе написан — сравнивает id:

import java.util.*;

public class Dedup {
    static class Payment {
        final String id;
        final long amount;
        Payment(String id, long amount) { this.id = id; this.amount = amount; }

        @Override public boolean equals(Object o) {                    // equals переопределён...
            return o instanceof Payment p && id.equals(p.id);
        }
        // ...а hashCode — нет: остаётся Object.hashCode, у каждого объекта свой
    }

    public static void main(String[] args) {
        Set<Payment> processed = new HashSet<>();
        processed.add(new Payment("p-1", 1000));
        Payment retry = new Payment("p-1", 1000);                         // брокер доставил повторно
        System.out.println("equals: " + retry.equals(new Payment("p-1", 1000)));
        System.out.println("уже обработан: " + processed.contains(retry));
        processed.add(retry);
        System.out.println("в множестве платежей: " + processed.size());
    }
}
equals: true
уже обработан: false
в множестве платежей: 2

Объекты равны по equals, а множество считает их разными — платёж проведён дважды. HashSet сначала по hashCode выбирает корзину и только внутри неё вызывает equals. Без своего hashCode у двух равных платежей разные хеши, их ищут в разных корзинах, и до equals дело не доходит.

В этой теме — контракт equals и hashCode и что ломается при каждом нарушении, изменяемые ключи, качество хеша, согласованность с compareTo, а также toString и clone. Как устроен сам HashMap — корзины, деревья, расширение — разобрано в теме HashMap.

Контракт: равные объекты обязаны иметь равные хеши

Правила из javadoc Object, на которые опираются все коллекции:

Свойство equalsСмыслЧто ломается при нарушении

Обратное не требуется: разные объекты могут иметь одинаковый хеш (коллизия). Это разрешено, но дорого — шаг 4. Нарушение симметрии проявляется так:

import java.math.BigDecimal;
import java.util.*;

public class Contract {
    // «удобное» сравнение: код валюты равен и объекту, и строке
    record Currency(String code) {
        @Override public boolean equals(Object o) {
            if (o instanceof Currency c) return code.equalsIgnoreCase(c.code);
            if (o instanceof String s) return code.equalsIgnoreCase(s);  // нарушает симметрию
            return false;
        }
        @Override public int hashCode() { return code.toUpperCase().hashCode(); }
    }

    public static void main(String[] args) {
        Currency rub = new Currency("rub");
        System.out.println("rub.equals(\"RUB\") = " + rub.equals("RUB") + ", \"RUB\".equals(rub) = " + "RUB".equals(rub));
        List<Object> strings = List.of("RUB"), currencies = List.of(rub);
        System.out.println("strings.contains(rub) = " + strings.contains(rub)          // вызывает rub.equals("RUB")
            + ", currencies.contains(\"RUB\") = " + currencies.contains("RUB"));        // вызывает "RUB".equals(rub)

        BigDecimal a = new BigDecimal("100.0"), b = new BigDecimal("100.00");
        System.out.println("equals: " + a.equals(b) + ", compareTo: " + a.compareTo(b));
        System.out.println("HashSet: " + new HashSet<>(List.of(a, b)).size() + " элемента, TreeSet: " + new TreeSet<>(List.of(a, b)).size());
    }
}
rub.equals("RUB") = true, "RUB".equals(rub) = false
strings.contains(rub) = true, currencies.contains("RUB") = false
equals: false, compareTo: 0
HashSet: 2 элемента, TreeSet: 1

Currency «умеет» сравниваться со строкой, а String о Currency не знает. Итог зависит от того, какая сторона вызвала equals, и две похожие проверки дают разные ответы. Правило: equals сравнивает только с объектами своего типа. Последние две строки — к шагу 5.

Отдельная ловушка — наследование. Если подкласс добавляет поле в equals, симметрию или транзитивность с базовым классом сохранить нельзя. Отсюда выбор между instanceof (подклассы равны базовому, но не должны менять equals) и getClass() == o.getClass() (объекты разных классов никогда не равны, но это ломает принцип подстановки). Обычный выход — сделать класс final или использовать композицию.

Писать equals и hashCode руками почти не нужно. Record генерирует оба по всем компонентам. Для обычных классов есть Objects.equals и Objects.hash, генерация в IDE, @EqualsAndHashCode в Lombok. Главное — одинаковый набор полей в обоих методах.

Ключ, изменённый после put, в HashMap больше не найти

Контракт позволяет hashCode меняться, если меняется объект. Но коллекция запомнила объект по старому хешу:

import java.util.*;

public class MutableKey {
    static class Card {
        String number;                                                  // изменяемое поле участвует в hashCode
        Card(String number) { this.number = number; }
        @Override public boolean equals(Object o) { return o instanceof Card c && number.equals(c.number); }
        @Override public int hashCode() { return number.hashCode(); }
        @Override public String toString() { return "Card(" + number + ")"; }
    }

    public static void main(String[] args) {
        Map<Card, Long> limits = new HashMap<>();
        Card card = new Card("4111 1111");
        limits.put(card, 50_000L);

        card.number = "4111-1111";                                      // «нормализовали» номер после put
        System.out.println("get(card):         " + limits.get(card));
        System.out.println("containsKey(card): " + limits.containsKey(card));
        System.out.println("get(старый номер): " + limits.get(new Card("4111 1111")));
        System.out.println("remove(card):      " + limits.remove(card) + ", size = " + limits.size());
        System.out.println("но при обходе запись есть: " + limits);
    }
}
get(card):         null
containsKey(card): false
get(старый номер): null
remove(card):      null, size = 1
но при обходе запись есть: {Card(4111-1111)=50000}

Правило: поля, которые участвуют в equals и hashCode, у ключей не меняются. Проще всего сделать ключ неизменяемым — record, String, Long. Если объект изменяемый, его вынимают из карты, меняют и кладут заново.

Та же проблема в JPA-сущностях. Если hashCode считается по id, который база присваивает при сохранении, то сущность, положенная в HashSet до persist, «теряется» после него: id был null, стал числом. Обычные решения — сравнение по естественному неизменяемому ключу или hashCode, возвращающий константу класса вместе с equals по непустому id.

Плохой hashCode превращает HashMap в список

Контракт выполняет и hashCode, возвращающий одну константу: равные объекты получают равный хеш. Но тогда все ключи попадают в одну корзину. Сравним с нормальным хешем и с тем же постоянным хешем у ключа, который реализует Comparable:

import java.util.*;
import java.util.function.LongFunction;

public class BadHash {
    record Good(long id) { }                                         // hashCode от record — по полям
    static final class Bad {                                          // одинаковый hashCode у всех
        final long id;
        Bad(long id) { this.id = id; }
        @Override public boolean equals(Object o) { return o instanceof Bad b && b.id == id; }
        @Override public int hashCode() { return 42; }
    }

    static final class BadComparable implements Comparable<BadComparable> {   // тот же hashCode, но с порядком
        final long id;
        BadComparable(long id) { this.id = id; }
        @Override public boolean equals(Object o) { return o instanceof BadComparable b && b.id == id; }
        @Override public int hashCode() { return 42; }
        @Override public int compareTo(BadComparable o) { return Long.compare(id, o.id); }
    }

    static long run(int n, LongFunction<Object> key) {               // n вставок и n поисков, мс
        long start = System.nanoTime();
        Map<Object, Long> map = new HashMap<>();
        for (long i = 0; i < n; i++) map.put(key.apply(i), i);
        for (long i = 0; i < n; i++) map.get(key.apply(i));
        return (System.nanoTime() - start) / 1_000_000;
    }

    public static void main(String[] args) {
        run(5_000, Good::new); run(5_000, Bad::new); run(5_000, BadComparable::new);   // прогрев
        for (int n : new int[]{5_000, 10_000, 20_000})
            System.out.printf("%,6d ключей: хороший hashCode %d мс, hashCode = 42 %4d мс, 42 + Comparable %2d мс%n",
                n, run(n, Good::new), run(n, Bad::new), run(n, BadComparable::new));
    }
}
 5,000 ключей: хороший hashCode 0 мс, hashCode = 42   53 мс, 42 + Comparable  1 мс
10,000 ключей: хороший hashCode 0 мс, hashCode = 42  201 мс, 42 + Comparable  1 мс
20,000 ключей: хороший hashCode 0 мс, hashCode = 42 1038 мс, 42 + Comparable  3 мс

С постоянным хешем каждая операция перебирает всю корзину. Вдвое больше ключей — в 4–5 раз больше времени, и на 20 000 ключей это секунда вместо долей миллисекунды. С Java 8 большая корзина превращается в красно-чёрное дерево, но упорядочить его без хеша можно только через compareTo. Для Comparable-ключей поиск остаётся логарифмическим — 3 мс. Для остальных дерево не помогает.

Хороший хеш зависит от тех же полей, что и equals, и равномерно их перемешивает. Сгенерированный hashCode record или Objects.hash(a, b, c) для этого достаточен. Objects.hash создаёт массив для varargs, поэтому в очень горячем коде пишут 31 * a.hashCode() + b.hashCode(). Постоянные хеши и хеши по одному полю с малым числом значений, например по статусу, — частая причина внезапно медленных карт.

compareTo должен соглашаться с equals, иначе HashSet и TreeSet расходятся

Сортированные коллекции — TreeMap, TreeSet — не используют equals: одинаковыми для них считаются элементы с compareTo(...) == 0. Если порядок не согласован с equals, одни и те же данные дают разный результат. В выводе шага 2: BigDecimal("100.0") и BigDecimal("100.00") не равны по equals — у них разный масштаб, — но равны по compareTo. Поэтому HashSet хранит два элемента, а TreeSet — один. Деньги в BigDecimal сравнивают через compareTo (тема BigDecimal & Money).

Вторая классическая ошибка — компаратор через вычитание:

import java.util.*;

public class Compare {
    record Payment(String id, int amount) { }

    public static void main(String[] args) {
        List<Payment> list = new ArrayList<>(List.of(
            new Payment("a", 2_000_000_000), new Payment("b", -2_000_000_000), new Payment("c", 0)));

        list.sort((x, y) -> x.amount() - y.amount());                           // вычитание переполняется
        System.out.println("x - y:            " + list.stream().map(Payment::id).toList());

        list.sort(Comparator.comparingInt(Payment::amount));                     // Integer.compare внутри
        System.out.println("comparingInt:     " + list.stream().map(Payment::id).toList());

        list.sort(Comparator.comparingInt(Payment::amount).reversed().thenComparing(Payment::id));
        System.out.println("по убыванию суммы: " + list.stream().map(Payment::id).toList());
    }
}
x - y:            [a, b, c]
comparingInt:     [b, c, a]
по убыванию суммы: [a, c, b]

2 000 000 000 − (−2 000 000 000) переполняет int и становится отрицательным, поэтому «a» оказывается меньше «b». Сортировка вышла неверной, и никакого исключения. Сравнивают через Integer.compare, Long.compare или фабрики Comparator.comparing…, которые собираются в цепочки thenComparing и reversed.

toString — для логов без секретов, clone — лучше не использовать

Два других метода Object, о которых спрашивают на собеседованиях.

toString по умолчанию печатает имя класса и хеш в шестнадцатеричном виде: Payment@1b6d3586. Переопределять его стоит для логов и отладки. Record делает это сам. Но в toString не включают номера карт, токены и персональные данные: всё, что попало в toString, рано или поздно окажется в логах. И не обращаются к ленивым связям JPA — это лишний запрос к базе или LazyInitializationException при логировании.

clone — неудачный механизм. Он требует маркерного интерфейса Cloneable, бросает checked-исключение, обходит конструкторы и по умолчанию копирует поля поверхностно:

import java.util.*;

public class Cloning {
    static class Order implements Cloneable {
        String id;
        List<String> items = new ArrayList<>();
        Order(String id) { this.id = id; }

        @Override public Order clone() {
            try { return (Order) super.clone(); }                      // поверхностная копия полей
            catch (CloneNotSupportedException e) { throw new AssertionError(e); }
        }
        Order(Order other) {                                            // конструктор копирования
            this.id = other.id;
            this.items = new ArrayList<>(other.items);                  // глубокая копия списка
        }
    }

    public static void main(String[] args) {
        Order original = new Order("o-1");
        original.items.add("кофе");
        Order cloned = original.clone(), copied = new Order(original);
        cloned.items.add("торт");
        copied.items.add("чай");
        System.out.println("original: " + original.items + ", clone делит список: " + (cloned.items == original.items));
        System.out.println("copy:     " + copied.items);
    }
}
original: [кофе, торт], clone делит список: true
copy:     [кофе, чай]

Клон делит список с оригиналом, и «торт» появился в исходном заказе. Конструктор копирования или статический метод copyOf явно решают, что копировать глубоко, и работают с final-полями. Effective Java прямо советует их вместо clone. Для массивов clone() по-прежнему удобен: int[] copy = array.clone().

  • Хеш-коллекции ищут сначала по hashCode, потом по equals. Переопределён equals — обязательно переопределить и hashCode по тем же полям.
  • equals: рефлексивность, симметричность, транзитивность, согласованность, false для null. Сравнение только с объектами своего типа.
  • Ключ, изменённый после put, не найти и не удалить. Ключи делают неизменяемыми.
  • Постоянный или плохой хеш превращает карту в список: секунда вместо миллисекунды на 20 000 ключей. Дерево в корзине спасает только Comparable-ключи.
  • compareTo должен соглашаться с equals: BigDecimal 100.0 и 100.00 — два элемента в HashSet и один в TreeSet. Компаратор — через Integer.compare, не вычитание.
  • toString — без секретов и ленивых связей. Вместо clone — конструктор копирования.

На собеседовании

Какой контракт у equals и hashCode? Что будет, если переопределить только equals?

equals должен быть рефлексивным, симметричным, транзитивным, согласованным и возвращать false для null. Главное правило связи: равные по equals объекты обязаны иметь одинаковый hashCode. Обратное не требуется — коллизии допустимы.

Если переопределить только equals, равные объекты получат разные хеши от Object.hashCode. HashSet и HashMap будут искать их в разных корзинах и считать разными: дубликаты в множестве, get возвращает null. В замере урока повторная доставка того же платежа не распознавалась.

  • С наследованием контракт хрупок: подкласс, добавивший поле в equals, ломает симметрию или транзитивность. Выход — final-классы, record или композиция.
  • Для JPA-сущностей id меняется при persist, поэтому хеш по id «теряет» сущность в HashSet.
class Payment { String id; public boolean equals(Object o) {...по id...} } — используется в HashSet для дедупликации. Что не так?

Нет hashCode. Два платежа с одним id имеют разные хеши, и множество их не отождествляет: contains возвращает false, дубликат добавляется. Нужен hashCode по тем же полям, что и equals, а проще — сделать Payment record.

Что будет, если изменить объект, который лежит ключом в HashMap?

Если изменилось поле, участвующее в hashCode, запись останется в корзине, вычисленной по старому хешу. get и containsKey по этому же объекту будут искать в другой корзине и вернут null. Поиск по старому значению попадёт в нужную корзину, но не пройдёт equals. Запись нельзя найти и удалить, её видно только при обходе — это утечка. Ключи делают неизменяемыми.

Можно ли вернуть из hashCode константу?

Контракт это допускает, но все ключи окажутся в одной корзине, и HashMap станет линейным: в замере урока 20 000 ключей обрабатывались секунду вместо долей миллисекунды. С Java 8 большая корзина превращается в дерево, но без хеша упорядочить его можно только через compareTo. Для Comparable-ключей поиск остаётся логарифмическим, для остальных — нет.

Что значит «compareTo согласован с equals» и почему это важно?

Что a.compareTo(b) == 0 тогда и только тогда, когда a.equals(b). TreeSet и TreeMap определяют равенство через compareTo, а хеш-коллекции — через equals. При несогласованности одни и те же данные ведут себя по-разному. Пример — BigDecimal: 100.0 и 100.00 не равны по equals, но равны по compareTo, поэтому в HashSet их два, а в TreeSet один.

Компаратор (a, b) -> a.amount() - b.amount() для сумм до ±2 млрд. Что может пойти не так?

Вычитание переполняет int: 2 000 000 000 − (−2 000 000 000) становится отрицательным, и порядок переворачивается без исключения. В замере урока список отсортировался неверно. Нужно Integer.compare или Comparator.comparingInt.

Почему clone считается неудачным механизмом?

Нужен маркерный интерфейс Cloneable, Object.clone — protected и бросает checked-исключение, он обходит конструкторы и по умолчанию копирует поля поверхностно: изменяемые поля остаются общими с оригиналом. С final-полями глубокую копию через clone не сделать. Вместо него используют конструктор копирования или фабрику copyOf.
