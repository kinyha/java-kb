Observability Overview

Наблюдаемость — способность понять по внешним сигналам, что происходит внутри системы, включая проблемы, которых не ждали. Три вида сигналов отвечают на разные вопросы: метрики — «что-то не так и насколько» (дёшево, агрегированно, для алертов), логи — «что именно случилось с этим запросом» (подробно и дорого), трассы — «где по пути через сервисы ушло время». Связывает их сквозной идентификатор запроса: без него ошибку в третьем сервисе не сопоставить с запросом пользователя, в демо по её идентификатору находятся только строки самого упавшего сервиса. MDC в Java живёт в потоке и теряется при переходе в пул — 200 асинхронных строк из 200 остались без идентификатора. Для алертов и SLO смотрят на четыре золотых сигнала и перцентили: средняя задержка 35 мс скрыла p99 в 440 мс.

Пользователь пишет «платёж не прошёл», а в логах тысячи строк

Поддержка пересылает жалобу: у клиента не прошёл платёж в 14:32. Логи трёх сервисов собраны в одно хранилище, за минуту в нём десятки тысяч строк. В сервисе платежей есть ошибка «issuer unavailable», но к какому запросу пользователя она относится — неизвестно: каждый сервис пишет свой идентификатор, и связать строки шлюза, заказов и платежей можно только по времени, а в минуту таких запросов тысячи.

Тема — обзор: какие сигналы собирать, как связать их между сервисами и на что смотреть. Метрики подробно — в Metrics, трассировка — в Tracing, алерты и инциденты — в Alerting & Incidents, логирование в Java — в Logging. Демо ObservabilityDemo.java запускает три сервиса на JDK HttpServer — gateway, orders, payments — с SLF4J, Logback и JSON-логами через logstash-logback-encoder в общий файл; каждый 50-й платёж медленный, запрос 137 падает.

Метрики, логи и трассы отвечают на разные вопросы

СигналВопросСтоимостьИнструменты
МетрикиЧто-то не так? Насколько? С какого момента?Дёшево: числа, агрегированные во времениMicrometer, Prometheus, Grafana
ЛогиЧто именно случилось с этим запросом?Дорого: каждое событие, хранение по объёмуLogback JSON, Loki, Elasticsearch
ТрассыГде по пути через сервисы ушло время?Средне: обычно выборка запросовOpenTelemetry, Jaeger, Tempo

Типичный путь расследования идёт от дешёвого к подробному: алерт по метрике показывает, что выросла доля ошибок оплаты; трасса медленного или упавшего запроса показывает, в каком сервисе и на каком вызове; логи этого запроса по его идентификатору показывают, что именно произошло. Для этого сигналы должны быть связаны: идентификатор трассы и запроса — в каждой строке лога, метки сервиса и версии — в метриках, ссылки из метрик на примеры трасс (exemplars).

Мониторинг отвечает на заранее известные вопросы: «доля 5xx выше 1 %?». Наблюдаемость — на вопросы, которых не было при проектировании: «почему падают платежи только для карт одного банка и только с мобильного приложения?». Для второго нужны высокодетальные данные — структурированные логи и трассы с атрибутами, по которым можно резать.

Идентификатор создаёт первый сервис, к которому пришёл запрос, — шлюз или балансировщик, — и каждый следующий передаёт его дальше в заголовке, в сообщениях брокера и в задачах фоновой обработки. В современных системах эту роль играет идентификатор трассы из заголовка W3C traceparent, который OpenTelemetry передаёт автоматически и добавляет в MDC, как в Tracing. Логи пишут структурированно — JSON с полями, а не строкой: тогда фильтр по requestId, сервису или коду ответа работает в хранилище логов, а не регулярными выражениями.

MDC живёт в потоке и теряется в пуле

// MDC живёт в ThreadLocal: в другой поток его надо перенести вручную.
static Runnable withMdc(Runnable r) {
    Map<String, String> ctx = MDC.getCopyOfContextMap();
    return () -> { MDC.setContextMap(ctx); try { r.run(); } finally { MDC.clear(); } };
}
CompletableFuture.runAsync(copyMdc ? withMdc(sendEvent) : sendEvent, analytics);
   async 'analytics event sent' lines without requestId: 0 of 200

Сервис orders отправляет событие аналитики в отдельном пуле потоков. В первом прогоне все 200 строк «analytics event sent» записаны без идентификатора: MDC хранится в ThreadLocal потока, обработавшего запрос, а задача выполнялась в потоке пула, где MDC пуст. Обёртка, копирующая контекст при создании задачи и восстанавливающая его в потоке пула, вернула идентификатор во все 200 строк. В Spring это делает TaskDecorator у пула; в реактивном коде и с виртуальными потоками — context propagation из Micrometer или OpenTelemetry. Очистка MDC.clear() в finally обязательна: поток пула, не очистивший MDC, пометит чужим идентификатором следующую задачу — это хуже, чем отсутствие идентификатора.

Золотые сигналы: перцентили, а не средние

== golden signals from gateway logs
   traffic 200 requests, errors 1 (0.5%)
   latency avg 35 ms, p50 29 ms, p95 31 ms, p99 440 ms, max 441 ms

Четыре золотых сигнала Google SRE для сервиса: трафик (запросов в секунду), ошибки (доля неуспешных), задержка (распределение времени ответа) и насыщение (насколько заполнены ресурсы: пулы, очереди, CPU). Для сервисов, обрабатывающих запросы, то же называют RED — rate, errors, duration; для ресурсов — USE: utilization, saturation, errors, как в Metrics.

Задержку смотрят перцентилями. Средняя — 35 мс — выглядит нормально, медиана — 29 мс, p95 — 31 мс, а p99 — 440 мс: каждый 50-й запрос, у которого платёж медленный. Средняя смешала 196 быстрых запросов с 4 медленными и не показала ни тех, ни других. Перцентили считают по распределению — в метриках гистограммой, а не усреднением перцентилей разных экземпляров, которое математически бессмысленно. Задержку успешных и неуспешных запросов разделяют: быстрые ошибки улучшают среднюю задержку и прячут проблему.

Достаточно писать в лог идентификатор запроса в обработчике — в остальном коде он подставится сам.

MDC привязан к потоку. В демо все 200 строк, записанных в пуле асинхронных задач, остались без идентификатора. Контекст надо переносить в пулы (TaskDecorator, обёртка задачи), в сообщения брокера и в вызовы других сервисов, а в потоках пула — очищать после задачи.

  • Метрики — обнаружить и измерить, трассы — найти место, логи — понять, что случилось; сигналы связаны идентификаторами.
  • Без сквозного id ошибка в payments нашлась только с двумя своими строками; с X-Request-Id — путь через три сервиса.
  • MDC в ThreadLocal: 200 из 200 асинхронных строк без id; копирование контекста в задачу — 0 из 200, очистка в finally.
  • Логи — структурированные (JSON), в одном хранилище, с полями для фильтрации.
  • Золотые сигналы — трафик, ошибки, задержка, насыщение; средние 35 мс скрыли p99 440 мс.

На собеседовании

Чем отличаются логи, метрики и трассы?

Метрики — числовые ряды во времени: дёшево хранить, удобно строить графики и алерты, но без деталей отдельного запроса. Логи — отдельные события с подробностями: дорого хранить, удобно разбирать конкретный случай. Трассы — путь одного запроса через сервисы с длительностью каждого шага: показывают, где ушло время. Используются вместе: алерт по метрике, затем трасса, затем логи по идентификатору.

  • Связь сигналов: trace id в логах, exemplars в метриках.
  • Наблюдаемость — ответы на непредусмотренные вопросы; нужны детальные атрибуты.
  • Трассы обычно с выборкой, ошибки — сохранять всегда.

Как связать логи одного запроса в разных сервисах?

Сквозным идентификатором: его создаёт первый сервис, передаёт заголовком дальше, каждый сервис кладёт его в MDC, и он попадает в каждую строку лога. Логи структурированные и собраны в одно хранилище, где фильтр по идентификатору даёт путь запроса. Сейчас обычно используют trace id из W3C traceparent, который передаёт OpenTelemetry.

  • MDC — ThreadLocal: переносить в пулы и асинхронный код, очищать в finally.
  • Передавать и в сообщения брокера, и в фоновые задачи.
Почему в логах у части строк чужой requestId? 
ExecutorService pool = Executors.newFixedThreadPool(8);
void handle(Request r) {
    MDC.put("requestId", r.id());
    pool.submit(() -> {
        MDC.put("requestId", r.id());
        log.info("enrich started");
        enrich(r);                                   // может бросить исключение
        MDC.remove("requestId");
    });
}

Если enrich бросает исключение, MDC.remove не выполняется, и поток пула остаётся с идентификатором старого запроса. Следующая задача в этом потоке, которая не ставит свой id или пишет лог до установки, получит чужой идентификатор. Очистку делают в finally, а перенос контекста — одной обёрткой для пула (TaskDecorator), а не вручную в каждой задаче. Кроме того, MDC в потоке обработчика не очищается вовсе.

Что такое золотые сигналы и почему задержку смотрят перцентилями?

Трафик, ошибки, задержка и насыщение — минимальный набор для понимания здоровья сервиса. Задержку смотрят перцентилями, потому что средняя смешивает быстрые и медленные запросы: в демо средняя 35 мс при p99 440 мс. p99 показывает опыт каждого сотого пользователя, а у активного пользователя за сессию сотни запросов.

  • Перцентили не усредняют между экземплярами — считают по гистограмме.
  • Задержку ошибок отделяют от задержки успешных запросов.
  • RED для сервисов, USE для ресурсов.
