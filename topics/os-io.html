I/O Models

Платёжный сервис ждёт байты от банка, читает их и собирает ответ. ОС может усыпить отдельный поток, сообщить одному потоку о готовности многих сокетов или уведомить о завершённой операции. Готовность сокета ещё не означает, что весь ответ уже прочитан. Для файлов появляется отдельная граница: данные могут быть в памяти ядра, но ещё не сохранены на накопителе. Хорошая модель I/O учитывает и ожидание, и путь байтов, и момент, после которого можно подтвердить результат.

Банк прислал ответ, но цикл событий оставил половину в сокете

Платёжный сервис получил уведомление о готовности сокета. Обработчик прочитал два байта и снова ушёл ждать событие. В буфере ядра ещё есть остаток ответа, но нового уведомления нет. Банк уже сделал свою работу; сервис завис на собственной схеме ожидания.

В Linux epoll позволяет одному потоку следить за множеством дескрипторов. Уведомление говорит, где можно попытаться выполнить I/O. При флаге EPOLLET приложение должно забирать доступные данные до EAGAIN, а не рассчитывать на новое событие после каждого короткого чтения.

Проверим на четырёх байтах paid. IODemo.c использует пару локальных потоковых Unix-сокетов; второй конец играет роль банка. Режим events сначала выполняет опыт LT, затем ET. Фрагмент readiness(1), где edge == 1:

const char *mode = edge ? "ET" : "LT";
int sockets[2];
socketpair(AF_UNIX, SOCK_STREAM | SOCK_NONBLOCK, 0, sockets);
int watcher = epoll_create1(EPOLL_CLOEXEC);
struct epoll_event interest = {
    .events = EPOLLIN | (edge ? EPOLLET : 0), .data.fd = sockets[0]
};
epoll_ctl(watcher, EPOLL_CTL_ADD, sockets[0], &interest);
write(sockets[1], "paid", 4);                     // Банк уже передал весь короткий ответ.

int first_event = next_event(watcher);           // epoll_wait: timeout=0, возвращает число событий.
char first[3];
read_exact(sockets[0], first, 2);                 // Ошибка опыта: намеренно прочитали только pa.
printf("%s first event=%d, first read=%s\n", mode, first_event, first);
printf("%s event with unread bytes=%d\n", mode, next_event(watcher));
ET first event=1, first read=pa
ET event with unread bytes=0

Следующий epoll_wait с нулевым ожиданием вернул 0. Это количество уведомлений, а не байтов в сокете. Если здесь поставить бесконечное ожидание, обработчик может ждать новое поступление, пока уже пришедшие id остаются непрочитанными. Ни потеря пакета, ни долгий ответ банка для этого не нужны.

Демо предназначено для Linux. Из examples/os: cc -std=c11 -Wall -Wextra -Werror IODemo.c -o IODemo, затем ./IODemo events. Команды остальных режимов — в README. Все показанные результаты получены в Linux-контейнере. В фрагментах опущены проверки системных вызовов; полный файл проверяет ошибки и закрывает свои дескрипторы.

Дескриптор выбирает открытый ресурс, а dup сохраняет общую позицию файла

Файловый дескриптор — небольшое целое число, индекс в таблице процесса. Через него программа обращается к файлу, сокету, pipe и другим объектам ядра. Число 7 не описывает содержимое ресурса: после close оно может достаться новому сокету. Дескриптор нужно связывать с владельцем и временем жизни.

Для обычного файла таблица ведёт к open file description: записи ядра с текущей позицией и режимом открытого файла. dup создаёт другой дескриптор к той же записи. Поэтому два дескриптора двигают одну позицию. Два независимых open существующего файла, напротив, создают отдельные записи с отдельными позициями.

Режим descriptors записывает во временный файл paid и возвращает позицию к нулю. Затем сравнивает обычное чтение через два дескриптора с pread, которому передана явная позиция. Фрагмент:

int original = receipt_file("paid");             // Файл открыт, offset=0, в нём четыре байта.
int duplicate = dup(original);                   // Новый номер, та же запись открытого файла.
printf("different descriptor=%s\n", original != duplicate ? "true" : "false");

char first[3], second[3], positioned[3] = {0};
read_exact(original, first, 2);                   // pa: общая позиция стала 2.
read_exact(duplicate, second, 2);                 // id: продолжаем с общей позиции 2.
pread(duplicate, positioned, 2, 0);               // pa: позиционное чтение общую позицию не меняет.
off_t position = lseek(original, 0, SEEK_CUR);
printf("read original=%s\n", first);
printf("read duplicate=%s\n", second);
printf("pread offset 0=%s\n", positioned);
printf("shared position=%jd\n", (intmax_t) position);
different descriptor=true
read original=pa
read duplicate=id
pread offset 0=pa
shared position=4

read возвращает фактически прочитанное число байтов. Для потокового сокета это может быть часть сообщения: границы платежа задаёт протокол, а не один read. Возврат 0 при чтении с ненулевой длиной означает EOF. Для обычного файла дошли до конца; для сокета сосед завершил своё направление записи, и накопленные данные уже прочитаны.

Под капотом: одни флаги относятся к дескриптору, другие — к общей записи

O_NONBLOCK относится к состоянию открытого ресурса и разделяется между дескрипторами после dup. FD_CLOEXEC относится к отдельному дескриптору: он задаёт, закрыть ли эту ссылку при exec. Ресурс может пережить удаление имени файла из каталога, пока открыт дескриптор. Поэтому удалённый большой лог иногда продолжает занимать место, а унаследованный конец pipe — удерживать EOF. Наследование и EOF подробнее разобраны в Processes & Threads.

Неблокирующий read возвращает управление, а асинхронная операция сообщает завершение

Когда у банка пока нет ответа, блокирующий read может усыпить вызывающий поток. Ядро разбудит его после появления данных, завершения соединения или другого подходящего исхода. Поток ждёт, но не должен непрерывно тратить CPU. Пока данные уже доступны, тот же вызов способен вернуть их сразу.

У неблокирующего сокета попытка чтения пустого буфера возвращает -1 с EAGAIN или EWOULDBLOCK. Это «сейчас продвинуть чтение нельзя». Ответ банка может прийти позже. Цикл из бесконечных повторов read лишь превращает ожидание в расход CPU; нужен способ дождаться изменения готовности.

Неблокирующий режим и способ ожидания независимы. epoll_wait может блокировать поток, хотя все наблюдаемые сокеты неблокирующие. Это полезно: один поток спокойно спит, когда работы нет, затем обрабатывает готовые сокеты. Вызывать read по уведомлению безопаснее в неблокирующем режиме — готовность могла измениться или данные мог забрать другой читатель.

Асинхронность определяется тем, когда API сообщает результат. Реализация может использовать средства ядра или выполнять обычные операции в пуле потоков. Future само по себе не раскрывает этот механизм. Термин «синхронная запись» также встречается в другом смысле — сохранение данных на накопителе через O_SYNC. При обсуждении сначала уточняют: речь о потоке, об уведомлении или об устойчивости данных?

В JDK 21 Selector сообщает готовность каналов, а AsynchronousFileChannel завершает заданные файловые операции. Перенос блокирующего чтения в CompletableFuture меняет поток, на котором оно ждёт. Нагрузка и потребность в рабочих потоках остаются частью решения.

LT повторяет готовность, а ET требует дочитывать до EAGAIN

При множестве соединений платёжный сервис хочет дождаться любого ответа одним ожиданием. select получает наборы дескрипторов и отмечает готовые. Приложение после возврата обходит результат; наборы для нового вызова приходится подготовить снова. У обычного интерфейса select в Linux/glibc fd_set ограничен номерами меньше FD_SETSIZE = 1024. Это ограничение представления, а не общий предел файлов процесса.

poll получает массив записей с дескрипторами и интересующими событиями. Он снимает ограничение fd_set, но список передаётся и проверяется на каждом ожидании. epoll хранит постоянный набор интересов в ядре: приложение меняет его через epoll_ctl, а epoll_wait забирает готовые события. При большом числе в основном молчащих соединений это избавляет от повторного обхода всего списка приложением.

Level-triggered, LT сообщает готовность, пока условие сохраняется. Если в сокете осталось два байта, последующее ожидание снова может вернуть его. Edge-triggered, ET сообщает изменения и требует дисциплины чтения. Оно не обязано напоминать об оставшихся байтах после частичного чтения. Новые поступления тоже могут дать события, поэтому ET нельзя трактовать как ровно одно уведомление на сообщение или на соединение.

Полный вывод ./IODemo events добавляет два важных края: чтение до данных и чтение после закрытия соседа. Демо после первого короткого чтения намеренно делает ещё один epoll_wait, затем само дочитывает остаток:

read_exact(sockets[0], remaining, 2);             // Забираем id даже без нового события ET.
const char *drained = empty_read(sockets[0]);      // Следующий read получает EAGAIN.
printf("%s remaining read=%s, drained=%s\n", mode, remaining, drained);

close(sockets[1]);                               // У банка больше нет открытого конца этой пары.
int close_event = next_event(watcher);
ssize_t final_read = read_once(sockets[0], &byte, 1);
printf("%s event after close=%d, read=EOF\n", mode, close_event);

LT first event=1, first read=pa
LT event with unread bytes=1
LT remaining read=id, drained=EAGAIN

Готовность на чтение означает также возможность получить EOF или ошибку. При EOF соединение убирают из наблюдения и закрывают по правилам протокола. Иначе готовый EOF способен бесконечно будить цикл. При HUP ещё могут оставаться непрочитанные байты; потерять их немедленным закрытием — тоже ошибка.

Обычный обработчик читает порциями до EAGAIN, накапливает состояние протокола и обрабатывает уже целые сообщения. Если ответ банка содержит длину и тело, первая готовность может принести только часть длины. Обработчик сохраняет её и продолжает позже. Запись симметрична: короткий write и EAGAIN оставляют неотправленный хвост. Интерес к записи включают, когда хвост есть, и снимают после его отправки.

Под капотом: epoll уменьшает обход, но обработка готовых событий всё равно стоит работы

У epoll есть набор зарегистрированных интересов и список готовности. События источника делают соответствующие записи готовыми; ожидание возвращает их порциями. Это не обещание O(1) для всего сервера: нужно зарегистрировать ресурсы, обработать каждую готовую запись, скопировать результат и выполнить бизнес-код. Когда активны почти все сокеты, стоимость работы с ними никуда не исчезает.

EPOLLONESHOT выключает уведомления для конкретной регистрации после события; её нужно вновь активировать через EPOLL_CTL_MOD. Это помогает организовать владение обработчиком. Регистрация после dup также связана с открытым ресурсом, а не только с числовым fd. При передаче между потоками важно удалить ненужные регистрации и подтвердить, кто ещё удерживает ресурс.

Файловое чтение идёт через page cache, а write не обещает сохранения на накопителе

Сервис читает файл квитанции. В обычном буферизованном I/O ядро ищет нужные страницы в page cache. Если они уже есть, данные можно скопировать в пользовательский буфер без чтения накопителя. Если их нет, нужны запрос к устройству и ожидание. Это кеш файловых данных в RAM; кеши CPU и TLB из Virtual Memory решают другие задачи.

На обычном файле O_NONBLOCK в Linux не устраняет ожидание устройства. Такие файлы не дают epoll модель готовности к промаху файлового кеша: попытка обычной регистрации файла через epoll_ctl завершается EPERM. Следить за сокетами и читать холодный файл в том же цикле — способ остановить все соединения одним дисковым ожиданием. Здесь нужен отдельный исполнитель или подходящее асинхронное файловое I/O.

Буферизованный write обычно копирует данные в память ядра и помечает страницы изменёнными. Успешный возврат сообщает о принятой работе, а не о пережитом отключении питания. Позже writeback переносит изменения на накопитель. На этом этапе тоже могут обнаружиться ошибки: свободное место, сбой устройства или отложенное выделение блоков.

Для замены квитанции часто сначала полностью пишут временный файл, синхронизируют его, переименовывают в итоговое имя и синхронизируют каталог. Переименование внутри поддерживающей файловой системы помогает атомарно заменить наблюдаемое имя, а синхронизация отвечает за устойчивость. Это разные свойства. Протокол зависит от файловой системы и требований; он не превращает несколько файлов или операцию с банком в одну транзакцию.

Чтение своего текста после write подтверждает видимость в работающей ОС. Такое демо не проверяет сохранность при потере питания. Поэтому здесь важен контракт fsync, а не опыт «записали, прочитали, всё хорошо». Большой файловый кеш также расходует RAM и участвует в давлении памяти контейнера.

Под капотом: mmap, direct buffer и O_DIRECT меняют разные границы

mmap позволяет обращаться к файловым страницам через адресное пространство. Он убирает явное read с копированием в отдельный буфер, но промах страницы по-прежнему может потребовать I/O и page fault. Запись в частное отображение создаёт частные данные; общий файл автоматически от неё не меняется.

Прямой ByteBuffer в Java находится вне обычного heap и может сократить промежуточные копии JVM. Это не флаг O_DIRECT. O_DIRECT меняет путь файлового I/O относительно page cache и предъявляет требования к выравниванию и поддержке файла. Сам по себе он также не заменяет гарантию синхронного сохранения. Эти способы выбирают по измеренной проблеме, а не по слову «direct».

sendfile передаёт файл без буфера приложения, но продолжение остаётся его обязанностью

Квитанция уже лежит в файле, и сервис должен отдать её клиенту. Обычный путь read → write переносит байты из page cache в буфер приложения, затем из него в сокет. Если приложение не меняет содержимое, этот круг создаёт лишнюю работу. sendfile поручает перенос ядру и убирает промежуточный буфер приложения.

Режим sendfile из IODemo отправляет семь байтов paid-42. Для первой операции он намеренно запрашивает только четыре. В sendfile передан отдельный offset: ядро обновляет его, а общая позиция файла остаётся прежней. После чтения первой части демо продолжает с сохранённого места. Фрагмент:

int file = receipt_file("paid-42");              // Содержимое готово, общая позиция файла = 0.
int sockets[2];
socketpair(AF_UNIX, SOCK_STREAM, 0, sockets);     // Блокирующая локальная пара; семь байтов помещаются.
off_t offset = 0;
ssize_t first = sendfile(sockets[0], file, &offset, 4);
off_t file_position = lseek(file, 0, SEEK_CUR);
printf("first sent=%zd, explicit offset=%jd, file position=%jd\n",
       first, (intmax_t) offset, (intmax_t) file_position);
char head[5];
read_exact(sockets[1], head, (size_t) first);     // Получатель забирает уже отправленную часть.
printf("receiver first=%s\n", head);

ssize_t resumed = 0;
while (offset < 7) {
    ssize_t count = sendfile(sockets[0], file, &offset, (size_t) (7 - offset));
    if (count == -1 && errno == EINTR) continue;
    require(count > 0, "resume sendfile");       // Здесь маленькая блокирующая пара, есть место.
    resumed += count;                          // offset уже изменён самим sendfile.
}
char tail[8];
read_exact(sockets[1], tail, (size_t) resumed);
printf("resumed sent=%zd, explicit offset=%jd\n", resumed, (intmax_t) offset);
printf("receiver tail=%s\n", tail);
first sent=4, explicit offset=4, file position=0
receiver first=paid
resumed sent=3, explicit offset=7
receiver tail=-42

Получатель увидел обе части. Возврат sendfile на стороне отправителя сообщает о переданных байтах по контракту системного вызова; обработку квитанции клиентом подтверждает уже протокол. Если повторить отправку с offset=0, клиент получит дублированное начало. Если передать в Linux sendfile NULL вместо указателя offset, операция будет пользоваться общей позицией файла и двигать её.

На реальном неблокирующем сокете sendfile может передать меньше запрошенного или вернуть EAGAIN. Приложение сохраняет позицию и остаток, ждёт готовности к записи и продолжает. Холодный исходный файл при этом может потребовать дискового I/O даже при неблокирующем сокете. Оптимизация копий и устранение ожиданий — отдельные задачи.

В Java FileChannel.transferTo(position, count, target) позволяет реализации использовать эффективный путь ОС. Метод может передать только часть диапазона, в том числе ноль байтов, и не меняет позицию исходного канала. Буфер из allocateDirect и вызов transferTo не дают одинакового обещания; ни один из них не гарантирует отсутствие всех копий. Контракт есть в JDK 21 FileChannel.

Если приложение шифрует или сжимает байты само, содержимое нужно преобразовать, и простой путь «исходный файл → сокет» уже недостаточен. TLS с обработкой в ядре и аппаратные возможности могут менять реализацию, но это требует отдельной поддержки. mmap тоже не равен sendfile: он меняет способ доступа к файлу в адресном пространстве, а передачу в сокет ещё нужно выполнить.

Цикл событий защищают от долгой работы, лишней готовности и неограниченных буферов

Неблокирующие сокеты позволяют одному потоку обслуживать много ожиданий банка. Но тот же поток может надолго занять CPU разбором огромного ответа, ждать блокировку или читать холодный файл. Тогда готовые соединения стоят в очереди. Реактор отделяет ожидание I/O от обработки, а для тяжёлой работы нужны ограниченные исполнители и понятный возврат результата в цикл.

Сокет обычно готов к записи, когда в выходном буфере есть место. Если постоянно подписаться на EPOLLOUT при пустой очереди данных, цикл может просыпаться без полезной работы. Когда клиент читает медленно, хвосты ответов растут в памяти приложения. Нужно ограничить объём на соединение и на сервис, перестать принимать лишнюю работу или замедлить производителя — это backpressure.

Для диагноза сопоставляют профиль CPU и стеки, задержку цикла, размеры очередей, счётчики байтов и состояние сокетов. В Linux ss показывает соединения и очереди, lsof — открытые ресурсы, трассировка системных вызовов — ожидания и короткие операции. Сама трассировка влияет на работу, поэтому её выбирают для конкретного вопроса. Команды и чтение системных логов — в Linux Basics; TCP и его подтверждения — в TCP & UDP.

У Java NIO неблокирующий SocketChannel.read может вернуть 0 без EOF, а -1 означает EOF: код Java использует другой контракт, чем POSIX read. FileChannel не регистрируется в Selector. Виртуальные потоки дают удобную последовательную запись ожидающего кода; они также не ускоряют накопитель и не убирают лимит живых запросов. Выбор между ними, реактором и пулом делают по модели нагрузки и сложности состояния, а не по одному числу потоков.

Ограничение работы за один проход помогает справедливости: один непрерывно активный сокет не должен захватить весь цикл. В ET при остановке до EAGAIN нужно сохранить сокет как готовый в очереди самого приложения и продолжить позже. Просто вернуть управление в epoll_wait — значит снова оставить уже доступные данные без владельца. Модель I/O заканчивается там, где начинается планирование вашей работы; его тоже нужно спроектировать.

Дескриптор даёт доступ к открытому ресурсу; несколько дескрипторов могут делить его позицию и флаги. Готовность помогает выбрать момент попытки I/O, а результат операции сообщает о реально обработанных байтах. Page cache связывает файловое I/O с памятью, fsync — с устойчивым хранением. Zero-copy сокращает путь данных, сохраняя обязанности приложения по продолжению, ошибкам и ограничению нагрузки.

На собеседовании

Чем блокирующий I/O отличается от неблокирующего и асинхронного?

Блокирующая операция допускает ожидание в вызывающем потоке. Неблокирующая пробует выполнить работу сейчас и возвращает доступный результат либо признак «пока нельзя». Чтобы не крутить пустые попытки, можно ждать готовность многих сокетов через select или epoll, а затем читать самому. Асинхронный API принимает операцию и позже сообщает её завершение. Поэтому epoll — уведомление о готовности, а callback завершённого read — результат конкретной операции. В обоих случаях сообщение протокола может потребовать нескольких операций.

  • Асинхронный API может опираться на пул блокирующих работников. Проверяю, где находятся очередь, лимит параллелизма и выполнение обработчиков; Future не показывает внутреннее устройство.
  • Отмена ожидания результата и отмена операции различаются. Особенно при записи проверяю, какие байты уже могли уйти, прежде чем повторять платёж.
  • Неблокирующий режим относится к конкретному пути I/O. Он не запрещает обработчику взять обычный замок или выполнить блокирующую файловую операцию.

Почему epoll лучше select при множестве соединений? Что меняется между LT и ET?

У select приложение каждый раз передаёт наборы, получает изменённый результат и обходит его. Epoll хранит регистрацию в ядре и возвращает готовые записи. Это особенно помогает, когда соединений много, а активна малая часть. Но обработка всех активных соединений всё равно стоит времени. LT повторяет уведомление, пока готовность сохраняется. В ET после события я работаю с неблокирующим ресурсом до EAGAIN, иначе остаток данных может остаться без нового уведомления. EOF и ошибки тоже требуют обработки готовности.

  • Число событий не равно числу сообщений банка. Поступления могут объединяться, сообщение дробится чтениями, а формат хранит состояние отдельно.
  • Если ограничил чтение ради справедливости и ещё не дошёл до EAGAIN, добавляю продолжение в очередь готовых задач приложения. Уже имеющиеся байты не требуют нового события ядра.
  • При нескольких обработчиках нужна модель владения соединением. EPOLLONESHOT помогает раздать обработку и затем явно восстановить регистрацию.
ET-обработчик читает максимум 64 КиБ, затем снова ждёт epoll. Где ошибка и как сохранить ограничение?

Ограничение полезно для справедливости, но после него в сокете могут остаться данные. Если EAGAIN ещё не получен, сокет остаётся готовым для приложения. Нужно поставить его продолжение в собственную очередь и дать другим соединениям поработать, затем вернуться к чтению. Ожидать только новое уведомление ET в этой точке опасно. После полного исчерпания доступного снова можно полагаться на ожидание ядра.

Что делает page cache и почему успешного write недостаточно для сохранности квитанции?

Page cache держит страницы файлов в RAM ядра. Повторное чтение может обойтись без накопителя. При обычной записи ядро принимает байты в изменённые страницы и записывает их позже. Поэтому успешный write и чтение своего текста ещё не подтверждают сохранность после сбоя системы. Для нужной границы устойчивости использую синхронизацию файла и проверяю результат; при создании или замене имени может понадобиться синхронизация каталога. Flush пользовательского буфера решает только часть пути до хранения.

  • Атомарная видимость замены имени и устойчивость после сбоя — разные свойства. Rename не заменяет запись и синхронизацию подготовленного содержимого.
  • Ошибки writeback могут появиться позже первого успешного write. Подтверждение клиенту должно учитывать результат требуемой синхронизации, а не только попадание байтов в кеш.
  • Сброс кеша ради теста меняет рабочую нагрузку всей системы. Для оценки холодного пути изолирую условия и сопоставляю их с реальным распределением доступа.

Что означает zero-copy? Достаточно ли один раз вызвать transferTo?

При отправке готового файла zero-copy обычно убирает промежуточные копии через буфер приложения. Sendfile делает перенос внутри ядра, а Java transferTo позволяет реализации выбрать эффективный путь. Аппаратная передача данных и работа сетевого стека всё равно есть. Один вызов может передать лишь часть или не продвинуться сейчас; я храню позицию и остаток, продолжаю после готовности и обрабатываю ошибки. Завершение передачи отправителем ещё не говорит, что клиент обработал квитанцию.

  • При нулевом результате нельзя бесконечно повторять transferTo без изменения условий. Проверяю размер исходного файла и состояние получателя, сохраняю продолжение и выбираю ожидание или поддерживаемый запасной путь.
  • Если передаваемые страницы ещё используются путём zero-copy, изменение исходного диапазона опасно. Выдаю неизменяемую версию квитанции и заменяю её новым файлом, сохраняя время жизни старой версии.
  • Сжатие и шифрование в приложении требуют преобразовать байты. Польза прямой передачи зависит от места преобразования и поддержки выбранного стека.
