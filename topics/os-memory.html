Virtual Memory

Платёжный сервис обращается к своим виртуальным адресам, а ОС решает, какие страницы физической памяти за ними стоят. Большой диапазон адресов можно зарезервировать раньше, чем понадобится RAM для его содержимого. При первом доступе ядро достраивает отображение, при нехватке памяти освобождает страницы, а иногда завершает процесс. Поэтому размер heap, виртуальная память и память контейнера отвечают на разные вопросы. Для задержки платежа важно понять, что именно пришлось сделать при обращении к данным.

Сервис получил 4 МиБ адресов, но RAM понадобилась при записи

Сервис резервирует область для пакета квитанций. В мониторинге растёт виртуальный размер процесса, хотя пакет ещё пуст. Команда пугается: «мы уже заняли всю память». Но выделенный диапазон адресов и физические страницы с данными появляются в разное время.

Виртуальное адресное пространство — набор адресов, к которым процесс может обращаться по своим правилам. Ядро хранит области отображения: начало, конец, права, связь с файлом или анонимной памятью. В Linux такую область называют VMA. Успешный mmap создаёт отображение; обычная анонимная память заполняется по требованию. Её начальное содержимое — нули.

Проверим это без Java-аллокатора. MemoryDemo.c — короткая программа для Linux. Режим resident резервирует 1024 базовые страницы, читает по байту из каждой, затем записывает туда 1. RSS берётся из /proc/self/smaps только для этой области. Счётчики page fault берутся через getrusage для процесса. Фрагмент режима:

Mapping m = mapping(1024);                    // mmap: частная анонимная область, права RW.
printf("page_bytes=%zu, mapped_bytes=%zu\n", m.page, m.bytes);
printf("reserved rss_kib=%lu\n", stats(m.data).rss);

struct rusage before = usage();
unsigned long sum = 0;
for (size_t offset = 0; offset < m.bytes; offset += m.page)
    sum += m.data[offset];                    // volatile: каждое чтение действительно выполняется.
struct rusage after_read = usage();
printf("read sum=%lu, rss_kib=%lu\n", sum, stats(m.data).rss);
printf("read minor_faults_increased=%s, major_faults_delta=%ld\n",
       after_read.ru_minflt > before.ru_minflt ? "true" : "false",
       after_read.ru_majflt - before.ru_majflt);

before = usage();
for (size_t offset = 0; offset < m.bytes; offset += m.page)
    m.data[offset] = 1;                       // Один байт делает нужной целую физическую страницу.
struct rusage after_write = usage();
printf("write rss_kib=%lu, minor_faults_increased=%s\n", stats(m.data).rss,
       after_write.ru_minflt > before.ru_minflt ? "true" : "false");

В проверенном Linux-запуске базовая страница равна 4096 байт. При чтении ядро подставило общую нулевую страницу; она не вошла в RSS этой анонимной области. После записи каждой странице понадобились свои данные, и RSS области вырос до 4096 КиБ. Мы записали всего 1024 байта, но разместили их на 1024 разных страницах.

Рост minor faults говорит, что ядру пришлось обслужить обращения. Major faults не выросли: читать данные с накопителя здесь не требовалось. Точное число minor faults программа не обещает — счётчик относится ко всему процессу, включая его служебную работу. Размер RSS всей программы тоже больше показанного: код, стек и библиотека C живут в других отображениях.

Сборка и запуск на Linux: cc -std=c11 -Wall -Wextra -Werror MemoryDemo.c -o MemoryDemo, затем ./MemoryDemo resident из examples/os. Все три режима ниже проверены в Linux-контейнере. В README описаны условия: две защитные страницы отделяют измеряемую VMA, а MADV_NOHUGEPAGE отключает для неё transparent huge pages. Размер страницы программа узнаёт у ОС; число 4096 не универсально для всех машин.

MMU переводит номер страницы, а смещение внутри неё сохраняется

Виртуальная память позволяет каждому процессу видеть своё пространство адресов. Соседние виртуальные страницы могут лежать в разных местах RAM; ОС собирает для программы непрерывный диапазон из отдельных физических фреймов. Несколько процессов также могут отображать один фрейм — например, с кодом общей библиотеки. Сам числовой адрес без процесса ещё не определяет данные.

CPU делит виртуальный адрес на номер страницы и смещение. Для модели со страницей 4 КиБ адрес 12 345 — это страница 3 и смещение 57: 3 × 4096 + 57. Таблица страниц связывает номер виртуальной страницы с номером физического фрейма и правами доступа. Если страница 3 отображена во фрейм 9, физический адрес получается 9 × 4096 + 57 = 36 921. Смещение не меняется.

MMU — аппаратный механизм перевода и проверки доступа. В обычном случае приложение не вызывает ядро на каждое чтение переменной. Переводы кешируются в TLB. Если нужного перевода там нет, аппаратура на распространённых серверных архитектурах проходит таблицу страниц и заполняет TLB. Если запись присутствует и разрешает доступ, инструкция продолжает работу. Промах TLB может стоить времени, но сам по себе не является page fault.

Настоящие таблицы страниц обычно многоуровневые. Верхний уровень ведёт к нижнему; для незадействованных диапазонов нижние таблицы можно не создавать. Это сокращает цену огромного разреженного адресного пространства, но сами таблицы всё равно занимают память. Большие страницы позволяют описать больше памяти меньшим числом переводов и снизить давление на TLB. Цена — более крупная единица размещения, внутренние потери и дополнительные сложности выделения. Эффект зависит от рабочей нагрузки.

Кеши CPU хранят другое: инструкции и данные небольшими линиями, а не соответствия адресов. После получения перевода нужные байты могут оказаться в L1/L2/L3 или потребовать обращения к RAM. В модели важно различать кеш перевода и кеш данных; реальная аппаратура может выполнять часть работы параллельно. Последовательный обход платежей обычно использует локальность лучше, чем прыжки по большой цепочке объектов.

Под капотом: переключение процесса и соседние записи потоков влияют на разные кеши

TLB должен различать адресные пространства. Метки ASID/PCID позволяют аппаратуре сохранить переводы нескольких процессов; полное очищение TLB при каждом переключении не обязательно. Если ядро меняет отображение, устаревшие переводы нужно инвалидировать, в том числе на других CPU, которые им пользуются. Такая согласованность требует работы и иногда межпроцессорных уведомлений.

У потоков одного процесса общий адресный мир, но два счётчика платежей могут попасть в одну линию кеша данных. Потоки пишут в разные счётчики, а механизм согласованности кешей всё равно передаёт право записи на одну линию между CPU. Это false sharing: замка на уровне Java может не быть, а пропускная способность падает. Правила видимости и порядка Java отдельно задаёт JMM; наличие кеша не заменяет эти правила.

Page fault бывает штатной работой ядра и нарушением прав доступа

Page fault возникает, когда аппаратура не смогла выполнить доступ по текущей записи таблицы страниц: страницы нет в отображении CPU либо права записи не подходят. Управление переходит в ядро. Оно проверяет область памяти и решает, можно ли исправить состояние. Если можно, ядро подготавливает страницу и повторяет исходную инструкцию. Код платежа может вообще не узнать, что между двумя его командами поработала ОС.

В первом опыте VMA с самого начала разрешала чтение и запись. Но сразу после mmap ещё не было готовых переводов для каждого адреса. При чтении хватило общей нулевой страницы. Для записи потребовалась отдельная страница, в которой сервис может хранить своё значение. Пройдём один адрес; в демо таких адресов 1024:

Minor page fault обслуживается без I/O: выделение нулевой страницы, COW, установка перевода на уже загруженную страницу. Major page fault требует I/O. Это может быть чтение страницы файла, а не только swap. Наоборот, чтение файла, уже находящегося в page cache, способно вызвать minor fault для нового отображения. Слово fault описывает переход к ядру; оно не означает, что программа написана с ошибкой.

Посмотрим границу с настоящим нарушением доступа. Режим protect создаёт ребёнка и меняет его VMA на чтение. У родителя своё адресное пространство. Фрагмент:

Mapping m = mapping(1);                       // Сначала область разрешает чтение и запись.
m.data[0] = 41;
pid_t child = fork();
if (child == 0) {
    struct rlimit no_core = {0, 0};
    setrlimit(RLIMIT_CORE, &no_core);           // Для этого опыта дамп памяти не сохраняется.
    mprotect((void *) m.data, m.bytes, PROT_READ);
    m.data[0] = 99;                            // Запрет в VMA: ядро не разрешит запись через COW.
    _exit(2);                                 // До этой строки ребёнок не дойдёт.
}
reap(child, &status);                         // waitpid получает причину завершения.
printf("child terminated by SIGSEGV=%s\n",
       WIFSIGNALED(status) && WTERMSIG(status) == SIGSEGV ? "true" : "false");

В коде выше опущены проверки системных вызовов; в полном демо они есть. У обычной Java-программы доступ к массиву контролирует JVM, а не этот C-код. Ошибка индекса даёт Java-исключение. Защита страниц находится ниже языка и ограничивает доступ процесса независимо от проверки бизнес-кода.

После fork RSS считает общую страницу дважды, а PSS делит её стоимость

Сервис запускает вспомогательную программу для квитанции. На уровне Unix fork создаёт отдельное адресное пространство с исходным содержимым родителя; его API разобран в Processes & Threads. Копировать всю RAM сразу дорого. Copy-on-write позволяет сначала отображать частные страницы обоих процессов на те же фреймы, временно запретив запись в PTE. Сама VMA при этом может оставаться доступной для записи.

Когда ребёнок меняет страницу, ядро видит допустимую запись в COW-страницу. Оно создаёт для ребёнка копию, переносит туда исходные данные и меняет его PTE. Родитель продолжает видеть прежний фрейм. Положение программы и числовой виртуальный адрес у ребёнка сохранились, а физическое место данных стало другим.

Режим cow из MemoryDemo работает с одной страницей. До fork родитель записывает 41. Ребёнок измеряет область, записывает 99 и измеряет снова. Родитель ждёт его выхода и проверяет свою страницу. Фрагмент с ключевыми действиями:

Mapping m = mapping(1);
m.data[0] = 41;                                // Фрейм уже существует до fork.
pipe(ends);                                  // Маленькое сообщение: передадим числовой адрес.
pid_t child = fork();
if (child == 0) {
    close(ends[0]);
    Stats shared = stats(m.data);
    printf("child before write: rss_kib=%lu, pss_kib=%lu\n", shared.rss, shared.pss);
    m.data[0] = 99;                            // COW: тот же виртуальный адрес, свой физический фрейм.

В этом опыте у каждой общей страницы одно отображение на процесс и базовый размер 4 КиБ. У больших страниц, повторных отображений и специальных видов памяти учёт сложнее. Для оценки цены набора JVM PSS полезнее простой суммы RSS; для проверки лимита контейнера нужен счётчик самого контейнера.

Под капотом: частное отображение файла тоже может создавать анонимные страницы

MAP_PRIVATE описывает видимость изменений, а не обещает сразу отдельную физическую копию всего файла. Для чтения процесс может использовать страницу файла из общего page cache. Запись создаёт частную анонимную копию; исходный файл от неё не меняется. MAP_SHARED даёт другую семантику обмена изменениями. Нужную видимость между участниками и устойчивость на накопителе всё равно определяют отдельно: общая страница не означает, что операция уже долговечно сохранена.

Ядро освобождает восстанавливаемые страницы, а рабочий набор определяет цену подкачки

При росте нагрузки квитанции, объекты платежей и файлы конкурируют за RAM. Ядру нужно найти место для новых страниц. Reclaim освобождает память, которую можно убрать или сохранить вне RAM. У разных страниц разная цена восстановления. Чистую страницу файла можно отбросить и позже прочитать снова. Изменённым данным нужен способ сохранить содержимое.

Swap — место для содержимого вытесненных страниц, в типичном случае область на накопителе. Доступ к выгруженным данным требует их вернуть. Для приложения адрес сохраняется; меняются состояние перевода и местонахождение данных. Использование swap не начинается по простому правилу «свободная RAM дошла до нуля»: ядро учитывает давление, активность страниц и относительную цену их сохранения. Наличие занятого swap само по себе не доказывает, что текущие платежи тормозят.

Рабочий набор — страницы, которые задача активно использует за рассматриваемый промежуток. Если он помещается в доступную RAM, холодные страницы могут оставаться в swap без постоянного чтения. Если рабочий набор больше доступной памяти, обращения непрерывно возвращают только что вытесненные страницы. Получается thrashing: сервис тратит время на перемещение памяти, очередь запросов растёт, а CPU может оставаться свободным.

Отключение swap устраняет именно путь выгрузки анонимных данных. Чистые страницы файлов всё ещё можно вытеснять; при новом доступе чтение вернётся. Без swap ядру может раньше стать нечего освобождать. Увеличение swap тоже не делает активный рабочий набор быстрым: оно расширяет пространство хранения, а задержка накопителя остаётся.

Для Java здесь две отдельные работы. GC находит недостижимые объекты внутри heap. Ядро управляет физическими страницами процесса. После GC свободное место heap может оставаться в выделенных JVM страницах, поэтому RSS не обязан сразу упасть. Вернёт ли JVM часть памяти ОС и когда, зависит от сборщика и его состояния. Разбор GC и GC Tuning дополняет эту границу; page cache, I/O и гарантии записи — в I/O Models.

При исчезновении JVM сначала различают ошибку выделения и OOM killer

У сервиса задан -Xmx512m, контейнер имеет лимит 768 МиБ. В один момент процесс исчезает, хотя heap на последнем графике занимал 300 МиБ. Лимит heap не ограничивает всю память процесса. Вне него находятся стеки потоков, Metaspace, код JIT, прямые буферы и другие нативные выделения. Контроллер cgroup учитывает также другие процессы группы и часть памяти ядра и файлового кеша.

OutOfMemoryError сообщает JVM: конкретную потребность в памяти выполнить не удалось. Например, после попыток GC нельзя выделить объект в heap; отдельные варианты связаны с Metaspace, прямыми буферами или созданием потока. OOM killer работает в ядре: в условиях нехватки он выбирает процесс и посылает SIGKILL, освобождая его ресурсы. JVM не получает Java-исключение и не выполняет shutdown hooks.

В cgroup v2 memory.max задаёт жёсткую границу учтённой памяти. Если очередное выделение упирается в неё и reclaim не помогает, OOM может произойти внутри этой группы даже при свободной памяти на хосте. memory.high задаёт другую границу: заставляет активнее освобождать память и замедляет выделения, сам по себе OOM killer не вызывает. Поэтому задержка запросов может вырасти ещё до убийства процесса. Это поведение описано в документации cgroup v2.

Код выхода 137 в распространённой записи оболочки означает завершение сигналом 9: 128 + SIGKILL. По одному коду причина не ясна — SIGKILL мог послать и оператор. Для подтверждения OOM нужны события контейнера, счётчик oom_kill в memory.events и сообщения ядра, когда они доступны. У Java OOME, наоборот, ищут текст ошибки, профиль памяти и данные JVM. Перезапуск возвращает доступность, но не устраняет причину роста.

Под капотом: успешное резервирование не обещает RAM для всех будущих записей

Политика overcommit определяет, сколько будущих обязательств по памяти ядро разрешает принять. При допускающей overcommit политике malloc или mmap могут успешно вернуть адреса, хотя одновременно заполнить все диапазоны физической памятью и swap не получится. Проблема обнаружится позже, при необходимости подготовить страницы. Есть также отказы выделения с ENOMEM; OOM killer не вызывается на всякой неудачной операции. Успешный возврат указателя, первая запись и последующий рост нагрузки — три разных момента.

При OOM ядро выбирает жертву по своим правилам с учётом доступного домена и настроек вроде oom_score_adj; правило «всегда убить самый большой процесс» слишком грубо. В cgroup v2 memory.oom.group позволяет рассматривать нагрузку как группу при убийстве, чтобы её часть не продолжила работу после потери соседей. Это эксплуатационное решение о границе отказа. Для платежа оно не отменяет уже сохранённую транзакцию или отправленное списание.

Если после прогрева выросли minor faults, это может быть обычное освоение новых страниц. Если вместе с задержкой растут major faults и давление памяти, ищут вытеснение рабочего набора и чтение данных. Если процесс исчез без Java-ошибки, проверяют cgroup и причину сигнала. На следующем шаге выбирают конкретное действие: сократить одновременно живые пакеты платежей, ограничить кеш и буферы, убрать утечку или увеличить действительно недостающий ресурс.

Виртуальный адрес задаёт место в пространстве процесса. Таблица страниц связывает его с физической памятью и правами; TLB ускоряет этот перевод, кеш CPU — доступ к данным. Page fault может штатно подготовить страницу, вернуть её с накопителя или обнаружить запрещённый доступ. RSS показывает резидентность, PSS — долю разделяемой памяти, а cgroup — свой учёт группы. Память Java heap составляет только часть этой картины.

На собеседовании

Чем виртуальная память отличается от RSS и почему сумма RSS завышает расход RAM?

У процесса свои виртуальные адреса; ОС отображает их на физические страницы и проверяет права. Диапазон можно зарезервировать раньше, чем появятся отдельные страницы с данными. RSS показывает резидентные страницы отображений процесса, а общую страницу считает целиком. Поэтому два процесса после fork могут каждый иметь RSS 4 КиБ для одного общего фрейма. PSS делит его стоимость между участниками: в этом случае по 2 КиБ. После записи через COW данные расходятся, и цена физической памяти растёт.

Для контейнера я отдельно смотрю учёт cgroup: в нём учитывается вся группа и дополнительные виды памяти. Большой VIRT без роста резидентных данных ещё не означает нехватку RAM. Низкий Java heap тоже не гарантирует, что процесс помещается в свой лимит.

  • После освобождения объекта память может остаться у аллокатора и использоваться повторно. Низкая живая масса объектов и стабильный RSS совместимы; для утечки ищу продолжающийся рост и владельца данных.
  • Подробное сканирование smaps даёт более точный снимок отображений, чем некоторые быстрые счётчики RSS. На большом процессе цена такого снимка сама может стать заметной.
  • На NUMA-машине важна и близость физической памяти к CPU. First touch влияет на размещение страниц; миграция потока может сделать ту же резидентную память дороже по времени доступа.

Любой ли page fault читает диск? И чем он отличается от промаха TLB?

Промах TLB означает, что кеш перевода не нашёл нужное соответствие. MMU может получить его из таблицы страниц и продолжить работу без обращения к ядру. Page fault возникает, когда по текущей записи выполнить доступ нельзя. Ядро либо исправляет отображение и повторяет инструкцию, либо сообщает об ошибке доступа. Minor fault обходится без I/O — например, при первом выделении страницы или COW. Major fault требует I/O, в том числе для страницы файла. Отдельно есть промах кеша CPU: перевод уже найден, но нужных байтов нет в быстром кеше данных.

  • Виртуальный диапазон может быть допустим, хотя текущая PTE строже его VMA. При COW это нужно для перехвата первой записи. Ошибка определяется допустимостью доступа и возможностью ядра подготовить страницу.
  • Большое число minor faults само по себе не доказывает проблему. Важны стоимость обслуживания, скорость их появления и фаза нагрузки: первый проход по новому буферу отличается от постоянного вытеснения.
  • Обычные размер страницы и размер линии кеша относятся к разным механизмам. Большие страницы уменьшают число переводов, но не устраняют false sharing у часто меняемых счётчиков.
После fork PTE только для чтения. Ребёнок пишет 99: предскажи исход с прежней VMA и после mprotect(PROT_READ).

В cow VMA оставалась доступной для записи. Read-only PTE помогала ядру заметить первую запись и сделать частную копию. В protect mprotect изменил права самой VMA на PROT_READ. Разрешить запись созданием копии уже нельзя: приложение запретило её для этого диапазона. При стандартном действии SIGSEGV ребёнок завершается, а память родителя остаётся доступной по его собственным правилам.

Почему контейнер убили при свободном heap и поможет ли добавить swap?

Лимит -Xmx относится к Java heap, а контейнер расходует ещё нативную память, стеки, буферы и файловый кеш по правилам cgroup. Я проверяю события OOM и состав памяти группы. При убийстве ядром JVM получает SIGKILL: Java OutOfMemoryError и shutdown hooks могут вообще не появиться. Код 137 только указывает на сигнал в обычной записи оболочки, поэтому причину подтверждаю отдельно.

Swap может хранить холодные анонимные страницы и дать больше места для активной работы. Если весь активно используемый набор больше доступной RAM, страницы будут постоянно уходить и возвращаться, а задержка вырастет. Для платёжного сервиса сначала выясняю размер рабочего набора и направление роста. Увеличение места хранения не устраняет утечку и не ускоряет постоянный обмен с накопителем.

  • Обрабатываемый Java OOME не даёт безопасного способа «продолжить как обычно»: обработчику тоже может понадобиться память. План получения диагностики и политика завершения задаются заранее.
  • У группы может быть собственный лимит swap и ограничения родительской cgroup. Размер swap хоста ещё не доказывает, что он доступен конкретному сервису.
  • Предварительное касание страниц переносит часть затрат первого доступа на старт и раньше проверяет доступность памяти. Это меняет время проявления затрат; вместимость RAM и границы группы от него не увеличиваются.
