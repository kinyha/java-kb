Partitioning

Секционирование делит одну большую таблицу на несколько физических таблиц-секций внутри одной базы, а запросы по-прежнему обращаются к общей таблице. Ключ секционирования — обычно время — определяет, в какую секцию попадает строка. Если запрос фильтрует по ключу, планировщик читает только нужные секции (partition pruning). Главная польза — управление данными: старый месяц удаляется отсоединением секции за миллисекунды вместо многочасового DELETE с раздуванием. Цена — ограничения: уникальность должна включать ключ секционирования, запросы без ключа обходят все секции, а секции нужно создавать заранее.

Журнал проводок вырос до миллиардов строк, и удаление старого года шло сутки

Журнал проводок платёжной системы хранится пять лет, потом удаляется. Таблица выросла до миллиардов строк. Ежемесячный DELETE строк старше пяти лет идёт часами, создаёт миллионы мёртвых версий, раздувает таблицу и индексы, а autovacuum после него работает сутки. Индекс по счёту и дате весит больше памяти сервера, и даже запросы за последний месяц читают его с диска.

Тема разбирает декларативное секционирование PostgreSQL: как оно устроено, что даёт и чего стоит. Распределение данных по разным серверам — в Sharding, VACUUM и раздувание — в VACUUM. Демо PartitionDemo.java работает с PostgreSQL 17 в Docker: журнал из трёх миллионов проводок за год, секции по месяцам, и для сравнения та же таблица без секций.

Одна логическая таблица, много физических секций

create table ledger(id bigint, created_at timestamptz not null, account int, amount bigint)
    partition by range (created_at);
create table ledger_2026_03 partition of ledger
    for values from ('2026-03-01') to ('2026-04-01');
create index on ledger(account, created_at);     -- создаётся в каждой секции

Родительская таблица не хранит строк. Вставка в ledger направляется в секцию по значению created_at, индекс, созданный на родителе, создаётся отдельно в каждой секции. Для приложения это одна таблица: JPA-сущность и SQL не меняются.

ВидКак делитКогда
RangeПо диапазонам значенийВремя: журналы, события, платежи — удаление старых периодов
ListПо перечню значенийСтрана, регион, тип клиента
HashПо хешу ключа на N секцийРавномерно разбить большую таблицу без естественного диапазона

Запрос с ключом секционирования читает только нужные секции

== one month for one account
   Bitmap Heap Scan on ledger_2026_03 ledger (actual rows=54 loops=1)
   partitions scanned: 1 of 12; Execution Time: 0.182 ms
== no partition key in WHERE
   Bitmap Heap Scan on ledger_2026_01 ledger_1 (actual rows=54 loops=1)
   partitions scanned: 12 of 12; Execution Time: 1.174 ms

Условие на created_at позволило планировщику отбросить одиннадцать секций ещё до выполнения, и запрос прочитал одну. Работает это и с параметрами подготовленного запроса — тогда отбрасывание происходит при выполнении. Запрос только по счёту прошёл по индексам всех двенадцати секций: в шесть раз медленнее, хотя строк столько же. На проде с сотнями секций такой запрос дорожает пропорционально, а планирование с тысячами секций само по себе занимает заметное время. Поэтому ключ секционирования выбирают по тому, как данные фильтруют, и он должен быть в каждом частом запросе.

Скорость поиска внутри одного месяца секционирование почти не меняет: B-tree по 270 тысячам строк лишь на уровень мельче, чем по трём миллионам. Индексы секций меньше, и горячие — последних месяцев — помещаются в память, но главный выигрыш не в чтении.

Старые данные удаляются отсоединением секции, а не DELETE

== removing January
   DELETE from flat table: 267839 rows, 98 ms (and dead rows left for VACUUM)
   DETACH + DROP partition: 3 ms

Удаление января из обычной таблицы — 268 тысяч удалённых строк, мёртвые версии в таблице и индексе, работа для VACUUM и WAL на каждую строку. На миллиардах строк это часы, как в истории выше. Отсоединение и удаление секции — операция над каталогом и файлом: 3 мс, без мёртвых версий и почти без журнала. DETACH PARTITION CONCURRENTLY отсоединяет секцию без долгой блокировки родителя. Отсоединённую секцию можно не удалять, а выгрузить в архив или перенести в дешёвое хранилище.

Так же дёшево загружать: подготовить данные в отдельной таблице с нужными индексами и подключить её как секцию ATTACH PARTITION. Чтобы при подключении не сканировать таблицу, заранее добавляют CHECK-ограничение, совпадающее с диапазоном секции.

Уникальность включает ключ, секции создают заранее, а глобального индекса нет

== unique constraint without the partition key
   unique (id) -> ERROR: unique constraint on partitioned table must include all partitioning columns
   unique (id, created_at) -> ok
== insert outside any partition
   23514 ERROR: no partition of relation "ledger" found for row

Индексы существуют в каждой секции отдельно, глобального индекса по всей таблице в PostgreSQL нет. Поэтому уникальность можно проверить только внутри секции, и ограничение обязано включать ключ секционирования: unique (id) отклонён, unique (id, created_at) принят. Если нужен глобально уникальный id, его обеспечивают генератором — последовательностью или UUIDv7 — а не ограничением. По той же причине внешние ключи на секционированную таблицу должны ссылаться на ключ, включающий колонку секционирования.

Строка, для которой нет секции, отклоняется: вставка 2027 года упала, потому что секции на него никто не создал. Секции создают заранее по расписанию — расширение pg_partman или задача в приложении, — и добавляют секцию DEFAULT как страховку. С ней нужна осторожность: при создании новой секции PostgreSQL проверяет default-секцию на строки, которые должны были бы туда попасть, и чем она больше, тем дольше.

Секционирование ускоряет все запросы к большой таблице.

Ускоряются запросы с условием на ключ секционирования, и то в основном за счёт меньших индексов. Запрос без ключа обходит все секции и становится медленнее: в демо 12 секций вместо одной. Главная польза секционирования — дешёвое удаление и загрузка периодов: DROP секции 3 мс против DELETE с мёртвыми версиями.

  • Одна логическая таблица, физические секции по range, list или hash; приложение не меняется.
  • Pruning: запрос с ключом читает 1 секцию из 12; без ключа — все 12, и в шесть раз дольше.
  • Удаление периода: DETACH + DROP за 3 мс вместо DELETE с мёртвыми версиями и VACUUM.
  • Уникальность включает ключ секционирования, глобального индекса нет; секции создают заранее, default-секция — страховка с оговорками.

На собеседовании

Что такое секционирование таблицы и зачем оно нужно?

Разделение одной логической таблицы на физические секции по ключу — диапазону времени, списку значений или хешу — внутри одной базы. Запросы с условием на ключ читают только нужные секции. Главная польза — управление жизненным циклом: старый период удаляется отсоединением секции мгновенно, а новые данные загружаются подключением готовой таблицы.

  • Индексы секций меньше, горячие секции помещаются в память.
  • Запросы без ключа обходят все секции; тысячи секций дорожают на планировании.
  • Секционирование — в одной базе; распределение по серверам — шардирование.

Какие ограничения у секционирования в PostgreSQL?

Нет глобального индекса, поэтому первичный ключ и уникальные ограничения должны включать ключ секционирования. Строка без подходящей секции отклоняется, и секции нужно создавать заранее. Запросы без условия на ключ обходят все секции. Перенос строки между секциями при изменении ключа — это удаление и вставка.

  • DEFAULT-секция ловит строки без секции, но замедляет создание новых секций.
  • pg_partman автоматизирует создание и удаление секций.
Что не так с этим планом секционирования? 
create table payment(id uuid primary key, merchant_id int, created_at timestamptz, amount bigint)
    partition by hash (merchant_id);
-- 64 секции; самые частые запросы: «платежи за последний час» и удаление данных старше 3 лет

Первичный ключ id не включает ключ секционирования и не будет создан. Хеш по магазину не помогает ни частым запросам за последний час — они обойдут все 64 секции, — ни удалению старых данных: каждая секция содержит все годы, и удалять придётся DELETE. Для этих задач нужен range по created_at с ключом (id, created_at), а поиск по магазину — индекс внутри секций.

Как регулярно удалять старые данные из таблицы на миллиарды строк?

Не DELETE: он создаёт мёртвые версии каждой строки, раздувает таблицу и индексы, пишет WAL на каждую строку и нагружает VACUUM. Таблицу секционируют по времени, и старый период удаляют отсоединением и удалением секции — операция над каталогом и файлом, миллисекунды. В демо DROP секции занял 3 мс.

  • DETACH PARTITION CONCURRENTLY не держит долгую блокировку родителя.
  • Если секционировать поздно, DELETE делают пачками по id в коротких транзакциях.

  • pg_partman — автоматическое создание и удаление секций.
