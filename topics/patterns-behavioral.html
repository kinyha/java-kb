Design: Behavioral Patterns

Поведенческие паттерны распределяют решения и реакции между объектами. Strategy выносит вариант алгоритма в отдельный объект. Chain of responsibility передаёт запрос по цепочке, пока кто-то его не остановит, и порядок звеньев стоит денег. Template method фиксирует порядок шагов в родителе, а шаги отдаёт подклассам. Observer рассылает событие подписчикам, и один упавший подписчик может остановить остальных. Command делает действие объектом, который можно сохранить, повторить и отменить. State описывает, какие переходы допустимы, и запрещает остальные.

Метод оплаты оброс проверками, статусами и реакциями на каждый случай

Метод checkout платёжного сервиса проверяет сумму, страну и антифрод, выбирает банк по способу оплаты, меняет статус платежа, а после успеха пишет проводку, шлёт SMS и событие в аналитику. Каждое новое требование добавляет ещё один if: новую проверку, новый статус, нового получателя уведомления. Через год в методе четыреста строк, и никто не знает, в каком порядке выполняются проверки и что произойдёт, если упадёт SMS.

Поведенческие паттерны разбирают такой метод на объекты, у каждого из которых одна роль: проверка, шаг интеграции, подписчик, операция, состояние. Порядок и связи между ними становятся явными. Демо BehavioralDemo.java запускается командой java BehavioralDemo.java на JDK 21. Strategy подробно разобран в SOLID на примере способов оплаты; здесь он появится как основа остальных.

Chain of responsibility передаёт запрос по звеньям, и дешёвые ставят первыми

Каждая проверка платежа — звено. Звено либо отклоняет платёж и останавливает цепочку, либо пропускает его дальше. Код оплаты не знает, сколько проверок и какие: он прогоняет платёж через список.

interface Check { Optional<String> reject(Payment p); } // empty — пропустить дальше.

static Optional<String> runChain(List<Check> chain, Payment p) {
    for (Check c : chain) {
        var r = c.reject(p);
        if (r.isPresent()) return r; // Первый отказ останавливает цепочку.
    }
    return Optional.empty();
}

var bad = new Payment("p-1", 500, "XX", "4111"); // Страна под санкциями.
runChain(List.of(amount, country, fraud), bad);  // Дешёвые проверки первыми.
runChain(List.of(fraud, amount, country), bad);  // Удалённый антифрод первым.
  cheap first: sanctioned country, calls=[amount, country]
  fraud first: sanctioned country, calls=[fraud(remote, 120 ms), amount, country]

Тот же паттерн устроен в цепочке фильтров сервлета и в Spring Security: каждый фильтр решает, вызвать ли chain.doFilter дальше или ответить сам. Там порядок определяет не только цену, но и смысл: CSRF-фильтр перед аутентификацией превращает 403 в 401. В Spring порядок звеньев задают @Order или явный список; полагаться на порядок обнаружения бинов нельзя.

Template method фиксирует порядок шагов в родителе, но родитель видит наследника недостроенным

У интеграций с разными банками общий порядок: собрать запрос, подписать, отправить, разобрать ответ. Отличаются отдельные шаги: адрес, формат подписи. Template method держит порядок в final-методе родителя, а шаги объявляет абстрактными или переопределяемыми.

abstract class BankIntegration {
    BankIntegration() {
        System.out.println("constructor sees endpoint=" + endpoint()); // Переопределяемый метод.
    }
    final String charge(Payment p) {          // Шаблон: порядок шагов фиксирован.
        return sign(endpoint() + "/charge?" + p.id());
    }
    abstract String endpoint();               // Шаг, который задаёт подкласс.
    String sign(String request) { return request + "&sig=sha256"; }
}

class TinkoffIntegration extends BankIntegration {
    private final String endpoint;
    TinkoffIntegration(String endpoint) {
        super();                              // Сначала конструктор родителя...
        this.endpoint = endpoint;             // ...и только потом присваивание.
    }
    String endpoint() { return endpoint; }
}
  constructor sees endpoint=null
  https://securepay.tinkoff.ru/charge?p-2&sig=sha256
  constructor sees endpoint=https://securepay.tinkoff.ru

Первая строка — классическая ловушка шаблонного метода. Конструктор родителя выполняется раньше, чем поля наследника получат значения, и переопределённый метод видит null. Если бы родитель в конструкторе строил URL или открывал соединение, он бы сделал это с пустым адресом. Правило из Effective Java: конструктор не вызывает переопределяемые методы.

Третья строка — сюрприз демо. У класса ConstantIntegration поле объявлено как private final String endpoint = "https://…", и конструктор родителя видит правильный адрес. Это не значит, что поле уже присвоено: final-поле, инициализированное литералом, — константа времени компиляции, и компилятор подставил строку прямо в метод endpoint(). Стоит заменить литерал на значение из настроек, и ошибка вернётся. Такие «работает, пока не трогаешь» места опаснее явной ошибки.

Template method строит поведение наследованием, strategy — композицией: шаги передают объектами или лямбдами. Spring почти везде выбирает второе, хотя называет классы «шаблонами»: JdbcTemplate.query(sql, rowMapper) фиксирует порядок работы с ресурсами, а разбор строки получает как стратегию. Наследование с шаблонным методом в Spring осталось там, где расширяют сам фреймворк: OncePerRequestFilter.doFilterInternal, AbstractRoutingDataSource.determineCurrentLookupKey.

Observer рассылает событие подписчикам, и один упавший подписчик останавливает остальных

После оплаты три части системы должны отреагировать: бухгалтерия записывает проводку, SMS-шлюз уведомляет клиента, аналитика считает выручку. Observer отделяет источник события от получателей: сервис оплаты знает только список подписчиков и вызывает каждого.

List<PaymentListener> listeners = new ArrayList<>();
listeners.add(p -> System.out.println("ledger: recorded " + p.id()));
listeners.add(p -> { throw new IllegalStateException("sms gateway down"); });
listeners.add(p -> System.out.println("analytics: counted " + p.id()));

for (var l : listeners) l.paid(payment); // Синхронная рассылка в одном потоке.
  ledger: recorded p-3
  publish failed: sms gateway down (analytics never ran)

Подписчики не знают друг о друге, но выполняются в одном цикле. Исключение второго прервало рассылку, и аналитика не получила событие. Хуже того, исключение вылетело в сервис оплаты: упавший SMS-шлюз может откатить уже проведённый платёж. Слабая связь в коде не означает изоляции при выполнении.

Второй сюрприз — подписчик, который отписывается во время рассылки. Код отписки удаляет себя из того же ArrayList, по которому идёт цикл:

once.add(new PaymentListener() {
    public void paid(Payment p) { once.remove(this); } // Отписаться после первого события.
});
once.add(p -> System.out.println("second listener got " + p.id()));
once.add(p -> System.out.println("third listener got " + p.id()));
  unsubscribe during publish: ConcurrentModificationException
  second listener got p-5
  third listener got p-5
  CopyOnWriteArrayList: listeners left=2

С тремя подписчиками итератор ArrayList бросил ConcurrentModificationException, и ни второй, ни третий событие не получили. В первой версии демо подписчиков было два, и исключения не было вовсе: после удаления первого элемента итератор решил, что список кончился, и второй подписчик молча пропустил событие. Поведение зависит от позиции и размера — это худший вид ошибки. CopyOnWriteArrayList итерирует снимок, сделанный в начале цикла, поэтому все подписчики получили событие, а отписка вступила в силу со следующей рассылки.

В Spring этот паттерн — ApplicationEventPublisher и @EventListener. Там те же вопросы решаются явно: по умолчанию рассылка синхронная и исключение доходит до публикующего кода, @Async уводит слушателя в пул, а @TransactionalEventListener привязывает его к коммиту. Всё это разобрано в Application Events.

Command делает действие объектом, который можно сохранить, повторить и отменить

Обычный вызов метода исчезает, как только выполнился. Если действие оформить объектом с методом execute, его можно положить в очередь, записать в журнал, выполнить позже в другом потоке или отменить. В платёжном сервисе так устроены операции с балансом: списание и комиссия — команды, у каждой есть обратная.

interface Command { void execute(); void undo(); String name(); }

Deque<Command> history = new ArrayDeque<>();
for (var c : List.of(charge, fee)) { c.execute(); history.push(c); } // charge −300, fee −5.
while (!history.isEmpty()) history.pop().undo();                    // Отмена в обратном порядке.
  after commands: balance=695, log=[fee 5, charge 300]
  after undo all: balance=1000

Журнал команд показывает операции в порядке отмены: последней выполнили комиссию, первой её и отменяют. Отменять в другом порядке нельзя, если команды зависят друг от друга: комиссия считалась от суммы после списания.

В Java команда встречается постоянно, просто без этого имени. Runnable и Callable, отправленные в ExecutorService, — команды: действие отделено от того, кто и когда его выполнит. Запись в таблице outbox — команда «отправить событие», сохранённая вместе с транзакцией. Сообщение в очереди с типом операции — команда для другого сервиса.

Отмена в реальной системе редко бывает обратной операцией над памятью. Деньги, ушедшие в банк, возвращаются отдельной операцией возврата, которая сама может не пройти. Поэтому для распределённых процессов отмену проектируют как компенсацию — новую команду, которая исправляет последствия, а не стирает их. Это основа саг.

State описывает допустимые переходы и запрещает остальные

Платёж проходит через статусы: создан, авторизован (деньги заблокированы), списан, возвращён или отменён. Не каждый переход возможен: списанный платёж нельзя отменить, его можно только вернуть. Если статус — строка, а проверки разбросаны по сервисам, рано или поздно кто-то отменит списанный платёж, и деньги клиента зависнут.

enum Status {
    NEW, AUTHORIZED, CAPTURED, REFUNDED, CANCELLED;

    static final Map<Status, List<Status>> NEXT = Map.of(
            NEW, List.of(AUTHORIZED, CANCELLED),
            AUTHORIZED, List.of(CAPTURED, CANCELLED),
            CAPTURED, List.of(REFUNDED),
            REFUNDED, List.of(),
            CANCELLED, List.of());

    Status to(Status next) {        // Единственный способ сменить статус.
        if (!NEXT.get(this).contains(next)) {
            throw new IllegalStateException(this + " -> " + next + " is not allowed");
        }
        return next;
    }
}

Status s = Status.NEW.to(Status.AUTHORIZED).to(Status.CAPTURED);
s.to(Status.CANCELLED);
  CAPTURED
  CAPTURED -> CANCELLED is not allowed

Классический State из GoF выносит поведение каждого состояния в свой класс: CapturedState.cancel() бросает исключение, AuthorizedState.cancel() снимает блокировку. Это оправдано, когда у состояний много разного поведения. Когда различаются только допустимые переходы, таблица в enum проще и нагляднее. Для сложных процессов с таймерами и параллельными ветками есть Spring Statemachine, но для платежа из пяти статусов он избыточен.

Проверка в памяти не защищает от гонки. Два обработчика одновременно читают AUTHORIZED, один списывает, другой отменяет, и оба переходы допустимы с их точки зрения. Переход должен быть атомарным в базе: UPDATE payment SET status = 'CAPTURED' WHERE id = ? AND status = 'AUTHORIZED' с проверкой числа изменённых строк или версия сущности из Locking & Caching.

  • Chain of responsibility останавливается на первом отказе: дешёвые звенья первыми, порядок задают явно.
  • Template method держит порядок шагов в родителе; конструктор родителя видит поля наследника пустыми.
  • Observer слабо связывает код, но синхронная рассылка падает целиком; отписка во время рассылки ломает ArrayList.
  • Command превращает действие в объект для очереди, журнала и отмены; в распределённой системе отмена — компенсация.
  • State задаёт допустимые переходы; атомарность перехода обеспечивает база, а не проверка в памяти.

На собеседовании

Чем strategy отличается от template method?

Оба позволяют менять часть алгоритма. Template method делает это наследованием: родитель фиксирует порядок шагов в final-методе, подкласс переопределяет шаги. Strategy — композицией: изменяемая часть передаётся объектом или лямбдой, и её можно подменить во время работы.

Я обычно выбираю strategy: она не привязывает к иерархии, легче тестируется и комбинируется. Spring делает так же — JdbcTemplate фиксирует работу с ресурсами, а разбор строки получает как RowMapper.

  • Ловушка шаблонного метода: конструктор родителя, вызвавший переопределяемый метод, видит поля наследника пустыми.
  • Литерал в final-поле — константа компиляции, и эта ошибка прячется, пока значение не придёт из настроек.
  • Template method остаётся там, где расширяют фреймворк: OncePerRequestFilter, AbstractRoutingDataSource.

Какие проблемы бывают у observer и как их решает Spring?

Синхронная рассылка выполняет подписчиков в одном потоке: исключение одного прерывает остальных и уходит в код, который опубликовал событие. Медленный подписчик тормозит всех. Отписка во время рассылки по ArrayList даёт ConcurrentModificationException или молча пропускает подписчика.

В Spring слушатели по умолчанию тоже синхронные; @Async уводит их в пул, а @TransactionalEventListener выполняет после коммита. Для списка подписчиков, который меняется во время рассылки, подходит CopyOnWriteArrayList.

  • Событие в памяти теряется при падении процесса; если реакция обязательна, нужен outbox или брокер.
  • Порядок слушателей задают @Order, иначе на него нельзя рассчитывать.
  • Подписчик, державший ссылку на большой объект, удерживает его от GC — классическая утечка в UI и кешах.
Почему отписка во время рассылки иногда не бросает исключение?

Итератор ArrayList проверяет изменения в next, а hasNext сравнивает только позицию с размером. С двумя подписчиками после удаления первого размер стал 1, позиция тоже 1, и цикл просто закончился — второй подписчик не получил событие без всякой ошибки. С тремя next вызвался ещё раз и бросил ConcurrentModificationException.

Где в Spring встречается chain of responsibility?

Цепочка фильтров сервлета и Spring Security: каждый фильтр решает, передать запрос дальше через chain.doFilter или ответить сам. HandlerInterceptor в Spring MVC, цепочки advice в AOP, обработчики ошибок — тоже цепочки.

Главное в цепочке — порядок. Он определяет и смысл, и цену: дорогие сетевые проверки ставят после дешёвых, чтобы платёж с неверной суммой не ходил в антифрод.

  • Порядок задают @Order или явный список; порядок обнаружения бинов не гарантирован.
  • Звено, забывшее вызвать следующее, молча обрывает цепочку — частая ошибка в собственных фильтрах.

Как моделировать статусы платежа?

Как конечный автомат: enum статусов и таблица допустимых переходов, единственный метод смены статуса проверяет переход и бросает исключение для запрещённых. Списанный платёж нельзя отменить, только вернуть. Таблицу легко проверить тестом и показать аналитику.

Переход должен быть атомарным в базе: UPDATE с условием на текущий статус и проверкой числа строк или оптимистичная блокировка, иначе два обработчика выполнят несовместимые переходы.

  • Классы на каждое состояние из GoF оправданы, когда у состояний разное поведение, а не только разные переходы.
  • История переходов в отдельной таблице нужна для аудита и разбора спорных платежей.
  • Spring Statemachine полезен для процессов с таймерами и параллельными ветками, для пяти статусов он избыточен.
Найди гонку в отмене платежа 
@Transactional
public void cancel(long id) {
    Payment p = repository.findById(id).orElseThrow();
    if (p.getStatus() != Status.AUTHORIZED) throw new IllegalStateException();
    bank.voidAuthorization(p);
    p.setStatus(Status.CANCELLED);
}

Между чтением статуса и записью другой поток может списать этот же платёж: оба прочитали AUTHORIZED. Отмена снимет блокировку в банке и запишет CANCELLED поверх CAPTURED, хотя деньги уже списаны. Нужна атомарная проверка: @Version на сущности, SELECT ... FOR UPDATE или UPDATE ... WHERE status = 'AUTHORIZED' с проверкой числа строк, а вызов банка — после фиксации перехода.
