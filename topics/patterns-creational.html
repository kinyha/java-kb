Design: Creational Patterns

Порождающие паттерны отвечают на вопрос, кто и как создаёт объект. Фабричный метод прячет за именем выбор класса и кеширование. Builder собирает объект с многими полями и проверяет его целиком. Singleton даёт один экземпляр, но только в пределах загрузчика классов, а singleton Spring — в пределах контекста. Abstract factory выдаёт согласованное семейство объектов. Prototype копирует готовый объект, и clone() копирует ссылки, а не содержимое. В Spring почти всё создание забирает контейнер, поэтому эти паттерны чаще встречаются в его API, чем в твоём коде.

Платёж создают в двадцати местах, и каждое собирает его по-своему

Объект платежа нужен контроллеру, импорту из CSV, повтору из очереди и тестам. В каждом месте свой вызов конструктора с семью параметрами, половина из которых null или false. Кто-то забыл валюту, кто-то перепутал местами две строки одного типа, и компилятор этого не заметил.

new Payment("p-1", 500, null, "coffee", false, null, true); // Что значат null и true?

Порождающие паттерны выносят создание в одно место с понятным именем. Банда четырёх (GoF) описала пять: фабричный метод, абстрактную фабрику, строителя, одиночку и прототип. Джошуа Блох в Effective Java добавил к ним статический фабричный метод, который в Java встречается чаще всех. Демо CreationalDemo.java запускается командой java CreationalDemo.java на JDK 21.

Статический фабричный метод выбирает класс и может вернуть готовый объект

У конструктора три ограничения: у него нет имени, он всегда создаёт новый объект и всегда объект ровно этого класса. Статический метод снимает все три. JDK пользуется этим повсюду:

List.of(1).getClass();        // Класс выбирает фабрика, не вызывающий.
List.of(1, 2, 3).getClass();
Integer a = 127, b = 127, c = 128, d = 128; // Автоупаковка — это Integer.valueOf.
System.out.println((a == b) + ", " + (c == d)); // Сравниваем ссылки.
List.of(1): List12, List.of(1,2,3): ListN
valueOf(127) same object: true, valueOf(128) same object: false

List.of возвращает разные скрытые классы: компактный для одного-двух элементов и общий для остальных. Вызывающий видит только List, и JDK может поменять реализацию в любой версии. Integer.valueOf отдаёт заранее созданные объекты для чисел от −128 до 127 и новые для остальных. Поэтому == для Integer «работает» на маленьких числах и ломается на больших — классическая ошибка с суммами платежей.

На собеседовании полезно различать два понятия. Статический фабричный метод из Effective Java — метод класса вместо конструктора: Money.of(500, RUB), Payment.refundOf(original). Factory Method из GoF — переопределяемый метод, через который базовый класс поручает подклассу решить, какой объект создать. В Spring второе встречается в виде методов @Bean: класс конфигурации решает, какую реализацию создать, а остальной код получает интерфейс.

Builder собирает объект с многими полями и проверяет его целиком

Когда полей много, а часть необязательна, конструкторы множатся: с тремя параметрами, с четырьмя, с пятью. Сеттеры решают проблему ценой изменяемого объекта, который какое-то время существует наполовину собранным. Builder копит значения в отдельном объекте и создаёт результат одним вызовом build(), где можно проверить всё сразу:

record Payment(String id, long cents, String currency, String description, boolean recurring) {
    static final class Builder {
        private String id, currency = "RUB", description = ""; // Значения по умолчанию в одном месте.
        private long cents;
        private boolean recurring;

        Builder id(String v) { id = v; return this; }
        Builder cents(long v) { cents = v; return this; }
        Builder currency(String v) { currency = v; return this; }

        Payment build() { // Проверка инварианта всего объекта.
            Objects.requireNonNull(id, "id");
            if (cents <= 0) throw new IllegalStateException("amount must be positive, got " + cents);
            return new Payment(id, cents, currency, description, recurring);
        }
    }
}

Payment.builder().id("p-1").cents(500).description("coffee").build();
Payment.builder().id("p-2").currency("USD").build(); // Сумму забыли.
Payment[id=p-1, cents=500, currency=RUB, description=coffee, recurring=false]
build failed: amount must be positive, got 0

Вызов читается как описание: видно, какое значение к какому полю относится, и порядок неважен. Объект Payment неизменяемый, а получить неправильный нельзя: build() не выпустит платёж без суммы. Цена — второй класс с копией всех полей, поэтому для трёх-четырёх обязательных параметров обычный конструктор record проще.

Lombok @Builder генерирует такой класс, но не проверяет инварианты: build() вызовет конструктор как есть. Проверку переносят в компактный конструктор record или пишут свой build(). Ещё одна ловушка Lombok: значение по умолчанию у поля без @Builder.Default builder игнорирует. В Spring builder — основной способ настройки: RestClient.builder(), UriComponentsBuilder, MockMvcRequestBuilders, SpringApplicationBuilder.

Singleton даёт один экземпляр, но один на что

Классический singleton — приватный конструктор и статическое поле. Он защищает от случайного new, но не от сознательного обхода. Демо создаёт второй экземпляр двумя способами:

static final class BankRegistry implements Serializable {
    static final BankRegistry INSTANCE = new BankRegistry();
    private BankRegistry() {}
}
enum Banks { INSTANCE } // Singleton по Блоху.

var ctor = BankRegistry.class.getDeclaredConstructor();
ctor.setAccessible(true);
ctor.newInstance() == BankRegistry.INSTANCE;          // Рефлексия.
roundTrip(BankRegistry.INSTANCE) == BankRegistry.INSTANCE; // Сериализация туда и обратно.
reflection copy == INSTANCE: false
deserialized == INSTANCE: false
enum via reflection: Cannot reflectively create enum objects
enum deserialized == INSTANCE: true

Рефлексия вызвала приватный конструктор, десериализация собрала новый объект в обход конструктора. Для класса защита пишется вручную: проверка в конструкторе и метод readResolve, возвращающий INSTANCE. Enum защищён языком: JVM запрещает создавать его константы рефлексией, а сериализация хранит только имя константы. Поэтому Effective Java называет enum с одним элементом лучшим способом сделать singleton. Ленивую инициализацию без синхронизации даёт идиома holder-класса: вложенный класс с полем загружается при первом обращении, а JVM гарантирует потокобезопасную инициализацию класса.

Singleton Spring — не паттерн GoF. Scope singleton значит «один объект на определение бина в контейнере». Два метода @Bean, возвращающих FeeCalculator, дают два объекта, а второй контекст — ещё по одному. Конструктор при этом обычный и открытый: тест создаёт объект через new с заглушками.

Поэтому в коде на Spring классический singleton почти не нужен и даже вреден. Статическое глобальное состояние нельзя подменить в тесте, оно живёт между тестами одного JVM и прячет зависимость: по сигнатуре класса не видно, что он ходит в реестр банков. Бин-синглтон, внедрённый через конструктор, даёт ту же единственность без этих проблем.

Abstract factory выдаёт семейство объектов, которые работают только вместе

Для работы с банком нужны три объекта: HTTP-клиент, проверка подписи ответов и перевод кодов ошибок банка в коды сервиса. Каждый банк поставляет свой комплект. Ошибка, от которой защищает абстрактная фабрика, — смешать комплекты: клиент Тинькофф и проверку подписи Сбера. Каждый объект по отдельности рабочий, а вместе они отклоняют все ответы.

interface BankKit {                       // Абстрактная фабрика.
    BankClient client();
    SignatureVerifier verifier();
    ErrorMapper errors();
}

class TinkoffKit implements BankKit { /* три согласованных объекта Тинькофф */ }
class SberKit implements BankKit { /* три объекта Сбера */ }

// Код платежа получает весь комплект сразу и не может собрать чужую смесь.
PaymentService(BankKit bank) { … }

В Spring абстрактную фабрику обычно выражают конфигурацией: класс @Configuration на каждый банк с @ConditionalOnProperty(name = "payments.bank", havingValue = "tinkoff") создаёт все три бина. Сам BeanFactory — фабрика в самом общем смысле: он создаёт любые объекты по описаниям. Разбор того, как Boot выбирает такие конфигурации, — в Auto-configuration.

Prototype копирует готовый объект, а clone() копирует ссылки

Прототип нужен, когда новый объект проще получить копией настроенного, чем собирать заново: шаблон тарифа с двадцатью комиссиями, из которого делают тариф для конкретного магазина. В Java для этого есть Cloneable и clone(), и с ними легко ошибиться:

class Tariff implements Cloneable {
    String bank;
    List<String> fees = new ArrayList<>(List.of("1.5%"));

    public Tariff clone() { return (Tariff) super.clone(); } // Поверхностная копия.

    Tariff(Tariff other) {                       // Конструктор копирования.
        this.bank = other.bank;
        this.fees = new ArrayList<>(other.fees); // Копия списка явная.
    }
}

var cloned = base.clone();
cloned.fees.add("promo -1%");   // Скидка только для одного магазина.
var copied = new Tariff(base);
copied.fees.add("vip -0.5%");
base after changing clone: [1.5%, promo -1%]
base after changing copy:  [1.5%, promo -1%]

Во второй строке вывода в базовом тарифе осталась промо-скидка из первого опыта, но vip-скидки нет: конструктор копирования сделал свой список. Object.clone() создаёт поверхностную копию, и глубокое копирование каждого изменяемого поля надо писать вручную. Ещё у механизма неудобный контракт: Cloneable не объявляет метод clone, а final-поля в копии не переназначить. Effective Java советует конструктор копирования или статический метод copyOf.

Лучшая защита — неизменяемость. Если тариф — record с List.copyOf в компактном конструкторе, делить его между магазинами безопасно, а «копия с изменением» — это новый объект с одним другим полем. Scope prototype в Spring — другое понятие: контейнер создаёт новый объект на каждый запрос бина по его описанию, ничего не копируя. Он разобран в Bean Scopes.

  • Статический фабричный метод даёт имя, кеширование и выбор класса; Integer.valueOf кеширует −128…127, поэтому == для Integer ненадёжно.
  • Builder нужен для многих необязательных полей и проверяет инвариант в build(); Lombok @Builder сам ничего не проверяет.
  • Singleton уникален в загрузчике, singleton Spring — на определение бина в контейнере. Enum защищён от рефлексии и сериализации.
  • Abstract factory выдаёт согласованное семейство; в Spring это условная конфигурация.
  • clone() копирует ссылки; вместо него — конструктор копирования или неизменяемые объекты.

На собеседовании

Как правильно реализовать singleton в Java?

Самый надёжный способ — enum с одним элементом. JVM гарантирует одну константу на загрузчик, запрещает создать её рефлексией и при десериализации возвращает ту же константу. Классический вариант с приватным конструктором и static final полем обходится рефлексией и сериализацией, если не добавить проверку в конструктор и readResolve.

Для ленивой инициализации подходит holder-класс: вложенный класс со статическим полем загрузится при первом обращении, а потокобезопасность даёт инициализация класса в JVM. Double-checked locking требует volatile и сложнее читается.

  • Singleton уникален только в своём загрузчике классов: в серверах приложений и плагинах их может быть несколько.
  • Глобальное статическое состояние плохо тестируется и прячет зависимость; в Spring вместо него используют бин-синглтон.
  • Volatile в double-checked locking нужен из-за возможной публикации не до конца сконструированного объекта.
Чем singleton Spring отличается от паттерна singleton?

Scope singleton означает один объект на определение бина в контейнере. Два метода @Bean одного типа дают два объекта, второй контекст — ещё объекты. Конструктор обычный, объект можно создать через new в тесте. Паттерн GoF запрещает второй экземпляр в пределах загрузчика классов и делает доступ глобальным.

Когда нужен builder и чем он лучше конструктора или сеттеров?

Когда у объекта много параметров и часть необязательна. Конструктор с семью аргументами нечитаем, и легко перепутать два параметра одного типа. Сеттеры дают изменяемый объект, который какое-то время существует наполовину собранным. Builder копит значения и создаёт неизменяемый объект одним вызовом build, где можно проверить инварианты сразу для всех полей.

Для трёх-четырёх обязательных полей обычный конструктор или record проще.

  • Lombok @Builder не проверяет инварианты и игнорирует инициализаторы полей без @Builder.Default.
  • Step builder через цепочку интерфейсов заставляет задать обязательные поля на этапе компиляции.
  • В Spring builder — основной API настройки: RestClient.builder, UriComponentsBuilder, SpringApplicationBuilder.

Что такое фабричный метод и где он в JDK и Spring?

В обиходе так называют статический метод вместо конструктора: List.of, Integer.valueOf, Optional.of. У него есть имя, он может вернуть закешированный объект и выбрать подкласс: List.of возвращает разные скрытые реализации в зависимости от числа элементов.

Factory Method из GoF — другое: переопределяемый метод, через который базовый класс поручает подклассу создать объект. В Spring близкий аналог — методы @Bean в конфигурации, а сам BeanFactory — фабрика объектов по описаниям.

  • Integer.valueOf кеширует −128…127, поэтому == для Integer ломается на 128; верхнюю границу можно поднять флагом JVM.
  • Минус статических фабрик — их труднее найти в API, чем конструкторы; помогают соглашения об именах of, from, valueOf, getInstance.
  • Abstract factory создаёт согласованное семейство объектов; в Spring её роль играет условная @Configuration.

Что не так с clone() в Java?

Object.clone делает поверхностную копию: поля-ссылки копируются как ссылки. Копия тарифа делит с оригиналом тот же список комиссий, и изменение копии меняет оригинал. Глубокое копирование нужно писать вручную для каждого изменяемого поля.

Вместо clone лучше конструктор копирования или статический метод copyOf, а ещё лучше — неизменяемые объекты, которые копировать не нужно.

  • Cloneable не объявляет clone, это интерфейс-маркер, меняющий поведение защищённого метода Object.
  • final-поля в копии не переназначить, поэтому clone плохо сочетается с неизменяемыми полями.
  • Scope prototype в Spring не копирует объект, а создаёт новый по описанию бина.
