Design: Structural Patterns

Структурные паттерны отвечают на вопрос, как собрать объекты вместе, не переписывая их. Adapter переводит чужой интерфейс в твой. Decorator оборачивает объект тем же интерфейсом и добавляет одно поведение, и порядок обёрток меняет результат. Proxy устроен так же, но контролирует доступ, и именно его Spring создаёт вокруг бинов. Facade даёт простой вход в сложную подсистему. Composite позволяет работать с деревом как с одним объектом. Главная путаница на собеседовании — декоратор и прокси, у которых одинаковая структура и разное назначение.

SDK банка говорит на чужом языке, а вокруг каждого вызова нужны лог и повтор

Платёжному сервису достался SDK старого банка. Он принимает сумму в рублях типа double, бросает свои исключения и называет списание pay. Вокруг каждого вызова нужно писать лог, повторять запрос при таймауте и мерить время. А комиссия складывается из дерева правил: эквайринг, фиксированная часть банка, надбавка за 3-D Secure.

Можно вписать всё в один класс: перевод единиц, лог, повтор и расчёт комиссии. Тогда SDK нельзя поменять без правки бизнес-кода, повтор нельзя выключить в тестах, а новое правило комиссии требует правки общего метода. Структурные паттерны разносят эти задачи по маленьким объектам, которые соединяются через общий интерфейс. Демо StructuralDemo.java запускается командой java StructuralDemo.java на JDK 21.

Adapter переводит чужой интерфейс в тот, которого ждёт твой код

interface BankGateway {                       // Язык платёжного сервиса.
    String charge(String id, long cents);
}

class LegacyBankSdk {                          // Чужой язык: рубли в double.
    String pay(String reference, double rubles) { … }
}

class LegacyBankAdapter implements BankGateway {
    private final LegacyBankSdk sdk;

    public String charge(String id, long cents) {
        // Копейки в рубли через BigDecimal: потеря точности только на границе SDK.
        double rubles = BigDecimal.valueOf(cents).movePointLeft(2).doubleValue();
        return sdk.pay(id, rubles);
    }
}

Сервис платежей знает только BankGateway и копейки в long. Всё, что относится к SDK, — единицы, имена методов, его исключения, его коды ошибок — живёт в одном классе. Когда банк выпустит новую версию SDK или его заменят, правится адаптер. Это DIP из SOLID в действии: интерфейс принадлежит сервису, адаптер подстраивается под него.

Адаптер может быть объектным — хранит ссылку на адаптируемый объект, как здесь, — или классовым, через наследование. В Java почти всегда используют объектный: наследование открывает весь API SDK и привязывает к его реализации. На уровне целого сервиса та же идея называется anti-corruption layer: слой, который не пускает модель чужой системы в твою. В Spring адаптеры повсюду: HandlerAdapter вызывает контроллер любого вида одинаковым способом, а MessageListenerAdapter превращает обычный метод в слушателя сообщений.

Decorator добавляет поведение обёрткой, и порядок обёрток меняет результат

Декоратор реализует тот же интерфейс, что и оборачиваемый объект, хранит ссылку на него и добавляет одно поведение до или после вызова. Лог и повтор — два декоратора, а не два наследника адаптера. Наследование дало бы класс на каждую комбинацию: с логом, с повтором, с логом и повтором.

class Logging implements BankGateway {
    private final BankGateway next;
    public String charge(String id, long cents) {
        System.out.println("log: charge " + id);
        return next.charge(id, cents);       // Передаём вызов дальше по цепочке.
    }
}

class Retrying implements BankGateway {
    private final BankGateway next;
    public String charge(String id, long cents) {
        try { return next.charge(id, cents); }
        catch (IllegalStateException e) {    // SDK падает с таймаутом на первой попытке.
            System.out.println("retry after: " + e.getMessage());
            return next.charge(id, cents);
        }
    }
}

BankGateway a = new Retrying(new Logging(new LegacyBankAdapter(sdk)));
BankGateway b = new Logging(new Retrying(new LegacyBankAdapter(sdk)));
== adapter + decorators: Retrying(Logging(adapter))
  log: charge p-1
  retry after: timeout
  log: charge p-1
  result: OK p-1 123.45
== decorators reversed: Logging(Retrying(adapter))
  log: charge p-2
  retry after: timeout
  result: OK p-2 123.45

Тот же вопрос порядка возникает в Resilience4j и Spring: circuit breaker снаружи повтора видит одну неудачу на весь вызов, внутри — каждую попытку. Метрика времени снаружи повтора покажет полную задержку для клиента, внутри — длительность одной попытки банка. Об этом стоит думать при каждой цепочке обёрток.

Классический пример декораторов — потоки ввода-вывода: new BufferedReader(new InputStreamReader(new FileInputStream(file), UTF_8)). Каждый слой добавляет одно: буфер, декодирование байтов в символы. Collections.synchronizedList и unmodifiableList — тоже декораторы над любым списком.

Proxy устроен как декоратор, но контролирует доступ и обычно создаётся фреймворком

Структурно прокси не отличается от декоратора: тот же интерфейс, ссылка на настоящий объект, код до и после вызова. Отличается назначение. Декоратор добавляет поведение, и клиент сам решает, что во что обернуть. Прокси стоит на месте объекта и управляет доступом к нему: проверяет права, откладывает создание, открывает транзакцию, ходит по сети. Клиент обычно не знает, что работает с прокси.

В Java прокси можно создать во время работы, не написав класс. java.lang.reflect.Proxy генерирует класс, реализующий интерфейсы, и направляет все вызовы в один обработчик:

BankGateway target = (id, cents) -> "charged " + id;
BankGateway timed = (BankGateway) Proxy.newProxyInstance(
        BankGateway.class.getClassLoader(), new Class<?>[] {BankGateway.class},
        (proxy, method, params) -> {
            System.out.println("intercepted " + method.getName()); // До вызова цели.
            return method.invoke(target, params);                   // Вызов настоящего объекта.
        });
timed.getClass().getName();
timed.charge("p-3", 100);
timed.toString(); // Тоже идёт через обработчик.
  proxy class: $Proxy0
  intercepted charge
  result: charged p-3
  intercepted toString
  toString is target's: true

Класс $Proxy0 сгенерирован JVM. Через обработчик идут не только методы интерфейса, но и toString, equals и hashCode. Обработчик, который не учитывает их, ломает логи и коллекции: прокси, положенный в HashSet, будет сравниваться так, как решит обработчик.

Spring строит на прокси свой AOP: @Transactional, @Cacheable, @Async, @PreAuthorize. Для бинов с интерфейсами он может использовать JDK-прокси, как здесь, а для классов — CGLIB-подкласс. У обоих одно ограничение: прокси перехватывает только вызовы снаружи. Вызов через this внутри объекта идёт мимо, и транзакция, кеш или проверка прав не срабатывают. Подробно — в AOP & Proxies.

Декоратор и прокси — это одно и то же, просто разные названия.

Структура одна, назначение разное. Декоратор добавляет поведение, и цепочку явно собирает клиент. Прокси замещает объект и контролирует доступ к нему: лениво создаёт, проверяет права, оборачивает в транзакцию; клиент о нём обычно не знает. На собеседовании ждут именно этого различия.

Facade даёт один простой вход в подсистему из многих классов

Чтобы провести оплату, контроллеру нужно проверить антифрод, посчитать комиссию, списать деньги, записать проводку и отправить уведомление. Если контроллер вызывает пять сервисов сам, он знает порядок шагов, обработку ошибок каждого и что делать при частичном успехе. Это знание копируется во второй контроллер, в обработчик очереди, в админку.

@Service
class CheckoutFacade {                  // Один вход: сценарий оплаты.
    Receipt checkout(Order order) {
        fraud.check(order);
        long fee = fees.calculate(order);
        String bankRef = bank.charge(order.id(), order.cents() + fee);
        ledger.record(order, fee, bankRef);
        notifier.paid(order);
        return new Receipt(order.id(), bankRef, fee);
    }
}

Фасад не запрещает работать с подсистемой напрямую: админка по-прежнему может вызвать ledger. Он даёт короткий путь для частого сценария. Разница с адаптером: адаптер переводит один интерфейс в другой, а фасад упрощает множество интерфейсов до одного нового. JdbcTemplate — фасад над JDBC: соединение, statement, ResultSet и исключения скрыты за query и update, как разобрано в JDBC & Connection Pools.

Опасность фасада — он притягивает всё. Каждый новый сценарий добавляет в него метод, и через год это класс на две тысячи строк, который меняют все команды. Фасад на сценарий или на группу близких сценариев держит его небольшим.

Composite позволяет работать с деревом правил как с одним правилом

Комиссия по карте складывается из процента эквайринга и комиссии банка, а комиссия банка — из фиксированной части и надбавки за 3-D Secure. Правила вкладываются друг в друга, и каждое должно уметь посчитать свою часть. Composite даёт листьям и группам один интерфейс, так что вызывающий не различает, считает он одно правило или целое дерево.

interface FeeRule { long fee(long cents); }

record Percent(String name, int basisPoints) implements FeeRule {
    public long fee(long cents) { return cents * basisPoints / 10_000; } // 150 = 1.5%
}
record Fixed(String name, long cents) implements FeeRule {
    public long fee(long amount) { return cents; }
}
record AllOf(String name, List<FeeRule> rules) implements FeeRule { // Группа — тоже правило.
    public long fee(long cents) { return rules.stream().mapToLong(r -> r.fee(cents)).sum(); }
}

FeeRule card = new AllOf("card", List.of(
        new Percent("acquiring 1.5%", 150),
        new AllOf("bank", List.of(new Fixed("fixed 10", 10), new Percent("3ds 0.1%", 10)))));
card.fee(10_000);
  card[acquiring 1.5%, bank[fixed 10, 3ds 0.1%]]
  fee for 10000: 170

Composite хорош, когда структура действительно древовидная и операции одинаковы для листа и группы: посчитать, вывести, проверить. Если у группы появляются свои операции, которых нет у листа (добавить правило, удалить), их либо поднимают в общий интерфейс и бросают исключение в листе — нарушая LSP, — либо держат только в группе и теряют единообразие. В Spring композиты служат для объединения однотипных стратегий: CompositePropertySource, HandlerMethodArgumentResolverComposite, составные индикаторы health из Actuator.

  • Adapter переводит чужой API в интерфейс, которым владеет твой код; изменения SDK остаются в одном классе.
  • Decorator добавляет одно поведение обёрткой того же интерфейса; порядок обёрток меняет, сколько раз каждая видит вызов.
  • Proxy структурно как декоратор, но контролирует доступ; Spring AOP — прокси, и вызов через this его обходит.
  • Facade упрощает подсистему до одного входа для частого сценария; следи, чтобы он не стал god-классом.
  • Composite даёт листу и группе один интерфейс, и дерево считается как одно правило.

На собеседовании

Чем декоратор отличается от прокси?

Структура одинаковая: тот же интерфейс, ссылка на настоящий объект, код до и после вызова. Разница в назначении. Декоратор добавляет поведение, и цепочку собирает сам клиент: BufferedReader поверх InputStreamReader, логирование поверх повтора. Прокси замещает объект и управляет доступом к нему: ленивое создание, проверка прав, транзакция, удалённый вызов; клиент обычно не знает о нём.

Spring AOP — прокси: @Transactional и @Cacheable работают через объект, который контейнер подставил вместо бина.

  • JDK-прокси генерируется для интерфейсов во время работы; через обработчик идут и equals, hashCode, toString.
  • CGLIB-прокси — подкласс, поэтому не работает с final-классами и методами.
  • И декоратор, и прокси видят только внешние вызовы; this внутри объекта их обходит.

Чем adapter отличается от facade?

Adapter переводит один существующий интерфейс в другой, которого ждёт клиент: SDK банка с рублями в double — в BankGateway с копейками. Набор возможностей тот же, меняется форма. Facade создаёт новый упрощённый интерфейс над несколькими классами подсистемы: checkout вместо пяти вызовов антифрода, банка, проводок и уведомлений.

Адаптер нужен для совместимости, фасад — для удобства и сокрытия сложности.

  • На уровне сервисов адаптер к чужой системе называют anti-corruption layer.
  • Фасад притягивает всё подряд; делят его по сценариям, чтобы он не стал god-классом.
  • В Spring: HandlerAdapter — адаптер, JdbcTemplate — фасад над JDBC.

В каком порядке ставить повтор, логирование и circuit breaker вокруг вызова?

Внешняя обёртка видит вызов один раз, внутренняя — столько раз, сколько её вызвала внешняя. Если лог внутри повтора, в логе каждая попытка; если снаружи — один вызов бизнеса. В демо при Retrying(Logging(...)) лог появился дважды, при Logging(Retrying(...)) — один раз.

Обычно circuit breaker ставят снаружи повтора, чтобы при открытом breaker повторы не выполнялись вовсе, а метрику длительности для клиента — снаружи всего.

  • Breaker внутри повтора считает каждую попытку отдельной ошибкой и открывается быстрее.
  • В Spring порядок прокси задаёт @Order аспектов или явная конфигурация Resilience4j.
  • Таймаут на одну попытку ставят внутри повтора, общий срок — снаружи.
Почему метрика ошибок банка показывает втрое больше отказов, чем видят клиенты? 
BankGateway bank = new Retrying(3,
        new Metrics(registry,            // Считает ошибки вызовов банка.
            new TinkoffAdapter(sdk)));

Metrics стоит внутри повтора и считает каждую попытку. Клиент, у которого третья попытка прошла, получил успех, а метрика записала две ошибки. Это может быть нужно, если метрика про здоровье банка. Для метрики пользовательских отказов обёртку ставят снаружи повтора, а иногда держат обе.

Где структурные паттерны встречаются в JDK и Spring?

Декоратор — потоки ввода-вывода: BufferedReader поверх InputStreamReader поверх FileInputStream; Collections.synchronizedList. Прокси — java.lang.reflect.Proxy и весь Spring AOP: транзакции, кеш, безопасность. Адаптер — HandlerAdapter в Spring MVC и MessageListenerAdapter. Фасад — JdbcTemplate и RestClient. Composite — CompositePropertySource и составные индикаторы health.

  • BeanPostProcessor — точка, где Spring заменяет бин прокси или декоратором.
  • FilterChain сервлета — цепочка декораторов вокруг запроса, разобранная в теме про Tomcat.
  • Gamma, Helm, Johnson, Vlissides, Design Patterns, глава 4 — основа урока: adapter, decorator, proxy, facade, composite.
  • Refactoring.Guru: Structural Patterns — сравнение декоратора и прокси, схемы.
  • java.lang.reflect.Proxy javadoc — какие методы попадают в обработчик.
  • Spring Framework Reference: Proxying Mechanisms — JDK и CGLIB прокси, self-invocation.
