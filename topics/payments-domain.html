Payments

Платёж проходит через несколько участников, и каждый видит свою часть исполнения. Банк может одобрить покупку, пока продавец ещё не получил деньги. Запрос на завершение оплаты может быть принят, а его результат прийти позже. Поэтому статус должен отвечать на конкретный вопрос: что разрешено, что исполнено, между кем завершён расчёт и что мы об этом знаем. Карта, СБП и перевод через сообщения SWIFT решают эту задачу разными путями.

Одобренная покупка ещё не означает выплату продавцу

Alice покупает товар за 120 ₽. Она подтверждает оплату, приложение банка показывает удержанную сумму, сайт пишет «успешно». Но магазин пока не получил выплату. Деньги не потерялись: слово «успешно» смешало несколько разных событий. Банк одобрил операцию, а завершение покупки и расчёты с магазином имеют собственные стадии.

В карточном сценарии с раздельной авторизацией и завершением авторизация разрешает операцию и связывается с резервированием суммы у эмитента. Capture — команда завершить оплату по этой авторизации. Дальше информация участвует в клиринге и расчётах. Выплата продавцу со стороны его провайдера может идти по отдельному графику. Эти границы нужны, даже если API объединяет первые действия одним запросом.

В StageDemo.java локально моделируются подтверждённые стадии покупки. Все целые суммы — копейки RUB. Это учебный порядок, без сетевого клиента и без имитации точных моментов проводок каждого банка. Запуск на JDK 21: java -ea examples/payments-domain/StageDemo.java.

static final class Payment {
    final long requested = 12_000;
    long authorised, captureRequested, captured, settledGross, paidOut;
    String captureState = "NONE";
    void authorise() { authorised = requested; }
    void requestCapture() {
        captureRequested = authorised; captureState = "REQUESTED";
    }
    void confirmCapture() {
        captured = captureRequested; captureState = "CONFIRMED";
    }
    void failCapture() { captureState = "FAILED"; }
    void settle() {
        if (captured == 0) throw new IllegalStateException("not captured");
        settledGross = captured;
    }
    void payout(long fee) {
        if (settledGross == 0 || fee < 0 || fee > settledGross)
            throw new IllegalArgumentException("invalid payout");
        paidOut = settledGross - fee;
    }
    void show(String tag) {
        System.out.printf("%s auth=%d capture=%s captured=%d settled=%d paid=%d%n",
            tag, authorised, captureState, captured, settledGross, paidOut);
    }
}
static void authorisation() {
    Payment p = new Payment(); p.authorise(); p.show("approved");
    if (p.paidOut != 0) throw new AssertionError();
}

На стадии approved известно только об авторизации 12 000 копеек. Нули остальных полей здесь относятся к специально заданному учебному сценарию: следующие действия ещё не выполнялись. При наблюдении реального провайдера отсутствие события нельзя автоматически превращать в доказанный нулевой результат. Эту разницу покажем отдельно.

Аутентификация покупателя и авторизация платежа решают разные вопросы

3-D Secure помогает проверить участие держателя карты: например, через подтверждение в приложении банка. Это аутентификация. Платёжная авторизация отвечает на другой вопрос: одобряется ли конкретная операция с учётом суммы, состояния карты, средств и проверок риска. Успешная проверка покупателя сама по себе не гарантирует одобрения, capture или расчёта. Разделение видно и в документации Stripe об аутентификации, где результат проверки можно использовать для последующей авторизации.

Какой момент позволяет отдать товар, определяет договорённость продукта с провайдером и риск бизнеса. Для мгновенной цифровой услуги и отгрузки товара через несколько дней нужны разные решения. Условие должно ссылаться на подтверждённое событие, а не на слово success в любом ответе.

Эмитент отвечает за карту, эквайер — за приём оплаты продавцом

Эмитент выпускает карту и обслуживает связанный с ней платёжный продукт держателя. В выбранном онлайн-сценарии он проверяет запрос авторизации и одобряет либо отклоняет его. Эквайер обеспечивает продавцу приём карточных операций и участвует в расчётной стороне. Эти роли задаются конкретной операцией: один банк может выпускать карту Alice и одновременно принимать оплаты у другого магазина.

Карточная платёжная система задаёт правила взаимодействия и связывает участников обработки и расчётов. PSP, payment service provider, предоставляет продавцу платёжный интерфейс и дополнительные услуги. PSP может объединять шлюз и эквайринговые функции либо работать с другими эквайерами. HTTP-адрес, куда обращается сервис магазина, ещё не объясняет, кто фактически принял решение и кто должен деньги продавцу.

Это распространённый онлайн-маршрут, а не единственная форма карточной обработки. При on-us эмитент и эквайер могут совпасть. При автономной обработке или решении сети от имени недоступного эмитента порядок отличается. Для backend важнее знать, кто дал конкретное подтверждение и что оно означает, чем считать обязательным ровно четыре сетевых узла.

Capture, клиринг, расчёт и выплата завершают разные части работы

После авторизации магазин просит завершить оплату: например, когда товар готов к отправке. Capture может быть автоматическим, ручным или отложенным. В двухстадийном сценарии отдельно сохраняй сумму авторизации и проведённую сумму. Окончательная сумма может быть меньше первоначального резерва; допустимость частичных действий и увеличение суммы определяются правилами продукта.

Клиринг готовит денежные обязательства к расчёту: сведения передаются, сопоставляются, проверяются, формируются позиции участников. В некоторых моделях встречные требования сворачиваются в нетто-позицию. Settlement, расчёт, исполняет эти обязательства через расчётные счета и выбранный расчётный механизм. Это разделение определено в глоссарии BIS / CPMI; клиринг не сводится только к вычитанию двух сумм.

Неттинг уменьшает расчётную позицию, но не число покупок

В учебной пачке карты банка A использованы в магазинах эквайера B на 120 и 80 ₽. Встречная покупка картой B у эквайера A — 50 ₽. Без учёта комиссий встречные обязательства дают A → B 200 ₽ и B → A 50 ₽. При выбранном двустороннем неттинге A должен перечислить B 150 ₽. Три исходные покупки сохраняются для обслуживания клиентов и сверки.

record Purchase(String issuer, String acquirer, long minor) {}
public static void main(String[] args) {
    List<Purchase> batch = List.of(
        new Purchase("A", "B", 12_000), new Purchase("A", "B", 8_000),
        new Purchase("B", "A", 5_000)); // Оба банка играют разные роли в разных покупках.
    Map<String, Long> netDebit = new TreeMap<>();
    long gross = 0;
    for (Purchase p : batch) {
        gross = Math.addExact(gross, p.minor());
        netDebit.merge(p.issuer(), p.minor(), Math::addExact);
        netDebit.merge(p.acquirer(), -p.minor(), Math::addExact);
    }
    System.out.println("gross=" + gross);
    System.out.println("net-debit=" + netDebit);
    System.out.println("settlement A->B=" + netDebit.get("A"));
    if (netDebit.get("A") != 15_000 || netDebit.get("B") != -15_000)
        throw new AssertionError();
}
gross=25000
net-debit={A=15000, B=-15000}
settlement A->B=15000

Полный источник — ClearingDemo.java. Положительный net-debit здесь значит «участник должен заплатить», отрицательный — «получить». Сумма покупок 25 000 копеек отличается от расчётного движения 15 000. Подменить отдельный платёж этой нетто-суммой нельзя: у него другой получатель и другое основание.

Получение средств провайдером и выплата магазину могут быть разными событиями

В StageDemo сначала принимается команда capture, потом приходит подтверждённый результат, затем сведения о получении 120 ₽ провайдером и выплате магазину 117 ₽ после учебной комиссии 3 ₽. Суммы и порядок заданы для примера. Слово Settled всегда читай вместе с тем, между кем завершён расчёт.

static void captureAndPayout() {
    Payment p = new Payment(); p.authorise();
    p.requestCapture(); p.show("accepted-command");
    p.confirmCapture(); p.show("confirmed-capture");
    p.settle(); p.show("settlement-report");
    p.payout(300); p.show("merchant-payout"); // Учебная комиссия 3 RUB, не тариф провайдера.
    if (p.paidOut != 11_700) throw new AssertionError();
}

В Adyen Payments Lifecycle Settled означает, что средства получены Adyen; выплату продавцу определяет модель payout. В Adyen Capture успешное уведомление о принятии capture может позже сопровождаться CAPTURE_FAILED. Поэтому собственный статус «деньги получены» нельзя выводить только из HTTP-ответа о принятой команде.

static void acceptedThenFailed() {
    Payment p = new Payment(); p.authorise(); p.requestCapture();
    p.failCapture(); p.show("later-failure");
    if (p.captured != 0 || p.settledGross != 0) throw new AssertionError();
}

В демо FAILED относится именно к capture, авторизация остаётся отдельным фактом. Это не полная машина состояний провайдера: освобождение резерва и возможный повтор требуют его правил. Срок действия авторизации, обработка после него и расписание расчёта отличаются по сети, способу оплаты и договорённости. Универсального «всегда списывается через сутки» здесь нет.

Статус должен хранить подтверждённые факты и неизвестный результат

Если запрос ушёл, а ответ не вернулся, сервис знает о таймауте своей связи. Он ещё не знает, отказал ли банк, удержал ли сумму или завершил ли действие. UNKNOWN описывает эту неопределённость наблюдения. DECLINED описывает подтверждённое отклонение конкретной попытки. Перевести один в другой по истечению собственного таймера — значит выдать отсутствие сведений за банковское решение.

Сохраняй разные идентификаторы. Номер заказа связывает бизнес-покупку, идентификатор попытки — один выбранный путь оплаты. Провайдер присваивает свой идентификатор операции; у capture и возврата могут быть отдельные ссылки. Идентификатор события помогает узнавать повтор сообщения. Ключ идемпотентности связывает повтор команды с исходным действием. Совпадение слов «reference» в двух API ещё не делает их одной сущностью.

Неупорядоченная доставка также не равна неупорядоченному исполнению. Сообщение об авторизации может прийти позже отчёта о расчёте. Если присваивать status = event.status, поздний AUTHORISED откатит видимое состояние рассчитанного платежа. Лучше хранить сведения о стадиях отдельно и выводить представление из имеющихся фактов.

StatusFactsDemo.java хранит по одному подтверждённому итогу авторизации, capture и расчёта. Неизвестная сумма — null, а не ноль. Это модель с одной авторизацией и одним полным capture; подтверждённые возвраты поступают отдельными событиями. Для нескольких частичных capture нужны отдельные операции и их суммы.

enum Type { AUTHORISED, CAPTURED, SETTLED, REFUNDED, DISPUTE_OPENED }
record Event(String id, String payment, Type type, long minor) {}

static final class Facts {
    final String payment = "psp-1";
    final Map<String, Event> seen = new HashMap<>();
    Long authorised, captured, settled;
    long refunded;
    boolean dispute;
    String observation = "WAITING";
    void timeout() { observation = "UNKNOWN"; } // Локальное знание, а не отказ банка.
    boolean apply(Event e) {
        if (!payment.equals(e.payment())) throw new IllegalArgumentException("wrong payment");
        Event old = seen.get(e.id());
        if (old != null) {
            if (!old.equals(e)) throw new IllegalArgumentException("event conflict");
            return false;
        }
        if (e.minor() <= 0) throw new IllegalArgumentException("invalid amount");
        switch (e.type()) {
            case AUTHORISED -> authorised = e.minor();
            case CAPTURED -> captured = e.minor();
            case SETTLED -> settled = e.minor();
            case REFUNDED -> refunded = Math.addExact(refunded, e.minor());
            case DISPUTE_OPENED -> dispute = true;
        }
        seen.put(e.id(), e); observation = "OBSERVED";
        return true;
    }
    static String value(Long n) { return n == null ? "unknown" : n.toString(); }
    void show(String tag) {
        String financial = settled != null ? "SETTLED" : captured != null ? "CAPTURED"
            : authorised != null ? "AUTHORISED" : "UNKNOWN";
        System.out.printf("%s observation=%s financial=%s auth=%s captured=%s settled=%s refunded=%d dispute=%s%n",
            tag, observation, financial, value(authorised), value(captured), value(settled),
            refunded, dispute ? "OPEN" : "NONE");
    }
}
static void uncertainAndOutOfOrder() {
    Facts f = new Facts(); f.timeout(); f.show("timeout");
    // Присланы подтверждённые сведения, но порядок доставки отличается от порядка исполнения.
    f.apply(new Event("e3", "psp-1", Type.SETTLED, 12_000)); f.show("settled-first");
    f.apply(new Event("e1", "psp-1", Type.AUTHORISED, 12_000)); f.show("late-authorisation");
    f.apply(new Event("e2", "psp-1", Type.CAPTURED, 12_000)); f.show("late-capture");
    if (f.settled != 12_000) throw new AssertionError();
}

Состояние SETTLED остаётся прежним, хотя подробности заполняются позже. Оно не значит, что дальнейших событий не будет: возможны возврат и спор. Поэтому у платежа отдельно сохраняются исходное исполнение, возвращённая сумма и состояние спора.

static void refundsAndDispute() {
    Facts f = new Facts();
    f.apply(new Event("e1", "psp-1", Type.AUTHORISED, 12_000));
    f.apply(new Event("e2", "psp-1", Type.CAPTURED, 12_000));
    f.apply(new Event("e3", "psp-1", Type.SETTLED, 12_000));
    Event refund = new Event("r1", "psp-1", Type.REFUNDED, 4_000);
    System.out.println("refund-first=" + f.apply(refund));
    System.out.println("refund-repeat=" + f.apply(refund));
    f.apply(new Event("d1", "psp-1", Type.DISPUTE_OPENED, 12_000));
    f.show("after-refund-and-dispute");
    try { f.apply(new Event("r1", "psp-1", Type.REFUNDED, 4_100)); }
    catch (IllegalArgumentException e) { System.out.println("conflict=" + e.getMessage()); }
    if (f.refunded != 4_000) throw new AssertionError();
}

Здесь refunded — сумма наблюдённых подтверждений возврата, а OPEN означает открытый спор. Сам спор ещё не доказывает окончательного списания спорной суммы. При его открытии провайдер может уже удержать спорную сумму или создать резерв; это отдельное денежное изменение, а окончательное решение ещё впереди. Демо узнаёт повтор одного event.id; в рабочем контракте также нужен идентификатор самой операции возврата, если о ней поступают несколько разных событий. Противоречащие сведения требуют сохранения исходного сообщения и разбирательства, а не выбора «самого старшего» enum по порядковому номеру.

Для восстановления неизвестного результата опрашивают провайдера по сохранённой операции, принимают подтверждения и сверяют отчётные сведения. Повтор команды сохраняет её ключ и параметры. Подробная архитектура устойчивой обработки разобрана в Payment System и Idempotency. Здесь важно правильно определить смысл результата до проектирования повторов.

СБП переводит между счетами, а SWIFT передаёт инструкции участникам расчёта

У СБП плательщик переводит деньги между банковскими счетами; наличие карты не определяет этот способ оплаты. Для покупки клиент получает реквизиты платежа, например из QR-кода, проверяет получателя и подтверждает действие в банковском интерфейсе. Банк России описывает СБП как круглосуточный сервис переводов в реальном времени, а не как карточную авторизацию с отдельным capture.

Банк России выступает оператором и расчётным центром СБП, НСПК выполняет операционные и платёжные клиринговые функции. Это роли инфраструктуры, а клиентские счета обслуживают банки-участники. Поля и уведомления, которые увидит сервис продавца, определяет его банковская интеграция. Быстрота расчёта не гарантирует мгновенного получения сообщения нашим HTTP-клиентом.

QR-код содержит или связывает сведения о платеже. Его создание и сканирование ещё не доказывают, что деньги зачислены. Подтверждение в приложении клиента и редирект на сайт тоже не заменяют проверку результата на банковской стороне. Подписка или разрешение на будущие списания относятся к согласию на операции; их состояние следует хранить отдельно от исполнения каждой покупки.

У SWIFT сообщения и денежный расчёт находятся на разных слоях

SWIFT предоставляет защищённый обмен финансовыми сообщениями. В официальном FAQ прямо разделены передача платёжной инструкции и фактический перевод средств участниками. Поэтому подтверждение доставки сообщения в сеть ещё не является подтверждением зачисления конечному получателю.

Разберём упрощённый перевод 100 EUR без FX и комиссий. У банков A и B есть счета в банке-корреспонденте C. По согласованной инструкции C уменьшает свой долг перед A на 100 EUR и увеличивает долг перед B на 100 EUR. Банк B отражает зачисление клиенту по своему процессу. Инструкция может передаваться через SWIFT; денежное изменение происходит в книгах банков.

Для A его счёт у C — nostro: «наш счёт у вас», актив A. Для C тот же счёт — vostro: «ваш счёт у нас», обязательство C. Это две перспективы одного отношения, а не два независимых мешка денег. Для перевода могут потребоваться несколько корреспондентов, конвертация и проверки; время и сумма зачисления зависят от всего маршрута.

UETR — сквозная ссылка для отслеживания платёжной инструкции. Она связывает сведения участников цепочки; сама ссылка не доказывает успешного зачисления. При расследовании нужны конкретный результат и сторона, которая его сообщила: инструкция принята, задержана, отклонена или средства зачислены получателю.

Обобщай подтверждённые факты и доступные действия, оставляя детали конкретному способу.

Отмена, возврат и спор требуют разных денежных действий

Если сумма только зарезервирована, отмена авторизации прекращает дальнейшее использование этого разрешения и связана с освобождением резерва. В карточном языке reversal может относиться к обратному сообщению об авторизации; точный смысл зависит от стадии. Если оплата уже исполнена, возврат представляет новое связанное денежное движение. Освободить старый hold вместо возврата проведённой суммы нельзя.

У возврата свой идентификатор и свой результат. Принятие заявки ещё не означает, что клиент получил деньги. Возврат может быть частичным, а несколько возвратов относятся к одной исходной оплате. Сумму, доступную для новой заявки, надо уменьшать и на уже подтверждённые возвраты, и на ожидающие исполнения. Иначе две заявки успеют запросить больше исходной оплаты.

RefundDemo.java моделирует оплату 120 ₽ и заявки в одном потоке. Первая заявка 80 ₽ ещё ожидает подтверждения, поэтому для второй доступны только 40 ₽. Это ограничение принятия команды, а не банковский учёт уже исполненного возврата.

enum State { PENDING, CONFIRMED, FAILED }
record Refund(long minor, State state) {}
static final class Payment {
    final long captured = 12_000;
    final Map<String, Refund> refunds = new LinkedHashMap<>();
    long remaining() {
        long committed = 0;
        for (Refund r : refunds.values())
            if (r.state() != State.FAILED) committed = Math.addExact(committed, r.minor());
        return Math.subtractExact(captured, committed); // И подтверждённые, и ещё ожидаемые.
    }
    boolean request(String id, long amount) {
        Refund old = refunds.get(id);
        if (old != null) {
            if (old.minor() != amount) throw new IllegalArgumentException("id conflict");
            return false;
        }
        if (amount <= 0 || amount > remaining()) throw new IllegalArgumentException("refund exceeds available");
        refunds.put(id, new Refund(amount, State.PENDING));
        return true;
    }
    void resolve(String id, State state) {
        Refund old = refunds.get(id);
        if (old == null || old.state() != State.PENDING || state == State.PENDING)
            throw new IllegalArgumentException("invalid resolution");
        refunds.put(id, new Refund(old.minor(), state));
    }
}
public static void main(String[] args) {
    Payment p = new Payment();
    p.request("r1", 8_000); System.out.println("pending remaining=" + p.remaining());
    try { p.request("r2", 5_000); }
    catch (IllegalArgumentException e) { System.out.println("second=" + e.getMessage()); }
    p.resolve("r1", State.CONFIRMED);
    System.out.println("confirmed remaining=" + p.remaining());
    System.out.println("retry=" + p.request("r1", 8_000));
    p.request("r3", 4_000); p.resolve("r3", State.FAILED);
    System.out.println("failed remaining=" + p.remaining());
    if (p.remaining() != 4_000) throw new AssertionError();
}

second=refund exceeds available

retry=false

Пока r1 ожидает и после её подтверждения доступно одинаково 4 000 копеек. Отказ по r3 освобождает сумму для новой заявки. UNKNOWN после таймаута не следует приравнивать к такому отказу: ожидающее действие ещё могло состояться. В рабочей системе проверка доступной суммы и регистрация заявки имеют общую транзакционную границу.

Спор не стирает исходный расчёт

Dispute означает процедуру оспаривания операции, а chargeback — соответствующее обратное денежное действие по правилам карточного процесса. Исходная оплата при этом сохраняется в истории. Могут появиться спорная сумма, комиссия, сроки представления сведений и последующие решения. Ответ «платёж окончательный» должен уточнять: завершён текущий расчёт или больше невозможны никакие связанные события.

Возврат и спор способны пересечься. Поэтому состояние спора ведут отдельно от возвращённой суммы и сопоставляют реальные движения: автоматическое «вернуть ещё раз» при открытии спора может создать лишнее возмещение. Для СБП и других способов процедура возврата и разрешения спорной ситуации имеет собственные правила; карточный chargeback нельзя переносить на них как универсальное API.

Границы главы — доменные значения, а не полный регламент сети. Онлайн-авторизация с отдельным capture не покрывает автономную обработку, изменение авторизованной суммы и позднее предъявление операции. Право выполнить действие, срок и доверенное подтверждение проверяются по выбранному продукту и провайдеру. Суммы, проводки и резервы разобраны в Banking Basics; архитектура доставки событий и повторов — в Payment System. Прежде чем писать обработчик статуса, сформулируй, какое денежное событие он подтверждает.

  • Авторизация разрешает операцию; capture завершает оплату в выбранном карточном процессе. Ни одно слово success не описывает весь путь.
  • Эмитент и эквайер — роли сторон покупки. PSP предоставляет интеграцию и может объединять несколько функций.
  • Клиринг готовит обязательства к расчёту. Расчёт между участниками и выплата продавцу могут быть разными событиями.
  • Таймаут означает неизвестность наблюдения. Сохраняй попытки, операции и подтверждённые сведения раздельно.
  • Карта, СБП и обмен сообщениями SWIFT имеют разные модели; интерфейс должен сохранять их смысл.
  • Отмена резерва, возврат проведённого и оспаривание исходной оплаты не заменяют друг друга.

На собеседовании

Чем эмитент отличается от эквайера и где здесь PSP?

Я разделяю стороны операции. Эмитент выпускает карту и обслуживает держателя; в обычной онлайн-авторизации он решает, одобрить ли запрос. Эквайер обслуживает приём карточной оплаты продавцом и участвует в расчётах. Карточная система связывает участников и задаёт правила.

PSP даёт продавцу платёжную интеграцию. Он может сам выполнять эквайринговые функции или работать с отдельными эквайерами. Поэтому по адресу платёжного API я ещё не определю, кто принял решение и между кем завершён расчёт.

  • Один банк может быть эмитентом в одной покупке и эквайером в другой. On-us сокращает маршрут, но не меняет смысл ролей.
  • У результата есть источник: собственная проверка PSP, решение эмитента, ответ сети. Причина отказа зависит от этой границы.
  • Авторизацию платежа отделяю от аутентификации держателя через 3DS. Проверка участия клиента не гарантирует денежного исполнения.

Что происходит после авторизации: capture, клиринг и settlement?

Авторизация одобряет операцию и связана с резервом. В раздельном процессе capture запрашивает завершение оплаты. Клиринг готовит обязательства участников к расчёту, иногда с неттингом. Settlement исполняет эти обязательства через расчётную инфраструктуру.

Я отдельно уточню выплату продавцу. Провайдер может уже получить расчётные средства, а магазин — получить их позже в своей выплате. Поэтому собственное «оплачено» связываю с определённым подтверждением и правилами продукта.

  • Сумма авторизации и итоговая сумма могут отличаться. Для нескольких capture нужна история отдельных завершений, а не одно перезаписываемое число.
  • Расчётная нетто-позиция не заменяет исходные покупки. Их отдельные основания нужны для клиентских операций и сверки.
  • Завершённый расчёт сохраняется в истории даже при последующем возврате или chargeback.
Можно ли считать средства полученными после ответа «capture принят»?

Нужно прочитать контракт именно этого результата. Подтверждение команды может означать её отправку на обработку, а позднее прийти отказ. В демо после принятия captured, settled и paid всё ещё нули. Ожидай событие или отчёт, который подтверждает нужную стадию, и сохраняй отдельное состояние обработки команды.

Какой статус поставить после таймаута и как обработать позднее подтверждение?

После отправленного запроса таймаут означает, что мне неизвестен результат. Я сохраню попытку и её идентификаторы, затем восстановлю сведения через провайдера и его подтверждения. Отказом обозначаю подтверждённое отклонение, а не отсутствие ответа.

Позднее сообщение сопоставлю с той же операцией и уже известными фактами. Если об исполнении известно больше, событие прежней стадии дополнит историю. Авторизация, пришедшая после расчёта, не должна откатить рассчитанный платёж назад.

  • Идентификатор сообщения и идентификатор денежной операции — разные уровни. Несколько уведомлений могут описывать один возврат.
  • При противоречии сохраняю исходные сведения и инициирую проверку. Порядковый номер enum не определяет истинность сообщения.
  • Отдельно храню исполнение, возвращённую сумму и спор. Одно поле SETTLED не описывает открытую процедуру оспаривания.
После таймаута capture сняли hold и решили, что возврат не нужен. Где ошибка?

Локальный таймаут не доказывает, что capture не исполнился. Снятие резерва и возврат уже проведённых средств — разные денежные действия. Сначала восстанови результат исходной операции, затем выбери допустимое действие по её подтверждённой стадии. Скрыть неизвестность общим состоянием «отменён» опасно.

Чем СБП и перевод через SWIFT отличаются от карточной оплаты?

Карточная оплата связывает держателя, эмитента, эквайринговую сторону и правила карточного продукта. СБП — банковский перевод между счетами; QR-код помогает задать платёж, а результат относится к самому переводу. Карточные авторизация и capture не становятся обязательными стадиями СБП.

SWIFT передаёт финансовые инструкции. Деньги учитываются и перемещаются участниками через их счета и расчётные отношения. Поэтому доставленное сообщение отличается от зачисления получателю. Сквозная ссылка помогает проследить цепочку, но успешный результат всё равно надо подтвердить.

  • Одинаковое слово «успешно» в интеграциях может означать принятие команды, исполнение или зачисление. Обобщаю семантику, сохраняя источник подтверждения.
  • Корреспондентский перевод может включать FX и несколько участников. Сообщение без данных о комиссии и валюте не объясняет итоговую сумму.
  • Правила отмены, возврата и спора выбираю по способу и стадии. Карточный chargeback не является общим механизмом всех переводов.
Покупатель показал экран «СБП успешно» и вернулся на сайт. Можно ли исполнить заказ по этому экрану?

Экран относится к клиентскому интерфейсу и не заменяет проверку в нашей банковской интеграции. Сопоставь подтверждение перевода с нужной попыткой, получателем, суммой и валютой. Если сообщение задержалось, результат пока неизвестен сервису; это не повод автоматически создавать новую оплату.

  • BIS / CPMI Glossary — определения clearing, settlement и netting; учебный двусторонний расчёт отдельно от правил реальной сети.
  • Банк России: Система быстрых платежей и устройство инфраструктуры СБП — переводы между счетами, роли Банка России и НСПК. Тарифы и лимиты в урок не включены.
