Performance Antipatterns

Большинство проблем производительности backend — не медленный код, а лишние круги по сети и лишние данные. Каждый запрос к базе стоит как минимум круг по сети, и при миллисекунде на круг 200 запросов в цикле — это уже 334 мс, тогда как те же данные двумя запросами приходят за 4 мс. Тысяча вставок с отдельными коммитами — 1,6 с, пакетом — 17 мс. Выборка 100 000 строк, чтобы посчитать сумму в Java, проигрывает агрегату в SQL в 18 раз. Остальные антипаттерны из каталога Azure — busy database, noisy neighbor, синхронный ввод-вывод, retry storm — сводятся к тому же: работа делается не там, не так часто или не теми ресурсами.

Страница заказов: 40 мс на ноутбуке, 400 мс в продакшене

Разработчик проверил страницу истории заказов локально: база на той же машине, ответ за 40 мс. В продакшене база в соседней зоне доступности, круг по сети — около миллисекунды, и страница отвечает за 400 мс. Код тот же; разница — в числе обращений к базе, которое локально было незаметно. Hibernate загружал позиции каждого заказа отдельным запросом при первом обращении к ленивой коллекции — классический N+1.

Демо AntipatternsDemo.java воспроизводит продакшен-условия: отдельный PostgreSQL 17 в Docker, к сетевому интерфейсу которого добавлена задержка 1 мс через tc netem. Данные — 20 000 заказов по 5 позиций. Порядки задержек разобраны в Back-of-the-envelope, планы запросов — в Query Tuning.

Chatty I/O: N+1 запросов вместо одного-двух

// N+1: позиции каждого заказа — отдельным запросом.
ResultSet o = c.createStatement().executeQuery("select id from orders order by id limit 200");
var ps = c.prepareStatement("select sku, price from item where order_id = ?");
while (o.next()) {
    ps.setInt(1, o.getInt(1));
    try (ResultSet r = ps.executeQuery()) { while (r.next()) items++; }
}

// Два запроса: заказы, затем все их позиции одним = ANY(массив).
var ps = c.prepareStatement("select order_id, sku, price from item where order_id = any(?)");
ps.setArray(1, c.createArrayOf("int4", ids.toArray()));
== load 200 orders with their items (1 ms network round trip)
   N+1: one query per order           334 ms   201 queries, 1000 items
   one JOIN                             8 ms   1 query, 1000 items
   two queries, = ANY(array)            4 ms   2 queries, 1000 items

N+1 опасен тем, что не виден локально: на машине разработчика круг по сети — десятки микросекунд, и 201 запрос занимает пару десятков миллисекунд. В JPA он появляется при обращении к ленивым коллекциям в цикле; лечат join fetch, @EntityGraph или @BatchSize — последний превращает N запросов в N/размер пачки, как разобрано в Relations & Fetching. Обнаруживают по числу запросов на запрос пользователя: счётчик запросов Hibernate в тестах или трассировка, где под одним HTTP-запросом сотни одинаковых SQL.

Один JOIN оказался вдвое медленнее двух запросов — 8 мс против 4. EXPLAIN ANALYZE показал, что для JOIN планировщик выбрал hash join с полным проходом по всем 100 000 позициям, а = ANY идёт по индексу. «Меньше запросов» — не самоцель; цель — меньше кругов и разумный план для каждого. JOIN к тому же размножает строки родителя на каждую дочернюю, что при больших строках заказа даёт лишний трафик.

Extraneous fetching: тянуть всё, чтобы посчитать одно

== revenue of customer 7
   fetch all items, sum in Java        18 ms   rows transferred 100000, revenue 47800
   sum in SQL                           1 ms   rows transferred 1, revenue 47800

Чтобы посчитать выручку одного клиента, код выбрал все 100 000 позиций с номером клиента и отфильтровал в Java: 18 мс и 100 000 строк по сети ради 25 нужных. Агрегат в SQL с условием по индексу вернул одну строку за миллисекунду — фактически за один круг. На полной таблице в миллионы строк разница растёт линейно, а память приложения забивается строками, которые сразу выбрасываются. Та же ошибка в мелком масштабе — select * там, где нужны два столбца, или загрузка сущности с коллекциями ради одного поля: лишние данные читаются с диска, передаются и разбираются.

Обратная ошибка — busy database: перенос в базу тяжёлой логики, которая там не нужна, например формирования отчётов на основной базе в часы пик или бизнес-правил в хранимых процедурах, которые конкурируют за процессор с транзакциями. Фильтры и агрегаты — в базу; вычисления, не требующие данных, и тяжёлая аналитика — в приложение или на реплику, как в Replication.

Запись по одной строке: тысяча кругов и тысяча коммитов

== insert 1000 rows
   one insert per row, autocommit    1559 ms   1000 round trips, 1000 commits
   JDBC batch, one transaction         17 ms   batched round trips, 1 commit

Тысяча вставок в режиме autocommit — тысяча кругов по сети и тысяча коммитов, каждый со сбросом журнала: 1,56 с. Пакет JDBC в одной транзакции — 17 мс, в 90 раз быстрее: драйвер отправляет команды пачками, а коммит один. С параметром reWriteBatchedInserts=true pgjdbc ещё и склеивает вставки в многострочный INSERT. В Hibernate пакетная запись включается hibernate.jdbc.batch_size, но не работает с GenerationType.IDENTITY: чтобы узнать id, Hibernate вынужден вставлять строки по одной.

Диагностика у всех одна: измерять число запросов и данных на одну операцию пользователя, а не только время. Трассировка показывает лишние круги, pg_stat_statements — запросы с огромным числом вызовов или строк, как в Slow Queries. Тесты производительности с задержкой сети, как в этом демо, ловят N+1 до продакшена.

Запрос выполняется за 0,1 мс — значит, делать его в цикле не страшно.

Время выполнения в базе не включает круг по сети. В демо каждый запрос N+1 сам по себе мгновенный, но 201 круг с задержкой 1 мс дал 334 мс против 4 мс у двух запросов. Локально разница незаметна, в продакшене — в 80 раз.

  • С кругом по сети 1 мс: N+1 на 200 заказов — 334 мс, два запроса с = ANY — 4 мс, JOIN — 8 мс из-за выбранного плана.
  • Сумма в Java по 100 000 строкам — 18 мс, агрегат в SQL — 1 мс и одна строка.
  • 1 000 вставок с autocommit — 1,56 с, пакет в одной транзакции — 17 мс.
  • Считать число запросов и строк на операцию пользователя; тестировать с задержкой сети.
  • Остальные антипаттерны: busy database, синхронный ввод-вывод, нет кеша, noisy neighbor, retry storm.

На собеседовании

Что такое проблема N+1 и как её найти и исправить?

Один запрос за списком и по одному запросу на каждый элемент за связанными данными. Каждый запрос быстрый, но круги по сети складываются: в демо 201 запрос — 334 мс против 4 мс у двух. Исправляют загрузкой связанных данных одним запросом — JOIN или where id = any(...); в JPA — join fetch, EntityGraph или BatchSize. Находят по числу SQL на один HTTP-запрос: трассировка, счётчики Hibernate в тестах.

  • Локально незаметен: круг по сети там — десятки микросекунд.
  • Один JOIN не всегда быстрее двух запросов: смотреть план; JOIN размножает строки родителя.
  • Тест с netem-задержкой ловит N+1 до продакшена.
Сколько запросов сделает этот код на странице из 50 заказов? 
@Transactional(readOnly = true)
public List<OrderDto> page(long customerId) {
    return orders.findTop50ByCustomerIdOrderByIdDesc(customerId).stream()
        .map(o -> new OrderDto(o.getId(),
                               o.getItems().size(),                 // LAZY
                               o.getDelivery().getCity()))          // LAZY @ManyToOne
        .toList();
}

1 запрос за заказами, затем 50 за позициями и до 50 за доставкой — до 101 запроса; при 1 мс на круг — около 100 мс только на сеть. Нужны @EntityGraph(attributePaths = {"items", "delivery"}) или join fetch, а для количества позиций лучше проекция с count в запросе, чтобы не загружать сами позиции.

Как ускорить массовую запись в базу?

Писать пакетами в одной транзакции, а не по строке с autocommit: каждый коммит — круг по сети и сброс журнала. В демо 1 000 строк — 1,56 с по одной и 17 мс пакетом. В pgjdbc — reWriteBatchedInserts, в Hibernate — jdbc.batch_size; для очень больших объёмов — COPY.

  • Hibernate не пакетирует вставки при IDENTITY — нужен SEQUENCE с allocationSize.
  • Слишком большие транзакции держат блокировки и мешают VACUUM — пачки по тысячам строк.

Какие антипаттерны производительности вы знаете?

Chatty I/O — много мелких запросов вместо немногих; extraneous fetching — выборка лишних строк и столбцов; busy database — тяжёлая логика в базе; synchronous I/O — потоки, ждущие сеть; отсутствие кеша для неизменных данных; noisy neighbor — один клиент съедает общий ресурс; retry storm — повторы, усиливающие сбой.

  • Метрика — запросы и строки на операцию пользователя, а не только время.
  • pg_stat_statements: calls и rows выдают chatty и extraneous.

  • pgjdbc: reWriteBatchedInserts.
  • Hibernate: Batching — batch_size и ограничение IDENTITY.
  • tc-netem — эмуляция сетевой задержки.
