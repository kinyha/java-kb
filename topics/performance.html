Load Testing

Нагрузочный тест отвечает на вопрос, сколько выдержит сервис и что с ним будет за пределом. Главное — модель нагрузки. В закрытой модели фиксированное число пользователей ждёт ответа перед следующим запросом, и когда сервис тормозит, нагрузка сама падает. В открытой модели запросы приходят с заданной частотой, как от реальных пользователей. Закрытая модель скрывает задержки: при одной и той же паузе сервиса в 2 секунды она показала p99 41 мс, открытая — 1 925 мс. Это coordinated omission — генератор нагрузки ждёт вместе с сервисом и не отправляет запросы, которые пострадали бы. Открытая модель с растущей частотой находит колено: до 300 запросов в секунду p99 — около 30 мс, на 380 — около секунды, а за пределом ёмкости пропускная способность падает.

Тест показал p99 40 мс, а на распродаже — секунды

Перед распродажей команда прогнала нагрузочный тест: 200 виртуальных пользователей в цикле «запрос — ответ — следующий запрос», p99 — 40 мс, сервис готов. На распродаже p99 вырос до нескольких секунд, хотя запросов в секунду было примерно столько же, сколько в тесте. Тест мерил не то: когда сервис замедлялся, виртуальные пользователи тоже замедлялись и посылали меньше запросов, а реальные покупатели продолжали приходить.

Тема разбирает модели нагрузки, поиск колена и coordinated omission на настоящем генераторе k6 1.3 в Docker. Цель — Service.java: 8 рабочих потоков по 20 мс на запрос, теоретически около 400 запросов в секунду, на деле около 355. Запросом /stall демо имитирует паузу сборки мусора: все обработчики стоят 2 секунды. Перегрузка подробно — в Overload, метрики — в Metrics, оценка мощности — в Back-of-the-envelope.

Открытая модель: найти колено

// Открытая модель: запросы приходят с заданной частотой независимо от ответов.
export const options = {
  scenarios: { open: { executor: 'constant-arrival-rate', rate: __ENV.RATE, timeUnit: '1s',
    duration: '20s', preAllocatedVUs: 200, maxVUs: 2000 } },
};
export default function () { http.get('http://target:8601/pay'); }
== open model: arrival rate vs latency (capacity ~400 req/s)
   rate 200/s ->    200 req/s   p50     24 ms   p99     35 ms   dropped 0
   rate 300/s ->    300 req/s   p50     23 ms   p99     31 ms   dropped 0
   rate 380/s ->    355 req/s   p50    636 ms   p99    984 ms   dropped 154
   rate 420/s ->    350 req/s   p50   1206 ms   p99   2289 ms   dropped 588
   rate 500/s ->    187 req/s   p50   2175 ms   p99   4110 ms   dropped 1368

Рост частоты шагами даёт кривую «частота → задержка», и важна не точка, где сервис падает, а колено — где задержка начинает расти быстрее нагрузки. Рабочую мощность берут ниже колена с запасом: здесь не 355, а около 300 запросов в секунду на экземпляр, — по ней считают число экземпляров для пика. dropped — запросы, которые k6 не смог отправить вовремя: у него закончились виртуальные пользователи, занятые ожиданием ответов. Это тоже сигнал перегрузки.

Падение пропускной способности за пределом ёмкости объясняет Overload: очередь растёт, тысячи открытых соединений требуют ресурсов, и часть работы тратится впустую. Здесь к этому добавляется честная оговорка: генератор и сервис работали на одной машине и конкурировали за процессор, поэтому точки за коленом показывают характер, а не точные числа. Для настоящих тестов генератор запускают на отдельных машинах и проверяют, что сам он не упирается в CPU или сеть.

Coordinated omission: закрытая модель не видит паузу

// Закрытая модель: N виртуальных пользователей, каждый шлёт следующий запрос после ответа.
export const options = { scenarios: { closed: { executor: 'constant-vus', vus: __ENV.VUS, duration: '20s' } } };
== a 2 s stall at second 10: closed model (10 users) vs open model (200 req/s)
   closed, 10 VUs   ->    211 req/s   p50     24 ms   p99     41 ms   dropped 0
   open, 200 req/s  ->    195 req/s   p50     24 ms   p99   1925 ms   dropped 103

Генератор закрытой модели «координируется» с сервисом: когда тот тормозит, генератор тоже замедляется и пропускает именно те измерения, которые были бы плохими. Отсюда название — coordinated omission (термин Гила Тене). Те же 2 секунды паузы у реального сервиса задели бы всех, кто пришёл в это время, и именно это видит открытая модель. Закрытая модель уместна для систем, где число клиентов действительно ограничено — пул воркеров, пакетная обработка, — но не для пользовательского трафика. В JMeter и Gatling та же разница: thread groups и constantUsersPerSec, а wrk2 и HdrHistogram корректируют пропущенные измерения.

Профили нагрузки и поиск узкого места

ПрофильВопросКак
НагрузочныйВыдерживает ли ожидаемый пик?Частота пика на 20–60 минут
СтупенчатыйГде колено?Частота растёт ступенями до деградации
СтрессКак ломается и как восстанавливается?Выше ёмкости, затем снижение
ВсплескПереживает ли резкий скачок?Мгновенно ×5, автоскейлинг, очереди
Длительный (soak)Есть ли утечки и деградация со временем?Обычная нагрузка на часы

Тест имеет смысл только с наблюдением за сервисом: во время прогона смотрят насыщение ресурсов — загрузку CPU, очереди пулов потоков и соединений, паузы GC, ожидание блокировок в базе. Узкое место — первый ресурс, который заполнился; здесь это пул из 8 потоков, и добавление потоков сдвинуло бы колено, пока не упрёмся в следующее — базу или сеть. Для Java полезны профилировщики под нагрузкой — async-profiler, JFR: они показывают, где тратится время, а не только что его не хватает, как в Diagnostics.

Условия теста должны быть похожи на продакшен: прогретая JVM (первые минуты — интерпретатор и JIT, результаты выбрасывают), реалистичные данные и их объём в базе, смесь запросов как в логах доступа, те же лимиты контейнера. Тест на пустой базе с одним эндпоинтом измеряет что-то, но не сервис.

Если 200 виртуальных пользователей получили p99 40 мс, сервис выдержит такую же нагрузку от реальных пользователей.

Виртуальные пользователи закрытой модели замедляются вместе с сервисом и не отправляют запросы, которые пострадали бы. В демо пауза в 2 секунды в закрытой модели дала p99 41 мс, в открытой — 1 925 мс. Пользовательский трафик моделируют частотой прихода запросов.

  • Открытая модель — частота прихода запросов; закрытая — фиксированное число клиентов, ждущих ответа.
  • Колено между 300 и 380 запросами в секунду: p99 с 31 мс до 984 мс; рабочая мощность — ниже колена с запасом.
  • За пределом ёмкости пропускная способность падает: 187 вместо 355 в секунду при 500 входящих.
  • Coordinated omission: пауза 2 с — p99 41 мс в закрытой модели и 1 925 мс в открытой.
  • Тест — с наблюдением за насыщением, прогретой JVM, реалистичными данными и генератором на отдельной машине.

На собеседовании

Чем открытая модель нагрузки отличается от закрытой?

В закрытой модели фиксированное число пользователей шлёт следующий запрос после ответа: если сервис тормозит, нагрузка падает. В открытой запросы приходят с заданной частотой независимо от ответов, как от реальных пользователей, и очередь при перегрузке растёт. Для пользовательского трафика нужна открытая модель, иначе тест занижает задержки.

  • Coordinated omission: в демо p99 41 мс против 1 925 мс при одной паузе.
  • k6 constant-arrival-rate, Gatling constantUsersPerSec, wrk2.

Как провести нагрузочный тест и найти узкое место?

Определить цель (пик запросов, SLO по задержке), смесь запросов и данные. Поднимать частоту ступенями в открытой модели и смотреть на задержку, ошибки и насыщение ресурсов. Колено — где задержка растёт быстрее нагрузки; узкое место — ресурс, который заполнился первым: пул потоков, соединения с базой, CPU, GC. Исправить и повторить.

  • Генератор на отдельных машинах, проверка, что он не упёрся сам.
  • Прогрев JVM, реалистичный объём данных, лимиты контейнера как в продакшене.
  • Профилировщик под нагрузкой — async-profiler, JFR.
Что не так с этим тестом? 
export const options = { vus: 50, duration: '2m' };
export default function () {
  http.get('https://staging/api/payments/1');      // один и тот же платёж
  sleep(1);
}
// вывод: сервис держит 50 запросов в секунду с p99 80 мс — запаса хватит

Закрытая модель: при замедлении сервиса нагрузка сама падает, и p99 занижен. Один и тот же платёж — всё в кеше, база не нагружена. Две минуты без прогрева — результат смешан с работой интерпретатора. «Держит 50» не измерено: 50 пользователей с паузой в секунду дают не больше 50 запросов в секунду, предел не искали. Нужно: открытая модель со ступенями частоты, разные данные, прогрев, наблюдение за ресурсами.

Как по результатам теста определить, сколько нужно экземпляров?

Найти рабочую частоту на экземпляр ниже колена с запасом, при которой выполняется SLO по задержке, — здесь около 300 запросов в секунду при колене около 355. Число экземпляров — пиковая нагрузка, делённая на эту частоту, плюс запас на отказ экземпляра или зоны и на рост.

  • Масштабирование нелинейно: общие ресурсы (база, кеш) могут стать узким местом раньше.
  • Проверять горизонтальное масштабирование тестом на нескольких экземплярах.
  • k6: Open and closed models, constant-arrival-rate.
  • Gil Tene, «How NOT to Measure Latency» — coordinated omission.
  • Brendan Gregg, «Systems Performance» — USE и поиск узкого места.
  • wrk2 — генератор с постоянной частотой.
