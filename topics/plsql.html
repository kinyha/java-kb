Stored Procedures

Хранимые функции и процедуры выполняют логику внутри базы: PL/pgSQL в PostgreSQL, PL/SQL в Oracle. Их главный выигрыш — меньше кругов по сети: несколько запросов с проверками становятся одним вызовом, а данные не уходят в приложение. Функция возвращает значение и вызывается в SELECT; процедура вызывается CALL и может сама коммитить. Триггеры выполняются на каждое изменение строки и подходят для аудита и инвариантов, но делают запись дороже и скрывают логику. Курсор читает большой результат порциями. Цена логики в базе — тестирование, версионирование, отладка и масштабирование, поэтому в неё выносят то, что действительно связано с данными.

Банк держит логику в PL/SQL, а новый сервис на Java читает миллион строк и падает по памяти

В банковских системах до сих пор много логики живёт в базе: расчёт процентов, проводки, проверки лимитов в PL/SQL-пакетах. Новый Java-сервис должен вызывать эти процедуры, обрабатывать их ошибки и не ломать их инварианты. А его ночная выгрузка читает миллион операций одним запросом и падает с OutOfMemoryError, хотя обрабатывает строки по одной.

Тема разбирает хранимые функции, процедуры, триггеры и курсоры на примере PL/pgSQL и то, когда логика должна жить в базе. Блокировки и порядок захвата — в Locks, круги по сети и N+1 — в Slow Queries, JDBC — в JDBC & Connection Pools. Демо PlpgsqlDemo.java работает с PostgreSQL 17 в Docker.

Функция выполняет несколько шагов за один вызов

create function transfer(p_from int, p_to int, p_amount bigint) returns bigint
language plpgsql as $$
declare v_balance bigint;
begin
    -- Блокируем счета в порядке id, чтобы встречные переводы не попали в deadlock.
    perform 1 from account where id in (p_from, p_to) order by id for update;
    select balance into v_balance from account where id = p_from;
    if v_balance < p_amount then
        raise exception 'insufficient funds on account %', p_from using errcode = 'P0901';
    end if;
    update account set balance = balance - p_amount where id = p_from;
    update account set balance = balance + p_amount where id = p_to;
    return v_balance - p_amount;
end $$;
== 2000 transfers: from the app (3 statements + commit) 1048 ms, one function call + commit 556 ms
== transfer over balance -> SQLState P0901: ERROR: insufficient funds on account 1

Перевод из приложения — три запроса и коммит, четыре круга по сети на перевод. Через функцию — один вызов и коммит: вдвое быстрее даже на локальной машине, а в реальной сети разница больше. Пока транзакция ждёт следующего запроса приложения, она держит блокировки строк; в функции весь путь от блокировки до изменения проходит без пауз, и блокировки держатся меньше. Ошибка из функции приходит в Java как SQLException с заданным SQLSTATE P0901, по которому приложение отличает «недостаточно средств» от прочих ошибок.

Функция выполняется в транзакции вызывающего: raise exception откатывает всё, что она сделала. Блок BEGIN ... EXCEPTION внутри PL/pgSQL перехватывает ошибку, но создаёт подтранзакцию, и в цикле по тысячам строк это заметно дорого. У функции важна категория изменчивости: IMMUTABLE и STABLE позволяют планировщику вычислять её реже и использовать в индексах по выражению, а неверно объявленная IMMUTABLE функция, читающая таблицы, даёт неверные результаты.

Процедура может коммитить сама, функция — нет

create procedure archive_old_payments() language plpgsql as $$
declare v_rows int;
begin
    loop
        delete from payment where id in (select id from payment where created_at < now() - interval '3 years' limit 10000);
        get diagnostics v_rows = row_count;
        exit when v_rows = 0;
        commit;                       -- пачками, без одной огромной транзакции
    end loop;
end $$;
call archive_old_payments();

С PostgreSQL 11 есть процедуры: они вызываются CALL, не возвращают значение в запрос и могут выполнять COMMIT и ROLLBACK внутри. Это нужно для длинной фоновой работы пачками: каждая пачка коммитится отдельно, блокировки и горизонт VACUUM не держатся часами, как разобрано в MVCC. Функция всегда выполняется внутри транзакции вызывающего и коммитить не может. В Oracle процедуры и функции объединяют в пакеты PL/SQL с общим состоянием сессии; в PostgreSQL пакетов нет, их заменяют схемы.

Триггер выполняется на каждую строку: удобно для аудита, дорого для массовых изменений

create function audit_balance() returns trigger language plpgsql as $$
begin
    if new.balance <> old.balance then
        insert into account_audit(account_id, old_balance, new_balance) values (old.id, old.balance, new.balance);
    end if;
    return new;
end $$;
create trigger account_audit_trg after update on account for each row execute function audit_balance();
== update 1000 accounts: without trigger 2.2 ms, with row trigger 3.2 ms, audit rows 1000

Триггер аудита записал строку истории на каждое изменение баланса — независимо от того, какой сервис или скрипт изменил счёт. Это его сила: инвариант или аудит, который нельзя обойти. Цена — каждый UPDATE теперь две записи, и массовое обновление тысячи счетов стало в полтора раза дольше; на миллионах строк с несколькими триггерами разница кратная. Вторая цена — скрытность: разработчик смотрит в код сервиса и не видит, что изменение счёта пишет ещё в две таблицы и проверяет лимиты.

Триггеры уместны для аудита, поддержания денормализованных счётчиков и инвариантов, которые нельзя выразить ограничением. Бизнес-процессы — отправка писем, вызовы других сервисов — в триггерах не делают: они выполняются внутри транзакции, и откат её не отменит отправленное. Для событий наружу есть outbox, как в Transactional Outbox, и запись в таблицу outbox из триггера — один из рабочих способов его наполнять.

Курсор читает большой результат порциями, а не целиком в память

c.setAutoCommit(false);          // курсор драйвер открывает только в транзакции
var st = c.createStatement();
st.setFetchSize(1000);           // 0 — по умолчанию: весь результат в память
var rs = st.executeQuery("select g, md5(g::text) from generate_series(1, 1000000) g");
== read 1M rows, fetchSize    0: first row after  624 ms, heap growth at first row ~138 MB, rows 1000000
== read 1M rows, fetchSize 1000: first row after   24 ms, heap growth at first row ~0 MB, rows 1000000

По умолчанию драйвер PostgreSQL читает весь результат в память, прежде чем отдать первую строку: 138 МБ кучи и 624 мс до первой строки на миллионе строк. На десятках миллионов это OutOfMemoryError из истории выше. С setFetchSize(1000) при выключенном автокоммите драйвер открывает серверный курсор и забирает строки по тысяче: первая строка через 24 мс, память почти не растёт. В JPA то же делает Stream из репозитория с подсказкой HINT_FETCH_SIZE. Внутри PL/pgSQL цикл for row in select ... сам использует курсор, а курсор, объявленный явно, можно вернуть из функции как refcursor.

Логика в хранимых процедурах всегда быстрее, поэтому её стоит переносить в базу.

Быстрее она за счёт меньшего числа кругов по сети и коротких блокировок — в демо перевод вдвое быстрее. Но база — самый дорогой и трудно масштабируемый ресурс, а логику в ней сложнее тестировать, версионировать и отлаживать. В базу выносят операции, тесно связанные с данными: атомарные переводы, массовые преобразования, аудит. Остальное остаётся в приложении.

  • Функция PL/pgSQL делает несколько шагов за один вызов: 2000 переводов за 556 мс против 1048 из приложения; ошибки — со своим SQLSTATE.
  • Процедура (CALL, PostgreSQL 11+) может коммитить пачками; функция — только в транзакции вызывающего.
  • Триггер на строку — аудит и инварианты, которые не обойти, но каждое изменение дороже и логика скрыта.
  • setFetchSize с выключенным автокоммитом читает курсором: 24 мс до первой строки вместо 624 и почти без памяти.
  • В базу выносят то, что связано с данными; остальное — в приложении.

На собеседовании

Когда логику стоит держать в хранимых процедурах?

Когда она тесно связана с данными и выигрывает от выполнения рядом с ними: атомарный перевод с проверками за один вызов вместо нескольких кругов по сети, массовые преобразования без выгрузки в приложение, аудит и инварианты, которые нельзя обойти. Минусы — сложнее тестировать, версионировать и отлаживать, а нагрузка ложится на базу, которую трудно масштабировать.

  • Изменения функций и процедур — миграции, как и схема.
  • Короткая транзакция в функции держит блокировки меньше, чем та же логика из приложения.
  • SECURITY DEFINER выполняется с правами владельца; нужен явный search_path.

Чем функция отличается от процедуры в PostgreSQL?

Функция возвращает значение, вызывается в SELECT и выполняется внутри транзакции вызывающего — коммитить не может. Процедура (с PostgreSQL 11) вызывается CALL, ничего не возвращает в запрос и может выполнять COMMIT и ROLLBACK внутри, что нужно для обработки пачками.

  • Категории IMMUTABLE, STABLE, VOLATILE влияют на оптимизацию; неверная категория даёт неверные результаты.
  • BEGIN … EXCEPTION создаёт подтранзакцию и дорог в циклах.
Что опасного в этом триггере? 
create function notify_merchant() returns trigger language plpgsql as $$
begin
    perform http_post('https://partner.example/hook', row_to_json(new)::text);   -- расширение http
    return new;
end $$;
create trigger payment_notify after insert on payment for each row execute function notify_merchant();

Сетевой вызов внутри триггера выполняется в транзакции вставки: она ждёт партнёра и держит блокировки, а медленный или недоступный партнёр замедлит или сломает вставку платежей. Если транзакция откатится, уведомление уже уйдёт. Триггер должен только записать событие в таблицу outbox, а отправку делает отдельный ретранслятор после коммита.

Как прочитать из базы миллион строк в Java, не съев всю память?

Драйвер PostgreSQL по умолчанию загружает весь результат в память. Нужно выключить автокоммит и задать setFetchSize — тогда драйвер откроет серверный курсор и будет забирать строки порциями. В демо первая строка пришла через 24 мс вместо 624, а куча почти не выросла.

  • В Spring Data — Stream с HINT_FETCH_SIZE внутри транзакции; в JdbcTemplate — setFetchSize.
  • Долгий курсор держит транзакцию и горизонт VACUUM; большие выгрузки делят на порции по keyset.
