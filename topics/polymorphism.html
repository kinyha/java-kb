Полиморфизм

Код, который знает обо всех

Платёжный сервис банка принимает оплату картой: считает комиссию, проверяет лимит, печатает строку в чеке. Потом добавили СБП, ещё через полгода — оплату из кошелька. Самый прямой способ поддержать новый вариант — ветвиться по типу:

long fee(Payment p) {
    return switch (p.type()) {
        case "CARD"   -> p.amount() * 15 / 1000;              // 1,5%
        case "SBP"    -> 0;
        case "WALLET" -> Math.min(p.amount() / 100, 5_000);   // 1%, не больше 50 ₽
        default -> throw new IllegalArgumentException("unknown type " + p.type());
    };
}

long limit(Payment p)        { /* такой же switch */ }
String receiptLine(Payment p) { /* и ещё один */ }

Пока вариантов три, это читается. С ростом начинаются проблемы:

  • Новый способ оплаты — правка в каждом таком switch. А они не только здесь: в отчётах, антифроде, возвратах.
  • Забытую ветку компилятор не заметит. Тип «QR» уйдёт в default и упадёт уже в проде.
  • Сервис платежей импортирует клиентов всех провайдеров. Обновился SDK эквайера — пересобирается и заново тестируется ядро, хотя бизнес-правила не менялись.

Корень у всех трёх проблем один: код, который принимает решение, знает про все варианты. Полиморфизм переносит это знание внутрь самих вариантов.

Общий контракт, разное поведение

Розетка одна, а приборы разные. Розетка не знает, что в неё включили, чайник или зарядку: она выдаёт ток по общему стандарту, а что с ним делать, решает прибор. Интерфейс в Java — стандарт вилки, реализация — прибор.

Контракт описывают интерфейсом, а каждый вариант реализует его по-своему:

interface PaymentMethod {
    long fee(long amount);                 // комиссия в копейках
    long limit();                          // лимит одного платежа
}

class Card implements PaymentMethod {
    public long fee(long amount) { return amount * 15 / 1000; }   // 1,5%
    public long limit() { return 10_000_000; }                    // 100 000 ₽
}

class Sbp implements PaymentMethod {
    public long fee(long amount) { return 0; }
    public long limit() { return 100_000_000; }                   // 1 000 000 ₽
}

long total(PaymentMethod m, long amount) {   // не знает ни про Card, ни про Sbp
    if (amount > m.limit()) throw new IllegalStateException("limit exceeded");
    return amount + m.fee(amount);
}

System.out.println(total(new Card(), 10_000));
System.out.println(total(new Sbp(), 10_000));
10150
10000

Метод total написан один раз и работает с любым способом оплаты, в том числе с тем, которого ещё нет. Это и есть полиморфизм: один и тот же вызов m.fee(amount) выполняет разный код в зависимости от того, какой объект лежит в m.

Новый способ оплаты теперь — новый класс, а существующий код не меняется. Забыть метод тоже не получится: класс, который реализует интерфейс не полностью, не скомпилируется. Это принцип открытости-закрытости из SOLID: код открыт для расширения и закрыт для изменения.

Три вида полиморфизма

Строго говоря, этим словом называют три механизма. Всё, что выше, — первый, и на собесе почти всегда спрашивают про него.

ВидКак в JavaКогда выбирается код
Подтиповinterface, extends, переопределениеВо время выполнения, по классу объекта
Ad-hocПерегрузка: print(int), print(String)При компиляции, по типам аргументов
ПараметрическийGenerics: List<T>При компиляции, один код для всех T

Как JVM выбирает метод

Вызов m.fee(amount) проходит два решения, и принимают их в разное время разные участники.

  1. Компилятор смотрит на объявленный тип переменной m — PaymentMethod. Проверяет, что там есть метод fee(long), и записывает в байткод его сигнатуру.
  2. JVM при выполнении смотрит на объект, который реально лежит в m, берёт его класс и ищет реализацию этой сигнатуры в нём, поднимаясь по иерархии вверх.

Из этого правила следуют ответы почти на все задачи «что выведет». Тип переменной решает, какие методы можно вызвать и с какой сигнатурой. Класс объекта решает, чья реализация выполнится. Проверь на примере, где работают оба решения:

class Printer {
    void print(Object o) { System.out.println("Printer.Object"); }
    void print(String s) { System.out.println("Printer.String"); }
}
class LoudPrinter extends Printer {
    @Override void print(Object o) { System.out.println("Loud.Object"); }
}

Printer p = new LoudPrinter();
Object text = "hi";
p.print(text);
p.print("hi");
Loud.Object
Printer.String

В первом вызове компилятор по типу Object выбрал print(Object), а JVM нашла его версию в LoudPrinter. Во втором компилятор выбрал print(String). LoudPrinter его не переопределяет, поэтому выполняется версия Printer.

Выбор по классу объекта касается только методов экземпляра, которые можно переопределить. Остальное компилятор фиксирует по типам, известным при компиляции:

Он определяет, какие методы можно вызвать и какую сигнатуру выберет компилятор. Выполнится реализация из класса объекта. Приведение (Printer) p тоже меняет только тип ссылки, но не объект.

Под капотом: vtable, itable и JIT

У каждого класса HotSpot хранит таблицу виртуальных методов, vtable. Унаследованный метод лежит в той же ячейке, что у родителя, а переопределение подменяет адрес в ней. Поэтому invokevirtual — это чтение класса из заголовка объекта и переход по известному индексу. У интерфейсных методов индекс в разных классах разный, и invokeinterface ищет по отдельной таблице, itable, — чуть дороже.

На практике обе таблицы почти всегда обходит JIT. Он профилирует, какие классы приходят в точку вызова. Если один-два, вставляет проверку класса и тело метода прямо в место вызова. Если позже придёт новый класс, проверка не пройдёт, код откатится в интерпретатор (деоптимизация) и перекомпилируется с новым профилем. Дорогим вызов остаётся только там, где встречается много классов без явного лидера, — megamorphic call site.

Главное: зависимость можно развернуть

Самое ценное в полиморфизме видно не внутри одного метода, а в устройстве всего приложения. Смотри не на то, кто кого вызывает, а на то, кто кого импортирует.

Без интерфейса вызов и зависимость идут в одну сторону. PaymentService вызывает CardGatewayClient и поэтому импортирует его. Бизнес-правила зависят от HTTP-клиента эквайера, его DTO и версии SDK.

С интерфейсом вызов идёт так же — из сервиса в шлюз. А зависимость в исходниках разворачивается: интерфейс PaymentMethod лежит рядом с бизнес-логикой, а класс CardGateway в модуле интеграций импортирует его и реализует. Ядро не знает, что шлюз вообще существует.

Что это даёт на практике:

  • Ядро собирается и тестируется без инфраструктуры: в тесте вместо шлюза — фейковая реализация на три строки.
  • Провайдера меняют, не трогая бизнес-правила: пишут новый класс в модуле интеграций.
  • Границу закрепляет сборка. Модуль core в Maven или Gradle не зависит от integrations, и случайный импорт шлюза в бизнес-логику просто не скомпилируется.
bank.payments.core           PaymentService, PaymentMethod   ← ничего не знает об интеграциях
bank.payments.integrations   CardGateway implements PaymentMethod

Это принцип инверсии зависимостей (DIP) из SOLID, и работает он только благодаря полиморфизму. Spring здесь — механизм сборки: при старте он находит реализации интерфейса и подставляет их туда, где их ждут.

История: полиморфизм до ООП

Идея старше Java. В UNIX каждый драйвер устройства ввода-вывода обязан предоставить одинаковый набор функций: open, close, read, write, seek. Структура файла в C хранит указатели на функции своего драйвера, а getchar просто вызывает функцию read того файла, что стоит за стандартным вводом. Поэтому программа, которая копирует ввод в вывод, работает с клавиатурой, файлом и сетью, и её не нужно переписывать под новое устройство.

Цена — дисциплина. Таблицы указателей собирали руками, и нарушенное соглашение всплывало только во время выполнения. ООП-языки сделали то же самое безопасным: таблицу методов строит компилятор, а класс, который не реализовал метод, не соберётся. Роберт Мартин в «Чистой архитектуре» (глава 5) считает именно это главным вкладом ООП: полный контроль над направлением зависимостей в исходниках.

Когда полиморфизм не спасает

Реализация нарушает контракт

Подстановка работает, только если каждая реализация ведёт себя так, как обещает интерфейс. Иначе вызывающий код снова начинает проверять тип.

class DepositAccount implements Account {   // вклад: снимать нельзя
    public void withdraw(long amount) {
        throw new UnsupportedOperationException("deposit");
    }
}

Код, написанный для Account, теперь падает на вкладах, и в нём появляется if (acc instanceof DepositAccount). Это нарушение принципа подстановки Лисков (LSP). Лечится моделью, а не проверками: если снимать можно не со всех счетов, withdraw не должен входить в общий контракт. Его выносят в отдельный интерфейс, например WithdrawableAccount.

Цепочка instanceof вместо метода

if (p instanceof Card) … else if (p instanceof Sbp) … возвращает проблему из первого шага: новый тип молча проскочит мимо всех веток. Если ветки выбирают поведение, это поведение должно быть методом типа.

Набор типов закрыт, а операций много

Бывает обратная ситуация. Типы известны заранее и описывают данные: события, команды, ответы API. А операций над ними много, и живут они в разных модулях: сериализация, валидация, отчёты. Добавлять метод во все классы ради каждой операции неудобно. В Java 21 для этого есть sealed-иерархия и switch по типу:

sealed interface Payment permits CardPayment, SbpPayment {}
record CardPayment(long amount, String pan) implements Payment {}
record SbpPayment(long amount, String phone) implements Payment {}

static long fee(Payment p) {
    return switch (p) {                 // без default: компилятор проверит полноту
        case CardPayment c -> c.amount() * 15 / 1000;
        case SbpPayment s -> 0;
    };
}

Добавишь WalletPayment в permits — этот switch перестанет компилироваться с ошибкой the switch expression does not cover all possible input values, пока не допишешь ветку. От switch из первого шага он отличается именно этим: компилятор знает все варианты.

Интерфейс и реализацииsealed и switch
Добавить типНовый класс, старый код не трогаешьПравка каждого switch, компилятор покажет где
Добавить операциюМетод в каждом классеНовый switch в одном месте
Подходит дляПоведения, интеграций, плагиновДанных: событий, команд, ответов

Этот компромисс называют expression problem. Выбирай по тому, что будет меняться чаще: набор типов или набор операций.

Интерфейс ради интерфейса

Интерфейс с единственной реализацией внутри одного модуля — лишний файл и лишний переход при чтении кода. Spring проксирует и классы, Mockito мокает класс. Интерфейс нужен, когда вариантов больше одного или когда он разворачивает зависимость между модулями, как в прошлом шаге.

  • Полиморфизм — один вызов выполняет разный код в зависимости от объекта.
  • Компилятор выбирает сигнатуру по типу ссылки, JVM — реализацию по классу объекта. Перегрузка, поля, static и private выбираются при компиляции.
  • Главная польза — управление зависимостями: ядро объявляет интерфейс, детали его реализуют.
  • Реализации обязаны выполнять контракт, иначе в код возвращаются проверки типов.
  • Закрытый набор типов, над которым много операций, — повод для sealed и switch.

На собеседовании

Что такое полиморфизм?

Полиморфизм — это когда один и тот же вызов выполняет разный код в зависимости от объекта. В Java это прежде всего полиморфизм подтипов: я работаю через интерфейс или базовый класс, а какая реализация выполнится, JVM решает во время выполнения по классу объекта. Это позднее связывание. Сигнатуру метода при этом выбирает компилятор по типу ссылки.

Практический смысл — вызывающему коду не нужно знать о вариантах. Например, расчёт платежа работает через интерфейс PaymentMethod, и новый способ оплаты — это новый класс, а не правка всех switch по типу. А на уровне архитектуры полиморфизм позволяет развернуть зависимость: бизнес-логика объявляет интерфейс, интеграции его реализуют, и ядро не зависит от инфраструктуры.

  • Кроме полиморфизма подтипов есть ad-hoc (перегрузка) и параметрический (generics), но оба выбираются при компиляции.
  • Если набор типов закрыт, а операций много, вместо полиморфизма беру sealed-иерархию и switch по типу: компилятор проверяет полноту. Это другая сторона expression problem.
  • Полиморфизм работает, пока реализации выполняют контракт. Реализация, которая бросает UnsupportedOperationException, нарушает LSP и возвращает в код проверки типов.
  • По скорости: JIT инлайнит вызов, если в точку вызова приходят один-два класса. Дорого только в megamorphic-точках горячего кода.
Что выведет этот код? 
class A {
    String who() { return "A"; }
    String hello() { return "hello from " + who(); }
}
class B extends A {
    String who() { return "B"; }
}

A a = new B();
System.out.println(a.hello());
System.out.println(((A) a).who());
hello from B
B

hello объявлен в A, но who() внутри него — это this.who(), а this указывает на объект B. Приведение к A меняет только тип ссылки, класс объекта остаётся B.

Что такое раннее и позднее связывание?

Раннее связывание — метод известен уже при компиляции: static- и private-методы, конструкторы, вызовы через super. Позднее — реализация выбирается во время выполнения по классу объекта: так вызываются все остальные методы экземпляра. final-метод формально вызывается как виртуальный, но переопределить его нельзя, поэтому результат тот же, что при раннем связывании.

Приведи пример полиморфизма из своего проекта.

Хороший ответ строится так: задача, как выглядел бы код без полиморфизма, что сделал, что это дало. Например: «Уведомления уходили по email и SMS, потом добавили push. Сделали интерфейс NotificationSender с реализацией на канал, Spring собирает их в Map по имени канала. Новый канал — новый класс, сервис уведомлений не меняли, а в тестах подменяли отправку фейком». Подойдут расчёт комиссий, обработчики событий по типу, адаптеры внешних систем.

Чем перегрузка отличается от переопределения?

Перегрузка — несколько методов с одним именем и разными параметрами. Какой вызвать, решает компилятор по объявленным типам аргументов. Переопределение — подкласс заменяет реализацию метода с той же сигнатурой, и выбирает её JVM во время выполнения по классу объекта.

У переопределения есть правила: та же сигнатура, тип возврата тот же или подтип, доступ не уже, checked-исключения не шире. static-, private- и final-методы не переопределяются. На каждое переопределение ставлю @Override: иначе опечатка вроде equals(Money) вместо equals(Object) тихо превращает его в перегрузку.

  • Перегрузка ищется в три фазы: без упаковки и varargs, потом с упаковкой, потом с varargs. Поэтому f(1) при f(long) и f(Integer) уйдёт в long, а list.remove(1) на List<Integer> удалит элемент по индексу.
  • С лямбдами перегрузка коварна: executor.submit(() -> work()) выбирает между Runnable и Callable по тому, возвращает ли work значение. Поменял void на int — вызывается другой метод.
  • Ковариантный возврат и generics компилятор поддерживает bridge-методами: синтетический метод со старой сигнатурой вызывает новый. Их видно в javap и в stack trace.
Что выведет этот код? 
static void f(long x)     { System.out.println("long"); }
static void f(Integer x)  { System.out.println("Integer"); }
static void f(Object x)   { System.out.println("Object"); }
static void f(int... x)   { System.out.println("varargs"); }

f(1);
f(Integer.valueOf(1));
Object o = 1;
f(o);
long
Integer
Object

Расширение int до long возможно в первой фазе поиска, а упаковка в Integer — только во второй, поэтому выигрывает long. Второй вызов — точное совпадение. В третьем тип переменной Object, и реальный Integer внутри ни на что не влияет.

Что останется в списке? 
List<Integer> ids = new ArrayList<>(List.of(10, 20, 1));
ids.remove(1);
System.out.println(ids);
ids.remove(Integer.valueOf(1));
System.out.println(ids);
[10, 1]
[10]

remove(1) — это remove(int index): он подходит без упаковки и выигрывает у remove(Object). Удалился элемент с индексом 1, то есть 20. Чтобы удалить значение, нужен объект.

Почему переопределяющий метод не может сузить доступ или бросить более широкое исключение?

Код, который держит ссылку на родителя, рассчитывает на его контракт: метод доступен и бросает только объявленные checked-исключения. Если бы подкласс сузил доступ или добавил исключение, этот код ломался бы при подстановке подкласса, хотя компилятор его пропустил. Подтип может обещать больше, но не меньше — это LSP на уровне языка.

Можно ли перегрузить метод только по типу возврата?

Нет. По вызову f() компилятор не поймёт, какой из методов нужен, поэтому второй такой метод — ошибка «method f() is already defined». При этом в байткоде тип возврата входит в дескриптор метода, и такие пары там встречаются: это bridge-методы, которые генерирует сам компилятор.

Что в Java не полиморфно?

Полиморфны только методы экземпляра, которые можно переопределить. Поля, static- и private-методы выбираются при компиляции по типу ссылки. Поле с тем же именем в подклассе не переопределяет, а скрывает родительское: в объекте лежат оба.

Отдельная ловушка — вызов переопределяемого метода из конструктора. Выполнится версия подкласса, но его поля ещё не инициализированы: там null и 0. Поэтому в конструкторе вызываю только private- и final-методы.

  • Прокси Spring на CGLIB — подкласс бина. Он не может переопределить private- и final-методы, поэтому @Transactional на них не работает, и ошибки нет. final-метод вообще выполнится на самом прокси, у которого пустые поля, и внедрённый репозиторий окажется null.
  • Вызов через this внутри бина идёт мимо прокси, поэтому @Transactional на методе, вызванном из соседнего метода того же класса, не сработает.
  • Ленивые прокси Hibernate — тоже подклассы. Поэтому сущности не делают final, а в Kotlin, где всё final по умолчанию, подключают плагины all-open и no-arg.
Что выведет этот код? 
class A {
    int x = 10;
    A() { print(); }
    void print() { System.out.println("A " + x); }
}
class B extends A {
    int x = 20;
    B() { print(); }
    @Override void print() { System.out.println("B " + x); }
}

A a = new B();
System.out.println(a.x);
B 0
B 20
10

Конструктор A вызывает print(), и выполняется версия B, но поле B.x ещё не инициализировано — 0. Инициализаторы полей B выполняются после super(), в начале конструктора B, поэтому второй вызов печатает 20. a.x — поле, выбранное по типу ссылки A, в нём 10.

Почему @Transactional не срабатывает при вызове из того же класса и что с этим делать?

Транзакцию открывает прокси, а вызов this.method() идёт в сам объект, минуя прокси. Лучший выход — вынести метод в отдельный бин, тогда вызов естественно пойдёт через прокси. Другие варианты: TransactionTemplate для транзакции прямо в коде или внедрение бина в самого себя через @Lazy. Последнее работает, но маскирует проблему дизайна.

Что не так с этим базовым классом? 
public abstract class BaseHandler {
    protected final String name;

    protected BaseHandler() {
        this.name = handlerName();
        Registry.register(this);          // публикуем себя
    }
    protected abstract String handlerName();
}

public class PaymentHandler extends BaseHandler {
    private final String prefix;

    public PaymentHandler(String prefix) {
        this.prefix = prefix;
    }
    @Override
    protected String handlerName() { return prefix + "-payment"; }
}
  • handlerName() вызывается из конструктора BaseHandler, когда prefix ещё null. Имя станет "null-payment", и никакой ошибки не будет.
  • this уходит в Registry до конца конструирования. Другой поток может взять из реестра недостроенный объект.
  • Исправление: передать имя в конструктор базового класса — super(prefix + "-payment"), а регистрировать объект снаружи после создания: в фабрике или в @PostConstruct.

Как полиморфизм связан с инверсией зависимостей?

Обычно зависимость в коде идёт туда же, куда вызов: сервис вызывает клиент банка и потому его импортирует. Полиморфизм позволяет это развернуть. Интерфейс объявляется рядом с бизнес-логикой, а реализация в модуле интеграций импортирует его. Вызов по-прежнему идёт из сервиса в клиент, а зависимость в исходниках — в обратную сторону.

В результате ядро не знает про HTTP, SDK и базу. Его можно тестировать с фейковыми реализациями, а провайдера менять, не трогая бизнес-правила. Spring при старте находит реализации и внедряет их.

  • Границу закрепляю сборкой: модуль core не зависит от integrations, и неправильный импорт не компилируется. Внутри одного модуля — тестами ArchUnit.
  • Это же лежит в основе гексагональной архитектуры: порт — интерфейс, который объявляет ядро, адаптер — его реализация снаружи.
  • Интерфейс принадлежит тому, кто его использует, а не тому, кто реализует. Если интерфейс лежит в модуле интеграций рядом с реализацией, зависимость не развёрнута.
Зачем интерфейс, если реализация одна?

Если он разворачивает зависимость между модулями — например, ядро и интеграция с банком, — он нужен даже с одной реализацией: без него ядро будет импортировать клиент банка. Если и интерфейс, и реализация живут в одном модуле и других реализаций не предвидится, интерфейс обычно лишний: Spring проксирует классы, Mockito мокает класс.

Что не так с зависимостями в этом сервисе? 
package bank.payments.core;

import org.springframework.web.client.RestClient;
import bank.payments.integrations.acquirer.AcquirerPaymentRequest;

@Service
public class PaymentService {
    private final RestClient acquirer;

    public PaymentService(RestClient acquirer) { this.acquirer = acquirer; }

    public PaymentResult pay(Payment payment) {
        checkLimits(payment);
        var request = new AcquirerPaymentRequest(payment.pan(), payment.amount());
        return acquirer.post().uri("/payments").body(request)
                .retrieve().body(PaymentResult.class);
    }
}
  • Бизнес-логика из core импортирует HTTP-клиент и DTO эквайера из integrations: зависимость идёт от ядра к деталям.
  • Проверить checkLimits и сценарий оплаты в тесте без HTTP нельзя, а смена эквайера или его API — правка ядра.
  • Исправление: интерфейс PaymentGateway в core с методом pay(Payment), класс AcquirerGateway в integrations реализует его и сам строит запрос. PaymentService получает PaymentGateway в конструкторе.
