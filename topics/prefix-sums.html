Prefix Sums

Сумму участка журнала можно получить из двух накопленных сумм: до его правой границы и до левой. Общий кусок в начале отменится. Если нужный участок ещё неизвестен, то же равенство подсказывает, какую прошлую сумму искать. Для числа участков сохраняют частоты, для максимальной длины — самые ранние границы. Отрицательные платежи не мешают этому равенству: важны порядок границ и точность арифметики.

Две накопленные суммы заменяют повторное сложение отрезка

Сверка хранит журнал платежей и возвратов в копейках: [10, −4, 7, 0, −3, 5]. Оператор запрашивает итоги разных участков, соседние запросы перекрываются. Обычный цикл снова читает те же операции. Для q запросов по массиву из n элементов худшее время O(nq); чтобы ускорить запросы, нужно сохранить уже выполненную работу.

Пусть P[i] содержит сумму первых i элементов. Тогда P[0] = 0, а P[i + 1] = P[i] + a[i]. В массиве из n элементов есть n + 1 границ, поэтому префиксный массив на одну ячейку длиннее. Последний P[n] хранит сумму всего журнала.

Итог участка [left, right) равен P[right] − P[left]. Оба префикса включают первые left элементов, и при вычитании они отменяются. Остаются элементы с индексами left..right − 1. Длина участка right − left, правый элемент уже не входит. Для диапазона с включённым последним индексом R формула будет P[R + 1] − P[left].

Фрагменты RangeDemo.java; полный файл запускается командой java RangeDemo.java на JDK 21. Здесь и далее входы не null, сумма выражена целым числом копеек:

record Result(long sum, int reads) {}

static Result direct(int[] values, int left, int right) {
    long sum = 0;
    for (int i = left; i < right; i++) sum += values[i];
    return new Result(sum, right - left);
}

static long[] prefix(int[] values) {
    long[] p = new long[values.length + 1]; // P[0] — сумма пустого начала.
    for (int i = 0; i < values.length; i++) p[i + 1] = p[i] + values[i];
    return p; // P[i] — сумма ровно i первых элементов.
}

static long range(long[] p, int left, int right) {
    if (left < 0 || left > right || right >= p.length) throw new IllegalArgumentException("invalid range");
    return p[right] - p[left]; // Общие первые left элементов отменяются.
}

System.out.println("== sums on boundaries ==");
int[] payments = {10, -4, 7, 0, -3, 5};
long[] p = prefix(payments);
System.out.println("prefix=" + Arrays.toString(p));
int reads = 0;
int[][] queries = {{1, 5}, {2, 6}, {0, 6}, {3, 3}, {4, 5}};
for (int[] q : queries) {
    Result slow = direct(payments, q[0], q[1]);
    long fast = range(p, q[0], q[1]);
    if (slow.sum() != fast) throw new AssertionError("range mismatch");
    reads += slow.reads();
    System.out.println("[" + q[0] + ", " + q[1] + ") direct=" + slow.sum() + " prefix=" + fast);
}
System.out.println("direct reads=" + reads + "; build reads=" + payments.length + "; prefix reads=" + queries.length * 2);

На небольшом наборе обычный цикл прочитал 15 элементов; построение префиксов прочитало 6, затем запросы прочитали 10 ячеек P. На таком размере выигрыш ещё не виден — предобработка тоже стоит работы. Главное, что каждый следующий запрос теперь использует ровно два префикса независимо от длины участка. Общая стоимость O(n + q), память O(n) без учёта ответов.

Участок [3, 3) пустой: P[3] − P[3] = 0. Участок [1, 5) тоже дал 0, но содержит четыре операции, которые взаимно компенсировались. Для отрицательных значений формула не меняется: ей нужна возможность отменить общий префикс, а не возрастающий порядок сумм.

P[i] — сумма до элемента i включительно, а запрос [left, right) считается P[right] − P[left].

Это смешение двух соглашений. В нашем массиве P[i] содержит ровно i элементов и лежит на границе перед a[i]. Если хранить сумму до a[i] включительно, сдвинутся индексы формулы и появится отдельная обработка левого края 0. Выбери одно соглашение и проверь его на одном элементе.

Участок с суммой k задаёт пару префиксов с разностью k

Теперь сверке нужна другая статистика: сколько непустых непрерывных участков дают ровно k копеек. Их границы заранее неизвестны. Всего участков n(n + 1) / 2. Если вычислять каждый с нуля, получится O(n³). Даже два цикла с накоплением суммы или два префикса на пару границ оставляют O(n²) проверок.

Нельзя просто передвигать окно, уменьшая слишком большую сумму. В журнале есть возвраты. Для [4, −1, 1] и k = 3 после первого платежа 4 такое окно выкинет его, хотя следующая операция −1 создала бы подходящий [4, −1]. Правило «сумма больше — убери слева» требует монотонности, которой здесь нет.

Следующие фрагменты CountingDemo.java сравнивают разумный медленный перебор с неверно перенесённым окном. Это демонстрация ошибки, а не универсальный алгоритм подсчёта для неотрицательных значений:

static long brute(int[] values, long target) {
    long answer = 0;
    for (int left = 0; left < values.length; left++) {
        long sum = 0;
        for (int right = left; right < values.length; right++) {
            sum += values[right]; // Не пересчитываем отрезок целиком: уже O(n²), не O(n³).
            if (sum == target) answer++;
        }
    }
    return answer;
}

static long wrongWindow(int[] values, long target) {
    long sum = 0, answer = 0;
    int left = 0;
    for (int right = 0; right < values.length; right++) {
        sum += values[right];
        while (left <= right && sum > target) sum -= values[left++];
        if (left <= right && sum == target) answer++;
    }
    return answer;
}

Вернёмся к префиксам. Для непустого участка [left, right) требуется left < right и P[right] − P[left] = k. Переносим известные величины: P[left] = P[right] − k. Если правая граница уже известна, нам нужна конкретная сумма на одной из прежних границ.

Это тот же ход, что в поиске дополнения через хеш-таблицу: из текущего значения и цели вычисляем то, что должно было встретиться раньше. Разница в том, что одинаковая сумма может соответствовать многим разным границам. Они дают разные участки и должны считаться отдельно.

При k = 0 нужно встретить тот же префикс ещё раз. В [2, −2, 2, −2] префиксы [0, 2, 0, 2, 0] возвращаются к прежним значениям. Каждая пара равных префиксов с разными позициями означает непустой участок с суммой 0. Сортировать суммы не нужно: важен исходный порядок границ.

Частоты прошлых префиксов считают все начала одним поиском

Храним Map<Long, Long>: сумма префикса → число прежних границ с этой суммой. Перед обработкой очередного элемента в карте лежат P[0]..P[right − 1]. Сначала прибавляем элемент к текущей сумме P[right]. Затем частота значения P[right] − k показывает число подходящих начал. Только после этого записываем P[right].

Карту начинаем с 0 → 1. Это единственная граница перед первым элементом, P[0] = 0. Она нужна, чтобы считать участки, начинающиеся с индекса 0. Пустой участок не становится ответом: текущей правой границы в карте ещё нет, поэтому каждая найденная левая граница строго меньше правой.

static long count(int[] values, long target, boolean trace) {
    Map<Long, Long> frequency = new HashMap<>();
    frequency.put(0L, 1L); // Одна граница до первого элемента: P[0]=0.
    long sum = 0, answer = 0;
    int right = 0;
    for (int value : values) {
        right++;
        sum += value;
        long need = sum - target;
        long ways = frequency.getOrDefault(need, 0L); // Только уже прошедшие границы left < right.
        answer += ways;
        if (trace) System.out.println("r=" + right + " prefix=" + sum + " need=" + need + " ways=" + ways + " total=" + answer);
        frequency.merge(sum, 1L, Long::sum); // Текущая граница станет прошлой для следующего шага.
    }
    return answer;
}

На последнем −2 текущая сумма снова 0. В карте до записи уже два нулевых префикса: на границах 0 и 2. Они дают [0, 4) и [2, 4). Алгоритм не создаёт эти участки в памяти, а сразу прибавляет их число 2. У каждого участка одна правая граница, поэтому повторно он посчитан не будет.

На шаг приходится постоянное число операций с HashMap. При нормальном распределении ключей их амортизированная стоимость даёт ожидаемое O(n) время. Карта хранит не больше n + 1 разных сумм: память O(n). Полный массив P для этого алгоритма не нужен — достаточно текущей суммы и карты прежних состояний. Устройство коллизий и расширения разобрано в Hash Tables.

Множество и ранняя запись теряют смысл границ

Множество отвечает только «есть ли такая сумма». Для [0, 0, 0] каждый новый ноль имеет одно и то же значение префикса, но всё больше разных начал. Частоты дают 1 + 2 + 3 = 6 участков; множество добавит лишь по одному и вернёт 3. Число результатов само может быть квадратичным, хотя вычисляем его одним проходом.

static long wrongSet(int[] values, long target) {
    Set<Long> seen = new HashSet<>();
    seen.add(0L);
    long sum = 0, answer = 0;
    for (int value : values) {
        sum += value;
        if (seen.contains(sum - target)) answer++; // Ошибка: теряется число разных границ с одной суммой.
        seen.add(sum);
    }
    return answer;
}

Два других изменения ломают инвариант карты. Без начального 0 → 1 исчезает участок [3] с суммой 3. Если сначала записать текущий префикс, при k = 0 он найдёт сам себя и добавит пустой участок. Флаги в ошибочной версии позволяют увидеть каждую ошибку отдельно:

static long wrongCount(int[] values, long target, boolean seed, boolean writeFirst) {
    Map<Long, Long> frequency = new HashMap<>();
    if (seed) frequency.put(0L, 1L);
    long sum = 0, answer = 0;
    for (int value : values) {
        sum += value;
        if (writeFirst) frequency.merge(sum, 1L, Long::sum); // Ошибка: собственная граница уже в карте.
        answer += frequency.getOrDefault(sum - target, 0L);
        if (!writeFirst) frequency.merge(sum, 1L, Long::sum);
    }
    return answer;
}

Начальный нулевой префикс и запись текущего — две версии одной технической операции, их можно переставлять.

Это разные позиции. Начальный P[0] стоит до любого непустого отрезка, а текущий P[right] на его правой границе. Порядок «найти прошлое → записать настоящее» обеспечивает left < right. Для пустого входа цикл вообще не выполняется и ответ равен 0.

Условие выбирает ключ, а нужный ответ — значение карты

Равенство префиксов полезно не только для подсчёта суммы. Допустим, журнал помечает операции двух типов числами 0 и 1. Ищем самый длинный непрерывный участок с одинаковым числом обоих типов. Заменим вклад 0 на −1, вклад 1 на +1. Сумма участка станет количеством единиц минус количество нулей; требуемый баланс равен 0.

Ключ — накопленный баланс. На текущей границе right такой же баланс был на left — значит, участок [left, right) сбалансирован. Для максимальной длины right − left нужен самый ранний left. Сохраняем первый индекс через putIfAbsent. Частота здесь ничего не говорит о длине, а перезапись индекса оставляет только короткие будущие участки.

Фрагменты KeyDemo.java. Флаг overwrite включает ошибочную перезапись для сравнения:

static int balanced(int[] values, boolean overwrite, boolean trace) {
    Map<Integer, Integer> first = new HashMap<>();
    first.put(0, 0); // Нулевой баланс перед элементами, позиция границы 0.
    int balance = 0, best = 0;
    for (int right = 1; right <= values.length; right++) {
        balance += values[right - 1] == 0 ? -1 : 1;
        Integer left = first.get(balance);
        if (left != null) best = Math.max(best, right - left);
        if (trace) System.out.println("r=" + right + " balance=" + balance + " first=" + left + " best=" + best);
        if (overwrite) first.put(balance, right); // Ошибка для максимальной длины: заменяем раннюю границу.
        else first.putIfAbsent(balance, right); // Чем раньше начало, тем длиннее отрезок.
    }
    return best;
}

Кратность k превращает ключ в остаток

Если сумма должна делиться на положительный divisor, равенство меняется: P[right] − P[left] кратно divisor. Значит, оба префикса принадлежат одному классу остатков. Ключом станет нормализованный остаток в [0, divisor), значением для подсчёта остаётся частота.

У Java знак результата % следует за делимым. Для −1 и 4 остатки от деления на 5 равны −1 и 4, хотя их разность 5 кратна делителю. Math.floorMod при положительном делителе приводит их к одному значению 4:

static long divisible(int[] values, int divisor, boolean normalize) {
    Map<Integer, Long> frequency = new HashMap<>();
    frequency.put(0, 1L);
    long sum = 0, answer = 0;
    for (int value : values) {
        sum += value;
        int remainder = normalize ? (int) Math.floorMod(sum, (long) divisor) : (int) (sum % divisor);
        answer += frequency.getOrDefault(remainder, 0L); // Разность префиксов кратна divisor.
        frequency.merge(remainder, 1L, Long::sum);
    }
    return answer;
}

В последней задаче возможны только divisor разных ключей. HashMap хранит O(min(n + 1, divisor)) ключей; если делитель мал, можно взять long[divisor] и получить O(n + divisor) время с учётом создания массива. Для огромного делителя массив был бы расточительным. Выбор хранения следует из пространства ключей, а не из названия паттерна.

Префиксы требуют точной арифметики и стабильного исходного журнала

Перед реализацией оцени границы чисел. Для приведённых задач n ≤ 200 000, элементы — int: модуль суммы не превысит 200 000 · 2 147 483 648 = 429 496 729 600 000 и помещается в long. В задаче точной суммы |k| ≤ 10¹², поэтому sum − k тоже помещается. Расширение нужно выполнить до сложения; присваивание уже переполненного int в long не восстановит сумму.

При построении P[i] уже long, поэтому p[i] + values[i] вычисляется в long. В отдельном выражении a + b оба операнда int: позднее приведение сохранило ошибку. Math.addExact(int, int) сообщил о переполнении исключением. Для произвольных long-сумм потребуется собственная граница, точные операции Math.addExact/subtractExact или BigInteger. У арифметики произвольной точности стоимость зависит ещё и от числа битов.

Префиксный массив — отдельный снимок. Если в журнале исправили a[2] с 7 на 70, все P[j] при j ≥ 3 должны вырасти на 63. Старый массив P сам этого не увидит. В RangeDemo после исправления читаем тот же участок [1, 4) через старый снимок, напрямую и после перестроения:

System.out.println("== a prefix is a snapshot ==");
payments[2] = 70;
System.out.println("changed=" + Arrays.toString(payments));
System.out.println("old [1, 4)=" + range(p, 1, 4));
System.out.println("actual [1, 4)=" + direct(payments, 1, 4).sum());

System.out.println("rebuilt=" + Arrays.toString(rebuilt));

Старый итог 3 был верным для прошлой версии, текущий — 66. Исправление одного элемента требует изменить n − i последующих префиксов, в худшем O(n). При частых обновлениях полезны дерево Фенвика для сумм или дерево отрезков: точечное изменение и запрос суммы у них O(log n). Полная реализация этих структур выходит за scope этой темы.

В backend префиксы подходят для неизменяемой выгрузки, последовательности событий или повторных итогов по временным корзинам. Порядок и версия данных должны быть определены до построения. Если другой поток меняет массив во время прохода, получится смесь состояний; сначала получи согласованный снимок. При дописывании в конец можно вычислить следующий префикс, а произвольные исправления меняют весь зависимый суффикс.

Для одного запроса обычный проход уже O(n); префиксы займут столько же времени и добавят память. Для множества запросов они окупаются. Сам факт возможности быстро накопить состояние ещё недостаточен: нужно уметь убрать общее начало. Для суммы это вычитание, для XOR повторное XOR. Из двух префиксных минимумов минимум внутреннего участка восстановить нельзя: утраченную информацию вычитание не вернёт.

На собеседовании начни с [left, right) и смысла P[i], выведи равенство, затем выбери содержание карты. Проверь край 0, правую границу n, пустой вход, отрицательные числа, повторяющиеся суммы и порядок записи. Для неравенства суммы при отрицательных значениях простого поиска точного ключа недостаточно; для «подпоследовательности» вместо непрерывного участка меняется сама модель. Sliding Window и Binary Search требуют своего доказательства монотонности.

  • P[i] — сумма первых i элементов; сумма [left, right) равна P[right] − P[left]. Нулевой префикс убирает отдельный случай начала 0.
  • Неизвестное начало ищется по P[right] − k среди прежних границ. Отрицательные значения не ломают это равенство.
  • Для подсчёта нужны частоты, для максимальной длины — первые индексы. Одинаковые суммы на разных границах обозначают разные начала.
  • Сначала найди прежние префиксы, затем запиши текущий: иначе при k = 0 посчитаешь пустой участок.
  • Сумма и число ответов требуют отдельной оценки диапазона. Исправленный журнал требует обновить зависимые префиксы.

Подсказка 2

Для запроса [left, right) ответ P[right] − P[left]. Сумму считай в long с первой операции, пустой диапазон обработается той же формулой.

Решение

Один проход сохраняет накопленные суммы на всех границах. Два чтения на запрос отменяют общее начало. Массив префиксов длиннее входа на одну ячейку, поэтому допустима правая граница n.

static long[] solve(int[] values, int[][] queries) {
    long[] p = new long[values.length + 1];
    for (int i = 0; i < values.length; i++) p[i + 1] = p[i] + values[i];
    long[] result = new long[queries.length];
    for (int i = 0; i < queries.length; i++) {
        int left = queries[i][0], right = queries[i][1];
        result[i] = p[right] - p[left]; // Оба индекса обозначают границы, right не входит в отрезок.
    }
    return result;
}

static long solve(int[] values, long target) {
    Map<Long, Long> frequency = new HashMap<>();
    frequency.put(0L, 1L); // Позволяет выбрать начало перед первым элементом.
    long sum = 0, answer = 0;
    for (int value : values) {
        sum += value;
        answer += frequency.getOrDefault(sum - target, 0L); // Сначала считаем только непустые отрезки.
        frequency.merge(sum, 1L, Long::sum);
    }
    return answer;
}

Решение

Накопленный баланс равен разности количеств двух типов во всём начале. Если на двух границах он одинаков, разность внутри участка равна 0. Самая ранняя левая граница даёт максимальную длину для любого будущего конца.

static int solve(int[] values) {
    Map<Integer, Integer> first = new HashMap<>();
    first.put(0, 0);
    int balance = 0, best = 0;
    for (int right = 1; right <= values.length; right++) {
        balance += values[right - 1] == 0 ? -1 : 1; // Сумма равна количеству единиц минус количество нулей.
        Integer left = first.get(balance);
        if (left != null) best = Math.max(best, right - left);
        first.putIfAbsent(balance, right); // Первая граница даёт наибольшую длину для будущих right.
    }
    return best;
}

Подсказка 2

Сохрани frequency[0] = 1; текущую сумму считай в long. Math.floorMod(sum, (long) divisor) даёт остаток в [0, divisor), который безопасно привести к int. После подсчёта увеличь его частоту.

Решение

Вместо точной суммы ключ хранит класс остатка. Нормализация объединяет отрицательные и положительные префиксы, разность которых кратна делителю. Порядок поиска и записи сохраняет непустоту, как в задаче точной суммы.

static long solve(int[] values, int divisor) {
    Map<Integer, Long> frequency = new HashMap<>();
    frequency.put(0, 1L);
    long sum = 0, answer = 0;
    for (int value : values) {
        sum += value;
        int remainder = (int) Math.floorMod(sum, (long) divisor); // При divisor > 0 всегда в [0, divisor).
        answer += frequency.getOrDefault(remainder, 0L);
        frequency.merge(remainder, 1L, Long::sum);
    }
    return answer;
}
