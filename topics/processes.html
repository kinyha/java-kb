Processes & Threads

Процесс даёт программе собственное адресное пространство и набор ресурсов. Потоки выполняют её код: у каждого свой стек и положение в программе, а память процесса у них общая. Ядро распределяет между готовыми потоками время CPU и снимает с CPU тех, кому пока нечего делать. Отсюда следуют два разных вида ожидания: поток может ждать своей очереди или ждать внешнего события. Если их различать, становится понятнее и зависший платёж, и цена сотни рабочих потоков, и остановка сервиса сигналом.

Дочерняя программа зависла на логах, пока родитель ждал её завершения

Платёжный сервис запускает отдельную программу для формирования квитанции. Она пишет результат в stdout, логи — в stderr. Родитель вызывает waitFor(), чтобы дождаться результата. Программа уже запустилась, но вызов не возвращается. CPU почти свободен: оба процесса ждут.

У запущенного через ProcessBuilder ребёнка по умолчанию три канала. Их названия в API относятся к родителю:

Поток Java у родителяКуда идут байты
getOutputStream()Родитель пишет в stdin ребёнка.
getInputStream()Родитель читает stdout ребёнка.
getErrorStream()Родитель читает stderr ребёнка.

В ProcessDemo.java ребёнок сообщает о готовности и пишет 32 МиБ в stderr. Родитель читает их позже. Короткий срок waitFor позволяет увидеть зависание и продолжить опыт. Фрагмент режима pipe:

Process process = child("log-child");               // Отдельная JVM, stderr пока не читается.
System.out.println("ready=" + output.readLine());   // Ребёнок уже сообщил child ready.
boolean finished = process.waitFor(150, TimeUnit.MILLISECONDS);
System.out.println("finished without reading stderr=" + finished);

long bytes = process.getErrorStream()
    .transferTo(OutputStream.nullOutputStream());   // Освобождаем место в канале.
System.out.println("drained stderr bytes=" + bytes);
System.out.println("finished after drain=" + process.waitFor(5, TimeUnit.SECONDS));
System.out.println("stdout=" + output.readLine());
System.out.println("exit=" + process.exitValue());
ready=child ready
finished without reading stderr=false
drained stderr bytes=33554432
finished after drain=true
stdout=child done

Запись в заполненный pipe ждёт, пока родитель освободит место чтением. Родитель ждёт выхода ребёнка. Продвижения нет: waitFor не забирает вывод. Такое взаимное ожидание возникает через ресурсы ОС, без Java-мониторов.

Демо запускается из examples/os: java ProcessDemo.java pipe. Нужен JDK 21, сборки и банковского сервера нет. Полные команды — в README. POSIX-примеры fork ниже написаны на C: Java не даёт клонировать работающую JVM через публичный API. Все показанные результаты проверены на macOS; описанные отдельно средства Linux отмечены явно.

Потоки делят память процесса, но продолжают работу каждый со своего места

Программа — файл с кодом. Процесс — её работающий экземпляр: виртуальное адресное пространство, открытые файлы, права, сведения о выполнении. Два запуска одного JAR создают два процесса с отдельными Java heap. Одинаковый числовой адрес в них может указывать на разные данные. Передать ссылку Payment соседней JVM через обычный вызов метода нельзя.

У потока свои регистры, следующая инструкция, стек и локальное состояние. Код, heap и таблица файлов общие. Поток уведомления получает ссылку на тот же объект платежа, с которым работает его сосед. Собственный стек не делает объект по этой ссылке частным.

Режим threads использует именно платформенный поток. Рабочий поток меняет поле класса, затем завершается из-за исключения. Обработчик исключения печатает причину, а main дожидается окончания:

private static int captured = 41;                 // Одно поле на эту JVM.

Thread worker = Thread.ofPlatform().unstarted(() -> {
    captured = 99;
    System.out.println("worker captured=" + captured);
    throw new IllegalStateException("bank refused");
});
worker.setUncaughtExceptionHandler((thread, error) ->
    System.out.println("worker failed=" + error.getClass().getSimpleName()));
worker.start();
worker.join();                                    // После join запись worker видна main.
System.out.println("main after join: captured=" + captured + ", alive=true");
worker captured=99
worker failed=IllegalStateException
main after join: captured=99, alive=true

main видит 99 в общем поле. Исключение завершило только worker. Видимость записи обеспечил join; переключение CPU само по себе не заменяет правила Java Memory Model. Одновременно выполняющиеся команды требуют согласования доступа.

В Linux каждый поток имеет TID. Потоки процесса объединены в группу с общим TGID — его возвращает getpid(). Ядро планирует отдельные задачи-потоки. Платформенные потоки JVM соответствуют потокам ОС. Виртуальные потоки Java планирует JVM на потоки-носители; ядро распределяет CPU между носителями. Их количество не равно количеству виртуальных потоков.

Готовый поток ждёт CPU, заблокированный — события, которое вернёт его в очередь

Один логический CPU выполняет один поток; другие готовые потоки ждут выбора планировщика. Читатель пустого сокета ждёт данные. Когда они приходят, ядро делает его снова готовым. Пробуждение и получение CPU — разные события.

В упрощённой модели OSTEP есть три состояния: Running — выполняется, Ready — может выполняться, Blocked — ждёт событие. В Linux в инструментах часто видны R для выполняющегося или готового потока, S для прерываемого ожидания и D для непрерываемого ожидания в ядре. Они не равны состояниям Thread.State Java: Java RUNNABLE тоже не доказывает, что поток сейчас получил CPU.

Переключение контекста сохраняет состояние уходящего потока и восстанавливает другой: регистры, стек, место продолжения и сведения ядра. Java heap при этом не копируется. Для другого процесса меняется адресное пространство; у соседних потоков оно общее. Цена включает работу ядра и потерю локальности кешей. Маркировка адресных пространств помогает сохранять часть TLB, поэтому его полный сброс при каждом переключении не обязателен.

Системный вызов — другой переход: тот же поток входит из пользовательского режима в ядро. Если read сразу нашёл данные, он может вернуться без выбора другого потока. Если данных нет и чтение блокирующее, появляется причина снять его с CPU. Вытесняющая многозадачность также позволяет ядру сменить поток по таймеру: бесконечный цикл пользователя не получает CPU навсегда.

Планировщик задаёт политику выбора, переключение — механизм. С Linux 6.6 обычный справедливый класс начал переходить от CFS к EEVDF. Его выбор учитывает полученную долю CPU и виртуальный срок выполнения; это не простая круговая очередь с одним неизменным квантом. nice влияет на относительный вес конкурирующих задач, а не обещает срок ответа банка. На нескольких CPU добавляются очереди, распределение нагрузки и миграция потоков.

fork отделяет память, exec заменяет программу, wait забирает результат выхода

В Unix fork() создаёт ребёнка, который продолжает выполнение после того же вызова. Родитель получает PID ребёнка, ребёнок — 0; ошибка даёт −1. После успешного fork у них отдельные адресные пространства с исходно одинаковым содержимым. Linux использует copy-on-write: сначала страницы могут ссылаться на общую физическую память, а запись вызывает создание отдельной копии нужной страницы. Это не общий изменяемый Java heap.

Файлы устроены иначе. Ребёнок наследует копию таблицы дескрипторов; соответствующие записи обеих таблиц ссылаются на одну open file description в ядре. У неё общая позиция чтения. Режим copy из ForkDemo.c показывает обе границы сразу. Фрагмент без проверок ошибок:

int captured = 41;
int fd = mkstemp(name);                // Временный файл открыт один раз, до fork.
write(fd, "ABC", 3);
lseek(fd, 0, SEEK_SET);                // Оба начнут с одной записи ядра: позиция 0.

pid_t child = fork();
if (child == 0) {
    captured = 99;                    // Собственная копия памяти.
    char letter;
    read(fd, &letter, 1);              // A; общая позиция становится 1.
    printf("child captured=%d, file=%c\n", captured, letter);
    fflush(stdout);                   // _exit не выгружает буферы stdio.
    _exit(0);
}
waitpid(child, &status, 0);            // Родитель читает строго после ребёнка.
char letter;
read(fd, &letter, 1);                  // B: закрытие fd ребёнка позицию не сбросило.
printf("parent captured=%d, file=%c\n", captured, letter);
child captured=99, file=A
parent captured=41, file=B

exec загружает другую программу в тот же процесс: PID сохраняется, прежняя память и код заменяются. При успехе старый вызов не возвращается; при ошибке выполнение продолжается в старой программе. Так оболочка может сначала создать ребёнка, затем запустить в нём java. Дескрипторы, помеченные close-on-exec, закрываются. Это позволяет отделить создание процесса от выбора новой программы.

Ядро сохраняет статус завершившегося ребёнка. waitpid получает статус и освобождает оставшуюся запись. До этого ребёнок — zombie: код уже не выполняется, прежней памяти нет, но запись о завершении занимает место. Если родитель вышел раньше ребёнка, ребёнок становится сиротой и получает нового родителя. В Linux им может быть subreaper или init соответствующего пространства PID.

Под капотом: fork многопоточного процесса копирует замки без их владельцев

У ребёнка остаётся только поток, который вызвал fork, но память остальных потоков, включая состояния mutex, скопирована. Замок мог быть занят потоком, который в ребёнке вообще не существует. Поэтому до exec в ребёнке многопоточной программы разрешены только async-signal-safe операции. Прямой fork работающей JVM ради фоновой задачи — плохая граница: JVM, аллокатор и библиотеки уже имеют потоки и замки. Для новой программы Java предоставляет ProcessBuilder; конкретный способ запуска выбирает реализация JDK.

Процессы общаются через явный канал, а EOF зависит от всех его писателей

IPC связывает процессы: нужно определить данные, ожидание и окончание обмена. Pipe удобен родителю и ребёнку, Unix-сокет — независимым локальным процессам, TCP — для сети. Разделяемая память сокращает копирование и требует синхронизации.

У pipe чтение возвращает 0 после исчерпания данных, когда закрыты все дескрипторы, удерживающие конец записи. Завершение ребёнка закрывает его дескрипторы. Если у родителя осталась унаследованная копия, читатель продолжает ждать будущие байты. Режим eof намеренно оставляет эту копию открытой:

pipe(ends);                           // ends[0] — чтение, ends[1] — запись.
pid_t child = fork();
if (child == 0) {
    close(ends[0]);
    write(ends[1], "paid", 4);
    close(ends[1]);
    _exit(0);
}
waitpid(child, &status, 0);            // Ребёнок уже завершился.
read(ends[0], text, 4);                // Забрали четыре готовых байта.
poll(&ready, 1, 0);                   // Пусто, EOF ещё нет: у родителя открыт ends[1].
close(ends[1]);                       // Закрыли последнюю копию писателя.
read(ends[0], &next, 1);              // Теперь возвращает 0, то есть EOF.
child exited=true, message=paid
EOF while parent owns writer=false
EOF after closing parent writer=true

Отсюда два правила для запуска программы квитанций. Вывод и ошибки читают параллельно либо сразу направляют в файл. Если оба канала можно объединить, redirectErrorStream(true) оставляет один поток для чтения. Когда ребёнку больше не будут посылать вход, родитель закрывает его stdin: иначе ребёнок сам может ждать EOF и не выходить. Чтение только stdout не освобождает stderr.

Отложенное чтение stderr — намеренная ошибка демо. В сервисе оба потока читают с момента старта, ограничивают сохраняемые логи и ставят общий срок. waitFor(timeout) сам ребёнка не убивает: остановка требуется отдельно. После выхода проверяют код и квитанцию.

SIGTERM даёт программе остановиться, SIGKILL обрывает её без очистки

Сигнал — механизм ОС, а не Java-исключение. При доставке ядро учитывает действие для сигнала: стандартное поведение, игнорирование или обработчик. SIGTERM по умолчанию завершает процесс, но приложение может перехватить его и выполнить свою остановку. SIGKILL и SIGSTOP нельзя перехватить, заблокировать или проигнорировать. SIGSTOP приостанавливает выполнение; SIGCONT позволяет продолжить.

При обычной остановке JVM на Unix выполняются shutdown hooks — потоки Java для завершения работы. Они работают вне низкоуровневого POSIX-обработчика сигнала. Режим signals регистрирует hook в дочерней JVM, ждёт её готовности и сравнивает запросы через ProcessHandle:

// В дочерней JVM, до сообщения child ready.
Runtime.getRuntime().addShutdownHook(new Thread(() -> {
    System.out.println("hook ran");
    System.out.flush();
}));
new CountDownLatch(1).await();          // Ожидание остаётся до остановки процесса.

// В родителе: отдельный ребёнок для каждого варианта.
process.toHandle().destroy();          // В этом Unix-запуске: обычная остановка, SIGTERM.
process.waitFor(5, TimeUnit.SECONDS);

process.toHandle().destroyForcibly();   // Во втором опыте: SIGKILL, hook не выполнится.
destroy hook=hook ran
destroy exited=true
destroyForcibly hook=<none>
destroyForcibly exited=true

Это результат Unix-запуска; Java API не задаёт номер сигнала для каждой ОС. ProcessHandle запрашивает остановку, объект Process остаётся для чтения и ожидания. После принудительного запроса всё равно нужен wait, чтобы подтвердить выход.

Thread.interrupt() помогает кооперативно остановить задачу внутри JVM. SIGTERM всей JVM он не посылает; сам SIGTERM также не превращается в InterruptedException каждого потока. Приложение определяет порядок остановки платежей: прекратить приём, закончить или отменить работу, сохранить состояние и освободить ресурсы. В Spring это разобрано в Boot Startup & Shutdown.

Под капотом: маска принадлежит потоку, а обычные сигналы могут сливаться

Действия для сигналов общие у потоков процесса, но маска блокируемых сигналов своя у каждого. Сигнал, адресованный процессу, ядро доставляет подходящему потоку; заблокированный сигнал остаётся ожидающим. Несколько одинаковых стандартных сигналов могут слиться в один ожидающий сигнал. Поэтому SIGUSR1 не подходит как счётчик «пришло пять платежей». Низкоуровневый обработчик ограничен async-signal-safe функциями; работу с очередью и данными лучше продолжать в обычном контексте выполнения.

Для задержки платежа сначала различают очередь CPU, ожидание и ограничение ресурсов

Готовые потоки конкурируют за CPU. Потоки, ожидающие банк, могут оставлять CPU свободным: задержка определяется внешним событием или блокировкой. Размер пула и количество CPU решают разные задачи.

В Linux cgroup v2 квота cpu.max задаёт доступное время CPU за период, а cpu.stat показывает в том числе ограничения времени выполнения. Нехватка квоты способна остановить продвижение всей группы, хотя на хосте есть свободные ядра. cpuset ограничивает допустимые CPU — это другой механизм. В контейнере PID и путь к cgroup также зависят от пространства имён; их читают в контексте самого приложения.

Процесс даёт более сильную границу отказа и ресурсов, но требует запуска, IPC, контроля выхода и отдельной эксплуатации. Потоки проще делят данные, зато нуждаются в согласовании и не изолируют фатальный отказ JVM. Виртуальные потоки уменьшают цену множества ожидающих Java-задач, но не ускоряют вычисления и не увеличивают пропускную способность банка. Модель памяти — в Virtual Memory, дескрипторы и способы ожидания I/O — в I/O Models, рабочие команды диагностики — в Linux Basics.

На собеседовании

Чем процесс отличается от потока и что копирует fork?

Процесс задаёт адресное пространство и ресурсы программы. Поток выполняет код внутри него: свой стек, регистры и следующая инструкция, но общая память с соседними потоками. fork создаёт процесс с отдельной копией исходной памяти; запись ребёнка не меняет переменную родителя. Дескрипторы копируются как ссылки на объекты ядра, поэтому позиция одного открытого до fork файла остаётся общей. exec затем может заменить программу ребёнка с сохранением его PID.

  • Copy-on-write уменьшает немедленное копирование физических страниц, но не делает fork бесплатным: нужны структуры ядра и управление отображениями памяти.
  • В ребёнке многопоточного процесса остаётся один поток, а состояния чужих замков уже скопированы. До exec нужны async-signal-safe операции.
  • Изоляция памяти не изолирует внешний мир: процессы могут писать в тот же файл и проводить операции с той же базой. Эта граница требует протокола и согласования.

Что происходит при переключении контекста и почему больше потоков не всегда быстрее?

Ядро сохраняет состояние уходящего потока и восстанавливает выбранный поток: регистры, стек, место продолжения. Для другого процесса меняется адресное пространство. Если готовых задач больше, чем доступных CPU, они делят время и ждут очереди. Если задача ждёт I/O, ядро отдаёт CPU другой; это помогает перекрывать ожидания. Но для вычислений дополнительные потоки не добавляют CPU и увеличивают издержки.

  • Системный вызов может выполнить всю работу в контексте того же потока. Число syscall не равно числу переключений.
  • Миграция на другой CPU влияет на локальность данных. Цена переключения зависит от рабочей нагрузки и памяти; одна универсальная цифра в микросекундах мало помогает.
  • Доля CPU зависит от весов и ограничений cgroup. Свободные ядра хоста не доказывают, что контейнеру разрешено ими пользоваться.
  • Java RUNNABLE объединяет несколько ситуаций ОС. Для диагноза сопоставляю стек Java, состояние потока в ОС и профиль ресурса, на котором он задержался.

Почему программа, запущенная через ProcessBuilder, не завершается?

Проверяю протокол всех трёх каналов. Ребёнок может ждать вход или EOF на stdin, а может стоять на записи в заполненный stdout или stderr. waitFor не читает эти каналы. Я забираю вывод и ошибки одновременно либо направляю их в файл, закрываю законченный ввод и задаю общий срок. Когда процесс вышел, проверяю его код и результат. Для pipe EOF наступает после закрытия всех концов записи, включая копии у родителя.

  • У pipe и TCP есть поток байтов: одно write не равно одному read. Протокол задаёт длину, разделитель или иной способ выделить сообщение.
  • Чтение в память без ограничения меняет зависание на риск исчерпания памяти. Большой вывод направляю в ограниченное хранилище или разбираю по мере поступления.
  • Потомок ребёнка тоже может удерживать канал. Завершение прямого ребёнка и завершение всего дерева работы — разные события.
Почему квитанция иногда создаётся, но запрос навсегда остаётся в ожидании? 
Process child = new ProcessBuilder(command).start();
child.waitFor();                                  // Вывод пока никто не забирает.
String errors = new String(child.getErrorStream().readAllBytes());
String receipt = new String(child.getInputStream().readAllBytes());

Ребёнок может заполнить любой из двух выходных каналов и блокироваться до чтения. Родитель ждёт его выхода перед первым чтением. Нужно читать оба потока с начала работы или перенаправить их; перестановка двух последних строк после waitFor причину не устраняет. Если ещё и вход останется открытым, ребёнок может ждать EOF от родителя.

Чем SIGTERM отличается от SIGKILL и зачем ждать уже завершившегося ребёнка?

SIGTERM даёт программе обработать запрос остановки; SIGKILL прекращает её без обработчика и shutdown hooks. Для платежей сначала прекращают приём и дают текущей работе ограниченный срок, потом применяют принудительную остановку. Родитель через wait получает статус ребёнка и освобождает запись о завершении. Без этого может остаться zombie: CPU он не тратит, но запись в системе занимает. Запрос остановки и подтверждённый выход я считаю разными шагами.

  • Убийство процесса не отменяет уже сохранённую транзакцию и не возвращает автоматически списание банка. После перезапуска нужна сверка состояния.
  • Остановка родителя не обязана остановить всех его детей. Для фоновой работы важно определить владельца и порядок завершения всей группы процессов.
  • Даже SIGKILL не даёт обещания немедленно убрать задачу из настоящего непрерываемого ожидания в ядре. Исчезновение процесса подтверждают отдельно.
  • Стандартные сигналы не являются надёжной очередью бизнес-сообщений: одинаковые ожидающие сигналы могут объединяться.
