Design: Project Structure

Раскладка пакетов решает не только, где искать файл, но и что компилятор разрешит соседнему коду. Класс без модификатора доступа виден только своему пакету. Поэтому граница держится там, где рядом лежит код одной возможности, а наружу открыт один вход. Если все типы public, четыре известные раскладки отличаются только именами папок. Где компилятора не хватает, границу проверяет тест Spring Modulith или ArchUnit, а дальше — отдельный модуль сборки.

Обход хранилища прошёл ревью, потому что компилятору нечего было возразить

Платёжный сервис разложен привычно: web, service, repository. Через год в каждом пакете лежат десятки классов платежей, возвратов, выплат и отчётов вперемешку. Новому разработчику нужен экран возврата. Ему проще прочитать платёж прямо из хранилища, чем разбираться в PaymentService:

kb.layer
├── web
│   ├── PaymentController.java
│   └── RefundController.java        // новый класс
├── service
│   └── PaymentService.java          // правила: сумма, статусы, лимит возврата
├── repository
│   ├── PaymentRepository.java
│   └── JdbcPaymentRepository.java
└── model
    └── Payment.java
package kb.layer.web;

import kb.layer.repository.PaymentRepository;

public class RefundController {                   // Новый класс: читает платёж мимо сервиса.
    private final PaymentRepository store;        // Тип из чужого пакета: javac проверит доступ.

    public RefundController(PaymentRepository store) { this.store = store; }

    public String status(String id) { return store.find(id).status(); }
}

Код компилируется, тесты зелёные, в diff один файл. Правила возврата живут в PaymentService, а новый экран их не вызывает. Компилятор не мог возразить: PaymentRepository обязан быть public, потому что им пользуется PaymentService из соседнего пакета service. Тип, открытый одному соседу, открыт всему приложению.

Вторая проблема видна по дереву. Верхние папки сообщают «Spring MVC с базой данных», а не «платежи и возвраты». Возврат размазан по трём каталогам: правка одного сценария трогает три папки, а в каждой рядом лежит чужой код.

Отсюда вопрос собеседования: «как ты раскладываешь проект по пакетам и почему». Ответ «по слоям» или «по фичам» — только половина. Вторая половина — что твоя раскладка запрещает и чем это проверяется. Simon Brown в главе «The Missing Chapter» книги Мартина «Чистая архитектура» сравнивает четыре раскладки одного сервиса. Дальше они разобраны на этом платёжном примере.

Все примеры лежат в examples/project-structure. Первое демо — java StructureDemo.java, нужен только JDK 21.

Четыре раскладки отличаются тем, что лежит рядом и что открыто наружу

Package by layer режет приложение горизонтально, по технической роли класса. Это раскладка из прошлого шага. Она понятна любому, кто видел Spring-проект, и для маленького сервиса её хватает.

Package by feature режет вертикально, по возможности системы. Всё для платежей лежит в одном пакете: контроллер, сервис, хранилище, модель. Раз соседи в одном пакете, public им не нужен. У Брауна наружу смотрит один тип — контроллер.

kb.feature
├── payments
│   ├── PaymentController.java       // public: единственный вход
│   ├── PaymentService.java
│   ├── PaymentRepository.java
│   ├── JdbcPaymentRepository.java
│   └── Payment.java
└── refunds
    └── …

Ports and adapters делит код на ядро и всё остальное. Ядро domain не знает о вебе и базе и объявляет порт Payments; адаптер database его реализует. Браун называет порт по-доменному, Payments, а не PaymentRepository. Почему зависимости смотрят внутрь, разобрано в Clean & Hexagonal Architecture. Здесь важнее другое: что из этого должно быть public.

kb.hex
├── domain                           // ядро
│   ├── Payment.java                 // public: его видят адаптеры
│   ├── PaymentService.java          // public: его вызывает web
│   └── Payments.java                // public: порт, его реализует database
├── web
│   └── PaymentController.java
└── database
    └── JdbcPayments.java            // адаптер скрыт, снаружи только порт

Package by component — вариант самого Брауна. Правила и хранение платежей собраны в один пакет за одним интерфейсом PaymentComponent, а веб лежит отдельно. Веб вынесен потому, что способов доставки бывает несколько: REST, слушатель Kafka, задача по расписанию. Все они вызывают один и тот же компонент и не могут дотянуться до его хранилища.

kb.component
├── payments                         // компонент: правила + хранение
│   ├── PaymentComponent.java        // public: единственный вход
│   ├── PaymentComponentImpl.java
│   ├── PaymentRepository.java
│   ├── JdbcPaymentRepository.java
│   └── Payment.java                 // public: результат для вызывающих
└── web
    └── PaymentController.java

Кричащая архитектура

У Мартина есть глава «Screaming Architecture»: чертёж библиотеки сразу говорит «библиотека», а не «кирпич и бетон». Так и дерево проекта должно говорить «платежи, возвраты, выплаты», а не «контроллеры, сервисы, репозитории». В раскладках по фичам и компонентам верхние папки называют предметную область, а Spring виден только в аннотациях внутри.

Польза практическая. Задача «новое правило возврата» начинается с поиска кода. Если ответ — одна папка refunds, новый человек находит его за минуту, а ревьюер видит, что правка не вышла за пределы фичи. Фреймворк при этом остаётся деталью: его можно обновить, не переименовав ни одного пакета.

Компилятор держит границу только там, где тип не public

Тип без модификатора доступа — package-private — виден только классам того же пакета. Именно того же, а не вложенного: для javac payments и payments.persistence — два несвязанных пакета, точка в имени ничего не даёт. Значит, внутри одного модуля сборки Java даёт ровно одну границу, которую проверяет компилятор: границу пакета.

Проверим это на всех четырёх раскладках. Демо добавляет в каждую тот же RefundController и смотрит, пустит ли его javac. Вот объявления типов, к которым он тянется:

// layer: repository/PaymentRepository.java
public interface PaymentRepository { … }         // Сервис в другом пакете: только public.
// feature: payments/PaymentRepository.java
interface PaymentRepository { … }                // Все соседи в том же пакете.
// hex: domain/Payments.java и database/JdbcPayments.java
public interface Payments { … }                  // Исходящий порт: его реализует адаптер из database.
class JdbcPayments implements Payments { … }     // Адаптер: снаружи виден только через порт.
// component: payments/PaymentRepository.java
interface PaymentRepository { … }                // Видят только классы компонента.

Демо компилирует каждый вариант с обходом через javax.tools.JavaCompiler и печатает первую ошибку. Второй прогон добавляет public всем типам без модификатора и повторяет то же самое:

for (boolean allPublic : new boolean[]{false, true}) {
    for (Case c : CASES) {                                    // Пять обходов из схемы.
        List<Path> withShortcut = new ArrayList<>(variant);  // Исходники раскладки…
        withShortcut.addAll(sources(base.resolve("shortcuts").resolve(c.shortcut()))); // …и RefundController.
        String error = compile(withShortcut, allPublic, out);  // Первая ошибка javac или null.
        // …печать результата
    }
}
// Только во втором прогоне: типы без модификатора доступа становятся public.
code = code.replaceAll("(?m)^(final |abstract )?(class|interface|record|enum) ", "public $1$2 ");

В layer и в ports and adapters обход прошёл не по недосмотру, а по устройству раскладки: тип, которым пользуется соседний пакет, обязан быть public. В гексагональной раскладке порт Payments лежит в ядре и реализуется в database, поэтому web может взять его напрямую и пропустить правила PaymentService. Компилятор такое не запретит; нужна проверка структуры.

Второй прогон — главная мысль главы Брауна. Если всё public, пакеты становятся способом организации кода, как папки, а не способом его скрыть. Так и выходит в живых проектах: шаблон нового класса в IDE начинается с public class, и через год раскладка по фичам защищает не больше, чем раскладка по слоям.

Package by feature сам по себе изолирует фичи друг от друга.

Только если внутри фичи типы package-private. С public-типами фича — это папка: обход из соседней фичи компилируется, как во втором прогоне демо.

Цена закрытой фичи

У раскладки по фичам две честные оговорки. Первая: если public только контроллер, другим фичам платёж недоступен иначе как по HTTP. Возвратам нужны данные платежа, поэтому на практике открывают PaymentService или отдельный фасад, и раскладка становится раскладкой по компонентам с веб-слоем внутри.

Вторая: внутри пакета компилятор слоёв не видит. PaymentController в пакете payments может позвать PaymentRepository напрямую, и javac промолчит. Package by component выносит веб в отдельный пакет как раз затем, чтобы этот обход стал ошибкой компиляции. Браун предпочитает именно такие границы: ошибку компиляции видно сразу в IDE, а правило в отдельном анализаторе срабатывает позже и только если его запускают.

Под капотом: что именно проверяет доступ

Правила доступа описаны в JLS §6.6. Для типа верхнего уровня выбор из двух: public или package-private. Про вложенность пакетов JLS §7.1 говорит прямо: иерархия имён нужна для удобной организации, а особого смысла сама по себе не имеет. Поэтому payments.internal не получает доступа к package-private типам payments, и наоборот.

JVM проверяет доступ ещё раз при связывании. Если класс собрали, а потом поменяли модификатор у зависимости и не пересобрали вызывающий код, вызов упадёт с IllegalAccessError. Рефлексия устроена иначе: в приложении на classpath все классы лежат в безымянном модуле, и setAccessible(true) открывает package-private конструктор. Поэтому Spring, Jackson и Hibernate создают такие объекты. В модульном приложении JPMS для этого понадобится opens.

Spring работает с package-private, а разросшуюся фичу держит тест Spring Modulith

Частый страх: Spring не найдёт непубличный класс. Сканирование компонентов читает class-файлы пакета и создаёт бины рефлексией, поэтому package-private класс с package-private конструктором — обычный бин. Тесты кладут в тот же пакет в src/test/java, и им доступно всё, что видно соседям по пакету. Последняя строка Maven-демо поднимает AnnotationConfigApplicationContext и вызывает возврат через такой бин:

package kb.shop.refunds;

import kb.shop.payments.PaymentService;           // API модуля payments.
import org.springframework.stereotype.Service;

@Service
class RefundService {                             // package-private бин: Spring его найдёт и внедрит.
    private final PaymentService payments;

    RefundService(PaymentService payments) { this.payments = payments; }

    String refund(String id) { return "REFUNDED " + payments.find(id).amount(); }
}
fixed spring: REFUNDED 2500

Настоящая проблема — размер. Пакет payments дорастает до сорока классов: контроллеры, сервисы, мапперы, сущности, клиенты банка. Хочется подпакетов payments.web и payments.persistence. Но подпакет для javac чужой: PaymentRepository из payments.persistence придётся сделать public, иначе его не увидит PaymentService из payments. Вместе с ним хранилище увидят и возвраты, и отчёты.

Выходов три. Можно держать пакет плоским, пока он читается: тридцать классов одной фичи в одном пакете — это нормально. Можно ввести подпакеты и проверять границу тестом. Можно вынести часть в модуль сборки — это следующий шаг. Для второго варианта в Spring есть Spring Modulith: он считает модулями прямые подпакеты пакета приложения, public-типы корневого пакета модуля — его API, а всё вложенное глубже — внутренностями, даже если оно public.

// broken/kb/shop/refunds/RefundService.java
import kb.shop.payments.persistence.PaymentRepository; // Внутренний пакет чужого модуля.

// StructureCheck.java: в обычном проекте это одна строка в тесте —
// ApplicationModules.of(Application.class).verify();
ApplicationModules modules = ApplicationModules.of("kb.shop");
var violations = modules.detectViolations();       // verify() бросил бы это же исключением.
broken modules: payments, refunds
broken verify: FAIL x4 Module 'refunds' depends on non-exposed type kb.shop.payments.persistence.PaymentRepository within module 'payments'!
fixed modules: payments, refunds
fixed verify: PASS

javac этот импорт пропустил: PaymentRepository public. Modulith нашёл четыре места в байткоде, где refunds держит чужой внутренний тип: поле, параметры конструктора, вызов метода. В исправленном варианте возвраты ходят через PaymentService, и проверка проходит. Демо вызывает ApplicationModules без запуска приложения; в проекте тест подключает spring-modulith-starter-test.

Так тест возвращает то, что Java теряет на подпакетах. Цена — граница держится, только пока тест запускают в CI, и узнаёшь о нарушении после сборки, а не при наборе кода. Как открыть подпакет намеренно через @NamedInterface, ограничить соседей через allowedDependencies и написать те же правила на ArchUnit, разобрано в Components & Modules.

Модуль сборки делает границу физической: чего нет в зависимостях, того не видно

Следующая ступень — отдельные модули Gradle или Maven. Каждый модуль компилируется со своим classpath. Если класса нет на classpath, javac не находит пакет вовсе: проверять нечего, импорт просто не собирается. Демо в examples/project-structure/gradle собирает три модуля, и app пытается импортировать хранилище в обход payments:

// settings.gradle.kts
include("app", "payments", "payments-persistence")

// app/build.gradle.kts
dependencies {
    implementation(project(":payments"))             // persistence сюда не попадает.
}

// payments/build.gradle.kts
dependencies {
    // implementation: persistence нужен payments, но не попадает на classpath его потребителей.
    // С -Pleak демо подключает его через api, как compile-зависимость в Maven, — и app его видит.
    if (providers.gradleProperty("leak").isPresent) {
        api(project(":payments-persistence"))
    } else {
        implementation(project(":payments-persistence"))
    }
}
== implementation
kb/shop/app/RefundController.java:3: error: package kb.shop.persistence does not exist
== api
app compiles

В Gradle implementation не передаёт зависимость дальше, api передаёт. В Maven зависимость со scope compile транзитивна, то есть ведёт себя как api: app увидит persistence через payments. Поймать это помогает mvn dependency:analyze — он печатает «Used undeclared dependencies» для классов, которыми модуль пользуется через чужую зависимость.

Браун для ports and adapters предлагает два дерева исходников: domain и infrastructure. Ядро тогда физически не может импортировать Spring Web или JPA — их нет в его зависимостях. Но внутри infrastructure адаптеры видят друг друга: веб-адаптер может позвать адаптер базы, минуя ядро. Браун называет это анти-паттерном «Périphérique», по кольцевой дороге вокруг Парижа: движение идёт по кругу снаружи и в центр не заходит.

Модуль сборки — самая крепкая граница внутри одного приложения, но и самая дорогая. Каждый модуль — свой файл сборки, свои зависимости, медленнее импорт в IDE. Циклы между модулями Gradle и Maven не собирают, и это плюс. Выносить модуль стоит, когда логическая граница уже устоялась и проверена тестом, а не наугад в первый день проекта.

Живой проект переводят по одной фиче, а новое правило сначала замораживают

Переложить триста файлов одним PR — значит получить конфликты во всех открытых ветках, ревью, которое никто не прочтёт, и сломанный git blame. Переход делают постепенно, и первым шагом идёт правило, а не перенос файлов.

Проблема правила в том, что в старом коде нарушений сотни, и тест сразу красный. ArchUnit решает это заморозкой: FreezingArchRule при первом запуске записывает все текущие нарушения в хранилище, а дальше падает только на новых. Во втором Maven-демо правило запрещает трогать payments.persistence снаружи модуля. Вариант later — это broken плюс новый ReportService с тем же обходом:

ArchRule rule = FreezingArchRule.freeze(noClasses()
        .that().resideOutsideOfPackage("kb.shop.payments..")
        .should().dependOnClassesThat().resideInAPackage("kb.shop.payments.persistence.."));
rule.check(new ClassFileImporter().importPath(classes));

Первый запуск записал три нарушения старого RefundService и прошёл. В later старый обход по-прежнему заморожен, а новый ReportService валит тест, и хранилище при этом не растёт. Когда возвраты перевели на PaymentService, ArchUnit сам убрал исправленные строки: хранилище пустеет вместе с долгом.

По умолчанию allowStoreCreation выключен. Без хранилища тест падает с StoreInitializationFailedException: «Creating new violation store is disabled». Это защита: если в CI хранилище потерялось, тест не должен молча заморозить все нарушения заново. Включи создание один раз локально, закоммить хранилище и выключи настройку.

Дальше порядок такой:

  1. Договорись о целевом дереве. Какие фичи на верхнем уровне, что считается API фичи, где живёт общий код. Запиши это правилом — Modulith или ArchUnit с заморозкой.
  2. Переноси по одной фиче. Move Class в IDE обновит импорты. Перенос — отдельный коммит без правок логики: так git распознает переименование по сходству содержимого, а ревьюер увидит, что смысл не менялся. Крупный перенос делай, когда открытых веток мало, и предупреди команду.
  3. Сузь доступ. После переноса многие типы public только по привычке. Инспекция IntelliJ «Declaration access can be weaker» находит типы и методы, которыми никто не пользуется снаружи пакета.
  4. Разрежь данные. Самое трудное — связи между сущностями разных фич. @ManyToOne Customer внутри Payment тянет фичу клиентов в платежи. Храни идентификатор и запрашивай данные через API соседней фичи, как ссылаются друг на друга агрегаты в DDD.
  5. Убери старое. Пустые service и repository удали, когда хранилище заморозки опустеет; заморозку по этому правилу сними.

Для маленького CRUD это церемония: раскладка окупается, когда растут фичи и команды

Сервис справочника валют с пятью таблицами и десятком эндпоинтов спокойно живёт по слоям. Правил почти нет, обходить нечего, раскладку понимает любой новичок. Компонент с интерфейсом и единственной реализацией на каждую таблицу, порты с мапперами между одинаковыми моделями, отдельный модуль сборки на три класса — это церемония: она добавляет файлы и переходы при чтении, а защищать ей нечего.

СитуацияРазумная раскладкаПочему
Маленький CRUD, одна командаby layer или плоские пакеты фич без правилсамая дешёвая, правила почти не нужно защищать

Смешанная раскладка нормальна: фичи на верхнем уровне, внутри крупной фичи — слои или порты и адаптеры, маленькие фичи плоские. Не нужно, чтобы все пакеты выглядели одинаково. Нужно, чтобы граница каждой фичи была видна и проверялась.

Пора менять раскладку, если правка одной фичи регулярно трогает три папки, на ревью находят обходы сервисов, а новички не могут найти код сценария. Перестарался, если интерфейсы появляются ради схемы, мапперы копируют поля между одинаковыми классами, а модуль сборки содержит три класса. Вывод Брауна в конце главы — не про конкретную раскладку. Задуманная архитектура теряется, если не решить, как она ляжет на пакеты, модификаторы доступа и модули. Решение зависит от размера и опыта команды, сложности задачи, сроков и бюджета.

  • Раскладка важна тем, что запрещает. Компилятор внутри модуля проверяет одну границу — пакет, и только для package-private типов.
  • В by layer и в портах ядра public вынужден: тип, нужный соседнему пакету, видят все. Feature и component могут спрятать хранилище за одним входом.
  • Всё public — и четыре раскладки становятся четырьмя способами разложить папки.
  • Подпакеты в Java — чужие пакеты. Разросшуюся фичу с подпакетами держит тест Spring Modulith или ArchUnit, а следующая ступень — модуль сборки.
  • Живой проект переводят по фиче, начиная с замороженного правила: старые нарушения записаны, новые валят сборку.

На собеседовании

Как ты раскладываешь Spring-проект по пакетам и почему?

На верхнем уровне — по фичам: payments, refunds, payouts. Внутри фичи всё, что меняется вместе: контроллер, сервис, хранилище, модель. Наружу открываю один вход — сервис или фасад фичи, остальное package-private. Spring такие классы находит и внедряет без проблем.

Зачем: правка сценария живёт в одной папке, по дереву видно, что делает система, а обход чужого хранилища не компилируется. Когда фича вырастает и нужны подпакеты, границу держит тест Spring Modulith: он считает вложенные пакеты модуля внутренними, даже если типы в них public.

  • Раскладка ценна тем, что запрещает. Если все типы public, by feature защищает не больше, чем by layer: пакеты превращаются в папки.
  • Внутри пакета фичи слоёв для компилятора нет: контроллер может звать репозиторий. Поэтому для крупных фич выношу веб отдельно — это package by component — или ставлю порты и адаптеры внутри фичи.
  • Маленький CRUD оставляю по слоям, и это нормально. Меняю раскладку, когда правки фичи начинают трогать три папки или на ревью находят обходы.
  • Следующая ступень — модули Gradle с implementation: чего нет в зависимостях, того javac не найдёт. Выношу модуль, когда граница уже устоялась.
Куда тогда класть общее: Money, общие исключения, конфигурацию?

В маленький общий пакет с понятным владельцем: типы-значения вроде Money, базовые исключения, утилиты без бизнес-логики. Сервисы и сущности туда не кладут, иначе common становится местом, от которого зависит всё и которое никто не может поменять. Конфигурация приложения лежит в корневом пакете рядом с классом @SpringBootApplication, а конфигурация фичи — в самой фиче. Почему большой common вредит, разобрано в Components & Modules.

Чем package by layer хуже package by feature?

By layer раскладывает классы по технической роли: контроллеры, сервисы, репозитории. Один сценарий размазан по трём папкам, а дерево сообщает о фреймворке, а не о предметной области. Главное — сервису нужен репозиторий из соседнего пакета, поэтому репозиторий обязан быть public, и его может взять любой контроллер в обход правил.

By feature кладёт сценарий в одну папку. Соседи по пакету видят друг друга без public, поэтому хранилище фичи можно спрятать, а обход из соседней фичи станет ошибкой компиляции.

  • By layer не ошибка для маленького сервиса: проблемы проявляются с ростом числа фич и людей.
  • Фича, у которой public только контроллер, недоступна соседям иначе как по HTTP. В реальности открывают сервис или фасад — получается package by component.
  • В ports and adapters порт обязан быть public, потому что адаптер лежит в другом пакете. Поэтому веб-адаптер может обойти сервис ядра, и это ловит только тест.
Скомпилируется ли этот обход в гексагональной раскладке? 
// kb/hex/domain/Payments.java
public interface Payments { Payment find(String id); /* … */ }

// kb/hex/web/RefundController.java
package kb.hex.web;
import kb.hex.domain.Payments;

public class RefundController {
    private final Payments store;
    public RefundController(Payments store) { this.store = store; }
    public String status(String id) { return store.find(id).status(); }
}

Скомпилируется: демо печатает hex RefundController -> Payments (port) compiles. Порт должен быть public, иначе его не реализует адаптер из database. Поэтому web может читать через порт напрямую и пропускать правила PaymentService. Сделать порт package-private нельзя, не переложив адаптер в пакет ядра. Остаётся правило ArchUnit «классы web не зависят от исходящих портов» или вынос веба и ядра в разные модули сборки с явным API.

Почему говорят, что public везде стирает архитектуру?

Из всей раскладки компилятор проверяет только модификаторы доступа. Package-private тип виден лишь своему пакету, public — всему приложению. Если всё public, любой класс может импортировать любой, и пакеты остаются просто папками. Я проверял это на четырёх раскладках одного сервиса: как написано, три обхода из пяти не компилируются; после замены модификаторов на public компилируются все пять.

Поэтому в фиче я по умолчанию не пишу public и открываю только вход фичи.

  • Подпакеты не помогают: для javac payments.internal — отдельный пакет, и слово internal — только соглашение. Правилом его делает Spring Modulith или ArchUnit.
  • Причина обычно бытовая: шаблон нового класса в IDE начинается с public class. Инспекция IntelliJ «Declaration access can be weaker» находит лишние public.
  • Фреймворки это не ломает: в приложении на classpath рефлексия открывает package-private конструкторы, поэтому Spring, Jackson и Hibernate работают. С JPMS понадобился бы opens.
Найди проблему в этой границе 
// kb/shop/payments/persistence/PaymentRepository.java
package kb.shop.payments.persistence;

/** Внутренний тип платежей. Не использовать вне payments! */
public interface PaymentRepository { Payment find(String id); }

// kb/shop/refunds/RefundService.java
import kb.shop.payments.persistence.PaymentRepository;

Комментарий ничего не запрещает: тип public, потому что им пользуется PaymentService из родительского пакета, и javac пропускает импорт из refunds. Варианты: вернуть хранилище в пакет payments и сделать его package-private, если пакет ещё читается, или оставить подпакет и добавить тест ApplicationModules.of(Application.class).verify(). В демо Modulith находит ровно это нарушение: «depends on non-exposed type … within module 'payments'».

Как перевести живой проект с package by layer на package by feature?

Постепенно, по одной фиче. Сначала договариваемся о целевом дереве и сразу включаем правило в тестах, заморозив текущие нарушения через FreezingArchRule: старые записаны в хранилище, новые валят сборку. Потом переносим фичи по одной, отдельными коммитами без правок логики, и после каждой сужаем доступ до package-private.

Хранилище заморозки уменьшается само, когда нарушения исправляют. Когда оно пустое, старые пакеты по слоям удаляем.

  • Самое трудное — данные: JPA-связи между сущностями разных фич и общие таблицы. Связь заменяю хранением id и запросом через API соседней фичи.
  • Перенос файлов конфликтует со всеми открытыми ветками. Делаю его, когда веток мало, и отдельным коммитом, чтобы git распознал переименование, а blame не сломался.
  • В ArchUnit создание хранилища по умолчанию выключено: без закоммиченного хранилища тест падает, а не замораживает всё заново.
  • Модули сборки не делаю первым шагом. Сначала логические границы с тестом; модуль выношу, когда граница устоялась.
  • Роберт Мартин, «Чистая архитектура», глава 34 «The Missing Chapter» (Simon Brown) — основа урока: четыре раскладки, какие типы должны быть public в каждой, organization versus encapsulation, модули сборки и анти-паттерн Périphérique.
  • Роберт Мартин, «Чистая архитектура», глава 21 «Screaming Architecture» — дерево проекта должно говорить о предметной области, а не о фреймворке.
  • Spring Modulith Reference: Fundamentals — как пакеты становятся модулями, что считается API и внутренностями; раздел Verification — что проверяет verify().
  • ArchUnit User Guide: Freezing Arch Rules — хранилище нарушений, настройки allowStoreCreation и refreeze.
  • Gradle: The Java Library Plugin — api и implementation, что попадает на classpath потребителей. Правила доступа — JLS §6.6 и §7.1.
