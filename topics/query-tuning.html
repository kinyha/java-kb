Query Plans

План запроса — дерево операций, которое выбрал планировщик: как читать каждую таблицу и как соединять результаты. Выбор он делает по оценкам: сколько строк вернёт каждый узел и сколько это стоит. EXPLAIN ANALYZE выполняет запрос и показывает рядом оценку и факт, и почти любая плохая производительность начинается с расхождения между ними. Соединение выполняется вложенным циклом, хешем или слиянием, и каждый способ хорош при своих объёмах. Неверная статистика, коррелированные колонки и нехватка work_mem — частые причины плохих планов.

Отчёт по городу шёл секунды, хотя по одному магазину — миллисекунды

Запрос платежей одного магазина выполняется за доли миллисекунды. Тот же запрос по всем магазинам города — уже десятки миллисекунд на тестовой базе и секунды на проде. После загрузки справочника новых магазинов отчёт внезапно стал медленным, а через час сам «вылечился». Чтобы разбираться в таком, нужно уметь читать план и понимать, откуда планировщик берёт свои решения.

Тема разбирает EXPLAIN ANALYZE, алгоритмы соединения, статистику и память под операции. Индексы и способы доступа к таблице — в Indexes, поиск медленных запросов в проде — в Slow Queries. Демо QueryPlanDemo.java работает с PostgreSQL 17 в Docker: 10 тысяч магазинов и миллион платежей; в выводе стоимость показана только конечным числом.

EXPLAIN ANALYZE показывает дерево операций, оценку и факт

== join: one merchant's payments
   Nested Loop  (cost=...561.46 rows=100 width=16) (actual rows=100 loops=1)
     ->  Seq Scan on merchant m  (cost=...189.00 rows=1 width=4) (actual rows=1 loops=1)
           Filter: (name = 'shop-42'::text)
           Rows Removed by Filter: 9999
     ->  Bitmap Heap Scan on payment p  (cost=...371.46 rows=100 width=20) (actual rows=100 loops=1)
           Recheck Cond: (m.id = merchant_id)
   Execution Time: 0.317 ms

План читают от листьев к корню: вложенные узлы выполняются первыми и отдают строки родителю. Здесь Seq Scan по магазинам нашёл один нужный, отбросив 9999, а для него Bitmap Heap Scan по индексу merchant_id достал сто платежей. В каждом узле две пары чисел. cost — оценка стоимости в условных единицах (последняя цифра — полная стоимость узла), rows — сколько строк планировщик ожидает. В скобках actual — что было на самом деле, а loops — сколько раз узел выполнялся; итог узла — rows, умноженное на loops.

Главное, на что смотреть, — расхождение rows и actual rows. Ошибка в разы на нижнем узле множится вверх, и планировщик выбирает соединения и порядок для объёмов, которых нет. Здесь оценки точные: 1 и 1, 100 и 100. Добавляйте BUFFERS, чтобы видеть, сколько страниц прочитано, как в Indexes; время узлов на загруженном сервере полезнее с timing on, но оно само замедляет выполнение.

Для одного магазина планировщик выбрал вложенный цикл: одна внешняя строка — один поиск по индексу. Для двух тысяч магазинов города — хеш: прочитать миллион платежей подряд и сопоставить с хешем на 2000 магазинов дешевле, чем 2000 раз искать по индексу. Когда хеш запретили, вложенный цикл выполнил индексный поиск 2000 раз (loops=2000), и его оценка стоимости вышла вдвое выше.

Но по факту он оказался даже чуть быстрее: 35,8 мс против 41,4. Стоимость — модель, а не измерение. Она исходит из того, что случайное чтение страницы в четыре раза дороже последовательного (random_page_cost = 4) — это правда для HDD, а данные демо целиком в памяти. На SSD и при большом кеше random_page_cost снижают до 1,1–1,5, и планировщик чаще выбирает индексы. Переключатели enable_hashjoin и подобные годятся только для экспериментов, как здесь; в проде лечат причину — статистику, индексы, параметры стоимости.

Планировщик считает условия независимыми и ошибается на коррелированных колонках

Оценки строк берутся из статистики, которую собирает ANALYZE: для каждой колонки — частые значения, гистограмма, число различных. Для условия по двум колонкам планировщик по умолчанию перемножает их доли, как если бы колонки были независимы. Город и страна — не независимы: Алматы всегда в Казахстане.

== correlated columns: country = 'KZ' and city = 'Almaty'
   Aggregate  (cost=...215.01 rows=1 width=8) (actual rows=1 loops=1)
     ->  Seq Scan on merchant  (cost=...214.00 rows=400 width=0) (actual rows=2000 loops=1)
   Execution Time: 0.325 ms
== after CREATE STATISTICS (dependencies)
   Aggregate  (cost=...219.01 rows=1 width=8) (actual rows=1 loops=1)
     ->  Seq Scan on merchant  (cost=...214.00 rows=2000 width=0) (actual rows=2000 loops=1)
   Execution Time: 0.296 ms

20 % магазинов в KZ и 20 % в Алматы — планировщик перемножил и ожидал 4 %, 400 строк, а их 2000. В этом запросе ошибка ни на что не повлияла, но если бы от этого узла зависело соединение с миллионом платежей, в пять раз заниженная оценка могла бы выбрать вложенный цикл вместо хеша. CREATE STATISTICS ... (dependencies) собирает статистику зависимости между колонками, и после ANALYZE оценка стала точной.

Вторая частая причина — устаревшая статистика. После массовой загрузки таблица выросла, а статистика описывает старые данные, пока autovacuum не запустит ANALYZE — это и был отчёт, который «вылечился» через час. После массовых загрузок ANALYZE запускают явно. Для колонок с неравномерным распределением увеличивают число собираемых значений: alter table ... alter column ... set statistics 1000.

Сортировка и хеш, не уместившиеся в work_mem, уходят на диск

== sort 1M payments by amount, work_mem = 4MB
   Sort  (cost=...140020.84 rows=1000000 width=24) (actual rows=1000000 loops=1)
     Sort Key: amount, created_at
     Sort Method: external merge  Disk: 33296kB
   Execution Time: 185.774 ms
== sort 1M payments by amount, work_mem = 64MB
   Sort  (cost=...119510.84 rows=1000000 width=24) (actual rows=1000000 loops=1)
     Sort Key: amount, created_at
     Sort Method: quicksort  Memory: 63639kB
   Execution Time: 158.134 ms

С умолчанием work_mem = 4MB сортировка миллиона строк не поместилась в память и пошла внешним слиянием через временные файлы на 33 МБ. С 64 МБ сортировка прошла в памяти. Разница здесь небольшая, потому что временные файлы попали в кеш ОС; на настоящем диске и под нагрузкой она растёт в разы. Хеш-соединение с нехваткой памяти показывает Batches больше единицы. Временные файлы видны в log_temp_files и pg_stat_database.temp_bytes.

Поднимать work_mem глобально опасно: лимит действует на каждый узел сортировки или хеша в каждом запросе каждого соединения, и сотня соединений со сложными запросами может взять гигабайты. Его повышают точечно — SET LOCAL work_mem в транзакции отчёта — или для роли, под которой работают тяжёлые запросы. А лучше убрать саму сортировку: индекс, который отдаёт строки в нужном порядке, как в Indexes.

Чем меньше cost в плане, тем быстрее выполнится запрос.

Cost — оценка по модели с параметрами вроде random_page_cost и по статистике, которая может быть неточной. В демо вложенный цикл с вдвое большей стоимостью выполнился быстрее хеш-соединения. Сравнивают фактическое время и actual rows из EXPLAIN ANALYZE, а не cost.

  • План читают от листьев; rows — оценка, actual rows × loops — факт; расхождение — первая улика.
  • Nested Loop для малого внешнего набора с индексом, Hash Join для больших наборов, Merge Join для отсортированных.
  • Cost — модель: вложенный цикл с вдвое большей стоимостью оказался быстрее; на SSD снижают random_page_cost.
  • Коррелированные колонки: оценка 400 при факте 2000; CREATE STATISTICS исправил. После массовых загрузок — ANALYZE.
  • Нехватка work_mem — external merge на диске; повышают точечно или убирают сортировку индексом.

На собеседовании

Как читать EXPLAIN ANALYZE и что в нём искать?

План — дерево узлов, читается от вложенных к корню. В каждом узле оценка (cost, rows) и факт (actual rows, loops, время). Ищут узлы, где оценка строк сильно расходится с фактом, полные проходы больших таблиц с большим Rows Removed by Filter, вложенные циклы с огромным loops, сортировки и хеши на диске. С BUFFERS видно, сколько страниц прочитано.

  • Итог узла — actual rows × loops; время узла тоже на одну итерацию.
  • EXPLAIN без ANALYZE не выполняет запрос и показывает только оценки.
  • EXPLAIN ANALYZE на UPDATE и DELETE реально меняет данные — выполняют в транзакции с ROLLBACK.

Какие алгоритмы соединения есть и когда какой выбирается?

Nested Loop: для каждой строки одного набора ищет пары в другом — хорош, когда внешних строк мало и у внутренней таблицы есть индекс по ключу. Hash Join: строит хеш по меньшему набору и проходит больший — для больших объёмов без порядка. Merge Join: слияние двух отсортированных по ключу наборов. Выбор делает планировщик по оценкам числа строк.

  • Заниженная оценка внешнего набора ведёт к вложенному циклу с огромным loops.
  • Hash Join с Batches больше 1 не уместился в work_mem.
  • random_page_cost и effective_cache_size влияют на выбор между индексами и полным проходом.
Что подозрительно в этом плане? 
Nested Loop  (rows=12) (actual rows=480000 loops=1)
  ->  Index Scan using merchant_city_idx on merchant (rows=3) (actual rows=1200 loops=1)
  ->  Index Scan using payment_merchant_idx on payment (rows=4) (actual rows=400 loops=1200)
Execution Time: 9412 ms

Планировщик ждал 3 магазина, а получил 1200, и вложенный цикл выполнил 1200 индексных поисков вместо одного хеш-соединения. Нужно понять, почему оценка занижена в 400 раз: устаревшая статистика после загрузки справочника, коррелированные условия или неравномерное распределение. Лечат ANALYZE, CREATE STATISTICS или увеличением статистики колонки, а не переключателями enable_*.

Откуда планировщик берёт оценки и почему они ошибаются?

Из статистики, которую собирает ANALYZE: частые значения, гистограмма, число различных значений для каждой колонки. Ошибки бывают из-за устаревшей статистики после массовых изменений, из-за коррелированных колонок — планировщик считает условия независимыми, — и из-за неравномерных распределений, которые не попали в выборку.

  • CREATE STATISTICS для зависимостей и совместных распределений колонок.
  • ALTER COLUMN SET STATISTICS увеличивает выборку для сложных колонок.
  • Параметризованные запросы с generic plan могут планироваться без учёта конкретных значений.
