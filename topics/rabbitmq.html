RabbitMQ

RabbitMQ — брокер, который сам раздаёт сообщения консьюмерам и удаляет их после подтверждения. Exchange раскладывает сообщения по очередям, а очередь отправляет их подписчикам, не дожидаясь запроса. Сколько неподтверждённых сообщений держит один консьюмер, задаёт prefetch: без него медленный обработчик забирает половину очереди и держит её у себя. Для надёжности используют quorum-очереди — реплицированные по Raft, с лимитом доставок. Возврат сообщения в очередь ломает порядок, а nack с requeue крутит ядовитое сообщение бесконечно: лимит его не считает.

Очередь задач платёжного сервиса тормозит из-за одного воркера, а одно сообщение грузит процессор

Платёжный сервис ставит в RabbitMQ задачи на отправку чеков, сверку с банком и уведомления. Однажды на графике видно: в очереди тысяча задач, пять воркеров, четыре простаивают, а очередь не уменьшается. В другой день брокер грузит процессор на 100 %, хотя новых сообщений нет: одно сообщение с битым JSON доставляется тысячи раз в секунду. После деплоя события одного платежа обработались в обратном порядке, и сверка увидела возврат раньше списания.

Это не баги кода, а свойства брокера, которые нужно знать. Сообщение публикуется в exchange, тот по правилам binding копирует его в очереди, а очередь отправляет сообщения подписанным консьюмерам и ждёт подтверждения ack. Маршрутизация, publisher confirms, обработка ошибок в листенере и DLX со стороны Spring разобраны в RabbitMQ in Spring; здесь — поведение самого брокера. Демо BrokerDemo.java работает с настоящим RabbitMQ 4.3.6 в Docker через Java-клиент 5.37.

Без prefetch брокер раздаёт сообщения поровну, и медленный консьюмер держит свою половину

RabbitMQ отправляет сообщения консьюмерам сам, по кругу, сразу как они появились, — он не знает, кто сколько обрабатывает. Prefetch (basicQos) ограничивает число отправленных, но не подтверждённых сообщений на одного консьюмера. Демо подписывает быстрого (5 мс на задачу) и медленного (300 мс) воркеров на одну очередь и публикует 20 задач:

if (prefetch > 0) ch.basicQos(prefetch);
ch.basicConsume(q, false, consumer);   // autoAck=false: ack после обработки.
== prefetch unlimited: fast=10 slow=10, all done in ~3100 ms
== prefetch 1: fast=19 slow=1, all done in ~300 ms

Без ограничения брокер отдал каждому по 10 задач сразу. Быстрый закончил свои за 50 мс и простаивал, а медленный обрабатывал свою десятку 3 секунды. С prefetch 1 брокер даёт следующую задачу только после подтверждения предыдущей, и быстрый забрал 19 из 20. Маленький prefetch даёт справедливое распределение, но каждое сообщение ждёт круга по сети; большой повышает пропускную способность для быстрых однородных задач. Обычно выбирают 10–300; в Spring AMQP по умолчанию 250. Неподтверждённые сообщения брокер вернёт в очередь, только когда канал консьюмера закроется, а если консьюмер жив, но завис, — после consumer_timeout, по умолчанию 30 минут.

Quorum-очередь реплицирована по Raft, а stream хранит журнал для повторного чтения

Classic-очередь живёт на одном узле: если он упал, очередь недоступна, а если пропал диск — сообщения потеряны. Зеркалирование classic-очередей удалено в RabbitMQ 4.0. Quorum-очередь хранит копии на нескольких узлах и подтверждает публикацию, когда запись приняло большинство, как в Consensus & Time. Кластер из трёх узлов переживает потерю одного. Цена — больше дисковых операций и памяти, поэтому quorum-очереди не используют для временных очередей ответов.

Stream — журнал в духе Kafka внутри RabbitMQ: сообщения не удаляются после чтения, и каждый читатель хранит своё смещение. Это закрывает частую причину выбирать Kafka — повторное чтение событий, — но с меньшей пропускной способностью и экосистемой.

Nack с возвратом в очередь крутит ядовитое сообщение бесконечно: лимит доставок его не считает

Сообщение с битым JSON падает при каждой обработке. Типичный код ловит исключение и делает basicNack(tag, false, true) — вернуть в очередь, может, в следующий раз получится. Так же по умолчанию поступает Spring AMQP. У quorum-очереди есть лимит доставок, и кажется, что он остановит цикл:

// Очередь: quorum, DLX настроен, delivery-limit по умолчанию.
getChannel().basicNack(env.getDeliveryTag(), false, true);   // requeue=true

// Второй вариант: консьюмер падает, не подтвердив.
var got = c.basicGet("payments", false);
c.close();                                                    // Без ack.
== poison + nack(requeue): 1678 deliveries in 1 s, x-delivery-count [null, null, null]
== poison + consumer crash: 20 deliveries, then DLQ reason=delivery_limit

За секунду одно сообщение доставлено 1678 раз, и счётчик доставок не появился вовсе. В RabbitMQ 4 явный возврат через nack или reject с requeue=true не считается неудачной доставкой, и лимит его не останавливает: брокер и консьюмер крутят сообщение, пока кто-то не вмешается. А когда консьюмер падает, не подтвердив сообщение, — процесс умер, канал закрылся, — счётчик растёт, и после 20 таких доставок сообщение уходит в dead letter exchange с причиной delivery_limit.

Отсюда правило. Ошибку, которая не исправится повтором — битые данные, нарушение бизнес-правила, — отклоняют с requeue=false, и сообщение сразу уходит в DLX. Временную ошибку — недоступен банк — повторяют с паузой: в приложении или через очередь задержки с TTL, а после N попыток отправляют в DLX. Лимит доставок quorum-очереди — страховка от консьюмеров, которые падают на сообщении целиком, а не замена обработке ошибок. В Spring для этого есть AmqpRejectAndDontRequeueException и defaultRequeueRejected=false.

Порядок держится только в одной очереди с одним консьюмером и без возвратов

Очередь — FIFO, но порядок обработки ломается тремя способами. Возврат в очередь: первое событие платежа упало, вернулось, а следующие уже обработаны:

== requeue order, classic queue: [p-1:CAPTURED, p-1:REFUNDED, p-1:AUTHORIZED]
== requeue order, quorum queue: [p-1:CAPTURED, p-1:REFUNDED, p-1:AUTHORIZED]

Второй способ — несколько консьюмеров: события одного платежа уходят разным воркерам и обрабатываются параллельно. Третий — prefetch больше единицы и параллельная обработка внутри одного консьюмера. Если порядок важен, есть три приёма. Single active consumer: на очередь подписаны несколько консьюмеров, но сообщения получает только один, а остальные ждут его ухода:

== single active consumer: [A:e1, A:e2, A:e3, B:e4, B:e5, B:e6]

Консьюмер A получил первые три события, затем ушёл, и B продолжил с четвёртого — без параллелизма, но с запасным консьюмером. Чтобы масштабироваться, события разбивают по ключу на несколько очередей, каждая со своим single active consumer, — consistent hash exchange делает это по хешу ключа, как партиции в Kafka. И третий приём, самый надёжный: обработчик сам защищён от неправильного порядка — хранит версию или статус и игнорирует устаревшие события, как идемпотентный консьюмер из Brokers & Guarantees.

Длинная очередь — авария, а не буфер: брокер начинает тормозить издателей

RabbitMQ рассчитан на то, что очереди почти пустые: сообщения приходят и быстро уходят. Миллионы сообщений в очереди — это память, диск и медленные операции. Когда память узла превышает порог (vm_memory_high_watermark, по умолчанию 60 % ОЗУ) или свободного диска меньше порога, срабатывает alarm, и брокер блокирует все публикующие соединения кластера. Сервис платежей, который публикует события, начинает зависать на basicPublish из-за отставших консьюмеров совсем другой очереди.

Поэтому длину очередей и возраст самого старого сообщения мониторят и алертят, а для очередей, которые могут расти, задают лимиты: x-max-length с политикой переполнения reject-publish, чтобы издатель получил отказ сразу, а не блокировку всего узла. Публикацию подтверждают publisher confirms, а соединения и каналы переиспользуют: открывать соединение на каждое сообщение — частая причина перегрузки брокера.

В quorum-очереди ядовитое сообщение само уйдёт в DLQ после лимита доставок.

Лимит считает только доставки, после которых консьюмер не ответил: падение процесса, закрытие канала. Явный nack или reject с requeue=true в RabbitMQ 4 счётчик не увеличивает, и в демо сообщение прошло 1678 доставок за секунду. Ошибки, которые не исправятся повтором, отклоняют с requeue=false.

  • Брокер сам раздаёт сообщения; prefetch ограничивает неподтверждённые. Без него: 10/10 и 3,1 с, с prefetch 1: 19/1 и 0,3 с.
  • Quorum-очереди реплицированы по Raft и выбираются по умолчанию для надёжных задач; stream — журнал с повторным чтением.
  • Nack с requeue не считается в лимит доставок: ядовитое сообщение крутится бесконечно. Неисправимое — requeue=false в DLX.
  • Возврат, несколько консьюмеров и параллельный prefetch ломают порядок; single active consumer, разбиение по ключу, версии в обработчике.
  • Длинные очереди включают memory и disk alarm и блокируют издателей; лимиты длины и мониторинг возраста сообщений.

На собеседовании

Что такое prefetch и как его выбрать?

Prefetch — максимум отправленных, но не подтверждённых сообщений на консьюмера. RabbitMQ сам раздаёт сообщения по кругу; без ограничения он отдаст медленному консьюмеру столько же, сколько быстрому, и тот будет держать их у себя. Маленький prefetch даёт справедливое распределение, большой — пропускную способность для быстрых однородных задач.

  • При autoAck prefetch не работает: сообщение считается подтверждённым при отправке и теряется при падении.
  • Неподтверждённые возвращаются при закрытии канала или по consumer_timeout, 30 минут по умолчанию.
  • Prefetch больше единицы с параллельной обработкой ломает порядок.

Что делать с сообщением, которое всегда падает при обработке?

Не возвращать его в очередь бесконечно: отклонить с requeue=false, чтобы оно ушло в dead letter exchange, и разбирать DLQ отдельно. Временные ошибки повторять с паузой ограниченное число раз — в приложении или через очередь задержки с TTL — и после этого тоже отправлять в DLX.

  • У quorum-очередей лимит доставок по умолчанию 20, но nack и reject с requeue=true его не увеличивают; он срабатывает на падениях консьюмера.
  • Spring AMQP по умолчанию возвращает сообщение при исключении; нужны AmqpRejectAndDontRequeueException или defaultRequeueRejected=false.
Что случится с этим консьюмером на битом сообщении? 
ch.basicConsume("payments", false, (tag, d) -> {
    try {
        handle(json.readValue(d.getBody(), PaymentEvent.class));
        ch.basicAck(d.getEnvelope().getDeliveryTag(), false);
    } catch (Exception e) {
        log.warn("retry later", e);
        ch.basicNack(d.getEnvelope().getDeliveryTag(), false, true);
    }
}, tag -> {});

Ошибка разбора JSON не исправится повтором, а nack с requeue вернёт сообщение в очередь, и оно придёт снова через миллисекунды: процессор и логи загружены, лимит доставок quorum-очереди такой возврат не считает. Нужно отделять неисправимые ошибки и отклонять их с requeue=false в DLX, а временные повторять с паузой и счётчиком попыток.

Чем RabbitMQ отличается от Kafka?

RabbitMQ — брокер очередей: гибкая маршрутизация через exchange, сообщения раздаются консьюмерам и удаляются после ack, есть приоритеты, TTL, DLX. Хорош для задач и команд. Kafka — распределённый журнал: сообщения хранятся по сроку, консьюмеры читают по смещению и могут перечитать, порядок гарантирован в партиции. Хорош для потоков событий, многих независимых читателей и высокой пропускной способности.

  • В RabbitMQ брокер отвечает за раздачу и подтверждения каждого сообщения; в Kafka консьюмер хранит смещение.
  • Streams в RabbitMQ дают журнал с повторным чтением, quorum-очереди — репликацию по Raft.
  • Порядок в RabbitMQ ломают возвраты и несколько консьюмеров; решение — single active consumer и разбиение по ключу.
