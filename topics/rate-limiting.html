Rate Limiting

Ограничение частоты защищает общий ресурс от одного клиента: каждый ключ (API-ключ, пользователь, IP) получает не больше N запросов за период, лишние — 429 с Retry-After. Алгоритмы различаются поведением на всплесках и ценой. Фиксированное окно дешёвое, но на границе окон пропускает вдвое больше лимита. Скользящий журнал точен, но хранит каждый запрос. Скользящий счётчик приближает журнал двумя числами. Token bucket разрешает управляемый всплеск при ограниченной средней скорости. В распределённом сервисе состояние держат в Redis, а проверку и изменение делают одним Lua-скриптом: GET и SET отдельными командами пропускают все запросы гонки.

Один партнёр забрал всю ёмкость API

Платёжный API обслуживает сотни магазинов. Один из них запустил сверку и опрашивает статусы платежей в цикле без паузы — 3 000 запросов в секунду. База отвечает медленнее, пулы соединений заняты, и остальные магазины получают таймауты при создании платежей. Ни один сервис не упал, но один клиент сделал API недоступным для всех. Нужен лимит на клиента: магазин получает, скажем, 100 запросов в секунду, а сверх лимита — быстрый отказ, который ничего не стоит серверу.

Тема разбирает алгоритмы и их поведение на одном и том же трафике, распределённую реализацию на Redis, место лимитера в архитектуре и ответ клиенту. Демо RateLimitDemo.java запускает четыре алгоритма Lua-скриптами в Redis 8. Защита сервиса от общей перегрузки, а не от отдельного клиента, — в Overload, повторы на стороне клиента — в Resilience Patterns.

Фиксированное окно пропускает двойной лимит на границе

Самый простой лимитер — счётчик на номер окна: ключ fw:anna:0 для первой секунды, fw:anna:1 для второй, INCR и срок жизни в одно окно. Демо подаёт одинаковый трафик всем алгоритмам: 10 запросов в момент 900 мс и ещё 10 — в 1100 мс, при лимите 10 в секунду. Время передаётся в скрипты явно, чтобы сценарий на границе был воспроизводимым; в сервисе это текущее время.

== 10 requests at t=900 ms, 10 more at t=1100 ms; limit 10 per second
   fixed window     allowed 10 + 10 = 20 within 200 ms
   sliding log      allowed 10 +  0 = 10 within 200 ms
   sliding counter  allowed 10 +  1 = 11 within 200 ms
   token bucket     allowed 10 +  2 = 12 within 200 ms

Двойной лимит на границе — не теоретическая проблема: клиенты с расписанием (cron, ретраи по таймеру) часто стреляют ровно в начале секунды или минуты. Если лимит защищает базу, выдерживающую 10 запросов в секунду, фиксированное окно в худший момент пропускает 20. Для лимитов «на час» или «на сутки» это обычно приемлемо, для коротких окон, защищающих ресурс, — нет.

Четыре алгоритма: точность, всплески и память

-- Token bucket: остаток жетонов и время последнего пополнения в одном хеше.
local now, capacity, perMs = tonumber(ARGV[1]), tonumber(ARGV[2]), tonumber(ARGV[3])
local b = redis.call('HMGET', KEYS[1], 'tokens', 'ts')
local tokens, ts = tonumber(b[1]) or capacity, tonumber(b[2]) or now
tokens = math.min(capacity, tokens + (now - ts) * perMs)   -- пополнение за прошедшее время
local ok = 0
if tokens >= 1 then tokens = tokens - 1; ok = 1 end
redis.call('HSET', KEYS[1], 'tokens', tokens, 'ts', now)
redis.call('PEXPIRE', KEYS[1], math.ceil(capacity / perMs))  -- полное ведро можно забыть
return ok

Token bucket не пополняет ведро таймером: при каждом запросе он досчитывает жетоны за прошедшее время. Состояние — два числа, а у двух параметров ясный смысл: capacity — допустимый всплеск, скорость пополнения — средний предел. Скользящий журнал хранит в ZSET время каждого запроса, удаляет устаревшие и считает оставшиеся. Скользящий счётчик хранит только счётчики текущего и предыдущего окна и взвешивает предыдущее по доле перекрытия — это приближение, которое считает запросы прошлого окна равномерно распределёнными. Цена журнала видна на лимите 10 000 запросов в минуту:

== memory for one client, limit 10000 per minute, full window
   sliding log:     815826 bytes
   sliding counter: 35 bytes
   token bucket:    75 bytes

Leaky bucket — зеркало token bucket: запросы встают в очередь и уходят с постоянной скоростью. Так работает limit_req в nginx: без burst лишние запросы сразу получают отказ, с burst встают в очередь и задерживаются, а с nodelay пропускаются сразу, но занимают место в очереди. Leaky bucket сглаживает поток к защищаемому ресурсу ценой задержки; token bucket не задерживает, а отказывает.

Распределённый лимит: проверка и изменение — одна операция

Сервис работает в десяти экземплярах за балансировщиком. Лимит в памяти каждого экземпляра — 100 в секунду на клиента — превращается в 1 000 при равномерной балансировке и в непредсказуемую величину при неравномерной. Поэтому общий лимит держат в Redis. Частая ошибка — прочитать счётчик, сравнить с лимитом в коде и записать новое значение отдельной командой. Демо отправляет 200 одновременных запросов при лимите 100:

// Неверно: между GET и SET другие потоки читают то же старое значение.
long n = Long.parseLong(redis.get("race:naive") == null ? "0" : redis.get("race:naive"));
if (n >= 100) return false;
redis.set("race:naive", String.valueOf(n + 1));
return true;

// Верно: INCR и сравнение внутри одного Lua-скрипта, Redis выполняет его атомарно.
return eval(FIXED, "race:lua", 60_000, 100);
== 200 concurrent requests, limit 100
   GET then SET:   allowed 200
   Lua INCR:       allowed 100, counter 200

Наивный вариант пропустил все 200: каждый поток прочитал маленькое значение, а итоговый счётчик между запусками оказывался от 11 до 37 — записи затирали друг друга. Lua-скрипт выполняется в Redis целиком, без вклинивания других команд, поэтому пропущено ровно 100. Счётчик 200 показывает, что скрипт считает и отклонённые попытки; если это нежелательно, сначала сравнивают, а потом увеличивают, — внутри скрипта это так же атомарно.

Остальные вопросы распределённого лимита — это компромиссы. Каждый запрос получает поход в Redis, около миллисекунды; для очень горячих путей держат локальный лимит и синхронизируют его с общим пачками, жертвуя точностью. Если Redis недоступен, выбирают: пропускать всех (fail open — API работает без защиты) или отказывать всем (fail closed — API недоступен из-за лимитера); для защиты от злоупотреблений обычно выбирают первое с локальным запасным лимитом. Время берут из одного источника — команды TIME в Redis или часов сервиса с синхронизацией, — иначе расхождение часов экземпляров сдвигает окна. В Redis Cluster все ключи одного клиента должны попасть в один слот: {anna}:prev и {anna}:cur с hash tag.

Где ставить лимитер и что отвечать клиенту

Лимиты стоят на нескольких уровнях. На входе — шлюз или nginx: грубые лимиты по IP против ботов и всплесков, до того как запрос дошёл до приложения, — в API Gateway. В приложении — лимиты по смыслу: по API-ключу магазина, по пользователю, по дорогой операции («не больше 5 попыток входа в минуту», как в Authentication). Ключ выбирают по тому, кто потребляет ресурс: лимит по IP наказывает всех клиентов за NAT одного офиса, а лимит по API-ключу — только виновного.

HTTP/1.1 429 Too Many Requests
Retry-After: 1
RateLimit-Policy: "default";q=100;w=1
RateLimit: "default";r=0;t=1

Ответ на превышение — 429 Too Many Requests (RFC 6585) с Retry-After: через сколько секунд повторить. Заголовки RateLimit и RateLimit-Policy из черновика IETF сообщают остаток и сброс заранее, чтобы клиент замедлялся до отказа. Клиент, получив 429, повторяет с экспоненциальной задержкой и jitter, а не сразу, иначе отказ превращается в шторм повторов. Отказ дешёв для сервера только если лимитер стоит до тяжёлой работы: проверять лимит после запроса в базу бессмысленно.

В Java-сервисе лимитер можно не писать самому: Bucket4j реализует token bucket с хранением в Redis, Hazelcast или JDBC. RateLimiter из Resilience4j — локальный, на один экземпляр: он делит время на циклы limitRefreshPeriod и выдаёт limitForPeriod разрешений в цикле, то есть это фиксированное окно в памяти процесса. Он подходит для ограничения собственных вызовов внешнего API, а не для общего лимита клиентов кластера.

Лимит 10 запросов в секунду на фиксированном окне гарантирует, что ресурс не получит больше 10 запросов за любую секунду.

Окно считает запросы по номеру секунды, а не за любую секунду. Десять запросов в 900 мс и десять в 1100 мс попали в разные окна: фиксированное окно пропустило 20 за 200 мс. Точную гарантию «за любую секунду» даёт скользящий журнал, приближённую — скользящий счётчик.

  • Лимит на клиента защищает общий ресурс от одного потребителя; сверх лимита — дешёвый отказ 429 с Retry-After.
  • На границе окон фиксированное окно пропустило 20 при лимите 10; журнал — 10, скользящий счётчик — 11, token bucket — 12.
  • Журнал точен, но занимает около 800 КБ на 10 000 запросов; счётчик и token bucket — десятки байт.
  • Token bucket: capacity — допустимый всплеск, скорость пополнения — средний предел.
  • Распределённый лимит — в Redis одним Lua-скриптом: GET и SET отдельно пропустили 200 из 200 при лимите 100.
  • Решить заранее: fail open или closed при недоступном Redis, единые часы, hash tag в Redis Cluster.

На собеседовании

Какие алгоритмы rate limiting вы знаете и чем они отличаются?

Фиксированное окно — счётчик на интервал: просто, но на границе окон пропускает до двойного лимита. Скользящий журнал хранит время каждого запроса — точен, но дорог по памяти. Скользящий счётчик взвешивает предыдущее окно по доле перекрытия — два счётчика и приближённая точность. Token bucket пополняет жетоны с постоянной скоростью и разрешает всплеск до ёмкости. Leaky bucket выпускает запросы с постоянной скоростью из очереди.

  • Token bucket досчитывает жетоны при запросе, без таймеров: состояние — остаток и время.
  • Leaky bucket сглаживает ценой задержки, token bucket отказывает без задержки.
  • Скользящий счётчик предполагает равномерность запросов в прошлом окне.
Лимит защищает базу, выдерживающую 50 запросов в секунду. Что не так? 
long window = System.currentTimeMillis() / 1000;
long n = redis.incr("rl:" + client + ":" + window);
redis.expire("rl:" + client + ":" + window, 1);
if (n > 50) throw new TooManyRequests();

Фиксированное окно на границе секунд пропустит до 100 запросов за доли секунды — вдвое больше, чем выдерживает база; нужен скользящий счётчик или token bucket с ёмкостью, которую база переживёт. Лимит на клиента вообще не защищает базу от суммы всех клиентов — для этого нужен общий лимит или ограничение конкурентности перед базой. И INCR с EXPIRE отдельными командами: при сбое между ними ключ останется без срока жизни; их объединяют в скрипт или транзакцию.

Как сделать rate limiter для сервиса из нескольких экземпляров?

Держать состояние в общем хранилище, обычно Redis, и выполнять проверку с изменением атомарно — Lua-скриптом. Локальные лимиты в каждом экземпляре умножаются на число экземпляров и зависят от балансировки. Ответ сверх лимита — 429 с Retry-After.

  • Отдельные GET и SET пропускают все запросы гонки.
  • Fail open или fail closed при недоступном Redis — осознанный выбор.
  • Для горячих путей — локальный лимит с периодической синхронизацией, ценой точности.
  • Redis Cluster: ключи клиента в одном слоте через hash tag.

По какому ключу ограничивать и где ставить лимитер?

По тому, кто потребляет ресурс: API-ключ или пользователь для аутентифицированных запросов, IP — только для анонимных и грубой защиты. Грубые лимиты — на шлюзе или nginx, до приложения; смысловые — в приложении, до тяжёлой работы. Для дорогих операций — отдельные лимиты.

  • Лимит по IP наказывает всех за NAT.
  • Заголовки RateLimit позволяют клиенту замедлиться до отказа.
  • Клиент повторяет после 429 с backoff и jitter.
