Reactive Pitfalls

Платёжный сервис на WebFlux прошёл все тесты, а в проде под нагрузкой health-check отвечает через секунды, часть платежей не сохраняется, в логах нет traceId, а банк жалуется на шквал запросов. У этих багов общая черта: ни один не бросает понятное исключение в месте, где ошибся разработчик. Блокировка тормозит чужие запросы, неподписанный Mono молча ничего не делает, отдельная подписка теряет ошибку и контекст, flatMap без лимита запускает сотни вызовов. Ниже каждый баг воспроизведён и показано, каким инструментом его находят: BlockHound, PublisherProbe, checkpoint и Reactor Debug Agent.

Блокировку в event loop тесты не замечают, а BlockHound находит

Почему блокирующий вызов в потоке event loop останавливает все соединения этого потока, показано в теме WebFlux: с Thread.sleep в обработчике шесть запросов прошли тремя волнами. Здесь — почему такие вызовы доходят до прода. В тестах цепочку обычно подписывают из потока JUnit, данные приходят из моков мгновенно, и ничего не блокирует event loop, потому что его в тесте просто нет.

Первая защита встроена в сам Reactor: block() в потоке, помеченном как неблокирующий (event loop Netty, Schedulers.parallel()), бросает исключение. Но только если ждать действительно придётся. PitfallsDemo.java, часть block; поток event-loop-1 создан через Schedulers.newParallel и помечен так же, как поток Netty:

cd examples/reactive
./run.sh PitfallsDemo block
Mono.delay(Duration.ofMillis(10), LOOP)            // дальше цепочка идёт в потоке event-loop-1
        .map(x -> Mono.just("paid").block())        // значение уже готово: ждать не нужно
        .subscribe(...);
Mono.delay(Duration.ofMillis(10), LOOP)
        .map(x -> bankSlow().block())               // bankSlow() отвечает через 100 мс
        .subscribe(...);
block: block() inside a non-blocking thread
  ready Mono: block() returned paid
  slow Mono: java.lang.IllegalStateException: block()/blockFirst()/blockLast() are blocking, which is not supported in thread event-loop-1

Проверка срабатывает, когда block() собирается ждать. Мок банка в тесте возвращает Mono.just, значение готово, и ошибки нет. В проде настоящий WebClient отвечает через 100 мс, и тот же код падает. А JDBC, RestClient, синхронный SDK или Thread.sleep не проверяет никто: они просто блокируют поток.

BlockHound закрывает эту дыру. Это Java-агент от команды Reactor: он инструментирует блокирующие методы JDK (Thread.sleep, чтение сокета и файла, Object.wait, парковку потоков) и бросает ошибку, если их вызвали из неблокирующего потока. Подключают его в тестах вызовом BlockHound.install(). Часть blockhound: вместо JDBC — метод, который ждёт 20 мс, три способа его вызвать.

JAVA_OPTS=-XX:+AllowRedefinitionToAddDeleteMethods ./run.sh PitfallsDemo blockhound  # флаг нужен на JDK 13+
BlockHound.install();
Mono.delay(Duration.ofMillis(10), LOOP)
        .map(x -> jdbcFindAccount());                // блокирует event loop

Mono.delay(Duration.ofMillis(10), LOOP)
        .flatMap(x -> Mono.just(jdbcFindAccount())   // аргумент считается здесь, на event loop
                .subscribeOn(Schedulers.boundedElastic()));

Mono.delay(Duration.ofMillis(10), LOOP)
        .flatMap(x -> Mono.fromCallable(PitfallsDemo::jdbcFindAccount) // вызов внутри подписки
                .subscribeOn(Schedulers.boundedElastic()));
blockhound: blocking calls on non-blocking threads
  map(x -> jdbc()) -> reactor.blockhound.BlockingOperationError: Blocking call! java.lang.Thread.sleep0
  flatMap(x -> Mono.just(jdbc()).subscribeOn(boundedElastic)) -> reactor.blockhound.BlockingOperationError: Blocking call! java.lang.Thread.sleep0
  flatMap(x -> Mono.fromCallable(jdbc).subscribeOn(boundedElastic)) -> ACC-1 on boundedElastic-1

Второй вариант — самый коварный: на ревью видно subscribeOn(boundedElastic()), и кажется, что всё вынесено. Но Mono.just принимает готовое значение, и JDBC выполняется в event loop при сборке внутреннего Mono. Правильно — fromCallable: тогда вызов произойдёт при подписке, а подписка уже переехала в boundedElastic. Сообщение BlockHound называет метод JDK, а стектрейс под ним ведёт к твоему коду: здесь PitfallsDemo.jdbcFindAccount.

BlockHound ставят в тесты, а не в прод: инструментирование стоит времени, а исключение в проде ломает запрос. BlockHound смотрит на сам факт блокирующего метода, а не на то, сколько он ждал: интеграционный тест с быстрой базой в Testcontainers поймает JDBC в event loop. Мок, который вообще не вызывает блокирующих методов JDK, он не поймает, поэтому такие тесты гоняют на настоящих драйверах. Разрешённые места, например логирование с блокировкой внутри аппендера, добавляют через BlockHound.builder().allowBlockingCallsInside(класс, метод).

Mono, на который никто не подписался, ничего не делает и не падает

Реактивный репозиторий возвращает Mono<Void>: сохранение произойдёт при подписке. Если результат вызова не встроен в цепочку, подписки не будет, а значит, и сохранения. Явная форма этой ошибки — repository.save(p); отдельной строкой — разобрана в теме WebFlux. В реальном коде она чаще прячется. Часть forgotten:

Mono.just("p1").doOnNext(p -> save(p)).block();                          // Mono из save выброшен
Mono.just("p1").flatMap(p -> { save(p); return notifyClient(p); }).block(); // тоже выброшен
Mono.just("p1").flatMap(p -> save(p).then(notifyClient(p))).block();      // встроен в цепочку
forgotten: Mono that nobody subscribed to
  doOnNext(p -> save(p)):            saved = 0
  flatMap { save(p); return notify }: saved = 0
  flatMap(p -> save(p).then(notify)): saved = 1

doOnNext предназначен для побочных эффектов вроде логирования: он вызывает лямбду и выбрасывает её результат. Мысль «сохранить — это побочный эффект» приводит к самому частому варианту бага. Во втором случае save стоит отдельной строкой внутри лямбды flatMap: возвращается только Mono уведомления. В обоих случаях клиент получает 200, а в базе ничего. Исправление одно: каждый Mono должен стать частью возвращаемой цепочки — через flatMap, then, Mono.when или zip.

Найти такое место по логам нельзя: ошибки нет. Его ловят тестом, который проверяет эффект, а не ответ. Когда реальной базы в тесте нет, подходит PublisherProbe из reactor-test: мок репозитория возвращает probe.mono(), и тест проверяет, была ли на него подписка.

PublisherProbe<Void> probe = PublisherProbe.empty();  // мок save вернёт probe.mono()
Mono.just("p1").doOnNext(p -> probe.mono()).block();
probe.assertWasSubscribed();
  test with PublisherProbe: PublisherProbe should have been subscribed but it wasn't

Если метод вызван, а исключения нет, значит, он отработал.

Метод, который возвращает Mono, только собирает описание работы. Без подписки работа не начнётся, и ни Reactor, ни BlockHound об этом не сообщат. Признак в коде — вызов, чей Mono или Flux не используется дальше: не возвращается, не передаётся в flatMap или then.

subscribe() внутри flatMap отрывает работу от запроса: ошибка, контекст и отмена до неё не доходят

Обратная крайность: разработчик знает, что без подписки ничего не произойдёт, и подписывается сам. Платёжный сервис пишет аудит, и чтобы «не задерживать ответ», аудит запускают отдельно: audit(p).subscribe() внутри flatMap. Часть nested на виртуальном времени: банк отвечает за 50 мс, аудит пишет 200 мс и в первом сценарии падает; запрос несёт в Context пользователя alice, как это делает Spring Security.

Mono.just("p1")
        .flatMap(p -> {
            audit(p, 200, true).subscribe();         // отдельная подписка, без обработчика ошибок
            return bank(p);
        })
        .contextWrite(Context.of("user", "alice"))   // контекст запроса
        .subscribe(v -> vlog("response: " + v), e -> vlog("response error: " + e.getMessage()));

Mono.just("p1")
        .flatMap(p -> audit(p, 200, true).then(bank(p))) // аудит в цепочке запроса
        .contextWrite(Context.of("user", "alice"))
        .subscribe(...);
nested: subscribe() inside flatMap
 fire-and-forget, audit fails after 200 ms:
  t=50   response: p1 paid
[main           ] traceId=none  Operators ERROR Operator called default onErrorDropped
reactor.core.Exceptions$ErrorCallbackNotImplemented: java.lang.IllegalStateException: audit DB down
 fire-and-forget, audit ok, user from context:
  t=50   response: p1 paid
  t=200  audit saved p1 for user anonymous
 fire-and-forget, client disconnects at 20 ms:
  t=20   bank call cancelled
  t=20   client gone
  t=200  audit saved p1 for user anonymous
 in the chain: audit(p).then(bank(p)):
  t=200  response error: audit DB down
 in the chain: audit ok:
  t=200  audit saved p1 for user alice
  t=250  response: p1 paid

Строка с ошибкой аудита напечатана в 200 мс виртуального времени из лога Reactor; стектрейс под ней обрезан. Четыре последствия одной отдельной подписки:

  • Ошибка теряется. Клиент получил «paid» в 50 мс, а падение аудита ушло в лог ERROR без связи с запросом. У subscribe() без обработчика ошибок Reactor отдаёт ошибку в onErrorDropped, и её видно только в логах.
  • Контекст теряется. Аудит записан от имени anonymous: Context пишет contextWrite снизу, а у отдельной подписки своя цепочка без него. Так же пропадают SecurityContext, traceId и реактивная транзакция.
  • Отмена не доходит. Клиент ушёл в 20 мс, вызов банка отменён, а аудит продолжил жить и записал платёж, которого клиент не дождался.
  • Нет backpressure и предела. Под нагрузкой каждый запрос порождает фоновую задачу, и их число никто не ограничивает.

Правило: в прикладном коде subscribe() не вызывают, его вызывает фреймворк на то, что вернул обработчик. Работу встраивают в цепочку: последовательно через then, параллельно через Mono.when(audit(p), notify(p)).then(bank(p)). Если аудит и правда не должен задерживать ответ и может упасть, это требование надёжной фоновой доставки: событие кладут в outbox в той же транзакции или в Kafka, и его обработают с повторами. Отдельная подписка не даёт ни повторов, ни гарантии, что работа переживёт рестарт сервиса.

Context едет снизу вверх: операторы ниже contextWrite и чужие подписки его не видят

Reactor Context заменяет ThreadLocal в реактивном коде (основы — в теме WebFlux). Его пишет contextWrite, а читает deferContextual или код фреймворка, например ReactiveSecurityContextHolder.getContext(). Ошибки начинаются, когда забывают, куда он течёт. Context привязан к подписке, а подписка идёт от подписчика к источнику, снизу вверх по коду. Значит, contextWrite видят только операторы, стоящие выше него. Часть context, currentUser() читает пользователя так же, как ReactiveSecurityContextHolder:

static Mono<String> currentUser() {
    return Mono.deferContextual(ctx -> Mono.just(ctx.getOrDefault("user", "anonymous")));
}

currentUser()
        .contextWrite(Context.of("user", "alice"))   // ниже чтения: видно
        .block();
Mono.just("p1")
        .contextWrite(Context.of("user", "alice"))   // выше чтения: не видно
        .flatMap(p -> currentUser())
        .block();
context: Context flows from subscriber up to source
  contextWrite below the read: alice
  contextWrite above the read: anonymous

Поэтому в WebFlux контекст кладут как можно ниже: в WebFilter, вокруг всей цепочки обработчика, — так делает Spring Security. А читать его можно где угодно выше. Ошибку из второго ряда обычно делают в сервисе: кладут Context в середине цепочки, а читают в коде, который подставили ниже через flatMap. Отдельная подписка из прошлого шага — крайний случай того же правила: у неё вообще нет ни одного contextWrite.

MDC и traceId в логах

Логгеры читают MDC, а это ThreadLocal. Фильтр положил traceId в MDC потока, который принял запрос, но следующий оператор выполнился в другом потоке, и в логе пусто. Reactor умеет копировать значения из Context в ThreadLocal на каждом переходе через библиотеку Micrometer Context Propagation: нужно зарегистрировать, какое значение какому ThreadLocal соответствует, и включить хук.

ContextRegistry.getInstance().registerThreadLocalAccessor("traceId",   // ключ в Context
        () -> MDC.get("traceId"), v -> MDC.put("traceId", v), () -> MDC.remove("traceId"));
Hooks.enableAutomaticContextPropagation();          // в Boot: spring.reactor.context-propagation=auto

Mono.just("p1")
        .publishOn(LOOP)
        .doOnNext(p -> log.info("charging " + p))   // значение из Context вернулось в MDC
        .contextWrite(Context.of("traceId", "t-42"))
        .block();
 MDC without propagation:
[main           ] traceId=t-42  payments INFO request accepted
[event-loop-1   ] traceId=none  payments INFO charging p1
 MDC with Hooks.enableAutomaticContextPropagation():
[event-loop-1   ] traceId=t-42  payments INFO charging p1

Без хука строка из event-loop-1 потеряла traceId, хотя это тот же запрос. С хуком Reactor перед каждым оператором восстанавливает MDC из Context подписки и очищает после. В Spring Boot 4 этим управляет spring.reactor.context-propagation: по умолчанию limited, значение auto включает тот же хук; Micrometer Tracing регистрирует свои ключи сам. Цена — работа на каждом операторе, поэтому включают осознанно.

С безопасностью и транзакциями механизм тот же. ReactiveSecurityContextHolder хранит SecurityContext в Reactor Context, и код в отдельной подписке видит анонимного пользователя. Реактивная транзакция (@Transactional над методом, который возвращает Mono, или TransactionalOperator) привязана к Context подписки: запись через R2DBC в отдельной подписке пройдёт вне транзакции и не откатится вместе с ней.

flatMap без лимита превращает пачку платежей в шквал запросов к соседу

Ночной job проводит 1000 платежей через банк: Flux.fromIterable(ids).flatMap(bank::charge). flatMap по умолчанию держит 256 одновременных вызовов (тема Reactor Operators). Банк обслуживает 20 запросов одновременно, каждый 100 мс, а сверх этого отвечает 429. Часть flatmap на виртуальном времени:

Flux.range(1, 1000)
        .flatMap(i -> bank.charge("p" + i)
                .onErrorResume(e -> Mono.just("rejected")), concurrency) // 256 или 16
        .subscribe();
flatmap: 1000 payments, bank accepts 20 concurrent requests, 100 ms each
  flatMap(charge)         peak at bank = 20, rejected with 429 = 980, served = 20, took 100 ms
  flatMap(charge, 16)     peak at bank = 16, rejected with 429 = 0, served = 1000, took 6300 ms

Без лимита job закончился за 100 мс — и провёл 20 платежей из тысячи. Отказы приходят мгновенно, flatMap тут же освобождает слот и запускает следующий вызов, так что 980 отказов случились в первую же миллисекунду. С concurrency = 16 все платежи прошли за 6,3 секунды, и банк ни разу не отказал. Медленнее, но это скорость, которую банк реально выдерживает.

В проде хуже, чем в демо. Если на 429 стоит retry с backoff, отказы вернутся волнами, и вместе с ними запросы других клиентов банка. Если банк не отказывает, а замедляется, 256 запросов упрутся в пул соединений WebClient. В Reactor Netty по умолчанию в пуле 2 × max(число ядер, 8) соединений на хост (на 18-ядерной машине автора — 36), очередь ожидания по документации вдвое больше пула, а ждать соединение запрос может 45 секунд. Остальные запросы того же сервиса к этому хосту, в том числе от пользователей, встанут в ту же очередь.

Reactive Streams даёт backpressure, значит, flatMap сам не перегрузит соседа.

Backpressure защищает подписчика от источника внутри процесса. Банк не участвует в контракте request(n): он не может попросить «меньше». flatMap запросит у источника столько элементов, сколько разрешает concurrency, и запустит столько же вызовов. Ограничение нагрузки на внешнюю систему — это явный параметр concurrency или limitRate, а для общего лимита на весь сервис — rate limiter вроде Resilience4j.

Найти такое место помогают метрики, а не тесты: число активных и ожидающих соединений пула (Reactor Netty публикует их в Micrometer, если включить metrics(true) у ConnectionProvider), количество 429 и 503 от партнёра, время получения соединения. Всплеск ожидающих соединений одновременно с запуском job — почти всегда flatMap без лимита.

Стектрейс реактивной ошибки показывает Reactor, а не твой код: место сборки возвращают checkpoint и Debug Agent

ReactorDebugAgent из reactor-toolsто же место сборки, что и хукправит байткод при загрузке классов, на выполнение почти не влияетможно в проде; Boot включает его сам, если reactor-tools в classpath

Debug Agent подменяет вызовы операторов в твоих классах на версии с отметкой места: строку и метод он берёт из байткода, а не из стектрейса, поэтому дёшев. В Spring Boot 4 его включает свойство spring.reactor.debug-agent.enabled, по умолчанию true, достаточно добавить зависимость io.projectreactor:reactor-tools. Без Boot агент запускают ReactorDebugAgent.init() в начале main, до сборки цепочек. Хук onOperatorDebug даёт то же самое, но собирает настоящий стектрейс на каждый оператор, поэтому годится только для локального разбора.

  • block() в event loop падает, только когда надо ждать, а JDBC и синхронные клиенты не проверяет никто. BlockHound в тестах ловит любую блокировку, включая Mono.just(jdbc()) внутри subscribeOn.
  • Mono, который не встроен в возвращаемую цепочку, не выполняется и не падает: doOnNext(repo::save) — частый вариант. Ловят тестом эффекта или PublisherProbe.
  • subscribe() внутри flatMap теряет ошибку, Context, отмену и предел нагрузки. Работу встраивают через then и Mono.when, гарантированную фоновую — через outbox или брокер.
  • Context видят только операторы выше contextWrite. MDC переносят Hooks.enableAutomaticContextPropagation и Micrometer Context Propagation.
  • flatMap без concurrency шлёт соседу до 256 запросов сразу: backpressure не защищает внешние системы.
  • Место сборки в стектрейс возвращают checkpoint (дёшево, точечно) и ReactorDebugAgent (дёшево, везде); onOperatorDebug — только локально.

На собеседовании

Как найти блокирующий вызов в реактивном коде?

Подключаю BlockHound в тестах: это Java-агент, который инструментирует блокирующие методы JDK и бросает BlockingOperationError, если их вызвали из неблокирующего потока — event loop Netty или parallel. Он ловит сам факт вызова, а не задержку, поэтому срабатывает и с быстрой тестовой базой; мок, который не вызывает блокирующих методов, он не поймает. Встроенная проверка Reactor на block() срабатывает, только когда значение надо ждать, а JDBC и синхронные клиенты не проверяет вовсе.

В проде симптом — растущая задержка у всех запросов при свободном CPU и health-check, который отвечает секундами. Снимаю дамп потоков: если в стеке потока reactor-http-nio видны JDBC-драйвер, Thread.sleep или синхронный HTTP-клиент, кто-то блокирует event loop.

  • Частая ложная починка: Mono.just(jdbc()).subscribeOn(boundedElastic()). Аргумент вычисляется в event loop до перехода; нужен fromCallable.
  • На JDK 13+ BlockHound требует -XX:+AllowRedefinitionToAddDeleteMethods; разрешённые блокировки добавляют через builder().allowBlockingCallsInside.
  • boundedElastic — ограниченный пул: если в нём всё, это тот же MVC, только сложнее. Тогда честнее MVC на виртуальных потоках.
Тест с block() внутри обработчика зелёный, а в проде IllegalStateException. Почему?

Reactor бросает «block() … not supported in thread …» только если в неблокирующем потоке приходится ждать значения. В тесте мок вернул Mono.just, значение готово, ожидания нет. В проде настоящий клиент отвечает через сеть, block() начинает ждать в потоке Netty и падает. Лечится не тестом, а заменой block() на flatMap.

Почему нельзя вызывать subscribe() внутри flatMap или в сервисе?

subscribe() создаёт отдельную цепочку, оторванную от запроса. Её ошибка не дойдёт до клиента: без обработчика Reactor просто напишет её в лог через onErrorDropped. Context туда не попадёт, поэтому пропадут SecurityContext, traceId и транзакция. Отмена запроса её не остановит, и под нагрузкой таких фоновых задач станет сколько угодно.

Правильно встроить работу в цепочку: then для последовательной, Mono.when или zip для параллельной. Подписывается фреймворк — на то, что вернул контроллер.

  • Если работа правда фоновая и должна пережить сбой, нужна надёжная доставка: outbox в той же транзакции или брокер с повторами, а не отдельная подписка.
  • Обратная ошибка — забыть подписку: doOnNext(p -> repo.save(p)) выбрасывает Mono из save. Ловится тестом эффекта или PublisherProbe.assertWasSubscribed.
Найди три ошибки 
public Mono<Receipt> pay(Payment p) {
    return bank.charge(p)
            .doOnNext(r -> paymentRepository.save(p.paid(r)))   // R2DBC, возвращает Mono
            .doOnNext(r -> audit.write(p).subscribe())
            .contextWrite(ctx -> ctx.put("tenant", p.tenant()));
}

Первая: save внутри doOnNext не подписан — платёж не сохранится. Вторая: audit подписан отдельно — его ошибка не дойдёт до клиента, а tenant и SecurityContext он не увидит, потому что у отдельной подписки свой Context. Третья: contextWrite стоит в сервисе, а не на входе запроса; если tenant читают операторы, которые вызывающий код добавит ниже pay(), они его не увидят. Исправление: bank.charge(p).flatMap(r -> paymentRepository.save(p.paid(r)).then(audit.write(p)).thenReturn(r)), а tenant класть в WebFilter.

В WebFlux пропал traceId в логах и пустой SecurityContext. Почему?

MDC и классический SecurityContextHolder — ThreadLocal, а реактивная цепочка переходит между потоками, и в другом потоке значения нет. В Reactor данные запроса хранят в Context, который привязан к подписке. Spring Security кладёт туда SecurityContext, а читать его надо через ReactiveSecurityContextHolder.

Для логов включаю автоматический перенос: Micrometer Context Propagation и Hooks.enableAutomaticContextPropagation, в Boot — spring.reactor.context-propagation=auto. Тогда Reactor восстанавливает MDC из Context перед каждым оператором.

  • Context течёт от подписчика к источнику: contextWrite видят только операторы выше него. Кладут его как можно ниже — в WebFilter.
  • Отдельная подписка через subscribe() получает пустой Context: там анонимный пользователь и нет транзакции.
  • Автоматический перенос стоит работы на каждом операторе; Micrometer Tracing регистрирует свои ключи сам.

Как отлаживать реактивный код, если стектрейс состоит из операторов Reactor?

Ошибка случается при выполнении в потоке планировщика, а оператор был создан при сборке в другом стеке, поэтому обычный стектрейс не показывает мой код. Место сборки возвращают три способа. checkpoint("описание") ставлю на важных границах — он почти бесплатный и даёт метку в пути ошибки. ReactorDebugAgent из reactor-tools добавляет место сборки ко всем операторам через байткод, его можно держать в проде, а Spring Boot включает его сам, если reactor-tools в classpath.

Hooks.onOperatorDebug() даёт то же, но собирает стектрейс на каждый оператор, поэтому только локально.

  • В suppressed-записи «Error has been observed at the following site(s)»: *__ — где ошибка возникла, |_ — через какие места прошла.
  • checkpoint("…", true) добавляет стек сборки, но ценой стектрейса при сборке.
  • Для «тихих» багов вроде неподписанного Mono стектрейса нет вовсе: тут помогают log() на подозрительном участке, doOnSubscribe и тест с PublisherProbe.
