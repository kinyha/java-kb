Reactive Philosophy

Платёжный сервис отдаёт клиенту выписку из миллиона платежей. Если читать базу быстрее, чем клиент принимает, строки копятся в памяти, сколько бы потоков ни было. Reactive Streams договаривается иначе: клиент сам говорит, сколько строк готов принять, вызовом request(n), и источник читает из базы ровно столько. Пока никто не подписался и ничего не запросил, ничего не происходит вообще. Реактивные библиотеки — Reactor, RxJava, драйверы R2DBC — реализуют этот контракт, а в JDK он лежит как java.util.concurrent.Flow.

Медленный банк съедает потоки, а асинхронная выгрузка — память

Сервис платежей принимает 400 запросов в секунду. Каждый ходит в банк за 500 мс и в базу за 50 мс. По закону Литтла одновременно в работе 400 × 0,55 = 220 запросов, и в модели «поток на запрос» каждый держит поток, хотя почти всё время ждёт сеть. У Tomcat по умолчанию 200 потоков, так что очередь растёт, а если банк замедлится до двух секунд, потоков понадобится 800. Как это выглядит в Tomcat и что меняют виртуальные потоки, разобрано в темах Servlet & Tomcat и Virtual Threads.

Первое, что приходит в голову, — не ждать в потоке: отдать вызов в пул и продолжить по готовности. Так работает CompletableFuture, и для одного ответа от банка этого хватает. Но сервис ещё и выгружает выписку: миллион строк из базы в HTTP-ответ клиенту на медленном мобильном интернете. Асинхронно это пишут так: курсор читает строки и каждую отправляет задачей в исполнитель, который пишет в сокет.

var client = new ThreadPoolExecutor(1, 1, 0, SECONDS,
        new LinkedBlockingQueue<>());               // очередь без границы, как у newFixedThreadPool
client.execute(() -> await(clientBusy));          // клиент медленный: пока занят
for (int row = 1; row <= 100_000; row++) {        // курсор БД отдаёт строки
    client.execute(() -> sent.incrementAndGet()); // «отправить клиенту» — задача в очередь
}
System.out.println("rows read from DB: 100000, sent to client: " + sent.get()
        + ", waiting in memory: " + client.getQueue().size());
1. Push without demand: async callback into a slow client
  rows read from DB: 100000, sent to client: 0, waiting in memory: 100000

Ни один поток не ждал, а все сто тысяч строк уже в памяти. Чтение из базы ничего не знает о скорости клиента: у асинхронного вызова нет обратного канала «притормози». С миллионом строк по килобайту это гигабайт heap на одного медленного клиента, а десять таких клиентов кладут сервис с OutOfMemoryError. Ограничить очередь не помогает: execute на полной очереди бросит RejectedExecutionException, и строки придётся либо терять, либо снова блокировать поток курсора.

Нужны сразу три свойства: асинхронность (поток не ждёт сеть), неблокирующая передача (никто не спит на полной очереди) и обратная связь от потребителя к источнику. Третье называют backpressure. Именно для этого инженеры Netflix, Pivotal, Lightbend (тогда Typesafe) и других компаний написали спецификацию Reactive Streams, версия 1.0 вышла в 2015 году. Слово «реактивный» в Java означает прежде всего её: код реагирует на сигналы о готовых данных, а источник подстраивается под спрос.

Реактивный — значит асинхронный: CompletableFuture и колбэки уже реактивны.

Асинхронность убирает ожидание из потока, но не защищает от быстрого источника. Реактивные потоки добавляют к ней спрос: источник отдаёт не больше, чем подписчик запросил. Демо выше полностью асинхронное и всё равно складывает сто тысяч строк в память.

Подписчик сам говорит, сколько готов принять, а источник отдаёт не больше

Спецификация — это четыре интерфейса и около сорока правил к ним. Интерфейсы почти пустые, вся суть в том, кто кого и когда вызывает:

public final class Flow {                       // java.util.concurrent, с Java 9
    interface Publisher<T> {
        void subscribe(Subscriber<? super T> s); // «хочу получать данные»
    }
    interface Subscriber<T> {
        void onSubscribe(Subscription s);         // первым сигналом: вот твой пульт
        void onNext(T item);                      // очередной элемент
        void onError(Throwable t);                // конец с ошибкой
        void onComplete();                        // конец без ошибки
    }
    interface Subscription {                      // пульт, который держит подписчик
        void request(long n);                     // «готов принять ещё n»
        void cancel();                            // «больше не нужно»
    }
    interface Processor<T, R> extends Subscriber<T>, Publisher<R> { }
}

Порядок сигналов фиксирован: сначала onSubscribe, потом сколько угодно onNext, потом не больше одного финального сигнала, onError или onComplete. После финального сигнала нет ничего. Главное правило 1.1: число onNext не превышает суммы всех request(n). Если подписчик ничего не запросил, издатель обязан молчать, даже если данные готовы.

Напишем издатель выписки на интерфейсах Flow. Он держит счётчик спроса и читает из курсора только тогда, когда спрос больше нуля. Подписчик-клиент просит две строки, после второй — ещё три, а после пятой отключается. PhilosophyDemo.java, часть 2, фрагмент:

public void request(long n) {
    demand.getAndAccumulate(n, (a, b) -> a + b < 0 ? Long.MAX_VALUE : a + b); // спрос копится, правило 3.17
    drain();
}

void drain() {
    if (wip.getAndIncrement() != 0) return;          // цикл уже крутится выше по стеку — он и отдаст
    do {
        while (demand.get() > 0 && !cancelled && cursor.hasNext()) {
            demand.decrementAndGet();
            subscriber.onNext(cursor.next());        // строку читаем, только когда её запросили
        }
        if (!cursor.hasNext() && !cancelled && !done) { done = true; subscriber.onComplete(); }
    } while (wip.decrementAndGet() != 0);            // пока крутились, пришёл новый request — ещё круг
}

// подписчик
public void onSubscribe(Flow.Subscription s) { subscription = s; s.request(2); }
public void onNext(String row) {
    received++;
    if (received == 2) subscription.request(3);      // отправил две — прошу ещё три
    if (received == 5) subscription.cancel();        // клиент отключился
}

Сравни с первым шагом: там курсор прочитал сто тысяч строк, здесь — пять. Отмена так же важна, как спрос: оборванное соединение в WebFlux превращается в cancel(), и он доходит до драйвера базы, который закрывает курсор.

Правила, на которых ломаются самописные издатели

Сложный в этом коде только drain, и он нужен из-за правила 3.3: request обязан ограничивать рекурсию между издателем и подписчиком. Подписчик почти всегда вызывает request(1) прямо из onNext. Если издатель отдаёт элемент внутри request, получается цепочка request → onNext → request → onNext, и каждый элемент углубляет стек. Часть 3 демо сравнивает наивный издатель с циклом drain на ста тысячах элементов:

public void request(long n) {                       // наивный издатель
    for (long i = 0; i < n && next < size; i++) {
        subscriber.onNext(++next);                   // а onNext вызовет request(1)
    }
    if (next == size) subscriber.onComplete();
}
3. request(1) from onNext: naive publisher vs drain loop
  naive: StackOverflowError after 8356 items
  drain loop: onComplete after 100000

Наивный падает через несколько тысяч элементов. Точное число зависит от размера стека и от того, какие методы JIT уже успел скомпилировать: в пяти запусках части 3 от 8131 до 8362, при запуске всех частей подряд 6–7 тысяч, с -Xss512k около 1200. Цикл drain отдаёт все сто тысяч: вложенный request только увеличивает счётчик и выходит, а элемент отдаёт тот виток, который уже крутится выше по стеку. Счётчик wip (work in progress) заодно не даёт двум потокам одновременно вызывать onNext: правило 1.3 требует, чтобы сигналы шли подписчику последовательно.

Источник собирают из готовых: Flux.generate для синхронного состояния вроде курсора, Flux.create для колбэков, Flux.using или Flux.usingWhen, чтобы закрыть ресурс при отмене. Корректность проверяет Reactive Streams TCK: набор тестов, через который проходят Reactor, RxJava и драйверы. Reactor сам ловит нарушения правил у «чужих» подписчиков, часть 4 демо:

Под капотом: почему BaseSubscriber не получил ошибку

Если подписать на Flux обычный org.reactivestreams.Subscriber, Reactor оборачивает его в StrictSubscriber. Обёртка проверяет правила спецификации строго, и request(0) превращается в onError со ссылкой на §3.9 — это видно в стектрейсе: StrictSubscriber.request(StrictSubscriber.java:134).

Собственные подписчики Reactor, CoreSubscriber, к которым относится и BaseSubscriber, живут по ослабленным правилам ради скорости: операторы доверяют друг другу и не перепроверяют каждый сигнал. Некорректный запрос там проверяет Operators.validate(n): она пишет его в лог на уровне DEBUG и игнорирует. Поэтому подписка из демо просто висит без единого сигнала. В проде это выглядит как запрос, который не отвечает и не падает.

Flow в JDK и org.reactivestreams

Спецификация появилась как отдельная библиотека org.reactivestreams, и Reactor, RxJava, R2DBC построены на её интерфейсах. В Java 9 те же четыре интерфейса добавили в JDK как вложенные в java.util.concurrent.Flow (JEP 266). Методы и правила совпадают один в один, отличается только пакет, поэтому типы не совместимы напрямую: нужен адаптер. В самой библиотеке спецификации это FlowAdapters, в Reactor — JdkFlowAdapter.flowPublisherToFlux и publisherToFlowPublisher.

В JDK нет ни одного оператора: ни map, ни flatMap. Flow — это стандарт для обмена, чтобы библиотеки могли соединяться без общей зависимости. Им пользуется java.net.http.HttpClient: тело запроса — HttpRequest.BodyPublisher, то есть Flow.Publisher<ByteBuffer>, а тело ответа читает HttpResponse.BodySubscriber. Единственная готовая реализация издателя в JDK — SubmissionPublisher, к нему вернёмся в последнем шаге.

Спрос идёт вверх по цепочке, данные — вниз, и режим сам переключается между push и pull

В чистом push источник отдаёт данные, как только они есть, и потребитель обязан успевать: так работает колбэк из первого шага. В чистом pull потребитель забирает по одному элементу, как Iterator.next(), и ждёт каждый — это блокировка. Reactive Streams смешивает оба: спрос идёт от подписчика к источнику (pull), а данные в пределах спроса источник отдаёт сам, когда они готовы (push). Если подписчик успевает, он запрашивает много, и поток идёт как push без пауз. Если не успевает, запрашивает мало, и источник ждёт его, как при pull. Этот режим называют dynamic push-pull.

В цепочке операторов каждый оператор одновременно подписчик для того, кто выше, и издатель для того, кто ниже. Спрос он не обязан передавать как есть: может пересчитать. Часть 5 демо печатает, какой request доходит до источника в трёх цепочках:

Flux.range(1, 3)
        .doOnRequest(n -> System.out.println("source got request(" + n + ")"))
        .subscribe(i -> { });                         // подписка лямбдой

Flux.range(1, 20)
        .doOnRequest(n -> System.out.println("source got request(" + n + ")"))
        .publishOn(Schedulers.single(), 8)            // очередь на 8 элементов между потоками
        .subscribe(i -> { }, e -> { }, done::countDown);

Flux.range(1, 25)
        .doOnRequest(n -> System.out.println("source got request(" + n + ")"))
        .limitRate(10)                                // дробит спрос на пачки
        .subscribe(i -> { });

Подписка лямбдой запрашивает Long.MAX_VALUE, то есть «сколько угодно»: это чистый push, и так подписывается большинство кода. Backpressure при этом не исчезает, но работает только до ближайшего оператора с собственной очередью. publishOn переносит элементы в другой поток через очередь. Он запросил у источника размер очереди, 8, а потом дозапрашивал по 6, когда три четверти очереди освобождались. По умолчанию очередь 256 элементов, и тогда в логе будут request(256) и потом request(192). Так же устроены flatMap (по 32 элемента от каждого внутреннего издателя) и limitRate(n), который вставляют специально, чтобы источник не получил неограниченный спрос.

Источник, который не умеет ждать

Pull работает, только если источник умеет подождать: курсор базы, файл, сокет с TCP-окном. Таймер, клики пользователя, котировки с биржи, события из чужой системы приходят, когда приходят. Такой источник при нулевом спросе может только выбросить элемент, сложить его в буфер или упасть. Flux.interval по умолчанию падает, часть 6 демо:

Flux.interval(Duration.ofMillis(1))                 // тикает по таймеру, ждать не умеет
        .publishOn(Schedulers.single(), 16)          // очередь на 16 тиков
        .subscribe(tick -> sleep(5_000),             // потребитель завис на первом тике
                   e -> System.out.println("onError: " + e));
6. A source that cannot wait: Flux.interval and a stuck consumer
  onError: reactor.core.Exceptions$OverflowException: Could not emit tick 16 due to lack of requests (interval doesn't support small downstream requests that replenish slower than the ticks)

Тики 0–15 легли в очередь publishOn, спрос кончился, и тик 16 стал ошибкой. Номер тика равен размеру очереди, а не времени: это прямое следствие правила 1.1. Для таких источников выбирают стратегию явно: onBackpressureBuffer(n) копит до лимита, onBackpressureDrop выбрасывает лишнее, onBackpressureLatest держит только последнее значение. Для котировок разумно Latest, для платёжных событий ни Drop, ни Latest не подходят: их не теряют, а читают из брокера, который сам хранит хвост и отдаёт по запросу.

Reactive Streams — это push: источник шлёт данные подписчику.

Данные действительно идут push-ом, но только в пределах спроса, который подписчик выдал через request(n). Спрос — это pull. Подписчик с request(Long.MAX_VALUE) превращает поток в чистый push, с request(1) — в чистый pull.

До subscribe ничего не происходит: cold издатель повторяет работу для каждого, hot раздаёт общую

У реактивного кода два момента времени. Сборка (assembly) — когда вызываются Flux.range, map, flatMap: они только создают объекты-описания и связывают их в цепочку. Подписка (subscription) — когда кто-то вызвал subscribe: тогда подписка поднимается к источнику, спрос идёт вверх, и только после этого источник начинает работу. В WebFlux подписывается фреймворк на Mono, который вернул контроллер, — основы разобраны в теме WebFlux.

Ловушка в том, что Java вычисляет аргументы метода до его вызова, и реактивная библиотека на это повлиять не может. Часть 7 демо:

Mono<String> eager = Mono.just(charge("just"));           // charge() выполняется прямо здесь
Mono<String> lazy = Mono.fromCallable(() -> charge("fromCallable")); // здесь только лямбда
// никто не подписан; теперь по две подписки на каждый
eager.subscribe(); eager.subscribe();
lazy.subscribe(); lazy.subscribe();
7. Assembly vs subscription
  assemble Mono.just(charge()):
    bank.charge() called by just
  assemble Mono.fromCallable(charge):
  nobody subscribed. Now subscribe twice to each:
    bank.charge() called by fromCallable
    bank.charge() called by fromCallable

Деньги через Mono.just списались один раз — при сборке, до подписки, даже если подписки не будет никогда. Две подписки получили одно и то же готовое значение. fromCallable не списал ничего при сборке и списал дважды при двух подписках. Правило простое: just — для уже готовых значений, работу заворачивают в fromCallable, defer или вызов, который сам возвращает Mono, как WebClient или R2DBC.

Второе следствие ленивости — каждая подписка запускает источник заново. Такой издатель называют cold: у каждого подписчика свой прогон. Запрос в базу, HTTP-вызов, чтение файла — cold. Hot-издатель работает независимо от подписчиков: события идут, даже если никто не слушает, а новый подписчик получает только то, что случилось после подписки. Часть 8 демо: выписка из базы и поток статусов платежей.

Flux<String> cold = Flux.defer(() -> {
    queries.incrementAndGet();                       // каждый подписчик — свой запрос в БД
    return Flux.just("p1", "p2", "p3");
});
cold.subscribe(p -> System.out.println("cold A got " + p));
cold.subscribe(p -> System.out.println("cold B got " + p));

Sinks.Many<String> statuses = Sinks.many().multicast().directBestEffort();

statuses.tryEmitNext("p1 NEW");                      // никого нет — событие пропало

Обе стороны дают свои баги. Cold, подписанный дважды, дважды списывает деньги или дважды ходит в банк. Hot теряет события, которые пришли до подписки. Превратить cold в hot или раздать один прогон нескольким подписчикам можно операторами share, cache, replay, а hot-источник с ручной отправкой — это Sinks; их варианты и отличия разобраны в теме Reactor Operators.

С виртуальными потоками backpressure даёт обычная блокировка, и реактивность нужна реже

Reactive Streams понадобился спрос request(n), потому что в неблокирующем мире у источника нет другого способа узнать, что потребитель не успевает. В блокирующем мире этот способ встроен: write в сокет блокируется, когда TCP-буфер полон, put в ограниченную очередь — когда она заполнена. Поток производителя просто останавливается, и сигнал «притормози» доходит до источника сам. Это видно даже на издателе Flow из JDK: SubmissionPublisher.submit блокирует вызывающий поток, пока у подписчика нет места. Часть 9 демо, буфер на 4 элемента, клиент обрабатывает каждый 100 мс:

try (var publisher = new SubmissionPublisher<Integer>(delivery, 4)) { // буфер на 4 элемента
    publisher.subscribe(slowClient);                 // request(1), 100 мс на элемент, снова request(1)
    for (int i = 1; i <= 8; i++) {
        publisher.submit(i);                         // блокирует, если буфер полон
        log.add("submitted " + i + (waited ? " after waiting" : ""));
    }
}

На платформенном потоке такое ожидание дорого, поэтому реактивный подход и избегает его. На виртуальном оно стоит пару килобайт стека в heap. Выписку из первого шага с виртуальными потоками пишут обычным циклом while (rs.next()) out.write(row): медленный клиент блокирует write, цикл встаёт, а JDBC-драйвер дочитывает строки пачками по fetchSize, только когда цикл их забирает. В PostgreSQL для этого нужен выключенный autocommit, иначе драйвер читает весь результат сразу.

Реактивность окупается, когда данные и правда идут потоком: стриминг ответов и SSE, тысячи долгих соединений в шлюзе, склейка событий из нескольких источников с окнами и таймаутами, источники, которые не умеют ждать. И когда вся цепочка уже неблокирующая, от драйвера базы до HTTP-клиента. Для сервиса «принял запрос, сходил в базу и в банк, ответил» на Java 21 хватит Spring MVC на виртуальных потоках: та же масштабируемость по ожиданию, а код последовательный. Практические последствия выбора для веб-слоя разобраны в теме WebFlux, а типичные ошибки реактивного кода — в теме Reactive Pitfalls.

С виртуальными потоками Reactor больше не нужен.

Виртуальные потоки закрывают главный мотив — дорогое ожидание I/O. Backpressure для стриминга, отмена по цепочке и операторы для потоков событий остаются сильной стороной реактивного подхода. Выбор теперь зависит от формы данных: запрос-ответ — блокирующий код на виртуальных потоках, поток событий — реактивный.

  • Асинхронность убирает ожидание из потока, но без обратной связи быстрый источник складывает данные в память. Reactive Streams добавляет спрос: request(n).
  • Контракт: subscribe → onSubscribe → onNext не больше запрошенного → один onError или onComplete. Отмена cancel() доходит до источника.
  • Спрос идёт вверх (pull), данные вниз (push). Операторы с очередью пересчитывают спрос: publishOn просит у источника размер очереди и дозапрашивает по три четверти.
  • Свой Publisher не пишут: правила про рекурсию, последовательные сигналы и переполнение спроса легко нарушить. Источник собирают из Flux.generate, create, using.
  • До subscribe ничего не выполняется, но аргументы Mono.just вычисляются сразу. Cold повторяет работу на каждую подписку, hot теряет события до подписки.
  • Flow в JDK — те же четыре интерфейса без операторов. На виртуальных потоках backpressure даёт обычная блокировка, и реактивность нужна там, где данные идут потоком.

На собеседовании

Что такое Reactive Streams и зачем они, если есть CompletableFuture?

Reactive Streams — спецификация асинхронной обработки потока данных с неблокирующим backpressure. В ней четыре интерфейса: Publisher, Subscriber, Subscription и Processor. Подписчик подписывается, получает Subscription и через request(n) говорит, сколько элементов готов принять; издатель отдаёт не больше, потом onComplete или onError. Reactor, RxJava и R2DBC реализуют этот контракт, а в JDK он есть как java.util.concurrent.Flow.

CompletableFuture асинхронный, но про одно значение, и обратной связи у него нет. Если я выгружаю миллион платежей медленному клиенту колбэками, база прочитается целиком в память. С Reactive Streams клиент запрашивает строки по мере отправки, и курсор читает ровно столько.

  • Ключевые правила: onNext не больше суммы request (1.1), сигналы строго последовательно (1.3), тишина после финального сигнала (1.7), null запрещён (2.13), рекурсия request ↔ onNext ограничена (3.3), request(n ≤ 0) — onError (3.9).
  • Свой Publisher в прикладном коде не пишу: его надо прогонять через TCK. Источник собираю из Flux.generate, Flux.create, Flux.usingWhen.
  • Flow и org.reactivestreams совпадают по методам, но это разные типы; соединяются через FlowAdapters или JdkFlowAdapter. В JDK Flow используют HttpClient (BodyPublisher, BodySubscriber) и SubmissionPublisher.
Что не так с этим издателем? 
public void subscribe(Flow.Subscriber<? super Integer> s) {
    s.onSubscribe(new Flow.Subscription() {
        int next;
        public void request(long n) {
            for (long i = 0; i < n && next < size; i++) s.onNext(++next);
            if (next == size) s.onComplete();
        }
        public void cancel() { }
    });
}

Четыре нарушения. Подписчик, который вызывает request(1) из onNext, уходит в рекурсию и на нескольких тысячах элементов получает StackOverflowError (правило 3.3). Каждый request после конца снова вызывает onComplete (1.7). cancel ничего не делает, и издатель продолжает отдавать элементы. Если request придёт из двух потоков, onNext пойдёт параллельно (1.3), а next не защищён. Исправление — счётчик спроса и цикл drain с wip, флаги cancelled и done, а лучше Flux.generate вместо своего класса.

Reactive Streams — это push или pull?

И то и другое. Спрос идёт от подписчика к источнику через request(n) — это pull. Данные в пределах спроса источник отдаёт сам, как только они готовы, — это push. Если подписчик успевает и запросил много, получается чистый push без пауз; если не успевает и просит по одному, источник его ждёт. Это называют dynamic push-pull.

На практике большинство подписывается лямбдой, а это request(Long.MAX_VALUE). Backpressure при этом работает до ближайшего оператора с очередью: например, publishOn просит у источника 256 элементов и потом дозапрашивает по 192.

  • Источник, который не умеет ждать (таймер, события, котировки), при нулевом спросе должен выбросить, сохранить или упасть: Flux.interval падает с OverflowException. Стратегию выбирают явно: onBackpressureBuffer, Drop, Latest.
  • limitRate(n) ставят перед источником, которому вреден неограниченный спрос: он дробит запрос на пачки и дозапрашивает по 75%.
  • В WebFlux спрос доходит до сети: Netty не читает сокет, пока цепочка не запросила данные, и отправителя тормозит TCP.
Что напечатает источник? 
Flux.range(1, 20)
        .doOnRequest(n -> System.out.println("request(" + n + ")"))
        .publishOn(Schedulers.single(), 8)
        .subscribe(i -> { });
request(8)
request(6)
request(6)
request(6)

Лямбда запрашивает неограниченно, но publishOn отвечает за свою очередь на 8 элементов. Он запрашивает у источника 8, а каждый раз, когда подписчик забрал 6 (три четверти очереди), дозапрашивает ещё 6. После 8 + 6 + 6 = 20 элементов источник уже завершился, и четвёртый request(6) пришёл в пустоту: doOnRequest его напечатал, но отдавать нечего.

Что значит «ничего не происходит до subscribe»? Чем cold отличается от hot?

Операторы вроде map и flatMap только собирают описание конвейера. Работа начинается, когда кто-то подписался: подписка поднимается к источнику, спрос идёт вверх, и только тогда источник делает запрос в базу или в банк. Поэтому Mono, который никто не вернул и не подписал, просто не выполнится.

Cold-издатель повторяет работу для каждого подписчика: две подписки на вызов банка — два вызова. Hot работает независимо от подписчиков, как поток статусов платежей: новый подписчик получает только события после подписки. Cold раздают нескольким подписчикам через cache или share, а hot-источник с ручной отправкой делают через Sinks.

  • Ленивость не спасает от Java: аргументы метода вычисляются до вызова. Mono.just(charge()) списывает деньги при сборке, даже без подписки. Работу заворачивают в fromCallable или defer.
  • Hot-источник обычно не умеет ждать, поэтому вопрос backpressure для него — это вопрос стратегии переполнения.
  • Повторная подписка — механизм retry: retryWhen переподписывается на cold-источник и выполняет вызов заново. На hot-источнике повтор не вернёт пропущенное.
Платёж нашёлся в кеше. Будет ли списание? 
Mono.just("cached")
        .switchIfEmpty(Mono.just(charge("fallback")))
        .subscribe(v -> System.out.println("result: " + v));
    bank.charge() called by fallback
    result: cached

Будет. Результат взят из кеша, и запасной Mono даже не подписан, но charge вызван при сборке: это аргумент Mono.just. Правильно switchIfEmpty(Mono.fromCallable(() -> charge("fallback"))) или Mono.defer. Ошибку часто ловят только по двойным списаниям в логах банка.

Нужна ли реактивность, если есть виртуальные потоки?

Главную причину реактивности — дорогое ожидание I/O в платформенном потоке — виртуальные потоки закрывают: ожидающий поток почти ничего не стоит, и код остаётся последовательным, с обычными стектрейсами и ThreadLocal. Для запрос-ответ сервиса, который ходит в базу и пару API, я возьму MVC на виртуальных потоках.

Реактивность оставляю там, где данные идут потоком: стриминг, SSE и WebSocket, шлюзы с тысячами соединений, склейка событий из нескольких источников с окнами, таймаутами и retry. Плюс если вся цепочка уже неблокирующая.

  • В блокирующем коде backpressure встроен: write в сокет и put в ограниченную очередь блокируются. Поэтому на виртуальных потоках выгрузку пишут циклом, а JDBC дочитывает строки по fetchSize.
  • Что остаётся за реактивным подходом: отмена, которая проходит по цепочке до драйвера; готовые операторы для потоков; единая модель для источников, которые не умеют ждать.
  • Смешивать дорого: блокирующий вызов в реактивной цепочке требует boundedElastic, а реактивный в блокирующем коде — block(). Выбирают модель на сервис, а не на метод.
