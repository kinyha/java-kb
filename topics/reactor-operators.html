Reactor Operators

Платёжный сервис проводит пачку платежей через банк, собирает карточку платежа из трёх сервисов и переживает ответы 503. В Reactor каждая такая задача — несколько операторов, и почти все ошибки возникают на стыке между ними. Оператор, который вызывает другой сервис, должен на него подписаться: это делает flatMap и его родственники, и они различаются тем, сколько вызовов идёт сразу и в каком порядке приходят ответы. Ошибка завершает поток, а повтор — это новая подписка, поэтому повторится только то, что создаётся при подписке. Всё время в этой теме виртуальное: демо проверяют сценарии с секундами и минутами ожидания за миллисекунды, тем же способом, каким их тестируют.

map меняет значение, а flatMap подписывается на то, что вернула функция

Сервис получает пачку идентификаторов платежей и для каждого вызывает банк. Вызов банка в реактивном клиенте возвращает Mono<String>. Первая попытка обычно выглядит как ids.map(bank::charge): компилируется, запускается, ошибок нет. OperatorsDemo.java, часть 1:

cd examples/reactive
./run.sh OperatorsDemo 1
Function<String, Mono<String>> charge = id -> Mono.fromCallable(() -> {
    calls.incrementAndGet();                         // считаем реальные вызовы банка
    return id + " paid";
});
Flux.just("p1", "p2")
        .map(charge)                                 // Flux<Mono<String>>: на Mono никто не подписан
        .subscribe(v -> System.out.println("map emitted: " + v.getClass().getSimpleName()));
Flux.just("p1", "p2")
        .flatMap(charge)                             // подписывается на каждый Mono и отдаёт его значение
        .subscribe(v -> System.out.println("flatMap emitted: " + v));

  flatMap emitted: p2 paid
  bank calls after flatMap: 2

map применил функцию и отдал дальше её результат — два объекта Mono, то есть два рецепта вызова. Банк не вызван ни разу: на эти Mono никто не подписался (почему подписка решает всё, разобрано в теме Reactive Philosophy). flatMap делает три вещи: применяет функцию, подписывается на каждый полученный издатель и сливает их элементы в один выходной поток. Правило выбора простое: функция возвращает обычное значение — map; возвращает Mono или Flux — flatMap или его варианты.

У Mono тот же набор: Mono.flatMap для функции, которая вернёт Mono, flatMapMany, если вернёт Flux. Когда результат предыдущего шага не нужен, а нужно только дождаться его конца, пишут then(next): «сохрани платёж, потом отправь уведомление». thenReturn(value) дожидается конца и отдаёт готовое значение.

Если код с map скомпилировался, вызов выполнится.

Компилятор видит только тип: Flux<Mono<String>> так же законен, как Flux<String>. Подсказка — вложенный издатель в типе результата. Если в сигнатуре появился Flux<Mono<…>> или Mono<Mono<…>>, почти наверняка вместо map нужен flatMap.

flatMap, concatMap и flatMapSequential отличаются тем, сколько вызовов идёт сразу и в каком порядке приходят ответы

Теперь банк отвечает с разной задержкой: на p1 — 300 мс, p2 — 100, p3 — 200, p4 — 50. Часть 2 демо проводит пачку четырьмя способами и печатает, когда начался каждый вызов и когда пришёл его результат. Время виртуальное: VirtualTimeScheduler подменяет планировщики Reactor, и Mono.delay срабатывает ровно в нужную миллисекунду, без настоящего ожидания.

static Mono<String> bank(String id) {               // задержка по id: 300, 100, 200, 50 мс
    return Mono.delay(Duration.ofMillis(latency(id))).map(x -> id)
            .doOnSubscribe(s -> log("call " + id));
}

Все различия видны по тому, когда стартует вызов и когда отдаётся результат:

Параметр concurrency — главный рычаг на flatMap. По умолчанию это 256: пачка из десяти тысяч платежей превратится в 256 одновременных запросов к банку, и пул соединений WebClient или лимит банка закончатся раньше. Его ставят по возможностям того, кого вызывают: flatMap(bank::charge, 8). Как неограниченный flatMap кладёт соседний сервис, разобрано в теме Reactive Pitfalls. У flatMapSequential цена порядка — память: если p1 отвечает минуту, все остальные ответы копятся в буфере эту минуту.

Под капотом: как flatMap держит 256 подписок

flatMap — это оператор с двумя уровнями спроса. Вверх, к исходному Flux, он запрашивает concurrency элементов, по умолчанию Queues.SMALL_BUFFER_SIZE = 256, и дозапрашивает по одному, когда очередная внутренняя подписка завершилась. У каждой внутренней подписки своя очередь с prefetch 32 (Queues.XS_BUFFER_SIZE), дозапрос по 24. Элементы всех внутренних подписок отдаёт вниз один цикл drain, так что подписчик получает их последовательно, без гонок, хотя внутренние издатели работают в разных потоках. Если подписчик не успевает, очереди внутренних подписок заполняются, и они перестают запрашивать — backpressure работает и здесь (механизм спроса — в теме Reactive Philosophy).

zip ждёт всех, merge отдаёт по мере прихода, а пустой Mono молча обрывает zip

Чтобы показать карточку платежа, сервис параллельно спрашивает счёт в базе, лимиты в сервисе лимитов и вердикт антифрода. Mono.zip подписывается на всех сразу и отдаёт кортеж, когда пришли все значения. Часть 3 демо, ответы через 100, 300 и 200 мс:

Mono.zip(after(100, "accounts", "ACC-1"),
         after(300, "limits", 1000),
         after(200, "antifraud", "OK"))
    .doOnNext(t -> log("got " + t.getT1() + " limit=" + t.getT2() + " fraud=" + t.getT3()));

Mono.zip(after(100, "accounts", "ACC-1").filter(a -> false), // счёт не найден: пустой Mono
         after(300, "limits", 1000),
         after(200, "antifraud", "OK"))

Первый zip занял 300 мс — время самого медленного, а не сумму. Второй показывает ловушку: счёт не найден, Mono завершился без значения, и zip сразу отменил два других вызова и завершился пустым. Ни ошибки, ни значения: контроллер вернёт 200 с пустым телом, а в логах тишина. Так же zip реагирует на ошибку любого источника: отменяет остальных и передаёт ошибку дальше.

Пустоту делают явной оператором switchIfEmpty: accounts.find(id).switchIfEmpty(Mono.error(new AccountNotFound(id))), и тогда zip получит ошибку, а обработчик ошибок вернёт 404. Альтернатива — defaultIfEmpty(value), если есть разумное значение по умолчанию. Запасная ветка в switchIfEmpty должна быть ленивой: switchIfEmpty(Mono.just(loadFromDb())) ходит в базу при сборке, даже когда значение нашлось, поэтому пишут switchIfEmpty(Mono.defer(() -> loadFromDb())). Mono.defer откладывает создание издателя до подписки и создаёт его заново для каждой — ниже это понадобится для повторов.

merge решает другую задачу: слить несколько однотипных потоков в один, отдавая элементы по мере прихода. concat подписывается на следующий источник только после конца предыдущего. Статусы карточных платежей приходят каждые 100 мс, платежей СБП — каждые 150:

Flux.merge(cardStatuses(), sbpStatuses())            // оба источника сразу
Flux.concat(cardStatuses(), sbpStatuses())           // СБП только после конца карт

В concat часы СБП начали тикать только в 300 мс, когда закончились карты, поэтому его события сдвинулись на 300 мс. Для бесконечного первого источника concat не дойдёт до второго никогда. flatMap — это map плюс merge внутренних издателей, concatMap — map плюс concat, отсюда и их поведение во втором шаге.

Ошибка завершает поток: её заменяют, переводят на язык сервиса или повторяют новой подпиской

По контракту Reactive Streams onError — финальный сигнал. Если банк ответил 503 на втором платеже из трёх, третий уже не будет обработан. Часть 4 демо:

Flux.just("p1", "p2", "p3")
        .map(id -> { if (id.equals("p2")) throw new BankUnavailable(); return id + " paid"; })
        .subscribe(v -> System.out.println("got " + v),
                   e -> System.out.println("onError " + e.getMessage() + ", p3 never processed"));

Flux.just("p1", "p2", "p3")
        .concatMap(id -> charge(id)
                .onErrorResume(BankUnavailable.class, e -> Mono.just(id + " PENDING"))) // внутри, на один платёж
        .subscribe(v -> System.out.println("per item: " + v));

charge("p2")
        .onErrorMap(BankUnavailable.class, e -> new PaymentFailed("payment p2 failed", e)) // перевод
        .subscribe(v -> { }, e -> System.out.println("onErrorMap: " + e + " cause=" + e.getCause().getMessage()));
4. Errors are terminal: resume, map, and what retry re-runs
  got p1 paid
  onError 503 from bank, p3 never processed
  per item: p1 paid
  per item: p2 PENDING
  per item: p3 paid
  onErrorMap: OperatorsDemo$PaymentFailed: payment p2 failed cause=503 from bank

Чтобы ошибка одного платежа не убивала пачку, её ловят внутри flatMap или concatMap, на уровне одного элемента. Там onErrorResume заменяет ошибку запасным издателем: платёж p2 получил статус PENDING, сверка разберётся с ним позже, а p3 прошёл. Если поставить onErrorResume снаружи, после concatMap, он заменит ошибку, но поток всё равно закончится на p2. onErrorReturn(value) — то же с готовым значением. onErrorMap не спасает поток, а переводит ошибку: наружу уходит доменное PaymentFailed с исходной причиной внутри, и обработчик в контроллере не знает про HTTP-клиент банка. Для логирования без изменений есть doOnError.

Существует ещё onErrorContinue: он пропускает упавший элемент и продолжает поток. Он работает только с операторами, которые его поддерживают, передаётся вверх по цепочке через Context и меняет поведение операторов, которых ты не видишь в этом месте кода. Javadoc называет его оператором для специалистов с запутанным поведением и советует onErrorResume внутри flatMap — как выше.

Повтор — это новая подписка

retry(n) при ошибке подписывается на источник заново. Повторится ровно то, что выполняется при подписке. Сравни два способа обернуть асинхронный клиент банка, который возвращает CompletableFuture:

Mono.fromFuture(bankAsync(futureCalls))             // CompletableFuture создан один раз, при сборке
        .retry(2)
Mono.fromFuture(() -> bankAsync(supplierCalls))     // новый вызов на каждую подписку
        .retry(2)
  fromFuture(cf).retry(2): bank calls = 1
  fromFuture(() -> cf).retry(2): bank calls = 3

В первом варианте вызов банка сделан при сборке, и обе повторные подписки получили тот же упавший future. В логах будут три ошибки, но банк видел один запрос. Во втором Reactor вызывает поставщика на каждую подписку, и повторы настоящие. Это то же правило ленивости, что с Mono.just: повторяемый вызов создают внутри Mono.defer, fromCallable, fromFuture(Supplier) или он сам возвращает ленивый Mono, как WebClient.

retryWhen с backoff повторяет только временные ошибки, а место timeout решает, что он ограничивает

Голый retry(3) повторяет сразу и на любую ошибку: банк, который лёг под нагрузкой, получит тройную волну запросов без паузы, а ошибка «недостаточно средств» будет повторена трижды. Для сетевых вызовов берут retryWhen со стратегией Retry.backoff: пауза растёт вдвое после каждой попытки, и повторяются только ошибки из фильтра. Часть 5 демо:

Retry retry = Retry.backoff(3, Duration.ofMillis(100)) // до 3 повторов, первая пауза 100 мс
        .jitter(0)                                       // только для воспроизводимости демо
        .filter(e -> e instanceof BankUnavailable || e instanceof TimeoutException);

flakyBank(attempts, 2, 0).retryWhen(retry)            // банк дважды отвечает 503
flakyBank(attempts, 99, 0).retryWhen(retry)           // банк лежит
flakyBank(attempts, 0, 5_000)                         // банк висит 5 с
        .timeout(Duration.ofSeconds(1)).retryWhen(retry) // timeout на каждую попытку
flakyBank(attempts, 0, 5_000)
        .retryWhen(retry).timeout(Duration.ofSeconds(1)) // timeout на всю операцию

Паузы 100, 200, 400 мс: каждая вдвое длиннее предыдущей. backoff(3, …) — это три повтора, то есть четыре попытки, после чего приходит RetryExhaustedException с исходной ошибкой в cause; проверяют её через Exceptions.isRetryExhausted(e), а свою ошибку вместо неё задают onRetryExhaustedThrow. В проде jitter оставляют по умолчанию, 0,5: каждая пауза случайно отклоняется до половины своей длины, и тысяча клиентов, упавших одновременно, не придут к банку одной волной. Верхнюю границу паузы задаёт maxBackoff.

timeout ограничивает время от подписки до первого элемента и между элементами того участка цепочки, который стоит выше него. Поставленный до retryWhen, он ограничивает одну попытку, и его TimeoutException попадает в фильтр повторов. Поставленный после, он ограничивает всю операцию вместе с паузами, и повторов не будет вовсе, если первая попытка висит дольше. На практике ставят оба: короткий на попытку и общий на весь вызов, меньше таймаута клиента, который ждёт ответа сервиса.

Когда timeout срабатывает, он отменяет подписку выше себя: WebClient закрывает соединение. Банк при этом мог уже принять запрос и провести списание. Повтор такого запроса без ключа идемпотентности — двойное списание. Это не особенность Reactor, а свойство любого повтора; как его делают безопасным, разобрано в теме HTTP Clients.

cache, share и replay решают, сколько раз выполнится источник, а Sinks кладут в поток события извне

Каждая подписка на cold-издатель выполняет его заново (тема Reactive Philosophy). Иногда это нужно, как в retry, а иногда нет: токен от сервера авторизации банка живёт пять минут, и запрашивать его на каждый платёж незачем. Часть 6 демо: первый вызов сервера авторизации падает, следующие успешны.

Mono<String> cachedForever = token.cache();         // запоминает первый результат навсегда
Mono<String> cachedValuesOnly = token.cache(
        v -> Duration.ofMinutes(5),                  // значение живёт 5 минут
        e -> Duration.ZERO,                          // ошибку не кешируем
        () -> Duration.ZERO);                        // пустой результат тоже
6. cache, share, replay, Sinks

  cache(): second -> auth server 503, auth calls = 1
  cache(ttl): first  -> auth server 503
  cache(ttl): second -> token-2
  cache(ttl): third  -> token-2, auth calls = 2

cache() без аргументов запоминает первый сигнал любого вида — и значение, и ошибку — навсегда. Временный сбой сервера авторизации при старте превратился в вечную ошибку: все платежи получают 503, хотя сервер давно поднялся, и помогает только перезапуск. Версия с TTL на каждый вид сигнала кеширует только успех и только на время жизни токена.

share() решает другую задачу: несколько подписчиков одновременно читают один и тот же бесконечный источник. Например, один цикл опроса статусов у банка на всех клиентов, подписанных на обновления. Это сокращение для publish().refCount(): первый подписчик запускает источник, остальные подключаются к идущему потоку, последний отписавшийся его останавливает.

Flux<String> statuses = Flux.interval(Duration.ofMillis(100)).map(i -> "status-" + i)
        .doOnSubscribe(s -> log("polling started"))
        .doOnCancel(() -> log("polling stopped"))
        .share();

  t=1650    late got status-2

B подключился к идущему опросу и получил status-1, а status-0 пропустил: share делает поток hot. Когда A и B забрали своё и отписались, опрос остановился, а C запустил его заново с нуля. Если опоздавшему нужно последнее известное значение, берут replay(n): он хранит n последних элементов и отдаёт их каждому новому подписчику, а autoConnect() запускает источник при первом подписчике и не останавливает при уходе последнего.

Sinks: события снаружи

Все издатели выше берут данные из источника, на который подписываются. Бывает наоборот: события рождаются в обычном коде — в обработчике сообщения Kafka, в колбэке старой библиотеки, — и их нужно отдать в реактивный поток. Для этого есть Sinks: объект, в который пишут tryEmitNext, а читают через asFlux() или asMono(). Вариант выбирается при создании, и от него зависит, что будет с событием, если подписчиков нет или они не успевают:

  multicast().directBestEffort(), no subscribers: FAIL_ZERO_SUBSCRIBER
  multicast().onBackpressureBuffer(), no subscribers: OK
  buffered first subscriber got e1
  unicast, second subscriber: Sinks.many().unicast() sinks only allow a single Subscriber
ВариантПодписчиковЕсли подписчика нет или он не успевает
Sinks.one(), Sinks.empty()сколько угодноодно значение или только завершение, запоминается для поздних

tryEmitNext не бросает исключений, а возвращает EmitResult, и его надо проверять: FAIL_ZERO_SUBSCRIBER, FAIL_OVERFLOW, FAIL_TERMINATED или FAIL_NON_SERIALIZED. Последний означает, что два потока пишут в Sink одновременно: Sink, как любой издатель, обязан отдавать сигналы последовательно (правило 1.3), поэтому второй вызов не ждёт, а сразу проваливается. Если писателей несколько, вызывают emitNext(value, EmitFailureHandler.busyLooping(Duration.ofMillis(100))): он повторяет попытку, пока другой поток не закончит.

StepVerifier проверяет сигналы по порядку, а виртуальное время прокручивает минуты ожидания мгновенно

Проверять реактивный код через block() в тесте неудобно: видно только последнее значение, а не сигналы, и любая задержка становится настоящим ожиданием. Для тестов есть StepVerifier из модуля reactor-test: он подписывается на издатель и сверяет каждый сигнал со сценарием. Часть 7 демо:

StepVerifier.create(Flux.just("p1", "p3").flatMap(OperatorsDemo::charge))
        .expectNext("p1 paid", "p3 paid")
        .verifyComplete();                           // подписаться, проверить и дождаться onComplete

StepVerifier.create(Flux.just("p1", "p2", "p3").flatMap(OperatorsDemo::charge)) // p2 падает
        .expectNext("p1 paid", "p3 paid")
        .verifyComplete();
7. StepVerifier
  plain test passed
  failed test: expectation "expectNext(p3 paid)" failed (expected: onNext(p3 paid); actual: onError(OperatorsDemo$BankUnavailable: 503 from bank))

Сообщение называет сигнал, который пришёл вместо ожидаемого: не «тест упал», а «ждал onNext(p3 paid), получил onError». Ошибку проверяют так же явно: expectErrorMatches(e -> e instanceof PaymentFailed) или verifyError(PaymentFailed.class). verify…() возвращает Duration — сколько шла проверка.

Retry из прошлого шага с паузами в минуты тестировать честным временем нельзя. StepVerifier.withVirtualTime устанавливает VirtualTimeScheduler вместо всех планировщиков Reactor на время теста: Mono.delay, timeout, паузы backoff встают в очередь виртуальных часов, а thenAwait их прокручивает.

static Mono<String> chargeWithRetry(AtomicInteger attempts) {
    return flakyBank(attempts, 2, 0)                // две ошибки, потом успех
            .retryWhen(Retry.backoff(3, Duration.ofMinutes(1)).jitter(0)); // паузы 1 и 2 минуты
}

StepVerifier.withVirtualTime(() -> chargeWithRetry(attempts)) // Mono создаётся внутри поставщика
        .expectSubscription()
        .expectNoEvent(Duration.ofMinutes(1))        // первая пауза: ни одного сигнала
        .thenAwait(Duration.ofMinutes(2))            // вторая пауза
        .expectNext("paid")
        .verifyComplete();

Mono<Long> assembledOutside = Mono.delay(Duration.ofMinutes(1)); // собран ДО withVirtualTime
StepVerifier.withVirtualTime(() -> assembledOutside)
        .expectSubscription()
        .thenAwait(Duration.ofMinutes(2))
        .expectNext(0L)
        .expectComplete()
        .verify(Duration.ofSeconds(2));              // без лимита ждал бы настоящую минуту
  t=0    attempt 1
  t=60000 attempt 2
  t=180000 attempt 3
  virtual-time test passed: 3 min of backoff, attempts = 3, real time < 1 s: true
  assembled outside supplier: VerifySubscriber timed out on reactor.core.publisher.MonoDelay$MonoDelayRunnable

Три минуты пауз прошли за доли секунды, а попытки легли ровно на 0, 60 000 и 180 000 мс виртуального времени. Второй тест показывает главную ловушку: Mono.delay(Duration) берёт планировщик Schedulers.parallel() в момент сборки. Собранный до withVirtualTime, он уже держит настоящий планировщик, и виртуальные часы его не касаются. Поэтому издатель создают внутри лямбды-поставщика, а verify(Duration) ставят, чтобы зависший тест падал, а не висел.

Ещё два инструмента из того же модуля. TestPublisher — управляемый источник: тест сам решает, когда отдать элемент или ошибку, и может нарушить спецификацию, чтобы проверить свой оператор. PublisherProbe отвечает на вопрос «была ли подписка на эту ветку»: например, что при найденном в кеше платеже запасной поход в базу через switchIfEmpty не случился.

  • Функция вернула Mono или Flux — нужен flatMap: map отдаст рецепт вызова, на который никто не подпишется.
  • flatMap запускает до 256 вызовов и отдаёт ответы по мере прихода; concatMap — по одному, по порядку; flatMapSequential — параллельно, но держит готовые ответы в буфере ради порядка. concurrency ставят по возможностям вызываемого.
  • zip ждёт самого медленного, отменяет остальных при ошибке и молча завершается пустым, если пуст любой источник; switchIfEmpty делает пустоту явной.
  • Ошибка завершает поток. Ошибку одного элемента ловят внутри flatMap; retry — это новая подписка, поэтому повторяемый вызов должен создаваться при подписке.
  • Retry.backoff с фильтром временных ошибок и jitter; timeout до retryWhen ограничивает попытку, после — всю операцию. Повтор списания безопасен только с идемпотентностью.
  • cache() запоминает и ошибку навсегда; share раздаёт один идущий поток, replay — ещё и последние значения; Sinks превращают события из обычного кода в поток. Тесты — StepVerifier, задержки — withVirtualTime с издателем внутри поставщика.

На собеседовании

Чем map отличается от flatMap? А flatMap от concatMap?

map синхронно превращает элемент в другое значение. flatMap принимает функцию, которая возвращает издатель, подписывается на каждый такой издатель и сливает их элементы в один поток. Если вызвать через map метод, который возвращает Mono, получится поток из Mono, и вызов не выполнится — на него никто не подписан.

flatMap запускает внутренние подписки параллельно, до 256 по умолчанию, и отдаёт результаты по мере прихода, поэтому порядок не сохраняется. concatMap подписывается по одному и сохраняет порядок, но медленнее. Если нужны и параллельность, и порядок, беру flatMapSequential: он держит готовые результаты в буфере, пока не придёт предыдущий.

  • Параметр concurrency у flatMap — ограничение нагрузки на вызываемый сервис; 256 по умолчанию обычно больше, чем пул соединений WebClient или лимит партнёра.
  • flatMap = map + merge, concatMap = map + concat. Внутренний prefetch у flatMap — 32 элемента на подписку.
  • У flatMapSequential цена порядка — память: один медленный элемент держит в буфере все готовые после него.
Как ограничить число одновременных вызовов банка до 8?

Вторым аргументом flatMap: ids.flatMap(bank::charge, 8). Тогда flatMap запросит у источника 8 элементов и будет брать следующий, только когда закончится один из вызовов. Если порядок важен — flatMapSequential(bank::charge, 8). Ограничение пулом соединений WebClient тоже сработает, но тогда лишние запросы будут ждать в очереди пула и упираться в её таймаут, а не в понятный лимит в коде.

Как сделать повтор с backoff и timeout в Reactor?

Через retryWhen(Retry.backoff(3, Duration.ofMillis(100))): три повтора с паузой, которая растёт вдвое, плюс случайный jitter, чтобы клиенты не пришли к сервису одной волной. Обязательно filter: повторяю только временные ошибки — 503, таймауты, обрыв соединения, — а не 400 или «недостаточно средств». После исчерпания приходит RetryExhaustedException с исходной ошибкой в cause.

timeout ставлю до retryWhen, чтобы ограничить одну попытку, и ещё один после — на всю операцию. Повтор — это новая подписка, поэтому вызов должен создаваться при подписке: Mono из WebClient или Mono.defer, а не готовый CompletableFuture.

  • Повтор неидемпотентного запроса опасен: timeout отменил ожидание, но банк мог провести платёж. Нужен ключ идемпотентности.
  • maxBackoff ограничивает рост паузы; onRetryExhaustedThrow заменяет RetryExhaustedException своей ошибкой; Exceptions.isRetryExhausted проверяет её тип.
  • Сумма пауз и таймаутов попыток должна укладываться в таймаут того, кто ждёт сервис, иначе повторы идут для клиента, который уже ушёл.
Что не так с этим повтором? 
Mono<Receipt> charge(Payment p) {
    return Mono.fromFuture(bankClient.chargeAsync(p))
            .retryWhen(Retry.backoff(5, Duration.ofSeconds(1)))
            .timeout(Duration.ofSeconds(2));
}

Три проблемы. CompletableFuture создан при сборке, поэтому повторы переподписываются на тот же упавший future, и банк видит один запрос. Фильтра нет, и ошибки вроде 400 тоже повторяются. timeout стоит после retryWhen и ограничивает всё двумя секундами, а первая же пауза — секунда, так что до третьей попытки дело не дойдёт. Исправление: Mono.fromFuture(() -> bankClient.chargeAsync(p, idempotencyKey)), .timeout(…) на попытку до retryWhen, filter для временных ошибок и общий timeout после, длиннее суммы попыток и пауз.

Чем cache отличается от share? Когда нужен Sinks?

Обычный Mono или Flux холодный: каждая подписка выполняет его заново. cache() выполняет источник один раз и отдаёт сохранённый результат всем следующим подписчикам, как бы поздно они ни пришли. share() делает один общий горячий поток: первый подписчик его запускает, остальные подключаются к идущему и получают только новые элементы, а когда все отписались, источник останавливается.

Sinks нужен, когда события рождаются не в реактивном источнике, а в обычном коде — колбэк, слушатель сообщений, — и их надо отдать подписчикам Flux. Я пишу в Sink через tryEmitNext и проверяю EmitResult.

  • cache() запоминает и ошибку, навсегда. Для токенов и справочников беру cache с TTL отдельно для значения, ошибки и пустоты.
  • share() = publish().refCount(); replay(n).autoConnect() хранит последние n значений для поздних подписчиков и не останавливается.
  • Sink, как любой издатель, отдаёт сигналы последовательно: конкурентная запись даёт FAIL_NON_SERIALIZED, для нескольких писателей нужен emitNext с EmitFailureHandler.busyLooping.

Как тестировать реактивный код, особенно с задержками и повторами?

StepVerifier из reactor-test: он подписывается и проверяет сигналы по порядку — expectNext, expectError, verifyComplete. Если пришёл не тот сигнал, сообщение говорит, что ожидалось и что пришло. block() в тестах не люблю: он показывает только последнее значение и прячет порядок.

Для задержек, таймаутов и backoff — StepVerifier.withVirtualTime: он подменяет планировщики Reactor виртуальными часами, и thenAwait прокручивает минуты мгновенно. Тест на retry с паузами в минуты идёт доли секунды.

  • Издатель создаётся внутри поставщика withVirtualTime: Mono.delay и interval берут планировщик при сборке, и собранный снаружи будет ждать настоящее время.
  • verify(Duration) — страховка от зависшего теста; expectNoEvent проверяет, что во время паузы не было сигналов.
  • TestPublisher — управляемый источник, PublisherProbe — проверка, что ветка switchIfEmpty или fallback была (или не была) подписана.
  • Reactor Reference Guide — основа урока: Which operator do I need?, Handling Errors (retry, retryWhen, onErrorContinue), Testing (StepVerifier, virtual time, PublisherProbe), Sinks.
  • Reactor Core javadoc — мраморные диаграммы операторов flatMap, concatMap, flatMapSequential, zip, cache, share, а также Retry.backoff и RetryBackoffSpec.
  • Исходники reactor-core — FluxFlatMap (concurrency и prefetch), MonoCacheTime, SinkManyMulticast.
