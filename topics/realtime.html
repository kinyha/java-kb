API: Real-time

HTTP устроен так, что спрашивает клиент, а сервер отвечает. Чтобы сервер сообщил о событии сам, есть четыре способа. Short polling — спрашивать по таймеру: просто, но с задержкой и лишней нагрузкой. Long polling — сервер держит запрос, пока не появится событие. Server-Sent Events — один долгий HTTP-ответ, в который сервер дописывает события, а браузер сам переподключается и продолжает с последнего id. WebSocket — постоянное двустороннее соединение для чатов и совместного редактирования. Чем живее соединение, тем больше забот: переподключение, пропущенные события, балансировка и рассылка между экземплярами сервиса.

Экран платежа должен обновиться сам, когда банк подтвердил списание

Пользователь оплатил заказ и смотрит на экран «Платёж обрабатывается». Банк подтверждает списание через секунду или через минуту. Экран должен смениться на «Оплачено» сразу, без кнопки «Обновить». А у оператора поддержки открыта панель, где появляются новые платежи и куда он пишет комментарии, которые видят коллеги.

В обычном REST клиент узнаёт о состоянии, только когда спросит; ресурс операции из REST честно говорит «спросите позже». Тема разбирает, как сервер может сообщить о событии сам, чем способы отличаются по задержке, нагрузке и надёжности, и что ломается при масштабировании. Демо RealtimeDemo.java поднимает на встроенном HttpServer long polling и SSE и обрывает поток посередине, чтобы показать продолжение: java RealtimeDemo.java на JDK 21.

Long polling держит запрос, пока не появится событие

Short polling спрашивает по таймеру: раз в 2 секунды GET /payments/p-1. Задержка — до целого интервала, а почти все запросы возвращают «ничего не изменилось». 100 тысяч открытых экранов — 50 тысяч запросов в секунду ради нескольких событий. Уменьшить интервал — больше нагрузки, увеличить — больше задержки.

Long polling меняет одну вещь: сервер не отвечает сразу, а ждёт, пока появится событие новее того, что клиент уже видел, или пока не истечёт таймаут. Клиент передаёт курсор — номер последнего увиденного события — и сразу после ответа отправляет следующий запрос:

// Сервер: ждёт события новее after не дольше 500 мс.
int last = awaitAfter(after, 500);
if (last == after) { ex.sendResponseHeaders(204, -1); return; }   // Ничего нового — 204.
send(ex, String.join(",", events.subList(after, last)) + " (next after=" + last + ")");
== long polling
GET /poll?after=0 -> 200 after ~0 ms AUTHORIZED (next after=1)
GET /poll?after=1 -> 200 after ~200 ms CAPTURED (next after=2)
GET /poll?after=2 -> 204 after ~500 ms

Первый запрос получил уже случившееся событие сразу. Второй ждал 200 мс и вернулся в момент, когда платёж списали, — задержка близка к нулю. Третий не дождался ничего и через 500 мс вернул 204, после чего клиент спросит снова. Курсор важен: событие, случившееся между двумя запросами, не потеряется, потому что следующий запрос попросит всё после after=2.

Цена — запрос, который висит на сервере. С пулом из 200 потоков Tomcat 200 ждущих клиентов занимают весь пул; поэтому long polling делают асинхронно (DeferredResult в Spring MVC) или на виртуальных потоках, как в демо. Таймаут держат меньше, чем у прокси и балансировщиков по пути, иначе они оборвут запрос раньше сервера: у nginx по умолчанию 60 секунд.

SSE — один долгий ответ, в который сервер дописывает события

Server-Sent Events — стандарт из HTML Living Standard. Клиент делает обычный GET, сервер отвечает Content-Type: text/event-stream и не закрывает ответ, а дописывает в него события в текстовом формате. Каждое событие — несколько строк поле: значение и пустая строка в конце:

retry: 1000           ← через сколько мс переподключаться при обрыве

id: 3                 ← номер события, браузер его запомнит
event: status         ← тип события
data: SETTLED         ← данные; несколько строк data склеиваются

В браузере это new EventSource("/stream"). Главное его свойство — встроенное переподключение: при обрыве браузер подождёт retry и сам повторит запрос с заголовком Last-Event-ID, а сервер продолжит с этого места. Демо обрывает поток после третьего события и подключается снова, как сделал бы браузер:

String lastSeen = readStream(client, base, null, 3);  // Читаем три события и рвём соединение.
readStream(client, base, lastSeen, 99);              // Новый запрос с Last-Event-ID.

// Сервер начинает с события после присланного id.
String lastId = ex.getRequestHeaders().getFirst("Last-Event-ID");
int sent = lastId == null ? 0 : Integer.parseInt(lastId);
== server-sent events
event id=1 data: AUTHORIZED
event id=2 data: CAPTURED
event id=3 data: SETTLED
-- reconnect with Last-Event-ID: 3
event id=4 data: REFUND_PENDING

Событие REFUND_PENDING появилось, пока клиента не было, и он его получил: продолжение работает, потому что сервер хранит журнал событий с номерами. Если сервер помнит только текущее состояние, переподключившийся клиент пропустит всё, что случилось в разрыве. Поэтому id события — позиция в журнале или в топике Kafka, а не случайное число.

Ловушки SSE в основном инфраструктурные. Прокси и сжатие любят буферизовать ответ, и события приходят пачкой через минуту: в nginx для потока выключают буфер (X-Accel-Buffering: no), а сервер вызывает flush после каждого события. Простаивающее соединение обрывают по таймауту, поэтому сервер раз в 15–30 секунд шлёт комментарий-пульс : ping. В браузере по HTTP/1.1 на один домен не больше шести соединений, и седьмая вкладка с SSE зависнет; с HTTP/2 потоки идут по одному соединению. SSE — только от сервера к клиенту и только текст; команды клиент отправляет обычными запросами. В Spring это SseEmitter в MVC или Flux<ServerSentEvent> в WebFlux.

WebSocket — двусторонний канал, но переподключение и продолжение приходится писать самим

WebSocket начинается как HTTP-запрос с заголовками Upgrade: websocket и Connection: Upgrade. Сервер отвечает 101 Switching Protocols, и дальше TCP-соединение несёт уже не HTTP, а кадры WebSocket в обе стороны: текст, бинарные данные, ping и pong. Задержка минимальна, накладных заголовков на сообщение почти нет. Это то, что нужно чату, совместному редактированию, торговому терминалу, игре.

За гибкость платят тем, что WebSocket — низкоуровневый канал. В нём нет встроенного переподключения, номеров сообщений и продолжения с места обрыва, как в SSE: всё это пишут сами или берут протокол поверх. Обрыв на мобильной сети — обычное дело, и без своего механизма клиент молча пропустит события. Нет и семантики HTTP внутри канала: кодов ответа, кеширования, привычных метрик по запросам. Spring поддерживает WebSocket напрямую и протокол STOMP поверх него с подписками на темы.

Аутентификация делается при рукопожатии: браузерный API не позволяет добавить заголовок Authorization, поэтому используют cookie или короткоживущий токен в первом сообщении. Сервер обязан проверять заголовок Origin: браузер отправит cookie на WebSocket и с чужой страницы, и без проверки это атака Cross-Site WebSocket Hijacking. А токен, проверенный при подключении, может истечь, пока соединение живёт часами, — права приходится перепроверять.

Долгие соединения меняют масштабирование: рассылка между экземплярами и шторм переподключений

Сто тысяч открытых экранов — сто тысяч одновременных соединений, каждое со своими буферами и состоянием. Для этого нужен неблокирующий сервер или виртуальные потоки, а не поток платформы на соединение. Но главное — соединение привязано к одному экземпляру сервиса. Банк подтвердил платёж, событие обработал экземпляр A, а клиент подключён к экземпляру B. Поэтому события раздают через общий канал — Redis Pub/Sub, топик Kafka, брокер для STOMP, — и каждый экземпляр пересылает своим клиентам то, что им адресовано.

Деплой обрывает все соединения экземпляра разом, и тысячи клиентов одновременно переподключаются к оставшимся — шторм переподключений. Клиенты ждут перед повтором случайную задержку с экспоненциальным ростом, а сервер при остановке закрывает соединения постепенно. Балансировщик должен поддерживать долгие соединения и Upgrade, а его таймаут простоя — быть больше интервала пульса.

Для обновлений в реальном времени всегда нужен WebSocket.

Большинству экранов нужен поток только от сервера: статус платежа, уведомления, лента. SSE работает поверх обычного HTTP, сам переподключается и продолжает с последнего события. WebSocket оправдан, когда клиент часто пишет в тот же канал, и тогда переподключение и продолжение придётся строить самим.

Если событие должно дойти, даже когда экран закрыт, ни один из способов не подходит: соединения нет. Тогда нужны push-уведомления через APNs и FCM или вебхук для серверных клиентов.

  • Short polling — задержка до интервала и пустые запросы; long polling держит запрос до события или таймаута и передаёт курсор.
  • SSE — text/event-stream с id, event, data, retry; браузер переподключается с Last-Event-ID, в демо событие из разрыва дошло.
  • Продолжение работает, только если сервер хранит журнал событий с номерами.
  • WebSocket — двусторонний канал без встроенного переподключения; проверка Origin и токена обязательна.
  • Долгие соединения требуют рассылки между экземплярами через общий канал и защиты от шторма переподключений.

На собеседовании

Чем отличаются long polling, SSE и WebSocket и что когда выбрать?

Long polling — обычный запрос, который сервер держит, пока не появится событие или не истечёт таймаут; клиент сразу шлёт следующий с курсором. SSE — один долгий HTTP-ответ text/event-stream, в который сервер дописывает события; только от сервера к клиенту, браузер сам переподключается с Last-Event-ID. WebSocket — после рукопожатия 101 двусторонний канал кадров поверх TCP.

Для статусов и уведомлений хватает SSE. WebSocket — когда клиент часто пишет в тот же канал: чат, совместное редактирование. Long polling — запасной вариант, когда потоковые ответы режет инфраструктура.

  • В WebSocket нет встроенного продолжения после обрыва: номера сообщений и догрузку пропущенного пишут сами.
  • SSE ломают буферизующие прокси; нужны flush, X-Accel-Buffering: no и пульс-комментарии.
  • По HTTP/1.1 браузер держит не больше шести соединений на домен, HTTP/2 снимает ограничение для SSE.

Как масштабировать WebSocket или SSE на несколько экземпляров сервиса?

Соединение живёт на одном экземпляре, а событие может произойти на другом. Поэтому события публикуют в общий канал — Redis Pub/Sub, Kafka, брокер сообщений, — и каждый экземпляр пересылает своим подключённым клиентам. Балансировщик должен поддерживать долгие соединения и Upgrade.

  • Деплой рвёт все соединения экземпляра: клиенты переподключаются со случайной экспоненциальной задержкой, сервер закрывает соединения постепенно.
  • Чтобы переподключившийся клиент догрузил пропущенное, события хранят в журнале с номерами, а не только рассылают.
  • Сотни тысяч соединений требуют неблокирующего сервера или виртуальных потоков.
Почему клиенты иногда не видят смену статуса? 
@GetMapping("/payments/{id}/events")
SseEmitter events(@PathVariable String id) {
    var emitter = new SseEmitter(0L);
    emitters.put(id, emitter);              // Локальная Map в этом экземпляре.
    return emitter;
}

@KafkaListener(topics = "payment-status", groupId = "notifier")
void onStatus(PaymentStatus s) {
    var e = emitters.get(s.paymentId());
    if (e != null) e.send(SseEmitter.event().data(s.status()));
}

Все экземпляры в одной группе потребителей, поэтому каждое событие получает только один из них, а клиент может быть подключён к другому — событие теряется. Нужно, чтобы каждый экземпляр получал все события: отдельная группа на экземпляр или Redis Pub/Sub. Кроме того, у событий нет id, и после обрыва клиент не догрузит пропущенное; emitter не удаляется из Map при завершении и ошибке, и Map растёт.

Какие особенности безопасности у WebSocket?

Аутентификация — при рукопожатии: браузерный API не даёт задать Authorization, поэтому используют cookie или токен в первом сообщении. Сервер проверяет заголовок Origin, иначе чужая страница откроет соединение с cookie пользователя — Cross-Site WebSocket Hijacking.

  • Соединение живёт часами, а токен истекает и права меняются: их перепроверяют или рвут соединение по сроку токена.
  • Входящие сообщения валидируют и ограничивают по размеру и частоте, как обычные запросы.
  • HTML Living Standard: Server-sent events — основа урока о SSE: формат потока, retry, Last-Event-ID.
  • RFC 6455: The WebSocket Protocol — рукопожатие, кадры, проверка Origin.
  • RFC 6202: Known Issues and Best Practices for the Use of Long Polling and Streaming — long polling и потоковые ответы через прокси.
  • Spring Framework: WebSockets — WebSocket, SockJS и STOMP в Spring.
