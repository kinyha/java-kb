Records

Record объявляет данные через компоненты и связывает с ними конструктор, доступ и равенство. Поля нельзя переназначить, но объект, на который ссылается компонент, может меняться. Надёжный record начинается с решения о владении данными: какие значения допустимы, что нужно скопировать и что должно считаться равным.

Final-ссылка не спасает ключ от изменения hashCode

Пачку платежей положили в HashSet, чтобы не обработать её повторно. DTO объявлен как record, сеттеров нет. Но после добавления id во входной список тот же объект перестал находиться в наборе. Размер набора остался один: потерялся не объект, а возможность найти его по новому hashCode.

В AliasingDemo.java record хранит ссылку на переданный список. Его сгенерированный hashCode зависит от hashCode списка, а список считает хеш по элементам. При вставке HashSet запомнил старый хеш; при поиске вычислил новый. Record запретил заменить поле ids, но не запретил изменить список через другую ссылку.

// Фрагмент AliasingDemo.java; запуск на JDK 21 из корня проекта:
// java examples/records/AliasingDemo.java
record BadBatch(List<String> ids) {}
List<String> input = new ArrayList<>(List.of("p1"));
BadBatch bad = new BadBatch(input);
Set<BadBatch> keys = new HashSet<>();
keys.add(bad);
System.out.println("before: " + keys.contains(bad));
input.add("p2"); // изменился компонент, а с ним хеш уже вставленного ключа
System.out.println("after: " + keys.contains(bad) + ", size=" + keys.size());
before: true
after: false, size=1

Record полезен для значения, определяемого компонентами: команды платежа, результата расчёта, строки отчёта. Он делает этот контракт видимым и убирает повторяющийся код. Если компонент сам не имеет стабильной семантики значения, короткая запись не исправит модель. Поэтому вопрос «immutable ли record» начинается с графа объектов, а не с наличия final.

Заголовок record задаёт состояние и публичный контракт

Объявление record Receipt(String id, long minorUnits) обещает, что Receipt — значение из id и minorUnits. Компилятор создаёт отдельный класс со своим типом; это не анонимный tuple. В Java 16 records стали постоянной возможностью языка; примеры этой темы используют Java 21 без preview.

Каждый компонент даёт private final поле и public accessor с тем же именем: id(), а не getId(). Canonical constructor принимает все компоненты в порядке заголовка. Если ты не написал нужный метод сам, компилятор добавляет equals, hashCode и toString, основанные на компонентах. Два Receipt с одинаковыми компонентами равны через equals, хотя это два разных объекта.

// Фрагмент RecordsDemo.java; java examples/records/RecordsDemo.java
record Receipt(String id, long minorUnits) {}
Receipt a = new Receipt("p1", 100), b = new Receipt("p1", 100);
System.out.println("identity=" + (a == b) + ", equals=" + a.equals(b));
System.out.println(a);
Class<?> type = Receipt.class;
System.out.println("record=" + type.isRecord()
        + ", final=" + Modifier.isFinal(type.getModifiers()));
System.out.println("parent=" + type.getSuperclass().getName());
identity=false, equals=true
Receipt[id=p1, minorUnits=100]
record=true, final=true
parent=java.lang.Record

У record уже есть родитель java.lang.Record, а сам класс неявно final. Наследоваться от другого класса или сделать подкласс такого DTO нельзя. Можно реализовывать интерфейсы, объявлять методы поведения и static-члены, использовать generics. Но нельзя добавить ещё одно instance-поле, не отражённое в компонентах: скрытый изменяемый кеш разрушал бы обещание заголовка о состоянии.

На Java 21 это обычный ссылочный объект: new создаёт экземпляр, == проверяет идентичность, equals — value-контракт. Record не означает автоматическое размещение на стеке или отсутствие allocation. JIT может устранить отдельное выделение при escape analysis, как и для обычного класса; обещанием языка это не становится.

Reflection видит компоненты через getRecordComponents(), их типы и методы доступа. Даже после setAccessible(true) изменение final-поля record через Field.set в нашем опыте бросает IllegalAccessException. Это дополнительное ограничение reflective API, а не доказательство, что весь граф объектов immutable.

Под капотом: класс, метаданные и сгенерированные методы

В class-файле есть метаданные Record с описанием компонентов, отдельные поля и методы. Javap на JBR 21.0.11 показывает вызовы invokedynamic для сгенерированных equals/hashCode/toString; реализация связывается через java.lang.runtime.ObjectMethods. Точный алгоритм hashCode и порядок сравнения компонентов не являются переносимым обещанием API, поэтому их нельзя использовать как формат хранения или криптографический отпечаток.

Аннотация компонента переносится на поле, неявный accessor и параметр конструктора только там, где допускает её Target. У явно написанного accessor аннотации компонента автоматически не появляются. Наличие аннотации в DTO само по себе не запускает Bean Validation: кто и когда вызывает валидатор, разобрано в Validation & Errors.

Compact constructor сначала обрабатывает параметры, потом заполняет поля

Canonical constructor — путь, который устанавливает все компоненты. Его можно написать полностью с параметрами и присваиваниями. Compact constructor сокращает именно эту форму: параметры не повторяются в заголовке, а их присваивания в поля компилятор дописывает после успешного выполнения тела.

Внутри compact constructor имя id обозначает параметр. Можно проверить его и заменить нормализованным значением. Вызов id() уже читает поле объекта, которое пока содержит значение по умолчанию. Поэтому нормализацию и проверку проводят по параметрам, а методы, ожидающие готовый объект, вызывают после завершения конструирования.

// Фрагмент RecordsDemo.java; полный файл содержит imports и main
record Normalized(String id) {
    Normalized {
        id = Objects.requireNonNull(id).strip().toUpperCase(Locale.ROOT);
        System.out.println("constructor: param=" + id + ", accessor=" + id());
        if (id.isEmpty()) throw new IllegalArgumentException("empty id");
    } // здесь компилятор неявно присвоит this.id = id
    Normalized() { this("fallback"); } // дополнительный конструктор ведёт к canonical
}
Normalized n = new Normalized(" p1 ");
System.out.println("after constructor=" + n.id());
constructor: param=P1, accessor=null
after constructor=P1

В compact constructor нельзя вручную присваивать this.id: этот режим резервирует присваивания за компилятором. В полной canonical-форме, наоборот, поля нужно установить самому. Права доступа canonical constructor не могут быть уже прав самого record: для public record нужен public canonical constructor, а не private фабричный путь.

Дополнительные конструкторы должны делегировать через this к другому конструктору этого record, в итоге к canonical. Это сохраняет общий путь установления компонентов. Делать валидацию только в статической фабрике недостаточно: прямой вызов new обойдёт такую фабрику. Нормализация в canonical должна сохранять смысл значения и быть повторяемой при копировании уже нормализованного record.

Неизменяемость определяется всеми доступными ссылками

Защита списка требует двух решений: не хранить изменяемый список вызывающего и не отдавать наружу изменяемый список своего объекта. List.copyOf в compact constructor создаёт snapshot с неизменяемой структурой. Если вход уже подходит, API может переиспользовать его; важен контракт независимости от будущих структурных изменений исходной коллекции, а не обязательное выделение памяти.

Collections.unmodifiableList(input) решает только вторую половину. Оно запрещает изменение через представление, но исходный ArrayList остаётся тем же объектом. Владельцу input ничто не мешает добавить элемент, и DTO увидит его через это представление. Для значения нужен snapshot, а не read-only окно на чужое состояние.

// Фрагмент AliasingDemo.java; исходный список здесь создаётся заново
record BadBatch(List<String> ids) {}
record Batch(List<String> ids) {
    Batch { ids = List.copyOf(ids); } // копируем до неявного присваивания полю
}
List<String> input = new ArrayList<>(List.of("p1"));
BadBatch bad = new BadBatch(input);
Batch safe = new Batch(input); // snapshot содержит только p1
input.add("p2");
System.out.println("bad=" + bad.ids() + ", safe=" + safe.ids());
// safe.ids().add("p3") бросит UnsupportedOperationException
bad=[p1, p2], safe=[p1]

Этот опыт использует String, который сам immutable. Если в списке лежит Item с изменяемым status, copyOf скопирует ссылки на Item. Вторая часть AliasingDemo меняет status исходного элемента и через accessor record видит PAID. Чтобы получить immutable граф, нужны неизменяемые элементы или копирование их состояния в другой тип.

// Фрагмент AliasingDemo.java: snapshot списка сохраняет ссылки на элементы
static final class Item { String status = "NEW"; }
record ShallowBatch(List<Item> items) {
    ShallowBatch { items = List.copyOf(items); }
}
Item item = new Item();
ShallowBatch shallow = new ShallowBatch(List.of(item));
item.status = "PAID"; // тот же Item доступен через обе ссылки
System.out.println("element status=" + shallow.items().getFirst().status);
element status=PAID

С массивом ситуация ещё строже: clone на входе защищает от вызывающего, но автоматически созданный accessor отдаст внутренний массив. Нужна копия и на выходе, а затем согласованная семантика equals/hashCode. Если модель допускает List неизменяемых элементов, её проще правильно реализовать, чем вручную поддерживать все обещания массива-компонента.

Любой record можно безопасно передавать между потоками и использовать ключом карты.

Это верно только при подходящих компонентах и публикации. Final-поля не синхронизируют последующие изменения вложенного ArrayList или Item. Проверяй все пути доступа к изменяемым объектам и не публикуй this из конструктора; final-field semantics подробно разобраны в JMM.

Равенство компонентов наследует их собственные правила

Сгенерированный equals требует тот же record-класс и равные соответствующие компоненты. Для reference-компонента семантика соответствует Objects.equals, включая null; для primitive-компонента — сравнению соответствующего wrapper. Массив не переопределяет equals по содержимому, поэтому одинаковые числа в двух разных int[] не делают два ArrayKey равными.

// Фрагмент EqualityDemo.java; java examples/records/EqualityDemo.java
record ArrayKey(int[] values) {}
record ListKey(List<Integer> values) {
    ListKey { values = List.copyOf(values); }
}
record Reading(double value) {}
record Amount(BigDecimal value) {}
System.out.println("arrays=" + new ArrayKey(new int[]{1, 2})
        .equals(new ArrayKey(new int[]{1, 2})));
System.out.println("lists=" + new ListKey(List.of(1, 2)).equals(new ListKey(List.of(1, 2))));
System.out.println("NaN=" + new Reading(Double.NaN).equals(new Reading(Double.NaN)));
System.out.println("signed zero=" + new Reading(0.0).equals(new Reading(-0.0)));
System.out.println("decimal scale=" + new Amount(new BigDecimal("1.0"))
        .equals(new Amount(new BigDecimal("1.00"))));
arrays=false
lists=true
NaN=true
signed zero=false
decimal scale=false

NaN и знаковый ноль ведут себя здесь иначе, чем при primitive ==: сравнение должно поддерживать корректный equals и согласованный hashCode. BigDecimal сохраняет своё правило равенства с учётом scale. Если бизнес считает 1.0 и 1.00 одним значением, это отдельное решение модели: нормализация в canonical или согласованное переопределение равенства, а не свойство record по умолчанию.

У record есть дополнительный copy invariant: создай новый R из значений всех accessors исходного r — полученная копия должна быть равна r. Поэтому accessor не должен незаметно менять наблюдаемое значение. Если поле хранит -10, accessor возвращает 10, а generated equals читает поле -10, реконструирование через accessor создаст другое значение.

Защитный clone массива на выходе сам по себе разумен, но вместе с generated equals по ссылке на массив нарушит этот же invariant. Для массива со сравнением по содержимому нужны одновременно Arrays.equals, Arrays.hashCode и копирование в обе стороны. Переопределять один equals без hashCode нельзя; лучше выбирать компонент с уже подходящим value-контрактом.

Сгенерированный toString печатает значения компонентов. Нельзя бездумно логировать record с токеном, PAN или персональными данными. Исключи секрет из безопасного описания либо переопредели toString. Сам record не добавляет маскировку.

Record подходит значению, а жизненному циклу нужен другой контракт

DTO результата запроса, команда, ключ со стабильными компонентами и небольшой value object хорошо совпадают с record. Их состояние задаётся при создании и читается как целое. Методы расчёта и реализации интерфейса допустимы: record не обязан быть мешком данных без поведения. Но сущность с идентичностью, изменениями и скрытым жизненным циклом — другая модель.

По контракту Jakarta Persistence 3.2 record не может быть entity. Для entity нужны другие правила конструирования и состояния; часто также нужны ленивые прокси. Record подходит для результата проекции; спецификация 3.2 также допускает record как embeddable и класс составного ключа. Не делай из запрета entity вывод «records не работают с БД»: различай эти роли и проверяй поддержку в выбранном провайдере.

JSON-мапперу нужно распознавать компоненты и уметь вызвать canonical constructor. Обычный механизм «пустой объект плюс setters» не соответствует record. Нормализация и constructor validation тогда могут быть частью создания DTO, но аннотации Bean Validation проверяются механизмом интеграции отдельно. Поддержку и поведение при отсутствующем поле проверяют на конкретном маппере и версии.

У Java Object Serialization есть специальный record-протокол: компоненты читаются, затем создаётся объект через canonical constructor. В SerializationDemo.java счётчик увеличился при new и снова при readObject. Пользовательский readObject самого record не был вызван. Полный файл запускается на JDK 21 без файлов и внешней инфраструктуры.

// Ключевые строки SerializationDemo.java
record Invoice(String id, long minorUnits) implements Serializable {
    static int constructions;
    static boolean customRead;
    Invoice {
        constructions++;
        if (id == null || id.isBlank() || minorUnits < 0)
            throw new IllegalArgumentException("invalid invoice");
    }
    private void readObject(ObjectInputStream in) throws IOException, ClassNotFoundException {
        customRead = true;
        in.defaultReadObject(); // этот hook для record игнорируется
    }
}
Invoice original = new Invoice("p1", 100);
ByteArrayOutputStream bytes = new ByteArrayOutputStream();
try (ObjectOutputStream out = new ObjectOutputStream(bytes)) { out.writeObject(original); }
Invoice restored;
try (ObjectInputStream in = new ObjectInputStream(new ByteArrayInputStream(bytes.toByteArray()))) {
    restored = (Invoice) in.readObject();
}
System.out.println("equal=" + original.equals(restored));
System.out.println("canonical calls=" + Invoice.constructions);
System.out.println("custom readObject=" + Invoice.customRead);
equal=true
canonical calls=2
custom readObject=false

Constructor invariants сохраняются этим путём, но это не повод принимать произвольный поток сериализованных объектов из сети. Для records игнорируются и ряд других обычных serialization hooks; совместимость такого формата изучают по его специальному протоколу, а не по правилам обычного Serializable-класса. Здесь важно различать Java Serialization и JSON: это разные механизмы.

Добавление компонента меняет canonical-сигнатуру, равенство, hashCode и представление. Это изменение публичной модели, а не косметика. Для долгоживущего API продумай версионирование DTO и адаптеры на границе. Если нужны скрытое mutable-состояние, подклассы или традиционный JavaBean-контракт, выбирай обычный класс.

  • Record — отдельный final-класс, чьё состояние и value-контракт объявлены компонентами.
  • Compact constructor работает с параметрами; поля присваиваются после успешного тела.
  • Final фиксирует ссылку. Неизменяемость требует контроля всех объектов и ссылок в графе.
  • Generated equals использует правила компонентов: массив, BigDecimal и double имеют разные ловушки.
  • Реконструирование через accessors должно сохранять равенство; custom accessor обязан поддерживать этот контракт.
  • DTO и value object подходят record; entity и mutable JavaBean требуют другой модели.

На собеседовании

Что такое record и что генерирует компилятор?

Я использую record для значения, которое определяется объявленными компонентами. По заголовку компилятор создаёт private final поля, accessors с именами компонентов, canonical constructor и, если я их не написал, equals, hashCode и toString. Это отдельный final-класс, унаследованный от java.lang.Record, а не просто сокращение любого JavaBean.

Например, Receipt(id, minorUnits) можно передать как результат расчёта. Два экземпляра с одинаковыми компонентами равны через equals; сеттеров у него нет. При этом record с List не становится глубоко immutable: я отдельно определяю владение коллекцией.

  • Можно реализовывать интерфейсы и писать методы, но нельзя добавить instance-поле вне компонентов или выбрать другой superclass.
  • Member и local records неявно static: они не захватывают внешний экземпляр как inner class.
  • Record component metadata доступны через getRecordComponents; аннотации переносятся с учётом Target, а явно объявленный accessor требует отдельной проверки аннотаций.

Чем compact constructor отличается от canonical constructor?

Canonical constructor принимает все компоненты record и устанавливает их. Compact constructor — сокращённая canonical-форма: параметры берутся из заголовка record, я проверяю и нормализую их, а присваивания полям компилятор добавляет после тела. Поэтому внутри этой формы работаю с параметрами, а не читаю готовые значения через accessors.

Так я могу запретить пустой id и скопировать входной список до попадания в DTO. Если проверка бросит исключение, вызывающий не получит готовый record. Дополнительный конструктор делегирует через this к canonical-пути.

  • В полной canonical-форме присваивания надо написать самому; в compact-форме присваивать component fields запрещено.
  • Доступ canonical constructor не может быть уже доступа record. Фабрика не закрывает прямой new, если canonical по контракту публичен.
  • Нормализация должна быть идемпотентной для уже нормализованных компонентов, чтобы реконструирование через accessors сохраняло значение.

Record immutable? Можно ли использовать его как ключ HashMap?

У record неизменяемы поля компонентов, но изменяемость объектов за этими ссылками сохраняется. Если компонент — чужой ArrayList, его можно поменять после конструктора или через accessor. Для значения со списком String я делаю List.copyOf в canonical: список не меняется ни через исходный контейнер, ни через DTO.

Ключом карты использую record только со стабильными equals и hashCode. Если hashCode компонента поменялся после вставки, поиск вычислит другой хеш и ключ потеряется, хотя сам объект всё ещё находится в карте.

  • Read-only wrapper не делает snapshot, а copyOf копирует структуру, но не mutable-элементы.
  • Массив требует защитной копии на входе и выходе, а также согласованных content-based equals/hashCode; иначе ломается copy invariant.
  • Final-field semantics не заменяют синхронизацию последующих изменений вложенных объектов. Для передачи между потоками нужно учитывать весь граф и безопасную публикацию.
Accessor возвращает abs(value). Сохранится ли контракт record?
// Фрагмент EqualityDemo.java
record Misleading(int value) {
    public int value() { return Math.abs(value); }
}
Misleading source = new Misleading(-10);
Misleading copy = new Misleading(source.value());
System.out.println(source.equals(copy));
false

Accessor возвращает 10, поле source хранит -10, и generated equals сравнивает поля. Реконструирование изменило значение, нарушив copy invariant. Нормализуй параметр в canonical, если abs — настоящий смысл компонента; иначе возвращай исходное значение.

Где record подходит в backend и где обычный класс лучше?

Я беру record для DTO, команды, проекции запроса и небольшого value object, если данные задаются при создании. Canonical constructor поддерживает инварианты, а компонентное равенство помогает сравнивать результаты теста. Выбор компонента должен совпадать с бизнес-равенством: например, BigDecimal по умолчанию учитывает scale.

Для JPA entity по переносимому контракту record не подходит. Обычный класс также нужен при mutable lifecycle, скрытом состоянии или наследовании. Маппер DTO должен уметь создавать record через canonical, а не рассчитывать на no-arg constructor и setters.

  • Java Serialization десериализует record через canonical и игнорирует его readObject; это специальный протокол, отдельный от JSON.
  • Новый компонент меняет конструктор, equals/hashCode и наблюдаемую форму DTO. Эволюцию внешнего контракта надо проектировать явно.
  • Generated toString раскрывает компоненты. Токены и платёжные реквизиты нельзя автоматически выводить в лог целым DTO.
