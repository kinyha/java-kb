Recursion

Вложенность данных задаёт вложенность вызовов

Сервис получает пакет платежей. Внутри могут быть отдельные платежи и подпакеты, а в подпакетах — ещё подпакеты. Чтобы вычислить итоговую сумму, нельзя заранее написать три вложенных цикла: завтра придёт четвёртый уровень. Каждый подпакет при этом устроен так же, как исходный.

Здесь полезен контракт: «метод возвращает сумму всего переданного пакета». Он складывает собственные платежи и результаты вызова того же метода для дочерних пакетов. Не нужно мысленно раскрывать все уровни сразу. Предположи, что метод правильно решил меньший пакет, и объясни, как из этого получается ответ для текущего.

Сама запись «метод вызывает себя» не даёт ни корректности, ни эффективности. Вызов должен получать меньшую или структурно более простую подзадачу. А результаты должны правильно объединяться. Для суммы объединение — сложение; для максимальной глубины дерева — единица плюс максимум глубин детей. Алгоритмы обхода деревьев разобраны отдельно в Tree Traversal.

Начнём с короткого плоского пакета [10, 20, -5], чтобы увидеть возвраты без шума дерева. Определим sum(a, i) как сумму суффикса с позиции i до конца. Это текущая сумма платежа плюс сумма оставшегося суффикса; для пустого суффикса ответ 0. Цикл для этой конкретной задачи проще, но рекурсивный вариант позволяет наблюдать сам механизм.

Каждый вызов сохраняет незавершённую работу

Вызов sum(a, 0) не перескакивает к началу того же кадра. Для sum(a, 1) создаётся новый кадр со своими параметрами и локальными переменными. Первый кадр остаётся ждать, потому что ещё должен прибавить 10 к результату дочернего вызова.

Сохрани как TraceSum.java, запусти java TraceSum.java на JDK 21.

public class TraceSum {
    static long sum(int[] amounts, int i) {
        System.out.println("enter " + i);
        if (i == amounts.length) {
            System.out.println("base 0");
            return 0; // Пустой суффикс завершает цепочку вызовов.
        }
        int current = amounts[i]; // Значение остаётся в своём кадре, пока работает ребёнок.
        long rest = sum(amounts, i + 1);
        long result = current + rest; // Эта строка выполнится только ПОСЛЕ возврата.
        System.out.println("return " + i + " = " + result);
        return result;
    }

    public static void main(String[] args) {
        System.out.println("total=" + sum(new int[]{10, 20, -5}, 0));
    }
}

Сообщения enter идут вперёд по массиву, return — в обратном порядке. Сначала программа дошла до базы, только затем начала завершать сложения. Если поставить лог или отправку события после рекурсивного вызова, действие тоже произойдёт при возврате, а не при входе.

По модели JVM кадр содержит локальные переменные и operand stack; связь с вызывающим методом позволяет продолжить вычисление после возврата. Значения аргументов передаются по значению: каждый кадр получил своё значение i и копию ссылки a. Сам массив один. Изменение a[0] будет видно другим кадрам, а изменение локального i не изменит i у родителя.

Кадр JVM — модель исполнения, а не обещание физического адреса

JVMS §2.6 описывает создание кадра при вызове и уничтожение при нормальном или аварийном завершении. Конкретная JVM может оптимизировать машинный код и размещение данных, сохраняя семантику программы. Для объяснения рекурсии достаточно логических кадров: у каждого своё незавершённое продолжение и свои локальные значения.

В Java левый операнд выражения вычисляется раньше правого. В выражении a[i] + sum(a, i + 1) значение слева уже получено перед вызовом справа. В TraceSum оно вынесено в current специально, чтобы ожидание было видно прямо в коде.

Рекурсия заканчивается, когда убывает мера подзадачи

У корректного решения есть три части: контракт результата, базовый случай и переход, который приближает к базе. Для суммы суффикса контракт действует при 0 ≤ i ≤ a.length. Мера оставшейся работы — a.length − i. Она неотрицательна и строго уменьшается на каждом вызове, поэтому бесконечной цепочки быть не может.

База должна стоять до чтения a[i]: при i = a.length такого элемента нет. Возврат 0 выбран не случайно: это нейтральный элемент сложения, поэтому сумма пустого пакета и завершение любого непустого обрабатываются одним правилом.

Доказательство корректности похоже на индукцию. Пустой суффикс даёт 0. Если вызов для i + 1 вернул правильную сумму хвоста, прибавление a[i] даёт ровно сумму с i. Доказательство остановки при этом отдельное: даже правильная формула не спасёт, если передавать ту же подзадачу снова.

Раз в методе есть if с return, рекурсия обязательно завершится.

До этого if ещё нужно дойти с нужным аргументом. Вызов sum(a, i++) передаёт старое i: каждый ребёнок снова получает ту же позицию. Родитель увеличил только свою локальную переменную и ждёт. Верно передавать i + 1, не полагаясь на побочные эффекты.

Для дерева мера — размер дочернего поддерева. Для графа ссылка на соседа не обязательно уменьшает задачу: A → B → A возвращает к прежнему состоянию. Тогда нужны явные правила посещения и обнаружения циклов из Graph Search. Подставлять рекурсивный обход дерева в произвольный граф без изменения контракта нельзя.

Строго убывающая мера доказывает конечность вычисления, но не достаточность памяти. Цепочка из миллиона конечных подзадач может закончиться StackOverflowError раньше базового случая. Глубину надо оценить до запуска на пользовательских данных.

Время считает все вызовы, а память — активный путь

У суммы суффикса n + 1 вызовов, по постоянной работе в каждом: время Θ(n), максимальное число кадров n + 1, дополнительная память Θ(n). Рекурсия сама по себе не означает ни экспоненту, ни логарифм. Форма подзадач определяет обе оценки.

Теперь платёжный пакет разбивают на последовательные группы по одному или два платежа. Пусть ways(n) — количество вариантов для n оставшихся платежей. Первый шаг берёт один или два, поэтому ways(n) = ways(n − 1) + ways(n − 2). Для пустого остатка есть один способ закончить разбиение, для одного платежа тоже один.

Сохрани как BranchCost.java, запусти java BranchCost.java на JDK 21.

public class BranchCost {
    static int calls, maxDepth;

    static long plans(int n, int depth) {
        calls++;
        maxDepth = Math.max(maxDepth, depth);
        if (n <= 1) return 1;
        // Два способа начать пакет: один платёж или сразу два.
        return plans(n - 1, depth + 1) + plans(n - 2, depth + 1);
    }

    public static void main(String[] args) {
        for (int n : new int[]{4, 10, 20}) {
            calls = maxDepth = 0;
            long result = plans(n, 1);
            System.out.println("n=" + n + " plans=" + result
                    + " calls=" + calls + " depth=" + maxDepth);
        }
    }
}

n=10 plans=89 calls=177 depth=10
n=20 plans=10946 calls=21891 depth=20

Для n = 20 глубина всего 20 кадров, но вызовов 21 891: одинаковые остатки вычисляются многократно. Если C(n) — число вызовов, то C(0) = C(1) = 1 и C(n) = 1 + C(n − 1) + C(n − 2). Индукцией получаем C(n) = 2·ways(n) − 1, что совпадает с выводом программы.

Здесь время Θ(φⁿ), где φ ≈ 1,618; более простая верхняя оценка O(2ⁿ) тоже верна. Память стека O(n): два дочерних вызова выполняются последовательно, а не держат всё дерево в памяти одновременно. Если при каждом вызове копировать массив или накапливать все варианты ответа, это добавит другую стоимость.

В таблице глубина превращается в оценку стека только при постоянном размере кадра и последовательных вызовах. Время объединения и размеры выделенных буферов надо считать дополнительно. Общие правила — в Big O.

Кеш объединяет одинаковые подзадачи

В подсчёте разбиений ответ зависит только от n. Если ways(8) уже вычислен, второй вызов с 8 не обязан заново раскрывать всё поддерево. Мемоизация запоминает результат состояния и возвращает его при повторном обращении: из дерева повторяющихся вычислений получается граф зависимостей уникальных состояний.

Сохрани как MemoPlans.java, запусти java MemoPlans.java на JDK 21.

public class MemoPlans {
    static int computed;

    static long plans(int n, Long[] memo) {
        if (n <= 1) return 1; // Пустой остаток имеет один способ: ничего не добавлять.
        if (memo[n] != null) return memo[n]; // Состояние уже решено — сразу возвращаем ответ.
        computed++;
        long result = plans(n - 1, memo) + plans(n - 2, memo);
        memo[n] = result; // Публикуем в кеш только полностью вычисленный результат.
        return result;
    }

    public static void main(String[] args) {
        for (int n : new int[]{4, 10, 20}) {
            computed = 0;
            System.out.println("n=" + n + " plans=" + plans(n, new Long[n + 1])
                    + " computed=" + computed);
        }
    }
}

n=10 plans=89 computed=9
n=20 plans=10946 computed=19

Нетривиальные состояния — n от 2 до исходного значения. Каждое раскрывается один раз и имеет два перехода, поэтому время O(n). Кеш занимает O(n), максимальная цепочка первого спуска тоже O(n). Даже идеально работающий кеш не сокращает её: для большого n рекурсия всё ещё может переполнить стек.

Ключ кеша обязан включать всё, от чего зависит ответ. Если группировать разрешено не любые соседние платежи, а только платежи одной валюты, одного числа оставшихся записей уже недостаточно: состояние может зависеть от позиции и ограничений. Кеш между запросами также требует учитывать изменившиеся входные данные. Поэтому в учебном примере он создаётся на одно вычисление.

Нулём удобно обозначать «ещё не вычислено» в любой задаче.

Ноль может быть правильным ответом: например, нет допустимых разбиений. Тогда состояние будет пересчитываться. Разделяй статус и значение: используй null, массив visited или специальное значение вне допустимого диапазона.

Результат кладётся в кеш после завершения подзадачи. Это не защита от циклов: A снова запросит ещё не готовый A и продолжит вызывать себя. Для циклических зависимостей нужен отдельный признак «сейчас вычисляется» и правило обработки цикла. Мемоизация также не годится для бездумного пропуска побочных эффектов: отправить платёж и вернуть уже посчитанное число — разные операции.

Мемоизация и табличная динамика меняют порядок вычислений

Мемоизация идёт от запрошенного состояния к зависимостям, вычисляя только достигнутые состояния. Таблица может идти снизу вверх: ways(0), ways(1), затем ways(2) и далее. Для этой формулы достаточно помнить два предыдущих значения, поэтому можно убрать и стек, и линейный кеш. Построение состояний и переходов для других задач — тема Dynamic Programming.

Неограниченную глубину выносят в явный стек

В сервисе глубина вложенного пакета приходит с данными, поэтому аккуратной формулы недостаточно. Для короткой линейной цепочки переход к циклу прямой: индекс и аккумулятор становятся переменными цикла. Для ветвящегося обхода нужно хранить ещё не обработанные узлы в собственном стеке или очереди.

Хвостовой вызов — вызов, после которого текущему методу остаётся лишь вернуть результат. В некоторых языках такие вызовы переиспользуют кадр. Java не даёт переносимой гарантии такой оптимизации: перенос накопленной суммы в аргумент не является доказательством O(1) памяти стека.

Сохрани как TailCalls.java, запусти java -Xss256k TailCalls.java на JDK 21.

public class TailCalls {
    static long tail(long n, long accumulated) {
        if (n == 0) return accumulated;
        return tail(n - 1, accumulated + n); // После вызова работы нет: хвостовая позиция.
    }

    public static void main(String[] args) {
        try {
            System.out.println(tail(1_000_000, 0));
        } catch (StackOverflowError error) {
            // Перехват нужен только для демонстрации ограничения стека.
            System.out.println("StackOverflowError");
        }
        long total = 0;
        for (long n = 1_000_000; n > 0; n--) total += n;
        System.out.println("loop=" + total);
    }
}

loop=500000500000

Это реальный вывод JBR/OpenJDK 21.0.11 с указанным флагом. Точное количество вызовов до ошибки намеренно не используется как контракт: оно зависит от размера стека, кадров и компиляции. Увеличение -Xss отодвигает предел, но не исправляет неограниченную глубину. Перехват Error здесь нужен только для демонстрации, а не как штатная стратегия обработки платежей.

При переносе обхода на ArrayDeque вызывающие кадры заменяются элементами коллекции. Для бинарного дерева стек ожидающих узлов занимает O(h) в худшем случае, где h — высота; цикл использует O(1) стека вызовов. На цепочке ожидает всего один узел, а на дереве во время спуска накапливаются правые ветви. Очередь для обхода по уровням имеет другой максимум — ширину дерева.

Для суммы можно сразу прибавлять собственное значение узла и ставить детей в очередь работы. Но алгоритму «сначала вычисли обоих детей, потом объедини результаты» одного узла в стеке мало: нужно помнить фазу обработки и частичные результаты, то есть явно представить продолжение. Такие варианты разобраны в Tree Traversal. Выбор рекурсии или цикла — выбор способа хранить это состояние, а не автоматическое ускорение.

На собеседовании сначала произнеси контракт метода и базу, затем покажи убывающую меру. После кода отдельно оцени количество вычислений и максимальную глубину. Проверь пустой вход, один элемент, отрицательные суммы, общие ссылки и длинную цепочку — они вскрывают разные ошибки.

  • Кадр хранит параметры, локальные значения и незавершённое продолжение; возвраты идут в обратном порядке.
  • Корректность доказывают через контракт меньшей задачи, остановку — через строго убывающую меру.
  • Время зависит от всех вычислений, стек — от максимального активного пути.
  • Мемоизация переиспользует результат состояния, но не устраняет первую глубокую цепочку и не обнаруживает циклы сама.
  • Хвостовая форма не гарантирует постоянного стека в Java; неограниченную глубину обрабатывай явно.

Задачи

Починить сумму суффикса

Реализуй рекурсивную сумму amounts[from..length) для короткого учебного массива до 30 элементов. Разрешены отрицательные значения, from может совпадать с длиной. Возвращай long; недопустимый индекс отклоняй. Найди две ошибки в предложенном переходе: if (from == amounts.length - 1) return amounts[from]; return amounts[from] + sum(amounts, from++);.

[10, 20, -5], from = 1 → 15
[], from = 0 → 0

Авторская задача на механизм рекурсии · Время Θ(k + 1), дополнительная память Θ(k + 1), где k = length − from. В боевом коде длинный плоский массив проще суммировать циклом.

Подсказка 1

Пустой суффикс — такой же допустимый вход, как любой другой. Не читай элемент до проверки базы.

Подсказка 2

В дочерний вызов должно уйти новое значение индекса. Постинкремент возвращает старое.

Решение

Условие from == length − 1 не обрабатывает пустой суффикс; from++ не уменьшает подзадачу у ребёнка. Исправляем базу на from == length, затем передаём from + 1. Результат дочернего вызова имеет тип long, поэтому сложение также выполняется в long.

    static long sum(int[] amounts, int from) {
        if (from < 0 || from > amounts.length) throw new IllegalArgumentException();
        if (from == amounts.length) return 0; // База ДО чтения элемента.
        return amounts[from] + sum(amounts, from + 1); // Значение from у родителя не меняем.
    }

Время Θ(k + 1), дополнительная память Θ(k + 1), где k = length − from. В боевом коде длинный плоский массив проще суммировать циклом.

Почему заменить from++ на ++from всё ещё плохой ремонт?

Это исправит продвижение дочернего аргумента, но сохранит побочный эффект в локальном состоянии. Дальнейшее обращение к from после возврата увидит уже другое значение. Выражение from + 1 явно сохраняет контракт родительского кадра.

В каком порядке будут напечатаны индексы, если печатать их перед вызовом и после?

Перед вызовом: 0, 1, 2 для трёх непустых суффиксов. После возврата: 2, 1, 0. Если лог стоит до проверки базы, при входе дополнительно появится 3, как в TraceSum.

Посчитать разбиения пакета без повторных вычислений

n платежей идут в фиксированном порядке, 0 ≤ n ≤ 45. Разбей их на последовательные группы размера 1 или 2 и верни число вариантов. Порядок размеров групп важен: 1+2 и 2+1 — разные варианты. Для пустого пакета есть один вариант — пустое разбиение. Реализуй рекурсию с мемоизацией и кешем на один вызов count.

n = 3 → 3: 1+1+1, 1+2, 2+1
n = 4 → 5
n = 0 → 1

Авторская задача на механизм рекурсии · Время O(n), кеш O(n), стек O(n). Если нужны сами последовательности групп, размер результата снова экспоненциальный; мемоизация счётчика эту выдачу не ускоряет.

Подсказка 1

Раздели варианты по размеру первой группы. После её выбора остаётся такая же задача.

Подсказка 2

Результат состояния n зависит от n − 1 и n − 2. null отличает отсутствующий ответ от уже вычисленного.

Решение

Две ветви не пересекаются: первая группа имеет разный размер. Поэтому их количества складываются. База 0 возвращает 1, иначе вариант, который ровно добрал пакет группой размера 2, потерялся бы. Кеш хранит результат остатка, а не весь список разбиений.

    static long count(int n) {
        if (n < 0 || n > 45) throw new IllegalArgumentException();
        return solve(n, new Long[n + 1]); // Кеш принадлежит одному вычислению.
    }

    static long solve(int n, Long[] memo) {
        if (n <= 1) return 1;
        if (memo[n] != null) return memo[n];
        return memo[n] = solve(n - 1, memo) + solve(n - 2, memo);
    }

Время O(n), кеш O(n), стек O(n). Если нужны сами последовательности групп, размер результата снова экспоненциальный; мемоизация счётчика эту выдачу не ускоряет.

Как убрать и стек, и массив кеша?

Идти от 0 к n циклом и хранить два предыдущих значения. Это даст O(n) времени и O(1) дополнительной памяти. Такой порядок возможен, потому что зависимости известны и идут только к меньшим n.

Можно ли один раз создать static Long[] memo и использовать для любых правил группировки?

Нет: ответ зависит от правил. Если разрешить другие размеры групп или добавить ограничения, кеш с ключом только n станет неверным. Для неизменной чистой функции общий кеш возможен, но добавляет вопросы конкурентного доступа и срока жизни.

Сумма глубоко вложенных пакетов без рекурсии

Batch содержит собственную сумму и до двух подпакетов. Верни сумму всех вхождений узлов, root может быть null. Циклов нет; общая ссылка на лист в двух ветках считается двумя вхождениями. Сумма и промежуточные суммы помещаются в long. Глубина достигает 10 000, поэтому используй явный стек. Модель Batch и проверяющий main уже даны.

Batch(-3, Batch(10), Batch(20)) → 27
Batch(0, leaf10, leaf10) → 20
цепочка из 10 000 узлов по 1 → 10 000

Авторская задача на механизм рекурсии · Время O(N), где N — число посещённых вхождений. Для бинарного дерева дополнительная память O(h) в худшем случае, стек вызовов O(1). При общих поддеревьях N может быть больше числа уникальных объектов. Алгоритм не обещает линейность по числу уникальных объектов произвольного DAG.

import java.util.Deque;

public class NestedTotal {

    static long total(Batch root) {

    public static void main(String[] args) {
        check(total(null), 0);
        Batch leaf = new Batch(10, null, null);
        check(total(leaf), 10);
        check(total(new Batch(-3, leaf, new Batch(20, null, null))), 27);
        check(total(new Batch(0, leaf, leaf)), 20); // Два вхождения — считаем дважды.
        Batch chain = null;
        for (int i = 0; i < 10_000; i++) chain = new Batch(1, chain, null);
        check(total(chain), 10_000); // Без глубокой рекурсии при обходе.

Подсказка 1

Храни узлы, до которых ещё нужно добраться. Достань один, прибавь его значение, добавь детей.

Подсказка 2

ArrayDeque не принимает null. Для обхода слева направо правого ребёнка положи в стек раньше левого.

Решение

Стек pending представляет отложенные вызовы. Сумму можно накапливать сразу, потому что операция сложения не требует сначала получить отдельный результат каждого поддерева. Здесь считаются вхождения, поэтому множество visited изменило бы условие задачи и потеряло второе вхождение общего листа.

    static long total(Batch root) {
        if (root == null) return 0;
        Deque<Batch> pending = new ArrayDeque<>();
        pending.push(root);
        long sum = 0;
        while (!pending.isEmpty()) {
            Batch current = pending.pop();
            sum = Math.addExact(sum, current.ownAmount());
            // LIFO: правого кладём первым, чтобы левый обработался раньше.
            if (current.right() != null) pending.push(current.right());
            if (current.left() != null) pending.push(current.left());
        }
        return sum;
    }

Время O(N), где N — число посещённых вхождений. Для бинарного дерева дополнительная память O(h) в худшем случае, стек вызовов O(1). При общих поддеревьях N может быть больше числа уникальных объектов. Алгоритм не обещает линейность по числу уникальных объектов произвольного DAG.

Почему нельзя безусловно делать pending.push(current.left())?

ArrayDeque запрещает null и выбросит NullPointerException у листа. Проверять детей нужно до вставки, а пустой root — до создания первого задания.

Подойдёт ли тот же стек только из узлов для вычисления значения арифметического дерева?

Не в таком виде: операция родителя зависит от уже вычисленных результатов детей. Нужно хранить фазу кадра и результаты либо организовать обход после детей. Наш накопитель суммы устроен иначе и не требует этого состояния.

Будет ли у цепочки из 10 000 узлов pending содержать 10 000 элементов?

Нет: каждый раз удаляется единственный узел и добавляется единственный ребёнок. Размер pending не превышает 1. Оценка O(h) — верхняя граница для всех форм бинарного дерева, а не точный расход каждой формы.
