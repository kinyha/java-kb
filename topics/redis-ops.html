Redis in Production

Redis держит данные в памяти, и на диск их сохраняет только если включить персистентность: снимки RDB или журнал команд AOF. Реплики получают изменения асинхронно, поэтому при отказе мастера подтверждённые записи, не дошедшие до реплики, теряются. Sentinel следит за мастером и переключает клиентов на реплику, а Redis Cluster ещё и делит ключи по 16 384 слотам между мастерами, разрешая операции над несколькими ключами только внутри одного слота. Распределённая блокировка на Redis — это SET NX PX с уникальным токеном и освобождением через проверку токена, но от пауз процесса защищает только fencing token на стороне хранилища.

После перезапуска Redis исчезли ключи идемпотентности, а при failover вернулся старый баланс

Платёжный сервис хранит в Redis ключи идемпотентности, лимиты и блокировки на выплаты. После планового перезапуска пода Redis все ключи пропали, и повторные запросы клиентов провели платежи второй раз. В другой раз мастер упал, Sentinel переключил клиентов на реплику, и счётчик лимита откатился на несколько секунд назад. А блокировка на выплату магазину однажды оказалась у двух экземпляров сразу.

Тема разбирает, что Redis гарантирует в проде: сохранность на диске, поведение репликации и отказов, шардирование в кластере и пределы распределённых блокировок. Модель выполнения и структуры данных — в Redis Basics, кеширование — в Caching Strategies. Демо в examples/redis-ops работают с Redis 8 в Docker: persistence.sh и cluster.sh поднимают контейнеры сами, LockDemo.java использует Jedis 8.

Без RDB или AOF данные живут до перезапуска процесса

redis-server --save "" --appendonly no                            # без персистентности
redis-server --save "" --appendonly yes --appendfsync everysec    # журнал команд
== persistence: restart after 3 writes
no persistence: dbsize=0
AOF everysec:   dbsize=3

Без персистентности перезапуск стёр все три ключа. С AOF Redis дописывает каждую изменяющую команду в журнал и при старте проигрывает его. Политика appendfsync решает, как часто журнал сбрасывается на диск: always — на каждую команду, медленно; everysec — раз в секунду, при падении теряется до секунды записей; no — когда решит ОС. Журнал растёт, и Redis периодически переписывает его в компактный вид.

RDB — снимок всей памяти в файл по расписанию (save 3600 1 300 100 60 10000) или по команде. Он компактный и быстро загружается, но теряет всё после последнего снимка. Снимок делает дочерний процесс через fork, и пока он пишет, изменяемые страницы памяти копируются: под интенсивной записью Redis может временно занять почти вдвое больше памяти. По умолчанию AOF пишется с RDB-преамбулой: перезапись журнала начинается со снимка, а дальше идут команды. Для кеша персистентность часто выключают; для ключей идемпотентности, лимитов и сессий — включают AOF everysec и понимают, что секунда может потеряться.

Реплика получает изменения асинхронно, и failover теряет подтверждённые записи

Мастер отвечает клиенту OK сразу после выполнения команды и отправляет её репликам в фоне. Команда WAIT позволяет дождаться, пока запись получат N реплик, — для записей своего соединения. Демо разрывает сеть между мастером и репликой, пишет, убивает мастер и делает реплику новым мастером:

== async replication and failover
SET 100 + WAIT 1 replica 1000 ms -> OK 1
replica sees balance: 100
SET 40  + WAIT 1 replica 500 ms  -> OK 0
after failover balance: 100

WAIT вернул 0 — честный сигнал, что запись есть только на мастере, но клиенту уже ответили OK. WAIT не делает Redis строго согласованным: он только сообщает, сколько реплик успело, и не откатывает запись, если их не хватило. min-replicas-to-write 1 с min-replicas-max-lag 10 заставляет мастер отказывать в записи, если реплики давно не отвечали, и сужает окно потерь до этих секунд. Поэтому Redis не хранят как единственную копию данных, потеря которых недопустима: деньги и балансы живут в базе, а Redis — ускоритель и вспомогательные структуры.

Sentinel переключает мастер, а Cluster ещё и делит ключи по слотам

Sentinel — отдельные процессы, обычно три, которые следят за мастером. Если большинство из них считает мастер недоступным, они выбирают реплику, повышают её и сообщают клиентам новый адрес; клиент спрашивает у Sentinel, где мастер, а не хранит адрес жёстко. Данные при этом целиком на одном мастере. Redis Cluster добавляет шардирование: пространство из 16 384 слотов делится между мастерами, у каждого свои реплики, и отказ мастера переключается внутри кластера без Sentinel.

== slots per master
slots 0-5460
slots 5461-10922
slots 10923-16383
== key -> slot
payment:p-1 -> 9759
payment:p-2 -> 5756
{m-7}:limit -> 12084
{m-7}:tariff -> 12084
== client without cluster support
MOVED 5756 172.23.0.3:6379

== cluster-aware client (-c) follows MOVED
OK
== multi-key command across slots
CROSSSLOT Keys in request don't hash to the same slot

== same hash tag, same slot
OK

Слот ключа — CRC16 от имени по модулю 16 384. Узел, которому достался не свой ключ, отвечает MOVED с адресом владельца, и клиент с поддержкой кластера — Jedis, Lettuce, redis-cli -c — переходит туда и запоминает карту слотов. Команда над несколькими ключами работает, только если все ключи в одном слоте: payment:p-1 и payment:p-2 лежат даже на одном узле, но в разных слотах, и MSET получил CROSSSLOT. Это касается и транзакций, и Lua-скриптов. Решение — hash tag: если в имени есть {...}, слот считается только от этой части, и все ключи магазина {m-7} попадают в слот 12084. Злоупотреблять им нельзя: один огромный тег — одна перегруженная шарда.

Блокировку освобождают по токену, а от пауз процесса защищает только fencing token

Простая блокировка в Redis — SET lock owner NX PX 30000: ключ создаётся, только если его нет, и сам истекает, если владелец упал. Опасности две. Если освобождать обычным DEL, процесс, у которого блокировка уже истекла, удалит чужую. Демо: A берёт блокировку на 100 мс и замирает на 200 мс — пауза GC, — блокировка истекает, её берёт B, а проснувшийся A удаляет ключ:

== release with plain DEL
B acquires: true
A wakes up and releases: deleted 1
C acquires: true -> inside critical section: [B, C]
== release with Lua compare-and-delete
B acquires: true
A wakes up and releases: deleted 0
C acquires: false -> inside critical section: [B]

С DEL A удалил блокировку B, и C зашёл в критическую секцию, пока B ещё там: два владельца сразу. Освобождение Lua-скриптом, который удаляет ключ только если значение равно своему токену, это исправляет: A ничего не удалил, и C подождёт. Но вторая опасность остаётся: пока A спал, B уже работал, а A после пробуждения продолжит, думая, что блокировка его. Никакая проверка в Redis этого не отменит — A не знает, что спал.

== fencing token
B write with token 2 accepted
A write with token 1 rejected (last 2)

Защита — fencing token: вместе с блокировкой выдаётся монотонно растущий номер, и хранилище, куда идёт запись, отвергает операции с номером меньше уже виденного. A пришёл с номером 1 после B с номером 2 и получил отказ. Для этого хранилище должно уметь проверять номер — условный update в базе по версии делает то же самое. Алгоритм Redlock с блокировкой на нескольких независимых Redis спорен ровно по этой причине: он полагается на время и не даёт fencing token. Если корректность критична — выплата не должна уйти дважды, — опираются на ограничения базы: уникальный ключ, версию, SELECT ... FOR UPDATE, а блокировку в Redis используют как оптимизацию, чтобы не делать лишнюю работу.

SET NX с TTL и освобождением по токену — надёжная распределённая блокировка.

Токен защищает от удаления чужой блокировки, но не от того, что владелец заснул дольше TTL и продолжил работать параллельно с новым. В демо A и B оказались бы в секции вместе. Нужен fencing token, который проверяет хранилище, или ограничения в самой базе.

  • Без RDB или AOF рестарт стирает данные; AOF everysec теряет до секунды, RDB — всё после снимка; fork под записью удваивает память.
  • Репликация асинхронная: подтверждённый SET 40 пропал при failover. WAIT только сообщает, min-replicas-to-write сужает окно.
  • Sentinel переключает мастер; Cluster делит 16 384 слота, клиент следует MOVED, мультиключевые команды — только в одном слоте, hash tags.
  • Блокировка: SET NX PX с токеном и Lua-освобождением; от пауз — fencing token или ограничения базы.

На собеседовании

Чем RDB отличается от AOF?

RDB — периодический снимок всей памяти в компактный файл: быстро загружается, но теряет всё после последнего снимка. AOF — журнал изменяющих команд, который проигрывается при старте; с appendfsync everysec теряется не больше секунды. По умолчанию AOF пишется с RDB-преамбулой, сочетая быстрый старт и малые потери.

  • Снимок делает fork, и при интенсивной записи copy-on-write может почти удвоить память.
  • appendfsync always медленный; no отдаёт решение ОС.
  • Для чистого кеша персистентность выключают.

Чем Sentinel отличается от Redis Cluster и какие гарантии дают реплики?

Sentinel следит за одним мастером с репликами и при отказе повышает реплику, сообщая клиентам новый адрес; все данные на одном мастере. Cluster делит 16 384 слота между несколькими мастерами с репликами и сам переключает отказавшие. Репликация в обоих случаях асинхронная: подтверждённые записи, не дошедшие до реплики, теряются при failover.

  • WAIT сообщает число реплик, получивших запись своего соединения, но не откатывает её.
  • В Cluster мультиключевые команды, транзакции и скрипты — только в одном слоте; hash tags.
  • Клиент обязан поддерживать MOVED и ASK и кешировать карту слотов.

Как сделать распределённую блокировку на Redis и в чём её пределы?

SET key token NX PX ttl — ключ создаётся, только если его нет, и истекает сам, если владелец упал. Освобождают Lua-скриптом, который удаляет ключ только при совпадении токена, иначе можно удалить чужую блокировку. TTL выбирают больше времени работы и продлевают, если работа идёт дольше.

Предел: если владелец заснул дольше TTL — GC, сеть, — блокировку получит другой, а первый продолжит, думая, что она его.

  • Fencing token: монотонный номер с блокировкой, хранилище отвергает старые номера.
  • Redlock опирается на время и не даёт fencing token, поэтому спорен для корректности.
  • Когда важна корректность, опираются на ограничения базы; блокировка в Redis — оптимизация.
Что не так с этой блокировкой выплаты? 
if (redis.setnx("lock:payout:" + merchant, "1") == 1) {
    try {
        payouts.sendToBank(merchant);
    } finally {
        redis.del("lock:payout:" + merchant);
    }
}

У ключа нет срока: если процесс упадёт внутри try, блокировка останется навсегда и выплаты магазину встанут. Значение не уникально, и DEL удалит чужую блокировку, если своя истекла бы. А если добавить срок, долгий вызов банка может его пережить, и выплату отправит второй экземпляр. Нужны SET NX PX с уникальным токеном, Lua-освобождение по токену и идемпотентность выплаты на стороне базы или банка по ключу выплаты.
