Redis Basics

Redis — хранилище структур данных в памяти. Команды выполняет один поток по очереди, поэтому каждая команда атомарна, а одна медленная команда задерживает всех клиентов. Значения — не только строки: хеши, списки, множества, отсортированные множества, потоки, и у каждой структуры свои атомарные операции, на которых строят счётчики, очереди с отложенным запуском и лимиты. Время отклика определяет сеть, поэтому много команд отправляют пачкой через pipelining. Ключам задают TTL, а при нехватке памяти maxmemory-policy решает: вытеснять ключи или отказывать в записи.

Лимит платежей пропускал лишние операции, а Redis раз в час «замирал» на полсекунды

Сервис платежей хранит в Redis счётчик операций магазина за минуту для лимита. Код читает значение, прибавляет единицу и записывает обратно, и под нагрузкой лимит в 100 операций пропускает 300. В соседнем сервисе раз в час все запросы к Redis на полсекунды упираются в таймаут: по расписанию запускается очистка, которая удаляет ключи через KEYS session:*. А пакетная загрузка тарифов десяти тысяч магазинов занимает секунду, хотя каждая команда выполняется за микросекунды.

Все три истории объясняются устройством Redis: один поток, атомарные команды, задержка сети. Тема разбирает модель выполнения, структуры данных, pipelining, сроки жизни и вытеснение. Стратегии кеширования поверх Redis — в Caching Strategies, репликация, кластер и блокировки — в Redis in Production. Демо RedisDemo.java работает с Redis 8 в Docker через Jedis 8; миллисекунды в выводе меняются от запуска к запуску.

Один поток выполняет команды по очереди, и медленная команда задерживает всех

Redis принимает команды от тысяч соединений, но выполняет их в одном потоке, одну за другой. Ввод-вывод сети с Redis 6 можно распределить по дополнительным потокам, но сами команды по-прежнему исполняются последовательно. Это даёт простоту и атомарность без блокировок, а цена видна в демо: пока Lua-скрипт крутит цикл, PING из другого соединения ждёт.

r.eval("local x = 0 for i = 1, 150000000 do x = x + i end return 1");   // В одном соединении.
other.ping();                                                         // В другом — ждёт.
== PING alone: 0.10 ms
== PING during a 381 ms script: 351 ms
   big set size 200000
== DEL of 200k-member set: 3.5 ms
== UNLINK of the same set: 0.2 ms

Обычный PING — десятая доля миллисекунды. Во время скрипта — 351 мс: столько оставалось скрипту, и все клиенты Redis всё это время стояли в очереди. Так же действуют KEYS по миллионам ключей, SMEMBERS и HGETALL огромных коллекций, DEL большого ключа — удаление 200 тысяч элементов заняло 3,5 мс, а миллионов займёт секунды. UNLINK отвязывает ключ мгновенно, а память освобождает фоновым потоком. Вместо KEYS перебирают ключи курсором SCAN небольшими порциями. Медленные команды видны в SLOWLOG GET.

Внутри Lua-скрипта время заморожено: redis.call('TIME') возвращает одно и то же значение весь скрипт, чтобы скрипт был детерминированным при репликации. Первая версия демо ждала по TIME и зациклилась навсегда — Redis отвечал всем BUSY, пока скрипт не убили SCRIPT KILL.

Каждая команда атомарна, а чтение и запись двумя командами — нет

r.set("limit:m-7", String.valueOf(Long.parseLong(r.get("limit:m-7")) + 1));   // GET, прибавить, SET.
r.incr("limit:m-7");                                                         // Одна команда.
== 8 threads x 250 increments, GET+SET: 408
== 8 threads x 250 increments, INCR: 2000

Восемь потоков сделали по 250 увеличений. С GET и SET между чтением и записью успевают другие потоки, и их увеличения затираются: из 2000 осталось 408. INCR — одна команда, Redis выполняет её целиком, и результат точный. Это и был лимит платежей, который пропускал лишние операции.

Когда одной команды мало, есть три средства. MULTI/EXEC выполняет группу команд подряд, не прерываясь чужими, но внутри нельзя принять решение по прочитанному значению. WATCH добавляет оптимистичную проверку: транзакция не выполнится, если ключ изменился после WATCH. Lua-скрипт выполняется атомарно целиком и может читать, проверять и писать: «уменьшить остаток, только если хватает» — одна атомарная операция. Скрипты держат короткими по той же причине, что и выше.

Структуры данных дают готовые атомарные операции под типичные задачи

r.hset("session:s-1", Map.of("user", "anna", "role", "merchant", "shop", "m-7"));
r.zadd("retry:payments", now + 30, "p-1");          // score — время следующей попытки.
r.zrange("retry:payments", ZRangeParams.zrangeByScoreParams(0, now + 40));
r.sadd("cards:m-7", "4111", "5500", "4111");
== hash session: {user=anna, role=merchant, shop=m-7}, ttl 1800
== zset due by t=1040: [p-2, p-1]
== set unique cards: 2
СтруктураОперацииЗадача в платёжном сервисе
StringGET, SET … NX EX, INCRКеш, счётчик лимита, ключ идемпотентности
HashHSET, HGET, HINCRBYСессия, объект по полям без сериализации целиком
ListLPUSH, BRPOP, LMOVEПростая очередь задач
SetSADD, SISMEMBER, SINTERУникальные карты магазина, чёрные списки
Sorted setZADD, ZRANGE BYSCORE, ZPOPMINОтложенные повторы по времени, рейтинги, скользящее окно лимита

Sorted set, где score — время следующей попытки, превращается в очередь отложенных задач: воркер забирает всё, у чего срок наступил, и платежи p-2 и p-1 оказались готовы раньше p-3. Hash хранит сессию по полям, и роль можно изменить одной командой без чтения и записи всего объекта. Сложность операций указана в документации каждой команды, и её стоит смотреть: ZADD — O(log N), а SMEMBERS — O(N) и опасна на больших множествах.

Задержку определяет сеть, и pipelining отправляет команды пачкой

== 10000 SETs: one by one 906 ms, pipelined 6 ms

Каждая команда без pipelining — это круг по сети: отправить, дождаться ответа, отправить следующую. Redis тратит на SET микросекунды, а круг до контейнера — около 90 мкс, поэтому десять тысяч команд по одной заняли 906 мс. В режиме pipelining клиент отправляет все команды подряд, не дожидаясь ответов, и читает ответы потом: 6 мс, в 150 раз быстрее. В реальной сети между дата-центрами круг — миллисекунды, и разница ещё больше. Пакетная загрузка тарифов из истории выше — именно этот случай.

Pipelining не делает команды атомарными: между ними могут выполниться команды других клиентов. Для атомарности нужен MULTI или скрипт. Многие операции имеют и пакетные формы: MSET, MGET, HSET с несколькими полями.

TTL удаляет ключи по сроку, а maxmemory-policy решает, что делать при нехватке памяти

Ключу задают срок жизни: EXPIRE или SET ... EX. Истёкшие ключи удаляются двумя способами: при обращении к ним и фоновым процессом, который выборочно проверяет ключи со сроком. Поэтому память от истёкших ключей освобождается не мгновенно. Когда занятая память достигает maxmemory, поведение определяет политика:

== maxmemory 4mb, noeviction: wrote 1971, keys now 1971, error: OOM command not allowed when used memory > 'maxmemory'.
== maxmemory 4mb, allkeys-lru: wrote 20000, keys now 1964

С noeviction — умолчание — Redis отказал в записи после 1971 ключа: данные целы, но запись падает. С allkeys-lru все 20 000 записей прошли, а в памяти осталось 1964 последних: остальные вытеснены как давно не использованные. Политики volatile-* вытесняют только ключи с TTL, *-lfu — редко используемые, а не давно использованные.

Выбор политики — это выбор роли Redis. Для кеша — allkeys-lru или allkeys-lfu: потеря ключа означает промах, а не потерю данных. Если в том же Redis лежат ключи идемпотентности, сессии или блокировки, вытеснение молча их удалит, поэтому кеш и данные держат в разных инстансах или используют volatile-lru с TTL только у кеша. maxmemory задают обязательно: без него Redis растёт, пока его не убьёт OOM killer ОС.

Redis однопоточный, значит, любая последовательность команд в нём атомарна.

Атомарна каждая отдельная команда. Между GET и SET одного клиента выполняются команды других, и в демо из 2000 увеличений осталось 408. Для составных операций нужны атомарные команды вроде INCR, MULTI/EXEC с WATCH или Lua-скрипт.

  • Один поток исполняет команды по очереди: PING ждал 351 мс за скриптом. KEYS, большие DEL и коллекции — через SCAN и UNLINK.
  • Атомарна каждая команда: GET+SET потерял 80 % увеличений, INCR — ни одного. Для составных — MULTI/WATCH или Lua.
  • Структуры: hash для объектов, sorted set для отложенных задач и окон, stream для журнала, HyperLogLog для подсчёта уникальных.
  • Pipelining: 10 000 SET за 6 мс вместо 906; атомарности не даёт.
  • maxmemory обязателен; noeviction отказывает в записи, allkeys-lru вытесняет. Кеш и данные — в разных инстансах.

На собеседовании

Почему Redis быстрый, если он однопоточный?

Данные в памяти, команды простые и выполняются за микросекунды, а один поток не тратит время на блокировки и переключение контекста. Узкое место обычно сеть, а не процессор. Ввод-вывод с Redis 6 можно распределить по I/O-потокам, но команды исполняются последовательно.

Обратная сторона: одна медленная команда — KEYS, Lua-скрипт, DEL большого ключа — задерживает всех клиентов.

  • SCAN вместо KEYS, UNLINK вместо DEL для больших ключей, SLOWLOG для поиска медленных команд.
  • Масштабирование по CPU — шардирование в Redis Cluster, а не потоки.
  • Время внутри Lua-скрипта заморожено, скрипты должны быть короткими.

Как в Redis сделать атомарную операцию из нескольких шагов?

Каждая команда атомарна, поэтому лучше найти одну подходящую: INCR, SET NX, ZPOPMIN, HINCRBY. Для группы команд — MULTI/EXEC: выполняются подряд без чужих команд. Если решение зависит от прочитанного, — WATCH с MULTI (оптимистичная проверка) или Lua-скрипт, который читает и пишет атомарно.

  • Pipelining не атомарен: он только экономит круги по сети.
  • В Redis Cluster атомарные операции над несколькими ключами возможны только в одном слоте: hash tags {m-7}.
Почему этот лимит пропускает лишние платежи? 
String key = "limit:" + merchant + ":" + minute;
long used = Long.parseLong(Optional.ofNullable(redis.get(key)).orElse("0"));
if (used >= 100) throw new LimitExceeded();
redis.set(key, String.valueOf(used + 1));
redis.expire(key, 60);

Чтение и запись — разные команды, и параллельные запросы читают одно значение, проходят проверку и записывают одно и то же used+1: лимит пропускает в разы больше. Нужен INCR с проверкой результата (и EXPIRE при первом увеличении) или Lua-скрипт, который увеличивает и проверяет атомарно. Кроме того, SET без EX и отдельный EXPIRE оставляют окно, в котором ключ живёт без срока.

Что произойдёт, когда в Redis закончится память?

Зависит от maxmemory-policy. noeviction (по умолчанию) отказывает в записи с ошибкой OOM. allkeys-lru и allkeys-lfu вытесняют любые ключи — давно или редко используемые. volatile-* вытесняют только ключи с TTL. Для кеша выбирают allkeys-*, для хранилища данных — noeviction и мониторинг памяти.

  • Без maxmemory Redis растёт до OOM killer ОС.
  • Истёкшие ключи удаляются лениво и выборочно, память освобождается не мгновенно.
  • Кеш и данные с разными требованиями держат в разных инстансах.
