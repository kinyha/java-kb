Annotations & Reflection

Аннотация — метаданные, которые сами ничего не делают: смысл им придаёт код, который их читает. Читают в двух местах. При выполнении — рефлексией: Spring, Hibernate, Jackson и Bean Validation находят @Transactional, @Entity и @NotBlank и меняют поведение; для этого нужна @Retention(RUNTIME), иначе аннотация в демо невидима. При компиляции — обработчиками аннотаций, как Lombok и MapStruct: они видят исходник, генерируют код и могут остановить сборку. Поведение «вокруг» метода фреймворки добавляют прокси: объект-посредник с тем же интерфейсом. Отсюда главный подвох: вызов метода изнутри того же объекта идёт мимо прокси, и в демо два внутренних вызова не попали в аудит — так же теряется @Transactional. Рефлексия к тому же медленнее прямого вызова, обходит инкапсуляцию и ограничена модулями.

Валидация и аудит, переписанные в каждом методе

В сервисе возвратов каждый метод начинается с одних и тех же строк: проверить, что paymentId не пустой, что сумма не больше лимита, записать в журнал аудита, кто и что сделал. Эти строки повторяются в десятке сервисов и расходятся при правках. Аннотации позволяют объявить правило один раз, рядом с полем или методом, — @NotBlank, @Max(100_000), @Audited("refund"), — а общий код, читающий эти метаданные, выполняет его везде.

Тема разбирает, как аннотации читаются при выполнении и при компиляции и как фреймворки встраивают поведение через прокси. Демо ReflectionDemo.java строит валидатор и аудит на рефлексии и прокси JDK, скрипт processor.sh собирает обработчик аннотаций. Как Spring использует это в контейнере — в AOP, транзакции — в Transactions.

Retention: где аннотация существует

@Retention(RetentionPolicy.RUNTIME) @Target(ElementType.METHOD) @interface Audited { String value(); }
@Retention(RetentionPolicy.CLASS)   @Target(ElementType.METHOD) @interface Internal {}

@Audited("refund") @Internal
public void refund(String paymentId, long amount) { ... }

Обе аннотации стоят на одном методе, но рефлексия видит только @Audited. У @Internal retention CLASS — значение по умолчанию, если его не указать, — и при загрузке класса JVM её не сохраняет. Это частая ошибка при написании своей аннотации для фреймворка: забыли @Retention(RUNTIME), и аспект «не видит» аннотацию. @Target ограничивает, где аннотацию можно поставить; мета-аннотации @Inherited, @Repeatable и @Documented управляют наследованием, повторением и документацией. На мета-аннотациях построены составные аннотации Spring: @RestController помечен @Controller и @ResponseBody.

Reflection API: обойти поля и прочитать аннотации

record RefundRequest(@NotBlank String paymentId, @Max(100_000) long amount, String reason) {}

static List<String> validate(Record r) throws Exception {
    List<String> errors = new ArrayList<>();
    for (RecordComponent c : r.getClass().getRecordComponents()) {
        Object v = c.getAccessor().invoke(r);                       // вызов метода по объекту Method
        if (c.isAnnotationPresent(NotBlank.class) && (v == null || v.toString().isBlank()))
            errors.add(c.getName() + " must not be blank");
        Max max = c.getAnnotation(Max.class);
        if (max != null && ((Number) v).longValue() > max.value())
            errors.add(c.getName() + " must be <= " + max.value());
    }
    return errors.isEmpty() ? List.of("valid") : errors;
}

Двадцать строк дают то, что делает Hibernate Validator: валидатор ничего не знает о RefundRequest, он обходит его компоненты, читает аннотации и значения и применяет правила. Так же Jackson находит поля для сериализации, а Spring — конструктор и @Autowired. Reflection API — это Class, Field, Method, Constructor, RecordComponent и Parameter: получить члены класса, их модификаторы, типы с параметрами из атрибута Signature, как в Generics, и аннотации, а также прочитать поле или вызвать метод.

setAccessible(true) открывает приватные члены — своего кода спокойно: демо прочитало приватное поле record. Но с Java 9 модули закрывают внутренности чужих модулей: String.value из java.base недоступен — InaccessibleObjectException, пока модуль не открыт флагом --add-opens, как в Enums. Цена рефлексии — скорость и безопасность: вызов через Method.invoke проходит проверки доступа и упаковку аргументов (с JDK 18 он реализован через MethodHandle, и разрыв с прямым вызовом сократился), ошибки в именах всплывают при выполнении, а не при компиляции, и код, лезущий в приватные поля, ломает инкапсуляцию из Encapsulation.

Динамический прокси: поведение вокруг метода и вызов через this

RefundService proxy = (RefundService) Proxy.newProxyInstance(RefundService.class.getClassLoader(),
        new Class<?>[] { RefundService.class }, (p, method, a) -> {
            Method impl = target.getClass().getMethod(method.getName(), method.getParameterTypes());
            Audited audited = impl.getAnnotation(Audited.class);
            if (audited != null) System.out.println("   audit: " + audited.value() + " " + Arrays.toString(a));
            return method.invoke(target, a);                      // дальше — настоящий объект
        });

@Audited("refund-all")
public void refundAll(List<String> ids) { for (String id : ids) refund(id, 100); }   // вызов через this, мимо прокси

Это ровно та ловушка, на которой теряются @Transactional, @Async и @Cacheable: метод с аннотацией, вызванный из соседнего метода того же бина, выполняется без транзакции, синхронно и без кеша. Исправляют, вынося метод в отдельный бин, или явно вызывают через прокси (самовнедрение, AopContext.currentProxy()). Прокси JDK умеет только интерфейсы; для классов Spring генерирует подкласс через CGLIB или ByteBuddy, и тогда не перехватываются final- и private-методы — их нельзя переопределить. Поэтому методы с @Transactional должны быть public и не final.

Обработка аннотаций при компиляции

@SupportedAnnotationTypes("audit.Audited")
public class AuditProcessor extends AbstractProcessor {
    public boolean process(Set<? extends TypeElement> annotations, RoundEnvironment env) {
        for (Element e : env.getElementsAnnotatedWith(Audited.class))
            if (!e.getModifiers().contains(Modifier.PUBLIC))
                processingEnv.getMessager().printMessage(Diagnostic.Kind.ERROR,
                        "@Audited method must be public (proxies cannot intercept it): " + ..., e);
        return true;
    }
}

Обработчик аннотаций работает внутри javac: он видит элементы исходника — классы, методы, их модификаторы и аннотации с retention SOURCE — и может выдать ошибку, остановив сборку, или сгенерировать новые исходники. Демо остановило компиляцию на не-public методе с @Audited: ошибку, которая при выполнении превратилась бы в тихо пропущенный аудит, поймал компилятор. На генерации кода построены Lombok (геттеры, билдеры), MapStruct (мапперы), Dagger и Micronaut (внедрение зависимостей без рефлексии при выполнении).

Выбор между рефлексией при выполнении и генерацией при компиляции — компромисс. Рефлексия гибче и не требует шага сборки, но медленнее на старте, ошибки всплывают поздно, а в нативных образах GraalVM её нужно описывать конфигурацией. Генерация даёт обычный быстрый код и ошибки при компиляции, но усложняет сборку и отладку сгенерированного кода. Spring Boot 3 сочетает оба: AOT-обработка заранее генерирует часть конфигурации для нативных образов.

Если поставить @Transactional на метод, он всегда выполнится в транзакции.

Аннотацию исполняет прокси, а вызов изнутри того же объекта идёт через this, мимо него. В демо аудит записал внешний вызов refundAll, но не два внутренних refund. Кроме того, прокси на основе подкласса не перехватывает private- и final-методы.

  • Аннотация — метаданные; поведение даёт код, который её читает: рефлексия при выполнении или обработчик при компиляции.
  • Retention: SOURCE — компилятор, CLASS (по умолчанию) — в класс-файле, но не видна рефлексии, RUNTIME — для фреймворков.
  • Reflection API обходит поля и методы; setAccessible открывает private своего кода, а модули закрывают чужие внутренности.
  • Динамический прокси добавляет поведение вокруг вызова; вызов через this идёт мимо — так теряются @Transactional и @Async.
  • Прокси-подкласс не перехватывает private и final; методы с аспектами — public и не final.
  • Обработчик аннотаций видит исходник, генерирует код и может остановить сборку.

На собеседовании

Что такое retention аннотации и зачем он нужен?

Retention определяет, где аннотация существует. SOURCE — только в исходнике, её видят компилятор и обработчики аннотаций. CLASS, значение по умолчанию, — в класс-файле, но JVM не загружает её, и рефлексия её не видит. RUNTIME — доступна рефлексии при выполнении; такие нужны Spring, JPA, валидации. Своя аннотация для фреймворка без @Retention(RUNTIME) просто не будет найдена.

  • @Target ограничивает места, @Inherited — наследование с класса, @Repeatable — повторение.
  • Составные аннотации Spring построены на мета-аннотациях.

Как работают прокси в Spring и почему @Transactional иногда не срабатывает?

Spring оборачивает бин прокси: для интерфейсов — динамическим прокси JDK, для классов — подклассом через CGLIB. Прокси выполняет дополнительную логику — открывает транзакцию, проверяет права — и вызывает настоящий метод. Вызов метода из соседнего метода того же бина идёт через this, мимо прокси, поэтому аннотация не срабатывает. Также не перехватываются private- и final-методы.

  • Исправление: вынести метод в другой бин или вызвать через прокси.
  • AspectJ с вплетением при компиляции или загрузке обходит ограничение прокси.
Почему возвраты иногда сохраняются частично? 
@Service
public class RefundService {
    public void refundAll(List<Refund> refunds) {
        for (Refund r : refunds) refundOne(r);
    }
    @Transactional
    public void refundOne(Refund r) {
        ledger.post(r);            // первая запись
        payments.markRefunded(r);  // может бросить исключение
    }
}

refundOne вызывается из refundAll через this, мимо транзакционного прокси, поэтому @Transactional не работает: проводка сохраняется, а при исключении в markRefunded не откатывается. Нужно вынести refundOne в отдельный бин или сделать транзакционным вызов снаружи — и решить, нужна ли транзакция на каждый возврат или на всю пачку.

Каковы недостатки рефлексии?

Ошибки в именах и типах всплывают при выполнении, а не при компиляции. Вызов через Method.invoke медленнее прямого: проверки доступа, упаковка аргументов. setAccessible ломает инкапсуляцию, а с Java 9 модули запрещают доступ к закрытым пакетам чужих модулей без --add-opens. В нативных образах GraalVM рефлексию нужно описывать конфигурацией.

  • С JDK 18 рефлексия реализована через MethodHandle — разрыв с прямым вызовом сократился.
  • Альтернатива — генерация кода при компиляции: MapStruct, Dagger, Micronaut.

Что такое обработка аннотаций при компиляции?

Обработчик аннотаций — класс, который javac вызывает во время компиляции. Он видит элементы исходника и их аннотации, может выдать ошибку или предупреждение и сгенерировать новые исходники. Так работают Lombok, MapStruct, Dagger. Ошибки находятся при сборке, а сгенерированный код работает без рефлексии.

  • Обработка идёт раундами: сгенерированные файлы снова обрабатываются.
  • Lombok изменяет AST через внутренние API javac, а не только генерирует новые файлы.
