Replication

Реплика получает журнал WAL от primary и проигрывает его, становясь копией базы только для чтения. По умолчанию репликация асинхронная: primary подтверждает коммит, не дожидаясь реплики, поэтому чтение с реплики сразу после записи может вернуть старое значение, а при отказе primary подтверждённые, но не доехавшие транзакции теряются. Синхронный режим заставляет коммит ждать реплику — без потерь при failover, но с задержкой на каждый коммит и зависанием записи, если синхронная реплика недоступна. Чтение с реплик масштабирует чтение, но требует решить, где допустимо устаревание.

Клиент оплатил заказ и увидел «не оплачено», а после аварии пропали подтверждённые платежи

Чтобы разгрузить основную базу, чтение статусов платежей перевели на реплику. Сразу пошли жалобы: клиент нажимает «Оплатить», получает подтверждение, обновляет страницу — и видит «Не оплачено». Через полгода основной сервер упал, автоматический failover повысил реплику, и сверка с банком нашла несколько платежей, которые клиенты успели получить как успешные, но которых нет в базе.

Тема разбирает физическую потоковую репликацию PostgreSQL: как она работает, откуда берутся отставание и потери и что дают режимы синхронности. Устройство WAL — в Architecture & WAL, репликация Kafka и Redis — в Kafka: Replication и Redis in Production, распределение данных по серверам — в Sharding. Демо ReplicationDemo.java поднимает primary и реплику PostgreSQL 17 в Docker скриптом setup.sh, разрывает сеть между ними, убивает primary и повышает реплику.

Реплика проигрывает WAL primary и доступна только для чтения

pg_basebackup -h pg-primary -U repl -D /var/lib/postgresql/data -R -X stream
# -R: standby.signal и primary_conninfo — сервер стартует как реплика

Реплику создают копией файлов primary, и дальше процесс walreceiver получает поток WAL, а startup-процесс проигрывает его — так же, как при восстановлении после сбоя, только непрерывно. Это физическая репликация: копия побайтная, со всеми базами и индексами, той же мажорной версии PostgreSQL. Реплика в режиме hot standby принимает чтения, но не запись:

== pg_stat_replication: replica1 sync, replay_lag 00:00:00.501145
== write on replica: 25006 ERROR: cannot execute UPDATE in a read-only transaction

pg_stat_replication на primary показывает каждую реплику и её отставание по трём стадиям: записала WAL, сбросила на диск, применила. Здесь применение отстаёт на полсекунды — в демо реплике задана задержка recovery_min_apply_delay = 500ms, чтобы отставание было стабильным; в жизни оно зависит от нагрузки, сети и долгих запросов на реплике. Логическая репликация — другой механизм: она передаёт изменения строк выбранных таблиц и позволяет реплицировать между версиями и в другие системы, как CDC в Transactional Outbox.

Чтение с реплики сразу после записи возвращает старое значение

exec(p, "set synchronous_commit = " + mode);
exec(p, "update account set balance = balance - 30 where id = 'acc-1'");
scalar(r, "select balance from account where id = 'acc-1'");   // сразу читаем с реплики
== synchronous_commit=local        commit   3 ms; primary 70, replica right after 100
== synchronous_commit=remote_apply commit 502 ms; primary 40, replica right after 40

При обычном коммите primary ответил за 3 мс, и чтение с реплики сразу после этого вернуло старый баланс 100: изменение ещё не применено. Это нарушение read-your-writes — та самая «неоплаченная» оплата. С synchronous_commit = remote_apply коммит ждёт, пока реплика применит изменение, и чтение согласовано — но коммит занял 502 мс, ровно отставание реплики.

На практике remote_apply для всех коммитов слишком дорог, и read-your-writes решают в приложении. Читать с primary то, что пользователь только что изменил: например, первые секунды после записи или в рамках одного сценария. Привязать сессию к primary после записи. Запомнить LSN коммита (pg_current_wal_lsn()) и читать с реплики, только если она его уже применила (pg_last_wal_replay_lsn()). Чтение с реплики подходит для отчётов, каталогов и истории, где отставание в секунды допустимо.

Синхронная репликация не теряет коммиты, но останавливает запись без реплики

synchronous_commitКоммит ждётЧто теряется при отказе primary
offНичего, даже свой дискПоследние коммиты даже без failover
localСвой дискНе доехавшие до реплики коммиты
remote_writeРеплика получила WAL в память ОСТолько при одновременном падении реплики
onРеплика сбросила WAL на дискНичего
remote_applyРеплика применила изменениеНичего; чтения с реплики согласованы

Синхронные уровни действуют только для реплик из synchronous_standby_names. И у них есть обратная сторона, которую демо показывает, разорвав сеть до единственной синхронной реплики:

-- docker network disconnect pg-repl pg-replica
== synchronous_commit=on, replica unreachable: commit still waiting after 3 s: true
   warning: canceling wait for synchronous replication due to user request
   balance on primary after cancel: 10

Коммит повис и ждал бы вечно: primary не подтвердит транзакцию, пока реплика не ответит. Вся запись в базу стоит. Отмена ожидания не откатывает транзакцию — предупреждение честно говорит, что она уже закоммичена локально: баланс 10 виден на primary, но реплика его не получила. Поэтому синхронную репликацию строят как минимум с двумя кандидатами: synchronous_standby_names = 'ANY 1 (r1, r2)' — коммит ждёт любую одну из двух, и отказ одной реплики запись не останавливает. Синхронный режим можно включать и точечно — SET LOCAL synchronous_commit = on для транзакций с деньгами.

Failover на асинхронную реплику теряет подтверждённые транзакции

== async commit while replica is cut off: primary balance 999
-- docker kill pg-primary
-- docker network connect pg-repl pg-replica
== after promote, new primary balance: 40, in recovery: 0

Новый primary знает только то, что успел получить: подтверждённые клиенту изменения пропали. Это и есть потерянные платежи из истории — RPO асинхронной репликации не ноль, а величина отставания. Автоматический failover делают инструменты вроде Patroni: они выбирают реплику с наибольшим LSN, повышают её и не дают старому primary вернуться как ведущему. Последнее критично: если старый primary оживёт и продолжит принимать запись, у кластера два primary — split brain, и данные разойдутся необратимо. Поэтому старый узел изолируют (fencing), а при возвращении он становится репликой после pg_rewind.

Реплика — это резервная копия: при отказе primary ничего не потеряется.

Асинхронная реплика отстаёт, и всё, что primary подтвердил, но не успел отправить, при failover пропадает: в демо новый primary вернулся к балансу 40 после подтверждённых 999. Реплика не защищает и от ошибочного DELETE — он реплицируется мгновенно. Нужны синхронный режим для критичных транзакций и отдельные бэкапы с PITR.

  • Физическая реплика проигрывает WAL primary и открыта только для чтения (25006 на запись).
  • Асинхронный коммит 3 мс, но реплика сразу после него вернула 100 вместо 70; remote_apply — согласованно, но 502 мс.
  • Read-your-writes — в приложении: читать с primary после записи или ждать LSN на реплике.
  • Синхронный коммит висит без реплики; отмена оставляет транзакцию закоммиченной локально. Минимум два кандидата: ANY 1 (r1, r2).
  • Failover на асинхронную реплику потерял подтверждённые 10 и 999; Patroni, fencing старого primary, бэкапы с PITR.

На собеседовании

Чем синхронная репликация отличается от асинхронной?

При асинхронной primary подтверждает коммит сразу, а реплика получает изменения позже: коммит быстрый, но реплика отстаёт, и при отказе primary недоставленные транзакции теряются. При синхронной коммит ждёт подтверждения от реплики: потерь нет, но каждый коммит дольше на время сети и реплики, а при недоступности синхронной реплики запись останавливается.

  • В PostgreSQL уровни synchronous_commit: off, local, remote_write, on, remote_apply.
  • Отказоустойчивая синхронная схема — ANY 1 из двух и более реплик.
  • Синхронность можно включать для отдельных транзакций через SET LOCAL.

Почему после записи пользователь может не увидеть свои данные и как это исправить?

Если чтение идёт с асинхронной реплики, она может ещё не применить только что закоммиченное изменение — нарушение read-your-writes. Решения: читать с primary данные, которые пользователь только что изменил, или всю сессию в течение короткого времени после записи; запоминать LSN коммита и читать с реплики, только если она его применила; для критичных случаев — synchronous_commit = remote_apply.

  • Монотонность чтений тоже нарушается: два запроса к разным репликам могут вернуть «новое», потом «старое»; помогает привязка сессии к одной реплике.
  • Долгие запросы на реплике могут задерживать применение WAL или отменяться из-за конфликтов.
Что не так с этой маршрутизацией чтения? 
@Transactional
public void pay(String orderId) { payments.markPaid(orderId); }          // primary

@Transactional(readOnly = true)                                         // routing → replica
public PaymentStatus status(String orderId) { return payments.status(orderId); }
// фронт сразу после pay() вызывает status() и показывает результат

Статус читается с асинхронной реплики сразу после записи на primary, и при любом отставании пользователь увидит «не оплачено». Для чтения сразу после собственной записи нужно идти на primary (например, по признаку недавней записи в сессии) или дождаться, пока реплика применит LSN коммита. Реплики оставить для отчётов и истории.

Что происходит при failover и какие риски?

Реплику повышают до primary, и клиенты переключаются на неё. При асинхронной репликации теряются транзакции, которые старый primary подтвердил, но не отправил. Главный риск — split brain: если старый primary оживёт и продолжит принимать запись, данные разойдутся. Поэтому старый узел изолируют, а возвращают репликой через pg_rewind.

  • Patroni и подобные выбирают реплику с наибольшим LSN и держат лидерство через распределённое хранилище согласия.
  • RPO асинхронной схемы — величина отставания; RTO — время обнаружения и переключения.
  • Реплика не заменяет бэкап: ошибочный DELETE реплицируется.
