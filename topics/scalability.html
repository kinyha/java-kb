Scalability

Масштабируемость — способность обслуживать больше нагрузки, добавляя ресурсы. Вертикально — больше ядер и памяти на одной машине, — пока работа не упирается в общее: в демо 16 потоков без общего состояния дали ×14,3, а с общей блокировкой на 10 % работы — ×0,4, медленнее одного потока, потому что ядра тратят время на передачу друг другу кеш-линии. Горизонтально — больше экземпляров, — если экземпляры не хранят состояние: сессия в памяти одного экземпляра за балансировщиком узнаётся в половине запросов. Состояние выносят в общие хранилища, и тогда узким местом становятся они: их масштабируют репликами для чтения, кешами и, в последнюю очередь, шардированием.

Добавили серверов — стало не быстрее, а пользователей выкидывает

Сервис личного кабинета не справлялся с нагрузкой. Сначала его перенесли на машину вдвое мощнее — пропускная способность почти не выросла: потоки ждали один общий объект с кешем курсов, защищённый synchronized. Затем запустили второй экземпляр за балансировщиком — и пользователей стало выкидывать на страницу входа через раз: сессия хранилась в памяти экземпляра, на котором пользователь вошёл.

Тема разбирает пределы вертикального масштабирования, требование отсутствия состояния для горизонтального и порядок масштабирования данных. Демо в examples/scalability: ContentionDemo меряет пропускную способность потоков на 18 ядрах, SessionDemo поднимает два экземпляра за nginx 1.31 с сессиями в памяти и в Redis. Балансировка подробно — в Load Balancing, шардирование — в Sharding.

Вертикально: всё упирается в общее

while (running) {
    for (int k = 0; k < 90; k++) x = x * 6364136223846793005L + 1442695040888963407L;   // независимая работа
    if (withLock) synchronized (lock) { for (int k = 0; k < 10; k++) shared = shared * 31 + x; }

}

Закон Амдала даёт верхнюю границу ускорения при последовательной доле работы s: 1 / s, то есть ×10 при 10 %. Универсальный закон масштабируемости Ганнера добавляет стоимость согласования между участниками, которая растёт с их числом, — и предсказывает ретроградное масштабирование, которое видно в демо: после некоторого числа потоков пропускная способность падает. Это верно не только для потоков: общая строка в базе, на которую пишут все экземпляры, глобальный счётчик в Redis, один брокер на всех — то же общее состояние, только дороже.

Вертикальное масштабирование всё равно стоит пробовать первым: оно не требует менять архитектуру, а современные машины огромны. Но у него есть потолок, цена растёт быстрее мощности, а одна машина остаётся единой точкой отказа. Прежде чем покупать ядра, ищут общие ресурсы: synchronized на горячем пути, общие счётчики, пулы с одной очередью. Разбор блокировок в JVM — в Locks, атомики и LongAdder — в Atomics.

Горизонтально: экземпляры не должны хранить состояние

// Сессии в памяти процесса: у каждого экземпляра своя карта.
instance(8191, local()); instance(8192, local());
// Сессии в Redis: общая для всех экземпляров.
Store shared = new Store() {
    public void put(String sid, String user) { redis.set("session:" + sid, user, SetParams.setParams().ex(1800)); }
    public String get(String sid) { return redis.get("session:" + sid); }
};
instance(8193, shared); instance(8194, shared);
== log in, then call /me 6 times through nginx round robin
   sessions in memory   logged in on 8191; /me: 401 200 401 200 401 200 -> 3 of 6 recognized
   sessions in Redis    logged in on 8193; /me: 200 200 200 200 200 200 -> 6 of 6 recognized

Пользователь вошёл на экземпляре 8191, и сессия легла в его память. Round robin отправляет каждый второй запрос на 8192, который о сессии не знает: 401 через раз. С сессией в Redis любой экземпляр находит её по идентификатору из cookie — все 6 запросов узнаны. Это и есть требование горизонтального масштабирования: экземпляр сервиса взаимозаменяем, любой запрос может прийти на любой, и экземпляр можно убить или добавить в любой момент.

Где держать состояниеПлюсыМинусы
Redis, общая базаЭкземпляры взаимозаменяемыСетевой вызов на запрос, хранилище надо масштабировать

Состоянием бывает не только сессия: загруженные файлы на локальном диске, задачи в памяти, планировщик, запущенный на каждом экземпляре, локальные счётчики лимитов. Каждое такое место при втором экземпляре даёт ошибку, которой не было на одном. Принципы Twelve-Factor — конфигурация в окружении, логи в поток, ничего важного на локальном диске — и есть способ сделать экземпляры взаимозаменяемыми.

Масштабирование данных: от дешёвого к дорогому

Когда сервисы без состояния, узким местом становится хранилище, куда это состояние переехало. Порядок шагов — от дешёвых и обратимых к дорогим:

ШагЧто даётЦена
Индексы, запросы, пулыЧасто кратный выигрышТолько время разработчика — Query Tuning
ВертикальноБольше памяти — больше данных в кеше базыДеньги, потолок
КешСнимает повторяющиеся чтенияИнвалидация, устаревание — Caching
Реплики для чтенияМасштабирует чтенияОтставание реплик — Replication
ПартиционированиеМаленькие горячие партиции, дешёвое удаление старогоКлюч партиции в запросах — Partitioning
ШардированиеМасштабирует запись и объёмЗапросы и транзакции между шардами, перебалансировка

Шардирование — последний шаг, потому что оно меняет модель данных и код: всё, что раньше было одной транзакцией или одним JOIN, через границу шардов становится сагой или агрегацией в приложении. До него доходят, когда запись или объём перерастают самую большую разумную машину, — как показывает оценка в Interview Framework, это случается позже, чем кажется.

Масштабирование в облаке добавляет автоматику: горизонтальный автоскейлер добавляет экземпляры по CPU или по длине очереди. Новый экземпляр JVM не сразу работает в полную силу — классы загружаются, JIT ещё не скомпилировал горячие методы, кеши пустые, — поэтому масштабируются заранее, по прогнозу или с запасом, а readiness-проба пускает трафик после прогрева.

Если сервис упирается в CPU, достаточно дать ему больше ядер или потоков.

Дополнительные ядра помогают только работе без общего состояния: в демо 16 потоков без него дали ×14,3. Та же работа с общей блокировкой на 10 % стала медленнее одного потока — ×0,4. Сначала ищут общий ресурс, потом добавляют ядра.

  • 16 потоков без общего состояния — ×14,3; с общей блокировкой на 10 % работы — ×0,4: передача кеш-линий дороже работы.
  • Амдал даёт предел 1/s, универсальный закон масштабируемости — ещё и падение при росте числа участников.
  • Сессия в памяти за round robin узнана в 3 запросах из 6, в Redis — в 6 из 6: экземпляры должны быть взаимозаменяемы.
  • Данные масштабируют от дешёвого к дорогому: запросы, вертикально, кеш, реплики, партиции, шарды.
  • JVM нужен прогрев: масштабироваться заранее, трафик — после readiness.

На собеседовании

Чем вертикальное масштабирование отличается от горизонтального?

Вертикальное — более мощная машина: просто, без изменения кода, но есть потолок, цена растёт быстрее мощности, а машина остаётся единой точкой отказа. Горизонтальное — больше экземпляров: почти без потолка и с отказоустойчивостью, но требует, чтобы экземпляры не хранили состояние, а данные — распределения.

  • И то и другое упирается в общие ресурсы: блокировки, горячие строки, один брокер.
  • Амдал и универсальный закон масштабируемости: ретроградное масштабирование при согласовании.

Что значит «сервис без состояния» и как его добиться?

Любой экземпляр может обработать любой запрос, а экземпляры можно добавлять и убивать в любой момент. Сессии — в Redis или в токене, файлы — в объектном хранилище, задачи — в очереди, конфигурация — в окружении. Локально можно держать только то, что можно потерять: кеш.

  • Sticky sessions — обходной путь с неравномерной нагрузкой и потерей сессий при отказе.
  • Скрытое состояние: планировщики на каждом экземпляре, локальные лимиты, файлы на диске.
Что сломается при запуске второго экземпляра? 
@RestController
class ReportController {
    private final Map<String, byte[]> ready = new ConcurrentHashMap<>();
    @PostMapping("/reports") String start() { String id = uuid(); executor.submit(() -> ready.put(id, build())); return id; }
    @GetMapping("/reports/{id}") byte[] get(@PathVariable String id) { return ready.get(id); }
    @Scheduled(cron = "0 0 3 * * *") void cleanup() { ... }       // удаляет старые отчёты из S3
}

Отчёт строится и хранится в памяти экземпляра, принявшего POST; GET попадёт на другой экземпляр и вернёт пустоту, а при перезапуске отчёты пропадут. Задача в executor теряется при остановке экземпляра. Планировщик cleanup запустится на каждом экземпляре. Нужно: задача в общей очереди, результат в объектном хранилище, статус в базе, планировщик с блокировкой (ShedLock), как в Background Jobs.

Как масштабировать базу данных?

От дешёвого к дорогому: оптимизировать запросы и индексы, увеличить машину, добавить кеш, вынести чтения на реплики, партиционировать большие таблицы, и только потом шардировать. Шардирование масштабирует запись и объём, но транзакции и JOIN между шардами становятся задачей приложения.

  • Отставание реплик — read-your-writes надо обеспечивать отдельно.
  • Ключ шардирования выбирают по главным запросам, чтобы они не ходили по всем шардам.
  • Alex Xu, «System Design Interview», том 1, глава 1 «Scale from Zero to Millions of Users» — основа урока.
  • Neil Gunther, «Guerrilla Capacity Planning» — универсальный закон масштабируемости.
  • Gene Amdahl, «Validity of the single processor approach to achieving large scale computing capabilities», 1967.
  • The Twelve-Factor App — процессы без состояния.
