Booking System

Бронирование — это продажа ограниченного ресурса, за который одновременно борются многие: последнее место в самолёте, номер на даты, слот к врачу. Главный дефект — двойное бронирование, и проверка «свободно ли» в приложении перед вставкой его не предотвращает: в демо 50 одновременных покупателей последнего места получили 30 подтверждений. Защиту ставят в базе: счётчик свободных мест с условным UPDATE, уникальный индекс на конкретное место, ограничение исключения на пересекающиеся интервалы дат. Между выбором и оплатой место держат временной бронью со сроком, который проверяют при каждом захвате, а не только фоновой задачей. Поиск и просмотр обслуживают из кешей и реплик, а точные проверки — только на шаге бронирования.

Требования: поиск, временная бронь, оплата, никаких двойных продаж

Система бронирования гостиниц или билетов: пользователь ищет варианты, выбирает конкретный номер или место, получает временную бронь на 10 минут, оплачивает — бронь подтверждается; не оплатил — место освобождается. Нефункционально: ни одной двойной продажи, поиск быстрый и может показывать немного устаревшую доступность, бронирование — точное. На старте продаж популярного концерта тысячи людей одновременно хотят одни и те же места.

Типичная нагрузка асимметрична: поисков и просмотров в 100–1 000 раз больше, чем бронирований. 10 млн поисков в сутки — около 115 в секунду в среднем, а бронирований — десятки тысяч в сутки. Отсюда разделение: поиск через кеш, реплики или Elasticsearch, как в Elasticsearch; бронирование — через основную базу с проверками в транзакции. Демо BookingDemo.java запускает 50 одновременных попыток бронирования в PostgreSQL 17.

Последнее место: проверка в приложении продаёт его десятки раз

// Наивно: посчитать брони, сравнить с вместимостью, вставить.
ResultSet r = c.createStatement().executeQuery(
    "select count(*) < (select capacity from flight where id = 'SU-100') from ticket where flight = 'SU-100'");
r.next();
if (!r.getBoolean(1)) return false;
exec(c, "insert into ticket values ('SU-100', " + user + ")");

// Счётчик свободных мест в строке рейса: уменьшается, только если больше нуля.
int n = c.createStatement().executeUpdate("update flight set free = free - 1 where id = 'SU-100' and free > 0");
if (n == 0) return false;
exec(c, "insert into ticket values ('SU-100', " + user + ")");
== 50 users try to book the last seat of flight SU-100
   check, then insert           confirmed 30, tickets for 180 seats: 209
   conditional update           confirmed  1, tickets for 180 seats: 180

Продано 179 мест из 180. Все 50 транзакций одновременно посчитали брони, увидели 179 и вставили свою: подтверждено 30, в самолёте на 180 мест — 209 билетов. Число зависит от того, как переплелись потоки, — в других запусках было от 9 до 46, — но двойная продажа случается всегда. Причина та же, что у потерянного обновления в Digital Wallet: в READ COMMITTED чтение не блокирует ничего, и между проверкой и вставкой проходят чужие транзакции. Условный UPDATE счётчика берёт блокировку строки рейса: первая транзакция уменьшает счётчик до нуля, остальные ждут её коммита, видят ноль и получают отказ — ровно одно подтверждение.

Если продаются конкретные места, а не «любое из 180», защита ещё проще: строка на каждое место и уникальный индекс (flight, seat) на билетах — вторая вставка того же места получает ошибку уникальности. Строка рейса со счётчиком становится горячей точкой при старте продаж: все покупатели ждут одну блокировку. Тогда места делят на группы со своими счётчиками или выдают места из очереди, о чём ниже.

Номер на даты: пересечение интервалов проверяет ограничение исключения

create table booking(room int, stay daterange, user_id int);
alter table booking add constraint no_overlap
  exclude using gist (room with =, stay with &&);   -- нужен extension btree_gist для room with =
== 50 users book room 7 for overlapping dates
   check overlap, then insert   confirmed 40, overlapping pairs: 780
   exclusion constraint         confirmed  1, overlapping pairs: 0

Гостиничный номер бронируют не местом, а интервалом дат, и конфликт — не совпадение ключа, а пересечение интервалов: заезд 10–13 октября конфликтует с 12–15. Уникальный индекс такого не выразит. Проверка «есть ли пересекающиеся брони» перед вставкой проигрывает гонку так же, как с местом: в демо 50 пользователей хотели три ночи с заездом 10, 11 или 12 октября — любые две такие брони пересекаются, — и наивный вариант подтвердил 40, то есть 780 пересекающихся пар. Ограничение исключения в PostgreSQL гарантирует, что никакие две строки с равным room не имеют пересекающихся stay: подтверждена одна бронь.

Деталь, найденная демо: при одновременной вставке пересекающихся интервалов PostgreSQL иногда сообщает проигравшей транзакции не нарушение ограничения (23P01), а взаимную блокировку (40P01) при проверке ограничения. Код должен считать оба исхода отказом «занято» и откатывать транзакцию. Без этого первая версия демо падала с необработанным исключением. В базах без ограничений исключения ту же гарантию дают блокировкой строки номера (SELECT ... FOR UPDATE) перед проверкой пересечений или таблицей «номер × ночь» с уникальным индексом — строка на каждую ночь.

Временная бронь: срок проверяется при захвате, а не только задачей очистки

insert into hold values ('12A', 9, 'HELD', now() + interval '10 minutes')
on conflict (seat) do update set user_id = 9, status = 'HELD', expires_at = excluded.expires_at
where hold.status = 'HELD' and hold.expires_at < now();   -- занять можно только истёкшую бронь
== hold expires after 10 minutes
   user 9 takes 12A: held
   user 9 takes 12B: busy
   user 9 takes 12C: busy

Место 12A держали минуту назад истёкшей бронью — новый пользователь занял его. 12B держится ещё 9 минут, 12C оплачено — оба заняты. Одна команда INSERT ... ON CONFLICT DO UPDATE ... WHERE атомарно решает три случая: место свободно, бронь истекла, место занято. Если корректность зависит только от фоновой задачи, которая раз в минуту снимает истёкшие брони, то место простаивает до её запуска, а при её сбое — бесконечно.

Оплата и подтверждение — отдельная развилка: оплата прошла на 10-й минуте и 1-й секунде, а бронь уже занял другой. Защита — подтверждать условным UPDATE status = 'CONFIRMED' where user_id = ? and status = 'HELD' и, если ноль строк, вернуть деньги автоматически. Платёж стоит проводить через ключ идемпотентности брони, как в Payment System, а срок брони делать с запасом больше времени ожидания оплаты.

Старт продаж: очередь вместо толпы у одной блокировки

На старте продаж популярного концерта сотни тысяч людей одновременно пытаются занять несколько тысяч мест. Даже правильные блокировки здесь становятся узким местом: все транзакции ждут одни и те же строки, пулы соединений забиты, база перегружена, как в Overload. Решение — виртуальная очередь перед бронированием: пользователи встают в очередь (в Redis или в отдельном сервисе), и в зал бронирования пропускают столько, сколько система обслуживает, с понятным временем ожидания. Остальное — уже знакомые механизмы: лимиты на пользователя против ботов из Rate Limiting, отказ лишнему вместо очередей в базе.

Поиск при этом показывает доступность из кеша и может ошибаться: место, видимое свободным, уже держит другой покупатель. Это нормально, если точная проверка происходит при захвате брони и пользователь получает понятный ответ «место только что заняли». Делать поиск строго согласованным — значит гонять каждый просмотр через основную базу ради редкого случая.

Если перед вставкой брони проверить в той же транзакции, что место свободно, двойной продажи не будет.

В READ COMMITTED проверка ничего не блокирует: все транзакции видят место свободным и вставляют. В демо так последнее место продали 30 раз, а номер на пересекающиеся даты — 40 раз. Гарантию дают условный UPDATE счётчика, уникальный индекс места или ограничение исключения на интервалы.

  • Проверка «свободно?» в приложении продала последнее место 30 раз; условный UPDATE счётчика — один.
  • Интервалы дат: ограничение исключения exclude using gist (room with =, stay with &&) — 0 пересечений против 780.
  • Проигравшая вставка может получить 23P01 или 40P01 — оба означают «занято».
  • Временная бронь со сроком: захват проверяет expires_at < now(), фоновая очистка не нужна для корректности.
  • Подтверждение после оплаты — условным UPDATE с автоматическим возвратом при опоздании; старт продаж — через виртуальную очередь.

На собеседовании

Как не допустить двойного бронирования?

Проверку и захват делать одной операцией в базе, а не «прочитать и вставить». Для «N любых мест» — счётчик с условным UPDATE free = free - 1 where free > 0; для конкретного места — уникальный индекс; для интервалов дат — ограничение исключения или блокировка строки ресурса перед проверкой пересечений. Отказ базы означает «занято» и превращается в понятный ответ пользователю.

  • READ COMMITTED не защищает проверку перед вставкой; SERIALIZABLE защитит ценой повторов.
  • При конкурентной проверке ограничения исключения возможен 40P01 вместо 23P01.
  • Горячая строка счётчика на старте продаж — делить на группы или ставить очередь.
Что не так с этим бронированием? 
@Transactional
public Booking book(long roomId, LocalDate from, LocalDate to, long userId) {
    if (bookings.existsOverlap(roomId, from, to)) throw new RoomTaken();
    return bookings.save(new Booking(roomId, from, to, userId));
}
@Scheduled(fixedDelay = 60_000)
void releaseExpired() { bookings.deleteHeldBefore(Instant.now().minus(10, MINUTES)); }

Проверка пересечений и вставка разделены: одновременные запросы обе пройдут проверку, и номер забронируют дважды. Нужно ограничение исключения на интервал или блокировка строки номера перед проверкой. Истёкшие брони освобождает только задача раз в минуту: до её запуска место простаивает, а если она упала — навсегда. Захват должен сам считать бронь со сроком в прошлом свободной.

Как реализовать временную бронь на время оплаты?

Строка брони со статусом HELD и сроком истечения. Занять место можно, если его нет или бронь в статусе HELD с прошедшим сроком — одной командой upsert с условием. Подтверждение после оплаты — условным UPDATE по пользователю и статусу; если бронь уже занята другим, деньги возвращаются автоматически. Фоновая очистка только убирает мусор.

  • Срок брони — с запасом к времени ожидания оплаты.
  • Платёж — с ключом идемпотентности брони.
  • Можно хранить бронь в Redis с TTL, но источником истины для продажи остаётся база.

Как выдержать старт продаж популярного события?

Виртуальная очередь перед бронированием пропускает столько пользователей, сколько система обслуживает; остальным показывает позицию и время ожидания. Поиск и просмотр — из кеша, точная проверка — только при захвате. Лимиты на пользователя и защита от ботов. Лишнее — быстрый отказ, а не ожидание в пулах соединений.

  • Горячая строка счётчика — делить места на группы со своими счётчиками.
  • Предварительно прогретые кеши и заранее масштабированные экземпляры.
