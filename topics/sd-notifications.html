Notification Service

Сервис уведомлений принимает события от других сервисов и доставляет их пользователю по каналам — push, SMS, email — через внешних провайдеров. Сообщения неравноценны: код для входа должен прийти за секунды, а рекламная рассылка может идти часами. Общая очередь ставит код за всей рассылкой: в демо он пришёл через 5,4 секунды, после 3 000 рекламных пушей, а в отдельной приоритетной очереди — через миллисекунду. События приходят «хотя бы один раз», поэтому отправку дедуплицируют по ключу события и получателя. Пользователя защищают лимитами частоты и тихими часами, провайдеров — повторами с задержкой и запасным провайдером. Доставка не гарантирована даже после ответа провайдера: статус отслеживают по его обратным вызовам.

Требования и нагрузка

Сервис уведомлений банка: коды подтверждения (OTP), уведомления об операциях, напоминания и маркетинговые рассылки по push, SMS и email. Пользователь управляет подписками по каналам и типам, транзакционные уведомления отключить нельзя. Нефункционально: код входа — за секунды, уведомление об операции — за десятки секунд, рассылка — в течение часов; без дублей; без сообщений ночью, кроме срочных.

Оценка: 20 млн пользователей, 3 транзакционных уведомления в день — 60 млн в сутки, около 700 в секунду в среднем и 2–3 тысячи в пик. Рассылка на всех пользователей — 20 млн сообщений, которые порождаются за минуты. Именно рассылка определяет устройство очередей: её всплеск не должен задерживать срочные сообщения. SMS стоят денег за каждое сообщение, поэтому дубли и лишние отправки — прямые потери.

POST /v1/notifications                   # вызывают другие сервисы, а не пользователь
{ "event_id": "payment-81", "user_id": "anna", "type": "PAYMENT_DONE",
  "priority": "HIGH", "params": { "amount": "150.00", "merchant": "Coffee Lab" } }
202 Accepted

Модель данных: шаблоны по типу, языку и каналу; настройки пользователя (каналы, подписки, тихие часы, часовой пояс); токены устройств для push; журнал отправок со статусом доставки. Сервис-источник присылает событие и параметры, а не готовый текст: текст, канал и время отправки выбирает сервис уведомлений по настройкам пользователя.

Общая схема: приём, маршрутизация, очереди по приоритету, отправка

Приём отделён от отправки: API записывает событие и отвечает 202, остальное асинхронно. Маршрутизатор отбрасывает дубли, проверяет подписки и лимиты, выбирает канал и шаблон и кладёт готовое сообщение в очередь своего приоритета. Воркеры каналов масштабируются отдельно: email-провайдер пропускает тысячи писем в секунду, SMS-шлюз — сотни, у push-сервисов Apple и Google свои лимиты. Источники пишут события через outbox, чтобы уведомление не потерялось при сбое после коммита, как в Transactional Outbox.

Срочное не должно стоять за рассылкой

// Воркер всегда сначала смотрит в приоритетную очередь.
List<String> m = priority ? redis.brpop(1, "q:high", "q:low") : redis.brpop(1, "q:all");
== campaign of 3000 marketing pushes is queued, then a login code (OTP) arrives
   one FIFO queue:            OTP delivered after  5428 ms, 3000 promos sent before it
   separate priority queue:   OTP delivered after     1 ms,    0 promos sent before it

Маркетинг поставил в очередь 3 000 пушей, и следом пользователь запросил код для входа. В общей очереди код ждёт всю рассылку: 5,4 секунды при одном воркере, который отправляет около 550 сообщений в секунду. Для настоящей рассылки на миллионы пользователей это часы — код истечёт, пользователь не войдёт. BRPOP с несколькими ключами проверяет их по порядку, поэтому воркер берёт сообщение из q:high, если оно там есть, и только потом из q:low: код ушёл через миллисекунду.

Приоритетные очереди — минимум. Надёжнее разделить и воркеров: у срочных сообщений свой пул, который рассылка не может занять, — bulkhead из Resilience Patterns. В Kafka приоритетов внутри топика нет, поэтому срочные и массовые сообщения пишут в разные топики с разными группами потребителей. Рассылку к тому же ограничивают по скорости, чтобы она не съела лимиты провайдера, нужные срочным сообщениям.

Рассылка на 20 миллионов: порождать частями и с темпом

Рассылку на всех пользователей нельзя поставить в очередь одной командой: 20 млн сообщений по килобайту — 20 ГБ в очереди, и всё это время они ждут отправки. Её разбивают: задача рассылки делится на пачки по тысяче пользователей, каждая пачка — отдельная задача, которая выбирает получателей с учётом подписок, рендерит текст и ставит сообщения в низкоприоритетную очередь. Генератор пачек работает с темпом, а не залпом.

Темп определяет самый узкий канал. Если push-провайдер принимает 5 000 сообщений в секунду, рассылка на 20 млн займёт 20 000 000 / 5 000 = 4 000 секунд — больше часа; SMS по 300 в секунду на ту же аудиторию — 18,5 часа, поэтому массовые SMS почти не отправляют. Часть лимита провайдера оставляют срочным сообщениям: если рассылка заберёт все 5 000 в секунду, коды входа получат 429. Учитывают и часовые пояса: утренняя рассылка в 10:00 по местному времени — это 11 запусков для России, по одному на пояс.

Задача рассылки хранит прогресс — какая пачка отправлена последней, — чтобы после сбоя продолжить с места остановки, а не отправить всё заново. Отмена рассылки должна работать сразу: воркеры перед отправкой проверяют, не отменена ли кампания, иначе уже поставленные в очередь миллионы сообщений уйдут после нажатия «стоп».

Дубли, лимиты, тихие часы и повторы

== the same event delivered 3 times (at-least-once)
   pushes sent 1, duplicates skipped 2
== frequency cap: at most 2 marketing pushes per user per day
   promo-1: sent; promo-2: sent; promo-3: dropped; promo-4: dropped;

Событие «платёж 81 проведён» пришло трижды — брокер доставляет хотя бы один раз, источник повторил после тайм-аута. Ключ sent:payment-81:anna, установленный через SET NX со сроком жизни сутки — дольше окна повторной доставки, пропустил одну отправку и отбросил два дубля, как в Idempotency. Ключ — событие плюс получатель и канал: одно событие может законно породить push и email.

Лимит частоты защищает пользователя от рекламы: счётчик на пользователя и день, сверх двух в день — отбросить. Транзакционные сообщения под лимит не попадают. Тихие часы считают по часовому поясу пользователя: несрочное сообщение ночью не отбрасывают, а откладывают до утра — в отложенную очередь с временем отправки, как в Background Jobs.

Провайдеры отказывают: 429 при превышении лимита, 5xx при сбоях, тайм-ауты. Повторы — с экспоненциальной задержкой и ограничением, для SMS с OTP — быстрое переключение на запасного провайдера, потому что код через минуту бесполезен. Повтор после тайм-аута может отправить SMS дважды: провайдер мог принять первую попытку. Если провайдер поддерживает ключ идемпотентности, его передают; если нет — для OTP дубль допустим, для дорогой массовой рассылки повтор после тайм-аута делают только после запроса статуса.

Ответ провайдера «принято» не значит «доставлено»: push не дойдёт до выключенного телефона, токен устройства мог устареть, письмо попадёт в спам. Провайдеры сообщают статус обратными вызовами — доставлено, токен недействителен, отписка, — и сервис обновляет журнал, удаляет мёртвые токены и учитывает отписки. По этим данным строят метрики доставки по каналам и провайдерам.

Все уведомления можно класть в одну очередь: она быстрая, воркеров можно добавить.

Порядок в очереди не учитывает срочность. В демо код входа ждал 3 000 рекламных пушей — 5,4 секунды; на рассылке в миллионы это часы. Срочное идёт отдельной очередью и отдельными воркерами: код ушёл через 1 мс.

  • Приём (202) отделён от отправки; источники пишут события через outbox; текст и канал выбирает сервис уведомлений.
  • Срочное — своя очередь и свои воркеры: OTP за 1 мс вместо 5,4 с за 3 000 пушей рассылки.
  • Рассылка — пачками с темпом, с запасом лимита провайдера для срочного, по часовым поясам, с прогрессом и мгновенной отменой.
  • Дубли — SET NX по событию, получателю и каналу: из трёх доставок одна отправка.
  • Лимит частоты для рекламы, тихие часы по часовому поясу с откладыванием, а не удалением.
  • Повторы с задержкой и запасной провайдер; «принято» не значит «доставлено» — статусы по обратным вызовам.

На собеседовании

Спроектируйте сервис уведомлений

API принимает события от сервисов и отвечает 202. Маршрутизатор отбрасывает дубли, проверяет настройки пользователя, лимиты и тихие часы, выбирает шаблон и канал. Сообщения — в очереди по приоритетам, воркеры по каналам отправляют через провайдеров с повторами и запасным провайдером. Журнал отправок и статусы доставки по обратным вызовам. Настройки, шаблоны и токены устройств — в базе.

  • Рассылка и срочные — разные очереди и пулы воркеров.
  • Дедупликация по событию, получателю и каналу; at-least-once на входе.
  • SMS стоят денег — лимиты, дедупликация, контроль повторов после тайм-аутов.

Как не задержать код подтверждения массовой рассылкой?

Разделить по приоритетам: срочные сообщения — в свою очередь или топик, которую воркеры разбирают первой, лучше — со своим пулом воркеров. Рассылку ограничить по скорости, чтобы она не съела лимиты провайдера. Для OTP — короткий тайм-аут и быстрое переключение на запасной канал или провайдера.

  • В Kafka приоритетов внутри топика нет — разные топики и группы.
  • Код, пришедший после истечения, бесполезен: срок жизни сообщения — часть модели.
Что не так с этим обработчиком? 
@KafkaListener(topics = "notifications")      // OTP, операции и рассылки — один топик
void on(NotificationEvent e) {
    String text = templates.render(e);
    smsGateway.send(e.phone(), text);             // тайм-аут 30 с, повтор Kafka при исключении
    log.save(e.eventId(), "SENT");
}

Один топик для всего: OTP стоит за рассылкой. Нет дедупликации — повторная доставка события или повтор после исключения отправят SMS дважды, а исключение после успешной отправки, но до записи журнала, гарантирует дубль. Тайм-аут 30 секунд держит потребителя, и вся партиция стоит. Нет проверки подписок и тихих часов. Нужны: разные топики по приоритету, ключ дедупликации до отправки, короткие тайм-ауты с повторами по расписанию, учёт настроек пользователя.

Как узнать, что уведомление доставлено?

Ответ провайдера означает только «принято». Доставку подтверждают обратные вызовы провайдера: доставлено, не доставлено, токен недействителен, отписка. Сервис хранит журнал отправок с этими статусами, удаляет мёртвые токены и считает метрики доставки по каналам. Для критичных сообщений — повтор по другому каналу, если статус не пришёл за отведённое время.

  • Обратные вызовы тоже приходят повторно и не по порядку — обрабатывать идемпотентно.
  • Метрика «доставлено за N секунд» по приоритетам — основа SLO сервиса.
  • Alex Xu, «System Design Interview», том 1, глава 10 «Design a Notification System» — основа урока.
  • Redis: BRPOP — порядок проверки нескольких ключей.
  • Apple: Sending notification requests to APNs и Firebase Cloud Messaging — статусы и недействительные токены.
