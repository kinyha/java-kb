URL Shortener

Сокращатель ссылок — система с очень разными путями записи и чтения: создают ссылки десятки раз в секунду, а переходят по ним тысячи. Две трудные части. Генерация ключа: префикс хеша длинной ссылки даёт коллизии по парадоксу дней рождения — 12 на 10 млн ссылок даже при 7 символах, — поэтому нужен счётчик, а чтобы коды не шли подряд, его пропускают через обратимую перестановку. Чтение: переходы распределены по закону Ципфа, и кеш на 1 % ссылок обслуживает 64 % переходов. Редирект 301 кешируется браузером и экономит запросы, но лишает статистики; 302 — наоборот. Статистику пишут асинхронно, чтобы переход не ждал запись.

Требования: короткий код, быстрый переход, статистика

Функционально: по длинной ссылке выдать короткую вида sho.rt/4WveT3H; по короткой — перенаправить на длинную; показать владельцу число переходов. Дополнительно стоит уточнить: может ли пользователь задать свой код (alias), есть ли срок жизни ссылки, нужна ли одинаковая короткая ссылка для одной и той же длинной, удаляются ли ссылки. Нефункционально: переход быстрый — p99 до 50 мс внутри региона, — и очень доступный: недоступный сокращатель ломает ссылки в чужих письмах и постах. Коды не должны угадываться перебором подряд.

Выводы: запись тривиальна, хранение умеренное, а переходы — главная нагрузка, и в основном это чтение по ключу. Значит, нужны хранилище с быстрым поиском по ключу, кеш перед ним и масштабирование чтения. Семи символов base62 хватает с большим запасом; шести (56 млрд) формально хватило бы, но с запасом меньше чем в десять раз.

API, модель данных и общая схема

POST /v1/links                       { "url": "https://shop.example/item/42?ref=mail" }
201 Created                          { "code": "4WveT3H", "short": "https://sho.rt/4WveT3H" }

GET /4WveT3H
302 Found
Location: https://shop.example/item/42?ref=mail
create table link(
  code text primary key,           -- 7 символов base62
  url text not null,
  owner_id bigint,
  created_at timestamptz not null default now(),
  expires_at timestamptz
);

Переходы обслуживает отдельный сервис без состояния: он ищет код в Redis, при промахе — в базе, отвечает редиректом и отправляет событие перехода в Kafka, не дожидаясь подтверждения записи статистики. Создание ссылок — отдельный API с другой нагрузкой и другими требованиями. Для 3 ТБ данных подходит PostgreSQL с шардированием по коду или ключ-значение хранилище вроде DynamoDB и Cassandra; выбор определяют не запросы — они все по ключу, — а то, что удобнее эксплуатировать команде.

Генерация ключа: хеш даёт коллизии, счётчик — предсказуемость

Первая идея — взять хеш длинной ссылки и первые 7 символов в base62: одинаковые ссылки получат одинаковый код, хранить счётчик не нужно. Демо ShortenerDemo.java проверяет это на 10 млн разных ссылок:

== hash prefix as key: collisions among 10,000,000 distinct URLs
   6 chars (62^6 = 5.7e+10 keys): 830 collisions, birthday estimate 880
   7 chars (62^7 = 3.5e+12 keys): 12 collisions, birthday estimate 14

Пространство в 350 000 раз больше числа ссылок, но коллизий 12. Это парадокс дней рождения: число совпадающих пар растёт как квадрат числа элементов, n²/2N, и при 10 млн ссылок в пространстве 3,5 трлн ожидается 14 коллизий — демо дало 12. К 6 млрд ссылок их будут миллионы. Значит, при хеше нужна проверка «код занят — взять следующий вариант» (добавить соль и перехешировать), а это запрос к базе на каждую попытку и гонка между двумя одновременными вставками, которую решает только уникальный индекс.

== counter-based keys
   counter:  4c92 4c93 4c94 4c95
   permuted: 4WveT3H 6Fb4HBe a15fxdx dFFKTrY
   permutation of 1,000,000 ids: 1000000 distinct, max code length 7

Счётчик уникален по построению, но коды идут подряд: зная свой код, можно перебрать соседние и найти чужие ссылки, часто приватные. Решение — пропустить номер через обратимую перестановку: сеть Фейстеля из нескольких раундов над 40 битами превращает соседние номера в непохожие коды, а обратимость гарантирует, что разные номера дают разные коды, — миллион номеров дал миллион различных кодов. 2⁴⁰ — 1,1 трлн номеров, меньше 62⁷, поэтому код не длиннее 7 символов. Это не шифрование: ключи раундов надо держать в секрете, а для настоящей стойкости используют блочный шифр с форматом, сохраняющим длину.

// Сеть Фейстеля на 40 битах: обратимая перестановка, поэтому разные id дают разные коды.
static long feistel(long x) {
    long l = x >>> 20, r = x & 0xFFFFF;
    long[] keys = {0x5bd1e995L, 0x1b873593L, 0x2c1b3c6dL, 0x297a2d39L};
    for (long k : keys) {
        long f = ((r * 0x9E3779B1L) ^ k) & 0xFFFFF;   // любая функция: обратимость даёт сама схема
        long t = l ^ f; l = r; r = t;
    }
    return (l << 20) | r;
}

Чтобы счётчик не стал узким местом, сервисы берут у него блоки — по 1 000 номеров за раз — и раздают их из памяти, как allocationSize в Hibernate из Unique ID Generation. 40 запросов в секунду — это поход к счётчику раз в 25 секунд на экземпляр. Если нужна одна короткая ссылка для одной длинной, хранят ещё индекс по хешу длинной ссылки и сначала ищут в нём.

Чтение: закон Ципфа, кеш и выбор между 301 и 302

== LRU cache hit rate, 10,000,000 links, 20,000,000 Zipf(1.0) reads
   cache   0.1% of links (   10,000): hit rate 48.5%
   cache   1.0% of links (  100,000): hit rate 64.1%
   cache  10.0% of links (1,000,000): hit rate 79.8%

Переходы распределены крайне неравномерно: ссылку из рассылки на миллион адресов открывают сотни тысяч раз, а большинство ссылок — единицы раз. Демо моделирует это законом Ципфа с показателем 1 — частота k-й по популярности ссылки пропорциональна 1/k. LRU-кеш на 0,1 % ссылок уже обслуживает почти половину переходов, на 1 % — 64 %. Для 6 млрд ссылок 1 % — 60 млн записей по ~200 байт, около 12 ГБ: один узел Redis. Реальный показатель может отличаться — его измеряют по логам переходов, — но форма кривой типична: первые проценты кеша дают основную выгоду, каждый следующий — всё меньше. Самые горячие ссылки дополнительно держат в локальном кеше сервиса, чтобы не упираться в один узел Redis, как в Caching.

ОтветПоведение браузераКогда
301 Moved PermanentlyКеширует редирект; повторные переходы не доходят до сервисаСтатистика не нужна, ссылка неизменна
302 Found / 307Не кеширует без явных заголовков; каждый переход — запросНужна статистика, ссылку можно изменить или отключить

301 снижает нагрузку бесплатно, но сервис больше не видит повторных переходов и не может отозвать ссылку, если она оказалась фишинговой: браузер помнит редирект. Большинство сокращателей отвечают 302 и платят за это нагрузкой. Можно и промежуточный вариант: 302 с Cache-Control: max-age=300 — повтор в течение пяти минут обходится без сервиса.

Статистику не пишут в базу ссылок синхронно: это превратило бы каждый переход в запись, а горячую ссылку — в горячую строку с конкуренцией за блокировку. Сервис отправляет событие в Kafka и сразу отвечает; потребитель агрегирует клики по минутам и пишет счётчики пачками, как в Kafka Consumer. Потеря нескольких событий при сбое допустима — статистика переходов не деньги.

Сбои и компромиссы

СбойЧто происходитЧто делаем

Kafka недоступнаСобытия кликов не отправляютсяПереход отвечает всё равно; события в локальный буфер или теряются
Счётчик недоступенНельзя выдать новые кодыЭкземпляры дорабатывают выданные блоки; переходы не затронуты
ЗлоупотребленияФишинговые ссылки, перебор кодовПроверка URL по спискам, лимиты на создание, 302 для возможности отзыва

Компромиссы, которые стоит назвать: 302 против 301 (статистика и отзыв против нагрузки), счётчик против хеша (уникальность без проверок против дедупликации одинаковых ссылок), синхронная статистика против асинхронной (точность против задержки и нагрузки на базу). Переходы важнее создания: при перегрузке создание можно ограничить, а переходы — нет, иначе ломаются ссылки, уже разосланные по всему интернету.

7 символов base62 — это 3,5 трлн кодов, поэтому коллизии префикса хеша на миллионах ссылок можно не учитывать.

Коллизии растут как квадрат числа ссылок: на 10 млн ссылок демо нашло 12 совпадений при 7 символах и 830 при 6. Без проверки занятости и уникального индекса две разные ссылки получат один код, и одна из них будет вести не туда.

  • 40 созданий и ~4 000 переходов в секунду, 3 ТБ за 5 лет: главная нагрузка — чтение по ключу.
  • Префикс хеша: 12 коллизий на 10 млн ссылок при 7 символах, по оценке n²/2N — 14.
  • Счётчик блоками + обратимая перестановка (Фейстель на 40 битах): уникальные непредсказуемые коды до 7 символов.
  • Zipf(1): кеш на 1 % ссылок — 64 % попаданий; 1 % от 6 млрд — около 12 ГБ.
  • 302 — статистика и отзыв, 301 — меньше нагрузки; клики — асинхронно через Kafka.

На собеседовании

Спроектируйте сокращатель ссылок

Уточнить требования (свои коды, срок жизни, статистика), оценить: 100 млн ссылок в месяц — 40 в секунду, переходов в сто раз больше. Отдельный stateless-сервис переходов с Redis перед хранилищем ключ-значение, отдельный API создания. Коды — из счётчика блоками, 7 символов base62, через обратимую перестановку против перебора. Редирект 302, клики — событиями в Kafka.

  • Хеш-префикс требует проверки коллизий: их число растёт как n².
  • Кеш по закону Ципфа: малый кеш даёт большую долю попаданий.
  • Переходы приоритетнее создания при перегрузке.

Как генерировать короткий код и избежать коллизий?

Счётчик с кодированием в base62 даёт уникальные коды без проверок; чтобы коды не шли подряд, номер пропускают через обратимую перестановку. Хеш от длинной ссылки даёт одинаковые коды для одинаковых ссылок, но требует проверки занятости и повторной попытки с солью при коллизии, а гонку решает уникальный индекс.

  • Ожидаемое число коллизий — n²/2N: 14 на 10 млн при 62⁷.
  • Счётчик раздают блоками, чтобы не обращаться к нему на каждую ссылку.
Что не так с этой генерацией кода? 
String code = Base62.encode(md5(longUrl)).substring(0, 7);
if (!repository.existsByCode(code)) {
    repository.save(new Link(code, longUrl));
}
return code;

При коллизии с другой ссылкой код молча возвращается, но ведёт на чужую ссылку: проверка «существует» не отличает ту же ссылку от другой. Между existsByCode и save есть гонка — две одновременные вставки разных ссылок с одним кодом. Нужно: уникальный индекс на code, при конфликте сравнить сохранённый URL и, если он другой, перехешировать с солью; или перейти на счётчик.

301 или 302 для редиректа?

301 кешируется браузером: повторные переходы не доходят до сервиса, нагрузка ниже, но пропадает статистика и возможность отозвать ссылку. 302 приходит на сервис каждый раз: статистика точная, ссылку можно изменить или заблокировать. Сокращатели с аналитикой выбирают 302.

  • Промежуточный вариант — 302 с коротким Cache-Control.
  • Отзыв фишинговых ссылок невозможен, если браузеры закешировали 301.

  • RFC 9110: Redirection 3xx — семантика 301, 302, 307 и кеширование.
  • Michael Luby, Charles Rackoff, «How to Construct Pseudorandom Permutations from Pseudorandom Functions» — сеть Фейстеля.
