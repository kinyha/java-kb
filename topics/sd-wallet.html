Digital Wallet

Кошелёк хранит деньги пользователей и переводит их между счетами. Главное требование — сумма денег в системе не меняется сама: перевод списывает ровно столько, сколько зачисляет, и не уводит баланс в минус. Три механизма. Изменение баланса — одной атомарной операцией в базе (условный UPDATE), а не «прочитать в приложении, посчитать, записать»: в демо наивный вариант создал из воздуха 5 662,99 на 2 000 переводов. Строки обоих счетов блокируют в одном порядке, иначе встречные переводы дают взаимные блокировки — 189 из 200 в демо. Каждый перевод записывают двумя проводками с противоположными знаками: сумма всех проводок — ноль, баланс восстанавливается из них на любой момент. При шардировании перевод между шардами становится сагой.

Требования и нагрузка

Кошелёк для 50 млн пользователей: пополнение с карты, перевод другому пользователю, оплата у магазина, история операций и выписка. Сумма переводов в системе должна сходиться до копейки, каждая операция — объяснима годами для аудита, отрицательный баланс запрещён. Переводы — около 20 млн в сутки: ≈ 230 в секунду, в пик ×5 — около 1 200. Нагрузка невелика, сложность в корректности при конкурентных операциях и в горячих счетах: у крупного магазина тысячи зачислений в секунду на одну строку.

Приём денег с карты через провайдера разобран в Payment System; здесь — внутренний учёт: счета, переводы, проводки. Блокировки и уровни изоляции PostgreSQL — в Locks и Transactions. Демо WalletDemo.java выполняет переводы в PostgreSQL 17 из 16 потоков; балансы — в копейках, 1 000 000 = 10 000,00.

create table account(id text primary key, balance bigint not null check (balance >= 0));
create table entry(transfer_id bigint, account text, amount bigint, at timestamptz default clock_timestamp());
-- плюс transfer(id, idempotency_key unique, from, to, amount, status) для повторов клиента

Прочитать, посчитать, записать — и деньги появляются из воздуха

// Наивно: прочитать балансы, проверить в Java, записать новые значения.
static void naive(Connection c, String from, String to, long amount) throws SQLException {
    long a = balance(c, from), b = balance(c, to);
    if (a < amount) return;
    set(c, from, a - amount);
    set(c, to, b + amount);
}

// Условный UPDATE: проверка и изменение — одна операция под блокировкой строки.
static void conditional(Connection c, String from, String to, long amount) throws SQLException {
    var debit = c.prepareStatement("update account set balance = balance - ? where id = ? and balance >= ?");
    debit.setLong(1, amount); debit.setString(2, from); debit.setLong(3, amount);
    if (debit.executeUpdate() == 0) { c.rollback(); return; }        // недостаточно средств
    var credit = c.prepareStatement("update account set balance = balance + ? where id = ?");
    credit.setLong(1, amount); credit.setString(2, to);
    credit.executeUpdate();
}

Наивный вариант за 2 000 переводов увеличил сумму на четырёх счетах с 40 000,00 до 45 662,99: потерянные обновления чаще съедали списания, чем зачисления, и деньги «появились». Условный UPDATE сохранил сумму до копейки, а условие balance >= ? внутри того же оператора не даёт уйти в минус даже при одновременных списаниях — проверка в Java после чтения такой гарантии не даёт. Альтернативы — SELECT ... FOR UPDATE перед вычислением или уровень SERIALIZABLE с повтором при ошибке сериализации; оптимистичная блокировка по версии строки работает так же, но при горячих счетах даёт много повторов.

Строки failed — не ошибки денег: это транзакции, которые PostgreSQL прервал из-за взаимной блокировки, и их сумма откатилась целиком. Откуда они — следующий шаг.

Встречные переводы блокируют друг друга, если порядок разный

Перевод anna → boris блокирует сначала anna, потом boris; встречный boris → anna — наоборот. Если оба успели взять первую блокировку, каждый ждёт строку другого. PostgreSQL через deadlock_timeout (1 секунда по умолчанию) находит цикл и прерывает одну из транзакций с SQLSTATE 40P01. Сумма не пострадала — прерванная транзакция откатилась, — но 189 из 200 переводов не прошли, а каждый ждал секунду; поэтому этот прогон демо самый долгий. Если блокировать строки в одном порядке для всех — например, по возрастанию id счёта, — цикл невозможен: ноль блокировок. Для прерванных из-за взаимной блокировки или ошибки сериализации транзакций нужен повтор, и он безопасен только с ключом идемпотентности перевода.

Проводки: баланс — это сумма записей, а не просто число

== ledger: balance is a sum of entries
   anna   stored 977000, from entries 977000
   boris  stored 1023000, from entries 1023000
   sum of all entries: 0
   anna as of after transfer 2: 982000

Поле balance отвечает на вопрос «сколько сейчас», но не «почему столько» и не «сколько было вчера в 18:00». Поэтому каждый перевод пишет в журнал две проводки в той же транзакции: минус у отправителя, плюс у получателя. Из демо видно три свойства. Сохранённый баланс совпадает с суммой проводок — это проверяют регулярно, и расхождение означает ошибку в коде. Сумма всех проводок — ноль: деньги только перемещаются. Баланс на любой момент — сумма проводок до этого момента: после второго перевода у anna было 982 000, а не нынешние 977 000.

Двойная запись пришла из бухгалтерии, и в кошельке у неё те же правила: проводки не изменяют и не удаляют, ошибку исправляют сторнирующей проводкой; внешние деньги проходят через технические счета — пополнение с карты записывается как минус на счёте «расчёты с провайдером» и плюс у пользователя. Тогда сверка с провайдером из Payment System — это сверка одного технического счёта с файлом провайдера.

Следующий шаг — event sourcing: источником истины становится журнал событий («переведено», «пополнено»), а баланс — проекция, которую можно пересчитать заново. Для кошелька это естественно — журнал проводок уже почти и есть журнал событий. Чтобы не суммировать годы проводок на каждый запрос, хранят снимки баланса на начало дня или месяца и досчитывают от них, как разобрано в Event-driven, CQRS, Event Sourcing.

Масштабирование: шарды, переводы между шардами и горячие счета

1 200 переводов в секунду — нагрузка для одного узла PostgreSQL. Шардирование по id счёта понадобится, когда вырастут объём журнала и число пользователей, и тогда перевод между счетами на разных шардах перестаёт быть одной транзакцией. Его делают сагой: списать у отправителя на шарде A с зачислением на технический счёт «в пути», затем зачислить получателю на шарде B, при ошибке — компенсирующей проводкой вернуть деньги, как в Distributed Transactions. Технический счёт «в пути» сохраняет инвариант суммы нулём на каждом шаге и показывает, сколько денег сейчас в полёте.

Горячий счёт — крупный магазин, получающий тысячи зачислений в секунду, — упирается в блокировку одной строки: все транзакции ждут друг друга. Варианты: разбить счёт на N подсчетов и зачислять на случайный, суммируя их при чтении; копить зачисления в журнале и обновлять баланс пачкой раз в секунду, если магазину не нужен баланс до копейки в реальном времени; не хранить баланс зачислений вовсе, а считать его из проводок. Списания с горячего счёта редки — выплата раз в день, — поэтому для них достаточно блокировки всех подсчетов разом.

Достаточно проверить баланс в приложении перед списанием: if (balance >= amount) save(balance - amount), а транзакция базы защитит от гонок.

В READ COMMITTED транзакция не защищает от потерянного обновления: обе транзакции прочитали старое значение и записали посчитанное от него. В демо так сумма на счетах выросла на 5 662,99. Нужен условный UPDATE с вычислением в базе, SELECT FOR UPDATE или SERIALIZABLE с повтором.

  • Изменять баланс в базе одним оператором: balance = balance - ? where balance >= ?; наивный вариант исказил сумму на 5 662,99.
  • Блокировать строки счетов в одном порядке: иначе 189 взаимных блокировок из 200 встречных переводов, по порядку — 0.
  • Двойная запись: две проводки на перевод, сумма всех — 0, баланс на любой момент — сумма проводок до него.
  • Повтор прерванных транзакций — только с ключом идемпотентности перевода.
  • Между шардами — сага через технический счёт «в пути»; горячие счета — подсчета или пакетное обновление.

На собеседовании

Как реализовать перевод между счетами без гонок?

В одной транзакции: списание условным UPDATE balance = balance - x where id = ? and balance >= x — если изменено ноль строк, средств не хватает; затем зачисление balance = balance + x; затем две проводки в журнал. Строки счетов блокировать в одном порядке, например по id, чтобы встречные переводы не давали взаимных блокировок. Перевод — с ключом идемпотентности, чтобы повтор клиента не перевёл дважды.

  • Чтение в приложении и запись вычисленного значения теряют обновления в READ COMMITTED.
  • Альтернативы: SELECT FOR UPDATE, SERIALIZABLE с повтором, оптимистичная версия.
  • Прерванные по 40P01 и 40001 транзакции повторять с тем же ключом.
Что не так с этим переводом? 
@Transactional
public void transfer(long fromId, long toId, BigDecimal amount) {
    Account from = accounts.findById(fromId).orElseThrow();
    Account to = accounts.findById(toId).orElseThrow();
    if (from.getBalance().compareTo(amount) < 0) throw new InsufficientFunds();
    from.setBalance(from.getBalance().subtract(amount));
    to.setBalance(to.getBalance().add(amount));
}

Чтение без блокировки и запись вычисленного значения: два одновременных перевода с одного счёта оба пройдут проверку и запишут каждый своё — потерянное обновление и возможный минус. Нужна блокировка (@Lock(PESSIMISTIC_WRITE) в порядке возрастания id), @Version с повтором или условный UPDATE. Нет проводок — баланс невозможно объяснить и проверить. Нет ключа идемпотентности — повтор запроса переведёт дважды.

Зачем журнал проводок, если есть поле баланса?

Поле отвечает только «сколько сейчас». Проводки объясняют каждое изменение, позволяют получить баланс на любой момент и проверить сохранённый баланс пересчётом. По двойной записи каждый перевод — две проводки с противоположными знаками, сумма всех проводок — ноль; ненулевая сумма означает ошибку. Проводки не меняют и не удаляют, исправляют сторно.

  • Внешние деньги — через технические счета: провайдер, «в пути», комиссии.
  • Снимки баланса, чтобы не суммировать весь журнал.
  • Журнал проводок — готовая основа для event sourcing.

Что делать с горячим счётом и переводами между шардами?

Горячий счёт разбивают на подсчета и зачисляют на случайный, а баланс получают суммой; или копят зачисления и обновляют баланс пачкой. Перевод между шардами — сага: списание на шарде отправителя с зачислением на технический счёт «в пути», затем зачисление получателю, при ошибке — компенсация.

  • Технический счёт «в пути» сохраняет нулевую сумму на каждом шаге саги.
  • Шардировать по счёту, чтобы большинство операций было внутри шарда.
