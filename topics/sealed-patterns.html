Sealed & Pattern Matching

Платёж может завершиться успехом, отказом или просьбой повторить попытку. Sealed-тип ограничивает варианты результата, а pattern matching проверяет вариант и даёт доступ к его данным. Компилятор помогает обнаружить пропущенный вариант, но не проверяет бизнес-условия и отсутствие null внутри данных. При разборе проследи три вещи: какие типы возможны, что извлекает pattern и какая ветка первой подходит.

Новый результат должен заставить пересмотреть обработчики

Сервис раньше возвращал Paid или Rejected. В обработчике два instanceof и общий ответ 500 для всего остального. Позже провайдер добавил Retry: это временный результат с задержкой, а не внутренняя ошибка. Код продолжил компилироваться и стал отправлять 500 вместо планирования повторной попытки. Проблема не в cast, а в том, что обработчик не выражает обещание разобрать все варианты.

В PatternDemo.java результат задан sealed interface. Варианты содержат разные данные, поэтому один enum с флагами потребовал бы дополнительных проверок: например, у отказа нет суммы успешного платежа. Отдельные типы позволяют связать данные с конкретным исходом.

// Фрагмент PatternDemo.java; JDK 21, без --enable-preview
sealed interface Outcome permits Paid, Rejected, Retry {}
record Money(long minorUnits, String currency) {}
record Paid(String id, Money amount) implements Outcome {}
record Rejected(String reason) implements Outcome {}
record Retry(int afterSeconds) implements Outcome {}

static int legacyStatus(Outcome outcome) {
    if (outcome instanceof Paid) return 200;
    if (outcome instanceof Rejected) return 422;
    return 500; // новый Retry попадает сюда без ошибки компиляции
}
System.out.println("legacy retry=" + legacyStatus(new Retry(30)));
legacy retry=500

У switch expression есть обязанность вернуть значение или завершиться исключением для каждого варианта. Если перечислить Paid и Rejected, но забыть Retry, javac отвергнет код. Sealed даёт компилятору сведения, которых нет у открытого интерфейса: список допустимых прямых потомков. При повторной компиляции нового обработчика этот список превращается в полезную проверку полноты.

// negative/MissingCase.java намеренно не компилируется; imports не нужны
sealed interface Outcome permits Paid, Rejected, Retry {}
record Paid() implements Outcome {}
record Rejected() implements Outcome {}
record Retry() implements Outcome {}
static int status(Outcome value) {
    return switch (value) {
        case Paid p -> 200;
        case Rejected r -> 422;
    }; // Retry не покрыт; добавление default убрало бы эту проверку вариантов
}
error: the switch expression does not cover all possible input values

Это сокращённая диагностика настоящего запуска javac: путь, указатель позиции и итоговое «1 error» опущены. Полные команды и все отрицательные примеры есть в README. В этой теме instanceof patterns — постоянная возможность Java 16, sealed — Java 17, record patterns и pattern switch — Java 21. Все демо запущены на JDK 21 без preview.

Sealed закрывает прямые ветви, а каждый потомок решает судьбу своей

Permits перечисляет именно прямые subclasses или subinterfaces. Само перечисление не создаёт наследование: Paid должен написать implements Outcome. Такой потомок обязан определить дальнейшее расширение. Класс выбирает final, sealed или non-sealed; интерфейс — sealed или non-sealed. Record уже неявно final.

В HierarchyDemo.java обычные исходы закрыты, временная ошибка уточняется ещё на одном уровне, а External оставляет точку расширения для провайдера. Это дерево ограничивает не все конечные классы навсегда, а каждую ветвь согласно её объявлению. Любая новая реализация External всё ещё является Outcome.

// Фрагмент HierarchyDemo.java; отдельная модель с точкой расширения
sealed interface Outcome permits Paid, Rejected, Temporary {}
record Paid(String id) implements Outcome {}
record Rejected(String reason) implements Outcome {}
sealed interface Temporary extends Outcome permits Retry, External {}
record Retry(int seconds) implements Temporary {}
non-sealed interface External extends Temporary {}
record ProviderWait(String provider) implements External {}

static String route(Outcome value) {
    return switch (value) {
        case Paid p -> "paid";
        case Rejected r -> "rejected";
        case Retry r -> "retry";
        case External e -> "external"; // достаточно охватить открытую ветвь её типом
    };
}
System.out.println("sealed=" + Outcome.class.isSealed());
System.out.println("direct=" + Arrays.stream(Outcome.class.getPermittedSubclasses())
        .map(Class::getSimpleName).sorted().toList());
System.out.println("external sealed=" + External.class.isSealed());
System.out.println("provider=" + route(new ProviderWait("bank")));
sealed=true
direct=[Paid, Rejected, Temporary]
external sealed=false
provider=external

В named module разрешённые прямые потомки должны находиться в том же модуле; в unnamed module — в том же package. Это одна область сопровождения модели, а не список плагинов из любых библиотек. Если подходящие объявления находятся в одной compilation unit, permits можно опустить: компилятор выведет прямых потомков с canonical names. Это не поиск всех классов в package; local и anonymous классы в такой список не попадают.

Sealed не означает abstract или immutable. Sealed class может быть конкретным и иметь mutable-поля. Тогда одних case для потомков недостаточно: возможен экземпляр самого базового класса. Правило исчерпывающего покрытия через permits относится к sealed interface или abstract sealed class. Non-sealed допустим, когда у типа есть sealed прямой родитель, чьё ограничение он продолжает; это не универсальный модификатор обычного интерфейса. JVM также проверяет разрешённость наследования: обход через старый или вручную созданный class-файл не превращает закрытую ветвь в открытую.

Pattern-переменная существует там, куда можно попасть только после совпадения

Старый instanceof отвечал только на вопрос о типе, затем приходилось повторять тип в cast. value instanceof Paid p соединяет проверку с получением ссылки подходящего типа. P не новый объект и не копия: это тот же target, доступный через переменную Paid. При несовпадении и при null выражение возвращает false.

Область видимости определяется потоком управления — flow scoping. В правую часть && попадём только после true слева, поэтому p уже есть. При отрицательной проверке с ранним return до следующих строк доходят только Paid. Компилятор знает этот факт и разрешает p после if.

// Фрагмент PatternDemo.java; Paid и Money объявлены в первом шаге
static String paidId(Object value) {
    if (!(value instanceof Paid p)) return "not paid";
    return p.id(); // путь с несовпадением уже завершился
}
static boolean positive(Object value) {
    return value instanceof Paid p && p.amount() != null
            && p.amount().minorUnits() > 0;
}
Paid paid = new Paid("p1", new Money(100, "EUR"));
System.out.println("id=" + paidId(paid) + ", positive=" + positive(paid));
System.out.println("null instanceof=" + positive(null));
id=p1, positive=true
null instanceof=false

Для || логика обратная: если matching не прошёл, нужно вычислить правую часть. Там ещё нет pattern-переменной. Если убрать return из отрицательной ветки и позволить ей продолжиться, p также исчезнет из области видимости после if. Это не требование «обязательно использовать фигурные скобки», а доказательство, какие пути способны дойти до чтения переменной.

// negative/OrScope.java: правая часть достижима без совпадения
return value instanceof String s || !s.isEmpty();
error: cannot find symbol
  symbol:   variable s

Pattern-переменные не являются неявно final; при необходимости final пишут явно. Но изменять такую ссылку обычно мешает смыслу проверки. Из matching не следует глубокая неизменяемость объекта: Paid из примера — record, а его контракт и граф владения разобраны в Records. Sealed для instanceof вообще не требуется: String, коллекция или обычный открытый интерфейс тоже могут быть pattern-типом.

Record pattern извлекает компоненты через accessors и проверяет вложенную структуру

Paid p даёт весь объект, а Paid(var id, Money(var units, var currency)) проверяет Paid, получает id и amount через accessors, затем проверяет amount как Money и получает его компоненты. Количество и порядок component patterns соответствуют заголовку record. Дополнительный конструктор не задаёт новую форму деконструкции.

Var в component pattern выводит статический тип компонента: здесь id и currency — String, units — long. Это не динамический тип и не разрешение пропустить проверки. Если компонент объявлен Object, более узкий String pattern будет дополнительным условием. Generic record patterns также выводят type arguments из статического контекста, но не восстанавливают потерянную при erasure информацию.

// GenericDemo.java: Text допустим для Result<String>, но не Result<Integer>
sealed interface Result<T> permits Text, Value {}
record Text(String text) implements Result<String> {}
record Value<T>(T value) implements Result<T> {}
static int number(Result<Integer> result) {
    return switch (result) {
        case Value<Integer>(var n) -> n; // n имеет тип Integer
    }; // Text не нужен для полноты именно этого selector type
}
System.out.println("number=" + number(new Value<>(42)));
number=42

Для Object нельзя проверить Box<String>(var s), потому что такой cast потребовал бы unchecked conversion. В negative/Unchecked.java javac сообщает Object cannot be safely cast to Box<String>. Если target имеет известный Box<String> тип, эта деконструкция допустима. Проверять сам компонент через Box(String s) — другая операция: она смотрит на значение внутри, а не доказывает generic-тип всего контейнера.

Accessors действительно вызываются. Record pattern не читает private-поля напрямую и не обходит переопределённый метод. Поэтому defensive copy в accessor может выделять память, а исключение accessor прерывает matching: оно оборачивается в MatchException с исходной причиной. Скрывать I/O или побочные эффекты в accessor — плохая опора для декларативного разбора. В EdgeDemo этот случай показан отдельно.

Под капотом: почему это не универсальная деконструкция любого класса

На Java 21 record pattern опирается на известные компилятору record components и методы доступа. Обычный JavaBean с getAmount не получает такой pattern автоматически. Top-level type patterns на этой версии используют reference types; primitive-компонент record может извлекаться pattern того же primitive-типа. Это не общее разрешение написать switch с boolean или long selector на Java 21. Более поздние возможности языка надо оценивать отдельно, вместе с их preview-статусом.

Switch выбирает первое совпадение, а guard уточняет данные после деконструкции

Успешный платёж в EUR с положительной суммой идёт в автоматическое проведение. Остальные Paid отправляются на ручной разбор, Rejected сохраняет причину, Retry планирует задержку. Здесь pattern отвечает за тип и структуру, а when — за бизнес-условие. Guard выполняется только после совпадения pattern; его переменные уже инициализированы.

// Фрагмент PatternDemo.java; типы Outcome, Paid, Money — в первом шаге
static String route(Outcome outcome) {
    return switch (outcome) {
        case null -> "bad request";
        case Paid(var id, Money(var units, var currency))
                when units > 0 && "EUR".equals(currency) -> "book:" + id;
        case Paid p -> "manual"; // guard false или amount == null
        case Rejected(var reason) -> "reject:" + reason;
        case Retry(var seconds) -> "retry:" + seconds;
    };
}
System.out.println(route(new Paid("p1", new Money(100, "EUR"))));
System.out.println(route(new Paid("p2", new Money(-1, "EUR"))));
System.out.println(route(new Paid("p3", null)));
System.out.println(route(new Rejected("limit")));
System.out.println(route(new Retry(30)));
System.out.println(route(null));
book:p1
manual
manual
reject:limit
retry:30
bad request

Если поставить case Paid p первым, специализированный Paid pattern после него станет недостижимым. Это dominance: все значения поздней ветки уже принимает ранняя. Аналогично CharSequence перед String закрывает String, и javac выдаёт this case label is dominated by a preceding case label. У unguarded-ветки шире покрытие, чем у того же pattern с guard.

Компилятор не решает произвольную бизнес-логику guard. Ветка case Integer i when i > 0 перед case 1 допустима, но для 1 вернётся positive, а не one. Этот отдельный опыт PatternDemo печатает guarded 1=positive. Константы ставь перед широкими guarded patterns, узкие условия — перед общей веткой. Guard с константным true имеет особое правило и учитывается как безусловный.

// Фрагмент PatternDemo.java: логически закрытый case 1 всё же компилируется
static String guardedOrder(Integer n) {
    return switch (n) {
        case Integer i when i > 0 -> "positive";
        case 1 -> "one"; // javac не доказывает свойства произвольного guard
        case Integer i -> "other";
    };
}
System.out.println("guarded 1=" + guardedOrder(1));
guarded 1=positive

Полнота — проверка type coverage, а не «сумма условий вроде n > 0 и n <= 0». Обычные guards не доказывают исчерпывающий охват типа; нужна ветка без такого условия. Все switch expressions и enhanced switch statements с patterns должны быть exhaustive. Устаревший statement с обычными константами может иметь другие требования. Синтаксис выражения, yield и fall-through относится к теме о switch expressions; здесь стрелки исключают проваливание в следующую ветку.

Null selector, null компонент и сбой accessor — три разных границы

Default означает «прочие значения selector», но не заменяет case null. Если selector равен null и такой метки нет, pattern switch на Java 21 бросает NullPointerException. Даже case Object o этого не меняет. Можно явно отклонить null, обработать его отдельно или объединить только в форме case null, default. Выбор зависит от контракта входа.

// Фрагмент EdgeDemo.java; show печатает имя пойманного RuntimeException
static String withDefault(Object value) {
    return switch (value) {
        case String s -> "string";
        default -> "other"; // null сюда не попадает
    };
}
static String totalType(Object value) {
    return switch (value) { case Object o -> "object"; };
}
show("default null", () -> withDefault(null));
show("Object null", () -> totalType(null));
default null=NullPointerException
Object null=NullPointerException

Сам record pattern тоже не совпадает с null. Но его компонентный type pattern может принимать null, если безусловен для статического типа компонента. Поэтому Box(var text) подходит Box с null строкой, а Envelope(Box(var text)) не подходит Envelope с null вместо Box. Это различие между «значение компонента получено» и «вложенный объект существует и его можно разобрать».

// Фрагмент EdgeDemo.java; выведи результат до раскрытия
record Box(String value) {}
record Envelope(Box box) {}
static String nested(Envelope envelope) {
    return switch (envelope) {
        case Envelope(Box(var text)) -> String.valueOf(text);
    }; // javac считает покрытие Envelope исчерпывающим
}
System.out.println("null record=" + ((Object) null instanceof Box(var text)));
Box box = new Box(null);
if (box instanceof Box(var text)) System.out.println("component=" + text);
show("null nested", () -> nested(new Envelope(null)));
System.out.println("nested component=" + nested(new Envelope(new Box(null))));
null record=false
component=null
null nested=MatchException
nested component=null

Null nested не равен null selector: Envelope существует, но единственный вложенный pattern не подошёл. Runtime сообщает MatchException для неожиданной невозможности выбрать ветку у статически полного switch. Защитой может быть constructor invariant, запрещающий null Box, либо отдельный fallback для Envelope. Case null вверху не лечит null внутри Envelope.

// Фрагмент EdgeDemo.java: pattern вызывает accessor, а не читает поле
record Broken(int value) {
    public int value() { throw new IllegalStateException("broken accessor"); }
}
try {
    if (new Broken(1) instanceof Broken(var value)) System.out.println(value);
} catch (MatchException e) {
    System.out.println("accessor=" + e.getClass().getSimpleName()
            + ", cause=" + e.getCause().getClass().getSimpleName());
}
accessor=MatchException, cause=IllegalStateException

Guard — обычное выражение, выполняемое после matching. Его собственное исключение распространяется как исключение выражения; специальное оборачивание относится к accessor во время record matching. Поэтому не стоит ловить MatchException как универсальный сигнал «платёж временно не прошёл». Retry — вариант доменной модели, а MatchException показывает нарушение предпосылок разбора.

Исчерпывающий разбор требует согласованной версии модели и клиента

При добавлении Retry и полной пересборке компилятор покажет обработчики без этой ветки. Но библиотеку результата можно обновить отдельно от клиентского class-файла. Добавление разрешённого потомка само по себе сохраняет binary compatibility: старый клиент способен загрузиться. Его прежнее доказательство полноты больше не отражает runtime-модель.

В Client.java v1 знает два типа. Затем опыт заменяет только API-классы на v2 с Retry, сохраняя Client.class. Run из v2 передаёт Retry в старый обработчик. Так мы проверяем реальную отдельную компиляцию, а не имитируем невозможный тип через cast.

// evolution/v1: Client.class компилируется с API из двух вариантов
public sealed interface Outcome permits Paid, Rejected {}
record Paid() implements Outcome {}
record Rejected() implements Outcome {}
public static String route(Outcome value) {
    return switch (value) {
        case Paid p -> "paid";
        case Rejected r -> "rejected";
    };
}
// evolution/v2: Outcome заменён, Client.class оставлен старым
public sealed interface Outcome permits Paid, Rejected, Retry {}
record Paid() implements Outcome {}
record Rejected() implements Outcome {}
record Retry() implements Outcome {}
try { System.out.println(Client.route(new Retry())); }
catch (MatchException e) {
    System.out.println("old client=" + e.getClass().getSimpleName());
}
old client=MatchException

Фрагмент показывает две разные версии файла, а не одну compilation unit; README даёт команды с отдельными каталогами. Javap подтвердил в Client.class аварийную ветку с java.lang.MatchException. Повторная компиляция Client.java уже против API v2 отвергает неполный switch с той же диагностикой, что в первом шаге. Совместимость загрузки не означает прежнюю семантику всех вызовов.

Добавить default — осознанный выбор политики эволюции. Если это закрытая доменная модель, отсутствие default заставляет при пересборке принять решение о новом варианте. Для открытой External-ветви общий case External уже выражает поддержку расширений. На внешней границе всё равно нужны проверка входных данных, версионирование сообщения и обработка неизвестных вариантов протокола: Java permits не валидирует JSON.

Выбирай sealed, когда варианты принадлежат одной модели и один владелец контролирует её расширение. Если каждое расширение само знает поведение, обычный полиморфный метод может дать проще поддерживаемый код. Pattern switch полезен для нескольких внешних операций над известными вариантами, но большой switch в каждом слое заставляет менять много мест. Sealed не заменяет SPI для независимых плагинов, records не делают результат глубоко immutable, а matching не является проверкой бизнес-инвариантов.

  • Sealed ограничивает прямых потомков; final закрывает ветвь, non-sealed открывает её, sealed продолжает контроль.
  • Instanceof pattern связывает проверку с доступом к тому же объекту; flow scoping следует успешным путям.
  • Record pattern вызывает accessors и рекурсивно проверяет компоненты.
  • Switch выбирает первый подходящий case; guard уточняет значения, а dominance запрещает заведомо закрытые ветки.
  • Exhaustiveness не доказывает отсутствие null и не защищает старый class-файл от эволюции API.
  • Null selector без case null даёт NPE; неподошедшая вложенная структура полного switch или сбой accessor могут дать MatchException.

На собеседовании

Зачем sealed и чем он отличается от final и non-sealed?

Sealed позволяет владельцу модели ограничить её прямых наследников. Например, Outcome может быть Paid, Rejected или Retry, и посторонний класс не реализует его напрямую. Permits перечисляет разрешённые типы, а каждый из них действительно пишет extends или implements.

Final закрывает дальнейшее наследование, sealed передаёт контроль следующему уровню, non-sealed открывает конкретную ветвь. Record уже final. Такой набор вариантов полезен для доменных результатов и исчерпывающего switch; для независимых плагинов я выберу открытый контракт.

  • Прямые потомки должны быть в том же named module, либо в том же package для unnamed module; это единая область сопровождения.
  • Без permits вывод идёт по одной compilation unit и canonical names, а не по всему package или classpath.
  • Case открытой ветви покрывает неизвестных потомков этой ветви. Sealed ограничивает наследование, но не гарантирует abstract или immutable.

Как работает instanceof pattern и где доступна его переменная?

Value instanceof Paid p одновременно проверяет тип и даёт ссылку Paid на тот же объект. Мне не нужно повторять cast. При null и неподходящем типе получится false; новая переменная доступна на путях, где matching точно успешен.

Поэтому p можно использовать справа от &&, в успешной ветке if или после отрицательной проверки с ранним return. Справа от || он обычно недоступен: туда можно попасть после false, когда никакого p ещё нет.

  • Flow scoping учитывает завершение путей через return и throw; одних фигурных скобок для объяснения области недостаточно.
  • Pattern-переменная не неявно final и не означает копирование или неизменяемость target.
  • Parameterized pattern допустим при checked cast; erasure не позволяет распознать Box<String> из произвольного Object.

Что проверяет компилятор в pattern switch: guards, dominance и exhaustiveness?

Switch выбирает первый подходящий case. Pattern проверяет тип или структуру и связывает переменные, а when добавляет условие по данным. Я ставлю узкие случаи перед общей веткой: иначе общий Paid поглотит специализированный Paid с условием.

Dominance запрещает ветку, которую всегда закроет предыдущая, например String после CharSequence. Exhaustiveness требует охватить все варианты статического типа. У sealed-модели я могу перечислить их без default и получить ошибку при пропуске нового типа. Обычные guards не доказывают полное покрытие.

  • Javac не решает произвольные условия guard: positive перед case 1 может скомпилироваться и первым перехватить 1. When true — особый безусловный случай.
  • У generic sealed selector учитывается применимость конкретных type arguments: реализация Result<String> не нужна для Result<Integer>.
  • Default скрывает необходимость обновить обработчик при пересборке; эта политика подходит только при продуманном поведении для остальных вариантов.

Как record patterns обрабатывают null и почему полный switch может бросить MatchException?

Record pattern проверяет тип и разбирает компоненты через accessors. Null вместо самого record не совпадает. Но Box(var text) может получить null в компонент text, а вложенный Envelope(Box(var text)) не совпадёт с Envelope, у которого box равен null.

Null selector без case null приводит к NPE; default его не закрывает. Для существующего Envelope с неподходящей вложенной структурой статически полный switch может бросить MatchException. Я определяю constructor invariants и fallback для допустимых данных, вместо того чтобы считать exhaustiveness доказательством null safety.

  • Если accessor record бросает исключение во время matching, оно становится cause у MatchException; исключение обычного guard распространяется само.
  • После отдельного обновления sealed API старый исчерпывающий switch может встретить новый вариант и бросить MatchException. Полная пересборка обнаружила бы пропущенный case.
  • Деконструкция следует компонентам canonical-формы, не дополнительным конструкторам; custom accessor может добавить копирование или побочный эффект.
