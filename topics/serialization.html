Serialization Formats

Платёж существует в памяти одного процесса, а другому приходят только байты. Чтобы восстановить смысл, получатель должен знать, где заканчивается сообщение, как найти поля и что означают их значения. Формат решает часть этой задачи; остальное задаёт контракт. При обновлении сервисов одновременно живут несколько контрактов, поэтому правильный вопрос — какие старые данные прочитает новый код и какие новые данные переживёт старый.

Между сервисами передаются байты и договорённости

Сервис платежей записал событие об оплате на 150 центов. Сервис отчётов обновили: теперь его разработчик считает, что поле amount хранит доллары. JSON разбирается, число положительное, валидация проходит. Выручка выросла в сто раз. Ошибка лежит в значении поля, хотя на графике ошибок десериализации всё спокойно.

Сериализация переводит данные в последовательность байтов, десериализация восстанавливает представление у получателя. Ссылка на Java-объект, его методы и identity через сеть сами не переезжают. Обычно мы передаём DTO с выбранными полями: идентификатором платежа, суммой, валютой и временем события. Ссылки между сущностями заменяем явными идентификаторами, иначе случайный граф ORM-объектов становится сетевым контрактом.

У контракта несколько слоёв. Транспорт отделяет одно сообщение от другого и сообщает формат. Кодировка превращает текст в байты. Грамматика формата распознаёт структуру. Схема связывает поля с типами и обязательностью. Семантика объясняет единицы измерения, допустимые состояния и смысл отсутствия. Успешный нижний слой ничего не доказывает о следующем: корректный UTF-8 ещё не JSON, а корректный JSON ещё не платёж.

Для сквозного примера договоримся: amountMinor = 150, currency = "USD", feeMinor = 7. Сумма и комиссия выражены в минимальных единицах указанной валюты; правила округления задаёт домен. Название поля помогает, но не заменяет описание: у валют бывают разные масштабы, а платёж, возврат и бухгалтерская корректировка имеют разные ограничения на знак.

JSON, XML, Protobuf и Avro — разные способы передать этот контракт. Первые два несут текстовые имена, Protobuf — номера полей, бинарный Avro опирается на порядок полей в схеме записи. От выбора зависит, что получатель сможет пропустить без знания поля и какие метаданные придётся сохранить вместе с данными.

Событие живёт дольше релиза: оно остаётся в журнале, DLQ, архиве или резервной копии. Даже когда все процессы обновились, старый writer никуда не исчез — его роль играют сохранённые байты. Срок поддержки схемы определяй по сроку возможного replay, а не по времени завершения деплоя.

Читаемый текст не отменяет схему и точность типов

JSON удобен на границе с браузером и внешним API: объект содержит пары имя–значение, массив сохраняет порядок элементов, примитивы читаются без специального инструмента. По RFC 8259 JSON знает строку, число, boolean, null, объект и массив. Отдельных типов для даты, UUID, decimal и Java long у него нет. Их смысл и представление приходится согласовать: например, момент в UTC строкой ISO 8601, идентификатор строкой, сумму целым числом минимальных единиц.

{
  "paymentId": "p-42",
  "amountMinor": 150,
  "currency": "USD",
  "feeMinor": 7
}

Число в JSON — последовательность символов с допустимой грамматикой. Конкретный парсер и целевой тип решают, станет оно BigDecimal, long или double. Java long может точно хранить целое, которое JavaScript Number уже округлит. Поэтому произвольный 64-битный ID безопаснее передавать строкой, если среди клиентов есть такие ограничения. Перевод в строку должен быть частью схемы: внезапная смена JSON number на string тоже ломает строгого потребителя.

Это фрагмент SerializationDemo.java, Jackson 2.17.2, JDK 21. Оба чтения используют один текст; различается только заказанный Java-тип. Зависимости и команда запуска приведены в конце урока.

var mapper = new ObjectMapper();
String token = "9007199254740993";
System.out.println("JSON as decimal = "
        + mapper.readValue(token, BigDecimal.class).toPlainString());
// Потеря появляется при выборе Double, а не при записи текста JSON.
System.out.println("JSON via double = "
        + BigDecimal.valueOf(mapper.readValue(token, Double.class)).toPlainString());
JSON as decimal = 9007199254740993
JSON via double = 9007199254740992

BigDecimal, созданный после округления, уже не вернёт потерянную единицу. Для денег точность нужна на всём пути: отправитель, JSON-парсер, DTO, преобразования и хранилище. Основа двоичной точности разобрана в Numbers & Text; здесь важно, что корректный документ не гарантирует точного round trip.

Отсутствие поля, null и ноль — разные команды

В частичном обновлении платежа отсутствие feeMinor может означать «оставь как было», явный null — «сбрось», а 0 — «комиссия рассчитана и равна нулю». Если все три случая сразу связать с примитивным Java long, часть состояний исчезнет. Даже nullable-поле различает лишь null и значение: для PATCH нужна отдельная информация о присутствии, дерево JSON или специальная модель поля обновления.

Неизвестное поле тоже проверяет контракт потребителя. Один mapper отвергнет feeMinor, другой проигнорирует, третий сохранит в дополнительной map. Это политика библиотеки и настройки, а не обещание JSON. Дублирующиеся имена лучше отклонять на входе: RFC рекомендует уникальность имён, а разные реализации могут выбрать последнее значение, сохранить все или выдать ошибку. Подписывать один разбор, а исполнять другой — опасная неоднозначность.

XML описывает документ и имена с пространствами

XML полезен, когда партнёрский контракт уже строится на XSD, пространствах имён и документной структуре. У него есть элементы, атрибуты, упорядоченное содержимое и смешанный текст. XSD может задать тип decimal, допустимое число элементов и структуру, однако сам вызов XML-парсера ещё не означает проверку по XSD. Хорошо сформированный документ и валидный по схеме документ — разные уровни.

В namespace-aware разборе имя элемента — пара {namespace URI, local name}. Префикс служит локальным сокращением URI. Поэтому эти документы называют один и тот же элемент, хотя строковые имена узлов различаются:

<p:payment xmlns:p="urn:pay:v1" amountMinor="150"/>
<x:payment xmlns:x="urn:pay:v1" amountMinor="150"/>

JAXP-пример использует DOM для двух крошечных документов. Для большого потока записей разумнее SAX или StAX: DOM строит дерево целиком, поэтому размер heap зависит от всего документа, а не только от текущей записи. Обработчик должен сравнивать namespace URI и local name, иначе смена префикса у партнёра станет ложным изменением контракта.

var factory = DocumentBuilderFactory.newInstance();
factory.setNamespaceAware(true);
factory.setFeature(XMLConstants.FEATURE_SECURE_PROCESSING, true);
// Для этого контракта DTD не нужны: отклоняем сам DOCTYPE.
factory.setFeature("http://apache.org/xml/features/disallow-doctype-decl", true);
factory.setAttribute(XMLConstants.ACCESS_EXTERNAL_DTD, "");
factory.setAttribute(XMLConstants.ACCESS_EXTERNAL_SCHEMA, "");
var builder = factory.newDocumentBuilder();
String a = "<p:payment xmlns:p='urn:pay:v1' amountMinor='150'/>";
String b = "<x:payment xmlns:x='urn:pay:v1' amountMinor='150'/>";
var left = builder.parse(new InputSource(new StringReader(a))).getDocumentElement();
var right = builder.parse(new InputSource(new StringReader(b))).getDocumentElement();
boolean sameName = left.getNamespaceURI().equals(right.getNamespaceURI())
        && left.getLocalName().equals(right.getLocalName());
System.out.println("XML expanded names equal = " + sameName);
String withDtd = "<!DOCTYPE payment [<!ENTITY amount '150'>]><payment>&amount;</payment>";
try {
    builder.parse(new InputSource(new StringReader(withDtd)));
    throw new AssertionError("DOCTYPE was accepted");
} catch (SAXParseException expected) {
    System.out.println("XML DOCTYPE = rejected");
}
XML expanded names equal = true
XML DOCTYPE = rejected

В полном файле обработчик ошибок убирает стандартную печать диагностики парсера и пробрасывает исключение. Эти настройки проверены на встроенном JAXP-провайдере JDK 21; неподдерживаемую настройку нельзя молча проглотить. Запрет внешних DTD закрывает загрузку внешних сущностей, запрет DOCTYPE дополнительно отсекает и внутренние объявления. Для XSD-валидации и XSLT отдельно настраивают используемые SchemaFactory и TransformerFactory: настройка DOM-фабрики не распространяется на все XML API процесса.

JSON или XML самодокументируемы, поэтому отдельная схема не нужна.

Имена позволяют увидеть структуру, но не сообщают, что 150 — центы, timestamp — миллисекунды, а null запрещён. OpenAPI/JSON Schema и XSD делают часть ограничений проверяемой; доменная семантика всё равно требует документации и тестов совместимости.

Protobuf узнаёт поле по номеру, а длину — по wire type

В бинарном Protobuf строка amount_minor не повторяется в каждом сообщении. Схема назначает полю постоянный номер, а generated-код или descriptor связывает номер с именем и типом. Для нашего платежа схема proto3 выглядит так; в первой версии поля 3 ещё нет:

syntax = "proto3";
message Payment {
  int64 amount_minor = 1;
  string currency = 2;
  int64 fee_minor = 3;  // добавлено в v2, новый номер
}

Тег вычисляется как (fieldNumber << 3) | wireType и тоже кодируется varint. В младших трёх битах лежит способ прочитать или пропустить значение: varint, фиксированные 32/64 бита, length-delimited и исторические groups. Wire type — не полноценный тип поля: одинаковый length-delimited подходит строке, bytes, вложенному сообщению и packed-числам. Знать границы ещё не значит знать смысл.

Отсюда появляется удобная эволюция: старый reader способен пройти незнакомое поле, не зная его бизнес-смысла. Порядок разных полей в сообщении не обязан совпадать с порядком объявления. Но номер — постоянная identity поля: после удаления его резервируют, чтобы будущие байты не были прочитаны старым кодом под прежним именем. Практика — резервировать и номер, и имя: имя важно для текстовых представлений и инструментов.

Одинаковый wire type может тихо поменять значение

int64 и sint64 используют varint, но второй сначала применяет ZigZag: отрицательные и положительные числа превращаются в небольшие неотрицательные коды. Поэтому значение 150 типа int64 записывается как varint 150, а тот же varint reader типа sint64 интерпретирует как 75. Теги и длины правильные; исключения не будет.

В демо protoSchema строит настоящий descriptor: поле 1 получает переданный тип, поле 2 — string, поле 3 — int64, если включён параметр fee. Все поля singular, syntax — proto3. DynamicMessage позволяет выполнить опыт без protoc и сгенерированных Java-файлов.

var v2 = protoSchema(true, FieldDescriptorProto.Type.TYPE_INT64);
var v1 = protoSchema(false, FieldDescriptorProto.Type.TYPE_INT64);
var changed = protoSchema(false, FieldDescriptorProto.Type.TYPE_SINT64);
byte[] bytes = DynamicMessage.newBuilder(v2)
        .setField(v2.findFieldByNumber(1), 150L)
        .setField(v2.findFieldByNumber(2), "USD")
        .setField(v2.findFieldByNumber(3), 7L).build().toByteArray();
var old = DynamicMessage.parseFrom(v1, bytes);
System.out.println("protobuf bytes = " + HexFormat.ofDelimiter(" ").formatHex(bytes));
System.out.println("protobuf int64 amount = " + old.getField(v1.findFieldByNumber(1)));
// Тот же номер и wire type, но другая интерпретация полезной нагрузки.
System.out.println("protobuf sint64 amount = " + DynamicMessage.parseFrom(changed, bytes)
        .getField(changed.findFieldByNumber(1)));
var throughOld = DynamicMessage.parseFrom(v2, old.toByteArray());
System.out.println("protobuf fee after binary relay = " + throughOld.getField(v2.findFieldByNumber(3)));
// Копируем только известные поля: как при переходе через старый DTO.
var rebuilt = DynamicMessage.newBuilder(v1);
old.getAllFields().forEach(rebuilt::setField);
var throughDto = DynamicMessage.parseFrom(v2, rebuilt.build().toByteArray());
System.out.println("protobuf fee after known-field copy = " + throughDto.getField(v2.findFieldByNumber(3)));
protobuf bytes = 08 96 01 12 03 55 53 44 18 07
protobuf int64 amount = 150
protobuf sint64 amount = 75
protobuf fee after binary relay = 7
protobuf fee after known-field copy = 0

Последний ноль — не переданная комиссия, а значение по умолчанию отсутствующего scalar-поля с implicit presence. Старый binary relay сохранил новое поле, а пересборка только известных полей его уничтожила. Поэтому проверять совместимость нужно через весь маршрут: Protobuf → DTO → JSON → Protobuf уже не тот же канал, что бинарная пересылка сообщения.

Presence, отрицательные числа и почему сериализация не каноническая

Для обычного scalar-поля proto3 без optional getter возвращает default, а состояние «не было» неотличимо от «явно прислали 0». optional int64 fee_minor = 3 добавляет явное присутствие; generated Java API даёт hasFeeMinor(). Это полезно для частичных обновлений. Nullable-значение при этом не возникает автоматически: присутствующий long всё равно число. У message-полей присутствие есть; для нескольких взаимоисключающих вариантов служит oneof.

У отрицательного int64 обычный varint занимает 10 байт. ZigZag у sint64 делает малые отрицательные значения компактными, но сменить int64 на sint64 на прежнем номере нельзя. Для миграции вводят новое поле, договариваются о приоритете и некоторое время поддерживают обе формы.

Одни логические данные могут иметь разный порядок полей и разные допустимые бинарные представления. Даже deterministic serialization конкретной библиотеки не обещает вечный канонический формат для всех языков и версий. Хеш сырых байтов годится для идентичности именно этих байтов; для бизнес-дедупликации нужен устойчивый event ID, а для подписи — заранее определённое представление.

Avro сначала читает по схеме записи, затем сопоставляет со схемой чтения

Бинарный Avro идёт дальше в экономии метаданных: у record в теле нет ни имён, ни номеров полей. Значения следуют в порядке writer schema — схемы, по которой их записали. Для платежа с двумя long сначала записана сумма 150, затем комиссия 7. Чтобы найти второе поле, reader должен знать, как прочитать первое. Угадать структуру по одним байтам нельзя.

Reader schema описывает результат, который хочет получить приложение. Библиотека читает байты по writer schema и выполняет schema resolution: сопоставляет поля record по именам, пропускает ненужные и подставляет default для полей reader, отсутствовавших у writer. Поэтому перестановка полей в reader разрешима, хотя физический порядок в данных не меняется. Подставить новую схему вместо старой writer schema — совершенно другая операция.

В следующем опыте amount и fee имеют один тип long. Если ошибочно объявить новый порядок порядком записи, декодер честно прочитает первое число как комиссию. Типовая проверка не поймает подмену: оба значения корректны для long. С двумя схемами Avro восстановит исходные имена, переставит поля в результат и добавит валюту.

Схемы опыта ниже имеют одинаковое имя record Payment. В реальном контракте также контролируй namespace и правила именованных типов. writer — настоящая схема записи; reordered нужна, чтобы воспроизвести ошибку; reader задаёт желаемую проекцию.

var writer = new Schema.Parser().parse("""
    {"type":"record","name":"Payment","fields":[
      {"name":"amountMinor","type":"long"},
      {"name":"feeMinor","type":"long"}]}
    """);
var reordered = new Schema.Parser().parse("""
    {"type":"record","name":"Payment","fields":[
      {"name":"feeMinor","type":"long"},
      {"name":"amountMinor","type":"long"}]}
    """);
var reader = new Schema.Parser().parse("""
    {"type":"record","name":"Payment","fields":[
      {"name":"feeMinor","type":"long"},
      {"name":"amountMinor","type":"long"},
      {"name":"currency","type":"string","default":"USD"}]}
    """);
var payment = new GenericData.Record(writer);
payment.put("amountMinor", 150L); payment.put("feeMinor", 7L);
var out = new ByteArrayOutputStream();
var encoder = EncoderFactory.get().binaryEncoder(out, null);
new GenericDatumWriter<GenericRecord>(writer).write(payment, encoder);
encoder.flush();
byte[] bytes = out.toByteArray();
// Ошибка: выдаём reader-порядок за тот, которым пользовался writer.
var wrong = new GenericDatumReader<GenericRecord>(reordered).read(null,
        DecoderFactory.get().binaryDecoder(bytes, null));
// Правильно: сообщаем библиотеке обе схемы с разными ролями.
var resolved = new GenericDatumReader<GenericRecord>(writer, reader).read(null,
        DecoderFactory.get().binaryDecoder(bytes, null));
System.out.println("avro bytes = " + HexFormat.ofDelimiter(" ").formatHex(bytes));
System.out.println("avro wrong writer schema = " + wrong);
System.out.println("avro writer + reader = " + resolved);
avro bytes = ac 02 0e
avro wrong writer schema = {"feeMinor": 150, "amountMinor": 7}
avro writer + reader = {"feeMinor": 7, "amountMinor": 150, "currency": "USD"}

Avro long применяет ZigZag и varint: 150 превращается в 300, записанное ac 02; 7 превращается в 14, записанное 0e. Три байта — только тело record с двумя числами. Сравнивать их с десятью байтами Protobuf из предыдущего шага как «выигрыш формата» нельзя: там присутствует ещё и валюта. В честном сравнении одинаковы данные, требования к присутствию, конверт и метаданные схемы.

Как получатель найдёт writer schema

В Avro Object Container File схема лежит в метаданных заголовка, а блоки содержат данные. У raw datum из демо заголовка нет: схему нужно передать отдельно. В сообщениях часто хранят ID схемы в конверте и получают её из registry с локальным кешем. Конкретная раскладка такого конверта принадлежит выбранному serializer, она не является универсальным свойством любого Avro. В спецификации также есть single-object encoding с fingerprint схемы; fingerprint помогает найти схему, но не содержит её полного описания.

Связка «байты + идентификатор writer schema + доступная неизменная схема» должна переживать архивирование и восстановление. Если registry удалён или ID переиспользован в другом окружении, синтаксически целые данные могут оказаться нечитаемыми или получить неверный смысл. Backup только Kafka-топика без его схем — неполный план восстановления.

Default, union и logical type не одно и то же

Default у поля Avro применяется при чтении, когда этого поля не было в writer schema. Он не разрешает writer пропускать поле в бинарной записи. Если writer schema содержит currency, writer должен закодировать её значение по этой схеме. Поэтому «добавим default, и размер сообщений не изменится» — неверная модель.

Для nullable-поля используют union, например ["null", "string"], и default null. В байтах есть индекс выбранной ветки union, затем её значение. Null в этом случае — настоящий вариант данных, а не отсутствие записи поля. Указанный порядок совместим со старыми версиями инструментов; при изменениях union проверяй сочетания reader/writer, а не только успешный парсинг схемы.

Logical type добавляет значение поверх физического типа: например, decimal поверх bytes/fixed, timestamp-millis поверх long. Нельзя считать смену единицы времени безопасной только потому, что физический long не изменился. Для decimal важны precision и scale; настройки и поддержка преобразования в Java-тип должны совпадать у участников.

Совместимость проверяют в обе стороны и через посредников

Назови W1 старого writer, R1 старого reader, а W2 и R2 — новые версии. Backward compatibility означает, что новый reader читает старые данные: W1 → R2. Forward compatibility — старый reader читает новые: W2 → R1. Full compatibility объединяет оба направления. Это отношения между версиями, а не свойство слова «Avro» или «JSON».

Представь, что в событие добавляют currency. Для Avro новый reader с default USD прочитает старый record без валюты; старый reader пропустит новое поле writer. Формальная совместимость есть. Но default USD допустим лишь если исторически все такие платежи действительно были долларовыми. Если в архиве были EUR, автоматическая подстановка превратит совместимую схему в финансовую ошибку. Default — бизнес-решение о старых данных.

Таблица предполагает, что остальные части схемы не меняются. Для XML нет универсального «добавление элемента безопасно»: строгая XSD старого читателя может запретить новый элемент, а контракт с extension point — разрешить. Переименование JSON/XML-поля тоже часто означает удаление старого и добавление нового; без периода двойного чтения старое имя потеряется. В Protobuf binary имя можно поменять, сохранив номер, но ProtoJSON и исходный API при этом требуют отдельной проверки.

Порядок релизов следует из направления совместимости

Если гарантировано только W1 → R2, сначала обнови всех readers, затем включай новый writer. Иначе во время rolling update старый reader получит неподдерживаемый payload. Если гарантировано только W2 → R1, новые writers могут появляться первыми, но новый reader ещё не способен безопасно перечитать историю. Для независимых деплоев и replay обычно требуется поддержать оба случая или организовать явный переходный протокол.

Типичная безопасная миграция единиц выглядит так: добавляем amountMinorV2 на новом имени/номере, учим readers читать новое поле с согласованным fallback на старое, затем включаем двойную запись. Сравниваем значения и бизнес-метрики, переключаем чтение, а удаление старой формы откладываем до завершения окна rollback и поддержки истории. Если обе формы присутствуют и противоречат друг другу, правило приоритета или отказа должно быть частью контракта, иначе два consumer посчитают разную сумму.

Проверка только последней пары схем недостаточна, когда consumer может читать данные трёхлетней давности. Транзитивная политика проверяет новую схему против всей заданной истории версий, а не только соседней. Что именно registry называет BACKWARD, FULL и их TRANSITIVE-вариантами, проверяй в документации выбранного продукта; библиотека сериализации сама не управляет релизами и retention.

Совместимость — это набор исполняемых сценариев

Храни небольшие старые payload-fixtures рядом с контрактом и проверяй чтение новым кодом. Для обратного направления запускай старого reader на новых данных. Добавляй случаи отсутствия, null, нуля, нового enum, неизвестного поля, максимального числа и противоречащих полей переходного периода. Утверждай не только «не упало», но и полученную сумму, валюту, присутствие и сохранение неизвестных данных после промежуточного сервиса.

Простой round trip новым writer и новым reader скрывает ошибки миграции: обе стороны одинаково понимают новую ошибочную схему. Нужна перекрёстная матрица версий. Демо Avro показывает почему: неправильная схема даёт правдоподобный объект без исключения, а проверка значений выявляет перестановку.

Выбор формата зависит от границы системы и срока жизни данных

Для внешнего API важны удобство клиентов, наблюдаемость и договорённости об ошибках; для внутренних RPC — компактность и удобный типизированный контракт; для архива — возможность прочитать данные без запуска прежнего приложения. Это разные ограничения. JSON часто удобен для публичного API, Protobuf — для типизированного межсервисного обмена, Avro — для потоков и хранения со схемами, XML — для существующих документных контрактов. Это отправные точки, а не запрет использовать формат в другой роли.

Измеряй полный путь: размер после сжатия, затраты CPU на encode/decode, аллокации, p95/p99 и нагрузку на GC. Повторяющиеся имена JSON хорошо сжимаются, маленькие события могут больше зависеть от конверта и сетевых заголовков. Бинарный формат не гарантирует победу в конкретном сервисе: часто основная стоимость — преобразования DTO, копирование буферов и бизнес-обработка. Сравнение по одному демонстрационному сообщению не заменяет измерения на распределении реальных данных.

При инциденте сначала выясни формат и schema ID из конверта, версии producer/consumer и стадию отказа: framing, синтаксис, schema resolution, mapping или доменная валидация. Сохраняй безопасный образец payload или его диагностическое представление вместе с версией схемы. Сумма без валюты, «schema not found» и «unknown field» — разные причины, поэтому их не стоит сводить в одну метрику decode error. Полные платёжные данные в лог ради удобства отладки не нужны.

Ограничивай размер сообщения, вложенность, длины строк/массивов и время обработки до дорогих аллокаций. После распаковки данных лимит проверяется заново: маленький сжатый вход может развернуться в огромный документ. Не разрешай входному полю выбирать произвольный Java-класс для полиморфной десериализации; набор допустимых вариантов принадлежит контракту. XML требует отдельного контроля внешних ресурсов и сущностей, как в примере выше.

Ни один из четырёх форматов не обеспечивает доставку ровно один раз, порядок событий, транзакцию с базой или бизнес-идемпотентность. Это задачи протокола и обработки сообщений. Native Java serialization через ObjectInputStream — другой механизм с привязкой к Java-классам и своими рисками; он не заменяет межъязыковой контракт. Здесь мы рассматриваем форматы данных, а не перенос внутреннего графа Java-объектов.

Запустить все опыты без Maven и генерации кода

Полный файл: examples/cs/SerializationDemo.java. Проверено на JDK 21.0.11 JBR, protobuf-java 4.28.3, Avro 1.12.0, Jackson 2.17.2, SLF4J 2.0.13. Зависимости нужны только этому запуску. SLF4J nop убирает диагностическое сообщение о ненайденном logging provider; сеть при выполнении опытов не используется.

# Из корня репозитория; для скачивания нужен curl и доступ к Maven Central.
SERIALIZATION_LIBS=$(mktemp -d /tmp/java-kb-serialization-libs.XXXXXX)
SERIALIZATION_MAVEN=https://repo.maven.apache.org/maven2
for artifact in \
  com/google/protobuf/protobuf-java/4.28.3/protobuf-java-4.28.3.jar \
  org/apache/avro/avro/1.12.0/avro-1.12.0.jar \
  com/fasterxml/jackson/core/jackson-core/2.17.2/jackson-core-2.17.2.jar \
  com/fasterxml/jackson/core/jackson-databind/2.17.2/jackson-databind-2.17.2.jar \
  com/fasterxml/jackson/core/jackson-annotations/2.17.2/jackson-annotations-2.17.2.jar \
  org/slf4j/slf4j-api/2.0.13/slf4j-api-2.0.13.jar \
  org/slf4j/slf4j-nop/2.0.13/slf4j-nop-2.0.13.jar
do
  curl --fail --location --silent --show-error \
    "$SERIALIZATION_MAVEN/$artifact" -o "$SERIALIZATION_LIBS/${artifact##*/}"
done
java -version  # нужен JDK 21
java --class-path "$SERIALIZATION_LIBS/*" examples/cs/SerializationDemo.java

Фрагменты вывода выше — части одного реального запуска, без замены чисел. Демо использует библиотеки форматов: Protobuf работает через DynamicMessage и descriptors, Avro — через GenericDatumWriter/Reader. Самодельного кодека, который лишь повторяет объяснение, здесь нет.

  • Формат восстанавливает структуру; единицы измерения, обязательность и смысл отсутствия задаёт контракт.
  • JSON-number не обязан быть double. Потеря точности может появиться при выборе Java-типа и пережить все дальнейшие преобразования.
  • Protobuf узнаёт поле по номеру и пропускает его по wire type. Номер нельзя переиспользовать; одинаковый wire type не гарантирует одинакового значения.
  • Avro читает порядок байтов по writer schema и сопоставляет поля с reader schema по именам. Подмена writer schema способна тихо поменять сумму и комиссию местами.
  • Совместимость проверяют W1 → R2 и W2 → R1, с историческими payload и всеми посредниками. Успешный парсинг — лишь начало проверки.

На собеседовании

Чем JSON, XML, Protobuf и Avro отличаются и как выбрать формат?

Я начинаю с участников и срока жизни данных. JSON и XML несут текстовые имена, их удобно исследовать обычными инструментами. У XML богаче документная модель, namespaces и XSD; это важно в готовых партнёрских контрактах. Protobuf передаёт номера полей и wire types, а полный тип знает из схемы. Avro binary убирает даже номера: для чтения нужна схема, по которой записали данные.

Для внешнего API я часто рассматриваю JSON, для типизированных RPC — Protobuf, для событий и архивов со схемами — Avro. Но решение принимаю по совместимости, инструментам клиентов и измерениям полного пути. Формат не определяет ни единицы денег, ни идемпотентность платежа.

  • Размер нужно сравнивать на одинаковом наборе данных, с одинаковыми требованиями к presence и с учётом сжатия и метаданных. Три байта Avro record без валюты нельзя сравнивать с полным Protobuf payment.
  • Цена схемы у Avro вынесена в контейнер или инфраструктуру её доставки. В план disaster recovery входят и payload, и неизменные writer schemas.
  • Граница ProtoJSON отличается от Protobuf binary: текстовые имена и неизвестные поля дают другой набор рисков совместимости. Транскодирующий gateway входит в проверяемый маршрут.

Что такое backward и forward compatibility? Как обновить событие без остановки?

Backward означает, что новый reader умеет читать старые данные, forward — старый reader умеет читать новые. Я явно рисую направления writer → reader, чтобы не перепутать. Для нового поля проверяю обе стороны: как новый код обрабатывает отсутствие и как старый — незнакомое поле. Затем выбираю порядок релизов, совместимый с этими гарантиями.

Если меняется смысл суммы, не переиспользую прежнее поле. Ввожу новое, сначала выкатываю читающий обе формы код, потом writer, проверяю согласованность и только после окна rollback убираю старый путь. Исторические сообщения остаются частью контракта дольше деплоя.

  • Совместимость с предыдущей схемой не равна совместимости со всем архивом. Для replay нужна проверка исторических версий, часто транзитивная политика registry.
  • Default у нового Avro-поля может сделать чтение технически успешным и одновременно испортить смысл: USD допустим только для действительно долларовой истории.
  • Матрица тестов утверждает значения и presence, а не только отсутствие исключения. Нужно включить старые DTO-посредники, потерю unknown fields и конфликт двух форм миграции.
Сначала обновили writer, затем readers. Registry пропустил BACKWARD-проверку. Почему старый consumer упал?

BACKWARD проверяет чтение старых данных новым reader, а во время такого деплоя возникло обратное направление: новые данные пришли старому reader. Например, Avro int заменили на long: новый reader расширит исторический int, но старый reader не обязан сужать long. Нужно либо сначала обновить всех readers, либо подготовить схему, совместимую в обе стороны. Отдельно проверь возможность отката readers после включения нового writer.

Почему Protobuf переживает новые поля, но запрещает переиспользовать номера?

В каждом поле передаётся тег: номер и wire type. По номеру reader находит поле своей схемы, а по wire type понимает границу значения, даже если номер неизвестен. Поэтому новое поле можно прочитать как unknown и продолжить разбор. Если отдать старый номер другому полю, старый reader будет интерпретировать новые данные как прежнее значение. Удалённые номера я резервирую.

Проверяю и изменение типов. Например, int64 и sint64 используют один wire type, но ZigZag меняет смысл числа: varint 150 становится 75 у sint64. Отсутствие ошибки парсинга ещё не означает совместимость.

  • Proto3 Java сохраняет unknown fields при бинарном parse/serialize, но копирование только известных полей или переход через JSON может их потерять. Посредник способен нарушить совместимость без изменения своей схемы.
  • Для partial update важна presence: implicit scalar не отличает отсутствующее поле от default. Explicit optional позволяет отдельно проверить присутствие нулевой комиссии.
  • Стабильность номеров не означает каноничность байтов. Для бизнес-дедупликации нужен идентификатор события, а не произвольный hash сериализованного message.
В v2 появилась комиссия. Старый сервис прочитал платёж и отправил его дальше. Сохранится комиссия?

При бинарной пересериализации исходного message в нашем опыте сохраняется 7: поле осталось в UnknownFieldSet. Если сервис создал новый message по getAllFields(), там только известные поля; новая комиссия исчезает, а getter v2 возвращает 0 для implicit scalar. Поэтому ответ зависит от операции посредника. Сохранение unknown проверяй на реальном коде пересылки, а не только на схемах endpoints.

Зачем Avro две схемы? Что произойдёт при перестановке и добавлении полей?

Writer schema описывает физический порядок значений в старых байтах, reader schema — объект, который нужен моему приложению. Avro сначала использует правильную writer schema, затем сопоставляет поля record по именам. Поэтому reader может переставить поля, убрать ненужные и добавить поле с default. Без default новое поле, которого у writer не было, даст ошибку resolution.

Самую новую схему нельзя просто объявить схемой записи старого сообщения. В демо это молча меняет сумму и комиссию местами, потому что оба поля long. Я сохраняю writer schema или устойчивую ссылку на неё вместе с данными и отдельно задаю схему чтения.

  • Default нужен для отсутствия поля у writer, а не для пропуска поля текущим writer. Nullable union — отдельная конструкция с индексом ветки в байтах.
  • Проекция reader не сохраняет автоматически все отброшенные поля для будущей пересылки. Если промежуточный сервис читает старую проекцию и пишет новый record из неё, нужна отдельная стратегия сохранения данных.
  • Logical type добавляет семантику поверх физического типа. Long с миллисекундами нельзя без миграции читать как микросекунды, даже если базовый binary decoder успешно вернул число.
  • Martin Kleppmann, Designing Data-Intensive Applications, 1-е изд., глава 4 «Encoding and Evolution» — основа урока: направления совместимости, схемы writer/reader и данные, переживающие релиз.
  • RFC 8259, JSON, §§4, 6, 8 — уникальность имён, числа, Unicode; JDK 21 JAXP Security Guide — внешние ресурсы, secure processing и конфигурация XML API.
  • Protobuf Encoding — теги, varint и ZigZag; proto3 Language Guide, Updating a Message Type и Unknown Fields — эволюция и сохранение неизвестных полей.
  • Avro 1.12.0 Specification, Binary Encoding, Object Container Files, Schema Resolution и Logical Types — порядок байтов, две схемы, defaults и преобразования типов.
  • Namespaces in XML 1.0, §2 — expanded names; Protobuf Serialization Is Not Canonical — границы детерминированности бинарного представления.
