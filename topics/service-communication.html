Service Communication

Сервисы общаются синхронно — запрос и ожидание ответа (REST, gRPC) — или асинхронно — сообщение в брокер, обработка позже. Синхронный вызов связывает сервисы во времени: если вызываемый лежит, вызывающий тоже не может выполнить работу — в демо за две секунды простоя склада сервис заказов отклонил 20 заказов из 40. Сообщение в очередь развязывает их: все 40 заказов приняты, а резервирование догнало через 2 секунды после восстановления. Синхронно вызывают то, без чего нельзя ответить прямо сейчас; всё, что может подождать, отправляют сообщением. Когда ответ собирается из нескольких сервисов, вызовы делают параллельно: три вызова по 50 мс — 60+ мс вместо 170+.

Склад перезапускался две минуты, и заказы не принимались

При создании заказа сервис заказов синхронно вызывает склад, чтобы зарезервировать товар. Склад выкатывали две минуты, и всё это время покупатели видели ошибку оформления — хотя товар был, а резерв можно было сделать через минуту. Сервис заказов был доступен ровно настолько, насколько доступен склад, а его собственная доступность ничего не значила.

Тема разбирает синхронное и асинхронное взаимодействие, выбор протокола между сервисами, тайм-ауты и сборку ответа из нескольких сервисов. Брокеры подробно — в Messaging и Kafka Delivery, публикация вместе с транзакцией — в Transactional Outbox, стили API — в API Styles. Демо CommunicationDemo.java: склад — HTTP-сервер на JDK, очередь — список в Redis 8; 40 заказов по 10 в секунду, склад недоступен с 1-й по 3-ю секунду.

Синхронный вызов связывает доступность, очередь — развязывает

// Синхронно: заказ создан, только если склад ответил.
try {
    var r = http.send(HttpRequest.newBuilder(URI.create("http://localhost:8201/reserve")).timeout(Duration.ofMillis(300))
            .POST(HttpRequest.BodyPublishers.noBody()).build(), HttpResponse.BodyHandlers.discarding());
    if (r.statusCode() == 204) ok++; else failed++;
} catch (Exception e) { failed++; }                      // заказ не создан: склад не ответил

// Асинхронно: заказ принят сразу, сообщение ждёт в очереди; потребитель склада повторяет, пока склад не ответит.
redis.lpush("inventory-queue", String.valueOf(System.currentTimeMillis()));
== 40 orders at 10/s; inventory is down from 1.0 s to 3.0 s
   sync HTTP:    orders accepted 20, rejected 20, reserved 20
   async queue:  orders accepted 40, rejected  0, reserved 40, max delay to reserve 2.0 s

Синхронный вызов создаёт временную связь (temporal coupling): оба сервиса должны быть живы одновременно. Доступность цепочки синхронных вызовов — произведение доступностей, как в Availability & SLO. Сообщение разрывает эту связь: отправителю нужен только брокер, получатель может быть недоступен, медленен или перегружен — очередь выравнивает нагрузку. Цена — итоговая согласованность: заказ принят, но резерв ещё не сделан, и бизнес-процесс должен уметь с этим жить. Если товара не оказалось, заказ отменяется компенсацией, как в саге из Distributed Transactions.

В демо очередь — простой список Redis, и сообщение, взятое потребителем и не обработанное до его падения, пропало бы. Настоящие брокеры держат сообщение до подтверждения, а запись заказа и сообщения делают атомарной через outbox: иначе заказ сохранён, а сообщение — нет.

ПротоколREST, gRPCKafka, RabbitMQ, SQS

Между сервисами внутри системы gRPC часто удобнее REST: строгий контракт в Protobuf, генерация клиентов, компактный формат, HTTP/2 с мультиплексированием и встроенные дедлайны. REST проще для внешних API и отладки. Для сообщений важна семантика: команда («зарезервируй») адресована одному получателю, событие («заказ создан») — любому числу подписчиков, как в Event-driven, CQRS, Event Sourcing. Запрос-ответ поверх брокера (сообщение с адресом ответа и корреляционным id) возможен, но сохраняет временную связь и добавляет задержку — им пользуются, когда ответ нужен позже, а не сразу.

Каждый синхронный вызов обязан иметь тайм-аут. Без него один медленный сервис занимает потоки вызывающего, и отказ распространяется по цепочке, как разобрано в Resilience Patterns.

Тайм-ауты в цепочке: передавать дедлайн, а не заводить свой

// C: если до дедлайна меньше, чем нужно на работу, — не начинать.
String d = ex.getRequestHeaders().getFirst("X-Deadline");
if (d != null && Long.parseLong(d) - System.currentTimeMillis() < 500) {
    ex.sendResponseHeaders(504, -1); ex.close(); return;
}
// B: без передачи — свой тайм-аут 1 с; с передачей — дедлайн A уходит к C в заголовке.
var req = HttpRequest.newBuilder(URI.create("http://localhost:8204/")).timeout(Duration.ofSeconds(1));
if (propagate && d != null) req.header("X-Deadline", d);
== chain A -> B -> C: A waits 300 ms, C needs 500 ms; 10 requests
   own timeout in B:     A: timeouts 10, fast 504  0; C: useless work done 10, refused  0
   deadline propagated:  A: timeouts  0, fast 504 10; C: useless work done  0, refused 10

A ждёт ответа 300 мс, B вызывает C, которому на работу нужно 500 мс. Если у B свой тайм-аут в секунду, все 10 запросов A заканчиваются тайм-аутом, а C всё равно доделывает все 10 работ — для ответа, который уже никто не ждёт. Под нагрузкой эта бесполезная работа отнимает ресурсы у живых запросов, как разобрано в Overload. Если дедлайн A передаётся по цепочке, C видит, что не успеет, и отказывается сразу: A получает быстрый 504 вместо тайм-аута, а C не тратит ни миллисекунды.

В gRPC дедлайн — часть протокола: клиент задаёт его один раз, он передаётся в заголовке grpc-timeout на каждый следующий вызов, а сервер получает отмену, когда время вышло. В HTTP это делают вручную, заголовком с абсолютным временем или остатком. Абсолютное время требует синхронизированных часов, остаток — вычитания времени, потраченного на каждом звене. Тайм-ауты нижних звеньев должны быть меньше верхних: иначе верхний сдаётся раньше, а нижние продолжают работать.

Сборка ответа из нескольких сервисов: параллельно и с частичным ответом

var fs = List.of("/profile", "/orders", "/bonuses").stream()
        .map(p -> CompletableFuture.runAsync(() -> call(p)))
        .toList();
CompletableFuture.allOf(fs.toArray(CompletableFuture[]::new)).join();
== order page needs profile, orders and bonuses, 50 ms each
   sequential: 170+ ms
   parallel:   60+ ms

Страница кабинета собирает профиль, заказы и бонусы — три сервиса по 50 мс. Последовательно — сумма, 170+ мс с накладными расходами; параллельно — максимум, 60+ мс. Числа округлены вниз до десятков и меняются от запуска к запуску на десяток миллисекунд. Это API composition: сборку делает BFF или сервис-агрегатор, как в API Gateway. Второстепенные части — бонусы — запрашивают с коротким тайм-аутом и отдают страницу без них при отказе, а не ошибку целиком.

Если один и тот же набор данных нужен часто, агрегацию делают заранее: сервис кабинета подписывается на события профилей, заказов и бонусов и держит у себя готовое представление (CQRS). Тогда чтение — один запрос в свою базу без вызовов соседей, а данные отстают на секунды. Глубокие цепочки синхронных вызовов — A вызывает B, тот C, тот D — признак неудачных границ: каждое звено добавляет задержку и снижает доступность, как в Monolith & Microservices.

Сервис заказов развёрнут в трёх экземплярах, поэтому он высокодоступен.

Если создание заказа синхронно зависит от склада, доступность заказов не выше доступности склада: в демо при живом сервисе заказов 20 из 40 заказов отклонены за две секунды простоя склада. Развязка через очередь приняла все 40.

  • Синхронный вызов связывает доступность: 2 секунды простоя склада — 20 отклонённых заказов из 40.
  • Очередь развязывает: приняты все 40, резерв догнал за 2 с после восстановления; цена — итоговая согласованность.
  • Синхронно — то, без чего нельзя ответить сейчас; остальное — сообщением; запись и сообщение — через outbox.
  • Тайм-аут на каждом вызове; без передачи дедлайна C доделал 10 из 10 бесполезных работ, с передачей — 0 и быстрый 504.
  • Сборка из нескольких сервисов — параллельно (60+ мс вместо 170+) с частичным ответом; частые сборки — готовым представлением.

На собеседовании

Синхронное или асинхронное взаимодействие между сервисами — как выбрать?

Синхронно — когда результат нужен для ответа прямо сейчас: проверка прав, цена, баланс. Асинхронно — когда действие может произойти позже: резервирование, уведомления, аналитика. Синхронный вызов делает вызывающего недоступным вместе с получателем и передаёт ему всплески нагрузки; очередь развязывает доступность и сглаживает нагрузку ценой итоговой согласованности.

  • Temporal coupling: в демо 20 из 40 заказов отклонены синхронно и 0 через очередь.
  • Сообщение вместе с изменением в базе — через outbox; обработка идемпотентна.
  • Отказ обработки — компенсация, а не откат.
Что не так с этим созданием заказа? 
@Transactional
public Order create(OrderRequest r) {
    Order o = orders.save(new Order(r));
    inventoryClient.reserve(o.getId(), r.items());     // HTTP, без тайм-аута
    loyaltyClient.addPoints(o.getUserId(), o.total()); // HTTP
    mailClient.sendConfirmation(o);                    // HTTP
    return o;
}

Три синхронных вызова внутри транзакции: создание заказа недоступно, если недоступен любой из трёх сервисов, а без тайм-аута медленный сервис держит поток и соединение с базой. Если упадёт письмо, откатится заказ, хотя резерв и бонусы уже сделаны. Резерв можно оставить синхронным, если без него нельзя ответить, но с тайм-аутом и вне транзакции; бонусы и письмо — событием через outbox после коммита.

REST или gRPC между сервисами?

gRPC: строгий контракт в Protobuf и генерация клиентов, компактный бинарный формат, HTTP/2 с мультиплексированием, стриминг и дедлайны из коробки — удобен внутри системы. REST: проще отлаживать, понимают все инструменты и браузеры, удобен для внешних API. Выбор часто такой: REST снаружи, gRPC внутри.

  • gRPC через L4-балансировщик — одно долгое соединение на один экземпляр.
  • Совместимость контрактов: добавлять поля, не менять номера в Protobuf.

Как собрать ответ из данных нескольких сервисов?

API composition: агрегатор или BFF вызывает сервисы параллельно и собирает ответ; второстепенные части — с коротким тайм-аутом и частичным ответом. Если такой запрос частый, лучше заранее построенное представление, обновляемое событиями сервисов (CQRS): чтение без вызовов соседей.

  • Параллельно — время самого медленного, последовательно — сумма.
  • Глубокие цепочки синхронных вызовов — признак неудачных границ.
