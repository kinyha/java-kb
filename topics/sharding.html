Sharding

Шардирование распределяет строки одной логической таблицы по нескольким серверам баз данных, чтобы запись и объём масштабировались горизонтально. Ключ шардирования определяет, на каком сервере лежит строка: запросы с этим ключом идут на один шард, остальные приходится рассылать на все и собирать результат. Отображение ключа на шард выбирают так, чтобы добавление сервера переносило малую часть данных: hash mod N переносит почти всё, а consistent hashing и фиксированное число виртуальных шардов — долю нового сервера. Цена — транзакции, уникальность, соединения и отчёты через границы шардов, поэтому шардируют последним, после остальных способов.

Один сервер базы перестал справляться с записью платежей

Платёжная система выросла до десятков тысяч платежей в секунду. Самый мощный сервер, реплики для чтения, секционирование по месяцам и архивирование старых данных уже сделаны, но запись упирается в один primary: WAL, блокировки, диски одного сервера. Остаётся разложить данные по нескольким независимым базам. Первая попытка — shard = hash(merchant_id) mod 4 — работала, пока не понадобился пятый сервер: перенос занял неделю, потому что переезжали почти все данные. А один крупный маркетплейс перегрузил свой шард.

Тема разбирает выбор ключа, отображение ключей на шарды, перешардирование и то, что ломается между шардами. Секционирование внутри одной базы — в Partitioning, реплики — в Replication, распределённые транзакции — в Distributed Transactions, глобальные id — в Unique ID Generation. Демо ShardingDemo.java считает перенос ключей и распределение нагрузки на миллионе ключей: java ShardingDemo.java на JDK 21.

Шардируют последним: вертикальное масштабирование, реплики и секции дешевле

Один современный сервер PostgreSQL с NVMe выдерживает десятки тысяч транзакций в секунду и терабайты данных. Шардирование превращает одну базу в распределённую систему: каждый запрос должен знать, куда идти, транзакции через шарды теряют атомарность, уникальность и внешние ключи работают только внутри шарда, а миграции схемы выполняются на каждом. Поэтому его откладывают, пока остальные средства не исчерпаны, или берут готовые решения — Citus для PostgreSQL, Vitess для MySQL, — которые прячут часть сложности.

Ключ шардирования выбирают по запросам, и неравномерный ключ создаёт горячий шард

Хороший ключ — тот, по которому идут почти все запросы и транзакции: тогда каждый запрос обращается к одному шарду, а транзакция остаётся локальной. Для платёжной системы это магазин или счёт: платежи, возвраты и выписка одного магазина живут вместе. Запрос без ключа — «все платежи с картой X» — придётся отправить на все шарды и слить результаты (scatter-gather), и он медленнее самого медленного шарда.

== load per shard when one merchant makes 30% of payments (shard by merchant)
   shard 0: 17.4%
   shard 1: 47.5%
   shard 2: 17.5%
   shard 3: 17.6%

Вторая сторона ключа — равномерность. Если один маркетплейс делает 30 % платежей, его шард несёт почти половину нагрузки, а добавление шардов не помогает: все платежи магазина всегда на одном сервере. Для таких ключей используют составной ключ — магазин плюс месяц или магазин плюс хеш платежа, — жертвуя локальностью части запросов, или выносят крупного клиента на выделенный шард через таблицу-справочник.

hash mod N переносит почти всё при росте, виртуальные шарды — только нужную долю

== keys that move when growing from 4 to 5 shards
   hash mod N:                  79.9%
   consistent hashing (ring):   19.9%
   1024 virtual shards:         20.0%

При hash mod N номер шарда зависит от числа серверов, и переход с 4 на 5 меняет его у 80 % ключей: переносить приходится почти все данные. Consistent hashing размещает серверы и ключи на кольце хешей, и ключ принадлежит ближайшему серверу по часовой стрелке; новый сервер забирает только свои участки — 20 %. Подробно кольцо разобрано в Consistent Hashing. Практичнее для баз — фиксированное большое число виртуальных шардов: ключ раз и навсегда отображается в один из 1024 слотов, а слоты распределены по серверам таблицей. Новый сервер забирает пятую часть слотов, и переносятся только они. Так устроены Redis Cluster с 16 384 слотами, Vitess и Citus.

Сам перенос — отдельная операция: скопировать данные слота на новый сервер, догнать изменения через логическую репликацию или CDC, на короткое время заблокировать запись в слот, переключить таблицу маршрутизации. Таблица «слот → сервер» живёт в конфигурационном сервисе, и все приложения должны видеть её согласованно.

Отчёты по всем даннымScatter-gather на каждый отчётCDC в аналитическое хранилище

Перевод между счетами разных магазинов — классический пример: списание на одном шарде и зачисление на другом не могут быть одной транзакцией. Его делают сагой с компенсацией или через промежуточный счёт, как разобрано в Distributed Transactions. Справочники, которые нужны всем шардам, — валюты, тарифы, — реплицируют целиком на каждый шард, и соединения с ними остаются локальными.

Шардирование по hash(id) mod N — простое и достаточное решение.

Оно работает, пока число шардов не меняется: переход с 4 на 5 переносит 80 % данных. Ключ id случайной сущности ещё и разносит связанные данные по разным шардам, превращая обычные транзакции и запросы в распределённые. Нужны ключ по сущности, вокруг которой идут транзакции, и виртуальные шарды или consistent hashing.

  • Шардирование — последнее средство после вертикального роста, реплик, секций и архивирования; Citus и Vitess берут часть сложности на себя.
  • Ключ — сущность, вокруг которой идут запросы и транзакции; неравномерный ключ даёт горячий шард (47,5 % у шарда крупного магазина).
  • hash mod N переносит 80 % ключей при росте 4 → 5; кольцо и 1024 виртуальных шарда — 20 %.
  • Через шарды нет атомарных транзакций, глобальной уникальности, последовательностей и JOIN; саги, UUIDv7, копии справочников, CDC для отчётов.

На собеседовании

Как выбрать ключ шардирования?

По основным запросам и транзакциям: ключ должен быть в большинстве запросов, чтобы они шли на один шард, и объединять данные, которые меняются вместе, чтобы транзакции оставались локальными. И он должен распределять данные и нагрузку равномерно. Для платежей — магазин или счёт, а не id платежа.

  • Горячий ключ перегружает шард; помогают составной ключ или выделенный шард через справочник.
  • Запросы без ключа — scatter-gather на все шарды; их выносят в аналитическое хранилище.
  • Сменить ключ шардирования потом — почти переписать систему.

Как добавить шард и не перенести все данные?

Не использовать hash mod N: он меняет шард почти у всех ключей. Использовать consistent hashing или фиксированное большое число виртуальных шардов с таблицей «слот → сервер»: новый сервер забирает только свою долю слотов. Перенос слота — копирование, догонка изменений репликацией, короткая блокировка записи и переключение маршрутизации.

  • В демо: mod N — 80 % ключей, кольцо и 1024 слота — 20 %.
  • Таблица маршрутизации должна обновляться согласованно у всех клиентов.
  • Redis Cluster, Vitess и Citus используют виртуальные шарды.
Что не так с этой схемой шардирования? 
int shard = Math.abs(payment.getId().hashCode()) % shards.size();
DataSource ds = shards.get(shard);
// переводы между счетами: debit на шарде одного платежа, credit — другого, в двух транзакциях

Шард зависит от числа серверов — добавление шарда перенесёт почти все данные. Ключ — id платежа, поэтому платежи одного магазина разбросаны, и любые запросы по магазину идут на все шарды. Math.abs(Integer.MIN_VALUE) отрицателен, и индекс станет отрицательным. Перевод в двух независимых транзакциях может списать без зачисления. Нужны ключ по счёту или магазину, виртуальные шарды и сага или промежуточный счёт для межшардовых переводов.

Чем шардирование отличается от секционирования?

Секционирование делит таблицу на части внутри одного сервера базы: транзакции, ограничения и запросы работают как обычно, база сама выбирает секции. Шардирование распределяет данные по разным серверам: масштабирует запись и объём, но транзакции, уникальность и соединения между шардами становятся задачей приложения или промежуточного слоя.

  • Секционирование решает управление данными и размер индексов, шардирование — предел одного сервера.
  • Citus совмещает: распределённые таблицы по шардам на разных узлах с SQL поверх.
  • Martin Kleppmann, «Designing Data-Intensive Applications», глава 6 — основа урока: ключи, перебалансировка, вторичные индексы, маршрутизация.
  • Vitess: Concepts и Citus documentation — готовое шардирование для MySQL и PostgreSQL.
  • Karger et al., «Consistent Hashing and Random Trees» — исходная работа о согласованном хешировании.
