Slow Queries

Медленную базу чаще всего тормозит не один ужасный запрос, а тысячи быстрых: N+1 из ORM, вставки по одной строке, пагинация через OFFSET. В логе медленных запросов их не видно — каждый выполняется за доли миллисекунды. Видно их в pg_stat_statements, который агрегирует все запросы по тексту и показывает число вызовов, суммарное и среднее время. Искать нужно по суммарному времени, а не по самому медленному вызову. Лечат сокращением кругов по сети: соединение вместо цикла запросов, пакетная запись, keyset-пагинация.

База загружена на 80 %, а в логе медленных запросов пусто

Сервис платежей растёт, процессор базы загружен на 80 %, страницы кабинета отвечают по секунде. В лог попадают запросы дольше 500 мс — log_min_duration_statement = 500, — и он пуст: ни одного медленного запроса. Ночная выгрузка аудита идёт полчаса, хотя пишет всего несколько миллионов строк.

Тема о том, как найти, что на самом деле нагружает базу, и о трёх самых частых антипаттернах приложений. Разбор плана одного запроса — в Query Plans, индексы — в Indexes, N+1 со стороны JPA — в Relations & Fetching, OFFSET и keyset — в API Design. Демо SlowQueriesDemo.java работает с PostgreSQL 17 в Docker, запущенным с pg_stat_statements, и драйвером pgjdbc 42.7.

pg_stat_statements собирает все запросы по тексту и считает суммарное время

-- postgresql.conf: shared_preload_libraries = 'pg_stat_statements'
create extension pg_stat_statements;
select calls, total_exec_time, mean_exec_time, rows, query
from pg_stat_statements order by total_exec_time desc limit 10;
== pg_stat_statements, top by total time
    calls  total_ms  mean_ms    rows  query
    40000      34.9    0.001   40000  insert into audit values ($1, $2)
      200      11.4    0.057     200  select sum(amount) from payment where merchant_id = $1
        1       6.9    6.929     200  select m.id, sum(p.amount) from merchant m join payment p on
        1       3.9    3.926   16384  insert into audit values ($1, $2),($3, $4),($5, $6),($7, $8)
        1       0.5    0.475    2048  insert into audit values ($1, $2),($3, $4),($5, $6),($7, $8)
        1       0.3    0.251    1024  insert into audit values ($1, $2),($3, $4),($5, $6),($7, $8)

Расширение нормализует текст — константы заменяются на $1, — и все вызовы одного запроса складываются в одну строку. Верх списка по суммарному времени — вставка одной строки: каждая выполняется за микросекунду, но их сорок тысяч. Второй — запрос суммы по магазину, 200 вызовов по 0,06 мс. Ни один из них не попал бы в лог медленных запросов. Самый «медленный» единичный запрос, соединение за 6,9 мс, на деле самый полезный: он один заменяет двести.

Важно, что total_exec_time — время внутри базы. Время на сеть, разбор и ожидание в пуле соединений приложения сюда не входит, а именно оно у многократных мелких запросов главное. Поэтому смотрят ещё и на calls: тысячи вызовов одного запроса на одну операцию пользователя — почти всегда N+1. Для отдельных медленных запросов включают auto_explain, который пишет в лог план запроса дольше порога, а текущие зависшие запросы ищут в pg_stat_activity.

N+1 тратит время на круги по сети, а не на работу базы

// Магазины, затем платежи каждого отдельным запросом.
var shops = c.createStatement().executeQuery("select id from merchant order by id limit 200");
while (shops.next()) {
    ps.setInt(1, shops.getInt(1));
    ps.executeQuery();                       // select sum(amount) from payment where merchant_id = ?
}
== N+1: 1 + 200 queries, 56 ms
== one join query, 7 ms (same totals: true)

Двести запросов по магазинам заняли 56 мс, из которых в самой базе — 11 мс. Один запрос с соединением и группировкой дал те же суммы за 7 мс. Здесь база и приложение на одной машине; в реальной сети круг — от 0,3 до нескольких миллисекунд, и N+1 на 200 строк превращается в секунду. В JPA N+1 возникает незаметно: ленивая коллекция, к которой обращаются в цикле, или @ManyToOne без JOIN FETCH. Лечат запросом, который сразу достаёт всё нужное: JOIN, where id = any(?) по списку или @BatchSize/default_batch_fetch_size в Hibernate.

Пакетная запись сокращает круги, а reWriteBatchedInserts — ещё и операторы

var ps = c.prepareStatement("insert into audit values (?, ?)");
for (int i = 0; i < 20_000; i++) {
    ps.setLong(1, i); ps.setString(2, "payment captured");
    ps.addBatch();                            // вместо ps.executeUpdate()
}
ps.executeBatch();
// URL: jdbc:postgresql://...&reWriteBatchedInserts=true
== insert 20k rows, row by row:                       1936 ms
== insert 20k rows, addBatch:                         50 ms
== insert 20k rows, addBatch + reWriteBatchedInserts: 32 ms

Вставка по одной строке — двадцать тысяч кругов «отправить — дождаться ответа»: почти две секунды. addBatch отправляет операторы пачками без ожидания ответа на каждый — 50 мс, в 39 раз быстрее. Но для базы это всё ещё двадцать тысяч отдельных INSERT: в pg_stat_statements их 40 000 вызовов вместе с построчным вариантом. С reWriteBatchedInserts=true драйвер склеивает пачку в многострочные INSERT по степеням двойки — values ($1, $2),($3, $4),... — и база выполняет единицы операторов: 16 384 строк одним, затем 2048, 1024 и так далее. Для самых больших загрузок есть ещё COPY.

В Hibernate пакетная вставка включается hibernate.jdbc.batch_size, но ломается, если id сущности генерируется IDENTITY: чтобы узнать id, Hibernate обязан выполнить каждый INSERT сразу. С последовательностью и allocationSize пакеты работают. Ночная выгрузка аудита из начала темы — именно этот случай.

Порядок работы с медленной базой: найти верх pg_stat_statements по суммарному времени и по числу вызовов, для каждого понять, лишний ли он целиком (N+1) или медленный сам по себе, во втором случае — EXPLAIN (ANALYZE, BUFFERS) и разбор по Query Plans. После исправления статистику сбрасывают pg_stat_statements_reset() и смотрят снова.

Если в логе медленных запросов пусто, база работает хорошо.

Лог видит только запросы дольше порога, а нагрузку часто создают тысячи быстрых: в демо вставка по строке шла почти две секунды, а каждая отдельная — микросекунду. Нагрузку ищут в pg_stat_statements по суммарному времени и числу вызовов.

  • pg_stat_statements агрегирует запросы по тексту: сортировать по total_exec_time и смотреть на calls.
  • N+1: 201 запрос за 56 мс, из них в базе 11; соединение — 7 мс. В JPA — JOIN FETCH, any(?), batch fetch.
  • Вставка 20 000 строк: по одной — 1936 мс, addBatch — 50, с reWriteBatchedInserts — 32; IDENTITY ломает пакеты Hibernate.
  • OFFSET, SELECT *, count для проверки наличия, функции над колонкой, долгие транзакции — частые причины.

На собеседовании

Как найти, какие запросы нагружают PostgreSQL?

pg_stat_statements: агрегирует все запросы по нормализованному тексту и показывает число вызовов, суммарное и среднее время, строки, буферы. Сортируют по суммарному времени — так видны и редкие тяжёлые запросы, и частые лёгкие. Для единичных медленных — log_min_duration_statement и auto_explain, для того, что выполняется сейчас, — pg_stat_activity.

  • Время в pg_stat_statements — внутри базы; сеть и ожидание пула в него не входят.
  • Огромный calls на одну операцию — признак N+1.
  • Расширение нужно загрузить через shared_preload_libraries, это требует перезапуска.

Что такое проблема N+1 и как её решить?

Один запрос получает список из N объектов, а затем для каждого выполняется ещё запрос за связанными данными. Каждый запрос быстрый, но N кругов по сети складываются: в демо 201 запрос шёл 56 мс против 7 мс одного соединения. Решение — достать всё одним запросом: JOIN или JOIN FETCH, выборка по списку id через any(?), batch fetching в Hibernate.

  • В JPA N+1 дают ленивые связи в цикле и EAGER @ManyToOne в списках.
  • JOIN FETCH коллекций с пагинацией делает пагинацию в памяти — для них лучше два запроса.
Почему этот экспорт идёт полчаса? 
@Transactional
public void export(List<Long> merchantIds) {
    for (Long id : merchantIds) {
        Merchant m = merchants.findById(id).orElseThrow();
        for (Payment p : m.getPayments()) {          // LAZY
            auditRepository.save(new Audit(p.getId(), "exported"));   // @Id IDENTITY
        }
    }
}

Магазины грузятся по одному, платежи каждого — отдельным ленивым запросом (N+1), и каждая запись аудита вставляется отдельным INSERT: IDENTITY не даёт Hibernate собирать пакеты. Нужно загрузить магазины и платежи одним запросом или пачками по списку id, перейти на последовательность с allocationSize и hibernate.jdbc.batch_size, включить reWriteBatchedInserts и разбить работу на транзакции разумного размера.

Как быстро вставить много строк из Java?

Пакетами: PreparedStatement.addBatch и executeBatch вместо executeUpdate на каждую строку, в одной транзакции. Для PostgreSQL — ещё reWriteBatchedInserts=true, тогда драйвер склеивает пакет в многострочные INSERT. В демо: 1936 мс по одной, 50 мс пакетом, 32 мс с переписыванием. Для миллионов строк — COPY.

  • В Hibernate — hibernate.jdbc.batch_size и order_inserts; генерация IDENTITY отключает пакеты.
  • Слишком большая транзакция держит горизонт VACUUM; загрузку бьют на порции.
  • PostgreSQL 17: pg_stat_statements — основа урока: колонки, нормализация, сброс.
  • pgjdbc: Connection parameters — reWriteBatchedInserts.
  • auto_explain — планы медленных запросов в логе.
  • Vlad Mihalcea, «High-Performance Java Persistence» — N+1, пакетная запись и IDENTITY в Hibernate.
