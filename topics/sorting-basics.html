Sorting Basics

Правильный отчёт требует и порядка, и сохранения записей

В журнале платежей нужно показать операции по сумме. После сортировки цифры идут по возрастанию, но один платёж пропал, а другой встретился дважды. Проверка «каждый следующий элемент не меньше предыдущего» проходит — отчёт всё равно неверен. Контракт сортировки состоит из двух независимых требований.

Первое: результат упорядочен по выбранному отношению. Для массива a достаточно проверить соседей compare(a[i − 1], a[i]) ≤ 0, если компаратор задаёт согласованный транзитивный порядок. Второе: результат является перестановкой входа — сохранены элементы и их кратности. Сортировка не фильтрует и не удаляет дубликаты.

Для массива Payment сортируются ссылки на объекты. Идентичность платежа, сумма и другие поля сами от перемещения ссылки не меняются. Но массив после вызова содержит ссылки в другом порядке. Если вызывающий код должен сохранить исходную последовательность, сортируй копию массива и учитывай O(n) памяти на неё.

Сохрани как StablePayments.java и запусти java StablePayments.java на JDK 21.

import java.util.Arrays;
import java.util.Comparator;

public class StablePayments {
    record Payment(String id, long cents) {}

    public static void main(String[] args) {
        Payment[] payments = {
            new Payment("A", 200), new Payment("B", 100),
            new Payment("C", 200), new Payment("D", 100)
        };
        Payment first = payments[0];
        Arrays.sort(payments, Comparator.comparingLong(Payment::cents));
        // При равных cents объектная сортировка сохраняет порядок прихода.
        System.out.println(Arrays.toString(payments));
        System.out.println("same A=" + (first == payments[2])); // Переставлены ссылки, не поля объектов.
    }
}
[Payment[id=B, cents=100], Payment[id=D, cents=100], Payment[id=A, cents=200], Payment[id=C, cents=200]]
same A=true

Платёж A после сортировки находится на другой позиции, но это тот же объект. Возвращённая или созданная копия массива ссылок не делает объекты неизменяемыми: если суммы позже меняются, ранее отсортированный отчёт может перестать быть упорядоченным. В примере поля record неизменяемы.

Comparator должен задавать согласованный порядок

Алгоритм не знает, что сумма больше даты или что статус FAILED важнее PENDING. Он получает от Comparator отрицательное число, ноль или положительное число. Важен знак, а не обязанность вернуть ровно −1, 0, 1. Ноль означает эквивалентность для этого порядка, а не обязательно equals между объектами.

У знаков должны быть согласованные свойства. При перестановке аргументов знак меняется на противоположный. Из a < b и b < c следует a < c. Если compare(a, b) = 0, сравнения a и b с любым третьим элементом должны иметь одинаковый знак. Без этих правил последовательность сравнений не задаёт общего порядка, а результаты алгоритма теряют смысл.

Сохрани как BadCompare.java и запусти java BadCompare.java на JDK 21.

public class BadCompare {
    public static void main(String[] args) {
        int a = 0, b = Integer.MIN_VALUE;
        System.out.println("a-b=" + (a - b));
        System.out.println("b-a=" + (b - a)); // Оба знака отрицательные: порядок противоречит себе.
        System.out.println("compare(a,b)=" + Integer.compare(a, b));
        System.out.println("compare(b,a)=" + Integer.compare(b, a));
    }
}
a-b=-2147483648
b-a=-2147483648
compare(a,b)=1
compare(b,a)=-1

Вычитание переполнилось: компаратор одновременно объявил a меньше b и b меньше a. Для int бери Integer.compare, для long — Long.compare или comparingLong. Приведение результата long-вычитания к int тоже неверно: теряются старшие биты. Для обратного порядка меняй компаратор через reversed, а не надеясь на арифметический трюк.

Составной ключ задаётся лексикографически: сначала сравниваем главный признак, затем следующий только при равенстве. Для «сумма убывает, время прихода возрастает» reversed должен относиться только к сравнению суммы. Вызов reversed в конце всей цепочки развернёт также время и остальные признаки.

Нарушенный Comparator обязательно сразу выдаст понятное исключение.

Некоторые нарушения реализация сортировки может обнаружить и бросить IllegalArgumentException, но это не полная проверка контракта. Маленький пример может случайно отсортироваться ожидаемо. Проверять нужно свойства сравнения и крайние значения, а не только один результат sort.

Эквивалентность порядка, equals и null — разные решения

Два разных платежа одинаковой суммы могут сравниваться как 0 и при этом не быть equals. Сортировка сохранит обе записи; структура вроде TreeSet использует сравнение для эквивалентности ключей, поэтому выбор компаратора там имеет другой эффект. Нужна ли согласованность с equals, зависит от использования порядка.

Политику null задают явно. Comparator.nullsLast(order) обрабатывает null вместо целого объекта, а компаратор поля с nullsLast — null в этом поле. Реверс внешнего nullsLast-компаратора поменяет также расположение null. Для non-null платежей с nullable ключом выбирай поведение на уровне извлечённого ключа.

Стабильность сохраняет прежний порядок равных ключей

Входной журнал упорядочен по приходу, а отчёт группирует его по сумме. Внутри группы одинаковых сумм нужно оставить хронологию. Стабильная сортировка сохраняет относительный порядок элементов, для которых компаратор вернул 0. Стабильность не запрещает им перемещаться и не сравнивает ID автоматически.

Arrays.sort для массива объектов и List.sort гарантируют стабильность. Это свойство API полезно независимо от названия внутреннего алгоритма. Для одинаковых примитивных int наблюдаемой идентичности нет; если требуется сохранить связанную с числом запись, нужно сортировать запись или индекс, а не отрывать ключ от остальных данных.

Стабильность позволяет сортировать по нескольким ключам несколькими проходами. Сначала сортируй по второстепенному ключу, затем стабильным проходом по главному. Последний проход создаёт основные группы и сохраняет внутри них порядок предыдущего.

Сохрани как MultiPass.java и запусти java MultiPass.java на JDK 21.

import java.util.ArrayList;
import java.util.Comparator;
import java.util.List;

public class MultiPass {
    record Payment(String id, String account, int day) {}

    public static void main(String[] args) {
        List<Payment> payments = new ArrayList<>(List.of(
            new Payment("A", "X", 2), new Payment("B", "Y", 1),
            new Payment("C", "X", 1), new Payment("D", "Y", 2)));
        payments.sort(Comparator.comparingInt(Payment::day)); // Сначала второстепенный ключ.
        payments.sort(Comparator.comparing(Payment::account)); // Стабильный главный проход.
        System.out.println(payments.stream().map(Payment::id).toList());
    }
}
[C, A, B, D]

Получилось: сначала счёт X, в нём день 1 перед днём 2; затем счёт Y в таком же порядке. В одном вызове тот же порядок задаёт comparing(account).thenComparingInt(day). Если перепутать порядок проходов, главным окажется день. Составной компаратор проще читать и делает один запуск сортировки вместо двух.

Стабильная сортировка делает результат одинаковым при любом исходном порядке.

Наоборот, при равных ключах она сохраняет именно входной порядок. Если вход приходит из источника с произвольным порядком, результат тоже может различаться. Для воспроизводимого отчёта добавь явный последний ключ, например уникальный ID; это уже отдельное требование к порядку.

Сравнения должны различить все возможные перестановки

Почему универсальную сортировку сравнениями нельзя гарантированно сделать за линейное число сравнений? Возьмём n различных ключей. У них n! возможных взаимных порядков. Каждый ответ на вопрос «a меньше b?» выбирает одну из двух ветвей; в конце алгоритм должен отличить все порядки, иначе для двух разных входных отношений вернёт одно неверное решение.

Дерево высоты h имеет не более 2ʰ листьев. Нужно хотя бы n! листьев, значит h ≥ log₂(n!). Для n ≥ 2 произведение последних примерно n/2 множителей в n! не меньше (n/2)ⁿᐟ², откуда log₂(n!) = Ω(n log n). В худшем случае любой алгоритм, узнающий порядок только сравнениями, требует Ω(n log n) сравнений.

Это граница для всех допустимых входов с различными ключами, а не запрет обработать конкретный отсортированный массив за O(n). Адаптивная сортировка может использовать уже готовые серии; множество одинаковых ключей также меняет количество различных возможных порядков. Нужно называть модель и случай входа, как в Big O.

Counting sort и radix sort не опровергают доказательство: они используют информацию о ключах помимо парных сравнений. Для целых из диапазона 0…k − 1 counting sort требует O(n + k) работы и память, зависящую от k. Если суммы платежей — произвольные 64-битные значения, массив счётчиков по всему диапазону непригоден. Представление ключа и диапазон входят в условия алгоритма.

Цена одного сравнения тоже важна. Если строки длины до L могут совпадать почти целиком, O(n log n) сравнений даёт верхнюю оценку O(L·n log n) работы на сравнении ключей. Извлекать дорогой ключ заново внутри каждого compare — отдельный источник лишней работы; предварительное вычисление ключей меняет баланс времени и памяти.

Выбор сортировки зависит от гарантий и ограничений данных

Слова «быстрее» без условий недостаточно. Для отчёта важны стабильность и неизменность входа; для ограниченного буфера — дополнительная память; для недоверенных данных — худший случай. Таблица ниже относится к классическим реализациям, которые разбираются в соседних темах, а не ко всем перегрузкам Arrays.sort.

Не сортируй все данные, если нужен только минимум: линейный проход дешевле полного упорядочивания. Для top-K полезны куча или выбор порядковой статистики. Если отчёт не помещается в память, нужны отсортированные части на диске и их слияние; если обновления приходят непрерывно, может подойти упорядоченная структура вместо полной пересортировки после каждого события.

Во время сравнения ключи должны оставаться неизменными. Компаратор, зависящий от текущего времени, случайного числа или изменяемого баланса из другого потока, может нарушить транзитивность прямо в ходе sort. Сначала получи согласованный снимок ключей, потом сортируй. Это условие корректности, а не только оптимизация.

Порядок ответа на собеседовании: какие данные и ключи, допустимы ли повторы и null, нужна ли стабильность, можно ли менять вход, какие гарантии времени и памяти. Только после этого выбирай алгоритм. Механизмы merge, quick и heap разобраны отдельно; конкретные перегрузки JDK — в Sorting in Java.

  • Корректная сортировка даёт упорядоченную перестановку: без потери элементов и изменения кратностей.
  • Comparator задаёт согласованные знаки и транзитивность; вычитание вместо сравнения ломается на переполнении.
  • Стабильность сохраняет входной порядок только внутри равных ключей; воспроизводимость между разными входами требует явного tie-breaker.
  • Ω(n log n) — нижняя граница сравнений в худшем случае для произвольных различных ключей.
  • Стек, копии, дорогие ключи и требования к исходному порядку учитываются при выборе реализации.

Задачи

Сумма убывает, время прихода возрастает

У Payment есть уникальный non-null id, сумма cents и номер прихода sequence. Верни ID в порядке: cents по убыванию, sequence по возрастанию, затем id лексикографически по возрастанию. Входной массив не менять; null-платежей нет. Значения long могут быть крайними.

(B,100,3), (A,100,3), (C,200,9), (D,100,1) → [C,D,A,B]

Подсказка 1

Составь лексикографический Comparator из трёх сравнений.

Подсказка 2

Разверни только компаратор суммы, затем добавь thenComparing для остальных ключей.

Решение

Поверхностная копия массива сохраняет исходную последовательность ссылок. Компаратор сначала сравнивает суммы безопасным comparingLong, затем время, затем ID. Время O(n log n) сравнений, память O(n) на копию, результат и работу объектной сортировки. При переменной длине ID учитывается цена сравнения строк.

    static List<String> orderedIds(Payment[] source) {
        Payment[] copy = source.clone(); // Внешний порядок входа сохраняем.
        Comparator<Payment> order = Comparator.comparingLong(Payment::cents).reversed()
                .thenComparingLong(Payment::sequence)
                .thenComparing(Payment::id);
        Arrays.sort(copy, order);
        return Arrays.stream(copy).map(Payment::id).toList();
    }
Что не так с comparingLong(cents).thenComparingLong(sequence).reversed()?

Будут убывать оба признака. В условии sequence должен возрастать, поэтому reversed вызывают до thenComparingLong.

Можно ли убрать последний ключ, раз сортировка стабильная?

Тогда A и B с одинаковыми cents и sequence сохранят входной порядок B, A. Условие требует A, B по ID, поэтому стабильность не заменяет последний ключ.

Проверить результат чужой сортировки

Даны два int-массива before и after. Верни true, только если after отсортирован по возрастанию и является перестановкой before с теми же кратностями. Входы не менять, сортировку не вызывать. Нужна ожидаемая линейная сложность при стандартном предположении о работе HashMap.

[2,1,2] → [1,2,2]: true
[2,1,2] → [1,1,2]: false

Подсказка 1

Упорядоченность соседей и сохранение содержимого проверяются независимо.

Подсказка 2

Множество потеряет кратности. Храни частоту каждого значения до сортировки и расходуй её после.

Решение

Сначала проверяем длину и соседние пары, затем баланс частот. Новый элемент или лишняя копия обнаруживаются при расходовании отсутствующей частоты. Ожидаемое время O(n), дополнительная память O(u), где u — число разных значений. Здесь n — длина входа после проверки равенства длин.

    static boolean valid(int[] before, int[] after) {
        if (before.length != after.length) return false;
        for (int i = 1; i < after.length; i++) {
            if (after[i - 1] > after[i]) return false; // Только порядок ещё не доказывает корректность.
        }
        Map<Integer, Integer> counts = new HashMap<>();
        for (int value : before) counts.merge(value, 1, Integer::sum);
        for (int value : after) {
            Integer count = counts.get(value);
            if (count == null) return false;
            if (count == 1) counts.remove(value);
            else counts.put(value, count - 1);
        }
        return counts.isEmpty(); // Проверили кратности, а не только набор разных значений.
    }
Почему сравнить Set.copyOf(before) и Set.copyOf(after) недостаточно?

У [1,1,2] и [1,2,2] одинаковые множества значений, но разные кратности. Кроме того, такой вызов непосредственно на int[] не является подходящим способом создания множества элементов. Нужен именно подсчёт частот.

Можно ли проверкой соседей обойтись с произвольным Comparator?

Только при корректном транзитивном компараторе. Если сравнение циклическое, соседние пары не гарантируют согласованность всех пар. Проверка результата не исправляет нарушенный контракт порядка.

Сохранить порядок равных ключей явным индексом

Платежи сортируются по cents по возрастанию, равные суммы должны сохранять порядок входа. Покажи способ задать это требование в самом составном ключе, не опираясь на стабильность используемого алгоритма. Для запуска можно применять Arrays.sort; вход не менять. ID не участвует в сравнении.

(Z,5), (A,5), (B,1) → [B,Z,A]

Подсказка 1

Входной порядок можно превратить в обычное числовое поле.

Подсказка 2

Создай пары (платёж, исходный индекс), сортируй сначала по сумме, затем по индексу.

Решение

Декорируем каждое вхождение уникальным исходным индексом. Для равных сумм меньший индекс всегда идёт раньше, поэтому стабильность алгоритма больше не требуется: составные ключи различных вхождений не равны. В этой реализации время O(n log n), память O(n). Это полезная трансформация, но при уже стабильном API дополнительные обёртки могут быть лишними.

    static List<String> orderedIds(Payment[] input) {
        Indexed[] decorated = new Indexed[input.length];
        for (int i = 0; i < input.length; i++) decorated[i] = new Indexed(input[i], i);
        Arrays.sort(decorated, Comparator.comparingInt((Indexed v) -> v.payment().cents())
                .thenComparingInt(Indexed::index)); // Равных составных ключей больше нет.
        return Arrays.stream(decorated).map(v -> v.payment().id()).toList();
    }
Что будет, если вместо индекса взять ID?

В примере получится [B,A,Z], что меняет порядок равных сумм. ID обеспечивает другой порядок, а не сохранение исходного.

Почему это не превращает heapsort в стабильный алгоритм с O(1) памятью?

Мы изменили данные и компаратор, добавив индексы. Поведение результата соответствует стабильному порядку исходных ключей, но обёртки и индексы требуют O(n) дополнительной памяти; свойство исходного heapsort от этого не изменилось.
