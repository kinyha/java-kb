Spring: RabbitMQ in Spring

В RabbitMQ отправитель пишет не в очередь, а в exchange, и брокер по ключу маршрутизации раскладывает копии по привязанным очередям. Сообщение живёт в очереди, пока потребитель его не подтвердит, а потом исчезает. Spring AMQP даёт RabbitTemplate для отправки и @RabbitListener, который подтверждает сообщение после успешного метода. Без настройки исключение в листенере возвращает сообщение в очередь, и оно мгновенно приходит снова — тысячи раз в секунду.

Событие платежа нужно трём получателям с разными правилами

Платёжный сервис сообщает о каждом платеже. Бухгалтерии нужны только успешные, дежурным — только неудачные, аудиту — все. Добавится антифрод, и ему нужны крупные платежи. Если отправитель сам знает про каждого получателя, каждое новое правило — релиз платёжного сервиса.

RabbitMQ выносит маршрутизацию в брокер. Отправитель публикует сообщение с ключом вроде payment.completed в exchange. Exchange по привязкам (bindings) кладёт копию в каждую подходящую очередь. Получатель читает свою очередь и подтверждает обработку, после чего брокер удаляет сообщение. Новому получателю достаточно своей очереди и привязки.

В этом главное отличие от Kafka из Kafka in Spring. Kafka хранит журнал, и каждый читатель сам двигает своё смещение; прочитанное остаётся. RabbitMQ — почтовое отделение: брокер решает, куда доставить, и забывает сообщение после подтверждения.

Демо RabbitDemo.java работает с настоящим RabbitMQ 4.3 в Docker. Стек: JDK 21, Spring Boot 4.1.1, Spring AMQP 4.1.

docker run -d --name kb-rabbit -p 5672:5672 rabbitmq:4-management
cd examples/rabbit
./run.sh RabbitDemo routing # exchange, привязки, подтверждение и возврат
./run.sh RabbitDemo requeue # исключение без настройки
./run.sh RabbitDemo dlx     # повторы и dead letter exchange

Exchange по ключу раскладывает копии по очередям

Топологию объявляют бинами. RabbitAdmin, который создаёт Boot, при первом подключении объявляет в брокере все бины Exchange, Queue и Binding, а также содержимое Declarables:

@Bean
Declarables topology() {
    var ex = new TopicExchange("payments");
    var ledger = QueueBuilder.durable("ledger").build(); // durable: очередь переживёт рестарт брокера.
    var alerts = QueueBuilder.durable("alerts").build();
    var audit = QueueBuilder.durable("audit").build();
    return new Declarables(ex, ledger, alerts, audit,
            BindingBuilder.bind(ledger).to(ex).with("payment.completed"),
            BindingBuilder.bind(alerts).to(ex).with("payment.failed"),
            BindingBuilder.bind(audit).to(ex).with("payment.*")); // * — ровно одно слово.
}

for (String key : List.of("payment.completed", "payment.failed", "refund.completed")) {
    template.convertAndSend("payments", key, key); // exchange, routing key, тело.
}
ledger=[payment.completed], alerts=[payment.failed], audit=[payment.completed, payment.failed]
Тип exchangeКак выбирает очереди
directКлюч совпадает с ключом привязки точно
topicПо шаблону из слов через точку: * — одно слово, # — ноль и больше

Подтверждение брокера не означает, что сообщение куда-то попало

По умолчанию convertAndSend пишет в сокет и возвращается. Брокер мог не принять сообщение, а приложение об этом не узнает. Для надёжной отправки включают два механизма:

spring:
  rabbitmq:
    publisher-confirm-type: correlated # Брокер подтверждает приём: ack или nack.
    publisher-returns: true            # Брокер возвращает сообщения без маршрута...
    template:
      mandatory: true                  # ...если отправитель об этом попросил.
template.setReturnsCallback(r -> System.out.println("returned " + r.getRoutingKey() + ": " + r.getReplyText()));
var cd = new CorrelationData(key);
template.convertAndSend("payments", key, key, cd);
System.out.println("sent " + key + ": confirm ack=" + cd.getFuture().get(5, TimeUnit.SECONDS).ack());
sent payment.completed: confirm ack=true
sent payment.failed: confirm ack=true
sent refund.completed: confirm ack=true
returned refund.completed: NO_ROUTE

Для refund.completed брокер ответил ack=true, хотя сообщение не попало ни в одну очередь. Confirm значит «брокер принял сообщение и отвечает за него», а не «сообщение лежит в очереди». Без mandatory сообщение без маршрута молча удаляется, и даже return не придёт. Поэтому надёжная отправка смотрит на оба ответа: nack — повторить, return — ошибка топологии, которую нельзя лечить повтором.

Чтобы принятое сообщение пережило рестарт брокера, нужны долговечная очередь и постоянное сообщение. Spring по умолчанию отправляет с deliveryMode=PERSISTENT, а QueueBuilder.durable создаёт долговечную очередь. В RabbitMQ 4 для важных данных рекомендуют quorum-очереди: они реплицируются на несколько узлов кластера через Raft. Classic-очередь живёт на одном узле.

Как и в Kafka, отправка не атомарна с транзакцией базы. Платёж закоммитился, а сообщение не ушло — или наоборот. Надёжная схема — Transactional Outbox.

Исключение в листенере по умолчанию возвращает сообщение в очередь, и оно приходит снова

@RabbitListener создаёт контейнер, который держит канал к брокеру и получает сообщения пачками до prefetch (по умолчанию 250) неподтверждённых штук. Режим AcknowledgeMode.AUTO: метод вернулся — контейнер отправляет basic.ack, и брокер удаляет сообщение. Метод бросил исключение — контейнер отправляет basic.reject с requeue=true, и брокер кладёт сообщение обратно в голову очереди.

@RabbitListener(queues = {"charges-classic", "charges-quorum"})
void on(String body, Message m) {
    deliveries.computeIfAbsent(m.getMessageProperties().getConsumerQueue(), q -> new AtomicInteger())
              .incrementAndGet();
    throw new IllegalStateException("bank declined"); // Каждая доставка падает.
}

// По одному сообщению в classic- и quorum-очередь, ждём 3 секунды.
deliveries in 3 s: classic=21205, quorum=4621
quorum x-delivery-count on last delivery: null
left in queue: classic=0, quorum=0

Одно сообщение за три секунды доставлено двадцать тысяч раз. Брокер возвращает его в очередь и тут же отдаёт тому же потребителю. Процессор занят, лог забит стеками, а очередь показывает ноль сообщений: единственное сообщение всё время «в работе». Остальные сообщения очереди за ним стоят.

Quorum-очередь в RabbitMQ 4 имеет лимит доставок, по умолчанию 20, после которого сообщение удаляется или уходит в dead letter. От этого цикла он не спас: заголовок x-delivery-count так и не появился, а доставок было больше четырёх тысяч. Рассчитывать на лимит брокера вместо своей обработки ошибок нельзя.

Исключения, которые не имеет смысла повторять, Spring сам отклоняет без возврата: MessageConversionException (тело не разобрать) считается фатальным. Для остальных выбор за тобой. Бросить AmqpRejectAndDontRequeueException — сообщение не вернётся. Настройка spring.rabbitmq.listener.simple.default-requeue-rejected=false меняет поведение для всех исключений. И то и другое без dead letter exchange означает удаление сообщения.

Если листенер упал, сообщение вернётся в очередь и обработается позже, когда сервис восстановится.

Оно вернётся в голову очереди и придёт снова через миллисекунды, тому же потребителю. Без паузы и лимита это бесконечный цикл, который блокирует остальные сообщения. Повторы с паузой и dead letter настраивают явно.

Повторы с паузой в приложении, затем dead letter exchange в брокере

Нормальная схема делит ответственность. Приложение делает несколько попыток с растущей паузой, чтобы пережить кратковременный сбой банка. Если не помогло, оно отклоняет сообщение без возврата, а брокер по аргументу очереди x-dead-letter-exchange перекладывает его в очередь мёртвых писем для разбора людьми.

var refunds = QueueBuilder.durable("refunds")
        .deadLetterExchange("dlx")             // Куда брокер переложит отвергнутое.
        .deadLetterRoutingKey("refunds.dead")
        .build();
spring:
  rabbitmq:
    listener:
      simple:
        retry:
          enabled: true
          max-retries: 2         # Boot 4: повторы сверх первой попытки.
          initial-interval: 300ms
          multiplier: 2          # 300 мс, затем 600 мс.
509 ms: attempt 1 for refund-7
813 ms: attempt 2 for refund-7
1415 ms: attempt 3 for refund-7
DLQ got refund-7, x-death reason=rejected, queue=refunds

В Boot 4 число повторов задаёт max-retries, и по умолчанию их 3, то есть 4 попытки. Первая версия демо использовала прежнее имя max-attempts: 3 и получила четыре попытки, а не три, как было в Boot 3. При переходе на Boot 4 такие настройки стоит перепроверить по фактическому числу попыток.

Повторы внутри приложения держат поток контейнера: пока refund-7 ждёт паузы, этот потребитель не берёт другие сообщения. Паузы в минуты так не делают. Для долгих задержек используют очередь ожидания с TTL, из которой сообщение через dead letter возвращается в рабочую, или плагин отложенных сообщений.

Аргументы очереди фиксируются при её объявлении. Если добавить deadLetterExchange к уже существующей очереди, следующий запуск упадёт с PRECONDITION_FAILED: брокер не меняет аргументы. Для живых очередей dead letter задают политикой RabbitMQ, а не аргументом в коде.

Для платёжного сервиса это часто значит обе системы. Задачи с индивидуальной судьбой — отправить чек, повторить вызов банка, разобрать отказ — удобно раздавать через RabbitMQ: каждое сообщение подтверждается и повторяется отдельно. Поток событий, который нужен многим сервисам и который полезно перечитать, например история платежей для аналитики, — в Kafka.

Конкурирующие потребители одной очереди ломают порядок: два потребителя с prefetch 250 обрабатывают соседние сообщения параллельно, а requeue кладёт упавшее сообщение обратно позже остальных. Если порядок по счёту важен, нужна одна очередь на группу счетов с единственным потребителем или Kafka с ключом.

  • Отправитель пишет в exchange; привязки решают, в какие очереди лягут копии.
  • Confirm ack значит «брокер принял», а не «положил в очередь»: без mandatory и returns сообщение без маршрута теряется молча.
  • AUTO ack: метод вернулся — ack, исключение — reject с возвратом в голову очереди и мгновенный повтор.
  • Повторы с паузой делает приложение, потом reject без возврата и dead letter exchange в брокере. В Boot 4 это retry.max-retries.
  • RabbitMQ удобен для задач с индивидуальной судьбой, Kafka — для журнала событий, который читают многие.

На собеседовании

Как сообщение доходит до потребителя в RabbitMQ и чем это отличается от Kafka?

Отправитель публикует сообщение с ключом маршрутизации в exchange. Exchange по привязкам кладёт копию в каждую подходящую очередь: direct по точному ключу, topic по шаблону, fanout во все. Потребитель читает очередь и подтверждает сообщение, после чего брокер его удаляет.

В Kafka отправитель пишет в топик, сообщения хранятся в журнале независимо от чтения, а каждая группа потребителей сама ведёт своё смещение и может перечитать прошлое. В RabbitMQ после подтверждения сообщения нет.

  • Exchange по умолчанию "" маршрутизирует в очередь с именем, равным ключу.
  • Конкурирующих потребителей на очередь может быть сколько угодно, но порядок между ними не гарантирован.
  • Quorum-очереди реплицируются через Raft и рекомендуются для важных данных; classic живёт на одном узле.

Что произойдёт, если @RabbitListener бросит исключение?

В режиме AUTO контейнер отправит reject с requeue=true, и брокер вернёт сообщение в голову очереди. Оно тут же придёт снова, и без настройки это бесконечный цикл: в демо одно сообщение доставлено двадцать тысяч раз за три секунды.

Я включаю повторы с паузой в приложении, после них сообщение отклоняется без возврата, а у очереди задан dead letter exchange, который перекладывает его в DLQ для разбора.

  • MessageConversionException Spring считает фатальным и не возвращает; AmqpRejectAndDontRequeueException отклоняет без возврата явно.
  • Повторы интерцептора держат поток контейнера; для долгих пауз нужна очередь ожидания с TTL.
  • Лимит доставок quorum-очереди в демо не остановил цикл явного requeue; полагаться на него вместо своей обработки нельзя.
  • В Boot 4 число повторов — retry.max-retries; с прежним max-attempts: 3 демо получило четыре попытки вместо трёх.

Как убедиться, что отправленное сообщение не потерялось?

Включаю publisher confirms: брокер подтверждает приём каждого сообщения ack или nack. И publisher returns с mandatory: если сообщение не подошло ни одной очереди, брокер вернёт его. Confirm сам по себе не значит, что сообщение в очереди: в демо сообщение без маршрута получило ack и вернулось с NO_ROUTE.

Чтобы сообщение пережило рестарт брокера, очередь должна быть durable, а сообщение persistent; Spring отправляет persistent по умолчанию.

  • Отправка не атомарна с транзакцией базы; для гарантии используют outbox.
  • nack — повод повторить отправку, return — ошибка топологии, повтор её не исправит.
  • Транзакции канала AMQP медленные и редко нужны; confirms решают ту же задачу дешевле.
Почему после переименования привязки события о возвратах перестали доходить, а ошибок в логах нет? 
// Привязку refunds.completed переименовали в refund.completed, отправитель не обновили.
rabbitTemplate.convertAndSend("payments", "refunds.completed", event);

Ключ больше не совпадает ни с одной привязкой, и exchange удаляет сообщение. Без mandatory брокер ничего не возвращает, а confirm приходит с ack=true, поэтому отправитель считает отправку успешной. Нужно включить publisher-returns и template.mandatory, логировать и алертить возвраты, а изменения топологии проверять тестом с реальным брокером.
