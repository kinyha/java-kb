Spring: AOP & Proxies

Общее поведение удобно добавить вокруг вызова сервиса: измерить время, проверить права, открыть транзакцию. Spring выдаёт клиенту оболочку, которая выполняет эти действия и обращается к исходному объекту. Поэтому главный вопрос — прошёл ли конкретный вызов через эту оболочку. От него зависят и работа аннотаций, и внутренние вызовы, и ограничения final.

Метрики и транзакции добавляются на границе вызова сервиса

Десять сервисов отправляют платежи, и в каждом нужны измерение времени, журналирование ошибок и проверка прав. Если вставлять одинаковый код вокруг каждого метода, основная логика становится труднее читать. Общее поведение удобно выделить отдельно и подключить к нужным вызовам.

Spring AOP делает это через прокси: клиент получает ссылку на оболочку. Она выполняет дополнительные действия, вызывает исходный объект и обрабатывает завершение. Исходный PaymentService по-прежнему содержит обычный метод Java. Разница возникает на пути, по которому клиент в него пришёл.

Так устроены многие инфраструктурные аннотации, в том числе декларативные транзакции, кеширование и асинхронные вызовы. Для них нужна подключённая инфраструктура и вызов через подходящий прокси. Простое присутствие аннотации в исходном файле описывает намерение, а работу выполняет цепочка обработчиков.

Полезный мысленный опыт: возьми ссылку, через которую вызывается сервис, и проследи её до реального метода. Это сразу отличает внешний вызов через Spring от самостоятельного new и внутреннего вызова через this.

Pointcut выбирает вызов, advice задаёт добавленное действие

Join point — место, где можно подключить дополнительное поведение. В Spring AOP это выполнение метода бина через прокси. Pointcut отбирает такие места, advice выполняет действие до, после или вокруг вызова. Advisor связывает условие выбора с обработчиком, а aspect объединяет связанные правила.

Например, pointcut выбирает pay у бина gateway, advice измеряет длительность вызова. Аннотация @Aspect описывает этот набор правил, но сам аспект также должен стать бином: через @Bean, сканирование или импорт. В обычном Framework приложение подключает @EnableAspectJAutoProxy; Boot может сделать это автоматической конфигурацией.

execution описывает сигнатуру метода, within ограничивает область классов, @annotation проверяет аннотацию метода, args учитывает аргументы. this относится к объекту прокси, target — к исходному объекту. Поэтому this(ConcreteService) различает JDK-прокси и прокси-подкласс, тогда как target проверяет реальную реализацию. bean — расширение Spring для выбора по имени бина.

Spring использует синтаксис pointcut и аннотации AspectJ, сохраняя собственный механизм прокси. Для перехвата конструктора, доступа к полю или произвольного вызова внутри объекта нужен другой механизм, например weaving AspectJ. Наличие aspectjweaver.jar для разбора выражений ещё не включает такое преобразование классов.

Под капотом: как аспект превращается в цепочку

AnnotationAwareAspectJAutoProxyCreator обнаруживает аспекты и подходящие advisors. При создании бина он определяет, нужна ли оболочка; при вызове прокси строится цепочка подходящих перехватчиков для метода. Часть проверки pointcut возможна заранее по классу и методу, а условие по реальным аргументам может проверяться при каждом вызове.

Around охватывает следующий участок цепочки, а не только target

Вызов проходит через упорядоченную цепочку. Around получает ProceedingJoinPoint и решает, когда передать управление дальше через proceed. Следующим участком может быть ещё один advice. Поэтому код после proceed выполняется на обратном пути, в порядке, обратном входу.

В AdviceDemo.java аспекты имеют разные Order. Все регистрации и оба Around показаны ниже. Меньшее число означает более высокое предпочтение: такой аспект выполняется первым на входе и последним на выходе.

Полный пример AdviceDemo.java, Java 21, Spring 7.0.9. 

cd examples/spring-core
./run.sh AdviceDemo
import org.aspectj.lang.ProceedingJoinPoint;
import org.aspectj.lang.annotation.*;
import org.springframework.context.annotation.*;
import org.springframework.core.annotation.Order;

public class AdviceDemo {
    interface Gateway { void pay(); }
    static class BankGateway implements Gateway {
        public void pay() { System.out.println("target pay"); }
    }
    @Aspect @Order(1)
    static class Outer {
        @Around("bean(gateway) && execution(* pay(..))")
        Object around(ProceedingJoinPoint call) throws Throwable {
            System.out.println("outer enter");
            try { return call.proceed(); }
            finally { System.out.println("outer exit"); }
        }
    }
    @Aspect @Order(2)
    static class Inner {
        @Around("bean(gateway) && execution(* pay(..))")
        Object around(ProceedingJoinPoint call) throws Throwable {
            System.out.println("inner enter");
            try { return call.proceed(); }
            finally { System.out.println("inner exit"); }
        }
    }
    @Configuration(proxyBeanMethods = false)
    @EnableAspectJAutoProxy
    static class Config {
        @Bean Gateway gateway() { return new BankGateway(); }
        @Bean Outer outer() { return new Outer(); }
        @Bean Inner inner() { return new Inner(); }
    }
    public static void main(String[] args) {
        try (var ctx = new AnnotationConfigApplicationContext(Config.class)) {
            ctx.getBean(Gateway.class).pay();
        }
    }
}

BeforeПеред охваченным вызовомПроверить условия; исключение прервёт вызов
AfterReturningПри нормальном завершенииПолучить результат, выполнить побочное действие
AfterThrowingПри подходящем исключенииРеагировать на ошибку; восстановление нормального результата требует Around
AfterПосле завершения, как finallyОсвободить ресурс при успехе и ошибке
AroundОхватывает следующий участокИзменить аргументы/результат, вызвать дальше или вернуть ответ сразу

Around может вызвать proceed несколько раз. Для повторной попытки это означает повторное выполнение следующей цепочки и целевого действия, а для списания денег — риск повторного списания. Если задача только наблюдать успех, AfterReturning проще. Присвоение новой ссылки локальной переменной в AfterReturning не заменяет возвращаемый результат; такую замену выполняют через Around.

Порядок имеет смысл для взаимодействующих механизмов. Retry снаружи transaction advice может создавать отдельную транзакционную попытку; retry внутри одной транзакции продолжает работу в её контексте, который уже мог стать rollback-only. Конкретное поведение зависит от propagation и обрабатываемой ошибки. Сам Order задаёт вложенность, а корректность повторов определяет бизнес-протокол.

JDK-прокси реализует интерфейсы, CGLIB создаёт подкласс

У JDK-прокси есть интерфейсы сервиса, но он не является экземпляром BankGateway. Клиенту удобно зависеть от Gateway. Вызов интерфейсного метода направляется обработчику, который может вызвать даже final-метод исходного объекта: наследование BankGateway для этого не требуется.

CGLIB создаёт подкласс BankGateway и переопределяет методы для перехвата. Поэтому final-класс невозможно расширить, а final-метод невозможно переопределить. Private и static тоже обходят обычный путь такого AOP. Унаследованные методы с ограниченной видимостью дополнительно зависят от пакета и доступности для подкласса.

Boot по умолчанию включает прокси классов через автоматическую конфигурацию AOP. Свойство spring.aop.proxy-target-class=false переключает её на интерфейсный вариант. В явном ProxyFactory ниже выбор задан для каждого опыта, поэтому результат не зависит от настроек Boot.

В ProxyDemo.java один интерфейс и одна реализация используются с обоими видами оболочки. owner — final-метод, читающий поле, присвоенное в конструкторе. Лог показывает также внутренний и внешний audit.

Полный пример ProxyDemo.java, Java 21, Spring 7.0.9. 

cd examples/spring-core
./run.sh ProxyDemo
import java.util.logging.*;
import org.aopalliance.intercept.MethodInterceptor;
import org.springframework.aop.framework.ProxyFactory;
import org.springframework.aop.support.AopUtils;

public class ProxyDemo {
    public interface Gateway {
        void pay();
        void audit();
        String owner();
    }
    public static class BankGateway implements Gateway {
        final String bank;
        public BankGateway() { bank = "bank"; }
        public void pay() {
            System.out.println("target pay");
            audit(); // Этот вызов идёт через this исходного объекта.
        }
        public void audit() { System.out.println("target audit"); }
        public final String owner() { return bank; }
    }
    static void run(boolean classProxy) {
        var target = new BankGateway();
        var factory = new ProxyFactory(target);
        factory.setInterfaces(Gateway.class);
        factory.setProxyTargetClass(classProxy);
        factory.addAdvice((MethodInterceptor) invocation -> {
            String method = invocation.getMethod().getName();
            System.out.println("advice > " + method);
            try { return invocation.proceed(); }
            finally { System.out.println("advice < " + method); }
        });
        var proxy = (Gateway) factory.getProxy();
        System.out.println(classProxy ? "CGLIB:" : "JDK:");
        System.out.println("class proxy: " + AopUtils.isCglibProxy(proxy));
        proxy.pay();
        proxy.audit(); // Здесь вызов приходит снаружи через прокси.
        System.out.println("owner: " + proxy.owner()); // В CGLIB метод final.
    }
    public static void main(String[] args) {
        // Предупреждение о final-методе ожидается; результат печатаем сами.
        Logger.getLogger("org.springframework").setLevel(Level.SEVERE);
        run(false);
        run(true);
    }
}

В этом запуске CGLIB-оболочка создана через Objenesis с обходом своего конструктора. Final owner выполняется прямо на ней, поскольку не переопределён: он читает её незаполненное поле и возвращает null. Обычные перехваченные методы делегируют отдельному подготовленному target. Если обход конструктора недоступен и применяется резервный способ создания, значение поля может отличаться; отсутствие перехвата final сохраняется.

Вызов через this остаётся внутри исходного объекта

В ProxyDemo внешний proxy.pay проходит через advice. Затем BankGateway.pay вызывает audit через this, то есть исходный BankGateway. Внутренний вызов не возвращается к прокси, поэтому отдельный advice для audit отсутствует. При следующем внешнем proxy.audit появляется перехват для этого же метода.

Из-за этого собственный метод с @Transactional, @Cacheable или @Async способен вести себя как обычный метод. Переключение JDK на CGLIB сохраняет причину: стандартный Spring AOP делегирует выполнение отдельному target. При разборе ошибки важен вызывающий объект, а не только аннотация на вызываемом методе.

Самое ясное исправление — выделить отдельный компонент с нужной границей поведения и внедрить его. Тогда внешний вызов проходит по ссылке Spring. Ссылка на собственный прокси также может работать, но добавляет зависимость на механизм сборки и возможный цикл. AopContext.currentProxy требует exposeProxy и связывает код с текущим AOP-вызовом; это более тесная зависимость от инфраструктуры.

У full @Configuration другой способ перехвата: тело выполняется в усиленном экземпляре конфигурации, и прямой вызов другого @Bean может попасть в переопределённый метод этого же подкласса. Название CGLIB общее, но геометрия объектов отличается. Подмена методов конфигурации и сервисный AOP решают разные задачи.

В init исходный объект также ещё готовится, а самостоятельно созданный new вообще не проходит стандартную обработку бина. Для первого случая выбирают отдельный этап запуска, для второго — управляемую сборку или явную обычную оболочку Java. Эти причины разобраны в Bean Lifecycle.

Диагностика прокси начинается с реальной ссылки клиента

Проверь AopUtils.isAopProxy, isJdkDynamicProxy или isCglibProxy на той ссылке, через которую выполняется вызов. AopUtils.getTargetClass помогает узнать исходный тип. Если объект реализует Advised и конфигурация доступна, getAdvisors показывает подключённые правила. Класс из исходного файла и класс фактически полученной ссылки могут различаться.

Дальше проверь, попал ли метод в pointcut, какая версия конфигурации включена и откуда пришёл вызов. Прямой new, this и final у прокси класса объясняют разные обходы. Проверка типа прокси не доказывает, что нужный advice подходит конкретному методу.

Для порядка разных аспектов используй Ordered или @Order на аспекте. Два advice одного вида в одном аспекте не получают надёжный порядок из расположения методов в исходнике. Если их последовательность важна, объедини логику или выдели упорядоченные аспекты. Несколько оболочек разных подсистем также могут иметь внешнюю и внутреннюю цепочки.

AOP хорошо выражает общее техническое поведение на границе вызова. Если аспект начинает выбирать банк, менять бизнес-состояние или незаметно повторять необратимое действие, основная логика становится трудно обозримой. Такие решения лучше показать в сервисе или явной стратегии, оставив инфраструктуре измерение, проверку и управление контекстом.

  • Pointcut выбирает вызов, advice выполняет добавленное действие, а прокси связывает их с target.
  • Around охватывает оставшуюся цепочку. Меньший Order входит первым и выходит последним.
  • JDK использует интерфейс; CGLIB — подкласс с ограничениями переопределения.
  • This внутри target обходит обычный Spring AOP у обоих видов прокси.
  • Проверяй реальную ссылку, matching и путь вызова; повторение proceed может повторить бизнес-действие.

На собеседовании

Как Spring AOP добавляет поведение к методу?

Клиент получает прокси бина. Прокси выбирает подходящие обработчики, выполняет их и вызывает исходный объект. Pointcut отвечает за выбор метода, advice — за действие; advisor соединяет их, а аспект группирует правила.

При разборе я прослеживаю путь ссылки. Аннотация описывает намерение, но для её работы нужна подключённая инфраструктура и подходящий внешний вызов.

  • Spring AOP перехватывает выполнение методов через прокси. Конструкторы и доступ к полям требуют другого механизма.
  • Синтаксис AspectJ и его аннотации могут использоваться без weaving: исполнение остаётся в Spring-прокси.

Чем JDK-прокси отличается от CGLIB и что происходит с final?

JDK-прокси реализует интерфейс и передаёт вызов обработчику. CGLIB создаёт подкласс и переопределяет методы. Поэтому JDK может перехватить интерфейсный вызов final-метода target, а CGLIB — нет.

Для final-класса подходит интерфейсный вариант. Клиент JDK-прокси зависит от интерфейса; приведение к конкретной реализации ошибочно. В Boot автоматическая конфигурация по умолчанию выбирает прокси класса.

  • Обход конструктора прокси через Objenesis отделяет его состояние от состояния target. Final-метод, исполненный на самой оболочке, способен читать незаполненные поля.
  • Private, static и недоступные подклассу методы не образуют обычный путь перехвата CGLIB.

Почему вызов собственного метода обходит AOP даже с CGLIB?

Перехват находится в оболочке, а целевой метод выполняется на исходном объекте. Его this ссылается на этот объект, поэтому внутренний вызов остаётся внутри него. Выбор подкласса для оболочки сам по себе этот путь не меняет.

Я выделяю компонент, чью границу действительно нужно перехватывать, и вызываю его через внедрённую ссылку. Это делает транзакцию, кеш или асинхронность видимыми по структуре кода.

  • Собственный прокси требует отдельного получения ссылки и может добавить цикл; AopContext требует exposeProxy и текущего AOP-вызова.
  • У full Configuration прямые Bean-вызовы устроены иначе: усиленный экземпляр конфигурации использует собственные переопределённые методы.

Как работает порядок Around и почему важен proceed?

Around окружает следующий участок цепочки. При меньшем Order обработчик выполняется раньше на входе и позже на выходе. Proceed передаёт управление дальше; без него метод может вообще не выполниться.

Для нескольких попыток каждый proceed повторяет оставшийся участок. Я учитываю вложенность retry и transaction, а также безопасность повторного бизнес-действия.

  • AfterReturning наблюдает нормальный результат, но присвоение его параметру другую ссылку не заменяет ответ клиента. Для замены нужен Around.
  • У однотипных advice в одном аспекте порядок не следует надёжно из исходника. Если он важен, задаётся между отдельными аспектами.

Аннотация стоит, но перехвата нет. Что проверить?

Я проверяю реальную ссылку клиента через AopUtils, затем регистрацию инфраструктуры и соответствие метода pointcut. После этого смотрю на путь вызова: внешний через прокси, внутренний this или самостоятельный new. Для CGLIB также важны final и видимость метода.

Разные причины требуют разных исправлений: зарегистрировать бин или аспект, уточнить выбор методов, изменить границу компонента. Добавление аннотации к той же строке не меняет геометрию вызова.

  • У доступного Advised можно посмотреть advisors, но наличие одного из них не доказывает его применимость к каждому методу.
  • Init выполняется на этапе подготовки объекта: обычный внешний путь AOP для собственных вызовов там отсутствует.
