Spring: Scheduling & Async

@Async отдаёт вызов метода в пул потоков и сразу возвращает управление. Делает это прокси, поэтому вызов изнутри класса остаётся синхронным. Пул Boot по умолчанию держит 8 потоков и бесконечную очередь: лишние задачи не создают потоки, а копятся в памяти. В новый поток не переходят ни исключение, ни MDC, ни SecurityContext, ни транзакция. @Scheduled запускает задачи по времени, по умолчанию в одном потоке, и в кластере — на каждом экземпляре сразу.

Платёж ждёт SMS и чек, хотя клиенту они не нужны сразу

После списания платёжный сервис отправляет SMS, формирует PDF-чек и пишет событие в аналитику. Каждое действие ходит во внешний сервис и занимает сотни миллисекунд. Клиент ждёт ответа «оплачено», а ответ задерживают задачи, результат которых ему сейчас не нужен. Когда SMS-шлюз тормозит, тормозят и платежи.

Такие действия выносят из потока запроса. В Spring для этого две аннотации. @Async выполняет метод в другом потоке: вызвал и пошёл дальше. @Scheduled запускает метод по расписанию: ночная сверка, очистка устаревших броней, повтор неотправленных уведомлений.

Обе выглядят как одна строка, и обе прячут пул потоков с настройками по умолчанию. Демо AsyncDemo.java показывает эти настройки на трёх запусках. Стек: JDK 21, Spring Boot 4.1.1, ShedLock 6.6 и H2.

cd examples/integration
./run.sh AsyncDemo async  # @Async: поток, пул, ошибки, MDC
./run.sh AsyncDemo sched  # @Scheduled: один поток планировщика
./run.sh AsyncDemo lock   # ShedLock: два экземпляра с общей базой

@Async отправляет вызов в пул через прокси

@EnableAsync // Без неё @Async молча выполняется в потоке вызывающего.
class App {}

@Service
class Notifier {
    @Async
    public void sendSms(String paymentId) {
        System.out.println("sendSms " + paymentId + " on " + Thread.currentThread().getName()
                + ", requestId=" + MDC.get("requestId"));
    }

    public void notifyAll(String paymentId) { sendSms(paymentId); } // this.sendSms
}

MDC.put("requestId", "req-42"); // Идентификатор запроса для логов.
n.sendSms("p-1");
n.notifyAll("p-2");
caller thread: main
sendSms p-2 on main, requestId=req-42
sendSms p-1 on task-1, requestId=null

Порядок строк неожиданный: p-2 напечатан раньше p-1, хотя вызван позже. p-1 ушёл в пул и выполнился в потоке task-1, а notifyAll вызвал sendSms через this, мимо прокси, и p-2 выполнился сразу в main. Это то же ограничение прокси, что у @Transactional и @Cacheable.

@EnableAsync регистрирует AsyncAnnotationBeanPostProcessor, и бины с @Async получают прокси. Его AsyncExecutionInterceptor заворачивает вызов в задачу и отдаёт её executor-у. Какому именно: указанному в @Async("smsExecutor"), иначе бину AsyncConfigurer, иначе единственному бину TaskExecutor или бину с именем taskExecutor. В Boot это applicationTaskExecutor с потоками task-N.

Метод с @Async возвращает void или CompletableFuture. Любое другое значение вызывающий не получит: прокси вернёт управление раньше, чем метод что-то вычислит, и отдаст null.

Пул Boot: 8 потоков и бесконечная очередь, поэтому max не достигается

Демо отправляет 20 задач по 300 мс и через 100 мс смотрит на пул:

for (int i = 0; i < 20; i++) n.slow(); // Каждая задача спит 300 мс.
sleep(100);
var pool = ctx.getBean("applicationTaskExecutor", ThreadPoolTaskExecutor.class);
pool: core=8, max=2147483647, threads=8, active=8, queued=12

Причина — устройство ThreadPoolExecutor. Новая задача сначала получает поток, пока их меньше core. Дальше она идёт в очередь. Потоки сверх core создаются, только если очередь отказала, то есть заполнена. У Boot очередь без предела, поэтому она никогда не отказывает, и пул навсегда остаётся на восьми потоках.

Если SMS-шлюз завис на минуту, восемь потоков висят вместе с ним, а очередь растёт на каждый платёж. Задачи копятся в heap и пропадут при перезапуске. Настройка для прода задаёт предел очереди и решение на переполнение:

spring:
  task:
    execution:
      pool:
        core-size: 8
        max-size: 32        # Сработает, когда очередь заполнится.
        queue-capacity: 500 # Предел ожидающих задач.
      thread-name-prefix: notify-

Когда заняты и очередь, и все 32 потока, executor отклоняет задачу: по умолчанию TaskRejectedException летит вызывающему, то есть в платёж. Если уведомление можно потерять, его ловят и логируют. Если нельзя, задачу вообще не стоит держать в памяти: её пишут в таблицу или брокер, а @Async оставляют для действительно необязательного.

С виртуальными потоками (spring.threads.virtual.enabled=true) Boot заменяет пул на SimpleAsyncTaskExecutor: новый виртуальный поток на каждую задачу, без очереди. Потоки дешёвые, но внешний сервис от этого не становится быстрее. Ограничение одновременных вызовов SMS-шлюза тогда задают явно, например spring.task.execution.simple.concurrency-limit или семафором.

Разным задачам — разные пулы. Если SMS и PDF делят один executor, зависший SMS-шлюз забирает все восемь потоков, и чеки перестают формироваться. Отдельный бин ThreadPoolTaskExecutor на каждую интеграцию и @Async("smsExecutor") изолируют сбои — это bulkhead.

Исключение, MDC и транзакция остаются в потоке вызывающего

Метод в пуле выполняется после того, как вызывающий уже ушёл дальше. Исключению из void-метода некуда вернуться:

n.sendSms("bad"); // Внутри: throw new IllegalStateException("SMS gateway down").
try {
    n.receipt("bad").get(); // CompletableFuture: ошибка вернётся в get().
} catch (ExecutionException e) {
    System.out.println("receipt failed: " + e.getCause().getMessage());
}
sendSms bad on task-2, requestId=null
ERROR [task-2] .a.i.SimpleAsyncUncaughtExceptionHandler : Unexpected exception occurred invoking async method: public void kb.integration.AsyncDemo$Notifier.sendSms(java.lang.String)
java.lang.IllegalStateException: SMS gateway down
receipt failed: PDF render failed

Для void единственный след — строка в логе от SimpleAsyncUncaughtExceptionHandler. Вызывающий не узнает об ошибке, повтора не будет. Свой AsyncUncaughtExceptionHandler через AsyncConfigurer может хотя бы считать метрику. Если результат важен, метод возвращает CompletableFuture, и вызывающий решает, что делать с ошибкой. Строка лога в выводе сокращена: убраны дата и pid.

Во всех выводах выше requestId=null, хотя вызывающий положил его в MDC. MDC, SecurityContext и контекст транзакции хранятся в ThreadLocal, а у потока пула свои ThreadLocal. Логи асинхронной задачи теряют связь с запросом. Перенести контекст можно через TaskDecorator: он оборачивает задачу в момент отправки, ещё в потоке вызывающего. Boot сам подключает бин TaskDecorator к своему executor-у:

@Bean
TaskDecorator mdcCopy() {
    return task -> {
        Map<String, String> mdc = MDC.getCopyOfContextMap(); // Поток вызывающего.
        return () -> {
            if (mdc != null) MDC.setContextMap(mdc); // Поток пула.
            try { task.run(); } finally { MDC.clear(); } // Не оставить чужой MDC потоку.
        };
    };
}
sendSms p-3 on task-1, requestId=req-42

Для SecurityContext есть готовый DelegatingSecurityContextAsyncTaskExecutor, разобранный в Architecture. Трассировка Micrometer переносит контекст через ContextPropagatingTaskDecorator.

@Async-метод, вызванный внутри @Transactional, видит то, что транзакция только что записала.

Задача выполняется в другом потоке со своим соединением. Транзакция вызывающего может быть ещё не закоммичена, и задача не найдёт платёж или прочитает старое состояние. А если транзакция откатится, SMS «оплачено» уже уйдёт. Отправку привязывают к коммиту: @TransactionalEventListener(phase = AFTER_COMMIT) вместе с @Async, как в Application Events.

@Scheduled по умолчанию выполняет все задачи в одном потоке

@EnableScheduling находит методы с @Scheduled и регистрирует их в TaskScheduler. Варианты расписания: fixedRate — запуск через равные промежутки от начала предыдущего, fixedDelay — пауза после окончания предыдущего, cron — по календарю, с часовым поясом в атрибуте zone.

Планировщик Boot по умолчанию — пул из одного потока scheduling-1. Все задачи приложения стоят к нему в очередь. Демо запускает две задачи: heartbeat каждые 100 мс и отчёт раз в секунду, который работает 600 мс. Затем то же самое с двумя потоками:

@Scheduled(fixedRate = 100) // Каждые 100 мс записывает момент запуска.
public void heartbeat() { heartbeats.add(System.currentTimeMillis() - start); }

@Scheduled(fixedRate = 1000) // Отчёт работает 600 мс.
public void report() { sleep(600); }
pool.size=1: heartbeats=10 at [655, 655, 655, 656, 656, 656, 656, 752, 849, 953]
pool.size=2: heartbeats=13 at [15, 121, 220, 320, 417, 519, 617, 721, 818, 918, 1018, 1119, 1221]

С одним потоком heartbeat первые 655 мс не запускался вовсе: поток держал отчёт. Затем семь пропущенных запусков выполнились подряд за одну миллисекунду — так fixedRate догоняет расписание. Если бы heartbeat продлевал аренду или отправлял сигнал «я жив», за эти 655 мс его бы сочли мёртвым. С двумя потоками он идёт ровно.

Решение — spring.task.scheduling.pool.size по числу независимых задач или отдельный executor для тяжёлых. Одну и ту же задачу Spring не запускает параллельно с самой собой: следующий запуск ждёт окончания предыдущего. Исключение из @Scheduled логируется, и задача продолжит работать по расписанию: одна ошибка не останавливает ночную сверку навсегда.

В кластере задачу запускает каждый экземпляр, если не взять общий замок

Платёжный сервис работает в трёх pod-ах. Ночная сверка с банком помечена @Scheduled, и в 3:00 она стартует трижды: три запроса выписки, три сравнения, три письма бухгалтерии. Планировщик Spring ничего не знает о других экземплярах.

ShedLock добавляет общий замок в базе. Перед запуском задача пытается обновить строку в таблице shedlock: поставить lock_until в будущее, если текущее значение уже в прошлом. Это один атомарный UPDATE, и выигрывает ровно один экземпляр. Остальные пропускают запуск.

@Scheduled(fixedRate = 100)
@SchedulerLock(name = "reconcile", lockAtLeastFor = "PT0.4S") // Держать замок минимум 400 мс.
public void reconcile() { runs.incrementAndGet(); }

// Два «экземпляра» сервиса в одной JVM, общая база H2.
try (var a = start(shared, LockApp.class); var b = start(shared, LockApp.class)) { sleep(1500); }
without lock: A=16, B=16, total=32
with ShedLock: A=1, B=3, total=4

Без замка за полторы секунды задача выполнилась 32 раза: по 16 на каждом экземпляре. С ShedLock — 4 раза на двоих: каждый запуск держит замок 400 мс, и все попытки в это время пропускаются. Какой экземпляр выиграет, не определено: здесь B взял замок трижды, A — один раз.

Два параметра замка решают разные задачи. lockAtMostFor — сколько держать замок, если экземпляр упал посреди задачи и не снял его: после этого срока задачу сможет взять другой. Он должен быть больше самого долгого нормального выполнения, иначе второй экземпляр запустит задачу, пока первый ещё работает. lockAtLeastFor держит замок даже после быстрого окончания задачи, чтобы экземпляр с отстающими часами не запустил её второй раз в ту же секунду. usingDbTime() берёт время из базы, а не с часов pod-ов.

ShedLock — не очередь и не гарантия «ровно один раз». Он не запускает пропущенную задачу, если все экземпляры лежали, и не повторяет упавшую. Для задач с историей, повторами и параметрами берут Quartz с кластерным JDBC-хранилищем, db-scheduler или выносят задачу в Kubernetes CronJob. И в любом случае сама задача должна быть идемпотентной: повторный запуск сверки не должен отправлять второе письмо.

  • @Async работает через прокси: без @EnableAsync и при вызове через this метод выполняется синхронно.
  • Пул Boot — 8 потоков и бесконечная очередь; max-size без queue-capacity не действует.
  • Исключение void-метода уходит только в лог. MDC, SecurityContext и транзакцию в поток пула переносят явно.
  • @Scheduled по умолчанию делит один поток на все задачи; fixedRate догоняет пропущенные запуски пачкой.
  • В кластере @Scheduled запускается на каждом экземпляре; ShedLock даёт общий замок, но не гарантию ровно одного выполнения.

На собеседовании

Как работает @Async и почему метод может выполниться синхронно?

@EnableAsync включает постпроцессор, который оборачивает бины с @Async в прокси. Прокси превращает вызов в задачу и отдаёт её TaskExecutor, а вызывающему сразу возвращает управление. Метод возвращает void или CompletableFuture.

Синхронно он выполнится, если нет @EnableAsync или вызов идёт мимо прокси: через this из того же класса, на private или final методе. В демо вызов через this выполнился в потоке main.

  • Executor выбирается по имени в @Async("..."), затем AsyncConfigurer, затем единственный TaskExecutor или бин taskExecutor; в Boot это applicationTaskExecutor.
  • Метод с другим типом возврата вернёт null: прокси отвечает раньше, чем метод выполнится.
  • Транзакция, MDC и SecurityContext в поток пула не переходят; для MDC и трассировки есть TaskDecorator.
Почему иногда SMS «оплачено» приходит по платежу, которого нет в базе? 
@Transactional
public void pay(Payment p) {
    repository.save(p);
    notifier.sendSms(p.getId()); // @Async: читает платёж из базы и шлёт SMS.
    bank.charge(p);              // Может бросить исключение — транзакция откатится.
}

sendSms выполняется в другом потоке сразу, до коммита. Он может не найти платёж, потому что транзакция ещё не закоммичена, а если charge бросит исключение, транзакция откатится, но SMS уже ушло. Отправку нужно привязать к коммиту: опубликовать событие и обработать его в @TransactionalEventListener(phase = AFTER_COMMIT) с @Async.

Какой пул использует @Async в Spring Boot и что с ним не так?

Boot создаёт ThreadPoolTaskExecutor applicationTaskExecutor: 8 core-потоков, очередь без предела и max-size Integer.MAX_VALUE. Потоки сверх core в ThreadPoolExecutor создаются только при полной очереди, а бесконечная очередь не заполняется, поэтому работают всегда 8 потоков, а лишние задачи копятся в памяти.

Я задаю queue-capacity и max-size, решаю, что делать при отказе, и выделяю отдельный пул для каждой медленной интеграции, чтобы зависший SMS-шлюз не остановил чеки.

  • Задачи в очереди теряются при перезапуске; обязательную работу пишут в базу или брокер, а не в пул.
  • С виртуальными потоками Boot использует SimpleAsyncTaskExecutor без очереди; ограничение параллельности задают через concurrency-limit.
  • При отказе по умолчанию летит TaskRejectedException прямо в вызывающий код.

Что происходит с исключением в @Async-методе?

Если метод возвращает CompletableFuture, исключение попадает в него, и вызывающий получит его в get или join. Если метод void, вернуть исключение некому: его получает AsyncUncaughtExceptionHandler, который по умолчанию только пишет в лог.

Поэтому важные асинхронные операции возвращают CompletableFuture или сами обрабатывают ошибку: повтор, запись в таблицу недоставленных, метрика.

  • Свой обработчик для void-методов задают через AsyncConfigurer.getAsyncUncaughtExceptionHandler.
  • Повтор через @Retryable поверх @Async работает только при правильном порядке прокси; надёжнее повторять внутри задачи.

Как не запустить @Scheduled-задачу на всех экземплярах сервиса?

Планировщик Spring не знает о других экземплярах, поэтому задача стартует на каждом. Обычное решение — ShedLock: перед запуском задача атомарно берёт замок в общей таблице, и выполняет её только тот экземпляр, который его получил. В демо без замка задача выполнилась 32 раза на двух экземплярах, с замком — 4.

Я задаю lockAtMostFor больше самого долгого выполнения, чтобы упавший экземпляр не держал замок вечно, и делаю саму задачу идемпотентной.

  • ShedLock не повторяет пропущенные и упавшие запуски; для истории и повторов берут Quartz в кластерном режиме или db-scheduler.
  • usingDbTime и lockAtLeastFor защищают от расхождения часов между pod-ами.
  • Альтернатива — Kubernetes CronJob, который запускает отдельный процесс, а не задачу внутри каждого pod-а.
  • Один поток планировщика по умолчанию: долгая задача задерживает остальные, поэтому pool.size увеличивают.
