Spring Security: Authentication

Фильтр входа только достаёт из запроса то, что прислал клиент: логин и пароль, API-ключ, токен. Он заворачивает это в неаутентифицированный объект Authentication и отдаёт AuthenticationManager. Менеджер находит провайдер, который умеет проверять такой тип, и получает обратно аутентифицированный Authentication с правами. Пароль при этом сравнивается с медленным солёным хешем. Результат кладётся в SecurityContext и, если есть сессия, переживает запрос.

Платёжный сервис впускает людей по паролю, а партнёров по ключу

У платёжного сервиса два вида клиентов. Сотрудники поддержки входят в админку логином и паролем. Партнёры-магазины вызывают API с ключом X-Api-Key. Через полгода добавится вход по корпоративному SSO. Если каждый способ проверять прямо в своём фильтре, получатся три копии одной логики: найти пользователя, проверить секрет, выдать права, записать результат.

Spring Security разделяет эту работу. Фильтр отвечает за транспорт: где в запросе лежат данные. AuthenticationManager отвечает за проверку. Между ними путешествует один тип — Authentication. До проверки в нём лежат присланные данные, после — пользователь, его права и флаг isAuthenticated() == true.

Тема разбирает, что происходит внутри менеджера, как хранить пароли и как результат входа доживает до следующего запроса. Путь запроса через фильтры разобран в Architecture, права и роли — в Authorization, токены JWT и OAuth2 — в OAuth2 & JWT.

Демо AuthnDemo.java состоит из трёх частей: пароли, менеджер без веб-сервера и настоящий вход через форму. Стек: JDK 21, Spring Boot 4.1.1, Spring Security 7.1.

cd examples/security
./run.sh AuthnDemo

ProviderManager отдаёт токен первому провайдеру, который понимает его тип

Главная реализация менеджера — ProviderManager. В нём список AuthenticationProvider. На каждый токен он спрашивает провайдеры по очереди: supports(Class) — умеешь проверять такой тип? Первый согласившийся вызывает authenticate. Если провайдер вернул результат, перебор заканчивается. Если бросил исключение, менеджер запоминает его и пробует следующий подходящий.

Поэтому новый способ входа — это новый тип токена и новый провайдер, а не правка существующих. Для партнёров достаточно своего токена и провайдера, который знает только про него:

class ApiKeyProvider implements AuthenticationProvider {
    public Authentication authenticate(Authentication a) {
        if (!"pk_live_42".equals(a.getCredentials())) throw new BadCredentialsException("bad key");
        // Фабрика authenticated(...) даёт токен с isAuthenticated() == true.
        return UsernamePasswordAuthenticationToken.authenticated("partner-42", null,
                AuthorityUtils.createAuthorityList("ROLE_PARTNER"));
    }

    public boolean supports(Class<?> type) { // Остальные токены не трогаем.
        return ApiKeyToken.class.isAssignableFrom(type);
    }
}

var manager = new ProviderManager(daoProvider, new ApiKeyProvider()); // Порядок важен.

Менеджер из демо собран вручную из двух провайдеров. Четыре попытки входа:

tryAuth(manager, UsernamePasswordAuthenticationToken.unauthenticated("alice", "secret"));
tryAuth(manager, UsernamePasswordAuthenticationToken.unauthenticated("alice", "wrong"));
tryAuth(manager, UsernamePasswordAuthenticationToken.unauthenticated("nobody", "secret"));
tryAuth(manager, new ApiKeyToken("pk_live_42"));
// tryAuth печатает имя, права и credentials результата или класс исключения.
alice/secret   -> OK alice [ROLE_USER, FactorGrantedAuthority [authority=FACTOR_PASSWORD, issuedAt=2026-10-02T09:30:26.063042Z]] credentials=null
alice/wrong    -> BadCredentialsException: Bad credentials
nobody/secret  -> BadCredentialsException: Bad credentials
api key        -> OK partner-42 [ROLE_PARTNER] credentials=null

В выводе три неочевидные вещи. Первая: credentials=null. После успешного входа ProviderManager вызывает eraseCredentials, чтобы пароль не лежал в SecurityContext, сессии и логах. Вторая: несуществующий пользователь получает тот же BadCredentialsException, что и неверный пароль. Об этом следующий шаг.

Третья — право FACTOR_PASSWORD рядом с ролью. Это новинка Spring Security 7: каждый пройденный способ входа добавляет право-фактор с моментом выдачи. На нём строится многофакторная аутентификация: правило может требовать, чтобы у пользователя были и пароль, и одноразовый код, и чтобы фактор был свежим. Код, который сравнивает список прав целиком, после обновления до Security 7 может неожиданно сломаться.

У ProviderManager может быть родительский менеджер. Если ни один провайдер не согласился проверить токен, запрос уходит родителю. Так в Boot несколько цепочек делят общий набор пользователей, а у отдельной цепочки бывают свои провайдеры. Если не справился никто, получится ProviderNotFoundException.

Ошибка входа не говорит, существует ли логин, и занимает столько же времени

Логин и пароль проверяет DaoAuthenticationProvider. Сам он не знает, где лежат пользователи. Он просит UserDetailsService.loadUserByUsername найти запись, затем сравнивает пароль через PasswordEncoder, затем проверяет флаги учётной записи: заблокирована, выключена, истёк ли срок. Источник пользователей — твоя реализация UserDetailsService: таблица, LDAP, другой сервис.

Если пользователя нет, UserDetailsService бросает UsernameNotFoundException. Провайдер по умолчанию превращает его в BadCredentialsException (флаг hideUserNotFoundExceptions). Иначе форма входа выдавала бы по разным сообщениям, какие логины существуют, и атакующий собирал бы список клиентов перебором.

Сообщения мало: различие видно и по времени. Проверка bcrypt длится десятки миллисекунд, а «пользователя нет» без хеширования отвечала бы мгновенно. Поэтому для несуществующего пользователя провайдер всё равно сверяет пароль с заранее подготовленным фиктивным хешем. Демо замеряет обе ошибки:

// Средняя длительность пяти попыток; пароль "x" неверный в обоих случаях.
timeMs(() -> tryAuth(manager, unauthenticated("alice", "x")), 5);  // логин есть
timeMs(() -> tryAuth(manager, unauthenticated("nobody", "x")), 5); // логина нет
time wrong password: 50 ms
time unknown user:   50 ms

Числа измерены на Apple M5 Pro; на другой машине они будут другими, но останутся равными между собой. Своя реализация входа, которая делает if (user == null) return error до проверки пароля, ломает обе защиты сразу.

Если UserDetailsService не нашёл пользователя, клиент получит UsernameNotFoundException и сообщение «пользователь не найден».

DaoAuthenticationProvider по умолчанию прячет это исключение за BadCredentialsException и тратит на ответ столько же времени, сколько на неверный пароль. Отличить «нет логина» от «неверный пароль» снаружи нельзя, и это сделано специально.

Блокировки после неудачных попыток Spring Security сам не ведёт. Флаг isAccountNonLocked он проверяет, а считать ошибки и ставить флаг — задача приложения: слушатель AuthenticationFailureBadCredentialsEvent увеличивает счётчик, а ограничение частоты на входе защищает от массового перебора.

Пароль хранят медленным хешем с солью и пометкой алгоритма

База пользователей однажды утечёт: через бэкап, логи или SQL-инъекцию. Хранение должно сделать утёкшие записи бесполезными. Обычный SHA-256 для этого не подходит: видеокарта считает миллиарды таких хешей в секунду, и популярные пароли находятся за минуты. Нужна функция, которая специально медленная и с солью: bcrypt, scrypt, Argon2 или PBKDF2.

Boot по умолчанию создаёт DelegatingPasswordEncoder. Он кодирует новые пароли через bcrypt и ставит перед хешем префикс алгоритма. При проверке он читает префикс и отдаёт сравнение нужному кодировщику:

PasswordEncoder enc = PasswordEncoderFactories.createDelegatingPasswordEncoder();
String h1 = enc.encode("secret"), h2 = enc.encode("secret");
System.out.println(h1);
System.out.println(h2); // Тот же пароль, другая соль — другой хеш.
System.out.println("matches=" + enc.matches("secret", h1)
        + ", noop matches=" + enc.matches("secret", "{noop}secret"));
System.out.println("upgrade {noop}=" + enc.upgradeEncoding("{noop}secret")
        + ", upgrade bcrypt=" + enc.upgradeEncoding(h1));
{bcrypt}$2a$10$j1ceA9d.Npfx5zhK.TW5POEFk.JVXrFTcNgEciOLdCJ4T9wI4k6tW
{bcrypt}$2a$10$qpfFQ8NNSJrmFpn3tgQVMebpbvSGBZkQpnWbEIsGc3hjqwvxtEHTC
matches=true, noop matches=true
upgrade {noop}=true, upgrade bcrypt=false

Строку хеша стоит уметь читать. {bcrypt} — префикс делегирующего кодировщика. $2a$ — версия bcrypt. 10 — стоимость: 210 раундов. Следующие 22 символа — соль, остальное — сам хеш. Соль хранится внутри строки, поэтому отдельная колонка для неё не нужна, а одинаковые пароли двух клиентов дают разные записи.

Префикс решает задачу миграции. Старые записи {noop} или {sha256} продолжают проверяться. upgradeEncoding говорит, что запись устарела. Если UserDetailsService реализует ещё и UserDetailsPasswordService, провайдер сам перекодирует пароль в bcrypt при ближайшем успешном входе: только в этот момент приложение знает пароль в открытом виде.

Стоимость выбирают по времени одной проверки

Каждая единица стоимости удваивает работу и для атакующего, и для твоего сервера. Демо меряет одну проверку пароля на трёх значениях:

bcrypt cost 10: 52 ms per check
bcrypt cost 12: 203 ms per check
bcrypt cost 14: 811 ms per check

Миллисекунды меняются от запуска к запуску и от машины к машине, а соотношение остаётся: плюс два к стоимости — вчетверо дольше.

Ориентир — сотни миллисекунд на вход, на железе прода. При стоимости 14 сотня одновременных входов займёт все ядра на секунды. Поэтому для API, где клиент присылает пароль в каждом запросе через Basic, bcrypt становится узким местом: такие клиенты получают токен один раз и дальше ходят с ним.

bcrypt учитывает только первые 72 байта пароля. В Spring Security 7.1 encode отклоняет более длинный пароль: IllegalArgumentException: password cannot be more than 72 bytes. А matches по-прежнему сравнивает только первые 72 байта: проверка демо показала true для пароля из 72 байт с тремя лишними символами в конце. Длину пароля ограничивай при регистрации и помни про кириллицу: один символ — два байта UTF-8, предел наступает уже на 37 символах.

После входа сессия получает новый id, и дальше пользователь живёт в ней

Проверка пароля дорогая, поэтому браузер не присылает его на каждом запросе. После входа формой Spring Security сохраняет SecurityContext в HTTP-сессии через HttpSessionSecurityContextRepository, а браузер хранит только cookie JSESSIONID. На следующем запросе SecurityContextHolderFilter достаёт контекст из сессии по этой cookie.

В момент входа есть ловушка. Сессия часто создаётся до логина: например, для CSRF-токена формы. Если атакующий заранее подсунет жертве свой id сессии, а сервер после входа оставит этот id, атакующий окажется залогинен как жертва. Это session fixation. Защита — сменить id сессии в момент успешного входа.

Третья часть демо проходит этот путь настоящими HTTP-запросами с хранилищем cookie. Программа читает CSRF-токен со страницы входа, отправляет форму и сравнивает id сессии до и после. Идентификаторы обрезаны до восьми символов:

POST /login -> 302 Location: /
session before login: 958B9BF0…
session after login:  D6110E1D… (changed)
GET /me -> alice [ROLE_USER, FactorGrantedAuthority [authority=FACTOR_PASSWORD, issuedAt=2026-10-02T09:30:27.577Z]]

Сессия даёт удобство и ограничения. Она хранится в памяти конкретного экземпляра, поэтому при нескольких pod-ах нужен общий стор вроде Spring Session с Redis или привязка клиента к pod-у. sessionManagement().maximumSessions(1) ограничивает одновременные входы одного пользователя. Выход через /logout инвалидирует сессию и очищает контекст.

API для мобильных и партнёрских клиентов обычно работает без сессии: SessionCreationPolicy.STATELESS. Клиент присылает доказательство в каждом запросе. Пароль для этого слишком дорог и опасен, поэтому присылают ключ или токен, который проверяется быстро. Токены с подписью разобраны в OAuth2 & JWT.

Свой способ входа добавляют провайдером, а не обходом менеджера

Самая частая ошибка при своём входе — фильтр, который сам проверяет ключ и сам кладёт пользователя в SecurityContextHolder. Такой код пропускает события аутентификации, стирание секретов, родительский менеджер и общую обработку ошибок. Правильная форма: фильтр извлекает данные в свой тип токена и вызывает AuthenticationManager, а проверку делает провайдер. Готовый каркас для этого — AuthenticationFilter с AuthenticationConverter.

Если свой фильтр всё-таки сохраняет контекст сам, с Spring Security 6 он обязан вызвать SecurityContextRepository.saveContext. Иначе вход работает ровно один запрос: на следующем пользователь снова анонимный. Раньше это делал общий фильтр автоматически, и старые примеры из интернета эту строку не содержат.

Многофакторный вход в Security 7 строится на тех же провайдерах и правах-факторах из второго шага. Пароль даёт FACTOR_PASSWORD, одноразовый код — свой фактор, а правило доступа требует нужный набор. Внешние системы входа — Keycloak, Google, корпоративный SSO — обычно подключают через OAuth2 и OpenID Connect, а не через свою реализацию UserDetailsService.

Механизм аутентификации отвечает только на вопрос «кто ты». Что этому пользователю можно — следующий шаг, его делает AuthorizationFilter и method security. Смешивать их опасно: проверка прав внутри провайдера даст отказ в 401 вместо 403 и спрячет причину.

  • Фильтр достаёт данные в неаутентифицированный Authentication, AuthenticationManager возвращает аутентифицированный с правами.
  • ProviderManager выбирает провайдер по типу токена через supports и стирает credentials после успеха.
  • Неизвестный логин и неверный пароль дают одинаковое BadCredentialsException за одинаковое время.
  • Пароли хранят bcrypt или Argon2 с солью; префикс DelegatingPasswordEncoder позволяет мигрировать без сброса паролей.
  • После входа формой id сессии меняется против session fixation; stateless API присылает токен в каждом запросе.

На собеседовании

Как устроена аутентификация в Spring Security?

Фильтр, например UsernamePasswordAuthenticationFilter или BasicAuthenticationFilter, достаёт из запроса логин и пароль и создаёт неаутентифицированный токен. Он передаёт его в AuthenticationManager. Основная реализация, ProviderManager, перебирает AuthenticationProvider и отдаёт токен тому, кто поддерживает его тип.

Для логина и пароля это DaoAuthenticationProvider: он загружает пользователя через UserDetailsService, сверяет пароль через PasswordEncoder и проверяет статус учётной записи. Результат — аутентифицированный Authentication с правами, который фильтр кладёт в SecurityContext.

  • Свой способ входа — свой тип токена и свой провайдер; фильтр не должен сам проверять секрет и класть пользователя в контекст.
  • ProviderManager стирает credentials после успеха и может делегировать родительскому менеджеру, если ни один провайдер не подошёл.
  • С Security 6 сохранение контекста в репозиторий явное: свой фильтр входа вызывает saveContext, иначе вход живёт один запрос.
  • В Security 7 успешный вход добавляет права-факторы вроде FACTOR_PASSWORD, на которых строится MFA.

Как правильно хранить пароли и что делает DelegatingPasswordEncoder?

Пароли хранят медленной функцией с солью: bcrypt, Argon2, scrypt или PBKDF2. Быстрый SHA-256 не подходит: на видеокарте перебор идёт миллиардами в секунду. Соль делает хеши одинаковых паролей разными, и заранее посчитанные таблицы не помогают.

DelegatingPasswordEncoder пишет перед хешем префикс алгоритма, например {bcrypt}. При проверке он выбирает кодировщик по префиксу. Это позволяет менять алгоритм постепенно: старые записи проверяются старым способом и перекодируются при следующем входе.

  • Стоимость bcrypt подбирают так, чтобы одна проверка шла сотни миллисекунд на прод-железе; каждая единица удваивает время.
  • Автоматическая перекодировка работает, если UserDetailsService реализует UserDetailsPasswordService; пароль в открытом виде есть только в момент входа.
  • bcrypt учитывает 72 байта: encode отклоняет более длинный пароль, а matches сравнивает только начало, поэтому длину ограничивают при регистрации.
Что не так с этим хранением пароля? 
String hash = HexFormat.of().formatHex(
        MessageDigest.getInstance("SHA-256").digest((login + password).getBytes()));
userRepository.save(new UserRow(login, hash));

SHA-256 быстрый: видеокарта проверяет миллиарды вариантов в секунду, и словарные пароли из утёкшей базы находятся сразу. Логин в роли соли не случайный, и одинаковые пароли у одного логина в разных системах дают одинаковый хеш. Нет префикса алгоритма, поэтому миграция потребует сброса паролей. Исправление: PasswordEncoder из Spring Security, encode при регистрации и matches при входе.

Что такое session fixation и как Spring Security от неё защищает?

Атакующий заранее получает id сессии и подсовывает его жертве. Если после входа сервер оставит тот же id, атакующий с этим id окажется залогинен как жертва. Spring Security по умолчанию меняет id сессии в момент успешной аутентификации через changeSessionId: данные сессии сохраняются, старый id перестаёт работать.

Это особенно важно, потому что сессия часто создаётся до входа, например чтобы хранить CSRF-токен формы.

  • Стратегии: changeSessionId по умолчанию, newSession с копированием атрибутов, migrateSession, none.
  • Сессия живёт в памяти экземпляра; при нескольких pod-ах нужен Spring Session с общим стором или привязка клиента.
  • maximumSessions ограничивает одновременные входы и требует слушателя HttpSessionEventPublisher, чтобы узнавать об истёкших сессиях.

Почему для несуществующего пользователя приходит BadCredentialsException?

Чтобы снаружи нельзя было узнать, какие логины существуют. DaoAuthenticationProvider по умолчанию прячет UsernameNotFoundException за BadCredentialsException, и неверный пароль и неизвестный логин выглядят одинаково.

Кроме сообщения выравнивается время: для неизвестного пользователя провайдер всё равно сверяет пароль с фиктивным хешем, иначе быстрый ответ выдал бы отсутствие логина.

  • Своя логика «если пользователя нет — сразу ошибка» до проверки пароля ломает защиту по времени.
  • Счётчик неудачных попыток и блокировку ведёт приложение, например по событию AuthenticationFailureBadCredentialsEvent; Security только проверяет флаг locked.
  • Форма регистрации и восстановление пароля тоже не должны раскрывать существование адреса.
