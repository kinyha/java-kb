Spring Security: Authorization

Авторизация решает, можно ли уже известному пользователю сделать то, о чём он просит. В Spring это происходит на двух уровнях. Правила URL в цепочке фильтров грубо отсекают целые разделы: админка только для админов. Правила на методах сервисов смотрят на аргументы и результат: клиент читает только свой счёт. Оба уровня спрашивают одно и то же — права текущего пользователя из SecurityContext — и оба легко обойти незаметно: неправильным порядком правил или вызовом метода изнутри того же класса.

Залогиненный клиент читает чужой счёт, и аутентификация тут не поможет

Платёжный API отдаёт баланс по адресу /api/accounts/{id}/balance. Все запросы требуют логина. Клиент alice заходит под собой и меняет в адресе свой id на bob. Если сервер проверяет только «пользователь залогинен», alice видит чужие деньги. Это самая частая уязвимость веб-API, у неё даже есть имя: IDOR, небезопасная прямая ссылка на объект.

Аутентификация ответила на вопрос «кто это» — это alice. Вопрос «можно ли alice смотреть счёт bob» — другой. Его задают правила авторизации, и у них два уровня:

  • правила URL — в цепочке фильтров, до контроллера: кто вообще может зайти в /api/payments/admin/**;
  • правила методов — на бинах сервисов: может ли этот пользователь вызвать balance("bob") и получить этот платёж.

Первый уровень дешёвый и не знает о данных. Второй знает об аргументах и результате, поэтому только он закрывает IDOR. Демо AuthzDemo.java показывает ошибки обоих уровней на четырёх пользователях: alice с ролью USER, bob с ролью SUPPORT, ops с правом ADMIN без префикса и admin с ролью ADMIN.

cd examples/security
./run.sh AuthzDemo        # правила URL в неправильном порядке
./run.sh AuthzDemo fixed  # узкое правило первым

Правила URL проверяются сверху вниз до первого совпадения

Последний фильтр цепочки, AuthorizationFilter, передаёт запрос в AuthorizationManager. Для правил URL это RequestMatcherDelegatingAuthorizationManager: список пар «шаблон запроса → правило» в том порядке, в каком они написаны в authorizeHttpRequests. Менеджер берёт первую пару, чей шаблон подошёл, и применяет её правило. Остальные не смотрит.

Команда сначала защитила все платежи, а через месяц добавила отчёт для админов строкой ниже:

http.authorizeHttpRequests(a -> a
    .requestMatchers("/api/payments/**").authenticated()        // Ловит и admin/report.
    .requestMatchers("/api/payments/admin/**").hasRole("ADMIN") // До неё не доходит.
    .anyRequest().authenticated());
report as alice      -> 200 report
report as ops        -> 200 report
report as admin      -> 200 report

Исправление — переставить строки: от узких шаблонов к широким, anyRequest() последним. Второй запуск демо:

report as alice      -> 403
report as ops        -> 403
report as admin      -> 200 report

Spring Security ловит только самый грубый случай: anyRequest() не на последнем месте роняет старт. Перекрытие двух обычных шаблонов он не замечает. Поэтому для каждого закрытого раздела нужен тест «пользователь без роли получает 403», а не только «админ получает 200».

Последнее правило стоит выбирать осознанно. anyRequest().authenticated() открывает любому залогиненному каждый новый эндпоинт, про который забыли написать правило. anyRequest().denyAll() закрывает их по умолчанию, и забытое правило проявится сразу как 403 в тесте, а не как утечка в проде.

Роль — это authority с префиксом ROLE_

Права пользователя — список строк GrantedAuthority. Отдельного понятия «роль» в ядре нет. Роль — соглашение: authority, которое начинается с ROLE_. roles("ADMIN") при создании пользователя сохраняет ROLE_ADMIN, а hasRole("ADMIN") при проверке ищет ROLE_ADMIN. hasAuthority("ADMIN") ищет строку как есть.

В демо у ops право записано как authorities("ADMIN"), без префикса. Даже с правильным порядком правил он получил 403 на отчёт: hasRole("ADMIN") искал ROLE_ADMIN и не нашёл. Такая ошибка возникает при загрузке прав из базы или LDAP, где колонка хранит ADMIN, а код проверяет роль.

Создание пользователяХранитсяhasRole("ADMIN")hasAuthority("ADMIN")
roles("ADMIN")ROLE_ADMINданет
authorities("ADMIN")ADMINнетда
JWT со scope payments.readSCOPE_payments.readнетнет; нужно hasAuthority("SCOPE_payments.read")

Принято так: роль описывает, кто человек (ROLE_SUPPORT), а authority без префикса — конкретное действие (payments:refund). Проверять действия гибче: роль поддержки сегодня может делать возвраты, завтра — нет, и это меняется в данных, а не в коде. Иерархию ролей, где ADMIN включает SUPPORT, задаёт бин RoleHierarchy; без него hasRole("SUPPORT") откажет админу.

Method security проверяет правило на прокси, до вызова метода

Правило «клиент видит только свой счёт» зависит от аргумента. Шаблон URL его не выразит красиво, а сервис вызывают ещё и из очередей и планировщиков, где URL нет. Поэтому правило ставят на метод сервиса:

@Configuration
@EnableMethodSecurity // Без неё аннотации ниже молча игнорируются.
class Security { /* ... */ }

@Service
class AccountService {
    // SpEL: роль поддержки или свой счёт; #id — параметр метода.
    @PreAuthorize("hasRole('SUPPORT') or #id == authentication.name")
    public String balance(String id) { return id + ": 1200"; }
}
alice balance alice  -> 200 alice: 1200
alice balance bob    -> 403
bob   balance alice  -> 200 alice: 1200

Механизм — тот же Spring AOP, что у @Transactional. @EnableMethodSecurity регистрирует advisor, и контейнер оборачивает AccountService прокси. Контроллер получает ссылку на прокси. При вызове прокси отдаёт метод и аргументы AuthorizationManagerBeforeMethodInterceptor, тот вычисляет выражение и либо вызывает настоящий объект, либо бросает AuthorizationDeniedException. Это наследник AccessDeniedException, поэтому ExceptionTranslationFilter превращает его в 403.

Выражение #id ссылается на имя параметра. Оно доступно, если класс скомпилирован с флагом -parameters: Spring Boot включает его в своей Maven- и Gradle-конфигурации, демо — в run.sh. Без флага имени параметра в байткоде нет, и выражение не находит переменную. Для надёжности параметр можно назвать явно аннотацией @P("id").

@PostAuthorize проверяет результат, а вызов через this обходит любую аннотацию

Иногда владельца нельзя узнать из аргументов: платёж ищут по id, а владелец записан в самом платеже. Тогда проверяют результат. @PostAuthorize выполняет метод, кладёт результат в returnObject и только потом вычисляет выражение:

@PostAuthorize("returnObject.owner() == authentication.name")
public Payment payment(String id) { // Выполнится в любом случае.
    return new Payment(id, id.equals("p-1") ? "alice" : "bob", 500);
}
alice payment p-1    -> 200 Payment[id=p-1, owner=alice, amount=500]
alice payment p-2    -> 403

Платёж p-2 принадлежит bob, и alice получила 403. Но метод уже выполнился: запрос к базе прошёл, и если бы метод что-то менял или писал в аудит «платёж выдан», это бы произошло. @PostAuthorize годится только для чтения без побочных эффектов. Для списков есть @PostFilter, но он загружает все записи и отбрасывает чужие в памяти. На тысяче платежей правильнее фильтровать в запросе: WHERE owner = :currentUser.

Теперь утечка из последнего шага схемы. Демо вызывает summary, который внутри обращается к balance:

// Аннотации нет: прокси пропускает вызов к настоящему объекту.
public String summary(String id) {
    return "summary of " + balance(id); // this.balance — мимо прокси и правила.
}
alice summary bob    -> 200 summary of bob: 1200

Это то же ограничение прокси, что и у @Transactional, разобранное в AOP & Proxies. Правило висит на прокси, а вызов изнутри объекта идёт по ссылке this на настоящий объект. Так же правило не сработает на private методе и на final методе класса с CGLIB-прокси. Защиты две: ставить правило на каждый публичный метод, который отдаёт защищённые данные, или выносить проверяемую операцию в отдельный бин, чтобы вызов шёл через его прокси.

@PreAuthorize на методе сервиса защищает данные, которые этот метод возвращает.

Аннотация защищает вызов через прокси. Другой метод того же класса может прочитать те же данные через this без проверки. Защищай точку входа, через которую данные уходят наружу, и проверяй её тестом с чужим пользователем.

Сложное правило выносят в бин, а доступ к спискам решают в запросе

Выражение вроде hasRole('SUPPORT') or #id == authentication.name терпимо, но правило «поддержка видит счета только своего региона, а менеджер — счета своих магазинов» в SpEL превращается в строку, которую никто не тестирует. Такое правило выносят в бин и вызывают из выражения: @PreAuthorize("@accountAccess.canRead(#id, authentication)"). Логика становится обычным Java-кодом с юнит-тестами.

Можно собрать свою аннотацию: @PreAuthorize("hasRole('SUPPORT')") на аннотации @SupportOnly работает как мета-аннотация. С Security 6.3 у неё бывают параметры через шаблоны выражений. Это убирает повторение строк SpEL по всему коду.

Проверка на методе работает с одним объектом за раз. Для экранов со списками и поиском правило доступа становится частью запроса к базе: фильтр по владельцу, региону, магазину. В JPA для этого используют параметр текущего пользователя в запросе репозитория; Spring Data умеет подставлять ?#{authentication.name} в @Query с модулем security-data. Полные ACL на каждый объект Spring Security тоже поддерживает, но они тяжёлые и нужны редко.

Правила проверяют тестами с разными пользователями. @WithMockUser(roles = "USER") подставляет пользователя без логина, и для каждого закрытого действия пишут хотя бы один тест «чужой получает 403». Тестирование разобрано в Testing.

  • Правила URL проверяются по порядку до первого совпадения: узкие шаблоны пиши выше широких, anyRequest последним.
  • Роль — authority с префиксом ROLE_. hasRole добавляет префикс сам, hasAuthority сравнивает строку как есть.
  • @PreAuthorize работает на прокси и видит аргументы; без @EnableMethodSecurity аннотации молча игнорируются.
  • @PostAuthorize проверяет результат уже выполненного метода — только для чтения без побочных эффектов.
  • Вызов через this, private и final методы обходят правило. Доступ к спискам фильтруй в запросе к базе.

На собеседовании

Чем hasRole отличается от hasAuthority?

Права пользователя — это строки GrantedAuthority. Роль — просто authority с префиксом ROLE_. hasRole("ADMIN") ищет строку ROLE_ADMIN, а hasAuthority("ADMIN") ищет ADMIN без изменений. Метод roles("ADMIN") при создании пользователя сам добавляет префикс.

Ошибка бывает, когда права загружают из базы как ADMIN, а проверяют через hasRole: пользователь получает 403 при правильной роли. Я различаю их по смыслу: роль описывает, кто человек, authority вроде payments:refund — конкретное действие.

  • JWT Resource Server превращает scope в authority с префиксом SCOPE_, их проверяют через hasAuthority.
  • Иерархию ролей задаёт бин RoleHierarchy; без неё админ не получает права поддержки автоматически.
  • Префикс меняется бином GrantedAuthorityDefaults, но лучше этого не делать: ломаются ожидания библиотек и коллег.

Как работает @PreAuthorize и когда он не срабатывает?

@EnableMethodSecurity включает advisor, и Spring оборачивает бины с аннотациями в прокси. При вызове прокси вычисляет SpEL-выражение с текущим Authentication и аргументами метода. Если оно ложно, бросается AuthorizationDeniedException, и клиент получает 403, а метод не выполняется.

Не срабатывает там, где нет прокси: при вызове метода изнутри того же класса через this, на private методах, на final методах при CGLIB, на объектах, созданных через new, и если забыли @EnableMethodSecurity.

  • Ссылки на параметры вроде #id требуют компиляции с -parameters или аннотации @P.
  • @PostAuthorize выполняет метод до проверки, поэтому подходит только для чтения без побочных эффектов; @PostFilter фильтрует в памяти.
  • Сложное правило выносят в бин и вызывают как @bean.method(...) в выражении, чтобы тестировать его обычным кодом.
  • Старая @EnableGlobalMethodSecurity заменена на @EnableMethodSecurity, где prePostEnabled включён по умолчанию.
Найди обход проверки в сервисе возвратов 
@Service
class RefundService {
    @PreAuthorize("hasAuthority('payments:refund')")
    public void refund(String paymentId) { /* деньги уходят клиенту */ }

    public void refundAll(List<String> ids) {
        ids.forEach(this::refund); // Вызывается из контроллера для пакета.
    }
}

refundAll не защищён, а refund внутри него вызывается через this, мимо прокси. Любой пользователь, которому доступен эндпоинт пакетного возврата, вернёт деньги без права payments:refund. Исправление: та же аннотация на refundAll или вызов refund через другой бин.

В каком порядке применяются правила authorizeHttpRequests?

Сверху вниз до первого совпадения шаблона. Если широкое правило /api/payments/** стоит выше узкого /api/payments/admin/**, узкое никогда не применится, и админский раздел откроется любому залогиненному. Поэтому узкие шаблоны пишу первыми, anyRequest — последним.

Spring Security проверяет только то, что anyRequest стоит в конце. Перекрытие обычных шаблонов он не видит, поэтому на каждый закрытый раздел нужен тест с пользователем без роли.

  • anyRequest().denyAll() вместо authenticated() закрывает новые эндпоинты по умолчанию, пока для них не написали правило.
  • securityMatcher выбирает цепочку, а requestMatchers внутри authorizeHttpRequests выбирают правило внутри цепочки; это разные уровни.
  • Правила URL и method security складываются: запрос должен пройти оба.

Как не дать пользователю прочитать чужие данные по id в URL?

Правила URL тут не помогут: они знают путь, но не владельца объекта. Проверяю на уровне сервиса. Если владелец виден из аргумента, ставлю @PreAuthorize с выражением вроде #id == authentication.name. Если только из результата — @PostAuthorize с returnObject.owner, для операций чтения.

Для списков и поиска фильтрую в самом запросе: WHERE owner = текущий пользователь. Так чужие записи не загружаются вовсе.

  • Последовательные id облегчают перебор; UUID снижают риск, но не заменяют проверку.
  • Отказ можно отдавать как 404 вместо 403, чтобы не подтверждать существование чужого объекта.
  • Проверка должна стоять на каждой точке выхода данных: экспорт, отчёт, пакетная операция, а не только на основном методе.
