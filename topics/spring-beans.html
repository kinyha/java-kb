Spring: Configuration & Beans

Конфигурация сначала наполняет реестр определений. Scan обнаруживает классы, @Bean задаёт factory methods, @Import подключает модули, условия выбирают состав. Full Configuration перехватывает прямые Bean-вызовы; lite оставляет их обычными Java-вызовами. Явные зависимости в параметрах делают результат понятным в обоих режимах.

Аннотация станет определением только после обнаружения

В проект добавили BankGateway с @Component, но приложение пишет «нет bean такого типа». Аннотация на месте, класс компилируется. Не хватает шага между исходным кодом и графом объектов: этот класс должен попасть в область сканирования или быть зарегистрирован явно. Контейнер не ищет все классы во всех JAR без границ.

@ComponentScan задаёт пакеты и фильтры. Если пакеты не указаны, отправная точка — пакет класса с этой аннотацией. В Boot default scan следует расположению @SpringBootApplication, поэтому главный класс в корневом пакете приложения имеет практический смысл. Класс в соседнем дереве пакетов автоматически не попадёт в контекст.

Сканер читает metadata class-файлов, в стандартном пути через ASM, и регистрирует BeanDefinition подходящих независимых классов. Для этого не требуется создавать каждый компонент или выполнять его конструктор. Регистрация объясняет, почему сначала можно проверить кандидатов и условия, а уже позже собирать экземпляры.

@Service, @Repository и @Controller — специализации @Component; они выражают роль, а не другой DI-контейнер. @Service сам по себе не начинает транзакцию. @Repository служит маркером для перевода persistence exceptions при подключённой инфраструктуре exception translation. Собственная stereotype-аннотация может использовать @Component как meta-аннотацию.

Для диагностики сначала проверь границу scan и import, затем condition/profile, и только после этого разрешение зависимости. Сканирование всего com часто затягивает чужие конфигурации и тестовые реализации. Для библиотечного модуля явный import конфигурации обычно делает состав приложения понятнее.

Метод @Bean описывает объект, которым дальше управляет Spring

Некоторые классы нельзя или не хочется аннотировать: клиент SDK банка, пул соединений, Clock. Метод @Bean позволяет создать и настроить такой объект обычным Java-кодом, а результат отдать контейнеру. Это полноценный managed bean: к нему применяются scope, callbacks и подходящие BeanPostProcessor.

По умолчанию имя bean совпадает с именем метода. Атрибут name позволяет задать основное имя и aliases: несколько имён ведут к одному определению, а не создают несколько объектов. У scanned-компонентов имя по умолчанию берётся из имени класса с правилами JavaBeans decapitalize; URLClient остаётся URLClient. Для внешнего контракта лучше задать имя явно, чем зависеть от необычного сокращения.

Параметры @Bean Spring разрешает как зависимости: Gateway gateway в параметрах service означает запрос подходящего bean. Внутри factory method выбираются адрес, таймаут и конструктор, а сам service не узнаёт про Environment или ApplicationContext. Это удобная граница между политикой сборки и бизнес-логикой.

Declared return type — важная часть metadata до создания объекта. Если @Bean объявлен как Object, контейнеру труднее заранее распознать его как конкретный клиент или инфраструктурный processor. Возвращай достаточно точный тип: контракт приложения для обычного сервиса, конкретный контракт расширения для BPP/BFPP. Не рассчитывай на удачный порядок создания, чтобы тип стал известен.

Внутри @Bean всё созданное через new автоматически становится bean.

Управляемым становится результат, возвращённый в путь создания контейнера. Если внутри service() вручную создан вложенный Gateway и его отдельно не зарегистрировали, контейнер не обязан внедрять его поля, вызывать @PostConstruct и оборачивать в AOP.

Full и lite различаются перехватом прямого вызова @Bean

Класс @Configuration по умолчанию использует proxyBeanMethods=true. Spring создаёт CGLIB-подкласс конфигурации и переопределяет подходящие @Bean-методы. Когда один из них вызывается из другого, вызов перенаправляется в BeanFactory. Для singleton это возвращает уже управляемую ссылку, для другого scope соблюдает правила этого scope.

Но фабрике всё же нужно однажды выполнить тело @Bean, чтобы получить объект. Interceptor различает внутренний вызов контейнера, создающий этот bean, и пользовательскую ссылку на другой @Bean. В первом случае выполняется тело, во втором — getBean. Именно это различие не даёт бесконечной рекурсии.

При @Configuration(proxyBeanMethods=false) и @Bean в обычном @Component работает lite mode. Определения остаются зарегистрированными, но прямой gateway() — обычный вызов Java. Он выполнит new повторно. Такой экземпляр не проходит managed lifecycle Gateway, даже если отдельный одноимённый bean зарегистрирован в том же контексте.

Полный пример BeansDemo.java, Java 21, Spring 7.0.9. Ниже — фрагмент.

cd examples/spring-core
      ./run.sh BeansDemo
@Configuration(proxyBeanMethods = false)
      static class Parameters {
          @Bean Gateway gateway() { return new Gateway(); }
          @Bean Service service(Gateway gateway) {
              return new Service(gateway); // Spring передал managed-зависимость.
          }
      }
      // В полном примере есть Full и Lite с service() -> gateway(),
      // а Gateway считает конструкторы и @PostConstruct отдельно.
Full: same=true, created=1, initialized=1
      Lite: same=false, created=2, initialized=1
      Parameters: same=true, created=1, initialized=1
      product same: true
      factory: TokenFactory

Full, Lite и Parameters различаются именно связями. В lite создано два Gateway, но init вызван у одного managed Gateway. В параметрическом варианте один объект и одна инициализация без enhancement конфигурации. Это хороший default для конфигураций без прямых inter-bean calls: зависимости видны в сигнатурах.

Full-конфигурация не может быть final, а interceptable instance @Bean-методы — private/final: подкласс не способен их переопределить. Static @Bean не участвует в таком instance-перехвате. Отключение enhancement позволяет final-конфигурации, но требует дисциплины в прямых вызовах. Не путай enhancement @Configuration с AOP-прокси сервисов: задачи у них разные.

Явный import собирает модуль без бесконтрольного сканирования

@Import(BankConfig.class) подключает конфигурацию как часть текущего контекста. Это не создание второго ApplicationContext и не переход в другой scope. Можно импортировать обычный компонент, группу конфигураций, ImportSelector или registrar. Так модуль предоставляет понятную точку подключения вместо требования «просканируй мои пакеты».

ImportSelector по metadata выбирает имена классов для регистрации; ImportBeanDefinitionRegistrar непосредственно добавляет определения. DeferredImportSelector обрабатывается позже обычных imports — такой механизм полезен для инфраструктуры, которая должна учесть пользовательскую конфигурацию. Spring Boot использует расширения этого семейства для auto-configuration, но конкретные условия и imports Boot разобраны в соседней теме.

XML, @ImportResource и программная registerBeanDefinition по-прежнему доступны. Их результаты сходятся в общем реестре. Не существует правила «XML bean хуже аннотационного»: важно, что metadata описывает, какие processors включены и как разрешаются зависимости.

Конфликт имени и неоднозначность типа — разные проблемы. Два определения paymentGateway спорят за одно имя; два имени одного типа дают два кандидата для DI. У обычной DefaultListableBeanFactory overriding разрешён по умолчанию, Boot запрещает его по умолчанию. При сканировании несовместимые одноимённые компоненты могут вызвать конфликт ещё до обычного bean overriding. Нельзя лечить все три ситуации одним @Primary.

Практическое правило: один модуль — явная точка импорта и узкая область scan внутри модуля. Тогда при чтении startup failure можно восстановить, кто зарегистрировал определение. Если bean неожиданно появился, исследуй граф импортов так же внимательно, как граф объектов.

Profile и condition решают состав графа до его создания

@Profile — условие регистрации определения. Если банковский sandbox включён только в profile test, без активного test определения не будет вовсе. Bean не создаётся и не ждёт переключения режима. Профиль задаётся в Environment до обработки конфигурации; изменение active profiles после refresh не пересобирает уже работающий граф.

@Conditional вызывает Condition.matches с доступом к metadata и ConditionContext: Environment, registry и другим доступным на этой фазе данным. @Profile сам построен на @Conditional. Условие должно отвечать, регистрировать ли компонент, а не создавать бизнес-объекты ради проверки: ранний getBean ломает нормальный порядок startup.

Environment объединяет property sources и active/default profiles. ${bank.url} в @Value означает подстановку свойства, #{…} — вычисление SpEL-выражения. Затем ConversionService или conversion-механизм приводит значение к ожидаемому типу параметра/поля. Это не тот же алгоритм, что поиск bean по типу. Возможность прочитать property не означает, что classpath application.yml автоматически загружен голым Framework-контекстом.

Spring Boot добавляет загрузку configuration files, свой порядок источников и удобный binding @ConfigurationProperties. Здесь достаточно удержать границу: настройки помогают выбрать и собрать определения, DI связывает объекты. При инциденте «взялся неправильный клиент» нужно проверить и активные условия регистрации, и выбор среди уже зарегистрированных кандидатов.

Не делай профиль названием каждой маленькой бизнес-развилки. Чем больше независимых profile-комбинаций, тем больше разных графов нужно понимать. Для изменяемого во время работы бизнес-правила используй явную стратегию или feature configuration; профиль описывает состав приложения при запуске.

FactoryBean разделяет фабрику и продукт под одним именем

BeanFactory создаёт и управляет бинами всего контейнера. FactoryBean<T> — отдельный bean, который производит продукт T. Такой адаптер полезен, если внешний объект сложно создать: нужен dynamic proxy, SDK builder или интеграция с другой фабрикой. Это два разных уровня слова «factory».

Для bean с именем token обычный getBean("token") возвращает продукт getObject(), а getBean("&token") — сам FactoryBean. isSingleton сообщает, можно ли кешировать продукт; это отдельная политика от scope самого factory bean. При singleton-фабрике и isSingleton=false фабрика одна, продуктов много.

getObjectType позволяет контейнеру сопоставить тип продукта без его изготовления. Если он возвращает null, некоторые операции поиска по типу не увидят продукт заранее. Поэтому фабрики инфраструктуры должны давать точную type information и избегать побочных действий в методах определения типа.

Сама фабрика проходит обычный lifecycle bean. За полную инициализацию и уничтожение продукта отвечает FactoryBean: контейнер постобрабатывает выданный продукт, но не автоматически проводит через него все init/destroy callbacks как через самостоятельное обычное определение. Ресурсы продукта фабрика закрывает в своём destroy. Не путай cached product с автоматически зарегистрированным disposable bean.

Под капотом: два кеша и префикс &

AbstractBeanFactory.getObjectForBeanInstance распознаёт dereference-префикс и FactoryBean. Затем FactoryBeanRegistrySupport получает или создаёт продукт и хранит singleton-продукты в отдельном кеше. Из этого следует, что «singleton factory» и «singleton product» нельзя выводить друг из друга без проверки isSingleton.

Граница декларативной конфигурации проста: она делает сборку обозримой, пока связи остаются в параметрах и определения не меняются во время живой работы. Если конфигурация начинает управлять бизнес-процессом, искать половину контекста через getBean и создавать скрытые вложенные объекты, верни эту логику в обычные сервисы. Следующая тема — как Spring выбирает зависимости среди готовых определений.

  • Аннотация без обнаружения не регистрирует bean.
  • Component и Bean сходятся в реестре, но отвечают за разные способы описать создание.
  • Lite не отменяет DI; он отменяет перехват прямого вызова Bean-метода.
  • Profile/Conditional выбирают определения при запуске, а не переключают живой граф.
  • FactoryBean — managed-фабрика и отдельный продукт с собственной политикой кеширования.

На собеседовании

Чем @Component отличается от @Bean?

@Component сообщает сканеру, что класс можно зарегистрировать. @Bean описывает factory method, результат которого контейнер берёт под управление. Я выбираю Component для собственных компонентов и Bean для внешних классов или явной настройки создания.

Оба пути дают BeanDefinition в общем реестре. Отсутствие bean с Component сначала заставляет меня проверить scan/import/condition, а не переписывать конструктор.

  • Stereotype-аннотации могут быть составными. @Repository несёт роль для инфраструктуры exception translation, @Service сам не включает транзакции.
  • Точный declared return type factory method нужен для определения кандидатов и раннего обнаружения processors.

Зачем proxyBeanMethods и что изменится при false?

Full Configuration перехватывает прямые calls между Bean-методами и направляет их в контейнер. При false определения остаются, но вызов метода выполняется как обычный Java-код. Если он делает new, получится дополнительный объект вне managed-пути.

Я передаю зависимости параметрами Bean-метода. Тогда контейнер разрешает их явно, и lite-конфигурация безопасно обходится без CGLIB enhancement.

  • Scope соблюдается при обращении к контейнеру, а не потому, что метод помечен Bean.
  • Static методы не перехватываются как instance-вызовы. Full configuration ограничена правилами переопределения final/private.
Почему в lite у вложенного Gateway не вызвался PostConstruct?

Потому что service() вызвал gateway() напрямую. Его результат передан в Service и не возвращён контейнеру как создаваемый gateway-bean. Исправление — зависимость в параметрах service(Gateway gateway), а не ручной вызов init.

На каком этапе работают @Profile и @Conditional?

Они участвуют в решении, попадёт ли определение в контекст. Profile проверяет активные профили Environment, Conditional применяет условие к metadata. Без определения нет ни создания объекта, ни дальнейшего выбора этого bean для DI.

Я задаю окружение до refresh и проверяю граф для нужной комбинации. Изменение свойства после запуска не включает автоматически пропущенный bean.

  • Profile реализован через Conditional. Состав графа и runtime-бизнес-правила требуют разных механизмов.
  • Условия регистрации нельзя использовать как повод для раннего создания обычных бинов; это нарушает фазы расширения контейнера.

Чем FactoryBean отличается от BeanFactory?

BeanFactory — контейнерный механизм; FactoryBean — bean, который создаёт продукт. По обычному имени я получаю продукт, по имени с амперсандом — саму фабрику. Это удобно для адаптации сложного создания объектов к контейнеру.

Я отдельно проверяю scope фабрики, isSingleton продукта и getObjectType. Одна фабрика не обязана всегда возвращать один продукт.

  • Singleton product кешируется отдельно от самой фабрики.
  • Фабрика отвечает за init/destroy продукта; автоматический lifecycle продукта не равен обычному bean-definition пути.
