Spring: Configuration & Beans

Способ сборки может незаметно изменить, каким банком пользуется сервис. В одной конфигурации вызов gateway() возвращает готовый бин, в другой создаёт лишний объект. Разберём путь от регистрации компонента до этого вызова: тогда станет понятно, какую ссылку получит сервис и кто подготовит её к работе.

Spring найдёт компонент, если его пакет входит в поиск

В проект добавили BankGateway с @Component, но запуск падает: PaymentService требует Gateway, а контейнер его не находит. Класс компилируется и аннотация стоит на месте. Проверим, как этот класс должен попасть в реестр: через сканирование пакета или явное подключение конфигурации.

@ComponentScan задаёт пакеты, в которых Spring ищет компоненты. Без указания пакетов поиск начинается с пакета класса, помеченного этой аннотацией. В Boot точкой отсчёта обычно служит @SpringBootApplication. Если основной класс лежит в com.example.app, соседний пакет com.example.bank останется за границей такого поиска. Поэтому главный класс часто помещают в общий корневой пакет.

Сканер читает аннотации из файлов классов, в стандартном пути с помощью ASM. Для подходящих классов он создаёт BeanDefinition. Конструкторы компонентов выполняются позже, когда фабрика начинает собирать объекты. Это позволяет сначала определить состав приложения и лишь затем подключаться к банкам и открывать ресурсы.

@Service, @Repository и @Controller включают @Component и уточняют роль класса. Для сканера все они обозначают компонент. Другие подсистемы могут использовать эту роль: например, инфраструктура перевода исключений доступа к данным обрабатывает @Repository. Транзакция подключается отдельно, через соответствующую аннотацию и обработчик.

При ошибке отсутствующей зависимости начни с границы поиска. Затем проверь, подключена ли конфигурация и выполнены ли её условия. Узкие пакеты упрощают этот разбор: видно, откуда пришёл каждый компонент. Поиск по всему com способен захватить конфигурацию чужого модуля и изменить состав приложения.

Метод @Bean передаёт созданный объект контейнеру

SDK банка предоставляет свой клиент. Менять его класс и добавлять @Component неудобно, зато ты можешь создать его в методе @Bean: задать адрес, таймауты и учётные данные, затем вернуть готовый объект. Spring обработает результат как бин: внедрит его зависимости, выполнит инициализацию и при необходимости добавит прокси.

Имя бина по умолчанию совпадает с именем метода. Через name можно дать основное имя и дополнительные имена — aliases. Они ведут к одному бину. При сканировании имя обычно получается из имени класса: BankGateway превращается в bankGateway; для начальных заглавных букв действует правило JavaBeans, поэтому URLClient сохраняет имя URLClient. Если имя важно для подключения модуля, его удобно задать явно.

Параметры метода @Bean — запросы зависимостей к Spring. В service(Gateway gateway) контейнер сначала выбирает и подготавливает Gateway, затем вызывает метод с этой ссылкой. Метод отвечает за создание Service, а правила выбора Gateway остаются в конфигурации. Так бизнес-класс получает готовое подключение без чтения Environment.

Возвращаемый тип метода помогает Spring узнать тип бина до его создания. Если написать @Bean Object gateway(), контейнер заранее видит только Object. Точный контракт Gateway позволяет обнаружить зависимость раньше. Для специальных обработчиков особенно важен их собственный интерфейс: Spring должен распознать и подключить их до подготовки остальных объектов.

Все объекты, созданные внутри @Bean, проходят обработку Spring.

Spring обрабатывает возвращённый результат метода. Если service() создаёт вложенный Gateway обычным new и отдаёт только Service, этот Gateway остаётся обычной вложенной зависимостью. Для отдельной подготовки Gateway его тоже нужно получить через контейнер.

Одинаковый вызов gateway() даёт разные связи в full и lite

Рассмотрим два метода @Bean: gateway() создаёт Gateway, а service() вызывает gateway() и передаёт результат в Service. Кажется, что вызов должен всегда выполнять new. Но у @Configuration по умолчанию включён proxyBeanMethods=true. Spring создаёт подкласс конфигурации и перенаправляет такие вызовы между её методами в контейнер.

Этот режим называют full. Когда service() вызывает gateway(), Spring получает бин gateway по правилам его области видимости. Для singleton это тот же объект, который выдаёт контекст. Чтобы создать его в первый раз, контейнер всё же выполняет исходное тело gateway(): обработчик различает создание бина и обращение к нему из другого метода.

В режиме lite, с proxyBeanMethods=false, методы сохраняют обычное поведение Java. Прямой gateway() заново выполняет new. Отдельно Spring создаёт собственный бин gateway по зарегистрированному методу. В результате сервис хранит один Gateway, а контекст — другой. Вызов @PostConstruct позволяет увидеть, какой из них прошёл подготовку контейнера.

Фрагменты BeansDemo.java, Java 21, Spring 7.0.9. Здесь показаны все три варианта и само сравнение. Imports и оболочка main находятся в полном файле.

static int created, initialized;
static class Gateway {
    Gateway() { created++; } // Считаем все созданные объекты, включая лишние.
    @PostConstruct void init() { initialized++; } // Считает объекты, подготовленные Spring.
}
record Service(Gateway gateway) {}
@Configuration
static class Full {
    @Bean Gateway gateway() { return new Gateway(); }
    @Bean Service service() { return new Service(gateway()); } // Spring перенаправит gateway() в контейнер.
}
@Configuration(proxyBeanMethods = false)
static class Lite {
    @Bean Gateway gateway() { return new Gateway(); }
    @Bean Service service() { return new Service(gateway()); } // Обычный вызов создаёт лишний объект.
}
@Configuration(proxyBeanMethods = false)
static class Parameters {
    @Bean Gateway gateway() { return new Gateway(); }
    @Bean Service service(Gateway gateway) { return new Service(gateway); } // Готовую зависимость передаёт Spring.
}
static void compare(Class<?> config) {
    created = initialized = 0;
    try (var ctx = new AnnotationConfigApplicationContext(config)) {
        System.out.printf("%s: same=%s, created=%d, initialized=%d%n",
            config.getSimpleName(), ctx.getBean(Service.class).gateway() == ctx.getBean(Gateway.class),
            created, initialized);
    }
}
// В main:
compare(Full.class);
compare(Lite.class);
compare(Parameters.class);
cd examples/spring-core
./run.sh BeansDemo  # Первые три строки сравнивают конфигурации.
Full: same=true, created=1, initialized=1
Lite: same=false, created=2, initialized=1
Parameters: same=true, created=1, initialized=1

Передача через параметр service(Gateway gateway) делает связь явной и в full, и в lite. Она удобна, когда методы конфигурации создают компоненты независимо друг от друга: по сигнатуре сразу видно, что нужно каждому из них.

Перехват full-конфигурации работает через переопределение методов подклассом. Поэтому такой класс и его переопределяемые @Bean-методы должны допускать наследование: final и private этому мешают. Для static @Bean прямой вызов остаётся вызовом статического метода. Прокси конфигурации управляет обращениями к бинам; AOP-прокси сервиса решает другую задачу — добавляет поведение при его вызове.

Импорт делает точку подключения модуля явной

Банковский модуль может предоставить BankConfig. Приложение подключает его через @Import(BankConfig.class), и определения модуля попадают в текущий контекст. При чтении конфигурации сразу видно, что подключено. Это удобнее, чем просить приложение искать компоненты во всех пакетах библиотеки.

Импортировать можно конфигурацию, обычный компонент или расширение регистрации. ImportSelector выбирает имена классов по метаданным конфигурации. ImportBeanDefinitionRegistrar добавляет описания напрямую. DeferredImportSelector откладывает выбор до более позднего этапа обработки конфигураций; этот механизм используется и в автоматической конфигурации Boot.

Описание также можно добавить из XML через @ImportResource или программно через registerBeanDefinition. После регистрации фабрика работает с тем же реестром. Для поведения важны свойства описания и подключённые обработчики, а способ записи конфигурации остаётся выбором автора приложения.

Составляя модули, различай два конфликта. Два определения под именем paymentGateway спорят за одну запись реестра. Два разных имени одного типа создают выбор для DI. У DefaultListableBeanFactory замена существующего определения разрешена по умолчанию, а Boot по умолчанию запрещает её. Сканер способен остановиться ещё раньше, если найдёт несовместимые компоненты с одним именем.

Поэтому добавление @Primary помогает выбрать один из нескольких бинов, но конфликт имён нужно решать в регистрации. Узкая область сканирования и явная точка импорта делают обе ситуации понятнее: можно проследить, какая конфигурация добавила каждый бин.

Условия определяют, какие компоненты войдут в приложение

Для песочницы нужен SandboxGateway, для рабочего окружения — ProductionGateway. @Profile позволяет зарегистрировать разные определения в зависимости от активных профилей. Если профиль sandbox выключен, его Gateway отсутствует в реестре. Состав приложения выбирается до создания этой зависимости.

@Profile построен на @Conditional. Более общее условие реализует Condition.matches: оно читает метаданные и доступную информацию из ConditionContext, например свойства Environment. Здесь нужно решить, добавлять ли описание. Создание бизнес-компонентов через getBean в таком условии запускает их слишком рано, до обычной подготовки контейнера.

Environment объединяет источники свойств и профили. В @Value запись ${bank.url} подставляет значение свойства, а #{…} вычисляет выражение SpEL. Затем значение преобразуется в нужный тип. Например, строка с таймаутом превращается в число. Это отдельный механизм от выбора Gateway среди бинов.

Spring Boot добавляет загрузку файлов application.properties/application.yml, порядок источников и привязку настроек через @ConfigurationProperties. В обычном Framework-контексте источники нужно подключить самому. Профили также устанавливают до refresh: изменение списка профилей в работающем контексте сохраняет уже собранные объекты.

Профиль удобно описывает вариант запуска целого приложения. Для правила, меняющегося во время работы, например временного отключения банка, лучше отдельная стратегия или настройка сервиса. Иначе придётся пересобирать граф ради изменения одного бизнес-решения.

FactoryBean выдаёт продукт, а по &имя можно получить саму фабрику

Иногда готовый объект получается через сложную фабрику: она настраивает SDK, создаёт динамический прокси или соединяет Spring с другой библиотекой. Такой объект можно адаптировать через FactoryBean<T>. Это бин-фабрика, который выдаёт продукт T. А BeanFactory — механизм всего контейнера, который получает и создаёт бины.

Для имени token обычный getBean("token") возвращает результат getObject(), а getBean("&token") — сам TokenFactory. Метод isSingleton сообщает Spring, следует ли сохранять продукт для повторных обращений. Даже если фабрика одна, она может выдавать разные продукты при isSingleton=false.

Следующая часть того же BeansDemo.java показывает оба способа получения. Вывод взят из последних двух строк запуска ./run.sh BeansDemo.

record Token(int number) {}
static class TokenFactory implements FactoryBean<Token> {
    int number;
    public Token getObject() { return new Token(++number); }
    public Class<?> getObjectType() { return Token.class; } // Тип продукта доступен без его создания.
    public boolean isSingleton() { return true; } // Spring сохраняет продукт отдельно от экземпляра фабрики.
}
@Configuration(proxyBeanMethods = false)
static class Factories {
    @Bean TokenFactory token() { return new TokenFactory(); }
}
// В main:
try (var ctx = new AnnotationConfigApplicationContext(Factories.class)) {
    System.out.println("product same: " + (ctx.getBean("token") == ctx.getBean("token")));
    System.out.println("factory: " + ctx.getBean("&token").getClass().getSimpleName());
}
product same: true
factory: TokenFactory

Метод getObjectType даёт тип продукта заранее, пока getObject ещё не вызван. По этой информации Spring ищет зависимости. Если фабрика возвращает null вместо типа, часть поиска по типу пропустит её продукт. Поэтому определение типа должно быть доступно без дорогого создания объекта.

Саму фабрику Spring готовит и уничтожает как обычный бин. Инициализацией и освобождением ресурсов продукта занимается фабрика: выданный объект проходит постобработку Spring, но полный набор обычных init/destroy-вызовов продукта автоматически не повторяется. Например, фабрика, создавшая соединение, закрывает его в собственном методе уничтожения.

Под капотом: почему фабрика и продукт хранятся отдельно

AbstractBeanFactory.getObjectForBeanInstance распознаёт префикс & и объект FactoryBean. Затем FactoryBeanRegistrySupport получает продукт и при необходимости сохраняет его в отдельном кеше. У фабрики и продукта разные записи и разные правила повторного использования.

Конфигурация остаётся понятной, пока показывает создание компонентов и их связи. Проведение платежа, повторные попытки и выбор маршрута во время работы удобнее оставить обычным сервисам. Следующая тема разбирает выбор зависимостей: что произойдёт, если несколько зарегистрированных бинов подходят одному аргументу.

  • Сканирование и явная регистрация сначала добавляют описания; объекты создаются позже.
  • @Bean подходит для сторонних классов и явной настройки. Его результат обрабатывается контейнером.
  • В full прямой вызов другого @Bean обращается к контейнеру. В lite он выполняет обычное тело метода.
  • Параметры @Bean показывают зависимости и дают Spring возможность подставить подготовленные бины.
  • Profile и Conditional выбирают состав при запуске. FactoryBean разделяет фабрику и выдаваемый продукт.

На собеседовании

Чем @Component отличается от @Bean?

@Component позволяет сканеру зарегистрировать класс. @Bean описывает метод, который создаёт объект и передаёт его контейнеру. Для собственного сервиса я часто использую Component, а для клиента сторонней библиотеки — Bean с явными настройками создания.

Оба способа добавляют BeanDefinition в общий реестр. Если компонент отсутствует, я проверяю его пакет, подключение конфигурации и условия регистрации.

  • @Service и @Repository уточняют роль компонента. Инфраструктура перевода исключений использует Repository; транзакции подключаются отдельно.
  • Точный возвращаемый тип @Bean помогает найти зависимости до создания объекта и вовремя обнаружить специальные обработчики.

Зачем proxyBeanMethods и что изменится при false?

С proxyBeanMethods=true Spring перехватывает обращения между методами @Bean и получает соответствующий бин из контейнера. При false прямой вызов выполняет тело метода как обычный Java-код. Поэтому gateway() с new может создать второй объект, который останется внутри сервиса и пройдёт только обычный конструктор.

Я передаю Gateway параметром метода service. Тогда его выбирает и подготавливает Spring, и конфигурация даёт нужную связь в обоих режимах.

  • Получение из контейнера соблюдает scope. Для prototype это новый объект по запросу, для singleton — сохранённая ссылка.
  • Full использует подкласс конфигурации: final-класс и private/final-методы мешают переопределению. Статические методы вызываются обычным способом.
У Gateway внутри Service в lite отсутствует вызов PostConstruct. Что исправить?

Метод service() получил вложенный объект через прямой gateway(), то есть обычный new. Передай Gateway параметром service(Gateway gateway): Spring подставит бин, который прошёл подготовку.

На каком этапе работают @Profile и @Conditional?

Они решают, добавить ли описание бина в реестр. Profile проверяет активные профили Environment, Conditional применяет заданное условие. Затем Spring создаёт объекты из оставшихся описаний и выбирает их для внедрения.

Я задаю окружение до refresh. Для изменения поведения во время работы использую стратегию или настройки сервиса; собранный граф сохраняется после изменения списка профилей.

  • Profile реализован через Conditional. Условие должно читать данные, доступные на этапе регистрации.
  • Вызов getBean внутри условия может запустить обычный компонент до подключения обработчиков. Это нарушает порядок подготовки.

Чем FactoryBean отличается от BeanFactory?

BeanFactory обслуживает весь контейнер. FactoryBean — отдельный бин-фабрика, который создаёт свой продукт. По обычному имени я получаю продукт, по имени с & — саму фабрику. Такой адаптер полезен для сложного создания объекта сторонней библиотеки.

Я смотрю на scope фабрики, isSingleton продукта и getObjectType отдельно: они описывают время жизни фабрики, повторное использование продукта и его тип для поиска зависимостей.

  • Spring сохраняет singleton-продукт в отдельном кеше, поэтому одна фабрика может иметь собственные правила выдачи продуктов.
  • Фабрика отвечает за инициализацию и закрытие своего продукта. Сам FactoryBean проходит обычный жизненный цикл бина.
