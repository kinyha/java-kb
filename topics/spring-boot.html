Spring Boot: Auto-configuration

Платёжному сервису нужен готовый шлюз банка. Boot находит конфигурацию из подключённой библиотеки и проверяет, подходит ли она этому приложению. Если ты уже описал свой шлюз, стандартный вариант уступает ему место. Решение принимается во время сборки контекста по классам, настройкам и описаниям бинов. Поэтому неожиданный выбор стоит разбирать от условия и доступного типа, а затем смотреть на созданный объект.

Каждый платёжный сервис повторяет одну и ту же сборку

У команды есть три сервиса: списания, возвраты и сверка. Все ходят в один банк. В каждом приходится подключать SDK, создавать шлюз, передавать адрес и таймауты, подключать метрики. Через месяц один сервис уже отправляет запросы с новыми настройками, а второй всё ещё держит старую конфигурацию.

Spring умеет собрать граф объектов из @Configuration, @Bean и компонентов. Но решение «какие инфраструктурные бины добавить» остаётся за каждым приложением. Команда может вынести конфигурацию банка в общую библиотеку. Следующая задача — подключать её только там, где есть SDK и включена работа с банком, а также дать отдельному сервису заменить стандартный шлюз.

Автоконфигурация Boot — это такая общая конфигурация с условиями включения. Она добавляет обычные описания бинов в тот же контейнер Spring. После этого зависимости разрешаются и объекты создаются по знакомым правилам. В готовых модулях Boot тем же способом собираются HTTP-инфраструктура, подключение к базе и другие стандартные части приложения.

Ниже мы сделаем небольшую автоконфигурацию банка. SDK изображает локальный класс, а списание — функция, возвращающая строку. Сеть здесь лишняя: опыт проверяет выбор объекта, который получит платёжный сервис. Демо запускается на JDK 21, Spring Boot 4.1.1 и Spring Framework 7.0.9.

interface BankGateway {
    String charge(String paymentId);
}

class PaymentService {
    private final ObjectProvider<BankGateway> gateway;

    PaymentService(ObjectProvider<BankGateway> gateway) {
        this.gateway = gateway; // Выбор отложен, чтобы увидеть и отсутствие шлюза.
    }

    String pay(String id) {
        BankGateway selected = gateway.getIfAvailable(); // Два кандидата дадут ошибку.
        return selected == null ? "unavailable:" + id : selected.charge(id);
    }
}

В обязательном платёжном пути лучше требовать BankGateway прямо в конструкторе: отсутствие шлюза тогда сорвёт запуск сервиса. ObjectProvider в этом опыте позволяет сравнить три контекста одной программой. Он меняет момент выбора зависимости, а правила автоконфигурации остаются теми же.

Стартер приносит зависимости, автоконфигурация — описания бинов

Команда выпускает bank-spring-boot-starter. Его главная задача — собрать совместимые зависимости: SDK банка и модуль bank-spring-boot с конфигурацией. Maven или Gradle добавляет их в classpath. Стартер сам по себе ещё не доказывает, что шлюз появился в контексте: Boot должен найти конфигурацию, а её условия должны пройти.

Разделение на два модуля полезно, если SDK бывает нескольких видов. Модуль конфигурации умеет работать с доступным вариантом, стартер выбирает набор библиотек для обычного случая. Для маленькой интеграции оба можно объединить. Своему стартеру дают название организации или технологии; префикс spring-boot-starter- оставляют официальным стартерам Spring.

Ещё одна часть сборки — управление версиями. spring-boot-dependencies задаёт согласованный набор версий через BOM. spring-boot-starter-parent добавляет к нему настройки Maven и плагинов. Если проект уже наследует корпоративный parent, BOM можно импортировать отдельно. BOM задаёт версии, но зависимости в проект добавляешь ты или стартер.

В Boot 4 инфраструктура и её автоконфигурации разделены по технологическим модулям. Для Spring MVC основной стартер — spring-boot-starter-webmvc. Поэтому при миграции проверяют и зависимости, и новые пакеты классов автоконфигурации. Механизм выбора по условиям остаётся прежним.

Boot находит конфигурации через imports и проверяет условия

Обычное приложение начинается с @SpringBootApplication. Она объединяет @SpringBootConfiguration, @EnableAutoConfiguration и @ComponentScan. Первая делает класс конфигурацией приложения, вторая включает импорт автоконфигураций, третья ищет пользовательские компоненты. Главный класс ставят в корневой пакет приложения: тогда сканирование охватывает его подпакеты.

Поиск компонентов и поиск автоконфигураций идут разными путями. Для автоконфигураций Boot читает ресурсы META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports из classpath. В каждой строке — полное имя одного класса. Такой класс может находиться в пакете библиотеки, далеко за пределами сканирования приложения. Расширять @ComponentScan на все библиотеки ради этого не требуется.

В демо список содержит вложенный класс, поэтому его имя записано с $. Это полноценный ресурс, который находит Boot. В библиотеке верхний уровень чаще удобнее: com.acme.bank.BankAutoConfiguration. Здесь классы собраны в одном файле, чтобы опыт легко запускался.

# examples/boot/resources/META-INF/spring/
# org.springframework.boot.autoconfigure.AutoConfiguration.imports
kb.boot.AutoConfigDemo$BankAutoConfiguration

Наш кандидат действует при двух условиях: доступен класс SDK и работа с банком включена. Сам шлюз добавляется, только если приложение ещё не описало другой BankGateway. Условия на классе закрывают всю конфигурацию, условие на методе — один конкретный бин.

@AutoConfiguration // Конфигурация с proxyBeanMethods=false, импортируемая Boot.
@ConditionalOnClass(BankSdk.class) // Есть библиотека, с которой умеем работать.
@ConditionalOnProperty(prefix = "payments.bank", name = "enabled",
        havingValue = "true", matchIfMissing = true) // Без свойства включаем по умолчанию.
class BankAutoConfiguration {
    @Bean
    @ConditionalOnMissingBean(BankGateway.class) // Проверяем доступные описания по типу.
    BankGateway bankGateway() {
        return id -> "bank:" + id;
    }
}
УсловиеЧто решаетПограничный случай
@ConditionalOnClassДоступны ли нужные классыНаличие SDK ещё не говорит, что банк доступен по сети
@ConditionalOnMissingBeanЕсть ли уже подходящий бин по известным описаниямТип Object скрывает роль будущего объекта
@ConditionalOnBeanЕсть ли зависимость, вокруг которой строится дополнительная инфраструктураЕё конфигурацию нужно обработать раньше
@ConditionalOnPropertyПодходит ли значение из EnvironmentБез havingValue подходит любое присутствующее значение, кроме false; отсутствие регулирует matchIfMissing
@ConditionalOnWebApplicationПодходит ли вид веб-приложенияServlet и reactive требуют разной инфраструктуры

Почему @ConditionalOnClass(BankSdk.class) вообще удаётся прочитать, если SDK отсутствует? Spring читает метаданные аннотации из байткода через ASM. Для этой проверки ему не требуется загрузить сам класс конфигурации и связать все её методы. Условие может отвергнуть кандидат до такого шага.

Эта защита должна охватывать класс, использующий необязательный тип. Если тип SDK фигурирует в сигнатуре @Bean, а проверка стоит только на этом методе, загрузка и анализ класса могут потребовать SDK раньше проверки. Такие методы выносят в отдельную конфигурацию с @ConditionalOnClass на классе. При собственной составной аннотации имя класса указывают через name.

В старых примерах список автоконфигураций лежит под ключом EnableAutoConfiguration в spring.factories. Boot 2.7 ввёл AutoConfiguration.imports с поддержкой обоих вариантов; Boot 3.0 убрал регистрацию автоконфигураций через старый ключ. Остальные назначения spring.factories сохранились.

Свой бин занимает место стандартного до создания объектов

Сервис возвратов получает особые условия банка. Ты добавляешь свой @Bean BankGateway. Почему он успевает повлиять на автоконфигурацию, хотя в контексте ещё нет готового шлюза? Потому что условие проверяет известные контейнеру описания и их типы. Вызывать пользовательскую фабрику для этого не требуется.

@EnableAutoConfiguration подключает AutoConfigurationImportSelector. Он реализует DeferredImportSelector: импорт кандидатов отложен до обработки обычных пользовательских конфигураций. К моменту проверки @ConditionalOnMissingBean пользовательские описания уже доступны. Boot также удаляет исключённых кандидатов, отбрасывает неподходящие варианты и упорядочивает автоконфигурации.

Когда обнаружен пользовательский BankGateway, стандартный метод bankGateway() пропускается. Здесь нет двух готовых объектов, из которых Boot выбрал один. Для стандартного шлюза вообще не появляется описание, а значит, его фабрика не вызывается. Этот подход часто называют отступлением автоконфигурации, или back-off.

Теперь сравним три запуска. В первом добавляем только приложение и ресурс imports. Во втором дополнительно передаём пользовательскую конфигурацию. В третьем через аргумент запуска выключаем стандартную конфигурацию. Полный файл — AutoConfigDemo.java; фрагменты ниже взяты из него.

@Configuration(proxyBeanMethods = false)
class ManualConfiguration {
    @Bean
    BankGateway customGateway() { // Имя отличается; для условия важен тип.
        return id -> "custom:" + id;
    }
}

@SpringBootConfiguration(proxyBeanMethods = false)
@EnableAutoConfiguration // Читает imports, конфигурацию банка сюда не импортируем вручную.
@Import(PaymentService.class) // Компонент сервиса добавлен явно.
class Application {}

// start(extra, args) создаёт SpringApplication(Application.class),
// добавляет extra в primary sources и запускает без веб-сервера.
// Никакого component scan: соседние учебные варианты не попадут в контекст.
scenario("default", null);
scenario("manual", ManualConfiguration.class);
scenario("disabled", null, "--payments.bank.enabled=false");

// Внутри scenario после запуска контекста:
System.out.println(name + " gateways="
        + Arrays.toString(context.getBeanNamesForType(BankGateway.class)));
System.out.println(name + " result=" + context.getBean(PaymentService.class).pay("p-17"));

Пользовательский бин заменил стандартный по типу, хотя имена разные. При отключении свойства стандартного шлюза нет совсем. Если одновременно выключить стандартную конфигурацию и добавить свой бин, пользовательский бин останется: свойство стоит на конфигурации библиотеки и управляет только её участием.

Достаточно поставить @ConditionalOnMissingBean на любой @Bean, и пользовательская конфигурация всегда победит.

Условие видит только уже обработанные описания. В двух обычных пользовательских @Configuration оно зависит от порядка регистрации. Автоконфигурации специально импортируются после пользовательских; для двух собственных вариантов лучше выразить выбор через профили, свойства или явную конфигурацию.

Отчёт условий показывает, почему Boot выбрал этот вариант

После добавления библиотеки сервис неожиданно получил другой клиент. Начни с отчёта условий: запусти приложение с --debug или настройкой debug=true. Отчёт показывает прошедшие и отклонённые условия, а также исключённые конфигурации. Это ответ на вопрос «почему добавлено это описание», а список бинов отвечает на следующий вопрос — «что в итоге есть в контейнере».

В отчёте ищи полное имя конфигурации и конкретного метода. Отрицательный результат для ненужной библиотеки нормален: Boot рассматривает много кандидатов. Проблема начинается там, где ты ожидал положительный результат. Условия на классе могут пройти, а условие одного метода внутри — нет.

Демо читает тот же ConditionEvaluationReport и печатает только запись о стандартном шлюзе. Ниже показан настоящий вывод запуска с пользовательским BankGateway; строка сообщения остаётся на языке самой библиотеки.

// Контекст запущен с ManualConfiguration; её @Bean возвращает BankGateway.
var report = ConditionEvaluationReport.get(context.getBeanFactory());
String source = BankAutoConfiguration.class.getName() + "#bankGateway";
var outcomes = report.getConditionAndOutcomesBySource().get(source);
System.out.println("bankGateway fullMatch=" + outcomes.isFullMatch());
outcomes.forEach(outcome -> System.out.println(outcome.getOutcome().getMessage()));

Слишком общий тип прячет пользовательский шлюз

Теперь изменим только тип возврата пользовательской фабрики на Object. Внутри всё ещё создаётся BankGateway. Но при проверке условия контейнеру доступна сигнатура метода, а там роль шлюза потеряна. Стандартное описание тоже регистрируется. После создания singleton-бинов обнаруживаются уже два объекта нужного типа.

@Configuration(proxyBeanMethods = false)
class OpaqueConfiguration {
    @Bean
    Object customGateway() { // При выборе конфигурации известен только Object.
        return (BankGateway) id -> "opaque:" + id;
    }
}

// BankAutoConfiguration остаётся прежней: MissingBean(BankGateway.class).
try (var context = start(OpaqueConfiguration.class)) {
    System.out.println("opaque gateways="
            + Arrays.toString(context.getBeanNamesForType(BankGateway.class)));
    try {
        System.out.println(context.getBean(PaymentService.class).pay("p-17"));
    } catch (NoUniqueBeanDefinitionException ex) {
        System.out.println("opaque result=" + ex.getClass().getSimpleName());
    }
}
./run.sh AutoConfigDemo opaque # Та же функция, другая сигнатура @Bean.
opaque gateways=[customGateway, bankGateway]
opaque result=NoUniqueBeanDefinitionException

Исправление — вернуть BankGateway, как в предыдущем опыте. Если другие условия ищут конкретную реализацию, объяви и её конкретный тип. @Primary решил бы выбор зависимости между двумя кандидатами, но не отменил бы создание стандартного шлюза. Это разные задачи: один механизм регистрирует описания, другой выбирает из уже имеющихся кандидатов.

Между двумя автоконфигурациями порядок тоже имеет смысл. Если конфигурация аудита проверяет @ConditionalOnBean(BankGateway.class), конфигурацию шлюза обрабатывают раньше: @AutoConfiguration(after = BankAutoConfiguration.class). before и after упорядочивают регистрацию описаний. Объекты затем создаются по зависимостям; требование порядка инициализации задают зависимостью или @DependsOn.

Под капотом: где искать решение о регистрации

AutoConfigurationImportSelector получает кандидатов через ImportCandidates, применяет исключения и фильтры. Группа отложенного импорта упорядочивает кандидатов. Условия могут проверяться на разных этапах разбора и регистрации; OnBeanCondition работает на этапе регистрации, когда уже накоплены описания. Это позволяет использовать сведения о пользовательских бинах без массового раннего создания объектов.

Предварительные метаданные помогают быстро отбросить явно неподходящие конфигурации. Окончательное решение отдельных методов всё равно зависит от их условий. Поэтому наличие имени в imports означает «рассмотреть кандидат», а положительное условие класса ещё не означает «зарегистрировать все его @Bean».

Отключай конкретное решение и сохраняй явные границы

Если нужно изменить адрес банка или таймаут, начни с свойства, которое предоставляет библиотека. Если нужен особый шлюз, добавь свой бин ожидаемого типа. Если всё решение библиотеки здесь лишнее, исключи класс автоконфигурации. Масштаб вмешательства должен соответствовать задаче: исключение убирает также остальные бины этого класса.

@SpringBootApplication(exclude = BankAutoConfiguration.class) // Убираем весь кандидат.
class PaymentsApplication {
    public static void main(String[] args) {
        SpringApplication.run(PaymentsApplication.class, args);
    }
}

// Когда тип не должен фигурировать в исходниках, доступен строковый вариант:
// @SpringBootApplication(excludeName = "com.acme.bank.BankAutoConfiguration")
spring:
  autoconfigure:
    exclude: com.acme.bank.BankAutoConfiguration # То же решение через настройку.

Исключение автоконфигурации не удаляет пользовательский бин и не отменяет обычный @Import. Если ты сам импортировал класс или включил его в component scan, он пришёл другим путём. Поэтому собственные автоконфигурации держат в отдельном пакете и подключают через imports; их внутренние части добавляют явно, без широкого сканирования.

Условия оцениваются при построении контекста. Изменение переменной окружения у уже работающего процесса само по себе не удалит шлюз и не пересоберёт граф объектов. Проверка класса SDK также не проверяет DNS, сертификат или работоспособность банка. Готовность инфраструктуры, здоровье приложения и восстановление после сетевой ошибки решаются отдельно.

Для библиотечного стартера важен небольшой, устойчивый договор: пространство свойств, типы точек расширения и правила отступления. Не привязывай бизнес-решение «списать повторно или вернуть ошибку» к незаметному появлению класса в classpath. Такое решение платёжный сервис должен выражать явно. При обновлении Boot сравнивай отчёт условий и состав зависимостей: новый модуль способен изменить выбранную инфраструктуру без изменения бизнес-кода.

Порядок источников настроек и @ConfigurationProperties разобраны в Configuration & Profiles. Запуск контекста, сервер и упаковка — в Startup & Packaging. HTTP-отчёт /actuator/conditions, проверки готовности и метрики — в Actuator.

  • Стартер добавляет зависимости. Boot читает imports и условия, затем регистрирует обычные описания бинов Spring.
  • Отложенный импорт даёт пользовательским описаниям появиться раньше автоконфигураций. Отступление происходит до создания стандартного объекта.
  • Условие по типу опирается на известные типы описаний. Точный тип возврата @Bean — часть договора конфигурации.
  • Отчёт условий объясняет регистрацию. @Primary объясняет выбор зависимости. before/after объясняют порядок описаний.
  • Исключение убирает кандидата автоконфигурации. Доступность банка и изменение работающего графа объектов требуют отдельных решений.

На собеседовании

Как Boot понимает, что нужно настроить автоматически?

Я включаю автоконфигурацию через @SpringBootApplication. Boot читает AutoConfiguration.imports из подключённых модулей и получает кандидатов. Для каждого проверяет условия: нужные классы, свойства, вид приложения и уже известные бины. Прошедшие варианты добавляют обычные BeanDefinition в контейнер Spring.

Например, модуль банка предлагает шлюз, если есть SDK и включена интеграция. Если я объявил свой BankGateway, условие MissingBean отклоняет стандартную фабрику. В итоге платёжный сервис получает мой шлюз через обычное внедрение зависимости.

  • AutoConfigurationImportSelector реализует DeferredImportSelector. Поэтому условия по бинам видят пользовательские описания, обработанные раньше; готовые объекты для этого создавать не нужно.
  • Component scan ищет компоненты приложения по пакетам. Кандидаты из imports находятся независимо от этих пакетов. Расширение scan на библиотеки способно включить конфигурацию в обход задуманного порядка.
  • Условия класса и его методов проверяются отдельно. Положительный результат класса ещё не обещает каждый бин; для расследования нужен отчёт конкретного метода.

Чем отличаются Spring, Spring Boot и стартер?

Spring даёт контейнер, внедрение зависимостей, обработку конфигураций и другие механизмы. Boot собирает на их основе приложение с готовыми инфраструктурными решениями и удобным запуском. Стартер — зависимость, которая приносит нужный набор библиотек и модулей интеграции.

Я разделяю два события: библиотека появилась в classpath и бин появился в контексте. Между ними находится проверка условий. Даже с подключённым стартером конкретная автоконфигурация может отступить перед моей или быть выключена настройкой.

  • @SpringBootApplication объединяет @SpringBootConfiguration, @EnableAutoConfiguration и @ComponentScan. Эти части можно использовать отдельно, как в демо с явными источниками.
  • BOM согласует версии, а зависимости добавляют отдельно. Импорт spring-boot-dependencies не равен подключению всех стартеров; parent также добавляет настройки сборки.
  • В Boot 4 автоконфигурации распределены по технологическим модулям. Старые пакеты и набор зависимостей при миграции проверяют вместе.

Как заменить стандартный бин или отключить автоконфигурацию?

Если меняется параметр, сначала ищу свойство библиотеки. Если нужна другая реализация, объявляю свой бин того типа, который проверяет MissingBean. Тогда стандартный вариант отступает, и его объект вообще не создаётся.

Чтобы убрать автоконфигурацию целиком, использую exclude или excludeName у @SpringBootApplication либо spring.autoconfigure.exclude. Сначала смотрю, какие ещё бины она создаёт: исключение класса шире замены одной фабрики.

  • Имена бинов при проверке по типу могут различаться. Совпадение имени и разрешение перезаписи BeanDefinition — отдельный механизм, который маскирует ошибки конфигурации.
  • @Primary управляет внедрением при нескольких кандидатах. Он не убирает второй бин, его инициализацию, потоки или подключения.
  • Исключения действуют на путь автоконфигурации. Явный @Import и component scan могут снова привести тот же класс в контекст.
Выключили payments.bank.enabled, но шлюз банка остался. Это ошибка Boot?

Сначала смотрю происхождение бина. В нашем примере свойство выключает только BankAutoConfiguration. Пользовательский @Bean из ManualConfiguration продолжает действовать. В отчёте будет отрицательное условие библиотеки, а у оставшегося бина — пользовательский метод-фабрика. Если флаг должен выключать и свой вариант, его условие нужно выразить в конфигурации этого варианта.

Как бы ты написал свой стартер для подключения к банку?

Я отделил бы автоконфигурацию от набора зависимостей, если интеграции нужны разные варианты SDK. Конфигурацию пометил бы @AutoConfiguration и записал в AutoConfiguration.imports. Условия проверяют наличие SDK, включённое свойство и отсутствие пользовательского шлюза. Стартер подключает этот модуль и обычный SDK.

У настроек будет свой префикс payments.bank, а правило включения задам явно: havingValue="true" и выбранное matchIfMissing. Для замены дам устойчивый тип BankGateway. Проверю основные комбинации: библиотека есть и отсутствует, свойство включено и выключено, пользовательский бин есть и отсутствует.

  • Необязательные типы из SDK изолирую в конфигурации с условием на классе. Метаданные читаются без его загрузки; сигнатура метода с отсутствующим типом иначе может потребовать SDK слишком рано.
  • Зависимость между автоконфигурациями выражаю через before/after у @AutoConfiguration. Это порядок описаний; инициализацию объектов задают связи между бинами.
  • Для проверки условий удобен ApplicationContextRunner, а отсутствие библиотеки моделирует FilteredClassLoader. Эти проверки ловят ошибку в договоре стартера до запуска полного сервиса.

Я объявил свой бин, но Boot создал ещё и стандартный. Где искать причину?

Я смотрю отчёт условий и точный тип, который проверяет автоконфигурация. Потом проверяю, зарегистрирована ли моя конфигурация и что возвращает её @Bean по сигнатуре. Если там Object, условие может не распознать будущий BankGateway и добавить стандартный вариант.

Ещё проверяю момент регистрации: MissingBean в обычной пользовательской конфигурации видит только уже обработанные описания. Полезно сначала понять, откуда взялись оба бина, затем исправить тип или порядок. Простое добавление @Primary уберёт неоднозначность внедрения, но оставит два объекта.

  • Условие может искать конкретную реализацию, имя, аннотацию или тип в иерархии контекстов. Проверяю критерий целиком, а не только похожее имя метода.
  • При двух кандидатах прямое внедрение обычно ломает запуск. ObjectProvider переносит эту ошибку на обращение к зависимости, как в нашем опыте.
  • После обновления зависимости сравниваю кандидатов из imports и отчёт условий. Новая библиотека может сделать положительным условие, которое раньше отсеивалось по classpath.
Поможет ли переименовать метод Object customGateway() в bankGateway()?

Тип в описании останется Object. Условие по BankGateway от этого не начнёт видеть пользовательскую роль. Зато совпадение имени создаст конфликт регистрации описаний или сделает результат зависимым от разрешённой перезаписи. Исправление — точный тип возврата, а имя можно оставить customGateway.
