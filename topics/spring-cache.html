Spring: Caching

@Cacheable превращает метод в «посмотри в кеш, а если нет — вызови и запомни». Делает это прокси вокруг бина, поэтому кеш работает только для вызовов снаружи. Ключ по умолчанию — аргументы метода, а хранилище выбирает CacheManager: карта в памяти, Caffeine или Redis. От хранилища зависит, получит ли вызывающий тот же объект или копию, есть ли срок жизни и видят ли кеш другие экземпляры сервиса. Самое трудное в кеше — не положить значение, а вовремя его убрать.

Тариф банка запрашивают на каждый платёж, хотя он меняется раз в день

Перед списанием платёжный сервис узнаёт у банка тариф: комиссию и лимиты. Запрос идёт 200 мс, а тариф меняется раз в сутки. На тысяче платежей в минуту сервис тратит на одинаковые ответы больше времени, чем на сами платежи, а банк начинает ограничивать частоту запросов.

Решение — запомнить ответ и отдавать его из памяти. Писать это вручную в каждом методе однообразно: проверить карту, вызвать банк, положить, не забыть про конкурентный доступ. Spring выносит эту обвязку в аннотации: @Cacheable, @CachePut, @CacheEvict. Механизм тот же, что у @Transactional: прокси вокруг бина.

Демо CacheDemo.java кеширует тариф банка. Метод сервиса спит 200 мс, изображая банк, и считает свои вызовы. Стек: JDK 21, Spring Boot 4.1.1, Caffeine 3.2.

cd examples/integration
./run.sh CacheDemo           # простой кеш в памяти
./run.sh CacheDemo caffeine  # Caffeine со сроком жизни

@Cacheable — прокси, который сначала смотрит в кеш

@Configuration
@EnableCaching // Без неё аннотации ниже ничего не делают.
class App {}

@Service
class TariffService {
    @Cacheable("tariffs") // Имя кеша; ключ — аргумент bank.
    public Tariff tariff(String bank) {
        calls.incrementAndGet();
        sleep(200); // Медленный запрос к банку.
        return new Tariff(bank);
    }
}

@EnableCaching регистрирует advisor, и контейнер оборачивает TariffService в CGLIB-прокси. Каждый вызов метода с аннотацией проходит CacheInterceptor: он вычисляет ключ, спрашивает кеш, и только при промахе вызывает настоящий метод.

cache manager: ConcurrentMapCacheManager
service class: TariffService$$SpringCGLIB$$0
first read: 204 ms, second read: 0 ms, calls=1

Раз кеш живёт в прокси, у него те же слепые зоны, что у транзакций. Метод quote без аннотации вызывает tariff через this, мимо прокси:

public Tariff quote(String bank) { return tariff(bank); } // this.tariff — без кеша.

s.quote("tinkoff");
s.quote("tinkoff");
quote() twice via this: calls=3

Счётчик вырос с 1 до 3: оба вызова дошли до банка. Так же кеш не работает на private методах, на final методах CGLIB-прокси и для объектов, созданных через new. Подробно о прокси и self-invocation — в AOP & Proxies.

Демо наткнулось и на вторую особенность прокси. Первая версия читала счётчик полем: s.calls.get(). Через прокси это дало NullPointerException: CGLIB-прокси — подкласс, его собственные поля не инициализированы, а вызовы методов он передаёт настоящему объекту. Состояние бина читай через методы, а не через поля прокси.

Ключ решает, какие вызовы считаются одинаковыми

По умолчанию ключ строит SimpleKeyGenerator. Без аргументов — SimpleKey.EMPTY, с одним аргументом — сам аргумент, с несколькими — SimpleKey из всех аргументов. Ключ попадает в карту, поэтому его equals и hashCode должны сравнивать по значению. Объект без них даст новый ключ на каждый вызов и вечный промах.

Явный ключ задаётся выражением SpEL. Комиссия зависит только от банка, а сумма в ключ не входит:

@Cacheable(cacheNames = "fees", key = "#bank") // amount не участвует в ключе.
public String fee(String bank, long amount) { return bank + " fee for " + amount; }

s.fee("sber", 100);
System.out.println(s.fee("sber", 500)); // Тот же ключ "sber".
fee(sber, 500) -> sber fee for 100

Вызов с суммой 500 получил ответ, посчитанный для суммы 100. Если результат зависит от аргумента, этот аргумент должен быть в ключе. Обратная ошибка — лишний аргумент в ключе, например timestamp или объект запроса целиком: кеш никогда не попадает.

Ещё одна ловушка — общий кеш для разных методов. Если tariff(String bank) и limits(String bank) кешируют в одно имя "bank", ключ sber у них совпадает, и второй метод получит результат первого чужого типа. У каждого метода своё имя кеша или ключ с префиксом: key = "'limits:' + #bank".

По умолчанию кешируется и null: «у банка нет лимита» тоже ответ. Если null значит «временно неизвестно», его не кладут через unless:

@Cacheable(cacheNames = "limits", unless = "#result == null") // null не кешируем.
public String limit(String bank) { return bank.equals("unknown") ? null : bank + " limit 1000"; }
null result twice: calls=6

Оба вызова для unknown дошли до метода. condition проверяется до вызова и решает, использовать ли кеш вообще; unless проверяется после и видит #result. Optional Spring разворачивает: в кеш кладётся значение, а пустой Optional хранится как null.

Кеш в памяти отдаёт тот же объект, Redis — новую копию

Аннотации описывают, что кешировать. Где хранить, решает CacheManager. Boot выбирает его по classpath в порядке: свой бин, JCache, Hazelcast, Couchbase, Infinispan, Redis, Caffeine, Cache2k и в конце простой ConcurrentMapCacheManager. Демо явно просит простой кеш через spring.cache.type=simple: Caffeine уже лежит в classpath, и без этой строки Boot выбрал бы его.

В кеше в памяти лежит ссылка на объект, который вернул метод. Каждый вызывающий получает тот же экземпляр. Если кто-то его изменит, изменение увидят все:

Tariff mine = s.tariff("sber");
mine.fees.add("promo -1%"); // Скидка только для одного клиента.
System.out.println("another caller sees: " + s.tariff("sber"));
System.out.println("same object: " + (mine == s.tariff("sber")));
another caller sees: sber [1.5%, promo -1%]
same object: true

ConcurrentMapCacheManagerНет: растёт без пределаНетСсылку
CaffeinemaximumSize, expireAfterWriteНетСсылку
Redisspring.cache.redis.time-to-liveДаКопию после десериализации

Простой кеш не годится для прода: у него нет ни срока жизни, ни ограничения размера. Кеш по номеру платежа на нём медленно съест heap. Caffeine задаёт и то, и другое строкой настроек:

spring:
  cache:
    type: caffeine
    caffeine:
      spec: maximumSize=1000,expireAfterWrite=1s # 1 секунда только ради демо.
calls after 2 reads: 1
calls after TTL:     2

Через секунду значение истекло, и третье чтение снова пошло в банк. Redis-кеш общий для всех экземпляров сервиса и переживает их перезапуск, но каждый доступ — сетевой вызов и сериализация. По умолчанию RedisCacheManager использует сериализацию JDK; в проде её заменяют на JSON, иначе любое изменение класса ломает чтение старых записей. Ключи в Redis выглядят как tariffs::sber. Сам Redis разобран в соседнем разделе о базах данных.

Убрать значение вовремя сложнее, чем положить

Банк прислал новый тариф. Кеш должен об этом узнать. Есть три инструмента. @CacheEvict удаляет запись, и следующий вызов пойдёт в банк. @CachePut всегда вызывает метод и кладёт результат в кеш — так обновляют значение сразу. Срок жизни ограничивает время, в течение которого кеш может врать, даже если инвалидацию забыли.

@CacheEvict(cacheNames = "tariffs", key = "#bank")
public void evict(String bank) {}

s.evict("sber");
System.out.println("after evict: " + s.tariff("sber")); // Новый объект из банка.
after evict: sber [1.5%]

Скидка из прошлого шага пропала: метод создал новый Tariff. @CacheEvict(allEntries = true) очищает весь кеш. beforeInvocation = true удаляет до вызова метода, чтобы запись ушла, даже если метод упал.

Инвалидация и транзакция

Если тариф хранится в своей базе, обновление выглядит так: транзакция меняет строку, метод с @CacheEvict удаляет запись. Удаление срабатывает при выходе из метода, а коммит может случиться позже, во внешней транзакции. В этот промежуток другой поток получает промах, читает из базы старый тариф (новый ещё не закоммичен) и кладёт его в кеш. Коммит проходит, а в кеше до конца TTL лежит старое значение.

Защита — удалять после коммита. TransactionAwareCacheManagerProxy откладывает put и evict до коммита; у RedisCacheManager для этого есть transactionAware(). Другой вариант — @TransactionalEventListener(phase = AFTER_COMMIT), который чистит кеш после события об изменении тарифа.

Несколько экземпляров сервиса

Локальный Caffeine живёт в каждом pod-е отдельно. @CacheEvict на pod-е, который принял обновление, очистит только его кеш, а два других будут отдавать старый тариф до истечения TTL. Варианты: общий Redis-кеш, рассылка события об инвалидации всем экземплярам через брокер или короткий TTL, если минута устаревших данных приемлема. Для тарифа, который меняется раз в день, обычно хватает TTL. Для остатка на счёте локальный кеш недопустим вовсе.

При одновременном промахе метод вызывают все, если не попросить sync

Тариф истёк в 9:00, и в эту же секунду пришли десять платежей. Все десять видят промах, и все десять идут в банк. Это cache stampede: в момент истечения популярного ключа нагрузка на источник резко прыгает, а именно её кеш должен был снимать. Демо запускает десять потоков одновременно на пустой ключ:

@Cacheable(cacheNames = "tariffs-sync", sync = true) // Один считает, остальные ждут.
public Tariff tariffSync(String bank) { /* те же 200 мс */ }

// 10 потоков одновременно стартуют на пустом кеше.
System.out.println("stampede, no sync: calls=" + stampede(s, false));
System.out.println("stampede, sync=true: calls=" + stampede(s, true));
stampede, no sync: calls=10
stampede, sync=true: calls=1

С sync = true кеш получает значение через Cache.get(key, valueLoader). Первый поток вычисляет значение, остальные ждут его результата. У ConcurrentMapCacheManager и Caffeine это блокировка на ключ внутри JVM. Ограничения: sync нельзя сочетать с unless и с несколькими кешами на одном методе.

Синхронизация действует в пределах одного экземпляра. Десять pod-ов дадут десять вызовов банка даже с sync. Для общего кеша спасают другие приёмы: разброс TTL случайной добавкой, чтобы ключи не истекали одновременно, фоновое обновление до истечения (refreshAfterWrite в Caffeine) или распределённая блокировка.

Кеш — не источник правды. Его в любой момент можно очистить, и сервис должен работать, только медленнее. Если после перезапуска Redis сервис падает от нагрузки на банк, кеш стал частью ёмкости системы, и для этого нужен свой план: прогрев, ограничение частоты, деградация.

  • @Cacheable работает через прокси: вызов через this, private и final методы идут мимо кеша.
  • Ключ по умолчанию — аргументы метода. Аргумент, от которого зависит результат, обязан входить в ключ.
  • Кеш в памяти отдаёт ссылку на общий объект, Redis — копию. Кешируй неизменяемые объекты.
  • Простой ConcurrentMap-кеш растёт без предела; в проде — Caffeine с размером и TTL или Redis.
  • Удаляй после коммита и помни, что локальный evict чистит только один экземпляр. sync=true защищает от одновременного промаха в пределах JVM.

На собеседовании

Как работает @Cacheable и почему он иногда не кеширует?

@EnableCaching добавляет advisor, и Spring оборачивает бин в прокси. При вызове CacheInterceptor вычисляет ключ из аргументов, ищет значение в кеше и вызывает настоящий метод только при промахе, а результат кладёт в кеш.

Не работает, если вызов не проходит через прокси: из того же класса через this, на private или final методах, для объекта, созданного через new. И если забыли @EnableCaching — тогда аннотации просто игнорируются.

  • Ключ по умолчанию строит SimpleKeyGenerator; у объекта-ключа должны быть equals и hashCode по значению.
  • condition проверяется до вызова, unless — после и видит #result; null кешируется по умолчанию.
  • Два метода с одним именем кеша и одинаковыми аргументами перетирают друг друга.
Почему кеш курсов валют почти никогда не попадает? 
@Cacheable("rates")
public BigDecimal rate(String from, String to, Instant at) { /* запрос в ЦБ */ }

// Вызывается так:
rate("USD", "RUB", Instant.now());

Instant.now() входит в ключ и каждый раз разный, поэтому каждый вызов — новый ключ. Кеш только растёт и никогда не попадает. Курс меняется раз в день: ключом должна быть дата, например key = "#from + #to + T(java.time.LocalDate).ofInstant(#at, T(java.time.ZoneOffset).UTC)", или метод должен принимать LocalDate.

Какой CacheManager выбрать и чем локальный кеш отличается от Redis?

Локальный кеш вроде Caffeine живёт в памяти экземпляра: он быстрый, умеет TTL и ограничение размера, но у каждого pod-а свой, и инвалидация на одном не видна другим. Redis общий для всех экземпляров и переживает их перезапуск, но каждое обращение — сеть и сериализация.

Простой ConcurrentMapCacheManager годится только для тестов: у него нет срока жизни и предела размера.

  • Локальный кеш отдаёт ссылку на общий объект, Redis — копию; изменение результата из локального кеша портит данные всем.
  • Для Redis сериализацию JDK заменяют JSON, иначе изменение класса ломает чтение старых записей.
  • Двухуровневый кеш (Caffeine поверх Redis) ускоряет чтение, но удваивает проблему инвалидации.

Как правильно инвалидировать кеш при изменении данных?

@CacheEvict удаляет запись, @CachePut обновляет её результатом метода, TTL ограничивает время устаревания, если инвалидацию пропустили. Обычно сочетаю явную инвалидацию с TTL как страховкой.

Важно удалять после коммита. Если evict случился до коммита, другой поток успеет прочитать старое значение из базы и положить обратно в кеш.

  • TransactionAwareCacheManagerProxy или transactionAware() у RedisCacheManager откладывают put и evict до коммита.
  • С локальным кешем на нескольких экземплярах evict нужно разослать всем, например событием через брокер.
  • Для данных, где устаревание недопустимо, вроде остатка на счёте, кеш не используют или кешируют только неизменяемые части.

Что такое cache stampede и как от него защищаются?

Популярный ключ истекает, и все одновременные запросы видят промах и идут в источник. Нагрузка на базу или внешний сервис резко прыгает именно тогда, когда кеш должен был её снимать.

В Spring помогает @Cacheable(sync = true): первый поток вычисляет значение, остальные ждут его. В демо десять потоков без sync вызвали метод десять раз, с sync — один.

  • sync работает в пределах одной JVM; на нескольких экземплярах нужны разброс TTL, фоновое обновление или распределённая блокировка.
  • sync нельзя сочетать с unless и несколькими кешами на методе.
  • refreshAfterWrite в Caffeine обновляет значение фоном, отдавая старое, пока новое не готово.
