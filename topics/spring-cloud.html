Spring Cloud

Spring Cloud — набор библиотек для сервиса, у которого есть соседи. Discovery и LoadBalancer превращают имя сервиса в адрес конкретного экземпляра. OpenFeign превращает Java-интерфейс в HTTP-клиент. Circuit breaker перестаёт звать соседа, который часто падает, и отдаёт запасной ответ. Config Server раздаёт настройки, Gateway принимает внешний трафик. Половину этих задач сегодня решает Kubernetes, поэтому главный вопрос на собеседовании — какой слой за что отвечает.

У платёжного сервиса появились соседи, и каждый может упасть

Пока платёжный сервис один, адрес базы и банка записан в настройках, а сбой виден сразу. Потом сервис разделяют: банк-шлюз, антифрод, уведомления, у каждого несколько экземпляров. Появляются новые вопросы. По какому адресу звать соседа, если его экземпляры появляются и исчезают? Как не повесить все потоки, если сосед отвечает минуту? Где хранить настройки двадцати сервисов?

Spring Cloud — набор проектов, которые отвечают на эти вопросы в коде приложения. Версии выходят поездом (release train) и привязаны к Boot: ветка 2025.1 «Oakwood» сделана для Boot 4.0. Демо этой темы запущено на Boot 4.1.1 со Spring Cloud 2025.1.3 и заработало. Официальная ветка для Boot 4.1 — 2026.0; на момент проверки в Maven Central был только её milestone. Несовместимую пару Spring Cloud обычно ловит при старте: compatibility verifier останавливает приложение с объяснением.

Демо CloudDemo.java поднимает в одной JVM два экземпляра «банка» на случайных портах и платёжный сервис с Feign-клиентом, балансировкой и circuit breaker. Стек: JDK 21, Spring Boot 4.1.1, Spring Cloud 2025.1.3, Resilience4j 2.3.

cd examples/cloud
./run.sh CloudDemo # Внешние сервисы не нужны: discovery задан списком адресов.

Discovery и LoadBalancer превращают имя сервиса в адрес экземпляра

Код платёжного сервиса знает только имя соседа: bank. DiscoveryClient знает, какие экземпляры с этим именем сейчас живы. Источник списка — реестр вроде Eureka или Consul, API Kubernetes или, как в демо, просто список в настройках. LoadBalancer на каждый вызов выбирает один экземпляр из списка, по умолчанию по кругу.

spring:
  cloud:
    discovery:
      client:
        simple:
          instances:
            bank: # Имя сервиса и его экземпляры; в проде список даёт реестр.
              - uri: http://localhost:51001
              - uri: http://localhost:51002
== both banks healthy
p-1 -> bank-2 charged p-1
p-2 -> bank-1 charged p-2
p-3 -> bank-2 charged p-3
p-4 -> bank-1 charged p-4

Порты в настройке выше для примера, демо подставляет случайные. Балансировка здесь клиентская: решение принимает платёжный сервис, а не отдельный балансировщик. Это удобно, когда сеть плоская и экземпляры регистрируются сами. Цена — каждый клиент должен знать о здоровье экземпляров, и это важно в шаге 4.

В Kubernetes эту задачу обычно уже решает платформа. Service bank получает постоянное DNS-имя, а kube-proxy раскладывает соединения по живым pod-ам, которых отбирает readiness probe из Actuator. Клиенту достаточно адреса http://bank, и Spring Cloud Discovery не нужен. Его берут, когда нужна своя логика выбора: по зоне, по весу, по версии.

OpenFeign делает из интерфейса HTTP-клиент, но новый код пишут на HTTP-интерфейсах

// name — логическое имя сервиса; адрес выберет LoadBalancer.
@FeignClient(name = "bank", fallback = BankFallback.class)
interface BankClient {
    @GetMapping("/charge")
    String charge(@RequestParam("id") String id);
}

@EnableFeignClients(clients = BankClient.class)
class PaymentApp {}

Feign строит реализацию интерфейса при старте: читает аннотации Spring MVC, на вызов собирает запрос, через LoadBalancer выбирает экземпляр, отправляет, разбирает ответ. Код сервиса вызывает bank.charge("p-1") как обычный метод. Ошибки HTTP становятся FeignException.

Spring Cloud OpenFeign объявлен завершённым по функциям: новых возможностей не будет, только исправления. Для нового кода Spring рекомендует HTTP-интерфейсы из самого Framework: @HttpExchange поверх RestClient, разобранные в HTTP Clients. Идея та же — интерфейс вместо кода, но без отдельной библиотеки, и LoadBalancer к ним подключается через @LoadBalanced RestClient.Builder.

Таймауты в Feign задают явно: spring.cloud.openfeign.client.config.bank.read-timeout. Значения по умолчанию рассчитаны на терпеливого клиента — секунды и десятки секунд, а платёж ждать столько не может. Медленный сосед без таймаута забирает потоки сервиса, и проблема одного сервиса превращается в проблему всех, кто его зовёт.

Circuit breaker отсекает соседа целиком, даже здоровые экземпляры

Bank-2 начал отвечать 503. Каждый второй платёж теперь падает, а сервис продолжает его звать. Circuit breaker считает результаты последних вызовов. Если доля ошибок выше порога, он открывается: следующие вызовы сразу получают отказ или fallback, без похода в сеть. Через паузу он пропускает несколько пробных вызовов (half-open) и по их результату закрывается или снова открывается.

spring.cloud.openfeign.circuitbreaker.enabled: true # Обернуть Feign-клиенты в breaker.
resilience4j.circuitbreaker.configs.default:
  sliding-window-size: 4                    # Считать последние 4 вызова.
  minimum-number-of-calls: 4
  failure-rate-threshold: 50                # Открыть при 50% ошибок.
  wait-duration-in-open-state: 1s           # Через 1 с — пробные вызовы.
  permitted-number-of-calls-in-half-open-state: 2
== bank-2 returns 503
p-5 -> fallback: queued p-5  [CLOSED]
p-6 -> bank-1 charged p-6  [CLOSED]
p-7 -> fallback: queued p-7  [OPEN]
p-8 -> fallback: queued p-8  [OPEN]
p-9 -> fallback: queued p-9  [OPEN]
p-10 -> fallback: queued p-10  [OPEN]
p-11 -> fallback: queued p-11  [OPEN]
p-12 -> fallback: queued p-12  [OPEN]
breaker name: BankClientchargeString
bank hits while broken: {bank-1=1, bank-2=2}
== after 1.1 s, bank-2 still broken
p-13 -> bank-1 charged p-13  [HALF_OPEN]
p-14 -> fallback: queued p-14  [OPEN]
p-15 -> fallback: queued p-15  [OPEN]

Счётчик попаданий подтверждает: пока bank-2 сломан, восемь платежей сделали всего три запроса — bank-1 получил один, bank-2 два. Breaker защитил сломанный сервис от лишней нагрузки, но заодно отрезал здоровый экземпляр. Он связан не с экземпляром, а с методом клиента: имя BankClientchargeString собрано из интерфейса и сигнатуры.

Отсюда несколько правил. Breaker не заменяет проверку здоровья экземпляров: балансировщик должен перестать слать запросы на bank-2 сам. Для этого есть HealthCheckServiceInstanceListSupplier, повтор на другом экземпляре через Spring Cloud LoadBalancer retry или реестр, который снимает больной экземпляр. А fallback должен быть честным. В демо он не делает вид, что платёж прошёл, а ставит его в очередь — клиент получит «обрабатывается», а не ложное «оплачено».

Fallback — это способ вернуть пользователю успешный ответ, когда сосед упал.

Fallback возвращает то, что честно можно сказать без соседа: кешированный тариф, «платёж в очереди», пустой список рекомендаций. Fallback «APPROVED» для списания превращает сбой банка в пропавшие деньги.

Config Server раздаёт настройки, Gateway принимает внешний трафик

Эти две части не запускались в демо: им нужны git-репозиторий настроек и отдельный сервер. Описание по документации Spring Cloud.

Spring Cloud Config — сервер, который отдаёт настройки сервисам из git-репозитория или хранилища секретов. Сервис подключает его строкой spring.config.import=configserver:http://config:8888, и настройки попадают в Environment как ещё один источник со своим приоритетом из Configuration & Profiles. Плюсы — история изменений в git и одно место для настроек всех сервисов. Изменение на лету даёт @RefreshScope: бины в этой области пересоздаются после события обновления, а @ConfigurationProperties перепривязываются. Обычный Boot так не умеет. Обратная сторона — Config Server становится зависимостью старта: без него сервис не поднимется, если импорт не помечен optional:.

Spring Cloud Gateway — входная точка для внешних запросов. Он маршрутизирует /api/payments/** в сервис payments, проверяет JWT, ограничивает частоту запросов, добавляет заголовки трассировки. Есть два варианта: на WebFlux и Server MVC на обычных сервлетах и виртуальных потоках. Gateway удобен, когда правила маршрутизации — часть кода команды и их тестируют вместе с сервисами.

Каждую задачу решает один слой: приложение или платформа

В Kubernetes Spring Cloud чаще всего нужен частично. Discovery, Config Server и Gateway обычно заменяет платформа. Circuit breaker, таймауты и fallback остаются в коде: только приложение знает, что честно ответить без соседа и какой таймаут допустим для платежа.

Главная опасность — сделать одно и то же на двух уровнях. Если клиент повторяет вызов три раза, service mesh — ещё три, а gateway — ещё три, один пользовательский запрос в худшем случае становится двадцатью семью запросами к уже перегруженному банку. Это retry storm: повторы добивают сервис, который пытался восстановиться. Повторы, таймауты и breaker настраивают в одном месте и проверяют, что сумма таймаутов вложенных вызовов меньше таймаута внешнего.

  • Discovery даёт список экземпляров по имени сервиса, LoadBalancer выбирает один на вызов, по умолчанию по кругу.
  • OpenFeign завершён по функциям; новый декларативный клиент — @HttpExchange поверх RestClient.
  • Circuit breaker считает ошибки по клиенту и при пороге отсекает весь сервис, даже здоровые экземпляры.
  • Fallback возвращает честный ответ без соседа, а не фальшивый успех.
  • В Kubernetes discovery, настройки и вход обычно берёт платформа; повторы и breaker настраивают в одном слое.

На собеседовании

Как работает circuit breaker и что такое half-open?

Breaker считает результаты последних вызовов в скользящем окне. Пока доля ошибок ниже порога, он закрыт и пропускает вызовы. Когда порог превышен, он открывается: вызовы сразу получают отказ или fallback и не нагружают больной сервис. Через заданную паузу он переходит в half-open и пропускает несколько пробных вызовов. Если пробы успешны — закрывается, если нет — снова открывается.

В Spring это Resilience4j через Spring Cloud CircuitBreaker; для Feign-клиентов он включается одной настройкой.

  • Breaker привязан к клиенту и методу, а не к экземпляру: в демо он отрезал и здоровый bank-1.
  • Он не заменяет таймауты: медленный вызов без таймаута держит поток, и breaker его не прервёт; нужны TimeLimiter или таймаут клиента.
  • Окно может считаться по числу вызовов или по времени; минимальное число вызовов защищает от открытия по одной ошибке.

Как один сервис находит другой и нужен ли для этого Spring Cloud в Kubernetes?

В Spring Cloud клиент знает имя сервиса, DiscoveryClient получает список живых экземпляров из реестра — Eureka, Consul или API Kubernetes, — а LoadBalancer выбирает один экземпляр на каждый вызов. Это клиентская балансировка.

В Kubernetes обычно хватает Service: у него постоянное DNS-имя, а kube-proxy раскладывает соединения по pod-ам, прошедшим readiness probe. Тогда клиенту нужен только адрес http://bank, и Spring Cloud Discovery лишний.

  • Клиентская балансировка нужна для своей логики выбора: зона, вес, версия, sticky-сессии.
  • Kube-proxy балансирует соединения, а не запросы; при долгих HTTP/2- и gRPC-соединениях нагрузка распределяется неровно.
  • Без проверки здоровья клиентский балансировщик продолжает слать запросы на сломанный экземпляр.

Где настраивать повторы и таймауты между сервисами?

В одном слое. Если повторы есть в клиенте, в service mesh и в gateway, они перемножаются: три уровня по три попытки — до 27 запросов на один пользовательский. Это retry storm, который добивает восстанавливающийся сервис.

Таймауты строю сверху вниз: внешний запрос платежа ждёт, например, 3 секунды, значит вызов банка с повтором должен уложиться меньше чем в 3 секунды. Повторяю только идемпотентные операции или с ключом идемпотентности.

  • Повторы с экспоненциальной паузой и случайным разбросом, чтобы клиенты не били синхронно.
  • Retry budget ограничивает долю повторов от общего трафика вместо фиксированного числа попыток.
  • Breaker ставят снаружи повторов: когда он открыт, повторы не выполняются вовсе.
Что опасного в этом fallback? 
@Component
class BankFallback implements BankClient {
    public ChargeResult charge(ChargeRequest r) {
        return new ChargeResult(r.paymentId(), "APPROVED"); // Чтобы клиент не видел ошибку.
    }
}

При открытом breaker все списания «проходят», хотя банк денег не списал. Сервис отгрузит товар без оплаты, а сверка найдёт расхождение только ночью. Fallback для платежа должен возвращать честный статус — «в обработке» с постановкой в очередь — или ошибку, которую увидит клиент.
