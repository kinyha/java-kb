Spring Boot: Configuration & Profiles

Платёжный сервис получает настройки из нескольких мест: файла в приложении, файлов окружения и параметров запуска. Boot загружает их в Environment и для каждого ключа выбирает значение из источника с большим приоритетом. Затем связывает нужную группу настроек с объектом, который получает сервис. Профиль меняет участвующие файлы и бины, а проверка настроек останавливает запуск, если сервис собран неправильно. При неожиданном поведении сначала найди источник значения, затем проверь, что попало в объект настроек.

Один сервис получает разные настройки из нескольких источников

Платёжный сервис ждёт ответ банка. На локальной машине можно подождать две секунды. В проде общий бюджет запроса меньше, поэтому команда записала в application-prod.yaml таймаут 600ms. После деплоя часть платежей всё равно обрывается уже через 250ms.

Код и файл правильные. В параметрах контейнера остался аргумент --payments.bank.timeout=250ms от прошлого эксперимента. Он перекрыл профильный файл. Изменение ещё одного YAML не исправит ситуацию: сервис берёт значение из другого места.

Настройки позволяют запускать один и тот же артефакт в разных окружениях. Но теперь важно понимать две вещи: какое значение выбрано и как оно попало в работающий объект. Эти вопросы связаны, хотя решаются на разных этапах. Сначала Boot загружает источники, затем контейнер создаёт сервисы и связывает их настройки.

Сквозной пример — настройки банка: адрес, таймаут, число попыток и каналы платежей. Демо использует JDK 21, Spring Boot 4.1.1 и Spring Framework 7.0.9. Полный код и файлы лежат в ConfigDemo.java и examples/boot. Банк не вызывается: мы наблюдаем настройки, с которыми сервис начал бы работу.

Environment выбирает победителя по приоритету источника

Environment хранит упорядоченные источники свойств, PropertySource. При запросе ключа оно ищет значение в порядке приоритета. Первый источник, который даёт значение, определяет результат. Значения из остальных источников остаются доступны для диагностики, но для этого запроса они уже проиграли.

Это выбор по каждому ключу. Переменная окружения с таймаутом не заменяет весь YAML. Адрес банка может прийти из файла, таймаут — из переменной, число попыток — из профильного файла. Так один объект настроек собирается из нескольких слоёв.

От меньшего приоритета к большемуЧто это даёт
SpringApplication.setDefaultPropertiesЗапасные значения, которые перекрывает любой обычный источник
@PropertySourceИсточник пользовательской конфигурации; появляется во время refresh

Почему JSON побеждает переменную окружения, хотя сам может быть записан в переменной? Boot отдельно разбирает SPRING_APPLICATION_JSON и помещает его свойства в источник с большим приоритетом. Значение payments.bank.timeout из этого источника побеждает обычную PAYMENTS_BANK_TIMEOUT. Аргументы запуска находятся ещё выше.

В демо профильный файл задаёт 600ms. Проверим три запуска. Ниже из каждого настоящего вывода оставлены строки timeout и origin: последнее поле показывает происхождение победившего значения.

cd examples/boot
PAYMENTS_BANK_TIMEOUT=900ms ./run.sh ConfigDemo --spring.profiles.active=prod
# Обычная переменная побеждает профильный файл.
timeout=900ms
origin=System Environment Property "PAYMENTS_BANK_TIMEOUT"
PAYMENTS_BANK_TIMEOUT=900ms \
SPRING_APPLICATION_JSON='{"payments":{"bank":{"timeout":"500ms"}}}' \
./run.sh ConfigDemo --spring.profiles.active=prod
# JSON разобран в отдельный источник с большим приоритетом.
timeout=500ms
origin=System Environment Property "SPRING_APPLICATION_JSON"
PAYMENTS_BANK_TIMEOUT=900ms \
SPRING_APPLICATION_JSON='{"payments":{"bank":{"timeout":"500ms"}}}' \
./run.sh ConfigDemo --spring.profiles.active=prod --payments.bank.timeout=250ms
# Аргумент перекрывает и обычную переменную, и JSON.
timeout=250ms
origin="payments.bank.timeout" from property source "commandLineArgs"

Boot по умолчанию добавляет аргументы -- в Environment. Приложение может выключить это через setAddCommandLineProperties(false). JSON со значением null также не стирает нижнее значение: при разрешении свойства null считается отсутствием. В тестах есть дополнительные источники с ещё большим приоритетом; их порядок разобран в Spring Testing.

Профиль добавляет конфигурацию, а не отдельное приложение

Профиль — именованное условие для загрузки настроек и регистрации бинов. При prod остаётся то же приложение и тот же контейнер, но Boot дополнительно читает профильные файлы. Аннотация @Profile позволяет тем же именем включить нужную реализацию бина. Эти два применения профиля работают вместе, хотя сам профиль не создаёт новый контекст.

Сначала загружаются обычные файлы внутри артефакта, затем профильные внутри него. Выше стоят обычные внешние файлы, ещё выше — внешние профильные. Поэтому внешний application.yaml способен перекрыть application-prod.yaml из jar. У нескольких активных профилей в пределах одной группы расположений выигрывает последний: prod,live даёт файлу live перекрыть prod.

Обычный поиск включает корень classpath и его /config, текущую директорию, ./config/ и непосредственные подпапки ./config/*/. Демо задаёт своё расположение classpath:/config-demo/, чтобы не зависеть от файлов на твоей машине. В этих опытах classpath играет ту же роль, что файлы внутри упакованного приложения.

# config-demo/application.yaml: базовые настройки.
payments:
  bank:
    url: https://bank.test
    timeout: 2s
    max-attempts: 2
    channels: [card, sbp]
    rules:
      card: 2
      sbp: 1
--- # В том же физическом файле начинается второй документ.
spring:
  config:
    activate:
      on-profile: sandbox # Документ участвует только при активном sandbox.
payments:
  bank:
    url: https://sandbox.bank.test
    timeout: 100ms

YAML разворачивается в ключи вроде payments.bank.timeout. В многодокументном файле каждый документ добавляется отдельно; нижний активный документ перекрывает предыдущий. Условие spring.config.activate.on-profile выбирает документ по уже активным профилям. Оно само профиль не включает.

# config-demo/application-prod.yaml: добавляется поверх обычного файла.
payments:
  bank:
    timeout: 600ms
    max-attempts: 3
    channels: [card] # Список заменяется целиком: sbp исчезнет из channels.
    rules:
      card: 5 # Map объединяется по ключам: старое правило sbp остаётся.
./run.sh ConfigDemo --spring.profiles.active=prod
# Ни переменная таймаута, ни JSON в этом запуске не заданы.
profiles=[prod]
url=https://bank.test
timeout=600ms
maxAttempts=3
channels=[card]
rules={card=5, sbp=1}

Здесь видно различие между перекрытием списка и map. В новой конфигурации список каналов состоит только из card. В map правило card изменилось, а sbp осталось из базового файла. Эти правила связывания коллекций важны при профилях и при любом переопределении с большим приоритетом.

./run.sh ConfigDemo --spring.profiles.active=sandbox
# Подключается второй документ обычного YAML, файл prod не участвует.
profiles=[sandbox]
url=https://sandbox.bank.test
timeout=100ms
# config-demo/external/application.yaml: файл на диске вне classpath.
payments:
  bank:
    timeout: 800ms
./run.sh ConfigDemo --spring.profiles.active=prod \
  --spring.config.additional-location=file:./config-demo/external/
# Добавленная внешняя директория перекрывает classpath, включая его prod-файл.
timeout=800ms
origin=URL [file:config-demo/external/application.yaml] - 3:14

Включение профилей и расположение файлов решают разные задачи

spring.profiles.active задаёт активные профили и перекрывается по обычному приоритету. spring.profiles.include добавляет общие профили; они включаются перед явно активными. spring.profiles.group.production: [prod, audit] позволяет включить связанный набор одним именем production. Если активных профилей нет, действует набор по умолчанию с именем default; его можно изменить через spring.profiles.default.

В документе с on-profile: prod можно включить audit через spring.profiles.include.

active, default, include и group задают в обычном документе. Они запрещены в profile-specific файле и в документе, активируемом через on-profile. Набор профилей определяет, какие документы читать; активируемый документ не должен одновременно переопределять этот набор.

spring.config.location заменяет стандартные расположения поиска. spring.config.additional-location дополняет их, а spring.config.import подключает конкретный ресурс. Директорию в location записывают с завершающим /. Эти настройки нужны до чтения файлов, поэтому место поиска передают через аргумент, системное свойство JVM или переменную ОС.

Импортированный файл перекрывает документ, который его подключил. Несколько imports обрабатываются по порядку; поздний перекрывает ранний. В примере override.yaml содержит payments.bank.timeout: 700ms; его подключение даёт следующий результат.

./run.sh ConfigDemo --spring.config.import=classpath:/config-demo/override.yaml
# Базовый таймаут 2s перекрыт импортируемым файлом.
timeout=700ms
origin=class path resource [config-demo/override.yaml] - 3:14
Под капотом: группы расположений и приоритет форматов

В сложном spring.config.location запятая отделяет последовательные группы расположений, а точка с запятой объединяет расположения на одном уровне. От этого зависит, как чередуются файлы нескольких профилей. Правило «последний профиль победит» применяют внутри одной группы, а затем учитывают приоритет следующей группы.

Если в одном расположении лежат и application.properties, и YAML, приоритет выше у properties. Выбери один формат для приложения: скрытое дублирование файлов затрудняет расследование. Обычный @PropertySource не загружает YAML и многодокументный Config Data тем же способом; для них используй механизм Boot.

ConfigurationProperties связывает настройки в проверяемый объект

Сервису нужен таймаут типа Duration, а не строка с неопределённой единицей. Адрес банка удобно хранить как URI, число попыток — как int. @ConfigurationProperties объединяет эти поля под одним префиксом. Binder читает выбранные значения, преобразует типы и создаёт объект настроек.

У record с единственным конструктором Boot использует связывание через конструктор. Аннотация сама по себе не регистрирует бин. В демо он подключён через @EnableConfigurationProperties(PaymentSettings.class); в приложении можно использовать @ConfigurationPropertiesScan. Обычное создание record через component scan направило бы его параметры в механизм DI, поэтому для такого объекта нужен именно способ регистрации настроек.

@Validated // Запускает Bean Validation после связывания.
@ConfigurationProperties("payments.bank") // Берём только эту группу ключей.
public record PaymentSettings(
        @NotNull URI url,
        @NotNull Duration timeout,
        @Min(1) int maxAttempts, // Ноль попыток запрещён при запуске.
        List<String> channels,
        Map<String, Integer> rules) {}

@SpringBootConfiguration(proxyBeanMethods = false)
@EnableConfigurationProperties(PaymentSettings.class) // Регистрирует record и связывание.
@Import(ScalarValues.class) // Отдельный пример @Value ниже.
class Application {}

var settings = context.getBean(PaymentSettings.class);
System.out.println("timeout=" + settings.timeout().toMillis() + "ms");
System.out.println("maxAttempts=" + settings.maxAttempts());

Демо запускает этот класс через SpringApplication, задаёт spring.config.location=classpath:/config-demo/ и передаёт аргументы запуска. Веб-сервер здесь не нужен. YAML читает SnakeYAML; валидацию выполняет Hibernate Validator. Зависимости зафиксированы через BOM Boot в pom.xml.

Binder поддерживает relaxed binding: Java-параметр maxAttempts связывается с max-attempts в YAML. В файлах и параметрах запуска используй каноническое имя с маленькими буквами и дефисами. Для переменной ОС точки заменяют на подчёркивания, дефисы убирают и имя переводят в верхний регистр: payments.bank.max-attempts становится PAYMENTS_BANK_MAXATTEMPTS.

Для Duration удобнее явно писать единицу: 250ms, 2s или ISO-форму PT2S. Число без единицы по умолчанию означает миллисекунды. @DurationUnit меняет единицу для таких чисел. В нашем record этой аннотации нет, поэтому следующий аргумент означает четверть секунды.

./run.sh ConfigDemo --payments.bank.timeout=250
# Без суффикса Binder использует миллисекунды.
timeout=250ms

Value разрешает отдельное выражение, Properties собирает структуру

@Value удобно для одного значения или выражения SpEL. Оно тоже умеет преобразовать значение в нужный тип. Но набор связанных параметров, вложенные структуры, проверки и подсказки IDE проще держать в @ConfigurationProperties. Его Binder поддерживает структуру и relaxed binding; SpEL в значениях настроек он не вычисляет.

class ScalarValues {
    @Value("${payments.bank.max-attempts:-1}")
    int canonical; // Каноническое имя видит YAML с max-attempts.

    @Value("${payments.bank.maxAttempts:-1}")
    int camel; // Для этого placeholder YAML с max-attempts не подходит.
}

// В базовом YAML max-attempts=2. ScalarValues зарегистрирован через @Import.
var values = context.getBean(ScalarValues.class);
System.out.println("value canonical=" + values.canonical + ", camel=" + values.camel);
./run.sh ConfigDemo # Базовый YAML, без активных профилей.
value canonical=2, camel=-1

У @Value есть ограниченная поддержка разных написаний в Boot, поэтому утверждение «оно вообще не знает relaxed binding» слишком грубое. Канонический placeholder даёт ожидаемую совместимость. Значение -1 здесь — запасное из выражения, а не результат чтения YAML. Для обязательной настройки незаметный запасной параметр способен скрыть опечатку.

Чтобы IDE подсказывала имена, типы и описание полей, при сборке подключают spring-boot-configuration-processor. Он генерирует META-INF/spring-configuration-metadata.json из классов настроек. Например, в Maven процессор можно явно указать в annotationProcessorPaths компилятора:

<annotationProcessorPaths>
  <path>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-configuration-processor</artifactId>
    <version>4.1.1</version> <!-- Та же версия, что у Boot приложения. -->
  </path>
</annotationProcessorPaths>

Метаданные помогают человеку написать конфигурацию. Во время запуска Binder работает по типам класса настроек; сгенерированный файл не включает валидацию и не регистрирует бин. Для стороннего изменяемого объекта можно поставить @ConfigurationProperties на метод @Bean: его уже созданные поля связываются через доступные свойства.

Настройка не применилась: сначала найди, откуда пришло значение

Сервис всё ещё ждёт две секунды, хотя ты записал 250ms. Сначала проверь активные профили и сам ключ в Environment. Если там старое значение, ищи загрузку файла, написание ключа и перекрывающий источник. Если Environment уже видит новое значение, а объект настроек держит старое, смотри момент связывания и объект, который реально получил сервис.

В демо поле origin читается из того же порядка источников, который использует связывание настроек. Для файла Boot хранит ресурс и строку. Для аргумента и переменной ОС — источник. Это помогает отделить «файл не прочитан» от «файл прочитан и проиграл».

var name = ConfigurationPropertyName.of("payments.bank.timeout");
for (var source : ConfigurationPropertySources.get(context.getEnvironment())) {
    var property = source.getConfigurationProperty(name);
    if (property != null) {
        System.out.println("origin=" + property.getOrigin()); // Файл и строка либо параметр запуска.
        break; // Первое найденное значение победило, как при связывании.
    }
}

В реальном сервисе /actuator/env помогает исследовать источники, а /actuator/configprops — связанные объекты настроек. Отчёт --debug объясняет условия автоконфигураций: почему конкретный бин включён или выключен. Это другая часть расследования. Доступ к диагностическим endpoints и скрытие значений разобраны в Actuator.

Ошибка преобразования и неправильный допустимый тип — разные сбои

Строка oops не превращается в Duration. Здесь Binder останавливается на преобразовании. Значение 0 превращается в int без проблем, но нарушает @Min(1). Здесь запуск останавливает Bean Validation. Приложение в обоих случаях собрано неправильно, но исправлять нужно разные причины.

./run.sh ConfigDemo --payments.bank.timeout=oops
# Конвертер не смог получить Duration.
startup=ConfigurationPropertiesBindException
binding=conversion
./run.sh ConfigDemo --payments.bank.max-attempts=0
# Тип int получен, затем нарушено ограничение Min(1).
startup=ConfigurationPropertiesBindException
binding=validation
maxAttempts: must be greater than or equal to 1

Демо перехватывает ожидаемые ошибки и печатает их вид. Сервис с такими настройками запуск не завершил; успешный код завершения учебной программы означает только, что она показала сбой. В открытом коде record видны все ограничения, которые объясняют результат.

Валидация начинается с @Validated на классе настроек и доступного провайдера Bean Validation. Для проверки вложенного объекта ставят @Valid. Одного правильного типа мало: @NotNull Duration допускает отрицательное время, @NotNull URI допускает неподходящую схему адреса. Такие бизнес-ограничения добавляют отдельными проверками, в том числе проверками отношений между полями.

По умолчанию @ConfigurationProperties игнорирует неизвестные поля, а ошибки преобразования — нет. Поэтому лишний payments.bank.timout может остаться незамеченным. Для группы с чётко определённым набором ключей можно задать ignoreUnknownFields=false. Значения для обязательных полей и проверку диапазонов всё равно задают отдельно.

@PropertySource появляется во время refresh. Это слишком поздно для выбора logging.* и многих spring.main.*, которые читаются раньше. Укажи такие настройки в Config Data или источнике запуска. Если свойство влияет на поиск файлов, оно должно быть доступно ещё до загрузки Config Data.

Когда ключ сложнее обычного имени поля

Для списка индекс в переменной ОС отделяют подчёркиваниями: payments.bank.channels[0] связывается из PAYMENTS_BANK_CHANNELS_0_. Для map со специальными символами в ключе используй запись в квадратных скобках; в YAML такой ключ дополнительно заключают в кавычки. Иначе Binder может изменить его или трактовать как путь вложенного свойства.

Имена переменных ОС при связывании map переводятся в нижний регистр. Поэтому переменные неудобны для словаря, где регистр ключа имеет смысл. YAML или JSON точнее передают такую структуру. Значение переменной при этом не переводится в нижний регистр.

Секреты и изменение настроек требуют своего жизненного цикла

Адрес и таймаут можно хранить в базовом файле приложения. Ключ доступа к банку приходит из окружения деплоя. Его не стоит размножать по профильным файлам в git: смена ключа тогда требует пересборки артефакта, а доступ к репозиторию становится доступом к банковскому секрету.

В контейнере секрет удобно смонтировать отдельным файлом. Через configtree: Boot превращает имена файлов в имена свойств, содержимое — в значения. Если в /run/secrets/ лежит файл payments.bank.api-key, следующий import делает его содержимое доступным под этим ключом:

spring:
  config:
    import: "configtree:/run/secrets/" # Наличие каталога обязательно для этого приложения.

Префикс optional: меняет смысл отсутствия ресурса. Он позволяет продолжить запуск, если ресурса нет; синтаксическую ошибку в существующем YAML и плохое значение он не скрывает. Если без ресурса приложение не должно работать, оставь import обязательным и проверяй наличие конкретного секрета через настройки. Пустой существующий каталог и отсутствующий каталог — разные ситуации: обязательный import проверяет загрузку ресурса, а обязательное поле — нужное значение.

./run.sh ConfigDemo --spring.config.import=classpath:/config-demo/missing.yaml
# Файла нет: без optional старт прекращается до создания сервисов.
startup=ConfigDataResourceNotFoundException
./run.sh ConfigDemo --spring.config.import=optional:classpath:/config-demo/missing.yaml
# Файла нет: продолжаем с базовым YAML. Ниже строки timeout и origin.
timeout=2000ms
origin=class path resource [config-demo/application.yaml] - 4:14

Обычный Boot загружает Config Data и связывает @ConfigurationProperties при запуске. Изменение YAML, файла секрета или переменной окружения снаружи процесса само по себе не пересоздаёт готовый record. Даже если новый источник уже появился внутри Environment, существующий объект настроек автоматически не пересвязывается.

var settings = context.getBean(PaymentSettings.class); // Record создан из базовых 2s.
System.out.println("before=" + settings.timeout().toMillis() + "ms");

context.getEnvironment().getPropertySources().addFirst(
        new MapPropertySource("live-change", Map.of("payments.bank.timeout", "99ms")));
// Сам Environment теперь действительно даёт новое значение.
System.out.println("environment=" + context.getEnvironment().getProperty("payments.bank.timeout"));
System.out.println("after=" + settings.timeout().toMillis() + "ms"); // Старый объект уже связан.
./run.sh ConfigDemo snapshot # Явно меняем Environment работающего контекста.
before=2000ms
environment=99ms
after=2000ms

Сервис, который получил PaymentSettings в конструкторе, продолжит использовать старое время. Уже настроенный HTTP-клиент или пул подключений также не изменится от нового свойства. Для обновления нужен управляемый перезапуск либо отдельный механизм, который заново проверяет настройки и безопасно применяет их к ресурсам. Возможности Spring Cloud разобраны в Spring Cloud; наличие одного Boot не включает обновление на лету.

Для платёжного сервиса заранее реши, какие настройки фиксируются до следующего деплоя, а какие требуют ротации без простоя. У клиента банка смена секрета и смена таймаута могут иметь разные правила. При диагностике показывай отдельные безопасные поля и происхождение ключа; печать всего record вместе с секретом превращает удобный объект настроек в источник утечки через логи.

  • Значение выбирается по ключу и приоритету источника. JSON выше обычных переменных ОС, аргументы запуска выше JSON.
  • Профильный файл перекрывает обычный на своём уровне. Внешние файлы перекрывают файлы внутри приложения.
  • ConfigurationProperties собирает структуру и преобразует типы. Валидация проверяет пригодность значений для сервиса.
  • При сбое сравнивай Environment, Origin и готовый объект настроек: источник и связывание — разные этапы.
  • optional разрешает отсутствие ресурса. Готовые настройки и использующие их ресурсы обычный Boot на лету не пересобирает.

На собеседовании

Если настройка есть в YAML, переменной окружения и аргументе, что победит?

В обычном Boot аргумент запуска побеждает переменную окружения, а переменная — Config Data из файла. Это поиск по упорядоченным источникам в Environment: для каждого ключа берётся первое найденное значение. Остальные ключи могут прийти из других источников.

Например, адрес банка останется из YAML, а --payments.bank.timeout=250ms перекроет профильный таймаут. Я смотрю итоговое значение и его Origin, чтобы найти реальный источник. Редактировать нижний файл до этого бессмысленно.

  • SPRING_APPLICATION_JSON разбирается в отдельный источник выше обычных переменных ОС. Аргументы выше JSON; null в JSON не стирает нижнее значение.
  • System properties JVM выше переменных ОС. Приложение может выключить добавление аргументов через setAddCommandLineProperties(false).
  • Источники тестов стоят ещё выше обычных аргументов. При расследовании теста учитываю его свойства отдельно от правил продового запуска.

Что делают профили и как Boot выбирает профильные файлы?

Профили включают дополнительные настройки и бины в том же приложении. Если активен prod, Boot читает обычный application.yaml и application-prod.yaml. Профильный файл перекрывает обычный на своём уровне, а внешний файл может перекрыть файл внутри jar.

В одном YAML можно сделать несколько документов и активировать нужный через spring.config.activate.on-profile. Это условие документа, а сам набор профилей задаю через spring.profiles.active, include или группу. Если активных профилей нет, используется default.

  • active, default, include и group задают только в непрофильных документах. Поместить include внутрь документа on-profile — ошибка конфигурации.
  • У нескольких профилей действует правило последнего в пределах группы расположений. Запятая и точка с запятой в location могут изменить такие группы.
  • При переопределении список заменяется целиком. Map объединяет ключи, а одинаковый ключ получает значение из более приоритетного источника.
В jar есть application-prod.yaml с 600ms, рядом с jar — application.yaml с 800ms. Активен prod, других настроек нет. Какой таймаут получит сервис?

800ms. При стандартном поиске внешний обычный файл стоит выше профильного файла внутри jar. Профильное имя не даёт файлу абсолютный приоритет над внешней конфигурацией. Именно такой результат получен в демо с additional-location.

Когда ты выберешь ConfigurationProperties, а когда Value?

Для группы настроек банка я выберу ConfigurationProperties: один объект с адресом, Duration, попытками и коллекциями. Его проще проверить при запуске и передать сервису целиком. Для одного значения или выражения SpEL подходит Value.

Properties связывает разные написания имени с полем Java. У Value эта поддержка ограничена, поэтому placeholder пишу в каноническом kebab-case. В нашем опыте max-attempts дал 2, а placeholder maxAttempts взял запасное -1.

  • Record регистрирую через EnableConfigurationProperties или ConfigurationPropertiesScan. Его параметры должен связывать Binder; обычная регистрация как компонента направляет конструктор в DI.
  • Validated и провайдер Bean Validation проверяют ограничения после преобразования. Вложенные объекты требуют Valid, а проверка типов ещё не проверяет диапазоны и отношения между полями.
  • Configuration processor создаёт метаданные для IDE при сборке. Он не заменяет регистрацию настроек, не выполняет runtime-валидацию и не включает SpEL в Binder.

Ты поменял настройку, а сервис ведёт себя по-старому. Как будешь разбираться?

Сначала проверю активный профиль и итоговое значение ключа в Environment. По Origin найду источник: возможно, файл проиграл аргументу или вообще не был загружен. Затем сравню значение с полем объекта ConfigurationProperties, который получил сервис.

Если в Environment значение новое, а в record старое, смотрю момент создания объекта. Обычный Boot не пересвязывает его после изменения файла или источника. Если запуск упал, отдельно различаю ошибку преобразования и нарушение валидации: строка oops и число попыток 0 ломаются на разных этапах.

  • У configuration properties неизвестные поля по умолчанию игнорируются. Опечатка может оставить старое или запасное значение; строгий набор ключей поддерживает ignoreUnknownFields=false.
  • PropertySource во время refresh слишком поздний для некоторых ранних свойств, в том числе logging и spring.main. Проверяю, когда настройка впервые читается.
  • env показывает источники, configprops — связанные объекты, отчёт --debug — решения автоконфигураций. Выбираю инструмент под конкретный вопрос.

Как передать секрет банку и что произойдёт, если файл секрета поменяется?

Я передам секрет из окружения деплоя, например смонтирую файл и подключу его через configtree. Имя файла станет именем свойства, содержимое — значением. Для обязательного ресурса import оставлю без optional и проверю само поле настроек.

Простая смена файла не пересоберёт уже созданный объект настроек и клиента банка в обычном Boot. Для ротации нужен перезапуск или отдельный механизм обновления. При этом новое значение должно пройти проверку до переключения рабочего клиента.

  • optional относится к отсутствию ресурса. Существующий пустой каталог не гарантирует наличие нужного секрета; это проверяет обязательное поле.
  • Изменённый Environment и обновлённый HTTP-клиент — разные состояния. Даже заново связанные свойства нужно применить к ресурсам с их правилами закрытия и переключения.
  • Не печатаю весь record, если в нём есть секрет. Для диагностики достаточно происхождения и отдельных безопасных полей; доступ к endpoints ограничиваю отдельно.
