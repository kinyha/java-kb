Spring: IoC & Context

В платёжном сервисе удобно отделить проведение платежа от выбора подключения к банку. Spring получает описание этой сборки, создаёт нужные объекты и передаёт сервису готовые зависимости. После запуска сервис работает по обычным Java-ссылкам. Чтобы понять неожиданное поведение, проследи, какой объект был создан и какую ссылку получил его клиент.

Сервис выполняет платёж, а его зависимости выбираются при сборке

У тебя есть PaymentService, который отправляет платёж в банк. Если он сам создаёт BankGateway и HTTP-клиент, то знает сразу две вещи: как провести платёж и как подключиться к конкретному банку. Для песочницы приходится менять код сервиса. Когда сервисов становится много, настройки подключения оказываются разбросаны по приложению.

Передадим Gateway в конструктор. Теперь сервис получает готовое подключение, а выбор банка остаётся в одном месте — в коде сборки приложения. Такой подход называется внедрением зависимостей, DI. Его легко использовать вручную: создать Gateway, затем передать его в новый PaymentService. В тесте вместо настоящего банка можно передать подставной объект.

Вот небольшая часть ContextDemo.java. Сервису достаточно ссылки на зависимость; откуда она пришла, решает вызывающий код.

record Gateway(String origin) {}

static class PaymentService {
    final Gateway gateway;
    PaymentService(Gateway gateway) {
        this.gateway = gateway; // Внешний код выбирает объект и передаёт сюда.
    }
}

Инверсия управления, IoC, описывает сам перенос решения наружу. Раньше сервис управлял созданием Gateway; теперь это делает код сборки. DI — один из способов такой инверсии. У другого механизма будет другое переданное решение: например, servlet-контейнер сам выбирает момент вызова обработчика HTTP-запроса.

Spring берёт сборку приложения на себя. Ты описываешь, какие компоненты нужны и как их создавать; контейнер находит зависимости, создаёт объекты и готовит их к работе. Благодаря этому подключение к банку можно менять через конфигурацию, сохраняя код платежа. После сборки сервис пользуется обычной Java-ссылкой.

Spring сначала читает описание, затем создаёт объект

Контейнеру нужен рецепт создания каждого компонента. В Spring этот рецепт называется BeanDefinition: он содержит класс или метод создания, имя, правила повторного использования, способы инициализации и завершения работы. Например: «создать Gateway для банка из конфигурации и использовать один экземпляр в этом контейнере».

По рецепту Spring создаёт бин — объект, который он связывает с зависимостями и обрабатывает при запуске. Бином может быть твой PaymentService или HTTP-клиент из сторонней библиотеки. Оба проходят один путь подготовки, хотя библиотечный класс ничего о Spring не знает.

Разделение описания и объекта помогает понять отложенное создание. Описание отчёта уже зарегистрировано, но сам отчёт появится только тогда, когда его кто-то запросит. А для prototype по одному описанию Spring создаёт новый объект при каждом запросе. Один Java-класс также можно зарегистрировать дважды: например, как gatewayForProduction и gatewayForSandbox, с разными настройками.

Аннотации и Java-конфигурация — способы получить эти описания. Сканер обнаруживает @Component и добавляет описание в реестр. Для @Bean описанием становится способ вызвать метод и обработать его результат. Дальше контейнер работает с общим реестром, независимо от того, как он был заполнен.

Поставлю @Component, и любой экземпляр класса получит зависимости от Spring.

Сканер использует аннотацию, чтобы зарегистрировать бин. При самостоятельном new ты создаёшь другой экземпляр. Он проходит только обычный Java-конструктор. Если new находится внутри @Bean, результат метода передаётся Spring, и контейнер продолжает его подготовку.

Представь, что управляемый PaymentService создаёт Receipt для ответа клиенту. Receipt остаётся обычным результатом метода: Spring подготавливал сам сервис, а не каждый объект, который тот создаёт. Поэтому при разборе ошибки полезнее найти место создания конкретного экземпляра, чем проверять аннотации на его классе.

Чтобы собрать сервис, Spring сначала получает его зависимости

Для вызова конструктора PaymentService нужен готовый Gateway. Spring ищет его среди уже созданных объектов. Если такого объекта ещё нет, читает описание Gateway, получает его зависимости и создаёт его. Затем возвращается к PaymentService и передаёт полученную ссылку в конструктор.

Получается обход графа: зависимость готовится раньше компонента, который её использует. В реальном приложении Gateway может зависеть от HTTP-клиента, а тот — от настроек и пула соединений. Схема ниже показывает тот же процесс для короткой цепочки.

При стандартном запуске ApplicationContext заранее создаёт singleton-бины, для которых включено немедленное создание. Поэтому отсутствие обязательного Gateway обычно обнаруживается при старте, а первый HTTP-запрос приходит уже в собранный PaymentService. Флаг lazy откладывает создание до первого обращения. Если другой запускаемый бин сразу требует этот объект, потребность возникнет уже на старте.

После конструктора Spring ещё выполняет внедрение в поля и методы, вызывает инициализацию и подключает обработчики. Один из них может обернуть сервис в прокси: клиент получит ссылку на оболочку, которая добавляет поведение вокруг вызова. Этот этап объясняется в Bean Lifecycle и AOP & Proxies.

В рабочем методе сервис обычно просто вызывает gateway. Если вместо этого каждый раз писать context.getBean, зависимости скрываются внутри логики: чтобы понять требования класса, придётся прочитать все его методы. Такой способ называется service locator. Конструктор показывает требования сразу; отложенное получение через ObjectProvider полезно, когда момент создания действительно важен.

ApplicationContext подготавливает контейнер к работе приложения

BeanFactory отвечает за получение и создание бинов. Его рабочая реализация DefaultListableBeanFactory хранит описания, выбирает зависимости и создаёт экземпляры. Её можно использовать отдельно, но тогда подготовку специальных обработчиков придётся организовать самому.

ApplicationContext организует этот запуск и добавляет то, что нужно целому приложению. Через Environment он даёт доступ к свойствам и профилям; через ResourceLoader — к ресурсам; через MessageSource — к локализованным сообщениям. Также он позволяет публиковать события. Работу с бинами типичный контекст передаёт внутренней фабрике.

Метод refresh() запускает подготовку контекста: сначала обрабатываются описания, затем подключаются обработчики объектов, создаются оставшиеся singleton-бины и завершается запуск. Вызов register лишь добавляет описание. Конструктор AnnotationConfigApplicationContext(Config.class) делает регистрацию и refresh сразу; пустой конструктор позволяет сначала настроить контекст и только затем запустить его.

Под капотом: как увидеть порядок запуска

В AbstractApplicationContext.refresh этот порядок виден в вызовах invokeBeanFactoryPostProcessors, registerBeanPostProcessors, finishBeanFactoryInitialization и finishRefresh. Сначала расширения меняют описания, потом фабрика создаёт по ним объекты. Если поменять порядок, уже созданные экземпляры сохранят старые настройки.

Контекст с Java-конфигурацией наследуется от GenericApplicationContext и поддерживает один refresh на экземпляр. Для нового запуска создают новый контекст. Другие реализации имеют свои правила обновления, поэтому наличие метода в интерфейсе ещё недостаточно для повторного запуска.

Spring Boot автоматизирует подготовку приложения: подбирает конфигурации, свойства и веб-окружение, затем запускает Spring-контекст. Сам контейнер доступен и без Boot. Для следующего примера достаточно Spring Framework; HTTP-сервер и база данных не требуются.

Имя зависимости может изменить выбор между родителем и ребёнком

Допустим, общее подключение к банку хранится в родительском контексте, а отдельный сервис — в дочернем. Ребёнок видит бины родителя. При поиске по имени он сначала проверяет свои бины и затем обращается наверх. Родитель ищет только у себя: дочерний контекст ему недоступен.

Если в обоих контекстах зарегистрировать gateway, из ребёнка будет виден его собственный бин. Но переименование локального бина в localGateway меняет ситуацию: для конструктора PaymentService подходят уже два объекта одного типа. Правило «локальный всегда важнее» здесь отсутствует; Spring должен выбрать зависимость.

У аргумента конструктора в нашем примере имя gateway. При компиляции с -parameters оно сохраняется в байткоде, и Spring может выбрать одноимённый бин родителя. Без флага имя аргумента недоступно, и два одинаково подходящих кандидата приводят к ошибке. С Spring 6.1 для такого выбора по имени параметра требуется этот флаг. Maven-конфигурация spring-boot-starter-parent включает его по умолчанию; импорт одного Boot BOM даёт управление зависимостями, а настройки компилятора задаются отдельно.

Полный ContextDemo.java, Java 21, Spring 7.0.9. Каждый запуск сравнивает два имени локального бина. Комментарии отмечают условия выбора.

import java.util.logging.Level;
import java.util.logging.Logger;
import org.springframework.context.annotation.AnnotationConfigApplicationContext;

public class ContextDemo {
    record Gateway(String origin) {}

    static class PaymentService {
        final Gateway gateway;
        PaymentService(Gateway gateway) {
            this.gateway = gateway; // Имя параметра станет доступно Spring с -parameters.
        }
    }

    static void compare(AnnotationConfigApplicationContext parent, String localName) {
        try (var child = new AnnotationConfigApplicationContext()) {
            child.setParent(parent);
            child.registerBean(localName, Gateway.class, () -> new Gateway("child"));
            child.registerBean(PaymentService.class);
            try {
                child.refresh();
                System.out.println(localName + " -> " + child.getBean(PaymentService.class).gateway.origin());
            } catch (org.springframework.beans.factory.UnsatisfiedDependencyException ex) {
                // Для сравнения нужен корень ошибки, а не весь стек запуска.
                Throwable cause = ex;
                while (cause.getCause() != null) cause = cause.getCause();
                System.out.println(localName + " -> " + cause.getClass().getSimpleName());
            }
        }
    }

    public static void main(String[] args) {
        // Ожидаемую ошибку второго варианта печатаем сами, без служебного WARNING.
        Logger.getLogger("org.springframework").setLevel(Level.SEVERE);
        try (var parent = new AnnotationConfigApplicationContext()) {
            parent.registerBean("gateway", Gateway.class, () -> new Gateway("parent"));
            parent.refresh();
            compare(parent, "gateway");      // Одно имя: дочерний бин скрывает родительский.
            compare(parent, "localGateway"); // Два имени: выбор зависит от метаданных параметра.
        }
    }
}
cd examples/spring-core
./run.sh ContextDemo               # javac без -parameters
gateway -> child
localGateway -> NoUniqueBeanDefinitionException
./run.sh ContextDemo --parameters  # javac с -parameters
gateway -> child
localGateway -> parent

Такое совпадение имени удобно как соглашение, но связывает выбор банка с названием аргумента. Рефакторинг gateway → localGateway способен изменить поведение. Если выбор важен для бизнеса, вырази его явно через @Qualifier: тогда имя локальной переменной перестанет управлять маршрутом платежа.

Отдельное правило действует при перечислении. getBeanNamesForType и getBeansOfType возвращают бины локальной фабрики; для объединённого списка из иерархии есть BeanFactoryUtils с методами IncludingAncestors. Поиск зависимости и перечисление всех бинов решают разные задачи.

Для диагностики найди место, где сборка оборвалась

Ошибка запуска часто начинается с UnsatisfiedDependencyException. Она показывает, какой бин создавался и какую зависимость Spring пытался передать. Двигайся по причинам исключения: NoSuchBeanDefinitionException указывает на отсутствие кандидата, NoUniqueBeanDefinitionException — на неоднозначный выбор. Если упал сам метод @Bean, внизу будет его исходное исключение.

От этой причины зависит исправление. Отсутствующее описание требует проверить сканирование, импорт и условия регистрации. Несколько кандидатов требуют уточнить выбор. Ошибка подключения внутри @Bean требует разобраться с созданием клиента. Для просмотра состава получи имена определений и нужный BeanDefinition. Вызов getBeansOfType может создать отложенные бины, поэтому для диагностики регистрации лучше начать с метаданных.

Собранные ссылки ещё нужно правильно использовать. Один singleton-сервис доступен нескольким потокам: изменяемые поля требуют отдельного решения для конкурентного доступа. Обычный вызов метода отправляет платёж так, как написано в Java-коде; транзакция и перехват появляются при подключении соответствующей инфраструктуры. Сборка, время жизни и поведение вызова — три разных вопроса.

Ручной сборки хватает для небольшой утилиты с несколькими объектами. Контейнер особенно полезен в backend-приложении, где много компонентов и интеграций, а правила подготовки повторяются. Он централизует эту работу, сохраняя обычные классы и конструкторы внутри приложения.

Следующая тема, Configuration & Beans, объясняет, как заполняется реестр описаний. Dependency Resolution показывает, как из кандидатов выбирается конкретная ссылка. После этого проще разбирать время жизни объектов и прокси.

  • DI начинается с передачи готовой зависимости в конструктор. Spring автоматизирует сборку большого приложения.
  • Сначала контейнер получает описания, затем создаёт по ним объекты. Отложенный бин может долго существовать только как описание.
  • При refresh контекст подготавливает обработчики и создаёт бины, нужные для запуска.
  • Singleton принадлежит конкретной фабрике. В иерархии выбор зависит от типа, имён и уточнений зависимости.
  • С -parameters имя аргумента конструктора участвует в выборе. Важное намерение лучше выразить через @Qualifier.

На собеседовании

Чем IoC отличается от DI и какую проблему решает Spring?

Я передаю Gateway в конструктор PaymentService, чтобы сервис занимался платежом, а выбором подключения занималась сборка приложения. Такая передача зависимости называется DI. Более общая идея IoC — передать внешнему механизму часть управления, в этом случае создание и связывание объектов.

Сначала я могу собрать всё вручную. Spring становится полезен, когда компонентов много: он читает конфигурацию, создаёт нужные объекты и готовит их к работе по общим правилам.

  • Если сервис сам ищет зависимость через getBean, требования класса скрываются внутри методов. Это service locator; конструктор показывает те же требования сразу.
  • Поиск кандидатов происходит при сборке. После внедрения сервис вызывает метод по готовой Java-ссылке; прокси добавляет отдельный путь вызова.

Чем BeanFactory отличается от ApplicationContext?

BeanFactory создаёт и выдаёт бины. ApplicationContext организует запуск этой фабрики и даёт приложению свойства, ресурсы, локализованные сообщения и события. В обычном приложении я использую контекст, а отдельную фабрику — когда нужен низкоуровневый контроль.

При refresh контекст подключает обработчики и заранее создаёт singleton-бины, у которых включено немедленное создание. Флаг lazy откладывает создание, prototype создаётся по запросу. У отдельной фабрики предварительное создание можно вызвать явно.

  • Обработчик, объявленный бином, ещё нужно подключить к фабрике. Контекст делает это при запуске; при использовании фабрики отдельно этот шаг организует вызывающий код.
  • В типичной реализации контекст использует внутреннюю DefaultListableBeanFactory. Дополнительные возможности контекста и хранение бинов распределены между этими объектами.

Что такое бин и чем он отличается от BeanDefinition?

BeanDefinition — описание создания и настройки, а бин — объект, подготовленный по этому описанию. Например, определение отложенного отчёта уже находится в реестре, хотя сам отчёт ещё никто не запросил.

По одному prototype-описанию создаются разные экземпляры. Один класс также можно описать дважды под разными именами, например для двух банков. Поэтому я различаю класс, описание и конкретный объект.

  • Метод @Bean может создавать объект сторонней библиотеки: Spring обработает его результат без аннотации на самом классе.
  • Обработчик может вернуть прокси вместо исходного объекта. Класс из описания и класс ссылки, полученной клиентом, тогда различаются.

Как выбирается зависимость между родителем и дочерним контекстом?

Ребёнок видит свои бины и бины родителя. Локальный бин с тем же именем скрывает родительский. Если имена разные, оба объекта одного типа участвуют в выборе зависимости.

Для одиночной ссылки Spring учитывает уточнения выбора. В нашем примере аргумент gateway при компиляции с -parameters совпадает с именем родительского бина, и сервис получает его. Без метаданных имени выбор неоднозначен.

  • Singleton считается относительно имени и фабрики. Два независимых контекста могут создать два экземпляра одного класса; закрытие ребёнка сохраняет родительские бины.
  • getBeansOfType перечисляет локальные бины. Для всей иерархии есть BeanFactoryUtils с методами IncludingAncestors.
  • Выбор по имени параметра зависит от настроек компиляции. Явный @Qualifier фиксирует намерение лучше, чем название аргумента.
