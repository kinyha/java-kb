Spring: IoC & Context

Spring собирает граф объектов по описанию приложения. BeanDefinition — рецепт, bean — управляемый экземпляр, BeanFactory — механизм сборки, ApplicationContext — окружение и запуск. После DI у сервиса обычные Java-ссылки. Аннотации дают метаданные; поведение зависит от того, кто зарегистрировал и создал конкретный объект.

Сервис должен выполнять платёж, а сборка — выбирать его зависимости

Представь PaymentService, который внутри конструктора создаёт BankGateway, а тот — HTTP-клиент с адресом банка. Чтобы подключить песочницу или другой банк, приходится менять бизнес-класс. Когда таких сервисов десятки, адреса, пулы соединений и правила создания объектов расползаются по приложению. Проблема здесь в том, кто принимает решение о составе приложения.

Первый ход вообще не требует Spring: передать Gateway в конструктор. Service знает, как провести платёж через этот контракт, а отдельный код сборки выбирает реализацию и создаёт объекты в нужном порядке. Такой код называют composition root: место, где граф зависимостей собирается целиком. В тесте в тот же конструктор можно передать маленькую подставную реализацию без запуска контекста.

interface Gateway { void charge(long cents); }
      final class PaymentService {
          private final Gateway gateway;
          PaymentService(Gateway gateway) { this.gateway = gateway; }
          void pay(long cents) { gateway.charge(cents); } // Обычный вызов Java.
      }
      // Фрагмент: выбор реализации находится в коде сборки.
      // new PaymentService(gatewayForThisEnvironment);

Dependency Injection — передача зависимостей извне. Inversion of Control — более широкая идея: часть управления передана внешнему механизму. В DI это управление сборкой объектов; в servlet-контейнере — момент вызова обработчика. Аннотация не является определением IoC: вручную собрать объект через конструктор — тоже DI.

Spring масштабирует эту идею: читает описание приложения, строит граф, выбирает зависимости и управляет жизненным циклом. Контейнер нужен, когда ручная сборка становится отдельной большой программой. Вызов gateway.charge после внедрения остаётся обычным вызовом метода; дополнительное поведение появится только при наличии прокси.

Описание бина и сам объект живут на разных уровнях

Bean — объект, которым управляет контейнер. Это может быть твой сервис, DataSource сторонней библиотеки или конфигурационный объект. Bean не обязан иметь интерфейс, аннотацию или особый базовый класс. DTO одного платежа обычно остаётся обычным объектом: контейнер не должен хранить каждый запрос пользователя.

До создания объекта Spring хранит BeanDefinition. В нём записано, что создавать и как: класс или factory method, имя, scope, lazy-флаг, init/destroy callbacks и другие метаданные. Из component scan, Java-конфигурации и XML получаются разные способы наполнить один реестр определений. После этого общая фабрика работает с единым описанием.

Одно определение не всегда означает один объект: singleton даёт одну готовую ссылку на имя в этой фабрике, prototype — новый экземпляр при каждом запросе создания. И один Java-класс может иметь два определения с разными именами и настройками. Поэтому вопрос «есть ли этот класс в контексте?» менее точен, чем «какое определение, в какой фабрике и с каким scope?».

Любой new объекта с @Component создаёт Spring bean.

Аннотация — метаданные для сканера. new обходит путь создания контейнера; созданный объект сам не получит DI, init callbacks и AOP. Внутри @Bean new допустим: результат factory method передаётся контейнеру для дальнейшей обработки.

Граница управления относится к конкретному экземпляру. Вызов метода managed-сервиса не делает managed все объекты, которые этот метод вернул или создал. При чтении кода сначала найди место регистрации и получения ссылки — это объясняет больше, чем поиск аннотаций по проекту.

Контейнер собирает граф при создании, а не заново при каждом запросе

Чтобы создать PaymentService, нужно сначала получить Gateway. Фабрика идёт по зависимостям, пока не найдёт готовый объект или определение без ещё не разрешённых зависимостей. Затем возвращается вверх и передаёт готовые ссылки в конструкторы. Это рекурсивная сборка графа, а не последовательный обход классов по алфавиту.

В обычном ApplicationContext non-lazy singleton создаются во время refresh. Поэтому первый HTTP-запрос чаще получает уже собранный сервис, а ошибка обязательной зависимости останавливает запуск приложения. Lazy и prototype меняют момент создания. Lazy-бин всё равно создастся на старте, если eager-сервис требует его прямую ссылку.

Ссылку после инициализации может заменить BeanPostProcessor: например, вернуть AOP proxy. Тогда поле gateway или ссылка на Service у клиента содержит именно объект, опубликованный контейнером. Привычное «Spring вызывает new и присваивает поле» объясняет только часть пути; lifecycle и прокси раскрыты в следующих темах.

Искать bean из ApplicationContext внутри каждого бизнес-метода — service locator. Это работает, но скрывает зависимости: по конструктору уже нельзя понять требования класса, а простой тест вынужден воспроизводить контекст. Явный конструктор сохраняет видимость графа; ObjectProvider оправдан там, где важен отложенный или повторный поиск.

ApplicationContext организует запуск поверх BeanFactory

BeanFactory — базовый контракт получения и управления бинами. ListableBeanFactory добавляет перечисление, HierarchicalBeanFactory — родителя, ConfigurableBeanFactory — настройки. Рабочая реализация DefaultListableBeanFactory хранит определения и разрешает зависимости. Сам интерфейс не задаёт «ленивость» как обязательное отличие от любого контекста.

ApplicationContext расширяет BeanFactory и добавляет окружение приложения: Environment, ресурсы, сообщения для локализации, события. Типичная реализация делегирует работу с бинами внутренней фабрике и организует её подготовку. AnnotationConfigApplicationContext умеет читать Java-конфигурацию; web-контекст добавляет окружение web-приложения.

refresh готовит инфраструктуру: обрабатывает определения, регистрирует BeanPostProcessor, настраивает события, создаёт оставшиеся eager-singleton и завершает запуск. register только сообщает контексту об определении. Конструктор AnnotationConfigApplicationContext(Config.class) делает регистрацию и refresh сразу; пустой конструктор оставляет момент refresh тебе.

Под капотом: где смотреть refresh

В AbstractApplicationContext.refresh найди invokeBeanFactoryPostProcessors, registerBeanPostProcessors, finishBeanFactoryInitialization и finishRefresh. Порядок объясняет, почему расширение, меняющее определения, должно отработать до создания обычных бинов. GenericApplicationContext и его annotation-наследник поддерживают один refresh на экземпляр; наличие метода refresh в контракте не обещает произвольные перезапуски любого контекста.

Spring Boot готовит такое приложение по соглашениям: выбирает конфигурации, свойства, web-окружение и вызывает запуск контекста. Это надстройка над Spring Framework. IoC, DI и AOP не требуют Boot, сервера или application.yml: демо ниже использует только Framework.

Родительский контекст виден ребёнку, но поиск зависит от вида запроса

В иерархии контекстов общие инфраструктурные бины можно держать в родителе, а отдельные компоненты — в дочернем контексте. При поиске по имени ребёнок сначала смотрит у себя и при отсутствии передаёт запрос родителю. Родитель вниз не смотрит. Singleton принадлежит фабрике, поэтому два самостоятельных контекста могут создать два экземпляра одного класса.

Если ребёнок определил bean с тем же именем, родительский bean скрыт для поиска из ребёнка. Но два bean одного типа с разными именами не превращаются в «выбираем локальный»: при autowiring учитываются подходящие кандидаты предков, и возможна неоднозначность. Это частая причина сюрприза при совмещении конфигураций.

Полный пример ContextDemo.java, Java 21, Spring 7.0.9. 

cd examples/spring-core
      ./run.sh ContextDemo
import org.springframework.context.annotation.AnnotationConfigApplicationContext;
      import org.springframework.beans.factory.support.RootBeanDefinition;
      
      public class ContextDemo {
          static class Gateway {}
          static class PaymentService {
              final Gateway gateway;
              PaymentService(Gateway gateway) { this.gateway = gateway; }
          }
          static class Report {
              Report() { System.out.println("Report created"); }
          }
          public static void main(String[] args) {
              try (var parent = new AnnotationConfigApplicationContext()) {
                  parent.registerBean("gateway", Gateway.class);
                  parent.registerBean("bankName", String.class, () -> "Parent bank");
                  parent.refresh();
                  try (var child = new AnnotationConfigApplicationContext()) {
                      child.setParent(parent);
                      child.registerBean(PaymentService.class);
                      child.registerBean("gateway", Gateway.class); // То же имя скрывает bean родителя.
                      var definition = new RootBeanDefinition(Report.class);
                      definition.setLazyInit(true);
                      child.registerBeanDefinition("report", definition);
                      System.out.println("before refresh: " + child.containsBeanDefinition("report"));
                      child.refresh();
                      System.out.println("singleton exists: " + child.getBeanFactory().containsSingleton("report"));
                      System.out.println("service uses local: " +
                          (child.getBean(PaymentService.class).gateway == child.getBean("gateway")));
                      System.out.println("inherited name: " + child.getBean("bankName"));
                      System.out.println("parent sees child: " + parent.containsBean("report"));
                      Object first = child.getBean("report"); // Lazy bean создаётся на первом запросе.
                      System.out.println("same report: " + (first == child.getBean("report")));
                      System.out.println("manual is managed: " + (new Gateway() == child.getBean("gateway")));
                  }
              }
          }
      }
before refresh: true
      singleton exists: false
      service uses local: true
      inherited name: Parent bank
      parent sees child: false
      Report created
      same report: true
      manual is managed: false

Здесь report зарегистрирован до refresh, но lazy-singleton ещё отсутствует в кеше. Его первый getBean создаёт объект; второй отдаёт ту же ссылку. gateway ребёнка скрывает одноимённый gateway родителя, а bankName наследуется. Если переименовать локальный gateway в localGateway, PaymentService получит двух кандидатов и запуск упадёт с NoUniqueBeanDefinitionException внутри UnsatisfiedDependencyException.

Перечисление через getBeanNamesForType и getBeansOfType локального ListableBeanFactory не включает предков автоматически. Для объединённого списка есть BeanFactoryUtils.*IncludingAncestors. Нельзя переносить правило одного lookup на все API: по имени, по типу и при перечислении контекстов работают разные операции.

Контейнер управляет сборкой, а корректность сервиса остаётся твоей

Если приложение не стартует, читай цепочку causes до конкретного injection point: имя создаваемого bean, параметр конструктора и тип зависимости. NoSuchBeanDefinitionException означает отсутствие подходящего кандидата; NoUniqueBeanDefinitionException — несколько подходящих. Внешняя UnsatisfiedDependencyException добавляет место, где разрешение зависимости сорвалось, но не является отдельной причиной.

Не начинай лечение с добавления @Primary ко всему: сначала отдели отсутствие определения от ошибки выбора и от исключения внутри factory method. Для проверки состава удобно получить имена определений и выборочно inspect BeanDefinition. В большом приложении getBeansOfType может создать lazy-объекты, поэтому диагностика сама способна изменить наблюдаемое состояние.

Spring не делает singleton потокобезопасным, не превращает локальный кеш в распределённый и не создаёт транзакцию вокруг каждого метода. DI организует связи, scope задаёт жизненный цикл, AOP добавляет перехват вызова; это разные механизмы. Разделение помогает объяснять ошибки без фразы «Spring почему-то не сработал».

Для небольшой утилиты ручная сборка через конструкторы часто яснее. Для backend с множеством интеграций контейнер экономит повторяющийся код и даёт единый путь расширения. Выбор зависит от сложности графа и нужной инфраструктуры, а не от количества аннотаций.

Дальше: Configuration & Beans объясняет, откуда берутся определения; Dependency Resolution — как выбирается ссылка. Scopes отвечает за повторное использование, Lifecycle — за готовность, AOP — за подмену пути вызова.

  • DI можно сделать вручную; контейнер централизует большую сборку и lifecycle.
  • Определение, экземпляр и опубликованный proxy — разные сущности.
  • refresh подготавливает расширения и создаёт eager-singleton; lazy откладывает создание до потребности.
  • Singleton ограничен именем и фабрикой, а не всей JVM.
  • Иерархия поиска по имени и выбор кандидатов по типу не одно и то же.

На собеседовании

Чем IoC отличается от DI и какую проблему решает Spring?

Я разделяю логику объекта и его сборку. IoC передаёт часть управления внешнему механизму; DI — конкретный способ: зависимости приходят извне. Spring строит граф из конфигурационных метаданных, а сервис использует уже переданные ссылки.

Я могу применить DI и без Spring: собрать PaymentService через конструктор вручную. Контейнер становится полезен, когда нужно единообразно собирать большое приложение, выбирать реализации и управлять инициализацией.

  • Service locator тоже инвертирует часть управления, но скрывает требования класса за getBean. Конструктор показывает их явно.
  • После внедрения вызовы обычные; накладные расходы поиска кандидатов в основном относятся к созданию, а proxy добавляет отдельную стоимость вызова.

Чем BeanFactory отличается от ApplicationContext?

BeanFactory задаёт базовый контракт контейнера бинов. ApplicationContext расширяет его ресурсами, окружением, сообщениями и событиями, а также организует запуск и подключение processors. Для приложения я использую контекст; голая фабрика полезна для низкоуровневого контроля.

Отличие «фабрика всегда lazy, контекст всегда eager» слишком грубое. Стандартный refresh создаёт non-lazy singleton, но есть lazy и prototype, а у фабрики есть явный preInstantiateSingletons.

  • Контекст обнаруживает специальные бины по контрактам, голую фабрику нужно подготовить вручную.
  • В конкретной реализации контекст делегирует внутренней DefaultListableBeanFactory; наследование интерфейсов не означает единственный объект с одной структурой данных.

Что такое bean и чем он отличается от BeanDefinition?

Bean — управляемый объект, BeanDefinition — метаданные для его создания и настройки. Сначала Spring читает определения, потом по ним создаёт и связывает экземпляры. Поэтому определение lazy-бина может существовать задолго до самого объекта.

Два определения одного класса дают два bean по разным именам; prototype даёт много экземпляров одного определения. Сам по себе new аннотированного класса управление контейнеру не передаёт.

  • Factory method может вернуть объект сторонней библиотеки: @Component на его классе не нужен.
  • Клиенту может быть опубликован proxy. Тип target, метаданные определения и runtime-класс полученной ссылки — разные наблюдения.

Что означает singleton в нескольких контекстах?

Я считаю singleton относительно имени bean и конкретной фабрики. Два отдельных контекста способны создать два экземпляра. В иерархии ребёнок может пользоваться bean родителя, пока не скрывает его локальным одноимённым определением.

При lookup по имени ребёнок делегирует наверх, родитель вниз не ищет. При autowiring два одинаковых типа с разными именами в родителе и ребёнке могут дать неоднозначность.

  • getBeansOfType у локальной фабрики не равно списку всей иерархии; для него нужен BeanFactoryUtils.
  • Закрытие дочернего контекста не означает уничтожение singleton родительской фабрики.
Появится ли report при refresh из демо?

Сам lazy report не создастся. Если добавить eager-bean, которому report нужен как прямая зависимость, создание report понадобится уже во время refresh. Lazy-флаг не отменяет потребность в реальном объекте.
