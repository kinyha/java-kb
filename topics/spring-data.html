Spring Data

Репозиторий Spring Data превращает интерфейс приложения в операции конкретного хранилища. В JPA он вызывает EntityManager и сохраняет правила контекста персистентности; в JDBC работает с явно сохраняемым агрегатом. Название метода может задать запрос, возвращаемый тип — форму результата и цену пагинации. Чтобы понимать поведение платежа, проследи весь путь: какой метод вызван, какой запрос построен и где заканчивается транзакция.

Вызов save заканчивается раньше, чем весь платёж

Сервис создаёт платёж на 1000 копеек и вызывает repository.save. Затем меняет сумму на 1200 и ждёт, что Hibernate заметит изменение. В базе остаётся 1000. Отдельный вызов save завершил свою транзакцию, а дальнейший Java-код уже работал с отсоединённым объектом.

Spring Data JPA упрощает доступ к JPA, но не создаёт контекст персистентности на всё время жизни возвращённого объекта. Если общей внешней транзакции нет, стандартный save открывает свою и завершает её до возврата. Сервисная граница @Transactional позволяет объединить несколько операций и сохранить managed-состояние на весь нужный участок.

@Entity(name = "Payment")
class Payment {
    @Id String id; // Идентификатор назначает платёжный сервис.
    @Version Long version; // null означает новый объект для Spring Data.
    String status;
    long cents;
    protected Payment() {}
    // Конструктор и getters есть в полном демо.
}

var original = new Payment("p-17", "NEW", 1_000);
var inserted = repository.save(original); // Здесь отдельная транзакция save уже завершилась.
System.out.println("new save same object=" + (inserted == original));
original.cents = 1_200; // После save внешней транзакции нет, объект detached.
System.out.println("without save cents=" + repository.findById("p-17").orElseThrow().cents);
var merged = repository.save(original); // Состояние копируется в managed-объект нового контекста.
System.out.println("update save same object=" + (merged == original));
System.out.println("after save cents=" + repository.findById("p-17").orElseThrow().cents);

new save same object=true
without save cents=1000
update save same object=false
after save cents=1200

Это первые строки SpringDataDemo.java. Демо использует Framework 7.0.9 и зависимости из BOM Boot 4.1.1. Контекст создаётся самостоятельно, OSIV отсутствует. Один файл регистрирует фабрику EntityManager, JpaTransactionManager и настоящие репозитории Spring Data.

Save выбирает между persist и merge по признаку нового объекта. По умолчанию сначала смотрит на nullable-поле версии, затем — на id, если подходящей версии нет. В нашем случае version=null позволяет persist даже с уже назначенным id. После первой фиксации версия появилась, поэтому второй save использовал merge. Его возвращаемый объект нужно учитывать: merge копирует состояние, а исходный detached-объект managed не делает.

Для назначенных приложением id без nullable-версии можно реализовать Persistable.isNew(). Но это должно быть правильное состояние жизненного цикла, а не вечное true. В общей JPA-транзакции managed-сущность обновляется через dirty checking; обязательного save после каждого setter там нет. Подробно состояния и flush разобраны в JPA Basics.

За интерфейсом репозитория стоят разные пути выполнения

Интерфейс репозитория выглядит как обычный код приложения. Реализацию создаёт фабрика модуля Spring Data. Она знает тип сущности и id, базовые CRUD-операции, объявленные запросы и пользовательские фрагменты реализации. Вызов проходит через прокси; дальше выбирается путь конкретного метода.

В JPA стандартный save выполняет SimpleJpaRepository через EntityManager. Метод поиска по имени получает подготовленную модель запроса. Пользовательский фрагмент может выполнить сложную операцию своим кодом. Сам Spring Data не заменяет Hibernate и JDBC: они продолжают загружать объекты и общаться с базой.

CRUD-методы базовой реализации уже имеют транзакционные настройки. Для объявленных поисковых методов и своих фрагментов границу задают с учётом операции; надёжный ориентир — транзакция сервиса. Она охватывает чтение, проверку и изменения вместе. Несколько по отдельности успешных save могут оставлять частично выполненный платёж, если общей границы нет.

При нескольких модулях Spring Data важно, какой модуль создаёт репозиторий. JPA-тип репозитория и @Entity у модели помогают определить JPA-хранилище; JDBC имеет свою модель и аннотации. Разделяй пакеты и настройку сканирования, когда в приложении используются оба подхода. Условия Boot и прокси транзакции разобраны в Spring Boot и Transactions.

Название метода задаёт запрос по свойствам модели

Нужно найти новые платежи от 2000 копеек и вернуть их по id. Spring Data разбирает имя метода: после By идут свойства и условия, And связывает их, GreaterThanEqual задаёт сравнение, OrderByIdAsc — порядок. Параметры остаются значениями, связанными с запросом.

interface Payments extends JpaRepository<Payment, String> {
    List<Payment> findByStatusAndCentsGreaterThanEqualOrderByIdAsc(String status, long minimum);

    @Query("select p from Payment p where p.cents >= :minimum order by p.id")
    List<Payment> expensive(@Param("minimum") long minimum); // JPQL использует Payment и поле cents.
}

// В демо NEW: p-17=1200, p-18=2000, p-19=3000; PAID: p-20=4000.
System.out.println("derived=" + ids(repository.findByStatusAndCentsGreaterThanEqualOrderByIdAsc("NEW", 2_000)));
System.out.println("jpql=" + ids(repository.expensive(3_000)));
derived=[p-18, p-19]
jpql=[p-19, p-20]

Второй запрос не фильтрует статус: p-20 вошёл в результат. Имя expensive ничего не добавляет к объявленному JPQL. @Query задаёт явный запрос для метода; JPQL использует имена сущностей и Java-полей. При nativeQuery=true это SQL конкретной базы с её таблицами и столбцами.

Ошибка имени свойства обычно обнаруживается при создании репозитория. Подчёркивание в имени метода помогает явно разделить путь вложенных свойств, когда разбор имени неоднозначен. Но метод из десяти условий плохо читается и трудно расширяется. Для сложного поиска выбери явный запрос, Specifications или пользовательский фрагмент с понятной моделью фильтра.

Меняющий данные запрос требует @Modifying и подходящей транзакционной границы. Bulk UPDATE выполняется напрямую в базе и может оставить уже загруженные сущности со старым состоянием. Нужно согласовать flush, сам запрос и очистку либо обновление контекста. Само наличие аннотации репозитория не заменяет эту последовательность.

Проекция задаёт данные, нужные конкретному ответу

Для списка платежей нужны id и сумма. Загрузка полной сущности с её связями и последующая сериализация могут сделать лишнюю работу. Проекция позволяет вернуть специально выбранную форму результата, не превращая внутреннюю entity-модель в API ответа.

interface PaymentView {
    String getId();
    long getCents(); // Оба свойства существуют у Payment: закрытая проекция.
}

// Метод объявлен внутри Payments.
List<PaymentView> findByStatusOrderByIdAsc(String status);

var views = repository.findByStatusOrderByIdAsc("NEW");
System.out.println("projection=" + views.stream().map(v -> v.getId() + ":" + v.getCents()).toList());
projection=[p-17:1200, p-18:2000, p-19:3000]

Для интерфейса Spring Data создаёт объекты проекции через прокси. Закрытая проекция знает набор свойств и позволяет ограничить выборку нужными данными. Проекция с вычисляемым SpEL может обращаться к произвольному состоянию объекта, поэтому такую оптимизацию обещать нельзя. Простое вычисление из известных getters удобно оставить default-методу интерфейса.

Другой вариант — DTO или record с конструктором нужных значений. Это обычные объекты без проекционного прокси. В явном JPQL можно использовать конструкторное выражение; именование и конструктор должны соответствовать выбранному типу. Для интерфейсной проекции поля явного запроса должны правильно сопоставляться getters, обычно через подходящие псевдонимы.

Проекция не гарантирует отсутствие join и N+1. Вложенные свойства могут потребовать соединить таблицы или загрузить связанный объект. Проверяй фактический SQL для своего запроса. Способы загрузки связей, fetch join и EntityGraph разобраны в Relations & Fetching.

Page считает весь результат, Slice проверяет продолжение

Пользователь просит первые два новых платежа. Если экран показывает «страница 1 из N», ему нужен полный размер результата. Если экран только предлагает «показать ещё», достаточно узнать, есть ли следующий кусок. Возвращаемый тип репозитория определяет эту разницу.

Page<Payment> findByStatus(String status, Pageable pageable);
Slice<Payment> findSliceByStatus(String status, Pageable pageable);

var request = PageRequest.of(0, 2, Sort.by("id")); // Номер страницы с 0, порядок по уникальному id.
Selects.count.set(0); // StatementInspector считает SELECT, реально отправленные Hibernate.
var page = repository.findByStatus("NEW", request);
System.out.println("page=" + ids(page.getContent()) + ", total=" + page.getTotalElements()
    + ", selects=" + Selects.count.get());
Selects.count.set(0);
var slice = repository.findSliceByStatus("NEW", request);
System.out.println("slice=" + ids(slice.getContent()) + ", hasNext=" + slice.hasNext()
    + ", selects=" + Selects.count.get());
page=[p-17, p-18], total=3, selects=2
slice=[p-17, p-18], hasNext=true, selects=1

В демо три подходящих строки и размер страницы два. Page выполнил выборку данных и count. Slice запросил дополнительную строку для проверки продолжения, но вернул только две. Подробности счётчика видны в полном файле; он не добавляет собственный SELECT для проверки результата.

РезультатЧто знает вызывающий кодЦена
PageДанные, общий размер, число страницЧасто отдельный count; иногда размер выводится из полученного короткого результата
SliceДанные и наличие следующего кускаДополнительная строка вместо общего count
Список с ограничениемТолько возвращённые данныеБез обещания общего размера и продолжения

Page не обязан всегда отправлять два запроса: на неполной странице Spring Data иногда может определить размер без count. Для сложного JPQL или native SQL count также должен корректно отражать условия. Join, который размножает платежи, требует учитывать distinct и реальный смысл количества строк.

Большое смещение заставляет базу пройти и отбросить много строк. Для длинного журнала полезна навигация по последнему ключу: например «после пары createdAt/id», с подходящим индексом и устойчивым порядком. Дополнительный уникальный id разрешает равенство времён. При изменениях между двумя запросами offset-страницы способны повторять или пропускать записи; простой count тоже не делает весь просмотр единым снимком.

Пагинация сущности вместе с fetch join коллекции может размножить строки и привести к ограничению результата в памяти или ошибке в зависимости от настроек Hibernate. Для списка платежей часто безопаснее сначала выбрать страницу id, затем нужные данные по этим id, сохранив порядок.

Spring Data JDBC сохраняет агрегат без контекста персистентности

У платежа есть корень с id и статусом, а также принадлежащие ему строки проводки. Spring Data JDBC читает такую структуру и сохраняет её явно. У него нет JPA-контекста, dirty checking и ленивого прокси связи. Изменённый объект нужно передать save; после чтения он не наблюдается скрыто открытой сессией.

@Table("ledger_payment") // Здесь аннотации Spring Data Relational, а не JPA.
record LedgerPayment(@Id @Column("id") Long id, @Column("status") String status,
    @MappedCollection(idColumn = "payment_id", keyColumn = "line_index") List<LedgerLine> lines) {}

@Table("ledger_line")
record LedgerLine(@Column("account_id") String account, @Column("cents") long cents) {}

interface Ledger extends CrudRepository<LedgerPayment, Long> {}

var saved = repository.save(new LedgerPayment(null, "NEW", List.of(new LedgerLine("payer", 1_000))));
long firstToken = token(jdbc); // У таблицы строк есть дополнительный identity-столбец row_token.
var changed = new LedgerPayment(saved.id(), "POSTED", saved.lines()); // Строка проводки та же.
System.out.println("without save status=" + repository.findById(saved.id()).orElseThrow().status());
repository.save(changed); // Явное сохранение всего агрегата.
System.out.println("after save status=" + repository.findById(saved.id()).orElseThrow().status());
System.out.println("child row_token=" + firstToken + " -> " + token(jdbc));
System.out.println("child count=" + jdbc.queryForObject("select count(*) from \"ledger_line\"", Long.class));

Полный JdbcAggregateDemo.java создаёт таблицы H2 с явно согласованными именами столбцов. row_token не входит в модель: база назначает его каждой новой строке, чтобы увидеть замену. Данные проводки остались прежними, но токен изменился. При сохранении существующего агрегата JDBC удалил принадлежащие ему строки и записал актуальный набор заново.

Это важная цена простого агрегатного подхода. Большая коллекция может дать много записи при маленьком изменении корня. Границу агрегата выбирают по тому, что должно согласованно сохраняться и принадлежит корню. Ссылку на другой самостоятельный агрегат обычно представляют id или AggregateReference, а не включают его целиком во владение первого.

Spring Data JDBC подходит, когда нужен понятный жизненный цикл небольшого агрегата и явное сохранение. JPA удобнее там, где полезны контекст, отслеживание изменений и развитая загрузка связей. Оба подхода всё равно требуют индексов, ограничений базы, транзакций и контроля фактических запросов. Для сложного отчёта или точечного массового изменения полезнее явный SQL, чем попытка выразить всё одним save.

  • Репозиторий — прокси над механизмом своего хранилища. Он не отменяет правила JPA, JDBC и транзакций.
  • JPA save выбирает persist или merge по новизне. При merge учитывай возвращённый объект; внешняя транзакция определяет время managed-состояния.
  • Derived query разбирается по Java-свойствам. Явный Query выполняет написанные условия и не дополняется смыслом имени метода.
  • Проекция задаёт форму данных. Page часто добавляет count, Slice проверяет продолжение дополнительной строкой.
  • JDBC сохраняет агрегат явно. Его дочерние строки могут быть пересозданы даже при неизменных значениях.

На собеседовании

Как Spring Data создаёт реализацию интерфейса репозитория?

Фабрика модуля создаёт прокси и собирает способы выполнения методов. В JPA стандартные CRUD-методы идут в базовую реализацию через EntityManager; методы поиска получают запрос из имени или аннотации; свой фрагмент даёт отдельный код. Поэтому интерфейс экономит обычную обвязку, но Hibernate и JDBC продолжают работать под ним.

Границу бизнес-операции задаю в сервисе. Успешные отдельные save не означают, что весь перевод атомарен: для него нужна общая транзакция.

  • Объявленные поисковые методы и свои фрагменты требуют осмысленной транзакционной настройки. Поведение CRUD нельзя автоматически переносить на любой метод интерфейса.
  • При нескольких модулях разделяю пакеты и модели, чтобы JPA и JDBC не пытались обслуживать неоднозначный репозиторий.
  • Для сложного фильтра использую пользовательский фрагмент или Specifications, сохраняя понятную модель поиска.

Что делает save в Spring Data JPA? Почему важен возвращённый объект?

Save выбирает persist для нового объекта и merge для существующего. По умолчанию новизна определяется nullable-версией, затем id, если подходящей версии нет. Merge копирует состояние в managed-объект и возвращает его, а исходная detached-ссылка остаётся прежней.

В демо первый save вернул тот же объект, второй — другой. Без внешней транзакции после возврата дальнейший setter сам не обновил базу. В общей транзакции managed-сущность отслеживается, поэтому обязательного save после каждого изменения нет.

  • Назначенный id без nullable-версии может направить новый объект в merge. Для явного определения новизны есть Persistable.isNew; его состояние должно корректно меняться после сохранения и чтения.
  • Save не равен немедленному SQL, а saveAndFlush не равен commit внешней транзакции. Ограничение может обнаружиться при последующей синхронизации.
  • Merge всего объекта из JSON способен перенести нежелательные поля и связи. Для перехода статуса загружаю текущий платёж и применяю разрешённую команду.
Объект имеет назначенный id и version=null. Можно ли по одному id уверенно сказать, что save вызовет merge?

Нет. При обычной nullable-проверке версии null означает новизну, поэтому будет выбран persist. Если nullable-версии нет, проверяется id. Нужно знать всю стратегию определения новизны, включая возможный Persistable.

Когда выбрать запрос по имени, Query и проекцию?

Для короткого понятного условия выберу имя метода по свойствам модели. Если условия становятся длинными или нужен особый запрос, запишу Query либо свой фрагмент. В JPA Query по умолчанию содержит JPQL с entity и Java-полями; nativeQuery включает SQL конкретной базы.

Для списка id и сумм возвращу проекцию, чтобы результат отражал нужды ответа. Закрытый интерфейс перечисляет свойства; DTO или record задаёт обычный объект с нужными значениями.

  • Явный Query выполняет свои условия. Слова имени метода не добавляют пропущенный фильтр статуса или проверку владельца платежа.
  • Вложенная проекция может потребовать join или загрузку связи. Форму результата и число SQL проверяю отдельно.
  • Для bulk UPDATE нужны Modifying и транзакция; уже загруженные сущности могут устареть. Согласую flush и очистку контекста.

Чем Page отличается от Slice и что плохо в далёких страницах?

Page даёт общий размер результата и число страниц, поэтому часто выполняет count. Slice знает только, есть ли следующий кусок: для этого берёт дополнительную строку. В нашем опыте Page выполнил два SELECT, Slice — один, при одинаковых двух возвращённых платежах.

Большое offset заставляет базу пройти много лишних строк. Для длинного журнала рассматриваю переход по последнему ключу с устойчивым порядком и подходящим индексом.

  • Page не всегда выполняет count: неполный результат иногда позволяет вывести размер без дополнительного запроса.
  • Сортировка должна различать равные значения, например createdAt плюс уникальный id. Между запросами данные меняются, поэтому offset способен повторять или пропускать записи.
  • Коллекционный fetch join и пагинация требуют осторожности из-за размножения строк. Часто выбираю страницу id, затем нужный граф отдельным запросом.

Чем Spring Data JDBC отличается от Spring Data JPA?

JPA работает с контекстом, managed-сущностями, dirty checking и стратегиями загрузки связей. JDBC читает и явно сохраняет агрегат без контекста персистентности. Setter вне JPA-контекста и создание нового JDBC-объекта сами по себе базу не меняют.

В JDBC-демо изменили только статус корня, но save пересоздал принадлежащую строку проводки. Поэтому выбираю границу агрегата и оцениваю размер коллекций; простой API save не всегда означает одну короткую команду SQL.

  • Ссылка на самостоятельный агрегат обычно представлена id или AggregateReference. Включённый дочерний объект означает владение и совместное сохранение.
  • У JDBC есть свои аннотации отображения и контроля версии. Entity-модель JPA не переносится автоматически в другой модуль.
  • Если нужны отчёт или точечный массовый UPDATE, явный SQL может быть проще обоих способов сохранения графа. Транзакции и ограничения базы нужны в каждом случае.
  • Spring Data JPA: Persisting Entities — persist/merge, версия и id, Persistable.
  • Spring Data Commons: Query Methods — имена методов, ограничения, Page и Slice.
  • Spring Data JPA: Projections — интерфейсы, DTO, вложенность и ограничения выбора полей.
  • Spring Data JPA: Transactionality — базовые методы, запросы и сервисная граница.
  • Spring Data JDBC: Persisting Entities — сохранение агрегата и повторная запись дочерних строк.
