Spring: Dependency Resolution

Injection point задаёт требования к ссылке: тип, generic-аргументы, qualifiers и допустимость отсутствия. Spring сначала ограничивает кандидатов, затем выбирает одного или собирает группу. Конструктор показывает контракт объекта; Optional разрешает отсутствие; ObjectProvider переносит запрос к фабрике на более поздний момент.

Конструктор делает обязательные зависимости частью инварианта

PaymentService без Gateway не умеет выполнять свою основную работу. Если Gateway спрятан в @Autowired поле, обычный new PaymentService() создаёт внешне существующий, но неполный объект. Ошибка вылезает позже при первом вызове. Конструктор требует зависимость в момент создания и не позволяет забыть её при ручной сборке или тесте.

Для класса с единственным конструктором @Autowired не нужен: Spring использует его для разрешения параметров. Поле можно сделать final. Это не магия immutable service — внутреннее состояние зависимости может быть изменяемым, — но сам контракт «после конструктора ссылка задана» становится понятным без знания Spring.

Setter и field injection происходят после конструктора при population объекта. Поэтому обращаться к field-injected зависимости из конструктора рано. Setter полезен, если объект действительно допускает изменение или отсутствие collaborator и сохраняет корректное значение по умолчанию. Field injection скрывает контракт и связывает полноценное создание объекта с reflection/processor; удобство короткой записи имеет эту цену.

При нескольких конструкторах явно обозначь намерение. Только один может быть @Autowired(required=true). Если несколько помечены required=false, Spring выбирает удовлетворимый вариант с наибольшим числом зависимостей; при невозможности использует подходящий default/primary constructor, если он есть. Несколько конструкторов не означают автоматическое «всегда взять самый длинный».

Большой конструктор — сигнал, что у класса много требований. Field injection этот сигнал прячет. Не нужно дробить сервис ради произвольного числа параметров, но стоит понять, почему один объект одновременно знает про платежи, уведомления, отчётность и управление сессиями.

Каждый injection point задаёт запрос к множеству кандидатов

Autowired начинается с требуемого типа и metadata injection point: параметр, поле или аргумент factory method. Spring учитывает типы определений, generic-аргументы, qualifiers и eligibility для autowiring. Bean, подходящий по имени, но не по типу, не становится корректной зависимостью. Несколько зарегистрированных реализаций — нормальная ситуация, пока правила дают понятный ответ.

Для PaymentService с Gateway это могут быть клиенты разных регионов. Qualifier eu означает требование к роли, а не приказ взять произвольный объект с похожим названием. Когда остаётся несколько допустимых кандидатов для одиночной ссылки, вступают приоритеты. Если победителя нет, контейнер сообщает неоднозначность; он не выбирает случайный bean.

Важно отличать процесс выбора от создания. Сопоставление старается пользоваться metadata без instantiation, но недостаточная type information factory methods/FactoryBean способна потребовать ранней инициализации. Поэтому точные сигнатуры помогают и пониманию, и предсказуемому startup.

Под капотом: DependencyDescriptor и resolver

DependencyDescriptor хранит injection point и ResolvableType. QualifierAnnotationAutowireCandidateResolver проверяет квалификацию, DefaultListableBeanFactory находит кандидатов и выбирает результат. doResolveDependency отдельно обрабатывает Optional/Provider, suggested values, name shortcuts и multi-element dependencies. Это объясняет, почему один заученный линейный список «сначала имя, потом тип» плохо описывает все запросы.

Qualifier и generics выражают смысл зависимости

@Qualifier может совпадать с bean name, поскольку имя используется как fallback qualifier value. Но сама семантика — сужение type-compatible кандидатов. Несколько бинов могут иметь одинаковый qualifier eu: один нужен для одиночного клиента, а List<Gateway> с eu должен собрать группу. Для растущего проекта собственная qualifier-аннотация с region/channel часто понятнее свободных строк.

Generic metadata тоже участвует в выборе. Если определения объявлены как Store<Payment> и Store<Refund>, параметр Store<Payment> сужает выбор. JVM стирает generic-типы из runtime-класса объекта, но Spring читает сохранённые сигнатуры классов, методов и injection point через ResolvableType. Raw type или чрезмерно общий @Bean return type теряет эту информацию.

@Resource из jakarta.annotation задаёт другую исходную модель: именованный ресурс. При явном name Spring ищет это имя и проверяет совместимость типа. Без имени использует имя поля или property; при отсутствии такого bean стандартная реализация может перейти к type-based resolution. Resource ставят на поля/методы, а не используют как constructor injection. Для явной зависимости по роли чаще яснее constructor плюс Qualifier.

Переименование поля может незаметно изменить name-based выбор, поэтому бизнес-контракт лучше делать явным. Аналогично Lombok-конструктор нужно проверять по реально сгенерированным параметрам: qualifier на поле не обязан автоматически копироваться в параметр. Смотри деломбокированный код и annotation-copy настройки, а не только короткий исходник.

Qualifier всегда сильнее Primary, потому что это поиск по имени.

Qualifier сначала ограничивает допустимых кандидатов. Primary выбирает среди них. Primary в другом регионе не отменяет eu, а два eu-кандидата всё ещё требуют выбора для одиночной ссылки.

Primary выбирает предпочтительный bean, Fallback обозначает резерв

@Primary означает предпочтение для одиночной зависимости среди допустимых кандидатов. Если в локальном множестве два Primary, это ошибка неоднозначности. Отмечать каждую реализацию Primary бессмысленно: предпочтение должно иметь одного победителя. Явный qualifier помогает обозначить особую роль в отдельных injection points.

@Fallback появился в Framework 6.2. Он понижает кандидат для одиночного выбора: если среди оставшихся ровно один обычный non-fallback bean, тот выигрывает. Но Fallback не исчезает из контейнера и не становится недоступным для группового внедрения. Если обычных кандидатов несколько, аннотация сама не выбирает среди них.

Когда primary/non-fallback-предпочтение не определило результат, в 7.0.9 учитываются имя зависимости и suggested name qualifier, затем highest priority, unique default candidate и зарегистрированные resolvable dependencies. @Order упорядочивает группы; это не обещание выбрать минимальный Order вместо явного single-bean контракта. @Priority имеет отдельную single-candidate семантику.

Совпадение parameter name с bean name требует, чтобы имя параметра сохранилось в bytecode. Начиная с 6.1 для обычных Java-параметров нужен компиляторный -parameters; Spring больше не извлекает имена из debug local variable table. В 6.2+ name matching может идти через оптимизированный shortcut, который проверяет тип, qualifiers и конфликты предпочтений. Поэтому имя параметра — вспомогательная часть алгоритма, а не надёжная замена квалификации.

Resolvable dependencies — специальные объекты окружения вроде самого ApplicationContext или BeanFactory, которые контекст предоставляет по контракту без обычного пользовательского определения. Их наличие не оправдывает инъекцию контекста в каждый сервис: для бизнес-класса видимые зависимости полезнее универсального доступа ко всему графу.

Коллекция собирает кандидатов, а не победителя одиночного выбора

Антифрод может прогонять платёж через несколько правил. List<Rule> означает «собери подходящие Rule», а не «выбери Rule и положи в список». Primary и Fallback не выкидывают остальные подходящие элементы. Qualifier на коллекции по-прежнему ограничивает группу, потому что меняется требование к допустимости, а не предпочтение одиночного результата.

Массивы и List можно упорядочить Ordered, @Order или @Priority: меньшее число раньше. Без указаний порядок следует регистрации. Не превращай случайный registration order в бизнес-гарантию. Map<String, Gateway> собирает ссылки под bean names; @Order не означает общий контракт сортировки keys Map или Set.

Полный пример DiDemo.java, Java 21, Spring 7.0.9. Ниже — фрагмент.

Вывод одновременно показывает три разных правила: поле ещё null в конструкторе, одиночный eu-запрос выбрал euSafe, а List содержит все четыре Gateway. Порядок списка задан явно. FallbackConfig отдельно подтверждает, что один обычный bean выигрывает у резервного без Primary.

Пустая коллекция зависит от injection point: для единственного конструктора multi-element аргумент может разрешиться в пустую коллекцию; для обычного required field/method отсутствие matching элементов по умолчанию считается неудовлетворённой зависимостью. Если отсутствие плагинов — часть контракта, укажи её явно через provider stream или соответствующую необязательность и проверь именно свой вариант.

Optional описывает отсутствие, ObjectProvider — отложенный запрос

Optional<T> делает отсутствие T допустимым, но не лечит два равноправных кандидата. При внедрении разрешается фактическое состояние: Optional содержит выбранный bean или empty. Это снимок результата внедрения, а не динамический registry lookup на каждом isPresent.

ObjectProvider<T> внедряется как handle к фабрике и разрешает target при вызове. Это нужно для lazy-получения, необязательной интеграции и повторного получения prototype. Если target singleton, несколько вызовов всё равно вернут одну опубликованную ссылку. Сам provider не меняет scope и не обеспечивает отсутствие ошибок в target constructor.

@Autowired(required=false) на поле оставляет значение по умолчанию при отсутствии зависимости. На многопараметрическом методе может пропустить весь method call, если хотя бы один обязательный аргумент не найден; это не поэлементная подстановка null. Nullable-аргумент явно допускает null. Эти варианты лучше выбирать по инварианту объекта, а не использовать как универсальное средство скрыть startup failure.

Lazy proxy на injection point откладывает получение ссылки до первого вызова. Но если dependency на самом деле отсутствует, ошибка перемещается в runtime. Lazy не выражает optional-контракт; для него подходят Optional или provider.getIfAvailable. Если вызвать provider.getObject прямо из конструктора, отложенность сразу теряется.

Ошибка DI говорит о конкретном запросе, а не о неисправности Spring

При NoSuchBeanDefinitionException сначала найди требуемый type/generic/qualifier и проверь definitions: package scan, import, active profiles, conditions, declared factory type. При NoUniqueBeanDefinitionException выпиши имена реально подходящих кандидатов, а затем проверь primary/fallback и совпадение имени зависимости. Эти две ветки требуют разных исправлений.

Необязательность имеет смысл только тогда, когда приложение корректно работает без интеграции. Если обязательный банковский gateway скрыт за getIfUnique и в отсутствие выбора код молча пропускает платёж, это уже бизнес-ошибка. Контейнер может сообщить факт, но не определить за тебя контракт отсутствия.

DI не вычисляет маршрутизацию по данным каждого платежа. Один constructor injection выбирается при создании сервиса, а решение «этот клиент платит через банк X» требует явной стратегии: registry Map, router или отдельной фабрики бизнес-объектов. Не пытайся выразить runtime-выбор новым набором Primary-аннотаций.

Цикл обязательных конструкторов относится к порядку создания и раскрыт в Lifecycle. Provider для нового экземпляра и scoped proxy раскрыты в Scopes. Здесь главное — восстановить требования injection point и объяснить, почему контейнер выдал именно эту ссылку.

  • Конструктор выражает обязательные требования; field injection происходит после new.
  • Qualifier ограничивает множество, Primary/Fallback помогают одиночному выбору внутри него.
  • List собирает группу и не сужается до Primary.
  • Optional и provider не делают неоднозначность корректной.
  • Runtime-маршрутизация платежей — бизнес-решение, а не повторный autowiring сервиса.

На собеседовании

Почему constructor injection предпочитают field injection?

Я делаю обязательные зависимости явными при создании объекта. Конструктор позволяет final-поля, простую ручную сборку и тест без контекста. Объект после конструктора уже имеет нужные ссылки, а field injection сначала оставляет поле с default value и заполняет его позднее.

Setter использую, когда optional или изменяемая dependency действительно допускается контрактом. Field injection короче, но скрывает требования и момент готовности.

  • Единственный конструктор используется без Autowired; несколько конструкторов требуют понимания candidate selection.
  • Constructor injection проявляет циклы и перегруженные ответственности вместо того, чтобы скрывать их в полях.

Как Spring выбирает между несколькими бинами одного типа?

Я начинаю с требуемого типа и qualifiers injection point. Qualifier ограничивает кандидатов, а Primary задаёт предпочтение для одной ссылки среди допустимых. Если одного победителя нет, Spring сообщает неоднозначность; имя и другие metadata могут уточнить выбор.

Для регионального клиента я делаю роль явной qualifier-аннотацией. Имя параметра оставляю удобством, потому что оно зависит от сохранения parameter metadata.

  • Generic signatures участвуют как дополнительные qualifiers через ResolvableType, несмотря на type erasure объекта.
  • С 6.2 есть Fallback; при одном обычном non-fallback bean он выигрывает у резервных.
  • В 7.0.9 есть name shortcuts и unique default-candidate. Алгоритм нужно связывать с версией, а не считать вечной последовательностью по памяти.

Что попадёт в List бинов и как управлять порядком?

Я получу все подходящие для этого injection point beans. Qualifier ограничит группу, а Primary не оставит в списке один элемент. Ordered или Order задаст порядок массива/List, меньшее значение раньше.

Для registry по имени можно внедрить Map с ключом String. Если порядок правил влияет на результат, я задаю его явно и не полагаюсь на расположение классов.

  • Order не задаёт порядок singleton creation: это другой граф, где влияют зависимости и DependsOn.
  • Не переношу sorting guarantee List на Set и Map; одинаковые Order требуют отдельного решения, если нужна строгая последовательность.
Если пометить euSafe как Primary, исчезнет ли fallback из all?

Нет. Это preference одиночного запроса. В DiDemo all по-прежнему содержит четыре Gateway; qualifier eu на all сузил бы группу до двух региональных кандидатов.

Чем Optional отличается от ObjectProvider?

Optional описывает допустимое отсутствие на этапе внедрения. ObjectProvider хранит возможность обратиться к фабрике позже. Для optional-интеграции я могу использовать getIfAvailable, а для нового prototype на каждую операцию — getObject.

Оба подхода требуют понятного контракта ошибок. Optional не устраняет неоднозначность, provider не меняет scope и не гарантирует успешное создание.

  • getIfAvailable возвращает null при отсутствии, но падает при нескольких равноправных кандидатах; getIfUnique возвращает null и при неоднозначности.
  • Если provider вызывается уже в конструкторе, выигрыша от отложенной зависимости нет.

Чем @Autowired отличается от @Resource?

Autowired разрешает зависимость по типу и metadata injection point; Resource начинается с имени ресурса. При явном Resource name это lookup по имени с type-check, при отсутствии name Spring выводит его из поля/property и может перейти к type fallback.

Для обязательных collaborator я чаще выбираю constructor injection и явную роль qualifier. Resource уместен, когда контракт именно именованный ресурс.

  • Resource относится к Jakarta common annotations и поддерживает поля/методы, а не конструкторы.
  • Переименование поля способно изменить name-based lookup: это скрытая связь API и сборки.
