Spring: Dependency Resolution

Когда в приложении несколько подключений к банкам, сервису нужно получить подходящую ссылку. Spring читает требования его конструктора: какой тип нужен и какую роль должно выполнять подключение. Для одного аргумента он выбирает один бин, для списка собирает группу. Разберём, почему эти запросы дают разные результаты и как выразить свой выбор явно.

Обязательная зависимость нужна уже в момент создания сервиса

PaymentService умеет проводить платёж только с Gateway. Если зависимость хранится в поле с @Autowired, вызов new PaymentService() создаёт объект с пустым полем. При первом платеже он упадёт. Конструктор с аргументом Gateway сразу показывает, что нужно для работы сервиса, и требует эту ссылку при сборке.

Spring использует единственный конструктор класса без @Autowired. Ссылку можно записать в final-поле: после создания сервиса она уже задана. В тесте достаточно вызвать тот же конструктор с подставным Gateway. Изменяемое состояние самого Gateway по-прежнему требует отдельного решения, но связь между сервисом и зависимостью видна прямо в коде.

Поля и сеттеры Spring заполняет после выполнения конструктора. Поэтому поле с @Autowired внутри конструктора ещё хранит исходное значение. Сеттер подходит объекту, который действительно допускает замену зависимости или умеет работать без неё с заранее заданным поведением. Для обязательного подключения к банку конструктор делает момент готовности яснее.

При нескольких конструкторах обозначь нужный через @Autowired. Только один может требовать обязательного выбора, с required=true. Несколько вариантов с required=false позволяют Spring выбрать доступный конструктор с наибольшим числом разрешимых аргументов. Если подходящих аргументов нет, остаётся допустимый конструктор по умолчанию или основной конструктор, если он предусмотрен. Одного размера сигнатуры для выбора недостаточно.

Длинный конструктор помогает заметить, сколько требований накопилось у класса. Если PaymentService одновременно зависит от отчётности, уведомлений и управления сессиями, стоит проверить его обязанности. Перенос этих зависимостей в поля сокращает запись, но сохраняет ту же сложность.

Тип даёт кандидатов, уточнения помогают выбрать нужного

Приложение работает с несколькими банками. Для аргумента Gateway selected подходят четыре зарегистрированных Gateway. Все они умеют выполнять нужный контракт, но сервису нужна одна конкретная ссылка. Spring читает требование аргумента: его тип, параметры обобщённого типа и аннотации выбора.

Уточнение @Qualifier("eu") оставляет европейские подключения. Если их два, @Primary может обозначить предпочтительное. Получается два вопроса: какие объекты подходят этому аргументу и какой из подходящих нужен для одиночной ссылки. Схема разделяет эти решения.

Spring старается узнать типы по описаниям, до создания объектов. Поэтому точный тип метода @Bean и getObjectType у FactoryBean помогают заранее определить кандидатов. Если этих сведений мало, часть проверки типа может потребовать создания фабрики или объекта раньше ожидаемого.

Под капотом: как требование аргумента попадает в фабрику

DependencyDescriptor описывает место внедрения, например аргумент конструктора. ResolvableType сохраняет сведения о типе и его параметрах. Проверку @Qualifier выполняет QualifierAnnotationAutowireCandidateResolver, а поиск и выбор — DefaultListableBeanFactory.

В doResolveDependency есть отдельные пути для одной ссылки, коллекции, Optional и отложенного получения. Поэтому правило для Gateway нельзя автоматически переносить на List<Gateway>: эти запросы требуют разных результатов.

Qualifier выражает роль, generics уточняют тип

Значение @Qualifier удобно описывает роль: eu, sandbox или notifications. Несколько бинов могут иметь одинаковую роль. Для одного Gateway это создаёт дополнительный выбор; для List<Gateway> с тем же уточнением получается группа европейских подключений. Имя бина тоже может выступать значением qualifier, но совместимость типа проверяется в любом случае.

Если строк становится много, собственная аннотация с полями region и channel делает требования понятнее. Например, сервис явно просит европейское подключение для карточных платежей. Такая запись описывает смысл зависимости и меньше зависит от названия метода конфигурации.

Обобщённые типы также участвуют в выборе. Store<Payment> отличается для Spring от Store<Refund>, если описания и аргументы сохраняют эти сигнатуры. JVM стирает параметры типа из класса самого объекта, но в объявлениях классов и методов остаются метаданные. Spring читает их через ResolvableType. Объявление сырого Store или слишком общего Object теряет полезное уточнение.

@Resource из jakarta.annotation начинает поиск с имени ресурса. С явным name Spring ищет этот бин и проверяет тип. Без name использует имя поля или свойства; если такого имени нет, стандартная реализация может перейти к выбору по типу. Аннотация применяется к полям и методам. Для аргумента конструктора роль удобно выразить через @Qualifier.

При использовании Lombok проверь сгенерированный конструктор: аннотация поля должна попасть на его аргумент, чтобы участвовать в выборе. Это зависит от правил копирования аннотаций. Сгенерированный код показывает реальные требования Spring точнее, чем сокращённый исходник.

Primary европейского Gateway заставит любой сервис использовать именно его.

Сначала Spring проверяет требования конкретного аргумента. При @Qualifier("us") европейский Gateway отсеется по роли. Primary задаёт предпочтение среди тех, кто прошёл эту проверку.

Primary задаёт предпочтение, Fallback обозначает резерв

@Primary помогает выбрать одну ссылку среди допустимых кандидатов. У европейских Gateway можно предпочесть euSafe, сохранив euFast для явного запроса или коллекции. Если в одном контексте одинаково подходят два Primary, предпочтение снова неоднозначно и Spring сообщает ошибку.

@Fallback, доступный с Framework 6.2, помечает резервный вариант. Если остался ровно один обычный кандидат, Spring выберет его перед резервными. При нескольких обычных кандидатах нужно другое уточнение. Резервный бин при этом остаётся доступен и попадает в подходящие коллекции.

Отдельный фрагмент DiDemo.java создаёт два подключения. В обоих методах один возвращаемый тип; резерв отмечен явно. Вывод — последняя строка запуска ./run.sh DiDemo.

@Configuration(proxyBeanMethods=false)
static class FallbackConfig {
    @Bean Gateway real() { return new Gateway("real"); }
    @Bean @Fallback Gateway reserve() { return new Gateway("reserve"); }
}
// Отдельный контекст из main:
try (var ctx = new AnnotationConfigApplicationContext(FallbackConfig.class)) {
    System.out.println("non-fallback wins: " + ctx.getBean(Gateway.class).name());
}
non-fallback wins: real

Имя аргумента тоже способно уточнить выбор. С -parameters компилятор сохраняет имя в байткоде, и Spring может сопоставить его с именем бина. С 6.1 для обычных Java-параметров требуется этот флаг. В примере с двумя контекстами аргумент gateway выбирает родительский бин: наличие локального объекта того же типа само по себе не даёт ему преимущество.

Порядок списка и предпочтение одной ссылки задаются разными правилами. @Order сортирует группу. @Priority также участвует в выборе одиночного кандидата. Если выбор банка важен для смысла сервиса, явная роль через @Qualifier понятнее зависимости от порядка или имени аргумента.

Под капотом: дополнительные правила выбора в 7.0.9

В determineAutowireCandidate сначала ищется primary или единственный обычный кандидат среди резервных. Дальше проверяются имя зависимости и имя, предложенное qualifier, затем наивысший @Priority, единственный кандидат по умолчанию и специальные зависимости окружения.

В некоторых случаях doResolveDependency выбирает совпадающее имя быстрее, проверив тип, qualifier и конфликты предпочтений. Это оптимизация того же выбора. Контекст также предоставляет специальные объекты, например BeanFactory и ApplicationContext, без пользовательского определения каждого из них.

Коллекция получает группу подходящих бинов

Антифрод проверяет платёж несколькими правилами. Аргумент List<Rule> просит всю подходящую группу. Для List<Gateway> в нашем примере действует тот же принцип: @Primary выбирает одну ссылку для selected, а all получает четыре подключения. Если на all добавить @Qualifier("eu"), группа сузится до двух европейских бинов.

Для массивов и List порядок задают Ordered, @Order или @Priority: меньшее число идёт раньше. Без явных указаний элементы следуют регистрации. Если порядок влияет на бизнес-результат, задай его явно. Map<String, Gateway> позволяет получить подключения под именами бинов; на порядок ключей такой карты и Set правило сортировки List переносить нельзя.

Фрагменты DiDemo.java, Java 21, Spring 7.0.9. Здесь видны все четыре регистрации, требования Client и само сравнение. В полном файле есть также получение необязательной зависимости, разобранное в следующем шаге.

record Gateway(String name) {}
static class Missing {}
static class FieldClient {
    @Autowired Gateway gateway;
    FieldClient() { System.out.println("field during constructor: " + gateway); }
}
static class Client {
    final Gateway selected;
    final List<Gateway> all;
    final Optional<Missing> optional;
    final ObjectProvider<Missing> deferred;
    Client(@Qualifier("eu") Gateway selected, List<Gateway> all,
           Optional<Missing> optional, ObjectProvider<Missing> deferred) {
        this.selected=selected; this.all=all; this.optional=optional; this.deferred=deferred;
    }
}
@Configuration(proxyBeanMethods=false)
@Import({Client.class, FieldClient.class})
static class Config {
    @Bean @Qualifier("eu") @Order(1) Gateway euFast() { return new Gateway("eu-fast"); }
    @Bean @Qualifier("eu") @Primary @Order(2) Gateway euSafe() { return new Gateway("eu-safe"); }
    @Bean @Order(3) Gateway us() { return new Gateway("us"); }
    @Bean @Fallback @Order(4) Gateway fallback() { return new Gateway("fallback"); }
}
// В main; импорты и оболочка класса — в полном файле.
try (var ctx = new AnnotationConfigApplicationContext(Config.class)) {
    var c = ctx.getBean(Client.class);
    System.out.println("selected: " + c.selected.name());
    System.out.println("field after creation: " + ctx.getBean(FieldClient.class).gateway.name());
    System.out.println("all: " + c.all.stream().map(Gateway::name).toList()); // Собираются все четыре бина.
}

Пустая группа зависит от места внедрения. Для единственного конструктора аргумент-коллекция может разрешиться в пустую коллекцию. Для обычного обязательного поля или метода отсутствие элементов приводит к неудовлетворённой зависимости. Если набор плагинов может быть пустым по смыслу приложения, это требование стоит выразить через отложенный поток provider или явную необязательность.

Optional допускает отсутствие, ObjectProvider переносит получение

Интеграция с необязательной системой уведомлений может отсутствовать в конфигурации. Optional<T> позволяет собрать сервис с пустым значением. Выбор выполняется при внедрении: сервис получает выбранный объект или Optional.empty. Если подходящих объектов несколько и победителя нет, Spring сообщает неоднозначность.

ObjectProvider<T> позволяет обратиться к фабрике позже, когда зависимость действительно нужна. Он полезен для отложенного создания и для получения нового prototype на каждую операцию. Повторный запрос singleton возвращает сохранённый объект: provider использует правила бина, а не создаёт собственную область видимости.

У Client выше оба аргумента относятся к Missing, которого в конфигурации нет. Следующие строки взяты из того же main; контекст уже создал Client, а переменная c содержит его ссылку.

System.out.println("optional: " + c.optional.isPresent());
System.out.println("available: " + (c.deferred.getIfAvailable() != null));
try { c.deferred.getObject(); } // Обязательный запрос выполняется только здесь.
catch (org.springframework.beans.factory.NoSuchBeanDefinitionException ex) {

@Autowired(required=false) оставляет поле с исходным значением, если зависимости нет. Для метода с несколькими аргументами Spring может пропустить весь вызов, когда обязательный аргумент не найден. Nullable-аргумент разрешает передать null. Выбери вариант, который совпадает с реальным поведением сервиса без интеграции.

@Lazy в месте внедрения даёт прокси, который получает объект при первом использовании. Если обязательный объект отсутствует, ошибка возникнет тогда. Для допустимого отсутствия подходят Optional или getIfAvailable. Вызов provider.getObject уже внутри конструктора получает зависимость сразу, в момент сборки.

Ошибка выбора помогает проверить конкретное требование сервиса

При NoSuchBeanDefinitionException выпиши тип и уточнения аргумента. Затем проверь, зарегистрировано ли подходящее описание: нужный пакет, импорт, профиль, условие и возвращаемый тип @Bean. При NoUniqueBeanDefinitionException выпиши имена кандидатов и правила выбора. Это две разные причины, и исправление следует из каждой из них.

Допустимое отсутствие — решение самого приложения. Если уведомления можно временно пропустить, пустой Optional может быть корректным. Если обязательный Gateway скрыть за getIfUnique и при null пропустить платёж, сервис выполнит неверный бизнес-контракт. Сообщение контейнера помогает обнаружить проблему, а смысл отсутствия определяет разработчик.

Выбранная при создании сервиса ссылка сохраняется для его работы. Маршрут конкретного платежа — отдельное решение: например, сервис получает Map подключений и router выбирает банк по данным клиента. Аннотации DI описывают сборку, а бизнес-стратегия принимает решения во время обработки платежа.

Циклы конструкторов разбираются в Bean Lifecycle, а повторное получение prototype и зависимости на один запрос — в Bean Scopes. Здесь опорный вопрос такой: что требовало место внедрения и какое правило привело к полученной ссылке?

  • Конструктор получает обязательную зависимость при создании. Поля и сеттеры заполняются после него.
  • Tип, generics и qualifier определяют подходящих кандидатов. Primary и Fallback помогают выбрать одну ссылку.
  • С -parameters имя аргумента может уточнить выбор; Qualifier выражает роль явно.
  • Коллекция собирает подходящую группу. Primary сохраняет остальные элементы.
  • Optional допускает отсутствие, provider переносит получение. Бизнес-маршрут платежа выбирает отдельная стратегия.

На собеседовании

Почему внедрение через конструктор предпочитают полям?

Я показываю обязательные зависимости в момент создания объекта. Конструктор позволяет использовать final-поля, собирать сервис вручную и тестировать его без контекста. При внедрении в поле конструктор сначала выполняется с исходным значением, а Spring заполняет поле позже.

Сеттер подходит, когда замена или отсутствие зависимости действительно допустимы. Для обязательного Gateway конструктор делает требования и момент готовности сервиса яснее.

  • Единственный конструктор Spring использует без Autowired. При нескольких нужно обозначить выбор и учитывать доступность аргументов.
  • Конструктор помогает обнаружить цикл создания и слишком много обязанностей класса: все требования видны в сигнатуре.

Как Spring выбирает между несколькими бинами одного типа?

Сначала я смотрю на тип аргумента, его generics и qualifier. Они задают подходящих кандидатов. Primary помогает выбрать одну ссылку среди них. Если победитель отсутствует, Spring сообщает неоднозначность; совпадение имени и другие правила могут уточнить выбор.

Для европейского подключения я указываю роль явно через Qualifier. Имя аргумента тоже участвует в выборе с -parameters, поэтому простое переименование иногда меняет получаемую ссылку.

  • Store<Payment> и Store<Refund> можно различить по сохранённым сигнатурам. Spring читает их через ResolvableType.
  • С 6.2 Fallback обозначает резерв. Единственный обычный кандидат выигрывает у резервных.
  • Правила одиночного выбора и сборки коллекции различаются. Primary определяет предпочтение одной ссылки, а не исключает остальные бины из группы.

Что попадёт в List бинов и как управлять порядком?

List получает все бины, подходящие требованиям этого аргумента. Qualifier ограничивает группу, а Primary сохраняет остальные элементы. Ordered или Order задаёт порядок: меньшее значение раньше.

Для доступа по имени я могу внедрить Map с ключами String. Порядок правил, влияющий на результат, задаю явно, вместо зависимости от регистрации классов.

  • Order сортирует группу, а порядок создания singleton следует зависимостям и DependsOn.
  • Одинаковые значения Order оставляют дополнительный выбор порядка. Если он важен, значения должны различаться; сортировку List нельзя переносить на Set и Map.
Что изменится, если поставить Qualifier eu на all?

В список попадут euFast и euSafe. Primary по-прежнему выберет euSafe для selected, а региональный список сохранит оба подходящих подключения.

Чем Optional отличается от ObjectProvider?

Optional допускает отсутствие зависимости при внедрении. ObjectProvider позволяет обратиться к фабрике в выбранный момент. Для необязательной интеграции я использую getIfAvailable, а для нового prototype на каждую операцию — getObject.

При нескольких одинаково подходящих объектах Optional и getIfAvailable сообщают неоднозначность. Повторное получение через provider соблюдает область видимости самого бина.

  • getIfUnique возвращает null и при отсутствии, и при неоднозначном выборе. getIfAvailable различает эти ситуации и сообщает ошибку во второй.
  • Получение через provider внутри конструктора происходит уже при сборке; отложенность появляется только при более позднем вызове.

Чем @Autowired отличается от @Resource?

Autowired выбирает по типу и уточнениям места внедрения. Resource начинает с имени ресурса: явного name или имени поля/свойства. Тип результата проверяется. Если выведенного имени нет, стандартная реализация Spring может перейти к выбору по типу.

Для обязательной зависимости я обычно выбираю конструктор и явную роль через Qualifier. Resource подходит, когда сам контракт подключения задан именем.

  • Resource относится к Jakarta common annotations и применяется к полям и методам.
  • При имени, выведенном из поля, переименование способно изменить выбор зависимости. Это нужно учитывать при рефакторинге.
