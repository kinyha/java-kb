Spring: Application Events

После платежа несколько компонентов реагируют на один факт: готовят чек, обновляют статистику, ведут журнал. Событие даёт им общий сигнал, а способ доставки определяет связь с исходным вызовом. В обычной конфигурации слушатели работают сразу в потоке издателя; Async переносит их в пул, а транзакционный слушатель ждёт нужного результата. Для важной обработки после сбоя понадобится сохраняемая запись о работе.

Событие позволяет сообщить о факте, сохранив выбор реакции у слушателей

Платёж завершён. Теперь нужно подготовить чек, обновить статистику и журнал действий. Если сервис платежей внедряет все эти компоненты, каждое новое действие меняет его зависимости. Через событие сервис сообщает факт Paid, а нужные бины сами подписываются на этот тип.

ApplicationEventPublisher.publishEvent передаёт объект системе событий контекста. Слушатель объявляется через @EventListener на методе управляемого бина либо реализует ApplicationListener. Тип аргумента задаёт интересующее событие. Сам издатель знает факт и контракт публикации, а состав слушателей определяется конфигурацией.

Событием может быть обычный объект, например record с ID платежа и суммой. Spring оборачивает такой объект в PayloadApplicationEvent, а метод слушателя получает исходные данные. Передавай снимок нужного состояния: ссылка на изменяемый объект делает результат зависимым от того, когда слушатель её прочитает.

Эта форма связи скрывает конкретных получателей, но время их работы всё равно влияет на издателя. Сначала проследим обычную синхронную рассылку. Название «событие» само по себе ещё ничего не говорит о потоке, транзакции и сохранности доставки.

Под капотом: регистрация, выбор типа и повторная публикация

EventListenerMethodProcessor находит методы и создаёт адаптеры слушателей. Рассылкой занимается ApplicationEventMulticaster; обычный контекст использует SimpleApplicationEventMulticaster. Java-конфигурация регистрирует нужную обработку аннотаций. Метод на объекте, созданном вручную, становится слушателем только после явного подключения к этой инфраструктуре.

condition задаёт дополнительный фильтр SpEL. Обращение #a0 к первому аргументу работает и без -parameters; имя аргумента требует сохранённых имён. Для события с generic-параметром его тип должен быть доступен во время выполнения: через конкретный подкласс или ResolvableTypeProvider. Одной записи new Event<Payment>(...) при стирании типов недостаточно.

Результат обычного синхронного метода слушателя может стать новым событием; массив или коллекция публикуются по элементам. Это создаёт вложенную рассылку ещё до возврата исходного слушателя. Случайная цепь, снова публикующая тот же факт, способна уйти в рекурсию. События дочернего контекста также передаются родительскому; в обратную сторону такой рассылки нет.

Синхронный слушатель выполняется в стеке издателя и влияет на его ошибку

По умолчанию все подходящие слушатели выполняются в том же потоке, который вызвал публикацию. publishEvent возвращается после их завершения. Задержка отправки чека входит в длительность исходного запроса, а обычный слушатель видит привязанный к этому потоку транзакционный контекст.

@Order задаёт порядок вызова: меньшее число идёт раньше. Без явного порядка на расположение методов в файле полагаться не стоит. В EventsDemo порядок задан для всех трёх методов, поэтому можно точно предсказать, до кого дойдёт событие при ошибке второго.

Полный пример EventsDemo.java, Java 21, Spring 7.0.9. 

cd examples/spring-core
./run.sh EventsDemo
import org.springframework.context.annotation.*;
import org.springframework.context.event.EventListener;
import org.springframework.core.annotation.Order;

public class EventsDemo {
    record Paid(boolean fail) {}

    static class Listeners {
        @EventListener @Order(1)
        public void audit(Paid event) {
            System.out.println("audit: " + Thread.currentThread().getName());
        }

        @EventListener @Order(2)
        public void receipt(Paid event) {
            System.out.println("receipt");
            if (event.fail()) throw new IllegalStateException("receipt failed");
        }

        @EventListener @Order(3)
        public void statistics(Paid event) {
            System.out.println("statistics");
        }
    }

    @Configuration(proxyBeanMethods = false)
    static class Config {
        @Bean Listeners listeners() { return new Listeners(); }
    }

    public static void main(String[] args) {
        try (var ctx = new AnnotationConfigApplicationContext(Config.class)) {
            System.out.println("success:");
            ctx.publishEvent(new Paid(false));
            System.out.println("caller returned");
            System.out.println("failure:");
            try {
                ctx.publishEvent(new Paid(true));
            } catch (IllegalStateException e) {
                // Ошибка второго слушателя прерывает рассылку и доходит до издателя.
                System.out.println("caller caught: " + e.getClass().getSimpleName());
            }
        }
    }
}

При стандартной настройке исключение слушателя прерывает рассылку и возвращается издателю. Для этой политики у multicaster можно заменить ErrorHandler: например, зарегистрировать ошибку и продолжить. Это решение меняет смысл успешной публикации, поэтому пропущенную обработку нужно наблюдать явно.

Уже выполненные действия живут по правилам своих ресурсов. Запись в ту же транзакцию БД может откатиться вместе с издателем; отправленный HTTP-запрос или письмо остаётся внешним эффектом. Поэтому обязательные проверки платежа удобнее вызвать прямо в сервисе, а реакции на завершённый факт выбирать с учётом их времени и отказов.

Async переносит обработку в пул, а завершение и контекст становятся отдельными

Чек можно подготовить позже, чтобы клиент не ждал. @Async вместе с @EnableAsync направляет вызов конкретного слушателя в executor. Остальные обычные слушатели продолжают выполняться синхронно. Для опыта пул выбран явно: один поток, очередь на десять задач.

В AsyncEventDemo защёлка удерживает слушатель до разрешения из main. Это делает сравнение времени возврата воспроизводимым, без задержек через sleep. Публикация возвращается раньше завершения обработки, хотя сама задача действительно принята пулом.

Полный пример AsyncEventDemo.java, Java 21, Spring 7.0.9. 

cd examples/spring-core
./run.sh AsyncEventDemo
import java.util.concurrent.CountDownLatch;
import java.util.concurrent.TimeUnit;
import org.springframework.context.annotation.*;
import org.springframework.context.event.EventListener;
import org.springframework.scheduling.annotation.*;
import org.springframework.scheduling.concurrent.ThreadPoolTaskExecutor;

public class AsyncEventDemo {
    record Paid() {}

    static class Gate {
        final CountDownLatch release = new CountDownLatch(1);
        final CountDownLatch finished = new CountDownLatch(1);
    }

    static class Receipt {
        final Gate gate;
        Receipt(Gate gate) { this.gate = gate; }

        @Async("eventsExecutor")
        @EventListener
        public void send(Paid event) throws InterruptedException {
            // Удерживаем слушатель, чтобы порядок не зависел от скорости потоков.
            if (!gate.release.await(5, TimeUnit.SECONDS)) throw new IllegalStateException();
            System.out.println("listener: " + Thread.currentThread().getName());
            gate.finished.countDown();
        }
    }

    @Configuration(proxyBeanMethods = false)
    @EnableAsync(proxyTargetClass = true)
    static class Config {
        @Bean Gate gate() { return new Gate(); }
        @Bean Receipt receipt(Gate gate) { return new Receipt(gate); }
        @Bean ThreadPoolTaskExecutor eventsExecutor() {
            var pool = new ThreadPoolTaskExecutor();
            pool.setCorePoolSize(1);
            pool.setMaxPoolSize(1);
            pool.setQueueCapacity(10);
            pool.setThreadNamePrefix("events-");
            return pool; // Контейнер запускает и закрывает пул.
        }
    }

    public static void main(String[] args) throws InterruptedException {
        try (var ctx = new AnnotationConfigApplicationContext(Config.class)) {
            var gate = ctx.getBean(Gate.class);
            ctx.publishEvent(new Paid());
            System.out.println("publisher returned");
            gate.release.countDown();
            if (!gate.finished.await(5, TimeUnit.SECONDS)) throw new IllegalStateException();
        }
    }
}

Ошибка тела такого void-слушателя обрабатывается через AsyncUncaughtExceptionHandler и не возвращается уже ушедшему издателю. Ошибка принятия задачи — другой случай: переполненная очередь способна отклонить отправку прямо во время публикации. Настройка размера очереди и политики отказа определяет поведение под нагрузкой.

Поток пула получает свои ThreadLocal. Транзакция издателя и данные текущего HTTP-запроса автоматически в него не переносятся; нужные значения передают в событии, а контекст логирования настраивают отдельно. Слушателю для доступа к БД нужна собственная корректная транзакционная граница.

Порядок постановки задач через @Order отличается от порядка их завершения. Если второе действие использует результат первого, вырази зависимость явно: составной обработчик, цепь событий или сохраняемый процесс. Возврат нового события из метода @Async тоже заменяют явным вызовом publisher.

Под капотом: Async у слушателя и executor у multicaster

Executor можно назначить самому multicaster с именем applicationEventMulticaster. Тогда он передаёт в пул всех слушателей, поддерживающих асинхронное выполнение. Это более широкое изменение политики контекста, чем @Async на одном методе.

В Spring 7.0.9 транзакционный адаптер объявляет supportsAsyncExecution=false, чтобы зарегистрировать синхронизацию в исходной транзакции. После выбранной фазы сам метод с @Async может уйти в пул. Это сохраняет условие «после commit», но обработка всё равно выполняется отдельно и может потеряться при падении процесса.

TransactionalEventListener сохраняет вызов до выбранной фазы транзакции

Обычный слушатель получает Paid сразу после публикации. Если затем сохранение платежа откатится, уже отправленный чек окажется ложным. @TransactionalEventListener связывает обработку с результатом текущей транзакции: по умолчанию используется AFTER_COMMIT.

При публикации адаптер регистрирует синхронизацию и удерживает событие до нужной фазы. Поэтому возврат publishEvent внутри сервиса ещё предшествует транзакционным слушателям. Синхронный AFTER_COMMIT всё же работает на пути завершения транзакции, до возврата её внешнему вызову; его длительность продолжает влиять на ответ.

TransactionEventDemo использует учебный менеджер без БД. Он печатает место commit/rollback, а настоящая инфраструктура Spring выполняет синхронизации. Опыт проверяет фазы, порядок и отсутствие транзакции; сохранение строк в БД здесь не моделируется.

Полный пример TransactionEventDemo.java, Java 21, Spring 7.0.9. 

cd examples/spring-core
./run.sh TransactionEventDemo
import org.springframework.context.annotation.*;
import org.springframework.context.event.EventListener;
import org.springframework.core.annotation.Order;
import org.springframework.transaction.*;
import org.springframework.transaction.annotation.EnableTransactionManagement;
import org.springframework.transaction.event.*;
import org.springframework.transaction.support.*;

public class TransactionEventDemo {
    record Paid() {}

    static class Listeners {
        @EventListener
        public void ordinary(Paid event) { System.out.println("ordinary"); }

        @TransactionalEventListener(phase = TransactionPhase.BEFORE_COMMIT)
        public void before(Paid event) { System.out.println("before commit"); }

        @TransactionalEventListener @Order(1)
        public void committed(Paid event) { System.out.println("after commit"); }

        @TransactionalEventListener(phase = TransactionPhase.AFTER_ROLLBACK)
        @Order(1)
        public void rolledBack(Paid event) { System.out.println("after rollback"); }

        @TransactionalEventListener(phase = TransactionPhase.AFTER_COMPLETION)
        @Order(2)
        public void completed(Paid event) { System.out.println("completion"); }
    }

    // Учебный менеджер без БД. Синхронизации и фазы исполняет настоящий Spring.
    static class DemoTxManager extends AbstractPlatformTransactionManager {
        protected Object doGetTransaction() { return new Object(); }
        protected void doBegin(Object tx, TransactionDefinition definition) {}
        protected void doCommit(DefaultTransactionStatus status) {
            System.out.println("manager commit");
        }
        protected void doRollback(DefaultTransactionStatus status) {
            System.out.println("manager rollback");
        }
    }

    @Configuration(proxyBeanMethods = false)
    @EnableTransactionManagement
    static class Config {
        @Bean Listeners listeners() { return new Listeners(); }
        @Bean PlatformTransactionManager transactionManager() {
            return new DemoTxManager();
        }
    }

    public static void main(String[] args) {
        try (var ctx = new AnnotationConfigApplicationContext(Config.class)) {
            var tx = new TransactionTemplate(ctx.getBean(PlatformTransactionManager.class));
            System.out.println("outside transaction:");
            ctx.publishEvent(new Paid()); // fallbackExecution оставлен false.

            System.out.println("commit:");
            tx.executeWithoutResult(status -> {
                ctx.publishEvent(new Paid());
                System.out.println("publication returned");
            });

            System.out.println("rollback:");
            tx.executeWithoutResult(status -> {
                ctx.publishEvent(new Paid());
                status.setRollbackOnly();
                System.out.println("publication returned");
            });
        }
    }
}

При отсутствии активной транзакции этот слушатель по умолчанию пропускается. fallbackExecution=true разрешает обработать событие сразу в таком случае. Включай его, если такое поведение подходит контракту: фактической фиксации, которую можно дождаться, вне транзакции нет.

После commit новая запись и новая ошибка требуют отдельного решения

AFTER_COMMIT сообщает о свершившемся результате. Исключение на этом этапе уже не отменит платеж. Для синхронного BEFORE_COMMIT ошибка ещё может привести к откату, поэтому перенос одного и того же метода между фазами меняет бизнес-поведение.

Есть тонкость самого API: фаза @TransactionalEventListener(AFTER_COMMIT) реализована внутри afterCompletion с проверкой результата COMMITTED. В стандартном пути AbstractPlatformTransactionManager исключения таких callbacks записываются в лог и не пробрасываются вызывающему коду. Это отличается от отдельного TransactionSynchronization.afterCommit(), где ошибка пробрасывается. При диагностике важно назвать конкретный механизм, а не просто сказать «после commit».

Соединение или EntityManager исходной транзакции ещё может быть привязано к потоку после её завершения. Видимость ресурса создаёт ловушку: изменение данных через него не получает следующего commit автоматически. Для новой записи из такого обработчика вызывай отдельный управляемый сервис с REQUIRES_NEW; это отдельная фиксация и отдельный возможный отказ.

Комбинация транзакционного слушателя и Async откладывает постановку задачи до выбранной фазы, а затем выполняет её в другом потоке. Чек не уйдёт до успешного платежа, но успешный платеж ещё не доказывает успешную отправку чека. Для важных реакций нужна сохраняемая запись о предстоящей работе.

Под капотом: что проверить в исходниках и реактивном приложении

В TransactionalApplicationListenerSynchronization видно две точки: обработка BEFORE_COMMIT в beforeCommit, остальные фазы в afterCompletion(status). TransactionSynchronizationUtils.invokeAfterCompletion оборачивает каждый callback в try/catch с логированием. Поэтому ошибки этих callbacks требуют собственного наблюдения и повторов.

С версии 6.1 доступны и реактивные транзакционные события. Их контекст живёт в Reactor Context, поэтому передаётся через источник события; для публикации служит TransactionalEventPublisher. Модель thread-local из синхронного JDBC-приложения туда переносить буквально нельзя. Подробное управление реактивной транзакцией остаётся в разделе доступа к данным.

Важное событие должно пережить падение процесса и повторную доставку

Платёж зафиксирован, а процесс упал за миг до запуска AFTER_COMMIT или до чтения задачи из памяти пула. После перезапуска Spring Core не восстановит потерянное событие. Транзакционная фаза выбирает момент обработки; долговечность возникает там, где записано само намерение выполнить действие.

В outbox бизнес-изменение и запись события сохраняют одной транзакцией в одной БД. После commit отдельный отправитель читает эту запись; другой вариант — CDC, например Debezium. Если сервис упал до отправки, запись остаётся доступной после перезапуска. Это вывод из архитектуры хранения, а не дополнительное свойство @EventListener.

Отправитель может успеть доставить сообщение и упасть до отметки об успехе. При повторе получатель увидит то же событие ещё раз. Устойчивый ID и идемпотентная обработка связывают повтор с уже выполненной работой; отметка обработанного ID и локальный результат по возможности фиксируются атомарно. Outbox закрывает окно потери между бизнес-commit и сохранением события, сохраняя задачу работы с повторами.

Spring Modulith предлагает журнал публикаций для подходящих транзакционных слушателей: запись создаётся в исходной транзакции и отмечается после успешной обработки. Для доставки между сервисами нужны выбранные транспорт и правила подтверждения. Конкретные настройки Kafka/CDC и полной транзакции БД разобраны в соседних разделах.

В проде полезно видеть ID события, длительность и ошибки каждого слушателя, заполненность очереди, число отказов и возраст необработанной записи. Если действие определяет успех платежа, вырази его в понятной общей транзакционной границе. Если оно должно продолжиться после перезапуска, начни с сохраняемой работы и стратегии повторов.

  • Обычная публикация синхронна: время и ошибка слушателя входят в вызов издателя.
  • Async меняет поток и обработку ошибок; порядок отправки задач ещё не задаёт порядок завершения.
  • TransactionalEventListener выбирает фазу текущей транзакции; без неё по умолчанию событие пропускается.
  • После commit платеж уже сохранён. Новая запись и ошибка обработчика требуют отдельного решения.
  • Для продолжения после перезапуска храни событие вместе с бизнес-данными и рассчитывай на безопасные повторы.

На собеседовании

Как работают события Spring и как ошибка слушателя влияет на издателя?

Я публикую объект через ApplicationEventPublisher, а методы бинов с @EventListener выбираются по типу события. В обычной конфигурации они выполняются последовательно в потоке издателя, поэтому publishEvent ждёт окончания обработки.

Ошибка слушателя прерывает стандартную рассылку и возвращается издателю. Уже выполненные внешние действия сохраняются; их нельзя считать автоматически откатанными вместе с публикацией.

  • Order задаёт вызов слушателей, а ErrorHandler multicaster способен изменить политику остановки.
  • Обычный объект оборачивается в PayloadApplicationEvent; условие SpEL и доступные generic-метаданные дополнительно ограничивают выбор.
  • Возврат события из синхронного слушателя создаёт вложенную публикацию; случайная цепь может рекурсивно публиковать сама себя.

Когда вызывается TransactionalEventListener и что будет без транзакции?

Он регистрирует обработку события в синхронизациях текущей транзакции. По умолчанию метод вызывается после успешного commit. Можно выбрать фазу до commit, после rollback или после любого завершения.

Без активной транзакции метод по умолчанию пропускается. FallbackExecution разрешает немедленную обработку в этом случае, если это соответствует смыслу реакции.

  • BEFORE_COMMIT ещё способен сорвать фиксацию; AFTER_COMMIT реагирует на уже сохранённые данные.
  • В стандартном PlatformTransactionManager AFTER_COMMIT этой аннотации выполняется через afterCompletion: ошибки логируются. Отдельный synchronization.afterCommit имеет другую политику проброса.
  • Связанные ресурсы после commit ещё доступны, но новые изменения через них не получают нового commit. Для новой записи нужна отдельная корректная транзакция, например REQUIRES_NEW у вызываемого сервиса.

Что меняется, если добавить Async к слушателю событий?

Вызов направляется в выбранный executor при подключённой поддержке Async. Издатель возвращается раньше завершения слушателя. Поэтому длительность и ошибка обработки становятся отдельными от исходного вызова.

Я явно выбираю пул, размер очереди и обработку ошибок. Данные события передаю снимком, а собственную транзакцию слушателя задаю отдельно: thread-local транзакция издателя в другой поток не переходит.

  • Order управляет порядком отправки задач, а завершение при нескольких потоках зависит от их выполнения.
  • Ошибка тела void-метода попадает в AsyncUncaughtExceptionHandler. Отклонение самой задачи пулом может возникнуть ещё у издателя.
  • Async вместе с TransactionalEventListener откладывает передачу в пул до выбранной фазы, сохраняя риск потери задачи в памяти при падении.

Почему After Commit не гарантирует доставку и как помогает outbox?

После commit процесс может упасть до выполнения слушателя. Локальное событие и задача в памяти пула потеряются. Поэтому факт сохранённого платежа ещё не означает отправленного чека.

Для важной доставки я сохраняю событие в outbox вместе с бизнес-данными одной транзакцией. Отдельный отправитель продолжает работу после перезапуска, а получатель умеет безопасно обработать повтор по ID события.

  • Сбой после доставки, но до отметки об успехе создаёт повтор. Требуется идемпотентность конечного действия, а не только повтор чтения outbox.
  • Если запись платежа и outbox находятся в независимых транзакциях, исходное окно потери сохраняется.
