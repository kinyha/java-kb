Spring: Kafka in Spring

Spring Kafka прячет KafkaProducer и KafkaConsumer за двумя вещами. KafkaTemplate отправляет запись асинхронно, а ключ записи выбирает партицию. @KafkaListener превращает метод в контейнер: потоки, каждый со своим консьюмером, читают партиции и коммитят смещение после обработки. Самое важное поведение спрятано в обработчике ошибок: по умолчанию он десять раз подряд повторяет упавшую запись, держа всю партицию, а потом пропускает её с одной строкой в логе.

Платёж разносят по сервисам через Kafka, а Spring берёт на себя цикл poll

После списания платёжный сервис публикует событие payment-completed. Его читают бухгалтерия, антифрод и уведомления, каждая в своём темпе. Если бухгалтерия упала на час, события ждут её в топике, а платежи продолжают проходить. Как устроены топики, партиции и группы потребителей, разобрано в Kafka Basics.

Голый клиент Kafka требует много обвязки. Консьюмер не потокобезопасен, его poll надо крутить в цикле в своём потоке, следить за коммитом смещений, ребалансировками и ошибками. Spring Kafka заменяет это на KafkaTemplate для отправки и @KafkaListener для чтения. Обвязка не исчезает, а переезжает в контейнер с настройками по умолчанию, и эти настройки надо знать.

Демо KafkaDemo.java поднимает настоящий брокер Kafka в режиме KRaft внутри той же JVM через EmbeddedKafkaKraftBroker из spring-kafka-test. Docker не нужен. У каждого топика три партиции. Стек: JDK 21, Spring Boot 4.1.1, Spring Kafka 4.1, Kafka 4.2.

cd examples/kafka
./run.sh KafkaDemo basics # ключ и партиция, concurrency
./run.sh KafkaDemo errors # обработчик ошибок по умолчанию
./run.sh KafkaDemo dlt    # повторы с паузой и dead letter topic

В Boot 4 стартер называется spring-boot-starter-kafka; Boot сам создаёт KafkaTemplate, фабрику контейнеров и KafkaAdmin по настройкам spring.kafka.*.

KafkaTemplate отправляет асинхронно, а ключ выбирает партицию

Порядок в Kafka гарантирован только внутри партиции. Чтобы события одного счёта не обогнали друг друга, им дают одинаковый ключ: производитель берёт хеш ключа и выбирает по нему партицию. Демо отправляет по два события для трёх счетов:

for (String key : List.of("acc-1", "acc-2", "acc-3", "acc-1", "acc-2", "acc-3")) {
    // send асинхронный; get() здесь только чтобы напечатать, куда легла запись.
    var meta = template.send("payments", key, "pay " + key).get().getRecordMetadata();
    System.out.println("sent key=" + key + " -> partition " + meta.partition() + ", offset " + meta.offset());
}
sent key=acc-1 -> partition 0, offset 0
sent key=acc-2 -> partition 2, offset 0
sent key=acc-3 -> partition 2, offset 1
sent key=acc-1 -> partition 0, offset 1
sent key=acc-2 -> partition 2, offset 2
sent key=acc-3 -> partition 2, offset 3

Одинаковый ключ всегда попадает в одну партицию: acc-1 оба раза в 0. Но acc-2 и acc-3 тоже оказались в одной партиции, а партиция 1 пуста. Хеш не делит ключи поровну на маленьких числах. При трёх тысячах счетов распределение выровняется, но один очень активный ключ всё равно нагрузит одну партицию и одного потребителя.

send возвращает CompletableFuture<SendResult> сразу, а запись уходит в брокер фоном пачками. Если не посмотреть на результат, ошибка отправки останется незамеченной. Блокирующий get() на каждой записи убивает пропускную способность. Обычный вариант — whenComplete с логированием и метрикой ошибок:

template.send("payment-completed", payment.accountId(), event)
        .whenComplete((result, ex) -> {
            if (ex != null) log.error("event lost for {}", payment.id(), ex); // Брокер не принял.
        });

Клиент Kafka 3.0 и новее по умолчанию отправляет с acks=all и enable.idempotence=true: брокер подтверждает запись после копирования на реплики, а повторная отправка той же пачки не создаёт дубликат в партиции. Но ни это, ни Spring не делают отправку атомарной с транзакцией базы: платёж может закоммититься, а событие — не уйти. Надёжная схема для этого — Transactional Outbox.

@KafkaListener — это контейнер потоков, и больше потребителей, чем партиций, бесполезно

@KafkaListener(id = "ledger", topics = "payments", concurrency = "4") // 4 потребителя на 3 партиции.
void onPayment(ConsumerRecord<String, String> r) {
    threadByPartition.put(r.partition(), Thread.currentThread().getName());
}

Для такого метода Spring создаёт ConcurrentMessageListenerContainer. Внутри него четыре KafkaMessageListenerContainer, у каждого свой поток и свой KafkaConsumer, все в одной группе payments-service. Поток крутит poll, получает пачку записей и по одной вызывает метод. Брокер раздаёт партиции членам группы так, что каждую партицию читает ровно один из них.

consumed: {0=ledger-0, 2=ledger-2}
ledger-0 assigned [0]
ledger-1 assigned [1]
ledger-2 assigned [2]
ledger-3 assigned []

Демо ждёт, пока ребалансировка раздаст партиции, иначе в первые мгновения все три партиции могут достаться одному потребителю, который подключился раньше остальных. Партиции между экземплярами сервиса делятся так же: три pod-а с concurrency 4 дают 12 потребителей на 3 партиции, и девять из них простаивают.

Внутри одной партиции записи обрабатываются строго по одной в одном потоке, отсюда и гарантия порядка. Если обработка медленная, распараллелить её внутри метода — значит потерять порядок и усложнить коммит. Правильнее добавить партиций, а ключ выбрать так, чтобы нагрузка распределялась.

Контейнер следит за временем между вызовами poll. Если обработка пачки заняла больше max.poll.interval.ms (по умолчанию 5 минут), брокер считает потребителя мёртвым и отдаёт его партиции другим. Начатая пачка будет обработана ещё раз другим потребителем. Тяжёлую обработку уменьшают пачкой max.poll.records или выносят из листенера.

Смещение коммитится после обработки, поэтому повтор после сбоя — норма

Spring выключает автокоммит клиента (enable.auto.commit=false) и коммитит смещения сам. Режим по умолчанию AckMode.BATCH: после того как метод успешно обработал все записи пачки из одного poll, контейнер коммитит смещение следующей записи.

Это даёт доставку «хотя бы один раз». Если pod упал после обработки, но до коммита, после перезапуска партиция продолжит с последнего закоммиченного смещения, и часть записей придёт второй раз. Для бухгалтерии это значит двойную проводку, если обработчик не идемпотентен. Защита — запомнить id обработанного события в той же транзакции базы, что и проводку, и пропускать повтор. Подробнее о гарантиях доставки — в Delivery Semantics.

AckModeКогда коммитЗачем
BATCH (по умолчанию)После обработки всей пачки pollМало коммитов, но при сбое повторится вся пачка
RECORDПосле каждой записиМеньше повторов, больше нагрузки на брокер

По умолчанию упавшая запись повторяется десять раз и пропускается

Метод бухгалтерии бросил исключение. Что сделает контейнер? Им управляет DefaultErrorHandler. Без своей настройки он повторяет запись 10 раз (9 повторов, FixedBackOff(0, 9)), а затем логирует ошибку, коммитит смещение и идёт дальше. Запись не теряется в брокере, но потребитель к ней больше не вернётся.

@KafkaListener(id = "charger", topics = "charges")
void onCharge(String value) {
    if (value.equals("bad")) {
        attempts.incrementAndGet();
        throw new IllegalStateException("bank declined"); // Ошибка на каждой попытке.
    }
    log.add(now() + " ms: processed " + value);
}

// Три записи с одним ключом — одна партиция, порядок ok-1, bad, ok-2.
for (String v : List.of("ok-1", "bad", "ok-2")) template.send("charges", "acc-1", v);
ERROR [charger-0-C-1] o.s.kafka.listener.DefaultErrorHandler : Backoff FixedBackOffExecution[interval=0, currentAttempts=10, maxAttempts=9] exhausted for charges-0@1
2185 ms: processed ok-1
7269 ms: processed ok-2
attempts for bad: 10

Для платёжного сервиса оба эффекта плохие. Временная ошибка банка не получила паузы на восстановление: десять мгновенных повторов почти всегда падают по той же причине. Постоянная ошибка, например битый JSON, остановила партицию на пять секунд и затем исчезла. Если в логах ERROR не алертится, о потерянном платеже никто не узнает.

Свой обработчик: пауза для временных ошибок и DLT для остальных

Обработчик настраивают одним бином: Boot передаст CommonErrorHandler в фабрику контейнеров. Временные ошибки повторяем с паузой, постоянные сразу отправляем в dead letter topic, где их увидят люди:

@Bean // Boot подключит этот бин к фабрике контейнеров.
CommonErrorHandler errorHandler(KafkaTemplate<Object, Object> template) {
    var recoverer = new DeadLetterPublishingRecoverer(template); // В <топик>-dlt, та же партиция.
    var handler = new DefaultErrorHandler(recoverer, new FixedBackOff(200, 2)); // 1 + 2 повтора.
    handler.addNotRetryableExceptions(IllegalArgumentException.class); // Битые данные — сразу в DLT.
    return handler;
}

@KafkaListener(id = "refunds-dlt", topics = "refunds-dlt")
void onDead(String value, @Header(KafkaHeaders.DLT_EXCEPTION_MESSAGE) String error,
            @Header(KafkaHeaders.DLT_ORIGINAL_OFFSET) long offset) { /* алерт, разбор */ }

2757 ms: attempt for bad

Битый JSON ушёл в DLT после первой попытки. bad получил три попытки и тоже ушёл в DLT, а в заголовках записи остались исходный топик, смещение и текст исключения. Паузы между попытками — около 500 мс, а не 200: после seek следующий poll ждёт данных до fetch.max.wait.ms. Реальная пауза — не меньше настроенной и не меньше задержки poll.

Имя DLT здесь refunds-dlt: так Spring Kafka 4 называет его по умолчанию. В Spring Kafka 3.x DeadLetterPublishingRecoverer писал в refunds.DLT, поэтому после обновления стоит проверить, куда уходят записи и кто их читает. Топик DLT должен существовать и иметь не меньше партиций, чем исходный: запись уходит в партицию с тем же номером.

Повторы с паузой всё ещё блокируют партицию: пока bad ждёт третьей попытки, следующие записи этого счёта стоят. Для долгих пауз, минуты и часы, есть неблокирующие повторы @RetryableTopic: запись перекладывается в топики refunds-retry-0, refunds-retry-1 с отложенным чтением, а партиция идёт дальше. Цена — порядок: следующие записи того же счёта обгонят ту, что ждёт повтора. Схема топиков повторов разобрана в Retries & DLQ.

Транзакции

С spring.kafka.producer.transaction-id-prefix KafkaTemplate работает в транзакциях Kafka, а контейнер коммитит смещение в той же транзакции, что и отправку. Для цепочки «прочитать из Kafka — записать в Kafka» это даёт exactly-once: результат и коммит смещения появятся вместе или не появятся вовсе. Читатели должны использовать isolation.level=read_committed, иначе увидят и откаченные записи.

База данных в эту транзакцию не входит. Проводка в PostgreSQL и коммит смещения в Kafka остаются двумя отдельными действиями, и между ними возможен сбой. Поэтому для «обработал событие и записал в базу» по-прежнему нужен идемпотентный обработчик, а для «записал в базу и отправил событие» — outbox.

  • Ключ выбирает партицию, порядок гарантирован только внутри неё. send асинхронный: результат проверяют в whenComplete.
  • @KafkaListener — контейнер с потоком и консьюмером на каждый concurrency; потребители сверх числа партиций простаивают.
  • Смещение коммитится после обработки: повтор после сбоя нормален, обработчик должен быть идемпотентным.
  • DefaultErrorHandler по умолчанию делает 10 мгновенных попыток, держа партицию, затем пишет ERROR и пропускает запись.
  • Свой обработчик: пауза для временных ошибок, DLT для постоянных; транзакции Kafka не включают базу.

На собеседовании

Как работает @KafkaListener и что даёт concurrency?

Для метода создаётся ConcurrentMessageListenerContainer. Concurrency задаёт число дочерних контейнеров, у каждого свой поток и свой KafkaConsumer в одной группе. Поток в цикле делает poll и по одной передаёт записи в метод, затем коммитит смещение.

Каждую партицию группа отдаёт одному потребителю, поэтому concurrency больше числа партиций бесполезен: лишние потоки простаивают. В демо при четырёх потребителях на три партиции четвёртый не получил ничего.

  • Порядок сохраняется внутри партиции, потому что её читает один поток; распараллеливание внутри метода его ломает.
  • Обработка дольше max.poll.interval.ms вызывает ребалансировку и повторную обработку пачки другим потребителем.
  • Партиции делятся между всеми экземплярами сервиса: три pod-а с concurrency 4 на трёх партициях — девять простаивающих потоков.

Что произойдёт, если @KafkaListener бросит исключение?

Ошибку обрабатывает DefaultErrorHandler. По умолчанию он возвращает позицию на упавшую запись и повторяет её ещё девять раз без паузы, всего десять попыток. Пока идут повторы, остальные записи партиции ждут. Потом он пишет ERROR в лог, коммитит смещение и идёт дальше, то есть запись для группы потеряна.

Я настраиваю свой обработчик: FixedBackOff или ExponentialBackOff для временных ошибок, addNotRetryableExceptions для битых данных и DeadLetterPublishingRecoverer, чтобы неисправимые записи попадали в DLT с заголовками об ошибке.

  • Реальная пауза между повторами не меньше задержки poll: в демо 200 мс превратились в 500.
  • Блокирующие повторы держат партицию; для долгих пауз используют @RetryableTopic с топиками повторов, жертвуя порядком.
  • В Spring Kafka 4 DLT по умолчанию называется <топик>-dlt, в 3.x — <топик>.DLT; DLT нужен с тем же числом партиций.
  • Ошибка десериализации случается до метода; её ловит ErrorHandlingDeserializer, иначе контейнер не сможет пройти запись.
Почему этот обработчик теряет платежи при сбое банка? 
@KafkaListener(topics = "charges")
void onCharge(ChargeEvent e) {
    try {
        bank.charge(e);
    } catch (Exception ex) {
        log.warn("charge failed {}", e.id(), ex); // Исключение проглочено.
    }
}

Метод не бросает исключение, поэтому контейнер считает запись обработанной и коммитит смещение. Ни повтора, ни DLT не будет: временный сбой банка превращается в потерянное списание с предупреждением в логе. Исключение нужно пробросить, чтобы сработал обработчик ошибок, а повторы и DLT настроить в CommonErrorHandler.

Как не обработать одно событие дважды?

Spring коммитит смещение после обработки, поэтому доставка — хотя бы один раз. Сбой между обработкой и коммитом или ребалансировка приводят к повтору. Единственная надёжная защита — идемпотентный обработчик: сохранить id события в той же транзакции базы, что и бизнес-изменение, и пропустить повтор по уникальному ключу.

Транзакции Kafka дают exactly-once только для цепочки Kafka → Kafka: результат и коммит смещения атомарны. База в эту транзакцию не входит.

  • Для exactly-once Kafka → Kafka нужны transaction-id-prefix у производителя и read_committed у читателей.
  • Идемпотентность производителя убирает дубликаты от повторной отправки пачки, но не от повторной обработки.
  • Для «записал в базу и отправил событие» используют transactional outbox.

Как отправить сообщение через KafkaTemplate и не потерять его?

send асинхронный: возвращает CompletableFuture, а запись уходит фоном пачками. Результат надо обработать в whenComplete, иначе ошибка отправки пропадёт незаметно. Блокировать get на каждой записи можно только там, где пропускная способность не важна.

Ключ задаю по сущности, порядок которой важен, например по счёту: тогда её события попадут в одну партицию.

  • С Kafka 3.0 по умолчанию acks=all и enable.idempotence=true; ослаблять их для платёжных событий нельзя.
  • Отправка не атомарна с транзакцией базы: событие может уйти без коммита платежа или не уйти после коммита. Решение — outbox.
  • Хеш ключа на малом числе ключей распределяет неровно; горячий ключ нагружает одну партицию.
