Spring Security: OAuth2 & JWT

В OAuth2 пароль видит только сервер авторизации, например Keycloak. Он выдаёт клиенту access token, а платёжный API принимает этот токен вместо пароля. Если токен — JWT, API проверяет его сам, без сетевого вызова: подпись публичным ключом издателя, срок жизни, издателя. Из claim-ов токена получаются права пользователя. Всё, что не проверено явно, API принимает на веру, и самое частое такое место — аудитория токена.

Платёжный API принимает токены от Keycloak, а паролей не видит

У компании десяток сервисов: платежи, возвраты, отчёты, личный кабинет. Если каждый проверяет пароль сам, пароль хранится в десяти местах, а смена политики паролей — десять релизов. Вход через Google или корпоративный SSO придётся встраивать в каждый сервис отдельно.

OAuth2 выносит вход в отдельный сервер авторизации: Keycloak, Okta, Auth0 или Spring Authorization Server. Пользователь вводит пароль только там. Клиент — веб-приложение или мобильное — получает от сервера авторизации access token. Resource server — наш платёжный API — принимает запросы с этим токеном в заголовке Authorization: Bearer и решает, пускать ли.

Эта тема про две стороны Spring Security. Большая часть — resource server: как платёжный API проверяет JWT и превращает его в права. В конце — клиентская сторона: вход через внешнего провайдера и получение токена для вызова другого сервиса.

Демо JwtDemo.java само играет роль сервера авторизации: создаёт RSA-ключ и подписывает им токены с нужными claim-ами. Платёжный API в том же процессе проверяет их публичным ключом. Keycloak для запуска не нужен.

cd examples/security
./run.sh JwtDemo # Boot 4.1.1, Spring Security 7.1, nimbus-jose-jwt 10.9.

JWT несёт утверждения открытым текстом, а подпись доказывает, кто их выдал

JWT — три части через точку: header, payload и подпись, каждая в Base64URL. Header говорит, каким алгоритмом и каким ключом подписано: {"kid":"k1","alg":"RS256"}. Payload — набор claim-ов, утверждений о пользователе и самом токене:

{
  "iss": "https://auth.payments.example", // кто выдал
  "sub": "alice",                         // о ком
  "aud": "payments-api",                  // для какого сервиса
  "exp": 1790933100,                      // до какого момента действует, секунды
  "scope": "payments.read",               // что разрешил пользователь
  "roles": ["USER"]                       // свой claim сервера авторизации
}

Base64 — не шифрование. Любой, у кого есть токен, прочитает payload, поэтому в токен не кладут номера карт и персональные данные. Защищает подпись: сервер авторизации подписывает header и payload своим приватным ключом, а API проверяет публичным. Изменить хоть один символ payload без приватного ключа нельзя.

Демо берёт настоящий токен, меняет в payload payments.read на payments.admin и собирает его обратно со старой подписью:

String[] p = jwt.split("\\.");
String payload = new String(Base64.getUrlDecoder().decode(p[1]))
        .replace("payments.read", "payments.admin"); // Повышаем себе права.
return p[0] + "." + Base64.getUrlEncoder().withoutPadding()
        .encodeToString(payload.getBytes()) + "." + p[2]; // Подпись прежняя.
tampered payload  -> 401 Bearer error="invalid_token", error_description="An error occurred while attempting to decode the Jwt: Signed JWT rejected: Invalid signature"

В выводах этой темы из заголовка WWW-Authenticate убраны поля error_uri и resource_metadata, чтобы строки помещались. Второе поле — новинка Spring Security 7: ссылка на метаданные защищённого ресурса по RFC 9728, по которой клиент узнаёт, где брать токен.

В Boot resource server включается стартером и одной настройкой. В Boot 4 стартер переименован: spring-boot-starter-security-oauth2-resource-server вместо прежнего spring-boot-starter-oauth2-resource-server.

spring:
  security:
    oauth2:
      resourceserver:
        jwt:
          issuer-uri: https://auth.payments.example/realms/payments # iss и адрес JWKS
          audiences: payments-api # Без этой строки aud не проверяется.

Resource server проверяет подпись, срок и издателя, но не аудиторию

Запрос с заголовком Authorization: Bearer перехватывает BearerTokenAuthenticationFilter. Он создаёт неаутентифицированный токен и отдаёт его в AuthenticationManager, а там JwtAuthenticationProvider вызывает JwtDecoder. Декодер выполняет проверки по порядку, и любая неудача даёт 401 с error="invalid_token".

Два вывода из демо заслуживают внимания. Первый — допуск по времени:

expired 30s ago   -> 200 payments
expired 120s ago  -> 401 Bearer error="invalid_token", error_description="An error occurred while attempting to decode the Jwt: Jwt expired at 2026-10-02T09:37:35Z"

Допуск нужен, потому что часы сервера авторизации и сервиса расходятся на секунды. Но он означает, что «токен живёт 5 минут» на деле — 6. Для коротких токенов это заметная прибавка.

Второй — аудитория. Компания выпускает токены для нескольких сервисов одним Keycloak. Токен с aud=ledger-api предназначен бухгалтерии, но платёжный API его принимает:

aud=ledger-api    -> 200 payments

Подпись верна, издатель свой, срок не истёк — а проверки аудитории нет. Любой сервис, получивший токен пользователя для своих нужд, может пойти с ним в платежи. Во втором запуске демо декодер настроен с проверками издателя и аудитории:

OAuth2TokenValidator<Jwt> aud = new JwtClaimValidator<List<String>>("aud",
        a -> a != null && a.contains("payments-api")); // Токен должен быть выдан нам.
decoder.setJwtValidator(new DelegatingOAuth2TokenValidator<>(
        JwtValidators.createDefaultWithIssuer(ISSUER), aud)); // exp/nbf + iss + aud.
strict aud=ledger -> 401 Bearer error="invalid_token", error_description="An error occurred while attempting to decode the Jwt: The aud claim is not valid"
strict aud=pay    -> 200 payments

В Boot то же самое делает одна настройка spring.security.oauth2.resourceserver.jwt.audiences. Если ты задаёшь свой бин JwtDecoder, настройки Boot к нему не применяются, и валидаторы приходится собирать самому, как в демо. Вызов setJwtValidator заменяет валидаторы целиком: без createDefault… пропадёт и проверка срока.

Если подпись JWT верна, токен можно принимать.

Подпись доказывает только, кто выдал токен. Для кого он выдан, говорит aud, и по умолчанию Spring её не проверяет. Без проверки аудитории токен любого сервиса компании открывает твой API.

Права из токена получаются конвертером, и для Keycloak его пишут сами

После проверки JwtAuthenticationConverter превращает Jwt в JwtAuthenticationToken. По умолчанию он читает claim scope или scp и делает из каждого значения authority с префиксом SCOPE_. Другие claim-ы, в том числе роли, он не трогает. Имя пользователя по умолчанию берётся из sub.

Демо добавляет к scope роли из своего claim roles:

var scopes = new JwtGrantedAuthoritiesConverter(); // scope -> SCOPE_*
var roles = new JwtGrantedAuthoritiesConverter();
roles.setAuthoritiesClaimName("roles"); // Читать из claim roles
roles.setAuthorityPrefix("ROLE_");      // и добавить префикс роли.
var converter = new JwtAuthenticationConverter();
converter.setJwtGrantedAuthoritiesConverter(jwt -> {
    var all = new ArrayList<>(scopes.convert(jwt));
    all.addAll(roles.convert(jwt));
    return all;
});
http.oauth2ResourceServer(o -> o.jwt(j -> j.jwtAuthenticationConverter(converter)));
me                -> 200 alice [SCOPE_payments.read, ROLE_USER, FactorGrantedAuthority [authority=FACTOR_BEARER, issuedAt=2026-10-02T09:39:35.616374Z]]
scope write only  -> 403 Bearer error="insufficient_scope", error_description="The request requires higher privileges than provided by the access token."
refunds as USER   -> 403 Bearer error="insufficient_scope", error_description="The request requires higher privileges than provided by the access token."
refunds SUPPORT   -> 200 refunds

Право FACTOR_BEARER — фактор аутентификации из Spring Security 7, как FACTOR_PASSWORD в Authentication. Ответ 403 в resource server всегда говорит insufficient_scope, даже если не хватило роли, а не scope: так устроен BearerTokenAccessDeniedHandler. По этому тексту причину отказа не определить.

Keycloak кладёт роли realm не в плоский список, а во вложенный объект: "realm_access": {"roles": ["SUPPORT"]}, а роли клиента — в resource_access.<client>.roles. Стандартный конвертер вложенность не понимает, и интеграция с Keycloak почти всегда начинается со своего конвертера, который достаёт jwt.getClaimAsMap("realm_access") и превращает список в ROLE_*. Без него hasRole("SUPPORT") отвечает 403 пользователю, у которого роль в Keycloak есть.

Scope и роль отвечают на разные вопросы. Scope — что пользователь разрешил клиенту делать от своего имени: мобильному приложению только чтение платежей. Роль — что пользователю можно вообще. Сильная проверка учитывает оба: hasAuthority('SCOPE_payments.refund') and hasRole('SUPPORT').

JWT нельзя отозвать, поэтому его делают короткоживущим

С настройкой issuer-uri Boot находит адрес JWKS через документ /.well-known/openid-configuration издателя. Декодер создаётся лениво: Keycloak нужен при первом запросе с токеном, а не при старте сервиса. Скачанные ключи кешируются. Сервер авторизации меняет ключи плавно: сначала публикует новый ключ рядом со старым, потом начинает подписывать им. Незнакомый kid заставляет декодер перечитать JWKS, поэтому ротация проходит без перезапуска сервисов.

Обратная сторона локальной проверки — токен нельзя отозвать. Пользователя уволили, пароль сменили, а выданный JWT продолжает работать до exp: ни один сервис не спрашивает Keycloak, жив ли токен. Поэтому access token делают коротким, на 5–15 минут, а для продления выдают refresh token, который проверяет сам сервер авторизации и может отказать.

Для платёжного сервиса типичный компромисс: короткие JWT для обычных запросов и дополнительная проверка для опасных действий. Возврат крупной суммы может требовать свежего входа: claim auth_time не старше нескольких минут или второй фактор.

OAuth2 Client получает токены, когда сервис сам ходит к другим

До сих пор платёжный API только принимал токены. Иногда сервис должен их получать. Spring Security даёт для этого клиентскую часть, стартер spring-boot-starter-security-oauth2-client. Эту часть мы не запускали: ей нужен настоящий сервер авторизации и браузер. Поведение описано по документации Spring Security.

Вход через внешнего провайдера, oauth2Login(). Админка платёжного сервиса пускает сотрудников через корпоративный Keycloak. Браузер уходит на страницу входа Keycloak, возвращается с одноразовым code, и сервер админки сам меняет code на токены прямым запросом к Keycloak. Это authorization code flow. В Spring Security 7 к нему по умолчанию добавляется PKCE (ClientSettings.requireProofKey равен true для всех клиентов): случайный секрет, хеш которого уходит в первом запросе, а сам секрет — при обмене code. Перехваченный code без секрета бесполезен. Токены остаются на сервере в сессии, браузер получает только cookie. С OpenID Connect Keycloak дополнительно выдаёт id token — сведения о том, кто вошёл.

Вызов другого сервиса от своего имени, client credentials. Ночная сверка платёжного сервиса вызывает API бухгалтерии. Пользователя нет, сервис сам получает токен у Keycloak по client_id и секрету. В Spring это регистрация клиента в настройках и OAuth2ClientHttpRequestInterceptor на RestClient. Он получает токен, кеширует до истечения и подставляет в заголовок Bearer.

spring:
  security:
    oauth2:
      client:
        registration:
          ledger:                           # Имя регистрации в коде.
            provider: keycloak
            client-id: payments-service
            client-secret: ${LEDGER_CLIENT_SECRET} # Из окружения, не из git.
            authorization-grant-type: client_credentials
            scope: ledger.read
        provider:
          keycloak:
            issuer-uri: https://auth.payments.example/realms/payments

Для SPA сейчас рекомендуют схему BFF, backend for frontend: токены держит сервер с oauth2Login(), а браузер общается с ним по cookie-сессии. Токены в localStorage браузера читает любой внедрённый скрипт, поэтому XSS превращается в кражу токена. С BFF возвращается CSRF-защита из Architecture: снова есть cookie, которую браузер шлёт сам.

  • Сервер авторизации выдаёт токен, resource server проверяет его локально публичным ключом из JWKS.
  • Payload JWT читает любой; подпись доказывает издателя, aud — для кого токен. По умолчанию Spring проверяет срок и издателя, но не aud.
  • Допуск по времени — 60 секунд. Свой JwtDecoder без createDefault… теряет проверку срока.
  • scope становится SCOPE_*, роли Keycloak из realm_access нужно доставать своим конвертером.
  • JWT не отзывается: короткий access token, refresh token, introspection для случаев, где отзыв обязателен.

На собеседовании

Как Spring Resource Server проверяет JWT?

BearerTokenAuthenticationFilter достаёт токен из заголовка Authorization и передаёт в AuthenticationManager. JwtAuthenticationProvider вызывает JwtDecoder: тот находит публичный ключ по kid из JWKS сервера авторизации, проверяет подпись, затем валидаторы — срок с допуском 60 секунд и издателя, если задан issuer-uri. Потом конвертер превращает scope в authorities SCOPE_*.

Проверка локальная: на каждый запрос Keycloak не нужен, только ключи, которые кешируются и перечитываются при незнакомом kid.

  • Аудитория по умолчанию не проверяется; нужна настройка audiences или свой JwtClaimValidator, иначе принимаются токены других сервисов.
  • setJwtValidator заменяет валидаторы целиком; без JwtValidators.createDefault… пропадает проверка exp.
  • Свой бин JwtDecoder отключает настройки Boot для декодера.
  • Ответ 403 всегда содержит insufficient_scope, даже если не хватило роли.
Что не так с этим декодером? 
@Bean
JwtDecoder jwtDecoder() {
    var decoder = NimbusJwtDecoder.withIssuerLocation(ISSUER).build();
    decoder.setJwtValidator(new JwtClaimValidator<List<String>>("aud",
            aud -> aud.contains("payments-api")));
    return decoder;
}

setJwtValidator заменил стандартные валидаторы, и остался только aud. Срок и издатель больше не проверяются: токен, истёкший месяц назад, принимается. Ещё aud может отсутствовать, и тогда лямбда упадёт с NullPointerException. Правильно: DelegatingOAuth2TokenValidator из JwtValidators.createDefaultWithIssuer(ISSUER) и проверки aud с учётом null.

Какие роли есть в OAuth2 и как работает authorization code flow?

Владелец ресурса — пользователь. Клиент — приложение, которое действует от его имени. Сервер авторизации, например Keycloak, проверяет пользователя и выдаёт токены. Resource server — API, который принимает токены.

В authorization code flow браузер уходит на страницу входа сервера авторизации и возвращается с одноразовым code. Клиент меняет code на токены прямым запросом со своим секретом или PKCE. Токен никогда не проходит через адресную строку браузера.

  • PKCE связывает запрос code и его обмен случайным секретом, поэтому перехваченный code бесполезен; сейчас его применяют и для серверных клиентов.
  • OpenID Connect добавляет id token — кто вошёл; access token — что можно делать. Путать их нельзя: id token не предназначен для вызова API.
  • Для сервис-сервис без пользователя используется client credentials. Implicit и password grant устарели.
  • Для SPA рекомендуют BFF: токены на сервере, браузеру — cookie.

Как отозвать JWT и чем он отличается от opaque token?

JWT проверяется локально по подписи, поэтому отозвать его до истечения нельзя: сервис не спрашивает сервер авторизации. Решение — короткий срок жизни access token, 5–15 минут, и refresh token, который проверяет сервер авторизации и может отказать.

Opaque token — случайная строка. Сервис проверяет его introspection-запросом к серверу авторизации, поэтому отзыв действует сразу, но каждый запрос зависит от этого сервера.

  • Чёрный список jti в Redis возвращает отзыв для JWT, но добавляет сетевой вызов, от которого JWT избавлял.
  • Для опасных операций проверяют свежесть входа по auth_time или требуют второй фактор.
  • Допуск часов 60 секунд продлевает жизнь любого токена на минуту.

Роль в Keycloak назначена, а hasRole отвечает 403. Почему?

Стандартный JwtAuthenticationConverter делает authorities только из claim scope с префиксом SCOPE_. Keycloak кладёт роли в realm_access.roles и resource_access.<client>.roles, и Spring их не видит.

Я пишу свой конвертер: достаю вложенный список ролей, добавляю префикс ROLE_ и объединяю со scope. После этого hasRole работает.

  • Имя пользователя берётся из sub, а это UUID в Keycloak; для логов удобнее principalClaimName=preferred_username.
  • Роли клиента и роли realm — разные пространства; правило должно знать, какие оно проверяет.
  • Конвертер стоит покрыть тестом на реальном токене Keycloak, а не на собранном вручную.
