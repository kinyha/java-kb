Spring Security: Architecture

Spring Security — это цепочка обычных сервлетных фильтров, которая стоит перед контроллерами. Запрос проходит её сверху вниз: сначала из него достают, кто пришёл, потом решают, можно ли ему сюда. Результат первого шага лежит в SecurityContext — ThreadLocal текущего запроса. Почти любое странное поведение — 401 вместо 403, пропавший пользователь в другом потоке, preflight без заголовков — объясняется тем, какой фильтр сработал и в каком порядке.

Стартер закрыл весь API, и даже правильный POST получает 401

Платёжному API нужна защита. Команда добавляет spring-boot-starter-security и ни строчки конфигурации. Сервис поднимается, а в логе появляется сгенерированный пароль пользователя user. Мобильное приложение тут же начинает получать ошибки, а браузер внезапно открывает страницу входа.

Демо повторяет этот момент. Пароль задан через spring.security.user.password=secret, чтобы не читать его из лога. Программа шлёт пять запросов к одному контроллеру:

cd examples/security
./run.sh SecurityDemo # Boot 4.1.1, Spring Security 7.1; только стартеры webmvc и security.
GET  no auth, JSON  -> 401 WWW-Authenticate: Basic realm="Realm", charset="UTF-8"
GET  no auth, HTML  -> 302 Location: /login
GET  user           -> 200 payment 1
POST user           -> 401 WWW-Authenticate: Basic realm="Realm", charset="UTF-8"
OPTIONS preflight   -> 401 WWW-Authenticate: Basic realm="Realm", charset="UTF-8"

Первые три строки объяснимы: без логина JSON-клиент получает 401, браузер — переход на форму, с логином всё работает. Последние две выглядят как ошибка. POST с тем же правильным паролем получает 401. Запрос браузера «можно ли сюда с чужого сайта» тоже получает 401.

Чтобы предсказывать такие ответы, а не подбирать настройки наугад, нужно понять, как устроен путь запроса. Он целиком состоит из фильтров, и шаги ниже проходят его от Tomcat до контроллера. Аутентификация паролем и хранение пользователей — тема Authentication, правила доступа — Authorization, токены — OAuth2 & JWT.

Security живёт в фильтрах сервлета, до DispatcherServlet

Tomcat прогоняет каждый запрос через цепочку jakarta.servlet.Filter, и только потом отдаёт его DispatcherServlet. Spring Security встраивается в эту цепочку одним фильтром. Поэтому он видит запрос раньше контроллеров, interceptor-ов MVC и @ControllerAdvice, и может ответить 401, не дойдя до них.

Встраивание двухступенчатое. Tomcat создаёт свои фильтры по собственным правилам и ничего не знает о бинах Spring. Поэтому в него регистрируется DelegatingFilterProxy — тонкий фильтр, который на каждом запросе находит в контексте бин с именем springSecurityFilterChain и передаёт работу ему. В Boot это делает DelegatingFilterProxyRegistrationBean; его порядок среди фильтров сервлета задаёт spring.security.filter.order, по умолчанию -100.

Бин springSecurityFilterChain — это FilterChainProxy. Он хранит список SecurityFilterChain, выбирает первую цепочку, которой подходит запрос, и прогоняет запрос через её фильтры. У каждой цепочки свой набор: у API нет формы входа, у сайта есть CSRF. Ещё FilterChainProxy проверяет URL через StrictHttpFirewall (отклоняет ;, //, закодированные слеши) и очищает SecurityContext после запроса.

Список фильтров можно увидеть в самом приложении. Демо достаёт бин FilterChainProxy и печатает фильтры каждой цепочки. Для настроек Boot по умолчанию цепочка одна:

var proxy = ctx.getBean("springSecurityFilterChain", FilterChainProxy.class);
for (SecurityFilterChain chain : proxy.getFilterChains()) { // В порядке проверки.
    chain.getFilters().forEach(f -> System.out.println(f.getClass().getSimpleName()));
}

Сначала фильтры выясняют, кто пришёл, потом последний решает, можно ли

Каждый фильтр делает одно дело и передаёт запрос дальше. Пройдём запрос GET /api/admin/stats с Basic-заголовком обычного пользователя через цепочку API из второго запуска демо. Правило цепочки: /api/admin/** только для роли ADMIN.

Правило из последнего шага стоит запомнить точно. 401 значит «не знаю, кто ты» — сработал AuthenticationEntryPoint. 403 значит «знаю, кто ты, но нельзя» — сработал AccessDeniedHandler. ExceptionTranslationFilter выбирает между ними по тому, анонимен ли текущий пользователь. Запуск демо с двумя пользователями:

GET  admin as user  -> 403
GET  admin as admin -> 200 stats

ExceptionTranslationFilter ловит только исключения, которые летят из фильтров после него. Ошибку в собственном фильтре, поставленном раньше, он не переведёт в ответ. Поэтому свой фильтр аутентификации ставят перед AuthorizationFilter: http.addFilterBefore(apiKeyFilter, AuthorizationFilter.class), и в нём не бросают исключения наружу, а оставляют контекст пустым.

Если поставить @Component на свой фильтр безопасности, он встанет в цепочку Spring Security.

Boot регистрирует любой бин-Filter в цепочке Tomcat, рядом с DelegatingFilterProxy, а не внутри SecurityFilterChain. Фильтр отработает на каждом запросе, вне правил securityMatcher, и иногда дважды, если его ещё и добавили через addFilterBefore. Свой фильтр безопасности создают внутри конфигурации цепочки или отключают его автоматическую регистрацию через FilterRegistrationBean с setEnabled(false).

SecurityContext — ThreadLocal текущего запроса, и в другой поток он не переходит

SecurityContextHolder.getContext().getAuthentication() работает в любом месте кода без параметров. Это возможно, потому что контекст лежит в ThreadLocal потока, который обрабатывает запрос. Фильтры кладут его туда в начале и очищают в конце, чтобы следующий запрос на том же потоке пула не получил чужого пользователя.

Следствие: в другом потоке контекста нет. Контроллер демо читает имя пользователя у себя и внутри CompletableFuture.supplyAsync, который выполняется в общем ForkJoinPool:

@GetMapping("/api/whoami")
String whoami() throws Exception {
    String here = name(); // Поток Tomcat: контекст положил фильтр.
    // Поток ForkJoinPool: его ThreadLocal никто не заполнял.
    String other = CompletableFuture.supplyAsync(SecurityDemo::name).get();
    return "request thread=" + here + ", pool thread=" + other;
}
GET  whoami         -> 200 request thread=user, pool thread=null

Код аудита, который пишет «кто списал деньги» из пула потоков, запишет null или упадёт. Решения: передать пользователя явным параметром, обернуть пул в DelegatingSecurityContextExecutor или DelegatingSecurityContextAsyncTaskExecutor, которые копируют контекст в задачу и очищают после. Режим MODE_INHERITABLETHREADLOCAL копирует контекст только при создании потока; пулы переиспользуют потоки, поэтому с ним пользователь одного запроса может достаться другому.

Между запросами контекст хранит SecurityContextRepository. Для формы входа это HTTP-сессия: после логина пользователь лежит в сессии, а cookie JSESSIONID связывает следующий запрос с ним. Для API с Basic или токеном сессия не нужна: SessionCreationPolicy.STATELESS не создаёт её, и пользователь восстанавливается из заголовка на каждом запросе. С Spring Security 6 контекст сохраняется в репозиторий только явно: свой фильтр логина должен вызвать securityContextRepository.saveContext, иначе на следующем запросе пользователь «забудется».

Несколько цепочек разделяют API без сессий и сайт с формой

У одного сервиса бывают разные клиенты. Мобильное приложение ходит в /api/** с Basic или токеном и не хранит cookie. Админка открывается в браузере и использует форму входа и сессию. Одной цепочке пришлось бы совмещать обе модели. Две цепочки дают каждой свой набор фильтров:

@Bean
@Order(1) // Проверяется первой.
SecurityFilterChain api(HttpSecurity http) throws Exception {
    http.securityMatcher("/api/**") // Без него цепочка поймала бы все запросы.
        .authorizeHttpRequests(a -> a
            .requestMatchers("/api/admin/**").hasRole("ADMIN")
            .anyRequest().authenticated())
        .httpBasic(Customizer.withDefaults())
        .csrf(c -> c.disable()) // Нет cookie-сессии — нечего подделывать.
        .sessionManagement(s -> s.sessionCreationPolicy(SessionCreationPolicy.STATELESS))
        .cors(Customizer.withDefaults()); // Берёт бин corsConfigurationSource.
    return http.build();
}

@Bean
@Order(2) // Всё, что не /api/**: форма входа, сессия, CSRF.
SecurityFilterChain web(HttpSecurity http) throws Exception {
    http.authorizeHttpRequests(a -> a.anyRequest().authenticated())
        .formLogin(Customizer.withDefaults());
    return http.build();
}

В цепочке API нет CsrfFilter и фильтров формы, и POST с паролем теперь проходит. Запрос вне /api/** попадает во вторую цепочку и получает переход на форму входа.

securityMatcher решает, какая цепочка обработает запрос. requestMatchers внутри authorizeHttpRequests решают, какое правило применить внутри цепочки. Их путают: правило requestMatchers("/api/**") в цепочке без securityMatcher не ограничивает цепочку, она по-прежнему ловит всё. Как только в контексте есть свой бин SecurityFilterChain, цепочка Boot по умолчанию отключается.

Цепочки объединяются: если /api/** не пустила первая, запрос проверит вторая.

FilterChainProxy берёт первую цепочку, чей securityMatcher подошёл, и больше ни одну не смотрит. Цепочка с @Order(1) без securityMatcher делает все остальные мёртвыми; Spring Security при старте падает, если такая цепочка стоит не последней.

CSRF защищает cookie от чужих сайтов, CORS разрешает чужим сайтам читать ответ

CSRF — атака через браузер жертвы. Пользователь залогинен в админке платёжного сервиса, cookie сессии лежит в браузере. Он открывает чужую страницу, а на ней форма, которая сама отправляет POST /admin/refunds на наш домен. Браузер приложит cookie автоматически, и сервер увидит обычный запрос залогиненного админа. Защита — секретный токен, который сервер выдаёт своей странице и проверяет в каждом изменяющем запросе. Чужая страница его не знает.

Поэтому CsrfFilter проверяет POST, PUT, PATCH и DELETE и пропускает GET, HEAD, OPTIONS и TRACE. Безопасные методы не должны ничего менять: GET, который списывает деньги, CSRF-защита не спасёт. Для API без cookie, где клиент сам кладёт токен в заголовок Authorization, CSRF отключают: браузер не подставит такой заголовок на чужой странице. Если же SPA ходит в API с cookie-сессией, CSRF оставляют и передают токен через cookie XSRF-TOKEN и заголовок X-XSRF-TOKEN.

Почему POST с правильным паролем получил 401, а не 403

Вернёмся к загадке из первого шага. В цепочке по умолчанию CsrfFilter стоит раньше BasicAuthenticationFilter. POST без CSRF-токена отклоняется ещё до проверки пароля. Дальше включается механизм ошибок сервлета, и это видно в DEBUG-логе того же запроса:

Securing POST /api/payments
Invalid CSRF token found for http://localhost/api/payments   # CsrfFilter: токена нет (порт убран)
Responding with 403 status code                              # AccessDeniedHandlerImpl
Securing GET /error                                          # Tomcat: error dispatch на /error
Set SecurityContextHolder to anonymous SecurityContext       # Basic на error dispatch не работает
No match found. Using default entry point ...BasicAuthenticationEntryPoint  # /error требует логина

403 вызывает sendError, и Tomcat делает внутренний переход на /error. Этот переход снова проходит FilterChainProxy. BasicAuthenticationFilter, как и большинство фильтров-наследников OncePerRequestFilter, на error dispatch не срабатывает, поэтому запрос анонимный. Страница /error закрыта правилом anyRequest().authenticated(), и клиент получает 401 вместо настоящих 403. В своей цепочке открывают error dispatch: .dispatcherTypeMatchers(DispatcherType.ERROR).permitAll() или .requestMatchers("/error").permitAll(). После этого клиент видит честный 403.

CORS

CORS работает в обратную сторону. Браузер по умолчанию не даёт скрипту сайта shop.example читать ответы нашего API на другом домене. Для запросов с нестандартными заголовками или методами он сначала шлёт preflight: OPTIONS с заголовками Origin и Access-Control-Request-Method, без логина и cookie. Если ответ не содержит Access-Control-Allow-Origin с этим сайтом, настоящий запрос не уйдёт.

Preflight не несёт логина, поэтому в цепочке по умолчанию он получил 401. .cors() ставит CorsFilter перед фильтрами аутентификации: тот сам отвечает на preflight и не пускает его дальше. Во втором запуске разрешён только магазин:

@Bean // Имя бина важно: по нему его ищет .cors().
CorsConfigurationSource corsConfigurationSource() {
    var c = new CorsConfiguration();
    c.setAllowedOrigins(List.of("https://shop.example"));
    c.setAllowedMethods(List.of("GET", "POST"));
    c.setAllowedHeaders(List.of("Authorization", "Content-Type"));
    var source = new UrlBasedCorsConfigurationSource();
    source.registerCorsConfiguration("/api/**", c);
    return source;
}
OPTIONS preflight   -> 200 Access-Control-Allow-Origin: https://shop.example
OPTIONS evil origin -> 403 Invalid CORS request

Имя метода здесь не косметика. Когда в приложении есть Spring MVC, .cors() берёт бин corsConfigurationSource по имени, а при его отсутствии — CORS-настройки MVC. В первой версии демо метод назывался cors(), и preflight получал 200 без заголовка Allow-Origin: Security пропускал его, MVC не находил настроек, а браузер такой ответ отвергает. На стороне сервера всё выглядит успешным, ошибка видна только в консоли браузера.

CORS — не защита API. Его проверяет браузер, а curl, Postman и чужой backend игнорируют. Он защищает пользователя от чужих сайтов, а не сервер от чужих клиентов. Доступ к API по-прежнему определяют аутентификация и правила авторизации.

  • Tomcat вызывает DelegatingFilterProxy, тот — бин FilterChainProxy, тот — первую подходящую SecurityFilterChain. Всё это происходит до DispatcherServlet.
  • Порядок фильтров — это алгоритм: контекст, CSRF, аутентификация, аноним, перевод исключений, авторизация.
  • 401 — неизвестный пользователь и AuthenticationEntryPoint, 403 — известный без прав и AccessDeniedHandler. Error dispatch на закрытый /error превращает 403 в 401.
  • SecurityContext лежит в ThreadLocal; в пул потоков его переносят явно.
  • CSRF нужен там, где браузер сам шлёт cookie. CORS разрешает чужому сайту читать ответ и проверяется браузером, а не сервером.

На собеседовании

Как запрос проходит через Spring Security?

Spring Security — это фильтры сервлета. В цепочку Tomcat регистрируется DelegatingFilterProxy, который на каждом запросе передаёт работу бину springSecurityFilterChain, то есть FilterChainProxy. Тот выбирает первую SecurityFilterChain, которой подходит запрос, и прогоняет его через её фильтры. Всё это происходит до DispatcherServlet.

Внутри цепочки порядок такой: восстановить SecurityContext, проверить CSRF, попробовать аутентифицировать по форме, Basic или токену, подставить анонима, затем ExceptionTranslationFilter и AuthorizationFilter, который проверяет правила. Если права не прошли, контроллер не вызывается вообще.

  • DelegatingFilterProxy нужен потому, что Tomcat создаёт фильтры сам и не знает о бинах; прокси ищет бин лениво, когда контекст уже поднят.
  • FilterChainProxy — единая точка входа: StrictHttpFirewall, очистка контекста после запроса, DEBUG-лог пути запроса.
  • Цепочек может быть несколько с securityMatcher и @Order. Срабатывает ровно одна; общая цепочка без securityMatcher должна стоять последней.
  • Бин-Filter с @Component Boot регистрирует в цепочке Tomcat, а не в SecurityFilterChain, и он отработает на всех запросах.
Фильтр API-ключей для партнёров срабатывает дважды и проверяет даже /actuator/health. Почему? 
@Component
class ApiKeyFilter implements Filter { /* проверяет X-Api-Key и пишет аудит */ }

@Bean
SecurityFilterChain partners(HttpSecurity http, ApiKeyFilter apiKey) throws Exception {
    http.securityMatcher("/partners/**")
        .addFilterBefore(apiKey, AuthorizationFilter.class);
    return http.build();
}

Из-за @Component Boot зарегистрировал фильтр ещё и в цепочке Tomcat, рядом с DelegatingFilterProxy. Там securityMatcher не действует, поэтому фильтр видит все запросы, включая health. На /partners/** он вызывается второй раз внутри SecurityFilterChain. OncePerRequestFilter скрыл бы повтор, но не убрал бы лишнюю регистрацию для всех остальных путей. Исправление: убрать @Component и создать фильтр внутри конфигурации цепочки или оставить бин и отключить его регистрацию через FilterRegistrationBean с setEnabled(false).

Когда Spring Security отвечает 401, а когда 403?

401 значит, что сервер не знает, кто пришёл: запрос анонимный или логин не прошёл. Тогда ExceptionTranslationFilter вызывает AuthenticationEntryPoint, который отвечает 401 с WWW-Authenticate для API или редиректом на форму для браузера. 403 значит, что пользователь известен, но прав не хватает: срабатывает AccessDeniedHandler.

Выбор делает ExceptionTranslationFilter, когда ловит AccessDeniedException от AuthorizationFilter: если пользователь анонимный, это 401, если аутентифицирован — 403.

  • Ошибка CSRF в цепочке по умолчанию возникает до аутентификации. Её 403 уходит на /error, error dispatch идёт анонимно, и закрытый /error превращает ответ в 401. Лечится permitAll для DispatcherType.ERROR.
  • ExceptionTranslationFilter обрабатывает только исключения из фильтров после себя. Свой фильтр раньше него должен сам формировать ответ или оставлять контекст пустым.
  • Ответы 401 и 403 настраиваются: свой AuthenticationEntryPoint и AccessDeniedHandler пишут ProblemDetail вместо HTML-страницы.
Почему preflight-запрос браузера может получить 401, хотя пользователь залогинен?

Preflight OPTIONS браузер отправляет без cookie и заголовка Authorization. Если CorsFilter не настроен, запрос идёт в фильтры аутентификации анонимным и упирается в anyRequest().authenticated(). Решение — .cors() в цепочке: CorsFilter стоит раньше аутентификации и сам отвечает на preflight.

Что такое CSRF и когда защиту можно отключить?

CSRF — атака, при которой чужой сайт заставляет браузер жертвы отправить запрос на наш сервис. Браузер сам прикладывает cookie сессии, и сервер видит законного пользователя. Защита — токен, который знает только наша страница, и CsrfFilter проверяет его на POST, PUT, PATCH и DELETE.

Отключить можно там, где аутентификация не опирается на то, что браузер шлёт сам: stateless API с токеном в заголовке Authorization. Если API работает через cookie-сессию, в том числе SPA, защиту оставляю и передаю токен через cookie XSRF-TOKEN и заголовок.

  • GET не проверяется на CSRF, поэтому GET не должен менять состояние: списание через GET защиту обходит.
  • SameSite=Lax у cookie сильно уменьшает риск, но не заменяет токен: остаются поддомены и старые браузеры.
  • Basic-аутентификация браузера тоже подставляется автоматически после ввода пароля, поэтому для неё CSRF актуален так же, как для cookie.

Чем CORS отличается от CSRF и как настроить CORS в Spring Security?

CSRF защищает сервер от запросов, которые чужой сайт отправляет от имени пользователя. CORS — политика браузера, которая решает, может ли скрипт чужого сайта читать наши ответы. Перед сложными запросами браузер шлёт preflight OPTIONS без логина, и сервер отвечает разрешёнными origin, методами и заголовками.

В Spring Security я включаю .cors() в цепочке и объявляю бин CorsConfigurationSource с конкретными origin. CorsFilter стоит перед аутентификацией, поэтому preflight не получает 401.

  • При наличии Spring MVC .cors() ищет бин по имени corsConfigurationSource. С другим именем preflight получает 200 без Allow-Origin, и ошибка видна только в браузере.
  • allowedOrigins("*") нельзя сочетать с allowCredentials(true); для нескольких поддоменов есть allowedOriginPatterns.
  • CORS не защищает API от curl и других серверов: это защита пользователя в браузере, а не контроль доступа.

Почему в @Async-методе SecurityContextHolder возвращает null?

SecurityContextHolder по умолчанию хранит контекст в ThreadLocal. Фильтры заполняют его для потока Tomcat, который обрабатывает запрос. @Async, CompletableFuture или свой пул выполняют код в другом потоке, где ThreadLocal пуст, поэтому Authentication там null.

Я передаю пользователя явно параметром или оборачиваю пул в DelegatingSecurityContextAsyncTaskExecutor, который копирует контекст в задачу и очищает после неё.

  • MODE_INHERITABLETHREADLOCAL копирует контекст только при создании потока. В пуле потоки живут долго, и задача может увидеть пользователя давно завершённого запроса.
  • Контекст очищается в конце запроса, иначе поток пула отдал бы пользователя следующему запросу.
  • В WebFlux ThreadLocal не работает вовсе: там ReactiveSecurityContextHolder хранит контекст в Reactor Context.
