Spring: Testing

Тест в Spring поднимает настоящий контекст приложения — целиком через @SpringBootTest или только один слой через срез вроде @WebMvcTest. Подъём дорогой, поэтому TestContext кеширует контексты и отдаёт готовый следующему классу с той же конфигурацией. Любое отличие — другой @MockitoBean, свойство, профиль — даёт новый контекст, и набор тестов незаметно становится медленным. @Transactional на тесте откатывает изменения, а Testcontainers даёт вместо H2 настоящий PostgreSQL.

Тест платежа должен поймать ошибку слоя, а не ждать минуту ради всего приложения

Платёжный сервис принимает POST /payments, проверяет сумму, списывает через банк и сохраняет платёж в PostgreSQL. Ошибки бывают в каждом слое: контроллер вернул 500 вместо 400, SQL работает в H2, но не в PostgreSQL, транзакция не откатилась. Юнит-тест с моками ловит ошибки логики, но не видит ни валидации Spring MVC, ни SQL, ни транзакций — их делает контейнер.

Spring Test поднимает настоящий контекст в тесте. Вопрос в том, какой контекст и как часто. Полный контекст с базой честнее, но медленнее. Срез поднимает только один слой и проверяет его быстро. Тема разбирает, как выбрать, и почему набор из двухсот тестов иногда идёт десять минут, хотя каждый тест быстрый.

Демо — небольшой Maven-проект examples/testing: приложение и четыре тестовых класса A–D, которые запускаются по алфавиту. Им нужен Docker для PostgreSQL. Стек: JDK 21, Spring Boot 4.1.1, Testcontainers 2, PostgreSQL 17.

cd examples/testing
mvn test # Docker должен быть запущен: B и D поднимают PostgreSQL в контейнере.

Срез @WebMvcTest поднимает только веб-слой, остальное подменяют

@WebMvcTest(PaymentController.class) включает автоконфигурации Spring MVC, Jackson и валидации и регистрирует только указанный контроллер и веб-компоненты: @ControllerAdvice, фильтры, конвертеры. Сервисы, репозитории и DataSource не создаются. Контроллеру нужен PaymentService, поэтому тест даёт mock:

@WebMvcTest(PaymentController.class)
class A_PaymentControllerTest {
    @Autowired MockMvcTester mvc;
    @MockitoBean PaymentService service; // Бин-заглушка вместо настоящего сервиса.

    @Test
    void negativeAmountReturns400WithoutCallingService() {
        var result = mvc.post().uri("/payments").contentType(MediaType.APPLICATION_JSON)
                .content("{\"account\":\"acc-1\",\"cents\":-5}");
        assertThat(result).hasStatus(400);
        verify(service, never()).pay(any()); // Валидация остановила запрос раньше.
    }
}

Срезов много, и у каждого своя граница: @DataJpaTest — JPA и репозитории с тестовой транзакцией, @JdbcTest — JdbcTemplate и DataSource, @JsonTest — сериализация, @RestClientTest — HTTP-клиент с заглушкой сервера, @DataRedisTest, @WebFluxTest. В Boot 4 срезы переехали в модули своих технологий: @WebMvcTest теперь лежит в spring-boot-webmvc-test, пакет org.springframework.boot.webmvc.test.autoconfigure, и подключается стартером spring-boot-starter-webmvc-test.

@WebMvcTest всегда поднимает только веб-слой, как бы ни было устроено приложение.

Срез фильтрует то, что находит сканирование. Первая версия демо держала сервис и репозиторий вложенными static-классами внутри класса @SpringBootApplication, и срез упал: No qualifying bean of type 'JdbcClient' для PaymentRepository. Вложенные классы с @Component в конфигурационном классе регистрируются как member classes, в обход фильтров среза. То же ломает свой @ComponentScan на главном классе. Компоненты держат в отдельных файлах.

Контекст кешируется по конфигурации теста, и любое отличие создаёт новый

Подъём полного контекста с базой занимает секунды. Если делать его в каждом из двухсот классов, набор тестов будет идти минуты. Поэтому Spring TestContext хранит поднятые контексты в статическом кеше на время работы JVM. Ключ кеша — MergedContextConfiguration: классы конфигурации, @Import, профили, свойства, инициализаторы и customizers. @MockitoBean тоже часть ключа: набор подменённых бинов меняет контекст.

@SpringBootTest @Import(Containers.class) @Transactional class B_RepositoryWriteTest { … }
@SpringBootTest @Import(Containers.class)                class C_RepositoryReadTest { … }
@SpringBootTest @Import(Containers.class) @AutoConfigureMockMvc
class D_PaymentFlowTest { @MockitoBean BankClient bank; … } // Ещё и mock банка.

Счётчик contexts растёт в конструкторе репозитория, то есть на каждый полный контекст. B создал первый, C получил его из кеша за 6 мс, D создал второй. В статистике кеша три контекста: срез, полный и полный с mock-ом. Включить её можно через logging.level.org.springframework.test.context.cache=DEBUG.

Отсюда главный приём ускорения набора тестов: меньше уникальных конфигураций. Каждый класс со своим набором @MockitoBean, своим @TestPropertySource или профилем — новый контекст и новые секунды. Общие подмены выносят в базовый класс или общую тестовую конфигурацию, чтобы классы делили контекст. @DirtiesContext выбрасывает контекст из кеша; его ставят, только когда тест действительно портит состояние синглтонов.

Кеш держит до 32 контекстов (spring.test.context.cache.maxSize) и выбрасывает самые давно использованные. Каждый живой контекст держит свои пулы соединений, потоки и контейнеры. Большой набор с десятками уникальных конфигураций может исчерпать соединения базы или память ещё до того, как кеш начнёт вытеснять.

@Transactional в тесте откатывает изменения, но не всё, что сделал тест

B и C в выводе выше делят один контекст и одну базу. B сохранил платёж и внутри теста видит одну строку. C после него видит ноль: @Transactional на тестовом классе открывает транзакцию вокруг каждого метода и откатывает её в конце. Тесты не мешают друг другу без ручной очистки таблиц.

@SpringBootTest
@Import(Containers.class)
@Transactional // Тестовая транзакция откатывается после каждого метода.
class B_RepositoryWriteTest {
    @Test
    void savesPayment() {
        repository.save("acc-1", 500, "APPROVED");
        assertThat(repository.count()).isEqualTo(1); // Видно в той же транзакции.
    }
}

У отката есть цена: в тесте не происходит коммит. Ошибки, которые проявляются только при коммите, тест не увидит: отложенные ограничения базы, flush Hibernate, который случается перед коммитом, слушатели @TransactionalEventListener(AFTER_COMMIT). Чтобы закоммитить внутри теста, есть @Commit и TestTransaction.flagForCommit().

Откат действует только на транзакцию потока теста. D не помечен @Transactional, и строка осталась в базе: rows before=0, after=1. То же случится, если код под тестом работает в другом потоке (@Async), открывает REQUIRES_NEW или тест ходит в приложение по HTTP через webEnvironment = RANDOM_PORT: сервер обрабатывает запрос в своём потоке и коммитит. Такие тесты чистят данные сами — удалением, уникальными ключами на каждый тест или отдельной схемой.

Если интеграционный тест помечен @Transactional, после него база всегда чистая.

Откатывается только транзакция, открытая в потоке теста. HTTP-запрос к серверу на случайном порту, @Async и REQUIRES_NEW коммитят в своих транзакциях, и данные остаются для следующих тестов.

@MockitoBean заменяет бин в контексте, MockMvc вызывает контроллер без сервера

Mockito-аннотация @Mock создаёт mock в обычном юнит-тесте, контекст о нём не знает. @MockitoBean из Spring Framework 6.2 заменяет бин в контексте: все, кто внедряет BankClient, получают mock. После каждого теста mock сбрасывается. Прежняя @MockBean из Boot устарела в Boot 3.4 и удалена в Boot 4. Есть и @MockitoSpyBean — настоящий бин с возможностью переопределить отдельные методы.

@SpringBootTest
@AutoConfigureMockMvc
@Import(Containers.class)
class D_PaymentFlowTest {
    @Autowired MockMvcTester mvc;
    @MockitoBean BankClient bank; // Настоящий банк недоступен из теста.

    @Test
    void fullPathFromHttpToDatabase() {
        when(bank.charge(anyString(), anyLong())).thenReturn("APPROVED");
        var result = mvc.post().uri("/payments").contentType(MediaType.APPLICATION_JSON)
                .content("{\"account\":\"acc-2\",\"cents\":700}");
        assertThat(result).hasStatus(201); // Контроллер, сервис, транзакция и SQL настоящие.
    }
}

MockMvc прогоняет запрос через настоящий DispatcherServlet, фильтры, конвертеры и валидацию, но без сети и без Tomcat. Запрос выполняется в потоке теста. MockMvcTester из Framework 6.2 даёт тот же MockMvc с проверками в стиле AssertJ: hasStatus, bodyJson().extractingPath.

Когда нужен настоящий сервер — проверить Tomcat, фильтры сервлет-контейнера, таймауты — используют @SpringBootTest(webEnvironment = RANDOM_PORT) и HTTP-клиент. В Framework 7 для этого появился RestTestClient. Помни о предыдущем шаге: такой тест не откатывает данные.

Моки внешних систем удобны, но проверяют только твоё представление о них. Если банк меняет формат ответа, тест с mock-ом останется зелёным. Для HTTP-клиентов полезен @RestClientTest с MockRestServiceServer или WireMock — они проверяют реальный разбор ответа. Контракт с другими сервисами фиксируют контрактными тестами.

Testcontainers даёт настоящий PostgreSQL, а @ServiceConnection — настройки к нему

H2 в режиме совместимости похож на PostgreSQL, но не равен ему. Репозиторий демо пишет insert … returning id и создаёт таблицу с bigserial. Это синтаксис PostgreSQL. Тест на H2 либо упадёт, либо будет проверять другой SQL, чем работает в проде. Testcontainers запускает настоящую базу в Docker на время тестов.

// Один контейнер на контекст; @ServiceConnection сам задаёт spring.datasource.*.
@TestConfiguration(proxyBeanMethods = false)
class Containers {
    @Bean
    @ServiceConnection
    PostgreSQLContainer postgres() {
        return new PostgreSQLContainer("postgres:17-alpine");
    }
}

@ServiceConnection (с Boot 3.1) берёт адрес, порт, логин и пароль из запущенного контейнера и подставляет их в автоконфигурацию DataSource. Раньше это делали через @DynamicPropertySource вручную. Контейнер — бин контекста: он стартует вместе с контекстом и останавливается с ним. Поэтому кеш контекстов заодно кеширует и контейнер, а у каждого нового контекста свой контейнер, как у D в демо.

В Testcontainers 2 изменились имена: модуль называется testcontainers-postgresql вместо postgresql, а класс лежит в пакете org.testcontainers.postgresql и больше не параметризован типом. Примеры из интернета для версии 1.x придётся поправить.

Цена — Docker в CI и время старта контейнера. Его сокращают одним контейнером на весь набор: static-поле в базовом классе или общая конфигурация, которую импортируют все интеграционные тесты, чтобы контекст был один. Для локальной разработки есть повторное использование контейнеров между запусками и spring-boot-docker-compose.

  • @SpringBootTest поднимает весь контекст, срез вроде @WebMvcTest — только свой слой; остальное подменяют @MockitoBean.
  • Контексты кешируются по полной конфигурации теста; уникальные моки, свойства и профили множат контексты и время.
  • @Transactional откатывает только транзакцию потока теста: HTTP на RANDOM_PORT, @Async и REQUIRES_NEW коммитят.
  • @MockitoBean заменил удалённую в Boot 4 @MockBean; MockMvcTester проверяет MVC без сервера.
  • Testcontainers с @ServiceConnection даёт настоящую базу; контейнер живёт столько же, сколько контекст.

На собеседовании

Чем @SpringBootTest отличается от @WebMvcTest и когда что использовать?

@SpringBootTest поднимает весь контекст приложения: все бины, базу, клиентов. Он проверяет совместную работу слоёв, но медленный. @WebMvcTest — срез: только контроллеры и инфраструктура Spring MVC, без сервисов и базы, их подменяю через @MockitoBean. В демо срез поднял 112 бинов против 195 у полного контекста.

Срезом проверяю то, что делает фреймворк в своём слое: JSON, валидацию, коды ответов, обработку ошибок. Полный контекст с Testcontainers — для пути от HTTP до базы. Логику без Spring — обычными юнит-тестами.

  • Другие срезы: @DataJpaTest, @JdbcTest, @JsonTest, @RestClientTest; в Boot 4 они лежат в модулях своих технологий.
  • Вложенные @Component-классы в главном классе и свой @ComponentScan ломают фильтрацию срезов.
  • Срез с кучей @MockitoBean — сигнал, что контроллер делает слишком много.

Почему набор Spring-тестов медленный и как его ускорить?

Обычно из-за числа поднятых контекстов. Spring TestContext кеширует контекст по конфигурации теста, и классы с одинаковой конфигурацией используют один контекст. Но каждый уникальный набор @MockitoBean, свойств, профилей или @Import создаёт новый контекст, а @DirtiesContext выбрасывает его.

Я свожу тесты к нескольким общим конфигурациям: общий базовый класс с моками, один контейнер базы на набор, срезы вместо полного контекста там, где он не нужен. Статистику кеша видно в DEBUG-логе org.springframework.test.context.cache.

  • Кеш живёт в JVM; параллельные форки surefire поднимают контексты каждый у себя.
  • maxSize кеша по умолчанию 32; живые контексты держат пулы соединений и контейнеры.
  • @MockitoBean входит в ключ кеша, поэтому разный набор моков — разный контекст.

Что делает @Transactional в тесте и какие у него ловушки?

Открывает транзакцию вокруг каждого тестового метода и откатывает её в конце, так что тесты не оставляют данных. В демо один тест сохранил платёж, а следующий класс с тем же контекстом увидел пустую таблицу.

Ловушка — откатывается только транзакция потока теста. Запрос к серверу на RANDOM_PORT, @Async и REQUIRES_NEW коммитят свои транзакции, и данные остаются. И коммита в тесте нет, поэтому ошибки, которые проявляются при коммите, тест не видит.

  • Hibernate может не выполнить flush до отката; для проверки SQL вызывают flush явно.
  • AFTER_COMMIT-слушатели в тесте с откатом не срабатывают; для них нужен @Commit или тест без транзакции.
  • Тесты без транзакции чистят данные сами: уникальные ключи, удаление, отдельная схема.
Почему этот тест проходит один, но ломает соседние? 
@SpringBootTest(webEnvironment = WebEnvironment.RANDOM_PORT)
@Transactional
class PaymentApiTest {
    @Autowired RestTestClient client;

    @Test
    void createsPayment() {
        client.post().uri("/payments").body(new PaymentRequest("acc-1", 500))
              .exchange().expectStatus().isCreated();
    }
}

Запрос обрабатывает Tomcat в своём потоке и коммитит в своей транзакции. Тестовая транзакция в потоке теста пустая, её откат ничего не убирает. Платёж остаётся в базе, и тесты, которые считают строки, начинают зависеть от порядка запуска. Нужно чистить данные явно или проверять через MockMvc, где запрос идёт в потоке теста.

Чем @MockitoBean отличается от @Mock?

@Mock создаёт mock Mockito в обычном тесте, контекст Spring о нём не знает, и его передают в конструктор вручную. @MockitoBean заменяет бин в контексте Spring: все бины, которые внедряют этот тип, получат mock. Он сбрасывается после каждого теста.

@MockitoBean появился в Spring Framework 6.2 и заменил @MockBean из Boot, который устарел в 3.4 и удалён в Boot 4.

  • @MockitoSpyBean оборачивает настоящий бин и позволяет переопределить отдельные методы.
  • Набор подменённых бинов входит в ключ кеша контекстов.
  • Mock внешней системы проверяет твоё представление о ней; разбор настоящих ответов проверяют MockRestServiceServer или WireMock.
