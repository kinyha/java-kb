Spring Transactions

Платёж меняет несколько строк, а для клиента это одно действие. Spring открывает транзакцию перед вызовом сервиса и решает, сохранить ли изменения, когда вызов закончился. Сам метод выполняет обычный Java-код; границу вокруг него держит прокси. Чтобы объяснить неожиданный результат, проследи три вещи: через какой объект пришёл вызов, какую транзакцию получил метод и что увидел прокси на выходе.

Платёж должен сохранить все изменения вместе

У счёта было 100 учебных денежных единиц. Сервис списал 10 и записал платёж p-17, а затем проверка завершилась ошибкой. В auto-commit обе SQL-операции уже сохранены: клиент получил ошибку, но осталось 90. Не хватает общей границы, которая держит изменения до окончательного решения.

При commit транзакция сохраняет операции вместе, при rollback откатывает. Spring управляет механизмом JDBC или JPA и освобождает сервис от обвязки ресурсов. Границу ставь на целую операцию сервиса: «провести платёж», а не на каждый запрос репозитория.

Демо использует H2 и JdbcTransactionManager. Сервис, менеджер и JdbcTemplate — бины; менеджер и шаблон получают один DataSource. Полная обвязка — в TxDemo.java.

@Configuration(proxyBeanMethods = false)
@EnableTransactionManagement(proxyTargetClass = true)
class Config {
    @Bean
    PlatformTransactionManager transactionManager(DataSource dataSource) {
        return new JdbcTransactionManager(dataSource); // Управляет одним DataSource.
    }
    // JdbcTemplate и PaymentService тоже создаются как бины.
}

public class PaymentService {
    private final JdbcTemplate jdbc;

    void record() {
        jdbc.update("update account set balance = balance - 10 where id = 1");
        jdbc.update("insert into payment values ('p-17')");
    }

    @Transactional
    public void fail() {
        System.out.println("transaction active="
                + TransactionSynchronizationManager.isActualTransactionActive());
        record(); // Обе записи используют транзакционное подключение.
        throw new IllegalStateException("bank rejected"); // Ошибка выйдет к прокси.
    }
}

context.getBean(PaymentService.class).fail(); // Получили из Spring прокси сервиса.

./run.sh TxDemo proxy # Скрипт ловит ошибку снаружи и читает сохранённые строки.

exception=IllegalStateException
balance=100, payments=0, audit=0

Прокси откатил списание и запись до возврата вызывающему. Обработка ошибки в main уже не меняет исход. Все варианты запущены на JDK 21, Spring 7.0.9; зависимости управляются BOM Boot 4.1.1 в pom.xml.

Раз оба метода репозитория помечены @Transactional, платёж уже атомарен.

Без внешней транзакции каждый вызов может открыть и завершить свою. Списание сохранится раньше, чем начнётся запись платежа. Общая граница должна охватывать всю операцию, которая обязана завершиться целиком.

Прокси открывает транзакцию только на пути вызова через него

Перед сервисом стоит AOP-прокси с TransactionInterceptor. Он читает аннотацию, обращается к PlatformTransactionManager и вызывает настоящий объект. При нормальном возврате просит commit, при исключении выбирает действие по правилам отката. Ошибка возможна и во время commit.

Для новой транзакции менеджер JDBC выключает auto-commit и связывает подключение с потоком через TransactionSynchronizationManager. JdbcTemplate находит его через DataSourceUtils: разным репозиториям не нужно передавать Connection. При завершении этой транзакции менеджер убирает привязку, восстанавливает настройки и возвращает ресурс в пул.

Внешний метод без аннотации вызывает fail() на том же объекте. Прокси пропускает внешний вызов без транзакции. Дальше this.fail() идёт к реализации напрямую: перехватчик этого перехода не видит.

public void selfInvocation() {
    fail(); // То же, что this.fail(): вызов внутри настоящего объекта.
}

// fail() из прошлого шага по-прежнему содержит @Transactional и бросает ошибку.
context.getBean(PaymentService.class).selfInvocation();
./run.sh TxDemo self
transaction active=false
exception=IllegalStateException
balance=90, payments=1, audit=0

Исключение прежнее, но SQL сохранился через auto-commit. Если внешний метод транзакционный, внутренний код участвует в его транзакции; собственные REQUIRES_NEW и правила внутреннего метода всё равно не применятся.

Вынеси отдельную операцию в другой бин либо задай участок через TransactionTemplate. Сервис, созданный через new, и вызов из @PostConstruct тоже не получают обычную обработку готового прокси.

Под капотом: видимость метода и тип прокси

JDK-прокси перехватывает публичные методы интерфейса. Прокси класса создаёт подкласс, поэтому private/final методы и final класс не подходят. С Spring 6.0 protected и package-visible поддерживаются по умолчанию для прокси класса. Требование внешнего вызова сохраняется.

Режим по умолчанию — proxy. AspectJ внедряет обработку в байткод и способен перехватить внутренний вызов, но требует weaving. Отдельный сервис чаще делает границу понятнее.

Результат транзакции зависит от ошибки, которую увидела её граница

По умолчанию Spring откатывает при RuntimeException и Error, а checked exception приводит к commit. Это правило Spring. Если BankException extends Exception означает неуспешный платёж, укажи rollbackFor = BankException.class.

static class BankException extends Exception {}

@Transactional
public void checkedFailure() throws BankException {
    record();
    throw new BankException(); // Checked exception: правило по умолчанию выберет commit.
}

@Transactional(rollbackFor = BankException.class)
public void checkedRollback() throws BankException {
    record();
    throw new BankException(); // Теперь правило явно требует rollback.
}

@Transactional
public void swallowed() {
    record();
    try { throw new IllegalStateException("bank rejected"); }
    catch (IllegalStateException ignored) { /* До прокси ошибка не дошла. */ }
}

// Каждый вариант запускается в новой базе: исходный баланс снова 100.
service.checkedFailure(); // checked
service.checkedRollback(); // checked-rollback
service.swallowed(); // swallowed
./run.sh TxDemo checked
./run.sh TxDemo checked-rollback
./run.sh TxDemo swallowed
# checked
exception=BankException
balance=90, payments=1, audit=0
# checked-rollback

balance=100, payments=0, audit=0

balance=90, payments=1, audit=0

Заголовки # добавлены к реальному stdout. swallowed() вернулся нормально и сохранил изменения. Возврат false или FAILED также не требует rollback: решение надо выразить явно.

noRollbackFor разрешает commit для указанной ошибки. Более близкий тип исключения сильнее общего правила. Задавай классы: строковый rollbackForClassName совпадает по части имени и захватывает лишние типы. С Spring 6.2 можно выбрать общий @EnableTransactionManagement(rollbackOn = ALL_EXCEPTIONS); здесь оставлены стандартные правила.

Пойманная ошибка и rollback-only — разные ситуации

Внешний платёж и отдельный бин аудита с REQUIRED имеют две логические границы, но одну транзакцию базы. Ошибка дошла до внутреннего прокси — тот пометил общую транзакцию rollback-only. Внешний код может поймать исключение, но отметка остаётся.

// Steps — другой бин, вызов проходит через его собственный прокси.
@Transactional
public void requiredFailure() {
    jdbc.update("insert into audit values ('required')");
    throw new IllegalStateException("audit rejected");
}

// Метод PaymentService.
@Transactional
public void required() {
    record();
    try { steps.requiredFailure(); } // REQUIRED присоединяется к транзакции платежа.
    catch (IllegalStateException ignored) { /* В Java ошибка обработана. */ }
    // Метод вернётся нормально, но общую транзакцию уже нельзя сохранить.
}

service.required(); // Исключение появится при выходе через внешний прокси.
./run.sh TxDemo required
exception=UnexpectedRollbackException
balance=100, payments=0, audit=0

После SQL-ошибки база тоже может требовать откат: в PostgreSQL продолжить можно после rollback либо отката до savepoint. Catch сам по себе не чинит транзакцию. Частичный успех требует границы, которая соответствует допустимому бизнес-результату.

Propagation выбирает, делить ли с вызывающим одну транзакцию

Аудит «попытка отклонена» должен пережить откат платежа. Необязательное дополнение к платежу, напротив, можно убрать при сбое и продолжить основную операцию. Одинаковый try/catch в Java не выражает эту разницу.

REQUIRED использует текущую транзакцию либо открывает новую. REQUIRES_NEW приостанавливает внешнюю привязку и открывает независимую физическую транзакцию на другом подключении. Внешний ресурс остаётся занятым вместе со своими блокировками. После внутреннего commit менеджер восстанавливает внешнюю привязку.

NESTED в JDBC использует savepoint на том же подключении. Вложенная ошибка откатывает изменения после точки сохранения. Отдельного commit нет: последующий внешний rollback отменит и успешную вложенную операцию. Все три случая ниже вызывают отдельный бин Steps через его прокси.

// Методы отдельного бина Steps.
@Transactional(propagation = Propagation.REQUIRES_NEW)
public void independentAudit() {
    jdbc.update("insert into audit values ('new')"); // Отдельный commit на C2.
}
@Transactional(propagation = Propagation.NESTED)
public void nestedFailure() {
    jdbc.update("insert into audit values ('nested')");
    throw new IllegalStateException("audit rejected"); // Откат до savepoint.
}
@Transactional(propagation = Propagation.NESTED)
public void nestedSuccess() {
    jdbc.update("insert into audit values ('nested')"); // Пока только часть C1.
}

// Методы PaymentService.
@Transactional
public void requiresNew() {
    record();
    steps.independentAudit();
    throw new IllegalStateException("payment rejected"); // C2 уже сохранена.
}
@Transactional
public void nested() {
    record();
    try { steps.nestedFailure(); }
    catch (IllegalStateException ignored) { /* C1 остаётся пригодной к commit. */ }
}
@Transactional
public void nestedOuterFailure() {
    record();
    steps.nestedSuccess();
    throw new IllegalStateException("payment rejected"); // Отдельного commit аудита не было.
}

service.requiresNew(); // new
service.nested(); // nested
service.nestedOuterFailure(); // nested-outer

./run.sh TxDemo nested
./run.sh TxDemo nested-outer

Остальные значения задают требования к готовой транзакции на входе.

REQUIRES_NEWПриостановить и открыть новуюОткрыть
NESTEDSavepoint, если менеджер поддерживаетОткрыть, как REQUIRED
SUPPORTSПрисоединитьсяРаботать без физической транзакции

Если все потоки держат внешнее подключение и ждут второе для REQUIRES_NEW, пул исчерпан. Внутренний запрос также способен ждать строку, которую заблокировал его же внешний вызов. Сначала реши, нужен ли отдельный commit, затем считай запас пула и проверяй порядок доступа к данным.

Поддержка NESTED зависит от менеджера и драйвера. JDBC-откат до savepoint не возвращает Java-объекты persistence context в прежнее состояние. Поэтому этот пример нельзя автоматически перенести на JPA; изменения entity и flush разобраны в JPA Basics.

Настройки влияют на новую транзакцию и зависят от её менеджера

Атомарность объединяет commit, изоляция управляет видимостью конкурентных изменений. Два запроса прочитали баланс 100 и разрешили списать по 80. Каждый платёж может завершиться целиком, а правило «не уйти в минус» всё равно нарушится.

isolation = DEFAULT оставляет уровень подключения и СУБД. Это стандарт Spring, а не универсальный READ_COMMITTED. При присоединении через REQUIRED метод получает изоляцию и срок уже начатой транзакции. Посередине они не меняются.

УровеньЧто исключает модель SQLЧто ещё нужно учитывать

READ_COMMITTEDГрязное чтениеПовторный SELECT способен увидеть новое сохранённое значение

Для баланса часто яснее условный UPDATE ... WHERE balance >= amount с проверкой числа строк или блокировка счёта. Для entity полезен @Version. Подробности — в Locking & Caching, устройство MVCC — в темах базы.

readOnly передаёт намерение, а не универсальный запрет записи

readOnly по умолчанию равен false. JDBC-менеджер передаёт hint через Connection.setReadOnly(true). Менеджер JPA с Hibernate способен изменить flush и загрузку объектов, уменьшая dirty checking. Результат зависит от менеджера и драйвера.

@Transactional(readOnly = true)
public void readOnlyWrite() {
    System.out.println("readOnly flag="
            + TransactionSynchronizationManager.isCurrentTransactionReadOnly());
    record(); // H2 принимает запись: setReadOnly(true) не запрещает этот SQL.
}

service.readOnlyWrite();

readOnly flag=true
balance=90, payments=1, audit=0

Для строгого запрета нужны права базы либо её режим read-only transaction. JDBC-менеджер с setEnforceReadOnly(true) выполняет явный SET TRANSACTION READ ONLY на поддерживающей его СУБД. Это проверяют на целевом драйвере.

Внутренний readOnly = true не переделывает внешнюю read-write транзакцию. setValidateExistingTransaction(true) у менеджера помогает обнаружить несовместимую изоляцию и присоединение метода readOnly=false к готовой read-only транзакции. Это проверка настроек границы, а не анализ выполняемого SQL.

Срок транзакции не отменяет произвольный Java-код

timeout задаётся в секундах; по умолчанию используется срок менеджера. JDBC-менеджер применяет оставшийся срок к выражениям через JdbcTemplate и поддержку Spring. Произвольный HTTP-вызов или sleep() он не прерывает. Срок банка, ожидание пула и SQL настраиваются отдельно.

Внутренний метод поставит SERIALIZABLE, readOnly и timeout, даже когда REQUIRED получил готовую транзакцию.

Физическая транзакция уже начата. При обычном присоединении действуют её настройки; новая аннотация не создаёт второй BEGIN. Проверь внешнюю границу, а для отдельной транзакции осознанно выбери REQUIRES_NEW.

Граница базы не охватывает другой поток и удалённый банк

Императивная транзакция привязана к потоку. Новый поток, в том числе виртуальный, не наследует подключение внешней операции. Его вызов транзакционного прокси способен открыть собственную, отдельную транзакцию.

@Transactional
public void otherThread() throws Exception {
    System.out.println("caller transaction="
            + TransactionSynchronizationManager.isActualTransactionActive());
    var result = new CompletableFuture<Boolean>();
    Thread.ofVirtual().start(() -> result.complete(
            TransactionSynchronizationManager.isActualTransactionActive()));
    System.out.println("worker transaction=" + result.get(10, TimeUnit.SECONDS));
    // Передали результат вычисления. Ресурсы транзакции потоку не передавались.
}

service.otherThread();
./run.sh TxDemo thread
caller transaction=true
worker transaction=false
balance=100, payments=0, audit=0

Ошибка async-задачи после завершения сервиса не откатит его данные. Реактивная транзакция использует ReactiveTransactionManager и Reactor Context вместо этой модели ThreadLocal.

JDBC rollback не отменяет HTTP-списание в банке. Транзакция вокруг сети лишь дольше держит подключение и блокировки. Надёжный вариант — сохранить платёж и outbox вместе, затем вызвать банк отдельно с ключом идемпотентности. После таймаута выясняй результат по тому же ключу.

@TransactionalEventListener(phase = AFTER_COMMIT) задаёт порядок обработчика, но не сохраняет задание: процесс может упасть между commit и обработкой. Новая запись из такого обработчика требует новой транзакции. Для события, которое нельзя потерять, нужен outbox.

Небольшую границу можно задать прямо в коде

TransactionTemplate позволяет выделить короткий участок SQL отдельно от сетевой работы. Он использует тот же менеджер и propagation, но граница задана прямо в коде.

var template = new TransactionTemplate(transactionManager);
template.executeWithoutResult(status -> {
    jdbc.update("insert into payment values ('p-17')");
    status.setRollbackOnly(); // Бизнес решил отменить запись без исключения.
});
// Управление вернулось нормально. Запись не сохранена.
./run.sh TxDemo template
balance=100, payments=0, audit=0

Диагностику начинай с пути вызова и выбранного менеджера. DEBUG/TRACE для org.springframework.transaction и org.springframework.jdbc.datasource показывает открытие, присоединение и завершение. SQL-лог не доказывает commit: читай сохранённый результат после выхода из сервиса.

В проде сопоставляй длительность операции, занятость пула и ожидание блокировок. Ошибка связи при commit оставляет неопределённость результата: повтор должен быть безопасен по ключу платежа. Несколько локальных менеджеров не дают общей атомарности; для неё нужен XA/JTA либо протокол согласования бизнес-состояний.

  • Поставь границу вокруг целой операции сервиса. Отдельные транзакции репозиториев не склеивают платёж в одно действие.
  • В режиме proxy аннотация работает на внешнем вызове через прокси. Внутренний this-вызов получает лишь уже существующую транзакцию.
  • Прокси принимает решение по результату своего вызова. Checked exception, пойманная ошибка и rollback-only дают разные исходы.
  • REQUIRES_NEW фиксируется отдельно и занимает ещё одно подключение. NESTED использует savepoint и остаётся частью внешней транзакции.
  • Настройки присоединённого метода не переделывают начатую транзакцию. readOnly и timeout надо понимать через менеджер и целевую базу.
  • Локальный rollback не отменяет банк и фоновую задачу. Короткие транзакции, идемпотентность и outbox закрывают эти границы.

На собеседовании

Как работает @Transactional и почему self-invocation её ломает?

Вызов Spring-бина проходит через AOP-прокси. Перехватчик читает аннотацию, через менеджер открывает транзакцию или присоединяется к готовой, затем вызывает сервис. На выходе выбирает commit или rollback. Внутренний this-вызов идёт к настоящему объекту, поэтому новая аннотация не применяется. Я выношу отдельную операцию в другой бин либо использую TransactionTemplate.

  • JDK-прокси перехватывает публичные методы интерфейса. Прокси класса не перехватит private/final; protected и package-visible поддерживаются с Spring 6.0.
  • JdbcTemplate находит ресурс через DataSourceUtils. Прямой DataSource.getConnection() способен вернуть другое подключение.
  • Ошибка возможна во время commit после нормального возврата тела метода. Повтор ставлю снаружи всей границы.

Когда происходит rollback и откуда берётся UnexpectedRollbackException?

По умолчанию Spring откатывает при RuntimeException и Error; checked exception требует rollbackFor. Ошибка, пойманная внутри метода, до его прокси не дойдёт. Но отдельный внутренний бин с REQUIRED уже мог поставить rollback-only своим прокси. Тогда внешний catch не поможет: при попытке commit произойдёт откат и UnexpectedRollbackException. Вызывающий узнает, что операция не сохранилась.

  • С Spring 6.2 общий rollbackOn=ALL_EXCEPTIONS включает checked exceptions. Правила операции уточняют этот стандарт.
  • Более близкий тип исключения сильнее общего правила. Строковый шаблон способен захватить лишние имена.
  • После SQL-ошибки сама база может требовать rollback. Catch не заменяет откат до savepoint.

Чем REQUIRED, REQUIRES_NEW и NESTED отличаются на практике?

REQUIRED делит текущую транзакцию с вызывающим либо открывает новую. REQUIRES_NEW приостанавливает внешнюю и фиксируется независимо: аудит переживёт откат платежа. NESTED использует JDBC savepoint в той же физической транзакции. Вложенную ошибку можно убрать, а внешний платёж продолжить; внешний rollback всё равно отменит и успешную вложенную запись. Я выбираю по тому, какой частичный результат бизнес допускает сохранить.

  • REQUIRES_NEW требует запас пула. Внутренний запрос способен ждать блокировку своего внешнего вызова.
  • NESTED зависит от менеджера. JDBC savepoint не восстанавливает поля объектов persistence context JPA.
  • MANDATORY требует готовую транзакцию. NOT_SUPPORTED убирает её из текущего выполнения, но внешние ресурсы остаются заняты.
Аудит успешного платежа пишется через REQUIRES_NEW. Где ошибка?

Сначала уточню смысл аудита. Если он утверждает «платёж успешно проведён», отдельный ранний commit способен сохранить ложную запись перед откатом платежа. Такую запись сохраняю вместе с платежом или формирую из надёжного события после commit. REQUIRES_NEW уместен для факта попытки, который обязан пережить ошибку самой операции.

Что дают isolation, readOnly и timeout? Какие у них ограничения?

Isolation управляет видимостью конкурентных изменений; DEFAULT оставляет уровень базы. readOnly передаёт намерение менеджеру и драйверу, но не запрещает INSERT универсально. Timeout действует там, где менеджер применяет срок, например к JDBC-выражениям. Если REQUIRED получил готовую транзакцию, он получил её настройки. Внутренняя аннотация не повышает изоляцию посередине и не прерывает HTTP-вызов.

  • validateExistingTransaction выявляет несовместимую изоляцию и присоединение read-write метода к готовой read-only транзакции. Проверяется настройка метода, а не факт SQL-записи.
  • Ошибка сериализации требует повторить всю короткую транзакцию с новым чтением.
  • Финансовый инвариант часто яснее выражают условный UPDATE, уникальность и блокировка строки.

Можно ли транзакцией защитить вызов банка и работу в другом потоке?

Локальный rollback не отменяет HTTP-списание. Транзакция вокруг сети дольше держит подключение и блокировки, но не даёт общей атомарности. Я сохраняю платёж и outbox вместе, затем вызываю банк по ключу идемпотентности. Новый поток не наследует императивную транзакцию; его транзакционный вызов откроет отдельную границу. Ошибка после внешнего commit уже не откатит платёж.

  • AFTER_COMMIT задаёт порядок, но не долговечность задания. Окно падения закрывает outbox.
  • Ошибка связи при commit оставляет неизвестный результат. Уникальный ключ позволяет безопасно выяснить состояние.
  • Для атомарности нескольких ресурсов нужен XA/JTA либо согласование бизнес-состояний.
