Validation & Errors

Аннотации вроде @NotBlank сами ничего не проверяют: проверка происходит, когда кто-то вызывает валидатор. В контроллере это делает Spring MVC, пока собирает аргументы, и неверный запрос получает 400 ещё до вызова метода. На сервисе это делает прокси @Validated, и без своего обработчика клиент получит 500. Любое исключение DispatcherServlet отдаёт обработчикам по порядку: сначала @ExceptionHandler в самом контроллере, потом в @ControllerAdvice, выбирая ближайший тип исключения. Хороший API отвечает на все ошибки в одном формате — ProblemDetail из RFC 9457 — и не выдаёт клиенту внутренности.

Без проверки отрицательная сумма доходит до сервиса, а клиент не узнаёт, что исправить

На платёжный эндпоинт пришёл запрос с пустым счётом и суммой −500. В DTO поля размечены @NotBlank и @Positive, но метод контроллера принимает тело без @Valid. Запрос проходит, ответ 201, и сервис пытается списать отрицательную сумму. Аннотации на полях есть, а проверки нет.

Добавим @Valid, и запрос получит 400. Но в стандартном ответе Spring Boot нет ни слова о том, какое поле неверное: клиенту остаётся гадать. А если правило сработает глубже, в сервисе, клиент увидит 500, будто упал сервер, хотя виноват его запрос. У темы две половины: кто, где и когда проверяет данные, и как исключение превращается в понятный ответ. ValidationDemo.java, Spring Boot 4.1.1, Hibernate Validator 9.1.3, фрагмент:

record Recipient(@NotBlank String iban) {}

record PaymentRequest(@NotBlank String account, @Positive long amount,
                      @Valid Recipient recipient) {} // @Valid: проверять и вложенный объект

@PostMapping("/plain")
@ResponseStatus(HttpStatus.CREATED)
String plain(@RequestBody PaymentRequest request) {        // нет @Valid: никто не проверяет
    return "created " + request;
}

@PostMapping("/valid")
@ResponseStatus(HttpStatus.CREATED)

    return "created " + request;
}

Bean Validation описывает правила аннотациями, а проверяет их только вызов валидатора

Bean Validation — спецификация Jakarta: набор аннотаций-ограничений (@NotNull, @NotBlank, @Size, @Positive, @Email, @Pattern) и интерфейс Validator. Реализация — Hibernate Validator, его подключает spring-boot-starter-validation. Аннотации — только метаданные. Конструктор record создаёт объект с любыми значениями, и ошибка появится, только когда кто-то передаст объект валидатору.

Валидатор обходит поля, проверяет каждое ограничение и возвращает набор нарушений: путь к полю и сообщение. Во вложенный объект он заходит, только если поле помечено @Valid, — это называется каскадной проверкой. Для коллекций аннотацию ставят на тип элемента: List<@Valid Item>. Та же первая часть ValidationDemo, без Spring:

record ShallowRequest(@NotBlank String account, @Positive long amount,
                      Recipient recipient) {}        // без @Valid вложенный объект не проверяется

var shallow = new ShallowRequest(" ", -500, new Recipient(""));

        .sorted().forEach(System.out::println);
System.out.println("without @Valid on recipient:");
validator.validate(shallow).stream().map(v -> "  " + v.getPropertyPath() + ": " + v.getMessage())
        .sorted().forEach(System.out::println);

Без @Valid на поле recipient пустой IBAN прошёл незамеченным, хотя на самом Recipient стоит @NotBlank. Это частая дыра: DTO с вложенными объектами проверяется только на верхнем уровне. Сообщения переведены на язык локали, и в Spring MVC это локаль запроса: с заголовком Accept-Language: ru то же нарушение приходит как «не должно быть пустым» (проверено на Boot 4.1.1). Свои правила, например «валюта из справочника», оформляют аннотацией с @Constraint и классом ConstraintValidator.

@NotNull на поле не даст создать объект с null.

Аннотация ничего не запрещает: объект создаётся с любыми значениями. Проверку запускают Spring MVC для @Valid-аргументов, прокси @Validated-бина при вызове метода, Hibernate перед сохранением сущности или твой код через Validator.

В контроллере проверку запускает Spring MVC ещё до вызова метода

Помнишь резолверы аргументов из Spring MVC? Для @Valid @RequestBody резолвер сначала читает JSON через Jackson, потом передаёт объект валидатору. Есть нарушения — бросает MethodArgumentNotValidException со списком ошибок по полям, и метод контроллера не вызывается. Стандартный обработчик Spring превращает это исключение в 400.

С Spring 6.1 MVC проверяет и ограничения прямо на параметрах метода: @PathVariable @Positive long id работает без дополнительных аннотаций на классе. Ошибка здесь другого типа — HandlerMethodValidationException, тоже 400. И важная деталь: если в методе есть ограничения на параметрах, Spring проверяет весь метод целиком, и ошибки @Valid-тела приходят уже как HandlerMethodValidationException. Обработчик ошибок должен понимать оба типа. Продолжение ValidationDemo:

String find(@PathVariable("id") @Positive long id) {...}       // ограничение прямо на параметре

@PostMapping("/payments/{id}/refund")

@RestController
@Validated                                                     // старый способ до Spring 6.1

    @GetMapping("/legacy/payments/{id}")

Тот же @Positive на контроллере с @Validated дал 500. До Spring 6.1 так и писали: аннотация на классе включала AOP-прокси, а прокси бросает ConstraintViolationException, которую MVC не переводит в 400. Сейчас прокси срабатывает раньше встроенной проверки, поэтому при обновлении @Validated с классов контроллеров убирают.

Если ошибки нужно обработать прямо в методе, следующим параметром после @Valid-аргумента ставят BindingResult. Тогда исключения не будет, и метод сам решит, что ответить. Это нужно редко, обычно ошибки собирают в одном месте — в обработчике, о котором дальше.

@Validated на сервисе проверяет вызов через прокси и без обработчика даёт 500

Правила можно поставить и на параметры метода сервиса. Чтобы они проверялись, класс помечают @Validated. Boot регистрирует MethodValidationPostProcessor, и тот заменяет бин прокси-подклассом, который перед каждым вызовом проверяет аргументы, а после — возвращаемое значение. В демо это видно по имени класса бина:

@Validated                                           // Spring обернёт бин в прокси
static class PaymentService {
    long charge(@NotBlank String account, @Positive long amount) { return amount; }
}

@PostMapping("/service")
String viaService(@RequestBody PaymentRequest request) { // проверку делает прокси сервиса
    return "charged " + service.charge(request.account(), request.amount());
}

System.out.println("service bean class: " + spring.getBean(PaymentService.class).getClass().getSimpleName());
service bean class: ValidationDemo$PaymentService$$SpringCGLIB$$0
POST /service
  exception: ConstraintViolationException
  500 {"timestamp":"2026-10-01T22:19:18.177Z","status":500,"error":"Internal Server Error","path":"/service"}

Прокси бросил ConstraintViolationException, и Spring MVC не знает, что это ошибка клиента: получился 500. В логе приложения при этом строка charge.arg0: must not be blank, charge.arg1: must be greater than 0 — имена arg0 и arg1, потому что демо собрано без флага -parameters. Чтобы ответ был 400, исключение явно переводят в нужный статус в обработчике ошибок.

Раз проверка живёт в прокси, у неё ограничения прокси: вызов метода из того же класса через this её не проходит, а private и final методы не перехватываются (тема AOP & Proxies). Зато @Validated умеет группы: @Validated(OnCreate.class) проверит только правила из группы OnCreate. Стандартная @Valid групп не знает. Отсюда короткий ответ на частый вопрос: @Valid — аннотация Jakarta, она включает проверку аргумента и каскад во вложенные объекты; @Validated — аннотация Spring, она добавляет группы, а на классе включает проверку методов через прокси.

Где что проверять. Формат запроса — обязательные поля, диапазоны, длины — проверяет контроллер, ответ 400. Бизнес-правила вроде «на счёте хватает денег» — это не аннотации, а код сервиса со своим исключением: InsufficientFundsException и ответ 422 или 409. Ограничения в базе — последняя линия, они ловят то, что пропустили остальные, например гонку двух одинаковых платежей.

Ответ на исключение выбирают по ближайшему типу: сначала в контроллере, потом в @ControllerAdvice

Когда метод бросил исключение, DispatcherServlet отдаёт его цепочке HandlerExceptionResolver (шаг 6 темы Spring MVC). Первым идёт ExceptionHandlerExceptionResolver. Он ищет метод с @ExceptionHandler сначала в классе контроллера, где случилась ошибка, потом в бинах @ControllerAdvice по их порядку. Внутри класса выигрывает обработчик, чей тип ближе всего к исключению по иерархии. Пролистай, куда попадают разные исключения из демо:

Обрати внимание на /payments/report: текст исключения с адресом базы и именем пользователя попал только в лог, клиент получил «Internal error». /payments/archive бросил ResponseStatusException — исключение, которое несёт статус в себе. Это удобно для простых случаев без advice, как и @ResponseStatus на классе исключения, но так HTTP-статус попадает в слой, где его не должно быть: в сервисы и доменные исключения.

Advice видит только то, что прошло через DispatcherServlet в потоке запроса. Последняя строка вывода — исключение из фильтра: ответ в другом формате, и advice о нём не знает. Так же мимо проходят исключения в другом потоке: в @Async-методе или в CompletableFuture, который контроллер не вернул. А если ответ уже отправлен клиенту, обработчик не сможет поменять статус. Ошибки фильтров обрабатывают в самом фильтре или настраивают ответ /error Boot (ErrorAttributes, свой ErrorController).

ProblemDetail даёт всем ошибкам один формат, а catch-all обработчик легко его ломает

RFC 9457 описывает тело ошибки с типом application/problem+json и полями type, title, status, detail и instance. Можно добавлять свои поля, как paymentId или errors в демо. Поле type в выводе пропущено: по RFC это значит about:blank, то есть «смотри на статус». Клиент на любом языке разбирает ошибки одинаково, а не угадывает формат каждого эндпоинта. В Spring это класс ProblemDetail. Исключения Spring MVC и ResponseStatusException реализуют интерфейс ErrorResponse и уже содержат готовый ProblemDetail.

Включить формат можно двумя способами. spring.mvc.problemdetails.enabled=true регистрирует в Boot обработчик для исключений Spring MVC. Он выключен по умолчанию, и для ошибок валидации пишет только "detail":"Invalid request content." без списка полей. Второй способ — своё advice, наследующее ResponseEntityExceptionHandler, как в демо. Список полей добавляют, переопределив метод базы:

@Override // MethodArgumentNotValidException уже обработан в базе: дополняем, а не дублируем
protected ResponseEntity<Object> handleMethodArgumentNotValid(MethodArgumentNotValidException ex,
        HttpHeaders headers, HttpStatusCode status, WebRequest request) {
    var problem = ex.getBody(); // ProblemDetail, который Spring уже собрал
    problem.setProperty("errors", ex.getFieldErrors().stream()
            .map(e -> e.getField() + ": " + e.getDefaultMessage()).sorted().toList());
    return ResponseEntity.status(status).body(problem);
}

Именно переопределить. Если в наследнике ResponseEntityExceptionHandler объявить ещё и @ExceptionHandler(MethodArgumentNotValidException.class), приложение не стартует: «Ambiguous @ExceptionHandler method mapped for MethodArgumentNotValidException» — у базы уже есть обработчик этого типа. Проверено на Boot 4.1.1. Не забудь и HandlerMethodValidationException из шага 3: для неё в базе есть свой метод, handleHandlerMethodValidationException.

Неверное тело, архивный платёж и неподдерживаемый метод стали 500. ExceptionHandlerExceptionResolver стоит в цепочке первым, обработчик Exception подходит к любому исключению, и до стандартного обработчика Spring дело не доходит. Мониторинг теперь видит ошибки сервера там, где ошибся клиент, а клиент не может отличить свою ошибку от сбоя. Поэтому catch-all ставят только вместе с базой ResponseEntityExceptionHandler или проверяют внутри, не реализует ли исключение ErrorResponse.

Последнее — что писать в лог. Ошибки 4xx — забота клиента: уровень WARN или DEBUG, без стека, иначе один кривой клиент засыплет лог. 5xx — ERROR со стеком и идентификатором запроса. Тот же идентификатор отдают клиенту в ProblemDetail, чтобы по обращению в поддержку найти запись в логе.

  • Аннотации Bean Validation — метаданные; проверка происходит, только когда валидатор вызывает MVC (@Valid), прокси (@Validated) или твой код. Во вложенные объекты валидатор заходит только по @Valid.
  • MVC проверяет тело и параметры до вызова метода и отвечает 400; ошибки приходят как MethodArgumentNotValidException или HandlerMethodValidationException.
  • @Validated на сервисе работает через прокси и даёт ConstraintViolationException, то есть 500, пока её не переведёшь в 400. На контроллерах с Spring 6.1 его убирают.
  • Обработчик исключения ищется сначала в контроллере, потом в @ControllerAdvice, по ближайшему типу; исключения фильтров и других потоков advice не видит.
  • Один формат ошибок — ProblemDetail; catch-all на Exception без базы ResponseEntityExceptionHandler превращает 400 и 405 в 500.

На собеседовании

Как валидировать входящий запрос и чем @Valid отличается от @Validated?

Правила пишу аннотациями Bean Validation на полях DTO: @NotBlank, @Positive, @Size. Проверку включает @Valid на аргументе контроллера: Spring после чтения JSON отдаёт объект валидатору и при ошибках бросает MethodArgumentNotValidException, клиент получает 400, а метод не вызывается. Ограничения на @PathVariable и @RequestParam со Spring 6.1 проверяются сами.

@Valid — стандартная аннотация Jakarta: включает проверку и каскад во вложенные объекты. @Validated — аннотация Spring: умеет группы правил, а на классе включает проверку параметров методов через прокси — так валидируют вызовы сервисов.

  • Если у метода есть ограничения на параметрах, ошибки тела приходят как HandlerMethodValidationException, а не MethodArgumentNotValidException; обработчик должен понимать оба типа.
  • Прокси @Validated бросает ConstraintViolationException, которая без своего обработчика даёт 500. Вызов через this проверку обходит.
  • @Validated на классе контроллера — наследие до 6.1: прокси срабатывает раньше встроенной проверки и превращает 400 в 500.
На поле recipient нет @Valid, а внутри Recipient стоит @NotBlank на iban. Пройдёт ли запрос с пустым iban?

Пройдёт. Валидатор заходит во вложенный объект, только если поле помечено @Valid. Ограничения самого Recipient останутся непроверенными, ответ будет 2xx. Для списков аннотацию ставят на тип элемента: List<@Valid Item>.

Как в Spring обрабатывать исключения контроллеров?

Пишу методы с @ExceptionHandler в классе с @RestControllerAdvice: метод получает исключение и возвращает ответ, обычно ProblemDetail или ResponseEntity. Spring выбирает обработчик с ближайшим типом исключения, поэтому одним методом на базовое PaymentException закрываю семейство бизнес-ошибок, а для частных случаев пишу отдельные.

Обработчик в самом контроллере проверяется раньше advice. Для простых случаев есть ResponseStatusException и @ResponseStatus на классе исключения, но тогда HTTP-статус живёт в доменном коде.

  • Под капотом это первый HandlerExceptionResolver в цепочке DispatcherServlet; за ним идут ResponseStatusExceptionResolver и DefaultHandlerExceptionResolver.
  • Advice наследую от ResponseEntityExceptionHandler, иначе catch-all на Exception перехватит 400, 405 и 415 и превратит их в 500.
  • Advice не видит исключения фильтров, других потоков и ошибки после отправки ответа.
Что сломает такой advice? 
@RestControllerAdvice
class ApiErrors {
    @ExceptionHandler(Exception.class)
    ProblemDetail any(Exception ex) {
        return ProblemDetail.forStatusAndDetail(HttpStatus.INTERNAL_SERVER_ERROR, ex.getMessage());
    }
}

Две вещи. Обработчик ловит и стандартные исключения Spring MVC: неверное тело, неподдерживаемый метод, неверный Content-Type, ResponseStatusException — все станут 500. И в detail уходит ex.getMessage(), а там бывают адреса баз, SQL и имена пользователей. Исправление: наследовать ResponseEntityExceptionHandler, клиенту отдавать общий текст и id запроса, подробности писать в лог.

В каком формате отдавать ошибки клиенту?

В формате RFC 9457, Problem Details: тип application/problem+json, поля title, status, detail, instance и type, плюс свои поля, например список ошибок валидации по полям. В Spring это класс ProblemDetail, и исключения Spring MVC уже умеют его отдавать.

Главное — один формат для всех ошибок сервиса, чтобы клиент разбирал их одним кодом. В 5xx не отдаю детали исключения, только общий текст и идентификатор запроса.

  • spring.mvc.problemdetails.enabled выключен по умолчанию, а для ошибок валидации пишет только «Invalid request content.» — список полей добавляю в своём наследнике ResponseEntityExceptionHandler.
  • Ответ /error Boot не в формате ProblemDetail; туда попадают исключения фильтров, и формат приходится выравнивать отдельно.
  • 4xx логирую без стека и на уровне WARN или DEBUG, 5xx — ERROR со стеком и id запроса.

Почему @ControllerAdvice не поймал исключение?

Advice работает внутри DispatcherServlet, в потоке запроса. Исключение из фильтра, например из Spring Security или своего фильтра tenant, до него не доходит: Tomcat отправит запрос на /error. Исключение в @Async-методе или в отдельном CompletableFuture случается в другом потоке и тоже мимо.

Ещё бывает, что исключение перехватили раньше: обработчиком в самом контроллере или другим advice с большим приоритетом по @Order.

  • Advice можно ограничить пакетами, типами контроллеров или аннотацией (basePackages, assignableTypes, annotations), и контроллер может просто не входить в его область.
  • Если ответ уже отправлен клиенту, обработчик не поменяет ни статус, ни заголовки: они ушли с первым сброшенным буфером.
  • Если сам @ExceptionHandler бросил исключение, Spring пишет в лог «Failure in @ExceptionHandler» и продолжает с исходным исключением, как будто обработчика не было.
