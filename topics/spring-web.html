Spring MVC

Tomcat отдаёт каждый запрос одному сервлету — DispatcherServlet. Сам он запрос не обрабатывает, а по очереди спрашивает помощников. Таблица маршрутов выбирает метод контроллера, резолверы собирают его аргументы из пути, параметров и тела, конвертер превращает результат в JSON. Если какой-то этап не справился, он бросает исключение, и по статусу видно, где сломалось: 404 — не нашёлся путь, 405 — метод, 415 — формат тела, 406 — формат ответа, 400 — аргумент. Аннотации на контроллере — описание, которое эти помощники читают при старте и на каждом запросе.

Контроллер — это описание, а запрос обрабатывает DispatcherServlet

Вот контроллер платёжного сервиса из демо этой темы. В нём нет ни слова об HTTP: не видно, где разбирается путь, где читается JSON и откуда берётся статус 201.

@RestController
@RequestMapping("/payments")

    @PostMapping
    @ResponseStatus(HttpStatus.CREATED)

        return new Payment(42, request.account(), request.amount(), "NEW");
    }

    @GetMapping
    List<Payment> list(@RequestParam("limit") int limit) { ... }
}

На голом Servlet API из прошлой темы всё это пришлось бы писать руками в doPost и doGet: сверить путь и метод, проверить Content-Type, прочитать тело через Jackson, перевести строку "300" в число, поставить статус, записать JSON, а каждое исключение превратить в код ответа. Spring MVC делает эту работу один раз для всех контроллеров. Аннотации говорят, какие запросы метод принимает, откуда брать аргументы и как вернуть результат, а выполняют это конкретные классы:

Всех их вызывает DispatcherServlet — обычный сервлет. Spring Boot регистрирует его в Tomcat на путь /, и все запросы приложения попадают к нему. Как и любой сервлет, по умолчанию он инициализируется на первом запросе: до этого внутри нет ни таблицы маршрутов, ни конвертеров. Это видно в демо на Boot в следующем шаге.

DispatcherServlet ничего не знает о контроллерах: он опрашивает списки стратегий

В коде DispatcherServlet нет ни слова про @RequestMapping или JSON. При инициализации он находит в Spring-контексте бины нескольких типов и на каждый запрос опрашивает их по порядку. HandlerMapping отвечает, кто обработает запрос. HandlerAdapter знает, как этого обработчика вызвать. HandlerExceptionResolver превращает исключение в ответ. Ещё есть ViewResolver для HTML-страниц, в REST-сервисе он почти не участвует.

Чтобы увидеть это без магии Boot, демо поднимает Spring MVC руками на Tomcat из прошлой темы и печатает, что нашёл DispatcherServlet. MvcTraceDemo.java, Java 21, Spring 7.0.9, Tomcat 11.0.26, фрагмент:

Зачем адаптер, если можно просто вызвать метод? Обработчик бывает разным: метод с @RequestMapping, функция из RouterFunction, объект HttpRequestHandler, старый интерфейс Controller. DispatcherServlet не разбирается в их сигнатурах, он ищет адаптер, который умеет вызвать такой объект. Поэтому новый способ писать обработчики Spring добавляет новой парой «маппинг + адаптер», не меняя DispatcherServlet: так появились функциональные эндпоинты, и их RouterFunctionMapping стоит в списке первым.

В приложение на Spring Boot для MVC нужно добавить @EnableWebMvc.

Аннотация регистрирует WebMvcConfigurationSupport, а автоконфигурация MVC в Boot срабатывает, только когда такого бина нет. Поставишь @EnableWebMvc — потеряешь настройки Boot: статические файлы, конвертеры с Jackson из spring.jackson.*, форматы spring.mvc.*. Настраивают MVC в Boot бином, реализующим WebMvcConfigurer.

Таблица маршрутов строится при старте, а запрос выбирает самый точный вариант

RequestMappingHandlerMapping при старте контекста проходит по бинам с @Controller и превращает аннотации каждого метода в запись таблицы: шаблон пути, HTTP-метод, условия на параметры и заголовки, какой формат тела метод принимает (consumes) и какой отдаёт (produces). Таблица из MvcTraceDemo:

mapping.getHandlerMethods().entrySet().stream()

Таблица готова до первого запроса, поэтому ошибка в ней ломает старт, а не запрос: два метода с одинаковыми путём и HTTP-методом дают «Ambiguous mapping» при запуске приложения. На запросе маппинг берёт записи, чей шаблон подходит под путь, отсеивает те, что не прошли остальные условия, и из оставшихся выбирает самую точную. Если не осталось ни одной, ответ зависит от того, на каком условии отсеялись кандидаты.

Читай статус как адрес поломки. 405 — путь верный, а HTTP-метод нет, и заголовок Allow подсказывает допустимые. 415 — сервер не понимает формат тела: проверь Content-Type у клиента. 406 — сервер не умеет ответить в формате из Accept. 400 — запрос дошёл до метода, но аргумент не собрался: строка не стала числом или JSON не разобрался.

Две ловушки при переходе со старых версий. С Spring 6 путь с завершающим слешем /payments/42/ больше не совпадает с /payments/{id}, и клиенты, которые его добавляли, получают 404. А 404 в Boot выглядит иначе, чем в демо: запрос без контроллера подхватывает обработчик статических файлов на /**, и исключение называется NoResourceFoundException. Строки из MvcBootDemo:

Сокращённый метод, обработка multipart и асинхронности убрана. Видно, что исключение из любого этапа попадает в одно место — processDispatchResult.

mappedHandler = getHandler(processedRequest);           // HandlerMapping по порядку
if (mappedHandler == null) {
    noHandlerFound(processedRequest, response);           // 404
    return;
}
if (!mappedHandler.applyPreHandle(processedRequest, response)) {
    return;                                               // интерцептор вернул false
}
HandlerAdapter ha = getHandlerAdapter(mappedHandler.getHandler());
mv = ha.handle(processedRequest, response, mappedHandler.getHandler()); // аргументы, вызов, запись тела
mappedHandler.applyPostHandle(processedRequest, response, mv);
// исключение из любой строки выше ловится и передаётся сюда:
processDispatchResult(processedRequest, response, mappedHandler, mv, dispatchException);
// внутри: HandlerExceptionResolver по порядку, затем afterCompletion

Аргументы собирают резолверы: аннотация говорит, откуда взять значение

Перед вызовом метода RequestMappingHandlerAdapter проходит по его параметрам и для каждого ищет HandlerMethodArgumentResolver, который умеет его заполнить. @PathVariable берёт кусок пути, @RequestParam — параметр запроса, @RequestHeader — заголовок, @RequestBody — тело через конвертер. Есть резолверы, которые узнают параметр по типу: HttpServletRequest, Principal, Locale.

Из пути, параметров и заголовков приходят строки. Резолвер переводит их в тип параметра через ConversionService: "42" становится long. Если не получилось, будет MethodArgumentTypeMismatchException и 400, как у /payments/abc. Тело читает конвертер, которого выбирают по Content-Type: для application/json это Jackson. Обрезанный JSON дал HttpMessageNotReadableException и тоже 400.

Параметр без аннотации Spring не отвергает, а угадывает. Простой тип — строку, число, дату — он считает @RequestParam и не требует его в запросе. Остальное — @ModelAttribute: объект собирается из параметров запроса по именам полей. Отсюда тихая ошибка: забыл @RequestBody, и JSON в теле никто не читает. Ещё одна ловушка — имя параметра. @PathVariable long id без имени в скобках работает, только если компилятор сохранил имена параметров в байткоде флагом -parameters: с Spring 6.1 их больше не достают из отладочной информации. Проблема всплывает в модулях со своей сборкой и после копирования кода между проектами, поэтому в общих библиотеках имена пишут явно.

Если в JSON нет поля, Spring вернёт 400.

Зависит от типа поля. String или Long молча станут null, а лишние поля Jackson просто пропустит. Отсутствующее поле примитивного типа в Boot 4 даёт 400: Jackson 3 по умолчанию не кладёт null в long (FAIL_ON_NULL_FOR_PRIMITIVES), а Jackson 2 в Boot 3 молча ставил 0. Проверено на Boot 4.1.1 и отдельно на Jackson 2.21. Обязательность описывают явно: @Valid и @NotNull (тема Validation & Errors).

Ответ пишет конвертер, выбранный по Accept и типу результата

@RestController — это @Controller плюс @ResponseBody на каждом методе. С ним значение, которое вернул метод, становится телом ответа. Его обрабатывает RequestResponseBodyMethodProcessor. Он берёт типы из заголовка Accept, оставляет те, что метод разрешил в produces и что умеет записать хотя бы один конвертер для этого класса, выбирает самый конкретный и отдаёт значение конвертеру. Если ничего не осталось — 406, как у запроса с Accept: application/xml: XML-конвертера в демо нет.

Конвертеры опрашиваются по порядку, и StringHttpMessageConverter стоит раньше Jackson. Поэтому String из REST-метода уходит как есть. Продолжение MvcArgumentsDemo:

@RestController
static class PaymentController {
    @GetMapping(value = "/status", produces = "application/json")
    String status() { return "ok"; }  // StringHttpMessageConverter пишет строку как есть, без кавычек JSON
}

@Controller
static class PageController {
    @GetMapping("/page")
    String page() { return "ok"; }    // без @ResponseBody строка — имя представления (view)
}
GET /status -> 200
  body: ok  (application/json)
GET /page -> 404
  NoHandlerFoundException: No endpoint GET /ok.

В первом случае заголовок обещает JSON, а в теле ok без кавычек — клиент на Jackson упадёт при разборе. Нужна JSON-строка — верни объект или Map. Во втором случае @Controller без @ResponseBody воспринял "ok" как имя страницы. Spring нашёл стандартный InternalResourceViewResolver, сделал внутренний forward на /ok и не нашёл там обработчика. Так выглядит частая ошибка: REST-контроллер пометили @Controller.

Кодировка тоже зависит от конвертера. В чистом Spring MVC StringHttpMessageConverter пишет в ISO-8859-1 — это видно по Content-Type в выводе выше, и кириллица превратится в знаки вопроса. Boot настраивает UTF-8 (spring.http.converters.string-encoding-charset). Тот же String в MvcBootDemo:

GET /payments/1
  200 application/json Платёж 1

Кириллица на месте, но тело опять не JSON: Boot исправляет кодировку, а не формат. Для статуса и заголовков, вычисленных в коде, метод возвращает ResponseEntity. @ResponseStatus на методе подходит, когда статус фиксирован, как 201 у create.

JSON в Spring 7 и Boot 4 пишет Jackson 3. Его классы переехали в пакет tools.jackson, конвертер называется JacksonJsonHttpMessageConverter, а старый MappingJackson2HttpMessageConverter для Jackson 2 помечен на удаление. Аннотации остались прежними: @JsonProperty и другие лежат в com.fasterxml.jackson.annotation, в демо для этого подключается jackson-annotations 2.21.

Если метод бросил исключение, DispatcherServlet по порядку спрашивает HandlerExceptionResolver. Первым идёт поиск @ExceptionHandler в контроллере и в @ControllerAdvice. Потом @ResponseStatus на классе исключения. Последний переводит стандартные исключения Spring в 4xx — им выданы все коды из шага 3. Если не справился никто, исключение уходит в Tomcat, и в Boot ответ собирает /error. Как сделать единый формат ошибок — в теме Validation & Errors.

Spring MVC держит поток до конца ответа, и это его главная граница

Всё описанное выше выполняется в одном потоке Tomcat. Пока метод ждёт базу или внешний API, поток занят (тема Servlet & Tomcat). Отпустить его можно асинхронным результатом: если метод возвращает CompletableFuture, DeferredResult или Callable, DispatcherServlet запускает асинхронную обработку сервлета и возвращает поток в пул. Когда результат готов, запрос второй раз проходит через DispatcherServlet и только тогда пишет ответ. Интерцептор получает в этот момент afterConcurrentHandlingStarted вместо postHandle. Это нужно для долгого ожидания — long polling, SSE через SseEmitter, — а не для ускорения обычного запроса.

Функциональные эндпоинты (RouterFunction) описывают маршруты кодом, а не аннотациями. Это не отдельный фреймворк: тот же DispatcherServlet, свои маппинг и адаптер. Их удобно собирать программно и тестировать без рефлексии, но команда должна договориться об одном стиле.

В Spring 7 появилось версионирование API. У @GetMapping есть атрибут version: один путь может вести в разные методы для версий 1 и 2, а откуда брать версию, задаёт настройка — заголовок, параметр запроса или сегмент пути, в Boot это spring.mvc.apiversion.use.*. Проверено на Boot 4.1.1 с spring.mvc.apiversion.use.header=API-Version: заголовок 1 и 2 вызвал разные методы, неизвестная версия 3 получила 400.

MVC плохо подходит там, где соединений тысячи, живут они долго, а работы по каждому мало: стриминг, тысячи подписчиков SSE, прокси-шлюз. Там нужен WebFlux с неблокирующим стеком (тема WebFlux). Если код блокирующий, а проблема только в числе ожидающих потоков, сначала попробуй виртуальные потоки: модель MVC и код контроллеров не меняются.

  • DispatcherServlet — обычный сервлет, который опрашивает списки стратегий: маппинг находит обработчик, адаптер вызывает, резолверы исключений превращают ошибки в ответы.
  • Таблица маршрутов строится при старте; на запросе побеждает самый точный вариант, а статус ошибки показывает первый не пройденный этап: 404, 405, 415, 406, 400.
  • Аргументы собирают резолверы по аннотациям; без аннотации Spring угадывает, и забытый @RequestBody даёт null-поля без ошибки.
  • Тело читает и пишет HttpMessageConverter, выбранный по Content-Type, Accept и типу; String обгоняет Jackson и уходит как есть.
  • postHandle вызывается после записи JSON — менять ответ нужно раньше, в ResponseBodyAdvice или ResponseEntity.

На собеседовании

Что происходит с запросом в Spring MVC от Tomcat до контроллера?

Tomcat передаёт запрос по цепочке фильтров в DispatcherServlet — единственный сервлет приложения. Тот спрашивает HandlerMapping, кто обработает запрос. RequestMappingHandlerMapping находит метод контроллера по таблице, которую построил при старте из аннотаций. Дальше интерцепторы, затем HandlerAdapter собирает аргументы через резолверы и конвертеры, вызывает метод, а результат через конвертер пишет в ответ.

Если на каком-то этапе бросилось исключение, его разбирают HandlerExceptionResolver: @ExceptionHandler, @ResponseStatus, стандартные коды. Поэтому по статусу видно, где запрос сломался: 404 — путь, 405 — метод, 415 и 406 — форматы, 400 — аргументы.

  • Адаптеры нужны, потому что обработчики бывают разными: HandlerMethod, RouterFunction, HttpRequestHandler. DispatcherServlet не знает их сигнатур.
  • В Boot DispatcherServlet инициализируется на первом запросе; spring.mvc.servlet.load-on-startup переносит это на старт.
  • @EnableWebMvc в Boot отключает автоконфигурацию MVC; настраивать нужно через WebMvcConfigurer.
Клиент шлёт DELETE /payments/42 с битым JSON, а такого метода нет. Какой будет статус?

405. Таблица маршрутов отсеивает кандидатов по пути и HTTP-методу до того, как кто-то читает тело. Путь /payments/{id} нашёлся, метода DELETE у него нет, и HttpRequestMethodNotSupportedException случается раньше, чем дело доходит до JSON. В ответе будет заголовок Allow с допустимыми методами.

Чем @Controller отличается от @RestController?

@RestController — это @Controller и @ResponseBody на всех методах. В нём то, что вернул метод, становится телом ответа: объект превращается в JSON конвертером, строка уходит как есть.

В обычном @Controller без @ResponseBody возвращённая строка — имя представления, страницы для шаблонизатора. Если REST-метод по ошибке оказался в @Controller, Spring попробует отрисовать view и вернёт 404 или ошибку шаблона вместо JSON.

  • String из REST-метода пишет StringHttpMessageConverter, он стоит раньше Jackson. С produces=application/json клиент получит ok без кавычек — невалидный JSON.
  • Для вычисляемого статуса и заголовков возвращают ResponseEntity; @ResponseStatus — для фиксированного.

Чем фильтр отличается от HandlerInterceptor?

Фильтр — часть Servlet API, он стоит в цепочке Tomcat до DispatcherServlet и видит все запросы, включая статику и отказы Spring Security. Интерцептор — часть Spring MVC: его вызывает DispatcherServlet после выбора обработчика, поэтому он знает метод контроллера и его аннотации.

Фильтр беру для того, что не зависит от контроллера: логирование, MDC, CORS, безопасность. Интерцептор — когда решение зависит от метода: проверка по аннотации, метрики по обработчику.

  • postHandle вызывается после того, как @ResponseBody записал тело. Большой ответ уже ушёл клиенту, и даже заголовки не поменять. Менять JSON-ответ надо в ResponseBodyAdvice.
  • afterCompletion получает исключение, только если его не обработал ни один HandlerExceptionResolver.
  • Для асинхронного результата вместо postHandle вызывается afterConcurrentHandlingStarted, а остальное — при повторном проходе запроса.

Чем отличаются @PathVariable, @RequestParam и @RequestBody?

@PathVariable берёт часть пути по шаблону, например id из /payments/{id}. @RequestParam — параметр запроса после знака вопроса или поле формы. @RequestBody — всё тело запроса, которое конвертер, выбранный по Content-Type, превращает в объект; для JSON это Jackson.

Первые два приходят строками и переводятся в нужный тип; не получилось — 400. Тело с неверным Content-Type даёт 415, а непарсящийся JSON — 400.

  • Без аннотации простой тип считается необязательным @RequestParam, а объект — @ModelAttribute из параметров. Забытый @RequestBody даёт объект с null-полями и ответ 200.
  • Имена без явного указания берутся из байткода только с флагом компилятора -parameters; в Boot его включает сборка, в других модулях — 500 с подсказкой.
Клиент шлёт JSON, а в сервис приходят пустые поля, и ошибок нет. Где искать? 
@PostMapping("/payments")
Payment create(PaymentRequest request) {
    return service.create(request.account(), request.amount());
}

У параметра нет @RequestBody. Spring считает его @ModelAttribute и ищет account и amount в параметрах запроса, а тело никто не читает. Поля остаются null, ответ 200. Нужна аннотация @RequestBody, а обязательные поля стоит проверять через @Valid.

Как Spring превращает JSON в объект и обратно?

Через HttpMessageConverter. Для @RequestBody Spring смотрит Content-Type запроса и ищет конвертер, который умеет читать такой тип в класс параметра, — для JSON это Jackson. Для ответа берёт типы из Accept, пересекает с тем, что умеют конвертеры и что разрешено в produces, и пишет значение выбранным конвертером.

Если подходящего конвертера для чтения нет — 415, для ответа — 406. В Spring Boot конвертеры настроены автоконфигурацией, и Jackson берёт настройки из spring.jackson.*.

  • Порядок конвертеров важен: StringHttpMessageConverter стоит раньше Jackson, поэтому String уходит как есть.
  • Spring 7 и Boot 4 работают на Jackson 3: пакет tools.jackson, конвертер JacksonJsonHttpMessageConverter; MappingJackson2HttpMessageConverter помечен на удаление. Аннотации остались в com.fasterxml.jackson.annotation.
  • Переезд с Boot 3 на Boot 4 меняет поведение: отсутствующее поле примитивного типа Jackson 2 заполнял нулём, а Jackson 3 отвечает ошибкой, и клиент получает 400.
  • В чистом Spring MVC StringHttpMessageConverter пишет в ISO-8859-1; Boot ставит UTF-8.
