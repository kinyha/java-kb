SQL: Joins

JOIN строит строки из подходящих пар. У платежа две заявки на возврат — в результате появятся две строки с тем же платежом. Чтобы отчёт был правильным, сначала реши, что обозначает одна его строка: платёж, заявка или их пара. Затем выбери, нужны ли сами совпадения, сохранение строк без совпадений или только проверка существования.

После соединения сумма платежей выросла без новых платежей

В отчёте нужно показать платежи вместе с заявками на возврат. Платежей четыре, их суммы 100, 100, 300 и 400 копеек. У первого платежа две заявки, у третьего одна. Ещё одна заявка пришла от провайдера без сопоставленного платежа: её payment_id пока NULL.

Эти данные используются во всём уроке. settled означает проведённый возврат, pending — ожидающий. refunds.id всегда заполнен, а payment_id допускает NULL; это различие пригодится при поиске отсутствующих совпадений.

CREATE TABLE payments (
    id integer PRIMARY KEY,
    customer_id integer,
    amount integer NOT NULL CHECK (amount > 0)
);
CREATE TABLE refunds (
    id integer PRIMARY KEY,
    payment_id integer REFERENCES payments(id), -- NULL: ещё не сопоставлена с платежом.
    amount integer NOT NULL CHECK (amount > 0),
    state text NOT NULL CHECK (state IN ('settled', 'pending'))
);
INSERT INTO payments VALUES (1, 10, 100), (2, 10, 100), (3, 20, 300), (4, NULL, 400);
INSERT INTO refunds VALUES (101, 1, 20, 'settled'), (102, 1, 10, 'pending'),
                           (103, 3, 50, 'pending'), (104, NULL, 7, 'settled');

Запрос ниже суммирует p.amount после LEFT JOIN. Кажется, что сохранение всех платежей должно сохранить и общую сумму. Но сохранение строки не означает, что она встретится ровно один раз.

SELECT count(*) AS result_rows, sum(p.amount) AS wrong_total,
       sum(DISTINCT p.amount) AS distinct_total -- Две законные сотни тоже сольются.
FROM payments p
LEFT JOIN refunds r ON r.payment_id = p.id;
SELECT sum(amount) AS actual_total FROM payments; -- Сумма до размножения строк.
 result_rows | wrong_total | distinct_total
-------------+-------------+----------------
           5 |        1000 |            800
(1 row)

 actual_total
--------------
          900
(1 row)

Первый платёж вошёл дважды, поэтому сумма стала 1000 вместо 900. SUM(DISTINCT p.amount) убрал повтор значения 100, но вместе с ним исчез вклад второго законного платежа: получилось 800. Отчёт потерял исходную единицу строки — один платёж — ещё до агрегирования.

INNER выбирает пары, CROSS оставляет все пары

Мысленно поставь каждую левую строку рядом с каждой правой. Четыре платежа и четыре заявки дают 16 возможных пар — результат CROSS JOIN. У INNER JOIN остаются только пары, для которых ON дал TRUE. Предикат может быть равенством, диапазоном или сочетанием условий.

У платежа 1 ключ совпал с заявками 101 и 102: обе пары остаются. У платежей 2 и 4 совпадений нет: они исчезают. Для заявки 104 условие p.id = r.payment_id даёт UNKNOWN: её ключ отсутствует, поэтому подходящей пары нет. FALSE и UNKNOWN одинаково не проходят ON, хотя означают разные вещи.

SELECT p.id AS payment, p.amount, r.id AS refund
FROM payments p
INNER JOIN refunds r ON r.payment_id = p.id -- По одной строке на каждую подходящую пару.
ORDER BY p.id, r.id;
SELECT count(*) AS cross_rows
FROM payments p CROSS JOIN refunds r; -- 4 × 4, условия связи нет.
 payment | amount | refund
---------+--------+--------
       1 |    100 |    101
       1 |    100 |    102
       3 |    300 |    103
(3 rows)

 cross_rows
------------
         16
(1 row)

Это модель результата, а не требование физически перебрать 16 пар. PostgreSQL выбирает алгоритм соединения отдельно; hash join, merge join и nested loop разбираются в Query Plans. При любом алгоритме набор подходящих пар и их кратность должны остаться теми же.

CROSS JOIN полезен для намеренной сетки: например, все сочетания каналов оплаты и дней для отчёта с нулевыми значениями. Его размер равен N × M, если один вход пуст — результат пуст. При обычной связи таблиц явно пиши ON: внешний ключ проверяет данные, но сам не добавляет условие в запрос.

Под капотом: USING задаёт условие, NATURAL зависит от схемы

USING (payment_id) — краткая запись равенства одноимённых столбцов; в результате остаётся один общий столбец этого имени. В нашем примере имена p.id и r.payment_id разные, поэтому нужен ON. NATURAL JOIN выбирает все общие имена автоматически: добавление одноимённого поля меняет смысл запроса. Явное условие легче проверить при изменении схемы.

LEFT сохраняет отсутствие совпадений, WHERE может убрать его

LEFT JOIN сначала даёт подходящие пары, как INNER. Если у левой строки нет ни одной пары с TRUE, он добавляет ровно одну строку с NULL во всех правых столбцах. При k совпадениях получится max(1, k) строк на одну левую. Условие «все платежи» соблюдено; условие «один раз каждый» — только при не более чем одном совпадении.

Нужны все платежи и только проведённые возвраты рядом. Поставим r.state = 'settled' в ON: pending-заявки не образуют подходящих пар. У платежа 3 заявка существует, но для этого соединения совпадений нет, поэтому справа появляется NULL.

SELECT p.id AS payment, r.id AS refund, r.state
FROM payments p
LEFT JOIN refunds r ON r.payment_id = p.id AND r.state = 'settled' -- Отбираем совпадения.
ORDER BY p.id, r.id;
 payment | refund |  state
---------+--------+---------
       1 |    101 | settled
       2 |   NULL | NULL
       3 |   NULL | NULL
       4 |   NULL | NULL
(4 rows)

Теперь перенесём проверку состояния в WHERE. Сначала платёж 3 соединится с pending-заявкой, а затем готовая строка не пройдёт фильтр. Строки с добавленными NULL тоже исчезнут: NULL = 'settled' даёт UNKNOWN, а WHERE сохраняет только TRUE.

SELECT p.id AS payment, r.id AS refund, r.state
FROM payments p
LEFT JOIN refunds r ON r.payment_id = p.id
WHERE r.state = 'settled' -- Отбираем готовые строки: NULL тоже не проходит.
ORDER BY p.id, r.id;
 payment | refund |  state
---------+--------+---------
       1 |    101 | settled
(1 row)

FULL JOIN сохраняет несопоставленные строки с обеих сторон. Для сверки с провайдером это позволяет увидеть и платежи без заявок, и заявку 104 без платежа. NULL в её ключе не совпадает с другим NULL по обычному =; сохранение строки обеспечивает тип соединения.

SELECT p.id AS payment, r.id AS refund, r.payment_id
FROM payments p
FULL JOIN refunds r ON r.payment_id = p.id -- Сохраняем несопоставленные строки с обеих сторон.
ORDER BY p.id NULLS LAST, r.id NULLS LAST;
 payment | refund | payment_id
---------+--------+------------
       1 |    101 |          1
       1 |    102 |          1
       2 |   NULL |       NULL
       3 |    103 |          3
       4 |   NULL |       NULL
    NULL |    104 |       NULL
(6 rows)

Добавленный NULL-ряд всё равно является строкой. Поэтому COUNT(*) считает его, а COUNT(r.id) — нет. Для отчёта «число проведённых возвратов каждого платежа» считаем правый первичный ключ, а не число строк после соединения.

SELECT p.id AS payment, count(*) AS rows_after_join, count(r.id) AS settled_refunds
FROM payments p
LEFT JOIN refunds r ON r.payment_id = p.id AND r.state = 'settled'
GROUP BY p.id
ORDER BY p.id;
 payment | rows_after_join | settled_refunds
---------+-----------------+-----------------
       1 |               1 |               1
       2 |               1 |               0
       3 |               1 |               0
       4 |               1 |               0
(4 rows)

Semi и anti выбирают платежи по существованию пары

Если нужен список платежей, у которых есть хотя бы одна заявка, поля заявки и число совпадений не нужны. INNER JOIN создаст две строки платежа 1, а проверка EXISTS оставит его один раз. Это semi join: для каждой левой строки ответить «совпадение есть?» и сохранить её, если да.

SELECT p.id, p.amount
FROM payments p
WHERE EXISTS (SELECT 1 FROM refunds r WHERE r.payment_id = p.id) -- Нужен факт, а не пары.
ORDER BY p.id;
 id | amount
----+--------
  1 |    100
  3 |    300
(2 rows)

Обратная задача — платежи без заявок. NOT EXISTS сохраняет левую строку, когда подходящих правых строк ноль: это anti join. Оба выражения возвращают TRUE или FALSE по наличию строк, поэтому неизвестный ключ заявки 104 не делает результат неизвестным.

SELECT p.id, p.amount
FROM payments p
WHERE NOT EXISTS (SELECT 1 FROM refunds r WHERE r.payment_id = p.id) -- Ни одной заявки.
ORDER BY p.id;
 id | amount
----+--------
  2 |    100
  4 |    400
(2 rows)

В PostgreSQL нет отдельного синтаксиса SEMI JOIN или ANTI JOIN для такого SELECT: смысл выражают через EXISTS и NOT EXISTS. SELECT 1 — соглашение: значение не используется, важен сам факт строки. Не нужно ни считать все заявки, ни устранять размножение через DISTINCT.

Условие внутри проверки задаёт, каких совпадений нет. Добавишь r.state = 'settled' — получишь платежи без проведённых возвратов, включая платёж 3 с pending-заявкой. «Нет проведённого возврата» и «нет никаких заявок» — разные бизнес-вопросы.

Anti join можно выразить как LEFT JOIN … WHERE r.id IS NULL, если r.id не бывает NULL у настоящей правой строки. Проверка nullable-поля заявки способна принять существующую строку за отсутствие. Первичный ключ refunds.id в нашем демо даёт надёжный признак.

NOT IN с NULL отвечает «неизвестно», а не «совпадения нет»

Попробуем найти платежи без заявок через NOT IN. Справа получится список 1, 1, 3, NULL. Для платежа 2 выражение означает 2 <> 1 AND 2 <> 1 AND 2 <> 3 AND 2 <> NULL. Первые сравнения истинны, последнее неизвестно; всё выражение равно UNKNOWN.

У платежей 1 и 3 есть равный элемент, поэтому результат FALSE. У 2 и 4 равного элемента нет, но NULL справа не позволяет доказать, что все элементы различны. WHERE не сохраняет ни FALSE, ни UNKNOWN: ошибочный anti-запрос вернёт ноль строк.

SELECT p.id,
       p.id NOT IN (SELECT r.payment_id FROM refunds r) AS not_in,
       NOT EXISTS (SELECT 1 FROM refunds r WHERE r.payment_id = p.id) AS not_exists
FROM payments p
ORDER BY p.id;
SELECT count(*) AS rows_kept
FROM payments p
WHERE p.id NOT IN (SELECT r.payment_id FROM refunds r); -- NULL справа лишает TRUE все несовпадения.
 id | not_in | not_exists
----+--------+------------
  1 | f      | f
  2 | NULL   | t
  3 | f      | f
  4 | NULL   | t
(4 rows)

 rows_kept
-----------
         0
(1 row)

В этом опыте p.id не бывает NULL. Фильтр WHERE r.payment_id IS NOT NULL внутри списка исправит запрос для этих ключей, но выражать отсутствие пары через NOT EXISTS проще и устойчивее к изменению nullable-полей. Его NULL-безопасность не означает «NULL равен NULL»: равенство в корреляции всё ещё проверяется обычным =.

Если левая сторона сама nullable, определись, что означает отсутствие значения. При непустом правом наборе NULL NOT IN (…) неизвестно. В NOT EXISTS сравнение с NULL не находит равных строк, поэтому левая строка остаётся. Если бизнес требует связывать отсутствующие значения друг с другом, это другой предикат: IS NOT DISTINCT FROM; его нужно выбрать явно.

NOT IN и NOT EXISTS — взаимозаменяемые записи одного anti join.

NOT IN проверяет, что значение отличается от всех правых значений. NOT EXISTS проверяет, что нет строки с TRUE в заданном условии. При NULL эти вопросы дают разные ответы; замена требует доказать подходящие ограничения данных.

Выбор JOIN начинается с того, что означает одна строка

Self join — обычное соединение, где одна таблица играет две роли. Например, ищем разные платежи одного клиента на одну сумму. Alias a обозначает первый платёж пары, b — второй. Условие a.id < b.id исключает сравнение строки с собой и оставляет одну ориентацию пары.

SELECT a.id AS first_payment, b.id AS second_payment, a.amount
FROM payments a
JOIN payments b ON a.customer_id = b.customer_id AND a.amount = b.amount
               AND a.id < b.id -- Не соединяем строку с собой, оставляем одну ориентацию пары.
ORDER BY a.id, b.id;
 first_payment | second_payment | amount
---------------+----------------+--------
             1 |              2 |    100
(1 row)

Если оставить только равенство клиента и суммы, появятся и пары строки с собой, и зеркальные пары 1/2 и 2/1. Условие a.id <> b.id уберёт первые, но сохранит обе ориентации. Такой поиск отмечает кандидатов для проверки: одинаковые клиент и сумма сами по себе не доказывают повторное списание.

Вернёмся к отчёту из первого шага. Нужна одна строка на платёж и сумма проведённых возвратов рядом. Сначала сведём заявки к одной строке на payment_id, затем соединим этот результат с платежами. Это согласует единицы строк двух входов: платёж и итог по тому же платежу.

SELECT p.id, p.amount, coalesce(r.total, 0) AS settled_refund_amount
FROM payments p
LEFT JOIN (
    SELECT payment_id, sum(amount) AS total
    FROM refunds
    WHERE state = 'settled'
    GROUP BY payment_id -- Теперь не больше одной строки на ключ платежа.
) r ON r.payment_id = p.id
ORDER BY p.id;
 id | amount | settled_refund_amount
----+--------+-----------------------
  1 |    100 |                    20
  2 |    100 |                     0
  3 |    300 |                     0
  4 |    400 |                     0
(4 rows)

Теперь четыре строки действительно обозначают четыре платежа: сумма p.amount равна 900. COALESCE превращает отсутствие суммы проведённых возвратов в ноль по смыслу отчёта. Неизвестная заявка 104 остаётся отдельной задачей сверки и не приписывается произвольному платежу.

Уникальность правого ключа может гарантировать не больше одного совпадения. Сам внешний ключ такой гарантии для дочерних заявок не даёт: он разрешает многим заявкам ссылаться на один платёж. Для составной связи проверяй все части ключа. При неверной кратности индекс ускорит ошибочный отчёт, но не исправит его результат.

  • JOIN создаёт пары: повтор левой строки при нескольких правых совпадениях — ожидаемый результат.
  • LEFT дополняет NULL только при отсутствии подходящих пар. WHERE фильтрует готовый результат и не создаёт дополнение заново.
  • Для проверки наличия и отсутствия пары используй semi/anti через EXISTS и NOT EXISTS.
  • NOT IN с NULL справа не подтверждает отсутствие значения. Ограничения nullable-полей меняют смысл запроса.
  • Перед агрегацией и пагинацией назови единицу строки. DISTINCT по сумме не восстанавливает идентичность платежа.

На собеседовании

Чем INNER, LEFT, FULL и CROSS JOIN отличаются по результату?

Я представляю JOIN как выбор пар строк. INNER сохраняет пары с TRUE в условии, CROSS — все сочетания. LEFT дополнительно сохраняет каждую левую строку без совпадения с NULL справа, FULL делает это для обеих сторон. FALSE и UNKNOWN в ON не образуют совпадения.

При нескольких совпадениях строка повторится и в LEFT: он обещает присутствие, а не уникальность. Поэтому для сверки выбираю FULL, для списка всех платежей с необязательными данными — LEFT, а для отчёта заранее проверяю, сколько пар приходится на один платёж.

  • SQL сохраняет кратность строк. Если одному ключу соответствуют m левых и n правых строк, равенство даёт m × n пар; картинка пересечения множеств эту кратность не показывает.
  • Модель всех пар не определяет физический алгоритм. Планировщик может не строить полный CROSS, но обязан сохранить семантику и количество результирующих строк.
  • Порядок строк не задан самим JOIN. Для воспроизводимого вывода и пагинации задаю явный ORDER BY с достаточным ключом порядка.

Почему условие правой таблицы в WHERE превращает LEFT JOIN в INNER?

Я разделяю два момента: ON выбирает совпадения, WHERE отбирает готовые строки. У LEFT строка без подходящей пары дополняется NULL справа. Если WHERE требует r.state = 'settled', такой ряд не проходит, потому что сравнение с NULL неизвестно.

Если нужны все платежи и проведённые возвраты рядом, условие состояния ставлю в ON. Тогда даже платёж только с pending-заявкой остаётся с NULL справа. Если нужны лишь платежи с проведённым возвратом, INNER с этим условием лучше выражает задачу.

  • Не любой фильтр справа убирает дополненные строки: r.id IS NULL, напротив, выбирает их. Проверяю, даёт ли конкретный предикат TRUE на добавленном NULL-ряде.
  • После удаления совпавшей строки WHERE не возвращается к outer join. Поэтому добавление OR r.id IS NULL не эквивалентно переносу условия состояния в ON.
Вернёт ли OR r.id IS NULL все четыре платежа? 
SELECT p.id AS payment, r.id AS refund
FROM payments p
LEFT JOIN refunds r ON r.payment_id = p.id
WHERE r.state = 'settled' OR r.id IS NULL
ORDER BY p.id, r.id;
 payment | refund
---------+--------
       1 |    101
       2 |   NULL
       4 |   NULL
(3 rows)

Нет, платёж 3 пропал. Его pending-заявка образовала настоящую пару, поэтому NULL-ряд не создавался. Затем оба условия WHERE оказались ложными. Нужно отбирать settled в ON, если цель — сохранить любой платёж.

Что такое semi и anti join? Когда брать EXISTS вместо JOIN?

Semi join оставляет левые строки, для которых есть совпадение справа, anti join — строки без такого совпадения. В PostgreSQL я выражаю их через EXISTS и NOT EXISTS с условием связи. Правая сторона отвечает только на вопрос о наличии и не добавляет свои строки к результату.

Если нужны платежи с заявками на возврат, EXISTS сохраняет один исходный платёж даже при десяти заявках. Если нужны сами заявки рядом, беру JOIN и принимаю нужную кратность. NOT EXISTS удобен для поиска необработанных или несопоставленных сущностей.

  • «Один раз» относится к каждой исходной левой строке. Если левый вход уже содержит повторы, EXISTS их не устраняет; это не DISTINCT по бизнес-ключу.
  • В варианте LEFT JOIN … WHERE r.id IS NULL проверяемое поле должно отличать отсутствие от настоящего совпадения. Nullable-описание заявки для этого не годится.
  • Anti с условием settled допускает наличие pending. Согласую предикат с бизнес-вопросом, прежде чем сравнивать способы записи.

Почему NOT IN неожиданно возвращает пустой результат при NULL?

NOT IN требует доказать, что значение отличается от каждого элемента справа. Если равный элемент не найден, но есть NULL, одно сравнение неизвестно и результат тоже UNKNOWN. WHERE его отбрасывает. В нашем примере платежи 2 и 4 существуют без заявок, но NOT IN не оставляет их.

Для поиска отсутствующей пары беру NOT EXISTS. Если сохраняю NOT IN, доказываю ограничения обеих сторон: правый набор не содержит NULL, а смысл nullable-значения слева определён. Удалить NULL только справа недостаточно для произвольного nullable-выражения слева.

  • При найденном равном элементе NOT IN даёт FALSE даже при других NULL. UNKNOWN получается у несовпавших значений: формулировка «любой NULL делает всё UNKNOWN» неверна.
  • NOT EXISTS с обычным равенством оставляет nullable-левую строку, потому что сравнения не дают TRUE. Если NULL должен совпадать с NULL по контракту, выбираю IS NOT DISTINCT FROM.
Изменится ли NULL NOT IN, если правый набор пуст? 
SELECT NULL::integer NOT IN (SELECT payment_id FROM refunds WHERE false) AS null_not_in_empty,
       NULL::integer NOT IN (SELECT payment_id FROM refunds WHERE payment_id IS NOT NULL) AS null_not_in_nonempty;
 null_not_in_empty | null_not_in_nonempty
-------------------+----------------------
 t                 | NULL
(1 row)

С пустым набором получается TRUE: нет значения, с которым нужно доказать неравенство. С непустым набором известные значения сравниваются с NULL и дают UNKNOWN. Поэтому ответ «NULL слева всегда делает NOT IN неизвестным» тоже требует этой границы.

После JOIN сумма выросла. Как найти причину и исправить отчёт?

Я проверяю, что обозначает строка до и после JOIN, и вывожу ключи обеих сторон без агрегирования. Если платёж соединяется с несколькими заявками, его сумма повторяется в каждой паре. SUM(DISTINCT amount) не чинит связь: разные платежи могут иметь одинаковую сумму.

Дальше выбираю по задаче. Нужен факт заявки — EXISTS. Нужен дочерний итог — сначала группирую заявки по payment_id, затем соединяю. Нужны все пары — оставляю JOIN, но не считаю повторённую родительскую сумму как независимые платежи.

  • Две независимые связи «один ко многим» размножают друг друга: m заявок и n событий платежа дают m × n сочетаний. Предагрегирую обе стороны или вычисляю нужные итоги отдельно.
  • При обычном равенстве гарантию одного совпадения даёт уникальность полного правого ключа соединения. FOREIGN KEY дочерней таблицы обеспечивает существование родителя, но разрешает много дочерних строк.
  • LIMIT после размножающего JOIN ограничивает пары. Чтобы страница содержала заданное число платежей, выбираю родительские строки до раскрытия дочерних данных; порядок запросов — в Queries, варианты подзапросов — в Subqueries & CTE.
