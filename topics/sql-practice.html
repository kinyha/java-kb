Сначала договорись, что считается одной строкой ответа

На live coding просят «второй платёж» или «найти дубликаты», а неверный запрос часто появляется ещё до первого SELECT. Второй по сумме ряд и вторая различная сумма — разные ответы. Повтор request ID может означать повторную попытку, а не лишнюю запись, которую можно удалить. Перед кодом сформулируй ключ результата, политику равенств и поведение для пустых групп.

Пять задач ниже используют один журнал попыток оплаты. Строка payments — отдельная попытка с уникальным ID; повторный request_id связывает попытки одного клиентского запроса внутри счёта. Статус PAID означает фактическое списание, FAILED — неуспешную попытку. В отчёте о деньгах суммируем все PAID, даже если request ID повторился: представление последней попытки не отменяет уже сделанные списания.

Суммы — целые минимальные единицы одной валюты. NULL amount допустим только для FAILED: запрос мог оборваться до получения суммы. NULL request_id означает, что идентификатор неизвестен; две такие строки нельзя считать одним запросом. В refunds лежат проведённые возвраты к PAID-платежам; несколько частичных возвратов разрешены. Это условия учебного набора, а не попытка описать полный банковский учёт.

Общая схема и данные: fixture.sql

После каждого преобразования проверяй единицу строки

Надпиши словами, что означает строка на каждом этапе: «попытка», «различная сумма счёта», «один request ID», «итог счёта». GROUP BY меняет эту единицу, оконная функция её сохраняет, соединение с несколькими дочерними строками может размножить. Эта проверка полезнее попытки угадать, нужен ли в конце DISTINCT.

Похожая ошибка возникает со «вторым местом». У Alice отсортированные суммы строк — 300, 300, 100, 50; различные суммы — 300, 100, 50. Это два разных набора до ранжирования. Удалять повторы после того, как выбрана вторая строка, поздно: неправильный кандидат уже выбран.

Для «ровно N строк» задай полный порядок: время и уникальный ID при равенстве времени. Для «все разделившие место» сначала определи, по каким значениям строки равны. Если добавить уникальный ID в ORDER BY функции DENSE_RANK, равных групп не останется: так можно незаметно превратить ранг значения в номер строки.

Не смешивай логический ответ с оптимизацией. Сначала объясни число строк и крайние случаи, затем обсуждай индекс, селективность и план. Для окон без подходящего порядка сортировка часто является заметной частью работы; для агрегатов и соединений стоимость зависит от объёма входа и выбранного алгоритма. Формула «любой SQL с одним SELECT работает за O(n)» ничего не доказывает.

Если задача решена, измени одно условие: включи неуспешные попытки, сохрани равные места или потребуй счёт без платежей. Умение показать, какой именно этап изменится, лучше демонстрирует понимание, чем запомненный шаблон запроса.

  • До SQL определи ключ строки ответа, смысл NULL, критерий равенства и политику top-N.
  • GROUP BY, окно и JOIN меняют количество строк разными способами. Проверяй единицу строки после каждого этапа.

  • Сравнивай ответ с явными expected в обе стороны и с учётом кратности, а не только по числу строк.

Задачи

Найти повторные request ID внутри счёта

На общей таблице payments найди пары (account_id, request_id), для которых записано больше одной попытки. Считай все статусы, поскольку проверяем повтор обращения, а не повтор успешного списания. Строки с NULL request_id не включай: неизвестные идентификаторы нельзя объединить в один клиентский запрос.

Верни account_id, request_id, attempts. Одна строка ответа — одна повторная пара. Вывод отсортируй по account_id, затем request_id. Ожидаемый ответ на общих данных:

account_idrequest_idattempts
1r-a2
2r-d2

Авторская задача · medium · группировка, NULL и составной бизнес-ключ

Заготовка: task_duplicates в starter.sql 
CREATE TEMP VIEW task_duplicates AS
-- Замени пустой SELECT запросом к payments.
SELECT NULL::integer AS account_id,
       NULL::text AS request_id,
       NULL::bigint AS attempts
WHERE false;
Подсказка 1

Ключ группы состоит из двух полей. r-a у Carol и r-a у Alice — разные запросы, потому что принадлежат разным счетам.

Подсказка 2

Отбрось строки без request_id до группировки. Проверка «попыток больше одной» относится к готовой группе, поэтому нужна после GROUP BY.

Решение 
SELECT account_id, request_id, count(*) AS attempts
FROM payments
WHERE request_id IS NOT NULL    -- неизвестные ID не составляют одну группу
GROUP BY account_id, request_id -- составной ключ, а не только request_id
HAVING count(*) > 1
ORDER BY account_id, request_id;

WHERE определяет вход группировки, HAVING отбирает группы по их размеру. COUNT(*) считает попытки независимо от статуса и суммы. У Alice одна из повторных попыток FAILED — исключение этого статуса спрятало бы повтор request ID. Группировка только по request_id смешала бы её r-a со строкой Carol и дала неверную кратность.

Результат — диагностический список, не список строк для DELETE. Повторная попытка может быть ожидаемым retry, а две PAID-попытки одного запроса могут требовать расследования повторного списания. Решение о компенсации нельзя вывести из одного HAVING без бизнес-контракта.

На больших данных план может использовать HashAggregate или GroupAggregate с сортировкой. Индекс по (account_id, request_id) бывает полезен для упорядоченного чтения, но запрос по всему журналу всё равно должен обработать соответствующие строки. На собеседовании достаточно объяснить масштаб входа и что именно хранится на группу, не обещая индексный поиск каждой пары.

Авторская задача · medium · различное значение против второй строки

Заготовка: task_second в starter.sql 
CREATE TEMP VIEW task_second AS
SELECT NULL::integer AS account_id,
       NULL::bigint AS second_amount
WHERE false;
Подсказка 1

Сначала получи таблицу, в которой одна строка — различная успешная сумма конкретного счёта. Только потом определяй второе место.

Подсказка 2

Пронумеруй суммы внутри account_id по убыванию. Чтобы сохранить счета без второго значения, начни финальный запрос с accounts и присоедини кандидата слева.

Подсказка 3

Условие «номер равен 2» должно ограничивать присоединяемого кандидата, а не удалять итоговые строки без совпадения.

Решение 
WITH amounts AS (
  SELECT DISTINCT account_id, amount
  FROM payments WHERE status = 'PAID' -- PAID amount не NULL по схеме
), ranked AS (
  SELECT account_id, amount,
         row_number() OVER (
           PARTITION BY account_id ORDER BY amount DESC
         ) AS rn
  FROM amounts                       -- равные суммы уже объединены
)
SELECT a.id AS account_id, r.amount AS second_amount
FROM accounts a
LEFT JOIN ranked r ON r.account_id = a.id AND r.rn = 2
ORDER BY a.id;

После amounts повторяющихся сумм внутри счёта нет, поэтому ROW_NUMBER уже нумерует значения, а не исходные платежи. Условие rn = 2 находится в ON: если кандидата нет, LEFT JOIN оставляет счёт и NULL. Внешний WHERE rn = 2 удалил бы Carol, Dave и Eve и нарушил требование «все счета».

Можно использовать DENSE_RANK по amount на исходных PAID-строках, но тогда несколько платежей со второй суммой дадут несколько строк ответа. Их потребуется свести к одному значению на счёт. В наших edge-проверках вторая сумма 0 встречается дважды: тест ловит такое размножение. RANK не заменяет DENSE_RANK: после двух одинаковых максимумов следующий ранг будет 3, а нам нужно второе различное значение.

Стоимость зависит от числа PAID-платежей и числа различных пар: удаление повторов и упорядочивание требуют работы, даже если итоговых строк мало. Для выборки отдельных счетов возможны другие формы запроса с индексом; на интервью сначала докажи именно семантику DISTINCT и NULL.

Как изменится задача, если нужна вторая строка, а не вторая различная сумма?

Убери DISTINCT и нумеруй исходные PAID-платежи. Для определённого выбора добавь уникальный id к порядку по amount. Теперь одинаковые суммы занимают отдельные позиции, и Alice может получить 300 вместо 100. Это изменение условия, а не альтернативная оптимизация исходного решения.

Авторская задача · medium · top-N в группе с определённой политикой ties

Заготовка: task_top в starter.sql 
CREATE TEMP VIEW task_top AS
SELECT NULL::integer AS account_id, NULL::integer AS payment_id,
       NULL::bigint AS amount, NULL::bigint AS position
WHERE false;
Подсказка 1

LIMIT 2 в конце всего запроса оставит два платежа всего журнала. Нужна отдельная нумерация для каждого account_id.

Подсказка 2

Исключи FAILED до ранжирования. Для точного числа строк используй ROW_NUMBER с двумя полями сортировки; фильтр по номеру поставь на следующем уровне запроса.

Решение 
WITH ranked AS (
  SELECT account_id, id AS payment_id, amount,
         row_number() OVER (
           PARTITION BY account_id
           ORDER BY created_at DESC, id DESC -- полный порядок при равном времени
         ) AS position
  FROM payments WHERE status = 'PAID'       -- ранжируем только кандидатов
)
SELECT account_id, payment_id, amount, position
FROM ranked WHERE position <= 2
ORDER BY account_id, position;

ROW_NUMBER даёт каждой строке свою позицию. У Alice платёж 105 идёт первым, а из двух платежей с одинаковым временем вторым становится 104. FAILED 106, хотя он новее всех, не занимает место в рейтинге. Если сначала пронумеровать все попытки и лишь потом убрать FAILED, можно получить меньше двух PAID даже там, где они есть.

Равенство created_at разрешено id, но это правило только для воспроизводимого ответа, не доказательство реальной причинности событий. Если бизнес требует иной порядок, например номер версии от платёжного провайдера, сортировать нужно по нему. Внешний ORDER BY нужен отдельно: порядок окна не обещает порядок строк готового результата.

Для большого числа строк обсуди индекс по (account_id, created_at DESC, id DESC), в том числе частичный для PAID, и фактический план. Для небольшого заранее выбранного списка счетов альтернативой служит LATERAL с LIMIT. Эти формы имеют одинаковую цель, но разный характер доступа к данным; заранее объявлять одну «всегда быстрее» нельзя.

Интервьюер меняет условие: нужны две последние различные даты и все платежи этих дат. Достаточно убрать id?

Нет: ROW_NUMBER всё равно раздаёт разные номера равным датам. Нужно ранжировать группы равных created_at через DENSE_RANK и отбирать ранг не больше 2. Уникальный id исключи именно из оконного ORDER BY, иначе равные даты перестанут быть равными для ранга; во внешней сортировке id можно оставить. Количество строк теперь вправе превышать два.

Подсказка 3

Отдельные FILTER позволяют посчитать PAID и FAILED в одной группировке. Затем присоедини итог к accounts и замени отсутствующие агрегаты нулями согласно условию.

Решение 
WITH refunds_per_payment AS (
  SELECT payment_id, sum(amount) AS refunded
  FROM refunds GROUP BY payment_id          -- теперь максимум одна строка на платёж
), totals AS (
  SELECT p.account_id,
         count(*) FILTER (WHERE p.status = 'PAID') AS paid_count,
         count(*) FILTER (WHERE p.status = 'FAILED') AS failed_count,
         sum(p.amount) FILTER (WHERE p.status = 'PAID') AS gross,
         sum(coalesce(r.refunded, 0))
           FILTER (WHERE p.status = 'PAID') AS refunded
  FROM payments p
  LEFT JOIN refunds_per_payment r ON r.payment_id = p.id
  GROUP BY p.account_id
)
SELECT a.id AS account_id,
       coalesce(t.paid_count, 0) AS paid_count,
       coalesce(t.failed_count, 0) AS failed_count,
       coalesce(t.gross, 0) AS gross,
       coalesce(t.refunded, 0) AS refunded,
       coalesce(t.gross, 0) - coalesce(t.refunded, 0) AS net
FROM accounts a LEFT JOIN totals t ON t.account_id = a.id
ORDER BY a.id;

Первый CTE превращает два возврата платежа 101 в одну сумму 50. После соединения строка 101 остаётся единственной, поэтому gross и paid_count не завышаются. Сначала возвращаем кардинальность к одной строке на платёж, затем агрегируем по счёту. Эквивалентный подход — отдельно собрать суммы платежей и возвратов по счёту и соединить уже эти итоги.

COALESCE нужен на двух уровнях по разным причинам. Внутри нет возврата у конкретного PAID-платежа — вклад refunded равен 0. Снаружи Dave вообще отсутствует в totals, а у Eve нет входных строк для SUM с фильтром PAID. По условию оба случая дают нулевые деньги, но failed_count у Eve остаётся 1. COUNT(amount) для количества попыток был бы неверен: FAILED с неизвестной суммой тоже попытка.

SUM(DISTINCT p.amount) не исправляет прямое соединение. Оно удаляет равные значения сумм, а не повторения одного payment_id. У Alice два разных PAID-платежа по 300, оба должны участвовать в gross. При прямом JOIN платёж 101, наоборот, встретится дважды из-за двух возвратов. Нужен контроль единицы строки, а не глобальная уникальность суммы.

В PostgreSQL SUM(bigint) возвращает numeric, поэтому денежные колонки заготовки имеют этот тип. В Java-проекции не предполагай автоматически Long только потому, что исходное поле bigint. На больших таблицах обсуждай объём предварительных агрегатов и соединений; индекс refunds(payment_id) полезен для доступа по платежу, но группировка всего журнала не превращается в бесплатную операцию.

В отчёт добавляют количество уведомлений платежа из второй дочерней таблицы. Можно просто присоединить её рядом с refunds?

Если у платежа два возврата и три уведомления, прямое соединение двух дочерних наборов даст шесть сочетаний. Предварительно сведи каждый независимый набор к одной строке на payment_id, затем соединяй итоги с платежом. Иначе даже сумма возвратов, которая раньше считалась правильно, начнёт повторяться по числу уведомлений.

Оставить последнюю попытку запроса, сохранив неизвестные request ID

Сформируй представление последней попытки для каждой пары (account_id, request_id) с известным request_id. Выбирай по created_at DESC, затем id DESC. Статус при выборе не фильтруй: последняя попытка может быть FAILED. Для NULL request_id сохрани каждую исходную строку отдельно — доказательств, что это один запрос, нет.

Верни account_id, request_id, payment_id, status. Никакие записи не удаляй. Сортировка: account_id, request_id с NULL в конце, затем payment_id. Это отчёт о последних попытках, поэтому он не заменяет финансовую агрегацию предыдущей задачи.

Подсказка 1

Для известного request_id задача похожа на top-1, только ключ группы теперь состоит из двух полей, а статусы не ограничиваются.

Подсказка 2

PARTITION BY account_id, request_id объединит NULL request ID одного счёта в одну группу. Проще применить разные правила к двум непересекающимся наборам.

Подсказка 3

В первой ветке оставь rn = 1 среди известных запросов; во второй верни все неизвестные без ранжирования. Соедини ветки через UNION ALL.

Решение 
WITH known_requests AS (
  SELECT p.*,
         row_number() OVER (
           PARTITION BY account_id, request_id
           ORDER BY created_at DESC, id DESC
         ) AS rn
  FROM payments p WHERE request_id IS NOT NULL
)
SELECT account_id, request_id, id AS payment_id, status
FROM known_requests WHERE rn = 1
UNION ALL
SELECT account_id, request_id, id AS payment_id, status
FROM payments WHERE request_id IS NULL
ORDER BY account_id, request_id NULLS LAST, payment_id;

Две ветки не пересекаются по условию NULL, а исходный id уникален. Здесь не нужен DISTINCT: мы заранее выразили, где требуется один представитель группы, а где должны остаться все строки. Alice сохраняет обе неизвестные попытки 105 и 106, а Eve — 501. Из двух r-a Alice выбирается FAILED 102, при этом r-a Carol остаётся независимой группой.

Не используй MAX(created_at) вместе с независимо выбранными MAX(id) и MAX(status): агрегаты могут прийти из разных строк и собрать несуществующую попытку. Присоединение обратно по максимальному времени тоже недостаточно, если на нём несколько строк. ROW_NUMBER выбирает целую исходную строку по полному порядку.

Подмена NULL выражением вроде coalesce(request_id, id::text) кажется короткой, но способна столкнуть неизвестную попытку с настоящим текстовым request ID, равным этому числу. Разделение наборов не требует придумывать зарезервированный префикс и объяснять его уникальность. Альтернатива — составной ключ, который отдельно хранит признак неизвестности и исходный ID.

Для полного журнала решение обрабатывает известные запросы с разбиением на группы и упорядочиванием внутри них. Индекс по (account_id, request_id, created_at DESC, id DESC) может помочь форме доступа, но его цена для записи тоже существует. Если отчёт нужен часто, сначала измерь план и частоту обновлений; не добавляй индекс только из-за совпадения имён колонок в запросе.
