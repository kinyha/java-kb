Subqueries & CTE

Подзапрос описывает результат, которым пользуется другая часть SQL: одно значение, факт существования или набор строк. Корреляция добавляет зависимость от текущей внешней строки. CTE даёт промежуточному результату имя, LATERAL позволяет зависимому подзапросу вернуть несколько строк и столбцов, а рекурсивный CTE повторяет шаг над очередной порцией найденных строк. Сначала определи форму результата и зависимости, затем смотри физический план.

Подзапрос должен вернуть результат нужной формы

В кабинете клиента нужно показать счета и максимальный успешный платёж для каждого. У Alice несколько платежей, у Bob два, у Carol ни одного. Если сделать отдельный запрос из Java для каждого счёта, появится N+1 с сетевыми задержками. SQL позволяет описать вычисление рядом со строкой счёта, но сначала нужно решить, что должно вернуться: одно число, несколько платежей или только ответ «есть».

Данные всех примеров ниже одинаковы. Суммы храним целыми в минимальных единицах одной валюты. У платежей Bob намеренно одинаковое время: позже это заставит нас явно выбрать порядок при равенстве дат.

CREATE TEMP TABLE accounts (id integer PRIMARY KEY, owner text NOT NULL);
CREATE TEMP TABLE payments (
  id integer PRIMARY KEY,
  account_id integer NOT NULL REFERENCES accounts(id),
  amount bigint NOT NULL,
  status text NOT NULL,
  created_at timestamp NOT NULL
);
INSERT INTO accounts VALUES (1, 'Alice'), (2, 'Bob'), (3, 'Carol');
INSERT INTO payments VALUES
  (101, 1, 100, 'PAID',   '2026-01-01 10:00'),
  (102, 1, 300, 'FAILED', '2026-01-02 10:00'),
  (103, 1, 250, 'PAID',   '2026-01-03 10:00'),
  (201, 2,  50, 'PAID',   '2026-01-03 10:00'),
  (202, 2,  70, 'PAID',   '2026-01-03 10:00');

Скалярный подзапрос в выражении должен иметь один столбец и не более одной строки. Одна строка даёт значение, ноль строк — SQL NULL, больше одной — ошибку cardinality violation. Поэтому имя «скалярный» описывает контракт результата, а не обещание, что написанный SELECT действительно ему соответствует.

SELECT a.id,
       (SELECT max(p.amount) FROM payments p
        WHERE p.account_id = a.id AND p.status = 'PAID') AS max_paid,
       (SELECT p.amount FROM payments p
        WHERE p.account_id = a.id AND p.id = 103) AS amount_103
FROM accounts a ORDER BY a.id;
id|max_paid|amount_103
1|250|250
2|70|NULL
3|NULL|NULL

Вторая колонка использует агрегат без GROUP BY: он создаёт одну строку даже при пустом входе, а MAX пустого набора равен NULL. Третья колонка ограничена уникальным p.id; у Bob и Carol подзапрос не вернул строк. Снаружи оба пути дают NULL, хотя внутри произошло разное. COALESCE(..., 0) допустим, только если бизнесу действительно не нужно различать «платежей не было» и «максимум равен нулю».

Удалим агрегат и ограничение по уникальному ID. Для Alice останутся три строки; SQL не выберет из них первую. В полном демо ожидаемая ошибка перехвачена отдельно, остальные ошибки останавливают запуск:

DO $$
BEGIN
  PERFORM (SELECT p.amount FROM payments p WHERE p.account_id = 1);
  RAISE EXCEPTION 'expected cardinality_violation';
EXCEPTION WHEN cardinality_violation THEN
  RAISE NOTICE 'scalar multirow SQLSTATE = %', SQLSTATE;
END $$;
NOTICE:  scalar multirow SQLSTATE = 21000

Корреляция передаёт внешние значения, EXISTS проверяет строки

В условии p.account_id = a.id имя p принадлежит внутреннему SELECT, а a — внешнему. Такой подзапрос коррелирован: его результат зависит от текущего счёта. Для понимания можно мысленно подставить сначала 1, затем 2 и 3. Это логическая модель зависимости, а не обязательный цикл из трёх отдельных сканирований в плане PostgreSQL.

EXISTS возвращает boolean: true, если подзапрос произвёл хотя бы одну строку, false — если ни одной. Содержимое найденной строки обычно не нужно, поэтому пишут SELECT 1. Это соглашение о намерении, а не оптимизация значения 1. Нельзя помещать туда действия, на выполнение которых рассчитывает приложение: PostgreSQL не обязан вычислять всё содержимое и читать все строки подзапроса.

SELECT a.id,
       EXISTS (SELECT 1 FROM payments p
               WHERE p.account_id = a.id AND p.status = 'PAID') AS has_paid,
       -- Ловушка: count(*) без GROUP BY создаёт строку даже для пустого входа.
       EXISTS (SELECT count(*) FROM payments p
               WHERE p.account_id = a.id AND p.status = 'PAID') AS count_row_exists
FROM accounts a ORDER BY a.id;
id|has_paid|count_row_exists
1|t|t
2|t|t
3|f|t

У Carol агрегат вычисляет число 0, но EXISTS видит строку с этим нулём и возвращает true. Для вопроса «есть ли успешный платёж» нужен первый вариант. Выражение (SELECT count(*) ...) > 0 тоже проверяет наличие, но требует выразить и посчитать число там, где оно не нужно; предпочитай прямой EXISTS. При этом конкретный объём работы определяется планом, а не только синтаксисом.

Для отбора счетов перенеси первый EXISTS в WHERE. Для счетов без подходящих платежей используй NOT EXISTS с тем же коррелирующим условием. Различие с NOT IN при NULL, semi/anti join и размножение строк при обычном соединении разобраны в Joins. Здесь важна граница: проверка наличия не возвращает столбцы платежа.

Коррелированный подзапрос обязательно выполняется N раз и поэтому всегда медленнее JOIN.

Корреляция описывает зависимость от внешних значений. Планировщик может преобразовать EXISTS в semi join; скалярный подзапрос может остаться SubPlan с повторными запусками. Сравнивай реальные планы и число loops на своих данных. Замена формы SQL без сохранения NULL и числа строк может изменить ответ, даже если ускоряет запрос.

Всегда квалифицируй поля алиасами. Если во внутреннем SELECT ошибиться именем столбца, PostgreSQL может найти одноимённый столбец во внешнем scope. Запрос останется корректным синтаксически, но получит другую корреляцию. Явные p.account_id и a.id делают зависимость видимой при ревью.

LATERAL возвращает таблицу для текущей внешней строки

Теперь кабинету нужны два последних успешных платежа каждого счёта: ID и сумма, а не одно число. Скалярный подзапрос не подходит по форме. Обычный подзапрос в FROM не может просто сослаться на соседний a.id. LATERAL разрешает правой части использовать строки, стоящие слева от неё, и вернуть для каждой ноль, одну или несколько строк.

SELECT a.id AS account_id, p.id AS payment_id, p.amount
FROM accounts a
LEFT JOIN LATERAL (
  SELECT p.id, p.amount, p.created_at FROM payments p
  WHERE p.account_id = a.id AND p.status = 'PAID'
  ORDER BY p.created_at DESC, p.id DESC -- id разрешает равенство времени
  LIMIT 2                              -- два на счёт, а не на весь результат
) p ON true
ORDER BY a.id, p.created_at DESC, p.id DESC;
account_id|payment_id|amount
1|103|250
1|101|100
2|202|70
2|201|50
3|NULL|NULL

LEFT JOIN ... ON true сохраняет Carol: зависимая таблица пуста, поэтому столбцы платежа заполняются NULL. CROSS JOIN LATERAL в этой ситуации убрал бы её строку. Условие ON true здесь не связывает счета с платежами: связь уже задана внутри, а ON лишь принимает все строки полученного результата. Правила outer join остаются обычными.

Два ORDER BY решают разные задачи. Внутренний выбирает, какие именно два платежа попадут в результат для счёта. Внешний определяет порядок готового ответа. Без p.id DESC у Bob нет определённого победителя при LIMIT 1: время одинаковое. Внешняя сортировка не исправит произвольный выбор, уже сделанный внутри LIMIT.

Под эту форму доступа подходит индекс с account_id первым и последующими ключами в порядке top-N. В демо он создан так:

CREATE INDEX payments_account_latest
ON payments(account_id, created_at DESC, id DESC)
WHERE status = 'PAID'; -- индекс хранит только нужное подмножество

На большой таблице такой индекс позволяет найти диапазон одного счёта и остановиться после двух записей. На наших пяти платежах PostgreSQL вправе предпочесть последовательное чтение: наличие подходящего индекса не принуждает планировщик его выбрать. Если нужны последние платежи миллионов счетов, миллионы коротких обращений тоже стоят дорого. Сравни LATERAL с обработкой общего набора и ранжированием из Window Functions; выбирай по селективности внешнего набора.

Корреляция задаёт область видимости, но не заменяет план

LATERAL — полезная модель «параметризованной таблицы»: слева получен account_id, справа найден его top-N. Зависимость ограничивает возможные перестановки соединений. В плане часто видны Nested Loop и внутренний Limit с параметром внешней строки; если зависимость удаётся устранить, план может выглядеть иначе. Не считай ключевое слово обещанием определённого алгоритма или кеширования результатов для повторяющихся значений.

CTE даёт имя результату, но не обещает отдельное вычисление

WITH c AS (...) определяет именованный результат в пределах одного SQL-оператора. Это удобно, когда запрос распадается на смысловые этапы: отобрать успешные платежи, посчитать итоги, сравнить их с порогом. Имя CTE можно использовать несколько раз. Оно не создаёт постоянную таблицу, не становится кешем между запросами и само по себе не задаёт порядок вычислений.

Начиная с PostgreSQL 12, нерекурсивный CTE на SELECT без побочных эффектов может быть встроен в родительский запрос. Здесь «без побочных эффектов» означает, в частности, отсутствие volatile-функций. По умолчанию при одной ссылке подходящий CTE встраивается; при нескольких обычно вычисляется отдельно и используется повторно. Поэтому правило «WITH всегда является барьером оптимизации» описывает старое поведение, а не современный PostgreSQL.

Для подходящего CTE MATERIALIZED запрещает такое объединение, а NOT MATERIALIZED разрешает его и при нескольких ссылках. Это выбор между повторным использованием результата и возможностью протолкнуть разные внешние фильтры внутрь. NOT MATERIALIZED не заставляет встроить рекурсивный CTE или SELECT с volatile-функциями: условия применимости сохраняются.

Проверим механизм на 20 000 строках. У ledger.id есть индекс первичного ключа, статистика собрана ANALYZE. Сначала обычный CTE, используемый один раз:

CREATE TEMP TABLE ledger (id integer PRIMARY KEY, amount integer NOT NULL);
INSERT INTO ledger SELECT n, n % 1000 FROM generate_series(1, 20000) n;
ANALYZE ledger;

EXPLAIN (ANALYZE, COSTS OFF, TIMING OFF, SUMMARY OFF)
WITH c AS (SELECT id, amount FROM ledger)
SELECT amount FROM c WHERE id = 42;
Index Scan using ledger_pkey on ledger (actual rows=1 loops=1)
  Index Cond: (id = 42)

Узла CTE Scan нет: условие по ID попало прямо в индексное чтение. Теперь запрещаем встраивание, сохраняя тот же логический ответ:

EXPLAIN (ANALYZE, COSTS OFF, TIMING OFF, SUMMARY OFF)
WITH c AS MATERIALIZED (SELECT id, amount FROM ledger)
SELECT amount FROM c WHERE id = 42;
CTE Scan on c (actual rows=1 loops=1)
  Filter: (id = 42)
  Rows Removed by Filter: 19999
  CTE c
    ->  Seq Scan on ledger (actual rows=20000 loops=1)

CTE произвёл 20 000 строк, внешний фильтр отбросил 19 999. Это фактические счётчики выполнения, не оценка cost. Мы не утверждаем универсальный выигрыш во столько же раз: время включает другие расходы. Но лишняя работа видна без сравнения микросекунд на маленьком стенде. В другом запросе родитель может запросить лишь часть результата материализованного SELECT; MATERIALIZED не означает безусловно «всегда прочитать всё до конца».

Две ссылки: дешевле вычислить дважды или сохранить всё?

Для двух разных ID можно разрешить независимое проталкивание фильтров. На этих данных получаются два точечных чтения вместо общего результата из 20 000 строк:

EXPLAIN (ANALYZE, COSTS OFF, TIMING OFF, SUMMARY OFF)
WITH c AS NOT MATERIALIZED (SELECT id, amount FROM ledger)
SELECT (SELECT amount FROM c WHERE id = 42) AS first,
       (SELECT amount FROM c WHERE id = 43) AS second;
Result (actual rows=1 loops=1)
  InitPlan 1
    ->  Index Scan using ledger_pkey on ledger (actual rows=1 loops=1)
          Index Cond: (id = 42)
  InitPlan 2
    ->  Index Scan using ledger_pkey on ledger ledger_1 (actual rows=1 loops=1)
          Index Cond: (id = 43)

Обратный случай — дорогой расчёт, один и тот же результат которого нужен несколько раз. Встраивание способно повторить расчёт, а материализация — выполнить его один раз. Если промежуточный набор велик, хранение требует памяти и может использовать временные файлы. Выбирай по плану и нагрузке, а не по длине текста запроса. Не путай CTE MATERIALIZED с materialized view: у view другой жизненный цикл и явное обновление.

Рекурсивный CTE обрабатывает очередной фронт найденных строк

У исходного платежа 101 есть связанные операции 301 и 302, а у 301 — дальнейшая корректировка 401. Чтобы собрать всю цепочку зависимостей неизвестной глубины, одного фиксированного JOIN недостаточно. Храним рёбра parent_id → child_id и повторяем один шаг: для текущих операций найти их непосредственных потомков.

CREATE TEMP TABLE operation_edges (
  parent_id integer NOT NULL, child_id integer NOT NULL,
  PRIMARY KEY (parent_id, child_id)
);
INSERT INTO operation_edges VALUES (101,301), (101,302), (301,401);

WITH RECURSIVE related(id, depth) AS (
  VALUES (101, 0)                         -- начальная строка, anchor
  UNION ALL
  SELECT e.child_id, r.depth + 1
  FROM related r JOIN operation_edges e ON e.parent_id = r.id
)
SELECT id, depth FROM related ORDER BY depth, id;
id|depth
101|0
301|1
302|1
401|2

Начальная часть выполняется один раз, её строки попадают и в результат, и в рабочую таблицу. Затем рекурсивная часть использует related как текущую рабочую таблицу, а не как все строки, когда-либо найденные запросом. Новые строки добавляются в общий результат и заменяют рабочую таблицу на следующей итерации. Когда следующая порция пуста, вычисление заканчивается. Внутри это итерация над наборами, а не рекурсивные вызовы Java-метода.

Цикл определяется по выбранной identity, а не по слову RECURSIVE

Добавим ошибочное ребро 401 → 101. Теперь исходная форма с UNION ALL бесконечно получает новые порции. В PostgreSQL нет автоматического бизнес-ограничения глубины: нужен критерий остановки. В демо действует statement_timeout = '5s' как страховка запуска, но правильное завершение задаёт сам запрос.

INSERT INTO operation_edges VALUES (401,101);
WITH RECURSIVE related(id, depth) AS (
  VALUES (101, 0)
  UNION ALL
  SELECT e.child_id, r.depth + 1
  FROM related r JOIN operation_edges e ON e.parent_id = r.id
) CYCLE id SET is_cycle USING path
SELECT id, depth, is_cycle FROM related ORDER BY depth, id;
id|depth|is_cycle
101|0|f
301|1|f
302|1|f
401|2|f
101|3|t

CYCLE отслеживает повтор ID в текущем пути. Строка, замыкающая цикл, попадает в результат с is_cycle = true, но из неё поиск дальше не продолжается. Для ответа без этой строки добавь WHERE NOT is_cycle в финальный SELECT; для диагностики её полезно оставить. Два разных пути до одной операции — не обязательно цикл: CYCLE проверяет путь, а не глобальную уникальность результата.

UNION вместо UNION ALL удаляет дубликаты целых строк, в том числе уже встречавшихся на прошлых итерациях. Если CTE возвращает только ID, повторный 101 исчезнет и этот граф завершится. Но с (id, depth) строки (101, 0) и (101, 3) различаются: смена UNION не спасает. Ниже отдельная проверка этой развилки в карточке.

SEARCH задаёт ключ сортировки, а не порядок обхода движком

Начиная с PostgreSQL 14 доступны SEARCH и CYCLE. SEARCH DEPTH FIRST BY id SET ordercol или BREADTH FIRST добавляет служебный столбец для желаемого порядка вывода; затем нужен внешний ORDER BY ordercol. Это не команда планировщику выполнять рекурсивные шаги именно в таком порядке. Наша сортировка ORDER BY depth, id уже явно показывает уровни и стабильный порядок внутри них.

Для графа с большим числом путей результат может расти гораздо быстрее числа вершин даже без циклов. Если нужны уникальные достижимые операции, форма с одним ID и UNION выражает другую задачу, чем перечисление всех путей с UNION ALL и path. Определи требуемую уникальность до выбора защиты от циклов.

Форма SQL выбирается по смыслу, стоимость проверяется планом

Один результат часто можно получить подзапросом, соединением или оконной функцией. Начни с вопроса: нужны столбцы связанных строк, факт наличия, одно агрегированное значение или повторяемый шаг по графу? Так проще сохранить пустые случаи и число строк. Затем проверь стоимость: читабельная форма сама по себе не гарантирует хороший доступ к данным.

В EXPLAIN (ANALYZE, BUFFERS) для подзапроса ищи SubPlan/InitPlan, для материализации — CTE Scan, для рекурсии — Recursive Union и WorkTable Scan. Названия показывают организацию работы. Счётчик loops объясняет, сколько раз запущен внутренний узел; actual rows при нескольких loops — среднее число строк за запуск. Дешёвый внутренний поиск, повторённый миллион раз, перестаёт быть дешёвым в сумме.

Большое число Rows Removed by Filter подсказывает, что данные отсекаются поздно. В нашем CTE-примере причина видна прямо в дереве: фильтр расположен над материализацией. При временных файлах смотри объём промежуточного результата и память на операции, а при LATERAL — сколько внешних строк породило индексные обращения. Детали чтения плана вынесены в EXPLAIN; здесь важно не выводить скорость из наличия слова WITH или EXISTS.

Не лечи нарушение скалярности случайным LIMIT 1. Если данные должны быть уникальны, закрепи это ограничением, иначе запрос скроет ошибку модели. Если нужна последняя запись, задай полный порядок. Если нужна сумма, агрегируй явно. При переписывании в JOIN проверь, не исчезли ли счета без платежей и не размножились ли строки; те же проверки нужны при переходе на окна.

Внешний LIMIT не является надёжной защитой бесконечной рекурсии. Некоторые запросы смогут остановиться после первых строк, но ORDER BY или соединение выше могут потребовать весь результат. Остановка должна следовать из рекурсивного условия, устранения дубликатов или контроля цикла; timeout ограничивает ущерб, а не доказывает корректность.

В этой теме CTE используется для чтения. Изменяющие данные CTE, транзакционная видимость, блокировки и побочные эффекты функций требуют отдельных правил; их нельзя переносить из модели обычного SELECT по аналогии. Задачи на массовое ранжирование принадлежат Window Functions, комбинации соединений — Joins, тренировка запросов — SQL Practice.

  • Скалярный подзапрос: одна строка — значение, ноль — NULL, несколько — ошибка. Форма результата важнее расположения скобок.
  • EXISTS проверяет наличие строк. COUNT без GROUP BY сам создаёт строку, поэтому EXISTS над ним не проверяет наличие платежей.
  • LATERAL выражает зависимый табличный результат; LEFT сохраняет пустые внешние строки, внутренний ORDER BY задаёт выбор top-N.
  • CTE — имя в одном SQL-операторе. В PostgreSQL 12+ подходящий SELECT CTE может встраиваться; материализация меняет возможности оптимизации.
  • Рекурсивный шаг видит текущую рабочую таблицу. UNION устраняет повтор целой строки, CYCLE проверяет выбранную identity внутри пути.

На собеседовании

Что такое коррелированный подзапрос и когда нужен LATERAL?

Коррелированный подзапрос использует значения внешней строки: например, ищет платежи с account_id текущего счёта. Я сначала определяю форму ответа. Для одного максимума подходит скалярный подзапрос; если он вернёт несколько строк, будет ошибка, а при отсутствии строк получится NULL. Для нескольких последних платежей с несколькими столбцами использую LATERAL в FROM.

LATERAL разрешает правой части ссылаться на строки слева. LEFT JOIN LATERAL сохраняет счёт без платежей, CROSS JOIN LATERAL убирает его. Если внутри LIMIT, обязательно задаю ORDER BY с правилом разрешения равенства, иначе выбор «последнего» не определён.

  • Корреляция — зависимость в SQL, а не гарантия N физических запусков. Смотрю SubPlan, параметризованные узлы и loops; оптимизатор может преобразовать запрос.
  • Top-N через LATERAL удобен для небольшого внешнего набора с индексом по ключу и порядку. Для всех групп большого набора сравниваю с ранжированием общего потока.
  • LIMIT 1 не заменяет уникальность. Он либо выражает осмысленный выбор по полному порядку, либо маскирует несколько строк там, где модель обещала одну.

Что именно проверяет EXISTS и почему SELECT COUNT(*) внутри него — ловушка?

EXISTS проверяет, вернул ли подзапрос хотя бы одну строку, и выдаёт true или false. Сами значения обычно не важны, поэтому я пишу SELECT 1. Для счёта с несколькими платежами внешний счёт остаётся одной строкой: EXISTS не присоединяет каждое совпадение.

COUNT без GROUP BY возвращает одну строку даже для пустого набора, со значением 0. Поэтому EXISTS над таким агрегатом равен true и для счёта без платежей. Я проверяю существование строк платежей напрямую, а агрегат беру, только если нужен сам счётчик.

  • Не рассчитываю на побочные эффекты внутри EXISTS: содержимое SELECT и весь вход не обязаны вычисляться. Возможность остановиться после найденной строки не означает конкретный план на любых данных.
  • NOT EXISTS ищет отсутствие совпадения по выбранному условию. Его нельзя механически заменить на NOT IN, не проверив NULL и требуемую логику сравнения.
  • Случайно найденное во внешнем scope неквалифицированное имя способно изменить корреляцию без синтаксической ошибки. Алиасы — часть проверки корректности.

Материализуется ли CTE? Чем отличаются MATERIALIZED и NOT MATERIALIZED?

CTE даёт промежуточному результату имя в одном операторе, но не гарантирует временную таблицу. В PostgreSQL 12+ нерекурсивный SELECT CTE без volatile-функций может объединяться с родительским запросом: по умолчанию при одной ссылке встраивается, при нескольких обычно вычисляется отдельно для повторного использования.

MATERIALIZED запрещает объединение, NOT MATERIALIZED разрешает его для подходящего CTE и при нескольких ссылках. Встраивание помогает протолкнуть внешние фильтры внутрь; материализация помогает избежать повторения дорогого вычисления. Выбираю по плану: в демо одна форма прочитала индексом одну строку, другая сначала произвела 20 000.

  • NOT MATERIALIZED не отменяет ограничения для рекурсивных и содержащих volatile-функции CTE. Это не универсальная команда «оптимизируй всё».
  • Материализация может хранить большой промежуточный набор и использовать временные файлы. Встраивание нескольких ссылок может повторить дорогое выражение: оба направления требуют измерений.
  • Отдельно вычисляемый SELECT CTE не всегда читается до конца: потребитель может запросить лишь часть. В примере полный проход нужен из-за фильтра над материализованным набором.

Как выполняется рекурсивный CTE и почему UNION не всегда останавливает цикл?

Начальная часть даёт первые строки и рабочую таблицу. Рекурсивный шаг читает текущую рабочую таблицу, добавляет найденное в результат и заменяет рабочую таблицу новой порцией. Когда порция пуста, запрос завершается. Он не перечитывает весь накопленный результат на каждом шаге.

UNION убирает дубликаты целых строк. Если возвращаю только ID, повторный ID можно удалить; если вместе с ID растёт depth, каждая строка новая и цикл продолжается. Для циклов по ID использую CYCLE либо явный путь и проверку посещения. Ограничение глубины нужно, когда сама задача ограничена глубиной.

  • CYCLE проверяет повтор в конкретном пути и включает замыкающую строку с отметкой. Это не глобальная дедупликация вершин, достижимых несколькими путями.
  • SEARCH строит ключ порядка вывода, а не диктует порядок физического исполнения. Результат всё равно сортирую явно.
  • Даже ациклический граф способен породить огромное число путей. Решаю заранее, нужны уникальные вершины, все пути или ограниченный обход.
Рёбра 101 → 301 → 401 → 101 образуют цикл. Что меняет добавление depth?

Используй граф из урока, включая ветку 101 → 302. Первый запрос возвращает только ID:

WITH RECURSIVE related(id) AS (
  VALUES (101)
  UNION
  SELECT e.child_id
  FROM related r JOIN operation_edges e ON e.parent_id = r.id
)
SELECT id FROM related ORDER BY id;
id
101
301
302
401

Теперь добавь depth. Чтобы опыт гарантированно завершился, ограничение задано внутри рекурсивной части:

WITH RECURSIVE related(id, depth) AS (
  VALUES (101, 0)
  UNION
  SELECT e.child_id, r.depth + 1
  FROM related r JOIN operation_edges e ON e.parent_id = r.id
  WHERE r.depth < 4
)
SELECT id, depth FROM related ORDER BY depth, id;
id|depth
101|0
301|1
302|1
401|2
101|3
301|4
302|4

Во втором запросе повторились 101, 301 и 302: UNION сравнивает пару столбцов. Завершение обеспечил только предел depth. Если убрать его, строки с новыми глубинами продолжат появляться. Для прекращения конкретного циклического пути нужно отслеживать identity операции, например CYCLE id.
