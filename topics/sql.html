SQL: Queries

SQL описывает результат над строками, а база выбирает способ его получить. Чтобы понять запрос, проследи, какие строки прошли фильтр, какие попали в одну группу и какие колонки остались в результате. NULL означает отсутствие известного значения и меняет правила сравнения и подсчёта. Перед оптимизацией отчёта сначала проверь его смысл: быстрый запрос способен совершенно правильно посчитать не то, что требовалось.

Одна строка отчёта должна иметь понятную единицу подсчёта

Платёжный сервис строит отчёт для магазинов. Нужны число оплаченных платежей и их сумма; показываем магазины, у которых сумма не меньше 200 минимальных денежных единиц. На входе есть два разных платежа по 100. Есть незавершённые платежи и старая запись с неизвестной суммой. По отдельности все данные читаются легко. Ошибка возникает, когда запрос незаметно меняет, что именно он считает.

У исходной таблицы единица — платёж, его отличает id. У отчёта единица — магазин. После группировки в строке уже нельзя без объяснения показать один id: платежей у магазина несколько. После выбора только суммы нельзя отличить два платежа по 100. Эта смена единицы результата объясняет и правила GROUP BY, и опасность DISTINCT.

Все опыты выполнены на PostgreSQL 17.11. Полный файл Queries.sql создаёт временную таблицу и эти семь строк. amount_minor и fee_minor — целые минимальные денежные единицы; в данном наборе одна валюта. NULL оставлен намеренно, чтобы увидеть поведение старых неполных данных. Для нового подтверждённого платежа доменная модель должна требовать известную сумму и валюту.

CREATE TEMP TABLE payments (
    id integer PRIMARY KEY,
    merchant text,
    status text,
    amount_minor bigint,
    fee_minor bigint,
    created_at timestamp NOT NULL
);

Разделитель колонок в выводах — |, заголовки и служебные сообщения выключены. Запуск создаёт собственный контейнер без опубликованных портов и удаляет его после завершения:

Перед написанием запроса полезно ответить на три вопроса. Что означает одна входная строка? Что означает одна выходная строка? Что делать с отсутствующим значением: пропустить, показать отдельно или отклонить данные? Если эти ответы меняются по ходу запроса, это должно быть видно в его стадиях.

WHERE выбирает строки, GROUP BY собирает группы, HAVING выбирает группы

SELECT пишется первым, но смысл запроса удобно читать от источника. FROM задаёт входные строки. WHERE оставляет строки с истинным условием. GROUP BY собирает строки по ключу, агрегаты считают значения внутри каждой группы. HAVING отбирает уже готовые группы. SELECT формирует выходные колонки, DISTINCT удаляет повторяющиеся выходные строки, ORDER BY задаёт порядок, LIMIT ограничивает число строк.

Это логическая модель, а не расписание физического выполнения. Оптимизатор способен раньше применить безопасный фильтр, выбрать индекс вместо чтения всей таблицы или объединить операции. Но результат должен сохранять смысл запроса. В частности, нельзя перенести условие суммы группы в фильтр отдельных платежей и ждать прежний ответ.

SELECT merchant,
       count(*) AS paid_count,
       sum(amount_minor) AS total_minor
FROM payments
WHERE status = 'paid'              -- Сначала только оплаченные платежи.
GROUP BY merchant                 -- Теперь одна группа на магазин.
HAVING sum(amount_minor) >= 200    -- Порог для суммы группы, не для платежа.
ORDER BY total_minor DESC,
         merchant ASC NULLS LAST; -- При одинаковой сумме порядок явный.
A|2|200
B|1|200

Почему псевдоним результата не виден в WHERE

AS doubled называет выходную колонку SELECT. PostgreSQL разрешает использовать такое имя в ORDER BY и GROUP BY, но не в WHERE или HAVING. В этих местах укажи исходное выражение либо выдели вычисление во вложенный запрос. В GROUP BY неоднозначное имя PostgreSQL трактует как входную колонку, в ORDER BY — как выходную; одинаковые имена лучше не создавать.

-- doubled существует как имя результата, но не как колонка payments.
SELECT amount_minor * 2 AS doubled
FROM payments WHERE doubled > 200;

-- Группа merchant содержит несколько id: какой из них вернуть?
SELECT merchant, id, sum(amount_minor)
FROM payments GROUP BY merchant;

В полном демо эти два ошибочных запроса выполняет обвязка pg_temp.query_state. Она перехватывает ожидаемую ошибку и печатает SQLSTATE, поэтому остальные опыты продолжаются. Ниже показаны именно строки этой обвязки, а не текст диагностического сообщения psql.

alias in WHERE|42703
ungrouped id|42803

Первый код — undefined_column, второй — grouping_error. Агрегат тоже нельзя поставить в WHERE: в этой логической точке группы ещё не образованы. Для фильтра суммы есть HAVING. Исключение из требования перечислять все неагрегированные колонки — доказанная функциональная зависимость: PostgreSQL узнаёт её, когда GROUP BY включает первичный ключ соответствующей таблицы. Это не разрешение выбирать случайную строку группы.

База обязана сначала выполнить FROM, потом WHERE и только потом SELECT именно в таком порядке.

Этот порядок объясняет смысл и доступность данных. Реальные узлы, перестановки и способы доступа смотри в Query Plans. Логическое правило не требует создавать промежуточную таблицу на каждом шаге.

NULL добавляет UNKNOWN, а фильтр оставляет только TRUE

NULL — маркер отсутствующего значения. Это не ноль, не пустая строка и не ещё один статус. Если неизвестно значение статуса, сравнение status = 'paid' тоже неизвестно. Обычные сравнения с NULL дают логическое UNKNOWN; PostgreSQL представляет этот результат как NULL типа boolean. Поэтому NULL = NULL не даёт TRUE.

WHERE и HAVING пропускают только TRUE. FALSE и UNKNOWN одинаково не проходят, но остаются разными результатами. Отрицание UNKNOWN снова UNKNOWN: условие «не paid» не превращает неизвестный статус в подходящий. Для самого маркера отсутствия есть IS NULL и IS NOT NULL; для сравнения с учётом отсутствия — IS DISTINCT FROM и его отрицание.

SELECT NULL::bigint = NULL::bigint AS eq_null,
       NULL::text <> 'paid' AS not_paid,
       NOT (NULL::text = 'paid') AS negated,
       TRUE OR NULL::boolean AS true_or_unknown,
       FALSE AND NULL::boolean AS false_and_unknown;
NULL|NULL|NULL|t|f

t и f — формат TRUE и FALSE у psql. UNKNOWN не всегда делает всё выражение неизвестным: TRUE уже достаточно для OR, FALSE — для AND. Остальные комбинации можно восстановить по правилу: если неизвестный операнд способен изменить итог, итог неизвестен.

aba AND ba OR b
TRUEUNKNOWNUNKNOWNTRUE
FALSEUNKNOWNFALSEUNKNOWN
UNKNOWNUNKNOWNUNKNOWNUNKNOWN

Попросим список платежей, которые не оплачены. Здесь нужны две разные формулировки: «известно, что статус другой» и «статус отличается от paid, включая отсутствие». Они возвращают разные id:

SELECT 'status <> paid', string_agg(id::text, ',' ORDER BY id)
FROM payments WHERE status <> 'paid';
SELECT 'status DISTINCT FROM paid', string_agg(id::text, ',' ORDER BY id)
FROM payments WHERE status IS DISTINCT FROM 'paid';
SELECT 'status IS NULL', string_agg(id::text, ',' ORDER BY id)
FROM payments WHERE status IS NULL;
status <> paid|3,5
status DISTINCT FROM paid|3,5,6
status IS NULL|6

IS DISTINCT FROM возвращает обычный boolean: два NULL для него не различаются, NULL и известное значение различаются. Это удобный способ обнаружить изменение nullable-поля без сложного набора OR. Он не назначает NULL бизнес-смысл: в отчёте «не оплачено» неизвестный статус иногда надо показать отдельной категорией, а не смешать с pending.

Подстановка значения меняет смысл данных

COALESCE(x, 0) выбирает первое не-NULL значение. Для известного отсутствия комиссии это может быть правильный ноль. Для неизвестной суммы платежа это финансовая ложь. Различай отсутствие строки, отсутствующее поле и известное нулевое значение. Не подставляй ноль только ради удобства Java-примитива или красивого отчёта.

В SQL нельзя использовать AND как обещание порядка вызовов. Условие x <> 0 AND 100 / x > 2 не является общим способом защитить деление: оптимизатор вправе перестроить выражение. Для такого вычисления вырази допустимую операцию, например 100.0 / NULLIF(x, 0). NULLIF превращает запрещённый делитель в NULL, а дальнейший фильтр решает, что делать с отсутствующим результатом.

Почему CHECK и WHERE по-разному относятся к UNKNOWN

WHERE выбирает только TRUE, а CHECK отклоняет FALSE и допускает TRUE или UNKNOWN. Поэтому CHECK (amount_minor > 0) не запрещает NULL. Если значение обязательно, нужен также NOT NULL. Одинаковое условие в фильтре и ограничении выполняет разные задачи; переносить интуицию из Java boolean без проверки нельзя.

Если условие и его отрицание объединить OR, любая строка пройдёт.

Для UNKNOWN выражение p OR NOT p остаётся UNKNOWN. Например, status = 'paid' OR status <> 'paid' исключит строку 6. Полноту категорий нужно обеспечить отдельным случаем IS NULL.

COUNT строк и COUNT известных значений отвечают на разные вопросы

GROUP BY собирает строки с одинаковым ключом. Для группировки несколько NULL в одном ключе попадают в одну группу: это правило групп, а не результат обычного сравнения NULL = NULL. Затем каждый агрегат получает набор входных значений своей группы. COUNT(*) считает строки, COUNT(amount_minor) — только строки с известной суммой, SUM и AVG пропускают NULL-значения.

Поэтому у оплаченного платежа 7 число строк равно одному, число известных сумм — нулю, а сумма и среднее неизвестны. Статус paid не создаёт отсутствующее значение суммы. Для сверки качества данных полезно вывести оба счётчика: их разница покажет оплаченные записи, которые требуют разбора.

SELECT merchant,
       count(*) AS rows,
       count(amount_minor) AS known_amounts, -- Не считает NULL.
       sum(amount_minor) AS total_minor,
       round(avg(amount_minor), 2) AS average_minor
FROM payments WHERE status = 'paid'
GROUP BY merchant
ORDER BY merchant ASC NULLS LAST;
A|2|2|200|100.00
B|1|1|200|200.00
NULL|1|0|NULL|NULL

Пустой набор не всегда даёт пустой результат

Агрегаты без GROUP BY считают весь отфильтрованный набор как одну общую группу. Даже если строк не осталось, обычный агрегатный запрос без HAVING вернёт одну строку: COUNT — 0, SUM — NULL. С GROUP BY на пустом наборе не возникнет ни одной группы, и выходных строк не будет. Для клиента это разница между «получили запись с неизвестной суммой» и «записей нет».

SELECT count(*) AS rows,
       count(amount_minor) AS known_amounts,
       sum(amount_minor) AS total_minor,
       coalesce(sum(amount_minor), 0) AS chosen_zero -- Явная политика для пустого набора.
FROM payments WHERE status = 'missing';
0|0|NULL|0

AVG делит сумму на число известных значений, а не на COUNT(*). Если заменить его на SUM(x) / COUNT(*), NULL-строки изменят знаменатель. Ещё проверь типы: деление целых обрезает дробную часть; PostgreSQL AVG для целочисленного входа возвращает numeric. ROUND в опыте сокращает печать до двух десятичных знаков, но не меняет число участников среднего.

Один набор строк можно считать по нескольким условиям

WHERE действует на весь запрос, FILTER — на вход конкретного агрегата. Если поставить paid в WHERE, потеряем pending и refunded из общего числа платежей. Если поставить его в FILTER у COUNT и SUM, сохраним все строки группы и посчитаем оплаченные отдельно.

SELECT merchant, count(*) AS all_count,
       count(*) FILTER (WHERE status = 'paid') AS paid_count,
       sum(amount_minor) FILTER (WHERE status = 'paid') AS paid_total
FROM payments
GROUP BY merchant
ORDER BY merchant ASC NULLS LAST;
A|3|2|200
B|3|1|200
NULL|1|1|NULL

Это полезно для отчёта по нескольким статусам за один и тот же период. Общие ограничения периода и магазина оставляй в WHERE, условия отдельных метрик — в FILTER. CASE внутри SUM тоже возможен, но важно выбрать ELSE: ноль и NULL создают разную семантику для других агрегатов. А для упорядоченных агрегатов вроде STRING_AGG порядок задавай внутри самого агрегата, как в опыте со статусами; внешнее ORDER BY сортирует готовые группы.

Сумма всех известных оплаченных значений в демо равна 400. Полная сумма оплат неизвестна: у платежа 7 нет суммы. SUM не выдаёт ошибку и не отмечает неполноту, поэтому финансовый отчёт должен отдельно проверять число неизвестных сумм. Иначе технически правильный итог выглядит как подтверждённая полная выручка.

Что группировка требует от памяти и почему HAVING не ускоряет вход само по себе

PostgreSQL может построить хеш-таблицу групп или использовать отсортированный поток. Количество групп, ширина данных и доступная рабочая память влияют на объём состояния и запись на диск. HAVING по SUM отбрасывает группу после получения её агрегата; он не позволяет пропустить часть платежей этой группы. Фильтр по самому ключу иногда можно перенести раньше без изменения смысла. Конкретное преобразование проверяют по EXPLAIN, а не по месту слова в запросе.

DISTINCT удаляет одинаковые результаты, а не повторные бизнес-события

Обычный SELECT сохраняет повторяющиеся строки результата. SQL часто называют работой с множествами, но по умолчанию здесь важна кратность: два платежа по 100 должны участвовать в сумме дважды. SELECT DISTINCT удаляет повторы по всем выбранным выражениям. DISTINCT merchant и DISTINCT merchant, amount_minor — разные вопросы к тем же данным.

SUM(DISTINCT amount_minor) сначала оставляет уникальные известные значения сумм, затем складывает их. У оплаченных платежей суммы 100, 100, 200 и NULL. Обычная SUM даёт 400; SUM(DISTINCT) — 300. Два независимых платежа магазина A не становятся одним событием только потому, что их суммы совпали.

SELECT count(*) AS paid_rows,
       sum(amount_minor) AS paid_total,
       sum(DISTINCT amount_minor) AS distinct_amount_total -- Уникальны суммы, не id.
FROM payments WHERE status = 'paid';
4|400|300

У DISTINCT несколько NULL в одной позиции считаются повторами, хотя обычное сравнение двух NULL неизвестно. А COUNT(DISTINCT merchant) сначала исключает NULL, затем считает уникальные известные магазины. Поэтому список DISTINCT merchant содержит три строки, а COUNT(DISTINCT merchant) равен двум:

SELECT DISTINCT merchant
FROM payments WHERE status = 'paid'
ORDER BY merchant ASC NULLS LAST;
SELECT count(DISTINCT merchant) AS known_merchants
FROM payments WHERE status = 'paid';
A
B
NULL
2

Один представитель группы требует правила выбора

Иногда нужен не список уникальных значений, а последний оплаченный платёж каждого магазина. PostgreSQL DISTINCT ON оставляет первую строку каждой группы по указанным выражениям. Чтобы «первая» значила «последняя по времени», нужен согласованный ORDER BY: ключ DISTINCT ON идёт в начале, затем время по убыванию и id для разрешения равного времени.

SELECT DISTINCT ON (merchant) merchant, id, status
FROM payments WHERE status = 'paid' -- Последний среди оплаченных, не вообще последний.
ORDER BY merchant ASC NULLS LAST,
         created_at DESC, id DESC;  -- Равное время разрешаем однозначно.
A|2|paid
B|4|paid
NULL|7|paid

У A вообще последний платёж — 3, но последний оплаченный — 2. У B эти строки — 6 и 4. Если сначала выбрать последний платёж любого статуса, а потом оставить paid, оба магазина исчезнут. Порядок смысловых операций меняет результат. DISTINCT ON — расширение PostgreSQL; переносимый вариант с ROW_NUMBER разобран в Window Functions.

После JOIN сумма завышена — достаточно добавить DISTINCT.

Сначала выясни, почему одна строка платежа дала несколько строк соединения. DISTINCT суммы выбросит независимые платежи с одинаковыми значениями. Нужен правильный уровень соединения или предварительная агрегация; это разобрано в Joins.

Порядок и границы результата нужно задавать явно

Без ORDER BY база не обещает порядок строк. Вчера они шли по id, сегодня новый индекс, параллельный план или изменение объёма данных дадут другой порядок. GROUP BY и DISTINCT тоже не являются обещанием сортировки. Если клиент видит «первые три платежа», запрос должен определить, по какому признаку они первые.

Одного неуникального признака мало. При одинаковой сумме два платежа по 100 не упорядочены относительно друг друга. Добавление id делает порядок полным для этого набора строк. LIMIT выбирает часть уже упорядоченного результата; это особенно важно для пагинации, повторяемых отчётов и выбора одной строки группы.

SELECT id, amount_minor FROM payments WHERE status = 'paid'
ORDER BY amount_minor DESC NULLS LAST, id ASC LIMIT 3;

-- В PostgreSQL DESC по умолчанию ставит NULL первым.
SELECT id, amount_minor FROM payments WHERE status = 'paid'
ORDER BY amount_minor DESC, id ASC LIMIT 1;
4|200
1|100
2|100
7|NULL

Последняя строка — результат второго запроса. Неизвестная сумма оказалась «самой большой» только из-за политики расположения NULL. Для ASC в PostgreSQL по умолчанию NULLS LAST, для DESC — NULLS FIRST. Укажи нужную политику явно, если «первые» значения имеют бизнес-смысл. Сама SUM пропускает NULL, а сортировка обязана куда-то поставить строку с ним: это разные операции.

Правильный ответ и хороший план проверяют отдельно

Для запроса с миллионами строк потребуются индексы, оценка числа групп, память для сортировки и проверка плана. Но LIMIT не означает, что база прочтёт только столько строк: для суммы всех платежей сначала надо получить вход агрегатов. DISTINCT тоже требует доказать уникальность или удалить повторы; большой список результатов не становится бесплатным от одного слова.

Сначала проверяй смысл на маленьком наборе: два платежа по одной сумме, NULL, пустой результат, равные ключи сортировки. Затем смотри EXPLAIN ANALYZE на реальном распределении данных. Отдельно сравни ожидаемое и фактическое число строк после JOIN и группировки. Ускорение не должно менять единицу подсчёта, значение отсутствия или порядок выбора.

Для пользовательского ввода используй параметры запроса. Значение магазина передают как значение, а не вклеивают в текст SQL. Имена колонок и направления ORDER BY параметром значения не заменить: для них нужен разрешённый набор вариантов. Работа JDBC и PreparedStatement — в JDBC & Connection Pools, физические планы — в Query Plans.

Полный порядок не сохраняет один снимок данных между отдельными запросами страниц. Пока клиент листает OFFSET-пагинацию, новые записи и изменения ключей могут сдвинуть строки. Курсор и уровень изоляции решают другие части этой задачи; продолжение — в Slow Queries и ACID & Isolation. Соединения, вложенные запросы и окна изучаются отдельно: они добавляют новые способы формировать вход, но не отменяют правила NULL, кратности и группировки.

  • Проследи единицу строки: платёж, группа магазина или выбранные значения. Смена этой единицы меняет правила подсчёта.
  • WHERE фильтрует строки, HAVING — группы. Логические стадии объясняют смысл, а физический порядок выбирает оптимизатор.
  • Обычные сравнения с NULL дают UNKNOWN. WHERE оставляет только TRUE; отрицание не превращает UNKNOWN в TRUE.
  • COUNT(*) считает строки, COUNT(поле) — известные значения. Без GROUP BY пустой вход всё ещё даёт строку агрегатов.
  • DISTINCT удаляет повторы выбранных значений. Два платежа по одной сумме остаются двумя бизнес-событиями.
  • ORDER BY должен разрешать равенство ключей и явно размещать NULL. LIMIT без определённого порядка не выбирает определённые строки.

На собеседовании

В каком порядке работает SELECT и чем WHERE отличается от HAVING?

Я читаю смысл запроса от FROM: получаю строки, фильтрую их WHERE, собираю группы и считаю агрегаты, затем отбираю группы HAVING. SELECT задаёт выходные колонки, DISTINCT удаляет повторы, ORDER BY и LIMIT задают порядок и часть результата. Это логическая последовательность, а не обязательный физический план.

В отчёте по оплатам WHERE оставляет paid, а HAVING выбирает магазины с общей суммой от 200. Если заменить этот порог на WHERE amount_minor ≥ 200, магазин с двумя платежами по 100 исчезнет. Псевдоним суммы из SELECT в PostgreSQL доступен ORDER BY, но в HAVING я пишу агрегат или использую внешний запрос.

  • Фильтр по ключу группы иногда можно перенести до группировки, фильтр по SUM — не просто фильтр платежей. Возможность переноса определяется сохранением смысла, а не общим правилом «WHERE быстрее».
  • Нельзя выбрать произвольный id из группы merchant. Исключение PostgreSQL с первичным ключом основано на функциональной зависимости, а не на выборе случайного представителя.
  • Оптимизатор может переупорядочивать условия. AND не является контрактом короткого замыкания для опасной операции; выражаю безопасное деление через NULLIF.

Почему сравнение с NULL не работает как сравнение с обычным значением?

NULL означает неизвестное или отсутствующее значение. Обычное сравнение с ним даёт UNKNOWN, в том числе NULL = NULL. WHERE принимает только TRUE, поэтому и равенство paid, и его отрицание исключат строку с неизвестным статусом. Для отсутствия использую IS NULL, а для сравнения двух nullable-значений — IS DISTINCT FROM.

В платёжном отчёте я не превращаю неизвестную сумму в ноль без бизнес-правила. COALESCE полезен для выбранной политики, но он не восстанавливает отсутствующие данные. Отдельная категория неизвестных записей часто честнее, чем красивый общий итог.

  • TRUE OR UNKNOWN даёт TRUE, FALSE AND UNKNOWN — FALSE. Поэтому наличие nullable-поля не делает автоматически неизвестным любой составной предикат.
  • GROUP BY и DISTINCT объединяют одинаковые NULL-позиции, хотя обычное равенство двух NULL неизвестно. Нельзя выводить правила всех операций из одного оператора =.
  • CHECK допускает UNKNOWN, WHERE его исключает. Ограничение суммы через CHECK(amount > 0) требует отдельного NOT NULL, если сумма обязательна.
Все статусы попали в отчёт по этому условию? 
WHERE status = 'paid' OR status <> 'paid'

Нет: неизвестный статус даст UNKNOWN OR UNKNOWN. Если нужны все строки, условие вообще не требуется. Если надо явно описать категории, добавь IS NULL и реши, к какой категории относятся такие платежи. Простое отрицание первого условия не закрывает отсутствие значения.

Чем COUNT(*), COUNT(поле) и SUM отличаются на NULL и пустом наборе?

COUNT(*) считает входные строки, COUNT(поле) — известные значения поля. SUM и AVG пропускают NULL. Поэтому один paid-платёж с неизвестной суммой даёт count строк 1, count сумм 0, sum NULL. AVG делит на число известных значений, а не на число всех строк.

Без GROUP BY агрегатный запрос на пустом входе возвращает одну строку: count 0, sum NULL. С GROUP BY групп нет и строк результата тоже нет. Если контракт требует ноль для пустой суммы, выбираю COALESCE явно и отдельно проверяю неполные платежи.

  • FILTER меняет вход конкретного агрегата. WHERE paid удалит pending из всех метрик, а COUNT(*) FILTER(WHERE paid) сохранит общий count рядом.
  • Тип результата важен: SUM(integer) в PostgreSQL возвращает bigint, SUM(bigint) — numeric. AVG целого возвращает numeric, а самостоятельно написанное целочисленное деление может обрезать дробь.
  • COUNT(*) требует посчитать видимые строки конкретного снимка; «точный размер таблицы из метаданных» не заменяет его. Стоимость и выбранный доступ проверяю планом.

Что удаляет DISTINCT и почему SUM(DISTINCT) не чинит задвоенную сумму?

DISTINCT сравнивает выбранные выражения, а не идентичность сущности. Если выбрать только сумму, два платежа по 100 станут одним значением 100. SUM(DISTINCT amount) поэтому считает сумму разных сумм, а не сумму разных платежей. Для бизнес-дедупликации нужен ключ события или платежа.

Если после JOIN отчёт удвоился, сначала проверяю кратность соединения. Возможно, платёж соединился с двумя попытками. Исправляю вход агрегации, а не удаляю одинаковые денежные значения. Когда нужен один представитель группы, задаю правило выбора: в PostgreSQL DISTINCT ON с ORDER BY, либо окно ROW_NUMBER.

  • COUNT(DISTINCT merchant) исключает NULL; SELECT DISTINCT merchant сохраняет одну NULL-строку. Эти результаты отвечают на разные вопросы.
  • В DISTINCT ON фильтр перед выбором определяет набор кандидатов. «Последний paid» и «последний вообще, если paid» — разные отчёты.
  • Ширина выбранной строки и число входных строк влияют на стоимость удаления повторов. DISTINCT в конце способен скрыть ошибку кратности и добавить дорогую сортировку или хеширование.

Достаточно ли ORDER BY created_at и LIMIT для стабильной страницы?

Если время повторяется, относительный порядок этих строк не задан. Я добавляю уникальный ключ, например id, и явно решаю, где стоят NULL. Без ORDER BY вообще нельзя обещать, какие строки выберет LIMIT: порядок чтения таблицы не часть контракта.

Даже полный порядок решает только порядок внутри результата. Между запросами страниц данные могут измениться и сдвинуть OFFSET. Для стабильного обхода выбираю подходящий курсор, а для единого снимка — отдельно продумываю транзакцию и изоляцию.

  • В PostgreSQL DESC по умолчанию даёт NULLS FIRST. Неполный платёж способен попасть на вершину рейтинга сумм; для такого контракта пишу NULLS LAST.
  • LIMIT после агрегатов не обещает малое число прочитанных строк. База ещё должна получить данные для группировки и сравнения итоговых сумм.
  • Курсор по изменяемому ключу сортировки тоже требует политики: изменение суммы или времени может перенести запись относительно уже выданной границы.
  • PostgreSQL 17: Table Expressions, §§7.2.2–7.2.3 — основа порядка объяснения: фильтр строк, группы и HAVING; логическую модель в уроке отличаем от физического плана.
  • SELECT — доступность псевдонимов, функциональная зависимость, DISTINCT ON, ORDER BY, NULLS FIRST/LAST и LIMIT.
  • Comparison Functions — UNKNOWN, IS NULL и IS DISTINCT FROM; Constraints, §5.5.1 — почему CHECK допускает UNKNOWN.
  • Aggregate Functions — пустой вход, типы SUM/AVG, COUNT и порядок внутри агрегата. SQLSTATE — коды ожидаемых ошибок демо.
