Stream Practice

Сначала назови форму результата: список id, карта сумм или карта списков. Затем реши, что считается одним элементом, как обращаться с повтором и какой порядок нужен. Только после этого выбирай операции Stream. В задачах ниже одни и те же платежи дают разные отчёты, и именно контракт определяет правильную цепочку.

Работающий pipeline ещё не означает правильный отчёт

Сервис получил пачку платежей и должен показать оборот клиента. Два платежа по 100 выглядят одинаково, пока не выяснится, что один в рублях, другой в долларах. mapToLong(...).sum() успешно вернёт 200, но это число нельзя подписать никакой валютой. Технически корректная цепочка может нарушать смысл результата.

На live coding сначала задай вопросы, которые меняют алгоритм. Нужны только оплаченные события или последнее состояние каждого платежа? Одинаковый id — дубль доставки или новая версия? Нужно сохранять порядок входа, сортировать ключи или ранжировать значения? Для равной суммы нужен второй критерий, иначе порядок зависит от того, как обходится карта.

Дальше проговори тип результата. List<String> означает проекцию и выбор элементов. Map<String, Long> — классификацию с агрегатом. Map<String, Map<String, Long>> добавляет ещё один уровень классификации. Направление преобразования видно до того, как ты вспомнил имя коллектора.

КонтрактЧто проверитьТипичный приём
Уникальные оплаченные id в порядке появленияNEW до PAID того же id; повтор PAIDfilter → map → distinct → toList
Сумма отдельно по клиенту и валютеОдинаковые числа разных валютgroupingBy → groupingBy → summingLong

Во всех задачах списки, их элементы и поля не null. Суммы — неотрицательные целые minor units, без переполнения long. Это условия упражнения, которые позволяют сосредоточиться на преобразованиях. В реальном сервисе отдельно проверяют вход, денежную модель и предел суммы; округлению отведена тема BigDecimal & Money.

distinct удалит повторные платежи по id.

distinct сравнивает текущие элементы через equals. У record Payment с полями id и status разные статусы делают записи разными. Если нужен уникальный id, сначала проецируй на id; если нужно последнее состояние, используй слияние по версии.

Группа хранит тот агрегат, который нужен результату

Для отчёта по валюте не нужно сначала собирать все платежи в списки. Классификатор выбирает ключ, а downstream-коллектор накапливает значение именно этой группы. При summingLong это промежуточная сумма. Каждый оплаченный платёж увеличивает только сумму своей валюты; платежи другой валюты туда не попадают.

Пошаговая схема показывает состояние при последовательном обходе трёх оплаченных платежей. Она не означает, что JVM создаёт поток для каждой группы. У каждой группы свой накопитель; после обработки входа коллектор завершает накопление и формирует значения результата. Оба сравнения этого шага и пример с заказами запускаются одним файлом ShapeDemo.java.

// Фрагмент ShapeDemo.java; java examples/stream-practice/ShapeDemo.java
record Payment(String client, String currency, long minorUnits, boolean paid) {}
List<Payment> batch = List.of(new Payment("a", "RUB", 100, true),
        new Payment("a", "USD", 100, true), new Payment("a", "RUB", 250, true),
        new Payment("b", "RUB", 900, false));
Map<String, Long> totals = batch.stream().filter(Payment::paid)
        .collect(groupingBy(Payment::currency, TreeMap::new,
                summingLong(Payment::minorUnits))); // агрегат, а не список платежей
System.out.println(totals);
{RUB=350, USD=100}

TreeMap::new задаёт сортировку ключей. Это самостоятельная часть контракта, не свойство groupingBy без фабрики. Если нужен порядок первого появления, подходит LinkedHashMap; если порядок не нужен, не добавляй сортировку ради красивого вывода.

Фильтр до группировки и внутри группы отвечают на разные вопросы

// Тот же batch из ShapeDemo.java
Map<String, Long> before = batch.stream().filter(Payment::paid)
        .collect(groupingBy(Payment::client, TreeMap::new, counting()));
Map<String, Long> inside = batch.stream().collect(groupingBy(Payment::client,
        TreeMap::new, filtering(Payment::paid, counting()))); // группа b есть, PAID в ней нет
System.out.println(before);
System.out.println(inside);
{a=3}
{a=3, b=0}

Первый вариант отвечает «сколько оплаченных платежей у клиентов, для которых они есть». Во втором сначала известен клиент, и downstream отбрасывает неоплаченные события уже внутри его группы. Поэтому b остаётся с нулём. Нулевое значение и отсутствие ключа — разные ответы API; выясни, какой нужен потребителю отчёта.

Разворачивая вложенный список, сохрани владельца

Заказы содержат списки товаров. Если нужен один общий список, flatMap превращает поток заказов в поток товаров: ноль, один или несколько элементов вместо каждого заказа. Но после перехода к Stream<String> клиента уже нет в элементе. Следующий groupingBy не сможет восстановить потерянную связь.

Когда результат должен быть «клиент → товары», можно сохранить пару клиент–товар при разворачивании. Однако заказ без товаров не выдаст ни одной пары, и такой клиент исчезнет. Другой путь — классифицировать заказ по клиенту первым, а внутри группы использовать flatMapping. Тогда пустой список товаров даёт пустое значение существующей группы.

// Фрагмент ShapeDemo.java
record Order(String client, List<String> products) {}
List<Order> orders = List.of(new Order("a", List.of("tea", "milk")),
        new Order("b", List.of()));
System.out.println(orders.stream().flatMap(o -> o.products().stream()).toList());
Map<String, Set<String>> byClient = orders.stream().collect(
        groupingBy(Order::client, TreeMap::new,
                flatMapping(o -> o.products().stream(), toCollection(TreeSet::new))));
System.out.println(byClient);
[tea, milk]
{a=[milk, tea], b=[]}

Тип downstream подсказывает, где удалить дубли: TreeSet собирает уникальные названия в каждой группе и одновременно сортирует их. Глобальный distinct перед группировкой удалял бы данные между клиентами, если элементом было бы только название товара. Нужна уникальность пары либо отдельное множество у каждого клиента.

Порядок операций определяет и ответ, и стоимость

Для топа клиентов сначала посчитай оборот каждого клиента, затем сортируй записи карты по обороту и только потом делай limit(k). Если сначала выбрать k крупнейших платежей, клиент с множеством небольших платежей не попадёт в кандидаты. Это другой вопрос, даже если названия операций совпадают.

У ранжирования два порядка: сумма по убыванию и id или имя по возрастанию при равенстве. comparingLong(...).reversed().thenComparing(...) разворачивает только первый критерий. Если поставить reversed() после thenComparing, развернутся оба. Вычитание сумм в компараторе тоже не подходит: разность может переполниться и нарушить порядок.

Оценка сложности должна учитывать контейнер и накопитель. Хеш-группировка с суммой обычно делает O(n) работы и хранит O(g) агрегатов для g ключей. Сортировка g агрегатов добавляет O(g log g). Используемый в задачах TreeMap делает поиск группы за O(log g). Если downstream — список всех платежей, память уже O(n), даже если финальный результат содержит только k элементов.

Топ внутри каждой группы через collectingAndThen(toList(), ...) прост для объяснения: собрать группу, отсортировать, взять первые k. Его цена — O(Σ nᵢ log nᵢ) времени для сортировок и O(n) памяти. Для больших групп и малого k можно держать ограниченный heap размера k: каждый кандидат сравнивается с худшим сохранённым, затем итог сортируется. У такого решения больше кода и нужно корректно сливать частичные heap; паттерн разобран в Top K.

Не добавляй найденные элементы через forEach во внешний ArrayList. При parallelStream несколько потоков начнут менять один список. collect с подходящим коллектором задаёт правила накопления и слияния; mutable reduce с одним общим identity их не заменяет. Полные контракты — в Collectors, условия полезного параллелизма — в Parallel Streams.

Если миллионы платежей уже лежат в БД, выгрузка всех строк ради in-memory группировки увеличит трафик и heap. Обсуди SQL-агрегат и пагинацию результата. На интервью сначала представь простое проверяемое решение, затем объясни, какое ограничение заставит его поменять. Усложнение оправдывает размер данных, а не желание показать больше методов Stream.

  • До pipeline договорись о форме результата, дублях, пустом входе и порядке.
  • Группируй по всем измерениям, которые нельзя складывать: валюты остаются разными суммами.
  • Downstream накапливает результат группы; filtering и flatMapping сохраняют её даже с пустым значением.
  • Топ агрегатов начинается с агрегации. Для ничьей нужен явный второй критерий.
  • limit после sorted сокращает результат, но не память, нужную сортировке всей группы.

Задачи

Уникальные id оплаченных платежей

Верни id событий со статусом PAID, без повторов, в порядке первого появления среди оплаченных событий. Статус NEW того же id до PAID не мешает включить этот id позже. Результат — неизменяемый список; вход — упорядоченный List.

[p2 NEW, p1 PAID, p2 PAID, p1 PAID] → [p1, p2]

Авторская backend-задача · JDK 21 · без зависимостей

Заготовка: PaidIds.java; запуск java PaidIds.java 
import java.util.*;

public class PaidIds {
    record Payment(String id, String status) {}

    }

    public static void main(String[] args) {
        check(paidIds(List.of(new Payment("p2", "NEW"), new Payment("p1", "PAID"),

        check(paidIds(List.of()), List.of());
        check(paidIds(List.of(new Payment("x", "FAILED"))), List.of());
        check(paidIds(List.of(new Payment("z", "PAID"), new Payment("a", "PAID"))), List.of("z", "a"));
    }

        if (!Objects.equals(got, want)) throw new AssertionError("got " + got + ", want " + want);
        System.out.println("OK " + got);

}
Подсказка 1

Сначала реши, по какому типу должно работать равенство: по Payment или по String.

Подсказка 2

Отфильтруй PAID, получи id через map, затем distinct. Не сортируй: порядок задан входом.

Решение

У filter на выходе всё ещё Payment. После map равенство сравнивает только id, поэтому distinct удаляет повторные оплаченные id. Упорядоченный поток сохраняет первый из равных элементов. Пустой вход даёт пустой список без отдельной ветки.

    static List<String> paidIds(List<Payment> payments) {
        return payments.stream()
                .filter(p -> p.status().equals("PAID")) // сначала отбираем события
                .map(Payment::id)                       // равенство теперь по id
                .distinct()                            // первый id в encounter order
                .toList();                             // неизменяемый список
    }

Ожидаемое время O(n), память O(u) для u уникальных оплаченных id и результата. toList возвращает неизменяемый список, поэтому не обещай вызывающему возможность add.

Подставь метод в заготовку. Полный проверенный файл: PaidIds.java.

OK [p1, p2]
OK []
OK []
OK [z, a]
Почему нельзя сначала distinct по всем событиям?

У record с полями id и status равенство учитывает оба поля; это не уникальность по id. Если же вручную убрать повтор id до фильтра, событие NEW p2 может вытеснить PAID p2. Условия удаления дублей определяются смыслом отчёта, а не удобством перестановки операторов.

Оборот клиента отдельно в каждой валюте

Верни карту client → currency → сумма minorUnits, учитывая только paid=true. Клиент без оплаченных платежей отсутствует; нулевая оплаченная сумма создаёт группу. Оба уровня ключей должны быть по алфавиту. Суммы каждой группы помещаются в long.

a: [100 RUB paid, 100 USD paid, 250 RUB paid]
b: [900 RUB unpaid]
→ {a={RUB=350, USD=100}}

Подсказка 1

Прочитай тип результата справа налево: сумма, сумма по валюте, валюты по клиенту.

Подсказка 2

Внешний groupingBy выбирает клиента. Его downstream — ещё groupingBy по валюте; самым внутренним будет summingLong.

Решение

filter убирает неоплаченные события до появления групп. Внешний классификатор выбирает клиента, внутренний — валюту; summingLong увеличивает только соответствующий накопитель. TreeMap задаёт порядок обоих наборов ключей. Проверка на четыре миллиарда ловит случайный выбор int.

    static Map<String, Map<String, Long>> totals(List<Payment> payments) {
        return payments.stream().filter(Payment::paid)
                .collect(groupingBy(Payment::client, TreeMap::new,
                        groupingBy(Payment::currency, TreeMap::new,
                                summingLong(Payment::minorUnits)))); // сумма отдельно в каждой валюте
    }

O(n(log c + log v)) времени, где c — число клиентов, v — максимальное число валют клиента. Память O(g) для g пар клиент–валюта. С HashMap ожидаемое накопление O(n), но порядок вывода пришлось бы обеспечивать отдельно.

Подставь метод в заготовку. Полный проверенный файл: Totals.java.

OK {}
OK {}
OK {b={EUR=0}}
OK {x={RUB=4000000000}}
Какая перестановка оставит клиента b в результате?

Если внешний groupingBy идёт до отбора paid, а filtering находится внутри его downstream, ключ b уже будет создан. В зависимости от расположения второго groupingBy получишь пустую карту валют либо валюту RUB с нулевой суммой. Прежде чем менять цепочку, назови нужную форму пустого значения.

Последняя версия события для каждого платежа

Поступил упорядоченный список Event(id, version, status). Верни по одному событию на id с максимальной version. При одинаковой version выбирай событие, стоящее позже во входном списке. Ключи результата сортируются по алфавиту. Версия задаёт порядок состояний; позиция во входе используется только для ничьей.

[p1 v2 PAID, p1 v1 NEW, p2 v1 FAILED]
→ {p1=v2 PAID, p2=v1 FAILED}

import static java.util.stream.Collectors.*;

public class Latest {
    record Event(String id, long version, String status) {}

    static Map<String, Event> latest(List<Event> events) {
        // твоё решение
        return Map.of();
    }

    public static void main(String[] args) {
        Event paid = new Event("p1", 2, "PAID"), failed = new Event("p2", 1, "FAILED");
        check(latest(List.of(paid, new Event("p1", 1, "NEW"), failed)), Map.of("p1", paid, "p2", failed));
        check(latest(List.of()), Map.of());
        Event replacement = new Event("p1", 2, "REFUNDED");
        check(latest(List.of(paid, replacement)), Map.of("p1", replacement));
        check(latest(List.of(replacement, paid)), Map.of("p1", paid));
        check(latest(List.of(paid, paid)), Map.of("p1", paid));
    }

    static void check(Object got, Object want) {
        if (!Objects.equals(got, want)) throw new AssertionError("got " + got + ", want " + want);
        System.out.println("OK " + got);
    }
}
Подсказка 1

groupingBy с последующим поиском максимума возможен, но хранение списка событий не нужно.

Подсказка 2

Используй toMap с id как ключом и Event как значением. Merge-функция выбирает большую версию; на равенстве — правый аргумент.

Решение

Два аргумента merge — уже выбранное событие и очередной кандидат для этого id. Выбор максимальной версии не даёт старой поздней доставке откатить состояние. На равенстве выбор правого аргумента реализует оговорённый порядок входа. Это свёртка группы без хранения всех её элементов.

    static Map<String, Event> latest(List<Event> events) {
        return events.stream().collect(toMap(Event::id, Function.identity(),
                (a, b) -> a.version() > b.version() ? a : b, // равная версия: позже во входном списке
                TreeMap::new));                              // ключи по алфавиту, не по версии
    }

O(n log u) времени с TreeMap, O(u) памяти для u уникальных id. При хеш-карте ожидаемое время O(n). В отличие от distinct, правило выбирает содержимое победившего события.

Подставь метод в заготовку. Полный проверенный файл: Latest.java.

OK {p1=Event[id=p1, version=2, status=PAID], p2=Event[id=p2, version=1, status=FAILED]}
OK {}
OK {p1=Event[id=p1, version=2, status=REFUNDED]}
OK {p1=Event[id=p1, version=2, status=PAID]}
OK {p1=Event[id=p1, version=2, status=PAID]}
Подходит ли эта merge-функция для параллельной свёртки?

Она ассоциативна: для последовательности выбирается правый из элементов максимальной версии независимо от расстановки скобок. Но она не коммутативна на равных версиях. Нужен сохранённый encounter order; unordered источник или concurrent unordered collector меняют смысл «позже». В распределённой обработке порядок доставки не задаёт глобальный tie-break: нужен отдельный идентификатор или правило конфликта.

Топ клиентов по обороту одной валюты

Верни до k имён клиентов по сумме платежей заданной currency: сумма по убыванию, имя по возрастанию при ничьей. k=0 даёт пустой список; k<0 — IllegalArgumentException, даже при пустом входе. Все входные платежи уже оплачены. Не смешивай валюты; суммы помещаются в long.

currency=RUB, k=2 → [a, z]

Подсказка 1

Топ платежей и топ клиентов — разные результаты. У клиента a два платежа.

Подсказка 2

После отбора валюты собери Map client → sum. Новая цепочка по entrySet сортирует по value.reversed, затем key, и делает limit.

Решение

Выделенный Map фиксирует переход от платежа к клиентскому агрегату. Сортировка входных платежей до группировки этого перехода не делает. Второй критерий гарантирует воспроизводимый результат при равных оборотах, независимо от порядка обхода хеш-карты. Вызов limit до sorted выбрал бы случайных кандидатов.

    static List<String> topClients(List<Payment> payments, String currency, int k) {
        if (k < 0) throw new IllegalArgumentException("negative k");
        Map<String, Long> totals = payments.stream()
                .filter(p -> p.currency().equals(currency)) // сначала одна валюта
                .collect(groupingBy(Payment::client, summingLong(Payment::minorUnits)));
        return totals.entrySet().stream()
                .sorted(Map.Entry.<String, Long>comparingByValue().reversed()
                        .thenComparing(Map.Entry.comparingByKey())) // стабильное правило для ничьей
                .limit(k).map(Map.Entry::getKey).toList();
    }

Ожидаемое O(n + c log c) времени, O(c) памяти, где c — число клиентов выбранной валюты. Сортировка хранит все c записей; limit(k) не превращает её в heap размера k.

OK [a, z, b]
OK []
OK []
OK negative k rejected
Почему не сравнивать обороты через (int)(b.getValue() - a.getValue())?

Разность long может переполниться; приведение к int дополнительно отбрасывает старшие биты. Знак перестаёт выражать числовой порядок. comparingByValue для Long и comparingLong сравнивают значения, не вычисляя опасную разность. Тест с близкими суммами не заменяет понимания этого контракта.

Уникальные товары каждого клиента, включая пустые заказы

Подсказка 1

Проверь решение на единственном заказе b с пустым списком: глобальное разворачивание его потеряет.

Подсказка 2

groupingBy выбирает клиента ещё по Order, затем flatMapping разворачивает products внутри группы. Собирай в TreeSet.

Решение

Ключ создаётся при обработке заказа, даже если downstream не получил ни одного товара. TreeSet удаляет повторы внутри группы и задаёт порядок названий. Глобальный flatMap в пары клиент–товар с последующей группировкой требует отдельно добавить пустых клиентов, иначе нарушается условие.

    static Map<String, Set<String>> products(List<Order> orders) {
        return orders.stream().collect(groupingBy(Order::client, TreeMap::new,
                flatMapping(o -> o.products().stream(),
                        toCollection(TreeSet::new)))); // flatMapping после выбора клиента сохраняет пустую группу
    }

O(o log c + m log u) времени: o заказов, c клиентов, m вхождений товаров, u — максимум уникальных товаров клиента. Память O(c + U), где U — число уникальных пар клиент–товар.

Топ-N платежей внутри каждой валюты

Верни карту currency → до k id платежей. Внутри группы сумма по убыванию, при равенстве id по возрастанию. Ключи валют — по алфавиту. id уникальны, все платежи оплачены. При k=0 существующие валюты остаются с пустыми списками; при k<0 брось IllegalArgumentException. Вход менять нельзя.

[b RUB 100, a RUB 100, c RUB 50, x USD 900], k=2
→ {RUB=[a, b], USD=[x]}

import java.util.*;
import static java.util.stream.Collectors.*;

public class TopPayments {
    record Payment(String id, String currency, long minorUnits) {}

    static Map<String, List<String>> topPayments(List<Payment> payments, int k) {
        // твоё решение
        return Map.of();
    }

    public static void main(String[] args) {
        List<Payment> data = List.of(new Payment("b", "RUB", 100), new Payment("a", "RUB", 100),
                new Payment("c", "RUB", 50), new Payment("x", "USD", 900));
        check(topPayments(data, 2), Map.of("RUB", List.of("a", "b"), "USD", List.of("x")));
        check(topPayments(data, 0), Map.of("RUB", List.of(), "USD", List.of()));
        check(topPayments(data, 10), Map.of("RUB", List.of("a", "b", "c"), "USD", List.of("x")));
        check(topPayments(List.of(), 2), Map.of());
        try {
            topPayments(data, -1);
            throw new AssertionError("negative k accepted");
        } catch (IllegalArgumentException expected) {
            System.out.println("OK negative k rejected");
        }
        // Независимый эталон: сортируем весь вход циклом и выбираем первые k по каждой валюте.
        Random random = new Random(42);
        for (int test = 0; test < 100; test++) {
            List<Payment> input = new ArrayList<>();
            int size = random.nextInt(50);
            for (int i = 0; i < size; i++) {
                input.add(new Payment("p" + i, "C" + random.nextInt(3), random.nextInt(5)));
            }
            int k = random.nextInt(6);
            Map<String, List<String>> want = new TreeMap<>();
            for (Payment p : input) want.computeIfAbsent(p.currency(), ignored -> new ArrayList<>());
            input.sort((a, b) -> {
                int c = Long.compare(b.minorUnits(), a.minorUnits());
                return c != 0 ? c : a.id().compareTo(b.id());
            });
            for (Payment p : input) {
                List<String> ids = want.get(p.currency());
                if (ids.size() < k) ids.add(p.id());
            }
            if (!Objects.equals(topPayments(input, k), want)) throw new AssertionError("random case " + test);
        }
        System.out.println("OK 100 randomized cases");
    }

    static void check(Object got, Object want) {
        if (!Objects.equals(got, want)) throw new AssertionError("got " + got + ", want " + want);
        System.out.println("OK " + got);
    }
}
Подсказка 1

Один глобальный limit(k) не даст k элементов каждой валюты.

Подсказка 2

Собери groupingBy(currency) с collectingAndThen(toList(), ...). Finisher сортирует одну группу, выбирает k и получает id.

Решение

Коллектор сначала сохраняет платежи каждой валюты. Finisher работает с внутренним списком, а не с исходным входом; stream().sorted(...) не сортирует входной List на месте. При k=0 группы уже созданы, поэтому значения становятся пустыми списками. Comparator разворачивает сумму перед thenComparing, сохраняя возрастающий id.

    static Map<String, List<String>> topPayments(List<Payment> payments, int k) {
        if (k < 0) throw new IllegalArgumentException("negative k");
        Comparator<Payment> rank = Comparator.comparingLong(Payment::minorUnits).reversed()
                .thenComparing(Payment::id); // reversed только для суммы: id остаётся по возрастанию
        return payments.stream().collect(groupingBy(Payment::currency, TreeMap::new,
                collectingAndThen(toList(), group -> group.stream()
                        .sorted(rank).limit(k).map(Payment::id).toList())));
    }

O(n log g + Σ nᵢ log nᵢ) времени с TreeMap и сортировкой групп, O(n + g) памяти накопления. Финальные списки неизменяемые, внешняя карта остаётся изменяемой: глубокую неизменяемость нужно обеспечивать отдельно.

Что изменить для миллиона платежей одной валюты и k=10?

Список и полная сортировка держат миллион элементов ради десяти. Ограниченный heap размера k хранит худшего выбранного кандидата на вершине: лучший новый кандидат заменяет его, затем десять элементов сортируются для ответа. Цена выбора O(n log k), память O(gk), плюс финальная сортировка. Для параллельного коллектора обязательно слияние двух heap по тому же полному компаратору, а не простое добавление всех элементов без ограничения.
