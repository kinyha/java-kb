Stream Processing

Антифрод считает платежи каждой карты за последнюю минуту и поднимает тревогу на четвёртом. Счётчик — это состояние: он должен пережить рестарт, переехать вместе с партицией на другой экземпляр и не задвоиться после сбоя. Kafka Streams держит его в локальном store рядом с задачей, а копию пишет в changelog-топик. Минуту он меряет временем события, а не часами сервера, поэтому опоздавший платёж попадает в своё окно, пока окно не закрыто. Exactly-once связывает выход, changelog и смещения одной транзакцией.

Антифрод должен заметить четыре платежа за минуту, а консьюмер с HashMap теряет счёт на деплое

Правило антифрода: больше трёх платежей по одной карте за 60 секунд — тревога, карту на ручную проверку. Платежи идут в топик payments. Первая мысль — ночной job: GROUP BY card_id по таблице платежей за сутки. Он посчитает правильно, но в три часа ночи, когда деньги уже ушли. Антифроду нужен ответ через секунды после четвёртого платежа.

Вторая мысль — обычный консьюмер с HashMap<String, Deque<Instant>>: на каждый платёж добавить время, выкинуть старше минуты, проверить размер. Работает в демо и ломается в проде сразу в нескольких местах:

  • Рестарт. Деплой или OOM — и карта памяти пуста. Серия, начатая до деплоя, после него считается с нуля.
  • Rebalance. Партицию с картой c-1 забрал другой экземпляр. Её счётчик остался в памяти старого, у нового его нет.
  • Повторы. Консьюмер упал до коммита смещения и прочитал те же платежи снова. Для идемпотентной записи в базу это не страшно, а счётчик задвоится.
  • Чья минута. Если сервис час лежал, он догоняет lag за десять секунд. По часам сервера весь час платежей влезет в одну минуту — тревоги посыплются по всем картам. Считать надо по времени платежа, а оно приходит не по порядку.

Stream processing — непрерывное вычисление над бесконечным потоком событий: агрегаты, окна, join, где фреймворк сам хранит состояние, восстанавливает его после сбоя и ведёт время событий. Очередь доставляет отдельные сообщения отдельным обработчикам. Батч считает конечный набор данных целиком, но поздно. Поток считает по мере прихода и держит промежуточный результат между событиями.

Stream processing — это консьюмер Kafka в цикле.

Консьюмер даёт доставку и смещения. Состояние между событиями, его восстановление после сбоя, время событий и окна, join двух потоков и согласованность счётчика с выходом приходится строить поверх. Kafka Streams и Flink — это и есть такая готовая надстройка.

Дальше — Kafka Streams: это библиотека, которая живёт внутри обычного Java-сервиса и читает и пишет топики Kafka. Flink и чем он отличается — в последнем шаге. Устройство топиков, партиций и групп — в Kafka Basics и Consumer Groups, транзакции на уровне брокера — в Delivery Semantics. Все демо лежат в examples/stream-processing: Kafka Streams 4.2.1, JDK 21, окна и join проверены на TopologyTestDriver без брокера, сбои — на встроенном брокере KRaft.

Топология режется на задачи по партициям, а состояние задачи лежит рядом с ней и копируется в changelog

Приложение Kafka Streams описывают как граф обработчиков — топологию. Часть операций stateless: filter, mapValues, selectKey, split смотрят на одну запись и ничего не помнят. Другие stateful: count, aggregate, reduce, окна и join хранят результат между записями в state store. Входящий топик payments имеет ключ — id платежа, а считать нужно по карте:

b.stream("payments", Consumed.with(Serdes.String(), Serdes.String()))
    .filter((paymentId, v) -> amount(v) > 0)                     // stateless: смотрит на одну запись
    .selectKey((paymentId, v) -> card(v))                        // ключ теперь — карта
    .groupByKey(Grouped.with(Serdes.String(), Serdes.String()))  // группировать по новому ключу
    .windowedBy(TimeWindows.ofSizeWithNoGrace(Duration.ofMinutes(1)))
    .count(Materialized.as("card-counts"))                       // stateful: store с именем card-counts
    .toStream()
    .filter((window, count) -> count > 3)
    .map((window, count) -> KeyValue.pair(window.key(), "payments in 1m: " + count))
    .to("fraud-alerts", Produced.with(Serdes.String(), Serdes.String()));

Одна строка selectKey разрезала граф на две под-топологии. Счётчик карты c-1 должен жить в одном месте, а платежи c-1 с разными id лежат в разных партициях payments. Поэтому Streams сам перекладывает записи в служебный repartition-топик, где партицию выбирает уже ключ-карта, и вторая под-топология читает оттуда. Это лишняя запись и чтение каждого платежа через брокер — цена смены ключа.

Дальше Streams режет каждую под-топологию на задачи: одна задача на партицию входа. Задача — единица параллельности: её целиком обрабатывает один поток одного экземпляра. Экземпляры приложения с одинаковым application.id — это одна consumer group, и задачи распределяются между ними, как партиции между консьюмерами. Тот же код, запущенный на встроенном брокере с тремя партициями:

Шесть задач: две под-топологии на три партиции, 1_2 — под-топология 1, партиция 2. Два топика Streams создал сам, с префиксом application.id. В repartition бесконечный retention: Streams сам удаляет прочитанные записи. changelog — копия store card-counts.

Store и changelog

Store по умолчанию — RocksDB на локальном диске в state.dir, своя копия у каждой задачи: antifraud/1_2/rocksdb/card-counts. Каждое изменение store Streams дополнительно пишет в changelog-топик <application.id>-<store>-changelog, с тем же числом партиций, что и у входа задачи. Changelog — источник истины, а RocksDB — быстрый локальный кеш над ним.

Для обычного store топик compacted: важно последнее значение ключа (Operations). Для оконного — compact,delete, и старые окна удаляются по retention: размер окна плюс grace плюс сутки запаса (windowstore.changelog.additional.retention.ms). В выводе это 60 000 + 86 400 000 = 86 460 000 мс.

Когда задача переезжает на другой экземпляр после падения или rebalance, новый владелец сначала читает changelog её партиции и наполняет свой store, и только потом берёт новые записи. Если на диске уже есть store этой задачи, Streams читает только хвост changelog после смещения, записанного в файле .checkpoint. Поэтому в Kubernetes state.dir кладут на persistent volume: по умолчанию это java.io.tmpdir/kafka-streams, и после пересоздания пода store на сотни гигабайт восстанавливается из changelog с нуля, минутами.

Чтобы не ждать восстановления, включают num.standby.replicas (по умолчанию 0): другой экземпляр постоянно дочитывает changelog в теневую копию store и при падении получает задачу почти тёплой. Новый экземпляр без копии Streams не делает активным сразу: если его отставание больше acceptable.recovery.lag (10 000 записей), задача остаётся у старого владельца, а на новом прогревается warmup-копия.

Store — это отдельная база, которую можно читать из любого экземпляра.

У каждого экземпляра в store только ключи его задач. Interactive queries (streams.store(...)) читают локальную часть, а за чужим ключом надо идти по сети к экземпляру-владельцу: его подсказывает queryMetadataForKey.

Имена вроде KSTREAM-AGGREGATE-0000000003 Streams генерирует по порядку операторов. Добавил filter перед агрегатом — номер сдвинулся, у store и changelog новое имя, и приложение после деплоя стартует с пустым состоянием. Store и repartition называют явно: Materialized.as("card-counts"), Grouped.as(...). В 4.2 есть ensure.explicit.internal.resource.naming=true: с ним приложение не стартует, если хоть одно внутреннее имя сгенерировано.

Почему в тесте видно каждое обновление, а в проде — меньше

Перед store стоит кеш записей, statestore.cache.max.bytes, по умолчанию 10 МБ на все потоки. Он схлопывает несколько обновлений одного ключа и сбрасывает их дальше по графу и в changelog при коммите — по умолчанию раз в commit.interval.ms = 30 с — или при вытеснении. Поэтому в проде вниз по топологии уходит меньше промежуточных значений счётчика. TopologyTestDriver коммитит после каждой записи, и в тесте видно все обновления. Опираться на число промежуточных обновлений нельзя; нужен один итог окна — это suppress из шага про время.

Окно делит бесконечный поток на конечные группы, и разные окна по-разному режут одну серию

«Платежей за минуту» — это агрегат по окну. Поток бесконечен, и count() без окна считает за всё время. Окно задаёт, какие события сложить вместе. В Kafka Streams ключ оконного агрегата — Windowed<K>: карта плюс границы окна, и у каждой пары свой счётчик в store.

  • Tumbling — окна фиксированного размера встык: каждое событие ровно в одном окне. Отчёты «за минуту», «за час».
  • Hopping — окна размера size с шагом advance, они перекрываются: событие попадает в size / advance окон.
  • Session — окно на ключ, которое растёт, пока между событиями не больше gap тишины. Размер заранее неизвестен.
  • Sliding — SlidingWindows: окна заданной длины, которые строятся по самим событиям, а не по сетке. Ровно «любые 60 секунд».

Пять платежей одной карты, три вида окон. Порог антифрода — больше трёх в окне:

var byCard = b.<String, String>stream("payments").groupByKey();   // ключ — карта
byCard.windowedBy(TimeWindows.ofSizeWithNoGrace(Duration.ofMinutes(1)))
      .count(Materialized.as("tumbling"));
byCard.windowedBy(TimeWindows.ofSizeWithNoGrace(Duration.ofMinutes(1)).advanceBy(Duration.ofSeconds(30)))
      .count(Materialized.as("hopping"));
byCard.windowedBy(SessionWindows.ofInactivityGapWithNoGrace(Duration.ofSeconds(30)))
      .count(Materialized.as("session"));

Границы tumbling и hopping выровнены по эпохе, а не по первому событию: окна начинаются в 10:00:00 и 10:00:30, потому что это кратно шагу. Начало включено, конец исключён. Отсюда первое hopping-окно [09:59:30, 10:00:30): платёж в 10:00:05 попал и в него, и в [10:00:00, 10:01:00). У session-окна обе границы — времена первого и последнего события, а одиночный платёж даёт окно нулевой длины.

Hopping ловит серию, которую tumbling разрезал, но платит за это: каждое событие обновляет size / advance окон. Окно в час с шагом в минуту — 60 записей в store и changelog на каждый платёж. Session-окна сливаются: если опоздавшее событие легло ближе чем gap и к одной сессии, и к другой, Streams удаляет обе и пишет одну общую — вниз по топологии уходит удаление старой сессии и новое значение.

Hopping-окно в минуту с шагом в секунду — это скользящее окно «за последние 60 секунд».

Это 60 перекрывающихся окон на каждое событие и всё равно сетка с шагом в секунду. Для правила «N событий за любые 60 секунд» есть SlidingWindows.ofTimeDifferenceWithNoGrace(Duration.ofMinutes(1)): окна создаются только по временам самих событий.

Окно выбирает время события, а закрывает его stream time: опоздавший платёж принимается только в пределах grace

У платежа два времени. Event time — когда платёж случился: timestamp записи Kafka, который ставит продюсер (CreateTime), или поле внутри события, если написать свой TimestampExtractor. Processing time — когда Streams до него дошёл. Окна в Kafka Streams считаются по event time: платёж из 10:00:55 попадает в окно [10:00, 10:01), даже если приложение дочитало его в 10:05 после рестарта. Так снимается проблема «час lag за десять секунд» из первого шага.

Но event time приходит не по порядку: мобильное приложение было офлайн, продюсер повторил отправку. Значит, нельзя закрыть окно в момент, когда пришло первое событие следующего окна. Kafka Streams ведёт stream time — максимальный timestamp, который задача уже видела. Он не идёт назад и не зависит от часов. Окно закрывается, когда stream time дошёл до конца окна плюс grace. Опоздавшее событие в ещё открытое окно принимается, в закрытое — отбрасывается.

KTable<Windowed<String>, Long> counts = b.<String, String>stream("payments")
    .groupByKey()
    .windowedBy(TimeWindows.ofSizeAndGrace(Duration.ofMinutes(1), Duration.ofSeconds(10)))
    .count(Materialized.with(Serdes.String(), Serdes.Long()));   // serde нужны буферу suppress
counts.toStream().to("updates", ...);                            // каждое изменение счётчика
counts.suppress(Suppressed.untilWindowCloses(Suppressed.BufferConfig.unbounded()))
      .toStream().to("final", ...);                              // один итог после закрытия окна

// Секунды от 10:00:00 в порядке прихода: 55 и 58 опоздали.
for (int sec : new int[] {5, 40, 65, 55, 90, 58}) in.pipeInput("c-1", "500", T0.plusSeconds(sec));
driver.advanceWallClockTime(Duration.ofHours(1));                // настенное время сдвинули на час

Без suppress оконный count — это поток обновлений: каждый платёж выпускает новое значение счётчика для своего окна, и потребитель должен воспринимать его как upsert по ключу «карта + окно». Для дашборда это удобно. Для тревоги «отправить одно письмо на окно» нужен итог: suppress(untilWindowCloses(...)) держит последнее значение в буфере до закрытия окна. Цена — задержка на размер окна плюс grace и память буфера.

Последние строки вывода — главная ловушка. Настенное время сдвинули на час, а итога W2 нет: окно закрывает только stream time, а его двигают только новые записи этой задачи. Если ночью платежей в партиции нет, последнее окно вечера закроется утром с первым платежом. Причём двигает его любая запись партиции, не только той же карты. Если итог нужен вовремя, в топик шлют служебные heartbeat-события или пишут закрытие через Processor API и punctuator по настенному времени.

Минутное окно закрывается, когда по часам сервера прошла минута после его конца.

Часы сервера Kafka Streams для окон не использует. Окно закрывает stream time — максимальный timestamp увиденных записей задачи. Нет новых записей — окно открыто сколько угодно, и suppress молчит.

Watermarks во Flink

Flink решает ту же задачу явным сигналом. Источник генерирует watermark — служебную метку «событий старше T больше не жду», обычно WatermarkStrategy.forBoundedOutOfOrderness(Duration.ofSeconds(10)): максимум увиденного времени минус 10 секунд. Watermark течёт по графу вместе с данными, оператор с несколькими входами берёт минимальный.

Окно срабатывает, когда watermark прошёл его конец. Опоздавшие события можно ещё принять через allowedLateness или отправить в side output вместо тихого отбрасывания. Для тихих партиций есть withIdleness: иначе минимальный watermark стоит, и окна не закрываются нигде. Stream time плюс grace в Kafka Streams — та же идея, только без отдельной метки: время ведёт каждая задача сама.

Join со справочником берёт текущее значение таблицы, а не значение на момент платежа

Обогащение: к каждому платежу приклеить статус карты — active или blocked, чтобы антифрод видел платежи по заблокированным картам. Статусы карт пишет другой сервис в compacted-топик cards. Тут нужны две абстракции. KStream — каждая запись отдельный факт: платёж p-1, платёж p-2. KTable — каждая запись заменяет прежнее значение ключа: статус карты c-1 сейчас blocked, а запись с value = null удаляет ключ. Один и тот же топик можно читать и так и так, смысл задаёт код.

Join KStream с KTable асимметричен. Платёж приходит — Streams смотрит в локальный store таблицы и берёт значение ключа, которое там лежит прямо сейчас. Обновление таблицы ничего не выпускает: прошлые платежи не пересчитываются. Тот же вход прогоним через обычную KTable и через версионированную, которая хранит историю значений:

KTable<String, String> cards = b.table("cards", Consumed.with(Serdes.String(), Serdes.String()), store);
b.<String, String>stream("payments")                                   // ключ — карта, как и у cards
 .leftJoin(cards, (payment, status) -> payment + " card=" + status)    // поиск в таблице в момент платежа
 .to("enriched");
// store: Stores.persistentKeyValueStore("cards")
//    или Stores.persistentVersionedKeyValueStore("cards", Duration.ofDays(1))

cardsIn.pipeInput("c-1", "active", at(0));
payIn.pipeInput("c-1", "p-1@10:00:10", at(10));
cardsIn.pipeInput("c-1", "blocked", at(60));      // карту заблокировали в 10:01:00
payIn.pipeInput("c-1", "p-2@10:01:10", at(70));
payIn.pipeInput("c-1", "p-3@10:00:50", at(50));   // опоздал: совершён до блокировки
payIn.pipeInput("c-2", "p-4@10:01:20", at(80));   // профиля c-2 ещё нет
cardsIn.pipeInput("c-2", "active", at(85));       // профиль пришёл после платежа
== plain KTable
  p-1@10:00:10 card=active
  p-2@10:01:10 card=blocked
  p-3@10:00:50 card=blocked
  p-4@10:01:20 card=null
== versioned KTable
  p-1@10:00:10 card=active
  p-2@10:01:10 card=blocked
  p-3@10:00:50 card=active
  p-4@10:01:20 card=null

Какой ответ верный, решает бизнес. Для отчёта «сколько платежей прошло по заблокированным картам» нужен статус на момент платежа — versioned store (Kafka 3.5, KIP-914) с историей на заданный срок. Для решения «пропускать ли платёж сейчас» — текущий. p-4 пришёл раньше профиля c-2: leftJoin отдал null, внутренний join выкинул бы платёж совсем, а профиль, пришедший позже, p-4 уже не догонит. Если справочник может опаздывать, его заранее загружают, а платёж без профиля отправляют на повторную обработку.

В тесте порядок задаёт сам тест. В настоящем приложении задача, читающая и payments, и cards, выбирает следующую запись по наименьшему timestamp среди своих партиций. С max.task.idle.ms=0 по умолчанию она ждёт данные, которые уже лежат на брокере, но не ждёт продюсеров. Поэтому на догоне lag join идёт почти по времени событий, а в реальном времени возможны перестановки — от них и спасает versioned store.

Co-partitioning: ключи должны лежать в партициях с одинаковыми номерами

Задача 0_1 видит только партицию 1 платежей и партицию 1 карт. Join найдёт статус карты, только если продюсеры обоих топиков положили ключ c-1 в партицию с одним номером: одинаковый ключ, одинаковый partitioner, одинаковое число партиций. Проверка на встроенном брокере: у payments 3 партиции, у cards сначала 3, потом 2, статус есть у всех шести карт.

java -cp "$(cat target/classpath.txt)" CopartitionDemo.java 3   # cards: 3 партиции
java -cp "$(cat target/classpath.txt)" CopartitionDemo.java 2   # cards: 2 партиции
### 3
state: RUNNING
tasks: {0_0=[cards-0, payments-0], 0_1=[cards-1, payments-1], 0_2=[cards-2, payments-2]}
enriched: [p-1 card=active, p-2 card=active, p-3 card=active, p-4 card=active, p-5 card=active, p-6 card=active]
### 2
state: RUNNING
tasks: {0_0=[cards-0, payments-0], 0_1=[cards-1, payments-1], 0_2=[payments-2]}
enriched: [p-1 card=null, p-2 card=null, p-3 card=active, p-4 card=null, p-5 card=active, p-6 card=null]

С двумя партициями у cards приложение не упало и работает: у задачи 0_2 таблицы нет вовсе, а у остальных номер партиции ключа в двух топиках разный, потому что hash(key) % 3 и hash(key) % 2 совпадают не всегда. Четыре платежа из шести молча ушли без статуса. Так ломается join после того, как кто-то добавил партиции в один из топиков (Operations). Если ключи не совпадают по смыслу, Streams делает repartition сам, как при selectKey; совпадение числа партиций у входных топиков обеспечиваешь ты.

Если справочник небольшой, его читают как GlobalKTable: полная копия на каждом экземпляре, co-partitioning не нужен, а ключ для поиска можно вытащить из значения платежа. Цена — весь справочник на диске каждого экземпляра, и обновления global-таблицы не синхронизированы по времени с потоком. Join двух потоков, например авторизации и списания одного платежа, требует окна JoinWindows.ofTimeDifferenceAndGrace(...): Streams держит обе стороны в оконных store и выпускает пару, когда записи с одним ключом встретились в пределах окна.

Когда профиль карты придёт, join допишет статус к уже обработанному платежу.

В join KStream–KTable запись выпускает только сторона потока. Обновление таблицы меняет store и ничего не отправляет: в демо p-4 так и остался с card=null. Пересчёт в обе стороны даёт join двух таблиц, KTable–KTable.

Exactly-once коммитит выход, changelog и смещения одной транзакцией, иначе счётчик задваивается после падения

При at_least_once, режиме по умолчанию, у задачи три независимые записи: результат в выходной топик, изменение store в changelog и смещение входа, которое коммитится раз в commit.interval.ms (30 с). Экземпляр, упавший между ними, оставляет changelog впереди смещения. Новый владелец восстановит store из changelog — уже с учётом платежей — и обработает те же платежи снова. Для идемпотентной записи в базу это повтор, для счётчика — неверное число.

Опыт: два платежа карты c-1, экземпляр A считает их и умирает через Runtime.halt до коммита, задачу забирает экземпляр B с пустым диском. A и B — отдельные JVM, брокер встроенный.

b.<String, String>stream("payments")
 .groupByKey()
 .count(Materialized.as("totals"))                       // store totals, changelog antifraud-totals-changelog
 .toStream()
 .peek((card, n) -> System.out.println(me + ": " + card + " count=" + n))
 .to("card-totals", Produced.with(Serdes.String(), Serdes.Long()));

props.put(StreamsConfig.PROCESSING_GUARANTEE_CONFIG, guarantee);   // at_least_once или exactly_once_v2
props.put(StreamsConfig.COMMIT_INTERVAL_MS_CONFIG, 10_000);        // A упадёт раньше коммита
props.put(StreamsConfig.STATESTORE_CACHE_MAX_BYTES_CONFIG, 0);     // каждое обновление сразу в changelog

// Экземпляр A: обработал оба платежа, подождал секунду, пока записи уйдут на брокер, и
Runtime.getRuntime().halt(1);                                      // kill -9: ни коммита, ни закрытия
// Экземпляр B: тот же application.id, другой state.dir, StateRestoreListener печатает восстановление.
### at_least_once
A: restored 0 records of antifraud-totals-changelog
A: c-1 count=1
A: c-1 count=2
A: crash before commit
B: restored 2 records of antifraud-totals-changelog
B: c-1 count=3
B: c-1 count=4
B: store totals[c-1]=4
card-totals read_uncommitted: [1, 2, 3, 4]
card-totals read_committed:   [1, 2, 3, 4]
antifraud-totals-changelog cleanup.policy=compact
### exactly_once_v2
A: restored 0 records of antifraud-totals-changelog
A: c-1 count=1
A: c-1 count=2
A: crash before commit
B: restored 0 records of antifraud-totals-changelog
B: c-1 count=1
B: c-1 count=2
B: store totals[c-1]=2
card-totals read_uncommitted: [1, 2, 1, 2]
card-totals read_committed:   [1, 2]
antifraud-totals-changelog cleanup.policy=compact

С processing.guarantee=exactly_once_v2 каждый поток Streams держит один транзакционный продюсер. Коммит задачи — это транзакция: выходные записи, записи changelog и смещения входа через sendOffsetsToTransaction фиксируются вместе или отменяются вместе. Восстановление читает changelog с read_committed, поэтому store всегда соответствует закоммиченному смещению. Как устроены маркеры, LSO и фенсинг зомби — в Delivery Semantics. Значения exactly_once и exactly_once_beta в 4.x больше нет: 4.2 принимает только at_least_once и exactly_once_v2.

Цена видна в цифрах. В EOS commit.interval.ms по умолчанию 100 мс, а не 30 с: результат виден read_committed-читателям только после коммита, и частые транзакции снижают пропускную способность. Интервал нельзя поднять выше transaction.timeout.ms продюсера, у Streams это 10 с: на 60 с конструктор KafkaStreams падает с IllegalArgumentException.

В опыте B начал обработку примерно на 9 секунд позже, чем в at-least-once. Это сходится с таймаутом транзакции в 10 с: пока брокер не отменил открытую транзакцию A, LSO changelog стоит на её начале, и read_committed-восстановление не может его пройти. Ещё одна цена — после аварийной остановки в EOS Streams не доверяет локальному store без чекпойнта и восстанавливает его из changelog заново.

С exactly_once_v2 каждый платёж обрабатывается ровно один раз.

Обработка повторяется: в опыте B второй раз прочитал p-1 и p-2. Ровно один раз фиксируется результат в Kafka — выход, changelog и смещения. HTTP-вызов банка, письмо или запись в базу из peek или foreach повторятся. Для них нужен идемпотентный обработчик (Brokers & Guarantees) или запись результата в топик и outbox-подобная доставка дальше. И читатели card-totals должны читать с isolation.level=read_committed: по умолчанию они видят и отменённые [1, 2, 1, 2].

Kafka Streams хорош для Kafka-в-Kafka внутри сервиса, Flink — для больших состояний и других источников

Kafka Streams — библиотека. Его разворачивают как обычный Spring Boot-сервис, масштабируют числом подов до числа партиций и мониторят как обычное приложение. Зато он привязан к Kafka: вход и выход — топики, состояние — RocksDB плюс changelog в той же Kafka. Flink — отдельный кластер: JobManager планирует job, TaskManager-ы исполняют операторы, а состояние периодически сохраняется целиком в checkpoint на S3 или HDFS. Барьеры checkpoint идут по графу вместе с данными и дают согласованный снимок всех операторов сразу.

Признаки, что Kafka Streams мало: состояние в терабайты, которое после потери диска восстанавливается часами; нужно соединять Kafka с CDC из нескольких баз и файлами; аналитики хотят писать окна на SQL. Тогда смотрят на Flink, а если в компании уже есть Spark — на Structured Streaming с микробатчами и задержкой от сотен миллисекунд.

Признаки, что stream processing не нужен вовсе: каждое событие обрабатывается само по себе — отправить уведомление, записать в базу, переложить в другой топик. Это обычный консьюмер или Spring Kafka с идемпотентной обработкой. Агрегат нужен раз в сутки для отчёта — батч SQL по таблице проще и дешевле. Состояние маленькое и уже есть в базе — UPDATE ... SET count = count + 1 с таблицей обработанных id даёт тот же счётчик без нового фреймворка. Если события — источник истины, а не поток для вычисления, это Event Sourcing и CQRS.

  • Stream processing — это управляемое состояние поверх потока: Kafka Streams держит store рядом с задачей и копию в changelog, поэтому счётчик переживает рестарт и переезд задачи.
  • Задача = партиция входа под-топологии. Смена ключа перед агрегатом добавляет repartition-топик, а join требует одинакового числа партиций — иначе часть записей молча не найдёт пару.
  • Окна считаются по event time, а закрываются stream time + grace. Нет новых записей в партиции — окно открыто, и suppress молчит.
  • Join потока с таблицей берёт значение на момент обработки; значение на момент события даёт versioned store.
  • exactly_once_v2 коммитит выход, changelog и смещения одной транзакцией: без него счётчик после падения задвоился 4 на 2 платежа. Внешние эффекты он не покрывает.

На собеседовании

Чем потоковая обработка отличается от очереди и от батча? Когда нужен Kafka Streams?

Очередь доставляет отдельные сообщения обработчикам, и каждое обрабатывается само по себе. Батч считает конечный набор данных целиком — точно, но поздно, раз в час или в сутки. Потоковая обработка считает по бесконечному потоку по мере прихода событий: агрегаты по окнам, join со справочником, и при этом фреймворк хранит промежуточное состояние, восстанавливает его после сбоя и ведёт время событий.

Например, антифрод «больше трёх платежей по карте за минуту». На обычном консьюмере с HashMap счётчик теряется на деплое и при rebalance, задваивается при повторах, а после простоя весь lag влезает в одну минуту по часам сервера. Kafka Streams решает это store с changelog, окнами по event time и exactly-once. Беру его, когда вход и выход — топики Kafka и нужна агрегация или обогащение; если события обрабатываются по одному — хватает Spring Kafka.

  • Kafka Streams — библиотека: масштаб — число экземпляров сервиса до числа партиций, отдельного кластера нет. Flink — кластер с JobManager и TaskManager, состояние в checkpoint на S3, любые источники, watermarks. Его беру для состояний в терабайты и источников кроме Kafka.
  • Параллельность ограничена партициями: задача на партицию под-топологии. Смена ключа добавляет repartition-топик — лишняя запись и чтение каждого события через брокер.
  • Слабое место Kafka Streams — восстановление большого store из changelog. Лечат persistent volume под state.dir, standby-репликами и warmup-копиями.
Что такое KStream и KTable и можно ли читать один топик и так и так?

KStream — поток фактов: каждая запись отдельное событие, два платежа одной карты — два платежа. KTable — таблица: запись заменяет прежнее значение ключа, null удаляет ключ. Топик один и тот же, разница в интерпретации. Платежи читают как поток, статусы карт из compacted-топика — как таблицу. Агрегат потока по ключу — тоже KTable: счётчик карты меняется с каждым платежом.

Экземпляр Kafka Streams упал посреди обработки. Что будет с состоянием и с результатом?

Состояние задачи лежит в локальном RocksDB, а каждое его изменение Streams пишет в changelog-топик. После падения группа отдаёт задачу другому экземпляру, он перечитывает changelog в свой store и продолжает с последнего закоммиченного смещения входа. Состояние не теряется, но платежи после последнего коммита обработаются ещё раз.

В at-least-once это значит, что changelog уже содержит их вклад, и счётчик задвоится: я проверял — два платежа, падение до коммита, новый экземпляр восстановил 2 и досчитал до 4. С exactly_once_v2 выход, changelog и смещения коммитятся одной транзакцией, записи упавшего отменяются, новый экземпляр восстанавливает 0 и получает правильные 2.

  • EOS стоит задержки: коммит каждые 100 мс, результат виден read_committed только после коммита. При падении новый владелец ждёт отмены открытой транзакции по transaction.timeout.ms — в опыте на 9 секунд дольше.
  • Время восстановления — размер changelog. Persistent volume для state.dir и .checkpoint сокращают его до хвоста, num.standby.replicas держит тёплую копию на другом экземпляре.
  • Exactly-once покрывает только записи в Kafka. HTTP-вызов или запись в базу из foreach повторятся — их делают идемпотентными или выносят в отдельный консьюмер выходного топика.
  • Downstream-консьюмеры должны читать с read_committed, иначе увидят и отменённые записи.
Найди проблему: приложение с exactly_once_v2 списывает комиссию через API банка 
props.put(StreamsConfig.PROCESSING_GUARANTEE_CONFIG, StreamsConfig.EXACTLY_ONCE_V2);
b.<String, Payment>stream("payments")
 .filter((card, p) -> p.amount() > 10_000)
 .foreach((card, p) -> bankClient.chargeFee(p.id(), 50));   // списать комиссию

Транзакция Kafka не откатывает HTTP-вызов. Если экземпляр упадёт после chargeFee, но до коммита, новый владелец прочитает тот же платёж и спишет комиссию второй раз. EOS здесь ничего не даёт: в Kafka ничего не пишется. Решение — передавать в банк ключ идемпотентности p.id(), чтобы банк отбросил повтор, или писать «комиссию к списанию» в топик и списывать отдельным идемпотентным консьюмером.

Какие бывают окна и что делать с опоздавшими событиями?

Tumbling — окна фиксированного размера встык, событие ровно в одном. Hopping — окна размера size с шагом advance, перекрываются, событие попадает в несколько. Session — окно на ключ, которое растёт, пока между событиями не больше gap. Sliding — окна по самим событиям, для правил «N событий за любые 60 секунд». Hopping ловит серию на стыке минут, которую tumbling разрезает на две половины.

Окна считаются по времени события. Kafka Streams ведёт stream time — максимум увиденных timestamp задачи — и закрывает окно, когда stream time дошёл до конца окна плюс grace. Опоздавшее событие в открытое окно принимается и обновляет счётчик, в закрытое — отбрасывается, и растёт метрика dropped-records-total. Если нужен один итог на окно, а не поток обновлений, ставлю suppress(untilWindowCloses(...)).

  • Stream time двигают только новые записи партиции, часы сервера на него не влияют. Тихой ночью последнее окно не закроется и suppress не выпустит итог до первого утреннего события — нужны heartbeat-события или punctuator по настенному времени.
  • Grace — компромисс полноты и задержки: больше grace — меньше потерь, но итог позже и дольше держится состояние. С 3.0 его задают явно (ofSizeAndGrace), старый TimeWindows.of с grace в сутки в 4.x удалён.
  • Во Flink вместо stream time — watermarks от источника с bounded out-of-orderness, плюс allowed lateness и side output для опоздавших вместо тихого отбрасывания.
  • Hopping с маленьким шагом дорог: событие обновляет size / advance окон в store и changelog.
Окно 1 минута, grace 10 секунд. Платежи приходят в порядке 10:00:20, 10:01:08, 10:00:50, 10:01:15, 10:00:59. Какие попадут в окно [10:00, 10:01)?

10:00:20 — да. 10:01:08 открывает следующее окно, stream time 10:01:08, а [10:00, 10:01) закрывается в 10:01:10 — ещё открыто. 10:00:50 опоздал, но stream time 10:01:08 < 10:01:10 — принят. 10:01:15 сдвигает stream time за 10:01:10, окно закрыто. 10:00:59 отброшен. В окне два платежа, итог через suppress выйдет на записи 10:01:15.

Как работает join потока с таблицей в Kafka Streams и что может пойти не так?

Таблица, например статусы карт, материализуется в локальный store задачи. Когда приходит платёж, Streams ищет в этом store значение по ключу и выпускает обогащённую запись. Обновление таблицы ничего не выпускает: прошлые платежи не пересчитываются. Если ключа ещё нет, leftJoin отдаст null, а join выкинет платёж.

Ключ и партиции должны совпадать: задача видит партицию N платежей и партицию N карт, поэтому у топиков должно быть одинаковое число партиций. Я проверял: платежи в трёх партициях, карты в двух — приложение работает, но четыре платежа из шести без статуса. Если справочник маленький, беру GlobalKTable — полная копия на каждом экземпляре, co-partitioning не нужен.

  • Join берёт значение на момент обработки. Опоздавший платёж увидит статус, установленный после него. Versioned store (3.5, KIP-914) ищет значение на timestamp платежа.
  • Порядок между топиками задача выбирает по наименьшему timestamp; max.task.idle.ms=0 ждёт только данные, уже лежащие на брокере, поэтому в реальном времени перестановки возможны.
  • Join двух потоков требует JoinWindows: обе стороны буферизуются в оконных store, и состояние растёт с размером окна.
  • Добавить партиции в один топик из пары — тихо сломать join. Число партиций у пары меняют вместе и с перезаливкой справочника.
