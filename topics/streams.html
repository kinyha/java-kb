Stream API

Стрим — не коллекция, а описание вычисления над источником: цепочка промежуточных операций (filter, map, flatMap, sorted) и одна терминальная (toList, sum, findFirst, collect). Промежуточные операции ленивы, без терминальной ничего не выполняется. Терминальная собирает из стадий цепочку приёмников и проталкивает через неё элементы по одному: в демо findFirst прошёл два платежа из пяти, а map вызвался один раз. Операции с состоянием, как sorted, — барьер: они сначала забирают все элементы. Стрим одноразовый. С Java 9 count() может вообще не выполнять конвейер, если размер известен заранее, и тогда peek молчит. У reduce identity обязана быть нейтральной, иначе параллельный результат разойдётся с последовательным. Стримы дают читаемость, а не скорость. На 10 млн элементов цикл по long[] в 5 раз быстрее LongStream и в 13 раз — стрима обёрток. На коротких списках накладные расходы на создание стрима доминируют.

Конвейер вместо цикла

Отчёт о крупных платежах: отфильтровать по сумме, взять идентификаторы, отсортировать, ограничить. Цикл смешивает «что» и «как»: переменные-аккумуляторы, условия, временные списки. Стрим описывает только «что» — и каждая стадия читается отдельно. Демо LazyDemo.java добавляет в стадии печать, чтобы увидеть, когда и в каком порядке они работают:

Optional<String> firstBig = BATCH.stream()
        .filter(p -> { System.out.println("   filter " + p.id()); return p.amount() > 50_000; })
        .map(p -> { System.out.println("   map    " + p.id()); return p.id(); })
        .findFirst();
== nothing runs without a terminal operation
pipeline built, no output above this line
== element by element, and only as many as needed
   filter p-1
   filter p-2
   map    p-2
findFirst = p-2

Конвейер без терминальной операции ничего не напечатал: filter только запомнил функцию. С findFirst видно главное свойство: обработка идёт не «стадия за стадией по всей коллекции», а «элемент за элементом через все стадии». p-1 отсеян фильтром, p-2 прошёл фильтр и map, findFirst получил результат — и остальные три платежа не тронуты вообще. Никаких промежуточных списков между стадиями нет.

Стадии с состоянием и сюрпризы ленивости

== sorted is a barrier: it needs every element first
   before sorted p-1
   before sorted p-2
   before sorted p-3
   before sorted p-4
   before sorted p-5
   after sorted  p-3
   after sorted  p-2

Чтобы выдать первый элемент по убыванию суммы, sorted должен увидеть все. Поэтому он собирает весь поток в буфер, сортирует и только потом отдаёт дальше — limit(2) не избавил от чтения всех пяти. Такие операции называют stateful: sorted, distinct (помнит увиденные элементы в HashSet), limit и skip в параллельном режиме. Они требуют памяти пропорционально потоку и не работают с бесконечными источниками. Топ-N из миллиона через sorted().limit(10) — сортировка миллиона; куча на 10 элементов из Heap & Top-K дешевле.

== count() may skip the pipeline entirely
count = 5 (size known, peek never ran)
   peek p-1
   peek p-2
   peek p-3
   peek p-4
   peek p-5
count after filter = 5

Неочевидное следствие ленивости. Источник — List с известным размером, и между ним и count() только peek, который размер не меняет. С Java 9 count() возвращает размер, не проходя по элементам, и peek не выполнился ни разу. Стоило добавить filter — размер стал неизвестен, и конвейер выполнился. Документация прямо предупреждает: реализация может не выполнять поведенческие параметры, если результат вычисляется без них. Вывод: peek — только для отладки, а побочные эффекты в стадиях — ошибка проектирования, на которую нельзя полагаться.

== a stream is single-use
second terminal op: stream has already been operated upon or closed

Стрим одноразовый: после терминальной операции объект отработал, и повторный вызов бросает IllegalStateException. Хранить Stream в поле или возвращать его «на потом» — значит рассчитывать, что потребитель вызовет его ровно один раз. Нужно многократно — храните коллекцию или Supplier<Stream<T>>. Стримы над файлами (Files.lines) держат открытый ресурс и закрываются в try-with-resources, как в I/O & NIO.

flatMap, reduce и бесконечные источники

== map vs flatMap
map:     [2, 0, 1]
flatMap: [card, 3ds, sbp]

map — один элемент в один. flatMap — один элемент в поток из нуля или многих, которые вливаются в общий поток: теги всех платежей одним списком, строки всех файлов, позиции всех заказов. Пустой список тегов у второго платежа просто ничего не добавил. С Java 16 есть mapMulti — то же через приёмник, без создания промежуточного стрима на каждый элемент. Практические задачи на flatMap и группировку — в Stream Practice.

== reduce: identity must be neutral
sum, identity 0:          280800
identity 100 sequential:  280900
identity 100 parallel:    281300

reduce(identity, op) сворачивает поток в одно значение. Identity — нейтральный элемент операции: 0 для суммы, 1 для произведения, пустая строка для конкатенации. «Начальное значение 100» — ошибка: последовательно оно добавилось один раз, а в параллельном стриме каждая часть начинает свёртку со своего identity, и 100 добавилось пять раз. Операция должна быть ассоциативной: (a op b) op c == a op (b op c), иначе результат зависит от разбиения. Для сумм есть sum() у примитивных стримов, для сборки в коллекции — collect из Collectors; reduce с созданием новой коллекции на каждом шаге — квадратичная работа.

== infinite sources need a short-circuit
retry delays: [100, 200, 400, 800, 1600, 3200]
takeWhile < 1000: [100, 200, 400, 800]

Stream.iterate и generate — бесконечные источники; работают только с limit, takeWhile (Java 9) или коротким замыканием в терминальной операции. С Java 9 есть и iterate(seed, hasNext, next) — аналог цикла for. Без ограничения toList() на бесконечном потоке закончится OutOfMemoryError.

== toList() vs collect(Collectors.toList())
Stream.toList(): unmodifiable
Collectors.toList(): ArrayList, add worked

Stream.toList() (Java 16) возвращает неизменяемый список и разрешает null-элементы; Collectors.toList() на практике возвращает ArrayList, хотя спецификация этого не обещает. Замена одного на другой при рефакторинге ломает код, который потом добавляет элементы в результат. Если нужен изменяемый — Collectors.toCollection(ArrayList::new).

Сколько стоит стрим

== sum of amounts > 50 000, 10M elements
for loop over long[]                           4.4 ms
LongStream over long[]                        20.3 ms
for loop over List<Long>                       5.1 ms
stream().filter().mapToLong().sum()           59.1 ms
stream().filter().reduce(0L, Long::sum)       69.7 ms
== a stream over 5 elements, called 1M times
for loop                                       2.1 ms
stream                                        38.0 ms

Замер CostDemo.java — однопоточный, лучший из восьми прогонов; для точных выводов нужен JMH, но порядок разницы показателен. На 10 миллионах элементов цикл по массиву JIT превращает в плотный, векторизуемый код; LongStream над тем же массивом в 5 раз медленнее — вызовы лямбд через интерфейсы и цепочку приёмников JIT встраивает не всегда. Стрим обёрток Long — ещё в 3 раза медленнее: разыменование и распаковка на каждом шаге, а reduce(0L, Long::sum) к тому же упаковывает промежуточные суммы — mapToLong().sum() лучше. Короткий стрим на 5 элементов, вызванный миллион раз, в 18 раз медленнее цикла: создание стадий, приёмников и Spliterator на каждый вызов дороже самой работы.

Вывод не «стримы медленные», а «стримы — для читаемости». В типичном бизнес-коде с вызовами базы и сети разница в микросекундах не видна, а конвейер из трёх операций понятнее цикла с флагами. В горячих циклах на миллионах элементов — массивы примитивов и циклы, и всегда — примитивные стримы (mapToLong, IntStream) вместо стримов обёрток. Параллельные стримы — отдельная тема со своими ловушками, в Parallel Streams. Отладка — ещё одна цена: в стеке исключения из лямбды десяток кадров ReferencePipeline, а точку останова в лямбде IDE ставит отдельно от строки.

peek — удобное место для логирования или побочного действия над каждым элементом.

Стрим может не выполнить стадии, если результат получается без них: в демо count() вернул размер списка, и peek не вызвался ни разу. Документация разрешает это явно. peek — только для отладки, действия над элементами — в forEach или обычном цикле.

  • Промежуточные операции ленивы; терминальная строит цепочку приёмников и проталкивает элементы по одному.
  • Короткое замыкание (findFirst, anyMatch, limit, takeWhile) останавливает источник — поэтому работают бесконечные стримы.
  • sorted и distinct — барьеры с состоянием: читают весь поток.
  • count() с Java 9 может не выполнять конвейер при известном размере — peek только для отладки.
  • Стрим одноразовый; файловые стримы закрывать.
  • reduce: нейтральная identity и ассоциативная операция, иначе параллельный результат другой.
  • toList() неизменяемый, Collectors.toList() — нет.
  • Стримы медленнее циклов, особенно на обёртках и коротких списках; примитивные стримы обязательны для чисел.

На собеседовании

Чем промежуточные операции отличаются от терминальных? Что значит ленивость?

Промежуточные операции (filter, map, flatMap, sorted, distinct, limit) возвращают новый стрим и ничего не выполняют — только описывают шаг. Терминальная (collect, toList, forEach, reduce, count, findFirst, anyMatch) запускает вычисление. Элементы проходят через все стадии по одному, без промежуточных коллекций, и короткозамыкающие операции останавливают обработку, как только результат известен.

  • Терминальная операция строит цепочку Sink; источник — Spliterator.
  • sorted и distinct — stateful-барьеры.
  • count() с Java 9 может пропустить конвейер при SIZED-источнике.
Почему аудит иногда не записывает платежи? 
long processed = payments.stream()
        .peek(audit::record)          // записать каждый платёж в журнал
        .count();

Если payments — список, count() вернёт его размер, не выполняя конвейер, и audit::record не вызовется ни разу (Java 9+). С фильтром перед count поведение снова изменится. Побочное действие не должно жить в peek: нужен явный цикл или forEach(audit::record) и отдельно payments.size().

Можно ли использовать стрим повторно?

Нет: после терминальной операции стрим считается использованным, повторный вызов бросает IllegalStateException. Для повторного обхода хранят источник — коллекцию — или Supplier<Stream>, создающий новый стрим.

  • Стримы над ресурсами (Files.lines) нужно закрывать — они AutoCloseable.

Чем map отличается от flatMap, и как работает reduce?

map преобразует каждый элемент в один элемент. flatMap преобразует элемент в стрим и вливает его элементы в общий поток — так «расплющивают» вложенные списки. reduce сворачивает поток в одно значение: identity — нейтральный элемент, операция — ассоциативная функция.

  • Ненейтральная identity добавляется на каждую часть параллельного стрима.
  • mapMulti (Java 16) — flatMap без промежуточных стримов.
  • Для коллекций — collect, а не reduce.

Стримы быстрее циклов?

Обычно нет: у стрима накладные расходы на стадии, лямбды и итератор-разделитель, а стримы обёрток добавляют упаковку. На больших массивах примитивов цикл заметно быстрее, на коротких списках создание стрима дороже самой работы. Стримы выбирают ради читаемости; в горячем коде — циклы и примитивные стримы.

  • Для замеров — JMH, а не System.nanoTime.
  • reduce(0L, Long::sum) упаковывает промежуточные суммы, mapToLong().sum() — нет.
