Strings

Комиссия за рубли нулевая — но только если «RUB» написан в коде

Платежи в рублях идут без комиссии. Проверка написана через ==, и в юнит-тестах, где валюта задана литералом, всё работает. В проде валюта приходит из JSON или из базы:

public class Currency {
    static long fee(String currency, long amount) {
        if (currency == "RUB") return 0;                          // сравнение строк через ==
        return amount / 100;
    }

    public static void main(String[] args) {
        String fromCode = "RUB";                                  // литерал в коде
        String fromJson = new StringBuilder("RU").append('B').toString();   // как из разобранного JSON
        String fromDb = "rub".toUpperCase();                      // как после нормализации
        System.out.println("литерал:   комиссия " + fee(fromCode, 10_000));
        System.out.println("из JSON:   комиссия " + fee(fromJson, 10_000) + ", equals: " + fromJson.equals("RUB"));
        System.out.println("из базы:   комиссия " + fee(fromDb, 10_000) + ", intern() == \"RUB\": " + (fromDb.intern() == "RUB"));
    }
}
литерал:   комиссия 0
из JSON:   комиссия 100, equals: true
из базы:   комиссия 100, intern() == "RUB": true

Клиенты платят комиссию, которой не должно быть. == сравнивает ссылки, а строка, построенная во время работы программы, — новый объект, даже если символы совпадают. Литерал "RUB" в коде и строка из JSON — разные объекты.

В этой теме — почему строки неизменяемы и что такое пул строк, как работает intern(), почему конкатенация в цикле квадратичная, как строки хранятся в памяти и что происходит с кодировками. Отдельно — ловушки с эмодзи, пробелами и text blocks.

Литералы живут в пуле строк, а построенные строки — отдельными объектами

String неизменяем: ни один метод не меняет строку, все возвращают новую. Поэтому одинаковые строки можно безопасно разделять между всеми, кто их использует. JVM так и делает с литералами: все одинаковые литералы во всех классах — один объект из пула строк. Какие выражения попадают в пул:

public class Pool {
    static final String PREFIX = "RU";                            // константа времени компиляции
    public static void main(String[] args) {
        String a = "RUB";
        String b = "RU" + "B";                                    // склеено компилятором
        String c = PREFIX + "B";                                  // тоже: PREFIX — final-константа
        String part = "RU";
        String d = part + "B";                                    // склеивается во время работы
        String e = new String("RUB");                             // новый объект в heap
        System.out.printf("a == b: %s, a == c: %s, a == d: %s, a == e: %s, a == e.intern(): %s%n",
            a == b, a == c, a == d, a == e, a == e.intern());
    }
}
a == b: true, a == c: true, a == d: false, a == e: false, a == e.intern(): true

С Java 7 пул строк лежит в обычном heap и собирается GC, а не в PermGen. intern() иногда используют для экономии памяти, когда в данных миллионы одинаковых строк — коды валют, статусы. Но это ручная работа с глобальной хеш-таблицей, и у G1 есть автоматическая альтернатива: -XX:+UseStringDeduplication. Он объединяет внутренние массивы одинаковых строк, переживших несколько сборок.

Неизменяемость даёт строкам и другие свойства. Строку можно безопасно использовать как ключ HashMap, а её хеш вычисляется один раз и кешируется в поле объекта. Строки потокобезопасны без синхронизации (тема Thread Safety). И строку, которую проверили, — путь к файлу, имя пользователя, — никто не подменит после проверки.

Конкатенация в цикле копирует всю строку на каждой итерации

Раз строка неизменяема, каждое += создаёт новую строку и копирует в неё всё старое содержимое. Выгрузка платежей в CSV построчно:

public class Concat {
    static long plus(int rows) {
        long start = System.nanoTime();
        String csv = "";
        for (int i = 0; i < rows; i++) csv += "payment-" + i + ";1000;RUB\n";   // новая строка на каждой итерации
        return (System.nanoTime() - start) / 1_000_000 + csv.length() * 0;
    }

    static long builder(int rows) {
        long start = System.nanoTime();
        StringBuilder csv = new StringBuilder();
        for (int i = 0; i < rows; i++) csv.append("payment-").append(i).append(";1000;RUB\n");
        String result = csv.toString();
        return (System.nanoTime() - start) / 1_000_000 + result.length() * 0;
    }

    public static void main(String[] args) {
        plus(5_000); builder(5_000);                                             // прогрев
        for (int rows : new int[]{10_000, 20_000, 40_000})
            System.out.printf("%,6d строк: += %5d мс, StringBuilder %2d мс%n", rows, plus(rows), builder(rows));
    }
}
10,000 строк: +=    44 мс, StringBuilder  0 мс
20,000 строк: +=   124 мс, StringBuilder  0 мс
40,000 строк: +=   461 мс, StringBuilder  1 мс

Вдвое больше строк — вчетверо больше времени: сложность квадратичная. На 40 000 строк это полсекунды, на 400 000 — минуты. StringBuilder держит изменяемый массив с запасом и при переполнении увеличивает его вдвое, поэтому добавление в среднем O(1), и весь CSV строится за миллисекунду.

При этом + в одном выражении — не проблема. С Java 9 javac компилирует a + b + c в вызов invokedynamic к StringConcatFactory. JVM сама собирает оптимальный код склейки: считает итоговую длину и копирует каждую часть один раз. Писать StringBuilder вместо обычного + в одной строке незачем. Он нужен, когда строка собирается в цикле. Для склейки через разделитель есть String.join, StringJoiner и Collectors.joining.

StringBuilder не потокобезопасен. Его синхронизированный предок StringBuffer остался для совместимости: строку почти никогда не собирают из нескольких потоков.

Строка хранит байты: по одному на символ латиницы, по два — на остальное

С Java 9 внутри String лежит byte[] и поле coder (compact strings, JEP 254). Если все символы строки помещаются в Latin-1, каждый занимает один байт. Если есть хоть один символ вне Latin-1 — кириллица, эмодзи, — вся строка хранится в UTF-16, по два байта на char. «payment» занимает 7 байт данных, «платёж» — 12. До Java 9 все строки хранились в char[] по два байта. Для приложений с английскими идентификаторами и JSON переход сэкономил до трети heap.

Длина строки при этом — число единиц UTF-16, а не символов. С этим связаны ошибки на эмодзи и на кодировках:

import java.nio.charset.*;

public class Encoding {
    public static void main(String[] args) {
        String purpose = "Оплата 💳";
        byte[] utf8 = purpose.getBytes(StandardCharsets.UTF_8);
        System.out.println("length() = " + purpose.length() + ", кодовых точек = " + purpose.codePointCount(0, purpose.length())
            + ", байт в UTF-8 = " + utf8.length);

        Charset cp1251 = Charset.forName("windows-1251");
        String wrong = new String(utf8, cp1251);                                 // прочитали UTF-8 как windows-1251
        System.out.println("не та кодировка: " + wrong);
        System.out.println("обратно через те же байты: " + new String(wrong.getBytes(cp1251), StandardCharsets.UTF_8));
        String ascii = new String(utf8, StandardCharsets.US_ASCII);             // ASCII заменяет чужие байты на �
        System.out.println("ASCII необратимо: " + new String(ascii.getBytes(StandardCharsets.UTF_8), StandardCharsets.UTF_8));

        String cut = purpose.substring(0, 8);                                   // обрезали по длине 8 — посреди эмодзи
        System.out.println("substring(0, 8) = [" + cut + "], последний char = U+" + Integer.toHexString(cut.charAt(7)).toUpperCase());
        System.out.println("по кодовым точкам: [" + purpose.substring(0, purpose.offsetByCodePoints(0, 8)) + "]");
        System.out.println("кодировка по умолчанию: " + Charset.defaultCharset());
    }
}
length() = 9, кодовых точек = 8, байт в UTF-8 = 17
не та кодировка: РћРїР»Р°С‚Р° рџ’і
обратно через те же байты: Оплата 💳
ASCII необратимо: ������������ ����
substring(0, 8) = [Оплата ?], последний char = U+D83D
по кодовым точкам: [Оплата 💳]
кодировка по умолчанию: UTF-8
  • Три разных «длины». 9 единиц UTF-16, 8 символов (кодовых точек), 17 байт в UTF-8. Эмодзи 💳 — это суррогатная пара из двух char, кириллица в UTF-8 — два байта на букву. Лимит «не больше 140 символов» или «не больше 255 байт в колонке базы» нужно считать в тех единицах, в которых он задан.
  • Разрезанная суррогатная пара. substring(0, 8) оставил половину эмодзи — одиночный суррогат U+D83D, и на выводе появился ?. Обрезать текст безопасно по кодовым точкам: offsetByCodePoints, codePoints().
  • Байты без кодировки — не текст. Одна и та же последовательность байт, прочитанная как windows-1251, даёт знакомые «РћРїР»Р°С‚Р°». Такое повреждение обратимо, пока байты не потеряны. Декодирование в ASCII заменяет всё непонятное на �, и исходные байты уже не вернуть.
  • Кодировка по умолчанию с Java 18 — UTF-8 на всех платформах (JEP 400). Раньше она зависела от ОС, и getBytes() без аргумента на Windows давал windows-1251. Кодировку всё равно указывают явно — StandardCharsets.UTF_8 — на границах: файлы, сеть, база.

Text blocks, strip и другие методы, которые появились после Java 8

public class Blocks {
    public static void main(String[] args) {
        String sql = """
            SELECT id, amount
            FROM payments
            WHERE status = '%s'
              AND amount > %d\
            """.formatted("NEW", 1000);                   // общий отступ срезан, \ склеивает строки
        System.out.println(sql);
        System.out.println("---");

        String em = "  1000  ";                  // широкие пробелы U+2003 из копипаста
        System.out.println("trim():  [" + em.trim() + "], strip(): [" + em.strip() + "]");
        String nbsp = "  1000  ";                // неразрывные пробелы, например из Excel
        System.out.println("NBSP после strip(): длина " + nbsp.strip().length() + " — не убраны");
        System.out.println("\"  \".isBlank() = " + "  ".isBlank() + ", \"ab\".repeat(3) = " + "ab".repeat(3));
    }
}
SELECT id, amount
FROM payments
WHERE status = 'NEW'
  AND amount > 1000
---
trim():  [  1000  ], strip(): [1000]
NBSP после strip(): длина 8 — не убраны
"  ".isBlank() = true, "ab".repeat(3) = ababab
  • Text blocks (Java 15). Общий отступ строк срезается по самой левой строке, включая закрывающие кавычки. Относительный отступ ( AND) сохраняется. \ в конце строки склеивает её со следующей. formatted — то же, что String.format. Для SQL с пользовательскими данными подстановка строк — это SQL-инъекция: значения передают параметрами PreparedStatement.
  • trim() и strip(). trim убирает только символы с кодом до пробела (≤ U+0020). strip (Java 11) убирает всё, что Unicode считает пробелом, например широкий пробел U+2003. Но неразрывный пробел U+00A0 не считается пробелом даже для strip. Данные из Excel и веб-форм чистят явно: replace(' ', ' ').
  • isBlank, repeat, lines (Java 11), indent и transform (Java 12) закрыли большую часть того, за чем раньше шли в Apache Commons.

Пароли и секреты по возможности держат в char[], а не в String. Строку нельзя стереть: она живёт в heap до сборки мусора и попадёт в дамп heap (тема Diagnostics). Массив можно затереть Arrays.fill(password, '\0') сразу после использования. Поэтому JPasswordField.getPassword() и KeyStore работают с char[].

  • Строки сравнивают через equals. == сравнивает ссылки и работает только для строк из пула, например литералов.
  • Литералы и константные выражения лежат в пуле строк. Строки, собранные при выполнении, — новые объекты. intern() возвращает объект из пула.
  • Неизменяемость даёт безопасное разделение, кеш хеша, потокобезопасность и защиту от подмены.
  • += в цикле квадратичен: удвоение данных — вчетверо дольше. Для цикла — StringBuilder. Обычный + в одном выражении компилируется через StringConcatFactory и эффективен.
  • Внутри строки — byte[]: Latin-1 по байту, иначе UTF-16 по два. length() считает единицы UTF-16, эмодзи — две.
  • Кодировку указывают явно на границах. По умолчанию с Java 18 — UTF-8.
  • strip() убирает Unicode-пробелы, trim() — только ASCII. Неразрывный пробел не убирают оба.

На собеседовании

Почему строки нельзя сравнивать через ==?

== сравнивает ссылки, а не содержимое. Литералы и константные выражения лежат в пуле строк, поэтому два одинаковых литерала — один объект, и == для них «работает». Строки, полученные во время работы — из JSON, базы, toUpperCase, склейки переменных, — новые объекты, и == для них даёт false. Строки сравнивают через equals, с возможным null — Objects.equals или "RUB".equals(x).

static final String P = "RU"; String part = "RU"; Какие из сравнений "RUB" == P + "B" и "RUB" == part + "B" истинны?

Первое — true: P — константа времени компиляции, и javac склеивает P + "B" в литерал из пула. Второе — false: part не константа, склейка идёт при выполнении и создаёт новый объект. Проверено запуском.

Почему String неизменяем?

Неизменяемость позволяет безопасно разделять одну строку между многими пользователями: пул строк, ключи HashMap, общие константы. Хеш строки вычисляется один раз и кешируется. Строки потокобезопасны без синхронизации. Строку, которую проверили — путь к файлу, URL, имя класса для загрузки, — нельзя подменить после проверки. Цена — каждое изменение создаёт новую строку, поэтому для построения в цикле нужен StringBuilder.

Что такое пул строк и intern()?

Пул — таблица уникальных строк внутри JVM. Литералы и константные выражения из всех классов попадают в него, и одинаковые литералы — один объект. intern() возвращает строку из пула с тем же содержимым, а если её нет — добавляет текущую. С Java 7 пул лежит в heap и очищается сборщиком. new String("x") всегда создаёт новый объект вне пула.

  • Для экономии памяти на повторяющихся строках вместо ручного intern() есть -XX:+UseStringDeduplication: G1 объединяет массивы одинаковых долгоживущих строк.
  • С Java 9 строки хранятся в byte[] с кодировкой Latin-1 или UTF-16 (compact strings).

Когда нужен StringBuilder, а когда хватит +?

Когда строка собирается в цикле. += в цикле каждый раз копирует всё накопленное, и время растёт квадратично: в замере урока 40 000 строк CSV собирались 461 мс против 1 мс у StringBuilder. Склейка в одном выражении — a + b + c — с Java 9 компилируется через StringConcatFactory, и вручную заменять её на StringBuilder незачем. StringBuffer — синхронизированный аналог, в новом коде не нужен.

Что возвращает length() у строки с эмодзи?

Число единиц UTF-16, а не символов. Эмодзи вне базовой плоскости Unicode — суррогатная пара из двух char, поэтому «Оплата 💳» имеет length() 9 при 8 символах и 17 байтах в UTF-8. Символы считают через codePointCount, обрезают через offsetByCodePoints. Иначе substring может разрезать пару, и появится ?.

new String(bytes) и text.getBytes() без аргументов в коде чтения файлов из банка. Что не так?

Используется кодировка по умолчанию. До Java 18 она зависела от ОС: на Windows это windows-1251, и UTF-8 из банка превращался в «РћРїР»Р°С‚Р°». С Java 18 по умолчанию UTF-8, но файл банка может быть и в другой кодировке. Кодировку указывают явно — ту, в которой файл реально пришёл.

  • JEP 254: Compact Strings — хранение строк в byte[] с Latin-1 или UTF-16.
  • JEP 280: Indify String Concatenation — конкатенация через invokedynamic.
  • JEP 400: UTF-8 by Default — кодировка по умолчанию с Java 18.
  • JEP 378: Text Blocks — правила отступов и экранирования.
