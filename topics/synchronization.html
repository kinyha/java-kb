Concurrency: synchronized & wait/notify

Два потребителя, notifyAll — и NoSuchElementException из пустой очереди

Очередь входящих платежей на synchronized и wait/notify. Если платежей нет, потребитель ждёт; производитель кладёт платёж и будит ждущих. Код выглядит учебным и правильным:

import java.util.*;

public class Inbox {
    private final Deque<String> payments = new ArrayDeque<>();

    synchronized void put(String p) {
        payments.addLast(p);
        notifyAll();                                             // разбудить всех ждущих
    }

    synchronized String take() throws InterruptedException {
        if (payments.isEmpty()) wait();                          // ждём платёж — через if
        return payments.removeFirst();
    }

    public static void main(String[] args) throws Exception {
        Inbox inbox = new Inbox();
        for (int c = 1; c <= 2; c++) {
            new Thread(() -> {
                try {
                    while (true) inbox.take();
                } catch (Exception e) {
                    System.out.println(Thread.currentThread().getName() + ": " + e);
                }
            }, "consumer-" + c).start();
        }
        for (int i = 0; i < 100_000; i++) inbox.put("p" + i);
        Thread.sleep(500);
        System.exit(0);
    }
}
consumer-2: java.util.NoSuchElementException

Три запуска — три падения, в разных потребителях. Метод take() целиком под synchronized, проверка пустоты есть, а removeFirst() всё равно достаёт из пустой очереди. Ошибка в одном слове — if вместо while. Чтобы понять почему, нужно знать, как устроен монитор и что происходит с потоком между notifyAll() и возвратом из wait().

В этой теме — что такое монитор и что именно блокирует synchronized, почему важно, на каком объекте брать замок, как работают wait, notify и notifyAll, и почему notify() может остановить систему без единого deadlock в дампе.

synchronized захватывает монитор объекта: this, класс или явно указанный

У каждого объекта в Java есть монитор — замок, который в каждый момент может держать только один поток. synchronized захватывает монитор при входе и отпускает при выходе, в том числе по исключению. Какой объект — зависит от формы:

ФормаЧей монитор
synchronized void m()this
static synchronized void m()объект класса, Monitors.class
synchronized (lock) { ... }объект lock

Проверим три свойства — повторный вход, независимость статического и обычного замков и запрет wait() без монитора:

public class Monitors {
    static synchronized void staticWork() throws InterruptedException { Thread.sleep(200); }   // замок: Monitors.class
    synchronized void instanceWork() throws InterruptedException { Thread.sleep(200); }       // замок: this

    synchronized void outer() { inner(); }                       // уже держим монитор this
    synchronized void inner() {                                  // и входим в него снова
        System.out.println("inner: держим this — " + Thread.holdsLock(this));
    }

    public static void main(String[] args) throws Exception {
        Monitors m = new Monitors();
        m.outer();                                               // реентерабельность: не зависли

        long start = System.nanoTime();
        Thread a = new Thread(() -> { try { staticWork(); } catch (InterruptedException e) { } });
        Thread b = new Thread(() -> { try { m.instanceWork(); } catch (InterruptedException e) { } });
        a.start(); b.start(); a.join(); b.join();
        System.out.printf("static + instance: %d мс — выполнялись одновременно%n", (System.nanoTime() - start) / 1_000_000);

        try {
            m.wait();                                            // монитор m не захвачен
        } catch (IllegalMonitorStateException e) {
            System.out.println("wait() без synchronized: " + e);
        }
    }
}
inner: держим this — true
static + instance: 211 мс — выполнялись одновременно
wait() без synchronized: java.lang.IllegalMonitorStateException: current thread is not owner
  • Монитор реентерабелен. Поток, который уже держит монитор, входит в него снова без ожидания. JVM считает число входов и отпускает монитор, когда счётчик вернётся к нулю. Без этого вызов одного synchronized-метода из другого зависал бы навсегда.
  • Статический и обычный методы защищены разными замками: 211 мс, а не 400. Если статический метод меняет то же состояние, что и обычный, защиты между ними нет.
  • wait и notify можно вызывать, только держа монитор этого объекта, иначе IllegalMonitorStateException.

Кроме взаимного исключения, synchronized даёт видимость: всё, что поток записал до выхода из блока, увидит следующий поток, вошедший в блок с тем же монитором. Это правило happens-before из темы Java Memory Model. Поэтому чтение общего поля тоже должно идти под тем же замком, что и запись.

Устроен монитор так. Пока за него никто не соревнуется, JVM обходится флагом в заголовке объекта и одной атомарной операцией. При конкуренции монитор «раздувается» в полноценную структуру с очередями ждущих, и потоки паркуются через ОС. Оптимизацию для объектов, которые всегда захватывает один поток (biased locking), убрали: с JDK 15 она выключена (JEP 374), в JDK 21 флага UseBiasedLocking уже нет.

Замок должен быть приватным, неизменным и вашим

Монитор есть у любого объекта, поэтому чужой код может захватить монитор вашего объекта — и остановить ваши synchronized-методы. Сервис отчётов «для согласованности» строит отчёт под synchronized (account):

public class Exposed {
    static class Account {
        private long balance;
        synchronized void deposit(long amount) { balance += amount; }        // замок — this
    }

    static class SafeAccount {
        private final Object lock = new Object();                            // замок недоступен снаружи
        private long balance;
        void deposit(long amount) { synchronized (lock) { balance += amount; } }
    }

    public static void main(String[] args) throws Exception {
        Account account = new Account();
        SafeAccount safe = new SafeAccount();
        Thread reporter = new Thread(() -> {
            synchronized (account) {                                         // чужой код взял наш монитор
                synchronized (safe) {
                    try { Thread.sleep(500); } catch (InterruptedException e) { }  // «строит отчёт»
                }
            }
        });
        reporter.start();
        Thread.sleep(50);

        long start = System.nanoTime();
        account.deposit(100);
        System.out.printf("Account.deposit:     %d мс%n", (System.nanoTime() - start) / 1_000_000);
        start = System.nanoTime();
        safe.deposit(100);
        System.out.printf("SafeAccount.deposit: %d мс%n", (System.nanoTime() - start) / 1_000_000);
        reporter.join();
    }
}
Account.deposit:     459 мс
SafeAccount.deposit: 0 мс

Пополнение счёта ждало чужой отчёт полсекунды. SafeAccount держит замок в приватном поле, и захват его монитора снаружи ни на что не влияет. synchronized-методы удобны, но их замок — публичный объект.

Вторая ошибка — замок, который меняется. Счётчик-Integer как замок:

public class WrongLock {
    static Integer count = 0;

    public static void main(String[] args) throws Exception {
        Thread[] threads = new Thread[8];
        for (int t = 0; t < threads.length; t++) {
            threads[t] = new Thread(() -> {
                for (int i = 0; i < 100_000; i++) {
                    synchronized (count) {                       // замок — текущий объект Integer
                        count++;                                 // count = Integer.valueOf(count + 1): новый объект
                    }
                }
            });
            threads[t].start();
        }
        for (Thread t : threads) t.join();
        System.out.println("ожидали 800000, получили " + count);
    }
}
$ javac WrongLock.java
WrongLock.java:9: warning: [synchronization] attempt to synchronize on an instance of a value-based class
$ java WrongLock
ожидали 800000, получили 654090

Каждый count++ кладёт в поле новый объект Integer, и потоки захватывают мониторы разных объектов. Защиты нет, хотя synchronized в коде стоит. То же случится с любым полем, которое переприсваивают, пока его используют как замок. Отдельная опасность — Integer от −128 до 127 и строковые литералы: это общие объекты на всю JVM. Замок на "lock" в вашем классе — тот же замок, что в чужой библиотеке.

Правило: замок — private final Object lock = new Object() или this, если класс осознанно документирует, что синхронизирован на себе. Никогда — строки, обёртки, Class чужих классов и изменяемые поля.

wait() отпускает монитор, а notify() лишь переводит поток в очередь за ним

wait и notify позволяют потоку ждать условия, не занимая монитор и не тратя CPU. Ключ к ним — у монитора две очереди: entry set — потоки, которые хотят войти (BLOCKED), и wait set — потоки, которые вызвали wait() (WAITING).

Поэтому условие после wait() всегда перепроверяют в цикле:

    synchronized String take() throws InterruptedException {
        while (payments.isEmpty()) wait();                       // проснулся — проверь снова
        return payments.removeFirst();
    }

С while программа из шага 1 отрабатывает все 100 000 платежей без ошибок. Есть и вторая причина для цикла — spurious wakeup. Спецификация разрешает потоку выйти из wait() вообще без notify, и на некоторых платформах это действительно случается. Цикл покрывает оба случая. Это не стиль, а часть контракта wait(), записанная в его javadoc.

notify() будит одного случайного — и может разбудить не того

notify() переводит из wait set один произвольный поток, notifyAll() — все. Кажется, что notify() экономнее. Буфер на один платёж, два производителя и два потребителя, все проверяют условие в while:

import java.util.concurrent.atomic.AtomicLong;

public class OneSlot {
    private String slot;                                         // буфер на один платёж
    private final boolean all;
    static final AtomicLong moved = new AtomicLong();

    OneSlot(boolean all) { this.all = all; }

    synchronized void put(String p) throws InterruptedException {
        while (slot != null) wait();                             // ждём, пока место освободится
        slot = p;
        if (all) notifyAll(); else notify();
    }

    synchronized String take() throws InterruptedException {
        while (slot == null) wait();                             // ждём платёж
        String p = slot;
        slot = null;
        if (all) notifyAll(); else notify();
        return p;
    }

    public static void main(String[] args) throws Exception {
        OneSlot buf = new OneSlot(args[0].equals("notifyAll"));
        for (int i = 0; i < 2; i++) {
            Thread producer = new Thread(() -> { try { while (true) buf.put("p"); } catch (InterruptedException e) { } });
            Thread consumer = new Thread(() -> { try { while (true) { buf.take(); moved.incrementAndGet(); } } catch (InterruptedException e) { } });
            producer.setDaemon(true); consumer.setDaemon(true);
            producer.start(); consumer.start();
        }
        long before = -1;
        for (int sec = 1; sec <= 5; sec++) {
            Thread.sleep(1000);
            long now = moved.get();
            System.out.printf("%d с: передано %,d%s%n", sec, now, now == before ? " — стоит" : "");
            before = now;
        }
    }
}

С notify() система передала 5–10 платежей и встала навсегда: так было во всех трёх запусках. Сценарий такой. Потребитель забрал платёж и вызвал notify(), чтобы разбудить производителя. А проснулся второй потребитель: слот пуст, и он снова уснул, никого не разбудив. Сигнал потерян, в wait set оказываются все четыре потока. Дамп потоков показывает всех в WAITING (on object monitor) внутри Object.wait(), а строки Found one Java-level deadlock нет. Формально это не deadlock — никто не ждёт замок, который держит другой. Но система стоит так же.

Беда в том, что в одном wait set ждут потоки с разными условиями: производители — «место есть», потребители — «платёж есть». notify() безопасен, только если все ждущие ждут одного и того же, и любого из них достаточно разбудить. Во всех остальных случаях — notifyAll().

В прикладном коде wait/notify сегодня почти не пишут. Для очереди есть BlockingQueue, для разных условий — Lock с несколькими Condition (тема Locks), для «дождаться N событий» — синхронизаторы. Но на собеседовании эти механизмы спрашивают, и они объясняют, как устроены готовые классы.

Под замком — только короткая работа без ввода-вывода

Пока поток держит монитор, остальные стоят в entry set. Отсюда практические правила:

  • Минимальная критическая секция. Под замок попадает только работа с общим состоянием. Подготовку данных и вычисления делают до входа, логирование — после выхода.
  • Никакого ввода-вывода под замком. HTTP-вызов, запрос в базу или запись в файл под synchronized превращают сетевую задержку в задержку всех потоков, которым нужен этот замок.
  • Никаких чужих методов под замком. Вызов слушателя или колбэка, пока держишь монитор, — прямой путь к deadlock: чужой код может захватить другой замок в обратном порядке (тема Deadlocks & Liveness).

Цена конкуренции заметна: в теме Thread Safety 8 потоков, которые наращивали общий счётчик под synchronized, работали в 26 раз медленнее, чем с LongAdder. Когда один замок становится узким местом, его разбивают на несколько (lock striping, как в старом ConcurrentHashMap) или уходят от блокировок к атомарным операциям.

С виртуальными потоками в Java 21 у synchronized есть особая цена. Виртуальный поток, который блокируется внутри synchronized, закрепляется (pinning) за потоком-носителем и не отпускает его. Долгий ввод-вывод под synchronized съедает носители. Поэтому в Java 21 для такого кода рекомендуют ReentrantLock. В JDK 24 это ограничение сняли (JEP 491). Подробно — в теме Virtual Threads.

  • synchronized захватывает монитор: у метода — this, у статического метода — объект класса, у блока — указанный объект. Статический и обычный методы защищены разными замками.
  • Монитор реентерабелен и даёт видимость: запись до выхода видна тому, кто войдёт следующим с тем же монитором.
  • Замок — приватное final-поле. Не this публичного объекта, не Integer, не строковый литерал, не переприсваиваемое поле.
  • wait() отпускает монитор и уводит поток в wait set. notify() только переводит поток в очередь за монитором, и к моменту пробуждения условие может снова стать ложным.
  • Условие после wait() проверяют в while: из-за «украденных» условий и spurious wakeup.
  • notify() безопасен только при одном условии у всех ждущих, иначе сигнал теряется и система встаёт без deadlock в дампе. По умолчанию — notifyAll(), а в новом коде — BlockingQueue и Condition.

На собеседовании

Как работает synchronized?

У каждого объекта есть монитор. synchronized захватывает его при входе и отпускает при выходе, в том числе по исключению. Пока монитор занят, другие потоки, которые хотят войти, стоят в BLOCKED. У метода монитор — this, у статического метода — объект класса, у блока — указанный объект. Монитор реентерабелен: поток может войти в него повторно.

Кроме взаимного исключения, synchronized даёт видимость: выход из блока happens-before следующего входа в блок с тем же монитором.

  • Без конкуренции монитор — флаг в заголовке объекта и CAS; при конкуренции он раздувается в структуру с очередями, и потоки паркуются.
  • Biased locking выключен с JDK 15 (JEP 374), в JDK 21 флага уже нет.
  • Виртуальный поток, заблокированный внутри synchronized, в Java 21 закрепляется за носителем; в JDK 24 это исправлено (JEP 491).
Класс с static synchronized методом a() и обычным synchronized методом b(). Могут ли они выполняться одновременно?

Могут: a() захватывает монитор объекта класса, b() — монитор экземпляра. В замере урока два метода по 200 мс в разных потоках вместе заняли 211 мс. Если они меняют общее состояние, защиты между ними нет.

Чем wait() отличается от sleep()?

wait() — метод Object. Его вызывают только под монитором этого объекта, и на время ожидания он монитор отпускает. Будит его notify или notifyAll, таймаут или прерывание. sleep() — статический метод Thread. Он просто останавливает поток на время и никакие замки не отпускает: если вызвать его внутри synchronized, монитор останется занят.

Что будет, если вызвать wait() вне synchronized?

IllegalMonitorStateException: current thread is not owner. Требование не формальное: проверка условия и уход в ожидание должны быть атомарны относительно notify. Иначе сигнал может прийти между проверкой и wait() и потеряться.

Почему wait() вызывают в цикле while, а не в if?

Потому что к моменту возврата из wait() условие может снова стать ложным. notify только переводит поток в очередь за монитором. Пока он дождётся монитора, другой поток может успеть забрать то, чего он ждал. Вторая причина — spurious wakeup: спецификация разрешает выйти из wait() без уведомления. Цикл перепроверяет условие в обоих случаях.

synchronized String take() { if (queue.isEmpty()) wait(); return queue.removeFirst(); } — производитель вызывает notifyAll(). Что не так?

if вместо while. notifyAll() будит всех потребителей. Первый забирает элемент, остальные выходят из wait() на пустую очередь и падают с NoSuchElementException. В замере урока с двумя потребителями это случилось в каждом из трёх запусков. Нужно while (queue.isEmpty()) wait();.

Чем notify() отличается от notifyAll()? Что выбрать?

notify() будит один произвольный поток из ожидающих, notifyAll() — все. notify() безопасен, только если все ожидающие ждут одного и того же условия и достаточно разбудить любого. Иначе он может разбудить поток с другим условием: тот снова уснёт, и сигнал потеряется. По умолчанию выбирают notifyAll(), а в новом коде — BlockingQueue или Condition.

Буфер на один элемент, два производителя и два потребителя, while-циклы, notify(). Что произойдёт?

Система может встать навсегда. Потребитель освобождает слот и будит второго потребителя вместо производителя. Тот видит пустой слот и снова ждёт, и в какой-то момент все четыре потока оказываются в wait set. В замере урока так было в каждом запуске после 5–10 передач. В дампе все в WAITING (on object monitor), а deadlock JVM не находит: никто не держит замок, которого ждёт другой.

На каком объекте лучше синхронизироваться?

На приватном final-поле: private final Object lock = new Object(). На this может синхронизироваться и чужой код, и тогда он блокирует ваши методы. Нельзя синхронизироваться на строках, Integer и других value-based объектах: они бывают общими на всю JVM, а при переприсваивании поле указывает на новый объект. Нельзя и на поле, которое меняется, — потоки будут захватывать разные мониторы.

static Integer count; ... synchronized (count) { count++; } — javac выдаёт предупреждение. Работает ли защита?

Нет. count++ кладёт в поле новый объект Integer, и потоки захватывают мониторы разных объектов. В замере урока 8 потоков по 100 000 увеличений получили 654 090 вместо 800 000. javac предупреждает: attempt to synchronize on an instance of a value-based class. Нужен отдельный private static final Object для замка или AtomicInteger.
