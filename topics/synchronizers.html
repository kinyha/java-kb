Concurrency: Synchronizers

Банк держит три запроса одновременно, а сервис шлёт девять

Платёжный шлюз банка обрабатывает не больше трёх запросов одновременно, остальным отвечает 429 Too Many Requests. У сервиса десять потоков обработки платежей, и каждый ходит в банк сам. Сравним вызовы без ограничения и через Semaphore на три разрешения:

import java.util.concurrent.*;
import java.util.concurrent.atomic.*;

public class BankLimit {
    // банк принимает не больше 3 запросов одновременно, остальным отвечает 429
    static final AtomicInteger inFlight = new AtomicInteger();
    static final AtomicInteger rejected = new AtomicInteger(), maxSeen = new AtomicInteger();

    static void callBank() throws InterruptedException {
        int now = inFlight.incrementAndGet();
        maxSeen.accumulateAndGet(now, Math::max);
        try {
            if (now > 3) { rejected.incrementAndGet(); return; }     // 429 Too Many Requests
            Thread.sleep(20);                                        // банк отвечает 20 мс
        } finally {
            inFlight.decrementAndGet();
        }
    }

    static void run(String name, Callable<Void> payment) throws Exception {
        rejected.set(0); maxSeen.set(0);
        ExecutorService pool = Executors.newFixedThreadPool(10);     // 10 потоков обработки платежей
        long start = System.nanoTime();
        for (Future<Void> f : pool.invokeAll(java.util.Collections.nCopies(100, payment))) f.get();
        pool.shutdown();
        System.out.printf("%-10s отказов банка: %2d, одновременно у банка до %2d, %4d мс%n",
            name, rejected.get(), maxSeen.get(), (System.nanoTime() - start) / 1_000_000);
    }

    public static void main(String[] args) throws Exception {
        run("без лимита:", () -> { callBank(); return null; });

        Semaphore permits = new Semaphore(3);                        // 3 разрешения — 3 запроса к банку
        run("Semaphore:", () -> {
            permits.acquire();                                       // ждём свободное разрешение
            try { callBank(); } finally { permits.release(); }       // вернуть при любом исходе
            return null;
        });
    }
}
без лимита: отказов банка: 97, одновременно у банка до  9,   26 мс
Semaphore: отказов банка:  0, одновременно у банка до  3,  791 мс

Без лимита почти все 100 платежей получили отказ — «быстро» только потому, что отказ приходит мгновенно. С семафором у банка никогда не бывает больше трёх запросов, и все платежи прошли. Семь потоков из десяти просто ждут своей очереди на разрешение.

Semaphore — один из синхронизаторов: объектов, которые координируют потоки через общее состояние. Кроме него в java.util.concurrent есть CountDownLatch, CyclicBarrier, Phaser и Exchanger. В этой теме — как устроен каждый, чем защёлка отличается от барьера и на каких ошибках все они ломаются.

Semaphore — счётчик разрешений, у которого нет владельца

Семафор хранит число разрешений. acquire() забирает одно или ждёт, пока появится, release() возвращает. Устроен он, как и замки, на AQS: число разрешений — это state. Главное отличие от замка — у разрешения нет владельца. Вернуть его может любой поток, и семафор не проверяет, брали ли у него что-то. Отсюда характерная ошибка:

import java.util.concurrent.*;

public class ExtraPermit {
    public static void main(String[] args) throws Exception {
        Semaphore permits = new Semaphore(3);
        permits.acquire(3);                                      // все разрешения заняты

        Thread waiter = new Thread(() -> {
            try {
                permits.acquire();                               // ждёт разрешение...
                System.out.println("получил разрешение");
            } catch (InterruptedException e) {
                System.out.println("ожидание прервано, разрешения нет");
            } finally {
                permits.release();                               // ...но возвращает в любом случае
            }
        });
        waiter.start();
        Thread.sleep(100);
        waiter.interrupt();                                      // например, запрос отменён по таймауту
        waiter.join();
        permits.release(3);                                      // остальные вернули свои
        System.out.println("разрешений теперь: " + permits.availablePermits() + " вместо 3");
    }
}
ожидание прервано, разрешения нет
разрешений теперь: 4 вместо 3

Поток не получил разрешение, но в finally вернул его. Лимит тихо вырос до четырёх, и после нескольких отмен банк снова начнёт отвечать 429. Правило то же, что у Lock: acquire() — до try, release() — в finally, как в шаге 1.

  • tryAcquire(timeout) — ждать разрешение ограниченное время и вернуть ошибку клиенту, а не держать запрос вечно.
  • new Semaphore(n, true) — справедливая очередь, как у ReentrantLock.
  • Семафор на одно разрешение похож на мьютекс, но им не является. Он нереентерабелен: повторный acquire() тем же потоком повиснет. Отпустить его может чужой поток.

Ограничение одновременных вызовов внешнего ресурса называют bulkhead — переборка, как в корпусе корабля. Если банк замедлится, заняты окажутся только три потока, а не весь пул. В Resilience4j основная реализация bulkhead — SemaphoreBulkhead, на семафоре.

CountDownLatch открывается один раз, когда счётчик дошёл до нуля

Защёлка ждёт, пока N событий произойдут. countDown() уменьшает счётчик, await() ждёт нуля. Классический сценарий — сервис при старте загружает три кеша параллельно и объявляет готовность, когда загружены все:

import java.util.concurrent.*;

public class Startup {
    static void load(String cache, int ms, boolean fail) throws InterruptedException {
        Thread.sleep(ms);
        if (fail) throw new IllegalStateException(cache + ": база недоступна");
        System.out.println("  " + cache + " загружен за " + ms + " мс");
    }

    static void start(boolean countDownInFinally) throws InterruptedException {
        CountDownLatch ready = new CountDownLatch(3);               // ждём три кеша
        ExecutorService pool = Executors.newFixedThreadPool(3);
        String[] caches = {"курсы валют", "тарифы", "справочник банков"};
        int[] times = {120, 80, 150};
        for (int i = 0; i < 3; i++) {
            int n = i;
            pool.submit(() -> {
                try {
                    load(caches[n], times[n], n == 2);              // третий падает
                    if (!countDownInFinally) ready.countDown();      // только при успехе
                } catch (Exception e) {
                    System.out.println("  ошибка: " + e.getMessage());
                } finally {
                    if (countDownInFinally) ready.countDown();       // при любом исходе
                }
                return null;
            });
        }
        long start = System.nanoTime();
        boolean ok = ready.await(2, TimeUnit.SECONDS);              // сервис ждёт готовности
        System.out.printf("готовность: %s, счётчик %d, ждали %d мс%n", ok, ready.getCount(), (System.nanoTime() - start) / 1_000_000);
        pool.shutdown();
    }

    public static void main(String[] args) throws Exception {
        System.out.println("countDown только при успехе:");
        start(false);
        System.out.println("countDown в finally:");
        start(true);
    }
}

  тарифы загружен за 80 мс
  курсы валют загружен за 120 мс
  ошибка: справочник банков: база недоступна
готовность: false, счётчик 1, ждали 2005 мс

  тарифы загружен за 80 мс

В первом варианте упавшая загрузка не уменьшила счётчик, и без таймаута старт висел бы вечно. Во втором countDown() стоит в finally — зависания нет. Но защёлка открылась, хотя справочник банков не загружен: она считает события, а не успехи. Сервис объявит себя готовым со сломанным кешем. Результат задач нужно проверять отдельно: хранить ошибки или собирать Future. А для «дождаться N асинхронных результатов и узнать об ошибке» удобнее CompletableFuture.allOf (тема CompletableFuture).

  • Защёлка одноразовая: дойдя до нуля, она открыта навсегда, и следующие await() проходят сразу. Сбросить её нельзя.
  • Всё, что поток сделал до countDown(), видно потоку после возврата из await() — это ребро happens-before из темы Java Memory Model. Поэтому загруженные кеши можно читать без дополнительной синхронизации.
  • Второй частый сценарий — обратный: new CountDownLatch(1) как стартовый пистолет, чтобы N потоков начали одновременно. Так пишут нагрузочные тесты.

CyclicBarrier заставляет потоки ждать друг друга и открывается снова

На собеседовании часто спрашивают, чем защёлка отличается от барьера. Разница в том, кто ждёт:

Барьер удобен для пошаговых вычислений: каждый поток делает свою часть шага, ждёт остальных, и шаг заканчивается общим действием. Сверка платежей по дням — три потока, каждый сверяет свою часть, итог дня считает действие барьера. На четвёртый день один поток падает:

import java.util.concurrent.*;
import java.util.concurrent.atomic.AtomicLongArray;

public class Reconcile {
    public static void main(String[] args) throws Exception {
        int workers = 3;
        AtomicLongArray partial = new AtomicLongArray(workers);
        // действие барьера выполняет последний пришедший поток, пока остальные ждут
        CyclicBarrier dayDone = new CyclicBarrier(workers, () -> {
            long sum = 0;
            for (int i = 0; i < workers; i++) sum += partial.get(i);
            System.out.println("  итог дня: " + sum);
        });
        Thread[] ts = new Thread[workers];
        for (int w = 0; w < workers; w++) {
            int id = w;
            ts[w] = new Thread(() -> {
                try {
                    for (int day = 1; day <= 3; day++) {                 // один барьер на все дни
                        partial.set(id, day * 100L + id);                // сверили свою часть платежей
                        dayDone.await();                                 // ждём остальных
                    }
                    if (id == 0) {                                       // день 4: один поток падает
                        System.out.println("  сверка-0: файл банка повреждён, к барьеру не пришёл");
                        return;
                    }
                    dayDone.await(1, TimeUnit.SECONDS);
                } catch (BrokenBarrierException e) {
                    System.out.println("  " + Thread.currentThread().getName() + ": барьер сломан");
                } catch (TimeoutException | InterruptedException e) {
                    System.out.println("  " + Thread.currentThread().getName() + ": не дождался — " + e.getClass().getSimpleName());
                }
            }, "сверка-" + w);
            ts[w].start();
        }
        for (Thread t : ts) t.join();
        System.out.println("барьер сломан: " + dayDone.isBroken());
    }
}

  итог дня: 603
  итог дня: 903
  сверка-0: файл банка повреждён, к барьеру не пришёл
  сверка-1: барьер сломан

Три дня один и тот же барьер открывался и сбрасывался. На четвёртый день поток сверка-0 не пришёл. Один из ждущих вышел по таймауту и сломал барьер, второй тут же получил BrokenBarrierException. Какой поток получит какое исключение, от запуска к запуску меняется. Сломанный барьер не ждёт вечно: всех участников выбрасывает сразу. Но после этого он бесполезен, пока не вызвать reset(). Без таймаута на await оставшиеся двое ждали бы вечно — таймаут и здесь обязателен.

Phaser — барьер с меняющимся числом участников, Exchanger — встреча двоих

Phaser обобщает оба синхронизатора: фаз может быть сколько угодно, а участники регистрируются и уходят на ходу. Сверка выписок трёх банков в две фазы. У ВТБ выписка пустая, и после первой фазы он выходит из игры:

import java.util.concurrent.*;

public class Phases {
    public static void main(String[] args) throws Exception {
        Phaser phaser = new Phaser(1) {                          // 1 — сам main
            @Override protected boolean onAdvance(int phase, int parties) {
                System.out.println("фаза " + phase + " завершена, участников: " + parties);
                return parties == 0;                             // true — фазер закончил работу
            }
        };
        String[] banks = {"Сбер", "ВТБ", "Тинькофф"};
        for (String bank : banks) {
            phaser.register();                                   // участник добавляется на ходу
            new Thread(() -> {
                phaser.arriveAndAwaitAdvance();                  // фаза 0: скачать выписку
                if (bank.equals("ВТБ")) {                        // у ВТБ выписка пустая — дальше не участвует
                    phaser.arriveAndDeregister();
                    return;
                }
                phaser.arriveAndAwaitAdvance();                  // фаза 1: сверить
                phaser.arriveAndDeregister();                    // фаза 2: закончил
            }).start();
        }
        phaser.arriveAndAwaitAdvance();                          // main проходит фазу 0 вместе со всеми
        phaser.arriveAndAwaitAdvance();                          // и фазу 1
        phaser.arriveAndDeregister();                            // main выходит
        while (!phaser.isTerminated()) Thread.sleep(10);
    }
}
фаза 0 завершена, участников: 4
фаза 1 завершена, участников: 3
фаза 2 завершена, участников: 0

В CyclicBarrier число участников задают в конструкторе навсегда. Phaser позволяет добавить участника через register(), уйти через arriveAndDeregister() и отметиться без ожидания через arrive(). onAdvance выполняется при смене фазы и решает, закончить ли работу.

Exchanger — точка встречи ровно двух потоков: каждый отдаёт объект и получает объект другого. Классический сценарий — двойная буферизация: один поток наполняет буфер, другой опустошает, и в точке встречи они меняются буферами без копирования:

import java.util.*;
import java.util.concurrent.*;

public class Swap {
    public static void main(String[] args) throws Exception {
        Exchanger<List<String>> exchanger = new Exchanger<>();
        Thread reader = new Thread(() -> {                           // читает платежи из сети в буфер
            List<String> buffer = new ArrayList<>();
            try {
                for (int batch = 1; batch <= 3; batch++) {
                    for (int i = 1; i <= 2; i++) buffer.add("p" + batch + "." + i);
                    buffer = exchanger.exchange(buffer);                 // отдали полный, получили пустой
                }
            } catch (InterruptedException e) { }
        });
        Thread writer = new Thread(() -> {                           // пишет буфер в базу
            List<String> buffer = new ArrayList<>();
            try {
                for (int batch = 1; batch <= 3; batch++) {
                    buffer = exchanger.exchange(buffer);                 // отдали пустой, получили полный
                    System.out.println("записал в базу: " + buffer);
                    buffer.clear();
                }
            } catch (InterruptedException e) { }
        });
        reader.start(); writer.start(); reader.join(); writer.join();
    }
}
записал в базу: [p1.1, p1.2]
записал в базу: [p2.1, p2.2]
записал в базу: [p3.1, p3.2]

Список безопасно переходит между потоками без volatile и блокировок: обмен даёт happens-before, как и остальные синхронизаторы. В прикладном коде Phaser и Exchanger встречаются редко, но на собеседовании их спрашивают, чтобы проверить, знает ли кандидат весь набор.

Выбор синхронизатора сводится к вопросу «кто кого ждёт»

У всех синхронизаторов общее: ожидание без таймаута превращает любую ошибку в зависание. В проде используют версии с таймаутом — tryAcquire, await(time, unit), exchange(x, time, unit) — и логируют, кто не дождался.

  • Semaphore — счётчик разрешений без владельца. Ограничивает одновременные вызовы (bulkhead). acquire() до try, release() в finally, иначе лимит растёт.
  • CountDownLatch — одноразовая защёлка: ждущие проходят, когда счётчик дошёл до нуля. countDown() — в finally, а успех задач проверяют отдельно.
  • CyclicBarrier — потоки ждут друг друга, действие барьера выполняется в конце раунда, барьер сбрасывается. Опоздавший ломает барьер для всех.
  • Защёлка: рабочие отмечаются и идут дальше, ждёт кто-то другой. Барьер: ждут сами участники.
  • Phaser — фазы с динамическим составом, Exchanger — обмен между двумя потоками.
  • Все синхронизаторы дают happens-before, и все требуют таймаутов в проде.

На собеседовании

Чем CountDownLatch отличается от CyclicBarrier?

В защёлке ждёт кто-то один или несколько, а рабочие потоки вызывают countDown() и идут дальше. Когда счётчик дошёл до нуля, ждущие проходят, и защёлка остаётся открытой навсегда — она одноразовая. В барьере ждут сами участники: каждый вызывает await() и стоит, пока не придут все N. Затем выполняется необязательное действие барьера, все идут дальше, и барьер сбрасывается для следующего раунда.

  • Если участник барьера не пришёл, прервался или вышел по таймауту, барьер ломается: все ждущие получают BrokenBarrierException, и нужен reset().
  • Число событий у защёлки не обязано совпадать с числом потоков: один поток может вызвать countDown() несколько раз.
  • Для динамического состава есть Phaser.
Сервис при старте грузит 3 кеша параллельно. Как дождаться всех и не зависнуть, если один упадёт?

CountDownLatch(3), countDown() в finally каждой загрузки, await с таймаутом. Но защёлка считает события, а не успехи — ошибки нужно собрать отдельно и проверить после await. Иначе сервис станет готовым со сломанным кешем, как в замере урока. Проще — CompletableFuture.allOf(...): он завершится исключением, если упала любая загрузка.

Что такое Semaphore и где его применяют?

Счётчик разрешений. acquire() забирает разрешение или ждёт, release() возвращает. Применяют, чтобы ограничить число одновременных обращений к ресурсу: внешний API с лимитом параллельных запросов, тяжёлые отчёты, пул дорогих объектов. В замере урока семафор на 3 разрешения убрал все 97 отказов банка. Такой шаблон называют bulkhead.

  • У разрешения нет владельца: вернуть может любой поток, и лишний release() увеличивает лимит. Поэтому acquire() ставят до try.
  • Семафор на одно разрешение — не мьютекс: он нереентерабелен и не привязан к потоку.
try { permits.acquire(); callBank(); } finally { permits.release(); } — что не так?

Если acquire() прервали, разрешение не получено, а finally всё равно его возвращает. Лимит растёт: в замере урока после одной отмены стало 4 разрешения вместо 3. Правильно — permits.acquire(); try { callBank(); } finally { permits.release(); }.

Зачем нужен Phaser, если есть CyclicBarrier?

У CyclicBarrier число участников фиксировано в конструкторе. Phaser позволяет участникам регистрироваться (register) и уходить (arriveAndDeregister) между фазами, отмечаться без ожидания (arrive) и решать в onAdvance, когда закончить. Он нужен для многофазных вычислений, где состав меняется.
