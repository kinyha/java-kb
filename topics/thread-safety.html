Concurrency: Thread Safety

Одно поле в синглтоне — и 95% чеков уходят не тем людям

Сервис чеков в Spring — синглтон: один объект обслуживает все запросы. Разработчик сохранил пользователя в поле, чтобы не передавать его в каждый метод. Под нагрузкой восемь потоков обработки запросов вызывают сервис одновременно:

import java.util.*;
import java.util.concurrent.*;

public class ReceiptService {
    // синглтон, как @Service в Spring: один объект на все запросы
    private String currentUser;                                  // «удобно»: не передавать в каждый метод

    String receipt(String user, long amount) throws InterruptedException {
        currentUser = user;
        Thread.sleep(1);                                         // поход в базу за шаблоном чека
        return "чек для " + currentUser + " на " + amount;
    }

    public static void main(String[] args) throws Exception {
        ReceiptService service = new ReceiptService();
        ExecutorService pool = Executors.newFixedThreadPool(8);   // 8 потоков обработки запросов
        List<Future<Boolean>> ok = new ArrayList<>();
        for (int i = 0; i < 1000; i++) {
            String user = "user" + i;
            ok.add(pool.submit(() -> service.receipt(user, 100).contains(user + " ")));
        }
        long wrong = 0;
        for (Future<Boolean> f : ok) if (!f.get()) wrong++;
        pool.shutdown();
        System.out.println("чеков с чужим именем: " + wrong + " из 1000");
    }
}
чеков с чужим именем: 956 из 1000

В трёх запусках — 956, 957 и 954. Пока один поток ждёт базу, другой перезаписывает общее поле, и первый читает уже чужое имя. В тесте с одним запросом код работает идеально.

Код потокобезопасен, если он работает правильно при вызове из нескольких потоков — при любом их чередовании и без дополнительной синхронизации со стороны вызывающего. Проблемы возникают, только когда несколько потоков обращаются к одному изменяемому состоянию. Отсюда три способа их избежать: не делить состояние между потоками, сделать его неизменяемым или синхронизировать доступ. В этой теме — почему даже одна строка кода не атомарна, как ломаются составные действия и инварианты и как выбирать между этими тремя способами.

count++ — это три операции, и между ними может вклиниться другой поток

Восемь потоков увеличивают общий счётчик по миллиону раз:

public class Counter {
    static int count;                                            // общий счётчик платежей

    public static void main(String[] args) throws Exception {
        Thread[] threads = new Thread[8];
        for (int t = 0; t < threads.length; t++) {
            threads[t] = new Thread(() -> {
                for (int i = 0; i < 1_000_000; i++) count++;     // одна строка — три операции
            });
            threads[t].start();
        }
        for (Thread t : threads) t.join();
        System.out.println("ожидали 8000000, получили " + count);
    }
}
ожидали 8000000, получили 2337824
ожидали 8000000, получили 2195493
ожидали 8000000, получили 1252686

Потеряно 70–85% увеличений, и каждый запуск даёт другое число. Причина видна в байткоде цикла (javap -c):

      11: iconst_1
      12: iadd                                                  прибавить 1 у себя
      13: putstatic     #28                 // Field count:I   записать обратно

Чтение, вычисление и запись — отдельные шаги. Если два потока прочитали одно и то же значение, один из результатов затрётся:

Это race condition — результат зависит от того, как потоки чередуются во времени. Действие «прочитать, изменить, записать» должно быть атомарным: другой поток видит либо состояние до него, либо после, но не середину. Та же потеря есть и без JIT: с -Xint получилось 1 209 836 и 1 257 576.

Рядом стоит термин data race из Java Memory Model: два потока обращаются к одной переменной без синхронизации, и хотя бы один пишет. Data race — про видимость и порядок операций, race condition — про логику. Они часто совпадают, но не всегда. Шаг 3 покажет race condition без единого data race — на потокобезопасных коллекциях.

volatile здесь не поможет. Он гарантирует, что потоки видят свежее значение, но count++ на volatile-поле всё равно три отдельные операции. Подробно — в теме Java Memory Model.

Потокобезопасная коллекция не делает потокобезопасным код вокруг неё

Вторая классическая форма гонки — check-then-act: проверить условие, потом действовать по его результату. Между проверкой и действием условие может измениться. Каждая операция ConcurrentHashMap по отдельности потокобезопасна, но их сочетание — нет:

import java.util.*;
import java.util.concurrent.*;

public class Compound {
    static void inParallel(Runnable action) throws Exception {
        ExecutorService pool = Executors.newFixedThreadPool(8);
        List<Future<?>> fs = new ArrayList<>();
        for (int i = 0; i < 80_000; i++) fs.add(pool.submit(action));
        for (Future<?> f : fs) f.get();
        pool.shutdown();
    }

    public static void main(String[] args) throws Exception {
        Map<String, Integer> byBank = new ConcurrentHashMap<>();
        inParallel(() -> {                                                   // проверить, потом записать
            Integer old = byBank.get("sber");
            byBank.put("sber", old == null ? 1 : old + 1);
        });
        System.out.println("get + put: " + byBank.get("sber") + " из 80000");

        Map<String, Integer> fixed = new ConcurrentHashMap<>();
        inParallel(() -> fixed.merge("sber", 1, Integer::sum));             // одна атомарная операция
        System.out.println("merge:     " + fixed.get("sber") + " из 80000");
    }
}
get + put: 69215 из 80000
merge:     80000 из 80000

Тот же count++, только распределённый по двум вызовам карты. merge делает чтение и запись одной атомарной операцией внутри карты.

Опаснее всего check-then-act в проверке идемпотентности. Брокер доставляет сообщение о платеже повторно, и обработчик проверяет, не отправляли ли его уже:

import java.util.*;
import java.util.concurrent.*;
import java.util.concurrent.atomic.AtomicInteger;

public class Idempotent {
    static final AtomicInteger sent = new AtomicInteger();

    static void send(String id) throws InterruptedException {
        Thread.sleep(1);                                             // вызов платёжного шлюза
        sent.incrementAndGet();
    }

    static void run(String name, Set<String> seen, Callable<Void> perMessage) throws Exception {
        sent.set(0);
        ExecutorService pool = Executors.newFixedThreadPool(8);
        List<Future<Void>> fs = new ArrayList<>();
        for (int i = 0; i < 2_000; i++) fs.add(pool.submit(perMessage));
        for (Future<Void> f : fs) f.get();
        pool.shutdown();
        System.out.printf("%-16s отправлено %d, уникальных платежей %d%n", name, sent.get(), seen.size());
    }

    public static void main(String[] args) throws Exception {
        Set<String> seen = ConcurrentHashMap.newKeySet();
        run("contains + add:", seen, () -> {
            String id = "payment-" + ThreadLocalRandom.current().nextInt(500);  // брокер доставляет повторно
            if (!seen.contains(id)) {                                    // проверили: ещё не отправляли
                send(id);                                                // отправили
                seen.add(id);                                            // отметили
            }
            return null;
        });

        Set<String> seen2 = ConcurrentHashMap.newKeySet();
        run("add как проверка:", seen2, () -> {
            String id = "payment-" + ThreadLocalRandom.current().nextInt(500);
            if (seen2.add(id)) send(id);                                 // add атомарно проверяет и отмечает
            return null;
        });
    }
}
contains + add:  отправлено 510, уникальных платежей 488
add как проверка: отправлено 486, уникальных платежей 486

22 платежа ушли дважды: пока первый поток ходил в шлюз, второй успел проверить тот же id и тоже не нашёл его. Set.add возвращает false, если элемент уже был, и делает это атомарно — проверка и отметка стали одним действием. Числа случайные, но в трёх запусках дубли были каждый раз: 22, 21 и 16.

У потокобезопасных классов почти всегда есть атомарные версии частых составных действий. Их и нужно искать вместо «get, потом put»:

Составное действиеАтомарная замена
если нет — положитьmap.putIfAbsent(k, v), map.computeIfAbsent(k, f), set.add(x)
прочитать, изменить, записатьmap.merge, map.compute, atomic.updateAndGet
увеличить счётчикAtomicLong.incrementAndGet, LongAdder.increment
заменить, если значение не изменилосьmap.replace(k, old, new), atomic.compareAndSet

Если нужной операции нет, составное действие целиком заключают под одну блокировку. В базе данных та же проблема решается уникальным индексом или INSERT ... ON CONFLICT DO NOTHING. Проверка в коде не спасёт, если экземпляров сервиса несколько.

Две атомарные переменные — ещё не атомарная пара

Лимиты платежа хранятся в двух AtomicLong, и должно выполняться min <= max. Каждый сеттер проверяет инвариант. Два потока меняют границы одновременно, и каждое изменение по отдельности допустимо:

import java.util.concurrent.atomic.AtomicLong;

public class Limits {
    // инвариант: min <= max
    static final AtomicLong min = new AtomicLong(0), max = new AtomicLong(1_000);

    static void setMin(long v) { if (v <= max.get()) min.set(v); }   // каждая операция атомарна,
    static void setMax(long v) { if (v >= min.get()) max.set(v); }   // а пара — нет

    public static void main(String[] args) throws Exception {
        long broken = 0;
        for (int round = 0; round < 20_000; round++) {
            min.set(0); max.set(1_000);
            Thread a = new Thread(() -> setMin(900));                // оба изменения по отдельности допустимы
            Thread b = new Thread(() -> setMax(100));
            a.start(); b.start(); a.join(); b.join();
            if (min.get() > max.get()) broken++;
        }
        System.out.println("min > max в " + broken + " раундах из 20000");
    }
}
min > max в 2 раундах из 20000

Поток A проверил, что 900 ≤ 1000, поток B — что 100 ≥ 0. Обе проверки прошли на старых значениях, обе записи состоялись, и получилось min = 900, max = 100. Это случилось 2–3 раза на 20 000 попыток. Такую ошибку не поймает ни один тест, а в проде она однажды пропустит платёж, который лимит должен был запретить.

Правило: все переменные одного инварианта защищаются вместе — одной блокировкой или одной атомарной заменой. Второй вариант — сложить границы в неизменяемый объект и менять его целиком:

import java.util.concurrent.atomic.AtomicReference;

public class SafeLimits {
    record Range(long min, long max) { }                            // неизменяемая пара
    static final AtomicReference<Range> range = new AtomicReference<>(new Range(0, 1_000));

    // обе границы меняются одной атомарной заменой всего объекта
    static void setMin(long v) { range.updateAndGet(r -> v <= r.max() ? new Range(v, r.max()) : r); }
    static void setMax(long v) { range.updateAndGet(r -> v >= r.min() ? new Range(r.min(), v) : r); }

    public static void main(String[] args) throws Exception {
        long broken = 0;
        for (int round = 0; round < 20_000; round++) {
            range.set(new Range(0, 1_000));
            Thread a = new Thread(() -> setMin(900));
            Thread b = new Thread(() -> setMax(100));
            a.start(); b.start(); a.join(); b.join();
            Range r = range.get();
            if (r.min() > r.max()) broken++;
        }
        System.out.println("min > max в " + broken + " раундах из 20000");
    }
}
min > max в 0 раундах из 20000

updateAndGet применяет функцию к текущему значению и подменяет его, только если за это время никто другой не успел. Иначе повторяет с новым значением. Проверка инварианта и запись стали одной операцией. Как устроен этот повтор — в теме Atomics & CAS.

Неизменяемый объект потокобезопасен без единой блокировки

Если состояние нельзя изменить, гонкам не на чем возникнуть. Неизменяемый объект можно отдавать любым потокам. Условия:

  • все поля final, и состояние не меняется после конструктора;
  • ссылка this не утекает из конструктора — например, в регистрацию слушателя;
  • изменяемые объекты внутри не доступны снаружи: их копируют на входе и не отдают наружу.

Поля final дают ещё и гарантию Java Memory Model: другой поток, получивший ссылку на объект, увидит их проинициализированными даже без синхронизации. Подробнее — в теме Java Memory Model.

Record выглядит неизменяемым, но его неизменяемость поверхностная: final — ссылка на список, а не сам список:

import java.util.*;

public class Orders {
    record Order(String id, List<String> items) { }                  // поля final, но список — нет

    record SafeOrder(String id, List<String> items) {
        SafeOrder { items = List.copyOf(items); }                    // своя неизменяемая копия
    }

    public static void main(String[] args) {
        List<String> items = new ArrayList<>(List.of("кофе"));
        Order order = new Order("1", items);
        SafeOrder safe = new SafeOrder("2", items);
        items.add("торт");                                           // вызывающий меняет свой список
        System.out.println("Order:     " + order.items());
        System.out.println("SafeOrder: " + safe.items());
        try {
            safe.items().add("чай");
        } catch (UnsupportedOperationException e) {
            System.out.println("изменить SafeOrder нельзя: " + e.getClass().getSimpleName());
        }
    }
}
Order:     [кофе, торт]
SafeOrder: [кофе]
изменить SafeOrder нельзя: UnsupportedOperationException

Order изменился без единого вызова его методов: список остался общим с вызывающим. List.copyOf в компактном конструкторе делает собственную неизменяемую копию. Такой record можно передавать между потоками без оглядки.

Неизменяемость не запрещает изменений, а меняет их форму: вместо правки объекта создают новый. String, BigDecimal, LocalDate и Range из шага 4 работают так. Новое значение публикуют заменой одной ссылки — через volatile-поле или AtomicReference.

Лучшая синхронизация — не делить состояние вообще

Самый надёжный способ — thread confinement: изменяемые данные доступны только одному потоку. Тогда синхронизация не нужна.

  • Стек. Локальные переменные и объекты, созданные внутри метода и никуда не сохранённые, видит только текущий поток. Исправление сервиса чеков из шага 1 — передавать пользователя параметром, а не хранить в поле. Синглтоны Spring должны быть без изменяемого состояния на запрос.
  • ThreadLocal — копия на поток. Удобно для контекста запроса, но в пуле его нужно чистить (тема Threads).
  • Один поток-владелец. Всё изменение состояния отдаётся одному потоку через очередь, например Executors.newSingleThreadExecutor(). Так устроены event loop в Netty и акторы: снаружи много потоков, внутри последовательная обработка.

Если делить состояние всё-таки нужно, остаётся синхронизация. Её инструменты сильно различаются по цене. Тот же счётчик из шага 2, 8 потоков по миллиону увеличений:

import java.util.concurrent.atomic.*;

public class Fixes {
    static int plain;
    static int locked;
    static final Object LOCK = new Object();
    static final AtomicInteger atomic = new AtomicInteger();
    static final LongAdder adder = new LongAdder();

    static long run(Runnable increment) throws InterruptedException {
        Thread[] threads = new Thread[8];
        long start = System.nanoTime();
        for (int t = 0; t < threads.length; t++) {
            threads[t] = new Thread(() -> { for (int i = 0; i < 1_000_000; i++) increment.run(); });
            threads[t].start();
        }
        for (Thread t : threads) t.join();
        return (System.nanoTime() - start) / 1_000_000;
    }

    public static void main(String[] args) throws Exception {
        long ms;
        ms = run(() -> plain++);
        System.out.printf("без защиты:    %8d за %4d мс%n", plain, ms);
        ms = run(() -> { synchronized (LOCK) { locked++; } });
        System.out.printf("synchronized:  %8d за %4d мс%n", locked, ms);
        ms = run(atomic::incrementAndGet);
        System.out.printf("AtomicInteger: %8d за %4d мс%n", atomic.get(), ms);
        ms = run(adder::increment);
        System.out.printf("LongAdder:     %8d за %4d мс%n", adder.sum(), ms);
    }
}
без защиты:     1342708 за    4 мс
synchronized:   8000000 за  185 мс
AtomicInteger:  8000000 за   69 мс
LongAdder:      8000000 за    7 мс

Без защиты — быстро и неправильно. synchronized правилен, но потоки выстраиваются в очередь за монитором. AtomicInteger обходится без блокировки, но все 8 потоков бьются за одну ячейку памяти. LongAdder раскладывает счёт по нескольким ячейкам и складывает их при чтении, поэтому почти не мешает потокам. Цифры из трёх запусков сходятся с точностью до 10%. Устройство каждого варианта — в темах synchronized, Locks и Atomics & CAS.

Порядок выбора такой:

  1. Можно не делить состояние — не делить: параметры, локальные переменные, один поток-владелец.
  2. Можно сделать неизменяемым — сделать: records с копиями, замена целого объекта.
  3. Иначе — готовые потокобезопасные классы и их атомарные операции: ConcurrentHashMap.merge, атомики.
  4. И только потом свои блокировки. Одна блокировка на весь инвариант, и документировать, что именно она защищает.
  • Проблемы возникают, только когда несколько потоков обращаются к общему изменяемому состоянию. Три защиты: не делить, сделать неизменяемым, синхронизировать.
  • count++ — чтение, изменение и запись. Без атомарности увеличения теряются: в замере 70–85%. volatile не помогает.
  • Check-then-act ломается и на потокобезопасных коллекциях. Нужны атомарные операции: merge, computeIfAbsent, putIfAbsent, Set.add как проверка.
  • Переменные одного инварианта защищают вместе: одной блокировкой или неизменяемым объектом в AtomicReference.
  • Неизменяемый объект — final-поля, без утечки this, с копиями изменяемых частей. Record неизменяем только поверхностно.
  • Синглтоны вроде Spring-бинов не хранят данные запроса в полях.

На собеседовании

Что значит «потокобезопасный класс» и как его добиться?

Класс ведёт себя правильно при вызове из нескольких потоков при любом их чередовании и не требует от вызывающих дополнительной синхронизации. Проблемы возникают только из-за общего изменяемого состояния, поэтому способа три. Не делить состояние: локальные переменные, параметры, ThreadLocal, один поток-владелец. Сделать его неизменяемым. Или синхронизировать доступ: synchronized, Lock, атомики, потокобезопасные коллекции.

  • Все переменные одного инварианта защищаются одной блокировкой или меняются одной атомарной заменой неизменяемого объекта.
  • Потокобезопасность составных действий над потокобезопасными объектами не наследуется: get плюс put на ConcurrentHashMap теряет обновления.
@Service с полем private String currentUser, которое метод заполняет в начале обработки запроса. Что не так?

Бин — синглтон, поле общее для всех потоков запросов. Пока один запрос работает, другой перезаписывает пользователя. В замере урока 95% чеков получили чужое имя. Пользователя нужно передавать параметром или брать из контекста запроса; бины не хранят данные запроса в полях.

Что такое race condition? Почему count++ не потокобезопасен?

Race condition — ситуация, когда результат зависит от чередования потоков. count++ — это три операции: прочитать, прибавить, записать. Если два потока прочитали одно значение, одна запись затрёт другую. В замере 8 потоков по миллиону увеличений потеряли больше двух третей. Лечится атомарностью: synchronized, AtomicInteger.incrementAndGet() или LongAdder.

  • Data race — термин JMM: доступ к переменной из нескольких потоков без синхронизации, и хотя бы один пишет. Race condition бывает и без data race — например, check-then-act на ConcurrentHashMap.
  • volatile даёт видимость, но не атомарность составных операций.
Поможет ли сделать count volatile?

Нет. volatile гарантирует, что каждое чтение видит последнюю запись, но между чтением и записью в count++ другой поток всё так же успевает вклиниться. Нужна атомарная операция или блокировка.

Что такое check-then-act и как с ним бороться?

Шаблон «проверить условие, потом действовать»: ленивая инициализация, «если ключа нет — положить», «если платёж ещё не отправлен — отправить». Между проверкой и действием другой поток может изменить условие. Лечится тем, что проверку и действие делают одной атомарной операцией: putIfAbsent, computeIfAbsent, merge, Set.add как проверка — или ставят обе части под одну блокировку.

if (!sent.contains(id)) { gateway.send(id); sent.add(id); } — sent это ConcurrentHashMap.newKeySet(). Может ли платёж уйти дважды? Как исправить?

Может: два потока с одним id оба проверят contains до того, как кто-то вызовет add. В замере урока из 2000 сообщений 22 платежа ушли дважды. Исправление — if (sent.add(id)) gateway.send(id);. Если сервис запущен в нескольких экземплярах, нужна проверка в общем хранилище — например, уникальный ключ в базе.

Почему неизменяемые объекты потокобезопасны? Как сделать класс неизменяемым?

Их состояние нельзя изменить, значит, гонкам не на чем возникнуть, и синхронизация не нужна. Правила: все поля final, нет сеттеров, this не утекает из конструктора, изменяемые поля копируются на входе и не отдаются наружу. Record помогает, но его неизменяемость поверхностная: список внутри нужно копировать через List.copyOf.

  • JMM гарантирует видимость final-полей после конструктора любому потоку, получившему ссылку, даже при публикации без синхронизации.
  • Изменения делают заменой целого объекта через volatile-поле или AtomicReference. Так защищают инварианты из нескольких полей.
  • Brian Goetz et al., Java Concurrency in Practice, гл. 2–3 «Thread Safety», «Sharing Objects» — основа урока: атомарность, составные действия, инварианты, неизменяемость, confinement.
  • JLS 21, глава 17: Threads and Locks — формальное определение data race и семантика final-полей.
  • ConcurrentHashMap (JDK 21) — какие операции атомарны: merge, compute, putIfAbsent.
