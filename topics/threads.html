Concurrency: Threads

shutdownNow() не остановил задачу — прерывание проглотили

Фоновая задача раз в секунду проверяет статус платежа, пока её не отменят. При остановке сервиса пул вызывает shutdownNow() и ждёт три секунды:

import java.util.concurrent.*;

public class Stubborn {
    // «повторять раз в секунду, пока не отменят»
    static void pollStatus() {
        while (!Thread.currentThread().isInterrupted()) {
            try {
                Thread.sleep(1000);                              // ждём следующей проверки
            } catch (InterruptedException e) {
                System.out.println("прерывание пришло — и проглочено");
            }
        }
        System.out.println("задача остановлена");
    }

    public static void main(String[] args) throws Exception {
        ExecutorService pool = Executors.newSingleThreadExecutor();
        pool.submit(Stubborn::pollStatus);
        Thread.sleep(300);
        pool.shutdownNow();                                      // прерывает рабочие потоки
        boolean done = pool.awaitTermination(3, TimeUnit.SECONDS);
        System.out.println("пул остановился за 3 с: " + done);
        System.exit(0);
    }
}
прерывание пришло — и проглочено
пул остановился за 3 с: false

Цикл проверяет флаг прерывания, shutdownNow() прерывание послал — и всё равно задача крутится дальше. Без System.exit процесс бы не завершился вовсе. Причина в одной строке catch, и чтобы её увидеть, нужно знать, как устроено прерывание.

В этой теме — что такое поток в Java и сколько он стоит, как запускать задачи, какие бывают состояния, как правильно останавливать поток, что такое daemon-потоки, куда деваются исключения и как работает ThreadLocal.

Поток Java — это поток ОС, и start() создаёт его, а run() — нет

Каждый объект Thread после start() получает свой поток операционной системы со своим стеком. Планирует его ОС, а не JVM. Код для потока передают как Runnable. Наследоваться от Thread можно, но не нужно: задача и механизм её выполнения — разные вещи.

public class StartRun {
    public static void main(String[] args) throws Exception {
        Runnable task = () -> System.out.println("выполняет: " + Thread.currentThread().getName());
        Thread t = new Thread(task, "worker");
        t.run();                                                 // обычный вызов метода
        t.start();                                               // новый поток
        t.join();
        try {
            t.start();                                           // второй раз
        } catch (IllegalThreadStateException e) {
            System.out.println("повторный start(): " + e);
        }
    }
}
выполняет: main
выполняет: worker
повторный start(): java.lang.IllegalThreadStateException

run() — просто метод: код выполнился в вызывающем потоке main. Новый поток создаёт только start(), и только один раз. Закончивший поток перезапустить нельзя.

Runnable ничего не возвращает и не может бросить checked-исключение. Если нужен результат, используют Callable и отдают задачу пулу, который вернёт Future:

import java.io.IOException;
import java.util.concurrent.*;

public class Calls {
    public static void main(String[] args) throws Exception {
        ExecutorService pool = Executors.newSingleThreadExecutor();

        Future<?> log = pool.submit(() -> System.out.println("Runnable: ничего не возвращает"));
        System.out.println("Runnable вернул: " + log.get());

        Future<Integer> fee = pool.submit(() -> 1_000 * 3 / 100);          // Callable: возвращает значение
        System.out.println("комиссия: " + fee.get());

        Future<Integer> bank = pool.submit(() -> {                          // Callable может бросить checked
            throw new IOException("банк недоступен");
        });
        try {
            bank.get();
        } catch (ExecutionException e) {                                    // исключение задачи — внутри
            System.out.println("get() бросил: " + e.getCause());
        }
        pool.shutdown();
    }
}
Runnable: ничего не возвращает
Runnable вернул: null
комиссия: 30
get() бросил: java.io.IOException: банк недоступен

Исключение из задачи не теряется: get() бросает его, обёрнутое в ExecutionException. Но только если кто-то вызовет get(). Об этом шаг 6.

Сколько стоит поток

Поток ОС — дорогой ресурс. Замер на JDK 21, macOS, 10 000 повторов после прогрева:

import java.util.concurrent.*;

public class Cost {
    public static void main(String[] args) throws Exception {
        int n = 10_000;
        for (int round = 0; round < 3; round++) {                // первые круги — прогрев
            long start = System.nanoTime();
            for (int i = 0; i < n; i++) {
                Thread t = new Thread(() -> { });
                t.start();
                t.join();
            }
            long perThread = (System.nanoTime() - start) / n;

            ExecutorService pool = Executors.newFixedThreadPool(1);
            start = System.nanoTime();
            for (int i = 0; i < n; i++) pool.submit(() -> { }).get();
            long perTask = (System.nanoTime() - start) / n;
            pool.shutdown();
            System.out.printf("новый поток: %d мкс, задача в пуле: %d мкс%n", perThread / 1000, perTask / 1000);
        }
    }
}
новый поток: 28 мкс, задача в пуле: 8 мкс
новый поток: 27 мкс, задача в пуле: 5 мкс
новый поток: 27 мкс, задача в пуле: 5 мкс

Создать и дождаться поток — около 27 мкс, передать задачу готовому потоку пула — 5 мкс, в пять раз дешевле. Вторая цена — память. Под стек каждого потока JVM резервирует ThreadStackSize: на macOS arm64 это 2 МБ, на Linux x86_64 — 1 МБ. Реально занята только использованная часть. Около 60–90 КБ реальной памяти на простаивающий поток, плюс резерв адресов. Поэтому потоки не создают на каждый запрос, а держат в пуле ограниченного размера (тема Executors). А если задачи в основном ждут ввода-вывода, есть виртуальные потоки — тема Virtual Threads.

У потока шесть состояний, и три из них — разные виды ожидания

Состояние возвращает getState(), и его же показывает дамп потоков. Проведём один поток через все шесть состояний:

public class States {
    static final Object LOCK = new Object();

    public static void main(String[] args) throws Exception {
        Thread t = new Thread(() -> {
            synchronized (LOCK) { }                              // 1) ждёт монитор
            synchronized (LOCK) {
                try { LOCK.wait(); } catch (InterruptedException e) { }   // 2) ждёт notify
            }
            try { Thread.sleep(200); } catch (InterruptedException e) { } // 3) спит с таймаутом
            for (long i = 0; i < 3_000_000_000L; i++) { }        // 4) считает
        }, "worker");
        System.out.println("до start():        " + t.getState());
        synchronized (LOCK) {
            t.start();
            Thread.sleep(100);
            System.out.println("монитор занят:     " + t.getState());
        }
        Thread.sleep(100);
        System.out.println("в wait():          " + t.getState());
        synchronized (LOCK) { LOCK.notify(); }
        Thread.sleep(100);
        System.out.println("в sleep(200):      " + t.getState());
        Thread.sleep(200);
        System.out.println("считает:           " + t.getState());
        t.join();
        System.out.println("после join():      " + t.getState());
    }
}
до start():        NEW
монитор занят:     BLOCKED
в wait():          WAITING
в sleep(200):      TIMED_WAITING
считает:           RUNNABLE
после join():      TERMINATED

Главный поток ждёт по 100 мс между проверками, чтобы worker успел дойти до нужного места. Результат проверен в пяти запусках подряд. Переходы между состояниями:

Поток, который ждёт ответа от базы, находится в состоянии WAITING.

Обычно нет: чтение из сокета — системный вызов, и Java показывает такой поток как RUNNABLE. В дампе потоков его выдаёт стек: в JDK 21 верхний кадр — sun.nio.ch.SocketDispatcher.read0. Проверено: поток, который читает из сокета без данных, показывает RUNNABLE и остаётся в нём после interrupt(). Поэтому сотня потоков в RUNNABLE ещё не значит, что CPU занят.

Замки из java.util.concurrent (ReentrantLock, очереди) ждут через park(), поэтому поток, который ждёт такой замок, будет в WAITING, а не в BLOCKED. BLOCKED бывает только у synchronized.

Прерывание — это просьба остановиться, а не приказ

Остановить поток силой в Java нельзя: Thread.stop() в Java 21 бросает UnsupportedOperationException. Вместо этого есть кооперативный механизм. t.interrupt() поднимает у потока флаг, а поток сам решает, когда и как завершиться. Как ведёт себя флаг:

public class Interrupts {
    static final Object LOCK = new Object();

    public static void main(String[] args) throws Exception {
        Thread self = Thread.currentThread();

        self.interrupt();                                         // флаг поднят заранее
        try {
            Thread.sleep(10_000);                                 // бросает сразу, не ждёт 10 с
        } catch (InterruptedException e) {
            System.out.println("sleep бросил сразу, флаг после catch: " + self.isInterrupted());
        }

        self.interrupt();
        System.out.println("interrupted(): " + Thread.interrupted() + ", второй вызов: " + Thread.interrupted());

        Thread blocked = new Thread(() -> {
            synchronized (LOCK) { System.out.println("вошёл в монитор, флаг: " + Thread.currentThread().isInterrupted()); }
        });
        synchronized (LOCK) {
            blocked.start();
            Thread.sleep(100);
            blocked.interrupt();                                  // поток в BLOCKED
            Thread.sleep(100);
            System.out.println("после interrupt() состояние: " + blocked.getState());
        }
        blocked.join();
    }
}
sleep бросил сразу, флаг после catch: false
interrupted(): true, второй вызов: false
после interrupt() состояние: BLOCKED
вошёл в монитор, флаг: true

Три правила, которые видны в выводе:

  • Блокирующие методы отвечают на прерывание исключением: sleep, wait, join, BlockingQueue.take, Future.get. Если флаг уже поднят, исключение летит сразу.
  • Бросая InterruptedException, метод сбрасывает флаг. После catch поток выглядит непрерванным. Thread.interrupted() тоже сбрасывает флаг, а isInterrupted() — нет.
  • Не всё прерывается. Ожидание входа в synchronized прерыванием не отменить: поток остался в BLOCKED и узнал о флаге, только войдя в монитор. Чтение из java.net.Socket в обычном потоке тоже не прерывается — для него ставят таймаут setSoTimeout или закрывают сокет.

Теперь понятно, что случилось в шаге 1. shutdownNow() прервал поток посреди sleep. Исключение сбросило флаг, catch его проглотил, и условие цикла снова увидело «не прерван». Исправление — одна строка:

            } catch (InterruptedException e) {
                Thread.currentThread().interrupt();              // восстановить флаг: цикл увидит его и выйдет
            }
задача остановлена
пул остановился за 3 с: true

Если метод не может обработать прерывание сам, у него два честных варианта. Можно объявить throws InterruptedException и отдать решение вызывающему. А если сигнатуру менять нельзя, например в Runnable.run(), — восстановить флаг, как выше. Пустой catch — ошибка: он ломает отмену для всего кода выше по стеку.

JVM ждёт все обычные потоки, а daemon-потоки обрывает без finally

t.join() ждёт завершения потока t. Кроме ожидания, он даёт гарантию видимости: всё, что поток записал до завершения, вызывающий увидит после join(). Подробно — в теме Java Memory Model.

JVM завершается, когда закончились все не-daemon потоки. Daemon-поток — фоновый, JVM его не ждёт. Разница видна на потоке, который в finally сбрасывает буфер:

public class Daemon {
    public static void main(String[] args) {
        Thread flusher = new Thread(() -> {
            try {
                while (true) Thread.sleep(100);                  // «сбрасывает буфер на диск»
            } catch (InterruptedException e) {
            } finally {
                System.out.println("finally: буфер сброшен");     // выполнится?
            }
        });
        flusher.setDaemon(Boolean.parseBoolean(args[0]));
        flusher.start();
        System.out.println("main закончился");
    }
}
$ java Daemon true
main закончился                   # JVM вышла сразу, finally не выполнен
$ java Daemon false
main закончился                   # процесс не завершается, пока поток жив; пришлось убить через kill

Daemon-поток при выходе JVM просто исчезает: ни finally, ни закрытия ресурсов. Поэтому в daemon-потоках не делают ничего, что нельзя бросить на полуслове, — например, запись в файл. Обычный поток, наоборот, держит JVM живой: забытый не-daemon поток — частая причина того, что утилита «не завершается». Признак daemon наследуется от создающего потока и задаётся до start().

Для действий при штатной остановке есть Runtime.getRuntime().addShutdownHook(thread). Хук выполняется при System.exit, конце последнего обычного потока и по сигналу SIGTERM, но не при kill -9.

Исключение в потоке убивает только этот поток, и его легко не заметить

public class Crash {
    public static void main(String[] args) throws Exception {
        Thread t = new Thread(() -> { throw new IllegalStateException("баланс отрицательный"); }, "payment-1");
        t.start();
        t.join();
        System.out.println("main жив, поток " + t.getName() + ": " + t.getState());

        Thread.setDefaultUncaughtExceptionHandler((th, e) ->
            System.out.println("handler: " + th.getName() + " упал с " + e.getMessage()));
        Thread t2 = new Thread(() -> { throw new IllegalStateException("таймаут банка"); }, "payment-2");
        t2.start();
        t2.join();
    }
}
Exception in thread "payment-1" java.lang.IllegalStateException: баланс отрицательный
	at Crash.lambda$main$0(Crash.java:3)
	at java.base/java.lang.Thread.run(Thread.java:1583)
main жив, поток payment-1: TERMINATED
handler: payment-2 упал с таймаут банка

Исключение, которое никто не поймал, завершает только свой поток. По умолчанию стек печатается в System.err, а в проде stderr часто никто не читает. UncaughtExceptionHandler — для одного потока через setUncaughtExceptionHandler или для всех через setDefaultUncaughtExceptionHandler — позволяет хотя бы залогировать падение.

С пулом всё ещё тише. submit() ловит исключение задачи и кладёт его в Future, как в шаге 2. Handler не вызывается, в stderr ничего не печатается. Если результат get() никто не спрашивает, ошибка пропадает бесследно. execute() ведёт себя иначе: исключение уходит в handler потока пула. Подробнее — в теме Executors.

ThreadLocal даёт каждому потоку свою копию значения

ThreadLocal хранит значение отдельно для каждого потока. Два применения: дать каждому потоку свой экземпляр непотокобезопасного объекта и неявно передавать контекст запроса вниз по стеку. Первое — на классическом примере SimpleDateFormat, у которого общее изменяемое состояние:

import java.text.SimpleDateFormat;
import java.util.*;
import java.util.concurrent.*;

public class Tl {
    static final SimpleDateFormat SHARED = new SimpleDateFormat("yyyy-MM-dd");          // не потокобезопасен
    static final ThreadLocal<SimpleDateFormat> LOCAL =
        ThreadLocal.withInitial(() -> new SimpleDateFormat("yyyy-MM-dd"));              // свой у каждого потока

    static long errors(boolean local) throws Exception {
        ExecutorService pool = Executors.newFixedThreadPool(8);
        List<Future<Boolean>> results = new ArrayList<>();
        for (int i = 0; i < 10_000; i++) {
            String date = String.format("2026-%02d-%02d", i % 12 + 1, i % 28 + 1);
            results.add(pool.submit(() -> {
                SimpleDateFormat f = local ? LOCAL.get() : SHARED;
                try { return f.format(f.parse(date)).equals(date); } catch (Exception e) { return false; }
            }));
        }
        long bad = 0;
        for (Future<Boolean> r : results) if (!r.get()) bad++;
        pool.shutdown();
        return bad;
    }

    public static void main(String[] args) throws Exception {
        System.out.println("общий SimpleDateFormat: ошибок " + errors(false) + " из 10000");
        System.out.println("ThreadLocal:            ошибок " + errors(true) + " из 10000");
    }
}
общий SimpleDateFormat: ошибок 8752 из 10000
ThreadLocal:            ошибок 0 из 10000

С общим экземпляром восемь потоков портят друг другу разбор, и неверных дат тысячи. Число меняется от запуска к запуску: 8752, 8451, 8767. С ThreadLocal ошибок нет. В новом коде ту же задачу решает неизменяемый DateTimeFormatter, которому ThreadLocal не нужен.

Второе применение встречается чаще, чем кажется. На ThreadLocal держатся MDC в логах, SecurityContextHolder в Spring Security и текущая транзакция в Spring. Отсюда классическая ловушка: код, запущенный в другом потоке — @Async, CompletableFuture.supplyAsync, свой пул, — не видит ни пользователя, ни транзакции вызывающего потока.

  • В пуле потоки живут долго, и значение переживает задачу. Без remove() в finally следующая задача увидит чужой контекст, а память не освободится. Как именно течёт ThreadLocalMap — в теме References.
  • InheritableThreadLocal копирует значение в дочерний поток при его создании. С пулами это не работает: потоки пула созданы заранее.
  • В Java 21 в статусе preview есть ScopedValue — неизменяемый контекст с ограниченной областью жизни, рассчитанный на виртуальные потоки.
  • Поток Java — поток ОС: около 27 мкс на создание и 60–90 КБ памяти в простое. Потоки держат в пулах, задачи передают как Runnable или Callable.
  • start() создаёт поток, и только один раз; run() — обычный вызов в текущем потоке.
  • Состояния: NEW, RUNNABLE (в том числе чтение из сокета), BLOCKED (только вход в synchronized), WAITING, TIMED_WAITING, TERMINATED.
  • Прерывание — кооперативный флаг. InterruptedException сбрасывает его, поэтому его пробрасывают или восстанавливают через interrupt(), но не глотают.
  • JVM ждёт все не-daemon потоки. Daemon-потоки обрываются без finally.
  • Непойманное исключение убивает только свой поток. В пуле после submit() оно живёт в Future и теряется, если не вызвать get().
  • ThreadLocal — копия на поток. На нём живут MDC, security-контекст и транзакции Spring, поэтому они не переходят в другие потоки. В пуле его очищают через remove().

На собеседовании

Чем start() отличается от run()?

start() создаёт новый поток ОС, и уже в нём JVM вызывает run(). Прямой вызов run() — обычный вызов метода: код выполнится в текущем потоке, синхронно. Повторный start() у того же объекта бросает IllegalThreadStateException: закончившийся поток перезапустить нельзя.

В коде: new Thread(this::sendReport).run(); — «отправляем отчёт в фоне». Что не так?

Вызван run(), а не start(), поэтому отчёт отправляется синхронно в текущем потоке, и запрос ждёт отправки. Нужен start(), а лучше — отдать задачу пулу, чтобы не создавать поток на каждый отчёт и не терять исключения.

Какие состояния бывают у потока?

Шесть, из Thread.State. NEW — создан, не запущен. RUNNABLE — выполняется или готов выполняться. BLOCKED — ждёт входа в synchronized. WAITING — ждёт без таймаута: wait(), join(), park(). TIMED_WAITING — то же с таймаутом: sleep, wait(ms). TERMINATED — run() закончился.

  • Чтение из сокета — это RUNNABLE, а не WAITING: Java не различает «на CPU» и «в системном вызове».
  • Ожидание ReentrantLock — WAITING через park(). BLOCKED бывает только у synchronized.
Чем BLOCKED отличается от WAITING?

BLOCKED — поток хочет войти в synchronized, но монитор занят. Он выйдет из этого состояния сам, когда монитор освободят, и прерывание на это не влияет. WAITING — поток сам вызвал ожидание (wait, join, park) и ждёт, пока его разбудят. Это ожидание можно прервать через interrupt().

Как правильно остановить поток?

Через прерывание. Вызывающий делает interrupt(). Поток проверяет флаг isInterrupted() в цикле и завершается сам; блокирующие вызовы вроде sleep, wait и take в ответ бросают InterruptedException. Главное — не глотать это исключение: оно сбрасывает флаг, поэтому его пробрасывают дальше или восстанавливают флаг через Thread.currentThread().interrupt().

Thread.stop() использовать нельзя: он бросал исключение в произвольном месте и оставлял объекты в сломанном состоянии, а в Java 21 просто бросает UnsupportedOperationException.

  • Не прерываются ожидание входа в synchronized и чтение из java.net.Socket в платформенном потоке. Для сокета ставят таймауты или закрывают его из другого потока.
  • ExecutorService.shutdownNow() и Future.cancel(true) работают через тот же interrupt().
while (!isInterrupted()) { try { Thread.sleep(1000); } catch (InterruptedException e) { log.warn("interrupted"); } } — что не так?

InterruptedException сбрасывает флаг, а catch его не восстанавливает. Цикл снова видит «не прерван» и продолжает работу, так что поток нельзя остановить ни interrupt(), ни shutdownNow(). В замере урока пул не остановился за 3 секунды. Нужно добавить в catch Thread.currentThread().interrupt() или выйти из цикла через return.

Чем Runnable отличается от Callable?

Runnable.run() ничего не возвращает и не может бросать checked-исключения. Callable.call() возвращает значение и может бросать любые исключения. Callable отдают пулу через submit() и получают Future. get() вернёт результат или бросит ExecutionException с исходным исключением внутри.

Что такое daemon-поток?

Фоновый поток, которого JVM не ждёт при завершении: процесс заканчивается, когда не осталось обычных потоков. При выходе daemon-поток обрывается сразу, без finally, поэтому ничего важного в нём не делают. Признак задают setDaemon(true) до start(), и он наследуется от создающего потока.

Утилита печатает результат, но процесс не завершается. Что проверить?

Остался живой не-daemon поток: пул, который не закрыли через shutdown(), таймер, клиент с собственными потоками. Дамп потоков (jcmd <pid> Thread.print) покажет, какой поток жив и где он стоит.

Что такое ThreadLocal и какие с ним проблемы?

Переменная, у которой своё значение в каждом потоке. Используют, чтобы дать каждому потоку свой экземпляр непотокобезопасного объекта или чтобы передавать контекст запроса неявно: MDC, пользователь в Spring Security, текущая транзакция.

Проблемы. В пуле потоки переиспользуются, и без remove() в finally значение переходит к следующей задаче и держит память. Контекст не переходит в другие потоки: @Async и CompletableFuture его не видят.

  • Значения хранятся в ThreadLocalMap самого потока: ключ — слабая ссылка на ThreadLocal, значение — сильная.
  • InheritableThreadLocal копирует значение только при создании потока, поэтому с пулами не помогает.
  • ScopedValue (preview в Java 21) — неизменяемая альтернатива с ограниченной областью жизни.
Почему @Transactional-метод, вызванный через CompletableFuture.supplyAsync, не видит транзакцию вызывающего?

Spring привязывает транзакцию к текущему потоку через ThreadLocal. supplyAsync выполняет код в потоке ForkJoinPool.commonPool(), где этого значения нет. Там либо откроется новая транзакция, либо её не будет вовсе.
