Networking: TLS & HTTPS

TLS решает три задачи: никто по дороге не прочитает данные, не изменит их незаметно и не выдаст себя за сервер. Шифрование даёт общий ключ, который стороны вырабатывают в рукопожатии, не передавая его по сети. Подлинность даёт сертификат: сервер показывает цепочку подписей до корня, которому клиент доверяет заранее, и клиент проверяет, что имя в сертификате совпадает с адресом. В TLS 1.3 рукопожатие занимает один круг до сервера. Почти все ошибки TLS в проде — не про шифры, а про доверие: истёкший сертификат, сменённый центр сертификации, имя не то.

Банк сменил сертификат, и все платежи упали с PKIX path building failed

В понедельник утром вызовы банка начали падать с SSLHandshakeException: PKIX path building failed: unable to find valid certification path to requested target. Код не менялся. Банк перевыпустил сертификат у другого центра сертификации, а платёжный сервис жил в контейнере с собственным truststore, куда когда-то вручную положили старый корневой сертификат. Через месяц другая авария: истёк сертификат внутреннего сервиса, и проверка здоровья проходила, потому что ходила по HTTP.

Чтобы разбираться в таких ошибках, нужно понимать, что и в какой момент проверяет TLS. Демо TlsDemo.java делает рукопожатие с реальным сервером, проверяет сертификаты на тестовых хостах badssl.com и поднимает на loopback сервер с взаимной аутентификацией: java TlsDemo.java на JDK 21. Первым двум частям нужен интернет; время рукопожатия снято на машине автора через VPN.

В рукопожатии стороны вырабатывают общий ключ, не передавая его, и TLS 1.3 делает это за один круг

Данные шифруются симметричным алгоритмом вроде AES-GCM: он быстрый, но обеим сторонам нужен один и тот же ключ. Передать ключ открыто нельзя, поэтому стороны вырабатывают его обменом Диффи — Хеллмана на эллиптических кривых (ECDHE). Каждая сторона генерирует временную пару ключей и отправляет только открытую часть, а общий секрет вычисляет сама. Подслушавший видит обе открытые части, но вычислить секрет не может.

Ключи временные, на одно соединение. Если через год украдут закрытый ключ сертификата сервера, записанный трафик всё равно не расшифровать: сертификат только подписывал рукопожатие, а ключ шифрования из него не выводится. Это прямая секретность (forward secrecy). В TLS 1.3 обмен ключами без неё вообще убрали.

try (var tcp = new Socket("example.com", 443)) {      // TCP уже установлен.
    var s = (SSLSocket) factory.createSocket(tcp, "example.com", 443, true);
    s.setEnabledProtocols(new String[] {protocol});     // TLSv1.2 или TLSv1.3.
    long t = System.nanoTime();
    s.startHandshake();                                  // Меряем только TLS.
}
TLSv1.2 TLS_ECDHE_ECDSA_WITH_AES_128_GCM_SHA256 in 621 ms
TLSv1.3 TLS_AES_256_GCM_SHA384 in 373 ms

Рукопожатие несёт ещё две полезные вещи. SNI — имя сервера в ClientHello: на одном IP живут сотни сайтов, и сервер по SNI выбирает, какой сертификат показать. ALPN — договорённость о протоколе поверх TLS: здесь клиент и сервер решают, говорить ли HTTP/2, как разобрано в HTTP/2 & HTTP/3. Возобновление сессии и 0-RTT сокращают повторные рукопожатия, но 0-RTT-данные можно перехватить и повторить, поэтому для POST платежа его не используют.

Сертификат проверяется цепочкой подписей до корня, которому клиент доверяет заранее

Шифрование без проверки собеседника бесполезно: можно зашифрованно поговорить с атакующим. Сертификат связывает открытый ключ с именем домена, и эту связь подписывает центр сертификации (CA). Сервер example.com показал цепочку из четырёх сертификатов:

  cert: CN=example.com <- CN=Cloudflare TLS Issuing ECC CA 3
  cert: CN=Cloudflare TLS Issuing ECC CA 3 <- CN=SSL.com TLS Transit ECC CA R2
  cert: CN=SSL.com TLS Transit ECC CA R2 <- CN=SSL.com TLS ECC Root CA 2022
  cert: CN=SSL.com TLS ECC Root CA 2022 <- CN=AAA Certificate Services
  SAN: [example.com, *.example.com], valid until 2026-12-25

Последний сертификат цепочки подписан старым корнем AAA Certificate Services — это кросс-подпись. Новый корень SSL.com 2022 ещё есть не во всех старых хранилищах, и кросс-подпись позволяет старым клиентам дойти до известного им корня. В Java корни лежат в $JAVA_HOME/lib/security/cacerts. Если образ контейнера собран со своим урезанным truststore, смена банком центра сертификации ломает проверку — та самая авария из первого шага.

Имя проверяется по полю Subject Alternative Name, а не по CN: здесь это example.com и *.example.com. Звёздочка покрывает ровно один уровень: api.example.com подходит, v1.api.example.com — нет. Срок действия сертификатов сокращается: решение CA/Browser Forum 2025 года поэтапно уменьшает его с 398 дней до 47 к 2029 году, так что ручной перевыпуск раз в год перестаёт быть вариантом.

Клиент проверяет срок, имя и путь к корню, и каждая ошибка значит своё

Тестовые хосты badssl.com специально показывают сломанные сертификаты. Демо включает проверку имени так же, как это делает HttpClient:

var params = s.getSSLParameters();
params.setEndpointIdentificationAlgorithm("HTTPS"); // Без этой строки SSLSocket имя не сверяет.
s.setSSLParameters(params);
s.startHandshake();
expired.badssl.com: SSLHandshakeException: validity check failed
wrong.host.badssl.com: SSLHandshakeException: (certificate_unknown) No subject alternative DNS name matching wrong.host.badssl.com found.
self-signed.badssl.com: SSLHandshakeException: unable to find valid certification path to requested target

Три разные причины: срок истёк; сертификат валиден, но выдан другому имени; цепочка не доходит ни до одного доверенного корня. Третья ошибка — та же, что в аварии с банком, только по другой причине. Её лечат добавлением нужного корня или промежуточного CA в truststore, а не отключением проверки.

PKIX path building failed чинится TrustManager, который доверяет всем сертификатам.

Такой TrustManager отключает проверку собеседника, и любой узел по пути может выдать себя за банк и читать платежи. Ещё обратите внимание на строку с setEndpointIdentificationAlgorithm: голый SSLSocket без неё проверяет цепочку, но не имя, и сертификат чужого сайта проходит. HttpClient и RestClient делают эту проверку сами. Правильное исправление — добавить нужный CA в truststore.

В Java различают keystore — свои ключи и сертификаты для представления себя — и truststore — чужие сертификаты, которым доверяешь. В Spring Boot с версии 3.1 оба удобно описываются через SSL bundles: spring.ssl.bundle.jks.bank.truststore.location и ссылка на bundle из настроек сервера или HTTP-клиента. С Boot 3.2 bundle можно перезагружать при обновлении файлов на диске без перезапуска (reload-on-update).

При mTLS сертификат показывает и клиент, и сервер решает, кого пускать

Обычно сертификат показывает только сервер, а клиента опознают паролем или токеном. Банковские API и сервисы внутри кластера часто требуют взаимной аутентификации: клиент тоже показывает сертификат, подписанный CA, которому доверяет сервер. Демо генерирует утилитой keytool две пары ключей, раздаёт каждой стороне сертификат другой и поднимает сервер с setNeedClientAuth(true):

server.setNeedClientAuth(true); // Без сертификата клиента — отказ в рукопожатии.
SSLContext clientCtx = context(dir, withCert ? "client.p12" : null, "client-trust.p12");
client cert=false: SSLHandshakeException: (certificate_required) Received fatal alert: certificate_required
client cert=true: hello CN=client.payments.test

Без сертификата клиент не прошёл рукопожатие: сервер ответил фатальным сигналом certificate_required, до HTTP дело не дошло. С сертификатом сервер знает клиента по имени из сертификата и может принимать решения по нему. В Spring Security это x509(), который превращает сертификат клиента в Authentication.

mTLS переносит сложность в управление сертификатами: кто их выпускает, как часто обновляет, как отзывает. Внутри кластера это обычно делает service mesh: Istio или Linkerd выдают каждому pod-у сертификат на часы и обновляют автоматически, а sidecar устанавливает mTLS вместо приложения. Для внешнего банка сертификат клиента выдаёт банк, и его срок — ещё одна дата, за которой нужно следить.

В проде TLS ломается сроками, завершением на балансировщике и отзывом

Самая частая авария с TLS — истёкший сертификат. Она неожиданна, потому что всё работало ровно до определённой секунды. Защита — автоматический выпуск и обновление (ACME, cert-manager в Kubernetes) и мониторинг срока каждого сертификата, в том числе клиентских и внутренних, с алертом за несколько недель.

TLS часто завершается на балансировщике: он расшифровывает трафик и передаёт его приложению по HTTP внутри сети. Это просто, но трафик внутри кластера идёт открыто, а приложение не знает исходного протокола — его передают заголовком X-Forwarded-Proto, как разобрано в How a Request Travels. Для платёжных данных внутри сети используют повторное шифрование от балансировщика до pod-а или mTLS через mesh.

Отзыв сертификатов работает плохо. Списки отзыва большие, онлайн-проверка OCSP медленная и при недоступности обычно пропускается. Поэтому на практике полагаются на короткий срок действия: украденный ключ перестанет работать вместе с сертификатом. HSTS — заголовок Strict-Transport-Security — запрещает браузеру ходить на домен по HTTP, закрывая атаку с перехватом первого незашифрованного запроса.

  • TLS даёт шифрование, целостность и подлинность; ключ шифрования вырабатывается ECDHE и не передаётся.
  • TLS 1.3 тратит на рукопожатие один круг вместо двух: в демо 373 мс против 621.
  • Клиент проверяет цепочку подписей до корня из своего truststore, срок и имя в SAN.
  • PKIX path building failed — нет пути к доверенному корню; лечится нужным CA в truststore, а не доверием ко всем.
  • mTLS требует сертификат клиента; главная работа — выпуск, обновление и мониторинг сроков.

На собеседовании

Как работает TLS-рукопожатие?

В TLS 1.3 клиент отправляет ClientHello с поддерживаемыми шифрами и своей временной частью ключа ECDHE. Сервер отвечает ServerHello со своей частью, сертификатом, подписью рукопожатия и Finished. Обе стороны вычисляют общий секрет, из которого получают симметричные ключи, и дальше данные шифруются AES-GCM или ChaCha20. Это один круг до сервера; в TLS 1.2 — два.

Клиент проверяет сертификат сервера: цепочку до доверенного корня, срок и имя.

  • Временные ключи дают прямую секретность: кража ключа сертификата не раскрывает записанный трафик.
  • SNI выбирает сертификат на общем IP, ALPN согласует HTTP/2.
  • 0-RTT при возобновлении экономит круг, но данные можно повторить, поэтому только для идемпотентных запросов.

Что значит PKIX path building failed и как это исправить?

Java не смогла построить цепочку подписей от сертификата сервера до корня из своего truststore. Причины: сервер не отправил промежуточный сертификат, сертификат подписан корпоративным или новым CA, которого нет в cacerts, или образ собран с урезанным truststore.

Исправление — добавить нужный корень или промежуточный CA в truststore приложения, например через SSL bundle в Spring Boot. Отключать проверку TrustManager-ом «доверять всем» нельзя: это открывает подмену сервера.

  • Голый SSLSocket без EndpointIdentificationAlgorithm=HTTPS не проверяет имя; HttpClient проверяет.
  • Keystore — свои ключи, truststore — чужие сертификаты, которым доверяешь.
  • openssl s_client -showcerts показывает, какую цепочку реально отдаёт сервер.

Что такое mTLS и где он используется?

Взаимная аутентификация: сертификат показывает не только сервер, но и клиент, а сервер проверяет его по своему truststore. Без сертификата клиент не проходит рукопожатие — в демо сервер ответил certificate_required. Используется в банковских API и между сервисами внутри кластера.

Внутри кластера mTLS обычно делает service mesh: выдаёт pod-ам короткоживущие сертификаты и устанавливает соединения в sidecar.

  • Главная сложность — жизненный цикл сертификатов: выпуск, обновление, мониторинг сроков.
  • Spring Security x509() превращает сертификат клиента в Authentication.
  • Отзыв работает плохо, поэтому полагаются на короткий срок действия.
Что опасного в этом «исправлении» ошибки сертификата? 
TrustManager[] trustAll = { new X509TrustManager() {
    public void checkClientTrusted(X509Certificate[] c, String a) {}
    public void checkServerTrusted(X509Certificate[] c, String a) {} // Ничего не проверяем.
    public X509Certificate[] getAcceptedIssuers() { return new X509Certificate[0]; }
}};
SSLContext ctx = SSLContext.getInstance("TLS");
ctx.init(null, trustAll, null);

Клиент принимает любой сертификат, в том числе самоподписанный от атакующего. Шифрование остаётся, но собеседник не проверен: узел по пути выдаёт себя за банк и видит все платежи. Обычно такой код приходит из ответа на форуме «как исправить PKIX» и попадает в прод. Правильно — добавить сертификат CA банка в truststore этого клиента.
