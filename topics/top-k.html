Heap & Top-K

Куча полезна, когда следующий шаг зависит от одной границы набора. Для K наибольших она хранит худший из выбранных: больший входящий элемент вытесняет именно его. Для слияния источников она хранит лучший из ещё доступных голов. Для медианы две кучи разделяют значения на нижнюю и верхнюю половины, а их корни дают середину. Форма heap здесь уже известна; задача — доказать, что нужная граница действительно находится в корне.

Для K лучших достаточно хранить худшего из сохранённых

Платёжный сервис прочитал миллионы сумм и хочет показать три наибольших. Можно сохранить все числа, отсортировать за O(n log n) и взять последние три. Для непрерывного потока такое решение копит весь вход, хотя почти все значения в ответ не попадут.

Оставим только K лучших прочитанного префикса. Пока мест меньше K, добавляем очередное значение. Затем корень должен представлять наименьшее из сохранённых, поэтому для K наибольших нужна min-heap. Если новое значение больше корня, заменяем корень. Иначе оно не улучшает набор и пропускается.

Инвариант после каждого шага: heap содержит min(K, число прочитанных) наибольших значений префикса с учётом повторов. Когда мест уже K, новое число не больше корня хуже или равно всем выбранным, его безопасно отбросить. Если больше, единственный элемент, который нужно вытеснить, — прежний минимум. На его место входит новое число; остальные K−1 остаются лучшими.

Устройство sift и heapify подробно дано в Heaps. Здесь опыты из examples/top-k запускаются на JDK 21 без сборки, например java TopDemo.java. Трасса TopDemo.java сортирует диагностическую копию выбранных значений:

static PriorityQueue<Integer> select(int[] values, int k, boolean trace) {
    if (k < 0 || k > values.length) throw new IllegalArgumentException("k outside [0,n]");
    PriorityQueue<Integer> kept = new PriorityQueue<>(); // Минимум — худший из K наибольших.
    if (k == 0) return kept; // Не читаем peek у пустой кучи.
    for (int value : values) {
        String action;
        if (kept.size() < k) { kept.add(value); action = "fill"; }
        else if (value > kept.peek()) { kept.remove(); kept.add(value); action = "replace"; }
        else action = "skip"; // Существующий равный элемент уже даёт тот же top-K значений.
        if (trace) {
            List<Integer> ordered = new ArrayList<>(kept); Collections.sort(ordered);
            System.out.println("value=" + value + " action=" + action + " kept=" + ordered + " root=" + kept.peek());
        }
    }
    return kept;
}

static List<Integer> descending(PriorityQueue<Integer> heap) {
    List<Integer> result = new ArrayList<>(heap); result.sort(Comparator.reverseOrder()); return result;
}

В конце корень 4 — третий по величине элемент, хотя в ответе по убыванию он последний. Max-heap размером K показывала бы лучший выбранный, а для замены нужен худший. Для K наименьших ориентация обратная: max-heap хранит самую большую из оставленных величин.

Отбор требует O(n log(K+1)) времени и O(K) памяти; при K=1 это O(n), а не «O(n log1)=0». Полная выдача K значений по убыванию стоит ещё O(K log K): в примере отдельно сортируется копия результата. Для одного K-го достаточно peek, когда прочитано не меньше K элементов.

Позиция в порядке учитывает повторы, а равенство объектов требует своей политики

K-й наибольший означает элемент на позиции K в упорядоченной последовательности. Он не означает K-е различное значение. Для 9,9,8,7 третий —8; если сначала убрать повторы, получится 7. PriorityQueue хранит повторяющиеся значения, поэтому обычная ограниченная куча решает именно задачу о позициях.

При равном входящем значении можно оставить уже выбранную копию: мультимножество сумм не изменится. Если элементы — платежи с идентификаторами, выбор копии становится частью требований. Равная сумма не означает тот же платёж. Определи порядок, например сначала по сумме, потом по идентификатору или времени; этот полный порядок должен использоваться и при решении о замене, и внутри heap.

Для «всех платежей не ниже K-й суммы» размер ответа может превысить K: на границе бывает много равных. Ограниченная куча на K местах сама не хранит отброшенные равные объекты. Сначала уточни, нужны ровно K записей, одно пороговое значение или весь набор по этому порогу.

Сравнивай через Integer.compare или Comparator.comparingInt, не через a−b: крайние int переполняют разность. Значимые поля объекта нельзя менять, пока он находится в куче: heap не перестроится от записи в поле. Итерация по PriorityQueue не выдаёт отсортированный результат; правила API остаются в теме Heaps.

Слияние хранит по одной голове каждого незавершённого источника

Три банка отдают страницы платежей, уже отсортированные по одному ключу. Нужно объединить их в один порядок. Сложить все N записей и заново сортировать можно за O(N log N), но готовый порядок источников тогда не используется. Попарно искать минимум среди всех M голов на каждый вывод стоило бы O(NM).

В min-heap кладём первую запись каждого непустого источника. У отсортированного источника все скрытые записи не меньше его головы. Поэтому минимум среди голов — минимум вообще среди ещё не выданного. После извлечения заменяем голову только того источника, из которого пришёл победитель. Остальные головы остаются актуальными.

Инвариант: от каждого незавершённого источника в heap ровно одна запись, его первая не выданная. Heap охватывает границу между готовым результатом и скрытыми хвостами. Cursor хранит значение, источник и индекс: одного значения недостаточно, чтобы узнать, какой хвост открыть следующим.

Фрагменты MergeDemo.java. Массивы моделируют доступные отсортированные источники; ties разрешаем по номеру источника. Для связанных списков меняется способ продвижения головы, сама граница остаётся прежней:

record Cursor(int value, int source, int index) {}
static final Comparator<Cursor> ORDER = Comparator.comparingInt(Cursor::value)
        .thenComparingInt(Cursor::source).thenComparingInt(Cursor::index); // Равные значения: порядок источников.
static List<Integer> merge(int[][] sources, boolean trace) {
    PriorityQueue<Cursor> heads = new PriorityQueue<>(ORDER);
    for (int source = 0; source < sources.length; source++)
        if (sources[source].length != 0) heads.add(new Cursor(sources[source][0], source, 0));
    List<Integer> result = new ArrayList<>();
    while (!heads.isEmpty()) {
        Cursor head = heads.remove(); result.add(head.value());
        int next = head.index() + 1;
        if (next < sources[head.source()].length)
            heads.add(new Cursor(sources[head.source()][next], head.source(), next)); // Продвинули только победивший источник.
        if (trace) {
            List<Cursor> ordered = new ArrayList<>(heads); ordered.sort(ORDER);
            System.out.println("take=" + head.value() + " source=" + head.source() + " index=" + head.index() + " heads=" + ordered);
        }
    }
    return result;
}

Пусть M — число всех источников, r — число непустых, N — число всех записей. Сканирование первых элементов стоит O(M), затем каждая запись извлекается один раз из heap размером не больше r. Время O(M+N log(r+1)), память heap O(r). Показанный ответ List занимает O(N); запись в выходной поток убирает необходимость хранить весь результат. Нельзя назвать память O(r), оставив в коде растущий List и не упомянув его отдельно.

У источника [5,1] меньшая 1 была скрыта за 5. Алгоритм честно выдал 2,3,5 и только потом увидел 1: результат не отсортирован. Гарантия порядка каждого источника нужна до запуска, а одинаковый Comparator должен использоваться по всей цепочке. На сетевых потоках также требуется знать текущую голову каждого активного источника либо иметь доказанную нижнюю границу его будущих записей. Сам heap не позволяет безопасно угадать данные задержавшегося банка.

Две кучи поддерживают порядок половин и нужное число элементов в каждой

Теперь после каждого платежа нужна медиана всех сумм с начала наблюдения. Одна min-heap даёт минимум, а не середину; сортировка каждого префикса повторяет работу. Разделим мультимножество на low и high: low хранит нижнюю половину как max-heap, high верхнюю как min-heap.

Поддерживаем два независимых условия. Порядок: каждый элемент low ≤ каждого элемента high. Размер: low.size равен high.size либо больше на 1. При нечётном количестве медиана — максимум low. При чётном — среднее максимума low и минимума high. Один баланс размеров без порядка ещё не даёт медиану.

Новое число не выше low.peek идёт в low, больше — в high. Это сохраняет порядок раздела. Если low стал слишком большим, переносим его максимум в high; если high больше, переносим её минимум в low. Переносим именно граничный элемент, поэтому порядок между половинами сохраняется. Одно добавление нарушает баланс не больше чем на одну лишнюю переносимую запись.

Фрагменты MedianDemo.java. State сортирует копии половин только для печати; в low первая величина — максимум, в high — минимум:

static final class Median {
    final PriorityQueue<Integer> low = new PriorityQueue<>(Comparator.reverseOrder());
    final PriorityQueue<Integer> high = new PriorityQueue<>();
    void add(int value) {
        if (low.isEmpty() || value <= low.peek()) low.add(value); // Нижняя половина хранит максимум в корне.
        else high.add(value);
        if (low.size() > high.size() + 1) high.add(low.remove());
        else if (low.size() < high.size()) low.add(high.remove()); // Low содержит один лишний при нечётной длине.
    }
    double value() {
        if (low.isEmpty()) throw new NoSuchElementException("empty stream");
        return low.size() == high.size()
            ? ((long) low.peek() + high.peek()) / 2.0 // Расширяем до сложения: int может переполниться.
            : low.peek();
    }
    String state() {
        List<Integer> a = new ArrayList<>(low), b = new ArrayList<>(high);
        a.sort(Comparator.reverseOrder()); Collections.sort(b);
        return "low=" + a + " high=" + b;
    }
}

У пустого потока медианы нет, API демо бросает NoSuchElementException. Добавление стоит O(log n), запрос O(1), память обеих куч O(n), где n — число сохранённых значений. Это точная медиана всего префикса, и её память растёт вместе с историей. «Потоковый алгоритм» не означает ограниченную память.

Ограниченный top-K, граница слияния и точная медиана хранят разное прошлое

Назови нужный ответ до выбора heap. В top-K можно навсегда отбросить значение ниже текущего порога, если K фиксирован и прочитанные значения не удаляются. При слиянии нужно лишь удержать доступную голову каждого отсортированного хвоста. Для точной медианы префикса нужны обе половины и вся накопленная история.

K наибольшихХудший сохранённый минимумO(K)
Слияние M источниковЛучшая текущая головаO(r) непустых источников

Для одной конечной пачки, которую нужно целиком выдать по порядку, сортировка проще. Для одного K-го в доступном массиве можно использовать quickselect: ожидаемое O(n) время при подходящем выборе pivot, возможная перезапись входа и худший O(n²) у обычной версии. Ограниченная куча даёт O(n log(K+1)) и подходит потоку без доступа к прежним значениям. Основы partition разобраны в Quick Sort.

При увеличении K после отбрасывания истории потерянные элементы не восстановятся из прежней маленькой кучи. Если запросы меняют K произвольно, нужно хранить больше данных или использовать структуру порядковых статистик. Для top-K по частоте сначала требуется счётчик каждого различного значения: память карты O(u), где u — число различных ключей. Heap на K местах не отменяет эту карту.

Когда локальные top-K можно объединить

Если разные части содержат разные записи и используют один полный порядок, глобальный top-K входит в объединение локальных top-K. Запись вне локального набора уже имеет перед собой K записей своей части, поэтому не может попасть в глобальные K. Можно собрать локальные результаты и снова выбрать top-K.

Это не переносится автоматически на частоты одного ключа, разделённые по узлам. У ключа умеренная частота в каждой части может сложиться в глобальный максимум, хотя локальные heap его отбросили. Требуется объединять счётчики либо выбирать иной алгоритм с явно заданными гарантиями.

Для медианы только последних W платежей нужно удалять истёкшие значения. PriorityQueue.remove(Object) ищет объект линейно; базовая вставка в две кучи не решает задачу удаления. Ленивая очистка требует отдельного учёта логических размеров и истёкших элементов, а скрытые записи могут накапливаться без политики очистки. Другой вариант — дерево со счётчиками и порядковыми статистиками. Эти варианты не смешиваем с доказательством медианы всего префикса.

На собеседовании покажи, какая величина лежит в корне, почему следующий элемент может изменить именно её и какое состояние разрешено забыть. Затем проверь повторы, пустой вход, допустимость K, крайние числа и размер сохраняемой истории. Если вывод выглядит отсортированным, объясни, откуда взялся этот порядок: poll, отдельная сортировка или порядок источников.

  • Для K наибольших нужна min-heap: её корень — худший среди сохранённых.
  • K-й учитывает повторяющиеся элементы. Ровно K записей и все записи на пороге — разные ответы.
  • K-way merge хранит по одной голове и продвигает только выбранный источник.
  • У медианы нужны порядок половин и баланс размеров; сумма корней расширяется до сложения.
  • Top-K хранит O(K), слияние O(r), точная медиана префикса O(n). Память возвращаемого результата добавляется отдельно.

Решение

После каждого шага heap хранит K лучших прочитанного префикса, либо весь короткий префикс. Когда прочитаны все значения, минимум этих K и есть K-й наибольший.

static int solve(int[] values, int k) {
    PriorityQueue<Integer> kept = new PriorityQueue<>();
    for (int value : values) {
        if (kept.size() < k) kept.add(value);
        else if (value > kept.peek()) { kept.remove(); kept.add(value); }
    }
    return kept.peek(); // Вход обещает 1 <= k <= n.
}

Подсказка 2

Cursor хранит value, source и index. После извлечения добавь следующий элемент только этого source; у закончившегося источника новой головы нет.

Решение

Heap содержит границу слияния: по одной первой не выданной записи каждого источника. Минимальная голова выдаётся, затем её место занимает следующий элемент того же массива.

static List<Integer> solve(int[][] sources) {
    PriorityQueue<Cursor> heads = new PriorityQueue<>(ORDER);
    for (int source = 0; source < sources.length; source++)
        if (sources[source].length != 0) heads.add(new Cursor(sources[source][0], source, 0));
    List<Integer> result = new ArrayList<>();
    while (!heads.isEmpty()) {
        Cursor head = heads.remove(); result.add(head.value());
        int next = head.index() + 1;
        if (next < sources[head.source()].length)
            heads.add(new Cursor(sources[head.source()][next], head.source(), next)); // Продвинули только победивший источник.

    }
    return result;
}

Подсказка 2

Low содержит столько же, сколько high, либо на 1 больше. После вставки перенеси граничный элемент из слишком большой половины. При чётной длине приведи корень к long до сложения.

Решение

Два корня ограничивают середину. Баланс оставляет лишний элемент в low, поэтому при нечётной длине берётся low.peek; при чётной — среднее обоих корней.

static double[] solve(int[] values) {
    PriorityQueue<Integer> low = new PriorityQueue<>(Comparator.reverseOrder());
    PriorityQueue<Integer> high = new PriorityQueue<>();
    double[] result = new double[values.length];
    for (int i = 0; i < values.length; i++) {
        int value = values[i];
        if (low.isEmpty() || value <= low.peek()) low.add(value); // Новое число выбирает половину по её границе.
        else high.add(value);
        if (low.size() > high.size() + 1) high.add(low.remove());
        else if (low.size() < high.size()) low.add(high.remove()); // При нечётной длине лишний элемент остаётся в low.
        result[i] = low.size() == high.size()
            ? ((long) low.peek() + high.peek()) / 2.0 : low.peek(); // Расширение до сложения защищает от переполнения int.
    }
    return result;
}
