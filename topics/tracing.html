Tracing

Распределённая трасса — дерево спанов одного запроса через все сервисы: у каждого спана имя, время начала, длительность, атрибуты и ссылка на родителя. Связывает спаны разных процессов контекст, который передаётся в заголовке W3C traceparent: идентификатор трассы и идентификатор родительского спана. В демо трасса показала, что из 312 мс оформления 255 мс ушло на ожидание платёжного провайдера. Если хоть один сервис не передаёт заголовок, трасса рвётся на две несвязанные, и путь запроса уже не восстановить. Трассы дорогие, поэтому их выбирают: решение принимает первый сервис, а остальные следуют решению родителя, — тогда сохраняются целые трассы: из 200 запросов при 10 % — 19 полных трасс и ни одного обрывка.

Оформление заказа медленное, а каждый сервис говорит «у меня всё быстро»

p99 оформления заказа — 300 мс при цели 150. Команда шлюза смотрит свои метрики: шлюз отвечает быстро, ждёт заказы. Команда заказов: запрос к базе 35 мс, остальное ждём платежи. Команда платежей: сами мы почти ничего не делаем, ждём провайдера. Каждый прав, а общей картины нет. Трасса показывает одним деревом, кто кого вызвал и сколько ждал.

Тема разбирает устройство трассы, передачу контекста и выборку. Демо TracingDemo.java запускает три сервиса на JDK HttpServer, инструментированных OpenTelemetry Java SDK 1.55 вручную, и экспортирует спаны по OTLP в Jaeger 2.10 в Docker. Затем демо забирает трассы через API Jaeger и печатает их деревом. Обзор сигналов — в Observability Overview, метрики — в Metrics.

Трасса — дерево спанов, где видно, куда ушло время

// Сервер: достать контекст из traceparent, открыть серверный span, выполнить работу.
Context parent = W3C.extract(Context.root(), ex, GETTER);
Span span = t.spanBuilder("GET " + path).setParent(parent).setSpanKind(SpanKind.SERVER).startSpan();
try (Scope ignored = span.makeCurrent()) { w.run(path); }
finally { span.end(); }

// Клиент: клиентский span и traceparent в заголовке исходящего запроса.
Span span = t.spanBuilder("call " + path).setSpanKind(SpanKind.CLIENT).startSpan();
try (Scope ignored = span.makeCurrent()) {
    var b = HttpRequest.newBuilder(URI.create("http://localhost:" + port + path));
    W3C.inject(Context.current(), b, (req, k, v) -> req.header(k, v));
    http.send(b.build(), HttpResponse.BodyHandlers.discarding());
} finally { span.end(); }

Спан описывает одну операцию: входящий запрос (SERVER), исходящий вызов (CLIENT), запрос к базе, отправку в брокер (PRODUCER и CONSUMER), внутреннюю работу. Атрибуты по семантическим соглашениям OpenTelemetry — http.request.method, db.system, messaging.destination.name — делают трассы разных сервисов сравнимыми. Ошибки пишут в спан как события и статус ERROR. В реальных сервисах вручную спаны почти не создают: Java-агент OpenTelemetry или Micrometer Tracing в Spring Boot инструментирует HTTP-серверы, клиенты, JDBC, Kafka и Redis автоматически, а вручную добавляют только бизнес-операции.

Сервис orders вызвал payments, не добавив traceparent. Payments не нашёл контекста и начал новую трассу. В Jaeger теперь две трассы: в первой 5 спанов и вызов payments, обрывающийся без продолжения, во второй — 2 спана payments без родителя. По времени их ещё можно сопоставить на тестовом стенде, но в продакшене одновременно идут тысячи запросов. Контекст теряется в самописных HTTP-клиентах, при переходе в другой поток без переноса контекста — как MDC в Observability Overview, — в сообщениях брокера без заголовков и в фоновых задачах. Автоинструментирование закрывает типичные клиенты; самописные места проверяют тестом, который ищет разрывы трасс.

Через асинхронные границы контекст передают в заголовках сообщения: продюсер Kafka кладёт traceparent в заголовки записи, потребитель создаёт спан со ссылкой на него. Для пакетной обработки, где одно сообщение порождает работу над сотней других, вместо родителя используют span links — ссылки на несколько трасс.

Выборка: решает первый сервис, остальные следуют

// Решение о выборке принимает первый сервис; остальные следуют решению родителя.
Tracer gw = tracer("gateway", Sampler.parentBased(Sampler.traceIdRatioBased(0.1)));
Tracer orders = tracer("orders", Sampler.parentBased(Sampler.alwaysOn()));
Tracer payments = tracer("payments", Sampler.parentBased(Sampler.alwaysOn()));
== 200 requests, gateway samples 10%, others follow the parent
   traces stored: 19, complete with all 7 spans: 19
   payments spans without their gateway trace: 0

Сохранять каждую трассу дорого: на тысячах запросов в секунду трассы занимают больше места, чем логи. Шлюз выбирает 10 % по идентификатору трассы — в этом прогоне 19 из 200, число меняется от запуска к запуску. Решение передаётся флагом в traceparent, и orders и payments с parentBased следуют ему: все 19 трасс полные, по 7 спанов, и ни одного спана payments без своей трассы. Если бы каждый сервис выбирал независимо по 10 %, полной трассой через три сервиса оказалась бы лишь тысячная доля запросов, а остальное — обрывки.

Выборка в начале (head sampling) не знает, будет ли запрос интересным: медленный запрос или ошибка с вероятностью 90 % не сохранятся. Выборка в конце (tail sampling) в OpenTelemetry Collector держит спаны трассы в памяти до её завершения и сохраняет все ошибки и медленные трассы плюс долю обычных. Это точнее, но требует коллектора, который видит все спаны трассы. Практичная комбинация — небольшая доля обычных трасс, все ошибки и медленные, и связь с метриками через exemplars: точка на графике p99 ведёт к конкретной трассе.

Если в каждом сервисе включить выборку 10 %, сохранится 10 % трасс.

Независимая выборка в трёх сервисах сохраняет полной трассу лишь 0,1 % запросов, остальное — обрывки. С parentBased решение первого сервиса наследуется: в демо 19 из 200 трасс, все с 7 спанами, ни одного спана без трассы.

Трассировка в Java-сервисе: агент, Spring Boot и связь с логами

# Java-агент OpenTelemetry: инструментирование без изменения кода
java -javaagent:opentelemetry-javaagent.jar \
     -Dotel.service.name=orders \
     -Dotel.exporter.otlp.endpoint=http://otel-collector:4318 \
     -Dotel.traces.sampler=parentbased_traceidratio -Dotel.traces.sampler.arg=0.1 \
     -jar orders.jar
# Spring Boot 3: Micrometer Tracing с мостом в OpenTelemetry
management:
  tracing:
    sampling:
      probability: 0.1
  otlp:
    tracing:
      endpoint: http://otel-collector:4318/v1/traces
logging:
  pattern:
    correlation: "[${spring.application.name:},%X{traceId:-},%X{spanId:-}] "

Агент подключается при запуске JVM и через инструментирование байткода создаёт спаны для HTTP-серверов и клиентов, JDBC, Kafka, Redis, gRPC — то, что демо делало руками. Настройки передают системными свойствами или переменными окружения OTEL_*, одинаковыми для всех языков. В Spring Boot 3 трассировку даёт Micrometer Tracing с мостом в OpenTelemetry: он создаёт спаны для входящих запросов, RestClient, WebClient, KafkaTemplate и кладёт traceId и spanId в MDC. Шаблон логов выше добавляет их в каждую строку, и по trace id из Jaeger находятся логи всех сервисов этого запроса.

Спаны отправляют не прямо в хранилище, а в OpenTelemetry Collector рядом с сервисами: он буферизует, повторяет отправку, обогащает атрибутами окружения, делает tail sampling и пересылает в Jaeger, Tempo или облачный сервис. Отказ хранилища трасс не должен влиять на сервис: экспорт асинхронный, пачками через BatchSpanProcessor, а при переполнении буфера спаны отбрасываются, а не блокируют запросы.

Накладные расходы трассировки — создание объектов спанов, запись атрибутов, сериализация и отправка. Для обычного HTTP-сервиса это доли процента CPU, но спан на каждую итерацию цикла или на каждый вызов кеша в горячем пути заметен и бесполезен. Ручные спаны ставят на операции, длительность которых интересна при разборе: обращение к внешнему провайдеру, тяжёлый расчёт, ожидание блокировки.

  • Трасса — дерево спанов через сервисы; в демо 255 мс из 312 — ожидание провайдера в payments.
  • Разница клиентского и серверного спана (~18 мс) показывает время в сети и очередях, невидимое сервисам.
  • Контекст передаётся заголовком traceparent; один сервис без него — две несвязанные трассы.
  • Контекст переносят в потоки, сообщения брокера и фоновые задачи; автоинструментирование закрывает типичные клиенты.
  • parentBased-выборка: 19 полных трасс из 200 при 10 %, без обрывков; tail sampling сохраняет ошибки и медленные.
  • В сервисах — Java-агент или Micrometer Tracing, экспорт через Collector, trace id в каждой строке лога.

На собеседовании

Как работает распределённая трассировка?

Каждая операция — спан с идентификатором трассы, своим идентификатором, родителем, временем и атрибутами. При исходящем вызове контекст — trace id и id текущего спана — передаётся в заголовке traceparent; принимающий сервис создаёт дочерний спан. Спаны экспортируются в коллектор и хранилище (Jaeger, Tempo), где собираются в дерево. Инструментирование — Java-агент OpenTelemetry или Micrometer Tracing.

  • Разрывы контекста: самописные клиенты, пулы потоков, сообщения без заголовков.
  • Span links для пакетной обработки.
  • Trace id в логах связывает трассы и логи.
Почему в Jaeger трасса заказа обрывается на orders? 
// orders, после сохранения заказа
executor.submit(() -> {
    var req = HttpRequest.newBuilder(URI.create(paymentsUrl)).POST(body).build();
    rawHttpClient.send(req, BodyHandlers.ofString());   // свой HttpClient, без инструментирования
});

Вызов уходит в пул потоков, куда текущий контекст трассы не переносится, и через самописный клиент, который не добавляет traceparent. Payments начинает новую трассу. Нужно обернуть пул в Context.taskWrapping(executor) или использовать инструментированный клиент и при ручном вызове вставлять контекст пропагатором.

Как выбирать, какие трассы сохранять?

Head sampling: первый сервис решает по доле, решение передаётся флагом в traceparent, остальные следуют родителю — сохраняются целые трассы. Tail sampling в коллекторе: решение после завершения трассы, можно сохранить все ошибки и медленные запросы. Независимая выборка в каждом сервисе даёт обрывки.

  • Tail sampling требует, чтобы все спаны трассы попали на один экземпляр коллектора.
  • Exemplars связывают точку метрики с конкретной трассой.

Чем трассы полезнее логов и метрик для поиска медленного места?

Метрики показывают, что медленно и где в среднем, но не связывают сервисы в один запрос. Логи подробны, но разбросаны по сервисам. Трасса показывает один запрос целиком: кто кого вызвал, что шло последовательно, что параллельно, сколько ждал каждый вызов, включая время в сети между клиентским и серверным спаном.

  • Последовательные вызовы, которые можно распараллелить, видны как лестница спанов.
  • N+1 виден как сотни одинаковых спанов к базе под одним запросом.
