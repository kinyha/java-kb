Trees

Дерево сокращает поиск, когда выбор ветки позволяет отбросить целую группу записей. В дереве поиска ветку задаёт порядок ключей, в B-дереве один узел разделяет сразу несколько диапазонов, а в trie путь задают части самого ключа. Скорость зависит от длины пути: обычное двоичное дерево может вытянуться в цепочку. Балансировка сохраняет короткие пути после изменений, не нарушая правило поиска.

Порядок ключей позволяет пропускать целые поддеревья

Платёжный сервис ищет результат по номеру платежа. Теперь нужен и другой запрос: показать платежи с номерами от 5 до 11, найти ближайший номер к 9, отдать записи по возрастанию. Хеш-таблица быстро находит точный ключ, но её бакеты не задают порядок. Для диапазона пришлось бы просмотреть все записи или построить ещё один индекс.

Двоичное дерево поиска, binary search tree, BST, хранит в узле ключ, значение и две ссылки: left и right. У узла не больше двух детей. Все ключи левого поддерева меньше его ключа, все ключи правого — больше. Это правило действует рекурсивно в каждом узле. Проверить только двух соседей недостаточно: дальний потомок тоже должен укладываться в границы всех предков.

При поиске сравниваем ключ с текущим узлом. Равенство завершает поиск. Меньший ключ отправляет влево, больший — вправо. Вторая ветка целиком исключается: там не может быть нужного номера. Пустая ссылка означает отсутствие. Вставка идёт тем же путём и ставит новый узел на месте пустой ссылки; равный ключ обновляет значение.

Фрагменты BstDemo.java, JDK 21. Учебная таблица хранит int-ключи; поэтому порядок выражен обычными сравнениями. Поле path записывает посещённые узлы:

static final class Node {
    int key;
    String value;
    Node left, right;
    Node(int key, String value) { this.key = key; this.value = value; }
}
static final class Tree {
    Node root;
    final List<Integer> path = new ArrayList<>();

    void put(int key, String value) { root = put(root, key, value); }
    Node put(Node node, int key, String value) {
        if (node == null) return new Node(key, value);
        if (key < node.key) node.left = put(node.left, key, value);
        else if (key > node.key) node.right = put(node.right, key, value);
        else node.value = value; // Равный ключ обновляет запись.
        return node;
    }
    String get(int key) {
        path.clear();
        for (Node node = root; node != null;) {
            path.add(node.key);
            if (key == node.key) return node.value;
            node = key < node.key ? node.left : node.right;
        }
        return null;
    }
}

static Tree payments() {
    var tree = new Tree();
    for (int id : new int[]{8, 4, 12, 2, 6, 10, 14, 5, 7}) tree.put(id, "P" + id);
    return tree;
}

Любое двоичное дерево автоматически даёт быстрый поиск.

«Двоичное» ограничивает число детей, «поиска» добавляет порядок. Даже правильный BST может стать длинной цепочкой. Стоимость поиска — O(h), где h — высота; логарифм появляется только при подходящей форме дерева.

Обход и удаление опираются на порядок поддеревьев

Чтобы вывести платежи по возрастанию, сначала обходим левую ветку, затем обрабатываем текущий узел, затем правую. Это inorder, симметричный обход. К моменту обработки узла все меньшие ключи уже выданы, а большие ещё впереди. Отсортированный результат получается из инварианта BST, а не из дополнительной сортировки.

У preorder текущий узел идёт перед детьми: удобно сначала обработать родителя или записать структуру. У postorder он идёт после детей: удобно сначала собрать результаты поддеревьев. Эти три обхода идут в глубину, DFS. Обход по уровням, BFS, использует очередь: выдаёт корень, затем его детей, затем следующий уровень. Один порядок ключей не заменяет другой порядок обработки.

List<Integer> walk(String order) {
    var result = new ArrayList<Integer>();
    walk(root, order, result);
    return result;
}
void walk(Node node, String order, List<Integer> result) {
    if (node == null) return;
    if (order.equals("pre")) result.add(node.key);
    walk(node.left, order, result);
    if (order.equals("in")) result.add(node.key);
    walk(node.right, order, result);
    if (order.equals("post")) result.add(node.key);
}
List<Integer> breadthFirst() {
    var result = new ArrayList<Integer>();
    var queue = new ArrayDeque<Node>();
    if (root != null) queue.add(root);
    while (!queue.isEmpty()) {
        Node node = queue.remove();
        result.add(node.key);
        if (node.left != null) queue.add(node.left);
        if (node.right != null) queue.add(node.right);
    }
    return result;
}

Для диапазона [low, high] берём тот же inorder и пропускаем лишние ветки. Если low не меньше текущего ключа, искать влево незачем. Если high не больше текущего ключа, искать вправо незачем. Остаток обхода выдаёт только подходящие номера:

List<Integer> range(int low, int high) {
    var result = new ArrayList<Integer>();
    range(root, low, high, result);
    return result;
}
void range(Node node, int low, int high, List<Integer> result) {
    if (node == null) return;
    if (low < node.key) range(node.left, low, high, result);
    if (low <= node.key && node.key <= high) result.add(node.key);
    if (node.key < high) range(node.right, low, high, result);
}

Полный обход посещает n узлов и стоит O(n). Рекурсивный DFS хранит путь вызовов, O(h) дополнительной памяти. У BFS память зависит от максимальной ширины дерева и в худшем случае достигает O(n). Поиск диапазона с k результатами стоит O(h + k): нужно дойти до его границ и выдать сами записи. У сбалансированного BST это O(log n + k), а не O(log n) для выдачи любого количества платежей.

Две ветки нельзя потерять при удалении корня

Удаление листа возвращает пустую ссылку его родителю. У узла с одним ребёнком возвращаем ссылку на этого ребёнка: он занимает прежнее место. Для двух детей нужен ключ, который подходит между левой и правой ветками. Берём преемника, successor: минимальный ключ правого поддерева. Он больше удаляемого и меньше остальных ключей справа.

В нашей реализации переносим в существующий узел пару ключ–значение, затем удаляем прежнюю запись преемника из правого поддерева. Его левой ветки нет по определению минимума; возможный правый ребёнок будет сохранён первым случаем remove. Возвращаем новый корень каждого обработанного поддерева, чтобы родитель обновил свою ссылку:

void remove(int key) { root = remove(root, key); }
Node remove(Node node, int key) {
    if (node == null) return null;
    if (key < node.key) node.left = remove(node.left, key);
    else if (key > node.key) node.right = remove(node.right, key);
    else {
        if (node.left == null) return node.right; // В том числе лист: вернёт null.
        if (node.right == null) return node.left;
        Node successor = node.right;
        while (successor.left != null) successor = successor.left;
        node.key = successor.key;
        node.value = successor.value; // Переносим пару, а не один ключ.
        node.right = remove(node.right, successor.key);
    }
    return node;
}

        + " keys=" + tree.walk("in"));
tree.remove(2); // Лист.
tree.remove(12); // Теперь у 12 один ребёнок — 14.

Новый ключ корня — 10, новое значение — P10. Скопировать только ключ означало бы вернуть результат другого платежа. После удаления листа 2 и узла 12 с одним ребёнком номер 14 сохранился. Операция стоит O(h); выбор преемника сохраняет порядок, но сам по себе не удерживает высоту дерева.

Под капотом: восстановление формы и подсчёт записей

Чтобы восстановить произвольное двоичное дерево из сериализованного preorder, нужно хранить и форму, например маркеры пустых детей. Одного списка ключей без дополнительных правил недостаточно. Для BST с уникальными ключами порядок задаёт дополнительные ограничения, но это отдельная задача восстановления.

Если в узле хранится размер его поддерева, можно искать k-й ключ и считать число ключей меньше заданного, спускаясь по одной ветке. После вставки, удаления и поворота размеры пересчитываются. Простое TreeMap таких операций rank/select в своём API не предоставляет.

Балансировка сохраняет короткий путь после вставки

В этой странице высоту считаем числом узлов на самом длинном пути: у пустого дерева 0, у листа 1. Другие источники считают рёбра, и тогда высота на единицу меньше. Вставим номера 1…31 подряд. Каждый новый ключ больше всех прежних, поэтому он уходит в конец правой цепочки. Получаем высоту 31 и столько же сравнений для последнего номера.

Если сначала вставить медиану 16, затем медианы двух половин и повторять это рекурсивно, те же ключи образуют дерево высоты 5. Такое построение полезно для известного набора, но новые вставки и удаления снова меняют форму. Динамическому индексу нужны правила, которые поддерживают баланс при каждой операции.

int height() { return height(root); }
int height(Node node) {
    return node == null ? 0 : 1 + Math.max(height(node.left), height(node.right));
}

static void medians(Tree tree, int low, int high) {
    if (low > high) return;
    int mid = low + (high - low) / 2;
    tree.put(mid, "P" + mid);
    medians(tree, low, mid - 1);
    medians(tree, mid + 1, high);
}

for (int id = 1; id <= 31; id++) sorted.put(id, "P" + id);
var balanced = new Tree();
medians(balanced, 1, 31);
System.out.println("sorted height=" + sorted.height() + " get 31=" + sorted.get(31)
        + " checks=" + sorted.path.size());
System.out.println("medians height=" + balanced.height() + " get 31=" + balanced.get(31)
        + " checks=" + balanced.path.size());

Суммарная цена последовательных вставок в обычный BST может стать O(n²): первая проходит короткий путь, следующая длиннее, затем ещё длиннее. AVL-дерево хранит высоты и требует, чтобы в каждом узле высоты двух поддеревьев отличались не больше чем на 1. Красно-чёрное дерево удерживает логарифмическую высоту с помощью цветов и локальных перестроек. Оно допускает менее ровную форму; оба подхода дают поиск, вставку и удаление за O(log n) в худшем случае.

Поворот меняет ссылки, но сохраняет порядок ключей

При правом повороте верхний узел top опускается вправо, а его левый ребёнок up поднимается. Между ними могло быть среднее поддерево up.right. Все его ключи больше up, но меньше top, поэтому оно переходит в top.left. Поворот изменяет постоянное число ссылок: O(1). Восстановление всего пути после изменения дерева — отдельная работа.

Ниже RedBlackDemo.java показывает LLRB, левосторонний вариант красно-чёрного дерева. Это учебная реализация вставки, не исходник TreeMap. Цвет хранится в узле и описывает входящую связь; R — красный, B — чёрный. В открытом уроке важны общие правила: корень и пустые листья NIL чёрные, у красного узла нет красного ребёнка, число чёрных узлов на всех путях от данного узла до NIL одинаково.

static final class Node {
    final int key;
    boolean red = true;
    Node left, right;
    Node(int key) { this.key = key; }
}

Далее фрагменты класса Tree с полями root и trace. Метод red считает пустую ссылку чёрной; новые Node из конструктора выше красные:

Node root;
boolean trace;

boolean red(Node node) { return node != null && node.red; }
void put(int key) {
    root = put(root, key);
    root.red = false; // Корень после операции всегда чёрный.
    if (trace) print("root black", root);
}
Node put(Node node, int key) {
    if (node == null) return new Node(key);
    if (key < node.key) node.left = put(node.left, key);
    else if (key > node.key) node.right = put(node.right, key);
    if (trace && node == root) print("inserted", node);
    if (red(node.right) && !red(node.left)) node = left(node);
    if (red(node.left) && red(node.left.left)) {
        node = right(node);
        if (trace) print("rotate right", node);
    }
    if (red(node.left) && red(node.right)) {
        node.red = !node.red;
        node.left.red = !node.left.red;
        node.right.red = !node.right.red;
        if (trace) print("flip colors", node);
    }
    return node;
}
Node right(Node top) {
    Node up = top.left;
    top.left = up.right; // Среднее поддерево остаётся между up и top.
    up.right = top;
    up.red = top.red;
    top.red = true;
    return up;
}
Node left(Node top) {
    Node up = top.right;
    top.right = up.left;
    up.left = top;
    up.red = top.red;
    top.red = true;
    return up;
}

Новый красный узел не меняет чёрную высоту, но способен создать два красных подряд. Поворот и смена цветов исправляют это нарушение. В LLRB есть ещё правило: красные связи наклонены влево. Поэтому код также исправляет одиночную красную правую связь левым поворотом. Обычное красно-чёрное дерево не обязано соблюдать этот дополнительный наклон.

Демо считает blackHeight вместе с чёрным NIL и проверяет равенство обеих ветвей, отсутствие двух красных подряд и правой красной связи. После 1000 последовательных вставок фактическая высота стала 10. Это конкретный результат нашего алгоритма, а не обещание всегда получить минимальную высоту.

Под капотом: откуда берётся логарифмическая граница

Пусть b — число чёрных обычных узлов на пути от корня, без NIL. При одинаковой чёрной высоте дерево содержит как минимум 2ᵇ − 1 обычных узлов: каждый чёрный уровень требует соответствующих ветвей. Между чёрными узлами не бывает двух красных подряд, поэтому длина самого длинного пути не больше удвоенного числа чёрных узлов. Отсюда высота ограничена 2 log₂(n + 1).

Удаление чёрного узла способно уменьшить чёрную высоту одной ветки. Поэтому в сбалансированном дереве нельзя взять обычный remove и ограничиться перекраской корня: нужны перестройки с учётом соседних ветвей. Полный набор случаев удаления здесь не реализован; для рабочего индекса в памяти используем готовую коллекцию. Наше демо проверяет именно вставку.

Проверка цветов и чёрной высоты из демо:

int blackHeight(Node node) {
    if (node == null) return 1; // Чёрный NIL включаем в счётчик.
    if (red(node) && (red(node.left) || red(node.right)))
        throw new IllegalStateException("two reds");
    if (red(node.right)) throw new IllegalStateException("right red link");
    int left = blackHeight(node.left), right = blackHeight(node.right);
    if (left != right) throw new IllegalStateException("black height mismatch");
    return left + (node.red ? 0 : 1);
}

B-дерево сокращает число переходов между крупными узлами

Красно-чёрное дерево уменьшает длину пути, но каждый его узел хранит всего один ключ. Для данных в страницах памяти или на диске переход к следующему узлу может быть намного дороже сравнения. Хочется за одно чтение получить сразу много границ диапазонов и выбрать из множества ветвей.

B-дерево хранит в узле несколько отсортированных ключей. При k ключах внутренний узел имеет k + 1 ребёнка: первый для ключей меньше первой границы, следующие для промежутков, последний для ключей больше последней. Если ключ совпал с ключом внутреннего узла, обычное B-дерево уже нашло запись. Все листья находятся на одной глубине.

Зафиксируем обозначение: минимальная степень t = 2. Некорневой узел хранит от t − 1 до 2t − 1 ключей: здесь от 1 до 3. Внутренний узел имеет от t до 2t детей: здесь от 2 до 4. У непустого корня может быть меньше ключей; если он внутренний, детей хотя бы два. Термин «порядок B-дерева» в книгах считают по-разному, поэтому в ответе лучше прямо назвать границы.

В BTreeDemo.java храним только множество числовых ключей, без значений платежей. Перед спуском в полный узел разделяем его: средний ключ переходит в родителя, меньшие остаются слева, большие — справа. У внутреннего узла вместе с ключами разделяются и ссылки на детей:

static final class Node {
    final List<Integer> keys = new ArrayList<>();
    final List<Node> children = new ArrayList<>();
    boolean leaf() { return children.isEmpty(); }
}
static final class Tree {
    Node root = new Node();
    boolean trace;
    void put(int key) {
        if (contains(root, key)) return; // Демо хранит множество уникальных ключей.
        if (root.keys.size() == 3) {
            Node parent = new Node();
            parent.children.add(root);
            root = parent;
            if (trace) print("new root", root);
            split(parent, 0);
            if (trace) print("split", root);
        }
        insert(root, key);
        if (trace) print("inserted", root);
    }
    boolean contains(Node node, int key) {
        int i = 0;
        while (i < node.keys.size() && key > node.keys.get(i)) i++;
        if (i < node.keys.size() && key == node.keys.get(i)) return true;
        return !node.leaf() && contains(node.children.get(i), key);
    }
    void split(Node parent, int at) {
        Node left = parent.children.get(at);
        Node right = new Node();
        int middle = left.keys.get(1);
        right.keys.add(left.keys.get(2));
        left.keys.subList(1, 3).clear(); // Слева остаётся младший ключ.
        if (!left.leaf()) {
            right.children.addAll(left.children.subList(2, 4));
            left.children.subList(2, 4).clear();
        }
        parent.keys.add(at, middle); // Медиана переходит в родителя.
        parent.children.add(at + 1, right);
    }
    void insert(Node node, int key) {
        int i = 0;
        while (i < node.keys.size() && key > node.keys.get(i)) i++;
        if (node.leaf()) {
            node.keys.add(i, key);
            return;
        }
        if (node.children.get(i).keys.size() == 3) {
            split(node, i); // Спускаемся только в неполный узел.
            if (key > node.keys.get(i)) i++;
        }
        insert(node.children.get(i), key);
    }
}

Чем больше ветвление, тем меньше страниц на пути: число уровней имеет порядок logₜ n. Внутри страницы ещё нужно выбрать ключ или промежуток. Это можно сделать линейным поиском по небольшому узлу либо двоичным поиском; сравнения не исчезают. Выгода B-дерева — прежде всего меньше дорогих переходов и более плотное размещение данных.

B+ оставляет сами записи в листьях

В B+-дереве внутренние ключи направляют поиск, а записи хранятся в листьях. Поиск доходит до листа и при совпадении с разделителем сверху. Листья связаны между собой, поэтому диапазон начинается с одного спуска, затем продолжается по соседним листьям. При разделении листа разделитель появляется в родителе, а запись остаётся в листе — это существенная разница с нашим B-демо.

Удаление тоже должно сохранять заполнение. Если узлу не хватает ключей, можно заимствовать у соседнего узла через родителя или слить соседей, забрав разделитель вниз. Когда корень становится пустым и у него остался один ребёнок, ребёнок занимает место корня: высота уменьшается. Устройство страниц, конкурентные изменения и поведение индексов базы вынесены в Indexes и Index Types.

Trie выбирает ветку по части ключа, а не по сравнению целиком

В интерфейсе операций нужны коды PAY, PAID и PAYOUT. По префиксу PA надо выдать подходящие коды, а по точному PAY — проверить наличие самого слова. Сравнивать каждый код с запросом можно, но большая часть работы повторяет сравнение одного общего начала.

Trie, префиксное дерево, хранит общее начало один раз. Рёбра помечены символами; путь от корня до узла соответствует префиксу. Для PA сначала идём по P, затем по A. Оставшееся поддерево содержит все продолжения PA. Порядок номеров из BST здесь не нужен: следующий шаг задаёт очередной символ ключа.

Узел должен отдельно хранить признак конца слова, terminal. Путь PAY может существовать только из-за PAYOUT. Наличие пути ещё не доказывает наличие PAY. В TrieDemo.java точный поиск требует и путь, и terminal; поиск префикса обходит всё поддерево после пути:

static final class Node {
    boolean terminal;
    final TreeMap<Character, Node> children = new TreeMap<>();
}
static final class Trie {
    final Node root = new Node();
    Node follow(String text) {
        Node node = root;
        for (int i = 0; i < text.length() && node != null; i++)
            node = node.children.get(text.charAt(i));
        return node;
    }
    void put(String text) {
        Node node = root;
        for (int i = 0; i < text.length(); i++)
            node = node.children.computeIfAbsent(text.charAt(i), c -> new Node());
        node.terminal = true; // Путь существовал и до добавления слова-префикса.
    }
    boolean contains(String text) {
        Node node = follow(text);
        return node != null && node.terminal;
    }
    List<String> prefix(String text) {
        var result = new ArrayList<String>();
        collect(follow(text), new StringBuilder(text), result);
        return result;
    }
    void collect(Node node, StringBuilder word, List<String> result) {
        if (node == null) return;
        if (node.terminal) result.add(word.toString());
        for (var edge : node.children.entrySet()) {
            word.append(edge.getKey());
            collect(edge.getValue(), word, result);
            word.setLength(word.length() - 1); // Возвращаем общий префикс перед соседней веткой.
        }
    }
}

Удаление снимает terminal у конечного узла. Обратный проход убирает только узлы без продолжений и без собственного слова; иначе он уничтожил бы другие ключи с тем же префиксом:

void remove(String text) { remove(root, text, 0); }
boolean remove(Node node, String text, int at) {
    if (at == text.length()) node.terminal = false;
    else {
        char letter = text.charAt(at);
        Node child = node.children.get(letter);
        if (child != null && remove(child, text, at + 1)) node.children.remove(letter);
    }
    return !node.terminal && node.children.isEmpty(); // Только бесполезный узел можно отсечь.
}

При прямом доступе к ребёнку точный поиск требует O(L) по длине ключа, а не по числу всех слов. Но хранение большого массива ссылок в каждом узле дорого. Наш пример использует TreeMap для детей: переход стоит O(log d), где d — число детей, поэтому путь имеет оценку O(L log d). Цена выдачи префикса дополнительно включает посещённые узлы и символы возвращённых строк; тысячи результатов нельзя получить за одну короткую операцию.

Под капотом: сжатие пути и смысл «символа»

В radix tree цепочки без развилок сжимают в рёбра с фрагментами строки. Узлов становится меньше, но при вставке ключа с частично общим ребром его приходится разделять. Маркер конца ключа всё ещё нужен: слово может закончиться внутри прежнего общего пути.

Наш код идёт по char, то есть по кодовым единицам UTF-16. Для кодов из ASCII это совпадает с буквами. Для произвольного Unicode нужно явно выбрать представление и нормализацию: кодовая точка за пределами BMP занимает два char, а визуально одинаковые строки могут иметь разную последовательность знаков. Сравнение префиксов должно использовать те же правила, что и запись.

Правило сравнения и запросы определяют выбор дерева

Дерево поиска требует согласованного порядка: natural ordering через Comparable или переданный Comparator. В TreeMap два ключа обозначают одну запись, когда сравнение даёт 0. Это может отличаться от equals. Например, BigDecimal сравнивает численное значение, а equals учитывает ещё масштаб:

Диагностируя свой BST, сравни число записей с высотой и числом посещённых узлов. Пример 31 против 5 показывает форму без нестабильного измерения времени. У готового TreeMap высота не является штатной метрикой. Профиль CPU поможет увидеть дорогой compareTo или Comparator: длинный составной ключ увеличивает стоимость каждого уровня. Даже O(log n) сравнений не означает O(log n) наносекунд.

TreeMap не согласует доступ нескольких потоков. Если дерево меняют одновременно с чтением, нужны подходящая коллекция или внешняя координация; потокобезопасный упорядоченный вариант ConcurrentSkipListMap устроен как skip list, а не красно-чёрное дерево. Дерево также не сохраняет платежи после падения процесса. Выбор структуры решает способ поиска, а атомарность и долговечность данных требуют своих решений.

Для простого получения минимального приоритета дерево с полным порядком может быть лишним: куча даёт более узкий набор операций. Для маршрутов между произвольными объектами нужны графы. На собеседовании сначала назови операции, объём и характер изменений, затем объясни, какие ветки выбранная структура позволяет пропускать.

  • В BST весь левый диапазон меньше ключа, весь правый — больше. Поиск стоит O(h), а не безусловное O(log n).
  • Inorder выдаёт ключи по порядку; диапазон отсекает лишние ветки. При удалении двух детей преемник сохраняет обе части дерева.
  • Повороты сохраняют порядок. AVL и красно-чёрные правила ограничивают высоту после изменений.
  • B-дерево помещает много границ в один узел. Разделение поднимает медиану; в B+ записи остаются в листьях.
  • В trie путь означает префикс, а terminal — точный ключ. В TreeMap идентичность записи определяет нулевой результат сравнения.

На собеседовании

Как устроено BST? Как искать и удалить узел с двумя детьми?

В каждом узле ключ и две ссылки. Все ключи слева меньше его, все справа больше. При поиске сравниваю ключ с текущим и выбираю одну ветку; пустая ссылка означает отсутствие. Стоимость зависит от высоты. В сбалансированном дереве это O(log n), в вытянутой цепочке O(n).

При удалении листа убираю ссылку, при одном ребёнке ставлю ребёнка на его место. При двух беру минимум правой ветки — преемника. Он подходит между левой веткой и оставшейся правой. Переношу ключ вместе со значением и удаляю старую запись преемника. Порядок сохраняется, баланс сам собой не восстанавливается.

  • Инвариант относится ко всему поддереву, а не только к детям. Проверка корректности несёт нижнюю и верхнюю границу от предков; локального сравнения двух соседей недостаточно.
  • У преемника не бывает левого ребёнка, но правый возможен. Его надо вернуть вместо удалённого узла, иначе теряется целая ветка.
  • Последовательная вставка уже отсортированных ключей может стоить O(n²). Хорошая форма при первоначальной загрузке не даёт гарантии после дальнейших изменений.

Какие бывают обходы дерева? Как выдать ключи диапазона без полного просмотра?

В inorder обрабатываю левое поддерево, узел и правое. Для BST это отсортированный порядок. В preorder узел идёт первым, в postorder — после обоих детей. Это обходы в глубину. Обход по уровням использует очередь и идёт от корня по слоям.

Диапазон делаю на основе inorder: спускаюсь влево, только если там могут быть ключи не ниже нижней границы, и вправо, только если там могут быть ключи не выше верхней. Подходящие ключи выдаю между ветками. Стоимость O(h + k), где k — число результатов; в сбалансированном дереве O(log n + k).

  • DFS требует O(h) памяти для рекурсии или явного стека, BFS — O(w) для ширины, в худшем O(n). Заменить стек очередью — значит изменить не только порядок, но и пик памяти.
  • Длинная цепочка делает рекурсивный обход опасным для стека JVM. Итеративный обход управляет стеком явно, но не исправляет форму дерева и сложность поиска.
  • При сохранении произвольной структуры список ключей не содержит информацию о пустых детях. Добавляют маркеры или другое описание формы; восстановление одного порядка значений не означает восстановление дерева.

За счёт чего красно-чёрное дерево удерживает логарифмическую высоту?

Узлы имеют красный или чёрный цвет. Корень и NIL чёрные, красный узел не имеет красного ребёнка, на всех путях до NIL одинаковое число чёрных узлов. Из-за последнего правила короткая ветка не может состоять из одного чёрного узла, пока другая накопила много чёрных уровней. Запрет двух красных подряд ограничивает растяжение пути.

После вставки или удаления алгоритм восстанавливает правила поворотами и сменой цветов. Поворот меняет несколько ссылок и сохраняет порядок ключей. Поэтому поиск остаётся обычным BST-поиском, а высота ограничена O(log n). AVL держит более строгое условие: разность высот детей не больше единицы в каждом узле.

  • При правом повороте среднее поддерево поднятого узла переходит к опущенному. Потерять эту ссылку — значит потерять ключи, хотя три нарисованных узла выглядят правильно.
  • Новый узел делают красным, чтобы сразу не менять чёрную высоту. Нарушение двух красных подряд исправляется локально. Удаление чёрного узла создаёт другой вид нарушения — дефицит чёрного уровня.
  • LLRB дополнительно требует наклона красных связей влево. Код его вставки нельзя выдавать за единственную форму красно-чёрного дерева или за реализацию TreeMap.

Когда выберешь BST, B-дерево или trie? Чем B+ отличается от B?

Для диапазонов и ближайших ключей в памяти подходит сбалансированное BST. Если данные читаются крупными страницами, B-дерево помещает много ключей в один узел и уменьшает число переходов. В обычном B-дереве записи могут находиться и во внутренних узлах. В B+ внутренние узлы только направляют поиск, записи лежат в листьях; связи между листьями удобны для диапазонов.

Для поиска продолжений общего префикса выберу trie: очередной символ задаёт ветку. Точный поиск проверяет маркер конца ключа, а поиск префикса обходит поддерево. Я сначала уточню нужные операции: эти структуры используют разные причины для выбора ветки.

  • В B-дереве надо явно назвать степень и пределы ключей. При разделении медиана переходит вверх; при удалении недостаточную заполненность исправляют заимствованием или слиянием. Число уровней не описывает число сравнений внутри страницы.
  • В trie переход O(1) предполагает соответствующее представление детей. Разреженные словари экономят ссылки, но добавляют цену поиска ребёнка. Сжатие цепочек уменьшает число узлов ценой сравнения фрагментов рёбер.
  • В TreeMap два ключа совпадают при compare == 0. В trie они совпадают по выбранной последовательности частей ключа. Правило идентичности должно сохранять различия, которые важны приложению.
В TreeSet платежи сравниваются только по сумме. После загрузки пропали операции с одинаковой суммой. Балансировка виновата?

Сравнение дало 0 для разных платежей, поэтому TreeSet счёл их одним элементом. Нужно добавить устойчивый уникальный идентификатор как следующий критерий или хранить платежи в списке и сортировать по сумме. Сравнение должно быть транзитивным; случайный результат для равных сумм не исправляет структуру. Балансировка сохраняет определённый компаратором порядок и не восстанавливает потерянную часть идентичности.
