VACUUM

Каждый UPDATE и DELETE в PostgreSQL оставляет мёртвую версию строки, и убирает её VACUUM. Обычный VACUUM не уменьшает файл таблицы, а отмечает место свободным для новых версий; вернуть место ОС может только VACUUM FULL, который переписывает таблицу под эксклюзивной блокировкой. HOT-обновление кладёт новую версию на ту же страницу без записи в индексы, если индексированные колонки не менялись и на странице есть место — его оставляет fillfactor. Autovacuum приходит, когда мёртвых строк набралось 20 % таблицы, и на больших таблицах это слишком поздно. Ещё одна его задача — заморозка: 32-битные номера транзакций исчерпываются, и без неё база остановится.

Таблица балансов выросла вчетверо, а после VACUUM диск не освободился

Таблица балансов на сто тысяч счетов занимала 14 МБ. Ночной пересчёт обновляет каждый баланс несколько раз, и утром таблица весит 57 МБ, а запросы, читающие её целиком, стали в четыре раза медленнее. Администратор запустил VACUUM — размер не изменился. Ещё через полгода в логе базы появилось предупреждение о скором исчерпании номеров транзакций.

Тема объясняет, откуда берётся раздувание, что именно делает VACUUM, как HOT-обновления его уменьшают, когда приходит autovacuum и зачем нужна заморозка. Почему версии вообще остаются — в MVCC, устройство страниц и WAL — в Architecture & WAL. Демо VacuumDemo.java работает с PostgreSQL 17 в Docker и считает версии точно через расширение pgstattuple; autovacuum для демо-таблиц выключен, чтобы он не вмешивался.

VACUUM освобождает место внутри файла, но не возвращает его ОС

== after insert of 100k rows          size 14 MB   live 100000  dead 0       free 0%
== after 3 full-table UPDATEs         size 57 MB   live 100000  dead 100000  free 49%
== after VACUUM                       size 57 MB   live 100000  dead 0       free 75%
== after 2 more UPDATE+VACUUM rounds  size 57 MB   live 100000  dead 0       free 75%
== after VACUUM FULL                  size 14 MB   live 100000  dead 0       free 0%

Три обновления всех строк создали триста тысяч новых версий, и таблица выросла с 14 до 57 МБ. Часть мёртвых версий уже убрала внутристраничная очистка (pruning), которую PostgreSQL делает попутно при чтении страницы, — поэтому мёртвых 100 тысяч, а не 300. VACUUM удалил остальные: мёртвых 0, свободно 75 % — но размер файла тот же. Место отмечено в карте свободного пространства, и новые версии будут занимать его: ещё два раунда обновлений с VACUUM между ними не увеличили таблицу. Так выглядит здоровое состояние нагруженной таблицы: она немного больше минимального размера и стабильна.

VACUUM FULL переписал таблицу в новый файл и вернул 14 МБ, но для этого он держит ACCESS EXCLUSIVE: таблица недоступна даже на чтение всё время перезаписи, а на диске нужно место под копию. На проде вместо него используют pg_repack, который перестраивает таблицу в фоне и берёт эксклюзивную блокировку лишь на короткое переключение. Обычно же лечат причину: частый autovacuum и отсутствие долгих транзакций, которые держат горизонт очистки, как показано в MVCC.

HOT-обновление не трогает индексы, если на странице есть место

Обычный UPDATE создаёт новую версию где-нибудь в таблице и добавляет запись о ней в каждый индекс таблицы. HOT (heap-only tuple) — оптимизация: если ни одна индексированная колонка не изменилась и новая версия помещается на ту же страницу, индексы не трогаются, а старая версия ссылается на новую внутри страницы. Демо обновляет каждую десятую строку таблицы с индексом по status:

== HOT, fillfactor 100, update non-indexed (balance):     updated 2000, HOT 0
== HOT, fillfactor 100, update indexed column (status):   updated 2000, HOT 0
== HOT, fillfactor 90, update non-indexed (balance):     updated 2000, HOT 2000
== HOT, fillfactor 90, update indexed column (status):   updated 2000, HOT 0

С fillfactor = 100 страницы заполнены целиком, новой версии некуда лечь, и HOT не случился ни разу. С fillfactor = 90 каждая страница оставляет 10 % под обновления, и все две тысячи изменений баланса прошли как HOT. Изменение индексированного status не может быть HOT при любом fillfactor: индекс должен узнать новое значение. Отсюда два практических правила: не индексировать часто меняющиеся колонки без нужды и снижать fillfactor у таблиц с частыми обновлениями. Долю HOT показывают n_tup_hot_upd и n_tup_upd в pg_stat_user_tables.

Autovacuum приходит по доле мёртвых строк, и на больших таблицах это поздно

== autovacuum_vacuum_threshold=50, scale_factor=0.2
   table of 10,000 rows: vacuum after ~2,050 dead rows
   table of 1,000,000 rows: vacuum after ~200,050 dead rows
   table of 100,000,000 rows: vacuum after ~20,000,050 dead rows

Autovacuum запускает очистку таблицы, когда мёртвых строк больше threshold + scale_factor × число строк. Для маленьких таблиц это часто, для таблицы платежей на сто миллионов строк — двадцать миллионов мёртвых версий, и проход по такой таблице займёт часы. Поэтому большим таблицам задают собственные параметры: alter table payment set (autovacuum_vacuum_scale_factor = 0.01) или фиксированный порог. Для таблиц, куда только вставляют, есть отдельный порог по вставкам — VACUUM нужен им для карты видимости и заморозки.

Autovacuum намеренно медленный: autovacuum_vacuum_cost_limit ограничивает, сколько работы он делает перед паузой, чтобы не мешать запросам. На нагруженной базе этот лимит поднимают, иначе очистка не успевает за потоком изменений. Мониторят n_dead_tup, last_autovacuum и длительность проходов в логах (log_autovacuum_min_duration).

Номера транзакций 32-битные, и без заморозки база остановится

Номер транзакции — 32-битное число, и PostgreSQL сравнивает их по кругу: из любой точки два миллиарда номеров считаются прошлым, а два миллиарда — будущим. Если строка, созданная транзакцией 100, доживёт до момента, когда счётчик ушёл на два миллиарда вперёд, её xmin внезапно окажется «в будущем», и строка исчезнет. Чтобы этого не случилось, VACUUM замораживает старые версии: помечает, что они видны всем, независимо от номера.

== ledger relfrozenxid age 9 of autovacuum_freeze_max_age 200000000

Когда возраст relfrozenxid таблицы превышает autovacuum_freeze_max_age — 200 миллионов, — autovacuum запускает агрессивную очистку для защиты от переполнения, даже если autovacuum для таблицы выключен, и такая очистка не уступает конфликтующим блокировкам, как обычный autovacuum. Если и это не успевает — например, долгая транзакция держит горизонт или очистка не справляется, — база ближе к границе перестаёт выдавать новые номера и работает только на чтение, пока не пройдёт VACUUM. Возраст отслеживают по age(datfrozenxid) в pg_database и алертят задолго до порога. Проходы заморозки по большим таблицам ускоряет карта видимости: страницы, где все версии уже заморожены, VACUUM пропускает.

После массового UPDATE нужно запустить VACUUM, чтобы таблица уменьшилась.

VACUUM не уменьшает файл: в демо таблица осталась 57 МБ, но 75 % внутри стали свободными для новых версий. Уменьшает только VACUUM FULL с полной блокировкой таблицы или pg_repack. Обычно правильная цель — стабильный размер при частом autovacuum, а не минимальный.

  • UPDATE оставляет мёртвые версии: 14 МБ → 57 МБ после трёх обновлений всех строк.
  • VACUUM делает место переиспользуемым (75 % свободно), но размер не меняет; VACUUM FULL сжимает под ACCESS EXCLUSIVE, pg_repack — в фоне.
  • HOT не пишет в индексы: с fillfactor 90 все 2000 обновлений баланса — HOT, с 100 и для индексированной колонки — ни одного.
  • Autovacuum по умолчанию ждёт 20 % мёртвых строк — для больших таблиц задают свой scale_factor и поднимают cost_limit.
  • Заморозка защищает от переполнения 32-битных номеров транзакций; возраст свыше 200 млн запускает агрессивную очистку.

На собеседовании

Зачем в PostgreSQL нужен VACUUM?

MVCC оставляет мёртвые версии строк после UPDATE и DELETE. VACUUM удаляет те, которые уже не видит ни один снимок, и отмечает место свободным для новых версий; обновляет карту видимости для index-only scan и статистику; замораживает старые версии, защищая от переполнения номеров транзакций. Autovacuum делает это автоматически по порогам.

  • Обычный VACUUM не уменьшает файл; VACUUM FULL переписывает таблицу под ACCESS EXCLUSIVE.
  • Долгие транзакции и idle in transaction держат горизонт, и VACUUM не может убрать версии.
  • Для больших таблиц задают свой autovacuum_vacuum_scale_factor.

Что такое HOT-обновление и как его получить?

Heap-only tuple: новая версия строки ложится на ту же страницу, а индексы не обновляются, потому что ни одна индексированная колонка не менялась. Это экономит запись в индексы и их раздувание. Нужны два условия: изменение только неиндексированных колонок и свободное место на странице, которое оставляет fillfactor меньше 100.

  • Долю HOT видно в n_tup_hot_upd в pg_stat_user_tables.
  • Лишний индекс на часто меняющейся колонке отключает HOT для всех её обновлений.
Почему таблица сессий раздувается, хотя autovacuum включён? 
create table session(id uuid primary key, user_id bigint, last_seen timestamptz, data jsonb);
create index on session(last_seen);
-- каждый запрос пользователя: update session set last_seen = now() where id = :id

last_seen меняется на каждом запросе и проиндексирована, поэтому ни одно обновление не может быть HOT: каждое создаёт новую версию и записи во всех индексах, включая первичный. При fillfactor 100 новым версиям и так нет места на странице. Если индекс по last_seen нужен только для чистки старых сессий, можно обновлять last_seen реже, хранить его отдельно или заменить индекс; таблице стоит снизить fillfactor и поставить агрессивный autovacuum.

Что такое transaction ID wraparound?

Номера транзакций 32-битные и сравниваются по кругу: половина считается прошлым, половина будущим. Незамороженная старая версия со временем оказалась бы «в будущем» и исчезла. VACUUM замораживает старые версии, делая их видимыми всем. Когда возраст relfrozenxid превышает autovacuum_freeze_max_age (200 млн), запускается принудительная очистка, а у границы база перестаёт выдавать номера транзакций.

  • Мониторят age(datfrozenxid) по базам и age(relfrozenxid) по большим таблицам.
  • Причины опасной ситуации — долгие транзакции, заброшенные слоты репликации, отстающий autovacuum.
  • PostgreSQL 17: Routine Vacuuming — основа урока: очистка, autovacuum, заморозка и wraparound.
  • Егор Рогов, «PostgreSQL изнутри», часть I — внутристраничная очистка, HOT, VACUUM, заморозка.
  • pgstattuple — точная статистика версий из демо.
  • pg_repack — перестройка таблиц без долгой блокировки.
