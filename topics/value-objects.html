Valhalla: Value Objects

Дата валютирования 2026-10-22 — значение, как число 4. Но в Java каждый LocalDate — объект со своей identity: отдельный адрес в heap, заголовок, право на synchronized. Value-класс от identity отказывается: два объекта с одинаковыми полями становятся неразличимы даже для ==. Взамен JVM может не выделять их в heap, а держать поля прямо в массиве, в поле другого объекта или в регистрах. В JDK 28 это preview-возможность, она включается флагом --enable-preview.

Дата платежа платит за identity, которая ей не нужна

Платёжный сервис держит в памяти пачку платежей. У каждого есть id пользователя типа Long и дата валютирования LocalDate. Оба поля — неизменяемые значения: две даты 2026-10-22 ничем не отличаются. Но для JVM каждая дата — отдельный объект. У него свой адрес, заголовок в heap, его можно использовать как монитор в synchronized. Это и есть identity: свойство «этот объект, а не другой, даже если поля совпадают».

Identity видна в двух местах. Первое — оператор ==: он сравнивает адреса, поэтому два одинаковых Long больше 127 не равны (разбор этой ошибки — в теме Types & Wrappers). Второе — память: массив дат хранит не даты, а ссылки на миллион разбросанных по heap объектов. Один и тот же исходник на JDK 28 показывает разницу, если запустить его с preview и без:

public class SameCode {
    record Payment(Long userId, LocalDate valueDate) { }        // обычный record: identity-класс

    public static void main(String[] args) throws Exception {
        Payment a = new Payment(100_500L, LocalDate.of(2026, 10, 22));
        Payment b = new Payment(100_500L, LocalDate.of(2026, 10, 21).plusDays(1));

        System.out.println("userId ==    " + (a.userId() == b.userId()));        // Long вне кеша -128..127
        System.out.println("valueDate == " + (a.valueDate() == b.valueDate()));  // одна дата, создана двумя путями
        System.out.println("payment ==   " + (a == b));                          // сам Payment остаётся identity

        // Миллион дат валютирования в массиве: что лежит в heap
        LocalDate[] dates = new LocalDate[1_000_000];
        LocalDate start = LocalDate.of(2020, 1, 1);
        for (int i = 0; i < dates.length; i++) dates[i] = start.plusDays(1 + i % 3650);
        histogram("java.time.LocalDate ", "[Ljava.time.LocalDate;");           // строки из GC.class_histogram
        System.out.println(dates[dates.length - 1]);                            // массив жив до замера
    }
}

Без preview всё привычно: равные значения не ==, а миллион дат стоит 20 МБ — 4 байта ссылки в массиве и 16 байт объекта на каждую (из чего складывается размер объекта — тема Object Layout & Allocation). С preview Long и LocalDate становятся value-классами. == сравнивает их по полям, массив весит 8 МБ, а отдельных объектов LocalDate почти нет. Payment по-прежнему сравнивается по адресу: это обычный record, и от identity он не отказывался. Метод histogram печатает строки из GC.class_histogram — то же, что jcmd <pid> GC.class_histogram. Полный файл — examples/value-objects/SameCode.java.

Почему JVM не делала так раньше? Язык позволяет identity наблюдать. == сравнивает адреса, synchronized захватывает монитор конкретного объекта, System.identityHashCode возвращает хеш, привязанный к объекту, WeakReference следит за смертью именно этого экземпляра. Если хоть один такой вызов возможен, JVM обязана хранить объект отдельно и отдавать на него ссылку. Убрать объект она может, только если доказала, что ссылка не выходит из метода. Это escape analysis (тема Object Layout & Allocation), а элемент массива из метода как раз выходит.

Project Valhalla предлагает другой путь. Автор класса сам обещает, что identity его объектам не нужна. Язык после этого запрещает операции, которые её наблюдают, а JVM получает свободу хранить значение как удобнее. Весь урок — про то, что именно меняется после такого обещания.

Модификатор value — обещание: identity не нужна, поля не меняются

Value-класс объявляется модификатором value перед class или record. Остальные классы теперь называются identity-классами, и их поведение не меняется.

value record Money(long kopecks, String currency) { }   // value record: компоненты, equals, toString как у record

value class Iban {                                       // value class: своё представление, свои методы
    private final String digits;                         // final можно не писать: поля value-класса неявно final
    Iban(String digits) { this.digits = digits; }
    @Override public boolean equals(Object o) { return o instanceof Iban i && digits.equals(i.digits); }
    @Override public int hashCode() { return digits.hashCode(); }
}

Обещание «identity не нужна» имеет смысл только для неизменяемых и взаимозаменяемых объектов. Поэтому компилятор добавляет ограничения:

  • Все поля неявно final. Если бы поле можно было поменять, два «одинаковых» объекта разошлись бы после изменения одного из них, а отличить их без identity нельзя.
  • Класс неявно final. Наследование разрешено только от абстрактного value-класса, помеченного abstract value class.
  • Родитель — Object или абстрактный value-класс. Identity-родитель мог бы хранить в себе изменяемые поля и опираться на this как на монитор.
  • Типы полей любые. Поле может ссылаться на identity-объект, например на String или List. Ссылка на value-объект может быть null, как любая ссылка.
static abstract class Account { }                          // identity-класс
static value class Card extends Account { }                // value не может наследовать identity

static abstract value class Amount { abstract long kopecks(); }
static value class Fee extends Amount { … }                // можно: родитель — abstract value
static class Balance extends Amount { … }                  // можно: identity-наследник abstract value
static value class Bonus extends Fee { … }                 // value class неявно final

static value class Counter {
    long n;                                                // неявно final
    void inc() { n++; }                                    // запись после конструктора
}

Number и Record в JDK 28 стали абстрактными value-классами: у них нет полей и кода, завязанного на identity. Поэтому от Number наследуют и value-класс Integer, и identity-класс BigInteger, а от Record — и value record, и обычный record. Абстрактный value-класс можно сделать sealed и перечислить в permits его value-наследников: так моделируют закрытый набор значений вроде видов идентификатора пользователя (тема Sealed & Pattern Matching).

Value record подходит, когда поля и есть публичный контракт: Money(kopecks, currency). Value class нужен, когда внутреннее представление отличается от внешнего. Например, сумма хранится одним long в копейках, а наружу отдаются рубли и копейки по отдельности. Record так не умеет: его поля совпадают с компонентами (тема Records).

Какие классы JDK стали value-классами

С --enable-preview value-классами становятся 30 классов JDK: восемь обёрток примитивов, Number и Record, четыре Optional*, большинство типов java.time (LocalDate, LocalTime, LocalDateTime, ZonedDateTime, OffsetDateTime, Instant, Duration, Period, Year и другие) и четыре даты из java.time.chrono. Новый метод Objects.hasIdentity показывает, какой объект перед тобой:

String остался identity-классом: его API и реализация опираются на identity, например intern(). BigDecimal, UUID, ZoneOffset и неизменяемые коллекции в JDK 28 тоже не перевели. Перевод — решение авторов класса, автоматически он не происходит. Классы, которые перевели, давно были описаны в javadoc как value-based: «не полагайтесь на identity, не создавайте конструктором, не синхронизируйтесь». Поэтому в JDK 9 конструкторы обёрток объявили deprecated, а в JDK 16 добавили предупреждения о synchronized на таких объектах (JEP 390).

Value class — это struct, как в C#: копируется при присваивании и лежит на стеке.

В Java нет новой семантики копирования. Value-объект по-прежнему передаётся по ссылке и может быть null. Меняются только правила наблюдения: identity нет, поэтому JVM вправе хранить его как угодно — указателем, в поле, в регистрах. Struct в C# изменяем, поэтому семантику копий там приходится явно описывать. Value-объект неизменяем, и копия от оригинала не отличается.

== сравнивает поля рекурсивно, но equals всё равно нужен

Раньше == отвечал на вопрос «тот же ли это объект». Теперь он отвечает на вопрос «можно ли отличить эти объекты». Для identity-объектов ответ прежний: сравниваются адреса. Два value-объекта неразличимы, если:

  1. они одного класса;
  2. их примитивные поля совпадают побитово;
  3. их ссылочные поля равны по == — то же правило применяется рекурсивно.

Это не equals. Правило не знает, что две строки с одинаковыми буквами — одно и то же значение, и не знает, что 0.0 и -0.0 равны как числа:

value record Money(long kopecks, String currency) { }

static value class Iban {                              // value class без equals и hashCode
    private final String digits;
    Iban(String digits) { this.digits = digits; }
}

value record Rate(double percent) { }

String rub = "RUB";
String rubCopy = new String("RUB");                    // та же строка, другой объект
Money a = new Money(100, rub);
Money b = new Money(100, rub);
Money c = new Money(100, rubCopy);
System.out.println("a == b        " + (a == b));
System.out.println("a == c        " + (a == c));
System.out.println("a.equals(c)   " + a.equals(c));

a == c ложно, потому что поле currency ссылается на два разных объекта String, а строки сравниваются по адресу. Iban без своего equals ломается так же: унаследованный Object.equals для value-объекта — это ==, а hashCode считается по битам полей, то есть по адресу строки. Два одинаковых IBAN попадут в разные корзины HashSet. С double всё упирается в биты: -0.0 отличается от 0.0 знаковым битом, а два одинаковых NaN совпадают побитово, хотя nan == nan для примитива ложно.

Отсюда главное правило: == отвечает «неразличимы ли объекты», а equals — «одно ли это значение». Для Integer и LocalDate ответы совпадают. Для класса, у которого внутри строка, коллекция или double, — нет. Поэтому value-классу со ссылочными полями нужен свой equals и hashCode с тем же контрактом, что у обычного класса (тема equals & hashCode). Value record генерирует их сам, как любой record.

С Valhalla обёртки можно сравнивать через ==, а equals больше не нужен.

Только когда код запущен с --enable-preview на JDK 28 и новее. На JDK 21 и без preview тот же код снова сравнивает адреса и ломается на значениях больше 127. А для value-класса со строковым полем == ошибается и с preview. JEP 401 прямо говорит: менять == на замену equals не цель.

У нового == есть цена. Сравнение идёт по всему графу value-объектов: глубоко вложенные значения сравниваются долго и в пределе могут дать StackOverflowError. Зациклиться оно не может: правила конструирования (следующий шаг) не дают value-объекту сослаться на себя. И ещё деталь для безопасности: по == и System.identityHashCode можно косвенно узнать значения приватных полей. Value-класс не годится для данных, которые надо защищать от такого подбора.

Под капотом: во что превращается if_acmpeq

Байткод не изменился: == над ссылками — по-прежнему if_acmpeq. Раньше это одно сравнение указателей. Теперь JVM сначала проверяет быстрый путь: указатели равны — значит, объекты неразличимы; один из объектов identity — значит, достаточно сравнить указатели. Только если оба объекта value и одного класса, она сравнивает содержимое. Для этого у каждого value-класса есть карта: какие байты сравнивать побитово, а какие поля — ссылки, которые нужно сравнить рекурсивно.

Эту карту видно в -XX:+PrintFieldLayout (шаг 6): у Transfer строка Non-oop acmp map <offset,size>: <8,25> — 25 байт с восьмого сравниваются как обычные данные. JEP 401 отдельно отмечает, что дополнительная проверка в if_acmpeq стоит немного и для identity-объектов, но её оптимизировали как быстрый путь.

Операции, которым нужна identity, перестают работать

Identity использовали не только через ==. Монитор synchronized живёт в заголовке конкретного объекта. WeakReference сообщает о смерти конкретного экземпляра (тема References). IdentityHashMap различает ключи по адресу. Сериализация и рефлексия умеют создавать объект в обход конструктора и записывать в его поля. У value-объекта нет ни адреса, ни заголовка, на который можно опереться, поэтому все эти операции для него запрещены или меняют смысл:

value record Money(long kopecks, String currency) { }

static value class Ticket implements java.io.Serializable {   // value class, не record
    private final long id;
    Ticket(long id) { this.id = id; }
}

Money fee = new Money(150, "RUB");
Object lock = fee;                                  // статический тип Object: javac не видит value-класс

try { synchronized (lock) { } }
catch (IdentityException e) { System.out.println("synchronized: " + e.getMessage()); }

try { lock.wait(10); }
catch (IllegalMonitorStateException e) { System.out.println("wait:         " + e.getClass().getSimpleName()); }

try { new WeakReference<>(fee); }
catch (IdentityException e) { System.out.println("WeakReference:" + " " + e.getMessage()); }

Map<Object, String> seen = new IdentityHashMap<>();
seen.put(new Money(150, "RUB"), "first");
seen.put(new Money(150, "RUB"), "second");          // == и identityHashCode совпадают

Самое неожиданное здесь — new Integer(1996) == new Integer(1996). Классический ответ на собеседовании «new всегда создаёт новый объект» для value-классов неверен. new может вернуть уже существующее значение или вообще не выделять память, и отличить одно от другого нельзя. Кеш Integer от −128 до 127 при этом теряет смысл для ==: равные значения равны всегда. IdentityHashMap тоже не ошибся: два Money(150, "RUB") неразличимы, поэтому это один ключ.

Старый JAR ломается от одного флага

Value-версии Integer и LocalDate включаются флагом запуска, а не версией class-файла твоего кода. Класс, собранный без preview, но запущенный с --enable-preview, уже работает с value-Integer:

// JDK 21 без preview. Код, который сломается, когда LocalDate и Integer станут value-классами.
public class Prepare {
    static final Map<LocalDate, String> holidays = new WeakHashMap<>();   // слабые ключи-даты

    public static void main(String[] args) {
        Object lock = Integer.valueOf(1996);              // статический тип Object: javac не предупредит
        synchronized (lock) {
            var ref = new WeakReference<>(LocalDate.of(2026, 10, 22));
            System.out.println("locked, ref alive: " + (ref.get() != null) + ", holidays: " + holidays.size());
        }
    }
}

JDK 21 молчит о WeakHashMap<LocalDate, …>: предупреждения [identity] для java.lang.ref и WeakHashMap javac выдаёт начиная с JDK 25. Синхронизацию через Object компилятор не видит ни в одной версии, а флаг -XX:DiagnoseSyncOnValueBasedClasses=2 пишет её в лог при выполнении. Он есть с JDK 16 и подходит, чтобы прогнать тесты и найти такие места заранее.

Частый прод-паттерн — блокировка по id: synchronized (accountId) { … }, где accountId — Long. Он сломан уже сегодня: для id до 127 все потоки делят один закешированный объект с любым другим кодом, а для больших id два потока с равными id получают разные объекты и вообще не исключают друг друга. С value-классами такой код падает с IdentityException. Блокировку по ключу делают через ConcurrentHashMap<Long, Lock> с computeIfAbsent или блокировкой строки в базе.

Value-объект заполняет поля до super(), и verifier это проверяет

У identity-объекта есть период, когда он уже создан, но ещё не готов: конструктор родителя выполнился, а поля наследника пока ноль и null. Если в этот момент объект утечёт наружу, чужой код увидит недостроенное состояние, а потом то же поле изменится. Для identity-объекта это неприятная ошибка. Для value-объекта это нарушение самой модели: без identity объект и есть его поля. «Тот же» объект с kopecks = 0 и потом с kopecks = 150 — это два разных значения под одной ссылкой.

Проблема реальная и для обычных record. Compact constructor выполняется до присваивания полей, и this в нём видит значения по умолчанию:

record Payment(String id, long amount) {
    Payment {
        if (amount < 0)
            throw new IllegalArgumentException("bad " + this);   // this до присваивания полей
    }
}

new Payment("p-1", -500);
bad Payment[id=null, amount=0]

Так печатают JDK 21 и JDK 28 без preview: в сообщении не id платежа и не сумма, а null и 0. Value-классы закрывают эту дыру правилом: весь конструктор value-класса выполняется до вызова super(). Компилятор ставит super() в конец тела, а не в начало. До него можно присваивать поля и читать уже присвоенные, но нельзя вызывать методы экземпляра и передавать this куда-либо:

public value class EarlyThis {
    private final long kopecks;
    private final String currency;

    public EarlyThis(long kopecks, String currency) {
        this.kopecks = kopecks;
        this.currency = normalize(currency);    // метод экземпляра: нужен this
    }

    private String normalize(String c) { return c.toUpperCase(); }
}
javac --release 28 --enable-preview negative/EarlyThis.java
EarlyThis.java:8: error: reference to normalize(String) may only appear after an explicit constructor invocation
        this.currency = normalize(currency);    // метод экземпляра: нужен this
                        ^

Исправление — сделать вспомогательный метод static. Если после заполнения полей нужен this, например для лога, явный super() отмечает границу: всё до него — ранняя фаза, после — поздняя, где this доступен. Этот синтаксис пришёл из flexible constructor bodies (JDK 25):

static value class Money {
    private final long kopecks;
    private final String currency;

    Money(long kopecks, String currency) {
        if (kopecks < 0) throw new IllegalArgumentException("negative");
        this.kopecks = kopecks;
        this.currency = normalize(currency);    // static-метод: this не нужен
        super();                                // к этой строке все поля обязаны быть заданы
        System.out.println("создан " + this);   // после super() this уже можно использовать
    }

    private static String normalize(String c) { return c.toUpperCase(); }

    @Override public String toString() { return kopecks + " " + currency; }
}

new Money(150, "rub");
создан 150 RUB

Инициализаторы полей (long kopecks = 0;) выполняются в начале ранней фазы. Блоки инициализации экземпляра { … } выполняются после super(), поэтому поля value-класса в них присваивать нельзя.

С --enable-preview это же правило распространяется на все record, включая обычные identity-record. Пример с Payment выше перестаёт компилироваться:

java --enable-preview RecordThis.java
RecordThis.java:6: error: reference to this may only appear after an explicit constructor invocation
                throw new IllegalArgumentException("bad " + this);   // this до присваивания полей
                                                            ^

Это редкий случай несовместимости по исходникам. Авторы JEP проверили большой корпус кода: record, которые обращаются к this до заполнения полей, встречаются редко и почти всегда содержат ту же ошибку, что Payment.

Strict-поля: гарантия на уровне JVM

Правила javac можно обойти другим компилятором или генератором байткода. Поэтому вместе с JEP 401 в JDK 28 вошёл JEP 539 «Strict Field Initialization in the JVM». javac помечает поля value-класса флагом ACC_STRICT_INIT (0x0800). Verifier отслеживает, какие из них ещё не заданы, пропускает вызов конструктора родителя только при пустом списке и запрещает putfield в такое final-поле после этого вызова. Нарушение ловит проверка байткода (verification) ещё до первого выполнения конструктора.

Из strict-полей следуют и ограничения прошлого шага. Рефлексия не может записать такое поле: setAccessible считает его неизменяемым, как static final, и --enable-final-field-mutation не помогает. Стандартная сериализация создаёт объект без конструктора и пишет поля рефлексией, поэтому для value class она отказывает с InvalidClassException. Value record сериализуется, потому что record и раньше восстанавливался через канонический конструктор. Есть и выигрыш: JIT считает strict final-поля по-настоящему неизменяемыми и может не перечитывать их из памяти.

Под капотом: early_larval frame в StackMapTable

Verifier проверяет метод без выполнения, по кадрам StackMapTable в точках ветвления. Раньше незаконченный объект там обозначался одним типом uninitializedThis. Теперь кадр должен ещё сказать, какие strict-поля не заданы. Для этого есть новый тип кадра 246. Он появляется, если ветвление случилось между присваиваниями полей:

value class Larval {

    private final String currency;
    Larval(long kopecks, String currency) {
        this.kopecks = kopecks;
        this.currency = currency == null ? "RUB" : currency;   // ветвление после первого putfield
    }
}

JEP 539 описывает strict-поля шире, чем их использует javac в JDK 28. JVM умеет то же для static-полей: читать поле до присваивания при инициализации класса нельзя, и нарушение даёт исключение при выполнении. Это задел на будущие возможности языка, например на поля, которые не могут быть null.

Без identity JVM кладёт поля объекта в массив, в поле и в регистры

Value-объект неотличим от своей копии, поэтому JVM может хранить не ссылку, а сами поля. JEP 401 называет два способа. Flattening — поля value-объекта записываются прямо в ячейку массива или в поле другого объекта. Scalarization — JIT раскладывает value-объект на отдельные локальные переменные и регистры, в том числе при передаче в метод и возврате из него. Это оптимизации, а не правила языка: управлять ими напрямую нельзя, и JVM применяет их по своему решению.

Flattening: поле должно читаться атомарно

Ячейку массива или поле identity-объекта можно перезаписать из другого потока. Если JVM хранит там дату как 48 бит данных, запись должна быть атомарной: иначе другой поток прочитает год от одной даты и день от другой — значение, которого никто не создавал. Распространённые процессоры атомарно пишут до 64 бит. Кроме данных нужен ещё флаг null: ссылка на value-объект может быть null, и это состояние надо отличать от «все поля нулевые». Поэтому правило JDK 28 такое: значение плюс флаг null должны уложиться в 64 бита.

int n = 1_000_000;
Integer[] fees = new Integer[n];                  // 32 бита + флаг null
Long[] amounts = new Long[n];                     // 64 бита + флаг null
LocalDate[] dates = new LocalDate[n];             // 48 бит + флаг null
Object[] mixed = new Object[n];                   // тип элемента Object: сюда можно положить что угодно
LocalDate start = LocalDate.of(2020, 1, 1);
for (int i = 0; i < n; i++) {
    fees[i] = 1_000 + i;
    amounts[i] = 1_000L + i;
    dates[i] = start.plusDays(1 + i % 3650);
    mixed[i] = 1_000 + i;                         // те же Integer, что в fees
}

Scalarization работает и через границы методов

В регистрах и локальных переменных гонок нет, поэтому там размер не ограничен. Сравним два одинаковых сумматора — на обычном record и на value record:

record IdMoney(long kopecks) {                       // обычный record: identity
    IdMoney plus(IdMoney o) { return new IdMoney(kopecks + o.kopecks); }
}

value record Money(long kopecks) {                   // тот же код, но без identity
    Money plus(Money o) { return new Money(kopecks + o.kopecks); }
}

static long sumIdentity(int n) {
    IdMoney total = new IdMoney(0);
    for (int i = 0; i < n; i++) total = total.plus(new IdMoney(i));   // total переходит в следующую итерацию
    return total.kopecks();
}

static long sumValue(int n) {
    Money total = new Money(0);
    for (int i = 0; i < n; i++) total = total.plus(new Money(i));
    return total.kopecks();
}

// в main — четыре раунда по миллиону сложений; счётчик байтов, выделенных потоком
var threads = (com.sun.management.ThreadMXBean) ManagementFactory.getThreadMXBean();
long start = threads.getCurrentThreadAllocatedBytes();
sink += sumIdentity(1_000_000);
long identity = threads.getCurrentThreadAllocatedBytes() - start;
// то же для sumValue

Сколько выделится, зависит от того, когда отработает JIT, поэтому ниже — реальные запуски, а не точный прогноз:

$ java --enable-preview Scalarization.java

раунд 2: identity 17,545 КБ, value  8,831 КБ
раунд 3: identity 15,625 КБ, value      0 КБ      # C2: Money не выделяется вовсе

15 625 КБ — это ровно миллион объектов по 16 байт. Escape analysis в identity-версии убрала временный new IdMoney(i), но не total: он переходит из итерации в итерацию, и C2 его не убирает. Когда plus не инлайнится, ссылки уходят в другой метод, escape analysis сдаётся, и выделений становится два на итерацию. Value-версия после прогрева не выделяет ничего в обоих случаях. JIT передаёт Money в метод как его поля и возвращает так же, потому что identity нет и никто не заметит, что объекта не было.

Первые раунды показывают и обратную сторону: в интерпретаторе и C1 value-объекты выделяются в heap как обычно. JVM называет такой экземпляр буферизованным. Он может весить больше identity-аналога: в выводе PrintFieldLayout выше буферизованный Money занимает 24 байта против 16 у IdMoney — у него есть флаг null.

Когда оптимизаций не будет

  • Тип переменной не точный. Object, интерфейс (Comparable<LocalDate>) или параметр T могут хранить объекты разных классов. Такое поле — обычная ссылка, как mixed выше.
  • Generics стираются. List<Money>, Map<Long, Money>, поле T value в Optional<T> — всё это Object после стирания. В коллекциях JDK 28 хранит value-объекты по ссылкам.
  • Значение больше 64 бит в изменяемом поле или массиве. Long, Double, Instant, LocalDateTime, сумма из long и валюты — ссылками.
  • Код не прогрет. Scalarization делает только C2. До неё value-объекты выделяются в heap, и чтение из flat-поля может даже создавать лишние объекты.
  • Класс собран против старой версии. javac записывает имена value-классов из сигнатур в атрибут LoadableDescriptors, чтобы JVM загрузила их заранее и разложила поля. Класс, собранный, пока Money был identity-классом, оптимизируется хуже. После перевода класса в value его клиентов стоит пересобрать.

Value class гарантирует, что объект не попадёт в heap и сэкономит память.

Гарантирована только семантика: нет identity, == по полям. Раскладку JVM выбирает сама. Миллион Long в массиве, List<Money> или объект в непрогретом коде лежат в heap, причём буферизованный value-объект бывает больше обычного. Выигрыш надо измерять на своей нагрузке: JMH, JFR, гистограмма heap.

Под капотом: соглашение о вызовах для value-объектов

Почему value-объект проходит через неинлайненный вызов без выделения? У C2 для методов с value-параметрами есть второй вход: аргумент Money передаётся как его поля, по регистру на поле, плюс флаг null. Возврат устроен так же. JEP 401 записывает это псевдокодом: plusYears у LocalDate принимает this_null, this_year, this_month, this_day и возвращает четвёрку значений. Поведение управляется диагностическими флагами ValueTypePassFieldsAsArgs и ValueTypeReturnedAsFields, оба включены по умолчанию. Если отключить первый, value-версия снова выделяет объекты:

$ java --enable-preview -XX:+UnlockDiagnosticVMOptions -XX:-ValueTypePassFieldsAsArgs \
       -XX:CompileCommand=quiet -XX:CompileCommand=dontinline,*::plus Scalarization.java
раунд 4: identity 31,250 КБ, value 46,875 КБ      # 2 буфера по 24 Б на итерацию

46 875 КБ на миллион итераций — два буферизованных Money по 24 байта. Это хуже identity-версии: без соглашения о вызовах value-объект теряет главное преимущество и платит за флаг null. Флаги диагностические, в проде их не трогают. Здесь они нужны, чтобы увидеть, какой механизм дал ноль.

Escape analysis для identity-объектов работает в похожем направлении, но она обязана доказать, что identity не наблюдается: объект не уходит в поле, в другой поток, в неинлайненный метод. Для value-объекта доказывать нечего: identity нет по определению. Поэтому JEP называет scalarization value-объектов более предсказуемой и работающей через границы методов.

Как попробовать

javac --release 28 --enable-preview Main.java    # class-файл версии 72.65535
java --enable-preview Main                       # без флага JVM откажется загружать такой класс
java --enable-preview Main.java                  # source launcher: компиляция и запуск сразу
jshell --enable-preview

Preview-класс запускается только на той же версии JDK и только с флагом. В Maven и Gradle флаг нужен в трёх местах: компилятору, запуску тестов и запуску приложения. С флагом в JVM существует только value-версия LocalDate: identity-версию уже не получить, даже если твой код собран без preview. Поэтому включение preview на существующем сервисе — проверка всех библиотек в classpath, как показал Prepare в шаге 4.

Null-restricted типы: следующий шаг

Главные ограничения flattening в JDK 28 — флаг null и атомарность. Из-за флага Long и Money(long) не укладываются в 64 бита. Черновик JEP «Null-Restricted Value Class Types» убирает оба ограничения для тех классов, которые на это согласились. Синтаксис черновой, в JDK 28 он не компилируется: javac отвечает на Money! ошибкой <identifier> expected.

// Черновик JEP, НЕ JDK 28: синтаксис может измениться
value record Range(int start, int end) {
    public implicit Range();                  // разрешает «нулевой» экземпляр Range(0, 0) без вызова конструктора
}

Range![] ranges = new Range![100];            // элементы не null: флаг не нужен, по умолчанию Range(0, 0)
void printAll(Range! r) { … }                 // printAll(null) — ошибка компиляции

value class Point implements LooselyConsistentValue {   // разрешает неатомарную запись, как у long и double
    double x;
    double y;
    public implicit Point();
}
  • Money! — ссылка, которая не может быть null. Флаг null не нужен, поэтому Long! помещается в 64 бита.
  • Implicit-конструктор. Поле или массив, где null запрещён, надо чем-то заполнить при создании. Класс явно разрешает JVM создавать «нулевой» экземпляр без кода конструктора. Не всякому классу это подходит: у Name(String first, String last) нулевой экземпляр — имя из двух null.
  • LooselyConsistentValue — класс соглашается, что при гонке можно прочитать смесь полей двух значений. Это то же, что JLS разрешает для неvolatile long и double. Взамен большой Point! на два double занимает в массиве ровно 128 бит без ссылок.

Когда value class не нужен

  • Сущность с жизненным циклом. JPA-entity меняет состояние, Hibernate отслеживает её по identity в persistence context и создаёт прокси-наследников. Value class неизменяем и final.
  • Объект — монитор, ключ слабого кеша или элемент IdentityHashMap. Всё это требует identity.
  • Защищаемые данные. Ключи, токены, пароли: == и identityHashCode раскрывают содержимое.
  • Value class с ручной сериализацией. Без writeReplace и readResolve стандартная сериализация не работает. Value record сериализуется сам.
  • Прод на JDK 28. Preview может измениться в следующей версии, а class-файлы привязаны к конкретному JDK. Сейчас value-классы — для экспериментов и замеров.

Подготовиться можно уже на JDK 21: не синхронизироваться на обёртках и датах, не сравнивать их через ==, создавать их фабриками (valueOf, of), моделировать значения через record и прогнать тесты с -XX:DiagnoseSyncOnValueBasedClasses=2.

  • Identity — свойство «этот объект, а не такой же». Её наблюдают ==, synchronized, identityHashCode и слабые ссылки, и из-за неё каждый объект — отдельный адрес в heap.
  • Value class отказывается от identity: поля и класс неявно final, == сравнивает класс и поля рекурсивно, побитово для примитивов. Для значения со строками и double всё равно нужен equals.
  • Операции, требующие identity, падают: ошибка javac или IdentityException. С --enable-preview это касается и Integer с LocalDate в старом коде.
  • Конструктор value-класса заполняет все поля до super(). Поля помечены ACC_STRICT_INIT, и verifier не даёт увидеть их незаданными или изменить потом.
  • Без identity JVM может хранить поля в массиве и в поле другого объекта, если значение с флагом null влезает в 64 бита, и раскладывать объект по регистрам через вызовы. Это оптимизация, а не гарантия.
  • В JDK 28 всё это preview. Null-restricted типы и специализация generics — следующие шаги Valhalla.

На собеседовании

Что такое value-объекты в Project Valhalla?

Это объекты без identity. Обычный объект отличается от такого же по адресу: два LocalDate с одной датой — разные объекты, == между ними ложно, на каждом можно сделать synchronized. Value-класс, объявленный через value class или value record, от этого отказывается. Его поля неявно final, класс final, а == сравнивает класс и значения полей.

Зачем: identity стоит памяти и обращений к ней. Массив дат — это массив ссылок на отдельные объекты с заголовками. Без identity JVM может хранить поля прямо в массиве или в поле другого объекта и не выделять объект вовсе в JIT-коде. В JDK 28 это preview по JEP 401: Integer, Long, Optional, большая часть java.time становятся value-классами при --enable-preview.

  • Это не struct из C#: семантика ссылок сохраняется, ссылка может быть null, копирования при присваивании нет. Раскладку выбирает JVM, гарантирована только семантика.
  • Наследовать value-класс может от Object или абстрактного value-класса. Number и Record стали abstract value, поэтому от них наследуют и value-классы, и identity-классы.
  • В class-файле value-класс — это отсутствие флага ACC_IDENTITY. Добавить value к final-классу с final-полями — бинарно совместимое изменение, но поведение ==, synchronized и слабых ссылок для клиентов меняется.
  • Поля value-класса — strict (JEP 539): заполняются до super(), verifier это проверяет, поэтому недостроенный value-объект никто не видит.
Чем value record отличается от обычного record?

Оба неизменяемы на уровне полей и генерируют equals, hashCode и toString по компонентам. Обычный record — identity-класс: == сравнивает адреса, на нём работает synchronized и WeakReference, JVM хранит его отдельным объектом. У value record identity нет: == сравнивает поля, identity-операции падают, и JVM может разложить его в поле, массив или регистры. С --enable-preview обычные record тоже получают строгие правила конструктора: this в compact constructor до заполнения полей — ошибка компиляции.

Почему String не стал value-классом?

Его API и реализация завязаны на identity. Пул строк и intern() гарантируют, что равные литералы — один и тот же объект, и на этом построен существующий код со сравнением строк через ==. Сам JEP объясняет решение именно зависимостью API и реализации от identity. Поэтому value-класс со строковым полем сравнивается по адресу строки, и ему нужен свой equals.

Как работает == для value-объектов? Можно ли теперь сравнивать Integer через ==?

Для value-объектов == проверяет, неразличимы ли они: тот же класс, примитивные поля совпадают побитово, ссылочные поля равны по == рекурсивно. Для identity-объектов ничего не изменилось — сравниваются адреса. Поэтому с --enable-preview два Integer 1996 равны по ==, и кеш −128..127 для сравнения больше не важен.

Но писать так в обычном коде я не буду. Без preview и на JDK 21 тот же код снова сравнивает адреса и ломается после 127. И даже с preview == не заменяет equals: если внутри value-объекта строка, сравнятся адреса строк, а -0.0 и 0.0 различаются битами.

  • Унаследованный Object.equals у value-класса — это ==, а hashCode и identityHashCode считаются по полям. Value class со строковым полем без своего equals ломает HashSet.
  • Сравнение рекурсивное и может быть долгим на глубоком графе, вплоть до StackOverflowError. Цикла быть не может: поля задаются до super(), и value-объект не может сослаться на себя.
  • По == и identityHashCode можно подбирать значения приватных полей. JEP прямо предупреждает, что value-классы не защищают чувствительные данные.
  • Байткод тот же if_acmpeq. Для identity-объектов JVM оставляет быстрый путь сравнения указателей, медленный путь — только для двух value-объектов одного класса.
Что выведет этот код с --enable-preview? 
value record Fee(Integer kopecks, String currency) { }

Fee f1 = new Fee(1996, "RUB");
Fee f2 = new Fee(1996, "RUB");
Fee f3 = new Fee(1996, "rub".toUpperCase());
System.out.println(f1 == f2);
System.out.println(f1 == f3);
System.out.println(f1.equals(f3));
true
false
true

Integer — value-класс, поэтому два 1996 равны по == рекурсивно, хотя оба больше 127. Литералы "RUB" — один объект из пула строк, поэтому f1 == f2. toUpperCase создаёт новую строку, и f1 == f3 сравнивает два разных identity-объекта String. equals у record вызывает String.equals и видит одинаковые буквы.

Что сломается, если класс станет value-классом или сервис запустят с --enable-preview?

Сломается всё, что опирается на identity. synchronized на value-объекте — ошибка компиляции, если тип известен, или IdentityException при выполнении. wait и notify бросают IllegalMonitorStateException. WeakReference и WeakHashMap — IdentityException. IdentityHashMap склеивает равные значения в один ключ. Код, который рассчитывал, что new даёт уникальный объект, тоже ошибётся.

Неприятно, что с --enable-preview это касается не только моих классов: Integer, Long, LocalDate становятся value-классами для всего classpath. Старый JAR с synchronized на Long упадёт, хотя его никто не пересобирал. Готовлюсь заранее: включаю предупреждения javac и прогоняю тесты с -XX:DiagnoseSyncOnValueBasedClasses=2.

  • Рефлексия больше не пишет в поля value-объекта: Field.set бросает IllegalAccessException даже с --enable-final-field-mutation. Библиотеки, которые создают объект без конструктора и заполняют поля, должны вызывать конструктор.
  • Сериализация value class требует writeReplace и readResolve, иначе InvalidClassException. Value record сериализуется сам через канонический конструктор.
  • Перевод своего класса в value бинарно совместим, если класс final или abstract и поля final. Но клиентов стоит пересобрать: javac записывает value-классы в LoadableDescriptors, и без этого JVM хуже раскладывает поля.
  • Публичные конструкторы — риск: клиенты могли создавать через них «уникальные» объекты для блокировок. JDK по той же причине в Java 9 объявил deprecated конструкторы обёрток.
Что не так с этой блокировкой по счёту? 
@Service
public class TransferService {
    public void transfer(Long fromAccountId, Long toAccountId, long kopecks) {
        synchronized (fromAccountId) {                 // «блокируем счёт»
            long balance = accounts.balance(fromAccountId);
            if (balance < kopecks) throw new InsufficientFundsException();
            accounts.debit(fromAccountId, kopecks);
            accounts.credit(toAccountId, kopecks);
        }
    }
}
  • Сегодня это не блокировка счёта. Для id больше 127 два запроса к одному счёту получают разные объекты Long и не исключают друг друга — двойное списание при гонке. Для id до 127 все такие запросы делят один закешированный объект с любым другим кодом, который синхронизируется на Long.
  • С --enable-preview на JDK 28 Long — value-класс: javac выдаст ошибку required: identity class, а через Object будет IdentityException.
  • Блокировка в памяти одного процесса не защищает от второго экземпляра сервиса. Для денег нужна блокировка в базе: SELECT … FOR UPDATE по счёту или условное обновление UPDATE … SET balance = balance - ? WHERE id = ? AND balance >= ?. Если блокировка в памяти всё же нужна — ConcurrentHashMap<Long, ReentrantLock> и computeIfAbsent.

Гарантирует ли value class, что объект не попадёт в heap? Чем это отличается от escape analysis?

Нет, гарантирована только семантика. JVM получает право не выделять объект: класть его поля в массив или в поле другого объекта (flattening) и раскладывать по регистрам в JIT-коде (scalarization). Но в JDK 28 flattening в изменяемых полях и массивах работает, только если значение вместе с флагом null влезает в 64 бита. Integer и LocalDate влезают, Long и LocalDateTime — нет. В List<Money> и полях типа Object из-за стирания generics лежат обычные ссылки.

Escape analysis работает и для обычных объектов, но должна доказать, что identity никто не видит: объект не уходит в поле, в другой поток или в неинлайненный метод. Value-объекту доказывать нечего, поэтому scalarization работает и через границы методов: JIT передаёт поля аргументами и возвращает их тоже в регистрах.

  • Атомарность нужна из-за гонок: при неатомарной записи другой поток прочитал бы смесь двух значений. Поля самого value-объекта не меняются после конструктора, поэтому внутри него JVM кладёт и большие значения неатомарно.
  • До прогрева C2 value-объекты буферизуются в heap и могут весить больше identity-аналога из-за флага null: Money(long) занимает 24 байта против 16.
  • Проверяю раскладку через -XX:+PrintFieldLayout, а выигрыш — через JMH, JFR и гистограмму heap, а не по ожиданиям.
  • Ограничение 64 бит снимают null-restricted типы: в Long! нет флага null, а LooselyConsistentValue разрешает неатомарную запись. Пока это draft JEP, не JDK 28.

Что дадут null-restricted типы?

Тип Money! запрещает null, поэтому флаг null не нужен, и Long! помещается в 64 бита. Поле или массив такого типа надо чем-то заполнить при создании, поэтому класс объявляет implicit-конструктор, и JVM получает право создавать «нулевой» экземпляр. Классы, которые терпят чтение смеси полей при гонке, реализуют LooselyConsistentValue — тогда и значения больше 64 бит хранятся без ссылок. Это draft JEP, в JDK 28 синтаксиса ! нет.

  • JEP 401: Value Objects (Preview) — основа урока: разделы Comparing value objects, Safe construction, Migrating to value classes, Run-time optimizations. Порядок урока и пример с датами взяты оттуда, демо на платежах и все выводы получены на JDK 28-ea+20.
  • JEP 539: Strict Field Initialization in the JVM (Preview) — правила verifier для strict-полей, early_larval frame, запрет записи рефлексией и сериализации.
  • Valhalla: Value Objects — короткие заметки о производительности в JDK 28: 64 бита, C2, полиморфные переменные, пересборка клиентов.
  • JEP draft: Null-Restricted Value Class Types (Preview) — !, implicit-конструктор, LooselyConsistentValue и модель производительности.
  • JEP 390: Warnings for Value-Based Classes — что можно сделать на JDK 16–21: deprecated конструкторы обёрток и DiagnoseSyncOnValueBasedClasses.
