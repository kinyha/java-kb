Concurrency: Virtual Threads

10 000 запросов по секунде ожидания: 50 секунд на пуле и одна на виртуальных потоках

Сервис должен сделать 10 000 вызовов банка, и каждый ждёт ответа секунду. Код одинаковый, меняется только исполнитель: пул из 200 обычных потоков или новый виртуальный поток на каждую задачу (Java 21):

import java.util.concurrent.*;
import java.util.stream.IntStream;

public class TenThousand {
    static void run(String name, ExecutorService executor) throws Exception {
        long start = System.nanoTime();
        try (executor) {                                             // close() ждёт все задачи
            IntStream.range(0, 10_000).forEach(i -> executor.submit(() -> {
                Thread.sleep(1_000);                                 // запрос к банку: секунда ожидания
                return i;
            }));
        }
        System.out.printf("%-34s %6d мс%n", name, (System.nanoTime() - start) / 1_000_000);
    }

    public static void main(String[] args) throws Exception {
        run("пул из 200 платформенных потоков:", Executors.newFixedThreadPool(200));
        run("виртуальный поток на задачу:", Executors.newVirtualThreadPerTaskExecutor());
    }
}
пул из 200 платформенных потоков:   50215 мс
виртуальный поток на задачу:         1040 мс

Пул обрабатывает по 200 задач за раз — 50 волн по секунде. Виртуальных потоков создано 10 000, все ждут одновременно, и всё заканчивается через секунду. При этом CPU почти не работал: задачи только ждали. Платформенный поток дорог — около 27 мкс на создание и 60–90 КБ памяти (тема Threads), поэтому их держат в пулах ограниченного размера. Виртуальный поток дёшев настолько, что его создают на каждую задачу.

В этой теме — как устроены виртуальные потоки и чем они отличаются от платформенных, где дают выигрыш, а где нет, что такое pinning и как structured concurrency исправляет недостатки CompletableFuture.allOf.

Виртуальный поток снимается с носителя, когда блокируется, и отдаёт его другому

Виртуальный поток — объект JVM, а не поток ОС. Выполняют его обычные потоки-носители (carrier threads) из отдельного ForkJoinPool, по умолчанию их столько же, сколько ядер. Когда виртуальный поток блокируется — sleep, чтение из сокета, BlockingQueue.take, ReentrantLock, — JVM снимает его с носителя: сохраняет его стек в heap и отдаёт носитель следующему. Когда ожидание кончилось, поток снова встаёт в очередь и продолжает на любом свободном носителе.

Смену носителя видно в toString() виртуального потока — там и сам поток, и его текущий носитель:

import java.util.concurrent.*;

public class Carrier {
    public static void main(String[] args) throws Exception {
        try (ExecutorService executor = Executors.newVirtualThreadPerTaskExecutor()) {
            for (int i = 0; i < 3; i++) {
                executor.submit(() -> {
                    System.out.println("до sleep:    " + Thread.currentThread());   // виртуальный поток и его носитель
                    Thread.sleep(100);                                           // блокировка — поток снимается с носителя
                    System.out.println("после sleep: " + Thread.currentThread());
                    return null;
                });
            }
        }
        Thread vt = Thread.ofVirtual().unstarted(() -> { });
        System.out.println("isVirtual: " + vt.isVirtual() + ", daemon: " + vt.isDaemon());
    }
}

до sleep:    VirtualThread[#31]/runnable@ForkJoinPool-1-worker-3
до sleep:    VirtualThread[#28]/runnable@ForkJoinPool-1-worker-1
после sleep: VirtualThread[#30]/runnable@ForkJoinPool-1-worker-3
после sleep: VirtualThread[#28]/runnable@ForkJoinPool-1-worker-1
после sleep: VirtualThread[#31]/runnable@ForkJoinPool-1-worker-2

В этом запуске поток #30 уснул на worker-2, а проснулся на worker-3. От запуска к запуску распределение разное. Виртуальные потоки всегда daemon: JVM их не ждёт.

Цена виртуального потока — его стек в heap, сколько он реально занимает. Миллион виртуальных потоков, каждый из которых ждёт на CountDownLatch, занял 765 МБ heap, то есть около 770 байт на поток. Миллион платформенных потоков ОС не создаст.

Виртуальные потоки ускоряют ожидание, а не вычисления

Виртуальные потоки не делают код быстрее, они позволяют ждать одновременно больше. Для вычислений выигрыша нет — ядер столько же:

import java.util.*;
import java.util.concurrent.*;

public class Cpu {
    static double cpuTask() {                                    // ~2 мс чистых вычислений
        double x = 1;
        for (int i = 0; i < 2_000_000; i++) x = x * 1.0000001 + 1e-9;
        return x;
    }

    static long run(ExecutorService executor) throws Exception {
        long start = System.nanoTime();
        try (executor) {
            Callable<Double> task = Cpu::cpuTask;
            for (Future<Double> f : executor.invokeAll(Collections.nCopies(720, task))) f.get();
        }
        return (System.nanoTime() - start) / 1_000_000;
    }

    public static void main(String[] args) throws Exception {
        run(Executors.newFixedThreadPool(18));                  // прогрев
        System.out.println("CPU-задачи, пул 18 потоков:     " + run(Executors.newFixedThreadPool(18)) + " мс");
        System.out.println("CPU-задачи, виртуальные потоки: " + run(Executors.newVirtualThreadPerTaskExecutor()) + " мс");
    }
}
CPU-задачи, пул 18 потоков:     110 мс
CPU-задачи, виртуальные потоки: 114 мс

Когда полезны:

  • Сервис, где запрос в основном ждёт — базу, HTTP, брокер. Классическая модель «поток на запрос» снова работает без асинхронного кода. В Spring Boot 3.2+ её включает spring.threads.virtual.enabled=true.
  • Много одновременных блокирующих операций: тысячи соединений, опрос внешних систем, fan-out запросов.
  • Замена CompletableFuture-цепочек обычным последовательным кодом: блокироваться дёшево, поэтому не нужно превращать логику в колбэки.

Правила, которые меняются вместе с моделью:

  • Виртуальные потоки не кладут в пул. Пул нужен, чтобы переиспользовать дорогие потоки, а виртуальные дешевле самой задачи. Каждой задаче — новый поток.
  • Ограничение конкурентности — отдельно. Раньше размер пула заодно ограничивал нагрузку на базу. Теперь 10 000 виртуальных потоков одновременно придут за соединением. Лимит ставят явно — Semaphore (тема Synchronizers) или размером пула соединений.
  • ThreadLocal осторожно. Потоков миллионы, и кеш на ThreadLocal вроде «свой форматтер на поток» перестаёт быть кешем и становится утечкой. Для контекста есть ScopedValue (preview в Java 21).

Блокировка внутри synchronized закрепляет виртуальный поток за носителем

В Java 21 виртуальный поток нельзя снять с носителя, пока он внутри synchronized или в нативном методе. Если в этот момент он блокируется, носитель простаивает вместе с ним. Проверим на четырёх носителях: 100 задач, каждая 50 мс ждёт банк под замком. Замки у задач свои — конкуренции за них нет:

import java.util.concurrent.*;
import java.util.concurrent.locks.*;

public class Pinning {
    static long run(String name, Runnable guardedCall) {
        long start = System.nanoTime();
        try (ExecutorService executor = Executors.newVirtualThreadPerTaskExecutor()) {
            for (int i = 0; i < 100; i++) executor.submit(guardedCall);
        }
        long ms = (System.nanoTime() - start) / 1_000_000;
        System.out.printf("%-16s 100 задач по 50 мс ожидания: %5d мс%n", name, ms);
        return ms;
    }

    static void io() {
        try { Thread.sleep(50); } catch (InterruptedException e) { }   // вызов банка под замком
    }

    public static void main(String[] args) {
        System.out.println("носителей: " + System.getProperty("jdk.virtualThreadScheduler.parallelism"));
        run("synchronized:", () -> {
            Object lock = new Object();                                 // у каждой задачи свой замок — конкуренции нет
            synchronized (lock) { io(); }
        });
        run("ReentrantLock:", () -> {
            Lock lock = new ReentrantLock();
            lock.lock();
            try { io(); } finally { lock.unlock(); }
        });
    }
}
$ java -Djdk.virtualThreadScheduler.parallelism=4 Pinning
носителей: 4
synchronized:    100 задач по 50 мс ожидания:  1364 мс
ReentrantLock:   100 задач по 50 мс ожидания:    55 мс

С synchronized 100 задач прошли волнами по четыре: 25 волн по 50 мс. Все четыре носителя были закреплены за спящими потоками. С ReentrantLock поток снимается с носителя, и все 100 ждут одновременно. Разница в 25 раз, хотя замки даже не конкурируют.

Найти закрепления помогает флаг -Djdk.tracePinnedThreads=short (или full со стеком) и событие JFR jdk.VirtualThreadPinned:

$ java -Djdk.virtualThreadScheduler.parallelism=4 -Djdk.tracePinnedThreads=short Pinning
VirtualThread[#28]/runnable@ForkJoinPool-1-worker-1 reason:MONITOR
    Pinning.lambda$main$0(Pinning.java:23) <== monitors:1

Поэтому в Java 21 для кода, который блокируется под замком, рекомендуют ReentrantLock. Короткий synchronized без ввода-вывода внутри безвреден: закрепление на наносекунды ничему не мешает. В JDK 24 ограничение сняли (JEP 491): виртуальный поток отпускает носитель и внутри synchronized. Нативные вызовы и вызовы через JNI закрепляют поток по-прежнему.

Structured concurrency отменяет соседей при первой ошибке

В теме CompletableFuture allOf ждал все три вызова, хотя один упал через 20 мс, — ошибка пришла только через 304 мс, а остальные вызовы доработали впустую. Structured concurrency (в Java 21 — preview, JEP 453) задаёт подзадачам область жизни: они не могут пережить блок, в котором запущены, и отменяются вместе с ним:

import java.util.concurrent.*;
import java.util.concurrent.StructuredTaskScope.Subtask;

public class Scope {
    static String call(String name, int ms, boolean fail) throws InterruptedException {
        try {
            Thread.sleep(ms);
        } catch (InterruptedException e) {
            System.out.println("  " + name + ": отменён");               // соседа отменили — он узнал об этом
            throw e;
        }
        if (fail) throw new IllegalStateException(name + " недоступен");
        return name;
    }

    public static void main(String[] args) throws Exception {
        long start = System.nanoTime();
        try (var scope = new StructuredTaskScope.ShutdownOnFailure()) {  // первая ошибка отменяет остальных
            Subtask<String> client = scope.fork(() -> call("клиент", 100, false));
            Subtask<String> limits = scope.fork(() -> call("лимиты", 20, true));
            Subtask<String> rate = scope.fork(() -> call("курс", 300, false));
            scope.join();                                                // ждём все или первую ошибку
            scope.throwIfFailed();                                       // пробросить её
            System.out.println(client.get() + limits.get() + rate.get());
        } catch (ExecutionException e) {
            System.out.printf("ошибка: %s — через %d мс%n", e.getCause().getMessage(), (System.nanoTime() - start) / 1_000_000);
        }
    }
}
$ javac --release 21 --enable-preview Scope.java
$ java --enable-preview Scope
  клиент: отменён
  курс: отменён
ошибка: лимиты недоступен — через 35 мс

Ошибка пришла через 35 мс вместо 304, а два других вызова получили прерывание и остановились. Порядок строк «отменён» меняется от запуска к запуску. fork запускает каждую подзадачу в новом виртуальном потоке. Блок try гарантирует, что после выхода из него ни одна подзадача не работает. Утечь в фон, как задача после orTimeout в теме CompletableFuture, ей некуда. В дампе потоков jcmd Thread.dump_to_file -format=json подзадачи видны сгруппированными по своей области.

API в статусе preview менялся от версии к версии: в JDK 25 вместо подклассов ShutdownOnFailure — StructuredTaskScope.open() с политиками. Идея та же: время жизни задач совпадает с блоком кода, отмена и ошибки распространяются по дереву.

  • Виртуальный поток — объект JVM. Его выполняют потоки-носители (по умолчанию по числу ядер). При блокировке он снимается с носителя, стек уходит в heap, носитель берёт другой поток.
  • Стоят сотни байт: миллион ждущих потоков — 765 МБ heap. Их не кладут в пул: новый поток на каждую задачу.
  • Выигрыш — для задач, которые ждут: 10 000 вызовов по секунде за 1 с вместо 50 с на пуле из 200. Для вычислений выигрыша нет.
  • Лимит нагрузки на внешние ресурсы ставят явно (Semaphore, пул соединений): размер пула потоков больше его не задаёт.
  • В Java 21 блокировка внутри synchronized закрепляет поток за носителем (в замере — в 25 раз медленнее, чем с ReentrantLock). Поиск: -Djdk.tracePinnedThreads, JFR. В JDK 24 исправлено.
  • Structured concurrency (preview) ограничивает жизнь подзадач блоком и отменяет соседей при первой ошибке: 35 мс вместо 304 у allOf.

На собеседовании

Что такое виртуальные потоки и чем они отличаются от обычных?

Виртуальный поток (Java 21) — поток, которым управляет JVM, а не ОС. Его выполняет небольшой пул потоков-носителей. Когда виртуальный поток блокируется на вводе-выводе, sleep или замке из java.util.concurrent, JVM снимает его с носителя и сохраняет стек в heap, а носитель выполняет другой поток. Поэтому виртуальный поток стоит сотни байт, а не десятки килобайт, и их можно создавать миллионами — по одному на задачу. Платформенный поток — обёртка над потоком ОС, дорогой и ограниченный.

  • Носители — ForkJoinPool размером по числу ядер (jdk.virtualThreadScheduler.parallelism).
  • Виртуальные потоки всегда daemon, не видны в Thread.print — только в Thread.dump_to_file.
  • API тот же Thread: Thread.ofVirtual(), Thread.startVirtualThread, Executors.newVirtualThreadPerTaskExecutor().
Ускорят ли виртуальные потоки вычислительную задачу?

Нет. Они выполняются на тех же ядрах, через те же носители. В замере урока 720 вычислительных задач на пуле из 18 потоков и на виртуальных потоках заняли одинаково: 110 и 114 мс. Выигрыш — только когда задачи ждут.

Что такое pinning?

Ситуация, когда виртуальный поток нельзя снять с носителя. В Java 21 — внутри synchronized и в нативных методах. Если закреплённый поток блокируется, например на вводе-выводе, носитель простаивает вместе с ним, и остальные виртуальные потоки его не получают. В замере урока на 4 носителях 100 задач с ожиданием под synchronized шли в 25 раз дольше, чем под ReentrantLock. Находят через -Djdk.tracePinnedThreads=full или событие JFR jdk.VirtualThreadPinned. Лечат заменой на ReentrantLock, а в JDK 24 проблему с synchronized исправили (JEP 491).

Когда использовать виртуальные потоки и что нужно поменять в коде?

Когда задачи в основном ждут: сервис «поток на запрос» с походами в базу и HTTP, тысячи одновременных соединений. Что меняется: виртуальные потоки не пулят — создают на каждую задачу; нагрузку на базу и партнёров ограничивают явно, через Semaphore или пул соединений, а не размером пула потоков; не кешируют дорогие объекты в ThreadLocal; блокирующий ввод-вывод под synchronized в Java 21 заменяют на ReentrantLock.

Сервис перевели на виртуальные потоки, и через час база начала отвечать «too many connections». Что случилось?

Раньше пул из 200 потоков неявно ограничивал число одновременных запросов к базе. Виртуальных потоков тысячи, и все одновременно идут за соединением. Нужно явное ограничение: пул соединений разумного размера с таймаутом ожидания или Semaphore перед обращением к базе.

Что такое structured concurrency?

Подход, при котором подзадачи живут в пределах блока кода, запустившего их, как локальные переменные. StructuredTaskScope (preview в Java 21) запускает подзадачи в виртуальных потоках, ждёт их в join() и гарантирует, что после выхода из блока ни одна не работает. Политика ShutdownOnFailure отменяет остальных при первой ошибке: в замере урока ошибка пришла через 35 мс, а не через 304, как у CompletableFuture.allOf.

  • Oracle: Virtual Threads (JDK 21) — руководство: когда применять, не пулить, ограничивать конкурентность.
  • JEP 453: Structured Concurrency (Preview) — StructuredTaskScope в Java 21.
  • JEP 491: Synchronize Virtual Threads without Pinning — что изменилось в JDK 24.
