Window Functions

В отчёте каждому платежу нужен контекст: оборот продавца, место по сумме, предыдущая оплата. Оконная функция дописывает этот контекст к строке, сохраняя сам платёж. Сначала она выбирает его partition, затем использует порядок строк и, для некоторых расчётов, границы frame. Ошибку в отчёте ищи в этих трёх решениях: надпись OVER сама по себе ещё не говорит, какие платежи попали в расчёт.

Итог продавца нужен рядом с каждым платежом

Поддержка проверяет выплаты продавцам. В отчёте должны остаться все платежи, а рядом с каждым — общий оборот его продавца. Разработчик добавляет GROUP BY merchant и получает правильные суммы, но теряет строки платежей: по такому отчёту уже нельзя найти спорную оплату по id.

У нас шесть успешных платежей двух продавцов. Суммы маленькие, чтобы считать в уме; все они в копейках одной валюты. paid_on — день расчёта, поэтому два разных платежа могут иметь одну дату. id различает их и даёт устойчивый порядок внутри дня.

-- Все суммы в копейках одной валюты; paid_on — день расчёта.
CREATE TEMP TABLE payments (
  id integer PRIMARY KEY,
  merchant text NOT NULL,
  paid_on date NOT NULL,
  amount integer NOT NULL CHECK (amount > 0)
);
INSERT INTO payments VALUES
  (101, 'A', '2026-10-01', 100),
  (102, 'A', '2026-10-01', 200),
  (103, 'A', '2026-10-02', 300),
  (104, 'A', '2026-10-03', 200),
  (201, 'B', '2026-10-01', 500),
  (202, 'B', '2026-10-02', 500);
SELECT merchant, sum(amount) AS total
FROM payments
GROUP BY merchant                  -- один результат на продавца
ORDER BY merchant;
 merchant | total
----------+-------
 A        |   800
 B        |  1000
(2 rows)

Группировка сворачивает четыре платежа A в одну строку с суммой 800, два платежа B — в одну строку с суммой 1000. Добавить id в GROUP BY не поможет: получится отдельная группа на платёж, и сумма будет равна его собственному amount. Нам нужен расчёт по группе без сворачивания её строк.

SELECT id, merchant, amount,
       sum(amount) OVER (PARTITION BY merchant) AS total
FROM payments                       -- каждая строка платежа остаётся
ORDER BY merchant, id;
 id  | merchant | amount | total
-----+----------+--------+-------
 101 | A        |    100 |   800
 102 | A        |    200 |   800
 103 | A        |    300 |   800
 104 | A        |    200 |   800
 201 | B        |    500 |  1000
 202 | B        |    500 |  1000
(6 rows)

OVER превращает вызов sum в оконный. Для 101 PostgreSQL находит partition A и записывает её итог 800 рядом с платежом. У 102 тот же контекст, но отдельная строка. Общий результат повторяется, идентичность оплат сохраняется.

PARTITION BY делит входные строки по указанным значениям; это не физические партиции таблицы. Без него весь вход запроса образует одну partition. А без ORDER BY в этом OVER стандартный frame охватывает всю partition: оборот не зависит от позиции текущего платежа. Дальше порядок понадобится, и тогда привычная сумма начнёт вести себя иначе.

Колонка total — повторённый итог, а не сумма конкретного платежа. Если сложить её по всем строкам отчёта, оборот A посчитается четыре раза. Окно не меняет смысл исходных строк и не исправляет дубли, которые раньше создал JOIN.

Равная сумма может означать общее место

Теперь поддержке нужны самые крупные платежи каждого продавца. Для A суммы по убыванию — 300, 200, 200, 100. Вопрос «какое место занимает платёж?» неоднозначен: это номер отдельной строки, место в соревновании или номер отличающейся суммы? Три функции отвечают на три разных вопроса.

ROW_NUMBER нумерует строки внутри partition от 1. RANK присваивает равным значениям одно место, а следующее место учитывает, сколько строк уже прошло: 1, 2, 2, 4. DENSE_RANK считает группы равных значений, поэтому получается 1, 2, 2, 3. Здесь равенство определяется всеми выражениями в оконном ORDER BY; такие строки называют peers.

SELECT merchant, id, amount,
       row_number() OVER (
         PARTITION BY merchant ORDER BY amount DESC, id
       ) AS rn,                     -- id разрешает равенство для выбора строки
       rank() OVER (
         PARTITION BY merchant ORDER BY amount DESC
       ) AS rnk,                    -- одинаковые суммы делят одно место
       dense_rank() OVER (
         PARTITION BY merchant ORDER BY amount DESC
       ) AS dense
FROM payments
ORDER BY merchant, amount DESC, id;  -- порядок вывода задаётся отдельно
 merchant | id  | amount | rn | rnk | dense
----------+-----+--------+----+-----+-------
 A        | 103 |    300 |  1 |   1 |     1
 A        | 102 |    200 |  2 |   2 |     2
 A        | 104 |    200 |  3 |   2 |     2
 A        | 101 |    100 |  4 |   4 |     3
 B        | 201 |    500 |  1 |   1 |     1
 B        | 202 |    500 |  2 |   1 |     1
(6 rows)

У ROW_NUMBER в запросе есть дополнительный ключ id. Благодаря ему из двух сумм 200 сначала идёт платёж 102, потом 104: они стабильно получают номера 2 и 3. У RANK и DENSE_RANK в порядке оставлена только сумма, чтобы 102 и 104 продолжали делить место. Разные окна в одном запросе могут задавать разные отношения между теми же входными строками.

Ключ разрешения равенства входит в правило отчёта. Для выбора более ранней оплаты используй время и уникальный id. Если равные суммы должны пройти вместе, оставь их peers в RANK; для устойчивого отображения добавь id только во внешний ORDER BY.

ORDER BY внутри OVER заодно задаёт порядок всего результата.

Он задаёт порядок для расчёта этой функции. Результат запроса упорядочивает внешний ORDER BY. Можно посчитать место по убыванию суммы, а показать платежи по дате; номера останутся привязанными к суммам.

Без полного порядка ROW_NUMBER выдаст разные номера равным строкам, но не определит, кто получит меньший. При повторении отчёта может смениться платёж на границе top-N. RANK сохранит общее место, если peers заданы бизнес-критерием.

Нарастающий итог зависит от границы frame

Выплата идёт по нескольким платежам, и бухгалтер просит показать оборот после каждой оплаты. У A платёж 101 приносит 100, следующий 102 — ещё 200. Разработчик добавляет к sum сортировку по дате и ждёт 100, 300, 600, 800. Но первые две строки обе показывают 300.

Partition задаёт доступный набор строк. Frame выбирает из него строки для расчёта у текущей строки. В PostgreSQL стандартная граница — RANGE BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW. При оконном ORDER BY она идёт от начала partition до последнего peer текущей строки. Для даты 1 октября оба платежа равны по ключу порядка, поэтому frame включает и 101, и 102 уже для первой строки.

SELECT id, paid_on, amount,
       sum(amount) OVER (
         PARTITION BY merchant ORDER BY paid_on
       ) AS by_day,                 -- default RANGE включает весь текущий день
       sum(amount) OVER (
         PARTITION BY merchant ORDER BY paid_on, id
         ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW
       ) AS by_payment,             -- устойчивый префикс до конкретного платежа
       sum(amount) OVER (
         PARTITION BY merchant ORDER BY paid_on, id
       ) AS unique_range            -- уникальный порядок убрал равенства и у RANGE
FROM payments
WHERE merchant = 'A'
ORDER BY paid_on, id;
 id  |  paid_on   | amount | by_day | by_payment | unique_range
-----+------------+--------+--------+------------+--------------
 101 | 2026-10-01 |    100 |    300 |        100 |          100
 102 | 2026-10-01 |    200 |    300 |        300 |          300
 103 | 2026-10-02 |    300 |    600 |        600 |          600
 104 | 2026-10-03 |    200 |    800 |        800 |          800
(4 rows)

В by_payment сделаны два осознанных выбора: id задаёт однозначную последовательность внутри даты, а ROWS заканчивает frame на конкретной текущей строке. Поэтому после 101 видны только его 100 копеек. В unique_range оставлен стандартный RANGE, но добавлен тот же уникальный ключ: peers из нескольких строк больше нет, и итог совпал с ROWS. Причина различия — и порядок, и правило границы; сравнивать только слова RANGE и ROWS недостаточно.

На всех четырёх шагах partition A содержит те же платежи. Меняется часть, вошедшая в frame: сверху peers определены датой, снизу порядок уточнён id. На первом платеже разница составляет 200, на остальных суммы совпадают.

ROWS выражает расстояние в строках, а не в днях: ROWS BETWEEN 2 PRECEDING AND CURRENT ROW берёт текущий платёж и до двух предшествующих, даже если между ними неделю не было оплат. RANGE с временным смещением задаёт расстояние по значению даты или времени. Это уже разные бизнес-задачи: «последние три оплаты» и «оплаты за последние три дня» нельзя подменять друг другом.

Для суммы по всей partition проще убрать оконный ORDER BY. Если порядок нужен другой функции, задай отдельное окно или полный frame. Добавление сортировки «для красоты» к SUM OVER меняет охват по умолчанию: вместо общего оборота получится нарастающий итог.

LAG и LEAD сравнивают соседей в последовательности

После итога поддержке нужна другая подсказка: как сумма оплаты изменилась относительно предыдущей. Делать self join по id - 1 опасно: идентификаторы могут иметь пропуски, а порядок расчёта не обязан совпадать с их ростом. Нам нужен предыдущий платёж этого продавца в выбранном порядке, а не арифметически соседний ключ.

LAG(amount) берёт сумму на одну строку раньше внутри partition; LEAD(amount) — на одну строку позже. На первом платеже у LAG нет соседа, на последнем его нет у LEAD; без дополнительных аргументов результат NULL. Перейти от первого платежа B к последнему A нельзя: partition разделяет их последовательности.

SELECT merchant, id, amount,
       sum(amount) OVER w AS frame_sum,
       lag(amount) OVER w AS prev_amount,
       lead(amount) OVER w AS next_amount,
       amount - lag(amount) OVER w AS delta
FROM payments
WINDOW w AS (
  PARTITION BY merchant ORDER BY paid_on, id
  ROWS BETWEEN CURRENT ROW AND CURRENT ROW
)                                   -- SUM видит одну строку, LAG/LEAD — соседей
ORDER BY merchant, paid_on, id;
 merchant | id  | amount | frame_sum | prev_amount | next_amount | delta
----------+-----+--------+-----------+-------------+-------------+-------
 A        | 101 |    100 |       100 |        NULL |         200 |  NULL
 A        | 102 |    200 |       200 |         100 |         300 |   100
 A        | 103 |    300 |       300 |         200 |         200 |   100
 A        | 104 |    200 |       200 |         300 |        NULL |  -100
 B        | 201 |    500 |       500 |        NULL |         500 |  NULL
 B        | 202 |    500 |       500 |         500 |        NULL |     0
(6 rows)

Здесь специально задан frame из одной текущей строки. Его видно по frame_sum: сумма равна своему amount. Но у строки 103 LAG всё равно находит 200 в строке 102, а LEAD находит 200 в 104. Эти функции ищут смещение в последовательности partition, а не край агрегатного frame. Для обычного сравнения соседей frame можно вообще не указывать.

WINDOW w AS (...) даёт имя общему описанию окна: все четыре выражения используют один порядок, и он не расходится при правке запроса. Разница amount - lag(amount) у первой строки тоже NULL, потому что неизвестная предыдущая сумма не превращается автоматически в ноль. По такому результату можно отличить «предыдущей оплаты нет» от «сумма не изменилась»: у B вторая оплата даёт настоящую разницу 0.

«Следующий» — сосед по выбранным ключам, а не событие из будущего. Поздняя вставка между двумя оплатами изменит соседей при повторном отчёте. Для воспроизводимости нужны срез данных и устойчивый бизнес-порядок.

Фильтрация входа меняет соседей. Если убрать вчерашние платежи в WHERE до расчёта LAG, первая строка сегодняшнего отчёта не увидит вчерашнюю оплату. Если она нужна для сравнения, посчитай окно по истории и только затем ограничь строки отчёта внешним запросом.

NULL соседа и отсутствие соседа — разные причины

У LAG(value, offset, default) значение default используется, когда строки на нужном смещении нет. Если сосед есть, но его value равен NULL, результат остаётся NULL. Подмена через COALESCE объединит эти причины — это допустимо только по правилу отчёта.

В нашей таблице amount NOT NULL, поэтому NULL в prev_amount однозначно означает начало partition. PostgreSQL 17 не реализует IGNORE NULLS для этих функций: соседняя строка с пустым значением не пропускается. Если данные допускают такие значения, сначала реши, что для бизнеса означает «предыдущая сумма».

LAST_VALUE смотрит на конец frame, а не всей partition

Для сверки нужен последний платёж каждого продавца, но его id хочется оставить рядом со всеми предыдущими оплатами. Название LAST_VALUE выглядит подходящим: разделяем по продавцу, сортируем по дате и id. Однако функция возвращает 101 рядом с 101, 102 рядом с 102 и так далее. В отчёт попал текущий платёж вместо последнего.

Причина уже знакома: эта функция читает последнюю строку frame. При полном порядке paid_on, id у текущей строки нет других peers. Стандартный frame кончается на ней самой, поэтому «последнее значение» оказывается текущим id. Порядок выбран правильно; неверна ожидаемая граница.

SELECT merchant, id,
       last_value(id) OVER (
         PARTITION BY merchant ORDER BY paid_on, id
       ) AS default_last,           -- конец default frame здесь — текущая строка
       last_value(id) OVER (
         PARTITION BY merchant ORDER BY paid_on, id
         ROWS BETWEEN UNBOUNDED PRECEDING AND UNBOUNDED FOLLOWING
       ) AS partition_last          -- конец frame явно перенесён в конец partition
FROM payments
ORDER BY merchant, paid_on, id;
 merchant | id  | default_last | partition_last
----------+-----+--------------+----------------
 A        | 101 |          101 |            104
 A        | 102 |          102 |            104
 A        | 103 |          103 |            104
 A        | 104 |          104 |            104
 B        | 201 |          201 |            202
 B        | 202 |          202 |            202
(6 rows)

UNBOUNDED FOLLOWING переносит конец frame к последней строке partition. Теперь у всех платежей A последним стал 104, у B — 202. В каждом случае сохраняется текущая строка отчёта, но контекст берётся из конца её последовательности. Если оставить порядок только по дате, несколько платежей последнего дня снова окажутся равны: выбор одного конкретного последнего id потребует дополнительного ключа.

Frame — общая настройка, которая одинаково ограничивает все оконные функции.

SUM и LAST_VALUE используют frame, а LAG и LEAD ищут соседей по partition и порядку. RANK описывает место peer-группы в partition. Сначала определи, на какой набор строк смотрит выбранная функция, затем меняй frame.

MAX(id) не заменяет последний платёж по времени, если идентификаторы не отражают бизнес-порядок. Если же нужна только одна последняя строка на продавца, проще дать строкам ROW_NUMBER по убыванию даты и id, затем оставить номер 1. LAST_VALUE с полным frame нужен именно тогда, когда последний контекст должен сопровождать остальные строки.

Полный frame может читать строки позже текущей. Его результат не означает «что сервис знал при оплате 101»: он рассчитан по всему срезу истории. Для состояния на момент платежа нужна граница до текущей строки.

Top-N фильтрует уже рассчитанные номера

Вернёмся к отчёту о двух крупнейших платежах продавца. Окно присваивает номер каждой строке, но само по себе не удаляет остальные. Написать WHERE row_number() OVER (...) <= 2 на том же уровне нельзя: WHERE определяет входные строки раньше, чем логически считаются окна. Номер в этот момент ещё не существует.

Сделай границу запроса явной: внутри посчитай номер, снаружи отфильтруй его как обычную колонку. Это логическая граница расчётов; она не обещает создание временной таблицы. Те же два уровня можно записать через CTE; их устройство разобрано в Subqueries & CTE.

SELECT merchant, id, amount, rn
FROM (
  SELECT merchant, id, amount,
         row_number() OVER (
           PARTITION BY merchant ORDER BY amount DESC, id
         ) AS rn
  FROM payments
) AS numbered
WHERE rn <= 2                       -- номер уже стал обычной колонкой
ORDER BY merchant, rn;
 merchant | id  | amount | rn
----------+-----+--------+----
 A        | 103 |    300 |  1
 A        | 102 |    200 |  2
 B        | 201 |    500 |  1
 B        | 202 |    500 |  2
(4 rows)

У A выбран 103 с суммой 300 и 102 с суммой 200; равный ему 104 не попал, потому что нужен максимум из двух конкретных строк. У B осталось две оплаты по 500. Если в partition меньше N строк, вернутся все имеющиеся — окно не создаёт недостающие платежи.

Требование «два первых места с сохранением равных» меняет функцию и peers. Убери уникальный id из порядка RANK, чтобы одинаковые суммы делили место:

SELECT merchant, id, amount, rnk
FROM (
  SELECT merchant, id, amount,
         rank() OVER (
           PARTITION BY merchant ORDER BY amount DESC
         ) AS rnk                   -- id не включён: равные суммы делят место
  FROM payments
) AS ranked
WHERE rnk <= 2
ORDER BY merchant, rnk, id;
 merchant | id  | amount | rnk
----------+-----+--------+-----
 A        | 103 |    300 |   1
 A        | 102 |    200 |   2
 A        | 104 |    200 |   2
 B        | 201 |    500 |   1
 B        | 202 |    500 |   1
(5 rows)

У A теперь три платежа: 103 на месте 1, а 102 и 104 делят место 2. Это корректное превышение N по числу строк. DENSE_RANK <= N выбирает N различных уровней суммы; после большой группы равных его результат может отличаться от RANK <= N, потому что пропуски мест отсутствуют.

«Крупнейшие оплаты за октябрь» — фильтр периода до окна. «Сегодняшние оплаты с местом среди всей истории» — фильтр дня после окна. Окна видят результат FROM, WHERE, обычной группировки и HAVING; после группировки по дням они работают с днями, а не с исходными оплатами.

Почему top-N не обещает дешёвое чтение

Условие rn <= 2 ограничивает итог, но чтобы определить победителей, базе нужен подходящий порядок внутри продавцов. На большой истории смотри EXPLAIN (ANALYZE, BUFFERS): сколько входных строк прочитано, где сортировка, не выходит ли она во временные файлы. Само наличие окна не гарантирует полного сканирования, а внешний фильтр не гарантирует чтения только двух строк на продавца: это решает конкретный план.

Индекс выбирают под реальные фильтры и ключи порядка. Для отчёта по множеству продавцов окно часто выражает задачу удобно. Если нужен один продавец и две оплаты, достаточно WHERE merchant = ... ORDER BY amount DESC, id LIMIT 2. Для других вариантов сравнивай планы, а не число строк SQL. Работа с ними — в Slow Queries и Indexes.

Перед добавлением окна назови единицу строки: платёж, продавец или день. Затем реши, кто его соседи, что означает равенство и какая граница нужна расчёту. Окно полезно, когда к этой строке нужен контекст; если нужен только итог на продавца, обычный GROUP BY короче и точнее выражает задачу.

  • Оконная агрегация сохраняет входные строки. PARTITION BY разделяет расчёт по продавцам, но не сворачивает платежи.
  • ROW_NUMBER считает строки, RANK — места с пропусками, DENSE_RANK — peer-группы без пропусков. Равенство задают все ключи оконного порядка.
  • Стандартный RANGE идёт до последнего peer текущей строки. Для устойчивого итога после каждой оплаты задай полный порядок и явный ROWS.
  • LAG и LEAD ищут соседей в partition. LAST_VALUE читает конец frame; последний платёж всей partition требует другой границы.
  • Входные фильтры меняют контекст окна. Для top-N и фильтра по оконному результату нужен внешний запрос; порядок вывода задаётся отдельно.

На собеседовании

Чем оконная функция отличается от GROUP BY?

Я использую GROUP BY для одного результата на группу. Когда нужен каждый платёж и оборот его продавца рядом, беру SUM(amount) OVER (PARTITION BY merchant). Четыре платежа A остаются четырьмя строками с общим итогом 800.

В OVER я выбираю partition, порядок и frame. Порядок нужен для места или соседей, frame ограничивает оконную агрегацию. Внешний ORDER BY отдельно задаёт отображение результата.

  • Окно видит результат WHERE, GROUP BY и HAVING своего уровня. После группировки по дням оно аннотирует дни, а не исходные платежи.
  • Повторённый итог нельзя суммировать по детальным строкам. Окно не устраняет размножение платежей предыдущим JOIN.
  • Несколько окон используют один вход, но могут задавать разные partitions и порядок. Связанные расчёты удобно объединить именованной спецификацией WINDOW.

Как выбрать между ROW_NUMBER, RANK и DENSE_RANK?

Я уточняю смысл равенства. ROW_NUMBER нумерует строки отдельно; для устойчивого выбора добавляю ключ разрешения равенства. RANK даёт общее место и пропуски: 1, 2, 2, 4. DENSE_RANK считает уровни без пропусков: 1, 2, 2, 3.

Для не более N оплат беру ROW_NUMBER <= N, для N мест с равными — RANK <= N, для N различных сумм — DENSE_RANK <= N. Фильтрую номер внешним запросом.

  • Peers определяет вся оконная сортировка. Уникальный id в RANK уничтожает общие места; только во внешней сортировке он их сохраняет.
  • Неопределённый порядок peers у ROW_NUMBER меняет состав top-N. Критерий выбора входит в контракт отчёта.
  • После большой группы равных лидеров RANK и DENSE_RANK дают разный проходной порог: один учитывает занятые места, другой считает уровни.
Разработчик добавил id в RANK, чтобы отчёт был стабильным. Что изменилось? 
SELECT id, amount,
       rank() OVER (ORDER BY amount DESC) AS by_amount,
       rank() OVER (ORDER BY amount DESC, id) AS with_id
FROM payments
WHERE merchant = 'A'
ORDER BY amount DESC, id;
 id  | amount | by_amount | with_id
-----+--------+-----------+---------
 103 |    300 |         1 |       1
 102 |    200 |         2 |       2
 104 |    200 |         2 |       3
 101 |    100 |         4 |       4
(4 rows)

Суммы 200 перестали быть peers: пары (200, 102) и (200, 104) различны. Второй платёж получил место 3 и выпал бы из условия rank <= 2. Для стабильного отображения с общим местом оставь сумму в окне, а id добавь во внешнюю сортировку.

Почему running sum одинаковый у нескольких соседних строк?

Я проверю frame и ключи порядка. Стандартный RANGE идёт от начала partition до последнего peer текущей строки. При сортировке только по дате обе оплаты одного дня входят вместе: вместо 100 и 300 получаем 300 и 300.

Для итога после каждой оплаты задаю однозначный порядок paid_on, id и ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW. Для итога к концу дня общая сумма у всех оплат дня корректна.

  • При уникальном порядке RANGE тоже не объединяет несколько peers. Совпадение его результата с ROWS на таком наборе не делает режимы одинаковыми.
  • ROWS 2 PRECEDING измеряет строки, а не дни. Смещение RANGE измеряет значения ключа; в PostgreSQL оно требует одного выражения ORDER BY.
  • Без оконного ORDER BY стандартный frame равен всей partition. Добавление сортировки меняет общий итог на нарастающий.

Чем LAG отличается от LAST_VALUE и где у них ловушки?

Через LAG я беру значение предыдущей строки внутри partition, через LEAD — следующей. У края без соседа результат по умолчанию NULL. Порядок задаю по бизнес-времени и ключу разрешения равенства.

LAST_VALUE читает конец frame. При стандартной границе и уникальном порядке это текущая строка. Для последнего платежа всей partition задаю конец UNBOUNDED FOLLOWING.

  • Frame из текущей строки ограничит SUM и LAST_VALUE, но не заставит LAG забыть предыдущую строку partition.
  • Третий аргумент LAG заменяет отсутствие строки, а не её NULL. PostgreSQL 17 не поддерживает IGNORE NULLS.
  • Последнее значение всей истории использует более поздние данные. Оно не описывает сведения на момент текущей оплаты.
Почему первый платёж 2 октября потерял предыдущий id?

Сравни prev_id для 103: дата отфильтрована до окна или после него.

SELECT id, paid_on,
       lag(id) OVER (ORDER BY paid_on, id) AS prev_id
FROM payments
WHERE merchant = 'A' AND paid_on >= DATE '2026-10-02'
ORDER BY paid_on, id;
 id  |  paid_on   | prev_id
-----+------------+---------
 103 | 2026-10-02 |    NULL
 104 | 2026-10-03 |     103
(2 rows)
SELECT id, paid_on, prev_id
FROM (
  SELECT id, paid_on,
         lag(id) OVER (ORDER BY paid_on, id) AS prev_id
  FROM payments
  WHERE merchant = 'A'
) AS history
WHERE paid_on >= DATE '2026-10-02'
ORDER BY paid_on, id;
 id  |  paid_on   | prev_id
-----+------------+---------
 103 | 2026-10-02 |     102
 104 | 2026-10-03 |     103
(2 rows)

Первое окно не видит прежние дни: для 103 сосед отсутствует. Второе видит историю и возвращает 102; затем ранние дни скрыты. Это разные отчёты: сосед внутри периода или в истории.

Как написать top-N в каждой группе и не поменять смысл фильтров?

Внутри я считаю ROW_NUMBER по продавцу с нужным порядком, снаружи оставляю rn <= N. Номер становится обычной колонкой перед фильтрацией; окно в WHERE того же уровня запрещено, потому что WHERE определяет его вход.

До окна ограничиваю участников отбора, например успешные оплаты октября. После него — рассчитанное место или отображаемые строки с контекстом истории. Выбор функции зависит от того, должны ли равные пройти вместе.

  • Подзапрос задаёт логическую границу, но не обещает материализацию. Чтение, сортировки и использование индекса проверяю по плану.
  • Внешний LIMIT ограничивает весь отчёт. Для одного продавца ORDER BY ... LIMIT достаточен, для множества нужны отдельные отборы или окно.
  • После JOIN окно нумерует строки соединения. Сначала обеспечиваю одну строку на платёж, иначе он может занять несколько мест.
