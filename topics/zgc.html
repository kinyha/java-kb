JVM: ZGC & Shenandoah

Паузе G1 есть пол — копирование живых, пока приложение стоит

Сервис авторизации платежей обязан ответить банку-эквайеру за 50 мс, иначе транзакция отклоняется. В heap 24 ГБ живут кеши лимитов и антифрод-профили. G1 работает честно, но его паузы — десятки миллисекунд, иногда за сотню: за время паузы он копирует живые объекты выбранных регионов, и чем больше живых, тем дольше. Из темы G1 мы знаем, что у этой паузы есть пол, и никакая цель MaxGCPauseMillis его не опустит.

Чтобы пауза перестала зависеть от объёма данных, копировать объекты нужно параллельно с работой приложения. Так устроены ZGC и Shenandoah: маркировка, перемещение и исправление ссылок идут конкурентно, а в паузах остаётся только работа, не зависящая от размера heap, — прежде всего снять корни со стеков потоков. Разберём, как можно двигать объект, который в это время читает приложение, и сколько это стоит на самом деле.

Барьер на чтение ссылки чинит её, если объект переехал

Главная трудность: сборщик скопировал объект на новое место, а у приложения в полях других объектов ещё лежат старые адреса. G1 переписывает такие ссылки в паузе. ZGC переписывает их лениво — в момент, когда приложение ссылку читает. Для этого JIT вставляет после каждой загрузки ссылки из поля несколько инструкций — load barrier. Его логика, упрощённо:

// Псевдокод барьера: выполняется при каждом чтении ссылки из поля, например a.rules
Object loadReference(Object holder, Field field) {
    Object ref = field.get(holder);
    if (isGood(ref)) {                          // быстрый путь: одна проверка битов указателя
        return ref;
    }
    Object fixed = forwardingTable.lookup(ref); // объект переехал? взять новый адрес
    if (fixed == null) fixed = relocateNow(ref);// ещё не переехал — перенести прямо сейчас
    field.compareAndSet(holder, ref, fixed);    // «самолечение»: записать исправленную ссылку обратно
    return fixed;
}

Проверка «хорош ли указатель» — одна инструкция сравнения, и почти всегда она проходит. Медленный путь срабатывает на первом чтении ссылки после переезда объекта и заодно чинит поле, чтобы следующие чтения шли быстро. Пролистай, как это выглядит.

Если поток приложения дочитался до объекта раньше сборщика, барьер перенесёт объект сам. Поэтому переезд никогда не ждёт паузы: его может закончить любой поток, который первым коснулся объекта.

Состояние ссылки ZGC хранит прямо в битах указателя

Как барьер за одну инструкцию понимает, что указатель устарел? ZGC держит служебные биты прямо в 64-битном указателе — это окрашенные указатели (colored pointers). Адрес занимает младшие биты, а несколько битов над ним — «цвет»: был ли объект помечен в текущем цикле и исправлена ли ссылка после переезда. Барьер сравнивает цвет с текущим «хорошим» — вот и вся проверка.

Но процессор не умеет обращаться к памяти по адресу с лишними битами. Классический ZGC решал это хитро: отображал одну и ту же физическую память по трём виртуальным адресам, по одному на цвет. Это видно в его логе при старте — адресное пространство умножено на три:

$ java -XX:+UseZGC -Xlog:gc+init -version
Using legacy single-generation mode
Address Space Size: 196608M x 3 = 589824M                  # одна и та же память в трёх «видах»

$ java -XX:+UseZGC -XX:+ZGenerational -Xlog:gc+init -version
Address Space Size: 196608M                                # поколенческий режим обходится без этого

Из-за тройного отображения классический ZGC пугал мониторинг: RSS процесса мог показывать втрое больше реального. Поколенческий ZGC устроен иначе: барьер сам снимает цветные биты перед обращением к памяти, и отображение одно. Детали реализации меняются от версии к версии, а суть остаётся: состояние ссылки проверяется одной инструкцией при каждом чтении.

Shenandoah решает ту же задачу с другой стороны

Ранний Shenandoah хранил в каждом объекте дополнительное слово с адресом переадресации (Brooks pointer). С JDK 13 от него отказались: адрес пишется в заголовок старой копии, а объекты стали на слово меньше. На практике выбор между ZGC и Shenandoah решают доступность в твоём дистрибутиве JDK и замер на своей нагрузке.

Паузы по десятым миллисекунды, если памяти с запасом

Проверим на одной нагрузке все сборщики. Программа 10 секунд обрабатывает платежи и держит живыми последние N из них — как очередь антифрода из темы Generations.

import java.util.ArrayDeque;

public class Bench {
    record PaymentDto(long id, long amount, byte[] body) { }

    static final ArrayDeque<PaymentDto> RECENT = new ArrayDeque<>();

    public static void main(String[] args) {
        int keep = Integer.parseInt(args[0]);                  // сколько платежей держать живыми
        long end = System.nanoTime() + 10_000_000_000L;         // 10 секунд работы
        long processed = 0, sum = 0;
        while (System.nanoTime() < end) {
            for (int i = 0; i < 1000; i++) {
                PaymentDto dto = new PaymentDto(processed, processed % 1000, new byte[200]);
                sum += dto.amount();
                RECENT.addLast(dto);
                if (RECENT.size() > keep) RECENT.removeFirst();  // старый платёж становится мусором
                processed++;
            }
        }
        System.out.println("обработано " + processed / 1_000_000 + " млн платежей, sum=" + sum % 7);
    }
}

Замер на JDK 21, macOS, 18 ядер, один поток приложения. Паузы взяты из -Xlog:safepoint, одинаково для всех сборщиков. CPU — время процесса по /usr/bin/time. Сначала heap с запасом: 4 ГБ при 720 МБ живых данных (N = 3 000 000):

Паузы у конкурентных сборщиков — десятые и сотые доли миллисекунды, в сотни раз короче, чем у G1. И на этой нагрузке они не проиграли в пропускной способности, а выиграли: миллионы платежей средней жизни ломают гипотезу поколений, и G1 с Parallel тратят много работы на их перекладывание из young в old. Отсюда урок, который важнее любых цифр: результат зависит от нагрузки, мерь на своей. На типичной нагрузке с маленьким живым набором (N = 20 000) все сборщики обработали 970–1200 млн, а паузы остались того же порядка: около 2 мс у G1 и Parallel и 0,05–0,16 мс у конкурентных.

Однопоточная нагрузка на 18 ядрах — лучший случай для конкурентного сборщика: его потокам есть где работать. В сервисе, который загружает все ядра, потоки ZGC отнимают CPU у запросов, и пропускная способность падает. Проверяй под реальной нагрузкой и с реальным числом ядер пода.

Цена низких пауз — запас памяти, иначе пауза прячется в allocation stall

Конкурентный сборщик освобождает память, пока приложение продолжает выделять новую. Если выделять быстрее, чем он успевает собирать, свободная память кончится. Проверим на той же нагрузке, но с тесным heap: 1,2 ГБ при 720 МБ живых данных.

По паузам safepoint ZGC всё ещё выглядит идеально — 16 мс за 10 секунд. Но в его логе другое:

[0.155s][info][gc] Allocation Stall (main) 14.328ms           # поток приложения ждал память 14 мс
[0.206s][info][gc] Allocation Stall (main) 36.898ms

Allocation stall — поток приложения хотел выделить объект, свободной памяти нет, и он ждёт, пока сборщик её освободит. Для запроса это та же пауза, только её нет в логе safepoint и в метриках пауз GC. За 10 секунд таких ожиданий набралось 5,2 секунды — почти столько же, сколько у G1 ушло на полные сборки. Поколенческий ZGC на этой нагрузке пострадал ещё сильнее.

Отсюда два практических правила. Первое: конкурентному сборщику нужен запас heap над живыми данными, часто на десятки процентов больше, чем G1. Второе: мерить нужно задержку запросов целиком, а не паузы сборщика. Если ограничиться графиком пауз GC, allocation stall останется невидимым.

ZGC даёт паузы меньше миллисекунды всегда.

Только пока у него есть запас памяти. При тесном heap поток приложения ждёт в allocation stall — десятки и сотни миллисекунд, которых не видно в паузах сборщика.

Generational ZGC: поколения вернулись, чтобы реже обходить весь heap

Классический ZGC маркирует весь heap в каждом цикле. Для сервиса, где большинство объектов умирает молодыми, это лишняя работа: живые долгожители в old маркируются снова и снова. Generational ZGC (JEP 439, JDK 21) делит heap на young и old, как в теме Generations, и собирает young чаще: в логе появляются Minor Collection и Major Collection. Паузы остаются такими же короткими, потому что все фазы конкурентные.

Статус по версиям: в JDK 21 режим включается флагом -XX:+ZGenerational, в JDK 23 он стал режимом по умолчанию, а в JDK 24 классический режим удалили. Обычно поколенческий режим снижает затраты CPU и нужный запас памяти на типичных нагрузках. В нашем замере со средней жизнью объектов он уступил классическому, и это ещё один повод мерить, а не верить таблицам.

Где кончается эта тема? ZGC и Shenandoah решают одну проблему — длину пауз при большом heap и строгом SLA. Если SLA мягкий, а важнее пропускная способность при тесной памяти, G1 или даже Parallel могут оказаться лучше. Как выбирать — в теме Choosing a Collector, как читать логи — в GC Logs & Tuning.

  • ZGC и Shenandoah перемещают объекты параллельно с приложением, поэтому их паузы не зависят от размера heap и объёма живых данных.
  • Load barrier проверяет каждую прочитанную ссылку. Если объект переехал, барьер берёт новый адрес и чинит поле — самолечение.
  • ZGC хранит состояние ссылки в битах указателя. Shenandoah хранит адрес переадресации в заголовке старой копии объекта.
  • Цена низких пауз — запас памяти и CPU. При тесном heap пауза прячется в allocation stall, которого нет в логе safepoint.
  • Generational ZGC — режим по умолчанию с JDK 23. Но результат любого сборщика зависит от нагрузки: мерь на своей.

На собеседовании

Как ZGC добивается пауз меньше миллисекунды?

Он делает конкурентно всю работу, которая зависит от размера heap: маркировку, перемещение объектов и исправление ссылок. В паузах остаются только операции, не зависящие от объёма данных, — в первую очередь снять корни со стеков потоков. Перемещать объекты во время работы приложения позволяет load barrier: после каждого чтения ссылки он проверяет, не переехал ли объект, и при необходимости берёт новый адрес и чинит поле.

В замере урока паузы ZGC были по 0,05–0,15 мс против десятков миллисекунд у G1 на той же нагрузке.

  • Паузы остаются короткими, пока есть запас памяти. При тесном heap потоки ждут в allocation stall, и это не видно в метриках пауз.
  • Цена — барьер на каждое чтение ссылки и CPU для конкурентных потоков сборщика.
Почему G1 не может так же?

G1 копирует объекты только в паузе, когда приложение стоит, поэтому ему не нужен барьер на чтение. Зато пауза растёт с объёмом живых данных в выбранных регионах.

Что такое load barrier и colored pointers?

Load barrier — несколько инструкций, которые JIT вставляет после каждого чтения ссылки из поля. Они проверяют, актуален ли указатель. Если объект переехал, барьер берёт новый адрес из таблицы переадресации и записывает его обратно в поле, чтобы следующие чтения шли по быстрому пути.

Colored pointers — способ сделать эту проверку одной инструкцией: ZGC хранит служебные биты — цвет — прямо в указателе. Барьер сравнивает цвет с текущим хорошим, и если совпало, ничего не делает.

  • Классический ZGC отображал одну память по трём виртуальным адресам, по одному на цвет, и RSS в мониторинге мог выглядеть втрое больше реального. В поколенческом режиме этого нет.
Кто переносит объект, если поток приложения прочитал ссылку раньше сборщика?

Сам поток приложения, внутри барьера: он копирует объект, записывает переадресацию и возвращает новый адрес. Поэтому перемещение никогда не ждёт паузы.

Какую цену платят за низкие паузы?

Запасом памяти и CPU. Конкурентный сборщик освобождает память параллельно с тем, как приложение её занимает, поэтому heap нужен с запасом над живыми данными. Если запаса нет, поток приложения ждёт памяти — allocation stall. В замере урока при тесном heap ZGC набрал 5 секунд таких ожиданий за 10 секунд работы, хотя его паузы в логе safepoint были по долям миллисекунды.

Ещё барьер на каждое чтение ссылки и потоки сборщика, которые делят CPU с приложением. На машине с запасом ядер это почти незаметно, на полностью загруженном поде — заметно.

Команда перешла на ZGC и смотрит только метрику пауз GC: «всё отлично, 0,1 мс». Но p99 запросов вырос. Что проверить?

Allocation stall в логе -Xlog:gc: при нехватке heap потоки ждут памяти, и это не попадает в метрику пауз. Если stall есть — увеличить heap или снизить скорость выделения. И вообще смотреть на задержку запросов, а не только на паузы сборщика.

Чем Shenandoah отличается от ZGC?

Задача та же — конкурентное перемещение объектов, — отличаются детали. ZGC хранит состояние ссылки в битах указателя, Shenandoah — адрес переадресации в заголовке старой копии объекта. При нехватке памяти ZGC останавливает выделяющий поток в allocation stall, а Shenandoah сначала притормаживает выделение (pacing), а затем может сделать degenerated GC в паузе.

Практическая разница — доступность: Shenandoah нет в сборках Oracle JDK, но он есть в OpenJDK от Red Hat, Temurin, Corretto. Выбор между ними решает замер на своей нагрузке.

Что такое generational ZGC и зачем он?

Это ZGC с поколениями: heap делится на young и old, молодое поколение собирается чаще. Классический ZGC маркировал весь heap в каждом цикле, повторяя работу над долгоживущими объектами. Поколенческий режим снижает затраты CPU и нужный запас памяти на типичных нагрузках, паузы остаются такими же короткими.

В JDK 21 он включается флагом -XX:+ZGenerational, в JDK 23 стал режимом по умолчанию, в JDK 24 классический режим удалён.

Сервис на JDK 21 запускают с -XX:+UseZGC. В каком режиме работает ZGC и как это проверить?

В классическом, одноуровневом: в JDK 21 поколения нужно включать отдельным флагом. В логе -Xlog:gc+init будет строка Using legacy single-generation mode.
